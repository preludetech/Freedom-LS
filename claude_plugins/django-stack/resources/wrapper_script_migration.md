# Wrapper-script migration

> Duplicated into each plugin that ships wrapper scripts, because `${CLAUDE_PLUGIN_ROOT}` is
> per-plugin and a plugin here depends on no other plugin. Apart from the parameter table below the
> copies are identical — diff them when you change one.

| Parameter | Value in this copy |
|---|---|
| `<SCRIPTS_DIR>` | `.claude/ds/scripts/` |
| `<PLUGIN_DIR_NAME>` | `django-stack` |
| `<HEADER_NAME>` | `django-stack (ds)` |
| `<INIT_COMMAND>` | `ds:init` |

Rewrites **one** `.sh` file at a time, inside this plugin's own scripts directory, so a wrapper an
older init generated matches the current template — without regenerating it, and without touching a
single line the user wrote.

Never run this on a directory this plugin does not own, and never on a file outside `<SCRIPTS_DIR>`.

## Step A — classify the file (read only)

Read the whole file, then pick exactly one classification:

- **Managed** — the basename is one of this plugin's template names in
  `${CLAUDE_PLUGIN_ROOT}/templates/wrapper_scripts/` (excluding `claude.sh`, which the launcher
  procedure owns), **and** the file contains a line matching `^PLUGIN_DIR=`. Migrate it: Steps B–D.
- **User-authored** — anything else. This includes any file whose basename is not one of this
  plugin's template names, and any template-named file with no `PLUGIN_DIR=` line. **Make no edit at
  all.** Report: "`<path>` — left alone (not a generated wrapper)."

A basename belonging to *another* plugin's template set is User-authored here, and therefore
untouched. Each plugin migrates only its own.

## Step B — establish the protected region

Find the **first** line whose content is exactly `# === Project-specific setup ===` (no leading
whitespace).

- **If the marker is absent, the entire file is protected.** Make no edit. Report: "`<path>` has no
  `# === Project-specific setup ===` marker — left alone. Add the marker by hand if you want this
  file to track the template."
- Otherwise everything **from that line to end-of-file** is the **protected region**, and everything
  above it is the **managed region**. A file may contain the marker more than once (older wrappers
  do); only the **first** occurrence starts the protected region, and every later duplicate is inside
  it and therefore untouchable.

No rule below may read from, match in, insert into, delete from, or reorder the protected region.

## Step C — the seven rewrites (managed region only)

Apply each rule at most once. A rule that finds no match is a no-op, not an error. Each rule is a
whole-line or exact-token replacement; none is a free-form rewrite. Preserve every line, blank line,
and comment that no rule names, in its existing order.

1. **Path variable.** Rename `FLS_PATH` to `PLUGINS_ROOT` everywhere in the managed region — the
   `FLS_PATH="…"` assignment, every `$FLS_PATH` / `${FLS_PATH}` expansion, and every mention inside a
   comment. **Keep the assigned value byte-for-byte.**

2. **Header line.** If line 2 matches `^# (?<name>[A-Za-z0-9_.-]+)\.sh — Generated by .*$`, replace
   the **whole line** with:

   ```
   # <name>.sh — Generated by the <HEADER_NAME> plugin init
   ```

   `<name>` comes from the existing line, not the filename. If line 2 does not match, leave it —
   never invent a header.

3. **Path-variable prose block.** Find the maximal run of consecutive `#` lines in the managed region
   whose **first** line matches `^# [A-Z_]+ is set during `. Replace that entire run — however many
   lines it is — with these two:

   ```
   # PLUGINS_ROOT is set during `<INIT_COMMAND>` to the relative path from the project root
   # to the checkout that holds `claude_plugins/` (default "." — the project root itself).
   ```

   Match on the run itself, never gated on the header line: a partially-migrated script carries a
   correct header and a stale block, and a header-gated rule skips exactly those files.

4. **`PLUGIN_DIR` target.** If a line matches `^PLUGIN_DIR=`, replace the **whole line** with:

   ```bash
   PLUGIN_DIR="$PROJECT_ROOT/$PLUGINS_ROOT/claude_plugins/<PLUGIN_DIR_NAME>"
   ```

   Apply this whenever the existing value differs, whatever it currently points at. This is the rule
   that stops a migrated wrapper from invoking a directory that no longer exists.

5. **Base-setup marker.** Replace any line matching `^# === .*[Bb]ase setup ===$` — case-insensitive
   on `base`, so it matches both a legacy `# === FLS base setup ===` and an already-migrated
   `# === Base setup ===` — with:

   ```
   # === Base setup ===
   ```

6. **Placeholder.** Replace every literal `__PLUGINS_ROOT__` with the `PLUGINS_ROOT` value resolved
   in preflight.

7. **Value check — report, never overwrite.** After rules 1 and 6, if a `PLUGINS_ROOT="…"` assignment
   exists in the managed region and its value differs from the preflight-resolved value, **leave it
   as it is** and report the difference as an outstanding user decision — a deliberately-set value is
   not a defect. If no `PLUGINS_ROOT=` assignment exists at all, insert
   `PLUGINS_ROOT="<resolved value>"` on its own line immediately above the `SCRIPT_DIR=` line, or if
   there is none, immediately above the `PLUGIN_DIR=` line.

## Step D — mode and reporting

1. If the file is not executable, `chmod +x` it. This is the only place this command changes a mode
   bit on a file it did not create.
2. Report per file which of rules 1–7 fired and which found nothing. A file where nothing fired is
   reported "already current".

## What this procedure never does

Never writes below the first `# === Project-specific setup ===` line. Never deletes, moves, renames,
or truncates a file. Never regenerates a file from a template. Never touches a file outside
`<SCRIPTS_DIR>`, a file Step A classified User-authored, or a file Step B found no marker in.

## Appendix — the "is this wrapper customised?" test

Used by any step deciding whether a wrapper is disposable. A wrapper is **pristine** only when all
three hold:

1. **Managed region.** Everything above the first `# === Project-specific setup ===` line is either
   byte-identical to the matching shipped template's managed region with `__PLUGINS_ROOT__`
   substituted, **or** differs from it only in ways rules 1–6 above would themselves produce
   (pristine-but-stale). *Any* other difference makes it **customised** — an added
   `set -euo pipefail`, an edited port range, an extra `export`, a reordered line, an added comment,
   a `PLUGINS_ROOT` value the user chose.
2. **Protected region.** The first marker line onward is exactly these two lines and nothing else:

   ```
   # === Project-specific setup ===
   # Add your implementation-specific steps below:
   ```

   Extra commands, an extra blank line, a second marker - any of these makes it **customised**.
   Compare the text ignoring a single trailing newline at end-of-file: a file that ends with one
   splits into a third, empty element, and a naive equality test would mark every wrapper customised
   and make nothing ever deletable.
3. **Clean in git.** `git status --porcelain -- <path>` is empty. Uncommitted work cannot be
   recovered from git, so it is never a delete candidate.

**Which template is "the matching shipped template".** The one whose basename matches, in the
`templates/wrapper_scripts/` of **whichever plugin owns that basename** — found by looking across
`<PLUGINS_ROOT>/claude_plugins/*/templates/wrapper_scripts/`. That is usually this plugin, but a
legacy directory can hold another plugin's wrapper, and judging it against this plugin's parameters
would compare it to a file that does not exist and never match. **Apply rules 1-6 with that owner's
parameter table too**, not this copy's - otherwise rule 4 emits this plugin's `PLUGIN_DIR` target, the
comparison can never succeed, and every foreign wrapper is wrongly judged customised. A basename no plugin ships has no
template, so it can never be pristine: it is the user's own file, and the answer is always
**customised**.

**A customised wrapper is never deleted and never overwritten, on any branch of any step.**
