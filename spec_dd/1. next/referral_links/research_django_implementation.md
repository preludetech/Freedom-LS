response mechanics and the FLS conventions it must follow. Assumes `referal_tracking`

## 1. URL routing

`config/urls.py:45-68` is the root URLconf. Relevant entries, in registration order:

```
path("health/", include("freedom_ls.health.urls"))          # config/urls.py:46
path(ADMIN_URL, admin.site.urls)                              # :47
path("robots.txt", robots_txt, name="robots_txt")             # :49
path("sitemap.xml", sitemap, ...)                              # :50-55
path("educator/", include("freedom_ls.educator_interface.urls"))  # :60
path("", include("freedom_ls.deployment.urls"))                # :61
path("accounts/", include("allauth.urls"))                     # :62
path("accounts/", include("freedom_ls.accounts.urls"))         # :63
path("", include("freedom_ls.learner_interface.urls"))         # :64
path("applications/", include("freedom_ls.course_applications.urls"))  # :65
path("interest/", include("freedom_ls.course_interest.urls"))  # :66
```

**`learner_interface.urls` is not a catch-all.** It is a plain, fully-enumerated pattern list
(`freedom_ls/learner_interface/urls.py:7-74`): `""` (dashboard), `courses/`, `courses/<slug>/detail/`,
`courses/<slug>/`, `courses/<slug>/access/`, `courses/<slug>/<int:index>/` and four more paths all
under `courses/<slug:course_slug>/...`. Nothing in it matches a bare `go/<anything>` or `d/<anything>`
— Django's URL resolver tries patterns in list order and only the patterns that structurally match a
path are candidates, so `learner_interface` being mounted at `""` does not intercept `/go/mrbeast` or
`/d/CODE`; it simply has no pattern shaped like either. `freedom_ls.deployment.urls` is also mounted at
`""` (`config/urls.py:61`) and is even smaller — one path, `sentry-debug/`
(`freedom_ls/deployment/urls.py:8`).

**No existing collision.** Grepped every app's `urls.py` for a `path("go/…")` or `path("d/…")` pattern
— none exists. `freedom_ls/health/urls.py:8-9` uses `liveness/`/`readiness/`; nothing else in the tree
touches a top-level `go` or `d` segment.

**Where the new routes must be registered.** Any `path("go/", include(...))` and `path("d/", include(...))`
(or a single `include()` covering both, see §2) added to `config/urls.py` is reachable regardless of
where in the list it sits, because no other pattern shares the prefix. Convention in this file,
though, is to put single-purpose top-level mounts (`health/`, `robots.txt`, `sitemap.xml`) near the
top, before the `""`-mounted apps — follow that placement rather than appending at the bottom, so a
future top-level pattern added to `learner_interface` or `deployment` can never silently shadow it.

**FLS URL conventions the new app's `urls.py` must follow** (`CLAUDE.md`, and every existing
`urls.py` — `freedom_ls/learner_interface/urls.py:5`, `freedom_ls/health/urls.py:5`,
`freedom_ls/deployment/urls.py:5`):
- `app_name = "..."` is mandatory — every app's `urls.py` declares one.
- URL *names* are snake_case (`name="course_detail"`, `name="dashboard"`).
- URL *paths* are kebab-case, though the two paths this feature needs (`go/<slug>`, `d/<code>`) are
  single ASCII tokens with no internal casing question — the slug/code values themselves are the
  visible content, not multi-word path segments.

**How a downstream project wires URLs.** Every app is `include()`-d individually in `config/urls.py`
with an explicit mount prefix chosen by the project — there is no dynamic app-discovery or
auto-mounting mechanism. A downstream project that installs FLS and wants these routes copies the
same `path("go/", include("freedom_ls.<app>.urls"))` pattern into its own root URLconf (or, if it
already `include()`s FLS's `config.urls` wholesale, gets them for free). Nothing here is FLS-specific
beyond the pattern already used by every other app.

## 2. Which app this belongs in

`docs/app_structure.md` is generated by `/app_map` and is authoritative for the dependency graph
(`docs/app_structure.md:3-11`). Relevant excerpts:

- `organisations --> base`, `organisations --> site_aware_models` (`:121-122`) — `organisations` sits
  low in the graph and is depended on by many apps (`deployment`, `educator_interface`, `learner_management`,
  `reports`, `qa_helpers`, …), but itself imports almost nothing.
- No `referral_tracking` (nor `referal_tracking`) node exists yet in this file, because that work has
  not merged (confirmed above — no code in its worktree).

**The `referal_tracking` spec commits to a specific app name and shape**, which this feature should
join rather than duplicate:

- App: `freedom_ls/referral_tracking`, label `freedom_ls_referral_tracking`
  (`referal_tracking:spec_dd/2. in progress/referal_tracking/1. spec.md:94-105`).
- Edge: `accounts --> referral_tracking` is the *only* new edge that spec adds (`1. spec.md:48-50`,
  `:464-465`) — the models FK to `settings.AUTH_USER_MODEL` as a string precisely so the app itself
  imports nothing from `accounts`, keeping the edge one-directional.
- The deferred work section of the idea explicitly earmarks *referrer codes for partner
  organisations* — a code "held on `Organisation` and checked at landing" — as the next spec on top of
  this app, and says two decisions from it must survive into that later spec: the row must store both
  the code it saw and the `Organisation` it resolved to, and issuing a code to an individual referrer
  needs its own `Organisation` row (`idea.md:178-189`).

That deferred item is a near-exact description of the `/go/{slug}` half of *this* feature (referrer →
`Organisation`). **This strongly suggests the redirect model belongs inside
`freedom_ls/referral_tracking`** (once it exists) rather than in a new app or in `organisations`
itself — reasons:

- `organisations` is deliberately kept dependency-light (`organisations --> base`,
  `organisations --> site_aware_models` only, `docs/app_structure.md:121-122`) and is imported by many
  apps above it; adding a redirect/hit-logging model there would put marketing-redirect concerns on
  every app that already depends on `organisations` for tenancy reasons alone. `OrganisationAdmin`
  (`freedom_ls/organisations/admin.py:30`) already documents the one sanctioned way other apps attach
  themselves to an `Organisation`'s admin page — `ORGANISATION_SUMMARIES` and `get_inlines`
  (`admin.py:25,54-64`) — precisely so `organisations` never has to import the contributing app. A new
  redirect app would use that same seam (a summary callback) rather than a cross-import, if it wants
  a link back from the `Organisation` change page.
- `referral_tracking` already owns "an opaque, staff-issued, admin-only, read-mostly tracking
  identifier that resolves to campaign/partner attribution" as its whole domain, already owns the
  `advert_code` vocabulary (`1. spec.md:271-278`) this feature's idea reuses verbatim for `/d/{CODE}`,
  and already has the settings/config/admin/testing scaffolding this feature needs a smaller version of.
- Putting the redirect model in a new third app would add a *second* new edge into `organisations`
  (for the `/go/` entry's optional `Organisation` FK) and would duplicate `referral_tracking`'s
  `advert_code` concept under a different name — exactly what the domain glossary warns against
  (coining a second noun for a concept that already has one).

**Dependency-graph consequence if placed in `referral_tracking`:** one new edge,
`referral_tracking --> organisations`, for the optional FK from a `/go/` entry to `Organisation`. That
is a *second* edge added on top of the `accounts --> referral_tracking` edge the `referal_tracking`
spec already commits to (`1. spec.md:48`) — `docs/app_structure.md` would need regenerating
(`/app_map`) and this new edge called out for review before code is written, per that file's own rule
(`docs/app_structure.md:5`). I could not find any existing `organisations --> referral_tracking` or
reverse edge in the current `docs/app_structure.md`, so this edge is net-new either way; placing the
model in `referral_tracking` rather than a fresh app avoids also introducing a third app's worth of
boilerplate (config, admin base classes, test conventions) for what the idea already frames as "one
model covers both routes."

**What I could not establish:** whether the SDD process intends this feature to literally extend the
`referral_tracking` app in the same PR that implements it, or to land as its own app with an explicit
`referral_tracking`-facing FK once that app exists. That is a spec-level decision, not something the
code answers — flagging it rather than picking for the spec author.

## 3. Site-awareness

`freedom_ls/site_aware_models/models.py`:

- `get_cached_site(request)` (`:36-82`) is how *any* code — view, middleware, admin — resolves the
  current `Site` for an unauthenticated, public request. It reads `config.FORCE_SITE_NAME` first
  (`:50-60`), then falls back to `get_current_site(request)` (Django's own Host-header resolution,
  `:63`), catching `DisallowedHost` and returning `UnknownSite()` — a `RequestSite` look-alike that is
  **not** a `Site` row (`:20-30`) — rather than raising, specifically so a request with a rejected Host
  still renders Django's 400 page instead of 500ing (`:64-71`). No login or session state is involved
  anywhere in this path — it works identically for an anonymous visitor hitting `/go/mrbeast`.
- `SiteAwareManager.get_queryset()` (`:117-128`) filters automatically **only when a request is
  present on the thread-local** (`_thread_locals.request`, set by `CurrentSiteMiddleware`,
  `freedom_ls/site_aware_models/middleware.py:26-36`) and only when `get_cached_site` resolves to a
  real `Site` row — an `UnknownSite` falls through to an *unfiltered* queryset (`:123-127`, comment
  explains this is safe because only the 400 handler renders such a request). `CurrentSiteMiddleware`
  is unconditional — it runs on every request regardless of auth state
  (`config/settings_base.py:159`, before `AccountMiddleware`) — so a plain public view under `/go/` or
  `/d/` sees exactly the same automatic site filtering any authenticated view gets, provided the view
  is reached through the normal middleware chain (i.e. not something that bypasses it).
- **Slug-uniqueness scope.** Every existing site-scoped slug/code uniqueness constraint in FLS is
  `UniqueConstraint(fields=["site", "<field>"], ...)` — see `Organisation`'s
  `unique_organisation_slug_per_site` and `unique_organisation_name_per_site`
  (`freedom_ls/organisations/models.py:96-102`). A redirect entry's slug (for `/go/`) or code (for
  `/d/`) should follow the identical shape: unique per `(site, slug)`, not globally unique. **What two
  sites wanting the same `/go/` slug means concretely:** since the view resolves the entry by
  `(site, slug)` — the current request's `Site`, taken from `get_cached_site(request)`, filtered
  through `SiteAwareManager` exactly as `Organisation` lookups are — two different `Site` rows can each
  own a `/go/mrbeast` entry pointing at two different targets with no collision, exactly as two sites
  can each have an `Organisation` named "Acme". This is consistent with the tenancy model documented in
  the domain glossary (`Site` is the isolation boundary; `docs/product/multi-tenancy-and-isolation.md`
  is cited there, `.claude/skills/domain-glossary/SKILL.md:126-127`) — I did not re-read that product
  doc directly, but the `Organisation` precedent in code is unambiguous on the scoping pattern.
- **Base class choice.** `SiteAwareModel` (`site_aware_models/models.py:160-165`) — UUID pk + site FK,
  the same base `Organisation` uses (`organisations/models.py:58`) — is the fit unless there is a
  reason to want a non-UUID pk, which nothing in the idea suggests.

## 4. View vs middleware

**A plain view behind two `path()` patterns is the right shape, not middleware.** Reasons, by
comparison with the two things in FLS closest to "match a fixed prefix and act":

- `CurrentSiteMiddleware` and the (unshipped) `AttributionCaptureMiddleware`
  (`referal_tracking:spec_dd/.../1. spec.md:316-345`) both run on **every** request and do work
  conditional on request shape (tracked query params present, etc.) — they are middleware because
  their job is "look at everything, act on a subset." A redirect for `/go/{slug}` and `/d/{CODE}` is
  the opposite: it only ever needs to run for exactly two fixed prefixes, which is precisely what
  Django's URL resolver already exists to dispatch on. Writing it as middleware would mean re-doing
  path-prefix matching by hand inside `__call__`, for no benefit — every other single-purpose,
  fixed-path endpoint in this codebase (`robots.txt`, `sentry-debug/`, `liveness/`) is a plain
  function view registered via `path()`, not middleware.
- Middleware also runs before Django resolves a URL match, so a middleware-based redirect would still
  need its own routing logic and would sit outside the URL-name/`reverse()` system entirely — no
  `reverse("go_redirect", kwargs={"slug": ...})` for the admin's own change-list "view on site" link,
  no automatic 404 for a request shaped like `/go/` with no slug. A view gets both for free.

**`django.contrib.redirects` (`RedirectFallbackMiddleware`) is not installed and not a fit.**
Confirmed: `INSTALLED_APPS` in `config/settings_base.py:72-138` has no `django.contrib.redirects`
entry, and `MIDDLEWARE` (`:148-164`) has no `RedirectFallbackMiddleware`. Even if it were added, its
design is wrong for this feature on three counts: (1) it is a **fallback** that only runs after every
URL pattern has failed to match and produced a 404 — it cannot coexist with a real `path("go/<slug>/",
...)` pattern doing the actual redirect, the two are alternative designs, not complementary; (2) its
`Redirect` model has no per-site scoping hook beyond `django.contrib.sites`' own `SITE_ID`-based
single-current-site model, not FLS's per-request multi-tenant resolution via `get_cached_site`; (3) it
has no hit-logging, no query-parameter appending, and no distinction between the two route shapes this
feature needs — it would have to be bypassed or monkey-patched to do any of what this feature actually
requires, at which point it is providing nothing.

## 5. Response mechanics

- **`HttpResponseRedirect` (302), not `HttpResponsePermanentRedirect` (301).** A 301 is
  browser-and-CDN cached indefinitely by default and is very hard to invalidate if a marketing entry's
  `target_url` is later changed — every hit thereafter would need to log, which a cached 301 makes
  impossible (the browser never re-requests). Since this feature's entire point is "log every hit," a
  302 is the only response code compatible with that requirement; a 301 would make most hits invisible
  to the server after the first.
- **`Cache-Control` must actively forbid caching**, for the same reason: `django.middleware.common.CommonMiddleware`
  is installed (`config/settings_base.py:153`) but does not set cache headers on redirects by default —
  nothing in `config/` sets a project-wide `Cache-Control` for arbitrary views (grepped
  `config/settings_base.py` and `config/settings_prod.py`: no `CACHE_MIDDLEWARE_*` setting, `CACHES`
  in `settings_prod.py:86` is `fls_defaults.DATABASE_CACHES` — the low-level cache framework used
  elsewhere, e.g. for axes' rate limiting, not an HTTP response cache). The view must therefore set its
  own header explicitly — `django.utils.cache.patch_cache_control(response, private=True, no_store=True)`
  is the idiom the `referal_tracking` spec already uses for exactly this reason on its own
  cookie-minting middleware response (`referal_tracking:spec_dd/.../1. spec.md:339`), and is the
  pattern to reuse here rather than inventing a second one.
- **`Vary` is not the mechanism that matters here** (unlike the attribution cookie case, which varies
  the response by `Cookie` because two visitors get two different cookies from the same URL). A
  redirect response is identical for every visitor hitting the same slug — `Vary` has nothing to key
  on. `Cache-Control: private, no-store` alone is the correct and sufficient header.
- **`APPEND_SLASH`.** Not overridden anywhere in `config/` (grepped both `settings_base.py` and
  `settings_prod.py`; no matches project-wide outside an unrelated Playwright screenshot fixture) —
  Django's default (`True`) applies. `APPEND_SLASH` only fires when a request path has **no** matching
  pattern and appending a `/` **would** match one. If the URL pattern is registered without a trailing
  slash (`path("go/<slug:slug>", view)`), a request to `/go/mrbeast` matches directly and
  `CommonMiddleware` never engages `APPEND_SLASH` at all — no extra redirect hop, no extra hit logged.
  If instead the pattern is registered *with* a trailing slash (`path("go/<slug:slug>/", view)`,
  matching the convention used by nearly every other FLS path — `courses/`, `liveness/`, `health/`),
  a request to the trailing-slash-less `/go/mrbeast` (the natural form for a printed/spoken URL) would
  **not** match, and `APPEND_SLASH` would issue its own 301 to `/go/mrbeast/` before the redirect view
  ever runs — a second network round trip and a lost opportunity to log the original hit if the client
  does not follow it. **This is a real decision the spec needs to make explicitly**: either drop the
  trailing slash on these two patterns specifically (breaking the house convention, justified by the
  marketing-URL use case), or accept the extra 301 hop. I could not find any existing FLS URL pattern
  that omits the trailing slash deliberately for this reason — `config/urls.py:49` (`robots.txt`) and
  `:52` (`sitemap.xml`) omit it only because those are fixed, non-parameterised paths mirroring
  external convention (robots.txt, sitemap.xml are always exactly those strings), not a precedent for
  parameterised paths.
- **No CDN or edge cache found in the repo that would swallow a 302.** `config/settings_prod.py:17`
  references a "Cloudflare tunnel" only in a CSRF-trusted-origins comment (TLS termination), and
  `CACHES` (`:86`) is the low-level Django cache framework, not an HTTP response cache in front of the
  app. I could not find deployment docs describing an edge cache layer within this repo — if one
  exists, it would live in infrastructure config outside this codebase (not something `Read`/`Grep`
  here can confirm or rule out). The explicit `Cache-Control: private, no-store` above is exactly the
  belt-and-braces defence the `referal_tracking` spec calls for against "FLS ships no cache middleware,
  but it is installed into projects that may front it with a CDN"
  (`referal_tracking:spec_dd/.../1. spec.md:343-344`) — the same reasoning applies here.

## 6. Safely building the target URL

No existing FLS helper does this — grepped the whole `freedom_ls/` tree for `url_has_allowed_host_and_scheme`,
`build_absolute_uri`, `urlencode(`, `urlsplit`, `urlunsplit`:

- `url_has_allowed_host_and_scheme` is used in exactly two places, both for **redirecting the current
  visitor back into FLS itself** after an action, not for building an outbound URL:
  `freedom_ls/accounts/views.py:60-68` (`_safe_post_completion_redirect`, validates a `next` GET/POST
  param against `request.get_host()` before `redirect()`-ing to it) and referenced in a docstring at
  `freedom_ls/accounts/utils.py:126` (`redirect_to_auth`, which explicitly says a `next_url` "must
  already be built server-side... passing through a next taken from user input would open a redirect;
  validate with `url_has_allowed_host_and_scheme` first if that ever changes").
- `build_absolute_uri` appears in `freedom_ls/learner_interface/views.py`,
  `freedom_ls/accounts/utils.py`, `freedom_ls/accounts/views.py`, `freedom_ls/reports/render.py` and
  others — all building an absolute URL *into* FLS (e.g. `config/views.py:15`,
  `sitemap_url = request.build_absolute_uri(reverse("sitemap"))`), never appending tracking params to
  an external, operator-supplied URL.
- No use of `urlencode`/`urlsplit`/`urlunsplit` anywhere in `freedom_ls/`.

**`url_has_allowed_host_and_scheme` does not apply to this feature's core case, and that is worth
stating precisely.** That function exists to stop an *attacker-supplied* URL (typically a `next=`
query param) from redirecting a victim off-site — it validates against `request.get_host()`, i.e. it
only ever approves same-host targets. This feature's `target_url` is the **opposite shape**: an
operator-supplied, admin-configured field whose entire purpose is to point *off-site* (a landing page,
a partner's site, a social profile) — running it through `url_has_allowed_host_and_scheme` would reject
every legitimate use of the feature. The open-redirect risk here is a *different* one: whether an
attacker can control which `target_url` a slug resolves to. Since `target_url` is set only in the
Django admin by staff (matching every other FLS admin-only field pattern — `Organisation.name`,
`SiteSignupPolicy` fields, etc.), not from any user-facing input, there is no attacker-controlled input
into `target_url` itself for this feature as scoped — the redirect is only as safe as the admin's own
access control, which is the standard FLS admin trust boundary, not a new one this feature introduces.
**What does need validating** is that `target_url` is a well-formed absolute URL at write time
(`URLField` with its default validators, or a custom validator restricting scheme to `http`/`https` to
rule out a staff member accidentally saving a `javascript:` URL) — a model-level concern, not a
redirect-time one.

**Building the redirect URL correctly.** The idea's decision ("appends tracking parameters to the
target URL; an existing attribution middleware... picks them up") means the view must merge FLS's own
tracking query params into whatever query string `target_url` may already carry, without duplicating
or clobbering. The stdlib-correct approach, absent an existing FLS helper:

```python
from urllib.parse import parse_qsl, urlencode, urlsplit, urlunsplit

def append_tracking_params(target_url: str, tracking: dict[str, str]) -> str:
    parts = urlsplit(target_url)
    query = parse_qsl(parts.query, keep_blank_values=True)
    query.extend(tracking.items())  # appended, not merged — last-value-wins is Django's own QueryDict
                                      # convention (referal_tracking spec, §5.4) but here duplicate
                                      # keys are a target_url-author error, not attacker input, since
                                      # target_url is admin-set
    new_query = urlencode(query)
    return urlunsplit(parts._replace(query=new_query))
```

`urlsplit`/`urlunsplit` (not `urlparse`/`urlunparse`) is the correct pair for round-tripping a URL
with a query string intact — `urlparse` additionally splits off `params` (the rarely-used `;`-segment
of RFC 3986), which is irrelevant here and better left untouched by not using that function at all.
`parse_qsl(..., keep_blank_values=True)` preserves a target URL's existing `?foo=` (blank value)
rather than silently dropping it, matching this feature's "never corrupt the operator's own target"
requirement. This exact pattern (`urlsplit`/`parse_qsl`/`urlencode`/`urlunsplit`) has no existing FLS
precedent to point to — it would be new code, following stdlib idiom rather than an in-repo one.

## 7. Model, admin and migration conventions FLS already has

Read `freedom_ls/organisations/models.py` and `freedom_ls/organisations/admin.py` in full as the house
pattern (they are the app named as the pattern to follow in the brief, and the most complete
`SiteAwareModel` + `SiteAwareModelAdmin` example short of `LegalConsent`):

- **Base classes.** `class Organisation(SiteAwareModel, TimestampedModel):`
  (`organisations/models.py:58`) — `SiteAwareModel` gives the UUID pk + site FK + auto-filtering
  manager (`site_aware_models/models.py:160-165`); `TimestampedModel` gives `created_at`/`updated_at`
  (`:167-179`), composed separately "so it also reaches `accounts.User`... and models that are
  deliberately not site-aware" (`:171-173`). A redirect entry model should compose the same two bases,
  in the same order, unless there is a stated reason not to.
- **Admin base and `SiteAwareModelAdmin` requirement.** `SiteAwareModelAdmin`
  (`site_aware_models/admin.py:15-18`) is `unfold.admin.ModelAdmin` with `exclude = ["site"]` — the
  site field is never exposed in a form because it is set automatically
  (`SiteAwareModelBase.save`/`full_clean`, `site_aware_models/models.py:139-157`, reading the
  thread-local). `GuardedSiteAwareModelAdmin` (`admin.py:21-31`) adds guardian's per-object permission
  UI on top — `OrganisationAdmin` uses this heavier variant because organisations get per-object
  guardian grants elsewhere in the codebase (the domain glossary's "grant" entry,
  `.claude/skills/domain-glossary/SKILL.md:138`); a redirect entry has no analogous need, so plain
  `SiteAwareModelAdmin` is the right base, not the guarded one.
- **`Organisation.slug` is NOT auto-derived in `Model.save()`.** This contradicts what the
  `referal_tracking` idea's slug write-up implies at a glance — reading the actual code:
  `Organisation.save()` (`organisations/models.py:116-134`) only handles logo-file cleanup; it never
  touches `slug`. The slug is instead assigned in **`OrganisationAdmin.save_model`**
  (`organisations/admin.py:84-98`): `if not obj.slug: ... obj.slug = get_unique_slug(Organisation,
  site, slug_base_for(obj.name), existing_uuid=str(obj.pk))`, called only when the admin form is
  submitted with no slug already present. The admin `ModelForm` (`OrganisationAdminForm`,
  `organisations/forms.py:12-36`) explicitly excludes `slug` from its `fields` and documents why: "read-only
  in the admin and assigned by `OrganisationAdmin.save_model`... validating
  `unique_organisation_slug_per_site` here would reject names the admin is able to accommodate"
  (`forms.py:16-19`). So: **the derivation lives in the admin layer, not the model layer**, and any new
  slug-bearing model following this pattern should put the same `if not obj.slug: obj.slug =
  get_unique_slug(...)` logic in its own `ModelAdmin.save_model`, reusing
  `freedom_ls.site_aware_models.slugs.get_unique_slug` and `slug_base_for`
  (`site_aware_models/slugs.py:19-29,32-67`) rather than reimplementing slug uniqueness.
  `get_unique_slug` already does the `(site, slug)` uniqueness loop with `-2`, `-3`, … suffixes
  (`slugs.py:38-67`), reading through `model_class._base_manager` specifically to avoid the ambient
  site-thread-local double-filtering it warns about (`:53-56`) — reuse it verbatim rather than
  reimplementing.

  **Caveat for this feature:** `Organisation.slug` is *derived from the name*, appropriate because a
  slug there is a courtesy identifier for something with a human name. A `/go/{slug}` redirect entry's
  slug is different in kind — it is very likely the **primary product of the admin form** (staff
  choose `mrbeast` deliberately, it is not derived from anything), so "derive it from another field on
  save" is probably the wrong shape here even though `get_unique_slug`/`slug_base_for` are still the
  right *uniqueness* helpers to reuse once a candidate slug is decided (staff-typed or
  auto-suggested). This is a spec-level decision, not a code fact — flagging it rather than assuming
  the `Organisation` pattern transfers wholesale.

- **Read-only admin.** `LegalConsentAdmin` is the example the brief points to. It is at
  `freedom_ls/accounts/admin.py:64` (`class LegalConsentAdmin(SiteAwareModelAdmin):`, `list_display`
  `:65-71`, `readonly_fields` `:74`ff, then `has_add_permission`/`has_change_permission`/
  `has_delete_permission` all returning `False`, `:84-91`). This is the pattern to follow for the
  **hit log** half of this feature (if hits get their own model/admin row rather than only a counter) —
  hits are write-once, append-only, and should never be editable through the admin. The redirect
  *entry* itself (slug/code/target_url/active) is different: it needs `has_add_permission` and
  `has_change_permission` to stay `True` (staff create and edit these), only `slug` (once set) arguably
  wanting the same read-only-after-creation treatment `Organisation.slug` gets.
- **Migration conventions.** Not separately verified beyond `CLAUDE.md`'s stated rule (`always run
  makemigrations after model changes`; `never edit existing migration files`) — no redirect-specific
  migration exists yet to inspect, since the model does not exist.

## 8. Per-app settings

`freedom_ls/organisations/config.py:1-14` is the pattern:

```python
class OrganisationsConfig(AppSettings):
    ORGANISATION_LOGO_STORAGE_ALIAS: str
    declared_settings = {"ORGANISATION_LOGO_STORAGE_ALIAS": Setting(default="public")}

config = OrganisationsConfig()
```

`AppSettings`/`Setting` (`freedom_ls/base/app_settings.py:11-59`) is the shared base: `config.NAME`
reads the project's Django setting if present, else the declared default; a `required=True` setting
raises `ImproperlyConfigured` lazily on first read if the project never set it (`:40-44`). The
`app-settings` skill (`claude_plugins/fls-dev/skills/app-settings/SKILL.md:11-13`) confirms this is the
one shared pattern every app — FLS's own or a downstream addition — should use, importing from
`freedom_ls.base.app_settings`.

**Yes, the two path prefixes should be settings.** `/go/` and `/d/` are exactly the kind of
project-specific customisation point `AppSettings` exists for — a downstream project may already use
`/go/` for something else, or prefer a branded prefix. Following the `OrganisationsConfig`/
`CourseAccessConfig` shape (`claude_plugins/fls-dev/skills/app-settings/SKILL.md:19-35`):

```python
# freedom_ls/<app>/config.py
class <App>Config(AppSettings):
    REFERRAL_REDIRECT_PREFIX: str
    ADVERT_REDIRECT_PREFIX: str
    declared_settings = {
        "REFERRAL_REDIRECT_PREFIX": Setting(default="go"),
        "ADVERT_REDIRECT_PREFIX": Setting(default="d"),
    }
```

One wrinkle worth flagging: unlike `ORGANISATION_LOGO_STORAGE_ALIAS` (read at call time, deep inside a
function), a URL *prefix* setting has to be read at **import time**, inside `config/urls.py` or the
app's own `urls.py`, because `path()` patterns are built once at URL-conf load — `AppSettings.__getattr__`
supports this (it just reads `django.conf.settings` each call, nothing async or request-scoped about
it), but it means the setting must be readable before `django.setup()`'s app registry is guaranteed
populated in every entry point; every other `AppSettings` reader in this codebase is read from inside a
function body executed per-request, not at URLconf import time — I found no existing precedent for an
`AppSettings` value driving a `path()` prefix, so this would be new usage of an existing pattern rather
than a well-trodden one. Worth testing that `manage.py` management commands and `pytest` collection
both import cleanly with a non-default prefix set.

## 9. Testing

`claude_plugins/fls-dev/skills/testing/SKILL.md` (FLS overlay) plus `Skill(ds:testing)` (not read here,
per the brief's scope — this file only covers the FLS-specific overlay):

- **Test file path:** `freedom_ls/<app_name>/tests/test_<module>.py` (`testing/SKILL.md:14-15`).
- **`mock_site_context` fixture is mandatory** for any test touching a site-aware model — "never
  manually set `site`" (`testing/SKILL.md:19`). A redirect-entry model is `SiteAwareModel`, so every
  test creating one, and every test hitting the `/go/`/`/d/` view (which resolves site via
  `get_cached_site`), needs this fixture.
- **Marker taxonomy** (`testing/SKILL.md:32-42`): unmarked = portable (the default, and almost
  certainly right for this feature's whole test suite — a redirect view has no FLS-branding
  dependency); `playwright` for browser tests (not needed here — this is server-side response-code and
  header assertions, not client-rendered UI); `fls_internal` only for tests genuinely coupled to FLS's
  own repo/brand/demo state (not applicable); `ci_only`/`weasyprint` clearly not applicable. Default
  expectation: this feature's tests ship unmarked.
- **Collection safety** (`testing/SKILL.md:50-62`) matters only if this feature's app is optional in
  `INSTALLED_APPS` for a downstream project — not yet decided at spec level; note it as a pattern to
  reach for if the app ends up optional, following the `course_applications` example given there.
- The `referal_tracking` spec's own testing section (`1. spec.md:428-460`) is the closest sibling
  precedent for this exact kind of feature: `django_assert_num_queries`, `time_machine` for frozen
  time, plain `django.test.Client`, and the project-root `mock_site_context`/`site` fixtures
  (`freedom_ls/conftest.py:135`, `:101` per that spec — not independently re-read here). Its "GET
  carrying param → cookie set" / "no cookie → no query" pairing (`1. spec.md:435-439`) is a direct
  template for this feature's own "GET on a real slug → 302 + one hit logged" / "GET on an unknown slug
  → 404, zero writes beyond whatever hit-logging failure handling is chosen" test pairs.
