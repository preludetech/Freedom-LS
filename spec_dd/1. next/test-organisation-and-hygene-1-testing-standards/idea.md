# The testing standard: file layout, cross-app imports, conftest/fixture/factory layering

Spec 1 of 15 in the Test organisation and hygiene effort. Read the "Test organisation and hygiene"
section of `spec_dd/1. next/roadmap.md` first: it holds the build order, what this spec depends on
and may run beside, the decisions already taken and the assumptions every idea in the effort makes.

## What

Write the two hygiene rules, and the conftest/fixture/factory layering that goes with them, into
`ds:testing` (`claude_plugins/django-stack/skills/testing/SKILL.md`,
`claude_plugins/django-stack/resources/testing.md`, `resources/factory_boy.md`). `fls-dev:testing`
gets a one-line pointer at the generic rules plus whatever FLS-specific instance is worth naming
(its existing "Collection safety for optional apps" FLS example, in particular).

This spec writes the standard only. It changes no test code anywhere in the repo, adds no
pre-commit or CI check, and touches no SDD command. Every downstream spec cites this one.

## Why

Two rules exist in the source idea, but no skill states either of them. `ds:testing` currently
says only "Test files: `<app>/tests/test_<module>.py`" and nothing about mirroring the app's
internal module hierarchy, nothing about cross-app test dependencies. The existing
conftest/fixture/factory guidance also has real gaps (no placement rule, no scope/idempotency
rule) and one factual inconsistency (the "Collection safety" example doesn't call the helper the
codebase actually uses). Every other spec in this effort needs one written, correct source of
truth to cite: the workflow wiring, the enforcement checks, and twelve cleanup specs. This spec
is that source, and runs first so nothing downstream reopens it.

## What is settled

**Rule 1. Mirroring.** State the convention the repo already uses almost everywhere, not a new
one: `freedom_ls/<app>/<module>.py` → `freedom_ls/<app>/tests/test_<module>.py`. This is a flat
`tests/` package inside the app, one test file per production module, not a top-level mirrored tree
and not a colocated `foo_test.py`. A subpackage is mirrored as a test subdirectory:
`freedom_ls/<app>/templatetags/content_tags.py` → `freedom_ls/<app>/tests/templatetags/test_content_tags.py`,
`freedom_ls/<app>/management/commands/foo.py` → `freedom_ls/<app>/tests/management/commands/test_foo.py`.
No app does this today; its tests for subpackage modules sit flat in `tests/`, and the cleanup specs
move them. Browser tests get one extra hop:
`freedom_ls/<app>/tests/playwright/test_<thing>.py`. A helper or URLconf module used only by an
app's tests lives alongside those tests, never in `conftest.py`. Cite
`panel_framework/tests/{root_urls.py,stub_panels.py}`, `health/tests/root_urls.py`,
`reports/tests/{gather_input_builders.py,report_data_builders.py}` as the pattern.

**Rule 2. Dependency direction.** `docs/app_structure.md`'s dependency table (Runtime-deps and
Test-only-deps columns, generated by `generate_app_map.py`) is the source of truth for what an app
depends on and where rule 2 is violated today. Two dependencies are real even though the import graph cannot
see them. A model relation declared by string label (`"content_engine.Course"`,
`settings.AUTH_USER_MODEL`) is a runtime dependency on the app that owns the model. And the user
is framework-level. Every request carries one, so any app's tests may use `accounts`'
`UserFactory`. Spec 3 decides how the automated check learns both; this spec states them in prose. A test that spans several apps belongs in the lowest app that depends on every app it
touches, not the app whose behaviour happens to be exercised first.

**conftest.py vs. plain module.** `conftest.py` holds only `@pytest.fixture`-decorated fixtures
plus private, underscore-prefixed helper functions that only those fixtures call. Anything meant
for manual import by test files, a plain function rather than a fixture, belongs in a plain module
(e.g. `helpers.py`, alongside the app's `factories.py`), never in `conftest.py`. A plain function
dropped into `conftest.py` gets none of pytest's auto-discovery and still needs an explicit import,
which defeats the reason to put it there. Cite `accounts/tests/conftest.py` (two
fixtures plus one underscore-prefixed `_seed_default_legal_docs`) as the pattern to follow, and
`learner_interface/tests/conftest.py` (eight plain functions requiring manual import, plus a
`reverse_url` re-export from the root conftest) as the pattern to avoid. `mail/tests/conftest.py`
is the one defensible exception, and states the test for when a plain conftest helper earns its
keep: its docstring says its helpers are deliberately public because several test files across the
app assert against the same message shape. This generalises to a rule. A plain helper may stay
in `conftest.py`, undocumented-underscore, only when more than one test file in the app needs it
**and** a comment at its definition says why.

**Fixture placement.** Put a fixture at the shallowest directory that still contains every
consumer. Root `conftest.py` (`freedom_ls/conftest.py`) is for project-wide, always-on fixtures
only. Cite `_disable_force_site_name`, `_disable_preview_overrides`,
`_clear_course_access_backend_cache`, and `mock_site_context` as the existing correct examples. An
app's `tests/conftest.py` is for fixtures used by more than one test file within that app. A
fixture used by only one test file stays in that file.

**Fixture scope and idempotent reset.** Default to function scope; widen to module or session only
for profiled-expensive setup, never to save typing. A session- or module-scoped fixture must never
hand back mutable state that a test then mutates. That is a live isolation bug `pytest-randomly` is
built to expose. Where cost genuinely needs a wider scope, build the expensive read-only part at
that scope and reset or verify the per-test-mutable part at function scope, idempotently
(`get_or_create`, an explicit cache clear). Cite `panel_framework/tests/conftest.py`'s
`_panel_test_tables` (autouse, session-scoped, wrapped in `django_db_blocker.unblock()`) paired
with `_panel_test_permissions` (autouse, function-scoped, `ContentType.objects.clear_cache()` plus
`get_or_create`, with its own comment explaining why function scope is required given
`transaction=True` tests elsewhere in the suite). Use it as the worked in-repo example, cited
near-verbatim rather than invented fresh.

**The "thin wrapper" rule, tightened.** The existing line in `resources/testing.md` ("Avoid
creating fixtures that are thin wrappers around factories. Rather just use the factories") stays,
with "thin" now defined: a fixture whose entire body is one factory call with fixed kwargs and
nothing else is thin, and should be deleted in favour of calling the factory directly in the test.
A fixture that composes more than one factory call, adds relationship logic no single factory
expresses, or depends on another fixture to work is not thin and is the correct use of the
factory-fixture pattern. Cite the root conftest's `course_with_topic` (two factory calls plus
`.items.create(...)`) and `logged_in_client` (depends on `mock_site_context`) as the not-thin,
correct-use examples.

**Factory cross-app direction.** A factory may import another app's factory at module scope only
in the direction the runtime dependency already runs: optional/feature-app factories may import
core-app factories directly; a core app's factory never imports an optional app's. Where two
factories genuinely need each other, use the dotted-string form of `SubFactory`
(`factory.SubFactory("app.factories.OtherFactory")`) instead of a direct class import, so neither
module needs the other at load time. The `INSTALLED_APPS` guard for an optional app's factory
belongs in the test file or conftest that imports it, never in the factory module itself.
`factories.py` files import freely; the caller carries the guard.

**Stub-model technique.** When a foundational, low-level app's tests need "some object with an
assignable role" or "any site-aware model" to prove genericity, define a tiny test-only model
inside that app's own `conftest.py`, register it with `connection.schema_editor()`, and never give
it a real `factory_boy` factory. A plain, non-fixture helper function stands in for that role
instead. This is the documented fix for a foundational app's tests reaching for a real downstream
model to exercise genericity. Cite `panel_framework/tests/conftest.py`'s
`StubModel`/`StubChild`/`StubProtectedChild` plus its `_make_stub`/`_make_stub_child` helpers as
the reference implementation; `site_aware_models` and `role_based_permissions` are named as the
apps that need this technique, but applying it there is spec 5's cleanup, not this spec's.

**Collection-safety example, corrected.** `SKILL.md`'s and `resources/testing.md`'s existing
"Collection safety for optional apps" examples show a raw
`if "myproject.optional_feature" not in settings.INSTALLED_APPS:` string check. Both get rewritten
to call the shared helper the codebase already has and already uses in
`course_applications/tests/conftest.py`: `from freedom_ls.tests.app_guards import
app_not_installed`, so the documented pattern matches the enforced one (read
`freedom_ls/tests/app_guards.py` for its exact signature before writing the example).
`fls-dev:testing`'s own FLS-specific `course_applications` example gets the same fix.

**Deciding an allowed exception.** State this as one test the standard itself answers, not a fixed
list: is the "wrong" import intrinsic to what's being tested, meaning the thing under test genuinely
can't exist without a real row from the other app, or is it standing in for something a local stub
or fixture could give instead? An intrinsic case gets a one-line comment at the import explaining why,
not a code change.

## Open until the spec

- Whether the placement guidance ("where does this fixture/factory go?") becomes its own named
  subsection in `resources/testing.md` or folds into the existing "Creating Test Data" material.
  This is a documentation-shape call, not a rule decision.
- How a test grants a role when its app does not depend on `role_based_permissions` at runtime.
  `reports`, `educator_interface`, `learner_interface`, `learner_management`, `base` and
  `organisations` all call `assign_object_role` in their tests to set up a user who may see
  something, while their own code reaches permissions only through another app or guardian. The
  standard says whether that is an intrinsic dependency (allowed, with a comment), a real runtime
  edge the import graph misses, or something a local fixture should provide. Specs 5, 8, 11, 13 and
  15 follow the answer.
- How many additional named exceptions get called out by name in the skill, beyond
  the `mail/tests/conftest.py` case. The layout audit surfaced others (e.g.
  `contrib/conformance/`'s dual-use test-module files) that may or may not warrant their own
  callout versus being left to the general intrinsic-vs-stub-in test above.

## Out of scope

- Any change to actual test code anywhere in the repo (specs 4 through 15).
- The boy-scout cleanup step and its "worth flagging" guidance text (spec 2).
- Pre-commit/CI enforcement of either rule, the import-linter contracts, the mirroring script, and
  the violation baseline (spec 3).
- Moving `SiteFactory` into `site_aware_models`, and the Playwright wildcard re-export's fate
  (spec 4).
