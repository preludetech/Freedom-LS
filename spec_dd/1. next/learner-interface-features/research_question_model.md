# Research: the question model, for the test-out pretest and the revision question bank

Codebase facts only. Checked on 2026-11-12 against `freedom_ls/form_engine`, `content_engine`, `content_base`, `learner_progress`, `learner_interface`, `demo_content/`, `claude_plugins/fls-content` and `docs/product/`.

## 1. The Form model family

All in `freedom_ls/form_engine/models.py` unless noted.

- **Form** (`TitledContent` + `MarkdownContent`): `strategy` (`QUIZ`, `CATEGORY_VALUE_SUM`, `UNSCORED`; `enums.FormStrategy`), `quiz_show_incorrect` (nullable bool), `quiz_pass_percentage` (nullable 0-100), `submit_on_exit` (bool). Slug unique per site. The pydantic schema (`form_engine/schema.py`, `Form.validate_quiz_fields`) requires both quiz fields when `QUIZ` and forbids them otherwise.
- **FormPage**: `form` FK, `order`, `category`, `condition_option` FK (branch gate).
- **FormContent**: `form_page` FK, `order`, markdown `content`, `condition_option`. The block a question sits next to is purely positional.
- **FormQuestion** (`BaseContent`, so it carries `file_path`, `meta`, `tags` as an `ArrayField`): `form_page` FK (CASCADE), `order`, `category`, `slug` (author's reference name, unique within its form, only used by `when`), `condition_option`, `question` (markdown, `rendered_question()`), `type` (12 types), `required`, `min`, `max`, `decimal_places`.
- **QuestionOption** (`SiteAwareModel`): `question` FK, `text`, `value`, `order`, `correct` (nullable bool). Nothing else: no explanation or feedback field.
- **FormProgress** (one sitting): `form` FK (PROTECT), `user` (nullable for anonymous), `start_time`, `completed_time`, `scores` (JSON), `furthest_page_reached`, `asked` (JSON, which pages, questions and content the sitting was asked, written at `complete()`).
- **QuestionAnswer**: `form_progress` FK, `question` FK (PROTECT), `selected_options` M2M, `text_answer`; unique on (`form_progress`, `question`).
- **CourseFormAttempt** (`learner_progress/models.py:254`): `course_progress` FK, `collection_item` FK to `ContentCollectionItem` (nullable, SET_NULL), `form_progress` OneToOne. No uniqueness on the placement. The absence of this row marks a standalone sitting.

**Scoring and correctness**
- `scoring.is_quiz_answer_correct(selected_option_ids, options)`: exact match. Every `correct=True` option selected and no `correct=False` option selected. `correct=None` is neutral. A question with no correct option can never be right (so free text scores 0). `scoring.evaluate_quiz_answers(answer_rows, options_by_question)` already does this in bulk over (attempt, question) pairs with no queries.
- `QUIZ` scoring (`FormProgress.compute_quiz_scores`): one mark per question, `scores = {"score", "max_score"}`. Frozen at `complete()`. `CATEGORY_VALUE_SUM` scores nested categories from option `value` (survey/assessment, multiple_choice and dropdown only).
- Pass: `quiz_percentage()` and `passed()`. `queries.quiz_verdict` returns True/False/None (None for a non-quiz, no pass mark or unreadable percentage). `queries.attempt_completes_form` is "verdict is not False".
- A learner must pass a quiz for the item to count complete and for the next item to unlock (`docs/product/learner-tracking.md`, `learner-experience.md:240`). A quiz with no pass mark counts complete on completion.

**Retakes and attempt limits.** Attempts are unlimited, each a separate `FormProgress` + `CourseFormAttempt` (`docs/product/learner-tracking.md:8`). No attempt cap, cooldown or lockout field exists. Failed results offer "Retry quiz" (`course_form_complete.html`) unless the item is closed by a deadline.

**`quiz_show_incorrect`.** Read only in `course_form_complete.html`. When true, the results page lists each wrong answer with "Your answer" and "Correct answer" (`FormProgress.get_incorrect_quiz_answers()`). Free-text questions are skipped. No explanation text.

**Branch logic.** `when:` (question slug plus `equals`/`includes`) sets `condition_option` on a page, question or content block. `conditions.py` computes a per-sitting `SittingPath`. **`when` is not allowed in a `QUIZ` form** (`claude_plugins/fls-content/skills/content-types/resources/form-files.md`), so branching and quiz scoring do not combine today.

## 2. Authoring and loading

- A form is a numbered directory holding one `form.md` (frontmatter) and numbered `*.yaml` page files (`form-files.md`). The first `---` section is the FORM_PAGE. Later sections are questions (have a `question` key) or content blocks (`content` key). Options are an inline list. Order comes from file name and position in the file. Only `correct: true` marks the answer. There is no explanation key (the schema models forbid extra keys on options).
- Loader: `content_engine/management/commands/content_save.py`. `save_form_question` calls `save_with_uuid`. `save_content_to_db` pairs each form with its pages by directory.
- **Stable identifiers.** `content_save` writes a `uuid` back into the source file the first time (`update_file_with_uuid`, and `update_file_with_option_uuids` for options). Later loads `update_or_create(id=uuid, site=site)`, so a question or option that keeps its `uuid` keeps its row, and `QuestionAnswer` rows keep pointing at it through edits to its text, position, or page. A question moved to another page file with its `uuid` keeps its id. A question authored without a `uuid` gets a fresh row on first load. The author-written `slug` is a separate reference name used only by `when`, unique per form, not site-wide.
- **Removal.** I found no code in `content_save` that deletes a question or option dropped from a file. `QuestionAnswer.question` is PROTECT. `queries.py` has `FINAL_GROUP_TITLE = "Questions no longer on the form"`, so answers to orphaned questions are expected to exist. Verify before relying on this.
- **Outside or shared across forms.** No. `FormQuestion.form_page` is a required CASCADE FK, so a question belongs to exactly one page of one form and cannot be shared. `compliance-form-randomization` listed shared cross-form banks as out of scope for its V1.
- `tags` (list of strings) and `meta` (dict) are valid on a question in YAML and stored (`BaseBaseContentModel`; `save_with_uuid` leaves stored tags alone if the key is absent). Nothing reads them for questions today.

## 3. Pools, random draw, shuffling, feedback

- **None built.** No pool, random draw, option shuffle, question-order shuffle, per-question explanation, or per-option feedback exists in `form_engine`, its templates, or the schema. A learner sees the identical full set in authored order.
- **`compliance-form-randomization`** is in `spec_dd/0. paused/compliance-form-randomization/` (idea, `todo.md` unticked past idea, two research files). It is not in `1. next` and not in `3. done`. The roadmap line `spec_dd/1. next/roadmap.md:249` still names it. It proposes: four opt-in shuffles per form (page order, question order, option order with position locks, random subset draw), a keep-together group between `FormPage` and its items, and a persisted per-attempt `realized_order` (and/or seed) on `FormProgress`. It says the pool is single-form, and defers shared banks and tag/topic-area draws. It defers remediation to a sibling spec named `compliance-exam-remediation`, which has no directory. Unbuilt, so cut nothing on it as if it existed. Note `FormProgress.asked` already records what a sitting was asked and `conditions.frozen_path` rebuilds a path from it.

## 4. Linking a question to the content it tests

- No link today. The only content-tree structure is `ContentCollectionItem` (`content_engine/models/courses.py`): a generic-FK placement row (`collection` = Course or CoursePart, `child` = Topic, Form, CoursePart, etc.) with `order` and due-date columns. A `CoursePart` (a "section") has `items`. The same Topic or Form can be placed in several courses, and each placement is its own row; learner progress hangs off the placement (`TopicProgress`, `CourseFormAttempt.collection_item`).
- Options, least to most invasive:
  1. **Tags on the question** (`FormQuestion.tags`, already in schema, DB and loader). No migration. A tag names a section by convention only, and there is no integrity check that the tagged section exists, and no per-course meaning if a `CoursePart` is reused in two courses.
  2. **A field on `FormQuestion` naming the tested content** (a nullable FK to `CoursePart` or `Topic`, written from an author-friendly path/uuid like the `children:` and `application_form:` references, which `resolve_author_path` already resolves). One migration plus schema/validator/loader/`fls-content` doc changes. Ties a question to the content, not to a course placement, which is what a renewal course that re-places the same part wants. Note `form_engine` depends on `content_engine`, not the reverse (`courses.py` `_is_form` comment), so this direction is allowed.
  3. **A separate bank model** (question-to-section rows, or a bank owning questions). Needed only if a question must be tested in several sections, belong to no form, or carry its own explanation and scheduling. Largest change, and it conflicts with the rule that a question lives on a form page.
- Related: a quiz placed after a section tests that section only by position; nothing records it.

## 5. Answer history per attempt

- Each submission is a `FormProgress` plus per-question `QuestionAnswer` rows with `selected_options`. A question left blank stores no row. `complete()` deletes answers to questions not on the sitting's path. `FormProgress.asked` records the path.
- **Right/wrong per question per learner can be derived, not read.** `QuestionAnswer` stores no correctness or timestamp of a verdict (it has `created`/`modified` from `TimestampedModel`). Correctness is recomputed from `selected_options` against the question's current `correct` flags, so editing an option's `correct` re-marks history. The score is frozen but the per-question verdict is not (`course_form_complete` detects this with `stored_score_outdated`). `scoring.evaluate_quiz_answers` makes the bulk derivation cheap.
- Only completed, course-placed `QUIZ` sittings give clean history. A blank answer is "wrong" by `get_incorrect_quiz_answers`, which is also how the pass mark counts it.
- **A revision record needs a new model for these**, which `QuestionAnswer` cannot hold: attempts outside any form sitting (revision draws one question at a time, not a `FormProgress` with pages), a stored verdict, a due date or box, confidence rating, and review count. Reusing `FormProgress` per revision question would pull in page flow, pass marks, `CourseFormAttempt`, `form_attempt_completed` receivers (course progress, webhooks) and educator reports (`reports` read quiz answers), none of which a revision answer should trigger.
- Educator and report code reads `QuestionAnswer` of completed quiz sittings (`docs/product/reports.md`, `exports.py`). A revision answer stored there would pollute those.

## 6. Where a quiz is rendered

- Learner player: `learner_interface/views.py` `view_form` (start screen, `course_form.html`), `form_start`, `form_fill_page` (-> `_render_form_fill_page`, `course_form_page.html`), `course_form_complete` (`course_form_complete.html`), `form_submit_and_exit`. All inside the course player chrome (`_player_chrome_context`) and gated by `_blocked_item_redirect` / sequential unlock.
- Reusable rendering: `form_engine/templates/form_engine/question.html` renders one question (fieldset, markdown legend, dispatches by type to `form_engine/inputs/*.html`). It needs `question`, `question_positions`, `rejected_answers`, `existing_answers`. Option rendering is `inputs/multiple_choice.html`, `checkboxes.html`, `dropdown.html`. `form_engine/page_flow.py` (`page_context`, `submit_page`, `render_form_page` with 422 on refusal and `Cache-Control: no-store`) is the page-level glue, and `form_engine` is also used by the application shell outside the course player, so the question partial is already shared between two shells.
- Results/review block: the "Review incorrect answers" cards in `course_form_complete.html` are inline, not a partial; a revision UI wanting "your answer / correct answer / why" would extract it.
- Standalone: `form_engine/urls.py` and `views.py` run forms outside a course (application forms).

## Implications for the cut

1. **Both features need the same primitive: a question that knows the section it tests.** Cut it as its own small spec, ahead of either feature. Cheapest sound version is a nullable reference from `FormQuestion` to a `CoursePart` (or Topic), authored in YAML by path or uuid. Tags are a no-migration stopgap with no integrity.
2. **Question identity is workable but not guaranteed.** A question keeps its row only if its YAML section keeps its `uuid`. Revision history keyed to `FormQuestion.id` survives edits and moves; a question deleted from a file is not pruned by the loader and answer rows are PROTECTed. The spec has to decide what happens to a learner's history when an author removes or substantially rewrites a question (the research file already lists this).
3. **Questions cannot be shared or live outside a form.** A revision bank of questions "belonging" to a section either (a) draws from questions already on quiz forms (revision reuses the section's quiz questions, nothing to author twice) or (b) needs a bank form: a `Form` (e.g. `QUIZ`/`UNSCORED`) placed nowhere or placed hidden, whose questions are tagged with the section. Option (b) needs no new question model but needs a way for a form to exist without a course placement and for a question to be drawn from it.
4. **Explanations need new fields.** Add an optional explanation on `QuestionOption` (why this wrong answer is wrong) and/or on `FormQuestion` (the general explanation), across the model, the pydantic `QuestionOption`/`FormQuestion` (both `extra="forbid"`), the loader (`save_with_uuid` rejects unknown fields), `fls-content` `form-files.md` and `validate`. `quiz_show_incorrect` and the existing results card would be the first consumer, so this delivers value for ordinary quizzes too.
5. **Revision needs its own record, not `FormProgress`.** A per-learner, per-question model (stored verdict at each answer, timestamp, scheduling state, optionally confidence) keyed to the learner and `FormQuestion`. Build the verdict on `scoring.is_quiz_answer_correct` / `evaluate_quiz_answers`. Do not reuse `QuestionAnswer`: it is unique per sitting and read by reports and completion receivers. Free-text types cannot be auto-marked (`correct` is meaningless), so revision is limited to multiple_choice, checkboxes and dropdown (as is the quiz scorer). Flashcards with confidence are a different question type (self-graded, no `correct`) and would need a new `QuestionType` or a separate card model.
6. **Pretest scoring per section has no code.** `QUIZ` scoring gives one `{score, max_score}` for the whole form; only `CATEGORY_VALUE_SUM` scores by category, and that is option-`value` sums, not right/wrong. Per-section right/wrong would be derived from `selected_options` + `correct` grouped by the new section link (point 1), or by reusing `FormQuestion.category`/`FormPage.category` (pipe-separated nesting) as the grouping with a quiz-aware scorer. A test-out also needs: per-section pass mark (none exists), a new "complete by test-out" status in `learner_progress` (today an item is complete only through a topic being done or a passed quiz attempt, `attempt_completes_form`), and a rule for how a skipped section's own quiz counts.
7. **Retakes and pools.** Attempts are unlimited today and the whole quiz is always shown, so a retake sees the same questions. The research file's gaming concern (pool larger than draw, no retake until studied) has no support; it is exactly what the paused `compliance-form-randomization` designs. Decide whether the pretest depends on it (then un-pause or fold in its per-attempt `realized_order` and draw count) or ships without it with a one-attempt rule.
8. **`when` and `QUIZ` do not combine.** A pretest that routes the learner (skip or study a section) by in-form branching is not possible; the routing has to be outside the form engine (course/player logic reading per-section results). Branching is not needed for per-section scoring.
9. **UI reuse.** A revision screen can include `form_engine/templates/form_engine/question.html` and the `inputs/*` partials directly, and `form_engine` already serves a second shell. It will need its own view, URL (kebab-case, in `learner_interface`), single-question submit with immediate feedback (not `page_flow`'s multi-page `FormProgress` flow), and an extracted version of the "your answer / correct answer" card. HTMX validation errors use 422 (project convention).
10. **Open facts to confirm in the spec stage.** (a) Whether `content_save` ever removes questions dropped from a file. (b) Whether a `QUIZ` form with no placement can load (the loader expects forms to be reached from a course's `children:` for placement but forms are loaded by directory). (c) Whether any consumer of `QuestionAnswer` (reports, `exports.py`, webhooks) assumes every question belongs to a sitting.
