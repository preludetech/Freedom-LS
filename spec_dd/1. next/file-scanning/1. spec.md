# Spec: file scanning

## Purpose

`QuestionAnswerFile` stores the documents applicants attach to a file-upload question -- in the first
deployment, scans of identity documents. `freedom_ls/form_engine/uploads.py` validates their *shape*:
an extension allowlist, a size cap, PDF magic bytes, and a Pillow decode-and-re-encode that strips
EXIF and settles the extension the file is stored under. It does not validate their *contents*. A
payload embedded in a well-formed PDF passes every check FLS makes, and PDFs are passed through
unmodified because there is no safe re-encode for them.

So today a reviewer downloads whatever was uploaded, onto a staff machine, with nothing between the
two.

`simple-application-forms` originally shipped a seam for this: a `scan_status` column, a pluggable
`FILE_SCAN_BACKEND`, a system check nagging production about it, and superuser admin actions to clear
files by hand. Nothing implemented the seam. It was removed rather than carried, because a scanner
nobody wrote and a review queue nobody could work through is not a control -- it is the appearance of
one. This spec exists so that when scanning is built it is built whole, and so none of the design
work already done has to be redone. §"The code that was removed" below is copy-back-able.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| clearing a file | coined | Deciding a stored file is safe to hand to a reviewer. In the removed design this was a superuser pressing an admin action; a scanner would do it automatically. |
| the quarantine gate | coined | The rule that the reviewer's download route refuses a file that has not been cleared. The applicant's own-file route is deliberately not behind it. |

## Scope

**In.** Automated inspection of a stored `QuestionAnswerFile` for malware. A status column and the
gate that reads it. A background driver that scans without blocking the upload request, and a sweep
that picks up rows the driver missed. A re-scan path. The reviewer-side admin surface: the status,
its filter, and whatever manual override survives the design. Operator documentation for whatever
configuration this introduces, which the removed seam never had.

**Out.** Any change to `uploads.py`. Shape validation and content inspection answer different
questions and the existing checks stand on their own. Encryption at rest, which is an infrastructure
concern. A retention scheduler. Scanning of any other uploaded file in FLS -- course content and
generated reports are authored by trusted staff, not submitted by applicants, and if that changes it
changes in its own spec.

## Decisions already settled

These were argued out during `simple-application-forms` and survive the removal. They are decisions,
not open questions.

- **A default that clears nothing.** If FLS ships a scanner seam whose default clears every file,
  every deployment that never configures it believes its uploads were scanned when they were not. The
  removed `NoOpScanner` left every file `PENDING` for exactly this reason. Whatever shape the new
  design takes, the failure mode must be "nothing is cleared", never "everything is".

- **An errored scan leaves the file uncleared.** A scanner that times out, cannot reach its daemon or
  raises must not flip the row either way. `PENDING` is the correct resting state for "we do not
  know". This was never implemented and is the single most likely thing to get wrong.

- **The applicant's own file is not behind the gate.** `own_question_answer_file` serves an applicant
  their own upload whatever its status. Withholding it hides from them only what they themselves
  attached, and they already possess the document. Ownership is the control on that route.

- **The applicant sees no scan state.** A status offers them no action, submission is not gated on
  it, and telling someone their document is "pending" raises a question they cannot answer. See
  `research_file_upload_ux.md:134` in the `simple-application-forms` spec directory.

- **Clearing is auditable.** If a human can clear a file, who did it and when has to survive. A
  custom `@admin.action` does **not** write a `LogEntry` the way editing through the change form
  does, so the action has to write one itself. Django 6 removed the per-object `log_action`; the
  queryset-wide `LogEntry.objects.log_actions(...)` is the replacement.

## The mistake not to repeat

The removed implementation called the scanner **synchronously, inside the upload request**, at
`freedom_ls/form_engine/views.py`:

```python
    with transaction.atomic():
        ...
        answer_file.file.save(f"file{extension}", content, save=True)

    get_file_scanner().scan(answer_file)
    return _render_file_widget(request, form_progress, question, answer_file)
```

Three things are wrong with it, and they were invisible only because the shipped scanner did nothing:

1. A real scan of a 6 MB PDF blocks the applicant's request for as long as it takes.
2. `scan()` returns `None` and is expected to save the row itself, but the `answer_file` handed to
   `_render_file_widget` on the next line is the in-memory instance. Any status the scanner wrote
   would not be in the response.
3. Nothing said the backend must call `save()`. The only worked example -- `NoOpScanner` -- saved
   nothing, so an implementer had no signal either way.

The replacement queues the work. This project already has everything needed: `django-tasks` and
`django-tasks-db` are pinned, `TASKS` is configured at `config/settings_base.py:494` (the
`ImmediateBackend` for dev and tests, the durable database backend in `settings_prod.py`), a worker
ships as `manage.py fls_run_worker`, and `freedom_ls/mail/tasks.py` is a working precedent down to
its queue-priority convention (`EMAIL_TASK_PRIORITY = 10`, ahead of the default 0, so a person
waiting on a password reset is not stuck behind a cohort report).

## Requirements

### The status column

Reinstate `ScanStatus` and the field on `QuestionAnswerFile`
(`freedom_ls/form_engine/models.py`). Two things to fix on the way back in:

- It belongs in `freedom_ls/form_engine/enums.py` alongside `QuestionType` and `FormStrategy`, unless
  it is genuinely only ever needed by `models`.
- Add `db_index=True`. The removed version had none, so the admin `list_filter` scanned unindexed.

### The driver

A `@task` in `freedom_ls/form_engine/tasks.py` taking the row id and nothing else, enqueued after the
upload transaction commits (`transaction.on_commit`, so a rolled-back upload never queues a scan for
a row that does not exist). It loads the row, scans, and writes the outcome. Errors propagate rather
than being swallowed, so the worker marks the result FAILED and `django_tasks`' own
`task_finished` receiver logs it at ERROR with the traceback -- the same contract
`freedom_ls/mail/tasks.py` documents.

### The sweep

Nothing in the removed design ever re-drove a `PENDING` row. A file whose task was lost -- worker
restarted mid-claim, enqueue lost, deployment ran no worker at all -- stayed `PENDING` forever with
no signal. Add either a `scan_pending_uploads` management command or a sweep in
`freedom_ls/deployment/housekeeping.py`, whichever fits that module's existing shape, and a re-scan
path for a file whose earlier scan errored.

### The gate

`question_answer_file_download_view` refuses anything not cleared. `QuestionAnswerFileAdmin` shows the
status, filters on it, renders no download link until the file is cleared, and keeps `file` in
`exclude` so no storage URL for an uncleared upload is rendered on the page.

### Documentation

The removed seam had none: `docs/product/configuration-and-extension.md` and
`docs/product/security-and-data-handling.md` were both silent on `FILE_SCAN_BACKEND` while a system
check told operators to configure it. Whatever configuration this spec introduces is documented in
both, and in `docs/deployment-security-checklist.md`.

## The code that was removed

Reproduced verbatim from `simple-application-forms` so it does not have to be rewritten. It is a
starting point, not a decision -- in particular the open question below may change the shape of
`scanning.py` and `config.py` entirely.

### `ScanStatus` and the field, from `freedom_ls/form_engine/models.py`

```python
class ScanStatus(models.TextChoices):
    """Where a stored file has got to in malware scanning."""

    PENDING = "PENDING", _("Pending")
    CLEAN = "CLEAN", _("Clean")
    REJECTED = "REJECTED", _("Rejected")


class QuestionAnswerFile(SiteAwareModel, TimestampedModel):
    ...
    scan_status = models.CharField(
        max_length=20, choices=ScanStatus.choices, default=ScanStatus.PENDING
    )
```

An earlier draft named the third state `INFECTED`, with lowercase values; the shipped version
renamed it `REJECTED` and uppercased, because a file can be refused for reasons other than a positive
detection.

### `freedom_ls/form_engine/scanning.py`

```python
"""The seam a deployment plugs a real malware scanner into.

FLS ships no scanner. The default leaves every file PENDING, which is what keeps
an unscanned upload from being mistaken for a cleared one: nothing downstream
serves a file to anyone but its owner until a superuser marks it clean.
"""

from __future__ import annotations

import functools
from typing import TYPE_CHECKING, Protocol

from django.utils.module_loading import import_string

from .config import config

if TYPE_CHECKING:
    from .models import QuestionAnswerFile


class FileScanner(Protocol):
    """Inspects a stored answer file and sets its scan_status."""

    def scan(self, answer_file: QuestionAnswerFile) -> None: ...


class NoOpScanner:
    """Clears nothing; every file stays PENDING until a superuser marks it."""

    def scan(self, answer_file: QuestionAnswerFile) -> None:
        return None


@functools.cache
def get_file_scanner() -> FileScanner:
    """The configured scanner (cached for the process lifetime).

    Test caveat, as for get_course_access_backend: a test overriding
    FILE_SCAN_BACKEND has to clear this cache, which the autouse fixture in
    form_engine/tests/conftest.py does for every test.
    """
    scanner_class: type[FileScanner] = import_string(config.FILE_SCAN_BACKEND)
    return scanner_class()
```

The `functools.cache` came with a test cost: an autouse fixture in
`freedom_ls/form_engine/tests/conftest.py` had to call `get_file_scanner.cache_clear()` before and
after every test in the app, or a test that overrode the setting left a stale instance behind for
whichever test ran next. `freedom_ls/course_access/loader.py` carries the same caveat.

### `freedom_ls/form_engine/config.py`

```python
from __future__ import annotations

from freedom_ls.base.app_settings import AppSettings, Setting


class FormEngineConfig(AppSettings):
    # Dotted path to the scanner every uploaded answer file is handed to. FLS
    # ships an inert default, so a deployment that leaves it alone is warned by
    # system check W001.
    FILE_SCAN_BACKEND: str

    declared_settings = {
        "FILE_SCAN_BACKEND": Setting(
            default="freedom_ls.form_engine.scanning.NoOpScanner"
        ),
    }


config = FormEngineConfig()
```

Not `required=True`, unlike `COURSE_ACCESS_BACKEND`, because a safe default existed. Sharing a name
with `FormEngineConfig(AppConfig)` in `apps.py` is the convention every other app follows.

### `freedom_ls/form_engine/checks.py`

```python
@register(Tags.security)
def check_file_scan_backend_configured(
    app_configs: Sequence[AppConfig] | None, **kwargs: object
) -> list[Warning]:
    """W001: warn when production is running the inert scanner."""
    if settings.DEBUG:
        return []

    default = FormEngineConfig.declared_settings["FILE_SCAN_BACKEND"].default
    if default != config.FILE_SCAN_BACKEND:
        return []

    return [
        Warning(
            "FILE_SCAN_BACKEND is the shipped no-op scanner with DEBUG=False; "
            "uploaded files stay pending until a superuser marks them by hand.",
            hint="Point FILE_SCAN_BACKEND at a scanner for this environment.",
            id="freedom_ls_form_engine.W001",
        )
    ]
```

`freedom_ls/form_engine/apps.py` had to import `checks` in `ready()` for it to register.

### The gate, from `freedom_ls/form_engine/views.py`

```python
def question_answer_file_download_view(
    request: HttpRequest, object_id: str
) -> FileResponse:
    """The reviewer's route, wired into the admin.

    Only a cleared file is served: an unscanned upload reaching a staff member's
    machine is the risk the scan gate exists for.
    """
    if not request.user.is_superuser:
        raise PermissionDenied
    answer_file = get_object_or_404(QuestionAnswerFile, pk=object_id)
    if answer_file.scan_status != ScanStatus.CLEAN:
        raise Http404
    return stream_question_answer_file(answer_file)
```

The `is_superuser` check is explicit because `admin_view` only guarantees staff.

### The manual clearance actions, from `freedom_ls/form_engine/admin.py`

```python
    actions = ["mark_clean", "mark_rejected"]

    @admin.display(description="Download")
    def download(self, obj: QuestionAnswerFile) -> str:
        if obj.scan_status != ScanStatus.CLEAN:
            return ""
        url = reverse(
            "admin:freedom_ls_form_engine_questionanswerfile_download", args=[obj.pk]
        )
        return format_html('<a href="{}">Download</a>', url)

    @admin.action(description="Mark selected files clean")
    def mark_clean(
        self, request: HttpRequest, queryset: QuerySet[QuestionAnswerFile]
    ) -> None:
        self._set_scan_status(request, queryset, ScanStatus.CLEAN)

    @admin.action(description="Mark selected files rejected")
    def mark_rejected(
        self, request: HttpRequest, queryset: QuerySet[QuestionAnswerFile]
    ) -> None:
        self._set_scan_status(request, queryset, ScanStatus.REJECTED)

    def _set_scan_status(
        self,
        request: HttpRequest,
        queryset: QuerySet[QuestionAnswerFile],
        status: ScanStatus,
    ) -> None:
        """Set the status and record who decided it.

        Clearing a file is a human judgement about someone's document, so the
        log entry is the point of the action rather than bookkeeping around it.
        """
        queryset.update(scan_status=status)
        # The class is superuser-only, so request.user is always a real row with
        # a UUID primary key here, never the anonymous user Django types it as.
        user_pk = cast("UUID", request.user.pk)
        LogEntry.objects.log_actions(
            user_pk,
            queryset,
            CHANGE,
            change_message=f"Scan status set to {status.label}",
        )
```

`scan_status` was in `list_display`, in `list_filter` alongside `created_at`, and in `readonly_fields`
so the change form could not edit it -- only the actions could. `exclude = ["site", "file"]` kept a
storage URL for an uncleared upload off the page; `file` was excluded rather than made read-only for
that reason.

## Testing

- A file whose scan comes back clean is served to a reviewer; one that has not been scanned is not.
- A scanner that raises leaves the row `PENDING`, and the failure reaches the task result as FAILED.
- The applicant's own-file route serves the file whatever its status.
- The changelist renders no download link for an uncleared file, and one for a cleared file.
- The sweep picks up a `PENDING` row whose task never ran, and does not re-queue one already in
  flight.
- Replacing a file resets its status: a replacement has not been scanned, whatever the file it
  replaced was.
- If a manual clearance action survives, it writes exactly one `LogEntry` per selected row with
  `action_flag=CHANGE`, and a staff-but-not-superuser user cannot reach it.

## Open questions

- **One scanner, or a seam?** The removed design shipped a dotted-path `FILE_SCAN_BACKEND` with no
  real implementation behind it, which is the worst of both: every production install got a warning
  pointing at a knob nobody had built. The two credible answers are (a) ship one real default --
  ClamAV over `clamd` is the standard self-hostable choice -- and keep the dotted path so a
  downstream can swap it, with the system check re-pointed to warn when scanning is genuinely
  *disabled* rather than merely default; or (b) drop the seam for a single integration configured by
  connection settings and an on/off flag. Deployments do genuinely differ -- an in-cluster ClamAV
  daemon, S3 or GCS native malware protection, a vendor API -- and dotted-path backends are the house
  pattern already (`COURSE_ACCESS_BACKEND`, `EMAIL_UPSTREAM_BACKEND`, `FREEDOM_LS_ICON_BACKEND`).
  What is not acceptable is (c): a seam with nothing behind it.

- **What a stock install does.** If the answer above is (a) with ClamAV as the default, a stock FLS
  install needs a ClamAV daemon to accept uploads usefully at all. Is that an acceptable dependency
  for a system designed to be installed into other Django projects, or does the default have to
  degrade to "scanning off, gate open, documented"?

- **Does a manual clearance queue still make sense?** With a working scanner, superuser
  mark-clean/mark-rejected becomes an override for false positives rather than the only thing that
  moves the queue. That is a different feature with a different justification, and it may not be
  worth its audit machinery.

- **Nothing inspects the inside of a PDF today.** This spec is the control for that. Until it ships,
  a stock install has none.

## Success criteria

- A file uploaded by an applicant is scanned without blocking their request, and the widget they get
  back is correct.
- A file whose scan has not completed, or whose scan errored, is not served to a reviewer.
- A reviewer can download a cleared file from the admin changelist.
- A `PENDING` row whose task was lost is picked up by the sweep rather than sitting forever.
- A deployment that has not configured scanning is told so somewhere an operator reads, and no file
  is silently treated as clean.
- `docs/product/security-and-data-handling.md` describes what a stock install does about malware.
