## 1. Attempt lifecycle

- **A sitting is one `FormProgress` row** (form_engine/models.py:419). Fields: `start_time` (`auto_now_add`, 438), `last_updated_time` (439), `completed_time` (null until finished, 440), `scores` JSON (441), `furthest_page` FK (448), `asked` (456), `served_paper` (464). **There is no attempt number and no status column.** "Open" means `completed_time IS NULL`.
- **Attempt number is derived, never stored**: the 1-based place among completed sittings of one form under one course progress record, oldest first (reports/gather.py:392-402, `attempt_numbers`, `attempt_number_of`). The educator review title uses it (educator_interface/panels/learner/quiz_attempt.py:132-157, 364). An open attempt has no number.
- **A course attempt = `FormProgress` + `CourseFormAttempt`** (course_progress, collection_item, form_progress), written together in `get_or_create_incomplete` (learner_progress/attempts.py:84-110). A retake is just a new pair; nothing links it to the earlier one. Every course-side caller must go through `learner_progress/attempts.py` (module docstring, lines 1-14).
- **Where an attempt starts**: learner_interface/views.py `form_start` (2044-2077) -> `start_attempt` (attempts.py:184-227), which locks the `CourseProgress` row (`select_for_update`, 205), reuses an unanswered sitting opened within `START_REUSE_WINDOW` = 10 s (32, `_kept_open` 140), else calls `finalise_stale_incomplete`, then `get_or_create_incomplete`. A declaration quiz goes `form_declaration` (2081-2130) -> `start_attempt(declaration=...)`. Both then call `ensure_served_paper`. **`form_start` is a GET that writes**; the "Start", "Continue" and "Try Again" buttons are links to it (`retry_url`, views.py:2458; template course_form_complete.html:260). `form_start` does not check whether the placement is passed, so a learner who passed can still mint a new sitting by URL.
- **The start gate**: `_form_start_gate` (views.py:1978-2021) runs access, blocked and closed checks before any write, and is shared by `form_start` and `form_declaration`. This, plus `start_attempt` (the lock), is the natural place for a max-attempts check and a minimum-wait check: both need a read of the record's completed attempts at the placement (`completed_attempts`, attempts.py:254, newest first by `completed_time`) under the same lock. The refusal needs a new gate outcome; today the gate only redirects (to `view_course_item` or the blocked/closed destinations).
- **What the learner sees today** (`view_form` 1897-1964, `form_start_page_buttons` learner_interface/utils.py:940-974): open attempt -> "Continue Form"; latest completed and `quiz_verdict(...) is False` -> "Try Again"; passed -> "Next" / "Finish Course"; none -> "Start Form". The results page (`course_form_complete`, views.py:2347) shows the verdict banner and offers retry only when `quiz_verdict == "failed" and not item_closed` (template line 260). The start page lists the 5 latest attempts (`exam_previous_attempts.html:25-32`, reading `progress.scores`). **Nothing in the UI or the gate knows an attempt count or a wait**; "try again" is unconditional while the item is open.
- **Completion**: `FormProgress.complete()` (models.py:606-635), idempotent on `completed_time`: `ensure_served_paper`, delete off-path answers, set `asked`, stamp `completed_time`, `score(path)`, save, then send `form_attempt_completed` after the atomic block. Callers: `form_fill_page` last page (views.py:2321), `form_submit_and_exit` (3237), `finalise_stale_incomplete` (attempts.py:136), the admin (form_engine/admin.py:123). There is no `completed_by`/reason field, so "completed by learner / expiry / disturbance" is not recorded anywhere today.
- **`submit_on_exit`** (models.py:85, schema.py:105): a form flag with no scheduler behind it. It does exactly three things:
  1. Shows the exit dialog text "Leaving now will submit..." and the "Leave and submit" button instead of "Leave and save" (course_form_page.html:122, 142). The button POSTs the runner page form to `form_submit_and_exit`, which saves the posted page with `require_answers=False` (views.py:3216-3222) then calls `complete()`; it refuses a non-`submit_on_exit` form unless the item is closed or access ended (3191-3199).
  2. **Lazily** finalises an abandoned open attempt the next time the learner opens the item: `view_course_item` (views.py:1583-1594), `form_start` and `start_attempt` all call `finalise_stale_incomplete` (attempts.py:113-137), which completes the open sitting if `form.submit_on_exit`. `kept_if_untouched_since` spares a sitting last touched before the latest course pause start (`_latest_pause_start`, views.py:1302).
  3. Nothing else. **Logout, closing the tab and losing the connection do nothing server-side**: the only client hook is a `beforeunload` warning that explicitly must not call the server (learner_interface/static/learner_interface/js/alpine-components.js:105-123), plus a `visibilitychange` listener at line 466. There is no `user_logged_out` receiver anywhere. So "disturbance/logout = fail" today means "scored when they next open the item", and a learner who never returns has an open attempt forever.
- Auto-fail vs auto-mark needs a new outcome: `complete()` always scores the saved answers (auto-mark). An auto-fail has to write a failing result without marking, and say why. Note `quiz_percentage()` (models.py:479) raises on `scores` with no `score`/`max_score` and `quiz_verdict` (form_engine/queries.py:29-52) then returns None, which `attempt_completes_form` treats as **not failed** (queries.py:55-67). A "failed" marker must therefore be a real score pair (for example score 0 of `max_score`), or the verdict reader must learn it.

## 2. Time limit seams

- **Nothing on a quiz is timed today.** No time-limit field on `Form`, no countdown widget on the runner (the only countdowns in the repo are unrelated: content_engine alpine-components.js:235, a polling timer in panel_framework). `grep` for `time_limit` finds only the course-level one below.
- **Deadlines app is calendar-based and request-time**: `Course.time_limit_days` resolves to a `ResolvedDeadline` per record (deadlines/resolver.py:257-263, 400-410); `close_instant`, `is_closed`, `has_access_ended` (deadlines/consequences.py:29-57) compare `now` with `due_at` + grace window. It ends access or closes items for incomplete work, evaluated on each request (`_is_closed_for_learner`, views.py:1245-1262; `course_deadlines`). No row is written at expiry and nothing completes an open attempt. The only finalisation on close is `form_submit_and_exit` accepting a closed item (views.py:3191). Reuse: the "closed" idea (compare an instant with now on every request) but not the model; a per-attempt expiry has to be `start_time + limit` per sitting, not per record.
- **Housekeeping pattern exists**: `run_housekeeping_sweeps()` (deployment/housekeeping.py:292-498) is invoked once per run by `fls_run_housekeeping`, with the schedule supplied by the deploy ("cron, a Kubernetes CronJob", module docstring lines 1-6). Each sweep has its own `try/except DatabaseError` and appends to `sweep_failures`/`findings`/`notes`; a sweep that "closes rows a dead worker left open" is the existing shape (`mark_orphaned_running_reports_failed`, 187-231, using `_base_manager` because there is no request site). A sweep that completes expired open sittings fits; it must use `_base_manager`/`unscoped` (site-aware manager has no request) and `complete()` per row. Cadence is the operator's cron, so an expiry sweep alone is minutes late at best; the learner-facing expiry has to be enforced on request too (the next page POST, results and start routes), with the sweep as the safety net for learners who never return. There is also a worker (`fls_run_worker`, django_tasks) for scheduled `run_after` tasks (`find_late_unpicked_tasks`, housekeeping.py:94).
- **Answers are saved per page, on POST.** `form_fill_page` POST -> `submit_page` -> `save_answers` (models.py:553-604; page_flow.py:117). An unposted page is lost; `form_submit_and_exit` saves the posted page first, then completes (views.py:3216-3237), and skips the save when closed (3217). So auto-submit at expiry can only mark what earlier pages posted unless the client posts the current page with the submit (the exit dialog pattern: `form="runner-page-form"` + `formaction`, course_form_page.html:151-158, with `formnovalidate`). A server-side sweep can only score what is stored. The expiry POST also has to run past `require_answers` (page_flow.py:122).

## 3. Scoring and consumers

- **Correctness is computed, never stored per answer.** `QuestionAnswer` (models.py:980) has `form_progress`, `question`, `selected_options` M2M, `text_answer`, timestamps; no mark, no correct flag. A question is correct by `is_quiz_answer_correct(selected_ids, options)` (form_engine/scoring.py:11-25): all `correct=True` options selected and no `correct=False` one; a question with no correct option can never score. **One point per question**, hard-coded (`max_score += 1`, models.py:813; `score += 1`, 821). There are no per-question weights, so "override a question's score" has no existing quantity to override beyond 0/1.
- **Stored aggregate only**: `FormProgress.scores = {"score": int, "max_score": int}` written by `score_quiz` (models.py:825-833) via `compute_quiz_scores` (787-823). `max_score` is the served paper's question count (`_quiz_questions`, 771-785; the whole form when `served_paper` is None). Stored scores are frozen at submission and never rescored (docstring 794-796).
- **Readers of the stored pair** (a stored-score override must update, or sit beside, this): `quiz_percentage()` (479), `passed()` (501), `quiz_verdict` (queries.py:29), `attempt_completes_form` (queries.py:55) -> course completion and unlocking (learner_progress/queries.py:49-91 `completed_form_item_ids`, 125-158 `completion_instants`; the **latest** completed attempt decides, 82-91, so a later failed retake un-completes the item), `form_attempt_completed` receiver `recalculate_course_progress_on_form_attempt` (learner_progress/signals.py:172) and the learner course index/unlock (learner_interface/utils.py:253, 349, 474). Report path: `score_attempt` (reports/gather.py:367-389) reads `scores`, `quiz_percentage()`, `passed()` for the attempts table, `QuizResult.latest_*`, at-risk (`FailedLatestQuizAttemptRule`, reports/at_risk.py:84-103, reads `passed`), cohort report screen and PDF; learner_progress/admin.py:63-79; learner results page (views.py:2400-2411) and templates (`course_form_complete.html`, `exam_previous_attempts.html`, `exam_score_ring.html`); educator attempt review header (`quiz_attempt_result`, quiz_attempt.py:169-178, `QuizAttemptInstanceView.get_stats` 311-325). Webhooks: only `course.completed`/`user.signed_up` style events; no event carries a quiz score (grep of webhooks/ and base/webhook_event_types.py for score/passed found none), but `course.completed` follows from the verdict above.
- **Readers that recompute from answers, ignoring the stored pair** (an override must win in each):
  - `get_incorrect_quiz_answers` (models.py:849-930; correctness at ~895) feeding the results page list (views.py:2396).
  - `stored_score_outdated` (form_engine/queries.py:251-257) compares stored vs `compute_quiz_scores`; it raises the "score is outdated" banner on the results page (views.py:2404) and the review (quiz_attempt.py:273). An override that changes only the stored pair would trip this on every overridden attempt, so `compute_quiz_scores` has to apply overrides too.
  - Educator review per-question mark `_mark` (quiz_attempt.py:210-235), by the same `is_quiz_answer_correct` over current options.
  - Reports question analytics: `build_sat_questions` (reports/indexes.py:642-685) uses `evaluate_quiz_answers` (scoring.py:28-38) for the confusion tables and per-learner wrong answers (gather.py:469-480) — this layer does not read `scores` at all.
  - Revision's `was_correct` (revision/services.py:131) is a separate learning feature, not attempt marks; out of scope.
- **Exports**: `form_engine/exports.py` (answer cells 143-180) exports answers only, no score or correctness; unaffected. The reports CSV/PDF go through `gather.py`.
- **Single recompute seam** is `compute_quiz_scores` plus the `is_quiz_answer_correct` callers (`_mark`, `get_incorrect_quiz_answers`, `build_sat_questions`). An override model keyed on (`FormProgress`, `FormQuestion`) read by those four, and by `score_quiz` at completion, covers every consumer above, because the aggregate consumers read the stored pair that `compute_quiz_scores` produces. A post-completion override still has to rewrite `scores` (and send a recalculation, as `form_attempt_completed` does) because the aggregate readers never recompute.
- Spec 3 (question versions) says the stored score is **not** recomputed against the live row (idea.md:35); keeping the original score means a second stored value beside `scores`, never an edit of it.

## 4. Audit log and educator gating

- **Write API**: `record_entry(*, action, actor, target, target_label, organisation, subjects=(), reason="", details=None, run_id=None, site=None)` (audit_log/writer.py:33-71). Old/new values go in `details` (a free `Mapping[str, JSONValue]`), e.g. `{"old": ..., "new": ...}` for `cohort.renamed` (audit_log/README.md:14-23; educator_interface/panels/cohort/actions.py:182). It opens no transaction (call inside the `atomic` of the change); reason max `REASON_LENGTH` = 500; the entry is append-only (README:168-181). Action codes are `noun.verb` registered in `AuditAction(...)` (audit_log/actions.py:152+) with a group in `AUDIT_ACTION_GROUPS` (20-29), and **the noun/verb must come from the domain glossary** (`tests/invariants/test_vocabulary.py`, README:128-130), so a new noun (for example `mark`/`score`/`answer`) needs the glossary first. Document the action in the README table. The educator ReasonForm dialog is `panel_framework.forms.ReasonForm` (README:26).
- **Educator attempt review** (`educator_interface/panels/learner/quiz_attempt.py`): `QuizAttemptConfig` (346-373), an `OrganisationSectionConfig` with `list_view = None`, `in_menu = False`, `instance_view = QuizAttemptInstanceView` (a `QuizAttemptStack` of `QuizAttemptSummaryPanel` + `QuizAttemptPaperPanel`). It names **no `view_capability`**; `authorise_instance` calls `openable_sitting_ids` (67-118), which needs a completed QUIZ sitting with a `CourseFormAttempt`, the learner visible via `learners_visible_to` (so `view_cohort`/`view_learner` scope) and the registration shown on the Courses tab. Read-only today: no actions. Reached from the learner Courses tab (`panels/learner_courses.html:37`).
- **Roles** (role_based_permissions/roles.py): `site_admin`, `organisation_admin` (hold `view_cohort`, `change_learner`, `bulk_manage_learners`, `download_cohort_report`, `view_auditlogentry`, ...), `cohort_admin`, `cohort_viewer` (read only), `organisation_staff_viewer`, `organisation_staff_roles_viewer`; placeholders `system_admin`, `learner`, `observer`. **No permission today governs marks or attempts**; no grading permission exists (roles.py:98 "FUTURE: add grading/analytics permissions").
- **Adding a permission**: declare it in `PERMISSIONS` (role_based_permissions/registry.py:80 shows `download_cohort_report`), as a model `Meta.permissions` entry (learner_management/models.py:171, migration 0004), add the string constant beside the others (learner_management/queries.py:86-113, report_panels.py:72), add it to the chosen `Role.permissions` frozensets in roles.py, then run `sync_role_permissions`; gate with `can(user, CAPABILITY, organisation)` (`OrganisationSectionConfig.has_capability`, panels/common/request.py:69-72). A site can extend a role via `FREEDOMLS_PERMISSIONS_MODULES` (README:86-126). Roles on a `Cohort` never satisfy an organisation check (spec 4 idea, line 24).
- **Question-access role (content-versions-4, in progress)**: a new organisation-scoped role (recommended `question_bank_viewer`) with a permission on `Course` (recommended `view_course_questions`), held by no existing role by default. Gates the course content preview (`PreviewContentAction`) and the cohort report quiz panel and PDF, writes one audit entry per view, and removes the QUIZ answer views from the Django admin (idea.md:9-14, 23-38). Spec 5 then puts the answered-version review behind it. **Not decided**: whether an override action should be an organisation-role permission of its own or ride that role. Seeing a learner's answers and correct answers in the review is currently open to anyone who can see the learner, which spec 5 wants gated; an override control has to be at least that restricted.

## 5. Form front matter path (existing quiz fields)

- `form.md` YAML front matter -> pydantic `Form` (form_engine/schema.py:78-172): `quiz_show_incorrect` (91), `quiz_pass_percentage` (95), `submit_on_exit` (105), `requires_declaration`/`declaration_text` (109-119), `shuffle_*` (120-131). `validate_quiz_fields` (133-172) requires the quiz pair for QUIZ and forbids the QUIZ-only knobs (`knobs` dict 156-167) on other strategies; a new QUIZ-only field is one `Field` plus one `knobs` entry, plus cross-field rules (for example the wait list needs a max or must be a non-decreasing list) in the same validator.
- -> `content_save.save_form` (content_engine/management/commands/content_save.py:743-751) -> generic `save_with_uuid` (300-): `item.model_dump(exclude_none=True)` minus excluded keys; **every dumped field name must exist on the Django `Form` model or it raises** ("Fields present in frontmatter but don't exist in Django model", 349-362). So a front matter key and a `Form` field share a name, and a migration on `Form` (form_engine/models.py:65-127) is mandatory. A list field becomes a `JSONField`; a `None` default drops out (`exclude_none`) so the model default applies, which means **removing the key later does not reset a stored value** unless the schema default is non-None (a documented trap: the QA note that `content_save` resets `submit_on_exit`, because the schema default is `False`, not None).
- **Bundled copy**: `claude_plugins/fls-content/validate/schema.py` is a copy of this schema (line 1: "Bundled from freedom_ls/content_engine/schema.py — re-sync via /update_claude_plugin_fls_content"; the form fields at 1023-1098). ## 6. Collisions

Among the four capabilities:
- **Override (a), expiry (b), disturbance (c) all touch `FormProgress.complete()`/`score()` and `scores`** (models.py:606-648, 787-847). (b) and (c) both need "complete this open attempt now for reason X" and a completion-reason record; build that once. (c)'s auto-fail also needs the failing-score question in section 1. (a) and (c) both write a stored result, so they must agree on how an overridden or auto-failed result shows in `quiz_verdict`.
- **(b) and (c) both need a server-side finaliser for attempts nobody is looking at** (the housekeeping sweep, deployment/housekeeping.py) and a client hook in the runner (learner_interface alpine-components.js `examRunner`, ~112-151 and 466) plus `form_fill_page` and `form_submit_and_exit` in learner_interface/views.py. **(b) and (c) and (d) all edit `finalise_stale_incomplete`/`start_attempt`/`get_or_create_incomplete`** (attempts.py:84-227) and `_form_start_gate`.
- **(d) and the "Try Again" button** (utils.py:964, template course_form_complete.html:260, `view_form` 1897) share the same UI; the cap and wait messages must show there, and the gate must refuse by URL too.
- **All four add `Form` fields and front matter** (schema.py, a `Form` migration, content_save automatic, fls-content bundled schema and docs, `content_preview.py:508`): a single migration and schema edit avoids rebase pain between them.
- **Time-limit expiry (b) vs deadlines**: do not reuse `deadlines/*` models; reuse the "compare instant with now on request" idea only.
