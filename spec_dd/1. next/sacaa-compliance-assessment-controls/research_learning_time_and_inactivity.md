# Research: minimum learning time and auto exit (SACAA compliance)

Findings and seams only. Paths are relative to the repo root.

## 1. Activity tracking today

- Nothing measures time on a page or tells whether a learner is present. There is no JS heartbeat, no per-page timer and no stored seconds-spent. The only `setInterval` uses are a tab-visibility notification-count poller (`freedom_ls/panel_framework/static/panel_framework/js/shell-components.js:17`, `visibilityPoller`, which already pauses while the tab is hidden) and the panel poll (`panel_framework/static/panel_framework/js/alpine-components.js:1069`). The `deployment` "heartbeat" files are worker liveness, unrelated.
- `User.last_login` is the only user-level timestamp. `account_setup` treats `last_login is None` as "never signed in" (`spec_dd/2. in progress/sacaa-complianc-deletion-and-declaration-1-force-delete/idea.md:47-49`).
- The in-progress force-delete spec adds a nullable last-active timestamp on `User`, "an authenticated request moves it". It is still only an `idea.md`, with no spec or code yet. Whether it is written every request or throttled, and whether API-key requests move it, are open (`idea.md:55-57`). Its research confirms no `last_seen` field, middleware or session tracking exists today (`research_user_deletion.md:45-50`). This is a coarse, per-request, server-side signal. It cannot see a learner sitting idle on one page, which is exactly what auto exit needs.
- Sessions: `SESSION_COOKIE_AGE = 1209600` (2 weeks) only in `config/settings_prod.py:51`. `SESSION_COOKIE_SECURE`, `HTTPONLY` and `SAMESITE` are set at `settings_prod.py:37-39`. `settings_base.py` sets no session expiry. The middleware list (`config/settings_base.py:178-198`) has `SessionMiddleware`, `AuthenticationMiddleware`, `CurrentSiteMiddleware`, `RegistrationCompletionMiddleware` and `AxesMiddleware`, and no activity middleware. Django's sliding expiry only applies when `SESSION_SAVE_EVERY_REQUEST` is on, which it is not.
- Progress timestamps:
  - `TopicProgress.start_time` (`auto_now_add`), `last_accessed_time` (`auto_now`, so any save moves it) and `complete_time` (`freedom_ls/learner_progress/models.py:88-90`).
  - `CourseProgress.created_at`, `started_at`, `last_accessed_time` and `completed_time` (`models.py:139-142`). `last_accessed_time` is written only by the player (`learner_interface/views.py:1645-1658`).
  - `CourseProgress.last_accessed_item` is the resume pointer, a `ContentCollectionItem` (`models.py:153`).
  - None of these records elapsed learning time. `TopicProgress.start_time` is when the row was created, and the row is created when the page first opens (`views.py:1856-1860`). Elapsed-since-start is therefore derivable server-side without any new field, but it counts wall-clock time, not attentive time.
  - Paused learners write nothing (`views.py:1645`, `1850-1853`), so a minimum-time rule needs a decision about pauses (the `deadlines` pause).

## 2. Navigation, completion and gating

- Player routes (`learner_interface/urls.py:56-85`) are index-based and 1-based over `course.viewable_collection_items()`, which flattens `CoursePart` placements away (`content_engine/models/courses.py:505-511`). Parts are not player pages, only outline groupings. The pages are: `view_course_item` (topic or form), `form_start`, `form_declaration`, `form_fill_page`, `course_form_complete`, `form_submit_and_exit` and `course_finish`. Reference topics are a separate read-only route that writes no progress (`course_reference_topic`, `views.py:2584`).
- Movement is Next and Previous buttons (`view_course_item` builds `next_url` and `previous_url`, `views.py:1560-1575`), the course outline or sidebar (rows from `get_course_index`, `learner_interface/utils.py`), and direct URLs.
- Topic completion happens on the Next click, not on view. `view_topic` POSTs `mark_complete`, sets `TopicProgress.complete_time` once, then redirects to `next_url` (`views.py:1864-1878`). The button is a form POST (`learner_interface/templates/learner_interface/course_topic.html:23-35`). Simply viewing creates the `TopicProgress` row (status `IN_PROGRESS`), not completion.
- Sequential unlock already exists and is enforced server-side. `get_content_status` (`utils.py:316-391`) marks a topic `IN_PROGRESS` (next is `BLOCKED`) until `complete_time` is set. A failed form is `FAILED` and blocks what follows. `_blocked_item_redirect` (`views.py:1326-1368`) redirects any `BLOCKED` item to `course_detail`. It is called from `view_course_item` (`views.py:1552`) before anything is written, and the form start, declaration and fill-in routes also call it (with `refuse_closed` for the start and fill-in routes). The `_unlocked_next_url` and `_unlocked_previous_url` helpers hide dead Next links (`views.py:1430-1448`). The comment at `views.py:1341-1344` records that the gate was once only in the outline, with its URL left open, and was fixed. A new gate that lives only in the template would repeat that bug.
- Deadlines also close content: `CLOSED` status, `_render_closed_notice`, `_is_closed_for_learner` (`views.py:1245-1262`, `1451`). Access, pause and end-of-access are decided by `_course_access_redirect` (`views.py:1203`).
- Seams for a "minimum time not met" gate:
  - Server-side refusal in the `mark_complete` branch (`views.py:1864`): refuse to stamp `complete_time` while `now - TopicProgress.start_time < minimum`. This is the one write that unlocks the next item, so a forged POST is also stopped.
  - Reuse of the status machinery: treat the item as not complete (next stays `BLOCKED`) in `get_content_status`, which every route reads, so URL guessing past the item is already refused by `_blocked_item_redirect`.
  - Form routes: `_form_start_gate` (`views.py:1978`) is where "may not write the knowledge test until the tutorial hours and modules are met" would sit. That is a course-level cumulative rule, not per-item, so it needs a course-wide sum.
  - `test-out` (`spec_dd/1. next/learner-interface-features-2-test-out/idea.md`) is the other thing that skips content. It will have to say whether a skipped section still owes its minimum time.
- Caveat on `start_time`: it is the first open, so a learner who opens a topic, leaves, and returns hours later would have already "met" the minimum. Real accumulated time needs a stored counter or periodic client pings.

## 3. Per-item configuration and cascade

- Front matter is pydantic with `extra="forbid"` (`content_base/schema.py:25-33`). `Topic` is `BaseContentModel + MarkdownContentModel + DueDateFields` (`content_engine/schema.py:105-111`). `Activity` adds `level` (`schema.py:114-117`). `CoursePart` has `children: list[Child]` (`schema.py:584-596`) and `Course` adds `estimated_duration` (a `timedelta`, `schema.py:485`). `Form` has `strategy`, `quiz_pass_percentage`, `submit_on_exit`, `requires_declaration` and the shuffle flags (`form_engine/schema.py:78-130`).
- A new field flows through `save_with_uuid` (`content_save.py:295-384`): it dumps every schema field (`exclude_none`) and rejects any key that is not a model field, with an error telling you to add the model field. So each new key needs both a pydantic field and a matching model column and migration. `save_topic` (`content_save.py:438`) excludes the due fields and hands them to the placement row. `save_form` (`:743-751`) excludes `sections`. Every other schema field must be a column on `Topic`, `Form` or `CoursePart`.
- The standalone offline validator mirrors the schema (see the `schema.py` comments on "offline validator"), and the `widget-reference` skill and the content-editing docs list authored keys, so a new key touches those too.
- Cascade precedent: due dates are placement-level. They live on `ContentCollectionItem` (`courses.py:611-640`: `due_date`, `due_time`, `no_due_date`) and in `CoursePartChildDueDate` (`courses.py:652`), where a part's `children:` entry overrides its children. `Child` and `PartChildDueDate` carry the override (`content_engine/schema.py:188-206`). Nothing cascades from `Course` or `CoursePart` to children by default today, apart from deadlines resolving per placement. A "course part enforces auto exit for all its topics and forms" setting has no existing inheritance mechanism. The cheapest shape is to resolve at request time by walking the item's `ContentCollectionItem` to its parent part (the same traversal `get_course_index` uses), rather than denormalising onto each row.
- Per item or per placement matters. A topic can be placed twice (`TopicProgress` is keyed per `collection_item`, `learner_progress/models.py:74-82`), so a setting on the `Topic` row differs from one on the placement.

## 4. Reading-time estimate inputs

- A `Topic` stores markdown in `MarkdownContent.content` (`content_base/models.py:85-99`). `rendered_content()` renders on each call and is not cached. `content_save` rewrites `![[image]]` into `<c-picture>` tags before saving (`content_save.py:387-411`, `:377-380`). So the stored text holds raw cotton tags (`c-picture`, `youtube`, `audio`, `audio-clip`, `audio-reveal`, `pdf-embed`; `content_engine/templates/cotton/`).
- Word counting at `content_save` time is feasible. The stored `content` is plain text and `save_with_uuid` already post-processes it, though tags and attribute text would need stripping for an honest count.
- Media length: only audio has a stored duration, `File.duration_seconds` read by `read_audio_duration` at `content_save.py:1136-1230` (`content_engine/models/files.py:52`). `youtube` and `pdf-embed` have none. Protected video is not built (`spec_dd/1. next/learner-interface-features-5-protected-video/idea.md`) and is meant to add a `video` widget, which would need a duration source of its own. A content-length estimate is therefore words plus audio-only media unless videos get a duration.
- `Course.estimated_duration` (`courses.py:260`) is an author-set display field. It shows that author-supplied time is an accepted pattern, but it is course-level and for display only.
- Forms: no `time_limit` exists yet (it is the separate "Maximum test time" item in the same idea).

## 5. Logout, redirect and modal mechanics

- allauth is in use (`settings_base.py:444-524`). The logout control is a POST form with CSRF (`base/templates/partials/logout_button.html`), the allauth default (`ACCOUNT_LOGOUT_ON_GET` is not set). A client timer cannot navigate to a logout URL. It would submit that form, or `fetch` a POST with the `X-CSRFToken` header. The CSRF token is set globally on `<body hx-headers>` per `CLAUDE.md`, so HTMX or fetch posts pick it up. Courses 403 pages already link to logout with `?next=` (`base/templates/403.html:17-18`). A redirect to the dashboard is a plain `learner_interface:dashboard` navigation. No server hook would be needed unless a timed-out session must be proven server-side.
- Alpine is the CSP build, which forbids inline expressions. Components are `Alpine.data(...)` in `*/static/*/js/alpine-components.js`, loaded before Alpine (`shell-components.js:1-7`). Every new countdown needs a registered component, not inline JS. The player shell is `x-data="coursePlayer"` (`learner_interface/static/learner_interface/js/alpine-components.js:87`), and `examRunner` there holds the `beforeunload` guard (`:112`).
- Dialog options: the panel framework's single shared native `<dialog id="app-modal" x-data="appModal">` is loaded by panel actions (`panel_framework/templates/panel_framework/partials/modal_host.html:152`), with `modal-header`, `modal-body` and `modal-footer` cotton components. It is built for fetched fragments and a discard prompt, so a self-opening countdown is a different use. Check whether the learner `_base_interface.html` includes the host before relying on it. The panel framework is being extracted to a package (`spec_dd/2. in progress/extract_panels_framework-5-package-and-install`), so a learner-side dependency on its modal could collide. A plain native `<dialog>` with its own Alpine component is the lower-coupling option.
- Timer precedent: the toast component in `base/static/base/js/alpine-components.js:250-370` keeps `_remainingMs`, pauses and resumes a `setTimeout`, and uses `Date.now()` deltas, which is the pattern to copy for drift-free countdowns. `visibilityPoller` (`shell-components.js:17`) is the tab-hidden precedent, and for compliance a hidden tab should probably keep counting down to exit rather than stop.
- No existing countdown UI for deadlines, only static labels (`learner_interface/tests/components/test_deadline_labels.py`).
- A client-only timer is bypassable (JS off, or a closed tab leaves the session alive). If the regulation needs real logout, a server-side check is also needed: store the last interaction time and refuse or log out on the next request past the limit. This is the same decision as the force-delete spec's last-active write throttle.

## 6. Shared code and collisions

- One shared signal: "learner is active on this page". Both features need a client-side interaction detector (pointer, key, scroll, HTMX request) in an Alpine component, plus a server ping that records the last interaction. Auto exit reads that ping to decide exit. Minimum time reads it to accumulate attentive seconds into a per-`TopicProgress` counter. Both want the same resolved per-item setting (enforce yes or no, interval, warning time, minimum seconds), resolved once from the item or its part via the course index.
- Overlap with the force-delete spec's `User` last-active: that field is coarse and per request and shows who has gone quiet. It should not be the auto-exit signal, because its write is expected to be throttled and spans the whole site. The spec should decide whether the new per-page signal also feeds `User` last-active or stays separate.
- Collisions with in-flight work:
  - `sacaa-complianc-deletion-and-declaration-1-force-delete` (in progress): adds the `User` field, and decides the middleware and throttle that this signal may reuse. Its force delete also removes `TopicProgress`, so any new accumulated-time column on `TopicProgress` is covered, but its confirmation page lists the models and would need updating.
  - `sacaa-compliance-content-versions-and-access-2-retire-removed-content` (in progress): adds a retired state to `Topic`, `CoursePart`, `Form` and others. A new column on those models is a parallel migration on the same tables.
  - `sacaa-compliance-content-versions-and-access-4-question-access` (in progress): touches question access, mostly away from the player.
  - `educator-interface-page-polish` and `extract_panels_framework-5-package-and-install` (in progress): the latter matters if the modal is borrowed from the panel framework (section 5).
  - Not yet built, shape the same code: `learner-interface-features-2-test-out` (completion and unlock rules), `learner-interface-features-5-protected-video` (a `video` widget needs a duration for estimates), `reference-material-content` (reference topics are separate routes, so they must stay outside both rules), and `deadlines-*` (pause semantics and `CLOSED` status).
  - The "Maximum test time" and "Auto mark or auto fail" items in the same idea are siblings. A form timer and the auto-exit timer on a form need one agreed behaviour, since a test logout is a fail by the regulation quoted in the idea.
