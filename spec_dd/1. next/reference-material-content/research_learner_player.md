# R2: learner player and reference material (facts and risks)

Scope: `freedom_ls/learner_interface/` (views.py, urls.py, utils.py, templates), `freedom_ls/learner_progress/`, `freedom_ls/course_access/`, the dashboard and catalogue templates. Read against `idea.md` (reference `CoursePart` rows attached by a new `CourseReferencePart`, outside `Course.items`). Facts and risks only; no plan.

Paths below are relative to `freedom_ls/` unless they start with `claude_plugins`.

## 1. Course player chrome

### URLs (`learner_interface/urls.py`)
- `courses/<slug>/` -> `course_home` (resume redirector, never renders).
- `courses/<slug>/detail/` -> `course_detail`; `courses/<slug>/access/` -> `initiate_course_access`.
- `courses/<slug>/<int:index>/` -> `view_course_item`; `.../start_form`, `.../fill_form/<page>`, `.../complete`, `.../submit-and-exit` for forms; `courses/<slug>/finish/` -> `course_finish`.
- `<int:index>` is the 1-based position in `course.viewable_collection_items()` (flat list, CoursePart rows dropped). A `courses/<slug>/reference/...` path does not collide with `<int:index>` or `finish/`/`detail/`/`access/` (slug converter, but `reference` would be a fixed segment before `<int>` patterns; ordering only matters if a course slug path ever has a second segment equal to `reference`, which `<int:index>` rejects).

### How the chrome is built (`views.view_course_item`, `_player_chrome_context`)
- `view_course_item` is `@login_required` (anonymous learners cannot use the player at all). Steps: `get_object_or_404(Course)` -> `_course_access_decision` (`raise_404_if_unavailable` then `get_course_access_backend().get_access`) -> index range check -> `_course_access_redirect` -> `_ensure_player_course_progress` -> `_player_course_index` (builds the outline rows) -> `_blocked_item_redirect` (progression gating) -> `next_url` / `previous_url` as `index +/- 1` -> chrome context -> write of resume pointer -> `view_topic` or `view_form`.
- Chrome context keys (`_player_chrome_context`): `course_index` (outline rows), `current_entry`, `next_deadline_card`, `current_part`, `current_part_index`, `course_progress`, `can_record_progress`, `course_organisation`, `item_title`, `index`, `paused`.
- Outline rows come from `utils.get_course_index` -> `create_child_dict_with_flattened_index`, which walks `course.collection_items()` only. Each row: `title`, `status` (READY/BLOCKED/IN_PROGRESS/COMPLETE/FAILED/CLOSED/PAUSED), `url` (`view_course_item` with a running index), `type`, `is_current`, deadline keys; a part row carries `children`, `contains_current`. The outline is learning-path only by construction.
- Template layering: `base/templates/_base_interface.html` (side-panel grid; blocks `sidebar_content`, `content_header`, `breadcrumbs`, `header_extra`, `page_title`, `content`) -> `learner_interface/_course_base.html` -> `course_topic.html`, `course_form*.html`, `course_item_closed.html`, `course_finish.html`.
  - Sidebar (outline panel): `_course_base.html` `{% block sidebar_content %}` renders `<div id="course-toc-region">` containing `partials/course_toc_header.html` (org chip, "Course outline" eyebrow, course title, progress bar, next-deadline card) and `partials/course_minimal_toc.html#course-children` (the row list, parts as collapsible `coursePart` Alpine blocks). Mobile: same panel as a bottom-sheet dialog opened by `panel_toggle` button ("Open course outline"). `#course-toc-region` is the HTMX OOB swap target for boosted Previous/Next.
  - Header: `partials/player_breadcrumbs.html` = `course title (links course_detail) > [part crumb, links view_course_item at part's first item index] > item title`. `header_extra` shows a progress bar on mobile only. `page_title` block shows the item deadline label then `item_page_title`.
  - Navigation: `cotton/player-footer.html` with `previous_url`; `course_topic.html` shows a "mark_complete" POST form (Next / Finish Course), or plain Next, or Home/Finish Course links. `cotton/player-nav.html` also exists (not read in depth).
- Part rows in the outline are not links to a part page; their `url` points at one child chosen by resume-aware routing.
- `hide_outline_panel` is only set by the exam-results view (`views.py` ~2284, ended access without kept outline); `_course_base.html` already supports a page with no outline.

### Where a Reference entry could sit (observations, not a plan)
- Reachable from every position and already present in all player pages: the `sidebar_content` block in `_course_base.html` (inside `#course-toc-region`, so it is also refreshed on the HTMX OOB swap) and the header/breadcrumb partial. `course_toc_header.html` is pinned (sticky) above the rows; the rows partial `course_minimal_toc.html#course-children` is also what `course_detail.html` includes (with `hide_deadlines=True`), so anything placed inside that partialdef appears on both the player and the detail page; anything placed in `course_toc_header.html` appears only in the player panel.
- The outline rows are a plain `list[dict]` from `get_course_index`; a Reference entry as a row in that list would be seen by every consumer of that list: `_item_rows`, `next_entry`/`previous_entry`, `current_entry`, `_annotate_next_up` (dashboard "Next up"), `card_deadline_line`/`_missed_and_next`, `next_deadline_card`, `course_detail`'s children. A row with no `due_at` and a status other than READY/IN_PROGRESS would be passed over by next-up and deadline picks, but `next_entry`/`previous_entry` walk `_item_rows` positionally and would treat it as a neighbour (affecting `_unlocked_next_url`/`_unlocked_previous_url`). Risk to check if a row approach is chosen.
- `course_finish.html` extends `_course_base.html` and gets its outline from `get_course_index` (no current item); `course_item_closed.html` and the form pages also extend it. Anything added to the base block shows on all of them.
- Paused / ended learners: `_outline_mode` gives `OutlineMode.PAUSED` / `ENDED` and `_status_in_outline` turns non-complete rows into PAUSED/BLOCKED with no url. The Reference entry's behaviour for these learners is an open question (see section 4).

### `course_home` and `course_detail` natural spots
- `course_home` never renders; it only redirects (`get_resume_index` -> `view_course_item`). No spot there.
- `course_detail` (`learner_interface/course_detail.html`, view `course_detail`): two columns. Right column: sign-up panel with CTA button, "This course includes" list (`{{ lesson_count }} lesson(s)`, "Includes assessments"), organisation card. Left/main column: `content_engine/partials/course_details_body.html`, then `<section><h2>Course content</h2>` with `course_minimal_toc.html#course-children`. A reference listing would naturally be a sibling `<section>` after "Course content" or an extra line in the "This course includes" list; the view would need to supply it in the render context (the template reads only `children`, `lesson_count`, `includes_assessments`, `extra_stats`, etc.). The detail page is public (no `login_required`), renders for anonymous and unregistered users, and `course_details_context(course)` (`content_engine/course_details.py`) supplies the counts.
- The "Course content" section is shown whenever `not course.table_of_contents_in_development` and (`children` or not `access_ended_at`), so a course with no children still gets an empty "Course content" heading plus an empty `<nav><ul>`.

## 2. Topic page rendering

- `view_topic` renders `learner_interface/course_topic.html` with `course`, `topic`, `is_complete`, `next_url`, `previous_url`, `is_last_item`, `is_course_complete` + chrome context. Body: `<c-markdown-container>{{ topic.rendered_content }}</c-markdown-container>` inside `<c-page flush="true">`.
- `Topic.rendered_content()` (`content_base/models.py` `MarkdownContent`): `render_markdown(self.content, None, context={"content_instance": self})` (`markdown_rendering/markdown_utils.py`: python-markdown with fenced_code, mdx_headdown, tables, pymdownx.tasklist; cotton components embedded in the markdown; output cleaned by nh3). No request is passed, so rendered output does not depend on the URL, the course or the player.
- Images / media: cotton components `picture.html`, `audio.html`, `pdf-embed.html`, `file-download.html` use `{{ src|get_file_by_path:content_instance }}`. `get_file_by_path` (`content_engine/templatetags/content_tags.py`) resolves `content_instance.calculate_path_from_root(src)` (relative to the topic's own `file_path`, `..` supported) to a `content_engine.File` row by `file_path` and renders `file_obj.file.url`. So image resolution is a function of the topic's `file_path` alone: reusable for a topic reached at any URL, and a shared reference part at `../shared_drone_regs/` resolves from the topic's own path wherever it is attached. `File.objects` goes through the site-aware manager (thread-local ambient site), so it is request-site dependent, same as today.
- `cotton/content-link.html` (`get_content_by_path`) renders no URL at all today ("Until a topic has a page of its own to link to, the text stands alone"); so cross-links inside reference topics do not need URL resolution but also would not link anywhere (a TODO is in the template; do not delete).
- Because `rendered_content` is a plain method on the model, a view that has a `Topic` can render it without any `ContentCollectionItem`.

### Assumptions that a topic is reached through a `ContentCollectionItem` flat index
- Selection: `view_course_item` picks `viewable_collection_items[index - 1]`; `current_item = collection_item.child`.
- `_blocked_item_redirect` / `current_entry_status`: the gate reads the status of the outline row marked `is_current`. A topic not in the learning path has no current row: `current_entry_status` returns None, which its docstring says callers must read as not blocked. `current_entry` None also means `current_entry.deadline_tier` is absent, so no deadline label (fine).
- Resume pointer: `view_course_item` writes `CourseProgress.last_accessed_item = current_collection_item`, `last_accessed_time`, and stamps `started_at` (+ `record_course_started` analytics) on first content access. `CourseProgress.last_accessed_item` is an FK to `ContentCollectionItem` (SET_NULL). A reference topic placed through a `ContentCollectionItem` in a reference `CoursePart` would be a valid FK target, but `get_resume_index` maps the pointer through `course.viewable_collection_items()` only and falls back to index 1 if not found. Reference viewing is meant to be untracked (idea), so the point is: nothing may write these fields on the reference route; and `started_at` is only ever stamped by `view_course_item`, so a library-only course never gets a `started_at`.
- `view_topic`: `TopicProgress.objects.get_or_create(course_progress, collection_item, defaults={"site_id", "topic"})` on every view (and `.save()` on a repeat view, which bumps `last_accessed_time` via `auto_now`), and a `mark_complete` POST that sets `complete_time`. `TopicProgress.collection_item` is nullable, unique on `(course_progress, collection_item)`; `topic` FK is PROTECT. The `post_save` receiver `recalculate_course_progress_on_save` (`learner_progress/signals.py`) recalculates `progress_percentage` when a completion transitions. Calling `view_topic` for a reference topic would create `TopicProgress` rows against a placement outside `Course.items`; `completed_collection_item_ids` counts any completed `TopicProgress` with a non-null collection item, but `calculate_course_progress_percentage` only counts ids that are in `course.viewable_collection_items()`, so those rows would be invisible to the percentage but present in educator/report/API reads of `TopicProgress`.
- Progression gating and next/previous: `next_url`/`previous_url` are `index +/- 1`; `is_last_item` is `index >= total` and drives "Finish Course" buttons and the redirect to `course_finish` after `mark_complete`; `_unlocked_next_url` / `_unlocked_previous_url` consult `next_entry`/`previous_entry` on the outline. None of these has a meaning for a reference topic; a reference page would need its own next/previous (within a reference part) or none.
- Chrome helpers that look only at the learning path: `utils.get_item_part(course, current_item)` walks `course.children()` and returns None for a topic that is only in a reference part (so no part crumb, `current_part` None, title suffix omitted); the part-crumb index lookup (`current_part_index`) searches `viewable_items` and would not find a reference part's first child. `partials/player_breadcrumbs.html` part crumb always links `view_course_item` at that index.
- Templates: `course_topic.html` is coupled to progress controls: `can_record_progress` / `is_complete` / `mark_complete` form / "Finish Course" / Home button linking `view_course_item index=1` (which is itself a 404 for an empty path). `_course_base.html` consumes `course_index`, `current_entry`, `course_progress.progress_percentage`, `next_deadline_card`, `current_part`; all degrade to empty/None without erroring, as `course_finish` already renders with no current item.
- `ContentCollectionItem` has `due_date`, `due_time`, `due_days_after_registration`, `no_due_date` columns; `deadlines` code resolves from `course.collection_items()`/placements (not read here beyond the player), so a part used only as reference has no placement in any course (as idea.md already notes).

## 3. A `Course` with no children today

`Course.collection_items()` is `list(self.items.prefetch_related("child"))`, so `viewable_collection_items()`, `viewable_items()`, `children()` all return `[]` for an empty course.

| Place | Behaviour for an empty `Course` | Verdict |
|---|---|---|
| `calculate_course_progress_percentage` (`learner_progress/utils.py`) | `if not completable: return 0` before the division | No division by zero. Stays 0 forever; used by signals (`recalculate_progress_percentage`), `recalculate_progress_percentages` command (same function). |
| `Course.lesson_count()` / `includes_assessments()` | `sum(... viewable_items())` -> 0 / False | No crash. Detail page shows "0 lessons" (`course_detail.html` list shown unless `table_of_contents_in_development`) and hero stat via `lesson_count_label` ("0 lessons") in `content_engine/partials/course_details_hero.html`. Misleading for a library. Educator course panel also lists `lesson_count` (`educator_interface/panels/course/panels.py`). |
| `get_resume_index` (`learner_interface/utils.py`) | no record / no pointer -> `1`; pointer not found -> `1` | Returns 1, which does not exist. |
| `course_home` | redirects to `view_course_item index=1` | `view_course_item` raises `Http404("No course item at this index.")` (`index > len([])`). A registered learner of an empty course gets a 404 from the course home URL. |
| `initiate_course_access` | self-registers, redirects to `course_home` | Ends in the 404 above. |
| `course_detail` | `children == []`; `_detail_start_url(... has_items=False)` -> `course_home` for registered learners; CTA label "Start course" (percentage 0) | CTA leads to the 404 above. Empty "Course content" section is drawn (see section 1). Unregistered path is unaffected (`initiate_course_access`). |
| `view_course_item` (any index) | 404 | Expected, but means a library-only course has no player entry at all. |
| `course_finish` (`views.course_finish`) | `outstanding_items(...)` returns `[]` (explicit `if not completable: return []`); condition `not course_progress.completed_time and not still_to_do` is true | Stamps `completed_time`, fires webhook `course.completed` (`fire_webhook_event`) and `record_course_completed` analytics on the first GET of `courses/<slug>/finish/` by any registered learner of the course. `course_finish` is a GET with side effects (existing design). For a library this "completes" the course, which is meaningless and announces a false completion to integrators; nothing in the UI links to `finish/` for an empty course, but the URL is guessable. Also renders "Congratulations" with an empty outline. |
| `CourseProgress.completed_time` for empty course | only ever set by `course_finish` (or QA commands) | A library course never completes through normal use. |
| Resume pointer / `started_at` | only written by `view_course_item` | Stay None; "Started" row on finish page hidden; `last_accessed_time` None. |
| Dashboard grouping (`dashboard_sections.py`, `views._in_progress_section`, `_history_section`, `utils.get_current_courses`/`get_completed_courses`) | "In progress" = every registered course with no `completed_time` (despite the name it includes registered-0%); "Learning history" = courses with `completed_time` | A library sits permanently in "In progress" with `listing_status` `registered` (percentage 0), never moves to history. `_in_progress_sort_key` bucket 1 (unstarted) forever. |
| Dashboard card (`partials/course_card.html`, `course_row.html`) | `_annotate_next_up` calls `get_course_index` -> `[]` -> `next_up_title`/`next_up_url` = `""`; card title link `{% firstof course.next_up_url home_url %}` falls back to the `course_home` URL | Card link goes to `course_home` -> 404. Card shows a 0% progress bar (registered/in_progress status) and no "Next up" line. Card status eyebrow reads "registered"/Not started. |
| Catalogue `all_courses` / `get_course_listing` | registered library: `REGISTERED` status at 0%; `_annotate_next_up` as above | Same dead link and meaningless progress bar for registered learners. Unregistered/anonymous: normal (`course_details_link` -> `course_detail`). The listing itself does not crash. |
| `derive_listing_status` | `progress_percentage > 0` -> IN_PROGRESS else REGISTERED; `is_complete` -> COMPLETE | Library is REGISTERED forever. |
| `get_course_index`, `current_entry`, `_item_rows`, `next_entry`, `card_deadline_line` | all handle empty lists | No crash. |
| Course time limit deadlines (`DeadlineEnforcingBackend`, `course_deadlines(...).time_limit`) | resolved per record from registration/policy, not from items | Not verified in detail; a time limit on an empty course could still end access / show "Access ended", since it needs no items. Flag for the deadlines review. |
| Completion webhooks / API | `course.completed` only from `course_finish`; `course-progress` API serialises `progress_percentage`, `completed_time`, `started_at`, `last_accessed_time` as stored | A library shows 0 / null forever to integrators (not an error). |
| Educator-side counts | `CohortCourseCompletionPanel` (`educator_interface/views.py` ~1198): `record_count`, `completed_count` from `completed_time`, `percentage` guarded by `if registration.record_count` | No crash. Shows "0 of N complete / 0%" for a library; misleading. Learner course tables show `progress_percentage` (0%). Reports (`reports/gather.py`) read form attempts, not item counts. `learner_progress/utils.plan_progress_carry` / `move_progress_preview` use stored percentage: fine. |
| `recalculate_progress_percentages` command | `calculate_course_progress_percentage` -> 0 | Fine. |

Crash list (hard): `course_home`, `initiate_course_access` (end state), the registered CTA on `course_detail`, and the dashboard/catalogue card title link for a registered library all land on an `Http404` from `view_course_item index=1`. No place divides by zero. Misleading list: "0 lessons" counts, "Course content" empty section, permanent 0% / "In progress"/ "Start course" label, `course_finish` completing a course with nothing in it and firing `course.completed`, educator "0% complete" figures.

## 4. Access

- Registration check: `learner_management/utils.is_registered_for_course(user, course)`: False for anonymous; True for an active `LearnerCourseRegistration` of an active `Learner`, or for an access-granting `CohortCourseRegistration` where the user has an active Learner in the cohort. Queryset twin: `learner_management/queries.is_registered_for_course_expression`. `learner_interface/utils.get_is_registered` is a thin wrapper.
- Backend: `course_access/loader.get_course_access_backend()` (cached) = `VisibilityEnforcingBackend(DeadlineEnforcingBackend(<configured COURSE_ACCESS_BACKEND>))`. Core backend `FreeOnlyCourseAccessBackend` -> `_free_access_decision`: `can_access_content=True` iff `is_registered_for_course`. Visibility wrapper: not in audience -> closed decision; `COMING_SOON` and not registered -> no content; `HIDDEN` and not registered -> closed; registered learners keep access in both. Deadline wrapper: a paused record -> paused decision; an ended-access record -> ended decision (`can_access_content` False, `access_ended_at` set), a finished course never ends.
- Gate used by player routes: `views._course_access_decision` = `raise_404_if_unavailable(user, course)` (`course_access/visibility.py`: 404 for HIDDEN and unregistered, 404 if not in audience; skipped under `override_visibility_to_visible`) then `backend.get_access`. `views._course_access_redirect` redirects to `course_detail` unless `decision.can_access_content`; for a paused or ended learner it only lets specific routes through via `_read_only_route_redirect` (`PlayerRoute.ITEM` only for a completed item when `finished_items_open`; `FORM_RESULTS`; `SUBMIT_AND_EXIT`; `FINISH`). `course_home` uses `raise_404_if_unavailable` + `get_access(...).can_access_content`.
- So "access checked by `is_registered_for_course`" in the idea is, in the code, `can_access_content` from the wrapped backend, whose core rule is `is_registered_for_course`. Reusing only `is_registered_for_course` directly would bypass: the audience gate and hidden 404 (those are in `raise_404_if_unavailable`, which does call `is_registered_for_course` itself), a non-free `COURSE_ACCESS_BACKEND` (e.g. applications backend `course_applications/backends.py`, where being registered may not equal can_access_content for an invalid config; `course_detail` comment notes the two "diverge for an invalid-config course"), and the paused/ended outcomes. A reference URL reusing `_course_access_decision` + `_course_access_redirect` would inherit the same decisions; for a paused or ended learner, `PlayerRoute` has no reference member, so the reference route would be redirected to `course_detail` unless a new rule is added (open question for the spec: may a paused or ended learner read reference material?).
- Anonymous visitors: all player routes are `login_required`; only `all_courses`, `course_detail` and dashboard render for anonymous users. `CourseVisibility` (`content_engine/models/courses.py`): PUBLISHED, COMING_SOON, HIDDEN. A COMING_SOON library cannot be entered by unregistered users (no content access); `initiate_course_access` redirects to detail for COMING_SOON. HIDDEN 404s for unregistered users on every slug chokepoint.
- Cross-site: models are `SiteAwareModel`; `get_object_or_404(Course, slug=...)` uses the site-aware manager, so a reference part must also be fetched through the site-aware manager (`CoursePart` unique slug is per site: `unique_course_part_slug_per_site`). `CoursePart.slug` is unique per site, not per course, so `<part_slug>` in the URL is unambiguous only if the lookup is scoped by `CourseReferencePart(course=course)` (a shared part attached to several courses is the same row, one slug); a topic slug uniqueness scope was not checked here.
- Registration and a library: for a library-only course, learners still need a `LearnerCourseRegistration` (or cohort registration) to pass the gate; `initiate_course_access` self-registration path works for free courses but ends in `course_home`'s 404 today (section 3).

## Risks summary
1. `view_course_item` hard-wires index -> `ContentCollectionItem` -> progress writes -> `view_topic` `TopicProgress.get_or_create`; calling it, or `view_topic`, for a reference topic would write progress, resume pointer and `started_at`, contradicting "not tracked".
2. `_player_chrome_context` / `get_item_part` / breadcrumb part crumb are learning-path only; a reference topic gets no part context unless supplied.
3. `course_topic.html` carries progress controls (`mark_complete`, Finish Course, Home -> index 1).
4. Empty-path course: 404 at `course_home` (and through `initiate_course_access`, `course_detail` CTA, dashboard/catalogue card link); `course_finish` completes it and fires `course.completed`; dashboard/educator figures read 0% forever.
5. Access wrappers: paused/ended routes enumerated in `PlayerRoute`; a reference route needs an explicit decision.
6. Outline rows are shared by chrome, dashboard next-up, deadline cards and detail page; adding non-path rows to that list has side effects on `next_entry`/`previous_entry`.
