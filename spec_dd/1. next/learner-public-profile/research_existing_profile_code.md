# Research: existing code relevant to the learner public profile idea

Source: the repo at the time of reading (main). Paths are under `/home/sheena/workspace/lms/freedom-ls-worktrees/main/`.

## 1. User and learner data today

- `accounts.User` (`freedom_ls/accounts/models.py`): `SiteAwareModelBase` + `TimestampedModel`, integer pk. Fields: `email` (unique, login), `first_name`, `last_name`, `is_active`, `is_staff`, `is_superuser`, `site`, `created_at`, `updated_at`. Properties `display_name` and `initials` (monogram used for avatars). No picture, bio, location, phone or social links.
- `Learner` (`freedom_ls/learner_management/models.py`): the `(site, user, organisation)` join row (`is_active`, `created_at`). Not a profile. `StaffMember` is its counterpart for staff.
- `hr_attributes` (`freedom_ls/hr_attributes/models.py`): `JobTitle`, `Department`, `Location` are per-organisation list entries (`name`, `is_active`); `LearnerHRAttributes` is one-to-one on `Learner` with `job_title`, `department`, `location` FKs plus start dates. `OrganisationHRSettings` is an off-by-default switch. This is org-HR data entered by staff, not a learner-chosen free-text location, and "willing to move" does not exist.
- Avatars: none stored. `panel-avatar-chip`, `participant_avatar.html` and the header menu render `User.initials`. `Organisation` has `logo`, `logo_on_dark`, `profile_logo` (ImageFields) and a 500-char `bio` (`freedom_ls/organisations/models.py`), so an org has a bio and picture, a user does not.
- `accounts/forms.py` `UserForm` has `fields = ["first_name", "last_name"]` and a comment `# TODO: allow the user to upload a profile picture`. Must not be deleted.
- No social links, work experience, open-to-work flag or blurb anywhere (grep for avatar/bio/social/linkedin found only the above).
- Learner-facing "my profile": `accounts:account_profile` at `accounts/profile/` (`freedom_ls/accounts/urls.py`), view `accounts.views.edit_profile` (`@login_required`, plain `ModelForm` POST, `messages.success("Profile saved")`). Template `accounts/templates/accounts/profile.html` extends `allauth/layouts/manage.html` and renders `{{form}}` with a `c-button`. No panel framework. Linked from `base/templates/partials/header_bar_user_menu.html` and educator `_shell.html`. Other account pages: allauth (`accounts/` prefix), `complete_registration`, `legal_doc`.
- Existing word "Profile" in code: `account_profile`, `edit_profile`, `Organisation.profile_logo`.

## 2. Certificates and completion data

- No certificate model exists. `docs/product/roadmap.md` has a "Completion Certificates" section: completing a course "produces a finish page but no certificate or downloadable completion evidence". `docs/product/roadmap.md` also notes no org branding in certificates.
- Storage alias `certificates` is declared (public bucket, key prefix `certificates/`, "None yet" consumer) in `freedom_ls/deployment/storage.py` (`CERTIFICATES` purpose) and the file-storage skill.
- Completion data that could be shown: `CourseProgress` (`freedom_ls/learner_progress/models.py`) has `learner`, `course`, `completed_time`, `progress_percentage`, `started_at`, `created_at`. It hangs off `Learner` (so per organisation), not `User`; a learner with an individual and a cohort registration for one course has two records, resolved by `course_progress_for`. A `course.completed` webhook is sent from `learner_interface/views.py` (~line 2204). `course_finish` view is the finish page.

## 3. "Schools" and staff attaching files

- Nothing is called a school. Candidates: `Organisation` ("a client inside a site", a grouping, not an isolation boundary; has logo, bio, `is_default`) and `Cohort` (owned by an organisation). `Learner.organisation` links a learner to an organisation, so "the organisation that issued this certificate" is reachable from a learner.
- Staff: `StaffMember` row per `(user, organisation)` gates organisation/cohort roles. Roles in `freedom_ls/role_based_permissions/roles.py`: `site_admin`, `cohort_admin`, `cohort_viewer`, `organisation_admin`, `system_admin`, `learner`, `observer`. Permission `VIEW_LEARNER` grants sight of learners; `educators_of(learner)` in `learner_management/queries.py` lists staff reaching a learner.
- No way for staff to attach a file to a learner today. File-owning models: `QuestionAnswerFile.file` (`form_engine/models.py`, `user_uploads` alias, applicant-supplied form answer; key `user_uploads/{user_id}/form_answers/{pk}{ext}`; `save()` deletes the superseded object), `GeneratedReport.file` (`reports/models.py`, `reports` alias), `content_engine.File.file` (course media), `Organisation` logos. `LearnerImport` records only a CSV file name; the file is not kept.

## 4. File storage

- Aliases (from `claude_plugins/fls-dev/skills/file-storage/SKILL.md`): `public` (public bucket, prefix `organisations/`, overwrites at stable key, `max-age=86400`), `certificates` (public bucket, prefix `certificates/`, no consumer), `course_media` (private), `reports` (user-data bucket, `cohort_reports/`), `user_uploads` (user-data bucket, `user_uploads/`, no overwrite), `default` (reserved; never use). The skill's table lists the user-data bucket as holding "profile pictures".
- Bucket test: "readable without logging in?" picks the bucket. A public profile picture is shown on a page that may be anonymous, but the skill's table places profile pictures in the user-data bucket (private, signed URLs or streamed by Django). A private certificate upload by a learner fits `user_uploads`. The skill says a `certificates` object key must be uuid-derived, and every `user_uploads/` key must be prefixed by the uploading user (for erasure). The `certificates` alias is public-bucket and is the stated home for learner certificates; whether a learner-uploaded one belongs there or in `user_uploads` is not settled by the skill.
- Mechanics: field uses `storage=<module callable>` resolved through `storage_for_alias(alias, setting_name)` (`freedom_ls/base/storage.py`); alias must exist in `build_storages()` and `config/settings_base.py` `STORAGES`. Example setting-named alias: `ORGANISATION_LOGO_STORAGE_ALIAS = "public"`. Overwrite semantics need an entry in `_OVERWRITE_PURPOSES` (`freedom_ls/deployment/storage.py`); do not reuse an existing purpose.
- Image handling: `pillow>=11.0` and `django-storages[s3]` in `pyproject.toml`. `freedom_ls/base/images.py` has the decode guard (`DECODE_FAILURES`, `bomb_warnings_as_errors`, `truncated_images_rejected`). `organisations/validators.py` has `validate_organisation_logo`/`check_logo_safety` (untrusted-upload check). `optimise_image` exists for author-supplied files (content_engine). No thumbnail library (no sorl/easy-thumbnails).

## 5. Site-level settings and swappable policy patterns

- Per-site configuration models (all `SiteAwareModel`, one row per site via `UniqueConstraint(fields=["site"])`, no row = default): `SiteSignupPolicy` (`accounts/models.py`: `allow_signups`, `require_name`, `require_terms_acceptance`, `additional_registration_forms`; falls back to `config.ALLOW_SIGN_UPS` when absent), `SiteTimeZoneConfig` (`site_aware_models/models.py`), `SiteMessagingConfig` (`messaging_policy/models.py`, with Organisation/Cohort/Learner/registration-level siblings through the `MessagingFlags` mixin). There is no generic "site settings" model with a display-name field. Closest per-site names: `site_display_name`/`HEADER_TITLE` in `site_aware_models`.
- Project-wide (not per-site) names: `BlogConfig` (`freedom_ls/blog/config.py`): `BLOG_NAME` default "Articles", `BLOG_URL_PREFIX` default "articles". This is the existing precedent for a renameable public index, as a Django setting and not a per-site row.
- `AppSettings` (`freedom_ls/base/app_settings.py`): per app a `config.py` subclass with `declared_settings = {NAME: Setting(default=..., required=...)}`; `config.NAME` returns the project's Django setting or the default; `required_settings_errors` builds system check errors.
- `COURSE_ACCESS_BACKEND`: dotted path, loaded by `freedom_ls/course_access/loader.py` with `import_string`, cached, checked by `course_access/checks.py`. A plain class `CourseAccessBackend` (not ABC) returning a `CourseAccessDecision`.
- Messaging policy (exists in code): `MESSAGING_POLICY` setting (`freedom_ls/comms/config.py`, default `freedom_ls.messaging_policy.policy.LayeredMessagingPolicy`), loaded by `comms/messaging_loader.py` `get_messaging_policy()`; base class `MessagingPolicy` in `freedom_ls/comms/messaging_policy.py` (plain class, methods `can_start`, `can_reply`, `can_reply_many`, `recipients_for`, each raising `NotImplementedError`); returns `MessagingDecision` (`.allowed`, `.reason: MessagingRefusal`; `__bool__` raises). `comms/checks.py` E003/E004 verify the dotted path is an importable subclass of an installed app. Tests need a cache-clearing fixture (`conftest.py`). A profile-index access policy could copy exactly this shape (setting + loader + base class + decision + checks); there is no such thing for profiles today.

## 6. Public/anonymous pages

- Served without login: `blog` (`freedom_ls/blog/views.py` `article_list`, `article_detail`, mounted at `BLOG_URL_PREFIX`), `course_applications` (`applications/apply/<slug>/`, `status/<uuid>/`, `claim/<token>/`, for anonymous applicants), `accounts:legal_doc`, allauth login/signup, `robots.txt`, health, `interest/` (course_interest). `educator_interface` and `learner_interface` require login.
- Multi-site isolation: public views use `Model.objects` (`SiteAwareManager`), which filters on `site` from the request kept in `_thread_locals` (set by middleware; `get_cached_site(request)`). `Article.objects.published()` is the pattern. An unknown Host resolves to `UnknownSite` and falls through unfiltered, to render the 400 page only. `User.objects` (`UserManager`) is site-filtered the same way. The blog uses `get_object_or_404(Article.objects.published(), slug=slug)`; `legal_doc_view` raises 404 when the site is not a `Site`. Test packages exist for isolation, e.g. `educator_interface/tests/invariants/test_organisation_isolation.py`.
- Public URL identifiers: `User` pk is an integer by design ("the one object whose identity appears in a URL as a small sequential number"); `SiteAwareModel` pks are UUIDs.

## 7. Panel framework

- Lives in `freedom_ls/panel_framework`, with a dev reference at `/panel-framework/` (dev only). Used by `freedom_ls/educator_interface` (`Panel`, `DataTablePanel`, `HistoryPanel`, e.g. `LearnerDetailsPanel`, `LearnerCohortsPanel`, `LearnerRegistrationsPanel`, `LearnerMessagesPanel`, `LearnerSettingsPanel` in `educator_interface/views.py`, `LearnerCoursesPanel` in `reporting.py`) and by `comms` (generic code to be gathered) and `reports`. No import of `panel_framework` in `learner_interface`, `accounts`, `blog`, `course_applications`; `learner_interface` and `accounts` are plain Django views plus cotton components.
- Roadmap (`spec_dd/1. next/roadmap.md`, "Panel framework extraction"): `extract_panels_framework-1-gather-generic-code` is in progress; later steps stop it importing FLS, add a template contract, then ship `django-panel-framework` as a separate repo (tag `v0.1.0`, app label `panel_framework`, FLS pins it via a git URL, import prefix changes at step 5). Specs touching `educator_interface`, `comms`, `reports` or `learner_management` must rebase onto step 1.
- Evidence for the editing question: panels are built for educator list/detail pages (tables, actions, filters, dialogs, quick views; per the educator-interface skill). Existing learner-facing self-edit (`edit_profile`) is a plain ModelForm with no panel. Using panels in the learner interface would be the first learner-side use and would depend on a package still in flux; a plain form view matches how `accounts` works today and does not collide with the extraction.
- Educators: the educator learner page already has panels (details, cohorts, registrations, courses, messages, history, settings; Settings tab holds actions with no home beside the thing they change, per `claude_plugins/fls-dev/skills/educator-interface/SKILL.md`). The skill's Placement table has no profile or certificate row. A school/staff certificate upload for a learner would be a new control; per the skill a control sits beside the thing it changes, so a certificates panel on the learner instance page (Overview or its own tab) would be the consistent home. Every action there must also write an audit entry (`noun.verb`, `freedom_ls/audit_log/README.md`).

## 8. Messaging

- `freedom_ls/comms` has direct messages: `Conversation` (exactly two users, `pair_key`), `ConversationParticipant`, `Message`; URLs at `messages/` (`comms/messaging_urls.py`); view `messaging_views.start` and the recipient picker only accept recipients from `get_messaging_policy().recipients_for(sender=..., site=...)` (`_offered_recipients`; others get 404/422).
- `LayeredMessagingPolicy` (`messaging_policy/policy.py`) opens a conversation only for a relationship: educators of a learner, cohort peers, course peers (`NO_RELATIONSHIP` otherwise, `CLOSED_BY_CONFIGURATION` when the layered flags are closed). So an unrelated profile viewer (for example an employer) cannot message a learner today; making it possible means a different `MESSAGING_POLICY` subclass or a new candidate type. Anonymous users cannot message at all.

## 9. Vocabulary (from `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md`)

- Always use `learner` for the person, `Learner` for the `(user, organisation)` row ("not a profile"). A new model keyed on `user` should say why (the glossary says FormProgress, Learner.user, RecommendedCourse key on `user`; enrolment and progress moved to `Learner`). A public profile is per person, so `User` keying would be the case to justify.
- profile: not a glossary term. Already in use: `account_profile`/`edit_profile` (the name-edit page), `Organisation.profile_logo`. `Learner` is explicitly "not a profile". Avoid redefining "profile" without distinguishing it from the account page; "public profile" is new and must be flagged and defined once.
- certificate: not a glossary term. Only the `certificates` storage alias (no consumer) and a roadmap item. Free to define; keep "completion certificate" distinct from an SSL certificate in `docs/deployment-security-checklist.md`.
- school: not a glossary term and no model. The tenancy word is `Organisation` ("a client inside a site"); `Cohort` is a group of learners. Use organisation unless a new noun is coined and defined.
- organisation: taken, `Organisation` in `organisations/models.py`; British spelling in code and prose.
- location: taken: `Location` in `hr_attributes` (per-organisation list entry that retires via `is_active`, `LearnerHRAttributes.location`). A learner's chosen place and "willing to move" is a different concept; naming it `location` would collide. Also `location_start_date`.
- public: used for the `public` storage alias, the "blog" ("the public index"), `Article` ("can be read publicly"). "Public" in the storage sense means anonymous-read bucket.
- employer: not in the glossary or code (grep found nothing). The nearest words: `organisation` (client), `job_title`, `department`, `organisation_start_date` ("hire date"), role names in `roles.py` (`learner`, `observer`, `site_admin`, ...). "role" and bare "title" are reserved/taken (permission role; content title; use `JobTitle`). "talent", "hiring", "work experience": not present.
- Also taken: `grant` (permission), `registered`/`registration` (course access), `staff member`, `item`, `link` as a noun, `is_active` semantics (deactivate/Inactive, never "remove"/"suspend"), `viewed` audit verb for a read worth auditing.
