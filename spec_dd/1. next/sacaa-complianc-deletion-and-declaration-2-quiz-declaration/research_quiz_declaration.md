# Research: quiz declaration (tick and typed name, with time and IP)

Read-only, from code at HEAD of main. Paths are under `freedom_ls/` unless noted. Nothing web-sourced.

## 1. Authoring and where the flag and text sit

- A Form is a `form.md` with YAML front matter plus page files. Pydantic `Form` is `form_engine/schema.py:58`; its form-level options are `strategy`, `quiz_show_incorrect`, `quiz_pass_percentage`, `sections`, `submit_on_exit` (schema.py:70-88), plus `DueDateFields`. `validate_quiz_fields` (schema.py:90) holds the QUIZ-only rules.
- Mirror model `form_engine.models.Form` (models.py:54): `strategy`, `quiz_show_incorrect`, `quiz_pass_percentage`, `submit_on_exit` (default False). `content_save.save_form` (content_save.py:670) maps them; a new field is pydantic field + model field + migration + save mapping (see `research_form_engine_seams.md` section 5).
- So an opt-in flag and a per-form declaration text sit naturally on the Form front matter and `Form` model, beside `submit_on_exit` (e.g. a boolean plus a text field). The markdown body of `form.md` (`MarkdownContent`) is the form intro and is not a fit for a declaration that must be stored verbatim.
- Site-level config: `SiteSignupPolicy` (accounts/models.py:208) is per-site (`allow_signups`, `require_name`, `require_terms_acceptance`) with a global fallback in `accounts/config.py` (`AppSettings`, `Setting(default=...)`; accessor pattern `get_effective_require_name` in accounts/utils.py:106). Every app has a `config.py` of that style; `form_engine` has none. No existing site-level model or setting holds form text. A default declaration text would be a new `AppSettings` entry (global default) or a new per-site model; nothing to reuse directly beyond the pattern.

## 2. Learner quiz start flow (learner_interface)

- Start screen already exists: `view_course_item` (urls.py:21) renders, for a form, `view_form` (views.py:1814) -> `learner_interface/course_form.html`, with question and page counts, the latest 5 completed attempts, and buttons from `form_start_page_buttons` (utils.py:940): "Start Form" / "Continue Form" / "Try Again" / "Next". Nothing is written on this screen ("the start screen reads, form_start writes", views.py:1834).
- Start button goes to `form_start` (urls.py:26, `learner_interface:form_start`, views.py:1885). It checks access and `_blocked_item_redirect`, then `start_attempt` (learner_progress/attempts.py:140) which resumes or creates the sitting via `get_or_create_incomplete` (attempts.py:84), which creates `FormProgress` and its `CourseFormAttempt` together. Then `ensure_served_paper` (form_engine/served_paper.py:45) writes `FormProgress.served_paper` once (QUIZ only), then redirects to `form_fill_page` (`.../fill_form/<page_number>`, views.py:2024) at `resume_page_number`.
- So "before the first page" is a hook between the Start button / `form_start` and the redirect to `form_fill_page`. Today `form_start` is a GET-reachable redirect view with no POST step and no template of its own; a tick and typed name need a POST (the start button is a link/action, not a form, today). Open question for the spec: whether the declaration is a new step before `start_attempt` (no row yet, so nothing to attach it to) or after (an open `FormProgress` exists, flagged as not yet declared, and `form_fill_page` must refuse until declared).
- Resume: an open sitting is resumed via "Continue Form" straight to `form_fill_page`, so a gate must also guard `form_fill_page` (and `form_submit_and_exit`, views.py:2390) or a resumed or deep-linked sitting skips it. Course applications reuse the same page flow (course_applications/views.py:725-870) without this start screen.

## 3. Precedent: LegalConsent

- `accounts.models.LegalConsent` (accounts/models.py:232): `user` FK, `document_type`, `document_version`, `git_hash`, `timestamp` (`auto_now_add`), `ip_address` (`GenericIPAddressField`, null), `consent_method` choices. Append-only: `save()` raises `ValueError` on update of an existing row (models.py:270-282, uses `_state.adding` because the PK is a UUID); the admin is fully read-only as a second layer (accounts/admin.py:88; the comment notes `QuerySet.update()` and `bulk_update()` bypass the guard). It stores a document version and hash, not the text itself, and no typed name.
- IP is read with `accounts.utils.get_client_ip(request)` (accounts/utils.py:24): uses `config.TRUSTED_PROXY_IP_HEADER` (settings_base.py:383 default None; settings_prod.py:132 from env) as the only source when set, rejecting a missing or malformed header with `PermissionDenied`; else `REMOTE_ADDR`. The docstring calls it "the only sanctioned way to derive a client IP for LegalConsent records ... and similar evidence trails". Used at accounts/forms.py:355-364 (`ip_address=ip or None`). System check E003 (accounts/checks.py:123) validates the header name.
- Reusable: yes for IP (`get_client_ip`, called from form_engine or learner_interface; form_engine importing from accounts is a new dependency edge to check). The model is not reusable as is (user + legal document shape, not a form sitting). The append-only pattern (guard in `save`, read-only admin) is the template for "cannot be changed". `FormProgress.served_paper` is the nearest in-form precedent for write-once data ("Written once, before the first page is shown"; conditional `update(... served_paper__isnull=True)` in served_paper.py:55) but it is a JSON column on a mutable row, so it is not truly tamper-proof either.
- Erasure: `LegalConsent` is in `USER_ERASURE_CASCADE_MODELS` (accounts/admin.py:26), so an append-only record still goes with a user erasure. `FormProgress.user` is `on_delete=CASCADE` and `form` is `PROTECT` (models.py:288-299). Relevant to the sibling "deletion" spec in this directory.

## 4. Retakes and attempts

- Yes, multiple attempts per placement: each `FormProgress` is one sitting; `CourseFormAttempt` links it to `(course_progress, collection_item)`; `completed_attempts` returns finished ones newest first (attempts.py:195); a failed quiz offers "Try Again" (utils.py:962-965), which goes through `form_start` and mints a new `FormProgress`. The roadmap states "a retake is a new attempt with a fresh draw and order" (roadmap.md, SACAA compliance, Decided). No attempt-number field exists; `sacaa-compliance-4-attempt-review` expects "its attempt number" (derived).
- Consequence: the declaration naturally attaches per `FormProgress` (per attempt), matching the old brief ("on the form progress record"). Per-form-once would need a different record keyed on user+form and is not suggested by anything in code. Stale submit-on-exit sittings are finalised on the next start (`finalise_stale_incomplete`), and a double start within `START_REUSE_WINDOW` (10 s) reuses a sitting, so a declaration step must be idempotent across those.
- `FormProgress.user` is nullable (anonymous visitor sittings, models.py:284); there is no user to match a typed name against, so the feature is for course-embedded quizzes with a logged-in learner.

## 5. Educator views and export

- Today: no per-attempt educator view. Only Django admin `FormProgressAdmin` (form_engine/admin.py:320; read-only fields at 353-361: `start_time`, `completed_time`, `scores`, `asked`, `served_paper`, `furthest_page_reached`; fieldsets at 367-383; `answers_change_form.html` renders `answer_groups`). A declaration would need adding there to be seen in admin. `educator_interface` only has a content preview (`full_path`).
- `sacaa-compliance-4-attempt-review` (spec_dd/1. next/sacaa-compliance-4-attempt-review/idea.md, blocked by `educator-interface-refactor-5-learner`) plans an educator view in `educator_interface/panels/learner/` of one `FormProgress`: paper served in order, options order, answers and correctness, score, percentage, pass mark, start and completion times, attempt number; `VIEW_LEARNER` permission; open questions include whether to audit-log the view. It does not mention a declaration. This is the natural place to show it; the old brief's "shows them to educators on the attempt" depends on it.
- Export: `form_engine/exports.py` has `answer_columns`, `answer_value`, `answer_cell`, `off_path_question_ids`; consumers found are `course_applications/resources.py:98` and `course_applications/api.py:11` (applications). Columns are per question; attempt-level columns (user, times) belong to the callers' resources, not exports.py. Attempt-review's idea adds served order and seed to "the existing form export", so an attempt-level column group is already planned; the declaration could ride with it, but that is that spec's decision. Whether a learner-quiz export (as opposed to applications) exists was not found in the files searched.

## 7. User name availability

- `accounts.models.User` has `first_name` and `last_name` (`CharField`, blank, default "", max_length 200; models.py:116-117) and `display_name_for(first, last, email)` (models.py:72) behind the user's display name (line 166). `SiteSignupPolicy.require_name` (default True) means names are normally collected at signup, but they may be blank (the field is `blank=True`, and the policy can turn it off), so a comparison cannot assume a name exists. Prefill or a match check against `f"{first_name} {last_name}"` is possible; whether to compare is a spec decision (typed name is the signature; mismatch handling is not defined anywhere).
