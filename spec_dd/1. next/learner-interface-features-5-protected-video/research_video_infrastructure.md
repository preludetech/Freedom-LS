# Research: video infrastructure for access-controlled course video

Scope: embed video in course content so only learners registered for the course can watch, and a shared link is useless to anyone else. Screen recording is out of scope. Source idea: `idea.md` ("video streaming"); landscape in `research_learner_features.md` section 3.

## Facts from the codebase

### 1. The YouTube widget and how widgets reach markdown

- Authors write `<c-youtube video_id="..." video_title="..." caption="...">` in a content file's markdown (`demo_content/functionality_demo_content_widgets/2. media/content.md`, `demo_content/functionality_demo_end_with_topic/6. topic/content.md`). The component is `freedom_ls/content_engine/templates/cotton/youtube.html`: `<c-vars video_id video_title caption>`, an `<iframe src="https://www.youtube.com/embed/{{video_id}}">` inside `<c-media-card>`. It does no access check at all.
- A widget is allowed in content only if it is a key in `MARKDOWN_ALLOWED_TAGS` (`config/settings_base.py:388`), a dict of tag name to the set of permitted attributes (`"c-youtube": {"video_id", "video_title", "caption"}`). Per `docs/how tos/custom-content-widgets.md`, every listed tag is registered as a block-level HTML tag for the markdown pass, then nh3 strips any tag or attribute not listed. A downstream project that overrides the dict must copy new entries across (upgrade notes list `MARKDOWN_ALLOWED_TAGS` under `changed_settings`).
- A new `c-video` widget therefore needs: a cotton template in `freedom_ls/content_engine/templates/cotton/`, an entry in `MARKDOWN_ALLOWED_TAGS`, and updates to the standalone content validator and authoring skill that mirror the allowed attributes (`claude_plugins/fls-content/validate/schema.py`, `claude_plugins/fls-content/skills/widget-reference/SKILL.md` and `resources/c-youtube.md`), plus `docs/product/content-editing-workflow.md:135` widget table.
- Widgets that reference a stored file do it by content-relative path: `pdf-embed.html` does `{% with file_obj=src|get_file_by_path:content_instance %}` then `src="{{ file_obj.file.url }}"`. `picture.html` and `card.html` do the same. This is the precedent for a `c-video src="videos/intro.mp4"` style widget.
- CSP is set report-only in `config/settings_base.py:555`. `default-src 'self'`; there is no `media-src`, so media falls back to `'self'`. `frame-src` lists youtube.com and youtube-nocookie.com. `connect-src` has no storage or CDN origin. Any player that fetches segments from the bucket or a vendor needs `media-src` and `connect-src` entries (and `script-src` if the player library comes from a CDN; `https://cdn.jsdelivr.net` is already allowed).

### 2. File storage

- `STORAGES` aliases (`config/settings_base.py:294-322`): `default` (reserved), `staticfiles`, `public` (logos), `course_media` (`content_engine.File.file`), `user_uploads`, `reports`, `certificates`. Three alias names are settings (`ORGANISATION_LOGO_STORAGE_ALIAS`, `CONTENT_MEDIA_STORAGE_ALIAS`, `REPORTS_STORAGE_ALIAS`). Dev and test use `FileSystemStorage`.
- Production: `config/settings_prod.py:150` calls `build_storages()` (`freedom_ls/deployment/storage.py`). It builds `storages.backends.s3.S3Storage` entries for an S3-compatible store; the code comments name Cloudflare R2 (no ACLs, boto3 checksum headers, region "auto"). Three buckets by sensitivity (public, course media, user data); per-purpose env vars `AWS_S3_<PURPOSE>_*`, falling back to shared `AWS_*`.
- Private vs public: `SIGNED_URL_PURPOSES = {COURSE_MEDIA, USER_UPLOADS, GENERATED}` (storage.py:29). Those use `querystring_auth=True`, `querystring_expire` default 3600 s. The course media bucket holds "Course images, PDFs, video" and is "Private, signed URLs" (`claude_plugins/fls-dev/skills/file-storage/SKILL.md`). Presigned URLs are therefore generated implicitly by `file_obj.file.url` through django-storages (boto3 `generate_presigned_url`). No explicit presign call exists elsewhere; there is no CloudFront or R2 custom-domain signing.
- How content `File`s get in: `content_save` (`freedom_ls/content_engine/management/commands/content_save.py:781-930`) walks the content repo, classifies by extension (`.mp4 .avi .mov .wmv .flv .webm .mkv` map to `File.FileType.VIDEO`, line 786-794), creates a `File` row keyed `(site, file_path)` and calls `file_obj.file.save(...)` (a synchronous upload of the whole file from disk). `File.file` uses `upload_to=file_upload_handler` -> `content_engine/{stem}{pk}{ext}` and `storage=get_content_media_storage` (`content_engine/models/files.py`). Only images get processing (re-encode via `ImageCache`); video is stored as-is, no transcode, no size cap found in that function.
- Access check today: none at fetch time. `docs/product/security-and-data-handling.md:78-84` states it plainly: course pages are access-controlled (a learner must be authorised before FLS renders the link), but the file is protected only by a time-limited signed URL, "a signed link works for anyone holding it until it expires". `docs/product/roadmap.md:109` lists routing every download through the course access check as not yet built. Without object storage, media is served from local disk unsigned (dev only).
- Precedent for Django-streamed, access-checked files: `reports/services.py:104` `report_file_response`, `form_engine/views.py:161` `stream_question_answer_file` (FileResponse, owner-scoped). Both are small files; no byte-range or X-Accel/sendfile handling exists.
- Registration check: `is_registered_for_course(user, course)` in `freedom_ls/learner_management/utils.py` (used by `course_access/backends.py`); `get_course_access_backend().get_access(user=..., course=...)` returns the decision that already wraps visibility and deadline enforcement (`course_access/loader.py:25`). A video-serving endpoint should use the backend decision, not raw registration, so deadline/end-of-access applies.

### 3. Background tasks

- Django 6 `django.tasks` plus `django-tasks-db==0.12.0` (pyproject.toml:35). `TASKS` is `ImmediateBackend` in dev/test (`config/settings_base.py:615`), database backend in prod (`settings_prod.py:85`). Worker: `manage.py fls_run_worker` (`freedom_ls/deployment/management/commands/fls_run_worker.py`, `deployment/worker.py`, a copy of the db_worker loop with a heartbeat). No Celery, no Redis. Tasks exist in `freedom_ls/registration_rules/tasks.py` and `freedom_ls/mail/tasks.py` (priority convention `EMAIL_TASK_PRIORITY = 10`).
- Housekeeping: `freedom_ls/deployment/housekeeping.py` `run_housekeeping_sweeps()` reaps orphaned running tasks and generated reports, stale previews and finished records. A transcode sweep (re-drive jobs whose task was lost) would slot in beside `mark_orphaned_running_reports_failed`.
- file-scanning spec (`spec_dd/1. next/file-scanning/0. idea.md`, parked in next) designs the exact pattern a transcode job would reuse: status column on the row, `@task` taking only the row id, enqueued via `transaction.on_commit`, errors propagate so the worker marks the result FAILED, plus a sweep for rows whose task was lost. It explicitly excludes course content from scanning.
- ffmpeg: no reference anywhere in `freedom_ls/`, `config/`, `docs/` or `claude_plugins/fls-content/`. There is no Dockerfile in this repo (deployment lives in a separate infrastructure repo; see `spec_dd/3. done/2026-08-31_08:32_deploy_prep_2/notes_from_infrastructrure_repo.md`). A self-hosted transcode adds a new system dependency FLS does not have, and a long CPU-bound job inside the single database-backed worker (no per-queue concurrency control found).

### 4. Pluggable backend precedent

- `COURSE_ACCESS_BACKEND`: dotted-path string in settings; `freedom_ls/course_access/config.py` declares it `Setting(required=True)` on a `CourseAccessConfig(AppSettings)` (`freedom_ls/base/app_settings.py`: `Setting(default, required)`, lazy read, `ImproperlyConfigured` if required and missing, `missing_required()` for a system check). `course_access/loader.py` resolves with `import_string` inside a `functools.cache`d getter, wrapped in enforcing decorators; tests must `cache_clear()`.
- Other dotted-path backends: `EMAIL_UPSTREAM_BACKEND`, `FREEDOM_LS_ICON_BACKEND`, and the removed/planned `FILE_SCAN_BACKEND` (file-scanning idea, with the lesson: do not ship a seam with nothing real behind it; a safe default must clear nothing).
- A `VIDEO_BACKEND` would be: `VideoConfig(AppSettings)` in the owning app's `config.py` with `VIDEO_BACKEND: Setting(default=<shipped class>)`, a base class (or Protocol; the project rule is no abstract base classes unless asked) with e.g. `playback_context(user, video) -> dict`, and a cached `get_video_backend()` loader. The widget template renders whatever partial the backend names.

### 5. How content and video enter the system

- Content is a git repo of markdown plus assets, loaded with `uv run python manage.py content_save <path> <site_name>` (`docs/product/content-editing-workflow.md:8,109`). UUIDs are written back into frontmatter. Binary assets "are uploaded and stored by `content_save` alongside text content" (line 163). Drafts are `_`-prefixed.
- Where a video would live in authoring: either (a) a video file in the content repo, found by relative path via `c-video src="..."` (reuses `File` + `get_file_by_path`; bad fit for git: large binaries, LFS or repo bloat, and `content_save` uploads synchronously); or (b) a hosted-video identifier attribute on the widget (`<c-video video_id="...">`), mirroring `c-youtube`'s `video_id`, with the bytes uploaded to the video host out of band by the educator. (b) needs no FLS change to ingestion and matches how authors already work; (a) needs a transcode pipeline and an ingest path other than git.

## Web verification (current as of 2026-11-12)

- Cloudflare Stream: `requireSignedURLs: true` blocks public links including the built-in player URL until a token is presented. Recommended at scale: create a signing key once (`POST /stream/keys`) and sign tokens locally with no per-token API call; the `/token` endpoint is rate-limited (about 1,000 tokens/day guidance). `exp` max 24 h ahead; optional `nbf`, `accessRules` (ip, country; first match wins; add a final block-all rule or unmatched is allowed). Revoking a key invalidates all its tokens. Allowed Origins is a separate, Referer-based control. https://developers.cloudflare.com/stream/viewing-videos/securing-your-stream/
- Mux: assets with `playback_policies: signed` need an RS256 JWT (`sub` playback id, `aud` v/t/g/s/d, `exp`, `kid`) appended as `?token=`; keys are created once via dashboard/API and the private key stays on the server. Token expiry must cover the whole video duration or playback dies mid-stream; separate tokens for poster/storyboard; optional referrer/user-agent restrictions; DRM via `aud=d`. Keep PII out of claims. https://www.mux.com/docs/guides/secure-video-playback
- CloudFront signed cookies: the app authenticates the user and sets the signed cookie; CloudFront checks it on the playlist and every segment, which suits HLS. It requires CloudFront in front of S3; our store is R2 (not S3), so this option means adding AWS (S3 + CloudFront) rather than reusing the existing buckets. https://aws.amazon.com/blogs/aws/new-amazon-cloudfront-signed-cookies-for-private-content
- Self-hosted HLS with AES-128: ffmpeg encrypts segments, the key URI in the playlist points at an authenticated Django endpoint; shared segment/playlist URLs are useless without the key. Needs ffmpeg + a player library (hls.js outside Safari) + CSP changes. Guide: https://ittybit.com/guides/encrypt-hls-streams.md (from the earlier research file; not re-fetched). Caveat: the key is just bytes returned to any logged-in registered learner, so a registered learner can fetch and share the key and playlist; per-learner key URLs (token in the key URI, short TTL) narrow this.
- Which is simplest with no vendor? None is simple. Self-hosted HLS+AES needs the ffmpeg worker, a ladder, a key view, a manifest rewrite (segment URLs on R2 are presigned per object, so either rewrite each segment URI to a presigned URL per request, or serve segments through Django, which is heavy), and a JS player. CloudFront cookies are simpler operationally but are a vendor (AWS) and a stack change. A managed host with signed tokens (Cloudflare Stream: R2 is already Cloudflare) is the least code: a signing key in settings, a token generated at render time, an iframe or player URL. Costs and the pricing table are in `research_learner_features.md` section 3 (not re-verified here).

## Implications for the cut

1. The real gap is "a link works for anyone holding it". The security doc itself says per-request authorisation of files is not built. Two distinct problems hide in the idea: (A) video-specific protection (short-lived, per-learner, tied to registration), and (B) the general file-fetch authorisation gap. A video spec solves A without needing B; do not widen it to B.
2. Minimal first video spec (smallest thing that satisfies the idea): a `c-video` widget with a `video_id` (provider's id) and `video_title`/`caption`, plus a `VIDEO_BACKEND` dotted-path setting (`AppSettings`, loader with `functools.cache`, same idiom as `COURSE_ACCESS_BACKEND`) and ONE real backend behind it, so there is no seam with nothing behind it (lesson from file-scanning). At render time the backend asks `get_course_access_backend().get_access(...)` for the learner, and only a permitted learner gets a signed, short-lived playback URL or token; others get the locked state the course player already uses. Token lifetime must outlast the video (Mux) or be re-minted on resume; Cloudflare caps at 24 h. Add the new origins to the report-only CSP (`frame-src` or `media-src`/`connect-src`), the widget to `MARKDOWN_ALLOWED_TAGS`, the validator/widget-reference skill, and product docs. Videos are uploaded to the host by the educator out of band; no FLS upload UI, no transcode, no ffmpeg, no worker work.
3. Decision to make before specifying: which first backend. Candidates: Cloudflare Stream (signing key, local JWT-style signing, same vendor as the R2 storage already in use) or Mux (JWT, RS256, `mux_python` optional; the token logic is small enough to need no SDK). Either is roughly one signing function plus a template partial. Self-hosted HLS+AES-128 is the only no-vendor path and should be a later backend, not the first: it introduces ffmpeg (absent today), a CPU-bound task in the single db worker, a key endpoint, a manifest rewrite for R2's per-object presigning, and hls.js.
4. Watermark (learner email overlay) is a cheap deterrent for sharing that can ride on the first spec as a template overlay, but it is a UI decision, not infrastructure; the research file flags it as an open threat-model question.
5. What could follow, each separable:
   - Captions: store VTT in FLS (a `File` of type DOCUMENT/OTHER or a new field) so they survive a provider switch; WCAG 1.2.2 Level A makes this important. Requires per-widget `captions`/`track` attributes and is a distinct spec.
   - Watch tracking / completion: needs a JS player events endpoint, a model (learner, video, unique seconds), and a decision on whether a video counts toward topic completion. Large; separate spec.
   - Upload UI: educators uploading to the host through direct upload (Mux direct upload / Cloudflare TUS) from the educator interface; needs a model for a stored video record (provider id, status, duration) and likely webhooks from the host. Only then is a video row needed; the first spec can use a bare `video_id` attribute.
   - Self-hosted HLS backend: depends on a transcode task using the file-scanning pattern (status column, `@task` by row id, `on_commit`, housekeeping sweep) and ffmpeg in the deployment image (infra repo change).
   - Routing all course-media downloads through the access check (problem B above): independent roadmap item (`docs/product/roadmap.md:109`); would give a general per-request authorisation seam that a self-hosted video backend could reuse.
6. Keep the existing `c-youtube` as-is and documented as unprotected (answers the design question in research section 3).
7. Compatibility flags for the spec author: FLS is installed into other projects, so the setting needs a safe default. Following the file-scanning rule, the default must fail closed (no playback for anyone) or the widget must show an explicit "video backend not configured" state, never an unprotected fallback; `VIDEO_BACKEND` as `required=True` mirrors `COURSE_ACCESS_BACKEND` but breaks every existing install on upgrade, so prefer a default with a system check. Per-site credentials: `SiteAwareModel` is multi-site, but settings are global; a host account per site is an open question the spec must settle.
