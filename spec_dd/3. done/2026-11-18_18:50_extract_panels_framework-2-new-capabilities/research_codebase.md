# Research: codebase (what spec 2 touches, reuses or conflicts with)

Paths are relative to the worktree root. Line numbers are as of branch `extract_panels_framework-2-new-capabilities` (HEAD a762fc492). I had no shell, so there is no `git log` evidence: authorship comes from the done specs and from the code.

## Headline findings

1. **Row detail already exists in the framework, and was built by the audit-log design spec, not by spec 1.** The idea's "Open until the spec" question 1 is answered: the other case holds. The default ("it did not; build fresh") is wrong. The framework already has the Python option, the cotton markup, the Alpine toggle, the mobile-card variant, CSS and tests. What is missing is only what the idea lists beyond that: nested child rows, an inline-vs-fetched choice (not needed), and a compact density option (nothing exists). Details in section 3.
2. **The option is named `row_detail_template_name`, not `row_detail_template`.** Spec 1 renamed it (`spec_dd/3. done/2026-11-16_19:13_extract_panels_framework-1-gather-generic-code/upgrade_notes.md:48`). The idea text still says `row_detail_template`; the spec should use the shipped name.
3. **The audit log is not left with a duplicate:** it already consumes the framework option (`AuditLogEntryTable.row_detail_template_name`, `freedom_ls/educator_interface/views.py:916`). Nothing needs to move out of `educator_interface` for row detail. Spec 2's job is to extend, not extract.
4. **The `as_of` stamp has no home in the loaded template today.** `lazy_panel.html` only includes the region template; the loaded state lives in `_lazy_region.html` (shared frame), which each consumer extends with a `loaded_body` block. A stamp must go into `_lazy_region.html` (or around `loaded_body`) so no subclass template changes.
5. **`reason_field.html` includes `partials/form.html`, which lives in `freedom_ls/base/templates/partials/form.html`** (a host template). That is a spec 4 template-contract concern, but a new select/required rendering will go through the same host include.
6. **The reference page is static cotton markup in `_examples.html`, with no entry yet for DataTable, lazy panels, reason dialogs or actions.** `reference.py` holds only `EXAMPLE_CONTEXT` and the view. Three new "entries" are therefore new `<section>`s in `_examples.html` plus new names in the test's `COMPONENT_NAMES` (section 5).

How it works:

- `ReasonForm.__init__(self, data=None)` builds the field in `__init__` (so subclass class attributes apply): `forms.CharField(required=False, max_length=self.reason_max_length, strip=True, label=self.reason_label, help_text=self.reason_help_text)`. Class attributes `reason_label = "Reason (optional)"`, `reason_help_text = ""`, `reason_max_length = REASON_LENGTH`. **Required is hard-coded `False`** (`forms.py:27`): the required variant needs a new class attribute (e.g. `reason_required`) read here, or a form subclass.
- `ReasonMixin.get_context_data` (`actions.py:730-733`): `context.setdefault("reason_form", self.reason_form_class())`. Only the unbound form on GET.
- `ReasonMixin.handle_submit` (`actions.py:735-745`): binds `reason_form_class(ctx.request.POST)`; invalid gives `render_to_string(self.get_fragment_template_name(), {**self.get_context_data(ctx), "reason_form": form}, request=...)` with `HttpResponse(html, status=422)`. Valid gives `self.handle_confirmed_submit(replace(ctx, reason=str(form.cleaned_data["reason"])))`.
- `handle_confirmed_submit` calls `super().handle_submit(ctx)` (the next in MRO). The form is only constructed with `data`; there is no per-request hook (no `ctx`, no `request`), so a per-request computed choice list needs the form constructor or a hook to receive `ctx`.
- So the 422 on an over-long reason already exists and is tested: `tests/test_actions.py:1708-1720` (`test_an_over_length_reason_is_a_422_with_the_field_re_rendered`: asserts `422`, the input re-rendered with the posted value, and a `.text-error` element). An empty required reason would reuse that exact path.
- Actions read the reason as `ctx.reason` (educator examples: `educator_interface/actions.py:489, 571, 635, 783, 887, 1052, 2419, 2583, 2771`). A chosen reason (the select) would need a second `ctx` field. `PanelContext` is a frozen kw_only dataclass; its docstring says new fields can be added with a default without breaking subclasses (`context.py:31-35`). Candidate: `reason_choice: str = ""` beside `reason`.

Existing action option naming (to follow in new names), all class attributes unless noted:

### What the outline needs from `<c-data-table>` to move

`cotton/data-table.html` is rendered from explicit context (it does not need a queryset: it takes `columns`, `header_columns`, `rows`, etc.), so the outline can include it directly with prebuilt row dicts; `DataTable.get_context` and `DataTablePanel` (queryset, paging, search, sort, `get_row_label`) do not fit rows that come from `Course.collection_items()`. Needs:

1. **Columns:** `#` (`tabular-nums`, muted, `w-0`), Title, Type (`md` and up only, which is `Column.card = "md_only"`/`header_class`/`cell_class`), Actions (`c-data-table-actions` with `modal-trigger`, per-row `aria_label` and URL, so the cell template needs the row's `preview_query` and the panel's `row_action_urls`; the cell templates currently receive only `object` and `column`, so these come from `object` = the `OutlineRow`). The title cell is custom: depth indent, optional chevron, icon + sr-only kind label.
2. **Row shapes:** a normal row; a group row (chevron); a child row indented by depth and hidden when any ancestor is collapsed; a note row spanning columns with no hover (`colspan`, `hover:bg-transparent`); the course-details row; an empty-state row inside the table when the course has no items.
3. **Nested child rows:** today's row-detail is one hidden `<tr data-row-detail>` carrying `include row_detail_template_name`, controlled by `rowDetail` through `hidden`. The outline's children are full data rows with their own columns, their own chevrons and their own children, controlled by `aria-controls` listing several ids and hiding at any ancestor. So the framework needs a row-level notion of `row_id`/`parent_ids`/`child_row_ids` (or equivalent) on the row dict, and a toggle that handles multiple controlled ids and arbitrary depth. The existing `rowDetail` toggle handles exactly one id via `aria-controls`; `courseOutline.shown()` implements the ancestor rule through reactive `collapsed` state. The user allows custom child-row overrides if useful (e.g. a `row_template_name`/child-row template so the title cell can be custom).
4. **Expand-all / default open state:** the outline starts **open** (server renders `aria-expanded="true"`), the opposite of row detail (closed). No expand-all or collapse-all control exists on either today; none is required by the idea.
5. **Card layout:** the outline has no mobile card layout (the table scrolls, with only the Type column hidden below md). `<c-data-table>` renders a `<ul>` of `c-data-table-card` below md; the outline would need either a card form for nested rows or `cards_when_narrow`-style opt-out. The test selectors (`[aria-label='Course outline'] tbody tr`) read the table, which is `hidden` below md but present in the DOM.
6. **Toolbar/footer/region plumbing:** `data-table.html` always includes `partials/table_toolbar.html` (search, filters, sheet) and renders a `data-table-region` with `id="{{ region_id }}"` and `entry_count` footer when set. Static rows with no filters/search should render no toolbar; verify `table_toolbar.html` renders nothing when `searchable`, `toolbar` and `sortable_columns` are empty, otherwise add a switch.
7. **Accessible name:** the table's `<caption>` is `{{ noun|default:"Data"|capfirst }}` and the scroll region `aria-label` is the same, so `noun="course outline"` gives `aria-label="Course outline"` (matches the tests and the Playwright selector).
8. **Query budget:** the outline test asserts bounded queries; rows are already in memory, so no extra queries are introduced, but `get_row_label` should not touch the DB.
