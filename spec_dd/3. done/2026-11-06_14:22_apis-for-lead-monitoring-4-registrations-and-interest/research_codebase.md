## 2. The models

`freedom_ls/site_aware_models/models.py`: `SiteAwareModelBase` (site FK PROTECT, `objects = SiteAwareManager()`), `SiteAwareModel` (+ UUID `id`), `TimestampedModel` (abstract: `created_at` auto_now_add, `updated_at` auto_now).

### LearnerCourseRegistration (`freedom_ls/learner_management/models.py:240`)
`LoadedIsActiveMixin, SiteAwareModel`. Fields: `course` FK (PROTECT, related `learner_registrations`), `learner` FK Learner (CASCADE), `is_active` (default True), `self_registered` (default False, "False for registrations made before this field existed"), `registered_at` (auto_now_add). Unique `(site, learner, course)`. No `updated_at`, no `created_at`. Latest learner_management migration: `0009_learnerimport_learnerimportrow`.

### CohortCourseRegistration (`:278`)
Same, with `cohort` FK (CASCADE, related `course_registrations`), no `self_registered`. Unique `(site, course, cohort)`.

### Learner (`:151`)
`LoadedIsActiveMixin, SiteAwareModel`: `user` FK (CASCADE), `organisation` FK Organisation (PROTECT), `is_active`, `created_at`. Unique `(site, user, organisation)`. No `updated_at`. So organisation reach for a registration is `registration.learner.organisation` (id UUID, `name`), user via `registration.learner.user` (int pk, `email`). A cohort's organisation is `cohort.organisation` (`Cohort` is `TimestampedModel`, has `name`, `is_active`, `organisation`).

### Organisation (`freedom_ls/organisations/models.py:63`)
`SiteAwareModel, TimestampedModel`; `name`, `slug`, `is_default`.

### CourseInterest (`freedom_ls/course_interest/models.py:16`)
`SiteAwareModel` only: `user` FK (CASCADE, related `course_interests`), `course` FK (CASCADE, related `interests`), `created_at` (auto_now_add). Unique `(site, user, course)`. Latest migration `0001_initial` only. Note the docstring NOTE: a future `notified_at` is planned; the model must stay "standalone and additive". `created_at` already exists, so use a bare `updated_at = DateTimeField(auto_now=True)` or `TimestampedModel` (redefining `created_at` on the concrete class overrides the abstract one in Django, which works but is redundant; mixing would also be wrong for registrations, whose creation stamp is `registered_at`, not `created_at`).

### Mixin choice (decision for the spec)
- Registrations have `registered_at`, no `created_at`. `TimestampedModel` would ADD `created_at` (auto_now_add) duplicating `registered_at`; the same awkwardness spec 5 flags for `CourseProgress.created_at`. A bare `updated_at = models.DateTimeField(auto_now=True)` per model avoids a duplicate column and a second backfill. Foundation tests/pagination only need an `updated_at` attribute (`ApiKeysetPagination` types `M` as `TimestampedModel` but nothing enforces it at runtime; `helpers.paginate_all` is typed the same).
- `LoadedIsActiveMixin` (`models.py:64`) overrides `save`; fine with extra fields.

## 3. Where rows are written (the `auto_now` hazard)

`auto_now` is set in `pre_save`, but with `save(update_fields=[...])` the column is only written if `updated_at` is IN `update_fields`. Every production flip of `is_active` uses `update_fields=["is_active"]`, so adding `auto_now` alone leaves `updated_at` STALE on exactly the event the idea cares about (deactivate/reactivate):

- `freedom_ls/learner_management/utils.py:209-210` (reactivate cohort registration) and `:242-243` (deactivate), in the cohort-registration create/set-active path (`_base_manager.get_or_create` at `:204`, `select_for_update().get` at `:238`).
- `freedom_ls/learner_management/learner_actions.py:343-344` (reactivate learner registration after `_base_manager.get_or_create` at `:333`) and `:385-386` (deactivate).
- `freedom_ls/registration_rules/evaluation.py:473` (`registration.save(update_fields=["is_active"])`, rule retraction).
- Precedent for the fix in this very file: `learner_actions.py:138` already does `locked.save(update_fields=["is_active", "updated_at"])` for `Cohort`. Spec must list these 5 call sites (or override `save` on `LoadedIsActiveMixin`-using registration models to append `updated_at` to `update_fields` when it is not None; note `LoadedIsActiveMixin.save` already normalises `update_fields` to a frozenset, and signal receivers read `update_fields` from the post_save kwargs, e.g. `registration_rules/signals.py:213,316`, `course_recommendations/signals.py`, `learner_progress/signals.py`; adding `updated_at` to the set must not break their `"is_active" not in update_fields` / `isdisjoint` tests). A model-level `save` override is safer than patching call sites, and a test can pin it.
- Create paths: `_base_manager.get_or_create` (utils.py:204, learner_actions.py:333) set defaults via `save`, so `auto_now` fires on create. Admin saves (`LearnerCourseRegistrationAdmin`, `CohortCourseRegistrationAdmin`, inlines at `admin.py:146,320`) call full `save`, so they move `updated_at`. `registration_rules` creates registrations through `save`-based paths ("Not bulk_create" comment at `evaluation.py:258`).
- Queryset `.update()` / `bulk_create` on registrations in NON-test code: none found in production modules (all hits are tests: `reports/tests/test_gather.py:166`, `registration_rules/tests/test_evaluation.py:1279` `_base_manager.bulk_create`, `test_signals.py:285,322,1249`, `learner_progress/tests/test_signals.py:716,755`, `course_access/tests/test_backends.py:556`, `learner_management/tests/test_utils.py:523`, `test_queries.py:149,160`, `learner_progress/tests/test_queries.py:306`) and `qa_helpers` commands (`qa_create_permissions_scenario.py:129,144` update, `qa_create_course_access_types.py:153` update). Those do not move `updated_at` but are test/QA only; the spec need only state "no production bulk update exists" and that new ones must set `updated_at`.
- Hard deletes (invisible to `updated_since`, as the idea accepts): `CourseInterest` toggle off `course_interest/views.py:101` (`.filter(...).delete()`); registrations are `PROTECT`ed by `CourseProgress` (`learner_progress/models.py:119-132`), so a registration with progress cannot be deleted; admin can delete a registration with no progress; deleting a `Cohort` CASCADEs its `CohortCourseRegistration` rows (cohort delete is allowed when it has no memberships/registrations in the educator interface, per roadmap decision 1; admin may differ); deleting a `Learner` or `User` CASCADEs registrations/interest; deleting `User` CASCADEs `CourseInterest`.
- Writers that change the FLATTENED data without touching the registration row: `Learner.is_active` flips (`learner_actions.py:55-58`), `Cohort.is_active` flips (`:135-139`), user email/name changes, organisation rename, course title edits. None moves a registration's `updated_at`, so a script keyed on `updated_since` sees stale `email`/`organisation`/`course title`. Document this in `docs/api.md` as it is for `last_login` ("a full pull always has the current value"), or decide to accept. Note `Learner.is_active=False` effectively revokes access via `LEARNER_REGISTRATION_GRANTS_ACCESS = Q(is_active=True, learner__is_active=True)` (`learner_management/queries.py:101`) even though the registration row's `is_active` stays True: an API consumer reading only registration `is_active` over-reports active access. Out of scope per idea (Learner is not a resource) but worth one sentence in docs.
- Course interest: only ever created (`get_or_create`, `views.py:31`) or deleted. No update path exists, so `updated_at` will equal creation time except after a future `notified_at`. Fine; `auto_now` future-proofs it.

## 4. Data migration for `updated_at`

- Adding a non-null `auto_now` field to existing rows needs a default. Options: (a) `AddField(null=True)`, `RunPython`/`RunSQL`/`F()` update setting `updated_at = registered_at` (registrations) / `created_at` (interest), then `AlterField` to non-null `auto_now=True`; (b) one `AddField` with `default=timezone.now, preserve_default=False` stamps every old row with the migration time — wrong for `updated_since` (every row looks changed at deploy; acceptable only if stated, but backfilling from `registered_at`/`created_at` is the honest value and matches spec 5's idea, "latest of the row's existing timestamps"). Use (a) so a script's first full pull orders by true age.
- Do the backfill with `QuerySet.update(updated_at=F("registered_at"))` inside `RunPython` on the historical model (no `save`, no signals, no `auto_now` rewriting); on historical models `objects` is a plain manager, but use `_base_manager`/`objects` per what the migration state offers (see `learner_management/migrations/0006_delete_orphan_cohort_role_rows.py` for a data migration precedent in this app). Also a reverse no-op.
- Index: foundation added `accounts_user_site_updated_idx` on `(site, updated_at, id)` (`accounts/migrations/0004_user_accounts_user_site_updated_idx.py`; `Meta.indexes = [Index(fields=["site","updated_at","id"], name=...)]`). The same index is warranted on each of the three models (every list query is `site_id = X ORDER BY updated_at, id`). Index names max 30 chars.
- Migrations are per app: `learner_management` (next number `0010_...`, covers both registrations) and `course_interest` (`0002_...`). `learner_management/tests/test_migrations.py` exists (contains no matching test names in my grep; check its pattern before adding a backfill test). Run `uv run manage.py makemigrations` then migrate; never edit old migrations.
- Admin: `list_filter`/`readonly_fields`/fieldsets in `learner_management/admin.py:350-388` show `registered_at`; adding `updated_at` as readonly in the "Timestamps" fieldset is optional (idea says "changing the admin exports" is out; do not touch `SiteAwareExportModelAdmin` resources; check whether any registration/interest `ModelResource` exists, none found in grep). `course_interest/admin.py` should be read before touching.
- Factories: `LearnerCourseRegistrationFactory`, `CohortCourseRegistrationFactory` (`learner_management/factories.py:99,110`) and `CourseInterestFactory` (`course_interest/factories.py:13`) extend `SiteAwareFactory`; `auto_now` ignores a passed `updated_at` on create, so tests that need specific timestamps must `Model._base_manager.filter(pk=).update(updated_at=...)` or use `time_machine`.

## 5. One endpoint vs two (what the code says)

- `ReadOnlyApiViewSet` is a `ReadOnlyModelViewSet`; `ApiKeysetPagination.paginate_queryset` filters/orders one ORM queryset by `updated_at` and `pk` and decodes the cursor pk with `queryset.model._meta.pk.to_python`. `DjangoFilterBackend` needs a single `Meta.model` FilterSet. A merged list over two tables would need: a UNION queryset (no `.filter()` after union, so the keyset `Q(...)` and `site_id` filter in `filter_queryset` cannot apply; they would have to be pushed into each branch), or a custom paginator/viewset merging two page streams, which diverges from the foundation convention and its tests. Detail lookup by id would also need to probe two tables.
- UUID pks are unique across tables in practice but the cursor's tie-break `(updated_at, id)` would then compare ids from two tables; workable (UUID total order) but fragile and not what `ApiKeysetPagination` implements.
- Two endpoints follow the existing pattern with zero changes to `freedom_ls/api/`: e.g. `learner-course-registrations` (basename `learner_course_registration`) and `cohort-course-registrations` (basename `cohort_course_registration`), plus `course-interests` (`course_interest`). Kebab-case plural paths per roadmap decisions. Both registration endpoints in `learner_management/api.py`, interest in `course_interest/api.py`.
- A `kind` field on a merged list is only needed if a script wants one stream; a script can pull two. Spec 5's `CourseProgress` already exposes the registration id plus kind itself (`learner_progress/models.py`: exactly one of `learner_registration` / `cohort_registration`, CHECK `course_progress_has_exactly_one_grant`), so with two endpoints a script joins course-progress `registration_id` + kind to the right registration endpoint by id. With two endpoints, spec 5's "kind" field is a new constant, not shared with a field of spec 4 (spec 5 idea lists this as open: "whether the registration kind field is shared with... the `kind` field child 4 may introduce"). The spec 4 answer must say: (merged) `kind` values and registration `id` namespace, or (split) the two endpoint names that course-progress' `registration_kind` values should mirror (e.g. `learner` / `cohort`).

## 8. Query shape and hazards

- N+1: the idea's flattening touches `learner -> user`, `learner -> organisation`, `course`, and (cohort) `cohort -> organisation`. `get_queryset` must `select_related("course", "learner__user", "learner__organisation")` for individual and `select_related("course", "cohort__organisation")` for cohort; interest `select_related("user", "course")`. No prefetch needed. Pin with `django_assert_num_queries` independent of page size (foundation test pattern for users: "query count fixed regardless of page size").
- Use `Model._base_manager` as the base (not `.objects`), because `filter_queryset` adds `site_id`. But joined rows: a registration's `learner`, `course` and `user` come from joins and are not site-filtered; cross-site leakage would need a registration on site A pointing at a learner/course on site B. `CourseProgress.clean` checks `learner.site_id == course.site_id`; registrations do NOT have an equivalent check in `clean` (only `validate_course_open_to`). Low risk, but the serializer should not expose anything beyond the flattened fields; add one test with a second site to assert other-site rows are absent from list and 404 on detail.
- `User.objects` is site-filtered via thread-local request; `select_related("learner__user")` does not use managers for joins, so no problem. Accessing `registration.learner` lazily (without select_related) goes through `_base_manager`, fine.
- Course title: `course.title` from `content_engine.Course` (UUID pk, `BaseContent` with `title`); serializer needs `course_id` + `course_title`; both via select_related. Course is `PROTECT` on registrations, `CASCADE` on interest (deleting a course deletes its interest rows silently).
- Cohort registration "kind of learner" analogue: expose `cohort_id`, `cohort_name`, and cohort's `organisation_id`/`organisation_name` so the two kinds share the organisation field names (idea says "carries the cohort in place of a learner").
- `registered_at` is `auto_now_add` and cannot be backdated via the API; serializers read only. Ordering is by `updated_at`, so `registered_at` appears non-monotonic in output; that is expected and should be said in docs.
- Hazard: pagination cursor uses `last.updated_at.isoformat()` microsecond precision; Postgres stores microseconds; fine.
- `is_active` semantics for docs: registration `is_active=False` is deactivation (soft). Roadmap decision 1: educator interface deactivates, never deletes. So the registration feed is a faithful state feed except admin hard deletes and cohort/learner/user cascades.
- Rule-made registrations (`registration_rules`) are `self_registered=False` (roadmap registration-rules decision 10) — a script cannot tell staff-placed from rule-placed; the optional `registration_rules.RuleRegistration` (1:1 `registration`) exists but is out of scope.
- Webhook payload (`learner_progress/signals.py:179`) already serialises `registered_at.isoformat()`; no shared serializer to reuse.
