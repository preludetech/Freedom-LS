# Research: known complaints about registration and interest export APIs

Scope: complaints specific to enrolment/registration lists, interest lists and incremental-sync of them. Generic API complaints (keys, 401/403, throttling, cursor ties, overlap windows, OPTIONS, schema) are in the foundation's `research_known_complaints.md` and are not repeated. Other systems keep their own terms (enrolment, section, enrollment state). FLS terms: `LearnerCourseRegistration`, `CohortCourseRegistration`, `CourseInterest`.

Evidence level: (web) = seen in a search result snippet or summary this run; I fetched no full threads, so quotes are paraphrased from search summaries. (experience) = general practice, unverified.

## Findings

| # | Complaint | Evidence | What this spec should do |
|---|---|---|---|
| 1 | Deactivated/dropped enrolments vanish from default list calls. Canvas only returns deleted enrollments if you pass `state[]=deleted`; the Course Users endpoint omits deleted users and does not accept the deleted state. | (web) https://community.canvaslms.com/t5/Canvas-Question-Forum/Students-are-randomly-being-dropped-from-Courses/m-p/637757 ; https://community.canvaslms.com/t5/Canvas-Ideas/API-Update-Courses-API-to-Allow-More-User-Enrollment-States/idi-p/540241 | Return inactive registrations by default with `is_active` visible. No hidden default filter. Optional `is_active` filter is acceptable but must not be the default. State in docs that rows are never dropped for being inactive. |
| 2 | `updated_at` on an enrolment is unreliable as a change signal: bulk operations stamp many rows with the same second; it records only when the record last entered its current state; one Thinkific guide describes it as "last activity" rather than any change. | (web) https://community.canvaslms.com/t5/Canvas-Question-Forum/Students-are-randomly-being-dropped-from-Courses/m-p/637757 ; https://www.rapidevelopers.com/md/retool-integrations/thinkific | Define `updated_at` as "any change to the row, including `is_active` toggles". Add a test per model: create, deactivate, reactivate, and `self_registered` edits each advance it. Test bulk-created rows with identical `updated_at` walk correctly (foundation tie test). Audit every write path (admin actions, `bulk_update`, `QuerySet.update()`, management commands, registration-on-signup flows) so none skips `updated_at`. |
| 3 | Deletions invisible to incremental sync. Cursor/`updated_at` sync cannot see removed rows; Airbyte says only CDC captures deletes; Fivetran delete capture is per table and a resync cannot detect earlier deletes; full refresh is the only cleanup. | (web) https://discuss.airbyte.io/t/how-airtbyte-incremental-sync-mode-handles-data-which-is-deleted-in-the-base-system/1247 ; https://github.com/airbytehq/airbyte/discussions/82094 ; https://support.fivetran.com/hc/en-us/community/posts/42307693020567-Fivetran-Feature-Request-capture-deletes-on-the-Clockify-TIME-ENTRY-table?page=1 ; https://support.fivetran.com/hc/en-us/community/posts/37468360263447-Destination-Improvement-During-resync-fivetran-synced-timestamp-should-update-for-records-that-are-deleted | Already settled: no deletion feed. Docs must name which rows hard-delete (`CourseInterest` toggled off; registrations if an admin deletes) and say a periodic full walk of ids, diffed against the local copy, is the only way to detect them. Example script should offer a `--full` mode that does this reconciliation. Registrations are deactivated, not deleted, in normal flows: say so if true (verify in code). |
| 4 | Cannot tell self-enrolled from staff-enrolled. Moodle splits this over enrolment instances (manual vs self) and the core enrolled-users web service does not make the method obvious or give per-enrolment status; suspension is handled via filters and `onlyactive` flags rather than a field. | (web) https://moodle.org/mod/forum/discuss.php?d=305578 ; https://github.com/moodle/moodle/blob/1c059cb3fe39da46959e912dc671844dd204e83b/enrol/upgrade.txt | Expose `self_registered` and `is_active` as plain booleans on every individual registration (settled). Document `self_registered` precisely: true when the learner placed themselves, false for staff, import or cohort placement. Check the model default and the data migration story for existing rows (null versus false) and say which. Cohort rows do not have it; say why in docs. |
| 5 | Same user appears once per section/group, so a "list of users" has duplicates; consumers dedupe by user. | (web) https://community.canvaslms.com/t5/Developers-Group/All-things-API/m-p/50664 (search summary of cross-list/section duplicate request; thread not fetched) ; https://community.canvaslms.com/t5/Canvas-Ideas/API-Update-Courses-API-to-Allow-More-User-Enrollment-States/idc-p/546510 | A learner can be on an individual registration and also reach the course via a `CohortCourseRegistration` (cohort membership is out of scope). Docs must say the API lists registration rows, not users, so the same person can appear in both kinds or in several courses, and that the script must key on registration `id` (plus kind), not on user. Do not try to dedupe or resolve effective enrolment. |
| 6 | Two enrolment kinds with inconsistent fields and no shared id space force clients to special-case. Cohort enrolment in LMSs is often a separate mechanism with different shape. Open question in idea (one endpoint with `kind` vs two). | (experience) | Prefer two endpoints, each with a uniform shape and its own `(updated_at, id)` cursor, over one merged endpoint: a merged cursor needs a composite key across tables (updated_at, kind, id) and UUIDs from two tables with identical-looking shape invite id-space confusion. If merged is chosen anyway, `kind` must be a first-class field, ids documented as unique only within kind, and the cursor must include kind. Either way keep field names identical where the meaning is identical (`course_id`, `course_title`, `is_active`, `registered_at`, `updated_at`), and make the course progress child able to reference registration by (kind, id). Record the decision explicitly. |
| 7 | N extra calls to resolve user email. Canvas enrollments omit email; users report one profile call per student (about 1,200 requests for a term) or special `include` workarounds. | (web) https://community.canvaslms.com/t5/Canvas-Question-Forum/Canvas-API-call-not-returning-email-of-students/m-p/521045 ; https://community.canvaslms.com/t5/Developers-Group/How-do-we-get-the-students-emails-when-querying-Canvas-course/m-p/603966 | Flattening user id, email, organisation into each row is the right call (settled). Test it: `select_related("learner__user", "learner__organisation")` style, with a `django_assert_max_num_queries` fixed regardless of page size. Include email on `CourseInterest` rows too. Docs: email is the user's current primary email at read time and can change, so scripts should join on user id, not email. |
| 8 | Primary/changed email makes email an unstable join key (and a changed email on `User` does not bump the registration's `updated_at`). | (web) https://community.canvaslms.com/t5/Developers-Group/How-do-we-get-the-students-emails-when-querying-Canvas-course/m-p/604110 (search summary: primary email can change) | Flattened fields (email, organisation) come from other tables, so a change to them will NOT advance the registration `updated_at`. Document this: the incremental feed is for registration changes; use the users endpoint (spec 1) to pick up email changes, and always send user id. Do not add signals or cascade writes to bump registration timestamps; that would be unrequested scope. |
| 9 | Interest/wishlist toggles: removing an item is a hard delete and invisible; re-adding creates a new id. Consumers complain wishlist-style APIs "lose" history and show spurious new rows. | (experience); related delete-invisibility sources in finding 3 | Settled: no deletion feed. Document the toggle off/on cycle (row disappears, a re-add shows as a new row with a new id and new `created_at`). Do not change how toggle works (out of scope). Verify in code whether re-adding reuses the id; document the actual behaviour. |
| 10 | Timezone confusion: naive local times, or date-only fields. | (experience); foundation A9 covers general rule | Reuse the foundation timestamp format. `registered_at` must be a real datetime (UTC) not a date; confirm the model field type. If `registered_at` is derived from `created_at`, say so, and say how it relates to `updated_at` (always `<=`). |
| 11 | Missing `updated_at` on the model makes the first deploy a trap: all existing rows get the migration timestamp, so the first `updated_since` run looks like everything changed at deploy time, and genuine history is lost. | (experience) | Migration should backfill `updated_at` from the best existing value (`registered_at`/`created_at`) where one exists, not `now()`. For `CourseInterest`, use its existing created timestamp if present. State in docs that `updated_at` before the deploy date is a best-effort value. Use `auto_now` semantics but check `update_fields` callers: `save(update_fields=[...])` does not bump `auto_now` unless `updated_at` is listed. |
| 12 | Consumers want to filter by course and by `self_registered` rather than pull everything. | (experience) | Not requested; don't build. Mention in docs that filtering is client-side and only `updated_since` exists. Leave as roadmap pointer if the user wants it. |
| 13 | Inactive/expired enrolment semantics: an expiry date makes a row "active" in the DB but not effective (Thinkific `expiry_date`, Moodle start/end dates). | (web) https://mindcloud.co/docs/universal/rest/thinkific/latest/actions/update-enrollment (expiry date is an updatable enrollment field); https://docs.moodle.org/311/en/enrol/manual/edit | Check whether FLS registrations have any date-based validity beyond `is_active`. If not, say `is_active` is the only state. If there is, expose it or document that it is not exposed. |

## What to put in the spec (summary)

1. Return all registrations with `is_active`; no hidden filtering.
2. Define and test `updated_at` as any row change, including bulk and admin paths; backfill in migration.
3. Say clearly that flattened email/organisation changes do not bump registration `updated_at`; point to the users endpoint.
4. Decide two endpoints (recommended) versus one with `kind`; record the cursor and id-space consequences for the progress child.
5. Document `self_registered` semantics and null handling.
6. Document that rows are registrations, not unique users; key on id.
7. Document hard-delete cases (interest toggle, admin delete) and offer a full-walk reconciliation in the example script.
8. Fixed query count tests with flattening via `select_related`.
