# Spec: Lead monitoring API, course registrations and course interest

Spec 4 of 6 in the Lead monitoring API effort. Inputs: `idea.md` and the `research_*.md` files
beside it, the "Lead monitoring API" section of `spec_dd/1. next/roadmap.md`, and the shipped
foundation spec `spec_dd/3. done/2026-11-03_09:54_apis-for-lead-monitoring-1-foundation-and-users/1. spec.md`,
whose conventions (auth, scopes, site filtering, `(updated_at, id)` cursor, inclusive
`updated_since`, error shape, throttling) this spec uses unchanged.

## Purpose

A lead monitor needs to know who is registered for a course and who has shown interest in one. No
export or API covers either today. This spec adds three read-only API endpoints under the
existing `registrations_and_progress` scope: individual course registrations, cohort course
registrations and course interest. It also gives the three models the `updated_at` that
incremental sync needs.

## Scope

In:

- `GET`, `HEAD` and `OPTIONS` list and detail endpoints for `LearnerCourseRegistration`,
  `CohortCourseRegistration` and `CourseInterest`, scoped to the key's site.
- An `updated_at` on each of the three models that moves on every change to the row, including
  the `is_active` flips that use `save(update_fields=["is_active"])` today, and a backfill for
  existing rows.
- One shared flattening of a user, and one of a learner's organisation.
- `docs/api.md` and `docs/product/security-and-data-handling.md`.

Out:

- Course progress, topic progress, form attempts and scores (spec 5).
- A deletion feed, and any change to how removing course interest works.
- Cohort membership, `Learner` as a resource, HR attributes, legal consent records.
- Filters beyond `updated_since`, `cursor` and `page_size`: no `is_active`, course or
  `self_registered` filter.
- Write endpoints, UI, admin exports, admin changes.

## Decisions

| Decision | Reason |
| --- | --- |
| Two registration endpoints, one per model, with no `kind` field. | `ApiKeysetPagination` and `UpdatedSinceFilterSet` work on one model's queryset; a merged list would need a union cursor and nullable learner-or-cohort fields. |
| Each model declares `updated_at = models.DateTimeField(auto_now=True)` itself, after its creation timestamp. Not `TimestampedModel`, and no new abstract base. | Registrations already record creation in `registered_at`; the mixin would add a second creation column. `CourseInterest` already has `created_at`. `ApiKeysetPagination` binds its model type to `Model` and reads the cursor field by name, so no shared base is needed. An earlier draft put `updated_at` in an `UpdatedAtModel` base that `TimestampedModel` subclassed; that reversed the field order of every `TimestampedModel` subclass, and fields stamp in declaration order, so `updated_at` landed before `created_at`. Reverted in code review. |
| The registration models' `save` adds `updated_at` to `update_fields`. | All five production `is_active` writers pass `update_fields=["is_active"]`, which skips `auto_now`. One override covers future writers too. |
| Backfill `updated_at` from the row's creation timestamp. | Stamping the migration time would make every row look changed at deploy and lose the ordering by age. |
| Flattened copies of user, organisation, course and cohort data do not move a row's `updated_at`. | Cascading the bump needs signals on four other models; the users endpoint already gives current identity. Course applications do move on a user's email or name change because an applicant's identity is part of the application record; a registration's or interest's user is a row of its own on the users endpoint. |
| Inactive registrations are returned. There is no default filter. | A deactivation is the change incremental sync exists to report. |
| This spec lands before spec 5 (course progress). | Spec 5 imports the two flattenings defined here. |

## Requirements

### Models and migrations

`freedom_ls/learner_management/models.py`, on `LearnerCourseRegistration` and
`CohortCourseRegistration`; `freedom_ls/course_interest/models.py`, on `CourseInterest`:

- Declare `updated_at = models.DateTimeField(auto_now=True)` directly, after `registered_at`
  (`created_at` on `CourseInterest`), so the creation stamp is written first.
- Add `Meta.indexes` entry `models.Index(fields=["site", "updated_at", "id"], name=...)`, the
  pattern of `accounts_user_site_updated_idx`. Names stay within 30 characters:
  `lm_learner_reg_site_upd_idx`, `lm_cohort_reg_site_upd_idx`, `course_interest_site_upd_idx`.
- On both registration models only, override `save` so that when `update_fields` is not `None`
  and not empty, `"updated_at"` is added to it before `super().save()`. The override is written
  once, as `UpdatedAtInUpdateFieldsMixin` beside `LoadedIsActiveMixin`, and both models take it
  ahead of `LoadedIsActiveMixin`, whose `save` already normalises `update_fields`. The `post_save` and `pre_save` receivers that read
  `update_fields` on these models (`freedom_ls/registration_rules/signals.py`,
  `freedom_ls/course_recommendations/signals.py`) test membership or disjointness, and adding
  `updated_at` must not change what any of them does.
- No application code calls `QuerySet.update()`, `bulk_update()` or `bulk_create()` on these
  models. Two QA seeding commands do
  (`qa_helpers/management/commands/qa_create_permissions_scenario.py:129`,
  `qa_create_course_access_types.py:153`) and pass `updated_at=timezone.now()` in the same
  `update()` call. Any application code added later must set `updated_at` itself.

Migrations, one per app: `learner_management` (both registration models) and `course_interest`.
Each adds the column nullable, backfills it in `RunPython` (`backfill_updated_at`) on the historical model with
`_base_manager.update(updated_at=F("registered_at"))` (`F("created_at")` for interest), alters it
to non-null `auto_now=True`, then adds the index. The column must be backfilled before it becomes
non-null. The reverse of the backfill is a no-op. Existing migrations are not edited.

### Typing in `freedom_ls/api/`

`ApiKeysetPagination` in `freedom_ls/api/pagination.py` and `paginate_all` in
`freedom_ls/api/tests/helpers.py` bind their model type to `Model` and read the cursor field by
name, so the three models need no shared base and nothing in `freedom_ls/api/` changes.
`TimestampedModel` in `freedom_ls/site_aware_models/models.py` is untouched.

### Shared flattening

- **User.** Defined once in `freedom_ls/accounts/api.py` and reused by every serializer that
  flattens a user: `user_id` (integer, the `id` of the users endpoint), `user_email`,
  `user_first_name`, `user_last_name`. It takes the source path to the user (`learner.user` for a
  registration, `user` for interest). `learner_management`, `course_interest` and spec 5's
  `learner_progress` all already depend on `accounts`.
- **Organisation.** Defined once in `freedom_ls/learner_management/api.py`: `organisation_id`
  (UUID string) and `organisation_name`, from `learner.organisation`. Spec 5 imports it from
  there (`learner_progress -> learner_management` already exists).

The mechanism (a `Serializer` subclass mixin, or a function returning declared fields) is the
plan's call; the functions are `user_fields(source)` and `organisation_fields(source)`. The
field names and types are fixed here.

### Endpoints

Each follows `freedom_ls/accounts/api.py`: a `ModelSerializer` with an explicit `fields` tuple,
all read-only; a `UpdatedSinceFilterSet` subclass with `fields: list[str] = []`; a
`ReadOnlyApiViewSet` subclass with `required_scope = ApiScope.REGISTRATIONS_AND_PROGRESS` and a
`get_queryset` that starts from `Model._base_manager` and lets `filter_queryset` apply the key's
site; and `router.register(...)`. `autodiscover_modules("api")` in `freedom_ls/api/urls.py` picks
up the new modules.

`freedom_ls/learner_management/api.py`:

| | Learner course registrations | Cohort course registrations |
| --- | --- | --- |
| Path | `learner-course-registrations` | `cohort-course-registrations` |
| Basename | `learner_course_registration` | `cohort_course_registration` |
| `select_related` | `course`, `learner__user`, `learner__organisation` | `course`, `cohort` |

`freedom_ls/course_interest/api.py`: path `course-interests`, basename `course_interest`,
`select_related("course", "user")`.

Fields, in this order:

| Field | Learner reg. | Cohort reg. | Interest | Type |
| --- | --- | --- | --- | --- |
| `id` | yes | yes | yes | UUID string |
| `course_id` | yes | yes | yes | UUID string |
| `course_title` | yes | yes | yes | string |
| `user_id`, `user_email`, `user_first_name`, `user_last_name` | yes | | yes | integer, strings |
| `organisation_id`, `organisation_name` | yes | | | UUID string, string |
| `cohort_id`, `cohort_name` | | yes | | UUID string, string |
| `self_registered` | yes | | | boolean |
| `is_active` | yes | yes | | boolean |
| `registered_at` | yes | yes | | ISO 8601 |
| `created_at` | | | yes | ISO 8601 |
| `updated_at` | yes | yes | yes | ISO 8601 |

Every `*_id` field is declared explicitly with its type (`UUIDField` or `IntegerField` with a
`source`), so the OpenAPI schema types it. No other field is returned. `Learner.id`,
`Learner.is_active`, `Cohort.organisation`, `Cohort.is_active` and the `RuleRegistration` link are
not exposed.

A `CourseProgress` row in spec 5 references its registration by the `id` of one of the two
registration endpoints. This spec introduces no `kind` field, so spec 5 names its own.

## Testing

Endpoint tests in `freedom_ls/learner_management/tests/test_api.py` and
`freedom_ls/course_interest/tests/test_api.py`, following `freedom_ls/accounts/tests/test_api.py`
and the helpers in `freedom_ls/api/tests/helpers.py`, with the throttle cache cleared as
`freedom_ls/api/tests/conftest.py` does. For each of the three endpoints, prove:

- A key without `registrations_and_progress` gets 403; no key gets 401.
- The response's key set equals the field list above exactly.
- Rows on another site are absent from the list, and their detail is 404. Use a second real
  `Site`, as the foundation's QA bug B3 showed is needed.
- `updated_since` returns rows at or after the given time, and paging walks rows that share one
  `updated_at` with no gaps or duplicates.
- The query count is the same at page size 2 and at page size 50.
- Changing a flattened source (the user's email or name, the organisation name, the cohort name,
  the course title) leaves the row's `updated_at` unchanged.
- Registration endpoints: an inactive registration appears with `is_active: false`.
- Learner registrations and interest: `user_id`, `user_email`, `user_first_name` and
  `user_last_name` carry the user's values, including blank names.

Model and migration tests:

- `updated_at` moves on `save(update_fields=["is_active"])` for both registration models, and
  `save(update_fields=[])` still writes nothing (creation and a full `save` are `auto_now`'s own
  behaviour and are not tested). A test drives each of the five production call sites (deactivate
  and reactivate in `learner_management/utils.py:210,243` and `learner_actions.py:344,386`, and
  rule retraction in `registration_rules/evaluation.py:473`) and asserts `updated_at` advanced.
- The receivers that read `update_fields` behave as before when `updated_at` is added. The
  existing `registration_rules`, `course_recommendations` and `learner_progress` signal tests pass
  unchanged.
- The backfill sets `updated_at` to `registered_at` / `created_at` on rows that existed before the
  migration, following the pattern in `learner_management/tests/test_migrations.py`.

`freedom_ls/api/tests/invariants/test_api_docs.py` must still compile every Python block in
`docs/api.md`.

## Documentation and downstream

`docs/api.md`:

- The intro line "Today there is one: [users](#users)" and the scope-table note "Only `users` has
  an API endpoint so far" are rewritten to list the new endpoints and to say course progress is
  still to come under `registrations_and_progress`.
- Three new `##` sections after Users, in the order learner course registrations, cohort course
  registrations, course interest. Each follows the Users section and adds an example response
  with one active and one inactive row (interest: one row).
- Each "What moves `updated_at`" note says that changes to a user's email or name, an
  organisation or cohort name, or a course title do not move the row, and that `user_id` joins to
  `id` on the users endpoint for current identity. It also says that `updated_at` on rows that
  existed before this release is the registration or interest date.
- Learner course registrations: `self_registered` is `true` when the learner registered
  themselves, and `false` for staff, imports, registration rules and rows made before the field
  existed. `is_active` is the registration's own flag. A registration whose `Learner` is
  deactivated (`Learner.is_active` false) still shows `is_active: true` but gives no access. Rows
  are registrations, not people: one user can appear in several rows, and also reach a course
  through a cohort registration.
- Course interest: removing interest deletes the row, so the only signal is absence from a full
  pull. Showing interest again creates a new row with a new `id`.
- The "Deletions" section gains a table: users and registrations are deactivated (visible) or
  deleted by staff or cascade (invisible); removed interest is invisible. A full pull diffed by
  `id`, applied only after the pull completes, is the way to find them.
- The Python example covers every endpoint with one sync loop and one checkpoint per endpoint.

`docs/product/security-and-data-handling.md`: extend the summary bullet (line 22) and
"### API Access (built)" to say the `registrations_and_progress` scope exposes user id, email,
first and last name, organisation, `self_registered` and course interest. Bump "Last updated".

The new `learner_management -> api` and `course_interest -> api` import edges are recorded in
`docs/app_structure.md` and `test_organisation/import_contracts.toml`. The upgrade notes record

In `spec_dd/1. next/roadmap.md`, the `apis-for-lead-monitoring-5-course-progress` row gains

## Open questions

- Q: Can each app's migration add the column, backfill and alter it to non-null in one
  transaction on PostgreSQL 17? → A: Yes, one migration per app. (Assumed default: the backfill
  touches no foreign-key column, so no deferred trigger events block the `ALTER TABLE`; a
  migration test against a populated table proves it. Overrule by editing "Models and
  migrations" to split into separate migrations.)
- Q: Which migration number does `learner_management` take? → A: The next after the latest
  present when the plan is built (0010 today; 0008 is absent). (Assumed default: another spec in
  the effort may claim a number first. Overrule by editing "Models and migrations".)
- Q: The pagination's model bound was to become a `Protocol`; mypy rejects `QuerySet[M]` for a
  `Protocol`-bound `M` because django-stubs binds `QuerySet`'s model type argument to `Model`.
  What replaces it? → A: Nothing: `freedom_ls/api/` already binds to `Model` and reads the
  cursor field through `getattr`, so the three models declare `updated_at` themselves. (The
  first answer, an abstract `UpdatedAtModel` that `TimestampedModel` also subclassed, reversed
  the stamp order of every `TimestampedModel` row and was reverted in code review; see the
  Decisions row.)

## Success criteria

- The three endpoints pass the endpoint tests listed under Testing.
- Deactivating a registration through the educator interface or a registration rule moves its
  `updated_at`, and the next `updated_since` pull returns it with `is_active: false`.
- After `migrate`, every existing row's `updated_at` equals its `registered_at` or `created_at`.
- There is no diff in `freedom_ls/api/`.
- `uv run pytest` passes, mypy passes with no `# type: ignore`, and
  `uv run manage.py makemigrations --check` reports no changes.
- `docs/product/security-and-data-handling.md` names the new exposed fields and has a bumped
  "Last updated"; `test_organisation/import_contracts.toml` has the `learner_management -> api`
  and `course_interest -> api` edges and the import linter passes.
