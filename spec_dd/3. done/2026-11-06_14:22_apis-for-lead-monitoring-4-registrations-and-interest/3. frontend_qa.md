# Frontend QA: Lead monitoring API, course registrations and course interest

This change adds three read-only endpoints under `/api/v1/` for a key with the "Registrations and
progress" API scope: `learner-course-registrations/`, `cohort-course-registrations/` and
`course-interests/`. It also gives those three models an `updated_at` that moves on every change,
including the deactivations the educator interface makes, and backfills it on existing rows from
the registration or interest date.

What a browser can see:

- **The admin** issues the API key (as in the foundation's QA) and still lists registrations and
  course interest unchanged.
- **The educator interface** deactivates a learner's registration and a cohort's registration;
  the API must then show `is_active: false` with a moved `updated_at`.
- **The learner dashboard** expresses and removes interest in a coming-soon course; the API
  must show the row appear, vanish and reappear under a new `id`.
- **The API itself** answers JSON to a terminal (`curl`).

Beyond the golden path, this run hunts for:

- **Over-reach.** A key with only the Users scope must be refused on all three endpoints, and a
  key must never see another site's rows.
- **Leaks.** No row may carry `Learner.id`, `Learner.is_active`, the cohort's organisation, a
  password or anything outside the documented field list.
- **Stale sync.** A deactivation, a reactivation and a repeat deactivation must each move
  `updated_at` exactly when they change something; renaming a user, organisation, cohort or course
  must not move it.
- **Side effects.** Educator pages, learner course registration, the admin changelists and the
  users endpoint still work.

## §0 Setup

### 0.1 Server

1. `PORT=$(.claude/ds/scripts/find_available_port.sh)`. Use that number literally from here on.
2. `uv run python manage.py migrate` first: it applies the two new migrations to the dev database,
   which holds rows that predate them (§6 depends on that).
3. `uv run python manage.py runserver $PORT`, backgrounded.
4. Base URL: `http://127.0.0.1:$PORT`. Check that `#debug-branch-badge`, bottom left, names
   `apis-for-lead-monitoring-4-registrations-and-interest`.
5. The dev settings pin `FORCE_SITE_NAME = "DemoDev"`, so every host resolves to the DemoDev site.
   The second-site refusal is checked through data, not hosts (§2.3).

### 0.2 Login

Admin at `http://127.0.0.1:$PORT/admin/`, email `demodev@email.com`, password
`demodev@email.com`. This user is a superuser on DemoDev.

### 0.3 Data

Run `uv run python manage.py qa_create_learner_administration_scenario` and
`uv run python manage.py qa_create_cohort_administration_scenario`. Together they give DemoDev
organisations Northside and Southside, cohorts with course registrations (one of them already
deactivated), learners with individual registrations, a deactivated learner, a learner on another
site, and the educator personas (each persona's password is its own email address).

Also needed, and to be created through the `sdd:qa-data-helper` agent if the scenario above lacks
them:

- a **coming-soon course** visible on the DemoDev dashboard (the `qa_create_coming_soon_sections`
  command seeds `Mix Bravo`);
- a **learner account** that can log in and reach the dashboard (any active learner from the
  scenario, password = email).

Record: the Northside organisation admin's email, one active learner's email who holds an
individual registration on a published course, and that course's title.

### 0.4 Terminal helpers

Keep a shell open at the project root. `KEY` is the full key text from §1.1, `KEY_USERS` the one
from §1.2. Every API call uses the trailing slash. Define:

```
api() { curl -s -H "Authorization: Bearer $KEY" "http://127.0.0.1:$PORT/api/v1/$1" | python -m json.tool; }
```

## §2 Learner course registrations from a terminal

### 2.1 Refusals

- `curl -si http://127.0.0.1:$PORT/api/v1/learner-course-registrations/` → 401, JSON body with
  `code: not_authenticated`, header `WWW-Authenticate: Bearer realm="api"`.
- `curl -si -H "Authorization: Bearer $KEY_USERS" http://127.0.0.1:$PORT/api/v1/learner-course-registrations/`
  → 403, `detail` naming the `registrations_and_progress` API scope, `code: permission_denied`.
- The same two calls on `cohort-course-registrations/` and `course-interests/` give the same two
  answers.
- `curl -si -X POST -H "Authorization: Bearer $KEY" http://127.0.0.1:$PORT/api/v1/learner-course-registrations/`
  → 405 JSON. `-X OPTIONS` → 200 with `Allow: GET, HEAD, OPTIONS`. `curl -sI` (HEAD) → 200, no
  body.

### 2.2 The list

`api learner-course-registrations/` → `{"next": null, "results": [...]}`. Every row has exactly
the keys, in this order: `id`, `course_id`, `course_title`, `user_id`, `user_email`,
`user_first_name`, `user_last_name`, `organisation_id`, `organisation_name`, `self_registered`,
`is_active`, `registered_at`, `updated_at`.

- `id`, `course_id` and `organisation_id` are UUID strings; `user_id` is an integer; the two
  timestamps end in `Z`.
- No row has `learner_id`, `learner`, `learner_is_active`, `password` or any other key.
- The scenario's deactivated learner's registrations still show `is_active: true` (the
  registration's own flag, not the learner's).
- A learner with a blank first or last name shows `""`, not `null`.

Cross-check one row against the admin: Admin → Learner management → Learner course
registrations, find the row by learner and course; the organisation and `registered_at` match.

Detail: `api learner-course-registrations/<id>/` is that one row. A random UUID → 404
`{"detail": ..., "code": "not_found"}`.

### 2.3 Another site's rows are invisible

The scenario creates a learner on another site. Find its registration's id in the admin (the
changelist shows every site in dev). It is absent from the list and its detail is 404.

### 2.4 Paging and `updated_since`

- `api "learner-course-registrations/?page_size=2"` → 2 rows and a `next` URL carrying
  `page_size=2` and `cursor=`. Follow `next` by hand until `null`; every id is seen once and the
  total equals the unpaged count.
- `?updated_since=2000-01-01T00:00:00Z` → every row; `?updated_since=2999-01-01T00:00:00Z` →
  `[]`; `?updated_since=2000-01-01T00:00:00` → 400 naming `updated_since`.
- `?is_active=false` and `?course_id=<uuid>` change nothing: filters beyond `updated_since`,
  `cursor` and `page_size` do not exist, and the list is unchanged.

### 2.5 `user_id` joins to the users endpoint

Take one row's `user_id`; `api users/<user_id>/` is 403 with `KEY` (no Users scope), and with
`KEY_USERS` it is the user whose `email` matches the row's `user_email`.

## §3 Deactivation moves `updated_at`

### 3.1 Through the educator interface

1. Note `T0`: `date -u +%Y-%m-%dT%H:%M:%SZ`.
2. In the API, find the active row for the learner and course recorded in §0.3; note its `id`
   and `updated_at` (call it `U0`, equal to `registered_at` or later).
3. Log out of the admin. Log in as the Northside organisation admin at
   `http://127.0.0.1:$PORT/accounts/login/`, go to `http://127.0.0.1:$PORT/educator/`, open
   Northside, open the learner, and use **Deactivate registration** on that course, confirming
   in the modal.
4. `api learner-course-registrations/<id>/` → `is_active: false`, `updated_at` later than `U0`,
   `registered_at` unchanged.
5. `api "learner-course-registrations/?updated_since=$T0"` contains that row and no row the
   step did not touch (a row whose `updated_at` is before `T0` is absent).

### 3.2 Repeat does nothing

Reload the learner's page: the course now shows no Deactivate action for that registration (or
the action reports nothing to do). `updated_at` on the row is unchanged from step 3.1.4.

### 3.3 Reactivation through self-registration

Log in as that learner and register for the same course again from its course page. The API row
keeps its `id`, now shows `is_active: true`, and `updated_at` moved again. `self_registered`
stays `false`: reactivating a row staff made does not change who made it.

### 3.4 A cohort registration

As the organisation admin, open a Northside cohort that has an active course registration and
deactivate it. `api cohort-course-registrations/` shows that row with `is_active: false`, a moved
`updated_at`, and exactly the keys `id`, `course_id`, `course_title`, `cohort_id`, `cohort_name`,
`is_active`, `registered_at`, `updated_at`. No `organisation_id` on cohort rows. The scenario's
already-deactivated cohort registration is listed too, `is_active: false`.

---

## §4 Renames do not move a row

As the superuser in the admin:

1. Change the first name of the learner from §3 (Admin → Users). The API row shows the new
   `user_first_name`; `updated_at` is unchanged from §3.3.
2. Rename the Northside organisation. The row's `organisation_name` changes; `updated_at` does
   not.
3. Rename the course (its title). `course_title` changes on learner and cohort rows;
   `updated_at` does not.
4. Rename the cohort from §3.4. `cohort_name` changes; `updated_at` does not.

Undo the renames afterwards so the names match the scenario again.

## §5 Course interest

### 5.1 Express interest

1. `api course-interests/` → note the count; it may be `[]`.
2. Log in as the learner, open the dashboard, find the coming-soon course and click its
   express-interest call to action. The button flips to its "interested" state without a page
   reload.
3. `api course-interests/` has one new row with exactly the keys `id`, `course_id`,
   `course_title`, `user_id`, `user_email`, `user_first_name`, `user_last_name`, `created_at`,
   `updated_at`. `created_at` and `updated_at` are equal to the second. The `user_email` is the
   learner's.
4. Clicking express interest again (or reloading and clicking) does not add a second row.

### 5.2 Remove and re-express

1. Click the call to action again to remove interest. `api course-interests/` no longer has the
   row; `api course-interests/<old id>/` → 404.
2. Express interest once more. A row exists again with a **different** `id` and a fresh
   `created_at`.
3. The `?updated_since=` and `?page_size=` behaviours of §2.4 hold here too.

## §6 Backfill of rows that predate the migration

The scenario's registrations were created before 0.1's `migrate` only if the scenario was seeded
on an earlier run; the demo content's registrations were. For five rows whose `registered_at` is
older than today (any row the scenario did not create in §0.3):

`api learner-course-registrations/` and `api cohort-course-registrations/` show
`updated_at == registered_at` to the microsecond on each of them.

If every row in the database was created after the migration, record "backfill not observable in
this database" and rely on the migration tests.

## §7 Schema

`curl -s -H "Authorization: Bearer $KEY_USERS" http://127.0.0.1:$PORT/api/v1/schema/ | python -m json.tool`
→ 200. The document has paths `/api/v1/learner-course-registrations/`,
`/api/v1/learner-course-registrations/{id}/`, `/api/v1/cohort-course-registrations/` (and detail)
and `/api/v1/course-interests/` (and detail), each list with `updated_since`, `cursor` and
`page_size` parameters. In the learner-registration schema, `user_id` is `integer`, `course_id`
and `organisation_id` are `string` with `format: uuid`, `self_registered` and `is_active` are
`boolean`.
