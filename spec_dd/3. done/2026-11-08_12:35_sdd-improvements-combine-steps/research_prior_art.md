# Research: prior art for chaining SDD steps, front-loading questions and parallel worktrees

Question: what has already been tried, here or elsewhere, and what happened? Paths are relative to the project root. "Done" specs are under `spec_dd/3. done/`.

## Headline

1. **Much of idea points 1 to 3 is already built.** The done spec `2026-10-12_20:53_sdd-improve` is the earlier attempt at "run longer without a human". It merged `improve_idea` into `spec_from_idea` (with a review wave), removed `/sdd:next`, added `/sdd:document`, added a per-batch reviewer, and made late questions into defaults. The current tree reflects it (`commands/document.md`, `resources/spec_review_dimensions.md`, `resources/plan_review_dimensions.md`, Batch review in `commands/implement_plan.md`). The spec for this idea must start from that state and must not re-derive it.
2. **What `sdd-improve` did not do, and this idea now asks for:** chain `/sdd:start` into `register_design` and `spec_from_idea`; chain `implement_plan` into QA; parallel coding in worktrees. None has been tried in this repo. No done spec, command comment, TODO or `@claude` note mentions parallel batches, short-lived worktrees, or chaining across commands (Grep of `implement_plan.md` and `do_qa.md` for `worktree|parallel|TODO|@claude|chain` found none).
3. **Parallelism inside a command is proven; parallel coding is not.** Fan-out of read-only workers (research, review) is the established recipe. Batches in `implement_plan` are strictly sequential today ("The batch's tier must pass before moving to the next batch", `implement_plan.md` Step 2) and the only reason stated is the resume/atomic-commit marker.

## Local prior art

### `2026-06-01_12:31_sdd-token-efficiency-and-structure` (first tune-up)

- Found the **nesting bug**: `next.md` ran each `(cmd)` in a fresh subagent, so a command's own "create subagents" instructions silently could not run (subagents cannot spawn subagents).
- Decision: commands run on the main thread (depth 0); user does `/clear` before each `/sdd:next`. Keeps the single nesting level for each command's fan-out.
- Added model tiering (Haiku mechanic, Sonnet worker), one-subagent-per-unit with per-unit output files and `status:` footer, resume = skip units whose output ends `status: ok`, input-contract + re-spawn on `blocked`.
- Explicitly deferred: commands-to-skills migration, Agent Teams / `SendMessage`.
- Lesson for this idea: **chaining by wrapping a command in a subagent kills its fan-out.** Any chain must be an inline read-and-follow at depth 0 ("hook mode"), never a spawn.

### `2026-10-09_09:03_make-sdd-more-efficient` (test tiers)

- A spec walking the 14 todo stages triggered up to 40 full-suite passes (6,704 tests, more than 10 minutes each). Introduced tiers `none`, `targeted`, `full` via `protected/run_test_tier.md`, with an escalation list.
- Settled: "The four-worker cap on `-n auto` stays. **The dev Postgres is shared across worktrees.**" Full runs are kept at fixed milestones; CI is the backstop.
- Lesson for this idea: **parallel worktrees multiply test cost and contend for the shared dev Postgres** (and its four-worker cap). Parallel batches should run `targeted` only, with one `full` after merge. (Worktree setup does support a per-branch dev database via `## Worktree Scripts` in `.claude/sdd/config.md`; see `skills/git-worktree-setup/SKILL.md` and `commands/protected/start_worktree.md` Step 3. The test database for parallel pytest in sibling worktrees is not covered by that note.)
- It also records the "No QA needed" todo line as a jam; fixed later by `sdd-improve`.

### `2026-10-12_20:53_sdd-improve` ("SDD: run longer without a human"), the nearest prior art

Idea facts: the checklist had 18 `(user)` and 16 `(cmd)` items; about 9% of review gates ticked across 59 specs; four commands (`threat-model`, `plan_security_review`, `plan_structure_review`, `security-review`) had not been run since July. `research_where_the_pipeline_stalls.md` is the stop-point inventory.

What it changed in the sdd plugin (per its `1. spec.md`, and visible in the tree):
- Deleted `/sdd:next` and `/sdd:improve_idea`; `spec_from_idea` now does one research wave (topics `codebase`, `best_practices`, `reference_implementations`, `prior_art`, `ux_patterns`, `known_complaints`) with one question batch while workers run, then a spec review wave (`spec_review_dimensions.md`: completeness, feasibility, vocabulary, generic_plugin, cut_list), one bounded re-check, an end-of-run question batch.
- Question policy: ask once, early, in a batch of up to four, each with a recommended answer; later questions take the default and are recorded as "assumed default" (`## Open questions` in a spec, `> **Assumed default:**` in a plan).
- `plan_from_spec` gained `## Plan Review Hooks` and a `new_threats` dimension; `plan_security_review`, `plan_structure_review`, `/ds:threat-model`, `/ds:security-review` deleted.
- `implement_plan` gained a per-batch review (mechanic grep plus one worker, two-fix cap), Step 1 "raise doubts with the user" removed, a design miss after two fix batches no longer ends the run (filed as a `(user) Decide` item at the end), `/sdd:document` with `## Documentation Hooks` run inline at depth 0 in hook mode.
- Late questions turned to defaults: `finish_worktree` QA re-run confirmation, `commit_quickly` mine-or-all, ambiguous spec directory (resolve from branch name), `address_pr_review` skip confirmation.
- Stops it kept deliberately: real secret in a commit, incompatible rebase conflict, dirty main worktree, upstream-change review `direction: changed`, design-tool authorisation, roadmap precursor warnings in `start.md` (still `AskUserQuestion`), QA red-lane `Decide` items, PR approval.

Recorded lessons and reversals from its research:
- `/sdd:next` stopped after every `(cmd)` and told the user to `/clear` and rerun. The owner ignored it and ran commands by hand. **A chaining mechanism the owner does not use is wasted; the owner's real flow is run command, read result, run next.**
- QA wrote `user + cmd` markers in 168 items across 35 specs that `next.md` rejected by construction; fixed (`do_qa` run-time items now carry one marker).
- Merge risk it identified for merged commands: **non-idempotent in-place edits** after a crash mid-apply. Mitigation chosen: commit the artifact before the review wave (commit `write the spec`, then `review the spec`) as a resume marker. The same trick applies to "chain A then B": each link needs its own commit marker.
- Context cost of merging: `/sdd:document` runs product-docs inline "after an already long implementation+QA session". The research flagged context growth as the heaviest trade-off of merging; mitigation was `/clear` guidance and per-hook commits. **Chaining implement_plan into do_qa will land in the same long context.**
- A worker cannot fan out, so `/sdd:document` cannot hand a hook to a worker; hooks that fan out (`update_product_docs`) must be followed inline at depth 0. The same constraint applies to chaining `spec_from_idea` (fans out) and `register_design` (design-tool authorisation) from `/sdd:start`.
- Open question it left: should `/sdd:next` loop through several `(cmd)` items in one invocation? Its answer was to delete `next`; the idea here partly reverses that by chaining specific pairs inside commands.

### `2026-11-01_19:48_claude-plugin-tidy-up`

Relevant here: `do_qa` now lives at `claude_plugins/sdd/commands/do_qa.md` (the idea says `/sdd:do_qa`; `sdd-improve` still named `/fls-dev:do_qa`), and plugin text has been compacted, so added chain steps should stay terse. `do_qa.md` already has a "Project-root mode" via `Skill` args and "Inputs from the caller" lines, a hook-style entry point that a chain could use.

## Recorded hard-won facts the spec must not break

From `claude_plugins/sdd/skills/claude-code-authoring/SKILL.md` and `resources/` (Claude Code 2.1.x). Each is a constraint on chaining and parallelism:

- **No nesting.** The `Agent` tool is not exposed at depth 1; a subagent cannot spawn subagents. All fan-out at depth 0. Listing `Agent` in a subagent's `tools` is ignored. Depth is capped at one.
- **Subagents cannot type slash commands.** No `SlashCommand` tool in a subagent. Reusable logic must be a skill or a helper `.md` that the subagent reads and follows. (Chaining `/sdd:start` -> `register_design` -> `spec_from_idea` therefore means depth-0 read-and-follow, not a spawn.)
- **Spawn-time input only.** The `prompt` string is the only channel; no mid-run messaging. "Resuming" a subagent means spawning a fresh one with more context. `SendMessage` (Agent Teams) is experimental and out of scope.
- **Subagents cannot ask the user.** `AskUserQuestion` is orchestrator-only. A worker that lacks input returns `status: blocked` with `needs: [...]`. So front-loading questions means the depth-0 chain command must collect answers for every chained step before any step runs, then bake the answers into prompts and into the steps' inline inputs. Steps run inline must not re-ask what was answered.
- **Subagents can use skills**, and `skills:` frontmatter preloads full content.
- **Model resolution:** `CLAUDE_CODE_SUBAGENT_MODEL` env, then per-spawn `model`, then agent frontmatter, then parent. An inlined command's own `model:` frontmatter is inert, and **its `allowed-tools` is inert too**: the calling command's `allowed-tools` must be the union of its hooks' needs (hook-mode rule). A chain command needs the union of `start` + `register_design` + `spec_from_idea` tools (including Playwright/design-tool MCP for `register_design` if it uses it).
- **Hook mode.** A command followed inline at depth 0 gets `mode: hook`; it skips its own pre-step rebase and todo tick and keeps its own commit. Commands that can be hooks open with an "Inputs from the caller" line naming `<spec-dir>`, `<todo-path>` and `mode: hook`. Hooks from another plugin are invoked with the `Skill` tool (own plugin root, inputs as `args`), never by path, or `${CLAUDE_PLUGIN_ROOT}` resolves wrongly.
- **Output contract:** a worker writes its output in a single `Write` to a fixed path; completeness is only the `status:` footer; resume skips files that end `status: ok`. Workers get no Bash and no rename.
- **Recipe rules:** one subagent per unit (never one looping over a batch); `failed` retry same unit at most twice with the prior error; `blocked` answered from the idea, code or another worker's file before asking the user; synthesis reads files by path; clean up own scratch files by name, never the shared `.sdd-work/` directory.
- **Question test:** ask only when the answer changes the artifact, nothing on disk or in a running/finished unit can answer it, and there is no default the user would obviously accept. Batch up to four per `AskUserQuestion`, each with a recommended answer. Late questions take the default and are recorded.
- **Structured output is SDK-only;** the CLI Task path returns free text, so file-based hand-off with a `status:` footer is the contract.
- **Deferred, do not adopt:** hooks, plan mode / permission modes, Agent-SDK structured outputs. (The authoring skill says adopting these is out of scope for the current workflow; the spec should either respect that or amend the skill explicitly.)
- **Agent frontmatter supports `isolation: worktree`** (`resources/subagents.md` lists it among keys) but no sdd file uses it and no note records any test of it. Plugin subagents ignore `permissionMode`, `mcpServers`, `hooks`.
- **Atomic batch marker.** A batch worker commits its own work (`[batch <id>] ...`) so "work done" and "marker written" cannot split on a crash (`implement_plan.md` Step 2). Parallel branches/merges must preserve an equivalent atomic marker, and `pre_step_rebase` reads batch progress from commit subjects, never SHAs, because rebase rewrites SHAs.
- **Start-time stops that remain** in `/sdd:start` today: roadmap precursor and unmet-dependency `AskUserQuestion` (Step 0); `blocked` from setup helpers (ambiguous spec dir, existing `todo.md`, dirty tree). Those questions are already first in the run, so they are the natural seed of a front-loaded batch.
- **`register_design`** (`commands/register_design.md`): stops when no directory matches the branch, and on `/design-login` authorisation (a human act, kept as a stop by `sdd-improve`). Chaining it unattended can only proceed if authorisation is already valid; otherwise it must be asked up front or skipped with a recorded need.
- **Per-worktree environment.** Worktree layout is a bare repo with sibling worktrees; `start_worktree.md` Step 3 runs the project's configured Setup script (dependency sync, per-branch dev DB, migrations, demo data). The test-tier work settled that the dev Postgres is shared and `-n auto` is capped at four workers.

## Elsewhere (web)

Sources are blog posts and community write-ups, not formal post-mortems. Treat the specifics as anecdotal; where a page fetch failed or was not read in full this is stated.

### Parallel agents in git worktrees: what broke

- **Isolation defers conflicts, it does not remove them.** Worktrees stop simultaneous filesystem writes; they cannot make incompatible changes merge cleanly. Semantic conflicts can slip through (files merge cleanly, runtime breaks). A promising parallel task can produce merge conflicts that take longer than the task. https://medium.com/@ooi_yee_fei/parallel-ai-development-with-git-worktrees-f2524afc3e33 · https://www.aibuilderclub.com/blog/claude-code-worktree-parallel-agents (via search summaries, not fetched in full)
- **Partition work up front.** Assigning module or file ownership before spawning agents is the mitigation that practitioners report; dependent tasks merge badly. https://dev.to/yureki_lab/how-i-run-multiple-claude-code-agents-in-parallel-without-collisions-3pbk (search summary)
- **Lockfiles and migrations are the named hotspots.** The aident.ai guide (fetched): sequence dependency or schema changes under one owner; when a later branch needs rebasing, regenerate the shared artifact once and rerun targeted and integration tests. https://aident.ai/blog/run-parallel-claude-code-agents-git-worktrees
- **One integrator.** Same guide: do not let multiple agents independently resolve the same merge conflict; one integrator decides which behaviour survives and integrates branches one at a time, lower-risk or foundational first.
- **Ports and shared runtime state.** Each session needs its own port, and child services may still share a test database. Separate directories do not separate test databases, queues, Compose project names or browser profiles; do not invent a second database if the suite cannot create one safely. Same aident.ai guide. A vendor-style guide recommends database branching and a port per worktree. https://www.mindstudio.ai/blog/parallel-ai-coding-agents-git-worktrees (search summary)
- **A new worktree has only tracked files.** Gitignored `.env`, virtual environments, `node_modules`, generated files and local config are absent; the agent fails confusingly ("works in main, fails in worktree"). Fixes named: a `.worktreeinclude` for safe ignored files, a `WorktreeCreate` hook for deterministic setup, a per-worktree install, never copy shared `node_modules` between worktrees (shared mutable state), never commit secrets to fix a missing file. aident.ai guide; https://www.aibuilderclub.com/blog/claude-code-worktree-parallel-agents (summary). This matches the repo's own need for a Tailwind build, `uv sync` and a per-branch DB in `start_worktree.md` Step 3.
- **Disk.** Each worktree is a near-full working copy (one author: a 2 GB repo with five worktrees is 10 GB or more). https://www.mejba.me/blog/claude-code-git-worktrees-parallel-agents (summary)
- **Wrong checkout and dirty base.** Stale absolute paths in instructions or memory can send an agent to the main checkout; check `pwd` and repo root before edits; a dirty main checkout or a worktree branched from the wrong commit causes trouble; fetch first. Same aident.ai guide.
- **Known Claude Code bug (unverified):** a GitHub-issue mirror reports 3 or more parallel `Agent` calls with `isolation: worktree` failing because concurrent `git worktree add` calls race for `.git/config.lock`, so one or more agents fail immediately. Reported workaround direction: limit parallel fan-out or stagger worktree creation. I could not fetch the page (host did not resolve) and did not verify current status. https://claudeissues.com/issue/34645-bug-parallel-subagents-with-worktree-isolation-fail-due-to-git-config-lock-conte
- **How many.** The sources I read give no robust number; guidance is qualitative (independent, reviewable tasks; avoid shared files). The aident.ai guide names no cap.
- **Context exhaustion** is not discussed in the worktree sources I read. It is covered locally (above) and by Anthropic's own point that the context window "fills up fast" and quality degrades (https://code.claude.com/docs/en/best-practices, via `research_tiered_gating.md` in the done `make-sdd-more-efficient` spec).

### Chained spec to plan to implement to QA pipelines: where humans stayed

- Practitioner spec-kit pipeline write-up: the human still reviews spec, plan and final diff; an ambiguity at the spec stage either stops to ask (bringing back the human bottleneck) or guesses and spreads the error downstream; clearing context between implement and verify preserves tester independence. https://dev.to/herivgs/from-coding-to-lead-agents-1jfk (search summary)
- Thoughtworks Radar: teams still need a human in the loop to avoid context rot and noisy feedback; the "feedback flywheel" technique retros agent sessions to improve later runs. https://www.thoughtworks.com/es-cl/radar/techniques/feedback-flywheel (search summary)
- "Dark factory" overviews claim humans are out of the approval chain but still recommend a human summary review before deploy. https://www.mindstudio.ai/blog/what-is-dark-factory-ai-coding-autonomous-deployment (search summary)
- Already collected for the done `sdd-improve` spec (`research_autonomous_pipeline_patterns.md`, not re-fetched): spec-kit `clarify` (bounded batch, max 5, recommended default, why-it-matters, answers written into the spec as a dated Q to A log); spec-kit `implement` halts only on defined conditions and reports parallel `[P]` task failures while others continue; Kiro "Quick Spec" skips approval gates; practitioner consensus puts the one human gate at spec or plan, with the PR as the lighter check (opinion, not controlled evidence); Anthropic "effective harnesses for long-running agents" says continuity comes from committed artifacts and a progress file, not a human; AMBIG-SWE style benchmarks (secondary, preliminary) report much worse results when an agent guesses on underspecified tasks than when it may ask (37.94% vs 59.52% resolve rate). The "decision ledger" idea (log every guess with the question that would have been asked) is the pattern the repo adopted as "assumed default".
- No source found that reports measured results for a fully chained spec-to-QA pipeline on a real codebase; all of the above is anecdotal.

## What this means for the spec (observations, not decisions)

- Point 1 (chain `start` -> `register_design` -> `spec_from_idea`) is cheap to express as a depth-0 command that reads and follows the others in hook mode, gathers all questions first, and commits per link as a resume marker. The new pieces are: a pre-collected-answers input to `spec_from_idea` and `register_design`; `/design-login` authorisation asked up front; the chain command's `allowed-tools` as the union of its hooks'.
- Point 2 (QA right after `implement_plan`) must keep `do_qa` independently runnable; `do_qa` already has "Inputs from the caller". The long-context cost of running it right after implementation is the known trade-off (see `sdd-improve`).
- Point 4 (short-lived worktrees for parallel batches) has no local precedent and the web record is mostly warnings: partition by file ownership, one owner for lockfile and migrations, one integrator, per-worktree install and port, shared dev Postgres (already a known local constraint), the test DB for parallel pytest, plus a reported `.git/config.lock` race. It also collides with `test-organisation-and-hygene-2` over the batch resume scan and commit-subject shapes.
- The authoring skill lists hooks, plan mode and `isolation: worktree` as unadopted or unexercised. Using `isolation: worktree` or `WorktreeCreate` hooks would adopt something the skill says is out of scope, so the spec has to amend the skill if it does.
