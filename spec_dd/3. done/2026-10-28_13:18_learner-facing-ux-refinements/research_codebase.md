# Research: what the codebase touches, reuses or conflicts with

Paths are relative to the repo root. `LI` = `freedom_ls/learner_interface`.

## Part 1. Dashboard category course paging

- View: `LI/views.py::dashboard` (URL `learner_interface:dashboard`, path `""`, `LI/urls.py`). Builds `sections` via `_dashboard_inputs` then `_dashboard_sections`; renders `LI/templates/learner_interface/dashboard.html`. Category sections come from `_category_section(request, category, rest, backend)` (`CourseCategory.objects.filter(show_on_dashboard=True)`). Other sections: `_in_progress_section`, `_recommended_section`, `_available_section`, `_coming_soon_section`, `_history_section` - all share the same template, so any layout change hits every section, not only categories.
- Section model and paging: `LI/dashboard_sections.py`. `SECTION_PAGE_SIZE = 3`; `DashboardSection` dataclass (`slug`, `heading`, `wrapper_id`, `page_obj`, `courses`, `description`, `browse_all_url`; properties `swap_id` = `section-page-<slug>`, `position_text` "1 to 3 of 7", `status_text`, `nav_label`, `page_param_name` = `page_<slug>`). `page_for()` clamps junk pages to 1; `requested_section_slug()` reads `HX-Target`; `section_page_href` (template tag in `LI/templatetags/dashboard_tags.py`) builds hrefs preserving other sections' page state.
- Template: `LI/templates/learner_interface/partials/course_list.html` with partialdefs `section-heading`, `course-grid` (`grid md:grid-cols-2 lg:grid-cols-3`, includes `partials/course_card.html` per course), `section-page` (swap boundary `div#section-page-<slug>.contents`; holds position text + `<c-course-section-pagination>` + "Browse all courses" `<c-button variant="link" size="small" icon_right="next">` all at TOP-RIGHT, then the grid), `section-status` (single `role=status` live region, OOB-updated), `section-page-response`, `section-gone-response`, `course-section` (outer `grid grid-cols-1 sm:grid-cols-[1fr_auto]`, `x-data="courseSectionPagination"`), `in-progress-empty`.
- HTMX endpoint: the same dashboard URL; paging links are `<a href hx-get hx-target="#section-page-<slug>" hx-swap="outerHTML">`; view returns `course_list.html#section-page-response` (or `#section-gone-response` with `HX-Retarget`/`HX-Reswap`) from `_section_page_response`.
- Pagination component: `LI/templates/cotton/course-section-pagination.html` (`<c-course-section-pagination page_obj target_id page_param_name nav_label>`): prev/next only, icons `previous`/`next`, `btn btn-secondary p-2`, boundary controls keep markup (`aria-disabled`, `tabindex=-1`, no href) rather than `disabled`. Position text lives beside it in `course_list.html` (`tabular-nums`). The idea's "page 1 of 3" wording differs from today's "1 to 3 of 7" text (`position_text`); `DashboardSection` has no "page N of M" property (use `page_obj.number` / `page_obj.paginator.num_pages`). Tests pin the current `position_text`/status text.
- Alpine: `courseSectionPagination` in `LI/static/learner_interface/js/alpine-components.js` (~line 479): focus restoration to the pressed direction control (`[data-direction]`) or `h2` after `htmx:afterSwap`. Any reordering of controls (top on phones, Browse all at bottom) must keep `data-direction` controls inside the swapped `#section-page-<slug>` and the `h2` outside it.
- Card components today (grid cards only, no compact/row variant on the dashboard):
  - `LI/templates/learner_interface/partials/course_card.html` (single dashboard card, branches on `course.listing_status`; uses `<c-course-card-shell>`, `card_title_link.html`, `course_status_eyebrow.html`, `course_listing_price.html`, `course_details_link.html` in its own right-aligned line, `<c-course-progress-bar>` footer for registered/in_progress).
  - `LI/templates/cotton/course-card-shell.html` (vertical card with hero; not read in detail).
  - A ROW variant already exists for the all-courses page: `partials/course_row.html` (same field contract) + `cotton/course-row-shell.html` (`[accent icon box w-25][details]`, `article.course-card`, `<c-slot name="eyebrow">`, `footer`, `clickable`, `class` props) + `partials/course_row_list.html` (`all-courses-rows`, `ul.divide-y`). Not used by the dashboard. A mobile "minimal row-like card" can reuse `course_row.html`/`course-row-shell` (or a slimmer sibling) instead of a new component; row shell is `flex items-stretch` with a fixed `w-25` icon panel, so "minimal" probably needs a smaller icon box or a prop.
  - `LI/templates/cotton/course-card.html` is the markdown-content embed card (`variant` row/compact), not the dashboard card.
- Tests: `LI/tests/views/test_dashboard.py` (page size 3, `test_dashboard_available_page_one_holds_three_of_five`, `test_page_one_renders_three_and_reports_the_position`, htmx fragment tests, disabled-control tests `test_both_controls_render_with_previous_disabled_on_page_one`, `test_a_disabled_control_never_uses_the_disabled_attribute`, heading-outside-swap, one-status-region, query-count tests, browse-all link tests `test_dashboard_available_section_renders_browse_all_link`, `test_coming_soon_fragment_carries_the_browse_all_courses_button`, `test_the_learners_own_sections_offer_no_browse_all_courses`); `LI/tests/templatetags/test_course_card_tags.py`; `LI/tests/demo_content/test_course_card.py`. Playwright: `LI/tests/playwright/test_course_browse_flow.py` (course_detail navigation at lines ~121, ~491); no Playwright test targets dashboard paging or mobile viewport specifically (grep found none).
- Responsive notes: breakpoints used are Tailwind `sm`/`md`/`lg`; the grid turns 2-col at `md` (tablet = the "2 rows of 3" untidiness). Row variant for phone AND tablet means switching at `lg`, i.e. render both layouts and hide with `lg:hidden`/`hidden lg:grid`, or restructure; rendering both would duplicate course cards in the DOM (affects tests that count titles/links, and a11y, so prefer one structure with responsive classes where possible).
- Browse all: `DashboardSection.browse_all_url` = `_browse_all_url()` = `reverse("learner_interface:courses")`; currently label "Browse all courses" in the top-right group (idea wants "Browse all ->", bottom, centred, on phones/tablets). Only Recommended, categories, Available(?), Coming soon have it; own-courses sections (In progress, History) do not (tests pin this).

## Part 2. Course detail page "Back" link

- View: `LI/views.py::course_detail` (URL name `learner_interface:course_detail`, `courses/<slug:course_slug>/detail/`). It builds `breadcrumbs = [{"label": "All courses", "url": reverse("learner_interface:courses")}, {"label": course.title}]` (view ~line 747) and passes it in context; template `LI/templates/learner_interface/course_detail.html` renders `<c-breadcrumbs :crumbs="breadcrumbs" />` inside `<c-page class="pt-2 lg:pt-2">` above the full-bleed hero (comment says padding trimmed for the breadcrumbs).
- Component: `freedom_ls/base/templates/cotton/breadcrumbs.html` (`<c-breadcrumbs crumbs hx_target id oob class>`; `nav aria-label="Breadcrumb"`). Also used by `cotton/content-header.html`, `learner_interface/_course_base.html`, `cotton/course-progress-bar.html` (matches "breadcrumb" in a comment), `partials/player_breadcrumbs.html` (player: first crumb goes to `course_detail`, tested in `test_course_player.py` ~1027-1060 via regexp `<nav aria-label="Breadcrumb">`) - the player breadcrumbs are NOT in scope; do not change the shared component's behaviour for them.
- Existing back-link precedent to copy: `freedom_ls/panel_framework/templates/panel_framework/partials/breadcrumbs.html` renders `<nav id="breadcrumbs" aria-label="Back">` with `<c-icon name="previous" class="size-4" />` + label, styled `inline-flex min-h-11 items-center gap-1.5 ... text-sm font-semibold text-primary no-underline hover:text-primary-hover focus-visible:outline-2 ...` (educator panel only; HTMX nav into `#main-content` - must NOT be reused as-is on the standalone page). Also `course_applications/applicant_details.html` line 36 uses `<c-button href=course_detail variant="secondary" icon_left="previous">` as a back-style button.
- Everywhere that links to `learner_interface:course_detail` (determines where "Back" should go):
  - Dashboard cards (title link when status is `not_registered`/`coming_soon`; plus `partials/course_details_link.html` "Details" button for every status) via `partials/course_card.html`.
  - All-courses page `/courses/` via `partials/course_row.html` (title link and details link) - for these, Back = All courses is correct, for dashboard visits Back = dashboard.
  - Player breadcrumbs `partials/player_breadcrumbs.html` (first crumb) - from inside a course, Back = the player.
  - `course_applications/apply.html` line 26 (a secondary button back to detail) and `applicant_details.html` line 36.
  - Redirects in `LI/views.py` (initiate_course_access, course_finish and others, e.g. lines ~836, 870, 882, 932, 965, 1003) land on course_detail after POST/actions; `course_interest/views.py`, `course_applications/views.py`, `reports/gather.py`, `educator_interface/reporting.py`, `comms` notification links, `config/sitemaps.py`, and `qa_helpers/management/commands/qa_create_browsable_course.py` also reference it (not read in detail).
  - SEO/public: the detail page is public, indexable, has JSON-LD, and anonymous users can land directly from a search engine or a shared link (no referrer on our site). `LI/tests/views/test_seo.py` covers it.
  So there is no single origin. Options to decide in the spec: HTTP `Referer` (same-origin only; unreliable with `Referrer-Policy`, absent for direct hits, and the OOB form-redirect flows would point Back at POST endpoints), a `?next`/`from` query param on the dashboard/all-courses links (explicit; must be validated as a same-site relative URL, e.g. Django `url_has_allowed_host_and_scheme`), `history.back()` via Alpine (matches the "end up somewhere else" complaint literally but breaks with no history / external referrer), with a fixed fallback (dashboard for authenticated, `learner_interface:courses` for anonymous). No existing "back"/"next" param helper was found for learner pages; check allauth `next` handling in `freedom_ls/accounts` for a validated-redirect helper to reuse.
- Tests to change: `LI/tests/views/test_course_listing.py::test_course_detail_renders_breadcrumbs` (line 1377) asserts "All courses" and the courses URL in the body; must be rewritten. `LI/tests/views/test_course_detail.py` and `test_seo.py` render the page; Playwright `test_course_browse_flow.py` navigates to the detail page (check any breadcrumb assertions there, none found by grep).

- Tests: `freedom_ls/base/tests/invariants/test_error_pages.py` (references `learner_interface:dashboard` in error pages), `comms/tests/test_bell_tag.py`, `accounts/tests/test_middleware.py`. ## Part 4. My Applications section on the dashboard

- Data: `freedom_ls/course_applications/models.py::CourseApplication(SiteAwareModel)`: `user` (nullable), `anonymous_applicant` (OneToOne to `AnonymousApplicant`), `course`, `form_progress` (OneToOne, nullable), `created_at`, `updated_at`. NO `state` field yet (planned: FSM state, see model docstring NOTE and `spec_dd/1. next/educator-interface-full-polish/application-review-ui/`). The only status is derived: `is_submitted` property (no form_progress, or form_progress.completed_time set) vs draft. Constraint `unique_application_per_site_user_course`.
- Context builder: `course_applications/queries.py::get_active_applications(user)` (all of the user's applications, `select_related("course","form_progress")`, ordering not specified), used by `course_applications/backends.py::ApplicationCourseAccessBackend.get_dashboard_contributions(user=)` and `get_dashboard_contributions_for_request(request=)` (signed-in: all applications; anonymous: only drafts owned by the session via `anonymous_session.owned_applications`, ordered `-created_at`). `_applications_panel` returns a `DashboardContribution(template_name="course_applications/partials/dashboard_applications.html", context={"applications": [...]})` (`DashboardContribution` dataclass at `freedom_ls/course_access/backends.py:78`; hook declared at line ~192/498). `learner_interface` renders them generically with `render_to_string` in `dashboard()` into `dashboard_panels`, shown in `dashboard.html` via `{{ panel|safe }}` BETWEEN the greeting and the course sections. Layering rule: `learner_interface` never imports `course_applications` and never reads the context keys - so paging (below) must be implemented inside the backend contribution/`course_applications`, not in `learner_interface/views.py`.
- Template: `course_applications/templates/course_applications/partials/dashboard_applications.html`: `<section>` with `<h2>Your applications</h2>` (note: the design calls it "My Applications" / the idea "My Applications"; today's heading text is "Your applications", pinned by tests) and a `ul` of `li` rows. Two row states only: submitted -> `in_progress` icon, title link to `course_applications:status` (pk), plain text "Pending review"; draft -> title link, `<c-chip variant="warning" size="xs">Incomplete</c-chip>`, "Finish your application to have it reviewed.", `<c-button size="small" icon_right="next">Continue application</c-button>` (to `course_applications:status`, which resumes the draft at the page the applicant left). Statuses shown: Pending review, Incomplete. No paging exists.
- Paging reuse: the dashboard section paging is course-specific (`DashboardSection`, `page_for`, `course_section_pagination`) and keyed on `HX-Target` starting `section-page-`; `dashboard()` returns a section fragment for that, else the whole page. For applications paging: either (a) a separate param (`page_applications`) handled in the backend contribution using `request.GET` (contributions already receive `request`) with a new HTMX endpoint owned by `course_applications` (add to `course_applications/urls.py`; remember `app_name`), or (b) full-page links. The `<c-course-section-pagination>` component is generic enough (needs `page_obj`, `target_id`, `page_param_name`, `nav_label`) but lives in `learner_interface/templates/cotton/` and its link builder is `dashboard_tags.section_page_href`; `course_applications` importing a `learner_interface` cotton component through templates is a template dependency (cotton is global) rather than a Python import, but check the layering rule and `/home/.../freedom_ls` module-boundary checks before relying on it. `<c-pagination>` in `base/templates/cotton/pagination.html` is the educator table paginator (numbered), explicitly left alone by the dashboard pagination comment.
- Tests pinning the current behaviour: `LI/tests/views/test_course_listing.py` lines ~1813-1871 (`"Your applications"` shown/not shown, `"Continue application"`); `course_applications/tests/test_backends.py` (contribution template name, rendered "Pending review", lines ~394-500, `test_get_dashboard_contributions...` ~778-863); `course_applications/tests/playwright/test_application_form_flow.py` (heading role "Your applications" line 69, "Pending review" 106, link "Continue application" 196); `course_applications/tests/test_views.py` (status page); `course_access/tests/test_backends.py`, `test_visibility_enforcing_backend.py` (contribution hook).
