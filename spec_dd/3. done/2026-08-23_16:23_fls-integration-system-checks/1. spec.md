## Problem

FLS ships as a package installed into concrete downstream projects (e.g. First
Class). "Did I wire FLS up correctly?" is the signal a downstream actually needs,
and the canonical failure is the First Class integration of the `home_page`
update:

- `learner_interface` newly required `settings.COURSE_ACCESS_BACKEND`, which
  First Class had never set. FLS's loader (`get_course_access_backend()`,
  `freedom_ls/course_access/loader.py`) is `@functools.cache`d and does
  `import_string(settings.COURSE_ACCESS_BACKEND)` with **no fallback** — an unset
  key raised only on the *first real request*, not at `manage.py check` time.
- First Class's root `urls.py` was missing the `applications/` include.

Both would 500 the catalogue/dashboard at runtime while `manage.py check` passed
clean. They were caught only as a side effect of FLS's own tests being vacuumed
up by the downstream's `pytest` — the exact coupling Part 1 removed.

Layer 4's job is the **shift-left half** of the answer: convert static config
gaps that today surface as a silent runtime 500 into a boot-time failure that
`manage.py check`, `runserver` and `migrate` all surface.

### What is already solved

The required-setting half of the original problem statement **has since been
fixed** by the Layer-0 `per-app config.py settings convention` work.
`freedom_ls/course_access/checks.py` short-circuits on
`config.missing_required()` and returns
`required_settings_errors(config, "freedom_ls_course_access")`, and
`freedom_ls/course_access/tests/test_checks.py::test_unset_backend_reports_required_setting_error`
guards it. Deleting `COURSE_ACCESS_BACKEND` already makes `manage.py check` exit
non-zero with `freedom_ls_course_access.E001`.

This slice therefore does **not** re-implement that check. It treats the existing
behaviour as a regression guard and adds only the gaps that remain.

## Success criteria

1. Setting `COURSE_ACCESS_BACKEND` to an FLS-shipped backend whose app is **not**
   in `INSTALLED_APPS` — the realistic case being
   `freedom_ls.course_applications.backends.ApplicationCourseAccessBackend` with
   `freedom_ls.course_applications` removed — makes `manage.py check` exit
   non-zero with `freedom_ls_course_access.E003`.
2. A project that wires a `sitemap` URL without `django.contrib.sitemaps` in
   `INSTALLED_APPS` gets `freedom_ls_learner_interface.W001` from
   `manage.py check`.
3. Every check ID in `course_access` and `learner_interface` identifies exactly
   one condition, so `SILENCED_SYSTEM_CHECKS` can target it precisely.
4. **Regression guard, not new work:** deleting `COURSE_ACCESS_BACKEND` still
   makes `manage.py check` exit non-zero with `freedom_ls_course_access.E001`.
5. A downstream that removes an FLS app gets none of that app's checks.

   The outcome is uniform; the mechanism is not, which the testing strategy
   reflects. `course_access`'s checks are gated **structurally**: `checks.py` is imported
   only from `CourseAccessConfig.ready()`, so an uninstalled app registers
   nothing and there is no runtime branch to test. `learner_interface.W001`
   additionally carries an explicit `apps.is_installed()` guard, because a test
   using `@override_settings(INSTALLED_APPS=...)` reaches an already-registered
   check function; that guard is the belt-and-braces path and **is** tested.

## Scope

### 1. `freedom_ls_course_access.E003` — backend's app not installed

New check in `freedom_ls/course_access/checks.py` — the app that **owns** the
setting, so it inherits the existing install-gating for free (the module is only
imported from `CourseAccessConfig.ready()`, so an uninstalled `course_access`
registers nothing).

This is deliberately **not** registered from `learner_interface`. Doing so would
force `learner_interface` to import `course_access.config`, adding a cross-app
edge for no benefit; registering it from the consuming app buys nothing once
`E001` lives in `course_access` anyway.

The check must not fire on valid downstream config. A downstream that writes its
own backend at, say, `config/access.py::MyBackend` has it in no installed app at
all, so a naive "containing app config is `None` → error" test would flag a
working project. Scope the check to FLS-owned dotted paths; a non-`freedom_ls.`
backend is the downstream's own business, and Layer 3's
`test_configured_backend_instantiates` already covers whether it actually loads.

```python
if app_configs is not None and not any(
    c.label == "freedom_ls_course_access" for c in app_configs
):
    return []                       # scoped `manage.py check <app>` run
if config.missing_required():
    return []                       # E001 already reports this
dotted = config.COURSE_ACCESS_BACKEND
if not dotted.startswith("freedom_ls."):
    return []                       # the downstream owns its own backend
module_path = dotted.rsplit(".", 1)[0]
if apps.get_containing_app_config(module_path) is None:
    return [Error(..., id="freedom_ls_course_access.E003")]
return []
```

`apps.get_containing_app_config()` resolves by dotted-path prefix without
importing the target and only ever returns an *installed* app config or `None`.
Django uses it the same way in `ModelBase.__new__` to work out which app owns a
class from its module path. (`admin.check_dependencies` is *not* the precedent —
that one uses `apps.is_installed()`, which cannot answer "which app owns this
path".) This would be the codebase's first use of the helper. Because no import
happens and it returns `None` rather than raising, the "checks must never raise"
rule holds for every input this check can hand it. (The helper's own
`check_apps_ready()` can raise `AppRegistryNotReady`, but only before
`django.setup()` — at which point no check has been registered, let alone run.)

Behavioural verification — does the backend actually import and instantiate —
stays in Layer 3's `test_configured_backend_instantiates`
(`freedom_ls/contrib/conformance/test_settings.py`), per D8.

### 2. `freedom_ls_learner_interface.W001` — sitemap wired without `contrib.sitemaps`

New `freedom_ls/learner_interface/checks.py`, registered from a new
`LearnerInterfaceConfig.ready()` — `freedom_ls/learner_interface/apps.py` is
currently a bare `AppConfig` with no `ready()`.

`learner_interface` is the right owner: the sitemap advertises its course pages,
and it already owns `tests/test_seo_discoverability.py`. The sitemap classes and
`robots_txt` view themselves live in the project-root `config/` (excluded from
the package), which only *demonstrates* the reference wiring.

Why this is worth a check at all, confirmed against the tree rather than
assumed: `django.contrib.sitemaps` ships the only copy of the `sitemap.xml`
template (`django/contrib/sitemaps/templates/sitemap.xml`), and this project
reaches it through `django.template.loaders.app_directories.Loader`, listed
explicitly in `config/settings_base.py`'s `TEMPLATES["OPTIONS"]["loaders"]`
(`APP_DIRS` itself is commented out). That loader enumerates *installed* app
configs only. Drop the app and the template is unreachable, so `/sitemap.xml`
raises `TemplateDoesNotExist` on the first real request — the same
silent-runtime-500 shape as the originating bug.

That also fixes the severity. A downstream that supplies its own `sitemap.xml`
via `TEMPLATES["DIRS"]` or an app of its own has a working page with
`django.contrib.sitemaps` absent, so the condition is strong evidence of a
mistake but not proof of one. Hence `Warning`, not `Error`: it prints on every
`check`/`runserver`/`migrate` without blocking a project that knows better.

The warning is also reachable rather than theoretical. Layer 3 already asserts
that a downstream reverses `sitemap` and `robots_txt`
(`freedom_ls/contrib/conformance/test_urls.py`'s reference-URL probe, which calls
a bare `reverse()` with no installed-app guard), so a conformant project has the
URL wired by definition — leaving `django.contrib.sitemaps` out of
`INSTALLED_APPS` is the one remaining way to get there and still break.

Order the gates cheapest-first, so the URLconf is loaded only in the
already-suspect case:

```python
if not apps.is_installed("freedom_ls.learner_interface"):
    return []                       # belt-and-braces for an uninstalled app
if app_configs is not None and not any(
    c.label == "freedom_ls_learner_interface" for c in app_configs
):
    return []                       # scoped `manage.py check <app>` run
if apps.is_installed("django.contrib.sitemaps"):
    return []                       # nothing to warn about; no reverse() at all
if not getattr(settings, "ROOT_URLCONF", None):
    return []                       # no URLconf to interrogate
try:
    reverse("sitemap")
except (NoReverseMatch, ImproperlyConfigured):
    return []                       # nothing wired -> nothing to warn about
return [Warning(..., id="freedom_ls_learner_interface.W001")]
```

Use `apps.is_installed()`, never `name in settings.INSTALLED_APPS`. That setting
legitimately holds AppConfig dotted paths — this project's own
`config/settings_base.py` lists `django_cotton.apps.SimpleAppConfig` — so a
string membership test misses a downstream that names either app by its config
class, and would then warn about a correctly-configured project.
`apps.is_installed()` compares `app_config.name`, so it is immune. In-repo
precedent: `freedom_ls/contrib/conformance/_registry.py` and its
`test_settings.py`.

Checking the app registry first means the common (correct) case never touches the
URLconf.

Read `ROOT_URLCONF` through `getattr(..., None)`, never as `settings.ROOT_URLCONF`.
That setting has **no default in `django/conf/global_settings.py`**, so a project
that has not set one raises `AttributeError` — which the `except` clause does
not catch, breaking `check`/`runserver`/`migrate` with a raw traceback.
Django's own `check_url_config` (`django/core/checks/urls.py`) guards it exactly
this way. `ImproperlyConfigured` is still worth catching alongside
`NoReverseMatch`, but for a different case: a `ROOT_URLCONF` that imports yet
exposes no `urlpatterns`.

**Accepted residual:** a `ROOT_URLCONF` that raises on import for some other
reason would propagate out of `reverse()`. That case is only reachable when the
project is already broken, and Django's own `urls` checks report it; guarding it
here would mean catching bare `Exception`, which the codebase forbids.

### 3. Check-ID hygiene — split the overloaded `freedom_ls_course_access.E001`

`freedom_ls/course_access/checks.py` currently uses **one ID for two unrelated
conditions**: "required setting unset" (via the shared
`required_settings_errors` helper) and "a `Course` has an `access_config` the
active backend rejects". The module docstring concedes as much — "The two never
fire in the same run".

That defeats `SILENCED_SYSTEM_CHECKS`: a downstream silencing
`freedom_ls_course_access.E001` to suppress access-config noise during a backend
swap also silences the missing-required-setting error — the exact error this
whole track exists to surface. It also contradicts D3's "unique, stable IDs so
`SILENCED_SYSTEM_CHECKS` can target them precisely".

Re-ID the `access_config` validation error to `freedom_ls_course_access.E002`.
`E001` stays with the shared helper's missing-required-setting message, matching
`freedom_ls_reports.E001` and `freedom_ls_content_engine.E001`, which call the
same helper.

`freedom_ls/reports/checks.py` sets the house rule for check-ID churn — it keeps
a legend line reading "W003 — Retired. Do not reuse the id: a project may still
be silencing it." Follow that convention when rewriting the `course_access`
legend.

**This is downstream-visible**, and in a way that adding an ID is not. The split
*narrows* `E001` rather than retiring it, so a project with
`freedom_ls_course_access.E001` in `SILENCED_SYSTEM_CHECKS` for access-config
reasons must **remove** that entry and add `.E002`. Adding `.E002` alone leaves
the missing-required-setting error suppressed — the exact failure this track
exists to surface. Capture it at SDD step 11 (`/fls-dev:update_upgrade_notes`)
with `requires_settings_change: true`.

### Resulting ID allocation

| ID | Condition | Status |
|---|---|---|
| `freedom_ls_course_access.E001` | required setting unset | exists, unchanged |
| `freedom_ls_course_access.E002` | invalid `Course.access_config` | **re-ID** from E001 |
| `freedom_ls_course_access.E003` | FLS backend's app not installed | **new** |
| `freedom_ls_course_access.W001` | preview override with `DEBUG=False` | exists, unchanged |
| `freedom_ls_learner_interface.W001` | sitemap wired, `contrib.sitemaps` absent | **new** |

## Explicitly out of scope

- **A second "is `COURSE_ACCESS_BACKEND` set" check.** Already covered by
  `freedom_ls_course_access.E001` (see "What is already solved").
- **A pinned-`AUTH_USER_MODEL` check.** The original spec proposed
  `freedom_ls_accounts.E003`, erroring when `AUTH_USER_MODEL !=
  "freedom_ls_accounts.User"`. Dropped: it was not part of the originating bug,
  and Django already fails loudly and unmissably when the user model is swapped —
  every FK declared against `settings.AUTH_USER_MODEL` repoints and migrations
  break. This track exists to convert *silent* runtime failures into boot-time
  ones; a check guarding an already-deafening failure adds a maintained surface
  for no signal.
- **Renaming `icons/checks.py`'s flat `freedom_ls.E00N` IDs.** D3 already records
  this as the lone inconsistent precedent and as a deliberate non-fix. It is a
  consistency wart, not a correctness problem, and renaming shipped IDs would
  break downstream `SILENCED_SYSTEM_CHECKS` entries for no gain.
- **Anything behavioural.** Whether the backend imports and instantiates, whether
  a namespace reverses — Layer 3, already shipped.

## Conventions to follow

Match the existing house style in `course_access/checks.py`, `base/checks.py`,
`accounts/checks.py`:

- **App-label-namespaced IDs** (`freedom_ls_learner_interface.W001`). Do not copy
  `icons/checks.py`'s flat `freedom_ls.E00N` scheme (D3).
- Register at import time via `@register()`; `ready()` only imports the module.
- **No `Tags.database`, no `deploy=True`** — these are internal-consistency
  checks that must run on every `check`/`runserver`/`migrate`.
- **No DB access** — read `settings` and `apps` only.
- **Respect the `app_configs` contract:** when `app_configs is not None`,
  early-return `[]` unless the owning app's label is in it, so scoped
  `manage.py check <app>` runs stay correct.
- **Checks must never raise.** Django does not catch check exceptions; a raised
  exception breaks `check`/`runserver`/`migrate` with a raw traceback.

## Key decisions

- **D3 — app-label-namespaced check IDs**, not the flat `freedom_ls.E00N` scheme.
  Extended here to a corollary: one ID means one condition, which is what
  motivates the E001/E002 split above.
- **D7 — override-friendliness over completeness.** Checks are gated on their
  owning app being installed and no-op when absent. E003 extends this to the
  *backend* dimension: an FLS-shipped backend is checked, a downstream's own is
  left alone.
- **D8 — required-setting presence/value is Layer 4's job, not Layer 3's.**
  Unchanged in principle; in practice Layer 4 already discharged it via
  `freedom_ls_course_access.E001`. Layer 3 keeps only the behavioural seam
  (`test_configured_backend_instantiates`). The `freedom_ls_accounts.E003`
  example named in the umbrella's D8 prose no longer applies — that check is out
  of scope (see above).

## Testing strategy

Mirror `freedom_ls/course_access/tests/test_checks.py` — call each check directly
with `app_configs=None`, drive config via `@override_settings`, assert on
returned message IDs and levels. No `django_db` needed for the new checks: they
read `settings` and `apps` only.

- `freedom_ls/course_access/tests/test_checks.py` (extend):
  - E003 fires for an FLS backend whose app is not installed.
  - E003 stays silent for a non-`freedom_ls.` backend path (the false-positive
    guard).
  - E003 stays silent when `COURSE_ACCESS_BACKEND` is unset (E001 owns that).
  - E002 is the ID now returned for an invalid `access_config` — add explicit
    ID assertions to `test_bad_access_config_produces_error` and
    `test_error_includes_course_slug`, which currently assert on message text
    only. Leave `test_unset_backend_reports_required_setting_error` asserting
    E001; it is criterion #4's regression guard.
  - `app_configs` early-return honoured.
- `freedom_ls/learner_interface/tests/test_checks.py` (new):
  - W001 fires when a `sitemap` URL reverses and `django.contrib.sitemaps` is
    absent from `INSTALLED_APPS`.
  - Silent when `django.contrib.sitemaps` is installed.
  - Silent when no `sitemap` URL is wired.
  - Silent when there is no `ROOT_URLCONF` to interrogate — the guard that keeps
    the check from raising `AttributeError` on a project that never set one.
  - App-absent gate and `app_configs` early-return both return `[]`.
