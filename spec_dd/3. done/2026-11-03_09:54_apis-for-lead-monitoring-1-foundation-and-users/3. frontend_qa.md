# Frontend QA: Lead monitoring API, foundation and users

This change adds a read-only API under `/api/v1/` with a users endpoint, authenticated by a
site-bound API key that a site admin issues and revokes in the Django admin. It also removes
`django-ninja`, moves a user's `updated_at` when their email verification changes, and audits
key issue and revoke.

What a browser can see:

- **API keys** in the admin: an add form (name, API scopes as checkboxes, expiry; no site field),
  a one-off page that shows the full key once, a changelist with a status column and filter, a
  change form where only the name of a live key is editable, and a revoke flow (list action and
  change-page button) through one confirmation page.
- **Audit log entries** for every issue and revoke.
- **The API itself** answers JSON to a terminal (`curl`); a browser visiting an API URL sees the
  401 body.

Beyond the golden path, this run hunts for:

- **The key leaking.** The full key must appear on exactly one page, once. It must not be in a
  flash message, the changelist, the change form, the audit log, or a response that a browser may
  cache.
- **Over-reach.** A key missing an API scope, a revoked key, an expired key, a key sent in the
  query string and a logged-in browser session without a key must all be refused.
- **Repeat and stale actions.** Revoking an already-revoked key must do nothing and audit nothing;
  re-submitting the add form after the key page must issue a second key, not re-show the first.
- **Side effects.** The user CSV export, course pages (pydantic content loading) and the rest of
  the admin still work after the dependency changes.

## §1 Issue a key

### 1.1 The add form

1. Go to `http://127.0.0.1:$PORT/admin/freedom_ls_api/apikey/`. The page is titled "API keys" and
   is empty, with an "Add API key" button.
2. Click it. Expect fields **Name**, **Scopes** (four checkboxes: Users, Course applications,
   Referral data, Registrations and progress, each followed by the model names it covers) and
   **Expires at**. Expect **no** Site field and no key, prefix or hash field.

### 1.2 Validation

1. Submit with Name "QA nightly sync" and no scope ticked. Expect the form back with an error on
   Scopes ("Choose at least one API scope.") and no key issued (the changelist stays empty).
2. Tick **Users**, set Expires at to yesterday, submit. Expect an error on Expires at saying the
   expiry must be in the future.

### 1.3 The key page

1. Clear Expires at, keep Users ticked, submit.
2. Expect a page inside the admin shell titled "API key issued", with the key's name and the full
   key in a monospace box, starting `flsk_` and containing one `.`. Expect the sentence that it is
   not shown again, and a button back to the API keys list.
3. Expect **no** green "was added successfully" message anywhere on this page, and the URL to
   still be the add URL (no redirect).
4. In the browser's network panel (or `curl -i` of the same POST is not possible; use the panel),
   the response to the add POST has `Cache-Control: no-store`.
5. Copy the full key into `KEY` in the terminal.

### 1.4 After the page

1. Click the button back to the list. Expect one row: name "QA nightly sync", a 12-character
   prefix, scopes "Users", status **Active**, empty Expires at and Last used at, a Created at.
   Expect the full key text nowhere on the page (search the page for the secret part after the
   `.`).
2. Open the row. Expect Name editable, every other field read-only (prefix, scopes, status,
   expires at, revoked at, last used at, created at, updated at). Expect no "Key hash" field and
   no Delete button or link at the bottom.
3. Browser back twice to the add form, submit again with the same name. Expect a second,
   different key on a new key page (a repeat is a new key, never the old one shown twice). Copy
   this second key as `KEY2`. The list now has two Active rows with the same name and different
   prefixes.

### 1.5 Scoped key for the refusal tests

Issue a third key named "QA no users" with only **Course applications** ticked. Copy it as
`KEY_NOUSERS`.

## §2 The API from a terminal

### 2.1 No key

```
curl -si http://127.0.0.1:$PORT/api/v1/users/
```

Expect `HTTP/1.1 401`, header `WWW-Authenticate: Bearer realm="api"`, header
`Cache-Control: private, no-store`, body `{"detail": "...", "code": "not_authenticated"}` (one
sentence, no mention of what was wrong).

### 2.2 Refusals look the same

Each of these must be 401 with the same body and headers as 2.1:

```
curl -si -H "Authorization: Basic $KEY" http://127.0.0.1:$PORT/api/v1/users/
curl -si -H "Authorization: Bearer nonsense" http://127.0.0.1:$PORT/api/v1/users/
curl -si -H "Authorization: Bearer flsk_000000000000.wrong" http://127.0.0.1:$PORT/api/v1/users/
curl -si -H "Authorization: Bearer ${KEY%.*}.wrongsecret" http://127.0.0.1:$PORT/api/v1/users/
curl -si "http://127.0.0.1:$PORT/api/v1/users/?key=$KEY"
```

### 2.3 A valid key

```
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:$PORT/api/v1/users/ | python -m json.tool
```

Expect `{"next": null, "results": [...]}` with `N` users (fewer than 100) and, per user, exactly
the keys `id` (integer), `email`, `first_name`, `last_name`, `is_active`, `is_staff`,
`email_verified`, `created_at`, `last_login`, `updated_at`. Timestamps end in `Z` or an offset.
No `password`, `is_superuser`, `groups` or `user_permissions`.

Lowercase scheme also works: `-H "Authorization: bearer $KEY"` is 200.

Detail: take one `id` from the list; `curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:$PORT/api/v1/users/<id>/`
is that one user. `.../users/999999/` is 404 with body `{"detail": "...", "code": "not_found"}`.

### 2.4 Paging

```
curl -s -H "Authorization: Bearer $KEY" "http://127.0.0.1:$PORT/api/v1/users/?page_size=2" | python -m json.tool
```

Expect 2 results and a `next` URL that keeps `page_size=2` and adds `cursor=`. Follow `next` by
hand (quote the URL) until `next` is `null`; the ids seen across all pages are each seen once and
total `N`.

Then:

- `?page_size=0` → 400 `{"page_size": [...]}`.
- `?page_size=abc` → 400 naming `page_size`.
- `?page_size=5000` → 200 with at most 500 results (all `N` here).
- `?cursor=not-a-cursor` → 400 `{"cursor": [...]}`.

### 2.5 `updated_since`

- `?updated_since=2000-01-01T00:00:00Z` → every user.
- `?updated_since=2999-01-01T00:00:00Z` → `results: []`.
- `?updated_since=2000-01-01T00:00:00` (no timezone) → 400 `{"updated_since": [...]}`.
- `?updated_since=yesterday` → 400 naming `updated_since`.

### 2.6 Missing API scope, methods, OPTIONS, HEAD

- `-H "Authorization: Bearer $KEY_NOUSERS"` on the users list → 403 with a body whose `detail`
  names the `users` API scope and `code` is `permission_denied`.
- `curl -si -X POST -H "Authorization: Bearer $KEY" http://127.0.0.1:$PORT/api/v1/users/` → 405
  JSON `{"detail", "code": "method_not_allowed"}`. Same for `-X PUT`, `-X PATCH`, `-X DELETE`.
- `curl -si -X OPTIONS -H "Authorization: Bearer $KEY" http://127.0.0.1:$PORT/api/v1/users/` →
  200, an `Allow` header listing GET, HEAD, OPTIONS, and a body with only a `name`.
- `curl -sI -H "Authorization: Bearer $KEY" http://127.0.0.1:$PORT/api/v1/users/` → 200 with the
  same headers as GET and no body.

### 2.7 Schema

- `curl -si http://127.0.0.1:$PORT/api/v1/schema/` → 401.
- `curl -s -H "Authorization: Bearer $KEY_NOUSERS" http://127.0.0.1:$PORT/api/v1/schema/ | python -m json.tool`
  → 200 JSON OpenAPI with `securitySchemes.ApiKeyAuth` of type `http`, scheme `bearer`, and the
  `/api/v1/users/` operation listing `updated_since`, `cursor` and `page_size` parameters. A key
  with no `users` API scope still reads the schema.

### 2.8 Last used

Back in the admin, open "QA nightly sync" (the first key). Expect **Last used at** now filled, within
the last few minutes. Make one more API call, reload: it does not change (it moves at most every
5 minutes), and **Updated at** has not moved from the issue time.

### 2.9 A browser sees the 401 too

Logged in to the admin, visit `http://127.0.0.1:$PORT/api/v1/users/` in the browser. Expect the
401 JSON body as plain text (no browsable API page, no HTML), even though a session cookie was
sent.

## §3 Revoke

### 3.1 From the list, with a confirmation page

1. On the API keys changelist, tick "QA no users" and "QA nightly sync" (the second row, `KEY2`),
   choose action "Revoke selected keys", Go.
2. Expect a confirmation page in the admin shell titled "Revoke API keys", listing both keys by
   name and prefix, the sentence that scripts using them stop at once, a Revoke button and a cancel
   link. Nothing has changed yet: open the list in another tab, both are still Active.
3. Click Revoke. Expect to land back on the list with the message "Revoked 2 API keys. Scripts
   using them stop at once.", both rows now **Revoked** with a Revoked at time.
4. `curl -si -H "Authorization: Bearer $KEY2" http://127.0.0.1:$PORT/api/v1/users/` → 401, same
   body as 2.1. `KEY` (the first key) still works.

### 3.2 Already revoked is skipped

1. Tick the two Revoked rows plus the Active "QA nightly sync" (`KEY`), run the action again.
2. Expect the confirmation page to list only the active key under what will be revoked and the two
   revoked keys as already revoked and skipped.
3. Cancel (the cancel link). Expect the list unchanged: one Active key remains.

### 3.3 From the change page

1. Open the Active "QA nightly sync". Expect a "Revoke this key" button in the page's actions.
2. Click it. Expect the same confirmation page for this one key. Click Revoke.
3. Expect to return to the key's change page with the message "Revoked 1 API key. Scripts using
   it stop at once.": status Revoked, every field read-only, the Revoke button gone.
4. `KEY` is now 401 on the API.
5. Open the revoke URL by hand for a made-up id: `http://127.0.0.1:$PORT/admin/freedom_ls_api/apikey/revoke/?ids=00000000-0000-0000-0000-000000000000`
   is 404, and `?ids=not-a-uuid` is 404 too.

### 3.4 Revoked keys are inert

- The change page of a revoked key has no editable field; changing the URL to `.../delete/` is
  403 or 404, never a delete confirmation.
- The status filter on the changelist: **Active** shows nothing now, **Revoked** shows all three,
  **Expired** shows nothing.

## §5 Email verification moves `updated_at`

1. Issue a fresh key "QA sync 2" with Users ticked; copy it as `KEY3`.
2. In the terminal, `SINCE=$(date -u +%Y-%m-%dT%H:%M:%SZ)` and wait a few seconds.
3. `curl -s -H "Authorization: Bearer $KEY3" "http://127.0.0.1:$PORT/api/v1/users/?updated_since=$SINCE"`
   → `results: []`.
4. In the admin, open **Email addresses** (allauth, under Accounts), open a demo learner's address,
   untick **Verified**, save.
5. Repeat the curl. Expect exactly that learner in `results`, with `email_verified: false`.
6. Tick Verified again and save; the curl still returns that learner, now `email_verified: true`.
7. Log in as that learner in a private window (or just reload the admin as demodev): a login does
   not add demodev to the filtered results.

## §6 Side effects of the dependency change

1. Admin → Users changelist → tick a user → action "Export" (or the Export button). Expect a CSV
   download whose header includes `email_verified` and whose values match the API's
   `email_verified` for the same users.
2. Visit the learner home page and open one demo course and one topic inside it. Expect normal
   rendering (course content loads through pydantic schemas, which are now a direct dependency).
3. `uv run python manage.py check` prints no error. With `DEBUG=False` in the environment the dev
   settings support (if they do), expect `freedom_ls_api.W001` warning about the per-process
   cache; otherwise skip this line.
4. `grep -ri ninja freedom_ls config pyproject.toml` prints nothing.
