# Spec: Lead monitoring API, attribution touches and conversions

Spec 6 of 6 in the Lead monitoring API effort (`spec_dd/1. next/roadmap.md`, "Lead monitoring
API"). Source: `idea.md` in this directory. Recorded answers: `answers.md`. Research: the
`research_*.md` files beside it.

## Purpose

Child 3 lets a script see who arrived through which referral link. A payout or lead report also
needs to know which of that person's later actions to credit, and today only the admin CSV export
has that. This spec adds two read-only resources under `/api/v1/`, `attribution-touches` and
`conversions`, over the shipped `AttributionTouch` and `Conversion` models, readable by an `ApiKey`
with the `referral_data` scope.

## Scope

In:

- `attribution-touches` and `conversions`, each with a list route and a detail route, read only,
  bound to the key's site.
- `updated_since` on `recorded_at` for both. Equality filters on the user and on referral codes
  for both, and on `kind` for conversions. These are the first non-date filters in the API.
- Case-insensitive indexes on the code columns the filters match.
- Documentation in `docs/api.md` and the product docs.

Out (from `idea.md`): write endpoints and any change to how touches or conversions are recorded;
resolving a conversion's target, `content_type` or `object_id`; credit rules, payout calculation or
summaries; touch pruning and a deletion feed; device or browser identifiers; admin export changes.
Also out: filters or ordering on `occurred_at`, which can be older than rows already read because a
flushed touch is recorded after it happened; any other date-range filter; embedding touches in a
conversion; a filter for "no code in play" (an empty filter value means the filter is absent);
rejecting unknown query parameters.

## Decisions

| Decision | Reason |
| --- | --- |
| Flat lists joined by id. A conversion carries `first_touch` and `last_touch` as touch UUIDs, not embedded objects. | Matches children 1 to 5. The frozen codes on the conversion already answer the payout query without a join. |
| `user` (integer id) plus `user_email` on both resources. | The effort's pattern since child 3's signup attributions. The email already reaches `referral_data` keys, so this adds no new class of exposure. |
| Code filters match case-insensitively (`iexact`). | Stored codes keep the case they were typed or printed in, and `ReferralCode.code` is unique ignoring case. `CodeInPlayFilter` in `freedom_ls/referral_tracking/admin.py` matches the same way, so API counts agree with the admin. |

## Requirements

### Shared API machinery (`freedom_ls/api/`)

**`filters.py`.** Add `IntegerFilter`, a `django_filters.NumberFilter` whose `field_class` is
`forms.IntegerField`. A decimal or non-numeric value is a 400 keyed by the parameter name, and the
OpenAPI schema types the parameter as `integer`.

**`scopes.py`.** `_DESCRIPTIONS[ApiScope.REFERRAL_DATA]` becomes
`"ReferralCode, ReferralCodeHit, SignupAttribution, FirstTouchCount, AttributionTouch, Conversion"`.
The stored value stays `referral_data`.

Pagination and viewsets are unchanged: a `recorded_at` cursor already passes
`freedom_ls_api.E002`.

### Indexes (`freedom_ls/referral_tracking/models.py`)

One new migration adds functional indexes, so an `iexact` code filter does not scan the site's
rows:

- `AttributionTouch`: `Index(F("site"), Upper("referral_code"))`.
- `Conversion`: `Index(F("site"), Upper("first_referral_code"))` and
  `Index(F("site"), Upper("last_referral_code"))`.

Each index has an explicit `name`. The existing `(site, referral_code)` touch index stays. On
PostgreSQL, Django compiles `iexact` to `UPPER("col"::text) = UPPER(%s)`, so the plan checks with
`EXPLAIN` that the planner uses these indexes for that form.

### Resources (`freedom_ls/referral_tracking/api.py`)

Two more serializer, filterset and viewset trios in the existing module, following the four already
there. Serializers set an explicit `fields` tuple and `read_only_fields = fields`. Viewsets set
`required_scope = ApiScope.REFERRAL_DATA` and `cursor_field = "recorded_at"`, start from
`Model._base_manager.select_related("user")`, and look up details by the UUID `id`.

| Prefix / basename | Model | Filters |
| --- | --- | --- |
| `attribution-touches` / `attribution_touch` | `AttributionTouch` | `updated_since`, `user`, `referral_code` |
| `conversions` / `conversion` | `Conversion` | `updated_since`, `user`, `kind`, `referral_code`, `first_referral_code`, `last_referral_code` |

Fields, in this order:

- **`AttributionTouch`:** `id`, `user`, `user_email` (`source="user.email"`), `advert_code`,
  `referral_code`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`,
  `landing_path`, `occurred_at`, `recorded_at`, `recorded_via`. `key_hash` is withheld.
- **`Conversion`:** `id`, `user`, `user_email`, `kind`, `target_label`, `occurred_at`,
  `recorded_at`, `window_days`, `first_touch`, `last_touch`, `first_referral_code`,
  `last_referral_code`. `content_type` and `object_id` are withheld. `first_touch` and
  `last_touch` are listed in `fields`. The generated field is a nullable read-only UUID that reads
  `first_touch_id` without a join, so `select_related("user")` is the only join. Both are `null`
  when nothing was in play.

Filters. Every filter has `help_text` naming the field it compares against. Filters combine with
AND.

- `updated_since`: `AwareIsoDateTimeFilter(field_name="recorded_at", lookup_expr="gte")`, declared
  once on `RecordedAtFilterSet`, a filterset base in this module that both filtersets extend.
- `user`: `IntegerFilter` on `user_id`, declared on `RecordedAtFilterSet` too. An id with no rows
  on the key's site returns an empty list.
- `referral_code` on touches: `iexact` on `referral_code`.
- `referral_code` on conversions: a `method=` filter applying
  `Q(first_referral_code__iexact=v) | Q(last_referral_code__iexact=v)`, through
  `with_code_in_play(queryset, code)` in `models.py`, which the admin's `CodeInPlayFilter` also
  calls. For an empty value the method returns the queryset unchanged. Its `help_text` says it matches either code.
- `first_referral_code`, `last_referral_code`: `iexact` on their own column. `answers.md` says
  these match "exactly", read here as "only their own column", not as case-sensitive.
- `kind`: a `ChoiceFilter` over `ConversionKind` with an `invalid_choice` error message built from
  `ConversionKind.values`, so an unknown value is a 400 keyed `kind` that lists
  `account_signup`, `course_application`, `course_interest` and `course_registration`.

`target_label` is the frozen string the recorder wrote: `"Account signup"`
(`SIGNUP_CONVERSION_LABEL` in `freedom_ls/referral_tracking/signals.py`) for `account_signup`, and
the course title for the other three kinds. It is not an email, so the idea's "account email" does
not apply.

Both models live in `referral_tracking`, so the endpoints exist wherever the other referral
resources do. A site with no rows returns `{"next": null, "results": []}`. `referral_tracking → api`
already exists, so `docs/app_structure.md` and `test_organisation/import_contracts.toml` do not
change.

## Testing

Tests go in `freedom_ls/referral_tracking/tests/test_api.py`. Rows are built with
`AttributionTouchFactory` and `ConversionFactory`. `recorded_at` is set with
`Model._base_manager.filter(...).update(...)`, because `save()` refuses an update.

Both resources join the existing parametrised `TestSharedResourceBehaviour` for the checks already
in it: the exact field set (with `key_hash`, `content_type` and `object_id` never present), a
second-site row absent from the list and 404 on detail, 403 naming the scope without
`referral_data`, 401 with no key, 405 on POST, and HEAD and OPTIONS working. The existing four
resources' tests do not change.

A new class parametrised over the two new resources only:

- Rows come in ascending `(recorded_at, id)` order across pages.
- The query count is the same at page size 2 and 50.
- 1,500 rows sharing one `recorded_at`, paged at the maximum page size, each appear exactly once.
  The rows share one saved user. Touches vary `occurred_at` and conversions vary `object_id`, to
  satisfy each model's unique constraint. They are built with `build_batch` and `bulk_create`,
  then given the shared `recorded_at` with one `update()`.
- `updated_since`: a row exactly at the bound is included and one before it is excluded. A naive
  datetime is a 400.
- `user`: filters to that user's rows. `abc` and `1.5` are each a 400 keyed `user`. An id from
  another site returns an empty list.
- `next` keeps every filter and `page_size`.

Specific to one resource:

- A touch whose `occurred_at` is older than every row already read is still returned on a later
  page.
- On touches, `referral_code` matches regardless of case.
- On conversions, `referral_code` returns a row whose first code matches, a row whose last code
  matches, and one row once when both match. `?referral_code=` returns every conversion.
  `first_referral_code` and `last_referral_code` each match only their own column. All three
  ignore case.
- `kind` filters to one kind. An unknown value is a 400 keyed `kind` that lists the four values.
- A conversion with nothing in play serialises as null touches and empty codes.
- A conversion whose target has been deleted is still returned with its `target_label`.

`freedom_ls/api/tests/test_filters.py`: `IntegerFilter` accepts `42` and rejects `1.5` and `abc`.

Existing tests that must still pass: `manage.py spectacular --validate --fail-on-warn` and the
`docs/api.md` python fence compile check.

## Documentation and downstream

**`docs/api.md`:**

- The intro, the scope table and the "Referral data" intro ("Four API endpoints" becomes six) name
  the two endpoints. `referral_code` on both is code text captured at the landing, as on signup
  attributions.
- "Incremental syncs" gets two Checkpoint rows on `recorded_at`. The Checkpoint text adds
  `recorded_at` to the fields "stamped before the write commits", so the 5-minute margin and upsert
  by `id` apply. Touches and conversions never move, like hits and signup attributions.
- "Deletions": touches and conversions go when their user is deleted, and no filter shows it. A
  touch a conversion points at cannot be deleted on its own.
- One section per resource in the existing layout (header table, Fields table, notes):
  - **Two clocks.** `occurred_at` is when the landing or action happened. `recorded_at` is when the
    row was written. Checkpoint on `recorded_at` and sort a timeline on `occurred_at`. An example:
    a visitor lands on Monday and signs up on Thursday, so the touch is written on Thursday with
    `occurred_at` on Monday and `recorded_via` set to `signup_flush`.
  - A `recorded_via` table: `live` is written when the landing happened. `signup_flush` and
    `login_flush` are written later from the cookie.
  - A first and last touch table: the earliest and latest touches in play within `window_days`
    when the conversion was resolved. They are the same id when one touch was in play, and `null`
    with `""` codes when none was. That is a recorded answer, not missing data. Rows are final once
    written: a touch recorded later never changes an earlier conversion. `window_days` is the
    window at resolution time, not today's setting. The API picks no credit model.
  - A `kind` table with what `target_label` holds for each kind. The label does not follow course
    renames.
  - Filters: `referral_code` on conversions matches either code, so counting its rows does not
    give first-touch or last-touch credit. Code filters ignore case. An unknown query parameter is
    ignored, not rejected, so a misspelled filter returns every row.
- The example's `PATHS` gains `"attribution-touches": "recorded_at"` and
  `"conversions": "recorded_at"`.
- The "No conversion uploads" caveat says it means Google or Meta conversion uploads, which are not
  the `conversions` endpoint.

**`docs/product/security-and-data-handling.md`:** the "Built" API bullet and the "**Referral
data.**" paragraph under "API Access (built)" name both resources. They return the user's id and
email, codes, UTM values, `landing_path` and times, and no IP, user agent, referer, raw query,
click id or cookie id. The "Attribution touches and conversions" bullet's "neither is readable
through the API" now says both are readable under `referral_data`. Downstream copies of deleted
users' rows are the key holder's to delete. Bump "Last updated".

**`docs/product/signup-attribution.md`:** "the timeline and conversions are in the admin and CSV
only" and the paragraph beginning "Scripts can read the same signup attributions" now include the
API. **`docs/product/referral-codes.md`:** the sentence beginning "Both the code list and the hit
log export to CSV" lists the two resources among those a `referral_data` key reads. Bump "Last
updated" on both.

**Upgrade notes:** run the new `referral_tracking` migration, which adds three indexes. No new
setting.

## Open questions

- Q: Do `first_referral_code` and `last_referral_code` match case-sensitively, given `answers.md`
  says they match their own code "exactly"? → A: No, all three code filters ignore case (assumed
  default: "exactly" in the answer is read as "only its own column", and `iexact` keeps API counts
  equal to the admin's `CodeInPlayFilter`. Overrule by editing Decisions and the Filters list in
  Requirements.)

## Success criteria

- A reviewer given only `docs/api.md` can write a last-touch payout query for one code and a
  checkpoint sync of both endpoints.
- `EXPLAIN` of a conversions list filtered by `referral_code` on a seeded site shows the two new
  conversion indexes in use, and a touches list filtered by `referral_code` shows the new touch
  index.
