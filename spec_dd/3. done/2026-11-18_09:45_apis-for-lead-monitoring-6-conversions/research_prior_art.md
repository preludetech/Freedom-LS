# Research: prior art for the attribution touches and conversions API

Sources read: children 1 to 5 of the Lead monitoring API (specs, plans, QA reports, upgrade notes) and `referral-attribution-over-time` in `spec_dd/3. done/`, plus the shipped `freedom_ls/referral_tracking/models.py`, `freedom_ls/referral_tracking/api.py` and `docs/api.md`. Web research was not run; the "elsewhere" section reuses child 3's cited complaints file (URLs below) and general API practice.

## 1. What shipped that this child builds on

- **Child 3 (referral data) is the template.** `freedom_ls/referral_tracking/api.py` already holds four resources. Each has an explicit-field `ModelSerializer`, a `ReadOnlyApiViewSet` with `cursor_field` set (`created_at`, `hit_at`, `signed_up_at`, `day`), and a `FilterSet` that redeclares `updated_since = AwareIsoDateTimeFilter(field_name=<append-only timestamp>, lookup_expr="gte")`. Querysets start from `Model._base_manager.select_related(...)`. The two new resources fit this pattern with `cursor_field = "recorded_at"`, so child 6 needs no pagination change.
- **Cursor keying is already generalised.** The cursor is `(cursor_field, id)` and carries the field it pages on. A `cursor_field` must be a non-null `DateTimeField` or `DateField`. `manage.py check` reports anything else as `freedom_ls_api.E002`, and a list request raises `ImproperlyConfigured`. `recorded_at` is `auto_now_add`, so it is non-null and passes. Child 3's upgrade notes say a `next` link from before a release is a 400 after it. Child 6 adds no pagination change, so that does not recur.
- **Indexes were prepared for this child.** `AttributionTouch` and `Conversion` each carry `Index(fields=["site", "recorded_at"])`, commented in the models as "a cursor for a changed-since conversions feed". The cursor query needs no new index. The `id` tie-break only sorts ties, which is what child 3 concluded for its own indexes.
- **Default `Meta.ordering` is not the API ordering.** The models order `-occurred_at` (touches `-occurred_at, -recorded_at`). The paginator imposes `(cursor_field, id)` itself, as it does for hits (`hit_at`). The viewset must not rely on, or be surprised by, the model default.

## 2. Lessons and pitfalls from earlier children

1. **"Append-only" timestamps are stamped before commit, so the 5-minute margin applies.** Child 3's `docs/api.md` states that `hit_at` and `signed_up_at` are "stamped before the write commits, so the same 5-minute margin applies". `recorded_at` has the same property (`auto_now_add`, set at save time inside the transaction). The idea's claim that "a script that follows pages and remembers its last `recorded_at` misses nothing" is only true with that margin. Child 6's docs should say "checkpoint at the largest `recorded_at` seen, minus 5 minutes, upsert by `id`", and not promise exactness. This is the largest correctness gap I found in the idea's wording.
2. **Flushed touches write several rows in one moment.** A signup or login flush writes one touch per cookie entry in one transaction, so many rows can share nearly the same `recorded_at`. Child 3 hit the same issue with hits and tested 1,500 rows sharing one timestamp, paged at the maximum page size, each row appearing exactly once. Copy that test for `recorded_at`, for both resources.
3. **`updated_since` is inclusive, so the boundary row repeats.** Child 3's complaints research says to document that scripts de-duplicate on `id`. The tests assert a row exactly at the bound is included and a row before it is excluded, and a naive datetime is a 400.
4. **Docs conventions children 3 to 5 settled.**
   - `docs/api.md` has a table of endpoint, ordering field, filter and recipe, and a "Deletions" table of visible and invisible changes. Both gain two rows.
   - Each resource has a section in the Users layout: endpoint table, Fields table, notes.
   - The python fences in `docs/api.md` must still compile (`freedom_ls/api/tests/invariants/test_api_docs.py`).
   - `docs/product/security-and-data-handling.md` is updated, and "Last updated" is bumped.
   - `docs/app_structure.md` and `test_organisation/import_contracts.toml` are generated by `ds:app_map`, never hand-edited. The `referral_tracking -> api` edge already exists, so no new edge is expected.
   - The scope description in `scopes.py` (`ApiScope.REFERRAL_DATA` in `_DESCRIPTIONS`) lists model names and was changed by child 3. It should gain `AttributionTouch, Conversion`.
5. **Test conventions.** Endpoint tests go in `freedom_ls/referral_tracking/tests/test_api.py`. They use the `referral_tracking` factories, never `/go/`. Because the append-only `save()` refuses updates, timestamps are set with `Model._base_manager.filter(...).update(...)`, and the same applies to the new models, which use `_refuse_update`. Tests prove:
   - the exact field set;
   - a second-site row is absent and its detail is 404;
   - 403 without the scope, 401 without a key, 405 on POST;
   - a query-count bound over 20 rows to prove `select_related`;
   - the schema validates with `--fail-on-warn`.
   Two things are new here. An FK id exposed as a field (`first_touch`, `last_touch`) must be declared so OpenAPI types it as a UUID string. Child 5 hit this and declared every `*_id` explicitly. A nullable FK id must also be typed nullable.
6. **Nullable FKs and per-row queries.** Child 5 settled that `get_queryset` joins only what the serializer reads, and tests that the query count is the same at page size 2 and 50. For this child, `user` as an id and `first_touch` / `last_touch` as ids need no join. A `user_email` field would need `select_related("user")`. The idea leaves that open, and child 3 chose id plus `user_email` on signup attributions. Child 4 and 5 flattenings also carry `user_email`, so the whole effort returns id plus email. Matching that is the least surprising choice, and the security doc must then say the new endpoints return the email.
7. **Frozen-label design already pays off.** `Conversion.target_label`, `first_referral_code` and `last_referral_code` are frozen copies and `content_type` / `object_id` are not returned. This keeps the list free of per-row lookups, as the idea says. The attribution spec's note that `GenericForeignKey` must be resolved one row at a time, never with `prefetch_related`, because `object_id` is text, is a trap the API avoids by not resolving it.
8. **Deletions are invisible, and there are three channels here.**
   - Deleting a user cascades to touches and conversions.
   - `prune_attribution_touches` deletes touches older than the window across every site (spec section 9). `Conversion.first_touch` / `last_touch` use `RESTRICT`, so a touch a conversion rests on cannot be pruned on its own.
   - Conversions are never pruned.
   So a `first_touch` / `last_touch` id returned in a conversion always resolves in the touches list until the user is deleted. Pruned touches that no conversion points at disappear silently. Child 6's "Deletions" rows should say so. The idea puts the prune command and a deletion feed out of scope, which matches the pattern.
9. **Filters and indexes.**
   - Child 3 explicitly put "filters on referral codes" out of scope, so this child's filters are new, not copied. The idea's `user`, `kind`, `referral_code` and first / last code filters need `django-filter` declarations.
   - Touches have `Index(site, referral_code)`, so a code filter on touches is indexed.
   - Conversions have only `(site, kind, occurred_at)`, `(site, recorded_at)` and `(content_type, object_id)`. There is no index on `first_referral_code` or `last_referral_code`, so the "payout query" filter, and the "either code" filter in `answers.md`, are sequential scans within a site (with `site, recorded_at` as the most likely plan). That is fine at current volume, but the spec should either accept it knowingly or add an index. Adding one is a migration, and the idea does not mention it.
   - The "either code" filter must be written as `Q(first_referral_code=x) | Q(last_referral_code=x)`. The admin's "code in play" filter already does this, and its QA test 6.4 compared it to a manual count, which is a model for the endpoint test. The admin lowercases (`partnera` matched `PARTNERA`). The API spec must say whether matching is exact and case-sensitive. `answers.md` says exact for the first and last filters. For `referral_code` it says "as the admin's filter does", which was case-insensitive, so the two could diverge. Settle it in the spec.
   - Unknown filter parameters are ignored, not rejected. Child 4's QA confirmed `is_active=false` and `course_id=` returned the unfiltered list. A script that misspells `referal_code` silently gets everything. This is existing behaviour, but now that filters on codes exist it is a pay-out risk worth a docs line.
10. **QA history.**
    - Children 1 and 4 each had a frontend QA report; child 4 and the attribution QA had zero bugs. Child 1's three bugs were admin and UI items (key text overflow, scope labels clipped, allauth admin not site-aware), none in API logic.
    - Child 3's QA is absent. Children 2, 3 and 5 have no `qa_report.md`.
    - The child 1 report notes API keys and screenshots must not be committed, because snapshot and console files can hold key text. Any child 6 QA should grep for that.
    - The attribution QA report records that admin object labels use the user pk. This is a reminder that the API's `user` is an integer id, not a UUID.
11. **Seed data for QA.** `qa_create_referral_attribution_scenario` exists (re-run in the attribution QA) and seeds `qa.live`, `qa.login`, `qa.selfreg` and others. It already yields touches of all three `recorded_via` values and conversions of all four kinds. Reuse it for any API QA instead of writing new seed code.
12. **Behaviours the idea flags that are already answerable.**
    - *"Project where `referral-attribution-over-time` is not installed or has no rows."* The models now exist in this repo, and the idea's resources section says the spec is in `3. done/`. Both models are in `referral_tracking`, which the API already imports, so there is no optional install. An empty list is the answer with no rows. The question is moot for FLS and can be closed in the spec.
    - *"Shape drift."* The shipped models match the idea's field list exactly. The attribution spec's last doc item (updating this idea's pointer and `window_days`) appears done.
    - *Device or browser identifiers.* `AttributionTouch` holds none, as the attribution spec states.

## 3. Open choices, with what prior art suggests

| Open item in the idea | Prior art suggests |
| --- | --- |
| Flat lists or embed touches in conversions | Flat lists with ids, as children 2 to 5. Embedding adds a join and a nested shape no earlier child used. |
| User as id only or id plus email | Id plus `user_email`, as signup attributions and every registration endpoint (children 3 to 5). Needs `select_related("user")` and a query-count test. |
| Date-range filters beyond `updated_since` | None added in children 2 to 5 (child 5: "Any filter beyond `updated_since`, `cursor` and `page_size`" out). Children 3's `day_since` exists only because `day` is a date. Keep `updated_since` alone, plus the three-to-four resource filters from `answers.md`. |
| Filter names | `user` (integer id), `kind`, `referral_code`, `first_referral_code`, `last_referral_code`. Child 3 uses `<fk>` for the id and `<fk>_<attr>` for readable values, so `user` filtering by id is consistent. The filter should be declared so the OpenAPI schema types it (integer), and an invalid value should be a 400 keyed by name. The invalid `kind` choice should also be a 400. |

## 4. Elsewhere: known pitfalls of exposing attribution and conversion data via APIs

Taken from child 3's research (`research_known_complaints.md`, in `spec_dd/3. done/2026-11-05_15:00_apis-for-lead-monitoring-3-referral-data/`) and general practice. Web search was not repeated for this run.

- **Counts do not match the dashboard.** Causes include attribution windows, models and dimensions that differ ([Coupler](https://docs.coupler.io/troubleshooting/why-api-data-is-different-from-what-users-see-in-the-ui), [Merkle](https://www.merkle.com/en/merkle-now/articles-blogs/2025/navigating-ga4-pitfalls-that-could-derail-your-analytics.html)). For this API: `window_days` is stored per conversion, so a script must not recompute credit from the current setting. Document that "first" and "last" mean first and last in play within `window_days`, and that FLS does not pick which gets credit.
- **Restated conversions and conversion lag** ([Improvado](https://improvado.io/docs/google-analytics-4-troubleshooting)). Not an issue for append-only rows, but `occurred_at` can precede `recorded_at` by a long time, and a flushed touch can arrive after a conversion it should have been in play for? No: `record_conversion` resolves touches at write time and freezes the codes, so a late-arriving touch does not change an earlier conversion. Document that late touches never re-credit past conversions.
- **Cursor pitfalls:** ordering on a non-unique timestamp without a tie-break, and offset paging with a mutable key (Stripe-style id cursors). Prevented by `(recorded_at, id)`. The remaining trap is a checkpoint on `occurred_at`, which is why the idea keeps it out of ordering and filters.
- **Over-exposure of personal data** ([Adriel](https://docs.adriel.com/troubleshooting/numbers-dont-match-source-platform.md) discusses mismatches; PII points are general practice). Here: IP, user agent and cookie ids stay out. Residual: `user_email`, `landing_path` (which can carry tokens in query strings if a caller stored them; `AttributionTouch.landing_path` is a path, but confirm it holds no query string) and `target_label` (course title or account email). `target_label` of an `account_signup` is documented as "Account signup" in the attribution spec, with the label frozen as that string. The idea says it may be "the account email". Check the shipped call site before the spec describes `target_label`, because an email-bearing label would make a list that looks free of personal data return it.
- **Self-referral and typed codes** are an attribution-fraud class (spec open question in the attribution spec). The API makes rows readable, so a payout script can detect them, but FLS does no detection. Say so in the docs, as the attribution spec's open questions already do.
- **A consent gate is overdue** (attribution spec, open questions). Exposing the data through an API makes retention and erasure obligations more visible: downstream copies of deleted users' touches and conversions are the key holder's to delete, as child 3's `security-and-data-handling.md` wording says for signup attributions.
- **Blank vs null.** Child 3 settled blank text as `""`, nulls as `null`, with tests. For conversions: `first_touch` / `last_touch` are nullable FKs (`null`), and the two code fields are `""`. A script reading "both blank" must not also expect null touches to mean something different. They agree in practice but are different types.
- **Silent partial results.** An unknown filter name is ignored (see 2.9). A very small page size multiplies requests. Throttling is per key, 429 with `Retry-After`, inherited from child 1.

## 5. Corrections the spec should make to the idea's wording

1. Replace "misses nothing" with the 5-minute checkpoint margin and de-duplicate on `id` (child 3's docs wording).
2. Check `target_label` for `account_signup` against the shipped call site (`"Account signup"` per the attribution spec, "account email" per the idea). Settle one and describe it.
3. Decide filter case sensitivity for `referral_code` (answers.md says "as the admin's filter does", and the admin filter was case-insensitive) against exact-match first and last filters.
4. Decide on a conversions index for `first_referral_code` / `last_referral_code`, or record that a per-site scan is acceptable.
5. Close the "not installed" question: nothing to install, so an empty list.
6. Scope description in `scopes.py`, the docs "Deletions" table, and the "Known data caveats" section each need a row or entry for the two new resources.
