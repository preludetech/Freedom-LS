# Spec: Recommend outcome for registration rules

Spec 3 of 5 in the Registration rules effort, built on spec 2's engine
(`spec_dd/3. done/2026-10-23_20:02_corporate-job-course-recommendations-2-registration-rules/1. spec.md`).

## Purpose

A registration rule can only register learners today. Some courses should be offered rather than
imposed. This spec adds the `recommend` outcome: a rule puts its course in each matching learner's
"Recommended courses" dashboard section by creating a `RecommendedCourse`, and removes it when the
learner stops matching. Every registration path also clears a recommendation the user no longer
needs.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| recommend rule | coined | A `RegistrationRule` with `outcome="recommend"`. A rule with `outcome="register"` is a register rule. |
| rule-made recommendation | narrowed | "Rule-made" as spec 2 uses it for registrations (`freedom_ls/registration_rules/models.py`, `signals.py`); here a `RecommendedCourse` with at least one `RuleRecommendation`. |
| staff-made recommendation | coined | A `RecommendedCourse` with no `RuleRecommendation`, made in the Django admin or by a QA command. Rules never touch one. |
| registered (for a recommendation) | narrowed | The user-wide test in `is_registered_for_course_expression` (`freedom_ls/learner_management/queries.py`): an active registration through an active `Learner` in any organisation, or an access-granting cohort registration. |

## Scope

In: the `RecommendedCourse` uniqueness constraint and `RuleRecommendation`; evaluation, preview,
deletion and triggers for recommend rules; clearing on every registration path; re-recommending a
user who stops being registered; the admin changes below.

Out (from `idea.md`): dismissal, ranking, reasons or expiry on a recommendation; recommendations
from form answers (the commented-out `form_progress` FK stays); notifications and webhook events;
educator-interface screens (spec 4); CSV import (spec 5); any change to the dashboard templates.
Also out: telling the learner that a recommendation disappeared, and any cap on how many
recommendations a rule makes (the dashboard section already paginates).

## Decisions

1. **One `RuleRecommendation` per rule per recommendation, not a single owner.** A
   `RecommendedCourse` a rule made exists while it has a `RuleRecommendation`, and each rule adds
   and removes only its own. This is the organisation scoping the idea left open: no rule reads or
   writes another rule's rows, so no hand-over across organisations is needed and the row needs no
   organisation column.
2. **Provenance is a side table in the optional rules app**, as spec 2 did for registrations.
   `course_recommendations` gains no FK to the rules app; its only schema change is the
   constraint. The rules app now requires `course_recommendations`.
3. **A rule matches a user**, not a `Learner`: user U matches rule R when U's `Learner` in R's
   organisation (at most one, `unique_learner_per_organisation`) is in the kind's
   `matching_learners`. `RecommendedCourse` is keyed on `User`.
4. **A registered user counts as not matching** a recommend rule. This also cleans up a rule's
   own rows for users registered through a path that bypasses signals.
5. **The dashboard shows the union** of a user's recommendations across organisations, once per
   course. It gains no organisation filter.
6. **Removal is a hard delete** of the `RecommendedCourse` when its last `RuleRecommendation`
   goes. A recommendation holds no learner data, so spec 2's started-gate does not apply.
7. **Clearing lives in `course_recommendations`**, as receivers on `learner_management` models.
   This adds the runtime edge `course_recommendations -> learner_management` (no cycle) and keeps
   core apps ignorant of the rules app.
8. **A rule's `outcome` is set on the add page and read-only afterwards**, like `organisation` and
   `course` (spec 2 decision 9). Switching would silently swap registrations for recommendations.
9. **Staff may delete a rule-made recommendation**; it comes back on the next run while the rule
   still matches. Dismissal is out of scope.

## Requirements

### `RecommendedCourse` (`freedom_ls/course_recommendations/`)

- `models.py`: add `UniqueConstraint(fields=["site", "user", "course"],
  name="unique_recommended_course")`. Update the stale module and class docstrings; keep the
  commented-out `form_progress` FK.
- Migrations: `0002` is a `RunPython` that, per (`site_id`, `user_id`, `course_id`), keeps the
  oldest row (`created_at`, then `id`) and deletes the rest, through `apps.get_model`, with
  `reverse_code=migrations.RunPython.noop`. `0003` adds the constraint and depends on `0002`.
- `admin.py`: `RecommendedCourseAdmin` gets a form using `ConstraintValidationFormMixin`
  (`freedom_ls/site_aware_models/forms.py`), so a duplicate add is a form error, not a 500
  (`site` is excluded from the form).
- `freedom_ls/learner_management/queries.py`: add a set-based sibling of
  `is_registered_for_course_expression`, `registered_course_pairs(site_id: int, user_ids:
  Iterable[int]) -> set[tuple[int, UUID]]` of (`user_id`, `course_id`) pairs (`User.pk` is an
  integer). It reads through `_base_manager` with an explicit `site_id`, so its answer does not
  depend on whether a request is active. Extract the conditions both functions share into
  `LEARNER_REGISTRATION_GRANTS_ACCESS`, `COHORT_REGISTRATION_GRANTS_ACCESS` and
  `held_by_active_member` (the member lookup and the member-active condition in one `Q`, so they
  land on one membership join), so the two cannot drift. The rules app reuses the sibling for
  decision 4.
- `queries.py`: add `clear_registered_recommendations(site_id: int, user_ids: Iterable[int]) ->
  int`. It locks, with `select_for_update()` in pk order, every recommendation of those users for
  a course they are registered for, staff-made ones included, then deletes them and returns the
  count.
- New `signals.py`, connected from a `ready()` on `CourseRecommendationsConfig`. Each receiver
  skips `raw=True` and calls `clear_registered_recommendations` for the affected users:

  | Event | Users |
  | --- | --- |
  | `LearnerCourseRegistration` `post_save`, `is_active=True` | the learner's user |
  | `CohortCourseRegistration` `post_save`, `is_active=True` | users of the cohort's members |
  | `CohortMembership` `post_save`, created | the member's user |
  | `Cohort` `post_save`, `is_active` changed to `True` | users of the cohort's members |
  | `Learner` `post_save`, `is_active` changed to `True` | the learner's user |

  The `Learner` and `Cohort` receivers skip a save whose `update_fields` excludes `is_active`, as
  `evaluate_learner_on_save` does. To tell a change to `is_active` from a save that leaves it
  alone, `Learner` and `Cohort` gain the `loaded_is_active` snapshot `LearnerCourseRegistration`
  already keeps, through one shared `LoadedIsActiveMixin` in
  `freedom_ls/learner_management/models.py` (no field, no migration). Paths that bypass signals
  (`bulk_create`, `QuerySet.update()`) clear nothing.
- `freedom_ls/learner_interface/views.py`: delete the `RecommendedCourse.objects.filter(...)
  .delete()` after the self-registration `update_or_create` (line 913), and its import if unused.

### Models (`freedom_ls/registration_rules/models.py`)

- `RegistrationRule.Outcome` gains `RECOMMEND = "recommend"`. Default stays `register`.
- `RuleRecommendation(SiteAwareModel)`:

  | Field | Type |
  | --- | --- |
  | `recommendation` | FK `freedom_ls_course_recommendations.RecommendedCourse`, CASCADE, `related_name="rule_recommendations"` |
  | `rule` | FK `RegistrationRule`, CASCADE, `related_name="rule_recommendations"` |

  `UniqueConstraint(fields=["site", "recommendation", "rule"], name="unique_rule_recommendation")`.
  Unlike `RuleRegistration` it has no `rule_name`: a recommendation goes when its rule goes, so
  nothing is left to label.
- One migration, `0004`, for the choice change and the new model, depending on
  `freedom_ls_course_recommendations` `0003`.
- `apps.py`: `import_models` also refuses a missing `freedom_ls.course_recommendations` with
  `ImproperlyConfigured`, as it refuses a missing `hr_attributes`. The models, evaluation,
  signals and admin import `RecommendedCourse` at import time, so startup fails before a system
  check could run; no check is added.

### Evaluation (`freedom_ls/registration_rules/evaluation.py`)

- Every existing path that reads rules filters by outcome: `classify_rule_changes`,
  `apply_rule_changes` and `_hand_overs` see only register rules. A recommend rule never creates a
  `LearnerCourseRegistration` or a `RuleRegistration`.
- Add a read, `classify_recommendation_changes(rule, state, user_ids=None) ->
  RecommendationChanges`, and a write, `apply_recommendation_changes(rule, changes) ->
  EvaluationResult`. The preview runs the read alone. For rule R on course C:
  - **matched**: users of `matching_learners(state)`, minus registered users.
  - `recommend`: matched users with no `RecommendedCourse` for C. The write creates the row and
    R's `RuleRecommendation` in one savepoint. An `IntegrityError` on `unique_recommended_course`
    goes to the `add_rule_recommendation` path.
  - `add_rule_recommendation`: matched users whose recommendation for C is rule-made and has none
    from R.
  - Matched users with a staff-made recommendation: left alone.
  - `remove`: users R has a `RuleRecommendation` for who are not matched, where R's is the only
    one. The write deletes the `RecommendedCourse`.
  - `drop_rule_recommendation`: the same, where others remain, as a `SharedRecommendation` of the
    user pk and the other rules' names. The write deletes R's `RuleRecommendation` only.
  - Every write to an existing row first locks the `RecommendedCourse` with `select_for_update()`
    and re-reads it inside the batch transaction. A row that is gone is skipped; a row that is now
    staff-made gets no `RuleRecommendation`; a row with no `RuleRecommendation` left after a drop
    is deleted. With the lock in `clear_registered_recommendations`, no row is left deleted under
    a new `RuleRecommendation`, which would fail the deferred FK check at commit.
- `RecommendationChanges` is a frozen dataclass of those four groups, by user pk.
  `EvaluationResult` gains `recommended` and `recommendations_removed` (user pks), merged by
  `merged_with`.
- `evaluate_rule` dispatches on `rule.outcome`. For a recommend rule its scope is every user R
  matches plus every user R has a `RuleRecommendation` for, batched by
  `REGISTRATION_RULE_BATCH_SIZE` in user-pk order, with the register path's per-batch
  transaction, rule lock, switch re-read and `last_evaluated_at` handling. A disabled rule matches
  nobody, so its run removes all its `RuleRecommendation`s.
- `evaluate_learner(learner_id, site_id)` also runs every enabled recommend rule of the learner's
  organisation, and every rule with a `RuleRecommendation` on a recommendation of the learner's
  user, scoped to that user. It works for an inactive `Learner`. It keeps the `Learner` lock; the
  row locks cover one user evaluated through two `Learner` rows at once.
- `evaluate_organisation` needs no change.
- The organisation switch gates recommend rules through the existing `rules_enabled_for` early
  returns. Off means nothing is evaluated and existing recommendations stay.

### Triggers (`freedom_ls/registration_rules/signals.py`)

- Spec 2's triggers carry the new outcome. `_learner_needs_evaluation` is also true when any rule
  has a `RuleRecommendation` on a recommendation of the learner's user. A deactivated `Learner` is
  therefore evaluated itself, through the existing `Learner` `post_save` trigger.
- New: when a user may have stopped being registered for a course, re-evaluate them against the
  enabled recommend rules on that course whose organisation's switch is on. A single-learner event
  enqueues `evaluate_learner` for each of the user's active `Learner`s in those organisations. A
  cohort-wide event enqueues `evaluate_rule` once per matching rule instead of one task per member.

  | Event | Users and courses | Enqueues |
  | --- | --- | --- |
  | `LearnerCourseRegistration` `post_save` with `is_active=False`, or deleted | the learner's user, that course | `evaluate_learner` |
  | `CohortMembership` deleted | the member's user, the cohort's registered courses | `evaluate_learner` |
  | `Learner` `post_save` with `is_active` changed to `False`, or deleted | the user's other `Learner`s, courses registered through this one | `evaluate_learner` |
  | `CohortCourseRegistration` `post_save` with `is_active=False`, or deleted | the cohort's members, that course | `evaluate_rule` |
  | `Cohort` `post_save` with `is_active` changed to `False` | the cohort's members, the cohort's registered courses | `evaluate_rule` |

  For a delete, the receiver resolves users and courses in `pre_delete` and enqueues on commit,
  since a cascade may already have removed the rows by `post_delete`. A deleted `Learner` also
  enqueues `evaluate_rule` for each rule with a `RuleRecommendation` on the user's
  recommendations, so a user left with no `Learner` is still cleaned up. Each receiver skips
  `raw=True` and enqueues through `_enqueue_once` after commit. A register rule's own retraction
  also fires the first row. That is wanted: a learner a register rule lets go of can then be
  recommended the course.

### Deletion

- `_delete_refusal` (`admin.py`) also refuses a disabled rule whose last change is unapplied while
  it has any `RuleRecommendation`: "Rule still removing its recommendations: {name}".
- A second `pre_delete` receiver beside `snapshot_rule_name_before_delete`,
  `delete_solely_held_recommendations_before_delete`, deletes every `RecommendedCourse` whose only
  `RuleRecommendation` is the rule's, so a CASCADE never leaves a rule-made row looking
  staff-made. `RegistrationRuleAdmin.get_deleted_objects` names those recommendations on the
  delete page.
- `danger_content_delete` needs no change: the new rows cascade from `RecommendedCourse` and
  `RegistrationRule`.

### Admin (`freedom_ls/registration_rules/admin.py`)

- `RegistrationRuleAdmin`: `outcome` on the add page as radio buttons, with help text in learner
  terms ("Register: matching learners are registered. Recommend: the course appears in their
  Recommended courses and they choose whether to register."), read-only on the change page. Add
  `outcome` to `list_display` and `list_filter`.
- `_change_form_warnings`: for a recommend rule on an unpublished course, "This course is not
  published. The rule still recommends it, but learners will not see the recommendation until it
  is."
- Preview (`_render_preview`, `admin/registration_rules/preview.html`): a recommend rule runs
  `classify_recommendation_changes` against the same submitted `RuleState` and shows "Will be
  recommended" (`recommend`), "Recommendation will be removed" (`remove`) and "Stops matching but
  stays recommended" (`drop_rule_recommendation`, reason "Also recommended by {rule names}"), each
  a full list of user name and email with counts in the headings, behind the same `view_learner`
  permission gate and switch-off notice. A recommend rule's preview never shows the register
  headings or "Started the course". `add_rule_recommendation` is not listed, since nothing changes
  on that learner's dashboard.
- `RecommendedCourseAdmin`, wired at import time from the rules app as `registration_rule` is
  wired onto `LearnerCourseRegistrationAdmin`:
  - a read-only "Registration rules" field listing the rules as links, blank for a staff-made
    recommendation;
  - a "Made by" `list_display` column (the rule names, or "Staff") and a `list_filter` with
    "Registration rule" and "Staff";
  - rule names and links show only to a user with `view_registrationrule`; anyone else sees a
    rule-made row as "Registration rule" with no name, since a rule may belong to an organisation
    they may not see;
  - a wrapped `get_deleted_objects` that, on the confirmation request only (the single delete's
    GET, and the bulk action's first POST, the one without `post=yes`), adds a `messages.warning`
    when any selected row is rule-made: it comes back on the next evaluation while the rule still
    matches, so disable or change the rule instead. This covers single and bulk delete.

## Testing

Recommend-outcome tests go in `freedom_ls/registration_rules/tests/`, with a
`RuleRecommendationFactory` in `freedom_ls/registration_rules/factories.py`. Clearing tests go in
`freedom_ls/course_recommendations/tests/`, which must not import the rules app.

To prove:

- Migration: duplicates for one (site, user, course) collapse to the oldest; distinct rows and
  other sites are untouched; the constraint then holds.
- Admin form: adding a duplicate recommendation shows a form error.
- Recommend: a matching user gets one `RecommendedCourse` and one `RuleRecommendation`; a second
  run creates nothing; a recommend rule creates no registration and no `RuleRegistration`.
- No takeover: a matching user's staff-made recommendation gets no `RuleRecommendation` and
  survives the rule unmatching or being disabled.
- Registered users skipped: via an individual registration, a cohort registration, and a
  registration through the user's `Learner` in another organisation; a rule-made recommendation
  for a user registered through `bulk_create` is removed on the rule's next run.
- `registered_course_pairs` gives the same answer inside and outside a request.
- Unmatch and disable: the recommendation is deleted; with a second enabled rule (same or other
  organisation) also on it, only the first rule's `RuleRecommendation` goes; disabling both
  removes it.
- Two organisations: user U in organisations A and B, a recommend rule in each on one course; U
  sees one recommendation with two `RuleRecommendation`s; A's rule unmatching leaves it;
  `evaluate_learner` for both of U's `Learner`s back to back gives the same rows.
- Concurrency: a create racing an existing row joins or skips; a drop racing an add leaves a row
  with a `RuleRecommendation` or no row; `clear_registered_recommendations` racing
  `add_rule_recommendation` commits both transactions without an FK error.
- Switch off: no trigger changes anything and existing recommendations stay; turning it on
  catches up.
- Clearing, one test per row of the clearing table, staff-made and rule-made; an inactive
  registration, `Learner` or cohort clears nothing; a `Learner` save that leaves `is_active` alone
  runs no query; self-registration still clears.
- Re-recommend, one test per row of the trigger table, including the cascade from deleting a
  `Learner` and a `Cohort`; a user still registered another way is not recommended; a user whose
  only `Learner` is deactivated loses the recommendation.
- Staff delete: the rule's next run re-creates a deleted rule-made recommendation for a
  still-matching user; a deleted staff-made one stays gone.
- Register rules unaffected: with a register and a recommend rule on one course, `_hand_overs`
  never offers the recommend rule; spec 2's tests pass unchanged.
- Deletion: refused while a disabled recommend rule's run is pending and it holds
  `RuleRecommendation`s; deleting a rule removes the recommendations only it held, and the delete
  page names them.
- Preview: for edit, enable and disable, the three lists match what the confirmed save then does;
  "Also recommended by" names the other rule; a recommend rule's page shows no register headings.
- Admin: `outcome` is on the add page and read-only on the change page; the "Made by" column,
  filter and "Registration rules" field render; the delete page warns for a rule-made row only.
- App config: loading the models without `course_recommendations` raises `ImproperlyConfigured`
  naming it.
- Tasks run with no request against two sites and touch only the given site.
- With `freedom_ls.registration_rules` removed from `INSTALLED_APPS`, the dashboard, clearing and
  `RecommendedCourseAdmin` tests pass.
- One Playwright flow (`fls-dev:playwright-tests`): a recommend rule, once enabled and confirmed,
  puts the course in the learner's "Recommended courses"; registering moves it to their current
  courses.
