# Research: codebase (what spec 3, the recommend outcome, touches, reuses or conflicts with)

All paths are under the project root. Line numbers are from the working tree on 2026-10-24 (spec 2 and spec 1 have both landed).

## 1. Summary

- Spec 2's engine is built and merged: `RegistrationRule.outcome` already exists with one choice. Spec 3 plugs in beside it, but the engine does not read `outcome` anywhere today, so adding a `recommend` choice without guarding every query would make a `recommend` rule register learners. This is the biggest hazard (section 4).
- `RecommendedCourse` is still exactly as the idea describes: user, course, created_at; no constraint; one migration. Only the admin, the factory, QA commands and the self-registration view touch it.
- The "clear on every registration path" requirement has a natural chokepoint already: `post_save` receivers in `freedom_ls/learner_progress/signals.py` for `LearnerCourseRegistration`, `CohortCourseRegistration` and `CohortMembership`. Cohort registration needs the membership path as well, not just the two registration models (section 6).
- Organisation scoping: a user can hold one `Learner` per organisation, and every "is registered" test in the dashboard is user-wide across organisations. Facts in section 9.

### Evaluation (`evaluation.py`) and the outcome gap
- `classify_rule_changes(rule, state, learner_ids)` lines 90-150 is the read; `apply_rule_changes(rule, changes)` lines 191-269 the write; `evaluate_rule` 284, `evaluate_learner` 332, `evaluate_organisation` 373. `RuleChanges` fields (line 59): `register`, `reactivate`, `retract`, `hand_over`, `kept_started`. `EvaluationResult` (line 70): `registered`, `reactivated`, `retracted`. `rules_enabled_for(organisation_id)` line 83 reads `OrganisationHRSettings._base_manager` (no row = off).
- **No code reads `rule.outcome`.** `grep -i outcome|recommend` in `registration_rules/` outside migrations matches only `models.py` lines 31, 50, 51. So today any rule is a register rule. Places that would wrongly treat a `recommend` rule as a register rule if the choice is added without change:
  - `evaluate_rule` line 286 onward, `evaluate_learner` lines 349-357 (selects rules by organisation/enabled or by owning a `RuleRegistration`), `evaluate_organisation` line 376 all run `classify_rule_changes` + `apply_rule_changes`, which creates `LearnerCourseRegistration`s.
  - `_hand_overs` lines 153-188 selects "other enabled rules on the course" with no outcome filter, so a recommend rule would be offered as the rule that takes over a registration it never made. It must filter to `outcome=REGISTER` (and the recommendation side needs its own mirror: other enabled `recommend` rules).
  - The preview (`admin.py` `_render_preview` lines 303-380) calls `classify_rule_changes` and labels lists "Will be registered / retracted / stays registered".
  - `signals.py` `_learner_needs_evaluation` lines 89-105 only tests "organisation has an enabled-switch rule" or "a `RuleRegistration` exists for the learner", so a learner who owns only recommendations (moved organisation) would not be re-evaluated unless the check also looks at the recommendation provenance.
  - `admin.py` `_delete_refusal` lines 445-464 only looks at `RuleRegistration` rows; a recommend rule with live recommendations would be deletable once disabled even if its retract run has not happened.
  - `admin.py` `_change_form_warnings` lines 194-229: the unpublished-course warning text says "registers learners".
- Reusable as is: `matching_learners(state)` in `kinds.py` lines 107-137 (returns active `Learner` rows of the rule's organisation, explicit site, `_base_manager`); the `RuleState` / `AttributeConditions` / `from_rule` values (lines 18-58); the rule-kind seam (`loader.get_rule_kind`, `REGISTRATION_RULE_KINDS`). The kind seam is outcome-agnostic: spec 3 needs no change to `kinds.py`. `started_course_exists` already lives in `freedom_ls/learner_progress/queries.py` (imported at `evaluation.py` line 28) but is not needed for recommendations (no "started" test on a recommendation: the idea says unmatching removes it, registered learners are skipped).
- Registration skip condition: "a learner already registered" is, for the dashboard, any of: an active `LearnerCourseRegistration` for an active `Learner` of the same user in any organisation, or an active `CohortCourseRegistration` via an active membership of an active `Learner` (see `learner_management/utils.py` `is_registered_for_course` lines 24-59 and the queryset mirror `learner_management/queries.py` `is_registered_for_course_expression` lines 91-128, `access_granting_cohort_registrations` line 76). `classify_rule_changes` line 119 uses a narrower test for registering (any `LearnerCourseRegistration` row for the learner, active or not); a recommendation skip needs the broader, user-wide, cohort-inclusive test to match what the learner sees.
- Locking: `evaluate_rule` batches by `REGISTRATION_RULE_BATCH_SIZE` (config.py), each batch a transaction with `select_for_update(no_key=True)` on the rule row; `evaluate_learner` locks the `Learner` row. A recommendation write keyed on (site, user, course) now spans several `Learner` rows (one per organisation), so two `evaluate_learner` runs for the same user's different Learner rows can race on the same recommendation; a unique constraint plus `IntegrityError` savepoint (the line 201-219 pattern) covers the create race.
- Disable and deletion: a disabled rule retracts via `evaluate_rule` (matching is empty when `is_enabled` is False, `kinds.py` line 110). `snapshot_rule_name_before_delete` (`signals.py` lines 122-131) only updates `RuleRegistration`; recommendation provenance needs the same snapshot if it keeps `rule` SET_NULL + `rule_name`.

## 8. Uniqueness: can existing data violate it, and what a migration needs

- Proposed key: a `UniqueConstraint` on (`site`, `user`, `course`), named in the style of `unique_learner_course_registration` (`site` first, as every constraint in the project). Nothing today prevents duplicates: no constraint, the admin form has no uniqueness check (site excluded), the factory has none, and tests like `test_course_listing.py`/`test_dashboard.py` build multiple rows per user for different courses only (not verified for same-course duplicates; check with a grep of `create_batch` on `RecommendedCourseFactory` before landing). Production data could hold duplicates created by admin double-add or by a form flow once existed ("Created when a parent fills out a form" suggests earlier code paths).
- The migration must therefore remove duplicates first, in the same migration before `AddConstraint`, or in a prior `RunPython` migration: for each (`site_id`, `user_id`, `course_id`) keep one row and delete the others. Which to keep: with no provenance yet, pre-existing rows are all admin-made, so keep the oldest (`created_at` ascending, then `id`) so the learner's ordering position on the dashboard (newest first) is not bumped; deleting the extra rows loses nothing (no other field). Use the historical model through `apps.get_model`, `_base_manager`-equivalent (historical models have plain managers).
- Reverse migration: `RunPython.noop` for the dedup; the constraint is removed by the reversal of `AddConstraint`.
- If provenance lives in a rules-app side table (as spec 2 did), the `course_recommendations` migration adds only the constraint; the rules app gets a migration for the new table depending on `freedom_ls_course_recommendations`'s migration. If instead the `rule` FK is a column on `RecommendedCourse`, the core app's migration depends on the optional rules app (spec 2 decision 2 rejected that for registrations; same reasoning applies, and `course_recommendations` would also have to migrate in step with a nullable, `SET_NULL` FK).
- `makemigrations --check` with the rules app absent must report no changes (spec 2 success criterion); that holds only for the side-table design.
- Postgres 17: no concurrent-index concern at this table's size; a plain `AddConstraint` is fine.
- Writers must tolerate the constraint: admin form (add `ConstraintValidationFormMixin`), `qa_helpers` commands (`qa_create_rich_dashboard_learner` guards with `exists()` already), factory (`RecommendedCourseFactory` creating the same user+course twice in tests would now raise), and the rule engine (create via `get_or_create`-style with an `IntegrityError` savepoint, as `apply_rule_changes` does at lines 201-219).

## 9. Multi-tenancy, `Learner`/`User`, and organisation scoping facts

- `SiteAwareModel` (`site_aware_models/models.py`): `site` FK (PROTECT) filled from the thread-local request site on save; `.objects` is site-filtered ambiently; `_base_manager` is unfiltered, which is why the engine passes `site_id` explicitly everywhere. A task has no request, so recommendation writes from the engine must use `RecommendedCourse._base_manager` with explicit `site_id` and `user_id` (the default `.objects` raises or returns nothing outside a request; same rule as `RuleRegistration._base_manager.create(site_id=...)`). `RecommendedCourse.objects.filter(user=..., course=...)` in the view relies on the request site.
- `Learner` (`learner_management/models.py` lines 55-86): `user`, `organisation`, `is_active`; constraint `unique_learner_per_organisation` on (`site`, `user`, `organisation`). Docstring: "A user may hold a Learner row in more than one organisation." So a user can be matched by rules of two organisations on the same course.
- `LearnerCourseRegistration` is per `Learner` (hence per organisation), unique (`site`, `learner`, `course`) (line 167-172). A user with Learner rows in two organisations can legitimately hold two registrations for the same course. `CourseProgress` is per `Learner` and registration.
- `RecommendedCourse` is per `User` and `Site`, with no organisation. The dashboard has no organisation concept; registration status is user-wide (section 7). `ensure_learner` / self-registration lands on the Site's default Organisation (`views.py` lines 885-895).
- Facts bearing on the open question:
  1. With uniqueness on (`site`, `user`, `course`), two organisations' rules matching one user can want the same row; there is one slot. Which rule owns it is the same ownership problem spec 2 solved for registrations (decision 10, hand-over `_hand_overs` lines 153-188, rule order by `name`, `pk`; hand-over considers rules of every organisation because a learner who moved is matched by the new organisation's rules).
  2. If provenance is only `rule` (nullable FK + `rule_name`), the organisation is derivable as `rule.organisation` while the rule exists; after rule deletion `rule` is NULL and the organisation is lost (the snapshot would have to hold `organisation_id` too, or deletion must be refused until the retract has run, like `_delete_refusal` does for registrations, which makes the orphan case "retraction never happened" rare but possible after `SET_NULL`). Rows with no provenance are admin-made and belong to no organisation.
  3. A rule retracts only rows whose provenance names it (`rule=R`), so provenance alone already prevents one organisation's rule retracting another organisation's recommendation or an admin row. The organisation column would only be needed to (a) answer "this organisation's recommendations" without joining to rules, (b) survive rule deletion, or (c) scope a per-organisation view; nothing in the idea requires (a)-(c) except spec 4's screens.
  4. "Learner stops matching" is per `Learner`/organisation, but a user is recommended once. A user who stops matching in organisation A while still matching organisation B's rule on the same course should keep the recommendation (same as "another enabled rule matching the same learner and course blocks retraction", where "learner" must widen to user across organisations).
  5. Which `Learner` counts as "registered" for the skip: any active registration for any of the user's Learners (what the dashboard shows), not only the rule's organisation's Learner. A user registered through organisation B's Learner would still be recommended the course by organisation A's rule if the skip looked only at A's Learner, and the dashboard would show it twice.
  6. `evaluate_learner` is keyed on a `Learner` (one organisation). When a user's other Learner registers or unregisters, the recommendation outcome for organisation A's Learner changes though nothing about A's Learner changed; no signal on the registration path enqueues an evaluation (section 4, triggers). Unregistering (a registration going inactive) is a case the idea does not address: after deactivation, a still-matching learner could be recommended again on the next evaluation (reconcile-style, spec 2 decision 8) but no trigger fires; flag it.
  7. A user in two organisations with a rule in each, one `register` and one `recommend` on the same course: the register rule makes the recommendation unneeded; "no recommendation for a registered learner" covers it once registered.
- Site scope also matters across sites: the unique key includes `site`, so users on two sites are independent.

## 10. Conflicts with the idea's settled points

- **"Provenance... using the approach spec 2 chose for registrations"**: no conflict, but note the spec-2 approach is a side table owned by an optional app, so `RecommendedCourse` itself gains no field. The idea text ("`RecommendedCourse` records which rule made a row") reads as a column; the migration and `makemigrations --check` criterion (section 8) argue for the side table, matching spec 2.
- **"`RecommendedCourse` stays standalone and additive"**: a `UniqueConstraint` (and a dedup data migration that deletes rows) is not additive in the strict sense; and a clearing receiver in or near `course_recommendations` makes it depend on `learner_management`. The module docstring (lines 1-8) will need updating whichever way. Flag for the spec.
- **"Every registration path clears"**: the idea's list omits cohort membership (section 6 item 7) and Learner reactivation; also `bulk_create`/`update()` paths bypass signals.
- **"The preview... in the same list spec 2 builds"**: the existing preview page is register-specific (hard-coded headings and reasons, `_render_preview`), and `classify_rule_changes` is registration-specific. It reuses `RuleChanges`' shape but the semantics differ (no "reactivate", no "kept_started"). A second classifier for recommendations, or an outcome dispatch inside the kind-agnostic engine, is needed; the preview template and `RuleChanges` field names are named in spec 2's tests, so check `tests/test_admin.py` and `playwright/test_rule_preview_flow.py` before renaming anything.
- **"No notification, no webhook"**: no conflict. `_ensure_and_announce` (`learner_progress/signals.py` 130-179) fires `course.registered`; nothing there is touched by a recommendation. The register path's `course.registered` notification for rule-made registrations (spec 2) is unaffected.
- **Spec 2 "Rules never create a second registration"/outcome**: spec 2's `Outcome` TextChoices has only `REGISTER`; adding `RECOMMEND = "recommend"` changes `choices` which produces an `AlterField` migration in `registration_rules` (choices are part of migration state). That is the rules app's own migration, fine.
- **Same course, same organisation, a register rule and a recommend rule**: allowed by the model today (no uniqueness on rules). Their interplay (the register rule's registration clears the recommendation; the recommend rule skips registered learners) works out only if evaluation order is deterministic; since spec 2 reconciles state each run it converges, but a recommend run before the register run re-creates nothing (registered learner skipped) and the clear removes any leftover. Mention in the spec.
