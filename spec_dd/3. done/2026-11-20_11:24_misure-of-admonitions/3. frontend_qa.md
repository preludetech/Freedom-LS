# Frontend QA: theme-fit callouts for app pages

## Setup

1. Seed data if the database is empty: `yes | uv run manage.py create_demo_data`, then
   `uv run python manage.py content_save ./demo_content DemoDev`.
2. Build the CSS: `npm run tailwind_build`.
3. Start the server: `uv run python manage.py runserver $PORT`. Base URL `http://127.0.0.1:$PORT`.
4. Log in at `/accounts/login/` with the QA login from `.claude/sdd/config.md` (`## QA Login`). That
   user is staff on the DemoDev organisation and can reach `/educator/organisations/demodev/…`.
5. Some states need data the demo lacks (a paused registration, an ended access, a blocked delete, an
   only-admin staff member). Create it with the QA data helper, as each test says.

Check every test at desktop (1280 px), tablet (768 px) and phone (375 px) widths. Keep the console
open: no JavaScript errors at any point.

### What every callout must look like

Use this checklist on each callout the tests below reach:

- [ ] A tinted box with a thin full border in the tone's colour and rounded corners (`rounded-md`).
- [ ] No thick left stripe, and no large heading-sized title.
- [ ] A tone icon at the left (info, success, warning or error), in the tone's colour (a dark green or
      dark amber shade for success and warning, clearly visible on the tint), top-aligned with the first
      line of text.
- [ ] A title, when there is one, is bold and the same size as the body text.
- [ ] The text is the same size as the text around the callout (body size on a page, the dialog's body
      size in a dialog). It is dark on-surface text, not tone-coloured text, and easy to read on the tint.
- [ ] The box is as wide as its container; it does not overflow at 375 px, and nothing scrolls sideways.
- [ ] There is clear space between the border and the content, and between the title, the text and any
      button; nothing inside the box looks packed.
- [ ] There is visible space between the callout and its neighbours above and below; it neither touches
      them nor leaves a large gap.

## Test 1: login page "New here?" callout

1. Log out. At `/accounts/login/`, sign in with an email that has no account and any password.
2. Expect: an `error` callout holding the error sentence, then an `info` callout titled "New here?" with its sentence and a
   "Create an account" button inside it. Apply the checklist. The button sits inside the box with space
   above it, spans the full width of the callout's text column, and its label is centred. In the accessibility tree
   the error callout is the one `alert` region (the toast region aside); the "New here?" callout is not
   inside it.
3. Log back in.

## Test 2: learner form errors

1. As a learner registered on a course with a quiz or form (for example the "Functionality demo: show end
   with quiz" course), open a form page and submit it with a required question unanswered.
2. Expect: an `error` callout titled "Missing answers" above the form. Apply the checklist.
3. In the accessibility tree there is exactly one `alert` region holding "Missing answers" (the page's
   toast region aside); the callout itself is that region, not a wrapper around it.
4. Submit an answer the form rejects (for example text in a number question). Expect an `error` callout
   titled "Invalid answers", announced the same way.
5. Submit valid answers. The callouts go away.

## Test 3: course application pages

Use the "Functionality demo: application-gated course" (`/courses/functionality-demo-application-gated-course/detail/`)
and start an application.

1. On "Your details", submit details the form refuses at form level (for example a details combination
   the view rejects; ask the data helper if none is reachable). Expect an `error` callout titled
   "We couldn't use those details", with one `alert` region. Apply the checklist.
2. On "Check your answers", try to submit with a required answer missing. Expect an `error` callout with
   the missing-answers sentence and no title.
3. Submit a complete application. Expect a `success` callout ("Your application has been submitted…")
   followed by a "Your application" button, with space between them.
4. Re-open a form page of the submitted application. Expect an `info` callout ("This application has been
   submitted and can no longer be changed.").

## Test 4: course detail paused and access-ended callouts

1. Ask the data helper to pause the QA learner's registration on a course, with a planned resume date.
   Open that course's detail page. Expect an `info` callout ("Your educator paused this course. It resumes
   on …"). Apply the checklist; check the space between it and the content above and below.
2. Ask the data helper to end the learner's access on another course instead. Expect a `warning`
   callout ("Your access to this course ended on …"). Apply the checklist.
3. Open a course that is neither paused nor ended. No callout shows.
4. Open a topic that has closed in the course player (if the demo has none, skip). The "Closed on …"
   message is plain text, not a boxed callout.

## Test 5: educator course content outline

1. Go to `/educator/organisations/demodev/courses` and open a course whose table of contents is marked
   as still in development (ask the data helper to set one if none is).
2. Expect, above the outline, an `info` callout: "Learners can't see this outline yet. The course is
   marked as still in development." Apply the checklist. It sits inside the panel's padding with space
   below it and does not touch the panel header.
3. Open a course that is not in development. No callout shows.

## Test 6: educator dialogs

For each dialog, apply the checklist and check the callout's text is the same size as the dialog's other
body text.

1. Staff: open the staff list, open "Change role" on a staff member and submit an invalid choice (ask the
   data helper if the form cannot be made to fail). Expect an `error` callout, focused, inside the dialog.
2. Deactivate the only organisation admin's role or staff membership (ask the data helper for an
   organisation with one admin). Expect a `warning` callout ("… is the only organisation admin…").
3. Delete a record that has dependents. Expect an `error` callout titled "This will also delete:" holding a
   bulleted list; each bullet sits level with the start of the title text, not indented past it.
4. Try to delete a record whose delete is blocked. Expect an `error` callout holding the reason, and focus
   lands on it.
5. Move a learner (or cohort registration) where the move is refused. Expect an `error` callout with the
   refusal, focused.
6. Select several rows and start a bulk action that warns. Expect a `warning` callout in the confirmation.
7. Open an "add" form dialog that offers "Save and add another". Save one. Expect a `success` callout above
   the fields. Then submit the form with a form-level error: the error shows in the error summary and again
   above the end of the fields as an `error` callout (accepted duplicate). Field errors still show beside
   their fields as plain text, not as callouts.
8. Open a panel with an inline record form and submit a form-level error. Expect an `error` callout,
   focused.

## Test 7: educator dashboard and imports

1. `/educator/organisations/demodev/dashboard`: if any region shows an excluded-data message, it is a
   `warning` callout. A lazy region too large to load shows a `warning` callout.
2. Start a learner import and upload a file that cannot be read (for example an empty or non-CSV file).
   Expect an `error` callout titled "The file could not be uploaded." with a bulleted list, focused on load.
3. Upload a CSV with some bad rows. Expect a `warning` callout titled "N rows with errors will not be
   added." above the row errors.
4. Open the staff panel for an organisation with one staff member (ask the data helper). Expect an `info`
   callout ("You're the only staff member here…").

## Test 8: panel framework reference page

1. Go to `/panel-framework/components/`.
2. Expect a "Callout" section with four callouts in order: info, warning, error, success, each with its own
   icon. There is no "Notice" section and no second, differently styled callout example.
3. The callouts here look identical to the ones in Tests 5–7 (same border, tint, icon and text size).
4. The rest of the page still renders (no broken sections, no raw `<c-` tags shown as text).

## Test 9: the first_class theme

1. Stop the server. Rebuild with `FLS_THEME=first_class npm run tailwind_build` and restart with
   `FLS_THEME=first_class uv run python manage.py runserver $PORT`.
2. Revisit Test 1, Test 3 step 3, Test 6 step 2 and Test 8.
3. Expect the first_class tints (light status backgrounds, darker tone text) on every tone, warning
   included. Every tone is readable; no callout falls back to an unstyled box.
4. Stop the server, rebuild with the default theme (`npm run tailwind_build`) and restart.

## Test 10: things that must not change

1. Open the "Content widgets demo reference" course in the learner view (or the educator content preview)
   and find its admonitions. They keep the course-content look: a left stripe and a larger title.
2. Trigger a toast (save a profile change at `/accounts/profile/`). The toast still appears fixed on screen
   and can be dismissed; it is not a callout.
3. Course content markdown that contains `<c-callout>` does not render a callout (the tag is stripped).
