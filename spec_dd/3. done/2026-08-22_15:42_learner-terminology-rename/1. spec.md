# Specification: Standardise on "learner" — rename `student` → `learner`

## 1. Summary

FLS uses "student" and "learner" for the same person, inconsistently, across models, app labels,
permissions, URLs, templates, docs and UI copy. This spec settles it: **the word is "learner"**.

**This is a pure rename. No behaviour changes, no new features.** Every observable behaviour of the
system before and after this change is identical, with one deliberate, inert exception (§10.2).

What moves:

- Three Django app packages, each carrying three coupled names — package path, `AppConfig.label`, and
  `AppConfig` class name.
- One live model (`StudentDeadline` → `LearnerDeadline`) with its field, constraint, factory, admin
  and test module.
- One URL namespace (`student_interface` → `learner_interface`) and every reverse/`{% url %}` site.
- Template and static directories, which shadow by path and therefore break downstream themes.
- Permission-string prefixes (derived from app labels), one role key, and four dead permission
  codenames that are deleted rather than renamed.
- The downstream-importable conformance suite, the app-settings seam, the pluggable course-access
  backend, docs, QA helpers, plugin resources, and `CLAUDE.md` itself.

**It ships as a hard break with no compatibility shims**, backed by upgrade notes precise enough to
serve as a downstream find-and-replace recipe.

---

## 2. Why this matters

### 2.1 It blocks a cut already in progress

`spec_dd/2. in progress/learners-associated-with-organisations` introduces a model called `Learner`
and, without this rename, would file it inside an app called `student_management`. That spec's own
open-question section (`idea.md:267-274`) explicitly punts terminology here and states that renaming
the app is out of scope for itself. It is written assuming this lands first. **This spec is a hard
prerequisite for it.**

### 2.2 FLS already decided in writing; only the code disagrees

The in-tree brand-guidelines skill (`.claude/skills/brand-guidelines/SKILL.md:177`) has a terminology
table listing `learners` under "Use This" and `students` under "Not This", reasoned as *"works across
corporate, self-paced, and academic contexts"*. Five product docs already say "learner" in prose. This
is the code catching up to FLS's own documented voice, not a fresh stylistic call.

Terminology drift is already happening uncoordinated and in the right direction:
`qa_create_incomplete_registration_learner.py` already says "learner";
`.claude/agent-memory/fls-dev-qa-data-helper/reference_learner_visible_deadlines.md` sits beside four
siblings named `*_student_*`; `course_access/backends.py` docstrings (`:78,136,164,326`) say "learner"
while the same file's identifiers say "student". Left alone, the codebase converges on *both* words.

### 2.3 The wider industry settled it the same way

SCORM 2004 deliberately renamed `cmi.core.student_id` → `cmi.learner_id` between spec versions — the
same organisation renaming the same concept for the same reason. xAPI and LTI/1EdTech both use
"Learner" as the canonical role term, and South Africa's skills-development regime (SETA/QCTO,
"learnership") makes it the regionally natural word.

### 2.4 It is as cheap as it will ever be

**Confirmed premise:** the two downstream repos auto-notified on merge
(`.github/workflows/notify-downstream.yml` — `bloom_ls`, `first_class_ls`) are **dev/CI only, with no
persistent database**. There is no production data anywhere, and FLS's own dev database is rebuilt
from scratch rather than migrated forward.

App labels feed default table names, and **no model anywhere in the repo sets `db_table`** (verified:
zero `db_table` hits under `freedom_ls/`), so renaming a label renames every table it owns. With no
data to protect, that is a non-event. Every month FLS stays unshipped-but-growing this gets more
expensive; once there are downstream installs with data, it gets much more expensive.

### 2.5 It reopens a prior decision, deliberately

`spec_dd/3. done/2026-03-08_18:18_refactor-student-model` renamed `StudentCourseRegistration` →
`UserCourseRegistration` via `student_management/migrations/0011_rename_models.py`, but **explicitly
declined to rename the apps**, reasoning that *"renaming Django apps is extremely complex... the
benefit doesn't justify the risk."*

This spec reverses that call, and should be read as doing so knowingly. What changed: the risk it was
avoiding was data risk, which §2.4 establishes does not exist here; and the cost of *not* doing it has
since become concrete (§2.1). That spec also left measurable debt still live in the tree today — stale
`StudentFactory` references in three `claude_plugins/fls-dev` files, and the four dead
`view_student`/`add_student`/`change_student`/`delete_student` codenames — which this spec clears.

## 3. Decisions taken, and why

### 3.1 Migrations: regenerate a fresh `0001_initial` per renamed app

Delete the existing migration files in the two renamed apps that have them (15 in
`student_management`, 5 in `student_progress`; `student_interface` has **no `migrations/` directory at
all**) and regenerate a single `0001_initial.py` each, under the new label.

**The deciding factor is not tidiness.** Two migrations hardcode raw-SQL table names built from the
old app label:

| File | Old-label raw SQL |
| --- | --- |
| `0006_validate_no_duplicate_students.py:12` | `FROM freedom_ls_student_management_student` (inside `RunPython.forward()`; no-op reverse at `:33`) |
| `0008_populate_user_from_student.py:8-10, :14, :21-23` | table-name list, then `FROM freedom_ls_student_management_student AS s`, repeated for reverse |

Rewriting in place therefore means hand-editing SQL string literals, not just `dependencies` tuples
and `to=` references — a trap a naive sweep misses and a reviewer has to take on trust. Regenerating
removes the trap by construction and retires the four dead-`Student` migrations (`0006`, `0008`,
`0009`, `0010`) for free, since the model they service will not exist.

`squashmigrations`/`replaces` was considered and rejected: `replaces` exists to reconcile
*already-applied* history under the *same* app label across deployed databases, and that value is
nullified the moment the label itself changes. Full complexity, no benefit.

> **Assumption, explicitly named.** This is safe **only** because there is no production data (§2.4).
> If that premise stops holding before this ships, the choice flips to in-place rewrite plus a manual
> cutover script, and this section must be rewritten.

### 3.2 Persisted "student" strings: no data migration here; a documented recipe for downstream

The `"student"` role key is a **defined-but-unused placeholder** (`role_based_permissions/roles.py:93-101`,
`permissions=frozenset()`). No shipped code calls `assign_*_role(..., "student")`, no factory defaults
to it, nothing literal-compares against it, and no migration or `post_migrate` hook seeds it. FLS's own
database has nothing to migrate.

**But there is a bigger issue that only bites downstream.** Django's automatic content-type rename
machinery fires only for `migrations.RenameModel` operations — it has **no mechanism for
`AppConfig.label` changes at all**. Renaming the labels will not touch existing `django_content_type`
rows: it leaves them stale, and `create_contenttypes` inserts fresh rows under the new label, silently
orphaning anything FK'd to the old ones — `ObjectRoleAssignment.content_type`,
`CourseProgress.last_accessed_content_type`, guardian object permissions, `auth_permission`,
`django_admin_log`. `sync_role_permissions._ensure_permissions_exist` would then *create duplicate*
permissions rather than find the existing ones.

None of that can bite a rebuilt-from-scratch database. All of it would bite a downstream install with
real data. **Decision: ship no data migration; put a runnable recipe in the upgrade notes** (rename
`django_content_type.app_label` rows, backfill `role='student'` → `'learner'` on the three assignment
tables, then run `validate_role_permissions` as a smoke test).

### 3.3 Downstream: hard break, no compatibility shims

Of the six things this rename moves, only import paths and default table names can be cleanly shimmed
in Django. **App labels and permission strings cannot be aliased at all**; URL-namespace and
template-path shims are partial and costly. A shim would cost real code to cover under half the
breakage, and §2.4 confirms there are no installs with data to protect. Ship the break cleanly.

### 3.4 Commit shape: an ordered sequence, with two deliberately red commits

A single ~250-file commit is the worst shape for what review actually needs here: distinguishing
"mechanical, grep proves it" changes from "this needed a judgement call" changes. Interleaving both
forces the reviewer to read everything at the same attention level.

**Decision: an ordered sequence within one PR** (§16). **Commit 1 is a pure `git mv`**, carrying no
content edits beyond the `.secrets.baseline` regen the pre-commit hook forces (§13.2); it is expected
to be red (`ImportError` on `manage.py check`) until commit 2 lands. **Commit 3 is red for a second,
unrelated reason** — it renames a model ahead of the migration regen in commit 4, so both
`makemigrations --check` and `contrib/conformance/test_migrations.py` (which runs the same autodetector
check as a pytest test) fail until 4 lands. Two red commits, each for a stated reason. This is accepted
because:

- Isolating the move from every edit is the only way git reliably records `R100` renames — mixing a
  move with edits risks dropping below the default 50% similarity threshold and losing
  `git log --follow` history for that file.
- This repo's CI (`.github/workflows/tests.yml`) triggers on `push`/`pull_request` against the tip of
  a branch, **not per-commit**, so an intermediate red commit never fails a CI run.
- There is no live-data or rollout reason to keep every commit deployable.

### 3.5 Sweep technique: case-sensitive substring passes, never word-boundary regex

**`\bstudent\b` is the wrong tool and would silently miss the majority of hits.** `_` is a word
character, so there is no boundary between `student` and the following `_` — `\bstudent\b` does not
match `student_management`, `STUDENT_EMAIL`, `student_course_registration`, or
`student_a@example.com`, which is the overwhelming majority of the corpus. Use **plain substring**
matching (`grep -rn 'student'`), scoped to an explicit file inventory.

Every renamed identifier in this corpus is a strict **prefix** composition (`student` + `_management`,
`Student` + `Deadline`, `student` + `s`), so replacement order does not matter — a substring replace
of the stem produces the correct compound automatically. **What must not happen** is a
case-insensitive pass (`sed s/student/learner/gi`), which corrupts `StudentDeadline` → `learnerDeadline`
and `STUDENT_EMAIL` → `learner_EMAIL`. Run three distinct case-sensitive passes — `Student`→`Learner`,
`student`→`learner`, `STUDENT`→`LEARNER` — then a residual check. Plurals and possessives are handled
for free because the trailing `s` is untouched.

No AST-aware codemod tool (`ast-grep`, `comby`, `rope`, `bowler`, `repren`) is installed in this repo
(verified against `pyproject.toml`, `.pre-commit-config.yaml`, `package.json`). Introducing one is
disproportionate: this rename retires the word outright with a short, enumerated exception list
(§3.6), so there is no semantic ambiguity for AST matching to resolve.

### 3.6 Where mechanical substitution is wrong

These must be excluded by construction, not by hoping a reviewer notices:

| Category | Instance | Why |
| --- | --- | --- |
| Shipped specs | everything under `spec_dd/3. done/` | History; stays as written |
| Historical external quotes | `cmi.core.student_id` in `idea.md` and the upgrade notes | Rewriting it falsifies the historical claim the sentence makes |
| External contracts | webhook payload keys (`user_id`, `user_email`) | Already correctly "user"; an external contract |
| Prose in other in-flight specs | `spec_dd/2. in progress/*`, `1. next/*`, `0. drafts/*` | Out of scope to edit; they *will* appear in the residual grep |
| A TODO that is being satisfied | `roles.py:13` | Deleted only because this spec completes it (§10.3) — verify the condition, don't delete because the file was touched |

## 5. Migrations

Strategy is settled in §3.1. Additional facts that constrain execution:

- **No app outside the three has a migration depending on their labels** — verified by grepping every
  `freedom_ls/*/migrations/*.py`; all 20 matching files are the two apps' own migrations. The
  `organisations` dependency runs one way (`student_management` depends on `organisations`, not the
  reverse). The rewrite is local.
- **Hard ordering constraint:** the model-level renames (`StudentDeadline` → `LearnerDeadline` and its
  field/constraint, §9) must land **in source before** `makemigrations` regenerates the initial
  migration. Otherwise the fresh `0001_initial` creates a model called `StudentDeadline` under the new
  label — precisely the absurdity this spec exists to prevent.
- `swappable_dependency(settings.AUTH_USER_MODEL)` calls reference the setting indirectly, not a
  literal label string, so they survive regeneration without edits.
- All three `apps.py` files explicitly set `default_auto_field = "django.db.models.BigAutoField"`.
  **Do not drop these lines** during the rename.
- No `AppConfig` in the three apps sets `verbose_name`, so Django's auto-derivation picks up
  "Learner management" for free. No edit needed; confirm cosmetically in the django-unfold admin
  app-list during QA, since it is a user-facing surface with no automated coverage.
- No `Meta.app_label` override exists in any of the three apps (verified: zero hits).
- No `related_name`/`related_query_name` in current `models.py` contains "student" (verified).
  `0001_initial.py:207` does contain `related_name="student_registrations"` — a historical snapshot
  already superseded in `models.py` by `user_registrations`, and moot under regeneration.

## 6. URL namespace and cross-app Python imports

`app_name = "student_interface"` → `"learner_interface"`, and every `{% url %}` / `reverse()` site.

Two seams need more than find-and-replace, because they are **documented public interfaces**:

- **`course_access/backends.py`** returns URL *names* (`student_interface:course_home` at `:202`,
  `student_interface:initiate_course_access` at `:215`) across the pluggable-backend seam
  (`COURSE_ACCESS_BACKEND`) that downstream projects implement. It **also directly imports
  `student_management.queries` and `student_management.utils`** (`:20-23`) — a hard Python dependency.
- **`course_applications/`** — `backends.py:22` imports `student_management.utils`;
  `tests/test_backends.py:170` and `tests/test_views.py:19` import `student_management.factories`.
  `tests/test_collection_safety.py:48` is a third kind again — a **filesystem path**,
  `REPO_ROOT / "freedom_ls" / "student_interface"`, passed to a `pytester` subprocess. It is neither an
  import nor a URL name, so an import-focused sweep misses it; it is the only such path in the tree
  (verified). It fails loudly (pytest exits 4 on a missing path, and the test asserts `ret in (0, 5)`),
  and it must move with the package in §16 commit 2.

Also: `student_interface/tests/conftest.py:23` imports `student_management.factories`, and is the
fixture file used by all 27 `student_interface` test modules — not just itself.

## 7. The conformance suite — `freedom_ls/contrib/conformance/`

**This was not in the original idea's scope and is the highest-risk omission the research found.**

It is an opt-in, downstream-importable conformance/portability suite. It hardcodes the app path
`freedom_ls.student_interface`, the literal class name `StudentInterfaceConfig`, and a
`FLS_NAMESPACE_PROBES` data table of URL names, across four files (`__init__.py`, `test_settings.py:17-19`,
`test_urls.py`, `tests/test_conformance_meta.py`).

The **contract-tier** probes — which a downstream *cannot* prune even if it wants to — include:

```
student_interface:dashboard              [C]
student_interface:course_detail          [C]
student_interface:course_home            [C]
student_interface:initiate_course_access [C]
student_interface:courses                (internal, prunable)
```

The spec that built it (`spec_dd/3. done/2026-07-18_13:35_test_portability_2_conformance_suite`)
promised downstream, verbatim: *"This change only adds a new opt-in package... it stays inert until a
downstream explicitly imports it."* **This rename is the one exception to that promise**, and the
upgrade notes must say so in the same voice.

**The package holds two kinds of string, and they move on different commits.** Conflating them is the
trap here:

| Kind | Example | Moves with | If left stale |
| --- | --- | --- | --- |
| Python app path / AppConfig class | `"freedom_ls.student_interface"`, `"…apps.StudentInterfaceConfig"` | the package move (§16 commit 2) | **Silent** — see below |
| URL namespace | `"student_interface:dashboard"` | the namespace rename (§16 commit 5) | Loud — `NoReverseMatch` |

`_registry._app_installed` is just `apps.is_installed(dotted_path)`, and `probe_namespace_reverses`
**skips** when its app is not installed (`tests/test_conformance_meta.py:65-75` asserts exactly that
behaviour). So a stale `"freedom_ls.student_interface"` does not fail — **the whole probe table quietly
self-disarms and the suite reports green with skips**. This is the same failure class as §8's orphaned
theme override, in the one package whose entire job is to catch drift.

Requirements:

- The app-path and `StudentInterfaceConfig` strings — `test_settings.py:17`, `test_urls.py` (five
  `_Probe` rows), `tests/test_conformance_meta.py:60,69,71,82-83,87,95,104` — move **in the same commit
  as the package move** (§16 commit 2), not with the namespace rename.
- Every `student_interface:` URL string in the data tables becomes `learner_interface:` **in the same
  commit as the URL-namespace rename** (§16 commit 5).
- The two edits are deliberately **out of step** across commits 2–4, and that is correct: `app_name` is
  still `student_interface` until commit 5, so the URL strings keep resolving. What must hold at every
  green checkpoint is that each string matches what is actually live.
- Verify by **skip count, not exit code**: `uv run pytest freedom_ls/contrib/conformance -rs` must show
  the FLS namespace probes *running*, at commits 2, 4 and 5 alike. A run that goes green because every
  probe skipped is the failure this section exists to catch.
- Keep `__all__` in sync in every conformance submodule — a missed `__all__` update is **silent**
  (the function still exists, just isn't re-exported), unlike a missed probe-table rename, which fails
  loudly as `NoReverseMatch`.
- `_registry.py`, `test_migrations.py` and `test_theme.py` contain no "student" strings (verified) and
  need no edits — the four files named above are the complete set.
- The upgrade notes lead with this call-out.

## 8. Template and static directories

`student_interface/templates/student_interface/` → `learner_interface/templates/learner_interface/`,
and the same for `static/`. Every template path string in `render()`, `{% extends %}` and
`{% include %}` moves with it.

Scope: 29 `.html` files under `student_interface/templates/` (25 under `templates/student_interface/`,
4 app-scoped under `templates/cotton/`), plus
`student_interface/static/student_interface/js/alpine-components.js`.

**Themes shadow templates by path**, via a pure relative-path prepend with no registry. Neither
in-tree theme carries a student-named directory, but downstream themes will — and
`docs/how tos/theme-fls.md:321`'s own canonical Tier-3 worked example is literally
`themes/my-theme/templates/student_interface/partials/course_card_registered.html`. Any downstream
theme that followed FLS's own documentation has that directory.

> **This breakage is silent, not loud.** An orphaned theme override simply stops being found; the base
> template renders instead. Unlike `NoReverseMatch`, nothing raises. It therefore needs its own
> upgrade-notes call-out, distinct from the loud failures.

Fix the doc; call it out in the upgrade notes.

## 10. Permissions and roles

### 10.1 Permission-string prefixes follow the app label

`freedom_ls_student_management.*` → `freedom_ls_learner_management.*` in
`role_based_permissions/roles.py`, `registry.py`, and `config/role_based_permissions/demodev.py`.

**Carve-out:** three of the strings in `demodev.py` are *dead codenames*, not prefix renames — see
§10.2. Sweeping them mechanically produces `freedom_ls_learner_management.change_learner`, naming a
model that does not exist. Apply §10.2 to that file before the prefix pass, not after.

These strings are **not** stored on `auth_permission` — they are reconstructed at runtime from
`Permission.content_type.app_label`, which is exactly why the content-type issue in §3.2 matters
downstream. They must be edited **in the same commit as the `AppConfig.label` change**: a lag does not
cause an import error, but it does fail `sync_role_permissions`' tests against whichever label is live.

Permission **codenames** for models that keep their names (`view_cohort`, …) track model names that
are already correct — "user", not "learner" — and are **not** part of this rename.

### 10.2 Delete, do not rename, the four dead codenames

`view_student`, `add_student`, `change_student`, `delete_student` name the `Student` model deleted in
`0010_delete_student` and grant nothing today: `_filter_perms_for_content_type` excludes them from
every guardian sync because they never match a real object's content type. They are still live in **eight** files —
`role_based_permissions/registry.py`, `roles.py`, `README.md`, three test files
(`tests/test_roles.py`, `tests/test_management_commands.py`, `tests/test_utils.py`),
**`config/role_based_permissions/demodev.py`** and
**`qa_helpers/management/commands/qa_create_organisation_scenarios.py`** (`:334`, a comment explaining
that `view_student` is filtered out). A ninth hit,
`student_management/migrations/0011_rename_models.py`, is moot under §3.1's regeneration, and
`.claude/agent-memory/fls-dev-qa-data-helper/reference_organisation_scenarios_command.md` mirrors the
`qa_create_organisation_scenarios.py` comment and is swept with the rest of agent memory (§12).

`demodev.py` and `qa_create_organisation_scenarios.py` were missing from every prior inventory, and
both matter: they are the files where a mechanical prefix sweep would *silently succeed* at producing a
wrong string. In `qa_create_organisation_scenarios.py` the hit is a comment explaining the filtering
behaviour, so it goes with the thing it explains rather than being reworded.

Deleting them also removes a latent mis-binding bug in
`sync_role_permissions._ensure_permissions_exist`'s content-type fallback.

**Consequence in `demodev.py`, decided:** deleting the three codenames empties `senior_ta`'s
`add_permissions` (leaving it equivalent to the `ta` it inherits) and reduces `guest_reviewer` to
`view_cohort` alone. **Keep both roles**, with an empty `add_permissions` set and the single remaining
permission respectively. Neither role is referenced anywhere else in the tree, so nothing breaks; they
stay as demo scaffolding for a real permission to be added later. Deleting a role would be a scope
widening this spec does not take.

**This is the one deliberate non-rename change in the spec**, and it is removal of something already
inert — no behaviour changes.

### 10.3 Role key and the standing TODO

- Role key `"student"` → `"learner"` and `display_name="Student"` → `"Learner"` (`roles.py:93-94`,
  asserted in `tests/test_roles.py:57`). The role's own `description` already reads *"Standard learner

### 11.4 Audit for "user" leaking through where "learner" is meant

Mechanical renaming fixes the wrong word; it does not fix the vague one. **The decision rule:**

- **"user"** — account/identity/auth/audit-trail contexts, and anything true of a person regardless of
  role: `User`, `UserCourseRegistration`, `CohortMembership`, `UserCohortDeadlineOverride`, webhook
  payload keys (also an external contract).
- **"learner"** — course-taking contexts: progress, deadlines, enrolment rosters.

A `User` can hold `instructor` on one course and `learner` on another, so the account layer must stay
role-neutral. **The real risk is not the "student" hits a grep finds; it is the places the code
already, incorrectly, says "user".** This is a judgement pass, isolated into its own commit (§16), and
it cannot be scripted.

## 13. Newly discovered scope — not in the original idea

These three were found by verifying the idea against the tree, and none appear in any prior research
document.

### 13.1 `CLAUDE.md` itself

`CLAUDE.md:58,60-62` — the project-instructions file's own "App Structure" section names all three apps
with "student"-containing descriptions. Every prior grep swept `docs/`, `claude_plugins/`, `.claude/`

It **must** be updated in the same PR, or `CLAUDE.md` will describe three apps that no longer exist —
misleading every subsequent Claude Code session, including the one that regenerates
`docs/app_structure.md`, which this file is supposed to summarise.

### 13.2 `.secrets.baseline`

`.secrets.baseline:175,178,185` key three entries by the literal path
`freedom_ls/student_management/management/commands/create_demo_data.py`. `detect-secrets` (run via
`.pre-commit-config.yaml`) matches findings **by filename**.

If that file moves without the baseline being updated, the hook stops suppressing the finding it was
allowlisting, surfaces it as a *new* secret under the new path, and **fails the commit**.
**Regenerate it** (`detect-secrets scan --baseline .secrets.baseline`) rather than hand-editing paths.

**This lands in §16 commit 1, not commit 8.** `CLAUDE.md` mandates committing via `uv run git commit`,
so `.pre-commit-config.yaml`'s `detect-secrets` hook (`args: ['--baseline', '.secrets.baseline']`) runs
on the `git mv` itself — commit 1 cannot be created until the baseline knows the new path. This is the
**one** permitted exception to commit 1's "zero content edits" rule (§3.4, §16), and it costs nothing:
`.secrets.baseline` is not itself a renamed file, so git's rename detection for the moved packages is
unaffected.

`create_demo_data.py` is the only file in the three apps carrying a baseline entry (verified — the
other five baselined paths, including `qa_helpers/.../qa_create_large_cohort.py`, do not move).

### 13.3 `fls-test-portability-part-2` is further along than "prose mentions"

`spec_dd/3. done/2026-08-24_06:31_fls-test-portability-part-2/2. plan.md` specifies a **not-yet-created** file,
`freedom_ls/student_interface/checks.py` (confirmed absent), implementing Django system checks with IDs

## 15. Out of scope

- **Renaming any other app.** `educator_interface` and the rest keep their names.
- **`User`, `UserCourseRegistration`, `CohortMembership`, `UserCohortDeadlineOverride`.** "User" is the
  right word there; this spec only removes "student".
- **Permission codenames tracking correct model names** (`view_cohort`, …).
- **Per-tenant configurable role labels.** A fair question for a multi-tenant product, but FLS has no
  i18n infrastructure today (no `locale/`, no `LocaleMiddleware`, `gettext_lazy` used in 5 files for
  `verbose_name`s only), and a naive `LEARNER_LABEL` substitution breaks on plurals, possessives,
  capitalisation and sentence position. If wanted, it is its own spec built on real Django i18n.
- **Behaviour changes of any kind.** Anything broken that surfaces during the rename becomes its own
  spec. The single exception is deleting the four dead permission codenames (§10.2) — removal of
  something already inert. The "No students are currently enrolled" empty state gets a mechanical word
  swap, **not** a copy upgrade with a call-to-action.
- **Rewriting `spec_dd/3. done/`.** Shipped specs are history.
- **Renaming this spec's own directory or git branch.** SDD commands locate a spec by matching branch
  name to directory.
- **Adopting a codemod tool** (§3.5).
