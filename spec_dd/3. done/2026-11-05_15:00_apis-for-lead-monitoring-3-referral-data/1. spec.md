# Spec: Lead monitoring API, referral data

Spec 3 of 6 in the Lead monitoring API effort (`spec_dd/1. next/roadmap.md`, "Lead monitoring
API"). Source: `idea.md` in this directory. Research: the `research_*.md` files beside it.

## Purpose

Scripts that watch leads need a site's referral tracking data on a schedule, without a person
downloading four admin CSV exports and joining them. This spec adds four read-only resources under
`/api/v1/`, one per `referral_tracking` model, readable by an `ApiKey` with the `referral_data`
scope.

## Scope

In:

- `referral-codes`, `referral-code-hits`, `signup-attributions` and `first-touch-counts`, each with
  a list and a detail route, read only, bound to the key's site.
- Making child 1's keyset pagination order on a field other than `updated_at`, including a
  `DateField`.
- A date-typed `day_since` filter for first-touch counts.
- Documentation in `docs/api.md` and the product docs.

Out (from `idea.md`): attribution touches and conversions (child 6); `client_ip`, `user_agent`,
`ga_cookie`, `fbp_cookie`, `fbc_cookie` under any key or permission; adding `updated_at` to any
`referral_tracking` model; a deletion feed; correcting `hit_count` reconciliation or hit pruning;
write endpoints, UI, webhooks, admin export changes; derived fields such as marketing channel or
referer host; filters on referral codes; a `go_url` or any URL built from stored code text.

## Decisions

| Decision | Reason |
| --- | --- |
| Generalise the shared pagination; don't subclass it per resource. | One code path, which child 6 also needs. |
| `updated_since` on hits and attributions, a separate `day_since` on first-touch counts. | Hits and attributions are append-only. Counts change in place, and the name must not claim a change signal. |
| Flat foreign keys: the export's column name holds the id, `<fk>_<attr>` holds the readable value. | Loads straight into pandas and CSV. Owner's choice. |
| No migration. | The existing `(site, hit_at)`, `(site, signed_up_at)` and unique `(site, day, key_hash)` indexes serve the keyset queries; the `id` tie-break only sorts ties. |
| Values as stored: blank text is `""`, null datetimes `null`, booleans JSON booleans. No export resource or widget is reused. | The API must not pick up export formatting. |

## Requirements

### Shared API machinery (`freedom_ls/api/`)

**`viewsets.py`.** `ReadOnlyApiViewSet` gains `cursor_field: str = "updated_at"`, the model field
the list is ordered and paged on, with `id` as the tie-break.

**`pagination.py`.** `ApiKeysetPagination` reads `view.cursor_field` (falling back to
`updated_at` when `view` is `None`) in place of the hard-coded `ordering` and the three literal
`updated_at` references (`paginate_queryset`, `_next_link`, `_encode_cursor`):

- Order by `(cursor_field, "id")`. Position filter:
  `Q(**{f"{f}__gt": v}) | Q(**{f: v, "pk__gt": last_pk})`.
- The cursor stays `urlsafe_b64encode(json.dumps([value.isoformat(), str(pk)]))`.
- Decoding follows the field's type (`queryset.model._meta.get_field(cursor_field)`), checked
  with `get_internal_type()` (or `DateTimeField` before `DateField`, since `DateTimeField`
  subclasses `DateField`). For a `DateTimeField` it is `datetime.fromisoformat` and a naive value
  is rejected, as now. For a `DateField` it is `date.fromisoformat`, and any value with a time
  part is rejected. Every failure is the existing 400
  `{"cursor": ["The cursor is not one this API issued."]}`.
- The `TypeVar` bound changes from `TimestampedModel` to `Model`. `paginate_all` in
  `freedom_ls/api/tests/helpers.py` takes the same bound and a `cursor_field: str = "updated_at"`
  parameter, which it passes to the paginator through a stub view.

Users responses and cursors are byte-for-byte what they are today.

**`filters.py`.** Add `IsoDateFilter`, a `django_filters.DateFilter` whose field accepts only
`YYYY-MM-DD`. A datetime or unparseable value is a 400 keyed by the parameter name, with a message
saying a date is expected. `UpdatedSinceFilterSet` is unchanged. A filterset that needs
`updated_since` on another field redeclares it:
`updated_since = AwareIsoDateTimeFilter(field_name="hit_at", lookup_expr="gte")`. Every filter here
is inclusive (`gte`), and its OpenAPI description names the field it compares against.

**`scopes.py`.** The `ApiScope.REFERRAL_DATA` entry in `_DESCRIPTIONS` becomes
`"ReferralCode, ReferralCodeHit, SignupAttribution, FirstTouchCount"`. The stored value stays
`referral_data`.

### Referral resources (`freedom_ls/referral_tracking/api.py`, new)

Follows `freedom_ls/accounts/api.py`: one `ModelSerializer` per model with an explicit `fields`
tuple and `read_only_fields = fields`, one `ReadOnlyApiViewSet` per model with
`required_scope = ApiScope.REFERRAL_DATA`, and a `router.register` call. Each `get_queryset` starts
from `Model._base_manager`, and the base viewset's `site_queryset` binds it to the key's site.
Detail lookup is by the UUID `id`.

| Prefix / basename | Model | `cursor_field` | Filter | Queryset |
| --- | --- | --- | --- | --- |
| `referral-codes` / `referral_code` | `ReferralCode` | `created_at` | none | plain |
| `referral-code-hits` / `referral_code_hit` | `ReferralCodeHit` | `hit_at` | `updated_since` on `hit_at` | `select_related("referral_code")` |
| `signup-attributions` / `signup_attribution` | `SignupAttribution` | `signed_up_at` | `updated_since` on `signed_up_at` | `select_related("user")` |
| `first-touch-counts` / `first_touch_count` | `FirstTouchCount` | `day` | `day_since` (`IsoDateFilter` on `day`) | plain |

Fields, in this order:

- **`ReferralCode`:** `id`, `code`, `label`, `notes`, `destination`, `inactive_destination`,
  `is_active`, `hit_count`, `last_hit_at`, `created_at`.
- **`ReferralCodeHit`:** `id`, `referral_code` (the code's UUID), `referral_code_text` (the
  code's `code`, `source="referral_code.code"`), `door`, `is_machine_fetch`, `hit_at`. `door` is
  the stored value (`"go"` or `"d"`).
- **`SignupAttribution`:** `id`, `user` (the user's integer id), `user_email`
  (`source="user.email"`), `advert_code`, `referral_code`, `utm_source`, `utm_medium`,
  `utm_campaign`, `utm_content`, `utm_term`, `gclid`, `gbraid`, `wbraid`, `fbclid`,
  `landing_path`, `referer`, `raw_query`, `first_seen`, `signed_up_at`. `referral_code` here is
  the text captured at signup, not an id; it may match no `ReferralCode`.
- **`FirstTouchCount`:** `id`, `day` (ISO date), `advert_code`, `referral_code` (text),
  `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `is_overflow`,
  `key_hash`, `count`.

`client_ip`, `user_agent`, `ga_cookie`, `fbp_cookie` and `fbc_cookie` are on no serializer. Admin,
`resources.py` and the exports are unchanged.

### Dependency map

`referral_tracking/api.py` imports `freedom_ls.api`, a new `referral_tracking → api` runtime edge.
`docs/app_structure.md` shows the edge, and the generated `test_organisation/import_contracts.toml`
no longer forbids `freedom_ls.api` in the `referral_tracking` contract, as child 1 did for
`accounts → api`. Both files come from `ds:app_map`; neither is hand-edited. `rest_framework` is imported only from `api.py`, so a project that
installs `referral_tracking` without `freedom_ls.api` never imports it.

## Testing

Endpoint tests live in `freedom_ls/referral_tracking/tests/test_api.py`, with
`freedom_ls/accounts/tests/test_api.py` as the template. Rows are built through the
`referral_tracking` factories, never through `/go/`. Timestamps are set with
`Model._base_manager.filter(...).update(...)`, because `SignupAttribution.save` refuses an update.

For each of the four resources:

- The response's field set equals the list above exactly. For signup attributions, none of the
  five withheld names appears.
- A row on a second site is absent from the list, and its detail is 404.
- Detail by UUID returns the row. An unknown UUID is a 404 JSON body.
- A key without `referral_data` gets 403 naming the scope, on both list and detail. No key gets
  401.
- POST is 405. HEAD and OPTIONS work.
- A query-count bound over 20 rows proves `select_related` on hits and attributions.
- Rows come in ascending `(cursor_field, id)` order across pages.

Paging and filters:

- 1,500 hits sharing one `hit_at` and 1,500 first-touch counts sharing one `day`, paged at the
  maximum page size: every row appears exactly once.
- `updated_since` on hits and attributions: a row exactly at the bound is included and one before
  it is excluded. A naive datetime is a 400.
- `day_since`: a row on the bound day is included and the day before is excluded. A datetime
  value and an unparseable value are each a 400 keyed `day_since`.
- `next` keeps `updated_since`/`day_since` and `page_size`.
- On `first-touch-counts`, a date cursor round-trips and a cursor with a time part is a 400. On
  `referral-codes`, a `created_at` cursor round-trips. These live here, not in
  `freedom_ls/api/tests/`, because the `api` import contract keeps those tests away from every
  model with a `DateField`.

Shared machinery (`freedom_ls/api/tests/`):

- `test_pagination.py`: a naive datetime cursor is still rejected, and the existing users
  pagination tests pass unchanged.
- `test_filters.py`: `IsoDateFilter` accepts `YYYY-MM-DD` and rejects other forms.
- `manage.py spectacular --validate --fail-on-warn` passes with the four new resources (already a
  test from child 1).
- The `docs/api.md` python fences still compile (`freedom_ls/api/tests/invariants/test_api_docs.py`).

Values as stored: a referral code whose `hit_count` exceeds its surviving hits returns both values
unchanged, a blank `utm_source` is `""`, and a code never hit has `last_hit_at: null`.

## Documentation and downstream

**`docs/api.md`:**

- The intro and the "API keys → API scopes" table: four referral endpoints exist, and the
  `referral_data` row lists `FirstTouchCount`. Remove "Only `users` has an API endpoint so far".
- "Syncing data → Pages": rows come in ascending order of the endpoint's ordering field, then `id`.
- "Incremental syncs": a table of endpoint, ordering field, filter and recipe:
  - **Referral codes: full pull.** Every run reads every page and upserts by `id`. `label`,
    `is_active`, `hit_count` and `last_hit_at` change in place with no timestamp. Codes are never
    deleted.
  - **Hits and signup attributions: checkpoint.** Child 1's users recipe applies, checkpointing on
    `hit_at` or `signed_up_at` minus 5 minutes. Both are stamped before the write commits.
  - **First-touch counts: lookback.** `day_since` takes `YYYY-MM-DD`. `count` rises during the day
    and nothing records the change. A row is only ever incremented on the current `day`, so each
    run asks from yesterday and upserts by `id`. `day` is the date in the project's `TIME_ZONE`
    (UTC unless the project changes it), and the API does not convert it. A missing row means zero.
- "Deletions": hits older than the operator's `prune_referral_code_hits --older-than-days` cutoff
  disappear. A signup attribution goes when its user is deleted. Neither is visible to a filter.
- One section per resource, in the Users layout (endpoint table, Fields table, notes). The hit
  `referral_code` is an id, while on attributions and counts it is captured text. A "Not returned"
  line on signup attributions names the five withheld fields and says no key or scope returns them.
- A "Known data caveats" subsection:
  - `hit_count` excludes machine fetches. The hit log keeps them (`is_machine_fetch`) and is
    pruned, so the two never reconcile. Count hits with `is_machine_fetch` false for human visits.
  - Hits are capped per address per hour (`REFERRAL_TRACKING_HIT_LOG_LIMIT`).
  - `is_overflow` rows hold every attribution key past the daily cap, so per-campaign sums are
    lower bounds, and a campaign can span two rows on the day the attribution key fields changed.
  - Counts are not fraud-checked.
  - Without IP, user agent and cookie ids the data cannot feed a Google or Meta conversion upload.
- One Python example for the first-touch-count lookback that reuses child 1's `get_page`.

**`docs/product/security-and-data-handling.md`:** the "Built" summary and "API Access (built) →
What it exposes" name the four referral resources. The users paragraph's "returns no ... signup
attribution" says the users endpoint returns none, and that signup attributions come from
`signup-attributions` under `referral_data`. Referral codes, hits and first-touch counts hold
no personal data. Signup attributions return the user's id and email, click ids, `landing_path`,
`referer` and `raw_query`, which can carry personal data or tokens verbatim. `client_ip`,
`user_agent` and the three cookie ids are withheld from the API and stay behind the admin's view
permission and export. Downstream copies of deleted users are the key holder's to delete. The
signup attribution bullet under "Personal Data Collected" points to this. Bump "Last updated".

**`docs/product/referral-codes.md` and `docs/product/signup-attribution.md`:** codes, hits,
signup attributions and first-touch counts are readable through the API under `referral_data`,
linking to `docs/api.md`. Bump "Last updated".

**Upgrade notes:** no migration and no new setting. Downstream projects need no step.

## Success criteria

- Every test in the Testing section passes, with the users endpoint's existing tests unchanged.
- `docs/api.md` lets a script author write a sync for each of the four resources without reading
  the code: ordering field, filter, recipe, withheld fields and caveats are all on the page.
- `security-and-data-handling.md` names every referral field the API returns and the five it
  withholds.
