# Research: codebase (faster-test-runs-8-narrower-targeted-tier)

Question: what in the existing codebase does this work touch, reuse or conflict with? Line numbers are in this worktree at the start of the spec.

## 1. The selector: `claude_plugins/django-stack/scripts/select_tests.py` (818 lines)

`.claude/ds/scripts/select_tests.sh` is the generated wrapper (ds:init output). The logic lives only in the .py. Stdlib only, plus two siblings: `check_test_mirroring` (`is_collected`, `owning_app`) and `generate_app_map` (`App`, `Edges`, `find_apps`, `parse_existing_edges`).

### Rule order in `decide()` (377-415); the first match wins
1. `config.none` (NONE_GLOBS 35-43: `docs/**`, `.github/**`, root `*.md`, `.claude` md/json, agent-memory, `.gitignore`, plus project `none`) -> `none`.
2. `test_file_decision` (360-374): a collected test file under a `tests` dir selects itself (a deleted one selects nothing).
3. `config.dependency` (DEPENDENCY_GLOBS 58-64: pyproject.toml, uv.lock, .python-version, package*.json, plus project `dependency_files`) -> `full`.
4. `config.escalation` (ESCALATION_GLOBS 46-55: `**/migrations/**`, `**/conftest.py`, `**/factories.py`, `**/fixtures/**`, `**/urls.py`, `**/middleware.py`, `**/signals.py`, `**/apps.py`, plus project `escalation`) -> `full`. One hit means the whole run is full. It is checked before the owning-app rule, so an app's own `conftest.py` or `urls.py` never reaches `decide_app_path`.
5. `owning_app` hit -> `decide_app_path` (293-306): `owner_decision` (248-262, the owning app's `tests/` dir; UI globs 74-82 add the app's `playwright/` to the run via `touched`) plus `importer_decisions` (265-290), one `select` per importer's whole `tests/` dir. With no app map (`edges is None`) the result is `full` ("docs/app_structure.md missing").
6. `decide_tooling` (339-357): the generic `TOOLING` entries (68-71) plus project `[[tool.test_tiers.tooling]]`.
7. Otherwise `full` "unmapped path" (415); an untracked file gives `none` (413-414). This is the rule that sends `demo_content/**/*.yaml|*.md|images` to `full` (14 of the 34 full batches; 3 were `demo_content/**/*.md`). Root `*.md` is in NONE_GLOBS, but `demo_content/x.md` is deeper, and the comment at 33-34 says so on purpose.

### Importer fan-out
- `importers()` (197-218) is a BFS over `Edges`. Importers of the changed app come through any depth of **runtime** edges (a runtime importer is queued so its importers join). A **test-only** importer is added but not queued, so it is one hop. Each hit gives a reason string `"<src> has a runtime dep on <app> through <x>"`.
- `app_dependencies()` / `runtime_closure()` (225-245) is the opposite direction, used only by the upstream (`--upstream-range`) path.
- The granularity is the app. `Edges` are `(src_app, dst_app)` pairs from `generate_app_map.compute_edges` (395-431), built from `ast.ImportFrom` nodes only (`walk_app_imports` 386-392): `import x.y` is not seen, and an import under `if TYPE_CHECKING:` counts as runtime (there is no `TYPE_CHECKING` handling anywhere in `generate_app_map.py`). Model relations by string label or `AUTH_USER_MODEL` and `declared_edges.toml` edges also become runtime edges (413-429). The module-level facts (which module imports which) are discarded when the edges are made, so "select by the modules that import the changed one" needs new data: a per-module import graph with its own `ast` walk, or a call into `generate_app_map`'s helpers (`iter_app_trees` 163, `module_name` 186, `all_module_names` 434).
- The map is read from the committed `docs/app_structure.md` by `parse_existing_edges` (679-696), not recomputed. A stale table means a stale selection. Any module-level or depth data would have to be recomputed from source or be written into the doc.
- Every selected target is the whole `<app>/tests` dir (`tests_dir_of` 221-222). `minimal_selection` (703-710) drops a path that sits inside another selected dir. Selecting a sub-path such as `<app>/tests/test_x.py` or a `tests/<subdir>` is already supported by `compose_command` (683-700) and the tooling path.

### `--range`, `--working-tree`, `--upstream-range`, `--tests-changed-in`
- `range_type` (556-559) and `upstream_range_type` (562-568) validate the arguments. `range_paths` (571-583) runs `git diff -z --name-only --no-renames` (both sides of a rename count). `working_tree_paths` (586-594) and `changed_paths` (597-610) union paths, ranges and the working tree.
- `--upstream-range` (given once) is handled in `split_upstream` (621-631), `branch_context` (634-659) and `decide_upstream` (482-545). A path main brought in that the branch's own diff does not hold gets `from main;` reasons (`from_main` 430-432) and only counts where it meets the branch (`BranchContext` 418-427: branch apps, their runtime closure, their dependents, the tests the branch selects). Inside `decide_upstream`, escalation globs do not mean `full`: `related_tests_decision` (459-479) selects the tests of every related app. Dependency files stay `full` (500-501). An unmapped upstream path is `none` (543-545). An upstream path in a branch app uses every importer (533-534: `only=None`), and for an app the branch only imports it uses only the importers the branch changed.
- The idea says "how the selector treats paths main brought in does not change" (settled). Any new rule must therefore leave `decide_upstream` unchanged in outcome, and it shares `importer_decisions(only=...)` and `owner_decision` with the branch path. A fan-out limit added inside `importers()` would change the upstream result too. The limit has to be applied only on the branch-path call at 305, or `decide_upstream` has to be made to bypass it. Spec 8 should test both.
- `--tests-changed-in` (`branch_test_decisions` 662-680) adds changed test files without raising the tier.

### Config parsing and validation
- `load_tier_config` (158-174) reads `[tool.test_tiers]` with `tomllib` and builds the frozen `TierConfig` (102-110: `none`, `escalation`, `dependency`, `tooling`, `markers`). Project lists are appended to the built-ins (`NONE_GLOBS + glob_list(...)`), so **a project cannot remove or narrow a built-in rule today.** Narrowing needs a new mechanism.
- Validators: `glob_list` (122-130), `tooling_entries` (133-148), `marker_expression` (151-155). Each raises `ConfigError` naming the key, and `main()` turns it into `parser.error` (761-764, exit 2). The text is `"[tool.test_tiers] 'key' must be ..."`.
- An opt-in key is added by: a new field on `TierConfig` with a default that keeps today's behaviour, a validator beside the three above, a line in `load_tier_config`, and a rule that reads it. Nothing rejects unknown top-level keys of `[tool.test_tiers]` in the selector. `run_tests.py` (141-174) parses only the `memory` subtable, with unknown-key rejection inside `memory`. A new key beside `escalation` or `none` must not collide with `memory`, and a new subtable must not break `run_tests.py`'s check, which looks only inside `memory`.
- FLS values today (`pyproject.toml` 111-174): `none = ["spec_dd/**", "claude_plugins/**/*.jsx"]`, `escalation = ["config/**", "freedom_ls/site_aware_models/**", "freedom_ls/content_base/**"]`, `markers`, `[tool.test_tiers.memory]`, and 7 `[[tool.test_tiers.tooling]]` entries (plugin scripts and templates -> `tests`, icons generator, `fls-content` -> `claude_plugins/fls-content` plus `freedom_ls/content_engine/tests`, plugin `*.md` -> four named tests, drawio svg). The `fls-content` entry shows an existing way to map a path to specific test dirs and files: **a `demo_content/**` rule can be a new `[[tool.test_tiers.tooling]]` entry with no selector change**, because `decide` tries tooling (409) only after the unmapped fall-through is avoided: `owning_app` is None for `demo_content/`, so tooling is reached before the "unmapped" `full` at 415. This reuses `decide_tooling` and its existing tests. That one is a pyproject-only change.
- `freedom_ls/site_aware_models/**` and `freedom_ls/content_base/**` are project `escalation` entries (and they are also apps that nearly everything imports). The built-in `**/factories.py` etc. cannot be overridden by a project at all. `config/**` is the settings package (3 of the 34 full batches).

## 4. The app import graph and why some apps are widely imported (`docs/app_structure.md` dependency table, lines 310-353)
Number of apps with a runtime dependency on each (read from the table; the batch research counted test directories selected, with runtime edges chained and test-only edges one hop):
- `base` (38 dirs selected): runtime dep of nearly every app. It holds shared models, the site, templates, helpers (`base` itself depends at runtime on `learner_management` and `site_aware_models`, so the graph is cyclic through it, and the BFS at 197-218 reaches everything).
- `accounts` (36): the custom user model; the table has its dependants all over the place, and string model relations to `AUTH_USER_MODEL` count as runtime edges (`generate_app_map` 413-429).
- `panel_framework` (36): depends only on `accounts`, yet `accounts` has a runtime dep on `panel_framework` (accounts row, line 314) and `learner_management`, `educator_interface`, `reports`, `deployment`, `qa_helpers` import it. Because runtime deps chain, everything reaching `accounts` reaches `panel_framework`, and 20 of the 35 wide runs came from it.
- `icons` (30): no deps; `content_engine` and `accounts` (test-only) import it. The chain through `content_engine` reaches 28+.
- `content_engine` (28): imported at runtime by about 20 apps, and the chain adds more.
- `site_aware_models`, `content_base`: already project `escalation` entries.
Why the chain is so wide: one cycle-ish hub (`base` <-> `learner_management` <-> `accounts` <-> `panel_framework`) means `importers()` finds nearly all 42 test dirs. A depth limit (BFS level) or a per-app setting cuts at the hub. A per-module graph is the precise route but needs data the selector lacks (section 1). `qa_helpers`, `dev_tools` and `deployment` import many apps but are imported by few.

There are 42 app test directories (`freedom_ls/*/tests`); the number comes from the batch research.

## 6. Conftests (and whether an escalation hit could be scoped)
Files: `conftest.py` (root: `pytest_xdist_auto_num_workers` cap of 4 workers, line 20), `freedom_ls/conftest.py` (autouse fixtures: `_disable_force_site_name` 45, `_clear_django_cache` 51, `_isolate_media_root` 64, `_disable_preview_overrides` 109, `_clear_course_access_backend_cache` 123, `_clear_rule_kind_cache` 144, `_clear_messaging_policy_cache` 164, `_clear_deadline_policy_cache` 188; plain fixtures `site` 218, `mock_site_context` 251, `logged_in_client` 258, `staff_client` 270, `course_with_topic` 277, `article_with_image`, `site_aware_request`, `live_server_site` 316, `mock_legal_blobs` 325, `legal_repo_mock` 370, `database_task_backend` 393), `tests/conftest.py` (repository tooling), and per-app `tests/conftest.py` in: accounts, blog, comms, course_applications, course_interest, course_recommendations, deadlines, deployment, educator_interface, hr_attributes, icons, learner_interface, learner_management, learner_progress, mail, messaging_policy, panel_framework, registration_rules. Nested ones: `blog/tests/demo_content`, `content_engine/tests/demo_content`, `learner_interface/tests/demo_content` (each only re-exports the demo fixtures), `educator_interface/tests/panels/audit_log`, `educator_interface/tests/playwright`, `panel_framework/tests/playwright`.
- pytest scoping: a conftest applies to its own directory subtree, which `**/conftest.py -> full` ignores. A change to `<app>/tests/conftest.py` can only affect tests under `<app>/tests/` (and anything that imports it by module path, which is unusual: check with `grep` for `from freedom_ls.<app>.tests.conftest import`). A change to a nested conftest affects only its subdirectory. So `<dir>/conftest.py` can map to `<dir>` for every conftest other than the two roots (`conftest.py`, `freedom_ls/conftest.py`) and `tests/conftest.py` (which selects `tests/`, as the tooling rule does). The root and `freedom_ls/conftest.py` stay `full`. 9 of the 34 full batches were a conftest. `decide_upstream` already does a related mapping for upstream conftests (528: `related_tests_decision`), but only for main's paths.
- Caveats: `freedom_ls/tests/demo_content_fixtures.py` and `freedom_ls/tests/factories.py` / `site_context` are shared helper modules under `freedom_ls/tests/` (not an app, so `owning_app` is None, and `**/factories.py` forces `full` for `freedom_ls/tests/factories.py`). A file imported by many apps' tests is a plain module and needs the import graph, not the conftest subtree rule. Per-app `factories.py` (23 of them, including `site_aware_models`, `accounts`, `organisations`) are imported by other apps' tests as test-only edges: this is why `factories.py` is an escalation glob; a narrowing rule would map `<app>/factories.py` to `<app>` plus the apps with a (test or runtime) edge to it, which is exactly what `decide_app_path` produces now when the app is not in the escalation list. `urls.py` (16 files; a project `urls.py` change can break `reverse()` anywhere, and `panel_framework/tests/urls.py` is a test urlconf) and `apps.py` and `migrations` are the same trade: they affect the app and its importers, and also the whole DB schema (migrations: reused DB in spec 2 may change that).

## 9. Observations that bear on the design
1. `demo_content/**` is a pyproject-only fix through the existing `tooling` mechanism (no code change), though a generic "unmapped path maps to X" is not needed.
2. Conftest scoping and "factories/urls/apps map to the owning app plus importers" need selector code, because `escalation` is a `full` list and built-ins cannot be removed. The cheapest opt-in forms are: (a) a key that turns the built-in `**/conftest.py`-style hits into scoped selections, or (b) a key listing the built-in globs a project demotes to normal app handling.
3. Fan-out depth: `importers()` (197-218) is the only place to cap it (a `max_depth` argument on the BFS queue, tracking level), called from `importer_decisions` (276) for both branch and upstream. Apply it in the branch path only, to keep main's paths as they are today. Or give `decide_app_path` the limit and leave `decide_upstream` (537) calling with no limit.
4. Hub apps (`base`, `accounts`, `panel_framework`, `icons`, `content_engine`) would need an owner-only or direct-importers-only rule with a named run that still covers the rest: the `implement_plan` final full run (131) and `finish_worktree`'s checkpoint (but the checkpoint uses the same selector and may also narrow; see section 3).
5. `selected output is deterministic and printed with `why:` lines; `full_run_record.run_selector` (162-169) parses `-> full (` from those lines, so a changed `why:` format for `full` would break it. Keep that substring.
