# Frontend QA: footer area

Manual browser verification for the site footer. Everything here is observable in a browser; nothing
in this file belongs in the automated suite.

## §0 Setup

```
PORT=$(.claude/ds/scripts/find_available_port.sh)
npm run tailwind_build
uv run python manage.py runserver $PORT
```

Base URL is `http://127.0.0.1:$PORT`. The `bg-footer` / `text-on-footer` utilities do not exist
until the Tailwind build has run against the new tokens, so **do not skip the build** — a footer
with no background is a stale bundle, not a bug in the markup.

Credentials come from `.claude/fls-dev/config.md`:

- Admin / educator: `demodev@email.com` / `demodev@email.com`
- Learner: `demodev_s1@email.com` / `demodev_s1@email.com`

Seed data:

```
uv run python manage.py qa_create_course_player_learner
```

That gives the learner an enrolled course with parts (`functionality-demo-course-parts`), one with
saved progress (`functionality-demo-show-end-with-topic`), and one they are not enrolled in
(`functionality-demo-show-end-with-quiz`). If the demo courses are missing, load `demo_content/`
first.

Throughout, "the footer" means the copyright line plus the Terms and Conditions and Privacy Policy
links. "Full" means the roomy version on plain pages; "compact" means the short bar on the sidebar
shell.

---

## §1 The full footer on a plain page

1. Log in as the learner and go to `/` (the dashboard).
2. Scroll to the bottom.

Expect:

- One footer bar across the full width of the window, sitting below the page content on a faintly
  different background from the page, with a hairline border along its top edge.
- A line reading `© 2026 <site name>` — the same name shown in the header bar.
- Two links after it: **Terms and Conditions**, then **Privacy Policy**, in that order.
- The links are underlined and use the site's link colour. They are clearly readable against the
  footer's background — this is the specific thing to look at, not to skim past.

3. Click **Terms and Conditions**. You land on the terms document. Click **Privacy Policy** from
   that page's own footer. You land on the privacy document. Both pages carry the footer
   themselves.
4. Repeat step 1's checks on `/courses/` (all courses) and on a course's detail page,
   e.g. `/courses/functionality-demo-course-parts/detail/`.

**Short-page check (this is where it is most likely to look wrong):** find a page whose content does
not fill the window — the dashboard for a learner with one course, or `/courses/` filtered down, or
just widen the browser to a short height. The footer is in normal document flow and is *not* pinned
to the bottom of the viewport, so on a short page it will sit directly under the content with empty
space beneath it. Confirm this looks deliberate rather than broken. If it reads as a bar stranded in
the middle of the screen, say so in the QA report — it is a real finding even though it is not a
functional failure.

## §2 Anonymous visitors

1. Open a private window and go to the base URL without logging in.
2. Go to `/courses/` and to the login page.

Expect: the same full footer on every one of them, with both legal links working. The footer does
not depend on being signed in, so an anonymous visitor who needs the privacy policy can reach it.

## §3 The compact footer on the sidebar shell

1. As the learner, open a course topic:
   `/courses/functionality-demo-course-parts/1/`.
2. Scroll to the very bottom of the page.

Expect:

- A short bar, noticeably tighter and in smaller type than §1's, with the same copyright line and
  the same two links in the same order.
- It spans the full width *under* the whole grid, including under the sidebar column — that is
  intended.
- The desktop sidebar is a sticky full-height column, so reaching the footer means scrolling past
  it. Note roughly how much scrolling that takes; if it feels unreasonable, record it.

3. Click both links from here and confirm they reach the same two documents as in §1.
4. Log in as the admin and open the educator interface (the **Educator Interface** item in the
   header user menu). Confirm the same compact bar appears at the bottom there.

## §4 The exam and form runner has no footer

1. As the learner, open the course with a quiz and start the form. From
   `/courses/functionality-demo-show-end-with-quiz/` work through to the form, or go to a form item
   and start it.
2. Once in the runner (the page with its own top bar and a sticky action bar along the bottom):

Expect:

- **No footer at all.** No copyright line, no legal links.
- The sticky action bar is still flush with the bottom of the window, not pushed up, not clipped,
  and nothing is peeking out below it.
- Scrolling the question area does not reveal a footer underneath.

3. Submit the form and land on the completion page. That page is *not* the runner, so it **does**
   have the compact footer. Confirm it is back.

## §5 Error pages have no footer

1. Go to `/no-such-page-at-all/`. You get the "We cannot find that page" 404.

Expect: no footer. The page ends with its own buttons.

2. If you can reach them, check the 403 ("You do not have access to this page") and the 429
   ("You have made too many attempts") pages the same way. The 429 is reachable by failing the
   login form repeatedly from a private window — be aware that this locks the account out, so use
   a throwaway email rather than the seeded learner.
3. Leave `500.html` and `503.html` alone. They were never part of this change and should be
   untouched.

## §6 The landmark check

This is the reason the footer sits where it does, so verify it rather than assume it.

On the dashboard, in the browser's DevTools console:

```js
document.querySelectorAll('footer').length                 // 1
document.querySelector('main').contains(document.querySelector('footer'))  // false
document.querySelectorAll('[role="contentinfo"]').length   // 0
```

Then open the Accessibility pane (Chrome DevTools → Elements → Accessibility, or Firefox's
Accessibility panel) and confirm the `<footer>` is reported as **contentinfo**, not **generic**. If
it reads `generic`, the element has ended up inside `<main>` and the whole point of the feature is
lost — this is the single highest-value check in this document.

Repeat the three console lines on a course topic page (§3) and confirm the same results. Then run
them on the runner page (§4) and expect `0` footers there.

## §7 Keyboard and focus

1. On the dashboard, press Tab repeatedly until focus reaches the footer links.

Expect:

- Both links are reachable by keyboard, in the order they read.
- The focus indicator is clearly visible **against the footer's background** — not washed out the
  way it might be if the footer colour and the ring colour were too close.
- Enter activates the focused link.

2. With a screen reader if one is available (VoiceOver rotor, NVDA landmark list), confirm the
   footer is announced as a `contentinfo` landmark and the links group is announced as a navigation
   named "Legal" — distinct from the header's navigation and from any breadcrumb navigation on the
   page.

## §8 Responsive

1. Resize the window to about 400px wide (or use DevTools device emulation, iPhone SE).
2. Visit the dashboard, a course topic page, and a legal document page.

Expect:

- The copyright line and the two links wrap onto separate lines rather than being cut off or
  squashed.
- No horizontal scrollbar appears on any of them.
- The links are still comfortably tappable — each one is a reasonable finger-sized target, not a
  hairline of text.
- On the course topic page at this width the sidebar is a modal sheet rather than a column, so the
  compact footer should now sit directly under the content.

## §9 Side effects to look for

These are the places the footer could break something that already worked.

1. **Boosted navigation in the course player.** On a course topic page, use the sidebar to move
   between several items. The player swaps `#interface-main` rather than reloading the page.
   After each move, scroll to the bottom and confirm there is still **exactly one** footer — not
   two stacked, not zero. Re-run `document.querySelectorAll('footer').length` in the console after
   a few swaps.
2. **The debug badge.** In development a small branch-name badge is fixed at `bottom: 10px;
   left: 10px`, which is now on top of the footer. Scroll to the bottom of the dashboard and
   confirm the badge does not cover the copyright line or either link, and that clicking where the
   badge sits does not steal a click meant for a link. At 400px width the badge moves to
   `bottom: 4px; left: 4px` — check there too.
3. **The sticky header.** Scroll up and down a long page and confirm the header still sticks to the
   top and still gains its scrolled shadow. The footer should have changed nothing about it.
4. **Toast messages.** Visit `/qa/toasts/playground/` (DEBUG-only, admin) and
   `/qa/toasts/full/`. Confirm the message banners still appear where they did and are not pushed
   or overlapped by the footer.
5. **The mobile sidebar sheet.** On a course topic page at 400px, open the sidebar sheet. Confirm
   the footer does not show through the sheet's backdrop in a way that looks broken, and that
   closing the sheet leaves the footer intact.
6. **The modal and the media card.** Open any dialog that has a footer slot of its own (a modal
   with actions along its bottom, or a media card with a caption bar). Confirm those component
   footers are unchanged and that the page's own footer has not inherited their styling or vice
   versa — the two are unrelated and must stay that way.
7. **A very long legal document.** Open the terms page and scroll to the end. The footer should
   follow the document content normally, with no overlap of the last paragraph.

## §10 The other theme

The default theme is only half the shipped surface.

```
# stop the server, then:
FLS_THEME=first_class npm run tailwind_build
FLS_THEME=first_class uv run python manage.py runserver $PORT
```

Repeat §1 (full footer on the dashboard) and §3 (compact footer on a course topic page).

Expect: the footer picks up the `first_class` surface and text colours. Pay particular attention to
the copyright line's contrast against the footer background — this theme's muted grey is too low
contrast for text at this size, so if the copyright line looks washed out or grey rather than the
same dark body colour the rest of the page uses, that is a bug and should be reported.

Afterwards, rebuild for the default theme (`npm run tailwind_build`) so the working tree's compiled
bundle is not left on the wrong theme.

## §11 A downstream override

The whole reason for the feature is that a project can replace the footer without forking
`_base.html`. Prove the seam works.

This repo's `TEMPLATES["DIRS"]` starts empty; the only filesystem directory on it is the active
theme's `templates/`, which `configure_theme` prepends **at startup** if the directory exists. So
the override is exercised through the theme path here, and the server has to be restarted for it to
take effect.

1. Create `freedom_ls/themes/default/templates/partials/footer_bar.html` containing something
   obviously different, e.g. `<footer><p>OVERRIDE WORKS</p></footer>`.
2. Restart the dev server. (Neither shipped theme has a `templates/` directory today, so the
   directory is new and only a restart puts it on `DIRS`.)
3. Reload the dashboard, and a course topic page.

Expect: the override renders instead of FLS's footer on both shells, with no change to
`_base.html` — one partial replaced, the page shell untouched. That is the feature.

4. **Delete `freedom_ls/themes/default/templates/` entirely** and restart again before finishing.
   It is scratch; leaving it behind would change every page and would show up as an unwanted file in
   the diff.

Note for the report, not a bug: a template tree outside `freedom_ls/` is not covered by the Tailwind
`@source` globs, so Tailwind classes in a downstream override compile to nothing until that project
adds a glob of its own. If your override in step 1 uses Tailwind classes and they do nothing, that
is this pitfall, not a footer failure.
