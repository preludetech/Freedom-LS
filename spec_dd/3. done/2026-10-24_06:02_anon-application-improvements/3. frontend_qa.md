# Frontend QA: anonymous application improvements

An anonymous applicant on a course with an application form now gets the claim email as soon as
they give their address, not when they submit. Every form page carries a notice naming the
address with "Send the link again" and "Wrong address? Change it". The emailed link works on a
draft and signs the applicant in on it, in any browser. After submitting, the status page lets
them change the address, which kills every earlier link. The dashboard and the course page show
an anonymous session's own drafts. This run walks those flows and the ways they could go wrong:
reposting details, a stale link after an address change, a claim that collides with an account's
existing application, another browser trying to reach a draft, a verified application that must
refuse the change form, and the form-less course that must keep today's behaviour.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

Rate limits cannot be checked here: `settings_dev.py` turns `ACCOUNT_RATE_LIMITS` off. They are
covered by the test suite.

## §0 Setup

### 0.1 Server and mail

1. `.claude/ds/scripts/find_available_port.sh`: note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `anon-application-improvements` branch. If it names another branch, another server holds the
   port; go back to step 1.
4. Dev email goes to Mailpit. Open `http://localhost:8025/` and confirm the inbox loads. If it
   does not, start the dev containers (`dev_db/docker-compose.yaml`) before continuing. Clear the
   inbox before §1 so counts below start at zero.

### 0.2 Seed data

Every item below must exist before §1. Missing data is created through the
`fls-dev:qa-data-helper` agent, never by hand. The names are fictional.

1. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
2. **Form course:** the demo course "Functionality Demo - Application gated course" (slug
   `functionality-demo-application-gated-course`), loaded from `demo_content/`, whose application
   form has pages About you, Supporting documents and Availability.
3. **Second form course:** a copy of the first with another title and slug (the QA data helper
   can clone it as `qa-second-gated-form-course`, "QA Second Gated Form Course"), so one session
   can hold two drafts.
4. **Form-less course:** `QA Application-Gated Course (Access Types)` (slug
   `qa-application-gated-course-access-types`) from `qa_create_course_access_types`, with no
   application form.
5. **Signup policy** for the dev site: `require_name=True`, `require_terms_acceptance=True`,
   `allow_signups=True`.
6. **Existing account with a submitted application:** `qa_held_submitted@email.com`, password
   equal to the address, active, email verified, holding a **submitted** application to the first
   form course (the QA data helper completes the sitting).
7. **Existing account with a draft:** `qa_held_draft@email.com`, same shape, holding an
   **unfinished** draft application to the first form course.
8. **No** `AnonymousApplicant` and no `CourseApplication` for: `qa_early@email.com`,
   `qa_early_fixed@email.com`, `qa_change_a@email.com`, `qa_change_b@email.com`,
   `qa_two_drafts@email.com`, `qa_formless@email.com`, `qa_claim_draft@email.com`,
   `qa_held_submitted@email.com` (beyond item 6), `qa_held_draft@email.com` (beyond item 7).
9. A small PNG on disk to upload (any file under 1 MB).

Use a fresh browser context (no cookies) for every section that starts anonymous. Call that the
*anonymous browser*. Mailpit is read in a second tab. "The link in the email" means the
`Continue your application` or `Finish your application` link, whose URL starts with `/claim/`.

## §1 Early email and the claim link notice

### 1.1 The details step sends the email and page 1 shows the notice

1. In the anonymous browser open
   `http://127.0.0.1:<PORT>/courses/functionality-demo-application-gated-course/` and click
   "Apply now".
2. On "Your details" enter `qa_early@email.com`, first name `Early`, last name `Bird`, tick both
   consent boxes, click Next.
3. Expect page 1 of the form (heading "About you"). Expect a callout under the heading, with an
   info tint, reading "We've emailed a link to qa_early@email.com so you can come back to this
   application. Carry on here.", a "Send the link again" button and a "Wrong address? Change it"
   link.
4. In Mailpit expect exactly one new message to `qa_early@email.com`, subject "Continue your
   application for Functionality Demo - Application gated course". Open it: the body says the link
   takes them back to their application and confirms their email address; the button reads
   "Continue your application"; nothing says the application was received or will be reviewed.
5. Reload page 1. The notice is still there with the same wording (it reads the database, not a
   one-shot flag).
6. Click page 2 in the page navigation, then the check-your-answers link if offered (or reach it
   through the form's Next buttons after answering the required name). Expect the notice on every
   form page and on "Check your answers".

### 1.2 A name-only repost sends nothing; a changed address sends once to the new one

1. Click "Wrong address? Change it". Expect the "Your details" step with the three fields filled
   (`qa_early@email.com`, `Early`, `Bird`).
2. Change only the last name to `Worm`, click Next. Expect page 1 again. In Mailpit expect **no**
   new message (still one).
3. Click "Wrong address? Change it" again. Change the email to `qa_early_fixed@email.com`, click
   Next. Expect page 1 with the notice now naming `qa_early_fixed@email.com`.
4. In Mailpit expect exactly one new message, to `qa_early_fixed@email.com`, with the draft
   subject. Nothing new went to `qa_early@email.com`.
5. Open the **first** email (to `qa_early@email.com`) and follow its link in a third, fresh browser
   context. Expect "This link is invalid or has already been used". Close that context.

### 1.3 Resend from the notice on a draft

1. Back on page 1 in the anonymous browser, click "Send the link again".
2. Expect a success toast "We've emailed a link to qa_early_fixed@email.com." and to be back on
   the form page (page 1, the form state intact).
3. In Mailpit expect one more message to `qa_early_fixed@email.com` (two to that address now).
4. Open the **earlier** of the two `qa_early_fixed@email.com` emails and follow its link in a fresh
   context. Expect the confirm page "Continue your application for Functionality Demo -
   Application gated course" (a plain resend does not invalidate earlier links). Do not press
   Confirm. Close that context.

### 1.4 Submitting sends no email

1. In the anonymous browser fill in the required questions on each page (answer "Your name" or
   the equivalent required field; upload the PNG where asked if required), reach "Check your
   answers" and click "Submit application".
2. Expect the status page "Your application". In Mailpit expect **no** new message.
3. Expect the status page to say the link was sent to `qa_early_fixed@email.com`, with "Send the
   email again" and, below it, a change-of-address form with one email field and a button
   "Change address and send the link". Expect no wording that says the email was sent on
   submission.

## §2 Claiming a draft

### 2.1 The emailed link signs a second browser in on the draft

1. Fresh anonymous browser. Apply to the first form course with `qa_claim_draft@email.com`, first
   name `Claim`, last name `Draft`, consents ticked. On page 1 answer the required name question
   and click Next so the draft is on page 2. Leave this browser open.
2. In Mailpit open the email to `qa_claim_draft@email.com` and follow its link in a **fresh
   browser context** (call it the *claiming browser*).
3. Expect the heading "Continue your application for Functionality Demo - Application gated
   course", the sentence naming `qa_claim_draft@email.com`, and the line about choosing a password
   (no account exists yet). Expect no mention of review. Expect nothing in the database changed
   yet: reloading the page shows the same confirm state.
4. Click Confirm. Expect the set-password page. Set a password (use the address as the password
   per the dev convention) and submit.
5. Expect to land on the form, on the page the draft was left at (page 2), signed in: the header
   shows the account menu, and the claim link notice is **absent** (the address is verified).
6. Open `http://127.0.0.1:<PORT>/` in the claiming browser. Expect the greeting "Welcome back,
   Claim" and the "Your applications" panel listing the course as "Incomplete" with "Continue
   application".
7. Back in the original anonymous browser, reload the form page. Expect to be sent to the login
   page (the origin session no longer owns the draft).
8. Open the same claim link once more in a fresh context. Expect "This link is invalid or has
   already been used".

### 2.2 Admin shows the claimed draft

1. In a browser signed in as `demodev@email.com`, open `/admin/` and the Course applications
   changelist. Filter by "email verified: Verified". Expect `qa_claim_draft@email.com` with
   Submitted unticked (a verified draft is now possible).

## §3 Changing the address after submitting

### 3.1 A valid change kills the old link and emails the new address

1. Fresh anonymous browser. Apply to the first form course with `qa_change_a@email.com`, first
   name `Change`, last name `Address`, fill the form through to "Check your answers", submit.
2. On the status page type `qa_change_b@email.com` into the change-of-address field and click
   "Change address and send the link".
3. Expect the status page again with a success toast "We've emailed a link to qa_change_b@email.com."
   and the page now saying the link was sent to `qa_change_b@email.com`.
4. In Mailpit expect one new message, to `qa_change_b@email.com`, subject "Finish your application
   for ..." (submitted wording). Nothing new to `qa_change_a@email.com`.
5. Follow the link in the earlier email to `qa_change_a@email.com` in a fresh context. Expect
   "This link is invalid or has already been used".
6. Follow the link in the `qa_change_b@email.com` email in a fresh context. Expect the confirm page
   "Finish your application for ...". Do not confirm.

### 3.2 Unchanged, invalid and empty addresses

1. Back on the status page, submit the change form with `QA_Change_B@email.com` (same address,
   different case). Expect the status page, no toast, and in Mailpit no new message.
2. Submit the change form with `not-an-address`. Expect the status page re-rendered with an error
   under the field ("Enter a valid email address."), no toast, no new message. Open the browser's
   network panel or re-submit while watching it: the response status is 422.
3. Submit the change form with the field empty. Expect a required-field error, 422, no email.

### 3.3 The change form is refused where it must be

1. In a fresh context open the status URL of the §3.1 application directly. Expect the login page
   (another session does not own it).
2. Sign in as `qa_held_submitted@email.com` and open its own status page
   (`/status/<pk>/` from the dashboard's "Your applications" panel). Expect **no** change-of-address
   form and no "Send the email again": the account's address is verified.
3. Still signed in, POST to `/status/<pk>/change-email/` for that same application with a form
   tool or `curl` carrying the session cookie and CSRF token, email `qa_change_b@email.com`. Expect
   404.
4. In the anonymous browser from §3.1, open `/status/<pk>/change-email/` with a GET. Expect 405.

## §4 Collisions at claim time

### 4.1 Held submitted, incoming draft

1. Fresh anonymous browser. Apply to the first form course with `qa_held_submitted@email.com`,
   first name `Held`, last name `Submitted`, consents ticked. Stop on page 1.
2. In Mailpit open the email to `qa_held_submitted@email.com` and follow the link in a fresh
   context.
3. Expect the confirm page with the extra sentence "You've already applied for Functionality Demo
   - Application gated course. This unfinished application will be discarded." and the sentence
   that they will be signed in (no password step, the account is verified).
4. Click Confirm. Expect to land on the status page of the account's **submitted** application
   ("Your application ... pending review"), signed in as `qa_held_submitted@email.com`.
5. In admin, the Anonymous applicants changelist has no row for `qa_held_submitted@email.com`
   (the discarded draft and its applicant are gone), and Course applications shows one application
   for that address.

### 4.2 Held draft, incoming draft

1. Fresh anonymous browser. Apply to the first form course with `qa_held_draft@email.com`, first
   name `Held`, last name `Draft`. On page 1 answer the required name with `Incoming Draft` and
   click Next.
2. Follow the emailed link in a fresh context. Expect the confirm page with "This replaces the
   unfinished application for Functionality Demo - Application gated course already on your
   account."
3. Click Confirm. Expect to land on the **incoming** draft (page 2, or wherever it was left), signed
   in as `qa_held_draft@email.com`. Navigate to page 1: "Your name" reads `Incoming Draft`.
4. On the dashboard, "Your applications" lists the course once, as Incomplete.

### 4.3 Login adoption keeps the held submission and says so

1. Fresh anonymous browser. Apply to the first form course with `qa_held_submitted@email.com`
   again (a new draft). Stop on page 1.
2. In the same browser open `/accounts/login/` and sign in as `qa_held_submitted@email.com`.
3. Expect an info toast "You had already applied for Functionality Demo - Application gated
   course, so that application was kept." and the dashboard showing that one application as
   pending review. The draft is gone from admin as in §4.1 step 5.

### 4.4 Login adoption replaces the held draft and says so

1. Through the QA data helper, give `qa_held_draft@email.com` a fresh **unfinished** draft to the
   first form course again (the §4.2 claim replaced the earlier one), with the name answer
   `Account Draft`.
2. Fresh anonymous browser. Apply to the first form course with `qa_held_draft@email.com`; on
   page 1 answer the name with `Session Draft` and click Next.
3. In the same browser open `/accounts/login/` and sign in as `qa_held_draft@email.com`.
4. Expect an info toast "Your unfinished application for Functionality Demo - Application gated
   course was replaced by the one you just started." The dashboard lists the course once as
   Incomplete; opening it, page 1 reads `Session Draft`.

## §5 Drafts on the anonymous dashboard and course page

### 5.1 Two drafts, newest first, nothing personal in the page

1. Fresh anonymous browser. Apply to the first form course with `qa_two_drafts@email.com`, first
   name `Two`, last name `Drafts`; stop on page 1. Then open the second form course's page
   (`/courses/qa-second-gated-form-course/`), click "Apply now". Expect to land on "Your details"
   with the fields empty (one applicant per course), fill the same address and name, click Next;
   stop on page 1.
2. Open `http://127.0.0.1:<PORT>/`. Expect the anonymous hero **and** a "Your applications" panel
   with two rows, the second course first, each marked "Incomplete" with a "Continue application"
   button.
3. View the page source (or search the DOM): neither `qa_two_drafts@email.com` nor `Two` nor
   `Drafts` appears anywhere in the page.
4. Click "Continue application" for the first course. Expect page 1 of that course's form.

### 5.2 Course page CTA

1. Open `/courses/functionality-demo-application-gated-course/` in the same browser. Expect the
   call to action to read "View my application"; clicking it lands on the draft's form page.
2. Open `/courses/qa-application-gated-course-access-types/` (the form-less course, not applied
   to). Expect "Apply now".
3. In a fresh context open the dashboard. Expect the hero and **no** "Your applications" panel.
4. In the same fresh context open the first form course. Expect "Apply now".

### 5.3 A submitted application leaves the anonymous dashboard

1. In the §5.1 browser, finish and submit the first course's application. Open the dashboard.
   Expect only the second course's draft in the panel.
2. Open the first course's page. Expect "View my application" still, landing on the status page.

overflowing the callout.
