# Research: codebase (organisation-courses)

Question: what in the existing codebase does this work touch, reuse or conflict with?
Vocabulary follows `.claude/skills/domain-glossary/SKILL.md` (British "organisation"; `Learner` = a user's association with one organisation; "registration" not "enrolment").

## 1. Headline findings

1. **`Organisation` already exists** (`freedom_ls/organisations/models.py:58`, label `freedom_ls_organisations`). Grep for "organization" (US spelling) finds nothing in code; only the British form is used. No new organisation model is needed.
2. **`Course` has deliberately no organisation link today.** Codified in prose: `qa_register_org_course.py` docstring ("A Course has no Organisation FK of its own"), glossary line on `peers_of` ("a course is not owned by one"), `educator_interface/views.py:1360` and `:1518` ("Courses are shared across the site"), `educator_interface/tests/invariants/test_organisation_isolation.py:423` ("Courses are shared across organisations"), and `learner_management/queries.py:758`. This feature reverses that premise for some courses, so those comments and the invariant test will need to be reconciled (do not delete; amend where the new many-to-many changes the truth).
3. **A course-to-organisation relationship is currently derived from registrations**, not stored: `organisation_for_learner_course(user, course)` (`learner_management/queries.py:206`) via `learner_for_course` (`:161`). It returns the organisation the learner is studying that course through (cohort registration wins over individual; individual tie-break `latest_registration` `:132`). This is the existing seam for "in-progress card shows organisation info".
4. **An organisation chip already exists for the course player**: `learner_interface/templates/learner_interface/partials/course_organisation_chip.html`, included by `course_toc_header.html`; context var `course_organisation` built in `_player_chrome_context` (`learner_interface/views.py:1131-1193`) from `course_progress.learner.organisation`. It renders nothing for the site's default organisation (`is_default`). It is a vertical, centred, logo-or-monogram + name stack in the player sidebar; it is NOT sized for a dashboard card and carries a fixed `id="course-organisation-chip"` (duplicate ids if reused repeatedly in a list). Reuse the data conventions (logo, `initials`, `is_default` rule), probably not the template as-is.
5. **Course slug uniqueness will not block "same name" courses.** `Course` is unique on `(site, slug)` (`content_engine/models/courses.py:253-260`), but the content loader derives slug from `slugify(title)` then `get_unique_slug` (`site_aware_models/slugs.py:32`) appends `-2`, `-3`... (`content_save.py:307-310`). Two org versions titled identically load fine as `foo` and `foo-2`. Consequence: URLs (`course_detail`, `course_home`, etc. keyed by `course_slug`) differ by an arbitrary suffix, and which version gets the clean slug depends on load order. There is no title uniqueness constraint. `file_path` is not unique either; identity is the frontmatter UUID (`update_or_create(id=uuid, site=site)`), so each version must be its own course.md with its own UUID (copying a file without clearing the UUID would overwrite, not duplicate).

## 2. Existing organisation model and relations

- `Organisation(SiteAwareModel, TimestampedModel)`: `name`, `slug`, `logo`, `logo_on_dark`, `is_default`, `initials` property. Unique `(site, slug)`, `(site, name)`, one default per site. Logo storage via `ORGANISATION_LOGO_STORAGE_ALIAS` (public bucket). `Organisation.logo.url` is what templates use.
- `organisations/utils.py` has `get_default_organisation(site)`; every Site gets a default organisation via post_save receiver (`organisations/signals.py`).
- Learner side (`learner_management/models.py`): `Learner` (user, organisation, `is_active`; unique `(site, user, organisation)`), `OrganisationMember`, `Cohort.organisation` (FK, `:35`), `CohortMembership.clean()` forbids cross-organisation membership, `LearnerCourseRegistration` (learner, course, `is_active`, `self_registered`; unique `(site, learner, course)`), `CohortCourseRegistration` (cohort, course). Registrations carry no organisation field of their own; it comes via `learner.organisation` or `cohort.organisation`.
- A user can hold several `Learner` rows (one per organisation) and may therefore hold registrations for the same course through two organisations; listings already resolve "the one they are studying through" (`course_progress_by_course_for`, `learner_progress/queries.py:185`).
- Reverse relationships for the new link: `hr_attributes.OrganisationHRSettings` is a one-to-one on Organisation (precedent for an optional-app extension); `messaging_policy.OrganisationMessagingConfig` likewise.

## 3. Where courses are made visible / listed to learners

All discovery paths start from `Course.objects` (site-aware manager) with no organisation filter:

- `learner_interface/utils.py:801 get_all_courses()` returns `Course.objects.all()`. Used by `_discovery_courses` (`views.py:283`), `all_courses` (`views.py:649`), `get_course_listing` fallback (`utils.py:953`).
- Visibility filtering is delegated to the access backend: `backend.filter_visible(user=, courses=)`. `VisibilityEnforcingBackend.filter_visible` (`course_access/backends.py:468`) wraps whichever backend `COURSE_ACCESS_BACKEND` names (loader: `course_access/loader.py` `get_course_access_backend`, cached, always wrapped). It currently excludes HIDDEN courses for unregistered users and delegates to the inner backend's `filter_visible` (the documented seam: "a future backend that hides courses a learner genuinely cannot reach"). Anonymous users flow through it too.
- Direct slug chokepoints that do NOT go through `filter_visible`: `course_detail` (`views.py:702`), `course_home` (`:816`), `initiate_course_access` (`:847`), `_course_access_redirect` (`:920`), the player views. They use `get_object_or_404(Course, slug=...)` plus `raise_404_if_hidden_unregistered` (`course_access/visibility.py:20`). An organisation restriction enforced only in listings would leave course pages reachable by slug; any "available only to certain organisations" rule needs a decision about these chokepoints (404 like HIDDEN? CTA change?).
- Dashboard (`dashboard`, `views.py:616`): `_dashboard_inputs` builds `registered_courses` (via `get_current_courses`, `utils.py:859`), `completed_courses`, `recommended_courses` (`_visible_recommendations`, filters via `filter_visible`), and `coming_soon`/`rest` discovery querysets. Sections: In progress, category sections, Recommended, Available, Coming soon, Learning history. Annotation helpers stamp attributes onto Course instances: `_annotate_registered_courses`, `_annotate_discovery_courses`, `_annotate_recommendations`, `_annotate_completed_courses`.
- `get_course_registrations(user)` (`utils.py:355`) = every course the user is registered for via `is_registered_for_course_expression` (`learner_management/queries.py:91`). Registered-for exempts HIDDEN/COMING_SOON visibility; a similar exemption (already registered learner keeps access) is the established pattern and would apply equally to an organisation restriction.
- Other listing consumers of courses: `course_recommendations/queries.py` (`RecommendedCourse` keyed on `User`, not `Learner`; roadmap notes it is unresolved how org-owned rules scope it), `course_interest`, `registration_rules/evaluation.py` (creates `LearnerCourseRegistration` rows directly, per organisation), `educator_interface` (below), `reports`.
- Educator side: `courses_visible_to(user, organisation)` (`learner_management/queries.py:321`) returns every PUBLISHED course plus registered ones; `registerable_courses_for(cohort)` / `registerable_courses_for_learner(learner)` (`:355`, `:364`, via `_registerable_courses` `:347`) feed the registration forms (`educator_interface/forms.py:66,86`) and `educator_interface/filters.py:64`. An organisation-restricted course should presumably be registerable only into the organisations it is linked to (cohort/learner organisation known there), and the educator course lists scoped by the viewed organisation. These are the second-most-relevant touch points after the learner listings.

## 4. Course cards (cotton) and card data

- Dashboard card: `learner_interface/templates/learner_interface/partials/course_card.html` (documents required context on the `course` object: `listing_status`, `slug`, `accent_slot_key`, `icon`, `icon_fallback`, `title`, `progress_percentage`, `next_up_url`, `next_up_title`, `access_badge`, `current_price`). Branches on `course.listing_status` (`CourseListingStatus` in `utils.py:103`): `not_registered`, `coming_soon`, `registered`, `in_progress`, `complete`.
- Shell: `learner_interface/templates/cotton/course-card-shell.html` (`<c-course-card-shell>`; slots: `eyebrow`, default body `slot`, `footer`). Row variant `course-row-shell` is used by the all-courses list and by the markdown embed card.
- Markdown embed card: `cotton/course-card.html` (`<c-course-card path=...>`), uses `templatetags/course_card_tags.py` (`get_course_by_path` uses `Course._base_manager` for the content's site, excluding HIDDEN; `course_access_badge` filter). It lists a course by file path in course markdown with no user context; it would not know a viewer's organisation and would show org-scoped courses to everyone unless handled. Tested by `learner_interface/tests/demo_content/test_course_card.py` and `tests/templatetags/test_course_card_tags.py`.
- Data is stamped onto Course instances in view helpers (setattr with `# noqa: B010`), not via the template calling queries. An organisation for a card should follow that pattern (stamped by the annotate helpers, with prefetch/select_related so the dashboard doesn't gain per-card queries; project rule: select_related/prefetch_related for related-object queries).
- Two different organisation data sources are needed by the two card cases in the idea:
  - In-progress (and arguably registered/complete) cards: the organisation the learner is studying through. Available cheaply: `course_progress_by_course_for` already returns the winning `CourseProgress` per course with `select_related("learner", "course")` (note: only `learner`, NOT `learner__organisation`, in the bulk resolver at `learner_progress/queries.py:268`; the single-course `course_progress_for` does include `learner__organisation`). Adding `learner__organisation` to the bulk select_related is the likely hook. `get_current_courses` (`utils.py:859`) already has the winning record in hand per course (it stamps `progress_percentage`, `started_at`, `last_accessed_time`, `registered_at` from it).
  - Not-registered/discovery cards for a course scoped to exactly one organisation: the organisation comes from the new course-to-organisation link, not from a registration. "scoped to a single organisation" implies the many-to-many has cardinality 1 for that course; with 2+ organisations (or none) no organisation info is shown per the idea.
- `CourseListingStatus` / `CourseListingEntry` (`utils.py:103-120`) and `stamp_course_access_badge` (`:148`) are the existing patterns for carrying per-course display data into the listing (`all_courses.html`, `course_list.html`). The all-courses page (`all_courses` view) reuses the card; the idea only names the dashboard and in-progress cards, so confirm in the spec whether the all-courses list is in scope.

## 5. Course access backends and applications (do not change)

- `COURSE_ACCESS_BACKEND` setting read via `freedom_ls/course_access/config.py`; protocol in `course_access/backends.py` (`CourseAccessBackend`, `CourseAccessDecision`, `AccessBadge`, `FreeOnlyCourseAccessBackend`, `VisibilityEnforcingBackend`). Core `Course.access_config` is explicitly BACKEND-PRIVATE; no view/template/utility may read it (`courses.py:158` comment). So an organisation restriction must not be encoded in `access_config`.
- `course_applications/backends.py` (`ApplicationCourseAccessBackend`) extends the free backend; `course_applications` has zero references to organisations (grep is empty). The idea says leave applications alone. Note: the later step ("actually get added to an organisation course later") implies approval/registration will have to target an organisation-specific course version, but that is out of scope. Constraint: do not touch `course_applications/*`; the new filtering must work with an application-gated course unchanged.
- Self-registration path conflict: `initiate_course_access` (`views.py:885-906`) registers the learner on the Site's DEFAULT organisation (`ensure_learner(request.user, get_default_organisation(site))`). For an organisation-scoped course that is wrong or at least at odds: a learner self-registering would be associated with the default organisation, not the course's organisation. The idea only requires showing org info on cards and restricting availability, but the spec must say how (or whether) free self-registration into an organisation course behaves (probably: such a course is not self-registerable, or registers through the course's single organisation). This is a design decision, not a given.
- Seam options for the restriction, all already accommodated by the architecture: (a) core `filter_visible` in `VisibilityEnforcingBackend` (always applied regardless of configured backend, like HIDDEN), (b) a queryset helper in `learner_management/queries.py` used by `get_all_courses`/`_discovery_courses`. (a) matches "no backend can bypass" intent; the wrapper already imports `is_registered_for_course_expression` from `learner_management`, so it can import a new organisation-aware expression from the same module without a new app edge.

## 6. Site-aware models and app boundaries (hard constraints)

- Models: `SiteAwareModel` (`site_aware_models/models.py:165`, UUID pk + site FK, `SiteAwareManager` auto-filters by the thread-local request site), `SiteAwareModelBase`. Any new through model should subclass `SiteAwareModel`; use `_base_manager` when crossing sites (patterns throughout, e.g. `ensure_learner`).
- **Dependency graph (`docs/app_structure.md`, enforced by a generator/check; see `tests/test_generate_app_map.py`)**:
  - `content_engine` depends on: base, content_base, form_engine, icons, markdown_rendering, site_aware_models. It has NO edge to `organisations`.
  - `organisations` depends on: base, site_aware_models. It has no edge to `content_engine`.
  - `learner_management` depends on both `content_engine` and `organisations` (`:277`), and already holds `LearnerCourseRegistration`/`CohortCourseRegistration` with FKs to `Course` and `Organisation`.
  - `course_access` depends on content_engine and learner_management; `learner_interface` depends on organisations, content_engine, course_access, learner_management.
  - Implication: a `ManyToManyField("freedom_ls_organisations.Organisation")` directly on `Course` (content_engine) would add a new `content_engine --> organisations` edge (and `docs/app_structure.md` plus the dependency checks would need updating, and arguably it inverts layering since organisations is "above" content). Placing the link model (e.g. a `CourseOrganisation` through/link row) in `learner_management` (which already sees both) or in `organisations` (new edge organisations --> content_engine) avoids touching content_engine. This is an open design choice the spec must make; the lowest-friction place by the current graph is `learner_management`.
- Project rule from CLAUDE.md: generic plugins (`claude_plugins/django-stack`, `claude_plugins/sdd`) must not receive FLS-specific content; this spec/plan must not require that.
- Existing precedent for admin-only (non-content) course attributes: `CourseCategory` is content-declared; `RecommendedCourse` and `LearnerCourseRegistration` are DB-only; `Course.application_form` is a DB FK populated by a loader binding pass from an `access_config` key (`content_save.py` binding pass after `save_course`). So both models exist: content-declared and DB/admin-managed.

## 7. Content loading: can the link be expressed in content?

- Course frontmatter schema: `freedom_ls/content_engine/schema.py` `Course` (pydantic, `extra="forbid"` on CoursePart; Course extends the base schema; fields incl. categories, dashboard_category, icon, learning_outcomes, difficulty, visibility, access_config, price). Loader: `content_engine/management/commands/content_save.py` (`save_with_uuid` `:~250`, `save_course` `:521`, `save_content_to_db` `:830`), validated by `content_validate` / `content_engine/validate.py`, and the external authoring plugin `claude_plugins/fls-content` (`validate/schema.py`, `validate/validate.py`, `skills/content-types/resources/course-files.md`). `save_with_uuid` raises `ValueError` if a frontmatter field is not a model field, and `Organisation` is a per-Site DB row, not content.
- Content is repo-based and site-agnostic (`demo_content/*/course.md`, 13 courses, none with organisation data); `content_save` takes a site name. Organisations are created in the DB/admin, not in content (`qa_create_organisations`, `create_demo_data`). A content-level reference would have to be by organisation slug or name and resolved at load per site, mirroring how `dashboard_category` slugs resolve to `CourseCategory` rows (`save_course` errors on unknown slug) and how `application_form` paths bind in a second pass. Risks: a loader that re-saves a course and wipes DB/admin-assigned links (the `tags` and `price` handling in `save_with_uuid`/`save_course` is the precedent: absent key leaves stored value alone). If the link is DB/admin-only, no schema/loader/fls-content plugin changes are needed and the m2m survives content reloads; the m2m assigned in admin would need the through model registered in `CourseAdmin` (`content_engine/admin.py:160`, `SiteAwareModelAdmin`) or `OrganisationAdmin` (`organisations/admin.py`).
- The idea says each org version is a completely independent course (own content). In the content repo that means separate course directories/files with distinct UUIDs sharing a title. Nothing in the loader needs to know they are related.
- A schema change to Course frontmatter also triggers the `claude_plugins/fls-content` mirror (generic-plugin rule: that plugin is FLS content tooling, so a schema addition belongs there, but check `.claude` skill for content-types before extending).

## 8. Educator interface and other organisation-aware surfaces

- `educator_interface` is organisation-scoped (`organisations_accessible_to`, organisation switcher, `scoped.organisation`); course list/matrix uses `courses_visible_to` (`learner_management/queries.py:321`); register forms use `registerable_courses_for*`. See §3 for the likely changes; the idea does not mention the educator interface, so scope is a spec decision, but leaving it unchanged would let an organisation admin register learners into another organisation's private course (data-isolation gap vs "available only to certain organisations").
- `reports`, `registration_rules`, `messaging_policy`, `hr_attributes` all key off Organisation and registrations; none read a course-level organisation. `registration_rules/evaluation.py` creates registrations with `LearnerCourseRegistration._base_manager` in bulk and may need to respect the restriction.
- `qa_helpers` has commands for org + course scenarios (`qa_register_org_course.py`, `qa_create_organisations.py`, `qa_create_rich_dashboard_learner.py`, `qa_create_dashboard_paging_fixtures.py`, `qa_create_course_visibility.py`); a QA seed for org-scoped courses would follow `qa_create_course_visibility` / `qa_register_org_course`.

## 10. Constraints on the design (summary)

1. Reuse `Organisation`; do not add a model for it. Spelling is "organisation".
2. The link lives outside `access_config` (backend-private) and ideally outside `content_engine` (no `content_engine --> organisations` edge today); `learner_management` already sees both apps.
3. Many-to-many with "scoped to a single organisation" meaning exactly one linked organisation; define behaviour for zero (available to all, today's behaviour; keeps every existing course unchanged and needs no data migration) vs many.
4. Enforcement point needs a decision: listings only, or also slug chokepoints (`course_detail`, `course_home`, `initiate_course_access`, player). Existing exemption pattern: users already registered keep access.
5. `initiate_course_access` registers into the default organisation; org-scoped courses conflict with this.
6. `course_applications` and `Course.access_config` must stay untouched.
7. Card org info: in-progress cards use the studying-through organisation (add `learner__organisation` select_related to the bulk progress resolver, avoid N+1); discovery cards use the course's single linked organisation; reuse `is_default` suppression convention from `course_organisation_chip.html`; follow the stamp-attributes-in-views pattern; the existing chip template is not card-sized and has a fixed element id.
8. Same-title courses are fine for the loader (slug suffix `-2`), but URLs and slug-keyed lookups (`Course.objects.get(slug=...)` in QA commands, `course_slug` URLs) make the suffix visible; consider whether titles on cards need disambiguating (hence the org info on cards).
9. Content-declared link (frontmatter) vs DB/admin-managed link is an open decision; DB/admin-only avoids schema, loader and `fls-content` plugin changes and the reload-wipes-links risk.
10. Existing tests encode the old premise ("courses are shared across organisations", educator isolation invariants in `educator_interface/tests/invariants/test_organisation_isolation.py`); test mirroring rules (`tests/test_check_test_mirroring.py`) and the app-map generator must be kept green; new tests go in per-app `tests/` mirroring source layout.
