# Research: mechanical enforcement of the two test-organisation rules

Question asked: can rule 1 (test hierarchy mirrors app hierarchy) and rule 2 (a test may only
cross-import apps its own app depends on at runtime) be checked mechanically, and should they be?

Short answer: **yes for rule 2, with import-linter, generated from the same AST walk that already
produces `docs/app_structure.md`** — this is a near-zero-cost addition because the graph-building
work is already done in-repo. **Yes for rule 1, but only the "orphaned/misplaced test file"
direction** — with a small custom script, not a third-party tool, because no existing Python tool
checks source/test mirroring and the inverse direction ("every source module needs a test file") has
an unacceptable false-positive rate. Both rules should ship with a **baseline file that only shrinks**,
so the check is green from day one and each cleanup spec's job is to delete lines from that file, not
to fix everything at once.

## What already exists in this repo (read before designing anything new)

- `claude_plugins/django-stack/scripts/generate_app_map.py` — stdlib-only (`ast`, no third-party
  deps), walks every app directory, classifies every `ImportFrom` node as **runtime** or **test**
  (`is_test_path`: path contains `/tests/`, `/test_`, or the file is named `conftest.py` or
  `factories.py`), and renders `docs/app_structure.md` as a mermaid graph plus a dependency table
  (solid = runtime, dashed = test-only). It already **diffs** the graph against the previous run and
  prints added/removed edges to stderr. This is exactly the machine-readable input rule 2's
  enforcement needs, and it is regenerated by `/app_map` today, not hand-maintained.
- `docs/app_structure.md` (current, at time of writing) lists 29 apps. Some apps have **zero**
  test-only edges beyond runtime (`content_base`, `deployment`, `health`, `icons`,
  `panel_framework`, `qa_helpers`, `referral_tracking`, `xapi_learning_record_store`) — these are
  already rule-2-clean and would need no baseline entry. Others have a handful of dashed edges
  (e.g. `accounts` has 7 test-only deps, `qa_helpers` has 0, `site_aware_models` has 5) — this is
  the exact shape a per-app cleanup-spec roadmap (as `idea.md` asks for) would slice.
- `pyproject.toml` `[tool.pytest.ini_options]` already has a marker taxonomy
  (`playwright`, `ci_only`, `fls_internal`, `weasyprint`) documented in
  `claude_plugins/fls-dev/resources/testing.md` — relevant to "must the check be internal-only"
  below.
- `.pre-commit-config.yaml` today: `pre-commit-hooks` (whitespace/yaml/toml/secrets/AST/private-key),
  `detect-secrets`, `ruff-check`/`ruff-format`, `bandit`, `shellcheck`, and one `repo: local` hook —
  `mypy`, invoked as `uv run mypy . claude_plugins/fls-content/validate`. There is **no
  architecture/import-boundary check anywhere in the repo** (`import-linter`/`importlinter`, `tach`,
  `pytestarch` — zero hits searching the codebase).
- `.github/workflows/tests.yml` has four jobs: `lint` (ruff), `type-check` (mypy), `unit-tests`
  (pytest, not playwright), `playwright-tests`. No dedicated architecture-check job.
- No existing tool or skill checks rule 1 (test/source mirroring) anywhere in the repo or the
  `django-stack`/`fls-dev` plugins.

## Rule 2 — cross-app test-import boundary

### Candidate tools

**import-linter** ([docs](https://import-linter.readthedocs.io/en/stable/), config via
`[tool.importlinter]` in `pyproject.toml`, run via `lint-imports`):

- The `forbidden` contract type is the right shape for this rule, not `layers` or `independence`.
  `layers` enforces a *strict total ordering* between named strata (A may depend on B but not vice
  versa, and every layer is on one side of every other) — FLS's graph is a DAG with many
  independent siblings (`course_access`, `course_interest`, `course_recommendations` all sit at the
  same "distance" from `accounts` with no ordering between them), not a clean stack, so `layers`
  would force a fictitious ordering. `independence` asserts **zero** imports in either direction
  between a set of modules — it fits the handful of genuinely unrelated apps (`panel_framework`,
  `health`, `icons`) but not the general case where most apps *do* have real runtime deps and only
  the excess (non-runtime-dep) imports are the violation.
- `forbidden` contracts take `source_modules` and `forbidden_modules`, and `source_modules` accepts
  wildcarded package patterns — critically, **`mypackage.tests.*` is a documented example pattern**,
  so a contract's source can be scoped to *only the test subtree* of an app while runtime code in
  the same app is left unconstrained (or governed by a separate, stricter contract). Concretely, per
  app `A`:
  ```toml
  [[tool.importlinter.contracts]]
  name = "accounts tests only import accounts' own runtime deps"
  type = "forbidden"
  source_modules = [
      "freedom_ls.accounts.tests.*",
      "freedom_ls.accounts.factories",   # factories.py lives at the app root, not under tests/
      "freedom_ls.accounts.conftest",
  ]
  forbidden_modules = [
      # every other freedom_ls app except accounts' own runtime deps
      "freedom_ls.course_access", "freedom_ls.course_applications", "freedom_ls.course_interest",
      "freedom_ls.deployment", "freedom_ls.dev_tools", "freedom_ls.educator_interface", "...",
  ]
  ignore_imports = [
      # baseline: existing violations, shrinks one line per cleanup spec — see below
      "freedom_ls.accounts.tests.* -> freedom_ls.content_engine",
      "freedom_ls.accounts.tests.* -> freedom_ls.course_applications",
  ]
  ```
  [Forbidden contract docs](https://import-linter.readthedocs.io/en/stable/contract_types/forbidden/)
- At ~29 apps this means ~29 near-identical contracts, one per app, each listing "every app minus my
  runtime deps minus myself" as `forbidden_modules`. Hand-writing and hand-maintaining 29 contracts
  each with a ~25-entry forbidden list is exactly the kind of thing that rots the day after someone
  adds app #30 — **this must be generated, not hand-maintained** (see below).
- `ignore_imports` is the built-in per-edge exception list, and it is exactly the baseline/allowlist
  mechanism rule 2's gradual rollout needs: teams commonly use `ignore_imports` entries in a
  layers/forbidden contract "to baseline existing violations as they work to clean them up
  incrementally," landing on a monotonic cleanup path where CI only fails if a *new*, non-baselined
  violation appears, not the pre-existing ones — the exact "green on day one, shrinks spec by spec"
  shape the idea asks for.
- `include_external_packages = true` is irrelevant here (it only matters if you also want to forbid
  *third-party* packages like `django`/`requests` from a module — not needed for an internal
  app-to-app rule) so it can stay unset/default.
- Ships an official pre-commit hook (`seddonym/import-linter`'s `.pre-commit-hooks.yaml`), so it
  slots into `.pre-commit-config.yaml` the same way the existing local `mypy` hook does — no need to
  invent a wrapper script.
- Grimp (the graph library behind import-linter) builds the whole import graph once and checks all
  contracts against it in one pass; for a codebase this size (29 apps) this is materially cheaper
  than the mypy hook already running in pre-commit today.

**tach** ([docs](https://docs.gauge.sh/)): module-based `depends_on` declarations in `tach.toml`,
optional strict layering (`layers_explicit_depends_on`), and an `unchecked: true` escape hatch per
module. It is a real alternative and is arguably nicer for the *runtime* boundary (rule the project
already has informally, now made explicit) because its mental model — "list what each module
depends on" — maps 1:1 onto the dependency table `docs/app_structure.md` already renders. Its
weakness for **this specific rule** is that tach's primitives are built around one `depends_on` list
per module; there is no first-class "this import is fine at runtime but forbidden from a test
subpackage" split documented (unlike import-linter's `source_modules` wildcard on `*.tests.*`) — it
would need per-module tach config to separately declare the app's test subpackage as its own
"module" with a narrower `depends_on`, which is possible but more configuration surface for the same
result. Written in Rust (fast), but adds a project dependency stack with less direct precedent than
import-linter's pure-Python, pip-installable, pre-commit-hook-shipped design that fits the
uv/pre-commit toolchain already in place.

**pytestarch** ([GitHub](https://github.com/boidolr/pytestarch)) and **pytest-archon**
([GitHub](https://github.com/jwbargsten/pytest-archon`)): both express architecture rules as pytest
tests (ArchUnit-style: `rule().modules_that().are_sub_modules_of("app.a").should_not().import_modules_that().are_sub_modules_of("app.b")`).
This is attractive for a pytest-native project because failures show up in the normal `pytest` run
rather than a separate tool invocation — but for ~29 apps this means writing (or generating) ~29
assertions inside a test file, which is really the same "one entry per app" generation problem as
import-linter, just expressed as Python calls instead of TOML, with worse ergonomics for the
`ignore_imports`-style baseline (would need a custom skip/xfail mechanism per edge, whereas
import-linter has that built in). Reasonable fallback if the team wants "stays entirely inside
`pytest`, no new CLI," but strictly more code to write for the same coverage.

**Small custom script**: viable and arguably simplest, because 90% of the hard part (walking the AST,
classifying test vs. runtime imports, building the per-app edge sets) is **already written** in
`generate_app_map.py`. A custom script could reuse `compute_edges()` directly, compare `edges.test`
against `edges.runtime` per app, and fail on any test edge not already in a baseline file. Cost:
maintaining a bespoke checker instead of a maintained OSS tool (no pre-commit hook packaging, no
`ignore_imports` config surface to design — would have to build that too). Given import-linter
already ships all of this, a custom script only wins if the team specifically doesn't want the
`import-linter` dependency; the marginal engineering cost is likely higher than adopting the small,
single-purpose, already-idiomatic tool.

### Generating the contract instead of hand-maintaining it

The recommended shape: extend `generate_app_map.py` (or add a sibling script driven by the same
`find_apps`/`compute_edges` functions it already exports) to also emit a generated
`[tool.importlinter]` block — either written into `pyproject.toml` under a clearly-marked
`# GENERATED — do not hand-edit, run /app_map` banner (matching the existing banner convention on
`docs/app_structure.md` itself: "This file is the authoritative picture... **generated**... Treat it
as the source of truth"), or as a separate generated file imported by pyproject. For every app `A`:

- `forbidden_modules` = `{all app module_paths} - {A} - runtime_deps(A)` — computed straight from
  `edges.runtime`, the same set that already renders the solid arrows and the "Runtime deps" table
  column.
- `source_modules` = `A.tests.*` plus the app's own `factories`/`conftest` modules if they exist at
  the app root (matching `is_test_path`'s existing classification).
- The generator should **only ever regenerate `forbidden_modules`/`source_modules`**, never
  `ignore_imports`. `ignore_imports` is the baseline and must be a separately-committed, hand-edited
  list (see below) — if the generator regenerated it from current-state test imports every run, any
  *new* violation introduced by a careless change would silently get re-baselined into the ignore
  list on the next `/app_map` run, and the ratchet would never tighten. This mirrors the existing
  discipline already documented at the top of `docs/app_structure.md`: "Any implementation plan that
  introduces a new cross-app edge should be called out and approved before code is written" — a new
  *runtime* edge is expected to require deliberate approval (regenerating `forbidden_modules` is
  fine, because it only shrinks the forbidden set when a real, reviewed dependency is added); a new
  *test-only* edge must never get a free pass via auto-regeneration.
- Practical effect: today's `docs/app_structure.md` dashed edges become tomorrow's initial
  `ignore_imports` baseline, generated **once**, by hand-transcribing (or a one-off script converting)
  the current dashed-edge table into `ignore_imports` entries, then committed as a plain file that
  cleanup specs edit by deleting lines.

### False-positive profile and blind spots (rule 2)

- **Static-only detection.** Neither import-linter (via grimp) nor `generate_app_map.py`'s `ast.walk`
  can see Django's string-based dynamic coupling — `apps.get_model("other_app.Model")`,
  `"other_app.Model"` string FKs, `INSTALLED_APPS` string references, signal registration by app
  label. These are **false negatives**, not false positives: a genuine violation of the *spirit* of
  rule 2 (test data reaching into another app's models) done via `apps.get_model()` would pass the
  check silently. Worth a line in the rule's documentation so nobody treats a green check as proof
  of full compliance.
- **Deferred/function-local imports are still caught.** Both grimp and `ast.walk` traverse the whole
  function body, not just module scope, so an import hidden inside a test function to dodge
  collection-time issues is still flagged — this is a feature, not a false positive, but worth
  calling out since some `TYPE_CHECKING`-guarded imports could be flagged too; import-linter has no
  built-in `TYPE_CHECKING` exclusion documented for the `forbidden` type, so if the codebase later
  adopts `if TYPE_CHECKING:` cross-app type hints in tests, those would need an explicit
  `ignore_imports` entry (a minor, known, fixable false positive, not a systemic one).
- **App-name collisions.** `generate_app_map.py`'s module-matching (`imported == mp or
  imported.startswith(mp + ".")`) is sorted longest-path-first specifically to avoid a short app name
  falsely matching a longer sibling path — already handled correctly in the existing script, so
  reusing it (rather than reimplementing matching logic in a new tool) avoids reintroducing that bug
  class.
- Overall false-positive rate for rule 2 via generated import-linter contracts: **low**. The one
  structural risk (silent re-baselining via auto-regenerated `ignore_imports`) is a self-inflicted
  design mistake to avoid, not a tool limitation.

## Rule 1 — test hierarchy mirrors source hierarchy

### What "mirroring" actually means in this codebase today

`freedom_ls/<app>/` apps are almost entirely **flat** — most apps have no subpackages beyond
`migrations/`, `management/commands/`, and `templatetags/` (confirmed by listing `content_engine/`,
`panel_framework/`, `accounts/`: production modules sit directly at the app root — `views.py`,
`forms.py`, `email_utils.py`, etc.). Tests already sit flat under `<app>/tests/test_<module>.py`
today (confirmed in `accounts/tests/`, `panel_framework/tests/`), which is already "mirrored" for the
common case — the rule mostly bites in three places:

1. **`management/commands/<cmd>.py`** — a nested subpackage with real production code (29
   `qa_helpers` commands alone) that today has **zero** matching `tests/management/...` structure
   anywhere in the repo (`freedom_ls/*/tests/management/**` returned no matches at all). This is
   the biggest concrete gap rule 1 would surface.
2. **`templatetags/<tag_module>.py`** — e.g. `panel_framework/templatetags/panel_tags.py` is tested
   by `panel_framework/tests/test_panel_tags.py`, i.e. flattened rather than mirrored into
   `tests/templatetags/test_panel_tags.py`. Whether this counts as a violation is a judgement call
   the spec that adopts this rule needs to make explicit (flat single-level nesting for tests is
   arguably fine; the rule's real value is catching *disappeared* structure, not enforcing depth for
   its own sake).
3. **`tests/playwright/` and `tests/e2e/`** subtrees (both names are in active use —
   `base/tests/playwright/`, `panel_framework/tests/playwright/`, plus stale `.pyc` evidence of a
   prior `tests/e2e/` layout for the same apps, suggesting a past rename from `e2e` to `playwright`
   that didn't fully clean up `__pycache__`). These are **not** meant to mirror the source tree at
   all — a playwright test exercises a user-facing flow across several source modules and templates,
   not one `.py` file, so 1:1 mirroring is the wrong model here by design, not a violation to fix.

### No existing tool does this for Python

Searched for a pytest plugin or linter that checks test/source structural mirroring. The closest
hit, `architecture-kit`'s "test-mirror root" feature (a 2026 PR: `match: "folder"` requires a test's
mirrored source folder to exist), is a **JavaScript/TypeScript** tool (`backend/tests/features/...`
↔ `backend/src/features/...` examples) with no Python port. `pytest-archon`/`pytestarch` check import
*relationships*, not file-*path* correspondence, so they don't apply either. This is a genuinely
unfilled niche for Python/pytest — the honest option is a small custom script, not a third-party
adoption.

### What a custom check would look like, and why it should only run in one direction

The critical design decision: **split rule 1 into two checks with very different false-positive
risk, and only enforce the low-risk one as a hard gate.**

1. **"Every test file's target must exist"** (low false-positive, worth gating):
   For each `freedom_ls/<app>/tests/**/test_<name>.py`, strip the `tests/` prefix and `test_`
   prefix/`_tests` suffix, and check that a same-shaped source module
   (`freedom_ls/<app>/<...>/<name>.py`, or `<name>/` package) exists. This catches the actual
   hygiene failure mode that matters: a source module gets renamed or deleted and its test file is
   left behind under the old name, silently testing dead code or (worse) still importing a
   since-removed module and passing for the wrong reason. This direction has a clean, enumerable
   exception list: `conftest.py`, `factories.py`, files under `tests/playwright/` or `tests/e2e/`,
   underscore-prefixed private helper modules (already an established repo convention — see
   `accounts/tests/_completion_view_fixtures.py`, `_git_helpers.py`, `_registration_form_fixtures.py`
   — a leading underscore already signals "not a test module, don't apply test-naming rules to it"),
   `stub_*.py` files (`panel_framework/tests/stub_panels.py`), and integration-style test files whose
   name intentionally doesn't map to one production module (e.g. a
   `test_user_registration_webhook_integration.py` spanning `accounts` + `webhooks`) — these need an
   explicit per-file or per-pattern exemption, not a structural rule change.
2. **"Every source module must have a test file"** (high false-positive, do **not** gate on this):
   Many legitimate modules have no 1:1 test file — `apps.py`, `urls.py`, `admin.py` (admin
   registration is usually covered by integration/view tests, not a dedicated `test_admin.py`),
   `config.py` (settings-shaped modules), pure re-export `__init__.py`s, and modules covered
   adequately by a broader integration test that doesn't share the module's name. Coverage
   (`--cov-fail-under=73` today) already answers "is this code exercised at all" better than a
   filename-matching check could, and a hard gate here would generate constant, low-value noise for
   contributors adding a small file that's exercised only via an existing integration test.
   Recommendation: report this direction as an **advisory** (non-blocking summary, or a section in
   the SDD reviewer's checklist) rather than a pre-commit/CI failure.

### Baseline for rule 1, same shape as rule 2

Given the `management/commands/` gap alone is repo-wide (29 `qa_helpers` commands, several more in
other apps, zero mirrored test structure today), a hard "every test target must exist" gate enabled
without a baseline would fail on essentially every app on day one. Same fix as rule 2: a single
committed allowlist file (could be the *same* baseline file as rule 2's `ignore_imports`, or a
sibling `test_organisation_baseline.toml`/`.json`) listing the currently-known-misplaced or
currently-orphaned test files, generated once from a first run of the checker in
report-only/`--write-baseline` mode, then shrunk one line per cleanup spec — exactly the "green on
day one, each cleanup spec removes its app from the baseline" mechanism the idea document asks for.

## Where it would run

**Today:** nothing checks either rule anywhere — not pre-commit, not CI, not a documented SDD-review
step. `.pre-commit-config.yaml` has room for exactly this shape of check (it already runs `mypy` as a
`repo: local` hook via `uv run`); `.github/workflows/tests.yml`'s `lint` job is the natural CI home if
pre-commit is ever skipped locally (`--no-verify`) — belt-and-braces, same pattern the project already
uses for ruff (pre-commit *and* explicit `ruff check`/`ruff format --check` steps in CI).

**Recommendation:** run both checks as `repo: local` pre-commit hooks (`uv run lint-imports` for rule
2; `uv run python scripts/check_test_mirroring.py` for rule 1's low-risk direction), matching the
existing `mypy` hook's shape exactly, **and** mirror both into the CI `lint` job so a `--no-verify`
commit or a PR from a fork without pre-commit installed doesn't slip through — consistent with how
ruff already runs in both places. Do **not** make this an SDD-reviewer-only manual step: a check that
only a human/agent remembers to run at review time is exactly the kind of rule that erodes the moment
attention drifts, which is the stated problem in `idea.md` ("tests are not organised very well...
should not feel philosophical, it should feel obvious"). Mechanical enforcement at commit time is
what makes it obvious rather than aspirational.

## Downstream distribution — must this be internal-only?

Yes, and it already fits the existing internal/portable split cleanly. FLS ships as an installable
Django app library (`[tool.setuptools.packages.find]` → `include = ["freedom_ls*"]`); a concrete
downstream project installs the package and runs its own `INSTALLED_APPS` subset, filtering FLS's own
test suite down with `-m "not playwright and not fls_internal and not ci_only and not weasyprint"`
(documented in `claude_plugins/fls-dev/resources/testing.md`). Both rule-2 and rule-1 checks are
**repository hygiene tools that operate on FLS's own source tree during FLS development** — they are
not part of the `freedom_ls` package's runtime behaviour, they don't ship in the sdist/wheel, and a
downstream project never invokes `lint-imports` or the mirroring script against its own code (its own
app boundaries are its own business). Concretely:

- `import-linter` and any custom checker script belong in the **dev dependency group**
  (`[project.optional-dependencies].dev` / `[dependency-groups].dev`), exactly alongside `ruff`,
  `mypy`, `pre-commit`, `bandit` — never in `[project].dependencies`, so a downstream project's
  production install never pulls it in.
- The generated import-linter config and any baseline files should live in the FLS repo root
  (`pyproject.toml` / a `test_organisation_baseline.*` file next to it), not inside `freedom_ls/`
  itself, so they're excluded from the package build the same way `spec_dd/`, `claude_plugins/`,
  `demo_content/`, `config/` already are (per `[tool.setuptools.packages.find].exclude`).
- No `fls_internal`-style pytest marker is needed for either check, because neither is a *test* — an
  architecture-boundary check and a file-mirroring check are static/AST-level tools that run outside
  pytest collection entirely (`lint-imports` is its own CLI; the mirroring script is a plain script),
  so they don't interact with the marker taxonomy that governs which *tests* a downstream runs.
- One genuine downstream-facing artefact survives: `docs/app_structream.md` (generated) documents
  FLS's *own* internal app boundaries and is useful reading for a downstream integrator deciding
  which FLS apps are safe to import from their own code — but that's a documentation side-effect of
  running `/app_map`, not a reason to ship the enforcement tooling itself downstream.

## Recommendation, cost, and false-positive summary

| | Approach | Cost | False-positive risk |
|---|---|---|---|
| Rule 2 | `import-linter`, `forbidden` contracts generated per-app from `generate_app_map.py`'s existing AST walk; `pyproject.toml`-committed baseline (`ignore_imports`) shrunk by hand per cleanup spec; wired into `.pre-commit-config.yaml` as a `repo: local` hook + mirrored into the CI `lint` job | Low — one new dev dependency, one generator extension reusing existing code, ~29 generated contract blocks, one baseline file | Low — main blind spot is Django's string-based dynamic imports (false negatives, not positives); the one design trap (auto-regenerating the baseline) is avoidable by construction |
| Rule 1 | Small custom script (no existing Python tool fits), gating **only** the "test file has no matching source module" direction; "source module has no test file" reported advisory-only; same baseline-file mechanism as rule 2 | Low-medium — new script to write and maintain, but it's small (path-matching, no AST needed) | Medium if both directions were gated (many legitimate untested/renamed-away files); **low** once scoped to the orphaned-test-file direction only, with an explicit exemption list for `conftest.py`/`factories.py`/`_private.py`/`stub_*.py`/`playwright`/`e2e`/integration-named files |

Both should ship together as one spec (matching `idea.md`'s "first spec sets up the skills and best
practices"): extend `generate_app_map.py`, add the import-linter config + initial baseline, add the
mirroring script + its initial baseline, wire both into pre-commit and CI, and leave every *existing*
violation in a baseline that the follow-up per-app cleanup specs shrink one line at a time — never a
big-bang fix-everything-at-once change.
