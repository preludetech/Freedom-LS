Three decisions the spec leaves to the plan:

- **The Rebuild script key lives in `.claude/ds/config.md`.** The rebuild must run between the
  rebase and the test suite, and the suite runs inside `/ds:rebase_main`, so the command that needs
  the key is a `ds` command and `ds` reads only its own config. The Rebase command and Front-end
  check keys live in `.claude/sdd/config.md` because only the pre-step rebase follows them. A
  project that leaves a key blank skips that step. `sdd` names neither `ds` nor Playwright.
- **Every deterministic piece of behaviour is a script with pytest coverage.** Command, helper and
  agent `.md` files have no automated test mechanism in this repo. Slices that change only `.md`
  files name pre-commit as their gate and nothing else. The lost-change check, the rebuild and the
  upstream-change scan are scripts for that reason.
- **Status vocabulary.** Every file returns `status: ok|failed|blocked` as the rest of the workflow
  does. `blocked` means a human has to decide something now (a conflict the command will not
  resolve, a branch with merge commits). `failed` means a retry budget ran out or a push was
  rejected. `pre_step_rebase.md` adds one value, `paused`: unlike `blocked`, it is a gate that
  survives across sessions through an unticked `todo.md` item.

## Success criteria

1. `/ds:rebase_main` commits what is in flight, fetches, stops cheaply when `origin/main` is already
   in the branch's history, keeps a backup ref, rebases, resolves conflicts, runs the lost-change
   check every time, regenerates lockfiles, renumbers colliding migrations, rebuilds, migrates,
   passes the full test suite and pre-commit, fixes breakage on the branch test-first, and pushes
   with `--force-with-lease --force-if-includes` without asking.
2. `rebase_lost_change_check.sh` reports a dropped branch change as lost, and flags files upstream
   also touched for review with a range-diff, with tests proving both.
3. Every `(cmd)` item dispatched by `/sdd:next` on a feature branch runs the pre-step rebase first;
   every feature-branch command invoked directly runs it as Step 0; `/sdd:start`, `/sdd:roadmap` and
   `/sdd:finish_worktree`'s own rebase are untouched; on `main` the pre-step rebase does nothing.
4. After a rebase that changed front-end code on the branch or in pages the branch uses, the
   front-end check visits the affected pages at the three `do_qa` viewports, reusing
   `3. frontend_qa.md` where one exists, and a failure is fixed test-first and pushed before the
   step continues.
5. `upstream_change_scan.sh` decides mechanically whether an upstream-change review runs, with tests
   per signal. A review that finds a changed architectural direction writes
   `upstream_change_review.md` beside the spec and pauses the workflow behind a `(user)` item in
   `todo.md` until the human ticks it.

## Slice 1: `/ds:rebase_main` commits, backs up, rebases and pushes

**Behaviour.** A human runs `/ds:rebase_main` on a feature branch with uncommitted work. The work
is committed, `origin/main` is fetched, the backup ref is moved to the current tip, the branch is
rebased, conflicts are resolved under the new rules, tests and pre-commit pass, and the branch is
pushed without a question. Run again straight after, it fetches and reports there is nothing to do.

**Files.** `claude_plugins/django-stack/commands/rebase_main.md` (rewrite).

**Steps of the rewritten command** (Steps 7 and 8 are placeholders that Slices 2 and 3 fill; write
the step headings now so the numbering is stable):

```
Step 1  Check the branch
        git branch --show-current; on main/master: nothing to rebase, stop.
        git rev-parse --abbrev-ref @{upstream}; remember whether the branch has one.

Step 2  Commit what is in flight
        git status --porcelain; if empty, skip.
        git add -A
        uv run git commit -m "<branch>: wip before rebase onto main"
        Hook failures are handled as commit_quickly.md says (re-stage a rewrite, fix
        what takes a minute, otherwise stop with status: blocked; nothing has been
        rebased).
        A commit rather than --autostash so the lost-change check in Step 7 covers the
        in-flight work like any other commit. The wip commit rides to the PR unsquashed.

Step 3  Fetch, and stop early when there is nothing to do
        git fetch origin main
        git merge-base --is-ancestor origin/main HEAD
        → exit 0: print "branch already contains origin/main", return
          `status: ok · rebased: no`, stop.

Step 4  Record the starting point and back it up
        OLD_BASE=$(git merge-base origin/main HEAD)
        git log --merges --oneline $OLD_BASE..HEAD
        → non-empty: status: blocked. A rebase replays a merge commit's first parent
          only and drops the rest without a conflict; the human decides.
        BACKUP=rebase-backup/<branch>
        git branch -f $BACKUP HEAD          # one ref per branch, moved every rebase

Step 5  Rebase
        git rebase origin/main

Step 6  Resolve conflicts (existing loop, plus these rules)
        - During a rebase `--ours` is origin/main's side and `--theirs` is the
          branch's commit. A wholesale `git checkout --ours|--theirs <file>` is
          only ever right for a generated file.
        - uv.lock / package-lock.json: never hand-merge. Resolve pyproject.toml /
          package.json first, then `uv lock` / `npm install --package-lock-only`,
          then git add.
        - A branch migration numbered the same as a new one on main: `git mv` it to
          follow main's latest for that app (so the old path's removal and the new
          path are staged together), point its `dependencies` at main's leaf, and fix
          any later branch migration that depended on the old name. Never
          `makemigrations --merge`.
        - status: blocked when: both sides made substantive, incompatible changes to
          the same logic (existing rule); a resolution would need `--ours`/`--theirs`
          on a non-generated file; a conflict lands in a file none of the branch's
          commits meant to change.
        git add <file>; GIT_EDITOR=true git rebase --continue; repeat.

Step 7  Lost-change check                       (Slice 2)
Step 8  Rebuild and migrate                     (Slice 3; for now: uv run manage.py migrate)

Step 9  Run the tests
        uv run pytest -x -q until green, then uv run pytest -q once in full.
        A failure is fixed on the branch test-first: make or adjust the failing
        test, make the smallest fix, commit "<branch>: fix <what> after rebase".
        Three attempts, then status: failed.

Step 10 Pre-commit (existing)

Step 11 Summarise (existing list, plus the backup ref name and the Step 7 result)

Step 12 Push
        No upstream → say so and skip.
        git push origin HEAD --force-with-lease --force-if-includes
          (flags after the refspec: the deny rule `git push --force:*` is a prefix
          match, and `--force-with-lease` shares that prefix)
        Rejected → the remote moved; status: failed. Never retry with --force.

Return contract (for a caller that follows this file inline)
        status: ok|failed|blocked · rebased: yes|no · old-base: <sha> ·
        backup: <ref> · replayed: <n> · conflicts: <n> · lost-change check: pass|fixed ·
        tests: pass · pushed: yes|no · reason: <short>
```

The command keeps no `model:` frontmatter; it is followed inline by the pre-step rebase and runs on
the caller's model there.

**Tests.** None automated (a `.md` file). Gate: `uv run pre-commit run --all-files`.

## Slice 2: the lost-change check

**Behaviour.** After every rebase, whether or not git reported conflicts, Step 7 proves the branch's
own changes survived and `main`'s were not reverted. The deterministic part is a script; the
judgment part is a range-diff the script prints for the files that need it.

**Files.**

- `claude_plugins/django-stack/scripts/rebase_lost_change_check.sh` (new)
- `claude_plugins/django-stack/templates/wrapper_scripts/rebase_lost_change_check.sh` (new; the
  `kill_runserver.sh` template with the name swapped)
- `.claude/ds/scripts/rebase_lost_change_check.sh` (new; the generated wrapper, `PLUGINS_ROOT="."`,
  executable)
- `tests/test_rebase_lost_change_check.py` (new)
- `claude_plugins/django-stack/commands/rebase_main.md` Step 7

**Script.** `rebase_lost_change_check.sh <old-base> <old-tip> [<new-base> [<new-tip>]]`, the last
two defaulting to `origin/main` and `HEAD`.

```
set -euo pipefail
Each ref must pass `git rev-parse --verify --quiet "$ref^{commit}"`; otherwise print usage
and exit 64. Arguments are only ever passed to git as refs, never evaluated.

before   = git diff --name-only old-base old-tip        # the branch's changes before
after    = git diff --name-only new-base new-tip        # the branch's changes after
upstream = git diff --name-only old-base new-base       # what main gained

lost = []; review = []
for f in before:
    if f in upstream:                        review.append(f); continue
    if git ls-tree old-tip -- f != git ls-tree new-tip -- f:
                                             lost.append(f)
      # upstream did not touch f, so the replayed result must be the same blob and
      # mode; ls-tree compares both exactly, binary files included, and an empty
      # line on both sides is a file the branch deleted. Renames are compared
      # path by path on purpose: the old and new paths each match themselves.
for f in after not in before and not in upstream:
    review.append(f)                         # a change the branch never made

print "LOST:" one path per line
print "REVIEW:" one path per line, then
      git range-diff old-base..old-tip new-base..new-tip
exit 1 if lost non-empty; exit 2 if review non-empty; else exit 0
```

**Step 7 in `rebase_main.md`.**

```
.claude/ds/scripts/rebase_lost_change_check.sh $OLD_BASE $BACKUP
exit 0 → lost-change check: pass
exit 1 → for each LOST file, restore the branch's change from $BACKUP
         (git diff $OLD_BASE $BACKUP -- <file> is the hunk to re-apply), commit
         "<branch>: restore <what> lost in rebase", re-run the script.
exit 2 → read the range-diff for each REVIEW file. A benign difference is context
         drift; a `-`/`+` pair inside a commit that did not mean to touch that code
         is a dropped or altered change: restore it as for exit 1. Then check the
         file against git diff $OLD_BASE origin/main -- <file>: the branch may only
         remove an upstream line where its own commit meant to.
then     uv run manage.py makemigrations --check --dry-run
         "No changes detected" is the only pass. Multiple leaves → the Step 6
         renumbering is incomplete; fix it and commit.
```

**Tests** (`tests/test_rebase_lost_change_check.py`, no marker, no database). A fixture builds a
repository in `tmp_path` with `subprocess.run(["git", ...])`, with `GIT_CONFIG_GLOBAL=/dev/null`,
`GIT_CONFIG_NOSYSTEM=1` and the author/committer name and email in the environment so the
machine's config never leaks in, and returns a helper that commits a file with given content on a
given branch. Each test builds `old-base`, `old-tip`, `new-base`, `new-tip` by hand (no real
`git rebase` needed: `new-tip` is whatever content the test wants the "rebased" branch to hold) and
runs the wrapper script from the repo root with `cwd=tmp_path`, passing all four refs.

- disjoint files, identical branch content after → exit 0, no LOST line
- branch hunk missing after → exit 1, path under LOST
- branch file absent after → exit 1, path under LOST
- a binary file whose bytes differ after → exit 1, path under LOST
- upstream and branch both changed the file, branch hunk intact → exit 2, path under REVIEW, output
  contains a range-diff line for the commit
- a file changed after that neither side changed before → exit 2, path under REVIEW
- a non-ref argument → exit 64
- only two refs given → `origin/main` and `HEAD` are used (the fixture creates an `origin/main` ref)

## Slice 5: the front-end check

**Behaviour.** When the rebase changed front-end code, on the branch or in pages the branch uses
that `main` changed, the pre-step rebase drives a browser over the affected pages at 1920x1080,
375x812 and 768x1024 and fails on a 500, a 404, a traceback, a missing navigation or content
region, or a console error. A failure is fixed test-first and pushed before the step continues. A
project without the key skips the check; a rebase with no front-end change never starts a server.

**Files.**

- `claude_plugins/fls-dev/commands/protected/frontend_check.md` (new)
- `.claude/sdd/config.md`: `- Front-end check: claude_plugins/fls-dev/commands/protected/frontend_check.md`
- `claude_plugins/sdd/commands/protected/pre_step_rebase.md` Step 2:
  ```
  Under ## Rebase Hooks, the Front-end check value:
    non-blank path → read that file and follow its steps with <old-base> and <spec-dir>.
      failed → status: failed with its reason. Stop.
      ok with commits made → git push   (a fast-forward; the rebase was already pushed)
    blank, or file/section absent → skip.
  ```

## Slice 6: the upstream-change review and the pause

**Behaviour.** After a rebase that replayed commits, a script scans what `main` gained and decides
whether a review is needed. When the review finds that `main` has taken a different architectural
direction, the finding lands in `upstream_change_review.md` beside the spec, a `(user)` item goes
into `todo.md` above the first unchecked item, both are committed, and the workflow stops there
until the human ticks the item. A review that finds no change of direction leaves nothing behind.

**Files.**

- `claude_plugins/sdd/scripts/upstream_change_scan.sh` (new)
- `.claude/settings.json`: `"Bash(claude_plugins/sdd/scripts/*.sh:*)"` in `permissions.allow`,
  with the same review the README asks of the other script directories (the script validates its
  refs and its directory argument, writes nothing, executes nothing).
- `tests/test_upstream_change_scan.py` (new)
- `claude_plugins/sdd/commands/protected/update_todo.md`: a new argument
  `add_first:"<marker>|<text>"` inserting a new item immediately above the first `- [ ]` line in
  the file (a file with no unchecked item → stop and tell the caller). Step 4 gains the branch; the
  argument-hint and Step 1 mention it.
- `claude_plugins/sdd/commands/protected/pre_step_rebase.md` Step 0 pause condition and Steps 3
  to 5.
- `claude_plugins/sdd/commands/next.md` Step 2.5 already stops on `paused`; its Step 5 line for
  that case is "Paused: read `<spec-dir>/upstream_change_review.md`, change the idea, spec or plan
  as it says, then run `/sdd:next` and answer yes to the new item."

**Pause condition, Step 0.** `<todo-path>` has an unticked item whose text names
`upstream_change_review.md` → `status: paused · reason: upstream-change review awaiting a
decision`, print the file path, stop. Nothing is fetched or rebased while paused.

**Script.** `upstream_change_scan.sh <old-base> <new-base> <spec-dir>`. Prints a markdown report
to stdout. Exit 0 when no signal has a path, exit 2 when one does, exit 64 on a bad argument
(refs validated as in Slice 2; `<spec-dir>` must be an existing directory).

```
upstream = git diff --name-only old-base new-base
own      = git diff --name-only new-base HEAD
named    = every backticked span in <spec-dir>/*.md that names an existing path in the
           repo (test -e); a directory matches every upstream path under it
apps     = the path segments of own ∪ named
depends  = for every line `A --> B` in docs/app_structure.md with A in apps: B
           (skip the signal when the file is absent)

signals, each a list of paths from upstream:
  overlap          upstream ∩ (own ∪ named), directories expanded
  shared bases     upstream paths matching */models.py or */migrations/* whose app
                   segment is in depends
  conventions      paths matching */skills/*, .claude/skills/*, CLAUDE.md,
                   docs/app_structure.md
  done specs       paths under spec_dd/3. done/

Report:
  # Upstream-change scan
  branch, old-base, new-base, `git diff --stat old-base new-base | tail -1`,
  `git rev-list --count old-base..new-base`, then the commit list
  (git log --oneline old-base..new-base), then one section per signal listing its paths,
  then for every path in any signal `git diff old-base new-base -- <path>`, each diff
  truncated at 400 lines with a line saying so.
```

**Tests** (`tests/test_upstream_change_scan.py`, no marker, no database). The Slice 2 repository
fixture, extended with a helper that writes a spec directory holding an `idea.md`, and a
`docs/app_structure.md` with one `A --> B` edge.

- upstream changed only an unrelated file → exit 0, report has the size line and no signal paths
- upstream changed a file the branch also changed → exit 2, path under overlap
- upstream changed a file under a directory the spec names in backticks → exit 2, path under overlap
- a backticked span that is not a path (`` `status: ok` ``) matches nothing
- upstream changed `B/models.py` where the spec's app `A` depends on `B` → exit 2, under shared bases
- upstream changed `B/models.py` with no edge from `A` → exit 0
- upstream changed a `SKILL.md` under a `skills/` directory → exit 2, under conventions
- upstream added a directory under `spec_dd/3. done/` → exit 2, under done specs
- a signal path's diff longer than 400 lines is truncated with the marker line
- a missing spec directory → exit 64

**Step 3 in `pre_step_rebase.md`: upstream-change scan.**

```
claude_plugins/sdd/scripts/upstream_change_scan.sh <old-base> origin/main "<spec-dir>"
  > .sdd-work/rebase_upstream_scan.md
Delete any .sdd-work/rebase_upstream_review.md left by an earlier rebase (a fresh scan
means a fresh review).
exit 0 → delete the scan file. status: ok · rebased: yes. Stop.
exit 2 → Step 4.
```

**Step 4: upstream-change review.** Spawn one `sdd:sdd-worker` (depth 0; a solo call) that reads
`.sdd-work/rebase_upstream_scan.md`, the spec directory's artifacts (`idea.md`, `1. spec.md`,
`2. plan.md`, whichever exist; the scan's commit list shows how far implementation has got through
`[batch N]` commits), `docs/app_structure.md` and `CLAUDE.md`, and writes
`.sdd-work/rebase_upstream_review.md`:

```
# Upstream-change review: <spec name>

direction: unchanged | changed

## What main gained
one paragraph per signal that fired, in this project's words

## Why it matters for this spec            (only when changed)
which of the spec's decisions the upstream change undercuts, and the artifact that
holds each: idea.md, 1. spec.md, 2. plan.md, or an implemented batch

## What to change                          (only when changed)
one bullet per artifact, concrete enough to edit from

status: ok
```

Its brief says what `changed` means: the upstream change alters an app boundary in
`docs/app_structure.md`, a shared base the spec builds on, a skill or convention the spec's plan
contradicts, or a finished spec in `spec_dd/3. done/` that took a decision this spec reopens. Size
alone is never `changed`. Resume and retry per the fan-out recipe within this run: an existing
review ending `status: ok` is reused; `failed` retries twice with the prior error; `blocked`
supplies the `needs` from the scan file or the code. Still `failed` or `blocked` after that →
`status: failed · reason: upstream-change review <worker reason>`; the scan and partial review stay
in `.sdd-work/` for the next run, which Step 3 replaces.

**Step 5: act on the verdict.**

```
unchanged → delete .sdd-work/rebase_upstream_scan.md and .sdd-work/rebase_upstream_review.md
            by name. status: ok · rebased: yes.
changed   → mv .sdd-work/rebase_upstream_review.md "<spec-dir>/upstream_change_review.md"
            (replacing an earlier one)
            update_todo.md with <todo-path> and
              add_first:"user|Decide what to change after reading upstream_change_review.md,
              then edit the idea, spec or plan it names"
            commit_and_push.md with <summary> `record the upstream-change review`, staging
              upstream_change_review.md and todo.md
            delete .sdd-work/rebase_upstream_scan.md
            status: paused · reason: upstream-change review awaiting a decision
```

When the human later ticks the item through `/sdd:next`, the next pre-step rebase finds no unticked
item naming the file, so it proceeds; the review file stays as a sibling of the spec like any
research file.
