# Research: verifying a branch after rebasing onto main — tests + scoped Playwright check

Scope: what "front-end" means in this repo, which diff should drive a post-rebase browser check,
what already exists to reuse, and what a cheap "quick check" should look for. This does not decide
the rebase command's design — it only maps sources a future plan step will need.

---

## 1. What counts as "front-end" in this repo

`claude_plugins/fls-dev/commands/do_qa.md` (Step 2, "Diff-scoping gate") already answers this for the
existing QA flow, and its rule is worth reusing verbatim rather than re-deriving:

> classify `CLASS = FULL` if any changed path contains `templates/` or `static/`, or ends in `.html`,
> `.css`, or `.js`; `ADMIN_ONLY` if every changed path is `admin.py` / inside `admin/`; `BACKEND_ONLY`
> if every changed path ends in `.py`; else `FULL` (safe default).

Concretely, in this repo:

- **Templates**: `freedom_ls/<app>/templates/<app>/**/*.html` (page templates and
  `partials/`) and `freedom_ls/<app>/templates/cotton/*.html` (django-cotton components, e.g.
  `freedom_ls/learner_interface/templates/cotton/course-card-shell.html`,
  `player-footer.html`, `player-nav.html`). Cotton components are `.html` under `templates/`, so
  rule 1 already covers them without a separate case.
- **Static JS/CSS**: `freedom_ls/<app>/static/<app>/{js,css}/**` — e.g.
  `freedom_ls/base/static/base/js/{interface-swap-fallback,alpine-components}.js`,
  `freedom_ls/panel_framework/static/panel_framework/js/alpine-components.js`,
  `freedom_ls/referral_tracking/static/referral_tracking/{js/copy_button.js,css/copy_button.css}`,
  `freedom_ls/themes/{default,first_class}/static/themes/<slug>/theme.css`. Every app keeps its own
  static, no top-level `static/<app>` tree.
- **Tailwind**: entry file `tailwind.input.css` (root), `@import`s `tailwind.components.css` (the
  shared `.btn*`/`.chip*`/`.alert*`/component classes — see
  `claude_plugins/fls-dev/skills/frontend-styling/SKILL.md`) and the generated
  `tailwind.active_theme.css`. Built by `npm run tailwind_build` /
  `tailwind_watch` (`package.json:14-15`) into `static/vendor/tailwind.output.css`.
  **The compiled CSS is NOT committed** — `.gitignore:28` ignores `static/vendor/`, and
  `tailwind.active_theme.css` is also gitignored (`.gitignore:31`, generated by
  `manage.py write_active_theme_css`). So after a rebase the build is stale/missing by default; a
  front-end check needs a fresh `npm run tailwind_build` before trusting what renders.
- **Views returning HTML / HTMX partials**: any view importing `render`/`TemplateResponse` or a
  cotton component, and the `partials/` subdirectory convention itself (e.g.
  `learner_interface/templates/learner_interface/partials/course_card.html`). A changed view that
  renders a listed template is front-end-relevant even if the view file itself is `.py` (the diff-scoping
  rule catches this transitively only if the template also changed — a Python-only change to what a
  view *passes into* an unchanged template is a gap the rule accepts, per its own "safe default" note).
- **URLs**: every app's `urls.py` with `app_name` set (per `CLAUDE.md` convention) — changed URL
  patterns are the join key between a changed template/view and the page to visit (see §2).

## 2. Which diff should drive the check, and mapping files → pages

A rebase changes two things at once: the branch replays **its own** commits on a new base, and it
picks up **upstream `main`'s** commits that were not there before. Only one of these is "the feature
under test" — but both can break the UI, for different reasons:

- **The branch's own diff** (`git diff main...HEAD` — do_qa.md Step 2's exact form, i.e. the
  three-dot range from the merge-base) is what the branch *intended* to change. If the branch has its
  own `frontend_qa.md` test plan (see §3), that plan already targets exactly this diff — it was
  written against the feature, not against the rebase.
- **Upstream's diff over the branch's area** — the files `main` changed *underneath* the branch,
  restricted to files the branch also touches or imports. This is the dangerous case the idea draft is
  responding to ("a previous rebase broke a lot of front-end functionality without being noticed"): the
  rebase replays the branch's own commits cleanly (no conflict), but a template or JS helper the branch
  depends on changed shape upstream, and nothing in the branch's own diff would surface that — its own
  QA plan never re-checks code it didn't touch.

Given that, the diff that should drive the *scoping decision* is the union: `git diff main...HEAD`
still classifies FULL/ADMIN_ONLY/BACKEND_ONLY as today, but the set of pages to actually visit should
be derived from **both** sides intersected with what the branch's own changed files reference —
concretely:

1. Take the branch's changed templates/static/views (`git diff main...HEAD --name-only`).
2. For each changed template, find its callers: `grep -rl "<template-name-without-app-prefix>"` over
   `freedom_ls/*/views.py` (`render(request, "app/template.html", ...)`) and over other templates
   (`{% include %}` / cotton tags `<c-app.component-name>`) to reach the view, then `grep` that view's
   name in the app's `urls.py` to get the path.
3. Additionally, get upstream's own changed files for the same rebase
   (`git diff <old-base>...main --name-only`, i.e. what `main` gained since the branch's last rebase)
   restricted to templates/static the branch's own changed views import, per §1's classification rules.
   This surfaces the "shared code moved under you" case without re-testing all of `main`.
4. Cotton components and `partials/` are frequently multi-page (e.g. `course-card-shell.html` renders
   on the dashboard, all-courses, and course-detail pages) — a changed shared component should map to
   *every* page that includes it, not just the one the branch's own feature focused on. This is exactly
   the "if the fix touched shared code, spot-check 2-3 adjacent pages" instinct already codified in
   `do_qa.md` Step 13 ("Re-verify after a successful fix").

## 3. Existing assets to reuse

- **`claude_plugins/fls-dev/commands/do_qa.md`** — a full Playwright-MCP-driven QA runner: diff-scoping
  gate (Step 2), unused-port + dev-server start (Step 3), branch-identity check via
  `#debug-branch-badge` (Step 4, `freedom_ls/base/templates/_base.html`), login (Step 5), a **smoke
  gate** loading the two most critical pages before the full matrix (Step 6), desktop/mobile/tablet
  passes (Steps 7-9, viewports 1920x1080 / 375x812 / 768x1024), screenshot collection/compression,
  report generation, an auto-fix loop with a green/red-lane triage gate (Step 13), and todo/scratch
  cleanup. This is the directly reusable mechanism for "poke around in a browser" — it already knows
  how to scope viewports to a diff class, and its smoke gate is a cheap first check on its own.
- **Test plan format** (what `do_qa.md` calls "the test plan", argument to `/fls-dev:do_qa`): a
  numbered file in the spec dir, e.g. `spec_dd/3. done/2026-09-17_09:26_learner-dashboard-small-fixes/3. frontend_qa.md`,
  with a mandatory `§0 Setup` (server port + branch-badge check, then seed data keyed on stable slugs
  so reruns are idempotent), followed by numbered test IDs with inline `Expect:` lines. Produced by
  `claude_plugins/sdd/commands/plan_from_spec.md` alongside the implementation plan (its own todo
  entry: `tick:"Run /plan_from_spec to generate the implementation plan and QA plan"`). **If the
  branch being rebased has one of these already in its own spec dir, re-running it against
  `/fls-dev:do_qa` is exactly "reuse the spec's existing QA plan"** — it already encodes the seed data
  and the pages that matter for that feature, cheaper than devising a fresh scoped check.
- **Prior QA reports as a map of intended behaviour** — every spec in `spec_dd/3. done/*/qa_report.md`
  (70+ of them) documents what a screen was supposed to do and what was screenshotted, e.g.
  `spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/3a. seam_qa/frontend_qa_seam.md`
  models the newer, richer `§0` (a `showmigrations` sanity check, seed commands, credentials, a
  persona/fixture table, admin changelist URLs). `spec_dd/1. next/mega-qa/research_qa_plan_suite_organisation.md`
  is a sibling research doc already surveying this corpus for a durable whole-system suite — read
  before designing new scoping heuristics, since it has already extracted the recurring `§0` /
  test-ID / pass-fail-partial-vocabulary conventions from these reports.
- **`fls-dev:qa-data-helper` / `fls-dev:qa-bugfixer`** — the two agents `do_qa.md` spawns for missing
  test data and green-lane auto-fixes, respectively (Rule 2, Step 13). Reusable as-is if a post-rebase
  check follows the same shape.
- **In-suite Playwright regression tests** (pytest, not MCP) — `pytest-playwright` is already wired
  into `uv run pytest`: `freedom_ls/tests/playwright_fixtures.py` supplies `logged_in_page` /
  `reset_local_storage` fixtures, and 15+ files under `freedom_ls/*/tests/playwright/` exercise real
  browser interactions (`test_course_toc.py`, `test_flashcard_overflow.py`,
  `test_organisation_switcher_mobile.py`, `test_data_table_panel_htmx.py`, `test_toast_dismiss.py`,
  etc.). Every one is tagged `@pytest.mark.playwright` (see
  `claude_plugins/fls-dev/skills/playwright-tests/SKILL.md`) for downstream-portability reasons, but
  the marker is **not excluded** from `uv run pytest` locally — `pyproject.toml`'s addopts only exclude
  `ci_only` and `weasyprint` (`pyproject.toml:81`) — so a plain `uv run pytest` after rebasing already
  re-runs this whole automated browser-driven regression set. This materially shrinks what the *manual*
  MCP pass needs to cover: it only needs to catch what these automated tests don't — new/changed
  front-end behaviour with no pytest-playwright test yet, and visual/layout regressions no assertion
  encodes. `.github/workflows/tests.yml` confirms CI runs `uv run pytest -m "not playwright"` and a
  separate `uv run pytest -m playwright --no-cov` job, both after `npm run tailwind_build` — i.e. CI
  treats the Tailwind build as a prerequisite for trusting either suite.
- **`claude_plugins/django-stack/commands/rebase_main.md`** — an existing, generic (non-FLS,
  non-MCP) rebase command: fetch/rebase, resolve conflicts, `uv run pytest -x -q`, `uv run pre-commit
  run --all-files`, summarize, offer `--force-with-lease` push. It has no diff-scoping, no Playwright
  step, and no spec/todo awareness — a reasonable skeleton for the "rebase" half, but it is the generic
  `django-stack` plugin's version, not `fls-dev`'s, and it does not satisfy "if any front-end
  functionality was touched, use Playwright MCP" at all.
- **Dev-server / port conventions**: `.claude/ds/scripts/find_available_port.sh` (pick an unused port
  per worktree) and `.claude/ds/scripts/kill_runserver.sh <PORT>`; `.claude/fls-dev/config.md` holds
  admin credentials (`demodev@email.com`) and the `## QA Dev Data` ladder (`Content reset` →
  `danger_content_delete --yes`; `DB drop`/`DB create` → `.claude/fls-dev/scripts/dev_db_delete.sh` /
  `dev_db_init.sh`; `Migrate` → `manage.py migrate`). Demo content loads via
  `uv run python manage.py content_save demo_content DemoDev`.

## 4. Other cheap checks worth running

From `pyproject.toml` and `.pre-commit-config.yaml`:

- `uv run python manage.py makemigrations --check --dry-run` — catches model changes without a
  migration (not run anywhere in CI today; `.github/workflows/tests.yml` relies on the test suite
  hitting migration state indirectly, so this is a genuinely cheap addition).
- `uv run python manage.py migrate` — applies anything the rebase's replayed commits added.
- `uv run python manage.py check` — Django's system checks (not currently invoked by CI or
  pre-commit directly, though pytest-django running the suite exercises much of the same app-loading
  path).
- `npm run tailwind_build` — required before any front-end check is meaningful, since the compiled
  CSS is gitignored (§1) and CI always rebuilds it before either pytest job
  (`.github/workflows/tests.yml:81-82,127-128`).
- `uv run pre-commit run --all-files` — runs `ruff-check --fix`, `ruff-format`, `bandit`, `shellcheck`,
  `detect-secrets`, plus the local `mypy` hook (`.pre-commit-config.yaml`); mypy is also its own CI job
  (`.github/workflows/tests.yml` "Type check": `uv run mypy .`). `djlint` is present in `dev` deps
  (`pyproject.toml`) but its pre-commit hooks are commented out (`.pre-commit-config.yaml:45-49`), so it
  is not currently part of the automated gate.
- `uv run pytest` (no marker filter) — runs unit tests **and** the pytest-playwright browser set
  together locally (§3); CI splits them into two jobs but runs the same total set.

## 5. Screen sizes and what a "quick check" should look for

`do_qa.md` already fixes the three viewports this project uses everywhere else: **1920x1080**
(desktop), **375x812** (iPhone-sized mobile), **768x1024** (iPad-sized tablet) — Steps 7-9. Reusing
these exact numbers keeps a post-rebase check consistent with every existing QA report's screenshots,
rather than introducing a fourth convention.

What to look for at each, cheaply (general smoke-testing practice, not FLS-specific): a clean browser
console (no uncaught JS exceptions or error-level messages), no unexpected network failures — for an
HTMX-heavy app specifically, a partial that 404s or comes back as a full page instead of a fragment is
the characteristic post-rebase failure mode, since it usually means a `urls.py` name moved or an
`hx-get`/`hx-post` target template was renamed underneath the branch — and no HTTP 500/404 or visible
Python traceback on load (`do_qa.md`'s own smoke-gate check, Step 6). At mobile/tablet specifically:
navigation/menu behaviour (hamburger, drawers), layout overflow/overlap, and touch-target sizing (Step
8's own list) — these are the categories a compiled-but-untested Tailwind change is most likely to
silently break, per the general principle that a "quick check" should sample the layout-sensitive
surfaces rather than re-walk every assertion pytest already re-runs (§3).
