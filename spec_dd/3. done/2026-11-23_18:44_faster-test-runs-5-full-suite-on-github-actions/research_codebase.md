Points that matter for the split:

- The CI `-m` **replaces** the addopts `-m 'not ci_only and not weasyprint and not dev_tooling'`, so the CI unit job **does run `ci_only` and `weasyprint` tests**; the local full tier (`markers = "not ci_only and not weasyprint"`) does **not**. `ci_only` = slow real-time rate-limit tests. `weasyprint` needs Pango/cairo/gdk-pixbuf/HarfBuzz on the runner (never confirmed present in CI; the runner image is also newer now). So "the full suite" differs between local full tier and CI: the spec must say which set the remote run covers and whether remote pass equals local full pass.
- `dev_tooling` is the only marker group CI runs with `-m dev_tooling`; local full includes it (the tier `-m` drops `not dev_tooling`).
- `playwright` is the marker for browser tests; they live in `freedom_ls/*/tests/playwright/` (conftest in `educator_interface` and `panel_framework`) plus `freedom_ls/tests/playwright_fixtures.py`.
- Coverage is today only on the unit job and only in CI (`--cov --cov-fail-under=92`); it is not in `addopts`. Config: `[tool.coverage.run]` `branch = true`, `source = ["freedom_ls"]`, omit migrations, `*/tests/*`, conftest, manage.py, `*/qa_helpers/*`, `*/dev_tools/*`; `[tool.coverage.report] show_missing = true`. No `parallel = true` / `[tool.coverage.paths]` set, which a multi-job combine needs (per-job `.coverage.*` data files uploaded, then `coverage combine` + `coverage report --fail-under=92`, same checkout path so no remap needed). `pytest-cov>=7` in dev deps. dev_tools tests are excluded from coverage by comment ("run in the dev-tooling CI job, which carries no coverage").
- Standalone runs: `freedom_ls/panel_framework/tests/standalone_pytest.ini` (`--ds=...standalone_settings`, `--nomigrations`, `-m "not needs_fls_host"`, `norecursedirs = playwright`) and `freedom_ls/icons/tests/standalone_pytest.ini` (`--ds=freedom_ls.icons.tests.standalone_settings`). Their `python_files = test_*.py` is deliberately not auto-discovered. They check those apps work without the FLS host; they run in their own pytest process and so **are not part of `-n auto` coverage** and need their own job/step in any split. Neither is in the local full tier (the default run only uses the root config; panel_framework/icons tests do also run under the FLS settings).
- Jobs duplicate setup (uv sync, npm ci, tailwind build) three times; no `actions/cache` for node beyond `setup-node cache: npm`; `setup-uv` `enable-cache` only on lint/type-check.
- Postgres service port 6543 must match what `config.settings_dev` expects (not verified here; the three jobs already agree). The playwright job uses db `test_db` vs `db` elsewhere, an unexplained difference to preserve or unify.
- Branch protection / required-check names: job ids/names (`Lint`, `Type check`, `unit-tests`, ...) may be referenced by repo settings; renaming or matrixing `unit-tests` changes check names. Not verifiable from the repo.

Coverage "wherever the project puts them: in addopts, or in CI only" (FLS: CI only). Memory-aware runner section, "Reporting" (quote `run: summary (merged)` / `run: RESULT PASS|INCOMPLETE|FAIL`), "When a targeted run or full run fails" (failed set = `run: failed <node id>` / `run: unfinished <node id>` lines, else pytest `FAILED <id> - msg` lines; failed-only and whole-tier re-run). Note a full tier with the generic selector may print `tier: full` + a command; the remote option must be chosen by project config, not hard-coded here.

Runner output lines (`run: summary (merged)`, `run: failed`, `run: unfinished`, `RESULT ...`) are the contract a remote adapter should imitate or the tier definition must describe separately for the remote case.

## 4. SDD side: where the remote option plugs in

`claude_plugins/sdd/commands/protected/run_test_tier.md` (generic `sdd`, helper run inline by the caller on `sdd:sdd-mechanic`):
- Step 1 reads `Test tiers` under `## Test Hooks`; blank -> plain `uv run pytest` run as `tier: full`.
- Step 2 resolves `checkpoint` via `full_run_record.py resolve --selector "<selector>"`.
- **Step 3 "Record a full run"** applies to every `full`: `full_run_record.py start` (prints `sha: <HEAD>` or empty on dirty tree) before, `write --verdict pass|incomplete|fail --sha "<sha>"` after. Records only if HEAD unchanged and tracked tree clean.
- Step 4 report line: `tier: none|targeted|full · summary: ... · failed: <node ids>`.
Edit points for the spec: a Step 1 branch "the tier definition says full runs remotely via `<command>`", a remote start/wait/read loop, fallback-to-local after configured wait (answers.md), and a way for Step 3 to record a remote pass for the tested commit (the run's `head_sha`, which must equal the `start` sha; the branch must be pushed first, per answers.md auto-push).

`claude_plugins/sdd/scripts/full_run_record.py` (stdlib only): record = one file per branch, `.sdd-work/full_run_record_<percent-encoded branch>.txt`, contents one 40-hex SHA + newline. Verbs `read`, `resolve [--selector]`, `start`, `write --verdict --sha`. `write` rejects non-pass verdicts, detached HEAD, empty sha (dirty tree), non-full sha, HEAD moved, dirty tree. `resolve` goes: selector says `none` for `origin/main..HEAD` -> none; no/stale record -> full; else diffs `<sha>..HEAD` (plus `--upstream-range` if the merge-base with `origin/main` moved). A remote pass for the commit tested fits the existing `write --sha` unchanged as long as HEAD is still that commit and clean, so **no format change is required**; overlap risk is with `faster-test-runs-12-reliable-full-run-record` (ready, may change the runner and the record) and `-11-record-failed-full-runs` (blocked by 12; extends the record with failed tests). Tests: `tests/test_full_run_record.py`, `tests/test_checkpoint_prompts.py`, `tests/test_failed_only_rerun_prompts.py`.
Readers of the record: `run_test_tier.md` Step 2, `finish_worktree.md` Step 1 (delegates to `sdd:sdd-mechanic`, follows `run_test_tier.md` as far as the resolve step, then runs the resolved tier; line ~264 reads the last passing full run `implement_plan` Step 3 wrote), `implement_plan.md`, `hotfix.md`, `qa_fix.md`, `do_qa_fix_loop.md`, `agents/qa-bugfixer.md`, `django-stack/commands/rebase_main.md` and `commit.md`, `sdd/commands/init.md`, `sdd/README.md`, `commands/README.md`, diagram `docs/diagrams/implement_plan.drawio.svg` (a `tests/test_check_diagrams.py` test keeps diagram and command in step).

Hard constraints from tests: `tests/test_test_tiers.py` allows pytest invocations in plugin markdown only in `django-stack/resources/test_tiers.md`, `fls-dev/skills/testing/SKILL.md`, `fls-dev/resources/playwright-testing.md`, `fls-dev/resources/concrete_spec_integration.md`, `sdd/commands/protected/run_test_tier.md` (and forbids `--last-failed`). A remote adapter prompt that spells out a pytest command in some other file fails that test. Any new `gh` command (`gh workflow run`, `gh run watch/view`, `gh run download`) is not "pytest", fine, but is project-specific only as config; generic prompts say "the project's remote full-tier command".

Pushing: `claude_plugins/sdd/resources/commit_and_push.md`: commands that write artifacts end by committing and `git push` (`git push -u origin HEAD` if no upstream); refuses on `main`/`master`; if push rejected (remote moved) report and leave it, never force-push. The auto-push in answers.md has to use or mirror these rules: a rejected push cannot proceed remotely, and the remote run must test the pushed HEAD, so the dirty-tree rule in `full_run_record.py start` (empty sha) already means "no record" for a dirty run; a remote run on a dirty tree tests something other than the working tree and should be refused or fall back local. Pre-push hook interplay not checked.
