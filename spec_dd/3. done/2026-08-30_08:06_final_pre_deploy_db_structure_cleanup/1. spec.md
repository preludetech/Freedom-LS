# Spec: Final pre-deploy database structure cleanup

## 1. Purpose

FLS has never been deployed. It ships as a git submodule into downstream projects that run `migrate`
against their own databases, so the first `migrate` any downstream project runs against a database it
intends to keep turns every structural decision here into somebody else's production problem.

This is the sweep that catches what the shipped specs did not: absent timestamps, an app label that
namespaces four tables wrong, two names that no longer describe what they point at, deletion rules
that lose learner data through a live admin page, and a migration history worth discarding while
discarding it is still free. The findings, their ranking and the approach are settled in `idea.md`.

## 2. Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `collection` | narrowed | After this cut, `ContentCollectionItem.collection` (the `Course`/`CoursePart` generic FK) is the *only* thing the word names. The three registration-side fields that shared it become `course`. `.claude/skills/domain-glossary/SKILL.md` records the opposite today and is updated by §7. |
| `TimestampedModel` | coined | The abstract mixin carrying `created_at`/`updated_at`, defined in §5.1. No existing FLS name covers it. |
| extractable app | coined | An app a spec has committed to leaving `freedom_ls/` as its own installable package. It may decline two FLS conventions; see §4.3. |

## 3. Scope

### In scope

Every "do now" item in `idea.md`, and its Decisions 1 to 5.

### Out of scope

- Everything under `idea.md`'s "Do later" and "Won't do" headings, unchanged.
- `updated_at` on models that already carry `created_at` (`Learner`, `RecommendedCourse`,
  `CourseInterest`, `CourseProgress`, `WebhookEvent`, `WebhookDelivery`). A missing `updated_at` reads
  honestly whenever it is added, meaning "not known to have changed since", so it carries no pre-deploy
  deadline.
- Delete lockdown on the learner-data admins (`QuestionAnswerAdmin`, `FormProgressAdmin`). Deleting
  learner data through the admin is `user-data-retention-idea.md`'s question, not content authoring's.
- Admin-form validation of the five `(site, slug)` content constraints, which keep the `IntegrityError`
  they raise on a duplicate slug today. §5.5 explains why un-excluding `slug` is the wrong trade.
- The `Client.api_key` redesign. `app_authentication` is deleted, not fixed.

## 4. Decisions

### 4.1 Timestamps go on a standalone `TimestampedModel` mixin

Folding them into `SiteAwareModel` would miss the two models with the least coverage: `accounts.User`
subclasses the lower `SiteAwareModelBase`, and `SystemRoleAssignment` is a plain `models.Model`,
deliberately not site-aware. It would also force a generic pair onto models already carrying a correct
domain-named timestamp.

The mixin uses `auto_now_add` / `auto_now`, matching all ~20 existing timestamp declarations in the
tree. It is unoverridable, since Django discards any value a caller passes. But `freezegun` and
`time_machine` both patch `django.utils.timezone.now`, which is what these fields call, so tests keep
control of the clock.

**A model takes the mixin only if it has no creation timestamp at all.** A model that already has one,
under any name, does not, because the mixin would duplicate it. The three role-assignment models are
the one exception: they keep `assigned_at` and gain a bare `updated_at`, because they are edited in
place and `assigned_at` is a domain name worth keeping.

### 4.2 The content admin loses delete, inlines included

`webhooks/admin.py` already overrides `has_delete_permission` to `False` on its two audit models. The
same pattern applies here, and it is the only fix reaching the gap Django gives no lever for:
`QuestionAnswer.selected_options` uses an auto-generated through table, so deleting one `QuestionOption`
silently drops the join row from every answer that selected it, and `PROTECT` on
`QuestionAnswer.question` does not close that.

`has_delete_permission` returning `False` also removes the `delete_selected` bulk action, but it does
**not** reach inline formsets: `InlineModelAdmin.has_delete_permission()` checks the *inline model's
own* delete permission, independent of the parent's override. Every inline needs `can_delete = False`
separately or deletion stays reachable through the parent's form.

Add and change stay enabled. This does not replace the `on_delete` changes. `danger_content_delete`
and any future API bypass admin permissions entirely.

### 4.3 Extractable apps may decline the label and `SiteAwareModel` conventions

An app is extractable when a spec has committed it to leaving `freedom_ls/` as its own installable
package. Today that is `icons` (which becomes `django_semantic_iconify`, so an FLS-prefixed label would
only be renamed twice), `markdown_rendering`, and the planned `referral-link-tracker`. The exemption is
permitted, not required: `markdown_rendering` already carries `freedom_ls_markdown_rendering` and keeps
it, so `icons` is the only app taking it. They are exempt from nothing else; dependency direction still
points host to app, never the reverse. `health` is not extractable and gets `freedom_ls_health`.

The guardrail encodes the exemption as an allowlist rather than asserting a blanket prefix, and lives as
an FLS-internal probe, not an exported downstream check. A downstream project's own app labels are not
its business. The related house rule: a system-check id's label segment must equal that app's own
registered `AppConfig.label`, whatever it is.

### 4.4 The three pre-registration course FKs keep CASCADE

`CourseApplication.course`, `CourseInterest.course` and `RecommendedCourse.course` are pre-registration
signals with no progress, answers or registrations behind them; deleting the course discards a stale
preference. `CourseApplication` is the one to revisit when application review adds a decision state, and
that is the review spec's call.

### 4.5 The migration reset is authorised, and runs last

**No downstream project has run a `migrate` it intends to keep.** Confirmed by the repo owner on
2026-08-28, which is the precondition the whole reset rests on. All four specs it was waiting on have
landed. The reset goes ahead; there is no fallback branch to build.

This is a declared, one-time exception to `CLAUDE.md`'s "never edit existing migration files". The rule
guards against rewriting a migration some database's history already vouches for having run. Deleting a
file and regenerating from current model state does not touch such a file; it discards an artifact
before it was ever load-bearing. `learner_management` and `learner_progress` are each a single
`0001_initial` today, and got there by exactly this operation. The exception covers this pass and
nothing after it: once a downstream `migrate` has run against a database meant to be kept, only ordinary
forward migrations remain safe.

### 4.6 Respelling a site-scoped constraint silently disables its admin validation

`SiteAwareModelAdmin` excludes `site` from every admin form (`site_aware_models/admin.py:18`), and
`UniqueConstraint.validate()` abandons a constraint as soon as one of its fields sits in that exclusion
set. `Cohort` spells the field `"site_id"`, which matches nothing in the set, so Django validates that
constraint in the admin form today. Respelling it `"site"` stops that and reintroduces an
`IntegrityError` 500 where a clean field error appears now.

Every site-scoped `UniqueConstraint` this cut adds or respells on a model with a live admin therefore
needs a `ConstraintValidationFormMixin` form (`site_aware_models/forms.py:20`), and every other field in
that constraint has to be rendered by the admin for the error to attach.

### 4.7 The `webhooks` label change regenerates that app's migrations rather than rewriting them

Relabelling `webhooks` changes the label string in nine of its ten migration files. Editing them in place
is the option `research_migration_reset_strategy.md` rejects outright: same downstream risk, no benefit,
and it produces files that still look historical but no longer are. Instead, delete `webhooks`' ten
migrations and regenerate a single `0001_initial`.

This keeps the label change separately reviewable, since it is one app, and the later project-wide reset
subsumes it harmlessly. It rests on the same §4.5 authorisation: a label change after a downstream
`migrate` would need a downstream-authored data migration over `django_migrations`,
`django_content_type` and `auth_permission` regardless of how FLS's own files are shaped.

## 5. Requirements

Section order is not execution order.

### 5.1 The `TimestampedModel` mixin

Add to `freedom_ls/site_aware_models/models.py`, alongside `SiteAwareModelBase` and `SiteAwareModel`,
before any of the per-model additions below:

```python
class TimestampedModel(models.Model):
    """Adds creation and modification timestamps.

    Composed alongside whichever base a model already uses, rather than folded
    into SiteAwareModel, so it also reaches accounts.User (SiteAwareModelBase
    only) and models that are deliberately not site-aware.
    """

    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True
```

`site_aware_models` already supplies base classes to every app that would import the mixin, so no new
cross-app edge is created. `role_based_permissions` already imports `site_aware_models` for
`SiteRoleAssignment`.

Apply the mixin to every model below, listed after the model's existing FLS base. Base order is cosmetic
here, affecting generated column order and the admin's default field order and nothing else, so keep it
consistent rather than arguing it.

### 5.3 Renames

**`collection` → `course`**, on three FKs in `freedom_ls/learner_management/models.py`:
`LearnerCourseRegistration.collection` (`:111-115`), `CohortCourseRegistration.collection` (`:135-139`),
`RecommendedCourse.collection` (`:330-334`). Each is a `ForeignKey` to
`"freedom_ls_content_engine.Course"`. `related_name` values (`learner_registrations`,
`cohort_registrations`, `recommendations`) already say "course" on the `Course` side and do not change.
The two registration constraints `unique_learner_course_registration` (`:120-126`) and
`unique_cohort_course_registration` (`:146-152`) list the field and must be updated with it.

`ContentCollectionItem.collection` (`content_engine/models/courses.py:274-282`) is a genuine
`GenericForeignKey` over `Course`/`CoursePart` and **does not change**. The two meanings are
syntactically identical, both literally `.collection`, and are distinguishable only by the owning class.
They co-occur in the same modules (`learner_management/admin.py`, `learner_management/queries.py`,
`educator_interface/views.py` all touch both). **No regex safely separates them; the sweep triages per
call site by receiver type.**

Footprint, as a floor rather than a total: a whole-word search for `collection` finds 558 occurrences
across 106 Python files (58 of them under `tests/`, carrying 348 of the occurrences), 7 occurrences
across 6 templates, one in `demo_content/functionality_demo_content_widgets/4. interactive-widgets/content.md`
and one in `docs/product/deployment.md`. The last two need reading before touching; they are likely
prose. That search deliberately excludes the derived forms, every one of which also needs the rename:
`collection_id`, `collection=` keyword arguments, `collection__` ORM traversals, and the field named as a
string in `select_related`, `prefetch_related`, `values`, `only` and `order_by`.

**`UserCohortDeadlineOverride` → `LearnerCohortDeadlineOverride`** (`learner_management/models.py:252`).
Its only person-identifying field is `learner` (`:260`), a FK to `Learner`; the class name predates the
spec that re-keyed it. Its constraint `unique_user_cohort_override_per_item` (`:281`) is renamed with it,
to `unique_learner_cohort_override_per_item`. The rename touches the model, `learner_management/admin.py`
(inline at `:262`, admin class at `:394`), `learner_management/factories.py:174`, `deadline_utils.py`,
`educator_interface/views.py`, two `qa_helpers` commands (`qa_create_deadline_overrides.py`,
`qa_create_learner_deadlines.py`), and four test modules, one of which is named after the class and is
renamed with it (`learner_management/tests/test_user_cohort_deadline_override.py`).

Both renames generate migrations before the reset, so the tree stays migration-consistent at every
commit. **Verify the generated operations are `RenameField` and `RenameModel`, not `RemoveField`+`AddField`
or `DeleteModel`+`CreateModel`.** `makemigrations` asks interactively and a declined prompt produces the
destructive pair instead, which also orphans the `django_content_type` row rather than letting
`inject_rename_contenttypes_operations` rewrite it in place. Django 6.0 reverted the optimisation that
rewrote permission codenames on `RenameModel`, so `auth_permission` rows keep the old model name after a
rename; the reset recreates them from scratch, so nothing further is needed.

The two registration FKs are already blocked transitively, because every active registration mints a
`PROTECT`-guarded `CourseProgress`, so this changes no behaviour today. It stops the model's integrity
resting on another model's cascade policy, and covers the never-activated registration that has no
`CourseProgress` behind it.

`WebhookDelivery` gains `endpoint_url`, a non-null `URLField` written at dispatch from
`WebhookEndpoint.url` (`webhooks/models.py:49`), so the audit row still says where it was trying to send
after the endpoint is gone. Adding a non-null column needs a one-off migration default; use `""` with
`preserve_default=False`, since no rows exist to carry it. `WebhookDelivery.event` stays CASCADE:
`WebhookEventAdmin` (`webhooks/admin.py:191`) and `WebhookDeliveryAdmin` (`:236`) already hard-disable
delete, so it has no live surface.

**The GFK pair contract.** `SET_NULL` nulls `content_type` and leaves `object_id` populated; Django
enforces no pairing. Each deadline model's `clean()` tests `content_type is None and object_id is None` to
recognise a whole-course deadline, and each unique constraint is already conditioned on
`Q(content_type__isnull=False, object_id__isnull=False)`. Change each `clean()` to key on
**`content_type is None` alone**, whatever `object_id` holds, so a half-nulled row does not fail
`full_clean()` on the next admin edit. The `content_item` read path needs nothing: `GenericForeignKey`
already resolves to `None` once `content_type` is null, and each `__str__` already renders that as
"Whole course".

**Admin lockdown.** Add `has_delete_permission` returning `False` to every content admin, following
`webhooks/admin.py:191-194` verbatim in shape:

- `content_engine/admin.py`: `TopicAdmin`, `ActivityAdmin`, `CourseAdmin`, `CoursePartAdmin`,
  `ContentCollectionItemAdmin`, `FileAdmin`.
- `form_engine/admin.py`: `FormAdmin`, `FormPageAdmin`, `FormContentAdmin`, `FormQuestionAdmin`,
  `QuestionOptionAdmin`.

That is the whole authored-content family: leaving `Activity` or `File` deletable while locking `Topic`
would be incoherent. Add and change stay enabled.

Separately, set `can_delete = False` on every content inline, per §4.2: `ContentCollectionItemInline`
(used by `CourseAdmin:78` and `CoursePartAdmin:106`), `FormPageInline` (`FormAdmin:131`),
`FormContentInline` and `FormQuestionInline` (`FormPageAdmin:104`), `QuestionOptionInline`
(`FormQuestionAdmin:81`).

`danger_content_delete` (`content_engine/management/commands/danger_content_delete.py`) needs no ordering
change; it already clears `QuestionAnswer` before `FormQuestion` is reached. Extend its existing comment
at `:78-83` to name the `QuestionAnswer.question` `PROTECT` explicitly, so a future reorder has something
to trip over.

- `ContentCollectionItem.Meta` (`content_engine/models/courses.py:302-303`) carries only `ordering`. Add

  Containment is the only operator used, which is what `jsonb_path_ops` is for; `opclasses` requires an
  explicit `name`.

### 5.6 Field types and clarity fixes

- **`content_base.BaseContent.tags`** (`content_base/models.py:22`) becomes
  `ArrayField(models.CharField(max_length=255), blank=True, default=list)`, matching
  `Course.learning_outcomes` (`content_engine/models/courses.py:69-76`). PostgreSQL has no implicit cast
  from `jsonb` to `text[]`, so a plain autogenerated `AlterField` fails even against an empty table;
  hand-write `RemoveField` + `AddField`, which is safe only because nothing populates this field today.
  Nothing in the tree assigns `tags` to a model instance; the only place it is declared outside the model
  is the frontmatter schema `content_base/schema.py:27`, `tags: list[str] | None = Field(None, ...)`,
  which must stop defaulting to `None` now that the field is non-nullable. This does **not** fix the admin
  filter: `list_filter` on `TopicAdmin:19`, `ActivityAdmin:31`, `CourseAdmin:75` and `CoursePartAdmin:103`
  uses `AllValuesFieldListFilter`, which lists whole values and is equally broken on either type. That fix
  needs a `SimpleListFilter` and stays in "do later".
- **`ContentCollectionItem.collection_old`** is dead source, not a dead column: three commented-out lines
  at `content_engine/models/courses.py:284-286`. The real column was renamed in
  `0003_rename_collection_contentcollectionitem_collection_old_and_more.py` and dropped in
  `0004_remove_contentcollectionitem_collection_old.py`. Delete the lines; no migration follows.
- **`RecommendedCourse`'s commented-out `form_progress` FK** (`learner_management/models.py:335-337`)
  documents a deliberately-deferred link. Keep it, and carry it into the new app unchanged.
- **`accounts.User`'s integer primary key.** Add a comment on the class recording that it is deliberate:
  `User` is the one object whose identity appears in a URL as a small sequential integer, and `email` is
  the actual auth key behind per-object permission checks. Without it, the next reader reads it as an
  oversight.
- **`default_auto_field`** is declared in 19 `apps.py` files and consulted by exactly two models,
  `accounts.User` and `SystemRoleAssignment`. Every other concrete model extends `SiteAwareModel`, which
  declares its own UUID pk. Keep all 19: Django's own reference states reusable applications defining
  models *must* set it, so a downstream project's `DEFAULT_AUTO_FIELD` cannot retroactively change what
  FLS's `makemigrations` would generate. Record the rule in §7 so nobody removes them as dead weight, and
  nobody adds one expecting it to do something on a `SiteAwareModel`-rooted app.
- **The GFK `object_id` type rule.** `UUIDField` where the target set is closed and guaranteed-UUID;
  `CharField(max_length=255)` exactly once, on `ObjectRoleAssignment`
  (`role_based_permissions/models.py:92`), where the target set is deliberately open. Record it in §7;
  change no code.

## 6. Testing

- `TimestampedModel` sets `created_at` and `updated_at` on insert; a later `save()` advances `updated_at`
  and leaves `created_at` unchanged. One parametrised test over the models that take the mixin beats one
  test each.
- Deactivating a role through each of the three `role_based_permissions/utils.py` call sites advances
  `updated_at`. This is the test that would catch the `QuerySet.update()` trap regressing.
- `QuestionAnswer` keeps its original `created_at` across a second `save_answers()` pass that changes the
  answer.
- Every installed app whose `AppConfig.name` starts with `freedom_ls.` either carries a
  `freedom_ls_`-prefixed label or is on the allowlist. That is the §5.2 probe, which must fail if
  `health`'s label is removed and pass with `icons` unlabelled. `test_conformance_meta.py`'s existing
  approach of proving a probe has teeth is the model.
- Every `icons` check id starts with that app's own registered `AppConfig.label`.
- Deleting a `FormQuestion` that has any `QuestionAnswer` raises `ProtectedError`; deleting a `Course` that
  has any registration raises `ProtectedError`.
- Deleting the `ContentType` a deadline points at leaves the deadline row alive, and it then reads as a
  whole-course deadline with `object_id` still populated. `clean()` passes and `content_item` resolves to
  `None`.
- Deleting a `WebhookEndpoint` leaves its `WebhookDelivery` rows with `endpoint=None` and `endpoint_url`
  still naming where the send was attempted.
- `has_delete_permission` returns `False` for every admin in §5.4, and every inline named there reports
  `can_delete` as `False`. Assert on the admin classes directly, as the existing per-app
  `tests/test_checks.py` modules assert on check functions.
- `danger_content_delete` still runs clean end to end with `QuestionAnswer.question` set to `PROTECT`.
- `unique_cohort_name_per_organisation` is enforced: two cohorts in different organisations on one site
  may share a name, two in the same organisation may not.
- A duplicate submitted through the form returns a field error rather than an `IntegrityError`, for every
  form that gains or keeps the mixin: the `Cohort`, `LearnerCourseRegistration`,
  `CohortCourseRegistration`, `Learner`, `CourseInterest`, `File` and `WebhookSecret` admins, and
  `educator_interface`'s `CohortForm`. These are the assertions that catch the §4.6 regression.
- `tags` accepts and round-trips a list of strings, and `__contains` matches a single tag.
- `test_migration_state_consistent` passes after the reset, and after every intermediate step.
- The full suite passes with no reference to `.collection` on a registration or recommendation model, and
  no reference to `UserCohortDeadlineOverride`, remaining anywhere in the tree.
