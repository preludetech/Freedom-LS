# Research: codebase (hide the messages icon for some users)

Question: what in the existing codebase does this work touch, reuse or conflict with? All paths are relative to the project root.

## 1. Where the icon is rendered today

- Single render site: `freedom_ls/base/templates/partials/header_bar.html:22`, inside `{% if user.is_authenticated %}`, as `{% messages_button %}` followed by `{% notification_bell %}` and `partials/header_bar_user_menu.html`. It is included once, from `freedom_ls/base/templates/_base.html:118`. `_base_interface.html` extends `_base.html`, so the educator interface uses the same header. There is no separate educator header. Anonymous users get `partials/login_prompt.html`.
- Tag: `messages_button()` in `freedom_ls/comms/templatetags/comms_tags.py:45`. It is an inclusion tag with no `takes_context`, so it cannot see the request or user. It returns `{"enabled": False}` if `config.MESSAGING_ENABLED` is false, else `{"enabled": True, "poll_seconds": config.MESSAGE_INBOX_POLL_SECONDS}`. The docstring says no per-page query is allowed: the badge loads itself.
- Template: `freedom_ls/comms/templates/comms/partials/messages_button.html`. All of it sits under `{% if enabled %}`. It holds the button (`#messages-button`, `aria-labelledby="messages-button-label"`), the lazy badge (`#messages-badge`, `hx-get` to `conversations:unread_badge`, `hx-trigger="load, refresh, conversationChanged from:body"`, `x-data="refreshTimer"`), and the panel (`#messages-panel`, `hx-get` to `conversations:recent`).
- The only gate is the global setting. There is no per-user check. A per-user decision therefore means giving the tag the request (`takes_context=True`, as `notification_bell` already does at `comms_tags.py:33`) or computing a value in a context processor.
- Context processors in `config/settings_base.py:204-217`: `site_aware_models.context_processors.site_config`, `accounts.context_processors.signup_policy`, `learner_management.context_processors.can_access_educator_interface`, `deployment...`, `base.context_processors.analytics_events`, plus pixel and tag processors. None concern messaging. `can_access_educator_interface` (`freedom_ls/learner_management/context_processors.py`) is the best precedent for a header flag that needs a query: it returns a `SimpleLazyObject`, so the EXISTS runs only when a template reads it, and anonymous users cost nothing.

## 2. The comms app and what already gates messaging

- Config: `freedom_ls/comms/config.py` (`CommsConfig(AppSettings)`, `config` singleton). `MESSAGING_ENABLED` defaults False (`config/settings_base.py:520`, True in `config/settings_dev.py:71`). The same class holds `MESSAGING_POLICY` (dotted path, default `freedom_ls.messaging_policy.policy.LayeredMessagingPolicy`), `MESSAGE_INBOX_POLL_SECONDS`, and others. The `AppSettings` pattern lives in `freedom_ls/base/app_settings.py`, with one `config.py` per app.
- Every messaging view is wrapped by `messaging_view` in `freedom_ls/comms/views.py:66`, which raises `Http404` when `MESSAGING_ENABLED` is false and handles login. So when the global switch is off, the URLs 404 as well as the icon hiding. When the switch is on, nothing but the icon would be hidden by a header-only change: `conversations:inbox`, `thread`, `start`, `recent`, `unread_badge` and the other URLs stay reachable by anyone logged in. They are still protected by the policy at send and start time, and by participant checks on threads (`participant_conversation()` 404s non-participants).
- Policy contract: `freedom_ls/comms/messaging_policy.py`. `MessagingPolicy` has `can_start`, `can_reply`, `can_reply_many`, `recipients_for(sender, site) -> QuerySet[User]` and `group_recipients`. `MessagingDecision` is deliberately not truthy (read `.allowed`). `MessagingRefusal` has SAME_USER, INACTIVE_USER, NO_RELATIONSHIP and CLOSED_BY_CONFIGURATION. The class is loaded through `get_messaging_policy()` (`freedom_ls/comms/messaging_loader.py`). `comms` may not import organisation or role code (`comms/tests/invariants/test_boundaries.py`), so any rule that needs organisation, cohort or course knowledge must live behind the policy seam or in a separate app, not in `comms`.
- Existing "can this user message anyone" signal: `_has_recipients(request)` in `freedom_ls/comms/messaging_views.py:303` calls `get_messaging_policy().recipients_for(sender=viewer, site=site).exists()`. It already hides "New message" buttons in the panel, the list and the placeholder (`has_recipients` in `messages_panel.html`, `conversation_list.html`, `thread_placeholder.html`, `thread.html`). The header button is not gated by it. This is the most natural reuse for "show the icon only when the user has someone to message or already has a conversation", but it costs a query on every page. The tag docstring and `test_a_page_render_runs_no_conversation_query` (`comms/tests/test_bell_tag.py:192`) forbid any `comms_conversation` query on a page render. A recipients query hits learner/cohort/role tables, not `comms_conversation`, so that test would still pass. It would still be a new per-page cost, so the lazy pattern (SimpleLazyObject or an htmx-loaded button) matters.
- A user with existing conversations but no current recipients (policy now closed) is a real case. The product doc says old conversations stay readable. Hiding the icon on `recipients_for().exists()` alone would strand those conversations and unread messages. The decision needs to cover "has conversations".
- Default policy: `freedom_ls/messaging_policy/policy.py::LayeredMessagingPolicy`, flags in `freedom_ls/messaging_policy/models.py`. `MessagingFlag` is inherit/open/closed. The three flags (`FLAG_NAMES`) are `learner_to_educator`, `learner_to_cohort_peer` and `learner_to_course_peer`. Rows exist at each level: `SiteMessagingConfig` (one per site, also `offered_educator_roles`), `OrganisationMessagingConfig`, `CohortMessagingConfig`, `LearnerMessagingConfig`, `LearnerCourseRegistrationMessagingConfig` and `CohortCourseRegistrationMessagingConfig` (these last two carry only the course-peer flag). Defaults come from `freedom_ls/messaging_policy/config.py`: `MESSAGING_DEFAULT_FLAGS` has `learner_to_educator: "open"` (changed by the ux-improve spec), and the peer flags are "closed". `MESSAGING_OFFERED_EDUCATOR_ROLES` defaults to `["cohort_admin"]`.
- Consequence for the free-course case: with the shipped defaults, a self-registered learner on the default organisation (`organisations.utils.get_default_organisation`, `Organisation.is_default`) in no cohort has no educator, so `recipients_for` is empty and the icon would be useless. A learner in a cohort has `learner_to_educator` open by default, so the icon appears. To make an organisation or cohort "closed for messaging", set the `learner_to_educator` flag to `closed` on its `OrganisationMessagingConfig` or `CohortMessagingConfig` (admin-managed). That already makes `recipients_for` empty, with no new model. The gap is only that the header icon ignores it. Note: educators and other colleagues are reachable through the role route (`_role_condition`, `colleagues_of`), not only the flags.
- No per-course "free" or "public" flag exists on a course. `freedom_ls/content_engine/models/courses.py` has `PriceKind` (FIXED, RANGE, DISCOUNTED, ON_REQUEST), `price_kind` and `CourseVisibility` (PUBLISHED, COMING_SOON, HIDDEN). There is no FREE kind. Course access goes through the `COURSE_ACCESS_BACKEND` seam (`freedom_ls/course_access/backends.py`, `CourseAccessType` at line 242; the shipped default is `course_applications/backends.py`). Organisation restriction is `Course.organisations` (M2M), with `learner_management/queries.py::is_course_open_to_organisation` and `LearnerCourseRegistration.self_registered` (`learner_management/models.py:250`). "Free" is therefore best modelled by organisation (the default organisation versus a customer organisation) or by messaging flags, not by a course field. A new "free" course concept would be out of scope unless the spec asks.
- Learner relations: `Learner` (user x organisation, per site) -> `CohortMembership` -> `Cohort` (organisation FK) and `LearnerCourseRegistration` / `CohortCourseRegistration`. A user can hold Learner rows in several organisations, so any per-user rule must say what happens when one organisation allows messaging and another does not (the policy takes the union of open routes).

## 3. Per-site and per-app settings patterns to follow

- Deployment settings via `AppSettings` / `Setting(default=...)` in each app's `config.py` (`comms/config.py`, `messaging_policy/config.py`, `learner_management/config.py` with `DEADLINES_ACTIVE`, etc.), documented in `docs/product/configuration-and-extension.md` (setting table near line 165-167).
- Per-site rows: `accounts.models.SiteSignupPolicy` (`allow_signups`, unique per site, read by the `signup_policy` context processor via the allauth adapter) and `messaging_policy.SiteMessagingConfig`. Pattern: a `SiteAwareModel` with a `UniqueConstraint` on site, overriding a settings default. A toggle for header visibility could be added as a field on `SiteMessagingConfig` or a new level, but this would add a migration (`makemigrations` rule) and a decision on whether it applies per site, organisation or cohort. The messaging flag levels already exist for organisation, cohort and learner.
- Feature toggles are all plain Django settings read through `config`. There is no general feature-flag library. Existing global-only toggles: `NOTIFICATIONS_ENABLED`, `MESSAGING_ENABLED`, `ALLOW_SIGN_UPS`, `DEADLINES_ACTIVE`, `COURSE_ACCESS_BACKEND` (see `spec_dd/1. next/corporate-job-course-recommendations/research_fls_backends_and_toggles.md` for an inventory).

## 4. Comparison: the notification bell

- `notification_bell` (`comms_tags.py:33`) takes the context and gates only on the global `NOTIFICATIONS_ENABLED`. It shows for every authenticated user. It computes `_unseen_count(request)` at render time (unlike messages, which loads the badge lazily). The notification views are not 404-gated the same way (`login_required_htmx` only). The bell hidden/shown tests are in `comms/tests/test_bell_tag.py` (`TestBellWhenNotificationsDisabled`, class near line 90).
- There is no per-user bell visibility. This work would introduce the first per-user header gating, so there is no pattern to copy beyond `can_access_educator_interface` (a per-user header flag) and the `has_recipients` helper.
- The two panels are coordinated: opening one closes the other (ux-improve spec, Alpine `messagesPanel` / `notificationBell` in `comms/static/comms/js/alpine-components.js`). Hiding the messages button must not break the bell's close logic (check the helper tolerates a missing sibling).

## 5. Educator side

- Same header and same tag. Educators also have messaging entry points that depend on `comms_config.MESSAGING_ENABLED` and are independent of the header: `LearnerMessagesPanel.has_permission` (`freedom_ls/educator_interface/views.py:825-826`, also lines 882, 934 and 1879), the learner quick view message box (`educator_interface/quick_views.py:83`). The ux-improve spec removed the educator Messages sidebar section, so for educators the header icon is the only route to the shared messages page (`/messages/`) and to colleague conversations. A rule that hides the icon for learners must not hide it for educators or colleagues. In `recipients_for`, educators with colleagues or learners are covered by the role route.

## 6. Tests that cover the header

- `freedom_ls/comms/tests/test_bell_tag.py`: `MESSAGES_MARKER = 'aria-labelledby="messages-button-label"'`, class `TestMessagesButton` (off -> absent; on -> panel `hx-get`; icon only; accessible name; lazy badge; no `comms_conversation` query on render). These render `learner_interface:dashboard` with `UserFactory()` and no Learner row, so they must keep passing as-is or be updated where the rule now hides the icon for a user with no relationships. This is a likely conflict: the default test user has no recipients, so a "hide when no recipients" rule would break the existing `MESSAGING_ENABLED = True` tests unless they set up a relationship.
- `comms/tests/conftest.py:12,18` turns on `NOTIFICATIONS_ENABLED` and `MESSAGING_ENABLED` for the comms suite. `comms/tests/test_messaging_views.py` checks the 404 when off. The educator tests (`educator_interface/tests/test_views.py`, `test_quick_views.py`, `test_sidebar.py`, `invariants/test_organisation_isolation.py`) toggle `MESSAGING_ENABLED`. Playwright: `comms/tests/playwright/test_messaging_flow.py` and `educator_interface/tests/playwright/test_quick_view_messaging_flow.py` (set `MESSAGING_ENABLED = True`). `messaging_policy/tests/test_policy.py` covers the policy. Test conventions: pytest, factories (`UserFactory`, `ConversationFactory`, `MessageFactory`, messaging_policy factories), `mock_site_context`, `logged_in_client`.

- `spec_dd/3. done/2026-11-01_12:45_user-communication-ux-improve/1. spec.md`: header button is icon-only; `#messages-badge` and `refreshTimer` polling unchanged; panel content loads lazily from `conversations:recent`; page renders run no conversation query; "New message" is shown only when the user has recipients; `learner_to_educator` default became "open"; the educator Messages section was removed; `conversations:inbox` URL name stays (login redirect and back links use it). - `spec_dd/3. done/2026-10-10_08:57_user-communication-3-messaging-policy/` (layered flags; research files `research_layered_rule_shape.md`, `research_flexible_configurable_comms.md`) and `2026-10-22_20:02_user-communication-4-direct-messaging/` (research_placement_and_closed_threads.md covers what happens to threads when the policy closes). ## 8. Design options this research surfaces (for the spec to decide, not decided here)

1. Add `takes_context=True` to `messages_button` and show the button only when the viewer "has messaging": at least one conversation (cheap `Conversation` participant EXISTS) or a non-empty `get_messaging_policy().recipients_for(...)`. Reuses `_has_recipients` logic. Cost: one or two EXISTS per page, unless made lazy. Risk: the existing no-conversation-query test, so the existence check has to be an exception or be loaded lazily.
2. A context-processor flag (SimpleLazyObject, like `can_access_educator_interface`) computed through a new method on `MessagingPolicy`, e.g. a base-class `can_message_anyone(user, site)` defaulting to `recipients_for().exists()`, so downstream policies can override and `comms` stays free of organisation code.
3. A new explicit flag (a field on the messaging config levels, or a site/organisation setting) that hides the icon without changing who may message. This adds a migration and a second concept alongside the existing open/closed flags, and risks the icon and the policy disagreeing. The existing flags probably already express "this organisation does not get messaging", so reuse is likely better.
4. Also decide whether the messages URLs stay reachable when the icon is hidden. Today they are reachable with `MESSAGING_ENABLED` on, so a header-only change is cosmetic. Consider whether to 404 or redirect, and the interaction with the login-redirect to `conversations:inbox`.

## 9. Open questions found in the code

- Users with conversations but zero recipients (policy closed later) must still see the icon and their unread badge.
- Learners with multiple organisations, and anonymous or no-Learner-row users (staff, site admins) must be handled by the rule.
- `recipients_for` returns a user queryset that may be expensive on big sites. A bounded EXISTS is used by `_has_recipients` already, so cost is acceptable per request but not free on every page.
- `Organisation.is_default` identifies the free or self-service organisation, but nothing marks a course as free. Confirm whether "free courses" means the default organisation.
