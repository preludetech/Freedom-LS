# Spec: hide the header Messages button from users with no use for it

Idea: `idea.md`. Research files sit alongside.

## Purpose

The header Messages button shows for every signed-in user whenever `MESSAGING_ENABLED` is on. A user
the messaging policy gives nobody to message, such as a learner on a free course with no cohort
admin, still gets a button that opens an empty panel. The button should appear only for users who
can message someone or who already have a conversation.

## Scope

In:

- A per-user check on the header Messages button (`messages_button` tag), derived from the messaging
  policy and the user's existing conversations.
- Tests and product docs for the new rule.

Out:

- A new setting, model field or toggle. Who may message whom is already configured through the
  messaging policy flags (`SiteMessagingConfig`, `OrganisationMessagingConfig`,
  `CohortMessagingConfig`, `LearnerMessagingConfig`, `LearnerCourseRegistrationMessagingConfig`
  and `CohortCourseRegistrationMessagingConfig`).
- A "free course" concept on `Course`.
- Access control on the messaging views. They keep their current behaviour.
- The educator surfaces outside the header (`LearnerMessagesPanel`, the quick view message box).
- A cache of the button decision.

## Decisions

1. **Visibility is derived from the policy, not configured.**
2. **An existing conversation keeps the button.** Messages raise no notification, so the badge is
   the only way to learn of a reply.
3. **One rule for every role.** An offered educator of a learner, or a colleague, is reached through
   `recipients_for` like any other recipient, so there is no special case for educators or staff.
4. **`comms` reaches organisation knowledge only through the policy seam.** `comms` must not import
   organisation or role code (`comms/tests/invariants/test_boundaries.py`).

## Requirements

### The rule (`freedom_ls/comms/messaging.py`)

- Add `has_recipients(user: User, site: Site) -> bool`: `get_messaging_policy().recipients_for(
  sender=user, site=site).exists()`. Move the body of `_has_recipients(request)` in
  `freedom_ls/comms/messaging_views.py` into it. `_has_recipients` either becomes a thin request
  wrapper or its call sites call `has_recipients` directly.
- Add `can_see_messages_button(user: User, site: Site) -> bool`: true when
  `ConversationParticipant.objects.filter(site=site, user=user).exists()` or `has_recipients(user,
  site)`. Filter on `site` explicitly: the site-aware manager filters only inside a request. The
  conversation check runs first and short-circuits, so a user with a conversation never pays for the
  recipients queries.
- A learner with `Learner` rows in several organisations sees the button if any route is open. This
  is the union `recipients_for` already computes.

### The header button (`freedom_ls/comms/templatetags/comms_tags.py`)

- `messages_button` becomes `takes_context=True`, like `notification_bell`. With
  `MESSAGING_ENABLED` off it returns `{"enabled": False}` with no query, as now. With it on, it
  returns `{"enabled": False}` when `can_see_messages_button(request.user,
  get_cached_site(request))` is false, so the button is left out of the HTML.
- Update the docstring: the render never runs the unread count. For a user with no conversation it
  runs the recipients queries of the configured policy, which for `LayeredMessagingPolicy` is about
  five queries.

## Testing

In `freedom_ls/comms/tests/test_bell_tag.py`, `TestMessagesButton`:

- Existing "on" tests use `UserFactory()` with no relationships, so each needs a conversation or a
  recipient. In `test_the_accessible_name_reports_the_unread_count` the conversation must exist
  before the first page load, because the badge `hx-get` is read from that render.
- Narrow `test_a_page_render_runs_no_conversation_query` so it matches the quoted
  `"comms_conversation"` table (closing quote included, or `"comms_conversation"(?!\w)`) and
  `comms_message`, not `comms_conversationparticipant`. It keeps proving that no unread-count query
  runs on render.
- Prove the short-circuit by comparing query counts: a user with a conversation runs none of the
  recipients queries.

New cases, each asserting the button marker (`aria-labelledby="messages-button-label"`) is present
or absent on `learner_interface:dashboard`:

- `MESSAGING_ENABLED` off: absent, and no messaging query runs.
- A plain user with no `Learner` row, no conversation and no recipients: absent.
- A staff user (`is_staff`) with no recipients and no conversation: absent.
- A learner in a cohort with a `cohort_admin` assigned on it, `learner_to_educator` at its default
  (open): present.
- The same learner with `learner_to_educator` closed on their organisation's
  `OrganisationMessagingConfig`: absent.
- A learner in two organisations, one with a reachable `cohort_admin` and one closed: present.
- No recipients but one existing conversation: present.
- A conversation on another site only: absent.
- An `organisation_admin` with an active `OrganisationMember` row, assigned through
  `assign_object_role`, and a `Learner` in that organisation: present.

Unit-test `can_see_messages_button` outside a request for the site filter.

With `MESSAGING_ENABLED` on, a user with no button gets a 200 from `conversations:inbox`.

Playwright: the existing messaging flow tests under `freedom_ls/comms/tests/playwright/` keep
passing. The bell tests in `test_notifications_flow.py` run with a user who has no conversation, so
running them with `MESSAGING_ENABLED` on proves the bell opens and closes with no messages button.

## Documentation and downstream

- `docs/product/messaging.md`: rewrite the sentences that say the header button shows for everyone
  ("for everyone, educators included"), and the "Turning It On" section, to state the rule. With
  messaging on, the button shows only to users who have someone they may message or an existing
  conversation. Closing `learner_to_educator` for an organisation or cohort hides it for those
  learners.
- `docs/product/configuration-and-extension.md`: in the messaging policy section, state that the
  header Messages button follows `recipients_for` and the user's existing conversations.
- Upgrade notes (written by `/fls-dev:update_upgrade_notes`): the header now calls the configured
  `MESSAGING_POLICY`'s `recipients_for` on every page render for users with no conversation. A
  downstream policy whose `recipients_for` is expensive pays that on every page.

## Success criteria

- A learner with no conversation, once an educator starts a conversation with them, sees the button
  and its unread badge on their next page load.
- A page render runs no unread-count query, and runs the recipients queries only for a user with no
  conversation.
- `/messages/` returns the page as before for a user without the button.
