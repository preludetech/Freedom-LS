# Plan: hide the header Messages button from users with no use for it

Spec: `1. spec.md`.

## What exists today

- `freedom_ls/comms/templatetags/comms_tags.py`: `messages_button` is a no-argument inclusion
  tag. With `MESSAGING_ENABLED` off it returns `{"enabled": False}`; on, it returns
  `{"enabled": True, "poll_seconds": ...}` for every signed-in user. `notification_bell` in the
  same file is the model for a `takes_context=True` tag that reads `context["request"]`.
- `freedom_ls/base/templates/partials/header_bar.html` renders `{% messages_button %}` then
  `{% notification_bell %}` inside `{% if user.is_authenticated %}`. The template
  `freedom_ls/comms/templates/comms/partials/messages_button.html` wraps everything in
  `{% if enabled %}`, so the tag's return value alone decides whether the button is in the HTML.
  No template changes are needed.
- `freedom_ls/comms/messaging_views.py` holds `_has_recipients(request)`: it casts
  `request.user` and `get_cached_site(request)` and calls
  `get_messaging_policy().recipients_for(sender=..., site=...).exists()`. Its callers are
  `_page_context`, `partial_inbox_poll` and `partial_recent_conversations`, each passing the
  result into a template as `has_recipients`.
- `freedom_ls/comms/messaging.py` is the request-free service module: every function takes
  `site` explicitly, and it already imports `get_messaging_policy` and
  `ConversationParticipant`. `has_recipients` and `can_see_messages_button` go here.
- `ConversationParticipant` (`freedom_ls/comms/models.py`) is a `SiteAwareModel` with
  `conversation`, `user` and `last_read_at`, and an index on `(user, site)`, so the participant
  existence check is a single indexed query.
- The configured policy out of the box is `LayeredMessagingPolicy`
  (`freedom_ls/messaging_policy/policy.py`). Its `recipients_for` returns `User.objects.none()`
  for an inactive sender, otherwise one `User` queryset built from `pk__in` subqueries. `_resolve`
  runs two queries (the sender's `Learner` rows and the `SiteMessagingConfig`), and the role
  condition reads the sender's site grants, so `.exists()` on the result is about five queries in
  total. The existing constant `QUERIES_RECIPIENTS = 4` in
  `freedom_ls/messaging_policy/tests/test_policy.py` is the policy's own count; the tag's tests
  do not pin a number.
- Default policy flags (`freedom_ls/messaging_policy/config.py`): `learner_to_educator` open,
  the two peer flags closed, `MESSAGING_OFFERED_EDUCATOR_ROLES = ["cohort_admin"]`. So out of the
  box a learner reaches an active `cohort_admin` of a cohort they are a member of, and nobody else.
- Tests for the tag live in `freedom_ls/comms/tests/test_bell_tag.py`, class
  `TestMessagesButton`, with `MESSAGES_MARKER = 'aria-labelledby="messages-button-label"'`. They
  render `learner_interface:dashboard` through `logged_in_client`, under `mock_site_context`. The
  autouse `_enable_messaging` fixture in `freedom_ls/comms/tests/conftest.py` turns
  `MESSAGING_ENABLED` on for every comms test, browser flows included. The file already imports
  `assign_object_role`, `OrganisationFactory` and `LearnerCourseRegistrationFactory`.
- The boundary invariant `freedom_ls/comms/tests/invariants/test_boundaries.py` fails if any
  runtime module under `comms` imports `learner_management`, `organisations`,
  `role_based_permissions` or `messaging_policy`. Test modules are exempt, so
  `test_bell_tag.py` may build learners, cohorts and roles directly.
- Factories: `LearnerFactory(user=..., organisation=...)`, `CohortFactory(organisation=...)`,
  `CohortMembershipFactory(cohort=..., learner=...)`, `OrganisationMemberFactory(user=...,
  organisation=...)` in `freedom_ls/learner_management/factories.py`;
  `OrganisationMessagingConfigFactory(organisation=..., learner_to_educator="closed")` in
  `freedom_ls/messaging_policy/factories.py`; `ConversationFactory(between=(a, b))` in
  `freedom_ls/comms/factories.py` writes both participant rows on the conversation's site, and
  takes `site=` to put the conversation on another `Site`; `SiteFactory` in
  `freedom_ls/tests/factories.py`.
- Table names carry the app label prefix: the policy's first read is
  `freedom_ls_messaging_policy_sitemessagingconfig`, the conversation table is
  `freedom_ls_comms_conversation` and the participant table
  `freedom_ls_comms_conversationparticipant`. The substring `sitemessagingconfig` is the marker
  for "the recipients queries ran", since only `LayeredMessagingPolicy` reads that table and the
  dashboard itself never does.
- `freedom_ls/comms/tests/playwright/test_notifications_flow.py` and `test_messaging_flow.py`
  are the browser flows the spec says must keep passing; no browser test is added.

## Slice 1: the button follows the rule

**Behaviour.** With `MESSAGING_ENABLED` on, the header Messages button renders only for a user who
has a conversation on the current site or whom the messaging policy offers at least one
recipient. With it off, nothing changes: the tag returns `{"enabled": False}` without a query.

Steps run in this order: the tests first and red (1a), then the service functions (1b) and the
tag (1c) to turn them green, then the browser flows (1d) and the tier (1e).

### 1b. `has_recipients` and `can_see_messages_button` in `freedom_ls/comms/messaging.py`

Add, next to `search_recipients` (the other function that reads `recipients_for`):

```python
def has_recipients(user: User, site: Site) -> bool:
    """Whether the policy offers ``user`` anyone to message on ``site``."""
    return get_messaging_policy().recipients_for(sender=user, site=site).exists()


def can_see_messages_button(user: User, site: Site) -> bool:
    """Whether the header shows ``user`` the Messages button on ``site``.

    A conversation keeps the button whatever the policy says now: messages raise
    no notification, so the badge is the only way to learn of a reply. That
    check runs first and short-circuits, so a user with a conversation never
    pays for the policy's recipients queries. ``site`` is filtered explicitly
    because the site-aware manager narrows only inside a request.
    """
    return (
        ConversationParticipant.objects.filter(site=site, user=user).exists()
        or has_recipients(user, site)
    )
```

`User` and `Site` are already imported under `TYPE_CHECKING` in this module, and the file has
`from __future__ import annotations`, so the signatures need no new imports. The arguments stay
positional, like `conversation_between(user_a, user_b, site)` in the same module.

### 1c. `messages_button` in `freedom_ls/comms/templatetags/comms_tags.py`

```python
@register.inclusion_tag("comms/partials/messages_button.html", takes_context=True)
def messages_button(context: template.Context) -> dict[str, object]:
    """The header Messages button, for a user who can message someone or
    already has a conversation.

    The unread count is not computed here: the badge loads itself after the
    page renders, so no page pays for that query. A user with no conversation
    pays for the configured policy's recipients queries on every page render.
    """
    if not config.MESSAGING_ENABLED:
        return {"enabled": False}
    request = cast("HttpRequest", context["request"])
    site = cast("Site", get_cached_site(request))
    if not can_see_messages_button(cast("User", request.user), site):
        return {"enabled": False}
    return {"enabled": True, "poll_seconds": config.MESSAGE_INBOX_POLL_SECONDS}
```

Imports to add: `from freedom_ls.comms.messaging import can_see_messages_button` and
`from freedom_ls.site_aware_models.models import get_cached_site`; `Site` and `User` under
`TYPE_CHECKING` (the module already has `from __future__ import annotations`). The tag reads
`context["request"]` the same way `notification_bell` does, and `header_bar.html` only renders it
inside `{% if user.is_authenticated %}`, so `request.user` is always a `User` here. The two early
returns stay separate: the first must run no query at all, and the shape matches
`notification_bell`.

> **Assumed default:** the docstring says the render pays for "the configured policy's
> recipients queries" and names neither `LayeredMessagingPolicy` nor its query count. Why:
> `comms` is kept ignorant of the `messaging_policy` app, and a count drifts as the policy
> changes; the count stays in this plan and in the upgrade notes. To change: 1c, the docstring.
