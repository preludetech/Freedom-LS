# QA: the dev database stays up

Most of this feature is infrastructure, so most checks run in a terminal. One scenario uses the
browser, to prove runserver traffic arrives as `fls_dev`.

## 0. Before you start

**Scenario 1 switches the shared dev server, and that affects every worktree on this machine.**
Nothing on disk is deleted, but the new server starts empty. Every other worktree has no database
until it is rebased onto this branch, and other projects using port 6543 lose theirs too. Get the
human's go-ahead before Scenario 1, step 2.

Conventions:

- Run everything from this worktree's root unless a step says otherwise.
- `SCRATCH` is a scratch directory outside the repo, e.g. `SCRATCH=$(mktemp -d)`. Every temporary
  worktree and file below goes in it, and the last scenario removes it.
- `DC="docker compose -f dev_db/docker-compose.yaml"`.
- Admin psql: `$DC exec postgres psql -U pguser -d postgres` (or `dev_db/bin_sh.sh`).
- `DB` is this worktree's per-branch database, `db_database_keeps_going_down`.
- Login for the browser scenario: `demodev@email.com` / `demodev@email.com`.
- Web server: `PORT=$(.claude/ds/scripts/find_available_port.sh)`, then
  `uv run python manage.py runserver $PORT`. Base URL `http://127.0.0.1:$PORT`. Stop it afterwards
  with `.claude/ds/scripts/kill_runserver.sh $PORT`.

## Scenario 1: switch to the new server

1. `docker ps --format '{{.Names}} {{.Label "com.docker.compose.project"}}'`. **Expect** the old
   postgres container under project `dev_db`.
2. With the go-ahead: `docker compose -p dev_db down`.
3. `$DC up -d`, then `$DC ps`. **Expect** `postgres` running and, within about 20 s, `(healthy)`.
   **Expect** `mailpit` running too.
4. `docker volume ls`. **Expect** `fls_dev_db_pgdata`.
5. `docker inspect $($DC ps -q postgres) --format '{{json .Mounts}}'`. **Expect** one mount, type
   `volume`, named `fls_dev_db_pgdata`, and no `bind` mount.
6. `docker inspect $($DC ps -q postgres) --format '{{.Config.StopTimeout}} {{.HostConfig.RestartPolicy.Name}} {{.HostConfig.Memory}} {{.HostConfig.ShmSize}}'`.
   **Expect** `30 unless-stopped 3221225472 268435456`.
7. `ls dev_db`. **Expect** no `docker-entrypoint-initdb.d`.

## Scenario 2: server settings and the role

1. In admin psql: `SHOW max_connections;` → **120**. `SHOW shared_buffers;` → **768MB**.
   `SHOW fsync;` → **off**.
   `SHOW superuser_reserved_connections;` → **3**.
2. `.claude/fls-dev/scripts/install_dev.sh`. **Expect** it finishes with migrations applied and no
   permission errors. It ran `dev_db_init.sh` once, via the rebuild script.
3. `uv run python manage.py create_demo_data --yes`, so the browser scenario has a site and a login.
4. In admin psql:
   - `SELECT rolsuper, rolcreatedb, rolconfig FROM pg_roles WHERE rolname = 'fls_dev';` →
     **`f`, `t`, `{idle_in_transaction_session_timeout=15min}`**.
   - `SELECT rolconfig FROM pg_roles WHERE rolname = 'pguser';` → **empty**.
   - `SELECT datname, pg_get_userbyid(datdba), shobj_description(oid, 'pg_database') FROM pg_database WHERE datname LIKE '%database_keeps_going_down%';`
     → `db_…` and `test_db_…` owned by **`fls_dev`**. `db_…` carries a JSON worktree stamp whose
     `repo` is this checkout's git common dir (`git rev-parse --path-format=absolute --git-common-dir`)
     and whose `worktree` is this worktree's root. `test_db_…` has no comment.
5. Run `.claude/fls-dev/scripts/dev_db_init.sh` a second time. **Expect** no error. It is
   idempotent.

## Scenario 3: runserver traffic runs as `fls_dev` (browser)

1. Start runserver on `$PORT` as in §0.
2. Open `http://127.0.0.1:$PORT/`, log in as the admin, and open a course page and `/admin/`.
3. In admin psql:
   `SELECT usename, application_name, state FROM pg_stat_activity WHERE datname = 'db_database_keeps_going_down';`
   **Expect** every row has `usename = fls_dev` and `application_name = runserver:-:db_database_keeps_going_down`.
4. `uv run python manage.py shell -c "from django.db import connection; connection.ensure_connection(); import time; time.sleep(30)" &`,
   then run the same query within 30 s. **Expect** a `shell:-:db_database_keeps_going_down` row as
   `fls_dev`.
5. Stop runserver.

## Scenario 4: a parallel test run

Needs a machine with more than 4 cores (`nproc`).

1. In admin psql: `ALTER ROLE fls_dev SET log_statement = 'ddl';` (temporary, undone in step 6).
2. `uv run pytest -n auto` in the background (no `-q`: it hides xdist's header). **Expect** the
   header to say `created: 4/4 workers`.
3. While it runs, in admin psql:
   `SELECT usename, application_name, count(*) FROM pg_stat_activity WHERE datname LIKE 'test_db_%' GROUP BY 1, 2;`
   **Expect** only `fls_dev`, with names `pytest:gw0:…` to `pytest:gw3:…`.
4. When it finishes, **expect** the suite to pass.
   `SELECT datname FROM pg_database WHERE datname LIKE 'test_db_database_keeps_going_down_gw%';` →
   **nothing**. Without `--reuse-db`, each worker drops its database at the end of the session.
5. `$DC exec postgres sh -c 'grep -h "CREATE DATABASE" "$PGDATA"/log/postgresql-*.log | tail -8'`.
   **Expect** each `test_db_…_gwN` creation to name `TEMPLATE "template0"`, and no
   `being accessed by other users` errors.
6. `ALTER ROLE fls_dev RESET log_statement;`
7. `uv run pytest -n 6 --reuse-db --no-cov freedom_ls/accounts`. **Expect** `created: 6/6
   workers`. An explicit count is not capped. (`--collect-only` never starts workers, so it can't
   show this.) `--reuse-db` keeps `_gw0` to `_gw5` for step 8.
8. `.claude/fls-dev/scripts/dev_db_delete.sh`. **Expect** it to drop `db_…`, `test_db_…` and every
   `_gwN` database (check with the step 4 query, which returns nothing). Then rerun
   `.claude/fls-dev/scripts/install_dev.sh` and `uv run python manage.py create_demo_data --yes` to
   restore this worktree.

## Scenario 5: the container restarts itself, and survives other worktrees

1. Note `docker inspect $($DC ps -q postgres) --format '{{.Id}} {{.State.StartedAt}} {{.RestartCount}}'`.
2. `$DC exec -u postgres postgres pg_ctl stop -m immediate -D /var/lib/postgresql/data`.
3. Without running any other command, poll `$DC ps` for up to a minute. **Expect** `postgres` back
   and `(healthy)`, and `RestartCount` one higher than in step 1.
4. `git worktree add --detach "$SCRATCH/wt-same" HEAD`, then
   `docker compose -f "$SCRATCH/wt-same/dev_db/docker-compose.yaml" up -d`.
   **Expect** "Running", not "Recreate". The ID and `StartedAt` from step 1's command (run again)
   are unchanged since step 3.
5. `git worktree add --detach "$SCRATCH/wt-old" origin/main`, then
   `docker compose -f "$SCRATCH/wt-old/dev_db/docker-compose.yaml" up -d`.
   **Expect** it fails on port 6543 (or 1025/8025) already being allocated. **Expect** the new
   `postgres` container still running with the same ID.
6. Leave the failed old-project container in place for Scenario 8.

## Scenario 6: logs survive the container

1. `$DC exec postgres sh -c 'ls "$PGDATA"/log'`. **Expect** `postgresql-<Day>.log` for today.
2. `$DC exec postgres sh -c 'tail -3 "$PGDATA"/log/postgresql-*.log'`. Note one line. **Expect**
   the prefix to show time, pid, `user@db` and `app=` / `client=`.
3. `$DC down`, then `$DC up -d`.
4. `$DC exec postgres sh -c 'grep -hF "<noted line>" "$PGDATA"/log/postgresql-*.log'`. **Expect**
   it is still there.

## Scenario 7: the idle-in-transaction timeout

1. `PGPASSWORD=password psql -h 127.0.0.1 -p 6543 -U fls_dev -d db_database_keeps_going_down`, then
   `BEGIN; SELECT 1;` and leave it.
2. In a second terminal, the same with `-U pguser`, `BEGIN; SELECT 1;` and leave it.
3. After 16 minutes, run `SELECT 1;` in both. **Expect** the `fls_dev` session reports its
   connection was terminated for the idle-in-transaction timeout. **Expect** the `pguser` session
   still works. `ROLLBACK;` and quit it.

## Scenario 8: `diagnose`

1. With the old-project container from Scenario 5 still present:
   `uv run python -m dev_db.diagnose; echo "exit $?"`. **Expect** a `fail` line naming the leftover
   `dev_db` project with next step `docker compose -p dev_db down`, and exit 1.
2. `docker compose -p dev_db down`. Rerun. **Expect** exit 0. Expect one line per check in order:
   engine reachable, engine kind (with a Docker Engine recommendation on Linux Desktop), the
   container (running, healthy, restart count, and "recreated at … from …" because it was created
   within 24 h), Postgres log signatures (the `idle-in-transaction timeout` from Scenario 7 counted),
   connections by `application_name` against 120, no long idle-in-transaction sessions, volume and
   `/dev/shm` use, stale-database count, reaper candidates and orphaned pytest processes.
3. Docker Desktop signature, without touching the real home directory:
   ```bash
   mkdir -p "$SCRATCH/home/.docker/desktop/log/host"
   echo "[2026-09-28T10:00:00Z] injecting event blocked for 5s" > "$SCRATCH/home/.docker/desktop/log/host/com.docker.backend.log"
   HOME="$SCRATCH/home" DOCKER_HOST=unix:///nonexistent.sock uv run python -m dev_db.diagnose; echo "exit $?"
   ```
   **Expect** the engine is reported unreachable, the finding names a Docker Desktop file-service
   failure and quotes that line, and exit 1. Repeat with a line containing `Service fs failed`.
4. With the engine stopped or unreachable and no Desktop logs (`HOME="$SCRATCH/empty"`): **expect**
   a plain "engine unreachable" failure with no crash or traceback.

## Scenario 9: `stale_dbs`

1. `git worktree add -b qa-stale-check "$SCRATCH/wt-stale" HEAD`, then in it run
   `.claude/fls-dev/scripts/dev_db_init.sh`. That creates and stamps `db_qa_stale_check`.
2. Back here: `uv run python -m dev_db.stale_dbs`. **Expect** `db_qa_stale_check` is **not** listed.
3. In admin psql: `CREATE DATABASE db_fcweb_qa;`. That's an unstamped, other-project name.
4. `git worktree remove "$SCRATCH/wt-stale"`, then `uv run python -m dev_db.stale_dbs`.
   **Expect** `db_qa_stale_check` and `test_db_qa_stale_check` listed with sizes. **Expect**
   `db_fcweb_qa`, this worktree's databases and `db` are not listed, and the unstamped count
   includes `db_fcweb_qa`.
5. Detached HEAD keeps its database: in this worktree `git checkout --detach`, rerun `stale_dbs`, and
   **expect** this worktree's `db_…` is not listed. Then `git checkout database-keeps-going-down`.
6. `uv run python -m dev_db.stale_dbs --drop`. **Expect** it prints the two drops. Rerun without
   `--drop`. **Expect** none listed.
7. Clean up: `DROP DATABASE db_fcweb_qa;` in admin psql, `git branch -D qa-stale-check`.

## Scenario 10: an existing worktree recovers on rebase

1. `git worktree add -b qa-rebase-recovery "$SCRATCH/wt-rebase" HEAD`. Do **not** run
   `install_dev.sh` there.
2. In it, run the rebase's rebuild and migrate steps:
   `.claude/fls-dev/scripts/rebuild_after_rebase.sh && uv run manage.py migrate`. **Expect** both
   succeed. The rebuild created `db_qa_rebase_recovery` owned by `fls_dev`.
3. In it: `uv run pytest tests -q --no-cov`. **Expect** pass. (`--no-cov`: the project-wide coverage gate fails any run of a subset.)
4. Clean up: in it run `.claude/fls-dev/scripts/dev_db_delete.sh`. Then here,
   `git worktree remove "$SCRATCH/wt-rebase"` and `git branch -D qa-rebase-recovery`.

## Scenario 11: Playwright MCP

1. `cat claude_plugins/django-stack/.mcp.json`. **Expect** `@playwright/mcp@<exact version>` (no
   `@latest`) and `"--idle-timeout", "600000"`, with the other args unchanged.
2. `ls -l claude_plugins/django-stack/scripts/reap_playwright_mcp.sh claude_plugins/django-stack/templates/wrapper_scripts/reap_playwright_mcp.sh .claude/ds/scripts/reap_playwright_mcp.sh`.
   **Expect** all three, executable. The template has `PLUGINS_ROOT="__PLUGINS_ROOT__"` and the
   `.claude` copy `PLUGINS_ROOT="."`.
3. Make an orphan that keeps its stdin open:
   `(setsid sh -c 'sleep 100000 | npx -y @playwright/mcp@<pinned version> --headless' > /dev/null 2>&1 &)`.
   `ps -o pid,ppid,etime,args -C sh,node | grep playwright`. **Expect** its parent is 1 or your
   `systemd --user`.
4. `.claude/ds/scripts/reap_playwright_mcp.sh`. **Expect** it is **not** listed. It is younger than
   an hour.
5. After more than an hour, rerun. **Expect** the `sh` root and its `npx`/`node`/`sleep`
   descendants listed with `pid, age, rss, command`. If a real leaked server from an ended session
   is on the machine with a Chromium child, **expect** the browser listed under it.
6. Make sure no live Claude Code session's MCP server is listed. Its parent is a live `claude`
   process.
7. `.claude/ds/scripts/reap_playwright_mcp.sh --kill`. **Expect** it reports what it ended, and
   `ps` no longer shows those PIDs. Rerun without arguments. **Expect** "No orphaned" output.
8. Open `claude_plugins/django-stack/skills/use-playwright/SKILL.md`. **Expect** a short note that
   the server's processes can outlive the session, pointing at the reaper.

## Scenario 12: reset and helper scripts

1. `dev_db/bin_sh.sh`. **Expect** a `psql` prompt as `pguser` on `postgres`. `\q`.
2. `dev_db/cleanup_devdb.sh` and answer `no`. **Expect** "Aborted", exit 1, and the container ID
   unchanged.
3. Only with the human's go-ahead, since it wipes every worktree's databases: rerun and answer
   `yes`. **Expect** `down -v` then `up -d`, a new empty volume, and a message to rerun setup. Then
   `.claude/fls-dev/scripts/install_dev.sh` and `uv run python manage.py create_demo_data --yes` here.

## Final cleanup

- `git worktree prune` and `rm -rf "$SCRATCH"`.
- `git worktree list` shows no `qa-*` or detached QA worktrees. `git branch --list 'qa-*'` is empty.
- `uv run python -m dev_db.stale_dbs` lists nothing from this QA run.
