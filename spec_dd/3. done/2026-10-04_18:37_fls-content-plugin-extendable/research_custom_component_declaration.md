# Research: declaring custom components so authoring tooling knows them

Source note: written from established knowledge of each system's documented behaviour, not fresh page fetches. URLs are the canonical docs; verify details before quoting them in the spec.

## 1. How other systems declare custom components

| System | Declaration format and location | Fields carried | Base plus extension | Tooling consumer |
|---|---|---|---|---|
| Markdoc | JS/TS config object. `tags: { callout: { render, children, attributes: { type: { type: String, default, required, matches: ['note','warning'], errorLevel } } } }`. It lives in the project's Markdoc config, which is also the renderer's config. | name, attributes, type, required, default, allowed values (`matches`), error level, children (allowed node types), `selfClosing`, custom `validate()` | Additive. The caller builds `config = { tags: { ...base, mine } }` by hand. | `Markdoc.validate(ast, config)` returns errors for unknown tags, bad attribute types, missing required attributes and bad children. Unknown tags are errors, not silent. |
| MDX | `components` prop or `mdx-components.tsx` mapping name to a React component. TypeScript props supply the types. | name and props (through TS types) | Additive or replace, depending on the merge the project writes. | Editor TypeScript plugin and `remark-mdx`. A missing component is a runtime error. There is no schema-level validation. |
| Docusaurus | MDX components swizzled or registered through `MDXComponents`. Admonitions and directives are remark plugins. | as MDX | Additive, through `src/theme/MDXComponents.js`, which spreads the defaults. | MDX/TS tooling only. |
| Hugo shortcodes | Template files `layouts/shortcodes/NAME.html`. Parameters are read with `.Get`. There is no schema. | name only. Parameters are implicit in template code. | Additive. The project layouts override theme and module layouts by path, so a same-name file silently shadows the built-in. | None beyond the template engine. An unknown shortcode is a build error. |
| Sphinx / MyST directives | Python: `app.add_directive("name", Class)`. The class carries `required_arguments`, `optional_arguments`, `option_spec` (option name to converter) and `has_content`. MyST enables directive syntax through `myst_enable_extensions`. | name, arguments, options with converter types, content allowed | Additive. Extensions are listed in `conf.py`. Registering a name twice warns. | Sphinx validates at build. Editor tooling such as the MyST LSP reads the registered directives. Unknown directives give a warning or error. |
| Web Components `custom-elements.json` (Custom Elements Manifest) | JSON schema file, generated by `@custom-elements-manifest/analyzer` from JSDoc and TypeScript source. It is published in the package (`customElements` field in package.json). | tag name, attributes, types, default, description, slots, events, CSS parts, examples | Per-package manifests. Tools merge them by listing several. | Storybook, IDE plugins, lit-analyzer, and a converter to VS Code custom data. |
| VS Code `html.customData` | JSON files (`html-data` v1.1 schema) listed in `.vscode/settings.json` or a package's `contributes.html.customData`. Fields are `tags: [{name, description, attributes: [{name, description, values: [{name}], valueSet}]}]`. | name, description, attribute names, allowed values (`values` or `valueSet`), references | Additive. Custom data adds to the built-in HTML data. | Completion, hover and basic validation in the editor. Unknown tags are not flagged unless a linter is added. |
| markdownlint | Custom rules are JS modules (`customRules` in config) that receive parsed tokens. | the rule's own logic | Additive. Rules are enabled or disabled individually by name. | The CLI and the editor extension. The built-in MD033 `allowed_elements` is a plain list of allowed HTML tags with no attribute schema. |
| Vale | `.vale.ini` plus YAML style files, with a `Vocab` accept list. | token patterns | Additive via `BasedOnStyles`. | Prose rules only. It has no component schema. |

Patterns in the evidence:
- Only Markdoc and Sphinx use one declaration for both rendering and validation, and both include attribute types, required flags and allowed values. The HTML-oriented formats (`html.customData`, Custom Elements Manifest) are tooling-only descriptions, with `description` and `values` as the common fields.
- Every system extends additively. The base set is never replaced. The merge is either explicit code (Markdoc spread) or a list of sources (customData files, Sphinx extensions).
- The Custom Elements Manifest convention is "generate it from source, ship it with the package". That is the one widely adopted example of a machine-readable declaration produced from code.

## 2. Single source of truth versus hand-maintained docs

Patterns seen:
1. The renderer config is the schema (Markdoc, Sphinx). Validation reads the same object that renders. There is no drift because there is one object. The cost is that the config must carry authoring metadata (descriptions, types) that rendering does not need.
2. The manifest is generated from code (Custom Elements Manifest analyzer, `vscode-custom-data` generators). A CI step regenerates it and fails if `git diff` is non-empty. Storybook `autodocs` follows the same idea.
3. A hand-written side file (`html.customData`, a hand-kept docs page). It is cheap and works for any stack, but it drifts. Projects mitigate this with a CI check that every name in the renderer appears in the side file, and the reverse.
4. Docs as the contract with a conformance test. Hugo and Vale projects usually do this with a content-fixture build in CI that fails on an unknown shortcode.

Relevance to FLS: `MARKDOWN_ALLOWED_TAGS` carries only tag to attribute names, with no types, required flags, descriptions or allowed values. It is therefore enough for pattern 3's name-level check, but cannot alone supply what the `widget-reference` files carry (description, examples, required attributes). Options are (a) export a manifest of tag and attribute names from the setting and have the plugin read it, with richer metadata staying hand-written per widget; (b) a hand-written per-widget declaration in the concrete project, with a check that its tags and attributes match `MARKDOWN_ALLOWED_TAGS`; (c) extend the setting so each widget is declared once with metadata, and derive `MARKDOWN_ALLOWED_TAGS` from it (Markdoc's model).

## 3. Pitfalls and complaints

- Silently ignored unknowns. A sanitiser that strips unlisted tags (as FLS does) gives no author feedback. Markdoc's decision to make unknown tags a validation error is the counterexample. MDX gets a runtime error, Hugo a build error. Silent stripping is the hardest failure for authors to notice.
- Stale docs. Hand-written component documentation drifts from the code. The usual fix is generation or a CI check, as in section 2.
- Override versus extend confusion. Where a config is a complete set, projects forget the built-ins when they add one entry. This is the same failure FLS has with `MARKDOWN_ALLOWED_TAGS` and `.fls-content.yaml` lists. Mitigations seen: a merge helper (`{**BASE, **mine}`, Markdoc's spread, Docusaurus's `...MDXComponents`), or a documented `EXTRA_` setting that is additive while the full setting stays authoritative. Hugo's silent path shadowing and Sphinx's duplicate-registration warning show that name collisions with built-ins need an explicit policy (error, warn or last wins), because the default in most systems is to silently shadow.
- Declaration without enforcement. `html.customData` gives completion but flags nothing, so authors still ship unknown tags unless a validator runs in CI.
- Attribute sets are the easiest part to get wrong: an attribute missing from the allowed set is stripped silently, even when the tag is allowed.

## Options with evidence (no plan)

- Additive declaration with an explicit collision rule (all systems above are additive).
- Declaration generated from the setting, plus hand-written metadata (Custom Elements Manifest approach).
- Single declaration that drives both the allow-list and the plugin (Markdoc, Sphinx).
- Validator that reports tags and attributes missing from the declaration instead of stripping silently (Markdoc validation).
- CI parity check between `MARKDOWN_ALLOWED_TAGS` and the declaration (drift prevention in pattern 3).
