  - a bullet list ("N new accounts will get a setup email.", "Existing accounts keep their names.", "Counts can change if someone else...");

Exists. `learner_import_template` view, URL `learner_import_template`, plus `template_url` in the upload context (carries `?cohort=` for cohort imports so a cohort importer is not 403'd; test `test_a_cohort_page_importer_can_download_the_template`). ## 4. Is import synchronous? Is "importing" meaningful?

Hybrid. On POST to `learner_import_preview`, status flips to `queued`. If `add_count <= BULK_BACKGROUND_THRESHOLD` (default 250) `run_learner_import` runs inline in the request, then the redirect (303) to `learner_import_result` renders the finished result. Above the threshold it is enqueued (`educator_interface/tasks.py` `_run_learner_import_task`) and the result page renders the "Waiting to start." / "N of M rows processed." progress with a 2s HTMX poll (`hx-trigger="every 2s"`) until done or failed. So the importing state is real but only seen for large imports (> threshold; tests set `BULK_BACKGROUND_THRESHOLD` low to exercise it). It reuses the shared `partials/run_status.html` (used by both the page and the polled fragment; the test asserts `#run-status`, `role=status`, `hx-trigger="every 2s"`, `hx-get` status URL, "Waiting to start.", a `progress` element, and that done drops the trigger). The restyle must keep one template serving the first render and every poll. The design's "You can leave this page - the import continues in the background" matches the existing background behaviour for large imports only; the existing preview note "This import runs in the background. The result page will show progress." is the analogue.

## 7. Conflicts and constraints to flag for the spec

- The design's content disagrees with the product in many places (1,000 rows and 5 MB vs 2000 rows and 1 MB; columns first_name/last_name/email/cohort_code/location/licence_held vs email/first_name/last_name/cohort with only email required; update/skip and invitation options; sample file; cohort codes; by-cohort counts; Cancel; Replace file). The spec and existing behaviour win; these are out of scope.
- Three-step stepper stays "Upload / Preview / Result" (the design says "Upload file / Review / Import" with Importing and Done sharing step 3). Existing tests freeze the labels.
- No component for the drop zone, the numbered stepper, or an icon for file/upload exists; per design.md do not add new theme tokens or icons. Where the theme cannot express it, drop the treatment.
- `c-callout` and the current inline alert differ in a11y hooks (see section 5).
- The review page currently uses a pure server-rendered, no-JS flow with a single GET page and filter links. HTMX is used only for the result poll. Keep it so unless the spec asks otherwise.
- CLAUDE.md rules: no new abstract components if an existing one does the job; keep TODO/@claude comments (none seen in these templates); components own their styling; no raw design colours.
