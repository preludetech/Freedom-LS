# Spec: Lead monitoring API, course applications

Spec 2 of 6 in the Lead monitoring API effort, from `idea.md` beside this file. The effort-wide
conventions, dependencies and out-of-scope list are in the "Lead monitoring API" section of
`spec_dd/1. next/roadmap.md`.

## Purpose

Lead monitoring scripts get course applications today only as the admin's spreadsheet export,
whose answer columns are named after question text and shift as forms change. This spec adds the
API endpoint `GET /api/v1/course-applications/`. An API key with the `course_applications` API
scope reads every `CourseApplication` on its site there, drafts included, with each application's
answers nested and keyed by question id. `updated_since` returns every application whose
submission, answers or applicant details changed since a given time.

## Scope

In:

- List and detail API endpoints for `CourseApplication`, on child 1's API framework, for
  signed-in and anonymous applicants in one list.
- A nested `answers` array on each application.
- Making `CourseApplication.updated_at` move when the application's sitting, answers, files,
  anonymous applicant or user change, and indexing it for the site-scoped keyset.
- One shared answer-value function used by both this API endpoint and the admin export.
- `docs/api.md` and `docs/product/security-and-data-handling.md`.

Out (beyond the effort-wide list in the roadmap):

- A server-side `is_submitted` filter. Scripts filter on the field.
- Downloading uploaded files, or links to them.
- `AnonymousApplicant` consent evidence (`consent_ip_address`, `terms_version`, `consented_at`)
  and claim state.
- Linking an anonymous application to signup attribution.
- Application review state, decisions and the `view_application` permission.
- Any change to the course applications admin export's output.
- A deletion feed: a deleted application simply stops appearing.
- Moving `updated_at` when the course or form definition changes (course title, question text or
  type, option text, page or question order).

## Decisions

- **`updated_at` is a stored column bumped by its children, not a computed `Greatest()`.** A
  computed value cannot be indexed, cannot be named `updated_at` beside the real field, would force
  a change to child 1's `ApiKeysetPagination`, and cannot see a deleted answer. The users API
  endpoint set this precedent with `accounts/signals.py`.
- **Course and form-definition edits do not move `updated_at`.** They are rare, and a bump would
  touch every application of the course. A periodic full pull picks them up.
- **The column moves on any write to the application's `FormProgress`, including a form page being
  reached.** Pollers re-read a few unchanged applications; that is cheaper than a second timestamp.
- **Saves that touch only fields the API never returns do not move it.** A User save with
  `update_fields == {"last_login"}` (every sign-in) and an `AnonymousApplicant` save whose
  `update_fields` is a subset of `{"claim_email_sent_at", "updated_at"}` (the claim email going
  out) are skipped. Any other User save moves the user's applications, because `applicant_email`
  and `applicant_name` come from the user.
- **An unanswered question has no entry in `answers`.** The database holds no `QuestionAnswer`
  row for it.
- **An answer row that holds nothing has `value: null`**, never `""` or `[]`, for every question
  type.
- **No backfill migration.** The API endpoint is new, so every consumer's first run is a full pull.
- **Course is two flat fields, `course_id` and `course_title`**, as the idea asks.

## Requirements

### `freedom_ls/course_applications/models.py`: `CourseApplication`

- Add `models.Index(fields=["site", "updated_at", "id"], name="courseapp_site_updated_idx")` to
  `Meta.indexes`, in a new migration. Mirrors `accounts_user_site_updated_idx` on `User`.
- `updated_at` stays `auto_now`. Its meaning widens to "the application, its sitting, answers,
  files, anonymous applicant or user last changed".

### `freedom_ls/course_applications/receivers.py`: what moves `updated_at`

Each receiver bumps with
`CourseApplication._base_manager.filter(<match>).update(updated_at=timezone.now())`, the pattern
of `touch_user_updated_at` in `freedom_ls/accounts/signals.py`. The base manager works with no
request and with a request for another host, and `update()` moves only `updated_at`. Receivers
live here, not in `form_engine`, because `form_engine` must not import `course_applications`.

| Signal | Sender | Match |
| --- | --- | --- |
| `post_save` | `FormProgress` | `form_progress_id=instance.pk` |
| `post_save`, `post_delete` | `QuestionAnswer` | `form_progress_id=instance.form_progress_id` |
| `post_save`, `post_delete` | `QuestionAnswerFile` | `form_progress__answers__id=instance.answer_id` |
| `post_save` | `AnonymousApplicant` | `anonymous_applicant_id=instance.pk`, with the skip above |
| `post_save` | `User` (`settings.AUTH_USER_MODEL`) | `user_id=instance.pk`, with the skip above |

The events these must cover:

1. Submitting a sitting (`FormProgress.complete()`).
2. Saving a text or option answer (`FormProgress.save_answers`). Selected options change through
   `selected_options.set()`, which sends no `post_save`. They are covered because `save_answers`
   saves the answer after setting them, and a test pins that.
3. Clearing an answer (`self.answers.filter(question=question).delete()` in `save_answers`).
4. Uploading, replacing and removing a file (`freedom_ls/form_engine/views.py`).
5. An anonymous applicant's details changing (`claims.update_applicant_email`).
6. A claim (`claims.attach_to_user`).
7. A signed-in user changing their name, or their email by `save()` or through allauth's
   email-change flow.

Any write path that changes a value the API endpoint returns and sends no `post_save` or
`post_delete` (`QuerySet.update()`, `bulk_create`, `bulk_update`, or an allauth path that skips
`User.save()`) bumps `updated_at` explicitly.

Each receiver adds one UPDATE query to its sender's writes. Existing tests that pin an exact query
count across such a write get their counts updated in the same change.

### `freedom_ls/form_engine/exports.py`: one answer-value function

Add `answer_value(answer: QuestionAnswer) -> str | list[str] | None` and rebuild `answer_cell` on
it, so the export and the API cannot drift:

| `question.type` | `answer_value` returns |
| --- | --- |
| `checkboxes` | selected option texts as a list, sorted by `QuestionOption.order`; `None` if none selected |
| `multiple_choice`, `dropdown` | a string: the selected option's text, or several joined with `"; "` in `QuestionOption.order`; `None` if none |
| `file_upload` | `answer_file.original_filename`; `None` if no file or the name is empty |
| all other types | `text_answer` as stored (dates and times are already ISO text, numbers stay strings); `None` if empty |

`answer_cell` returns `""` for `None` and joins a list with `"; "`. Its output stays byte-for-byte
what it is now for every input; the existing export tests must pass unchanged.

### `freedom_ls/course_applications/api.py` (new)

Copy the shape of `freedom_ls/accounts/api.py`. `autodiscover_modules("api")` in
`freedom_ls/api/urls.py` picks the module up; nothing in `freedom_ls/api/` changes. The
`course_applications` API scope already exists (`ApiScope.COURSE_APPLICATIONS`).

- `QuestionAnswerApiSerializer`, fields in this order:

  | Field | Source | JSON |
  | --- | --- | --- |
  | `question_id` | `question_id` | UUID string |
  | `question_text` | `question.question` | string |
  | `question_type` | `question.type` | one of the `form_engine.enums.QuestionType` values |
  | `value` | `answer_value(answer)` | string, array of strings, or `null` |

  Declare `value`'s schema explicitly (`extend_schema_field`) so the OpenAPI schema shows a string,
  an array of strings, or null, not an untyped field.

- `CourseApplicationApiSerializer`, explicit fields in this order, all read-only: `id`,
  `applicant_email`, `applicant_name`, `is_email_verified`, `course_id`, `course_title` (from
  `course.title`), `is_submitted`, `submitted_time`, `created_at`, `updated_at`, `answers`.
  `is_submitted`, `submitted_time`, `is_email_verified`, `applicant_email` and `applicant_name`
  read the model properties, never re-deriving them, so they follow when the application review
  work adds a `state`. `answers` is `[]` when `form_progress` is null, and is ordered by the
  question's `form_page.order`, then `question.order`, then `question_id`. No `AnonymousApplicant`
  consent or claim field appears.

- `CourseApplicationFilterSet(UpdatedSinceFilterSet)` with empty `Meta.fields`.

- `CourseApplicationApiViewSet(ReadOnlyApiViewSet)` with
  `filterset_class = CourseApplicationFilterSet`,
  `required_scope = ApiScope.COURSE_APPLICATIONS` and
  `serializer_class = CourseApplicationApiSerializer`. `get_queryset()` starts from
  `CourseApplication._base_manager`, as users does, and loads everything in a fixed number of
  queries, whatever the page size:
  - `select_related("user", "anonymous_applicant", "course", "form_progress")`;
  - a `Prefetch("form_progress__answers", queryset=QuestionAnswer._base_manager...)`, ordered as
    above, with `question__form_page` selected and `answer_file` prefetched;
  - inside it, a nested `Prefetch("selected_options", queryset=QuestionOption._base_manager.all())`.
    The M2M related manager is otherwise built on the site-filtered default manager, so the request
    host would filter option values.

- `router.register("course-applications", CourseApplicationApiViewSet, basename="course_application")`,
  giving `api:course_application_list` and `api:course_application_detail`.

## Testing

Tests go in `freedom_ls/course_applications/tests/test_api.py`, `.../tests/test_receivers.py` and
`freedom_ls/form_engine/tests/`, following `freedom_ls/accounts/tests/test_api.py` and the helpers
in `freedom_ls/api/tests/`. Prove:

- **Access:** no API key is 401; an API key without `course_applications` is 403 on list and
  detail; an API key with it is 200. Another site's application is absent from the list and 404 on
  detail. POST, PUT, PATCH and DELETE are refused.
- **Shape:** the exact key set of an application and of an answer entry, in order. One signed-in
  and one anonymous application come back in the same list with the right `applicant_email`,
  `applicant_name` and `is_email_verified`. A draft has `is_submitted: false` and
  `submitted_time: null`. An application with no sitting has `answers: []` and `submitted_time`
  equal to `created_at`. Detail returns the same object as the list entry.
- **Answer values:** one test per row of the `answer_value` table, including each `None` case and
  a `multiple_choice` row holding two options. A file answer's response holds no storage key, path
  or URL. Answers come back in page, question, then id order. An unanswered question has no entry.
- **Host independence:** with the request's site context set to another site, option values and
  answers still come back complete.
- **Export unchanged:** the existing `answer_cell` and admin export tests pass without edits.
- **Changed-since:** for each of the seven events under the receivers, `updated_at` moves and an
  `updated_since` request from just before the event returns the application. A User save with
  `update_fields={"last_login"}` and an `AnonymousApplicant` save of only `claim_email_sent_at` do
  not move it.
- **Paging:** through `collect_pages` over the client, more applications than the page size sharing
  one `updated_at` page through with no row lost or repeated. `updated_at` round-trips at
  microsecond precision.
- **Query count:** a list with 1 application and one with several, each with answers of every
  kind, run the same number of queries (compared with `CaptureQueriesContext`), bounded above with
  `django_assert_max_num_queries`.
- **Schema:** `/api/v1/schema/` describes `answers` entries and `value`'s three shapes.

## Documentation and downstream

- `docs/api.md`:
  - Update the intro ("Today there is one") and the API-scope note ("Only `users` has an API
    endpoint so far").
  - Add a `## Course applications` section after `## Users`, in the same layout: the API endpoint
    table, a Fields table, an Answers table with the value-by-type rules, and
    `### What moves `updated_at``. That subsection lists the seven events, says which saves do not
    move it, and says course and form-definition edits never do, so scripts that need current
    titles should do a periodic full pull. Add a one-line warning that the list includes drafts,
    so scripts filter on `is_submitted`. Add a "Who applied" note: the contact fields come from
    the user when signed in and from the anonymous applicant otherwise, and an anonymous address
    is unverified. Say that a file upload gives the filename only, and that deleted applications
    are not reported.
  - Extend the existing Python example so one loop, parametrised by path, syncs both `users` and
    `course-applications`, with a separate checkpoint per path. No second copy of the loop.
    `freedom_ls/api/tests/invariants/test_api_docs.py` must still pass.
- `docs/product/security-and-data-handling.md`: in the summary bullet and `### API Access (built)`,
  say that an API key with the `course_applications` API scope reads applicants' names, email
  addresses and answers. Uploaded files are exposed as filenames only, never the file or a link.
  Consent evidence and claim state are not exposed.
- Upgrade notes: the new migration (index only), and that `CourseApplication.updated_at` now
  moves when the application's sitting, answers, files, anonymous applicant or user change.

## Success criteria

- `GET /api/v1/course-applications/` with a `course_applications` API key returns its site's
  applications, drafts and both applicant kinds included, each with the fields and `answers`
  above; `GET /api/v1/course-applications/<id>/` returns one, and 404 for another site's id.
- Every bullet under Testing has a passing test.
- `docs/api.md` documents the API endpoint, and its example compiles; the security doc names the
  new exposure.
