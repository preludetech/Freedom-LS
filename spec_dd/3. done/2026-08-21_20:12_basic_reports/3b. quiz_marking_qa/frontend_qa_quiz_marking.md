# Frontend QA: multi-select quiz scoring fix (student-facing)

Manual browser verification for the multi-select (`checkboxes`) quiz scoring fix and everything it
touches outside the report: the quiz runner, the results page, the course player, the student
dashboard, the educator live panel and the demo content. This changes existing student-facing
behaviour, so it needs its own pass. None of it is covered by the automated suite.

This is one of **two** QA plans for this spec. The other,
`../3a. report_generation_qa/frontend_qa_report_generation.md`, covers report generation, the PDF,
permissions and the system checks. The two can be run in either order and by different people.

### Forms with no pass mark are a supported configuration, not an edge case

`Form.quiz_pass_percentage` is `blank=True, null=True`. **Leaving it unset is a normal, intended
authoring choice** — a questionnaire, a survey, a self-assessment, a practice quiz, or any form
that should report a score without ever pronouncing the learner passed or failed. Authors will do
this routinely.

Everything that touches a form must therefore treat "no pass mark" as an ordinary state that
renders cleanly, never as a misconfiguration to reject. The rule for every surface in this plan:

> **A missing pass mark means "no verdict". It must never mean an error page, a blank panel, or a
> missing row.** Show the score; omit the pass/fail judgement.

Do not treat a crash on a no-pass-mark form as acceptable on the grounds that the author "should
have set one". They should not have to. Any surface that calls `FormProgress.passed()` — which
raises `ValueError` when `quiz_pass_percentage is None` — must guard the call.

Keep **at least one** no-pass-mark form in the fixture set for the whole run, reachable from a
student account and from a cohort, so QA 12.2 and QA 12.5 both exercise it. The report's half of the
same rule is the sibling plan's QA 2.8.

### Free-text questions do not appear in scored quizzes

**A quiz that gets scored will not contain `short_text` / `long_text` questions.** Free-text
belongs in questionnaires, surveys and reflective forms — the kinds of form that collect answers
without producing a mark. It is not an authoring pattern to mix free-text into a `strategy: QUIZ`
form that produces a score.

This matters for how fixtures are built and how results are read:

- **Build the scored-quiz fixtures from option-backed questions only** (`multiple_choice` and
  `checkboxes`). A quiz built that way can actually reach 100%, which is what makes pass marks and
  RAG bands meaningful.
- A fixture that mixes free-text into a scored quiz will show a **score ceiling below 100%**,
  because free-text questions count toward `max_score` but can never be scored correct. If you see
  a quiz that cannot reach 100%, check the fixture before reporting a scoring bug — it is far more
  likely to be an unrealistic fixture than a defect.
- Free-text is still worth exercising, but **in a non-scored form**, and the check is that the
  answer is captured and displayed — not that it is marked. That is QA 12.4.

If you do find free-text inside a `strategy: QUIZ` form in real authored or demo content, treat
that as an **authoring-content finding** to call out in the upgrade notes, in the same way QA 13.3
treats a `multiple_choice` question with more than one correct option.

## QA 11 — Checkbox scoring, student view (success criterion 8)

Use `qa_create_form_question_types` — it builds a checkbox question with **two correct options of
three** — inside a quiz form (`strategy: QUIZ`, `quiz_show_incorrect: true`, a `quiz_pass_percentage`
set).

**Score the quiz out of option-backed questions only.** Free-text does not belong in a scored quiz
(see "Free-text questions do not appear in scored quizzes" above), so if the fixture command
includes `short_text`/`long_text` questions in this form, either drop them from the fixture or
compute expected percentages excluding them — otherwise the quiz cannot reach 100% and every
expected percentage below will be wrong. Note the resulting maximum score in `qa_report.md` so the
figures on the results page can be checked against it.

Log in as a student and take the quiz repeatedly, checking the results page each time:

| What you tick | Expected score for that question | Expected on the results page |
|---|---|---|
| All three options | **0** — wrong | Question listed under incorrect answers |
| The two correct options only | **1** — right | Not listed as incorrect |
| One of the two correct options | **0** — wrong | Listed as incorrect |
| Both correct plus the incorrect one | **0** — wrong | Listed as incorrect |
| Nothing | **0** — wrong | Listed as incorrect |

The headline regression is row 1: **ticking everything must no longer score full marks.**

For each case confirm the **score and the incorrect-answer list agree** — a question counted wrong in
the score must appear in the incorrect list, and vice versa. A disagreement here is the exact bug this
fix exists to close.

## QA 12 — Knock-on effects of the scoring change

1. **Pass/fail and navigation:** take a quiz where the checkbox question is the difference between
   passing and failing, and fail it. **Expect** the results page shows the failed state, and the
   course player blocks progression to the next item (FAILED, not COMPLETE). Retake and pass —
   **expect** progression unblocks. This needs a course whose quiz is not the last item; ask
   `fls-dev:qa-data-helper` if the fixture set has none.
2. **Unset pass mark:** take a quiz whose `quiz_pass_percentage` is `None` — a supported
   configuration, see "Forms with no pass mark" above. **Expect** the results page renders with a
   score and **no** pass/fail verdict, and **no** error page.

   Do not stop at the results page. A missing pass mark is read wherever a course item's status is
   computed, so one completed attempt can break pages far away from the quiz. After submitting,
   walk **all** of these as the same student and expect every one to render:

   - the results page (`/courses/<slug>/<index>/complete`)
   - the course player for that item (`/courses/<slug>/<index>/`)
   - the course home and course detail pages
   - **the student dashboard (`/`)** — it builds the course index for every registered course
   - log out and log back in — login redirects to the dashboard, so a broken dashboard locks the
     student out of the platform entirely

   A 500 on any of these is a **critical** failure, not a cosmetic one: it makes the student's
   account unusable, and the only route back is deleting their `FormProgress` row.

   Then repeat the walk with a **second** course also registered to that student, to confirm an
   unrelated course still opens — that tells you whether the breakage is scoped to the affected
   course or global.
3. **Single-select multiple choice is unchanged:** answer a `multiple_choice` question correctly and
   incorrectly. **Expect** identical behaviour to before the change.
4. **Free-text questions:** answer a `short_text` / `long_text` question **in a non-scored form**
   (a questionnaire or survey — free-text does not belong in a scored quiz, see "Free-text
   questions do not appear in scored quizzes" above). **Expect** the answer is saved and shown
   back, the form completes normally, and no pass/fail or incorrect-answer machinery appears at
   all.

   Separately, as a **defensive** check only: if a `strategy: QUIZ` form does contain free-text,
   confirm it scores 0 and does **not** appear in the incorrect-answers list. This configuration
   should not exist in authored content, so a failure here is low priority — but it should not
   render a broken card with empty "Your answer" and "Correct answer" blocks either. Record it as
   a robustness finding rather than a user-facing bug, and check whether the fixture that produced
   it was realistic.
5. **Educator live panel:** as the admin/educator, open the cohort course progress panel in the
   educator interface for a cohort containing these attempts. **Expect** quiz percentages render, the
   panel does not error, and a quiz with no pass mark shows no verdict rather than crashing. Check it
   at tablet width too — it is a wide table on a custom frontend surface.
6. **Historical attempts are not rescored:** note a checkbox attempt's score from *before* the fix (or
   have `fls-dev:qa-data-helper` craft one: every option ticked, stored score full marks, as the old
   scoring would have recorded it). After the fix, reload the student's results page. **Expect** the
   stored score is **unchanged** — the fix scores new submissions, it does not retroactively rewrite
   history — while the incorrect-answer list, which is derived at read time, now marks that question
   wrong. The two disagreeing on this page is the expected outcome; confirm nothing on the page claims
   otherwise. The report-side counterpart of this check, which prints both numbers in one document
   with a methodology note explaining them, is QA 2.11 in the sibling plan.

## QA 13 — Demo content sanity

1. Load the demo content and walk `functionality_demo_end_with_quiz` and
   `functionality_demo_course_parts/02. Core Concepts/03. knowledge-check` as a student.
2. **Expect** every demo quiz still completable and passable — no demo question should have become
