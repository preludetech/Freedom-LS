# Spec: Cohort progress PDF report

## 1. Purpose

Educators and internal staff currently have exactly one way to see how a cohort is doing: the live
`CohortCourseProgressPanel` in `educator_interface`, which shows one course at a time, twenty
students and fifteen items to a page, with no per-question detail and no export path
(`educator_interface/views.py:260-712`). There is no way to take that information into a meeting,
file it, mark it up, or send it to someone who does not have a login. There is no aggregate view of
which quiz questions a cohort is collectively getting wrong.

This feature produces a single A4 PDF per cohort covering every course that cohort is registered
for: a summary of each student's progress, a per-student detail section, and a cohort-wide analysis
of quiz confusions. It is triggered from the admin, generated in the background, stored, and served
through a permission-gated download.

The audience is internal educators and staff. Real student names, no anonymisation.

The report is also the forcing function for fixing a live scoring bug (§14) — its whole purpose is
showing where learners went wrong, and it cannot sit on top of scoring that marks a wrong answer
right.

## 2. Scope

### In scope

- One report per **cohort**, covering **every course the cohort is registered for**, one section per
  course. Inactive registrations (`CohortCourseRegistration.is_active=False`) are **included** and
  marked inactive — learners did that work and it should not vanish from the record.
- A new `freedom_ls/reports` Django app owning the model, the gather and render layers, the print
  templates, the background task, the admin trigger and the download view.
- Fixing the multi-select quiz scoring bug in `FormProgress.score_quiz()` and
  `get_incorrect_quiz_answers()` (§14).
- An at-risk rule registry (§8).

### Out of scope

- The automated email. The design must make it a small addition (a second trigger adapter calling
  the same gather/render/persist path), not a rewrite — but it is not built here.
- CSV export. The `# TODO ... Export as csv` at `educator_interface/views.py:75` is **not** resolved
  by this feature and must not be deleted.
- Retention/expiry of stored reports (§12.4) — deliberately deferred, with the consequence stated.
- Deadlines. The live panel shows `CohortDeadline`/`StudentDeadline` data; the PDF does not.
  Deadlines are a live-tracking concept and a point-in-time PDF is the wrong place for them. This is
  intentional, not an oversight.
- Activities, free-text quiz questions, and individually-registered courses (§13).
- Backfilling or rescoring historical quiz attempts (§14).
- Access logging on downloads. Considered; omitted because the project convention is not to add
  logging unless asked. The download view is the natural chokepoint if audit requirements ever
  tighten.

## 3. Decisions and why

| Decision | Rationale |
|---|---|
| **New `freedom_ls/reports` app** | `student_management` is disqualified: it does not depend on `student_progress`, and `student_progress` already depends on *it*, so the report's gather layer there would create a cycle. `educator_interface` would add zero graph edges but is a views/UI app with no models today; a model, a migration, a background task and a PDF toolchain do not belong there. A dedicated app keeps the WeasyPrint dependency isolated and the feature cleanly removable. Nothing depends on `reports`, so the new edges (`reports` → `content_engine`, `student_management`, `student_progress`, `accounts`, `site_aware_models`) all point the safe way. `docs/app_structure.md` must be regenerated. |
| **WeasyPrint as a core dependency, imported lazily** | FLS is designed to work out of the box, so an optional extra that leaves a visibly broken admin button is the wrong default. But WeasyPrint needs Pango, cairo, gdk-pixbuf and HarfBuzz at runtime, and a module-level import would take the whole site down at startup in a project missing them. Importing inside the render function turns that into a clear, contained failure at generation time. |
| **Pin `weasyprint>=69`** | 68 fixed CVE-2025-68616; 69.0 fixes CVE-2026-49452 (CSS injection via HTML presentational hints when rendering untrusted HTML). This report renders author-supplied question text, so that CVE is directly relevant. |
| **Always a background task, PDF always stored** | Uniform code path: the admin enqueues and returns immediately, dev/test get synchronous behaviour for free from `ImmediateBackend` with no branching (`config/settings_base.py:406-414`). This is also exactly what the future automated email needs. |
| **Trigger lives in the reports app, not on `CohortAdmin`** | A "Generate report" button on `CohortAdmin` would make `student_management` import `reports` — inverting the dependency. Instead: Admin → Reports → "Generate cohort report", with the cohort dropdown filtered to cohorts the user has `view_cohort` on. One extra click, correct layering, and it also sidesteps `CohortAdmin`'s standing site-exclusion gap (`student_management/admin.py:38-44`). |
| **Completion percentage recomputed, not read from cache** | The live panel trusts `CourseProgress.progress_percentage` (`educator_interface/views.py:317-340`), which can go stale on bulk `.update()` paths that bypass `CourseItemProgress.save()` (`student_progress/models.py:110-113`). A wrong number on a screen gets refreshed; a wrong number in a filed PDF is permanent. The report derives completion from the progress rows themselves and says so in the definitions block. |
| **At-risk rules: an ordered list of named rule objects, in code** | idea.md asked for a module-path setting so a downstream project could add a rule without forking, on the `COURSE_ACCESS_BACKEND` / `FREEDOMLS_PERMISSIONS_MODULES` model. Built that way first, then removed: resolving one import path cost a cached loader with a `cache_clear()` discipline in every test that touched it, a two-name export contract, and a system check that existed only to validate the setting. The rules are a plain module-level list instead. `report-upgrades` moves rule selection into the database, which supersedes the seam entirely — and FLS had not shipped, so nothing depended on it. See §8. |
| **First-attempt-only for cohort-wide quiz analysis** | Retakes let students memorise answers; including them makes a hard question look easy. Per-student detail still shows every attempt. The report states this rule on the page. |
| **Cohort-wide percentages suppressed below 10 respondents** | Under ten students, each one moves a percentage by more than ten points. "7 of 9 students got this wrong" is the honest presentation; "78%" implies precision that is not there. |
| **Per-student wrong answers counted per attempt** | A question missed three times in a row is a persistent misconception; a question missed once is a slip. Collapsing them loses the signal the section exists to show. |
| **"No activity in 7 days" for the attention list** | Chosen as the v1 default. It is a threshold parameter on the rule, not a constant, so it can be retuned without touching rule code once real educators use the report. |
| **No retention policy in v1** | Reports are kept until deleted by hand. Accepted consequence: PII-bearing files accumulate. Deletion is still handled correctly when it happens (§12.4), and a TODO records the gap. |
| **Bundle the report font** | WeasyPrint falls back silently to a substitute when a `font-family` is not found via Fontconfig, and renders a `.notdef` box for a missing code point. Both failures are invisible until someone reads a printed report. Bundling one font as a static file with `@font-face` makes rendering reproducible across dev, CI and every downstream deployment, and guarantees the status glyphs (§10) exist. |

## 4. Architecture

Three layers plus adapters. The gather and render layers must not know what triggered them — that is
what makes the future email a small addition.

```
freedom_ls/reports/
    models.py            GeneratedReport
    at_risk.py           Rule objects + AT_RISK_RULES
    gather.py            gather_cohort_report_data(cohort_id, site_id) -> CohortReportData
    render.py            build_report_html(data) -> str
                         render_report_pdf(data) -> bytes      (lazy weasyprint import)
    tasks.py             generate_cohort_report(report_id, site_id)  [@task wrapper + real function]
    views.py             generate view + download view (plain view functions)
    admin.py             GeneratedReportAdmin — registers both views via get_urls()
    config.py            AppSettings subclass
    apps.py              AppConfig + system checks
    templates/reports/   report.html and section partials
    static/reports/      print.css, fonts/
```

The app sets an explicit `label = "freedom_ls_reports"` in `apps.py`, matching every other FLS app
(`student_management/apps.py:6-7` and siblings). The label is what the admin URL namespace and any
reversed route resolve against, so it is not incidental.

**Views live in `views.py`, not `admin.py`, and there is no `urls.py`.** Both the generate view and
the download view are plain view functions in `views.py`, registered through
`GeneratedReportAdmin.get_urls()` wrapped in `self.admin_site.admin_view(...)`, so they are reachable
only inside the admin namespace. This is exactly the in-repo precedent: `webhooks/admin.py:151-168`
imports `send_test_form_view` / `send_test_result_view` from `webhooks/views.py`, and `webhooks` has
no `urls.py` at all. The house rule that every app defines `app_name` in its `urls.py` binds apps that
own public routes; an admin-only feature owns none, and adding an empty `urls.py` would create a
public URL surface the security model (§12) exists to deny. Keeping the callables out of `admin.py` is
also what makes them reusable if the future email needs a link target.

**Layering precedent.** `webhooks/events.py:35-89` is the shape to mirror: a thin `@task()`-decorated
wrapper delegating to a plain function that takes primitive ids and does the real work.

**Gather returns a typed dataclass**, not a template context dict. `CohortReportData` and its nested
dataclasses (`CourseSection`, `StudentRow`, `StudentDetail`, `QuizConfusion`, `AtRiskFlag`) are the
contract between the layers. A plain-function + dataclass split matches FLS's existing style; a
class-based report framework was considered and rejected as inconsistent with the codebase.

**Render splits into two functions.** `build_report_html(data) -> str` is separately testable and is
where most content assertions live; `render_report_pdf(data) -> bytes` calls it and hands the string
to WeasyPrint. This keeps the majority of tests fast and free of the system-library dependency.

## 5. Data model

```python
class GeneratedReport(SiteAwareModel):
    STATUS_PENDING = "pending"
    STATUS_RUNNING = "running"
    STATUS_READY = "ready"
    STATUS_FAILED = "failed"
```

Fields:

- `cohort` — FK to `student_management.Cohort`, `on_delete=CASCADE`.
- `status` — indexed `CharField(choices=...)`, default `pending`. A plain field with choices and
  no state-machine library, mirroring `WebhookDelivery.status` (`webhooks/models.py:39-45,382-384`),
  which is the only status-lifecycle precedent in the codebase.
- `requested_by` — FK to `AUTH_USER_MODEL`, `on_delete=SET_NULL`, nullable. Printed on the title page.
- `requested_at` / `started_at` / `finished_at` — timestamps.
- `file` — `FileField(upload_to=report_upload_path, storage=..., blank=True)`. See §12.
- `error_message` — `TextField(blank=True, default="")`. Populated on failure so a failed report
  explains itself in the changelist instead of just saying "failed".

One in-flight report per cohort is enforced at the database level, not in the view:

```python
class Meta:
    constraints = [
        UniqueConstraint(
            fields=["cohort"],
            condition=Q(status__in=["pending", "running"]),
            name="one_inflight_report_per_cohort",
        ),
    ]
```

This compiles to a Postgres partial unique index. It survives both a double-click and two staff
members clicking simultaneously, which a `.exists()`-then-`.create()` guard does not — that is a
check-then-act race. The view still keeps a friendly pre-check for the common case and catches
`IntegrityError` around the create, redirecting with an "already in progress" message rather than a
500. `ready` and `failed` reports do not block a new run, so re-generation is always available.

`report_upload_path(instance, filename)` returns a pk-derived path (`reports/<pk>/cohort-report.pdf`),
mirroring `content_engine.file_upload_handler` (`content_engine/models.py:565-572`). Never the cohort
name — that is guessable and enumerable.

## 6. Gather layer

`gather_cohort_report_data(cohort_id: str, site_id: int) -> CohortReportData`.

### Site isolation — non-negotiable

`SiteAwareManager.get_queryset()` filters by site **only when a thread-local HTTP request is present**
(`site_aware_models/models.py:43-50`); with no request it returns the queryset entirely unfiltered,
with no exception and no warning. A background task has no request. Therefore **every query in the
gather layer filters explicitly on `site_id=site_id`**, exactly as `dispatch_event()` does
(`webhooks/events.py:66-70`). `recalculate_progress_percentages.py:20-38` is the in-repo example of
the shape to avoid.

The task receives primitive, JSON-safe ids — the report's pk and the site's pk — never model
instances, following `default_task_backend.enqueue(_dispatch_event_task, args=[str(event.pk), site_id])`
(`webhooks/events.py:35-39`).

### Query discipline

`FormProgress.get_incorrect_quiz_answers()` is per-attempt and unbatched — it issues two queries per
question per attempt. Called in a loop over a cohort it would run thousands of queries. The gather
layer must therefore:

1. Collect small id lists **once** up front: `student_ids`, `course_ids`, `topic_ids`, `quiz_form_ids`,
   `first_attempt_ids`.
2. Run a small, fixed number of batched queries against those lists. **No query inside a per-student
   or per-question loop.**

Specific shapes:

- **Latest attempt + attempt count per (student, quiz)** — reuse the proven pattern at
  `educator_interface/views.py:366-382`: one query ordered
  `F("completed_time").desc(nulls_last=True), "-start_time"`, taking the first row seen per
  `(user_id, form_id)` as latest and incrementing a completed counter. Batched cohort-wide rather
  than paged twenty at a time.
- **First completed attempt per (student, quiz)** — a `Window(RowNumber(), partition_by=[user_id,
  form_id], order_by=start_time asc)` annotation filtered to `rank=1`. Filtering directly on a window
  annotation works from Django 4.2 onward; FLS is on Django 6.x, so no manual subquery wrapping.
- **Distractor tallies** — pushed into the database rather than a Python `Counter`:
  `QuestionOption.objects.exclude(correct=True).filter(questionanswer__form_progress__in=<scope>)
  .values("question_id", "id", "text").annotate(times_selected=Count("questionanswer"))
  .order_by("question_id", "-times_selected")` — already ordered worst-first per question.
  **`.exclude(correct=True)`, never `filter(correct=False)`**: `correct` is `null=True`, so
  `correct=False` silently drops every `correct=None` option — and §14 requires `None` to be treated
  as not-correct. Filtering on `False` would make an option that scores a student wrong vanish from
  the confusion tally that exists to explain it. (`questionanswer` is the default reverse query name
  for `QuestionAnswer.selected_options`, which sets no `related_name` —
  `student_progress/models.py:529-531`.)
- **Question and option metadata** — one query for `FormQuestion` with
  `prefetch_related("options")`, building the correctness map in Python once.

The bulk correctness helper the report needs (§14) lives next to the fixed `score_quiz()` rule so
scores and wrong-answer detail can never diverge.

### Definitions the gather layer implements

- **Attempt** — a `FormProgress` row with `completed_time` set. In-progress rows (`completed_time is
  None`) are excluded from attempt counts, matching `educator_interface/views.py:380-381`.
- **Completion percentage** — recomputed. Denominator is the course's `viewable_items()` filtered to
  `Topic` and `Form` (Activities excluded, §13). Numerator is completed `TopicProgress`
  (`complete_time` set) plus completed `FormProgress` over those items. A student with no
  `CourseProgress` row has not started and is 0%, not omitted —
  `CourseProgress` rows only exist for explicitly registered users (`student_progress/models.py:568-572`).
- **Last item completed** — `max()` over `TopicProgress.complete_time` and
  `FormProgress.completed_time` across the course's items. `CourseProgress.last_accessed_item` is
  explicitly last *viewed* (`student_progress/models.py:586-592`) and must not be used.
- **Quiz score** — the *latest* attempt's stored `scores`, shown as-is (§14).
- **Quiz column order** — the quiz's position in `Course.viewable_items()`, never alphabetical.
  Question order within a quiz uses `FormQuestion.question_number()`
  (`content_engine/models.py:523-538`).

### Defensive guards

`quiz_percentage()` raises `ValueError` when `scores` is falsy (`student_progress/models.py:151-157`);
`passed()` raises when `Form.quiz_pass_percentage` is `None` (`student_progress/models.py:159-165`) —
and `quiz_pass_percentage` is genuinely nullable at the database level
(`content_engine/models.py:430-434`). Reuse the guard already proven at
`educator_interface/views.py:485-494` verbatim:

```python
if cell["is_completed"] and cell["is_quiz"] and fp.scores:
    try:
        cell["quiz_percentage"] = fp.quiz_percentage()
        cell["passed"] = fp.passed() if item.quiz_pass_percentage is not None else None
    except (KeyError, ValueError):
        cell["quiz_percentage"] = None
        cell["passed"] = None
```

Note `QuestionOption.correct` is `null=True`, so `None` and `False` are both falsy — an unset option
is neither correct nor incorrect, and the fixed scoring rule (§14) must handle that explicitly.

## 7. Report structure

All pages A4. Portrait by default; landscape only for the wide summary tables.

### 0. Title page (portrait)

Cohort name; the list of courses covered, with inactive registrations marked; generated-at timestamp
**with timezone**; who generated it; and the caveat that figures reflect data as of generation time
and cohort membership as of generation time.

### 0.5. Cohort at a glance (portrait)

Headline numbers — cohort size, median completion, count not started, count complete — and a
**students needing attention** list: name, one line per rule tripped, and a page reference into that
student's detail section (via `target-counter()`, §10).

**The list is capped at 12 students**, ordered worst-first by completion percentage, and the cap is
disclosed in the same shape as §7.3: "18 students flagged, 12 shown". Never silently truncated. The
number is a named constant, not a literal buried in a template, and the full flagged set still appears
in the per-student sections (§7.2), so the cap hides nothing — it only shortens the front page. This
does not weaken §17.4: a student who appears in both places shows identical flags in both.

### 0.6. Contents and definitions (portrait)

Table of contents with real page numbers, plus PDF bookmarks for on-screen readers. Then a
methodology block stating, in plain language:

- What "complete" means, and that completion is recomputed from progress records rather than read
  from a cached field.
- That quiz score means the **latest** attempt.
- What counts as an attempt (completed only).
- The first-attempt rule for cohort-wide analysis, and why.
- That multi-select scoring changed, so a stored score for a checkbox question answered before the
  change can disagree with the wrong-answer detail below it (§14).
- That Activities and free-text questions are excluded, and why.
- That courses a student registered for individually, outside the cohort's registrations, are not
  covered.
- The RAG legend, including the glyphs.

### 1. Summary of student progress (landscape)

**One table per course**, not one grid across all courses — this matches how educators already
navigate the data (the live panel is one course at a time) and keeps column counts sane.

Each table: student rows against completion (percentage and count, plus a fill bar), last course item
completed and when, then a column group per quiz showing latest score and number of attempts.

- Repeat the header row on every page the table spans.
- Cap at roughly **10–12 data columns**; split the table rather than shrinking the type. This number
  is an estimate and **must be validated against a real rendered A4 landscape sample** before
  sign-off. The live panel's own screen budget is 15 columns, which suggests the print figure is in
  the right region but is not directly transferable.
- Band alternate rows so the eye tracks across wide tables.
- Abbreviate quiz column headers, with a legend under the table title.
- Mark the section as inactive where the course registration is inactive.

### 2. Details per student (portrait)

One page-break-forced section per student, alphabetical by surname, with a running header carrying
the student's name.

Per student:

- **Every at-risk flag they tripped, at the top of their section**, using the same rule labels and
  reason text as the at-a-glance page. Both views render from **one** evaluation of the registry,
  never two — an educator who turns to page 41 after spotting a name on page 2 must find the same
  flags. A student who tripped nothing shows an explicit "No flags" line, so the absence is stated
  rather than inferred.
- Every item completed and when.
- Every quiz attempt with score and date.
- Per quiz, each question they got wrong, how many times, and which incorrect options they picked.
  **Counted per attempt** — three wrong answers across three attempts reads as "3 times", because
  repetition is the signal.
- Students with nothing to show get an explicit "No activity recorded" line. Silent omission reads
  as a data bug.

### 3. Quiz confusions across the cohort (portrait)

Per quiz: each question people got wrong, with the incorrect options chosen and how often, computed
over **first attempts only**. Ranked worst-first by error rate.

- Cap the list per quiz and **disclose the cap**: "showing worst 10 of 23 questions with at least one
  incorrect answer".
- Always show the correct option alongside the wrong ones, so the table stands alone.
- **Raw counts and percentages only.** No discrimination indices, no point-biserial correlations —
  with cohorts of 5–50 those are unstable to meaningless.
- **Below 10 respondents for a question, show plain counts** ("7 of 9 students got this wrong"), not
  percentages.
- Carry a short interpretive caution: a high error rate can mean a hard-but-fair question, not a
  broken one.

## 8. At-risk rule registry

### Why a registry

"What counts as at risk" is precisely the thing that gets tuned once real educators use the report,
and it varies by institution. Adding, removing or reordering a rule should be a one-line change to a
list, with no edit to the report-building or rendering code.

### Shape

A rule is a small object carrying:

- `id` — a stable identifier.
- `label` — a human-readable name, used identically on the at-a-glance page and in the student's own
  section.
- `severity` — a role token name, so the theme decides how heavily a flag is drawn rather than the
  rules module.
- an `evaluate(student_data) -> str | None` callable returning a reason string, or nothing.

Thresholds are **constructor parameters, not baked-in constants**, so the same rule class can be
reused at a different number.

`freedom_ls/reports/at_risk.py` exports `AT_RISK_RULES`, an ordered module-level list. That list is
the registry: there is no setting, no loader and no import indirection. Adding a rule means adding a
line to it.

An earlier draft of this spec made the registry pluggable — a per-app setting naming a module that
exported its own list — so a downstream project could contribute a rule without forking. It was built
and then removed. Resolving one import path cost a `functools.cache`d loader whose `.cache_clear()`
had to bracket every `override_settings` in four test files, a two-name export contract that leaked
into a system check's warning text, and a fixture module impersonating a downstream project. A
downstream project that needs its own rule must fork until `report-upgrades` lands, which moves rule
selection and thresholds into the database and replaces this mechanism outright.

### Rules must not query

A rule receives the student's **already-gathered** report data and returns a reason. A rule that
issues its own queries reintroduces the N+1 problem the gather layer is careful to avoid. The
`StudentDetail` dataclass must therefore carry everything the v1 rules need — completion, last
activity timestamp, and latest quiz outcomes — as plain values.

### v1 rules

1. **No recorded activity** — 0% complete with no progress rows at all.
2. **Failed latest quiz attempt** — failed their most recent attempt at any quiz. Must handle a null
   `quiz_pass_percentage` (no pass mark means no verdict, so no flag).
3. **Inactive for N days** — `N=7` by default, measured from the most recent completion timestamp.

A student can trip several rules and shows several reasons.

## 9. Rendering

WeasyPrint, invoked directly (`weasyprint.HTML(string=..., base_url=..., url_fetcher=...).write_pdf()`).
No wrapper library — `django-weasyprint` and `django-weasypdf` were reviewed and add nothing beyond
the `render_to_string` → `HTML(string=...)` seam the design already has.

### Stylesheet

A small, hand-authored print stylesheet at `reports/static/reports/print.css`. **Do not feed
WeasyPrint the compiled Tailwind bundle** (`static/vendor/tailwind.output.css`, ~136 KB) — full
compiled Tailwind is known to produce ignored and invalid CSS in WeasyPrint, and the bundle is
enormous relative to what a report needs. (`tailwind.components.css` is a *source* file of
`@layer`/`@apply` rules, not a compiled artefact, and is not a candidate either.) No `@media print`
stylesheet exists anywhere in the repo today; this is greenfield.

### Getting the theme tokens into the render

§10 requires the report to colour itself from the semantic role tokens and never from hex values.
Those tokens cannot be read from the theme source: `freedom_ls/themes/<slug>/static/themes/<slug>/theme.css`
declares them inside a Tailwind v4 `@theme { }` at-rule, which WeasyPrint does not understand — every
`var(--color-…)` would resolve to nothing and the report would render unstyled. The Tailwind build
*does* emit them as an ordinary CSS block: `static/vendor/tailwind.output.css` opens with
`:root, :host { --color-success: …; --color-success-light: …; … }`.

So: **at render time, extract that leading `:root` custom-property block from the compiled bundle and
inline it ahead of `print.css`.** The report then tracks whatever theme the project actually built,
with no hex values of its own and no Tailwind utilities or preflight in the document. The extraction
is a narrow, single-purpose read of one declaration block — not "feeding WeasyPrint compiled
Tailwind", which the section above rules out.

Consequences to handle:

- The report now depends on a built Tailwind artefact existing. A missing or unbuilt bundle must fail
  loudly — the app's system checks (§12.2) are the natural home for that warning, and a test must
  cover the render-time failure rather than letting it degrade to an uncoloured PDF.
- The active theme is resolved from the `FLS_THEME` setting at startup (`config/settings_base.py:31-33,
  245-248`), not per-request, so a background task with no request resolves it correctly. This is why
  the mechanism works at all in the worker.
- Every role token the report needs (`success`, `warning`, `error`, `info`, their `-light` tints and
  `on-*-light` foregrounds, `surface`, `muted`) is a literal hex value in the default theme — none of
  them go through `color-mix()`. The report must stay within that set; a token defined via
  `color-mix()` is not safe to rely on without first confirming WeasyPrint's support for it.

### Named pages for mixed orientation

```css
@page { size: A4 portrait; margin: 20mm 15mm; }
@page landscape-table { size: A4 landscape; margin: 15mm; }
.landscape-section { page: landscape-table; }
```

`page` is inherited, so applying it to the wrapping section covers every page its content flows onto.
Sections without the class fall back to the default page.

### Table headers, breaks, running headers

```css
thead { display: table-header-group; }
tr { break-inside: avoid; }
.student-section { break-before: page; }
.student-section:first-of-type { break-before: avoid; }
```

The table must not be wrapped in a container with `overflow: hidden` or a fixed height, or it will
not break across pages.

Per-student running headers use `position: running()` plus an `@page` margin box. WeasyPrint keeps
displaying the most recently declared running element until a new one is declared, which is exactly
"the current student's name stays in the header until the next student's section starts" — no
per-page logic in Python.

### Page numbers, contents, bookmarks

`counter(page)` / `counter(pages)` in a footer margin box. The table of contents uses
`target-counter(attr(href), page)` so page references resolve at render time rather than being
computed in Python. Ordinary `<a href="#id">` anchors become real clickable PDF internal links.
`bookmark-level` / `bookmark-label` build the PDF outline, mirroring the printed contents.

### Fonts

Bundle one text font as a static file under `reports/static/reports/fonts/` and declare it with
`@font-face`. Requirements: permissive licence, and coverage of the status glyphs in §10 (DejaVu Sans
satisfies both). Do not rely on system fonts — WeasyPrint substitutes silently when a family is
missing, and renders a visible `.notdef` box for a missing code point. A test should assert the
bundled font is actually embedded, so a missing font fails loudly in CI instead of quietly
substituting.

### Progress bars

A plain nested-div bar (fixed-width outer, percentage-width inner) using role-token background
colours. **Do not build it with flexbox** — WeasyPrint's flexbox support is not deeply tested. Inline
SVG is the fallback if the design needs rounded caps or a track that block layout cannot express.

### Asset resolution and the URL fetcher

With no request, `base_url` must be an explicit absolute path, or assets must be embedded inline as
`data:` URIs.

**That path cannot be `settings.STATIC_ROOT`.** `STATIC_ROOT` is defined only in
`config/settings_prod.py:86`; under `settings_base`/`settings_dev` it is unset — and `settings_dev` is
what the test suite runs on (`pyproject.toml: django_settings_module = "config.settings_dev"`). A
render keyed on `STATIC_ROOT` would work in production and fail everywhere else, including CI. Resolve
static assets — the bundled font, `print.css`, and the compiled Tailwind bundle the token block is
extracted from — through the **staticfiles finders API** instead, which searches `STATICFILES_DIRS`
and app static dirs in dev and falls through to collected storage in production. One resolution path,
all three environments.

The report renders author-supplied question and option text. WeasyPrint's default fetcher will
happily retrieve `http(s)://` and `file://` URLs it encounters, which is an SSRF and local-file-read
surface. Configure a restrictive fetcher:

```python
from weasyprint.urls import URLFetcher
restrictive_fetcher = URLFetcher(allowed_protocols=[], allow_redirects=False)
```

with `data` added to `allowed_protocols` only if inline base64 assets are used. Anything outside the
allowed set then raises, turning a would-be silent network call into a loud render failure that marks
the report `failed` — the right outcome for a background job.

### Performance

WeasyPrint's own documentation states speed is not its goal, and memory grows roughly with document
size with no effective in-process release. Mitigations, in order: generate only in the worker (already
the design); keep the stylesheet small; use explicit `break-before`/`break-after` rather than letting
the pagination engine repeatedly re-flow large sections. If a cohort produces a pathologically large
report, fail with an explicit documented row limit rather than risking an OOM kill mid-render.

## 10. Colour and accessibility

Use the existing semantic role tokens declared in
`freedom_ls/themes/default/static/themes/default/theme.css`, never a hex value or a brand colour name
— a downstream theme overrides these tokens, and a report naming colours directly will silently stop
matching its own product. See §9 for how the token *values* reach the renderer; they are not readable
from that file directly, because it declares them inside a Tailwind `@theme { }` block:

- `success` — on track / complete
- `warning` — behind / borderline
- `error` — failing / significantly behind
- `info` — in progress
- `surface` / `muted` — not started

Full table cells use the `*-light` tints with their paired `on-*-light` foregrounds; solid role fills
with `on-*` foregrounds are reserved for small badges.

**Colour is never the only signal.** Every status cell carries the number *and* a distinct glyph.
These PDFs get printed, sometimes in greyscale on an office printer, where two RAG tiers can land at
similar greys — and since a downstream theme can pick any hue, that risk varies by theme and cannot
be designed away centrally. The glyph is what makes the report survive it.

Use plain Unicode typographic characters, **not emoji**. Emoji render from a platform colour-emoji
font that a headless container may not have at all, and colour glyphs desaturate unpredictably —
defeating the entire greyscale requirement:

- Complete / on track: `✓` (U+2713)
- Failing / not started: `✗` (U+2717)
- Warning / borderline: `▲` (U+25B2)
- In progress: `●` (U+25CF); started-but-no-verdict `○` (U+25CB); not applicable `—`

Verify the bundled font contains these code points.

**Print a sample in black and white before sign-off.**

## 11. Trigger and task

### Admin

`GeneratedReportAdmin` extends `SiteAwareModelAdmin` (`site_aware_models/admin.py`) — cleanly, rather
than copying `CohortAdmin`'s `GuardedModelAdmin` base, which carries a standing `# @claude:` TODO
about missing site exclusion. **Do not delete that TODO**; this feature does not resolve it, and a new
admin must not silently re-create the gap.

Reports are created by the task, not edited by hand: override `has_add_permission` /
`has_change_permission` to `False` for direct editing, following
`WebhookEventAdmin`/`WebhookDeliveryAdmin` (`webhooks/admin.py:177-188,222-233`).

The changelist shows cohort, status, requested by, requested at, finished at, and a download link
where `status == ready`.

A custom admin view provides the generate flow, registered via `get_urls()` with
`self.admin_site.admin_view(...)`, mirroring `webhooks/admin.py:151-168` — the only precedent in the
repo for a permission-checked admin-namespaced custom view. Note that `admin_view()` only guarantees
staff status; the object-level check is separate and mandatory (§12).

The cohort dropdown is populated with `get_objects_for_user(request.user, "view_cohort", klass=Cohort)`,
mirroring `educator_interface/views.py:81-95`, so a user can never even select a cohort they cannot
see.

### Task

```python
@task()
def _generate_cohort_report_task(report_id: str, site_id: int) -> None:
    generate_cohort_report(report_id, site_id)
```

`generate_cohort_report()` sets `running`, gathers, renders, saves the file, sets `ready` — or catches
the failure, records `error_message` and sets `failed`. A crashed render must never leave a row stuck
in `running`, because the partial unique index would then block that cohort forever.

Enqueue inside `transaction.on_commit(...)`. There is **no** correct precedent for this in the repo —
`fire_webhook_event` enqueues immediately after `create()`, which is a live bug there. Without
`on_commit`, `ImmediateBackend` (dev/test) or a fast worker can start before the row is visible.

## 12. Security and file handling

### 12.1 Access control

The generated PDF contains student names and their answers. It must **never** be reachable via a
public media URL.

- **Generation** is gated on `freedom_ls_student_management.view_cohort` for the target cohort — not
  merely on staff status.
- **Download** goes through a view that checks
  `request.user.has_perm("freedom_ls_student_management.view_cohort", report.cohort)` — the same
  object-level permission `educator_interface` already uses, resolved by django-guardian. The call
  shape mirrors `panel_framework/actions.py:208-214`. No report-specific permission is invented.
- `{{ report.file.url }}` must never appear in any template. Note that the one existing file-download
  component in the codebase (`content_engine/templates/cotton/file-download.html:17`) does exactly
  this — it is the anti-pattern, not the precedent.

### 12.2 Storage

The field takes an explicit `storage=`, resolved from a `STORAGES` alias declared through the app's
`AppSettings` config (default alias `"reports"`), falling back to the default storage. Because that
fallback may be a publicly served `MEDIA_ROOT`, the app registers a **Django system check warning**
when the alias is not configured, so a deployment learns about it at `manage.py check` time rather
than after a leak. In S3 deployments the private-bucket configuration already exists
(`config/settings_prod.py:112-141`: no `custom_domain`, `querystring_auth=True`).

Unguessable pk-derived filenames are defence in depth, not the control — the view is the boundary.

### 12.3 Response

```python
response = FileResponse(report.file.open("rb"), as_attachment=True, filename=safe_filename)
response["Cache-Control"] = "private, no-store, must-revalidate"
```

`FileResponse` streams in chunks and handles RFC 5987 filename encoding — do not hand-roll the
header. `safe_filename` comes from `get_valid_filename`/`slugify`, never a raw cohort name.
`no-store` keeps a PII-bearing document out of shared caches and the browser disk cache.

`X-Accel-Redirect` / `X-Sendfile` are explicitly **not** v1: they are nginx/Apache-specific and FLS
installs into projects that may not be behind either. `FileResponse` is the portable default and is
comfortably sufficient for admin-only, low-volume downloads.

### 12.4 Deletion

Django has not deleted files on row delete since 1.3. A `GeneratedReport` deleted through the admin
would otherwise orphan its PDF in storage forever — with PII in it. Handle deletion explicitly:
delete the file first (`report.file.delete(save=False)`), then the row. That ordering matters: a
crash between the two leaves an orphaned file (a cheap storage leak) rather than a row pointing at
nothing (a 404 the download view must then defend against anyway).

**Two deletion paths, not one.** The `cohort` FK is `on_delete=CASCADE` (§5), so deleting a Cohort
also deletes its reports — and a cascade never runs the model's own `delete()`, so file cleanup wired
only into the admin's delete flow would silently orphan every PDF for that cohort. Cover both: the
admin path (single delete and the bulk delete action, which likewise bypasses per-instance `delete()`)
and the cascade path. A test must exercise deleting a Cohort and assert its reports' files are gone,
not just the rows.

No automatic retention or expiry in v1. Record the gap as a TODO — this is a deferred decision, not a
statement that files should be kept forever.

## 13. Known data gaps, worked around

These are pre-existing product gaps, not things this feature creates. Each is either handled or
disclosed in the methodology block.

| Gap | Handling |
|---|---|
| `CourseProgress.last_accessed_item` is last *viewed*, not last completed | Derive "last item completed" from `max()` over completion timestamps. |
| No `ActivityProgress` model exists | Activities are omitted from item lists **and from completion denominators**, matching what the app already does. Not reopened. |
| Free-text questions have no correctness concept — `short_text`/`long_text` are effectively always scored wrong | Omitted from the wrong-answer aggregation and the confusion tally entirely. Not reopened. |
| `QuestionOption.correct` can be edited after students answer | Frozen scores and live re-derivation can disagree. Date-stamp the report and disclose. Detecting *which* questions changed is impossible today — the content models carry no timestamps. |

## 14. In scope: fix multi-select quiz scoring

### The bug

`FormProgress.score_quiz()` awards the mark if **any** selected option is correct, breaking out of
the loop on the first hit (`student_progress/models.py:419-455`, specifically the
`if option.correct: score += 1; break` block). On a checkbox question with two correct and two
incorrect options, a student who ticks all four scores full marks — ticking everything is a
guaranteed 100%.

`get_incorrect_quiz_answers()` repeats the identical rule
(`is_correct = any(option.correct for option in selected_options)`, `models.py:505`), so the
wrong-answer view agrees with the wrong score and the bug is invisible from the UI.

Single-select `multiple_choice` questions are unaffected — only one option can ever be selected.

**There is no test coverage of checkbox scoring anywhere in the repo.** The three existing tests in
`student_progress/tests/test_form_progress_score_quiz.py` are all `multiple_choice`. This is
consistent with the bug going unnoticed.

This is a bug, not a design choice, and it is fixed here rather than filed: a report whose stated
purpose is revealing where learners went wrong cannot be built on scoring that marks a wrong answer
right, and under the current rule a checkbox question can never surface as confusing.

### The fix

- **Exact match, all-or-nothing.** A checkbox question is correct when every correct option is
  selected and no incorrect one is. No partial credit — it is the easiest rule to state on the
  definitions page and it leaves `max_score` semantics untouched.
- `correct` is `null=True`, so treat `None` as not-correct. An option with `correct=None` is neither
  required nor forbidden in the selection — spell this out in the implementation, not by accident.
- **`score_quiz()`, `get_incorrect_quiz_answers()` and the new bulk equivalent move to the new rule
  together**, sharing one correctness predicate, so scores and wrong-answer detail can never diverge
  again.
- **No rescore of historical attempts.** Scores are frozen at submission; learners keep the score they
  were shown. `complete()` is already idempotent (`if self.completed_time: return`), so nothing
  re-scores on its own. The consequence to handle: for checkbox questions answered before the fix, a
  stored score can be higher than a live re-derivation of the same answers, so the summary table's
  score and the wrong-answer detail may not reconcile. The report shows the stored score as-is and
  the definitions block notes the change, so the mismatch reads as history rather than a reporting
  bug.

### Knock-on effects to check

- `student_interface/views.py:1007` (`course_form_complete`) — the student-facing quiz results view,
  and its template.
- `student_interface/views.py:1013,1019` and `student_interface/utils.py:144` — pass/fail and
  navigation via `passed()`.
- `educator_interface/views.py:485-493` — the live progress panel.
- `student_interface/tests/playwright/form_ui_tests.py` — likely exercises quiz completion.
- **Authored content** in `demo_content/` and any downstream course content written on the assumption
  that ticking everything passes. Audit `demo_content/` for checkbox questions and note anything that
  changes meaning.
- The `fls-content` authoring plugin's validation and docs, if they describe checkbox scoring.

`qa_helpers/management/commands/qa_create_form_question_types.py:165-191` already builds a checkbox
question with two correct options of three — a ready-made fixture for both the regression test and
manual QA.

## 15. Testing

Layer the tests so the fast, portable ones dominate.

- **Scoring fix first, TDD.** A failing test proving "tick everything scores 100%" on a checkbox
  question, then the fix. Cover: all correct selected and nothing else (correct), all correct plus an
  incorrect (wrong), a subset of correct (wrong), nothing selected (wrong), `correct=None` options,
  and the unchanged `multiple_choice` behaviour. Assert `score_quiz()` and
  `get_incorrect_quiz_answers()` agree on every case.
- **Gather layer** — data shape, completion recomputation, first-vs-latest attempt selection, the
  null `quiz_pass_percentage` guard, the "no activity" and "no `CourseProgress` row" cases, and
  inactive-registration inclusion. Use `mock_site_context` (`freedom_ls/conftest.py:105-138`) for
  model creation, but assert that the gather code's **own** queries filter by explicit `site_id` —
  a two-site test where the second site's students must not appear is the test that actually proves
  isolation.
- **At-risk registry** — each rule independently at its threshold boundaries, that a student can trip
  several rules at once, and that the at-a-glance list and the per-student sections render from the
  same single evaluation.
- **HTML layer** — most content assertions run against `build_report_html()` output with **no
  WeasyPrint call**: student names present, flag labels matching rule labels, "No flags" and "No
  activity recorded" lines rendered, cap disclosure text, small-n counts instead of percentages.
- **PDF layer** — a small number of integration tests asserting only what the PDF can prove: it is a
  well-formed PDF, page orientation matches expectation (`mediabox.width > height` for the summary
  section), the bundled font is embedded, and the cohort name appears in extracted text. Use `pypdf`,
  which is **not currently a dependency** and must be added to the `dev` optional-dependency group in
  `pyproject.toml` (§16). Treat `extract_text()` as a smoke test only — it has known spacing artefacts.
- **Theme tokens** — a test that the `:root` extraction (§9) actually yields the role tokens the
  report uses, and that a missing or unbuilt Tailwind bundle fails loudly rather than producing an
  uncoloured PDF.
- **Never** assert exact PDF bytes. Fonts, timestamps and library versions make output
  non-reproducible byte-for-byte. Visual snapshot diffing is not part of the core suite.
- **Query count** — a test asserting the gather layer's query count stays within a fixed bound as the
  cohort grows. This is the only thing that actually prevents the N+1 regression the design exists to
  avoid.
- **Concurrency** — a test proving two simultaneous generate requests produce one report, exercising
  the partial unique index rather than the view's pre-check.
- **Download view** — a user without `view_cohort` on that cohort gets 403; the response is an
  attachment with the no-store header.
- Mark the handful of tests that actually invoke `write_pdf()` with a new **`weasyprint`** marker, so
  a contributor without Pango/cairo can still run the bulk of the suite. A marker alone does not
  achieve that, so this is a three-part change and all three parts are required:
  1. Register `weasyprint` in `[tool.pytest.ini_options] markers` — `--strict-markers` is on, so an
     unregistered marker is a hard error.
  2. Change the default `addopts` selector from `-m 'not ci_only'` to
     `-m 'not ci_only and not weasyprint'`. Without this the new marker excludes nothing locally and
     the stated goal is not met. CI is unaffected: `.github/workflows/tests.yml:82` passes
     `-m "not playwright"` on the command line, which overrides `addopts`, so CI still runs them —
     and CI is where the system libraries are installed.
  3. This is a fifth marker in a taxonomy that `fls-dev:testing` documents as four
     (unmarked/`playwright`/`fls_internal`/`ci_only`). That skill and the downstream exclusion command
     it publishes must both be updated, since a downstream without Pango needs
     `-m "not playwright and not fls_internal and not ci_only and not weasyprint"`.
- Tests must not depend on execution order — `pytest-randomly` and `pytest-xdist` are both active.
  `time-machine` is available for the "inactive for N days" rule.
- Network is blocked in tests (`--disable-socket`), which is a feature here: it proves the restrictive
  URL fetcher works.

## 17. Success criteria

1. A staff member with `view_cohort` on a cohort can generate a report from the admin, sees it appear
   as `pending`, and can download the finished PDF from the changelist without leaving the admin.
2. The PDF contains every course the cohort is registered for, active and inactive, with inactive
   sections marked.
3. Every student in the cohort appears in both the summary table and the per-student sections —
   including students with no activity at all, who show an explicit "No activity recorded" line.
4. The at-risk flags shown for a student on the at-a-glance page are identical to those in their own
   section, and a student with no flags says so explicitly.
5. Adding a fourth at-risk rule is a one-line change to a list, requiring no edit to gather, render or
   template code.
6. The summary tables repeat their header row on every page they span and render landscape; the rest
   of the document is portrait. Page numbers, a table of contents with real page numbers, and PDF
   bookmarks all resolve correctly.
7. Printed in greyscale on an office printer, every status is still unambiguous — verified by actually
   printing a sample.
8. A checkbox question with two correct options of four scores 0 when all four are ticked, and the
   wrong-answer detail agrees with the score.
9. The gather layer's query count stays within a fixed bound as cohort size grows — proven by test,
   not inspection.
10. A report generated for a cohort on site A contains no data from site B — proven by a two-site
    test.
11. The stored PDF is not retrievable by any unauthenticated or unauthorised request, and never
    through a media URL.
12. Two simultaneous generate requests for the same cohort produce one report, not two.
13. A failed render leaves the row `failed` with a readable error message, and the cohort can be
    retried immediately.
14. The definitions page states, in plain language, what "complete" means, that scores are the latest
    attempt, that cohort analysis uses first attempts, that multi-select scoring changed, and what is
    excluded (Activities, free-text questions, individually registered courses).
