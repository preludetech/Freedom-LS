# Research: codebase (profile-picture-on-id-rows)

All paths relative to the repo root. Predecessor: `spec_dd/3. done/2026-11-15_09:21_learner-public-profile-1-profile-picture/1. spec.md`.

## Headline findings

1. **`learner_id` on the cached report rows is a `Learner` pk (UUID), NOT a `User` pk (int).** `reports/indexes.py` `CohortRoster.learners_by_id: dict[UUID, User]` is "Keyed on Learner id throughout" (`load_roster`: `{m.learner_id: m.learner.user ...}`). `reports/gather.py` builds `LearnerSummary` / `LearnerRow` / `SummaryRow` with `learner_id=<Learner pk>` and `full_name=user.display_name`. So the attention rows and the report summary table need a **Learner-pk to user** resolution, not a `User.objects.filter(pk__in=ids)`. One query still: `Learner.objects.filter(pk__in=ids).select_related("user")` (or `values_list("pk", "user_id", "user__profile_picture")`).
2. **Side effect: avatar colour.** `panel-attention-row` / `panel-person-link` currently get `user_id=learner_id` (a UUID), so `avatar_slot` (crc32 of `str(value)`) picks a slot from the Learner UUID, while `data-table-cells/learner.html` keys colour on `learner.user.pk` (its comment: "a person keeps one colour across the interface"). Today the attention rows and report summary therefore already differ in colour from the learners table. Resolving users gives the chance to pass the user pk (fixes colour) at the same time; the spec should decide (it changes visible colour on those rows).
3. Audit log ids are `User` pks (`actor_id` is an FK to `AUTH_USER_MODEL`; `target_user_pk` is the User pk even for Learner/StaffMember targets), so those need a plain User lookup.
4. An existing test pins the current behaviour and must be flipped: `educator_interface/tests/test_views.py::test_the_audit_log_names_a_person_with_initials_alone` (~line 9095) asserts `profile_picture_sources(content) == []` for a person with a picture.
5. No shared helper resolves ids to picture URLs today.

## Site-awareness

- `User.objects` is `UserManager` (`accounts/models.py:29`): when a thread-local request exists it filters `site=<request site>`; with no request (tests without `mock_site_context`, background jobs) it is unfiltered. `Learner`, `AuditLogEntry`, `CohortMembership` use `SiteAwareManager` (same rule). The report gather itself passes explicit `site_id` because it can run outside a request (`gather_cohort_progress(cohort_id, site_id)`).
- The ids come from site-scoped, authorised data (cohort pk plus site in cache key; audit queryset filtered to the organisation and site), so filtering by site is redundant for correctness but is applied automatically in a request; it does no harm and is the existing convention (`_attach_target_users` uses `model.objects` unfiltered by site explicitly). Do not use `_base_manager` (the predecessor uses it only for reading the stored name under a lock). Tests need `mock_site_context` (as the existing picture tests do) so the factory-made users share the request site.
- `Learner.user` FK is the only link from learner id to user; a user may hold Learner rows in several organisations, so `Learner.objects.filter(pk__in=ids)` (not user-based) is the correct key.

## Conflicts and risks for the spec

- Learner pk vs User pk (finding 1) is the main trap: a naive `User.objects.filter(pk__in=learner_ids)` returns nothing (UUIDs vs ints may even raise a `ValueError` on the int pk lookup).
- `screen_cache.py` and the cached dataclasses must not change; no `SCHEMA_VERSION` bump needed.
- `FlaggedLearnerRow` / `LearnerSummary` / `SummaryRow` are frozen dataclasses; do not add URL fields to cached ones.
- Predecessor spec's Out list names the exact surfaces this idea takes over, and says the cohort report PDF stays initials-less: confirm in tests.
- The deleted-user branch in audit (`label` but no pk) must stay initials-only / neutral circle (no picture, no query for it).
- `audit_person.html` is shared by who, target, the run-entry detail and the mobile cards; pass the URL as a new variable (e.g. `picture_url`) and use the bound `:picture_url=` form.
- Colour change on attention/summary rows if `user_id` switches from learner uuid to user pk (see headline 2).
