# Spec: Messaging policy

Spec 3 of 8 in the User communication effort (`spec_dd/1. next/roadmap.md`). Source: `idea.md` in
this directory. The research files beside it hold the reasoning and worked examples.

## Purpose

One swappable `MessagingPolicy` answers "may this user message that user?" for every messaging
surface that specs 4 to 6 build. Its default implementation reads layered configuration that a site
admin edits in the Django admin. Beside it sit the relationship queries it needs: a learner's
educators, a learner's peers and an educator's colleagues. Nothing here is learner-facing or
educator-facing.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| educator of a learner | coined | a user who reaches an active `Learner` through an active role assignment whose role is in `roles_granting(VIEW_LEARNER, site)`, gated the way `learners_visible_to` gates it. The inverse of `learners_visible_to`, minus its superuser branch |
| offered educator | coined | an educator of a learner whose role toward that learner is on the offered-roles list |
| peer | coined | another user's active `Learner` row in the same organisation that shares a `CohortMembership` cohort, or a course through an active `LearnerCourseRegistration` or `CohortCourseRegistration` |
| colleague | coined | a user who holds a `VIEW_LEARNER`-granting role on an organisation, or on one of its cohorts, where another user holds one too. A site-scoped role makes nobody a colleague |
| candidate | coined | one concrete link from a sender to a recipient: a shared cohort, a shared course through one of the sender's registrations, or a role link that makes the recipient an educator of the sender. The configuration chain resolves once per candidate |

## Scope

In:

- The `MessagingPolicy` contract in `comms`: three questions, a typed decision, refusal reason
  codes, the `MESSAGING_POLICY` setting and its cached loader.
- A new app, `freedom_ls/messaging_policy`, holding the default `LayeredMessagingPolicy`, the
  configuration models, their admin and the settings defaults.
- `educators_of`, `peers_of` and `colleagues_of` in `freedom_ls/learner_management/queries.py`.
- System checks, tests, docs, glossary and the app-dependency map.

Out:

- Any screen beyond the Django admin, including a "why" screen and an educator-interface editor.
  Specs 4 and 5 build the inbox, composer and quick view. Spec 4 keeps a conversation readable
  after replies close and words each refusal reason.
- Report and block (spec 6), which is checked after the policy.
- A recipient-side veto or opt-out.
- Named presets, the platform-wide per-user level of service, and any subscriptions feature.
- Safeguarding modes for sites serving minors.
- Group conversations, announcements, forums, inline feedback.
- Notification configuration (specs 1 and 2).

## Decisions

1. **An educator can always start a conversation with any learner they are an educator of.** No
   flag governs it. Under the any-open rule a close on one level could not shut a pair that another
   role link leaves open. To stop an educator, remove the role.
2. **`is_superuser` grants no messaging rights.** A superuser is an educator or colleague only
   through a role assignment, like anyone else.
3. **Colleagues share an organisation.** One site can hold unrelated organisations, so a
   `site_admin` is not a colleague of every educator on the site.
4. **Replies are allowed when either direction's start is allowed now.** A learner can answer an
   educator who wrote first. Reply rights are symmetric, so ending a relationship, or closing peer
   configuration on both sides, stops replies both ways.
5. **Resolution pools the sender's active `Learner` rows on the site.** Each candidate resolves
   through the chain of its own organisation. The default policy ignores the conversation passed to
   `can_reply`, so it works whether spec 4 keeps one conversation per pair or one per organisation.

## Requirements

### The contract (`freedom_ls/comms`)

New module `freedom_ls/comms/messaging_policy.py`:

```python
class MessagingRefusal(StrEnum):
    SAME_USER = "same_user"
    INACTIVE_USER = "inactive_user"                       # sender or recipient User.is_active is False
    NO_RELATIONSHIP = "no_relationship"                   # no candidate, colleague or educator link on this site
    CLOSED_BY_CONFIGURATION = "closed_by_configuration"   # candidates exist, none resolves open

@dataclass(frozen=True, slots=True)
class MessagingDecision:
    allowed: bool
    reason: MessagingRefusal | None = None
    # __post_init__: allowed == (reason is None), else ValueError
    # __bool__: raises TypeError("use .allowed")
    # classmethods allow() and refuse(reason)

class MessagingPolicy:
    def can_start(self, *, sender: User, recipient: User, site: Site) -> MessagingDecision: ...
    def can_reply(self, *, sender: User, recipient: User, site: Site, conversation: Model) -> MessagingDecision: ...
    def recipients_for(self, *, sender: User, site: Site) -> QuerySet[User]: ...
```

- `MessagingDecision.__bool__` raises so that `if policy.can_start(...)` cannot silently allow
  everything.
- `MessagingPolicy` is a plain class whose methods raise `NotImplementedError`, not an `abc.ABC`,
  following `CourseAccessBackend` in `freedom_ls/course_access/backends.py`.
- `conversation` is typed `Model` because spec 4 creates `Conversation`.
- A policy instance is stateless and never caches an answer.
- Spec 6 adds its block reason to `MessagingRefusal`.

`freedom_ls/comms/config.py` declares `MESSAGING_POLICY: str` with
`Setting(default="freedom_ls.messaging_policy.policy.LayeredMessagingPolicy")`, so FLS works with no
configuration. A string default creates no import edge.

New `freedom_ls/comms/messaging_loader.py`: `get_messaging_policy() -> MessagingPolicy`, decorated
with `@functools.cache`, runs `import_string(config.MESSAGING_POLICY)()`, as
`freedom_ls/course_access/loader.py` does. An autouse fixture beside
`_clear_course_access_backend_cache` in `freedom_ls/conftest.py` calls `cache_clear()` before and
after each test.

`freedom_ls/comms/checks.py`, continuing from `E002`:

- `E003`: `MESSAGING_POLICY` does not import, or does not name a subclass of `MessagingPolicy`.
- `E004`: `MESSAGING_POLICY` starts with `freedom_ls.` and no installed app provides it. Copy
  `E003` in `freedom_ls/course_access/checks.py`.

`comms` runtime modules keep importing only `accounts`, `base` and `site_aware_models`.

### Relationship queries (`freedom_ls/learner_management/queries.py`)

All three take the site explicitly, filter every site-aware table with `site=`, never call
`_current_site()`, and return the same result inside and outside a request. They reuse the helpers
in `freedom_ls/learner_management/capabilities.py` (`roles_granting`, `_active_role_assignments`,
`_member_organisations` and the gate logic), never read guardian rows and never hard-code a role
key. Each returns a further-filterable queryset built from `pk__in` or `Exists` subqueries, never
`.union()`.

- `educators_of(learner: Learner) -> QuerySet[User]`: active users who are educators of the learner,
  and nothing if `learner.is_active` is False. Three sources: a `SiteRoleAssignment` (ungated); an
  `ObjectRoleAssignment` on `learner.organisation`, gated on an active `OrganisationMember` for it;
  and an `ObjectRoleAssignment` on any cohort the learner is a member of, gated on an active
  `OrganisationMember` of the cohort's organisation. Like `learners_visible_to`, it does not check
  the learner's `User.is_active` and does not exclude the learner's own user.
- `peers_of(learner: Learner) -> QuerySet[Learner]`: other users' active `Learner` rows in
  `learner.organisation` that share a cohort with the learner, or share a course with an active
  registration on both sides (either path, each side independently). An inactive learner has no
  peers. The membership and registration conditions for one path go in one `filter()` call, as the
  comment on `is_registered_for_course_expression` explains.
- `colleagues_of(user: User, site: Site) -> QuerySet[User]`: the active users, other than `user`,
  who hold an organisation-scoped or cohort-scoped `VIEW_LEARNER`-granting role in an organisation
  where `user` holds one too, each gated on an active `OrganisationMember` for that organisation.

The default policy's per-candidate expressions use the same link predicates as these functions, so
the two cannot drift, for example by factoring the predicates into helpers both call.

### The new app (`freedom_ls/messaging_policy`)

Label `freedom_ls_messaging_policy`, added to `INSTALLED_APPS` in `config/settings_base.py` after
`freedom_ls.comms`. It depends on `comms`, `learner_management`, `organisations` and
`role_based_permissions`, the way `course_applications` depends on `course_access`. `comms` gains no
runtime edge.

**`config.py`** (`AppSettings`):

- `MESSAGING_DEFAULT_FLAGS: dict[str, str]`, default
  `{"learner_to_educator": "closed", "learner_to_cohort_peer": "closed", "learner_to_course_peer": "closed"}`.
  Every value is `open` or `closed`.
- `MESSAGING_OFFERED_EDUCATOR_ROLES: list[str]`, default `["cohort_admin"]`. An install without
  cohorts adds `organisation_admin`.

**`models.py`.** Every model is `SiteAwareModel, TimestampedModel`. The flags are shared through
one abstract Django model, `MessagingFlags`, which the user explicitly approved:

```python
class MessagingFlag(models.TextChoices):
    INHERIT = "inherit"
    OPEN = "open"
    CLOSED = "closed"

class MessagingFlags(models.Model):            # abstract
    learner_to_educator = CharField(max_length=7, choices=MessagingFlag, default=INHERIT)
    learner_to_cohort_peer = ...
    learner_to_course_peer = ...
```

Each level has its own model. Below the site, it is OneToOne to its owner, so a reverse OneToOne
LEFT JOIN resolves the chain inside a single queryset.

| Model | Owner field | Flags |
| --- | --- | --- |
| `SiteMessagingConfig` | `site` (from `SiteAwareModel`), `UniqueConstraint(fields=["site"])` as on `SiteSignupPolicy` | `MessagingFlags`, plus `offered_educator_roles = JSONField(null=True, blank=True)` |
| `OrganisationMessagingConfig` | `organisation = OneToOneField(Organisation, CASCADE, related_name="messaging_config")` | `MessagingFlags` |
| `CohortMessagingConfig` | `cohort = OneToOneField(Cohort, …)` | `MessagingFlags` |
| `LearnerMessagingConfig` | `learner = OneToOneField(Learner, …)` | `MessagingFlags` |
| `LearnerCourseRegistrationMessagingConfig` | `registration = OneToOneField(LearnerCourseRegistration, …)` | `learner_to_course_peer` only |
| `CohortCourseRegistrationMessagingConfig` | `registration = OneToOneField(CohortCourseRegistration, …)` | `learner_to_course_peer` only |

A registration carries only the course-peer flag because no role is scoped to a course, so no other
candidate passes through it. Every flag column gets a
`CheckConstraint(condition=Q(<flag>__in=MessagingFlag.values))`. A missing row behaves exactly like
an all-`inherit` row.

`offered_educator_roles`: `None` inherits `MESSAGING_OFFERED_EDUCATOR_ROLES`, and `[]` offers
nobody.

**The resolver** walks an ordered list of layers, most specific first, and returns the first value
that is not `inherit` with the name of the layer that supplied it (`ResolvedFlag(value, source)`).
The settings default always supplies a value. The learner layer is the sender's `Learner` row in the
candidate's organisation.

| Candidate | Flag | Chain, most specific first |
| --- | --- | --- |
| Shared cohort C | `learner_to_cohort_peer` | learner, cohort C, organisation, site, settings |
| Shared course via the sender's `LearnerCourseRegistration` R | `learner_to_course_peer` | learner, registration R, organisation, site, settings |
| Shared course via the sender's `CohortCourseRegistration` R on cohort C | `learner_to_course_peer` | learner, registration R, cohort C, organisation, site, settings |
| Educator's role on cohort C | `learner_to_educator` | learner, cohort C, organisation, site, settings |
| Educator's role on the organisation, or a site-scoped role | `learner_to_educator` | learner, organisation, site, settings |

The layer list is one module-level sequence, so a later per-user level of service is one more entry
at the front. In SQL the chain is `Coalesce(NullIf(<layer>, "inherit"), …, Value(<default>))`. The
layers that depend only on the sender's `Learner` row (learner, organisation, site, settings) can be
resolved in Python per row and passed in as values. Where the learner layer is set, that row's
whole candidate kind is a constant.

**`policy.py`.** `LayeredMessagingPolicy(MessagingPolicy)`:

- `can_start` checks in this order:
  1. `sender == recipient` → `SAME_USER`.
  2. Either user is inactive → `INACTIVE_USER`.
  3. The recipient is in `colleagues_of(sender, site)` → allowed.
  4. The sender is in `educators_of(row)` for any active `Learner` row of the recipient on the
     site → allowed.
  5. Any candidate from any of the sender's active `Learner` rows on the site, reaching the
     recipient, resolves `open` → allowed.
  6. Otherwise `CLOSED_BY_CONFIGURATION` if at least one candidate exists, else
     `NO_RELATIONSHIP`.
- An educator role link resolves through its chain only when the role is offered. A link through a
  role that is not offered is still a candidate, and it resolves `closed`. The offered list is the
  site row's `offered_educator_roles` when that is not `None`, otherwise
  `MESSAGING_OFFERED_EDUCATOR_ROLES`, intersected with `roles_granting(VIEW_LEARNER, site)`, so
  offered educators are always a subset of `educators_of`.
- `can_reply` is allowed when `can_start(sender → recipient)` or `can_start(recipient → sender)` is
  allowed. When both are refused, it returns the sender-direction refusal.
- `recipients_for` returns one `User` queryset that ORs together the colleagues, the users whose
  active `Learner` rows the sender is an educator of, and the users reachable through an open
  candidate. It excludes the sender and inactive users, does not use `distinct()`, and costs a fixed
  number of queries that does not grow with the number of learners, cohorts or registrations.
- All three methods share one per-candidate resolution.

**`admin.py`.** One `SiteAwareModelAdmin` per model, with no inlines on the owners' admins, which
would import `messaging_policy` from `learner_management` or `organisations`. Every model except
`SiteMessagingConfig`, whose `site` the base admin excludes and fills from the request, gets an
autocomplete on its owner field. `list_display` shows the owner and the flags. Each flag's
`help_text` says "Inherit" uses the next level up. On `SiteMessagingConfig`,
`offered_educator_roles` is a multiple-choice field built from `roles_granting(VIEW_LEARNER, site)`,
with a "use the settings default" option (`None`) distinct from an empty selection (`[]`). Model
`clean()` runs the same validator, so a non-admin writer is also refused an unknown key.

**`checks.py`:**

- `freedom_ls_messaging_policy.E001`: a `MESSAGING_DEFAULT_FLAGS` key is missing or unknown, or a
  value is not `open` or `closed`.
- `E002`: a `MESSAGING_OFFERED_EDUCATOR_ROLES` key is missing from the base role config or from
  any module in `FREEDOMLS_PERMISSIONS_MODULES`.
- `W001`: a stored `offered_educator_roles` key is missing from that site's role config, which
  catches a role removed after the row was saved. It reads the database the way `E002` in
  `freedom_ls/course_access/checks.py` does, staying silent on an unmigrated database.

## Testing

Follow the `fls-dev:testing` skill. Tests live in `freedom_ls/messaging_policy/tests/`,
`freedom_ls/comms/tests/` and `freedom_ls/learner_management/tests/`.

- **Agreement matrix.** For every educator × organisation × learner in a scenario world,
  `learner in learners_visible_to(educator, org)` iff `educator in educators_of(learner)`, with
  superusers carved out. Model it on `test_learners_visible_to_agrees_with_can_on_every_learner` in
  `freedom_ls/educator_interface/tests/test_permission_matrix.py`. The world covers `site_admin`;
  `organisation_admin` with and without an active `OrganisationMember`; `cohort_admin` and
  `cohort_viewer` on one cohort and on two; an inactive assignment; an inactive user; a custom role
  from a test role config; a user with no role; learners in zero, one and two cohorts; an inactive
  learner; one user with `Learner` rows in two organisations. Run it under `mock_site_context` and
  with no request on the thread-local. Superusers and self-visibility get their own tests. A comment
  points at the planned `Cohort.is_active`.
- **`peers_of`.** A shared cohort, a shared course through each pair of registration paths, an
  inactive learner on either side, an inactive registration, a course shared across two
  organisations (not peers), and self exclusion.
- **`colleagues_of`.** An organisation role and a cohort role in the same organisation, a role in
  another organisation (not a colleague), a `site_admin` with no organisation or cohort role (not a
  colleague), the `OrganisationMember` gate, a superuser without a role (not a colleague), and a
  non-`VIEW_LEARNER` role (not a colleague).
- **Resolver.** A parametrised table of layer values checking the expected value and source for
  every chain above, that a missing row equals an all-`inherit` row, and that the learner layer
  beats every other layer.
- **Policy outcomes.** Worked examples 1 to 9 in `research_pair_resolution.md`, rewritten for the
  current role keys and the offered list, as named tests: one shared cohort, two cohorts that
  conflict, a stop at the learner level, the paid learner, the asymmetric sender-only course case,
  one learner on a course through two registration kinds, course peers across organisations, a
  removed learner, and a multi-organisation educator.
- **Out-of-the-box rules**, with no config rows: an educator may start with a learner they can see,
  and the learner may reply. A learner's start with any educator or peer returns
  `CLOSED_BY_CONFIGURATION`. Colleagues may start with each other. A superuser with no role may
  start with nobody.
- **Offered educators.** By default `cohort_admin` is offered, while `cohort_viewer`,
  `organisation_admin` and `site_admin` are not. A learner opened to educators who writes to a
  non-offered educator gets `CLOSED_BY_CONFIGURATION`. A site override applies, and `None` and `[]`
  behave differently. Every offered educator is in `educators_of`. On a site with no cohorts and
  `organisation_admin` offered, an opened learner reaches their organisation admins with no special
  case.
- **Replies after change.** Closing peer config on both sides, deactivating a registration, removing
  a learner and removing a role each refuse replies in both directions, with the expected reason.
- **Reason codes**, one test per `MessagingRefusal` member.
- **Consistency.** Across the scenario world, `user in recipients_for(sender)` iff
  `can_start(sender, user).allowed`.
- **Query counts.** `recipients_for` and `can_start` use pinned counts that stay the same when the
  world grows fivefold. The SQL contains no `DISTINCT`.
- **`MessagingDecision`.** `bool()` raises, and the `allowed`/`reason` invariant is enforced.
- **Checks.** Each check ID fires on bad input and stays silent on good input. The admin form
  rejects an unknown role key.
- **Boundary.** Extend `freedom_ls/comms/tests/test_boundaries.py`: no module under `comms` outside
  `tests/` has an import statement for `learner_management`, `organisations`,
  `role_based_permissions` or `messaging_policy`. It checks import statements rather than text, so
  the `MESSAGING_POLICY` default string passes.

## Open questions

Defaults taken. The user can overrule any of them.

- **Reason codes.** There are four. A removed sender `Learner` row is plain `NO_RELATIONSHIP`, with
  no separate "removed" code. Spec 4 supplies the wording and may ask for a finer split.
- **The `conversation` parameter** is typed `Model`. Spec 4 may prefer a narrower type, which would
  change the contract.
- **A role key unknown at runtime** is dropped quietly and left to `W001`. It does not raise during a
  request.
- **`Cohort.is_active`** (`educator-interface-6-cohort-administration`) decides whether an inactive
  cohort still links peers and educators. The agreement test catches a change made on one side only.

## Success criteria

- Swapping `MESSAGING_POLICY` to a test subclass changes what `get_messaging_policy()` returns.
- `uv run manage.py check` reports `freedom_ls_comms.E003` for a bad path and
  `freedom_ls_messaging_policy.E002` for an unknown default role key.
- A site admin can create every config model in the Django admin, and cannot save an offered role
  that is missing from the site's role config.
- Every test group under Testing passes, the agreement matrix both inside and outside a request.
- `docs/app_structure.md`, `docs/product/messaging.md` and the glossary describe the new app and the
  new terms.
