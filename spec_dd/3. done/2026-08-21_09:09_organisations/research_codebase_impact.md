# Research: codebase impact of a School layer

## Executive summary

The blast radius is moderate-to-large but concentrated in three places: (1) the `student_management`
models (`Cohort`, `CohortCourseRegistration`, `UserCourseRegistration` need a `school` FK; the four
deadline/override/recommendation models can inherit school transitively), (2) the entire
`educator_interface` surface (3 top-level sections, 7 `DataTable` classes, 10 `Panel` classes — every
one of them currently queries unscoped or site-scoped, none school-scoped) and its sidebar (a real,
identifiable insertion point exists), and (3) test/factory fallout — 366 call sites across 44 files use
the four affected factories, none of which set a school today, so a mandatory FK breaks the suite
project-wide until the factories default a school. There is **no existing per-object scoping mechanism
beyond Site** — `SiteAwareManager` filters transparently via a thread-local request; a School axis
cannot reuse it as-is because a user can belong to >1 School per Site (Site scoping is 1 site per
request, School scoping is "one selected School among several the user can see", i.e. stateful
per-session, not derivable from the request alone). The existing thread-local mechanism also has two
latent failure modes (no scoping outside the request cycle; no try/finally around `get_response`) that
a second thread-local axis would inherit and compound. There is no existing precedent for an uploaded
logo `ImageField` anywhere in the codebase — all current branding (including the email logo) is
static-file-path configuration, not a model field, which is a real design fork the spec must resolve
explicitly. `ObjectRoleAssignment` scoping today grants access to individual Cohorts/Courses one row at
a time; making a School role imply access to every Cohort inside it is not automatic and needs a
deliberate mechanism (see §6).

## 2. The site-aware scoping machinery

Source: `freedom_ls/site_aware_models/models.py`, `middleware.py`, `config.py`, `context_processors.py`, `factories.py`, `admin.py`.

**How it works today:**

1. `CurrentSiteMiddleware.__call__` (`freedom_ls/site_aware_models/middleware.py:8-13`) stashes the current `request` on a module-level `threading.local()` instance (`_thread_locals`, defined in `models.py:14`) at the start of every request, and deletes it at the end.
2. `SiteAwareManager.get_queryset()` (`freedom_ls/site_aware_models/models.py:43-50`) reads `_thread_locals.request` on every queryset build. If a request is present, it resolves the current `Site` via `get_cached_site(request)` (`models.py:19-40`, itself cached on the request object to avoid repeat lookups) and transparently filters `.filter(site=site)`. If there is **no** thread-local request (management command, background task, shell), the manager returns the **unfiltered** queryset — no site filtering happens at all.
3. `SiteAwareModelBase.save()`/`full_clean()` (`models.py:61-67`) auto-populate `self.site` from the same thread-local request if not already set, via `_set_site_from_request` (`models.py:69-76`).
4. `SiteAwareFactory` (`freedom_ls/site_aware_models/factories.py:23-48`) mirrors this for tests: it resolves site from `_thread_locals.request` too (line 33), and deliberately bypasses the custom manager by instantiating + calling `.save()` directly (line 38-48) rather than `.objects.create()`, because the manager's `get_queryset()` would otherwise be evaluated against a mock request that may not behave like a real one.

**Could a School scope ride the same mechanism?**

Not as-is, and the reasons matter for the spec:

- **Site scoping is derivable from the request alone** (host → `Site`, via `get_current_site`). **School scoping is not** — a user with access to multiple Schools on one Site has no way to know from the request+host alone *which* School is "current"; it must be an explicit, stateful choice (the "select school" dropdown), most naturally stored in the session or as a URL param, not inferred.
- Even if the selected School were also stashed on `_thread_locals` (e.g. `_thread_locals.selected_school`), that only helps for **write-time defaulting** (mirroring `_set_site_from_request`) and for views that explicitly opt in to reading it — it would **not** make `SiteAwareManager`-style *automatic* read-time filtering safe to bolt onto every `SiteAwareModel`, because most models (`Course`, `Topic`, `Form`, `User`, etc.) are legitimately **not** school-scoped and must never be silently filtered by a school selector. Site-wide models correctly stay outside `SiteAwareModel`; School filtering must be **explicit, per-query**, applied only to the handful of models that actually have (or inherit) a `school` — i.e., mirror the pattern at the `educator_interface` `DataTable.get_queryset()` / `Panel.get_filters()` call sites (see §3), not the transparent-manager pattern.
- Practically: the "which School(s) can this user see" question is answered by `ObjectRoleAssignment` rows scoped to `School` objects (per the fixed role-machinery decision), which is itself a query (`get_objects_for_user(user, "view_school", klass=School)` style), not a single-value thread-local like the current site.

**Failure modes of the existing thread-local approach that a second axis would inherit:**

1. **Silent no-op outside the request cycle.** `SiteAwareManager.get_queryset()` returns *unfiltered* data whenever `_thread_locals.request` is unset (`models.py:46-50`) — i.e. in every management command, the `db_worker` background-task process (deployment.md confirms webhook delivery runs via a separate `manage.py db_worker` process outside any request), and the Django shell. A School-scoped manager built the same way would have the identical hole: any background job or script that touches a school-scoped model gets **every** school's rows, not the selected one, unless it filters explicitly. This is already true today for Site; School doubles the surface area for "someone forgot to filter."
2. **No `try`/`finally` around cleanup.** `CurrentSiteMiddleware.__call__` (`middleware.py:8-13`) sets `_thread_locals.request` then calls `self.get_response(request)`; the `delattr` cleanup on line 11-12 only runs if `get_response` does not raise. If a view raises an unhandled exception, the thread-local is left dirty. Under a threaded WSGI worker (the shipped Gunicorn config uses "threaded worker class, 2 threads" per `docs/product/deployment.md:27`) a stale thread-local could theoretically leak into the *next* request handled by that same OS thread until overwritten by that request's own middleware pass (each request does overwrite it at line 9 before use, so this is a narrow window — but it is still an unguarded resource-cleanup pattern with no test coverage found under `freedom_ls/site_aware_models/tests/`). A second thread-local for the selected School would replicate this same unguarded pattern.
3. **`FORCE_SITE_NAME` escape hatch** (`config.py:7`, `models.py:25-35`) has no School analogue and doesn't need one, but it illustrates that Site is treated as effectively a single global pin in some deployments — School's "many per site, user-selected" model is a materially different shape than anything `site_aware_models` currently supports.

## 3. Educator interface surface area

Source: `freedom_ls/educator_interface/views.py`, `urls.py`, `templates/`; `freedom_ls/panel_framework/`.

**Top-level sections (`ListViewConfig` subclasses, registered in `interface_config`, `views.py:1032-1034`):** 3 — `CohortConfig` (`views.py:757-766`), `UserConfig` (`views.py:769-774`), `CourseConfig` (`views.py:1024-1029`).

**`DataTable` subclasses — 7, every one a candidate for school filtering:**

1. `CohortDataTable` (`views.py:81-117`) — `get_queryset` uses `get_objects_for_user(request.user, "view_cohort", klass=Cohort)` (line 85-89), i.e. guardian object permissions, not a school filter.
2. `UserDataTable` (`views.py:120-181`) — derives visible users from `accessible_cohorts` via the same `get_objects_for_user` call (line 126-130), then `User.objects.filter(cohortmembership__cohort__in=accessible_cohorts)` (line 134). No school awareness; would need to also intersect on the selected school (e.g. via `cohortmembership__cohort__school=selected_school` or, once `UserCourseRegistration` has a school, union in directly-registered users too — currently this table only shows users who are in *some* cohort, missing individually-registered users entirely, a pre-existing gap this feature would need to either fix or explicitly leave alone).
3. `CohortCourseRegistrationDataTable` (`views.py:213-241`) — unfiltered `CohortCourseRegistration.objects...order_by(...)` (line 216-218); used only inside `CourseRegistrationsPanel.get_filters()` (line 256-257) which further filters `{"cohort": self.instance}`, so it's already instance-scoped and inherits school transitively through the cohort.
4. `CourseDataTable` (`views.py:777-870`) — `Course.objects.all()` (line 780), **completely unfiltered**, not even by guardian permission. Every logged-in user hitting the educator interface currently sees every Course on the site. School-scoping the Course list is not a simple filter add — `Course` has no school concept at all (courses are shared content, only *registrations* are school-scoped), so "scope the course list to a school" really means "scope it to courses that have at least one registration/cohort in the selected school," a materially different (and non-trivial) query, not a straight `.filter(school=...)`.
5. `CourseCohortRegistrationDataTable` (`views.py:877-905`) — used inside `CourseCohortRegistrationsPanel.get_filters()` (`views.py:912-913`, filters `{"collection": self.instance}`); inherits school through `cohort.school` once that exists, but is not currently filtered to the selected school.
6. `CourseStudentRegistrationDataTable` (`views.py:916-957`) — used inside `CourseStudentRegistrationsPanel.get_filters()` (`views.py:964-965`, filters `{"collection": self.instance}`); same story via the direct `school` FK on `UserCourseRegistration`.
7. `CourseInterestDataTable` (`views.py:968-1004`) — used inside `CourseInterestPanel.get_filters()` (`views.py:1011-1012`); `CourseInterest` has **no** school concept (see §1), so this panel cannot be school-filtered without first deciding whether interest expressions get a school.

**`Panel` subclasses — 10:** `UserDetailsPanel` (184-189), `UserCohortsPanel` (192-197), `CohortDetailsPanel` (207-210), `CohortStudentsPanel` (244-249), `CourseRegistrationsPanel` (252-257), `CohortCourseProgressPanel` (260-710, by far the largest — a ~450-line panel building a course-progress grid for a cohort), `CourseDetailsPanel` (873-874), `CourseCohortRegistrationsPanel` (908-913), `CourseStudentRegistrationsPanel` (960-965), `CourseInterestPanel` (1007-1012).

`CohortCourseProgressPanel.get_content` (`views.py:618-705`) is worth flagging specifically: it independently re-queries `CohortCourseRegistration`, `CohortMembership`, `TopicProgress`, `FormProgress`, `CohortDeadline`, `UserCohortDeadlineOverride` (lines 623-661) rather than reusing the `DataTable` filter pattern, so school-scoping it means adding a school filter at each of those query sites individually, not just once.

**Where the "select school" dropdown would go:** The panel-framework left-hand nav is `freedom_ls/panel_framework/templates/panel_framework/partials/sidebar_nav.html`, included from `freedom_ls/educator_interface/templates/educator_interface/interface.html:11` inside the `{% block sidebar_content %}` block, which itself is defined by the shared shell `freedom_ls/base/templates/_base_interface.html:60-62` (the same shell the course player uses — see §4). The menu items rendered there are built server-side by `_build_menu_items()` (`freedom_ls/panel_framework/views.py:472-502`) and passed into the template as `menu_items`; a school switcher would be added either (a) as a new block in `educator_interface/interface.html` rendered before the `{% include "panel_framework/partials/sidebar_nav.html" %}` line, or (b) as new context (`schools`, `selected_school`) threaded through `panel_framework_view()` (`panel_framework/views.py:542-630`) and a new partial included at the top of `sidebar_nav.html` (`panel_framework/templates/panel_framework/partials/sidebar_nav.html:1-3`, before the `<ul>`). Because `sidebar_nav.html` is also OOB-swapped on every HTMX navigation (`panel_framework/views.py:604-608`, `sidebar_nav.html:2` `{% if oob %}hx-swap-oob="true"{% endif %}`), a school selector living inside it would need its own OOB-safe state handling (e.g. read the selection from the session, not re-render a stale value) — HTMX navigation swaps this partial on every click.

## 4. Student interface + course player

Source: `freedom_ls/student_interface/views.py`, `templates/student_interface/_course_base.html`, `templates/cotton/player-nav.html`, `templates/student_interface/partials/course_toc_header.html`.

The course player shell is `freedom_ls/student_interface/templates/student_interface/_course_base.html`, which extends the shared `_base_interface.html` (§3) and fills `{% block sidebar_content %}` (line 59-80) with the course outline (`course_toc_header.html` + `course_minimal_toc.html`). The sticky outline header — `freedom_ls/student_interface/templates/student_interface/partials/course_toc_header.html:1-16` — currently renders only an eyebrow ("Course outline"), the course title, and a progress bar; it has **no branding/logo slot today**. This is the natural injection point for a school logo in the player: either inside `course_toc_header.html` above the course title, or as a new block in `_course_base.html` alongside `{% block sidebar_content %}` (line 59).

Context is built in `freedom_ls/student_interface/views.py`:
- `view_course_item` (line 555-648) resolves `course`, `current_item`, and calls `_player_chrome_context` (line 622-624, defined 651-697).
- `_player_chrome_context` (line 651-697) builds `course_index`, `current_part`, `course_progress` (via `CourseProgress.objects.filter(user=user, course=course).first()`, line 666-670), `item_title`, `index` — **it never looks up which registration (`UserCourseRegistration` vs `CohortCourseRegistration`) got this learner into the course**, so there is currently no code path that could answer "which school is this learner doing this course through." Injecting a school logo means adding a lookup here (or in a shared helper) that resolves the learner's registration for `course` and reads `.school` off it — and see the ambiguity note in §1 (a learner could in principle have both an individual and a cohort registration for the same course, via different schools, with nothing today to disambiguate which one is "the" school for player-branding purposes).

**Existing branding/theme context:** the player does **not** currently receive any logo context at all — no `header_logo_static_path` or similar is passed into `_player_chrome_context`. Site-wide header branding is instead injected globally via the `site_config` context processor (`freedom_ls/site_aware_models/context_processors.py:9-31`, registered process-wide, not per-view), which supplies `header_logo_static_path` (line 27) to every template via `settings.TEMPLATES[...]['OPTIONS']['context_processors']`. A school logo would be the first *per-object* (not per-site, not global) branding value threaded through this view stack.

## 5. Existing branding/logo handling

Source: `freedom_ls/accounts/email_utils.py`, `freedom_ls/site_aware_models/config.py`, `freedom_ls/themes/`.

Every logo in the codebase today is **a static-file path supplied by settings**, not a database field:

- `freedom_ls/site_aware_models/config.py:8,12,16` — `HEADER_LOGO_STATIC_PATH`, `FAVICON_STATIC_PATH`, `EMAIL_LOGO_STATIC_PATH` are all `Setting(default=None)` string settings resolved to a static-file path.
- `freedom_ls/accounts/email_utils.py:418-426` (`resolved_email_logo_path`) simply falls back from `EMAIL_LOGO_STATIC_PATH` to `HEADER_LOGO_STATIC_PATH` — both settings-derived static paths, no model involved.
- `freedom_ls/accounts/email_utils.py:588-614` (`email_logo_dimensions`) resolves the *intrinsic pixel size* of that static file via `django.contrib.staticfiles.finders.find()` (line 600) and a hand-rolled PNG/GIF/JPEG header parser (`image_dimensions`, line 536-557) — i.e. the whole logo-sizing pipeline assumes a static asset discoverable by Django's staticfiles finders, cached for process lifetime (`@functools.cache`, line 588).
- `freedom_ls/themes/default/` and `freedom_ls/themes/first_class/` (per `docs/product/configuration-and-extension.md:36-40`) ship `theme.css` token files, not logo assets — themes control colour/shape/typography tokens, not imagery.
- Confirmed via a repo-wide grep: **no `ImageField` or `FileField` exists anywhere in `freedom_ls/` except `content_engine`'s content-file upload model** (`freedom_ls/content_engine/models.py`, used for authored course files, migrations `0001_initial.py` and `0002_alter_file_file.py`) — that is the only precedent for an uploaded, database-tracked file in the whole codebase, and it belongs to a different subsystem (content authoring) with its own storage/permission model.
- `docs/product/deployment.md:56` confirms media storage conventions *would* exist for an uploaded `ImageField` if one were added — S3-compatible object storage (Cloudflare R2) when configured, falling back to local filesystem, **private by default with signed URLs**. A School logo, if implemented as an uploaded `ImageField`, would need to be explicitly made *public* (a school logo needs to render in a course player without a signed-URL round trip), which cuts against the "private by default" media convention documented there — worth flagging to the spec as a real design tension, not a rubber-stamp "just add an ImageField."

**Conclusion for the spec:** there are two real options with different weights — (a) follow the existing `*_STATIC_PATH` settings convention (a School would need a per-School static path, which doesn't fit the "many Schools created/edited at runtime via admin CRUD" requirement — settings are deploy-time, not admin-editable), or (b) break new ground with an uploaded `ImageField`, which is architecturally sound but has zero precedent in this codebase and needs the public-media exception called out explicitly.

## 6. Role/permission integration

Source: `freedom_ls/role_based_permissions/{models,roles,types,utils,registry}.py`, `README.md`.

**Three assignment scopes today** (`types.py:13-17`): `SCOPE_SYSTEM`, `SCOPE_SITE`, `SCOPE_OBJECT`, backed by three models (`role_based_permissions/models.py`): `SystemRoleAssignment` (global, `models.py:9-43`), `SiteRoleAssignment` (per-Site, `models.py:46-77`), `ObjectRoleAssignment` (per-arbitrary-object via `GenericForeignKey`, `models.py:80-118`).

**`SCOPE_OBJECT` mechanically:** `ObjectRoleAssignment` (`models.py:80-118`) stores `(user, content_type, object_id, role, is_active)` with a `GenericForeignKey` (`target`, line 93) to any model instance — today used for `instructor`/`ta` roles on `Cohort` objects (per `README.md:35`, `assign_object_role(user, cohort, "instructor", ...)`). Assigning triggers `sync_user_object_permissions` (`utils.py:140-189`), which computes the desired guardian permission set from the union of the user's active roles on that **specific object** (`get_object_roles`, `utils.py:67-77`, a plain `ObjectRoleAssignment` filter) and diffs it against current `django-guardian` `UserObjectPermission` rows (`_get_guardian_perms_as_full_strings`, line 91-107), applying `assign_perm`/`remove_perm` (guardian) for the delta (line 176-181). Permissions are filtered to only those matching the target's own `ContentType` (`_filter_perms_for_content_type`, line 123-137) — a hard guardian requirement.

**The consequence for a School role:** guardian permissions are **per-object**, not per-object-type-and-descendants. Assigning a user `school_admin` on a `School` via `assign_object_role(user, school, "school_admin")` would sync guardian permissions **only on the `School` object itself** (e.g. `view_school`) — it does **not** automatically grant `view_cohort` on every `Cohort` inside that school. This directly conflicts with how the educator interface currently determines cohort visibility: `CohortDataTable.get_queryset` (`educator_interface/views.py:83-95`) calls `get_objects_for_user(request.user, "view_cohort", klass=Cohort)` (line 85-89), which is a **per-Cohort guardian check**, not a School-aware check. Making a School-scoped role imply "can see every Cohort in this School" requires one of:
  1. **Fan-out sync** — whenever a School role is assigned/removed, or a Cohort's `school` changes, or a Cohort is created, iterate every Cohort in that School and call `assign_object_role`/`remove_object_role` per-cohort. Correct but requires new signal/hook wiring (there is currently "no middleware or signals" by design, per `README.md:193`, so this would be new ground) and risks drifting out of sync if a Cohort is bulk-created outside the normal path.
  2. **Query-time union** — change `CohortDataTable.get_queryset` (and the analogous spots in `UserDataTable`, `CourseCohortRegistrationDataTable`, etc.) to compute visible cohorts as `(guardian per-cohort grants) OR (cohorts whose school is in the set of Schools the user holds a role on)`, bypassing guardian's per-object check for the School axis entirely and reserving guardian purely for the existing fine-grained per-cohort `instructor`/`ta` grants. This avoids fan-out but means School-based visibility is **not** enforced by guardian/`has_perm` at all — a second, parallel authorization path alongside the existing one, which the spec needs to consciously choose (and which weakens the "guardian is the enforcement layer" design principle stated in `README.md:189`).
- **New role needed**: none of `BASE_ROLES` (`roles.py:15-97`) has `assignment_scope=SCOPE_SITE`-equivalent-but-scoped-to-School; a `school_admin` (and/or reused `instructor`) role with a School-shaped `assignment_scope` would need to be added. `types.py`'s `AssignmentScope` (`types.py:13-17`) is a closed `Literal["system", "site", "object"]` — a School role fits under the existing `SCOPE_OBJECT` (a School is just another object with a `GenericForeignKey` target), so **no new scope enum value is required**, only a new role entry in `roles.py` and new permission strings registered in `registry.py` (currently `registry.py:50-57` only has cohort/student permissions active; a `freedom_ls_schools.view_school` etc. would need adding there, per the documented rule "add to PERMISSIONS first, then reference in roles", `README.md:141`).
- **Migration**: none needed for `role_based_permissions` itself — `ObjectRoleAssignment` already works with any model via its generic FK, so a new `School` model needs no schema change here, only new `roles.py`/`registry.py` entries (code, not migrations).

## 7. Admin

Source: `freedom_ls/*/admin.py`, `freedom_ls/site_aware_models/admin.py`, `freedom_ls/student_management/admin.py`.

`SiteAwareModelAdmin` (`site_aware_models/admin.py:13-16`) is the base class for a plain site-aware model admin — it wraps `unfold.admin.ModelAdmin` and just `exclude`s the `site` field (line 16). It is used directly by `UserCourseRegistrationAdmin`, `CohortCourseRegistrationAdmin`, `CohortDeadlineAdmin`, `StudentDeadlineAdmin`, `UserCohortDeadlineOverrideAdmin`, `RecommendedCourseAdmin` (`student_management/admin.py:57,104,120,161,198,243`) and by `FormProgressAdmin`, `QuestionAnswerAdmin`, `TopicProgressAdmin`, `CourseProgressAdmin` (`student_progress/admin.py:18,54,87,115`).

`Cohort` is the one exception: `CohortAdmin` (`student_management/admin.py:38-44`) extends `guardian.admin.GuardedModelAdmin` directly (not `SiteAwareModelAdmin`), because it needs guardian's per-object permission UI — and there is an **existing, un-implemented `@claude` TODO right there** (`student_management/admin.py:43-44`): *"We need a base class that extends from Guarded model admin and excludes the site (like SiteAwareModelAdmin). implement it and then update docs/admin_interface.md"*. **A `School` admin will hit exactly this same gap** — School needs both site-exclusion (it's a `SiteAwareModel`) and guardian object-permission UI (per the fixed decision that educators get School access via `ObjectRoleAssignment`), so School admin work should either implement that missing `GuardedModelAdmin` + site-exclusion base class (finally resolving the TODO) or duplicate `CohortAdmin`'s ad-hoc pattern. **Do not delete this TODO/`@claude` comment** — per CLAUDE.md, and because the School feature is a second, independent reason it now needs doing.

A School admin would also plausibly want inlines mirroring `CohortMembershipInline`/`CohortCourseRegistrationInline` (`student_management/admin.py:20-35`) — e.g. an inline listing the Cohorts belonging to a School, following the same `TabularInline` + `autocomplete_fields` pattern used throughout this file.

## 8. Tests and factories that would break

Source: `freedom_ls/student_management/factories.py`, repo-wide grep for factory usage.

`CohortFactory`, `CohortMembershipFactory`, `UserCourseRegistrationFactory`, `CohortCourseRegistrationFactory` (`factories.py:25-63`) all extend `SiteAwareFactory` (`site_aware_models/factories.py:23-48`) and currently set no `school` — only `site` is auto-populated (via `_get_current_site`, line 11-20). If `school` becomes a mandatory (non-nullable) FK on `Cohort` and `UserCourseRegistration` (and, per the transitive dependency, `CohortCourseRegistrationFactory` which sub-factories `CohortFactory`, line 61), **every one of these factories will start raising `IntegrityError`/`ValidationError`** the moment the migration lands, until the factories are updated to supply a default School (most naturally via a new `SchoolFactory` `SubFactory`, mirroring how `CohortMembershipFactory.cohort` sub-factories `CohortFactory`, line 41).

Blast radius, measured by grepping `freedom_ls/` (excluding `spec_dd/` docs and `.claude/` memory) for the four factory names: **366 call sites across 45 files** (44 test/QA files + `factories.py` itself). Notable concentrations:
- `freedom_ls/student_management/tests/test_deadline_utils.py` — 47 occurrences (the single largest file).
- `freedom_ls/student_management/tests/test_student_cohort_deadline_override.py` — 22.
- `freedom_ls/role_based_permissions/tests/test_utils.py` — 18 (role-assignment tests directly exercise `Cohort`/`ObjectRoleAssignment` together — relevant to §6).
- `freedom_ls/educator_interface/tests/test_cohort_course_progress_panel.py` — 35 (the panel from §3).
- The `freedom_ls/qa_helpers/management/commands/qa_create_*.py` files (8 files, e.g. `qa_create_large_cohort.py`, `qa_create_cohort_progress.py`, `qa_create_course_visibility.py`) — these are **not tests** but demo/QA data seeders used for manual QA and Playwright fixtures; they would also need updating to pass/create a School, and are easy to miss since they're not caught by `pytest` collection, only by someone actually running them.

None of this is exotic — a single `SchoolFactory` plus a one-line default added to the four affected factories fixes the mechanical breakage — but the **count** (366 sites, 45 files) means the migration cannot land as a schema-only change; it is inherently a coordinated factories + migration change, and any PR that adds the mandatory FK without updating `factories.py` in the same change will fail the entire `student_management`, `educator_interface`, `role_based_permissions`, and much of `student_interface`'s test suite simultaneously.

## 9. Downstream-package concerns

Source: `docs/product/deployment.md`, `docs/product/configuration-and-extension.md` (`docs/install.md` and `docs/app_structure.md` exist but were empty/not migration-relevant at the paths checked).

FLS is **never installed via pip/package** — per `docs/product/deployment.md:108-114`, "FLS is never deployed standalone. A production deployment is a **concrete project** — a downstream repository that installs `freedom_ls` as a **git submodule**." This has direct migration implications:

- A downstream project pins `freedom_ls` at a specific commit (submodule pointer) and bumps it on its own schedule, then runs `manage.py migrate` against **its own production database**, which already has real `Cohort`/`UserCourseRegistration`/`CohortCourseRegistration` rows created under the pre-School schema. The "data migration creating a default School per Site and backfilling" (already a fixed decision) is therefore not a toy migration to write once — it must be safe to run against an arbitrary downstream production dataset it has never seen, potentially at any scale, potentially with multiple Sites already configured (multi-tenancy per Site is a documented, real deployment shape, not hypothetical — see `docs/product/deployment.md`'s scale table implying "multiple tenants" at Phase 3, line 81).
- **No staged/two-step backfill pattern found in this codebase's migration history** to imitate — `freedom_ls/student_management/migrations/` shows straightforward `alter`/`add`/`delete` migrations (e.g. `0009_remove_student_fk_make_user_non_nullable.py`) but the task description doesn't show whether those handled large-table backfills carefully (e.g. `add nullable → backfill in batches → alter to NOT NULL` vs. a single blocking migration). For a downstream production Postgres table of unknown size, a naive "add column NOT NULL with default" or a single unbatched `UPDATE` inside one migration risks a long table lock; this needs explicit attention in the plan phase, not assumed away.
- **No repo-wide "upgrade notes" doc convention exists for FLS-as-a-package** today (the only `upgrade_notes.md` found via grep belongs to an unrelated, already-`done` spec about a Claude plugin split, not a mechanism downstream operators are told to consult when bumping the FLS submodule). If a mandatory-FK migration is going to require downstream operators to do anything (e.g. review their existing Cohort data pre-migration, decide whether multiple real Schools already exist implicitly in their data and should be split out instead of collapsed into one default School), there is currently **no documented channel** to tell them that — this is a process gap the plan phase should flag, not just a migration-script gap.
- `docs/product/configuration-and-extension.md:87-102` documents an **opt-in conformance suite** that checks "the database schema and the code's data model are in step, with no model change left un-migrated" (line 100) — a School app should be included in whatever that suite checks, so a downstream project that has customised the educator interface still gets a signal if it drifts.

## Risks and gotchas

Ranked by how likely each is to actually bite during implementation:

1. **Mandatory-FK backfill against unknown downstream production data** (§9). This is the single highest-risk item: FLS ships via git submodule into production databases the FLS team has never seen, with no existing large-table-safe-migration precedent in this repo to copy, and no upgrade-notes channel to warn operators. Get the migration strategy (nullable → backfill → NOT NULL, batched) and the "what if a downstream site already has what look like multiple logical schools crammed into one" question explicitly addressed in the plan.
2. **School-scoped role does not automatically grant per-Cohort guardian access** (§6). `ObjectRoleAssignment` + guardian is strictly per-object; a School role change does not cascade to the Cohorts inside it without new fan-out sync logic or a second, non-guardian authorization path in the `educator_interface` queries. This is an architecture decision, not a detail, and it directly determines how much of §3's query surface needs touching.
3. **366 factory call sites across 45 files will fail atomically the moment the FK goes NOT NULL** unless `factories.py` is updated in the same change (§8). Easy to fix, easy to forget, and it takes down four apps' test suites at once if missed.
4. **No uploaded-image precedent anywhere in the codebase** (§5); every existing "logo" is a deploy-time static path, and the one existing uploaded-file model (`content_engine`'s `File`) sits behind FLS's documented "private by default, signed URLs" media convention (`docs/product/deployment.md:56`), which is the wrong default for something that must render unauthenticated-adjacent in a course player. The spec needs to pick a lane (uploaded `ImageField` made explicitly public vs. reusing the static-path convention with a School-keyed settings dict) rather than defaulting to "just add an ImageField."
5. **Ambiguous school resolution when a learner has both an individual and a cohort registration for the same course via different schools** (§1, §4) — nothing in the schema prevents this today, and the course player has no existing code path that resolves "which registration got this learner into this course," so the school-logo feature is the first thing that will need to define and implement that resolution logic and its tie-break rule.
6. **`CourseDataTable` and the interest/application/progress subsystems have no natural school affiliation** (§1, §3) — `Course`, `CourseInterest`, `CourseApplication`, `FormProgress`/`TopicProgress`/`CourseProgress` are all keyed on content or user+content, never on a registration. "School-scope the educator interface" cannot mean "add `.filter(school=selected_school)` everywhere" for these; each needs its own derivation strategy (join through registrations) or an explicit decision to leave it unscoped, and `CourseDataTable` in particular is currently **completely unguarded** (no guardian check at all, `views.py:780`) — pre-existing gap this feature will make more visible.
7. **The thread-local site-scoping mechanism has two latent bugs a second axis would inherit**: silent unfiltered reads outside the request cycle (§2 point 1) and no `try`/`finally` around middleware cleanup (§2 point 2). Neither is School's fault, but adding a second stateful thread-local (or session value) for "selected School" without addressing these compounds the same class of bug rather than being independent risk.
8. **`sidebar_nav.html` is OOB-swapped on every HTMX navigation** (§3) — a school switcher living inside or alongside it needs to survive that swap without losing/resetting the user's selection; get this interaction pattern right early, it's a template detail that's easy to get subtly wrong (dropdown appears to reset on navigation) rather than catastrophically wrong.
