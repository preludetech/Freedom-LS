## Conflicts and tensions with this idea and its recorded answers

1. **No git binary vs. a real clean-tree check.** The idea says the check "does not depend on a `git` binary being installed". No filesystem-only implementation exists in the repo; `git_utils` reads refs only. A pure-Python check must read the binary `.git/index`, compare stat data and fall back to hashing contents, honour `.gitignore`, `.git/info/exclude` and global excludes, and handle untracked files, submodules, sparse checkout and `skip-worktree`. This is the largest unknown in the spec; the prior research did not size it. (Not a conflict in the text, but a gap no earlier spec covered.)
2. **Ignored files (`.fls-content.yaml` `ignore:`) vs. "check reads the directory only".** Answers say an ignored path is exempt from being saved/validated but NOT from the git check. The idea's own "ignored files" section says "Match exact paths to files and folders"; answers say entries are relative to the git repo root. These agree, but the idea's example (`CLAUDE.md`, `claude.sh`) shows repo-root files that are outside the content path when the path is a subdirectory; relative-to-repo-root entries need mapping to the saved path. Note a collision with "ignored" in the git sense: `.gitignore`d files are not "uncommitted" for git; the answers' "uncommitted change to an ignored file still fails" must be read as the `ignore:` list, not `.gitignore`.
3. **Answers vs. the idea's out-of-scope line.** Answers widen scope: `content_validate` and the offline validator also honour `ignore:`. The idea's "Changing what `content_validate` checks" is out of scope, so the idea text needs a matching edit. Answers also say the offline validator "already reads" `.fls-content.yaml`; verified, but it reads it only for `admonition_types` and access types (`claude_plugins/fls-content/validate/validate.py` lines 11-16, 62-93, "the only code path that reads .fls-content.yaml") and requires the file. It does not read an `ignore:` key today, and `_ignored` in validate.py (line ~103) ignores names starting with `_` or `.`, so `.fls-content.yaml` is already skipped by name. Adding `ignore:` is a schema change to a file `/fls-content:init` scaffolds (`commands/init.md`, which is non-destructive and parses existing keys), so `init` must also learn the key.
4. **Django side reads no `.fls-content.yaml`.** Per answers, Django takes admonition and access types from settings, so `content_save` and `content_validate` gain a new YAML reader, and the plugin comment "the only code path that reads `.fls-content.yaml`" becomes false. The plugin must stay generic (project rule: no FLS names in generic plugins); `fls-content` is the FLS content plugin, so this is fine, but the Django-side reader and the plugin reader are two copies of the same format (the validator is already a "copy" of Django's `validate.py`).
5. **`--generate-uuids` and `uuid` keying across several paths.** A uuid-less item in path B whose slug matches an item in path A is not covered by any prior decision.
6. **Idea says "the HEAD commit of each path".** For a path that is a subdirectory, the HEAD commit is the repo's, and the same repo may appear twice (two subdirectories). Prior art does not decide how a repeated repo is recorded.
7. **Roadmap vs. idea wording.** Roadmap says "Content authors run `content_save` over several clean git repos"; the idea allows subdirectories of one repo. Minor.

## Elsewhere: pitfalls of refusing dirty trees in deploy/import tooling

Brief and partly from general knowledge; only the first group is backed by a fetched source.

- **Phantom dirtiness from line endings and attributes.** A committed `.gitattributes` overrides `core.autocrlf` for everyone, and changing either can make git report files nobody edited; a fresh clone can be "dirty" under any `autocrlf` value when the repo's attributes disagree with the index. The durable fix is `git add --renormalize .` and committing. A CI guard that fails on CRLF in the index (`git ls-files --eol`) was suggested. Sources: GitHub Docs "About line endings" https://docs.github.com/dealing-with-lineendings ; Atlassian KB https://support.atlassian.com/bitbucket-data-center/kb/git-status-shows-as-files-modified-directly-after-clones/ ; git mailing list thread (brian m. carlson) https://public-inbox.org/git/20200609231336.GQ6569@camp.crustytoothpaste.net/ .
- **File-mode changes.** `core.filemode=false` is not a reliable fix on its own; users report everything still showing as changed on WSL with both settings, because the real cause was line endings or timestamps. Source: https://github.com/Microsoft/WSL/issues/184 . General knowledge: a Docker bind mount, a Windows or WSL checkout, or a volume with different permissions flips the executable bit across the whole tree; a pure-Python check that compares modes would refuse all of them.
- **Stat-cache vs. content.** Git's index stores mtime, size and inode; a copied or restored checkout shows stale stat data and `git status` re-hashes (and refreshes the index). A reader that compares only stat data would report false dirtiness; one that hashes every file must read blobs, including packed objects and `.gitattributes` filters (CRLF, LFS), to compare. General knowledge, not verified against a source here.
- **Submodules, sparse checkout and `skip-worktree`.** A submodule shows as modified when its HEAD differs from the recorded commit or its own tree is dirty; sparse checkouts and `skip-worktree` flags make absent files look deleted. General knowledge.
- **Untracked and ignored files.** "Nothing untracked" depends on `.gitignore`, `.git/info/exclude` and the global excludes file. Tools that run in containers often have editor, `.DS_Store` or build files that are not ignored; the answer here (an `ignore:` list that does not exempt the git check) means such files must be committed or gitignored.
- **CI checkouts.** Shallow clones (`--depth 1`), detached HEAD, and `actions/checkout` produce a HEAD with no branch or packed refs; `get_head_commit` already handles detached HEAD by reading `HEAD` directly (the file read is a SHA) but shallow `.git/shallow` files and partial clones are unverified. A CI job that runs the generate step (`--generate-uuids` or image cache manifests) and then checks cleanliness will always fail: the tool writes into the tree it then refuses. This repo already accepts that (idea: expected, author commits).
- **Worktrees.** `.git` is a file with `gitdir:`; `git_utils` already follows it and `commondir`, so the FLS repo's own worktrees are covered for the HEAD read.
- **Auto-writing ids into author files.** Known issues: merge conflicts when two authors branch before ids are committed and each generates different ids for the same new item (here: two uuids, two DB rows after both save); lost ids when the file is saved from a branch the DB never sees; formatters or editors that reorder or drop frontmatter keys erasing ids; mutation of the source making deploy non-reproducible; comment and formatting loss when YAML is rewritten (ruamel vs. PyYAML) and index-based write-back (options and categories are written by index) mis-assigning ids when entries are reordered between parse and write. Prior art in this repo: the course-editing-plugin research already states "never duplicate UUIDs", the multi-document YAML write-back picks the "first section without a UUID", and the option write-back requires the question uuid already in the file. The idea's design (flag off by default, all missing reported together, commit before the next run) addresses the deploy-reproducibility concern; the merge-conflict and index-mismatch risks are not addressed by any earlier spec. No external source was fetched for this group.
