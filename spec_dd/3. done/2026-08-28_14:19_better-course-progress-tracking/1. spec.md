# Better course progress tracking — specification

Re-keys `CourseProgress`, `TopicProgress` and `FormProgress` off the bare `User` and onto the models
the rest of the system already uses: `Learner` for who, `ContentCollectionItem` for where, and the
registration that granted access for why. A `CourseProgress` row stops being "this person's numbers
for this course" and becomes **one learner's pass through one course, minted by one registration**,
owning the item progress underneath it.

Sources, in precedence order: `decision.md` in this directory, then `idea.md`. Where the two
disagree, **`decision.md` wins** — every such reversal is marked **[decision.md]** below with the
idea-file position it replaces. Three questions neither document settled were resolved during this
spec phase and are marked **[settled here]**.

---

### `CourseProgress` carries no `is_active` **[settled here]**

An earlier draft of this spec gave `CourseProgress` its own `is_active`, meaning "this is the record
new work is written to" — a fourth meaning for a word that already carries three. **That flag is
dropped.** The record is keyed on the grant instead (§Keyed on the grant), and *which* record is live
is answered by the registration-resolution order the codebase already has, not by a stored flag.

Two prohibitions survive the removal, and both must be tested against:

- **No access check may read a `CourseProgress` at all.** Access is `is_registered_for_course`, and
  nothing in this work changes it (§Access stays organisation-blind).
- **No record resolution may read a registration's or a `Learner`'s `is_active` as a signal to retire
  or hide a record.** A deactivated registration keeps its record, with its progress, exactly as it
  stands (§Nothing in this work retires a record). `is_active` on a registration decides whether the
  learner may *enter*; it never decides whether their work still exists.

The upshot for the glossary: `is_active` keeps its three meanings, and
`.claude/skills/domain-glossary/SKILL.md` §"Words that are already taken" needs **no** fourth row.

## Why this matters

`idea.md` §Problem states it in full. In short, progress is keyed on `(user, content)` while
enrolment moved to `Learner`, and neither progress constraint includes `site`:

- `TopicProgress` — `unique_together = ["user", "topic"]` (`learner_progress/models.py:521`)
- `CourseProgress` — `unique_together = ["user", "course"]` (`:568`)
- `FormProgress` — no uniqueness constraint; many rows per `(user, form)`, one per attempt

Four things follow, all of which this spec closes:

1. **Two organisations share one row.** The shipped Organisations work deliberately allows one person
   to hold two registrations for one course, one per organisation. Today those share a single
   `CourseProgress`: one percentage, one completion time, one resume pointer. Finishing for Client A
   completes it for Client B. `docs/product/learner-tracking.md:23` says so in product language:
   "None of this is scoped by organisation."
2. **A course can only ever be taken once.** There is nowhere to put a second pass, so renewals,
   recertification and cohort re-runs are unrepresentable.
3. **Shared content corrupts progress in both courses.** `ContentCollectionItem` does not stop the
   same `Topic` being linked into two courses, and `update_course_progress_on_completion`
   (`learner_progress/signals.py:35-97`) computes completion from a **global per-user** id set
   (`:79-86`), so completing a topic in one course silently ticks it in the other.
4. **Rows are minted for courses nobody registered for, with no `site`.** Both
   `update_course_progress_on_completion` (`:92-96`) and `view_course_item`
   (`learner_interface/views.py:666-670`) `get_or_create` without `site=`, which is why eight
   `qa_helpers` commands pass it by hand, and which makes the model's own docstring
   (`learner_progress/models.py:527-534`) false today.

## Decisions

### The record is created at registration time, and that makes it the per-learner enrolment record **[decision.md]**

A `CourseProgress` row is created when a registration grants access, fanning out one row per affected
`Learner` when the registration is cohort-wide. This **reverses** the previous spec phase's "records
are created lazily, on first content access", which `idea.md` inherited as an open lifecycle
question.

The reason is that it collapses the cohort/individual polymorphism before it reaches progress.
Nothing downstream has to branch on "was this a cohort or an individual registration?" — it reads the
record. Two things then fall out for free:

- **Site scoping fixes itself.** `Learner` is a `SiteAwareModel`, so every uniqueness key that
  includes `learner` is transitively per-tenant. No `site_id` in any uniqueness key, and no
  organisation column.
- **The signal's upward traversal dies.** A row that knows its `CourseProgress` knows its course
  directly, so `update_course_progress_on_completion` stops walking `ContentCollectionItem` upward to
  find every parent course, and stops minting records for courses nobody registered for. That retires
  the `@claude` TODO at `signals.py:43`.

It also makes the model docstring true again, and it is what lets `course.registered` name a record
(see §Webhooks).

### Keyed on `Learner`, not on `(user, organisation)`

`Learner` *is* "this person, in this organisation". `learner_id` is on the table, so the record is
per-organisation with **no organisation column**, which is what keeps `learner_progress` off a new
`organisations` edge — `docs/app_structure.md:88` already has
`learner_progress --> learner_management`, and `Organisation` is reached transitively through it.

**Site scoping fixes itself.** `Learner` is a `SiteAwareModel`, so every uniqueness key that includes
`learner` is transitively per-tenant. No `site_id` in any uniqueness key.

Cost, stated plainly: every read path moves from `user=` to `learner=` or `learner__user=`.

### Keyed on the grant: `UNIQUE(learner_registration, learner)` and `UNIQUE(cohort_registration, learner)` **[settled here]**

Uniqueness is **one record per learner per registration**, not one per learner per course. This
replaces the earlier draft's `UNIQUE(learner, course) WHERE is_active`, and it is what lets the
`is_active` flag go.

The record is the per-learner enrolment record, so keying it on what enrolled the learner is the
honest key. Four things follow:

- **The grant can never go missing**, because both grant FKs are `PROTECT` (below). A record always
  names the registration that minted it, so the uniqueness key is never NULL on the side that
  matters, and the check constraint can say **exactly one** unconditionally.
- **NULLs in the *other* index are harmless.** A cohort-granted record has `learner_registration =
  NULL`, so it sits in `UNIQUE(learner_registration, learner)` as `(NULL, learner)`. PostgreSQL
  treats NULLs as distinct in a unique index, so every cohort-granted record coexists there without
  collision, and symmetrically for individually-granted records. No conditional constraint needed.
- **Cohort re-runs become representable** without a migration. A learner enrolled in a second cohort
  gets a second `CohortCourseRegistration`, and therefore a second record. `UNIQUE(learner, course)`
  would have forbidden exactly that — it is problem 2 of the problem statement.
- **The educator matrix's key is the constraint.** `filter(cohort_registration=selected_reg,
  learner=…)` returns at most one row *by construction*, so the matrix subquery needs no `[:1]` and
  no tiebreak (§Educator interface).

**The cost, stated plainly: one learner and one course can now hold more than one record**, when the
learner holds both a cohort and an individual registration for it. That is real, and it is why every
learner-facing read path resolves the **registration** first and reads the record from it, using the
precedence `organisation_for_learner_course` already implements — cohort registration wins, otherwise
`latest_registration`'s `(-is_active, -registered_at)` tiebreak. §Resolving the record is where that
lives, and it is one function, not a rule re-derived per call site.

`clean()` guards the pairing a compound unique key cannot: whichever grant is set must name this same
`learner` and this same `course`.

### A record names exactly one grant, and the grant is `PROTECT`ed **[settled here]**

The record carries `learner_registration` and `cohort_registration`, both nullable, **both
`PROTECT`**. This **reverses** the previous spec phase's "the two registration FKs are dropped"
(which `idea.md` had already reversed once) and it **reverses `decision.md`'s `SET_NULL`**. Their job
is now **identity and the uniqueness key**, not merely provenance: "which records did this
registration grant" is `registration.course_progress_records`, a one-join read rather than a query
reconstructing the answer from learner, course and organisation.

`decision.md` framed "`SET_NULL` versus exactly-one-is-set" as a conflict needing a `CheckConstraint`
conditional on `is_active`. `PROTECT` dissolves it from the other side: **a registration that granted
a record cannot be deleted**, so the FK never goes NULL behind the constraint's back, `is_active` is
not needed to guard it, and the check constraint reads **exactly one of the two is set**,
unconditionally.

This is the right direction for FLS. A registration is not bookkeeping to be tidied away — it is the
thing that authorises a learner's work, and the work outlives any reason to remove it. FLS has no
unregister flow (§Explicitly not in scope), and deactivation, not deletion, is already the house
removal for `Learner` and for both registrations. `PROTECT` makes the schema say what the product
already does.

**Two deletion paths change from silent to loud, and that is the intended outcome:**

- **Deleting a registration** — from the Django admin, or `qa_create_course_access_types.py:150`,
  which does `LearnerCourseRegistration.objects.filter(...).delete()` — raises `ProtectedError` once
  it has granted a record. The QA helper must deactivate, or clear the learner's progress first.
- **Deleting a `Cohort` or a `Course`** cascades to their registrations
  (`CohortCourseRegistration.cohort` and `LearnerCourseRegistration.collection` are both `CASCADE`),
  so those deletes are now blocked too. `CourseProgress.course` is already `PROTECT`, so course
  deletion was blocked regardless; cohort deletion is genuinely new.

Both belong with the `danger_content_delete` change in §`CourseProgress` — the same "clear progress
first, deliberately" discipline, applied at the other end of the graph.

### Nothing in this work retires a record **[decision.md]**

`idea.md` carried a resolution rule from the previous spec phase: resolve which registration the
learner currently holds, and if it differs from the one on the record, retire the record and start a
fresh one. **That rule is dropped.** The lifecycle table is:

| Event | Action |
| --- | --- |
| `LearnerCourseRegistration` created or reactivated | ensure a record exists |
| `CohortCourseRegistration` created or reactivated | fan out to every current member whose `Learner` is active |
| `CohortMembership` created for an active `Learner` while the cohort holds an active course registration | ensure a record exists |
| Membership deleted, registration deactivated, learner deactivated | **do nothing to the record** |

`CohortMembership` carries no `is_active` of its own (`learner_management/models.py:83-105`), so
"membership removed" is a row **delete**, and "active member" throughout this spec means
`learner__is_active=True` **[settled here]** — the same filter `is_registered_for_course`
(`learner_management/utils.py:95-100`) and `deadline_utils.py:64-65` already apply on the cohort path. A
member whose `Learner` is deactivated gets no *new* record; the ones they already hold are untouched,
per the last row above.

The last row is the load-bearing one. `research_enrolment_bound_progress_lifecycle.md` finds that
every system surveyed preserves by default — Moodle's cohort-sync data loss is the cautionary tale,
Docebo deliberately decoupled group churn from enrolment — and every system offering a real fresh
start (SCORM's new registration, Absorb re-enrolment, Totara recertification, Moodle
`local_recompletion`) makes the reset an **explicit named operation**. A cohort move is one human
click that produces two automatic writes (delete the old `CohortMembership`, create the new one), so
a rule keyed on membership churn would let a sync glitch destroy a learner's work.

The consequence for this cut: **nothing ever deletes or supersedes a record.** A record is created
by a registration and lives as long as that registration does, which — with `PROTECT` on the grant —
is forever. A retake is an explicit action, and it belongs to
`spec_dd/1. next/learner-management-actions/`; the schema makes it representable the day it is
wanted, with no further migration, because a second registration already means a second record.

Note what this cut *does* create more than one of: a learner holding **both** a cohort and an
individual registration for one course has **two** records, one per grant, from the moment the second
registration arrives. That is the uniqueness key working as designed, not a defect — and §Resolving
the record is what decides which of the two the learner interface writes to.

This also settles the caveat `idea.md` demanded the spec confront: an explicit transfer step inside a
future cohort-move action is **compatible with this design as written**, because the design does
nothing on membership change. The move action re-points `cohort_registration` on the existing record
rather than copying it — and it must handle one case this spec's key creates for it: if the learner
already holds a record under the *target* cohort's registration,
`one_course_progress_per_cohort_registration` rejects the re-point, and the move action has to decide
whether to merge or to leave the existing record in place. That is a decision for
`learner-management-actions`, not for this cut, but the constraint is what forces it to be made
rather than silently producing two records.

### A new record starts from zero

No partial credit across records. Every product surveyed defaults this way. "Keep the best score"
legitimately exists only across attempts *within* one record, which `FormProgress` already supports.
Nothing in this cut exercises this — see above — but the rule is stated so the retake action inherits
it rather than re-deciding it.

### No `attempt_number` column **[decision.md]**

The reports defect `idea.md` describes — a new record's first sitting renumbered as N+1 — is fixed by
**scoping** attempts to the record, not by numbering them. Ordering within a record by
`completed_time` / `start_time` already answers "first attempt" and "latest attempt" once the record
bounds the set. An explicit counter would need allocation under concurrency for no gain.

### Item progress is scoped to the collection item

`TopicProgress` and `FormProgress` hang off the record *and* off the `ContentCollectionItem` that
places the content, not off the bare `Topic`/`Form`:

```
TopicProgress:  one row per (course progress record, collection item)
FormProgress:   many rows per (course progress record, collection item), one per attempt
```

This is the definition-versus-usage split every comparable system draws: Open edX keys
`StudentModule` on `(student, module_state_key, course_id)`, SCORM scopes to a registration, LTI to a
`resource_link_id`. Progress attaches to where content is *used*, never to the shared content object.

Scoping to the record alone would already give per-course and per-organisation independence. Going to
the collection item additionally handles the same topic appearing twice in one course, and pays for
part of its own cost by killing the upward traversal in `signals.py`. It goes one step further than
`research_shared_content_across_courses.md` recommended (it favoured course-scoping only, deferring
placement-scoping) — but with the `CourseProgress` FK already present, the placement FK costs one
column and closes the case permanently.

### Access stays organisation-blind; the record is a state container, not a permission gate

Stated explicitly rather than left to be discovered. Three separable checks:

| Question | Answered by |
| --- | --- |
| May the learner enter? | `learner.is_active` AND any live grant for this course — `is_registered_for_course` (`learner_management/utils.py:69-101`), **unchanged by this work** |
| Which record does the work land in? | the record for the **resolved registration**, guaranteed unique by `one_course_progress_per_learner_registration` / `one_course_progress_per_cohort_registration` (§Resolving the record) |
| Which items are unlocked? | the sequential-unlock read of `TopicProgress`/`FormProgress` *within that record* |

Making the record the gate drags in a nest of edge cases — a learner removed from a cohort still has
a live `cohort_registration`; a learner holding both a cohort and an individual grant has one record
naming only one of them — and it would make a progress row answer a permission question it has no
business answering.

### `CourseProgress.id` is the durable handle

It names one learner's pass through one course in one organisation under one registration, it is
never reused, and `PROTECT` on the grant means it is never deleted. Downstream work (`certificates`, `xapi_implementation`, `report-upgrades`) may
bind to it. Nothing in this cut consumes it and this work adds no `PROTECT` relationship for them;
stating the guarantee here is what stops each of them re-deriving it.

### No rename

Renaming `CourseProgress` buys a word and costs a hand-authored migration plus churn across every
import, admin class, factory and test. The model keeps its name, and "course progress record" stays
the prose noun (§Terminology).

## Model changes

All three models stay in `freedom_ls/learner_progress/models.py` and stay `SiteAwareModel`
subclasses.

### `CourseProgress`

```python
class CourseProgress(SiteAwareModel):
    """One learner's pass through one course, granted by one registration."""

    learner = models.ForeignKey(
        Learner, on_delete=models.PROTECT, related_name="course_progress_records"
    )
    course = models.ForeignKey(
        Course, on_delete=models.PROTECT, related_name="progress_records"
    )

    # Exactly one is set, and PROTECT keeps it that way: a registration that
    # granted a record cannot be deleted. Bound to the registration, never to
    # CohortMembership -- membership churn is a bad lifecycle signal.
    learner_registration = models.ForeignKey(
        LearnerCourseRegistration, null=True, blank=True,
        on_delete=models.PROTECT, related_name="course_progress_records",
    )
    cohort_registration = models.ForeignKey(
        CohortCourseRegistration, null=True, blank=True,
        on_delete=models.PROTECT, related_name="course_progress_records",
    )

    created_at = models.DateTimeField(auto_now_add=True)       # registration minted it
    started_at = models.DateTimeField(null=True, blank=True)   # first content access
    last_accessed_time = models.DateTimeField(null=True, blank=True)  # explicit, not auto_now
    completed_time = models.DateTimeField(null=True, blank=True)
    progress_percentage = models.IntegerField(default=0, db_index=True)

    #: Replaces the GenericForeignKey resume pointer. A concrete FK to the
    #: placement, so resume identifies a position even once a Topic can be
    #: placed twice in one course.
    last_accessed_item = models.ForeignKey(
        ContentCollectionItem, null=True, blank=True,
        on_delete=models.SET_NULL, related_name="+",
    )

    class Meta:
        verbose_name_plural = "Course progress records"
        constraints = [
            # One record per learner per registration. NULLs are distinct in a
            # PostgreSQL unique index, so a cohort-granted record (which has a
            # null learner_registration) never collides in the first index, and
            # vice versa.
            models.UniqueConstraint(
                fields=["learner_registration", "learner"],
                name="one_course_progress_per_learner_registration",
            ),
            models.UniqueConstraint(
                fields=["cohort_registration", "learner"],
                name="one_course_progress_per_cohort_registration",
            ),
            # `condition=`, not `check=`: Django 6.0 removed the `check`
            # argument, and this project runs Django 6.0.
            models.CheckConstraint(
                condition=(
                    models.Q(learner_registration__isnull=False,
                             cohort_registration__isnull=True)
                    | models.Q(learner_registration__isnull=True,
                               cohort_registration__isnull=False)
                ),
                name="course_progress_has_exactly_one_grant",
            ),
        ]
        indexes = [models.Index(fields=["learner", "course"])]
```

`(learner, course)` is a plain index, not a constraint: it is the shape every read path filters on,
and it is deliberately **not** unique — see §Keyed on the grant for why one learner and one course
can hold two records.

`clean()` asserts `learner.site_id == course.site_id`, and that whichever grant is set names both
this same `course` (`learner_registration.collection_id == course_id`, or
`cohort_registration.collection_id == course_id`) **and this same `learner`**. The compound unique
keys cannot express that pairing, so `clean()` is the only guard on it.

For the individual grant, "names this same learner" is `learner_registration.learner_id ==
learner_id`, and that holds for the life of the record. For the cohort grant it is asserted at **two
different grains, deliberately** **[settled here]**:

- **Always**: `learner.organisation_id == cohort_registration.cohort.organisation_id`. Durable —
  `CohortMembership.clean()` already forbids a cross-organisation membership, so this is the part of
  the pairing that survives membership churn.
- **Only when the record is new** (`self._state.adding`): a `CohortMembership` exists for this
  learner in `cohort_registration.cohort`.

Asserting the membership unconditionally would contradict §Nothing in this work retires a record: a
learner removed from a cohort keeps their record, and an unconditional check would make that record
permanently unsaveable through the admin or any other `full_clean()` path. Gating it on creation
catches the mistake where it can actually be made — minting a record for a learner who was never in
the cohort — without letting membership churn invalidate work that already exists.

**`PROTECT` on `learner`, `course`, `topic` and `form` is deliberate, and it has two callers to fix
**[settled here]**.** All four are `CASCADE` today, which is the point: deleting a `Topic` currently
wipes every completion of it without a word. `PROTECT` stops that, and the cost is that two existing
deletion paths must change rather than being left to raise `ProtectedError`:

- `danger_content_delete` (`content_engine/management/commands/danger_content_delete.py:72-80`)
  deletes `Topic`, `Course` and `Form` with `.objects.all().delete()` and relies on `CASCADE`
  ("though CASCADE should handle it", `:76`). It must clear progress first — the same four deletes,
  in the same order, that `danger_clear_all_course_progress` already performs — inside the existing
  `transaction.atomic()`. Deleting all content while keeping progress that points at it is not a
  state anyone wants, so this is the right coupling, not a workaround.
- Deleting a `User` now raises. `Learner.user` is `CASCADE`, so a user delete cascades to `Learner`,
  which `CourseProgress` protects. Core FLS has no user-deletion path (nothing in `freedom_ls/`
  deletes a `User`), but the Django admin offers one. This is a **behaviour change worth stating**
  rather than discovering: an account holding progress cannot be deleted until its progress is.
  Nothing in this cut adds a deletion path — see §Explicitly not in scope.

`start_time` is **renamed** to `created_at` and `last_accessed_time` **loses `auto_now`**. Both are
forced by eager creation (§below), not cosmetic.

`TopicProgress` and `FormProgress` **keep** their `start_time` (`auto_now_add`), and the asymmetry is
the point: an item-progress row is still created on first access, so `start_time` still means "began"
there, while a `CourseProgress` row now exists before anything began. Nothing reads a bare
`start_time` across the three models, and nothing may start to — a sentence naming more than one of
them must name the model, exactly as §Terminology requires of `is_active`.

The `GenericForeignKey` resume pointer goes: `last_accessed_content_type` and
`last_accessed_object_id` (`:554-563`) are replaced by the concrete FK above. The attribute **keeps
the name `last_accessed_item`** **[settled here]**, but its **type changes** from `Topic | Form` to
`ContentCollectionItem`, so "the name is unchanged" is not the same as "the readers are unchanged".
There are no template references — grep finds none — and both Python readers change:

- `get_resume_index` (`learner_interface/utils.py:268-288`) drops
  `select_related("last_accessed_content_type")` and re-keys its `index_by_key` map (`:286-288`) from
  `(type(child), child.pk)` to the collection item.
- `view_course_item` (`learner_interface/views.py:669`) assigns the collection item rather than the
  resolved child.

Because `item` is already ambiguous in `content_engine` (see the glossary's taken-words table), any
docstring or comment on this field must say **collection item** explicitly.

### `TopicProgress`

```python
class TopicProgress(CourseItemProgress):
    course_progress = models.ForeignKey(
        CourseProgress, on_delete=models.CASCADE, related_name="topic_progress"
    )
    #: Where the content sits.
    collection_item = models.ForeignKey(
        ContentCollectionItem, null=True, blank=True,
        on_delete=models.SET_NULL, related_name="topic_progress",
    )
    #: What the content is. Kept alongside so "did they complete this topic
    #: anywhere in this record?" stays a one-line filter.

        Topic, on_delete=models.PROTECT, related_name="progress_records"
    )
```

### `CourseFormAttempt`, and why `FormProgress` did not move

**Revised during the rebase onto the `form_engine` split.** This section originally put
`course_progress` and `collection_item` FKs straight onto `FormProgress`. That is no longer possible,
and would have been the wrong shape anyway.

`FormProgress` and `QuestionAnswer` now live in `freedom_ls/form_engine/`, whose whole point is that a
form can be sat outside a course. Application forms and standalone surveys are the concrete cases.
Hanging a `CourseProgress` FK off `FormProgress` would make `form_engine` depend on
`learner_progress`, and `content_engine` already imports `form_engine`, so the graph would close a
cycle:

```
form_engine -> learner_progress -> content_engine -> form_engine
```

So the course context lives in `learner_progress` instead, as a new model:

```python
class CourseFormAttempt(SiteAwareModel):
    course_progress = FK(CourseProgress, CASCADE, related_name="form_attempts")
    collection_item = FK(ContentCollectionItem, SET_NULL, null=True,
                         related_name="form_attempts")
    form_progress   = OneToOneField(form_engine.FormProgress, CASCADE,
                                    related_name="course_attempt")
```

`FormProgress` keeps its `(user, form)` keying, its answers, its scoring and its `completed_time`, and
`form` moves to `PROTECT` so deleting content cannot erase what was answered. **No uniqueness
constraint** on the placement: many `CourseFormAttempt` rows per `(course_progress, collection_item)`,
one per attempt, as today. The index is
`models.Index(fields=["course_progress", "collection_item"])`; completion is not a local column any
more, so ordering by it crosses the one-to-one into `form_engine`.

The row is a pure join. Nothing is copied across it. Duplicating `form` or `completed_time` here would
give the two halves of one sitting two answers to the same question, and `form_progress.form` already
says what was completed once `collection_item` goes `SET_NULL`.

An attempt sat outside a course simply has no `CourseFormAttempt`. That is what the completion
receiver checks, and it is the only thing separating a course sitting from a standalone one.

### Both item-progress models lose `user`

The `user` FK comes off `TopicProgress`. It is `course_progress__learner__user` now.
`CourseItemProgress` declares `user: models.Model` for mypy; that becomes
`course_progress: models.Model`, and `signals.py` reads it off the instance.

`FormProgress` keeps its `user`, because `form_engine` has no `Learner` to read one through. The
course side reaches the learner as `course_attempt__course_progress__learner`.

### `QuestionAnswer`

Unchanged, and entirely `form_engine`'s. `unique_together = ["form_progress", "question"]` still
holds: answers are already per-`FormProgress`.

### Resolving attempts

The six attempt helpers move off `FormProgress` and into
`freedom_ls/learner_progress/attempts.py`, because they now span two apps:
`get_latest_incomplete`, `get_or_create_incomplete`, `finalise_stale_incomplete`,
`completed_attempts`, `latest_attempt` and `ensure_attempt`. Each takes
`(course_progress, collection_item)` and resolves through `CourseFormAttempt`.

`get_or_create_incomplete` writes both rows itself rather than calling `form_engine`'s own
`(user, form)` helpers, which would resume an attempt begun under another registration. `form_engine`
keeps those helpers for the standalone contexts it will grow later.

### Completion is announced, not observed

`TopicProgress` completion still fires `post_save`. Form completion arrives on `form_engine`'s
`form_attempt_completed` signal, whose payload gains the attempt itself so the receiver can find its
`CourseFormAttempt`. The receiver returns early when there is none.

This replaces the plan's `post_save` receiver on `FormProgress`, and it is strictly better: `complete()`
saves more than once, and a `post_save` receiver had to defend against recalculating on each. One
signal per completion needs no such guard.

### Why `topic` / `form` are kept alongside `collection_item`

Three reasons, all of which the implementation depends on:

- **`SET_NULL` on `collection_item` must not lose the completion.** `content_save` creates placements
  with `update_or_create` keyed on `(site, collection_type, collection_id, child_type, child_id)`
  (`content_engine/management/commands/content_save.py:677`), so re-importing content preserves row
  PKs, and it never sweeps stale items — a placement disappears only by deliberate act. "Did this
  learner ever complete this?" is an audit answer that must survive a content edit, so
  cascade-deleting it would be genuine data loss. Keeping `topic`/`form` means an orphaned row still
  says what was completed.
- **The read side stays cheap.** "Did they complete this topic anywhere in this record?" is one
  filter, not a join through the placement.
- **NULLs are distinct in a PostgreSQL unique index**, so orphaned rows coexist happily under
  `one_topic_progress_per_placement_per_record`. No special handling needed.

### Content accessors must expose the collection item

`Course.children()` (`content_engine/models.py:302-322`), `CoursePart.children()` (`:363`),
`children_flat()` (`:324`) and `viewable_items()` (`:337`) all discard the `ContentCollectionItem`
and return the resolved child. Every write path in this spec needs the placement, so the accessors
must expose it.

**This spec does not change the existing accessors' return types.** They are read by templates, the
educator matrix, the reports catalogue and the deadline utilities, and widening them would put a
tuple or a wrapper through all of it. Instead: add a parallel accessor returning
`ContentCollectionItem` rows in the same order, memoised the same way, and have the existing
accessors derive from it. The player and the fan-out read the new one; everything else keeps reading
the old ones unchanged.

The accessors are named for the **collection item** noun (§Terminology): `collection_items()`,
`collection_items_flat()` and `viewable_collection_items()`, one trio mirroring `children()`,
`children_flat()` and `viewable_items()`. They do not reuse the bare word "item" — per the domain
glossary, `Course.items` already means the rows and `viewable_items()` already means the children.

## Creating records: the sync service

Fan-out is **application logic** — not a migration, not a database constraint. One idempotent service
function in `learner_progress`, called from signal receivers.

### `ensure_course_progress_record`

Takes a `Learner`, a `Course` and the granting registration. Returns the `CourseProgress` for that
`(registration, learner)` pair.

**Idempotency rule:** if a record already exists for **`(registration, learner)`**, **leave it
alone**. Do not reset it, do not touch its timestamps. Note the key: it is the *registration*, not
`(learner, course)`. A learner already holding a record through a cohort registration who is then
registered individually gets a **second** record, because a second grant is a second enrolment. What
must never happen is one grant re-pointing or resetting another grant's record.

The `course` argument is therefore redundant with the registration's `collection` and exists only so
the record can carry `course` denormalised for the read paths. The service asserts they agree rather
than trusting the caller.

`site` is set explicitly from `learner.site` — never left to `SiteAwareModelBase._set_site_from_request`
(`site_aware_models/models.py:69-76`), which reads a thread-local request that a management command,
a bulk import or a signal fired under a foreign ambient site does not have. This is the same
constraint `ensure_learner` documents at `learner_management/utils.py:104-125`, and getting it wrong
is consequence 4 of the problem statement.

**The lookup half needs `_base_manager` for the same reason, and this is the easier half to get
wrong** **[settled here]**. Setting `site` explicitly fixes the *write*; it does nothing for the
*read*. `SiteAwareManager.get_queryset()` ANDs the ambient thread-local site onto every lookup when a
request exists, so `CourseProgress.objects.get_or_create(...)` under a foreign ambient site misses
the row that already exists, attempts an INSERT, and hits
`one_active_course_progress_per_learner_course` instead of being idempotent. `ensure_learner`
documents exactly this failure at `learner_management/utils.py:110-116` and uses
`Learner._base_manager`; `ensure_course_progress_record` uses `CourseProgress._base_manager`.

A cohort-wide fan-out uses `bulk_create(ignore_conflicts=True)` over the cohort's current memberships
whose `Learner` is active (§the lifecycle table), so a large cohort is one statement and a concurrent
individual registration loses the race harmlessly rather than raising. `bulk_create` bypasses
`save()`, so every instance must carry `site` and its grant FK before the call — there is no
`_set_site_from_request` to fall back on, which is the desired behaviour here, not a hazard.

### Where it is called from **[settled here]**

**Signal receivers in `learner_progress`**, listening on `post_save` for `LearnerCourseRegistration`,
`CohortCourseRegistration` and `CohortMembership`, registered from `LearnerProgressConfig.ready()`
alongside the existing receivers (`learner_progress/apps.py:8-9`, `signals.py:1-9`).

The alternative — explicit calls from `learner_management` — reads better but would promote
`learner_management -.-> learner_progress` from a **test-only** edge to a runtime one
(`docs/app_structure.md:126`, `:156`). `learner_progress --> learner_management` already exists
(`:88`), so receivers keep the arrow pointing the way it already points and `/fls-dev:plan_structure_review`
has nothing new to flag.

Each receiver wraps its work in `transaction.on_commit`. Two reasons: a `post_save` receiver that
writes inside the caller's transaction makes a partial fan-out visible to a concurrent reader before
the registration itself is committed, and `LearnerCourseRegistration.save()` already fires a webhook
inline (`learner_management/models.py:127-159`) — deferring the record write to commit is what lets
that webhook move to the receiver and still be ordered after the record exists (§Webhooks).

`raw=True` saves (`loaddata`) return early, matching `recalculate_course_progress_on_save`
(`signals.py:110-112`): deriving records from a fixture load would invent data the fixture author did
not ask for.

### Self-healing at first content access **[settled here]**

`view_course_item` (`learner_interface/views.py:621`) calls `ensure_course_progress_record` rather
than assuming a record exists. `learner_for_course` (below) returns a `Learner`, not a registration,
so the self-healing path needs **both** halves of that resolution: the resolved `Learner` *and* the
registration that resolution walked through, since `ensure_course_progress_record` takes the granting
registration as its third argument. `learner_for_course` therefore returns enough to recover the
registration it chose — the plan phase owns whether that is a second function, a returned pair, or a
`select_related` the caller re-reads. What must not happen is a second, subtly different resolution
order written at the call site.

If there is **no registration at all**, no record is created and **nothing is written** — the player
renders read-only and mark-complete is unavailable. In core FLS this cannot happen: every
`can_access_content=True` branch in `course_access/backends.py` is gated on
`is_registered_for_course` (`:198`, `:341`, `:358`). It can happen with a downstream
`COURSE_ACCESS_BACKEND` that grants content access without a registration, and it must degrade
rather than crash or mint a grant-less record.

This is why **no backfill is needed**: an existing registration whose record predates this work
self-heals the first time the learner opens the course. See §Migration.

## Resolution: which learner, which record

### Resolving the learner

`organisation_for_learner_course` (`learner_management/queries.py:89-115`) already answers "which
organisation is this person studying this course through": cohort registration wins, otherwise
`latest_registration`'s `(-is_active, -registered_at)` tiebreak (`:70-86`).

Add **`learner_for_course(user, course) -> Learner | None`** in the same module, using the same
resolution order, and re-express `organisation_for_learner_course` in terms of it so there is one
resolution order rather than two copies that can drift.

### Resolving the record

`course_progress_for(user, course)` in `learner_progress`: resolve the **registration** the learner
holds for this course, then fetch the one `CourseProgress` for `(that registration, learner)`.
Returns `None` when there is no registration or no record.

The resolution order is not new and must not be re-invented: it is the one
`organisation_for_learner_course` (`learner_management/queries.py:89-115`) already implements —
**cohort registration wins, otherwise `latest_registration`'s `(-is_active, -registered_at)` tiebreak
(`:70-86`)**. That order is what disambiguates a learner holding two records for one course, and it
is why dropping `CourseProgress.is_active` costs nothing: the flag would have encoded an answer the
registrations already carry.

**One gap in that order must be closed, and it is created by this work** **[settled here]**. The
cohort branch (`:101-110`) ends in a bare `.first()` with **no `order_by`**, so when a learner belongs
to two cohorts that both hold an active registration for the same course, which one wins is whatever
PostgreSQL returns. Today that is nearly harmless — it picks an organisation label off a single
shared record. Under this spec it picks **which of two records accumulates the learner's work**,
which is precisely the silent-corruption class this work exists to remove. The cohort branch takes
the same deterministic tiebreak as the individual one: `order_by("-is_active", "-registered_at")`.
Because `learner_for_course` and `organisation_for_learner_course` are one implementation, fixing it
fixes both, and a test must pin the choice rather than leave it to the query planner.

**Every read path that starts from a `User` goes through this one function** rather than filtering
`CourseProgress` directly — that is the whole learner interface. Three read paths do **not**, because
they never hold a `User` to resolve from and resolving one would be inventing an answer they already
have: the educator matrix (§Educator interface) starts from a `Learner` and a
`CohortCourseRegistration`, the reports app (§Reports) starts from a cohort roster, and
`recalculate_progress_percentages` (§Recomputing the progress percentage) iterates records directly.
Those three are the complete list; anything else filtering `CourseProgress` by hand is a defect.

### A learner reaches only one organisation's record through the UI, and that is intended

`learner_for_course` returns exactly one answer. A person holding registrations for one course in two
organisations has two `Learner` rows and two records; both exist in the database, only the resolved
one accumulates work. Holding an *active* registration for the same course in two organisations at
once is unlikely enough today that nothing is built for it. If it ever becomes real, the answer is to
route work to both registrations — not to re-key anything.

### A deactivated `Learner` keeps every record exactly as it stands

`learner.is_active = False` means the person no longer participates through that organisation. It is
**not** a retirement signal. Registrations, memberships and records are all left alone, and the
educator matrix keeps showing removed learners with their history intact. The only thing
deactivation changes is the *future*: the fan-out mints no new record for an inactive `Learner`
(§the lifecycle table).

## Recomputing the progress percentage

`update_course_progress_on_completion` (`learner_progress/signals.py:35-97`) is rewritten and
shrinks. It currently:

1. resolves the completed item's `ContentType` and walks `ContentCollectionItem` **upward** to find
   every parent `Course`, expanding `CoursePart`s (`:47-76`);
2. builds a **global per-user** completed-topic-id set (`:79-83`) and calls
   `completed_form_ids_by_user([user.pk])` (`:84`);
3. `update_or_create`s a `CourseProgress` per course found, with no `site=` (`:88-96`).

After this change the receiver is handed a `CourseItemProgress` that already names its
`course_progress`, so:

1. the upward traversal is deleted outright — this is the `@claude` TODO at `signals.py:43`, and the
   `topic.courses()` / `form.courses()` helpers it proposes are no longer needed;
2. the completed-id sets are scoped to **that record**, not to the user;
3. there is no `update_or_create` and no `site=` question — the record already exists.

`calculate_course_progress_percentage` (`learner_management/utils.py:17-67`) becomes
(`course`, `completed_collection_item_ids`) and counts placements rather than content. Keying it on
the topic/form id would put it at odds with the course outline, which is placement-keyed: a topic
placed twice in one course is two items to complete, and completing one of them is worth one. It
walks `viewable_collection_items()` — the same accessor the outline reads — filtered to `TOPIC` and
`FORM`, so a placed `Activity` still counts towards neither half.

`completed_form_ids_by_user` (`learner_progress/queries.py:26-51`) is re-keyed from user id to course
progress record id **and from form id to collection item id**, renamed
`completed_form_item_ids_by_course_progress` to match. Attempts whose placement has since been
removed are skipped — they name no live position, so they can credit none. `unpassed_forms` reads
both its halves from the placement for the same reason: passing one of two placements of a quiz must
not suppress the other. `attempt_completes_form` (`:9-24`) is unchanged — a failed
quiz still does not complete an item, and `course_finish` still withholds `completed_time` while any
quiz is unpassed. **This spec must not undo that behaviour.**

`recalculate_progress_percentages`
(`learner_progress/management/commands/recalculate_progress_percentages.py`) batches by user id
(`:35-37`, `:40-52`) and needs its batching and its completed-id sets re-scoped to the record.
`danger_clear_all_course_progress` still works as written — deletion order already goes
`QuestionAnswer` → `FormProgress` → `TopicProgress` → `CourseProgress`, which the new CASCADE makes
redundant but not wrong.

### The `FormProgress` attempt helpers

`get_latest_incomplete` (`:126`), `get_or_create_incomplete` (`:134`) and `finalise_stale_incomplete`
(`:149`) take `(user, form)` today, across six call sites in `learner_interface/views.py` (`:845`,
`:848`, `:913`, `:916`, `:960`, `:1326`). They become `(course_progress, collection_item)`.

**All six move together.** Scoping some but not all lets an attempt started under one record be
resumed or finalised under another, which is exactly the silent corruption this work exists to
prevent.

### The eager-creation timestamp split

Today a `CourseProgress` row existing means the learner started. Under eager creation it does not,
and `last_accessed_time` was `auto_now` — so a background percentage recalculation bumped it. Hence
`created_at` / `started_at` / explicit `last_accessed_time`.

Everything that infers "has begun" from row existence or those timestamps must be revisited, and
each must say which of the three it means:

- `_detail_cta_label` (`learner_interface/views.py:130-141`) — the Start / Continue / Review CTA
- `get_current_courses` and `get_completed_courses` (`learner_interface/utils.py:683-728`)
- the reports' `NoRecordedActivityRule` (`reports/at_risk.py:56-64`) and `has_any_progress`
- **`course_finish.html:74-78`**, which renders a user-visible "Started:" date from
  `{{ course_progress.start_time }}`. This is the one place the timestamp's *value* reaches a person,
  and it is what makes `started_at` a required column rather than a convenience: `created_at` is the
  date the learner was *registered*, so binding this template to it would silently mislabel the
  registration date as the start date. It must read `started_at`, and it must handle the null — a
  learner who reached the completion page has started, but the template should not assume it.

  **This one fails silently in the worst way.** Django templates resolve a missing attribute to the
  empty string, so after the rename `{{ course_progress.start_time }}` renders a blank row rather
  than raising. Nothing in the test suite or the type checker will catch it; only looking at the page
  will.

`started_at` is stamped once, by the player, on first content access. `last_accessed_time` is written
explicitly by the player alongside `last_accessed_item` — `view_course_item` already does exactly one
such write (`:663-670`), so this is a one-line change there and a deletion of the `auto_now` reliance
everywhere else.

### Educator interface

`_paginate_learners` (`educator_interface/views.py:353-376`) and `_fetch_progress_maps` (`:378-419`)
re-key from `user_id` to **`learner_id`** **[settled here]**. Both surfaces already iterate
`CohortMembership` rows and are already organisation-scoped, so `learner_id` is the natural key, and
it closes the missing organisation filter as a side effect.

**Both halves of the matrix read the selected cohort registration's records, and only those**
**[settled here]**. The panel already knows its `CohortCourseRegistration`
(`_get_selected_registration`, `:302-317`), so:

- the percentage column is `CourseProgress.objects.filter(learner=OuterRef("learner"),
  cohort_registration=selected_reg)`;
- the item cells are `filter(course_progress__cohort_registration=selected_reg)`.

Filtering both on the same registration is the point: a matrix whose percentage column and item cells
came from different records would be quietly incoherent, and that is exactly the class of defect this
work exists to remove. `one_course_progress_per_cohort_registration` makes each lookup single-valued,
so neither needs a tiebreak.

**The known cost, stated rather than discovered:** a cohort member who *also* holds an individual
registration for the course has two records, and this panel shows only the cohort one. If they did
their work under the individual registration, the cohort panel shows them at 0%. This is the correct
reading of "this cohort registration's progress" — the panel is scoped to a registration, and the
educator selected which one — but it is surprising enough that the plan phase must decide how the
panel *says so* rather than rendering a bare zero. The learner-facing surfaces are unaffected: they
resolve through §Resolving the record, where cohort registration wins.

### Reports

Reports never read `CourseProgress` in production code — verified by grep, and `reports/gather.py:217-219`
carries an explicit prohibition on the one field most likely to be reached for ("Never
`CourseProgress.last_accessed_item` — that tracks last viewed, not last completed"). The whole app
recomputes from `TopicProgress`/`FormProgress`. So the failure mode is not "reports on
an arbitrary record"; it is quieter: **every record merges into one.** Concretely:

- completions are unioned across records (`reports/indexes.py:267-284`);
- attempt numbering renumbers a new record's first sitting as N+1;
- `load_first_attempt_ids` (`:376-398`) partitions by `(user_id, form_id)`, so the cohort confusion
  analysis takes each learner's first attempt **ever** rather than this record's;
- `has_any_progress` stays true after a reset, so `NoRecordedActivityRule` (`reports/at_risk.py:56-64`)
  never fires for a learner starting again.

The app's **"first attempt" and "latest attempt" conventions are re-scoped to "within one course
progress record"**, explicitly, rather than left to surface as a report bug. `load_topic_progress_rows`
(`:256-264`), `load_form_progress_rows` (`:286-303`) and `load_first_attempt_ids` filter on the
records granted by the cohort registration being reported on, and every index key moves from
`user_id` to `learner_id`.

One naming trap to fix while there: `CohortRoster.learner_ids` (`reports/indexes.py:61`, built at
`:185-195`) currently holds **user** ids despite the name. Under this change it holds actual `Learner`
ids, and the name becomes true.

### Deadlines become `Learner`-scoped

This **reverses the shipped position**. `learners-associated-with-organisations` deliberately kept
`learner_management/deadline_utils.py` keyed on `learner__user` so a person holding two `Learner`
rows saw one merged deadline list. Progress is moving to the `Learner` grain and deadlines follow it,
so the two share one grain rather than sitting at odds.

The seven `learner__user=` filters (`deadline_utils.py:65`, `:81`, `:109`, `:136`, `:216`, `:228`,
`:247`) resolve against a single `Learner`, obtained from `learner_for_course`.

This is a behaviour change to shipped code outside the progress models and it needs its own tests: a
person in two organisations must see **each organisation's deadlines separately, not a union**. There
is nothing to grep for afterwards — the filters are correct today and become wrong only because the
grain moves under them. The tests are the only thing that will catch a missed one.

### Admin

All three admins in `learner_progress/admin.py` re-key from `user` to the new shape:
`CourseProgressAdmin` (`:114-139`) shows `learner`, `course` and the grant;
`TopicProgressAdmin` (`:86-112`) and `FormProgressAdmin` (`:17-49`) show `course_progress` and the
collection item. `search_fields` move to `course_progress__learner__user__email` (and
`learner__user__email` on `CourseProgressAdmin`). All stay `SiteAwareModelAdmin` subclasses.

### Factories and QA helpers

`CourseProgressFactory` / `TopicProgressFactory` / `FormProgressFactory`
(`learner_progress/factories.py:21-48`) have no `django_get_or_create`, so roughly forty test call
sites carry an implicit singleton assumption. `CourseProgressFactory` gains a `Learner` SubFactory
and a registration; the two item factories gain a `CourseProgressFactory` SubFactory.

Six `qa_helpers` management commands carry an `_ensure_course_progress_row` helper that pre-creates a
`CourseProgress` **with** a `site` purely to work around consequence 4 —
`qa_create_report_cohort.py:283-292` and `qa_create_legacy_checkbox_score.py:293-301` are the two
whose docstrings say why, and `qa_create_multiselect_quiz_scoring`,
`qa_create_quiz_progression_block`, `qa_create_rich_dashboard_learner` and
`qa_create_checkbox_scoring_quiz` carry the same helper. All six workarounds can go: the service sets
`site` from `learner.site`. Their docstrings must be corrected in the same pass rather than left
describing a defect that no longer exists.

`qa_create_course_access_types.py:150` deletes `LearnerCourseRegistration` rows and now hits
`PROTECT` — see §A record names exactly one grant.

## Webhooks

Both payloads gain `organisation_id` and the course progress record id. The additions are **purely
additive** — no existing field changes name or meaning. `xapi_implementation` is out of scope and
none of this is shaped for it.

### `course.registered` moves to the fan-out receiver **[settled here]**

It fires from `LearnerCourseRegistration.save()` today (`learner_management/models.py:127-159`).
Reading a `CourseProgress` from there would promote `learner_management → learner_progress` to a
runtime dependency, and it would fire before the record exists.

So the firing **moves** into the `learner_progress` receiver that mints the record. The receiver
already holds both the registration and the record, ordering is guaranteed by construction, and the
dependency direction stays `learner_progress → learner_management`.

The move does add one runtime edge — **`learner_progress --> webhooks`**, from importing
`fire_webhook_event`. It is accepted rather than avoided: `webhooks` is a leaf app that
`learner_management`, `learner_interface` and `accounts` already depend on, so the edge adds no
cycle and no new layering. Success criterion 12 names it as the one permitted addition. The
`organisation_id` the payload gains is read as `learner.organisation_id` — an FK id already on the
`Learner` row — so **no `learner_progress --> organisations` edge is created**, and none may be.

Two properties of the current site must be preserved in the move:

- It fires **only on creation** (`is_new = self._state.adding`, `:128`), not on every save.
- It reads the learner through `Learner._base_manager` (`:135-141`) deliberately, because `save()`
  can run from a management command with no ambient request or under a different ambient site. The
  organisation lookup it gains must respect the same constraint — `_base_manager`, never `objects`.

The webhook event name, its existing five fields and their formats are unchanged.

### `course.completed`

Fires from `course_finish` (`learner_interface/views.py:1267-1280`), which is already holding the
`CourseProgress`. It gains the two fields from the record it already has. No move needed.

### Two declaration sites move with the payloads

Adding a field to a payload is three edits, not one. `WEBHOOK_EVENT_TYPE_SAMPLES`
(`freedom_ls/base/webhook_event_types.py:14-27`) carries a sample payload per event and is what the
webhook admin renders for integrators; `docs/product/webhooks.md:21-22` tabulates each event's
fields. Both list the current five fields for each event by hand, so both go stale silently — nothing
asserts they match what `fire_webhook_event` actually sends.

## Migration

**No backfill, and no data migration.** There is no production data. The only progress data that
exists is development data, and re-keying `TopicProgress` from `(user, topic)` is ambiguous by nature
— the row never captured which course it belonged to — so a backfill would need a tie-break, a
quarantine and a retention story for no benefit.

The migration therefore:

1. deletes every `QuestionAnswer`, `FormProgress`, `TopicProgress` and `CourseProgress` row;
2. adds the new columns **non-nullable**, drops `user` from all three, drops the two
   `last_accessed_*` GenericForeignKey columns, and replaces both `unique_together` declarations with
   the new constraints and indexes.

Existing registrations are **not** touched and are **not** backfilled with records. They self-heal
the first time the learner opens the course (§Self-healing at first content access).

Sequencing constraints:

- The migration ships **in the same PR as the model change** —
  `freedom_ls/contrib/conformance/test_migrations.py:19-26` asserts there are no pending migrations.
- Never edit an existing migration file; create new ones.
- If the migration graph becomes awkward to author, **resetting `learner_progress`'s migration
  history to a single `0001_initial` is acceptable** — `learner-terminology-rename` already did
  exactly that for these three apps, and there is no data to preserve.
- `final_pre_deploy_db_structure_cleanup` sequences itself after this work and is built on the same
  no-production-data precondition, so whatever intermediate migration is written here is folded away
  by its later reset.

## Explicitly not in scope

Each is deferred to a named successor rather than refused.

- **No attempt-history UI.** Prior records are queryable, not surfaced.
- **No retake trigger, no progress reset, no unregister flow, no cohort-move action.** All four are
  claimed by `spec_dd/1. next/learner-management-actions/`, which sequences itself after this work.
  Note that a second record for one learner and course **is** reachable in this cut — by holding a
  cohort and an individual registration at once (§Keyed on the grant). What is not reachable is a
  *deliberate* second pass, because that needs a second registration for the same course through the
  same path, which `unique_learner_course_registration` forbids for the individual path.
- **No learner-facing organisation switch.** The learner interface has no organisation dimension in
  its URLs.
- **No organisation-aware course access.** `is_registered_for_course` and every
  `COURSE_ACCESS_BACKEND` stay organisation-blind. This asymmetry is deliberate: **access stays
  organisation-blind while progress becomes organisation-scoped.**
- **No validity / expiry / recertification window.** Additive once multiple records exist; a rewrite
  if not.
- **No registration-level provenance beyond the grant itself.** With `PROTECT`, a record's grant FK
  *is* durable — it names the registration that minted it and that registration cannot be deleted.
  What is still not captured is a history of the registration's own changes over time (deactivation,
  reactivation, a cohort move re-pointing it). If that is wanted, the answer is a record frozen at
  completion time, not more FKs.
- **No content snapshots.** Decided, not deferred by omission. A record does not pin a content
  snapshot in this cut. `content_snapshots` is in flight beside this work and names no consumer; the
  direction is fixed if it is ever built — progress may depend on `content_snapshots`, never the
  reverse. "What did this learner actually see" stays unanswerable, and that is accepted.
- **No modular-courses authoring.** Only the schema that stops it being a lossy migration later.
- **No `Learner` deletion path.** Deactivation is the only removal. Nothing here adds a delete path.
- **`RecommendedCourse` stays `User`-keyed** (`learner_management/models.py:352-378`). It is a
  recommendation, not an enrolment.
- **No new system check.** House conventions from `fls-integration-system-checks` forbid database
  access in a check, so a data-integrity assertion about progress rows is a management command or a
  test, never a check.
- **No `continued_from` column.** `decision.md` proposed a self-FK as an escape hatch for a future
  cohort-move that wants a clean per-cohort record rather than re-pointing. **It is dropped**: no
  code in this cut reads or writes it, and a column with no reader is scope creep, not
  foresight. There is no production data, so adding it later is a plain additive migration — the
  same cost as adding it now, minus the risk of shipping a field whose meaning nobody has had to
  pin down against a real caller.

## Success criteria

1. `CourseProgress` carries `learner`, `course`, exactly one of `learner_registration` /
   `cohort_registration`, and `last_accessed_item` as a concrete `ContentCollectionItem` FK. It
   carries **no** `is_active`. Neither `TopicProgress` nor `FormProgress` has a `user` field.
2. Registering a learner for a course creates exactly one record. Registering a cohort creates one
   per member whose `Learner` is active. Adding an active member to a cohort that holds an active
   course registration creates one. A member whose `Learner` is inactive gets none.
3. Re-registering, reactivating a registration, or re-adding a membership creates **no** second
   record for that same registration and does not modify the existing one.
4. Deleting a membership, deactivating a registration or deactivating a `Learner` leaves every record
   untouched, and deleting a registration that granted a record raises `ProtectedError`.
5. Two `Learner` rows for one user, registered for one course in two organisations, hold two
   independent records: completing the course in one leaves the other at its own percentage, its own
   `completed_time` and its own resume pointer.
6. The same `Topic` placed in two courses is completed independently in each.
7. Every record has a `site` matching its `learner`, with no caller passing `site=` by hand.
8. The educator matrix reads **both** its percentage column and its item cells from the selected
   cohort registration's records, and applies the same organisation scoping as the data tables
   beside it.
9. A person in two organisations sees each organisation's deadlines separately, not a union.
10. `course.registered` and `course.completed` both carry `organisation_id` and the course progress
    record id, with every existing field unchanged.
11. A learner with content access but no registration reaches the player without a 500, and no
    progress row is written for them.
12. `uv run pytest` passes, `uv run manage.py makemigrations --check` reports nothing pending, and
    `docs/app_structure.md` shows **exactly one** new runtime edge out of `learner_progress` —
    `learner_progress --> webhooks`, which §`course.registered` moves to the fan-out receiver
    creates — and **no** new runtime edge into `learner_progress` from `learner_management`.

## Test coverage required

Coverage for "two records, one learner, one course" is entirely net-new — the current constraints
make such a test impossible to write.

**Constraints**
- `one_course_progress_per_learner_registration` and `one_course_progress_per_cohort_registration`
  each reject a second record for the same `(registration, learner)`.
- Neither constraint interferes with the other: many cohort-granted records for one learner coexist
  despite all sharing a null `learner_registration`, and symmetrically.
- Two records for one `(learner, course)` — one per grant — are **permitted**, and
  `course_progress_for` resolves to the cohort one.
- A learner in two cohorts that both hold an active registration for one course resolves
  **deterministically** to the same record across repeated calls, per the `(-is_active,
  -registered_at)` tiebreak — not to whichever row the query planner returns first.
- `course_progress_has_exactly_one_grant` rejects a record with two grants and one with none.
- Deleting a `CohortCourseRegistration` or a `LearnerCourseRegistration` that granted records raises
  `ProtectedError`; deactivating it does not.
- `danger_content_delete` succeeds with progress rows present (it clears them first), and
  `PROTECT` blocks deleting a `Topic` that has progress by any other route.

**The sync service**
- Idempotent: called twice, one record, unchanged timestamps and unchanged grant.
- Cohort fan-out covers exactly the active members; a member added later gets one.
- `site` comes from `learner.site` with no ambient request — assert under a management-command-style
  context and under a *foreign* ambient site.
- `raw=True` (a `loaddata` fixture) creates nothing.
- Membership removal / registration deactivation / learner deactivation change nothing.

**Independence** — the shapes the current schema cannot express
- Two organisations: one user, two `Learner` rows, two registrations, two records. Completing one
  leaves the other's percentage, `completed_time` and resume pointer untouched.
- One `Learner`, one course, two grants (cohort and individual): two records, each starting at zero,
  each accumulating only its own work. The learner interface writes to the cohort one throughout, and
  the individual one stays at 0%.
- One `Topic` placed in two courses: completing it in course A leaves course B at 0%.

**Read paths** — each asserting *which* record's data appears, not just a 200
- The educator matrix percentage for a learner registered through two organisations.
- The educator matrix for a cohort member who also holds an individual registration: the panel shows
  the **cohort** record, and its percentage column and item cells agree with each other.
- The Start / Continue / Review CTA, the resume index, and the player progress maps.
- `get_current_courses` / `get_completed_courses` / `get_course_listing`.
- `unpassed_forms` — a failed quiz in another course does not withhold this course's completion.
- Reports: first-attempt and latest-attempt scoped within one record; `has_any_progress` false for a
  learner with a fresh record and no activity.

**Deadlines** — a person in two organisations sees each organisation's deadlines separately.

**Webhooks** — both payloads carry the new fields; `course.registered` fires once, on creation only,
after the record exists, and works with no ambient request.

**Degradation** — content access with no registration writes nothing and does not raise.

**Preserved behaviour** — a failed quiz still does not complete an item, and `course_finish` still
withholds `completed_time` while any quiz is unpassed.

**Timestamps** — the completion page's "Started:" date shows first *content access*, not the
registration date, for a learner registered well before they began.

## Risks

**The blast radius is large and mostly silent.** Roughly sixty files reference the three models.
The crashing sites are easy; the silently-wrong ones produce plausible percentages. Mitigation: the
"which record's data" assertions above are not optional, and the six `FormProgress` attempt-helper
call sites move as one unit.

**The deadline re-scoping has nothing to grep for.** Seven filters are correct today and become wrong
only because the grain moves under them. Mitigation: the tests are the only detector; write them
first.

**Moving `course.registered` changes a shipped webhook's firing site.** Mitigation: preserve
fire-on-creation-only and the `_base_manager` lookup explicitly, and test both.

**`transaction.on_commit` changes when records become visible.** A caller that registers a learner and
immediately reads their record inside the same transaction will not find one. Mitigation: the
self-healing path in `view_course_item` covers the user-facing case; test-side, factories that need a
record must create it rather than rely on the receiver.

**A cohort fan-out over a very large cohort is one large write.** Mitigation: `bulk_create` with
`ignore_conflicts=True`, deferred to commit. `reports` already caps cohort size via
`REPORTS_MAX_LEARNERS`; this spec adds no cap of its own.

**Exposing the collection item through the content accessors touches `content_engine`, which nothing
else in this work touches.** Mitigation: add a parallel accessor rather than widening the existing
ones, so every current reader is unaffected.
