## 2. Content loading and sync path

**Schemas.** `freedom_ls/content_engine/schema.py`:
- `Child` :172-180: `path: Path`, `overrides: dict[str, Any] | None`, `extra="forbid"`. The comment says "optional overrides as key-value pairs". **`overrides` is stored but read by nothing** (grep of `.overrides` in learner_interface, content_base, templates: no consumer). No demo content, plugin doc or test sets it (the `overrides` hits in `tests/` are unrelated kwargs).
- `Course` :345-470 (`model_config = ConfigDict(extra="forbid", use_enum_values=True)`; `children: list[Child]` :352; other optional fields `estimated_duration: timedelta | None` :407, `access_config`, `price`). Validation style: `field_validator`/`model_validator(mode="after")` raising `ValueError`; price rules shared via `content_engine/prices.py` and copied into the plugin.
- `CoursePart` :473-483 has `children: list[Child]` and `extra="forbid"`. `Topic` :94 / `Activity` :98 inherit `BaseContentModel, MarkdownContentModel` (`freedom_ls/content_base/schema.py`) with no `extra="forbid"` shown here; the item-level field choice (frontmatter on `Topic`/`Form` vs on the parent's `children` entry) matters because **the same child file can be placed in two collections**, and only the `children` entry knows the placement. With auto-discovery (no `children:` written, the case for every demo course) there is no `Child` entry at all, so an authored default for a placement needs either a `children:` list or a field on the child's own file.
- `Form` schema lives in `freedom_ls/form_engine/schema.py` (not re-read).
- Offline validator `claude_plugins/fls-content/validate/schema.py` is a **bundled, patched copy** ("Bundled from freedom_ls/content_engine/schema.py ... re-sync via /update_claude_plugin_fls_content", header lines 1-30, with listed patches; `Child` copy :254, `Course` children :581, `CoursePart` children :752). Resync command: `claude_plugins/fls-dev/commands/update_claude_plugin_fls_content.md`. Tests: `claude_plugins/fls-content/validate/tests/test_validator.py`. Any Django import in a new validator (the `price` rules use a patched `_default_currency`) needs a patch note; pure-pydantic fields need none. The date type must not rely on Django.

**Loader.** `freedom_ls/content_engine/management/commands/content_save.py`:
- `save_content_to_db` ends with the child pass :1001-1121. `children_list` is `(resolved path, child.overrides)` pairs from `schema_item.children` (:1015-1018); with none, it scans the directory (:1020-1085) and appends `(path, None)`.
- Placement write :1100-1110: `ContentCollectionItem.objects.update_or_create(site=, collection_type=, collection_id=, child_type=, child_id=, defaults={"order": order, "overrides": overrides})`. The lookup key is (site, collection, child). Consequences: (a) a placement keeps its pk while the child stays in the same collection, whatever its order; (b) **the same child twice in one collection's `children:` collapses to one row** (the second `update_or_create` overwrites order and overrides); two placements are only possible across different collections (course vs a part, or two parts); (c) moving a child to another collection creates a new row; (d) **there is no prune or delete of placements anywhere in the file**, so a dropped or moved child leaves the old `ContentCollectionItem` in the old collection and `Course.collection_items()` (`courses.py:405`, `self.items.prefetch_related("child")`) still returns it. Existing behaviour, and it means a moved child currently shows twice in the table of contents; spec 1's "what a re-import does to a moved placement" starts from that fact. `TopicProgress.collection_item`, `CourseFormAttempt.collection_item`, `CourseProgress.last_accessed_item` are `SET_NULL` (RCD s3).
- The `else` branch raises `ValueError` when a named child was not loaded (:1115-1121); the whole load is atomic (test `test_a_failure_later_in_the_load_leaves_no_course_with_a_partial_category_set`, `tests/management/commands/test_content_save.py:1414`).
- `save_course` :521-578 passes the schema through `save_with_uuid(Course, item, site, base_path, exclude_fields={"children","categories","dashboard_category","price"}, ...)`: a new scalar course field (e.g. a time limit) is written by name onto a same-named `Course` model field automatically; a structured field needs `exclude_fields` plus explicit columns as `price` does (`price_columns` :492). An absent key leaves the stored value alone for `price` (:562-565); that "absent means untouched vs null clears" rule is the precedent for default fields.
- Validation entry points: `content_validate` command and `validate(path)` called by the `command` at :1136-1144; the offline copy mirrors it.

**`ContentCollectionItem`** (`courses.py:518-557`): `SiteAwareModel, TimestampedModel`; `collection_type/collection_id`, `child_type/child_id` GenericForeignKeys with UUID ids, `order`, `overrides` JSONField(null). Admin: `ContentCollectionItemInline` `content_engine/admin.py:148` (`fields = ("child_type","child_id","order","overrides")`), `ContentCollectionItemAdmin` :229-230. Factory `ContentCollectionItemFactory` `content_engine/factories.py:94`; test helper `content_engine/tests/helpers.py:9 collection_item_for`.

## 5. Site time zone

- **There is no per-site time zone.** `config/settings_base.py:255 TIME_ZONE = "UTC"`, `:259 USE_TZ = True`; `LANGUAGE_CODE = "en-us"` :253. No `activate()`, `zoneinfo`, or `get_current_timezone` use in app code (one QA command, `qa_create_notification_scenarios.py:275`, uses `timezone.get_current_timezone()`). Django's `Site` (contrib.sites) is unregistered from admin by `site_aware_models/admin.py:19-20` and has no zone field. No middleware sets a zone.
- A time-zone setting has three existing homes to compare: (a) a per-site policy row, the `SiteSignupPolicy` pattern (`freedom_ls/accounts/models.py:150`; `SiteAwareModel, TimestampedModel`, `UniqueConstraint(fields=["site"])`, "no row means a global config default", admin `accounts/admin.py:55`), also `SiteMessagingConfig` (`messaging_policy/models.py:76`); (b) an `AppSettings` declared setting (`base/app_settings.py`, e.g. `learner_management/config.py`, which only declares `DEADLINES_ACTIVE` and would go with it, or a new default in another app's `config.py`); (c) Django's global `TIME_ZONE`. `docs/product` and `domain-glossary` define no site time zone. RDIP s2 notes `user-communication-7-email-digests` plans "timezone from the recipient" because no user zone exists; the idea here says no user zone field, so the two efforts share the same gap and must not each invent a site zone.
- Idea's "every date shown names its time zone": needs a formatter (template filter or tag) in `learner_interface` or `base`; none exists. Django's `|date:"T"` prints the abbreviation only when the value is in a zone-aware, activated zone; `timezone.override(...)` / `localtime` is the mechanism.
