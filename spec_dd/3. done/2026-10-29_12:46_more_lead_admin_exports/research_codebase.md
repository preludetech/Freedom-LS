# Research: codebase - more_lead_admin_exports

Question: what in the existing codebase does "export Users and Applications (including anon) through the admin, with the full application form" touch, reuse or conflict with?

Idea: export Users and Applications (including anonymous) via the admin; application export must include the full application form.

## 1. Short answer

- A complete, tested admin CSV export stack already exists and is the thing to reuse: `SiteAwareExportModelAdmin` + `SiteAwareModelResource` + `FormulaSafeCSV` (django-import-export, with unfold's integration). Only `referral_tracking` uses it today. Neither `UserAdmin` nor `CourseApplicationAdmin` nor `AnonymousApplicantAdmin` uses it.
- "Applications" = `CourseApplication` (in `freedom_ls/course_applications/`), which is either user-held (signed in or claimed) or anonymous (`anonymous_applicant` -> `AnonymousApplicant`, no User until the claim link is followed). "The full application form" = the applicant's `FormProgress` sitting and its `QuestionAnswer` rows, walked against the live `Form` definition by `form_engine.queries.answer_groups`.
- The hard design problem is not the CSV plumbing but the shape: one row per application with a column per form question (forms differ per course, and questions change), vs. one long row per answer. Nothing in the repo does a dynamic-column export yet.
- No "lead admin" role, no "lead" concept (as an application/lead entity) and no custom export permission exists anywhere. The word "lead" in the repo only occurs in unrelated prose/"leading" etc. (spot-checked `accounts`, `docs/product`; the glossary has no entry). The spec must define who "lead admin" is (see section 7).

## 3. What "Applications" means here

Models in `freedom_ls/course_applications/models.py`:
- `CourseApplication(SiteAwareModel)`: fields `user` (FK, null, CASCADE), `anonymous_applicant` (OneToOne -> `AnonymousApplicant`, null), `course` (FK -> `content_engine.Course`, related_name `applications`), `form_progress` (OneToOne -> `form_engine.FormProgress`, null, RESTRICT, related_name `course_application`), `created_at`, `updated_at`. Unique constraint `unique_application_per_site_user_course`. Properties: `is_submitted` (no sitting = submitted at creation; else `form_progress.completed_time` not null), `is_email_verified` (user is set), `unverified_applicant`, `applicant_email`, `applicant_name`. A module NOTE says review state (FSM `state`, `submitted_at`, notes, reviewer permissions) is planned but absent: do not architect against that.
- `AnonymousApplicant(SiteAwareModel, TimestampedModel)`: `course`, `email`, `first_name`, `last_name`, consent evidence (`terms_version`, `terms_git_hash`, `privacy_version`, `privacy_git_hash`, `consent_ip_address`, `consented_at`), `user` (set on claim), `claimed_at`, `claim_email_sent_at`, `claim_link_version`. `__str__` deliberately omits email (admin log outlives erasure).
- So "Applications (including anon)" = all `CourseApplication` rows: those with `user` set, and those whose only identity is `anonymous_applicant` (unverified, `user is None`). A claimed anonymous applicant also has `user` set, so the same application appears once; no double-count risk if exports key on `CourseApplication`. Exporting `AnonymousApplicant` rows separately would double count claimed ones.
- The course names its application form via `Course.application_form` (FK, `freedom_ls/content_engine/models/courses.py:176`), bound by the content loader from `access_config` `application_form:` in course.md. An application snapshots its own sitting in `form_progress`, so it survives the course being re-pointed.
- Related: `freedom_ls/course_applications/erasure.py` (`erase_anonymous_applicant`), `claims.py` (`attach_to_user`), `backends.py` (`ApplicationCourseAccessBackend`), `factories.py` (`CourseApplicationFactory`), `tests/helpers.py` (`UnverifiedApplication` NamedTuple for tests). Existing tests live in `course_applications/tests/`.
- Related but different: `accounts.SiteSignupPolicy.additional_registration_forms` (JSONField) = extra forms shown at signup/post-verification, and `accounts.LegalConsent` (consent method `application_details_step`). These are "registration forms" for ordinary signups, not applications; the idea does not mention them. Confirm out of scope.

## 4. How the application form answers are stored

(`freedom_ls/form_engine/models.py`)
- `Form` -> `FormPage` (`pages`) -> children: `FormQuestion` (`type`, `question`, `required`, `order`, `category`, `min`/`max`, `decimal_places`) and `FormContent` (non-question text). `QuestionOption` (`text`, `value`, `order`, `correct`) per question.
- `FormProgress(SiteAwareModel)`: `form` (PROTECT), `user` (null for anonymous sitting), `start_time`, `last_updated_time`, `completed_time`, `scores`, `furthest_page_reached`.
- `QuestionAnswer(SiteAwareModel, TimestampedModel)`: `form_progress` (related_name `answers`), `question` (PROTECT), `selected_options` (M2M `QuestionOption`), `text_answer` (TextField). Unique per (form_progress, question). A blank answer stores NO row.
- `QuestionAnswerFile`: OneToOne `answer`, `file` (stored in `user_uploads` storage alias via `get_user_uploads_storage`), `original_filename`. File-upload questions (`QuestionType.FILE_UPLOAD`) hold files (e.g. ID scans); a CSV can carry the filename but not the file.
- Question types in `form_engine/enums.py` (`QuestionType`, `FREE_TEXT_QUESTION_TYPES`); date/time answers are stored as text and rendered by `form_engine/typed_answers.py: format_answer` (locale-formatted - an export should prefer the stored ISO text, cf. `IsoDateWidget`), `parsed_date`, `parsed_time`, `parsed_number`.
- Reusable read model: `form_engine/queries.py: answer_groups(form_progress) -> list[AnswerGroup]` where `AnswerGroup(title, rows: list[AnswerRow(question, answer|None)])`. It walks the form's CURRENT pages so skipped questions get a row and edited questions show current wording, then appends a final group `FINAL_GROUP_TITLE = "Questions no longer on the form"` for answered questions that left every page. It prefetches `answers__selected_options`, `answers__answer_file`, `answers__question` per call (so an N-row export would cost per-row queries unless batched; consider prefetching). This is exactly what "the full application form" needs: question order, skipped questions, removed questions.
- Existing display consumer: `form_engine/admin.py: answers_context(request, form_progress)` (answer_groups + `can_download_answer_files`), used by `CourseApplicationAdmin.render_change_form` with `change_form_template = "admin/form_engine/answers_change_form.html"`. `form_engine/permissions.py: can_download_answer_files(user)` = `user.has_perm("freedom_ls_form_engine.view_questionanswerfile")` - the established precedent: file access is gated on a SEPARATE model view permission. An export that includes answers (possibly sensitive) should decide whether it needs similar gating.
- Also in `form_engine/admin.py`: `_with_applicant_select_related(list_select_related, sitting_path)` (adds `course_application__anonymous_applicant` only if `course_applications` is installed - form_engine sits below course_applications, so form_engine code must not import it); `applicant_label(form_progress)`.
- Done-spec decision (course-applications-admin, `research_admin_answer_display.md`): reviewers want answers in exports; competitors' known complaint is edited/removed questions showing wrongly or being lost in exports. Design implication: column per question needs a stable key (question id/pk, not label), with a label header, and handling for removed questions.

## 5. The admin classes to change

- `freedom_ls/course_applications/admin.py`:
  - `CourseApplicationAdmin(SiteAwareModelAdmin)`: read-only (no add/change/delete). `list_display = applicant_email, applicant_name, is_email_verified, course, is_submitted, submitted_time, created_at`; `list_select_related = [user, anonymous_applicant, course, form_progress]`; filters `CourseApplicationSubmittedFilter`, `EmailVerifiedFilter`, course autocomplete, created_at `InclusiveRangeDateTimeFilter`; `search_fields` cover user and anonymous applicant. `get_queryset` select_related already set. `has_change_permission` returns False => with the standard `ExportActionMixin`/`SiteAwareExportModelAdmin`, `has_export_permission` = view permission, so read-only models still export (this is how the read-only referral admins work). Switching its base to `SiteAwareExportModelAdmin` is the minimal reuse path. Note `unfold` action/list-filter submit is `list_filter_submit = True`.
  - `AnonymousApplicantAdmin(SiteAwareModelAdmin)`: read-only, delete = erase (claimed ones protected). Has consent fields (IP, versions) that a lead team may or may not want exported.
  - Module registers `USER_ERASURE_CASCADE_MODELS.add(CourseApplication)` and `(AnonymousApplicant)` (from `accounts.admin`).
- `freedom_ls/accounts/admin.py`: `UserAdmin(SiteAwareModelAdmin)` with `list_display = email, first_name, last_name, is_staff, is_active`, `search_fields`, `list_filter = is_staff, is_superuser, is_active`, `ordering = ["email"]`, inline `LegalConsentInline`. Not an export admin yet.
- `User` (`accounts/models.py:69`): `SiteAwareModelBase, TimestampedModel, AbstractBaseUser, PermissionsMixin`. Integer pk (deliberate), `email` (globally unique), `first_name`, `last_name`, `is_active/is_staff/is_superuser`, `groups`, `user_permissions`, timestamps; `USERNAME_FIELD = "email"`; manager `UserManager`. Sensitive fields to EXCLUDE from an export: `password` (hash), `user_permissions`/`groups` likely, `is_superuser`. A ModelResource with no `fields`/`exclude` would export `password` - an explicit `fields` whitelist is required. Other per-user data lives in other apps (hr_attributes - see `freedom_ls/hr_attributes/models.py`, `signup attribution` in `referral_tracking`, learner profile in `learner_management`); the idea says only "Users", so spec must say whether HR attributes/attribution are in the user export.
- Mixin ordering gotcha: `SiteAwareExportModelAdmin` is `(ExportActionMixin, SiteAwareModelAdmin)`; `UserAdmin` has its own `get_form`; any new base must keep `exclude = ["site"]`. `UserAdmin` is the only place that unregisters nothing for User; `Group` is unregistered in `accounts/admin.py`.

## 6. Site-awareness constraints

- `SiteAwareManager.get_queryset` (`site_aware_models/models.py:118`) filters by the current request's site (thread-local request, `get_cached_site`), falling through unfiltered only for an unknown Host. `User` is site-aware too (`SiteAwareModelBase`; `objects = UserManager()` - check `UserManager` inherits the site filtering before assuming; `freedom_ls/accounts/models.py` ~lines 20-66). The admin changelist/export therefore only sees the current site's rows automatically; the export action reuses `get_queryset`/changelist queryset, so no manual `site_id` filtering (CLAUDE.md: never filter on site_id manually). `SiteAwareModelResource` drops the `site` column.
- Gotcha: a resource's own `get_queryset` or any `Model.objects` use outside a request (management command, background job, celery) is NOT site filtered. A synchronous admin download is request-bound and safe; an async/emailed export would need explicit site scoping. Not asked for.
- Gotcha: `form_engine.queries.answer_groups` uses `form_progress.form.pages` (not site-aware-managed beyond the same manager) - fine in a request.
- `AnonymousApplicant.course`/`CourseApplication.course` and `FormProgress.form` are all site-aware; a course in another site cannot appear.

## 7. Permissions and roles

- `has_export_permission` on `SiteAwareExportModelAdmin` = `has_view_permission` on that admin's model. `CourseApplicationAdmin` does not override `has_view_permission`, so anyone with `course_applications.view_courseapplication` (superuser, or staff with granted permission) could export applications - including all answers if answers are exported. Because the answer text is the sensitive part and `view_questionanswerfile` already gates file downloads, the spec should decide whether exporting answers requires `view_formprogress`/`view_questionanswer` as well.
- GuardedSiteAwareModelAdmin exists (django-guardian, object-level) but neither UserAdmin nor CourseApplicationAdmin uses it. `freedom_ls/role_based_permissions/` (README mentions roles) is the educator-interface role system, separate from Django model permissions; its relation to the admin is unchecked here (flag for the spec: look at `freedom_ls/role_based_permissions/README.md` before inventing a "lead admin" role).
- There is NO "lead admin" role, group, permission or fixture anywhere in the repo (grep for `lead_admin`, `lead admin` returned nothing in code/docs). The done spec for applications admin considered `SuperuserOnlyAdmin` in research (`research_application_changelist.md` "Recommended `CourseApplicationAdmin(SuperuserOnlyAdmin, SiteAwareModelAdmin)`") but no such class exists in code (grep for `SuperuserOnlyAdmin` finds nothing), so the final design just uses model view permission. The branch/idea name `more_lead_admin_exports` suggests the user is the "lead admin"; the spec must say whether that is a Django Group with view permissions (no new code), superusers only, or a new role. Recommended default: no new role; export gated by existing Django view permissions (consistent with `SiteAwareExportModelAdmin`), documented so a site operator can grant them to whoever their lead admins are.
- User export of the `User` model needs `accounts.view_user`. Note `UserAdmin` has no permission overrides.
- PII: exporting users/applicants (emails, names, consent IPs) to CSV is a new data egress; `docs/product/security-and-data-handling.md` (line ~192 long entry) and `roadmap.md:115` describe the posture (operator is controller; no portability export). Admin log of exports: import-export has no export audit trail by default; check whether the spec wants one (CLAUDE.md says don't add logging unless asked).

## 10. Risks, conflicts and open questions for the spec

1. Column shape for the form: forms are per course; one changelist can mix several courses (different questions). Options: (a) one row per application with columns = union of questions of the forms involved (column key by question id, header = question text; stable even if question edited), (b) long format, one row per answer (application id, question, answer), (c) one export per course/form (filter by course first). `ModelResource` is static per-class; dynamic columns need overriding `get_export_headers`/`export_field` or `before_export` with a built dataset. Decide and state what happens for questions removed from the form (use `FINAL_GROUP_TITLE` group) and skipped questions (blank).
2. Multi-select answers: `selected_options` M2M plus `text_answer`; need an agreed join delimiter and whether to export option `text`, `value` or both.
3. File-upload answers: export `original_filename` only (or a flag), never storage keys/URLs; downloads are gated by `can_download_answer_files`.
4. Draft vs submitted applications: default export includes both unless filtered (existing filter `CourseApplicationSubmittedFilter`); export should include `is_submitted`/`submitted_time` columns so rows can be told apart.
5. Anonymous rows: identity from `anonymous_applicant` (email, names) when `user` is None - use `CourseApplication.applicant_email`/`applicant_name`; include `is_email_verified`. Consent fields on `AnonymousApplicant` - include or not.
6. Performance: `answer_groups` is per-sitting with its own prefetch; an export of thousands of applications needs a batched prefetch (`answers__selected_options`, `answers__answer_file`, `answers__question`, `form__pages`) and ideally streaming; import-export builds the whole dataset in memory.
7. Formula safety: answers are free text typed by anonymous visitors, the highest-risk CSV injection input; `FormulaSafeCSV` already escapes every string cell - dynamic columns must still go through it. Test that.
8. User export: whitelist fields (never `password`); decide on `groups`, `last_login`, `date_joined`-like timestamps (TimestampedModel `created_at`/`updated_at`), and extras from other apps.
9. Permissions: as section 7. Also staff users who lack `view_courseapplication` must get 403 on the export URL (the referral tests are the template).
10. Tests: follow `referral_tracking/tests/test_resources.py` and its admin export tests; `accounts` and `course_applications` have no export tests yet (grep: 0 in `accounts/tests`). Use `CourseApplicationFactory`, `UnverifiedApplication` helper, `FormProgressFactory`, `QuestionAnswerFactory`, `QuestionAnswerFileFactory`. Needs a multi-site test (rows from another site must not appear).
11. Dependency direction: `accounts` -> `site_aware_models`; `course_applications` -> `accounts`, `form_engine`; `form_engine` must not import `course_applications`. Put the application resource in `freedom_ls/course_applications/resources.py` and the user resource in `freedom_ls/accounts/resources.py` (use `get_user_model()`).
12. Upgrade notes: adding export is additive, no migration; likely an upgrade note only if new permissions or settings are introduced.
