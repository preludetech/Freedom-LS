## Ground rules for every slice

- **Generic files stay generic.** The three `django-stack` files use `myproject` / `myapp` /
  `optional_feature` / `WidgetFactory` placeholders and never name an FLS app, path, fixture or
  factory. Today they contain no FLS names (verified by grep); every slice keeps it that way.
- **FLS names go only into `fls-dev:testing`.** Each rule's FLS instance is one short paragraph or
  list in `claude_plugins/fls-dev/skills/testing/SKILL.md`, under a new `## Test organisation and
  hygiene` section that opens with the pointer at `ds:testing`'s section of the same name. The
  overlay's existing framing ("adds only the FreedomLS specifics; it does not repeat the generic
  body") is the rule for how much to write: name the FLS file and what makes it the instance, do
  not restate the generic rule.
- **One section in the resource.** All new generic material in `resources/testing.md` goes into one
  new `## Test organisation and hygiene` section, placed after `## Creating Test Data` and before
  `## Test Patterns`, with one `###` subsection per rule below. `SKILL.md` links to it by section
  name, as it already links to "Collection safety for optional apps" and "HTMX test patterns".
- **Spec vocabulary is the heading vocabulary.** Subsection titles are the spec's own bold headings:
  Mirroring, Dependency direction, Deciding an allowed exception, Granting permissions in tests,
  `conftest.py` vs. plain module, Fixture placement, Fixture scope and idempotent reset, The
  thin-wrapper rule, Stub-model technique, Factory cross-app direction, Named exceptions. One
  heading is not bold in the spec: "Cross-cutting tests" names the second paragraph under rule 1
  (the tests with no module to mirror), using the spec's own words for them.
- **Citations are checked, not remembered.** Every FLS path, fixture name and function name the
  overlay cites is in `research_skill_files_and_citations.md` with its verification. Three
  corrections from that research are already folded into the spec and must not regress:
  `staff_client` (not `logged_in_client`) is the composed-fixture example; `mock_site_context` is
  opt-in, not autouse; `learner_interface/tests/conftest.py` has ten plain functions, so cite "plain
  functions" without a count.
- **Skills to load while editing.** `ds:testing` and `fls-dev:testing` are the files under edit,
  so read both skills and their resources in full before the first slice and follow each file's
  existing conventions (how key rules are phrased, how resources are linked by section name, the
  overlay's "adds only the FreedomLS specifics" framing). Load `code-comments` for the generic code
  examples and for the one-line exception comment the dependency-direction rule prescribes (it
  explains why, never what). Load `domain-glossary` before naming anything FLS-specific; "grant"
  means a role or object permission there, which is the sense "Granting permissions in tests"
  uses. Load `unslop` for all prose: no em dashes, sentence-case headings, no bold-label lists
  that restate the label. The idea already writes in that register; match it. No MCP applies.
- **Skill files cite no spec.** The idea routes work between specs ("spec 10 decides", "specs 5,
  8, 11 and 15 apply this") and names research files under `spec_dd/`. None of that goes into a
  skill file: `spec_dd/` directories move when specs finish and `code-comments` forbids citing
  documents that get renumbered. Where the idea says a later spec will do something, the skill
  states the present fact ("no FLS app mirrors a subpackage yet") and stops.
- **Proof for each slice.** These are markdown files with no test suite of their own. Each slice is
  done when: the pre-commit hooks pass on the changed files (`uv run pre-commit run --files
  <paths>`), every section name a `SKILL.md` link cites exists as a heading in the file it points
  at (`grep -n "^## \|^### "`), `grep -n "freedom_ls\|FreedomLS\|FLS"` over the three
  `django-stack` files is still empty, and `uv run pytest -n auto` still passes (nothing under
  test changed, so this only guards against an accidental edit outside the four files).
- **Commit per slice.** Each slice is one commit, made with `uv run git commit` so the hooks run.

## Slice 2: Rule 1, Mirroring, and cross-cutting tests

**Behaviour delivered.** A reader of `ds:testing` knows where a test file goes for a module, a
subpackage module, a browser test, a test-only helper and a cross-cutting test, and a reader of
`fls-dev:testing` knows the FLS instances and the one deliberate exception.

**`claude_plugins/django-stack/skills/testing/SKILL.md`**, "Key rules": replace the single line
`Test files: <app>/tests/test_<module>.py` with:

- Tests mirror the app, subpackages included: `<app>/<module>.py` →
  `<app>/tests/test_<module>.py`. See "Mirroring" in `${CLAUDE_PLUGIN_ROOT}/resources/testing.md`.

The subpackage example and the test-only-helper clause live in the resource, not here.

**`claude_plugins/django-stack/resources/testing.md`**: create the `## Test organisation and
hygiene` section between `## Creating Test Data` and `## Test Patterns`, opening with one sentence
naming its two rules (mirroring and dependency direction) and the layering that follows from them.
Add the first two subsections.

`### Mirroring`:

- The convention: a flat `tests/` package inside the app, one test file per production module,
  `<app>/<module>.py` → `<app>/tests/test_<module>.py`. Not a top-level mirrored tree, not a
  colocated `foo_test.py`.
- A subpackage is mirrored as a test subdirectory. Give both spec examples:
  `<app>/templatetags/content_tags.py` → `<app>/tests/templatetags/test_content_tags.py` and
  `<app>/management/commands/foo.py` → `<app>/tests/management/commands/test_foo.py`.
- Browser tests get one extra hop: `<app>/tests/playwright/test_<thing>.py`. This is where the
  `Markers` section's "Lives under per-app `tests/playwright/` dirs" line already points.
- A helper or URLconf module used only by an app's tests lives alongside those tests (for example
  `<app>/tests/root_urls.py`, `<app>/tests/builders.py`), never in `conftest.py`. Forward-reference
  the `conftest.py` vs. plain module subsection.

`### Cross-cutting tests`:

- Some test files check a property rather than one module's behaviour: an import-order invariant,
  migration state, settings resolution, a content or vendored-asset regression. They have no
  module to mirror and are legitimate.
- Group them in a clearly named test subpackage (`tests/demo_content/`, `tests/invariants/`) so
  they are not mistaken for unit tests that lost their module.

**`claude_plugins/fls-dev/skills/testing/SKILL.md`**: rename the existing `## Test file path
convention` section to `## Test organisation and hygiene`, keep its one line
(`freedom_ls/<app_name>/tests/test_<module>.py`), and open it with the pointer: read the section
of the same name in `ds:testing`'s resource first; what follows is the FLS instance of each rule.
Add the first instances as `###` subsections named after the generic ones:

`### Mirroring`:

- Test-only helper and URLconf modules that sit correctly beside their tests:
  `panel_framework/tests/root_urls.py`, `panel_framework/tests/stub_panels.py`,
  `health/tests/root_urls.py`, `reports/tests/gather_input_builders.py` and
  `reports/tests/report_data_builders.py`.

`### Cross-cutting tests`:

## Slice 3: Rule 2, Dependency direction, allowed exceptions and permission grants

**Behaviour delivered.** A reader knows which apps a test may import from, how to decide an
exception, and how to grant a permission without importing a layer the app does not depend on.

**`claude_plugins/django-stack/skills/testing/SKILL.md`**, "Key rules": add one line after the
mirroring rule.

- An app's tests import only apps the app depends on at runtime. A test that spans several apps
  belongs in the lowest app that depends on every app it touches. See "Test organisation and
  hygiene" in `${CLAUDE_PLUGIN_ROOT}/resources/testing.md`.

Also add one row to the "Anti-pattern cheatsheet" table: a test imports an app its own app does not
depend on / hides a real dependency, couples unrelated apps / move the test to the lowest app that
depends on everything it touches, or replace the import with a local stub or fixture.

**`claude_plugins/django-stack/resources/testing.md`**, three more subsections:

`### Dependency direction`:

- The rule as in the key rule, plus: the project's app dependency map (the table the `/ds:app_map`
  command generates into `docs/app_structure.md`, with its "Runtime deps" and "Test-only deps" columns)
  is the source of truth for what an app depends on and where the rule is violated today.
- The generator reads Python imports only, so it misses two real dependencies. State both in prose:
  - A dependency expressed as a dotted string is a runtime dependency on the app that owns the
    target: a model relation declared by label (`"myapp.Article"`, `settings.AUTH_USER_MODEL`) and a
    settings-registered dotted path (a context processor, middleware or backend).
  - The user is framework-level. Every request carries one, so any app's tests may use the
    `UserFactory` of whichever app owns the user model (`AUTH_USER_MODEL`).
- A test that spans several apps belongs in the lowest app that depends on every app it touches,
  not the app whose behaviour happens to be exercised first.

`### Deciding an allowed exception`:

- One test, not a fixed list. Is the "wrong" import intrinsic to what is being tested, meaning the
  thing under test cannot exist without a real row from the other app? Or is it standing in for
  something a local stub or fixture could provide?
- An intrinsic case gets a one-line comment at the import saying why, and no code change. A
  stand-in gets replaced (forward-reference "Stub-model technique").

`### Granting permissions in tests`:

- When an app's code checks permissions through the authorisation layer's standard API
  (`user.has_perm(...)`, `get_objects_for_user(...)`), its tests grant exactly the permission the
  code checks, through that same layer (`assign_perm(codename, user, obj)` for guardian). They do
  not go through a higher-level role layer the app does not depend on. Whether a role maps to the
  right permissions is that role layer's own concern, tested in its own suite.

**`claude_plugins/fls-dev/skills/testing/SKILL.md`**, three matching subsections:

`### Dependency direction`:

- `docs/app_structure.md`'s dependency table is the source of truth. Regenerate it with the
  `/ds:app_map` command (`generate_app_map.py`) rather than editing it.
- The string-reference case in FLS: `base` depends on `learner_management` because `TEMPLATES` in
  `config/settings_base.py` registers
  `freedom_ls.learner_management.context_processors.can_access_educator_interface` and `base`'s
  header template reads it. The table cannot see this edge.
- Any app's tests may use `accounts`' `UserFactory`.

`### Granting permissions in tests`:

- Use `guardian.shortcuts.assign_perm(codename, user, obj)`, not `role_based_permissions`'
  `assign_object_role`. The role layer is transparent at check time: its README says roles decide
  what permissions a user should have and guardian enforces them.
- `reports`, `educator_interface`, `learner_management`, `base` and `organisations` check only
  `has_perm` / `get_objects_for_user`, so their `assign_object_role` calls are stand-ins.
  `reports/tests/test_admin.py` already uses `assign_perm` next to them.
- Whether a role maps to the right permissions is `role_based_permissions`' concern, tested in its
  own suite.

No FLS instance is needed for "Deciding an allowed exception"; the test is generic.

## Slice 4: `conftest.py` vs. plain module, and fixture placement

**Behaviour delivered.** A reader knows what may live in a `conftest.py`, where a plain helper goes,
and which directory's conftest a fixture belongs in.

**`claude_plugins/django-stack/skills/testing/SKILL.md`**, "Key rules": add one line.

- `conftest.py` holds fixtures only; helpers that tests import go in a plain module beside them.
  See "`conftest.py` vs. plain module" and "Fixture placement" in
  `${CLAUDE_PLUGIN_ROOT}/resources/testing.md`.

**`claude_plugins/django-stack/resources/testing.md`**, two more subsections:

`### conftest.py vs. plain module`:

- `conftest.py` holds only `@pytest.fixture` functions plus private, underscore-prefixed helpers
  that only those fixtures call.
- A plain function that test files import by hand belongs in a plain module alongside the app's
  tests (`helpers.py`, `builders.py`), never in `conftest.py`. pytest does not discover plain
  conftest functions, so they still need an explicit import, which defeats the reason for putting
  them there. pytest's maintainers discourage importing from conftest (pytest issue #13148).
- A plain helper may stay in `conftest.py` only when more than one test file in the app needs it
  **and** a comment at its definition says why.
- Short generic example: a `conftest.py` with one fixture and one `_seed_...` helper, beside a
  `helpers.py` with a public `make_...` function.

`### Fixture placement`:

- Put a fixture in the shallowest directory whose conftest reaches every consumer. The mechanism is
  pytest's own: conftest files are collected by walking up from the test, and the nearest
  definition wins.
- The project root `conftest.py` holds project-wide fixtures only, either autouse or opted into
  from many apps. An app's `tests/conftest.py` holds fixtures used by more than one test file in
  that app. A fixture used by only one test file stays in that file.

**`claude_plugins/fls-dev/skills/testing/SKILL.md`**, two matching subsections:

`### conftest.py vs. plain module`:

- Pattern to follow: `accounts/tests/conftest.py`, two fixtures plus the private
  `_seed_default_legal_docs`.
- Pattern to avoid: `learner_interface/tests/conftest.py`, plain functions for manual import plus a
  `reverse_url` re-export from the root conftest.
- Second entry under `### Named exceptions`: `mail/tests/conftest.py`. Its docstring says the
  helpers are public because serialisation, the worker send and the backend are all tested against
  the same message shape.

`### Fixture placement`:

- `freedom_ls/conftest.py` holds the autouse `_disable_force_site_name`,
  `_disable_preview_overrides` and `_clear_course_access_backend_cache`, and the opt-in
  `mock_site_context` (which many apps' fixtures build on). Say "autouse" and "opt-in" precisely;
  `mock_site_context` is not autouse.

## Slice 5: Stub-model technique

**Behaviour delivered.** A reader of a foundational app knows how to test genericity without
importing a downstream model. This slice comes before the fixture-scope slice because the scope
example builds on the stub model defined here.

**`claude_plugins/django-stack/skills/testing/SKILL.md`**, "Key rules": add one line.

- A foundational app proves genericity with a stub model in its own `tests/conftest.py`, never by
  importing a downstream app's model. See "Stub-model technique" in the resource.

**`claude_plugins/django-stack/resources/testing.md`**, `### Stub-model technique`:

- When a foundational app's tests need "some object with an assignable role" or "any model with
  this mixin" to prove genericity, define a tiny test-only model in that app's own `conftest.py`.
  Give it an explicit `Meta.app_label` (Django registers the class in the app registry as soon as
  the class body runs), create its table with `connection.schema_editor()` in a session-scoped
  fixture, and never give it a factory_boy factory. A plain underscore helper (`_make_stub`)
  stands in for the factory.
- This fixes a foundational app's tests reaching for a real downstream model (cross-link "Deciding
  an allowed exception").
- `django.test.utils.isolate_apps` (and pytest-django's `django_isolate_apps` marker) is the
  lighter tool when a test needs only a model class and no database rows. It does not create
  tables, so it does not replace the stub-model technique.
- Generic example. It is the de-branded shape of the FLS reference with one model and no FK
  children, so it needs no `apps.all_models` registration line; that line in the FLS file serves
  the cascade-delete chain across its child stubs.

```python
# myproject/widgets/tests/conftest.py
from __future__ import annotations

import itertools
from collections.abc import Iterator

import pytest
from django.db import connection, models
from pytest_django.plugin import DjangoDbBlocker

_counter = itertools.count(1)


class StubModel(models.Model):
    name = models.CharField(max_length=120, unique=True)

    class Meta:
        app_label = "myproject_widgets"


@pytest.fixture(autouse=True, scope="session")
def _stub_tables(django_db_setup: None, django_db_blocker: DjangoDbBlocker) -> Iterator[None]:
    """Create the stub table once per session; the model has no migration."""
    with django_db_blocker.unblock():
        with connection.schema_editor() as editor:
            editor.create_model(StubModel)
        yield
        with connection.schema_editor() as editor:
            editor.delete_model(StubModel)


def _make_stub(name: str | None = None) -> StubModel:
    return StubModel.objects.create(name=name or f"stub-{next(_counter)}")
```

**`claude_plugins/fls-dev/skills/testing/SKILL.md`**, `### Stub-model technique`: the reference
implementation is `panel_framework/tests/conftest.py`: `StubModel`, `StubChild`,
`StubProtectedChild` and `StubGrandchild` (whose docstring says why it exists), with `_make_stub`,
`_make_stub_child` and `_make_stub_protected_child`. `site_aware_models` and
`role_based_permissions` still borrow downstream models in their tests and need this technique.

## Slice 6: Fixture scope and idempotent reset, and the thin-wrapper rule

**Behaviour delivered.** A reader knows when a wider fixture scope is justified, how to keep it
isolated under random ordering and table flushes, and what "thin wrapper" means.

**`claude_plugins/django-stack/skills/testing/SKILL.md`**, "Key rules": add one line.

- Fixtures are function-scoped unless profiling justifies wider, and a wide-scoped fixture never
  hands back state a test mutates. See "Fixture scope and idempotent reset" in the resource.

The thin-wrapper definition stays in the resource; the existing key rule "Use factory_boy
factories for all test data creation" already covers the skill-level message.

Also extend the "Test hygiene" bullet "No shared mutable state between tests" with a pointer to
"Fixture scope and idempotent reset" in the resource, and add a cheatsheet row: session-scoped
fixture returns rows a test mutates / order-dependent failures under `pytest-randomly`, wiped by
`transaction=True` / build the read-only part at wide scope, reset the mutable part per test.

**`claude_plugins/django-stack/resources/testing.md`**:

`### Fixture scope and idempotent reset`:

- Default to function scope. Widen to module or session scope only for setup that profiling shows
  is expensive, never to save typing.
- A session- or module-scoped fixture never hands back mutable state that a test then mutates. That
  is an isolation bug, and `pytest-randomly` exposes it: it reorders tests and reseeds factory_boy
  and Faker for each test. Cross-link "Test order independence".
- Where cost justifies a wider scope, build the expensive read-only part at that scope and reset or
  verify the per-test mutable part at function scope, idempotently (`get_or_create`, an explicit
  cache clear). Rows created at session scope do not survive a `transaction=True` test, which
  flushes the database. Cross-link "`transaction=True` is expensive".
- Generic example: the session-scoped `_stub_tables` from "Stub-model technique" is the expensive
  read-only part. Pair it with a function-scoped autouse fixture that resets the mutable part:

```python
@pytest.fixture(autouse=True)
def _stub_permissions(db: None) -> None:
    """Runs per test: a transaction=True test elsewhere flushes session-scoped rows,
    and the ContentType cache can hold a PK from a rolled-back transaction."""
    ContentType.objects.clear_cache()
    ct, _ = ContentType.objects.get_or_create(app_label="myproject_widgets", model="stubmodel")
    Permission.objects.get_or_create(
        content_type=ct, codename="change_stubmodel", defaults={"name": "Can change stub model"}
    )
```

Place it in the same conftest as the slice 5 example (add the two `django.contrib` imports there)
so the two subsections read as one file.

`### The thin-wrapper rule`:

- Move the existing line from "Creating Test Data" ("Avoid creating fixtures that are thin wrappers
  around factories. Rather just use the factories") here and define "thin": a fixture whose entire
  body is one factory call with fixed kwargs. Delete it and call the factory in the test.
- A fixture that composes several factory calls, adds relationship logic no single factory
  expresses, or builds on another fixture is not thin. That is the correct use of a fixture.
- In "Creating Test Data", replace the moved line with a one-line pointer to this subsection so the
  section stays about calling factories.

**`claude_plugins/fls-dev/skills/testing/SKILL.md`**:

`### Fixture scope and idempotent reset`: the FLS worked example is
`panel_framework/tests/conftest.py`. Quote `_panel_test_tables` (autouse, session-scoped, wrapped
in `django_db_blocker.unblock()`) and `_panel_test_permissions` (autouse, function-scoped,

## Slice 7: Factory cross-app direction, and the overlay's description

**Behaviour delivered.** A reader knows which direction a factory module may import another app's
factory, how to break a mutual dependency with the dotted-string form, and where the
`INSTALLED_APPS` guard goes. The `fls-dev:testing` frontmatter describes what the overlay now
covers.

**`claude_plugins/django-stack/skills/testing/SKILL.md`**, "Key rules": add one line.

- A factory imports another app's factory only in the runtime dependency direction; a cycle
  between peers uses the dotted-string form. See "Factory cross-app direction" in
  `${CLAUDE_PLUGIN_ROOT}/resources/factory_boy.md`.

**`claude_plugins/django-stack/resources/factory_boy.md`**, new `### Factory cross-app direction`
subsection directly after `### SubFactory` (before `### RelatedFactory`):

- A factory module imports another app's factory at module scope only in the direction the runtime
  dependency already runs. An optional or feature app's factories may import a core app's
  factories directly. A core app's factory never imports an optional app's, in either form.
- Where two peer factories need each other, use the dotted-string form:
  `factory.SubFactory("myapp.factories.OtherFactory")`, the full import path ending in the class
  name. `RelatedFactory` takes the same form (point at the existing `RelatedFactory` example, which
  already uses it). factory_boy resolves the string at first use, so neither module needs the other
  at load time.
- The string form only breaks import cycles. It does not change which app depends on which, and it
  does not make a factory safe to use when its target app is not installed. The `INSTALLED_APPS`
  guard does that, and it belongs in the test file or conftest that imports an optional app's
  factory, never in the factory module. `factories.py` files import freely; the caller carries the
  guard. Cross-link "Collection safety for optional apps" in `testing.md`.
