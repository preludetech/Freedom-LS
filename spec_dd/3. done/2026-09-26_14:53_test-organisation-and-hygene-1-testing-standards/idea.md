# The testing standard: file layout, cross-app imports, conftest/fixture/factory layering

Spec 1 of 15 in the Test organisation and hygiene effort. Read the "Test organisation and hygiene"
section of `spec_dd/1. next/roadmap.md` first: it holds the build order, what this spec depends on
and may run beside, the decisions already taken and the assumptions every idea in the effort makes.

## What

Write the two hygiene rules, and the conftest/fixture/factory layering that goes with them, into
`ds:testing`: `claude_plugins/django-stack/skills/testing/SKILL.md`,
`claude_plugins/django-stack/resources/testing.md` and `resources/factory_boy.md`. Give
`fls-dev:testing` (`claude_plugins/fls-dev/skills/testing/SKILL.md`) a pointer at those rules plus
the FLS instances of each.

This spec writes the standard only. It changes no test code anywhere in the repo, adds no
pre-commit or CI check, and touches no SDD command. Every downstream spec cites this one.

## Why

`ds:testing` says only "Test files: `<app>/tests/test_<module>.py`". It says nothing about
mirroring an app's subpackages and nothing about cross-app test dependencies. It has no guidance on
conftest, fixture placement or fixture scope, and its "Collection safety for optional apps" example
uses a raw `INSTALLED_APPS` string check the codebase has already replaced. The workflow wiring,
the enforcement checks and twelve cleanup specs all need one correct source of truth to cite. This
spec writes it, and runs first so nothing downstream reopens it.

## Where each part goes

The three `django-stack` files are generic. They name no FLS app and use `myproject`/`myapp`
placeholders throughout, and they keep doing so. Every rule below goes into `ds:testing` with a
generic example. Every real FLS path cited below goes into `fls-dev:testing` as that rule's
worked instance, never into a `django-stack` file.

In `resources/testing.md` the new material becomes its own section, placed after "Creating Test
Data" and before "Test Patterns". It gets subsections for conftest vs. plain module, fixture
placement, scope, the thin-wrapper rule and stub models. "Creating Test Data" stays about calling
factories. `SKILL.md`'s key rules link to the new section by name, as they already do for
"Collection safety for optional apps". The cross-app factory rule goes in `resources/factory_boy.md`
next to its existing `SubFactory` section.

## What is settled

**Rule 1. Mirroring.** State the convention the repo already uses almost everywhere:
`<app>/<module>.py` → `<app>/tests/test_<module>.py`. That means a flat `tests/` package inside the
app with one test file per production module. It is not a top-level mirrored tree and not a
colocated `foo_test.py`. A subpackage is mirrored as a test subdirectory:
`<app>/templatetags/content_tags.py` → `<app>/tests/templatetags/test_content_tags.py`, and
`<app>/management/commands/foo.py` → `<app>/tests/management/commands/test_foo.py`. No FLS app
does this today; the cleanup specs move those tests. Browser tests get one extra hop:
`<app>/tests/playwright/test_<thing>.py`. A helper or URLconf module used only by an app's tests
lives alongside those tests, never in `conftest.py`. The FLS instances are
`panel_framework/tests/{root_urls.py,stub_panels.py}`, `health/tests/root_urls.py` and
`reports/tests/{gather_input_builders.py,report_data_builders.py}`.

Some test files check a cross-cutting property rather than one module's behaviour: an import-order
invariant, migration state, settings resolution, or a content or vendored-asset regression. These
have no module to mirror. They are legitimate. Group them in a clearly named test subpackage (e.g.
`tests/demo_content/`) so they are not mistaken for unit tests that lost their module. The FLS
instances are `form_engine/tests/test_import_independence.py` and `content_engine`'s
`test_demo_content_*.py` and `test_katex_vendor_assets.py`. Spec 10 decides where the
`content_engine` files end up.

**Rule 2. Dependency direction.** An app's tests import only apps that the app depends on at
runtime. `docs/app_structure.md`'s dependency table (its "Runtime deps" and "Test-only deps"
columns, generated by `generate_app_map.py`) is the source of truth for what an app depends on
and where rule 2 is violated today. The generator reads Python imports only, so it misses two
kinds of real dependency. The standard states both in prose, and spec 3 decides how the check
learns them.

- A dependency expressed as a dotted string is a runtime dependency on the app that owns the
  target. That covers a model relation declared by label (`"content_engine.Course"`,
  `settings.AUTH_USER_MODEL`) and a settings-registered dotted path (a context processor,
  middleware or backend). `base` depends on `learner_management` this way: `TEMPLATES` registers
  `learner_management.context_processors.can_access_educator_interface`, and `base`'s header
  template reads it.
- The user is framework-level. Every request carries one, so any app's tests may use `accounts`'
  `UserFactory`.

A test that spans several apps belongs in the lowest app that depends on every app it touches,
not the app whose behaviour happens to be exercised first.

**Deciding an allowed exception.** The standard answers every case with one test, not a fixed
list. Is the "wrong" import intrinsic to what's being tested, meaning the thing under test
cannot exist without a real row from the other app? Or is it standing in for something a local
stub or fixture could provide? An intrinsic case gets a one-line comment at the import saying
why, and no code change.

**Granting permissions in tests.** When an app's code checks permissions through the
authorisation layer's standard API, its tests grant exactly the permission the code checks. They
do not go through a higher-level layer that the app does not depend on. In FLS that means
`guardian.shortcuts.assign_perm(codename, user, obj)`, not `role_based_permissions`'
`assign_object_role`. The role layer is transparent at check time: its README says roles
decide what permissions a user should have, and guardian enforces them. `reports`,
`educator_interface`, `learner_management`, `base` and `organisations` check only
`has_perm`/`get_objects_for_user`, so their `assign_object_role` calls are stand-ins, not
intrinsic. `reports/tests/test_admin.py` already uses `assign_perm` next to them. Whether a role
maps to the right permissions is `role_based_permissions`' own concern, tested in its own suite.
Specs 5, 8, 11 and 15 apply this. `research_role_grants_in_tests.md` has the per-app trace. It
also covers two cases those specs need: `organisations`' single role test belongs in
`role_based_permissions`' suite, and `learner_interface`'s `clear_caches` import is dead code.

**conftest.py vs. plain module.** `conftest.py` holds only `@pytest.fixture` functions plus
private, underscore-prefixed helpers that only those fixtures call. A plain function that test
files import by hand belongs in a plain module alongside the app's tests (e.g. `helpers.py`),
never in `conftest.py`. pytest does not discover plain conftest functions, so they still need an
explicit import, which defeats the reason for putting them there. pytest's maintainers discourage
importing from conftest (pytest issue #13148). A plain helper may stay in `conftest.py` only when
more than one test file in the app needs it **and** a comment at its definition says why. The
FLS instances go in `fls-dev:testing`. `accounts/tests/conftest.py` (two fixtures plus the private
`_seed_default_legal_docs`) is the pattern to follow. `learner_interface/tests/conftest.py`
(plain functions for manual import, plus a `reverse_url` re-export from the root conftest) is the
pattern to avoid. `mail/tests/conftest.py` is the justified exception: its docstring says the
helpers are public because serialisation, the worker send and the backend are all tested against
the same message shape.

**Fixture placement.** Put a fixture in the shallowest directory whose conftest reaches every
consumer. The mechanism behind this is pytest's own: conftest files are collected by walking up
from the test, and the nearest definition wins. The project root `conftest.py` holds project-wide
fixtures only, either autouse or opted into from many apps. An app's `tests/conftest.py` holds
fixtures used by more than one test file in that app. A fixture used by only one test file stays
in that file. FLS instances in `freedom_ls/conftest.py`: the autouse `_disable_force_site_name`,
`_disable_preview_overrides` and `_clear_course_access_backend_cache`, and the opt-in
`mock_site_context`.

**Fixture scope and idempotent reset.** Default to function scope. Widen to module or session
scope only for setup that profiling shows is expensive, never to save typing. A session- or
module-scoped fixture never hands back mutable state that a test then mutates. That is an
isolation bug, and `pytest-randomly` exposes it: it reorders tests and reseeds factory_boy and
Faker for each test. Where cost does justify a wider scope, build the expensive read-only part at
that scope. Reset or verify the per-test mutable part at function scope, idempotently
(`get_or_create`, an explicit cache clear). Rows created at session scope do not survive a
`transaction=True` test, which flushes the database. The FLS worked example, quoted near-verbatim
rather than invented, is `panel_framework/tests/conftest.py`. `_panel_test_tables` is autouse,
session-scoped and wrapped in `django_db_blocker.unblock()`. It pairs with `_panel_test_permissions`,
which is autouse and function-scoped, calls `ContentType.objects.clear_cache()` plus
`get_or_create`, and has a docstring explaining why function scope is required.

**The thin-wrapper rule, tightened.** The existing line in `resources/testing.md` ("Avoid creating
fixtures that are thin wrappers around factories. Rather just use the factories") stays, and now
defines "thin". A fixture whose entire body is one factory call with fixed kwargs is thin: delete
it and call the factory in the test. A fixture that composes several factory calls, adds
relationship logic no single factory expresses, or builds on another fixture is not thin. That is
the correct use of a fixture. FLS instances in the root conftest: `course_with_topic` (two factory
calls plus `.items.create(...)`) and `staff_client` (builds on `mock_site_context` and
`logged_in_client`).

**Factory cross-app direction.** A factory module imports another app's factory at module scope
only in the direction the runtime dependency already runs. An optional or feature app's factories
may import a core app's factories directly. A core app's factory never imports an optional app's.
Where two factories need each other, use the dotted-string form,
`factory.SubFactory("myapp.factories.OtherFactory")` (the full import path ending in the class
name; `RelatedFactory` takes the same form). factory_boy resolves the string at first use, so
neither module needs the other at load time. The string form only breaks import cycles. It does
not make a factory safe to use when its target app is not installed. The `INSTALLED_APPS` guard
does that, and it belongs in the test file or conftest that imports an optional app's factory,
never in the factory module. `factories.py` files import freely; the caller carries the guard. No
FLS factory breaks the direction rule today, and none uses the string form yet, so this is new
guidance rather than a description of existing code.

**Stub-model technique.** When a foundational app's tests need "some object with an assignable
role" or "any site-aware model" to prove genericity, define a tiny test-only model in that app's
own `conftest.py`. Give it an explicit `Meta.app_label`, create its table with
`connection.schema_editor()`, and never give it a `factory_boy` factory. A plain underscore helper
stands in for the factory. This fixes a foundational app's tests reaching for a real downstream
model. Name `django.test.utils.isolate_apps` (and pytest-django's `django_isolate_apps` marker) as
the lighter tool when a test needs only a model class and no database rows. It does not create
tables, so it does not replace the stub-model technique. The FLS reference implementation is
`panel_framework/tests/conftest.py`: `StubModel`, `StubChild`, `StubProtectedChild` and
`StubGrandchild` (whose docstring says why it exists), with `_make_stub`, `_make_stub_child` and
`_make_stub_protected_child`. `site_aware_models` and `role_based_permissions` need this
technique; applying it is spec 5's job.

**Collection-safety example, corrected.** The "Collection safety for optional apps" examples in
`SKILL.md` and `resources/testing.md` (the guard and the colocated `collect_ignore_glob` conftest
alike) show `if "myproject.optional_feature" not in settings.INSTALLED_APPS:`. All of them change
to `apps.is_installed(...)`, which also recognises an app installed by its `AppConfig` path.
`fls-dev:testing`'s `course_applications` example changes to the helper FLS already uses in
`course_applications/tests/conftest.py`: `from freedom_ls.tests.app_guards import
app_not_installed` and then `app_not_installed("freedom_ls.course_applications")`.

**Named exceptions.** Apart from `mail/tests/conftest.py`, `fls-dev:testing` names one more:
`contrib/conformance/`. Its root-level `test_*.py` files are both collected tests and importable
probes, which `tests/test_conformance_meta.py` imports under aliases. It looks like a mirroring
violation but is deliberate, so the callout points readers at the module docstrings. Every other
case the layout audit found is decided by the rules above. Naming those cases would duplicate the
cleanup specs.

## Out of scope

- Any change to test code anywhere in the repo (specs 4 to 15), including the per-app findings in
  `research_role_grants_in_tests.md`.
- The boy-scout cleanup step and its "worth flagging" guidance text (spec 2).
- Pre-commit/CI enforcement of either rule, the import-linter contracts, the mirroring script, the
  violation baseline, and teaching the check the string-reference edges and the `UserFactory`
  allowance (spec 3).
- Moving `SiteFactory` into `site_aware_models`, and the fate of the Playwright wildcard re-export
  (spec 4).
