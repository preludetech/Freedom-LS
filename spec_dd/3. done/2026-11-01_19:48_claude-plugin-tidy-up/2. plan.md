# Plan: claude-plugin-tidy-up

Spec: `1. spec.md` in this directory. No `design.md` applies.

Nothing here touches a Django model, view, URL or template. Every slice edits markdown, shell,
JSON and two pytest files, so "the full test suite passing" means the checks each slice names plus
`uv run pytest tests/test_update_concrete_projects.py tests/test_compress_screenshots.py`.

## Conventions every slice follows

- **Moves are `git mv`.** `uv run git mv` is allow-listed. A moved file keeps its history; a
  copy-and-delete does not.
- **A move into a generic plugin and its genericising edits land in the same commit**, one commit
  per slice, so no commit holds a project value inside `claude_plugins/sdd`,
  `claude_plugins/django-stack` or `claude_plugins/productivity`.
- **`claude plugin validate --strict <plugin dir>`** runs for every plugin a slice touched, and for
  `claude_plugins/productivity` once it exists. A failure is fixed in the same slice.
- **`PLUGINS_ROOT` paths.** When a generic plugin names a script of its own, it writes the path the
  way `pre_step_rebase.md` Step 3 does: resolve `PLUGINS_ROOT` by the rule in `sdd`'s `init.md`,
  prefix `<PLUGINS_ROOT>/claude_plugins/<plugin>/…`, and write it as plain
  `claude_plugins/<plugin>/…` when the value is `.`, so it matches the project's allow entry.
- **The generic-plugin grep.** After every slice that adds or moves content into a generic plugin:

  ```
  grep -rn -E 'FreedomLS|FLS|freedom_ls|fls-dev|manage\.py|runserver|debug-branch-badge|factory_boy|qa_helpers|site-aware|\.claude/ds/|\.claude/fls-dev/|mcp__plugin_ds_playwright|[Ll]earner|[Cc]ohort|login_required|qa-screenshots|ruff|mypy|bandit|shellcheck' claude_plugins/sdd claude_plugins/django-stack claude_plugins/productivity
  ```

  Compare with the same grep on `origin/main` (`git grep -n -E '…' origin/main -- claude_plugins/sdd
  claude_plugins/django-stack`). Every new hit is fixed in the slice. The two known exceptions, both
  recorded in the file beside the line: `do_qa.md`'s Step 15 fallback for checklists written before
  the move, and `uv run --with pillow` in `compress_screenshots.sh`.
- **Skills to load.** `productivity:writing-for-agents` (before slice 1 lands, the project skill
  `writing-for-agents`) and its `SKILL-MECHANICS.md` for every new or rewritten skill, agent,
  command and README; `productivity:unslop` over every prose rewrite; `sdd:claude-code-authoring`
  when touching agent frontmatter (`skills:`, `memory`, `model`), command frontmatter
  (`allowed-tools`, `argument-hint`) or a plugin manifest; `ds:testing` and `fls-dev:testing` for
  the pytest edits in slices 8 and 9. No MCP server is needed by any slice.
- **Protected comments.** `TODO` and `@claude` comments are never deleted. Content that tells an
  implementer to keep something stays.
- **Commit messages** name the slice's behaviour. The `[batch <n>]` prefix is the one marker they
  carry: `implement_plan.md` mandates it, and slice 23 finds the tightening base by it.

> **Assumed default:** slice 1 stays as one slice (manifest, moves, launcher and settings wiring,
> README, init, launcher resource). Why: every file in it is short, and the plugin's own init and
> README are its contract, not a widening. To change: split README, `init.md` and
> `launcher_editing.md` into a slice 1b before slice 2.

  ```bash
  base_commit=$(git rev-list -n1 --grep='^\[batch 10\]' HEAD)
  [ -n "$base_commit" ] || { echo "no [batch 10] commit found" >&2; exit 1; }
  TIGHTEN_BASE=$(git rev-parse "${base_commit}^")
  for dir in claude_plugins/productivity claude_plugins/sdd claude_plugins/django-stack \
             claude_plugins/fls-dev claude_plugins/fls-content .claude/skills/brand-guidelines; do
    before=$(git ls-tree -r --name-only "$TIGHTEN_BASE" -- "$dir" | grep '\.md$' \
             | while read -r f; do git show "$TIGHTEN_BASE:$f"; done | wc -w)
    after=$(find "$dir" -name '*.md' -print0 | xargs -0 cat | wc -w)
    echo "| $dir | $before | $after |"
  done
  ```
