## 1. Moodle (random question type, quiz start)

- **Where the draw happens.** `quiz_start_new_attempt()` in `mod/quiz/locallib.php` **[verified]** loads fixed slots first, then resolves each random slot in a second pass with `$randomloader = new \core_question\local\bank\random_question_loader($qubaids, $usedquestionids)` and `$questionid = $randomloader->get_next_filtered_question_id($filters)`. `$qubaids` is the user's earlier attempts, so the loader can prefer questions not seen on previous attempts. The loader internals were not retrievable, so "avoid repeats across retakes" is **[doc]** only.
- **Pool too small.** If the loader returns `null`, the function throws `notenoughrandomquestions` **[verified]**. So Moodle fails at attempt start, not at authoring time. There is no validation at slot creation beyond the editor UI showing the available count **[doc]**.
- **Per-slot, not per-N.** A Moodle random slot draws one question; "draw 10" is 10 random slots with the same filter. Distinctness comes from excluding already-chosen ids. The legacy `qtype_random::choose_other_question($questiondata, $excludedquestions, $allowshuffle, $forcequestionid)` does `shuffle($available)`, optionally moves a forced id to the front, and takes the first id not in `$excludedquestions` **[verified, MOODLE_405_STABLE questiontype.php]**. Eligible set: `get_available_questions_from_category`, with `qtype NOT IN (excluded)` where types with `!is_usable_by_random()` are excluded (descriptions, essays and other non-auto-gradable types) **[verified]**.
- **Selection storage.** Resolved questions are added to the question usage by `$quba->add_question($question, $maxmark[$slot])` then `$quba->start_all_questions(...)` **[verified]**; the usage is the stored served paper (one `question_attempts` row per slot, holding the real question id), written once at attempt start. Resume reads those rows; nothing redraws. The legacy `_realquestionid` step-data detail in the earlier research is the pre-4.x mechanism **[doc]**. Pattern to copy: resolve everything in one pass at attempt start, write rows, never resolve again.
- **Max score fixed.** `$maxmark[$slot]` is read from the slot, not from the drawn question, and passed to `add_question` **[verified]**. This is how a draw keeps a common denominator: the slot carries the mark, the drawn question does not.
- **Shuffle is separate from draw.** Shuffling happens when the attempt `layout` is built, by `shuffle($questionsinthissection)` for sections with `shufflequestions`, after questions are chosen; the layout is stored as a comma-separated slot list on the attempt **[verified]**. This matches the idea's "order follows the shuffle setting".
- **Stimulus/group.** Moodle random draws are single questions; a multi-part stimulus is not drawn whole by the random type. Descriptions cannot be drawn at all (excluded type) **[verified]**. No Moodle precedent for "draw a group whole".
- Sources: https://raw.githubusercontent.com/moodle/moodle/MOODLE_405_STABLE/mod/quiz/locallib.php , https://raw.githubusercontent.com/moodle/moodle/MOODLE_405_STABLE/question/type/random/questiontype.php , https://docs.moodle.org/502/en/Random_question_type , https://docs.moodle.org/dev/Random_question_type , https://moodle.org/mod/forum/discuss.php?d=257898 (retakes returning identical questions when "each attempt builds on last" is set) , https://tracker-old.moodle.org/browse/MDL-42598 (variant seed derived from user id, question and attempt number; a seeded approach that produced duplicates across duplicated quizzes).

## 2. Open edX `library_content` / `ItemBankMixin`

- **Fields.** `max_count` (help: "Enter the number of components to display to each student. Set it to -1 to display all components.") and `selected = List(default=[], scope=Scope.user_state)` holding `(block_type, block_id)` tuples **[verified, xmodule/item_bank_block.py]**. So the draw is persisted per learner, once, as the list of ids, not as a seed.
- **Algorithm.** `make_selection(selected, children, max_count, ...)` **[verified]**: take the already-selected set; drop ids no longer valid (`invalid`); if `len(selected) > max_count` trim the surplus (`overlimit`); then `num_to_add = max_count - len(selected)`, `num_to_add = min(len(pool), num_to_add)`, sample from the not-yet-selected pool, then `random.shuffle(selected)`. Returns `selected, invalid, overlimit, added`. `selected_children()` writes `self.selected = selected` only when something changed ("Save our selections to the user state, to ensure consistency").
- **Consequence for FLS.** Open edX's draw is lazy and self-healing (top-up when `max_count` rises or a child disappears). It persists across the whole course run, with an optional `allow_resetting_children` "Reset Problems" that clears `selected` to redraw **[verified]**. FLS wants the opposite: one draw per attempt, frozen, no top-up. If content is edited mid-attempt, Open edX would silently change the served set; the FLS served paper must not. This supports persisting the full id list and having later readers read it, never re-run selection.
- **Validation.** Warnings, not errors **[verified]**: `max_count` not positive and not -1 is an error ("Please specify a positive number of problems, or specify -1 to show all problems"); `0 < len(children) < max_count` gives a warning ("... configured to fetch {count} problems, but there are only {actual} matching problems"). Runtime clamps via `min(len(pool), num_to_add)`. FLS is stricter (reject N > items at validation), which is the safer choice: it keeps `max_score` constant, whereas Open edX lets a short pool silently shrink the count.
- **Scoring.** Each child is graded as its own block; no fixed max is enforced. The course grade aggregates the children actually shown **[doc]**.
- **Groups/stimulus.** Children are whole blocks (a vertical can contain a stimulus and several problems), so Open edX draws a unit of any size whole. It does not enforce equal sizes, so scores per draw can differ. FLS's equal-size rule is a deliberate fix for exactly that gap.
- Sources: https://raw.githubusercontent.com/openedx/edx-platform/master/xmodule/item_bank_block.py , https://raw.githubusercontent.com/openedx/edx-platform/master/xmodule/library_content_block.py

## 3. QTI `selection` / `ordering` (spec and the qti-sdk implementation TAO uses)

- **Semantics.** `<selection select="N" withReplacement="false"/>` on an `assessmentSection`; `required="true"` on a child forces inclusion; `<ordering shuffle="true"/>` shuffles the selected children **[doc]** (QTI 2.2 impl guide example rtest12: "we select 2 children using the selection element, but assessmentSection B1 is required" **[verified]**). Children can be items or nested sections, so QTI draws sections (groups) whole by construction **[verified by example; the formal Selection class text was not reached in the 630k-char page]**.
- **Reference algorithm (oat-sa/qti-sdk `BasicSelection::select`)** **[verified]**:
  - `if ($select > $childCount && $withReplacement !== true) { $select = $childCount; }` so an oversized N is clamped, not an error.
  - Required children are taken first; without replacement they leave the bag and reduce `$select`.
  - Remaining picks: `mt_rand(0, $bagCount - 1)`; without replacement the picked entry is `unset` and the bag re-indexed.
  - Output preserves the **original order**, repeating a child per selection count; ordering/shuffle is applied by a separate step.
  - A section with no selection returns all children unchanged (opt-in default).
- **Selection persistence.** The qti-sdk session manager wraps each section's selected and ordered child routes in a `SelectableRoute`, pushes it on `$routeStack`, and builds the final route stored in the test session **[verified, one-line summary]**. The *route* (resolved list) is the persisted object; the engine never reselects on resume. Same principle as Moodle and Open edX.
- **TAO.** Built on qti-sdk, so the above is TAO's behaviour **[inferred]**. TAO-specific storage (its own session serialisation) was not reachable.
- **Scoring max.** QTI computes outcome from the resolved route; there is no fixed max, so equal-weight children are the author's responsibility. QTI offers no equal-size guard for nested groups.
- Sources: https://www.imsglobal.org/question/qtiv2p2/imsqti_v2p2_impl.html , https://www.imsglobal.org/question/qtiv2p2/QTIv2p2-ASI-InformationModelv1p0/imsqtiv2p2_asi_v1p0_InfoModelv1p0.html (sections 5.96 Selection, 5.96.1 select, 5.96.2 withReplacement) , https://github.com/oat-sa/qti-sdk/blob/master/src/qtism/runtime/tests/BasicSelection.php

## 4. ILIAS random tests

- Random tests are built from "question sets" each pointing at a pool with either a fixed selection or random selection by criteria; several pools per test; ILIAS stores the drawn questions per participant and pass **[doc, no source read]**. A Feature Wiki page says question sets in a random test can no longer be synchronised once participant data exists, "to be able to compare the test results", and a related proposal would lock changes once participants exist **[doc]**. A "least used questions" draw (prefer questions the user has not had in a previous pass) is only a proposal **[doc]**. When the source pool is removed, the test config freezes but stays takeable **[doc]**.
- Takeaway: ILIAS has the same weighted-per-source design as the idea (one draw rule per source, each with its own count, giving subject-weighted papers), and arrives at the same rule: the resolved draw is stored per attempt and edits to the source must not alter attempts already made. Table names (`tst_test_rnd_qst` etc.) could not be confirmed.
- Sources: https://docu.ilias.de/go/wiki/wpage_5279_1357 , https://docu.ilias.de/go/wiki/wpage_1373_1357 , https://docu.ilias.de/go/wiki/wpage_4319_1357

## 6. Patterns that carry to FLS (design-relevant)

1. **Resolve once, in one pass, at attempt start, persist the resolved id list.** Moodle (usage rows), qti-sdk (route), Open edX (`selected`) all do it. None reseed to reproduce; the earlier doc's seed idea (idea.md "with the attempt's seed") is workable only if the stored list is still the source of truth read by every reader. Recommend the served paper holds ids; the seed is incidental.
2. **Draw before shuffle.** Moodle builds layout after choosing; QTI separates `selection` from `ordering`. Drawn items then follow the page shuffle.
3. **Draw units may be sections.** QTI selects nested sections whole; Open edX selects a vertical whole. Neither guards equal size, so FLS's validator-enforced equal-size rule is stricter than any precedent and is what keeps `max_score` fixed. The Moodle precedent for a fixed max is "max mark lives on the slot, not on the drawn question".
4. **N versus pool size.** Moodle errors at attempt start (`notenoughrandomquestions`); qti-sdk clamps silently; Open edX warns in the editor and clamps. None rejects at authoring time with a hard error. FLS's hard validation `1 <= N <= items` is the strongest option and removes the attempt-time failure mode. Equal N and item count is accepted by all three.
5. **Edits after attempts exist.** ILIAS freezes sets once participant data exists; Open edX reconciles (`invalid`/`overlimit`/`added`). FLS freezes the served paper, but should state what happens to an in-progress attempt when the content-save command removes a drawn question (outside this research, flag for the spec).
6. **Without replacement is universal.** `withReplacement` exists in QTI; every LMS uses false. FLS should not offer it.
7. **Retake freshness.** Only Moodle's loader (and a proposed ILIAS option) prefers questions not seen before; pure uniform redraw, as in the idea, can repeat questions across retakes, which is acceptable and matches Canvas/Open edX. If SACAA needs "no repeats on retake", that is a separate rule (out of scope in idea.md).
