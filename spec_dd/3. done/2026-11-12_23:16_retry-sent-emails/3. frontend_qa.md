# Frontend QA: retry sent emails

The only screens this feature adds are in the Django admin: the `OutboundEmail` changelist, its
detail page, and the Resend confirmation page. Everything else is checked through those screens.

## 0. Setup

- Start the server: `uv run python manage.py runserver $PORT`. Base URL: `http://127.0.0.1:$PORT`.
- Run `uv run python manage.py migrate` first if the server reports unapplied migrations.
- Superuser login: `demodev@email.com`, password `demodev@email.com`, at
  `http://127.0.0.1:$PORT/accounts/login/`.
- Dev sends mail through `QueuedEmailBackend` with the inline task backend, so a send is attempted
  inside the request. Dev's upstream is Mailpit on `localhost`. Check whether Mailpit is up by
  opening `http://localhost:8025`. Several tests below have two acceptable outcomes, one for
  Mailpit up and one for Mailpit down. Record which case applied.
- Admin changelist: `http://127.0.0.1:$PORT/admin/freedom_ls_mail/outboundemail/`.

### Data to create before testing

Create these with `OutboundEmailFactory` (`freedom_ls/mail/factories.py`) through
`uv run python manage.py shell`. Give each a subject that names its state so it is easy to find,
and a payload whose body contains the string `QA-SECRET-BODY-TOKEN`.

| Name | State |
| --- | --- |
| Row A | `dead_letter`, `attempt_count` 6, payload present, `last_error` set, `last_attempt_at` an hour ago |
| Row B | `permanent_failure`, payload present, `last_error` set to a 550 error |
| Row C | `dead_letter`, payload `{}`, `scrubbed_at` set |
| Row D | `sent`, payload `{}`, `sent_at` and `scrubbed_at` set |
| Row E | `sending`, `last_attempt_at` one minute ago |
| Row F | `failed`, `attempt_count` 2, `next_attempt_at` 30 minutes ago |
| Row G | `sent`, `created_at`, `last_attempt_at`, `sent_at` and `scrubbed_at` 40 days ago |
| Row H | `permanent_failure`, payload present, recipients `["search-me@example.test"]`, subject `Findable subject QA` |

Also create a staff user who is not a superuser: `staff-qa@example.test`, `is_staff=True`,
`is_superuser=False`, password equal to the email, with a verified primary email address.

## 1. The changelist shows every row and no body

1. Log in as the superuser and open the admin index. Expect a "Mail" section with an entry for
   outbound emails.
2. Open the changelist. Expect rows A to H, with columns for recipients, subject, status, attempt
   count, next attempt, last attempt and last error.
3. Expect a long `last_error` to be cut short in the list.
4. Expect no "Add" button.
5. Search the page text for `QA-SECRET-BODY-TOKEN`. Expect no match.
6. Use the status filter to show only `dead_letter`. Expect rows A and C only.
7. Use the `created_at` filter. Expect it to narrow the list (row G drops out of "Past 7 days").
8. Search `search-me@example.test`. Expect row H. Search `Findable subject QA`. Expect row H.
   Copy row H's message id from its detail page and search for it. Expect row H.

## 2. The detail page is read-only and never shows the body

1. Open row A. Expect message id, recipients, subject, status, attempt count, next attempt, last
   attempt, last error, created, sent and scrubbed fields, all read-only.
2. Expect no Save button and no Delete button.
3. Search the page text and the page source for `QA-SECRET-BODY-TOKEN`. Expect no match. Expect
   no field named payload.
4. Expect the body line to say the body is still stored, not that it was removed.
5. Open row C. Expect the notice that the body was removed and that sending again means repeating
   the original action, such as a new password reset.
6. Open `.../outboundemail/add/` directly. Expect a 403.
7. Open row A's `.../delete/` URL directly. Expect a 403.

## 3. Resend from the detail page

1. Open row A. Expect a Resend button.
2. Click it. Expect a confirmation page titled "Resend email" at
   `.../outboundemail/<row A id>/resend/` that names row A by recipients and subject, with a Resend button and a Cancel link. Expect no body text on the page.
3. Without submitting, go back to row A's detail page and reload. Expect status still
   `dead_letter` and attempt count still 6: opening the confirmation page changed nothing.
4. Open the confirmation page again and click Cancel. Expect to land on row A's detail page, still
   `dead_letter`.
5. Open the confirmation page again and click Resend. Expect a redirect to row A with a success
   message saying one email was queued.
6. Reload row A. Expect one of:
   - Mailpit up: status `sent`, attempt count 1, sent time set, body-removed notice shown, and
     the message in the Mailpit inbox at `http://localhost:8025`.
   - Mailpit down: status `failed`, attempt count 1, a next attempt time about a minute ahead, and
     a connection error in last error.
   In both cases the attempt count is 1, not 7: the resend started a new ladder.
7. Open row A's history (the admin History link). Expect one entry recording the resend.
8. Use the browser Back button to return to the confirmation page and submit it again. Expect a
   warning that nothing was queued, with the reason (already sent, or in flight), and no second
   message in Mailpit.

## 4. Resend is offered only where it can work

1. Open row C (scrubbed). Expect no Resend button.
2. Open row D (`sent`). Expect no Resend button.
3. Open row E (`sending`). Expect no Resend button.
4. Open `.../outboundemail/<row D id>/resend/` directly. Expect a page saying the email cannot
   be resent because it was already sent, with a Back link and no form.
5. Open `.../outboundemail/<row C id>/resend/` directly. Expect the same page with the reason
   that the body was removed, and no form.
6. Open `.../outboundemail/not-a-uuid/resend/`. Expect a 404, not a 500.
7. Open `.../outboundemail/<a random UUID>/resend/`. Expect a 404.

## 5. Bulk resend with a mixed selection

1. On the changelist, select rows B, C, D and E.
2. Choose "Resend selected emails" and run it.
3. Expect a success message that one email was queued (row B).
4. Expect a warning that three were skipped, naming the reasons: body removed (C), already sent
   (D), in flight (E).
5. Open row B. Expect attempt count 1 and status `sent` (Mailpit up) or `failed` (Mailpit down).
6. Open rows C, D and E. Expect each unchanged.
7. Select only row D, run the action. Expect a warning and no success message.

## 6. A staff user who is not a superuser sees nothing

1. Log out. Log in as `staff-qa@example.test`.
2. Open the admin index. Expect no Mail section.
3. Open the changelist URL directly. Expect a 403.
4. Open row B's detail URL directly. Expect a 403.
5. Open `.../outboundemail/<row H id>/resend/` directly. Expect a 403.
6. Log out. Open the changelist URL. Expect a redirect to the admin login.
7. Log back in as the superuser and open row H. Expect it unchanged (`permanent_failure`).

## 7. A real send writes a row

1. Log out. Open `http://127.0.0.1:$PORT/accounts/password/reset/` and request a reset for
   `demodev@email.com`.
2. Mailpit up: expect the usual "we have sent you an email" page. Log in as the superuser, open
   the changelist, and expect a new newest row addressed to `demodev@email.com` with status `sent`,
   attempt count 1 and the body-removed notice. Expect exactly one new message in Mailpit, and its
   reset link to open the password change form (the link was not broken by line wrapping).
3. Mailpit down: expect the request to fail the same way it did before this feature (the send is
   inline in dev). Log in as the superuser and expect a new row with status `failed`, attempt
   count 1, a next attempt time ahead and a connection error in last error. Expect no row stuck in
   `pending`.
4. Open the new row's detail page. Expect no reset link and no body text anywhere on it.

## 8. Housekeeping moves rows, seen through the admin

1. Note row F (`failed`, due 30 minutes ago) and row G (`sent`, last attempted 40 days ago).
2. Run `uv run python manage.py fls_run_housekeeping`.
3. Expect the command output to include a note that one outbound email was requeued.
4. Reload the changelist. Expect row G to be gone.
5. Open row F. Expect attempt count 3, and status `sent` (Mailpit up) or `failed` with a new next
   attempt time (Mailpit down).
6. Open row E (`sending`, one minute old). Expect it unchanged: it is inside the stuck window.
7. Run `uv run python manage.py fls_run_housekeeping --help`. Expect the help text to mention
   outgoing email.

## 9. Layout at three viewports

Check the changelist, row B's detail page, and the confirmation page for row H at 1920x1080,
375x812 and 768x1024.

1. Expect no horizontal page scroll outside the changelist table's own scroll area.
2. Expect the Resend button on the detail page to be reachable at each size.
3. Expect the confirmation page's Resend and Cancel controls to be visible without overlapping.
4. Expect no console errors on any of the three pages.

## 10. Nothing else moved

1. Open the admin index as the superuser. Expect every other admin section to still be listed.
2. Open the webhook deliveries changelist. Expect it to load, with its retry action still listed.
3. Open the API keys changelist and one key's detail page. Expect the revoke button and its
   confirmation page to work as before (open it, then Cancel).
4. Submit a course application that sends a claim email, on a demo course that takes applications,
   using a new email address. Mailpit up: expect the "check your email" outcome and a `sent` row in
   the changelist. Mailpit down: expect the page to say the email could not be sent, as it did
   before, and a `failed` row in the changelist.
