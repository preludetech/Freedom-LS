# Frontend QA: panel framework form actions accept file uploads

No host panel has a file field yet, so a real upload cannot be made in the dev app. The upload
round trip, "Uploading…" and the discard prompt for a chosen file are covered by the framework's
own browser tests. This QA checks what a person can see in the dev app:

- the new "File field" section on the component reference page;
- that existing dialog and inline forms look and behave as before;
- the request error message, which every panel form now shows when its request fails.

## Setup

1. Build the stylesheet: `npm run tailwind_build`.
2. Start the server on a free port: `uv run python manage.py runserver $PORT`. Base URL:
   `http://127.0.0.1:$PORT`.
3. Log in at `http://127.0.0.1:$PORT/accounts/login/` with the QA login from
   `.claude/sdd/config.md` (`## QA Login`). That user is staff, a site admin and an organisation
   admin of the dev organisation.
4. Open `http://127.0.0.1:$PORT/educator/` and note the organisation slug in the URL
   (`/educator/organisations/<slug>/...`).
5. Data, in that organisation. Ask the QA data helper for whatever is missing
   (`qa_create_educator_interface_seed` covers it):
   - one active cohort ("QA cohort A");
   - one learner with a first and last name.

Viewports: 1920 (desktop), 768 (tablet) and 375 (phone). "No sideways scroll" means
`document.documentElement.scrollWidth <= window.innerWidth` after layout settles.

Keep the browser console open for every test. A JavaScript error or a CSP-build Alpine error
shows there and nowhere else. Any console error is a failure.

### Making a request fail

Several tests need a form's POST to fail. Use the Playwright MCP's code tool to route the request
before submitting, and remove the route afterwards:

```js
// status 500 or 413; "**/__actions/**" matches every panel action URL
await page.route("**/__actions/**", (route) =>
    route.request().method() === "POST"
        ? route.fulfill({ status: 500, body: "<h1>Server Error</h1>" })
        : route.continue(),
);
// network failure instead: route.abort()
// afterwards: await page.unroute("**/__actions/**");
```

## Test 1: the "File field" section on the reference page

Go to `http://127.0.0.1:$PORT/panel-framework/components/` and scroll to "File field".

Expect:

1. Three examples, with wrapper ids `file-field-dialog`, `file-field-error` and
   `file-field-inline`.
2. Dialog example: the text `Current file:` followed by `first-aid-certificate.pdf`. No directory
   (`certificates/2026/`) appears anywhere, and the name is not a link.
3. Dialog example: a checkbox labelled `Remove`, then a native file input ("Choose file" or the
   browser's wording). The field's label is tied to the file input: clicking the label opens the
   file picker, not the checkbox.
4. Error example: an error summary saying one or more fields need fixing, and under the file
   field the message "Choose the file again. It is not kept when the form has errors." The file
   input is empty, and `Current file:` with the name is still shown.
5. Inline example: a file input with Save at the end of the row, and no `Remove` checkbox and no
   `Current file:` line.
6. Text in the dialog examples is the dialog's base size, not smaller than the field labels'
   neighbours in other dialogs.
7. At 1920, 768 and 375: no sideways scroll, and no example overflows its box.
8. No console error. The rest of the reference page renders as before (spot-check Notice and
   Callout, the sections either side).

Side effects to check:

9. Tick `Remove` in the dialog example, then choose a file in the same example. Nothing on the
   page breaks (the example is static; no request should succeed or be needed).
10. Inspect the dialog example's checkbox: its accessible name includes the file name
    (`Remove first-aid-certificate.pdf`).

## Test 2: the learner Name panel (inline form) is unchanged

Go to `/educator/organisations/<slug>/learners/`, open the learner, and open the Settings tab.

Expect:

1. The Name panel shows First name and Last name in one row with Save at the end, as before.
2. Change the first name and press Save. While the request runs the button is disabled and reads
   `Saving…` with a single ellipsis character. After it, the name is saved, the page heading
   updates, and focus returns to the first field.
3. Clear the first name and press Save (or enter a name longer than 200 characters). The error is
   one line under the row, with no box around it and no summary, and the input is marked invalid.
4. Inspect the `<form>`: it has no `enctype` and no `hx-encoding` attribute.
5. No visible gap or empty line has appeared in the panel compared with the cohort Name panel
   before this change (the hidden request error element takes no space).
6. At 375: no sideways scroll.

## Test 3: the cohort Name panel (inline form) is unchanged

Go to `/educator/organisations/<slug>/cohorts/`, open "QA cohort A", and open the Settings tab.
Repeat Test 2 steps 1 to 5 on the cohort's Name panel.

## Test 4: an existing dialog form is unchanged

Go to `/educator/organisations/<slug>/cohorts/` and press the button that creates a cohort.

Expect:

1. The dialog opens with its header, fields and footer as before, focus in the first field.
2. Inspect the `<form>`: no `enctype` and no `hx-encoding`.
3. Submit it empty. The error summary appears with the field count, focus moves to it, and each
   field shows its error. No "Choose the file again" message appears anywhere.
4. Type a name, then press Esc. The "Discard changes?" prompt shows. "Keep editing" returns to the
   form with the typed name.
5. Clear the name back to empty and press Esc. The dialog closes with no prompt.
6. Reopen, enter a valid name and press Save. The button is disabled and reads `Saving…` while the
   request runs, never `Uploading…`. The cohort is created.
7. At 375 the dialog is a bottom sheet as before, with no sideways scroll.

## Test 5: a failed request shows a message in a dialog form

On the cohorts list, open the create dialog and type a name.

1. Route the POST to answer 500 (see "Making a request fail") and press Save.
   Expect: the dialog stays open. A message reads "Your changes could not be saved. Try again."
   in error colour inside the dialog body. Focus is on the message. The typed name is still in
   the field. Save is enabled and reads `Save`. The server's error page is not shown anywhere.
2. Route the POST to answer 413 and press Save again.
   Expect: the message now reads "The file may be too large to upload. Choose a smaller file."
   Only one message is shown.
3. Route the POST to abort (network failure) and press Save.
   Expect: "Your changes could not be saved. Try again."
4. Remove the route and press Save.
   Expect: the message disappears as the request starts, the cohort is created and the dialog
   closes.
5. Reopen the create dialog. Expect: no message left over from before.
6. With a screen reader or the accessibility tree: the message has `role="alert"`.
7. Repeat step 1 at 375. The message wraps inside the sheet with no sideways scroll.

## Test 6: a failed request shows a message in an inline form

On the learner's Settings tab, change the first name.

1. Route the POST to answer 500 and press Save.
   Expect: "Your changes could not be saved. Try again." appears under the field row, in the same
   size as a field error. The changed name is still in the field. Save is enabled. The panel is
   not replaced by an error page.
2. Remove the route and press Save. Expect: the message goes, the name saves.

## Test 7: requests the message must leave alone

1. Lost access: on the learner's Settings tab, route the Name form's POST to answer 404 with a
   plain body, and press Save. Expect: the page reloads (the existing behaviour). No request
   error message appears.
2. Validation: submit the create-cohort dialog empty. Expect: the 422 error summary only, and no
   request error message.
3. A dialog whose select refreshes the dialog on change (for example "Add to cohort" on a
   learner's Cohorts panel, if the learner can join a cohort): route GET requests to
   `**/__actions/**` to answer 500 and change the select. Expect: no request error message
   appears in the form, and nothing else breaks. Remove the route.
4. Quick view: on the learners list, route the quick-view GET to answer 500 and open a row's
   quick view. Expect: the drawer's own error block with Retry, as before.
5. A server error that carries a toast: if any educator action answers a 4xx or 5xx with a toast
   (none is known), the toast shows and the form shows no second message. Skip if none is found,
   and say so in the report.

## Test 8: other submit buttons are unaffected

The button component gained a `data-loading-label` attribute on its loading span.

1. On a learner's page, open a confirm dialog (for example Deactivate, or remove from a cohort)
   and confirm. Expect: the confirm button shows its spinner and its own loading text while the
   request runs, as before.
2. Log in as a learner (or use the learner view of the QA user), open a course activity with a
   form and submit it. Expect: the submit button's loading state looks as before.
3. Inspect either button: the loading span carries `data-loading-label` equal to its visible
   loading text.
