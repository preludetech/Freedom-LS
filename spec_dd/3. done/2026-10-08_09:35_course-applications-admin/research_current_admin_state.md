# Research: current admin state for course applications and form progress

Scope: what exists today, so the spec knows what to build on. Facts only; "awkward/missing" items are inferred by reading the code, not by running the admin.

## 1. `freedom_ls/course_applications/`

- App config `CourseApplicationsConfig` (`apps.py`): label `freedom_ls_course_applications`, verbose_name "Course applications", `ready()` is a no-op.
- Files: `models.py`, `queries.py`, `views.py`, `urls.py`, `backends.py`, `factories.py`, templates (`check_your_answers.html`, `form_page.html`, `partials/dashboard_applications.html`, `application_status.html`, `apply.html`). **There is no `admin.py`.** `CourseApplication` is not registered anywhere in the admin; grepping `freedom_ls/` shows it referenced only by this app, `course_access/backends.py`, `learner_progress` and `qa_helpers` commands.
- Model `CourseApplication(SiteAwareModel)`: `user` FK (`related_name="course_applications"`), `course` FK to `freedom_ls_content_engine.Course` (`related_name="applications"`), `form_progress` OneToOne to `freedom_ls_form_engine.FormProgress` (null, `on_delete=RESTRICT`, `related_name="course_application"`), `created_at`, `updated_at`. Constraint `unique_application_per_site_user_course` on `(site, user, course)`. Property `is_submitted`: true when `form_progress is None` or `form_progress.completed_time` is set. There is **no `state` field**; draft versus submitted is derived from the sitting's `completed_time`. `__str__` is `CourseApplication(<user_id>, <course_id>)` (raw ids, not readable in admin lists).
- Model docstring says application review will later add `state` (FSMField), transitions, `submitted_at`/`decided_at`/`decided_by`, `view_application`/`change_application` permissions, `ApplicationNote`, `ApplicationStateTransition`, a signal, and a partial unique index. "Do not architect these away - leave this model standalone and additive."
- `queries.py`: `get_application_for_course(user=, course=)` and `get_active_applications(user)` (select_related course, form_progress). Both are applicant-side and take a request user; nothing queries applications across applicants.
- `views.py` is entirely applicant-side, all scoped to `user=request.user`: `apply`, `application_status`, `application_form_page`, `application_check_answers`. Creating an application via a form-bearing course creates the `FormProgress` (draft) immediately; submitting calls `form_progress.complete()` from `application_check_answers`.
- Reusable answer rendering: `application_check_answers` builds `sections` (one per `form.pages.all()`; `page_questions(page)` from `form_engine/queries.py`; `form_progress.existing_answers_dict(questions)` after `prefetch_related_objects([form_progress], "answers__selected_options", "answers__answer_file")`) and `check_your_answers.html` renders question (`rendered_question`), then in order: file (original filename, size, applicant download link `form_engine:own_question_answer_file`), else `text_answer|answer_display:question.type`, else selected option texts joined with " · ", else "Not answered". It is applicant-only and wired to applicant URLs; the template extends `_base.html`, not the admin shell. The page grouping + "Not answered" logic is the closest existing model for what the admin needs.
- `format_answer(question_type, text)` in `form_engine/typed_answers.py` is the shared helper (formats `date` and `time` via `django.utils.formats`; everything else, including number/email/url/phone, returns the raw string; unparseable values fall back to raw). Template filter `answer_display` (`form_engine/templatetags/form_engine_tags.py`) wraps it.
- No educator_interface or panel_framework view lists applications or renders a `FormProgress`'s answers (grep for `answer|application` in `freedom_ls/educator_interface` non-test code finds nothing). Application review in the educator interface is a separate unstarted effort (see section 4).

## 2. `freedom_ls/form_engine/admin.py` as it stands

Base classes: `SiteAwareModelAdmin` (from `site_aware_models/admin.py`; subclass of `unfold.admin.ModelAdmin`, `exclude = ["site"]`, loads `site_aware_models/css/admin.css`). Also `SuperuserOnlyAdmin` mixin (a plain mixin overriding `has_view/change/add/delete_permission` to return `request.user.is_superuser`); docstring says rights over course content are not rights over an applicant's sitting, answers and files, and that Django per-model permissions cannot express that.

Registered: `QuestionOption`, `FormContent`, `FormQuestion`, `FormPage`, `Form` (all `SiteAwareModelAdmin`, deletion blocked via `has_delete_permission -> False`), plus the three answer-side admins below. `FormAdmin.save_model` mints a slug. `FormQuestionAdmin` has an "Answer format" fieldset for `min`/`max`/`decimal_places`.

**`FormProgressAdmin(SuperuserOnlyAdmin, SiteAwareModelAdmin)`**
- `list_display`: `user`, `form`, `in_course` (course from reverse one-to-one `course_attempt`; `None` means "sat outside a course"), `start_time`, `last_updated_time`, `completed_time`, `is_complete` (boolean).
- Filters: `FormProgressCompletionFilter`, `form` autocomplete filter, completed/start range filters; `date_hierarchy = "completed_time"`; `search_fields = user__email, form__title`; `ordering = -start_time`; `list_select_related` includes `course_attempt__course_progress__course`.
- `readonly_fields = start_time, last_updated_time, completed_time, scores` (completed_time read-only because only `FormProgress.complete()` may finish a sitting: it scores and sends `form_attempt_completed`).
- Fieldsets: `(user, form)` and "Progress" (`start_time`, `last_updated_time`, `completed_time`, `scores`). `user` and `form` are editable on change (not readonly).
- Inline: `QuestionAnswerInline`.

**`QuestionAnswerInline(admin.TabularInline)`** - note: Django's `admin.TabularInline`, not `unfold.admin.TabularInline` (so it renders unthemed; `learner_progress/admin.py` uses `unfold.admin.TabularInline`). `fields = (question, selected_options, text_answer, updated_at)`; only `updated_at` is read-only, so answers are **editable** inline (question dropdown listing every `FormQuestion` on the site, M2M multi-select of every `QuestionOption`, raw `text_answer` textarea). `extra = 0`, no ordering declared (QuestionAnswer has no Meta ordering, so rows come back in DB order, not question order), no `select_related`, no `can_delete`/add controls overridden (add and delete are therefore live for superusers; the `QuestionAnswer.question` FK is `PROTECT`).

**`QuestionAnswerAdmin(SuperuserOnlyAdmin, SiteAwareModelAdmin)`**: `list_display = form_progress, question, answer_preview, updated_at`; `answer_preview` = `format_answer(question.type, text_answer)[:50]` if `text_answer`, else comma-joined selected option texts[:50], else "-". It issues per-row queries (`obj.question.type`, `selected_options.exists()`; `list_select_related` only covers `form_progress` and `question`; the data-field QA report recorded these as pre-existing). Filters `question__form_page__form`, `updated_at`; search on user email, question text, `text_answer`. Change form editable: `form_progress`, `question`, `selected_options`, `text_answer`.

**`QuestionAnswerFileAdmin(SuperuserOnlyAdmin, SiteAwareModelAdmin)`**: list `applicant`, `question` (first 50 chars), `original_filename`, `created_at`, `download`. `has_add_permission -> False`. `exclude = ["site", "file"]` (the `file` field is deliberately never rendered so no storage URL reaches the page). `readonly_fields = answer, original_filename, created_at, updated_at`. `download()` renders an `<a>` to `admin:freedom_ls_form_engine_questionanswerfile_download`; `get_urls()` adds `<path:object_id>/download/` wrapped in `admin_site.admin_view(question_answer_file_download_view)`. That view (`form_engine/views.py`, `question_answer_file_download_view`) raises `PermissionDenied` unless `request.user.is_superuser`, then `get_object_or_404(QuestionAnswerFile, pk=object_id)` and `stream_question_answer_file(answer_file)` (a `FileResponse`, attachment, nosniff per the done spec). `admin_view` alone only guarantees staff, which is why the explicit superuser check exists. The `file-scanning` roadmap item will add a quarantine gate to this same download route.

**Awkward / missing today when viewing a FormProgress** (inferred):
- Answers are an editable tabular inline in arbitrary DB order: not sorted by page and question order, no page grouping, no page titles.
- Unanswered questions are not shown at all (a blank answer stores no row; `save_answers` deletes the row when blank). An applicant who skipped an optional question is invisible, and the reviewer cannot tell "skipped" from "never reached" (`furthest_page_reached` exists on the model but is not displayed or in a fieldset).
- The question column is the `FormQuestion.__str__` (first 50 chars of the markdown question text), not rendered and not tied to a page.
- `selected_options` is a raw multi-select widget of every option on the site, not the chosen option texts; `text_answer` is a raw textarea showing the stored ISO string for `date`/`time` (no `format_answer`); `format_answer` only reformats date/time anyway.
- File answers: the inline shows no file at all (the file lives on `QuestionAnswer.answer_file`, a reverse one-to-one on `QuestionAnswerFile`; the inline does not mention it). The only route to a file is the separate `QuestionAnswerFile` changelist, so a reviewer cannot download an applicant's document from the sitting.
- `scores` is shown as raw JSON in a readonly field (no formatting for `QUIZ` `{"score","max_score"}` or `CATEGORY_VALUE_SUM` nested category dicts; `UNSCORED` forms leave it null, which is what application forms use).
- No link from a `FormProgress` to its `CourseApplication` (reverse one-to-one `course_application`), nor to the course (only the `in_course` column on the changelist, which reads `course_attempt`, not `course_application`; an application sitting has no `course_attempt`, so `in_course` shows the empty dash for application forms).
- `FormProgressAdmin` has no way to tell an application sitting from a quiz or survey sitting (no column, filter or fieldset row naming the application or course).
- Applicant identity shows only as `user.__str__`/email; no name/other details panel.
- Editing hazards: `user`, `form` editable on an existing sitting; answers editable and deletable inline although they are an audit record (the `FormProgress.form` FK is `PROTECT`, comment calls the sitting "the audit record of a sitting").
- No `QuestionAnswerInline` queryset optimisation: each row loads `question`, `selected_options`.
- Pages and sections: the done spec research notes there is no export for form_engine data (`SiteAwareExportModelAdmin` exists in `site_aware_models/admin.py` if ever wanted).

**`CourseApplication` side**: not in admin at all, so a reviewer must open the `FormProgress` list and search by user email/form title to find an applicant's answers, with no course, application date, or "draft vs submitted" label.

**Admin conventions seen in `learner_progress/admin.py`** (usable patterns): Unfold `TabularInline` with `tab = True`, `per_page`, `show_count`, `max_num = 0`, `can_delete = False`, `show_change_link = True`, read-only fields, `get_queryset` with `select_related`; Unfold `@display(label={...})` coloured status badges; `RelatedDropdownFilter`/`AutocompleteSelectFilter`/`InclusiveRangeDateTimeFilter` with `list_filter_submit = True`; `quiz_result(attempt)` helper (formatted "NN% passed/failed", guards every `ValueError` case up front); `LEARNER_SUMMARIES` list and `learner_progress_links` helper for change-form summary panels (links built with `format_html_join`); `site_aware_models.admin.admin_page_context(request, model_admin, title)` for custom pages inside the admin shell (keeps the sidebar and breadcrumbs).

## 3. form_engine models and question types

- `FormProgress(SiteAwareModel)`: `form` FK (PROTECT, `related_name="progress_records"`), `user` FK (CASCADE, `related_name="form_progress"`), `start_time` (auto_now_add), `last_updated_time` (auto_now), `completed_time` (null), `scores` JSON (null), `furthest_page_reached` (PositiveSmallInt, default 0). `verbose_name_plural = "Form progress records"`. Methods: `quiz_percentage()`, `passed()`, `record_page_reached()`, `existing_answers_dict(questions)`, `save_answers()`, `complete()`, `score()` and strategy scorers, `compute_quiz_scores()`, `get_incorrect_quiz_answers()`. Reverse accessors: `answers` (QuestionAnswer), `course_application` (CourseApplication, only for application sittings), `course_attempt` (learner_progress `CourseFormAttempt`, only for sittings inside a course).
- `QuestionAnswer(SiteAwareModel, TimestampedModel)`: `form_progress` FK (`related_name="answers"`), `question` FK to `FormQuestion` (PROTECT), `selected_options` M2M to `QuestionOption`, `text_answer` TextField. Unique `(form_progress, question)`. **There is no `data` JSON field.** The done spec named "form_engine data field" is in fact "Typed question types for form_engine" (`date`, `time`, `email`, `url`, `phone`, `dropdown`, `min`/`max`/`decimal_places`); "storage does not change" and all typed answers stay strings in `text_answer`.
- `QuestionAnswerFile(SiteAwareModel, TimestampedModel)`: `answer` OneToOne to `QuestionAnswer` (`related_name="answer_file"`), `file` (storage alias `user_uploads`, key `user_uploads/<user_id>/form_answers/<pk><ext>`), `original_filename`. `save()` deletes the superseded object. Reverse access `answer.answer_file` raises `RelatedObjectDoesNotExist` when none.
- `FormQuestion(BaseContent)`: `form_page` FK (`related_name="questions"`), `order`, `category`, `question` (markdown text, `rendered_question()`), `type`, `required`, `min`, `max`, `decimal_places`. Ordered by `order` within a page. `FormPage` (ordered by `order`, `category`, `children()` returns text items + questions in order). `Form` fields: `strategy`, `quiz_show_incorrect`, `quiz_pass_percentage`, `submit_on_exit`.
- Question order across a form: pages by `FormPage.order`, questions by `FormQuestion.order`, content blocks (`FormContent`) share the same `order` space as questions on a page. `page_questions(page)` in `form_engine/queries.py` is the existing helper for ordered questions.

`QuestionType` (`enums.py`) and storage:

| Type | Stored in | Rendered by `format_answer` |
| --- | --- | --- |
| `multiple_choice` | `selected_options` (one option) | n/a (options) |
| `checkboxes` | `selected_options` (several) | n/a |
| `dropdown` | `selected_options` (one option, same as multiple choice) | n/a |
| `short_text`, `long_text` | `text_answer` | raw |
| `number` | `text_answer`, a number string honouring `decimal_places`/`min`/`max` | raw |
| `date` | `text_answer`, ISO `YYYY-MM-DD` | localised date (unparseable falls back to raw) |
| `time` | `text_answer`, `HH:MM` | localised time (same fallback) |
| `email`, `url`, `phone` | `text_answer` (url may lack scheme) | raw |
| `file_upload` | `QuestionAnswerFile` via the answer; `text_answer` empty | n/a; `save_answers` skips these on page POST |

`FREE_TEXT_QUESTION_TYPES` = all text-stored types above (short_text, long_text, number, date, time, email, url, phone). No type is "application-only" in code: `file_upload`, the typed set, and `UNSCORED` were all added for application forms but are available on any form. Application forms in practice use `UNSCORED` strategy.

`FormStrategy`: `CATEGORY_VALUE_SUM` (scores nested dict by page category | question category, option `value` ints; only multiple_choice and dropdown count), `QUIZ` (`scores = {"score", "max_score"}`, one point per fully correct question, uses `QuestionOption.correct`; free-text questions score zero), `UNSCORED` (no scores written, `scores` stays null; completing only stamps `completed_time`). `scores` is "frozen at submission and never rescored" (docstring of `compute_quiz_scores`).

## 5. Admin conventions that bind this work

- django-unfold is the admin theme (`SiteAwareModelAdmin` extends `unfold.admin.ModelAdmin`; `.claude/ds/config.md` says theme unfold and guardian enabled). Product doc: Unfold admin at a configurable path.
- `claude_plugins/fls-dev/skills/admin-interface/SKILL.md`: read `ds:admin-interface` first (unfold + guardian files); every admin class extends `SiteAwareModelAdmin` (not plain `ModelAdmin`); inlines "use `SiteAwareTabularInline` or `SiteAwareStackedInline`" (these do not exist in `site_aware_models/admin.py`; the application-review idea flags this skill as stale, and existing code uses `unfold.admin.TabularInline` directly with `exclude = ["site"]` on site-aware inline models, since the inline is not covered by the base class's exclude); CSV export uses `SiteAwareExportModelAdmin` plus a `SiteAwareModelResource`, never `IMPORT_EXPORT_FORMATS`; never display or edit `site`.
- `claude_plugins/django-stack/skills/admin-interface/SKILL.md` + `resources/admin_unfold.md`: Unfold bases (`ModelAdmin`, `TabularInline`, `StackedInline`) not Django's, or the page "renders unstyled"; register with `@admin.register`; `autocomplete_fields` for FK/M2M; `readonly_fields` for generated fields; `fieldsets` for organisation. Existing `QuestionAnswerInline` violates the inline rule (plain `admin.TabularInline`).
- Project rules: type hints on all functions, no `Any`, no `# type: ignore`, `select_related`/`prefetch_related` for related access, no logging unless asked, specific exception handling, no abstract base classes unless asked, no speculative functionality; use `format_html` for HTML output.
- Who has admin access: `User` has `is_staff` and `is_superuser` flags (`accounts/models.py`; `create_superuser` sets `is_staff=True`, `is_superuser=is_admin`). Admin site access is staff; per-model Django permissions are used for staff roles. The answer-data admins override every permission check with `request.user.is_superuser` regardless of grants. `role_based_permissions` roles (`site_admin`, `organisation_admin`, `cohort_admin`, `cohort_viewer`) only govern the educator interface and cohort reports and "grant nothing" in the admin; a staff user is not enough to see answers or download files. Superusers short-circuit role checks in `learner_management/queries.py`, `capabilities.py`, `role_assignment.py`.

## 6. Vocabulary

`.claude/skills/domain-glossary/SKILL.md` does **not** define application, applicant, sitting, answer, question or file. Per its own rule the code is the vocabulary, and where a concept is a model use the class name:

- `CourseApplication` ("application"): the learner's request for access to an application-gated course. Its owner is the `user`; "applicant" appears in code (`QuestionAnswerFileAdmin.applicant`, docstrings) and in done specs and product docs, so it is the established prose word for the user on an application.
- "sitting": used in model and code docs (`CourseApplication.form_progress` docstring: "the applicant's own sitting of the form"; `FormProgress.form` comment) and in the glossary: "`FormProgress` - the sitting itself: its answers, its score, when it finished". It is not coined.
- `FormProgress` ("form progress record", plural "Form progress records"): the glossary says keep **"form progress record"** for the `form_engine` row and **"course form attempt"** for `learner_progress`'s `CourseFormAttempt`; avoid unqualified "attempt" where the split matters. Note `FormProgressAdmin.in_course` and comments say "attempt" for the sitting; the glossary prefers "form progress record" or "sitting".
- `QuestionAnswer` ("answer"; glossary: "one answer within a `FormProgress`"), `QuestionAnswerFile` (the file an applicant attached), `FormQuestion` ("question"), `FormPage` ("page"), `QuestionOption` ("option"), `QuestionType`, `FormStrategy`, `scores`, `furthest_page_reached`.
- Course side: `Course`, `Learner` (the `(user, organisation)` row, not a synonym for `User`; `FormProgress` and `CourseApplication` key on `user`, not `learner`, per the glossary note and code), "registration" is the access word (not "enrolment", "grant", "entitlement"). "Approval is not enrolment" was an application-review decision.
- Taken words to avoid: **grant** (role/object permission), **item** (ambiguous: use "collection item" or "child"), **link** as a model/field noun, **slot**, **course item**, **collection**, bare "progress record" when several models are in play (say "form progress record"), **student** (never introduce a `student_*` name), **review/reviewer/state/status** are the territory of the unbuilt application-review effort and the glossary has no entry for them; avoid naming new fields or models with them. Also avoid "enrol"-style synonyms for registration, and "attempt" for a sitting unless it is the `CourseFormAttempt` meaning.
- Glossary doc-staleness spotted (not for this spec to fix, but cite carefully): glossary says `FormProgress` "has not moved yet - it still keys on `user`", which matches the current model.
