# Research: CourseApplication admin (changelist, change page, cross-links)

Scope: plain find-and-read admin for `CourseApplication`. No state machine, notes, approve/reject, decided_*, or `view_application`/`change_application` permissions (the `CourseApplication` docstring at `freedom_ls/course_applications/models.py:24-29` reserves all of these for "application review"; the roadmap, `spec_dd/1. next/roadmap.md:110,126`, and `spec_dd/1. next/educator-interface-full-polish/application-review-ui/research_review_workflow.md:221` say review lives in `educator_interface` and Django admin stays "read-mostly support access"). The admin must stay additive so review can replace the unique constraint, add `state`, and add a state filter without rework.

## 0. Existing FLS admin conventions (verified in repo)

- django-unfold IS in use (`pyproject.toml:14`, `freedom_ls/base/admin_config.py`). Base class `SiteAwareModelAdmin(unfold.admin.ModelAdmin)` in `freedom_ls/site_aware_models/admin.py` sets `exclude = ["site"]`. The fls-dev `admin-interface` skill says all admins MUST extend `SiteAwareModelAdmin` (or `SiteAwareExportModelAdmin` for CSV).
- `SuperuserOnlyAdmin` mixin lives in `freedom_ls/form_engine/admin.py:31` (NOT shared; defined in form_engine). It gates view/change/add/delete to `request.user.is_superuser`, with the rationale that applicant sittings/answers/documents are "their own words and papers" that per-model permissions cannot protect. Used by `FormProgressAdmin`, `QuestionAnswerAdmin`, `QuestionAnswerFileAdmin`. If CourseApplication admin shows answers, it should be superuser-only too, otherwise a staff user with just `view_courseapplication` would read what `FormProgressAdmin` hides. Importing it from `form_engine.admin` into `course_applications.admin` is possible but cross-app-admin coupling; alternative is moving it to `site_aware_models/admin.py` (small refactor, spec decision).
- Read-only pattern: `has_add/change/delete_permission` returning False + `readonly_fields` (`referral_tracking/admin.py:48-78` `SignupAttributionAdmin`, `webhooks/admin.py`, `LegalConsentAdmin` in `accounts/admin.py`). Helper `_readonly_field_names(model)` in referral_tracking builds the list (local, not shared).
- Custom list filters: `CompletionListFilter(SimpleListFilter)` in `freedom_ls/site_aware_models/admin_filters.py:17` already does "complete / not complete" on a nullable timestamp via `completion_field = "completed_time"` (subclassed as `FormProgressCompletionFilter`). `InclusiveRangeDateTimeFilter` (same file) is the date-range filter used with `list_filter_submit = True`. `AutocompleteSelectFilter` (`unfold.contrib.filters.admin`) used for `("form", AutocompleteSelectFilter)`; needs the related admin to have `search_fields`.
- Link columns: `format_html('<a href="{}">...</a>', reverse("admin:..."))` e.g. `QuestionAnswerFileAdmin.download`, `reports/admin.py:105`, `referral_tracking/admin.py:218`. `@admin.display(description=..., ordering=..., boolean=True)` is the display convention. No existing `admin:<app>_<model>_change` link column helper; each is hand-rolled.
- `FormProgressAdmin` is the closest model to copy: `list_select_related`, `date_hierarchy = "completed_time"`, `search_fields = ("user__email", ...)`, `ordering = ("-start_time",)`, `list_filter_submit = True`, and `QuestionAnswerInline` (editable inline of answers; raw `selected_options`/`text_answer`, readable but not a nice rendering; `typed_answers.format_answer(question.type, text)` is the existing formatter used by `QuestionAnswerAdmin.answer_preview`).
- UserAdmin (`accounts/admin.py:100`): `search_fields = ["email","first_name","last_name"]`, so it can be an autocomplete target; `inlines = [LegalConsentInline]` (read-only inline pattern). `User` has `first_name`, `last_name`, `display_name`. `USER_ERASURE_CASCADE_MODELS` (`accounts/admin.py:20`): models whose admins deny delete but that must cascade when a user is erased; `UserAdmin.get_deleted_objects` strips their "perms needed" so a superuser/staff can delete a user. `get_deleted_objects` would otherwise report "you don't have permission to delete CourseApplication" if CourseApplicationAdmin denies delete and the deleter lacks the perm. Add `CourseApplication` to this set if admin delete is denied (see section 2).
- `CourseAdmin` (`content_engine/admin.py:161`): `search_fields = ("title","subtitle","description")`, `inlines = [ContentCollectionItemInline]`. Good as autocomplete/filter target.

## 1. Changelist

Recommended `CourseApplicationAdmin(SuperuserOnlyAdmin, SiteAwareModelAdmin)` (see CSV section re. export).

list_display (all cheap unless noted):
| column | source | cost |
|---|---|---|
| applicant email | `user__email` via method `@admin.display(ordering="user__email")` | cheap (join; `list_select_related`) |
| applicant name | `user.display_name` or first+last | cheap; ordering via `user__last_name`/`user__first_name` |
| course | `course` (str via title) with `ordering="course__title"` | cheap |
| submitted (boolean) | `is_submitted` property -> `@admin.display(boolean=True, description="Submitted")` reading `obj.form_progress` | needs `form_progress` in `list_select_related`; python-side only, NOT sortable unless annotated |
| submitted time | `form_progress__completed_time` via method with `ordering="form_progress__completed_time"` | cheap, but sort puts NULL (no form / draft) ordering by DB default; blank for no-form apps (their submit time = `created_at`) |
| created | `created_at` | cheap |
| (optional) updated | `updated_at` | cheap |

Note the semantic gap: for a no-form application "submitted time" has no stamp; show `created_at` as the fallback in that cell (the `is_submitted` docstring says it is submitted the moment it is created) or leave dash. Recommend: show `form_progress.completed_time`, falling back to `created_at` when `form_progress is None`. No annotation required for display; annotation (`Case/When` or `Coalesce("form_progress__completed_time","created_at")`) is only needed to make that column sortable and to be reused by `date_hierarchy` (not possible; `date_hierarchy` takes a real field).

list_filter:
- Custom `SimpleListFilter` for submitted/draft: `submitted` -> `Q(form_progress__isnull=True) | Q(form_progress__completed_time__isnull=False)`; `draft` -> `form_progress__isnull=False, form_progress__completed_time__isnull=True`. DB-expressible, no annotation, no join explosion (one-to-one). Do not subclass `CompletionListFilter` as-is: its single `completion_field` can't express the "no form counts as submitted" OR. Keep the filter's logic next to the model/property so the later `state` filter replaces it cleanly. Note: this must stay consistent with `CourseApplication.is_submitted`; a test asserting filter results == property is cheap.
- `("course", AutocompleteSelectFilter)` (matches FormProgressAdmin; CourseAdmin has search_fields) or plain `"course"` FK filter if few courses. Prefer autocomplete (many courses on a site).
- `("created_at", InclusiveRangeDateTimeFilter)` with `list_filter_submit = True` (existing pair). Optional: `form_progress__form` filter (which form was used) — skip unless asked.

search_fields: `("user__email", "user__first_name", "user__last_name", "course__title")` — mirrors UserAdmin + CourseAdmin; all cheap `icontains`. Do not search answer text (joins to QuestionAnswer, heavy; PII search surface).

date_hierarchy: `"created_at"` (real field, always populated). `form_progress__completed_time` is legal for date_hierarchy via lookup path? Django allows FK-path date_hierarchy in recent versions but NULLs drop rows (drafts, no-form) — don't. Use `created_at`.

ordering: `("-created_at",)`. A deterministic tiebreak is unneeded (UUID pk fine).

list_select_related: `("user", "course", "form_progress")` (forward FKs only; no reverse lookups needed, unlike FormProgressAdmin's `course_attempt__...`).

list_per_page default is fine.

## 2. Change page

Recommendation: read-only change page; no add; delete only deliberately.

- Editable fields are a risk: `user`/`course` form fields render FK selects (all users on the site — heavy, though `SiteAwareManager` filters); editing them can violate `unique_application_per_site_user_course` (raises a form validation error, fine) but more importantly breaks the invariant that `form_progress` is the *applicant's own* sitting of *that course's* form: `form_progress.user` would differ from `application.user`, and the form could differ from the course's. Re-pointing `form_progress` can also collide with RESTRICT/one-to-one (a sitting already attached elsewhere) and orphans a sitting. Review will add `state` as `FSMField(protected=True)` — protected fields can't be set directly; an editable admin on a model that gains a protected state field invites bypass of transitions. So: `readonly_fields` = everything (`user`, `course`, `form_progress`, `created_at`, `updated_at`, plus computed `submitted`), no editable fields at all. Make `has_change_permission` return False? That makes the page view-only ("view" mode; Unfold renders readonly), matching `SignupAttributionAdmin`. But when review lands it needs a change permission for transitions; admin should not own that, so False is consistent with "review lives in educator_interface".
- `has_add_permission = False`: applications are created only by the learner apply flow (`views._start_application`), which also creates the `FormProgress`; an admin-created one would have no sitting or a mismatched one.
- Delete: FK semantics — deleting the application is plain (it holds the FK to `form_progress`; RESTRICT protects the *sitting* from being deleted while the application stands, not the reverse). So deleting a CourseApplication leaves the FormProgress orphaned (sitting + answers + uploaded files remain; cascades nothing). That orphan is PII with no owner row. Conversely deleting the FormProgress (via FormProgressAdmin, superuser) raises `RestrictedError`; Unfold/Django admin shows it in the "cannot delete" list (Django's `get_deleted_objects` collects `restricted`; Django 3.1+ handles RESTRICT in admin and displays protected objects). Deleting the User cascades both (docstring: "deleting the applicant must still take the application and the sitting away together"). Recommendation: `has_delete_permission = False` on the CourseApplication admin, and add `CourseApplication` to `USER_ERASURE_CASCADE_MODELS` so `UserAdmin` deletion still works (this is exactly what that set is for). Fallback if the spec wants deletable: delete is allowed but must also be paired with sitting deletion — don't build that; out of scope.
- Where answers go: inline on the change page as its own fieldset/section ("Answers"), below the read-only summary fieldset (applicant, course, status, dates) — i.e. second block on the page, not buried in a tab. Rendering handled by the other worker's research. The existing `QuestionAnswerInline` is on FormProgress (not reachable from CourseApplication, since the relation is a forward FK from application to sitting; a Django inline can't hang off it), so answers must be a readonly-field/method rendering via `format_html`, or a custom template. Answers shown only to superusers (`SuperuserOnlyAdmin`) unless the spec decides otherwise. `QuestionAnswerFile` documents are served only via the superuser-only download route (`QuestionAnswerFileAdmin`, `form_engine/admin.py:388`); do not emit file URLs/links from the application page that bypass that gate (the admin excludes `file` for exactly that reason). A link to the download route from the answers rendering is fine.
- Links to related pages on the change page (read-only fields): user -> `admin:freedom_ls_accounts_user_change`? (confirm label: `accounts` app label; use `reverse(f"admin:{model._meta.app_label}_{model._meta.model_name}_change", args=[pk])` rather than hardcoding). Course -> `admin:freedom_ls_content_engine_course_change`. FormProgress -> `admin:freedom_ls_form_engine_formprogress_change`. Note: unfold readonly FK fields already render as plain text; a small helper (`format_html` link) is needed. Link to FormProgress only when it exists, and the FormProgress admin is superuser-only so non-superusers can't follow it (another reason to gate the whole app admin to superuser).

## 3. Cross-links

- FormProgress admin -> application: add a readonly method field `application` to `FormProgressAdmin.readonly_fields`/fieldsets that reads `obj.course_application` (reverse one-to-one raises `CourseApplication.DoesNotExist`/`RelatedObjectDoesNotExist`; use `hasattr(obj, "course_application")`, same trick as `in_course` in `FormProgressAdmin`). Also add `"course_application"` to its `list_select_related` if shown in the list. Cheap; this edits form_engine admin from a course_applications spec (form_engine already knows `course_attempt` reverse one-to-one, so precedent exists). Layering: `course_applications` depends on `form_engine`; `form_engine.admin` referencing `course_applications` via reverse accessor name only (string, no import) keeps the direction clean; the reverse URL name is string too.
- User admin -> applications: preferred minimal: no inline (an inline of CourseApplication on UserAdmin would be an editable-model inline subject to the read-only rules; could use a read-only `TabularInline` like `LegalConsentInline` with `show_change_link = True`, fields course/is_submitted/created_at). Alternative: a link `"N applications"` to `admin:..._courseapplication_changelist?user__id__exact=<pk>` — needs `user` filter param allowed; `list_filter` doesn't need to include `user`, but Django admin only honours lookups on fields in list_filter/`lookup_allowed` — `user__id__exact` is allowed because `user` is a relation in `list_display`? Not automatically; `lookup_allowed` permits a lookup on a FK when it is part of `list_filter` or the FK is a related key to `to_field`. Simplest: `?q=<email>` (search param), which always works. Recommendation: read-only inline with change link on UserAdmin (matches `LegalConsentInline`), done in `accounts/admin.py`... but accounts importing course_applications creates a dependency; accounts is a lower-level app. Prefer the inverse: the course_applications admin module registers/augments? Django lets you do `UserAdmin.inlines = [...] + [ApplicationInline]` from the course_applications admin module, though that is fragile. Flag as a spec decision; lowest-risk is `?q=email` link only, or leave user->applications out of v1 and satisfy "find applications by applicant" with the search box.
- Course admin -> applications: same options; `CourseAdmin` in content_engine (lower-level). Cheapest equivalent: course filter on the application changelist (already specified), reachable via a changelist URL `?course__id__exact=<uuid>` (works because `course` is in list_filter). A link column on CourseAdmin is optional/out of scope for v1.

## 4. Applicant-tracking comparison (general knowledge; not freshly verified, no URLs fetched)

ATS/application tools (Greenhouse, Submittable, OpenWater and similar) lay the list out as one row per application with: applicant name (+ email), the program/job/course, a status column, submission date, and last-activity date; filters for program, status and date range; free-text search by name/email; the detail view leads with applicant summary + submission metadata then the submitted form answers in sections, with attachments listed. Drafts ("in progress") are generally distinguished from submitted by a status/tag and by a separate "submitted on" column. That maps directly onto the proposal: name/email, course, submitted-vs-draft, submitted time, created; filter course/status/date; summary then answers. Everything beyond that (assignment, scoring, tags, bulk status changes, notes) is review-workflow and excluded here. Treat this paragraph as unverified background; no source was fetched, so cite nothing from it in the spec.

## 5. CSV export

An export pattern exists: `SiteAwareExportModelAdmin` (`freedom_ls/site_aware_models/admin.py:28`) + `SiteAwareModelResource` and `FormulaSafeCSV` (`site_aware_models/admin_exports.py`), via django-import-export (`pyproject.toml:39`), used in `referral_tracking/admin.py`. It gates export on view permission and escapes formulae. Exporting applications would expose applicant email/PII (and, if answers were added, free text) — the form_engine admin deliberately limits answers to superusers. Not recommended for this spec; if wanted later it is a one-line base swap plus a `resource_classes` Resource with explicit fields (no answers). No export action is present on `reports`/cohort admins beyond a "Generate cohort report" Unfold action in `reports/admin.py:110` (a different report-file mechanism).

## 6. Summary recommendations (decisive)

1. `CourseApplicationAdmin(SuperuserOnlyAdmin, SiteAwareModelAdmin)` in `freedom_ls/course_applications/admin.py`; consider relocating `SuperuserOnlyAdmin` to `site_aware_models/admin.py` rather than importing across apps' admin modules.
2. Read-only change page: no add, no delete, all fields read-only; add `CourseApplication` to `USER_ERASURE_CASCADE_MODELS`.
3. Changelist: user email, name, course, submitted (boolean), submitted-time (completed_time else created_at), created; filters submitted/draft custom `SimpleListFilter`, course autocomplete, created range; search on email/name/course title; `date_hierarchy="created_at"`; `ordering=("-created_at",)`; `list_select_related=("user","course","form_progress")`. No annotation needed except to make submitted/submitted-time sortable (skip).
4. Change page layout: summary fieldset (links to user, course, FormProgress), then Answers section (rendered per the other worker's findings), then timestamps.
5. Cross-links: FormProgress admin readonly "application" link via `hasattr(obj, "course_application")`; user/course -> applications via search/changelist links only (no cross-app inline in v1).
6. Do NOT add: state/status filters, notes, approve/reject actions, `submitted_at`, custom permissions, CSV export.
