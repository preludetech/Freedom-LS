# Research: best practices for "say it, then reveal"

Provenance: written from background knowledge of the cited specs and docs. No page was fetched live in this pass, so treat version-specific browser claims as "verify before relying". It builds on `spec_dd/1. next/content-widget-sayit-reveal/research_audio_widgets.md` (sections 2, 5 and 6 cover reveal basics, WCAG 1.2.1/1.4.2/2.1.1 and format/preload) and does not repeat it.

## 1. Accessible reveal (disclosure) pattern

- **Use a real `<button>` with `aria-expanded` and `aria-controls`.** The APG Disclosure pattern is exactly this: a button toggles the visibility of a content region, and `aria-expanded` reflects its state. https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/
- **`aria-expanded` vs `aria-pressed`.** `aria-pressed` is for toggle buttons whose label stays fixed and whose state is on/off (mute, bold). `aria-expanded` is for a button that shows or hides a related region. Reveal/Hide is a disclosure, so use `aria-expanded`. Do not use both on one button. If the label changes ("Reveal" to "Hide"), do not also use `aria-pressed`, because the label change and the state then conflict. Either keep one label plus `aria-expanded`, or swap to two distinct buttons. https://www.w3.org/WAI/ARIA/apg/patterns/button/ and https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-expanded
- **Reveal and Hide as two buttons is fine and arguably clearer.** Spec outline: Reveal button (hidden or removed after use), then replay and Hide controls inside the revealed region. When the Reveal button is removed, the focus must be moved deliberately (see below), or it is lost to `<body>`.
- **Hiding content: `hidden` / `inert` / `aria-hidden`.**
  - `hidden` (display:none) removes content from the accessibility tree and focus order, but blocks CSS transitions. Fine if no animation is needed.
  - `inert` makes the subtree non-focusable, non-clickable and hidden from AT. It is the right tool when the content must stay laid out (a flip card's back face, an opacity or transform transition). It is Baseline in all current engines (Chrome 102, Safari 15.5, Firefox 112). https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inert
  - `aria-hidden="true"` alone is not enough: focusable children inside stay tabbable, which is an ARIA misuse. Pair it with `inert`, or use `inert` alone (it already hides from AT). https://www.w3.org/WAI/ARIA/apg/practices/hiding-semantics/ (see also the `aria-hidden` focusable-content rule)
  - Toggle `inert` from JS when revealing: remove `inert` from the answer, and set it on it again when hiding. The hidden answer must also not be read by find-in-page or Ctrl+A copy leaks. For genuinely "do not leak the answer" semantics, `hidden` is the safest, because `inert` plus opacity:0 content is still in the DOM and visible to view-source (it is a self-check, so this is acceptable).
- **Announcing the answer.** Two reliable options:
  1. Focus moves into/onto the revealed answer (a heading or a container with `tabindex="-1"`), so the screen reader reads it. This is the best fit when the answer is the thing the user needs next.
  2. A pre-existing `aria-live="polite"` (or `role="status"`) region whose text content is set on reveal. The live region must exist in the DOM before the content changes, and live regions do not reliably announce content that is merely un-hidden (display toggled) in some AT combinations. Inject the text (or toggle `inert`/`hidden` on a child while the region itself stays rendered) and test with NVDA+Firefox/Chrome, JAWS, VoiceOver. https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions and https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html
  - Do not do both focus move and live announcement for the same content: it double-speaks. Pick one. For this widget, announce via live region and keep focus on a stable control (see below), or move focus to the answer and skip the live region. Decide in the spec and test once.
  - Composing the live text: say "Answer: Juliett, pronounced JEW-lee-ETT" so the respelling is spoken. The audio playing at the same time can talk over the screen reader: this is a real conflict for blind learners (see section 2 mitigations).
- **Focus management after reveal and hide.**
  - Reveal pressed: the Reveal button is typically hidden or disabled, which drops focus. Move focus to a sensible target: the replay button (first interactive control in the revealed region) or the answer container. Keeping the focus on the pressed button works only if the button stays rendered (the `aria-expanded` approach with a single toggle button).
  - Hide pressed: return focus to the Reveal button (the control the learner will want next to retry). Never leave focus on an element that has just become `inert` or hidden. https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_visible and WCAG 2.4.3 Focus Order https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
  - The focus indicator must stay visible (2.4.7, and 2.4.11 Focus Not Obscured in WCAG 2.2). https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html
- **No-JS / progressive enhancement.** A native `<details><summary>` gives a free, accessible disclosure (and browsers handle exclusive groups through `name=`). It cannot run the audio click-to-play handler without JS, and it does not fit the flip card, but it is a useful baseline to compare when choosing "variant of `c-accordion`". `<details>` expanded state is toggled by `summary` click, so the audio play can hang on the `toggle` event, but `toggle` is not a user-gesture event in all browsers' autoplay checks: attach `click` on the summary instead. https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details
- **Target size.** WCAG 2.2 2.5.8: at least 24x24 CSS px, aim for 44x44 on touch. https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html

## 2. Audio on a user gesture: autoplay policy and pitfalls

- **Policy summary** (the gesture requirement the earlier file noted, in more detail):
  - Chrome: unmuted `play()` is allowed after a user activation on the page (click, tap, keypress) or on high Media Engagement Index sites. A click on the Reveal button counts. https://developer.chrome.com/blog/autoplay
  - Safari (macOS and iOS): `play()` must be called in the call stack of a user-gesture handler. iOS is the strictest: a gesture "unlocks" the specific media element (or the `AudioContext`) it was called on. A different, new `Audio()` created later and played outside a gesture can be rejected. https://webkit.org/blog/6784/new-video-policies-for-ios/
  - Firefox: blocks audible autoplay by default; allows it after user interaction with the page. https://support.mozilla.org/en-US/kb/block-autoplay
  - The whole spec: `click` handler to `audio.play()` synchronously, no `await fetch()` or `setTimeout` between the click and `play()`. Waiting on a network call or an HTMX swap in between can lose the gesture in Safari. If the answer clip is loaded by HTMX after the click, the play will not count as gesture-triggered. Therefore render the `<audio>` element (or have its URL ready) in the page before the click. https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay
- **`play()` returns a Promise.** It rejects with `NotAllowedError` (policy) or `NotSupportedError` (bad source) or `AbortError` (interrupted by `pause()` or a new load). Always handle: `audio.play().catch(err => ...)`. Ignoring it produces an "Uncaught (in promise)" error and, worse, a UI that says "playing" when nothing plays. Set the playing state from the `playing`/`pause`/`ended` events, not from the click. Treat `AbortError` as non-fatal. On `NotAllowedError` show the replay control as the visible fallback (the learner can press it, which is a fresh gesture). https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play
- **First-play latency.** With `preload="none"`, the first `play()` has to fetch headers and decode, giving a noticeable gap after Reveal (hundreds of ms on mobile). Mitigations:
  - `preload="auto"` or `"metadata"` on the one clip in the widget. The earlier note says iOS may ignore `auto`; metadata and a lazy prefetch when the widget nears the viewport (IntersectionObserver calling `audio.load()`) is the compromise. Some browsers (iOS Safari) will not preload before a gesture at all, so expect the first play to lag there, and do not design around zero latency.
  - Reveal visually first, then audio starts when ready. Avoid blocking the text on the audio.
  - Short clips: serve with correct `Content-Type`, `Accept-Ranges` (Safari needs HTTP range requests to play media, a common failure behind some dev servers). https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/Using_HTML5_Audio_Video/Device-SpecificConsiderations/Device-SpecificConsiderations.html
  - Web Audio `decodeAudioData` gives instant replay but needs fetch and decode and an `AudioContext` that must be resumed in a gesture. It is overkill for a single clip. The `<audio>` element is the right choice and is what `c-audio` already is.
- **Replay.** Set `audio.currentTime = 0` then `play()`, instead of reloading. If it has `ended`, `play()` restarts on its own in most browsers, but be explicit.
- **Silent switch / ringer (iOS).** `<audio>` elements respect the hardware silent switch in some configurations. The learner may hear nothing and think the widget is broken. Provide a visible control state and, in docs, a note. (Verify per iOS version.)
- **Reduce collisions with screen-reader speech.** If the widget announces the answer via live region and the clip plays at the same moment, they overlap. Options: autoplay anyway (the settled decision) and keep the live text short; or note it as an accepted known limit. Mention in the spec's accessibility notes. Not a blocker, since replay exists.
- **WCAG 1.4.2 Audio Control.** The clips are under 3 seconds, so the 3-second rule is not triggered, and the playback is click-initiated, not automatic on load. Still, expose the replay control as the stop/replay mechanism. https://www.w3.org/WAI/WCAG22/Understanding/audio-control.html

## 3. One-at-a-time playback

- **Pattern:** a module-level singleton ("current player"). Before starting a clip, pause the previous one (and reset or leave its position). Listen to the `play` event on the document in the capture phase (media events do not bubble, but they do capture): `document.addEventListener('play', e => { if (e.target !== current) current?.pause(); current = e.target }, true)`. This needs no registration from each component and works with any number of `<audio>` elements, including `c-audio` instances and flip-card audio, and any in-page `<audio controls>`. https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement#events
- Update every other player's UI from its own `pause` event, not from the singleton, so the visible state stays correct.
- On Hide: pause and reset the answer's clip so a hidden answer is not speaking. Also pause when a flip card flips back, or when the widget becomes inert.
- A new gesture-triggered `play()` that interrupts another produces `AbortError` on the older promise. Swallow it.
- Add the media session option only if wanted: `navigator.mediaSession` is not needed for one-second clips.
- Where `c-audio` (spec 1) already implements one-at-a-time, reuse it, and make sure a clip started by Reveal goes through the same path rather than calling `audio.play()` directly. That is a spec-1 contract to check.

## 4. Nested interactive controls inside a clickable card

- **The problem.** A card whose whole surface is a click target (flip) and that contains a real button is a "nested interactive" structure. WCAG has no single failure for it, but axe's `nested-interactive` rule flags focusable descendants of elements with roles whose children are presentational (button, checkbox, img, tab...). Putting a `<button>` inside `role="button"` is the trigger case: screen readers flatten the inner control or hide it. https://dequeuniversity.com/rules/axe/4.10/nested-interactive and https://www.w3.org/TR/wai-aria-1.2/#childrenArePresentational
- **Structure fix, preferred:** do not make the card face itself `role="button"`. Keep the flip control a sibling: one explicit `<button>` ("Flip card" / "Show answer") and the faces as plain content. The audio button sits in the face, not inside the flip button. Then there is no nesting, only a click handler on a wrapper for mouse convenience, which does not alter semantics (keyboard users get the explicit flip button). The wrapper click becomes a convenience that must ignore clicks that came from inner controls.
- **Event handling:**
  - In the wrapper's click handler, bail out when the event target is inside an interactive descendant: `if (e.target.closest('button, a, audio, [data-no-flip]')) return;`. This is more robust than `stopPropagation()` on each inner button, because stopping propagation breaks delegated listeners elsewhere (analytics, HTMX `hx-trigger` on ancestors, the one-at-a-time capture listener is unaffected since it is on `play`). If `stopPropagation()` is used, do it in the inner control only and know that HTMX and Alpine delegated handlers on ancestors then never see the click.
  - Prefer `closest()` target-checking in the flip handler over `stopPropagation` in the audio button. It keeps `c-audio` ignorant of its container, which matters because `c-audio` is a reusable component from another spec.
- **`pointer-events`.** `pointer-events: none` on the face stack (as `c-flashcard` does) means clicks go to whatever is behind: the card, not the button. A child with `pointer-events: auto` re-enables hits on just that child, since `pointer-events` is inherited but may be overridden per element. So the fix is `pointer-events: auto` on the visible face's interactive controls only, and hidden-face controls stay `none`. Do not rely on `pointer-events: none` for the hidden face: it blocks mouse only and keyboard Tab still reaches buttons. Pair it with `inert` on the hidden face, which blocks pointer, keyboard and AT in one attribute. https://developer.mozilla.org/en-US/docs/Web/CSS/pointer-events
- **3-D flip gotchas.** `backface-visibility: hidden` hides the rendering of the back face but not its hit-testing in every browser, and not its accessibility tree entry. Safari has historically had bugs where a rotated back face receives clicks or where `backface-visibility` needs the `-webkit-` prefix and `transform-style: preserve-3d` on the right ancestor. Test the audio button's hit area in Safari and with a flipped card. Also, on iOS `preserve-3d` children can be mis-hit-tested when a parent has `overflow:hidden` or `opacity < 1`. Toggle `inert` on whichever face is hidden at the flip's start (not the end) or at the midpoint, and move focus when a face goes inert. https://developer.mozilla.org/en-US/docs/Web/CSS/backface-visibility
- **Flip and audio.** Flipping must pause any clip playing in the face that is being hidden (see section 3). Pressing the audio button does not change the flip state or the card's `aria-expanded`/`aria-pressed`.
- **Touch.** Taps on a button inside a click-target give the same `click` as a mouse. The 300 ms delay is gone in modern browsers with the viewport meta tag. Make the audio button at least 44x44 so a tap does not miss and flip the card by accident.
- **Keyboard.** Space/Enter on the audio button must not bubble to a keydown handler on the card that also flips it. If the card has a `keydown` handler, apply the same `closest()` guard.

## 5. Reduced motion

- Honour `prefers-reduced-motion: reduce`. WCAG 2.3.3 (AAA, Animation from Interactions) says motion animation triggered by interaction can be disabled unless essential. Treat it as a project baseline even though it is AAA. https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html and https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion
- For the 3-D flip: under reduce, swap the rotation for an instant switch or a short cross-fade (opacity only, under 150 ms), instead of removing the state change. State change and `inert` toggling must still happen, and must not depend on `transitionend` (that event never fires when the transition is 0 s or `display:none`). Drive `inert` from JS state, not from the animation end.
- For reveal in an accordion style variant, skip height animations the same way.
- Tailwind: `motion-reduce:` variants are the project-native way to apply this (`motion-reduce:transition-none`, `motion-reduce:transform-none`). https://tailwindcss.com/docs/hover-focus-and-other-states#prefers-reduced-motion
- Reduced motion does not affect audio. Do not tie audio to the animation.

## 6. Retrieval practice evidence (brief)

- **Testing effect / retrieval practice.** Trying to recall an answer before seeing it produces better long-term retention than re-reading or re-listening. Roediger and Karpicke 2006, Psychological Science. https://doi.org/10.1111/j.1467-9280.2006.00012.x and a review: Dunlosky et al. 2013, practice testing rated "high utility". https://doi.org/10.1177/1529100612453266
- **Self-check works when recall is attempted, not when the answer is just peeked.** The benefit comes from the effortful attempt. UI implications: the answer should be hidden by default, the Reveal action should require a deliberate press (not hover), and a prompt line such as "Say it out loud, then reveal" helps convert reveal into an attempt. Learners who reveal at once get no benefit, and the widget cannot force it (no microphone by design). This is a known limit of unmarked self-testing, plus learners' calibration is imperfect (they tend to judge "I knew that" generously after seeing the answer), which is the usual argument for a self-rating or, better, spaced scheduling later. Spec 3 and `learner-interface-features-4-flashcards` own that.
- **Production effect.** Saying a word aloud makes it more memorable than reading it silently. MacLeod et al. 2010, J. Exp. Psychol. Learn. Mem. Cogn. https://doi.org/10.1037/a0018424 (and the review by Fawcett 2013, https://doi.org/10.1037/a0030420 ). The effect is for aloud, and also, in some studies, mouthing or whispering, so "say it aloud" can be offered with "or whisper/mouth it" for shared spaces such as an office or classroom, without losing the benefit.
- **Feedback with the answer.** Playing the correct pronunciation right after the attempt gives immediate corrective feedback, and replay allows repeated "listen, then say again" shadowing. The Hide control to retry matches the "successive relearning" practice (repeat retrieval across a session), which the evidence favours over single exposure. Dunlosky et al. above.
- **Pitfalls to design against:** answer visible before the attempt (any leaking through `title`, alt text, or the live region on page load, so keep the answer text out of AT until revealed); a shuffle control (Open until the spec) is supported by the interleaving and order-effect literature, since a fixed order lets learners cue on position, but it is a nice-to-have.

## 7. Design takeaways for the spec

1. Reveal is a `<button>`. Use `aria-expanded` + `aria-controls` if a single toggle, or two plain buttons (Reveal, Hide) with no pressed/expanded state, but never `aria-pressed` for this.
2. Hide the answer with `inert` (or `hidden`), set from JS state, not from animation events. Do not use `aria-hidden` without `inert`.
3. Pick one announcement route, live region or focus move, and write the respelling into it. Move focus to the replay control or answer on reveal, and back to Reveal on Hide.
4. Play on the click synchronously from a pre-rendered `<audio>`. Do not wait on HTMX or fetch. Handle the `play()` rejection and drive UI state from media events. Replay resets `currentTime`.
5. Implement one-at-a-time with a capture-phase `play` listener on `document`, and pause the clip on Hide and on card flip. Confirm `c-audio` (spec 1) does this and the Reveal path goes through it.
6. For the flashcard fix, use `pointer-events: auto` on the visible face's controls, `inert` on the hidden face, and a `closest('button, a, audio')` guard in the flip handler rather than `stopPropagation` in `c-audio`. Avoid `role="button"` on the whole card, to stay clear of axe `nested-interactive`.
7. Honour `prefers-reduced-motion` with `motion-reduce:` utilities, with a state change that does not depend on `transitionend`.
8. Test list: Safari iOS (gesture unlock, range requests, flip hit-testing), Firefox autoplay, Chrome; NVDA/VoiceOver announcement and overlap with the clip; keyboard-only flow Tab, Enter/Space for reveal, replay, hide, with focus never lost.
9. Copy: prompt line "Say it out loud, then reveal" (the production effect and retrieval attempt); mention that a whisper works.
