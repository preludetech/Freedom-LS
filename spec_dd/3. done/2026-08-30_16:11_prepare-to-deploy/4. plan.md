# Implementation plan 2: the updated app-repo contract

Implements the changes `1. spec.md` deferred to the infrastructure repo. `2. plan.md` built this
feature against the contract as it stood on 2026-08-28; this plan carries the answers that came
back on 2026-08-30 onto the same branch.

Everything here is TDD. For each task, write the named tests first, watch them fail, then write the
code. One task at a time.

---

## Why this plan exists

Three code-review findings could not be settled inside FLS, so they went to the infrastructure repo
and sat in the spec's Open questions. Two commits to
`/home/sheena/workspace/first_class/infrastructure` answered all three.

`287e5a0`, EDGE-12. The nested `AXES_LOCKOUT_PARAMETERS` stays, and the clause now requires a
failure rate limit layer above it. A lockout lasts an hour, so it keys on the account and the
address together. A failure rate limit lasts minutes, so it keys on each of those alone. The clause
also corrects its own old reasoning about the cache: axes runs on the database handler and its
counters are rows in Postgres, so what makes `CI-14` load-bearing is allauth's counters, not axes'.

`925eb07`, COMPOSE-8. Housekeeping gains a ninth bound property: it marks failed, and reports, any
task still claimed more than an hour after a worker took it. The task is never requeued. Separately,
a late-task finding no longer withholds the housekeeping heartbeat, because a stopped worker is not
a fault in housekeeping. The commit also names SIGTERM draining as a bound property of `run_worker`,
which FLS already satisfies but does not test.

CI-18 is still open and this plan does not touch it. The contract's runbook still invokes
`setup_initial_prod_data` with no arguments while FLS's command requires `admin_email`.

### Facts checked against the installed packages

- allauth 65.15.1 merges `ACCOUNT_RATE_LIMITS` over its defaults with `ret.update(rls)`
  (`allauth/account/app_settings.py:303`), so a partial dict keeps every other limit.
- allauth's `login_failed` default is computed from the deprecated `ACCOUNT_LOGIN_ATTEMPTS_LIMIT`
  and `ACCOUNT_LOGIN_ATTEMPTS_TIMEOUT` and evaluates to `"10/m/ip,5/300s/key"`
  (`allauth/account/app_settings.py:266-270`). `parse_duration` maps `5m` to `300.0`
  (`allauth/core/internal/ratelimit.py:52-64`), so `"10/m/ip,5/5m/key"` is the same limit stated
  in the contract's spelling.
- Defining either deprecated setting raises an allauth check warning, on `hasattr` alone
  (`allauth/account/checks.py:134-141`).
- Over the limit, `pre_authenticate` raises a `ValidationError`
  (`allauth/account/adapter.py:719-728`) carrying "Too many failed login attempts. Try again
  later." The login form redisplays. There is no 429 and no lockout page.
- `DBTaskResult` has no `last_attempted_at` column. `claim()` writes `status=RUNNING` and
  `started_at=timezone.now()` in one save, so `started_at` is the only record of when a worker took
  a row.
- `set_failed(exc)` needs an exception instance. `get_exception_traceback` is
  `"".join(format_exception(exc))` (`django_tasks/utils.py:45`), and on an instance that was never
  raised that yields one line, the class path and the message, with no frames. The message is the
  whole artefact.
- `prune_db_task_results` filters `finished_at__lte=now() - timedelta(days=min_age_days)` with
  `min_age_days` defaulting to 14, over `finished()` only. A row closed by the reap is 14 days from
  being prunable, so no ordering constraint exists between the two steps.
- `db_worker`'s `configure_signals()` installs handlers for SIGINT, SIGTERM and SIGQUIT; the first
  signal clears `self.running` and, when no task is in flight, exits immediately
  (`django_tasks_db/.../db_worker.py:56-79`).

### Constraints that shape the code

- Type hints on every function, no `Any`, no `# type: ignore`, no new abstract base class.
- `DTZ` is on: `django.utils.timezone.now()`, never `datetime.now()`.
- `T20` is on outside tests: no `print()`.
- mypy runs with `warn_unreachable`, so a branch that narrows `datetime | None` where the value is
  always set reads as dead code. Interpolate `started_at` directly rather than calling
  `.isoformat()` behind a guard.
- `pytest` runs with `--disable-socket` and a 73% coverage gate.
- Catching a real `DatabaseError` inside pytest's wrapping transaction poisons that transaction, so
  the per-row failure test patches `set_failed` rather than provoking a constraint violation.

## Task 1: the failure rate limits above the lockout

**Files:** `config/settings_base.py`, new `freedom_ls/accounts/tests/test_login_rate_limit.py`.

FLS already meets the rest of the rewritten clause. `AXES_LOCKOUT_PARAMETERS` is nested,
`AXES_CLIENT_IP_CALLABLE` and `AXES_RESET_COOL_OFF_ON_FAILURE_DURING_LOCKOUT` are set,
`ACCOUNT_PREVENT_ENUMERATION` is `True`, `ALLAUTH_TRUSTED_PROXY_COUNT` is deliberately unset, and
`ACCOUNT_RATE_LIMITS = False` sits in `config/settings_dev.py:61` and nowhere else, which is where
the clause says that value belongs.

The gap is that `login_failed` is inherited rather than stated. Today it comes from allauth's
computed default, which is derived from a deprecated pair and can move under a version bump.

### 1a. State the limit

`config/settings_base.py:404`, into the existing dict:

```python
ACCOUNT_RATE_LIMITS: dict[str, str] | bool = {
    "signup": "5/m/ip,3/m/key",
    "login_failed": "10/m/ip,5/5m/key",
}
```

The comment above it says what the lockout cannot do alone. A lockout that needs address and
username together leaves one address free to try five passwords against as many usernames as it
likes, and leaves a large enough set of addresses free to work one account five tries at a time.
Ten failures a minute per address caps the first, five in five minutes per account caps the second,
and neither shuts anyone out for an hour. Say that the value is written out because allauth derives
its default from two deprecated settings. Do not cite the clause number.

### 1b. Tests

New `freedom_ls/accounts/tests/test_login_rate_limit.py`, shaped like `test_signup_rate_limit.py`.

- `test_login_failed_limit_is_stated_rather_than_inherited`. Asserts
  `settings_base.ACCOUNT_RATE_LIMITS["login_failed"] == "10/m/ip,5/5m/key"`. It reads
  `config.settings_base` directly, because the suite runs under `config.settings_dev` where
  `ACCOUNT_RATE_LIMITS` is `False`.
- `test_deprecated_login_attempts_settings_are_unset`. Neither `ACCOUNT_LOGIN_ATTEMPTS_LIMIT` nor
  `ACCOUNT_LOGIN_ATTEMPTS_TIMEOUT` is on `django.conf.settings`. Defining either one raises a check
  warning and silently re-derives `login_failed`.
- `test_failed_logins_from_one_address_are_capped_before_any_lockout`. The behaviour the nested
  lockout cannot provide. Under `override_settings(ACCOUNT_RATE_LIMITS={"login_failed":
  "10/m/ip,5/5m/key"})`, with `cache.clear()` first, post eleven wrong-password logins from one
  client naming eleven different emails. axes never locks, because no address and username pair
  reaches five. The eleventh response is the login form carrying "Too many failed login attempts.
  Try again later.", not a 429 and not the axes lockout template. Takes `mock_site_context`, since
  the per-key half keys on `f"{site.domain}:{login}"`. Marked `ci_only` alongside `django_db`, like
  its sibling, so watching it fail needs `uv run pytest ... -m ci_only`.

## Task 2: housekeeping stops calling itself dead over a stalled worker

**Files:** `freedom_ls/deployment/housekeeping.py`,
`freedom_ls/deployment/management/commands/fls_run_housekeeping.py`,
`freedom_ls/deployment/tests/test_housekeeping.py`.

`run_housekeeping_sweeps()` returns one flat `list[str]` and `handle()` treats every entry the same
way: raise `CommandError`, skip the heartbeat. So a stopped worker turns the housekeeping container
unhealthy while housekeeping is fine. This is the matrix the two functions have to produce between
them:

| Situation | Sentry | Exit code | Heartbeat |
| --- | --- | --- | --- |
| `prune_db_task_results` or `clearsessions` raised | `capture_exception` | non-zero | not touched |
| the reap could not run, or could not close a row | `capture_exception` | non-zero | not touched |
| `READY` tasks late past the window | `capture_message` | non-zero | touched |
| `RUNNING` rows closed past the window | `capture_message` per row | zero | touched |
| all clean | nothing | zero | touched |

### 2a. Split the return value

Three lists, because three things can happen and they are spent differently. A `NamedTuple` in
`housekeeping.py`, which the repo already uses for small value objects and which keeps the fields
named at the call site:

```python
class HousekeepingOutcome(NamedTuple):
    """What one run did, split by who has to act on it.

    sweep_failures are housekeeping's own work not getting done. findings are that
    work getting done and turning up something wrong outside this container. notes
    are what the run put right by itself. Only sweep_failures withhold the
    heartbeat; sweep_failures and findings both force a non-zero exit; notes force
    nothing.
    """

    sweep_failures: list[str]
    findings: list[str]
    notes: list[str]

    def failure_message(self) -> str:
        """The CommandError text, labelled so the two exit causes stay apart."""
```

`failure_message()` joins each non-empty list under its own label, `Sweep failures:` and
`Findings:`. The labels live beside the fields they describe so the two cannot drift, and they are
what satisfies "the failure message names which": an operator reading stderr can tell whether the
container's own probe went red or whether housekeeping is reporting on the worker.

A bare `tuple[list[str], list[str], list[str]]` was the alternative and is worse. The whole point of
this change is that the three lists are not interchangeable, and positional unpacking hides exactly
that. Note that a populated NamedTuple is always truthy, so nothing may test `if outcome:`; every
branch tests a named field.

`run_housekeeping_sweeps() -> HousekeepingOutcome`. Prune and `clearsessions` failures go to
`sweep_failures`, the late-unpicked count goes to `findings`, and the reap (Task 3) contributes a
note on success and a `sweep_failures` entry when it could not do its work.

### 2b. Rewrite `handle()`

```python
outcome = run_housekeeping_sweeps()

for note in outcome.notes:
    self.stdout.write(note)

if not outcome.sweep_failures:
    touch_heartbeat(config.HOUSEKEEPING_HEARTBEAT_PATH)

if outcome.sweep_failures or outcome.findings:
    raise CommandError(outcome.failure_message())

self.stdout.write("Housekeeping complete.")
```

The touch has to precede the raise. The other order leaves the "a finding keeps the heartbeat"
property silently unreachable, and no existing test would catch it, which is why the new regression
test asserts `heartbeat.exists()` after `pytest.raises`.

### 2c. Tests

Existing tests change rather than go:

- `test_prune_failure_raises_and_leaves_heartbeat_untouched` and
  `test_clearsessions_failure_raises_and_leaves_heartbeat_untouched` keep their assertions.
- `test_late_unpicked_task_reported_to_sentry_and_returned_as_failure` becomes
  `..._returned_as_a_finding` and asserts on `outcome.findings`, plus the new part,
  `outcome.sweep_failures == []`.
- The independence tests read `outcome.sweep_failures`.
- `test_both_sweep_failures_each_reach_sentry` should still see two captures, because the reap runs
  against an empty table and adds none. It is the one existing assertion the fourth step could
  perturb, so check it rather than assume it.

New:

- `test_late_task_finding_raises_but_still_touches_heartbeat`. The regression test for this task.
  One `READY` row two hours old, both sweeps clean: `pytest.raises(CommandError)` and then

  `unpicked`.

  `not heartbeat.exists()`. A sweep failure outranks a finding.

## Task 3: close tasks orphaned in RUNNING

**Files:** `freedom_ls/deployment/housekeeping.py`, `freedom_ls/deployment/config.py`,
`freedom_ls/deployment/tests/test_housekeeping.py`, `freedom_ls/deployment/tests/test_config.py`.

A worker killed mid-task, by its own watchdog, the OOM killer, or a deploy recreating the container,
leaves its row claimed and `RUNNING`. `DBTaskResult.objects.ready()` offers only unclaimed work, so
no worker retries it. `find_late_unpicked_tasks` filters `status=READY`, so nothing reports it. The
prune deletes only finished rows, so nothing removes it. The row is lost without a word.

### 3a. The window

A new entry on `DeploymentSettings`, not a reuse of `HOUSEKEEPING_UNPICKED_TASK_MAX_AGE_SECONDS`:

```python
HOUSEKEEPING_ORPHANED_TASK_MAX_AGE_SECONDS: int = 3600
```

The two windows are both an hour today and measure different things, and only one of them writes.
The unpicked window decides when you get told. This one marks rows failed, so a value below the
longest legitimate task runtime closes live work and reports a worker death that did not happen.
A deployment with long tasks has to raise this window alongside `WORKER_HEARTBEAT_MAX_AGE_SECONDS`,
which is already the ceiling on how long a task may run before the watchdog kills the worker
holding it. One shared setting would force that operator to choose between reaping live work and
going blind to a stalled queue. The comment on the setting records that relationship. Add the
default assertion to `test_config.py` beside the existing four.

### 3b. The exception

```python
class OrphanedTaskError(RuntimeError):
    """Recorded on a task result housekeeping closed on the task's behalf.

    Never raised. set_failed needs an exception instance to record, and the class
    path it stores is what tells an operator the row was closed by the sweep rather
    than by the task's own code.
    """
```

A purpose-built class rather than a builtin. `exception_class_path` is the only machine-readable
field separating "the task failed" from "housekeeping gave up on the task", and a `TimeoutError`
there is indistinguishable from a task that genuinely timed out. `RuntimeError` as the base matches
`IconResolutionError`.

### 3c. The finder

```python
def find_orphaned_running_tasks(max_age_seconds: int) -> QuerySet[DBTaskResult]:
    """RUNNING task results claimed more than max_age_seconds ago.

    claim() is the only writer of started_at and sets RUNNING in the same save, so
    started_at is how long a worker has held the row; there is no last_attempted_at
    column to consult. A NULL started_at never satisfies the comparison, which is
    the right answer for a row no worker ever claimed. Every queue, no scoping.
    """
    cutoff = timezone.now() - timedelta(seconds=max_age_seconds)
    return DBTaskResult.objects.running().filter(started_at__lte=cutoff)
```

`.running()` is upstream's own predicate, so this function adds one clause and no duplication.
`find_late_unpicked_tasks` cannot do the same with `.ready()`, which bakes in `run_after__lte=now()`
rather than the cutoff, so leave that function alone.

### 3d. The reap

```python
class OrphanReapResult(NamedTuple):
    """How the orphan sweep went: rows closed, and rows the database would not close."""

    marked_failed: int
    left_running: int


def mark_orphaned_running_tasks_failed(max_age_seconds: int) -> OrphanReapResult:
    """Close every orphaned RUNNING row as FAILED. Bookkeeping, not recovery."""
```

- Materialise with `list(...)` before the loop starts changing the status the queryset filters on.
- Per row, `set_failed(OrphanedTaskError(...))`. Because `format_exception` gives one line and no
  frames, that message is everything the row will say. It names when the row was claimed, which
  workers held it, that housekeeping marked it failed, and that the task was not run again and not
  requeued. Interpolate `started_at` with an f-string rather than calling `.isoformat()`, which
  would need a narrowing branch mypy reads as dead.
- Per row, one `sentry_sdk.capture_message(...)` naming only the task path, with the row id,
  `started_at` and `worker_ids` attached through `sentry_sdk.new_scope()`. Sentry groups on the
  message, so a task that dies its worker every night becomes one recurring issue rather than a new
  one per run.
- Each row's write sits in its own `try`/`except DatabaseError`, which captures and counts before
  moving to the next row. One row the database refuses does not cost the rest their sweep.

The reap never requeues. Resetting the row to unclaimed is a one-line change and it is wrong: the
row records that the task started, not how far it got, so a task killed between sending an email and
recording that it sent one sends it twice. Closing the row says the true thing and makes the row
prunable, and the Sentry issue puts a person in front of the decision the automation cannot make.

### 3e. Wire it in

A fourth step in `run_housekeeping_sweeps()`, after the two sweeps and the late check, in its own
`try`/`except SWEEP_FAILURES`. A failure in the query itself lands in `sweep_failures`; so does a
non-zero `left_running`, because a row the reap could not close is housekeeping's own work not
getting done. A non-zero `marked_failed` is a note, not a failure. The sweep worked; what it found
is an application failure and it reaches the operator through Sentry.

Order does not matter, and a comment should say why rather than leave the next reader to work it
out: the prune deletes finished rows older than its fourteen-day default, and a row this step closes
has `finished_at` of now, so the same run's prune cannot delete the evidence. A prune given
`--min-age-days=0` could, which is the reason the note is worth writing down. The reap goes last so
the three existing blocks and their tests stay untouched.

## Task 4: pin the worker's SIGTERM drain

**Files:** `freedom_ls/deployment/tests/test_worker.py` only.

The contract now binds a property FLS already satisfies: on SIGTERM the worker stops claiming new
work and exits once the task in hand returns. `fls_run_worker` calls `configure_signals()`,
`HeartbeatWorker` overrides only `run()` so `shutdown` and `configure_signals` are upstream's, and
the copied loop keeps both `while self.running` and the guard that skips the sleep after an
interrupt.

Nothing holds that true. The copied loop is what a version bump breaks silently, so:

- `test_heartbeat_worker_inherits_upstream_signal_handling`. `HeartbeatWorker.shutdown is
  Worker.shutdown` and the same for `configure_signals`.
- `test_fls_run_worker_configures_signals_before_running`. Patch `HeartbeatWorker`, assert the
  order.
- `test_run_claims_no_work_once_running_is_cleared`. Build a `HeartbeatWorker` with
  `startup_delay=False`, clear `running`, call `run()`. It returns without querying and without
  touching the heartbeat, which is what a drained SIGTERM looks like from the loop's side.
- Close the gap in `test_fls_run_worker_processes_every_queue` while here: assert `batch=False` and
  `max_tasks=None` too, the two values the `HeartbeatWorker` docstring says the per-iteration
  heartbeat depends on.

`stop_grace_period: 60s`, the other half of `925eb07`, is a compose key and belongs to the
downstream repo.
