## How the clauses split

The contract's own README states the split explicitly: "The infra repo owns the box. Each
app repo owns the app on the box." Reading all six files, the clauses fall into three buckets:

1. **Infra repo's** — the box, the `edge` proxy config, the vault, `roles/*`. Not reviewed
   further here (e.g. EDGE-1, EDGE-2, EDGE-4, EDGE-5, EDGE-6, EDGE-9, CI-9, CI-10, CI-16, all
   of the "What the box gives you" / "Do not build these" tables in `README.md`).
2. **Downstream app repo's** (First-Class-LMS, the concrete Django project that installs FLS,
   not FLS the library) — `Dockerfile`, `docker-compose.yml`, `.env.example`, `ci.yml`,
   `deploy.yml`, the SSH keypair. Most of `dockerfile.md`, `compose.md` and `deploy_ci.md` is
   this bucket: image build mechanics, container names, published ports, CI sequencing. FLS
   ships no Dockerfile, compose file or `.env.example` of its own (confirmed: `Glob` for
   `Dockerfile*`, `docker-compose*.yml`, `.env.example` at this repo's root all returned no
   matches). FLS's job here is to make those artifacts *possible* to write correctly — i.e. to
   expose the right settings, commands and checks — not to write them itself.
3. **Needs something from FLS** — settings, views, management commands, or checks that only
   FLS's own Python code can provide, because the downstream repo just imports and configures
   FLS. This is the category below.

## Things FLS does that could conflict with the contract, or that are footguns for a downstream author

- **The concrete-template's reference `docker-compose.yml` bundles its own Caddy.** `/home/sheena/workspace/lms/freedom-ls-concrete-template/docker-compose.yml:67-80` defines a `caddy` service publishing `80:80`/`443:443` with its own `Caddyfile` bind mount. This is not FLS's own package code, but it is the concrete deployment template FLS ships as a worked example for a downstream author to copy — and it is a direct, named violation of `EDGE-5` ("Never ship an edge project... No `caddy` service in your compose file") and `COMPOSE-4` ("No service publishes a port"). Anyone building First-Class-LMS's actual compose file by copying this template would carry the violation forward unless they knew to strip it. Also note: this same compose file's `web` healthcheck (`docker-compose.yml:31-32`) uses a bare `urllib.request.urlopen(...)` with no `Accept` header at all, which per the verified `COMPOSE-8` finding above would hit the *default* `Accept` for Python's `urllib` (`*/*` unless set), landing on the HTML-render / `Site.DoesNotExist` 500 path rather than JSON — i.e. the template's own healthcheck is written in a way that would break on a fresh, unseeded stack. (This is the template repo's compose file, separate from any actual First-Class-LMS compose file, which I did not have access to and could not verify.)
- **`config/wsgi.py:14`** defaults `DJANGO_SETTINGS_MODULE` to `"config.settings"`, a module that does not exist in this repo (only `settings_base`, `settings_dev`, `settings_prod` exist). `IMAGE-8` requires `DJANGO_SETTINGS_MODULE=config.settings_prod` to be baked into the image `ENV`, which overrides this default in any correctly-built image, so this is likely inert in practice — flagging as **unverified** whether any code path (e.g. a bare `manage.py` invocation without the env var set) actually hits this broken default in a deployed container.
- **`config/settings_prod.py:90-93`** (this repo's own top-level settings, as distinct from the concrete-template's) still passes `log_dir=BASE_DIR / "logs"` into `build_logging_config()`, with an explicit comment: "log_dir is temporary: drop it once container-level log size/rotation caps exist, to move to stdout-only." This writes rotating log files to local disk at runtime — under `IMAGE-2`'s non-root `uid 10001`, that directory must exist and be writable, and per `COMPOSE-11` ("No bind mounts of repo files") it cannot be a bind mount, so it would need its own named volume or ephemeral container storage that a redeploy destroys — plus it duplicates `roles/docker`'s daemon-wide `json-file` cap that `COMPOSE-9` says the app doesn't need to reimplement. The concrete-template's own `settings_prod.py:93-98` has already dropped this (`build_logging_config()` with no `log_dir`, explicitly citing the same reasoning), so the fix pattern already exists downstream; it's just not applied to this repo's own top-level `config/settings_prod.py`. **This repo's `config/settings_prod.py` is presumably a demo/reference scaffold rather than what a downstream project deploys as-is** — I could not verify from the repo alone whether this top-level `config/` is ever deployed directly or exists purely for local development/testing; flagging as unverified.
