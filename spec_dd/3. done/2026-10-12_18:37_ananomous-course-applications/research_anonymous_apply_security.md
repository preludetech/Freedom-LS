# Research: security, abuse and identity risks of anonymous course application (email + name, no password)

Scope: web research plus a light read of this repo. Items marked (verified: URL) were fetched this session; items marked (background) come from my prior knowledge of the cited source and were not re-fetched, so treat them as lower confidence.

## 0. What this project does today (codebase facts)

- `config/settings_base.py` allauth: `ACCOUNT_EMAIL_VERIFICATION = "mandatory"`, `ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION = True`, `ACCOUNT_LOGIN_METHODS = {"email"}`, `ACCOUNT_PREVENT_ENUMERATION = True`, signup fields `email*, password1*, password2*, first_name*, last_name`.
- `ACCOUNT_RATE_LIMITS = {"signup": "5/m/ip", "login_failed": "10/m/ip,5/5m/key"}`; disabled in dev. Comment notes the signup limit has no `key` scope (allauth's signup view passes no key). No other rate-limit keys (e.g. `confirm_email`, `request_login_code`, `reset_password`) are set explicitly, so allauth defaults apply.
- Login by code and email verification by code are NOT enabled (no `ACCOUNT_LOGIN_BY_CODE_ENABLED`, no `ACCOUNT_EMAIL_VERIFICATION_BY_CODE_ENABLED`). No CAPTCHA or honeypot setting found in `config/`.
- `django-axes` is installed (5 failures, 1h cool-off, lockout on `[ip, username]` and `username`); IP comes from `freedom_ls.accounts.utils.get_client_ip` honouring `TRUSTED_PROXY_IP_HEADER` (default None -> `REMOTE_ADDR`; wrong behind a proxy).
- `SESSION_COOKIE_AGE` = 2 weeks in prod; cookie Secure/HttpOnly/Lax.
- `accounts.User` (`freedom_ls/accounts/models.py`): `SiteAwareModelBase`, `email = EmailField(unique=True)` - globally unique, not unique per site. `UserManager.create_user` raises if no password (`ValueError("User must have a password")`), so a passwordless user cannot be made with the current manager method; `set_unusable_password()` via the model, or a manager change, would be needed. `UserManager.get_queryset` filters by the site of the thread-local request.
- `LegalConsent` (SiteAwareModel): FK to `User` (CASCADE), `document_type` terms/privacy, `document_version`, `git_hash`, `ip_address`, `consent_method` choices only `signup_checkbox`; append-only; admin read-only; included in user-erasure cascade (`USER_ERASURE_CASCADE_MODELS`). Consent needs a `User` row, so consent captured before an account exists has nowhere to be stored today. Consent is only offered if the site's `SiteSignupPolicy.require_terms_acceptance` is effective and the legal doc resolves. Created in `SiteAwareSignupForm.custom_signup`.
- `registration` skill: post-verification `ADDITIONAL_REGISTRATION_FORMS` gate platform access via middleware; the completion view always saves to `request.user` and forbids `email`/`user` fields (confused-deputy guard). `AccountAdapter.save_user` fires `user.registered` webhook and `record_sign_up` analytics - an inactive/pre-verification user created through the same path would emit these for unverified people.
- `AccountAdapter.is_open_for_signup` honours `SiteSignupPolicy.allow_signups`; an anonymous-apply path must decide whether it respects that switch (it creates a user, so arguably yes).

## 1. Email ownership and pre-hijacking

Threat: an attacker types a victim's email (or an email they will later control) into a no-password form. Whatever is attached to that identity before ownership is proven is a liability.

- Pre-hijacking (Sudhodanan and Paverd, Microsoft, USENIX Security 2022) describes attacks where the attacker acts before the victim creates or uses the account. Classes (background; the PDF was not machine-readable here): classic-federated merge (attacker pre-creates a password account with the victim's email; victim later signs up via SSO and the two merge, leaving attacker credentials alive), unexpired session identifier (attacker creates account, keeps a logged-in session; victim "recovers" the account, attacker session still valid), trojan identifier (attacker attaches a second identifier, e.g. their own email/phone, to the pre-created account), unexpired email change (attacker starts an email change to their address, pending link stays valid after the victim takes over), non-verifying IdP. Mitigations stated by the authors: verify email ownership before the account is usable, invalidate all sessions and pending changes/credentials when a password is set or reset or when ownership is first proven, expire unverified accounts, and do not merge accounts on unverified identifiers.
- OWASP Authentication Cheat Sheet: an email may serve as the username only if verified at sign-up; email changes need confirmation on the new address and notification on the old; use time-limited nonces (verified: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- Relevance here: the anonymous flow is a pre-hijacking surface by design. Specific hazards: (a) attacker applies as the victim; staff see an application "from" the victim, and the victim may later be treated as having applied; (b) a user row created for the victim's email with attacker-chosen name, then victim signs up/resets and inherits attacker-supplied profile data and an application; (c) the attacker's browser session stays bound to a draft/user and survives the victim's later claim of the account; (d) attacker pre-sets a name or details to mislead staff or put defamatory text under the victim's address.

What must be verified, and when (options with consequences):
- Before staff see/act on the application: strongly recommended. Staff review is the point at which the application "counts" and staff may email, enrol or grant access; unverified applications create phishing/impersonation and spam load for staff and may trigger emails to the victim. Cheap form: the final submit step (or a step before it) requires entering a code emailed to the address; unverified drafts stay invisible to staff.
- Before the application is created as a submitted record: same as above; draft state may exist unverified, submitted state requires proof.
- Before the person can log in / before any session grants access to account data: mandatory. A passwordless flow that logs a browser in without proof of mailbox control is account creation for an arbitrary email. Verification is also the only thing separating the applicant's browser session from "being" that user, so do not log in on form submit.
- Before data is attached to an existing user: always (see section 2).
- Verification should prove control of the mailbox at the time of submission (a code or single-use link tied to this specific draft and this browser session), not merely that the address is syntactically valid.

## 2. Email already registered: no enumeration, no unverified append

- OWASP: registration must return the same message whether or not the account exists ("A link to activate your account has been emailed to the address provided"), with matching timing and status code; "This user ID is already in use" is the incorrect pattern (verified: Authentication cheat sheet URL above). OWASP Forgot Password cheat sheet gives the same principle for reset: uniform message, uniform timing, rate limiting (background: https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- allauth `ACCOUNT_PREVENT_ENUMERATION = True` already hides existence in signup and reset by always sending an email (verified: https://docs.allauth.org/en/latest/account/configuration.html). `"strict"` additionally lets signup proceed without revealing a collision. This project uses `True`.
- Design consequences for the anonymous apply step:
  - The first step must respond identically for new and existing emails: "We have emailed a code/link to continue". Timing must match: do the user lookup and email send asynchronously or equalise work; avoid revealing via redirect target, flash message, field errors, or step-count differences.
  - The email to an existing user differs in content (e.g. "someone tried to apply; if it was you, log in and apply while signed in" plus a normal login-by-code link), the email to a new address carries the verification. Never apply the typed name or other details to the existing user; existing profile data wins, and typed data is discarded or held only in the draft, applied only after the existing user has proven control and chosen to continue.
  - Because the account owner is not necessarily the person typing, the draft for an existing email must not be readable or submittable until the mailbox is proven; after proof, attach the application to the existing user explicitly (they are now effectively logged in by code).
  - Email-bombing amplification (section 4) is an enumeration side-channel as well as abuse: a per-email send limit must apply uniformly (new or existing) and must not return a distinguishable error when hit.
- Normalisation: Django `normalize_email` only lowercases the domain; the DB unique constraint on `User.email` is case sensitive for the local part in Postgres. An attacker can use `Victim@x.com` vs `victim@x.com`, or plus-addressing/dots, to create look-alike accounts or bypass per-email limits. Decide a canonical form (lowercase whole address) for lookup, limits and uniqueness checks. allauth's `EmailAddress` lookup is case-insensitive; the User model unique constraint is not.

## 3. Holding an in-progress anonymous application

Option A: session-keyed draft (no User until verified/submitted)
- Pros: no account, no unverified PII in the user table, no webhooks/analytics for non-users, no pre-hijacking account to claim, no enumeration at the point of data entry (uniqueness is not touched until later). Abandonment cleanup = session/draft expiry.
- Cons: server-side draft must be stored somewhere (DB row keyed to session key or a random draft token; or serialised in the session). Multi-page forms with file uploads fit poorly in cookie-backed sessions. Draft lost if session cookie lost or after expiry; user cannot resume on another device until verified (acceptable). Mid-flow login: Django `login()` cycles the session key and keeps data when a user logs in on an anonymous session only if it flushes selectively; `login()` calls `cycle_key()` (keeps data) when the session has no different user, so draft data in the session is retained, but a DB-keyed draft referencing the old session key is orphaned - key drafts by a draft token stored in the session, not by `session_key`. (Django docs on sessions and `login()`: https://docs.djangoproject.com/en/stable/topics/http/sessions/ , background.)
- Session fixation: always rotate the session key on privilege change (anonymous -> verified/logged in). Django `login()` does this; allauth login by code does too via the normal login. Never let a pre-authentication session ID carry over unchanged (OWASP Session Management cheat sheet, background: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Option B: inactive / unusable-password User created up front
- Pros: reuses `User`, `LegalConsent` (needs a user FK), registration forms, existing models and admin.
- Cons: this is exactly the pre-hijacking surface (section 1); consumes the globally unique `User.email` (an attacker can squat arbitrary emails, blocking or confusing the real owner's later signup; victim sees "already registered"; with `ACCOUNT_PREVENT_ENUMERATION` the victim's own signup silently sends an email instead); user rows for unverified people appear in staff user lists, webhooks (`user.registered`), and analytics; cleanup of unverified users is required (a reaper job) and cascades LegalConsent (erasure path already supports it); `UserManager.create_user` currently refuses no-password. Mitigations if chosen: `is_active=False` plus `set_unusable_password()`, no `EmailAddress.verified`, no events fired until verified, expiry job, claim step invalidates all sessions and pending email changes, and never merge with an existing user.
- Hybrid: session/token draft until the mailbox is verified, then create or find the User inside the verification handler (the point at which email control is proven). This keeps unverified data out of `User` and puts consent into `LegalConsent` at the moment a user exists (consent evidence recorded earlier, e.g. in the draft with doc version, git hash, timestamp and IP, then written to `LegalConsent` at user creation - though the model's `timestamp` is `auto_now_add`, so the original click time would be lost unless stored separately).

Draft expiry: define a hard TTL (e.g. days) independent of the 2-week session cookie; delete the draft row and uploaded files together. If the session cookie expires, the draft becomes unreachable (orphaned) - a scheduled purge must key off draft `created/updated_at`, not off session existence, otherwise orphans persist forever. If the draft's token is the only handle, resumption after expiry requires starting again; tell the user.

File uploads by anonymous users
- Risks: storage exhaustion, malware hosting, content-type spoofing (HTML/SVG/JS served from the site origin -> stored XSS), path traversal via filename, parser exploits in image/PDF libraries, illegal content, using the site as a free file host if URLs are guessable and public, and PII leakage if files are served from a public media path.
- Controls (OWASP File Upload cheat sheet, background: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html): allowlist extensions and sniff content type; cap size per file and per draft and total per IP/session; rename to random names; store outside the web root or on private storage served via authenticated view with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`; virus scan if feasible; never serve from a public MEDIA path before review; delete with the draft.
- Consider requiring email verification before accepting any file upload (so there is an accountable address), or deferring upload steps behind the verification step. Decision for the design: where in the step order does verification fall relative to uploads?

## 4. Bot and spam abuse

- Attack classes: mass fake applications (staff review queue flood); email bombing a victim (attacker submits the victim's address repeatedly to make the system send verification/notification emails); using the form as a mail relay for attacker-influenced content (name field injected into email body, e.g. phishing text or links in "name" - the system's own domain/reputation); disk fill via uploads; resource exhaustion; harming sender reputation (blacklisting by mailbox providers, which breaks real signup mail).
- Rate limits: per-IP limits are weak (shared NAT, botnets); per-email-address limits are the key one against email bombing: e.g. max N mails per address per hour regardless of IP, uniform response when hit (no enumeration). OWASP says lockout counters should be per account not per source IP (verified: Authentication cheat sheet URL). Existing `signup: 5/m/ip` shows the project already accepts per-IP throttling; allauth's signup rate limit does not apply to a custom view, so the custom step needs its own limits (django-allauth exposes `allauth.core.ratelimit` helpers for custom views; background - verify before relying). Also limit per site (tenant), since sender reputation and the review queue are per tenant.
- IP correctness: rate limiting by `REMOTE_ADDR` behind a proxy collapses all users into one bucket; `TRUSTED_PROXY_IP_HEADER` must be set correctly in production (the project has a check in `accounts/checks.py`).
- Honeypot: cheap, accessibility-neutral, stops naive bots only; add a minimum time-to-submit token. Does not stop targeted attackers or email bombing.
- CAPTCHA: stronger against bots but costs conversion and accessibility (WCAG) and adds a third-party processor to privacy disclosures (GDPR/POPIA transfer). OWASP: CAPTCHA is defence in depth, slows and raises cost, not complete prevention; may be shown only after suspicious behaviour (verified: Authentication cheat sheet URL). Privacy-friendlier proof-of-work or self-hosted options exist but are not evaluated here. A tenant-configurable switch (off/honeypot/CAPTCHA) is plausible; the CAPTCHA provider is a per-project dependency, not something to hardcode in a generic plugin (per CLAUDE.md plugin rules).
- Verification email content must not echo free-text attacker input (name) unescaped, and should state the requesting IP/site so a recipient can recognise an unsolicited mail; include no clickable "approve on behalf" action that works without mailbox proof.
- Make the verification code single-use, short TTL, limited attempts (allauth defaults below), bound to the draft and browser session so a code mailed to a victim is useless to an attacker with a different session.

## 5. Privacy and consent

- Before an account exists the system collects name, email, application answers and possibly files. Under GDPR (art. 5(1)(c) minimisation, 5(1)(e) storage limitation, art. 6 lawful basis, art. 13 information at collection) and POPIA (section 9-14 processing limitation/minimality, section 18 notification at collection, section 14 retention) the visitor must be told, at the first step, who is collecting, why and for how long, and a basis must exist. A common basis is steps taken at the data subject's request (applying) rather than consent, but this project's T&C/Privacy are clickwrap-recorded (verify: legal advice needed; background sources https://gdpr-info.eu/art-5-gdpr/ and https://popia.co.za/).
- Current mechanism: clickwrap `accept_terms`/`accept_privacy` at the allauth signup form, written to `LegalConsent` with user FK, doc version, git hash, IP, method `signup_checkbox`. For an anonymous first step: the checkboxes must appear there (policy `require_terms_acceptance`), and the evidence must be recorded. Gaps: no `User` -> no FK target; `consent_method` has only `signup_checkbox` (a new method value such as an application-step value would need a model change and migration; the model is append-only); `timestamp` is `auto_now_add`, so deferring writing until user creation loses the true click time unless held separately in the draft.
- Consent given by the typist is not proof the mailbox owner consented; the record is "someone at this IP accepted"; it becomes attributable only after email verification. Hence consent evidence should be treated as pending until verification, and the system should not treat unverified typed data as the data subject's own.
- Data minimisation: the first step should collect only what is required to verify and to contact (email, name); every extra "usual signup detail" collected before verification increases unverified-PII exposure. Defer optional details until after verification.
- Retention: define and enforce a purge for abandoned drafts (and uploaded files) with a stated period in the privacy notice; log the purge? (project says no logging unless asked). Unverified drafts should have a shorter life than submitted applications. Rejected/withdrawn applications also need a retention rule. Erasure requests: the existing user-erasure cascade (`USER_ERASURE_CASCADE_MODELS`) covers `LegalConsent` for users; anonymous drafts belonging to no user need an erasure path keyed by email.
- Third parties: CAPTCHA, email delivery and any analytics (`record_sign_up`) must not receive unverified applicant data without disclosure.
- Wrong-person risk: a mailbox owner who receives a verification email for something they did not request is receiving processing of their address; the email should offer a clear "not me" path and the data not retained.

## 6. django-allauth specifics (verified: https://docs.allauth.org/en/latest/account/configuration.html)

- Login by code: `ACCOUNT_LOGIN_BY_CODE_ENABLED` (default False) - user logs in with only an email, code emailed; `ACCOUNT_LOGIN_BY_CODE_MAX_ATTEMPTS` default 3; `ACCOUNT_LOGIN_BY_CODE_TIMEOUT` default 180s; `ACCOUNT_LOGIN_BY_CODE_REQUIRED` can force code on all logins; `ACCOUNT_LOGIN_BY_CODE_SUPPORTS_RESEND` default False.
- Email verification by code: `ACCOUNT_EMAIL_VERIFICATION_BY_CODE_ENABLED` (False), max attempts 3, timeout 900s, resend flag default False. Code verification is not a link, so it is bound to the browser session that requested it (good against a link forwarded or scanned by mail-security bots; link prefetch by corporate scanners can consume or confirm single-use links).
- `ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION`: logs in after confirming by link, only if confirmed in the same browser right after signup; does not apply to code-based verification. This project sets it to True, so a link flow here logs the clicker in: whoever holds the link (including a mail scanner or an attacker with mailbox access, which is expected, but not an attacker without it) is logged in. Check cross-browser behaviour in the design.
- `ACCOUNT_PREVENT_ENUMERATION` True (project) / `"strict"`.
- Passwordless accounts: Django supports `user.set_unusable_password()`; allauth login-by-code works for users with unusable passwords and does not require a password. allauth signup form requires passwords per `ACCOUNT_SIGNUP_FIELDS` (`password1*`/`password2*` here); dropping them is a signup-form change and would also affect the normal sign-up page unless separate. Note `ACCOUNT_LOGIN_BY_CODE_ENABLED` would turn on passwordless login site-wide, which is a security-posture change for all users (and conflicts with axes `username` lockouts only partly).
- Rate limits: allauth ships keys for login code requests, confirmation and reset; custom views must apply limits themselves (this project's own settings comment says the signup scope has no key). The allauth rate-limit page lists the keys and defaults (https://docs.allauth.org/en/latest/account/rate_limits.html - background, not fetched).
- allauth does not provide a draft/application concept; it creates the user at signup, so any "no user until verified" design builds its own draft model and calls allauth/Django to create the user on verification.
- The `AccountAdapter.save_user` hook fires webhook and analytics - these are tied to allauth signup; a custom creation path must decide whether to fire them (and only after verification).

## 7. Multi-site implications

- `User` is `SiteAwareModelBase`, but `email` is `unique=True` globally. An email registered on site A blocks creating the same email on site B (IntegrityError, or via ORM site-filtered lookup a "does not exist" that then fails on insert). The site-filtered `UserManager.get_queryset` means a lookup in site B for an email registered on site A returns nothing, then `create` collides. The anonymous flow must resolve this case without leaking that the email exists on another tenant (an enumeration across tenants, and a privacy leak about which organisation a person uses). Check current behaviour of allauth signup for that case before assuming it is handled.
- Drafts, verification codes, rate-limit keys, and uploaded files must all be site-scoped (SiteAwareModel for the draft; cache keys include site) - otherwise an application started on site A could be completed or retrieved on site B via the same session cookie/domain, and one tenant's attacker burns another's limits.
- Sessions: cookie domain/naming per host; ensure a draft token is rejected on a different site's host.
- Email: the verification mail must use the requesting site's branding/sender (the adapter already does via `get_cached_site`); email bombing harms that tenant's sender reputation.
- Legal docs and `SiteSignupPolicy` are per site: the consent shown at step one must be the current site's document, recorded with that site.
- Staff are per site: the review queue only shows the tenant's applications; staff roles must not see other sites' drafts.
- `SiteSignupPolicy.allow_signups` per site: decide whether anonymous apply is blocked when signups are closed.

## Implications for this idea

Security requirements any design must meet:
1. Unverified email must never grant a session, create a visible/active account, or fire user-created side effects (webhooks, analytics, staff lists).
2. Mailbox control must be proven (code or single-use link bound to the draft and the browser session) before staff can see the application and before any data is attached to a user; codes must be single-use, short TTL, attempt-limited.
3. The response to the first step must be identical (content, status, timing, side effects visible to the client) whether the email is new, already registered on this site, or registered on another site.
4. Typed data must never be written into an existing user's account without that user proving mailbox control and choosing to continue; existing profile values win.
5. Session must be rotated on the transition anonymous -> authenticated; verification invalidates other sessions/pending email changes on the claimed account; draft handles must not depend on the pre-login session key.
6. Per-email-address and per-IP and per-site send/creation limits, uniform responses when exceeded, plus a bot-deterrent; email content must not render attacker free text as active content.
7. Uploads by unverified visitors are bounded (size, count, type, quota), stored privately under random names, served only to authorised staff, and deleted with the draft.
8. Terms/Privacy shown and recorded at the first step with version and hash, treated as pending until verified, and attributable to a user afterwards; data collected before verification is minimal.
9. Every draft and upload has a hard TTL and a purge not dependent on session survival; erasure by email must be possible for drafts with no user.
10. All of it is site-scoped.

Decisions the requirements force (not answered here):
- Where does verification fall in the step order: right after the email step (gate everything, including uploads) or at final submit (cheaper for users, riskier for unverified storage)?
- Draft representation: session/token-keyed draft versus up-front inactive User (hybrid recommended by the security trade-offs: draft first, User at verification). The up-front User option requires a squatting/cleanup answer and a change to `UserManager.create_user`.
- How a visitor with an existing account is handled after the uniform response: log in by code then continue as an authenticated applicant (needs login-by-code enabled or a bespoke single-purpose code), or send to normal login; does enabling `ACCOUNT_LOGIN_BY_CODE_ENABLED` site-wide become acceptable?
- What happens to the account/passwordless state afterwards: unusable password until the applicant sets one (and how it is claimed), and whether the normal signup page also becomes passwordless.
- Cross-tenant email collision given globally unique `User.email`: reject uniformly, or change the uniqueness model (large change).
- Email canonicalisation rule used for lookup, limits and uniqueness.
- How and where consent evidence is stored before a User exists, and whether `LegalConsent` gains a new `consent_method` and a way to preserve the original timestamp.
- Bot defence level (honeypot + timing vs CAPTCHA) and whether it is tenant-configurable; CAPTCHA provider disclosure.
- Retention periods for unverified drafts, abandoned verified drafts, rejected applications, and uploads; the purge mechanism (scheduled job) and the erasure path.
- Whether the anonymous path honours `SiteSignupPolicy.allow_signups`.
- Whether the signup-step fields ("usual signup details") are minimised to email and name before verification, with the rest after.
