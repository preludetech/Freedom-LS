# Frontend QA: anonymous course applications

An anonymous visitor who clicks Apply now on an application-gated course no longer lands on the
signup page. They get an applicant details step, fill in the application (or confirm it on a
form-less course), and see a status page saying a link was emailed. Following that claim link
attaches the application to an account, new or existing, and logs them in. This run walks both
course shapes, the claim link for a new and an existing address, and the ways it could go wrong:
another browser reaching the application, a used or tampered link, a filled honeypot, missing
consent, an email that belongs to another site, and the admin screens that must flag unverified
applications.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

Rate limits cannot be checked here: `settings_dev.py` turns `ACCOUNT_RATE_LIMITS` off. They are
covered by the test suite.

---

## §0 Setup

### 0.1 Server and mail

1. `.claude/ds/scripts/find_available_port.sh`: note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `ananomous-course-applications` branch. If it names another branch, another server holds the
   port; go back to step 1.
4. Dev email goes to Mailpit. Open `http://localhost:8025/` and confirm the inbox loads. If it
   does not, start the dev containers (`dev_db/docker-compose.yaml`) before continuing.

### 0.2 Seed data

Every item below must exist before §1. Missing data is created through the
`fls-dev:qa-data-helper` agent, never by hand. The names are fictional.

1. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
2. **Form course:** the demo course "Functionality Demo - Application gated course" (slug
   `functionality-demo-application-gated-course`), loaded from `demo_content/`, whose application
   form has three pages: About you (full name, date of birth, email address, phone), Supporting
   documents (a file upload and a long text), Availability.
3. **Form-less course:** `QA Application-Gated Course (Access Types)` (slug
   `qa-application-gated-course-access-types`) from `qa_create_course_access_types`, with no
   application form.
4. **Signup policy** for the dev site: `require_name=True`, `require_terms_acceptance=True`,
   `allow_signups=True`. The default legal documents under `legal_docs/_default/` make the two
   consent checkboxes appear.
5. **Existing same-site account:** `qa_existing_applicant@email.com`, password
   `qa_existing_applicant@email.com`, first name `Existing`, active, email verified, with **no**
   application to either course.
6. **Existing other-site account:** `qa_other_site@email.com` on a second `Site` (domain
   `other.example.test`), active.
7. **Inactive same-site account:** `qa_inactive@email.com`, `is_active=False`.
8. **No** `AnonymousApplicant`, and no `CourseApplication` for the addresses used below:
   `qa_new_applicant@email.com`, `qa_formless@email.com`, `qa_consent@email.com`,
   `qa_existing_applicant@email.com`, `qa_other_site@email.com`, `qa_inactive@email.com`,
   `qa_resend@email.com`.
9. A small PNG on disk to upload (any file under 1 MB; the QA data helper can write one).

Use a fresh browser context (no cookies) for every section that starts anonymous. Call that the
*anonymous browser*. Mailpit is read in a second tab.

## §1 Form course, anonymous, start to status page

### 1.1 Apply now goes to the details step

1. In the anonymous browser open
   `http://127.0.0.1:<PORT>/courses/functionality-demo-application-gated-course/`.
2. Click "Apply now". Expect the URL
   `/apply/functionality-demo-application-gated-course/your-details/` and no login or signup
   page.
3. Expect the frame of a form page: the muted line "Application for Functionality Demo -
   Application gated course", the heading "Your details", fields Email, First name, Last name,
   two checkboxes "I accept the Terms and Conditions" and "I accept the Privacy Policy" whose
   links open the legal documents in a new tab, a Previous button and a Next button. Expect no
   password field and no visible "Leave this field empty" field.
4. Click the Terms link: a new tab shows the terms document at `/accounts/legal/terms/`. Close it.

### 1.2 Validation branches

1. Click Next with everything empty. Expect the page to come back (HTTP 422 in the network
   panel) with errors under Email and First name and under both checkboxes. Nothing in Mailpit.
2. Type `not-an-email` in Email, click Next. Expect an email format error.
3. Fill `qa_new_applicant@email.com`, First name `Nia`, tick both boxes, but leave the
   checkboxes unticked on a second try: expect the consent errors only, with the typed values kept.
4. Honeypot: in the browser dev tools set the hidden `fax_number` input's value to `x`, fill valid
   details and submit. Expect the page back with the message starting "We couldn't process this
   sign-up" and no `AnonymousApplicant` created (check via the admin in §6 later, or ask the data
   helper to count).

### 1.3 Valid details land on page 1

1. Fill Email ` QA_New_Applicant@Email.com ` (with spaces and capitals), First name `Nia`, Last
   name `Okafor`, tick both boxes, click Next.
2. Expect form page 1 ("About you") at `/application/<uuid>/page/1/`, with the page links
   1, 2, 3 across the top and the footer's left button reading "Previous".
3. Click Previous. Expect the details step again, prefilled with `qa_new_applicant@email.com`
   (lowercased, trimmed), `Nia`, `Okafor`, and the checkboxes ticked or required again. Click Next
   and expect to land back on page 1 of the **same** application (same uuid in the URL).

### 1.4 Fill, upload, check, submit

1. Page 1: answer the required questions (full name, date of birth, email address). Click Next.
2. Page 2: upload the PNG on "Upload a scan of your ID or a recent certificate". Expect the file
   name to appear with a Remove button. Click Remove, expect the empty picker; upload again.
   Click the file name's download link if shown: expect the file to download, not a 404.
3. Click Next to page 3, answer anything required, click Next to "Check your answers".
4. Expect one card per page with Edit links. Click "Edit About you", change the full name,
   click "Save and return to your answers", expect the new value on the check page.
5. Click "Submit application". Expect the status page at `/status/<uuid>/` saying the
   application for the course has been received and that a link was emailed to
   `qa_new_applicant@email.com`; a button back to the course, and **no** "Back to dashboard"
   button and no login prompt.
6. In Mailpit expect exactly one new message to `qa_new_applicant@email.com` whose subject
   names the course, whose body names the site and the course and holds a "Confirm" style link to
   `/claim/<token>/`, has a line for people who did not apply, and does **not** contain the name
   `Nia`. Keep this tab open; §3 uses the link.
7. Back in the app, open `/apply/functionality-demo-application-gated-course/`. Expect a redirect
   to the status page, not a new application. Open the details URL from 1.1 step 2: expect the
   same redirect.
8. Open page 1 of the application again (URL from 1.3). Expect it to render read-only with the
   callout that the application has been submitted.

### 1.5 Nobody else can see it

1. In a **second fresh browser context**, open the status URL, the page 1 URL and the
   check-your-answers URL from §1. Expect 404 for each.
2. In that second context open the file download URL from 1.4 step 2 (`/forms/answer-file/<uuid>/`
   or the href the Remove widget used). Expect 404.
3. Log in as `demodev@email.com` in a third context and open the status URL. Expect 404: a
   signed-in user who does not own it sees nothing.

## §2 Form-less course, anonymous

1. In a fresh anonymous browser open `/courses/qa-application-gated-course-access-types/` and
   click "Apply now". Expect the details step for this course.
2. Fill `qa_formless@email.com`, First name `Femi`, tick both boxes, Next.
3. Expect the confirmation page "Apply to QA Application-Gated Course (Access Types)" with a
   "Submit application" button and a "Previous" button (not "Cancel"). Click Previous: expect the
   details step prefilled. Click Next again.
4. Click "Submit application". Expect the status page with the received copy and the emailed-link
   sentence for `qa_formless@email.com`.
5. Press the browser Back button to the confirmation page and click "Submit application" again.
   Expect the status page for the **same** application (same uuid), and still exactly one email in
   Mailpit for this address.
6. Mailpit: one message to `qa_formless@email.com` with a claim link. Follow it in §3.3.

## §3 The claim link

### 3.1 GET changes nothing

1. In the **same** anonymous browser as §1 (or a fresh one; both must work), open the claim link
   from §1's email. Expect a page "Finish your application for Functionality Demo - Application
   gated course" with a single "Confirm" button. Expect no account to exist yet: in the admin tab
   (as `demodev@email.com`) search Users for `qa_new_applicant@email.com` and expect no result.
2. Reload the claim page twice. Expect the same page each time; still no user.

### 3.2 New email: confirm, set password, see the application

1. Click "Confirm". Expect a redirect to `/accounts/password/set/` with `next` pointing at the
   status page. Expect the header to show you signed in.
2. Set a password. Expect to land on the status page, now with the normal received copy and a
   "Back to dashboard" button (the emailed-link sentence is gone).
3. Click "Back to dashboard". Expect the dashboard listing the application under applications.
4. Admin, as `demodev@email.com`: Users shows `qa_new_applicant@email.com` with first name
   `Nia`, last name `Okafor`, email verified; the User change page's Legal consents inline shows
   two rows (terms, privacy) with method "Application details step" and an IP address.
5. Open the claim link again in the same browser. Expect the "This link is invalid or has already
   been used" page. Open it in a fresh anonymous browser: the same page.

### 3.3 Existing same-site account

1. In a fresh anonymous browser, apply to the form-less course as `qa_existing_applicant@email.com`
   (details step → Submit application), exactly as §2 but with that address.
2. Open the claim link from Mailpit. Click "Confirm". Expect to land **directly** on the status
   page, signed in as the existing account (no set-password page).
3. Open `/accounts/profile/`: expect first name still `Existing` (the typed first name did not
   overwrite it).
4. Admin: the User change page for `qa_existing_applicant@email.com` shows **no** new Legal
   consent rows, and the application appears under Course applications with Email verified
   ticked.

### 3.4 Other-site account

1. In a fresh anonymous browser, apply to the form-less course as `qa_other_site@email.com`.
   Expect the details step and status page to behave exactly like §2 (same pages, same copy).
2. Open the claim link. Click "Confirm". Expect the invalid-link page. Expect to remain signed
   out, no new user, and in the admin the application still Email verified = No.

### 3.5 Inactive account

1. Apply to the form-less course as `qa_inactive@email.com`, open the claim link, Confirm.
2. Expect a redirect to the login page, not signed in. Admin: the application now belongs to the
   inactive user (Email verified ticked, Applicant shows that user).

### 3.6 Tampered and expired links

1. Take a valid claim URL and change one character of the token. Expect the invalid-link page.
2. Expired: ask the data helper to produce a claim token for `qa_resend@email.com`'s submitted
   application with a signing timestamp older than `EMAIL_CONFIRMATION_EXPIRE_DAYS` (3 days), or
   temporarily set that setting to 0 in `config/settings_dev.py`, restart the server, and open a
   fresh link. Expect a page saying the link has expired with a "Send a new link" button.
3. Click it. Expect a page saying a new link is on its way, and one new Mailpit message to
   `qa_resend@email.com`. Follow the new link and confirm: expect the normal new-email flow of
   §3.2. Revert any settings change and restart the server.

## §5 Signup policy variations

1. Set the dev site's policy to `require_name=False`, `require_terms_acceptance=False`. In a fresh
   anonymous browser open the details step for the form-less course. Expect "First name
   (optional)" and no checkboxes. Submit with only an email: expect the confirmation page.

   exactly the same (anonymous applications ignore the signup switch). Then open
   `/accounts/signup/` and expect it closed as before.

## §6 Admin screens

Sign in as `demodev@email.com` at `http://127.0.0.1:<PORT>/admin/`.

1. **Course applications** changelist: expect an "Email verified" column. The §1 and §3.3
   applications show a tick; the §3.4 (`qa_other_site@email.com`) and §2 (`qa_formless@email.com`,
   unclaimed) ones show a cross with the applicant's email and name in the Applicant columns.
2. The right-hand filter offers "email verified": filter Unverified and expect only the crossed
   rows. Search `qa_formless` and expect that row.
3. Open the `qa_formless@email.com` application. Expect the summary rows to start with
   "Unverified email: qa_formless@email.com", then Applicant (linking to the anonymous applicant
   record), Course and the form-progress row.
4. **Form progress records**: find the §3.4 sitting (if it was a form course; otherwise create one
   by applying to the form course as `qa_other_site@email.com` and submitting). Expect the
   Applicant column to read "Unverified: qa_other_site@email.com". Open it: expect an
   "Unverified email" summary row and the application link.
5. **Question answer files**: the file uploaded by an unverified applicant shows "Unverified:
   <email>" in the Applicant column; Download works for the superuser.
6. **Anonymous applicants**: expect a changelist with email, names, course, Claimed and created
   columns; search `qa_formless` finds the row. Open it: every field read-only, no Save button.
   Expect no "Add" button on the changelist.
7. Delete `qa_formless@email.com`'s anonymous applicant via its Delete button. Expect the
   confirmation page to list the course application and to allow deletion (no "your account
   doesn't have permission" message). Confirm. Expect the applicant, its application and, for a
   form course, its form progress record and files to be gone from their changelists.
8. Bulk delete: tick two unclaimed anonymous applicants (apply twice more as fresh addresses if
   needed) and run "Delete selected". Expect both, their applications and their form progress
   records to be gone.
9. **User erasure**: delete the user `qa_new_applicant@email.com` from the Users admin. Expect
   the confirmation page to list the anonymous applicant and the course application, and the
   delete to succeed; afterwards none of them remain.

## §7 Layout

At 375 px, 768 px and 1280 px widths, open the details step with validation errors showing, the
claim confirm page, the expired page and the invalid page, and the unverified status page. Expect no
horizontal scrolling, the footer buttons stacked on the narrow width with Next on top, and the
consent labels wrapping cleanly next to their checkboxes.
