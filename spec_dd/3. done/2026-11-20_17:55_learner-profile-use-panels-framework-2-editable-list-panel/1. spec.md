# Spec: `EditableListPanel`

Idea: `idea.md`. Answers: `answers.md`. Research: `research_*.md` beside this file.

## Purpose

The panel framework has no shape for a short list of entries that belong to one object and that a
person adds to, edits and removes from. Today the only answer is a `DataTablePanel` with
hand-built row-scoped actions, which is heavy for five entries and needs a hand-written edit
action per list. `learner-public-profile-2-profile-and-page` (work experience) and
`learner-public-profile-4-certificates` need this shape. `EditableListPanel` builds it once, in
`freedom_ls/panel_framework`, with no FLS name in it.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `EditableListPanel` | coined | The framework panel this spec adds. Checked against `fls-dev:domain-glossary`: no clash. |
| entry | coined | One row of an `EditableListPanel`: an instance of the form's model that the panel's `get_entries()` returns for the parent. Not the glossary's "list entry" (`JobTitle`, `Department`, `Location`), and not `AuditLogEntry`. The framework's existing `row_param`, `get_row_object` and `get_row_queryset` carry the entry; "row" stays only in those names. |
| summary | coined | An entry's title and optional detail line, as `EditableListSummary` returned by `get_summary()`. |
| cap | coined | The `max_entries` limit. The cap line is what the panel shows in the Add trigger's place when the limit is reached. |
| parent | narrowed | The panel's bound `ctx.instance` (`panel_framework/context.py`), here always the object the entries belong to. |

## Scope

In:

- `EditableListPanel` in `panel_framework/panels.py`, with its add, edit and remove actions in
  `panel_framework/actions.py`, its templates (the Remove dialog included), a system check, framework
  tests with a new `aria_label` invariant, a static example on the component reference page, and the
  `fls-dev:panel-framework` skill update.
- Focus and announcement behaviour after add, edit and remove, in the framework's
  `alpine-components.js`.
- A hidden-fields hook on `FormPanelAction`, so a row-scoped form dialog posts its row back.
- One "Add and add another" mechanism on `FormPanelAction`, shared by `CreateInstanceAction` and
  `EditableListAddAction`. `CreateInstanceAction` moves onto it, and its labels change to the
  documented "Add" and "Add and add another" (`fls-dev:panel-framework`, Adding and editing records). This
  changes `CreateCohortAction`, its only consumer, and that action's tests.

Out:

- Manual reordering. The consumer's query sets the order.
- Inline editing of an entry inside the list.
- File fields on entries: `learner-profile-use-panels-framework-1-file-upload-actions` supplies
  them, and a consumer combines the two.
- Undo after a remove.
- Any consumer panel or page outside the framework's own tests, apart from the `CreateCohortAction`
  label change that comes with `CreateInstanceAction`.
- Moving `AddLearnerAction` (`educator_interface/actions.py`) onto the shared "Add and add another"
  mechanism. It hand-builds the same response today, with its own outcome sentence. See Open
  questions.

## Decisions

- The entry travels as a request parameter (`row_param`), not a path segment: `?<row_param>=<pk>`
  on the trigger's GET, a hidden field on the POST. The URL router knows only `__actions/<name>`
  (`views.py`), and `PanelAction.get_row_object` already gives the 404 the idea asks for.
- `get_entries()` is the single scope, so an entry outside the parent's entries is a 404 on GET and
  POST. The edit and remove lookup narrows it again by `parent_field` = the parent, so the scope
  holds even when a host's `get_entries()` forgets the filter.
- The add, edit and remove actions are new classes, because `CreateInstanceAction`, `EditAction` and
  `DeleteAction` bind the page's instance (the parent) and `CreateInstanceAction` navigates instead
  of firing events.
- "Add and add another" is built once, on `FormPanelAction`. It already exists twice, and the two
  copies have drifted: `CreateInstanceAction.form_valid` posts `action=save_and_add` under the
  labels "Save" and "Save and add another", while `AddLearnerAction.form_valid` posts
  `action=add_another` under "Add" and "Add and add another" and shows a `status_message`. The
  skill's wording and the learner dialog's value win, because the skill is the source of truth.

## Requirements

### Panel: `panel_framework/panels.py`

`EditableListPanel(Panel)`, added to `__all__`. A parent instance is required: construction
without `ctx.instance` raises `ImproperlyConfigured`, as `InstanceDetailsPanel` does.

What a consumer sets:

| Attribute / hook | Type | Default | Meaning |
| --- | --- | --- | --- |
| `form_class` | `type[ModelForm]` | required | The add and edit form. Its `Meta.model` is the entry model. It leaves out the parent field. |
| `get_form_class(self)` | `-> type[ModelForm]` | returns `form_class` | For a form class that can only be resolved per request. The framework reads the form through this hook. |
| `parent_field` | `str` | required | The entry model's foreign key to the parent. The add action sets it, and the edit action sets it back before saving. |
| `get_entries(self)` | `-> QuerySet` | required | The parent's entries, in display order. The consumer's ordering ends in a unique field (for example `-start_date, -pk`), so the order is stable. |
| `get_summary(self, entry)` | `-> EditableListSummary` | required | The entry's title and optional detail line. Reads only what `get_entries()` already loaded: no query per entry. |
| `noun` | `str` | entry model `verbose_name` | Words the labels: "Add work experience", the dialog titles. |
| `empty_message` | `str` | required | The empty state's sentence. |
| `max_entries` | `int \| None` | `None` | Optional cap. |
| `add_another` | `bool` | `False` | Offers "Add and add another" beside "Add". |
| `layout` | `Literal["list", "table"]` | `"list"` | Row markup. |
| `refresh_events` | `tuple[str, ...]` | `()` | The list's event, passed to the three actions as `success_events`. |

`EditableListSummary` is a frozen dataclass `(title: str, detail: str = "")`, exported from
`panels.__all__`. Both values render autoescaped.

`get_actions()` returns the add, edit and remove actions. `get_entries()` runs once per render.

### Actions: `panel_framework/actions.py`

Three classes, added to `__all__`, built by the panel and named by its `noun`:

- `EditableListAddAction(FormPanelAction)`: a footer action (`renders_in_footer = True`). The form
  takes no instance. On a valid POST it saves the entry with `parent_field` set to the parent, inside
  `transaction.atomic()` with the parent row locked (`select_for_update()`), and re-checks the cap
  under the lock. Success is `changed_response` with the panel's events (204, `HX-Trigger`,
  `closeModal`), never a navigation. Submit buttons: "Add" (loading "Adding…"), plus
  `ADD_ANOTHER_BUTTON` when `add_another` is set. That button answers through
  `add_another_response` with the status message "Added <summary title>.", and it is not offered
  when the save fills the last free place.
- `EditableListEditAction(FormPanelAction)`: a row action (`renders_in_footer = False`, `row_param`
  set, `get_row_queryset` returns `get_entries()`). The form's instance is `get_row_object(ctx)`.
  One "Save" button. Title "Edit <noun>".
- `EditableListRemoveAction(ConfirmAction)`: a row action scoped the same way. Label "Remove",
  `confirm_variant = "error"`, loading "Removing…", template `editable_list_remove.html`. Deletion runs in `transaction.atomic()`; a `ProtectedError`
  answers with `refusal_response`. Success is `changed_response` with the panel's events.

Each action derives its capability from the entry model (`add_`, `change_`, `delete_<model>`) and
asks it of the parent as `permission_object`, so a host's `has_capability` decides. Each action
carries `derive_capability = True`. A host subclass sets `derive_capability = False`, and its own
`capability` (a string, or `None` to allow whoever reaches the panel) then applies. A host hands
its subclasses to the panel by overriding `get_actions()`.

The cap: when `max_entries` is set and `get_entries().count() >= max_entries`, the add action's
`is_offered` is false, the cap line shows in the Add trigger's place, and both its GET and its POST
answer `refusal_response` (422, message dialog, Close footer) with the cap line's wording: "You can
have up to <max_entries>. Remove one to add another." Edit and remove still work at the cap.

`FormPanelAction` gains `get_hidden_fields(self, ctx) -> dict[str, str]` (default `{}`), rendered as
hidden inputs inside the form in `panel_framework/modal/form.html`. The edit action returns its
`row_param` and the entry's pk, mirroring `ConfirmAction.get_hidden_fields`.

#### "Add and add another" on `FormPanelAction`

- `ADD_ANOTHER_BUTTON`, a module constant in `panel_framework/actions.py` and in `__all__`: label
  "Add and add another", variant `secondary`, `name="action"`, `value="add_another"`, loading
  "Adding…".
- `FormPanelAction.wants_add_another(self, ctx) -> bool`: true when the POST's `action` is
  `add_another`.
- `FormPanelAction.add_another_response(self, ctx, events, status_message) -> HttpResponse`: 200,
  the fragment re-rendered with `get_unbound_form(ctx)` and `status_message`, and `HX-Trigger` built
  from `events` without `closeModal`, so the dialog stays open and the panels behind it refresh.
  Hidden fields come from `get_hidden_fields` as on any render.
- `CreateInstanceAction.submit_buttons` becomes `ADD_ANOTHER_BUTTON` then "Add" (primary, loading
  "Adding…"), and its `form_valid` uses `wants_add_another` and `add_another_response` with the
  status message "Added <instance>.". `action=save_and_add` stops being recognised.

### Templates

`panel_framework/panels/editable_list.html` extending `panels/_editable_list_base.html`, the
two-layer pattern every framework panel uses. It extends `_panel_base.html`, so a panel with
`refresh_events` refetches its own region.

- Each entry shows its summary: the title in `font-medium`, the detail under it in
  `text-sm text-muted` when set. `layout = "list"` uses `<c-panel-list>` and `<c-panel-list-row>`
  with the buttons in the row's item footer (its `footer` slot): under the title and detail, left
  edge on the title's, each button as wide as its label. `layout = "table"` uses the framework's
  table components inside `.panel-data-table`, buttons in a `<c-data-table-actions>` cell, cards
  when the container is narrow (the card's buttons in its own `footer` slot, laid out the same as a
  list row's), and the table footer's entry count.
- Per entry: an Edit trigger and a Remove trigger, `<c-modal-trigger size="small">`, URLs from
  `row_action_urls` plus `?<row_param>=<pk>`. The visible labels are "Edit" and "Remove". Each
  `aria_label` starts with the label and names the entry: "Edit <title>", or "Edit <title>, <detail>"
  when the detail is set. Remove is the same.
- Empty: `<c-panel-empty-state message="<empty_message>">` with the Add trigger in its slot, and no
  second Add in the footer.
- The cap line is a muted line in the footer, with `tabindex="-1"` so focus can land on it.
- Each row's Remove trigger carries data attributes for its entry's summary title and the pk of the
  entry to focus after the removal (next, else previous); each Edit trigger carries its entry's
  title. The focus and announcement code reads them.
- Add and edit use `modal/form.html`. Remove uses a new
  `panel_framework/modal/editable_list_remove.html` extending `modal/confirm.html`, whose body names
  the entry by its summary title and says the removal cannot be undone.

### Focus and announcements

After the panel refreshes from its own event:

- Add saved: focus moves to the new entry's Edit trigger, or to the cap line when the add reached the
  cap.
- Edit saved: focus moves to that entry's Edit trigger.
- Remove confirmed: focus moves to the next entry's Edit trigger, else the previous one, else the
  empty state's Add trigger.
- Cancel or close without a change: focus returns to the trigger, as the modal host already does.
- "Add and add another" saved: the dialog stays open. Focus moves to the empty form's first field,
  through the modal host's existing `[autofocus]` handling of a 200 swap inside an open dialog. The
  `status_message` notice (`role="status"`) is the announcement, so the page announcer says
  nothing. The panel still refreshes behind the dialog, and `data-focus-target` is not acted on
  while a dialog is open. When the dialog is then closed, focus returns to the Add trigger, or to
  the cap line when the list reached the cap.

Each change is announced once through the page announcer (`#scope-announcer`,
`panel_framework/partials/announcer_host.html`), which stays outside the closed dialog: "Added
<title>.", "Saved <title>.", "Removed <title>."

The mechanism lives in the framework's `alpine-components.js`. The refreshed panel marks the element
to focus with `data-focus-target`, and the existing `htmx:afterSwap` fallback that focuses the
region heading when focus was lost prefers that element when it is present. The add and edit
targets come from the entry pk the success event carries (`PanelAction.get_success_events`) and the
new row's title attribute. The remove title and target come from the clicked Remove trigger's data
attributes, read before the request, since the removed entry is gone from the refreshed list. Any
new `x-data` name is registered there.

### Errors

- An invalid add or edit re-renders the form in the dialog with the person's values and errors, 422.
- An edit or remove for an entry that no longer exists (removed in another tab) answers 404, and the
  person sees the framework's message dialog, not an empty modal.

### System check: `panel_framework/checks.py`

A new check id, `freedom_ls_panel_framework.E009`, held in one constant, run over every
`EditableListPanel` subclass: `form_class` is set and is a `ModelForm`; `parent_field` names a
foreign key on the form's model and is not among the form's fields; `max_entries` is `None` or a
positive integer; `layout` is `"list"` or `"table"`. The form conditions are skipped for a subclass
that overrides `get_form_class()`, since a check has no bound panel to call it on. The check skips `EditableListPanel` itself, as the table-key check skips its base
classes (`checks.py`).

### Component reference page

`panel_framework/templates/panel_framework/reference/_examples.html` gains an "Editable list"
section with static examples `editable-list-default`, `editable-list-empty`, `editable-list-cap` and
`editable-list-table`, and `"editable-list"` joins `COMPONENT_NAMES` in the reference tests. The page
stays zero-query.

## Open questions

- Q: Which layout is the default when a consumer sets none? → A: `"list"` (assumed default: it is the
  lighter shape the idea asks for, and a consumer can pick `"table"`. Overrule by editing Requirements,
  Panel.)
- Q: Do the actions derive `add_`/`change_`/`delete_<entry model>` capabilities by default, or default to
  `capability = None`? → A: Derive them, asked of the parent (assumed default: deny by default matches
  every other framework action, and a self-service host opts out per subclass. Overrule by editing
  Requirements, Actions.)
- Q: What does the cap line say? → A: "You can have up to <max_entries>. Remove one to add another."
  (assumed default: it states the number and the way out without needing a plural noun. Overrule by
  editing Requirements, Actions.)
- Q: How does the framework stop an edit moving an entry to another parent? → A: E009 fails when
  `parent_field` is among the form's fields, and the edit action sets the parent back before saving
  (answered during the plan review).
- Q: Does the framework narrow the edit and remove lookup by the parent itself? → A: Yes (answered
  during the plan review).
- Q: Do the announcements end in a full stop? → A: Yes, as the brand voice asks (answered during
  the plan review).
- Q: How does a host opt out of the derived capability? → A: `derive_capability = False` on a
  subclass (answered during the plan review).
- Q: Does `AddLearnerAction` move onto `add_another_response` in this spec? → A: No, it stays as it
  is and moves in a follow-up (assumed default: this spec keeps consumer changes to the one that
  `CreateInstanceAction` forces, and the learner dialog already uses the agreed value and labels.
  The move would pass its outcome sentence as `status_message`. Overrule by moving it from Out to
  In under Scope.)
