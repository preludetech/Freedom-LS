# Frontend QA: `EditableListPanel`

## 0. Setup

- Start the server on the port the QA command picks: `uv run python manage.py runserver $PORT`.
- Base URL: `http://127.0.0.1:$PORT`.
- Data: `uv run python manage.py create_demo_data --yes` if the database has no users.
- Log in at `/accounts/login/` as `demodev@email.com`, password `demodev@email.com`.
- The educator pages are under `/educator/organisations/demodev/`.

What a browser can and cannot reach: no page on the dev site uses `EditableListPanel` yet. Its
add, edit, remove, cap and focus behaviour run only on the framework's test stubs, and the
pytest-Playwright flow covers them. This plan checks what the dev site does show: the component
reference page's editable list examples, the cohort dialog's new buttons, and the dialogs that
share the changed code.

Viewports: 1920x1080, 375x812 and 768x1024 for tests 1 and 2. Desktop is enough for tests 3 to 6.

## Test 1: the editable list on the component reference page

URL: `/panel-framework/components/`

1. Scroll to the section headed "Editable list".
2. `#editable-list-default`:
   - Several entries, each with a title in medium weight and, where it has one, a muted detail
     line under it.
   - Each entry has two small buttons, "Edit" and "Remove", in a footer under its title and
     detail: side by side with a gap, the Edit button's left edge on the title's left edge, each
     button as wide as its label. Nothing sits at the right end of the row.
   - The footer is in the same place on every entry, with or without a detail line.
   - In the accessibility snapshot each button's name starts with its label and names its entry:
     "Edit <title>" or "Edit <title>, <detail>", and the same for Remove. No two buttons on the
     page section share a bare name "Edit" or "Remove".
   - One "Add …" button in the panel's footer.
3. `#editable-list-empty`:
   - One sentence and one "Add …" button, centred in the panel body.
   - No second Add button in a footer.
4. `#editable-list-cap`:
   - Entries with their Edit and Remove buttons in the same item footer as `#editable-list-default`.
   - Where the Add button was, a muted line: "You can have up to N. Remove one to add another."
     with the number filled in.
   - No Add button anywhere in this example.
5. `#editable-list-table`:
   - At 1920: a table, one row per entry, the Edit and Remove buttons together on one line in
     the last cell, each as wide as its label, and a footer line stating how many entries there
     are.
   - At 768 and 375 (the panel is narrower than the table needs): the entries as cards, each with its title, then its detail on its own line, then a
     footer with Edit and Remove side by side, left-aligned with the title, each as wide as its
     label. No button stretches across the card, shares a line with the detail, or wraps onto a
     line of its own. Only one set of buttons per entry is visible.
6. **MUST, blocking (this bug has been flagged more than once).** In `#editable-list-default`,
   `#editable-list-cap` and `#editable-list-table` at 375x812 and 768x1024, on every entry:
   - Edit and Remove are on the same row, inside the entry's item footer (`[data-item-footer]`),
     under the title and the detail.
   - Neither button is full width or stretches across the row or card. Each is only as wide as
     its label.
   - Neither button shares a line with the detail, and neither wraps onto a line of its own.
   - Don't eyeball it. With `browser_evaluate`, check that both buttons in the entry have the
     same `getBoundingClientRect().top`, that both have a `[data-item-footer]` ancestor, that
     each button's width is under a quarter of the entry's width, and that their top is below the
     detail line's bottom.
   - At 1920 in `#editable-list-table`, both buttons share a top in the row's last cell.
   - Any failure here is a blocking bug, not a polish item. Attach screenshots to the report.
7. At every viewport the entries are tidy: in list rows and cards every entry's buttons start at
   the same x and sit the same distance under the entry's text.
8. At every viewport: no horizontal scroll on the page, and no button's label wraps or is cut off.
9. The browser console shows no error.

## Test 2: the cohort dialog offers "Add and add another" then "Add"

URL: `/educator/organisations/demodev/cohorts`

1. Click the button that creates a cohort. The dialog opens with focus in the name field.
2. The footer reads, in order: Cancel, "Add and add another", "Add". Nothing says "Save".
3. Type a new name and click "Add and add another".
   - The dialog stays open with an empty name field, and focus is in it.
   - A success notice above the field reads "Added <the name>.".
   - The new cohort is in the list behind the dialog.
4. Type a second name and press Enter in the field.
   - The dialog closes and the page moves to the new cohort (Enter acts as "Add").
5. Go back to the cohorts list. Both cohorts are there, once each.
6. At 375x812: open the dialog again. All three footer buttons are inside the viewport and none
   is cut off.

## Test 3: the cohort dialog's failure paths

URL: `/educator/organisations/demodev/cohorts`

1. Open the create dialog, leave the name empty, click "Add and add another".
   - The dialog stays open with an error on the name field, and no cohort is created.
2. Type a name that already exists and click "Add".
   - The dialog stays open with the "already exists" error beside the field.
3. Type a new name, click "Add and add another", then click it again at once with the field
   empty.
   - One cohort was created by the first click. The second shows the required error.
4. With a name typed and not submitted, press Esc.
   - The discard prompt appears. "Keep editing" returns to the form with the name intact.
5. While a submit is in flight, the clicked button shows "Adding…".

## Test 4: the Add learner dialog is unchanged

## Test 5: other form dialogs still open, validate and save

The form dialog template now renders hidden fields, so check a dialog that has none.

1. Open a cohort (`/educator/organisations/demodev/cohorts`, then a cohort's name).
2. Open any Edit dialog the cohort page offers (for example on its Settings tab, or a details
   panel's Edit button).
   - It opens filled in. Its footer is Cancel and "Save".
   - Clear a required field and save: the error shows in the dialog.
   - Restore the value, change something, save: the dialog closes and the page shows the change
     without a full reload.
3. Page source of the open dialog's form holds no stray empty hidden input.

## Test 6: a delete confirmation still names what blocks it

The sentence about protected dependents moved into a shared helper.

1. On a cohort that still has learners or registrations, open its Delete dialog.
   - It either lists what will also be deleted, or says the cohort cannot be deleted because it
     still has "<count> <things>", in a readable sentence ("2 learners and 1 course
     registration", not a Python list).
2. Cancel. Nothing was deleted.
