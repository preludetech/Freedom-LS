# Research: best practices for a layered deadline consequence policy, enforced on read

Topic: `best_practices`. Input to the `deadlines-2-consequence-policy` spec. It does not repeat `spec_dd/1. next/deadlines/research_lms_deadlines_landscape.md` (what Moodle, Canvas, TalentLMS and others do). It covers design practice.

Evidence labels: **[sourced]** means a web result from this session, with URL. **[general]** means established engineering practice stated from general knowledge, not re-verified in this session; the spec author should treat it as a recommendation. Only three searches were run (Moodle overrides, time-mocking libraries, Django swappable settings). The third returned nothing useful on `import_string` or nullable overrides, so the Django sections are [general].

Terms in quotes belong to the named system. FLS terms follow the project vocabulary.

## 1. Hierarchical settings, inherit vs override

- **Per-field unset, not per-row override.** [sourced] Moodle's docs say to enable and set only the fields to override, leaving the rest blank so the assignment defaults apply. A layer row is a sparse set of fields, and each field is independently "unset" or "set". Resolution runs per field, not per row, so a cohort row that sets only the grace window leaves everything else to the organisation. https://docs.moodle.org/en/Assignment_overrides
- **Unset marker must be distinct from every legal value.** [general] A nullable column (`null=True`, `None` = inherit) works for durations and numbers. For booleans, `BooleanField(null=True)` gives a three-state value (inherit, on, off). Be careful: "grace window of zero" must be a legal explicit value that differs from "unset", so use `None` for unset and never `0`. The idea already says "each value that is not a flag has its own unset marker"; best practice is to apply the same three-state rule to flags too, otherwise a lower layer can never switch a consequence off that a higher layer turned on (and the reverse). This is a possible gap in the idea: a plain `BooleanField(default=False)` cannot express "inherit".
- **Most-specific-wins resolution as a pure function.** [general] Resolve by walking layers from most to least specific and taking the first non-unset value per field, falling through to a code-level default (the "settings layer is always present" in the idea). Return one immutable resolved object (frozen dataclass) holding the values and, ideally, which layer supplied each. Provenance per field is cheap and makes the admin and the learner message explainable ("grace window 3 days, from the organisation").
- **Conflict within one layer.** [sourced] Moodle: a user override beats group overrides; with several groups the most lenient date wins (earliest open, latest due and cut-off). Lesson for FLS: a layer that can match several rows (a learner in two cohorts) needs an explicit tie rule, and "most permissive wins" is the convention already in the roadmap. The idea settles this for registrations by "one registration governs"; the open question about a learner with both an individual and a cohort registration is exactly this case. https://docs.moodle.org/en/Assignment_overrides
- **Overrides do not follow base edits.** [sourced] Moodle overrides keep their own date when the base due date changes; Monash tells staff to review them. For a policy this is mostly moot because a policy layer holds a duration (grace length), not a date, so it follows the base date automatically. That favours storing **durations, not absolute close dates**, in policy rows. The interaction with a spec-1 override that moves a due date then falls out for free if closing = effective due date + resolved grace. https://www.monash.edu/learning-teaching/teachhq/moodle/assignment/how-to/extensions-and-resubmissions
- **Layer order.** [general] Order layers by "who is accountable for the decision" and "how narrow the scope": the narrowest scope wins. Registration > cohort > course > organisation > site is conventional. Course vs organisation is a real judgement call: a course author's default versus an organisation's compliance rule. The common resolution is that the more specific scope wins, and an organisation that needs a rule enforced uses a separate "locked/enforced" flag. Do not build that flag unless asked (project rule: no unrequested functionality), but record the decision and that the order is a single list in one place so it can be reordered.
- **Validate at write time, resolve at read time.** [general] Admin `clean()` should reject contradictory values within a row (negative grace, grace set while closing and ending are both unset is harmless but worth a help text). Do not rely on resolution to repair bad data.
- **Uniqueness.** [general] One row per (layer target); enforce with a `UniqueConstraint` per layer FK, or one table per layer, so "a missing row inherits" and duplicates cannot exist.

## 2. Computing state on read vs sweeps

- **Derive state from timestamps; do not store a status that time changes.** [general] Whether an item is overdue, closed or access has ended is a pure function of (now, effective dates, resolved policy). Storing `status="closed"` and flipping it with a job creates a window where the stored value is wrong, and a missed job leaves it wrong. The idea's "enforcement is on read" matches this. Standard references: the "derived state" idea in event-sourced and subscription systems, where "expired" is `now >= expires_at` and not a column.
- **Single decision function, injected `now`.** [general] One function `decide(now, dates, policy) -> Decision` (overdue, closed, access_ended, plus the instants at which each began). Callers pass `now` (default `timezone.now()` at the edge). Every surface (player, table of contents, dashboard, access check) calls it, which is what the idea's "single source of truth for closing" asks. Take `now` once per request so a page does not disagree with itself across a boundary.
- **Sweeps are still needed for side effects, not for state.** [general] Anything that must happen exactly once (a notification, a webhook, writing a "closed at" audit row) needs an idempotent sweep keyed on a marker or a unique constraint. That is spec 5. Keep the read path free of writes; an enforcement check that writes on GET is hard to test and cache.
- **Cost on read.** [general] The decision needs the resolved policy: up to five layer lookups. Resolve with `select_related` through the registration, and cache the resolved policy per request (or per registration within the request) so a table of contents with many items resolves once, not per item. Do not cache across requests without an invalidation story; admin edits must take effect on the next read.
- **Do not let a stale "ended" cache outlive a restore.** [general] If anything caches access decisions, restore must invalidate it. Simplest: do not cache across requests.
- **Return the reason, not just a boolean.** [general] Surfaces differ (player shows "closed", dashboard shows "access ended", spec 7 filters on overdue). A `Decision` carrying the state and the dates lets each render its own message, and supports the idea's "learner is shown the consequence next to the date" (Docebo and Canvas complaints in the sentiment file are about invisible or inconsistent consequences).

## 3. Grace periods, time zones, boundaries

- **Model the three instants separately.** [sourced] Moodle: due date only marks late; cut-off date is the hard stop. Canvas: Due, and "Until" as the close. FLS maps this to: overdue at `due`, closed at `due + grace`. A grace window is therefore not a second date field, it is a duration applied to the due date. https://docs.moodle.org/en/Assignment_overrides
- **Mark overdue at the due date, not at the end of grace.** [general, supported by the sentiment file cited in the idea] Hiding the overdue mark during grace is what makes consequences invisible; labelling "Late" with no way to turn it off is the opposite complaint. The idea's split (overdue mark at the due date, policy switch to disable it, close after grace) addresses both.
- **Boundary convention: half-open intervals.** [general] State one rule and test both sides: an item is open for `now < close_at` and closed for `now >= close_at`; overdue for `now > due_at` or `>= due_at`, whichever is chosen, but the same comparison everywhere. Recommended: the deadline instant itself is the first moment of the consequence (`now >= instant`), because "due at 17:00" users generally still expect to submit at 16:59:59 and not at 17:00:00.000001. Whatever is chosen, say it in the spec and in the learner copy ("closes at 17:00", not "after 17:00"). The inclusive/exclusive choice matters for the grace edge too: with `close_at = due_at + grace`, a zero grace makes overdue and closed begin at the same instant.
- **Store and compare in UTC; display in a named zone.** [general] Django stores aware datetimes in UTC when `USE_TZ = True`. Compute `due + timedelta(...)` in UTC, and convert only for display. For grace windows of whole days, adding a `timedelta(days=N)` to a UTC instant gives exactly 24N hours, which across a DST change is not "the same wall-clock time N days later". Decide which is meant: "3 days" as a duration (simple, DST-safe, recommended) versus "until end of the third day in the learner's/site's zone" (needs a zone and a date calculation). Pitfalls on date-only due dates and DST are already documented in the landscape file (section f); the spec should state that grace is a fixed duration unless it wants the calendar semantics, and show the time zone beside the time.
- **Which zone for a date-only due date?** [general] Out of scope here (spec 1 owns dates), but the consequence depends on it: if spec 1 stores midnight, closing at midnight plus a grace of 0 closes the item at the start of the due day. The consequence spec should assume spec 1 supplies a full instant, and note the dependency.
- **Grace and the course time limit.** [general] Ending access after a grace window is the same arithmetic on the course-level end date. Keep one grace length, or separate lengths for items and course access if the layers need it; that is a spec decision to flag (open: is it one setting or two?).
- **Integer overflow and absent dates.** [general] An item with no due date must resolve to "no consequences", not an error; a policy with grace set but no date is inert.

## 4. In-progress attempts at close time

No LMS source in this session documents this directly [no source found]. Practice from assessment systems, stated as [general]:

- **Distinguish "can start" from "can finish".** Closing normally blocks starting new work. For a timed or multi-page attempt already open, the two defensible rules are (a) **hard stop**: the attempt is closed with the item, saved answers kept and the attempt submitted or left unsubmitted as-is; (b) **finish allowed**: an attempt started before close may be submitted, optionally capped at a grace period or its own timer. Moodle quizzes expose this as a per-quiz "When time expires" setting (auto-submit, give a grace period to submit, or discard unsubmitted); Moodle is the named origin, not verified in this session.
- **Default recommendation for FLS:** do not lose learner work. Closing should block new attempts and new edits, but never delete answers. If the form engine has a draft state, a closed item should keep the draft readable. Whether the learner may submit it is the open question in the idea; the least surprising answer is "closing an item blocks starting; an attempt already in progress may be submitted until `close_at`, after which it is closed read-only", with the draft retained for staff restore/extension (spec 3). Whatever rule, state it per consequence, because "close" for an item with a form differs from "close" for a plain topic.
- **Make the rule one place.** The same decision function should answer "may start", "may save", "may submit" so those cannot drift.
- **Completed items are never gated** (already settled in the idea); the same principle applies to results and exit routes so a learner can always leave and see their results.

## 5. Restoring access with a new window

- **Reactivate with a new end date, keep records.** [sourced via landscape file] Moodle reactivates a suspended enrolment with a new "Enrolment ends"; TalentLMS lets the instructor pick a new expiration; LearnDash replaces the end date. The common model is: access is a derived result of the window, restoring means changing the window, not deleting history. https://telsupport.brookes.ac.uk/articles/how-do-i-reactivate-suspended-enrolments-in-moodle/ and https://help.talentlms.com/hc/en-us/articles/360014657413-How-to-change-the-expiration-date-of-a-course-for-specific-users
- **Record the restore as an event, not a silent edit.** [general] Keep an append-only record (who, when, reason, old end, new end), or at minimum reuse the audit log when it lands. An in-place overwrite of the end date makes "why did this learner get access" unanswerable. The destructive-reset pitfall (Coursera reset losing submissions, landscape section f) argues for keeping progress rows untouched.
- **What "new window" means must be specified.** [general] Options: new end = restore time + original length; new end = a date staff pick; end date shifted by the lapsed time. Pick one for the admin action and say what happens to item due dates already past (they remain overdue and, with a grace window, closed again immediately unless the restore also moves them). This is the real design trap: restoring course access while items remain closed gives the learner a course they still cannot work in. The spec should state whether restore also reopens items or leaves that to extensions (spec 3).
- **Self-registration must not bypass it.** [general] If registration is idempotent (`get_or_create`) and ending access leaves the registration active, a learner re-registering finds the existing row and nothing changes, which is what the idea wants. Check that no path creates a second registration for the same learner and course.
- **Keep the registration active.** Matches the idea (no `is_active=False`, no `course.unregistered`): "access ended" is a derived state on an active registration, so a restore is only a date change and fires no registration events.

## 6. Django patterns

- **Swappable class behind a setting.** [general] Standard pattern: a dotted-path setting, loaded with `django.utils.module_loading.import_string`, cached at first use, default value in the app's settings module. This is how `AUTHENTICATION_BACKENDS`, `STORAGES`, the cache and email backends, and `django-constance`'s `CONSTANCE_BACKEND` (selected by dotted path) work. https://django-constance.readthedocs.io/en/stable/backends.html . Django docs for import_string: https://docs.djangoproject.com/en/stable/ref/utils/#module-django.utils.module_loading . FLS already has the pattern in `COURSE_ACCESS_BACKEND` and `messaging_policy/resolver.py`; follow them rather than inventing a new loader. Tests that swap the setting need the loader's cache cleared (a `setting_changed` receiver, or no caching).
- **A small, typed interface.** [general] Define the contract as a `typing.Protocol` or a plain base class with one or two methods (`resolve(registration) -> ResolvedPolicy`, `decide(...)`). The project says not to create abstract base classes unless asked; a Protocol or a documented concrete default class that others subclass avoids that rule. Return the frozen `ResolvedPolicy`/`Decision` dataclasses so a replacement policy cannot return loosely-typed dicts (project forbids `Any`).
- **Per-field nullable overrides in the ORM.** [general] `DurationField(null=True, blank=True)`, `BooleanField(null=True, blank=True)`. In the admin, a nullable boolean renders as a select with "Unknown / Yes / No"; override the choice labels ("Inherit / On / Off") with a custom form field or `choices` so staff are not confused. Add `help_text` naming the next layer. A `CheckConstraint` can bound values (`grace >= 0`).
- **Resolution in one query path.** [general] Gather the layer rows with a small number of queries (one per layer table, or one union) using `select_related` from the registration. Avoid one query per field. Respect the site-aware manager (multi-tenant skill) on each layer.
- **Wrapper vs predicate for "access ended".** [general] A wrapper around the access backend centralises the check where visibility is already applied (as `VisibilityEnforcingBackend` does) and keeps the policy swappable in one place; a registration predicate is simpler but spreads the check into every caller of the predicate and changes who sees a hidden course. Best practice favours the one chokepoint that every access path already passes through; verify with a test that enumerates the entry points (player, results, exit routes, dashboard).
- **Admin.** [general] Use inlines on the owning model for the cohort, course and registration layers, so staff see the row where they work. Show the resolved policy as a read-only field or admin action ("what applies to this registration?"), since "a missing row inherits" is otherwise invisible.

## 7. Testing time-based behaviour

- **Prefer an injected `now` for the pure decision.** [general] Unit-test `decide(now, ...)` with explicit instants; no clock mocking needed. Table-driven tests on both sides of every boundary: `due - 1s`, `due`, `due + 1s`, `close - 1s`, `close`, `close + 1s`, with grace 0, grace > 0, and grace unset.
- **Clock-freezing libraries for integration tests.** [sourced] `freezegun` is the older, widely used option; `time-machine` patches at the C level and is reported (author's benchmark) to be about 100x faster in a minimal setup and about 200x in a small Django project. Caveat: with time frozen, `auto_now` and `auto_now_add` fields also take the frozen time. Choose one library, and use it with `tick=False` unless a test needs time to move. https://adamj.eu/tech/2021/02/19/freezegun-versus-time-machine/ , https://adamj.eu/tech/2020/06/03/introducing-time-machine/ , https://betterstack.com/community/guides/testing/time-machine-vs-freezegun/
- **Check which the project already uses** before adding a dependency (not checked in this research).
- **Matrix to cover.** [general] Each layer alone sets a field; two layers set the same field (specific wins); a layer sets a field to the "off" value while a higher layer has "on"; a layer sets explicit zero grace over a nonzero higher grace; all layers unset (code default); registration with both individual and cohort registrations; completed item past close (not gated); in-progress attempt at close; ended access then restore (new window, progress intact); a DST change inside a multi-day grace window; a learner whose zone differs from the site's.
- **Test that enforcement is read-only and consistent.** [general] Assert that the player and the table of contents give the same answer for the same item and `now`, since single-source-of-truth is a stated goal. Assert no query count blow-up on a table of contents with many items (`django_assert_num_queries`).
- **Admin tests.** [general] Cover the three-state boolean round trip (Inherit saves `None`, not `False`).

## 8. Items to settle in the spec (summary of recommendations)

1. Use three-state (null = inherit) for the on/off consequence flags as well as durations, otherwise a lower layer cannot turn off what a higher layer turned on.
2. Store the grace as a duration; compute `close_at = effective_due + grace`; this makes spec-1 overrides compose without extra rules.
3. Fix one half-open boundary rule (`now >= instant` starts the consequence) and the unit of "days" (fixed duration, UTC) and state them in learner copy.
4. One `decide(now, ...)` function, one resolved-policy object with per-field provenance, resolved once per request.
5. In-progress attempts: closing blocks starting, never discards work; choose explicitly whether an attempt in progress can be submitted before `close_at` and who can reopen it.
6. Restore as a recorded event that changes the window and keeps progress; say what happens to items already closed.
7. Layer order is a single list in one place; document course vs organisation order and the reason.
8. Enforce "access ended" at the one chokepoint all paths share and test every entry point.
