# Frontend QA: optimise content images

Manual verification for the image optimisation added by `content_save`. Two halves: the CLI output an
author sees while ingesting, and what the learner's browser actually loads afterwards.

## 0. Setup

### 0.1 Preview overrides

`demo_content/functionality_demo_content_widgets/course.md` sets `visibility: coming_soon`, so an
unregistered user is redirected to the course detail page instead of the player. Temporarily flip both
preview overrides in `config/settings_dev.py:125-126`:

```python
OVERRIDE_COURSE_VISIBILITY_TO_VISIBLE = True
OVERRIDE_COURSE_ACCESS_TO_FREE = True
```

**Revert both to `False` when QA is done.** They must never be committed as `True`.

### 0.2 Clean media directory

Dev storage is the filesystem (`MEDIA_ROOT = BASE_DIR / "media"`, `config/settings_base.py:259`), and
content files land in `media/content_engine/`. Start from a known state so orphan checks mean
something:

```bash
uv run python manage.py danger_content_delete --yes
rm -rf media/content_engine
```

### 0.3 Load the demo content and capture the output

```bash
uv run python manage.py content_save demo_content DemoDev 2>&1 | tee /tmp/content_save_run1.txt
```

Keep the terminal output. Section 1 reads it.

### 0.4 Start the server

```bash
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL is `http://127.0.0.1:$PORT`.

### 0.5 Log in

- Go to `http://127.0.0.1:$PORT/accounts/login/`
- Email `demodev@email.com`, password `demodev@email.com`

## 1. CLI output (the author's view)

This is the bug §4 of the spec exists to fix: today an author running `content_save` locally sees
nothing at all, because `LOGGING` is only configured in `config/settings_prod.py`.

**Read `/tmp/content_save_run1.txt`.**

| Check | Expected |
| --- | --- |
| 1.1 | A `Created IMAGE file: …` or `Updated IMAGE file: …` line appears for **every** image, not just the new photo. |
| 1.2 | Per-file lines appear for **non-image** file types too (`DOCUMENT`, `OTHER`, …) if the demo tree has any. The move to `click.echo` was not image-only. |
| 1.3 | The new demo photograph shows three lines: the path, a `JPEG WxH -> WebP lossy 1600x…` line, and a `… MB -> … KB (-…%), optimised.` line. The percentage is a large negative number. |
| 1.4 | Every `.svg` in the demo tree shows `SVG, passthrough.` and no size line. |
| 1.5 | `✓ Successfully saved all content for site: DemoDev` is visible in the terminal — not swallowed. |
| 1.6 | **Below** that success line, one run-summary line with the total images seen and a count per status. Statuses that did not occur are omitted, so this is one short line. |
| 1.7 | Nothing in the output is a stray `logger.info` that lost its formatting, and no traceback appears. |

**1.8 — order matters.** The summary must print *under* the success line, not above it. A summary
printed above a success line the author cannot see is exactly the failure mode being fixed.

## 3. Storage and the database

**3.1 — no orphaned originals.**

```bash
ls media/content_engine/
```

There must be **no** `.jpg` or `.png` object for a file that is now stored as WebP. The SVGs are still
`.svg`. This is the delete-before-write ordering; `course_media` is a non-overwrite alias, so getting
it wrong leaves a `photo<uuid>.jpg` behind next to `photo<uuid>.webp`.

**3.2 — the `File` rows.** Django admin at `http://127.0.0.1:$PORT/admin/`, then Content engine →
Files. For the new photograph's row:

- `file_path` is still the author's relative path with its original extension.
- `original_filename` is still the author's `*.jpg`.
- `mime_type` is `image/webp`.
- The stored file name ends `.webp`.

**3.3 — idempotency.** Re-run ingest and diff:

```bash
md5sum media/content_engine/* | sort > /tmp/media_run1.txt
uv run python manage.py content_save demo_content DemoDev 2>&1 | tee /tmp/content_save_run2.txt
md5sum media/content_engine/* | sort > /tmp/media_run2.txt
diff /tmp/media_run1.txt /tmp/media_run2.txt
```

- `diff` is empty: same filenames, same bytes. Any difference means either non-determinism or a
  cumulative re-encode reading its own previous output.
- `ls media/content_engine/ | wc -l` is unchanged — a second run did not add a renamed duplicate.
- The run-2 summary line matches run 1's counts.

**3.4 — `demo_content/` is not dirtied.** `git status --short demo_content/` is empty after both runs.

## 4. Failure and edge branches

Build a scratch content tree so these never touch `demo_content/`. Give it a course and one topic that
references each file.

```bash
mkdir -p /tmp/qa_images/"1. intro"/images
```

Author `/tmp/qa_images/course.md` (a `COURSE` with a fresh `uuid`) and
`/tmp/qa_images/1. intro/content.md` (a `TOPIC` with a fresh `uuid`) containing one `<c-picture>` per
file below. Then:

```bash
uv run python manage.py content_save /tmp/qa_images DemoDev
```

| # | File to drop in `images/` | Expected CLI | Expected in browser |
| --- | --- | --- | --- |
| 4.1 | A deliberately corrupted PNG (truncate a good PNG, or flip a byte inside its `IDAT`) | A `logger.warning` on stderr naming the relative path and the exception; the run **completes**; the per-file line reports `could not decode` | The topic page still loads. The figure shows as a broken image — the file was stored unchanged, so this is correct, not a failure. |
| 4.2 | An animated GIF | `passthrough` | Renders and still animates |
| 4.3 | A small already-optimised WebP (under 1600 px) | `passthrough` | Renders; `ls media/content_engine/` shows it byte-identical to the source (`cmp` it) |
| 4.4 | A tiny, already well-compressed PNG (e.g. 200x120 flat colour) | `kept source`, with the `re-encode not smaller` wording | Renders as PNG; served `Content-Type` is still `image/png` |
| 4.5 | A file named `DIAGRAM.SVG` (uppercase extension) | `SVG, passthrough.` — **not** `could not decode`. An uppercase suffix that fell through to a Pillow decode would be the silent bug here. | Renders |
| 4.6 | A real SVG renamed to `.png` | `could not decode`, warning on stderr | Stored unchanged; the browser sniffs and may or may not render it. Either is acceptable; the run completing is what matters. |
| 4.7 | A `.txt` or `.pdf` in the same tree | A per-file line with its own file type, and **no** image lines | Not applicable |
| 4.8 | A portrait phone photo carrying an EXIF orientation tag | `optimised`, lossy | Renders **upright**, not sideways. A rotated figure means `exif_transpose` did not run or ran after `draft()`. |
| 4.9 | A large annotated screenshot PNG (text and thin lines, over 1600 px) | `optimised`, and the line says **lossless** | Zoom into the text in the lightbox: crisp edges, no coloured haloes or ringing around letters. `lossy` on this line is the regression to catch. |
| 4.10 | A PNG with a transparent background | `optimised` | Transparency survives — the figure's background shows the page behind it, not black or white |

**4.11 — the same tree, twice.** Re-run `content_save /tmp/qa_images DemoDev`. The corrupt file warns
again, the run completes again, and no new objects appear in `media/content_engine/`.

**4.12 — clean up.** `rm -rf /tmp/qa_images` and
`uv run python manage.py danger_content_delete --yes` when finished, then re-run §0.3 if you want the
demo content back.
