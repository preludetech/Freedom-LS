# Frontend QA: miscellaneous small fixes

Eleven unrelated fixes made interactively, outside the SDD workflow. There is no spec and no plan —
`idea.md` is the whole brief — so this pass is the only gate the branch gets, and it has two jobs
rather than one:

1. **Confirm the eleven fixes landed**, and landed the way `idea.md` describes them.
2. **Confirm nothing else moved.** Several commits reached well past the item they were fixing.
   `get_cached_site()` learned to take `None`. `resolve_site_name()` was replaced by a new shared
   `site_display_name()`. `print.css` swapped ten theme-token fills for two new hex constants.
   `EMAIL_BACKEND` became a queueing backend in dev *and* prod. Two dev preview overrides were
   committed as `True`. Each of those is a wider blast radius than the one-line bug that prompted it.

§13 is the second job in one place: a read-only audit of everything that changed which no `idea.md`
item asked for.

**One failure is expected before you start.** See §3.6 — the form completion page is still missing
its Previous button. Record it as a failure; it is a real gap, not a stale check.

**A third job was added after the first QA pass.** Component styling was moved out of the shared
stylesheets and into the components themselves: `tailwind.picture_spotlight.css` and
`tailwind.base_interface.css` were deleted, `tailwind.components.css` lost 280 lines, seven theme
tokens were removed, and seven templates were restyled. **None of it is meant to change how
anything looks.** So §5 and the new §14 are a different kind of check from the rest of this plan:
everywhere else you are confirming an intended change, and there you are confirming its absence.
Treat any visible difference as a defect.

§14 lists the components that were restyled but whose look must not move. Read §5.25 before you
start — it wants a screenshot set captured from the commit *before* the restyle.

## 0. Setup

### 0.1 Build Tailwind first

`static/vendor/tailwind.output.css` is **not tracked in git**, and this branch rewrites what goes
into it. Component styling now lives in the component templates — as Tailwind utilities on the
markup, or a `<style>` block where no utility form exists — so the bundle must be recompiled before
those utilities exist at all.

```bash
npm run tailwind_build
```

**Skip this and every check in §5, §6 and §14 fails for the wrong reason.** It is the highest-value
step in this section.

Two files the plan below still refers to no longer exist: `tailwind.picture_spotlight.css` and
`tailwind.base_interface.css`. If either is present in your working tree, you are on the wrong
commit.

### 0.6 What dev pins, and why some expected values look wrong

Two settings will make you file false bugs if you do not read this first.

**The tenant is called "FirstClass", not "DemoDev".** `config/settings_dev.py` sets
`FORCE_SITE_NAME = "DemoDev"` but also `HEADER_TITLE = "FirstClass"`, and the new shared
`site_display_name()` is HEADER_TITLE-first. So email subjects, the site header and the report cover
must all say **FirstClass**. "DemoDev" is the Site row's name and is the fallback, not the answer.

**Every course is visible and free.** `OVERRIDE_COURSE_VISIBILITY_TO_VISIBLE` and
`OVERRIDE_COURSE_ACCESS_TO_FREE` are now committed as `True` — that is one of the changes under test
(§10), not a mistake, and you must **not** revert them. Older QA plans in `spec_dd/3. done/` tell you
to; ignore them. The consequence for every other section: the dashboard and `/courses/` show more
courses than a real learner would, and no paywall stops you. Anything that looks like a visibility or
access regression is almost certainly this.

Courses are reached by title from `http://127.0.0.1:$PORT/courses/` rather than by slug below, since
slugs are derived at ingest.

## 2. Mail is queued onto the background worker

`freedom_ls/deployment/mail.py` is new. `EMAIL_BACKEND` now names a `QueuedEmailBackend` in dev and in
production; the worker rebuilds each message from a JSON payload and sends it through
`EMAIL_UPSTREAM_BACKEND`. Dev's task backend is `ImmediateBackend`, so the task runs inline and Mailpit
still receives mail within the request — what dev buys is that the serialise/rebuild round-trip is
exercised every session instead of running first in production.

| Check | Expected |
| --- | --- |
| 2.1 | `uv run python manage.py check` is clean. In particular no `freedom_ls_deployment.E007`. |
| 2.2 | A password reset returns the browser response promptly and the mail still lands in Mailpit. |
| 2.3 | In Mailpit's source view, `Content-Transfer-Encoding: 8bit` on both the text and the HTML part, and no `=` soft line breaks anywhere. The 8bit patch is destroyed by serialisation and has to be re-applied by the worker — this check is the only thing that catches it if it is not. |
| 2.4 | A message with non-ASCII in subject and body arrives with correct characters, not mojibake. |
| 2.5 | A task row exists for the send and reached SUCCEEDED. Django admin → Task results. |

**2.6 — E007 fires when you point the queue at itself.** In `config/settings_dev.py`, temporarily set
`EMAIL_UPSTREAM_BACKEND = "freedom_ls.deployment.mail.QueuedEmailBackend"` and run
`uv run python manage.py check`.

- The check errors with `freedom_ls_deployment.E007`.
- The message says the upstream backend *is* the queue and no mail would ever be delivered.
- The hint names `EMAIL_UPSTREAM_BACKEND` as the thing to change, not `EMAIL_BACKEND`.
- Revert the line when done.

**2.7 — the worker is now load-bearing, and its failure is silent.** This is the most important check
in this section, because a deployment that runs no worker now swallows every password reset and
verification email without an error anywhere.

1. In `config/settings_dev.py`, temporarily point `TASKS` at
   `django_tasks_db.DatabaseBackend` (the production backend) rather than the immediate one.
2. With **no** worker process running, trigger a password reset.
   **Expect:** the browser flow completes normally, the mail does **not** arrive in Mailpit, and an
   unpicked task row sits in the database. That is the silent failure.
3. Start `uv run python manage.py fls_run_worker`.
   **Expect:** the mail now arrives, with its URL still unbroken (2.3 again — this is the path where
   the 8bit patch has genuinely been through serialisation).
4. Revert `TASKS`.

**2.8 — attachments and alternatives survive the JSON payload.**
`uv run python manage.py sendtestemail --admins` or an equivalent send carrying both an HTML
alternative and a binary attachment. Both must arrive intact; the attachment must open.

**2.9 — the documented consequence.** Rendered messages, live reset links included, now sit as
plaintext rows in the task-results table until housekeeping prunes them. Confirm
`docs/product/security-and-data-handling.md` says so. This is a documented trade-off, not a bug —
record it as a note if the docs are missing it.

## 5. Content widgets

Course **Content Widgets - Demo Reference**. The flashcards and accordions live in topic
**4. interactive-widgets**; the picture widget in topic **2. media**.

Nothing here is visible unless §0.1 ran.

**Every one of these three widgets now carries its own styling.** The flashcard, accordion and
picture used to be styled from `tailwind.components.css` (and, for the spotlight, from a stylesheet
of its own); they are now styled from their own templates. The accordion and picture are pure
Tailwind utilities on the markup with no CSS block at all; the flashcard keeps one small `<style>`
block for the answer-face prose, which `{% markdown back %}` generates and the template cannot
class directly.

So the checks below do double duty. Each one still tests the behaviour it always tested, and each
one is also the evidence that the conversion was faithful. **Do not accept "close enough" on any
visual check in this section** — an off-by-a-hair padding or a transition that now runs at a
different speed is exactly the failure mode a utility conversion produces.

| 5.2 | Both faces carry a "Tap to flip" hint with a retry icon, bottom-right. |

| 5.4 | Prose, bold text, links, inline code, tables and horizontal rules on the answer face are all legible against that tint — nothing keeps a colour meant for the plain surface. |

**5.8a — the second flashcard.** Topic 4 now carries a second card whose answer face holds a

It exists to make 5.4 checkable — the first card's answer is only bold text and paragraphs, so the

**5.8b — the answer face survives the token removal.** `--fls-flashcard-back-gradient`, `-fg`,

### Accordion

| Check | Expected |
| --- | --- |
| 5.9 | A closed accordion's summary is the normal text colour. |
| 5.10 | Hovering the summary tints its background, and the tint is clipped to the rounded corners rather than spilling into them. |
| 5.11 | Opening it shifts the summary text **and** the chevron to the brand primary colour, and rotates the chevron. |
| 5.12 | Keyboard focus draws a visible ring, inset so it is not clipped. |
| 5.13 | The summary row is visibly roomier than before, and the body's padding is unchanged. |
| 5.14 | A long title wraps without crushing the chevron, which stays pinned right. Topic 4 now carries a deliberately long summary for this; check it at desktop and at 375px. |

**5.14a — nested state does not leak.** The accordion's open-state rules name the full child path
from the `<details>` (`[[open]>&]`, `[[open]>summary>&]`) rather than matching any descendant, so an
accordion inside another accordion's body answers to its own open state. Author a nested pair, open
the outer one, and confirm the inner one stays closed, grey, and with its chevron unrotated. The
chevron and the body used to use any-descendant selectors and would have leaked; the summary colour
did not. If you would rather not author the case, record it as covered by inspection.

**5.14a-i — the chevron animates rather than snapping.** Tailwind's `rotate-180` sets the `rotate`
property, not `transform`, so the transition has to name `rotate`. Naming `transform` compiles
without complaint and silently snaps — which is exactly what happened once during this work. Watch
the chevron: it must sweep through the half-turn, not jump.

**5.14b — the disclosure triangle is gone in every engine.** No native marker beside the summary in
Chromium, and none in Firefox or WebKit if you have them. Both `marker:hidden` and the
`::-webkit-details-marker` reset are carrying this now.

### Picture

| Check | Expected |
| --- | --- |
| 5.15 | The `description` now renders **on the page**, under the caption. It used to appear only inside the lightbox. |
| 5.16 | That description runs the full width of the card — it does not stop short where the button starts. |
| 5.17 | "Figure N" sits in its own gutter in a mono face, with no `:` after it. Colour and typeface do the separating now. |
| 5.18 | The trigger button reads **Expand** (was "Open image"). |
| 5.19 | With a title that wraps to several lines — the demo content has a deliberately long one — the title's first line sits level with the Expand button, and later lines hang indented under the first. |
| 5.20 | The lightbox still opens, shows the heading and the description beneath it, and closes both on Escape and on its close button. |
| 5.21 | A picture with no `description` renders no empty paragraph and no stray gap. |
| 5.22 | A picture with no `number` still shows "Figure:" in the lightbox heading. |

**5.22a — the spotlight's open and close animation.** This is the single riskiest thing in the
whole change: the closed-dialog gating and the enter/leave transition were hand-written CSS and are
now Tailwind variants (`open:`, `starting:`, `transition-discrete`). A past QA bug came from
getting exactly this wrong. Open and close the spotlight several times and watch for all of:

- it fades and scales *in*, rather than appearing at full size instantly;
- it fades and scales *out* rather than vanishing on the first frame — the leave animation is what
  breaks first when `transition-discrete` is missing;
- a **closed** spotlight swallows no clicks. Click the page behind where the dialog would be,
  scroll, and click the Expand button of a *different* picture on the same page. If a closed dialog
  is covering the viewport, the second picture's button will not respond.

**5.22b — thirteen on one page.** Topic **2. media** renders 13 pictures. Every Expand button must
open its own image, and the page must not have grown a scrollbar or a layout shift. This is also
the page for the `<style>` count in §5.26.

**5.22c — the dialog's own padding.** The old `.spotlight-dialog` rule declared `padding: 1.5rem`,
but `p-0` on the markup sat in a later cascade layer and had been silently beating it — so the
effective padding has always been zero. The conversion preserves the effective value, not the
declared one. Confirm the spotlight card still reaches the viewport edges exactly as it did
before; if you think it should have breathing room, that is a **design change to raise
separately**, not a regression to file.

### Across themes and motion settings

**5.23 — run the flashcard and accordion checks again on the `first_class` theme.** The flashcard's
back gradient is mixed from `--color-primary`, so a different brand colour is the most likely way to
make the answer face illegible. This theme is also the proof that removing the four flashcard
tokens broke nothing: it never set them, and it must still get a coherent answer face for free.

**5.24 — reduced motion.** With `prefers-reduced-motion: reduce`, the flashcard still flips, the
accordion still opens and the spotlight still opens and closes; only the animation is dropped, not
the state change. Every one of those gates moved from a hand-written `@media` block to a
`motion-safe:` / `motion-reduce:` variant, so check all three rather than sampling one.

**5.25 — nothing moved. The primary gate.**

The whole restyle is meant to be visually inert, which is only checkable against a before.

1. Check out the commit **before** the restyle (`git log --oneline` — it is the last commit that
   still has `tailwind.picture_spotlight.css`), run `npm run tailwind_build`, and screenshot:
   the widgets demo topics 2 and 4, `/courses/`, the learner dashboard, a course detail page, and
   a player page with the side panel open — on **both** themes.
2. Return to the branch head, rebuild, and shoot the same set at the same viewport.
3. Compare pair by pair.

Any visible difference is a defect. Pay closest attention to: the accordion summary row's height
and hover tint, the flashcard's face padding and label positions, the picture caption's first line
sitting level with the Expand button, and the course card's corner radius, hero-band height and
body padding — those last three came from theme tokens that no longer exist.

**5.26 — the `<style>` blocks are where they should be, and no more of them.**

Component CSS that had no utility form now ships inside the component's template, so a component
rendered many times could in principle repeat its styles many times. Count the blocks in the
rendered DOM:

```js
document.querySelectorAll('style').length
```

| Page | Expected `<style>` blocks | Why |
| --- | --- | --- |
| Widgets topic **2. media** (13 pictures) | 1 | The side panel's. The picture widget is pure utilities and ships no CSS. |
| Widgets topic **4. interactive-widgets** (2 flashcards, 3 accordions) | 3 | The side panel's, plus one per flashcard. The accordion ships no CSS. |
| `/courses/` | 0 | No side panel on that shell. |

A count higher than the table says means a widget is emitting CSS it should be expressing as
utilities — record it. In DEBUG there is also the dev branch badge's block; do not count it.

## 13. What changed that nobody asked for

A read-only audit. Nothing here is a browser test; each item is either confirmed intentional or
written up under General notes in the report. None of it should be auto-fixed.

**13.2 — a hard-coded coupling.** The picture caption's title line carries
`py-[calc(0.375rem+1px)]` — `btn-sm`'s current padding plus its border — in order to line the
caption's first line up with the Expand button. The class it used to live in
(`.picture-figure-title`) is gone, so the value now sits as a utility directly on the markup in
`cotton/picture.html`, but the coupling is unchanged: changing `btn-sm` later will silently break
§5.19. Record the coupling; do not fix it.

**13.2a — a declaration that was already dead.** `.spotlight-dialog` declared `padding: 1.5rem`
while `p-0` on the markup, one cascade layer later, had always overridden it. The restyle kept the
effective value (zero) rather than the declared one, so nothing moved — but the original intent was
plainly the 1.5rem. Whether the spotlight *should* have that padding is a design question. Record
it; do not fix it.

**13.3 — a contributed-inlines seam that overwrites.** The learner-management admin *assigns*
`OrganisationAdmin.inlines` rather than appending to it, so a second app contributing inlines would
silently replace these. The parallel summaries registry does append correctly. Note only.

**13.4 — a context-key ordering hazard.** The form view sets `previous_url` in its context before
spreading the player chrome context over it, so if the chrome ever returned that key it would win
silently. It does not today. Note only.
