# Frontend QA: miscellaneous small fixes

Eleven unrelated fixes made interactively, outside the SDD workflow. There is no spec and no plan —
`idea.md` is the whole brief — so this pass is the only gate the branch gets, and it has two jobs
rather than one:

1. **Confirm the eleven fixes landed**, and landed the way `idea.md` describes them.
2. **Confirm nothing else moved.** Several commits reached well past the item they were fixing.
   `get_cached_site()` learned to take `None`. `resolve_site_name()` was replaced by a new shared
   `site_display_name()`. `print.css` swapped ten theme-token fills for two new hex constants.
   `EMAIL_BACKEND` became a queueing backend in dev, and a queueing backend production can opt
   into. Two dev preview overrides were committed as `True`. Each of those is a wider blast
   radius than the one-line bug that prompted it.

§13 is the second job in one place: a read-only audit of everything that changed which no `idea.md`
item asked for.

**Two failures are expected before you start.** See §3.6 — the form completion page is still
missing its Previous button. And see §13.1a — `upgrade_notes.md` covers only the styling move
and says nothing about the new `freedom_ls/mail` app, so a downstream taking this branch is not
told to add it to `INSTALLED_APPS`. Record both as failures; they are real gaps, not stale
checks.

**A third job was added after the first QA pass.** Component styling was moved out of the shared
stylesheets and into the components themselves: `tailwind.picture_spotlight.css` and
`tailwind.base_interface.css` were deleted, `tailwind.components.css` lost 280 lines, seven theme
tokens were removed, and seven templates were restyled. **None of it is meant to change how
anything looks.** So §5 and the new §14 are a different kind of check from the rest of this plan:
everywhere else you are confirming an intended change, and there you are confirming its absence.
Treat any visible difference as a defect.

**A fourth job arrived later still.** Learner monitoring was added to the Django admin — a
learner's page now gathers their cohorts, registrations and per-course progress, and the progress
changelists gained real filtering. That is a *new feature*, not a fix from `idea.md`, so §15 tests it
the way §7 tests the organisation page. Read §15's preamble before you start it: the seed fixtures
write progress records without going through the player, which makes two of the new columns read
wrong for reasons that are not defects.

**A fifth job arrived last.** Outgoing mail was pulled out into a `freedom_ls/mail` app of its
own, and production's default was changed back to sending inside the request, with queueing as
an opt-in. So there are now two supported mail configurations rather than one, and the branch is
only sound if **either** can be selected with a single setting and neither changes the mail a
learner receives. §2 was rewritten around that: §2.A is the invariant set, §2.B swaps the
backend and runs it again. Do not run §2 under one backend only.

**A sixth job is evidence.** The first pass ran §9 and the admin sections and left almost no pictures
behind — the report is a PDF nobody else opened, and §7 and §15 passed on prose alone. §9 now ends with
a set of rasterised report pages and a pixel measurement of the white-paper fix, and the new §16 names
the capture every changed admin surface owes. Neither adds an assertion; both make the ones already
there re-readable.

§14 lists the components that were restyled but whose look must not move. Read §5.25 before you
start — it wants a screenshot set captured from the commit *before* the restyle.

## 2. Mail, under either backend

The `freedom_ls/mail` app is new. It was extracted from `freedom_ls/deployment` and
`freedom_ls/base` part-way through this branch, and it now owns everything about outgoing mail:
the queueing backend, the worker task, the JSON serialiser, the 8bit encoder, the
`EMAIL_UPSTREAM_BACKEND` setting and a system check of its own.

**Two configurations ship, and both are supported.** Which one is in force is one setting:

| Configuration | `EMAIL_BACKEND` | What happens to a message |
| --- | --- | --- |
| **Direct** | `django.core.mail.backends.smtp.EmailBackend` | Sent inside the request. Production's default. |
| **Queued** | `freedom_ls.mail.backends.QueuedEmailBackend` | Serialised to JSON, put on the task queue; the worker rebuilds it and sends it through `EMAIL_UPSTREAM_BACKEND`. Dev's default; production opt-in via the `EMAIL_BACKEND` env var. |

Nothing else in the project knows which is in force — `EmailMessage.send()` resolves its connection
through `get_connection()`, so the setting catches every sender, allauth included. **That is the
property this section exists to prove.** A learner must not be able to tell from the mail they
receive which backend sent it.

So §2 is in four parts. **§2.A is the invariant set** — checks that must pass identically either
way. **§2.B swaps the backend and runs §2.A again**, which is the swappability gate. **§2.C** is
what only exists under the queue, and **§2.D** what only exists under direct send.

Dev's task backend is `ImmediateBackend`, so under the queue the task runs inline and Mailpit still
receives mail within the request. What dev buys is that the serialise/rebuild round-trip is
exercised every session instead of running first in production.

**One difference between the two is real and is not a defect.** The 8bit patch is applied in two
different places. The allauth adapter applies it to every mail *it* builds, so allauth mail is 8bit
under both backends. The queueing backend and the worker task apply it to *every* message that
passes through them, so under the queue a non-allauth send — `sendtestemail`, or anything a
downstream project sends — is 8bit too, and under direct send it is not. Check 2.3 is therefore
scoped to allauth mail. Do not file the difference on a test email.

### 2.A The invariants — every one must hold under both backends

### 2.B The swap

This is the gate. Dev ships the queued backend, so start there and swap to direct.

2. **Swap to direct.** Change that one line to
   `EMAIL_BACKEND = "django.core.mail.backends.smtp.EmailBackend"` and restart `runserver`.
   Change nothing else: `EMAIL_HOST`/`EMAIL_PORT` already point at Mailpit, and
   `EMAIL_UPSTREAM_BACKEND` is simply not read on this path.
3. Run every check in §2.A again, and §1.1–1.5 with it.
4. **Compare the two raw sources.** Subject, prefix, headers, both body parts and the reset URL
   must match apart from the per-message parts — Date, Message-ID, boundary strings and the token
   inside the URL. Any other difference is a finding.
5. Restore the dev line to `QueuedEmailBackend`.

| Check | Expected |
| --- | --- |
| 2.8 | Every §2.A check passes under the direct backend. |
| 2.9 | Every §2.A check passes under the queued backend. |
| 2.10 | The two raw messages differ only in their per-message parts. |
| 2.11 | Neither swap needs any other setting changed, and neither needs a migration, a rebuild or a data change. Swapping back and forth is one line each way. |
| 2.12 | `uv run python manage.py check` is clean in both configurations. |

### 2.C Under the queue only

| Check | Expected |
| --- | --- |
| 2.13 | A task row exists for the send and reached SUCCEEDED. Django admin → Task results. Its priority is 10 — ahead of report rendering and webhook delivery, so a person waiting on a password reset is not stuck behind a cohort report. |

**2.15 — E001 fires when you point the queue at itself.** In `config/settings_dev.py`, temporarily
set `EMAIL_UPSTREAM_BACKEND = "freedom_ls.mail.backends.QueuedEmailBackend"` and run
`uv run python manage.py check`.

- The check errors with `freedom_ls_mail.E001` — the mail app's id, not the retired
  `freedom_ls_deployment.E007`.
- The message says the upstream backend *is* the queue and no mail would ever be delivered.
- The hint names `EMAIL_UPSTREAM_BACKEND` as the thing to change, not `EMAIL_BACKEND`.
- Revert the line when done.

**2.16 — the worker is load-bearing, and its failure is silent.** The most important check in this
section, because a deployment that opts into queueing and then runs no worker swallows every
password reset and verification email without an error anywhere.

1. In `config/settings_dev.py`, temporarily point `TASKS` at `django_tasks_db.DatabaseBackend`
   (the production backend) rather than the immediate one.
2. With **no** worker process running, trigger a password reset.
   **Expect:** the browser flow completes normally, the mail does **not** arrive in Mailpit, and an
   unpicked task row sits in the database. That is the silent failure.
3. Start `uv run python manage.py fls_run_worker`.
   **Expect:** the mail now arrives, with its URL still unbroken and still 8bit (2.3 and 2.4 again —
   this is the path where the patch has genuinely been through serialisation and a database round
   trip).
4. Revert `TASKS`.

**2.17 — the documented consequence.** Rendered messages, live reset links included, sit as
plaintext rows in the task-results table until housekeeping prunes them. This is the queue's cost
and it does not exist under direct send. Confirm `docs/product/security-and-data-handling.md` says
so. A documented trade-off, not a bug — record it as a note if the docs are missing it.

### 2.D Under the direct backend only

**2.18 — E001 stays quiet under the direct backend.** With `EMAIL_BACKEND` on the SMTP backend
(§2.B step 2), set the same self-referential `EMAIL_UPSTREAM_BACKEND` and run `check` again. It must
be **clean**: the setting is not read on that path, and an error there would be a false alarm that
blocks a deployment which is not queueing at all. Revert both lines.

| Check | Expected |
| --- | --- |
| 2.19 | A password reset creates **no** `_send_email_task` row. Filter Task results by that task path across the send; other tasks a deployment fires are beside the point. The queue is genuinely out of the mail path, not merely bypassed at the last step. |
| 2.20 | No worker is needed. With `TASKS` on `django_tasks_db.DatabaseBackend` and no worker running, mail still arrives — the mirror of 2.16, and the reason direct send is production's default. |

**Known limitations — do not file these.** A failed send is not retried; a backend that returns 0
without raising is recorded as a success; and an enqueue joins whatever transaction is open, so a
rollback discards the mail silently. All three are known, and `spec_dd/1. next/retry-sent-emails/`
is the spec that addresses them. Note anything you see, but they are not defects in this branch.

## 5. Content widgets

Course **Content Widgets - Demo Reference**. The flashcards and accordions live in topic
**4. interactive-widgets**; the picture widget in topic **2. media**.

Nothing here is visible unless §0.1 ran.

**Every one of these three widgets now carries its own styling.** The flashcard, accordion and
picture used to be styled from `tailwind.components.css` (and, for the spotlight, from a stylesheet
of its own); they are now styled from their own templates. The accordion and picture are pure
Tailwind utilities on the markup with no CSS block at all; the flashcard keeps one small `<style>`
block for the answer-face prose, which `{% markdown back %}` generates and the template cannot
class directly.

one is also the evidence that the conversion was faithful. **Do not accept "close enough" on any
visual check in this section** — an off-by-a-hair padding or a transition that now runs at a
different speed is exactly the failure mode a utility conversion produces.

## 15. A learner's progress on their admin page

doing. Their journey now sits on their own page, and the progress changelists filter by whether an

**Read this first — two things will look like bugs and are not.** The seed fixtures write progress

## What to report

For every check: pass, fail or blocked, with the URL, the account used, a screenshot of anything that
failed, and the `runserver` traceback if there is one.

**§9's report pages and §16's admin captures are reported whether or not they failed.** They are the
pass's only durable evidence, and a report that names an image which is not in `screenshots/` is
reporting a check that was not run.

**§2.A is reported twice** — once under the queued backend and once under the direct one — and
the report must say which configuration each result came from. A §2.A result recorded without a
backend beside it is not a result. If the branch ships with only one of the two exercised, say
so plainly: the claim under test is that they are swappable, and half the evidence does not
support it.

The report must say explicitly that the **§13** findings are notes and human decisions rather than
bugs to fix. They belong under General notes, not in the fix loop.
