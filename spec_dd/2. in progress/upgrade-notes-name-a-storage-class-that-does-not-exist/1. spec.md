# Spec: correct the stale storage docs, and close the drift window

## Purpose

`spec_dd/3. done/2026-08-27_12:32_prod_bucket_setup/upgrade_notes.md` tells a downstream project to
point the `public` storage alias at `freedom_ls.deployment.storage.OverwritingFileSystemStorage`.
That class does not exist. Git dates the window: the class landed at 09:15 on 2026-08-27, the notes
were authored at 10:54, and a PR-review fix deleted the class at 11:18. Django resolves a callable
`storage=` while it imports the model, so a project following the prose gets an `ImportError` on that
dotted path. It does not boot and its test suite does not collect.

Ten more false or self-contradictory claims sit alongside it. `corrections_to_apply.md` holds the
row-by-row table and supersedes `research_upgrade_notes_claim_audit.md` wherever the two differ.

Separately, FLS's root `.env.example` never learned about the multi-bucket layout at all. It still
ships the single-bucket block and calls `AWS_STORAGE_BUCKET_NAME` an on/off gate, which is the
configuration `freedom_ls_deployment.E003` exists to reject. That file is what downstream projects
copy, so it matters more than the archive does.

The root cause is ordering. `/fls-dev:update_upgrade_notes` runs at todo step 11, PR review lands at
step 14, and nothing re-reads the notes in between.

## Scope

**In.** The archived `upgrade_notes.md`, corrected in place. The root `.env.example`. Two smaller
stale claims found by sweeping the rest of the doc surface. This spec's own `upgrade_notes.md`, which
is the only route by which the correction reaches a downstream project. A verification step in
`/fls-dev:update_upgrade_notes` and a re-verify item in the SDD todo template.

**Out.**

- A mechanical guard over the notes. An earlier draft of this spec proposed a pytest test resolving
  every backticked dotted path in an in-progress `upgrade_notes.md`, with a known-missing marker
  convention for names a document reports as deliberately gone. It is dropped. See "Why no guard".
- `First-Class-LMS`, which has not applied the notes and still declares the old two-key `STORAGES`.
  It will hit the boot failure when it pulls. That is that project's work.
- The archived `todo.md` line 85, which records the PR-review fix that deleted the class. It is an
  accurate historical record, not a false claim.
- Migration `0004`. `corrections_to_apply.md` rules it not a defect.

## Why no guard

The dropped design cost roughly 200 lines plus twelve tests plus a new markup convention. Against it:

- **It catches one of the eleven defects.** The wrong counts, the wrong exception name, the
  self-contradictions and the stale file path are not dotted paths.
- **Its scan set is empty.** No `upgrade_notes.md` exists under `spec_dd/2. in progress/` today.
  Twenty-one live under `3. done/`, which the guard would not read.
- **Its escape hatch would be routine.** The terminology-rename spec's notes name
  `freedom_ls.student_progress`, `freedom_ls.student_management` and `freedom_ls.student_interface`,
  all deliberately dead. `find_spec("freedom_ls")` succeeds, so all three become candidates and all
  three fail. Documenting a removal is what upgrade notes are for, so the guard would fire most often
  on correct documents.
- **The research already said so.** `research_notes_drift_mechanism.md` §4 concluded that a guard
  belongs after the exposure window closes rather than at authoring time.

The window needs no new hook either. `/sdd:address_pr_review` step 5 and `/sdd:finish_worktree` step 2
both already run the full suite. What was missing is that nothing re-reads the prose, which a
checklist item fixes for all eleven defect classes.

## Requirements

### A. The archived document

Rewrite `spec_dd/3. done/2026-08-27_12:32_prod_bucket_setup/upgrade_notes.md` against every row of
`corrections_to_apply.md` §1. Claims listed in its §4 "Claims that check out" survive unchanged.

The substantive changes: the nonexistent class becomes stock
`django.core.files.storage.FileSystemStorage` with `OPTIONS: {"allow_overwrite": True}`, which is one
edit with the contradictory "no `OPTIONS` key" instruction rather than two; `InvalidStorageError`
becomes `ImproperlyConfigured`; two checks become four; five per-bucket variables become six; the
blanket error count becomes the three traced states, of which the zero-error end state is the only
unconditional one and was never stated; the alias-counting convention is defined at first use and
held to; and the `env_example` citation points at a path that exists.

### B. The root `.env.example`

Port the storage block from `spec_dd/3. done/2026-08-27_12:32_prod_bucket_setup/env_example`, which
is accurate and is not edited. Three defects to close: no per-purpose bucket variables at all, the
"on/off gate" comment on `AWS_STORAGE_BUCKET_NAME`, and `AWS_QUERYSTRING_AUTH=False` presented as a
plain opt-in with no warning that its shared form reaches every media alias.

### C. The remaining stale claims

The rest of the doc surface is clean. `docs/deployment-security-checklist.md` already documents four
checks and six purposes correctly, and `claude_plugins/fls-dev/skills/file-storage/SKILL.md` is
accurate throughout. Two exceptions, plus one low-value third:

- `claude_plugins/fls-dev/resources/template_repo_manifest.md` says a file field names one of the
  six media aliases. There are five; `default` is the sixth key and explicitly not one of them.
- `docs/product/security-and-data-handling.md` describes only two of the four reports-storage failure
  modes. Product-doc rules forbid naming check ids, so the added modes are described, not numbered.
- `.claude/agent-memory/fls-dev-qa-data-helper/reference_legacy_report_prefix_staging.md` cites a line
  number for a six-alias, no-`OPTIONS` `STORAGES` dict that now has seven keys and one `OPTIONS` value.

### D. This spec's own upgrade notes

Authored later by `/fls-dev:update_upgrade_notes`. The content is fixed here because
`claude_plugins/fls-dev/commands/concrete/update_fls.md` steps 3a and 3c check the submodule out to
each spec's completion commit, so a downstream integrating `prod_bucket_setup` reads that tree's stale
notes and never sees the in-place fix.

Nothing shipped changes, so every frontmatter flag stays `false`/`[]` and `## Breaking changes` is
"None". `## Manual steps` restates the correction self-contained, without sending the reader to
another file: the substitution for the nonexistent class, four checks rather than two, six bucket
variables rather than five, ten errors rather than five from a shared-bucket start, and the refreshed
root `.env.example`. It closes with a line for the reader who already integrated `prod_bucket_setup`
and hit the `ImportError`.

Precedent: `spec_dd/3. done/2026-08-24_06:31_test_portability_4_upgrade_notes_and_docs/upgrade_notes.md:47`
corrects an earlier spec's stale docs the same way.

### E. The drift window

`claude_plugins/fls-dev/commands/update_upgrade_notes.md` reads the spec, the plan and
`git log/diff main..HEAD`. Nothing re-reads the final code, and its "Facts only" rule has no mechanism
behind it. It gains a verification step covering dotted paths, check ids, settings names and counts,
file paths and migration names, and an instruction to correct rather than trust an existing file on a
re-run. It stays depth 0 with no fan-out.

`claude_plugins/sdd/commands/protected/setup_todo_list.md` gains one §14 item, after the
`address_pr_review` line, to re-run `/fls-dev:update_upgrade_notes` once review feedback is addressed.
This spec's own `todo.md` gains the same item, so this run exercises it.

## Testing

No code changes, so nothing new is tested. `uv run pytest` is a regression check only.

## Success criteria

- `OverwritingFileSystemStorage` appears nowhere outside this spec's own working files.
- Every row of `corrections_to_apply.md` §1 is corrected in the archived document, and every claim in
  its §4 list is unchanged.
- The root `.env.example` declares all six `AWS_S3_<PURPOSE>_BUCKET_NAME` variables and no longer
  calls `AWS_STORAGE_BUCKET_NAME` a gate.
- `/fls-dev:update_upgrade_notes` names a verification pass, and the todo template schedules a re-run
  after PR review.
- `uv run pytest` and `uv run pre-commit run --all-files` pass.
