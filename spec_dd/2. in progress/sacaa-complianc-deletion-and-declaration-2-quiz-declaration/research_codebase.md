# Research: codebase touch points for the quiz declaration

Read-only, from this worktree. Paths are under `freedom_ls/` unless noted. It adds to `research_quiz_declaration.md` and does not repeat it. Line numbers there have drifted: `form_start` is now views.py:1919, `form_fill_page` 2060, `form_submit_and_exit` 2554 (all in `learner_interface/views.py`).

Settled by `answers.md`: own append-only model one-to-one with `FormProgress`; every attempt signs; no frequency setting; no skipping; no export columns, admin display only.

## 1. Routes into an attempt that a declaration gate must cover

All learner routes are in `learner_interface/urls.py`:

| URL name | Path | View | Writes? |
|---|---|---|---|
| `view_course_item` | `courses/<slug>/<index>/` | `view_form` (views.py:1848) | No. Start screen. Reads only, "the start screen reads, form_start writes" (1867-1868). |
| `form_start` | `.../start_form` (urls.py:37) | views.py:1919 | Yes. GET-reachable, mints the attempt. |
| `form_fill_page` | `.../fill_form/<page_number>` (urls.py:42) | views.py:2060 | Yes on POST: `submit_page` saves answers (2113) and may `complete()` (2136). |
| `form_submit_and_exit` | `.../submit-and-exit` (urls.py:52) | views.py:2554, `@require_POST` | Yes. Saves the posted page then `complete()` (2616, 2632). |
| `course_form_complete` | `.../complete` (urls.py:47) | views.py:2161 | Read only. Reads the latest completed attempt. |

- **No HTMX or separate answer-save endpoint exists.** Answers are saved only by a normal POST to `form_fill_page` or `form_submit_and_exit`. The only `hx-` use in learner_interface templates is `cotton/player-nav.html` (6), `_course_base.html` (1) and `partials/course_list.html` (2), which are navigation and listing. No other URLconf in `freedom_ls` names `form_progress` or `form_fill_page`. The commented-out `form_progress/<uuid:pk>/...` routes (urls.py:74-83) are dead.
- **`form_fill_page`.** It resolves the open attempt with `get_latest_incomplete` (views.py:2089-2093). If there is none it redirects to the start screen (2097-2102). A declaration check goes right after that, before `ensure_served_paper` (2104) and before the POST branch (2112). That ordering is the same one the existing gate uses ("a refused page must write nothing at all", 2074-2076). A learner who is not yet declared can be redirected to the declaration step or the start screen.
- **`form_submit_and_exit`.** It is reachable directly, and it finalises an open attempt (2603-2632). If an undeclared open attempt can exist, this endpoint would complete it, scored at zero, with no declaration. It also completes any attempt once the form is closed or access has ended (2593-2596). The gate is therefore not just "refuse the fill page". Either no undeclared sitting can exist, or `complete()` paths must tolerate or refuse it.
- **Course applications are not a quiz path in practice, but nothing forbids it.** `course_applications` has its own page flow (views.py:725-870, `submit_page` at 869, `complete()` at 952). It mints the sitting itself with `FormProgress.objects.create(user=user, form=course.application_form)` (views.py:165), so it bypasses `start_attempt` and `form_start`. `Course.application_form` is bound from the front matter path (content_save.py:1487-1498). Nothing restricts its `strategy`: grep of `course_applications` finds no `QUIZ` or `FormStrategy` use. A QUIZ form could therefore be named as an application form, and a declaration flag on it would not be enforced by a gate that lives only in `learner_interface`. Anonymous applicants have `FormProgress.user = None` (views.py:165, `allow_anonymous_form_progress` at 729), so the user to sign for does not exist. The options are: the validator rejects the declaration flag on a form named as `application_form`, or the flag is documented as ignored there. No existing validator ties the two together; the binding pass is in content_save.py:1478-1498.
- **Other creators bypass the views.** `qa_helpers` management commands call `FormProgress.complete()` directly (many in `qa_helpers/management/commands/`), and tests build attempts through `learner_interface/tests/helpers.py` (`form_attempt`, `course_with_form`). A model-level rule "a completed attempt must have a declaration" would break all of these, so the gate belongs in the views, not in `FormProgress.complete()`.
- **`form_start_page_buttons`** (utils.py:940) emits `start`, `try_again`, `continue`, `next` and `finish_course`. In `course_form.html`, `start` and `try_again` are both plain link buttons to `form_start` (lines 62-75), and `continue` goes straight to `form_fill_page` (56). A POST-based declaration therefore has to cover both the first start and every retry (each retry is a new attempt and signs again), and the template's start and try-again buttons need to become a form or a link to a declaration page.

## 2. Start and idempotency behaviour

- `form_start` order (views.py:1919-1977): login; course access decision (1923-1929); `_ensure_player_course_progress` (1930); `_blocked_item_redirect(..., refuse_closed=True)` (1937-1947), which "has to come before" minting; if `course_progress is None` redirect to the start screen (1949-1957); `start_attempt(...)` (1961); `ensure_served_paper` (1966); `resume_page_number` (1969); redirect to `form_fill_page` (1972). Any declaration step must come after the blocked and closed checks and before `start_attempt`, or the learner could sign for a sitting they are not allowed to open.
- `start_attempt` (learner_progress/attempts.py:140-168) runs in `transaction.atomic()` with `select_for_update()` on the `CourseProgress` row (155). Inside the lock it calls `get_latest_incomplete`, treats an open sitting as a double start if it was opened within `START_REUSE_WINDOW` = 10 s (attempts.py:32) and has no answers (157-161), otherwise runs `finalise_stale_incomplete`, then `get_or_create_incomplete` (168).
- `get_or_create_incomplete` (attempts.py:84-110) returns the open sitting if there is one, otherwise creates `FormProgress` and `CourseFormAttempt` together in `transaction.atomic()`. `FormProgress.objects.create` takes `site_id`, `user` and `form` only; there are no hook points for extra rows.
- `finalise_stale_incomplete` (attempts.py:113-137) does something only for `form.submit_on_exit`: it completes the open sitting, unless it is untouched since `kept_if_untouched_since` (the pause start). So with submit-on-exit, abandoning an undeclared sitting and starting again would finalise it as a completed, zero-score attempt with no declaration.
- Design consequences for idempotency:
  - **Declaration before the attempt exists (create both inside `start_attempt`'s lock).** The learner POSTs the declaration to a `form_start`-style endpoint. Inside the same `atomic()` block that holds the `CourseProgress` lock, the sitting is created and the declaration row is written. No undeclared sitting can exist, and a double POST either reuses the sitting through `START_REUSE_WINDOW` or hits the one-to-one unique constraint. This needs `get_or_create_incomplete` to accept an optional "create alongside" callback, or a wrapper. Note: sittings that already exist when a form is flagged (open and undeclared) still need a decision, either grandfathering or redirecting them to a declaration step.
  - **Declaration after the attempt exists (flag the sitting).** This lets `form_start` stay as is, but it leaves an undeclared open sitting that `form_fill_page`, `form_submit_and_exit` and `finalise_stale_incomplete` must all handle (section 1). It is more guard code and more ways to leak a zero-score completed attempt.
  - `ensure_served_paper` (form_engine/served_paper.py:45, conditional `update(... served_paper__isnull=True)` at 55) is the in-repo precedent for write-once, idempotent start data. A one-to-one `OneToOneField` unique constraint plus `get_or_create`/catching `IntegrityError` gives the equivalent for the declaration.
- Retakes: `completed_attempts` (attempts.py:195) and the "Try Again" path create a new `FormProgress` each time, so a one-to-one declaration per `FormProgress` gives "every attempt signs" with no extra logic.

## 4. Dependency edge for `get_client_ip`

- `docs/app_structure.md` already lists `form_engine --> accounts` (line 153) and the table row `form_engine | accounts, base, content_base, markdown_rendering, site_aware_models` (line 333). The edge exists because `form_engine.models` uses `get_user_model`/`User` and `form_engine/factories.py:11` imports `accounts.factories`. `accounts` does not depend back on `form_engine`. So importing `accounts.utils.get_client_ip` from `form_engine` adds no new edge.
- The call would normally be made in the `learner_interface` view (`learner_interface` already depends on `accounts`), which then hands the IP to the model write. `learner_interface/views.py` does not import `get_client_ip` today (no match).
- `get_client_ip` (accounts/utils.py:24) raises `PermissionDenied` when `TRUSTED_PROXY_IP_HEADER` is set and the header is missing or malformed; legal consent catches that and saves `ip or None` (accounts/forms.py:355-364 per the earlier report). The declaration view needs a decision on the same failure, since it would otherwise 403 at the step that lets a learner start a quiz.
- `form_engine/tests/invariants/test_import_independence.py` only probes `scoring`, `signals`, `submissions`, `typed_answers`, `phone_numbers` for importing `models`. A new helper module imported by `models.py` would need adding to that parametrised list if it must stay model-free. A model module in `models.py` itself is fine.

## 7. Erasure cascade

- `USER_ERASURE_CASCADE_MODELS` is a module-level `set[type[Model]]` in `accounts/admin.py:26`, seeded with `{LegalConsent}`. Apps that own audit models whose admin denies delete add themselves from their own admin module: `course_applications/admin.py:29-30` (`CourseApplication`, `AnonymousApplicant`), `learner_management/admin.py:279` (`Learner`), `referral_tracking/admin.py:92, 152-153`. `UserAdmin.get_deleted_objects` (accounts/admin.py:194-203) removes those models' verbose names from `perms_needed` so a superuser can delete a user whose cascade would otherwise be blocked by the read-only admins.
- **The new declaration model needs listing there if its admin denies delete.** Its FK path is user -> `FormProgress` (CASCADE) -> declaration (CASCADE, one-to-one to `FormProgress`). The cascade reaches it via `FormProgress`, so without the entry, deleting a user in the admin reports "permission needed for <declaration>" the moment a declaration exists. `FormProgress` itself is not in the set because its admin allows delete.
- **A second consequence: deleting a `FormProgress` from `FormProgressAdmin`** (e.g. a test sitting) collects the declaration. With a delete-denying read-only admin for it, Django's `get_deleted_objects` puts it in `perms_needed` and blocks that delete, because `FormProgressAdmin` is not the `UserAdmin` that filters `USER_ERASURE_CASCADE_MODELS`. Not verified by running it; the spec should check and decide (override `get_deleted_objects` on `FormProgressAdmin` to apply the same filter, or accept that sittings with a declaration cannot be deleted one by one). This sits next to the sibling spec `sacaa-complianc-deletion-and-declaration-1-force-delete` (in `spec_dd/2. in progress/`), which describes force delete as "the one erasure path" and its `research_user_deletion.md` lists delete-denying admins; coordinate so the two do not both rewrite `get_deleted_objects`.
- `FormProgress.form` is `PROTECT` (models.py:385), so deleting a Form already fails while sittings exist; a declaration adds nothing there.
- Models rows with `user = None` (anonymous applicants) have no user to cascade from; the declaration would not apply to them (section 1).
