# Spec: learners sign a declaration before each quiz attempt

Idea: `idea.md`. Answers: `answers.md`. Research: `research_*.md` in this directory.

## Purpose

An auditor checking a SACAA training organisation's quiz results needs evidence that the learner
attested to doing each quiz attempt themselves. A content author can make a quiz require a
declaration. Before the first page of every attempt the learner reads the declaration, ticks a box
and types their name. FLS stores the text as shown, the typed name, the time and the IP address
against that attempt, once, and never changes it. The record is attestation evidence, not identity
verification: the IP corroborates, it does not prove who sat the quiz.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `FormDeclaration` | coined | The signed declaration of one `FormProgress`: text shown, typed name, time, IP. No existing term; "declaration" appears in the code only in its CSS and Python senses. |
| **declaration quiz** | coined | A `Form` with `strategy` QUIZ and `requires_declaration` true. |
| **effective declaration text** | coined | `Form.declaration_text` when non-empty, else `form_engine.config.FORM_DECLARATION_DEFAULT_TEXT`. |

## Scope

In:

- Front matter keys `requires_declaration` and `declaration_text` on QUIZ forms, the model fields
  and the validator rules.
- A new `FormDeclaration` model, append-only.
- A declaration page in `learner_interface` between "Start Form" / "Try Again" and the first page,
  and a guard on every route into an attempt's pages.
- A new `form_engine` app setting for the default text.
- The declaration shown read-only on `FormProgressAdmin`.
- A demo course and product docs.

Out:

- Any frequency setting or reuse of an earlier signature: every attempt of a declaration quiz signs
  (`answers.md`). This replaces the idea's "every attempt / once per learner" setting.
- Declarations on surveys, applications or any non-QUIZ form.
- Comparing the typed name with the account name, or prefilling it.
- Export columns, and the educator attempt view: `sacaa-compliance-4-attempt-review` adds both and
  shows the declaration there.
- A site-level declaration text editable in the admin.
- A PostgreSQL trigger or HMAC column; storing the user agent.
- A learner-facing confirmation of the signed record.

## Decisions

- **The declaration is written in the same transaction that creates or resumes the attempt**, under
  `start_attempt`'s `CourseProgress` lock. Declaring after the attempt exists would leave unsigned
  open attempts that `form_submit_and_exit` and `finalise_stale_incomplete` could complete with no
  declaration.
- **Own model, one-to-one with `FormProgress`, `on_delete=CASCADE`.** "Never updated" is enforced in
  `save()` and in the queryset, and the admin is read-only (`answers.md`). Deleting the
  `FormProgress`, or the user through it, deletes the declaration; nothing here blocks the sibling
  force-delete spec.
- **No standalone admin for `FormDeclaration`; a read-only inline on `FormProgressAdmin` only.**
  Django's delete-permission check covers only registered `ModelAdmin`s, so without one, deleting a
  user or a `FormProgress` in the admin is not blocked by the declaration. `USER_ERASURE_CASCADE_MODELS`
  needs no entry.
- **The page re-checks the text it showed.** The form carries a SHA-256 of the effective declaration
  text it rendered. On a mismatch at submit nothing is stored and the page re-renders with the new
  text (`answers.md`).
- **The typed name is stored as typed** (`strip=False`); validation trims only to check it is
  non-empty.
- **The IP comes from `accounts.utils.get_client_ip`**, stored as `ip or None`. A `PermissionDenied`
  from it propagates, as it does at signup.

## Requirements

### Authoring: `form_engine/schema.py`, `form_engine/models.py`, `content_engine/validate.py`

1. Pydantic `Form` gains `requires_declaration: bool = False` and `declaration_text: str = ""`, beside
   `submit_on_exit`, each with a `Field(description=...)` that the offline reference picks up.
   Non-None defaults, because `save_with_uuid` drops `None` and would leave a removed key's old
   value in the database.
2. `validate_quiz_fields` rejects, with the existing error style (`"... should only be set when
   strategy is QUIZ (in {self.file_path})"`):
   - `requires_declaration` true, or `declaration_text` non-empty, on a non-QUIZ form;
   - `declaration_text` non-empty while `requires_declaration` is false.
3. A cross-file rule in `content_engine/validate.py`, called from the aggregate runner like
   `validate_form_shuffle`, rejects `requires_declaration: true` on a form a course names as its
   `application_form`. `course_applications` mints sittings itself, for anonymous applicants too, so
   no gate would run there.
4. Model `Form` gains `requires_declaration = BooleanField(default=False)` and
   `declaration_text = TextField(blank=True, default="")`, with `help_text`. `content_save` needs no
   change: same-named fields are saved by `save_with_uuid`.
5. `Form.effective_declaration_text()` returns the effective declaration text.

### Setting: new `form_engine/config.py`

6. `FormEngineConfig(AppSettings)` with `FORM_DECLARATION_DEFAULT_TEXT: str`, default a first-person
   statement under 100 words, e.g. "I declare that I am the person signed in to this account and that
   I am completing this quiz attempt myself, without help from anyone else. I understand that a false
   declaration may lead to my result being withdrawn." `config = FormEngineConfig()`, following
   `accounts/config.py`.

### Record: `form_engine/models.py`, migration `0015`

7. `FormDeclaration(SiteAwareModel)`:

   | Field | Definition |
   | --- | --- |
   | `form_progress` | `OneToOneField(FormProgress, on_delete=CASCADE, related_name="declaration")` |
   | `declaration_text` | `TextField()`: the effective declaration text exactly as rendered |
   | `typed_name` | `CharField(max_length=200)`: as typed |
   | `signed_at` | `DateTimeField(auto_now_add=True)` |
   | `ip_address` | `GenericIPAddressField(null=True, blank=True)` |

8. `save()` raises `ValueError` ("append-only") when the row already exists, using `_state.adding` as
   `LegalConsent.save()` does.
9. Its manager's queryset raises on `update()` and `bulk_update()` and composes with
   `SiteAwareManager`'s site filtering. `delete()` stays allowed so cascades work.
10. One migration, `0015`, adds the two `Form` fields and the model.
11. `form_engine/factories.py` gains `FormDeclarationFactory`.

### Starting an attempt: `learner_progress/attempts.py`

12. `start_attempt` takes an optional `declaration` argument (text, typed name, IP). Inside its
    existing `atomic()` block, after `get_or_create_incomplete`, it creates a `FormDeclaration` for
    the returned sitting when one is given and the sitting has none. A sitting that already has one
    (a double start within `START_REUSE_WINDOW`, or a resumed signed sitting) gets no second row. A
    second insert racing past the check is caught as `IntegrityError` and treated as already signed.
13. Two helpers in `form_engine`, the only places the rule lives:
    `form_requires_declaration(form, user) -> bool` (QUIZ strategy, `requires_declaration` true,
    user signed in) and `sitting_needs_declaration(form_progress) -> bool` (the same for the
    sitting's form and user, and the sitting has no `FormDeclaration`).

### Learner flow: `learner_interface/views.py`, `urls.py`, templates

14. New URL `.../declaration` named `form_declaration`, view `form_declaration`:
    - It runs the same access, blocked and closed checks as `form_start`, and the same
      `course_progress is None` redirect, before reading or writing anything. The plan extracts the
      shared prelude rather than copying it.
    - GET renders `learner_interface/form_declaration.html`.
    - POST validates a Django form: `agreed` (`BooleanField`, required), `typed_name`
      (`CharField(max_length=200, strip=False)`, non-empty after trimming), `text_hash` (hidden). On a
      field error or a hash mismatch it re-renders with HTTP 422 and stores nothing. On success it
      calls `start_attempt(..., declaration=...)` with the effective declaration text,
      `typed_name` and `get_client_ip(request)`, then `ensure_served_paper`, then redirects to
      `form_fill_page` at `resume_page_number`, as `form_start` does.
    - For a form that is not a declaration quiz it redirects to `form_start`.
15. `form_start`, for a declaration quiz, redirects to `form_declaration` unless the learner's open
    sitting (`get_latest_incomplete`) exists and is signed. It writes nothing on that redirect.
16. `form_fill_page` checks, after resolving the open sitting and before `ensure_served_paper` and the
    POST branch, whether that sitting still needs a declaration, and if so redirects to
    `form_declaration`, writing nothing. This covers "Continue Form", a direct link, and sittings
    opened before the author turned the declaration on.
17. `form_submit_and_exit` does the same check before saving or completing, and redirects to
    `form_declaration` without completing the sitting.
18. `form_declaration.html` reuses `course_form.html`'s layout (`<c-page flush="true">`, centred
    `max-w-xl` column, form title as heading, `<c-back-link>` to the start screen):
    - Lead line: "Before you start, read this declaration and sign it."
    - The effective declaration text, escaped, `linebreaks`, in a bordered block with an `id`, never a
      nested scroller.
    - The tick box in a `<label class="flex items-start gap-2">` as in `consent-checkboxes.html`,
      labelled "I make this declaration.", `aria-describedby` pointing at the text block.
    - "Full name" text input with `autocomplete="name"`, never prefilled, helper text "FLS stores your
      name with this declaration, the time and your IP address." linked by `aria-describedby`.
    - Field errors beside each field: "Tick the box to make the declaration." and "Type your full name
      to sign."; `aria-invalid` on a field in error; focus moves to the first error on a 422.
    - The text-changed case: a `<c-callout tone="error">` "The declaration has changed. Read it again
      and sign." with both fields cleared.
    - Submit button "Sign and start", always enabled.
19. The start screen's "Start Form" and "Try Again" buttons stay links to `form_start`, which
    forwards to the declaration page.

### Admin: `form_engine/admin.py`

20. `FormProgressAdmin` gets a read-only `FormDeclaration` inline modelled on
    `accounts.admin.LegalConsentInline`: `extra=0`, `can_delete=False`, every field read-only, add,
    change and delete permissions false. `FormDeclaration` gets no admin of its own.

### Demo content

21. A new demo course `demo_content/functionality_demo_quiz_declaration/` with one quiz that has
    `requires_declaration: true` and its own `declaration_text`, and a second that uses the default
    text. Existing demo quizzes are not changed.

## Testing

- Schema and validator: each rejection in requirements 2 and 3; a QUIZ with both keys passes; keys
  absent leave existing quizzes unchanged; removing the keys from front matter resets the model
  fields on the next `content_save`.
- `Form.effective_declaration_text()` falls back to the setting, and a project override of the
  setting is used.
- `FormDeclaration`: a second `save()` raises; `update()` and `bulk_update()` raise; a second row for
  one `FormProgress` fails; deleting the `FormProgress` or the user deletes it; site filtering
  applies.
- `start_attempt` with a declaration: one row on a new sitting; none added within
  `START_REUSE_WINDOW` (double POST); none added to a resumed signed sitting; added to a resumed
  unsigned sitting.
- Views, for a declaration quiz:
  - `form_start` with no open sitting redirects to `form_declaration` and creates no `FormProgress`.
  - GET `form_declaration` writes nothing; access, blocked and closed refusals match `form_start`.
  - POST success writes one `FormProgress`, one `CourseFormAttempt`, one `FormDeclaration` holding
    the exact rendered text, the name as typed (leading and trailing spaces kept) and the IP from
    `get_client_ip`, and redirects to the first page.
  - POST unticked, blank or whitespace-only name, or stale `text_hash`: 422, nothing written.
  - "Try Again" after a completed attempt asks again and stores a second declaration for the new
    sitting.
  - `form_fill_page` GET and POST and `form_submit_and_exit` on an unsigned open sitting redirect to
    `form_declaration` and write nothing (no answers, no `served_paper`, no completion).
  - A signed open sitting resumes straight to its page.
- A non-declaration quiz, a survey and an anonymous application flow behave exactly as today.
- Admin: the declaration shows read-only on the `FormProgress` change page; it cannot be added,
  changed or deleted; deleting a user and deleting a `FormProgress` in the admin succeed and remove it.
- Playwright: start a declaration quiz, see errors on an empty submit, sign, reach page 1; at the
  three QA viewports the name field is not hidden by the player footer.
- Demo content: the new course validates and saves.

## Open questions

- Q: What happens to an unsigned open sitting on a submit-on-exit quiz, opened before the author
  turned the declaration on, when the learner starts again? → A: `start_attempt` finalises it as
  today, so that one completed attempt has no declaration. (assumed default: only sittings that
  predate the setting are affected, and they never showed a declaration. Overrule by editing
  requirement 12.)
- Q: Is `declaration_text` with `requires_declaration: false` an error? → A: Yes, the validator
  rejects it. (assumed default: it catches an author who forgot the flag. Overrule by editing
  requirement 2.)
- Q: Does the learner see a confirmation that their declaration was recorded? → A: No. (assumed
  default: the idea asks only for the admin view. Overrule by editing Scope.)
- Q: What if `get_client_ip` raises `PermissionDenied` (proxy header configured but missing)? → A: It
  propagates as a 403, as at signup. (assumed default: a missing trusted header is a
  misconfiguration that signup already refuses. Overrule by editing Decisions.)

## Success criteria

- A QUIZ with `requires_declaration: true` cannot show any page of an attempt, by any route, until
  that attempt has a `FormDeclaration`.
- Every attempt of such a quiz, retakes included, has exactly one `FormDeclaration`, holding the text
  rendered on the page, the name as typed, a server time and the client IP or null.
- A `FormDeclaration` cannot be changed through `save()`, `update()`, `bulk_update()` or the admin.
- `requires_declaration` or `declaration_text` on a non-QUIZ form, or on an application form, fails
  validation.
- Quizzes without the keys, surveys and applications behave exactly as before.
- The declaration is visible read-only on the `FormProgress` admin page, and deleting a user or
  `FormProgress` in the admin removes it without a permission error.
