# Spec: learners sign a declaration before each quiz attempt

Idea: `idea.md`. Answers: `answers.md`. Research: `research_*.md` in this directory.

## Purpose

An auditor checking a SACAA training organisation's quiz results needs evidence that the learner
attested to doing each quiz attempt themselves. A content author can make a quiz require a signed
declaration before the first page of every attempt. The record is attestation evidence, not identity
verification: the IP corroborates, it does not prove who sat the quiz.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `FormDeclaration` | coined | The signed declaration of one form progress record (`FormProgress`): text shown, typed name, time, IP. No existing term; "declaration" appears in the code only in its CSS and Python senses. |
| **declaration quiz** | coined | A `Form` with `strategy` QUIZ and `requires_declaration` true. |
| **effective declaration text** | coined | `Form.declaration_text` when non-empty, else `form_engine.config.FORM_DECLARATION_DEFAULT_TEXT`. |
| **open sitting** | narrowed | The learner's incomplete form progress record at a placement, as `learner_progress/attempts.py` `get_latest_incomplete` returns it. |

"Attempt" in this spec means one sitting, which is one form progress record and its course form
attempt.

## Scope

In:

- Front matter keys `requires_declaration` and `declaration_text` on QUIZ forms, the model fields
  and the validator rules.
- A new `FormDeclaration` model, append-only.
- A declaration page in `learner_interface` between "Start Form" / "Try Again" and the first page,
  and a guard on every route into an attempt's pages.
- A new `form_engine` app setting for the default text.
- The declaration shown read-only on `FormProgressAdmin`.
- A demo course and product docs.

Out:

- Any frequency setting or reuse of an earlier signature: every attempt of a declaration quiz signs
  (`answers.md`).
- Declarations on surveys, applications or any non-QUIZ form.
- Comparing the typed name with the account name.
- Export columns (`sacaa-compliance-4-attempt-review` adds them). The educator attempt view: whichever
  of this spec and `sacaa-compliance-4-attempt-review` lands second shows the declaration there.
  Attempt review is blocked on the educator interface refactor, so it is expected to land second.
- A site-level declaration text editable in the admin.
- A PostgreSQL trigger or HMAC column; storing the user agent.
- A learner-facing confirmation of the signed record.

## Decisions

- **The declaration is written in the same transaction that creates or resumes the attempt**, under
  `start_attempt`'s `CourseProgress` lock. Declaring after the attempt exists would leave unsigned
  open sittings that `form_submit_and_exit` and `finalise_stale_incomplete` could complete with no
  declaration. The lock serialises two POSTs for one record, so the insert needs no `IntegrityError`
  handling; the one-to-one constraint is the backstop.
- **`FormDeclaration` is one-to-one with `FormProgress`, `on_delete=CASCADE`.** Deleting the form
  progress record, or the user through it, deletes the declaration; nothing here blocks the sibling
  force-delete spec.
- **No standalone admin for `FormDeclaration`; a read-only inline on `FormProgressAdmin` only.**
  Django's delete-permission check in `get_deleted_objects` covers only models registered with a
  `ModelAdmin`, so deleting a user or a form progress record in the admin is not blocked by the
  declaration, and `accounts/admin.py` `USER_ERASURE_CASCADE_MODELS` needs no entry.
- **The page re-checks the text it showed** with a SHA-256 of the effective declaration text it
  rendered, so the stored text is always the text on screen (`answers.md`).
- **A closed quiz finalises an unsigned open sitting unsigned.** Only sittings opened before the author
  turned the declaration on can be unsigned, and they never showed one.

## Requirements

### Authoring: `form_engine/schema.py`, `form_engine/models.py`, `content_engine/validate.py`

1. Pydantic `Form` gains `requires_declaration: bool = False` and `declaration_text: str = ""`, beside
   `submit_on_exit`, each with a `Field(description=...)` that the offline reference picks up.
   Non-None defaults, because `save_with_uuid` drops `None` and would leave a removed key's old
   value in the database.
2. `validate_quiz_fields` rejects, with the existing error style (`"... should only be set when
   strategy is QUIZ (in {self.file_path})"`):
   - `requires_declaration` true, or `declaration_text` non-empty, on a non-QUIZ form;
   - `declaration_text` non-empty while `requires_declaration` is false.
3. A cross-file rule in `content_engine/validate.py`, called from the aggregate runner like
   `validate_form_shuffle`, rejects `requires_declaration: true` on a form a course names as its
   `application_form`. It reuses `resolve_author_path` and the parsed `Course.access_config`, and the
   `content_save` comment that calls itself the one core reader of that key is updated to name both.
   `course_applications` mints sittings itself, for anonymous applicants too, so no gate would run
   there.
4. Model `Form` gains `requires_declaration = BooleanField(default=False)` and
   `declaration_text = TextField(blank=True, default="")`, with `help_text`.
5. `Form.effective_declaration_text()` returns the effective declaration text.

### Setting: new `form_engine/config.py`

6. `FormEngineConfig(AppSettings)` with `FORM_DECLARATION_DEFAULT_TEXT: str`, following
   `accounts/config.py`, default:

   > I declare that I am the person signed in to this account and that I am completing this quiz
   > attempt myself, without help from anyone else. I understand that a false declaration may lead to
   > my result being withdrawn.

### Record: `form_engine/models.py`, migration `0015`

7. `FormDeclaration(SiteAwareModel)`, added with the two `Form` fields in one migration:

   | Field | Definition |
   | --- | --- |
   | `form_progress` | `OneToOneField(FormProgress, on_delete=CASCADE, related_name="declaration")` |
   | `declaration_text` | `TextField()`: the effective declaration text exactly as rendered |
   | `typed_name` | `CharField(max_length=200)`: as typed, untrimmed |
   | `signed_at` | `DateTimeField(auto_now_add=True)` |
   | `ip_address` | `GenericIPAddressField(null=True, blank=True)` |

8. `save()` raises `ValueError` ("append-only") when the row already exists, using `_state.adding` as
   `LegalConsent.save()` does.
9. `objects` is `SiteAwareManager.from_queryset(...)` over a queryset whose `update()` and
   `bulk_update()` raise. Site filtering still applies; `delete()` stays allowed so cascades work.

### Starting an attempt: `learner_progress/attempts.py`, `form_engine`

10. `start_attempt` takes an optional `declaration` argument (text, typed name, IP). Inside its
    existing `atomic()` block, after `get_or_create_incomplete`, it creates a `FormDeclaration` for
    the returned sitting when one is given and the sitting has none. When a declaration is given
    and the open sitting has no `FormDeclaration` and no answers, `start_attempt` reuses and signs
    it, as it does a double start, instead of finalising it: the guards mean nothing was served for
    it, so it is not a sitting the learner left. This covers a sitting opened before the author
    turned the declaration on.
11. Two helpers in `form_engine`, the only places the rule lives:
    `form_requires_declaration(form, user) -> bool` (QUIZ strategy, `requires_declaration` true,
    user signed in) and `sitting_needs_declaration(form_progress) -> bool` (the same for the
    sitting's form and user, and the sitting has no `FormDeclaration`).

### Learner flow: `learner_interface/views.py`, `urls.py`, templates

12. New URL `.../declaration` named `form_declaration`, view `form_declaration`:
    - It runs the same access, blocked and closed checks as `form_start`, and the same
      `course_progress is None` redirect, before reading or writing anything.
    - GET renders `learner_interface/form_declaration.html`.
    - POST validates a Django form: `agreed` (`BooleanField`, required), `typed_name`
      (`CharField(max_length=200, strip=False)`, non-empty after trimming), `text_hash` (hidden). On a
      field error or a hash mismatch it re-renders with HTTP 422 and stores nothing. On success it
      calls `start_attempt(..., kept_if_untouched_since=_latest_pause_start(course_progress),
      declaration=...)` with the effective declaration text, `typed_name` and
      `get_client_ip(request)` stored as `ip or None` (a `PermissionDenied` propagates), then
      `ensure_served_paper`, then redirects to `form_fill_page` at `resume_page_number`, as
      `form_start` does.
    - For a form that is not a declaration quiz, or while the open sitting is already signed, it
      redirects to `form_start` on GET and POST, so a second signature never ends an attempt in
      progress.
13. `form_start`, for a declaration quiz, first finalises a signed open sitting the learner left
    (submit-on-exit forms only, by the same double-start and pause rules as `start_attempt`), under
    the course progress lock. It then redirects to `form_declaration` unless an open sitting is left
    and is signed, writing nothing on that redirect. A signed open sitting still open is resumed as
    it stands, without `start_attempt`, so `form_start` never mints an unsigned sitting. The start
    screen's buttons stay links to `form_start`.
14. `form_fill_page` checks `sitting_needs_declaration` after resolving the open sitting and before
    `ensure_served_paper` and the POST branch, and if true redirects to `form_declaration`, writing
    nothing. This covers "Continue Form", a direct link, and sittings opened before the author turned
    the declaration on.
15. `form_submit_and_exit` makes the same check before saving or completing, and redirects to
    `form_declaration` without completing the sitting, except when the form is closed or access has
    ended: then it finalises the sitting unsigned, as it does today.
16. `form_declaration.html` reuses `course_form.html`'s layout with a `<c-back-link>` to the start
    screen, and carries this copy and behaviour:
    - Lead line: "Before you start, read this declaration and sign it."
    - The effective declaration text, escaped, with `linebreaks`, in the page flow (no nested
      scroller).
    - A tick box labelled "I make this declaration.", with `aria-describedby` pointing at the text.
    - A "Full name" input with `autocomplete="name"`, never prefilled, helper text "Your name is
      stored with this declaration, the time and your IP address." linked by `aria-describedby`.
    - Field errors beside each field: "Tick the box to make the declaration." and "Type your full name
      to sign."; `aria-invalid` on a field in error; focus moves to the first error on a 422.
    - On a hash mismatch, a `<c-callout tone="error">` "The declaration has changed. Read it again
      and sign." with both fields cleared.
    - Submit button "Sign and start", always enabled.

### Admin: `form_engine/admin.py`

17. `FormProgressAdmin` gets a read-only `FormDeclaration` inline modelled on
    `accounts.admin.LegalConsentInline`: `extra=0`, `can_delete=False`, every field read-only, add,
    change and delete permissions false.

### Demo content

18. A new demo course `demo_content/functionality_demo_quiz_declaration/` with one quiz that has
    `requires_declaration: true` and its own `declaration_text`, and a second that uses the default
    text. Existing demo quizzes are not changed.

## Testing

Beyond a test per requirement:

- Removing the keys from front matter resets the model fields on the next `content_save`.
- A project override of `FORM_DECLARATION_DEFAULT_TEXT` is used.
- `FormDeclaration.objects` still filters by site.
- `start_attempt` with a declaration adds no second row within `START_REUSE_WINDOW` (double POST) or
  to a signed open sitting, and adds one to an unsigned open sitting.
- POST `form_declaration` with an unticked box, a blank or whitespace-only name, or a stale
  `text_hash` returns 422 and writes nothing. A successful POST keeps leading and trailing spaces in
  `typed_name`.
- A paused submit-on-exit sitting signed through `form_declaration` is kept, as through `form_start`.
- "Try Again" after a completed attempt asks again and stores a second declaration for the new
  sitting.
- `form_fill_page` GET and POST and `form_submit_and_exit` on an unsigned open sitting write nothing
  (no answers, no `served_paper`, no completion); on a closed quiz `form_submit_and_exit` completes it
  unsigned.
- A non-declaration quiz, a survey and an anonymous application flow behave exactly as today.
- Admin, as a non-superuser staff member holding only the delete permissions: deleting a user and
  deleting a form progress record succeed and remove the declaration.
- Playwright: start a declaration quiz, see errors on an empty submit, sign, reach page 1.

## Open questions

- Q: What happens to an unsigned open sitting on a submit-on-exit quiz, opened before the author
  turned the declaration on, when the learner starts again? → A: `start_attempt` finalises it as
  today, so that one completed attempt has no declaration. (assumed default: only sittings that
  predate the setting are affected, and they never showed a declaration. Overrule by editing
  requirement 10.)
- Q: What happens to an unsigned open sitting that already holds answers, on a quiz without
  submit-on-exit, opened before the author turned the declaration on? → A: The learner signs it
  when they next start and keeps their answers, so its `signed_at` is later than those answers.
  Only sittings that predate the setting are affected. (decided in review of PR 294)
- Q: What happens to a signed open sitting on a submit-on-exit quiz that the learner left, when
  they start again by any route? → A: `form_start` finalises it as for any submit-on-exit quiz, and
  the learner signs again for the next attempt. A double start within `START_REUSE_WINDOW`, or a
  sitting kept by a pause, is resumed. The declaration page never takes a second signature while a
  signed sitting is open: it sends the learner to `form_start`. (decided in review of PR 294)
- Q: What if `get_client_ip` raises `PermissionDenied` (proxy header configured but missing)? → A: It
  propagates as a 403, as at signup. (assumed default: a missing trusted header is a
  misconfiguration that signup already refuses. Overrule by editing requirement 12.)

## Success criteria

- No page of an attempt at a declaration quiz is served, by any route, while
  `sitting_needs_declaration` is true for it (except finalising on a closed quiz).
- Every attempt at a declaration quiz started after deploy has exactly one `FormDeclaration`.
- `FormDeclaration.objects.update(...)` and a second `save()` raise.
- `requires_declaration` or `declaration_text` on a non-QUIZ form, or on an application form, fails
  validation.
