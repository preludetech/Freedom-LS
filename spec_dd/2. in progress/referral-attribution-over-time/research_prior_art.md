# Research: prior art for referral attribution over time

Question: what has already been tried for tracking referral attribution over time rather than only at signup, here or elsewhere, and what happened?

Limits: no shell, so no `git log`. The done-spec artefacts, shipped code and the First-Class-LMS downstream stand in for history. Web results for "post-mortems" turned up almost none: the public record is vendor guides and support docs, not failure write-ups. That is stated where it matters. This file avoids repeating `research_attribution_models.md` (model vocabulary, window numbers, Django packages) and `research_existing_referral_tracking.md` (mechanics of the shipped app). It adds what neither says.

## 1. Here: nothing has been tried, and it was deferred on purpose

**No earlier attempt exists.** No code, comment, TODO or migration in `freedom_ls/referral_tracking/` anticipates multi-touch, last-touch or payouts (confirmed in `research_existing_referral_tracking.md` section 9). The only roadmap entries are the downstream ones: `apis-for-lead-monitoring-6-conversions` is blocked by this spec, and `referral-tracking-external-referer-first-touch` "must agree with the touch list" here (`spec_dd/1. next/roadmap.md` lines 180, 238).

**First-touch-only was a decision, not an omission.** The shipped `referal_tracking` spec (`spec_dd/3. done/2026-09-10_18:18_referal_tracking/1. spec.md`, line 13) says the approach is "first touch only, a signed first-party cookie as the only durable store" and "not reopened". Its idea file accepted the cost in terms: "There is no multi-touch path and no time from first click to signup, because nothing connects a particular landing to the particular person who later signed up." It added that joining forward to outcomes stays possible because the row keys on the user. Its own research recommended full multi-touch be skipped as over-engineering for an admin-only product (`research_attribution_capture.md` lines 105-111).

**What the earlier research warned about that this spec now meets.**
- `research_attribution_capture.md` finding 1: mixing first-touch `ref` with last-touch UTMs in one row yields a combination that never happened together (HubSpot keeps two full parallel sets, "Original Source" and "Latest Source"). Relevance: the idea's frozen `first_referral_code` / `last_referral_code` pair on `Conversion` is the parallel-sets shape, not the mixed-row shape. That is the established-practice answer. Sources there: https://www.iv-lead.com/hubspot-by-iv-lead/understand-original-and-latest-source-properties, https://www.terminusapp.com/blog/hubspot-utm-tracking-definitive-guide/.
- The same file (finding 2) records the session-row footgun: writing to `request.session` on anonymous GETs created "10K session rows in one day". The idea avoids sessions; live touches only run for authenticated users, so no new session row is created. Keep that property when adding the authenticated branch: `request.user` resolves the session, which the idea limits to tracked GETs after the view returns. https://docs.djangoproject.com/en/5.0/topics/http/sessions/

**Decisions in the shipped `referral-links` spec that this idea reverses or must reconcile with** (quoted via `research_existing_referral_tracking.md` section 9):
- "A referral code reaches attribution only as a first touch. The shipped cookie is frozen on the first tracked landing and this work does not change that." (`referral_links/1. spec.md:70-71`). This spec is the planned supersession. It should say so, since the two statements are in conflict until it lands.
- "Attribution rows hold the code text, not a foreign key. They are written once from the cookie, and codes are never reused." (`:75-76`). The idea keeps text-not-FK, but "written once" no longer holds for the new tables (they are append-only, many rows per user). "Codes are never reused" is what makes frozen text safe for payout: the admin refuses delete and `ReferralCodeHit` is `PROTECT`. A payout query that calls `lookup_referral_code` is safe only because of that.
- "The code's `ref` always wins, and otherwise the visitor's query wins. Letting a visitor-typed `ref` survive would let anyone re-attribute a landing." (`:59-61`). Multi-touch makes the same attack cheaper: any logged-in learner can append a touch to their own timeline by typing `?ref=THEIRCODE`, and the idea's live-touch branch writes it straight to a row. The idea's Open questions list self-referral as out of scope. The prior decision shows the project already treated visitor-supplied `ref` as a re-attribution vector once; the new write path (live touch, no `/go/` involvement) bypasses the `build_redirect_url` protection entirely.

**Prior failures in this app that bear on the design.**
- `referral-links` QA B1 (fixed in e7682f4): a stored code that no longer matches `CODE_PATTERN` made the admin change form 500 with `NoReverseMatch`. Stored code text predates current rules. A payout query or resolver must treat `referral_code` as opaque stored text and never reverse a URL from it (`research_prior_art.md` of `apis-for-lead-monitoring-3`, section 1b).
- `more_lead_admin_exports` QA B1: a late change to the shared `SiteAwareModelResource` altered the `is_active` rendering of a resource the spec said was untouched. The idea adds two resources subclassing the same base; any change to that base for them will reach the other four.
- `referral-links` QA: hit-count assertions were fragile because probe requests inflate counters. Tests for the new middleware should build touches through factories, not by driving the middleware, except where the middleware is the subject.
- `apis-for-lead-monitoring-3` prior art (section 2a): `hit_at` and `signed_up_at` are stamped in Python before commit, so a timestamp cursor can miss late-committing rows. The idea's `occurred_at` (not `auto_now_add`) is further from commit time than either, by design. The API spec already decided touches and conversions order on `recorded_at`, not `occurred_at`. Keep `recorded_at` indexed for that (the idea indexes `occurred_at` and `(site, user, occurred_at)` only).

## 2. Here: First-Class-LMS, the downstream consumer

Path: `/home/sheena/workspace/first_class/First-Class-LMS.git/main`. It has no attribution-over-time code, but it imports `referral_tracking.capture` and is the one real consumer of the cookie shape. **The idea's cookie change as written breaks it.**

- `apps/lead_forms/models.py:5-12`: `FIRST_TOUCH_FIELDS = tuple(name for name in COOKIE_KEYS if name != "first_seen")`. The idea adds `"touches": "t"` to `COOKIE_KEYS`. That makes `touches` a member of `FIRST_TOUCH_FIELDS`, which `apps/lead_forms/admin.py:79,81` puts in the admin fieldsets and `readonly_fields`. Admin system checks would then fail on a field that is not a model field. `apps/lead_forms/tests/test_models.py:119` asserts the dataclass fields equal `{*FIRST_TOUCH_FIELDS, "first_seen"}`.
- `apps/lead_forms/services.py:64-74,81-88`: `first_touch_fields_from_cookie` returns `{**cookie, "first_seen": ...}` and `save_lead` splats it into `LeadSubmission(**...)`. If `read_attribution_cookie` returns the list under any key, `LeadSubmission(touches=[...])` raises `TypeError` on the next lead form submission by a visitor who holds a multi-touch cookie. A cookie with no `t` key (every pre-upgrade cookie) still works, so the failure appears only after the first repeat landing, which is the worst kind of latent break.
- `apps/lead_forms/middleware.py:33-80` (`ExternalRefererCaptureMiddleware`) mints a cookie for untagged external landings and returns early if any cookie exists. It will not append touches. That is consistent with the answer in `answers.md` ("leave it to the external-referer spec"), but it means a visitor who first arrives untagged from a search engine, then follows a partner link, gets a touch list that starts at the partner link only if the earlier cookie lacks the external touch. Worth stating, because the roadmap note says the two specs must agree.
- Whatever shape the spec picks, the safe options are: keep `COOKIE_KEYS` as the first-touch map only and hold the list key in a separate constant; or have `read_attribution_cookie` strip the list and expose it through a separate reader. The downstream test at `test_models.py:119` is exactly the kind of equality assertion the idea's own "Testing" section flags for in-repo tests, but this one lives outside the repo and will not appear in a grep of `freedom_ls/`.

(Also noted: First-Class holds the `submodules/Freedom-LS` checkout, so the upgrade note should tell the downstream project about this edge.)

## 3. Elsewhere

### 3a. Written precedent for the decisions the idea makes

No published post-mortem of "we moved from first-touch-at-signup to a touch timeline" was found. A search for affiliate attribution disputes returned vendor guides and no documented case outcomes. What the sources do agree on, with the idea's decision each supports:

- **Store the full path, not only the winner.** "Platforms storing only the last click cannot retroactively apply multi-touch models"; multi-touch needs "tracking infrastructure that captures and stores the full conversion path, not just the final click", with timestamps, source identifiers and campaign parameters per interaction. Supports the idea's "timeline is the capture". https://track360.io/blog/affiliate-attribution-models-operators-guide-2026
- **Separate the payout policy from the analytic model, and write the rule down before a dispute.** Recommended pattern: commission attribution fixed in the agreement, multi-touch used for insight even if payouts stay last-click. Supports the idea's "no credit rule is baked in", with the caveat that deferring the rule is only safe if someone does write it before the first payment. The idea's Open questions do not name "who sets the credit rule, and when" as an open item. https://www.rootabl.com/blog/first-click-vs-last-click-attribution (search result; page not fetched), https://www.referralcandy.com/blog/attribution-models-for-affiliate-programs (search result; not fetched)
- **Ambiguity in the tracking data is the common thread in disputes**: "cookies can be overwritten, browser sessions lost, click timestamps conflict" (search summary; sources: https://www.tracknow.io/blog/multi-touch-attribution-affiliate-marketing/75, https://www.modash.io/blog/affiliate-attribution-models). The idea's `recorded_via` field (live vs flush) and the unique `(site, user, occurred_at, key_hash)` constraint address the timestamp-trust half of that. It has no answer for "the cookie was lost", which leaves a silent gap in a timeline that looks complete.
- **Disputes concentrate on coupon and loyalty partners** under first-click, and on awareness partners under last-click; "pure first-click creates as much distortion as last-click, just in the opposite direction" (same search summary). Supports recording both ends. Position-based 40/40/20 is the stated compromise, and the idea's pair of first/last codes cannot compute the middle 20%; only the raw touches can. The idea's PROTECT on both FKs means middle touches are prunable even when the conversion rests on them. That is a conscious trade, consistent with "frozen pair is the payout record".
- **Audit before changing a model.** The same guide suggests exporting 90 days of conversions with click history and counting those with multiple affiliate touchpoints before changing model. The idea ships no such view; the admin export of both tables serves it, but only once real data exists. Existing accounts start with empty timelines (upgrade note in the idea), so the first 90 days are the evidence base.

### 3b. What a mainstream affiliate vendor actually does

PartnerStack documents last-click: the most recently clicked referral link is tied to later sign-ups and transactions, a competing partner's click replaces the earlier cookie, and the cookie lasts 90 days from click, with a re-click restarting the window (search summary of https://support.partnerstack.com/hc/en-us/articles/360009312753-Cookie-windows-and-attribution-logic and https://support.partnerstack.com/hc/en-us/articles/360019537774; the page itself returned 403 to a fetch, so these are secondhand). Two consequences for the idea:
- The idea deliberately differs: a repeat landing does **not** extend the cookie (non-rolling 90 days from first touch). PartnerStack restarts the window on re-click. The idea's reasoning (a rolling window never closes for an active visitor) is sound, but it means a visitor re-clicking a partner link on day 85 gets a touch whose in-play life ends at day 90 from the first touch, not from the re-click, so it may not reach a conversion on day 100 that a vendor-style window would have credited. `touches_in_play` is judged against `when - 90 days` per touch, so the DB side does not share the cookie's cut-off, but a touch can only reach the DB if the cookie is alive when the visitor logs in or signs up. This difference between "the cookie's life" and "a touch's own window" is worth an explicit sentence in the spec.
- Rewardful and FirstPromoter: no documentation of an option to keep the first referrer was found; do not assume a vendor offers "first wins" as a setting. Rewardful's own guidance (cited in `research_attribution_models.md`) is to pick one model deliberately and stay consistent, because switching changes who is paid for the same events.

### 3c. Browser behaviour that limits what a touch timeline can capture

Covered in `research_attribution_models.md` section 4 (Safari ITP, Chrome caps). One point it does not make: the idea's design depends on a **server-set, HttpOnly, first-party** cookie surviving, and its flush-at-login path depends on the browser returning that cookie after weeks. Lost cookies produce a timeline with a hole and no marker of the hole. Nothing in the idea lets a reader distinguish "no touches happened" from "the cookie did not survive". The existing `utm_source="direct"/"none"` fallback on `SignupAttribution` is the only precedent for recording absence, and the idea's Conversion records "both codes blank" as "nothing was in play", which conflates the two.

## 4. Lessons for the spec

1. **Fix the `COOKIE_KEYS` hazard before design settles.** First-Class-LMS builds a model field list, an admin fieldset and a `LeadSubmission(**cookie)` call from `COOKIE_KEYS` and the cookie reader's output (section 2). Adding `"touches": "t"` to `COOKIE_KEYS` and returning the list from `read_attribution_cookie` breaks it. Choose a separate constant/reader, or state the downstream change in `upgrade_notes.md` and give the downstream project a test. The idea's "Documentation and downstream" section names no downstream breakage.
2. **State that this spec supersedes two shipped decisions** ("reaches attribution only as a first touch"; "written once"), and that "codes are never reused" is the property the text-not-FK approach rests on.
3. **Decide who writes the credit rule and when**, even if the answer is "the business, before the first payout, in the program terms". Every source says disputes follow from an unwritten rule; the idea's decision to bake in none makes this a real dependency, not a footnote.
4. **Name the tampering surface the live-touch branch opens.** A logged-in learner can add a touch with a typed `?ref=`. The shipped spec treated visitor-typed `ref` as a re-attribution vector. Self-referral is listed as out of scope, but the specific new route (authenticated tracked GET, no `/go/`) deserves a sentence, and a test that records what is stored, since the answer is "it is stored, because we log what was typed".
5. **Resolve the cookie-life vs touch-window difference** (3b). Either state that a touch's eligibility ends 90 days after the *first* touch for cookie-borne touches and 90 days after the touch itself for live ones, or align them.
6. **Record absence distinctly, or say the conflation is accepted.** A lost cookie and "nothing happened" look identical in a Conversion with blank codes (3c).
7. **Index `recorded_at`** if the API spec orders on it (section 1).
8. **Test strategy:** prior regressions were caused by shared-base changes (`SiteAwareModelResource`) and by equality assertions that silently pinned old behaviour. The idea already lists three tests to replace; add a grep-level check of downstream imports of `COOKIE_KEYS` to the plan.
9. **Expect no public failure data.** The research found none. Treat the shape (timeline plus frozen pair, first and last side by side, no baked-in rule) as consistent with vendor guidance, not as proven by someone's post-mortem.
