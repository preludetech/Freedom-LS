# Frontend QA: referral attribution over time

The feature has no learner-facing screen. QA checks it end to end in a browser: tracked landings,
signup, login, the learner actions that convert, and the two new read-only admin pages.

## Setup

- Start the server: `uv run python manage.py runserver $PORT`. Base URL `http://127.0.0.1:$PORT`.
- Admin login: the `## QA Login` credentials in `.claude/sdd/config.md`.
- Use a fresh browser context (no cookies) for each anonymous visitor below. The attribution cookie is
  `fls_attribution` (HttpOnly; read it from the browser's cookie store, not `document.cookie`).
- Data needed (use the QA data helper if missing): one published course open to self-registration,
  one course with an application form, one coming-soon course, and a referral code `PARTNERA` and
  `PARTNERB` in admin (`/admin/` → Referral tracking → Referral codes). Tagged landings below use
  `?ref=` directly so they do not depend on code rows existing.

## Test 1: anonymous touches, then signup (success criterion 1)

1. Fresh context. Visit `/?ref=PARTNERA`. Expect a `fls_attribution` cookie to be set.
2. Visit `/?ref=PARTNERA` again. Expect the cookie value unchanged.
3. Visit `/?gclid=abc123`. Expect the cookie value unchanged.
4. Visit `/?ref=PARTNERB&utm_source=newsletter`. Expect the cookie value to change (an entry was
   appended) and the response to carry `Cache-Control` with `private` and `no-store`.
5. Sign up a new account (`/accounts/signup/`) with a fresh email.
6. Expect the signup response to delete `fls_attribution` (cookie gone afterwards).
7. As admin, open Referral tracking → Attribution touches, search the new email. Expect two rows,
   `recorded_via` `signup_flush`, codes PARTNERA and PARTNERB, `occurred_at` the landing times. No row
   for the `gclid` landing.
8. Open Referral tracking → Conversions, search the email. Expect one `account_signup` row, target
   label "Account signup", first code PARTNERA, last code PARTNERB.
9. Open Signup attributions. Expect exactly one row for the account, first touch PARTNERA (unchanged
   behaviour).
10. As the new account, start an application on the course with an application form. Back in admin,
    expect a `course_application` conversion with the course title, first PARTNERA, last PARTNERB.

## Test 2: existing account, live touch, interest (success criterion 2)

1. Log in as an existing learner with no touches.
2. Visit `/?ref=PARTNERA`. Expect no `fls_attribution` cookie to be set.
3. Open the coming-soon course and click Express interest.
4. Admin: one `live` touch for PARTNERA, and one `course_interest` conversion naming PARTNERA as first
   and last, label the course title.
5. Click Express interest again (or reload the page in its interested state). Expect no second
   conversion.
6. Visit `/?ref=PARTNERA` again while signed in. Expect no second touch (repeat skipped). Visit
   `/?ref=PARTNERB`, then `/?ref=PARTNERA`. Expect two more touches (A, B, A is three).

## Test 3: login flush

1. Fresh context. Visit `/?ref=PARTNERB`. Cookie set.
2. Log in as an existing learner. Expect the cookie deleted on the login response.
3. Admin: a `login_flush` touch for PARTNERB on that learner.
4. Log out and log in again with no new landing. Expect no new touch and no error.

## Test 4: anonymous application claimed (success criterion 3)

1. Fresh context. Visit `/?ref=PARTNERA`, then apply anonymously for the course that allows it,
   using a fresh email.
2. Open the claim link from the email (dev mail output / console) in the same browser and complete
   the claim.
3. Admin: a `course_application` conversion for the new account, first code PARTNERA, `occurred_at`
   matching when the application was started (not the claim time), and an `account_signup`
   conversion beside it.
4. Reload the claim link. Expect no second `course_application` conversion.

## Test 5: self-registration and reactivation

1. Signed-in learner: visit `/?ref=PARTNERA`, then self-register for the open course.
2. Admin: one `course_registration` conversion naming PARTNERA. The learner lands in the course
   player as before.
3. Visit the self-registration URL again. Expect no second conversion.
4. Admin: deactivate that learner's registration (existing educator/admin flow), then have the learner
   self-register again. Expect the registration active again and still only one
   `course_registration` conversion.

## Test 6: admin pages are read-only, filter and export

1. Attribution touches changelist: columns for the codes, UTM source and campaign, occurred at and
   recorded via; a `recorded via` filter; date drill-down on occurred at; no Add button.
2. Open a touch: every field read-only, no Save or Delete button. Submitting the change URL by hand
   (POST) persists nothing.
3. Conversions changelist: columns user, kind, target label, both codes, occurred at; filters on kind
   and **code in play**.
4. Enter `partnera` (lower case) in code in play and submit. Expect every conversion whose first or
   last code is PARTNERA, and none other.
5. Click Export with that filter applied. Expect a CSV holding only the filtered rows and columns: id,
   user email, kind, target label, occurred at, first referral code, first touch occurred at, last
   referral code, last touch occurred at, window days. A cell starting with `=` is escaped.
6. A staff user without view permission on these models cannot see them or export them.
7. Admin user erasure (Accounts → Users → delete a learner with touches and conversions): the
   confirmation lists attribution touches and conversions; confirming succeeds and removes them.

## Test 7: nothing else broke

1. `/go/PARTNERA` (an active code) redirects and sets no cookie, as before.
2. An untracked page (`/`) for an anonymous visitor sets no cookie.
3. Signup with no prior landing still works and writes a direct-traffic Signup attribution, and an
   `account_signup` conversion with both codes blank.
4. Starting an application, expressing interest and self-registering all still work for a learner
   who never landed through a code (conversion with blank codes, no error page).
