# Research: what "signed up for a course" means in this codebase, and where a join/report may legally live

Scope: `freedom_ls/referral_tracking` currently imports only `accounts`, `base`,
`site_aware_models` (confirmed in `docs/app_structure.md:139-141`, runtime edges;
no test-only edges for `referral_tracking` either). Any new cross-app edge below
is called out explicitly.

Notes:
- `LearnerCourseRegistration` and `CohortCourseRegistration` key on `Learner`, not `User`, directly. `Learner` itself is keyed on `User` + `Organisation`. So tracing "this user registered for this course" always requires a join through `Learner`.
- `CohortCourseRegistration` never names an individual learner at all — a learner gets access to the course by `CohortMembership`, and the "moment" a cohort's course grant reaches a given learner is really the *later* of "cohort's `registered_at`" and "this learner's `CohortMembership` timestamp" (whichever is later — see `learner_progress/signals.py` fan-out logic, §7).

## 2. Who initiates each one, and when

| Model | Initiator | View / entry point | Timestamp meaning |
|---|---|---|---|
| `CourseApplication` | **Learner**, through `apply` view | `course_applications:apply` → `views.apply` (`course_applications/views.py:52-101`, URL `course_applications/urls.py:8`) | `created_at` = the moment the applicant (or a concurrent duplicate request, `get_or_create` is race-safe per the comment at `views.py:39-41`) started the application. ## 3. The application flow end to end (`CourseApplication`)

- Entry: `apply` view (`course_applications/views.py:52-101`), reached at `apply/<slug:course_slug>/` (`urls.py:8`).
- `_start_application()` (`views.py:32-49`) does `CourseApplication.objects.get_or_create(user=user, course=course)` inside `transaction.atomic()`. If the course names an `application_form` (`Course.application_form`, referenced at `views.py:44`) and the application has no `form_progress` yet, a `FormProgress` is created (`FormProgress.objects.create(user=user, form=course.application_form)`, line 45-47) and attached via `app.form_progress` (`OneToOneField`, `RESTRICT` on delete, `course_applications/models.py:51-57`).
- **Distinct submitted moment**: `CourseApplication.is_submitted` (`models.py:72-83`) is a property, not a field: `form_progress is None or form_progress.completed_time is not None`. So:
  - Course with **no** application form: `is_submitted` is `True` the instant the row is created — `created_at` **is** the submission moment (confirmed by the docstring at `views.py:64-66`).
  - Course **with** an application form: the applicant works through `application_form_page` (`views.py:174-238`) and `application_check_answers` (`views.py:241-301`). The actual submission moment is `form_progress.complete()` (called at `views.py:256`, inside `application_check_answers` POST handling when `unanswered` is empty), which sets `FormProgress.completed_time = timezone.now()` (`form_engine/models.py:339-344`, idempotent — the "mark once" logic at line 341-342). **`completed_time` on the `FormProgress`, not any field on `CourseApplication` itself, is the true submission timestamp** for a form-gated application; `CourseApplication.created_at` only marks when the draft was started.
  - NOTE in the model docstring (`course_applications/models.py:24-29`) says a future "application review" feature will add `state`, `submitted_at`, `decided_at`, transitions, etc. — **not built yet**; do not assume `submitted_at` exists.
- `course_access` gating: `raise_404_if_hidden_unregistered` (`course_access/visibility.py`, called at `views.py:77` and `course_interest/views.py:54,87,109`) 404s a hidden course for a non-registered user before either flow proceeds. `ApplicationCourseAccessBackend` (`course_applications/backends.py:45-212`) is the access backend that makes a course application-gated in the first place (`get_access`, lines 103-166): an unregistered visitor on an `application_gated` course gets `can_self_register=False` and a "Apply now" CTA pointing at `course_applications:apply`; a returning applicant gets a CTA to their status page instead of a new application.

### `CourseInterest` flow
- No form/sitting involved — a single `get_or_create` at click time (`course_interest/views.py:58` or `116`). There is no separate "submitted" moment; `created_at` is definitive for whichever row currently exists (but see §1's note on deletion losing history).
- Gated the same way: `raise_404_if_hidden_unregistered` (lines 54, 87, 109) and a `course.visibility != CourseVisibility.COMING_SOON` → HTTP 422 check (line 55-56) so interest can only be expressed in a course's coming-soon state.

## 4. Reactivation and re-registration (where the "when" is silently destroyed)

Three confirmed spots where a row is flipped back to active rather than a fresh row created, each losing the *later* moment as a distinct timestamp:

1. **`ensure_learner()`** — `freedom_ls/learner_management/utils.py:51-73`. `Learner._base_manager.update_or_create(site=organisation.site, user=user, organisation=organisation, defaults={"is_active": True})`. Docstring (lines 59-63) is explicit: "reactivates a row that was previously removed... a fresh enrolment is a live signal of re-association." `created_at` (`auto_now_add`) is untouched on reactivation, so it keeps recording the *first* association only.
2. **`initiate_course_access` self-registration** — `freedom_ls/learner_interface/views.py:864-868`. `LearnerCourseRegistration.objects.update_or_create(learner=learner, course=course, defaults={"is_active": True})`. Comment at lines 861-863 explains the choice explicitly: "update_or_create, not get_or_create: defaults only apply on create, so a registration an admin had deactivated would stay inactive and the learner would be bounced back out of the course they just asked to enter." `registered_at` is `auto_now_add`, so re-registering after a staff-driven deactivation **does not move `registered_at` forward** — the field will read the *original* registration time even though the learner is acting again, right now, possibly under a *different* attribution touch than the one in play originally.
3. **`Learner.is_active` model docstring** itself (`learner_management/models.py:59-63`) names this pattern as deliberate project policy, not an oversight — so any attribution design must treat `Learner.created_at` and `LearnerCourseRegistration.registered_at` as **lower bounds on "first ever", not the timestamp of the most recent qualifying action**.

No equivalent reactivation logic was found for `CohortCourseRegistration` or `CohortMembership` (`is_active` on `CohortCourseRegistration` is only ever set from the admin form directly — `CohortCourseRegistrationAdminForm`, no `update_or_create` call site found for it outside tests/factories).

## 5. Where a cross-app join could live

### `freedom_ls/reports/` app
- Dependency edges today (from `docs/app_structure.md:142-149, 224`): runtime → `accounts, base, content_engine, form_engine, learner_management, learner_progress, organisations, site_aware_models`; test-only → `role_based_permissions`. **No edge to `referral_tracking`, `course_applications`, or `course_interest` today.** Adding `reports -> referral_tracking` (or `-> course_applications` / `-> course_interest`) would be a **new edge**, per the project's own rule in `docs/app_structure.md:5` that it must be "called out and approved before code is written."
- Structure: `reports/models.py` — one model, `GeneratedReport` (a per-cohort PDF job: `status`, `requested_by`, `requested_at`, `file`, one-inflight-per-cohort partial unique index — lines 42-93). `reports/gather.py` — pure assembly of a frozen `CohortReportData` dataclass tree from data already loaded by `reports/indexes.py` (`gather.py:1-10` docstring: "the only module in the report pipeline that queries" is `indexes.py`; `gather.py` "issues no queries of its own"). `reports/indexes.py` is the actual **queries module** — batched, site-explicit loaders (`load_cohort`, `load_registrations`, `load_roster`, etc., `indexes.py:1-15` docstring) returning frozen bundles, explicitly because the background task that runs this has no HTTP request/ambient site (`indexes.py:7-9`). `reports/render.py` renders the PDF (not read in depth here). `reports/views.py` (no `urls.py` — wired only into the admin namespace via `GeneratedReportAdmin.get_urls()`, `reports/views.py:1-6`) exposes `generate_report_view` (POST creates a `GeneratedReport` row and enqueues `_generate_cohort_report_task` via `django.tasks.default_task_backend`, `reports/views.py:83-101`) and `download_report_view` (streams the PDF, `reports/views.py:109-132`). `reports/admin.py` registers `GeneratedReportAdmin`, entirely read-only for the model fields, with custom `get_urls()`/action wiring the generate/download views (`reports/admin.py:23-135`).
- **No management commands** in `reports/` (confirmed: `Glob freedom_ls/reports/management/**` → no files). **No CSV export module** either (only PDF, via `render.py`+WeasyPrint, not investigated further here) — `reports` does not use django-import-export at all today; that pattern lives only in `referral_tracking` (see below) and `site_aware_models`.
- `reports/admin.py` and `reports/views.py` both key off `Cohort` (from `learner_management`), and `reports/checks.py` / `reports/config.py` / `reports/factories.py` / `reports/at_risk.py` / `reports/report_data.py` / `reports/signals.py` / `reports/tasks.py` were not read in full — the existing report is cohort-progress/quiz-confusion-oriented, not signup/attribution-oriented; nothing in it currently reads `referral_tracking`, `course_applications`, or `course_interest`.

### `freedom_ls/dev_tools/` and `freedom_ls/qa_helpers/` — house convention for a cross-app management command
- `dev_tools` runtime deps: `accounts, base, content_engine, form_engine, learner_management, learner_progress, organisations` (`docs/app_structure.md:210`); test-only → `course_applications`. Its one command, `create_demo_data.py` (`dev_tools/management/commands/create_demo_data.py`), uses **`djclick`** (`import djclick as click`, but the `Command` class here is actually plain `django.core.management.base.BaseCommand`/`CommandParser` per lines 14-16/70-77 — this file mixes both: it imports `djclick` but subclasses `BaseCommand` directly with `add_arguments`/`CommandParser`). It imports across apps directly (`from freedom_ls.learner_management.models import Cohort, CohortMembership`, `from freedom_ls.learner_management.utils import ensure_learner`, line 20-21) — i.e. the house convention for a dev/ops command that must read or write another app's models is a **plain runtime import**, gated by `require_dev_tools_enabled` (`dev_tools/guard.py`, imported line 19) rather than by any app-boundary indirection.
- `referral_tracking`'s own command, `prune_referral_code_hits.py` (`referral_tracking/management/commands/prune_referral_code_hits.py`), instead uses **pure `djclick`** (`@click.command()` / `@click.option(...)`, lines 20-22) with `click.echo(...)` for output (line 36-38) — no CSV, just a summary line and a batched delete loop (`PRUNE_BATCH_SIZE = 1000`, lines 17, 26-34). This is the closer precedent for a `referral_tracking`-owned command.
- `qa_helpers` runtime deps span nearly every app (`docs/app_structure.md:124-138`) — by design, it is the one app allowed to import broadly for QA fixture generation; its ~50 commands (`qa_helpers/management/commands/*.py`) are not a precedent for production reporting code, only for how a cross-cutting command is structured (also `djclick`-based per the naming convention `qa_*`, not verified line-by-line here).
- **No CSV-writing management command exists anywhere in the codebase.** The only CSV output path is django-import-export through the admin (see next point). If a new report/export needs CSV, either extend `reports` (new edge to whatever source app) or add it to `referral_tracking`'s own admin exports (no new edge, but the join would have to be expressed as a query *from* `referral_tracking` context, which cannot import the course-signup apps either, per the constraint in this feature's brief).

### `django-import-export` resources / admin exports — house pattern
- `freedom_ls/site_aware_models/admin_exports.py` defines the shared base: `SiteAwareModelResource(ModelResource)` (lines 65-79) drops the `site` column and swaps in `IsoDateTimeWidget`/`IsoDateWidget` (ISO-8601 rendering regardless of Django's date-format settings, lines 47-63); `FormulaSafeCSV(CSV)` (lines 33-44) escapes formula-trigger leading characters and prepends a UTF-8 BOM.
- `freedom_ls/referral_tracking/resources.py` is the concrete pattern to follow: one `*Resource(SiteAwareModelResource)` per exportable model, each `Meta.model = ...`, and a `Field(attribute="user", widget=ForeignKeyWidget(get_user_model(), "email"))` override (lines 19-25) when a FK should export by a human-readable column (email/code) instead of a raw pk. `referral_tracking/admin.py` wires each via `resource_classes = [...]` on a `SiteAwareExportModelAdmin` subclass (e.g. lines 44-77, 218-251), with the exported models kept **fully read-only** in the admin (`has_add_permission`/`has_change_permission`/`has_delete_permission` all `False`, e.g. lines 63-74, 100-111).

## 6. Generic FK precedent

Three GFK usages found; all under `django.contrib.contenttypes`:

1. **`CohortDeadline` / `LearnerDeadline` / `LearnerCohortDeadlineOverride`** (`freedom_ls/learner_management/models.py:159-314`). Each declares `content_type = models.ForeignKey(DjangoContentType, on_delete=models.SET_NULL, null=True, blank=True)`, `object_id = models.UUIDField(null=True, blank=True)`, `content_item = GenericForeignKey("content_type", "object_id")` (e.g. lines 167-174). Indexed only implicitly through the partial unique constraint (`condition=models.Q(content_type__isnull=False, object_id__isnull=False)`, e.g. lines 179-184) — no separate `models.Index` on `(content_type, object_id)` for these three. These point at whatever concrete content item a deadline targets (`Topic`/`Form`, both of which `learner_management` **already imports** at runtime — `content_engine` and `form_engine` are both in `learner_management`'s dependency list, `docs/app_structure.md:108-113`). **This is GFK-for-polymorphism within an already-allowed import graph, not GFK used to avoid a new edge.**
2. **`ObjectRoleAssignment`** (`freedom_ls/role_based_permissions/models.py:82-121`). `content_type = models.ForeignKey(ContentType, on_delete=models.CASCADE)`, `object_id = models.CharField(max_length=255)`, `target = GenericForeignKey("content_type", "object_id")` (lines 90-95), with an explicit composite index `models.Index(fields=["content_type", "object_id", "role", "is_active"])` (line 117). The docstring says it "Assigns a role to a user scoped to a specific object (e.g. a Course)" (line 83) — **and `role_based_permissions`'s own dependency list is `accounts, base, site_aware_models` only** (`docs/app_structure.md:150-152, 225`), with **no runtime or test-only edge to `content_engine`** at all. **This is the direct precedent asked for**: a GFK used specifically so an app can point at a row in an app it does not import and is not permitted to import, by relying on `ContentType`/generic pk instead of a real FK.
3. No GFK was found anywhere pointing specifically *across* the exact boundary `referral_tracking` would need (into `course_applications`/`course_interest`/`learner_management` registration models), but pattern (2) is the established, in-house way to do it without adding an edge.

## 7. Signals precedent

### `post_save` / custom-signal receivers reacting to another app's model
- `freedom_ls/learner_progress/signals.py` (connected via `LearnerProgressConfig.ready()` → `from freedom_ls.learner_progress import signals`, `learner_progress/apps.py:10-11`) has three receivers, each named explicitly against a `learner_management` model — an app `learner_progress` **already imports** at runtime (`docs/app_structure.md:114-118`):
  - `@receiver(post_save, sender=LearnerCourseRegistration)` → `ensure_course_progress_on_learner_registration` (`signals.py:180-198`)
  - `@receiver(post_save, sender=CohortCourseRegistration)` → `ensure_course_progress_on_cohort_registration` (`signals.py:201-213`)
  - `@receiver(post_save, sender=CohortMembership)` → `ensure_course_progress_on_cohort_membership` (`signals.py:216-227`)
  - Design notes worth reusing: each checks `raw` and skips on fixture loads (`if raw: return`, e.g. line 189-192); each wraps its side effect in `transaction.on_commit(...)` (lines 198, 211-213, 226) specifically so a concurrent reader never sees a half-committed fan-out (comment at lines 174-177); there is **deliberately no `post_delete` counterpart** — "removing a membership, withdrawing a registration and deactivating a learner are access decisions, and none of them retires work already recorded" (lines 170-172).
  - These receivers also call `fire_webhook_event("course.registered", {...})` (`signals.py:143` onward, e.g. announced only on `created=True` for the individual-registration receiver, line 198's `announce=created`) — i.e. the webhook is fired *from inside* the same receiver that reacts to the foreign model, not the other way around.
- `freedom_ls/organisations/signals.py:44` — `@receiver(post_save, sender=Site)` reacts to `django.contrib.sites.models.Site`, a Django-framework model, not cross-app in the FLS sense.
- `freedom_ls/reports/signals.py:15` — `@receiver(post_delete, sender=GeneratedReport)` reacts to its own app's model (file cleanup), not cross-app.
- `freedom_ls/form_engine/receivers.py:15` — `@receiver(post_delete, sender=QuestionAnswerFile)` — also same-app.
- `freedom_ls/referral_tracking/signals.py` (connected via `ReferralTrackingConfig.ready()`, `apps.py:10-14`) has exactly one receiver, `record_attribution_on_signup` (`signals.py:21-47`), on **`allauth.account.signals.user_signed_up`** — a **third-party Django signal**, not a `post_save` on an FLS model, and specifically **not** on `accounts.User` directly. This is the existing, working precedent for how `referral_tracking` reacts to a "someone did a thing" moment without importing the app that did it: it hangs off a signal the *other* app (or a third-party package `accounts` already integrates) publishes, wrapped in its own `transaction.atomic()` savepoint and a best-effort `except DatabaseError: sentry_sdk.capture_exception(...)` (lines 42-47) so a failed attribution write never blocks the actual signup.

### FLS's own "event happened" hook: `freedom_ls/webhooks/events.py` + `freedom_ls/base/webhook_event_types.py`
- `fire_webhook_event(event_type, payload)` (`webhooks/events.py:10-39`) validates `event_type` against `webhooks/registry.py:9-16` (`get_event_type_registry()`, reading `WebhooksConfig.WEBHOOK_EVENT_TYPES`, `webhooks/config.py:7-12`, defaulting to `FLS_WEBHOOK_EVENT_TYPES` in `base/webhook_event_types.py`), then creates a `WebhookEvent` row (`site_id` explicit) and enqueues `_dispatch_event_task` via `django.tasks.default_task_backend` (lines 30-39).
- **Current event catalogue** (`base/webhook_event_types.py:1-5`): `user.registered`, `course.completed`, `course.registered`. No `course.applied` / `course.interest_expressed` event exists yet.
- Call sites found (`grep fire_webhook_event`):
  - `user.registered` fired from `freedom_ls/accounts/allauth_account_adapter.py:135-145`, inside `save_user()` (allauth's account adapter hook) — this is the moment a brand-new `User` row is actually committed, i.e. **exactly** where `referral_tracking`'s own `SignupAttribution` is also written (via the `user_signed_up` allauth signal, not this adapter hook, but the same event).
  - `course.completed` fired from `freedom_ls/learner_interface/views.py:1606-1622` (course-completion detection inline in a learner_interface view).
  - `course.registered` fired from `freedom_ls/learner_progress/signals.py:143-...` — i.e. from *inside* the cross-app `post_save` receivers described above, once a `CourseProgress` record is minted, not directly from `learner_management`.
- **Important structural fact**: every current call site imports `fire_webhook_event` directly (`from freedom_ls.webhooks.events import fire_webhook_event`, e.g. `learner_interface/views.py:1612`, `accounts/allauth_account_adapter.py:135`) — i.e. **publishing** an event still requires the publishing app to import `webhooks`, but **nothing requires the subscriber to import the publisher**. A new attribution write in `referral_tracking` could either:
  (a) add a receiver on `webhooks.models.WebhookEvent`'s own `post_save`, filtered by `event_type in {"course.registered", ...}` — this would need a **new edge `referral_tracking -> webhooks`** (not currently present, `docs/app_structure.md:139-141`), but avoids any edge to `course_applications`/`learner_management`; or
  (b) piggyback on the existing `user_signed_up`-style pattern by having each course-signup app (`course_applications`, `course_interest`, `learner_management`/`learner_progr­ess`) `fire_webhook_event` a new event type carrying enough payload (`user_id`, `course_id`, timestamp) for `referral_tracking` to act on via its *own* new receiver on `WebhookEvent` (same edge as (a)); or
  (c) use the `ObjectRoleAssignment`-style GFK (§6) directly from a new `referral_tracking` model, at the cost of the new attribution row's creation still needing to happen from *inside* the code that creates `CourseApplication`/`LearnerCourseRegistration`/etc — which still requires either a new edge *from* those apps *into* `referral_tracking`, or new webhook event types those apps fire and `referral_tracking` subscribes to per (a)/(b).
- No FLS-internal signal for "someone got a course" (application, interest, or registration) is fired today except `course.registered`, and that only exists for `learner_management`'s two registration models via the `learner_progress` receivers (§7 above) — **`CourseApplication` and `CourseInterest` fire no webhook event at all today.**

## Open items for the design phase (facts only, not design)

- Building attribution on `CourseApplication.created_at`/`LearnerCourseRegistration.registered_at` alone conflates "when the person acted" with "when staff acted" — the model layer carries no field that distinguishes the two, and no `created_by`/`actor` field exists on any of these models.
- `registered_at`/`created_at` being `auto_now_add` means **reactivation (Learner, LearnerCourseRegistration) freezes the original moment** and cannot represent a later act — §4 is the load-bearing constraint any "which referral code was in play at time of signup" design must resolve explicitly.
- The only currently-approved boundary `referral_tracking` may import is `accounts`. Any join with `course_applications`/`course_interest`/`learner_management`/`reports` needs either a new edge (named explicitly, approved) or a GFK/webhook-event indirection per §6/§7.
