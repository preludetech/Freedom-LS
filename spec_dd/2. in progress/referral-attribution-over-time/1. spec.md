# Spec: referral attribution over time

Inputs: `idea.md`, `answers.md` and the `research_*.md` files in this directory.

## Purpose

Attribution is captured once, at account signup. `SignupAttribution` is one row per user, written by
`record_attribution_on_signup` from a cookie frozen on the visitor's first tracked landing. A later
landing changes nothing: `AttributionCaptureMiddleware._site_to_mint_for` returns `None` as soon as a
valid cookie exists.

That says which code an account came from. It cannot say which code was in play when the person
applied for a course weeks later through a different partner's link. Referral payouts are coming, and
they need that answer recorded rather than reconstructed.

This work keeps a **timeline of touches per person**, and freezes the first and last referral code in
play at each attributable moment.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `AttributionTouch` | coined | One tracked landing recorded against one account. The app already calls a tracked landing a touch (`FirstTouchCount`, `first_touch_from_request`); this keeps every touch per person, in order, rather than tallying first touches. |
| `Conversion` | narrowed | One attributable moment for referral payouts: an account signup, or a learner-initiated course application, expression of interest or self-registration. Not the ad-platform conversion of `freedom_ls/google_tag/google_ads.py` (`GOOGLE_ADS_CONVERSION_ID`, conversion labels) or of the `server-side-conversion-tracking` idea, which are events reported to Google, Meta or TikTok. A `Conversion` is a database row in `referral_tracking` and is reported nowhere. |
| **in play** | coined | Of a referral code at an instant: carried by an `AttributionTouch` for that user, on that site, at or before the instant, and no older than the attribution window. |
| **live touch** | coined | A touch written straight to a row because the visitor was signed in when it happened, as against one carried in the cookie and flushed later. |

A `Conversion` is not a registration. "Registration" stays the FLS word for course access.

## Scope

**In.**

- A per-user `AttributionTouch` timeline, fed three ways: the cookie flushed at signup, the cookie
  flushed at login, and live touches while signed in.
- A cookie that carries a bounded list of touches beside the frozen first touch.
- One `Conversion` row per attributable moment, holding the first and last codes in play, frozen.
- Hooks in the four places a learner acts: signup, starting an application (including an anonymous
  application once it is attached to an account), expressing interest, self-registering.
- Read-only admin and CSV export over both models.
- A prune command for touches no conversion references.

**Out.**

- Payouts, commission, money, and anything partner-facing. No `Organisation` link on `ReferralCode`.
- A dashboard or conversion-rate view.
- A consent gate for the tracking cookie (see Open questions).
- Any change to `SignupAttribution`: its shape, append-only guard and read-only admin stay.
- Attributing staff-created registrations and cohort memberships.
- Touches for untagged landings from another site. `referral-tracking-external-referer-first-touch`
  adds its own touch kind, field and cookie key later.

## Decisions

- **This supersedes one shipped decision.** The `referral-links` spec said a referral code "reaches
  attribution only as a first touch". From here it also reaches attribution through every later
  tagged landing. Its other rule, that codes are never reused, still holds and is what makes storing
  code text safe for a payout.
- **The timeline is the capture; the frozen pair is the payout record.** Raw touches let a future
  credit rule be re-run over history. The frozen pair keeps a figure someone was paid on from moving
  when a touch is pruned or a rule changes.
- **No credit rule is built in.** A `Conversion` records `first_referral_code` and
  `last_referral_code` side by side. Whoever runs a payout picks first or last in the query.
- **Only referral codes are ever in play.** `first_touch` and `last_touch` are the earliest and latest
  touches with a non-blank `referral_code`. A UTM-only touch is recorded but never displaces a
  partner. A landing with no tracked parameter is never recorded, so there are no direct touches.
- **Both codes blank is a recorded answer.** It means no coded touch reached a row inside the window.
  A cookie that was lost or expired before signup looks the same. That is accepted.
- **A cookie-carried touch can only reach a row while the cookie lives.** The cookie dies 90 days
  after its first touch, whatever was appended later. A live touch has no such limit. The resolver's
  window applies to both the same way.
- **Only learner-initiated moments convert.** An admin registering a learner or adding a cohort is
  staff work, and crediting a partner for it would credit a decision made in the admin.
- **A reactivation converts nothing.** `_ensure_registration` returns `registration.reactivated` for
  a learner re-entering a course an admin deactivated. Only `registration.added` converts, so a
  partner is not credited twice for one course.
- **An application converts when it is started, not submitted.** Starting is where the learner acted
  on the referral; a form may be finished weeks later under unrelated touches. The GA4 event
  `record_application_submitted` fires on submission because it measures a different thing, and stays
  where it is.
- **An anonymous application converts when it is attached to an account.** Its `occurred_at` is still
  the application's `created_at`. It is resolved after the request's cookie is flushed to that account,
  so the touches that led to applying are in play.
- **`referral_tracking` gains no dependency.** The three product apps call into it, and a `Conversion`
  points at its target through a `GenericForeignKey`, as `ObjectRoleAssignment` does
  (`freedom_ls/role_based_permissions/models.py`).
- **A conversion stores code text, not a foreign key to `ReferralCode`.** A hand-typed `?ref=` that
  matches no row really happened. A payout query matches text to a row with
  `lookup_referral_code(site, code)`.
- **The cookie's first-touch keys do not change.** `COOKIE_KEYS` and the return value of
  `read_attribution_cookie` stay exactly as they are. The touch list is a separate key. First-Class-LMS
  builds model fields, admin fieldsets and `LeadSubmission(**cookie)` from both, so adding a key to
  either would break it on a visitor's second landing.
- **A repeat landing does not extend the cookie's life.** Re-setting with a full `max_age` would make
  the 90-day window roll forever for an active visitor.
- **A later touch tallies nothing.** `FirstTouchCount` is a conversion-rate denominator.
  `increment_first_touch` stays on the minting path only.
- **A repeat of the latest touch is skipped, in the cookie and live.** Seven identical attribution key
  values to the most recent touch add nothing. A, B, A is still three touches: the return to A is new.

## Requirements

### 1. `AttributionTouch` (`freedom_ls/referral_tracking/models.py`)

A `SiteAwareModel`, append-only. No IP, user agent, referer, raw query or click identifier: those stay
on `SignupAttribution`.

| Field | Type | Note |
| --- | --- | --- |
| `user` | `ForeignKey(AUTH_USER_MODEL, on_delete=CASCADE, related_name="attribution_touches")` | |
| `advert_code`, `referral_code`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` | `CharField(blank=True, max_length=CAPS[...])` | The seven `ATTRIBUTION_KEY_FIELDS`, existing caps. |
| `landing_path` | `CharField(blank=True, max_length=CAPS["landing_path"])` | Set on a live touch and on a flushed first touch; blank on a flushed list entry. |
| `occurred_at` | `DateTimeField(db_index=True)` | When the landing happened. Not `auto_now_add`: a flushed touch happened before the flush. |
| `recorded_at` | `DateTimeField(auto_now_add=True)` | When the row was written. |
| `recorded_via` | `CharField(max_length=16, choices=TouchSource)` | `live`, `signup_flush` or `login_flush`. Tells a reader how far to trust the ordering. |
| `key_hash` | `CharField(max_length=64)` | `counters.attribution_key_hash` over the seven key values. Makes the row idempotent. |

`Meta`:

- `UniqueConstraint(fields=["site", "user", "occurred_at", "key_hash"], name="unique_attribution_touch")`,
  so a flush that runs twice writes each touch once.
- `Index(fields=["site", "user", "occurred_at"])` for the resolver.
- `Index(fields=["site", "referral_code"])` for the payout query.
- `Index(fields=["site", "recorded_at"])` for the `apis-for-lead-monitoring-6-conversions` cursor.
- `ordering = ["-occurred_at"]`.

`save()` carries the same append-only guard as `SignupAttribution.save()`, in the same shape and with
the same comment. `TouchSource` is a `models.TextChoices` beside `Door`. The model stays out of
`TIMESTAMPED_MODELS` (`freedom_ls/contrib/conformance/tests/test_timestamped_models.py`), like every
model in this app.

### 2. `Conversion` (`freedom_ls/referral_tracking/models.py`)

A `SiteAwareModel`, append-only by the same guard.

| Field | Type | Note |
| --- | --- | --- |
| `user` | `ForeignKey(AUTH_USER_MODEL, on_delete=CASCADE, related_name="referral_conversions")` | |
| `kind` | `CharField(max_length=32, choices=ConversionKind)` | `account_signup`, `course_application`, `course_interest`, `course_registration`. |
| `content_type` | `ForeignKey(ContentType, on_delete=CASCADE, null=True, blank=True)` | |
| `object_id` | `CharField(max_length=255, blank=True)` | `CharField`, as `ObjectRoleAssignment.object_id`: this app cannot import the four target models and must not assume their pk type. |
| `target` | `GenericForeignKey("content_type", "object_id")` | `User`, `CourseApplication`, `CourseInterest` or `LearnerCourseRegistration`. |
| `target_label` | `CharField(max_length=255, blank=True)` | Frozen at write time: the course title, or `"Account signup"` for a signup. The admin and export read this and never resolve `target`; it survives the target being deleted. |
| `occurred_at` | `DateTimeField(db_index=True)` | Supplied by the caller. |
| `recorded_at` | `DateTimeField(auto_now_add=True)` | |
| `window_days` | `PositiveSmallIntegerField()` | `REFERRAL_TRACKING_ATTRIBUTION_WINDOW_DAYS` as it was when the pair was resolved. |
| `first_touch` | `ForeignKey(AttributionTouch, on_delete=PROTECT, null=True, blank=True, related_name="conversions_as_first")` | |
| `last_touch` | `ForeignKey(AttributionTouch, on_delete=PROTECT, null=True, blank=True, related_name="conversions_as_last")` | |
| `first_referral_code` | `CharField(blank=True, max_length=CAPS["referral_code"])` | Frozen copy. |
| `last_referral_code` | `CharField(blank=True, max_length=CAPS["referral_code"])` | Frozen copy. |

`PROTECT` on both touch keys means a touch a payout rests on cannot be pruned. Deleting a user still
works: the user's touches and conversions are collected in the same delete, and Django raises
`ProtectedError` only for a referrer outside the collection.

`Meta`:

- `UniqueConstraint(fields=["site", "kind", "content_type", "object_id"], name="unique_conversion_per_target")`,
  so a caller that fires twice records once.
- `Index(fields=["content_type", "object_id"])`.
- `Index(fields=["site", "kind", "occurred_at"])`.
- `Index(fields=["site", "recorded_at"])` for the API cursor.
- `ordering = ["-occurred_at"]`.

Both models are added to `USER_ERASURE_CASCADE_MODELS` in `referral_tracking/admin.py`, beside
`SignupAttribution`, so the account-erasure confirmation names them.

### 3. The cookie (`freedom_ls/referral_tracking/capture.py`)

**A separate touch-list key.** A new constant, `COOKIE_TOUCHES_KEY = "tl"`, outside `COOKIE_KEYS`. `t`
is taken by `utm_term`. Its value is a list of compact entries, each holding only the seven
`ATTRIBUTION_KEY_FIELDS` under their existing short keys (blank values omitted) plus `ts`, an ISO 8601
time. No landing path, referer, raw query or click identifier.

**Validation.** `_is_first_touch_payload` keeps its rule for every key except `tl`, which must be a
list of dicts whose keys are the seven attribution short keys or `ts`, whose values are all `str`, and
whose `ts` parses with `datetime.fromisoformat`. Anything else fails the whole payload, which is then
treated as absent, as today.

**Reading.** `read_attribution_cookie` keeps its signature and its `dict[str, str]` return, the first
touch only. A new `read_cookie_touches(request) -> list[CookieTouch]` returns the list (a `TypedDict`
or dataclass, no `Any`), empty for a cookie minted before this ships. Both share one decode.

Both readers also reject a cookie whose `first_seen` is more than
`REFERRAL_TRACKING_COOKIE_MAX_AGE_DAYS` old. `get_signed_cookie(max_age=...)` checks the age of the
signature, and every re-set signs afresh, so without this check the server would accept a cookie for 90
days after its last re-set.

**Appending.** `append_touch(touches, first_touch, request)` builds an entry from the request and
appends it, unless its seven values equal the last entry's, or, when the list is empty, the frozen
first touch's. The list holds at most `REFERRAL_TRACKING_MAX_COOKIE_TOUCHES` entries; at the cap the
oldest is evicted, so the first touch (in the frozen keys) and the newest entry always survive.

**Fitting.** `set_attribution_cookie` sheds `COOKIE_DROP_ORDER` fields first, unchanged. If the payload
still does not fit `COOKIE_MAX_ENCODED_LENGTH`, list entries go oldest first, never the newest. If the
frozen first touch plus one entry still does not fit, it returns `False` and sets nothing, as today.

**Expiry that does not roll.** `max_age` is `_cookie_max_age()` minus the time since the frozen
`first_seen`, floored at zero. The minting call has no `first_seen` yet and gets the full
`_cookie_max_age()`.

**Clearing.** `request_cookie_clear(request)` and `is_cookie_clear_requested(request)`, a request-flag
pair shaped like `suppress_capture` / `is_capture_suppressed`. The flush sets it; the middleware acts
on it.

### 4. The middleware (`freedom_ls/referral_tracking/middleware.py`)

`AttributionCaptureMiddleware` still reads the request before the view runs and writes nothing until
the view returns. It gains three behaviours.

1. **Honour the clear flag on any request.** The early return for a non-GET or untracked request runs
   `get_response`, then checks `is_cookie_clear_requested`; when set, `response.delete_cookie` with the
   name and path the cookie was set under. The signup and login POSTs are neither GETs nor tracked.
2. **A signed-in tracked GET writes a row, not a cookie.** After the view returns, when
   `request.user.is_authenticated` and the site resolves to a `Site`, call `record_live_touch` and leave
   the cookie alone. `request.user` is read only here, so an untracked request still resolves no
   session.
3. **An anonymous tracked GET with a cookie appends to it.** It reads the payload, calls
   `append_touch` and re-sets the cookie. It tallies nothing and issues no query. The first-touch branch,
   with no cookie present, is unchanged: mint, then tally.

`Vary: Cookie` and `private, no-store` apply to the append path as they do to the mint path, since it
also sets a cookie.

### 5. Writing touches and conversions (`freedom_ls/referral_tracking/conversions.py`, new)

All three entry points are best-effort: `transaction.atomic()`, catch `DatabaseError`, report with
`sentry_sdk.capture_exception`, return `None` (or an empty list). Attribution must never stop a signup,
an application or a registration. `record_hit` in `hits.py` and `record_attribution_on_signup` already
do this; extract one shared helper rather than writing a third copy.

**`record_live_touch(*, request, user, site) -> AttributionTouch | None`** writes one touch with
`recorded_via=live`, `occurred_at=timezone.now()`, field values from `first_touch_from_request` and
`key_hash` from `attribution_key_hash`. It writes nothing when the user's most recent touch on that
site has the same `key_hash`.

**`flush_cookie_touches(*, request, user, source) -> list[AttributionTouch]`** writes one touch per
cookie touch: the frozen first touch at its `first_seen` (with its `landing_path`), then each list entry
at its `ts`, all with `recorded_via=source`. `get_or_create` on the unique key, so a touch already
flushed is not written again. An entry whose `ts` is later than now or earlier than `first_seen` is
skipped. It then calls `request_cookie_clear(request)`, so the next person to sign in on a shared
device does not inherit these touches. Touches left by an earlier visitor on that device go to the
first account to sign up or log in there; that is accepted.

**`record_conversion(*, user, kind, target, occurred_at, target_label) -> Conversion | None`** resolves
the pair and writes the row with `get_or_create` on the unique key, copying each touch's
`referral_code` into the frozen column and the current window into `window_days`.

Resolution lives in **`freedom_ls/referral_tracking/resolution.py`**:
`touches_in_play(*, user, site, when) -> tuple[AttributionTouch | None, AttributionTouch | None]`. It
reads that user's touches on that site with a non-blank `referral_code` and
`when - window <= occurred_at <= when`, and returns the earliest and latest, or `(None, None)`.
`site` is explicit so a shell script or background job can call it without a request.

### 6. The call sites

Each fires once, on creation only, with no error handling of its own.

- **Signup.** `record_attribution_on_signup` (`signals.py`) writes `SignupAttribution` first, unchanged,
  then calls `flush_cookie_touches(source=signup_flush)`, then `record_conversion` with
  `kind=account_signup`, `target=user`, `occurred_at=attribution.signed_up_at`,
  `target_label="Account signup"`. The flush comes before the conversion so its touches exist. This
  receiver also runs for an account a claim creates, because `attach_claimed_application`
  (`course_applications/claims.py`) sends `user_signed_up`; that is a signup and converts as one.
- **Login.** A new `user_logged_in` receiver in `signals.py`, connected by the existing `ready()`.
  It calls `flush_cookie_touches(source=login_flush)` and nothing else. This catches an existing
  account that followed a partner's link and then logged in.
- **Signed-in application.** `_start_application` (`course_applications/views.py`) surfaces the
  `created` flag from its `get_or_create`. When `created` and a user was passed: `kind=course_application`,
  `target=app`, `occurred_at=app.created_at`, `target_label=course.title`. An anonymous start converts
  nothing here.
- **Anonymous application, once attached.** `attach_claimed_application` (after its signal) and
  `adopt_anonymous_applications_on_login` (`course_applications/receivers.py`), when the attach kept the
  incoming application, call `flush_cookie_touches` for that user and then `record_conversion` with
  `kind=course_application`, `target` the attached application, `occurred_at` its `created_at`, and
  `target_label` the course title. The flush source is `signup_flush` when the claim created the
  account, `login_flush` otherwise. The flush runs here, not only in the signup and login receivers,
  because receiver order is not guaranteed. Running it twice writes nothing twice. When the account's
  submitted application wins and the incoming one is erased, nothing converts.
- **Interest.** `_express_interest` (`course_interest/views.py`), on `created`, beside
  `record_interest_expressed`: `kind=course_interest`, `target=interest`,
  `occurred_at=interest.created_at`, `target_label=course.title`.
- **Self-registration.** `initiate_course_access` (`learner_interface/views.py`), on the branch where
  `self_register` reports a new registration, beside `record_course_self_registered`:
  `kind=course_registration`, `target` the new `LearnerCourseRegistration`,
  `occurred_at=registration.registered_at`, `target_label=course.title`. `self_register` returns only a
  `bool` today; the view needs the row.

Toggling interest off and on deletes and recreates the `CourseInterest`
(`course_interest/views.py`). The first `Conversion` is not deleted with it and the new row gets its
own. Both are true records; `target_label` keeps the orphan readable.

### 7. Settings and checks (`config.py`, `checks.py`)

| Setting | Default | Governs |
| --- | --- | --- |
| `REFERRAL_TRACKING_ATTRIBUTION_WINDOW_DAYS` | `90` | How far back `touches_in_play` looks. Equal to the cookie's life, so a flushed touch is never already out of window. |
| `REFERRAL_TRACKING_MAX_COOKIE_TOUCHES` | `10` | Entries in the cookie's touch list before the oldest is evicted. |

Both declared in `declared_settings` with defaults, neither required.

`checks.py` gains `freedom_ls_referral_tracking.W001`: a warning when
`REFERRAL_TRACKING_ATTRIBUTION_WINDOW_DAYS` is less than `REFERRAL_TRACKING_COOKIE_MAX_AGE_DAYS`,
because touches flushed at signup could then be recorded and already out of window.

### 8. Admin and export (`admin.py`, `resources.py`)

Both admins are `SiteAwareExportModelAdmin`, fully read-only (`has_add_permission`,
`has_change_permission`, `has_delete_permission` all `False`, `readonly_fields =
_readonly_field_names(...)`), matching `SignupAttributionAdmin`. Each has a resource subclassing
`SiteAwareModelResource`, exporting `user` by email through `ForeignKeyWidget` as
`SignupAttributionResource` does, and omitting `site`. The shared base resource is not changed.

- **`AttributionTouchAdmin`**: `date_hierarchy = "occurred_at"`; `list_display` of user, referral
  code, advert code, UTM source, UTM campaign, `occurred_at`, `recorded_via`; `list_filter` on
  `recorded_via`, `utm_source`, `utm_campaign`; `search_fields` on `user__email`, `referral_code`,
  `advert_code`, `utm_campaign`; `list_select_related = ["user"]`.
- **`ConversionAdmin`**: `date_hierarchy = "occurred_at"`; `list_display` of user, kind,
  `target_label`, `first_referral_code`, `last_referral_code`, `occurred_at`; `list_filter` on `kind`
  plus a **code-in-play filter**, a text input matching conversions whose `first_referral_code` or
  `last_referral_code` equals the entered code, case-insensitive; `search_fields` on `user__email` and
  `target_label`; `list_select_related = ["user"]`. No column resolves `target`.
- **`ConversionResource`** exports `id`, user email, `kind`, `target_label`, `occurred_at`,
  `first_referral_code`, `first_touch.occurred_at`, `last_referral_code`, `last_touch.occurred_at` and
  `window_days`, with `first_touch` and `last_touch` loaded by `select_related`.

Entering a code in the code-in-play filter and exporting gives a partner's payout list. The export
must export the filtered queryset, not the whole table.

### 9. `prune_attribution_touches` (management command)

A `djclick` command shaped on `prune_referral_code_hits`: `--older-than-days N` with
`click.IntRange(min=1)`, no default, across every site, in primary-key batches of `PRUNE_BATCH_SIZE`,
printing the total. It deletes only touches no conversion references
(`conversions_as_first__isnull=True, conversions_as_last__isnull=True`). The docstring says `PROTECT` is
the guarantee and the filter keeps the command from tripping over it.

## Testing

Use `mock_site_context` for anything touching a `SiteAwareModel` and `django_assert_num_queries` for
query-count pins. Build touches through factories except where the middleware is the subject.

**Tests that are replaced, not added to** (`referral_tracking/tests/test_middleware.py`):

- `test_second_tracked_get_in_the_same_client_leaves_the_cookie_byte_identical` becomes: a second
  tracked GET with a different key appends one entry; one with the same key leaves the cookie
  byte-identical.
- `test_a_tracked_get_with_an_existing_valid_cookie_costs_no_query` keeps its zero-query assertion for
  an anonymous visitor and gains a signed-in sibling pinning the query count of a live touch.
- `test_a_visitor_holding_the_cookie_is_logged_as_a_hit_and_keeps_the_first_touch` also expects an
  appended entry.
- `test_a_tracked_get_with_an_existing_valid_cookie_sets_no_cookie` holds only for a repeat of the
  same key.

`..._leaves_the_tally_at_one` is unchanged and proves a repeat landing tallies nothing.

**The cookie.** A pre-upgrade cookie with no `tl` key reads with an empty list (shape of
`test_a_pre_upgrade_cookie_without_rc_reads_with_a_blank_referral_code`), and
`read_attribution_cookie` returns exactly the keys of `COOKIE_KEYS` for a cookie that has a list. A
malformed `tl` makes the whole cookie absent. The same link twice appends nothing; a second link
appends one. Past the cap the oldest goes and the newest stays. The multibyte worst case with a full
list still fits 4096 bytes, succeeding `test_a_multibyte_worst_case_cookie_fits_the_browser_limit`. A
payload that cannot fit with one entry sets no cookie and mints no tally. A re-set never yields an
expiry past 90 days after `first_seen`; a cookie whose first touch is 90 days old gets `max_age` zero.
A re-signed cookie whose `first_seen` is over 90 days old reads as absent.

**Live touches.** A signed-in tracked GET writes one `live` touch and no cookie. Repeating it writes
nothing; a different key writes one more. A typed `?ref=` from a signed-in learner is stored as typed.

**Flushing.** A signup after three tracked landings writes three `signup_flush` touches at the landing
times, and the signup response deletes the cookie. Signup then login writes each touch once. A login
with no cookie writes nothing and fails nothing. A signup with no cookie writes no touches and a
conversion with both codes blank. An entry with a future `ts` is skipped.

**Resolution.** Touches at T-60, T-30 and T-1 days carrying A, B and C: a conversion at T freezes A and
C. A touch after the conversion is ignored. A touch older than the window is ignored for both codes. A
UTM-only touch between two coded ones changes neither. Another site's or user's touch is never in
play. `window_days` records the setting in force.

**Conversions.** Each call site writes exactly one row with the right `kind`, `target`, `occurred_at`
and `target_label`; calling it twice writes one. A reactivating `initiate_course_access` writes none.
An application converts at `created_at`, and completing its form adds nothing. An anonymous
application converts once when claimed and once when adopted on login, with `occurred_at` its
`created_at` and the claiming request's cookie touches in play; an erased incoming application converts
nothing. A `DatabaseError` writing a conversion leaves the application, interest or registration
committed and the request successful, tested per call site.

**Append-only and erasure.** Saving an existing `AttributionTouch` or `Conversion` raises, and the
admin change view persists nothing (shapes of `test_updating_an_existing_signup_attribution_raises`
and `test_signup_attribution_change_does_not_persist_modification`). Deleting a user with touches and
conversions that reference them succeeds and removes both. Both models appear on the erasure
confirmation.

**Pruning.** An old unreferenced touch is deleted; one referenced as `first_touch` or `last_touch` is
not; deleting a referenced touch directly raises `ProtectedError`.

**Admin and export.** Both changelists load, both exports omit `site` and give `user` as an email, and
both 403 without the view permission (shape of the existing `tests/test_exports.py` checks). The
code-in-play filter matches first or last, case-insensitively, and the export after filtering holds only
the matching rows with the listed columns. A `ConversionAdmin` changelist page resolves no generic FK,
pinned with `django_assert_num_queries`.

**Config.** One assertion per new default, and W001 fires when the window is shorter than the cookie's
life.

## Open questions

- **A consent gate is overdue.** FLS sets the tracking cookie on any tracked landing whatever the
  visitor agreed to. The ICO's April 2026 storage and access guidance puts affiliate attribution on the
  consent-required side. An operator in the UK or EU needs an answer before this goes live, and FLS
  needs a spec for it. The `cookie-banner` idea is a notice, not a gate.
- **Who sets the credit rule.** FLS records first and last and picks neither. The programme owner has
  to write first-click or last-click into the partner terms before the first payout.
- **Self-referral and typed codes.** Nothing stops a partner using their own code on their own account,
  or a signed-in learner typing `?ref=` to add a touch. This work makes both worth doing for the first
  time. Detection is out of scope.
- **Whether a partner should ever see any of this.** Everything here is admin-only.

## Success criteria

- A person who lands through code A, returns three weeks later through code B, signs up and applies
  for a course has two touches and two conversions, the application's freezing A as first and B as
  last.
- An existing account that follows a partner's link, logs in and expresses interest produces a
  conversion naming that code.
- An anonymous applicant who arrived through code A and claims the application has a
  `course_application` conversion freezing A, dated when they applied.
- Entering a code in the code-in-play filter and exporting gives one CSV row per conversion that code
  was first or last for.
- `prune_attribution_touches --older-than-days 400` deletes touches and changes no conversion's frozen
  codes.
- A `DatabaseError` in attribution leaves the application, interest and registration committed and the
  request successful.
- The same link twice grows the cookie by nothing and the `FirstTouchCount` tally by nothing.
- A cookie with every tracked value at its cap in multi-byte characters and a full touch list fits
  4096 bytes.
- `read_attribution_cookie` returns the same keys before and after this work.
- `docs/app_structure.md` shows `referral_tracking` depending on `accounts`, `api`, `base` and
  `site_aware_models` only.
