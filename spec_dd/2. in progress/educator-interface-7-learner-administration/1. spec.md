# Spec: Learner administration

Spec 7 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Idea: `idea.md`. Resources: `research_lms_educator_ux.md`; the mockups `Educator
Learners.dc.html` screens 02 and 03 and `Educator Mobile Learners.dc.html` M03 to M05, under
`spec_dd/1. next/educator-interface-full-polish/Educator LMS Interface Design/` (layout and density
only, never scope or theme).

## Purpose

Cohort membership, individual registration and staff-made accounts are only editable in the Django
admin today, and creating an account for someone means typing them a password. This spec makes the
educator interface's learners section complete: add a learner whether or not they have an account,
list and detail, deactivate and reactivate, cohort membership add, remove and move, individual
registration and unregistration, and resending the account setup email. It also settles what a
move does to the learner's course progress records.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| pending | coined | A `User` whose `last_login` is null and who has no usable password. Belongs to the `User`, so a person pending in one organisation is pending in all of them. A learner's status is `removed` if `Learner.is_active` is false, else `pending` if their user is pending, else `active`. |
| account setup email | coined | The email sent to a staff-created `User` carrying a password-set link built on allauth's reset token. |
| move | coined | One action that deletes a learner's `CohortMembership` in one cohort and creates one in another cohort of the same organisation, in a single transaction. |

## Scope

In:

- Adding learners to an organisation through one form: existing accounts matched, new accounts
  created with an account setup email, optional cohort.
- The learners list (status, search, filters) and the learner detail page (overview, courses and
  progress, empty history tab).
- Deactivate, reactivate, resend account setup email, site_admin name editing.
- Cohort membership add, remove and move, from the learner page and from the cohort's learners tab.
- Individual course registration, unregistration and re-registration from the learner page.
- What a move does to course progress records.
- Webhook event types for every action here, plus the names spec 6 fires for cohort registration.
- The permission matrix rows and capability strings these actions need.

Out: CSV import and bulk actions (spec 8). Educator roles (spec 9). Progress detail beyond a
percentage (spec 10). Audit history content (spec 11). Cohort registration UI (spec 6). Account
merge, log in as a learner, cross-organisation moves, hard delete of a `Learner` or `User`,
retakes and progress resets. Email editing in the educator interface (it stays in the Django
admin). Everything in the mockups the idea does not ask for: messaging, "Reset attempt", extra
statuses, assessments, certificates and activity tabs, extra profile fields, column visibility.

## Decisions

1. **Pending is derived, no new column.** `last_login IS NULL` alone also matches self-signups who
   never confirmed. Adding "no usable password" excludes them. The roadmap's "no invitation model"
   assumption holds, and so does the done learners spec's "no pending status field".
2. **A move re-points course progress records rather than copying them**, for each course that an
   active registration on the destination cohort grants and a registration on the source cohort
   granted. This is the rule the done progress spec (`spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/`)
   handed to this work.
3. **Move clash: the furthest-along record wins.** If the learner already has a course progress
   record under the destination registration, the one with the higher `progress_percentage` ends
   up under the destination registration. The other ends up under the source registration, unused.
   A tie keeps the destination record where it is. Nothing is merged or deleted.
4. **Name editing is `site_admin` only. Email editing stays in the Django admin**, because the
   email is the login for every organisation and changing it needs allauth re-verification.
5. **The add-learner code lives in `learner_management`**, user creation and the account setup
   email in `accounts`. `accounts` cannot import `learner_management` at runtime. Spec 9 needs user
   creation without `ensure_learner`.
6. **The account setup email is an allauth-adapter email** with its own templates in `accounts`,
   sent through `AccountAdapter.send_mail`, so it carries the existing site theme and logo. There
   is no subject setting. A project overrides `account_setup_subject.txt`.
7. **Staff-created users get a verified, primary `EmailAddress` at creation.** The only way in is
   the link sent to that address, so verification is proven by use. Without it,
   `ACCOUNT_EMAIL_VERIFICATION = "mandatory"` sends a second email at first login.
8. **Resend is rate limited with a cache guard** (`cache.add`) per user, not through
   `ACCOUNT_RATE_LIMITS`. That setting has no key for custom actions, is replaced wholesale by
   downstream projects and is off in dev.
9. **A move fires two webhook events** (`cohort.member_removed`, then `cohort.member_added`)
   sharing a `move_id`. Consumers keep one handler per fact.
10. **Self-registration can still undo a deactivation or unregistration** on the site's default
    organisation (`learner_interface/views.py:889-905`). No behaviour change. The confirmations say
    so where it applies.
11. **Row selection ships as a seam.** `LearnerConfig.get_bulk_actions` returns `[]` and the table
    defines `get_row_label`. Checkboxes appear when spec 8 registers its actions. A placeholder
    bulk action would be functionality nobody asked for.
12. **Revoking a pending learner is deactivating them, and it leaves the setup link alive.**
    Following the link gets the person an account with no access in this organisation. Killing the link would touch a `User` other
    organisations may share.

## Requirements

### R1. Accounts: users created by staff (`freedom_ls/accounts/`)

- New module `freedom_ls/accounts/account_setup.py`:
  - `match_or_create_user(site: Site, email: str, first_name: str = "", last_name: str = "") -> tuple[User, bool]`.
    Strips the address and normalises the domain. Looks it up with `User._base_manager` and
    `email__iexact` across all sites, because `User.email` is globally unique.
    - A match on `site`: returns it unchanged. Existing names are never overwritten.
    - A match on another site: raises `EmailInUseOnAnotherSite`.
    - No match: creates the `User` on `site` with `set_unusable_password()`. Do not use
      `UserManager.create_user`, which refuses an empty password. Also creates
      `EmailAddress(email=..., verified=True, primary=True)`.
  - `is_pending(user: User) -> bool` and `pending_user_q(prefix: str = "") -> Q`, the queryset form
    (`last_login__isnull=True` and `password__startswith=UNUSABLE_PASSWORD_PREFIX`), used by the list
    filter and the status column. One definition, two shapes.
  - `send_account_setup_email(user: User, organisation: Organisation) -> None`.
    - Builds the key as allauth does (`user_pk_to_url_str`, `default_token_generator.make_token`)
      and the absolute URL for `account_reset_password_from_key` from `user.site.domain` and
      `ACCOUNT_DEFAULT_HTTP_PROTOCOL`, never from the request.
    - Sends through `get_adapter().send_mail("account/email/account_setup", user.email, context)`
      on `transaction.on_commit`. The context holds `user`, `organisation`, `setup_url` and the
      expiry in days, from `PASSWORD_RESET_TIMEOUT`.
    - Sets the resend guard (below), so an immediate resend is refused.
    - Refuses (`AccountAlreadySetUp`) when the user is not pending.
  - `resend_account_setup_email(user: User, organisation: Organisation) -> None`. Raises
    `SetupEmailRecentlySent` when `cache.add(f"account-setup-email:{user.pk}", 1, timeout)` fails,
    otherwise sends.
- `accounts/config.py`: new setting `ACCOUNT_SETUP_EMAIL_RESEND_SECONDS: int`, default `900`.
- `AccountAdapter.send_mail` (`accounts/allauth_account_adapter.py:32-53`) reads the site from the
  allauth request today. With no request in context it falls back to the recipient user's site,
  so spec 8 can send from a background task.
- Templates: `accounts/templates/account/email/account_setup_subject.txt`,
  `account_setup_message.txt`, `account_setup_message.html` (extending `emails/base_email.html`).
  The copy names the organisation, says an account was made for them, gives the link and its
  expiry, and says an expired link can be replaced from the "forgot password" page. Write it with
  the `brand-guidelines` skill.
- The link lands on allauth's existing set-password page. `ACCOUNT_LOGIN_ON_PASSWORD_RESET = True`
  is already set, so finishing it logs the person in and they stop being pending. Pin with a test
  that the reset-from-key flow accepts a user with an unusable password on the installed allauth.

### R2. Learner management: the actions (`freedom_ls/learner_management/`)

New module `freedom_ls/learner_management/learner_actions.py`. Each function is the single seam
for its action (spec 11 instruments these). Each runs in one `transaction.atomic()`, takes no
`request`, is idempotent, and fires its webhook events on commit only when something changed.

- `add_learners(organisation: Organisation, entries: list[LearnerEntry], cohort: Cohort | None = None) -> list[AddLearnerResult]`.
  - `LearnerEntry` is a dataclass: `email`, `first_name`, `last_name`.
  - Entries are de-duplicated case-insensitively first.
  - Per entry it calls `match_or_create_user`, then `ensure_learner` (which reactivates), then the
    cohort membership if a cohort was given. It sends the account setup email for a new user.
  - `AddLearnerResult` is a dataclass: `email`, `outcome`, `learner: Learner | None`, and
    `cohort_outcome: CohortOutcome | None`.
    - `outcome` is a `TextChoices` with values `created`, `joined`, `reactivated`,
      `already_learner`, `invalid_email`, `email_in_use_elsewhere`.
    - `cohort_outcome` is a `TextChoices` with values `added`, `already_member`.
  - Spec 8 reuses these labels row by row.
- `deactivate_learner(learner: Learner) -> bool` and `reactivate_learner(learner: Learner) -> bool`.
  They set `Learner.is_active`. Nothing cascades.
- `add_to_cohort(learner: Learner, cohort: Cohort) -> bool`. Raises `ValueError` when the cohort's
  organisation differs from the learner's.
- `remove_from_cohort(learner: Learner, cohort: Cohort) -> bool`. Deletes the `CohortMembership`.
- `move_between_cohorts(learner: Learner, source: Cohort, destination: Cohort) -> str`. Returns the
  `move_id`.
  - Locks the learner (`select_for_update`), deletes the source membership and creates the
    destination membership.
  - Then sends a new signal `cohort_membership_moved(learner, source, destination)` synchronously,
    inside the transaction.
  - Raises `ValueError` if the cohorts are the same, are in different organisations, the source
    membership does not exist, or the destination membership already does.
- `register_for_course(learner: Learner, course: Course) -> bool`. Creates the
  `LearnerCourseRegistration` or reactivates it.
- `unregister_from_course(learner: Learner, course: Course) -> bool`. Sets the individual
  registration's `is_active` false.
- Consequence queries in `learner_management/queries.py`, reused by single and bulk confirmations:
  - `courses_losing_access(learner, removing: Cohort, adding: Cohort | None = None) -> list[Course]`:
    courses the cohort grants that no other active membership or active individual registration
    still grants.
  - `other_grants_for(learner, course) -> list[Cohort]`: the cohorts still granting a course after
    an unregistration.
- Visibility: `learners_visible_to` (`queries.py:288-321`) gains `include_removed: bool = False`.
  The list, the detail page's `authorise_instance` and the matrix agreement test
  (`test_permission_matrix.py:477`) use the widened form, so removed learners have rows and pages.

### R3. Learner progress: the move (`freedom_ls/learner_progress/`)

- A receiver for `cohort_membership_moved`, connected in `LearnerProgressConfig.ready()`, runs
  inside the move's transaction. For each course with a course progress record under one of the
  source cohort's registrations, and an active registration on the destination cohort, it applies
  Decisions 2 and 3:
  - No record under the destination registration. Re-point the source record's
    `cohort_registration`.
  - A record under both, source further along. Swap the two records' `cohort_registration` values
    in one `UPDATE` (ORM `Case`/`When`).
  - Otherwise, leave both.
- Swapping needs `one_course_progress_per_cohort_registration` to be
  `deferrable=Deferrable.IMMEDIATE`, so Postgres checks uniqueness at the end of the statement. New
  migration.
  - Check that `ensure_course_progress_records_for_cohort_registration` (`utils.py:95`,
    `bulk_create(ignore_conflicts=True)`) still skips conflicts against a deferrable constraint.
  - If it does not, it filters out existing `(learner, cohort_registration)` pairs before inserting.
- Because the re-point happens before commit, the on-commit mint fired by the new membership's
  `post_save` finds the moved record and creates nothing.
- `move_progress_preview(learner, source, destination) -> list[MoveProgressOutcome]`. Per affected
  course it says which record continues and its percentage. The move confirmation shows it.
  `educator_interface` calls it; `learner_management` never imports `learner_progress` at runtime.

### R4. Webhooks (`freedom_ls/base/webhook_event_types.py`, `freedom_ls/webhooks/events.py`)

- `fire_webhook_event(event_type, payload, site: Site | None = None)`. An explicit site is used
  when no request is in scope; the current early return stays for the no-site case.
- New entries in `FLS_WEBHOOK_EVENT_TYPES` and `WEBHOOK_EVENT_TYPE_SAMPLES`:

| Event | Fired by | Payload beyond `user_id`, `user_email`, `organisation_id`, `learner_id` |
| --- | --- | --- |
| `learner.added` | `add_learners`, new `Learner` row | `account_created: bool` |
| `learner.deactivated` | `deactivate_learner` | none |
| `learner.reactivated` | `reactivate_learner`, `add_learners` on a removed learner | none |
| `cohort.member_added` | `add_to_cohort`, `add_learners` with a cohort, `move_between_cohorts` | `cohort_id`, `cohort_name`, `move_id` (null unless a move) |
| `cohort.member_removed` | `remove_from_cohort`, `move_between_cohorts` | as above |
| `course.unregistered` | `unregister_from_course` | `course_id`, `course_title` |
| `cohort.course_registered` | spec 6 | `cohort_id`, `course_id`, `course_title`, no learner fields |
| `cohort.course_unregistered` | spec 6 | as above |

- `course.registered` keeps firing for a new individual registration
  (`learner_progress/signals.py:157`). It now also fires when `register_for_course` reactivates
  one. The learner notification stays as it is.
- Staff-created accounts do not fire `user.registered`.

### R5. Permissions (`learner_management/capabilities.py`, `role_based_permissions/`)

Matrix rows, with the spec 5 matrix and `test_permission_matrix.py` updated together:

| Action | Capability (scope) | Who |
| --- | --- | --- |
| View list and detail, including removed learners | `view_learner` (organisation / learner) | all four roles, as today |
| Add learners (new or existing accounts) | `add_learner` (organisation) | site_admin, organisation_admin |
| Deactivate, reactivate, resend account setup email | `change_learner` (learner) | site_admin, organisation_admin |
| Edit a learner's name | new string for `User` change (learner) | site_admin only |
| Add to cohort / remove from cohort | `add_cohortmembership` / `delete_cohortmembership` (cohort) | plus cohort_admin within assigned cohorts |
| Move | `delete_` on source and `add_` on destination | as above |
| Register, unregister, re-register individually | `add_learnercourseregistration` / `change_learnercourseregistration` (learner) | plus cohort_admin within assigned cohorts |

- The new string is registered in `role_based_permissions/registry.py` and granted to `site_admin`.
- On the cohort's learners tab, a cohort admin's picker offers only learners they can already see.
  The "add a new learner" path is hidden from anyone without `add_learner`.
- Controls the user cannot use are not rendered. A stale action returns the existing 403 fragment.

### R6. Educator interface (`freedom_ls/educator_interface/`, `freedom_ls/panel_framework/`)

**Shared learner cell.** `educator_interface/templates/educator_interface/data-table-cells/learner.html`:
`panel-avatar-chip` with the name and the email as secondary text, wrapped in the spec 3
quick-view trigger. Every table that lists learners uses it.

**List (`LearnerDataTable`, `views.py:220-285`).**

- Columns: Learner (shared cell, sortable by name), Status (`panel-status-badge`), Cohorts,
  Courses with progress percentage, Last active.
  - Status tones: Active `success`, Pending `info`, Removed `muted`.
  - Last active is the max `CourseProgress.last_accessed_time`, "Never" when there is none.
- Search: first name, last name, email (unchanged).
- Filters:
  - Status (Active, Pending, Removed), defaulting to Active and Pending. Cohort, from
    `cohorts_visible_to`. Course.
  - `TableFilter` in `panel_framework/filters.py` gains a `default` used when the query parameter
    is absent. The status filter's `apply` uses `pending_user_q`.
- `get_row_label` defined; `LearnerConfig.get_bulk_actions` returns `[]`.
- An "Add learners" list action, if the user holds `add_learner`.
- Mobile cards follow the spec 2 card layout.

**Add learners dialog.**

- One form: a textarea taking one entry per line, `email[, first name[, last name]]`, at most 50
  lines, and an optional cohort select.
  - The cohort select offers cohorts in the organisation where the user holds
    `add_cohortmembership`, excluding inactive cohorts once spec 6's `Cohort.is_active` exists.
  - It is preset and fixed when opened from a cohort's learners tab.
- Invalid input returns 422. A valid submit calls `add_learners` and replaces the dialog body with a
  per-address results list in plain words.
- Fires `learnerChanged`, plus `cohortChanged` when a cohort was given.
- It is a custom `PanelAction` subclass, since `FormPanelAction` is ModelForm-shaped.

**Detail (`LearnerInstanceView`).**

- A `TabSet` replaces `LearnerPanelStack`.
- The header shows name, email, status badge and actions: Edit name (R5), Deactivate or
  Reactivate, Resend setup email (pending learners only), Add to cohort, Register for course.
- Tabs:
  - `overview`:
    - Details: name, email, status, date added (`Learner.created_at`).
    - Cohorts: name and join date (`CohortMembership.created_at`), with row actions Remove and Move.
    - Registrations: course, source (individual or "via <cohort>"), active or inactive. Individual
      rows get Unregister or Re-register.
  - `courses`: per registration, progress percentage and last activity, with a panel slot spec 10
    fills.
  - `history`: empty state only, for spec 11.

**Cohort learners tab (`CohortLearnersPanel`, `views.py:349`).** Uses the shared cell and the
status filter. The tab action is Add learners:

- Pick existing learners in the organisation who are not already members, or open the add
  learners dialog with this cohort preset (R5 decides which the user sees).
- Row actions: Remove from cohort, Move to another cohort.

**Confirmations.** Each is a new `PanelAction` with its own modal fragment under
`panel_framework/modal/`. All return 204 with `HX-Trigger`, and 422 on a stale or invalid request.

| Action | The confirmation says |
| --- | --- |
| Deactivate | They lose access to this organisation's courses. Cohorts, registrations and progress are kept and return on reactivation. On the default organisation, self-registering for an open course reactivates them. |
| Reactivate | Access returns through their existing cohorts and registrations. |
| Remove from cohort | The courses from `courses_losing_access`. Progress is kept. |
| Move | The destination picker (same organisation, `add_cohortmembership` held, not the source, not already a member, not inactive once `Cohort.is_active` exists). The courses lost and gained. The `move_progress_preview` line per shared course, e.g. "Intro to X: continues at 40%". |
| Unregister | Whether a cohort still grants the course (named from `other_grants_for`). Progress is kept. On the default organisation, self-registration re-registers them. |
| Resend setup email | The address it goes to. A recent send returns 422 "Sent recently, try again in N minutes". |

- UI events: membership actions fire `learnerChanged` and `cohortChanged`; registration actions
  fire `registrationChanged` and `learnerChanged`; the rest fire `learnerChanged`. No new event
  names.
- **Quick view.** `quick_views/learner.html` shows Pending. The TODO at line 9 is then done and goes.

## Testing

- Accounts:
  - `match_or_create_user` matches case-insensitively and leaves existing names alone. It raises
    for an address on another site. A new user gets an unusable password and a verified primary
    `EmailAddress`.
  - `is_pending` and `pending_user_q` agree, including the self-signup who never logged in (not
    pending) and the admin-made user with a typed password (not pending).
  - The account setup email renders with the site theme, links to the user's site domain, sends
    with no request, and is not sent for a rolled-back creation.
  - The installed allauth accepts the setup link for an unusable-password user. Completing it logs
    them in and clears pending.
  - A resend inside `ACCOUNT_SETUP_EMAIL_RESEND_SECONDS` is refused. A resend to a non-pending user
    is refused.
- Actions (`learner_actions.py`):
  - Every outcome label of `add_learners`, including duplicates within one submission and the
    second run of the same input ("already_learner", "already_member").
  - Deactivate changes no registration, membership or progress row.
  - Every action is idempotent and fires no webhook on a no-op.
- Move:
  - Re-point with no clash.
  - Clash where the source is further along: swapped.
  - Clash where the destination is further along or tied: untouched.
  - A course only the source grants: record left in place. A course only the destination grants:
    fresh record minted.
  - No duplicate record after on-commit callbacks run (`django_capture_on_commit_callbacks(execute=True)`).
  - A failure mid-move rolls back both memberships.
  - `bulk_create(ignore_conflicts=True)` still behaves against the deferrable constraint.
- Webhooks:
  - Each new event fires once with the documented payload.
  - A move fires removed then added with one `move_id`.
  - Re-registration fires `course.registered`.
  - `fire_webhook_event` with an explicit site and no request records the event.
- Permissions: new matrix rows in `test_permission_matrix.py`, including the "every capability
  reachable from the interface is in the matrix" test. Cohort admin:
  - can move between two assigned cohorts but not to an unassigned one;
  - does not see the add-new path.
- Interface:
  - List status filter default and each status.
  - Removed learners reachable by filter and detail URL.
  - Each confirmation's copy for the cases in the table above.
  - 422 paths.
  - Organisation isolation for every new action (`test_organisation_isolation.py`).
- Playwright (marked `playwright`):
  - Add learners with mixed outcomes.
  - Move with a progress preview.
  - Deactivate and reactivate from the detail header.
  - The learners list and detail at mobile width.

## Open questions

- The setup link expires with `PASSWORD_RESET_TIMEOUT` (3 days by default). Resend and the "forgot
  password" page are the recovery paths. Raising the timeout would lengthen reset links too.
- The add form caps a submission at 50 lines. Larger lists are spec 8's CSV import.
- Staff-created accounts do not fire `user.registered`. A downstream CRM listening only to that
  event will miss them.
- Course picker for individual registration: courses on the site the learner is not actively
  registered for individually. Narrow it if courses become organisation-scoped.

## Success criteria

- A site_admin adds three addresses (one existing user on the site, one removed learner, one new)
  in one submit and sees "joined", "reactivated" and "created". The new person receives a themed
  email whose link sets a password and logs them in.
- The learners list defaults to active and pending learners. Filtering by Removed shows deactivated
  learners, and their detail page loads.
- A learner at 40% in a course both cohorts grant is moved and still reads 40% for that course, and
  the confirmation said so beforehand.
- A move creates no new 0% course progress record for a course both cohorts grant.
- A cohort admin cannot see Deactivate, Add new learner, or a destination cohort outside their
  assignments, and a forged POST to those actions returns 403.
- Each action in R2 produces the webhook events in R4 and none on a repeat.
- `uv run pytest` passes, and `learner_management` has no runtime import of `learner_progress`
  (`docs/app_structure.md` unchanged on that edge).
