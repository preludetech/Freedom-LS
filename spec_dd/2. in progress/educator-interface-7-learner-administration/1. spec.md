# Spec: Learner administration

Spec 7 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Idea: `idea.md`. Spec 6 (`educator-interface-6-cohort-administration`, now in
`spec_dd/3. done/`) landed first and provides `Cohort.is_active`,
`access_granting_cohort_registrations`, the `announce_cohort_registration_change` seam,
`PanelAction.is_offered`, `InstanceView.get_status_badge` and the organisation-scoped course
queries. Under spec 6's Decision 5 the spec that lands second does the joining work, so this one
fills the seam (R2) and keeps inactive cohorts out of membership actions (Decision 13). Resources:
`research_lms_educator_ux.md`; the mockups `Educator Learners.dc.html` screens 02 and 03 and
`Educator Mobile Learners.dc.html` M03 to M05, under
`spec_dd/1. next/educator-interface-full-polish/Educator LMS Interface Design/` (layout and density
only, never scope or theme).

## Purpose

Make the educator interface's learners section complete, so routine learner administration no
longer needs the Django admin or a typed password, and settle what a move does to the learner's
course progress records.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| pending | coined | A `User` whose `last_login` is null and who has no usable password. It belongs to the `User`, so a person pending in one organisation is pending in all of them. A learner's status is `removed` if `Learner.is_active` is false, else `pending` if their user is pending, else `active`. Unrelated to the `pending` status values on webhook deliveries and reports. |
| account setup email | coined | The email sent to a staff-created `User` carrying a password-set link built on allauth's reset token. |
| move | coined | One action that deletes a learner's `CohortMembership` in one cohort and creates one in another cohort of the same organisation, in a single transaction. |

## Scope

In:

- Adding learners to an organisation through one form: existing accounts matched, new accounts
  created with an account setup email, optional cohort.
- The learners list (status, search, filters) and the learner detail page (overview, courses and
  progress, empty history tab).
- Deactivate, reactivate, resend account setup email, site_admin name editing.
- Cohort membership add, remove and move, from the learner page and from the cohort's learners tab.
- Individual course registration, unregistration and re-registration from the learner page.
- What a move does to course progress records.
- Webhook event types for every action here and for cohort registration.
- The permission matrix rows and capability strings these actions need.

Out: CSV import and bulk actions (spec 8). Educator roles (spec 9). Progress detail beyond a
percentage (spec 10). Audit history content (spec 11). Cohort registration UI (spec 6). Account
merge, log in as a learner, cross-organisation moves, hard delete of a `Learner` or `User`,
retakes and progress resets, email editing. Everything in the mockups the idea does not ask for:
messaging, "Reset attempt", extra statuses, assessments, certificates and activity tabs, extra
profile fields, column visibility.

## Decisions

1. **Pending is derived, no new column.** `last_login IS NULL` alone also matches self-signups who
   never confirmed; requiring no usable password excludes them.
2. **A move re-points course progress records rather than copying them**, for each course that an
   active registration on the destination cohort grants and a registration on the source cohort
   granted. The done progress spec (`spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/`)
   handed this rule to this work.
3. **Move clash: the furthest-along record wins.** If the learner already has a course progress
   record under the destination registration, the one with the higher `progress_percentage` ends
   up under the destination registration and the other under the source registration, unused. A
   tie keeps the destination record where it is. Nothing is merged or deleted.
4. **Name editing is `site_admin` only. Email editing stays in the Django admin**, because the
   email is the login for every organisation and changing it needs allauth re-verification.
5. **The add-learner code lives in `learner_management`; user creation and the account setup email
   live in `accounts`.** `accounts` cannot import `learner_management` at runtime, and spec 9 needs
   user creation without `ensure_learner`.
6. **The account setup email is an allauth-adapter email** with its own templates in `accounts`, so
   it carries the site theme and logo. There is no subject setting; a project overrides
   `account_setup_subject.txt`.
7. **Staff-created users get a verified, primary `EmailAddress` at creation.** The only way in is
   the link sent to that address, so use proves verification. Without it,
   `ACCOUNT_EMAIL_VERIFICATION = "mandatory"` sends a second email at first login.
8. **Resend is rate limited with a per-user cache guard** (`cache.add`), not `ACCOUNT_RATE_LIMITS`,
   which has no key for custom actions, is replaced wholesale by downstream projects and is off in
   dev.
9. **A move fires two webhook events** (`cohort.member_removed`, then `cohort.member_added`)
   sharing a `move_id`, so consumers keep one handler per fact.
10. **Self-registration can still undo a deactivation or unregistration** on the site's default
    organisation (`learner_interface/views.py:889-905`). No behaviour change; the confirmations say
    so.
11. **Row selection ships as a seam.** No bulk actions here (the inherited `get_bulk_actions`
    returns `[]`), and `LearnerDataTable.get_row_label` names the learner. Checkboxes appear when
    spec 8 registers its actions.
12. **Revoking a pending learner is deactivating them, and it leaves the setup link alive.**
    Following the link gets the person an account with no access in this organisation. Killing the
    link would touch a `User` other organisations may share.
13. **An inactive cohort takes no membership action, from either side.** Spec 6's Decision 3 makes
    an inactive cohort read-only. Its learners tab offers no Add learners, Remove or Move; a
    learner page's row for it offers neither Remove nor Move; no membership picker offers it. The
    functions refuse too: `add_learners` with an inactive cohort, `add_to_cohort`,
    `remove_from_cohort`, and a move whose source or destination is inactive raise `ValueError`
    and change nothing. A stale POST answers 422 with spec 6's `cohort_inactive.html`. To empty an
    inactive cohort for deletion, reactivate it first.
14. **A learner with no name is shown by their email.** Staff-created users often have no name.
    Spec 6 fixed its QA bug B1 with the link cell's `fallback_text_attr`; the shared learner cell
    keeps that behaviour. Its primary text is `User.display_name`, which falls back to the email,
    and the email is the secondary text only when a name exists. The link and quick-view trigger
    always render, labelled by that text.
15. **The individual course picker follows spec 6's registerable rule.** Published and hidden
    courses, never coming-soon, minus those the learner already holds an active individual
    registration for. Spec 6 made the courses section organisation-scoped through
    `courses_visible_to`, under which an individual registration makes its course visible in this
    organisation, so the picker needs no further narrowing.

## Requirements

### R1. Accounts: users created by staff (`freedom_ls/accounts/`)

- New module `freedom_ls/accounts/account_setup.py`:
  - `match_or_create_user(site: Site, email: str, first_name: str = "", last_name: str = "") -> tuple[User, bool]`.
    Strips the address and normalises the domain. Looks it up with `User._base_manager` and
    `email__iexact` across all sites, because `User.email` is globally unique.
    - A match on `site`: returns it unchanged. Existing names are never overwritten.
    - A match on another site: raises `EmailInUseOnAnotherSite`.
    - No match: creates the `User` on `site` with `set_unusable_password()` (not
      `UserManager.create_user`, which refuses an empty password), and
      `EmailAddress(email=..., verified=True, primary=True)`.
  - `is_pending(user: User) -> bool` and `pending_user_q(prefix: str = "") -> Q`
    (`last_login__isnull=True` and `password__startswith=UNUSABLE_PASSWORD_PREFIX`). One definition,
    two shapes.
  - `send_account_setup_email(user: User, organisation_name: str) -> None`. A name rather than an
    `Organisation`, so `accounts` gains no runtime edge to `organisations`.
    - Builds the key as allauth does (`user_pk_to_url_str`, `default_token_generator.make_token`)
      and the absolute URL for `account_reset_password_from_key` from `user.site.domain` and
      `ACCOUNT_DEFAULT_HTTP_PROTOCOL`, never from the request.
    - Sends through `get_adapter().send_mail("account/email/account_setup", user.email, context)`
      on `transaction.on_commit`. The context holds `user`, `organisation_name`, `setup_url` and the
      expiry in days, from `PASSWORD_RESET_TIMEOUT`.
    - Sets the resend guard, so an immediate resend is refused.
    - Raises `AccountAlreadySetUp` when the user is not pending.
  - `resend_account_setup_email(user: User, organisation_name: str) -> None`. Raises
    `SetupEmailRecentlySent` when `cache.add(f"account-setup-email:{user.pk}", 1, timeout)` fails,
    otherwise sends.
- `accounts/config.py`: new setting `SETUP_EMAIL_RESEND_SECONDS: int`, default `900`. Not
  `ACCOUNT_`-prefixed, which is allauth's namespace.
- `AccountAdapter` (`accounts/allauth_account_adapter.py:32-53`) resolves the site from the allauth
  request for the branding context and, through `site_display_name_for_request`, the subject
  prefix. With no request, both fall back to `context["user"].site`, so spec 8 can send from a
  background task. `get_cached_site(None)` refuses today.
- Templates: `accounts/templates/account/email/account_setup_subject.txt`,
  `account_setup_message.txt`, `account_setup_message.html` (extending `emails/base_email.html`).
  The copy names the organisation, says an account was made for them, gives the link and its
  expiry, and says an expired link can be replaced from the "forgot password" page. Write it with
  the `brand-guidelines` skill.
- The link lands on allauth's set-password page. `ACCOUNT_LOGIN_ON_PASSWORD_RESET = True` is
  already set, so finishing it logs the person in and they stop being pending.

### R2. Learner management: the actions (`freedom_ls/learner_management/`)

New module `freedom_ls/learner_management/learner_actions.py`. Each function is the single seam for
its action (spec 11 instruments these). Each runs in one `transaction.atomic()`, takes no
`request`, and fires its webhook events on commit, with the organisation's site, only when
something changed. Every action except `add_learners` and the move is idempotent and returns
whether it changed anything.

- `add_learners(organisation: Organisation, entries: list[LearnerEntry], cohort: Cohort | None = None) -> list[AddLearnerResult]`.
  - `LearnerEntry` is a dataclass: `email`, `first_name`, `last_name`.
  - Raises `ValueError` before touching any entry when the cohort is inactive or in another
    organisation; the dialog answers 422.
  - Entries are de-duplicated case-insensitively first.
  - Per entry: `match_or_create_user`, then `ensure_learner` (which reactivates), then the cohort
    membership if a cohort was given. A new user gets the account setup email.
  - `AddLearnerResult` is a dataclass: `email`, `outcome`, `learner: Learner | None`,
    `cohort_outcome: CohortOutcome | None`.
    - `outcome` is a `TextChoices`: `created`, `joined`, `reactivated`, `already_learner`,
      `invalid_email`, `email_in_use_elsewhere`.
    - `cohort_outcome` is a `TextChoices`: `added`, `already_member`.
  - Spec 8 reuses these labels row by row.
- `deactivate_learner(learner: Learner) -> bool` and `reactivate_learner(learner: Learner) -> bool`.
  They set `Learner.is_active`. Nothing cascades.
- `add_to_cohort(learner: Learner, cohort: Cohort) -> bool`. Raises `ValueError` when the cohort's
  organisation differs from the learner's or the cohort is inactive.
- `remove_from_cohort(learner: Learner, cohort: Cohort) -> bool`. Deletes the `CohortMembership`.
  Raises `ValueError` when the cohort is inactive (Decision 13).
- `move_between_cohorts(learner: Learner, source: Cohort, destination: Cohort) -> str`. Returns the
  `move_id`.
  - Locks the learner (`select_for_update`), deletes the source membership and creates the
    destination membership.
  - Then sends a new signal `cohort_membership_moved(learner, source, destination)` synchronously,
    inside the transaction.
  - Raises `ValueError` if the cohorts are the same, are in different organisations, either
    cohort is inactive, the source membership does not exist, or the destination membership
    already does. A repeated move is therefore refused, not a no-op.
- `register_for_course(learner: Learner, course: Course) -> bool`. Creates the
  `LearnerCourseRegistration` or reactivates it.
- `unregister_from_course(learner: Learner, course: Course) -> bool`. Sets the individual
  registration's `is_active` false.
- Spec 6's `announce_cohort_registration_change(registration)` in `learner_management/utils.py`
  is a no-op carrying a TODO. It now fires `cohort.course_registered` or
  `cohort.course_unregistered` by the registration's `is_active`, with the cohort's site, on
  commit. Spec 6's `register_cohort_for_course` and `unregister_cohort_from_course` call it only
  when they created the row or changed its `is_active`, so a no-op fires nothing. The TODO is then
  done and goes.
- Consequence queries in `learner_management/queries.py`, reused by single and bulk confirmations.
  "Grants" means through an active individual registration, or a membership of a cohort with a
  registration from `access_granting_cohort_registrations`:
  - `courses_losing_access(learner, removing: Cohort, adding: Cohort | None = None) -> list[Course]`:
    courses `removing` grants that nothing else the learner holds, nor `adding`, still grants.
  - `other_grants_for(learner, course) -> list[Cohort]`: the cohorts still granting a course after
    an unregistration.
  - `registerable_courses_for_learner(learner) -> QuerySet[Course]`: spec 6's
    `registerable_courses_for(cohort)` rule for a learner (Decision 15). The two share one base
    queryset rather than repeating the visibility exclusion.
- Visibility: `learners_visible_to` in `queries.py` gains `include_removed: bool = False`,
  applied on both of its return paths. The list, the detail page's `authorise_instance` and the
  matrix agreement test (`educator_interface/tests/invariants/test_permission_matrix.py`) use the
  widened form, so removed learners have rows and pages. Spec 6's `courses_visible_to` and
  `educators_of` keep the default, so a removed learner's registrations do not widen the courses
  section and the `educators_of` agreement test is unchanged.
- New runtime app edges, for the plan structure review: `learner_management → webhooks` (the
  actions fire events) and `educator_interface → accounts` (resend and name editing).

### R3. Learner progress: the move (`freedom_ls/learner_progress/`)

- A receiver for `cohort_membership_moved`, connected in `LearnerProgressConfig.ready()`, runs
  inside the move's transaction. For each course with a course progress record under the source
  cohort's registration and an active registration on the destination cohort, it applies
  Decisions 2 and 3:
  - No record under the destination registration: re-point the source record's
    `cohort_registration`.
  - Both exist and the source record is further along: swap the two records' `cohort_registration`
    values in one `UPDATE` (ORM `Case`/`When`).
  - Otherwise, leave both.
- The swap needs `one_course_progress_per_cohort_registration` to be
  `deferrable=Deferrable.IMMEDIATE`, so Postgres checks uniqueness at the end of the statement. New
  migration. Postgres does not use a deferrable constraint as an `ON CONFLICT` arbiter, so
  `ensure_course_progress_records_for_cohort_registration` (`utils.py:95`) stops relying on
  `bulk_create(ignore_conflicts=True)` for this constraint and filters out existing
  `(learner, cohort_registration)` pairs before inserting.
- The re-point happens before commit, so the on-commit mint fired by the new membership's
  `post_save` finds the moved record and creates nothing.
- `move_progress_preview(learner, source, destination) -> list[MoveProgressOutcome]`: per affected
  course, which record continues and its percentage. `educator_interface` calls it;
  `learner_management` never imports `learner_progress` at runtime.
- `course.registered` (`learner_progress/signals.py:157`) fires when a `LearnerCourseRegistration`
  is created or its `is_active` changes from false to true, whoever made the change. The learner
  notification still goes out only on creation.

### R4. Webhooks (`freedom_ls/base/webhook_event_types.py`, `freedom_ls/webhooks/events.py`)

  when no request is in scope; the early return stays for the no-site case.
- New entries in `FLS_WEBHOOK_EVENT_TYPES` and `WEBHOOK_EVENT_TYPE_SAMPLES`:

| Event | Fired by | Payload beyond `user_id`, `user_email`, `organisation_id`, `learner_id` |
| --- | --- | --- |
| `learner.added` | `add_learners`, new `Learner` row | `account_created: bool` |
| `learner.deactivated` | `deactivate_learner` | none |
| `learner.reactivated` | `reactivate_learner`, `add_learners` on a removed learner | none |
| `cohort.member_added` | `add_to_cohort`, `add_learners` with a cohort, `move_between_cohorts` | `cohort_id`, `cohort_name`, `move_id` (null unless a move) |
| `cohort.member_removed` | `remove_from_cohort`, `move_between_cohorts` | as above |
| `course.unregistered` | `unregister_from_course` | `course_id`, `course_title` |
| `cohort.course_registered` | `announce_cohort_registration_change` | `cohort_id`, `course_id`, `course_title`, no learner fields |
| `cohort.course_unregistered` | `announce_cohort_registration_change` | as above |

- Staff-created accounts do not fire `user.registered`. A downstream CRM listening only to that

### R6. Educator interface (`freedom_ls/educator_interface/`, `freedom_ls/panel_framework/`)

**Shared learner cell.** `educator_interface/templates/educator_interface/data-table-cells/learner.html`:
`panel-avatar-chip` with the text Decision 14 sets, wrapped in the spec 3 quick-view trigger.
Every table that lists learners uses it.

**List (`LearnerDataTable`).**

- Columns: Learner (shared cell, sortable by name), Status (`panel-status-badge`: Active `success`,
  Pending `info`, Removed `muted`, through a three-state `learner_status_badge(learner)` helper and
  a `learner_status.html` cell; spec 6's `active_status_badge` and `<c-active-status-badge>` stay
  two-state, for `is_active` flags), Cohorts, Courses with progress percentage, Last active (the
  max `CourseProgress.last_accessed_time`, "Never" when there is none).
- Search: first name, last name, email (unchanged).
- Filters: Status (Active, Pending, Removed), defaulting to Active and Pending; Cohort, from
  `cohorts_visible_to`, which includes inactive cohorts (spec 6 Decision 6), labelled as such;
  Course, from `courses_visible_to`. `TableFilter` in `panel_framework/filters.py` gains a
  `default` used when the query parameter is absent. The queryset starts from
  `include_removed=True` and the status filter narrows it, so a filter still only narrows. Spec 6's
  `ShowInactiveFilter` in `educator_interface/filters.py` is a toggle that widens and has no
  default; it is left alone. The status filter's `apply` uses `pending_user_q`.
- An "Add learners" list action, if the user holds `add_learner`.
- Mobile cards follow the spec 2 card layout.

**Add learners dialog.**

- One form: a textarea taking one entry per line, `email[, first name[, last name]]`, at most 50
  lines (larger lists are spec 8's CSV import), and an optional cohort select.
  - The cohort select offers active cohorts in the organisation where the user holds
    `add_cohortmembership`.
  - It is preset and fixed when opened from a cohort's learners tab.
- Invalid input returns 422. A valid submit calls `add_learners` and replaces the dialog body with a
  per-address results list in plain words.
- It is a custom `PanelAction` subclass, since `FormPanelAction` is ModelForm-shaped.

**Detail (`LearnerInstanceView`).**

- `LearnerInstanceView.panel` becomes a `TabSet`, and `LearnerPanelStack` goes. Spec 6's
  `LearnerCohortsPanel` and `LearnerCohortDataTable` stay as the overview tab's Cohorts card
  (search, sort, no filters, inactive cohorts with their badge, as spec 6's tests in
  `test_learner_section.py` say), gaining a Joined column and the two row actions below.
  `LearnerDetailsPanel` becomes the details card.
- The header shows name, email, status badge and actions: Edit name, Deactivate or Reactivate,
  Resend setup email (pending learners only), Add to cohort, Register for course. The badge comes
  from spec 6's `InstanceView.get_status_badge`; `InstanceView` gains `get_subtitle`, rendered into
  the `panel-page-header` subtitle, which carries the email. State-dependent actions use
  `PanelAction.is_offered`.
- Register for course offers `registerable_courses_for_learner` (Decision 15). A course outside
  that set answers 422 and creates no row, as spec 6's cohort Register does.
- Tabs:
  - `overview`:
    - Details: name, email, status, date added (`Learner.created_at`).
    - Cohorts: name and join date (`CohortMembership.created_at`), an inactive cohort marked with a
      badge, with row actions Remove and Move. Neither is offered on an inactive cohort
      (Decision 13).
    - Registrations: course, source (individual or "via <cohort>"), active or inactive. Individual
      rows get Unregister or Re-register.
  - `courses`: per registration, progress percentage and last activity, with a panel slot spec 10
    fills.
  - `history`: empty state only, for spec 11.

**Cohort learners tab (`CohortLearnersPanel`).** Uses the shared cell and the status filter. The
tab count stays spec 6's: every member whose `Learner.is_active` is true, whatever the filter. The
tab action is Add learners: pick existing learners in the organisation who are not already members,
or open the add learners dialog with this cohort preset (R5 decides which the user sees). Row
actions: Remove from cohort, Move to another cohort. On an inactive cohort none of these is offered
(Decision 13), through spec 6's `RequiresActiveCohortMixin`.

**Confirmations.** Each is a new `PanelAction` with its own modal fragment under
`educator_interface/templates/educator_interface/modal/`, extending
`panel_framework/modal/read_only.html` or `delete_confirmation.html` as spec 6's do. All return 204
with `HX-Trigger`, and 422 on a stale or invalid request. On the learner page the cohort arrives
as a parameter, so the inactive check runs on the resolved cohort rather than through
`RequiresActiveCohortMixin`, which reads `ctx.instance`.

| Action | The confirmation says |
| --- | --- |
| Deactivate | They lose access to this organisation's courses. Cohorts, registrations and progress are kept and return on reactivation. On the default organisation, self-registering for an open course reactivates them. |
| Reactivate | Access returns through their existing cohorts and registrations. |
| Remove from cohort | The courses from `courses_losing_access`. Progress is kept. |
| Move | The destination picker (same organisation, active, `add_cohortmembership` held, not the source, not already a member). The courses lost and gained. The `move_progress_preview` line per shared course, e.g. "Intro to X: continues at 40%". |
| Unregister | Whether a cohort still grants the course (named from `other_grants_for`). Progress is kept. On the default organisation, self-registering for an open course re-registers them. |
| Resend setup email | The address it goes to. A recent send returns 422 "Sent recently, try again in N minutes". |

- UI events: membership actions and adding learners to a cohort fire `learnerChanged` and
  `cohortChanged`; registration actions fire `registrationChanged` and `learnerChanged`; the rest
  fire `learnerChanged`. No new event names.
- **Empty pickers.** When a picker has nothing to offer, its dialog shows one sentence in place
  of the select, a Close button and no submit button. The sentence is set once in the shared modal
  form fragment, and each picker supplies its own words:
  - Add learners (existing-learner picker on a cohort's learners tab): "Everyone in your other
    cohorts is already in <cohort>. To add someone new, ask an organisation admin."
  - Add to cohort: "<learner> is already in every active cohort you can add learners to."
  - Register for course: "There is no course <learner> can be registered for right now."
  - Move: "There is no other active cohort you can move <learner> to."
  `<learner>` is the Decision 14 text. A stale submit from an emptied picker still answers 422.
- **Quick view.** `quick_views/learner.html` shows Pending. The TODO at line 9 is then done and goes.

## Testing

- Accounts:
  - `match_or_create_user` matches case-insensitively and leaves existing names alone. It raises
    for an address on another site. A new user gets an unusable password and a verified primary
    `EmailAddress`.
  - `is_pending` and `pending_user_q` agree, including the self-signup who never logged in (not
    pending) and the admin-made user with a typed password (not pending).
  - The account setup email renders with the site theme and subject prefix, links to the user's
    site domain, sends with no request, and is not sent for a rolled-back creation.
  - The installed allauth accepts the setup link for an unusable-password user. Completing it logs
    them in and clears pending. The "forgot password" page sends a reset link to a pending user.
  - A resend inside `SETUP_EMAIL_RESEND_SECONDS` is refused. A resend to a non-pending user is
    refused.
- Actions (`learner_actions.py`):
  - Every outcome label of `add_learners`, including duplicates within one submission and the
    second run of the same input (`already_learner`, `already_member`).
  - Deactivate changes no registration, membership or progress row.
  - Every idempotent action fires no webhook on a no-op. A repeated move raises.
  - `courses_losing_access` ignores an inactive cohort and an inactive cohort registration as
    other grants.
  - `add_learners` with an inactive cohort, `remove_from_cohort` on one, and a move whose source or

## Success criteria

- A site_admin adds three addresses (one existing user on the site, one removed learner, one new)
  in one submit and sees "joined", "reactivated" and "created". The new person receives a themed
  email whose link sets a password and logs them in.
- The learners list defaults to active and pending learners. Filtering by Removed shows deactivated
  learners, and their detail page loads.
- A learner at 40% in a course both cohorts grant is moved and still reads 40% for that course, and
  the confirmation said so beforehand.
- A move creates no new 0% course progress record for a course both cohorts grant.
- A cohort admin cannot see Deactivate, Add new learner, or a destination cohort outside their
  assignments, and a forged POST to those actions returns 403.
- An inactive cohort offers no membership action from its learners tab or a member's page, and a
  forged POST to one returns 422 and changes nothing.
- A learner with no name opens from the learners list and the cohort learners tab, shown by email.
- Repeating any idempotent action in R2 fires no webhook event.
- `uv run pytest` passes, and `learner_management` has no runtime import of `learner_progress`
  (`docs/app_structure.md` unchanged on that edge).
