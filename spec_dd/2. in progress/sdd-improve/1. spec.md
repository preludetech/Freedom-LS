# Spec: SDD runs longer without a human

## Purpose

The SDD checklist stops for a human 18 times, and most of those stops guard commands nobody runs or
ask questions with an obvious default. `idea.md` settles the shape: fewer commands, each asking once
and early, a checklist of three real review points, and three new hook sections that keep every FLS
value out of the generic plugins. This spec names the files, sections, keys and contracts that make
that true.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| hook mode | coined | A command run inline at depth 0 by another command, told so by a `mode: hook` input. It skips its own pre-step rebase and todo tick and keeps its commit. |
| brief | narrowed | A file an `sdd:sdd-worker` reads and follows, as distinct from a hook file followed inline at depth 0 (`design_check.md`). Already used as "the worker's brief" in `plan_structure_review.md`. |
| clear fix | coined | A review finding the command applies itself: mechanical or with exactly one reading, backed by a quotable line, and not adding, removing or reordering a requirement. Everything else is a judgement call. |
| assumed default | coined | A choice a command made for a question it would otherwise have asked, recorded in the artifact as `> **Assumed default:**` so one grep finds every unconfirmed decision. |

## Scope

In:

- `claude_plugins/sdd`: delete `commands/next.md` and `commands/improve_idea.md`; merge research
  into `commands/spec_from_idea.md` with a review wave; rewrite `commands/spec_review.md` over the
  same dimension resource; add plan review hooks, a threats dimension and an end-of-run question
  batch to `commands/plan_from_spec.md`; add the per-batch reviewer to `commands/implement_plan.md`;
  add `commands/document.md`; shrink the todo template; three new config sections in
  `commands/init.md`; remove the late questions listed under "Late questions become defaults".
- `claude_plugins/fls-dev`: delete `commands/plan_security_review.md` and
  `commands/plan_structure_review.md`; add two plan review briefs under `resources/`; hook mode in
  the three documentation commands; FLS values for the new sections in `commands/init.md`.
- `claude_plugins/django-stack`: delete `commands/threat-model.md` and `commands/security-review.md`;
  hook mode in `commands/app_map.md`.
- `.claude/sdd/config.md`: the FLS values for the three new sections.
- Every README, resource and command line that names a deleted or merged command.

Out:

- The in-progress `todo.md` files of other specs. They keep the old template; a human running
  commands by hand skips a line naming a command that no longer exists.
- `/sdd:make_pr_quickly` stays as it is: `gh pr create --fill`, never reading `todo.md`.
- The batch-implementer agent file, boy-scout agent and test-organisation review dimension planned
  by `spec_dd/2. in progress/test-organisation-and-hygene-2-sdd-review-and-boy-scout/`. That spec is
  re-cut on top of the reviewer this spec builds. Its `## Testing Skills` section is not needed:
  `Test standard` under `## Review Hooks` is what the implementer brief loads.
- Dependency and secret scanning, pre-commit changes, a comment-leak script, CI linting, and
  `ds:code-reviewer`. Bandit stays in pre-commit; Claude Code's `/security-review` stays for ad hoc
  use.
- A QA hook section. The template keeps naming `/fls-dev:do_qa`, the documented coupling in
  `claude_plugins/sdd/README.md`.
- Deduplicating the fan-out recipe pasted into each command.
- These stops stay as they are: a real secret in a commit, an incompatible rebase conflict, a dirty
  main worktree, an upstream-change review saying `direction: changed`, design-tool authorisation,
  the roadmap precursor warnings in `start.md`, the `Decide` items QA files, and PR approval.

## Decisions

- **The Design check runs before the batch review.** The review then covers the batch commit and
  its design-fix commits in one diff, so no line the batch produced escapes it.
- **Research files are all durable.** Every research worker in `/sdd:spec_from_idea` writes
  `research_<topic>.md` beside the idea. One rule, and the resume scan is free.
- **List-valued config sections replace, never merge.** A non-empty list under a section in
  `.claude/sdd/config.local.md` replaces the whole list in `config.md`, matching "its values take
  precedence" for keyed sections.
- **`/sdd:document` commits what a hook leaves uncommitted.** `app_map.md` has no commit step and
  gets none; the generic command commits for it.
- **On resume, the last completed batch's Design check and review run again** before the next
  batch is spawned. A clean review costs one worker; a marker file would be state that outlives a
  crash.
- **The two on-demand PR commands do not tick.** `/sdd:make_pr_quickly` has no file tools and
  `/sdd:address_pr_review` runs repeatedly; the human ticks both when ticking the approval item.
- **The reviewer checks the test standard, not test coverage.** Whether every behaviour has a test
  is plan alignment, a wider review than this one.
- **Django-specific greps stay out of sdd.** `implement_plan.md` lists only SDD planning-noise
  patterns; everything else the reviewer reads from the files named under `## Review Hooks`.

## Requirements

### 1. Config: three new sections (`claude_plugins/sdd/commands/init.md`, `.claude/sdd/config.md`)

`init.md` Step 2 creates, and Step 5 validates, three sections after `## Test Hooks`:

```
## Plan Review Hooks

-

## Review Hooks

- Comment standard:
- Test standard:

## Documentation Hooks

-
```

- `## Plan Review Hooks` and `## Documentation Hooks` are ordered lists. Each bullet is
  `<label>: <path>`. The label is for reporting; order is the contract. An empty list, or an absent
  section or file, means no hooks.
- `## Review Hooks` is keyed like `## Rebase Hooks`. A blank key skips that half of the batch
  review.
- Step 2's intro "reads five sections" becomes eight, with one sentence per new section in the
  style of the existing ones. The extend-existing-file clause names all eight. Step 5 gains three
  validation lines in the existing phrasing ("has a `## Review Hooks` section with both `Comment
  standard` and `Test standard` keys (blank values are valid)"; "an empty list is valid" for the
  two lists) and renumbers what follows. Step 6 names the three new sections among the paths to
  fill in.
- Every reader of a new section uses the sentence `pre_step_rebase.md` Step 1 uses: read
  `.claude/sdd/config.md` and `config.local.md`, blank or absent means skip.

`claude_plugins/fls-dev/commands/init.md` gains a step beside Step 8 that fills the FLS values
below when a key is blank or a list is empty, never overwriting, with the same `PLUGINS_ROOT`
prefix rule; `Comment standard` is set only when `.claude/skills/code-comments/SKILL.md` exists
in the project. Its validation step and summary name the new keys. Its "Scope" and "Hard
requirements" text that mentions `Design check` mentions these too.

`.claude/sdd/config.md` in this repo gets:

## Plan Review Hooks

- Structure: claude_plugins/fls-dev/resources/plan_review_structure.md
- FLS threats: claude_plugins/fls-dev/resources/plan_review_fls_threats.md

### 2. Questions: once, early, with a default (every asking command)

- A command that can ask does so in one batch at the start, while its workers run, up to four per
  `AskUserQuestion`, each question carrying a recommended answer and one clause on why it matters.
  The question test from `fanout_recipe.md` ("What earns a question") is the only test.
- A question that surfaces after that batch takes the recommended default and is recorded in the
  artifact: in a spec under `## Open questions` as
  `- Q: <question>? → A: <default taken> (assumed default: <why safe>. Overrule by editing <section>.)`;
  in a plan as `> **Assumed default:** <what>. Why: <clause>. To change: <section>.`
- A `blocked` worker is answered from the idea, the code or another worker's file. A need nothing
  on disk answers goes to the user only when the recipe says so.
- Review findings that are judgement calls reach the user in one batch at the end of the command,
  recommended option first, each naming the artifact line it concerns. An unanswered one is recorded
  as an assumed default.

### 3. `/sdd:spec_from_idea` absorbs `/sdd:improve_idea` (`claude_plugins/sdd/commands/spec_from_idea.md`)

Steps, in order:

1. Pre-step rebase.
2. Research fan-out: one `sdd:sdd-worker` per topic, writing `research_<topic>.md` beside the
   idea with a `status:` footer. Topics: `codebase`, `best_practices`, `reference_implementations`,
   `prior_art`, `ux_patterns`, `known_complaints`. A topic whose file exists and ends `status: ok`
   is skipped. The idea file is never rewritten.
3. The question batch of requirement 2, while the workers run; follow-ups as research lands.
4. Write `1. spec.md` under the existing "The shape" rules.
5. Commit `write the spec`, staging the spec and the research files, via `commit_and_push.md`.
6. Review wave: one `sdd:sdd-worker` per dimension in
   `claude_plugins/sdd/resources/spec_review_dimensions.md` (requirement 4), each writing
   `.sdd-work/spec_review_<dim>.md`.
7. Apply the clear fixes; re-run only the dimensions that produced an applied fix, once, on the
   changed sections. A re-check finding that is not a regression of an applied fix goes to the
   human batch. No third round.
8. The end-of-run question batch; edit the answers into the spec.
9. Delete this run's `.sdd-work/spec_review_*.md` by name.
10. Tick `Run `/sdd:spec_from_idea``.
11. Commit `review the spec`, staging `1. spec.md` and `todo.md`.

The command's summary lists each applied fix as one line (what, dimension, evidence) and the
before/after line and word counts. The "Never write these in a spec" cut-list moves into
`spec_review_dimensions.md` so both commands read one copy; `spec_from_idea.md` points at it.

The "An idea is not a specification" and "Never write these in an idea" sections of
`improve_idea.md` move to `claude_plugins/sdd/resources/idea_standard.md`. `roadmap.md` C5 and
any other line that read them from `improve_idea.md` point there. The sentences saying
`/sdd:improve_idea` runs on main (`commands/README.md`, `resources/roadmap_format.md`) are
deleted; refining an idea before `/sdd:start` is hand editing.

### 4. Spec review dimensions (`claude_plugins/sdd/resources/spec_review_dimensions.md`, `commands/spec_review.md`)

The resource lists five dimensions, each with an id, what the worker checks, the evidence it may
cite, and which finding kinds are clear fixes:

| id | checks | clear fixes |
| --- | --- | --- |
| `completeness` | contradictions and gaps against the idea, its sibling files and the user's recorded answers | a contradiction where the idea's settled decision names the winner; a missing section the shape requires; a broken cross-reference |
| `feasibility` | project norms in `${CLAUDE_PLUGIN_ROOT}/resources/` and the skills the spec touches; whether each requirement can be built as written | none; all judgement |
| `vocabulary` | every noun and identifier against the `## Vocabulary Sources` | a term replaced by the source's term |
| `generic_plugin` | no project name, path, app or value in a plugin whose README says it is generic | moving a project value into the project's config section |
| `cut_list` | the "Never write these in a spec" list, held in this file | none; cuts are always judgement |

`spec_review.md` becomes: pre-step rebase, the wave of requirement 3 step 6, steps 7 to 9, then
commit `review the spec`. It has no todo item and no tick. Its `/threat-model` mention goes. Its
line that reads the cut-list from `spec_from_idea.md` reads the resource instead.

### 5. Plan review hooks and the threats dimension (`claude_plugins/sdd/commands/plan_from_spec.md`)

- Step 6's eight dimensions get ids, and a ninth, `new_threats`, joins them. All nine live in
  `claude_plugins/sdd/resources/plan_review_dimensions.md` with the same columns as requirement 4.
  Ids: `success_criteria`, `vertical_slices`, `skills`, `generic_plugin`, `junk_files`,
  `clean_code`, `comments`, `vocabulary`, `new_threats`.
- `new_threats` looks only at what the plan adds or changes. One narrow check per trigger:
  - a new view or endpoint: an explicit permission check, and the object looked up in a way that
    scopes it to the user or site, not fetched by id alone
  - a state-changing request, including a GET that changes state or an HTMX partial with weaker
    checks than its page: CSRF, and the same permission as the page
  - user input: a validating form; no `ModelForm` that takes owner, role or site fields from POST
  - rendered user content: escaped, or its sanitiser named
  - a redirect target from input: `url_has_allowed_host_and_scheme`
  - a file upload: size, type and content checked; filename not user-controlled
  - an outbound call: credential from the environment
  - a role, permission or act-as parameter: checked server-side; no user id from the request acted
    on as that user
  - an ORM escape hatch: rejected unless the plan says why the ORM cannot do it
  - a user-controlled string used as a path, template name or format string
  - deserialisation of untrusted data, or a subprocess with user-derived arguments
  - a settings change that weakens a security default

  No hits is `status: ok` with "no new threats" and produces nothing. Rate limiting, audit logging,
  dependency reputation and severity scales are out.
- After the built-in dimensions, Step 6 reads `## Plan Review Hooks` and spawns one
  `sdd:sdd-worker` per bullet, briefed to read that file and follow it with the plan path, the spec
  path and the output path `.sdd-work/plan_review_<file-stem>.md`. A brief returning `blocked` with
  a need the command cannot satisfy from disk is recorded as "plan review hook <label> skipped:
  <need>" in the summary and the run continues.
- Findings: clear fixes are edited into the plan. Judgement calls become callouts at the relevant
  section: `> **Structure concern:**` and `> **Security concern:**` keep their existing text shape
  (options numbered, recommended first); other dimensions use `> **Review concern:**`. The
  end-of-run batch of requirement 2 puts each callout to the user; the answer replaces the callout
  with the decision, an unanswered one becomes `> **Assumed default:**`. No `add:` todo items.
- Step 8's `add:"QA|user|No QA needed…"` goes; an observation is not an item. Line 23's "DO NOT
  mention the … security review" sentence goes.

### 6. FLS plan review briefs (`claude_plugins/fls-dev/resources/`)

Both are worker briefs: an "Inputs from the caller" line (plan path, spec path, output path), the
check, the finding shape (`<plan step>: <trigger>: <fix or "judgement call">`), a single `Write`,
and the worker's `status:` footer. Neither runs a tier or spells a pytest command.

- `plan_review_structure.md`: the "Scan specification" block of `plan_structure_review.md` (parse
  `docs/app_structure.md`, classify each proposed cross-app edge). Its plugin-boundary paragraph is
  dropped; the `generic_plugin` dimension covers it. A missing `docs/app_structure.md` returns
  `status: blocked · needs: docs/app_structure.md`.
- `plan_review_fls_threats.md`: the FLS triggers only. A new model extends `SiteAwareModel` or says
  why not, and never sets `site_id` by hand; a query or view that bypasses the site-filtering
  manager states why; a new `FileField` or `ImageField` names its storage alias per the
  `file-storage` skill and keeps learner-identifying files out of public buckets; a registration
  form obeys the `registration` skill's field and `?next=` rules; consent reads and writes keep
  `LegalConsent` append-only; HTMX validation returns 422 and relies on the global CSRF header; an
  educator-side view uses the project's educator permission mechanism, included only if the
  implementer finds the skill or documented mechanism that defines it.

### 7. Per-batch review in `/sdd:implement_plan` (`claude_plugins/sdd/commands/implement_plan.md`)

After a batch's `[batch <id>]` commit and its Design check:

1. **Mechanic** (`sdd:sdd-mechanic`): writes the added lines of `git diff <batch-commit>^..HEAD`,
   with path and line, to `.sdd-work/batch_review_<id>_diff.md`; greps them for the SDD
   planning-noise patterns listed in the command (section signs; `spec`, `slice`, `batch`, `phase`
   followed by a number; `this spec`, `a later spec`; `QA bug`; `spec_dd/`; `N. spec.md`,
   `N. plan.md`, `N. frontend_qa.md`) and writes hits to `.sdd-work/batch_review_<id>_mechanic.md`.
2. **Worker** (`sdd:sdd-worker`): reads both files and the files named by `Comment standard` and
   `Test standard`; applies them as a closed checklist to added lines only; writes
   `.sdd-work/batch_review_<id>.md` with one line per finding, `path:line: <rule>: <what to
   change>`, and the status footer. Its brief says: no findings is the normal result; do not review
   security, performance, architecture, design, naming or style outside the two standards; a
   `TODO` or `@claude` comment is rewritten with the concrete detail, never deleted; do not run
   tests.
3. The command drops any finding whose `path:line` is not an added line, then spawns one fix batch
   (`general-purpose`, `sonnet`) with the findings, committing `[batch <id>] review fix <n>` and
   running `targeted`. The re-review is bounded to the fix commit and to the rules violated in the
   previous round. Cap: two fix batches. Leftovers go into the final summary and the run continues.
4. A blank `Comment standard` or `Test standard` skips that half and records "review skipped: no
   <key> hook". The scratch files are deleted by name when the batch's review ends.

Other changes in the same file:

- The implementer brief (line 52's paragraph) adds: read and follow the files named by `Comment
  standard` and `Test standard` before writing code or tests.
- Step 1 item 3 ("raise them with the user before starting") is deleted. A `blocked` batch still
  follows the recipe.
- Design check step 4: a miss that survives two fix batches no longer ends the run. The command
  records it, keeps the screenshots, adds `(user) Decide what to do about design miss: <miss>
  (screenshots: <paths>)` under the implementation section of `todo.md`, and continues.
- Resume scan: a `review fix` commit counts as its batch's commit, like `design fix`.
- Step 3 defines the final summary: per batch, Design check passed, skipped or the surviving
  misses with their `fixes` count; review findings, fix batches and leftovers; then the full-tier
  result and the success criteria.
- Nothing in the command spells a pytest invocation; tiers go through `run_test_tier.md`.

### 8. `/sdd:document` and hook mode (`claude_plugins/sdd/commands/document.md` and the hooked commands)

`document.md`: pre-step rebase; resolve `<spec-dir>` from the branch; read `## Documentation Hooks`;
for each bullet in order, read the file and follow it inline at depth 0 with `<spec-dir>`,
`<todo-path>` and `mode: hook`; record its status; a `failed` hook is reported and the next one
runs; after each hook, if the working tree has changes, commit them via `commit_and_push.md` with
`<summary>` the hook's label; then tick `Run `/sdd:document``, commit `run the documentation
hooks` staging `todo.md`, and report one line per hook. Its `allowed-tools` is the union of its
hooks' needs, including `mcp__playwright__*` and `mcp__plugin_ds_playwright__*`.

Hooked commands (`app_map.md`, `update_upgrade_notes.md`, `update_product_docs.md`,
`update_claude_plugin_fls_content.md`) open with "Inputs from the caller: `<spec-dir>`,
`<todo-path>`, and `mode: hook` when another command runs you inline. Without `mode: hook` you are
standalone." In hook mode Step 0 is skipped. The three fls-dev commands drop their todo tick step
in both modes, since no template line names them, and resolve the spec directory from the branch
instead of asking. `update_upgrade_notes.md` stays runnable alone for the post-review re-check.

## Success criteria

- A fresh `/sdd:start` writes a `todo.md` with 8 `(cmd)` and 5 `(user)` items in five sections.
- `/sdd:spec_from_idea` on an idea directory produces `1. spec.md`, six `research_*.md` files and
  two commits, and asks at most two question batches: one at the start, one at the end.
- `/sdd:plan_from_spec` on this repo spawns eleven review workers (nine dimensions, two briefs)
  and leaves no `> **Structure concern:**` or `> **Security concern:**` callout without a decision
  or an `> **Assumed default:**`.
- `/sdd:implement_plan` on a plan whose batch adds a comment containing `spec_dd/` produces a
  `[batch <id>] review fix 1` commit that removes it, and never a third fix commit for one batch.
- `/sdd:implement_plan` with a design miss after two fix batches ends `status: ok` with a
  `(user) Decide what to do about design miss` item in `todo.md`.
- `/sdd:document` on this repo runs four hooks in config order and reports four status lines, with
  one commit per hook that changed a file.
- `/sdd:finish_worktree`, `/sdd:commit_quickly` with no argument, and `/sdd:address_pr_review` run
  to completion without an `AskUserQuestion`.
- The grep and `claude plugin validate` checks under Testing pass.
