# Spec: HR attributes on learners

Spec 1 of 5 in the Registration rules effort (`spec_dd/1. next/roadmap.md`, "Registration rules").
Source: `idea.md` in this directory.

## Purpose

FLS has nowhere to record a learner's job title, department, location or start dates. The
registration rules in spec 2 need these facts as exact list entries plus dates. This spec adds them,
and an off-by-default switch per organisation, in a new optional app managed through the Django
admin. A project that leaves the app out of `INSTALLED_APPS` sees no change.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| `JobTitle`, `Department`, `Location` | coined | Per-organisation list entries a learner's attributes point at. No existing model uses these names. The glossary's use of "department" to describe an `Organisation` is reworded (see Documentation). |
| list entry | coined | An instance of any of those three models. Used in prose only. |
| `LearnerHRAttributes` | coined | The one-to-one row on `Learner` holding its three list entries and four start dates. |
| `OrganisationHRSettings` | coined | The one-to-one settings row on `Organisation`. Its only field, `registration_rules_enabled`, is the switch. |

## Out of scope

Each is its own spec or isn't planned:
- Registration rules, their evaluation, provenance and retraction (spec 2). Nothing reads
  `registration_rules_enabled` in this spec.
- Recommendations (spec 3), educator-interface screens (spec 4), CSV import (spec 5).
- SCIM or SSO sync, list hierarchies, merging entries, organisation-defined custom attributes, line
  managers, relative due dates and recertification.

## Decisions

1. **Every field is independent.** A start date may be set while its list entry is empty. FLS never
   infers, clears or compares dates. Future dates are allowed and nothing checks their order,
   because rehires and acquisitions produce real data any ordering rule would reject.
2. **No abstract base model.** The three list models declare their own fields and constraints.
   CLAUDE.md forbids abstract bases unless asked. Shared behaviour lives in one queryset class, one
   form mixin and one admin base class.
3. **Uniqueness is a database constraint, and the form reports it on `name`.** The constraint's
   expression is `Lower(Trim("name"))`. `ConstraintValidationFormMixin` can only key an error on
   `constraint.fields`, so for an expression constraint it puts the error in the non-field errors.
   A `clean_name()` on the form puts it on `name`, following `referral_tracking/forms.py`
   (`ReferralCodeForm.clean_code`).
4. **Pickers are plain selects narrowed in `formfield_for_foreignkey`**, not autocomplete. The
   autocomplete endpoint ignores an inline's queryset (see `ScopedLearnerAutocompleteSelect`'s
   docstring in `learner_management/admin.py`). `limit_choices_to` is not used either, because it
   would also reject a deactivated entry the learner already holds.
5. **List-entry foreign keys use `PROTECT`.** Django's stock admin delete page then refuses to delete
   an entry in use and lists the attributes rows that hold it. No custom delete handling is needed.
6. **Moving a learner to another organisation must clear their attributes in the same save.**
   `LearnerAdmin` lets staff change `Learner.organisation`. The inline formset re-points each
   attributes row at the edited `Learner` and validates it, so the cross-organisation check in
   `LearnerHRAttributes.clean()` refuses the save until the old organisation's entries are cleared.
   ORM callers changing `Learner.organisation` are not policed. No such path exists today.

## Requirements

### App scaffold (`freedom_ls/hr_attributes/`)

- `apps.py`: `HrAttributesConfig` with `name="freedom_ls.hr_attributes"`,
  `label="freedom_ls_hr_attributes"` and `verbose_name="HR attributes"`, per
  `docs/app_conventions.md`.
- No `urls.py`. The app has no views.
- `config/settings_base.py` `INSTALLED_APPS` gains `"freedom_ls.hr_attributes"` after
  `"freedom_ls.learner_management"`.
- Runtime dependencies: `learner_management`, `organisations` and `site_aware_models`. No other app
  imports `hr_attributes`. Core code that ever needs it in future uses `apps.is_installed()` or
  `apps.get_model()`, as `config/urls.py` does for `blog`.
- `learner_management` and `organisations` gain no migrations, fields or code. With the app absent,
  their admins are as they are today.
- `tests/conftest.py` gates collection with `app_not_installed("freedom_ls.hr_attributes")` and
  `collect_ignore_glob`, copying `freedom_ls/course_applications/tests/conftest.py`.

### Models (`freedom_ls/hr_attributes/models.py`)

**`JobTitle`, `Department`, `Location`**, each a `SiteAwareModel` with:

| Field | Definition |
| --- | --- |
| `organisation` | `ForeignKey("freedom_ls_organisations.Organisation", on_delete=PROTECT, related_name=<"job_titles" \| "departments" \| "locations">)` |
| `name` | `CharField(max_length=200)` |
| `is_active` | `BooleanField(default=True)` |

- Constraint, one per model:
  ```python
  models.UniqueConstraint(
      Lower(Trim("name")), "site", "organisation",
      name="unique_job_title_name_per_organisation",  # department_ / location_ for the others
  )
  ```
  `site` is spelled in the constraint per `docs/app_conventions.md`.
- `clean()` strips surrounding whitespace from `name` and keeps its case as typed.
- `Meta.ordering = ["name"]`. `__str__` returns `name`, with " (inactive)" appended when
  `is_active` is false, so the Learner admin shows a held deactivated entry as such.
- A shared `ListEntryQuerySet`, exposed through a `ListEntryManager(SiteAwareManager)` with a
  hand-written pass-through, as `ArticleManager` in `content_engine/models/articles.py` does, so it
  keeps site filtering. It has one method:
  ```python
  def for_picker(self, organisation_id: UUID, current_pk: UUID | None) -> Self:
      """Active entries of the organisation, plus the currently held entry."""
  ```
  It returns `filter(organisation_id=organisation_id).filter(Q(is_active=True) | Q(pk=current_pk))`.
  Spec 4 reuses it.

**`LearnerHRAttributes`**, a `SiteAwareModel`:

| Field | Definition |
| --- | --- |
| `learner` | `OneToOneField("freedom_ls_learner_management.Learner", on_delete=CASCADE, related_name="hr_attributes")` |
| `job_title` | `ForeignKey(JobTitle, on_delete=PROTECT, null=True, blank=True, related_name="learner_hr_attributes")` |
| `department` | same, to `Department` |
| `location` | same, to `Location` |
| `organisation_start_date` | `DateField(null=True, blank=True)`. The hire date (Entra `employeeHireDate`). |
| `job_title_start_date` | `DateField(null=True, blank=True)` |
| `department_start_date` | `DateField(null=True, blank=True)` |
| `location_start_date` | `DateField(null=True, blank=True)` |

- `CASCADE` from `learner` keeps user erasure working: deleting a `User` cascades through `Learner`.
- `clean()` refuses a list entry from an organisation other than `learner.organisation`. The error
  is keyed on the offending field ("Choose a job title from this learner's organisation.").
  `clean()` returns early when `learner` is unset, catching `ObjectDoesNotExist` the way
  `_relations_are_set` in `learner_management/models.py` does. The new app does not import that
  private helper.
- `clean()` does not refuse a deactivated entry, so a learner who holds one can still be saved.
- `__str__` returns `f"HR attributes for {learner}"`.
- Callers outside forms must call `full_clean()` before `save()`. Factories are the existing
  exception.

**`OrganisationHRSettings`**, a `SiteAwareModel`:

| Field | Definition |
| --- | --- |
| `organisation` | `OneToOneField("freedom_ls_organisations.Organisation", on_delete=CASCADE, related_name="hr_settings")` |
| `registration_rules_enabled` | `BooleanField(default=False)` |

No row means off. Spec 2 reads it as
`OrganisationHRSettings.objects.filter(organisation=org, registration_rules_enabled=True).exists()`.

One `0001_initial` migration creates all five tables. Its dependencies are the latest
`freedom_ls_learner_management` and `freedom_ls_organisations` migrations at implementation time.

### Forms (`freedom_ls/hr_attributes/forms.py`)

- `ListEntryFormMixin` adds `clean_name()`. It strips the value, then raises
  `ValidationError("An entry with this name already exists in this organisation.")` on `name`
  when another row of the same model has the same organisation and the same `Lower(Trim(name))`,
  excluding the instance itself.
- `JobTitleForm`, `DepartmentForm` and `LocationForm` each combine `ListEntryFormMixin` with
  `ConstraintValidationFormMixin` (`freedom_ls/site_aware_models/forms.py`).

### Admin (`freedom_ls/hr_attributes/admin.py`)

**List admins.** One `SiteAwareModelAdmin` subclass per list model, sharing behaviour through one
`ListEntryAdmin` class in this module:
- `list_display = ["name", "organisation", "is_active"]`, `list_filter = ["organisation", "is_active"]`,
  `search_fields = ["name"]`, `list_select_related = ["organisation"]`.
- `form` is the model's form from `forms.py`, with fields `organisation`, `name`, `is_active` in that
  order, so `organisation` is cleaned before `clean_name()` reads it. `organisation` uses
  autocomplete, as on `LearnerAdmin`.
- Actions `deactivate_selected` and `activate_selected` set `is_active` with one `update()` and
  report the count through `message_user`. Stock delete stays. `PROTECT` makes it refuse an entry
  in use and allow an unused one.

**Learner inline.** `LearnerHRAttributesInline`, an unfold `StackedInline` on `LearnerHRAttributes`:
- `max_num = 1`, `can_delete = False`. Fields: the three list entries, then the four dates.
- `formfield_for_foreignkey` narrows `job_title`, `department` and `location` to
  `for_picker(learner.organisation_id, current_pk)`. The learner comes from
  `request.resolver_match.kwargs["object_id"]`, following `CohortMembershipInline.formfield_for_foreignkey`
  (`learner_management/admin.py`). On a missing or unparseable id it returns an empty queryset.
- Wired in at import time:
  `LearnerAdmin.inlines = [*LearnerAdmin.inlines, LearnerHRAttributesInline]`, as
  `learner_progress/admin.py` does. `LearnerAdmin.get_inlines` already hides it on the add page.
- An untouched inline creates no row.

**Organisation inline.** `OrganisationHRSettingsInline`, an unfold `StackedInline` on
`OrganisationHRSettings`, with `max_num = 1`, `can_delete = False` and the field
`registration_rules_enabled`. Wired in with
`OrganisationAdmin.inlines = [*OrganisationAdmin.inlines, OrganisationHRSettingsInline]`, as
`learner_management/admin.py` does. `OrganisationAdmin.get_inlines` already hides it on the add page.

`LearnerHRAttributes` and `OrganisationHRSettings` get no standalone admin. Because they are not
registered, the User delete confirmation never asks for their permission, so
`USER_ERASURE_CASCADE_MODELS` needs no entry.

### Factories (`freedom_ls/hr_attributes/factories.py`)

`JobTitleFactory`, `DepartmentFactory`, `LocationFactory` (`SiteAwareFactory`, `organisation =
SubFactory(OrganisationFactory)`, sequenced `name`), `LearnerHRAttributesFactory` and
`OrganisationHRSettingsFactory`. Factories never call `full_clean()`, so
`LearnerHRAttributesFactory`'s list-entry subfactories default their organisation to
`SelfAttribute("..learner.organisation")`, as `CohortMembershipFactory` does. Its dates default to
`None`.

Run `/ds:app_map` once the app exists and commit the regenerated `docs/app_structure.md` and
`test_organisation/import_contracts.toml`. The `app-map-fresh` and `lint-imports` pre-commit hooks

## Testing

Test files mirror modules: `hr_attributes/tests/test_models.py`, `test_forms.py`, `test_admin.py`.
Use `mock_site_context` and `staff_client` from `freedom_ls/conftest.py`.

Models:
- Two entries in one organisation whose names differ only by case or surrounding whitespace raise
  `IntegrityError`. Two organisations may share a name. One case per list model.
- `full_clean()` strips surrounding whitespace from `name` and keeps its case.
- `LearnerHRAttributes.full_clean()` refuses an entry from another organisation, with the error on
  that field, for each of the three fields.
- `full_clean()` accepts a deactivated entry, a start date with no entry, a future date and dates
  in any order.
- Deleting an entry held by an attributes row raises `ProtectedError`. Deleting an unused entry
  succeeds.
- Deleting a learner's `User` deletes their `LearnerHRAttributes`.
- `for_picker` returns the organisation's active entries plus the held inactive one, and nothing
  from another organisation.

Forms:
- A duplicate name, differing in case or whitespace, puts the error on `name`. Editing an entry
  without changing its name is valid.

Admin:
- Each list changelist loads and filters by organisation and `is_active`. `deactivate_selected` and
  `activate_selected` flip `is_active`.
- The delete view refuses an entry in use and deletes an unused one.
- The Learner change page has the attributes inline and the add page has no inlines.
- The inline pickers offer the learner's organisation's active entries plus the held deactivated
  one, never another organisation's entries.
- Posting the change page saves the attributes. Posting it untouched creates no row.
- Changing the learner's organisation while attributes hold the old organisation's entries is
  refused. Clearing the entries in the same post lets it save.
- The Organisation change page has the settings inline. Ticking the switch creates the row with
  `registration_rules_enabled=True`. An organisation with no row reads as off.

## Open questions

Each has a default the implementation takes unless the user overrules it.

- **Demo data.** The default seeds nothing, so the demo shows the admin screens with empty lists.
  The QA step creates its own data through `fls-dev:qa-data-helper`.
- **Internal whitespace.** "Human  Resources" and "Human Resources" count as different names by
  default. Collapsing inner whitespace would mean normalising in `clean()` beyond what the
  constraint enforces.
