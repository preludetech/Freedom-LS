## 0. Headline findings and corrections

1. **Removing `django-ninja` also removes `pydantic` unless it is declared.** `pydantic` is not in `pyproject.toml` dependencies (lines 7-41). In `uv.lock` its only dependent is `django-ninja` (`uv.lock:787-793`). Live code imports it directly: `freedom_ls/content_base/schema.py`, `freedom_ls/content_engine/schema.py`, `freedom_ls/content_engine/validate.py`, `freedom_ls/form_engine/schema.py`, `claude_plugins/fls-content/validate/{schema,validate}.py` (and the tests). The spec must add `pydantic` as an explicit dependency in the same change that drops ninja, or content loading breaks. `uv.lock` pins 2.12.5.
2. **`accounts.User` already has `created_at` and `updated_at`.** `User(SiteAwareModelBase, TimestampedModel, AbstractBaseUser, PermissionsMixin)` (`freedom_ls/accounts/models.py:78`); both columns exist in `accounts/migrations/0001_initial.py:25-26`. No column migration is needed. A **migration for an index is** needed: `User.Meta.indexes` holds only `Upper("email")` (`models.py:96-98`), and `accounts` migrations stop at `0003_user_email_upper_index.py`. `User` is in the conformance `TIMESTAMPED_MODELS` list (`freedom_ls/contrib/conformance/tests/test_timestamped_models.py:30`).
3. **`updated_at` is an unreliable changed-since signal for users.** It is `auto_now`. Django only writes it when the field is part of the save, so `save(update_fields=[...])` without it leaves it alone. Django's login signal handler saves `last_login` that way, so a login does not move `updated_at`. `UserFactory` also uses `save(update_fields=["password"])` (`accounts/factories.py:35`). `email_verified` is not a User field at all: it is an `Exists` over allauth `EmailAddress` (`accounts/resources.py:50-58`), and flipping `EmailAddress.verified` never touches the User row. So `updated_since` on users misses logins and email verification. State this in the docs; changing the signal is not in scope.
4. **User pk is a `BigAutoField` integer, not a UUID.** `DEFAULT_AUTO_FIELD = BigAutoField` (`config/settings_base.py:322`), and the comment at `accounts/models.py:79-81` confirms. The idea's "UUIDs as strings" applies to `SiteAwareModel` children, not to users. `(updated_at, id)` ordering works for both pk types.
5. **The app label of the user model is `freedom_ls_accounts`** (`AUTH_USER_MODEL = "freedom_ls_accounts.User"`, `settings_base.py:324`; `accounts/apps.py:7`). Every FLS app uses `label = "freedom_ls_<app>"` and a sentence-case `verbose_name` (`docs/app_conventions.md:10-57`, enforced by `freedom_ls/contrib/conformance/tests/test_app_labels.py`). Table names, check ids and TIMESTAMPED_MODELS keys use that form.
6. **`get_cached_site` raises `Site.DoesNotExist` for an allowed host that has no Site row.** It only catches `DisallowedHost` (`site_aware_models/models.py:62-72`). With `SITE_ID` unset (it is never set; `learner_management/capabilities.py:60`), `get_current_site` goes to `Site.objects.get_current(request)`, which raises `Site.DoesNotExist` for an unknown but allowed host (production allows `localhost` and `127.0.0.1` beside `HOST_DOMAIN`, `settings_prod.py:15`). The research file's "UnknownSite guard" is therefore not enough: the authenticator must also catch `Site.DoesNotExist` (and `SiteResolutionError`, `ImproperlyConfigured`) and answer the generic 401, not 500.
7. **DRF `Request` hazard with the site cache.** `get_cached_site` caches with `setattr(request, "_cached_site", ...)` (`models.py:82`). Passing a DRF `Request` would set it on the wrapper, while `SiteAwareManager` reads the thread-local Django `HttpRequest` (`models.py:121`). Pass `request._request`, or the HttpRequest from the thread local, so there is one cache and one answer.
8. **Dev pins the site, which defeats the wrong-host check.** `config/settings_dev.py:159` sets `FORCE_SITE_NAME = "DemoDev"`, so in dev every host resolves to DemoDev (`models.py:51-61`). The wrong-host rejection cannot be demonstrated by hand in the dev project. Tests reset it (`freedom_ls/conftest.py:44-47`).
9. **`mock_site_context` makes tests host-blind.** `site_context` patches `get_current_site` to always return the fixture site (`freedom_ls/tests/site_context.py:35-47`). Tests of "key used on another site's host" and "unresolvable site" must not use it. Build real `Site` rows with `SiteFactory(domain=...)`, set `settings.ALLOWED_HOSTS`, and send `headers={"host": ...}` / `HTTP_HOST` (precedent: `base/tests/invariants/test_error_pages.py:113`, `site_aware_models/tests/test_context_processors.py:73`). The Django test client's default host is `testserver`.
10. **The shared cache for throttling is a database cache in production and a per-process cache elsewhere.** See section 8.
11. **docs/product is not the place for the API page.** `docs/product/README.md:5` says it is "not developer or API reference", and `docs/build_product_docx.py:296-304` refuses to build unless every `docs/product/*.md` is in `DOC_ORDER` (that list already omits `notifications`, `messaging`, `hr-attributes`, `registration-rules`, `referral-codes`, `signup-attribution`, so it is already stale). Put the API reference page in `docs/` outside `product/` (for example `docs/api.md`) and update `docs/product/security-and-data-handling.md` for the security claims (section 11).

## 1. Site resolution

- Middleware: `freedom_ls.site_aware_models.middleware.CurrentSiteMiddleware` (`middleware.py:10-36`) stores the Django request in `_thread_locals.request` for the request, restoring the outer one after. It sits in `MIDDLEWARE` after `AuthenticationMiddleware` and before `AttributionCaptureMiddleware` (`settings_base.py:176`). It runs for API paths too, and DRF views run inside it, so the thread local is the real request throughout authentication and the viewset.
- `get_cached_site(request)` (`models.py:37-83`): cached attribute `_cached_site` on the request; else `config.FORCE_SITE_NAME` (a `Site` by name); else `get_current_site(request)`; `DisallowedHost` becomes `UnknownSite` (a `RequestSite` subclass, not a `Site`; `models.py:21-30`); no request and no pin raises `SiteResolutionError` (`models.py:33`, `74-79`). `Site.domain` match is case-insensitive and falls back to the host without its port; Django's process-global `SITE_CACHE` caches by host.
- Note the reach of `DisallowedHost`: `CommonMiddleware` calls `request.get_host()` first, so an unallowed host normally gets Django's 400 before DRF runs. The `UnknownSite` path is reached by the 400 handler's context processors, not by the API. The realistic "unresolvable" cases are an allowed host with no Site row (item 6) and a pinned `FORCE_SITE_NAME` that matches no row (`models.py:56-61` raises `Site.DoesNotExist`).
- `SiteAwareManager.get_queryset` (`models.py:118-129`) filters `site=<host site>` only when a thread-local request exists **and** the site is a `Site`. With no request it returns every site's rows; with `UnknownSite` it also returns every row (fails open).
- `SiteAwareModelBase.save/full_clean` fill `site` from the thread-local request when unset (`models.py:140-158`). `site_of(obj)` (`:161`). `_base_manager` always crosses sites (`site_aware_models/tests/test_models.py:159-168`).
- `User` uses its own `UserManager` with the same filter (`accounts/models.py:26-34`), so `User.objects` is host-scoped. The users endpoint should not rely on that alone: filter explicitly on `site=<key.site>` after the authenticator has proved `key.site == host site`. Keep the key lookup explicit as well (compare `key.site_id` to `site.pk` after `isinstance(site, Site)`), rather than trusting the default manager's host filter.
- Request-less callers: `get_cached_site(None)` only works with `FORCE_SITE_NAME`. API code always has a request, so this only bites a management command or task that reuses serializers.

## 5. App settings, config.py, and enabling the feature

- Pattern: `freedom_ls/base/app_settings.py` `AppSettings` with `declared_settings = {NAME: Setting(default, required)}`; `config.NAME` reads Django settings first (`None`/`""` count as unset), then the default, deep-copied (`app_settings.py:18-47`). Examples: `audit_log/config.py`, `webhooks/config.py`, `health/config.py`, `comms/config.py` (`NOTIFICATIONS_ENABLED`, `MESSAGING_ENABLED`, default False). Required settings get `<app_label>.E001` system checks via `required_settings_errors(config, app_label)` (`app_settings.py:62-75`).
- Gotcha: `__getattr__` treats `None` and `""` as unset, but `0` and `False` are returned as set; however a list/dict setting set to an empty value falls back to the default only for `None`/`""` (an explicit `{}`/`[]` is returned as given, since `{} not in (None, "")` is True). Throttle-rate dicts are fine.
- Toggling features on a concrete project today uses two mechanisms: (a) INSTALLED_APPS membership plus a conditional URL include, e.g. blog (`config/urls.py:51-61`, `apps.is_installed("freedom_ls.blog")`); (b) a boolean app setting, e.g. `MESSAGING_ENABLED` declared in `settings_base.py:520` and read through `comms/config.py`. `config/urls.py:63-91` is the in-repo project URLconf; concrete projects write their own and include FLS URLs themselves, so the API app ships `freedom_ls/<app>/urls.py` with `app_name`. Note `registration_rules/apps.py:18-21` checks that its prerequisite apps are installed.
- Recommended shape (for the spec to decide): enabling = adding the app to `INSTALLED_APPS` and including its urls; no separate `API_ENABLED` flag is needed, or if a flag is wanted it follows the `MESSAGING_ENABLED` pattern. Declare throttle rates, page size and max page size as `Setting`s in the new app's `config.py` and feed DRF from them.
- Settings layout: `config/settings_base.py` holds `INSTALLED_APPS` (74-152), no `REST_FRAMEWORK`, `SPECTACULAR_SETTINGS`, `CACHES` or `LOGGING`. `settings_dev.py` imports base and appends dev-only apps; `settings_prod.py` sets `CACHES`, `LOGGING`, `ALLOWED_HOSTS`. A new app goes in the `# CUSTOM APPS` block of `INSTALLED_APPS`, plus `rest_framework`, `django_filters` (needed only if its templates or `FilterSet` registration are used; the `django_filters.*` mypy override already exists at `pyproject.toml:359`) and `drf_spectacular`. DRF settings live in `config/settings_base.py`, but values a concrete project must be able to change should resolve through the app's `config.py`, since concrete projects have their own settings files.

## 6. Pagination ordering and ties

- Existing ordering conventions: `AuditLogEntry.Meta.ordering = ("-created_at", "-id")` (`audit_log/models.py:114`); `UserAdmin.ordering = ["email"]`.
- DRF `CursorPagination` accepts a tuple like `("updated_at", "id")`, but, per DRF's implementation, the cursor position records only the value of the first ordering field plus an offset; later fields only order rows within equal first-field values. Rows sharing one `updated_at` are paged by offset, and DRF refuses an offset beyond its cutoff (1000) with "invalid cursor". Treat as: verify against the installed DRF version in the spec's test (a test with more than a page of identical `updated_at`). Sources of identical values: `bulk_create`, imports, test factories using `time_machine`, and any sibling spec that adds `updated_at` with a migration default (siblings 4 and 5, roadmap lines 681-683). The spec should pin the behaviour (page size versus tie group size) and test a tie group larger than one page.
- Rows edited mid-crawl move to the end and reappear (at-least-once); say so in the docs. Deletions are invisible.
- Index to support it: `(site, updated_at, id)` on `User` (section 2).

## 8. Caching, throttling, logging

- No `CACHES` in `settings_base.py` or `settings_dev.py`, so dev and the test suite use Django's default `LocMemCache` (per process; separate for each gunicorn worker or xdist worker). Production sets `CACHES = fls_defaults.DATABASE_CACHES` (`settings_prod.py:89`): `DatabaseCache`, table `django_cache_table`, `MAX_ENTRIES = 50000` (`deployment/settings_defaults.py:86-92`). The table is not made by a migration; `createcachetable` is a deploy step, enforced by check `freedom_ls_deployment.E005` (`deployment/checks.py:335-382`).
- Consequences for throttling: DRF throttles use the default cache alias. In production the DB cache is shared across processes, so a per-key rate holds across workers, but each throttle check is DB traffic (a read plus a write per API call) on the same table that backs allauth rate limits and the referral-hit cap. The cull strategy deletes expired rows and then a third of the rest ordered by `cache_key`, blind to importance (comment at `settings_defaults.py:76-85`). A per-key counter is evictable under pressure, and a scripted crawl produces constant writes. The spec should say: rates hold across processes only where `CACHES` is shared; local-memory caches multiply the effective rate by the worker count; the docs and a system check/README line should state it. A named throttle cache alias is possible but would add a `CACHES` entry every concrete project must define.
- Tests: no autouse cache clear exists. `referral_tracking/tests/conftest.py:16-22` shows the pattern (`cache.clear()` before and after). The API tests must do the same or throttle counters leak between tests (LocMemCache lives for the process). `pytest-randomly` is installed, so order dependence shows up.
- Throttle keying: per key id, not IP (idea). Failed-auth requests have no key to key on; DRF's throttles run after authentication, so unauthenticated floods are not throttled by default. Decide whether to add a per-IP throttle for failed auth (`TRUSTED_PROXY_IP_HEADER` / `accounts.utils.get_client_ip` exists for the proxy-aware address, `settings_base.py:362,372`). `axes` is installed but only guards login (signals), not API auth.
- Logging: production `LOGGING = build_logging_config()` (`settings_defaults.py:141-250`): `console` stream only; loggers `django`, `django.request` (ERROR), `django.security`, `django.db.backends` (WARNING), `freedom_ls` (INFO); simple format `{levelname} {asctime} {message}`. No logger writes request headers, and there is no `AdminEmailHandler`. Django's debug error page cleanses `META` entries matching its sensitive-name regex (it contains `AUTH`/`KEY`/`TOKEN`), so `HTTP_AUTHORIZATION` is hidden; confirm in a test rather than assume. Outside the repo, a reverse proxy or gunicorn access log is the deployment's concern: the query string is where the key must never be (idea), so access logs stay safe only because the key is header-only. Sentry: `deployment/sentry.py:12-18` calls `sentry_sdk.init(..., send_default_pii=config.SENTRY_SEND_DEFAULT_PII)` (default False, `settings_base.py:674`) with no custom `before_send`; the Django integration is expected to drop `Authorization` and `Cookie` headers when PII is off, but the docs say "automated redaction ... not yet built" (`security-and-data-handling.md:158`). The spec should add a test that a captured event with an Authorization header has it scrubbed, or add an explicit scrub, not rely on the default.
- Code must not add logging (CLAUDE.md: "Don't add logging unless asked"), so the "never logged" requirement is met by not logging, plus not echoing the header in error bodies or exception messages.

## 9. Middleware and HTTP behaviour that touches `/api/`

Order (`settings_base.py:162-182`): Security, CSP, WhiteNoise, Session, Common, RemoveSlash, Csrf, Auth, Messages, HtmxMessages, XFrame, **CurrentSite**, AttributionCapture, allauth Account, RegistrationCompletion, Axes.

- `CommonMiddleware` with `APPEND_SLASH` (default True): `GET /api/v1/users` redirects to `/api/v1/users/` (301). httpx does not follow redirects by default, so the example must use the slashed URL. Router paths are kebab-case with trailing slash (`DefaultRouter`); `RemoveSlashMiddleware` only strips a slash on a 404 for a slashed path whose slashless form resolves (`base/middleware.py:91-139`), so it will not interfere with slashed API routes.
- `RegistrationCompletionMiddleware` redirects authenticated **session** users with incomplete registration forms (`accounts/middleware.py:79-127`); it keys on `request.user.is_authenticated` from Django's session auth, so a bearer-only request (no session cookie) is never redirected. A browser holding a session that sends a bearer header could be redirected before DRF runs; irrelevant to scripts, but `api` view names are not in `EXEMPT_URL_NAMES` (`:29-46`). A call with a stale session cookie is the only way to see it.
- `AttributionCaptureMiddleware` only acts on GET requests carrying tracked query parameters (`referral_tracking/middleware.py:50-53`); API GETs with `utm_*`/`gclid`-style params could mint cookies and tally first touches. The users filter parameters (`updated_since`, `cursor`, `page_size`) are not tracked parameters; confirm `has_tracked_params` against any future parameter names.
- CSRF: `APIView.as_view` is `csrf_exempt`; with token-only authentication no CSRF enforcement applies. Do not add `SessionAuthentication`.
- HTTPS: production sets `SECURE_SSL_REDIRECT = True` with exemption only for `^health/` (`settings_prod.py:21,27`, `settings_defaults.py:63`) and `SECURE_PROXY_SSL_HEADER` (`settings_defaults.py:31`). A plain-http request is answered with a 301 before any view, but the client has already sent the key. httpx keeps the Authorization header on a same-host http-to-https redirect, so the docs' "treat as compromised" rule stands. The cursor `next` link is built from the request, so under the proxy header it is https in production and http in dev.
- Response headers: CSP report-only and `X-Frame-Options` apply to JSON responses harmlessly; set `Cache-Control: private, no-store` on API responses (user PII), as the report downloads do (`security-and-data-handling.md:91`).

- Existing apps are listed in `INSTALLED_APPS` (`settings_base.py:104-152`); `health` is a good small template (`apps.py`, `config.py`, `urls.py` with `app_name = "health"`, `tests/`). Every new app needs `label = "freedom_ls_<name>"`, `verbose_name`, `default_auto_field` if it defines models (`docs/app_conventions.md:10-97`). The conformance suite (`freedom_ls/contrib/conformance/`) checks labels, headings and timestamped models for downstream projects; `ApiKey` (with `created_at`) would need an explicit yes/no in `TIMESTAMPED_MODELS` if it uses `TimestampedModel`.
- Import-linter here is **generated and test-only**: `test_organisation/import_contracts.toml` is "Generated by /ds:app_map. Do not hand-edit". Each app gets a `forbidden` contract saying its `factories` and `tests` import only its own runtime dependencies (`source_modules = [app.factories, app.tests]`, `forbidden_modules` = every other app not in its runtime-deps set; `allow_indirect_imports = true`). It does not constrain runtime imports; the allowed runtime graph is `docs/app_structure.md` (generated, "treat as the source of truth", new cross-app edges "called out and approved before code is written", `app_structure.md:5-9`). Three pre-commit/CI hooks enforce it: `app-map-fresh`, `lint-imports`, `test-mirroring` (`docs/app_conventions.md:106-108`). Baselines only shrink (`:117-122`). Runtime edges no import shows go in `test_organisation/declared_edges.toml` with a reason (today only `base -> learner_management`).
- The `api` app (name to be chosen; avoid `api_v1`, keep room for `v2`) would import at runtime: `accounts` (User, EmailAddress annotation), `audit_log`, `site_aware_models`, `base` (`app_settings`), and, depending on the ownership decision below, each resource's app. Its tests would import `accounts.factories` (the user-model app's factories are an allowed "allowance" in baselines, e.g. `import_contracts.toml:15`). After adding the app, `/ds:app_map` regenerates `docs/app_structure.md` and `import_contracts.toml`; root_packages list (`import_contracts.toml:4`) gains the app.
- The open question "where each resource's serializer and viewset live" has direct linter consequences:
  - **All in the API app:** `api --> accounts, course_applications, referral_tracking, learner_management, learner_progress, course_interest, form_engine, ...` (one fan-in node; no resource app depends on `api`; the API app's tests may only use factories of its runtime deps, which is satisfied because they are runtime deps). Simple, one place for scopes, router and docs, no cycles; the cost is that the API app imports most of the product, and sibling specs 2-6 all edit the same `serializers.py`/`filters.py`/`urls.py` (the roadmap already warns of merge conflicts at `roadmap.md:679-680`).
  - **In each resource app, registered with the API router:** each resource app gains `--> api` (for the base viewset, pagination, scope permission), so the shared base would sit in a low-level app that every resource app imports, and `api` itself must discover routers without importing resource apps (for example a registry the resource apps' `ready()` or `urls.py` write into). `accounts --> api` while `api --> audit_log --> accounts` would be a cycle at the app level (`audit_log --> accounts` exists, `app_structure.md:58`); runtime imports inside functions or a split between `api_core` (base, no audit) and the issuance admin would avoid it. This is the harder path and the one most likely to trip `lint-imports`.
  - Middle path: a base package that holds only key model, authentication, scopes, pagination, filters and throttling (depends on `site_aware_models`, `base`, `audit_log` for the admin), and a thin API app holding the router, serializers and viewsets per resource. Either way the spec must say which, and sibling specs inherit it.
- Spec constraint from CLAUDE.md (Plugins section): nothing FLS-specific goes into `claude_plugins/django-stack` or `claude_plugins/sdd`; any new testing guidance goes into `claude_plugins/fls-dev` only.

## 11. Admin base classes, issue/revoke UI, docs targets

- `SiteAwareModelAdmin(ModelAdmin from unfold)` with `exclude = ["site"]` and a CSS media file (`site_aware_models/admin.py:25-31`). `site` is filled by `_set_site_from_request` on save from the admin request host (`models.py:148-158`), so a key issued while on host A is bound to site A. Admin changelists use the site-filtered default manager, so each site sees only its own keys. With `FORCE_SITE_NAME` set (dev) every key binds to DemoDev.
- Unique-per-site constraints must be spelled `fields=["site", ...]` and the form must use `ConstraintValidationFormMixin` (`docs/app_conventions.md:69-85`; `site_aware_models/forms.py`; example `SiteTimeZoneConfigAdminForm`, `admin.py:77-89`).
- Webhook secrets show the existing masked-value pattern: `readonly_fields = ["masked_value", ...]` returning `"••••••••" + last 4` (`webhooks/admin.py:270-281`); the secret is auto-generated in `save` and create-form exclusion is handled in `get_fieldsets` (`:77-98`). There is no existing show-once-after-create screen to copy.
- **Show-once hazard:** `MESSAGE_STORAGE` is not set, so Django's default `FallbackStorage` applies (cookie first, then session). Putting the full key in `messages.success(...)` would write it into the signed (not encrypted) messages cookie or the session. Prefer a one-off response from the admin add view (render a page with the key once; `admin_page_context(request, model_admin, title)` at `site_aware_models/admin.py:92-105` builds an admin-shell context) or stash it on the response only. Also keep it out of `__str__`, `list_display`, `search_fields`, and the audit `details`.
- Revoke: an admin action and a change-form button; no hard delete from the UI (or delete allowed but audited; the audit log is append-only, `audit_log/models.py:35-70`). `has_delete_permission`/`has_change_permission` are the existing levers (`accounts/admin.py:94-101`). The key hash and prefix are read-only; scopes are editable only at issue, or via a new key (spec decision).
- Hashing: keys are high-entropy random strings, so a fast keyed digest (SHA-256 or HMAC with `SECRET_KEY`, constant-time compare via `django.utils.crypto`) is appropriate and a prefix column for lookup; Django's `PASSWORD_HASHERS` are Argon2/PBKDF2 (`settings_base.py:232-237`), which cost tens of ms per request and are the wrong tool for a per-request bearer. This refines `research_api_foundation.md` section 2 ("argon2/SHA-256").
- DRF authentication class notes: define `authenticate_header()` returning `Bearer`, otherwise DRF answers authentication failure with 403 instead of the required 401; use a principal object with `is_authenticated = True` rather than `AnonymousUser` (so `IsAuthenticated`-style checks work) and a scope permission class returning 403 for a missing scope.
- Docs layout: `docs/` holds `app_conventions.md`, `app_structure.md` (generated), `deployment-security-checklist.md`, `build_product_docx.py`, `product/*.md`. No existing API docs. New API page: `docs/api.md` (or `docs/api/…`), with the httpx example (`httpx` is already a dependency; the example runs outside FLS). Link it from `docs/product/README.md` only if listed under a non-docx-built table, because of the `DOC_ORDER` rule above.
- `docs/product/security-and-data-handling.md` (last updated 2026-10-30, `:3`) sections to touch: Summary bullets (`:7-23`); Runtime Application Security (new "API access (built)" subsection near "Multi-site data isolation", `:73`); Personal Data Collected (`:115-130`: API key records, `last_used_at`, and that the users endpoint exposes the same columns as the admin export plus `updated_at`); Audit Log (`:172-180`: add API key issue and revoke); Retention (`:202-204`: `last_used_at` retained; revoked keys retained); "Encryption at rest" (`:140-146`: keys are stored as a digest, not Fernet); Error Tracking (`:154-158`: Authorization header scrubbing). Also touch `docs/product/multi-tenancy-and-isolation.md` (key site binding) and `docs/product/admin-interface.md`; bump the "Last updated" line in the files edited.
