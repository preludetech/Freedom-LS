# Spec: panel framework form actions accept file uploads

Spec 1 of 3 in the "Account area on panels" effort (`spec_dd/1. next/roadmap.md`). Inputs: `idea.md`,
`answers.md` and the `research_*.md` files beside this spec.

## Purpose

A `FormPanelAction` builds its form from `request.POST` only, and neither the dialog form nor the
inline form posts multipart. So a panel form cannot carry a file. The account area's picture panel
(`learner-profile-use-panels-framework-3-account-page`) and certificate uploads
(`learner-public-profile-4-certificates`) both need one. This spec adds file upload to the
framework once, for `FormPanelAction` and its subclasses, in the dialog shape and the inline shape.

## Scope

In:

- Files reach the form of every `FormPanelAction`, `EditAction` and `CreateInstanceAction`.
- Multipart encoding on the dialog form and on the inline form, only for forms with a file field.
- A framework inline form partial, which the two existing FLS inline forms switch to with no
  visible change.
- A framework file widget: shows the stored file's basename, a Remove checkbox when the field is
  optional, and the picker.
- After a 422, a message on the file field telling the user to choose the file again.
- "Uploading…" on Save while a file form is in flight.
- An error message in the form when a panel form's request fails without a swappable response
  (413, other 4xx/5xx, network failure, timeout). This covers every panel form, with or without a
  file.
- Picking a file counts as an unsaved change for the dialog's discard prompt.
- A static example on the component reference page, and framework tests.

Out:

- Any consumer panel, including the picture panel, and any change to `accounts/`.
- Storage, size limits and file-type checks: these stay in the consumer's form and model.
- Keeping a chosen file across a 422 (server stash or `hx-preserve`).
- Progress bars, drag-and-drop, multiple files per field, previews, cropping, resizing.
- A link to the stored file. A consumer that wants one adds it in its own panel.
- File fields in a form that also uses `refresh_on_change`: the refresh is a GET and carries no
  file. Not supported, and not guarded.
- A live-region announcement of the busy state.

## Decisions

- **Multipart is decided by `form.is_multipart()`.** This is Django's own test, so forms without a
  file field render exactly as today.
- **A 422 empties the file input and says so.** Browsers can't refill a file input, and a server
  stash means temp storage, tokens and cleanup. The empty picker is the platform's behaviour; the
  message makes sure nothing is lost silently.
- **The stored file shows as basename text, not a link.** Django's stock `ClearableFileInput`
  calls `.url` (which signs a URL on private storage) and prints the storage key.
  `accounts/forms.py` avoids it for this reason.
- **The framework swaps its widget in for Django's `ClearableFileInput`.** `ModelForm` file fields
  get `ClearableFileInput` by default, so consumers get the safe widget without declaring it. A
  form that declares some other widget, such as `ProfilePictureForm`'s plain `FileInput`, is left
  alone.
- **A new upload with Remove ticked is a field error.** This is Django's own `ClearableFileInput`
  rule ("Please either submit a file or check the clear checkbox, not both."), and it stops the
  user from losing a file they didn't mean to.
- **The choose-again message is added in `handle_submit`, not `form_invalid`.**
  `educator_interface/actions.py:1286` overrides `form_invalid`. Adding the message before
  `form_invalid` is called reaches every override.
- **The inline form moves into the framework.** The account page (spec 3) uses it, and the
  framework stays generic. The FLS template that held it goes away rather than becoming a
  pass-through.

## Requirements

All new framework code, templates and tests stay generic, so they survive
`extract_panels_framework-3-standalone-backend` and `-4-template-contract` with the same
behaviour. They contain no FLS name. The only `freedom_ls.*` they import is `panel_framework`
itself, and the tests import no FLS model.

### Files reach the form (`freedom_ls/panel_framework/actions.py`)

1. `FormPanelAction.get_form_kwargs` adds `"files": ctx.request.FILES` on POST and
   `"files": None` otherwise. `CreateInstanceAction.get_form_kwargs` and
   `EditAction.get_form_kwargs` inherit it through `super()`. So does every override in
   `educator_interface/actions.py` (each one calls `super()`).
2. `FormPanelAction.get_unbound_form` sets `files` to `None` as well as `data`, so a "save and add
   another" form comes back empty.
3. The `refresh_on_change` GET rebuild in `FormPanelAction.get_form` passes no files.
4. `FormPanelAction.get_form` swaps the framework widget (requirement 10) into every field whose
   widget is exactly Django's `ClearableFileInput`. It keeps the field's `attrs`, such as `accept`.

### The choose-again message (`actions.py`)

5. In `FormPanelAction.handle_submit`, when the form is invalid, the framework adds this error to
   each file field that received an upload (its name is in `ctx.request.FILES`) and has no error
   of its own:
   "Choose the file again. It is not kept when the form has errors."
   It does this before calling `form_invalid`. A file field with its own error keeps that error
   only. The message counts towards `field_error_count`, so the dialog's error summary lists it.
6. The message wording is a module-level constant in `actions.py`, so a host can read it in
   tests.

### Multipart encoding (templates)

7. `panel_framework/modal/form.html`: when `form.is_multipart` is true, the `<form>` carries
   `hx-encoding="multipart/form-data"` and `enctype="multipart/form-data"`. Each submit button's
   default `loading_text` becomes `Uploading…` instead of `Saving…`. A `loading_text` set on a
   `submit_buttons` entry still wins. When `is_multipart` is false, the rendered markup is
   unchanged.
8. The new inline partial (requirement 9) does the same: multipart attributes and `Uploading…`
   when `form.is_multipart` is true, `Saving…` otherwise. Every loading text uses the single "…"
   character.

### The inline form partial

9. `educator_interface/partials/inline_record_form.html` moves to
    `freedom_ls/panel_framework/templates/panel_framework/partials/inline_record_form.html`. It
    keeps its context contract (`form`, `action_url`, `form_id`), its markup and its docstring
    comment, plus requirement 8. `educator_interface/partials/learner_name_form.html` and
    `cohort_name_form.html` include the framework path, and the old file is deleted. The learner
    name and cohort name panels render the same as before. The one change is that "Saving..."
    becomes "Saving…".

### The file widget (`freedom_ls/panel_framework/widgets.py`, new)

10. A `ClearableFileInput` subclass, public in the module's `__all__`, with its template at
   `panel_framework/widgets/clearable_file_input.html`:
   - `is_initial(value)` is true when the value has a non-empty `name`. It never reads `.url`.
   - With a stored file, the template shows `Current file:` followed by the basename
     (`os.path.basename(value.name)`), autoescaped. Long names wrap with `break-all`, and the full
     basename is in a `title` attribute. It never prints the storage key's directories or a URL.
   - When the field is not required and a file is stored, it shows a checkbox labelled `Remove`,
     whose accessible name also includes the basename (visually hidden text). The checkbox name
     stays Django's `<name>-clear`, so `value_from_datadict` and `FileField.clean` work unchanged.
   - Then the native file input, keeping the field's `id`, `aria-describedby` and `aria-invalid`.
     The field's label and error wiring stay on the file input, not on the checkbox. No custom
     button and no hidden input.
   - It uses only framework components and role tokens, and no `text-sm` (a dialog body is base
     size).

### Failed requests (`freedom_ls/panel_framework/static/panel_framework/js/alpine-components.js` and both form templates)

11. Both form templates (the dialog form and the inline partial) carry an empty error region for
    a failed request. When `htmx:responseError`, `htmx:sendError` or `htmx:timeout` fires for a
    request from one of these forms, the region shows a message with `role="alert"`:
    - 413: "The file is too large to upload. Choose a smaller file."
    - Anything else: "Your changes could not be saved. Try again."
12. The handler skips responses already dealt with elsewhere: a 403 or 404 (the framework's
    existing reload) and any response that `base/js/alpine-components.js` swapped because it
    carries an OOB toast. The response body is never swapped into the form. The dialog stays
    open, the values entered stay, and Save is usable again. The region clears on the next
    submit.

### Discard prompt (`alpine-components.js`)

13. `dirtyTracker` serialises a `File` value as its name, size and last-modified time, not
    `[object File]`. Picking a file then marks the dialog (and the quick view) dirty, and Esc
    shows the discard prompt. An empty file input matches its baseline.

### Component reference page (`panel_framework/reference.py`, `reference/_examples.html`)

14. A "File field" section with ids prefixed `file-field-`, rendered from static data with no
    queries:
    - a dialog form with an optional file field and a stored file (Current file, Remove, picker);
    - the same form after a 422, showing the choose-again message;
    - an inline form with a required file field.
    The stored file in the example is a stand-in object with a `name`, not a model instance.
    `file-field` is added to `COMPONENT_NAMES` in `tests/test_reference.py`.

## Testing

Framework suite (`freedom_ls/panel_framework/tests/`). It uses a plain `forms.Form` with a
`FileField` for `FormPanelAction`. For `EditAction` and `CreateInstanceAction` it uses a stub model
with a file field on temp-dir storage (`freedom_ls/tests/storages.py`), with no FLS storage alias.

- `get_form_kwargs` passes `request.FILES` on POST and nothing on GET. `get_unbound_form` is
  unbound for files too.
- A multipart POST to a dialog `FormPanelAction`, an `EditAction` and a `CreateInstanceAction`
  reaches `form_valid` with the file. The `EditAction` saves it on the instance.
- The same for an inline-shape action rendering `panel_framework/partials/inline_record_form.html`.
- 422 with a file chosen and another field invalid: the input renders empty, the choose-again
  message is on the file field, the dialog's error summary lists it, and the stored file is still
  shown.
- 422 where the file field has its own error: only that error shows.
- 422 with no file chosen: no choose-again message.
- Remove ticked on an optional field clears the instance's file. Remove ticked with a new upload
  gives Django's contradiction error.
- The widget shows the basename only, never calls `.url` (a value whose `url` raises still
  renders), escapes a hostile name (`<script>"x.png`), and shows no Remove on a required field.
- A `ModelForm` field's `ClearableFileInput` is replaced by the framework widget with its `attrs`
  kept. A declared plain `FileInput` is not replaced.
- `modal/form.html` and the inline partial: `hx-encoding` and `enctype` present and loading text
  `Uploading…` with a file field. With no file field, the dialog markup is byte-identical to
  before, and the inline markup differs only in the ellipsis character.
- The existing learner name and cohort name panel tests pass against the moved partial.
- The invariants in `tests/invariants/test_templates.py` pass, and the inline partial is added to
  the loading-text ellipsis check.
- Reference page: the `file-field-` example ids exist, no duplicate ids, still zero queries.
- Playwright, dialog and inline: upload succeeds and Save shows "Uploading…" while disabled.
  Picking a file then pressing Esc shows the discard prompt. A routed 413 and a routed 500 each
  show their message, keep the dialog open, keep the typed values and re-enable Save. A failed
  request on a form without a file field shows the generic message.

## Documentation and downstream

- `claude_plugins/fls-dev/skills/panel-framework/SKILL.md`: a "Forms with a file field" section.
  It covers what the framework does (files, multipart, widget, choose-again, Uploading…, failed
  requests) and what the consumer owns (storage alias per `fls-dev:file-storage`, size and type
  validators, the reverse proxy's body size limit at or above the largest allowed file). It also
  records the new home of `inline_record_form.html`.
- Upgrade notes: `educator_interface/partials/inline_record_form.html` is now
  `panel_framework/partials/inline_record_form.html`. A project that shadows or includes the old
  path must move to the new one.

## Open questions

None.

## Success criteria

- A `ModelForm` with a `FileField` on an `EditAction` saves an uploaded file from a dialog and from
  an inline form, with no consumer code beyond the form.
- A 422 on a file form shows the choose-again message on the file field, and the input is empty.
- The stored file renders as its basename. The rendered widget contains no URL and no storage
  directory.
- Every existing panel form test passes unchanged, apart from the inline loading text's ellipsis.
- A 413 or 500 from a panel form shows a message in the form, and Save works again.
- The component reference page shows the file field examples and stays query-free.
