# Research: codebase (file upload on panel framework form actions)

All paths are relative to the worktree root. Question: what does this work touch, reuse or conflict with?

## 1. Summary

- The framework builds every form action's form from `request.POST` only. The change is small in Python (pass `ctx.request.FILES` beside `data`) and larger in templates, tests and the reference page.
- There is **no inline panel form template in `panel_framework`**. The "inline shape" `LearnerNamePanel` uses is `educator_interface/templates/educator_interface/partials/inline_record_form.html`, an FLS template. The framework owns only the dialog form (`modal/form.html`). The spec has to decide where the generic inline form lives (see section 9).
- No file input widget or template exists in the framework. Styling for `input[type=file]` is already global CSS (`tailwind.components.css:155-168`). Django's `ClearableFileInput` renders `django/forms/widgets/clearable_file_input.html`, which is not overridden anywhere in the repo.
- The dev reference page (`/panel-framework/components/`, DEBUG only) is static example HTML with a 0-query test. It has no live actions, so a "file field example" there cannot be a working upload round trip without new plumbing.
- No in-flight spec edits `actions.py`/`modal/form.html` right now. Conflict risk is with `extract_panels_framework-2-new-capabilities` (in progress, edits `reference.py`, `tests/conftest.py`, templates) and the not-yet-started `-3` and `-4`.

## 2. Where forms are built from the request

### Framework

| Place | Ref | What it does |
|---|---|---|

`PanelContext` carries `request` (`ctx.request`), so `ctx.request.FILES` is available in every hook. Django populates `request.FILES` only for a multipart POST; for a urlencoded post it is empty, so passing `files` always is harmless for forms without a file field ("forms without a file field behave exactly as today").

### Subclasses in `educator_interface` that override `get_form_kwargs` (all call `super()`, so they pick up `files` automatically)

`educator_interface/actions.py:437` (`EditLearnerNameAction`), `:595`, `:808`, `:1262`, `:1325`, `:1404`; `educator_interface/views.py:1827-1834` overrides `get_form` and calls `super().get_form(ctx)`. None of them bypass `get_form_kwargs`, so none needs changing.

## 3. Templates

### Dialog form: `freedom_ls/panel_framework/templates/panel_framework/modal/form.html`

- Lines 13-16: `<form hx-post="{{ action_url }}" hx-target="#app-modal-body" hx-swap="innerHTML" hx-disabled-elt="#app-modal-body button[type='submit']">`. **No `hx-encoding`.** Add `hx-encoding="multipart/form-data"` (htmx 2 uses `FormData` for the post; precedent in the repo: `form_engine/templates/form_engine/inputs/file_upload.html:47`). Conditional on `form.is_multipart` (a Django `BaseForm` property, true when any widget has `needs_multipart_form`), so non-file forms are byte-identical to today.
- Line 21: `partials/error_summary.html`; line 23: `partials/form.html` (the field loop, in `freedom_ls/base/templates/partials/form.html`, **not** in `panel_framework`). That partial renders `{{ field.label_tag }}`, `{{ field }}`, help text and `field.errors`. A `ClearableFileInput` renders through `{{ field }}` with no template change.
- Lines 26-48: footer buttons are `<c-button type="submit" loading="true" loading_text="{{ btn.loading_text|default:'Saving…' }}">`. A per-button `loading_text` key already exists in the `submit_buttons` dicts. Using it for "Uploading…" needs a way to say "this form uploads": either `form.is_multipart` in the template (`{% if form.is_multipart %}Uploading…{% else %}...`) or a context flag.
- Also included by `educator_interface/templates/educator_interface/modal/move_confirmation.html:11` (`{% include "panel_framework/modal/form.html" %}`) and rendered by `form_fragment_context` for every `FormPanelAction`, so a change here reaches those.
- `modal/form.html` tests: `panel_framework/tests/components/test_modal_form_template.py` (renders the template with a plain `forms.Form`, lxml assertions); `tests/test_actions.py:940-1010` (GET fragment, posts to action URL, header-then-form-then-footer order), `:609-700` (plain-form action 422, `StubPlainFormAction` at `:609-626`).

### "Disabled while in flight" pattern that already exists

- `hx-disabled-elt` + `<c-button loading="true" loading_text="…">` (`freedom_ls/base/templates/cotton/button.html:19-20,57-61`). htmx adds `.htmx-request` to the element that issued the request (the `<form>`), and the button's two spans swap via `[.htmx-request_&]` CSS. So the visible label already changes to a spinner plus `loading_text` while the request is in flight, and `hx-disabled-elt` disables the button. **The user's "Save disabled, label 'Uploading…'" decision is the existing mechanism with a different `loading_text` for forms that carry a file.** No progress bar, no JS needed.
- `modal/form.html` uses `#app-modal-body button[type='submit']` (several submit buttons), listed in `MULTI_SUBMIT_DIALOGS` in `tests/invariants/test_templates.py:678`. Other dialogs use `find button[type='submit']`.
- Invariant `test_every_dialog_loading_text_ends_in_the_ellipsis_character` (`tests/invariants/test_templates.py:663-671`): `loading_text` must end with the "…" character, not "...". The inline template `inline_record_form.html:30` currently has `loading_text="Saving..."` (three dots), which that invariant does not scan (it covers `DIALOG_BODIES` only). "Uploading…" must use the single character.
- `test_no_dialog_form_with_a_find_selector_holds_an_element_that_issues_its_own_request` (`test_templates.py:693-712`): irrelevant to `#app-modal-body` selectors, relevant if the inline form uses `find button[type='submit']`: the file input must not carry its own `hx-post`/`hx-get`.

### Inline panel form (the shape `LearnerNamePanel` uses)

- `freedom_ls/educator_interface/templates/educator_interface/panels/learner_name.html:8` includes `educator_interface/partials/learner_name_form.html`, which includes `educator_interface/partials/inline_record_form.html` with `form_id`. The same partial serves the cohort name form (`partials/cohort_name_form.html:5`).
- `inline_record_form.html:11-19`: `<form id hx-post hx-target="#{{ form_id }}" hx-swap="outerHTML" hx-disabled-elt="find button[type='submit']" x-data="refocusAfterRequest" data-refocus-id=… x-on:htmx:after-request="refocus" class="space-y-3">`. No `hx-encoding`. Fields in one row with Save at the end (`:23-31`), field errors as one line with `role="alert"` and id `{{ field.auto_id }}_error` (`:32-34`), non-field errors in a `<c-panel-notice>` (`:20-22`). Save is `<c-button … size="small" loading="true" loading_text="Saving...">`.
- The skill rules for an inline form (`claude_plugins/fls-dev/skills/panel-framework/SKILL.md:285-296`): error is one line under the field, message alone, `role="alert"`, input has `aria-describedby` and `aria-invalid`, no notice box, no summary. Note `extract_panels_framework-1-gather-generic-code` (done or in done folder; see section 8) did not move this partial. The skill describes the inline form pattern as a framework rule, so (a) matches "framework owns it".

## 4. How 422 re-render works

- `FormPanelAction.form_invalid` (`actions.py:398-405`): `render_to_string(get_fragment_template_name(), get_fragment_context(ctx, form), request=ctx.request)`, `HttpResponse(html, status=422)`. Inline forms swap themselves `outerHTML` (target = form id); dialog forms swap `innerHTML` into `#app-modal-body`.
- htmx 2 swaps 4xx responses only when the project config allows it. Check `htmx.config.responseHandling` or the equivalent: all existing 422 forms already work, so no change; but a multipart request goes through the same path.
- On a re-render, a bound form with an `<input type=file>` renders the input **empty** by Django's design (`FileInput.format_value` returns `None`; the browser cannot be told a value). So "the file input comes back empty" is the default behaviour with no stash. The new part is the **message**: when a file field is bound and the form has any error, the file field should carry a "choose the file again" message. That is a framework-side step because the form class belongs to the consumer. Ways: add a non-blocking field message in `get_form`/`form_invalid` for bound `FileField` widgets whose cleaned value was dropped, or render a hint next to an empty file input in the template when `form.is_bound and form.errors`. The spec decides which; the note must not appear when the file field itself is the one with the error (its own error already says what is wrong), or must not hide it.
- Error focus: appModal `_afterBodySwap` on a 422 focuses `[data-error-summary]` or `[aria-invalid="true"]` (`static/panel_framework/js/alpine-components.js:352-366`), so the file input needs `aria-invalid` when it carries an error to take focus on the inline/dialog 422. Django adds `aria-invalid="true"` to widgets of fields with errors on its own (Django 5+ `BoundField.build_widget_attrs`), including file inputs.

### The dirty-form guard and file inputs

- `dirtyTracker` (`alpine-components.js:125-154`) compares `FormData` entries serialised as `${name}=${value}`. A file value stringifies as `[object File]` whether or not a file was chosen, so **choosing a file does not make the dialog "dirty"** and an Esc after choosing a file closes without the discard prompt. Also the "Remove" checkbox is tracked fine. The spec may want a test or a small tracker change (e.g. serialise a `File` as its name/size). `quickView` uses the same tracker (`:444`).

## 5. Widgets and field templates

- No file-input widget, widget template, or `FORM_RENDERER` override: grep for `ClearableFileInput`, `type="file"`, `widget` templates in `freedom_ls` shows no framework hit. `FORM_RENDERER` / `templates/django/forms/widgets/` overrides: none found in `panel_framework`.
- Field loop is `freedom_ls/base/templates/partials/form.html` (shared with other pages, **base app**, not framework). It renders `{{ field }}` raw, so widget markup decides everything.
- Styling for the native file input is in `tailwind.components.css:145-168`: `input[type="file"]` shares the text-input rules (`w-full px-3 py-2 border ...`) plus `text-sm cursor-pointer file:...` button styling. The checkbox rule is `:195-200`, `label` is `block text-sm font-medium text-muted mb-1` (`:141-143`).
- `ClearableFileInput` default template (`django/forms/widgets/clearable_file_input.html`) prints `Currently: <a href="url">name</a>`, `<input type=checkbox name=x-clear id=x-clear_id> <label for=x-clear_id>Clear</label>` (only when not required and an initial exists), then `Change: <input type=file>`. The user chose "name as a link + Remove checkbox when optional + picker". Both the initial text and the clear label are Django's `initial_text` / `clear_checkbox_label` class attributes or overridable templates. A framework widget subclass with `template_name = "panel_framework/widgets/clearable_file_input.html"` would be the "framework-styled" version; a default-renderer override would change every `ClearableFileInput` in the project (including ones used in admin) and is the wrong scope.
- **Existing precedent that argues against the stock widget:** `accounts/forms.py:52-54` deliberately avoids `ClearableFileInput` ("it would print the stored key and a signed link beside the input") and uses `forms.FileInput` plus its own `remove_profile_picture` `BooleanField` (`:71-74`) and a `clean()` that turns the tick into `False` (`:76-92`). Private storage (`user_data` bucket, `profile_pictures` alias) means `value.url` is a signed URL, and the default template also shows `{{ widget.value }}`, the stored key. The stock widget's `Currently:` line calls `value.url` and so signs a URL and prints `str(value)` (the storage key). The framework widget should print `value.name` basename only (and decide whether to link) so a consumer with private storage does not leak the key or fail on `.url`. Spec 3 will move this exact form onto a panel, so the widget has to work for `ProfilePictureForm`'s "remove" semantics (form-level BooleanField vs the widget's `-clear` checkbox; model `FileField` form field `FileField.clean` already understands `False` and the `-clear` checkbox through `ClearableFileInput.value_from_datadict`).
- Server-side: `forms.FileField` with `ClearableFileInput` reads `files` for the upload and `data` for `<name>-clear`; both must be passed to the form, which `get_form_kwargs` will now do.

## 9. htmx configuration and CSRF

- `freedom_ls/base/templates/_base.html:123`: `<body … hx-headers='{"X-CSRFToken": "{{ csrf_token }}"}'>`. htmx sends the header on every request, including a multipart post, so no `{% csrf_token %}` hidden input is needed in either shape (the existing modal/inline forms have none). htmx 2.x: `hx-encoding="multipart/form-data"` sets `Content-Type` automatically; the header is still added. Django checks the `X-CSRFToken` header for multipart POSTs too.
- htmx request size and timeout: not configured in the repo for panel forms (no `htmx.config.timeout`). A slow upload is not cut off by htmx by default. Within an htmx request the htmx `htmx-request` class remains until the response arrives, which is what the loading label hangs on.
- `hx-disabled-elt` is a plain attribute on the form; htmx also disables the button during a multipart post exactly as it does for urlencoded.
- `htmx.process(this._body)` in `_afterBodySwap` (`alpine-components.js:342`) re-wires a swapped-in dialog fragment, so a re-rendered form keeps its `hx-encoding`.

## 11. Rules that apply (from `fls-dev:panel-framework` SKILL and `CLAUDE.md`)

- Framework tests: unit tests for actions with stub actions in the framework suite; run `tests/invariants/test_templates.py` after any template change (SKILL.md:315-341).
- Public names: a name a host may import must be in the module's `__all__` (`tests/invariants/test_public_names.py`); a new public widget or helper in `forms.py` or `actions.py` needs an `__all__` entry (`forms.py:9` has `__all__ = ["REASON_LENGTH", "ReasonForm"]`; `actions.py:27-46`). Private modules: `tasks`, `checks`, `field_display`, `templatetags`.
- Hooks take `ctx` and read the request through it (no request state on the action); the action's URL is `action_url` in every fragment.
- Dialog shape: header, body, footer; loading text ends in "…"; error summary (`partials/error_summary.html`, `data-error-summary`, `role=alert`) for a dialog, one-line field error for an inline form.
- Project conventions: type hints everywhere, no `Any`, no `# type: ignore`, no abstract base classes unless asked, no logging, no new functionality beyond what was asked; never edit existing migrations; do not delete TODO / `@claude` comments.
- File-storage skill: do not add a `FileField` with a real alias to a framework model for the demo.
- `panel_framework/field_display.py` is vendored (Django licence header) and its docstring lists adaptations that a parity test enumerates.

## 12. Open points the spec has to settle (found while mapping)

1. Where the generic inline form lives (section 3): a framework partial vs the FLS `inline_record_form.html`.
2. How the form knows it carries a file: `form.is_multipart` in the templates vs a context key from `form_fragment_context` (`actions.py:241-272`). `form.is_multipart` is a Django property and needs no new API; it answers for formsets or forms whose widgets are swapped in `__init__`.
3. The "choose the file again" message: where it is added (form class vs framework, per file field, only when the form is bound and invalid) and that it does not hide the file field's own error.
4. The widget: a framework `ClearableFileInput` subclass/template that prints only the file's basename (no storage key, no signed-URL call when the storage is private), with a "Remove" checkbox when the field is optional. Interaction with `ProfilePictureForm`'s own remove `BooleanField`: spec 3 will either switch to the widget's `-clear` or keep the form's field; the framework widget must not force one.
