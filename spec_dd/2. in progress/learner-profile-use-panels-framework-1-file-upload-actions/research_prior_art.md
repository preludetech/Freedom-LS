# Research: prior art for file uploads in panel framework form actions

Spec: `learner-profile-use-panels-framework-1-file-upload-actions`. Question: what has already been tried, here or elsewhere, and what happened?

Limits of this pass: no shell was available, so `git log -S "request.FILES"`, `git log -S "multipart"` and `git log --all -- freedom_ls/panel_framework` were NOT run. Findings come from reading the working tree (specs, templates, JS, tests) and from web fetches. No commit hashes are cited. If commit-level history matters, re-run those three git commands.

## 1. Here: the framework has never carried a file

- No spec in `spec_dd/3. done/` (panel-framework specs `educator-interface-1..4`, `extract_panels_framework-1`) tried or deferred uploads. The only mentions are the CSV import page (restyled in `extract_panels_framework-1`, `3. done/2026-11-16_19:13_extract_panels_framework-1-gather-generic-code/`) and a mockup-inventory note that the design kit has an `upload-simple` icon but "no upload semantic" (`3. done/2026-09-29_14:19_educator-interface-4-panel-framework-components/research_mockup_inventory.md:361`).
- The gap was found by `spec_dd/1. next/learner-profile-use-panels-framework/research_panel_framework_fit.md`, "File upload: not supported" (lines 69-82). It records:
  - `FormPanelAction.get_form` and `EditAction.get_form` build the form from `request.POST` only (today `get_form_kwargs`, `panel_framework/actions.py:314-316`, passes `data = request.POST` or `None`).
  - `panel_framework/modal/form.html:13-16` is `<form hx-post hx-target="#app-modal-body" hx-swap="innerHTML" hx-disabled-elt="#app-modal-body button[type='submit']">` with no `hx-encoding` and no `enctype`.
  - The note's verdict: needs files on `get_form`, multipart on inline and modal forms, and "a 422 path that does not lose the chosen file". Neither `extract_panels_framework-2-new-capabilities` nor its out-of-scope list covers it.
- `panel_framework/field_display.py:49-51` deliberately dropped admin's `FileField` link branch; file values render as plain text. The spec's "show the current file as a link" therefore needs new display code, not a revival of something removed by accident.
- Sibling specs already depend on this one: `learner-profile-use-panels-framework-2-editable-list-panel/idea.md:51` ("File fields on entries: ...-1-file-upload-actions supplies"), `...-3-account-page/idea.md:26-28`, and the roadmap section "Account area on panels" in `spec_dd/1. next/roadmap.md:313-332` (which says collisions with `extract_panels_framework-2` and `-4` rebase on whichever lands second).

## 2. Here: existing uploads and what they teach

All three existing uploads avoid the panel framework's form actions.

1. **Learner CSV import** (`educator_interface/templates/educator_interface/learner_import_upload.html:19`, `views.py:~3057`). A plain Django view, `<form method="post" enctype="multipart/form-data">`, `request.FILES if request.method == "POST" else None`, then `status=422 if form.errors else 200` (`views.py:3084`). No htmx. Shows the project already returns 422 for a bad upload; the file input is simply re-rendered empty (browser behaviour), which is the same outcome the chosen answer wants.
2. **Profile picture** (`spec_dd/3. done/2026-11-15_09:21_learner-public-profile-1-profile-picture/`; code in `freedom_ls/accounts/`). A plain `<form method="POST" action=... enctype="multipart/form-data">` in `accounts/templates/accounts/profile.html:14`, with `request.POST, request.FILES, instance=...` in `accounts/views.py:77`. Its own idea said "Account editing stays on plain views, not the panel framework." Findings that carry over:
   - `research_codebase.md:57-59`: the first bug-in-waiting was the missing `request.FILES` and missing `enctype`, "easy to miss". The same two omissions are exactly what the panel framework has today.
   - `research_ux_patterns.md:91` anticipated this spec: "if the account form is already HTMX-submitted, file inputs need `hx-encoding="multipart/form-data"`; return 422". It cited htmx docs but did not fetch them.
   - Remove control: that spec picked Django's `ClearableFileInput` checkbox convention (`research_ux_patterns.md:25-26`; QA test 9 "Remove gives initials... new upload wins over Remove"). Our answers file picked the same behaviour, so the clear-versus-replace precedence (new upload wins) is tested prior art.
   - QA (`qa_report.md`, test 7): five invalid files each gave the right error, nothing saved, "field values kept", and no uploader filenames in errors. No bugs found. Validation lives in the model form and validators (`accounts/validators.py`, `images.py`), not in the view: consistent with the idea's "framework does not decide storage or file checks".
   - `accounts/tests/test_views.py:952-962` asserts `enctype="multipart/form-data"` on the rendered form, and `accounts/tests/playwright/test_profile_picture_flow.py` covers upload, replace, refuse, remove in a browser. Both are patterns to copy for the framework's own tests, but those are non-htmx.
3. **Question file upload in `form_engine`**. The only existing htmx upload, and the closest working prior art:
   - `form_engine/templates/form_engine/inputs/file_upload.html`: widget root has `hx-encoding="multipart/form-data"` (line 47, inherited by the input), the `<input type="file">` does `hx-post` on `change`, and swaps its own wrapper outerHTML (the view returns the whole widget for every state, including errors, at 422: `form_engine/views.py:96-123`).
   - Client size guard: `x-on:htmx:confirm="checkSize"` on the input; `form_engine/static/form_engine/js/alpine-components.js:8-28` calls `event.preventDefault()` and clears `input.value` so "the file never leaves the machine". The server still enforces the cap. Documented in `claude_plugins/fls-dev/skills/alpine-js/SKILL.md:32`.
   - It uses `FILES.get("file")` and a bespoke view, not a Django form, so it is not reusable for `FormPanelAction`, but it proves `hx-encoding` inheritance, 422 swapping (global `htmx:beforeSwap` allows 422, `base/static/base/js/alpine-components.js:9-21`) and CSP-build Alpine all work together in this stack.
4. **File storage rules** (`claude_plugins/fls-dev/skills/file-storage/SKILL.md`): profile pictures and certificates are "user data": private, signed URLs or streamed by Django; every `upload_to` must be prefixed per alias and (lines 118) per owning user. Relevance: the "current file name as a link" in the form cannot assume `field.url` works; a private-alias file may not have a public URL. `ClearableFileInput`'s default "Currently: <a href=url>" would break or leak on private storage. This is the main design hazard for the "name + link" answer.
5. **Existing disable-while-submitting pattern**. `hx-disabled-elt="find button[type='submit']"` is used on inline and dialog forms across `educator_interface/templates/.../modal/*.html`, `partials/inline_record_form.html:15`, `comms/.../composer.html:38`, `course_applications/...claim_link_notice.html:50,67`, and in `panel_framework/templates/panel_framework/modal/form.html:16`. So "Save disabled while in flight" already exists. What does not exist is the label change to "Uploading…"; nothing in the repo swaps a button label during a request. `base/templates/cotton/button.html:116` notes its `loading` state only works when the htmx attribute (e.g. `hx-post`) is on that same element; the form carries `hx-post`, not the button, so reusing the cotton `loading` prop for the inline or dialog form needs checking. The idea's third open item ("upload progress or a disabled Save") is therefore half-done already; the answers file ("Uploading…" label, no progress bar) is the new part.

## 3. Here: framework behaviours that touch a file input

- **Dialog dirty-tracker will not see a file pick.** `panel_framework/static/panel_framework/js/alpine-components.js:125-141` builds the "unsaved changes?" baseline from `new FormData(form)` and serialises entries as `` `${name}=${value}` ``. A `File` stringifies as `[object File]` whether or not a file is chosen (an empty input yields an empty-named File), so choosing, changing or clearing a file never marks the dialog dirty and closing it would discard a picked file without the "Discard changes?" prompt. (Inference from reading the code; not browser-tested.)
- **422 swap into the dialog body**: `_afterBodySwap` (line 332-369) takes a fresh snapshot after every swap and focuses `[data-error-summary]` or `[aria-invalid="true"]` on 422. A file field re-rendered empty with an error message and `aria-invalid="true"` slots into this unchanged; this supports the chosen "ask to choose again" answer.
- **Inline panel re-render**: `LearnerNamePanel` style forms re-render in place on 422 (`actions.py:399-405`, `636`, `742`); the whole form (including the input) is replaced, so the browser's file selection is lost by construction. That is the behaviour the answers file selected. No stash or `hx-preserve` needed.
- Bulk and reason dialogs (`actions.py:736`) build forms from `request.POST` too; they have no file fields, so can be left alone ("forms without a file field behave exactly as they do today").

## 4. Elsewhere: htmx and Django upload pitfalls

- **Multipart must be requested.** htmx posts `application/x-www-form-urlencoded` by default; set `hx-encoding="multipart/form-data"`. The attribute is inherited, so it can sit on the form or a parent (<https://htmx.org/attributes/hx-encoding/>). From prior knowledge of htmx 2 source (not re-verified here): `<form enctype="multipart/form-data">` is also honoured, so either works. The risk is the dialog: `modal/form.html` and the inline form must each carry it, but only when the form has a file field, otherwise forms without files change encoding and Django's `request.FILES` handling becomes inconsistent.
- **File input value is lost when a swapped form comes back with errors.** htmx documents this directly: "Preserving File Inputs after Form Errors" (<https://htmx.org/examples/file-upload-input/>). Their two fixes are `hx-preserve` on the input (needs an `id`, keeps the element across the swap) or moving the input out of the swapped region and associating it via the HTML `form` attribute. PR #2474 added the `hx-preserve` note (<https://www.Github.com/bigskysoftware/htmx/pull/2474>). The spec chose to NOT preserve (answers file), so this documents the road not taken: `hx-preserve` would also keep the browser's stale file when the server found the file itself invalid, which is why "choose again" is the cleaner behaviour for validation failures of the file itself.
- **Upload progress.** htmx 2 exposes `htmx:xhr:progress` (loaded/total) for a `<progress>` bar and `hx-indicator` for a spinner class (<https://htmx.org/examples/file-upload/>). htmx 4 switches to `fetch`, which has no upload progress, so any progress UI would need raw XHR there (<https://four.htmx.org/patterns/file-upload>). This supports the chosen "no progress bar, disable Save" decision as the version-proof option. `hx-disabled-elt` disables for the whole request duration, which covers a slow upload without extra JS.
- **`hx-disabled-elt` on the form versus a swapped target**: the dialog form disables `#app-modal-body button[type='submit']` by selector, not `find`; if the 422 swap replaces the body, htmx re-enables by removing the attribute from the elements it recorded (a detached button), so the new button arrives enabled from the server markup. A label change to "Uploading…" done by JS on `htmx:beforeRequest` must be undone on swap: since the whole fragment is replaced on 422 and on success the dialog closes or the panel re-renders, the label resets by replacement. Inline forms swap too. Only a non-swapping error (network failure, `htmx:sendError`, 5xx not in the swap allow-list) leaves the label stuck; handle `htmx:afterRequest` or `htmx:responseError` too. (Reasoned, not found as a reported issue.)
- **htmx-specific Django pitfalls to test**: `request.FILES` is empty unless `enctype` is multipart (silent: the `FileField` then reports "This field is required" or ignores the clear); CSRF header via `hx-headers` on `<body>` still applies to multipart posts (project convention, CLAUDE.md); a `ClearableFileInput` on a bound invalid form never re-renders the just-uploaded file, only the instance's saved file, so the re-render naturally shows the old file with the message (Django behaviour, <https://docs.djangoproject.com/en/stable/ref/forms/widgets/#clearablefileinput>).
- **Size limits server-side**: `DATA_UPLOAD_MAX_MEMORY_SIZE` does not cover file parts; `FILE_UPLOAD_MAX_MEMORY_SIZE` only switches memory/temp storage. A cap comes from the form's validators (as `accounts.validators` does) or the reverse proxy. The idea leaves limits to the consumer; the reference page example should show one validator so copying it is safe.
- I did not find a specific reported htmx GitHub issue about `hx-encoding` inheritance misbehaving, 422 swaps losing files beyond the documented example above, or `hx-disabled-elt` plus multipart. Absence of a hit is not proof there are none.

## 5. Implications for the spec (for the synthesiser)

1. Reuse proven pieces: `hx-encoding` inheritance, 422 swap, `hx-disabled-elt` (all in `form_engine` and the panel forms today); Django `ClearableFileInput` semantics (picture spec QA test 9) with framework styling.
2. Emit multipart only when the form `is_multipart()`, to keep file-less forms byte-identical. Both `get_form_kwargs` (add `files`) and both templates (inline and `modal/form.html`) need it.
3. Dialog "unsaved changes" guard ignores files today; decide whether a file pick counts as a change (requires a tracker change) or is a documented gap.
4. "Show current file name as a link" must work on private storage aliases; do not assume `.url`.
5. "Uploading…" label is new; no existing component does it. Make sure it resets on every outcome, including non-swapped errors.
6. Validation, size and type limits stay with the consumer; add a size/type validator to the dev reference page example.
7. Add tests mirroring the picture spec (`enctype` assertion, valid upload, invalid upload at 422 with field error and `aria-invalid`, clear versus replace precedence) for both inline and dialog shapes, plus a Playwright test for the label/disabled state.
