# Spec: learner-facing UX refinements

Source: `idea.md`. Resources: `design.md` (Claude Design reference for the Your applications panel;
read it as that file says).

## Purpose

Three parts of the learner dashboard and course pages look or behave badly:

- On phones and tablets, the dashboard's paged course sections stack three tall cards under the
  controls. On a two-column tablet grid the third card sits alone on a second row.
- The course detail page offers an "All courses" breadcrumb. A learner who came from the dashboard
  and uses it to go back lands somewhere else.
- The dashboard's Your applications panel is plain, and it lists every application with no paging.

## Scope

In:

1. Below the `lg` breakpoint, every paged dashboard section (In progress, Recommended courses,
   Available courses, Coming soon, Learning history and each category section) shows its courses
   as compact rows in one column. The position text and previous/next controls stay above the
   rows, and "Browse all courses" sits below them, centred.
2. The course detail page replaces its breadcrumbs with a single "Back" link, whatever page the
   learner arrived from.
3. The Your applications panel is restyled after the design and pages three applications at a
   time.

Out:

- The idea's "Home"/"Dashboard" hamburger-menu item. The hamburger it means belongs to a downstream
  project's header override. FreedomLS core has no such menu.
- The dashboard layout at `lg` and up: the card grid and the heading-row controls stay as they are.
- The position text wording, which stays "1 to 3 of 7". The course sections' page size. Paging
  still never pushes a URL.
- Anything in the design beyond the panel itself: the "All applications" / "My applications" links
  and page, the action-needed highlight, avatar-menu and notification entry points, counts in the
  heading, deadlines and step counts in the meta line.
- The course player's breadcrumbs (`partials/player_breadcrumbs.html`) and the shared
  `<c-breadcrumbs>` component.

## Decisions

| Decision | Reason |
| --- | --- |
| The compact row is the existing all-courses row, `learner_interface/partials/course_row.html`. No third card template. | It already renders every `listing_status` with the card's field contract. |
| Each section renders both layouts: the card grid as `hidden lg:grid` and a row list as `lg:hidden`. | A card and a row differ in structure, not only in classes. A `display: none` copy is out of the accessibility tree, so screen readers meet each course once. |
| Back uses browser history when the previous page is a different page on this site. Otherwise it follows its `href`, which is the dashboard. | User's choice: Back should return where the learner came from. The `href` keeps it working with no JavaScript, from a shared link or search result, and after a POST that redirected back to the same page. |
| Applications paging stays inside `course_applications`. `learner_interface` gains no knowledge of applications. | The applications panel reaches `learner_interface` only as pre-rendered HTML from `get_dashboard_contributions_for_request`. Earlier specs fixed that boundary and later ones build on it. |
| An applications page swap fetches the dashboard URL itself with `hx-select` (and `hx-select-oob` for the status region). There is no new endpoint. | The dashboard view already returns the whole page for any htmx request whose `HX-Target` is not a course section. Hrefs built from `request.path` are then always dashboard URLs. |
| The previous/next control, the clamped-page lookup and the page-href builder move from `learner_interface` to `base`. Both apps use the moved code. | `course_applications` cannot import `learner_interface`, and CLAUDE.md forbids copying the code. |
| Applications page size is 3, through the same previous/next control and "1 to 3 of 7" position text as the course sections. | User's choice: one paging pattern across the dashboard. |

## Requirements

### 1. Shared paging moves to `base`

- Move `freedom_ls/learner_interface/templates/cotton/course-section-pagination.html` to
  `freedom_ls/base/templates/cotton/section-pagination.html` (`<c-section-pagination>`) and delete
  the old file. Its existing contract stays: both controls always render, a boundary control keeps
  its markup with `aria-disabled="true"` and `tabindex="-1"`, `data-direction` sits on each
  control, and there is a real `href` plus a matching `hx-get`. Add two optional props, `hx_select`
  and `hx_select_oob`. When set, each live control carries `hx-select` / `hx-select-oob` with those
  values. Course sections pass neither.
- Move the href builder (`section_page_href` in `freedom_ls/learner_interface/dashboard_sections.py`)
  and the clamping logic of `page_for` into a new `freedom_ls/base/pagination.py`:
  - `page_href(request: HttpRequest, param_name: str, page_number: int) -> str`, same behaviour as
    today: copy the query, touch one key, drop it on page one.
  - `clamped_page(request: HttpRequest, param_name: str, object_list: Sequence[T] | QuerySet[T],
    per_page: int) -> Page`, same clamping as today: junk and below-range values give page one,
    above-range gives the last page.
- `page_for` keeps its signature and calls `clamped_page` with `SECTION_PAGE_SIZE`. The template
  tag in `freedom_ls/learner_interface/templatetags/dashboard_tags.py` moves to a `base`
  templatetag library so the moved component loads it. `learner_interface` callers and templates
  switch to the new names.

### 2. Dashboard course sections below `lg`

All in `freedom_ls/learner_interface/templates/learner_interface/partials/course_list.html`.

- `section-page`: the controls row holds the position text on the left and `<c-section-pagination>`
  on the right (`justify-between`, full width below `lg`). At `lg` and up it keeps today's
  heading-row placement and alignment. The "Browse all courses" button in the controls row gets
  `hidden lg:inline-flex`.
- Below the card grid, inside the swap boundary, add the row list as `lg:hidden`: a single-column
  `ul` with one `li` per course, each including `partials/course_row.html`. After it, when
  `section.browse_all_url` is set, a centred "Browse all courses" link (same `<c-button
  variant="link" size="small" icon_right="next">`, `lg:hidden`).
- `course-grid` gets `hidden lg:grid`. It drops the `md:grid-cols-2` step, since nothing below
  `lg` shows the grid.
- Unchanged: the swap id `section-page-<slug>`, the `<h2>` outside the swap, the single
  `#dashboard-section-status` live region, section wrapper ids, and the `courseSectionPagination`
  focus handling. There is exactly one `<c-section-pagination>` per section, so one `nav`
  landmark.
- `in-progress-empty` is unchanged.

### 3. Course detail Back link

- `freedom_ls/learner_interface/views.py::course_detail`: remove the `breadcrumbs` list and its
  context key.
- `freedom_ls/learner_interface/templates/learner_interface/course_detail.html`: replace
  `<c-breadcrumbs :crumbs="breadcrumbs" />` with a back link in the same place:

  ```html
  <a href="{% url 'learner_interface:dashboard' %}" x-data="historyBackLink" x-on:click="goBack"
     class="inline-flex min-h-11 items-center gap-1.5 text-sm font-semibold text-primary no-underline hover:text-primary-hover ...">
      <c-icon name="previous" class="size-4" /> Back
  </a>
  ```

  Take the styling from the back link in `freedom_ls/panel_framework/templates/panel_framework/partials/breadcrumbs.html`.
  Do not reuse that partial, which is htmx-specific. Update the padding comment above `<c-page>`
  so it describes the back link.
- New Alpine component `historyBackLink` in
  `freedom_ls/learner_interface/static/learner_interface/js/alpine-components.js`. `goBack(event)`
  calls `event.preventDefault()` and `history.back()` only when `document.referrer` has the page's
  origin and a path different from `location.pathname`. Otherwise the link navigates to its
  `href`.
- For an anonymous visitor the `href` is the same URL, which is the home page.

### 4. Your applications panel

`freedom_ls/course_applications/backends.py`, `freedom_ls/course_applications/queries.py` and
`freedom_ls/course_applications/templates/course_applications/partials/dashboard_applications.html`.

- Ordering: `get_active_applications` orders by `-created_at`, then `pk`. The anonymous drafts
  query in `get_dashboard_contributions_for_request` gets the same tie-break.
- Paging: `get_dashboard_contributions_for_request(request=)` pages the applications with
  `clamped_page(request, "page_applications", applications, 3)` and passes the page to the
  template. `get_dashboard_contributions(user=)` has no request, so it gives page one. Both keep
  returning `[]` when there are no applications, so the panel stays absent, as today.
- Template structure (visual reference: `design_screenshots/strip__strip-states.png` and
  `phone__p-dash.png`, in the project's theme):
  - `<section x-data="courseSectionPagination">` with the `<h2 tabindex="-1">Your applications</h2>`
    heading, and the position text plus `<c-section-pagination>` on the heading row (beside the
    heading at `sm` and up, under it on phones). The pager passes `target_id="applications-page"`,
    `page_param_name="page_applications"`, `nav_label="Your applications pages"`,
    `hx_select="#applications-page"` and `hx_select_oob="#applications-status"`.
  - `div#applications-page` is the swap boundary. It wraps the position text, the pager and the
    list. The `<h2>` stays outside it.
  - `div#applications-status`: `role="status"`, `aria-atomic="true"`, `sr-only`, outside the
    boundary. When the request is an htmx request whose `HX-Target` is `applications-page`, the
    backend tells the template so and the region holds "Your applications: showing 1 to 3 of 7".
    On any other load it is empty.
  - The list is one column of plain rows at every width, all styled the same, with no highlight.
    Each row has: the course's accent icon box (`course-accent-<accent_slot_key>` plus
    `{% course_icon %}`, as `cotton/course-row-shell.html` draws it, at a smaller size); the
    course title as a stretched link to `course_applications:status`; and a status chip,
    `<c-chip variant="info" size="xs">Pending review</c-chip>` when submitted or
    `<c-chip variant="warning" size="xs">Incomplete</c-chip>` for a draft. A draft also gets the
    meta line "Finish your application to have it reviewed." At `sm` and up the row ends with a
    `<c-button size="small" icon_right="next">`: "Continue application" for a draft, "View
    application" when submitted, each with an `sr-only` " for <course title>". Below `sm` the
    button is hidden and the row ends with a decorative `next` icon (`aria-hidden="true"`). The
    stretched title link makes the whole row the target.
  - Every link goes to the same `course_applications:status` URL as today.
  - An anonymous visitor's rows show no name or email, as today.
- Paging a course section leaves `page_applications` in the URL, and paging applications leaves
  every `page_<slug>`, because both build hrefs with `page_href`.

## Testing

- `base/pagination.py`: `page_href` keeps unrelated parameters and drops the key on page one.
  `clamped_page` clamps junk, zero, negative and above-range values. These are the existing
  dashboard tests, moved.
- `<c-section-pagination>` renders `hx-select` / `hx-select-oob` only when the props are given.
  Boundary controls keep `aria-disabled` and never use `disabled`.
- Dashboard sections: each section renders the card grid (`hidden lg:grid`) and the row list
  (`lg:hidden`) with the same courses. "Browse all courses" appears in both places only for
  sections that have a `browse_all_url`, and the learner's own sections still offer none. The
  htmx section fragment carries both layouts. The query-count tests still pass, since rows reuse
  the cards' annotated fields.
- Rewrite the dashboard tests that count course titles or links to allow for the two layouts.
- Course detail: the page has no `aria-label="Breadcrumb"` nav and no "All courses" link. It has
  a "Back" link whose `href` is the dashboard URL, for signed-in and anonymous visitors. Rewrite
  `test_course_listing.py::test_course_detail_renders_breadcrumbs` (around line 1377) for this.
- Applications backend: with 7 applications, page one holds the 3 newest. `?page_applications=3`
  holds 1. `?page_applications=junk` gives page one. Anonymous drafts page the same way. No
  applications gives no contribution.
- Applications template: the submitted row shows "Pending review" and "View application"; the draft
  row shows "Incomplete", the meta line and "Continue application". The position text and the
  `nav` label "Your applications pages" are present. Update the copy-pinning tests in
  `course_applications/tests/test_backends.py`, `learner_interface/tests/views/test_course_listing.py`
  (around lines 1813-1871) and `test_course_access.py`.
- Playwright:
  - At 375px and 768px, a section shows rows, the controls above them and "Browse all courses"
    centred below them, with no horizontal scroll. At 1280px it shows the card grid.
  - Course detail reached from the dashboard: Back returns to the dashboard. Reached from
    `/courses/`: Back returns to `/courses/`. Opened directly: Back goes to the dashboard.
  - Applications: next swaps in page two with the heading kept, and the status region announces
    the new position. Paging a course section afterwards keeps the applications page. At 375px
    the rows show chevrons and no buttons.
  - `course_applications/tests/playwright/test_application_form_flow.py` still finds the heading
    "Your applications" and the "Continue application" link at its viewport.

## Success criteria

- At 375px and 768px, every paged dashboard section shows one column of course rows, with the
  position text and arrows above. A section with a browse-all link shows a centred "Browse all
  courses" below the rows. The page does not scroll horizontally.
- At 1280px the dashboard looks as it did before this change.
- The course detail page has no breadcrumbs. Its Back link returns to the dashboard or
  `/courses/`, whichever the learner came from, and to the dashboard on a direct visit or with
  JavaScript off.
- A learner with 7 applications sees 3 at a time, can page through all of them without a full
  reload, and keeps every course section's page while doing so.
- The change adds no import of `course_applications` and no applications-specific code to `learner_interface`.
- `uv run pytest` passes.
