# Spec: the full test suite runs on GitHub Actions on demand

Idea: `idea.md`. Answers: `answers.md`. Research: `research_*.md` beside this file.

## Purpose

A local full run takes about 25 minutes on four workers, so only one worktree can be verified at a
time. The FLS `Tests` workflow has been red since 2026-10-10: the unit job hits its 15-minute cap
less than half way through, and the Playwright job cannot install its browser on `ubuntu-latest`
(Ubuntu 26.04). This spec makes the workflow pass by splitting the suite across parallel jobs on
free standard runners, and lets an SDD run send its full tier there, wait, and read the result in
place of a local run.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| remote full run | coined | A full tier run by the project's remote command on GitHub Actions in place of the local full command |
| test group | narrowed | pytest-split's "group": one of the N slices `--splits N --group K` selects, here always one matrix job |
| group report | coined | The file one test job uploads: its collected, failed and unfinished node IDs and short failure text; not the full-run record |

## Scope

In:

- `.github/workflows/tests.yml`: a manual trigger, the suite split into duration-balanced test
  groups, coverage combined across groups, a partition check, and the two current failures fixed.
- A committed durations file and the `pytest-split` dev dependency.
- The generic `ds` test runner keeps its run file on request and records failure text in it.
- An FLS remote command in `fls-dev` that pushes the branch, starts the workflow for HEAD, waits,
  and prints the result in the test runner's output shape. It names this repository's workflow, so
  it does not go in `ds`.
- The generic `ds` tier definition and the generic `sdd` tier helper learn that a full tier may run
  remotely, through per-project configuration.

Out:

- Running targeted tiers, failed-only re-runs or single tests remotely. A failed-only re-run after
  a remote failure runs locally.
- Changing the First Class workflow.
- Claude Code cloud sessions (`faster-test-runs-7-claude-cloud-test-runs`).
- Paid or third-party runners.

## Decisions

- **The split is `pytest-split` by recorded duration, per test.** It partitions the collected
  tests, so a new app lands in a test group with no workflow edit. A module split across groups
  runs its module-scoped fixtures once per group; the pull request measurement decides whether 6
  groups are enough.
- **Every test job runs on `ubuntu-24.04`,** which Playwright 1.58 supports. Playwright is not
  upgraded. `lint` and `type-check` stay on `ubuntu-latest`.
- **The remote marker set is a superset of the local full tier:** `ci_only`, `weasyprint` and
  `dev_tooling` tests run remotely. A remote pass counts as a full run.
- **Coverage is enforced once, on the combined data,** never per test group.
- **There is no `pull_request` trigger.** The workflow runs on pushes to `main` and on
  `workflow_dispatch`. A dispatch run runs the test jobs only; `lint` and `type-check` run on
  pushes to `main`. The remote verdict reads the test jobs and the `coverage` job.
- **FLS runs its full tier remotely by default, from the day this merges.** `DS_TEST_REMOTE=off`
  forces a local run. The fallback covers the time before the first real dispatch proves it.
- **No usable remote verdict means a local run.** When GitHub is unreachable, the run cannot start,
  no job starts within `start_timeout_s`, the run exceeds `run_timeout_s`, or it ends without a
  test verdict (a cancelled job, a failed setup step, a missing group report, a failed partition
  check), the remote command cancels the run if one exists and the full tier runs locally, saying
  why. A test failure or a coverage failure never falls back.
- **The remote command pushes the branch itself,** following
  `claude_plugins/sdd/resources/commit_and_push.md`: never force, never `main` or `master`, and a
  rejected push is reported. A dirty tracked tree, a rejected push, or HEAD on `main` that
  `origin/main` lacks has no remote verdict.

## Requirements

### Workflow: `.github/workflows/tests.yml`

1. Triggers: `push` to `main` and `workflow_dispatch` with no required inputs. The
   `pull_request` trigger is removed. `lint` and `type-check` carry
   `if: github.event_name != 'workflow_dispatch'`.
2. Concurrency: no run cancels another. The group includes `github.run_id`, and
   `cancel-in-progress` is `false`.
3. Every test job runs on `ubuntu-24.04` with `timeout-minutes: 15` and passes
   `--randomly-seed=${{ github.run_id }}`. Every pytest command except the standalone configs
   (Requirement 7) uses one of two marker
   expressions, written once as workflow-level `env` values: `not playwright` for the unit pool
   and `playwright` for the browser pool. Each overrides the `addopts` `-m`, so `ci_only`,
   `weasyprint` and `dev_tooling` tests run.
4. `unit-tests` is a matrix over test groups 1 to 6 (`fail-fast: false`). Each group:
   - runs the unit pool with `--splits 6 --group <K> --splitting-algorithm least_duration
     --durations-path .test_durations`, under `.claude/ds/scripts/run_tests.sh`, `-n auto`, with
     `--cov` and no `--cov-fail-under`, and `COVERAGE_FILE=.coverage.unit-<K>`;
   - installs the WeasyPrint system libraries (Pango, cairo, gdk-pixbuf, HarfBuzz) before the run;
   - sets `DS_TEST_RECORD_PATH` to a file under `$RUNNER_TEMP` and uploads that file as its group
     report;
   - uploads under `if: always()` its coverage data (`include-hidden-files: true`) and its group
     report, each with a name unique to the group.
5. `playwright-tests` is a matrix over test groups 1 and 2 with the same split flags over the
   browser pool, no coverage, the trace upload on failure, and the same keep path and group report
   upload as Requirement 4.
6. `dev-tooling-tests` is removed; its tests run in the unit groups. The `[tool.coverage.run]
   omit` comment in `pyproject.toml` that says they run in a job without coverage is corrected.
7. `standalone-tests` runs the two standalone configs the unit job runs today
   (`freedom_ls/panel_framework/tests/standalone_pytest.ini`,
   `freedom_ls/icons/tests/standalone_pytest.ini`) under `run_tests.sh`, with the unit job's setup,
   and the same keep path and group report upload as Requirement 4. Its tests sit outside the partition check: each config collects its
   own set.
8. Group report: the test runner's run file, kept (requirement 13). The remote command reads
   failures only from group reports, never from logs.
9. `coverage` (`needs` every unit group, `if: always()`) downloads every group's coverage data,
   fails when any group's data is missing, runs `coverage combine`, writes the report to
   `$GITHUB_STEP_SUMMARY`, and fails under 92. `[tool.coverage.run]` gains `parallel = true` and
   `relative_files = true`.
10. `test-verdict` (`needs` every test job and `coverage`, `if: always()`) has the unit job's setup
    and fails unless every needed job succeeded and, for each pool, the node IDs its groups'
    reports list as collected are a partition (no duplicate, none missing) of one
    `--collect-only -q` over that pool with the same seed. It prints which of the two failed.
11. `setup-uv` gets `enable-cache: true` in every job. The rest of the setup is unchanged (Postgres
    17 on port 6543, Node 20, `npm ci`, Tailwind build).

### Durations: `.test_durations`

12. A `.test_durations` file at the repository root, from a full `--store-durations` run, is
    committed, and `pytest-split` joins the dev dependencies. Refreshing it is manual; the FLS
    testing skill names the command.

### Generic test runner: `claude_plugins/django-stack/scripts/run_tests.py` and `ds_run_record.py`

13. An opt-in keep path (environment variable `DS_TEST_RECORD_PATH`) writes the run file there and
    keeps it on every result, `PASS` included. Without it, behaviour is unchanged. A failed
    `outcome` event carries the test's short failure text (`longreprtext`, `--tb=short` form).
14. The remote command imports the failed-set cap and node-ID quoting from `run_tests.py` by
    path, so they stay in one place.

### FLS remote command: `claude_plugins/fls-dev/scripts/remote_full_run.py`

15. Stdlib only, driving `gh` and `git` through `subprocess`, run as `uv run python
    claude_plugins/fls-dev/scripts/remote_full_run.py`.
16. Preconditions, each failing to `RESULT UNAVAILABLE <reason>`: the tracked tree is clean; HEAD
    is on a branch, not detached; HEAD is
    not on `main` or `master` while `origin` lacks it; `gh --version` is 2.87.0 or later;
    `gh auth status` succeeds.
17. When `origin` lacks HEAD, push as the Decisions bullet "The remote command pushes the branch
    itself" says. Dispatch with `gh workflow run tests.yml --ref <branch>` and take the run ID from
    the printed URL; no URL printed is `RESULT UNAVAILABLE`. The run's `headSha` must equal local
    HEAD.
18. Poll `gh run view <id> --json status,conclusion,jobs` every 20 seconds. Print the run URL
    first, then one line per job state change and a line after 60 seconds without one. Budgets come
    from `[tool.test_tiers.remote]`: `start_timeout_s` (default 900) and `run_timeout_s` (default
    1800). Exceeding either runs `gh run cancel <id>` and prints `RESULT UNAVAILABLE <reason>`.
19. On completion, download the group reports with `gh run download <id>` and print the runner's
    reporting lines: `run: tests <n> collected, ...`, `run: summary (merged): <totals>`, one `run:
    failed <node id>` per failed test (with the runner's cap), `run: tested <sha>`, `run: url
    <url>`, and `run: RESULT PASS|FAIL`. A coverage failure prints `run: coverage <pct>% below
    92%` and `RESULT FAIL` with no node IDs. The failure text goes to
    `.sdd-work/remote_full_run_<branch with / as ->.txt` (directory created), printed as
    `run: log <path>`.
20. A run without a test verdict, per the Decisions bullet "No usable remote verdict means a local
    run", prints `RESULT UNAVAILABLE <reason>` with the URL. A `coverage` failure counts as a
    coverage failure only when every test job and `test-verdict` succeeded; otherwise it is
    `RESULT UNAVAILABLE`.
21. FLS opts in in `pyproject.toml`: `[tool.test_tiers.remote]` with
    `command = "uv run python claude_plugins/fls-dev/scripts/remote_full_run.py"` and the two
    budgets.

### Generic tier definition: `claude_plugins/django-stack/resources/test_tiers.md` and `scripts/select_tests.py`

22. When `[tool.test_tiers.remote] command` is set and `DS_TEST_REMOTE` is not `off`, the `full`
    tier runs that command (in the background, as any full tier). On `RESULT UNAVAILABLE` it quotes
    the reason and runs the local full command.
23. The contract a remote command meets: it prints the runner's `run:` lines, `run: tested <sha>`
    and `RESULT PASS|FAIL|UNAVAILABLE`; it exits 0 only on `PASS`; its failed set is its `run:
    failed` lines. Other keys in the table belong to the command.
24. When `select_tests.py` resolves `tier: full` and the remote command applies, it prints the
    remote command on `command:` and the local command on a new `fallback:` line. Without the
    table, output is unchanged. Every reader of `select_tests.py` output learns the `fallback:`
    line.
25. `RESULT FAIL` with node IDs takes the local failed-only re-run; `RESULT FAIL` with none (a
    coverage failure) takes the whole-tier re-run.

### Generic tier helper: `claude_plugins/sdd/commands/protected/run_test_tier.md`

26. Step 3 records a remote full run only when its `run: tested <sha>` equals the `sha:` that
    `full_run_record.py start` printed. A fallback local run is recorded as any local run.
    `full_run_record.py` is unchanged.
27. Step 4: a remote full run's summary ends `(remote: <url>)`, a fallback's ends `(local:
    <reason>)`. The report line keeps its shape.

## Testing

- `tests/test_remote_full_run.py` (repository-root `tests/`) covers the remote command with `gh`
  and `git` faked: each precondition failure; a rejected push; push skipped when `origin` has HEAD;
  no URL printed; `headSha` mismatch; both budgets cancel the run; a pass, a test failure with node
  IDs, a coverage failure, a failed partition check, a cancelled job and a missing group report each
  print the right lines and exit code; the failed-set cap; a branch name with `/`.
- `tests/test_run_tests.py`: the keep path survives a `PASS`; failure text lands on failed outcome
  events; without the variable nothing changes.
- `tests/test_select_tests.py` and `tests/test_select_tests_wrapper.py`: `tier: full` prints
  `command:` and `fallback:` with the remote table, the local command alone without it and under
  `DS_TEST_REMOTE=off`. They use a placeholder remote command, never the FLS script path.
- `tests/test_test_tiers.py` still passes.
- A local `--splits 2` collection under two seeds shows whether the seed changes the partition.
- `test-verdict` is shown to fail on a test group given the wrong `--splits`.
- `coverage` is shown to fail with `--fail-under` raised above the measured combined coverage on a
  dispatch of this branch.
- A dispatch of the workflow on this branch passes, with every test group under 12 minutes.
  Dispatch needs the file on `main` first, so this runs after merge, before the next spec's full
  tier.
- Before and after times are reported against
  `spec_dd/1. next/faster-test-runs/research_test_timings.md`: workflow wall time and a remote full
  run's wait, queue included.

## Open questions

- Q: How many test groups? → A: 6 unit, 2 Playwright (assumed default: 13 jobs stay under the
  20-concurrent-job limit, and the first dispatch measures each group against the 12-minute bar.
  Overrule by editing Requirements 4 and 5.)
- Q: What does "we dont need the pr run. Just tests." mean for the workflow? → A: The
  `pull_request` trigger is removed and a dispatch run skips `lint` and `type-check` (assumed
  default: the closest reading of the answer. Overrule by editing the Decisions bullet "There is no
  `pull_request` trigger" and Requirement 1.)
- Q: What does the remote command do on a detached HEAD? → A: `RESULT UNAVAILABLE`, so the full
  tier runs locally (assumed default: there is no branch to push or dispatch on. Overrule by
  editing Requirement 16.)

## Success criteria

- A dispatched run is green with no test job cancelled at its cap.
- `test-verdict` fails when a test group's split flags are wrong.
- `coverage` fails when combined coverage is below 92%.
- From a clean worktree, a full tier prints the run URL, waits, and ends with `RESULT PASS` and a
  full-run record for HEAD.
- A failing test on GitHub comes back as a `run: failed <node id>` line the local failed-only
  re-run accepts.
- With `gh` logged out, a full tier prints the reason and runs locally.
- With `DS_TEST_REMOTE=off`, a full tier runs locally and never calls `gh`.
