# Spec: Profile picture

Source: `idea.md` in this directory. Recorded answers: `answers.md`. Research: the `research_*.md`
files beside this spec, and `research_existing_profile_code.md` and `research_comparable_systems.md`
in `spec_dd/1. next/learner-public-profile/`.

## Purpose

A `User` has a name and an initials avatar and nothing else. Every user gets one profile picture,
uploaded, replaced and removed on the account profile page. It shows on every surface listed under
"Avatars" below, and initials remain the fallback. The later public profile
(`learner-public-profile-2-profile-and-page`) shows the same picture to anonymous viewers.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| profile picture | narrowed | `fls-dev:file-storage` skill's "profile pictures" (user-data bucket); here the one image a `User` uploads to stand for themselves, stored as `User.profile_picture`. Not `Organisation.profile_logo`. |

## Scope

In:

- A `User.profile_picture` field, its storage alias, upload validation and re-encoding.
- Upload, replace and remove on `accounts:account_profile`.
- The picture in place of the initials on every surface listed under "Avatars" below.
- Deleting superseded and orphaned stored files.

Out:

- The public profile page and its fields (`learner-public-profile-2-profile-and-page`).
- A crop or zoom UI, moderation, per-viewer visibility rules, HEIC support.
- `Organisation` logos: `check_logo_safety` and its messages stay as they are.
- Surfaces that render from ids rather than loaded `User`s keep initials: the dashboard and cohort
  attention rows (cached report data in `reports/screen_cache.py`), the audit log who and target
  (`educator_interface/partials/audit_person.html`), and the cohort report
  (`educator_interface/panels/cohort_report_body_region.html` and its PDF). They move to the idea
  `spec_dd/1. next/profile-picture-on-id-rows/idea.md`.
- The deleted-user branch of `comms/partials/participant_avatar.html`. No user, so no picture.

## Decisions

- **Signed URLs, minted at render time.** The bucket is private (`answers.md`). Every URL comes
  from `User.profile_picture_url` while the page renders and expires after the purpose's
  `querystring_expire` (default 3600 s). No URL is stored in a model, a report snapshot or
  `reports/screen_cache.py`, and none is cached server-side: production `CACHES` is the database
  cache, so a lookup per avatar would add a query per row. The browser re-downloads avatars on each
  page load; the small rendition below keeps that cheap.
- **One stored rendition**: a 400×400 WebP, centre-cropped (`answers.md`), enough for a 200 px
  picture at 2× density on the later public page. The original upload is not kept.
- **A new storage alias and purpose.** Never `user_uploads` or `public`, so no other purpose's
  overwrite or signing behaviour changes.
- **A deactivated user keeps their picture** (`answers.md`). No avatar code checks `is_active`.
- **The panel framework stays FLS-free.** `panel-avatar-chip` takes a plain `picture_url` string and
  FLS templates resolve it. The framework is being extracted
  (`extract_panels_framework-1-gather-generic-code`).

## Requirements

### Model and storage

- `freedom_ls/accounts/models.py`: add `User.profile_picture`, a `FileField(blank=True)` with
  `storage=get_profile_picture_storage` and `upload_to=profile_picture_upload_to`, plus a migration
  in `freedom_ls/accounts/migrations/`.
  - `get_profile_picture_storage()` returns `storage_for_alias("profile_pictures",
    "STORAGES['profile_pictures']")`, as `form_engine.models.get_user_uploads_storage` does.
  - `profile_picture_upload_to(instance, filename)` ignores the uploader's filename and returns
    `profile_pictures/{user.pk}/{uuid4 hex}.webp`. A new key per upload means a replaced picture
    never shares a URL with the old one.
  - `User.profile_picture_url` (property) returns the storage URL, or `None` when the field is
    empty. It reads no request state, so it works for anonymous viewers and outside a request. It
    makes no network call to storage: no `exists()` check per render.
- `freedom_ls/deployment/storage.py`: add `PROFILE_PICTURES_PURPOSE = "PROFILE_PICTURES"`, map alias
  `profile_pictures` to it in `FIXED_ALIAS_PURPOSES`, add it to `SIGNED_URL_PURPOSES`. Leave it out
  of `_OVERWRITE_PURPOSES` and `_OBJECT_PARAMETERS`.
- `config/settings_base.py`: add a `profile_pictures` `FileSystemStorage` entry to `STORAGES`,
  without `allow_overwrite`.
- `config/settings_base.py` `SECURE_CSP_REPORT_ONLY` `img-src`: add the profile-picture bucket's
  host when one is configured, taken from the same `AWS_S3_PROFILE_PICTURES_*` custom domain or
  endpoint that `build_storages()` reads.
- `freedom_ls/tests/storages.py`: generalise `bind_pathless_logo_storage` into
  `bind_pathless_storage`, which takes the model fields to bind, and bind
  `get_user_model()._meta.get_field("profile_picture")`, so tests prove no code calls `.path()` on
  the picture.

### Validation and re-encoding

- `freedom_ls/accounts/validators.py` (new) validates a picture. It shares
  `bomb_warnings_as_errors`, `truncated_images_rejected` and `DECODE_FAILURES` from
  `freedom_ls/base/images.py`. Leave `check_logo_safety` unchanged, because the report pipeline
  also reads logos through it.
- Rules, checked in this order so nothing large is decoded before it is refused:
  1. `file.size` at most 10 MB, then a bounded read.
  2. Open the image and take its format from the decoder (`JPEG`, `PNG`, `WEBP`), never from the
     extension or `Content-Type`. `MPO`, which Pillow reports for a phone JPEG that carries extra
     frames, counts as JPEG; its first frame is the photo.
  3. From the header's `img.size`: at least 128 px on each side, at most 50 megapixels in total. A
     12 MP or 48 MP phone photo passes.
  4. `load()` the image inside `bomb_warnings_as_errors()` and `truncated_images_rejected()`, so a
     truncated JPEG fails here, not later in re-encoding. `verify()` alone does not catch it.
- Re-encoding, bytes in, bytes out, in `freedom_ls/accounts/images.py`: JPEG draft mode so a large
  JPEG does not decode at full size, `ImageOps.exif_transpose`, first frame only for animated
  input, `ImageOps.fit` to 400×400 centred with `LANCZOS`, convert to `RGB` or `RGBA`, save as WebP
  at quality 80. Carry no EXIF or XMP into the output. Do not reuse content_engine's
  `optimise_image`: it can return the source bytes.
- Errors, one per failure, on the field. A file Pillow cannot identify
  (`UnidentifiedImageError`, which covers HEIC and SVG) is the wrong type. Every other member of
  `DECODE_FAILURES` gets the "could not be read" message:
  - wrong type, including HEIC and SVG: "Use a JPEG, PNG or WebP image."
  - too large: "That file is {size} MB. The limit is 10 MB."
  - too small: "That image is {w}×{h} pixels. Use one at least 128×128."
  - too many pixels or a decompression bomb: "That image is too large to process. Use one under
    50 megapixels."
  - unreadable or truncated: "That image could not be read. Save it again or choose another file."
  The uploader's filename and Pillow's exception text never reach the page.

### Account page

- `freedom_ls/accounts/forms.py` `UserForm`:
  - Declare `profile_picture` with a plain `FileInput`, not `ClearableFileInput`.
    `clean_profile_picture` validates, re-encodes and returns a `ContentFile`, so only the WebP
    reaches storage.
  - Add `remove_profile_picture`, a `BooleanField` labelled "Remove profile picture", shown only
    when a picture exists. A new file wins over a ticked remove.
  - Remove the `# TODO: allow the user to upload a profile picture` comment.
- `UserForm.save()` handles upload, replace and remove. It reads the previous stored name through
  `User._base_manager` before saving, as `QuestionAnswerFile.save()` does. It deletes the
  superseded file in `transaction.on_commit`, so a rolled-back save keeps the old file. Delete
  failures are not caught, as in `Organisation.save()`.
- `freedom_ls/accounts/views.py` `edit_profile`: pass `request.FILES`. Bind the form to a fresh
  `User._base_manager.get(pk=request.user.pk)`, not `request.user`, so an invalid POST does not show
  the typed, unsaved names or picture in the header and sidebar of the same response. The form
  re-renders with the error and the typed names; nothing is saved. A valid POST saves and
  redirects to `accounts:account_profile`, so the next page renders the saved names and picture
  from a freshly loaded `request.user`; "Profile saved" shows there.
- `freedom_ls/accounts/templates/accounts/profile.html`: `enctype="multipart/form-data"`; the
  current picture (or initials) at the top of the form with `alt=""` and the user's name beside it
  as text; the file input labelled "Profile picture" with
  `accept="image/jpeg,image/png,image/webp"` and help text "JPEG, PNG or WebP, up to 10 MB. Square
  pictures work best; others are cropped to the centre.", linked by `aria-describedby`. No
  client-side preview.
- `freedom_ls/accounts/admin.py`: in `UserAdmin`, add `profile_picture` to a fieldset and to
  `readonly_fields`, so every stored picture has been through the form's validation. Exclude it
  from `UserResource`'s export.

### Avatars

Callers read `user.profile_picture_url` and pass it with a bound attribute
(`:picture_url="..."`), never `picture_url="{{ ... }}"`, which turns `None` into the string
"None". The chip treats an empty value as no picture. Initials keep their current derivation on
every surface.

| Surface | File | Where the `User` comes from |
| --- | --- | --- |
| Header menu trigger | `freedom_ls/base/templates/partials/header_bar_user_menu.html` | `request.user` |
| Educator sidebar user block | `freedom_ls/educator_interface/templates/educator_interface/_shell.html` | `request.user` |
| Messaging participant | `freedom_ls/comms/templates/comms/partials/participant_avatar.html` (all four includers) | already loaded in `comms/messaging_views.py` |
| Recipient picker | `freedom_ls/comms/templates/comms/partials/recipient_picker.html` | already loaded |
| Cohort settings panel | `educator_interface/panels/cohort_settings.html` | already loaded |
| Learner and staff member table cells | `educator_interface/data-table-cells/learner.html`, `staff_member.html` | `select_related` on the table query |

No row costs a query; each view loads its users once.

- `panel-avatar-chip.html` gains an optional `picture_url` attribute, passed through
  `panel-person-link.html`. With a URL, the circle holds an `<img>`
  with `alt=""`, explicit `width`/`height`, `object-fit: cover`, a `bg-surface` background so the
  initials do not show through a transparent picture, and `loading="lazy"` in lists. The
  circle keeps its `panel-avatar-N` class and `aria-hidden`; the accessible name still comes from
  the name text or the caller's label. The chip's comment block, the `panel-framework` skill and
  `panel_framework/reference/_examples.html` document the attribute.
- The header trigger is the one avatar outside the chip: its circle has header styling
  (`bg-header-action`, 40 px) that the chip's colour slots do not. It keeps its `aria_label` and
  uses the same `profile_picture_url`, `<img>` attributes and fallback as the chip.
- The initials stay in the markup under the picture. When the image fails to load (missing file,
  expired signature on a long-open page), the initials show, never a broken-image icon. One
  capture-phase `error` listener in `freedom_ls/base/static/base/js/` serves the chip and the
  header, because `error` does not bubble. Every base layout that renders an avatar loads it,
  `_base.html` and the educator `_shell.html` included. No inline `onerror` attribute: the CSP
  policy is due to tighten.

### Deleting files

- A `post_delete` receiver on `User` in `freedom_ls/accounts/signals.py` (already imported by
  `AccountsConfig.ready()`) deletes the stored picture in `transaction.on_commit`, as
  `form_engine/receivers.py` does. Queryset and cascade deletes fire it too.

## Testing

What needs more than a test per requirement:

- Validator: every rejection with its message, including a truncated JPEG (not only a truncated
  PNG), an SVG renamed `.png`, a HEIC file and a decompression bomb; a 4032×3024 and an 8000×6000
  JPEG are accepted.
- Re-encoding: a JPEG with GPS EXIF comes out with no EXIF; an EXIF-rotated photo comes out upright;
  a polyglot (image plus trailing payload) loses the payload.
- Logo regression: the existing `organisations` validator tests pass unchanged.
- Form: a rolled-back save keeps the old file (`django_capture_on_commit_callbacks`); an invalid
  file leaves the database unchanged and the rendered header shows the saved name and picture.
- Receiver: a rolled-back user delete keeps the file; a queryset delete removes it.
- Storage: the pathless binding passes. The deployment test fixtures are updated in place:
  `PRODUCTION_ENV` in `freedom_ls/deployment/tests/helpers.py` gains
  `AWS_S3_PROFILE_PICTURES_BUCKET_NAME`, `EXPECTED_ALIASES` and the alias parametrisations in
  `deployment/tests/test_storage.py` and `test_checks.py` gain `profile_pictures`.
- Avatars: each surface in the table renders the `<img>` for a user with a picture and initials for
  one without (never `src="None"`), with no extra query per row (`django_assert_max_num_queries`).
- Browser (Playwright): a picture whose file is missing shows initials, not a broken image; upload,
  replace and remove on the account page.

## Documentation and downstream

- Downstream projects get the migration and must set `AWS_S3_PROFILE_PICTURES_BUCKET_NAME` before
  deploying. The upgrade notes say so.

## Success criteria

- A user uploads a JPEG, PNG or WebP on the account page and sees it in the header, messaging and
  educator views; the stored object is a 400×400 WebP with no EXIF.
- A rejected file shows its named error and changes nothing on the account.
- After a replace, a remove or a user delete, no superseded object remains in storage.
- A missing or expired picture shows initials, never a broken image.
