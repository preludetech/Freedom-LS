## 1. Where the initials avatar renders today

`User.initials` is computed in `freedom_ls/accounts/models.py` (`User.initials`, uses
`freedom_ls/base/initials.py` `two_or_one`): both names -> first letters; one name token -> first
two letters (or first letters of two tokens); else first two alphabetic chars of the email local
part; else `None` (caller shows a `user` icon). Diacritics kept, NFC-normalised, non-Latin gives one
grapheme. `User.display_name` (via `display_name_for`) = both names, either, or email.

A second, separate derivation exists: the `initials` filter in
`freedom_ls/panel_framework/templatetags/panel_tags.py` (`initials(name)`, first and last words of a
name string, uppercased). `panel-avatar-chip` uses `{% firstof initials name|initials %}`, so the
chip only uses `User.initials` when a caller passes `:initials=`. Most callers do not, so the chip's
monogram can differ from the header's. `avatar_slot(user_id)` in the same file picks one of six
colour classes `panel-avatar-1..6` (accepts int, str or UUID).

Components (shared, in the package being extracted):
- `freedom_ls/panel_framework/templates/cotton/panel-avatar-chip.html`: `<c-vars name user_id initials secondary size name_hidden>`, sizes `sm` (size-6), `md` (size-8), `lg` (size-13). The circle is `aria-hidden`; the visible name is the accessible name. With `name_hidden` there is NO visible name at all (messaging uses this), so the avatar is the only mark of who. Tests: `freedom_ls/panel_framework/tests/components/test_avatar_chip.py`, `tests/templatetags/test_panel_tags.py`, `tests/components/test_attention_list.py`.
- `freedom_ls/panel_framework/templates/cotton/panel-person-link.html` wraps the chip (props `name`, `user_id`, `secondary`, `href`, `quick_view_url`, `hx_nav`).
- Documented in `claude_plugins/fls-dev/skills/panel-framework/SKILL.md` (lines ~37, 83) and shown in `panel_framework/templates/panel_framework/reference/_examples.html` (~120-128).

Constraints this creates for a shared picture-or-initials render:
- The panel framework is being extracted as `django-panel-framework` and must not import FLS
  (`spec_dd/1. next/roadmap.md`, "Panel framework extraction"; `extract_panels_framework-1-gather-generic-code` is in progress, and its start commit is HEAD~2). A picture lookup (`user.profile_picture.url`, a storage call) cannot live inside the chip. The chip would take a plain value, e.g. `picture_url`, and the callers (FLS templates / a templatetag in an FLS app) compute it. Any change to `panel-avatar-chip.html` or `panel-person-link.html` must rebase onto that effort.
- Callers pass strings and ids, not users. The audit log passes only `user_pk`; the cohort report passes a learner id; the attention row passes only `user_id`. Each needs either a User (with `select_related`/`prefetch_related` to avoid N+1 per CLAUDE.md) or a precomputed URL, and generating a signed URL is a per-row storage call (CPU only for S3, no network, but not free; on a 50-row table it is 50 signatures).
- The header menu does not use the chip; it is a separate inline span, so it is a different edit from the chip edit. `_shell.html`'s sidebar chip also passes `:initials="request.user.initials"` (the only chip callers that do).
- Neutral circle for `other=None` ("Deleted user") is a separate branch in `participant_avatar.html` and `audit_person.html`; both are untouched by this work.
- The initials colour slot (`avatar_slot`) is keyed on `User.pk` so a person has one colour across interfaces (comment in `data-table-cells/learner.html`). A picture should preserve that for the fallback.

Other `initials` uses that are NOT user avatars (out of scope): `organisation-mark.html`, `course_organisation_chip.html` (`Organisation.initials`), `organisation_switcher.html`, `reports/gather.py`.

## 3. Storage mechanics

`freedom_ls/base/storage.py`: single function `storage_for_alias(alias: str, setting_name: str) -> Storage`: `storages[alias]`, converting `InvalidStorageError` to `ImproperlyConfigured` naming the alias and setting. Tests: `freedom_ls/base/tests/test_storage.py`.

Model pattern (follow exactly): a module callable named by `storage=`, e.g.
- `organisations/models.py`: `get_organisation_logo_storage()` -> `storage_for_alias(config.ORGANISATION_LOGO_STORAGE_ALIAS, "ORGANISATION_LOGO_STORAGE_ALIAS")` (alias name from a setting declared in `organisations/config.py`).
- `form_engine/models.py` (line ~738): `get_user_uploads_storage()` -> `storage_for_alias("user_uploads", "STORAGES['user_uploads']")` (fixed alias name, no setting).
- `reports/models.py` line 39: `get_reports_storage()` -> `config.REPORTS_STORAGE_ALIAS`.

`freedom_ls/deployment/storage.py`:
- `FIXED_ALIAS_PURPOSES = {"user_uploads": "USER_UPLOADS", "certificates": "CERTIFICATES"}`; the logo, course-media and reports aliases come in as arguments to `media_alias_purposes(logo_alias=, content_media_alias=, reports_alias=)` and `build_storages(...)`. A new alias is added either to `FIXED_ALIAS_PURPOSES` (fixed name) or as a fourth named argument threaded through `media_alias_purposes`, `build_storages` and `config/settings_prod.py` line 150 (`STORAGES = build_storages(staticfiles=..., logo_alias=ORGANISATION_LOGO_STORAGE_ALIAS, content_media_alias=..., reports_alias=...)`).
- Purpose constants: `LOGO_PURPOSE="PUBLIC"`, `CONTENT_MEDIA_PURPOSE="COURSE_MEDIA"`, `USER_UPLOADS_PURPOSE="USER_UPLOADS"`, `CERTIFICATES_PURPOSE`, `REPORTS_PURPOSE="GENERATED"`, `DEFAULT_PURPOSE`. A new alias needs its own purpose string, because env var names derive from it (`AWS_S3_{PURPOSE}_BUCKET_NAME`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY`, `_ENDPOINT_URL`, `_REGION_NAME`, `_CUSTOM_DOMAIN`, `_QUERYSTRING_AUTH`, `_QUERYSTRING_EXPIRE`), each falling back to the shared `AWS_*` var. **Open question for the spec:** a new purpose gets its own bucket-name env var, but falls back to the shared `AWS_STORAGE_BUCKET_NAME`. To place profile pictures in the *same* user-data bucket as `reports`/`user_uploads`, the deployment must set the same bucket name for the new purpose (see `bucket_name_for`, which returns `(name, from_shared)`; a check elsewhere distinguishes an alias that named its own bucket from one that inherited; look at the deployment checks and `freedom_ls/deployment/tests/test_storage.py`, 40 tests, and the `docs/deployment*` docs when writing the spec).
- `SIGNED_URL_PURPOSES = frozenset({COURSE_MEDIA, USER_UPLOADS, REPORTS})` -- "purposes whose objects must never be reachable without a signature". A new purpose must be added here for the private bucket to be enforced (a check uses it).
- `_OBJECT_PARAMETERS` (CacheControl only for PUBLIC `public, max-age=86400` and CERTIFICATES `public, max-age=31536000, immutable`); private purposes get none.
- `_OVERWRITE_PURPOSES = frozenset({LOGO_PURPOSE})`. The idea says do not reuse an existing purpose for its overwrite behaviour. `_alias_entry` always writes `file_overwrite` in S3 options; local-disk entries get `{"allow_overwrite": True}` only for overwrite purposes. A profile picture on a no-overwrite alias needs a uuid-derived or otherwise unique key; replacing writes a new key and the old object is swept (as `QuestionAnswerFile.save()` does).
- Signed URL defaults: `_alias_entry` -> `querystring_auth=env_bool("AWS_S3_{PURPOSE}_QUERYSTRING_AUTH" / "AWS_QUERYSTRING_AUTH", True)` and `querystring_expire=env_int("..._QUERYSTRING_EXPIRE" / "AWS_QUERYSTRING_EXPIRE", 3600)`; i.e. signed, expiring after **3600 s (1 hour)** by default for any private alias. Signed URLs are per-request, change on every render, so they cannot be cached by the browser across page loads (the signature differs) and a cached page or a long-lived tab outlives the URL. `signature_version="s3v4"`, optional `custom_domain`. On local disk (dev/test) `.url()` returns `MEDIA_URL`-relative path, served by `config/urls.py` line 98 `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)` when DEBUG (so in dev the picture is served unsigned from MEDIA_ROOT; the spec should say what test proves signing).
- `build_s3_media_storage(...)` handles R2 specifics (no ACLs, checksum config, region "auto").

`config/settings_base.py` (lines 286-322): `MEDIA_URL = "media/"`, `MEDIA_ROOT = BASE_DIR / "media"`; settings `ORGANISATION_LOGO_STORAGE_ALIAS = "public"`, `CONTENT_MEDIA_STORAGE_ALIAS = "course_media"`, `REPORTS_STORAGE_ALIAS = "reports"`; `STORAGES` dict has `default`, `staticfiles`, the three named aliases, `"user_uploads"`, `"certificates"`, each `FileSystemStorage` (logo alias with `allow_overwrite`). A new alias must be added here (dev, test, non-prod) AND in `build_storages()` (prod via `config/settings_prod.py`). Tests double: `freedom_ls/tests/storages.py` `PathlessFileSystemStorage` (refuses `.path()` like S3) and `bind_pathless_logo_storage` (hard-wired to `Organisation` logo fields; a User-picture equivalent or a generalisation is needed to prove no `.path()` use). Note the comment there: swapping `settings.STORAGES` cannot rebind a field's storage, because Django resolves the callable once at model import.

`claude_plugins/fls-dev/skills/file-storage/SKILL.md`:
- Three buckets; user-data bucket "Holds: Cohort reports, user uploads, profile pictures. Read policy: Private, signed URLs or streamed by Django. Personal data: Yes".
- Six aliases table: `public`, `certificates`, `course_media`, `reports`(`cohort_reports/`), `user_uploads`(`user_uploads/`, consumer "None yet" -- stale, `QuestionAnswerFile.file` now uses it), `default`. **There is no profile-picture alias row**, and the skill says "six aliases" - adding one updates the skill, the table and "six".
- Choosing: "readable without logging in?" decides the bucket. Anonymous viewers on the public profile conflicts with a private bucket unless the page renders a signed URL (the decision in `answers.md`).
- Namespace `upload_to`: aliases in the same bucket must produce disjoint keys; "Give every upload_to a prefix scoped to its own alias". `reports` -> `cohort_reports/`, `user_uploads` -> `user_uploads/`; a new alias in the user-data bucket needs a prefix such as `profile_pictures/` that neither can produce.
- **User prefix rule:** "Every object under `user_uploads/` must be prefixed by the uploading user, so a right-to-erasure request becomes a scoped delete". Existing pattern: `form_engine/models.py` `question_answer_file_upload_to` -> `user_uploads/{user_id}/form_answers/{pk}{ext}` (or `user_uploads/anonymous/{form_progress.pk}/...`). A profile-picture key would follow it, e.g. `<prefix>/{user_pk}/...`. The skill's rule is written for `user_uploads/`; the idea (`What is settled`) extends the same principle to the new alias. User pk is an integer so is guessable, but the bucket is private and signed, so guessing is harmless. The idea's "found and erased with the user" implies a per-user prefix, not only a row-driven delete.
- Overwrite section: a stable key whose extension can change needs `save()` to delete the superseded object (pattern in `Organisation.save()` and `QuestionAnswerFile.save()`).

## 4. Existing save/delete patterns for stored files (what to copy)

- `Organisation.save()` (`organisations/models.py` ~line 142): read stored names from `_base_manager` BEFORE saving (`_stored_logo_names`), save, then `storage.delete(previous)` for each field whose name changed. `LOGO_FIELD_NAMES` tuple.
- `QuestionAnswerFile.save()` (`form_engine/models.py` ~line 784): same via `_stored_file_name()` using `QuestionAnswerFile._base_manager`. `_base_manager` is used because `objects` filters by the request's site.
- Row-delete cleanup: `reports/signals.py` `delete_report_file` (`post_delete`, `instance.file.delete(save=False)`, connected in `ReportsConfig.ready()`), and `course_applications/receivers.py` has a `post_delete` receiver sweeping `QuestionAnswerFile` storage. Both rely on a signal because `QuerySet.delete()`/cascades bypass model `delete()`.
- For a `User`: a `post_delete` receiver on `User` is needed to erase the picture when the user is deleted (Django does not delete files automatically). A cascade delete (queryset delete) also fires `post_delete` per instance, so a receiver works; a model `delete()` override would not. `course_applications/receivers.py` already registers `@receiver(pre_delete, sender=User)` (`erase_unclaimed_applicants_with_the_users_address`), the closest precedent for user-erasure hooks.
- Note: `User.delete()` is blocked by `Learner.user` PROTECT for users with a `Learner` row (`.claude/agent-memory/sdd-qa-data-helper/reference_dashboard_paging_fixture_teardown.md`), so erasure of a learner is a manual operator step.

## 5. User deletion and deactivation today

- No erasure workflow. `docs/product/roadmap.md` line ~115 and `docs/product/security-and-data-handling.md`: "no retention policy, scheduled deletion, subject-access-request tooling, right-to-erasure workflow ... User deletion is a manual admin or database operation." A user's picture file must go with the row (a `post_delete` receiver) because there is no other erasure code. Audit and message text is deliberately retained; "Deleted users stay named" in the audit log (`security-and-data-handling.md` line ~197); messages "show sender as a deleted user" (line ~215). So after deletion the picture must not remain in those views (they show the neutral circle already).
- Deactivation: `User.is_active`; "deactivate" and "inactive" are reserved vocabulary (`Learner.is_active`, `StaffMember.is_active`). Grep of `freedom_ls/comms` for `is_active` returned nothing: messaging participants, audit rows and educator tables render a deactivated user exactly like an active one today (no dimming, no different avatar). So "keep their picture" (answers.md) = no new code path, only do not hide it.
- Missing file: nothing in the codebase renders a missing stored file gracefully for users; organisation logo reads go through `check_logo_safety` (reports) and `organisation-mark.html` (`freedom_ls/learner_interface/templates/cotton/organisation-mark.html`) which picks logo, else initials monogram (`organisation.initials`), else generic icon. This is the nearest pattern for picture -> initials -> icon fallback, with tests in `learner_interface/tests/components/test_organisation_mark.py` (initials hidden from assistive technology without a logo) and `learner_interface/tests/views/test_course_player.py` ~3890-3936. A missing-file case in S3 only shows at image load time (browser 404/403), so the template needs an `onerror` fallback or an `exists()` check (a network call per render; avoid) -- spec decision.

## 6. Upload validation and image helpers

`freedom_ls/organisations/validators.py` (the pattern to follow):
- Constants: `ALLOWED_EXTENSIONS = ["png","jpg","jpeg","webp"]`, `ALLOWED_FORMATS = {"PNG","JPEG","WEBP"}`, `MAX_BYTES = 2 MiB`, `MAX_DIMENSION = 4000` each axis, `MIN_WIDTH, MIN_HEIGHT = 64, 32`, `LOGO_MIME_TYPES` (format -> mediatype), `validate_organisation_logo_extension = FileExtensionValidator(ALLOWED_EXTENSIONS)`.
- `SafeLogo` frozen dataclass (`mime_type`, `width`, `height`); `check_logo_safety(raw: bytes) -> SafeLogo` raises `ValidationError` on: oversize bytes; `Image.open(...).verify()` then re-open (verify consumes the object); bomb failures (`BOMB_FAILURES`) -> "Image is too large to process safely."; `DECODE_FAILURES` -> "File is not a readable image."; format not allowed; either dimension > 4000. Runs inside `bomb_warnings_as_errors(), truncated_images_rejected()`.
- `validate_organisation_logo(file: UploadedFile)`: checks `file.size` first, reads at most `MAX_BYTES + 1`, calls `check_logo_safety`, `finally: file.seek(0)`, then the minimum-dimension rule (64x32).
- The docstring says EXIF is deliberately NOT stripped for logos ("the usual motivation for stripping -- location metadata in personal photos -- does not apply to an admin-uploaded corporate logo"). A personal photo is exactly that case: GPS in EXIF would be publicly shown on the later public profile. The spec must decide to re-encode (which drops EXIF unless carried) rather than reuse that validator unchanged. Messages are hard-coded to logo wording ("PNG, JPEG or WebP", "maximum is 2MB", "minimum is 64x32px"), the validator names say "logo", and the minimum 64x32 allows non-square, so a reusable generic function would need extraction or a new module (CLAUDE.md: avoid repeating code; but "Any change to Organisation logos" is out of scope, so factoring `check_logo_safety` out must leave logo behaviour identical).
- `check_logo_safety` also has a second caller: the report pipeline reads a stored logo back through it (docstring: field validators only run under `full_clean()`). A `ModelForm.save()` always runs `full_clean`, but `QuerySet`/shell/admin paths may not; for a picture the read side matters less (browser renders it) but a stored file path that bypasses validation could exist via the Django admin.

`freedom_ls/base/images.py`: `DECODE_FAILURES = (OSError, Image.UnidentifiedImageError, SyntaxError, ValueError, struct.error, IndexError)`, `BOMB_FAILURES = (DecompressionBombWarning, DecompressionBombError)`, context managers `bomb_warnings_as_errors()` (escalates the warning band past `Image.MAX_IMAGE_PIXELS`, ~89M pixels) and `truncated_images_rejected()` (holds `ImageFile.LOAD_TRUNCATED_IMAGES` False; WeasyPrint sets it True process-wide after the first report render, so this guard is needed on the upload path). Tests: `freedom_ls/base/tests/` (look for `test_images.py`).

`freedom_ls/content_engine/images.py` `optimise_image(raw: bytes, suffix: str) -> ImageEncodeDecision`: pure bytes-in, bytes-out, never raises; SVG suffix passthrough; `MAX_DIMENSION_PX = 1600` longest edge via `img.thumbnail(..., LANCZOS)`; lossy quality `LOSSY_QUALITY = 80` (lossy first, lossless candidate if smaller / when transparent, never grow); applies `ImageOps.exif_transpose` (orientation) and carries the ICC profile; `opened.draft(...)` to cut decode memory; keeps the source on "never grow" (`ImageEncodeStatus.KEPT_SOURCE`) -- **which stores original bytes, including EXIF**. It is for author-supplied files and deliberately lets the bomb warning band decode ("legitimate 90-179 MP photo"), the opposite of what an untrusted upload wants. So: reuse of `optimise_image` is not safe as-is (could return the original with EXIF; band policy differs; 1600 px is large for an avatar). The Pillow primitives (`ImageOps.exif_transpose`, `Image.thumbnail`, `ImageOps.fit`) are available since `pillow>=11.0` is in `pyproject.toml`; no thumbnail library (no sorl/easy-thumbnails) is installed. Header avatar renders at 40 px, chip at 24/32/52 px, so 128 or 256 px square (2x/3x density) covers every current surface.

## 8. Things to flag for the spec (cross-cutting)

1. File-format: the key must derive the extension from the validated format (not the filename), as `question_answer_file_upload_to` does ("`filename` is the name FLS chose after sniffing the content").
2. Private bucket + anonymous viewers (answers.md): the later public-profile page will render signed URLs for users who are not logged in; a page cached by a CDN would carry an expired signature. Default expiry 3600 s, per-purpose env var `AWS_S3_<PURPOSE>_QUERYSTRING_EXPIRE`. The messaging/educator surfaces are logged-in only.
3. Site scoping: `User.objects` is site-filtered via the request thread local; `_base_manager` is used by existing sweep code for exactly that reason. The picture sweep in `User.save()`/signals must use the base manager.
4. `User.save()` does not exist as an override (grep: only `accounts/models.py:221`, which belongs to a later model). The user edit path is `ModelForm.save()` on `UserForm`; replacing via form triggers `User.save()`. Alternatives: sweep in the form's `save()` or a `User.save()` override or a dedicated service function.
5. The `# TODO` comment sits inside `class Meta` of `UserForm`; removing it is allowed by the idea. No other TODO is attached to it.
6. Vocabulary: `fls-dev:domain-glossary` / `research_existing_profile_code.md` section 9 notes `profile` is already used for `account_profile`, `Organisation.profile_logo`; "avatar" is not a glossary term (it is used only as `panel-avatar-chip`, `participant_avatar.html`, `avatar_slot`). Naming a `User` field `profile_picture` echoes `profile_logo` and the account profile page; the spec should decide and define once.
7. A migration for the new `User` field goes in `freedom_ls/accounts/migrations/`; the user model is custom and swappable (`AUTH_USER_MODEL = "freedom_ls_accounts.User"`), and FLS is installed into other Django projects, so downstream projects get the migration too.
8. Admin: `User` is registered in the Django admin (not read here); the admin form would show the new file field and bypass `edit_profile`; validators attached to the field (as logo's are) run there too.
