# Spec: Registration rules

Spec 2 of 5 in the Registration rules effort. The approach, scope and settled behaviour come from
`idea.md` and the "Registration rules" section of `spec_dd/1. next/roadmap.md`; the
`research_*.md` files beside this spec hold the evidence. This spec does not restate their reasoning.

## Purpose

An organisation admin wants "everyone in Finance in Cape Town is registered for Budgeting Basics" to
stay true as learners join, change department or move, without anyone registering them by hand. This
spec adds registration rules with the `register` outcome, managed in the Django admin, evaluated in
the background, with a preview list before any change applies and a record on every registration a
rule made.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| registration rule (`RegistrationRule`) | coined | A per-organisation rule naming one course, a rule kind, conditions on the HR attributes in `freedom_ls/hr_attributes/models.py` and an outcome. No existing term: nothing in `freedom_ls/` models a rule. |
| rule kind | coined | How a rule decides who matches. One ships: `attribute` (attribute matching). |
| rule-made registration | coined | A `LearnerCourseRegistration` that a `RuleRegistration` row links to a rule. |
| retract | coined | A rule setting `is_active=False` on a rule-made registration because the learner no longer matches. Never a delete. |
| registration source | coined | Who made a registration: rule, learner or staff. Derived, never stored (decision 4). |
| started | narrowed | A `CourseProgress` of that learner and course (`freedom_ls/learner_progress/models.py`) has `started_at` set, `progress_percentage > 0` or `completed_time` set. |

## Scope

In:

- A new optional app, `freedom_ls/registration_rules/`, that depends on `freedom_ls.hr_attributes`.
- `ListEntryQuerySet.for_picker` in `hr_attributes` accepts a set of held pks, not one.
- `RegistrationRule`, its attribute conditions, and `RuleRegistration` (provenance).
- The rule-kind seam, with the `attribute` kind.
- Evaluation as `django.tasks` tasks, triggered by rule changes, learner changes, attribute changes
  and the organisation switch turning on.
- Retraction, reactivation and hand-over between rules.
- Django admin for rules, with a preview page before every change that affects who is registered.
- A site-explicit webhook path so `course.registered` fires from a background task.
- A shared "started" helper in `learner_progress`.
- `danger_content_delete` clearing rules before courses.

Out:

- The attribute models, lists and organisation switch (spec 1, landed).
- The `recommend` outcome and `RecommendedCourse` changes (spec 3).
- Educator-interface screens (spec 4). CSV import (spec 5).
- Rule kinds other than attribute matching, rules that register cohorts, rule-filled cohorts.
- Exclusion conditions, OR across attributes.
- Bulk enable/disable admin actions, and a periodic reconcile job.
- Audit-log entries: `educator-interface-11-audit-log` has not landed.
- Showing the source on the educator-interface learner page: `educator-interface-7` has not landed.

## Decisions

1. **The rules app is optional in `INSTALLED_APPS`.** Decision 1a in the roadmap makes the effort
   optional and says core apps never import it. A system check errors when the rules app is
   installed without `freedom_ls.hr_attributes`.
2. **Provenance lives in the rules app, in a side table, not as a column on
   `LearnerCourseRegistration`.** A FK from `learner_management` to an optional app would make core
   migrations depend on it. `learner_management` gains no field and no migration.
3. **`self_registered` keeps its meaning**: the learner made the row. Rule-made rows have
   `self_registered=False`, so the existing signal sends `course.registered` as for an admin
   registration.
4. **Source is derived, never stored on the registration**: rule if a `RuleRegistration` exists,
   otherwise learner if `self_registered`, otherwise staff.
5. **Deleting a rule keeps the provenance.** `RuleRegistration.rule` is `SET_NULL` and
   `RuleRegistration.rule_name` holds a snapshot of the rule's name, so the row still reads as
   rule-made after the rule is gone.
6. **Any change to `is_active` that the rule engine did not make detaches the registration from its
   rule** (staff in the admin, the learner self-registering again).
7. **"Started" counts any of three fields (Terminology), from whichever registration minted the
   progress record.** Only the course player stamps `started_at`, so progress written by an import or
   `bulk_create` counts through the other two. Erring towards "started" never loses a learner's place.
8. **Evaluation reconciles current state; it never applies a stored diff.** Each run re-reads the
   rule, the switch and the learners, so a stale or repeated task is harmless, and the preview is a
   forecast rather than a contract.
9. **A rule's `organisation` and `course` are read-only after creation.** Changing either would
   silently retract one group and register another; staff disable the rule and create a new one.
10. **Ownership of a registration passes to another rule when its owner lets go.** If another
    enabled rule matches the same learner and course, the `RuleRegistration` is re-pointed at it.
11. **Registration webhooks fire wherever the registration is created.** `_ensure_and_announce` uses
    the site-explicit webhook function with `registration.site_id`, so `course.registered` now also
    fires for registrations created in tasks and management commands, not only in requests.
12. **A rule never deletes a registration and never makes a second one for the same learner and
    course**, so a learner whose attributes flap keeps their `CourseProgress`
    (`spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/research_enrolment_bound_progress_lifecycle.md`
    §3).
13. **A rule registers whatever the course's access type or visibility**, as a staff registration
    in the admin does; `get_course_access_backend()` gates only self-registration. The rule admin
    warns when the course is not `CourseVisibility.PUBLISHED` (`freedom_ls/content_engine/models/courses.py`),
    and evaluation still runs.

### Models (`freedom_ls/registration_rules/models.py`)

`RegistrationRule(SiteAwareModel, TimestampedModel)`:

| Field | Type |
| --- | --- |
| `organisation` | FK `freedom_ls_organisations.Organisation`, PROTECT, `related_name="registration_rules"` |
| `course` | FK `freedom_ls_content_engine.Course`, PROTECT, `related_name="registration_rules"` |
| `name` | `CharField(200)` |
| `kind` | `CharField`, a key of `REGISTRATION_RULE_KINDS`, default `"attribute"` |
| `outcome` | `CharField(choices=RegistrationRule.Outcome.choices)`, one choice `REGISTER = "register"`, default `register` |
| `is_enabled` | `BooleanField(default=False)` |
| `last_evaluated_at` | `DateTimeField(null=True)`, set when an `evaluate_rule` run finishes, to the time it started |

`last_evaluated_at` is written with `QuerySet.update()`, so it does not move `updated_at`. An
enabled rule whose `last_evaluated_at` is null or older than `updated_at` has a change that no run
has applied yet, because the task is still queued or failed.

`AttributeRuleConditions(SiteAwareModel)`, owned by the `attribute` kind, one-to-one on the rule
(`rule`, CASCADE, `related_name="attribute_conditions"`):

- `job_titles`, `departments`, `locations`: M2M to `freedom_ls_hr_attributes.JobTitle`,
  `Department`, `Location`, blank, each with `related_name="registration_rule_conditions"`. An
  empty set leaves that attribute unconstrained.
- Eight nullable `DateField`s, a pair per start date on `LearnerHRAttributes`:
  `organisation_start_on_or_after` / `organisation_start_before`, and the same for `job_title_`,
  `department_` and `location_`.
- `clean()`: every picked entry belongs to `rule.organisation`; where both bounds of a pair are set,
  `…_before` is later than `…_on_or_after`.

`RuleRegistration(SiteAwareModel)`:

| Field | Type |
| --- | --- |
| `registration` | OneToOne `freedom_ls_learner_management.LearnerCourseRegistration`, CASCADE, `related_name="rule_registration"` |
| `rule` | FK `RegistrationRule`, SET_NULL, null, `related_name="rule_registrations"` |
| `rule_name` | `CharField(200)`, the rule's name when the row was last pointed at a rule |
| `is_retracted` | `BooleanField(default=False)`, true while a rule has the registration deactivated |

A `RuleRegistration` exists only for a registration a rule created. A rule never creates one for a
registration that already existed.

### Rule-kind seam (`freedom_ls/registration_rules/kinds.py`, `loader.py`)

- `loader.get_rule_kind(key: str)` resolves `REGISTRATION_RULE_KINDS[key]` with `import_string`,
  cached with `functools.cache` like `course_access/loader.py`, and raises `ImproperlyConfigured`
  for an unknown key. An autouse fixture in `freedom_ls/conftest.py` clears the cache, beside
  `_clear_course_access_backend_cache`; it imports the loader only when
  `apps.is_installed("freedom_ls.registration_rules")`, so the suite runs with the app removed.
- A kind is a plain class (no ABC) with one query method used by evaluation and preview alike,
  `matching_learners(state: RuleState) -> QuerySet[Learner]`, and two builders for its
  conditions value: `conditions_from_rule(rule)` and `conditions_from_cleaned_data(cleaned)`.
- `RuleState` is a frozen dataclass: `site_id`, `organisation_id`, `course_id`, `is_enabled`, and
  `conditions` (kind-specific; for the `attribute` kind a frozen dataclass `AttributeConditions`,
  the value counterpart of the `AttributeRuleConditions` model). It is built from a saved rule
  (`RuleState.from_rule(rule)`) or from the admin's validated, unsaved form data, so preview and
  evaluation run the same query.
- `AttributeRuleKind.matching_learners` returns `Learner` rows with `site_id`, `organisation_id` and
  `is_active=True` filtered explicitly (no ambient site in a task), joined through
  `hr_attributes`: `__in` within an attribute, AND across attributes, `__gte` for "on or after",
  `__lt` for "before". A learner with no `LearnerHRAttributes` row, or a null date, does not match a
  condition on it. A rule with no conditions matches every active learner in the organisation.
  When `is_enabled` is false the result is empty.

### Started (`freedom_ls/learner_progress/`)

- Add `started_course_exists(learner: OuterRef | UUID, course: OuterRef | UUID) -> Exists`
  (or an equivalent queryset helper) to `learner_progress`: true when the learner has started the
  course (Terminology, decision 7). Spec 3 reuses it. It is used inside the retraction
  `UPDATE` filter so a learner who starts between the read and the write is not retracted.

### Evaluation (`freedom_ls/registration_rules/evaluation.py`, `tasks.py`)

Functions, each taking explicit ids and reading through `_base_manager` or site-filtered querysets:

- `evaluate_rule(rule_id, site_id) -> EvaluationResult`
- `evaluate_learner(learner_id, site_id) -> EvaluationResult`
- `evaluate_organisation(organisation_id, site_id) -> EvaluationResult`

`EvaluationResult` is a frozen dataclass of the learner ids registered, reactivated and retracted.
The reconcile below is split into a read, `classify_rule_changes(rule, state, learner_ids) ->
RuleChanges` (frozen: `register`, `reactivate`, `retract`, `hand_over`, `kept_started`), and a
write, `apply_rule_changes(rule, changes) -> EvaluationResult`; the preview runs the read alone.
Tasks in `tasks.py` are thin `@task()` wrappers, `evaluate_rule_task`, `evaluate_learner_task`
and `evaluate_organisation_task`, with `str`/`int` arguments (UUIDs as strings), enqueued with
`transaction.on_commit(partial(task.enqueue, ...))`.

Every evaluation first reads `OrganisationHRSettings` for the organisation through
`rules_enabled_for(organisation_id) -> bool`; with no row or `registration_rules_enabled=False` it
returns an empty result and changes nothing. The admin reads the same function for its warnings.

For a rule R on course C and the learners in scope, the reconcile is:

1. **Register.** A matching learner with no `LearnerCourseRegistration` for C gets one, created with
   `save()` (`self_registered=False`, `is_active=True`) plus a `RuleRegistration(rule=R)`, both
   with `site_id` passed explicitly because a task has no request to fill it from, so the existing `post_save` mints the progress record and raises `course.registered`. A unique-constraint
   race on `unique_learner_course_registration` counts as "already registered": no takeover.
2. **Reactivate.** A matching learner whose registration for C has a `RuleRegistration` with
   `is_retracted=True` is reactivated by `QuerySet.update(is_active=True)`; the `RuleRegistration`
   gets `rule=R`, `rule_name=R.name`, `is_retracted=False`. No notification is sent.
3. **Leave alone.** A registration for C with no `RuleRegistration`, active or not, is never
   touched.
4. **Retract.** An active registration whose `RuleRegistration.rule` is R, for a learner who no
   longer matches R:
   - another enabled rule on C in the learner's current organisation, whose switch is on, matches →
     hand over (decision 10). For a learner who moved, that is a rule of the new organisation;
   - otherwise, if not started → `update(is_active=False)` and `is_retracted=True`;
   - otherwise → leave it active.
   Registrations whose rule was deleted (`rule` null) are never retracted.

The engine changes `is_active` on existing registrations only with `QuerySet.update()`, never
`save()`, which is what lets the detach receiver below tell its writes from anyone else's.

Scope of each function:

- `evaluate_rule`: every learner R matches plus every registration R owns, in batches of
  `REGISTRATION_RULE_BATCH_SIZE` learners ordered by pk. Each batch is its own transaction: it locks
  the rule with `select_for_update()`, re-reads the rule, its conditions and the organisation
  switch, and stops the run if the switch went off. A rule disabled mid-run is retracted by the
  remaining batches rather than registered. When the last batch commits, set `last_evaluated_at`
  to the run's start time, so an edit made during the run still reads as unapplied.
- `evaluate_learner`: every enabled rule of the learner's current organisation, plus every
  registration of the learner that any rule owns (so a learner who moved organisation or was
  removed is retracted from the old organisation's rules). Lock the `Learner` row. A learner that
  no longer exists gives an empty result.
- `evaluate_organisation`: every rule of the organisation, enabled or not, so disabled rules'
  registrations are retracted on catch-up. It runs `evaluate_rule` per rule.

Lock order is fixed so a rule sweep and a learner evaluation cannot deadlock: `evaluate_learner`
locks only the `Learner` row, `evaluate_rule` only the rule row, and both write registrations in
learner-pk order. Both locks are `select_for_update(no_key=True)`: the foreign key checks on the
rows each run inserts take a key-share lock on the other run's locked row, which a plain
`FOR UPDATE` would block.

### Triggers (`freedom_ls/registration_rules/signals.py`)

| Event | Enqueues |
| --- | --- |
| `RegistrationRule` saved (after the admin confirm), its `AttributeRuleConditions` saved, or `m2m_changed` on one of the three condition M2Ms | `evaluate_rule` |
| `Learner` `post_save` (creation, organisation change, `is_active` change) | `evaluate_learner` |
| `LearnerHRAttributes` `post_save` or `post_delete` | `evaluate_learner` |
| `OrganisationHRSettings` `post_save` with `registration_rules_enabled=True` | `evaluate_organisation` |

Duplicate enqueues are harmless (decision 8), but each task is enqueued once per transaction: one
admin save fires the rule, its conditions and every picker change. A conditions save or picker
change also moves the rule's `updated_at`, so an edit made outside the admin reads as unapplied.
Learner and HR attribute saves enqueue only when the learner's organisation has rules and its
switch on, or a rule owns one of the learner's registrations. Every receiver skips `raw=True` saves (`loaddata`),
as the existing registration receiver does. Paths that bypass signals (`QuerySet.update()`, `bulk_create`)
trigger nothing; spec 5 enqueues one evaluation per import itself.

**Entry protection.** A `pre_delete` receiver on `JobTitle`, `Department` and `Location` raises
`ProtectedError` while any rule's conditions name the entry: the cascade to the picker's through row
sends no `m2m_changed`, and the emptied picker would widen the rule to the whole organisation.
The rules admin extends `ListEntryAdmin.get_deleted_objects` so the delete page lists those rules as
protected. Deactivating the entry is how it is retired.

**Detach receiver.** A `pre_save` receiver on `LearnerCourseRegistration`: when an existing row with
a `RuleRegistration` is saved with an `is_active` different from the stored value, delete its
`RuleRegistration` (decision 6).

### Webhooks (`freedom_ls/webhooks/events.py`, `freedom_ls/learner_progress/signals.py`)

- Split `fire_webhook_event` (line 10): new `fire_webhook_event_for_site(event_type, payload,
  site_id)` validates, creates the `WebhookEvent` and enqueues `_dispatch_event_task`.
  `fire_webhook_event` keeps resolving the site from the request and calls it.
- `_ensure_and_announce` calls `fire_webhook_event_for_site(..., registration.site_id)` (decision 11).

### Admin (`freedom_ls/registration_rules/admin.py`)

`RegistrationRuleAdmin(SiteAwareModelAdmin)`:

- `list_display`: `name`, `organisation`, `course`, `is_enabled`, `last_evaluated_at`, and two
  boolean columns, "Uses inactive entries" and "Change not yet applied" (enabled, and
  `last_evaluated_at` null or older than `updated_at`). `list_filter`: `organisation`, `is_enabled`,
  `course`.
- The change form shows a warning when the course is not published (decision 13) and when the
  rule's last change has not been applied. That warning names the cause it can see: the
  organisation's switch is off, or otherwise the task is queued or failed and the task worker
  needs checking.
- Creating a rule takes two steps. The add page takes `name`, `organisation` and `course` and has no
  conditions inline; saving it leaves the rule disabled and opens the change page.
- `AttributeRuleConditions` as an unfold `StackedInline` on the change page only, `max_num=1`. The
  three M2M pickers offer the active entries of the rule's organisation plus the entries already
  selected (`for_picker` with the selected pks); selected inactive entries show " (inactive)" (from
  the list models' `__str__`) and the change form shows a warning naming them.
- `organisation` and `course` are read-only on the change page (decision 9).
- Delete is refused while a rule is enabled, on the change page (`has_delete_permission`) and in the
  bulk delete action (enabled rules are listed as protected and not deleted). Deleting writes the
  rule's name to `rule_name` on its `RuleRegistration` rows first.

**Preview page.** When the change form is submitted and the rule is enabled before or after the save
(editing an enabled rule, enabling, disabling), the admin validates the form
and inline, saves nothing, and renders a confirmation page inside the admin shell
(`admin_page_context`) with:

- "Will be registered": the learners the change would register (new and reactivated), and
- "Will be retracted": the learners it would retract,

each as a full list of learner name and email, with counts in the headings. A learner whose
retraction is blocked is not in the retract list; a third list, "Stops matching but stays
registered", shows them with the reason: started the course, or still matched by another enabled
rule (named). If the
organisation's switch is off, the page says nothing will change until it is switched on, and shows
the lists as they would apply then. The preview runs inside `changeform_view`, behind its
permission checks. The confirmation page re-emits every POSTed key as a hidden input, inline
management-form data included, plus a `_confirmed` flag; Confirm posts them back and the save
proceeds through the normal admin path. Cancel returns to the unsaved form. The lists come from the
same kind query and reconcile rules as evaluation, run in dry-run mode against `RuleState`s built
from the stored and the submitted rule. Saving a rule that is disabled and stays disabled shows no
preview: the idea's "edited" means an edit that can change who is registered, and a disabled rule
registers nobody.

`RuleRegistrationAdmin` is not registered. Instead, the rules app adds a read-only "Registration rule"
field to `LearnerCourseRegistrationAdmin` at import time, appending it to the admin's `fieldsets`
and `readonly_fields`. It shows the rule's name (linked) or `rule_name` with "(deleted)", and is
blank on the add form and for registrations with no `rule_registration`.

### Dev tools (`freedom_ls/dev_tools/management/commands/danger_content_delete.py`)

`RegistrationRule.course` is `PROTECT`, so the course delete fails while a rule exists. When
`apps.is_installed("freedom_ls.registration_rules")`, append
`("freedom_ls_registration_rules", "RegistrationRule")` to `deletion_order` after the registrations,
fetched through the app registry, as `course_applications` is, but appended rather than inserted at
0. Conditions cascade from the rule;
`RuleRegistration` rows have already cascaded from their registrations.

## Testing

Unit and integration tests under `freedom_ls/registration_rules/tests/`, with a `conftest.py`
copied from `freedom_ls/hr_attributes/tests/conftest.py` (`app_not_installed` guard). Factories for
the three models in `freedom_ls/registration_rules/factories.py`.

To prove:

- Matching: AND across attributes, OR within; each start-date bound at, before and after its date;
  null dates and missing `LearnerHRAttributes` never match a date or entry condition; a rule with no
  conditions matches all active learners in the organisation and none in another; inactive learners
  never match; an inactive entry in a condition still matches.
- Admin: the add page has no conditions inline and saves a disabled rule; pickers offer active
  entries plus every selected inactive one (`for_picker` with several held pks); the warning names
  inactive entries; an entry from another organisation fails `clean()`; inverted date bounds fail;
  the "Registration rule" field renders on the registration change form and is blank on its add
  form.
- Register: creates the registration and `RuleRegistration`, `self_registered=False`, progress record
  minted, `course.registered` notification raised.
- No takeover: an existing staff-made or self-registered row, active or inactive, is untouched and
  gains no `RuleRegistration`.
- Retract: an unstarted learner who stops matching is deactivated with `is_retracted=True`; a started
  one is left active, for each of `started_at`, `progress_percentage > 0` and `completed_time` alone,
  and through a cohort-minted `CourseProgress`; progress rows survive.
- Flapping: retract then reactivate leaves the learner on the same registration and the same
  `CourseProgress` pk, with progress unchanged.
- Batching: with `REGISTRATION_RULE_BATCH_SIZE` set below the learner count, a run reaches every
  learner; a rule disabled between batches registers nobody in the later batches; the switch turned
  off between batches stops the run. `last_evaluated_at` is set only when the run finishes and does
  not change `updated_at`.
- Hand-over: two enabled rules on one course, disable the owner, the row stays active and points at
  the other rule; disable that one too and the row is retracted.
- Reactivate: a retracted learner who matches again is reactivated with no new notification; a
  staff-deactivated row is never reactivated.
- Detach: staff deactivating or reactivating a rule-made row in the admin, and a learner
  self-registering on a retracted row, deletes the `RuleRegistration`; the next evaluation leaves the
  row alone.
- Rule deletion: refused while enabled; once disabled and deleted, surviving rows keep `rule_name`
  with `rule=None` and are never retracted.
- Switch: with the switch off nothing changes on any trigger; turning it on runs
  `evaluate_organisation`, which applies the registrations and retractions that attribute and
  rule changes made while it was off would have caused.
- Triggers: each event in the trigger table enqueues the right task after commit
  (`django_capture_on_commit_callbacks`), including a condition M2M changed outside the admin;
  `loaddata` enqueues nothing; deleting a learner (cascading its `LearnerHRAttributes`) leaves an
  `evaluate_learner` that returns an empty result.
- Tasks run with no thread-local request and no `mock_site_context`, against two sites, and touch
  only the given site. Idempotency: running an evaluation twice gives the same rows.
- Webhook: `course.registered` produces a `WebhookEvent` when the registration is created with no
  request in the thread; `fire_webhook_event` still drops events outside a request. Use the
  `django_tasks_db.DatabaseBackend` override in at least one test so `ImmediateBackend` does not mask
  a missing request.
- Preview: the lists for edit, enable and disable match what the confirmed save then
  does; nothing is saved before confirm; disabled-to-disabled saves skip it; the switch-off notice
  shows; a started learner and a learner held by a second rule appear under "Stops matching but
  stays registered" with their reasons.
- Admin warnings: an unpublished course shows the warning and the rule still registers; an enabled
  rule whose task has not run shows "Change not yet applied" until it does.
- `danger_content_delete` succeeds with rules present, and the rules app removed.
- Checks: `ImproperlyConfigured` at app load without `hr_attributes`, E002 for a bad kind path; `get_rule_kind` raises
  `ImproperlyConfigured` for an unknown key.
- One Playwright flow (`fls-dev:playwright-tests`): create a rule, add a condition and enable it on
  the change page, see the preview list, confirm, and see the learner's registration show the rule.

## Open questions

Defaults taken; overrule any of them:

- Inactive learners (`Learner.is_active=False`) never match, so removing a learner retracts their
  unstarted rule-made registrations.
- A rule with no conditions is allowed and matches the whole organisation.
- The preview list is shown in full, with no cap or pagination.
- No periodic reconcile (Out): a failed learner run shows nothing; turning the switch off and on
  again forces a catch-up.
- Unpublished course: warn and keep registering (decision 13); the alternative is to pause until
  published.
- Enabling a rule for a large organisation sends one `course.registered` notification per learner
  (roadmap decision 10).

## Success criteria

- `uv run pytest freedom_ls/registration_rules freedom_ls/webhooks freedom_ls/learner_progress`
  passes.
- With `freedom_ls.registration_rules` removed from `INSTALLED_APPS`, the full suite passes and
  `makemigrations --check` reports no changes.
- `git diff main -- freedom_ls/learner_management/migrations` is empty.
- `uv run lint-imports` passes: no core app imports `freedom_ls.registration_rules`.
- `uv run manage.py danger_content_delete` completes on a database holding rules.
