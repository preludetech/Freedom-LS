Implements `1. spec.md`. Read the spec first — this plan does not restate the rationale, only the
work.

## 0. Ground rules that apply to every task below

These are the rules the spec sets that are easiest to break by accident. They apply to every phase.

1. **The move is verbatim (§6.6).** Same body, same signature, same docstring, same comments. Do not
   add type hints, do not remove `Any`, do not rename anything, do not "improve" an untyped
   `def complete(self):` on the way past. CLAUDE.md's "type hints required" convention does **not**
   license a sweep here — that is separate follow-up work. A reviewer must be able to read the diff
   as "these lines are now over there".

   **This waiver covers only code moved verbatim in Phases 1-4.** All *new* code — `form_engine/
   signals.py`, the Task 4.7c receiver, and the two Phase 6 tests — carries full type hints, no
   `Any` and no `# type: ignore`, exactly like any other new code in this repo.
2. **`@claude` and `TODO` comments travel with their code and are never deleted or resolved.**
   The four in range, all verified present: `learner_progress/models.py:59` (`@claude`, inside
   `CourseItemProgress.newly_completed_item` — which **stays** in `learner_progress`),
   `learner_progress/signals.py:43` (`@claude` on `update_course_progress_on_completion`),
   `learner_interface/utils.py:240` (`TODO`, inside `get_content_status` — stays),
   and `content_engine/templates/cotton/content-link.html:6` (a `TODO` list — the file is not
   touched at all). `FormProgress`'s own body carries none.
3. **The one exception to rule 1:** a comment that becomes *false* must be corrected. Exactly one
   such comment exists — the module docstring of `learner_progress/signals.py` (Task 4.7).
4. **No compatibility shims (§10.8).** No aliasing module, no deprecation re-export of `Form` from
   `content_engine.models`. Consumers are repointed; the break is loud and complete.
5. **No new functionality.** No slug field, no `preview_url()`, no `FORM_CONTEXT_BACKEND`, no
   `form_engine/urls.py`, no `form_engine/views.py`, no `form_engine/templates/`. §12 is deferred.
   No template moves, no URL changes.
6. **Migrations are ordinary `makemigrations` output and are throwaway (§9.1).** No
   `SeparateDatabaseAndState`, no hand-written `RenameContentType`, no data migration. Do not spend
   effort making them elegant.
7. **Existing migration files are never edited.** The only migration files this work writes are the
   ones `makemigrations` generates during this run (Tasks 3.9 / 4.11), and the only permitted
   hand-edit is adding a `dependencies` / `run_before` entry to one of *those* newly generated files
   if the graph will not order (Task 4.11).

### Task 1.1 — Split the module into a package

`git rm --cached` is not needed; use `git mv` where it helps the diff read as a move.

Create `freedom_ls/content_engine/models/` with these files. The grouping is chosen so that Phase 2
and Phase 3 are whole-file moves:

| File | Contents (current `models.py` line ranges) |
|---|---|
| `base.py` | `BaseContent` (55-101), `TitledContent` (104-121), `MarkdownContent` (124-142) — **moves out wholesale in Phase 2** |
| `topics.py` | `Topic` (145-157), `Activity` (159-170) |
| `courses.py` | `DifficultyLevel` (38-45), `CourseVisibility` (47-53), `Course` (172-345), `CoursePart` (347-379), `ContentCollectionItem` (381-419) |
| `forms.py` | `QuestionType` (17-26), `FREE_TEXT_QUESTION_TYPES` (28), `FormStrategy` (31-36), `Form` (421-453), `FormPage` (456-482), `FormContent` (485-500), `FormQuestion` (503-549), `QuestionOption` (552-567) — **moves out wholesale in Phase 3** |
| `files.py` | `file_upload_handler` (570-578), `File` (580-605) |
| `__init__.py` | explicit re-exports + `__all__` |

Verified intra-module dependency facts that make this grouping safe:

- `Course`, `CoursePart` and `ContentCollectionItem` are a mutually-referencing cluster
  (`Course.children_flat`/`viewable_items` call `isinstance(child, CoursePart)` at runtime;
  `Course.items` and `CoursePart.items` are `GenericRelation("ContentCollectionItem")` **string**
  references). Keeping all three in `courses.py` means no cross-file import between them and no
  ordering hazard.
- The five form models are a self-contained cluster; `QuestionOption` extends `SiteAwareModel`
  directly, the rest extend the shared bases.
- **`Course`, `CoursePart` and `ContentCollectionItem` contain zero references to any form model** —
  confirmed by grep over lines 172-419. `courses.py` therefore takes no import from `forms.py`, which
  is what makes Phase 3 a clean extraction.
- `DifficultyLevel` and `CourseVisibility` are used only by `Course`.

Each module keeps the imports it actually needs, e.g. `topics.py`/`courses.py`/`forms.py` each carry
`from ..schema import ContentType as SchemaContentTypes` (they set `CONTENT_TYPE`), `courses.py`
carries `from ..course_accent import PALETTE`, `base.py`/`forms.py` carry
`from freedom_ls.markdown_rendering.markdown_utils import render_markdown`.

`__init__.py`, base-first, one explicit line per module, never `import *`:

```python
from .base import BaseContent, MarkdownContent, TitledContent
from .courses import (
    ContentCollectionItem, Course, CoursePart, CourseVisibility, DifficultyLevel,
)
from .files import File, file_upload_handler
from .forms import (
    FREE_TEXT_QUESTION_TYPES, Form, FormContent, FormPage, FormQuestion,
    FormStrategy, QuestionOption, QuestionType,
)
from .topics import Activity, Topic

__all__ = [ ... every name above, alphabetically ... ]
```

`__all__` is house style here (cf. `freedom_ls/contrib/conformance/__init__.py`) and states the
package's public surface in one place. `pyproject.toml`'s ruff config already exempts `*/__init__.py`
from `F401`/`F403`, so **no `# noqa` comment is needed** — do not add one.

Delete the old `freedom_ls/content_engine/models.py` and its stale `__pycache__` entry.

### Task 2.4 — Guarantee registry population (§8.3)

This is the step that stops a **silent** failure, and it becomes load-bearing at exactly this point:
before Task 2.3, `content_engine/models.py` imported `content_engine/schema.py` (for `ContentType`)
and Django's app loading dragged the whole schema module in with it. After Task 2.3 the model modules
import `content_base.schema` instead, so **nothing on the app-loading path imports
`content_engine/schema.py` any more** and `TOPIC`/`ACTIVITY`/`COURSE`/`COURSE_PART` would vanish from
`SCHEMAS` with no error and no warning.

Add to `freedom_ls/content_engine/apps.py`'s `ready()`, beside the existing `checks` import:

```python
    def ready(self) -> None:
        from freedom_ls.content_engine import checks  # noqa: F401
        from freedom_ls.content_engine import schema  # noqa: F401
```

Same mechanism as the existing `checks`/`signals` imports. `form_engine/apps.py` gets the identical
line in Task 3.1. Registration *order* does not matter; only whether each module was imported at all.

### Task 3.3 — Move the pydantic form schema

From `content_engine/schema.py` into `form_engine/schema.py`, verbatim:

| Symbol | Lines |
|---|---|
| `QuestionType(StrEnum)` | 26-32 |
| `FormStrategy(StrEnum)` | 35-39 |
| `Form` | 223-269 |
| `FormPage` (including `derive_content_type`, 274-278) | 271-279 |
| `QuestionOption` | 281-293 |
| `FormContent` | 295-297 |
| `FormQuestion` | 299-332 |

**`QuestionType` and `FormStrategy` each exist twice in the tree** — a Django `TextChoices` in
`models.py` and an independent pydantic `StrEnum` of the same name in `schema.py`, with no shared
base. Both copies of both enums move; they are two symbols each, not one.

`form_engine/schema.py` imports its bases from `freedom_ls.content_base.schema`
(`BaseBaseContentModel`, `BaseContentModel`, `ContentType`, `MarkdownContentModel`). Importing the
module is what runs the `class` statements and populates `_registry` — which is why Task 3.1's
`ready()` import exists.

**Delete all seven from `content_engine/schema.py`.** This is not tidiness — it is correctness.
`BaseBaseContentModel.__init_subclass__` writes `BaseBaseContentModel._registry[content_type] = cls`
with **no duplicate-registration guard**. If both copies of `Form`/`FormPage`/`FormContent`/
`FormQuestion`/`QuestionOption` survive and both modules get imported (each app's `ready()` imports
its own `schema`), `SCHEMAS[ContentType.FORM]` silently ends up pointing at whichever `ready()` ran
last. That is the same class of silent registry corruption §8.3 exists to prevent, one level deeper —
and Task 6.1's test would not catch it, because a key *is* present either way.

After this task `content_engine/schema.py` holds: the `content_base` import line, `DifficultyLevel`,
`CourseVisibility`, and the `Topic`, `Activity`, `Child`, `Course` and `CoursePart` schema classes.
Nothing else.

`content_engine/validate.py:187-191` calls `first_model.derive_content_type(data)` polymorphically
off the registry. It needs no change.

### Task 4.7 — The `form_attempt_completed` signal

**a. Define it.** New file `freedom_ls/form_engine/signals.py`:

```python
"""Signals emitted by the form_engine app."""

from django.dispatch import Signal

# Sent when a learner finishes an attempt. Receivers take (sender, user, form).
form_attempt_completed = Signal()
```

No `providing_args=` — it was removed pre-Django 3.1. This is the first genuinely custom
`django.dispatch.Signal` in the codebase; every existing `signals.py` uses only built-in
`post_save`/`post_delete`/`post_migrate`. Follow Django's own `Signal` idiom.

**b. Send it.** `FormProgress.complete()` gains the send as its last statement:

```python
    def complete(self):
        """Mark the form as completed and calculate the final score (idempotent)."""
        if self.completed_time:
            return
        self.completed_time = timezone.now()
        self.score()
        self.save()
        form_attempt_completed.send(sender=type(self), user=self.user, form=self.form)
```

The early return when `completed_time` is already set means the send fires **once per completion by
construction**. That is why `form_engine` needs no equivalent of `mark_completion_recorded()`:
`complete()` saves three times (`score_quiz()`/`score_category_value_sum()` each save, then
`complete()` saves), and the old `post_save` receiver existed to suppress the repeats it caused. An
explicit send from the completion path has nothing to suppress.

`complete()` is the only writer of `FormProgress.completed_time` in the tree. The `qa_helpers`
commands that pass `completed_time` into `get_or_create(defaults=…)` create an already-complete row,
which `newly_completed_item()` reports as *no transition* today — so they trigger no recalculation
now and none after the change. No live path is lost.

**c. Subscribe to it.** In `learner_progress/signals.py`:

- Delete the `@receiver(post_save, sender=FormProgress)` line from
  `recalculate_course_progress_on_save` (line 99). It keeps **only**
  `@receiver(post_save, sender=TopicProgress)`, and its `CourseItemProgress` type hints stay correct
  because `TopicProgress` still subclasses it. Its body is otherwise unchanged, including the
  `newly_completed_item()`/`mark_completion_recorded()` calls.
- Add a **new, separate** receiver. The existing one cannot be reused: it reads two
  `CourseItemProgress` methods `FormProgress` no longer has, and its signature does not match a
  signal carrying `user`/`form`.

```python
@receiver(form_attempt_completed, dispatch_uid="learner_progress.form_attempt_completed")
def recalculate_course_progress_on_form_attempt(
    sender: type[models.Model], user: models.Model, form: Form, **kwargs: object
) -> None:
    """..."""
    update_course_progress_on_completion(user, form)
```

`update_course_progress_on_completion()` itself is unchanged, `@claude` comment and all.

The `dispatch_uid` is required: `ready()` can run more than once during testing and
double-connection is silent.

**d. Imports.** `learner_progress/signals.py` imports **three** things from `form_engine`, all part of
the same single `learner_progress → form_engine` app edge:

```python
from freedom_ls.form_engine.models import Form

from freedom_ls.form_engine.signals import form_attempt_completed
```

`Form` is still needed for the `content_item: Topic | Form` hint at line 36 and the
`ContentCollectionItem` walk; `completed_form_ids_by_user` is used at line 85 and moved by Task 4.3.
`FormProgress` is dropped from the `learner_progress.models` import.

`learner_progress/apps.py`'s `ready()` already does `from . import signals` for side effects and keeps
working unchanged. Because `learner_progress/signals.py` imports `form_engine.signals`, the signal
object is guaranteed to exist by the time anything connects to it — there is no ordering requirement
between the two apps' `ready()` calls.

**e. Correct the module docstring.** This is the one place rule 1 yields (rule 3). The current

### Task 6.2 — Signal wiring

`freedom_ls/form_engine/tests/test_form_attempt_completed_signal.py`.

### Task 6.3 — No collection-safety test

`course_applications` is *removed* from `INSTALLED_APPS`. It works only because that app is genuinely

needed.
