# Spec: Extract form functionality into its own app

## 1. Summary

Give FLS one questionnaire primitive that is usable outside course content, by moving the form
definition, the attempt and the marking out of `content_engine`/`learner_progress` into a new
`freedom_ls/form_engine/` app — while the *consequences* of a result (course progression, deadlines,
cohort reporting) stay with the apps that care about them.

Three changes land, in this order:

1. **`content_engine/models.py` becomes a `models/` package**, with `forms.py` as one of its files,
   everything re-exported from `__init__.py`. Zero migrations, zero new edges, zero behaviour change.
2. **A new `freedom_ls/content_base/` app** (label `freedom_ls_content_base`) owns the abstract model
   bases and the pydantic schema bases plus the content-type registry — and nothing else. Zero tables,
   zero migrations.
3. **A new `freedom_ls/form_engine/` app** (label `freedom_ls_form_engine`) owns the form definition
   models, their admin, factories, schema and loader functions, plus the attempt and marking layer
   (`FormProgress`, `QuestionAnswer`, scoring, submissions, queries). The one remaining behavioural
   coupling — `learner_progress` reacting to a completed attempt — becomes a custom
   `form_attempt_completed` signal instead of a `post_save` receiver on a model `learner_progress`
   no longer owns.

**This is a structural refactor with one behavioural substitution.** No URL changes, no template
moves, no new user-facing functionality. The identity and authorisation seam that actually unlocks
non-course use — a slug route, `Form.preview_url()`, and a pluggable form-context backend — is
explicitly **deferred to its own spec** (§12).

## 2. Why this, and why now

### 2.1 The prior verdict has been superseded by its own revisit trigger

`final_pre_deploy_db_structure_cleanup/research_forms_app_extraction.md` answered "are forms
complicated enough to deserve their own app?" with **no**, and named its own revisit condition:

> "Revisit only if a concrete reuse case for forms *outside* course content ever appears — not to
> satisfy a feeling that a 605-line file is big."

That trigger has fired, and the evidence is drafted duplication rather than a hypothetical. The
`application-forms` draft proposes mirroring `Form → FormPage → FormQuestion → QuestionOption` as a
parallel `ApplicationConfig`/`ApplicationStep`/`ApplicationQuestion`/`ApplicationQuestionOption`
family, loaded through the *same* `content_save` pipeline, with `ApplicationAnswer` "deliberately a
1:1 copy of the `QuestionAnswer` shape" — and to make that work it accepts a new
`content_engine → course_applications` edge, which inverts the dependency graph to avoid a coupling
that a shared primitive would remove outright.

The trade being made here is therefore **+7 legible app-level edges against +1 inverted edge and N
duplicated model families**. Edge count is not coupling: those imports exist today, the graph simply
cannot see them because they hide inside one app.

### 2.2 The attempt layer is already course-free — that is what makes this cheap

`FormProgress` is keyed `(user, form)` and has no `Course` FK at all. `scoring.py` and
`submissions.py` are pure functions over `QuestionOption`/`FormQuestion`. `queries.py`'s
`completed_form_ids_by_user()` already returns `{user_id: {form_id}}` — course code asks "which
forms are done"; form code never asks about courses.

The single course coupling in the whole attempt layer is `learner_progress/signals.py:35`, which
walks `ContentCollectionItem` up to a `Course` on completion. Everything downstream of that —
progression gating in `learner_interface/utils.py:165` `get_content_status`, deadlines, cohort
reporting — keeps working unchanged once the receiver subscribes to a signal instead of a `post_save`
on a foreign model.

### 2.3 The database cost is zero, and only because of when this lands

**This lands before `final_pre_deploy_db_structure_cleanup`.** That spec's one-time, project-wide
migration reset therefore runs *after* the extraction and regenerates every app's `0001_initial` on
top of it.

The standard cross-app-move recipe (`SeparateDatabaseAndState` table pinning, a hand-written
`RenameContentType`, state-only `CreateModel`/`DeleteModel` pairs) exists **entirely** to make a
*data-preserving* move safe. Django has no `RenameApp` operation and no "move model to another app"
operation at all — ticket [#24686](https://code.djangoproject.com/ticket/24686) has been open since
2015 — and the built-in `RenameContentType` fixup fires only for a `RenameModel` detected within a
single app's migration graph, so a cross-app move never triggers it regardless of technique.

None of that applies here: FLS dev databases are dropped and recreated, no downstream project has
migrated a database it intends to keep, and the reset that follows discards the migration history
anyway. **Ordinary `makemigrations` autodetector output is correct for this move, and the migrations
it produces are throwaway.** This is stated up front so that a future reader does not mistake the
absence of the standard recipe for an oversight.

## 4. Step 1 — the `models/` package

`content_engine/models.py` (605 lines) becomes `content_engine/models/` with one file per logical
group, and **every model class re-exported from `__init__.py`**. Django's app loading imports
`models.py` *or* `models/__init__.py`, whichever exists, so re-exporting everything keeps
`from freedom_ls.content_engine.models import Form` working unchanged at every call site.

**Why re-export rather than deep-import at each call site.** This is Django's own documented layout
for the case, not a convenience shortcut: *"Remove `models.py` and create a `myapp/models/`
directory with an `__init__.py` file and the files to store your models. You must import the models
in the `__init__.py` file."* App loading imports exactly one module per app — `models.py` *or*
`models/__init__.py` — so a model in a submodule that `__init__.py` never imports is invisible to
that pass, and `makemigrations` then reads it as a deleted model. The names are bound in
`content_engine.models` either way; respelling them as deep module paths at 123 call sites across
113 files adds no explicitness — they are already explicit named imports — and churns the one step
whose entire value is a zero-behaviour diff, a churn step 3 would undo again for every form symbol.

**`__init__.py` uses one explicit `from .<module> import …` line per file plus `__all__`, never
`import *`.** Django gives the reasons: a star import clutters the namespace, hurts readability, and
blinds code-analysis tools. `__all__` is house style here (cf.
`freedom_ls/contrib/conformance/__init__.py`) and states the package's public surface in one place;
ruff already exempts `__init__.py` from F401, so no `# noqa` is needed. Explicitness across an *app*
boundary is a separate question, and §10.8 answers it the other way: no re-export shim for `Form`
once it moves to `form_engine`.

`app_label` resolves per-model from the app registry by matching the module's parent package to an
installed app — not from the filename — so a model in `models/forms.py` still resolves to
`freedom_ls_content_engine` with no `Meta.app_label` anywhere. A pure file reorganisation with all
classes re-exported produces **zero migration operations**.

**The one way this "free" step can silently break:** if one file in the package needs a class from
another via a direct Python import (rather than a string FK reference), the import order in
`__init__.py` starts to matter and two files importing each other's classes will raise a circular
import. The rule for this step: **use Django's string-based FK references
(`models.ForeignKey("freedom_ls_content_engine.CoursePart", …)`) inside the split package**, and
order `__init__.py` base-first if any direct import remains.

Doing this first turns step 3 into a directory move rather than surgery on a 605-line file.

| `MarkdownContentModel` | `content_engine/schema.py` | 89-90 |

It owns nothing else. No concrete models, no tables, no migrations, no views, no templates.

### 5.2 Why a separate app, and why this name

**It costs nothing at the database level.** Abstract models generate no table and no migration.
Django does not even require an abstract model's module to live in an installed app — `ModelBase`
only needs a resolvable `app_label` for *concrete* models. `content_base` is an installed app because
**this project's tooling requires it** (`/ds:app_map` is ast-based and only maps installed apps), not
because Django does. `panel_framework` is the working precedent for the *shape*: a zero-model, zero-migration installed
app whose whole `apps.py` is an `AppConfig` with `name` and `label`. It is the model-less-app
precedent, not a zero-dependency one — `content_base` will depend on `site_aware_models` and
`markdown_rendering` (§13.4), which `panel_framework` does not.

**It removes the mutual edge.** Keeping the bases in `content_engine` would give
`form_engine → content_engine` (for bases) alongside `content_engine → form_engine` (for the loader).
With `content_base` the graph is a DAG: `content_engine → content_base`,
`form_engine → content_base`, `content_engine → form_engine`.

**It dissolves the registry problem.** With the pydantic bases and `_registry` in `content_base`,
both apps register into a registry neither owns — nothing to fork, nothing to re-couple, and
`validate.py` keeps its single walk.

**Name it `content_base`, not `content_engine_base`.** Two apps depend on it; naming it after one of
them reads as "form_engine depends on content_engine", which is the confusion it exists to remove.
Label `freedom_ls_content_base`.

**Do not put the bases in `base` instead.** `base` looks ideal — no `models.py`, bottom of the graph,
zero runtime deps — but `BaseContent` extends `SiteAwareModel`, so it would add
`base → site_aware_models` while `site_aware_models → base` already exists. That is a genuine cycle,
worse than the one being fixed.

### 5.3 `related_name` placeholders — checked, and a no-op in this cut

`related_name`/`related_query_name` on a relation declared on an abstract base **must** use the
`%(app_label)s` and `%(class)s` placeholders once more than one concrete subclass exists.
`%(app_label)s` resolves to the lowercased label of *the concrete subclass's* app — so a
`content_base`-hosted field with `related_name="%(app_label)s_%(class)s_related"` produces distinct
names for a `content_engine`-owned `Topic` and a `form_engine`-owned `Form` without either app
knowing about the other.

**Verified (2026-08-24): none of the three bases declares a relation field at all**, so there is
nothing to audit and no reverse-accessor clash is reachable in this cut. `BaseContent` declares
`file_path`, `meta`, `tags`; `TitledContent` adds `title`, `subtitle`, `description`, `slug`;
`MarkdownContent` adds `content`. Every `related_name` in `content_engine/models.py` sits on a
*concrete* model (`Course.items`, `CoursePart.items`, `FormPage.form`, `FormContent.form_page`,
`FormQuestion.form_page`, `QuestionOption.question`), where the placeholder rule does not apply.

The rule is recorded here anyway because it becomes live the first time anyone adds a relation to
one of these bases, which is exactly the change `content_base` makes cheap. `manage.py check` is the
standing guard (§13, criterion 13) — it costs nothing and catches the clash on the day it
appears.

### 5.4 Honest limitation

`content_base` removes today's mutual edge; it does not *prevent* one. The loader edge stays, so any
future `form_engine → content_engine` import re-creates the pair. A string FK
(`"freedom_ls_content_engine.Topic"`) dodges the Python import, but `/ds:app_map` is ast-based, so
that dependency would be real and *invisible* — worse for the graph than an edge you can see.

Also worth saying plainly: **the cycle being removed was never an `ImportError`.**
`content_engine/models.py` never imports form models; only `content_save.py` and `content_tags.py`
do. The win is legibility and passing `/fls-dev:plan_structure_review`, not a crash avoided.

**Marking belongs with forms, not layered on top of them.** `Form.strategy` is a field on the form;
`FormProgress.score()` dispatches on it; a quiz's pass mark is `Form.quiz_pass_percentage`. Splitting
scoring into a third app would separate a dispatch from the enum it dispatches on, and add edges for
no consumer. Two layers, not three.

`CourseItemProgress` (the abstract base at `learner_progress/models.py:36-74`) **stays in
`learner_progress`, and `FormProgress` stops inheriting it.** In `form_engine`, `FormProgress`
extends `SiteAwareModel` directly.

The base exists to let `learner_progress/signals.py` sniff a completion transition out of a generic
`post_save`. Its two methods have exactly one caller between them — that receiver; no other module in
the repo calls `newly_completed_item()` or `mark_completion_recorded()`. §7 replaces the
`post_save`-on-`FormProgress` half of that receiver with an explicit `form_attempt_completed` send,
so after this refactor `FormProgress` no longer travels that path and would inherit nothing it uses.
`CourseItemProgress` stays exactly where it is, unchanged, serving `TopicProgress` — which still
needs it, and whose `post_save` receiver is untouched.

**This is what keeps the app graph a DAG.** Inheriting the base across the boundary is still an
import: it would put a `form_engine → learner_progress` edge opposite the
`learner_progress → form_engine` edge of §8, which is a two-app cycle — the same shape this spec
exists to remove between `content_engine` and `form_engine`, rebuilt one layer down. Nothing is
duplicated to avoid it: `form_engine` needs no equivalent of the base, so there is no shared code to
extract and no second base app to invent.

Dropping the base costs no migration operation: `CourseItemProgress` declares **no fields** — only
two class-attribute annotations, a `user: models.Model` annotation for mypy that `FormProgress`
overrides with a real FK anyway, and three methods. Its parent `SiteAwareModel` is what contributes
the `site` field, and `FormProgress` still inherits that directly.

### 6.6 The move is verbatim

Every symbol listed above moves **as-is**: same body, same signature, same docstring, same
comments. No type hints added, no `Any` removed, no `# type: ignore` cleaned up, no function
renamed, no untyped `def complete(self):` improved on the way past. Several of the moving functions
predate the project's "type hints required on all functions" convention (`save_form`,
`save_form_page`, `FormProgress.complete`, `score_quiz`, …), and an implementer following CLAUDE.md
could reasonably decide to fix them in passing.

**Do not.** The value of this refactor is a diff a reviewer can read as "these lines are now over
there". Mixing in signature changes destroys that, and a type-hint sweep of `form_engine` is
perfectly good follow-up work once the boundary exists.

Two things this rule protects specifically:

- **`@claude` and `TODO` comments travel with the code they annotate** and are not deleted, edited or
  "resolved" by this work — CLAUDE.md is explicit about this. `FormProgress` and the form loader
  functions carry several. `content_engine/templates/cotton/content-link.html` carries a TODO list
  and a comment reading *"It can be a Topic or a Form"* that stays exactly as written (§8.2), as does
  the `@claude` comment on `update_course_progress_on_completion` in `learner_progress/signals.py`.
- **Comments that describe the old mechanism must be corrected, not preserved verbatim.** The
  module docstring of `learner_progress/signals.py` explains the `CourseItemProgress` sender
  convention; after §7 that docstring describes only the `TopicProgress` half and needs a sentence
  about the `form_attempt_completed` subscription. That is the one place the "verbatim" rule yields —
  a comment that is now false is not documentation.

## 7. The `form_attempt_completed` signal

### 7.1 What changes

`learner_progress/signals.py:99-100` currently stacks two decorators on
`recalculate_course_progress_on_save`:

```python
@receiver(post_save, sender=FormProgress)
@receiver(post_save, sender=TopicProgress)
```

`FormProgress` is no longer a `learner_progress` model after the move, so the `post_save` hook on it
becomes a receiver registered against a foreign app's model. It is replaced by:

- `form_engine/signals.py` defines `form_attempt_completed = Signal()` at module level.
  `FormProgress.complete()` sends it as its last statement, carrying the `user` and the `form` — the
  two arguments `update_course_progress_on_completion()` takes. `complete()` already returns early
  when `completed_time` is set, so the send fires once per completion by construction. That is also
  why `form_engine` needs no equivalent of `mark_completion_recorded()`: `complete()` saves three
  times (`score_quiz()`/`score_category_value_sum()` each save, then `complete()` saves), and the old
  `post_save` receiver had to suppress the repeats it caused. An explicit send from the completion
  path has nothing to suppress.

  `complete()` is verified to be the **only** writer of `FormProgress.completed_time` in the tree
  (`learner_interface/views.py:1012,1328`, `learner_progress/models.py:162`, four `qa_helpers`
  commands and `freedom_ls/conftest.py:252`). The `qa_helpers` commands that pass
  `completed_time` into `get_or_create(defaults=…)` create an already-complete row, which
  `newly_completed_item()` reports as *no transition* today — so they trigger no recalculation now
  and none after the change. Moving the trigger from "any save that completes the row" to "the
  `complete()` call" therefore loses no live path.
- `learner_progress/signals.py` gains a **new, separate receiver** for the custom signal — the
  existing one cannot be reused. `recalculate_course_progress_on_save(sender, instance, raw, …)`
  reads `instance.newly_completed_item()` and `instance.mark_completion_recorded()`, which are
  `CourseItemProgress` methods `FormProgress` no longer has after §6.2, and its signature does not
  match a signal carrying `user`/`form`. So:

  - `recalculate_course_progress_on_save` keeps **only** `@receiver(post_save, sender=TopicProgress)`.
    The `sender=FormProgress` decorator line is deleted, and its `CourseItemProgress` type hints stay
    correct because `TopicProgress` still subclasses it.
  - A new receiver — one function, connected with a `dispatch_uid` — takes
    `(sender, user, form, **kwargs)` and calls `update_course_progress_on_completion(user, form)`.
    `update_course_progress_on_completion()` itself is unchanged.
- `learner_progress/signals.py` imports **three** things from `form_engine`, not one: the signal
  object, `Form` (for the `content_item: Topic | Form` hint at line 36 and the
  `ContentCollectionItem` walk), and `completed_form_ids_by_user` (imported today from
  `learner_progress.queries` at line 32, and moved by §6.2). All three are the same single
  `learner_progress → form_engine` app edge.
- `learner_progress/apps.py`'s `ready()` already does `from . import signals` for side effects; that
  keeps working unchanged. Because `learner_progress/signals.py` now imports `form_engine.signals`,
  the signal object is guaranteed to exist by the time anything connects to it — there is no
  ordering requirement between the two apps' `ready()` calls.

The signal points **away from the floor of the graph**: defined in `form_engine` (which imports
`content_base` and nothing at all from `learner_progress` — §6.2), subscribed to from
`learner_progress`.
Never the reverse. This matches the reasoning `organisations/1. spec.md` §9.5 used for its own
receiver placement.

### 7.2 Why a signal here, when Django's docs discourage custom signals

Django's signals guide says plainly: *"If the sender and receiver of your custom signal are both
within your project, you're better off using an explicit function call."* `form_engine` and
`learner_progress` are both `freedom_ls/` apps, so a reviewer who knows that guidance will flag this.

**It is stated here deliberately, and this is the documented exception.** An explicit function call
would require `form_engine` to import `learner_progress` (or the reverse), re-creating the exact
cross-app coupling this spec exists to remove. That is the textbook "sender and receiver should not
know about each other" case signals were built for, not the anti-pattern the docs warn about.

### 7.3 Implementation constraints

- **This is the first genuinely custom `django.dispatch.Signal` in the codebase.** Every existing
  `signals.py` (`reports`, `organisations`, `learner_progress`) uses only built-in
  `post_save`/`post_delete`/`post_migrate` via `@receiver`. There is a house-style precedent for the
  *registration* half (module named `signals.py`, imported from `AppConfig.ready()`, never
  auto-discovered) but none for the *definition* half — follow Django's own `Signal` idiom directly.
  No `providing_args=` kwarg; it was removed pre-Django 3.1.
- Use a `dispatch_uid` on the receiver. `ready()` can run more than once during testing, and
  double-connection is silent.
- **Forward-looking note for future subscribers:** a signal fired from inside
  `FormProgress.save()`/`mark_completed()` can run while the enclosing transaction is still open. Any
  *future* subscriber that does more than in-process Python — queues a task, sends an email, writes to
  another service — must wrap that side effect in `transaction.on_commit(...)`. The current
  subscriber (a synchronous progression update inside the same transaction) is correct as-is and needs
  no change.
- `learner_progress/signals.py` keeps a `Form` import for the `content_item: Topic | Form` type hint
  at line 36 and its `ContentCollectionItem` walk, and gains a `completed_form_ids_by_user` import
  from `form_engine` (it uses it at line 85, and §6.2 moves `queries.py`). Both are legitimate parts
  of the remaining `learner_progress → form_engine` edge, not leftovers.

## 8. The `content_save` and registry seam

### 8.1 The loader stays whole

One `@transaction.atomic` importer (`content_save.py:491-698`) builds a single `content_by_path` map
spanning every content type and resolves `Course` children against it, including the forms-by-directory
join at 546-603 and the collection auto-scan treating `FORM` as a collection file at row 642.

**Decision: the loader stays whole in `content_engine` and imports form models from `form_engine`.**
One `content_engine → form_engine` edge, in exchange for keeping one transaction, one
`content_by_path` map and one validation walk. This is the same shape the `application-forms` draft
already proposed for its own config models — except pointed at a shared primitive instead of a second
copy.

`FormPage.derive_content_type` (`schema.py:274-278`) travels with the form schema classes into
`form_engine`; the generic parser in `validate.py:187-191` calls it polymorphically off the registry,
which it already does.

### 8.2 There are TWO `content_engine → form_engine` call sites, not one

Prior research treats the loader as "the one deliberate edge." The tree does not support that:

1. `content_engine/management/commands/content_save.py:25-37` — the importer (and
   `danger_content_delete.py:5-16` needs the same import).
2. `content_engine/templatetags/content_tags.py:9`, used by `get_content_by_path` (145-173), which
   tries `Topic` and falls back to `Form`.

They land as one app-level edge in `docs/app_structure.md`, but they are two live call sites and the
second runs at **template-render time**, on every request rendering a `get_content_by_path` lookup —
not only at import time. Both must be named, because removing one without the other is an easy way to
half-fix the edge and believe it is fixed.

`content_tags.get_content_by_path` is also the resolver behind `<c-content-link>`
(`content_engine/templates/cotton/content-link.html`), whose own comment already says *"It can be a
Topic or a Form"* and carries an unaddressed TODO list. **Do not delete that comment or its TODOs.**

### 8.3 Registry population — the silent failure mode

Django's Phase 2 app loading auto-imports each app's `models.py`/`models/__init__.py` and **nothing
else**. A pydantic base's `__init_subclass__` only populates `_registry` when the interpreter
actually executes the subclass's `class` statement — i.e. when something imports the module.

Today that happens by accident and it works: `content_engine/models.py:14` does
`from .schema import ContentType as SchemaContentTypes` (each model sets
`CONTENT_TYPE = SchemaContentTypes.<X>`), so auto-importing `models.py` drags `schema.py` in with it
and every schema class registers.

**The move breaks that accident for `form_engine`.** `ContentType` goes to `content_base` (§5.1), so
`form_engine/models.py` will import `content_base`, *not* `form_engine/schema.py` — and nothing else
in the app-loading path imports it either. If nothing imports `form_engine/schema.py` before
`validate.py` walks `SCHEMAS`, form content types are simply **absent** from the registry. No error,
no warning — content validation silently treats `.yaml` files declaring form content types as
unrecognised.

**Decision: both `content_engine/apps.py` and `form_engine/apps.py` import their own `schema` module
from `AppConfig.ready()`.** This is the same import-for-side-effect mechanism the codebase already
uses for `signals`/`checks` (`content_engine/apps.py:10`, `learner_progress/apps.py:10`), and it
guarantees registration by the time any management command or request runs. For `content_engine` the
line is belt-and-braces — `models.py` already pulls `schema.py` in — but stating the rule the same
way in both apps is what stops the next model reshuffle silently un-registering a content type. Relying on incidental imports from `content_save.py`/`content_tags.py` is fragile —
not every code path that reads `SCHEMAS` goes through those modules (a validate-only management
command, for instance, does not).

Registration order does not matter; only *whether* each module was imported at all.

**Required regression guard:** a test asserting `SCHEMAS` contains every expected `ContentType` key,
run as an ordinary pytest-django test (which executes after every app's `ready()` has completed).
The failure mode is silent, so the guard has to be an explicit assertion rather than an expectation
that something will raise.

## 10. Decisions and rationale

1. **`content_base` gets the pydantic bases and `_registry` in the same cut as the abstract model
   bases.** Splitting them would leave `form_engine` importing `content_engine.schema`, re-creating
   the exact mutual edge `content_base` exists to remove. Moving them together is what dissolves the
   registry problem rather than relocating it.

2. **The importer stays whole in `content_engine` and takes a direct `form_engine` import.** The
   alternative — a settings-driven list of modules to import for registration — is redundant
   machinery, since the importer needs the edge for `content_save.py` regardless. It becomes the
   right answer only if `/fls-dev:plan_structure_review` independently rejects the direct import.

3. **Two layers, not three.** Marking stays with forms because `FormProgress.score()` dispatches on
   `Form.strategy` and reads `Form.quiz_pass_percentage`. A third "marking" app would separate a
   dispatch from the enum it dispatches on.

4. **The identity and authorisation seam is deferred.** It is the part that actually unlocks
   non-course use, and it is genuinely new behaviour with new security surface (form-level
   authorisation where none exists today). Mixing it into a large mechanical refactor would make both
   halves harder to review, test and QA. See §12.

5. **This spec supersedes the `Won't do` entry in `final_pre_deploy_db_structure_cleanup`.** That
   spec is also in progress and the two documents now disagree in writing. The implementation edits
   that idea file: replace the `Won't do` entry with a pointer to this spec, and record that the
   migration reset now runs *after* the extraction — which is the assumption §2.3 depends on, and
   which is currently only stated here.

6. **The `application-forms` draft gets a short out-of-date note at the top, and nothing more.** It
   is not in scope for this spec. A brief note pointing at `form_engine` is enough to stop someone
   picking the draft up and building the duplicate; re-scoping it is that spec's own work.

7. **`FormProgress` moves to `form_engine`; the course association, when it arrives, stays in
   `learner_progress`.** `better_course_progress_tracking` (also in progress) proposes
   `FormProgress.run → FK CourseRun` (non-null) and scoping the attempt to a `ContentCollectionItem`
   placement. That would make the attempt layer course-bound and force a
   `form_engine → learner_progress` edge for a concrete model — undoing the reuse this spec exists to
   deliver.

   **Constraint that spec must honour:** `form_engine` owns the *course-free attempt*. The run and
   placement association becomes a **separate row owned by `learner_progress`** pointing at the
   attempt, not a field on `FormProgress`. That preserves the DAG (`learner_progress → form_engine`)
   and keeps an attempt recordable with no course in sight, which is the entire point. This spec does
   not implement that row; it records the boundary the later spec must design against.

   `CourseItemProgress` does **not** cross the boundary either, and there is no accepted
   `form_engine → learner_progress` edge of any kind. An abstract base is still an import: one
   `form_engine → learner_progress` edge against the `learner_progress → form_engine` edge is a
   two-app cycle, not a tolerable single dependency. It does not need routing through `content_base`
   or a second base app, because §6.2 shows `form_engine` does not need the base at all — its two
   methods serve the generic `post_save` receiver that §7 replaces for forms. `FormProgress` extends
   `SiteAwareModel` directly; `CourseItemProgress` stays in `learner_progress` for `TopicProgress`.

8. **Loud break, no compatibility shims** — but a *code* break only. No aliasing module, no
   deprecation shim re-exporting `Form` from `content_engine.models`. A shim would keep the mutual
   edge alive under a different name and let downstream projects defer the fix indefinitely.

9. **App named `form_engine`, label `freedom_ls_form_engine`.** Not a bare `freedom_ls/forms/` — it
   reads as `django.forms` and collides with the per-app `forms.py` convention.

## 12. Deferred: the identity and authorisation seam

Recorded here because it is the reason this extraction is worth doing, and because deferring it is a
decision rather than an omission. **It is not implemented in this spec.**

A form usable outside a course needs three things it does not have:

- **An identity.** Every form route is `courses/<slug:course_slug>/<int:index>/…` and the only
  resolver is `get_form_for_index(course, index)` (`learner_interface/utils.py:748`). A form has no
  addressable identity — it is "the Nth viewable item of a course". `Form` has no `preview_url()`, so
  `<c-content-link>` to a bare form renders an empty `href`. Exactly one model in the codebase
  implements `preview_url()` today: `Topic`, at `content_engine/models.py:155`. A future `Form.slug`
  should reuse the shared `get_unique_slug` collision helper rather than reinventing it.
- **An authorisation seam.** All authorisation to answer a form is *course* authorisation
  (`_course_access_redirect`, `views.py:577` → `raise_404_if_hidden_unregistered` +
  `COURSE_ACCESS_BACKEND`). There is no form-level permission concept anywhere. Follow the existing
  `COURSE_ACCESS_BACKEND` precedent end to end rather than inventing a pattern — the default in
  `config/settings_base.py:423`, the declaration in the owning app's `config.py`
  (`course_access/config.py` declares `COURSE_ACCESS_BACKEND: str` against
  `freedom_ls.base.app_settings`, per the `ds:app-settings`/`fls-dev:app-settings` skills), the
  `import_string` resolution in `course_access/loader.py`, and the system check that reports an
  unresolvable value (`course_access/checks.py`). The setting is: a `FORM_CONTEXT_BACKEND` returning can-answer, exit URL, and the
  chrome partial to wrap the runner in. The course player becomes the first implementation of that
  backend, not a special case.
- **A context-agnostic runner.** `form_fill_page` builds ~15 context keys, roughly half of them
  course chrome. The template partials in `course_form_page.html` are already generic; the view is
  what needs the seam.

Two things worth pre-recording for whoever writes that spec, so they do not have to rediscover them:

- Resolve the backend **lazily** (settings access needs the app registry populated), raise
  `ImproperlyConfigured` naming the setting rather than letting a bare `ImportError` surface, and
  document the interface contract **at the same time** the setting is introduced. If the resolution
  is memoized, the memoization must be clearable or `override_settings` will not take effect in tests
  — `COURSE_ACCESS_BACKEND` handles this with a `@functools.cache`-wrapped
  `get_course_access_backend()` (`course_access/loader.py`) whose docstring tells tests to call
  `.cache_clear()` either side of an `override_settings`; copy that arrangement, docstring warning
  included.
- `form_engine/urls.py` must define `app_name` from day one.
