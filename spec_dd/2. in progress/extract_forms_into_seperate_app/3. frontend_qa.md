# Frontend QA: extract form functionality into its own app

## What this is checking, and why the list looks long for a refactor

Nothing in this change is meant to be visible to a learner. That is exactly what makes it risky: the
refactor moves the code behind **every form page in the product**, repoints ~69 consumer files, and
replaces the `post_save` hook that recalculates course progress with a custom
`form_attempt_completed` signal. A regression here does not throw — it quietly shows the wrong
percentage, the wrong verdict, or an item that should be locked.

Four things could break silently and each gets its own section below:

1. **The signal substitution** — the one genuine behaviour change. Course progress is now
   recalculated from an explicit send inside `FormProgress.complete()` rather than from any save that
   completes the row.
2. **`ContentType.get_for_model(Form)`** — deadlines and cohort reporting resolve forms through the
   Django content-type table. The app label changed, so the content-type rows are new.
3. **`content_tags.get_content_by_path`** — a `Form` import that runs at *template-render time*, on
   every request rendering a `<c-content-link>`, not just at import time.
4. **The Django admin** — 12 admin classes moved app. They now appear under a new section, and their
   inlines have to still work.

### A2. Resume an incomplete attempt

   - **Expect:** the start page now offers to **resume/continue** rather than start fresh, and
     re-entering the runner shows page 1's answers still selected.
   - This exercises `FormProgress.get_latest_incomplete` / `get_or_create_incomplete` /

### A3. Free-text survey — a form with no verdict

3. Fill page 1's required short-text and long-text questions, continue to page 2, leave the optional

## Section B — the signal substitution (the one real behaviour change)

This is the highest-value section. Read the percentage **before** and **after**; a stale or unchanged
percentage is the failure mode.

### B1. Completing a form recalculates course progress

1. Log in as `demodev_quizqa@email.com`.
2. Go to the dashboard (`http://127.0.0.1:$PORT/`) and note the progress percentage shown on the
   card for the progression-block course (`qa-progression-block-course`). The first topic is
   pre-completed, so it should be non-zero and less than 100.
3. Open the course, sit the quiz (item 2), answer the checkbox question **correctly** plus all three
   multiple-choice questions correctly, and complete it.
4. Return to the dashboard **and** to `http://127.0.0.1:$PORT/courses/qa-progression-block-course/`.
   - **Expect:** the percentage has **increased**. If it is unchanged, the
     `form_attempt_completed` receiver is not connected, or the send is not firing.

### B2. Completing does not double-count

1. Immediately after B1, hard-refresh the course home page and the dashboard several times.
   - **Expect:** the percentage is stable and never exceeds 100.
2. Return to the completed quiz item.
   - **Expect:** it reads as complete; re-entering does not offer a second attempt that would
     re-fire the signal, and the percentage does not move again.
   - `complete()` returns early once `completed_time` is set, so a second call must be a no-op.
     Watch the `runserver` terminal for a burst of repeated queries — the old `post_save` receiver
     had to suppress three saves per completion; the new send should produce exactly one
     recalculation.

### B3. Failing a quiz blocks the next item

1. Reset the QA learner's progress so the quiz can be re-sat:
   ```bash
   uv run python manage.py qa_reset_learner_progress
   ```
   (This command also imports moved symbols — an `ImportError` here is a QA failure.)
2. Log in as `demodev_quizqa@email.com` and open `qa-progression-block-course`.
3. Sit the quiz again, this time answering the **checkbox question wrongly** (3/4 = 75%, below the
   80% pass mark) and everything else correctly.
4. On the completion page:
   - **Expect:** a **failed** banner (red), the score ring showing 75%, and — because
     `quiz_show_incorrect=True` on this form — a review of the incorrect answers.
5. Go back to the course home / table of contents.
   - **Expect:** item 3 (the successor topic) is **locked / blocked**, not clickable through to
     content.
   - **Expect:** the course percentage did **not** rise to reflect the failed quiz as complete —
     `attempt_completes_form` treats a failed scored quiz as an attempt, not a finished item.
6. Try to reach item 3 directly by URL: `http://127.0.0.1:$PORT/courses/qa-progression-block-course/3/`.
   - **Expect:** blocked — a redirect back to the course, or a 403/404. **Not** the topic content.
     This is the adversarial branch: gating must be enforced by the view, not only hidden in the
     table of contents.
7. Re-sit and pass the quiz.
   - **Expect:** item 3 unlocks and the percentage rises.

### B4. A pre-completed row does not trigger a recalculation

1. ```bash
   uv run python manage.py qa_complete_form --help
   ```
   then run it as its help describes, against a form the learner has not sat.
   - **Expect:** it succeeds. This command creates an already-complete `FormProgress` via
     `get_or_create(defaults={"completed_time": ...})` — which fired no recalculation before this
     change and must fire none after it. It is here to prove the change lost no live path *and*
     gained no new one.
2. Then run the batch recalculation and confirm the percentages settle correctly:
   ```bash
   uv run python manage.py recalculate_progress_percentages
   ```
   - **Expect:** it runs without an `ImportError` (it imports `completed_form_ids_by_user`, which
     moved apps) and the dashboard percentages afterwards match what the course pages show.

The app label changed, so `django_content_type` has new rows for `Form`. This is the one place a

### C1. Deadlines resolve against forms in the educator interface

1. Log in as `demodev@email.com`.
2. Go to `http://127.0.0.1:$PORT/educator/`.

### C2. Learner-side deadline display

1. Log in as a learner in that cohort and open the course table of contents.
   - **Expect:** the deadline you set in C1 shows against the correct form item.

1. Log in as `demodev@email.com`.
2. Open the topic at item 2 of `functionality-demo-show-end-with-quiz`

## Section F — failure and adversarial branches

Deliberately hostile input. None of this should 500 or leak content.

### F1. Required-question validation

1. As `demodev@email.com`, start the `qa-question-types-course` quiz (all four questions are
   required).
2. Submit the page with **nothing** answered.
   - **Expect:** an inline validation message naming the unanswered required questions; the page is
     **not** accepted; no 500. FLS returns HTTP 422 for HTMX validation errors, so a browser
     network-tab check should show **422**, not 200 and not 500.
3. Answer only the radio question and submit again.
   - **Expect:** validation still blocks, now naming the remaining three.

### F2. Repeat submission of the same page

1. Answer a page, submit, then use the browser **Back** button and submit the same page again.
   - **Expect:** the answers update rather than duplicating. `QuestionAnswer` has
     `unique_together = ["form_progress", "question"]`; a duplicate would surface as an
     `IntegrityError` 500.

### F3. Out-of-range and wrong-type item indexes

Visit each of these as a logged-in learner registered for the course:

| URL | Expect |
|---|---|
| `/courses/qa-question-types-course/99/` | 404 |
| `/courses/qa-question-types-course/0/` | 404 |
| `/courses/qa-question-types-course/1/fill_form/99` | 404 or redirect back to the form — **not** a 500 |
| `/courses/functionality-demo-show-end-with-quiz/1/start_form` where item 1 is a **Topic**, not a Form | 404 — `get_form_for_index` must reject a non-Form item |

### F4. Unregistered and unauthenticated access

1. Log out entirely and visit
   `http://127.0.0.1:$PORT/courses/qa-progression-block-course/2/start_form`.
   - **Expect:** redirect to login. Not the form, not a 500.
2. Log in as a learner **not** registered for that course and visit the same URL.
   - **Expect:** the course-access redirect (or a 404) — never the form's questions.
   - All authorisation to answer a form is *course* authorisation; this refactor deliberately did not
     add a form-level permission concept, so the existing course gate must still be the thing that
     stops you.

### F5. Submit-and-exit on a `submit_on_exit` form

The mid-course quiz in `functionality_demo_end_with_quiz` has `submit_on_exit: true`.

1. As a learner, start that quiz, answer page 1 only, then use the exit / leave affordance.
   - **Expect:** the attempt is **finalised and scored** rather than saved for resuming — you land on
     the completion page (or the course home showing it complete), and re-entering does not offer to
     resume.
   - **Expect:** the course percentage recalculated, since this path also ends in `complete()`.
2. Compare with the end-course quiz in the same course (`submit_on_exit` absent → `False`): exiting
   mid-attempt there must **save and allow resume**, and must **not** move the percentage.
