# Research: codebase (design_educator_interface_audit_log)

Question: what in the existing codebase does the audit log redesign (avatars where users are mentioned, export, compact accordion rows) touch, reuse or conflict with?

Not read in full (time-boxed): the done spec `educator-interface-11-audit-log` `1. spec.md` and its `research_codebase.md`. Everything below comes from reading the code directly.

## 1. How the three views are built today

All in `freedom_ls/educator_interface/views.py`.

- Base table `AuditLogEntryTable(DataTable)` (~L770): `page_size = 25`, `empty_state_template = "educator_interface/partials/audit_history_empty.html"`. `get_queryset` is `AuditLogEntry.objects.filter(organisation=request.organisation)` (site-aware manager, so multi-site scoped; plus an explicit organisation filter). **No `select_related` / `prefetch_related`** (`actor` FK is never read by the cells, only `actor_label`).
- Columns (4): When, Who, What (`card="primary"`), Details, each a cell template in `educator_interface/templates/educator_interface/data-table-cells/`: `audit_when.html` (date + HH:MM in two nowrap spans), `audit_who.html` (just `{{ object.actor_label|default:"System" }}`), `audit_what.html` (`{{ object.label }}`), `audit_details.html` (`object.description` + `object.reason`, plus a native `<details>` "Show N entries" listing `run_entries` as `actor_label, label, target_label` for bulk-run summaries). None of the columns is sortable (no `sortable=True`, no `default_sort`; ordering comes from model Meta `("-created_at", "-id")`).
- `TargetedAuditLogEntryTable` (~L802): adds a 5th "Target" column (`cotton/data-table-cells/text.html`, `attr="target_label"`) and `card_template = "educator_interface/partials/audit_log_card.html"` (below-md card: bold `label target_label`, then a `<dl>` of When / Who / Details that re-includes the cell templates).
- Learner History tab: `LearnerHistoryPanel(HistoryPanel)` -> `HistoryPanel(DataTablePanel)` (~L818), `table_key="history"`, `capability = "freedom_ls_audit_log.view_auditlogentry"`, `get_queryset` adds `.filter(subjects__contains=[subject_key(instance)])` (`subject_key` in `audit_log/writer.py`: `"app_label.model_name:pk"`). Registered as tab `"history"` in the learner `TabSet` (~L1032). Uses plain `AuditLogEntryTable` (4 columns, no Target). Empty message "No history for this learner yet...".
- Cohort History tab: `CohortHistoryPanel(HistoryPanel)` (~L1279) with `data_table = TargetedAuditLogEntryTable`, tab `"history"` (~L1295). Cohort rows are about different learners so Target is shown.
- Organisation Audit log: `OrganisationAuditLogTable(TargetedAuditLogEntryTable)` (~L1775) with `empty_state_template = ".../audit_log_empty.html"`; queryset excludes per-object entries of bulk runs (`Q(run_id__isnull=False) & ~Q(action__in=SUMMARY_ACTIONS)`); `get_rows` override attaches `run_entries` (windowed `RowNumber()`, up to `RUN_ROWS_KEPT = 50` per run), `run_entry_total`, `run_entries_more` to summary rows (a few extra queries, not per-row). Filters: `AuditActorFilter`, `AuditActionFilter`, `AuditPeriodFilter` (`educator_interface/filters.py` ~L184-261). `AuditLogConfig(OrganisationSectionConfig, ListViewConfig)` (~L1820): `url_name="audit-log"`, `menu_label="Audit log"`, `icon="notes"`, `table_key="audit_log"`, `view_capability="freedom_ls_audit_log.view_auditlogentry"`, `check_access_exempt_reason=...`. Listed in `NavGroup("Administration", [MemberConfig, AuditLogConfig])`. URL is the panel framework's generic `educator_interface:interface` route with path `audit-log`, `learners/<pk>/__tabs/history`, `cohorts/<pk>/__tabs/history` (there are no bespoke URL names for the audit log).
- Pagination: framework paginator, `page_size=25`, `{table_key}-page` param; stability on equal timestamps relies on `-id` tiebreak (tested).
- Permission: `freedom_ls_audit_log.view_auditlogentry` is granted to the two admin roles only (`role_based_permissions/roles.py` L26, L101; label in `registry.py` L110). Cohort admins/viewers get no History tab and a 404 (tested).
- Search: no `search_fields` on the audit tables (the product doc says "no search"). The design shows search and category chips; those are not asked for by the idea.

## 2. `AuditLogEntry` (`freedom_ls/audit_log/models.py`)

Fields: `created_at`, `organisation` (FK PROTECT, null), `actor` (FK to `AUTH_USER_MODEL`, null, `on_delete=set_null_by_instance`, `related_name="+"`), `actor_label` (CharField, unbounded, = `actor.display_name` at write time, "" for system), `action` (`noun.verb`), `target_content_type` + `target_object_id` (GenericFK `target`, `target_object_id` is a string), `target_label` (unbounded text), `subjects` (ArrayField of `"app.model:pk"` strings, GIN index), `reason` (<=500), `details` (JSONField; this is the "payload/changes" field; there is no separate `changes` field), `run_id` (UUID, indexed). Properties: `audit_action`, `label`, `description` (calls the action's `describe`). Append-only (`update`/`delete`/`bulk_update`/`save`-on-existing raise `AppendOnlyError`; only `prune_before` deletes).

Action codes and `describe` functions are in `freedom_ls/audit_log/actions.py` (`FLS_AUDIT_ACTIONS`, 26 actions; downstream `AUDIT_LOG_EXTRA_ACTIONS` have no describer). Describers return **plain strings** from `details` keys: `cohort`, `course`, `self_service`, `source`/`destination` (move), `old`/`new` (renames), `outcome`+`cohort` (learner.added), `role_label`/`role` + `scope`, `counts` (run summary). `details` for rename and move already hold old/new as free text, so a design "Changes (old -> new)" block can be built from `details["old"]`/`["new"]`, `source`/`destination` without model changes; fields of other kinds (role, outcome) are not old/new pairs.

**Which fields name users**
- Actor: `actor` FK (kept while the user lives) + `actor_label` (survives).
- Target: for learner/user/member actions the target is a Learner / User / OrganisationMember; only `target_label` (a name string) and `target_content_type`/`target_object_id` (a string pk; GenericFK) are stored. `subjects` also carries `app.model:pk` keys.
- `details` strings: names of cohorts/courses, not user ids. Run summary `details["rows"]` are `(email-or-label, outcome)` pairs, strings only.
- **Deleted users**: `actor` is nulled by `set_null_by_instance` and only `actor_label` remains. So an avatar for the actor can only be built from the FK while it exists; a deleted actor must fall back to a label-derived chip. Also the `AuditActorFilter` treats "System" as `actor__isnull=True, actor_label=""`, so a deleted-user entry is not System. The target side has no FK (GFK to a Learner/User that may be deleted); a Learner is deleted cascading from User? Not verified. The comms app already has the pattern: `comms/templates/comms/partials/participant_avatar.html` renders `c-panel-avatar-chip` or, for a deleted user, a grey circle with the `user` icon and aria_label "Deleted user".
- `actor_label` is a copy of `display_name` (falls back to email). `README` notes deleted users' names/emails remain in entries (documented in product security doc).

## 3. Avatars

There is no photo/avatar/picture field on `accounts.User` (`freedom_ls/accounts/models.py`): there is `display_name` (property, uses `display_name_for(first, last, email)`) and an `initials` property (documented cascade; returns `None` when it cannot, caller renders a fallback icon). So "avatar" here means initials circle.

Existing component: `freedom_ls/panel_framework/templates/cotton/panel-avatar-chip.html` (`<c-panel-avatar-chip name user_id initials secondary size name_hidden />`). Initials circle is `aria-hidden`; colour slot from `avatar_slot` filter (`panel_framework/templatetags/panel_tags.py`) keyed on `user_id`; six `panel-avatar-N` colour classes; `size` "md" (size-8) or "lg"; `name_hidden` shows the circle alone. Tests: `panel_framework/tests/components/test_avatar_chip.py`. Used by: `educator_interface/templates/educator_interface/data-table-cells/learner.html` and `member.html` (avatar + bold name + email second line + status badges), `panel-attention-row.html`, `learner_messages.html`, comms `participant_avatar.html`, `recipient_picker.html`, `conversation_row.html`, `thread.html`.

Implication: the audit cells need a `user_id` for the colour slot. The actor FK gives `actor_id`; `actor_label` gives name only. When `actor_id` is null (deleted user or system) there is no id for a stable colour (use a fixed id/blank fallback or the deleted-user circle). For the Target, only the GFK pk string exists, and only when `target_content_type` is a user-like model (Learner pk is not the User pk; avatar colour would then differ from the one used on the learners list unless the Learner's `user_id` is resolved, which needs a query). That is a risk: resolving target avatars with consistent colours needs prefetching `target` per content type (GFK prefetch) or accepting colour keyed on whatever pk is available. The `fls-dev:icon-usage` skill governs the icon (the `user` semantic icon is already used in `participant_avatar.html`).

How other screens show a user: `data-table-cells/learner.html` and `member.html` (above); learner list queries select_related user.

## 4. Existing export machinery (reuse, do not rebuild)

The panel framework already has a generic streamed CSV export; the audit tables just have not opted in.
- `freedom_ls/panel_framework/tables.py`: `ExportColumn(header, value: str | Callable)` (L187; `cell()` runs `escape_csv_formula`), `DataTable.get_export_columns()` (L246, empty by default = no export), and the context keys `exports` / `export_changes` (L437-438).
- `freedom_ls/panel_framework/templates/panel_framework/partials/table_toolbar.html` L117-120: renders an `Export CSV` link (`{{ base_url }}?{table_key}-export=csv`) when the table has export columns, so declaring export columns on the audit tables automatically adds the link (it is a plain `<a>`, text-sm).
- `freedom_ls/panel_framework/views.py`: `_export_response` (L1175) streams a `StreamingHttpResponse` with `UTF8_BOM`, `EchoWriter` (`base/csv_import.py`), `freedom_ls.base.csv_safety` formula escaping, `queryset.iterator(chunk_size=500)`, filename `{table_key}[-{scope_slug}]-{date}.csv`; it honours search/filter/sort but ignores pagination; the queryset is built before streaming so site scoping holds. `_respond` (L1210) intercepts `{table_key}-export` for any `DataTablePanel`. `DataTablePanel.get_export_scope_slug` (`panels.py` L265) lets a panel name its scope in the filename (educator_interface `views.py` ~L1142 overrides it for a cohort).
- Existing user: `LearnerDataTable.get_export_columns` (`educator_interface/views.py` ~L600) with comment that values must read prefetched caches so no per-row queries.
- Permission: the export is a variant of the panel GET, so it is behind the same panel/section capability gate as the table (`view_capability` / panel `capability`); I did not trace the exact order of the capability check vs `_respond` and the spec should confirm by test (existing tests: `educator_interface/tests/test_views.py` ~L1652, L1729; `panel_framework/tests/test_tables.py` L861-931).
- Audit of exports: none. The product roadmap says "report downloads are not logged" and "the log cannot be exported to CSV". If an export of the audit log must itself be audited, there is a precedent for a read being audited (`conversation.viewed` action, `FLS_AUDIT_ACTIONS`, written when an admin opens a conversation), but a new action code must follow glossary vocabulary (`audit_log/tests/invariants/test_vocabulary.py`), and entries written during a streaming response need `record_entry` called before streaming (site thread-local clears).
- Rate limiting: none for exports. `django-axes` is installed (login lockout only); `form_engine/views.py`, `referral_tracking/hits.py` and `course_applications/views.py` have their own throttles. No export-specific limit exists; an unbounded export of a long-retained table is the main exposure (`queryset.iterator` streaming mitigates memory; no row cap).
- Other export code (different mechanism): `site_aware_models/admin_exports.py` (admin export actions, `has_export_permission`), `reports` app downloads, `base/csv_import.py` (CSV import for learners; `EchoWriter`), earlier specs `3. done/2026-10-29_12:46_more_lead_admin_exports/` and `3. done/2026-10-03_05:29_educator-interface-2-panel-framework-tables/research_csv_export.md`. django-import-export is not used.
- Export columns design points: actor name/email (read `actor.email` needs `select_related("actor")`; deleted actor has no email), target, action label and code, `description`, `reason`, `details` (JSON), `run_id`, `created_at` (use `timezone.localtime` like `_last_active_cell`). `reason` and labels are user-derived free text, so `escape_csv_formula` (applied by `ExportColumn.cell`) matters. CSV would contain personal data (names; `rows` of a run summary include emails), so who may export is the same `view_auditlogentry` capability unless the spec adds a separate one (new capabilities are registered in `role_based_permissions/registry.py`).

## 5. Accordion / disclosure and density

- Cotton `freedom_ls/content_engine/templates/cotton/accordion.html`: native `<details>/<summary>` with grid-template-rows animation, chevron `c-icon name="dropdown"`, `[[open]>&]` variants, `motion-safe:` gates. It is a learner-content component (margins `my-6`, big padding `px-5 py-4`, bordered rounded card, body goes through `{% markdown slot %}`, lives in content_engine), so it is not suited as-is for a table row and its markdown slot sanitises content; reuse the *pattern* (native `<details>`, chevron rotate, `[[open]>&]` variants).
- The existing audit cell already uses a bare `<details class="mt-1"><summary class="cursor-pointer text-sm">Show N entries</summary>` (`audit_details.html`) and `table_toolbar.html` uses `<details>` for filter disclosures. Also `reports/templates/reports/partials/cap_disclosure.html`, `quiz_confusion.html`, `at_a_glance.html`, and `base/templates/cotton/dropdown-menu.html`, `quick-view-trigger.html`.
- Alpine in `panel_framework/static/panel_framework/js/alpine-components.js`: `appModal`, `quickView`, `tableSelection`, `listRefresh`, `headerRefresh`, a toggle with `aria-expanded` (~L535) used by `panel_toggle.html`; no accordion/row-expander component. The design's "expand all" would need either `<details>` toggled by a small Alpine component or a new one (note: HTMX swaps of a table region reset open state).
- Rows are `<tr>`s generated by the framework's table template; an accordion row means either a second `<tr>` per entry (colspan) toggled by Alpine, or putting a `<details>` inside the existing Details cell (a cell-only change). The framework's mobile card layout (`card_template`, `card="primary"/"secondary"/"md_only"` on `Column`) must be updated in parallel (`audit_log_card.html`). Check `panel_framework/templates/panel_framework/` table templates for how rows and cards are produced before choosing.
- Density: `Column.header_class` / `cell_class` exist for per-column padding; no table-wide density setting was found. The learner cell uses `size-8` avatars; a compact log would use `name_hidden` or md chips.

## 7. Conflicts and risks

1. **Deleted users**: `actor` FK is null after deletion; only `actor_label` survives. Avatar and export must render from the label, with a deleted-user fallback (pattern in `comms/.../participant_avatar.html`). `AuditActorFilter` already treats deleted-user entries as neither System nor any user.
2. **Target and subject users have no FK**: only `target_label` string, GFK pk and `subjects` keys. Showing avatars for "users mentioned" (learners as targets, cohort history rows) needs resolving ids to users (query per content type, extra prefetch, or the History-tab learner already known from the page instance). Learner pk is not the User pk. Within the free text (`details["cohort"]`, run summary rows, `reason`) no user is identifiable, so "where users are mentioned" realistically means actor and (learner/member/user) target. Stale/duplicate display names make avatar-by-label ambiguous.
3. **Query budget**: currently no related-object reads; adding `select_related("actor")` (and target resolution) must keep the History tab within `test_the_history_tab_renders_within_a_query_budget`. CLAUDE.md requires select_related for related reads.
4. **Multi-site isolation**: manager is site-aware plus organisation filter; export builds its queryset before streaming (documented in `_export_response`). Any new export/"affected members" query must use `AuditLogEntry.objects` (not `unscoped`) and organisation-filter. Actors listed in `AuditActorFilter` come from `User.objects` filtered by the organisation's entries.
5. **PII in export**: names, emails (run-summary `details["rows"]`), free-text `reason`. README says `details` must not hold tokens/links/emails beyond labels. The export is every matching row (no page cap) with no export-specific audit entry, no rate limit and no extra capability today.
6. **Docs to update**: `docs/product/educator-interface.md` History section (~L125-133) says "The log has no search or CSV export" and describes the filters; `docs/product/roadmap.md` L103 says "the log cannot be exported to CSV, and report downloads are not logged"; `freedom_ls/audit_log/README.md` (UI description, "disclosure of its per-object entries"); `docs/product/security-and-data-handling.md#audit-log-built` (data handling of exports of personal data). `docs/product/webhooks.md` and `messaging.md` mention the History tab only incidentally.
7. **Accordion hides required info**: the reason is currently always visible (and asserted visible by Playwright); the content_engine accordion's editorial note says do not hide required content. Spec must decide which fields stay in the collapsed row.
8. **HTMX re-render**: tables re-render on `LEARNER_CHANGED` refresh events and pagination/filter swaps, which reset client-side open/closed state; "expand all" state would not persist (native `<details>` has the same behaviour).
9. **Design vs existing scope**: design.md says it is a visual reference only. The design draws search, category chips, an "Area" column, a sortable When column, learner search, "Changes (old -> new)" and "affected members" blocks; none of these is in the idea beyond avatars/export/compact accordion, and `HistoryPanel`/org log currently have no search or sort, so they should stay out unless the spec asks.
10. **Genericity**: `panel_framework` and `audit_log` carry no educator names today; an avatar-in-audit change belongs in `educator_interface` cell templates, and any `audit_log` model/describe change must keep `audit_log` importing only `accounts`, `base`, `organisations`, `site_aware_models` (README "Dependencies"; `docs/app_structure.md`). The `audit_log` package must not import `panel_framework`'s avatar component.
