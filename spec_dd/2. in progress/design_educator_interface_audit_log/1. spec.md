# Spec: Educator audit log: avatars, export, compact expandable rows

Source: `idea.md`. Design reference: `design.md` (read it as that file says; it is never scope).

## Purpose

The audit log built by `spec_dd/3. done/2026-10-29_08:48_educator-interface-11-audit-log/` shows
four or five wrapped text columns per entry, names people as bare text, and cannot leave the
system. Admins need to scan it quickly, tell people apart at a glance, and hand it to an auditor.
This spec makes every row one compact line with an initials avatar beside each person, moves the
rest into an expandable panel, and adds a CSV export to the learner History tab, the cohort
History tab and the organisation Audit log.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `audit_log.exported` | coined | The audit action written when someone exports an audit log CSV. Noun `audit_log` (the log the `AuditLogEntry` rows make up) and verb `exported` are both new to the glossary's Changes section. |
| row detail | coined | A `DataTable` row's expandable panel: hidden content under the row, opened by a toggle in the row. |

## Scope

In:

- Initials avatars beside every person the log names, on all three screens and their mobile cards.
- Compact one-line rows, with the rest of an entry in a row detail.
- A generic row detail capability in `panel_framework`.
- CSV export on all three screens, at every width, with each export recorded.

Out:

- Everything the design draws beyond the idea (see `design.md`).
- Profile pictures. `accounts.User` has no image field; an avatar is an initials circle.
- JSON export, asynchronous or emailed exports, a row cap.
- Keeping rows expanded across pagination, filtering or a refresh swap.

## Decisions

1. **The avatar's initials come from the stored label; its colour comes from the live user's pk.**
   The name beside it stays the snapshot (`actor_label`, `target_label`). Keying colour on the
   user pk gives a person the same colour here as in the learner and member tables.
2. **No person, no initials circle.** System (`actor` null, `actor_label` empty) shows the
   `settings` icon in a neutral circle and the text "System". A deleted user (`actor` null with
   `actor_label` set, or a person target whose row is gone) shows the `user` icon in a neutral
   circle beside the stored label, as
   `freedom_ls/comms/templates/comms/partials/participant_avatar.html` does. An Inactive user still
   has a row and keeps their initials chip.
3. **Export is gated exactly as the screen is.** `freedom_ls_audit_log.view_auditlogentry` gates
   all three; whoever cannot see a screen gets a 404 on its export.
4. **The organisation log's export includes a bulk run's summary row and its per-object entries,**
   one CSV row each, tied together by the Run ID column. The screen hides the per-object entries
   behind the summary row and caps that list at `RUN_ROWS_KEPT`; the export has no cap.
5. **An export's entry always targets the organisation,** so it appears only on the organisation
   Audit log (`record_entry` puts the target in `subjects`, and a History tab lists entries whose
   subjects name its learner or cohort). The export never contains its own entry.
6. **One name per column across the model, the screen and the CSV.** A column the screen shows
   keeps its screen name in the CSV (When, Who, What, Target); a CSV-only column is named for the
   field it holds (Actor email is `actor.email`, Action is `action`, Description is `description`, Reason is `reason`, Run ID is
   `run_id`). The CSV carries no `details` JSON: auditors read it in a spreadsheet.
7. **Row detail lives in `panel_framework` and stays generic.** `extract_panels_framework` will
   move the table machinery into a package, so no audit or educator name enters it.

## Requirements

### `panel_framework`: row detail

- `DataTable` gains an optional row detail template class attribute (default `None`) and a
  per-row predicate saying whether a row has a detail (default: every row, when the template is
  set).
- `freedom_ls/panel_framework/templates/cotton/data-table.html`, `md` and up: a table with a row
  detail template gets a trailing toggle column whose visually hidden header is "More". A row with
  a detail renders a `<button>` there with `aria-expanded`, `aria-controls`, an accessible name
  naming the row, and the `dropdown` icon (`aria-hidden`) rotating on open under `motion-safe:`.
  The detail renders in a following `<tr hidden data-row-detail>` with one `<td colspan>` spanning
  every column, the bulk-selection column included. A row without a detail has an empty toggle
  cell. The empty-state row's `colspan` counts the toggle column.
- The `tbody tr` rules in `tailwind.components.css` skip `[data-row-detail]` rows, so an open detail adds no
  rule of its own and a closed one leaves the borders as they are today.
- A new Alpine component, `rowDetail`, in
  `freedom_ls/panel_framework/static/panel_framework/js/alpine-components.js`, with `x-data` on the
  table: a toggle shows or hides the row its `aria-controls` names and updates `aria-expanded`.
  Rows open independently. Focus stays on the button. An HTMX swap of the table region renders
  every row closed.
- Below `md` (`cotton/data-table-card.html` and any `card_template`), a card whose row has a
  detail ends with a native `<details>`/`<summary>` holding the same detail template.
- A table without a row detail template renders exactly as today.

### `panel_framework`: export

- `_export_response` in `freedom_ls/panel_framework/views.py` gains two `DataTablePanel` methods,
  whose defaults leave every existing export unchanged:
  - `get_export_queryset(request)`: the rows the export narrows with the same `parse_query` and
    `filter_queryset` as the screen, through `narrow(request, queryset)`, which gains that
    optional second argument. Default `self.get_queryset(request)`.
  - `before_export(request, rows)`: called after narrowing and before the
    `StreamingHttpResponse` is built, while the site thread-local is still set; returns the rows to
    stream. Default returns them unchanged.
- `ListViewPanel` forwards both to same-named `ListViewConfig` classmethods, bound in `_bind_root`
  as `cell_context` is, so a config such as `AuditLogConfig` can override them.
- `freedom_ls/panel_framework/templates/panel_framework/partials/table_toolbar.html`: the Export
  CSV link also renders below `md`, for every table with export columns, including a table with
  no filters, search or sortable columns (today the mobile block renders only
  `{% if toolbar or sortable_columns %}`).

### `educator_interface`: compact rows and avatars

In `freedom_ls/educator_interface/views.py` and
`freedom_ls/educator_interface/templates/educator_interface/data-table-cells/`:

- `AuditLogEntryTable` columns become When, Who, What; `TargetedAuditLogEntryTable` adds Target
  after What. The Details column and `audit_details.html` go.
- **When** (`audit_when.html`): one line, date and `HH:MM`, inside
  `<time datetime="<ISO 8601 with offset>">`.
- **Who** (`audit_who.html`): `c-panel-avatar-chip` with `actor_label` as name and `actor_id` as
  `user_id`, or a Decision 2 circle.
- **What** (`audit_what.html`): the action `label`, then the `description` in muted text, on one
  line. The column's `cell_class` caps its width so `truncate` clips the description inside the
  table rather than widening it.
- **Target**: `target_label`, with an avatar when the target is an `accounts.User`, a `Learner` or
  an `OrganisationMember`. One helper resolves user pks for a list of entries, keyed on
  `target_content_type_id` compared with `ContentType.objects.get_for_model` ids (never reading
  `target_content_type` per row), with one `objects` query per model type and no `is_active`
  filter. The user pk is `target_object_id` for a `User` and the row's `user_id` for the other
  two; a missing row gets the deleted-user circle. `AuditLogEntryTable.get_rows` calls it on the
  page's entries; `OrganisationAuditLogTable.get_rows` calls it once on the page's entries and the
  attached run entries together. Any other target shows its label with no avatar.
- **Row detail** (`audit_row_detail.html`): the description under a "Description" label, the
  reason under "Reason", and for a bulk run summary its entries under "Entries" (each line with
  actor and target avatars) and the "and N more" line. A row has a detail when it has a description, a reason or
  run entries.
- **Mobile card** (`educator_interface/partials/audit_log_card.html`): first line the Who chip and
  the When; second line the label, a visible separator, and the Target with its avatar; then the
  row detail disclosure. No labelled field renders empty.
- Every value stays escaped user text; nothing is marked safe.

### `educator_interface`: export

- `AuditLogEntryTable.get_export_columns()` returns, in this order:

  | Header | Value |
  | --- | --- |
  | When | `timezone.localtime(created_at).isoformat()` (ISO 8601 with offset) |
  | Who | `actor_label`, or `System` when empty |
  | Actor email | `actor.email` while the actor exists, else empty |
  | What | `label` |
  | Action | `action` |
  | Target | `target_label` |
  | Description | `description` |
  | Reason | `reason` |
  | Run ID | `run_id`, or empty |

  Values go through `ExportColumn`, so `escape_csv_formula` applies.
- The export queryset adds `select_related("actor")`; the screen's queryset does not.
- The organisation log's `get_export_queryset` is `AuditLogEntryTable.get_queryset(request)`,
  without `OrganisationAuditLogTable`'s exclusion of per-object entries. The History tabs export
  what they show.
- `get_export_scope_slug` names the scope in the filename: the organisation slug, the cohort as
  the cohort learner export already does, and the learner's `display_name` (which falls back to
  the email).
- `before_export` on all three screens writes the export's entry with `record_entry`:
  `action="audit_log.exported"`, `actor=request.user`, `target` and `target_label` the
  organisation, `organisation=request.organisation`, and
  `details={"scope": "organisation" | "learner" | "cohort", "scope_label": <learner or cohort name,
  empty for the organisation>, "count": <rows.count() at request time>, "filters": <the applied
  filters' toolbar chip text, joined; empty when none>}`. It returns the rows excluding that
  entry's pk.

### `audit_log`

- `freedom_ls/audit_log/actions.py`: add `AuditAction("audit_log.exported", "Audit log exported",
  _describe_export)` to `FLS_AUDIT_ACTIONS`. `_describe_export` returns `"<count> entries"`,
  prefixed by the `scope_label` when there is one and followed by `", filtered by <filters>"` when
  filters were applied.
- `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md`, Changes section, gains the noun
  `audit_log` and the verb `exported` ("a copy of records left the system as a file:
  `audit_log.exported`"; not `downloaded`), and
  `freedom_ls/audit_log/tests/invariants/test_vocabulary.py` adds them to `NOUNS` and `VERBS`.
- `freedom_ls/audit_log/README.md` records the new code, its target and details, and that
  `count` is taken at request time.

## Testing

- **Row detail:** the toggle column, button and hidden detail row render with matching
  `aria-controls`, and the detail's `colspan` and the empty-state `colspan` cover every column,
  with and without bulk actions; a row the predicate rejects has no button; the card renders a
  `<details>`; a table without a detail template renders as before.
- **Export hooks:** an overridden export queryset is narrowed by the screen's filters; a
  `ListViewConfig` override reaches the export; `before_export` runs once, before streaming, and
  its rows are what streams. The Export CSV link renders below `md` on a table with no toolbar.
- **Avatars:** System gets the `settings` circle; a deleted actor gets the `user` circle and the
  stored label; `Learner`, `OrganisationMember` and `User` targets get a chip keyed on the user pk,
  an Inactive learner included; a target whose row was deleted gets the `user` circle; a cohort
  target gets none; a nameless user's initials come from the email label; markup in a label
  renders as text.
- **Query budget:** `test_the_history_tab_renders_within_a_query_budget` passes with at most 3
  more queries; the organisation log gets the same test with bulk run summaries on the page.
- **Export:** the History tabs export only their subject's entries, across all pages; the
  organisation export honours each of the Who, What and When filters and includes a bulk run's
  summary row and per-object entries with their Run ID, and a What filter drops per-object
  entries that do not match it; another organisation's or site's entries
  never appear; a cohort admin or cohort viewer gets a 404; a reason starting with `=` is
  formula-escaped; a non-ASCII name survives.
- **Export entry:** each export writes one `audit_log.exported` entry targeting the organisation,
  with the right scope, scope label, count and filters; it shows on the organisation log and on
  neither History tab; it is not in the CSV that wrote it.
- **Playwright:** `test_a_deactivation_reason_shows_on_the_learner_history_and_the_audit_log`
  (`freedom_ls/educator_interface/tests/playwright/test_learner_page_flow.py`) opens the row,
  once by keyboard, before asserting the reason, and the table still fits its wrapper; at mobile
  width a card's disclosure opens.

## Open questions

- Q: Do the organisation export's filters also narrow a bulk run's per-object entries? → A: Yes,
  per-object entries are filtered like every other entry. (Assumed default: matches "every entry
  matching the current filters". Overrule by editing Decision 4 and `educator_interface`: export.)
- Q: What is the CSV header for the actor's email? → A: "Actor email". (Assumed default: Decision 6
  names a CSV-only column for its field, `actor.email`. Overrule by editing the export column table.)

## Success criteria

- Every entry on the three screens at `md` and up is one line, and the tables fit their wrappers.
- Rendering any of the three screens costs no per-row query.
- A downloaded organisation CSV opened in a spreadsheet holds every entry matching the screen's
  filters, including bulk runs' per-object entries that match them.
