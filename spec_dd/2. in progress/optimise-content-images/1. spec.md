# Spec: optimise content images

## Purpose

Course images are authored outside FLS and loaded by `content_save`. Authors drop in whatever their
camera or screenshot tool produced, so a topic image is routinely 5 MB, and every learner who opens
that topic downloads all of it to render it in a card 576 px wide.

`content_save` re-encodes each image once, at ingest, and stores that instead of the original. One
image in, one image out. `File.file` holds the optimised bytes, and no new model, field or copy is
introduced. `idea.md` settles the approach and `research_serve_time_renditions.md` records why a
serve-time resizer loses against a private bucket, signed URLs and a non-overwrite storage alias.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `ImageEncodeDecision` | coined | what `optimise_image` returns: the bytes to store and what to tell the author. Follows `CourseAccessDecision` (`freedom_ls/course_access/backends.py:41`), the house suffix for a resolver's return value |
| `ImageEncodeStatus` | coined | the four things the encoder can have done, as a `StrEnum` in the shape of `CourseListingStatus` (`freedom_ls/learner_interface/utils.py:101`). Deliberately not `*Outcome`: `Course.learning_outcomes` (`content_engine/models/courses.py:69`) already owns that word in this app |

## Scope

**In.** `content_engine.File` rows whose `file_type` is `File.FileType.IMAGE`, written through
`save_file_to_db` in `freedom_ls/content_engine/management/commands/content_save.py`. A shared
image-decode guard in `freedom_ls/base/`. The author-facing output `content_save` prints.

**Out.** A responsive `srcset` ladder, whose widths and markup `research_responsive_delivery.md`
works out if anyone picks it up. Stored `width`/`height` on `File`, so `c-picture` still cannot
reserve space and the page still shifts as figures arrive. Splitting the lightbox URL from the inline
thumbnail. A per-image opt-out. Skipping unchanged files between runs. Organisation logos and any
other image path outside `content_engine.File`.

Every run re-encodes everything, tens of seconds for a few hundred images. Each encode starts from the
pristine source on disk, never from what was stored last time, which is what makes repeated runs
produce identical bytes with no cumulative quality loss. A later optimisation that skips unchanged
files must key on the source file's identity. One that reads the stored output back as its input
would look like a pure speed-up and quietly introduce generation loss.

## Decisions

**WebP, and not AVIF.** Pillow 12.3.0, the version this repo locks, bundles libavif, so
`features.check("avif")` is already true and AVIF costs no new dependency. AVIF loses on reach. This
feature stores exactly one file and `picture.html` renders exactly one `<img src>`, with no
`<picture>`/`<source>` fallback anywhere in the codebase, so the stored format has to decode in every
browser that can reach a course player. WebP
does; AVIF is around 95%, and closing that gap means the fallback markup this change leaves alone.
AVIF also encodes 2-3x slower inside a synchronous command and would need the `pillow>=11.0` floor
raised.

**Lossless is the default for anything not already lossy, and a size floor gates the comparison.**
Lossy WebP always chroma-subsamples, which is what smears coloured text and thin lines, so raising
the lossy quality never fixes a screenshot. Measured against real FLS screenshots at 1600 px, the
lossy/lossless ratio runs 0.215 to 2.2, overlapping the band a bare ratio threshold would need, and
every one of them encodes losslessly to under 165 KB. Gating the second encode behind a 250 KB
lossless result keeps screenshots out of the comparison entirely, and leaves the 3x ratio to
arbitrate only large images, which are overwhelmingly photographs. A photographic source lands
between 0.05 and 0.11.

**A JPEG source gets one lossy encode and no comparison.** The pixels are already lossily compressed,
so a lossless encode preserves the existing artefacts bit-exactly at several times the bytes. EXIF
camera tags are read for the ambiguous non-JPEG case only.

**The decompression-bomb policy diverges from `check_logo_safety`.** That validator escalates
`DecompressionBombWarning` to an error because it is refusing an untrusted upload. Escalating here
would classify a legitimate 90-179 megapixel author photo as unprocessable and store it at full size.
That is the worst outcome available for the largest file in the tree. The optimiser lets the warning
band decode and catches `DecompressionBombError` only. `Image.MAX_IMAGE_PIXELS` stays at Pillow's
default in both paths, and `ImageFile.LOAD_TRUNCATED_IMAGES` is never set. It is global, and
`check_logo_safety` depends on truncated files failing to decode.

**The tunables are module constants, not `ContentEngineConfig` settings.** Nothing has asked to tune
them per deployment, and each `Setting` costs a declaration, a documentation row and a test.
Promoting one later is a small change.

## Requirements

### 1. Shared decode guard, in a new `freedom_ls/base/images.py`

`content_engine` has no dependency on `organisations` (`docs/app_structure.md:184`), and that document
requires any new cross-app edge to be approved before code is written (`:5`). Both
`content_engine --> base` (`:47`) and `organisations --> base` (`:118`) already exist, so the guard
goes in `base` and no edge is added.

The module holds, with the reasoning currently commented at `organisations/validators.py:72-101`
moved to it:

- `DECODE_FAILURES = (OSError, Image.UnidentifiedImageError, SyntaxError, ValueError, struct.error,
  IndexError)`. A PNG whose chunk checksum fails raises `SyntaxError`, one whose `IHDR` is too short
  raises `ValueError`, and only an unrecognisable or truncated body raises `OSError`, so catching
  `OSError` alone lets the first two escape. Seeking a truncated animated GIF's frames adds the last
  two: the plugin reads the remaining bytes without checking there are enough, so a two-byte duration
  field raises `struct.error` and a one-byte block label raises `IndexError`, depending on where the
  truncation falls.
- `BOMB_FAILURES = (Image.DecompressionBombWarning, Image.DecompressionBombError)`.
- `bomb_warnings_as_errors()`, a context manager wrapping `warnings.catch_warnings()` and
  `warnings.simplefilter("error", Image.DecompressionBombWarning)` so the warning band becomes
  catchable. Its docstring says that a caller which does *not* use it is choosing to decode the
  warning band, and why the two callers here choose differently.

`check_logo_safety` (`freedom_ls/organisations/validators.py:51`) imports all three rather than
inlining them. Its behaviour does not change and its existing tests must still pass untouched.

### 2. The optimiser, in a new `freedom_ls/content_engine/images.py`

One pure function with no Django or ORM imports, so it is testable on bytes alone.

```python
class ImageEncodeStatus(StrEnum):
    OPTIMISED = "optimised"
    KEPT_SOURCE = "kept source"
    PASSTHROUGH = "passthrough"
    UNDECODABLE = "could not decode"


@dataclasses.dataclass(frozen=True)
class ImageEncodeDecision:
    """What to store, and what to tell the author. Always returned."""

    status: ImageEncodeStatus
    source_format: str | None
    source_size: tuple[int, int] | None
    data: bytes | None
    suffix: str | None
    mime_type: str | None
    lossless: bool | None
    stored_size: tuple[int, int] | None
    error: str | None


def optimise_image(raw: bytes, suffix: str) -> ImageEncodeDecision: ...
```

`data is None` means "store `raw` unchanged" and covers SVG, animation, undecodable bytes, an
already-small WebP and the never-grow guardrail alike, so the caller has exactly one branch and can
never pair one branch's bytes with the other's name. The three statuses behind it are not
interchangeable to an author, so `status` tells them apart, and `source_format` and `source_size` are
filled in whenever Pillow decoded far enough to know them. Both are `None` when it did not: a PNG
whose `IHDR` is too short fails inside `Image.open` itself, before there is a format to name. The per-file line in §4 is written from the
decision alone, with no second look at the source.

`data`, `suffix`, `mime_type`, `lossless` and `stored_size` are set together or not at all, and are
`None` unless `status` is `OPTIMISED`. `error` is the mirror of that: `f"{type(err).__name__}: {err}"`
when `status` is `UNDECODABLE`, and `None` otherwise. It exists because the caller, not
`optimise_image`, is the one that knows the relative path and does the warning in §4, and nothing
raises out of the function for it to catch.

Constants, each named and commented:

| Constant | Value | Note |
| --- | --- | --- |
| `MAX_DIMENSION_PX` | `1600` | longest edge; covers the lightbox at 2x density |
| `LOSSY_QUALITY` | `80` | 0-100 fidelity dial, lossy branch only |
| `LOSSLESS_EFFORT` | `100` | passed as `quality=`. Under `lossless=True` this is encode *effort*, not fidelity. The pixels are bit-exact either way, so the two numbers are not commensurable and the comment must say so |
| `ENCODE_METHOD` | `6` | 0 fast, 6 slower and smaller. Encoded once, read many times |
| `SECOND_ENCODE_BYTES` | `250 * 1024` | the lossless size above which a second encode is worth running |
| `LOSSY_WINS_DIVISOR` | `3` | the margin lossy must beat lossless by. Integer arithmetic, no floats |
| `SVG_SUFFIXES` | `{".svg"}` | `.svgz` is deliberately absent. `get_file_type_from_extension` (`content_save.py:442`) does not list it, so it is never `FileType.IMAGE` and cannot reach here |

**Order of operations.** Each step below is load-bearing, and getting the order wrong fails silently.

1. **SVG by suffix, before any decode.** `suffix.lower() in SVG_SUFFIXES`, lowercased because
   `get_file_type_from_extension` (`content_save.py:440`) lowercases before its own comparison, so
   `DIAGRAM.SVG` is an `IMAGE` and must not then fall through to a decode it cannot survive. Pillow
   has no SVG codec, and the extension is the same key that function already uses, so the two cannot
   drift. This is the one status whose `source_format` cannot come from Pillow, so set it to `"SVG"`.
   An SVG mislabelled `.png` needs no sniffing, because it lands in the decode-failure branch and is
   stored unchanged either way.
2. **`Image.open(io.BytesIO(raw))`**, not the file handle. A `BytesIO` keeps backing the lazy image
   after the caller's `with` block exits.
3. Record `source_format = opened.format` and the source dimensions **before** step 6, which mutates
   `size`.
4. **Animation guard:** `source_format != "MPO" and getattr(opened, "n_frames", 1) > 1` is
   `PASSTHROUGH`. Use `getattr`, not `img.is_animated`. `JpegImageFile` and `BmpImageFile` define neither
   attribute. The MPO exclusion is not optional. Some phone `.jpg` files open as format `"MPO"` with
   `n_frames == 2`, and a bare frame count would silently pass real 5 MB photos through untouched.
   Route MPO through the JPEG rule and encode frame 0.
5. **Already WebP and within the cap** is `PASSTHROUGH`. Re-encoding buys nothing and would spend a
   generation of quality. An over-cap WebP falls through to the general rule.
6. **`opened.draft(None, (MAX_DIMENSION_PX * 2, MAX_DIMENSION_PX * 2))`.** A no-op for non-JPEG. For
   JPEG it uses libjpeg DCT scaling to cut the decode buffer 4-64x. It must precede step 7, because
   `draft()` works only on an unloaded image and `exif_transpose()` loads. `thumbnail()`'s own
   internal `draft()` therefore never fires and does not substitute for this.
7. **`img = ImageOps.exif_transpose(opened)`.** This rotates the pixels so phone photos do not come
   out sideways. It returns a new image, a copy when there is no orientation tag, and never `None`, so
   no guard is needed. It calls `load()` as its first statement, which is where a corrupt body raises.
8. **Capture `icc_profile = opened.info.get("icc_profile")` and the camera-EXIF signal.** The signal is
   `tags = opened.getexif()`, true when `ExifTags.Base.Make` or `ExifTags.Base.Model` is present. Read
   camera tags through `getexif()`, never `img.info["exif"]`, so a PNG carrying EXIF in a text chunk
   is handled. This still reads `opened`, so steps 2 to 8 sit inside one guarded block and inside
   whatever `with` holds the opened image.
9. **Mode conversion, before the resize.** `img.convert("RGBA" if img.has_transparency_data else
   "RGB")` when `img.mode not in ("RGB", "RGBA")`. Resampling a `P`-mode image interpolates palette
   indices and invents colours that are not in the image, so this cannot wait for the encoder's own
   conversion at save time. **Drop `icc_profile` when the source mode was outside
   `{"RGB", "RGBX", "RGBA", "RGBa", "P", "PA"}`.** `Image._new` copies `info` through `convert()`, so
   a CMYK or greyscale profile would otherwise ride along describing a colour space the pixels are no
   longer in, and a browser honouring it renders wrong colours.
10. **`img.thumbnail((MAX_DIMENSION_PX, MAX_DIMENSION_PX), Image.Resampling.LANCZOS)`.** A square box
    makes this a longest-edge cap with no orientation branch. `thumbnail` returns early without
    resampling when the image already fits, which is where "never upscale" comes from.
    `ImageOps.contain` has no such guard and would enlarge a 400x300 source. Both default to
    `BICUBIC`, so pass `LANCZOS` explicitly. `thumbnail` mutates in place and returns `None`, so call
    it as a statement.
11. **Encode**, per the rule below.
12. **Never grow:** an encode that is not strictly smaller than `raw` is discarded and the decision
    comes back `KEPT_SOURCE`. Strict, so a tie keeps the source rather than churning the extension and
    MIME type for nothing. It runs on the winning candidate only.

**The encode rule.**

```python
if source_format in ("JPEG", "MPO"):
    encoded, lossless = _encode(img, icc, lossless=False), False
else:
    candidate = _encode(img, icc, lossless=True)
    if not camera_exif and len(candidate) <= SECOND_ENCODE_BYTES:
        encoded, lossless = candidate, True
    else:
        lossy = _encode(img, icc, lossless=False)
        if len(lossy) * LOSSY_WINS_DIVISOR <= len(candidate):
            encoded, lossless = lossy, False
        else:
            encoded, lossless = candidate, True
```

`_encode` passes `format="WEBP"`, `lossless=`, `quality=LOSSLESS_EFFORT if lossless else
LOSSY_QUALITY`, `method=ENCODE_METHOD` and `icc_profile=icc`, where `None` is safe because Pillow
collapses it to no profile. Nothing else. `exact` and `alpha_quality` keep their defaults, and
`save_all` is never set because animated inputs never reach the encoder.

**Metadata.** Pillow's WebP `_save` reads `exif`, `xmp` and `icc_profile` from `encoderinfo` only,
never from `img.info`, and `Image.save()` does not merge the two. Not passing EXIF is therefore what
drops it, along with the GPS coordinates phones attach to author photos, and the ICC profile is the
one thing that needs passing back deliberately. This is WebP-specific. The JPEG and PNG save paths do
read from `info`.

Comment the asymmetry, or someone will later "fix" it to libwebp's own `-mixed` behaviour, which
dual-encodes and just takes the smaller bitstream. That suits animation frames, where both candidates
are equally acceptable. Here they are not.

**Failure.** `BOMB_FAILURES`, caught without `bomb_warnings_as_errors` per Decisions, and
`DECODE_FAILURES` both return `UNDECODABLE` for the caller to log. Nothing raises out of
`optimise_image`. One bad file must neither abort a run over a whole content repository nor vanish
from it.

The guard spans the encode as well as the decode, so the mode conversion, the resize and both
`_encode` calls sit inside it. libwebp reports a write it cannot complete as an `OSError` and an
unexpected mode conversion raises `ValueError`; guarding only `Image.open` would leave those two as
ways to abort a run. WebP's 16383 px format limit surfaces as `ValueError` on the same path, and is
unreachable while `thumbnail` is called unconditionally. An encode failure reuses `UNDECODABLE`
rather than adding a fifth status — `decision.error` names the exception type, which is what
distinguishes the two.

### 3. The ingest call site, `save_file_to_db` (`content_save.py:459-497`)

Restructure so the bytes are read and the source handle closed before the encode, rather than held
open across it:

- Read `raw = file_path.read_bytes()`.
- Call `optimise_image(raw, file_path.suffix)` when `file_type == File.FileType.IMAGE`, and skip it
  entirely otherwise.
- When `decision.data` is set, the stored name is `file_path.with_suffix(".webp").name` and
  `file_obj.mime_type = "image/webp"`. Write with `django.core.files.base.ContentFile(decision.data)`.
- When it is `None`, today's behaviour exactly: the original name, the original
  `mimetypes.guess_type` result, the original bytes.
- **Assign `mime_type` before the write at `:494`.** That `FieldFile.save(..., save=True)` is the only
  DB write in the function, and it is what persists the metadata mutations at `:483-485`. Both the
  `defaults=` dict at `:471-479` and the update branch at `:482-485` need the post-encode value.
- **The superseded object is always dealt with, but not always at the same moment.** `course_media` is
  excluded from `_OVERWRITE_PURPOSES` (`freedom_ls/deployment/storage.py:43`), so a write at an
  existing key is renamed rather than replaced, and `file_upload_handler` keys on the extension. A
  re-run at the same extension therefore writes back to the same key and must call
  `file_obj.file.delete(save=False)` first, or the write is renamed and
  `content_engine/photo<pk>.webp` stops being stable across runs. An extension change writes to a
  different key, so nothing collides — and there the delete is deferred with
  `transaction.on_commit`, because `save_content_to_db` is atomic and can still raise after this
  file: deleting the `.jpg` inline would leave every rolled-back `File` row naming an object that no
  longer exists. Compare `file_obj.file.field.generate_filename(file_obj, stored_name)` against
  `file_obj.file.name` to tell the two cases apart.
- `File.file_path` and `File.original_filename` are never touched. `file_path` is the unique key
  (`files.py:53-58`) and the key `<c-picture src="...">` resolves against, which is what keeps existing
  content working untouched. `original_filename` stays the author's `photo.jpg`.

`save_file_to_db` returns the `ImageEncodeDecision`, or `None` for a non-image, so
`save_content_to_db` can count the statuses for the run summary. It keeps the statuses, never the
decisions: a decision carries the encoded bytes, so a list of them holds every encode of the run in
memory to produce a count.

### 4. Author-facing output

`content_save.py:497` is `logger.info`, and `LOGGING` is configured only in
`config/settings_prod.py:95`. `config/settings_dev.py` and `config/settings_base.py` have none, and
`pyproject.toml:75` and `manage.py:10` both default to `settings_dev`, so an author running the
command locally sees no per-file line at all today.

- **Move the per-file line at `:497` and the closing line at `:707` to `click.echo`.** `djclick` is
  already imported at `content_save.py:13` and this is a CLI command with a human at the keyboard.
  Move the per-file line for every file type, not only images, and move `✓ Successfully saved all
  content for site: {site_name}` with it. Leaving either behind would print a run summary underneath
  a success line the author cannot see, which is the bug this section exists to fix. Every other
  `logger` call in the command stays as it is.
- **Extend it for images** with the source format, the resulting dimensions, the lossy/lossless
  decision, before and after bytes, the percentage, and the `ImageEncodeStatus` value, whose four
  words are the fixed, greppable vocabulary:

  ```
  Updated IMAGE file: intro/hero.jpg
    JPEG 4032x3024 -> WebP lossy 1600x1200
    5.1 MB -> 118 KB (-97.7%), optimised.

  Updated IMAGE file: intro/menu.png
    PNG 1840x1120 -> WebP lossless 1600x974
    412 KB -> 268 KB (-34.9%), optimised.

  Updated IMAGE file: intro/logo.svg
    SVG, passthrough.

  Updated IMAGE file: intro/tiny.png
    PNG 200x120, re-encode not smaller, kept source.
  ```

  The decision and the resulting dimensions both have to appear: an author who thinks a screenshot
  got mangled reads `lossy` rather than guessing, and silent scaling is what
  `research_prior_art.md` records authors complaining about.
- **Keep `logger.warning` for an undecodable file**, naming the relative path and `decision.error`.
  It already reaches stderr in dev via `logging.lastResort`.
- **Add one run-summary line** via `click.echo` at the end of `save_content_to_db`, under the closing
  line. It carries the total images seen and a count per `ImageEncodeStatus`, omitting any status that
  did not occur, so a clean run reads as one short line. A per-file warning inside a run over a whole
  content repository gets scrolled past. Eleventy Image's maintainers reached the same conclusion
  about granularity.

## Testing

Unit tests against `optimise_image` on bytes, no database. Extend `freedom_ls/tests/images.py` with
shared valid-image builders: PNG, JPEG, palette GIF, `P`-mode with `tRNS`, CMYK JPEG, EXIF
orientation 6, ICC-tagged, animated GIF. The corrupt-PNG builders `break_png_chunk_crc` and
`shorten_png_ihdr` are already there and cover the `SyntaxError` and `ValueError` decode paths.
`freedom_ls/reports/tests/test_gather_indexes.py:90-106` has private PNG/JPEG/GIF helpers worth moving
there rather than duplicating.

What has to be proved:

- **Format and cap.** A large JPEG comes back WebP with both edges at or under 1600 and fewer bytes. A
  900x600 source keeps its exact dimensions, never upscaled.
- **The rule.** A JPEG gets one lossy encode. A small screenshot PNG comes back lossless without a
  second encode. A large photographic PNG, and a PNG carrying camera EXIF, reach the comparison.
  Assert the winner on each side of the 3x boundary rather than asserting a byte count.
- **Orientation.** An EXIF-orientation-6 portrait fixture comes out with its width and height the way
  a viewer shows them, not the way the raw buffer stored them — `source_size` included, so the two
  halves of the author's line cannot read as an aspect-ratio change.
- **Colour and metadata.** An ICC-tagged RGB source keeps `info["icc_profile"]`. A CMYK source does
  not. `Image.open(decision.data).getexif()` is empty, including for a GPS-tagged fixture.
- **Transparency.** A `P`-mode PNG with `tRNS` and an `RGBA` PNG both survive with
  `has_transparency_data` true, and the resized output has no palette-index colour bleed.
- **Pass-through.** SVG, animated GIF and an already-small WebP come back `PASSTHROUGH`, and each
  corrupt-PNG fixture comes back `UNDECODABLE`, all with `data is None`. Assert the status, not just
  that nothing was encoded, or the four cases stay indistinguishable and §4's output cannot be
  trusted. Each `UNDECODABLE` decision carries an `error` naming the exception type, and every other
  status carries `error is None`. An MPO-format `.jpg` is optimised, not mistaken for animation.
- **Nothing escapes.** Every prefix of an animated GIF returns a decision rather than raising: the
  frame count seeks through the file, and which exception a truncation reaches depends on where it
  stops, so the whole range is swept rather than one hand-picked cut. A patched `_encode` that raises
  `OSError` returns `UNDECODABLE` too, which is what holds the guard around the encode.
- **Never grow.** A tiny well-optimised PNG comes back `KEPT_SOURCE`.
- **Determinism.** `optimise_image(raw, ".jpg").data == optimise_image(raw, ".jpg").data`. Assert
  run-to-run stability, **not** a committed golden file or digest. Pillow re-cuts wheels with new
  bundled libwebp versions independently of this repo, and libwebp's output is not promised stable
  across its own versions, so a golden hash turns a routine `uv lock --upgrade-package pillow` into a
  red test with no defect behind it.

Integration tests alongside `freedom_ls/content_engine/tests/test_content_save_course.py:298-341`,
which is the only existing test that puts an image through `save_file_to_db`. A JPEG in a temporary
content tree lands with `mime_type == "image/webp"`, a storage name ending `.webp`, an unchanged
`file_path` and an unchanged `original_filename`. A second `save_content_to_db` run over the same tree
produces identical stored bytes. A corrupt image stores its source bytes and does not abort the run.
An upgrade run over a pre-existing `.jpg` leaves no object at the old key once the run commits, and
leaves it in place while the run has not — the two halves of the deferred delete, separated with
`django_capture_on_commit_callbacks(execute=True)` and `(execute=False)`.
Tests that build their own tmp tree do not need `fls_internal`. Any test asserting against
`demo_content/` does. Watch `--cov-fail-under=73`, because the pass-through branches are easy to leave
uncovered.

`check_logo_safety`'s existing tests must pass unchanged after the extraction into
`freedom_ls/base/images.py`.

## Open questions

- The 250 KB floor and the 3x ratio are separators chosen against seven real FLS screenshots and
  published corpus figures, not tuned optima. Once a real course content repository has been run
  through, confirm the observed lossy/lossless ratios are still bimodal around them. The check is that
  the two populations stay separated, not that the numbers are optimal. Do not nudge them per image.
- Whether any downstream project wants `MAX_DIMENSION_PX` or `LOSSY_QUALITY` as a
  `ContentEngineConfig` setting. Nothing has asked yet.

## Success criteria

- A 5 MB camera JPEG in a content tree is stored as WebP at 1600 px on its longest edge, in the 80-150
  KB band, with `mime_type == "image/webp"`.
- An annotated screenshot PNG is stored as lossless WebP, with no ringing around its text.
- `<c-picture src="photo.jpg">` in existing content renders without any content edit.
- A corrupt image logs a warning naming it, is stored unchanged, and the `content_save` run completes.
