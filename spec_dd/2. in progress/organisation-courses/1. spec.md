# Spec: organisation courses

Source: `idea.md`. Research: the `research_*.md` files beside it.

## 1. Purpose

Every course on a site is open to every organisation today. Some courses have to belong to
particular organisations: a client gets its own version of a course, independent of every other
version that shares its title. Course content declares which organisations a course belongs to and
whether anyone outside them may see it. Course cards say which organisation a course belongs to, so
a learner can tell same-titled versions apart.

## 2. Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| organisation course | coined | A `Course` with at least one row in `Course.organisations`. No existing term: until now a course had no organisation. |
| `CourseAudience` | coined | Who may see an organisation course: `organisation_learners` (users with an active `Learner` row in one of its organisations) or `public` (everyone). Independent of `CourseVisibility`: a `hidden` course stays hidden whatever its audience. "Members" is avoided because `OrganisationMember` means organisation staff. |
| in the audience | coined | A user may see a course: it is not an organisation course, or its `audience` is `public`, or the user has an active `Learner` row in one of its organisations, or the user is registered for it. The last clause is the exemption `hidden` and `coming_soon` give, so a change to a course's organisations never strands a mid-course learner. |
| open to an organisation | coined | A course is open to an organisation when it is not an `organisation_learners` organisation course, or the organisation is one of its organisations. |

## 3. Scope

In:

- `Course.organisations` and `Course.audience`, set from course frontmatter by organisation slug.
- The audience gate wherever learners find or open a course, and the open-to-an-organisation check
  wherever a registration is made.
- An organisation byline on learner-dashboard cards.
- Self-registration through the learner's own organisation.

Out:

- `Course.access_config`, and the behaviour of `freedom_ls/course_applications/`. The only edit
  there is the import of the renamed 404 gate (§5.2). Which organisation an approved application
  registers through is unchanged.
- The organisation byline on the all-courses list, the markdown embed card, completed cards and
  the course detail page.
- Reports, and per-organisation scoping of `RecommendedCourse` rules (the
  `corporate-job-course-recommendations` effort). Recommendations still pass through
  `filter_visible`, so the audience gate covers them.
- Course slug derivation.

## 4. Decisions

- **Content owns the link.** The frontmatter names organisation slugs, resolved per site at
  `content_save`, the way `dashboard_category` is. The Course admin shows both fields read-only.
  `Organisation.slug` is set once and never re-derived on rename, so a reference stays valid.
- **`public` changes the card and the self-registration organisation, nothing else.** A public
  organisation course is seen, applied for and registered onto from any organisation, like a course
  that is not an organisation course.
- **The M2M lives on `Course`,** adding the edge `content_engine --> organisations` (no cycle; see
  `research_codebase.md` §6).

## 5. Requirements

### 5.1 Model and loader (`freedom_ls/content_engine`)

- `models/courses.py`: add `CourseAudience(models.TextChoices)` with `ORGANISATION_LEARNERS =
  "organisation_learners"` and `PUBLIC = "public"`. On `Course`, add
  `organisations = models.ManyToManyField("freedom_ls_organisations.Organisation", blank=True,
  related_name="courses")` and `audience = models.CharField(choices=CourseAudience.choices,
  default=CourseAudience.ORGANISATION_LEARNERS, max_length=32)`. `audience` has no effect on a
  course with no organisations. Existing courses get no organisations, so they behave as before.
- `schema.py` `Course`: add `organisations: list[str]` (organisation slugs, default empty) and
  `audience: CourseAudience` (default `organisation_learners`).
- `management/commands/content_save.py` `save_course`: add `"organisations"` to the
  `save_with_uuid` `exclude_fields`. Resolve the slugs with
  `Organisation._base_manager.filter(site=site, slug__in=...)`; an unknown slug fails the load with
  an error naming the slug, the course file and the site's valid organisation slugs, like the
  unknown-`dashboard_category` error. After `save_with_uuid` returns, in the same transaction, call
  `course.organisations.set(resolved)`; an absent `organisations` key clears it.
- `admin.py` `CourseAdmin`: add `organisations` and `audience` to the Details fieldset and to
  `readonly_fields`. A `list_display` method column joins the organisation names, with
  `get_queryset` prefetching `organisations`; `list_filter` on `organisations`. Same-titled courses
  can then be told apart.

### 5.2 The audience gate (`freedom_ls/learner_management/queries.py`, `freedom_ls/course_access`)

- Add a queryset expression for "in the audience" beside `is_registered_for_course_expression`, and
  a single-course form of it. Anonymous users are in the audience only of courses that are not
  organisation courses or are `public`. Both forms share one definition, so the list rule and the
  single-course rule cannot drift.
- `backends.py` `VisibilityEnforcingBackend`:
  - `filter_visible` also excludes courses the user is not in the audience of. This covers the
    dashboard sections, the all-courses list and recommendations.
  - `_visibility_decision` gains an audience branch returning the no-access decision it returns for
    `hidden`, so `get_access` and `get_access_for_request` agree with the 404 gate.
  - `override_visibility_to_visible()` lifts the audience rule as it lifts `hidden`.
- `visibility.py`: replace `raise_404_if_hidden_unregistered` with `raise_404_if_unavailable`,
  which raises for a hidden course the user is not registered for and for a course the user is not
  in the audience of. Update every call site (course detail, course home, `initiate_course_access`,
  `_course_access_redirect`, `course_applications/views.py`, `course_interest/views.py`) and the
  module docstring.
- `learner_interface/templatetags/course_card_tags.py` `get_course_by_path`: return `None` for an
  `organisation_learners` organisation course.

### 5.3 Registration (`freedom_ls/learner_management`, `freedom_ls/registration_rules`, `freedom_ls/learner_interface`)

- One shared check in `learner_management/queries.py`: is a course open to an organisation (§2).
  Every path that creates or reactivates a registration calls it and refuses a course not open to
  the learner's or cohort's organisation:
  - new `clean()` methods on `LearnerCourseRegistration` and `CohortCourseRegistration` (the admin);
  - the educator register views;
  - `initiate_course_access`;
  - `registration_rules/evaluation.py` `apply_rule_changes`, which skips such learners rather than
    registering them, since a course's organisations can change after a rule is saved.
- New `RegistrationRule.clean()`: refuse a rule whose course is not open to its organisation.
- `_registerable_courses` / `registerable_courses_for` / `registerable_courses_for_learner` and
  `courses_visible_to`: leave out courses not open to the cohort's, learner's or viewed
  organisation. In `courses_visible_to` the filter also applies after the superuser short-circuit,
  so a superuser sees only the courses open to the viewed organisation. The educator pickers,
  Courses list and the permission check at `educator_interface/views.py:1568` follow.
- `learner_interface/views.py` `initiate_course_access`, for an organisation course of either
  audience: when the user holds an active `Learner` row in one of its organisations, register
  through it, the earliest-created one if several. Otherwise register through the default
  organisation, as today.

### 5.4 Dashboard card byline (`freedom_ls/learner_interface`)

- A new cotton component, `templates/cotton/organisation-byline.html`, takes an organisation and
  renders a muted line: the `logo` in a small fixed-height opaque `bg-surface` box with `alt=""`,
  then the name as text; name only when there is no logo. It renders nothing for the site's
  default organisation, the rule `partials/course_organisation_chip.html` follows. Unlike that
  chip, it is card-sized and carries no element id, so a list can repeat it.
- `partials/course_card.html`: render the byline under the title when `course.card_organisation`
  is set. Not in the status eyebrow, which stays the one place status shows.
- Where `card_organisation` comes from:
  - In progress section cards (`registered`, `in_progress`) for an organisation course:
    `get_current_courses` (`learner_interface/utils.py`) stamps the organisation of
    `CourseProgress.learner` from the record `course_progress_by_course_for` returns, whichever
    registration (individual or cohort) won. A course with no `CourseProgress` record yet gets no
    byline.
  - `not_registered` and `coming_soon` cards for a course with exactly one organisation: that
    organisation, stamped by the dashboard annotate helpers in `views.py`. Zero or several: none.
- No query per card: add `learner__organisation` to the `select_related` in
  `course_progress_by_course_for` (`freedom_ls/learner_progress/queries.py`), and prefetch
  `organisations` on all three card sources: the discovery querysets, `get_course_registrations`
  and the courses behind `get_recommended_courses`.

## 6. Testing

- Loader: slugs resolve; an unknown slug fails naming slug, file and valid slugs; removing the key
  clears the M2M; `audience` defaults to `organisation_learners`.
- Audience predicate, both forms, over: a course that is not an organisation course;
  `organisation_learners` with the user in, out, inactive (`Learner.is_active=False`), anonymous,
  and registered while out; `public` with a user who has no `Learner` row in its organisations,
  and anonymous.
- `filter_visible`, `get_access` and `raise_404_if_unavailable` agree for every case above.
- Embed card returns nothing for an `organisation_learners` organisation course.
- The open-to-an-organisation refusal on each write path in §5.3, including `apply_rule_changes`
  skipping a learner after the course's organisations change; `RegistrationRule.clean()`; the
  educator pickers and `courses_visible_to`, superuser included, leave the course out of another
  organisation.
- `initiate_course_access` registers through the linked organisation's `Learner` row for both
  audiences, and through the default organisation for a public course the user has no row for.
- Cards: byline on a single-organisation discovery card, none for zero or several; byline on an
  in-progress card shows the `CourseProgress.learner` organisation, for a cohort registration too;
  none for the default organisation; name-only fallback. A `django_assert_max_num_queries` test proves
  the dashboard query count does not grow with the number of cards in any section.
- A Playwright flow: two same-titled courses for two organisations; a learner in one sees only
  theirs, with its byline.
- Tests and comments that state courses are shared across organisations
  (`research_codebase.md` §1, item 2, lists them) are amended, never deleted.

  "courses are shared" ones.
- `content_save` of `demo_content/` loads the two same-titled organisation courses with their
  organisations.
- Pre-commit, including `app-map-fresh`, passes on the branch.
