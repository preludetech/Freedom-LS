# Spec: full-test-run-still-too-often

## Purpose

The SDD cycle still runs the whole suite when nothing the branch owns has changed (`idea.md`). Two
causes remain after the checkpoint tier landed:

1. `/sdd:finish_worktree` Step 1 asks for the `full` tier outright. It ignores the full-run record,
   so a branch whose `implement_plan` full run passed, and which has changed only `spec_dd/` files
   since, runs the suite a second time.
2. The selector cannot tell a path main brought in from a path the branch changed. After a rebase,
   another spec's migration, a `factories.py` or an unmapped file escalates the rebase run
   (`rebase_main.md` Step 9.2) and the checkpoint (`full_run_record.py resolve`) to `full`, even when
   the branch's code never meets it.

When this work is done, `implement_plan` Step 3 is the only outright full run. Everything else is
chosen from what changed, and main's changes count only where they meet the branch. `finish_worktree`
Step 1 still runs `full` when no full-run record exists, for example when another process committed
during the `implement_plan` run.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| upstream path | narrowed | `upstream_change_review.md` uses it for any path main brought in. Here: a path an `--upstream-range` changed that the branch's own diff does not contain. |
| branch path | coined | Any changed path that is not an upstream path. |
| branch apps | coined | The owning apps of the paths in the branch's own diff (requirement 2) and of the branch paths. |
| related apps | coined | The branch apps plus every app they import (`A --> B` in `docs/app_structure.md`): the runtime-import closure of each branch app, plus each branch app's test-only imports and their runtime-import closure. |
| dependent apps | coined | Every app that imports a branch app: `importers()` of each, where runtime imports chain and a test-only import is one hop. |
| branch test targets | coined | The tests the branch's own paths select without the app map: each branch app's tests directory, and the targets of each tooling entry a branch path matches. Two targets overlap when they are the same path or one lies inside the other. |
| dependency files | narrowed | `commands/README.md` uses it loosely for escalating files. Here: the paths that force `full` from either side: the generic `pyproject.toml`, `uv.lock`, `.python-version`, `package.json` and `package-lock.json`, plus the project's `dependency_files` list. |

## Scope

Out:

- `implement_plan` Step 3 keeps its outright `full` run (`answers.md`).
- The pre-test rebuild cost (`rebuild_after_rebase.sh`).
- pytest-testmon or any coverage-based selection.
- CI's full run on the pull request, which stays the backstop.

## Decisions

- **Provenance lives only in the selector.** `resolve` and `rebase_main.md` pass ranges and never
  classify paths. `ds` cannot read the sdd record, so the rule sits in `ds`'s selector.
- **A spec-only branch never runs tests after a rebase, even when main changed a dependency file.**
  The branch-side `none` checks, `rebase_main.md` Step 9.1 (`--range origin/main..HEAD`) and the
  first check in `resolve()`, run before any upstream range is read. Neither changes.
- **Rebase Step 9.2 passes the literal `origin/main` as the new base.** Step 9 runs straight after
  the rebase. If `origin/main` moves in between, main's newer changes count as branch paths, which
  runs more tests, never fewer.

## Requirements

### Selector: `claude_plugins/django-stack/scripts/select_tests.py`

1. **New flag `--upstream-range <old>..<new>`**, given at most once and validated by `range_type`.
   The selector splits it on the first `..`. Update the module docstring's usage lines.
2. **Classification.** The paths the upstream range changed join the changed paths. A path is an
   upstream path when the upstream range changed it and the branch's own diff does not contain it.
   The branch's own diff is `<new>..HEAD`, plus the working tree when `--working-tree` is given.
   Every other path is a branch path, including a path only `--range` or a positional argument
   reported. A `--range <record>..HEAD` that mixes both sides is split by this rule. The paths of
   the branch's own diff do not join the changed paths: they only define the branch apps and the
   tooling entries the branch meets (rule 4.7).
3. **Related apps.** Add `app_dependencies(app, edges)` beside `importers()`, walking the opposite
   direction: the runtime-import closure of `app` (`edges.runtime`, `src == app`, transitive), then
   `app`'s own test-only imports (`edges.test`, one hop) and their runtime-import closure. The related
   apps are the branch apps plus `app_dependencies()` of each. The branch apps are the owning apps
   of the branch's own diff and of the branch paths, so rebase Step 9.2, whose changed paths hold
   none of the branch's commits, still knows which apps the branch changed.
4. **Rules for an upstream path**, first match wins:
   1. `none` globs: `none`.
   2. Dependency files (generic `DEPENDENCY_GLOBS`: `pyproject.toml`, `uv.lock`, `.python-version`,
      `package.json` and `package-lock.json`, extended by a new
      `dependency_files` list in `[tool.test_tiers]`): `full`. `pyproject.toml` and `uv.lock` move out
      of `ESCALATION_GLOBS` into `DEPENDENCY_GLOBS`.
   3. Changed test file under a `tests` directory with an owning app: select it when the owning app
      is a related app or a dependent app, else `none`. A test file with no owning app falls through
      to the tooling rule (4.7).
   4. Escalation glob: when the path's owning app is a related app or a dependent app, or it has no
      owning app (a root `conftest.py`, a project escalation glob from `[tool.test_tiers]`), select
      the tests of every related app and of the owning app. A path with no owning app also selects
      its tooling entry's tests under rule 4.7. When the owning app is neither related nor
      dependent: `none`.
   5. Owning app is a related app or a dependent app: select that app's tests. When it is a branch
      app, also the tests of every app among its `importers()`; otherwise the tests of each branch
      app among them.
   6. Owning app neither related nor dependent: `none`.
   7. Tooling glob: select the entry's tests when one of its targets overlaps a branch test target,
      else `none`.
   8. Anything else (unmapped): `none`.
5. **Branch paths** keep today's rules, with dependency files checked just before the escalation
   globs. An unmapped tracked branch path, a missing app map or a selector failure still means `full`.
   With no app map the related apps cannot be computed, so every path the upstream range changed is
   decided by these branch rules.
6. **`why:` lines** mark an upstream path and every dropped upstream path gets one, for example
   `why: app_a/migrations/0013_x.py -> none (from main; app_a meets no branch app)` and
   `why: uv.lock -> full (from main; dependency file)`.
7. `--tests-changed-in` files are branch test files whatever their side, and still never raise the
   tier.
8. Without `--upstream-range` the tier and selection are unchanged. Only the reason text of
   dependency-file lines changes.

### Project config: `pyproject.toml` `[tool.test_tiers]`

9. FLS adds nothing to `dependency_files`. `config/**`, `freedom_ls/site_aware_models/**` and
   `freedom_ls/content_base/**` stay escalation globs, scoped by rule 4.4.

### Checkpoint: `claude_plugins/sdd/scripts/full_run_record.py`

10. `resolve()`, after the branch-side `none` check and the record checks: compute
    `old = git merge-base <sha> origin/main` and `new = git merge-base HEAD origin/main`. When both
    succeed and differ, the diff is `--upstream-range <old>..<new> --range <sha>..HEAD --working-tree`.
    When the two are equal (main has not moved since the record), `origin/main` does not resolve or
    either `merge-base` fails, the diff is today's `--range <sha>..HEAD --working-tree`. The returned `diff` carries the arguments the tier was
    chosen on.
11. A `full` result's `why` is the first `-> full` line the selector printed, without its `why: `
    prefix. `selected_tier()` returns that line beside the tier. With no such line (the selector
    failed or printed no tier), the `why` stays `the selector escalates over <sha>..HEAD`.

### Rebase: `claude_plugins/django-stack/commands/rebase_main.md` Step 9

12. Step 9.2 becomes
    `--upstream-range $OLD_BASE..origin/main --range $REPLAYED_TIP..HEAD --tests-changed-in origin/main..HEAD`.

### Finish: `claude_plugins/sdd/commands/finish_worktree.md`

13. Step 1 runs `run_test_tier.md` with `<tier>: checkpoint`, and its heading stops saying "Full
    tier". Step 1 and the Step 7 loop share one description of a checkpoint run: resolve, then the
    pre-test rebuild only when the tier is `targeted` or `full`, then the run.
14. Every other place that calls Step 1 a full run says checkpoint run: the `full run` / `checkpoint
    run` contrast in the failure text, the failure-handling lead-in ("When Step 1's full run…"), the
    Step 7 note ("Step 1's full run wrote the full-run record", which becomes "the last passing full
    run, usually `implement_plan` Step 3, wrote it") and the Step 8 report text.

### Tier definition: `claude_plugins/django-stack/resources/test_tiers.md`

15. The `targeted` bullet documents `--upstream-range` and the dependency-file list beside the `none`
    and escalation lists.

## Testing

Selector and checkpoint fixtures use neutral app names (`app_a`, `app_b`) in a temporary repo.

- `tests/test_select_tests.py`: one test per rule in requirement 4, the generic and the
  `dependency_files` lists on both sides, a path both sides changed (a branch path), a
  `--tests-changed-in` file under an unrelated app (still selected), an
  `app_dependencies()` walk through a test-only import, and the requirement 6 `why:` wording. The
  existing tests pass unchanged apart from dependency-file reason text.
- `tests/test_full_run_record.py`:
  - a record taken before a rebase onto a main that added a migration in an unrelated app resolves to
    `none` when the branch is unchanged since the record, and `targeted` without that app when it
    changed;
  - `test_record_taken_before_a_rebase_onto_a_moved_main_sees_what_main_changed` (`uv.lock`) still
    resolves to `full`, and its `why` names `uv.lock`;
  - no `origin/main` falls back to the plain record range.
- `tests/test_checkpoint_prompts.py`: rewrite `test_finish_worktree_asks_for_the_full_tier_once`,
  `test_finish_worktree_step_one_is_the_full_tier` and the module docstring. `finish_worktree.md`
  passes `checkpoint` and never `full`; `implement_plan.md` is the only sdd command passing `full`.
- `tests/test_rebase_prompts.py`: Step 9.2 carries `--upstream-range $OLD_BASE..origin/main`.
- `tests/test_check_diagrams.py` and `tests/test_test_tiers.py` pass over the edited prompts and
  diagrams.

## Success criteria

- A branch that changed only `spec_dd/` after `implement_plan`'s full run passed reaches
  `/sdd:finish_worktree` Step 1 with `tier: none`.
- After a rebase onto a main that added a migration in an app no branch app imports, the rebase run
  and the checkpoint print a `from main` `why:` line for the migration and do not select that app's
  tests.
- After a rebase onto a main that changed `uv.lock`, a branch with a code change runs `full` and the
  reason names `uv.lock`.
- `grep -rn "<tier>\`: \`full\`" claude_plugins/sdd/commands/` matches only `implement_plan.md`.
