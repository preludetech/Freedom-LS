# Spec: full-test-run-still-too-often

## Purpose

The SDD cycle still runs the whole suite when nothing the branch owns has changed (`idea.md`). Two
causes remain after the checkpoint tier landed:

1. `/sdd:finish_worktree` Step 1 asks for the `full` tier outright. It ignores the full-run record,
   so a branch whose `implement_plan` full run passed, and which has changed only `spec_dd/` files
   since, runs the suite a second time.
2. The selector cannot tell a path main brought in from a path the branch changed. After a rebase,
   another spec's migration, `factories.py` or an unmapped file under `demo_content/` escalates the
   rebase run (`rebase_main.md` Step 9.2) and the checkpoint (`full_run_record.py resolve`) to `full`,
   even when the branch's code never meets it. Main passed CI. Only where main's changes meet the
   branch's code is anything left to test.

When this work is done, a branch runs the full suite outright once, in `implement_plan` Step 3. Every
other run is chosen from what changed, and main's changes count only where they meet the branch.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| upstream path | coined | A path an `--upstream-range` changed and the branch's own commits did not. "Upstream" is the sense `upstream_change_review.md` already uses for what main brought in. |
| branch apps | coined | The owning apps of the paths the branch's own commits (and, with `--working-tree`, its uncommitted files) changed. |
| related apps | coined | The branch apps plus every app a branch app depends on: runtime edges followed transitively, test-only edges one hop, both from `docs/app_structure.md`. |
| dependency file | coined | A path whose change from either side always means `full`: the generic `pyproject.toml` and `uv.lock`, plus the project's `dependency` list. |

## Scope

In:

- `select_tests.py` learns the provenance of a path and scopes upstream paths to the related apps.
- `full_run_record.py resolve` passes the upstream range, so a checkpoint after a rebase stops
  re-testing main.
- `rebase_main.md` Step 9.2 passes main's diff as the upstream range.
- `finish_worktree.md` Step 1 becomes a `checkpoint` run.
- The tier definition, the sdd README, the three affected diagrams and their tests.

Out:

- `implement_plan` Step 3 keeps its outright `full` run (`answers.md`).
- The pre-test rebuild cost (`rebuild_after_rebase.sh`).
- pytest-testmon or any coverage-based selection.
- CI's full run on the pull request, which stays the backstop.

## Decisions

- **Unknown still means full on the branch side.** An unmapped tracked path the branch changed, a
  missing app map or a selector failure still escalates. Only upstream paths are scoped.
- **An upstream path that meets no related app selects nothing.** That covers unmapped upstream
  paths such as `demo_content/**`: CI proved main, and the branch does not touch them.
- **Dependency files escalate from either side**, because a changed lockfile changes the code every
  test imports (`answers.md`).
- **A spec-only branch never runs tests after a rebase, even when main changed a dependency file.**
  The branch-side `none` check in `rebase_main.md` Step 9.1 and in `resolve` runs first, so it is
  unchanged.
- **Provenance is computed in the selector, once.** `resolve` and `rebase_main.md` pass ranges and
  never classify paths themselves. `ds` cannot read the sdd record, so the rule has to live in `ds`'s
  selector.
- **A missing or unresolvable record still resolves to `full`.** Falling back to a narrower run was
  rejected because the record is the only proof the branch's own code ran in full.

## Requirements

### Selector: `claude_plugins/django-stack/scripts/select_tests.py`

1. **New flag `--upstream-range <old>..<new>`**, repeatable, validated by `RANGE_PATTERN` like
   `--range`. `<old>` is main's previous position (the old base) and `<new>` is main's current
   position.
2. **Upstream paths.** Every path the upstream ranges changed joins the changed paths. It counts as
   an upstream path when the branch's own diff, `<new>..HEAD` plus the working tree when
   `--working-tree` is given, does not contain it. With several upstream ranges, `<new>` is the last
   range's right-hand side. A path the branch also changed is a branch path, whichever range
   reported it, so a `--range <record>..HEAD` that mixes both sides is split correctly.
3. **Branch apps and related apps** are computed from the branch's own diff in requirement 2. Add a
   `dependencies(app, edges)` helper beside `importers()` that walks `edges.runtime` from `src == app`
   (transitively) and `edges.test` (one hop). The related apps are the branch apps plus their
   dependencies.
4. **Rules for an upstream path**, in order (first match wins):
   1. `none` globs: `none`, as today.
   2. Dependency file (generic `DEPENDENCY_GLOBS = ("pyproject.toml", "uv.lock")`, plus a new
      `dependency` list in `[tool.test_tiers]`): `full`. Move `pyproject.toml` and `uv.lock` out of
      `ESCALATION_GLOBS` into `DEPENDENCY_GLOBS`. A branch-side dependency file still escalates, as
      before.
   3. Changed test file under a `tests` directory: select it only when its owning app is a related
      app, otherwise `none`.
   4. Escalation glob: if its owning app is a related app, or it has no owning app (a root
      `conftest.py`, a project glob such as `config/**`), select the tests of every related app.
      If its owning app is outside the related apps: `none`.
   5. Owning app is a related app: select that app's tests and the tests of each branch app that
      depends on it (the `importers()` result filtered to branch apps).
   6. Owning app outside the related apps: `none`.
   7. Tooling glob: select the entry's tests only when a branch path matched the same tooling entry,
      otherwise `none`.
   8. Anything else (unmapped): `none`.
5. **Branch paths** keep today's rules exactly, with dependency files checked in the escalation step.
6. **`why:` lines** for upstream paths say so and name the decision, for example
   `why: freedom_ls/form_engine/migrations/0013_x.py -> none (from main; form_engine meets no branch app)`
   and `why: uv.lock -> full (from main; dependency file)`. A dropped upstream path always gets a
   line.
7. Without `--upstream-range` the output is identical to today's, apart from the reason text of
   dependency-file lines.

### Project config: `pyproject.toml` `[tool.test_tiers]`

8. Document the new `dependency` key. FLS adds no entries: `config/**`, `site_aware_models/**` and
   `content_base/**` stay escalation globs, scoped by rule 4.4.

### Checkpoint: `claude_plugins/sdd/scripts/full_run_record.py`

9. `resolve()`: after the branch-side `none` check and the record checks, compute
   `old = git merge-base <sha> origin/main` and `new = git merge-base HEAD origin/main`. When they
   differ, pass `--upstream-range <old>..<new>` with `--range <sha>..HEAD --working-tree`. The
   returned `diff` carries the same arguments, so `run_test_tier.md` runs the targeted tier the
   decision was made on. A failed `merge-base` resolves to `full` with the reason.
10. The `why` for a `full` result names the escalating path's reason line from the selector rather than
    only the range.

### Rebase: `claude_plugins/django-stack/commands/rebase_main.md` Step 9

11. Step 9.2 becomes
    `--upstream-range $OLD_BASE..origin/main --range $REPLAYED_TIP..HEAD --tests-changed-in origin/main..HEAD`.
    Step 9.1 is unchanged.

### Finish: `claude_plugins/sdd/commands/finish_worktree.md`

12. Step 1 runs `run_test_tier.md` with `<tier>: checkpoint`, not `full`. The pre-test rebuild runs
    only when the checkpoint resolves to `targeted` or `full`, as in Step 7's loop. The kept report
    line names the tier and its reason, so a skip never reads as a pass.
13. The text at the Step 7 checkpoint ("Step 1's full run wrote the full-run record") changes to say
    the record comes from the last passing full run, usually `implement_plan` Step 3.

### Tier definition: `claude_plugins/django-stack/resources/test_tiers.md`

14. The `targeted` bullet documents `--upstream-range` and the dependency list beside the generic
    `none` and escalation lists. No pytest flags move out of this file.

## Testing

- `tests/test_select_tests.py`: one test per rule in requirement 4, including:
  - an upstream migration in an unrelated app selecting nothing;
  - an upstream migration in a dependency of a branch app selecting every related app's tests;
  - an upstream root `conftest.py` selecting every related app's tests;
  - an upstream unmapped path selecting nothing;
  - an upstream `uv.lock` resolving to `full`;
  - a path both sides changed treated as a branch path;
  - output unchanged with no `--upstream-range`;
  - the `why:` wording for a dropped upstream path.
- `tests/test_full_run_record.py`:
  - a record taken before a rebase onto a main that added a migration in an unrelated app resolves to
    `none` (branch unchanged since the record) or `targeted` (branch changed since);
  - `test_record_taken_before_a_rebase_onto_a_moved_main_sees_what_main_changed` (`uv.lock`) still
    resolves to `full`;
  - a failed `merge-base` resolves to `full`.
- `tests/test_rebase_prompts.py`, `tests/test_check_diagrams.py` and `tests/test_test_tiers.py`
  (the pytest-invocation ban) pass over the edited prompts and diagrams.

## Documentation and downstream

- `claude_plugins/sdd/commands/README.md` "When the full suite runs": one outright full run
  (`implement_plan` Step 3). `finish_worktree` Step 1 is a checkpoint. The checkpoint's third rule
  says upstream escalation globs are scoped to the related apps and dependency files still force
  `full`.
- Diagrams: `finish_worktree.drawio.svg` (Step 1 box becomes a checkpoint, no longer red),
  `overview.drawio.svg` (one red full-run box) and `rebase.drawio.svg` (Step 9.2 wording).
- `ds` and `sdd` stay generic: the dependency list and every FLS path live in `[tool.test_tiers]`.
- Upgrade notes for downstream projects: the `dependency` key, and the fact that `pyproject.toml` and
  `uv.lock` moved from the escalation list to the dependency list.

## Success criteria

- A branch that changed only `spec_dd/` after `implement_plan`'s full run passed lands through
  `/sdd:finish_worktree` with `tier: none` at Step 1.
- After a rebase onto a main that added a migration in an app no branch app depends on, the rebase
  run and the checkpoint print `tier: none` or a targeted run that excludes that app's tests, with a
  `from main` `why:` line for the migration.
- After a rebase onto a main that changed `uv.lock`, a branch with a code change runs `full`; a
  spec-only branch runs nothing.
- `select_tests.sh` without `--upstream-range` prints the same tier and selection as before for every
  existing test case.
- No sdd command other than `implement_plan.md` passes `<tier>: full` to `run_test_tier.md`.
