# Research: Group/Cohort Enrolment — Materialise vs Derive

## FLS current shape (for reference)

- `UserCourseRegistration(collection, user, is_active)` — unique per (site, collection, user). Fires `course.registered` webhook on creation.
- `CohortCourseRegistration(collection, cohort, is_active)` — unique per (site, collection, cohort). No per-user row; access derived via `Cohort → CohortMembership → user`.
- `is_registered_for_course()` (`student_management/utils.py`) does `UserCourseRegistration.objects.filter(user=, collection=, is_active=True).exists()` OR falls back to `CohortCourseRegistration.objects.filter(cohort__cohortmembership__user=, collection=, is_active=True).exists()`. No signal keeps these in sync with anything — it's a live derived query, computed fresh every check.
- Deadlines are already split three ways: `CohortDeadline` (FK to `CohortCourseRegistration`), `StudentDeadline` (FK to `UserCourseRegistration`), `UserCohortDeadlineOverride` (FK to `CohortCourseRegistration` + `user`, validated against `CohortMembership` in `clean()`). This is the same materialise-vs-derive fork already solved once, twice (deadlines chose "derive + per-user override row", not "materialise a registration per member").

## Industry precedent

### Moodle: cohort sync — materialises, decouples grades from the enrolment row

Moodle's `enrol_cohort` plugin creates one row per (enrolment-instance, user) in `user_enrolments`, linked to an `enrol` row representing the *method* (cohort sync, manual, self, database, etc.) attached to the course. Sync is triggered both by event observers (`\core\event\cohort_member_added` / `cohort_member_removed`) and a periodic scheduled task (`enrol_cohort_sync`, `sync.php`, historically hourly cron) as a backstop — i.e. Moodle does not trust events alone and reconciles periodically. [Cohort sync — MoodleDocs](https://docs.moodle.org/502/en/Cohort_sync); [Moodle PHP Documentation: enrol_cohort](https://phpdoc.moodledev.io/4.5/d1/df1/group__enrol__cohort.html)

Critically, **grades and completion in Moodle are NOT keyed on the enrolment row** — `grade_grades` and `course_completion` key on `(userid, courseid)`, independent of which `enrol` instance produced access. This is the load-bearing design decision: Moodle solves "what if a user is enrolled two ways" and "what happens to progress on removal" by **not** coupling progress to the enrolment method at all. Enrolment method only gates access and role; a user can have multiple `user_enrolments` rows (e.g. one from `enrol_manual`, one from `enrol_cohort`) for the same course simultaneously, and removing one doesn't touch the grade record, which is keyed on the user/course pair. [Enrolment API — Moodle Developer Resources](https://moodledev.io/docs/4.4/apis/subsystems/enrol); forum confirmation of multiple simultaneous enrolment methods per user per course: [Moodle: User shows enrolled 2 ways](https://moodle.org/mod/forum/discuss.php?d=401492); [Moodle: Multiple Self-Enrollment Methods - One Course](https://moodle.org/mod/forum/discuss.php?d=328298)

What happens on removal from cohort: the "External unenrol action" setting on the cohort-sync instance decides the fate of *that enrolment row* — options include suspending it, unenrolling and removing the associated role, or (least destructive) keeping enrolment but removing the role. Only the most destructive option ("unenrol user from course") actually deletes grade data, and only if no other active enrolment method still grants the user access to that course — because grades live independently and are only *purged* by an explicit unenrol-and-delete action, not by the mere absence of a cohort-sync row. [Cohort sync — MoodleDocs](https://docs.moodle.org/502/en/Cohort_sync)

### Canvas: sections are per-user `Enrollment` rows, and this causes real problems

Canvas's `Enrollment` object carries `course_id`, `course_section_id`, `user_id`, `type`, and `enrollment_state` all on the same row — a section assignment is not a separate join table, it's a field on the per-user enrolment record. A student in two sections of the same course (e.g. after a cross-list) gets **two separate `Enrollment` rows**, each independently active/inactive/concluded. [Enrollments - Canvas LMS REST API Documentation](https://www.canvas.instructure.com/doc/api/enrollments.html)

This is Canvas's version of "registered both directly and via cohort" and it is a documented pain point: Instructure explicitly warns that Canvas "is not designed to host conflicting enrollment statuses in the same course shell" — when one enrolment row is `active` and the sibling is `inactive`, students hit unpredictable access and gradebook problems, and the only supported fix is to manually conclude/delete the redundant row. [Canvas (Known Issues) - Students Enrolled in Multiple Sections of Course](https://kb.wisconsin.edu/dle/118712); [What happens if multiple courses share sections](https://community.canvaslms.com/thread/8009)

Read as precedent: coupling "which row is authoritative for this user's course state" to "which enrolment row happens to exist" produces exactly the disambiguation bug FLS is worried about in trade-off #3 — and Canvas's own support docs treat it as an unresolved edge case requiring manual admin cleanup, not an automated reconciliation.

### Open edX: no derived group access at all — "cohorts" are a discussion partition on top of always-materialised enrolment

Open edX's `CourseEnrollment` is per-user and created directly on enrol (including via "batch enrollment," which is UI sugar over a loop that creates one `CourseEnrollment` per learner, not a group-level row) — there is no concept of a group-level enrolment row that derives individual access. Open edX "cohorts" are a *different* concept from FLS's — they partition already-enrolled learners into discussion groups and are irrelevant to access control; "every learner must be assigned to a cohort" only after they already have a `CourseEnrollment`. [Using Cohorts in Your Courses — Open edX docs](https://edx.readthedocs.io/projects/open-edx-building-and-running-a-course/en/named-release-cypress/cohorts/cohorts_overview.html); [How to Do Batch Enrollment in Open edX](https://www.codetrade.io/blog/batch-enrollment-from-studio-side/)

Open edX is therefore the cleanest precedent for "always materialise, never derive" — it sidesteps the whole materialise-vs-derive question by never having group-level access rows in the first place. It buys simplicity (progress always keys on a single row type) at the cost of losing "manage access for a whole cohort in one place" as a first-class object — bulk operations are batch *mutations* over individual rows, not a standing group-level registration you can toggle `is_active` on.

### Systems that keep access purely derived

FLS's own current cohort access check (`cohort__cohortmembership__user=user` EXISTS) is itself an example of "purely derived, no materialised per-user row" — same category as, e.g., LDAP/AD-group-gated access in many enterprise systems, or Django's own `Group` → `Permission` model (permissions are never materialised per-user; every check re-derives through the M2M). The well-known cost of this pattern, visible in both FLS's current code and general practice, is that **anything wanting to attach state to "this user's access to this thing"** (progress, grades, deadlines, audit history) has nowhere natural to hang that state, because there is no durable row representing "this user's registration" — only a query that is true or false at read time. FLS has already hit this twice: `CohortDeadline`/`UserCohortDeadlineOverride` had to be invented specifically because deadlines couldn't hang off a per-user row for cohort members, and now progress hits the identical wall.

## Engineering trade-offs for FLS

### 1. Query cost/complexity of a polymorphic or dual-nullable-FK progress model

If progress FK's to "either a `UserCourseRegistration` or a `(CohortCourseRegistration, user)` pair," every query that needs "this user's progress in this course" (educator progress matrix, PDF cohort reports, `is_registered_for_course`-equivalent for progress) must branch on which FK is populated, or `UNION` two query shapes. Concretely:
- The educator progress matrix (cohort of N students × course) already needs `select_related`/`prefetch_related` per FLS conventions; a nullable dual-FK design means two separate prefetch paths merged in Python, or a `UNION`/`Coalesce` at the DB level — both add real complexity to code that CLAUDE.md says should avoid repetition, and both are easy to get subtly wrong (e.g. an educator report double-counting a learner who has both FKs populate through a bug).
- A `CheckConstraint` is needed to enforce "exactly one of user_registration_id / (cohort_registration_id, user_id) is set" — enforceable in Postgres but one more piece of DB-level bookkeeping to maintain alongside the existing `site_id`-scoped `UniqueConstraint`s already in this file.
- PDF cohort reports (per the idea's context) want "all members of this cohort, their progress" — this is actually easier if progress always has a plain `user` FK (regardless of how the registration was derived), because the report is just "cohort members JOIN progress WHERE user IN (...)" — no branch needed. This argues against a design that makes progress's FK shape polymorphic per registration-type, and for either materialising (real per-user row, one FK shape) or deriving-with-a-flat-user-key (design (d) below).

### 2. Learner removed from cohort mid-course / cohort registration deactivated

- **Derive (current FLS shape, design (d))**: the moment `CohortMembership` is deleted or `CohortCourseRegistration.is_active` flips false, `is_registered_for_course` returns false — but progress rows keyed on `(user, course)` are untouched (same as Moodle's grade table). This is arguably the *right* default: a learner who did real work shouldn't lose their history because a membership row was deleted. But it also means progress can now exist for a user with no current access — the UI must handle "has progress, not currently registered" as a distinct state (FLS may already need this for direct registrations too, since `UserCourseRegistration.is_active` can already go false).
- **Materialise (design (a)/(b))**: if removal from cohort also deletes/deactivates the per-user registration row, and progress FK's `on_delete=CASCADE` to that row, progress is destroyed or orphaned as a side effect of a membership change — this is the Moodle "External unenrol action" problem, and FLS would need to invent the equivalent setting (or hardcode a choice) plus a signal/task to actually perform the cascade, none of which exists today.
- Either way, "orphaning" is a policy decision, not something either design alone can dodge — but the derive model has this decision already made in FLS's favour for direct registrations (`is_active=False` never deletes progress), so extending it to cohort-derived progress keeps a single dodel of "access can lapse, progress persists," rather than requiring a new deletion-cascade policy for cohort members only.

### 3. Registered both directly AND via cohort simultaneously — who owns progress?

FLS's `is_registered_for_course` already handles this today for *access* (either being true wins — it's an OR), but progress has no such easy answer if it must physically hang off one specific registration row:
- Moodle's answer: **don't ask the question** — grades key on `(user, course)` only, and the multiple `user_enrolments` rows coexist as independent access grants pointing at the same shared grade record. There is no "which one owns it."
- Canvas's answer: each `Enrollment` row (section, method) is a genuinely separate context, and this is a documented source of bugs when a student ends up in two simultaneously-active enrolments for what's conceptually "the same course" — Instructure's own guidance is that this is unsupported and needs manual admin resolution. This is the cautionary precedent: any FLS design where progress physically belongs to *one* registration row will hit the identical question the moment dual-registration exists, and Canvas shows the failure mode (silent data split, admin-only fix) rather than a clean answer.
- **Implication for FLS**: designs (a)/(b)/(c) below all need an explicit disambiguation rule for the dual-registration case (e.g. "direct registration always wins, cohort registration is inert while a direct one exists" — which would need enforcing at registration-creation time, not just query time, otherwise you get two live progress rows for the same (user, course) that can drift apart). Design (d) inherits Moodle's answer for free: progress on `(user, course)` is single-valued no matter how many registration rows currently grant access.

### 4. Consistency with existing deadline models

- `CohortDeadline`/`StudentDeadline`/`UserCohortDeadlineOverride` already encode the split FLS is deciding on for progress, and they chose **derive + per-user override**, not **materialise a registration per member**. `UserCohortDeadlineOverride` proves the pattern works without materialising a full registration row: it's just `(cohort_course_registration, user)` + generic FK to the content item, validated in `clean()` against live `CohortMembership`.
- If FLS materialises per-user registrations for cohort members (design (a)), the three-deadline-model split becomes redundant complexity: `CohortDeadline` and `UserCohortDeadlineOverride` could collapse into `StudentDeadline` alone, since every cohort member now has a `UserCourseRegistration`-shaped row to hang a deadline off. That's a genuine simplification, but it's a breaking migration of an already-shipped, already-tested deadline system, not an additive change.
- If FLS keeps cohort access derived (design (d), matching deadlines' existing choice), progress could follow the exact same `UserCohortDeadlineOverride`-style pattern: a `ProgressOverride`-shaped concept is unnecessary because progress is naturally per-user already (`content_type`+`object_id` completion state per learner) — there's no override to invent, because progress was never cohort-level to begin with. This is the "no new model needed" path and is consistent with what's already shipped.

### 5. Drift risk for a materialised design

If FLS materialises (design a/b), keeping the per-user registration row in sync with `CohortMembership` needs an explicit mechanism — none of the three exists in FLS today:
- **Signals (`post_save`/`post_delete` on `CohortMembership`, or `m2m_changed` if membership becomes an M2M rather than the current explicit `CohortMembership` model)**: cheapest to build, but Django signals silently no-op on bulk operations (`bulk_create`, `bulk_delete`, `QuerySet.delete()`) — a `CohortMembership.objects.filter(...).delete()` bypasses `post_delete` per row unless `.delete()` is called per-instance, a well-known Django footgun. FLS's own convention of preferring the ORM directly (no raw SQL) makes this *more* likely to bite, not less, since a bulk-membership-import feature would naturally reach for `bulk_create`/queryset `.delete()`.
- **Management command / periodic reconcile task**: matches Moodle's actual production answer (event observer *plus* an hourly cron backstop) — Moodle doesn't trust events alone. FLS has no existing periodic task infrastructure referenced in the models read for this research; adding one is new infrastructure, not a reuse of something already in place.
- **Known failure mode either way**: a materialised row that isn't reconciled promptly means a removed cohort member keeps course access (and can keep progressing) until the next sync — a security-relevant staleness window, worse than the derived model's staleness window (which is zero, since access is computed live on every check).

### 6. Data volume: N members × M courses

A cohort of, say, 500 learners registered for 20 courses is 10,000 materialised registration rows just for that one cohort, on top of whatever progress-per-content-item rows already exist per learner per course. This is not large by Postgres standards (tens of thousands to low millions of rows is routine), and is not itself a reason to reject materialising — Moodle and Canvas both materialise at genuinely large scale (Moodle installations with tens of thousands of users; Open edX courses with hundreds of thousands of enrollments) without this being the limiting factor. The real costs identified above (drift risk, disambiguation, deadline-model churn) dominate; raw row count is not a credible objection on its own.

## Candidate designs

### (a) Materialise a per-user registration linked back to the cohort registration
`CohortRegistrationMember(cohort_course_registration FK, user FK, is_active)`, auto-created for every `CohortMembership` at the time a `CohortCourseRegistration` is created (and for every new member added afterward), progress FK's to this row.
- **Pros**: single FK shape for progress (matches design goal "progress hangs off a registration"); lets `CohortDeadline`/`UserCohortDeadlineOverride` collapse into one deadline model long-term; matches Moodle's `user_enrolments` shape closely.
- **Cons**: needs a sync mechanism (see #5) that doesn't exist in FLS today; needs an explicit disambiguation rule for dual-registration (#3); needs a policy + migration for what happens to progress on membership removal (#2); is a genuinely new moving part (signals or a periodic job) in a codebase whose CLAUDE.md explicitly says "don't add logging unless asked" / "don't build functionality that is not explicitly requested," i.e. the project leans minimal — this is the highest-effort option.
- **Django cost**: new model + migration, `post_save` signal on `CohortMembership` creation and a matching removal handler (with the bulk-operation caveat above), backfill migration/data migration for existing cohorts, a decision + implementation for removal semantics (cascade delete vs `is_active=False`), and (if collapsing deadlines) a breaking migration of three existing, shipped models.

### (b) Progress FK to a nullable user-registration + nullable cohort-registration (dual nullable FK)
Progress row carries `user_registration = FK(UserCourseRegistration, null=True)` and `cohort_registration = FK(CohortCourseRegistration, null=True)` (+ always a plain `user` FK for cohort case), with a `CheckConstraint` requiring exactly one populated.
- **Pros**: no new sync mechanism needed — reuses the two registration models exactly as they exist today, no membership-drift problem because there's no materialised member row to drift.
- **Cons**: this is the polymorphic-query-cost problem from #1 in its purest form — every progress query (educator matrix, PDF reports, "get my progress") must branch on which FK is set, `Coalesce`/`UNION` to get a uniform "registration" concept, and enforce the disambiguation rule from #3 at write time (what stops two progress rows existing for the same user/course, one via each FK, if both registrations exist?) with an additional partial-unique constraint on `(user, course)` computed across two FK paths — Postgres can do this with an expression index but it's non-trivial, and Django doesn't model "uniqueness across either of two FKs" natively.
- **Django cost**: two nullable FKs + `CheckConstraint` + a computed/partial `UniqueConstraint` are straightforward to declare, but every call site that currently or will read progress needs to know about the branch — this cost is paid repeatedly across the educator progress matrix, PDF reports, and student-facing progress views, not once.

### (c) Single polymorphic "enrolment" table (unify `UserCourseRegistration` and `CohortCourseRegistration`, or add a generic `Enrolment` progress hangs off, resolved via `ContentType`+`object_id` to either registration type)
- **Pros**: one FK shape for progress, and it doesn't require materialising per-user rows for cohorts — direct registration and cohort registration both become "an enrolment," and cohort access stays derived, but progress hangs off whichever registration is contextually relevant via generic FK.
- **Cons**: this is the heaviest migration of the four — it touches `UserCourseRegistration` and `CohortCourseRegistration`, both of which already have `Deadline`/`Override` models FK'd to them by PK (not generically), a webhook (`course.registered`) fired from `UserCourseRegistration.save()`, and presumably other call sites outside the two files read for this research (out of scope here, but real). Using a Django `GenericForeignKey` for something as central and query-heavy as "the thing progress is measured against" also works against the project convention of `select_related()`/`prefetch_related()` for all related-object queries — generic FKs cannot be `select_related()`, only `prefetch_related()` with per-content-type lookups, which is measurably worse for the progress-matrix and PDF-report query patterns called out in this idea.
- **Django cost**: highest of the four — new abstract/shared concept, migration of two existing FK'd model families, and a GenericForeignKey on the hot path, which actively fights the ORM conventions already in CLAUDE.md.

### (d) Keep access derived; key progress on `(user, course, run-number)` directly — no registration FK at all
Progress rows key on `user` + `course` (+ a course "run"/attempt number if FLS needs re-takes), exactly as Moodle's `grade_grades`/`course_completion` do. `is_registered_for_course`-style derivation stays exactly as it is today for the *access* question; progress is a separate concern that doesn't need to know how access was granted.
- **Pros**: zero new sync mechanism, zero disambiguation problem (#3 disappears — Moodle's answer, "don't ask," is free here), zero orphaning policy needed beyond what direct registrations already have (#2 is already-solved), simplest educator-matrix/PDF-report queries (`user` is a plain FK, no branching), and it is a **strict continuation** of the pattern FLS already chose for deadlines (`CohortDeadline`/`UserCohortDeadlineOverride` are per-user artifacts layered on top of derived access, not a materialised registration).
- **Cons**: does not literally satisfy "progress hangs off a registration" as stated in the idea's framing — if there's a hard requirement that a progress row's *foreign key* must point at a registration object (e.g. for reasons outside this research, such as reporting that explicitly needs to know "was this progress made under a cohort registration or a direct one"), this design doesn't provide that without adding a nullable "which registration granted this, if known, at time of last update" annotation field — which reintroduces a lightweight version of (b)'s branching problem, just as metadata rather than as the primary key.
- **Django cost**: lowest of the four — likely just `user` + `collection` (+ run number) FKs on the progress model, matching the shape `UserCourseRegistration` already uses for its own uniqueness constraint (`site_id, collection, user`).

---

## Implications for FLS

**Recommendation: design (d)** — keep cohort access derived exactly as it is today, and key progress on `(user, course)` (+ run/attempt number if retakes matter), independent of *how* access was granted. This is Moodle's actual production answer at scale (`grade_grades`/`course_completion` keyed on `(userid, courseid)`, decoupled from the `enrol`/`user_enrolments` layer), it requires zero new sync/reconciliation infrastructure that FLS doesn't already have, it inherits — rather than reopens — the disambiguation-free answer to "registered both directly and via cohort" that Canvas's precedent shows is genuinely hard to retrofit once you've coupled progress to a specific registration row, and it is consistent with the choice FLS already made for deadlines (derive access, layer a per-user override where needed) rather than requiring that decision to be re-litigated and made inconsistent between the deadline and progress subsystems.

**Strongest argument against it**: if the product requirement is genuinely "progress must be attributable to a specific registration" — e.g. for billing/reporting that needs to answer "did this completion happen under the cohort's paid registration or the learner's individual one," or for a future feature where re-registering (lapsing and re-joining) should reset progress and a bare `(user, course)` key can't represent "which registration-lifetime" a completion belongs to — then design (d) is under-specified and will need a bolt-on run/attempt or "granting registration" reference later anyway, at which point doing that retrofit is arguably more disruptive than picking design (a) up front while `student_progress` is presumably still early enough to redesign cheaply. That said, nothing in `student_management/models.py` as it stands today suggests re-registration/retake or per-registration billing is a live requirement — `UserCourseRegistration`/`CohortCourseRegistration` are both simple `is_active` toggles, not versioned/dated registration periods — so this risk is speculative against the current model shape, not evidenced by it.
