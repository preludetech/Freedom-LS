# Research: modelling progress when content is shared across courses

## FLS baseline (from code, for reference)

- `ContentCollectionItem` (`freedom_ls/content_engine/models.py`) is a polymorphic through-row: `collection_type/collection_id` (a `Course` or `CoursePart`) → `child_type/child_id` (a `Topic`, `Form`, or `CoursePart`), with `order` and `overrides`. There is **no uniqueness constraint on `child_type`/`child_id`**, so nothing in the schema stops the same `Topic`/`Form` row being linked from two different `ContentCollectionItem`s — in the same `CoursePart`, in two different `CoursePart`s of one `Course`, or in two different `Course`s. This is already possible today; it just isn't exercised by any current content.
- `TopicProgress` (`freedom_ls/student_progress/models.py`) is `unique_together = ["user", "topic"]` — one row per learner per `Topic`, full stop, no course dimension.
- `FormProgress` has **no** uniqueness constraint on `(user, form)` — multiple attempt rows already exist per learner per form (`start_time`/`completed_time` per row), but "is this form done" for course-percentage purposes is computed as `completed_time__isnull=False` **for that `form_id`, any attempt, any course** (`update_course_progress_on_completion`, lines 71-81).
- `calculate_course_progress_percentage` (`freedom_ls/student_management/utils.py`) walks `course.children()`/`CoursePart.children()` today, and tests topic/form membership against the learner's **global** `completed_topic_ids`/`completed_form_ids` sets — no course-scoping anywhere in the completion check.
- `CourseProgress` is `unique_together = ["user", "course"]` and stores a derived `progress_percentage`, recomputed on every completion event via `update_course_progress_on_completion`.

Net effect confirmed by reading the code: if the same `Topic` is linked into both a full course and a revision course, `TopicProgress` cannot represent "complete in one, incomplete in the other" — there is exactly one row, keyed only by `(user, topic)`. Completing it in either course completes it everywhere, and `calculate_course_progress_percentage` recomputes both `CourseProgress` rows to reflect that global row. The same is true for forms, but with an added wrinkle: because `FormProgress` already allows multiple attempts, a second attempt started in the revision course is still just another row against the same `form_id`, pooled into the same "ever completed" set used for both courses' percentages.

## Precedent in other systems

### Moodle — activities belong to exactly one course; sharing means duplication

Moodle's `course_modules` table has a non-nullable `course` field: a `course_module` (the placement of an activity in a course, e.g. an instance of `mod_quiz`) belongs to exactly one course, and the module's underlying "instance" row (in `mdl_quiz`, `mdl_page`, etc.) is not deduplicated across courses. Moodle's own docs list four ways to get the same activity into more than one course — **Import course data**, **Backup and restore**, **Course copy**, and third-party plugins like *Sharing Cart* — and all of them are variants of "duplicate the module and its instance into the target course," not "link one shared object into two courses." Import explicitly does **not** carry user data, i.e. no completion state travels with the copy. ([Reusing activities — MoodleDocs](https://docs.moodle.org/502/en/Reusing_activities), [Course module — MoodleDocs](https://docs.moodle.org/dev/Course_module), [Course Modules table — Moodle 3.9 schema](https://moodleschema.zoola.io/tables/course_modules.html))

Completion (`course_modules_completion`) is keyed off the `course_modules` row (the per-course placement), so two duplicated copies of "the same" activity in two courses have entirely independent completion rows by construction — there is no possibility of cross-course leakage, but also no possibility of intentional sharing; content maintenance is manual and forked after duplication (edit one copy, the other doesn't change) unless a sync-capable plugin is used.

Canvas's **Blueprint courses** are the closest thing to a Moodle-style model with sync bolted on: a blueprint is a master course; "associated" courses each get their own independent copy of every object (assignments, modules, pages), and syncing is an explicit, all-or-nothing push that overwrites *locked* objects in each associated course while leaving instructor-authored content alone. Grades/progress in each associated course remain fully independent — sync only pushes content, never learner state. ([Managing Course Content Using Canvas Blueprints](https://support.cmts.jhu.edu/hc/en-us/articles/30758133925517-Managing-Course-Content-Using-Canvas-Blueprints), [Blueprint sync mechanics — Instructure Community](https://community.canvaslms.com/t5/Admin-Guide/How-do-I-sync-course-content-in-a-blueprint-course-as-an-admin/ta-p/171))

### Open edX — explicit definition/usage split, and progress keyed by (student, block, **course**)

Open edX separates a block's **definition** (the shared, reusable content — what content libraries store) from its **usage** (`usage_key`/`BlockUsageLocator`, the specific placement of that definition inside one course's outline). Content Libraries let the same definition (e.g. a `library_content` block or an imported library problem) be referenced from multiple courses. ([Content Libraries Architecture — Open edX wiki](https://openedx.atlassian.net/wiki/spaces/AC/pages/144441629/Content+Libraries+Architecture), [Working with Content Libraries](https://edx.readthedocs.io/projects/open-edx-building-and-running-a-course/en/open-release-redwood.master/course_components/libraries.html))

Crucially, learner state is **not** keyed on the shared definition. `StudentModule` (`lms/djangoapps/courseware/models.py`) has:

```
unique_together = (('student', 'module_state_key', 'course_id'),)
```

`module_state_key` is the XBlock **usage_id**, and `course_id` is part of the key alongside it — so even when the underlying content definition is shared via a library, the same block placed into two different courses produces two independent `StudentModule` rows (different `course_id`), and the same block placed twice in *one* course (two different usage ids from the same definition) also produces independent rows (different `module_state_key`), because usage ids are unique per-placement, not per-definition. Tracking-log events for library-sourced blocks additionally emit `original_usage_key`/`original_usage_version` in their context, precisely so analytics can still tie a course-scoped completion event back to the shared definition it came from without conflating the two. ([edx-platform `courseware/models.py`](https://github.com/openedx/edx-platform/blob/f80720d09ec4d420cc36e235b83d07c6a698ccde/lms/djangoapps/courseware/models.py))

This is the cleanest precedent for FLS: **progress attaches to the placement (usage), not the definition**, and the placement's key includes the course context.

### SCORM, xAPI, LTI — the same generalisation from three more angles

- **SCORM**: a *Registration* is the atomic unit of progress — "the logical association of one Learner to one Course [package]." Multiple registrations can exist for the same learner against the same course package (e.g. re-takes), and registrations for different course packages are always independent, even if the packages were built from the same source content — SCORM has no notion of a single completion record shared across two different "courses." ([SCORM Cloud: What's a Registration?](https://support.scorm.com/hc/en-us/articles/206163476-Getting-Started-What-s-a-Registration), [SCORM Cloud Core Concepts](https://cloud.scorm.com/docs/v2/knowledge_base/concepts/))
- **xAPI**: statements identify the *activity* (which can legitimately be the same IRI/definition reused anywhere) but scope an individual experience with `context.registration` (a UUID tying together all statements of one attempt) and `context.contextActivities.parent`/`grouping` (which course/module the activity was experienced *within*). The activity identity and the context it was experienced in are deliberately separate fields — exactly the definition/placement split again, just expressed as statement metadata rather than a foreign key. ([xAPI Deep Dive: Context](https://xapi.com/blog/deep-dive-context/))
- **LTI**: `resource_link_id` is "an opaque unique identifier that the Tool Consumer guarantees will be unique... for every placement of the link" — the *same* tool configuration launched twice in one course, or the same tool launched from two different courses, gets a **different** `resource_link_id` each time, and re-importing a link into a new context also changes it. Tool-side state (e.g. an external quiz's grade) is naturally scoped per placement because the id it's keyed on is per-placement. ([What is the resource_link_id in LTI? — 1EdTech](https://support.imsglobal.org/support/solutions/articles/48000607731-what-is-the-resource-link-id-in-lti-))

### The general pattern

Every precedent draws the same line: a **content definition** (markdown text, a quiz's questions, a SCORM package, an xAPI activity IRI) is reusable and shared; a **usage/placement in a context** (a course_module, a `usage_key`, a registration, a `resource_link_id`) is where progress/completion actually attaches, and that placement's identity is scoped to (at minimum) the course, and ideally to the specific slot within the course. Systems either (a) literally duplicate the content object per placement (Moodle, Canvas Blueprint) so the existing "one row per content object" progress model needs no change, or (b) keep content genuinely shared and instead widen the *progress* key to include the context (Open edX, SCORM, xAPI, LTI). No system studied lets a single global completion row, keyed only on the content object, answer "is this done" across multiple independent course contexts — which is exactly what FLS's `TopicProgress.unique_together = ["user", "topic"]` does today.

## Design options for FLS

### 1. Progress keyed on (registration, content item) — add a course/registration FK to `TopicProgress`/`FormProgress`

Schema: `TopicProgress.unique_together = ["user", "course", "topic"]` (or FK to `CourseProgress`/a registration row instead of raw `user`+`course`). `calculate_course_progress_percentage` and `update_course_progress_on_completion` filter `completed_topic_ids`/`completed_form_ids` by course as well as user.

- Learner experience: completing a topic in the revision course does **not** tick it in the full course, and vice versa — this is the desired revision-course behaviour.
- Gap: still ambiguous if the **same course** links the same `Topic` twice (e.g. two `CoursePart`s of one course both reference it, or a "recap" section re-links an earlier topic within the same course) — the key `(user, course, topic)` collapses those two placements into one row, same problem as today just at a smaller scope. Given nothing currently stops this in `ContentCollectionItem`, it is a real (if currently unexercised) edge case, not a hypothetical.
- Migration cost: moderate — one new FK, a data migration to backfill `course` on existing rows (trivial today because every `Topic`/`Form` is in exactly one course now, so the backfill is unambiguous), and every read site that queries `TopicProgress`/`FormProgress` without a course qualifier needs auditing (learner dashboards, "resume" logic, quiz-attempt history displays).

### 2. Progress keyed on (registration, `ContentCollectionItem`) — the placement, not the content object

Schema: `TopicProgress`/`FormProgress` gain a FK to `ContentCollectionItem` (the specific slot in the specific course/part) instead of, or in addition to, the FK to `Topic`/`Form`. This is the direct FLS analogue of Open edX's `usage_key` + `course_id` composite key.

- Solves both the cross-course case and the within-course-duplicate-placement case from Option 1, because every placement is a distinct `ContentCollectionItem` row regardless of how many courses or parts reference the same `Topic`.
- Learner experience: identical to Option 1 for the stated modular-course use case — revision-course completion is independent of full-course completion.
- Cost: the largest of the four. `ContentCollectionItem` currently has no stable identity concept exposed to progress code; `content_item_field_name`/`completion_field_name` machinery in `CourseItemProgress`, `update_course_progress_on_completion`'s "find parent courses for this content item" traversal, and every "has the learner ever completed this Topic" check outside a course context (e.g. a topic preview page, if one shows global status) would need to decide whether "completed" means "completed in *this* placement" or requires a new cross-placement rollup concept. Given `Topic`/`Form` model instances are otherwise the natural unit content authors think in, this is more machinery than the problem currently requires — worth deferring unless within-course duplicate placement becomes a real content pattern (see Implications).

### 3. Duplicate-on-add (Moodle/Canvas-style)

Adding a `Topic` to a second course clones a new `Topic` row (new UUID, new slug, copied `content`) rather than re-linking the original. No changes to `TopicProgress`/`FormProgress`/`calculate_course_progress_percentage` at all — `unique_together = ["user", "topic"]` is correct again because each course's copy is a genuinely distinct `Topic`.

- Learner experience: fully correct — the revision course's topic and the full course's topic are unrelated objects, so completing one never touches the other. Matches "redo the material" intent exactly.
- Cost: shifts the problem to content maintenance. FLS's content model loads `Topic`/`Form`/`Form Question`/`QuestionOption` from markdown source files (`BaseContent.file_path`) — cloning a `Form` means cloning its `FormPage`/`FormQuestion`/`QuestionOption` tree too. Editing the tutorial text in the source file and re-running content load would need to propagate to every clone, or clones silently drift (exactly Moodle's documented downside — import doesn't sync). No sync story exists in FLS today (no Blueprint-equivalent), so this option trades a progress-modelling problem for a content-drift problem, which for a "revision course drawn from a full course" use case is probably worse: revision content by definition *should* track the source it's revising.

### 4. Deliberate carry-over: progress stays global, courses opt in/out via a "count prior completions" flag

Add e.g. `Course.credit_prior_completions: bool` (default `True`, preserving today's behaviour); when `False`, `calculate_course_progress_percentage` for that course ignores prior completions of shared items in its `completed_topic_ids`/`completed_form_ids` filtering, effectively "starting count from zero" without touching `TopicProgress` itself.

- This addresses the **display** half of the problem (a revision course's progress bar doesn't credit topics completed elsewhere) but not the **completion event** half: `TopicProgress.unique_together = ["user", "topic"]` means there is only one row and one `complete_time`. If a learner has already completed a topic via the full course, re-visiting it in the revision course cannot produce a *new* completion event to actually exercise "redo the material" — the existing row's `complete_time` is already set, so the revision course's own completion UI (a checkmark, a "mark as read" action) has nothing to do. Worse, if the revision-course visit is allowed to reset `complete_time` to blank so the learner can "redo" it, that silently un-completes the topic in the full course too — the opposite of the flag's intent.
- Verdict: Option 4 as a pure display filter is incoherent for the stated revision-course use case; making "redo" actually work requires a place to store a second completion event, which converges back to Option 1 or 2. It may still be useful **later** as an orthogonal opt-in for a *different* future case (e.g. a "prerequisite" course whose completions genuinely should count toward a follow-on course) — but it does not solve this problem alone.

## Removal and pooling questions

**Topic removed from a course after learners have progress against it.** Today, deleting a `ContentCollectionItem` link is independent of `TopicProgress` — the progress row is keyed on `(user, topic)`, not on the link, so it simply survives, orphaned relative to that course, and `calculate_course_progress_percentage` silently stops counting it (both the numerator and the denominator shrink because the walk is over `course.children()` as currently linked, not as historically linked) — so an existing `CourseProgress.progress_percentage` can jump on the next recompute with no explicit learner-facing signal. This is a pre-existing gap, not new to modular courses, but modular courses make it much more likely to be hit (a revision course is expected to have its item set edited over time). Under Option 2 (placement-keyed progress), the same question resurfaces explicitly: deleting the `ContentCollectionItem` must not cascade-delete the learner's completion record for it (that would be a genuine data-loss/audit problem — "did the learner ever complete this?" should survive a content edit), so it needs a deliberate on-delete policy (e.g. `SET_NULL` on the placement FK plus keeping the content FK, mirroring how `CourseProgress.last_accessed_content_type` already uses `SET_NULL` rather than `CASCADE` for exactly this reason).

**Shared `Form` (quiz) answered in two courses — pooled or separate attempts?** Under the current schema, always pooled: `FormProgress` has no course dimension, so a second attempt started from the revision course is just another attempt row against the same `form_id`, and `update_course_progress_on_completion`'s `completed_form_ids` set is global. For a revision course this is almost certainly wrong for the same reason Option 4 breaks down for topics — the point of revision is a fresh attempt, and a pass in the full course shouldn't silently satisfy the revision course's quiz requirement (or vice versa: a failed revision attempt shouldn't taint the original course's pass record). Any of Options 1/2 that add a course (or placement) dimension to `FormProgress` as well as `TopicProgress` fixes this the same way; Option 3 (duplicate the `Form`, including its `FormPage`/`FormQuestion`/`QuestionOption` tree) also fixes it but inherits the content-drift cost noted above, twice over for quizzes since duplicating a quiz risks the two copies' correct-answer keys diverging silently.

## Implications for FLS

**Recommendation.** Course-scope both `TopicProgress` and `FormProgress` (Option 1: add a `course` — or better, a FK to the specific `ContentCollectionItem` placement, Option 2 — dimension to the uniqueness/attempt-grouping key), rather than duplicating content (Option 3) or trying to make a pure display-layer flag work (Option 4, which this research shows cannot actually deliver "redo the material" on its own). Between Option 1 and Option 2: start with Option 1's shape (course-scoped, not placement-scoped) since it is materially cheaper and correctly handles the stated use case (revision course vs full course); only pay for Option 2's finer placement-level granularity if/when "the same topic twice in one course" becomes an actual content requirement rather than a theoretical gap in `ContentCollectionItem`'s constraints.

**Must this be designed now, or can it be deferred?** It does not need to be *built* now (no UI or authoring workflow for modular/revision courses needs to ship in this iteration), but the **schema decision should be made now**, because the alternative is a lossy, big-bang migration later:

- `TopicProgress.unique_together = ["user", "topic"]` is a real constraint that a later migration would have to drop and re-populate against every historical row, guessing which course each historical completion "belongs to" for learners who — under a future modular-course world — might legitimately have more than one course claiming the same topic. Doing the migration *before* any content is actually shared across courses means the backfill is unambiguous (today, by the current single-course-per-topic reality, `course` can be derived exactly for every existing row); doing it *after* content sharing has already happened means some rows will be genuinely ambiguous and require manual/product judgement calls.
- Concretely forward-compatible now, unblocking later: add the course-scoping FK to `TopicProgress`/`FormProgress` (or introduce it as part of this progress-tracking spec's other work) even though every `Topic`/`Form` is in exactly one course today — the change is behaviourally invisible (single course in, single course out) but converts a future breaking migration into a future additive one (just relax any lingering single-course assumptions in call sites when modular courses actually ship).
- Deferral is **not** safe if, in the meantime, any new feature bakes in the "global per-topic completion" assumption more deeply than it already is — e.g. a cross-course "you've completed this topic before" badge, a topic-level (course-independent) completion API, or public progress reporting keyed purely on `topic_id`. Each of those would need to be revisited (or removed) once course-scoping lands, so the safest posture is: do the additive schema change now, and treat "global topic completion" as an implementation detail scheduled for removal, not a public contract, in anything built between now and the modular-courses feature.
- `FormProgress`'s attempt-pooling is the sharper near-term risk of the two: it already stores multiple rows, so adding a course dimension to it is a low-risk, purely additive change (no uniqueness constraint to relax), and it should probably be done alongside whatever this progress-tracking spec is already touching in `FormProgress`, rather than left for a dedicated modular-courses project later.
