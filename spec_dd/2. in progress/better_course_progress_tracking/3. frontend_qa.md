# Better course progress tracking — browser QA

Manual browser verification for the work in `2. plan.md`. Everything below is done through a real
browser against a locally running dev server.

This change re-keys progress onto `Learner` + the granting registration. Almost every failure mode it
introduces is **silent**: a page renders 200 with a plausible-but-wrong percentage. So most steps
below tell you to check *whose* number is on screen, not just that a number is there.

---

## 0. Setup

### 0.1 Start the server

```
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL for everything below: `http://127.0.0.1:$PORT`

Substitute your actual port wherever you see `$PORT` in a URL.

### 0.2 Seed the data

Every command below is copy-pasteable as written. `SITE_NAME` is a **positional** argument on some
of these commands and an option on others, so the shapes deliberately differ — do not normalise them.

```
uv run python manage.py qa_create_organisation_scenarios
uv run python manage.py qa_create_course_player_learner
uv run python manage.py qa_create_cohort_progress DemoDev
uv run python manage.py qa_create_report_cohort \
    --cohort-name "QA Report Cohort" \
    --course-slug functionality-demo-course-parts \
    --educator-email org.educator@example.com
```

`qa_create_report_cohort` without `--course-slug` succeeds but registers the cohort for **nothing** —
its Course Progress panel then reads "No course registrations found for this cohort". That is the
command behaving as designed, not a bug.

`qa_create_organisation_scenarios` and `qa_create_cohort_progress` both expect the demo course
`functionality-demo-course-parts` to exist already; neither creates it. If one of them exits with a
`ClickException` naming a missing course, load the demo content and retry — that is a setup problem.
A **traceback** from either is a real regression in the QA helpers (plan Task 21). Record it.

## 1. The golden path: a learner takes a course

Log in as **Cara** (`cohort.learner@example.com`).

1. Go to `http://127.0.0.1:$PORT/` (the dashboard). **Expect:** her registered courses listed, each
   with a progress bar. Note the percentage on the cohort course.
2. Click into a course. **Expect:** the course detail page, with a CTA button.
   - If she has no progress at all, the CTA reads **"Start course"**.
   - If she has partial progress, it reads **"Continue"**.
   - If the course is complete, it reads **"Review course"**.
   - **This is the one to watch.** Under this change a progress row now exists from the moment she
     registers, *before* she has opened anything. A learner who has registered but never opened the
     course must still see **"Start course"**, not "Continue". If a freshly-registered learner sees
     "Continue" at 0%, that is the eager-creation regression.
3. Click the CTA. **Expect:** the player at item 1, with the table of contents panel, a progress bar
   in the header, and the item title.
4. Work through a topic: click **Next** / **Mark complete**. **Expect:** it advances, the TOC marks
   that item complete, and the header percentage goes **up**.
5. Leave the course (go back to the dashboard), then click back into the same course.
   **Expect:** you land on the item you left off at, **not** item 1. This is the resume pointer,
   which changed type in this work — a resume that always lands on item 1 is the regression.
6. Complete every item. On the last one, **Expect:** you are taken to the course finish page.
7. On the finish page, check the **Course Summary** box:
   - **"Started:"** shows the date she **first opened content**, not the date she was registered.
     Since the seed registers learners well before this QA run, if "Started:" shows a date that
     matches her registration rather than today, that is the `created_at` / `started_at` mix-up.
   - **"Started:" must not be blank.** A blank value here is the silent template failure this change
     is most likely to produce — Django renders a missing attribute as the empty string, so a wrong
     field name shows an empty row instead of raising.
   - **"Completed:"** shows today.
8. Go back to the dashboard. **Expect:** the course now appears as complete, and no longer appears in
   the in-progress list.
9. If completing that course leaves Cara with **nothing** in progress, read the empty **In Progress**
   section's copy. **Expect:** it says her courses are finished and waiting in Learning History —
   **not** "You haven't signed up for any courses yet.", which would be untrue for a learner who is
   still registered. A learner with no registrations at all still gets the never-signed-up copy.

## 2. Two organisations, one course — the core of this change

This is success criterion 5, and it is the reason the work exists. Cara holds a `Learner` row in two
organisations, but the seed registers her for a *different* course in each. Create the overlap.

### 2.1 Create the second registration

Log in as the superuser and go to `http://127.0.0.1:$PORT/admin/`.

Cara already reaches `functionality-demo-course-parts` through the **RPAS Training** Year 9 Maths
cohort — a *cohort* grant. Give her a second, *individual* grant on that same course through her
other organisation, so the two grants are of different kinds and §2.2's resolution order has
something to resolve.

1. Find **Learner course registrations**. Note the registration that gives Cara her Northside course.
2. Add a new **Learner course registration**: `learner` = Cara's **Northside** `Learner` row,
   `collection` = `functionality-demo-course-parts` (the course her RPAS **cohort** is registered
   for), `is_active` = checked.
3. **Expect:** it saves without error. Cara now holds two grants for one course — cohort-granted
   through RPAS Training, individually granted through Northside.

While you are in the admin, this doubles as QA of the rewritten admin (plan Task 5):

4. Open **Course progress records**. **Expect:** the changelist loads, and its columns show
   **Learner**, **Course**, and the granting registration — not a bare user. Search for
   `cohort.learner@example.com`. **Expect:** her records are found (the search now runs through
   `learner → user → email`).
5. **Expect:** **two** course progress records for Cara on that course — one per registration. Note
   both. Open one and save it without changing anything. **Expect:** it saves.
6. Open **Topic progress records** and **Form progress records**. **Expect:** both changelists load
   and show a course progress record and a collection item per row. A `FieldError` or a 500 here is
   the admin regression.

### 2.2 Prove the two records are independent

7. Log in as **Cara** and open that course. Complete a couple of items. Note the percentage.
8. Back in the admin as superuser, look at **both** of her course progress records for that course.
   **Expect:** exactly **one** of them has moved off 0%. The other is still at 0%, with no
   `completed_time` and no `last_accessed_item`.
   - Which one moved: the **cohort-granted** one, because cohort registration wins the resolution.
   - **If both moved, or if the individual one moved, that is the failure this whole change exists to
     prevent.**
9. Complete the course as Cara. **Expect:** the cohort-granted record has a `completed_time`; the
   individually-granted one still has none and is still at 0%.

### 2.3 The learner only ever sees one of them

10. As Cara, go back to the dashboard. **Expect:** the course appears **once**, not twice, and shows
    the percentage of the record she has been working in. A duplicated course card means a read path
    is listing records rather than courses.

## 4. The educator cohort progress matrix

Log in as **Olive Educator** (`org.educator@example.com`) and go to
`http://127.0.0.1:$PORT/educator/`.

1. Pick **RPAS Training**, then **Cohorts**, then the **Year 9 Maths** cohort, then the
   **Course Progress** tab.
2. **Expect:** the matrix renders — one row per cohort member, one column per course item, a
   percentage per learner, and part headers if the course has `CoursePart`s.
3. **The percentage column and the item cells must agree.** For at least two learners, read the
   percentage in the left column and count the completed cells across the row. If a learner shows
   40% but every cell is empty, or 0% with cells ticked, the two halves are reading different
   records — that is the incoherence this change is meant to remove.
4. Find **Cara** in the matrix (she is a Year 9 Maths member). **Expect:** the panel shows her
   **cohort** progress. If she did work under her individual registration for the overlapping course
   from §2, the cohort panel for *that* course legitimately shows her at 0%.
5. **Expect a visible explanatory line** near the registration selector, saying in plain language
   that the panel shows only this course registration's progress. A bare unexplained 0% is the
   defect; the copy is what makes it honest.
6. Change the **registration** dropdown (if the cohort holds more than one course registration).
   **Expect:** both the percentage column and the item cells change together to the newly selected
   registration. If only one half updates, they are not filtered on the same registration.
7. Page through the learner rows and the item columns (both are paginated). **Expect:** progress
   stays attached to the right learner and the right item on page 2 — a mis-keyed map usually shows
   up as everything reading "not started" on the second page.
8. **Organisation scoping:** confirm **no Northside learner** (`northside.learner1@example.com`,
   `northside.learner2@example.com`) appears in an RPAS Training matrix, and no Southgate learner
   either.

### 4.1 Educator permission branches

9. Log out, log in as **Lena Legacy** (`legacy.educator@example.com`), who holds a grant on **Year 9
   Maths only**. Go to `http://127.0.0.1:$PORT/educator/`.
   **Expect:** she can open Year 9 Maths and see its Course Progress tab.
10. Try to reach the **other RPAS cohort** by URL directly (take the cohort id from Olive's session
    and put it in `/educator/organisations/rpas-training/cohorts/<id>`). **Expect:** 404 or refusal,
    **not** a rendered matrix. This change touched the panel's querysets, so re-confirm the grant
    still gates it.
11. Log out, log in as **Noah** (`no.access@example.com`), who has no educator role at all.
    Go to `/educator/`. **Expect:** refused — no organisation list, no matrix.

### 4.2 The panel renders for someone who can delete the cohort

The delete button only renders for a viewer holding `delete_cohort` — site admins and superusers, not
the educator personas above. That viewer takes a different code path through the panel, and it is the
path that broke: the delete dialog previews what a deletion would cascade, and progress records now
refuse to be cascaded.

12. Log in as the **superuser** and open a cohort that **has** granted course progress — Year 9 Maths,
    or the report cohort from §12: `/educator/organisations/<org-slug>/cohorts/<id>`.
    **Expect:** the panel renders normally, with its tabs and Course Progress matrix. A **500** here
    (`ProtectedError`, "Cannot delete some instances of model Cohort…") is the regression.
13. Open that cohort's **Delete** dialog. **Expect:** a plain sentence saying the cohort cannot be
    deleted and naming what still depends on it — e.g. *"This cohort cannot be deleted because it
    still has 9 course progress records."* — and **no** Delete button, only Close. A cascade list
    ("This will also delete: …") here would be a lie: the deletion cannot happen.
14. Open a cohort with **no** granted progress. **Expect:** the ordinary "Are you sure you want to
    delete…" dialog with a working Delete button. The blocked message must not be shown for
    everything.

## 5. Removed learners and deactivated registrations

Success criterion 4 — nothing in this work retires a record.

1. As superuser in the admin, find **Rita Removed** (`removed.learner@example.com`). She is a
   deactivated `Learner` who still holds an active course registration.
2. Confirm she has (or give her) some progress: register a fresh course to her and complete an item

3. **Expect:** after deactivation, her course progress record still exists, with its percentage,
   `completed_time` and resume pointer **unchanged**. Deactivation must destroy nothing.
4. Find a **cohort membership** for a learner who has progress. Delete it in the admin.
   **Expect:** the deletion succeeds, and their course progress record still exists untouched.
5. Now try to **delete** a `LearnerCourseRegistration` that has granted a record.
   **Expect:** the admin refuses with a protected-object message naming the course progress record.
   This is intended: a registration that authorised a learner's work cannot be deleted while that

   **Expect:** also refused, for the same reason. This one is genuinely new behaviour — confirm the
   message is a protected-object error, not a 500. The refusal must be readable in **both** places
   the cohort can be deleted from: the admin (a protected-object page) and the educator interface
   (§4.2's blocked dialog).
7. Try to **delete a Topic** that has progress against it. **Expect:** refused, not a silent cascade
   that wipes completions.

## 8. Deadlines are now per-organisation

Success criterion 9. This is the behaviour reversal with nothing to grep for.

`qa_create_learner_deadlines` seeds its own hard-coded learners and courses and has nothing to do
with the personas below — run it only if you want a second, independent deadline fixture to look at.
The two commands that matter here take the cohort and course explicitly:

```
uv run python manage.py qa_create_soft_deadline DemoDev \
    --cohort-name "Year 9 Maths" --course-slug functionality-demo-course-parts
uv run python manage.py qa_create_deadline_overrides DemoDev \
    --cohort-name "Year 9 Maths" --course-slug functionality-demo-course-parts \
    --learner-email cohort.learner@example.com
```

`--days-from-now` (negative for the past) and `--hard` / `--soft` are how you produce the specific
deadlines steps 1–6 below ask for; `--item-slug` narrows a deadline to one topic or form instead of
the whole course.

1. Give **Cara** a deadline on the overlapping course from §2 through **one** organisation only —
   e.g. a `CohortDeadline` on the RPAS Year 9 Maths cohort's registration.
2. Log in as Cara and open that course's table of contents.
   **Expect:** the deadline shows, attached to the item it was set on.
3. Now add a **different** deadline for the same course through the **Northside** individual
   registration (a `LearnerDeadline`), with an obviously different date.
4. Reload Cara's course TOC.
   **Expect:** she sees the deadline for the organisation she is **studying through** — the cohort
   one, since cohort registration wins — and **not a merged list of both**. Two deadlines showing
   side by side for one item is the un-scoped union this change removes.
5. Set a **hard** deadline in the past on an item Cara has not completed, through her resolved
   organisation. Try to open that item's URL directly.
   **Expect:** she is redirected to the course detail page, not shown the item.
6. Set a hard past deadline through the **other** organisation only.
   **Expect:** it does **not** lock her out, because that is not the organisation she is studying

## 9. Quizzes and attempts

Attempts are now scoped to the record, and all six attempt helpers moved together.

```
uv run python manage.py qa_create_report_course --course-key short
uv run python manage.py qa_create_quiz_progression_block
uv run python manage.py qa_create_multiselect_quiz_scoring
```

`--course-key short` produces the slug `qa-report-short-course`; the key is required and is what the
slug is built from.

1. As a learner, open a course containing a scored quiz and start it.
2. Answer the questions and submit. **Expect:** the results page shows a score, a pass/fail verdict,
   and (if the quiz allows it) a retry link.
3. **Fail the quiz deliberately.** Then go to the course finish page.
   **Expect:** the course is **not** marked complete, and the page names the quiz you still have to
   pass and links to the retry. This behaviour predates the change and must survive it.
4. Retry and pass. **Expect:** the finish page now completes the course.
5. Go back to the quiz's start page. **Expect:** the previous-attempts list shows **your attempts in
   this course**, newest first, and the count is right. Attempts from a *different* course's record
   must not appear here.
6. **Leave a quiz half-finished** (start it, answer one page, navigate away). Come back to the quiz.
   **Expect:** it offers to resume, and drops you on the page you left off at — not back at page 1
   and not into a brand-new attempt.
7. For a **submit-on-exit** quiz, start it and use the exit dialog's "Leave and submit".
   **Expect:** it finalises and takes you to the results page. Do this twice in quick succession
   (double-click / resubmit) and **expect** no error and no second attempt.

### 9.1 Failure branches

8. Submit a form page with a **required** question unanswered. **Expect:** the page re-renders naming
   the question number, and **nothing is saved** — no attempt is completed and no progress advances.
9. Guess a form URL for an item you have not unlocked yet
   (`/courses/<slug>/<index>/start_form` for a later index). **Expect:** redirected to the course
   detail page, and **no** attempt is created for that quiz.

## What "pass" means

Every numbered **Expect** above holds, and in particular:

- No page 500s.
- Nothing shows a **blank** where a date or percentage belongs (§1.7 especially — the blank is the
  silent template failure).
- Every percentage on screen belongs to the record the learner is actually working in (§2, §4).
- The educator matrix's percentage column and its item cells always tell the same story (§4.3).
- Deleting a registration, cohort or topic that has progress is **refused**, not silently destructive
  (§5) — and the refusal is a readable message in both the admin and the educator interface (§4.2).
- `danger_content_delete` still works (§13.2).
- Every command in §0.2, §8, §9, §12 and §13 runs as written. A click usage error ("Missing argument
  'SITE_NAME'", "Missing option '--cohort-name'") means this plan has drifted from the commands
  again — fix the plan, do not log it as a product regression.

Record any failure with: the URL, the persona logged in, what you expected, what you saw, and the
relevant admin row ids so the record in question can be found.
