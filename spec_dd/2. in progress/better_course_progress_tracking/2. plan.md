# Better course progress tracking — implementation plan

Implements `1. spec.md` in this directory. The spec is the authority on *what* and *why*; this
document is the ordered *how*. Where this plan names an identifier, that identifier comes from the
spec's **Terminology** table — including the five rows added during this plan phase
(`ensure_course_progress_records_for_cohort_registration`, `ResolvedRegistration`, the
`collection_items()` accessor trio, `completed_form_ids_by_course_progress` and
`course_progress_by_course_for`).

Two spec contradictions were resolved before planning and the spec was edited in place:

1. **Success criterion 12 vs the webhook move.** Moving `course.registered` into a `learner_progress`
   receiver imports `fire_webhook_event` and therefore adds `learner_progress --> webhooks`.
   Criterion 12 now permits exactly that one new edge out of `learner_progress`, and still forbids any
   new runtime edge into it from `learner_management`.
2. **`clean()`'s cohort pairing vs records surviving membership deletion.** `clean()` now asserts the
   cohort pairing at the **organisation grain always** (`learner.organisation_id ==
   cohort_registration.cohort.organisation_id`) and asserts a live `CohortMembership` **only when the
   record is new** (`self._state.adding`). An unconditional membership check would make a removed
   cohort member's record permanently unsaveable, contradicting §Nothing in this work retires a record.

### Task 1 — Expose the collection item from `Course` and `CoursePart`

`freedom_ls/content_engine/models.py`.

Every write path in this work needs the `ContentCollectionItem`, not the resolved child. Per §Content
accessors must expose the collection item, **do not widen the existing accessors' return types** —
add a parallel trio and derive the existing three from it, so every current reader is untouched.

Add to `Course`:

```python
def collection_items(self) -> list[ContentCollectionItem]:
    """The ordered rows placing this course's children.

    Memoized per instance for the same reason children() is -- see its
    docstring for the request-scoped staleness contract. children() derives
    from this, so the two can never disagree about order.
    """
    if not hasattr(self, "_collection_items_cache"):
        self._collection_items_cache = list(self.items.prefetch_related("child"))
    return self._collection_items_cache

def collection_items_flat(self) -> list[ContentCollectionItem]:
    flattened = []
    for item in self.collection_items():
        flattened.append(item)
        if isinstance(item.child, CoursePart):
            flattened.extend(item.child.collection_items())
    return flattened

def viewable_collection_items(self) -> list[ContentCollectionItem]:
    return [
        item
        for item in self.collection_items_flat()
        if not isinstance(item.child, CoursePart)
    ]
```

Then rewrite the existing three to derive:

```python
def children(self):
    if not hasattr(self, "_children_cache"):
        self._children_cache = [item.child for item in self.collection_items()]
    return self._children_cache

def children_flat(self) -> list:
    return [item.child for item in self.collection_items_flat()]

def viewable_items(self) -> list:
    return [item.child for item in self.viewable_collection_items()]
```

`CoursePart` gains `collection_items()` (same body) and derives its `children()` the same way.

`Course.items` (the `GenericRelation`) keeps its name and meaning; `collection_items()` is the
memoised, `child`-prefetched accessor built on it.

**Tests first** (`content_engine/tests/`):
- `viewable_items()[n]` and `viewable_collection_items()[n]` name the same content at every position —
  this positional identity is what the player's 1-based index depends on, and Tasks 14 and 16 both
  assume it.
- `children()` / `children_flat()` / `viewable_items()` return exactly what they returned before, for
  a course with and without `CoursePart`s.
- The memoisation holds: two `collection_items()` calls on one instance issue one items query.

### Task 7 — `learner_for_course`, and one resolution order

`freedom_ls/learner_management/queries.py`.

```python
class ResolvedRegistration(NamedTuple):
    """Which Learner the work lands under, and the registration that decided it.

    The two travel together so no caller can resolve one and re-derive the
    other with a subtly different order.
    """
    learner: Learner
    registration: LearnerCourseRegistration | CohortCourseRegistration


def learner_for_course(user: User, course: Course) -> ResolvedRegistration | None:
    cohort_registration = (
        CohortCourseRegistration.objects.filter(
            collection=course,
            cohort__cohortmembership__learner__user=user,
            cohort__cohortmembership__learner__is_active=True,
            is_active=True,
        )
        .select_related("cohort__organisation")
        # Deterministic: without it a learner in two cohorts that both hold an
        # active registration for this course lands in whichever record the
        # query planner happened to return.
        .order_by("-is_active", "-registered_at")
        .first()
    )
    if cohort_registration is not None:
        learner = (
            Learner.objects.filter(
                user=user,
                is_active=True,
                cohortmembership__cohort_id=cohort_registration.cohort_id,
            )
            .select_related("organisation")
            .first()
        )
        if learner is not None:
            return ResolvedRegistration(learner, cohort_registration)

    registration = latest_registration(user, course)
    if registration is None:
        return None
    return ResolvedRegistration(registration.learner, registration)
```

The `order_by` on the cohort branch is the gap §Resolving the record requires closing. Today that
branch's bare `.first()` picks an organisation *label*; under this work it picks **which record
accumulates the learner's work**.

Re-express `organisation_for_learner_course` on top of it — one implementation, so fixing the
tiebreak fixes both:

```python
def organisation_for_learner_course(user, course) -> Organisation | None:
    resolved = learner_for_course(user, course)
    return resolved.learner.organisation if resolved is not None else None
```

This returns `learner.organisation` where the old cohort branch returned `cohort.organisation`.
They are the same organisation — `CohortMembership.clean()` forbids a cross-organisation membership —
so the answer is unchanged. `latest_registration` is **not** changed: its "most recent active, else
most recent of any status" behaviour is deliberate and is what lets a deactivated `Learner` still
reach their own record.

**The cohort path grows from one query to two, and an existing test pins the old number.**
`organisation_for_learner_course` today returns `cohort_registration.cohort.organisation` straight off
its `select_related`, in one query. `learner_for_course` needs a `Learner` *instance* as well, and the
join from the registration back to this member's `Learner` is a reverse relation that `select_related`
cannot follow — so the second query is unavoidable given the return shape. Update
`TestOrganisationForLearnerCourseQueryCount.test_cohort_path_never_looks_at_individual_registrations`
(`learner_management/tests/test_queries.py:541-562`) from `django_assert_max_num_queries(1)` to `(2)`
**in this task**, not when someone hits the failure. The ceiling that actually matters — that cost does
not grow with how many registrations the learner holds — still holds at 2, which is what that test
class exists to protect.

The `.first()` fallback on the `Learner` lookup is deliberate: `CohortMembership.clean()` forbids a
cross-organisation membership, but factories never call `full_clean()`, so a test-built row can exist
that the lookup cannot match. Falling through to the individual branch is the safe answer there.

**Tests first:** the cohort branch is deterministic across repeated calls for a learner in two
cohorts both holding an active registration for one course (pin the choice; do not assert "one of the
two"); cohort registration still wins over an individual one; `organisation_for_learner_course`
returns exactly what it returned before on every existing case; a cross-organisation
`CohortMembership` built by a factory falls through to the individual branch rather than raising.

### Task 8 — `ensure_course_progress_record` and the cohort fan-out

New file `freedom_ls/learner_progress/utils.py` — matching `ensure_learner`'s home in
`learner_management/utils.py`. There is no `services.py` convention in this codebase; do not
introduce one.

```python
def _registration_kwargs(
    registration: LearnerCourseRegistration | CohortCourseRegistration,
) -> dict[str, LearnerCourseRegistration | CohortCourseRegistration]:
    """Which of the two grant FKs this registration fills.

    One helper, so the service's write and course_progress_for's read can never
    disagree about which column a registration lives in.
    """
    if isinstance(registration, LearnerCourseRegistration):
        return {"learner_registration": registration}
    return {"cohort_registration": registration}


def ensure_course_progress_record(
    learner: Learner,
    course: Course,
    registration: LearnerCourseRegistration | CohortCourseRegistration,
) -> CourseProgress:
    """The record for this (registration, learner), created if it is missing.

    Idempotent on the *registration*, not on (learner, course): a learner
    already holding a cohort-granted record who is then registered individually
    gets a second record, because a second grant is a second enrolment. An
    existing record is returned untouched -- no timestamp is reset and no grant
    is re-pointed.

    site comes from learner.site, never from _set_site_from_request: a
    management command, a bulk import or a signal fired under a foreign ambient
    site has no request to read it from. _base_manager for the same reason on
    the lookup half -- SiteAwareManager.get_queryset() would AND a foreign
    ambient site onto it, miss the row that exists, and turn an idempotent call
    into a unique-constraint violation. ensure_learner documents the same trap.
    """
    if registration.collection_id != course.id:
        raise ValueError(...)
    record, _ = CourseProgress._base_manager.get_or_create(
        learner=learner,
        **_registration_kwargs(registration),
        defaults={"site_id": learner.site_id, "course": course},
    )
    return record


def ensure_course_progress_records_for_cohort_registration(
    cohort_registration: CohortCourseRegistration,
) -> None:
    """One record per current member of the cohort whose Learner is active.

    bulk_create so a large cohort is one statement, and ignore_conflicts so a
    concurrent individual registration or a re-fired signal loses the race
    harmlessly. bulk_create bypasses save(), so every instance carries its site
    and its grant before the call -- there is no _set_site_from_request to fall
    back on, which is what we want here.
    """
    # No .distinct(): unique_learner_cohort_membership guarantees one
    # membership row per (learner, cohort), so the join cannot duplicate.
    learners = Learner._base_manager.filter(
        cohortmembership__cohort_id=cohort_registration.cohort_id, is_active=True
    )
    CourseProgress._base_manager.bulk_create(
        [
            CourseProgress(
                site_id=learner.site_id,
                learner=learner,
                course_id=cohort_registration.collection_id,
                **_registration_kwargs(cohort_registration),
            )
            for learner in learners
        ],
        ignore_conflicts=True,
    )
```

`get_or_create` and not `update_or_create`: the idempotency rule is "leave it alone".

**Tests first** (the §Test coverage required "sync service" block): called twice → one record, with
unchanged timestamps and an unchanged grant; the cohort fan-out covers exactly the active members and
a member added later gets one; `site` comes from `learner.site` asserted **both** with no ambient
request at all and under a *foreign* ambient site (use `mock_site_context` pointed at a second site);
`ValueError` when the registration's `collection` is not the `course` passed.

### Task 9 — `course_progress_for`

```python
def course_progress_for(user: User, course: Course) -> CourseProgress | None:
    """This learner's live record for this course, or None.

    Resolves the registration first and reads the record from it: a learner
    holding both a cohort and an individual registration for one course has two
    records, and the registration order is what says which one the learner
    interface writes to. Every read path starting from a User goes through
    here; filtering CourseProgress by hand is a defect.
    """
    resolved = learner_for_course(user, course)
    if resolved is None:
        return None
```

## Phase 7 — Deadlines

### Task 20 — `Learner`-scoped deadlines

`freedom_ls/learner_management/deadline_utils.py`. This **reverses a shipped position**:
`learners-associated-with-organisations` deliberately kept deadlines keyed on `learner__user` so a
person holding two `Learner` rows saw one merged list. Progress is moving to the `Learner` grain and
deadlines follow it, so the two share one grain rather than sitting at odds.

The seven `learner__user=` filters — `:65`, `:81`, `:109`, `:136`, `:216`, `:228`, `:247` — resolve
against a single `Learner` obtained from `learner_for_course`:

- `get_effective_deadlines(user, course, content_item)` keeps its signature. At the top:
  `resolved = learner_for_course(user, course)`; return `[]` when it is `None`. Then `:65` and `:81`
  filter `learner=resolved.learner` (the `learner__is_active=True` conditions can go — a resolved
  `Learner` from the cohort branch is already active, and the individual branch deliberately tolerates
  an inactive one; keep the filter only where it does not contradict that).
- `_resolve_cohort_deadline(reg, user, …)` becomes `_resolve_cohort_deadline(reg, learner, …)`; its
  two override lookups (`:109`, `:136`) filter `learner=learner`. Its `source=` strings must keep
  rendering the **person**, so write `{learner.user}`, not `{learner}` — `Learner.__str__` is
  `"user - organisation"` and would change user-visible copy.
- `get_course_deadlines(user, course)` keeps its signature; `:216`, `:228` and `:247` take the same
  resolved `Learner`.
- `is_item_locked_by_deadline` is unchanged — it goes through `get_effective_deadlines`.

**There is nothing to grep for afterwards.** These seven filters are correct today and become wrong
only because the grain moves under them. The tests are the only detector, so write them first: a
person in two organisations, each with a different deadline for the same course, sees **each
organisation's deadlines separately, not a union**, and sees the right one when studying through each.
