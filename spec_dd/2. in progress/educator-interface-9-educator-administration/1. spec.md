# Spec: Educator administration

Spec 9 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Source: `idea.md`. Research beside it: `research_codebase.md`, `research_prior_art.md`,
`research_best_practices.md`, `research_reference_implementations.md`, `research_ux_patterns.md`,
`research_known_complaints.md`.

## Purpose

Giving someone an educator role takes a shell or a QA helper today. Spec 5 built the checked
entry points (`assign_role`, `remove_role`, `set_organisation_member_active` in
`freedom_ls/learner_management/role_assignment.py`) and the rules for who may grant what. No screen
calls them. This spec adds an Educators section to the educator interface. From it, an admin can
list, add, re-scope, remove, suspend and reactivate the people who hold a role in an organisation.
Every change that raises or removes access is confirmed first.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| educator | narrowed | A user holding an active `organisation_admin`, `cohort_admin` or `cohort_viewer` `ObjectRoleAssignment` on this organisation or one of its cohorts. Narrower than `cohort_educators` in `learner_management/queries.py`, which reads cohort grants only. |
| suspended | narrowed | An educator whose `OrganisationMember.is_active` is false. The word comes from the `set_organisation_member_active` docstring. Their assignments stay active but `can()` ignores them. |
| widening | coined | A change after which a person can do something they could not do before: a new role, a new cohort in a scope, or reactivation. No existing term covers this. |

## Scope

In:

- An Educators section, listed under each organisation's navigation. It lists educators, with
  search and a role filter.
- Add an educator by email, matching an existing user or creating an account through spec 7's
  path. The admin picks one role and, for cohort roles, the cohorts.
- Change the cohorts on a cohort role. Remove a role. Suspend and reactivate an `OrganisationMember`.
- Confirmations for widening and for loss of access.
- Rewritten role descriptions, used in the form, the confirmations and the product docs.
- An add action on the cohort overview's educators block.
- Cleanup of role assignments and guardian permissions when a cohort is deleted.

Out:

- New roles, custom roles, editing permissions one by one, and a read-only "roles and permissions"
  page. Descriptions appear inline, plus one help paragraph.
- Granting, removing or listing `site_admin`, and anything else site-level. A site admin appears
  only through an organisation or cohort role they hold in this organisation.
- Changing a role in place. Roles add up: to move someone from cohort viewer to cohort admin, add
  the new role and remove the old one.
- Notifying the person of a grant or removal. A new account still gets the setup email.
- Resending the setup email to an educator, a "pending" marker, last activity, and undo.
- Whatever the Django admin does with `SystemRoleAssignment` or `SiteRoleAssignment`.

## Decisions

1. **Only the checked entry points.** Views call `assign_role`, `remove_role` and
   `set_organisation_member_active`, never the raw `role_based_permissions/utils.py` functions. The
   grant check, the self check and the last-admin locks live there and must not be duplicated.
2. **The three educator roles are a fixed tuple.** `EDUCATOR_ROLES = ("organisation_admin",
   "cohort_admin", "cohort_viewer")`. A downstream role in `get_role_config` is never listed or
   offered, because it has no `assign_` capability.
3. **One function decides what a grantor may hand out.** It is the source for both the form's
   choices and the POST validation, so the two cannot drift. The POST still goes through
   `assign_role`, which checks again.
4. **The list is built from assignments, not member rows.** Spec 5 shipped no backfill of
   `OrganisationMember`, so a member-based list would leave people out.
5. **A match shows the account's name and email before confirming.** An organisation groups
   people inside a site; it does not isolate them (`docs/product/multi-tenancy-and-isolation.md`).
   Showing the match is what makes a typo visible.
6. **Cohort deletion deletes the cohort's role rows.** It does not deactivate them. With the
   target gone, an inactive row points nowhere and breaks `sync_role_permissions`. Spec 11's audit
   log is where the history lives.
7. **Reactivating an assignment resets `assigned_at`.** "Added on" then means the latest grant,
   not the first one.

## Requirements

### R1. Role descriptions (`freedom_ls/role_based_permissions/roles.py`)

Replace `description` on the four `BASE_ROLES` entries. These strings are the single source. The
form, the confirmations, the help paragraph and the product docs all read `Role.description` or
copy it word for word.

| Role | `description` |
| --- | --- |
| `site_admin` | Full access to every organisation on this site. |
| `organisation_admin` | Manages learners, cohorts and educators in this organisation. |
| `cohort_admin` | Manages the learners and course registrations in their cohorts. |
| `cohort_viewer` | Sees the learners and progress in their cohorts, and changes nothing. |

`display_name` values stay as they are.

### R2. Grant rules (`freedom_ls/learner_management/role_assignment.py`)

- Add `EDUCATOR_ROLES` (Decision 2).
- Add `grantable_roles(grantor: User, organisation: Organisation) -> list[GrantableRole]`, with
  `GrantableRole` a frozen dataclass of `role: str` and `cohorts: list[Cohort] | None`.
  `organisation_admin` is included when `can(grantor, ASSIGN.format(role=...), organisation)`.
  A cohort role is included with the organisation's active cohorts on which that check passes,
  and left out when there are none. `cohorts` is `None` for `organisation_admin`.
- Add `is_widening(before: set[tuple[str, str]], after: set[tuple[str, str]]) -> bool`. Each pair
  is a role and a target key: the organisation's pk or a cohort's pk. It returns true when `after`
  holds any pair `before` lacks. It is a pure function, unit tested on its own.

### R3. Reactivation timestamp (`freedom_ls/role_based_permissions/utils.py`)

When `assign_object_role` reactivates an inactive row, it sets `assigned_at` to now along with
`is_active` and `assigned_by`. Do the same in `assign_site_role`. Keep the six `# TODO: AuditLog`
comments.

### R4. The Educators section (`freedom_ls/educator_interface/views.py`)

- `EducatorConfig(OrganisationSectionConfig, ListViewConfig)`. Its view capability is
  `freedom_ls_learner_management.view_organisationmember` on the organisation, so cohort admins and
  cohort viewers never see it. Register it in `interface_config` under a new
  `NavGroup("Administration", [EducatorConfig])`. It must pass
  `invariants/test_config_authorisation.py` and `invariants/test_permission_matrix.py` with no new
  capability strings.
- `EducatorDataTable(DataTable)`. It is a `User` queryset with one row per person who holds an
  active assignment in `EDUCATOR_ROLES`, either on this organisation or on one of its cohorts
  (active or not). The holder's `User.is_active` must be true. The row prefetches those
  assignments with their targets and `assigned_by`, plus the person's `OrganisationMember` and
  `Learner` for this organisation. The list must not issue a query per row.
- Columns:
  - Name, with email as the secondary line. A person with no name shows their email.
  - Markers beside the name: "You" for the viewer, "Suspended" when the `OrganisationMember` is
    inactive, and "Also a learner" when an active `Learner` exists in this organisation. The
    learner marker is neutral in tone, not a warning.
  - Roles. One entry per role held, made of the role's `display_name` and its scope. The scope
    reads "Whole organisation" for `organisation_admin`. For a cohort role it lists cohort names,
    with the first two shown and then "+N more", and the full list available in the cell.
  - Added by and added on, per role entry, taken from the newest active assignment for that role.
    A null `assigned_by` reads "Not recorded".
- `search_fields` covers first name, last name and email. `EducatorRoleFilter` in
  `educator_interface/filters.py`, modelled on `LearnerStatusFilter`, offers "All roles" (the
  default) plus the three roles. Sorted by name.
- One help paragraph above the table explains roles in plain words. The role descriptions appear in
  the add form, not in the table.
- Empty states follow the voice in `brand-guidelines`: one for no matches (with a clear-filters
  link) and one for an organisation whose only educator is the viewer.

### R5. Row actions (`freedom_ls/educator_interface/actions.py`, cell templates in `templates/educator_interface/data-table-cells/`)

Per role entry:

- **Change cohorts**, for cohort roles. The admin ticks cohorts from `grantable_roles` for that
  role, and only those cohorts are accepted. Cohorts the viewer cannot grant on, or inactive
  cohorts the person already holds, are shown read-only and left alone. If the change adds cohorts,
  the confirmation names them as a widening. If it removes cohorts, the confirmation names what is
  lost. A change that does both names both. When the change removes every cohort, the confirmation
  uses the remove wording and the role is removed. All calls run in one `transaction.atomic()`.
- **Remove**. The confirmation names the person, the role, the scope and what they lose, plus what
  is kept: their account, their other roles and any `Learner`. When a site-level admin removes an
  organisation's last `organisation_admin`, the confirmation adds that the organisation will have
  no organisation admin.

Per row:

- **Suspend** and **Reactivate**, with capability `change_organisationmember`, through
  `set_organisation_member_active`. Suspend confirms like a removal: "keeps their roles, can do
  nothing in this organisation until reactivated". Reactivate confirms as a widening and lists the
  roles that take effect again.

The viewer's own row shows no actions. In their place is a lock icon and "You can't change your
own roles. Ask another organisation admin." Actions the viewer lacks the capability for are hidden.

Each successful action fires `EDUCATOR_CHANGED` (`educator_interface/events.py`).

### R6. Add an educator (`freedom_ls/educator_interface/actions.py`, `forms.py`)

`AddEducatorAction(PanelAction)` is a top-level action on `EducatorConfig`. It is offered when
`grantable_roles` is non-empty. It uses a plain `forms.Form`, following `AddLearnersAction`, with
invalid input returning 422. The steps:

1. **Email.** After an htmx lookup it shows either "Existing account: <name>, <email>" or "No
   account yet. One will be created and a setup email sent." For a new address it adds optional
   first-name and last-name fields. Matching is `match_or_create_user`'s case-insensitive,
   whitespace-stripped lookup, and the lookup step creates nothing.
2. **Role.** Radio cards, one per `grantable_roles` entry, each showing `display_name` with
   `description` under it. Nothing is preselected. When the organisation has no active cohorts,
   the cohort roles are absent and a line says "This organisation has no active cohorts yet."
3. **Cohorts**, for cohort roles. Checkboxes over that entry's `cohorts`, with a search box and a
   selected count. At least one cohort is required.
4. **Confirmation**, inside the same dialog. It restates the role description and the scope, and
   says whether an account will be created. If the person already holds roles here, it shows their
   current roles next to what they will have after. Cohorts they already hold for that role are
   named and skipped. If nothing new remains, the form answers 422: "<name> already holds this
   role on these cohorts." If the person is suspended, it says the role takes effect only once
   they are reactivated.

On submit, inside one `transaction.atomic()`: `match_or_create_user(site, email, first, last)`,
then `assign_role` once per target. When the account was created, call
`send_account_setup_email(user, organisation.name)`, which sends on commit. A refusal rolls back
the account too.

Error copy, each answered at 422 inside the dialog:

| Cause | Message |
| --- | --- |
| `EmailInUseOnAnotherSite` | This address belongs to an account on another site. Use a different address. |
| `RefusalReason.INACTIVE_USER` | This person's account is turned off, so they can't be given a role. |
| `RefusalReason.SELF` | You can't change your own roles. Ask another organisation admin. |
| `RefusalReason.LAST_ORGANISATION_ADMIN` | <name> is this organisation's only organisation admin. Add another organisation admin first. |

`RefusalReason.NOT_PERMITTED` gets spec 5's 403 denied response (`denied_response`), whichever
action raised it. The same mapping serves R5's actions and R7.

### R7. Cohort overview educators block (`CohortEducatorsPanel` in `views.py`)

`get_actions()` returns an `AddEducatorToCohortAction`. It is `AddEducatorAction` with the cohort
preset as a hidden input, which follows `AddLearnersToCohortAction`. The role choices are limited
to the cohort roles that `grantable_roles` allows on that cohort. The action is offered only when
there is at least one. The block refreshes on `EDUCATOR_CHANGED`, as it does today.

### R8. Stale submissions

Every action re-reads the target assignment or member row when it is submitted. If the assignment
it acts on is no longer active, or the cohort has left scope, it answers with spec 5's
`action_unavailable` fragment rather than silently changing nothing.

### R9. Cohort deletion cleanup (`freedom_ls/learner_management/signals.py`)

A `pre_delete` receiver on `Cohort` runs inside the deleting transaction. It deletes every
`ObjectRoleAssignment` whose target is that cohort, active or not. It also deletes the matching
guardian `UserObjectPermission` rows. Because it is a receiver, deletes from the Django admin are
covered too.

A data migration in `learner_management` deletes `ObjectRoleAssignment` rows whose cohort target
no longer exists, and the guardian rows that match them.

## Testing

- `grantable_roles`, for each grantor: site admin, organisation admin, cohort admin, cohort viewer,
  and a user with no role. Inactive cohorts are excluded, and a downstream role is never offered.
- `is_widening`: the add, remove, mixed and unchanged cases.
- Reactivation resets `assigned_at` in `assign_object_role` and `assign_site_role`.
- The list:
  - It shows exactly this organisation's educators: organisation grants and cohort grants, but not
    site-only admins, other organisations' educators, inactive users or removed assignments.
  - The "You", "Suspended" and "Also a learner" markers.
  - Search, the role filter and its default.
  - A fixed query count as rows grow.
- Add:
  - An existing user matched with different case and surrounding spaces.
  - A new address creating one account and sending one setup email.
  - An address on another site.
  - A duplicate role on the same cohorts.
  - Partial overlap of cohorts.
  - A refusal rolling back the new account.
  - A hand-made POST with a role or cohort the grantor may not grant answering 403, with nothing
    written.
  - The cohort roles absent when there are no active cohorts.
- Change cohorts: adding, removing, both together, and removing all, which removes the role.
  Cohorts outside the grantor's reach stay untouched.
- Remove: confirmation copy names what is lost. An organisation admin cannot remove the last
  organisation admin, but a site admin can and is warned.
- Suspend and reactivate: access through `can()` stops and returns. Suspending the last
  organisation admin is refused for an organisation admin.
- Self: the own row has no actions, and a hand-made POST against yourself is refused.
- Stale submissions return `action_unavailable`.
- Mid-session removal: a person whose role is removed gets spec 5's denied response on their next
  full-page request and on their next htmx request.
- Cohort page: the add action presets the cohort and is hidden from anyone without a grantable
  cohort role.
- Cohort deletion: assignment and guardian rows for the cohort are gone, and other cohorts' rows
  are untouched. The data migration removes existing orphans.
- `EDUCATOR_CHANGED` fires on every successful action.
- Playwright: add an existing user as cohort admin on two cohorts, change the cohorts, remove the
  role. Run it at the QA viewports, including the mobile card layout.

## Success criteria

- An organisation admin can add an existing user and a brand-new address as a cohort admin on
  chosen cohorts, without a shell. The new address receives the setup email.
- No hand-made POST lets anyone grant a role or cohort outside `grantable_roles`, change their own
  roles, or leave an organisation with no organisation admin unless a site-level admin did it.
- Every removal, suspension and widening shows a confirmation that names the change before
  anything is written.
- A person whose role is removed gets the denied response on their next request.
- Deleting a cohort leaves no `ObjectRoleAssignment` or guardian row pointing at it.
- `roles.py`, the add form and `docs/product/educator-interface.md` show the same four descriptions.
- The educators list issues the same number of queries for 5 rows as for 50.
