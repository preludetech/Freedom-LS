# Research: the harsh focus outline on the course-player side panel

## 1. Root cause, stated precisely

The heavy border is the browser's default **`:focus-visible` outline painted directly on the `<dialog>` element itself**, not on any descendant, and not an author style. Trace:

- `alpine-components.js:551-552` (`_setDesktopOpen`): on desktop the `sidePanel` Alpine component calls `this.dialog.show()` unconditionally whenever the panel should be open — and for the course player it is **locked open** (`_desktopLock = true`, set from `data-desktop-lock="true"` on the `_base_interface.html:22` wrapper, consumed at `alpine-components.js:420,512-513`). This runs on every `init()`, i.e. on first paint of the player.
- Per the HTML Standard, both `dialog.show()` and `dialog.showModal()` run the **"dialog focusing steps"**: if the dialog subtree has no `autofocus` attribute anywhere, and the dialog has no other focus delegate, **the dialog element itself becomes the focused element** — not the first focusable descendant. This was a deliberate spec change (whatwg/html PR #4184, "Focus the dialog element instead of the first focusable item") made specifically because forcing focus onto the *first* focusable control inside a dialog was judged bad UX/AX (unpredictable for screen-reader users, can trigger unintended content announcements). Neither the `<dialog>` in `_base_interface.html:45-48` nor anything inside `{% block sidebar_content %}` (the TOC header, the TOC links) carries `autofocus`, so **the dialog itself is `document.activeElement`** after `show()`.
- Confirmed by grep: no rule anywhere in `tailwind.base_interface.css`, `tailwind.components.css`, `first_class/theme.css` or `default/theme.css` targets `.side-panel-dialog:focus`, `dialog:focus`, or resets outline on the dialog. The `--color-focus-ring` token declared at `submodules/Freedom-LS/freedom_ls/themes/default/static/themes/default/theme.css:134` (`--color-focus-ring: var(--color-primary)`) is **never consumed** by any selector in the two stylesheets that would apply to this dialog — it is wired only as the Tailwind `--color-focus-ring` alias slot but nothing in the codebase writes `ring-focus` / `outline-focus` utilities that would use it on the dialog. So there is no author override at all; what renders is purely the **User-Agent default `:focus-visible` outline** (Chrome's default is `outline: auto 1px -webkit-focus-ring-color` /  effectively a ~2px black/blue ring, since 2021-2022 all major engines paint UA focus rings via `:focus-visible` rather than `:focus` — see `chromestatus.com/feature/5658873031557120` "Use :focus-visible in the default UA style sheet"). Because the `<dialog>` occupies the entire left column (`.side-panel-dialog` is sized to the full grid column per `tailwind.base_interface.css:100-105`), that UA ring outlines the *entire panel*, reading as the "heavy ugly border" reported.
- **This is `:focus-visible`, not merely `:focus`.** This matters because it rules out the lazy fix of `outline: none` "because it's not real keyboard focus" — it *is* the browser treating this as visible-focus-worthy on purpose. w3c/csswg-drafts#7214 ("`:focus-visible` should match when focus is programmatically moved into a dialog") establishes that browsers intentionally paint the ring when focus moves *programmatically* into a dialog (unlike most other programmatic `.focus()` calls after a mouse interaction, which usually suppress `:focus-visible`). Current Chrome (and Safformerly gnly Safari per that thread's original report, but Chrome later aligned) shows the ring for dialog-focusing-steps focus specifically because a dialog opening is treated as a context switch the user needs to notice.
- HTMX out-of-band swap of `#course-toc-region` (`_course_base.html:72`, Previous/Next navigation) is **not** implicated: that swap only replaces the content living inside the already-open, already-focused dialog; it does not call `show()`/`showModal()` again and does not move focus. Ruled out.
- Not an author `focus:ring-*` rule either: `.btn` (`tailwind.components.css:165`) and the course-card `focus-within:ring-2` (`tailwind.components.css:303`) are scoped to those specific classes and don't match `.side-panel-dialog`. Ruled out.

## 2. Should the panel be focused at all on load?

For the docked desktop rendering, no — arguably it should never receive focus at all. `dialog.show()` (non-modal) exists to get the dialog's top-layer/`::backdrop`-free rendering and open/close semantics, but the desktop case doesn't want or need any focus-moving behaviour: it is a permanently-open, non-dismissible in-flow column (no close control — `_base_interface.html:50-58`, `_desktopLock` blocks `toggle()` from doing anything on desktop, `alpine-components.js:582`). A column that is always there and never modal has no "entry moment" that justifies stealing focus from wherever the page already put it (e.g. skip-link target, first heading, or whatever the browser defaults to on load).

The mobile case is different and `showModal()` earns its keep there: focus trap, `inert` background, native Escape-to-close, and top-layer stacking are all real requirements for a dismissible overlay sheet, and the code comments (`alpine-components.js:391-399`) show this was a deliberate, reasoned choice, not an oversight. So: `showModal()` for mobile is right; `show()` for the desktop-locked column is questionable specifically *because* of its focus-stealing side effect, not because of its other behaviours (which are otherwise harmless/desired — sticky positioning, participating in the grid, etc.). Swapping the desktop rendering to a plain `<aside>` would sidestep the dialog-focusing-steps entirely, but this is a structural JS/template change deep in FLS's shared `sidePanel` Alpine component, used by every interface (learner, educator, panel_framework) — not something a downstream project can safely re-architect.

## 3. Options for a subtle-but-accessible indicator

Classify every option as **HIDE** (removes the indicator — never acceptable per WCAG 2.4.7), **MOVE** (relocates which element the indicator lands on), or **RESTYLE** (keeps an indicator on the same element, just quieter/branded).

| Option | Class | Notes |
|---|---|---|
| `outline: none` / `focus:outline-none` on `.side-panel-dialog` with nothing to replace it | **HIDE — reject** | Removes the only focus indicator with nothing compensating. Violates SC 2.4.7 outright. |
| `autofocus` on the first TOC link (or the TOC header) inside `{% block sidebar_content %}` | **MOVE** | Redirects the dialog-focusing-steps target from the dialog box to a small, real, interactive descendant. The ring then outlines one link, not the whole panel — inherently "subtle" because it's sized to content, not the column. Downside: on *every* open (including the locked desktop case on every page load) a screen-reader user's focus jumps into the TOC before they've read the page — same "poor UX/AX" concern PR #4184 was written to avoid, just relocated. Best paired with re-evaluating whether the panel should focus at all (§2), or scoped to only fire on the mobile `showModal()` open where an entry point is actually wanted (e.g. `autofocus` element only meaningful when the sheet opens as an overlay — but `autofocus` is a static template attribute, it fires identically for `show()` and `showModal()`; scoping it to "mobile only" would need a JS-driven `.focus()` call instead of the attribute). |
| Scope the ring with `[open]:focus-visible` (i.e. `.side-panel-dialog:focus-visible { outline: ... }` restated, or gated to close it off from the initial silent state) | Does not apply | `[open]` doesn't prevent the *initial* focus-visible paint — the dialog is `[open]` and focused at the same instant. This selector doesn't change *when* the ring shows, only lets you target dialog-focus specifically (useful for RESTYLE, not for suppressing the load-time occurrence). Listed because the brief asked for it: it's a targeting mechanism, not a fix by itself. |
| `tabindex="-1"` on the dialog | **Partial MOVE/HIDE risk** | Does *not* stop `dialog.show()` from focusing the dialog (the dialog-focusing-steps operate independently of tabindex — `tabindex` only affects sequential/Tab-key focusability, not programmatic `.focus()` targeting, and `<dialog>` is programmatically focusable regardless). This would not fix anything on its own; only relevant in combination with moving focus elsewhere first. |
| **RESTYLE**: override `.side-panel-dialog:focus-visible` (or `:focus`, since testing should confirm which pseudo-class Chrome actually matches here) with the project's own `--color-focus-ring` / `ring-primary` token — e.g. a slim `box-shadow: 0 0 0 2px var(--color-focus-ring)` inset, or `outline: 2px solid var(--color-focus-ring); outline-offset: -2px` — instead of the UA default | **RESTYLE — recommended** | Keeps a real, visible, on-brand indicator (satisfying 2.4.7/2.4.13) but stops it from reading as a jarring, oversized black/blue box around the whole column. This is the only option in this list that is both fully downstream-reachable (pure CSS) and fully accessible-safe by construction. |

## 4. The accessibility floor (WCAG 2.2)

Any fix must still satisfy, at minimum:

- **[SC 2.4.7 Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)** (Level AA): any keyboard-operable UI must have a mode of operation where the keyboard focus indicator is visible. Rules out any HIDE option with no replacement.
- **[SC 2.4.11 Focus Not Obscured (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)** (Level AA, new in 2.2): when an element receives focus, it must not be *entirely* hidden by author-created content (sticky headers, overlays, etc.). Not directly at risk here since the panel is not overlapped by anything, but relevant if a MOVE option relocates focus to a TOC link that could later sit under the sticky `course_toc_header.html` "sticky top-0" block (`course_toc_header.html:8`) — check the moved-to element isn't obscured by that sticky header.
- **[SC 2.4.13 Focus Appearance](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)** (Level AAA, but good practice regardless): where a focus indicator is present, it must have (a) an area at least as large as a 2 CSS px perimeter around the unfocused element, and (b) a contrast ratio of at least 3:1 between focused and unfocused states for the same pixels. A RESTYLE fix's ring must be measured against this: e.g. a 2px solid `--color-focus-ring` outline with adequate offset clears both the area and contrast bars; do not shrink it below ~2px or drop contrast to satisfy "subtle" — subtle should mean "smaller footprint / on-brand colour," not "thinner than spec."

**Minimum bar for this fix:** whatever ends up focused (dialog or a moved-to descendant) must show a visible, ≥3:1-contrast, ≥2px-equivalent-area indicator. "Subtle" must be achieved by scoping *what gets outlined* (a link, not the whole column) and/or *how it's drawn* (a themed ring instead of the UA default), never by removing it.

## 5. Recommended fix

**Restyle, don't hide, and restyle in the project's own CSS, not upstream JS.** Add a downstream CSS override targeting `.side-panel-dialog:focus-visible` (confirm empirically via devtools whether Chrome matches `:focus-visible` or plain `:focus` for the dialog-focusing-steps target before committing the selector — the csswg-drafts #7214 discussion shows this has been genuinely inconsistent across engines/versions) that replaces the UA outline with a slim, inset, on-brand ring using the existing `--color-focus-ring` token (which already resolves to `--color-primary` and is presently unused dead weight — this fix would be its first real consumer), sized and contrasted to clear SC 2.4.13's 2px-area / 3:1-contrast bars. This is a pure CSS change, ships today, requires no changes to FLS's shared Alpine component (so it doesn't regress educator/panel_framework panels that reuse the same controller), and doesn't touch focus semantics at all — a screen-reader user still lands on the dialog exactly as the spec intends, they just see a calmer ring. Separately, flag upstream (see §6) that a permanently-docked, non-dismissible desktop panel probably shouldn't run the dialog-focusing-steps at all — that's a real architectural question but is not blocking and not this project's to decide unilaterally.

## 6. Where the fix lives

Every file inspected above — `_base_interface.html`, `alpine-components.js`, `tailwind.base_interface.css`, `tailwind.components.css`, both `theme.css` files, `_course_base.html` — is under `submodules/Freedom-LS`, which per this project's `CLAUDE.md` must never be edited.

- **The recommended CSS restyle (§5) is fully downstream-reachable.** It's a pure `@layer components`/plain CSS addition. This project's own `tailwind.input.css` (project root, NOT in the submodule) already imports FLS's stylesheets in cascade order (`tailwind.components.css` → `tailwind.base_interface.css` → the active theme's `theme.css`) and already has a project-level `@theme { }` block at the bottom (`tailwind.input.css:54-56`) for exactly this kind of override. Add the `.side-panel-dialog:focus-visible` rule there (or in a new `@layer components` block appended after the existing imports), so it wins the cascade over the UA default without touching anything under `submodules/`. Note: `themes/custom/static/themes/custom/theme.css` exists in this project but is currently **not imported** by `tailwind.input.css` (which instead imports `submodules/Freedom-LS/freedom_ls/themes/first_class/...theme.css` — itself inside the submodule, so also off-limits for edits) — so `tailwind.input.css` itself, or a new project-owned CSS file imported from it, is the correct target, not the unused `themes/custom` file.
- **The JS-behaviour options (§2/§3 — `autofocus` on a TOC link, switching desktop to a plain `<aside>`, any change to `_setDesktopOpen`/`init()`) are NOT downstream-reachable.** They require editing `alpine-components.js` and/or `_base_interface.html`, `_course_base.html` — all inside the read-only submodule, shared by every FLS-based project. `autofocus` in particular could technically be added via a shadowed template override (this project's `templates/` directory can override FLS templates by path, same mechanism already used for `templates/learner_interface/partials/anonymous_hero.html`), so adding `autofocus` to a shadowed copy of `course_toc_header.html` or `_course_base.html`'s `sidebar_content` block *is* technically downstream-reachable without touching the submodule — but changing the underlying `sidePanel` Alpine controller's `show()`/`showModal()` split is not; that's an FLS upstream change. **Recommendation: do the CSS restyle downstream now; file the "should a locked-open desktop dialog run dialog-focusing-steps at all" architectural question upstream to FLS rather than attempting a template-shadow workaround for it.**
