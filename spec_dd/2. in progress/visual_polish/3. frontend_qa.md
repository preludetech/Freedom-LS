# Frontend QA: three visual defects in shared FLS chrome

Every change here is presentational and lands in shared chrome — the `.btn` size contract, the
`<c-button>` cotton component, `.course-card-body`, and the side-panel `<dialog>`. There are only two
committed tests (source-CSS contract assertions); the pixels are proved here.

Because the change is in shared chrome, the risk is not the three defects — it is the buttons and
cards that were **already fine** and must stay that way. Roughly half the tests below are regression
checks on untouched surfaces.

Use the `fls-dev:use-playwright` skill conventions. Where test data is missing, delegate its creation
to the `fls-dev:qa-data-helper` agent — do not create it by hand. Use the **DemoDev** site.

### Build the CSS, then serve

**Nothing below is visible until Tailwind is rebuilt.** `static/vendor/tailwind.output.css` and
`tailwind.active_theme.css` are gitignored and regenerated by the build.

```bash
npm run tailwind_build                          # default theme
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL: `http://127.0.0.1:$PORT`

To switch themes mid-run, stop the server, rebuild, restart:

```bash

```

Hard-reload the browser after every rebuild — the stylesheet is cached aggressively.

## §1 The headline defect — small buttons in the course player

**Theme: `first_class`.** This is where the defect was found and where the size contract is under
most stress, because that theme reopens `.btn` at `px-6 py-3`.

1. Log in as `demodev_s1@email.com`.
2. Open a course topic, e.g. `/courses/functionality-demo-show-end-with-topic/2/`.
3. Look at the player nav strip at the bottom of the content column (Previous on the left, Next /
   Finish Course on the right).

**Expected**

- The **Next** arrow no longer reads as jammed against the button's right edge. There is visible
  breathing room between the arrow's right edge and the button's border.
- The gap between label and arrow is tight but deliberate (6px), noticeably smaller than on a
  full-size button.
- The arrow is visibly smaller than an icon on a full-size button (16px vs 20px).
- Previous and Next read as a matched pair. They are not required to be pixel-identical in width —
  `first_class`'s `.btn-secondary { border-2 }` contributes 2px of asymmetry and is explicitly out of
  scope.
- Both buttons are taller than before (8px vertical padding, up from 6px).

Screenshot the nav strip and put it beside `buttons.png`.

**The open question to settle here.** The spec ships `first_class`'s `.btn-sm` at `px-3 py-2`, the
same as the base rule, even though that theme's full-size `.btn` is the chunkier `px-6 py-3`. Judge
from this screenshot whether the small button looks proportionate to the theme's own buttons or
whether it wants more padding. Record the answer in the QA report either way — it is a decision, not
a bug.

**If the arrow still reads as crowded**, say so explicitly. That is the trigger for a scoped
asymmetric-padding follow-up, not a reason to fail this change.

## §2 Prove the theme override actually wins

This is the test that catches the change's own worst failure mode. `.btn-sm` went from a compound
selector to a single class, which means it now sits at *equal* specificity to a theme's `.btn` and
wins only on source order.

1. Still on `first_class`, with the player nav on screen, open DevTools and inspect the **Next**
   button.
2. Read its computed `padding`.

**Expected:** `8px 12px` (`py-2 px-3`).

**Fail:** `12px 24px` (`py-3 px-6`) — the theme's full-size padding. That means the theme's `.btn-sm`
is missing, not being compiled, or losing the cascade. Check the Styles pane: the theme's `.btn-sm`
rule must appear below the base `.btn-sm` and below the theme's `.btn`.

3. Rebuild for the default theme (`npm run tailwind_build`), restart, hard-reload, and inspect the
   same button.

**Expected:** also `8px 12px`, from the base `.btn-sm` alone.

## §3 Every other small button

`px-3 py-2` reaches all of them. On the **borderless** variants (`link`, `ghost`) there is no box to
grow, so the extra padding must read as *offset* — the label sits further from its neighbours — not
as a bigger button.

Check each, at both themes if time allows, otherwise at `first_class`:

| Where | URL | Variant | What to look for |
|---|---|---|---|
| Details link on a dashboard card | `/` (as `demodev_s1@email.com`) | `link` | Right-aligned; the chevron is 16px and clear of the card's right padding edge. The link must not overflow the card. |
| "Browse all courses" | `/` | `link` | Sits on the same line as the "Available courses" heading, right-aligned, `whitespace-nowrap` still holding. Does not push the heading or wrap. |
| "Remove interest" | course detail for a coming-soon course, e.g. `/courses/qa-toc-in-development/`, after clicking **I'm interested** | `ghost` | Sits beside the green "Interested" label with the row still vertically centred. No icon, so the `gap` has nothing to act on — spacing must be unchanged apart from the padding. |
| "Open image" | a topic with an image, e.g. `/courses/functionality-demo-content-widgets/2/` (the media page) | `secondary` | Bordered, so the box genuinely grows. It must not push the image caption out of line or wrap. `shrink-0` still holds at narrow widths. |

**Adversarial:** narrow the viewport to ~375px on the dashboard and the course detail page. The extra
horizontal padding is the most likely cause of a new wrap or overflow. Nothing may clip or spill out
of its container.

## §4 Icon-only and dual-icon buttons

The whole point of moving to `gap` is that it fixes two cases the margins got wrong: an icon with no
label used to reserve a margin anyway, and a button with both a leading *and* a trailing icon only
got one of them spaced.

**No button in the shipped app is icon-only or dual-icon today**, so this needs a temporary probe.

1. Temporarily edit `freedom_ls/learner_interface/templates/learner_interface/course_topic.html`,
   line 40, adding `icon_left="previous"` to the existing `icon_right="next"` Next button, and add a
   second temporary `<c-button icon_left="check" size="small" />` with an empty slot beside it.
2. Reload the topic page (no rebuild needed — templates are not compiled into the CSS).

**Expected**

- The dual-icon button spaces **both** icons from the label by the same 6px.
- The icon-only button is optically symmetric: 12px of padding on each side of the icon, no phantom
  margin pulling the icon off-centre.
- Repeat both at default size (drop `size="small"`) and confirm 8px gaps and 20px icons.

3. **Revert the template edit.** Confirm with `git diff` that `course_topic.html` is clean before
   moving on.

## §5 Loading state

The `.htmx-hide-on-request` span became `inline-flex` with `gap: inherit`, so it now takes the
button's own gap. It was previously an unstyled inline span.

1. Log in as `demodev@email.com` and go to the educator interface at `/educator/`.
2. Open any cohort or organisation panel that offers an edit or delete modal
   (`panel_framework` modal forms and delete confirmations are the loading-button consumers).
3. Look at the **Save** / **Delete** button in the modal footer at rest.

**Expected at rest:** the label sits exactly where it did before. Making the wrapper span
`inline-flex` must not shift, re-centre, or re-wrap the label.

4. Submit and watch the button during the request.

**Expected during request:** the spinner and its text swap in, spinner on the left, correctly spaced,
vertically centred. The button must not jump in width or height as it swaps.

5. **Adversarial — long label.** Temporarily set a modal button's label to something long (or narrow
   the viewport hard) and confirm the label still wraps or truncates as it did before. `inline-flex`
   changes how the anonymous text run is laid out inside the span; a label that used to wrap and now
   overflows is a regression.

6. **Criterion 5 — a loading button carrying `icon_left`.** No such button ships today. Temporarily
   add `icon_left="check"` to the `<c-button ... loading="true">` at
   `freedom_ls/panel_framework/templates/panel_framework/partials/delete_confirmation.html:35`,
   reload the delete modal, and confirm the icon is spaced from the label at rest by 8px. Then set
   `size="small"` on the same button and confirm 6px and a 16px icon. **Revert both edits** and
   confirm with `git diff`.

## §7 Default-size buttons did not move

`gap-2` is 8px, exactly the `mr-2`/`ml-2` it replaces, so **no default-size button may change
spacing**. This is the largest blast radius in the change (163 `<c-button>` usages).

Walk these and compare against pre-change screenshots:

1. **Buttons with a leading icon** — anywhere `icon_left` is used at default size. Icon-to-label gap
   must be identical.
2. **Buttons with no icon at all** — the overwhelming majority. Login form submit, "I'm interested"
   on a course detail page, modal Cancel/Close. A single-child flex container gets nothing from
   `gap`, so these must be pixel-identical.
3. **`<c-button class="w-full">`** — the "I'm interested" CTA. `justify-center` plus `gap` must still
   centre the label in a full-width button.
4. **`<c-button-group>`** — the modal footer row. That component does its own `gap`; the button
   change must not double up the spacing between buttons.

## §8 Card grids — Details links share a baseline

1. Log in as `demodev_s1@email.com` and open the dashboard at `/`.
2. Find a grid whose card titles differ in length — one card with a one-line title beside one with a
   two-line title.

**Expected:** every **Details** link in the row sits on a common baseline. The row of links reads as
straight, not ragged. Compare against `dashboard cards.png`.

3. **Verify the chain, not just the picture.** A homogeneous grid can look right with a broken chain.
   In DevTools, walk from the grid down to the Details wrapper and confirm each link:
   - the grid container stretches its rows (default `align-items: stretch`; no `align-items: start`),
   - the card `<article>` is `display: flex; flex-direction: column`,
   - `.course-card-body` still has `flex: 1`,
   - `.course-card-body` computes `display: flex; flex-direction: column`,
   - the Details wrapper is a **direct child** of `.course-card-body` and computes
     `margin-top: auto`.

   If `margin-top` computes as `0px`, the `space-y-2` utility has beaten the pin — check that
   Tailwind still emits `space-y-*` inside a zero-specificity `:where()` wrapper.

4. **Cards with a progress footer.** On an in-progress card, Details and the progress bar are pushed
   to the bottom **as a group**, with Details directly above the bar. Details still aligns across
   cards that agree on whether they have a footer.

5. **Adversarial — a mixed grid.** The dashboard renders each status in its own grid today, so every
   grid is homogeneous. If you can produce a grid mixing a card that has a progress footer with one
   that does not, the Details links will **not** align. That is documented and acceptable — record it
   rather than filing it.

6. **Adversarial — one card in a row, and a single-column layout.** Narrow to ~375px so cards stack.
   With no free space to consume, `mt-auto` is a no-op. Confirm nothing collapses, and that the gap
   between "Next up:" and Details has not grown.

7. **Adversarial — the shortest possible card.** A not-registered card with no "Next up" line and no
   footer is the shortest content in the grid, so it absorbs the most free space. Confirm its Details
   link is pushed to the card's bottom padding edge and does not sit outside the padding.

## §10 The side-panel focus indicator

The docked desktop panel is opened with `dialog.show()`, which runs the dialog focusing steps. With
no `autofocus` in the subtree the `<dialog>` itself takes focus, so this indicator paints **on every
page load**. That is correct and intentional — it is a real `:focus-visible` indicator, and removing
it would fail WCAG 2.2 SC 2.4.7.

### 10a — Desktop, course player

1. At ≥1024px wide, load a course topic page fresh (hard reload, not an in-page navigation).

**Expected:** a flat 2px on-brand line traced just inside the side panel column's edge — the
`--color-focus-ring` colour, which resolves to the theme's primary. It sits *over* the side-panel
surface, flush to the edge (`outline-offset: -2px`), with no rounded halo and no blur.

**Fail:** the browser's default focus halo (usually a thick blue/black double ring, often with a
visible offset gap outside the element). That means the rule is not compiling or not matching.

**Fail:** no indicator at all. Do not report a missing ring as "fixed".

### 10b — Desktop, educator interface

2. Log in as `demodev@email.com`, load `/educator/` fresh, and confirm the same line on that shell's
   side panel. Same shared `_base_interface.html`, so it must match.

### 10c — Mobile overlay

3. Narrow below `lg` (~375px). The panel becomes a modal overlay opened with `showModal()`.
4. Open it with the header toggle.

**Expected:** the same 2px line. Check specifically how it reads against the bottom-sheet variant's
**rounded top corners** — `outline` follows the border box, so a square outline against a rounded
sheet can look wrong. Record how it looks; a mismatch here is a real finding.
5. Check the side-drawer variant too if the interface offers it.

### 10d — Adversarial: the ring must not be sticky or spurious

6. After the page loads with the ring showing, click somewhere in the main content. The ring must
   clear — focus moved off the dialog.
7. Press `Tab` repeatedly from the top of the page. The side panel column must **not** become a tab
   stop of its own. If it does, something added a `tabindex` — it should not have.
8. On desktop, toggle the panel closed and open again. The ring reappearing on reopen is expected
   (the panel is refocused); note it, do not fail it.
9. Confirm focus was **not** thrown into the panel's contents — a screen reader should still start at
   the top of the page, not inside the outline. Check that no element inside the panel has
   `autofocus`.

### 10e — Contrast

10. For **each** shipped theme (`default` and `first_class`), read the computed values of
    `--color-focus-ring` and `--color-sidepanel` off `:root` in DevTools and run them through a
    contrast checker.

**Expected:** at least **3:1** (WCAG 2.2 SC 1.4.11 Non-text Contrast, Level AA). Note that
`first_class` sets `--color-sidepanel: #FFFFFF` explicitly while the default theme aliases it to
`--color-surface`, so the two must be checked separately. A theme that fails is a finding.

### 10f — Forced colours

11. Enable Windows High Contrast Mode, or emulate `forced-colors: active` in DevTools
    (Rendering → Emulate CSS media feature forced-colors).
12. Reload the course player.

**Expected:** the side-panel indicator is still visible. `outline` is recoloured by forced-colors
mode rather than suppressed, which is exactly why it was chosen over a Tailwind `ring-*` (those
compile to `box-shadow`, which forced-colors drops outright).

**Also check:** the small buttons are still legible under forced colours, and `.btn`'s own
`focus:ring-*` behaviour is unchanged from before (it was already a `box-shadow` ring and is not part
of this change — do not file it as new).

### 10g — Browsers

13. Spot-check the dialog-focusing-steps case in current **Chrome**, **Firefox** and **Safari** — by
    **loading the page**, not by tabbing to a control. Browsers differ on when the focusing steps
    mark focus as `:focus-visible`, so a ring that appears in Chrome may not appear in Firefox.
    Report per browser.
