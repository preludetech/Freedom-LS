# Specification: Organisations

> **Naming note.** This feature was drafted as "Schools" and is now called **Organisation**. The spec
> directory and git branch remain `schools` deliberately — the SDD commands locate a spec by matching
> the current *branch name* to a directory under `spec_dd/`. The folder name is a workflow key, not a
> product name. The research documents in this directory pre-date the rename and say "School"
> throughout; they are kept as-is as a record of the research actually done.

---

## 1. Summary

Add an **Organisation**: a scoping layer that sits below Django's `Site` and above cohorts and course
registrations.

An Organisation is an **organisational and scoping layer within one Site's trust boundary — not a
security boundary.** Site remains the isolation boundary. Two groups that need genuine data isolation
need two Sites, not two Organisations. This is the same line Moodle draws for its own tenants
(`research_lms_school_modelling.md`).

Multiple Organisations may exist on one Site. An Organisation belongs to exactly one Site.

**What ships in this cut:**

- An `Organisation` model in a new `freedom_ls/organisations/` app, with name, slug and optional logo.
- Mandatory `organisation` FK on `Cohort` and `UserCourseRegistration`, with a backfill migration safe
  to apply to downstream databases we have never seen.
- An organisation switcher in the educator interface, with the selection carried in the URL.
- A second authorisation path: holding a role on an Organisation grants access to everything in it.
- A generic, deny-by-default object-authorisation hook in `panel_framework`, which closes the
  organisation boundary and gives `critical_security_fixes` the seam it needs.
- Small, clearly secondary organisation co-branding in the student course player.
- Organisation CRUD via the Django admin — create, rename, upload logo, assign staff. No delete, no merge.

---

## 2. Why this matters

FLS today has exactly one scoping axis: `Site`. Everything on a Site is one undifferentiated pool of
cohorts and registrations, and educator access is granted one cohort at a time through
django-guardian.

That breaks down for the customers FLS actually serves. A training provider running programmes for
three client companies, or a college with several departments, has to choose between two bad options:

- **One Site for everyone** — every educator's cohort list mixes all clients together, cohort names
  collide (`Year 9 Maths` can only exist once per Site), and a learner cannot take the same course
  through two different clients.
- **One Site per client** — genuine isolation, but each Site needs its own domain, its own course
  content, its own everything. Wildly disproportionate when the groups are meant to share courses and
  a single brand.

An Organisation is the missing middle. It gives grouping, per-group naming, per-group staff access and
light co-branding, while keeping one Site's shared course library and one set of chrome.

It also removes real per-cohort administration: today, giving someone access to a client's twelve
cohorts means twelve guardian grants, and a thirteenth cohort silently isn't covered. An organisation
role covers the organisation, including cohorts created later.

## 3. Data model

### 3.1 The `Organisation` model

Lives in the new app `freedom_ls/organisations/`, `label = "freedom_ls_organisations"`.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | UUID pk | inherited from `SiteAwareModel` |
| `site` | FK to `Site` | inherited from `SiteAwareModel` |
| `name` | `CharField(max_length=150)` | matches `Cohort.name`'s length |
| `slug` | `SlugField(max_length=150)` | URL identifier, see §3.3 |
| `logo` | `ImageField(blank=True)` | optional, see §8 |

It extends `SiteAwareModel` (`freedom_ls/site_aware_models/models.py:79-84`), not
`SiteAwareModelBase` — this gives it a UUID pk, consistent with `Cohort`, `UserCourseRegistration`
and every other domain model.

Constraints, using the `models.UniqueConstraint(fields=[...], name=...)` idiom that all recent models
in the repo use (`student_management/models.py:19-24`, `role_based_permissions/models.py:105-111`):

- `unique_organisation_slug_per_site` on `(site, slug)`
- `unique_organisation_name_per_site` on `(site, name)`

**Why names are unique per Site.** The idea did not settle this. The switcher's entire job is to say
unambiguously which organisation you are looking at, and it identifies organisations by name. Two
organisations called "Northside" on one Site would make the switcher — and every list that shows an
organisation name — actively misleading. Slug uniqueness alone does not prevent that, because
`slugify` can produce distinct slugs from identical-looking names. The name constraint is cheap now
and awkward to add later.

### 3.2 FKs added to existing models

- `Cohort.organisation` — mandatory FK, `on_delete=models.PROTECT`.
- `UserCourseRegistration.organisation` — mandatory FK, `on_delete=models.PROTECT`.

`PROTECT` rather than `CASCADE`: deleting an Organisation is refused outright at the admin layer
(§8.1), and `PROTECT` makes that refusal true at the database layer too. A stray `.delete()` from a
shell or a downstream script should fail loudly, not silently take a client's cohorts and
registrations with it.

**`CohortCourseRegistration` does not get its own FK.** Its organisation is reached via
`cohort.organisation`. One source of truth; no way for the two to disagree, and no consistency check
to write or forget.

**The deadline models and `CohortMembership` get no FK.** They inherit organisation transitively:

| Model | Reaches organisation via |
| --- | --- |
| `CohortMembership` (`student_management/models.py:30-43`) | `cohort.organisation` |
| `CohortDeadline` (`:126-170`) | `cohort_course_registration.cohort.organisation` |
| `StudentDeadline` (`:173-217`) | `student_course_registration.organisation` |
| `UserCohortDeadlineOverride` (`:220-281`) | `cohort_course_registration.cohort.organisation` |

### 3.3 The slug

`Organisation.slug` follows the mechanism already used everywhere in this codebase
(`content_engine.TitledContent`, `content_engine/models.py:99-116`): a `SlugField` unique per site,
derived with `slugify(name)`, and made collision-free by the shared `get_unique_slug` helper, which
appends `-2`, `-3`, … until the `(site, slug)` pair is free.

Generation is **not** in `save()`. It is called explicitly at each creation site: the admin, the data
migration, the new-Site receiver (§9.5), and `OrganisationFactory`.

**`get_unique_slug` moves to `site_aware_models`.** It currently lives inside a management command
(`content_engine/management/commands/content_save.py:193-224`), which a new app cannot import without
an `organisations → content_engine` edge that would invert the layering. Duplicating it would break
the repo's "extract rather than repeat" convention. Both apps already depend on `site_aware_models`,
so moving it there adds no edge. The helper is already generic over
`(model_class, site, base_slug, existing_uuid)` — this is a relocation, not a rewrite.

Two things to fix in transit, since the function is being touched anyway:

- It is currently untyped, which violates CLAUDE.md's repo-wide type-hint rule. Add hints.
- `content_save.py` imports it from its new home. Its single existing call site
  (`content_save.py:287`) is otherwise unchanged.

### 3.4 Uniqueness changes

| Model | Before | After |
| --- | --- | --- |
| `Cohort` | `(site, name)` | `(site, organisation, name)` |
| `UserCourseRegistration` | `(site, collection, user)` | `(site, organisation, collection, user)` |

Both keep their existing constraint names (`unique_cohort_name_per_site`,
`unique_user_course_registration`) so nothing downstream that references a constraint name by hand has
to change.

Note the shape of the existing definitions: both spell the site column as the attname, not the field
name — `fields=["site_id", "name"]` and `fields=["site_id", "collection", "user"]`
(`student_management/models.py:19-24`, `:59-65`). The replacements are `RemoveConstraint` +
`AddConstraint` under the same name, so switching to `"site"` here is possible but is a **separate,
deliberate change**; make it consistently across both or not at all, and check `makemigrations`
reports no residual drift afterwards.

Both are **narrowing** changes — adding a column to a unique key. Neither can fail against existing
data: two rows that satisfied the old, stricter key cannot collide under a looser one. This must be
said explicitly in the upgrade notes, because operators have been warned about a genuinely dangerous
constraint change before and will assume this one is the same.

### 3.5 Required audit: duplicate registrations

Widening `UserCourseRegistration` uniqueness means a learner can now hold **two** registrations for
the same course through two organisations. Any code that assumes at most one will start raising
`MultipleObjectsReturned` — a runtime 500, not a test failure, and only on multi-organisation Sites.

**Every `UserCourseRegistration.objects.get(...)` / `.get_or_create(...)` call site must be audited
during implementation**, with particular attention to the course-access backends behind
`COURSE_ACCESS_BACKEND`, `student_progress`, and `student_interface`. Where a single registration is
genuinely needed, the deterministic rule is: the most recent **active** registration by
`registered_at`, falling back to the most recent of any status. This is not optional cleanup; it is
part of the change.

## 4. Authorisation

### 4.1 The model: two paths, deliberately

Holding a role on an Organisation grants access to **everything in that organisation**. Educator
queries become "cohorts I hold a guardian grant on, **or** cohorts whose organisation I hold a role
on". Organisation staff need no per-cohort grant.

This is a second authorisation path alongside django-guardian's per-object grants, and it is not
merely a preference — **guardian cannot express "organisation role ⇒ cohort access" even in
principle**:

- `sync_user_object_permissions` filters a role's permission set through
  `_filter_perms_for_content_type` (`role_based_permissions/utils.py:123-137`), which drops any
  permission whose `app_label` differs from the target object's content type. Guardian requires that
  match for its own queries to work.
- So a role assigned on an Organisation can only ever sync `freedom_ls_organisations.*` permissions
  into guardian. It **cannot** carry `freedom_ls_student_management.view_cohort`.

Record this so nobody spends a day trying to route organisation access through guardian during
planning.

**But the useful half does work through guardian.** A role assigned on an Organisation syncs
`freedom_ls_organisations.view_organisation` onto that Organisation object, because the app labels
match. So:

- "Does this user hold a role on this Organisation?" → `user.has_perm("freedom_ls_organisations.view_organisation", organisation)`
- "Which Organisations does this user hold a role on?" → `get_objects_for_user(user, "freedom_ls_organisations.view_organisation", klass=Organisation)`

Both are ordinary guardian calls. What guardian cannot do is the **implication** from that grant to
cohort access — the query helpers in §4.4 perform that join explicitly.

The trade-off to record: guardian is no longer the single enforcement layer. Two mechanisms now decide
educator visibility, and a reader of the guardian tables alone will not see the whole picture.

### 4.2 Roles

No new model and no new dependency. `ObjectRoleAssignment`
(`role_based_permissions/models.py:80-118`) targets any model through a `GenericForeignKey`, and
`assign_object_role(user, target, role)` (`role_based_permissions/utils.py:192-226`) never imports the
target's class. Its `unique_object_role_per_user` constraint is on
`(user, content_type, object_id, role)`, so N rows for N organisations is the natural shape and needs
no schema change — which is exactly what makes holding roles on several Organisations at once work,
and what makes the switcher worth building.

One new role in v1, declared in `role_based_permissions/roles.py` alongside the existing
`SCOPE_OBJECT` roles (`roles.py:38-66`):

```python
"organisation_staff": Role(
    display_name="Organisation Staff",
    assignment_scope=SCOPE_OBJECT,
    lti_role=None,
    description="Access to every cohort and registration within an organisation.",
    permissions=frozenset({"freedom_ls_organisations.view_organisation"}),
),
```

Per `role_based_permissions/README.md:141`, the permission strings must be added to `registry.py`'s
`PERMISSIONS` dict before being referenced in a role.

### 4.3 The boundary: resolve and authorise, once

**Selecting an organisation is an authorisation decision, not a filter.** Unlike Site — which is
derived from the request host and cannot be forged — an organisation comes from user-supplied URL
input. Every `/organisations/<slug>/...` entry point must resolve the slug and check the user's
permission on it *before* anything else, and fail closed.

This lives in one shared boundary used by every entry point, never copy-pasted per view. Two pieces:

**(a) `panel_framework` gains a generic object-authorisation hook.**

`ListViewConfig.get_instance_view` (`panel_framework/views.py:180-185`) is currently a bare
`get_object_or_404` with no permission check of any kind, called from `_resolve_path`
(`panel_framework/views.py:318-319`) for every `cohorts/<pk>`, `users/<pk>` and `courses/<pk>` detail
URL. It is the single chokepoint for detail-view resolution across the whole educator interface, and
it is the same hole `critical_security_fixes` exists to close.

This spec adds:

```python
class ListViewConfig:
    #: Set to a short reason string on a config that deliberately does not
    #: authorise its detail views yet. Introspectable, so the §11.2 test can
    #: assert every exemption is declared rather than accidental.
    check_access_exempt_reason: str | None = None

    @classmethod
    def check_access(cls, request: HttpRequest, instance: Model) -> None:
        """Raise Http404 unless this request may see this instance.

        Deny by default: a config that does not override this cannot serve
        detail views at all.
        """
        raise Http404
```

**`get_instance_view` must gain the request.** Its current signature is
`get_instance_view(cls, pk: str) -> InstanceView` (`panel_framework/views.py:180-185`) — it has no
request at all, so the hook cannot be called from it as written. Two mechanical changes go with the
hook:

- `get_instance_view` becomes `get_instance_view(cls, request: HttpRequest, pk: str)` and calls
  `cls.check_access(request, instance)` before `cls.instance_view(instance)`.
- Its sole caller, `_resolve_path` (`panel_framework/views.py:318-319`), passes the
  `effective_request` it already computes.

This is a **breaking signature change on a public `panel_framework` class method**, not just a new
hook, and every override must follow it — including `panel_framework/tests/stub_panels.py:129-143`,
which overrides `get_instance_view` today and would otherwise bypass the check entirely inside
`panel_framework`'s own tests. Note this alongside §15.3 in the upgrade notes.

**Fail closed on a request with no user.** `_resolve_path` takes `request: HttpRequest | None = None`
and falls back to `effective_request = request or HttpRequest()` (`panel_framework/views.py:305`). A
bare `HttpRequest` has no `.user` and no `.organisation`, so a `check_access` that reads either would
raise `AttributeError` — a 500, not a denial. Every `check_access` implementation must treat a missing
or unauthenticated `request.user`, and a missing `request.organisation`, as a denial and raise
`Http404`. Today's only caller (`views.py:570`) always passes a real request; the rule exists so the
fallback path cannot become a hole later.

**Deny by default is the whole point.** A new config that forgets to think about authorisation fails
closed instead of leaking. Existing configs that are not organisation-scoped keep today's behaviour
via an explicit override that sets `check_access_exempt_reason` **and** carries a `@claude` TODO
naming `critical_security_fixes` as the owner of the real check. The attribute is what makes the
exemption machine-checkable (§11.2) — a comment alone is not introspectable; the TODO is what makes it
land in the security work's queue. That converts an invisible hole into a tracked one; it does not
make anything worse than it is today, and it does not pull the whole of `critical_security_fixes` into
this spec.

`panel_framework` gains **no new app dependency** — the hook is generic and never mentions
Organisation.

**(b) `educator_interface` resolves and authorises the organisation.**

A single wrapper around the educator entry point:

1. `organisation = get_object_or_404(Organisation, slug=organisation_slug)`
2. Deny unless the organisation is in `organisations_accessible_to(request.user)` (§4.4)
3. Set `request.organisation` and proceed

**Site scoping is already applied — do not write `request.site`.** FLS has no such attribute: it
appears nowhere in the codebase, and its `CurrentSiteMiddleware`
(`site_aware_models/middleware.py`) only stashes the request in a thread-local; it never annotates the
request. The canonical accessor is `get_cached_site(request)` (`site_aware_models/models.py:19-40`).

In this particular lookup neither is needed, because `Organisation.objects` is a `SiteAwareManager`
(`site_aware_models/models.py:43-50`) which already filters every queryset to the current site. So the
step-1 lookup cannot return another Site's Organisation, and a slug that exists only on another Site is
indistinguishable from one that does not exist — which is the correct outcome and is exactly the 404
uniformity the rest of this section argues for.

**Fail closed with 404, uniformly** — for "no such slug" and for "slug exists but you have no access"
alike. 403 would confirm that a slug is real, letting an attacker enumerate a Site's organisation
names by trying slugs. The idea said "403/404"; this spec picks 404 so implementers do not choose
inconsistently across views (OWASP IDOR Prevention Cheat Sheet). This path is only ever reached by a
hand-edited or guessed URL — the switcher never offers an organisation the user cannot enter, so no
legitimate navigation produces it.

The per-instance `check_access` implementations for organisation-scoped configs then assert the
instance belongs to `request.organisation`:

| Config | `check_access` rule |
| --- | --- |
| `CohortConfig` | `instance` is in `cohorts_visible_to(request.user, request.organisation)` |
| `UserConfig` | `instance` has a cohort membership or a registration within `request.organisation` that the user may see |
| `CourseConfig` | permissive override + `check_access_exempt_reason` + `@claude` TODO naming `critical_security_fixes` (courses are not organisation-scoped in this cut, §6.4) |

`CohortConfig`, `UserConfig` and `CourseConfig` (`educator_interface/views.py:757`, `:769`, `:1024`)
are the only three production `ListViewConfig` subclasses in the tree; the rest live under
`panel_framework/tests/` (§11.2).

### 4.4 Query helpers

The idea requires organisation scoping to live behind a small number of query helpers rather than
being inlined, so a future nested-organisation change ("or descendants") stays localised. Concretely,
one module carries them all. That module **already exists** —
`freedom_ls/student_management/queries.py`, currently holding
`is_registered_for_course_expression` — so this is an addition to an established home, not a new file.
It gains:

```python
def organisations_accessible_to(user: User) -> QuerySet[Organisation]:
    """Organisations this user may enter: an organisation role, OR a per-cohort
    guardian grant on any cohort inside it."""

def cohorts_visible_to(user: User, organisation: Organisation) -> QuerySet[Cohort]:
    """Cohorts within this organisation: all of them if the user holds an
    organisation role, otherwise only those with a per-cohort guardian grant."""

def users_visible_to(user: User, organisation: Organisation) -> QuerySet[User]:
    """Built on cohorts_visible_to — never re-derives cohort visibility."""
```

**The helpers live in `student_management`, not `organisations`.** They must import both `Cohort` and
`Organisation`; putting them in the `organisations` app would create an `organisations →
student_management` edge that inverts the layering and breaks §12 Decision 2. `student_management`
already sits above both.

**`organisations_accessible_to` must include the guardian-grant path.** This is load-bearing and easy
to miss: educators who today hold only per-cohort guardian grants and no organisation role must still
be able to enter the educator interface after every URL gains an organisation segment. Omitting the
union would lock every existing educator out on upgrade.

`CohortDataTable.get_queryset` (`educator_interface/views.py:81-95`) and `UserDataTable.get_queryset`
(`:120-141`) are rewritten to call these helpers. Note that `UserDataTable` today re-derives cohort
visibility with its own `get_objects_for_user` call (`:126-130`); after this change it goes through
`cohorts_visible_to` so an organisation-scoping change cannot apply to one table and not the other.

## 5. URL design

The organisation lives **in the URL, as a path segment** — not in the session.

```
/educator/organisations/<slug:organisation_slug>/...
```

**Why the URL and not the session.** A session-stored scope is shared across browser tabs, so an
educator comparing two organisations in two tabs silently gets whichever was switched to last — and
the switcher can then display one organisation while showing another's data. In the URL, each tab is
self-describing, pages are deep-linkable, the back button is correct, HTMX partials inherit the right
scope from server-rendered URLs with no extra propagation mechanism, and access logs get the
organisation for free.

**The segment prefixes the entire educator interface**, including the Courses section, which is not
organisation-scoped in this cut (§6.4). The Courses views simply ignore it. The alternative — bare
URLs for unscoped sections — would mean navigating to Courses drops the organisation context, so
returning to Cohorts would need a remembered value to restore it, reintroducing exactly the
session-state problem the URL design exists to avoid. One URL shape, stated plainly: the slug is
always present, and for Courses it scopes nothing.

Mechanics:

**The educator URLconf is a single catch-all `re_path`, not a set of `path()` patterns.**
`educator_interface/urls.py` is, in its entirety:

```python
urlpatterns = [
    re_path(r"^(?P<path_string>.*)$", views.interface, name="interface"),
]
```

Everything after the prefix is one opaque `path_string` walked by `panel_framework._resolve_path`.
That shapes the work:

- The slug becomes a **second named group in that same `re_path`**, e.g.
  `r"^organisations/(?P<organisation_slug>[-a-zA-Z0-9_]+)/(?P<path_string>.*)$"`. Django's built-in
  `slug` path converter is **not** available here — it belongs to `path()`, and a trailing catch-all
  cannot be expressed with `path()`. The regex character class above is what the `slug` converter uses
  anyway, so it rejects malformed segments at routing time just the same.
- `app_name = "educator_interface"` is unchanged, and there is still exactly **one** URL name,
  `educator_interface:interface`. The slug is a second kwarg on it, not a namespace segment.
- A second bare pattern is needed for `/educator/` itself, which redirects per the rule below.
- Every `reverse()` and `{% url %}` call into `educator_interface` gains `organisation_slug=...`.
  There are roughly **20 references to `educator_interface:interface`** across views and templates —
  smaller than the factory work in §10, and bounded, because a single URL name means a single grep
  finds all of them. Two chokepoints carry a disproportionate share and should be done first: the
  `url_name` / `url_path_template` entries in the data-table column definitions, and the
  `resolve_url_path_template` template tag used by the link cell partials.
- A `current_organisation` context variable, sourced from the §4.3 resolve step, so templates do not
  re-derive the slug from `request.path`.
- HTMX partial targets must always be built with `{% url %}` and the explicit kwarg — never by
  string-concatenating `request.path`, which would work today and break the moment the URL shape
  changes.

**Bare `/educator/` entry.** A "last selected organisation" may be remembered server-side (a session
key) but **only** to decide where a bare `/educator/` redirects. It is re-authorised on use and falls
back to the first accessible organisation by name. Once a URL names an organisation, the URL always
wins. A user with no accessible organisations gets a 404 from `/educator/`.

## 6. Educator interface

### 6.1 The switcher

A single control at the **top of the left-hand panel**, above the existing nav, inside the
`sidebar_content` block — i.e. a new include placed before the existing
`{% include "panel_framework/partials/sidebar_nav.html" %}` line in
`educator_interface/templates/educator_interface/interface.html:10-12`.

It always displays the **current organisation's name** — never a generic "Select organisation"
placeholder. The name is the ambient indicator; the chrome must never be able to say one organisation
while showing another's data.

- **More than one accessible organisation:** the name is a button that opens the list of the user's
  other organisations. It reuses the existing `c-dropdown-menu` cotton component
  (`base/templates/cotton/dropdown-menu.html`) with a custom `<c-slot name="trigger">`, exactly as
  `partials/header_bar_user_menu.html` already does, rather than rebuilding dropdown logic.
- **Exactly one accessible organisation:** hide the interactive control, but still render the
  organisation's name as static text in the same position. When a second organisation is later
  granted, the *same* label becomes clickable rather than a new element appearing from nowhere.

### 6.2 Accessibility

The idea asked for `role="listbox"` / `role="option"` / `aria-selected`. That conflicts with reusing
`c-dropdown-menu`, which hardcodes `aria-haspopup="menu"` on its trigger and is also used by the
header user menu. **The switcher uses menu semantics instead:**

- Trigger: the component's existing `aria-haspopup="menu"` + `aria-expanded`, with the organisation
  name as visible text and an `aria_label` naming the control.
- Each option: `role="menuitemradio"` with `aria-checked="true"` on the current organisation and
  `aria-checked="false"` on the others.

This is the WAI-ARIA APG-sanctioned pattern for "choose one of N" inside a menu button. It conveys the
same "which one am I on" state that `aria-selected` would, requires **no change to a shared component
the user menu depends on**, and needs no new keyboard JS beyond the open/close/click-away/Escape
behaviour `c-dropdown-menu` already provides.

Because switching re-renders the whole main content, the switch response must also announce the
change. Add a persistent visually-hidden live region:

```html
<div id="scope-announcer" class="sr-only" aria-live="polite" aria-atomic="true"></div>
```

placed as a sibling of `#main-content`, **not inside it**, so the swap updates the region rather than
destroying and recreating it (some screen readers miss a re-inserted live region). Concretely that is
inside the `{% block content %}` of `educator_interface/templates/educator_interface/interface.html`
(`:20-24`), beside the `main_content.html` include — **not** in `_base_interface.html`, which is shared
with the student course player and has no organisation concept. The switch response includes an
`hx-swap-oob="true"` fragment targeting that id with "Now viewing {organisation name}".

A live-region announcement is preferred over forcibly moving focus to the new page's heading: a focus
move is disruptive if the educator wants to immediately reopen the switcher to compare a third
organisation.

The mechanism exists: FLS's dispatcher already renders out-of-band fragments for breadcrumbs, sidebar
nav and page title on every `is_navigation` request (`panel_framework/views.py:590-615`), and the
switcher's `hx-target="#main-content"` satisfies the `is_navigation` condition. But the announcer is a
**new** fragment — one more `render_to_string` block in that dispatcher, conditional on a message
being set. Small, and it follows an established pattern rather than inventing one; it is not zero
work.

Note for implementation: `c-dropdown-menu` closes on any window scroll
(`x-on:scroll.window="close"`), which the existing `@claude` comment at `dropdown-menu.html:24-31`
already flags as more visible since the header went sticky. The switcher sits near the top of a
scrollable sidebar, so this behaviour will be noticeable. **Do not delete that comment**; if the
behaviour proves unacceptable during QA, it is a fix to that comment's issue, not a switcher-specific
workaround.

### 6.3 On switching

Reuse the existing HTMX navigation mechanism, not a new one: `hx-get` + `hx-target="#main-content"` +
`hx-push-url="true"` + `hx-swap="outerHTML"`, exactly as `sidebar_nav.html:8-16` already does.

- **On a list/index page:** reload it in place for the new organisation.
- **On a detail page for an object that does not belong to the newly selected organisation:** redirect
  to the equivalent list page with a one-line inline notice — "Switched to Northside — that cohort
  isn't in this organisation".

The notice uses Django's `messages` framework. `HtmxMessagesMiddleware` (`base/middleware.py`) already
handles both cases: it is a no-op on redirects (the message renders on the next full load) and
appends an OOB toast fragment otherwise. `messages.info(...)` before returning is the entire
integration point — there is no separate alert component to build.

**Never render a bare 404 as the direct consequence of a switch.** No confirmation dialog — the
educator interface is read-mostly.

### 6.4 What is not organisation-scoped in this cut

The Courses list, course interest, course applications and course recommendations stay unscoped.
Course content is shared across the whole Site and has no organisation; interest, applications and
recommendations all happen *before* a registration exists, so there is no organisation to inherit.

This means the switcher visibly does not apply to the Courses tab. That is a known, accepted gap for
v1, stated here rather than left for someone to trip over.

Separately: the Courses list is currently completely unguarded — `CourseDataTable.get_queryset`
(`educator_interface/views.py:777-801`) is `Course.objects.all()`, so every logged-in user sees every
course on the Site with no permission check at all. That is a pre-existing bug this work makes more
visible. It belongs with `critical_security_fixes`, not here; this spec's contribution is the
deny-by-default `check_access` hook that makes the exemption explicit and greppable rather than
invisible.

## 7. Student interface

If a learner is doing a course through a specific organisation, that organisation's logo appears in
the course player as a **small, clearly secondary** element.

**Placement: the course outline header**, beside the course title, in
`student_interface/templates/student_interface/partials/course_toc_header.html` — between the title
and the progress bar, or on the same line as the title. That region already sits inside
`#course-toc-region`, which is out-of-band swapped on Previous/Next navigation
(`_course_base.html:59-80`), so the chip stays in sync across player navigation for free. It also sits
with course identity rather than page-location chrome, which keeps the "who runs the platform" line
clear. The trade-off: on small screens the outline lives behind a dialog, so the logo is not
permanently on screen. That is acceptable for a secondary co-branding mark.

**Which organisation.** If the learner is in a cohort registered for this course, that cohort's
organisation — reached as `cohort_course_registration.cohort.organisation`, since
`CohortCourseRegistration` has no FK of its own (§3.2). Otherwise their individual registration's
`organisation`. Otherwise no logo. Where §3.5's duplicate-registration case applies, use the most
recent active registration by `registered_at`.

This resolution does not exist anywhere today. Neither `view_course_item`
(`student_interface/views.py:554-648`) nor `_player_chrome_context` (`:651-697`) ever looks up how the
learner got into the course — only `CourseProgress`. The lookup is new code threaded into
`_player_chrome_context`'s returned context, and must be written with `select_related` so it costs one
query, not one per render.

**Rendering rules.** Fixed height, **capped** width, inside a light padded chip. Not a link.

The chip is load-bearing, not cosmetic. The two shipped themes put the header on visually different
backgrounds — `themes/default/.../theme.css:151` sets `--color-header: var(--color-primary)` (solid
brand colour), while `themes/first_class/.../theme.css:226` sets `--color-header: white`. The
reference asset is a near-black mark on a transparent background, which is the normal case for a logo:
dropped straight onto the solid-brand-colour theme it disappears. **The chip must be an opaque light
fill, not just padding.**

The width cap matters too. The existing site logo uses `h-8 w-auto flex-shrink-0`
(`base/templates/partials/header_bar.html:9-10`), which is fine for one known static asset but has no
upper bound. The reference asset's aspect ratio is roughly 2.2:1; a wider banner-style logo under
"fixed height, auto width" would push the header out. Cap the width so wide marks scale down instead
of overflowing.

**Monogram fallback.** If an organisation has no logo, show an initials monogram derived from the
organisation name, mirroring the existing `User.initials` badge (`accounts/models.py:125-144`,
rendered at `partials/header_bar_user_menu.html:5-14`) so mixed lists stay visually consistent. An
`Organisation.initials` property, NFC-normalising before slicing exactly as `User.initials` does:

1. Two or more whitespace-separated tokens → first letter of the first two tokens, uppercased.
   "RPAS Training" → **"RT"**.
2. A single token → its first two letters, uppercased. "Northside" → **"NO"**.
3. No usable alphabetic characters → `None`, and the template falls back to a generic icon, exactly as
   the user badge falls back to `<c-icon name="user">`.

Rule 2 answers the question the idea flagged as open.

**Reference asset.** `RT-logo.webp` in this directory is the sample to build and QA against —
organisation name "RPAS Training", 1324×609, 12.6 KB, WebP with an alpha channel. Its name also
exercises the monogram sensibly: "RPAS Training" yields "RT", matching the mark in the logo itself.

**A deliberate departure from the big LMSs.** Docebo and TalentLMS rebrand the entire portal per
sub-organisation. FLS co-brands a shared chrome with a small secondary mark. That is much cheaper and
fine — provided the organisation logo stays visually subordinate, so a learner is never confused about
who runs the platform versus which organisation they are studying through.

## 8. Organisation management

### 8.1 Admin

Organisation CRUD is admin-only: create, rename, upload a logo, assign staff. **No delete and no
merge** — `has_delete_permission` returns `False`.

The admin needs both site-exclusion *and* guardian's object-permission UI (to assign organisation
staff). Neither existing base class provides both: `SiteAwareModelAdmin`
(`site_aware_models/admin.py:13-16`) excludes `site` but has no guardian integration, and `CohortAdmin`
(`student_management/admin.py:38-44`) extends `guardian.admin.GuardedModelAdmin` directly without
excluding `site`.

There is already an un-implemented `@claude` TODO asking for exactly this base class, sitting inside
`CohortAdmin`:

```python
# @claude: We need a base class that extends from Guarded model admin and excludes the site (like SiteAwareModelAdmin).
# implement it and then update docs/admin_interface.md
```

This feature is a second, independent reason it now needs doing. Add `GuardedSiteAwareModelAdmin` with
`exclude = ["site"]` to `site_aware_models/admin.py` alongside `SiteAwareModelAdmin`;
`OrganisationAdmin` and `CohortAdmin` both extend it. The TODO is only removed once that is genuinely
done, and the doc it names — now at `docs/product/admin-interface.md` — is updated in the same change.

**It must inherit from both guardian and unfold.** This project runs django-unfold:
`SiteAwareModelAdmin` extends `unfold.admin.ModelAdmin` (`site_aware_models/admin.py:13-16`), and
`unfold.contrib.guardian` is already in `INSTALLED_APPS` (`config/settings_base.py:91`) precisely for
this combination. A base class extending `guardian.admin.GuardedModelAdmin` alone would bypass unfold
entirely and render an unstyled admin page — which is what `CohortAdmin(GuardedModelAdmin)` does today
and is part of what the TODO is asking to fix. The base class is therefore
`GuardedSiteAwareModelAdmin(GuardedModelAdmin, ModelAdmin)`: guardian first so its object-permission
views win, unfold second for presentation. Verify the object-permissions page actually renders under
unfold during QA — this MRO is the one thing here most likely to need a small adjustment.

Slug generation happens in the admin's save path via `get_unique_slug`, not in `Organisation.save()`.

### 8.2 The logo field and its costs

`Organisation.logo` is an optional `ImageField` stored on FLS's existing media storage. Three real
costs come with it, named here rather than absorbed silently.

**1. Pillow becomes a base dependency.** FLS has no image infrastructure today at all — no
`ImageField`, no Pillow, no image validation anywhere (verified repo-wide). Add it via `uv add pillow`
as a main dependency with a lower bound (`pillow>=11.0`), not an exact pin and not a dev extra:
Django's `ImageField` requires Pillow at validation time whether or not a given install ever uploads a
logo, and Pillow's wheels statically bundle the image decoder libraries, so a version bump is how
downstream installs pick up an upstream decoder CVE fix. Prebuilt wheels exist for every platform FLS
deploys to, so no compiler toolchain is required. `pyproject.toml` already carries a defensive
`[tool.mypy.overrides]` entry for `"PIL.*"`; check whether it is still needed once Pillow ships its own
type information.

**2. New upload-security surface.** This is FLS's first user-uploaded, publicly-rendered image, and
the only existing upload precedent (`content_engine.File`, `content_engine/models.py:565-599`) has no
validation whatsoever. Everything below is new code.

**3. Storage.** Addressed in §8.4 — cheaper than the idea assumed.

### 8.3 Upload validation

Two layers. The extension check is cheap and first; the Pillow check is authoritative.

- **Extension allowlist** via Django's `FileExtensionValidator` for `png`, `jpg`, `jpeg`, `webp`. This
  is a filter, not a security boundary — a file can always be renamed — which is why the byte-level
  check below is mandatory rather than defence in depth.
- **SVG is rejected.** SVG is XML, not raster data: it can carry `<script>`, `on*` handler attributes
  and `<foreignObject>`-embedded HTML, and OWASP's File Upload Cheat Sheet names it specifically as an
  XSS vector even when allowlisted as an image type. Raster formats fully cover a logo's needs at the
  sizes rendered here, so there is no product reason to take the risk. Both layers exclude it.
- **Byte-level verification with Pillow.** Open, `verify()`, then **re-open on a rewound handle**
  before reading anything else. `Image.verify()` is documented as destructive to the object it is
  called on — reading `.size` after `verify()` on the same object raises. Two `Image.open()` calls with
  a `seek(0)` between them is the correct shape and the single most common thing to get wrong here.
- **Format assertion:** `img.format` must be one of `PNG`, `JPEG`, `WEBP`. This is what catches an SVG
  or anything else renamed to `.png`.
- **Decompression bombs:** leave Pillow's global `MAX_IMAGE_PIXELS` at its default — never set it to
  `None` — and escalate `Image.DecompressionBombWarning` to an error inside a
  `warnings.catch_warnings()` block, because a bare warning does nothing in production.
- **Pixel dimensions:** maximum **4000 × 4000**, minimum **64 × 32**. The maximum must clear the
  reference asset (1324 × 609) with real headroom — a cap of 1024 would reject an entirely ordinary
  logo — while staying far below Pillow's ~89.5M-pixel bomb threshold so the two guards do not fight.
  A square ceiling rather than a wide/tall-specific pair, because a crest-style logo can be tall and
  narrow just as plausibly as the reference asset is wide and short. The minimum rejects a 1×1
  tracking-pixel-style upload without rejecting a small square icon mark.
- **File size:** maximum **2 MiB**, checked explicitly in the validator. The project-wide
  `DATA_UPLOAD_MAX_MEMORY_SIZE` of 5 MB (`config/settings_prod.py:52-53`) already rejects anything
  larger before a view sees it, but a field-specific limit gives a useful error message and catches
  the case the pixel cap cannot: an image within dimensions but pathologically uncompressed.
- **Storage path** is `organisations/{pk}{ext}`. **The uploaded filename is never interpolated into
  the storage path** — that is what prevents path traversal, overwrite collisions, and leaking the
  uploader's local filesystem structure. `SiteAwareModel.id` defaults at instantiation, so the pk
  exists before the first `save()` and `upload_to` always has one.

  This is **deliberately stricter than the existing precedent**, not a copy of it.
  `file_upload_handler` (`content_engine/models.py:565-572`) builds
  `f"content_engine/{stem}{pk}{ext}"` — it *does* interpolate the uploaded filename's stem. Do not
  carry that across: the pk alone is sufficient to identify the file, and the stem is the part that
  carries the risk. Leaving `content_engine` as it is belongs to a separate change.

Validators run on the field; the admin form surfaces their messages. Error text names the actual
problem and the actual limit ("Image is too large (5000×5000px; maximum is 4000×4000px)"), not a
generic "invalid image".

**EXIF is not stripped, deliberately.** Stripping means re-encoding, and re-encoding a transparent
WebP risks a visible regression in exactly the asset class this feature is built for. The usual
motivation — location metadata in personal photographs — does not apply to a corporate logo uploaded
by an administrator. Recorded as a considered decision so a later security review sees a choice rather
than an oversight; revisit if logo upload is ever opened up beyond admin staff.

### 8.4 Storage: no public-read carve-out

The idea assumed a public-read carve-out was needed, because FLS's S3/R2 media is private by default
with signed URLs (`querystring_auth` defaults to `True`, `config/settings_prod.py:114-127`). **It is
not needed, and this spec does not add one.**

The logo only ever renders inside authenticated, server-rendered pages. `logo.url` on the existing
default storage returns a freshly signed URL on every render, which works exactly as it does for every
other media file in FLS. No second `STORAGES` alias, no `location` parameter added to
`build_s3_media_storage`, no bucket policy for operators to apply, no new environment variables, and
no upgrade step that can be got wrong in a way that exposes unrelated private media.

The trade-off, stated plainly: the signed query string changes on each render, so browsers re-fetch
the asset (~13 KB for the reference logo) rather than caching it across page loads, and a logo URL is
not shareable outside a session. Both are acceptable for a small, rarely-changing mark inside an
authenticated player. If logo rendering ever moves to an unauthenticated page — a public course
catalogue, a certificate, an email — that is the point at which a public carve-out or a Django-served
endpoint becomes necessary, and it can be added then without changing the model.

## 9. Migration and rollout

FLS ships as a git submodule into downstream projects that run `migrate` against their own live
databases. **This migration will be applied unmodified to databases we have never seen.**

### 9.1 The sequence

Separate migration files, never combined:

1. Create the `Organisation` model.
2. Add `organisation` as a **nullable** FK to `Cohort` and `UserCourseRegistration`.
3. **Data migration.** For each Site that actually exists, `get_or_create` one Organisation named
   after the Site, then backfill every cohort and registration for that Site into it.
4. **Validation.** Assert nothing is left null; fail loudly with our own message rather than a bare
   `IntegrityError`.
5. Make both FKs non-nullable.
6. Apply the constraint changes: `RemoveConstraint` the old name, `AddConstraint` the new definition
   under the same name.

Keeping the data migration in its own file matters: a schema migration is cheap to retry and has no
data-dependent failure mode, while a `RunPython` can fail for reasons specific to one downstream
database. Separate files mean `showmigrations` tells an operator exactly which step failed.

### 9.2 Rules the backfill must follow

- **Use `apps.get_model` throughout, never a real model import.** The real `save()` reads a
  thread-local request that does not exist during `migrate`.
- **Iterate the Sites that actually exist**; never assume a particular Site row is present. The
  precedent is `content_engine/migrations/0009_backfill_course_accent_slot.py`.
- **Idempotent**: `get_or_create`, not `create`, so a retried partial apply cannot create duplicates.
- **Leave `atomic` at its default `True`.** On PostgreSQL this wraps the whole file in one
  transaction, so a crash mid-loop rolls back entirely and the migration is not recorded as applied —
  which is what makes a retry safe by construction. Given FLS's documented scale (low thousands of
  rows, `docs/product/deployment.md:73-83`), a plain `AlterField(null=False)` is fine; the
  `NOT VALID` CHECK → `VALIDATE` → `SET NOT NULL` dance is not needed.
- **`reverse_code=migrations.RunPython.noop`** on the backfill. Not because there is a meaningful
  undo, but because omitting it raises `IrreversibleError` for an operator legitimately rolling back
  an unrelated later migration in the same app.
- Slug generation for the created Organisations uses `get_unique_slug` from its new home.

### 9.3 The validation step

Copy the shape of `student_management/migrations/0006_validate_no_duplicate_students.py`, but use the
ORM rather than that migration's raw cursor — the backfill's own rule is `apps.get_model` throughout,
and mixing the two styles inside one rollout invites confusion:

```python
def validate_organisation_backfilled(apps, schema_editor):
    Cohort = apps.get_model("freedom_ls_student_management", "Cohort")
    count = Cohort.objects.filter(organisation__isnull=True).count()
    if count:
        raise RuntimeError(
            f"{count} Cohort row(s) still have no organisation after the backfill "
            "migration. This means a Site existed without a default Organisation at "
            "backfill time, or a Cohort was created between the backfill and this "
            "check. Do not proceed: investigate before re-running `migrate`."
        )
```

The same check runs for `UserCourseRegistration`. This is what turns a bare
`null value in column "organisation_id" violates not-null constraint`, several steps later and with no
context, into a message that says what happened and what to do.

### 9.4 Upgrade notes must say

- Both constraint changes are **narrowing** and cannot fail against existing data. Say so explicitly:
  operators have been warned about a genuinely dangerous constraint change before and will assume this
  one is the same.
- **Do not `--fake` the backfill migration.** Faking records it as applied without running it; the
  not-null step then fails for real. (That failure is the safety net working, but the operator should
  not get there.)
- **Do not roll back after go-live.** The backfill's reverse is a no-op, and rolling back far enough
  drops the `organisation_id` columns and the `Organisation` table outright — there is nothing to put
  back except a database restore.
- If a downstream project has modified `unique_cohort_name_per_site` or
  `unique_user_course_registration` outside FLS's own migrations, reconcile before upgrading:
  `RemoveConstraint` addresses the constraint by name.
- The duplicate-registration consequence of §3.5, for any downstream code that queries
  `UserCourseRegistration` directly.
- **Two separate breaking changes to `ListViewConfig`** for any downstream project with its own
  subclass: `get_instance_view` gains a `request` argument, and `check_access` must be implemented or
  detail views 404 (§4.3, §15.3, §15.4). Both, not one.

### 9.5 New Sites get a default Organisation

Sites created after this migration must never be left without an Organisation, whatever route created
them.

**This is a `post_save` receiver on `django.contrib.sites.Site`, registered by the `organisations`
app** (in its `apps.py` `ready()`, per Django's convention), which `get_or_create`s an Organisation
named after the Site using the same naming and slug rule as the backfill.

**Why a signal rather than editing `create_site`.** The obvious move — adding the `get_or_create` to
`site_aware_models/management/commands/create_site.py` — would create a
`site_aware_models → organisations` import edge. `site_aware_models` currently has **zero** outgoing
edges in `docs/app_structure.md`; it is the floor of the dependency graph, which is the whole reason
§3.3 can move `get_unique_slug` there and §4.4 can put the query helpers in `student_management`. An
edge out of the floor would invert the layering this spec defends everywhere else and break §14.20.
The receiver points the other way — `organisations → django.contrib.sites` — and covers strictly more
ground: `create_site`, the Django admin, a shell session and `SiteFactory` all get a default
Organisation, with no command left to remember to run.

Two things the receiver must get right:

- **Idempotent** — `get_or_create`, so re-saving a Site (e.g. a domain change) never creates a second
  Organisation. The `created` flag from the sender is not sufficient on its own.
- **It does not fire during the data migration.** `RunPython` uses historical models from
  `apps.get_model`, and a receiver registered against the concrete `Site` class does not run for
  those. The §9.1 backfill therefore remains the only thing creating Organisations for pre-existing
  Sites, and the two cannot race or double up.

`create_site.py` is not modified by this spec at all.

*Adjacent, do not fix here:* `create_site.py:21-22` assigns `site.domain` without ever calling
`site.save()`, so a domain change to an existing Site is silently dropped. That is a separate
pre-existing bug and belongs in its own change. (Noted because it is directly above the code this
spec deliberately chose not to touch.)

## 10. Factories, QA data and test data

**The factories are part of this change, not a follow-up.** Roughly **366 call sites across 45 files**
use the four affected factories, none of which set an organisation (verified against the current tree).
The moment either FK goes non-nullable, four apps' test suites fail at once unless
`OrganisationFactory` and the factory defaults land in the same change.

- `OrganisationFactory(SiteAwareFactory)` with `name = factory.Sequence(...)`, mirroring
  `CohortFactory` (`student_management/factories.py:25-31`), and an explicit `get_unique_slug` call.
- `CohortFactory` and `UserCourseRegistrationFactory` each gain
  `organisation = factory.SubFactory(OrganisationFactory)`.
- `CohortMembershipFactory` and `CohortCourseRegistrationFactory` need no new field — they already
  `SubFactory` `CohortFactory` and inherit its organisation.

Independent `SiteAwareFactory` subfactories land on the same Site automatically, because each resolves
`site` from the same thread-local request (`site_aware_models/factories.py:23-48`). No shared-site
trait is needed; this is the same mechanism `CohortCourseRegistrationFactory` already relies on.

**The §9.5 receiver changes what `SiteFactory` produces.** Every `SiteFactory()` call — there are
about **17** in the suite — now yields a Site that already carries one Organisation. That is benign
for anything asserting on cohorts or registrations, but any test asserting an absolute
`Organisation.objects.count()`, or that a Site has no Organisation, must account for it. §11.3 is the
one place that must actively suppress the receiver.

**The QA data-seeding management commands need the same treatment and are easy to miss**, since pytest
never collects them: a mandatory-FK migration landing without updating them surfaces only as a runtime
failure the next time someone runs one. There are currently **16** `qa_create_*.py` commands in
`freedom_ls/qa_helpers/management/commands/` (the earlier research said 8 — that count is stale);
around five use the affected factories directly.

**QA data:** seed two Organisations — "RPAS Training" using `RT-logo.webp` from this directory, and a
second with no logo at all — so both the logo path and the monogram fallback are exercised in the same
run.

## 11. Testing

### 11.1 Cross-organisation isolation

The core guarantee: **two Organisations under one Site, a user with a role on Organisation A only, and
assertions that every educator list view, detail view and HTMX partial returns nothing — or 404 — for
Organisation B.**

The structural precedent is the existing cross-*site* isolation test
(`educator_interface/tests/test_course_visibility_and_interest.py:58-80`), generalised from "other
site" to "other organisation".

Every test touching a site-aware model takes the `mock_site_context` fixture
(`freedom_ls/conftest.py:106-135`), which establishes the ambient site that `SiteAwareFactory` and the
site-aware managers read; objects belonging to that ambient site never pass `site=` explicitly. A test
that deliberately constructs data on a *second* Site — the cross-site isolation tests, and the §11.3
multi-Site migration test — still takes the fixture for the ambient site and passes `site=other_site`
only on the factory calls for the foreign site, exactly as the cited precedent does
(`CourseFactory(site=other_site)`). Those two rules are the same rule: the fixture is mandatory, and
`site=` is set only to cross a boundary on purpose, never to stand in for the fixture.

Organisation scope needs no equivalent fixture: it comes from the resolved URL, not a second
thread-local. That is a benefit of the URL design, not an accident.

These tests stay **unmarked** in the FLS marker taxonomy — they assert a contract every downstream
install needs, so they must remain portable.

### 11.2 Coverage of the whole educator surface

A test that enumerates every organisation-scoped educator entry point and asserts each one denies a
foreign organisation. The load-bearing part is asserting the enumeration is **non-empty and grows with
the interface**: that converts "did we remember to test the new view" from a code-review habit into a
CI failure.

**Enumerate `interface_config`, not `urlpatterns`.** The idea called this a "URLconf-enumerating
test", but §5 establishes there is exactly **one** URL pattern behind the whole educator interface — a
catch-all `re_path` — so walking `urlpatterns` yields a single entry and proves nothing. The real
surface is `educator_interface.views.interface_config` (`views.py:1032-1034`), the
`{url_name: ListViewConfig}` mapping that `panel_framework._resolve_path` walks. The test builds
`path_string` values from it — the section list, a detail path per config with a seeded instance, and
the `__panels` / `__tabs` / `__actions` segments each config declares — and asserts every one of them
404s for an organisation the user cannot access.

This enumeration is what §14.5's guarantee actually rests on, and it grows automatically when a config
gains a tab, a panel or an action.

A parallel test asserts every production `ListViewConfig` either defines its own `check_access` or
declares `check_access_exempt_reason` (§4.3) — so no config silently inherits deny-by-default and
404s in production, and no config quietly gains a permissive override without a declared marker.

**Enumerate the configs from the educator interface's registered config mapping, not from
`ListViewConfig.__subclasses__()`.** There are only three production configs
(`educator_interface/views.py:757`, `:769`, `:1024`), but eight-plus test-only subclasses live in
`panel_framework/tests/` (`stub_panels.py:129`, `test_breadcrumbs.py`, `test_menu_items.py`,
`test_instance_dropdown.py`). A subclass walk would sweep those in and fail for reasons that say
nothing about production authorisation.

### 11.3 Migration behaviour

The migration test asserts: one Organisation per Site, correct backfill, and no cross-site
contamination.

**The backfill callable lives in an importable module and the migration file is a thin wrapper around
it.** Tests import that callable and run it against seeded multi-Site data using the real app
registry. This needs no new dependency, no migration harness, and runs fast.

**The test must disconnect the §9.5 `post_save` receiver while seeding.** Otherwise every seeded Site
arrives already carrying an Organisation, "one Organisation per Site" passes without the backfill
having done anything, and the test asserts the signal rather than the migration. Disconnect it for the
seeding step, run the backfill callable, then assert. A second, separate test covers the receiver's
own behaviour (§14.4).

The trade-off, stated: this tests the backfill logic, not Django replaying the migration graph. That
is the right balance here — there is no existing precedent in the repo for testing a `RunPython`
migration's behaviour (the only migration-adjacent test,
`contrib/conformance/test_migrations.py`, is a schema-drift probe), so this establishes the pattern
rather than importing a dependency downstream projects would inherit. If migration-replay coverage
becomes necessary later, `django-test-migrations` can be added without changing how the backfill is
written.

### 11.4 Other required coverage

- Logo validation: each rejection path (bad extension, SVG renamed to `.png`, oversized dimensions,
  oversized file, corrupt bytes, decompression bomb) and the reference asset passing.
- `Organisation.initials`: two-token, single-token, and no-alphabetic-characters cases.
- Logo resolution in the player: cohort registration wins over individual registration; no
  registration means no logo; the duplicate-registration tiebreak.
- Slug collisions: two Organisations whose names slugify identically.
- An educator holding only per-cohort guardian grants and no organisation role can still enter the
  educator interface and sees exactly their cohorts (the §4.4 lock-out risk).

## 12. Decisions and rationale

1. **`Organisation` lives in a new app**, `freedom_ls/organisations/`, with
   `label = "freedom_ls_organisations"` per the convention in every other `apps.py`. Added to
   `INSTALLED_APPS` in `config/settings_base.py` immediately before `"freedom_ls.student_management"`.
   (Note: that file is only *approximately* dependency-ordered — `site_aware_models` is currently
   listed after one of its own consumers — so the placement is about grouping with
   student-management-adjacent apps, not about a strict invariant.)

2. **The new app depends on `site_aware_models` only** — the same floor as `student_management` — plus
   `django.contrib.sites`, which is not an FLS app and does not appear in the graph. New runtime
   edges: `student_management → organisations`, `educator_interface → organisations`,
   `student_interface → organisations`, `qa_helpers → organisations`.

   Two apps deliberately gain **no** edge. `panel_framework` — its `check_access` hook is generic and
   never mentions Organisation. And `site_aware_models`, which today has zero outgoing edges and stays
   that way: that is why the default-Organisation-for-a-new-Site logic is a receiver owned by the
   `organisations` app rather than an edit to `create_site` (§9.5).

   These must be declared up front for `/fls-dev:plan_structure_review`, and `docs/app_structure.md`
   regenerated with `/ds:app_map`; that file is generated, never hand-edited.

3. **Organisation roles need no new model and no new dependency**, per §4.2. This resolves the "new
   app adds a cross-app dependency" worry that opened this question: `ObjectRoleAssignment` reaches
   Organisation through a `GenericForeignKey` and `assign_object_role` never imports the target class.

4. **A person can hold roles on several Organisations at once.** This is what makes the switcher worth
   building, and it needs no schema change (§4.2).

5. **The default Organisation is permanent and first-class**, not a migration scaffold. For a Site that
   never adds a second one, it is simply "the organisation" and never needs cleaning up. Consequently
   v1 admin ships create / rename / upload logo / assign staff only, and refuses deletion. Docebo's
   post-toggle migration pain — manual CSV cleanup of legacy multi-branch users
   (`research_lms_school_modelling.md`) — is the cautionary case: loosening later is easy, tightening
   later is not.

6. **Every new Site gets a default Organisation via a `post_save` receiver owned by the `organisations`
   app** — not via an edit to `create_site`, which would invert the dependency graph (§9.5).

7. **The name is "Organisation", not "School".** LearnWorlds uses "School" for something
   architecturally much closer to FLS's *Site* (own domain, full white-label), so "School" one level
   under "Site" invites the wrong mental model. "Organisation" also covers the non-school customers FLS
   serves — companies and training providers. British spelling is deliberate and matches the codebase,
   which already uses `colour` in Python identifiers.

8. **The slug follows the existing mechanism**, and `get_unique_slug` moves to `site_aware_models`
   (§3.3).

9. **This spec defines the `panel_framework` authorisation hook** rather than waiting for
   `critical_security_fixes` or building an organisation-only mechanism beside it (§4.3). That spec is
   still unstarted in `spec_dd/1. next/`, and `panel_framework` has no authorisation surface of any
   kind today — so there is nothing to plug into, and building organisation authorisation
   independently would either duplicate whatever lands later or leave organisations exempt from it.
   Defining a generic, deny-by-default hook here is the smallest thing that closes the organisation
   boundary properly and gives the security work its seam.

10. **The organisation segment prefixes the whole educator interface**, including unscoped sections
    (§5).

11. **Menu semantics rather than listbox semantics** for the switcher (§6.2).

12. **No public-read storage carve-out** (§8.4).

13. **404, not 403**, for both unknown and unauthorised organisation slugs (§4.3).

## 13. Non-goals for this cut

Stated explicitly so they are deferrals, not gaps.

- **No delete and no merge.** Follows from Decision 5. Nothing has to repoint cohorts and
  registrations or resolve name collisions, and single-organisation Sites never carry
  multi-organisation cleanup machinery.
- **No nested organisations.** Flat is a legitimate choice — Moodle Workplace and TalentLMS both ship
  flat. The only thing a tree buys is inherited staff access ("admin over a region"). If that is ever
  needed the schema change is cheap and additive; the cost is every scoping query becoming "or
  descendants". **This is why organisation scoping lives behind the §4.4 query helpers** — it keeps a
  future change localised.
- **No organisation membership object.** A learner's organisation comes from their registrations.
  Docebo tried permissive multi-org membership and walked it back to single-org-by-default; loosening
  later is easy, tightening later generated real customer cleanup work.
- **No per-organisation domain or subdomain.** The one branding axis that is genuinely expensive to
  retrofit, and every product that has it treats it as premium.
- **No per-organisation colours or theme.** If added later, follow Canvas's inheritance model — an
  organisation overrides only what it sets.
- **No organisation branding in emails or certificates.**
- **No search, recents or favourites in the switcher.** A flat list is right for the 2–5 organisations
  expected. Revisit at roughly 10+.
- **No EXIF stripping** (§8.3), for the stated reason.
- **Courses, course interest, applications and recommendations stay unscoped** (§6.4).
- **The unguarded Courses list is not fixed here** (§6.4) — it belongs to `critical_security_fixes`,
  which this spec's hook enables.
- **`create_site.py`'s missing `site.save()` is not fixed here** (§9.5).

## 14. Success criteria

The feature is done when all of the following hold.

**Data and migration**

1. `migrate` on a database with existing Sites, cohorts and registrations completes with no manual
   steps, and afterwards every Site has exactly one Organisation named after it, every cohort and
   registration points at the Organisation for its own Site, and no row crosses a Site boundary.
2. Re-running the backfill migration after a simulated partial apply produces no duplicate
   Organisations.
3. Both narrowed constraints apply cleanly to pre-existing data.
4. A Site created after the migration — via `create_site`, the Django admin, or `SiteFactory` — comes
   out with exactly one Organisation, identical in shape to one the migration would have produced, and
   re-saving that Site does not create a second.

**Authorisation**

5. A user with a role on Organisation A only receives 404 — never a 403, never a partial page — for
   every educator list view, detail view and HTMX partial belonging to Organisation B, verified by the
   `interface_config`-enumerating test of §11.2.
6. An educator holding only per-cohort guardian grants and no organisation role can still enter the
   educator interface and sees exactly the cohorts they hold grants on.
7. A `ListViewConfig` subclass with no `check_access` override serves no detail views, and a
   `check_access` reached with no authenticated user or no resolved organisation raises `Http404`
   rather than `AttributeError`.
8. Every permissive `check_access` override declares `check_access_exempt_reason` and carries a TODO
   naming `critical_security_fixes`.

**Educator interface**

9. The switcher shows the current organisation's name at all times, and the label sits in the same
   place whether the user has one organisation or several.
10. Switching on a list page reloads it in place for the new organisation; switching on a detail page
    for an object outside the new organisation redirects to the equivalent list with an inline notice.
    Neither path produces a bare 404.
11. Two browser tabs can sit on two different organisations simultaneously, and each keeps showing its
    own data after either is refreshed.
12. Keyboard-only operation of the switcher works end to end, the current organisation is exposed via
    `aria-checked`, and the change is announced through the live region after the content swap.

**Student interface**

13. A learner registered through a cohort sees that cohort's organisation logo in the course outline
    header; one registered individually sees their registration's organisation; one with no
    registration sees no logo.
14. `RT-logo.webp` renders legibly on **both** shipped themes, at a capped width, visually subordinate
    to the site's own branding.
15. An organisation with no logo shows the monogram; "RPAS Training" yields "RT".
16. The logo lookup adds no N+1 query to the player.

**Management and quality**

17. An admin can create, rename, upload a logo for, and assign staff to an Organisation; the delete
    action is unavailable.
18. Every rejection path in §8.3 is covered by a test, and `RT-logo.webp` uploads successfully.
19. `uv run pytest` passes, including all four apps whose factories changed and all 16 QA seeding
    commands running without error.
20. `docs/app_structure.md` is regenerated and shows only downward edges.

## 15. Known risks

1. **`reverse()` blast radius.** Every URL construction into `educator_interface` gains a kwarg.
   Missing one produces a `NoReverseMatch` at render time — loud, but only on the page that hits it.
   Bounded and greppable, because the whole interface has a single URL name (§5): sweep the ~20
   `educator_interface:interface` references systematically rather than fixing them as they break.
2. **Duplicate registrations** (§3.5). The most likely source of a post-upgrade production 500, and
   the least likely to be caught by tests, because it only manifests on multi-organisation Sites which
   no existing test constructs. The audit is mandatory.
3. **Deny-by-default `check_access`** changes behaviour for any downstream project that has defined
   its own `ListViewConfig` subclass — those will start 404ing on detail views until they implement
   the hook. This is correct (they were unguarded), but it is a breaking change and belongs
   prominently in the upgrade notes.
4. **`get_instance_view` changes signature** (§4.3), gaining a `request` argument. A downstream
   subclass that overrides it breaks loudly at call time rather than silently, but it is a second,
   independent breaking change to the same class and must be called out separately from risk 3 — a
   downstream that implements `check_access` and stops there will still be broken.
4. **Signed logo URLs are not cacheable** (§8.4). Accepted; revisit only if logo rendering moves to an
   unauthenticated surface.
5. **The switcher closes on window scroll**, inherited from `c-dropdown-menu` (§6.2). Known, tracked
   by the existing `@claude` comment, likely to be noticed in QA.
