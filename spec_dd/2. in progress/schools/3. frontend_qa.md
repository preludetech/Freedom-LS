# Frontend QA: Organisations

Browser QA for the Organisations feature. Every step below is a manual browser check — nothing here is
covered by the automated suite.

---

## 0. Setup

### 0.1 Start the server

```bash
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL for everything below: `http://127.0.0.1:$PORT`

Substitute the real port number wherever this document writes `$PORT`.

### 0.2 Credentials

From `.claude/fls-dev/config.md`:

- **Admin / superuser:** `demodev@email.com` / `demodev@email.com`

Other accounts are created in §0.4. Log out between personas — several checks depend on *who* you are.
Use a private/incognito window (or a second browser profile) when a step needs two personas signed in
at once.

### 0.3 Migrate

```bash
uv run python manage.py migrate
```

This runs the six-step Organisation rollout against the dev database. **Watch the output.** It should
complete with no manual steps and no errors. If the validation migration raises its `RuntimeError`,
stop and read the message — that is the safety net firing, and it means the backfill did not cover
everything.

### 0.4 Test data

Ask the `fls-dev:qa-data-helper` agent to create it, or run the QA seeding commands. You need:

| Object | Detail |
| --- | --- |
| Organisation **"RPAS Training"** | logo = `RT-logo.webp` (in the spec directory) |
| Organisation **"Northside"** | **no logo at all** |
| A third organisation, e.g. **"Southgate"** | no logo; used only as the "you have no access" target |
| Cohort **"Year 9 Maths"** in RPAS Training | with 2–3 student members |
| Cohort **"Year 9 Maths"** in Northside | **same name, different organisation** — this proves the narrowed uniqueness constraint |
| Cohort **"Southgate Only"** in Southgate | with at least one member |
| Educator **`org.educator@example.com`** | `organisation_staff` role on **both** RPAS Training and Northside; **no** role on Southgate |
| Educator **`single.org@example.com`** | `organisation_staff` role on RPAS Training **only** |
| Educator **`legacy.educator@example.com`** | **no** organisation role at all; a per-cohort guardian `view_cohort` grant on "Year 9 Maths" (RPAS Training) only |
| Educator **`no.access@example.com`** | no organisation role, no cohort grants |
| Learner **`cohort.learner@example.com`** | member of "Year 9 Maths" (RPAS Training), which is registered for a course |
| Learner **`solo.learner@example.com`** | an individual `UserCourseRegistration` in **Northside** for a course, no cohort |
| Learner **`no.reg.learner@example.com`** | logged in, viewing a course they reached without any registration |

All of the above sit on the **same Site**. Organisations are not a security boundary — everything here
is about scoping within one Site.

## 1. Admin: organisation management

**Persona: admin.** Go to `http://127.0.0.1:$PORT/admin/`.

### 1.1 The Organisation admin renders

1. Find **Organisations** in the admin index and open the changelist.
2. **Expect:** the list shows Name and Slug columns, and lists RPAS Training, Northside and Southgate.
3. **Expect:** the page is styled with the normal unfold admin theme — sidebar, dark/light styling,
   the usual admin chrome. An unstyled, plain-Django-looking page means the guardian/unfold MRO is
   wrong. This is the single most likely thing in the feature to be broken; look carefully.

### 1.2 Create

1. Click **Add Organisation**.
2. **Expect:** the form shows **Name** and **Logo**. It must **not** show a **Site** field.
3. **Expect:** the **Slug** field is visible and **read-only** — never editable, never absent. (A slug
   listed in `readonly_fields` but left out of `fields` silently disappears, so its presence is worth
   checking rather than assuming.)
4. Enter name `Westbrook` and save.
5. **Expect:** saved, and the changelist shows slug `westbrook`.

### 1.3 Slug collision

1. Add another Organisation named `West brook` (note the space — it slugifies to `west-brook`, so try
   `Westbrook.` with a trailing full stop instead, which slugifies to `westbrook`).
2. **Expect:** it saves, and its slug is `westbrook-2`, not a duplicate and not an error.

### 1.4 Name uniqueness

1. Add another Organisation named exactly `Westbrook`.
2. **Expect:** a validation error naming the uniqueness problem — not a 500, not an unhandled
   `IntegrityError` traceback.

### 1.5 Rename does not change the slug

1. Open `Westbrook` and rename it to `Westbrook Academy`. Save.
2. **Expect:** the name changes; **the slug stays `westbrook`**. A slug that changes on rename would
   break every open tab and bookmark.

### 1.6 Delete is unavailable

1. Open any Organisation's change page.
2. **Expect:** there is **no** Delete button.
3. On the changelist, select an Organisation and open the actions dropdown.
4. **Expect:** no "Delete selected organisations" action.
5. Try navigating directly to `.../admin/freedom_ls_organisations/organisation/<id>/delete/`.
6. **Expect:** 403 or a permission-denied page — not a confirmation screen.

### 1.7 Assign staff

1. Open RPAS Training. Find the **Object permissions** link/button (guardian's UI).
2. **Expect:** the object-permissions page renders, styled, with a user lookup.
3. Grant a test user object permissions on this Organisation.
4. **Expect:** it saves and shows the granted permission on reload.

### 1.8 Logo upload — the happy path

1. Open Northside, upload `RT-logo.webp` (from the spec directory), save.
2. **Expect:** it saves. Reopen and confirm the file is attached and the stored filename is based on
   the organisation's **id**, not the uploaded filename — the link should look like
   `organisations/<uuid>.webp`, with no trace of `RT-logo`.
3. **Then remove it again** — Northside must have no logo for §4.

### 1.9 Logo upload — rejection paths

Try each of these on any Organisation. Every one must produce a **field-level validation error naming
the actual problem and the actual limit**, and must not save. None may produce a 500 or a traceback.

| Upload | Expect |
| --- | --- |
| A `.gif`, `.bmp` or `.txt` file | Rejected on extension; message names the allowed formats |
| A real `.svg` file **renamed to `.svg`** | Rejected on extension |
| A real `.svg` file **renamed to `.png`** | Rejected on **format** — this is the one that proves the byte-level check works, not just the filename filter |
| A PNG larger than 4000×4000px | Message names the actual dimensions and the 4000×4000 limit |
| A 1×1px PNG | Rejected as too small; message names the 64×32 minimum |
| A valid-format image over 2 MiB | Rejected on file size; message names the 2 MB limit |
| A `.png` whose bytes are truncated/garbage | "not a readable image", not a traceback |

To make an oversized image quickly:

```bash
uv run python -c "from PIL import Image; Image.new('RGB', (5000, 5000), 'white').save('/tmp/big.png')"
```

**Also check:** after a *rejected* upload, the form re-renders with the error and the organisation's
**existing** logo is unchanged — a failed upload must not clear a good logo.

## 2. Educator interface: URLs and access

### 2.1 Bare `/educator/` redirects

**Persona: `org.educator@example.com`** (roles on RPAS Training and Northside).

1. Go to `http://127.0.0.1:$PORT/educator/`.
2. **Expect:** redirected to a URL of the shape
   `/educator/organisations/<slug>/cohorts` — the address bar must show a concrete organisation slug.
3. Note which organisation it chose.

### 2.2 The last-selected organisation is remembered, and re-authorised

1. Still as `org.educator`, switch to **Northside** (see §3), then go back to bare `/educator/`.
2. **Expect:** it lands on Northside.
3. Log out. Log in as **`single.org@example.com`** (RPAS Training only) and go to `/educator/`.
4. **Expect:** it lands on **RPAS Training**, not on Northside. A remembered slug must never grant
   access — this is the re-authorisation check.

### 2.3 A user with no organisations gets a 404

**Persona: `no.access@example.com`.**

1. Go to `/educator/`.
2. **Expect:** 404. Not a 500, not an empty interface, not a redirect loop.

### 2.4 Unknown and unauthorised slugs both 404 — identically

**Persona: `org.educator@example.com`.**

1. Visit `/educator/organisations/does-not-exist-at-all/cohorts`.
2. **Expect:** 404.
3. Visit `/educator/organisations/southgate/cohorts` (a **real** organisation this user has no role on).
4. **Expect:** 404 — **the same 404**, not a 403 and not a differently-worded page. Compare the two
   pages side by side; if the "real but unauthorised" case looks different, organisation names on the
   Site are enumerable.
5. Visit `/educator/organisations/Not A Slug!/cohorts` (invalid characters).
6. **Expect:** 404 from URL routing.

### 2.5 Every in-app link carries the organisation

**Persona: `org.educator@example.com`**, in RPAS Training.

1. From the cohorts list, click through to a cohort detail page.
2. **Expect:** the address bar keeps `/organisations/rpas-training/`.
3. Click every sidebar section (**Cohorts**, **Users**, **Courses**) in turn.
4. **Expect:** each URL keeps the organisation segment — **including Courses**, which is not
   organisation-scoped but still carries the slug.
5. Click a breadcrumb back to a list.
6. Click a cohort name from inside the **Users** table, and a user name from inside a **cohort**
   detail panel.
7. **Expect:** every one of these navigates correctly. A missing `organisation_slug` kwarg surfaces as
   a `NoReverseMatch` **500 on the page that builds the link**, so a link that renders at all is
   probably fine — the failure mode is a page that won't load, not a bad link.
8. Open the **user menu** in the header bar and click the educator-interface link.
9. **Expect:** it lands on `/educator/` and redirects as in §2.1 — not a `NoReverseMatch`.

### 2.6 Browser navigation

1. Navigate Cohorts → a cohort → Users → a user.
2. Press **Back** four times.
3. **Expect:** each step returns to the previous page with the correct organisation and correct
   content. The URL and the displayed data must never disagree.
4. Press **Forward** back through the same steps. Same expectation.
5. On any deep page, press **Reload**.
6. **Expect:** the same page re-renders identically (this is the deep-link check).

## 3. The organisation switcher

### 3.1 It is always present and always names the current organisation

**Persona: `org.educator@example.com`**, in RPAS Training.

1. Look at the **top of the left-hand panel**, above the section nav.
2. **Expect:** a control showing **"RPAS Training"**. Never a placeholder like "Select organisation".
3. Navigate to Users, then Courses, then a cohort detail.
4. **Expect:** the switcher stays in place and keeps naming RPAS Training on every page.

### 3.2 One organisation ⇒ static label in the same place

**Persona: `single.org@example.com`** (RPAS Training only).

1. Load the educator interface.
2. **Expect:** "RPAS Training" appears **in the same position**, as **static text** — no dropdown
   affordance, no chevron, nothing clickable.
3. Click on it.
4. **Expect:** nothing happens. No dropdown, no navigation, no console error.

### 3.3 Switching on a list page

**Persona: `org.educator@example.com`**, on the RPAS Training **Cohorts list**.

1. Open the switcher.
2. **Expect:** it lists RPAS Training and Northside. **Southgate must not appear** — the switcher must
   never offer an organisation the user cannot enter.
3. Click **Northside**.
4. **Expect:**
   - the cohorts list reloads in place (no full page flash),
   - the address bar becomes `/educator/organisations/northside/cohorts`,
   - **the switcher label itself now says Northside** — look at this specifically. Main content,
     breadcrumbs and sidebar nav are swapped by an existing mechanism; the switcher's own label needs
     its own out-of-band fragment. If that was missed, the label keeps saying "RPAS Training" while
     Northside's data is on screen — the exact chrome-disagrees-with-data failure this feature exists
     to prevent, and it looks subtle.
   - the list shows **Northside's** "Year 9 Maths" and not RPAS Training's.
5. **Expect:** the dropdown panel has **closed**. It sits outside the swapped region, so nothing closes
   it automatically — a panel left hanging open over the new content is a real defect here.
6. Reload the page.
7. **Expect:** still Northside, same data.
8. Switch back to RPAS Training and confirm the label updates in that direction too.

### 3.4 Switching on a detail page for an object in the *new* organisation

Both organisations have a cohort called "Year 9 Maths", but they are different objects.

1. In RPAS Training, open the "Year 9 Maths" cohort detail page.
2. Switch to Northside.
3. **Expect:** you are **not** left on a page showing RPAS Training's cohort under a Northside label.
   Either the Northside equivalent loads or you land on the Northside cohorts list with a notice — but
   the switcher label and the displayed data must **never** disagree. This is the core promise of the
   feature; look hard.

### 3.5 Switching on a detail page for an object *outside* the new organisation

1. In RPAS Training, open a cohort that has no Northside counterpart (or any cohort detail page).
2. Switch to **Northside**.
3. **Expect:**
   - **no bare 404**,
   - you land on the Northside **cohorts list**,
   - a toast/inline notice appears saying something like "Switched to Northside — that cohort isn't in
     this organisation",
   - the address bar shows the Northside **cohorts list** URL, not the old detail URL.
4. Press **Back**.
5. **Expect:** you return to the RPAS Training cohort detail, correctly rendered.
6. Repeat the whole check starting from a **user** detail page rather than a cohort detail page.

### 3.6 A switch does not disguise unrelated errors

The "that cohort isn't in this organisation" path must fire only for a genuine organisation mismatch,
never for any other reason a page fails to resolve.

1. In RPAS Training, open a cohort detail page and note a working URL.
2. Hand-edit the address bar to a **nonexistent path segment** under the other organisation, e.g.
   `/educator/organisations/northside/not-a-section`.
3. **Expect:** a plain 404.
4. **Expect specifically:** *not* a redirect to a list page with a "switched to Northside — that isn't
   in this organisation" notice. A message like that on a URL that simply does not exist means the
   switch handler is catching every 404 and mislabelling real errors.

### 3.7 The switch is *not* how you get a 404

1. From step 3.5's end state, manually paste a *foreign* cohort's detail URL under Northside into the
   address bar (take a cohort id from RPAS Training and put it in a Northside URL).
2. **Expect:** a plain 404. This is correct — a hand-edited URL gets a 404; a switch never does.

### 3.8 Two tabs, two organisations

This is the reason the organisation lives in the URL rather than the session.

1. Open **tab A** on `/educator/organisations/rpas-training/cohorts`.
2. Open **tab B** on `/educator/organisations/northside/cohorts`.
3. In tab B, click into a Northside cohort.
4. Switch back to **tab A** and press **Reload**.
5. **Expect:** tab A still shows **RPAS Training** in the switcher and RPAS Training's cohorts. If tab
   A has silently become Northside, the scope has leaked into the session.
6. Reload tab B. **Expect:** still Northside.
7. Switch tab A to Northside, then reload **tab B** (which is already Northside) and then reload tab A.
   **Expect:** both are Northside, each independently correct.

### 3.9 Keyboard and screen-reader behaviour

**Persona: `org.educator@example.com`.**

1. Load the educator interface. Press **Tab** repeatedly.
2. **Expect:** the switcher trigger receives a **visible focus ring** before the section nav.
3. Press **Enter** (or **Space**) on the trigger.
4. **Expect:** the menu opens.
5. Press **Tab** / arrow keys to move between the options.
6. **Expect:** focus moves visibly between them.
7. Press **Escape**.
8. **Expect:** the menu closes and focus returns to the trigger.
9. Reopen and press **Enter** on Northside.
10. **Expect:** the switch happens — keyboard-only operation must complete the whole flow with no mouse.

Then inspect the DOM (devtools) with the menu open:

11. **Expect:** the trigger has `aria-haspopup="menu"` and `aria-expanded="true"`.
12. **Expect:** each option has `role="menuitemradio"`; the **current** organisation has
    `aria-checked="true"` and the others `aria-checked="false"`.
13. **Expect:** a `<div id="scope-announcer" class="sr-only" aria-live="polite" aria-atomic="true">`
    exists, and it is a **sibling of `#main-content`, not inside it**.
14. Perform a switch and watch that element in the devtools DOM inspector.
15. **Expect:** its text content changes to "Now viewing Northside" (or similar) **and the element
    itself is not removed and re-added** — a live region that gets destroyed and recreated is missed by
    some screen readers. Watch for the element flashing/re-highlighting in the inspector.

If a screen reader is available (NVDA, VoiceOver, Orca), do the switch with it running and confirm the
change is announced.

### 3.10 Known behaviour: the menu closes on scroll

1. Open the switcher and scroll the window.
2. **Expect:** the menu closes.

This is inherited from the shared `c-dropdown-menu` component and is **known and tracked** by an
existing `@claude` comment. Note how disruptive it feels in this position (top of a scrollable sidebar)
in the QA report — do **not** file it as a switcher bug and do **not** work around it locally.

## 4. Cross-organisation isolation

This is the security-relevant section. **Persona: `org.educator@example.com`** unless stated.

### 4.1 Lists show only the current organisation

1. In RPAS Training, look at the **Cohorts** list.
2. **Expect:** only RPAS Training's cohorts. Northside's "Year 9 Maths" must **not** appear, even
   though it has the same name.
3. Look at the **Users** list.
4. **Expect:** only users who are in RPAS Training cohorts. A learner who is only in a Northside cohort
   must not be listed.
5. Switch to Northside and repeat both.
6. **Expect:** the mirror image. No cohort or user appears in both lists unless it genuinely belongs to
   both organisations.

### 4.2 Foreign detail URLs 404

1. From the Northside cohorts list, copy a Northside cohort's id out of its detail URL.
2. Paste it into an **RPAS Training** URL:
   `/educator/organisations/rpas-training/cohorts/<northside-cohort-id>`
3. **Expect:** 404.
4. Do the same with a **user** id: a user who is only in Northside, requested under RPAS Training.
5. **Expect:** 404.

### 4.3 Foreign HTMX partials 404

Detail pages load panels and tabs via HTMX. Those are separate requests and must be scoped too.

1. Open a Northside cohort detail page with the browser devtools **Network** tab open.
2. Note the URLs of the panel/tab requests — they contain `__panels`, `__tabs` or `__actions`.
3. Copy one, change `northside` to `rpas-training` in the path, keep the Northside object id, and open
   it directly in the address bar.
4. **Expect:** 404.
5. Repeat for a `__tabs` URL and an `__actions` URL.
6. **Expect:** 404 for each. A partial that renders foreign data is the exact leak this feature exists
   to prevent.

### 4.4 The Southgate organisation is fully invisible

1. Confirm Southgate never appears in the switcher.
2. Try `/educator/organisations/southgate/cohorts`, `/educator/organisations/southgate/users` and
   `/educator/organisations/southgate/courses`.
3. **Expect:** 404 for all three.

## 7. Student course player co-branding

### 7.1 Cohort learner sees the cohort's organisation logo

**Persona: `cohort.learner@example.com`** (member of RPAS Training's "Year 9 Maths").

1. Open a course they are registered for through the cohort, and enter the player.
2. Find the **course outline** panel (left side on desktop).
3. **Expect:** the **RPAS Training logo** appears in the outline header, between the course title and
   the progress bar.
4. **Expect:** it is **small and clearly secondary** to the site's own header branding. If your eye
   goes to the organisation logo before the site logo, it is too prominent.
5. **Expect:** it sits inside a **light opaque chip** — a padded box with a solid background, not a
   bare transparent image.
6. **Expect:** it is **not a link** — hovering shows no pointer cursor, clicking does nothing.
7. **Expect:** it has a sensible `alt` naming the organisation (check in devtools).

### 7.2 It survives player navigation

1. Click **Next** to move to the next course item.
2. **Expect:** the logo is still there, unchanged, and the outline's current-item highlight has moved.
3. Click **Previous**.
4. **Expect:** same. The outline region is OOB-swapped on these, so a logo that vanishes or duplicates
   after a Next/Previous is a real bug.
5. Do this five or six times in a row.
6. **Expect:** exactly one logo chip, every time — never two stacked.

### 7.3 Both themes

The two shipped themes put the header on visually different backgrounds — one is a solid brand colour,
the other is white. `RT-logo.webp` is a near-black mark on a **transparent** background, so a chip that
is only padding (no opaque fill) makes it vanish on the dark-header theme.

1. Switch the site to the **`default`** theme and reload the player.
2. **Expect:** the logo is clearly legible.
3. Switch to the **`first_class`** theme and reload.
4. **Expect:** the logo is clearly legible **here too**.
5. **Expect:** on both, the chip's background is visibly distinct from the surrounding header, and the
   mark has enough contrast to read.
6. If the site supports a dark/light preference, check both on each theme.

### 7.4 Width is capped

1. Upload a deliberately wide, banner-shaped logo to RPAS Training (e.g. 3000×300px) via the admin.

   ```bash
   uv run python -c "from PIL import Image; Image.new('RGBA', (3000, 300), (0,0,0,0)).save('/tmp/wide.png')"
   ```

2. Reload the player.
3. **Expect:** the chip scales the logo **down** to a capped width. The outline header must not grow
   wider, must not overflow, and must not push the progress bar off-screen or cause horizontal
   scrolling.
4. Also try a tall, narrow crest shape (e.g. 300×3000px).
5. **Expect:** it is height-constrained and does not stretch the header vertically.
6. Restore `RT-logo.webp` afterwards.

### 7.5 Monogram fallback

**Persona: `solo.learner@example.com`** (individual registration in **Northside**, which has **no**
logo).

1. Enter the player for their registered course.
2. **Expect:** the outline header shows **"NO"** — the initials monogram for "Northside" (single token
   ⇒ first two letters).
3. **Expect:** it is styled like the existing user-initials badge in the header user menu — same shape
   and visual weight, so mixed lists stay consistent.
4. In the admin, rename Northside to `Northside Academy` and reload the player.
5. **Expect:** the monogram becomes **"NA"** (two tokens ⇒ first letter of each).
6. Rename it to `123` (no alphabetic characters) and reload.
7. **Expect:** a **generic icon**, not an empty box, not "12", not a crash.
8. Rename it back to `Northside`.

Also confirm the reference case explicitly: RPAS Training with its logo *removed* should show **"RT"**.

### 7.6 No registration, no logo

**Persona: `no.reg.learner@example.com`.**

1. Open a course they can view but have no registration for.
2. **Expect:** the outline header shows the course title and progress bar and **no logo, no monogram,
   no empty chip and no gap where one would be**.

### 7.7 Small screens

1. Resize the browser to a narrow width (or use devtools device emulation, ~375px).
2. **Expect:** the outline moves behind a dialog/panel — the logo is no longer permanently on screen.
   This is expected and accepted.
3. Open the outline panel.
4. **Expect:** the logo chip is there, correctly sized, and does not overflow the panel.

### 7.8 No performance regression

1. Open the player with devtools **Network** open (and Django Debug Toolbar if enabled).
2. **Expect:** the query count for a player page is not noticeably higher than before the change —
   the logo lookup should be one extra query, not one per outline item.
3. If the debug toolbar is available, check the SQL panel for a repeated
   `SELECT ... FROM ..._organisation` pattern. Repeated identical organisation lookups mean an N+1.

## 8. Regression sweep

The change touches shared machinery. Walk these even though they are not new.

### 8.1 Existing educator interface still works

**Persona: `org.educator@example.com`**, in RPAS Training.

1. Open a cohort detail and click through **every tab** on it.
2. **Expect:** each tab loads its panels.
3. Use the **search** box on the Users list.
4. **Expect:** results filter, and the organisation is still correct afterwards.
5. **Sort** a sortable column.
6. **Expect:** sorting works and the URL still carries the organisation.
7. **Paginate** through a large cohort's members (use the large-cohort QA data).
8. **Expect:** page 2, 3 … load with the organisation intact.
9. Use a **delete** or other instance action if one is available on a cohort.
10. **Expect:** it works and redirects somewhere sensible within the organisation.

### 8.2 Courses tab is unscoped — and that is intended

1. Go to **Courses** in RPAS Training. Note the list.
2. Switch to **Northside** and go to Courses.
3. **Expect:** the **same** course list. Courses are shared across the Site and are deliberately not
   organisation-scoped in this cut. Confirm the URL still carries the Northside slug even so.
4. **Expect:** the switcher still renders and still says Northside on the Courses page.

### 8.3 Student self-registration still works

**Persona: any learner without a registration for some course.**

1. Find a self-registerable course and click **Register**.
2. **Expect:** registration succeeds and drops you into the player — **not** a 500 from the new
