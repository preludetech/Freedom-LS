## 0. Decisions this plan makes that the spec left open

Two gaps surfaced while reading the code. Both are settled here.

### 0.1 Which Organisation a *self-service* registration gets

`student_interface/views.py:540` creates a `UserCourseRegistration` when a learner clicks "register"
on a course. There is no organisation in scope, and the FK is becoming mandatory.

**Rule: the Site's own Organisation** — the one named after the `Site`, which both the §9.1 backfill
and the §9.5 receiver guarantee exists for every Site. A helper in the new app resolves it:

```python
# freedom_ls/organisations/utils.py
def get_default_organisation(site: Site) -> Organisation:
    """The Organisation named after the Site itself.

    Guaranteed to exist by the backfill migration and the post_save receiver.
    A DoesNotExist here means that invariant was broken out of band — there is
    no supported path to delete an Organisation — so it should surface as an
    error rather than be silently repaired on a learner-facing path.
    """
    return Organisation._base_manager.get(site=site, name=site.name)
```

**A plain `get`, not a `get_or_create`.** The admin refuses deletion (`has_delete_permission` returns
`False`) and both FKs are `PROTECT`, so the only route to a missing default Organisation is a direct
database operation or a shell session — operator error, which should be visible, not silently healed by
a write hidden inside a getter on the self-registration path.

`_base_manager` rather than `objects` for the same reason as §B6: the site-aware manager would AND the
ambient thread-local site onto the lookup.

No new field, no new constraint, deterministic on single- and multi-organisation Sites. An explicit
`is_default` boolean is the natural follow-up if a customer ever needs to point self-registration at a
non-Site-named Organisation; it is additive and can be done later.

### 0.2 `_two_or_one` is shared, not duplicated

`Organisation.initials` (spec §7) needs the same "two Latin letters, else one grapheme" composition as
`User.initials`. That logic lives in `accounts/models.py:23-49` as `_is_latin` / `_two_or_one`.

Importing it would create `organisations → accounts`, which inverts the layering. Duplicating it
violates the repo's extract-rather-than-repeat rule. **Move `_is_latin` and `_two_or_one` into
`freedom_ls/base/initials.py`** and import from both. `base` has zero outgoing edges in
`docs/app_structure.md` (same floor as `site_aware_models`), and `accounts → base` already exists, so
the only new edge is `organisations → base` — downward, and declared in §1 below.

The two `initials` properties stay separate: `User.initials` keeps its email-local-part fallback,
`Organisation.initials` has no email to fall back to.

### A2. Move `get_unique_slug` to `site_aware_models`

Currently at `content_engine/management/commands/content_save.py:193-224`, untyped.

- New home: `freedom_ls/site_aware_models/slugs.py`.
- Add type hints:
  `get_unique_slug(model_class: type[Model], site: Site, base_slug: str, existing_uuid: str | None = None) -> str`.
- Keep the `contextlib.suppress(ValueError, AttributeError)` around the `uuid.UUID(existing_uuid)`
  parse.
- **One behavioural fix, and it is required, not cosmetic.** The body currently queries
  `model_class.objects.filter(site=site, slug=slug)`. For a site-aware model, `objects` is
  `SiteAwareManager`, which ANDs the *ambient thread-local* site onto every queryset
  (`site_aware_models/models.py:43-50`). Whenever the caller passes a `site` that differs from the
  ambient one, the query becomes `site = <ambient> AND site = <argument>` — never true — and the helper
  reports **every** candidate slug as free. Change it to query `model_class._base_manager` instead:

  ```python
  queryset = model_class._base_manager.filter(site=site, slug=slug)
  ```

  The explicit `site=site` filter is what scopes the check; the manager's implicit filter only ever
  narrows it incorrectly. This is strictly more correct for the existing `content_save` caller too, and
  it is what makes the helper safe for the three new callers that legitimately pass a foreign site: the
  §B6 receiver, `OrganisationFactory` under the cross-site testing convention, and the §C3 backfill.
  Without it, a cross-site test that creates two Organisations whose names slugify identically fails
  with an `IntegrityError` instead of getting a `-2` suffix.

  There is one existing precedent for the `_base_manager` escape hatch in this codebase:
  `role_based_permissions/management/commands/sync_role_permissions.py:120-121`.
- `content_save.py` imports it from the new home. Its one call site (`content_save.py:287`) is
  otherwise untouched, and no test imports `get_unique_slug` from `content_save` by name (verified), so
  nothing else moves.

**Test:** the existing `content_save` tests must still pass; add a direct unit test for the helper in
`freedom_ls/site_aware_models/tests/test_slugs.py` covering the collision suffix, the `existing_uuid`
exclusion, and — the case the fix exists for — **a collision on a site that is not the ambient
thread-local site**.

### B3. Logo upload path

```python
def organisation_logo_upload_to(instance: Organisation, filename: str) -> str:
    """Storage path from the pk and the extension only.

    The uploaded filename is never interpolated — that is what prevents path
    traversal, overwrite collisions and leaking the uploader's local paths.
    SiteAwareModel.id defaults at instantiation, so the pk always exists here.
    """
    ext = Path(filename).suffix.lower()
    return f"organisations/{instance.pk}{ext}"
```

This is deliberately stricter than `content_engine.file_upload_handler`
(`content_engine/models.py:565-572`), which interpolates the uploaded stem. Do not copy that shape.
Leaving `content_engine` as-is is a separate change.

Derive `ext` from the **validated** extension allowlist, not blindly from the upload — reject anything
outside `{.png, .jpg, .jpeg, .webp}` before it reaches here (the field validators run first).

### B4. Logo validation

`freedom_ls/organisations/validators.py`. Two layers; the byte-level check is the authoritative one.

```python
ALLOWED_EXTENSIONS = ["png", "jpg", "jpeg", "webp"]
ALLOWED_FORMATS = {"PNG", "JPEG", "WEBP"}
MAX_BYTES = 2 * 1024 * 1024          # 2 MiB
MAX_DIMENSION = 4000                 # px, each axis
MIN_WIDTH, MIN_HEIGHT = 64, 32

validate_organisation_logo_extension = FileExtensionValidator(ALLOWED_EXTENSIONS)


def validate_organisation_logo(file: UploadedFile) -> None:
    if file.size > MAX_BYTES:
        raise ValidationError(
            f"Image file is too large ({file.size / 1024 / 1024:.1f}MB; maximum is 2MB)."
        )

    with warnings.catch_warnings():
        # A DecompressionBombWarning does nothing in production unless it is
        # escalated. MAX_IMAGE_PIXELS stays at Pillow's default — never None.
        warnings.simplefilter("error", Image.DecompressionBombWarning)
        try:
            file.seek(0)
            Image.open(file).verify()      # destroys the object it is called on
            file.seek(0)
            img = Image.open(file)         # re-open on a rewound handle
            width, height = img.size
            image_format = img.format
        except Image.DecompressionBombWarning as err:
            raise ValidationError("Image is too large to process safely.") from err
        except (OSError, Image.UnidentifiedImageError) as err:
            raise ValidationError("File is not a readable image.") from err
        finally:
            file.seek(0)

    if image_format not in ALLOWED_FORMATS:
        raise ValidationError(
            f"Image format {image_format} is not supported. Use PNG, JPEG or WebP."
        )
    if width > MAX_DIMENSION or height > MAX_DIMENSION:
        raise ValidationError(
            f"Image is too large ({width}×{height}px; maximum is 4000×4000px)."
        )
    if width < MIN_WIDTH or height < MIN_HEIGHT:
        raise ValidationError(
            f"Image is too small ({width}×{height}px; minimum is 64×32px)."
        )
```

The three things most likely to be got wrong, called out:

1. **Two `Image.open()` calls with a `seek(0)` between them.** `verify()` is documented as destructive
   to the object it is called on — reading `.size` afterwards on the same object raises.
2. **`format` assertion is what catches an SVG renamed to `.png`.** The extension allowlist is a filter,
   not a boundary. SVG is rejected by both layers: it is XML and can carry `<script>`, `on*` handlers
   and `<foreignObject>` HTML.
3. **`seek(0)` in a `finally`**, so a rejected file leaves the handle where Django expects it.

Error text names the actual problem and the actual limit, not a generic "invalid image".

**EXIF is not stripped** — deliberate. Stripping means re-encoding, and re-encoding a transparent WebP
risks a visible regression in exactly the asset class this feature targets; the usual motivation
(location metadata in personal photos) does not apply to an admin-uploaded corporate logo. Record the
reasoning in a comment on the validator so a later reader sees a choice, not an oversight.

**Tests:** `tests/test_validators.py`, one case per rejection path — bad extension, SVG renamed to
`.png`, oversized dimensions, undersized dimensions, oversized file, corrupt bytes, decompression bomb
— plus the reference asset passing.

**Two copies of `RT-logo.webp`, at named paths.** The repo has no binary-test-fixture convention at all
(verified: no `tests/fixtures/` directory, no image files anywhere under `freedom_ls/`), so this

- **Runtime copy for the QA seeding command (§C6):** `freedom_ls/qa_helpers/fixtures/RT-logo.webp`.

Never read the asset from `spec_dd/` — that directory is workflow scaffolding and does not ship.

### B6. The new-Site receiver

`freedom_ls/organisations/signals.py`:

```python
@receiver(post_save, sender=Site)
def ensure_default_organisation(sender, instance, **kwargs) -> None:
    """Every Site carries an Organisation named after itself.

    A receiver rather than an edit to create_site so site_aware_models keeps
    its zero outgoing edges, and so the admin, the shell and SiteFactory are
    covered too. get_or_create, not the `created` flag: re-saving a Site (a
    domain change, say) must never produce a second Organisation.

    _base_manager throughout: the site-aware manager would AND the ambient
    thread-local site onto the lookup, and the Site being saved is frequently
    not the Site the current request is for.
    """
    Organisation._base_manager.get_or_create(
        site=instance,
        name=instance.name,
        defaults={"slug": get_unique_slug(Organisation, instance, slugify(instance.name))},
    )
```

**`_base_manager`, not `objects`, and this is the subtlest thing in the whole feature.**
`Organisation.objects` is a `SiteAwareManager`, whose `get_queryset` ANDs the ambient thread-local
site onto every lookup (`site_aware_models/models.py:43-50`). `CurrentSiteMiddleware` sets that
thread-local on every request, so when an admin on one host creates a Site for another host — the
normal case in the multi-tenant setup this feature exists for — the lookup half of `get_or_create`
becomes `site = <ambient> AND site = <instance>`, which is never true.

The consequence is worse than a duplicate. The first save "works" (the lookup misses, `create()`
ignores the manager filter and lands the row correctly). The **second** save — exactly the
"re-saving does not create a second Organisation" case — misses the lookup again, attempts another
`INSERT`, and hits `unique_organisation_name_per_site`, raising `IntegrityError` **inside the
`post_save` signal** and failing the entire Site save.

`get_unique_slug` had the identical defect internally; §A2 fixes it at the source, so both halves of
this receiver are safe once that change is in.

`SiteAwareModelBase.save()` only assigns `site` when `site_id` is falsy
(`site_aware_models/models.py:69-76`), so the explicitly-passed `site=instance` is not overwritten.

It does **not** fire during the data migration: `RunPython` uses historical models from
`apps.get_model`, and a receiver registered against the concrete `Site` class does not run for those.
The backfill therefore remains the only thing creating Organisations for pre-existing Sites, and the
two cannot race.

`create_site.py` is not modified. (Its missing `site.save()` at `create_site.py:21-22` is a separate
pre-existing bug — leave it.)

**Tests:** `tests/test_signals.py` — a new Site gets exactly one Organisation; the Organisation lands
on the right Site when a *different* Site is the ambient thread-local one; and, the case that catches
the bug above, **create a Site under a foreign ambient thread-local site and then save it again**,
asserting exactly one Organisation and no `IntegrityError`. A test that only creates once passes
against the broken version.

### B8. `OrganisationAdmin`

```python
@admin.register(Organisation)
class OrganisationAdmin(GuardedSiteAwareModelAdmin):
    list_display = ["name", "slug"]
    search_fields = ["name"]
    readonly_fields = ["slug"]
    fields = ["name", "slug", "logo"]

    def has_delete_permission(self, request, obj=None) -> bool:
        return False

    def save_model(self, request, obj, form, change) -> None:
        if not obj.slug:
            obj.slug = get_unique_slug(
                Organisation, get_cached_site(request), slugify(obj.name),
                existing_uuid=str(obj.pk),
            )
        super().save_model(request, obj, form, change)
```

Slug is generated in the admin save path, not in `Organisation.save()`. A rename does not re-slug —
the slug is a stable URL identifier and re-slugging would break every bookmark and open tab. It is
listed in **both** `fields` and `readonly_fields`: when `fields` is set explicitly, Django renders only
what is listed there, so a field named in `readonly_fields` but omitted from `fields` is silently
dropped from the form.

Staff assignment is guardian's object-permissions page, provided by the base class.

**Tests:** `tests/test_admin.py` — delete action absent; creating an Organisation via the admin
produces a slug; two Organisations with names that slugify identically get distinct slugs.

```python
                fields=["site_id", "organisation", "name"],
                name="unique_cohort_name_per_site",
            )
        ]


class UserCourseRegistration(SiteAwareModel):
    organisation = models.ForeignKey(
        "freedom_ls_organisations.Organisation", on_delete=models.PROTECT
    )
    ...
    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["site_id", "organisation", "collection", "user"],
                name="unique_user_course_registration",
            )
        ]
```

- `PROTECT`, not `CASCADE` — deletion is refused at the admin layer, and `PROTECT` makes that true at
  the database layer too, so a stray `.delete()` from a shell fails loudly.
- **Keep the `"site_id"` spelling** in both constraints. Switching to `"site"` is a separate deliberate
  change per spec §3.4; mixing it into this migration adds drift risk for no benefit. Keep the
  constraint **names** unchanged so anything downstream referencing them by hand still matches.
- `CohortCourseRegistration` gets **no** FK — its organisation is `cohort.organisation`. Same for
  `CohortMembership` and all three deadline models.
- Use the string reference `"freedom_ls_organisations.Organisation"`, not a direct import, to keep the
  import graph clean at module load.

### C2. The migration sequence — six files, never combined

FLS ships as a submodule into downstream projects that run `migrate` against live databases we have
never seen. Separate files mean `showmigrations` tells an operator exactly which step failed.

| # | App | Contents |
| --- | --- | --- |
| 1 | `organisations` | `CreateModel` for `Organisation` |
| 2 | `student_management` | Add `organisation` as a **nullable** FK to both models |
| 3 | `student_management` | `RunPython` backfill |
| 4 | `student_management` | `RunPython` validation |
| 5 | `student_management` | `AlterField` both FKs to `null=False` |
| 6 | `student_management` | `RemoveConstraint` + `AddConstraint` for both constraints |

**The model file is edited twice.** §C1 shows the *final* state — a non-nullable FK. Migration #2 needs
a **nullable** one. So: write both FKs with `null=True` first and generate migration #2; then remove
`null=True` (restoring §C1's code) and generate migration #5. Skipping this and generating from §C1's
code directly makes Django prompt for a one-off default on tables that already have rows — which hangs
a non-interactive run, or bakes a meaningless literal default into a committed migration.

**Pass explicit app labels to every `makemigrations` call** —
`uv run manage.py makemigrations organisations`, `uv run manage.py makemigrations student_management`.
A bare `makemigrations` scans every app and can fold unrelated drift from elsewhere in the tree into one
of these six files.

After all six, run `makemigrations --check --dry-run`. Note what that does and does not prove: it fails
when a migration is **missing**, and says nothing about **extra** files. So also run
`git status freedom_ls/organisations/migrations/ freedom_ls/student_management/migrations/` and confirm
exactly six new files exist, matching the table above one for one.

### C3. The backfill (migration 3)

**The callable lives in an importable module, and the migration file is a thin wrapper** — so §12.1 can
test it directly with no migration harness.

`freedom_ls/student_management/migration_helpers/backfill_organisation.py`, **with an
`__init__.py` beside it**. This is a new sub-package shape for this repo — both existing `RunPython`
precedents define their callables inline — so it is a deliberate deviation, and the `__init__.py` is not
optional: `pyproject.toml`'s `[tool.setuptools.packages.find]` uses plain `find`, which only discovers
packages that have one, so an implicit namespace package would be silently dropped from the
distribution FLS ships downstream.

```python
def backfill_organisation(apps, schema_editor=None) -> None:
    """Give every Site an Organisation named after it, then point every
    cohort and registration on that Site at it.

    apps.get_model throughout: the real save() reads a thread-local request
    that does not exist during migrate. Iterates the Sites that actually
    exist rather than assuming a particular row is present.
    """
    Site = apps.get_model("sites", "Site")
    Organisation = apps.get_model("freedom_ls_organisations", "Organisation")
    Cohort = apps.get_model("freedom_ls_student_management", "Cohort")
    Registration = apps.get_model(
        "freedom_ls_student_management", "UserCourseRegistration"
    )

    for site in Site.objects.all():
        organisation, _ = Organisation.objects.get_or_create(
            site=site,
            name=site.name,
            defaults={"slug": get_unique_slug(Organisation, site, slugify(site.name))},
        )
        Cohort.objects.filter(site=site, organisation__isnull=True).update(
            organisation=organisation
        )
        Registration.objects.filter(site=site, organisation__isnull=True).update(
            organisation=organisation
        )
```

Rules, all load-bearing:

- **`apps.get_model` throughout, never a real model import.**
- **`get_or_create`, not `create`** — idempotent, so a retried partial apply cannot duplicate.
- **Leave `atomic` at its default `True`.** On PostgreSQL that wraps the whole file in one transaction:
  a crash mid-loop rolls back entirely and the migration is not recorded as applied, which is what
  makes a retry safe by construction. At FLS's documented scale (low thousands of rows,
  `docs/product/deployment.md:73-83`) a plain `AlterField(null=False)` is fine — no
  `NOT VALID` CHECK → `VALIDATE` → `SET NOT NULL` dance.
- **`reverse_code=migrations.RunPython.noop`** — not because there is a meaningful undo, but because
  omitting it raises `IrreversibleError` for an operator legitimately rolling back an unrelated later
  migration in the same app.
- **Call the real `get_unique_slug`; do not write a migration-local copy of it.** `apps.get_model`
  returns a historical model carrying Django's plain `models.Manager`, not `SiteAwareManager` — a custom
  manager is only inherited by historical models if it sets `use_in_migrations = True`, and
  `SiteAwareManager` does not (verified repo-wide). Combined with the `_base_manager` fix in §A2, the
  shared helper is correct here, and the backfill already relies on exactly this reasoning one line
  above when it calls `Organisation.objects.get_or_create` on a historical model.

The migration file is:

```python
operations = [
    migrations.RunPython(backfill_organisation, migrations.RunPython.noop),
]
```

### D1. The `organisation_staff` role

Per `role_based_permissions/README.md:141`, the permission strings must be in `registry.py`'s


Then in `role_based_permissions/roles.py`, alongside the existing `SCOPE_OBJECT` roles
(`roles.py:38-66`):

```python

    display_name="Organisation Staff",
    assignment_scope=SCOPE_OBJECT,
    lti_role=None,
    description="Access to every cohort and registration within an organisation.",
    permissions=frozenset({"freedom_ls_organisations.view_organisation"}),
```

No new model and no new dependency. `ObjectRoleAssignment`'s `unique_object_role_per_user` constraint
is on `(user, content_type, object_id, role)`, so N rows for N organisations is the natural shape —
which is what makes holding roles on several Organisations at once work with no schema change.

**Record this in a comment where the query helpers do the join, so nobody re-derives it later:**
guardian **cannot** express "organisation role ⇒ cohort access" even in principle.
`sync_user_object_permissions` filters a role's permissions through `_filter_perms_for_content_type`
(`role_based_permissions/utils.py:123-137`), which drops any permission whose `app_label` differs from
the target's content type. A role assigned on an Organisation can therefore only ever sync
`freedom_ls_organisations.*` permissions — never `freedom_ls_student_management.view_cohort`.

The useful half *does* work through guardian:

- "Does this user hold a role on this Organisation?" →
  `user.has_perm("freedom_ls_organisations.view_organisation", organisation)`
- "Which Organisations?" →
  `get_objects_for_user(user, "freedom_ls_organisations.view_organisation", klass=Organisation)`

What guardian cannot do is the **implication** to cohort access. D2 performs that join explicitly.

### D2. Query helpers

They go in `freedom_ls/student_management/queries.py` — an **existing** module (it already holds
`is_registered_for_course_expression`), not a new file. They must import both `Cohort` and
`Organisation`; putting them in the `organisations` app would invert the layering.

```python
def organisations_accessible_to(user: RequestUser) -> QuerySet[Organisation]:
    """Organisations this user may enter.

    Union of two paths: an organisation role, OR a per-cohort guardian grant
    on any cohort inside the organisation. The second half is load-bearing —
    without it, every educator who holds only per-cohort grants is locked out
    of the interface the moment every URL gains an organisation segment.
    """
    by_role = get_objects_for_user(
        user, "freedom_ls_organisations.view_organisation", klass=Organisation
    )
    granted_cohorts = get_objects_for_user(user, "view_cohort", klass=Cohort)
    return Organisation.objects.filter(
        Q(pk__in=by_role.values("pk"))
        | Q(pk__in=granted_cohorts.values("organisation_id"))
    ).order_by("name")


def cohorts_visible_to(user: RequestUser, organisation: Organisation) -> QuerySet[Cohort]:
    """Cohorts within this organisation: all of them if the user holds an
    organisation role, otherwise only those with a per-cohort guardian grant."""
    within = Cohort.objects.filter(organisation=organisation)
    if user.has_perm("freedom_ls_organisations.view_organisation", organisation):
        return within
    return within.filter(
        pk__in=get_objects_for_user(user, "view_cohort", klass=Cohort).values("pk")
    )


def users_visible_to(user: RequestUser, organisation: Organisation) -> QuerySet[User]:
    """Users this person may see within an organisation.

    Built on cohorts_visible_to — never re-derives cohort visibility. Members
    of visible cohorts, plus, for an organisation-role holder only, learners
    who hold an individual registration in the organisation and belong to no
    cohort at all.
    """
    visible = Q(cohortmembership__cohort__in=cohorts_visible_to(user, organisation))
    if user.has_perm("freedom_ls_organisations.view_organisation", organisation):
        visible |= Q(usercourseregistration__organisation=organisation)
    return User.objects.filter(visible).distinct()
```

**The registration half is not optional.** Spec §4.3's `UserConfig` rule is "has a cohort membership
**or a registration** within `request.organisation`". Individually registered learners — the case this
very plan threads `UserCourseRegistration.organisation` onto — have no `CohortMembership` row, so a
membership-only implementation makes them invisible in the Users list and 404s their detail page for
staff who should legitimately see them.

**The rule for a guardian-grant-only educator, which the spec left open:** they see only members of the
cohorts they hold grants on, and **no** individually-registered learners. A per-cohort grant says
nothing about people who are not in that cohort, so widening it would hand a cohort-scoped educator the
whole organisation's individual learners. An organisation-role holder sees both.

Every one of them must return an **empty** queryset for an anonymous or unauthenticated user rather
than raising. Guard at the top.

These three are the only place organisation scoping is expressed. Keeping it here is what makes a
future nested-organisation change ("or descendants") a localised edit.

described above.

## 7. Phase E — `panel_framework`: the authorisation hook

`panel_framework` gains **no** app dependency. Everything here is generic.

### E1. `check_access` on `ListViewConfig`

`panel_framework/views.py:162-191`:

**Two methods, not one.** `check_access` is the entry point and is **not** an override point; it runs a
fail-closed prologue and then delegates to `authorise_instance`, which is what subclasses override:

```python
class ListViewConfig:
    ...
    #: Set to a short reason string on a config that deliberately does not
    #: authorise its detail views yet. Introspectable, so a test can assert
    #: every exemption is declared rather than accidental.
    check_access_exempt_reason: str | None = None

    @classmethod
    def check_access(cls, request: HttpRequest, instance: Model) -> None:
        """Entry point. Do not override — override authorise_instance instead.

        The user and scope guard here runs for every config, so a request
        with no authenticated user or no resolved scope is denied before any
        subclass code can dereference either and turn a denial into a 500.
        """
        user = getattr(request, "user", None)
        if user is None or not user.is_authenticated:
            raise Http404
        if getattr(request, "organisation", None) is None:
            raise Http404
        cls.authorise_instance(request, instance)

    @classmethod
    def authorise_instance(cls, request: HttpRequest, instance: Model) -> None:
        """Raise Http404 unless this request may see this instance.

        Deny by default: a config that does not override this cannot serve
        detail views at all, so a new config that forgets to think about
        authorisation fails closed instead of leaking.
        """
        raise Http404
```

**Why a template method rather than a guard helper each override calls.** A helper that every subclass
must remember to invoke is deny-by-*convention*, not deny-by-default: the base class's `raise Http404`
only protects configs that never override, and every config that *does* override — which is the point
of the hook — reopens the `AttributeError`-on-a-bare-request hole unless its author remembers an
unenforced rule. Making the prologue non-overridable is the only shape that keeps the claim true once
real subclasses exist.

`request.organisation` is read via `getattr` and never imported or typed against `Organisation`, so
`panel_framework` still gains no dependency — the attribute is generic, exactly like
`panel_url_kwargs` below.

### E2. `get_instance_view` gains the request

**breaking signature change on a public class method**, not just a new hook.


## 8. Phase F — URLs and the educator entry point

### F1. `educator_interface/urls.py`

```python
app_name = "educator_interface"

urlpatterns = [
    re_path(r"^$", views.interface_root, name="root"),
    re_path(
        r"^organisations/(?P<organisation_slug>[-a-zA-Z0-9_]+)/(?P<path_string>.*)$",
```

- Django's built-in `slug` path converter is **not** available — it belongs to `path()`, and a trailing

- `^$` must come **first**.
- Still exactly **one** URL name for the interface itself; the slug is a second kwarg on it, not a

### F2. `interface_root`

```python
@login_required
def interface_root(request: HttpRequest) -> HttpResponse:
    """Redirect a bare /educator/ to a concrete organisation URL.

    A "last selected organisation" is remembered in the session, but only to
    decide this redirect, and it is re-authorised on use. Once a URL names an
    organisation, the URL always wins.
    """
    accessible = organisations_accessible_to(request.user)
    remembered = request.session.get(LAST_ORGANISATION_SESSION_KEY)
    organisation = (
        accessible.filter(slug=remembered).first() if remembered else None
    ) or accessible.first()          # accessible is ordered by name
    if organisation is None:
        raise Http404
    return redirect(
        "educator_interface:interface",
        organisation_slug=organisation.slug,
        path_string="cohorts",
    )
```

A user with no accessible organisations gets a 404 from `/educator/`.

### F3. `interface` — resolve and authorise, once

Selecting an organisation is an **authorisation decision, not a filter**. Unlike Site, which is derived
from the request host and cannot be forged, an organisation comes from user-supplied URL input.

```python
@login_required
def interface(
    request: HttpRequest, organisation_slug: str, path_string: str = ""
) -> HttpResponse:
    organisation = get_object_or_404(Organisation, slug=organisation_slug)
    if not organisations_accessible_to(request.user).filter(pk=organisation.pk).exists():
        raise Http404
    request.organisation = organisation
    request.panel_url_kwargs = {"organisation_slug": organisation.slug}
    if request.session.get(LAST_ORGANISATION_SESSION_KEY) != organisation.slug:
        request.session[LAST_ORGANISATION_SESSION_KEY] = organisation.slug
    ...
```

The write is guarded so the session is only touched when the value actually changes — an unconditional
assignment marks the session dirty on **every** educator page load, which means a session-store write
per request for no benefit.

Notes:

- **Do not write `request.site`.** FLS has no such attribute — `CurrentSiteMiddleware`
  (`site_aware_models/middleware.py`) only stashes the request in a thread-local. The canonical
  accessor is `get_cached_site(request)` (`site_aware_models/models.py:19-40`). In this lookup neither
  is needed: `Organisation.objects` is a `SiteAwareManager` and already filters to the current site, so
  step 1 cannot return another Site's Organisation, and a slug that exists only on another Site is
  indistinguishable from one that does not exist — which is the correct outcome.
- **404, uniformly** — for "no such slug" and "slug exists but you have no access" alike. A 403 would
  confirm the slug is real, letting an attacker enumerate a Site's organisation names. This path is
  only reached by a hand-edited or guessed URL; the switcher never offers an organisation the user
  cannot enter.
- Add `organisation` and `panel_url_kwargs` to a small typed protocol or use `setattr` — do not add a
  `# type: ignore`.

### G4. The switcher

A new include at the **top of the left-hand panel**, before the existing
`{% include "panel_framework/partials/sidebar_nav.html" %}` in
`educator_interface/templates/educator_interface/interface.html:10-12`:

```
{% block sidebar_content %}
    {% include "educator_interface/partials/organisation_switcher.html" %}
    {% include "panel_framework/partials/sidebar_nav.html" %}
{% endblock sidebar_content %}
```

Behaviour:

- It **always displays the current organisation's name** — never a "Select organisation" placeholder.
  The name is the ambient indicator; the chrome must never say one organisation while showing
  another's data.
- **More than one accessible organisation:** the name is a dropdown trigger. Reuse the existing
  `c-dropdown-menu` cotton component (`base/templates/cotton/dropdown-menu.html`) with a custom
  `<c-slot name="trigger">`, exactly as `partials/header_bar_user_menu.html` already does. Do not
  rebuild dropdown logic — and per `ds:alpine-js`, the CSP build forbids inline expressions, so a
  hand-rolled dropdown would need a newly registered `Alpine.data()` component for no gain.
- **Exactly one accessible organisation:** hide the interactive control but still render the name as
  static text in the same position, so when a second organisation is later granted the *same* label
  becomes clickable rather than a new element appearing from nowhere.

Accessibility — **menu semantics, not listbox semantics.** `c-dropdown-menu` hardcodes
`aria-haspopup="menu"` on its trigger and is shared with the header user menu, so `role="listbox"`
would mean changing a component another surface depends on.

- Trigger: the component's existing `aria-haspopup="menu"` + `aria-expanded`, organisation name as
  visible text, plus an `aria_label` naming the control.
- Each option: `role="menuitemradio"`, with `aria-checked="true"` on the current organisation and
  `"false"` on the others.

This is the WAI-ARIA APG pattern for "choose one of N" inside a menu button, conveys the same state
`aria-selected` would, and needs no keyboard JS beyond the open/close/click-away/Escape behaviour
`c-dropdown-menu` already provides.

Context: a `current_organisation` variable and an `accessible_organisations` list, both sourced from
the F3 resolve step. **Templates must not re-derive the slug from `request.path`.**

**The switcher's own label must be OOB-swapped, or it goes stale on every switch.** The dispatcher
OOB-swaps `#main-content`, breadcrumbs, `#sidebar-nav` and the page title — but the switcher is a
*sibling* of `sidebar_nav.html`, not part of it. Without its own fragment, a switch updates every other
piece of chrome and leaves the switcher naming the **previous** organisation: the chrome saying one
organisation while showing another's data, which is precisely what the design exists to prevent.

Give the switcher's root element an id (`#organisation-switcher`) and an `oob` flag exactly as
`sidebar_nav.html:1-2` already does, and render it as one more fragment in the navigation block (E4).
Do **not** solve this by folding the switcher into `sidebar_nav.html` — that partial belongs to
`panel_framework` and knows nothing about organisations.

**The dropdown does not close itself after a selection.** Every other use of `c-dropdown-menu`
(`header_bar_user_menu.html`) navigates away or triggers a full page load, so the panel is destroyed.
Here the options `hx-get` into `#main-content` while the dropdown lives in the sidebar, outside the swap
target — so it stays visually open after switching. Close it explicitly from the registered Alpine
component (e.g. an `hx-on::after-request` that calls the component's `close()`; a method reference, not
an inline expression, because the CSP build forbids those). If that proves awkward, record it as a known
trade-off rather than leaving it undecided.

Do **not** delete the existing `@claude` comment at `dropdown-menu.html:24-31` about
`x-on:scroll.window="close"`. The switcher sits near the top of a scrollable sidebar, so that behaviour
will be more noticeable — if it proves unacceptable, it is a fix to that comment's issue, not a
switcher-specific workaround.

Icons via `<c-icon name="dropdown" />` (or the closest semantic name that exists — check
`fls-dev:icon-usage`); never a raw SVG or Unicode glyph.

### G5. Switching

Reuse the existing HTMX navigation mechanism, not a new one — `hx-get` + `hx-target="#main-content"` +
`hx-push-url="true"` + `hx-swap="outerHTML"`, exactly as `sidebar_nav.html:8-16` already does.

Each switcher option additionally sends a marker header so the server can tell a switch from ordinary
navigation:

```
hx-headers='{"X-Organisation-Switch": "true"}'
```

A header rather than a query parameter, so `hx-push-url` does not leave `?switched=1` in the address
bar. `hx-headers` is an inheritable attribute and merges with the global CSRF header set on `<body>`,
so the CSRF token is not lost.

Two outcomes:

- **On a list/index page:** reload it in place for the new organisation. Nothing extra to do — the
  target URL already names the new organisation.
- **On a detail page for an object outside the newly selected organisation:** `authorise_instance`
  raises `OrganisationScopeDenied` (§G1). The `interface` view catches **that type specifically**, and
  only when the switch header is present, then:
  1. `messages.info(request, f"Switched to {organisation.name} — that {label} isn't in this organisation")`
  2. re-dispatches with `path_string` truncated to its first segment (the section list)
  3. sets `HX-Push-Url` on the response to the list URL

  This yields the correct content, the correct address bar, and a toast, in one request.
  `HtmxMessagesMiddleware` (`base/middleware.py`) appends the OOB toast fragment automatically for a
  normal HTMX HTML 200 — `messages.info(...)` is the entire integration point, there is no separate
  alert component to build.

**Catch `OrganisationScopeDenied`, never bare `Http404`.** `Http404` is the generic failure of the
whole resolver: unknown path segment, missing tab, missing panel, missing action, deleted object
(`_resolve_panels`, `_resolve_tabs`, `_resolve_action_on_*`, `get_tab`, and `get_object_or_404` inside
`get_instance_view` all raise it). A broad catch would relabel a genuine "this doesn't exist" as "that
cohort isn't in this organisation" and silently redirect — masking a real bug behind a plausible wrong
message, and only on requests carrying the switch header. Every other 404 must propagate normally even
mid-switch.

**No 302.** The in-request re-dispatch plus an explicit `HX-Push-Url` avoids depending on whether htmx's
custom headers survive a fetch redirect — implementation detail we should not build on either way.

**Never render a bare 404 as the direct consequence of a switch.** No confirmation dialog — the
educator interface is read-mostly.

**Test:** switching on a list page; switching on a detail page for a foreign object (asserts 200, the
list content, the `HX-Push-Url` header and the queued message); a foreign detail URL requested
*without* the switch header still 404s; and — the test that pins the narrow catch — **a switch request
to a genuinely nonexistent path segment still 404s** rather than redirecting with the "isn't in this
organisation" notice.

### G6. The live region

Because switching re-renders the whole main content, the change must also be announced.

Add a persistent visually-hidden live region **as a sibling of `#main-content`, not inside it**, so the
swap updates the region rather than destroying and recreating it (some screen readers miss a
re-inserted live region):

```html
<div id="scope-announcer" class="sr-only" aria-live="polite" aria-atomic="true"></div>
```

It goes inside the `{% block content %}` of
`educator_interface/templates/educator_interface/interface.html:20-24`, beside the `main_content.html`
include — **not** in `_base_interface.html`, which is shared with the student course player and has no
organisation concept.

The switch response includes an `hx-swap-oob="true"` fragment targeting that id with
"Now viewing {organisation name}". `educator_interface.interface` produces it by setting
`request.panel_announcement` before dispatch (§E4); the dispatcher renders it into the same OOB bundle
it already builds for breadcrumbs, sidebar nav and page title (`panel_framework/views.py:591-621`).

That is one place assembling OOB fragments, not two. Appending to `response.content` from
`educator_interface` instead would duplicate the concatenation and would have to re-derive
`HtmxMessagesMiddleware`'s `Content-Length` fix-up (`base/middleware.py:56-77`) — a second chance to get
it wrong for no benefit. The attribute is generic, so `panel_framework` still never mentions
Organisation.

A live-region announcement is preferred over forcibly moving focus to the new page's heading: a focus
move is disruptive if the educator wants to immediately reopen the switcher to compare a third
organisation.

```python
def organisation_for_learner_course(user, course) -> Organisation | None:
```

2. Otherwise `latest_registration(user, course).organisation` (the §C7 helper).

### H2. The chip

Placement: the **course outline header**, in
`student_interface/templates/student_interface/partials/course_toc_header.html` — between the course
title and the progress bar. That region already sits inside `#course-toc-region`, which is out-of-band

permanently on screen. Fine for a secondary co-branding mark.

Rendering rules — **the chip is load-bearing, not cosmetic:**

- **Opaque light fill, not just padding.** The two shipped themes put the header on visually different
  backgrounds — `themes/default/.../theme.css:151` sets `--color-header: var(--color-primary)` (solid

  straight onto the solid-brand-colour theme, it disappears.
- **Fixed height, capped width.** The existing site logo uses `h-8 w-auto flex-shrink-0`
  (`base/templates/partials/header_bar.html:9-10`), fine for one known static asset but with no upper
  bound. `RT-logo.webp` is roughly 2.2:1; a wider banner-style logo under "fixed height, auto width"

- **Not a link.**
- Use role tokens (`surface`, `border`, `muted`) rather than hardcoded colours — see

- Always render an `alt` naming the organisation.

**Monogram fallback.** No logo → an initials badge from `Organisation.initials`, mirroring the existing

`<c-icon name="user">`.

for every other media file in FLS. **No public-read carve-out, no second `STORAGES` alias, no bucket
policy.** The signed query string changes per render, so browsers re-fetch the ~13 KB asset rather than
caching it across page loads; acceptable for a small, rarely-changing mark inside an authenticated
player.

Keep the organisation mark **visually subordinate** to the site's own branding — a learner must never
be confused about who runs the platform versus which organisation they study through.

### 12.1 Migration behaviour

Asserts: one Organisation per Site, correct backfill, no cross-site contamination.

Because the backfill callable lives in an importable module (§C3), the test imports it and runs it
against seeded multi-Site data using the real app registry. No new dependency, no migration harness,
fast.

**The test must disconnect the §B6 `post_save` receiver while seeding.** Otherwise every seeded Site
arrives already carrying an Organisation, "one Organisation per Site" passes without the backfill
having done anything, and the test asserts the signal rather than the migration. Disconnect, seed, run
the callable, assert. The receiver's own behaviour is covered separately in
`organisations/tests/test_signals.py`.

Two further assertions, which are **not** the same thing:

- **Idempotence** — running the callable twice from a clean slate leaves one Organisation per Site both
  times.
- **Partial-apply resumption** — construct the state a crash mid-loop would leave: the Organisation for
  a Site already exists, **some** of that Site's cohorts and registrations already point at it, and
  others are still null. Re-run the callable and assert exactly one Organisation for the Site (the
  `get_or_create` on `(site, name)` found the existing row) and every remaining row now backfilled.

"Call it twice from empty" does not cover the second case, and the second case is what criterion 2
actually asks about. With `atomic=True` this state cannot arise from FLS's own migration, but it can
from a downstream fork that changed the transaction setting or from manual DBA intervention — which is
exactly when an operator will be re-running the backfill.

The trade-off, stated: this tests the backfill logic, not Django replaying the migration graph. That is
the right balance — the repo has no precedent for testing a `RunPython` migration's behaviour (the only
migration-adjacent test, `contrib/conformance/test_migrations.py`, is a schema-drift probe), so this
establishes a pattern rather than importing a dependency downstream projects would inherit.

### 12.2 Cross-organisation isolation

The core guarantee: **two Organisations under one Site, a user with a role on Organisation A only, and
assertions that every educator list view, detail view and HTMX partial returns nothing — or 404 — for
Organisation B.** Structural precedent: the existing cross-*site* isolation test
(`test_course_visibility_and_interest.py:58-80`), generalised from "other site" to "other
organisation".

Plus the lock-out case: **an educator holding only per-cohort guardian grants and no organisation role
can still enter the educator interface and sees exactly their cohorts.**

### 12.3 Coverage of the whole educator surface

Two tests, both in `test_config_authorisation.py`.

**(a) Enumerate `interface_config`, not `urlpatterns`.** There is exactly one URL pattern behind the
whole educator interface, so walking `urlpatterns` yields a single entry and proves nothing. The real
surface is `educator_interface.views.interface_config` (`views.py:1032-1034`), the
`{url_name: ListViewConfig}` mapping that `_resolve_path` walks. Build `path_string` values from it —
the section list, a detail path per config with a seeded instance, and the `__panels` / `__tabs` /
`__actions` segments each config declares — and assert every one 404s for an organisation the user
cannot access.

**Assert the enumeration is non-empty and grows with the interface.** That is what converts "did we
remember to test the new view" from a code-review habit into a CI failure, and it is what the
whole-surface guarantee actually rests on.

**(b)** Every production `ListViewConfig` either defines its own `authorise_instance` or declares
`check_access_exempt_reason` — so no config silently inherits deny-by-default and 404s in production,
and no config quietly gains a permissive override without a declared marker. A third assertion belongs
here too: **no production config overrides `check_access`**, which would bypass the fail-closed
prologue.

**Enumerate from `interface_config`, not `ListViewConfig.__subclasses__()`.** There are three
production configs (`views.py:757`, `:769`, `:1024`) but eight-plus test-only subclasses under
`panel_framework/tests/` (`stub_panels.py:129`, `test_breadcrumbs.py`, `test_menu_items.py`,
`test_instance_dropdown.py`). A subclass walk sweeps those in and fails for reasons that say nothing
about production authorisation.

Test (b) checks `authorise_instance`, not `check_access` — the latter is the non-overridable entry point
and every config inherits it, so asserting on it would pass vacuously.

### 12.4 The switcher's browser behaviour

Success criterion 12 — keyboard-only operation, `aria-checked` tracking the current organisation, and
the live region announcing **after** the content swap — cannot be verified with the Django test client.
Real focus movement, Escape/click-away on the Alpine component, and a live region updating after a DOM
swap need a browser.

`educator_interface/tests/playwright/test_organisation_switcher.py`, marked `@pytest.mark.playwright`,
following the existing convention (`freedom_ls/{base,panel_framework,student_interface}/tests/playwright/`):

- open the switcher with the keyboard, move between options, select with Enter;
- `aria-checked` moves to the newly selected option;
- the `#scope-announcer` text updates after the HTMX swap, and the element is not replaced;
- the switcher label itself shows the new organisation after the swap (the §G4 OOB fragment).

## 13. Upgrade notes content

Not written here — `/fls-dev:update_upgrade_notes` authors the file later. Collect these points as you
go so nothing is lost:

- Both constraint changes are **narrowing** (adding a column to a unique key) and **cannot fail against
  existing data**: two rows that satisfied the old, stricter key cannot collide under a looser one. Say
  this explicitly — operators have been warned about a genuinely dangerous constraint change before and
  will assume this one is the same.
- **Do not `--fake` the backfill migration.** Faking records it as applied without running it; the
  not-null step then fails for real. (That failure is the safety net working, but the operator should
  not get there.)
- **Do not roll back after go-live.** The backfill's reverse is a no-op, and rolling back far enough
  drops the `organisation_id` columns and the `Organisation` table outright — nothing to put back
  except a database restore.
- If a downstream project modified `unique_cohort_name_per_site` or `unique_user_course_registration`
  outside FLS's own migrations, reconcile before upgrading: `RemoveConstraint` addresses constraints by
  name.
- The duplicate-registration consequence (§C7) for any downstream code querying
  `UserCourseRegistration` directly.
- **Two separate breaking changes to `ListViewConfig`**, not one: `get_instance_view` gains a `request`
  argument, **and** `authorise_instance` must be implemented or detail views 404. A downstream that
  does one and stops there is still broken. Name `authorise_instance` explicitly — a downstream that
  overrides `check_access` instead will silently lose the fail-closed prologue.
- Every educator URL now carries an organisation segment; externally bookmarked bare paths 404.
- Pillow is a new base dependency.

## 14. Risks

1. **`reverse()` blast radius.** Every URL construction into `educator_interface` gains a kwarg. Missing
   one is a `NoReverseMatch` at render time — loud, but only on the page that hits it. Bounded and
   greppable because the whole interface has a single URL name. The E3 mechanism removes most of the
   sites at a stroke; sweep the rest systematically (§F4) rather than fixing them as they break.
2. **Duplicate registrations** (§C7) — the most likely post-upgrade production 500 and the least likely
   to be caught by tests, because it only manifests on multi-organisation Sites, which no existing test
   constructs. The audit is mandatory, and the new test must construct that shape.
3. **Deny-by-default `authorise_instance`** breaks any downstream project with its own
   `ListViewConfig` subclass. Correct — they were unguarded — but it belongs prominently in the upgrade
   notes.
4. **`get_instance_view`'s new signature** is a second, independent breaking change to the same class.
5. **The `GuardedModelAdmin` / unfold pairing** is unverified upstream by either package — its own
   resource doc says so. The documented order (`ModelAdmin, GuardedModelAdmin`) is what to use, but the
   object-permissions page rendering is what to actually watch, and the `@claude` TODO stays until it
   does.
6. **Signed logo URLs are not cacheable.** Accepted; revisit only if logo rendering moves to an
   unauthenticated surface (public catalogue, certificate, email), at which point a public carve-out or
   a Django-served endpoint can be added without changing the model.
7. **The switcher closes on window scroll**, inherited from `c-dropdown-menu`. Known, tracked by the
   existing `@claude` comment at `dropdown-menu.html:24-31`.
8. **`SiteFactory` now produces a Site with an Organisation** (§C5). Any test asserting an absolute
   `Organisation.objects.count()` needs updating.

## 15. Explicitly out of scope

Deferrals, not gaps. Do not drift into these:

- No organisation delete and no merge.
- No nested organisations. (This is why scoping lives behind the §D2 helpers.)
- No organisation membership object — a learner's organisation comes from their registrations.
- No per-organisation domain, subdomain, colours or theme.
- No organisation branding in emails or certificates.
- No search, recents or favourites in the switcher — a flat list is right for the 2–5 organisations
  expected.
- No EXIF stripping.
- Courses, course interest, applications and recommendations stay unscoped.
- **The unguarded Courses list is not fixed here** — it belongs to `critical_security_fixes`, which
  this plan's `check_access` hook enables.
- **`create_site.py`'s missing `site.save()` is not fixed here.**
- The `"site_id"` → `"site"` constraint-field-name cleanup is not done here.

## 17. Success criteria checklist

Straight from spec §14. The feature is done when all of these hold.

**Data and migration**

1. `migrate` on a database with existing Sites, cohorts and registrations completes with no manual
   steps; afterwards every Site has exactly one Organisation named after it, every cohort and
   registration points at the Organisation for its own Site, and no row crosses a Site boundary.
2. Re-running the backfill after a simulated partial apply produces no duplicate Organisations.
3. Both narrowed constraints apply cleanly to pre-existing data.
4. A Site created after the migration — via `create_site`, the admin, or `SiteFactory` — comes out with
   exactly one Organisation, identical in shape to one the migration would have produced, and re-saving
   it does not create a second.

**Authorisation**

5. A user with a role on Organisation A only receives 404 — never a 403, never a partial page — for
   every educator list view, detail view and HTMX partial belonging to Organisation B, verified by the
   `interface_config`-enumerating test.
6. An educator holding only per-cohort guardian grants and no organisation role can still enter the
   educator interface and sees exactly the cohorts they hold grants on.
7. A `ListViewConfig` subclass with no `authorise_instance` override serves no detail views, and a
   `check_access` reached with no authenticated user or no resolved organisation raises `Http404`
   rather than `AttributeError`.
8. Every permissive `authorise_instance` override declares `check_access_exempt_reason` and carries a TODO
   naming `critical_security_fixes`.

**Educator interface**

9. The switcher shows the current organisation's name at all times, and the label sits in the same
   place whether the user has one organisation or several.
10. Switching on a list page reloads it in place for the new organisation; switching on a detail page
    for an object outside the new organisation lands on the equivalent list with an inline notice.
    Neither path produces a bare 404.
11. Two browser tabs can sit on two different organisations simultaneously, and each keeps showing its
    own data after either is refreshed.
12. Keyboard-only operation of the switcher works end to end, the current organisation is exposed via
    `aria-checked`, and the change is announced through the live region after the content swap.

**Student interface**

13. A learner registered through a cohort sees that cohort's organisation logo in the course outline
    header; one registered individually sees their registration's organisation; one with no
    registration sees no logo.
14. `RT-logo.webp` renders legibly on **both** shipped themes, at a capped width, visually subordinate
    to the site's own branding.
15. An organisation with no logo shows the monogram; "RPAS Training" yields "RT".
16. The logo lookup adds no N+1 query to the player.

**Management and quality**

17. An admin can create, rename, upload a logo for, and assign staff to an Organisation; the delete
    action is unavailable.
18. Every rejection path in §B4 is covered by a test, and `RT-logo.webp` uploads successfully.
19. `uv run pytest` passes in full — the changed factories are used across at least eight apps' test
    suites — and all 16 QA seeding commands run without error.
20. `docs/app_structure.md` is regenerated and shows only downward edges.
