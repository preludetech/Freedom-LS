# Research: reference implementations

Topic: how reference implementations solve the learner move, the import-cycle break and the stored-path migration. Section (a) is in-repo and authoritative; (b) is brief external context.

## (a) In-repo references

### Package layout already used by `panels/common/`, `panels/audit_log/`, `panels/dashboard/`

- `panels/` and each area dir has an `__init__.py` (verified present for `common`, `audit_log`, `dashboard`). Module names are by role, not by area: `config.py`, `data_tables.py`, `data_table_panels.py`, `filters.py`, `panels.py`, `bulk_actions.py`. `learner/` should use exactly these names (the idea already does).
- `audit_log/` holds `config.py`, `data_tables.py`, `filters.py`, `data_table_panels.py`. `dashboard/` holds `config.py`, `panels.py`. `common/` holds `actions.py`, `badges.py`, `bulk_actions.py`, `filters.py`, `ids.py`, `report.py`, `request.py`, `tables.py`. So the shared bases the learner modules need already exist: `EducatorBulkAction` and `CoursePickerMixin` in `common/bulk_actions.py`, `OrganisationScopedRequest` in `common/request.py`.
- Module style to copy: a one-line docstring, then `from __future__ import annotations`, then absolute `freedom_ls.educator_interface.panels...` imports (never relative), then an `__all__` list of public names (e.g. `audit_log/data_table_panels.py` has `__all__ = ["HistoryPanel"]`; `common/bulk_actions.py` lists `CoursePickerMixin`, `EducatorBulkAction`). Underscore names that a sibling imports (e.g. `_record_export` imported from `audit_log/data_tables.py` by `data_table_panels.py`) are imported by name across modules, so moved `_`-prefixed helpers (`_last_active_cell`, `_membership_changed_response`, `_joinable_cohorts`, `_cohort_picker`, `_LEARNER_STATUS_TONES`) need no rename. Put them in `__all__` only if public.
- One-way import precedent for the cycle fix: `audit_log/data_table_panels.py` imports `AuditLogEntryTable` from its sibling `data_tables.py` and `DataTablePanel` from `panel_framework`; nothing imports back. `HistoryPanel` is already at `panels/audit_log/data_table_panels.py`, so `learner/data_table_panels.py` can import it from there as the idea says (no shell `views.py` import).
- Dependency rule to state in the spec: `common` imports no area; areas import `common`; `learner` imports `audit_log` and `cohort/data_tables.py`; `cohort/data_tables.py` imports only `common`; `cohort` (spec 6) imports `learner`, never the reverse.

### The migration and its test (copy these)

- `freedom_ls/educator_interface/migrations/0001_rename_unregister_bulk_runs.py` is the only migration in the app, so the new file is `0002_...`. Its shape:
  - `from django.apps.registry import Apps`, `BaseDatabaseSchemaEditor | None` annotations, no `Any`.
  - A module-level `RENAMES` list of tuples, built from a prefix constant (`_ACTIONS = "freedom_ls.educator_interface.actions."`).
  - A function using `apps.get_model("freedom_ls_panel_framework", "BulkActionRun")` (historical model, not an import), then `.filter(action_path=old).update(...)` per tuple.
  - `dependencies = [("freedom_ls_panel_framework", "0001_initial")]`. The new migration must also depend on `("freedom_ls_educator_interface", "0001_rename_unregister_bulk_runs")`, because it runs on the same app and on paths 0001 may already have rewritten (0001 rewrote to the `actions.<Name>` paths this spec then moves; order matters).
  - `RunPython(forward, migrations.RunPython.noop)`. The spec must replace `noop` with a real reverse function, since the idea requires one.
- Design for the new migration: one `PATHS` list of 7 class names (`AddToCohortBulkAction`, `RemoveFromCohortBulkAction`, `DeactivateLearnersBulkAction`, `ReactivateLearnersBulkAction`, `RegisterForCourseBulkAction`, `DeactivateRegistrationBulkAction`, `ResendSetupEmailBulkAction`, checked against the `@register_bulk_action` decorators in the tree), `OLD = "freedom_ls.educator_interface.actions."`, `NEW = "freedom_ls.educator_interface.panels.learner.bulk_actions."`, and a shared helper `_repoint(apps, source, target)` that `forward` and `reverse` call with the arguments swapped (avoid repeating code, per `CLAUDE.md`). It only touches `action_path`; `0001` also set `action_name`, this one must not. Match exact `action_path` equality per class, never `startswith`, so cohort bulk action rows (spec 6) and unknown rows stay untouched.
- `tests/migrations/test_0001_rename_unregister_bulk_runs.py` is the test template: `@pytest.mark.django_db(transaction=True)`, `MigrationExecutor(connection)`, `leaf = executor.loader.graph.leaf_nodes()`, `executor.migrate([(APP, None)])` to roll back, build the historical model with `executor.loader.project_state([(RUNS, "0001_initial")]).apps`, create rows, then rebuild the executor, call `executor.loader.build_graph()` and `executor.migrate(leaf)`, then read back through the current state. Constants: `APP = "freedom_ls_educator_interface"`, `RUNS = "freedom_ls_panel_framework"`. Rows need `site_id`, `requested_by_id`, `action_path`, `table_key`, `action_name`, `keys=[]`, and the `mock_site_context` fixture. Name the new file `test_0002_<slug>.py`. For the new test the rollback target must be `(APP, "0001_rename_unregister_bulk_runs")`, not `None`, so it exercises the reverse of 0002 alone. Cover three cases as the idea says: forward (old path becomes new, `action_name` unchanged), reverse (new back to old), untouched rows (a cohort bulk action path and a foreign path). Add one case asserting that a run is resolvable afterwards: `import_string(new_path)` succeeds and is a `RecordedBulkAction` subclass.

### How `action_path` is resolved (why the migration is needed and what breaks silently)

- `panel_framework/bulk_actions.py:401` records the path as `f"{type(self).__module__}.{type(self).__qualname__}"`, so the stored path is the defining module of the class. Moving the class therefore changes the path of every future run automatically, and only past runs need the migration.
- `panel_framework/bulk_runs.py:31-42` `action_for(run)` calls `import_string(run.action_path)` and returns `None` on `ImportError` or a non-`RecordedBulkAction` class. A missed rename does not crash: the run quietly becomes "This action is no longer available." The failure is silent, so the migration test, not a smoke test, is the guard. The `None` path is already tested with `"nowhere.RenamedAway"` (`panel_framework/tests/test_bulk_actions.py:1515`).
- `BULK_ACTIONS` (`panel_framework/bulk_actions.py:557`) is keyed by `(table_key, action_name)` and filled by `@register_bulk_action` at import time. It is not keyed by module, so the move does not change registry keys or the order of the action bar, but the order is registration order. The spec must make sure `learner/bulk_actions.py` is still imported at startup (it is only registered once the module is imported), and that action-bar order for the `learners` table is unchanged. Check which module imports the bulk action modules today (the `config.py` or `views.py` import chain) and keep the learner one in that chain.
- `BulkActionRun.action_path` is `CharField(max_length=255)` (`panel_framework/models.py:89`). The new path `freedom_ls.educator_interface.panels.learner.bulk_actions.DeactivateRegistrationBulkAction` is about 85 chars, so the length is fine.

## (b) External references (brief)

- Django's own docs on `RunPython` and reversibility (data migrations with `reverse_code`, historical models via `apps.get_model`): <https://docs.djangoproject.com/en/stable/ref/migration-operations/#runpython>. Our `0001` already follows this; the extra point is to supply a real `reverse_code` instead of `noop`.
- Wagtail: renaming a page model needs a hand-written `RunPython` data migration that updates stored content-type rows and the page revisions that reference them (revisions link by content type id and object id); Wagtail docs say data migrations are written by hand as an empty migration with forward and backward functions. Wagtail's `MigrateStreamData` and `RenameStreamChildrenOperation` are subclass-of-`RunPython` helpers for stored block names. Sources: <https://docs.wagtail.org/en/7.1/reference/streamfield/data_migrations.html>, <https://www.caktusgroup.com/blog/2019/09/12/wagtail-data-migrations/>, <https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/54318017/how-to-properly-rename-a-wagtail-page-model>. The lesson that fits here is to rewrite every table that stores the name, and to roll the data back with its own function. (The searches did not turn up a Wagtail doc about rewriting stored dotted class paths specifically; I did not verify more than this.)
- Celery task renames: the edX platform renamed tasks to match new import paths by registering the function under both the old and new names for a deploy, so queued messages with the old name were not dropped; the old name was removed afterwards. Source: <https://git.andalsoftware.com/Andal.LND/edx-platform/commit/b626a43fa1869f2cb8b70db51cfc1694c2029f59>. `celery.contrib.migrate` can also move queued messages: <https://docs.celeryq.dev/en/latest/reference/celery.contrib.migrate.html>. This is the alias/shim approach. The idea rejects it ("no shim and no leftover old path"), and a DB-stored path suits a one-shot data migration better than a queue, which cannot be rewritten in place.
- Django admin actions, django-import-export and Saleor were not researched in depth; none of them stores a dotted action path in the database that I know of, so they offer no precedent for this migration. Note that as a gap, not a finding.

5. Migration test `test_0002_*` built from the `test_0001` template, with rollback to `0001` and the three cases plus an `import_string` resolvability check.
