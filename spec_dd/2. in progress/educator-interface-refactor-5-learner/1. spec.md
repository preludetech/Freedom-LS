# Spec: educator interface refactor 5, learner

## Purpose

The learner area of `freedom_ls/educator_interface/` moves out of the flat `views.py`, `actions.py`,
`reporting.py`, `filters.py` and `quick_views.py` into `panels/learner/`, and its tests move to
`tests/panels/learner/`. The move also breaks the learner/cohort import cycle so that
`educator-interface-refactor-6-cohort` imports learner one way only, and a data migration repoints the stored
`BulkActionRun.action_path` of the seven learner bulk actions. It is a pure move on top of `panels/common/` and
`panels/audit_log/`, as settled in `idea.md`. `research_codebase.md` holds today's line numbers and test
clusters.

## Scope

In:
- New package `panels/learner/` and the module `panels/cohort/data_tables.py`, with the names listed under
  Requirements.
- `inactive_cohort_response` and `learner_status_badge` (with `_LEARNER_STATUS_TONES`) moving into
  `panels/common/`.
- Repointing every reference to a moved name, the data migration `0002` and its test, and the test moves listed
  under Testing.

Out:
- The rest of the cohort area: `CohortConfig`, cohort panels, `CohortCourseRegistrationDataTable`, the cohort
  actions (`AddExistingLearnersAction`, `AddLearnerToCohortAction`, `DeactivateCohortRegistrationAction`,
  `RequiresActiveCohortMixin`, `cohort_not_empty_sentence`, `KEEPING_NAMES_SHOWN`), the four cohort bulk
  actions and their migration. `educator-interface-refactor-6-cohort` owns them.
- The staff, course, dashboard and audit log areas, the shell trim, deleting emptied flat modules, and the
  `claude_plugins/fls-dev/skills/educator-interface/SKILL.md` path sweep
  (`educator-interface-refactor-7-cleanup`).
- Any behaviour, UI, URL, URL name, template path or app label change. The flat domain modules `forms.py`,
  `staff.py`, `learner_import.py` and `messaging.py`.

## Decisions

- **No re-export shim.** The flat modules lose each moved name. Flat cohort code that stays (in `views.py`,
  `actions.py`) imports learner names from `panels/learner/`, which is the allowed direction.
- **Import direction.** `panels/common` ← `panels/cohort/data_tables.py` ← `panels/learner/*`. A learner module
  imports `panels/common/`, `panels/audit_log/data_table_panels.py` (for `HistoryPanel`),
  `panels/cohort/data_tables.py` and nothing else under `panels/`. It never imports a flat module (`views`,
  `actions`, `reporting`, `filters`, `quick_views`) except that `import_views.py` imports the shell `views.py`.
  `panels/cohort/data_tables.py` imports only `panels/common/`. Inside the area, imports run one way:
  `filters` ← `data_tables` ← `data_table_panels`; `actions` ← `bulk_actions` ← `config`; `quick_view` ←
  `panels`; `panels`, `data_table_panels`, `messages` ← `instance_view` ← `config` ← `import_views`. Checked by grep, with
  no new import-linter contract.
- **`learner_status_badge` and `_LEARNER_STATUS_TONES` go to `panels/common/badges.py`**, beside
  `active_status_badge`, not to `instance_view.py`. `data_tables.py`, `panels.py` and `quick_view.py` all use it,
  and `instance_view.py` imports them, so `instance_view.py` would make a cycle. The lazy `_learner_status_badge`
  wrapper in `quick_views.py` goes away; `LearnerQuickView` imports the badge directly.
- **`partial_oversight_thread_older` goes to `import_views.py`**, not `messages.py`. It needs `LearnerConfig` and
  the shell's `_attach_organisation`, and `config` → `instance_view` → `messages` → `config` would be a cycle.
  `import_views.py` is the learner module that already imports `config.py` and the shell, and no config imports
  it.
- **`inactive_cohort_response` goes to `panels/common/actions.py`.** `MembershipAction`, `MoveToCohortAction`,
  `AddToCohortAction` and `AddLearnerAction` call it, and the learner area would otherwise import cohort.
- **`visible_registrations_with_progress` stays in the learner area** (`quick_view.py`). Only `LearnerQuickView`
  and `LearnerCoursesPanel` use it; the cohort and staff quick views do not.
- **Bulk-action registration stays at startup.** `@register_bulk_action` fills the registry when its module is
  imported, and today `views.py` imports `actions.py`. `panels/learner/config.py` imports the
  `panels.learner.bulk_actions` module for that side effect, with `# noqa: F401` and a one-line comment saying
  why, so the learners table offers the same bulk actions in the same order.
- **Patch strings name the module that looks the name up.** A stale string on a flat module that still imports the
  name resolves and patches nothing.
- **Underscore names keep their spelling** and are imported across modules by name.

## Requirements

Paths are under `freedom_ls/educator_interface/`. Each name moves byte-for-byte, comments and `TODO`s included,
except for its import lines; quoted casts stay quoted. Each new module starts with a one-line purpose docstring
and `from __future__ import annotations`, and declares a sorted `__all__` of every name it owns, as
`panels/common/` and `panels/audit_log/` do. Every new `__init__.py` is empty.

### Migration

`migrations/0002_<slug>.py`, modelled on `0001_rename_unregister_bulk_runs.py`, which is not edited:

- Depends on `("freedom_ls_educator_interface", "0001_rename_unregister_bulk_runs")`.
- Uses `apps.get_model("freedom_ls_panel_framework", "BulkActionRun")` and literal strings; it imports no action
  class.
- Maps `freedom_ls.educator_interface.actions.<Name>` to
  `freedom_ls.educator_interface.panels.learner.bulk_actions.<Name>` for exactly these seven:
  `AddToCohortBulkAction`, `RemoveFromCohortBulkAction`, `DeactivateLearnersBulkAction`,
  `ReactivateLearnersBulkAction`, `RegisterForCourseBulkAction`, `DeactivateRegistrationBulkAction`,
  `ResendSetupEmailBulkAction`.
- Matches each row by exact `action_path`, never by prefix, and updates only `action_path`.
- Its reverse maps the same seven back. Forward and reverse share one helper called with the pair swapped.

## Success criteria

- Over `panels/learner/` and `panels/cohort/`, these find nothing:
  - `grep -rnE "freedom_ls\.educator_interface\.(actions|reporting|filters|quick_views)\b"`
  - `grep -rnE "freedom_ls\.educator_interface\.views\b"` outside `learner/import_views.py`
  - `grep -rnE "panels\.(staff|course|dashboard)"`, and under `panels/cohort/`, `grep -rnE "panels\.(learner|audit_log)"`
  - `grep -rnE "^\s*from \."`
- No module under `panels/learner/` imports `panels.cohort` other than `panels.cohort.data_tables`.
- In `freedom_ls/educator_interface/` outside `tests/` and `migrations/`, each moved name has its `class`, `def` or
  assignment only in its new module.
- Each new module imports in a fresh interpreter (`python -I`, after `django.setup()`), and in a fresh interpreter
  that imports `freedom_ls.educator_interface.views`, `bulk_actions_for_table("learners")` lists the same actions
  in the same order as on `main`.
- `pytest --collect-only -q` collects the same number of tests as `main`, plus the new `_NEW_REPORTING_FILES` case
  and the `test_0002` cases, and the full suite passes.
- Pointing the `send_message` patch string back at `views` makes its messages test fail (a one-off manual check).
- `manage.py check` passes, and `makemigrations --check --dry-run` reports no changes.
- `migrate freedom_ls_educator_interface 0001` followed by `migrate` runs both ways on a database with learner bulk
  runs.
- The mirroring check passes, and `mirroring_baseline.txt` has lost only the `test_learner_section.py` line.
- `git diff main --stat` shows no change under `templates/` or `static/`, and the only migration file added is
  `0002`.
