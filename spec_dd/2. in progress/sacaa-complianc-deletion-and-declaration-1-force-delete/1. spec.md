# Spec: users are deactivated, not deleted, and superusers force delete with a reason

Spec 1 of 2 in the SACAA record retention and declarations effort. The idea (`idea.md`) holds the
why; `answers.md` holds the user's answers; `research_codebase.md` and `research_user_deletion.md`
hold the line-level map of the code this touches.

## Purpose

Close the ordinary user delete paths in the admin. Add one superuser-only, reasoned, audited force
delete for a `User` or a `Learner`. Add `User.last_active` so an admin can see who has gone quiet.
Why: `idea.md` (SACAA's five-year record retention).

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| force delete | coined | The superuser-only admin operation in this spec that deletes a `User` or a `Learner` with its records, a required reason and audit entries. |
| last active | narrowed | `User.last_active`, the new field. On the educator interface "Last active" meant `Max(CourseProgress.last_accessed_time)`; after this spec it means `User.last_active` everywhere. |

## Scope

In:

- `UserAdmin` loses delete: no Delete button, no "delete selected", the stock delete URL answers 403.
- Force delete on `UserAdmin` and `LearnerAdmin`: a changelist action and a change-page button,
  superusers only, through one confirmation page that lists what goes and requires a reason.
- Audit actions and entries for both kinds of force delete.
- `User.last_active`: field, throttled middleware write, `UserAdmin`, user export and API, and every
  educator "Last active" (learner detail page, quick view, learners table and its export).
- Docs, glossary, audit log README and the upgrade note.

Out (from the idea): read-only progress, attempt and answer admins; self-service account deletion;
force delete from the educator interface; any automatic cleanup or deactivation. Also out: the
reports inactivity rule (`reports/gather.py:314`) keeps reading course activity.

## Decisions

- **Superusers only, any time, any account.** `request.user.is_superuser` is the only grant. No
  retention-window check. A superuser may force delete another superuser or their own account.
- **No type-to-confirm.** The listed records plus the required reason are the confirmation, as the
  idea settles.
- **One reason per submission, all or none.** A multi-row action applies the one reason to every
  selected row, and the page says so. The whole submission is one `transaction.atomic()`.
- **`USER_ERASURE_CASCADE_MODELS` keeps its job as the allow-list.** `get_deleted_objects` puts a
  model's `verbose_name` in `perms_needed` whenever that model's admin refuses delete. Force delete
  ignores an entry for the target model or a model in the set; any other entry blocks it, and the
  page names the model. A new append-only model hanging off a user is therefore never erased
  silently: its app registers it in the set. Each app registers its own read-only admins'
  models from its `admin.py`: `deadlines` registers `CoursePause` and `DeadlineExtension`,
  `learner_progress` registers `CourseProgress`, `TopicProgress`, `CourseFormAttempt` and `Learner`,
  and `form_engine` registers `FormProgress`, `QuestionAnswer` and `QuestionAnswerFile`. Their
  admins have refused delete since `remove-unnecessary-admin-panel-functionality`.
- **Unlinked user records.** `USER_ERASURE_UNLINKED_RECORDS`, a list beside
  `USER_ERASURE_CASCADE_MODELS` in `accounts/admin.py`, holds one callable per kind of record a
  user force delete erases that no foreign key reaches, so no collector lists it. Each takes the
  users and returns the model and the count. `course_applications/admin.py` appends the unclaimed
  `AnonymousApplicant` rows that the `pre_delete(User)` receiver erases by email. A seam, because
  `course_applications` sits above `learner_progress` (through `course_access`) and is optional.
- **Force delete lives in `learner_progress`.** It is the lowest app that reaches `User`,
  `Learner`, `CourseProgress` and `FormProgress`; `accounts` and `learner_management` sit below it.
  `learner_progress/admin.py` re-registers `User` with a `UserAdmin` subclass that adds force
  delete, and registers the read-only `LearnerAdmin`.
- **Audit codes.** `user.deleted` (label "User force deleted", group "Other", since `user` has no
  entry in `NOUN_GROUPS`) and `learner.removed` (label "Learner force deleted", group "Learners").
  The glossary's verbs decide the codes: a `User` is a standalone object, a `Learner` the
  `(user, organisation)` association row.
- **Audit shape.** A user force delete writes one `user.deleted` entry with `organisation=None`, plus
  one `learner.removed` entry per `Learner` the user held, each with that learner's organisation, so
  every organisation's audit log shows its loss. A learner force delete writes one
  `learner.removed`. Entries are written inside the transaction, before the delete.
- **Learner force delete takes that organisation's form progress records.** Every `FormProgress`
  reached through a deleted `CourseFormAttempt.form_progress` is deleted too, with its
  `QuestionAnswer` rows and files. Form progress records not linked to the deleted course progress
  stay with the `User`.
- **Last active.** Moved by session-authenticated requests only, at most once per
  `LAST_ACTIVE_WRITE_SECONDS` (default 300). HTMX polling counts: it is an authenticated request.
  API-key requests do not count, and need no code for that: `ApiKeyAuthentication` runs inside DRF,
  after middleware, and sets no `request.user`.
- **`last_login` keeps its meaning.** `account_setup` treats `last_login is None` as "never signed in".

## Requirements

### Admin: no ordinary user delete

- `freedom_ls/accounts/admin.py` `UserAdmin.has_delete_permission` returns False for everyone,
  superusers included. This removes the change-page Delete button and `delete_selected`, and the
  stock delete view answers 403.
- `LearnerAdmin` returns, minimal: `remove-unnecessary-admin-panel-functionality` deleted it, and it
  is learner force delete's only entry point. It is read-only for everyone (`ReadOnlyAdminMixin`):
  a changelist of email, name, organisation, status and date added, searchable by email and name,
  filterable by organisation and status, and a change page showing the same fields. It has no
  inlines and no ordinary delete.
- `course_applications/admin.py`'s `AnonymousApplicantAdmin` docstring and its claimed-applicant
  message ("which the admin can't erase") say a superuser can force delete the user instead.

### Admin: force delete

- Both admins define `has_force_delete_permission(self, request, obj=None) -> bool`. The second
  argument is unused: Unfold passes an `object_id` string for detail actions, the stock action list
  passes nothing.
- Entry points on each admin, all naming `permissions=["force_delete"]`:
  - a stock `@admin.action` in `actions` ("Force delete selected users" / "…learners") that
    redirects the selection to the confirmation view;
  - an `@unfold_action` in `actions_detail` ("Force delete", `variant=ActionVariant.DANGER`) that
    redirects the one row to the same view.
- The confirmation view copies the API-key revoke flow in `api_admin/admin.py`, `api_admin/views.py`
  and `revoke_confirm.html`. Its URL goes in `get_urls()` before `super().get_urls()`, wrapped in
  `admin_site.admin_view`. The view re-checks `has_force_delete_permission`, because anyone can type
  the URL, and loads ids through the admin's `get_queryset`, so another site's row is a 404.
  `admin_page_context` supplies the Unfold page context.
- GET shows the page; POST with a valid form performs the delete, calls `message_user` and redirects
  to the changelist. An invalid POST re-renders the page with the error and deletes nothing. The
  actor and every label are read before the delete, so a superuser force deleting their own account
  gets a redirect (which then lands on login), not an error.
- The form has one field, `reason = forms.CharField(max_length=REASON_LENGTH,
  widget=UnfoldAdminTextareaWidget)`, `REASON_LENGTH` imported from `freedom_ls.audit_log.models`.
  Whitespace-only is invalid.
- The page shows:
  - the records that go, counted per model, with each model's rows listable;
  - for a user, the unclaimed `AnonymousApplicant` rows that the `pre_delete(User)` receiver
    (`course_applications/receivers.py:134`) erases by email, which a collector does not see;
  - for a learner, that the `User` account and its other organisations stay;
  - that SACAA requires records to be kept for five years, with a link to deactivate instead: "deactivate
    the user" to the `User` change page, "deactivate the learner" to the `Learner` change page;
  - the reason field, and that the one reason is recorded against every selected row.
  When a model outside the allow-list blocks, the page says force delete cannot run, names the
  model, and offers no submit.
- The listing joins two `NestedObjects` collections, because collection stops at a `PROTECT` edge:
  one over the course progress records (and, for a learner, the linked form progress records), one
  over the targets themselves. Objects the second collection reports as `protected` are dropped when
  the first collection holds them; any left over block force delete. An object in both collections
  is counted once. The delete runs the same collection code, so the page and the delete agree.
- Delete order, inside one transaction (`PROTECT` makes any other order fail):
  - **User:** `CourseProgress` with `learner__user` in the selection (cascades `TopicProgress`,
    `CourseFormAttempt`, deadline rows), then the users. Everything else cascades from `User`,
    `FormProgress` included.
  - **Learner:** collect the `FormProgress` ids from the learner's `CourseFormAttempt` rows first,
    because those rows go with the course progress; delete the learner's `CourseProgress`, then those
    `FormProgress` rows, then the learner (cascades `CohortMembership`, `LearnerCourseRegistration`,
    `LearnerMessagingConfig`).
  - Lookups inside the transaction use `_base_manager`. The admin `LogEntry` is not written; the
    audit log is the record.

### Audit log

- `freedom_ls/audit_log/actions.py` `FLS_AUDIT_ACTIONS` gains `user.deleted` and `learner.removed`.
- Entries are written with `record_entry` (user) and `record_learner_entry`
  (`learner_management/learner_actions.py:64`, per learner), `actor=acting_user(request)`
  and the reason. `acting_user` moves from `api_admin/audit.py` to `audit_log/writer.py`, so
  `learner_progress` reaches it without depending on `api_admin`.
- Fields: `target_label` is the display name. The user entry's `subjects` holds the user key and
  every learner key; its `details` holds the per-model counts, the count of erased unclaimed
  `AnonymousApplicant` rows and the organisation names. A learner entry's `details` holds that
  learner's counts.

### Last active

- `freedom_ls/accounts/models.py` `User.last_active = models.DateTimeField(null=True, blank=True,
  editable=False)`, added by migration `accounts/0006_*`.
- Migration `learner_progress/0004_*`, a `RunPython` with a no-op reverse that depends on
  `accounts/0006_*` (`learner_progress` depends on `accounts`, not the reverse), sets `last_active` to the later of `last_login` and the user's latest
  `CourseProgress.last_accessed_time`. Existing users then do not show "Never", and educators keep
  the course activity they saw before.
- `AccountsConfig` (`freedom_ls/accounts/config.py`) gains `LAST_ACTIVE_WRITE_SECONDS: int` with
  `Setting(default=300)`.
- `LastActiveMiddleware` in `freedom_ls/accounts/middleware.py`, after `AuthenticationMiddleware`
  and before `RegistrationCompletionMiddleware` in `config/settings_base.py` `MIDDLEWARE`. For an
  authenticated `request.user` whose `last_active` is null or older than the interval, it runs
  `User._base_manager.filter(pk=…).filter(Q(last_active__isnull=True) |
  Q(last_active__lt=cutoff)).update(last_active=now)` and sets the new value on `request.user`. It
  copies `ApiKey`'s `_record_use` (`api/authentication.py:78`): no `save()`, `updated_at` untouched,
  and a fresh value costs no query.
- A system check in `accounts` fails when `LastActiveMiddleware` is missing from `MIDDLEWARE`, after
  `check_htmx_messages_middleware` (`base/checks.py`).
- `UserAdmin`: `last_active` in `readonly_fields`, beside `last_login` under "Important dates", in
  `list_display`, sortable.
- `USER_EXPORT_FIELDS` (`accounts/resources.py:17`) gains `last_active` after `last_login`. This adds
  it to the user export and to the REST API (`accounts/api.py:40` shares the tuple).
- Educator interface, all labelled "Last active", showing the date only, or "Never" when null:
  - `LearnerDetailsPanel.get_rows()` (`educator_interface/panels/learner/panels.py:40`) gains a
    "Last active" row after "Date added", with `kind="text"` and the preformatted value, since the
    `date` kind prints "-" when empty.
  - The learner quick view (`panels/learner/quick_view.py:69`, `quick_views/learner.html:11-16`)
    reads `learner.user.last_active`. The template comment explaining the old choice goes.
  - The learners table (`panels/learner/data_tables.py`) drops the `Max(...)` annotation and reads
    and sorts on `user__last_active`. `_last_active_cell`, used by its export, reads the same value.

## Testing

- `UserAdmin` delete is gone for a superuser: no `delete_selected`, `has_delete_permission` False in
  the change-form context, the stock delete URL answers 403.
- Force delete is superuser-only on both admins: a superuser sees "Force delete" on the `User` and
  `Learner` change pages; a staff user with every model permission sees neither the action nor the
  button, and GET and POST on the view answer 403.
- A user with `CourseProgress`, `TopicProgress`, `CourseFormAttempt`, a `CoursePause`, a
  `DeadlineExtension`, `FormProgress`, `QuestionAnswer` with a file, `LegalConsent`, two `Learner`
  rows in two organisations and an unclaimed `AnonymousApplicant` with their email: the page lists
  every model with the right count, each counted once; POST removes all of it, deletes the answer
  file and profile picture on commit, and writes one `user.deleted` and two `learner.removed` entries
  with the reason, readable after the rows are gone.
- A learner force delete removes that organisation's `Learner`, `CohortMembership`,
  `LearnerCourseRegistration`, `CourseProgress` and linked `FormProgress`, and writes one
  `learner.removed` entry with the reason that shows in that organisation's educator audit log. The
  `User`, their other `Learner` and a `FormProgress` not linked to the deleted course progress
  record stay.
- A multi-row force delete writes one entry per row with the same reason; a failure part-way rolls
  back every row and every entry.
- A missing, blank or too-long reason re-renders the page and deletes nothing.
- A blocking model outside `USER_ERASURE_CASCADE_MODELS`, or a `protected` object not covered by the
  course progress collection, makes the page refuse.
- A walk of every model that cascades from `User`, `Learner` and `CourseProgress` finds none whose
  admin refuses delete and which is missing from `USER_ERASURE_CASCADE_MODELS`.
- Another site's id is a 404. A superuser force deleting their own account gets a redirect, not an
  error, and the entry keeps `actor_label`.
- The vocabulary invariants (`audit_log/tests/invariants/test_vocabulary.py`) pass for both codes.
- Middleware: a stale or null value is written; a fresh one issues no query; anonymous and API-key
  requests (Bearer header, no session) leave it null; `updated_at` and `last_login` do not move; no
  `post_save` fires.
- The system check errors without the middleware.
- The data migration takes the later of `last_login` and course activity, and leaves null when both
  are null.
- The export, the API (`EXPECTED_FIELDS`), `UserAdmin`, and the educator learner detail page, quick
  view, learners table and its export show `User.last_active`.
- Existing tests of the stock user delete and of its "delete the user" messages move to force delete.
- `UserFactory` sets `last_active` to now, so a test client's first request stays within the interval
  and the existing query-count assertions hold.

    brings back a read-only one that carries only learner force delete.

## Open questions

- Q: Should the system check make `LastActiveMiddleware` mandatory for downstream projects? → A: Yes,
  an error when it is missing. (assumed default: without it last active silently stays null, and
  `base/checks.py` sets the precedent. Overrule by editing "Last active".)
- Q: Should existing users get a backfilled last active? → A: Yes, the later of `last_login` and
  latest course activity. (assumed default: otherwise every user shows "Never" until their next
  request, and educators lose the course activity they saw. Overrule by editing "Last active".)
- Q: Should the reports inactivity rule (`reports/gather.py:314`) move to `User.last_active`? → A:
  No. (assumed default: it is a separate report rule the user did not ask to change. Overrule by
  editing "Scope".)
- Q: Should force delete also write Django's admin `LogEntry`? → A: No. (assumed default: `LogEntry`
  cascades with its actor and holds no reason; the audit log is the record. Overrule by editing
  "Admin: force delete".)

## Success criteria

- Force deleting a user with course progress succeeds and leaves no row pointing at them.
- A learner force delete leaves the `User` and their other organisations untouched.
- After a signed-in page view, `User.last_active` is within the interval of now; after an API-key
  request it has not moved.
