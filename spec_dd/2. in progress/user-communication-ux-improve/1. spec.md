# Spec: user-communication UX improvements

Source: `idea.md`.

## Purpose

Direct messaging (spec `user-communication-4-direct-messaging`) works, but people reach it through
too many doors and some doors are missing. This spec makes it one page with one unread signal, lets
anyone with a recipient start a conversation from that page, and gives educators and organisation
admins a view of a learner's conversations from the learner's page.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| messages page | coined | The two-pane page at `/messages/`: the inbox list beside a thread pane. Its URL name stays `conversations:inbox`. |
| messages panel | coined | The disclosure panel the header messages button opens, listing recent conversations. Modelled on the bell panel. |
| oversight | coined | Read-only access, for holders of `freedom_ls_comms.view_conversation`, to a learner's `Conversation` rows whose other participant is in `educators_of(learner)`. |

## Scope

In:

- Header messages button: icon only, opening the messages panel.
- Messages stop raising bell notifications.
- The messages page replaces the list-only inbox view.
- Starting a conversation from the messages page, with recipients listed before typing.
- Learners may message their educators by default.
- The educator-interface Messages section is removed.
- A Messages tab on the educator interface's learner page.
- Oversight for organisation and site admins, audited and disclosed.

Out:

- The course-player "ask for help" request, the shared help-desk queue and help tickets. These go
  to the follow-up `spec_dd/1. next/user-communication-help-desk/`.
- Learner-to-learner defaults. `learner_to_cohort_peer` and `learner_to_course_peer` stay closed
  until report and block exist (`user-communication-6-moderation`).
- Oversight of learner-to-learner and educator-to-educator conversations, and an
  organisation-wide conversation list. Oversight is reached through the learner page only.
- A setting to switch oversight off.
- Group conversations, attachments and real-time push, as in spec 4.

## Decisions

1. **`message.received` is deleted, not hidden.** The header badge already shows unread
   conversations, so a bell row repeats it. The rollup machinery (`NotificationCategory.rollup`,
   `Notification.rollup_key`, the rollup branch in `comms/notify.py`, `mark_notifications_read`)
   stays, tested against a test-only category, because the next rollup category will need it.
   Existing `message.received` rows stay where they are. `NotificationManager` already hides rows of
   unconfigured categories, so no data migration is needed.
2. **The URL name `conversations:inbox` stays.** Every `reverse("conversations:inbox")` caller
   (login redirect, back links) stays valid. Only the view and template change.
3. **No conversation is auto-selected on `/messages/`.** Auto-selecting would mark a thread read that
   the user never chose to open.
4. **Oversight never goes through participant code paths.** `participant_conversation()` 404s
   non-participants and `thread_context()` marks the thread read. Oversight uses neither, so a
   participant's unread state can't change because an admin looked.
5. **Disclosure is static copy.** `comms` may not import organisation or role code
   (`comms/tests/invariants/test_boundaries.py`), and one line is accurate for every conversation:
   "Organisation admins can read conversations between learners and their educators."

## Requirements

### Header messages button and messages panel (`freedom_ls/comms/`)

- `templates/comms/partials/messages_button.html` becomes a `<button>` holding only
  `<c-icon name="message">` and the `#messages-badge` badge. The visible "Messages" label is removed at
  every width. The accessible name still reads "Messages" plus the unread count, through the
  existing `aria-labelledby="messages-button-label"` span that `unread_badge.html` supplies. The
  badge's `hx-get`/`hx-trigger` and `refreshTimer` polling are unchanged.
- The button opens the messages panel, a WAI-ARIA disclosure with the bell panel's behaviour
  (`partials/notification_bell.html`): `aria-expanded`, Escape and click-away close it, focus returns
  to the button, a full-screen sheet below `sm` with a close button, separate loading and failed
  blocks with "Try again". It uses the bell's markup rather than `<c-dropdown-menu>`, because the
  menu component has no sheet or loading states.
- A new Alpine component, `messagesPanel`, in `comms/static/comms/js/alpine-components.js`, shares
  its open, close and retry logic with `notificationBell` through one helper.
- The panel's content loads on first open from a new URL, `conversations:recent` (`recent/`), view
  `partial_recent_conversations` under `@messaging_view`. Page renders still run no conversation
  query. The panel reloads on `conversationChanged from:body` while open.
- The view reads the five most recent conversations from a new
  `recent_conversations_for(user, limit)` in `comms/messaging.py`. It wraps `inbox_for` and adds a
  `last_message_body` subquery annotation, so `inbox_for` and the badge poll pay nothing extra. Rows
  show avatar, the other participant's name, a one-line excerpt, relative time, and unread styling
  that doesn't rely on colour alone. Each row links to `conversations:thread`.
- Panel header: "New message", linking to `conversations:start`, when the user has recipients.
  Footer: "See all messages", linking to `conversations:inbox`. Empty state: "No messages yet.", plus
  "New message" when the user has recipients.
- Opening the messages panel closes the bell panel, and the reverse. Both sit in
  `freedom_ls/base/templates/partials/header_bar.html`.

### Messages raise no notification (`freedom_ls/comms/`, `freedom_ls/base/`)

- No code path, the QA scenario commands included, raises or marks `message.received`. The
  category in `freedom_ls/base/notification_categories.py`, its URL resolver and the resolver's test
  are removed.
- `comms/tests/test_notify.py` uses a test-only `rollup=True` category.

### The messages page (`freedom_ls/comms/`)

- `messaging_views.inbox` renders `comms/thread.html` with no conversation selected. `thread.html`
  gets its own placeholder branch for that case and doesn't include `partials/thread.html`, which
  assumes a conversation. The placeholder reads "Select a conversation to read it." When the user has
  no conversations, it says so instead. Either way it offers "New message" when the user has
  recipients. `comms/inbox.html` is deleted. The htmx branch keeps returning the `conversation-list`
  partial for `inbox_poll`.
- Both `inbox` and `thread` supply `has_recipients`, from one shared helper.
- The list pane gets a header with the title "Messages" and a "New message" button, gated on
  `has_recipients`. The selected row carries `aria-current="true"`.
- Below `md`: with no thread selected, the list fills the page. With a thread selected, the thread
  fills the page and the back arrow in `partials/thread.html` links to `conversations:inbox`. Thread
  selection uses real links, so browser back and deep links work.

### Starting a conversation (`freedom_ls/comms/`, `freedom_ls/messaging_policy/`)

- On wide screens, "New message" on the messages page swaps the recipient picker
  (`partials/recipient_picker.html`) into the thread pane. Choosing a recipient swaps in the composer
  for that recipient. On narrow screens, and for direct links, it goes to the full
  `conversations:start` page, whose back link goes to `conversations:inbox`.
- The first send answers with `HX-Location` to the new thread, as `_send_response` does. Choosing
  someone the user already has a conversation with opens that conversation. A send refused by policy
  returns 422 and keeps the draft.
- `search_recipients` with an empty term lists recipients straight away, grouped by
  `group_recipients` and capped at `PICKER_RESULT_LIMIT`. Above the cap, the existing truncation note
  asks the user to type to narrow it. `PICKER_MIN_TERM_LENGTH` no longer gates the first list, and
  `PICKER_LIST_ALL_LIMIT` is removed. Absent and refused names still produce identical output.
- In `messaging_policy/config.py`, `MESSAGING_DEFAULT_FLAGS["learner_to_educator"]` becomes `"open"`.
  The peer flags stay `"closed"`, and offered roles stay `["cohort_admin"]`. Per-site, organisation,
  cohort, registration and learner rows still override the default.

### Educator interface: Messages section removed (`freedom_ls/educator_interface/`)

- The Messages section (`MessagesConfig`) and everything only it uses are removed, including its
  unread-count endpoint and `conversations_in_organisation`. The generic panel-framework hooks
  (`get_menu_count_url`, `get_menu_count_poll_seconds`, `is_available`) stay.
- The "Open conversation" link in the `LearnerQuickView` message box points to the learner page's
  Messages tab.

### Educator interface: Messages tab on the learner page (`freedom_ls/educator_interface/`)

- A new `LearnerMessagesPanel` (`model = Learner`) joins `LearnerTabSet.children` as `"messages"`,
  shown when `MESSAGING_ENABLED` is on. Its body loads when the tab activates.
- Own conversation: shown when the signed-in user has a conversation with the learner, or
  `get_messaging_policy().can_start` allows one. It reuses `comms/partials/thread.html` through
  `thread_context()` with a fixed pane height and no `back_url`, so opening it marks the
  conversation read for that user, with a composer beneath. With no conversation yet, it shows "No messages with <name> yet."
  and a composer addressed to the learner. Sends from the tab, the first one included, re-render the
  tab in place, through a tab-keyed response mode like `_quick_view_box_response`. They never
  redirect to `/messages/<pk>`.
- Oversight list: shown to holders of `freedom_ls_comms.view_conversation` on the learner, whatever
  the own-conversation area shows. It lists the learner's other conversations under oversight,
  excluding the viewer's own. Rows show the educator's name, an excerpt and the last-message time.
  The empty state reads "No other educator conversations."

### Oversight (`freedom_ls/educator_interface/`, `freedom_ls/comms/`, `freedom_ls/role_based_permissions/`, `freedom_ls/audit_log/`)

- Permission: `freedom_ls_comms.view_conversation`, the model's default view permission. It goes in
  `role_based_permissions/registry.py` and on `organisation_admin` and `site_admin` in `roles.py`,
  scoped to the learner. `can()` reads the role config live, so no data migration is needed. No other
  role holds it.
- The query lives in `educator_interface/messaging.py`, and `comms` gains no imports. It returns the
  learner's `Conversation` rows whose other participant is in `educators_of(learner)` at read time.
  So: a conversation with someone who has lost their educator role drops out; a deactivated learner
  has nothing under oversight; and a learner's conversation with an organisation or site admin is
  visible to other admins.
- Each oversight-list row opens the read-only thread through a row-scoped `PanelAction` with no
  `refresh_events`, authorised by `LearnerConfig.authorise_instance` plus the permission. A
  conversation outside the learner's oversight set is a 404.
- `partials/thread.html` takes a read-only flag. Under it, it renders no composer, no closed note and
  no poll span, and shows the banner "Read only. You are viewing this conversation as <role>.",
  where <role> is "a site admin" when the viewer's access comes from `site_admin` and "an
  organisation admin" otherwise. A comms helper builds the message page for a given conversation with no viewer
  side effects. A separate oversight endpoint under the learner instance serves older pages and
  writes no audit entry.
- Each open of the action writes one audit entry: `AuditAction("conversation.viewed",
  "Conversation viewed", ...)` in `audit_log/actions.py`, recorded through
  `audit_log/writer.py:record_entry`. The target is the `Conversation`, with label "Conversation with
  <name of the educator in the conversation>". The subject is the learner, the organisation is the
  learner's, and the actor is the viewer. The entry shows in the learner's History tab.
- The disclosure line from Decision 5 renders, in muted text, beside every composer
  (`comms/partials/composer.html` and the composer for a new conversation), and in the
  `partials/thread.html` footer whenever no composer shows.

## Testing

- The header button has no visible text, and its accessible name includes the count.
  `conversations:recent` returns at most five of the viewer's own conversations, newest first, with
  the excerpt and unread marker. The empty state follows `has_recipients`.
- Opening one header panel closes the other (Playwright).
- Sending a message creates no `Notification` row. The rollup suite passes on the test-only category.
- `/messages/` renders the placeholder and marks nothing read. At a narrow viewport the user goes from
  the list to a thread and back to the list (Playwright).
- An empty picker term lists grouped, capped recipients, with the truncation note above the cap.
  "New message" works from a selected-thread page. Choosing a recipient with an existing
  conversation opens it. A policy-refused first send returns 422 and keeps the draft. Absent and
  refused names give identical picker output.
- The disclosure line renders beside the composer, beside the new-conversation composer, and in the
  thread footer when no composer shows (a participant refused by `can_reply`, and the read-only
  oversight view).
- With no override rows, a learner can start a conversation with a `cohort_admin` of their cohort and
  can't start one with a cohort peer. An organisation row closing `learner_to_educator` still closes
  it.
- The educator URL `.../messages/` is a 404, and the sidebar has no Messages entry. The interface walk
  and the invariant suites (`test_permission_matrix.py` with a `VIEW_CONVERSATION` entry,
  `test_organisation_isolation.py`, `test_config_authorisation.py`) pass.
- Messages tab: an educator sees only their own conversation with the learner, and a first send stays
  on the learner page. An educator from another organisation gets a 404. With `MESSAGING_ENABLED`
  off there is no Messages tab. The quick-view "Open conversation" link points to the tab.
- Oversight: an organisation admin sees the learner's conversations with educators but not with
  peers. A deactivated learner shows an empty list. `cohort_admin` and `cohort_viewer` see no
  oversight list. Opening a conversation writes exactly one `conversation.viewed` entry, leaves both
  participants' `last_read_at` unchanged, renders no composer, and pages back through older
  messages. The entry shows in the learner's History tab. A conversation outside the set, or another
  organisation's learner, is a 404.

## Documentation and downstream

- The product docs and the `notifications` skill stop saying that messages raise notifications or
  that only the two participants can read them. The docs describe what this spec adds.
- `.claude/skills/domain-glossary/SKILL.md` gains an **oversight** (coined) row under Messaging, and
  `conversation` and `viewed` in the audit vocabulary, which `audit_log/tests/invariants/test_vocabulary.py`
  checks against.
- `spec_dd/1. next/roadmap.md`: the `user-communication-2-notification-email` row notes that message
  emails need their own trigger.
- Upgrade notes: the `educator_interface:messages*` URLs, the `message.received` category and
  `PICKER_LIST_ALL_LIMIT` are gone. Learners can message cohort admins unless the project overrides
  `MESSAGING_DEFAULT_FLAGS`. Organisation and site admins can read learner-educator conversations.

## Success criteria

- On a fresh install, a learner in a cohort with a `cohort_admin` starts a conversation with them
  from `/messages/`.
- An organisation admin opens a learner's conversation with an educator from the learner page and
  can't reply. The open appears in the learner's History tab.
