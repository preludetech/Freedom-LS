# Spec: Profile picture on id-only rows

Source: `idea.md` in this directory. Recorded answers: `answers.md`. Research: the `research_*.md`
files beside this spec. Predecessor:
`spec_dd/3. done/2026-11-15_09:21_learner-public-profile-1-profile-picture/1. spec.md`, whose
avatar rules (bound `:picture_url`, `alt=""`, `data-profile-picture`, initials underneath, the
`profile-picture-fallback.js` error listener) apply here unchanged.

## Purpose

A person with a profile picture shows it on the four educator surfaces that still render initials
from ids, and a learner has the same avatar colour there as in the learners table.

## Scope

In:

- Dashboard attention rows (`educator_interface/panels/dashboard_region.html`).
- Cohort attention rows (`educator_interface/panels/cohort_needs_attention_region.html`).
- The on-screen cohort report (`educator_interface/panels/cohort_report_body_region.html`): its
  "Learners needing attention" list and its "Summary of learner progress" name column
  (`answers.md`).
- The audit log who and target (`educator_interface/partials/audit_person.html`), on every page
  that renders it: the History tabs, the targeted log, the organisation log, run-entry detail and
  the mobile cards.

Out:

- The cohort report PDF (`freedom_ls/reports/templates/reports/`). It stays initials-only.
- `reports/screen_cache.py`, `reports/gather.py` and `reports/report_data.py`.
- The deleted-user and system branches of `audit_person.html`. A deleted user keeps the neutral
  circle and never gets a picture.

## Decisions

- **Cached `learner_id` is a `Learner` pk, not a `User` pk.** `reports/indexes.py` `load_roster`
  keys the roster on `CohortMembership.learner_id`. Report rows resolve through `Learner`, never
  `User.objects.filter(pk__in=…)`.
- **Resolve at render, in the panel or table, never in the cache.** Each render collects its ids,
  makes one query, and mints URLs through `User.profile_picture_url`. No URL enters
  `screen_cache`, a snapshot or a cached dataclass, so `SCHEMA_VERSION` stays 2. A changed or
  removed picture shows on the next render.
- **One extra query per render, none when there are no ids.** At most 12 learner ids on an
  attention list (`ATTENTION_LIST_MAX` in `reports/report_data.py`), up to
  `REPORTS_MAX_LEARNERS` (500) on the report, one page on the audit log. The count does not grow
  with rows or cohorts.
- **Attention and report rows key the avatar colour on the user pk**, as
  `data-table-cells/learner.html` does (`learner.user.pk`). Today they pass the `Learner` UUID.

## Requirements

### Resolver

New module `freedom_ls/educator_interface/avatars.py`. It imports models only, never
`educator_interface.views` or `reporting`, because `reporting` and the template tags import it.

- `PersonAvatar`, a frozen dataclass (not a model): `user_pk: int` and `picture_url: str | None`.
- `learner_avatars(learner_ids: Iterable[UUID]) -> dict[UUID, PersonAvatar]`: turns the ids into a
  set first, returns `{}` with no query when it is empty, otherwise makes one query:
  `Learner.objects.filter(pk__in=ids).select_related("user").only("pk", "user",
  "user__profile_picture")`. An id with no `Learner` row is absent from the result.
- `user_picture_urls(user_pks: Iterable[int]) -> dict[int, str]`: the same set and empty rules,
  one `User.objects.filter(pk__in=…).only("pk", "profile_picture")` query. Only users with a
  picture are in the result. It returns URLs alone because audit log callers already hold the user
  pk.
- No `is_active` filter in either: an inactive user keeps their picture.

A new filter, `lookup`, in `educator_interface/templatetags/educator_tags.py` returns
`mapping.get(key)`; no dict-lookup filter exists today. A missing key gives `None`, which the chip renders as initials.

### Attention rows and the on-screen cohort report

- `freedom_ls/panel_framework/templates/cotton/panel-attention-row.html`: add `picture_url=""` to
  `c-vars`, a plain string, forward it as `:picture_url="picture_url"` to `c-panel-person-link`,
  and document it in the comment block.
- `educator_interface/reporting.py` adds `avatars` to each panel's loaded context:
  - `DashboardPanel`: from `figures.attention_rows`.
  - `CohortNeedsAttentionPanel`: from `attention.learners`.
  - `CohortReportBodyPanel`: from `data.learners` together with every `learner_id` in each
    section's `learner_rows`, in one call. The two lists are cached separately and their id sets
    may differ.
- `dashboard_region.html`, `cohort_needs_attention_region.html` and `cohort_report_body_region.html`
  (its attention list and the summary table's `c-panel-person-link`, line 75) look up the row's
  avatar and pass `:user_id` as its `user_pk`, falling back to the row's `learner_id` when there is
  no avatar, and `:picture_url` as its `picture_url`. The fallback keeps `user_id` non-empty, which
  `panel-attention-row` and `panel-person-link` test with `|flag` to show the chip.
- Nothing under `freedom_ls/reports/templates/` changes.

### Audit log

- `educator_interface/views.py` `_attach_target_users` also sets the pictures, so its three call
  sites (`AuditLogEntryTable.get_rows` and both paths of `OrganisationAuditLogTable.get_rows`,
  including nested run entries) need no new call. After the target lookups it collects every
  `actor_id` and `target_user_pk`, calls `user_picture_urls` once, and sets
  `entry.actor_picture_url` and `entry.target_picture_url`. Both start as `None` on every entry.
  Rename the function `_attach_people`, to match what it now does.
- Declare both annotations on `AuditLogEntry` beside `target_user_pk` (`audit_log/models.py`).
- `audit_person.html` takes a `picture_url` and passes it, bound, to the chip in the `user_pk`
  branch only. `data-table-cells/audit_who.html` and `partials/audit_row_detail.html` (actor, line
  18) pass `actor_picture_url`; `data-table-cells/audit_target.html` passes `target_picture_url`.
  The mobile cards include these cells.
- The picture follows the live user: a picture removed after the entry was written no longer
  shows.

## Testing

- Resolver: no ids makes no query; a generator of ids is read once; a `Learner` id maps to its
  user's pk and URL with no further query when `picture_url` is read; an unknown id is absent; a
  user without a picture has `picture_url` `None` (learners) or is absent (users).
- Each surface renders `img[data-profile-picture]` (`educator_interface/tests/helpers.py`
  `profile_picture_sources`) for a person with a picture and initials alone for one without, never
  `src="None"`. For the audit log this covers who, target and the run-entry detail.
- A report or attention row whose `Learner` is gone renders initials with a chip, without error.
- More rows with pictures cost no more queries on each surface (the
  `test_more_learner_rows_with_pictures_cost_no_more_queries` pattern). The dashboard's warm-load
  test still passes.
- An attention row and a learners-table row for the same learner carry the same `panel-avatar-N`
  class.
- Audit log: a deleted actor shows the neutral circle and no picture; a system entry shows the
  system chip. `test_the_audit_log_names_a_person_with_initials_alone`
  (`educator_interface/tests/test_views.py`) flips to assert the picture.
- The rendered PDF report HTML for a cohort whose learners have pictures contains no
  `data-profile-picture` (`reports/tests/test_render.py`).
- `panel_framework` component test for `panel-attention-row` with and without `picture_url`.
- QA data: an attention-row learner, an audit actor and an audit target each with a picture.

## Documentation and downstream

- `panel_framework/templates/panel_framework/reference/_examples.html` and the `panel-framework`
  skill document `panel-attention-row`'s `picture_url`.
- No migration and no new setting, so downstream projects need no upgrade step.

## Success criteria

- Each surface in Scope makes at most one more query than before this work, with 1 row or 25.
- No surface outside Scope changes its output.
