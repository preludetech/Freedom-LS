# Spec: Profile picture on id-only rows

Source: `idea.md` in this directory. Recorded answers: `answers.md`. Research: the `research_*.md`
files beside this spec. Predecessor:
`spec_dd/3. done/2026-11-15_09:21_learner-public-profile-1-profile-picture/1. spec.md`, whose
avatar rules (bound `:picture_url`, `alt=""`, `data-profile-picture`, initials underneath, the
`profile-picture-fallback.js` error listener) apply here unchanged.

## Purpose

The predecessor put the profile picture on every surface that holds a loaded `User`. Four educator
surfaces still show initials because they render from ids: the dashboard and cohort attention
rows, the on-screen cohort report, and the audit log's who and target. After this work a person
with a profile picture shows it on all four, and a learner looks the same there as in the learners
table.

## Scope

In:

- Dashboard attention rows (`educator_interface/panels/dashboard_region.html`).
- Cohort attention rows (`educator_interface/panels/cohort_needs_attention_region.html`).
- The on-screen cohort report (`educator_interface/panels/cohort_report_body_region.html`): its
  "Learners needing attention" list and its "Summary of learner progress" name column
  (`answers.md`).
- The audit log who and target (`educator_interface/partials/audit_person.html`), on every page
  that renders it: the History tabs, the targeted log, the organisation log, run-entry detail and
  the mobile cards.

Out:

- The cohort report PDF (`freedom_ls/reports/templates/reports/`). It stays initials-only.
- `reports/screen_cache.py`, `reports/gather.py` and the cached dataclasses in
  `reports/report_data.py`. They do not change shape, and `SCHEMA_VERSION` stays 2.
- The deleted-user and system branches of `audit_person.html`. A deleted user keeps the neutral
  circle and never gets a picture.

## Decisions

- **Cached `learner_id` is a `Learner` pk, not a `User` pk.** `reports/indexes.py` `load_roster`
  keys the roster on `CohortMembership.learner_id`. Report rows resolve through
  `Learner.objects.filter(pk__in=ids).select_related("user")`, never `User.objects.filter(pk__in=…)`.
- **Resolve at render, in the panel or table, never in the cache.** Each render collects its ids,
  makes one query, and mints URLs through `User.profile_picture_url`. No URL enters
  `screen_cache`, a snapshot or a cached dataclass. A changed or removed picture shows on the next
  render, without waiting for the cache TTL.
- **Query cost: one query per render, none when there are no ids.** At most 12 learner ids on an
  attention list (`ATTENTION_LIST_MAX`), up to `REPORTS_MAX_LEARNERS` (500) on the report, and one
  page (25 entries plus nested run entries) on the audit log. The query count does not grow with
  rows or cohorts.
- **Attention and report rows key the avatar colour on the user pk.** Today they pass the
  `Learner` UUID as `user_id`, so their colour differs from `data-table-cells/learner.html`, which
  keys on `learner.user.pk`. The resolver already returns the user pk, so these rows pass it
  instead. A learner whose `Learner` row is gone falls back to the `Learner` UUID, as today.
- **The panel framework stays FLS-free.** `panel-attention-row` gains a plain `picture_url` string,
  as the predecessor gave `panel-avatar-chip` and `panel-person-link`.

## Requirements

### Resolver

New module `freedom_ls/educator_interface/avatars.py`:

- `PersonAvatar`, a frozen dataclass: `user_pk` and `picture_url: str | None`.
- `learner_avatars(learner_ids: Iterable[UUID]) -> dict[UUID, PersonAvatar]`: de-duplicates the
  ids, returns `{}` with no query when there are none, otherwise makes one query through
  `Learner.objects` with `select_related("user")` and `only()` the learner pk, user pk and
  `user__profile_picture`. An id with no `Learner` row is absent from the result.
- `user_picture_urls(user_pks: Iterable[int]) -> dict[int, str]`: the same rules with one
  `User.objects.filter(pk__in=…).only("pk", "profile_picture")` query. Only users with a picture
  are in the result.
- No `is_active` filter in either: an inactive user keeps their picture.

Templates read the dicts through one new filter in the educator interface's template tags that
returns `mapping.get(key)` (no dict-lookup filter exists today). A missing key is `None`, which the
chip renders as initials.

### Attention rows

- `freedom_ls/panel_framework/templates/cotton/panel-attention-row.html`: add `picture_url=""` to
  `c-vars`, forward it as `:picture_url="picture_url"` to `c-panel-person-link`, and document it in
  the comment block.
- `educator_interface/reporting.py`:
  - `DashboardPanel.get_loaded_context` adds `avatars = learner_avatars(row.learner_id for row in
    figures.attention_rows)`.
  - `CohortNeedsAttentionPanel.get_loaded_context` adds `avatars` for `attention.learners`.
- `dashboard_region.html` and `cohort_needs_attention_region.html` pass the row's avatar:
  `:user_id` gets the `PersonAvatar.user_pk` (the `learner_id` when absent) and `:picture_url` its
  `picture_url`.

### On-screen cohort report

- `CohortReportBodyPanel` (`educator_interface/reporting.py`) adds `avatars =
  learner_avatars(...)` over the ids of `data.learners`, which covers both the attention list and
  every summary table chunk.
- `cohort_report_body_region.html`: the attention list's `c-panel-attention-row` and the summary
  table's `c-panel-person-link` (line 75) take `:user_id` and `:picture_url` from the avatar, as
  above.
- Nothing under `freedom_ls/reports/templates/` changes.

### Audit log

- `educator_interface/views.py`: a new `_attach_avatars(entries)`, called after
  `_attach_target_users` wherever that runs (`AuditLogEntryTable.get_rows`,
  `OrganisationAuditLogTable.get_rows` including its nested run entries). It collects every
  `actor_id` and `target_user_pk`, calls `user_picture_urls` once, and sets
  `entry.actor_picture_url` and `entry.target_picture_url`. Declare both annotations on
  `AuditLogEntry` beside `target_user_pk` (`audit_log/models.py`).
- `audit_person.html` takes a `picture_url` and passes it, bound, to the chip in the `user_pk`
  branch only. Its includers (`data-table-cells/audit_who.html`, `audit_target.html`,
  `partials/audit_row_detail.html`, `audit_log_card.html`, `audit_log_card_targeted.html`) pass the
  matching attribute.
- The picture follows the live user: a picture removed after the entry was written no longer
  shows.

## Testing

- Resolver: no ids makes no query; a `Learner` id maps to its user's pk and URL; an unknown id is
  absent; a user without a picture has `picture_url` `None` (learners) or is absent (users); 12
  ids make one query.
- Each surface renders `img[data-profile-picture]` (`educator_interface/tests/helpers.py`
  `profile_picture_sources`) for a person with a picture and initials alone for one without, never
  `src="None"`.
- Query counts: more rows with pictures cost no more queries on each surface (`page_after_adding_rows`
  pattern, or `test_more_learner_rows_with_pictures_cost_no_more_queries`). The dashboard's
  existing warm-load test still passes.
- Colour: an attention row and a learners-table row for the same learner carry the same
  `panel-avatar-N` class.
- Audit log: a deleted actor shows the neutral circle and no picture; a system entry shows the
  system chip. `test_the_audit_log_names_a_person_with_initials_alone`
  (`educator_interface/tests/test_views.py`) flips to assert the picture.
- PDF: the rendered report HTML for a cohort whose learners have pictures contains no
  `data-profile-picture` (`reports/tests/test_render.py`).
- `panel_framework` component test for `panel-attention-row` with and without `picture_url`.
- QA data: an attention-row learner, an audit actor and an audit target each with a picture. The
  predecessor's QA could not check these surfaces because no such row named a user with one.

## Documentation and downstream

- `panel_framework/templates/panel_framework/reference/_examples.html` and the `panel-framework`
  skill document `panel-attention-row`'s `picture_url`.
- No migration and no new setting, so downstream projects need no upgrade step.

## Open questions

- Q: Should attention and report rows switch their avatar colour key from the `Learner` UUID to the
  user pk? → A: Yes. (assumed default: `data-table-cells/learner.html` already says a person keeps
  one colour across the interface, and the resolver returns the user pk at no extra cost. Overrule
  by editing "Decisions".)

## Success criteria

- A learner with a picture who needs attention shows it on the dashboard, the cohort attention
  list and the on-screen cohort report's attention list and summary table.
- An audit log entry whose actor or target has a picture shows it; a deleted actor shows the
  neutral circle.
- Each of those renders makes at most one extra query, whatever the number of rows.
- The cohort report PDF contains no profile picture.
- The same learner has the same avatar colour on an attention row and in the learners table.
