# Frontend QA plan: production object storage bucket layout

## What changed, and why a browser pass is worth doing

This is a settings and storage-layer change. No template, view, URL or CSS was touched. So the
question this QA answers is not "does the new UI work" but "did rewiring where files live break any
of the three places a user actually sees a stored file".

Three model fields moved off Django's `default` storage alias onto named aliases:

| Field | Alias it now names | Where a user sees it |
|---|---|---|
| `content_engine.File.file` | `course_media` | Images, embedded PDFs and download links inside course content |
| `organisations.Organisation.logo` | `public` | The organisation logo in the course table-of-contents header, and the admin form |
| `reports.GeneratedReport.file` | `reports` | The cohort report PDF download in the admin |

In dev every alias resolves to the same `FileSystemStorage` rooted at `MEDIA_ROOT`, so if the wiring
is right nothing visible changes at all. That is the point: **this QA is looking for regressions, not
for new behaviour.** A broken alias shows up as a missing image, a 500, or a server that will not
start.

One thing genuinely does change in dev: new report PDFs are written under `cohort_reports/` instead
of `reports/`. Report rows that already existed keep their old `reports/...` key in the database, so
both have to keep downloading. Part D covers that.

## Setup

**Server.** Do not use port 8000.

```
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL: `http://127.0.0.1:$PORT`

**Site.** Dev forces `FORCE_SITE_NAME = "DemoDev"`, so site selection does not depend on the port.

**Admin.** `http://127.0.0.1:$PORT/admin/`, logging in as `demodev@email.com` / `demodev@email.com`. If the user
does not exist: `uv run python manage.py create_demo_data`.

**Content.** Load the two demo courses that carry files:

```
uv run python manage.py content_save demo_content/functionality_demo_content_widgets DemoDev
uv run python manage.py content_save demo_content/functionality_demo_end_with_topic DemoDev
```

The first carries `c-picture` images and an image grid. The second carries `c-pdf-embed` and
`c-file-download` pointed at `sample.pdf`, so it exercises the non-image path too.

**Organisations.** `uv run python manage.py qa_create_organisations` seeds "RPAS Training" (has a
logo, so the logo path renders) and "Northside" (no logo, so the monogram fallback renders).

**Report data.**

```
uv run python manage.py qa_create_report_cohort --cohort-name "QA Storage Cohort" \
  --num-learners 9 --course-slug <slug-of-a-loaded-course> --num-flagged 2 \
  --educator-email qa-educator@email.com
```

The `--educator-email` learner is granted `view_cohort` on that cohort only. Part E uses it.

**Report generation needs a worker and a Tailwind bundle.** Reports render as a background task:

```
npm run tailwind_build
uv run python manage.py db_worker
```

Run the worker in its own terminal. Without it a requested report stays `pending` forever, which
would read as a storage failure and is not one.

**Baseline for the media check.** Before you start, note what is in the working tree's `media/`:

```
ls media/
```

You will compare against this at the end of Part F.

# Part A. The application still starts

The failure mode this change introduces is not a broken page. It is a broken import. A callable
`storage=` is resolved once, at model import, so an alias that is not declared takes down
`runserver`, `migrate` and `pytest` together rather than degrading. Check this first, because if it
fails nothing else in this plan can run.

## Test A1: server and checks come up clean

1. `uv run python manage.py check`, which must exit 0.
2. Confirm **no** `freedom_ls_reports.W001` appears. It was retired; if it still fires, the old check
   was not deleted.
3. Confirm **no** `freedom_ls_deployment.E001` appears. It is a `deploy=True` check and must be
   silent on plain `check`, on `runserver`, on `migrate` and in the test suite.
4. Start `runserver` on `$PORT`. Expect a normal boot with no `InvalidStorageError` and no traceback.
5. Load `http://127.0.0.1:$PORT/` and log in at `/accounts/login/`. Expect the dashboard.

**Expected:** clean boot, clean check, no storage warnings of any kind.

**If step 4 raises `InvalidStorageError`:** the base settings module is missing an alias key that a
model field names. That is the ordering constraint in the plan, not a data problem. No amount of
QA setup will fix it.

# Part B. Course media (`course_media` alias)

`content_engine.File.file` now names an alias instead of falling to `default`. Every cotton
component that renders `file_obj.file.url` is downstream of this.

## Test B1: images render inside course content

1. Go to `http://127.0.0.1:$PORT/courses/` and open the **content widgets** demo course.
2. Navigate to the **media** topic.
3. Expect every `c-picture` to render an actual image, not a broken-image icon and not alt text
   alone. There are several, including a two-column image grid and a numbered figure.
4. Click one image. Expect the lightbox to open full-screen with the title and description beneath.
5. Open DevTools → Network, reload, and filter to images. Every image request should be **200**.
   A **404** on a `/media/content_engine/...` URL means the file is on the wrong alias or was never
   written.

**Expected:** all images load, lightbox works, no 404s under `/media/`.

## Test B2: embedded PDF and file download

1. Open the **end with topic** demo course, first topic.
2. Expect the `c-pdf-embed` block to render the sample PDF inline in an iframe or object, not an
   empty box.
3. Click the **Download the sample PDF** link. Expect the PDF to download or open, not a 404.

**Expected:** both the inline embed and the download resolve. These are the non-image branch of the
same alias, and they fail differently from images, so check both.

## Test B3: uploading a new file through the admin

1. Go to `http://127.0.0.1:$PORT/admin/` → **Content engine** → **Files** → **Add**.
2. Upload any small image, fill the required fields, save.
3. On the change form, the **Currently:** link should be present. Click it. Expect the file to
   serve, not 404.
4. Confirm on disk that it landed under `media/content_engine/`.

**Expected:** upload succeeds, the admin link resolves, the key keeps its existing
`content_engine/` prefix. The prefix is deliberately unchanged by this work. If it moved, something
edited `file_upload_handler` that should not have.

# Part C. Organisation logo (`public` alias)

`Organisation.logo` now names the `public` alias. The logo has a **stable** key,
`organisations/{pk}{ext}`, so a re-upload overwrites the same object at the same URL. That
mutability is deliberate and is worth exercising, because it is the reason this alias does not get
an immutable cache header in production.

## Test C1: the logo renders in the course header

1. Log in as a learner registered on a course belonging to **RPAS Training** (the organisation
   `qa_create_organisations` gave a logo). If no learner is registered there, use the admin to
   register one, or use the educator interface.
2. Open that course. In the course table-of-contents header, expect the **RPAS Training logo image**,
   scaled to fit and sitting on an opaque surface fill.
3. Open a course belonging to **Northside**, which has no logo. Expect the **monogram fallback**
   ("NO"), not a broken image and not an empty gap.

**Expected:** logo where there is one, monogram where there is not. The no-logo branch matters. A
storage misconfiguration can make a present logo fail in a way that looks identical to the empty
case, so check both to tell them apart.

## Test C2: uploading and replacing a logo

1. Admin → **Organisations** → open **Northside** (no logo).
2. Upload a logo. Save.
3. Expect the **Currently:** link to appear and to resolve when clicked.
4. Reload the learner-facing course header for Northside. Expect the monogram to be replaced by the
   image.
5. Now upload a *different* logo to the same organisation and save.
6. Check the `Currently:` filename. For a same-extension replacement the key is unchanged, so the
   URL is identical and the browser may serve the cached old image. **Hard-reload** (Ctrl+Shift+R)
   and confirm the new image appears.
7. Confirm on disk that `media/organisations/` holds one file per organisation, not an accumulating
   pile of uniquely-named ones.

**Expected:** replacement overwrites in place at a stable key. Step 6's cache behaviour is expected,
not a bug. Note it, do not file it.

## Test C3: logo validation still rejects bad uploads

The validators are untouched, so this is a pure regression check that rewiring `storage=` did not
disturb the upload path.

1. Admin → **Organisations** → try to upload a `.gif`. Expect a **field validation error**, and
   expect the form to redisplay rather than 500.
2. Try a file that is not an image at all, renamed to `.png`. Expect a validation error naming the
   problem.
3. Confirm neither rejected file was written into `media/organisations/`.

**Expected:** rejections are clean form errors, and nothing reaches storage. A rejected upload that
still writes a file would mean validation now runs after the save.

# Part D. Cohort reports (`reports` alias and the prefix rename)

This is the alias holding learner names and quiz answers, and the only one whose key prefix changed.

## Test D1: generating a report writes under the new prefix

1. Admin → **Reports** → **Generated reports**.
2. Use the **Generate report** action, pick **QA Storage Cohort**, submit.
3. Expect a success message and a new row at status `pending`, then `running`, then `ready` as the
   `db_worker` picks it up. Refresh to follow it.
4. Once `ready`, check on disk: the PDF must be at `media/cohort_reports/<uuid>-cohort-report.pdf`.
   Nothing new should appear under `media/reports/`.

**Expected:** the file lands under `cohort_reports/`. This is the one intended behaviour change in
dev.

## Test D2: downloading a report

1. In the changelist, click the **Download** link on the ready report.
2. Expect a PDF download named `qa-storage-cohort-progress-report.pdf`, opening to a real report
   with learner names and quiz columns.
3. In DevTools → Network, check the response headers on that request. Expect
   `Cache-Control: private, no-store, must-revalidate` and a `Content-Disposition: attachment`.

**Expected:** the PDF streams through the permission-checked view. Note the URL is an
`/admin/.../download/` path, **not** a `/media/` URL. Reports are never served as a media URL, so
if you see one, that is a serious finding.

## Test D3: a report generated before the rename still downloads

The prefix change only affects new uploads. Rows written before it keep a `reports/...` value in the
database, and those files were never moved.

1. If you have a report row from before this change, download it and confirm it still works.
2. If you do not, stage one: take a ready report, and in the Django shell move its file back to the
   old layout.

```
uv run python manage.py shell
```
```python
import shutil
from pathlib import Path
from django.conf import settings
from freedom_ls.reports.models import GeneratedReport

report = GeneratedReport.objects.filter(status="ready").exclude(file="").first()
old_name = report.file.name.replace("cohort_reports/", "reports/")
src = Path(settings.MEDIA_ROOT) / report.file.name
dst = Path(settings.MEDIA_ROOT) / old_name
dst.parent.mkdir(parents=True, exist_ok=True)
shutil.copy(src, dst)
GeneratedReport.objects.filter(pk=report.pk).update(file=old_name)
print(report.pk, old_name)
```

3. Reload the changelist and download that report. Expect the PDF to download normally.

**Expected:** an old-prefix key still resolves. If it 404s, the rename was applied somewhere it
should not have been. The prefix belongs only in `report_upload_path`, which affects new writes,
and nothing should be rewriting stored `file.name` values.

## Test D4: a report whose file is missing gives 404, not 500

1. Pick a ready report. Delete its PDF from `media/` by hand, leaving the database row.
2. Click **Download**.

**Expected:** a clean **404**, not a 500 and not an unhandled `FileNotFoundError` traceback. The
view catches this explicitly; this checks the alias swap did not change which exception the storage
backend raises.

## Test D5: deleting a report removes only its own file

1. Note the filenames of two ready reports under `media/cohort_reports/`.
2. Delete one from the admin, confirming the deletion.

**Expected:** that report's PDF is gone from disk, the other report's PDF is still there, and the
`cohort_reports/` directory itself still exists. Both reports share one directory now, so a deletion
that took the directory with it would silently destroy every other report.

# Part E. Permission branches on the report download

Reports are the only one of the three files that holds personal data, so its access control is worth
re-checking after the storage change even though the view was not touched.

## Test E1: an unauthorised staff user cannot download

1. Log out. Log in as `qa-educator@email.com` (created by the setup command, granted `view_cohort` on
   **QA Storage Cohort** only). If it has no admin access, grant it staff in the admin first.
2. Reach the download URL for a report on **QA Storage Cohort**. Expect it to work.
3. Generate a report for a *different* cohort as the superuser, then, as `qa-educator`, request that
   report's download URL directly.

**Expected:** **403 Forbidden** on the second cohort's report. Staff status alone must not be
enough. Guessing a URL must not be enough either, because the check is per-cohort.

## Test E2: an anonymous user gets nothing

1. Log out entirely.
2. Paste a report download URL into a fresh private window.

**Expected:** redirected to the admin login, not the PDF.

## Test E3: the changelist does not leak a media URL

1. As the superuser, open the reports changelist.
2. View source (Ctrl+U) and search for `/media/`.

**Expected:** no `/media/` URL for a report file anywhere in the page. The reports admin
deliberately exposes no raw file field, unlike the file and organisation admins. This carve-out is
asserted by an existing test, and this is its browser-visible counterpart.

# Part F. Nothing wrote where it should not have

## Test F1: the test suite leaves the working tree alone

1. `find media -type f | sort > /tmp/media-before.txt` before you start.
2. `uv run pytest`
3. `find media -type f | sort | diff /tmp/media-before.txt -`

**Expected:** no difference. The whole suite is isolated by one autouse fixture that redirects
`MEDIA_ROOT` to a temp directory, and that only works while no storage alias declares its own
`location`. A new file under `media/` after a test run means an alias opted out of that isolation.

Use `find`, not `git status`. `media/` is gitignored, so `git status` reports clean whether or not
the suite wrote into it, which is exactly the failure this test exists to catch.

## Test F2: expected side effects of the deploy-check runs

Running `manage.py check --deploy --settings=config.settings_prod` loads the production logging
config, which writes rotating log files. So this is a "confirm what you expect" step, not a hunt for
a bug.

1. `ls logs/` afterwards. Expect `django.log`, `django_errors.log` and `security.log` alongside the
   `.gitkeep` that was already there. These are gitignored and harmless to leave. Delete them if you
   want the run to leave no trace.
2. Confirm no `staticfiles/` directory appeared. `check --deploy` does not run `collectstatic`, so
   one showing up means something else ran.
3. Confirm no throwaway `.env` file is sitting in the tree. All the check's variables are passed
   inline on the command line.

# Reporting

For anything that fails, record: which test, the URL, what you expected, what you got, and the
Network tab status code plus the runserver console output for that request. A missing image and a
403 look nothing alike but both come back to the same alias wiring, so the status code is the part
that identifies which.
