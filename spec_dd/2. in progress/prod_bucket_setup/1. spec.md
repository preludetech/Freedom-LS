# Spec: production object storage bucket layout

## 1. Purpose

FLS's production settings declare one media bucket and two `STORAGES` aliases. Three kinds of file
would write into that one bucket, with different access patterns and different sensitivity levels.
One of them is cohort report PDFs naming learners and their quiz answers.

This spec does two things. It fixes a live settings defect, and it puts the target bucket layout in
place before production is stood up for the first time.

The defect: `GeneratedReport.file` resolves storage through `get_reports_storage()`
(`freedom_ls/reports/models.py:36-41`), which reads `REPORTS_STORAGE_ALIAS` and silently falls back
to `storages["default"]` when that key is absent. `config/settings_prod.py:136-141` declares only
`default` and `staticfiles`. So `freedom_ls_reports.W001` fires today, and report PDFs would land in
the same bucket as public-facing course images. Step 6 of the `basic_reports` upgrade notes told
downstream projects to fix exactly this. FLS's own production settings never did.

Nothing has leaked, because nothing is deployed. There are no misplaced objects to move. It has to
be fixed before the first production deploy regardless of whether the rest of this spec is adopted.

## 2. Scope

### In scope

- A `build_storages()` helper in `freedom_ls/deployment/storage.py` that always emits every alias
  key, resolving each from per-bucket environment variables.
- Five media aliases declared from day one, including two with no consumer yet, resolving to three
  buckets, plus a `default` that resolves to a bucket name of its own so no media alias shares it.
- Key prefixes as the separator between the aliases that share a bucket, carried by the existing
  `upload_to` callables rather than by a storage `location`, so dev and production lay keys out the
  same way.
- Matching `STORAGES` defaults in `config/settings_base.py`, so every alias is declared under
  runserver and pytest too, not only in production.
- One environment variable per bucket property, keyed by bucket purpose, with the existing shared
  variables kept as a fallback so already-deployed downstream projects keep working.
- Per-bucket credential overrides, so an R2 API token can be scoped to a subset of buckets.
- A replacement system check that compares resolved bucket names instead of alias presence.
- `storage=` on the two model fields that lack it, through named module-level callables, so all
  three of the repo's file fields name an alias and none is left on `default`.
- A test that walks the model registry and fails if a `FileField` or `ImageField` resolves to
  `default`, so the rule still holds for fields added later.
- Removing the silent fallback inside `get_reports_storage()`.
- Renaming the report upload prefix from `reports/` to `cohort_reports/`.
- `Cache-Control` set at upload on the two anonymously readable aliases.
- Deleting a test fixture that reads as storage isolation and is not, and proving by test that the
  isolation the suite actually relies on covers all six storage aliases.
- Documentation, the template repo manifest, and a new `file-storage` skill.

### Out of scope

- Creating the R2 buckets. Section 13 lists the decisions an operator must make first, but the
  buckets themselves are provisioned outside this repo.
- Certificates and user document uploads as features. This spec declares their aliases, each
  pointing at a bucket that exists for another reason anyway. No model field, view or upload path
  for either.
- Per-request access-controlled media downloads, tracked in `docs/product/roadmap.md`.
- Data residency and file erasure mechanics, handed to
  `spec_dd/1. next/user-data-retention-idea.md`. That document should know R2 jurisdiction is fixed
  at bucket creation, so the only free moment to act on it is before these buckets exist.
- Object migration. Production is greenfield and R2 is the only target, so there is no S3 parity
  requirement.

## 3. Decisions and why

The layout argument lives in `idea.md`. These are the decisions this spec adds, or would otherwise
invite an implementer to reopen. Decisions explained where they are implemented are not repeated
here.

| # | Decision | Why |
|---|---|---|
| 1 | Buckets split by read policy, prefixes separate file types inside one | Three things R2 cannot scope narrower than a bucket bear on this layout: anonymous public read, jurisdiction and CORS. Lifecycle expiry, Bucket Locks, event notifications, backup fan-out and per-user erasure are all prefix-scopable, so none of them earns a bucket. |
| 2 | Three buckets, not five | A bucket boundary buys credential separation only where two principals hold different tokens. FLS has one. Web, the `django-tasks` worker and `content_save` all run the same settings module from one environment file, so splitting five ways splits variables inside a single `.env` rather than splitting trust. What is left is read policy, plus keeping personal data out of the widest-read bucket. |
| 3 | Six aliases over three buckets | An alias is one dict entry and carries its own key prefix, `Cache-Control` and querystring setting, so `certificates` can be immutable-cached while `public` is not, inside one bucket. It also means a project that does want a bucket per alias sets six different values for variables this spec already defines, with no code change and no migration. |
| 4 | Certificates share the public bucket | A certificate needs anonymous read, a custom domain and a CDN cache. Those are per-bucket properties, and they are exactly the branding bucket's. The separation a certificate actually needs is an unguessable object key, which is a key-naming rule rather than a bucket boundary. |
| 5 | All five media aliases declared now, including `user_uploads` and `certificates` | Declaring an alias with no consumer costs one dict entry. The certificates and document-upload features then add only a model field, instead of re-opening `build_storages()`, the docs and the manifest each time. |
| 6 | Environment variables keyed by bucket purpose, not by Django alias | Alias and bucket are different axes, which the layout relies on twice over: the `reports` alias resolves to the `fls-prod-user-data` bucket, and two pairs of aliases resolve to one bucket each. Naming the variable `AWS_S3_REPORTS_BUCKET_NAME` works only while each alias owns one bucket. |
| 7 | Every alias is always declared at the settings layer | The silent model-layer fallback is what turns a missing settings key into learner PII in a shared bucket. Replicating that shape across five aliases would replicate the failure five times. |
| 8 | Per-bucket credential overrides | Personal data sits in one bucket and gets a token reaching nothing else, which is the one credential boundary this deployment has a second holder for. The override is also the only way to give an alias a jurisdiction-specific endpoint, and R2 fixes jurisdiction at bucket creation. |
| 9 | No per-site or per-organisation buckets | Tenancy is a prefix concern. A bucket per tenant means credential sprawl. `organisation_logo_upload_to` and `report_upload_path` already prefix by pk. |
| 10 | Staging gets its own buckets, not a prefix inside production's | A token scopes to named buckets, so shared buckets would hand staging credentials that reach production objects. |
| 11 | Bucket names live only in environment values | No bucket name appears in the settings module, defaults included. The same code runs against production, staging and a downstream project's own buckets, and renaming a bucket is a deploy-config change instead of a release. |
| 12 | The uploads alias is `user_uploads`, not `learner_uploads` | Learners are the obvious uploader and not the only one. Educators and organisation admins upload through the same browser forms, and a name built on one role invites a second alias the day the first non-learner upload ships. |

## 4. The bucket layout

A bucket exists where R2 forces one. Everything else is a key prefix.

The three per-bucket properties that bear on FLS are anonymous public read, jurisdiction and CORS.
Lifecycle expiry, Bucket Locks, event notifications and per-user erasure all scope to a prefix, so
files differing only along those axes belong in one bucket. `research_r2_platform_constraints.md`
has each of these with its source.

### 4.1 Three buckets

| Bucket | Contents | Read policy | Holds personal data |
|---|---|---|---|
| `fls-prod-public` | Organisation logos, future public branding, future learner certificates | Anonymous read, custom domain, CDN cached | Once certificates ship |
| `fls-prod-course-media` | `content_engine.File`: images, PDFs, video | Private, signed URLs | No |
| `fls-prod-user-data` | Cohort reports, future user uploads and profile pictures | Private, signed URLs or streamed by Django | Yes |
| `fls-prod-default` | Nothing. The name is reserved and no bucket is created behind it | No token reaches it | No |

Those names are values, not constants. The `prod` in each is the environment, and staging runs the
same split under `fls-staging-`.

`fls-prod-course-media` is the one bucket that could change read policy later. It holds no personal
data and is rebuildable from the content repository, and its files carry the same caching problem
`research_public_vs_signed_logos.md` documents for logos: a fresh signature per render means browser
and CDN miss on every request, on images that appear on every course card. Whether to make it public
is a separate decision on a separate spec. Keeping it out of `fls-prod-user-data` is what leaves the
decision available, because anonymous read cannot be granted to part of a bucket.

`fls-prod-user-data` is the split jurisdiction argues for. It is the only bucket whose contents are
about an identified person, so it is the only one that would ever need EU residency, and R2 fixes
jurisdiction at creation and cannot scope it to a prefix. That makes this the one boundary a prefix
could not be retrofitted into later. It is also the one bucket worth a token of its own, for the
same reason: a leaked credential should not reach learner quiz answers.

`fls-prod-default` is not a place to put files. It is a name nothing else can collide with. All
three file fields in the repo name an alias, so `default` has no legitimate contents, and pointing
it somewhere of its own is what lets `E001` read any media alias resolving to `default` as a missing
variable. Nothing is created behind the name and no token reaches it, so a field that arrives later
without a `storage=` fails on its first write rather than quietly filling a bucket that holds real
content. A downstream project is unaffected. It sets `AWS_STORAGE_BUCKET_NAME` and no
`AWS_S3_DEFAULT_BUCKET_NAME`, so its `default` keeps resolving where it resolves today.

### 4.2 Six aliases

Bucket count follows what R2 enforces. Alias count follows what the settings layer has to say
differently about each kind of file, which is more.

| Alias | Bucket | Key prefix | Consumer |
|---|---|---|---|
| `public` | `fls-prod-public` | `organisations/` | `Organisation.logo` |
| `certificates` | `fls-prod-public` | `certificates/` | None yet |
| `course_media` | `fls-prod-course-media` | none, the bucket is its own namespace | `content_engine.File.file` |
| `reports` | `fls-prod-user-data` | `cohort_reports/` | `GeneratedReport.file` |
| `user_uploads` | `fls-prod-user-data` | `user_uploads/` | None yet |
| `default` | `fls-prod-default` | none | Nothing, deliberately |

An alias costs one dict entry and earns it three ways. It carries its own `Cache-Control`, so
`certificates` can be cached immutably against a uuid key while `public` cannot, in the same bucket.
It carries its own credentials and endpoint, which is what lets `fls-prod-user-data` have a token
reaching nothing else. And because every alias resolves through its own environment variable, a
downstream project that wants six buckets sets six different values and changes no code.

The prefixes live in the `upload_to` callables, not in a storage `location`. Two aliases sharing a
bucket must produce disjoint keys, and `upload_to` is the mechanism that already does this
(`organisation_logo_upload_to` returns `organisations/{pk}{ext}`, `report_upload_path` returns
`cohort_reports/...` after section 8.3). A `location` on the alias would work in production and be
absent in dev and the test suite, because section 5.5 forbids `location` on the `FileSystemStorage`
entries for the `MEDIA_ROOT` isolation reason in section 9. Keeping the prefix in `upload_to` means
one key layout everywhere, exercised by every test that saves a file. Section 10 pins the disjoint
prefixes with a test.

`reports` is the alias whose read policy the settings layer has to act on.
`download_report_view` (`freedom_ls/reports/views.py:109-125`) streams the file behind a per-cohort
permission check and never hands out a storage URL, so the alias needs no custom domain and no
signed-URL configuration at all, even though it shares a bucket with `user_uploads`, which will need
both.

Two constraints from the layout reach past this spec, into the features that will use these aliases.
Certificate object keys must be uuid-derived, because in a public bucket the key is the whole access
control, and the bucket they land in also serves branding assets under a guessable prefix. User
uploads must be prefixed per uploading user beneath `user_uploads/`, so a right-to-erasure request
becomes a scoped delete. They belong to `spec_dd/1. next/certificates/idea.md` and
`spec_dd/1. next/user-data-retention-idea.md` respectively.

## 5. Settings layer

### 5.1 The environment variable contract

Variables are keyed by bucket purpose. `PURPOSE` is one of `PUBLIC`, `COURSE_MEDIA`,
`USER_UPLOADS`, `GENERATED`, `CERTIFICATES`, `DEFAULT`.

| Property | Shared fallback, unchanged | Per-bucket override |
|---|---|---|
| Bucket name | `AWS_STORAGE_BUCKET_NAME` | `AWS_S3_<PURPOSE>_BUCKET_NAME` |
| Access key | `AWS_S3_ACCESS_KEY_ID` | `AWS_S3_<PURPOSE>_ACCESS_KEY_ID` |
| Secret key | `AWS_S3_SECRET_ACCESS_KEY` | `AWS_S3_<PURPOSE>_SECRET_ACCESS_KEY` |
| Endpoint URL | `AWS_S3_ENDPOINT_URL` | `AWS_S3_<PURPOSE>_ENDPOINT_URL` |
| Region | `AWS_S3_REGION_NAME` | `AWS_S3_<PURPOSE>_REGION_NAME` |
| Custom domain | `AWS_S3_CUSTOM_DOMAIN` | `AWS_S3_<PURPOSE>_CUSTOM_DOMAIN` |
| Querystring auth | `AWS_QUERYSTRING_AUTH` | `AWS_S3_<PURPOSE>_QUERYSTRING_AUTH` |
| Querystring expire | `AWS_QUERYSTRING_EXPIRE` | `AWS_S3_<PURPOSE>_QUERYSTRING_EXPIRE` |

Every variable is optional. An unset per-bucket variable falls through to the shared column.

`AWS_STORAGE_BUCKET_NAME` breaks the `AWS_S3_*` pattern the other shared variables follow. That name
is inherited from django-storages and boto3. Renaming it would break every already-deployed
downstream project, so it stays as it is. Only the shared fallback carries the odd name. The
per-bucket column is internally consistent. `default` reads `AWS_S3_DEFAULT_BUCKET_NAME` first and
falls back to `AWS_STORAGE_BUCKET_NAME` like every other alias, so it is configured the same way as
the rest instead of being the one alias with no override.

The alias name and the purpose prefix are allowed to differ, and for `reports` they do.
`REPORTS_STORAGE_ALIAS` keeps its default of `"reports"`, an app-owned name, while the bucket it
resolves to is named by `AWS_S3_GENERATED_*`. `build_storages()` is what maps one onto the other.

Two variables resolving to the same bucket name is a supported configuration, not a collision. FLS
production sets `AWS_S3_PUBLIC_BUCKET_NAME` and `AWS_S3_CERTIFICATES_BUCKET_NAME` to one value, and
`AWS_S3_GENERATED_BUCKET_NAME` and `AWS_S3_USER_UPLOADS_BUCKET_NAME` to another. Nothing in the
settings layer or in `E001` treats two media aliases agreeing as an error, because the section 4.2
prefixes keep their keys apart and the per-alias `OPTIONS` still differ. The only agreement that is
an error is a media alias agreeing with `default`, which is section 7.4.

Keeping the shared column has one consequence for a downstream project. It sets no per-bucket name,
so all five media aliases resolve to the shared bucket and `E001` reports five errors on the first
`check --deploy`, one per alias, naming the variable each one wants. Those errors arrive before
anything writes. Five errors do not mean five buckets: the fix is the three bucket names of section
4.1 spread across the five variables plus `AWS_S3_DEFAULT_BUCKET_NAME`, and the upgrade notes must
say which variables share a value rather than leaving a project to create five buckets it does not
need. A project already serving media publicly also has `AWS_S3_CUSTOM_DOMAIN` and
`AWS_QUERYSTRING_AUTH=false` reaching all five aliases after the upgrade, which is the same exposure
it already has, since every one of those files sits in that one public bucket today.

Endpoint override is not only a credentials convenience. R2 fixes bucket jurisdiction at creation
and enforces it through a jurisdiction-specific endpoint hostname, so a bucket created in the EU
jurisdiction has a different endpoint from every other bucket in the account. The override has to
exist for that even though on day one it repeats the shared value.

### 5.2 `build_storages()`

Lives in `freedom_ls/deployment/storage.py`, beside `build_s3_media_storage()`, which is already
alias-agnostic and becomes its single-alias building block. That helper keeps its signature and its
behaviour. It gains one defaulted argument, the `object_parameters` of section 5.4, and a docstring
correction, since it currently says it assembles the `STORAGES['default']` entry and now assembles
any of them.

House style for this module, from `freedom_ls/deployment/settings_defaults.py`: the caller in
`config/settings_prod.py` reads `os.getenv`, and the helper takes resolved values. `build_storages()`
is the exception, because reading forty environment variables at the call site would bury the
settings module. Resolve them inside `build_storages()`, keep it importable at settings-load time
with no app-registry dependency, and reuse `env_bool`/`env_int` from `freedom_ls/base/env.py` rather
than inventing new parsing. Those two already raise `ImproperlyConfigured` on a malformed value
instead of falling back silently, which is the behaviour wanted here.

Resolution order per alias, applied to each property independently:

1. The per-bucket variable, `AWS_S3_<PURPOSE>_<PROPERTY>`.
2. The shared variable.
3. For the bucket name only, if neither is set, the alias falls back to `FileSystemStorage`.

Shared-bucket-before-filesystem is the only non-breaking order for a downstream project upgrading in
place, because it reproduces today's single-bucket behaviour exactly. Rerouting a configured
production deployment to local disk would be an outage rather than a privacy improvement, since a
multi-process deployment writing to local disk loses files depending on which process serves the
next request. The system check in section 7 is what makes the shared-bucket case safe.

`build_storages()` always emits all seven keys: `default`, `staticfiles`, `public`, `course_media`,
`user_uploads`, `reports`, `certificates`. `staticfiles` stays WhiteNoise and is passed in by the
caller. The `reports` key is emitted under the name `REPORTS_STORAGE_ALIAS` resolves to, so a
downstream project that renamed the alias still gets a declared key. `default` goes through the same
three-step resolution as the rest, from `AWS_S3_DEFAULT_*` then the shared variables, so the helper
special-cases it nowhere.

Production is not the only settings module that has to declare all seven. Section 5.5 covers the
rest.

### 5.3 Resulting production configuration

Every alias names its bucket explicitly. FLS production sets `AWS_S3_PUBLIC_BUCKET_NAME`,
`AWS_S3_CERTIFICATES_BUCKET_NAME`, `AWS_S3_COURSE_MEDIA_BUCKET_NAME`,
`AWS_S3_GENERATED_BUCKET_NAME`, `AWS_S3_USER_UPLOADS_BUCKET_NAME` and
`AWS_S3_DEFAULT_BUCKET_NAME`, and leaves the shared `AWS_STORAGE_BUCKET_NAME` unset. Six variables,
four values.

Leaving the shared variable unset is the point of this section. No alias in FLS production reaches
its bucket through a fallback, so the two pairs that agree agree because the operator wrote the same
value twice, not because both fell through to the same place. It also improves the failure mode for
a typo. With nothing to fall back to, a misspelled per-bucket variable drops that alias to
`FileSystemStorage`, which `E001` catches under `DEBUG=False` (section 7.4). Falling back to a
shared bucket would instead have produced a working deployment writing to the wrong place.

`AWS_S3_CUSTOM_DOMAIN` and `AWS_QUERYSTRING_AUTH` are set per alias for the same reason. `public`
and `certificates` both get the custom domain and both get `QUERYSTRING_AUTH=false`, because they
share a bucket whose whole purpose is anonymous read and a signature on an anonymously readable
object is noise that defeats the CDN cache. The shared forms of both stay unset, so `course_media`,
`user_uploads` and `reports` keep signed URLs.

Two R2 API tokens for the first deploy:

- Token 1, scoped to `{fls-prod-public, fls-prod-course-media}`. Set as the shared
  `AWS_S3_ACCESS_KEY_ID` and `AWS_S3_SECRET_ACCESS_KEY`, covering `public`, `certificates` and
  `course_media`. Neither bucket holds personal data today.
- Token 2, scoped to `{fls-prod-user-data}` only. Set as `AWS_S3_GENERATED_ACCESS_KEY_ID` and
  `AWS_S3_GENERATED_SECRET_ACCESS_KEY`, and the same value again under
  `AWS_S3_USER_UPLOADS_ACCESS_KEY_ID` and `AWS_S3_USER_UPLOADS_SECRET_ACCESS_KEY`.

Both tokens sit in the same environment file and the same process reads both, so neither is a trust
boundary between two principals. What the split limits is reach. A credential that escapes through a
log line, a traceback or a third-party integration gets one bucket rather than all three, and the
bucket holding learner quiz answers is the one behind the narrower token.

Token 1 reaches `certificates` even though nothing writes certificates yet, and that is not
avoidable. Certificates live in the branding bucket, a token scopes to a bucket and nothing finer,
so a token that can write a logo can write a certificate. Nothing exercises the grant until the
feature ships.

`default` is reachable by neither token. It should never be written to at all, so a write that
reaches it fails on the credentials as well as on the missing bucket. Its name variable is still set
from day one, because `default` needs a name of its own for the `E001` comparison to mean anything.
Section 7.4 has the reasoning and section 13 has the operator steps.

### 5.4 `Cache-Control` on the anonymously readable aliases

R2 has no bucket-level `Cache-Control` default. The header is per-object metadata set at upload, so
`fls-prod-public` without it gets none of the caching that justified creating it. Per-object also
means the two aliases sharing that bucket can set it differently, which they do.

`S3Storage` reads a per-instance `object_parameters` dict and merges it into every write. Because
`OPTIONS` is per-alias, this needs no branching, and per-alias is the granularity the layout needs:
`public` and `certificates` share a bucket and want different cache lifetimes, which is only
expressible per object. Add one optional keyword argument to `build_s3_media_storage()`:

```python
object_parameters: dict[str, str] | None = None
```

threaded into `options` only when given. It needs a default so the existing downstream callers in
the template repo keep working. Keys are boto3 `put_object` parameter names, so `CacheControl`, not
`Cache-Control`.

The public alias gets `{"CacheControl": "public, max-age=86400"}`. The certificates alias gets
`{"CacheControl": "public, max-age=31536000, immutable"}`. A certificate is written once under a
uuid-derived key and never overwritten, which is the exact precondition `immutable` needs and the
one the logo does not meet. Setting it now costs one dict entry in `build_storages()` and means the
certificates feature does not have to reopen this module. The three remaining media aliases carry no
`object_parameters` key at all.

`immutable` is deliberately absent from the public alias. `organisation_logo_upload_to`
(`freedom_ls/organisations/models.py:17-25`) returns `organisations/{instance.pk}{ext}`, a stable
key, so a re-uploaded logo overwrites the same object at the same URL, and `immutable` would mean an
admin sees it change nowhere. That mutability is also why the logo keeps a guessable
`organisations/{pk}` key while a certificate cannot: the logo is not access-controlled by its key.
Versioning the key with a
content hash would allow `immutable` and a year of `max-age`, at the cost of an `AlterField`, two
test updates (`freedom_ls/organisations/tests/test_models.py:44,51`) and an orphan-deletion hook.
Worth revisiting if stale logos are ever reported in practice.

**Correction, post-QA.** As specified, nothing made that overwrite real — it rested on
`S3Storage` happening to default `file_overwrite=True`, and on local disk it was simply false:
`FileSystemStorage.get_available_name` suffixes on collision, so a replaced logo landed beside the
old one and left it orphaned. The alias now declares the property instead of assuming it.
`_OVERWRITE_ALIASES` in `freedom_ls/deployment/storage.py` names the aliases that replace at a
stable key — `public` only — `build_s3_media_storage` always writes `file_overwrite` rather than
inheriting a third-party default, and the non-production `public` entry uses
`OverwritingFileSystemStorage` so development and production agree about where a replaced logo
lives.

### 5.5 Non-production settings

`config/settings_base.py` declares no `STORAGES` at all today, so dev and the test suite run on
Django's two-key global default. That is survivable now only because of the fallback section 8.2
deletes.

Django resolves a callable `storage=` once, inside `FileField.__init__`, at model import. So the
moment `get_reports_storage()` stops swallowing `InvalidStorageError`, a settings module missing the
`reports` key does not degrade, it fails to import the model. Under `settings_dev` that means
`runserver`, `migrate` and every pytest run stop working, not just production. The same applies to
`course_media` and `public` once section 8.1 lands.

So `settings_base.py` declares all seven keys as `FileSystemStorage`, with `staticfiles` left as
Django's own `StaticFilesStorage`:

```python
STORAGES = {
    "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "staticfiles": {"BACKEND": "django.contrib.staticfiles.storage.StaticFilesStorage"},
    "public": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "course_media": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "user_uploads": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "reports": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "certificates": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
}
```

A literal dict, not a `build_storages()` call with nothing set. The two produce the same result, but
a developer who happens to have `AWS_*` exported for another project would get real S3 buckets in
dev and, worse, in the test suite. `settings_prod.py` still overrides the whole dict through
`build_storages()`, as it already overrides `default` and `staticfiles`.

No entry carries an `OPTIONS` key. That is load-bearing, not tidiness. `FileSystemStorage` resolves
its location as `self._location or settings.MEDIA_ROOT`, so an alias with no explicit `location`
tracks `MEDIA_ROOT`, and one with a `location` ignores it forever. Section 9 depends on it.

## 6. Per-app storage alias settings

Each consuming app declares which alias it uses, following the `AppSettings`/`Setting` pattern in
`freedom_ls/base/app_settings.py` and the existing `REPORTS_STORAGE_ALIAS` declaration at
`freedom_ls/reports/config.py:79`.

| App | Setting | Default |
|---|---|---|
| `reports` | `REPORTS_STORAGE_ALIAS` | `"reports"`, unchanged |
| `content_engine` | `CONTENT_MEDIA_STORAGE_ALIAS` | `"course_media"` |
| `organisations` | `ORGANISATION_LOGO_STORAGE_ALIAS` | `"public"` |

`content_engine` already has `config.py` and `checks.py`, so the setting extends the existing
`declared_settings` dict (`freedom_ls/content_engine/config.py:11-19`). Include the bare class-level
type annotation above the dict, as every `config.py` in the repo does.

`organisations` has neither file. Create `freedom_ls/organisations/config.py` following
`reports/config.py`, and `freedom_ls/organisations/checks.py` carrying the standard
`required_settings_errors(config, "freedom_ls_organisations")` E001 wrapper. Add the one-line
`from freedom_ls.organisations import checks  # noqa: F401` to `OrganisationsConfig.ready()`
(`freedom_ls/organisations/apps.py`), alongside the `post_migrate` connection already there.

## 7. System check

### 7.1 Retiring `freedom_ls_reports.W001`

`W001` detects a wholly undeclared alias (`freedom_ls/reports/checks.py:37-55`). Under the
always-declared design that state cannot occur through `build_storages()`, and a downstream project
that does not declare the key now fails loudly at model import instead (section 8.2). The check is
dead either way.

Delete `check_reports_storage_alias_configured` and its tests
(`freedom_ls/reports/tests/test_checks.py::TestReportsStorageAliasCheck`). Follow the retired-id
convention already set by `W003` in the same module: keep the id documented in the module docstring
as retired rather than renumbering, because a downstream project may still be silencing it.

```
W001 — Retired. Do not reuse the id: a project may still be silencing it.
       Replaced by freedom_ls_deployment.E001, which compares resolved bucket
       names rather than alias presence.
```

### 7.2 The replacement

Lives in `freedom_ls/deployment/checks.py`, id `freedom_ls_deployment.E001`. `deployment` owns the
`STORAGES` assembly and is the only app with cross-cutting settings-level checks, so it is the right
home. Putting the comparison in each consuming app's `checks.py` would duplicate the same logic
three times.

```python
@register(Tags.security, deploy=True)
def check_media_aliases_resolve_to_their_own_bucket(**kwargs: object) -> list[CheckMessage]:
```

`freedom_ls/deployment/checks.py` opens with a docstring that says "W = Warning" and lists W001.
Both lines are about to be wrong. Widen the legend and add the `E001` entry in the same edit, in the
shape `freedom_ls/reports/checks.py` already uses for a module holding both severities.

`deploy=True` is the mechanism that keeps it quiet, not a `DEBUG` branch inside the function.
Django's registry only includes deployment checks when `manage.py check --deploy` runs, so it never
fires on runserver, migrate, plain `check`, or the test suite. This is the first `deploy=True` check
in the repo. Because it is opt-in, an `Error` is safe, and an `Error` is what fails a deploy
pipeline's exit code. Blocking a deploy before learner PII reaches a shared bucket is the whole
reason the check exists. A `Warning` would not fail that exit code, and would be silenced and
forgotten. That weakness is why the section 1 defect survived into production settings.
`docs/deployment-security-checklist.md` must state that a pipeline has to actually run
`manage.py check --deploy` for this to bite.

### 7.3 Comparing resolved storage

Both `S3Storage.bucket_name`/`endpoint_url` and `FileSystemStorage.location` are plain attributes
resolved without any network call, so the check can read them safely. Dispatch on backend type
rather than assuming `S3Storage`, because a downstream project can point an alias at any `Storage`
subclass:

```python
def _storage_identity(storage: Storage) -> tuple[str, ...] | None:
    """Where a Storage writes, or None when the backend cannot be compared safely."""
    if isinstance(storage, S3Storage):
        return ("s3", storage.bucket_name, storage.endpoint_url)
    if isinstance(storage, FileSystemStorage):
        return ("fs", str(storage.location))
    return None
```

An unrecognised backend returns `None` and the check stays silent. A false positive on a custom
backend is exactly the kind of noise that gets a check silenced wholesale, which would lose the
signal permanently.

### 7.4 Which aliases the check covers, and the decision table

All five media aliases: `public`, `course_media`, `user_uploads`, `reports` and `certificates`. The
rule is two sentences. No media alias may resolve where `default` resolves. And in production, no
media alias may resolve to local disk at all.

The check compares each media alias against `default` and never against another media alias. That
is what lets two aliases share a bucket on purpose. `public` and `certificates` resolving to the
same bucket is the intended configuration, and a check that flagged any two aliases agreeing would
fire on it every deploy until somebody silenced the whole check.

Comparing against `default` is a usable rule only because `default` has a bucket name nothing else
uses. An alias matching it means either the per-bucket variable is missing and the alias fell
through to the shared one, or `AWS_S3_DEFAULT_BUCKET_NAME` was set to a real bucket. Both are
configuration errors, in every alias, so there is nothing to exempt. An exemption table would also
have to be kept true every time an alias is added.

`E001` is not the whole story for two of the five. `public`'s worse failure is not matching
`default`, it is failing to be publicly readable, which is a different check and out of scope here.
`certificates` is the mirror image. Falling back to a private `default` would silently break
certificate verification, so not matching `default` is no evidence of correctness. When the
certificates feature is built it needs its own check asserting the resolved alias is an `S3Storage`
with `querystring_auth is False`.

Covering `user_uploads` and `certificates` before either feature exists costs the operator two
environment variables and no buckets. With no per-bucket name set, each resolves to the shared
bucket or to local disk, and either way the first deploy fails. So both name variables are set from
the start, pointing at buckets that section 4.1 creates anyway for the aliases that do have
consumers. Deferring the check until the features ship would leave each guard arriving after the
thing it guards. Section 13 carries this as an operator step.

| Alias resolves to | Compared with `default` | Fires | Severity |
|---|---|---|---|
| Same `("s3", bucket, endpoint)` | identical | yes | Error |
| Same `("fs", location)`, `DEBUG=False` | identical | yes | Error |
| Same `("fs", location)`, `DEBUG=True` | identical | no | |
| `("fs", location)`, `DEBUG=False` | differs | yes | Error |
| `("fs", location)`, `DEBUG=True` | differs | no | |
| Different bucket or endpoint, both `s3` | differs | no | |
| `None` identity on either side | not comparable | no | |

The filesystem rows matter, and there are two of them because comparing against `default` is not
sufficient on its own. A typo in `AWS_S3_GENERATED_BUCKET_NAME` with the shared variable also unset
lands a production worker on local disk. Whether that shows up as *identical to `default`* depends
entirely on whether `AWS_S3_DEFAULT_BUCKET_NAME` is set — and section 13 requires that it always is,
which means the typo case always lands in the *differs* row. So an alias on local disk under
`DEBUG=False` is an error in its own right, regardless of where `default` points. Without that row
the guarantee section 5.3 makes for leaving the shared variable unset would not hold.

Gating both filesystem rows on `DEBUG=False` keeps the check aimed at real production
misconfiguration, since local disk is the normal dev and test configuration and a staging smoke
environment might use `FileSystemStorage` deliberately.

The two arms never double-report: an alias identical to `default` is reported once as a collision,
and only an alias that is *not* identical is considered for the local-disk arm.

The message has to name the alias and the per-bucket variable that fixes it. On a downstream
project's first `check --deploy` the operator sees five of these at once, and that list is the
work.

## 8. Model fields, callables and migrations

### 8.1 Named module-level callables

Every `FileField` and `ImageField` in the repo declares `storage=`. There are three, all in the
table below, so once this spec lands no field in FLS resolves to `default`. Section 10 adds a test
that walks the model registry and fails on a field that breaks the rule, because the rule is easy to
state and easy to forget the next time somebody adds a field.

Every per-field storage assignment goes through a named module-level callable. Never a bare
`Storage(...)` instance, and never a lambda.

The instance rule is not stylistic. django-storages backends are `@deconstructible`, so
`MigrationWriter` re-emits the constructor call as literal Python in the generated migration file,
including any resolved secret value rather than the environment variable reference. A field that
passes a bucket name and an access key straight into `S3Storage(...)` puts that secret in git
history in plaintext, permanently. The callable indirection is the only thing between credentials in
`.env` and credentials in `git log`.

A lambda cannot be serialised at all.

Django calls the callable at `FileField.__init__`, and records only its dotted path in the
migration, so later bucket changes need no migration. The result behaves as cached because
`storages[alias]` caches the constructed instance per alias for the process lifetime. That property
holds only while the callable delegates through `storages[alias]`, so it must not construct an
`S3Storage` itself.

Pick the final callable names and their module now. A migration freezes the whole dotted path at the
time it was generated, so moving or renaming one later breaks `migrate` for anyone replaying history
from scratch. Treat it as costing what a public API rename costs. Each callable goes in its own app's
`models.py`, beside the field it serves, which is where `get_reports_storage()` already sits and what
the migrations below will record.

| App | Callable | Field |
|---|---|---|
| `content_engine` | `get_content_media_storage()` | `File.file`, `freedom_ls/content_engine/models.py:590` |
| `organisations` | `get_organisation_logo_storage()` | `Organisation.logo`, `freedom_ls/organisations/models.py:31-35` |
| `reports` | `get_reports_storage()`, existing | `GeneratedReport.file`, `freedom_ls/reports/models.py:73-75` |

### 8.2 Removing the silent fallback

`get_reports_storage()` loses its `try`/`except InvalidStorageError` and becomes a one-liner, and the
two new callables never grow one:

```python
def get_reports_storage() -> Storage:
    """The alias named by REPORTS_STORAGE_ALIAS. The settings layer guarantees it exists."""
    return storages[config.REPORTS_STORAGE_ALIAS]
```

This is a breaking change for downstream projects and the upgrade notes must say so plainly. A
project whose own settings module declares no `reports` key currently boots and quietly writes
reports to default storage. After this change it raises `InvalidStorageError` at model import and
does not boot. That is the intended trade: a startup failure naming the missing key beats learner
PII in a public bucket. The migration path is to call `build_storages()`, which downstream projects
can import from `freedom_ls.deployment.storage` exactly as FLS's own settings module does.

### 8.3 The report prefix rename

`report_upload_path` (`freedom_ls/reports/models.py:24-33`) returns
`f"reports/{instance.pk}-cohort-report.pdf"`. Change the prefix to `cohort_reports/`. Update the
docstring in the same edit, since it names the `reports/` prefix too.

The prefix does two jobs under this layout. It is what keeps report keys clear of `user_uploads/`
in the shared `fls-prod-user-data` bucket, per section 4.2. And R2 applies lifecycle expiry per
prefix, so it is what attaches an expiry rule to reports without touching uploads, which must never
be auto-deleted. Naming the artifact rather than the app is what keeps both true once the bucket
gains a third kind of file. Nothing is deployed, so there is nothing to move.

Two tests assert the old literal and must change with it:

- `freedom_ls/reports/tests/test_models.py:62-67`, `test_upload_path_is_pk_derived`.
- `freedom_ls/reports/tests/test_deletion_hygiene.py:65`, the `storage.exists("reports")` assertion
  inside `test_other_reports_survive_deletion`.

Nothing else in the repo asserts on the prefix. The other `reports/` strings under
`freedom_ls/reports/tests/` are Django template paths and static asset paths, unrelated to storage.

## 9. Test isolation

`freedom_ls/conftest.py:31-41` has an autouse `_isolate_media_root` fixture redirecting `MEDIA_ROOT`
to a per-test tmp dir. `freedom_ls/reports/tests/conftest.py:15-31` has a second autouse fixture,
`isolated_reports_storage`, that reassigns `settings.STORAGES` to point the `reports` alias at
`tmp_path`.

That second fixture does nothing. `FileField.__init__` calls a callable `storage=` once, at model
import, and keeps the returned instance on the field, so reassigning `settings.STORAGES` afterwards
clears the `storages` cache but never reaches a field already holding a concrete `Storage`. Verified
against Django 6.0.4: after the fixture runs,
`GeneratedReport._meta.get_field("file").storage` is the same object it was before, still rooted at
`MEDIA_ROOT`. Report files are isolated today by `_isolate_media_root` alone.

So:

- Delete `isolated_reports_storage` from `freedom_ls/reports/tests/conftest.py`. Keep
  `requires_tailwind_bundle`, which is unrelated and still needed.
- Do not generalise the fixture to the other five aliases. A per-alias `tmp_path` fixture cannot work
  through settings at all.
- Add the section 5.5 declarations before the model fields are rewired. Between the two,
  `storage=get_content_media_storage` on a field whose alias is undeclared raises at import and the
  suite does not collect.

What does work is already in place. `FileSystemStorage` resolves its location as
`self._location or settings.MEDIA_ROOT` and drops the cached value on the `MEDIA_ROOT`
`setting_changed` signal, so every alias section 5.5 declares without an `OPTIONS` key follows
`MEDIA_ROOT` for the life of the process. One autouse fixture, six aliases, no new code. That is why
5.5 forbids an explicit `location`, why section 4.2 puts the production key prefixes in `upload_to`
instead, and why section 10 proves the outcome by test rather than leaving it to be noticed when
`media/` fills up.

## 10. Testing

`build_storages()` is a plain function returning a dict, and neither it nor `S3Storage.__init__`
touches the network, so it needs no credentials and no Django settings machinery. Drive it with
`monkeypatch.setenv`/`delenv` and assert on the returned dict, matching the existing pure unit tests
in `freedom_ls/deployment/tests/test_storage.py`.

Cases to cover:

1. Every alias key is present, in all configurations, including when nothing is set.
2. A per-bucket variable wins over the shared variable.
3. An unset per-bucket variable falls back to the shared bucket, and the resulting alias entry equals
   `default`. This is the collision `E001` targets, so the test pins the precondition.
4. Neither set gives `FileSystemStorage`.
5. Per-bucket credentials and endpoint override independently of the bucket name.
6. `public` carries `CacheControl` at `public, max-age=86400` with no `immutable`, `certificates`
   carries `public, max-age=31536000, immutable`, and the other three media aliases carry no

7. `build_s3_media_storage()` without `object_parameters` emits no such key, so existing behaviour is
   unchanged.
8. `default` resolves from `AWS_S3_DEFAULT_BUCKET_NAME` when it is set and from

   alias entry equals `default`.
9. Two purpose variables set to the same bucket name produce two distinct alias entries that agree
   on `bucket_name` and differ on the properties section 5.3 sets per alias. Drive it with the

Four more, aimed at sections 4.2, 5.5 and 8.1 rather than at `build_storages()`:

11. Saving real content through `File.file`, `Organisation.logo` and `GeneratedReport.file` writes

## 13. Operator decisions before the first deploy

These are outside the repo but have to be settled before the buckets exist, because two of them
cannot be changed afterwards.

- Final bucket names, for production and staging.
- Jurisdiction per bucket. Immutable at creation, and not scopable to a prefix. This is the only
  free moment to act on data residency, which is why `spec_dd/1. next/user-data-retention-idea.md`
  needs to know about it. Two of the three buckets need a decision rather than a default:
  `fls-prod-user-data` holds learner quiz answers from day one, and `fls-prod-public` holds a
  learner's name at an anonymously readable URL the day certificates ship. If EU residency is
  plausible for either, both are created in the EU jurisdiction now. Putting branding in an EU
  bucket costs nothing; discovering later that certificates needed it costs a bucket migration.
- The custom domain for `fls-prod-public`, serving both the `public` and `certificates` prefixes.
- Token count and scope. Section 5.3 gives the recommended two.
- Lifecycle expiry on the `cohort_reports/` prefix in `fls-prod-user-data`, and no expiry rule
  without a prefix, which would apply bucket-wide and reach `user_uploads/`.
- Bucket Locks on production only, and on the `user_uploads/` prefix rather than bucket-wide, for
  the same reason. Staging must not copy them, or it can never be torn down and rebuilt.

Three buckets are created now, and all six bucket name variables are set, `default` included. Two
pairs of variables carry the same value; section 5.3 says which. No bucket is created for
`user_uploads` or `certificates` in their own right, because each points at a bucket another alias
already needs.

`fls-prod-default` goes the other way. Its name is set and no bucket is created behind it. Nothing
should ever write there, so the write failing is the correct outcome, and `E001` compares names
rather than checking that buckets exist.

Two R2 limits are worth recording here, because they will otherwise be discovered during
implementation of a later feature: presigned URLs cap at 7 days and cannot be combined with custom
domains, and POST-based presigned uploads are not supported at all, so an S3
`createPresignedPost`-style browser upload will not work for user uploads.

## 14. The `file-storage` skill

The buckets are only worth having if new file fields land in the right one, and that decision gets
made the moment someone adds a `FileField` or `ImageField`, which is exactly when nobody re-reads a
spec.

Add `claude_plugins/fls-dev/skills/file-storage/SKILL.md`, following the freestanding shape of
`multi-tenant/SKILL.md` rather than the overlay shape of `app-settings/SKILL.md`, since no `ds:`
level storage skill exists to extend. Frontmatter carries `name`, `description` and
`allowed-tools: Read, Grep, Glob`.

The `description` must auto-trigger on adding or changing a file field, following the house phrasing
of one clause saying what the skill does then "Use when" plus concrete triggers. Something like:
"FreedomLS object storage layout: which STORAGES alias and which bucket a file belongs in. Use when
creating or modifying a FileField or ImageField, adding a file-owning model, or choosing a storage
alias."

Content, kept short enough to stay skimmable:

- The six aliases, what belongs in each, and which of the three buckets each resolves to. The two
  tables from section 4.
- That `default` is not one of the options. Every file field names an alias, and a field left on
  `default` fails its first write in production rather than storing anything.
- The decision rule, in the order the layout uses it. First, does the file need to be readable
  without logging in, which is the only question that picks a bucket. Then who supplies the bytes,
  whether it names a person, and whether it can be regenerated, which pick an alias inside that
  bucket.
- That a field on an alias sharing a bucket must namespace its `upload_to`, and which prefix its
  alias owns. This is the rule the layout leans on hardest and the easiest one to break, because a
  bare `upload_to="uploads/"` looks fine in dev where every alias has its own `MEDIA_ROOT` subtree.
- The mechanical rules: named module-level callable, never an instance, never a lambda, and why.
- That the alias must already be declared in both places, `build_storages()` for production and the
  base settings dict for everything else, and that adding a field before the alias exists breaks
  model import rather than degrading.

## 15. Success criteria

1. `config/settings_prod.py` declares all seven `STORAGES` keys through `build_storages()`, and no
   bucket name appears anywhere in the settings module or in any default.
2. `manage.py check --deploy` against a configuration where `reports` resolves to the same bucket as
   `default` exits non-zero with `freedom_ls_deployment.E001`.
3. The same command against the intended production configuration exits zero, with the five media
   aliases resolving to the three buckets of section 4.1 and none of them resolving where `default`
   does.
4. `manage.py check`, `runserver`, `migrate` and the test suite never emit `E001`.
5. `config/settings_base.py` declares the same seven keys, the six media aliases as
   `FileSystemStorage` and `staticfiles` as `StaticFilesStorage`, none of them carrying an `OPTIONS`
   key, and `runserver` and `pytest` both start with no `AWS_*` variable set.
6. `freedom_ls_reports.W001` is gone, and its id is documented as retired.
7. All three file fields declare `storage=` through a named module-level callable, and the three
   generated migrations contain a dotted path and no bucket name, credential or endpoint.
8. `get_reports_storage()` has no exception handling, and a settings module with no `reports` key
   fails at startup with a message naming the missing key.
9. Reports upload to `cohort_reports/`, and the docstring says so.
10. `public` sets `CacheControl` to `public, max-age=86400` with no `immutable`, `certificates`
    sets it to `public, max-age=31536000, immutable`, and no other alias sets it at all.
11. A per-bucket credential override reaches only its own alias, verified by test.
