### Two implementation decisions the spec leaves open

Both are stated here as assumptions rather than escalated, because either reading produces working
code and this one is strictly simpler.

1. **`build_storages()` takes the reports alias name as an argument.** Spec §5.2 says the `reports`
   key is emitted under whatever name `REPORTS_STORAGE_ALIAS` resolves to. `REPORTS_STORAGE_ALIAS`
   is a Django setting read through `AppSettings`, which reads `django.conf.settings`, and
   `build_storages()` runs while `settings_prod.py` is still executing.

   That does not fail cleanly, which is the point. Django's lazy settings bootstrap is already part
   way through importing this very module, so a read from inside it builds a `Settings` snapshot
   from whichever names happen to be bound at that instant. Whether the right value comes back
   depends on whether the project wrote its `REPORTS_STORAGE_ALIAS` override above or below the
   `STORAGES = build_storages(...)` line. Silently wrong some of the time is worse than unavailable.

   So the alias name is a defaulted keyword argument, `reports_alias: str = "reports"`, and a caller
   that renamed the setting passes its own value. This is also what keeps the helper importable at
   settings-load time with no app-registry dependency, which §5.2 requires.
2. **`E001` reports an undeclared media alias rather than crashing on it.** `storages[alias]` raises
   `InvalidStorageError` for a key that is not declared. `user_uploads` and `certificates` have no
   model consumer, so a downstream project missing those keys boots fine and would then hit an
   uncaught traceback inside `check --deploy`. The check catches `InvalidStorageError` per alias and
   emits an `E001` naming the undeclared key. This is the same failure class the check exists for
   and the message shape §7.4 asks for, so it does not widen the rule so much as keep the check from
   being the thing that breaks.

## Task 1. Env-name resolution helpers

**File:** `freedom_ls/base/env.py`

`build_storages()` has to read each property from a per-bucket variable, falling back to a shared
one. `env_bool`/`env_int` take a single name, and their `_raw()` is what already implements
"unset or blank counts as unset". Two additions expose that, and nothing else changes in this
module.

```python
def env_str(name: str, default: str | None = None) -> str | None:
    """The stripped value of ``name``, or ``default`` when unset or blank."""
    value = _raw(name)
    return default if value is None else value


def first_set_name(*names: str) -> str | None:
    """The first of ``names`` set to a non-blank value, or None when none is."""
    return next((name for name in names if _raw(name) is not None), None)
```

`first_set_name` returns a *name*, not a value, so a caller can hand it straight to `env_bool` or
`env_int` and keep their `ImproperlyConfigured` behaviour on a malformed value.

Do not change the signature of `env_bool` or `env_int`. Both are called positionally from
`config/settings_prod.py` and from the template repo.

**Tests first** (`freedom_ls/base/tests/test_env.py`, or wherever the existing env tests live.
Check before creating a new file):

- `env_str` returns the stripped value, returns the default when unset, and returns the default when
  the variable is set to whitespace only.
- `first_set_name` returns the first name, skips a blank-valued name and picks the next, and returns
  `None` when none is set.

## Task 3. `STORAGES` defaults in `config/settings_base.py`

**File:** `config/settings_base.py`, in the media-files block near `MEDIA_ROOT` (currently
`:257-258`).

A literal dict, exactly as spec §5.5 gives it. Seven keys, six `FileSystemStorage`, `staticfiles`
as Django's `StaticFilesStorage`, and **no `OPTIONS` key on any entry**.

The absent `OPTIONS` is load-bearing, not tidiness: `FileSystemStorage` resolves its root as
`self._location or settings.MEDIA_ROOT` and drops the cached value on the `MEDIA_ROOT`
`setting_changed` signal. An alias with no explicit `location` therefore tracks `MEDIA_ROOT` and is
covered by the one autouse `_isolate_media_root` fixture; an alias with a `location` ignores
`MEDIA_ROOT` forever and writes into the working tree on every test run. Task 9 pins this by test.

Do not build this dict by calling `build_storages()` with nothing set. The two produce the same
result today, but a developer with `AWS_*` exported for an unrelated project would get real R2
buckets under `runserver` and, worse, under `pytest`.

**Tests first** (`freedom_ls/deployment/tests/test_storage.py` or a new
`freedom_ls/deployment/tests/test_storage_settings.py`). This is spec §10 case 10:

- `settings.STORAGES` declares all seven keys.
- Every declared entry whose backend is `FileSystemStorage` carries no `OPTIONS["location"]`.

This is the assertion that stops a later alias quietly opting out of `MEDIA_ROOT` isolation, so
write it as a loop over `settings.STORAGES` rather than seven hand-written asserts.

**Verification:** `uv run python manage.py check` and `uv run pytest` both still pass with no
`AWS_*` variable set.

## Task 4. `build_storages()`

**File:** `freedom_ls/deployment/storage.py`

Module house style (from `freedom_ls/deployment/settings_defaults.py`) is that the settings module
reads `os.getenv` and the helper takes resolved values. `build_storages()` is the deliberate
exception: reading forty environment variables at the call site would bury `settings_prod.py`.
Resolve inside the helper, keep it importable at settings-load time, and take nothing from the app
registry or `django.conf.settings`.

### Shape

Two consumers need the alias-to-purpose mapping, and they need different slices of it, so define it
once here in the shape both can derive from. `build_storages()` needs all seven aliases. The `E001`
check in Task 8 needs the five media aliases and must never include `default`. Getting this
membership wrong is the single easiest way to break the check, so the names below are deliberate:

```python
#: The media aliases whose name is fixed. `reports` is absent because its alias
#: name is configurable, and `default` because it is not a media alias.
MEDIA_ALIAS_PURPOSES: dict[str, str] = {
    "public": "PUBLIC",
    "course_media": "COURSE_MEDIA",
    "user_uploads": "USER_UPLOADS",
    "certificates": "CERTIFICATES",
}

#: The purpose prefix behind whatever REPORTS_STORAGE_ALIAS resolves to.
REPORTS_PURPOSE = "GENERATED"

DEFAULT_PURPOSE = "DEFAULT"

_OBJECT_PARAMETERS: dict[str, dict[str, str]] = {
    "public": {"CacheControl": "public, max-age=86400"},
    "certificates": {"CacheControl": "public, max-age=31536000, immutable"},
}


def media_alias_purposes(reports_alias: str) -> dict[str, str]:
    """The five media aliases and their purposes, reports under its own alias name."""
    return {**MEDIA_ALIAS_PURPOSES, reports_alias: REPORTS_PURPOSE}


def build_storages(
    *,
    staticfiles: dict[str, object],
    reports_alias: str = "reports",
) -> dict[str, dict[str, object]]:
    """Every STORAGES key, each alias resolved from its own environment variables."""
```

`media_alias_purposes()` is the single source of "which aliases are media aliases". Task 8's check
calls it too. It deliberately excludes `default`, because `default` is not a media alias and the
check compares everything else *against* it. Getting that membership wrong is the one mistake that
silently breaks `E001`, so it lives in one function rather than being spelled out twice.

### Per-alias resolution

Applied to each property independently:

1. `AWS_S3_<PURPOSE>_<PROPERTY>`
2. the shared variable
3. for the bucket name only, if neither is set, the alias falls back to `FileSystemStorage`

Shared-before-filesystem is the only non-breaking order for a project upgrading in place: it
reproduces today's single-bucket behaviour exactly. `E001` is what makes that case safe.

Pseudocode for one alias:

```python
def _alias_entry(purpose: str, object_parameters: dict[str, str] | None) -> dict[str, object]:
    bucket = env_str(f"AWS_S3_{purpose}_BUCKET_NAME") or env_str("AWS_STORAGE_BUCKET_NAME")
    if not bucket:
        return {"BACKEND": "django.core.files.storage.FileSystemStorage"}

    def name_for(prop: str, shared: str) -> str:
        return first_set_name(f"AWS_S3_{purpose}_{prop}", shared) or shared

    return build_s3_media_storage(
        bucket_name=bucket,
        access_key=env_str(name_for("ACCESS_KEY_ID", "AWS_S3_ACCESS_KEY_ID")),
        secret_key=env_str(name_for("SECRET_ACCESS_KEY", "AWS_S3_SECRET_ACCESS_KEY")),
        endpoint_url=env_str(name_for("ENDPOINT_URL", "AWS_S3_ENDPOINT_URL")),
        region_name=env_str(name_for("REGION_NAME", "AWS_S3_REGION_NAME")),
        custom_domain=env_str(name_for("CUSTOM_DOMAIN", "AWS_S3_CUSTOM_DOMAIN")),
        querystring_auth=env_bool(name_for("QUERYSTRING_AUTH", "AWS_QUERYSTRING_AUTH"), True),
        querystring_expire=env_int(name_for("QUERYSTRING_EXPIRE", "AWS_QUERYSTRING_EXPIRE"), 3600),
        object_parameters=object_parameters,
    )
```

Passing a *name* to `env_bool`/`env_int` rather than a value is what keeps their
`ImproperlyConfigured` behaviour: a malformed `AWS_S3_PUBLIC_QUERYSTRING_AUTH` raises naming that
variable, not the shared one.

### Assembly

The body emits all seven keys. `default` goes through the same three-step resolution as every other
alias, from `AWS_S3_DEFAULT_*` then the shared variables, so its only special case is that it is not
a media alias.

```python
def build_storages(
    *,
    staticfiles: dict[str, object],
    reports_alias: str = "reports",
) -> dict[str, dict[str, object]]:
    """Every STORAGES key, each alias resolved from its own environment variables."""
    storages: dict[str, dict[str, object]] = {
        alias: _alias_entry(purpose, _OBJECT_PARAMETERS.get(alias))
        for alias, purpose in media_alias_purposes(reports_alias).items()
    }
    storages["default"] = _alias_entry(DEFAULT_PURPOSE, None)
    storages["staticfiles"] = staticfiles
    return storages
```

No bucket name, credential, endpoint or domain appears as a literal in this module.

### Tests first

`freedom_ls/deployment/tests/test_storage.py`. `build_storages()` is a plain function returning a
dict and neither it nor `S3Storage.__init__` touches the network, so this needs no credentials, no
Django settings machinery and no database. Drive it with `monkeypatch.setenv` / `monkeypatch.delenv`

The nine cases from spec §10:

1. Every alias key present, in every configuration, including nothing set at all. Cover the several
   configurations with `@pytest.mark.parametrize` or separate named tests, never a loop inside one
   test body. This is the widest set of input combinations in the plan and so the most tempting place
   to write the loop `ds:testing` forbids.
2. A per-bucket variable wins over the shared variable.
3. An unset per-bucket variable falls back to the shared bucket, and the resulting entry equals
   `default`. This pins the precondition `E001` targets.
4. Neither set ⇒ `FileSystemStorage`.
5. Per-bucket credentials and endpoint override independently of the bucket name.
6. `public` carries `CacheControl: public, max-age=86400` with no `immutable`; `certificates`
   carries `public, max-age=31536000, immutable`; the other three media aliases carry no
   `object_parameters` key at all.
7. (covered in Task 2)
8. `default` resolves from `AWS_S3_DEFAULT_BUCKET_NAME` when set and from `AWS_STORAGE_BUCKET_NAME`
   when not. With the intended production variables set, no media alias entry equals `default`.
9. Two purpose variables set to the same bucket name produce two distinct entries that agree on
   `bucket_name` and differ on the per-alias properties. Drive it with the intended production
   variables and assert both pairs: `public`/`certificates` agreeing on bucket and differing on
   `CacheControl`, and `reports`/`user_uploads` agreeing on bucket and credentials while `reports`
   has no custom domain.

Two more, which the spec's list does not cover:

10. A per-bucket credential reaches only its own alias. Set `AWS_S3_PUBLIC_ACCESS_KEY_ID` to one
    value and the shared `AWS_S3_ACCESS_KEY_ID` to a different one, then assert `public` resolves to
    the per-bucket value and every other alias resolves to the shared one. Spec §10 case 5 proves a
    credential can be set without also setting a bucket name, which is a different claim. This is the
    one that actually earns success criterion 11, because the whole point of the override is that a
    narrow token does not leak into aliases that should not have it.
11. The `reports_alias` argument: a non-default value emits that key and no `reports` key.

**Where the production env set lives.** Cases 8 and 9 both want "the intended production
configuration", and Task 8e wants the same one. `freedom_ls/deployment/tests/` has no `conftest.py`
today. Create one and put the env set there as a single `PRODUCTION_ENV: dict[str, str]` constant,
plus a fixture that applies it through `monkeypatch.setenv`. Both `test_storage.py` and
`test_checks.py` then import one name instead of each carrying its own twenty-line copy that drifts

## Task 7. Model fields, callables and migrations

Land this **after** Task 3. See the ordering constraint above.

### 7a. Named module-level callables

Every per-field storage assignment goes through a named module-level callable in its own app's
`models.py`, beside the field it serves. Never a bare `Storage(...)` instance, never a lambda.

This is not a style rule. django-storages backends are `@deconstructible`, so `MigrationWriter`
re-emits a constructor call as literal Python in the generated migration file, resolved secret
values included. A field passing a bucket name and an access key into `S3Storage(...)` writes that
secret into git history permanently. The callable indirection is the only thing between `.env` and
`git log`. A lambda cannot be serialised at all.

Django records only the dotted path in the migration, so later bucket changes need no migration.
The result behaves as cached because `storages[alias]` caches the constructed instance per alias for
the process lifetime. That holds **only** while the callable delegates through `storages[alias]`
and constructs nothing itself.

Pick the names now and do not move them later: a migration freezes the whole dotted path, so a
rename breaks `migrate` for anyone replaying history from scratch. Treat it as costing what a public
API rename costs.

`freedom_ls/content_engine/models.py`, above the `File` class:

```python
def get_content_media_storage() -> Storage:
    """The alias named by CONTENT_MEDIA_STORAGE_ALIAS. The settings layer guarantees it exists."""
    return storages[config.CONTENT_MEDIA_STORAGE_ALIAS]
```

then `file = models.FileField(upload_to=file_upload_handler, storage=get_content_media_storage)`
at `:590`.

`freedom_ls/organisations/models.py`, above the `Organisation` class:

```python
def get_organisation_logo_storage() -> Storage:
    """The alias named by ORGANISATION_LOGO_STORAGE_ALIAS. The settings layer guarantees it exists."""
    return storages[config.ORGANISATION_LOGO_STORAGE_ALIAS]
```

then `storage=get_organisation_logo_storage` on the `logo` `ImageField` at `:31-35`, leaving
`upload_to`, `blank` and `validators` exactly as they are.

Both need `from django.core.files.storage import Storage, storages` and the app's `config` import.

`file_upload_handler` and `organisation_logo_upload_to` do not change.

### 8c. Comparing resolved storage

Both `S3Storage.bucket_name`/`endpoint_url` and `FileSystemStorage.location` are plain attributes
resolved with no network call, so the check can read them safely. Dispatch on backend type rather
than assuming `S3Storage`, because a downstream project can point an alias at any `Storage` subclass:

```python
def _storage_identity(storage: Storage) -> tuple[str | None, ...] | None:
    """Where a Storage writes, or None when the backend cannot be compared safely."""
    if isinstance(storage, S3Storage):
        return ("s3", storage.bucket_name, storage.endpoint_url)
    if isinstance(storage, FileSystemStorage):
        return ("fs", str(storage.location))
    return None
```

`endpoint_url` can be `None`, hence `tuple[str | None, ...]` rather than `tuple[str, ...]`.

An unrecognised backend returns `None` and the check stays silent for that alias. A false positive
on a custom backend is exactly the noise that gets a check silenced wholesale, which would lose the
signal permanently.

### 8d. The rule

All five media aliases: `public`, `course_media`, `user_uploads`, `reports`, `certificates`. The
rule is one sentence. **No media alias may resolve where `default` resolves.**

Each media alias is compared against `default` and never against another media alias. That is what
lets two aliases share a bucket on purpose: `public` and `certificates` resolving to the same bucket
is the intended configuration, and a check that flagged any two aliases agreeing would fire on it
every deploy until somebody silenced the whole check.

Comparing against `default` is usable only because `default` has a bucket name nothing else uses. An
alias matching it means either the per-bucket variable is missing and the alias fell through to the
shared one, or `AWS_S3_DEFAULT_BUCKET_NAME` was pointed at a real bucket. Both are configuration
errors, in every alias, so there is nothing to exempt. An exemption table would also need keeping
true every time an alias is added.

**Which aliases the check iterates, exactly.** Call
`media_alias_purposes(config.REPORTS_STORAGE_ALIAS)` from Task 4. Do not reach for
`MEDIA_ALIAS_PURPOSES` directly and do not hand-write a second list.

Two properties of that function are what make the check correct, and both are easy to lose:

- **`default` is not in it.** If it were, `default` would be compared against its own identity, match
  every time, and fire an `E001` on every deploy including the intended production one. That single
  mistake breaks success criteria 3 and 19.
- **`reports` is in it, under whatever name the setting resolves to.** The reports alias is the one
  this whole spec exists to protect, and its key is configurable, so it cannot be a literal. The
  check runs after apps are loaded, so `AppSettings` is available here even though it is not inside
  `build_storages()`.

The decision table, which is also the test matrix:

| Alias resolves to | Compared with `default` | Fires | Severity |
|---|---|---|---|
| Same `("s3", bucket, endpoint)` | identical | yes | Error |
| Same `("fs", location)`, `DEBUG=False` | identical | yes | Error |
| Same `("fs", location)`, `DEBUG=True` | identical | no | |
| Different bucket or endpoint | differs | no | |
| `None` identity on either side | not comparable | no | |
| Alias key not declared at all | n/a | yes | Error |

The filesystem row matters: a typo in `AWS_S3_GENERATED_BUCKET_NAME` with the shared variable also
unset lands a production worker on local disk, and a bucket-name comparison alone would find no
difference, for the wrong reason. Gating that row on `DEBUG=False` keeps the check aimed at real
production misconfiguration, since a staging smoke environment might use `FileSystemStorage`
deliberately.

The last row is the robustness decision recorded in §0 above.

The message must name **the alias and the per-bucket environment variable that fixes it**. On a
downstream project's first `check --deploy` an operator sees five of these at once, and that list is
the work. A `hint` pointing at the three-bucket grouping keeps five errors from reading as five
buckets.

Sketch:

```python
    try:
        default_identity = _storage_identity(storages["default"])
    except InvalidStorageError:
        return [Error("settings.STORAGES declares no 'default' key.", ...)]
    if default_identity is None:
        return []

    errors = []
    for alias, purpose in media_alias_purposes(config.REPORTS_STORAGE_ALIAS).items():
        try:
            identity = _storage_identity(storages[alias])
        except InvalidStorageError:
            errors.append(Error(f"...{alias!r} is not declared in settings.STORAGES...", ...))
            continue
        if identity is None:
            continue
        if identity[0] == "fs" and settings.DEBUG:
            continue
        if identity == default_identity:
            errors.append(Error(f"...{alias!r} resolves where 'default' resolves...",
                                hint=f"Set AWS_S3_{purpose}_BUCKET_NAME.",
                                id="freedom_ls_deployment.E001"))
    return errors
```

`default` gets the same `InvalidStorageError` guard as the media aliases, and for the same reason
given in §0. A downstream project with a hand-written `STORAGES` that omits `default` would otherwise
crash the check itself. Resolve it once, above the loop, and return early: with nothing to compare
against there is no comparison to make, so an undeclared `default` is reported and a `default` on an
uncomparable custom backend makes the whole check silent.

**Both check runs write log files, and that is expected.** `config/settings_prod.py:92` sets
`LOGGING = fls_defaults.build_logging_config(log_dir=BASE_DIR / "logs")` unconditionally, and

its file on construction, so each run appends to `logs/django.log`, `logs/django_errors.log` and
`logs/security.log`. Those match the `*.log` gitignore pattern and are harmless to leave. Delete them
if you want the run to leave no trace. This is pre-existing behaviour of `settings_prod`, not
something this work introduces, but this plan is the first thing to ask anyone to run `settings_prod`
from a working tree, so it is worth knowing before it surprises somebody.

## Out of scope: do not do these

Stated because each is a plausible-looking adjacent change an implementer might reach for.

- **Do not create any R2 bucket, token or lifecycle rule.** Spec §13 lists the operator decisions;
  they happen outside this repo.
- **Do not add a model field, view or upload path for certificates or user documents.** Their aliases
  are declared and nothing else.
- **Do not change `file_upload_handler`.** `course_media` owns its whole bucket; the existing
  `content_engine/` prefix is harmless and changing it would cost a migration for nothing.
- **Do not add a `location` to any `FileSystemStorage` entry.** Task 3 explains why; Task 9 tests it.
- **Do not change `FileAdmin` or `OrganisationAdmin`.** Both expose the raw file field and both stay
  that way. Spec §12 is a decision, not an oversight. The reports admin's carve-out
  (`freedom_ls/reports/tests/test_admin.py:94-106`) also stays exactly as it is.
- **Do not generalise `isolated_reports_storage` to other aliases.** It cannot work; that is why it
  is being deleted.
- **Do not touch `spec_dd/1. next/certificates/idea.md` or
  `spec_dd/1. next/user-data-retention-idea.md`.** They are named as downstream consumers of these
  constraints, not as files this work edits.
- **Do not write `upgrade_notes.md`.** Spec §11 says what it must contain, and it is authored
  separately from this implementation.
- **Do not create any new documentation file.** Task 11 is edits to existing files only.
