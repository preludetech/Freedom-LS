# Per-placement due dates for shared content

Spec 8 of 8 in the Deadlines effort (`spec_dd/1. next/roadmap.md`, "Deadlines"). Source:
`idea.md` in this directory. Line targets for the plan are in `plan_notes.md`.

## Purpose

A due date lives in the child's own file today, so a topic or form placed in two courses has the
same date in both, and a part placed in two courses brings its children's dates into both. After
this spec, a `children:` entry in `course.md` or `part.yaml` can set a due date for that one
placement, or say there is none. A `course.md` entry that places a part can do the same for each
of the part's children. Staff deadline overrides still win over all of it. Courses that
auto-discover their children behave exactly as they do after spec 1.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| part placement | coined | A `ContentCollectionItem` whose collection is a `Course` and whose child is a `CoursePart` |
| `CoursePartChildDueDate` | coined | The due date one part placement sets for one child of its part |
| `children:` on a part placement | narrowed | The list nested in a `course.md` entry whose child is a part. It names the part's children by path to give them due keys. It never adds, removes or reorders the part's children |

## Scope

In:

- Due keys (`due_date`, `due_time`, `due_days_after_registration`) and a new `no_due_date` flag
  on a `children:` entry whose child is a topic or a form, in `course.md` and `part.yaml`.
- A nested `children:` list on a `course.md` entry whose child is a part, naming the part's
  topics and forms by path and giving each the same keys.
- Loading, validating, resolving, admin display and author-plugin support for both.
- Retiring `Child.overrides` and `ContentCollectionItem.overrides`.

Out:

- Dates on an activity or article placement. A time limit on a part.
- Any change to the staff override layers, the consequence policy or extensions (specs 1 to 3).
- Pruning stale placements on re-import.
- One value for every child of a part, or a due date on the part placement itself. Only named
  children carry a value.
- Parts nested in parts.
- The same child listed twice in one collection.

## Decisions

1. **Precedence, most specific first:** learner override, cohort override, then the content
   layer, which is the first of: the `course.md` part placement's value for the child, the
   `part.yaml` entry's value, the child file's value. A value replaces the layer below it whole;
   keys are never merged. A placement that sets `due_days_after_registration: 7` and no
   `due_time` is due at the end of the day even if the child file sets `due_time: "17:00"`.
2. **`no_due_date: true` is how a placement says "no deadline here"**, so a course can drop a
   date the child file sets. It is allowed only on a placement. It resolves as
   `DeadlineKind.NONE` with source `DeadlineSource.CONTENT`, so a staff override still beats it.
3. **A direct placement's value is written on its own row.** The `ContentCollectionItem` row for
   a topic or form is already that one placement. A part's own rows are shared by every course
   that places the part, which is exactly the `part.yaml` layer.
4. **A part placement's values for its children go in a new table, `CoursePartChildDueDate`**,
   one row per (part placement, child row). A JSON blob on the placement was rejected because it
   loses typed columns and foreign keys.
5. **The resolver's source stays `DeadlineSource.CONTENT`** for all three content layers. Specs 2
   and 3 read the content layer as one layer.
6. **`overrides` is retired.** Nothing but the content admin reads it, and the due keys are
   first-class fields on the entry.
7. **Spec 1's Decision 2 is revised.** A date lives in the child file when the content is placed
   once, and on the `children:` entry when it depends on where the content sits.

## Requirements

### Authoring shape

```yaml
# course.md frontmatter
children:
  - path: 01. intro/content.md
    due_days_after_registration: 3
  - path: shared-part/part.yaml
    children:
      - path: 01. welcome/content.md
        due_date: 2026-03-14
        due_time: "17:00"
      - path: 03. knowledge-check/form.md
        no_due_date: true
```

```yaml
# shared-part/part.yaml
children:
  - path: 01. welcome/content.md
    due_days_after_registration: 7
```

A nested `children:` path is relative to the directory holding the part's `part.yaml`. It is
matched against the part's children after both are resolved the way `resolve_author_path`
resolves them, so a child the `part.yaml` reaches through `../shared.md` is named the same way.
The part's own children may be listed in `part.yaml` or auto-discovered.

### Schema: `freedom_ls/content_engine/schema.py`, `freedom_ls/content_base/schema.py`

- `Child` keeps `extra="forbid"` and `path`. It drops `overrides` and gains the `DueDateFields`
  keys, `no_due_date: bool = False`, and `children: list[PartChildDueDate] | None`.
- New `PartChildDueDate(BaseModel)`, `extra="forbid"`, with `path: Path`, the `DueDateFields` keys
  and `no_due_date`.
- On both models, `no_due_date: true` with any due key is a validation error. So is a
  `PartChildDueDate` with no due key and no `no_due_date`.
- These messages name the entry's `path`. The existing parse error reporting adds the declaring
  file, as it does for every other schema error.

### Cross-reference rules: `content_save` and `freedom_ls/content_engine/validate.py`

One shared function applies the rules that need the child's type, and both the loader and the
validator call it:

- due keys or `no_due_date` on an entry whose child is an activity, article or part;
- a nested `children:` list on an entry whose child is not a part, or on a `part.yaml` entry;
- a nested path that names nothing in the part, or names a part;
- the same child named twice in one nested list.

A load collects every such error and fails once, inside the atomic load. Each error gives the
declaring file, the entry, the bad path and the paths the part does contain, in the style of the
existing unknown-child `ValueError` in `content_save`.

### Model: `freedom_ls/content_engine/models/courses.py`

- `ContentCollectionItem`: remove `overrides`; add
  `no_due_date = models.BooleanField(default=False)`.
- New `CoursePartChildDueDate(SiteAwareModel)`:
  - `part_collection_item`: FK to the part placement's `ContentCollectionItem`, `CASCADE`,
    `related_name="child_due_dates"`.
  - `collection_item`: FK to the part's `ContentCollectionItem` row for the child, `CASCADE`,
    `related_name="+"`.
  - `due_date`, `due_time`, `due_days_after_registration` and `no_due_date`, named and typed as
    on `ContentCollectionItem`.
  - `UniqueConstraint` on `(part_collection_item, collection_item)`.
- Migrations come from `makemigrations`. Dropping `overrides` needs no data step.
- Content admin (`freedom_ls/content_engine/admin.py`, `fls-dev:admin-interface`): remove
  `overrides` from `ContentCollectionItemInline` and add `no_due_date` to the read-only fields of
  both it and `ContentCollectionItemAdmin`. `ContentCollectionItemAdmin`, whose change page is
  one placement, gets a read-only `CoursePartChildDueDate` inline with no add or delete.

### Loader: `freedom_ls/content_engine/management/commands/content_save.py`

- `children_list` carries the `Child` entry, not `child.overrides`. Auto-discovered children carry
  no entry.
- Each placement row's due columns and `no_due_date` come from the entry when it holds any due key
  or `no_due_date`. Otherwise they come from the child file's schema through `due_date_columns`,
  and `no_due_date` is `False`. A part's own rows therefore hold the `part.yaml` entry's value or
  the file's, and that is the resolver's fallback.
- `CoursePartChildDueDate` rows are reconciled in a second pass, after every collection's rows
  are written, because a course is processed before the parts it places. For each part placement,
  each named child is upserted with every column written, and rows for children the entry no
  longer names are deleted.
- Every `CoursePartChildDueDate` write and delete passes the load's `site` explicitly, as the
  existing `ContentCollectionItem` writes do.

### Resolver: `freedom_ls/deadlines/resolver.py`

- `DeadlineValue.from_columns` takes `no_due_date` and returns `DeadlineValue(DeadlineKind.NONE)`
  when it is set.
- `_defaults_by_course` makes one more query: `CoursePartChildDueDate` rows whose
  `part_collection_item` is among the part rows in `top_rows`. A part's child row credited to a
  course takes that course's `CoursePartChildDueDate` value when one exists, and the row's own
  columns otherwise.
- `course_deadlines_for` makes at most 6 queries, whatever the number of children, courses or
  records. The docstring's query count is updated.

### Admin: `freedom_ls/deadlines/queries.py`, `freedom_ls/deadlines/admin.py`

- `content_default_for(row)` returns the content-layer value for the row's course
  (`row.course`), with the resolver's precedence. `layers_beneath`, `canonical_beneath`, the
  "Content default" column, the "Default has changed" note and the `replaced_value` stamp all build
  on it. So a placement value shows when one is set, and a changed placement value is reported
  like a changed file value.
- `content_default_for` and `layers_beneath` take an optional pre-read mapping of placement values
  keyed by child row id. Each inline builds it once in `get_formset`, the way
  `LearnerDeadlineOverrideInline` builds `cohort_rows`, so rendering costs no more queries for 20
  rows than for 2.

### Author plugin: `claude_plugins/fls-content`

- Make the schema and cross-reference changes in the app files, then re-sync the bundled
  `validate/` copy through `fls-dev:update_claude_plugin_fls_content`. Never hand-edit the copy.
- `skills/content-types/resources/course-files.md`, `topic-files.md` and `form-files.md` follow
  Decision 7 instead of "not in the course's `children:` list". They document the entry keys, the
  nested `children:` list, `no_due_date` and the precedence, using the YAML above as the example.

### Demo content: `demo_content/`

A new course with an explicit `children:` list places a part of
`functionality_demo_course_parts`. It gives one child a placement value and another
`no_due_date: true`.

## Testing

- Schema: each new key is accepted on `Child` and `PartChildDueDate`. `no_due_date` with a due
  key is rejected, as are a keyless `PartChildDueDate` and `overrides:`. Mirror these in
  `claude_plugins/fls-content/validate/tests/test_validator.py`.
- Cross-reference rules: each rule fails the load and the validator, and names the bad path.
  Several errors give one failure listing all of them.
- Loader: a `course.md` entry's value beats the child file's on that row only, and the same
  topic placed elsewhere keeps the file's value. A `part.yaml` entry's value beats the file's.
  A nested list writes `CoursePartChildDueDate` rows. Removing a key or a nested entry clears the
  column or deletes the row on the next sync.
- Resolver: one part placed in two courses, with child dates in one and none in the other,
  resolves per course. For one child, the `course.md` value beats the `part.yaml` value, which
  beats the file. `no_due_date` beats a file date and loses to a cohort override. A value
  replaces the lower one whole. The query-count tests use a course that places a part with child
  dates, so the new query runs, and stay within 6 for 6 and 60 children across one and several
  courses.
- Admin: "Content default" shows the placement value. Changing a placement value after an
  override was stamped shows "Default has changed". Inline query counts don't grow with rows.
- Regression: an auto-discovered course resolves the same as before.

## Documentation and downstream

- Upgrade notes: `overrides` is removed from `Child` and `ContentCollectionItem`, so content that
  sets `overrides:` fails to load. They also cover the new `children:` keys and
  `CoursePartChildDueDate`.
- `.claude/skills/domain-glossary/SKILL.md`: the `ContentCollectionItem` row drops `overrides`.
  The **content default** row gains the placement value and `CoursePartChildDueDate`. A new
  `CoursePartChildDueDate` row and a **placement** entry pointing at `ContentCollectionItem` are
  added. The "Never `ContentCollectionItem.overrides`" clause goes, along with the field.
- `docs/product/content-editing-workflow.md`: the entry due keys, the nested `children:` list and
  the new load errors, next to the unknown-child rule.

## Success criteria

- A part placed in two courses has child deadlines in one and none in the other, with no staff
  override.
- Neither `Child` nor `ContentCollectionItem` has an `overrides` field, and `overrides:` in a
  `children:` entry is rejected.
- The `fls-content` validator accepts and rejects the same files as `content_save`.
