# Per-placement due dates for shared content

Spec 8 of 8 in the Deadlines effort (`spec_dd/1. next/roadmap.md`, "Deadlines"). Source:
`idea.md` in this directory.

## Purpose

A due date lives in the child's own file today, so a topic or form placed in two courses has the
same date in both, and a part placed in two courses brings its items' dates into both. After this
spec, a `children:` entry in `course.md` or `part.yaml` can set a due date, or say there is none,
for that one placement. A `course.md` entry that places a part can do the same for each of the
part's items. Staff deadline overrides still win over all of it. Courses that auto-discover their
children behave exactly as they do after spec 1.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| placement | narrowed | One `ContentCollectionItem` row: a child in a course or part (glossary, `TopicProgress` line) |
| part placement | coined | A `ContentCollectionItem` whose collection is a `Course` and whose child is a `CoursePart` |
| `CoursePartItemDueDate` | coined | A due date one part placement sets for one item of its part. No existing model holds a per-course value for a shared part's item |

## Scope

In:

- Due keys (`due_date`, `due_time`, `due_days_after_registration`) and a new `no_due_date` flag
  on a `children:` entry whose child is a topic or a form, in `course.md` and `part.yaml`.
- An `items:` list on a `course.md` entry whose child is a part, naming the part's topics and
  forms by path and giving each the same keys.
- Loading, resolving, admin display and author-plugin support for both.
- Retiring `Child.overrides` and `ContentCollectionItem.overrides`.

Out:

- Dates on an activity or article placement. A time limit on a part.
- Any change to the staff override layers, the consequence policy or extensions (specs 1 to 3).
- Pruning stale placements on re-import.
- One value for every item of a part (only named items).
- Parts nested in parts. The resolver and `Course.collection_items_flat` go one level deep
  today, and so does this spec.
- The same child listed twice in one collection, which already collapses to one row.

## Decisions

1. **Precedence, most specific first:** learner override, cohort override, then the content
   layer, which is the first of: the `course.md` part placement's item value, the `part.yaml`
   entry's value, the child file's value. A value replaces the layer below it whole; keys are
   never merged across layers. So a placement that sets `due_days_after_registration: 7` and
   no `due_time` is due at the end of the day, even if the child file sets `due_time: "17:00"`.
   This matches how `resolve_deadline` already treats a layer.
2. **`no_due_date: true` is how a placement says "no deadline here".** Without it, a course
   cannot drop a date that the child file sets. It is only allowed on a placement. A child file
   says the same thing by leaving the due keys out. It resolves as `DeadlineKind.NONE` with
   source `DeadlineSource.CONTENT`, so a staff override above it still wins.
3. **A direct placement's value is written on its own row.** The `ContentCollectionItem` row for
   a topic or form is already that one placement. The loader writes the entry's value to its due
   columns, falling back to the child file's value. A `part.yaml` entry's row is shared by every
   course that places the part, which is what that layer means.
4. **A part placement's item values go in a new table, `CoursePartItemDueDate`**, one row per
   (part placement, item). A part's own item rows are shared across courses, so a per-course
   value can't live on them. A table keeps typed columns and foreign keys that a JSON blob keyed
   by row pk would lose. The cost is one extra resolver query, and that query doesn't grow with
   the number of items or courses.
5. **The resolver's source stays `DeadlineSource.CONTENT`** for all three content layers. Spec 1
   defines the content layer as one layer, and specs 2 and 3 read it as one.
6. **`overrides` is retired.** Nothing but the content admin reads it, no file in the repo sets
   it, and the glossary already tells people not to treat it as a deadline override. The due
   keys sit on the entry as first-class fields, so `overrides` has no use left. Downstream
   content that sets `overrides:` will fail to load, and the upgrade notes must say so.
7. **Spec 1's Decision 2 is revised.** When content is placed once, its date still lives in the
   child file. The `children:` entry is for a date that depends on where the content sits.

## Requirements

### Authoring shape

```yaml
# course.md frontmatter
children:
  - path: 01. intro/content.md
    due_days_after_registration: 3
  - path: shared-part/part.yaml
    items:
      - path: 01. welcome/content.md
        due_date: 2026-03-14
        due_time: "17:00"
      - path: 03. knowledge-check/form.md
        no_due_date: true
```

```yaml
# shared-part/part.yaml
children:
  - path: 01. welcome/content.md
    due_days_after_registration: 7
```

An `items:` path is relative to the directory holding the part's `part.yaml`. It is matched
against the part's children after both are resolved the way `resolve_author_path` resolves them,
so an item that a `part.yaml` entry reaches through `../shared.md` is named the same way.

### Schema: `freedom_ls/content_engine/schema.py`, `freedom_ls/content_base/schema.py`

- `Child` keeps `extra="forbid"` and `path`. It drops `overrides`, and gains the `DueDateFields`
  keys, `no_due_date: bool = False`, and `items: list[PartItemDueDate] | None`.
- New `PartItemDueDate(BaseModel)`, `extra="forbid"`, with `path: Path`, the `DueDateFields` keys
  and `no_due_date`.
- `no_due_date: true` together with any due key is a validation error, on both models.
- `DueDateFields` validation messages name the declaring file and the entry's `path`. Today a
  `Child` has no `file_path`, so the message prefix would read `None:`.
- Errors that need the child's type are raised at load time, in `content_save`, not in pydantic:
  due keys or `no_due_date` on an entry whose child is an activity, article or part; `items:` on
  an entry whose child is not a part; `items:` on a `part.yaml` entry; an `items:` path that
  names nothing in the part, or names a part; the same item named twice in one `items:` list.
  A load collects every such error and then fails once, inside the atomic load, listing for each
  the declaring file, the entry, the bad path and the paths the part does contain. This is the
  same style as the existing unknown-child `ValueError` at `content_save.py:1176-1182`.

### Model: `freedom_ls/content_engine/models/courses.py`

- `ContentCollectionItem`: remove `overrides`; add
  `no_due_date = models.BooleanField(default=False)`.
- New `CoursePartItemDueDate(SiteAwareModel)`:
  - `part_placement`: FK to the part placement's `ContentCollectionItem`, `CASCADE`,
    `related_name="item_due_dates"`.
  - `collection_item`: FK to the part's `ContentCollectionItem` row for the item, `CASCADE`,
    `related_name="+"`.
  - `due_date`, `due_time`, `due_days_after_registration` and `no_due_date`, named and typed as
    on `ContentCollectionItem`.
  - `UniqueConstraint` on `(part_placement, collection_item)`.
- Migrations made with `makemigrations`. Dropping `overrides` needs no data step because nothing
  reads it.
- Register `CoursePartItemDueDate` read-only in the content admin, as an inline under the part
  placement, via `SiteAwareModelAdmin` conventions (`fls-dev:admin-interface`). Remove
  `overrides` from `ContentCollectionItemInline` (`content_engine/admin.py:149-168`) and add
  `no_due_date` to its read-only fields.

### Loader: `freedom_ls/content_engine/management/commands/content_save.py`

- `children_list` carries the `Child` entry, not `child.overrides`. Auto-discovered children carry
  no entry.
- Each placement row's due columns and `no_due_date` come from the entry when it holds any due key
  or `no_due_date`. Otherwise they come from the child file's schema through `due_date_columns`.
  `no_due_date` is written `False` whenever the entry doesn't set it.
- For each part placement, `CoursePartItemDueDate` rows are reconciled every sync: each named
  item is upserted with every column written, absent keys included, and rows for items the entry
  no longer names are deleted. Removing a key removes its value, by spec 1's rule. A part
  placement with no `items:` ends up with no rows.

### Resolver: `freedom_ls/deadlines/resolver.py`

- `DeadlineValue.from_columns` takes `no_due_date` and returns `DeadlineValue(DeadlineKind.NONE)`
  when it is set.
- `_defaults_by_course` makes one more query: `CoursePartItemDueDate` rows whose `part_placement`
  is among the part rows in `top_rows`. In the crediting loop (`:185-197`) a part item row
  credited to a course takes that course's `CoursePartItemDueDate` value when one exists, and the
  row's own columns otherwise.
- `course_deadlines_for` makes 6 queries, whatever the number of items, courses or records. The
  query budgets go up by one: `freedom_ls/deadlines/tests/test_resolver.py` 5 to 6, and 6 to 7
  at `:577-581`; `freedom_ls/deadlines/tests/test_policy.py:272` 8 to 9.

### Admin: `freedom_ls/deadlines/queries.py`, `freedom_ls/deadlines/admin.py`

- `content_default_for(row)` returns the content-layer value for the row's course
  (`row.course`), with the same precedence as the resolver. `layers_beneath`, `canonical_beneath`,
  the "Content default" column (`admin.py:272-276`), the "Default has changed" note
  (`:286-296`), and the `replaced_value` stamp (`:141`) all build on it. So a placement value is
  shown when one is set, and a changed placement value is reported like a changed file value.
- Each inline reads the placement values in bulk. Rendering an inline costs no more queries for
  20 rows than for 2.

### Author plugin: `claude_plugins/fls-content`

- `validate/schema.py`: its copies of `Child` and `DueDateFields` match the app's. Add
  `PartItemDueDate` and `no_due_date`, and drop `overrides`. Report the type-dependent errors
  above wherever the validator can see the child's file.
- `skills/content-types/resources/course-files.md` (the `time_limit_days` and `children` rows,
  "Children ordering", the part table's `children` row), `topic-files.md` (`:30-33`) and
  `form-files.md` (`:30`): drop "not in the course's `children:` list". Say a date goes in the
  child file when the content is placed once, and on the `children:` entry when it depends on
  where the content sits. Document `items:`, `no_due_date` and the precedence, with the YAML
  above as the example.

### Demo content: `demo_content/`

A course with an explicit `children:` list places `functionality_demo_course_parts`' parts,
giving one item a placement value and another `no_due_date: true`. The existing auto-discovered
courses are left unchanged.

## Testing

- Schema: each new key is accepted on `Child` and `PartItemDueDate`. `no_due_date` with a due key
  is rejected. `overrides:` is rejected. Messages name the file and entry path. Mirror these
  tests in `claude_plugins/fls-content/validate/tests/test_validator.py`.
- Loader: a `course.md` entry's value beats the child file's on that row only, and the same
  topic placed elsewhere keeps the file's value. A `part.yaml` entry's value beats the file's.
  `items:` writes `CoursePartItemDueDate` rows. Removing a key or an `items:` entry clears the
  column or deletes the row on the next sync. Each type-dependent error fails the whole load and
  names the bad path. When several errors exist, one failure lists all of them.
- Resolver: one part placed in two courses, with item dates in one and none in the other,
  resolves per course. Precedence covers all three content layers and both override layers.
  `no_due_date` beats a file date and loses to a cohort override. The value is replaced whole,
  not merged. The query count is 6 for 6 and 60 items across one and several courses.
- Admin: "Content default" shows the placement value. Changing a placement value after an
  override was stamped shows "Default has changed". Inline query counts don't grow with rows.
- Regression: an auto-discovered course resolves identically to before.

## Success criteria

- A part placed in two courses has item deadlines in one and none in the other, with no staff
  override.
- `course.md` item value, then `part.yaml` entry value, then child file value, with staff
  overrides above, holds in resolver tests.
- `course_deadlines_for` costs 6 queries regardless of item count.
- Removing a placement key or `items:` entry and re-syncing removes the value.
- An unknown or misplaced `items:` path, or a due key on the wrong child type, fails the load
  and names the file and path.
- The admin's "Content default" and "Default has changed" follow placement values.
- `grep -rn overrides freedom_ls/content_engine claude_plugins/fls-content/validate` finds no
  `Child` or `ContentCollectionItem` field.
- An auto-discovered course's resolved deadlines are unchanged.
- The `fls-content` validator accepts and rejects the same files as `content_save`.
