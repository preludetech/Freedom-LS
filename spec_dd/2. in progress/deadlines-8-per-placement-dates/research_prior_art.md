# Prior art: per-placement due dates on shared content

## Here (FreedomLS)

**Nothing has been built for per-placement authored dates.** What exists, and why:

- **Old deadlines** (`2026-02-19_19:25_deadlines`, `2026-02-21_16:30_deadlines_deactivate`): `CohortDeadline`, `LearnerDeadline` and `LearnerCohortDeadlineOverride` were fixed lock dates set by staff in the admin, with no authored content default. Spec 1 removed them. They keyed on the content row's pk, not the placement.
- **Grain mismatch, found in `better-course-progress-tracking` QA (S10.3), recorded not fixed.** `CohortDeadline` stored the form's pk while progress keys on the `ContentCollectionItem`. One deadline badge showed on both placements of one form, each with independent progress. Source: `deadlines-1` `research_prior_art.md` section 1.3. This is why spec 1 attached deadlines to the placement.
- **Spec 1 Decision 2** (`3. done/2026-10-25_17:46_deadlines-1-dates-and-overdue/1. spec.md` line 46): content defaults live on the child's own file, not the `children:` list, because auto-discovered children (every demo course) have no `children:` entry. The spec states the consequence: "A file placed twice carries the same default on both collection items; deadline overrides still differ per collection item." Spec 1's idea listed "frontmatter shape (child list, `overrides`, or item)" as an unknown; the roadmap lists it as owned by spec 1 and affecting 2 and 6. It chose the item. Per-placement dates were not rejected as wrong. They were pushed out and became spec 8, added 2026-10-25 from review of spec 1's PR (roadmap Deadlines section).
- **Spec 1 glossary** (line 19): a "deadline override" is a `CohortDeadlineOverride` or `LearnerDeadlineOverride` row, "Not `ContentCollectionItem.overrides`, which this spec leaves alone".
- **Why `ContentCollectionItem.overrides` exists and is unread.** It was in `content_engine/migrations/0001_initial.py` and `Child.overrides` (`content_engine/schema.py:186-192`, "optional overrides as key-value pairs") from the start, as a speculative hook. Spec 1's `research_codebase.md` (line 34) confirms it is "stored but read by nothing": no demo content, plugin doc or test sets it. `content_save.py:1073,1165` writes it on every load. Only the admin (`content_engine/admin.py:160`) shows it. No doc records a design for it, so it was never specified. Treat it as dead schema, not as a prior decision.
- **Resolver** (`freedom_ls/deadlines/resolver.py`, `_defaults_by_course`): already credits a shared part's item rows to every course that places the part, in three queries. This is the exact place a per-course content layer would plug in, and it shows the shared-part problem is known: one set of item rows serves all courses.
- **Carry-over** (spec 1): when a load creates a new collection item for a child that has exactly one stale sibling in the course, deadline overrides move to it. A moved placement therefore re-derives content defaults on sync but keeps staff overrides. Any per-placement value stored on a row must also survive or be re-derived under this rule; the idea's "every sync, removing a key removes the value" matches spec 1's item-column rule.
- **Plugin docs** (`claude_plugins/fls-content/.../topic-files.md:32`, `course-files.md`, `form-files.md`) currently say to write due dates in the child file, not `children:`. They encode Decision 2.
- **In-progress specs.** `deadlines-2-consequence-policy` and `design_learner-interface-deadlines` do not touch authored placement dates. The roadmap says spec 8 edits the loader and the resolver's content layer, which 2 and 3 read but do not change.
- **Sentiment research** (`1. next/deadlines/research_deadlines_user_sentiment.md`, `research_lms_deadlines_landscape.md`): overrides must follow or visibly flag base-date edits (Moodle's do not; Moodle overrides are lost on backup/restore). Spec 1 answered with the "Default has changed" flag, which the idea wants extended to placement values.

## Elsewhere

- **Canvas Blueprint.** Locks can cover content, points, due dates and availability dates. Wharton's sites leave due and availability dates unlocked because they are "often modified in a section-specific child site". A date edited in a child stays put on later syncs; later parent edits keep updating every child where the date has not been changed. Cost: parent edits silently do not reach customised sections. A community thread reports sync changing course and module settings of sections that have different dates. The first sync after associating runs for all associated courses. Lesson for FLS: per-placement value that beats the shared one, with the base still flowing to un-customised placements, matches Canvas practice; show which value applies and when the base has moved. Sources: https://support.wharton.upenn.edu/help/blueprint-sites-in-canvas , https://kb.uwstout.edu/106873 , https://community.canvaslms.com/t5/Archived-Questions/ARCHIVED-Blueprint-Course-Sync-disrupts-module-settings/td-p/439152 , https://www.montana.edu/ecat/help/instructors/blueprint/blueprint-management-guide/
- **Open edX.** One library block can be reused in many courses. Due dates are set on graded subsections in the course, not on library components, so a reused block takes the date of the subsection it sits in. A library-sourced component can carry course-local overrides (title, text) that survive a library sync. Dates are stored in `edx-when`, which also holds per-learner extensions and relative dates. Lesson: the date belongs to the course's own structure, not to the shared content, and the override survives upstream sync. I did not find a source confirming a course-specific due date on a reused block. The component-level due date is a third-party XBlock. Sources: https://docs.openedx.org/en/latest/_sources/educators/concepts/instructional_design/content_libraries.rst , https://pypi.org/project/edx-when/1.2.6 , https://discuss.openedx.org/t/course-relative-due-dates-and-the-direction-for-scheduling/682 , https://github.com/eduNEXT/xblock-extemporaneous-grading
- **Moodle.** Dates live on the activity instance in a course. Course copy, import and backup/restore carry the activity's own dates, and overrides do not follow base-date edits (and are lost on restore). Source in repo: `research_lms_deadlines_landscape.md` (cites https://docs.moodle.org/en/Assignment_overrides and https://www.monash.edu/learning-teaching/teachhq/moodle/assignment/how-to/extensions-and-resubmissions). Not re-searched here.

## Takeaways for the spec

1. Nothing was tried and failed in FLS. The idea is a deferred decision, not a retry.
2. `ContentCollectionItem.overrides` has no design behind it; retiring or repurposing it is free of compatibility cost within FLS, though downstream data may hold values. Check `upgrade_notes.md` practice for a migration note.
3. The one known hazard is the shared part: its item rows are common to all courses, so per-course values need a course-to-part placement store that `_defaults_by_course` reads without adding per-item queries.
4. Peer systems keep the date on the course-side structure and let it win over the shared source, with upstream edits still flowing where nothing is customised. They also show the silent-staleness pain, which the "Default has changed" comparison addresses.
