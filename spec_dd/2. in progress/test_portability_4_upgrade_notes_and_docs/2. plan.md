## Ground truth (verified against this worktree, 2026-08-23)

- **Conformance probes carry no markers.** `test_urls.py`, `test_settings.py`,
  `test_theme.py`, `test_migrations.py` under `freedom_ls/contrib/conformance/`
  have no `pytestmark` and no `@pytest.mark.*`, and neither the root `conftest.py`
  nor `freedom_ls/conftest.py` injects markers (no
  `pytest_collection_modifyitems`, no `pytest_configure` marker logic). The
  `-m "not playwright and not fls_internal and not ci_only"` selection therefore
  **already collects every probe**. (`tests/test_conformance_meta.py` does carry
  `fls_internal`, but is never imported downstream.)
- **The gap is opt-in, not invocation.** The suite is an importable module with no
  management command and no `pytest --pyargs` target. Without a downstream
  `tests/` file importing it, pytest collects zero probes — silently, not as a
  collection error. The opt-in snippet (both the `import *` form and the
  collision-safe re-export form) is in
  `3. done/2026-07-18_13:35_test_portability_2_conformance_suite/upgrade_notes.md`.
- **`freedom_ls_course_access.E001` was repurposed.**
  `freedom_ls/course_access/checks.py`'s module docstring: `E001` = a required
  setting is unset (emitted by the shared `required_settings_errors` helper),
  `E002` = a `Course` has an `access_config` the active backend rejects, `E003` =
  the configured FLS backend's app is not installed. A downstream that silenced
  `E001` now silences a different check, with no error to say so.
- **`required_settings_errors(config, app_label)`** lives in
  `freedom_ls/base/app_settings.py` and builds `f"{app_label}.E001"` Errors. Its
  callers are `freedom_ls/course_access/checks.py` (`COURSE_ACCESS_BACKEND`) and
  `freedom_ls/content_engine/checks.py` (`ADMONITION_TYPES`) — the two current
  hard-requirement checks.
- **All FLS checks run on a plain `manage.py check`.** Eight `checks.py` modules
  under `freedom_ls/`; their `@register` decorators carry only `Tags.security` or
  `Tags.compatibility` — **no `deploy=True` anywhere**. Errors exit non-zero and
  abort `check`/`runserver`/`migrate`; Warnings do not. Do not hardcode a check
  count in the guidance: it goes stale on the next spec.
- **The migration gates already run every system check.** Neither Django's
  `migrate` nor its `makemigrations` overrides `requires_system_checks`
  (verified in `.venv/.../django/core/management/commands/`), so both inherit
  `"__all__"` and `BaseCommand.execute()` runs `self.check()` before the command
  body. `update_fls.md`'s 3b, 3e and 3g therefore already abort on any FLS
  `Error` today. The new `check` step is justified by **attribution** (a config
  Error currently reads as a migration-gate failure) and **warning visibility**
  (`display_num_errors` is set only by `check` itself), not by discovery.
- **The two required settings are currently the whole set.** Only
  `COURSE_ACCESS_BACKEND` and `ADMONITION_TYPES` are `Setting(required=True)`;
  `freedom_ls/reports/config.py` calls the same helper but declares none.
- **`claude_plugins/fls-dev/commands/concrete/update_fls.md`** runs the Part-1
  marker selection at four call sites — Step 3h "Verify", Step 4's final sync, the
  Rollback green-check, and the `# Per-spec loop (reference)` pseudocode. It runs
  no `manage.py check`. It has **no YAML front matter** (pre-existing; out of
  scope). Its Rollback intro lists failure triggers as "tests won't pass, a
  migration conflicts, an override can't be reconciled".
- **`claude_plugins/fls-dev/commands/update_upgrade_notes.md`** documents
  `requires_settings_change` and `changed_settings` in the schema block, the flag

- **Hard/soft-in-a-comment precedent** (the real D6 evidence, replacing the

## Task 1 — Layer 5: `update_upgrade_notes.md` guidance (D6)

Edit `claude_plugins/fls-dev/commands/update_upgrade_notes.md` to add two trigger
cases:

- **(a) Hard vs optional settings changes.** When a spec introduces a hard config
  requirement, set `requires_settings_change: true` with the specific keys in
  `changed_settings`; when a Layer-4 system check enforces it at boot, say so, so
  `update_fls` can point the downstream at `manage.py check`. Cite
  `freedom_ls_course_access.E001` (`COURSE_ACCESS_BACKEND`) and
  `freedom_ls_content_engine.E001` (`ADMONITION_TYPES`) as *examples*, and write
  the rule generally so a future hard-requirement check follows it automatically.
- **(b) Changed or repurposed check IDs are hard settings changes.** Name
  `SILENCED_SYSTEM_CHECKS` in `changed_settings`. Use the `E001` repurposing as
  the worked example, including why it is the sharp case: the silencing keeps
  working while now silencing the wrong check.

**No new schema flag (D6).** Instead, **the guidance must name the existing
convention**: an inline `#` comment on the `changed_settings` entry — see the two
`3. done/` notes in Ground truth. Say that this needs the block-sequence YAML
form, since the schema block's `changed_settings: []` flow style cannot carry a
comment. Do not cite Part 1's notes as the precedent; that was the spec's old,
weak citation.

### Authoring constraints for this edit

- **Match the file's terse idiom.** Its established style is dense bolded-lead-in
  bullets, not worked examples with before/after blocks. Extend the existing
  `requires_settings_change` flag-semantics bullet and Step 2's settings-detection
  bullet, and add the check-ID case as a **short paragraph** — not a new `##`
  section.
- **Do not add front-matter fields** (`model:`, `argument-hint:`) "for
  consistency". This is a prose-only content edit.
- **Do not duplicate the guidance into
  `docs/product/configuration-and-extension.md`** — `/update_product_docs` routes
  upgrade/migration/breaking-change content to `/update_upgrade_notes` by design.

   docstring**, which is the canonical current form — *not* from the Layer-3
   `upgrade_notes.md`, whose pruning example was pre-rename (corrected in Task 5b,

   > **Corrected after PR #154 review.** This instruction was wrong and produced
