## Layer 5 — tie into `upgrade_notes.md`

`concrete-implementation-helpers` shipped structured per-spec `upgrade_notes.md`.
The authoritative schema is in
`claude_plugins/fls-dev/commands/update_upgrade_notes.md` (richer than that
spec's prose — it includes `changed_settings: []`, npm fields, etc.).

The command must gain guidance covering **two** trigger cases. Write both
**generally**: any future spec that fits the pattern should follow it, so the
current check IDs appear as *examples*, never as the definition.

### (a) Hard vs optional settings changes

Teach the author to distinguish a **hard/required** settings change from an
optional/informational one. When a spec introduces a hard config requirement (as
the pluggable-course-access work did with `COURSE_ACCESS_BACKEND`), its notes set
`requires_settings_change: true` with the specific keys in `changed_settings`.
When the spec **also** adds a Layer-4 system check enforcing that requirement at
boot, say so in the notes, so `update_fls` can point the downstream at
`manage.py check`.

Why this is needed: today the boolean alone conflates "you must act before this
boots" with "here is a knob you may ignore." Several existing `upgrade_notes.md`
files set `requires_settings_change: true` for changes that are purely optional
`.env.example` parity, sitting in the corpus next to notes where an unset key
crash-loops the app.

The current hard-requirement checks, cited as examples:
`freedom_ls_course_access.E001` (`COURSE_ACCESS_BACKEND`) and
`freedom_ls_content_engine.E001` (`ADMONITION_TYPES`), both produced by the
shared `required_settings_errors()` helper in `freedom_ls/base/app_settings.py`.
These are the only two required settings in the tree today, so the pair is
currently exhaustive — another reason to write the rule generally rather than
against the list.

The guidance must also name **how to mark hardness inline**: an `#` comment on
the `changed_settings` entry itself, which is what D6's evidence shows authors
already doing unprompted. Note the mechanical consequence — a comment needs the
block-sequence YAML form; the schema block's `changed_settings: []` flow style
cannot carry one.

### (b) Changed or repurposed check IDs are hard changes

The command's current trigger list never mentions check IDs, yet renaming or
repurposing one silently breaks a downstream's `SILENCED_SYSTEM_CHECKS` entry.
Treat it as a hard settings change and name `SILENCED_SYSTEM_CHECKS` in
`changed_settings`.

**The worked example — and the sharpest one.**
`freedom_ls_course_access.E001` was **repurposed, not re-IDed**. It still exists
and now means "a required setting is unset" (currently `COURSE_ACCESS_BACKEND`);
`.E002` took over its old meaning ("a `Course` has an `access_config` the active
backend rejects"). This is worse than a plain rename: a downstream that silenced
`E001` for access-config noise is now silencing a **different check** than it
intended, the silencing keeps working, and nothing errors to tell it so.

The Layer-4 slice's own notes
(`3. done/2026-08-23_16:23_fls-integration-system-checks/upgrade_notes.md`)
already set `changed_settings: ["SILENCED_SYSTEM_CHECKS"]` by hand. The Layer-5
guidance is what makes that repeatable rather than lucky.

### Decision D6 — no new schema flag

**Conclusion unchanged:** `requires_settings_change: true` + `changed_settings`
is sufficient for the hard-requirement case. No new flag is required.

**Reasoning, corrected.** The only consumer of these fields in the repo is an
agent reading them as prose — `update_fls.md` renders `requires_settings_change`
as "review and apply the listed `changed_settings`" — so a machine-readable
hard/soft flag would buy nothing that a clear `changed_settings` entry does not.

**Evidence, corrected.** The precedent is *not* Part 1's own notes (that file's
single `changed_settings` entry is a pytest-marker registration caveat whose
hardness lives only in prose). Authors have already, independently, encoded
hardness as inline `#` comments inside `changed_settings`:

- `3. done/2026-07-17_09:57_support-concrete-project-deployment-1-prod-settings/upgrade_notes.md`
  — `SECRET_KEY # now mandatory — hard-fails at boot if missing/empty` sitting
  next to `DB_SSLMODE # new env var (default "prefer")`.
- `3. done/2026-07-19_07:52_more-deploy-preparation/upgrade_notes.md` —
  `WEBHOOK_ENCRYPTION_SALT # NEW required secret in production — app fails fast
  on boot if unset` next to four `# .env.example parity` entries.

The guidance's job is to make that ad-hoc convention explicit, not to add a field.

## Layer 6 — make the new conventions stick (Part-2 portion)

Part 1 covered the bulk of Layer 6 (testing/playwright skills, code-reviewer,
`update_fls.md` marker selection). Part 2 adds two verification steps to
`claude_plugins/fls-dev/commands/concrete/update_fls.md`.

### (a) A conformance opt-in precondition, not a new invocation

The originally-specified "invoke the Layer-3 conformance suite as the positive
signal" is redundant as scoped. No probe module under
`freedom_ls/contrib/conformance/` carries `playwright`, `fls_internal`, or
`ci_only`, and no `conftest.py` applies one after the fact, so the existing
`-m "not playwright and not fls_internal and not ci_only"` selection already
collects every probe. A second invocation would duplicate a run that already
happens.

The actual gap is **opt-in**. The suite is an importable module, so a downstream
only gets the signal if it has a `tests/` file importing it — and the
concrete-project template does not ship that file yet.

> **Corrected after PR #154 review.** The original claim here — that without the
> opt-in file "the existing pytest run silently collects zero conformance probes"
> — is false under FLS's documented default. A downstream that falls back to
> recursive collection over the vendored `submodules/Freedom-LS` tree collects
> `freedom_ls/contrib/conformance/test_*.py` directly (see
> `spec_dd/3. done/2026-07-09_09:37_fls-test-portability-part1/upgrade_notes.md:22-29`);
> FLS ships no `collect_ignore` guard against it. The opt-in file is still
> required, but for a different reason: recursive collection is incidental, not a
> contract, and a project that later scopes `testpaths` to its own `tests/` loses
> the conformance signal with no error.

The requirement is therefore:

- Before treating the existing pytest run as the wiring signal, **confirm the
  project has a `tests/` file importing `freedom_ls.contrib.conformance`.** If it
  does not, **write one from the inline snippet, report that it was added, and
  continue** — this is mechanical one-time wiring, not a judgement call, and
  blocking a whole submodule upgrade on a missing opt-in test file is
  disproportionate. The step blocks only if the file cannot be written: then stop
  and report, rather than letting a green pytest run stand in for a wiring signal
  it never produced.
- **Note at the existing pytest step that *this* is where the suite runs**, so a
  green run reads as meaningful rather than merely "tests passed".

### (b) `uv run python manage.py check`

**Not** because Layer-4 failures would otherwise go unseen — they would not.
Neither Django's `migrate` nor its `makemigrations` overrides
`requires_system_checks`, so both inherit `"__all__"` and `BaseCommand.execute()`
runs the full check set before the command body. Step 3b (`migrate --check`),
3e (`migrate`, when flagged) and the post-flight `makemigrations --check`
(unconditional) therefore already run every FLS check, and any `Error` already
aborts the integration there. Adding a second unconditional invocation for the
stated reason would repeat the mistake §6(a) corrects.

The dedicated step earns its place for two other reasons:

- **Attribution.** Today a configuration `Error` blows up the post-flight
  `makemigrations --check` and reads as migration trouble. A named `check` step
  makes it read as what it is: configuration drift the pointer move introduced.
- **Warning visibility.** A Warning piggy-backed onto another command prints into
  that command's output, gets no summary line (`display_num_errors` is set only
  by `check` itself) and never blocks. Layer 4's
  `freedom_ls_learner_interface.W001` is exactly that shape, and it is precisely
  the kind of finding an upgrade should put in front of the operator.

Every FLS check registered today runs on the plain command — none are
`deploy=True`, so no `--deploy` and no `--tag` are needed. Errors exit non-zero
and abort; Warnings print and do not.

### Placement, ordering, and blocking

- `manage.py check` goes **in its own sub-step, immediately before the
  post-flight `makemigrations --check`** (today's `3g`), which means renumbering
  the sub-steps after it. The conformance opt-in precondition goes in the
  **"Verify"** sub-step, ahead of the pytest gate it guards.
- The ordering rationale is attribution, not timing: `check` runs **after** the
  pointer move, `uv sync` and any flagged settings application, so it sees the
  state the upgrade actually produced; and **before** the migration conflict
  gate, so configuration drift is named as configuration drift instead of
  surfacing as a system-check abort inside a migration gate. Both sit well ahead
  of the slower pytest run.
- **Mirror both additions in the `# Per-spec loop (reference)` pseudocode
  block**, in the same order, so the file stays internally consistent — that
  block exists specifically to mirror the steps above it.
- Make both **blocking**, matching the file's existing convention — every
  verification step in it already is (the `migrate --check` and
  `makemigrations --check` gates both use "stop and resolve" language). For the
  conformance precondition, "blocking" means the sequence in (a): write the
  missing file and carry on; stop only if it cannot be written.
- Add **"a system check fails"** to the Rollback section's intro list of failure
  triggers, so that list stays consistent with the new blocking gate.
- **No new prose reaches Step 4's final sync or the Rollback green-check.** They
  are deliberately lightweight recovery gates. Only the Verify gate and the
  pseudocode block gain sentences; the Rollback section's only prose change is the
  intro clause above. The *marker selection* inside all four invocations does
  change — see below — but identically, and with no surrounding text added.

### `template_repo_manifest.md` — recorded, not implemented here

`claude_plugins/fls-dev/resources/template_repo_manifest.md`'s `urls.py`
checklist is out of sync with `config/urls.py`. The known divergences are wider
than earlier revisions of this spec recorded:

- **Missing routes:** `applications/` (`course_applications`), `interest/`
  (`course_interest`), `robots.txt`, `sitemap.xml`, and
  `path("", include("freedom_ls.deployment.urls"))`.
- **Missing ordering constraint:** robots and sitemap must be registered *before*
  the `learner_interface` root-prefix catch-all, and `deployment.urls` likewise
  precedes it. `config/urls.py` carries this as a comment; the manifest states it
  nowhere.
- **Wrong form:** the manifest records the health route as a direct view,
  `path("health/", health_check, name="health_check")`. The real wiring is
  `path("health/", include("freedom_ls.health.urls"))`, and no `health_check`
  name appears in `config/urls.py`.
- **Missing modules:** `config/sitemaps.py` and `config/views.py` are absent from
  the manifest's file tree, so the sitemap/robots routes have no supporting
  entries to point at.

Because the drift is this broad, the fix must **re-derive the whole checklist from
`config/urls.py`** rather than patch the known gaps one by one — the list above is
evidence of scale, not a to-do list. The actual manifest edit is
`/update_template_repo`'s job (SDD step 12), **not this slice** — this spec only
records the requirement so that step lands it. Do not pre-empt it. Note the
Layer-4 slice finished with its own step 12 unticked, so this slice's step 12 is
the only place the fix can now land.

That step must (a) fix the checklist, (b) ship the reference sitemap/robots
wiring so new projects get D1's forced existence, and (c) ship a downstream
`tests/` file importing the conformance suite. The manifest currently has **no
mention at all** of `tests/`, `pytest`, or `conformance` — without (c), Layer 6's
new precondition has to write that file into every freshly generated project
rather than finding it already there.
