# Spec: hide the header Messages button from users with no use for it

Idea: `idea.md`. Research: `research_codebase.md`, `research_best_practices.md`,
`research_reference_implementations.md`, `research_prior_art.md`, `research_ux_patterns.md`,
`research_known_complaints.md`.

## Purpose

The header Messages button shows for every signed-in user whenever `MESSAGING_ENABLED` is on. A
learner on a free course, whose messaging policy gives them nobody to message, still gets a button
that opens an empty panel. The button should appear only for users who can message someone or who
already have a conversation.

## Scope

In:

- A per-user check on the header Messages button (`messages_button` tag), derived from the messaging
  policy and the user's existing conversations.
- Tests and product docs for the new rule.

Out:

- A new setting, model field or toggle. Who may message whom is already configured through the
  messaging policy flags (`SiteMessagingConfig`, `OrganisationMessagingConfig`,
  `CohortMessagingConfig` and the other levels). Closing `learner_to_educator` on an organisation or
  cohort is how an operator hides the button for its learners.
- A "free course" concept on `Course`.
- Access control on the messaging views. They keep their current behaviour (404 only when
  `MESSAGING_ENABLED` is off, participant checks on threads, policy checks on start and send). A
  user without the button who goes to `/messages/` directly gets the page as today.
- The educator surfaces outside the header (`LearnerMessagesPanel`, the quick view message box).

## Decisions

1. **Visibility is derived, not configured.** A second switch next to the policy flags could
   disagree with them; the policy already answers "can this user message anyone".
2. **An existing conversation keeps the button.** Messages raise no notification, so the button and
   its badge are the only way a user learns of a reply. Hiding it would strand conversations whose
   policy has since closed.
3. **One rule for every role.** Educators and colleagues are reached through the policy's role route
   in `recipients_for`, so an educator with learners or colleagues sees the button without a
   special case. An educator or admin with nobody to message and no conversation sees no button.
4. **Hide, never disable.** The button is left out of the HTML, so no badge polls and the header
   reflows.
5. **The rule lives in `comms` and reaches organisation knowledge only through the policy seam.**
   `comms` must not import organisation or role code (`comms/tests/invariants/test_boundaries.py`).

## Requirements

### The rule (`freedom_ls/comms/messaging.py`)

- Add `has_recipients(user: User, site: Site) -> bool`: `get_messaging_policy().recipients_for(
  sender=user, site=site).exists()`. Move the body of `_has_recipients(request)` in
  `freedom_ls/comms/messaging_views.py` into it. `_has_recipients` either becomes a thin request
  wrapper or its call sites call `has_recipients` directly. The query is written once.
- Add `can_see_messages_button(user: User, site: Site) -> bool`: true when the user is a participant
  in any conversation on the site (`ConversationParticipant.objects.filter(user=user).exists()`,
  site-filtered by its manager) or `has_recipients(user, site)`. The conversation check runs first
  and short-circuits, so a user with a conversation never pays for the recipients query.

### The header button (`freedom_ls/comms/templatetags/comms_tags.py`)

- `messages_button` becomes `takes_context=True`, like `notification_bell`. With
  `MESSAGING_ENABLED` off it returns `{"enabled": False}` with no query, as now. With it on, it
  returns `{"enabled": False}` when `can_see_messages_button(request.user,
  get_cached_site(request))` is false.
- The unread count is still not computed on page render; the badge keeps loading itself.
- Update the tag's docstring: the render now runs up to two `EXISTS` queries, never the unread count.
- `freedom_ls/comms/templates/comms/partials/messages_button.html` is unchanged.

### Header coordination (`freedom_ls/comms/static/comms/js/alpine-components.js`)

- The `notificationBell` component's open/close coordination with `messagesPanel` must work when the
  messages button is absent from the page. Change it only if it assumes the sibling exists.

## Testing

In `freedom_ls/comms/tests/test_bell_tag.py`, `TestMessagesButton`:

- Existing "on" tests render with `UserFactory()` and no relationships, so under the new rule they
  see no button. Give each of those users a conversation through `ConversationFactory`, or a
  recipient, so they keep testing what they test now.
- `test_a_page_render_runs_no_conversation_query` forbids any SQL containing `comms_conversation`,
  which matches `comms_conversationparticipant`. Narrow it to what it protects: the render runs no
  unread-count query (no query on the `"comms_conversation"` table itself or on `comms_message`).
  Keep a test that the render runs at most the two `EXISTS` queries the rule needs.

New cases, each asserting the button marker (`aria-labelledby="messages-button-label"`) is present
or absent on `learner_interface:dashboard`:

- `MESSAGING_ENABLED` off: absent, and no messaging query runs.
- No conversation and no recipients (a learner whose policy is closed, and a plain user with no
  `Learner` row): absent.
- A recipient through `learner_to_educator` open on the learner's cohort: present.
- `learner_to_educator` closed on the learner's organisation, nobody else reachable: absent.
- No recipients but one existing conversation: present.
- A conversation on another site only: absent (site isolation).
- An educator who can reach a learner or colleague through the role route: present.

Unit-test `can_see_messages_button` directly for the conversation short-circuit (the recipients
query does not run when a conversation exists).

Playwright: an existing messaging flow test under `freedom_ls/comms/tests/playwright/` keeps passing,
and the notification bell opens and closes on a page with no messages button.

## Documentation and downstream

- `docs/product/messaging.md`: line 8 and line 22 ("for everyone, educators included") and the
  "Turning It On" section get the rule: with messaging on, the button shows only to users who have
  someone they may message or an existing conversation; closing the policy flags for an organisation
  or cohort hides it for those learners.
- Upgrade notes: the header now calls the configured `MESSAGING_POLICY`'s `recipients_for` on page
  renders for users with no conversation. A downstream policy whose `recipients_for` is expensive
  should know.

## Success criteria

- With `MESSAGING_ENABLED` on, a learner with no recipients and no conversation sees no Messages
  button on any page.
- The same learner, once an educator starts a conversation with them, sees the button and its unread
  badge on their next page load.
- Closing `learner_to_educator` on an organisation removes the button for its learners who have no
  conversation and no other route.
- An educator with learners or colleagues they may message sees the button.
- A page render runs no unread-count query and at most two `EXISTS` queries for the button.
- `/messages/` behaves as before for a user without the button.
- `uv run pytest freedom_ls/comms` passes.
