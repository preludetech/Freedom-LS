# Spec: conditional pages and questions

## Purpose

Every sitting of a `Form` sees every `FormPage`, `FormQuestion` and `FormContent`, and a required
question anywhere blocks submission whether or not it applied to that learner. A form author needs to
gate a page, a question or a content block on an answer given earlier, so that, for example, an
applicant whose employer is not paying never sees, or is held up by, the page of employer questions.
The approach is settled in `idea.md`.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| condition | coined | The rule on a `FormPage`, `FormQuestion` or `FormContent` that decides whether it is on a sitting's path. Authored as the `when` key; stored as `condition_option`. Distinct from `registration_rules`' attribute conditions. |
| path | coined | The `FormPage`s, `FormQuestion`s and `FormContent` blocks whose conditions hold for a sitting, in authored order. Never a model field or module name (`BaseContent.file_path` owns the word). |
| on-path / off-path | coined | Whether a page, question or content block is on the sitting's path. |
| `asked` | coined | `FormProgress.asked`: a sitting's path, frozen at completion. |
| not asked | coined | An off-path `FormQuestion` in a sitting, as shown to an admin or in an export. Distinct from "Not answered" (on-path, no answer). |
| `slug` | narrowed | `TitledContent.slug` on `Form`/`FormPage`; on `FormQuestion` it is the author's reference name for the question, unique within its form, never a URL segment. |

## Scope

In:

- A `when` key on page, question and content YAML sections, and an author-chosen `slug` on
  `FormQuestion`, validated at import.
- One server-side evaluator that decides the path from the sitting's stored answers, used by every
  consumer under Requirements.
- Off-path answers kept during a sitting and deleted at `FormProgress.complete()`.
- The path frozen on the `FormProgress` at completion.
- Per-sitting `max_score` for `CATEGORY_VALUE_SUM`.
- File-upload endpoints that 404 for off-path questions; dev-tool and `qa_helpers` commands that
  keep working with conditional forms; the employer case in the demo application form.

Out:

- `QUIZ` forms: a condition on one is an import error.
- Same-page reveal of any kind, client-side rule evaluation, HTMX or Alpine reveal.
- Visible-but-disabled questions.
- Boolean combinators (`all`/`any`), negation, numeric or text comparisons.
- Conditions on anything outside the sitting's own answers.
- `compliance-form-randomization`: this spec designs nothing for it.
- A path changed after submission (the reviewer re-routing case in
  `spec_dd/1. next/multi-step-course-applications/idea.md`).
- An author tool for previewing or enumerating paths.
- `freedom_ls/reports/`: unchanged (it reads `max_score` for `QUIZ` forms only).

## Decisions

- **The source of a condition is a `multiple_choice`, `dropdown` or `checkboxes` question**, so every
  literal can be checked against `QuestionOption.value` at import.
- **The condition is stored as a FK to the `QuestionOption` it tests** (see `idea.md`).
- **An unanswered source, or an off-path source, makes the condition false.**
- **The URL page number stays the authored page index; what the learner reads is the position on the
  path.** "Page 2 of 3" counts on-path pages; `/page/4/` still means the fourth authored page.
- **`question_number()` stays the stable ordinal in the full authored form and is used for identity
  only** (`data-testid`s). Every number a learner reads, the question's visible number and "Question N
  needs an answer", is its position among the sitting's on-path questions.
- **In-progress sittings are evaluated against the current form**, so an author's edit changes their
  path. Completed sittings read their frozen path.
- **The course start screen keeps whole-form counts** (`learner_interface/views.py`, the
  `question_count`/`page_count` context). It describes the form before any answer exists.

## Requirements

### Authoring schema (`freedom_ls/form_engine/schema.py`)

- `FormQuestion` gains `slug: str | None`, matching `^[a-z0-9_]+$`.
- A new `Condition` model, `extra="forbid"`:

  ```yaml
  when:
    question: employer_pays   # a FormQuestion slug in the same form
    equals: "yes"             # multiple_choice / dropdown source
  # or
  when:
    question: dietary_needs
    includes: vegetarian      # checkboxes source
  ```

  Exactly one of `equals` / `includes`. An `int` literal is coerced to `str` (the same normalisation
  `save_form_question` applies to `QuestionOption.value`). A `bool` literal is rejected with a message
  telling the author to quote it, since unquoted `yes`/`no`/`on` parse as booleans.
- `FormPage`, `FormQuestion` and `FormContent` gain `when: Condition | None = None`.

### Import validation (`freedom_ls/content_engine/validate.py`)

A new cross-file pass beside `validate_category_references`, run over each form's parsed pages in the
order `content_save` assigns `FormPage.order` (sorted file paths, so `10. x.yaml` before
`2. y.yaml`). It reports every error in one run, each naming the file, the target and the `when` key,
and rejects:

1. a duplicate `slug` within a form, naming both files;
2. a `when.question` that matches no slug in the form, listing the form's slugs;
3. a source on the same page as the target or a later one (this also rules out cycles);
4. a source whose type is not `multiple_choice`, `dropdown` or `checkboxes`;
5. `equals` on a `checkboxes` source, or `includes` on any other;
6. a literal matching no `QuestionOption.value` on the source, listing the valid values;
7. any `when` in a form whose `strategy` is `QUIZ`.

The same checks go into the offline validator in `claude_plugins/fls-content/validate/`
(`schema.py`, `validate.py`), whose `extra="forbid"` mirror otherwise rejects the new keys.

### Models (`freedom_ls/form_engine/models.py`, migration `0009`+)

- `FormQuestion.slug`: `CharField(blank=True, default="")`. Uniqueness within a form is an import
  check (a constraint cannot span `form_page__form`).
- `FormPage`, `FormQuestion`, `FormContent` each gain
  `condition_option = ForeignKey(QuestionOption, null=True, blank=True, on_delete=RESTRICT)`, with
  `related_name` `gated_pages`, `gated_questions`, `gated_content`. `RESTRICT` blocks deleting an
  option alone but lets a whole form cascade, as `danger_content_delete` and an admin form delete do.
- `FormProgress.asked`: `JSONField(null=True, blank=True)`, written once by `complete()`:

  ```json
  {"pages": ["<FormPage uuid>"], "questions": ["<FormQuestion uuid>"], "content": ["<FormContent uuid>"]}
  ```

  `null` while the sitting is in progress.

### Saving (`freedom_ls/content_engine/management/commands/content_save.py`)

- `save_form_page`, `save_form_content` and `save_form_question` pass `exclude_fields={"when"}`
  (`save_with_uuid` raises on a dumped key that is not a model field) and set `condition_option`
  explicitly: the resolved option, or `None` when the section has no `when`
  (`save_with_uuid` uses `exclude_none=True`, so an absent key would leave the old FK in place).
  `save_form_question` writes `slug`.
- `when` resolves against the objects saved earlier in the same import run: a map of slug to the
  saved `FormQuestion` and of value to the `QuestionOption` `save_with_uuid` returned. The earlier-page
  rule guarantees the source is already in the map. It never looks options up in the database, where
  questions removed from the YAML and options re-created without a uuid leave stale rows. A re-import
  therefore re-points `condition_option` at this run's option.

### The evaluator (new `freedom_ls/form_engine/conditions.py`)

- `compute_path(form: Form, answers: Mapping[UUID, QuestionAnswer]) -> SittingPath`, answers keyed
  by question id, walks pages in order. For each page:
  1. **Page gate:** the page has no `condition_option`, or its source question is on-path and that
     question's `QuestionAnswer.selected_options` contains `condition_option`.
  2. With the gate open, each question and content block on the page is on-path when it passes the
     same test on its own `condition_option`. With the gate shut, none is.
  3. The page is on-path when its gate is open and it has no children or at least one on-path child.
- `sitting_path(form_progress: FormProgress) -> SittingPath` returns the frozen path when `asked` is
  set, every page, question and content block when the sitting is complete with `asked` null (sittings
  completed before this feature, which were asked everything), and `compute_path` otherwise.
- `SittingPath` is a frozen dataclass holding the ordered on-path pages and the on-path question and
  content ids, with what callers need: whether a page or question is on it, a page's on-path
  questions and children, a page's position and the count of on-path pages, a question's position
  among on-path questions, and the next and previous on-path page after a given one.
- `compute_path` loads the form tree (pages, children, `condition_option`) and the answers with
  `selected_options` in a bounded number of queries. A request computes its `SittingPath` once and
  carries it on `CurrentPage`; `build_page_links`, `resume_page_number`, `answered_counts` and
  `page_context` take it rather than recomputing. The admin answers view and the exports load the form
  tree once and call `compute_path` per in-progress sitting.

### Paging and page flow (`freedom_ls/form_engine/paging.py`, `page_flow.py`, `queries.py`)

- `page_flow.submit_page` passes only the page's on-path questions to `unanswered_required_on_page`
  and `FormProgress.save_answers`. A value in the POST for an off-path question is never stored, and
  its existing row is left alone (`save_answers` deletes the row of any question it is handed blank).
- `unanswered_required_in_form` checks on-path questions only, recomputing the path server-side.
- The "Question N needs an answer" message builders use the question's on-path position.
- `CurrentPage`/`page_context`: `next_page_url`, `previous_page_url`, `has_next_page` and `is_last`
  come from the path. Requesting an off-path page number redirects to the next on-path page after it,
  else to the last on-path page.
- `FormProgress.furthest_page_reached` is written as today and is only an input to the resume
  candidate. `resume_page_number` (and `FormProgress.get_current_page_number`, rewritten over the path
  and one set of answered question ids): the candidate it computes today, moved to the first on-path
  page at or after it, else the last on-path page. `page_accessibility_limit` uses the same rule, so
  the resume page and the page-jump ceiling agree.
- `build_page_links` emits on-path pages only, labelled by position on the path; `is_accessible`
  keeps its current meaning for pages ahead of the learner.
- `answered_counts`: `answered_count` counts answers to on-path questions; `total_question_count`
  counts on-path questions.
- `FormPage.children()` callers that render a page show on-path children only, and
  `form_engine/question.html` shows the on-path position as the visible number while
  `data-testid` keeps `question_number()`.

### File-upload endpoints (`freedom_ls/form_engine/views.py`)

`partial_question_file_upload` and `partial_question_file_remove` 404 for an off-path question
(`_owned_file_question` checks the path as well as the form).

### Completion (`FormProgress.complete()`)

Inside one `transaction.atomic()` block: compute the path from the answers, delete `QuestionAnswer`
rows for off-path questions, write `asked`, then score. `form_attempt_completed` is sent directly after
the block exits, not through `on_commit`. The `delete_question_answer_file` receiver
(`form_engine/receivers.py`) removes the stored file through `transaction.on_commit`, so a rolled-back
deletion keeps the file. A `submit_on_exit` sitting completed through `form_submit_and_exit` records
its path the same way: an on-path question it never reached is asked and unanswered.

### Scoring (`FormProgress.score_category_value_sum`)

Walks on-path questions only, so each category's `max_score` is this sitting's. A category or
sub-category with no on-path question is absent from `scores`. The templates that render the tree
(`course_form_complete.html`, `partials/form_progress_scores.html`) already skip absent keys.
`compute_quiz_scores` and the other `QUIZ` paths are untouched.

### Course player (`freedom_ls/learner_interface/`)

- `form_fill_page` advances to the next on-path page. On the last on-path page it runs path-aware
  `unanswered_required_in_form` before `complete()`, and on a failure redirects to the first page
  holding an unanswered on-path required question: a page made applicable behind the learner would
  otherwise be skippable through the page-jump nav.
- `course_form_page.html`: "Page N of M", the progress bar, the sr-only `<h1>`, the `aria-live`
  announcement and the page dots use path position and on-path page count. The answered tally and the
  submit dialog's totals use the path-aware `answered_counts`.

### Application shell (`freedom_ls/course_applications/views.py` and templates)

- `application_form_page` follows the path for next, previous and the off-path redirect, including
  the read-only render of a submitted sitting (which reads the frozen path).
- `application_check_answers` shows on-path pages and questions only. A page with no on-path rows has
  no card. The untitled-page fallback "Page N" uses path position.
- Edit with `?return=check`: after an accepted POST, redirect to the first on-path page after the
  edited one that holds an unanswered on-path required question, carrying `return=check`; when there
  is none, to check-your-answers. Saving on that page applies the same rule, so the learner is walked
  through every newly applicable required question before returning.
- `_resume_url` uses the path-aware resume. A sitting with no on-path pages goes to
  check-your-answers, as a zero-page form does today.
- Submit from check-your-answers runs `unanswered_required_in_form` (path-aware) then `complete()`.

### Admin answers view and exports

- `queries.answer_groups` (admin `_answers.html`) shows an off-path question as a muted "Not asked",
  keeping "Not answered" for an on-path question without an answer. In-progress sittings use the live
  path; completed ones use `sitting_path`. An in-progress off-path answer row shows as "Not asked", not
  as its value.
- `exports.answer_cell` / `answer_columns` (and `course_applications/resources.py` through them) write
  `Not asked` for an off-path question; an on-path unanswered question stays an empty cell.

### Dev tools and QA helpers

`danger_content_delete`, `danger_clear_all_course_progress` and the `qa_helpers` commands that
complete a sitting work with conditional forms, and `qa_helpers` sittings carry `asked`.

### Demo content

`demo_content/functionality_demo_application_form` gains the employer case: a `multiple_choice`
question with a `slug` on page 1 ("Is your employer paying for this course?") and a page of employer
questions gated on it with `when`, including at least one required question.

## Testing

- **Schema:** both or neither of `equals`/`includes` rejected; int literal coerced; bool literal
  rejected with the quote hint.
- **Import validation:** each rejection 1–7 with its message naming file, target and key; several
  errors in one form reported together; `10.` vs `2.` file ordering decides "earlier"; existing demo
  forms import unchanged.
- **Saving:** removing `when` clears `condition_option`; a re-import re-points it at this run's
  option; a `when` block round-trips through `update_file_with_uuid`'s re-dump.
- **Evaluator:** checkbox membership with several selections; a chained condition whose source is
  itself off-path; a gated-open page whose children are all off-path; frozen `asked` wins over current
  answers and over a later condition edit; a complete sitting with `asked` null returns everything;
  query count is bounded (`django_assert_max_num_queries`) for the course-player and application page
  views.
- **Storage and validation:** a crafted POST carrying a value for an off-path question stores nothing
  and leaves the existing row; flipping a source answer and back keeps the earlier answers.
- **Completion:** off-path rows deleted and `asked` written; an off-path file answer's stored object is
  removed on commit and kept on rollback (`django_capture_on_commit_callbacks`); a `submit_on_exit`
  partial sitting records its path.
- **Scoring:** two sittings of one form with different paths score against different denominators,
  and a wholly off-path category is absent.
- **Navigation:** an off-path page URL redirects; resume never lands on an off-path page; the course
  player refuses completion while a page made applicable behind the learner holds an unanswered
  required question; visible question numbers are consecutive on the path while `data-testid`s keep
  `question_number()`.
- **Check-your-answers:** an edit that makes a required question applicable routes through its page
  with `return=check` then back; an edit that removes a page returns straight to review.
- **Admin and export:** "Not asked" vs "Not answered" for completed and in-progress sittings.

Playwright scenarios extend the existing application-form and course-player flows rather than adding
files: answer "no" and never see the employer page, submit with its required question unanswered;
answer "yes", fill the page, go back and answer "no", reach review without the employer card, switch to
"yes" from review and be walked through the employer page with the earlier answers still filled in. In
the course player, "Page N of M" reflects the path. Tests that import `demo_content/` or the QA seeders
carry the markers `fls-dev:testing` assigns.

## Success criteria

- A form directory with no `when` or `slug` imports and behaves exactly as before.
- Each of the seven invalid conditions fails import with a message naming file, target and key.
- On the demo application form, an applicant who answers "no" submits without seeing the employer
  page, and the completed sitting has no `QuestionAnswer` for any employer question.
- No POST, including a crafted one, stores an answer to an off-path question.
- An off-path required question never blocks a page or submission, and an on-path one always blocks
  completion in both the course player and the application shell.
- A completed sitting's `asked` is set, and editing a condition afterwards changes neither its
  check-your-answers page nor its admin view.
- A `CATEGORY_VALUE_SUM` sitting's `max_score` excludes off-path questions.
- A learner on any path sees consecutive question and page numbers.
