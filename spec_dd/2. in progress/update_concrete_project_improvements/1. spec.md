# Spec: update concrete projects from FLS

## Purpose

`/fls-dev:update_fls` (`claude_plugins/fls-dev/commands/concrete/update_fls.md`) runs inside a
concrete project and advances its `submodules/Freedom-LS` pointer one completed spec at a time.
When an integration breaks there, someone writes it up in the concrete project, hands it back to
FLS by hand, works around it in the meantime, and later has to roll the workaround back. See
`idea.md`.

This spec adds the same loop run from the FLS repo. The operator keeps a machine-local list of
concrete project checkouts. One command integrates each completed FLS spec into every listed
project, runs that project's test gate and an adapted QA plan, and treats every new failure as an
FLS problem first. It fixes small ones and lands them on FLS `main` before the next spec. Large
ones become an FLS idea. With the operator's approval it removes workarounds a spec makes obsolete,
and it proposes concrete-project code that looks generally useful for pulling into FLS.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| concrete project | narrowed | `docs/product/deployment.md` ("a **concrete project** — a downstream repository that installs `freedom_ls` as a git submodule"), `update_fls.md` ("the concrete project"). Here, one listed under `## Concrete Projects` in `.claude/fls-dev/config.local.md`. Bare "project" below means a concrete project. |
| cell | coined | one completed FLS spec integrated into one concrete project; the unit of work, commit, result and retry. Not a table cell. |
| last good | narrowed | `update_fls.md` Rollback: the project's most recent `Update FLS: <spec>` commit, or its HEAD when the run started. |
| baseline | coined | the portable contract test set run against a project at its current pointer before any spec moves; its failing node ids are the project's pre-existing failures. Not the detect-secrets or `settings.json` baselines the docs mention. |
| parked | coined | a project whose cell ended `blocked-on-spec`; its remaining specs are skipped and other projects continue. |
| pull-in | coined | concrete-project code proposed for moving into FLS. |

## Scope

In:

- A new command `/fls-dev:update_concrete_projects`, run from the FLS `main` worktree, that
  integrates pending specs into every configured concrete project, breadth-first by spec.
- The per-spec integration procedure moved out of `update_fls.md` into a shared resource both
  commands follow.
- The machine-local project list in `.claude/fls-dev/config.local.md`.
- FLS-side failure handling: a small fix landed on `main` and the cell retried; a large fix written
  as an FLS idea and the project parked.
- Workaround detection and approved removal in the concrete project.
- An adapted copy of the spec's frontend QA plan run against the concrete project through
  `/fls-dev:do_qa`, which gains a project-root mode.
- A pull-in scan per project with per-candidate questions and a declined list.
- An integration report, QA reports and screenshots committed in the concrete project.

Out:

- The concrete project's `spec_dd/for_freedom_ls/` inbox. The command neither reads nor imports it.
- Running `/sdd:start`, `/sdd:spec_from_idea` or any later SDD step on an idea the command writes.
- Opening pull requests in the concrete project by API.
- Changing the `upgrade_notes.md` schema or `/fls-dev:update_upgrade_notes`.
- The `mega-qa` idea 3 QA-plan propagation mechanism (`spec_dd/1. next/mega-qa/`). The adapted
  plan here is a per-run copy, not a stub that resolves into the submodule.

## Decisions

- **Breadth-first by spec.** Spec 1 goes into every project before spec 2 starts, so an FLS bug
  surfaces once, is fixed once, and no project moves past it.
- **The command runs from the FLS `main` worktree.** A concrete project can only check out
  commits on FLS `origin/main`, so every FLS change the run makes reaches `origin/main` before the
  cell that needs it retries. Nothing is committed directly on `main` except ideas and roadmap
  rows, pushed before the next cell starts; small fixes reach it only through
  `land_on_main.sh`.
- **Fix in FLS, never work around in the project.** The only edits the command makes to a
  concrete project are the flagged integration steps in the shared resource, approved workaround
  removals, and the run's artefacts under `spec_dd/fls_integration/`. Any other edit is a stop.
- **Run artefacts live in the concrete project**, because `spec_dd/3. done/` in FLS is immutable.
- **Only new failures block.** A failure already red at baseline is reported, not attributed to the
  spec.
- **`update_fls` stays** for projects without a local FLS checkout.
- **Absolute paths everywhere.** Bash `cwd` resets between calls and `do_qa.md` Rule 3c forbids
  `cd`. Every command against a project is `git -C <project-root> …`,
  `uv run --directory <project-root> …`, `uv sync --directory <project-root>` or
  `npm --prefix <project-root> …`. `uv --directory` changes the working directory, which
  `uv --project` does not, so `manage.py`, `pytest` rootdir and `.env` loading resolve in the
  project.

## Requirements

### 1. Shared integration procedure

Create `claude_plugins/fls-dev/resources/concrete_spec_integration.md`. It takes
`<project-root>` (absolute path, or `.` when run inside the project) and `<spec-commit>`, and
holds, moved from `update_fls.md` except where listed:

- Steps 3a to 3j: notes parsing with the no-notes fallback, `migrate --check`, the pointer move,
  `uv sync`, the flagged steps in the settings-before-migrations order, template-drift flagging,
  `check` and `check --deploy`, `makemigrations --check`, the conformance opt-in file, the
  portable contract test set, and the commit `Update FLS: <spec-name>`. The test set and the
  commit are the resource's last two steps, so a caller can stop before them, run its own gate
  and commit, as Requirement 3 Step 4 does; `update_fls.md` runs them inside the resource.
- The pointer move fetches first: `git -C <project-root>/submodules/Freedom-LS fetch origin main`
  then `checkout <spec-commit>`.
- The final sync and the final run of the portable contract test set (`update_fls.md` Step 4),
  as a section the caller runs once after the last spec.
- The Rollback section, rewritten. Reset to last good with
  `git -C <project-root> reset --hard <last-good-sha>` and
  `git -C <project-root> submodule update --init submodules/Freedom-LS`, then delete the files
  `git -C <project-root> status --porcelain --untracked-files=all` lists, each named on one
  `git -C <project-root> clean -f -- <path> …` call (a clean tree is a precondition, so every
  untracked file is the run's), then `uv sync --directory <project-root>` and
  `npm --prefix <project-root> install`. No `git checkout -- .` and no unscoped `git clean`.
- The collision-safe conformance binding list corrected to every probe
  `freedom_ls/contrib/conformance/__init__.py` exports, including
  `test_admin_registry_survives_installed_apps_override`.
- The commit body names the FLS spec directory and the old and new submodule SHAs.

`update_fls.md` keeps its Step 1 (pending specs), Step 2 (preview) and Step 5 (push). Its Step 3,
Step 4, Rollback and "Per-spec loop (reference)" become one pointer: follow
`${CLAUDE_PLUGIN_ROOT}/resources/concrete_spec_integration.md` with `<project-root>` `.`, the
way `claude_plugins/fls-dev/commands/init.md` reaches its own resources. The new command uses the
same form. The file gains the frontmatter every other command has: `description`, and
`allowed-tools: Bash, Read, Write, Edit, Glob, Grep, Skill, Agent, AskUserQuestion,
mcp__plugin_ds_playwright__*`.

The resource is the only file that spells the portable contract test set. The new command says
"the portable contract test set in `concrete_spec_integration.md`" wherever it runs it.

### 2. Configuration

`.claude/fls-dev/config.local.md` gains:

```markdown
## Concrete Projects

One absolute path per line, each the checked-out worktree of a concrete project.

- /home/me/workspace/first_class/First-Class-LMS.git/main
```

`claude_plugins/fls-dev/templates/config.local.md` gains the same section with no entries and a
comment saying what goes there.

The command reads `.claude/fls-dev/config.md` then `config.local.md` the way
`claude_plugins/sdd/commands/protected/pre_step_rebase.md` Step 1 does, and takes the list from
whichever file holds the section, local winning whole. An empty or absent section is
`status: blocked · needs: Concrete Projects in .claude/fls-dev/config.local.md`, printed with the
snippet above.

### 3. The command

`claude_plugins/fls-dev/commands/update_concrete_projects.md`, frontmatter `description`,
`argument-hint: [project path …]` (restricts the run to the named paths) and `allowed-tools: Bash,
Read, Write, Edit, Glob, Grep, Skill, Agent, AskUserQuestion, mcp__plugin_ds_playwright__*`. It
runs at depth 0 and follows
`claude_plugins/sdd/skills/claude-code-authoring/resources/fanout_recipe.md`. Its scratch files are
`.sdd-work/update_concrete_<unit>.md`, each deleted by name at the end, where `<project>` in a
unit name is the basename of the project path, with a numeric suffix when two projects share
one. Its preamble says that a run is attended: `/sdd:roadmap` confirms once per idea it files,
`/fls-dev:do_qa` has its own prompts, and Requirement 9 lists the commands that prompt by design.

**Step 0, FLS preflight.** `git branch --show-current` prints `main`, `git status --porcelain
--untracked-files=no` is empty, and after `git fetch origin main` local `main` equals
`origin/main`. Otherwise stop with the reason. `pre_step_rebase.md` is not run.

**Step 1, project preflight.** For each listed path, read-only, in the FLS session:

| check | on failure |
| --- | --- |
| the path exists and `git -C <p> rev-parse --show-toplevel` equals it | skip the project, reason `not a git checkout` |
| `.gitmodules` has `submodules/Freedom-LS`, and `git -C <p>/submodules/Freedom-LS remote get-url origin` names the same `owner/repo` as FLS `origin` once scheme, host and `.git` are stripped | skip, `not an FLS concrete project` |
| `git -C <p> status --porcelain` is empty and no `MERGE_HEAD` or `rebase-merge` exists | skip, `dirty tree`, and print the rollback recipe from the shared resource |
| `git merge-base --is-ancestor <submodule-sha> origin/main` in the FLS repo | skip, `pointer not on origin/main` |
| the path is listed under `permissions.additionalDirectories` in `.claude/settings.local.json` | warn, and print the JSON to add; a directory added another way still works |
| `uv run --directory <p> python manage.py migrate --check` passes | skip, `dirty migration state` |

Record per project: branch, HEAD SHA (the first last good), submodule SHA, and default branch from
`git -C <p> symbolic-ref refs/remotes/origin/HEAD`; when that ref is unset the default branch is
unknown and Step 5 refuses to push a branch named `main` or `master`. Then run the baseline, the
portable contract test set at the current pointer, and record its failing node ids. Every run does
this. A red baseline does not skip the project.

**Step 2, pending specs.** In the FLS repo:

```
git log --no-renames --diff-filter=A --name-only --format=%H --reverse <submodule-sha>..origin/main -- 'spec_dd/3. done/*/1. spec.md'
```

The output is a commit hash, a blank line, then the added paths, repeated per commit. A spec is a
path exactly one directory below `3. done/`; a deeper path (an effort's child) and `spec-order.md`
are ignored. The first commit that adds a directory's `1. spec.md` is that spec's commit; later
commits under the same directory are ignored. A project's pending
list is every such spec in that order, minus any spec whose name appears in the subject of one of
the project's `Update FLS:` commits. The union across projects, in commit order, is the run's
spec list.

**Step 3, preview and confirm.** Print one block per project (path, branch, submodule SHA, baseline
result, pending count), the skipped projects with their reasons, and one matrix row per spec:
name, completion date, the six `upgrade_notes.md` flags or `no notes`, and per project whether it
overrides any path in `changed_template_paths`. Nothing is written. One `AskUserQuestion` batch,
recommended option first: confirm the plan (yes); push policy (push each project's branch at the
end, as `update_fls.md` Step 5; the operator may override to leave it unpushed); for each project
with a QA cell pending, whether its dev database may be seeded (yes; no makes that project's QA
`skipped`). No per-spec confirmation.

**Step 4, the loop.** For each spec in order, for each project not parked, one cell:

1. Follow the shared resource with `<project-root>` and `<spec-commit>`, stopping before its
   portable contract test set.
2. Workaround detection (Requirement 5); approved removals are applied before the gate.
3. Run the portable contract test set. Only node ids outside the project's pre-existing set are
   failures. Re-run a new failure once on its own before counting it, to drop flakes.
4. QA (Requirement 6) when `spec_dd/3. done/<spec>/` holds a `3*. frontend_qa.md`.
5. Commit, per the shared resource, with the workaround removals and the cell's artefacts.
6. Write `.sdd-work/update_concrete_<project>_<spec>.md` with a `result:` line of `integrated`,
   `blocked-on-fix`, `blocked-on-spec` or `skipped` (the command's own cell results, distinct from
   a worker's `status:` footer).

A cell that fails goes to Requirement 4 before the next project starts the same spec. Once a
small fix has landed, every remaining cell for that spec uses the fix commit as `<spec-commit>`,
with the folding rule of Requirement 4 applied per project.

After the third QA walk of a run, the command finishes the current spec across the projects, then
runs Step 5 for every project and stops with the resume instruction.

**Step 5, after the last spec, per project.** Pull-in scan (Requirement 7), whether or not the
project had pending specs. Then the shared resource's final-sync section, the integration report
(Requirement 8) committed as `Update FLS: integration report <run-date>`, and the push under the
policy from Step 3, with `update_fls.md` Step 5's rule that the project's default branch is never
pushed.

**Resume.** Re-running recomputes pending specs from each project's submodule SHA and its
`Update FLS:` commits. A parked project resumes when the spec it was blocked on is in `3. done/`.

### 4. Failure handling

A cell fails when a shared-resource step errors, the gate has a new failure, or QA files a bug.
The command rolls the project back to last good per the shared resource, then classifies from the
evidence (step, command, last 30 lines of output, failing node ids, `git -C <p> diff --stat` of
the integration before the rollback):

| class | action |
| --- | --- |
| FLS code bug, or an FLS test that assumes FLS's own settings, theme, icon set or demo content | FLS fix |
| `upgrade_notes.md` of the spec missed a step the project needed | FLS fix: correct `spec_dd/3. done/<spec>/upgrade_notes.md`, plus code if any |
| the project's own override, subclass or template shadow is stale against the spec | report it; the cell is `blocked-on-fix`, not retried |
| pre-existing baseline failure | not a failure |
| environment (missing `node_modules`, DB not reachable) | fix the environment once and retry |

**Small fix.** All of: no model or migration change, no new setting, at most three FLS files plus
one test file, and one regression test covers it. Borderline goes to the operator in one question,
recommended option first. Procedure, in the FLS `main` worktree:

1. `git switch -c fix/<slug>`.
2. Write the regression test and the fix. Run the targeted tier per
   `claude_plugins/django-stack/resources/test_tiers.md`.
3. `uv run git commit`, subject `fix: <what> (found integrating <spec> into <project>)`.
4. `claude_plugins/sdd/scripts/land_on_main.sh land`. Exit 7 means `origin/main` moved: `git rebase
   origin/main` and run it once more. Any other non-zero exit stops the run with the script's
   message, the name of the `fix/` branch the worktree is left on, and `git switch main` as the
   way back; Step 0 guards the rerun. On success, `git switch main`; the script has already
   fast-forwarded it.
5. Retry the cell with `<spec-commit>` set to the fix commit. Completed specs between the spec's
   commit and the fix commit fold into the retry: their notes flags merge and the commit subject
   lists every spec name.

One fix attempt per cell. A second failure of the same cell is `blocked-on-fix`.

**Large fix.** Write `spec_dd/1. next/<slug>/idea.md` per
`claude_plugins/sdd/resources/idea_standard.md`: the failure, the project and spec it surfaced in,
the failing test or step, and the expected fix. Commit it on `main` with `uv run git commit`,
subject `idea: <slug> (found integrating <spec> into <project>)`, then `Skill(sdd:roadmap)` with no
argument, which commits the roadmap row, then `git push origin main`. A rejected push stops the run.
The cell is `blocked-on-spec <slug>` and the project is parked.

### 5. Workaround removal

Before the gate in each cell, a `sdd:sdd-worker` reads the project's `apps/`, `config/`,
`templates/`, `tests/`, `conftest.py` files and `pyproject.toml`, never `submodules/` and never
`.env*`, and lists workarounds that name FLS: comments containing `workaround` or `remove once`
near `FLS` or `upstream`; `--deselect` and `--ignore` entries inside the `addopts` string of
`pyproject.toml` naming paths under `submodules/Freedom-LS`; template shadows and `conftest.py`
fixtures whose comment cites an FLS defect. After removing an `addopts` entry the command re-runs
that project's baseline.
A workaround matches the cell's spec when its comment names the spec, or names a symbol,
test id, template path or setting that the spec's FLS diff (`<previous-spec-commit>..<spec-commit>`)
or its `upgrade_notes.md` touches. The worker has no Bash, so before it runs the command writes
`.sdd-work/update_concrete_specdiff_<spec>.md` once per spec: the diff stat and changed paths of
that range and the notes body. Output `.sdd-work/update_concrete_workarounds_<project>_<spec>.md`,
one line per match: path:line, what it works around, the evidence line, and the removal.

The command asks per match, batches of at most four, options `remove` (recommended) and `keep`.
It applies the approved removals, runs the gate, and reverts any removal that causes a new failure,
reporting it as still needed. Unmatched workarounds and declined matches are listed in the report.
`TODO` and `@claude` comments are never removed except with the code they annotate in an approved
removal.

### 6. QA in the concrete project

When `spec_dd/3. done/<spec>/` holds a `3*. frontend_qa.md`, a `sdd:sdd-worker` writes the adapted
plan to `.sdd-work/update_concrete_qa_<project>_<spec>/frontend_qa.md`. Inputs: the FLS plan; the
project's `INSTALLED_APPS` and template directories, which the command writes to
`.sdd-work/update_concrete_settings_<project>.md` from
`uv run --directory <p> python manage.py shell -c` printing only those two settings (never
`diffsettings`, which prints secrets); the project's `.claude/fls-dev/config.md`; and the spec's
`changed_template_paths`. Each step keeps its id and gains one marker: `run`, `adapted` (with the
changed selector, URL or copy and why), or `N/A` (the project overrides the view or template, or
the app is not installed). The `§0` seed list is rewritten against what the project has: FLS
`qa_*` and demo commands only when `freedom_ls.qa_helpers` is in its `INSTALLED_APPS`, otherwise
the project's own seed commands, and a `blocked` footer when neither exists, which makes the
cell's QA `skipped` with that reason. The seed list is additive only; a step that deletes or
resets data is marked `N/A`.

`/fls-dev:do_qa` gains optional inputs `project-root: <abs path>` and `diff-range: <a>..<b>`.
With `project-root:`:

- Step 0 is skipped.
- Step 2 classifies `git diff --name-only <diff-range>` run in the FLS repo instead of
  `git diff main...HEAD`.
- Step 3 starts `uv run --directory <project-root> python manage.py runserver <PORT>`.
- Step 4 accepts a badge naming the project's branch, or no badge at all; a badge naming another
  branch is still a port collision.
- Step 5 reads credentials and `Base URL` from `<project-root>/.claude/fls-dev/config.md`; absent,
  QA ends `blocked` with that need.
- Rule 2 rungs 2 and 3 and `fls-dev:qa-data-helper` are off: the project's dev database is not
  known to be disposable and the factories are FLS's. Data that blocks a test makes it PARTIAL.
- Step 13 is off: `qa-bugfixer` is never spawned, and bugs go in the report for the caller.
- Steps 15 and 17 are skipped.
- `<spec-dir>` is the adapted plan's directory under `.sdd-work/`, inside the FLS root, so Steps
  1, 10 and 16 and their scripts work unchanged.

Step 11's `compress_screenshots.sh` and `compress_screenshots.py` gain an optional positional
directory to scan after the existing flags, `compress_screenshots.sh [--max-kb N] [--quality N]
[DIR]`, default `spec_dd/`, which project-root mode passes as `<spec-dir>`.

The command invokes it as `Skill(fls-dev:do_qa)` with the plan path, `project-root:` and
`diff-range:`. Afterwards a `sdd:sdd-mechanic` copies `frontend_qa.md`, `qa_report.md` and
`screenshots/` from the scratch directory to
`<project-root>/spec_dd/fls_integration/<run-date>/<spec-name>/`, then deletes the scratch files
by name through `.claude/fls-dev/scripts/delete_sdd_work_files.sh`. A QA bug is a cell failure
(Requirement 4); the rollback deletes the failed cell's copied artefacts, so its report row cites
the stop card instead of a `qa_report.md` link.

### 7. Pull-in scan

Once per project per run, one `sdd:sdd-worker` reads the project's `apps/`, `templates/`,
`config/` and `pyproject.toml`, never `submodules/`, `spec_dd/for_freedom_ls/` or `.env*`, and the
project's `spec_dd/fls_integration/declined_pull_ins.md` if it exists. It writes
`.sdd-work/update_concrete_pullin_<project>.md` with at most ten candidates, each a card: what it
does in one sentence; project paths; the FLS app it would join or the gap it fills; why it is
general (no project name, brand, URL or data; another concrete project would use it; it fits an existing
extension point or `docs/app_structure.md` boundary; testable without the project); size S, M or
L; whether the project would delete its copy afterwards. Anything on the declined list is left out.

The command asks per candidate, batches of at most four, options in this order: write an FLS
idea; keep it in the project; ask again next run. "Write an FLS idea" produces
`spec_dd/1. next/<slug>/idea.md` naming the project path and files as the reference
implementation, committed and pushed the way Requirement 4's large fix is. "Keep it in the
project" appends a line (path, one-line what, date) to
`<project-root>/spec_dd/fls_integration/declined_pull_ins.md`, committed with the report. Nothing
is ever copied into FLS by the command.

### 8. Integration report

`<project-root>/spec_dd/fls_integration/<run-date>/integration_report.md`, `<run-date>` as
`yyyy-mm-dd_HH:MM`, sections in this order:

1. Verdict line: integrated N of M, parked on `<slug>` or none, FLS fixes landed, ideas written,
   pushed yes or no, and the resume instruction when not complete.
2. Needs attention: `blocked-on-fix` cells with their evidence, and stale overrides flagged by
   template drift.
3. Per-cell results: spec, FLS commit, flags, result, project commit, new failures, QA result
   with a relative link to its `qa_report.md` for an integrated cell.
4. Baseline: pre-existing failing node ids, and which of them passed after the run.
5. FLS changes made: fix commits with the spec and test that motivated them; ideas written with
   their paths.
6. Workarounds: removed, declined, still needed, unmatched.
7. Pull-in candidates: idea written, declined, deferred.
8. Assumed defaults: the push policy when the operator did not answer, and every borderline size
   call the command decided alone.

On a failure the transcript shows the stop card: project, spec, step, failing ids, diff stat,
class, proposed action.

### 9. Permissions

The command's preamble documents, and Step 1 checks, that each project path is listed under
`permissions.additionalDirectories` in `.claude/settings.local.json` (gitignored). Writes into a
project prompt unless the session runs in `acceptEdits` mode.

`.claude/settings.json` `allow` gains the forms the shared resource and the command use, verbs
listed rather than `git -C *` so that `reset --hard`, `clean`, `migrate`, `makemigrations`,
`npm install`, seed commands and `push` keep prompting:
`Bash(git -C * status*)`, `Bash(git -C * rev-parse *)`, `Bash(git -C * log*)`,
`Bash(git -C * diff*)`, `Bash(git -C * fetch origin main)` (pinned, since `git fetch` accepts
`--upload-pack=<cmd>`), `Bash(git -C * submodule update*)`,
`Bash(git -C * submodule status*)`, `Bash(git -C * add *)`, `Bash(git -C * symbolic-ref *)`,
`Bash(git -C * remote get-url *)`, `Bash(uv run --directory * pytest*)`,
`Bash(uv run --directory * python manage.py check*)`,
`Bash(uv run --directory * python manage.py makemigrations --check*)`,
`Bash(uv run --directory * python manage.py migrate --check*)`,
`Bash(uv run --directory * python manage.py runserver*)`,
the one `shell -c` settings dump Requirement 6 runs, allowed as its exact string rather than
`shell -c *` so no other Python is prompt-free,
`Bash(uv run --directory * git commit *)`, `Bash(uv sync --directory *)`,
`Bash(npm --prefix * run tailwind_build*)`, `Bash(git switch *)`. `deny` gains
`Bash(git -C * push --force*)`, `Bash(git -C * commit --no-verify*)` and
`Bash(uv run --directory * git commit --no-verify*)`. The submodule checkout (`git -C
<p>/submodules/Freedom-LS checkout <sha>`) prompts. A `*` before the verb also matches text after
it, so these entries over-match (`git -C p diff --output=<file>` passes); the deny entries cover
the two forms that matter most, and the rest is accepted. The concrete project's commit runs
through its own `uv run`.

## Testing

- `tests/test_test_tiers.py`: the detector becomes a regex matching `uv run`, any options, then
  `pytest` inside one inline-code span or on one fenced line, so `uv run --directory <p> pytest`
  counts and prose that mentions both words does not. `ALLOWED` lists
  `concrete_spec_integration.md` and not `update_fls.md`, and the comment above it changes to
  match.
- A structure test beside the existing plugin tests in `tests/`: `update_fls.md` and
  `update_concrete_projects.md` both name `resources/concrete_spec_integration.md`; the resource
  exists; its conformance binding list equals `freedom_ls.contrib.conformance.__all__` minus
  `drop`.
- A grep test over `do_qa.md`: the project-root bullets name no `cd`, and every `manage.py` and
  `pytest` form in them carries `--directory`.
- `compress_screenshots.py` with a directory argument compresses only under that directory.

  row, both on `origin/main`, the project parked at last good, and the other projects finished.

  operator approves it, and the gate stays green.
- A spec with a frontend QA plan has an adapted copy, `qa_report.md` and `screenshots/` under the
  project's `spec_dd/fls_integration/<run-date>/<spec>/`, every step marked `run`, `adapted` or
  `N/A`.

  pull-in line, to each project.

  shared resource.
