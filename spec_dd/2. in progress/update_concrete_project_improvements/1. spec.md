# Spec: update concrete projects from FLS

## Purpose

`/fls-dev:update_fls` (`claude_plugins/fls-dev/commands/concrete/update_fls.md`) runs inside a
concrete project and advances its `submodules/Freedom-LS` pointer one completed spec at a time.
When an integration breaks, the fix has to be written up in the concrete project, handed back to
FLS by hand, and worked around downstream in the meantime. First-Class carries 29 such hand-back
ideas and at least nine live workarounds marked "remove once FLS fixes it"; none of the hand-backs
has an FLS spec.

This spec adds the same loop run from the FLS repo. The operator keeps a machine-local list of
concrete project checkouts. One command integrates each completed FLS spec into every listed
project, runs that project's test gate and an adapted QA plan, and treats every new failure as an
FLS problem first: small ones are fixed and landed on FLS `main` before the next spec; large ones
become an FLS idea. Workarounds a spec makes obsolete are removed with the operator's approval, and
downstream code that looks generally useful is proposed for pulling into FLS.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| concrete project | narrowed | `claude_plugins/fls-dev/commands/concrete/README.md`: a Django project that vendors FLS as the git submodule `submodules/Freedom-LS`. Here, one listed under `## Concrete Projects` in `.claude/fls-dev/config.local.md`. |
| cell | coined | one completed FLS spec integrated into one concrete project; the unit of work, commit, result and retry. No existing term, because `update_fls` only ever has one project. |
| last good | narrowed | `update_fls.md` Rollback: the concrete project's most recent `Update FLS: <spec>` commit, or its HEAD when the run started. |

## Scope

In:

- A new command `/fls-dev:update_concrete_projects`, run from an FLS worktree on `main`, that
  integrates pending specs into every configured concrete project, breadth-first by spec.
- The per-spec integration procedure moved out of `update_fls.md` into a shared resource both
  commands follow, so the two cannot drift.
- The machine-local project list in `.claude/fls-dev/config.local.md`.
- FLS-side failure handling: small fix now on a short-lived branch landed on `main`; large fix as a
  new FLS idea; the cell retried after a small fix, parked after a large one.
- Workaround detection and approved removal in the concrete project.
- An adapted copy of the spec's frontend QA plan run against the concrete project through
  `/fls-dev:do_qa`, which gains a project-root input.
- A pull-in scan per project, proposals asked per candidate, approved ones written as FLS ideas,
  declined ones recorded so they are not asked again.
- An integration report, QA report and screenshots committed in the concrete project.

Out:

- The concrete project's `spec_dd/for_freedom_ls/` inbox. The command neither reads nor imports it.
- Running `/sdd:start`, `/sdd:spec_from_idea` or any later SDD step on an idea the command writes.
- Opening pull requests in the concrete project by API. The push rule stays as `update_fls.md`
  Step 5 has it.
- Changing the `upgrade_notes.md` schema or `/fls-dev:update_upgrade_notes`.
- The `mega-qa` idea 3 QA-plan propagation mechanism (`spec_dd/1. next/mega-qa/`). The adapted
  plan here is a per-run copy, not a stub that resolves into the submodule.

## Decisions

- **Breadth-first by spec.** Spec 1 goes into every project before spec 2 starts, so an FLS bug
  surfaces once, is fixed once, and no project moves past it.
- **The command runs from the FLS `main` worktree.** Fixes must reach FLS `origin/main` before a
  concrete project can check them out. A small fix is committed on a `fix/<slug>` branch created in
  that worktree, landed by fast-forward with `claude_plugins/sdd/scripts/land_on_main.sh land`,
  then the worktree switches back to `main`. Nothing is committed directly on `main` except the
  bookkeeping `/sdd:roadmap` already does there.
- **Fix in FLS, never work around in the project.** The only edits the command makes to a
  concrete project are the flagged integration steps, approved workaround removals, and the run's
  artefacts under `spec_dd/fls_integration/`. Any other edit is a stop.
- **Project list is machine-local.** `.claude/fls-dev/config.local.md` is gitignored and already
  the home for machine-specific values. Absolute paths never go into a committed file.
- **Run artefacts live in the concrete project.** `3. done/` in FLS is immutable and this spec's
  own directory gets archived. The report sits beside the commits it describes.
- **Only new failures block.** Each project's test gate runs once at its current pointer before any
  spec moves. A failure that was already red at baseline is reported, not attributed to the spec.
- **Keep `update_fls`.** A concrete project without a local FLS checkout still needs it. It keeps
  its name, path and the `tests/test_test_tiers.py` allow-list role moves with the pytest string.
- **Commit per spec in the project, push once at the end.** As today. The branch rule from
  `update_fls.md` Step 5 applies unchanged: never push the project's default branch.
- **`git -C`, `uv run --project`, `npm --prefix`.** Bash `cwd` resets between calls and `do_qa`
  Rule 3c forbids `cd`. Every command against a project takes its absolute path.

## Requirements

### 1. Shared integration procedure

Create `claude_plugins/fls-dev/resources/concrete_spec_integration.md`. It takes
`<project-root>` (absolute path, or `.` when run inside the project) and `<spec-commit>` and holds,
moved verbatim from `update_fls.md` except where listed:

- Steps 3a to 3j (notes parsing with the no-notes fallback, `migrate --check`, pointer move,
  `uv sync`, flagged steps in the settings-before-migrations order, template-drift flagging,
  `check` and `check --deploy`, `makemigrations --check`, the conformance opt-in file, the portable
  pytest gate, commit `Update FLS: <spec-name>`).
- The Rollback section, rewritten: reset to last good with
  `git -C <project-root> reset --hard <last-good-sha>` and `git -C <project-root> submodule update
  --init submodules/Freedom-LS`, then delete by name any untracked file the run created (the
  conformance file, generated migrations, `spec_dd/fls_integration/<run>/` leaf for the cell), then
  `uv sync` and `npm --prefix <project-root> install`. No `git checkout -- .` and no `git clean
  -fd`: a clean tree is a precondition, so the recorded SHA is the whole rollback.
- The collision-safe conformance binding list corrected to every probe
  `freedom_ls/contrib/conformance/__init__.py` exports, including
  `test_admin_registry_survives_installed_apps_override`. The current six-name list is stale and
  a silent false green.
- Every command written with `<project-root>`: `git -C <project-root> …`,
  `uv run --project <project-root> python manage.py …`, `uv sync --project <project-root>`,
  `npm --prefix <project-root> …`. When `<project-root>` is `.` the forms still work.
- The commit body names the FLS spec directory and the old and new submodule SHAs.

`update_fls.md` Step 3 and its Rollback section become a pointer: "Follow
`${CLAUDE_PLUGIN_ROOT}/resources/concrete_spec_integration.md` with `<project-root>` `.`". Its
Step 2 preview, Step 4 final sync and Step 5 push stay. Give the file the frontmatter every other
command has (`description`, `allowed-tools`).

`tests/test_test_tiers.py` `ALLOWED`: replace the `update_fls.md` entry with the resource path, and
update the comment above it. The new command never spells `uv run pytest`; it says "the portable
gate in `concrete_spec_integration.md`".

### 2. Configuration

`.claude/fls-dev/config.local.md` gains:

```markdown
## Concrete Projects

One absolute path per line, each the checked-out worktree of a concrete project.

- /home/me/workspace/first_class/First-Class-LMS.git/main
```

`claude_plugins/fls-dev/templates/config.local.md` gains the same section with no entries and a
comment saying what goes there. `/fls-dev:init` already copies that template, so no code change.
The command reads `config.md` then `config.local.md` the way `pre_step_rebase.md` Step 1 does;
the list is taken from whichever file holds the section, local winning whole, never merged.

An empty or absent section is `status: blocked · needs: Concrete Projects in
.claude/fls-dev/config.local.md`, printed with the snippet above.

### 3. The command

`claude_plugins/fls-dev/commands/update_concrete_projects.md`, frontmatter `description`,
`argument-hint: [project path …]` (restricts the run to the named paths), `allowed-tools: Bash,
Read, Write, Edit, Glob, Grep, Skill, Agent, AskUserQuestion, mcp__plugin_ds_playwright__*`. It
runs at depth 0 and follows the fan-out recipe in
`claude_plugins/sdd/skills/claude-code-authoring/resources/fanout_recipe.md`. Scratch files are
`.sdd-work/update_concrete_<unit>.md`; each one is deleted by name at the end.

**Step 0, FLS preflight.** `git branch --show-current` must print `main`, the tree must be clean,
and `git fetch origin main` then `git merge-base --is-ancestor origin/main HEAD` must succeed.
Otherwise stop with the reason. `pre_step_rebase.md` is not run: it is a no-op on `main`.

**Step 1, project preflight.** For each listed path, read-only, in the FLS session:

| check | on failure |
| --- | --- |
| path exists and `git -C <p> rev-parse --show-toplevel` equals it | skip project, reason `not a git checkout` |
| `.gitmodules` has `submodules/Freedom-LS` and `git -C <p>/submodules/Freedom-LS remote get-url origin` names the same repository as FLS `origin` | skip, `not an FLS concrete project` |
| `git -C <p> status --porcelain` empty, no `MERGE_HEAD` or `rebase-merge` | skip, `dirty tree`, print the rollback recipe from the shared resource |
| the path is covered by `permissions.additionalDirectories` in `.claude/settings.local.json` | skip, `not an additional directory`, print the JSON to add |
| `uv run --project <p> python manage.py migrate --check` | skip, `dirty migration state` |

Record per project: branch, HEAD SHA (the first last good), submodule SHA, default branch
(`git -C <p> symbolic-ref refs/remotes/origin/HEAD`). Then the baseline: run the portable gate from
the shared resource at the current pointer and record the failing node ids. A red baseline does
not skip the project; those ids are "pre-existing" for the run.

**Step 2, pending specs.** In the FLS repo, list the commits on `origin/main` that added a
directory under `spec_dd/3. done/` (`git log --diff-filter=A --name-only --format=%H origin/main
-- 'spec_dd/3. done/'`), chronological. A project's pending list is every such commit after its
submodule SHA. The union across projects, in order, is the run's spec list.

**Step 3, preview and confirm.** Print one block per project (path, branch, submodule SHA, baseline
result, pending count) and one matrix row per spec: name, completion date, the six
`upgrade_notes.md` flags or `no notes`, and per project whether it overrides any path in
`changed_template_paths`. Skipped projects are listed with their reason. Nothing is written. One
`AskUserQuestion` batch: confirm the plan (default yes), and the push policy (default: push each
project's branch at the end, as `update_fls.md` Step 5). No per-spec confirmation.

**Step 4, the loop.** For each spec in order, for each project not parked, one cell:

1. Follow the shared resource with `<project-root>` and `<spec-commit>`, stopping before the
   commit.
2. Workaround detection (Requirement 5). Approved removals are applied before the gate runs.
3. Run the gate. Compare its failing node ids with the project's pre-existing set; only new ids are
   failures. Re-run a new failure once on its own before counting it, to drop flakes.
4. QA (Requirement 6) when the spec directory holds a `3*. frontend_qa.md`.
5. Commit, per the shared resource, with workaround removals and the cell's artefacts included.
6. Record the cell result in `.sdd-work/update_concrete_<project>_<spec>.md` with a `status:`
   footer: `integrated`, `blocked-on-fix`, `blocked-on-spec`, `skipped`.

A cell that fails goes to Requirement 4 before the next project starts the same spec. A project
whose cell ends `blocked-on-spec` is parked: its remaining specs are skipped with that reason,
other projects continue.

**Step 5, after the last spec, per project.** Pull-in scan (Requirement 7). Then
`update_fls.md` Step 4 final sync and Step 5 push, with `<project-root>`, under the policy
confirmed in Step 3. The integration report (Requirement 8) is written before the push and
committed as `Update FLS: integration report <run-date>`.

**Step 6, FLS bookkeeping.** If local `main` is ahead of `origin/main` (ideas and roadmap commits
from Requirement 4 or 7), `git push origin main`. A rejected push is reported, not retried.

**Resume.** There is no state file. Re-running recomputes pending specs from each project's
submodule SHA and its `Update FLS:` commits, so a finished cell is never redone. A parked project
resumes when the spec it was blocked on is in `3. done/`, which the same computation finds.

### 4. Failure handling

A cell fails when a shared-resource step errors, the gate has a new failure, or QA files a bug.
Before anything else the command rolls the project back to last good per the shared resource, then
classifies from the evidence (step, command, last 30 lines, failing node ids, `git diff --stat`
of the integration):

| class | action |
| --- | --- |
| FLS code bug, or an FLS test that assumes FLS's own settings, theme, icon set or demo content | FLS fix |
| `upgrade_notes.md` of the spec missed a step the project needed | FLS fix: correct the notes in `spec_dd/3. done/<spec>/upgrade_notes.md`, plus code if any |
| the project's own override, subclass or template shadow is stale against the spec | flag for the operator in the report; the cell is `blocked-on-fix`, not retried |
| pre-existing baseline failure | not a failure |
| environment (missing `node_modules`, DB not reachable) | fix the environment once and retry; a second hit is `blocked-on-fix` |

**Small fix.** All of: no model or migration change, no new setting, at most three FLS files
plus one test file, and one regression test covers it. Borderline goes to the operator in one
question, recommended option first. Procedure, in the FLS worktree:

1. `git switch -c fix/<slug>` from `main`.
2. Write the failing test first, then the fix. Run the targeted tier per
   `claude_plugins/django-stack/resources/test_tiers.md`.
3. Commit with `uv run git commit`, subject `fix: <what> (found integrating <spec> into
   <project>)`.
4. `claude_plugins/sdd/scripts/land_on_main.sh land`; then `git switch main`. A non-zero exit
   stops the run with the script's message.
5. Retry the cell with `<spec-commit>` set to the fix commit. If other `3. done/` commits lie
   between the spec's commit and the fix commit, the retry cell covers them too: their notes flags
   are merged and the commit subject lists every spec name.

One fix attempt per cell. A second failure of the same cell is `blocked-on-fix` and the operator
decides.

**Large fix.** Write `spec_dd/1. next/<slug>/idea.md` per
`claude_plugins/sdd/resources/idea_standard.md`: the failure, the project and spec it surfaced in,
the failing test or step, and the expected fix. Run `/sdd:roadmap` (sync) so the row exists. The
cell is `blocked-on-spec <slug>` and the project is parked.

### 5. Workaround removal

Before the gate in each cell, a `sdd:sdd-worker` reads the project (never `submodules/`) and lists
workarounds that name FLS: comments containing `workaround` or `remove once` near `FLS` or
`upstream`; `--deselect` and `--ignore` entries in `pyproject.toml` that name paths under
`submodules/Freedom-LS`; template shadows and `conftest.py` fixtures whose comment cites an FLS
defect. A workaround matches the cell's spec when its comment names the spec, or names a symbol,
test id, template path or setting that the spec's diff (`<previous-spec-commit>..<spec-commit>`
in FLS) or its `upgrade_notes.md` touches. Output `.sdd-work/update_concrete_workarounds_<project>_<spec>.md`,
one line per match: path:line, what it works around, the evidence line, and the removal (delete
the fixture, the shadow, the pyproject entry, or the subclass with its setting).

The command asks per match in batches of at most four, recommended answer "remove". Approved
removals are applied, the gate runs, and a new failure caused by a removal reverts that removal and
reports it as "still needed". Unmatched workarounds and declined matches are listed in the report
under workarounds. `TODO` and `@claude` comments are never removed except as part of an approved
removal of the code they annotate.

### 6. QA in the concrete project

When `spec_dd/3. done/<spec>/` holds a `3*. frontend_qa.md`, a `sdd:sdd-worker` writes the
adapted plan to `<project-root>/spec_dd/fls_integration/<run-date>/<spec-name>/frontend_qa.md`.
Inputs: the FLS plan, the project's template directories and `INSTALLED_APPS` (from
`uv run --project <p> python manage.py diffsettings`), its `.claude/fls-dev/config.md`, and the
`changed_template_paths` of the spec. Each step keeps its id and gains one marker: `run`,
`adapted` (with the changed selector, URL or copy and why), or `N/A` (the project overrides the
view or template, or the app is not installed). The `§0` seed list is rewritten against what the
project has: FLS `qa_*` and demo commands only when `freedom_ls.qa_helpers` is in its
`INSTALLED_APPS`, otherwise the project's own seed commands from its config, and a `blocked` footer
when neither exists.

`/fls-dev:do_qa` gains an optional input `project-root: <abs path>` beside `mode: hook`. With it:

- `.claude/fls-dev/config.md`, the `.claude/*/scripts/` wrappers, `runserver`, `manage.py`,
  `qa_cleanup.sh`, `qa_collect_screenshots.sh` and the git calls all take that root (`git -C`,
  `uv run --project`, absolute script paths).
- Step 2 diff scoping uses a `diff-range:` input the caller passes (the spec's FLS range) instead
  of `git diff main...HEAD`.
- Step 4 checks the badge names the project's branch, not an FLS branch.
- Step 13 green-lane fixing is off: `qa-bugfixer` is never spawned. Bugs go in the report and the
  caller triages them.
- Step 15 (todo) is skipped; Step 17 commits nothing (the caller commits).
- `<spec-dir>` is the adapted plan's directory, so `qa_report.md` and `screenshots/` land there.

Without `project-root:` nothing changes. The command invokes it as
`Skill(fls-dev:do_qa)` with the plan path, `project-root:`, `diff-range:` and `mode: hook`. A QA
bug is a cell failure (Requirement 4).

### 7. Pull-in scan

Once per project per run, after its last cell, one `sdd:sdd-worker` reads the project's own code
(`apps/`, `templates/`, `config/`, its `pyproject.toml`; never `submodules/`, never
`spec_dd/for_freedom_ls/`) and the project's `spec_dd/fls_integration/declined_pull_ins.md` if it
exists. It writes `.sdd-work/update_concrete_pullin_<project>.md` with at most ten candidates, each
a card: what it does in one sentence; project paths; the FLS app it would join or the gap it fills;
why it is general (no project name, brand, URL or data; another FLS project would use it; it fits an
existing extension point or `docs/app_structure.md` boundary; testable without the project); size
S, M or L; whether the project would delete its copy afterwards. Anything on the declined list is
left out.

The command asks per candidate, batches of at most four, options in this order: write an FLS idea;
keep it downstream; ask again next run. "Write an FLS idea" produces
`spec_dd/1. next/<slug>/idea.md` naming the project path and files as the reference
implementation, then `/sdd:roadmap` (sync). "Keep it downstream" appends a line (path, one-line
what, date) to `<project-root>/spec_dd/fls_integration/declined_pull_ins.md`, committed with the
report. Nothing is ever copied into FLS by the command.

### 8. Integration report

`<project-root>/spec_dd/fls_integration/<run-date>/integration_report.md`, `<run-date>` as
`yyyy-mm-dd_HH:MM`, sections in this order:

1. Verdict line: integrated N of M, parked on `<slug>` or none, FLS fixes landed, ideas written,
   pushed yes or no, and the resume instruction when not complete.
2. Needs attention: `blocked-on-fix` cells with their evidence, stale overrides flagged by
   template drift, workarounds still needed.
3. Cell table: spec, FLS commit, flags, result, project commit, new failures, QA result with a
   relative link to its `qa_report.md`.
4. Baseline: pre-existing failing node ids, and which of them passed after the run.
5. FLS changes made: fix commits with the spec and test that motivated them; ideas written with
   their paths.
6. Workarounds: removed, declined, still needed, unmatched.
7. Pull-in candidates: idea written, declined, deferred.
8. Assumed defaults taken during the run.

Transcript output is one line per cell as it finishes (`<project> <spec> integrated`), the stop
card on a failure (project, spec, step, failing ids, diff stat, class, proposed action), and the
matrix redrawn after each spec.

### 9. Permissions

Document in the command's preamble, and check in Step 1, that each project path is listed under
`permissions.additionalDirectories` in `.claude/settings.local.json` (gitignored). Add to
`.claude/settings.json` `allow` the prefixes the shared resource and the command use:
`Bash(git -C *)`, `Bash(uv run --project *)`, `Bash(uv sync --project *)`,
`Bash(npm --prefix *)`, `Bash(claude_plugins/sdd/scripts/land_on_main.sh *)`, `Bash(git switch *)`.
The `.env*` read hook stays; the command never needs a project's `.env`.

## Open questions

- Q: After a small fix lands, should intervening done specs fold into the retry cell or get cells
  of their own first? → A: fold (assumed default: a cell of their own would check out a commit
  without the fix and fail the same way. Overrule by editing Requirement 4.)
- Q: Should the baseline gate run on every run, or once and be cached per project? → A: every run
  (assumed default: it is one pytest run per project and the only thing that makes "new failure"
  true. Overrule by editing Step 1.)
- Q: Does the pull-in scan run when a project had no pending specs? → A: yes (assumed default:
  the scan is about the project's code, not the run's specs. Overrule by editing Step 5.)

## Success criteria

- Running `/fls-dev:update_concrete_projects` from the FLS `main` worktree with First-Class listed
  integrates every pending spec, one `Update FLS: <spec>` commit each, and pushes the project's
  branch.
- A portable test that fails only under the project's settings ends the run with a `fix/` commit
  on FLS `origin/main`, a regression test, and the cell integrated on retry.
- A failure the command classes as large leaves an `idea.md` under `spec_dd/1. next/`, a roadmap
  row, the project parked at last good, and the other projects finished.
- A workaround whose FLS fix is in the integrated spec is removed in that spec's commit after the
  operator approves it, and the gate stays green.
- A spec with a frontend QA plan has an adapted copy, `qa_report.md` and `screenshots/` under the
  project's `spec_dd/fls_integration/<run-date>/<spec>/`, with every step marked run, adapted or
  N/A.
- A declined pull-in candidate is not proposed on the next run.
- `update_fls.md` run inside a project with no local FLS checkout still works, following the shared
  resource.
- `uv run pytest tests/test_test_tiers.py` and the new structure test pass.
- No file under `claude_plugins/sdd/` or `claude_plugins/django-stack/` changes.
