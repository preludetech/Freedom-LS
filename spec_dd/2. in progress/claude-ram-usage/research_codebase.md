# Research: codebase footprint of the RAM-gate / worker-cap / crash-retry work

All paths are relative to the repo root unless absolute.

## Key correction to the brief

The brief says `-n auto` spawns 16 workers. In this repo it does not. Root `conftest.py` defines
`pytest_xdist_auto_num_workers(config)` returning `min(4, os.cpu_count() or 1)` ("what the shared dev server
can serve"). `tests/test_conftest.py` (marked `dev_tooling`) pins this: 8 and 16 CPUs give 4, 2 CPUs give 2,
unknown CPU count gives 1; it loads the root conftest by path because `freedom_ls/conftest.py` shares the bare
module name `conftest`. So a worker-count cap already exists, a fixed 4, and is not RAM-aware. It is the natural
place for a RAM-aware reduction (the hook receives `config`, so `config.option`/env can be read), but it lives in
project (FLS) `conftest.py`, not the generic plugin. The generic plugin cannot ship a conftest hook into a
project; it can only (a) change the `command:` line it prints, or (b) wrap pytest in a script. Also
`concrete_spec_integration.md` and `fls-dev/skills/testing/SKILL.md` say CI's Playwright job runs
`-m playwright -n auto` "which the root conftest caps at four workers".

## pytest configuration (pyproject.toml)

- Dev deps: `pytest-xdist>=3.8.0`, `pytest-timeout>=2.4.0`, `pytest-randomly>=4.1.0`, `pytest-socket>=0.7.0`, plus pytest-playwright (`--tracing`, `--screenshot` in addopts). No rerun plugin (no `pytest-rerunfailures`), no memory plugin. (Dependencies listed twice, in dev group and optional extras around lines 67-75 and 210-219.)
- `[tool.pytest.ini_options]`: `timeout = 300`; `addopts = "--strict-markers -m 'not ci_only and not weasyprint and not dev_tooling' --disable-socket --allow-hosts=127.0.0.1,::1 --tracing=retain-on-failure --screenshot=only-on-failure --dist loadfile"`; `testpaths = ["freedom_ls", "tests", "claude_plugins/fls-content"]`. `--dist loadfile` is there so module-scoped fixtures (the demo-content import) run once per module, not once per worker. Because it groups by file, work is lumpy: per-worker memory and the order tests finish in are file-driven. Rerunning only unfinished tests must preserve loadfile semantics (pass files/nodeids, not a re-collected whole).
- `[tool.test_tiers]`: `none = [...]`, `markers = "not ci_only and not weasyprint"`, `[[tool.test_tiers.tooling]]` array of tables (glob + tests). This is the existing project config table the generic script already reads; the user's "thresholds overridable in a pyproject `[tool.*]` table" fits as new keys here (e.g. a RAM/worker sub-table) or a new table, following `glob_list`/`marker_expression` validation with `ConfigError` for bad types. Env var overrides do not exist yet anywhere in select_tests.py (it reads only pyproject).
- Coverage: no `--cov` in addopts (comment in test_tiers.md says coverage lives in addopts or CI); `--no-cov` is already on targeted commands.

## Resource-heavy things inside the test run

- DB: pytest-django creates one test DB per xdist worker (`test_<db>_gw0..`) , each cloned/migrated; with the existing cap at 4 that is 4 DBs per worktree. Each worktree has its own PostgreSQL DB name. No custom `django_db_setup` found in `conftest.py`/`freedom_ls/conftest.py`.
- `freedom_ls/conftest.py`: mostly autouse cache-clearing fixtures, `site`, `live_server_site(live_server, site)` (line 296), media root isolation, `mock_legal_blobs`; it registers the `playwright` override used for every test under `freedom_ls/` (root conftest `del playwright`). No session-scoped heavy fixture found by grep for `scope=`. Demo-content import is module-scoped in test modules (referenced by the loadfile comment), not in conftest.
- Playwright: tests marked `playwright`; `live_server` fixture plus Chromium per worker. Selected-but-playwright-free targeted runs use `--ignore=<tests dir>/playwright` unless a UI glob (`**/templates/**`, `**/static/**`, `*.html/css/js`, `views.py`, `views/**`) touched the app. So browser tests are already excluded from most targeted runs, which is a RAM saver already in place; the Playwright-heavy case is full tier and UI-touching targeted runs.

## SDD fan-out points (RAM from Claude Code subagent processes + their test runs)

- `.claude/sdd/config.md`: `Parallel batches: 3` under `## Worktree Scripts`; hooks: `Test tiers: claude_plugins/django-stack/resources/test_tiers.md`, `Pre-test rebuild: .claude/fls-dev/scripts/rebuild_after_rebase.sh`; Setup/Teardown scripts `.claude/fls-dev/scripts/install_dev.sh` / `dev_db_delete.sh`. `config.local.md` (gitignored) overrides every key, which is the existing per-machine override path for SDD settings (the user wanted env var per machine; config.local.md is already an alternative that the SDD side honours, the ds side does not read it for select_tests).
- `implement_plan.md` (generic sdd): **Cap** reads `Parallel batches` (blank/absent/1 is 1). **Batch waves**: `ready` batches whose `Builds on:` are done; wave = first `min(len(ready), cap)`. A wave of one runs in the feature worktree, no isolation, with the retry rule "at most two retries across every batch wave" (this paragraph owns the attempt count; failure -> reset partial uncommitted work, retry with prior error in the brief). A wave of two or more spawns all in one message with `isolation: "worktree"`, each worker running Setup script (a new test DB and venv per batch worktree), then its own targeted tier, then Teardown. So with cap 3: 3 worktrees x (targeted pytest -n up to 4 workers) = up to 12 workers concurrently plus 3 Claude subagents, which is the main fan-out RAM multiplier. Integration cherry-picks after all return. A batch that returns no status line is `failed` reason `no return`, and a crash/OOM-killed worker probably surfaces as that, consuming one of the two retries. The RAM-crash retry must be defined relative to this existing 2-retry budget (spec must say whether a worker-crash retry inside a test run is separate from a batch retry).
- `pre_step_rebase.md` (sdd protected): runs "the test tier the rebase runs" and spawns one solo `sdd:sdd-worker` (line ~102); `rebase_main.md` in django-stack also runs a tier.
- Parallel research/review fan-out (read-only, light on RAM but each is a Claude process): `spec_from_idea.md`, `plan_from_spec.md`, `roadmap.md` (units U1..Un "one worker per unit, in parallel"), `spec_review.md` (five dimension workers in parallel), `document.md`, `finish_worktree.md`. They have no cap setting today: only `implement_plan` has `Parallel batches`. `do_qa.md` says every Agent spawn is solo (step 3e) and runs a full tier at line ~736; QA browsers are out of scope per answers.
- Test-spelling guard: `tests/test_test_tiers.py` asserts the set of plugin `.md` files containing `uv run ... pytest` (regex `PYTEST_INVOCATION` in `tests/plugin_markdown.py`) equals an ALLOWED set: `test_tiers.md`, `fls-dev/skills/testing/SKILL.md`, `fls-dev/resources/playwright-testing.md`, `fls-dev/resources/concrete_spec_integration.md`, `sdd/commands/protected/run_test_tier.md`. Any new plugin markdown that spells `uv run pytest` (e.g. a new RAM-gate doc or retry procedure) fails this test unless it is added to ALLOWED or avoids the literal. A new script file (.py/.sh) is not scanned (only `*.md`).

## Existing tests for select_tests.py

- `tests/test_select_tests.py` (~1060 lines): runs the script via subprocess in `tmp_path` repos with a fake `pkg/alpha`, etc. Constant `FULL_COMMAND = "command: uv run pytest -n auto"` (line 19) and ~15 assertions of the exact string `command: uv run pytest -n auto --no-cov ...` (targeted), `-n auto -m 'not slow'` (markers). Any change to `FULL_COMMAND`/`TARGETED_PREFIX` (e.g. replacing `-n auto` by `-n <N>` or prefixing a gate script) changes all of these. Safest design for test stability: leave the `command:` line byte-identical by default and add the gate/cap as a separate step or separate printed line (e.g. a `workers:` line or a wrapper script that executes the command), so existing assertions keep passing; tests also assert identical output across runs (`test_two_runs_over_the_same_tree_print_identical_output`), so the printed line must stay deterministic: a RAM-reading value must not be baked into `command:` at selection time (RAM is read at run time, not select time).
- `tests/test_select_tests_wrapper.py` + `tests/stub_tools.py` (`StubTools`, `write_stub`, `run_script`): stub `uv` on PATH to test shell wrappers; reuse this pattern to test a new gate shell script with stubbed `free`/`/proc/meminfo` readers.
- `tests/test_conftest.py`: tests for the worker cap hook; any RAM-aware change to `pytest_xdist_auto_num_workers` extends these (they `mocker.patch("os.cpu_count")`, call with `config=None`; a new RAM read must tolerate `config=None` and be patchable).
- Tests under `tests/` are collected by default but `test_conftest.py` is `dev_tooling` (deselected unless `-m dev_tooling`; tiers pass the project's `markers` which does not exclude `dev_tooling`).

## Where each new piece plugs in

1. **RAM gate (wait for free RAM before a run).** Per-run, per-worktree only (no cross-worktree lock). Fits as a step before the pytest launch. Options: (a) a new stdlib-only generic script in `claude_plugins/django-stack/scripts/` (siblings are stdlib-only Python, e.g. `select_tests.py`) that reads `/proc/meminfo` `MemAvailable` (and optionally swap use / PSI at `/proc/pressure/memory`), waits with a bounded loop, and execs the command; (b) text in `test_tiers.md` telling the agent to run through it. Given the guardrail ("no `ps`/`pgrep` polling loops and no `timeout` wrapper" applies to the agent polling by Bash), the wait must live inside one script process that runs as the single background Bash call, not as an agent-side poll loop; the agent still just waits for the completion notification. It can print its own wait/backoff lines. Note host has 20 GB swap used at idle so `MemAvailable` (not free) and perhaps swap-in rate are the better signals; this is a research question for the other topics.
2. **Worker-count cap.** Two layers: (i) existing fixed cap in root `conftest.py` hook (project file; FLS-specific, 4); (ii) a generic reduction when RAM is low. The generic plugin cannot edit conftest, so the reduction should come from the runner script passing an explicit `-n <k>` (an explicit number bypasses the hook, since `pytest_xdist_auto_num_workers` is only consulted for `auto`/`logical`) or by setting an env var that a project hook reads. Interacts with `--dist loadfile` (fewer workers is fine) and with `-n 0` / no xdist (`concrete_spec_integration.md` notes projects without xdist reject `-n`; the generic script must not assume xdist present; select_tests.py today already hardcodes `-n auto` so xdist is assumed for the tier path).
3. **Crash vs failure and retry (max 2, fewer workers, only unfinished tests).** pytest-xdist reports a dead worker as "worker 'gwN' crashed while running '<nodeid>'" (replaced worker; after `--max-worker-restart`, default 4 times the worker count, it aborts with "maximum crashed workers reached"). Distinguishing crash from failure needs output/junit parsing or the `--lf` cache. Existing `--lf` guidance in test_tiers.md ("re-run only the failures with `uv run pytest --lf --no-cov`, append `-n auto`") reruns failures, not never-finished tests, and `--lf` also reruns tests that failed, so it is not the same operation: "never finished" tests are neither pass nor fail in `.pytest_cache/v/cache/lastfailed`. A rerun of unfinished tests needs a record of which nodeids completed (e.g. `--junitxml` or `-rA` log, or a small plugin/conftest hook writing nodeids as `pytest_runtest_logreport` fires). pytest-randomly is installed, so order is shuffled per seed; reruns should pass `-p randomly` seed (`-p no:randomly` or `--randomly-seed=<same>`) consistently or order-dependent flakes can mask. The `timeout = 300` (pytest-timeout) is separate: a timeout is a test failure (default `signal` method kills the test, not the worker) and must stay classified as a failure, not a crash. A kernel OOM-kill of the whole pytest process (parent) is a different signal (exit 137/-9) from a worker crash; both need handling in the runner. The "crash retry" must also stay consistent with the section "When a targeted run or full run fails" (agent-owned fix + `--lf` + whole-tier re-run as the gate): a crash retry would sit before that section, inside the single "run the tier" action, and the run's reported outcome is the final attempt's summary line; the gate is still the whole tier, so after retrying only unfinished tests the completed tests' results from the earlier attempt must be combined into the reported "no failures" verdict (or the full tier must be rerun) - a spec decision.
4. **Thresholds config.** Plugin defaults in the script; project override in a pyproject `[tool.*]` table read like `load_tier_config` (ConfigError on bad types, exit 2); per-machine override via env var. Env vars have no precedent in the plugins for test config; `.claude/sdd/config.local.md` is the precedent for per-machine SDD settings. SDD-side cap (`Parallel batches`) is read from `.claude/sdd/config.md`; `implement_plan` could additionally consult available RAM when forming a batch wave (reduce `min(len(ready), cap)`), a text change in a generic command with no FLS names, which is allowed.
5. **Guardrail consistency.** Keep: background run + wait for completion notification; one tier at a time per worktree; no agent-side `ps`/`pgrep` loops; no `timeout` wrapper (a wrapper `timeout` would also kill the whole retry loop; tests have their own pytest-timeout). The gate/retry has to be one script invoked once, not shell loops written by the agent. `run_test_tier.md` fallback (blank Test tiers) is plain `uv run pytest` with no `-n`, no gate: the spec should decide whether the gate applies there (a project with no tier definition has no select_tests path).
6. **Docs/tests to touch if implemented:** `test_tiers.md` (How to run a tier; failure section), `select_tests.py` plus `tests/test_select_tests.py` (new key parsing tests mirroring the `test_non_list_value_exits_2_naming_the_key` style), `claude_plugins/django-stack/README.md`/`skills/testing/SKILL.md` pointers, `claude_plugins/sdd/commands/README.md` if `implement_plan` changes, `tests/test_test_tiers.py` ALLOWED list if new md spells `uv run pytest`, `fls-dev/skills/testing/SKILL.md` if FLS-specific notes (cap 4 etc.), and the root `conftest.py` + `tests/test_conftest.py` if the hook becomes RAM-aware. Generic-plugin rule: none of `freedom_ls`, `weasyprint`, `ci_only` etc. may appear in the generic files; project values (like `markers`) stay in pyproject.

## Conflicts / risks to flag

- The existing fixed cap of 4 already reduces the RAM problem the idea attributes to 16 workers; per-test-run RAM is therefore at most 4 workers x (Python + Django + DB connection + optional Chromium) per worktree. The real multipliers are many worktrees/sessions at once and `Parallel batches: 3`; a per-run-only RAM check (answers.md) will not coordinate across worktrees, so thresholds must be conservative about total `MemAvailable`, not per-run need.
- `command:` line exactness is asserted in ~20 places in `tests/test_select_tests.py` and the doc says "run the `command:` line exactly as printed". Anything that rewrites the command at run time contradicts "exactly as printed" unless the doc is amended.
- `--dist loadfile` with fewer workers on retry: fine, but unfinished-test reruns by nodeid across files still group by file.
- pytest-randomly reorders and reseeds; retrying with a different seed changes order.
- `tests/test_conftest.py` and tiers: `dev_tooling` tests are only deselected by default `addopts`; the tier `-m` replaces it, so they run in tiers.
