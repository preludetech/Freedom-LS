## 1. Educator course detail view

### What builds it today

- Section config: `CourseConfig` in `freedom_ls/educator_interface/panels/course/config.py` (`url_name = "courses"`, `instance_view = CourseInstanceView`, `authorise_instance` uses `courses_visible_to`).

  `details` (`CourseDetailsPanel`), `content` (`CourseContentPanel`), `reference` (`CourseReferencePanel`), `cohorts` (`CourseCohortRegistrationsPanel`), `learners` (`CourseLearnerRegistrationsPanel`).
  So "too much stuff in the first tab" is really "one long page". The spec needs a `TabSet` (`panels.py`, `child_segment = "__tabs"`, template `panel_framework/panels/tab_set.html`).

- Learner page does the same: `freedom_ls/educator_interface/panels/learner/instance_view.py` (`LearnerRegistrationsPanel` in the Overview tab, `RegisterLearnerForCourseAction` in `get_actions`).
- Proposed shape: `CourseTabSet(TabSet)` with `overview` = `CoursePanelStack`-like stack (`details`, `cohorts`, `learners`) and `content` = stack (`content`, `reference`). The idea says tab 2 is "content"; it does not mention Reference, so the spec must decide (most natural: Reference goes with Course content on tab 2, as the skill says it "follows Course content").

- Existing tests that pin the current shape and will need updating: `freedom_ls/educator_interface/tests/panels/course/test_instance_view.py` (`test_the_course_panel_stack_orders_reference_after_content`, `test_the_rendered_course_page_shows_its_panels_in_stack_order`), `.../course/test_content_preview.py`, and the Playwright `freedom_ls/educator_interface/tests/playwright/test_course_preview_flow.py`.

### Conflicts and risks specific to a Course instance

1. **Capability scope.** `PanelAction.has_permission` asks `ctx.config.has_capability(request, capability, ctx.scope_object())`, and `scope_object()` is the bound instance, which on this page is a `Course`. `can()` in `freedom_ls/learner_management/capabilities.py` calls `_organisation_of(scope)`, which **raises `TypeError` for anything but Site, Organisation, Cohort or Learner**. A course-page action with a capability would crash. The hook is `PanelAction.permission_object(ctx)` (`freedom_ls/panel_framework/actions.py` ~line 207): override it to return the request's organisation (`cast(OrganisationScopedRequest, ctx.request).organisation`), or the specific cohort/learner for a row action. The existing `PreviewContentAction` avoids this with `capability = None`. `freedom_ls/educator_interface/tests/invariants/test_permission_matrix.py` and `test_config_authorisation.py` will want the new actions added.
2. **Cohort-level grants.** A cohort-only role (a role granted on a cohort, not the organisation) can act on that cohort but not on the whole course. A row-level `permission_object` (the row's cohort) fits the existing "a row the viewer cannot act on states its fields and leaves its buttons column empty" rule. The picker's cohort list must be narrowed to cohorts the educator can add registrations for.
3. **Course availability.** Like `_preview_available`, registering for a course not available to the organisation must be refused: `require_course_open_to` / `CourseNotOpenError` (services) and `is_course_available_to_organisation` (`freedom_ls/learner_management/queries.py`). A course listed only because the organisation holds a registration on it (the "shared, withheld content" case) should probably show the registrations tables but not an Add trigger.
4. **Inactive cohort.** `RequiresActiveCohortMixin` refuses actions on an inactive cohort; a cohort picker on the course page must exclude inactive cohorts.
5. **Header counts/refresh.** Cohort add uses `navigation_response(ctx.page_url)` to refresh header stats and tab counts; the course `InstanceView` has `header_refresh_events` (see `CohortInstanceView`). Decide whether the course header shows counts.
6. **Scoped site-aware managers.** Services use `_base_manager` with explicit `site`; new actions call the services, never raw ORM writes.

## 2. Button text vertical misalignment

### Where buttons come from

- Educator templates use `<c-modal-trigger>` / `<c-panel-button>` / `<c-modal-footer>` (panel-framework primitives, `freedom_ls/panel_framework/templates/cotton/`). The framework's own `panel-button.html` draws `.panel-btn panel-btn-<variant> [panel-btn-sm]`.
- **In FLS the host wrapper overrides it.** `freedom_ls/base/templates/cotton/panel-button.html` forwards every attribute to `<c-button>`, and `freedom_ls/base/templates/cotton/button.html` renders `class="btn btn-<variant> [btn-sm] ..."`. So in the running FLS app, the "Preview", "Deactivate" and "Close" buttons are `.btn` buttons, and the `.panel-btn` rules in `freedom_ls/panel_framework/css/panel_framework.css` (lines 111-193) do not apply (unless a project imports that file and the wrapper is bypassed). Both rule sets exist in parallel (duplicated).
- Base `.btn` rules: `tailwind.components.css` lines 221-311. `.btn` = `inline-flex items-center justify-center gap-2 px-6 py-2 font-medium rounded-md ...`; `.btn-secondary` = `bg-transparent text-primary inset-ring inset-ring-primary`; `.btn.btn-sm` = `px-2 py-1.5 text-sm`; `.panel-data-table td .btn, .panel-data-table-card .btn` = `px-2 py-1.5 text-sm`; `[data-modal-footer] .btn` = `max-md:min-h-11`; below `md` an invisible `::after` hit area.
- `.btn` is `inline-flex items-center`, so the label is centred as a line box inside the padding. There is no `leading-*`, `h-*` or `min-h-*` on desktop (only the footer's `max-md:min-h-11`). A text that "sits low" in a symmetric `py-1.5` box points at the line box, i.e. font metrics.
- Preview triggers add `md:-my-1` (`partials/course_outline_actions.html`), which cancels vertical margin but does not move the label inside the button.

### Theme layer (FLS side)

- `freedom_ls/themes/first_class/static/themes/first_class/theme.css`: tokens `--fls-font-sans: "DM Sans", system-ui, Arial, sans-serif;` `--fls-font-display: "Outfit", ...;` (lines 82-84), and a Tier-2 override at lines 93-97: `.btn { @apply px-6 py-3 text-sm font-semibold rounded-md; transition: ... }` and `.btn-secondary { @apply inset-ring-2; }`. The `font-semibold` is why the labels in the screenshots look bold (default theme `.btn` is `font-medium`).
- Default theme: `freedom_ls/themes/default/static/themes/default/theme.css` maps `--font-sans: var(--fls-font-sans)` (lines 119-142), system-ui stack by default.
- **No `@font-face`, Google Fonts `<link>` or font file loads DM Sans or Outfit anywhere in the FLS repo or in First-Class-LMS** (searched templates, CSS, static in both; only the design-source TTFs under `spec_dd/` exist). `.claude/skills/brand-guidelines/visual.md` line 55 says the same: "These faces are the brand's intent, not what ships ... Adopting the brand faces is theme work: see `docs/how tos/theme-fls.md`" (which tells the host to load the external font files).
- So the rendered font is `system-ui`/Arial unless the viewer's machine has DM Sans installed locally (a designer or developer machine would). A locally installed DM Sans (often a static TTF from the design system with its own ascent/descent) is the one known way for the brand font to reach buttons today, and mismatched vertical metrics in such a font shift a centred label. This is a hypothesis, not confirmed: no browser measurement was done.

### Concrete project (First Class) side

- `/home/sheena/workspace/first_class/First-Class-LMS.git/main/tailwind.input.css` imports, in order, the FLS default theme, `submodules/Freedom-LS/tailwind.components.css`, the FLS `panel_framework.css`, then the FLS `first_class/theme.css`. It adds only a `@theme` block with four colour roles; **no button, font or line-height override**.
- `config/customisation.py` sets the active theme; `templates/` has no `cotton/button.html` or `panel-button.html` override (`templates/cotton/` does not exist), and its other templates only use `<c-button>`. No project CSS sets `.btn`, `line-height` or fonts (`static/vendor/tailwind.output.css` is the build output).
- First-Class-LMS consumes FLS as a submodule (`submodules/Freedom-LS`), so it renders exactly the FLS rules above.
- Conclusion on which side: **the cause sits on the FLS side** (the first_class theme and `.btn` / font handling), not in the First Class repo, going by the code. The most likely contributors, in order: (a) the theme declares DM Sans/Outfit with no `@font-face` or metric overrides (`ascent-override`, `descent-override`, `size-adjust`), so a locally installed or later-loaded DM Sans shifts the baseline of an `inline-flex items-center` label; (b) the first_class `.btn` override (`py-3`, `font-semibold`) versus the data-table/`btn-sm` overrides (`py-1.5`): specificity is intentional but the two paths are duplicated in `.btn`/`.panel-btn`; (c) `inset-ring-2` makes the outline thicker but adds no height, so it is not the cause. Per `answers.md`, anything found only in the First Class repo is a downstream note; nothing in that repo currently looks like a cause.
- The three screenshots (`image.png`, `image-1.png`, `image-2.png` beside the idea) show small outlined buttons ("Preview", "Deactivate") with the label clearly nearer the bottom edge. A Playwright measurement (label glyph box versus button box) in a browser with and without DM Sans installed is the quickest way to confirm. `freedom_ls/educator_interface/tests/playwright/test_touch_targets.py` already measures button heights and is the right home for a regression test of label centring.
- Fix surface if confirmed: `freedom_ls/themes/first_class/static/themes/first_class/theme.css` (ship `@font-face` with metric overrides and the font files, or use `leading-none`/an explicit `line-height` on `.btn`), `tailwind.components.css` `.btn` and the duplicate `.panel-btn` in `freedom_ls/panel_framework/css/panel_framework.css` (the framework test `test_framework_copies_match_base` pins some copies; change pairs together). Docs: `docs/how tos/theme-fls.md`, `claude_plugins/fls-dev/skills/frontend-styling/SKILL.md` (theme tokens).

## 3. Course content preview modal

### Where it is built

- Action classes in `freedom_ls/educator_interface/panels/course/content_preview.py`:

The footer has no way to omit the cancel button today (`cancel` is always rendered). Header close (`<c-modal-header closable="true">`, `modal-header.html`), Esc (`alpine-components.js` ~line 299-330) and backdrop click all stay, matching the answer.
- Swapping inside an already open modal already works: modal forms use `hx-target="#app-modal-body"` (`modal/form.html`, `modal/confirm.html`), and the Alpine code handles focus on swap (`~line 1496`, `pendingEntryAction`, `focus_title`). Next/Previous would be `hx-get` buttons with the same `hx-target`/`hx-swap` as `modal-trigger.html`; `<c-modal-trigger>` itself can be reused with `size` unset (full size in a footer), since it forwards attributes.

### Next/previous from the outline order

- The outline order is already defined in one place: `outline_rows(course)` returns `OutlineRow`s: the "Course details" row first (`kind="course"`, no `preview_query`; it previews via the different action URL), then each collection item in order, parts expanded to their children via `_part_row`/`_outline_item_rows`; a multi-page form is a group row (`preview_query="item=<pk>"`, start page) followed by one `page` row per page (`preview_query="item=<pk>&page=<pk>"`); a single-page form and a topic have one row. A part row has no `preview_query`.
- A sequence for the modal = depth-first walk of `outline_rows(course)`, keeping the course-details row (own URL) and every row with a non-empty `preview_query`, skipping parts and `note` rows. The walk should be written once next to `outline_rows` (the file already has `_outline_content_count` and `_all_collection_items` doing similar tree walks). The "whole course, across parts" answer maps to this exactly; the first item is Course details (Previous disabled) and the last is the final item or page (Next disabled).
- `PreviewContentAction.get_context_data` already has the course and the current `(item, page)` pair, so it can compute `previous_url` / `next_url` for the template. Footer URLs: item rows use `action_url?item=...[&page=...]` and the first row uses `preview_course_details`'s URL. Both actions use `ctx.base_url`-derived URLs through `PanelAction.get_action_url(ctx)`. `PreviewCourseDetailsAction` needs the same next URL (to the first item). Reference panel previews (`course_list="reference"`) are a separate list with its own numbering and `reference_rows(course)`; the spec should say whether Next/Previous walks the reference list within it (simplest) or only Course content.
- Cost: `_course_list_items` and `outline_rows` both call `course.collection_items()` and prefetch form pages (`_prefetch_form_pages`), so building the sequence per request is the same query shape the outline already has; add a query-count assertion in `freedom_ls/educator_interface/tests/panels/course/test_content_preview.py`.
- Disabled ends: render a `disabled` `c-panel-button` (not a missing button), so the footer layout does not jump.
- Tests that currently assert the Close button or footer: `freedom_ls/educator_interface/tests/panels/course/test_content_preview.py` and `test_course_preview_flow.py` (Playwright). Panel-framework invariants to read before changing the footer: `freedom_ls/panel_framework/tests/invariants/test_templates.py` (`test_every_dialog_ends_in_the_modal_footer_not_a_button_group`, `test_every_dialog_renders_one_modal_footer_outside_its_body`, `test_no_dialog_template_hand_writes_what_a_component_owns`), plus `educator_interface/tests/invariants/test_panel_template_rules.py`. The skill rules "A dialog ends in `<c-modal-footer>`: it renders its own Cancel at the left" and "a message dialog ... ends in a Close footer like every other" mean the footer contract changes and the skill must be updated.
- Phone behaviour: `[data-modal-footer] .btn` is 44px tall below `md` and the slot "wraps onto its own row below sm"; two buttons (Previous, Next) fit.

### Quiz top-level preview: stats and settings

- "Quiz top level preview" means the preview of a form row whose `Form.strategy == FormStrategy.QUIZ` (`freedom_ls/form_engine/models.py`).
