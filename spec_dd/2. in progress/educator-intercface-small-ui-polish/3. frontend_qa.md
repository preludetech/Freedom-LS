# Frontend QA: educator interface small UI polish

What changed that a browser can see:

- **The educator course page** (`/educator/organisations/<org>/courses/<uuid>`) has two tabs:
  Overview (Course details, Cohort registrations, Direct registrations) and Content (Course
  content, Reference).
- **Outline groups** (parts, multi-page forms) start collapsed on the Content tab.
- **Registration actions** on the course page: Register in each registration panel's footer,
  Deactivate on active rows, Reactivate on inactive direct registrations.
- **The content preview** footer has Previous and Next instead of Close.
- **A quiz's own preview** shows its facts and settings.
- **Button labels** sit centred in the First Class theme.

Beyond the golden path, this run hunts for:

- **Over-granting.** A cohort admin acting on another cohort's registration, a viewer seeing any
  write control, a footer Register on a course the organisation cannot use.
- **Stale pages.** Acting from a second tab after the row changed must answer with a reason or a
  "not available" message, never silently succeed or crash.
- **Repeat submissions.** Registering the same cohort or learner twice must not create a second row.
- **Side effects on other pages.** The cohort page's Courses tab and the learner page's
  Registrations card must behave exactly as before. Other tables with child rows must still start
  open.
- **Preview edges.** Stepping must never leave its list (Reference never reaches Course content),
  and must not break at either end or across a part.

---

## §0 Setup

1. `PORT=$(.claude/ds/scripts/find_available_port.sh)`. Use that number literally from here on.
2. Start the server with the `Dev server start` command from `## QA Hooks` in
   `.claude/sdd/config.md`, on `$PORT`. The base URL is `http://127.0.0.1:$PORT`. Check the
   `debug-branch-badge` names this branch.
3. Load the demo content if it is missing: `uv run python manage.py content_save ./demo_content DemoDev`.
4. Log in at `http://127.0.0.1:$PORT/accounts/login/` with the QA login from `## QA Login`
   (`demodev@email.com`). That account is an admin and an educator.
5. Open the educator interface from the header, pick an organisation, then "Courses". Use
   "Functionality Demo - Course Parts" (three parts; "Core Concepts" holds the quiz
   "Knowledge Check") and "Functionality Demo - Reference Material" (reference parts). Below,
   `<course-url>` is the course page URL.
6. Data the tests need. Ask the QA data helper for whatever is missing, in the organisation in view:
   - Cohorts "QA Cohort A" (active, with two learners) and "QA Cohort B" (active), and
     "QA Cohort Inactive" (inactive), none registered for "Course Parts".
   - A learner "QA Learner One" in the organisation with no direct registration for "Course Parts".
   - A multi-page quiz form in a course the educator can open (for example the demo
     "functionality_demo_end_with_quiz" or "shuffled_quiz" courses; check which quiz has more than
     one page), and a non-quiz (survey) form.
   - A staff user "QA Cohort Admin" holding `cohort_admin` on "QA Cohort A" only, with a password
     the helper reports, for Test 6.

Check each page at 1920x1080, 375x812 and 768x1024 unless a test names one width. At every width:
no horizontal scroll, no console errors, no 500 in the server log.

## Test 1: Overview and Content tabs

1. Go to `<course-url>` for "Course Parts".

Expect:

- Two tabs, "Overview" (selected) and "Content".
- Overview shows, top to bottom: the course details card, "Cohort registrations", "Direct
  registrations". No outline on this tab.
- Click "Content": the URL ends in `/__tabs/content`. It shows "Course content" then "Reference".
- Reload the Content URL directly: the Content tab is selected.
- The cohort page of any cohort still shows its own tabs unchanged (Overview, Learners, Courses,
  Report, Settings, History).

## Test 2: outline groups start collapsed

1. Open the Content tab of "Course Parts".

Expect:

- Every part row ("Getting Started", "Core Concepts", "Wrapping Up") is collapsed: its child rows
  are hidden and its chevron points down (not rotated).
- Inspect a part's chevron button: `aria-expanded="false"`.
- Click "Core Concepts": its items show, the chevron turns, `aria-expanded="true"`. Click again: it
  closes.
- In a course with a multi-page form inside a part, open the part: the form row is itself still
  collapsed; open it to see its page rows.
- At 375x812 the card list behaves the same way: groups closed, each opens on tap.
- Reference ("Functionality Demo - Reference Material", Content tab): its parts start collapsed too.
- Another table with child rows that is not an outline (if any page uses one, such as the
  component reference page at `/panel-framework/reference/` when it is routed) still starts open.

## Test 3: register and deactivate a cohort from the course page

On "Course Parts", Overview tab, "Cohort registrations" panel.

1. The panel footer shows one primary "Register" button. Click it.

Expect: a dialog titled "Register a cohort for Functionality Demo - Course Parts?" with a cohort
picker. It lists "QA Cohort A" and "QA Cohort B", not "QA Cohort Inactive", and no cohort already
actively registered.

2. Pick "QA Cohort A". The title changes to name the cohort. Click "Register".

Expect: the dialog closes; the panel refreshes in place (no full page load) and shows a row
"QA Cohort A", Status active, with a small secondary "Deactivate" button. The cohort name links to
the cohort page.

3. Click Register again. "QA Cohort A" is no longer offered.
4. On the row, click "Deactivate". Its accessible name is "Deactivate QA Cohort A".

Expect: the same confirmation the cohort page shows (who loses access, a reason field). Enter a
reason and confirm. The row shows Inactive and no Deactivate button.

5. Click Register: "QA Cohort A" is offered again. Register it.

Expect: the same row is active again (one row for "QA Cohort A", not two).

6. Open "QA Cohort A"'s page, Courses tab: "Course Parts" is listed active, with its own
   Deactivate as before. Its History tab records the registration, deactivation (with the reason)
   and reactivation.
7. Submit twice quickly: on the Register dialog, double-click "Register". Only one registration
   results; the button disables while saving.

## Test 4: register, deactivate and reactivate a learner from the course page

On "Course Parts", Overview tab, "Direct registrations" panel.

1. Click the footer "Register". A single-learner picker lists learners of this organisation; pick
   "QA Learner One" and register.

Expect: the panel refreshes in place with a row for "QA Learner One" (linking to the learner page),
active, with "Deactivate".

2. Deactivate it with a reason. If "QA Learner One" is also in a cohort registered for the course,
   the dialog says they still have access through that cohort.

Expect: the row becomes inactive and shows "Reactivate" ("Reactivate QA Learner One").

3. Click "Reactivate" and confirm. The row is active again with "Deactivate".
4. Open "QA Learner One"'s learner page: the Registrations card shows the course active and its
   own Deactivate/Reactivate still work there.

## Test 5: refusals and stale pages

1. Open the course page Overview in two tabs. In tab 1, deactivate "QA Cohort A"'s registration.
   In tab 2 (not refreshed), click "Deactivate" on that row and confirm.

Expect: a message that the action is not available or nothing changed, not a 500 and not a silent
success.

2. Deactivate "QA Cohort B" itself from its Settings tab after registering it for the course. Back
   on the course page, its row shows no actions. Using a stale tab that still shows its Deactivate,
   confirm: the dialog says the cohort is inactive and nothing changed.
3. Find (or ask the data helper for) a course listed on this organisation's Courses page only
   because a cohort holds a registration on it, not available to the organisation. Its Overview tab
   shows both registration panels with no footer "Register" buttons.
4. Edit an action URL by hand: copy a Deactivate trigger's `hx-get` URL from the DOM and change the
   `registration=` value to a random UUID, then open it. Expect a 404 or "not available" response,
   never another organisation's data.

## Test 6: a cohort admin sees only their own cohort's rows

   and "QA Cohort B" both registered).

Expect:

- "QA Cohort A"'s row has Deactivate; "QA Cohort B"'s row (if visible at all) has an empty actions
  cell, with no note.
- The footer Register lists only "QA Cohort A" (or says there is nothing to register when it is

- Direct registrations rows show actions only for learners in "QA Cohort A".

2. Log back in as the QA admin login for the remaining tests.

## Test 7: Previous and Next in the preview

Design reference: none. Judge against this list.

1. On "Course Parts", Content tab, open "Getting Started" and click Preview on "Course details".

Expect:

- The footer has "Previous" at the left (disabled) and "Next" at the right. No "Close" button.
- The header still has its X.

2. Click Next repeatedly. The title changes each time (a topic, the next topic, then across the
   "Core Concepts" part boundary into its first item), and keyboard focus is on the title after each
   step (press Tab once: focus moves into the dialog, not back to the page).
3. Click Previous once: you are back on the item before.
4. Keep clicking Next to the last item of "Wrapping Up": Next is disabled and the footer has not
   shifted.
5. A multi-page form: its own row, then Next goes to "Page 1 of N", then each page in order.
6. Press Esc: the dialog closes. Reopen a preview and click the header X: it closes. Reopen and
   click the backdrop: it closes, with no "discard changes" prompt.
7. "Functionality Demo - Reference Material", Content tab, Reference panel: Preview its first
   reference topic. Previous is disabled (it never steps into Course content or Course details).
   Next steps through the reference topics only; the last has Next disabled.
8. At 375x812: Previous and Next are full-size footer buttons (44px tall), side by side or wrapped
   tidily, with no horizontal scroll.

## Test 9: button labels centred in the First Class theme

1. Stop the server. Build and run with the First Class theme:
   `FLS_THEME=first_class npm run tailwind_build`, then start the server with `FLS_THEME=first_class`
   in front of the `Dev server start` command, on the same `$PORT`.
2. Open the course page and the cohort page's Courses tab at 1920x1080.

Expect, judged by eye and by `browser_evaluate` on a few buttons (label text box centre against the
button box centre):

- "Preview" buttons in the outline, "Deactivate" row buttons, the footer "Register" buttons, the
  preview's Previous/Next, and a dialog's Cancel/confirm: each label sits visually centred top to
  bottom, not lower than centre.
- Buttons of one size are one height in each place (row buttons match each other; footer buttons
  match each other). Heights look the same as before the change: no button is visibly taller or
  shorter than its neighbours of the same size.
- Icon-only buttons still centre their icons.

3. Repeat at 375x812: dialog footer buttons are 44px tall, row buttons keep their small look.
4. Clean up: stop the server, run `npm run tailwind_build` with no `FLS_THEME` so the built CSS is the
   default theme again, and confirm `git status` shows no changed tracked file from the build.
