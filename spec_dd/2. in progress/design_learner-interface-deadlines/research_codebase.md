# Research: codebase touchpoints for design_learner-interface-deadlines

Scope: dashboard course card band, player outline "next deadline" card, inline outline row deadlines, body-header deadline card. Upcoming-deadlines page is out of scope (separate spec). Design is a visual reference only (design.md).

Headline: learner-facing deadline display ALREADY EXISTS end to end (resolver, policy, per-row `due_at`/`is_overdue`/`closes_at`/`is_closed`, a card line, outline due-date lines, a header line). This work is a re-presentation plus a small amount of new derived data (urgency tiers, "next deadline" for the player, a time-left string), not new deadline plumbing.

## 1. Deadline data layer (reuse as is)

App `freedom_ls/deadlines/` (apps.py, models.py, resolver.py, policy.py, consequences.py, loader.py, queries.py, config.py, signals.py, templatetags/deadline_tags.py).

- `resolver.py`
  - `DeadlineValue(kind, due_date, due_time, due_days_after_registration)`; `DeadlineKind` (models.py: FIXED / RELATIVE / NONE). `no_due_date` content flag = explicit "no deadline" layer value.
  - `DeadlineSource` StrEnum: CONTENT, COHORT_REGISTRATION, LEARNER. `resolve_deadline(layers, registration_date, tz)`: first layer holding a value wins outright. Layer order: `LearnerDeadlineOverride` > `CohortDeadlineOverride` > content default.
  - `ResolvedDeadline(due_at: datetime|None, source)`; `NO_DEADLINE`. `due_instant()`: a date without a time is due at `time.max` (23:59:59.999999) of the day, in the site zone; relative offsets are added to the local registration date (`registration_date_of(CourseProgress)` = `created_at` in site zone).
  - `CourseDeadlines(items: dict[collection_item_id -> ResolvedDeadline], time_limit: ResolvedDeadline)`; `course_deadlines(record)`, `course_deadlines_for(records)` (fixed query count regardless of rows; `_defaults_by_course` does 4 queries). Time limit is `Course.time_limit_days` -> relative deadline, keyed `item_id=None` in override tables.
  - `is_overdue(resolved, completed, now)`; `content_defaults_for_course()` (shared with admin).
  - Per-placement dates (deadlines-8 equivalent): `CoursePartChildDueDate` (`freedom_ls/content_engine/models/courses.py:598`), one row per (`part_collection_item`, `collection_item`); `_defaults_by_course` already applies the placement value for the course that places the part. Placements are `ContentCollectionItem` rows with due keys (`due_date`, `due_time`, `due_days_after_registration`, `no_due_date`). The learner interface needs no extra work for per-placement dates: it keys everything by `collection_item.pk`. (I could not find the done spec directories by `*deadlines*` glob; only `spec_dd/3. done/2026-02-19_19:25_deadlines/` and `spec_dd/1. next/deadlines/research_*.md` exist; glossary and product docs are the authority.)
- `policy.py`: `ResolvedDeadlinePolicy(mark_overdue, close_items, end_course_access, notify_educators, grace_window: timedelta, after_access_ended, sources)`; `LayeredDeadlinePolicy` layers registration > cohort > organisation > course > site > settings; `get_deadline_policy()` (loader.py) -> `resolve(record)` / `resolve_for(records)` (bulk). Defaults: only `mark_overdue` on.
- `consequences.py`: `shows_overdue(resolved, policy, completed, now)` (= policy.mark_overdue and is_overdue), `close_instant`, `is_closed`, `access_end_instant`, `has_access_ended`.
- `templatetags/deadline_tags.py`: `{% local_time dt %}` simple_tag -> `<time datetime=UTC x-data="localTime" data-show-zone=...>` with site-zone server text (`site_zone_text`, `freedom_ls/site_aware_models/time_zones.py`); Alpine `localTime` in `freedom_ls/base/static/base/js/alpine-components.js:728` rewrites into the browser's zone; zone label only when `show_time_zone_to_learners` (SiteTimeZoneConfig, `site_aware_models/models.py:202`) is true; context var set in `learner_interface/views.py:792`. Any new date text MUST go through `local_time` (no `|date` filters) and the template needs `show_time_zone_to_learners` in context. Note the design's "23:59 SAST" and "Today 23:59" tile: localTime output format is whatever the Alpine component produces; check its formatter (alpine-components.js:728) before assuming time-only or "3 days left" formatting is available.

Hard vs soft: there is no per-deadline hard/soft flag. The "consequence" is a POLICY per record (not per deadline): `mark_overdue` (soft "Missed deadline" mark), `close_items` (+`grace_window`) -> item CLOSED, `end_course_access` -> access ended. The design's per-deadline "Target date / Marked late / Locks" taxonomy (key__key.png) maps onto record-level policy, not per-deadline authored data. Design also shows "late penalty 10%/day", "Late submissions accepted until 06 Mar": not in the system (product doc: no penalties, no extensions, no reminders).

## 2. How the learner interface exposes it today

`freedom_ls/learner_interface/utils.py`
- `get_course_index(user, course, current_index, *, can_access_content, course_progress, course_deadlines, deadline_policy, now, access_ended_outline)` -> list of dicts; leaf rows (topics/forms, including a CoursePart's children) carry `**DeadlineKeys`: `collection_item_id, due_at, is_overdue, closes_at, is_closed` (`_deadline_keys`, utils.py:630). CoursePart rows have NO deadline keys, only `children`, `status` (derived via `derive_part_status`), `contains_current`. Statuses: BLOCKED/READY/IN_PROGRESS/COMPLETE/FAILED/CLOSED.
- `_deadline_keys`: completed row never overdue/closed; BLOCKED row never closed; `closes_at` only set if closed or still in the future.
- Helpers: `current_entry(course_index)`, `next_entry`, `previous_entry`, `current_entry_status`, `_item_rows`.
- `get_course_index` takes `now` (testable); rows are plain dicts.

`freedom_ls/learner_interface/views.py`
- Dashboard card data: `_annotate_registered_courses` (views.py:360) bulk-resolves `course_deadlines_for(records)` and `get_deadline_policy().resolve_for(records)` once, then `_annotate_next_up` -> `get_course_index(...)` -> `_card_deadline_line` (views.py:164) which stamps on the Course: `missed_deadline` (earliest past, unfinished `CardDeadline`), `next_deadline` (earliest upcoming), `access_ends_at`, plus `next_up_title/url`. `CardDeadline(title, due_at, is_overdue, status, closes_at, is_closed)` frozen dataclass. Deadlines are withheld (`None`) when the backend says no content access; access-ended courses show "Access ended" not a deadline line. Completed courses carry no line (`_annotate_completed_courses`). Missed wins over next (a design with both a missed and a next band would need both; current model chooses one).
- Player: `_player_course_index` (views.py:1350) passes `_deadlines_or_none` and `_deadline_policy_or_none` (views.py:797-810) -> `chrome` context (`_player_chrome`-style dict around views.py:1627-1690) with `course_index`, `current_entry`, `course_progress`; `hide_outline_panel` for ended learners with no outline. Closed gating at views.py:1247 (`course_deadlines(...).items.get(collection_item.pk)`) and 2105 (`current_entry_status == CLOSED` -> `course_item_closed.html`, which says "Closed on {% local_time entry.closes_at %}").
- NOT currently in player context: the course time limit (`CourseDeadlines.time_limit`), a policy object, `now`, any "next deadline for the whole course" value, a count of deadlines ("All 7"), urgency tier, time-left. `_deadlines_or_none` is only resolved when needed on some paths (views.py:965-977 resolves only if `close_items`); the player path resolves always.

## 4. Existing urgency/state logic and gaps

Existing: overdue (`is_overdue`, gated by `mark_overdue`), closed (`is_closed`, `closes_at`), completed (never overdue), access ended, no-deadline (NONE). "Past" for the card = `due_at <= now` regardless of mark.
Missing (the design's urgency tiers in `DeadlinesPlayer.jsx`/`Deadlines.jsx`: `dlTone`: overdue (days<0), today (days==0), soon (<=7 days), upcoming (>7)): no "due today", "due soon" or "time left / N days left" logic exists anywhere; no threshold constant. This must be new pure code (suggest next to `deadlines/consequences.py` or in `learner_interface/utils.py`), computed in the SITE zone for "today" vs browser zone (local_time rewrites into browser zone client-side, so server-side "today"/"3 days left" could disagree with the displayed local date; a risk to resolve in the spec). "Completed late" does not exist (no completion-vs-deadline comparison stored); not required by the idea.
Glossary / copy rule (domain-glossary SKILL.md line 75, docs/product/learner-experience.md:291-308): learner-facing copy says "Deadline" and "Missed deadline", NEVER "Due" or "Overdue". The design's labels "Due today", "Due 02 Mar - 3 days left", "Overdue - was due 25 Feb", "Course due", "was due" CONFLICT; the spec must use "Deadline"/"Missed deadline" wording (and "Closed" when closed) and keep text minimal (idea says so). The design's duration text ("1h 20m", "14 hrs", "~12 min remaining", "5 / 8 mods", "Bookmarks", "All 7 ->", "All deadlines", "Practical/Reading" tags, "SAST" label, hero tags) is not deadline data: out of scope; "All N" links to the deferred upcoming-deadlines page which does not exist (do not build a link).

## 9. Conflicts and gaps summary

1. Copy: design says "Due"/"Overdue"; project rule says "Deadline"/"Missed deadline". Project wins.
2. Urgency tiers (today / within 7 days / later), "N days left", "Due today 23:59" tile: no existing logic; new derived state needed; threshold (7) is a design number, not a project value (a spec decision). Server "today" (site zone) vs client-rendered local zone mismatch.
3. Hard/soft/target taxonomy (target date / marked late / locks, plus penalties) is not per-deadline data; only record-level policy exists (mark_overdue, close_items+grace, end_course_access). Show "Closed"/"Closes <date>" only where the data exists; no penalty text.
4. Module (CoursePart) rows have no deadline of their own; design shows module-level dates and "Module 3 due today". Needs an aggregate or leave modules blank. Also "Module 3 - Pre-flight checklist" in the next-deadline card names a module; the system's deadline holder is a topic/form placement (title = item title) or the course time limit ("Course").
5. Course card: a deadline band needs a new slot in `cotton/course-card-shell.html` (`course-row-shell.html` shares `course_deadline_line.html`); byline overlap with the hero; current model gives either missed OR next, plus separate `access_ends_at` line; band for "no deadline" (design shows "No deadline" footer, "Locks", "Marked late" footers) is not a requirement of the idea; completed courses and not-registered cards carry none.
6. Player next-deadline card: needs a course-wide "next" selection (earliest open leaf deadline or time limit, missed vs upcoming) not currently computed for the player (it exists only as `_card_deadline_line` in views.py for the dashboard: reuse/extract it rather than duplicate; it takes `flat` rows + `CourseDeadlines` + policy + `now`, all available in the player). "All 7 ->" link and the count have no target: drop.
7. Header: `header_extra` sits above the title; design hd-b puts the card to the right of the title; `c-content-header` + `partials/page_title.html` layout decides feasibility. `data-testid="player-item-deadline"` should be kept or updated with tests.
8. Outline panel tablet/mobile: same dialog markup; design's separate tablet docked layout is not an existing breakpoint behaviour. Mobile sheet is a bottom sheet with the same `sidebar_content`, so one markup change covers all three.
9. `HTMX`: the toc region is OOB-refreshed on Previous/Next; next-deadline card must be inside `#course-toc-region`; the header card is in the main response.
10. Icons: no semantic calendar/flag/hourglass/lock-key/clock-countdown; map to `deadline`, `warning`, `error`, `locked`, `info` or drop.
11. Accessibility existing conventions: `forced-colors:border` on chips, sr-only status text, closed state not told by colour alone: keep when adding colour-coded rows.
12. Query budget: stay within existing ceilings by reusing resolved `course_index`/`CourseDeadlines`/policy; no new queries.
