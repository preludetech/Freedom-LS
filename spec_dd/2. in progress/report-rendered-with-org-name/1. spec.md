# Spec: Reports rendered with the organisation's brand

## 1. Summary

Cohort progress reports currently render the **site's** logo and name as the only brand on the
document. This change makes the **organisation's** name and logo the primary brand on the report
cover, and demotes the platform to a small "Powered by &lt;site&gt;" attribution mark that appears
on the cover band and in every interior page footer.

Alongside the branding change, three smaller things follow from it:

- **PDF document metadata** — `Author` set to the organisation, `Creator` to the site, so the
  file's document-properties panel agrees with its cover.
- **The download filename** carries the organisation name (the *stored* filename stays pk-derived
  and identity-blind).
- **The footer identity line stops naming the site**, because "Powered by &lt;site&gt;" now sits
  beside it in the same footer row.

No model changes. No migrations. This is render-layer and application-layer work only — every
piece of data the feature needs already exists on `Organisation`
(`freedom_ls/organisations/models.py:29,31-35,39`).

## 2. Why this matters

A cohort progress report is a document an organisation shows to somebody else — a learner, an
employer, an accreditation body, a funder. When that document leads with the platform's brand, it
reads as the platform's document about the organisation's learners. When it leads with the
organisation's brand, it reads as the organisation's own training record, which is what it
actually is.

The organisation's brand leads. The platform is attribution, not the headline.

The attribution still matters, and stays visible: a progress record shown to a third party benefits
from a legible provenance mark, and a single extracted or forwarded page should still say where it
came from.

## 3. Scope

### In scope

- Organisation name and logo as the primary brand on the report cover.
- "Powered by &lt;site&gt;" on the cover band and in every interior page footer.
- Suppression of that mark for the site's auto-created `is_default` "house" organisation.
- Reading the organisation logo from media storage safely, on any storage backend.
- A deliberate `data:` URI branch in the report's restrictive WeasyPrint URL fetcher.
- Wordmark fallback when an organisation has no logo.
- Deterministic handling of long organisation names on the cover and in the footer.
- PDF document metadata (`Author`, `Creator`).
- Organisation-named download filename via `Content-Disposition`.
- Footer identity line re-ordered to lead with the organisation and drop the site.

### Out of scope (unchanged from the idea)

- **Any setting to suppress the platform attribution.** Comparable products make this a paid-tier
  removal; FLS is not selling tiers, and a visible mark supports provenance for training records
  shown to third parties. A toggle can be added later without breaking anything.
- **A low-resolution warning** when a too-small logo is uploaded. Worth revisiting — see the
  legibility arithmetic in §11.3 — but there is no feedback mechanism today and building one is a
  separate piece of work.
- **An organisation descriptor/strapline field.** The reference design renders one
  (`build_report.py:96`, `"SACAA ATO 0231"`), and it is genuinely useful for a regulated training
  provider, but it is a new field with an ambiguous definition (accreditation number? tagline?
  legal name? — four different typographic treatments implied by one freeform field). The
  reference design is not a scope document. **The cover layout must not reserve permanent vertical
  space for a line that is not shipping.**
- **PDF/UA tagging.** A document-wide accessibility track with its own validation burden.
- **A per-organisation brand colour.** No such field exists (`organisations/models.py` has only
  `name`, `slug`, `logo`, `is_default`). The organisation wordmark renders in the deployment's own
  `--color-primary` token — the same colour the platform's UI uses. Stated explicitly so the spec
  does not imply organisations get a colour they do not have.

## 4. Decisions taken

### 4.1 Carried over from idea refinement

**Where the platform mark appears.** Both the cover band and every interior page footer, at the
existing small/muted treatment. A prominent one-time mark at first contact, plus a quiet one that
survives a single page being extracted, printed or forwarded — which is what a report used as a
progress record needs.

**The house-organisation case.** Every Site auto-creates exactly one `is_default` Organisation
(`organisations/models.py:36-39`). For cohorts sitting in that house org, the "Powered by
&lt;site&gt;" mark is **suppressed** — the primary brand already is the platform, and showing both
says the same thing twice. `is_default` is already in memory (`load_cohort()` does
`select_related("organisation")`, `freedom_ls/reports/indexes.py:159-165`), so detecting this costs
no extra query.

*Accepted caveat:* an admin can rename the default organisation so it no longer matches the site
name, and this rule suppresses the mark anyway.

**Attribution is always on.** No setting, per §3.

**Logos are contained, never cropped or distorted.** An organisation's mark is an identity asset;
clipping a wordmark's descenders or a badge's outer ring reads as broken rather than styled. This
pattern already exists in the codebase for both the site logo (`print.css:494-499`) and the
on-screen organisation chip (`course_organisation_chip.html:22-25`).

**The organisation logo is not placed on the solid primary-colour cover band.** It sits on the
white cover area; the band carries only the small "Powered by" text. This is what makes a
protective plate behind the mark unnecessary. **If a later design ever moves an uploaded logo onto
a coloured fill, that decision has to come back** — a dark-on-transparent logo would partly
disappear into the band. (The codebase already has the plate pattern for exactly this reason, at
`course_organisation_chip.html:22`, `bg-surface`; it is deliberately not needed here.)

### 4.2 Confirmed with the user during spec authoring

### 4.3 Decided during spec authoring, from research

**"Powered by" is text only, everywhere.** Never the site's logo graphic, in the band or the
footer. The reference design never puts an image in either slot
(`build_report.py:860-861`, `934-938`). A footer-scale logo would reintroduce exactly the
storage/allowlist complexity that is this feature's main risk, for a mark whose entire purpose is
to be minimal. Whether it should ever become a graphic stays an open product question, not part of
this change.

**The footer "Powered by" gets its own `@bottom-center` margin box**, rather than being folded into
the existing `.footer-identity` string. FLS's base `@page` has no centre box today
(`print.css:34-65`); the reference design's four-box shape (`build_report.py:853-864`) is the
better one, because the two strings never fight over one line's width and the identity line can
grow without displacing the attribution.

**Every name reaching an `@page` margin box goes through a running element**, never a CSS
`content: "…"` string. `.footer-identity` already works this way
(`report.html:30-40`, `print.css:106-116`) precisely because organisation and cohort names are
admin-typed data that must be HTML-escaped, not interpolated into a stylesheet.
`site_name`/`HEADER_TITLE` is admin-configured too (`site_aware_models/config.py`), so the new
"Powered by" box must use the same mechanism. **The reference design's
`string-set`/`Template.substitute()` approach is explicitly rejected** — its text *shape* is worth
adopting, its mechanism is not.

**`@page :first` is kept; the reference design's named `cover` page is rejected.** FLS's choice is
deliberate and documented (`print.css:69-89`): naming the page would force a break before the
cover, and since `.footer-identity` must appear in the DOM *before* the cover include
(`report.html:38-41`), that leaves a blank page in front of it. The reference design avoids this
only because it has no running element ahead of its cover. Do not "align" FLS toward it.

**A vanished logo file falls back to the wordmark; it does not raise.** This is deliberately
*different* from how the site logo behaves — `_resolve_logo()` raises `ReportRenderError` when a
configured static path cannot be resolved (`render.py:162-173`, and its docstring explains why: a
static path is deploy-time configuration, and a broken one is a misconfiguration that should be
loud). An uploaded media object is not deploy-time configuration: it can drift at runtime,
independently of any FLS deploy. A report that renders with the organisation's name as a wordmark
is a correct report; a report that fails to generate because a logo object went missing is not.

## 5. The organisation logo pipeline (the hard part)

The organisation logo is not the same kind of thing as the site logo, and this is the main
correctness risk in the whole feature.

The site logo is a **static** asset resolved through the staticfiles finders to a local path
(`render.py:43-61`). `Organisation.logo` is an `ImageField` on **media storage** with no `storage=`
kwarg (`organisations/models.py:31-35`), so it resolves to `STORAGES["default"]` — which in
production is `storages.backends.s3.S3Storage` whenever `AWS_STORAGE_BUCKET_NAME` is set
(`config/settings_prod.py:112-141`, `freedom_ls/deployment/storage.py:38`), serving **private
signed URLs** by default (`querystring_auth=True`).

### 5.1 The failure this spec exists to prevent

A naive `organisation.logo.path` → `file://` implementation **works in development and breaks in
production**. `Storage.path()` raises `NotImplementedError` by default
(`django/core/files/storage/base.py:131-137`) and `S3Storage` does not override it.

**This belongs in the acceptance criteria explicitly** (§12.2), not left to be discovered against a
real S3-backed deployment.

Fetching the logo over its signed `https://` URL at render time is also rejected: the URL is
time-limited, the render happens in a background task with no fixed latency bound, and it would
mean teaching the restrictive fetcher to reach the network — the one thing it exists to prevent.

### 5.2 The approach

Read the logo bytes through Django's **storage API** on the **gathering** side and embed them as a
base64 `data:` URI. This behaves identically on local disk and on S3, because the bytes are read
before WeasyPrint ever sees a URL.

The storage read belongs in `gather.py`, which is already allowed to touch the ORM and storage. The
render layer must keep receiving an already-resolved value — `render.py` does no ORM access by
contract (`render.py:1-12`, `report_data.py:1-8`). Note that this contract is documented in
docstrings but **not mechanically enforced** — no lint rule or import check catches a violation, so
this is a code-review responsibility.

Recommended shape, in `gather.py` or a helper it calls:

```python
_LOGO_MIME_TYPES: dict[str, str] = {
    "PNG": "image/png",
    "JPEG": "image/jpeg",
    "WEBP": "image/webp",
}


def resolve_organisation_logo_data_uri(organisation: Organisation) -> str | None:
    if not organisation.logo:
        return None

    try:
        with organisation.logo.storage.open(organisation.logo.name, "rb") as handle:
            raw = handle.read()
    except OSError:
        return None

    try:
        image_format = Image.open(io.BytesIO(raw)).format
    except (OSError, UnidentifiedImageError):
        return None

    mime_type = _LOGO_MIME_TYPES.get(image_format or "")
    if mime_type is None:
        return None

    encoded = base64.b64encode(raw).decode("ascii")
    return f"data:{mime_type};base64,{encoded}"
```

Points that are load-bearing, not stylistic:

- **`organisation.logo.storage`, not an imported `default_storage`.** Matches the codebase's
  existing idiom (`get_reports_storage()`, `reports/models.py:36-41`) and keeps working unchanged
  if `Organisation.logo` ever gets its own storage alias.
- **`storage.open()`, not `field.open()`.** `FieldFile.open()` caches the handle on the instance;
  `gather.py` holds a live `cohort.organisation` that nothing else in the pipeline should observe
  mutating mid-render.
- **A context manager**, so the handle (and, for `S3File`, the underlying HTTP response) is
  released even if `.read()` raises.
- **The MIME type comes from a fresh Pillow decode, not the stored filename.**
  `organisation_logo_upload_to` derives the stored extension from the *uploaded* filename's suffix
  (`organisations/models.py:17-25`) while `validate_organisation_logo` validates the *decoded*
  format separately (`validators.py:30-82`) — nothing enforces the two agree, so a `.png`-suffixed
  file containing genuine JPEG bytes passes both. Sniffing the bytes is also the right defense
  against the gap below.
- **`except OSError` is correct on both backends, verified from source.** `S3Storage._open()`
  normalises a 404 to a plain `FileNotFoundError` (`storages/backends/s3.py:529-537`) and re-raises
  any *other* `ClientError` unchanged. So a vanished object falls back to the wordmark on both
  local disk and S3, while an S3 outage or credentials failure propagates — deliberately. That
  propagation is consistent with the pipeline's existing behaviour: `gather_cohort_report_data()`
  already issues ORM queries whose infrastructure failures are not caught by `tasks.py`'s
  narrow `except (ReportRenderError, ReportTooLargeError, Cohort.DoesNotExist)` (`tasks.py:57`).
  This feature introduces no new class of gap there.
- **Pillow's exception tuple matches the existing validator's** — `(OSError,
  UnidentifiedImageError)`, exactly as `validators.py:66` already writes it. Do not infer a class
  hierarchy that the repo's own code declines to assume.
- **No bare `except Exception`.** Both failure classes are enumerated above.

### 5.3 A validation gap the render path must tolerate

`validate_organisation_logo` is wired as a field validator (`organisations/models.py:34`), and
Django runs field validators only via `full_clean()` — which a `ModelForm` save does, but a bare
`Organisation.objects.create(logo=...)`, a management command, or a data migration does **not**. An
unvalidated file can therefore reach storage.

Sniffing the format at read time closes this: a file that is not really a PNG/JPEG/WebP fails the
`_LOGO_MIME_TYPES` lookup and falls through to the wordmark, rather than being trusted or embedded
as garbage. **The render path must degrade gracefully — never raise, never embed garbage — for a
logo that bypassed upload-time validation.**

### 5.4 Widening the restrictive URL fetcher

`_restrictive_url_fetcher` (`render.py:203-247`) accepts only `parsed.scheme == "file"` against an
exact-file allowlist and refuses everything else (`render.py:237-246`). Verified against the
installed WeasyPrint 69 source: **`data:` URIs do not bypass the custom fetcher** — they hit this
function and are currently refused. So a deliberate, reviewable `data:` branch is required.

That boundary exists because reports render author-supplied text, and it is locked in by a test
that refuses even a *sibling file in an allowed directory*
(`test_render.py:258-266`).

**Framing for reviewers:** allowing `data:` is a change in the *shape* of the allowlist, not a
weakening of it. A `data:` URI carries its own bytes rather than pointing at something external, so
permitting the scheme cannot expand the fetcher's reach. The fetcher goes from "an allowlist of
specific named local files" to "an allowlist of specific named local files, plus one scheme whose
payload can only ever be its own bytes." Still zero externally-resolved resources.

The branch must nonetheless be narrow to what FLS itself produces, as defense in depth against a
future bug in FLS's own code:

1. **Scheme exactness** — `parsed.scheme == "data"`, added as an `elif` beside the existing `file`
   branch.
2. **Mediatype allowlist** — exactly the three types `_LOGO_MIME_TYPES` emits (`image/png`,
   `image/jpeg`, `image/webp`). Reject `image/svg+xml` (already banned at upload) and everything
   else, so the branch reads to a reviewer as "the mediatypes this feature emits", not "whatever
   `data:` allows".
3. **Base64 required** — refuse the percent-encoded form. FLS never generates it.
4. **Size cap on the decoded payload** — reuse `organisations.validators.MAX_BYTES` (2 MiB,
   `validators.py:23`), checked after decode, raising `FatalURLFetchingError` (loud, matching this
   module's philosophy) rather than truncating. The upload validator already bounds today's only
   caller; this cap protects a *future* caller that reuses this fetcher for a different, unvalidated
   image source without re-deriving the reasoning.

After validation, delegate to `default_url_fetcher(url)`, mirroring exactly what the `file` branch
does. (Implementation should confirm WeasyPrint's default fetcher handles `data:` as expected; if
not, construct the response dict directly from the decoded bytes and mediatype.)

**Accepted, documented non-change:** the existing `file` branch compares the scheme without
lower-casing, so a `FILE:`/`DATA:` URI matches neither branch and falls through to the refusal.
Schemes are case-insensitive per RFC 3986 §3.1, so this is a robustness nit — but FLS never
constructs an uppercase scheme itself, no functional bug exists, and the new branch matches the
existing style rather than diverging from it. Left as-is deliberately.

**Payload size in the PDF.** Worst case is ≈2.7 MiB of base64 text for a 2 MiB logo. WeasyPrint
de-duplicates images at the PDF object level keyed by URL string, so a logo referenced on every
page is still embedded **once**.

## 6. Render-layer contract changes

`CohortReportData` (`report_data.py:221-238`) is a frozen dataclass tree of primitives and nested
frozen dataclasses. It has **no existing precedent for a resolved file/image reference** — this
feature adds the first one, so the shape sets precedent.

Replace the flat `organisation_name: str` with a nested brand dataclass, and add one flag:

```python
@dataclasses.dataclass(frozen=True)
class OrganisationBrand:
    name: str
    logo_data_uri: str | None
    wordmark_size_class: str   # "full" | "condensed"; meaningful only when logo_data_uri is None
    footer_name: str           # deterministically truncated for the footer identity line


@dataclasses.dataclass(frozen=True)
class CohortReportData:
    ...
    organisation: OrganisationBrand
    show_powered_by: bool
    ...
```

Rationale:

- **Nested rather than four more flat fields**, matching the file's existing nested style
  (`CourseSection`, `AttentionList`, `LearnerDetail`).
- **`organisation_name` is replaced, not kept alongside.** Keeping both `organisation_name` and
  `organisation.name` would state the same value twice, against the repo's "avoid repeating code"
  convention. The churn is small and contained: `gather.py:741`, `report.html:39`,
  `title_page.html:36`, `test_gather.py:960-970`, and the builders at
  `report_data_builders.py:92-108`.
- **`show_powered_by` is top-level, not on the brand**, because it is a fact about the platform's
  attribution, not about the organisation. It is computed in `gather.py` as
  `not cohort.organisation.is_default` — zero extra queries, since `is_default` is already loaded.
- **`site_name` stays** on `CohortReportData`. After this change it is used only by the "Powered
  by" mark and the PDF `generator` metadata, but both still need it.
- **`wordmark_size_class` and `footer_name` are computed in `gather.py`**, not in the template.
  The render layer walks an already-resolved tree; deterministic text decisions are Python's job
  and are unit-testable in isolation.

**Every test that constructs report data through `report_data_builders.py` breaks at construction
time unless defaults are added there first** — do that before touching anything else.

## 7. Cover layout

### 7.1 Brand slot

- The block moves to the **top-left** (§4.2 #1). `.cover-accent`'s `margin: 8pt 0 0 auto`
  (`print.css:507-514`) becomes a left-edge margin so the rule still sits under the identity it
  belongs to.
- **With a logo:** an `<img>` in the slot, `max-height: 16mm; max-width: 70mm;`, no explicit
  `width`/`height` attributes. WeasyPrint preserves intrinsic aspect ratio under that combination
  without needing `object-fit` — this is already the working pattern at `print.css:494-499`, and
  `object-fit` is browser-only insurance the report does not currently rely on.
  - A wide banner logo is bound by the 70mm width cap; a square crest is bound by the 16mm height.
    Neither is cropped; both simply resolve to different visual sizes in the same box, which is the
    correct behaviour for contain-fit and needs no per-aspect-ratio special-casing.
  - `alt=""`. The image is decorative in the accessibility sense — the organisation's name is
    stated in the cover metadata list regardless. See §11.4 on what `alt` does and does not do in
    an untagged PDF.
  - The logo is left-aligned in the slot and vertically centred within its fixed height.
- **Without a logo:** the organisation name set as a **wordmark** — large, in
  `var(--color-primary)`, in the slot the logo would have occupied.
  - **Not the initials monogram.** The existing on-screen organisation chip uses one
    (`course_organisation_chip.html:27-35`) and it reads correctly as an avatar at UI scale, beside
    other UI, on a busy page. A report cover is a single-purpose page with nothing else competing;
    at that scale, in the one slot that would otherwise hold a full mark, a small monogram badge
    reads as a broken-image placeholder rather than an identity mark. `Organisation.initials`
    remains available as data and stays appropriate for smaller, secondary placements — it must not
    be rendered in this slot at any size.
- **The slot always has content**, so it never needs to collapse: an organisation always has a
  name, and the wordmark fills the slot whenever the logo does not. This differs from the current
  site brand block, where both parts are optional and `print.css:489-490` therefore notes that
  "neither may reserve space" — that reasoning does not carry over to the organisation slot.

### 7.2 Long organisation names on the cover

`Organisation.name` allows up to 150 characters (`organisations/models.py:29`). CSS cannot help
(§11.1), so `gather.py` picks a size class from the name and the CSS gives each class a line
budget:

| Class | Size | Line budget | Applies when |
|---|---|---|---|
| `full` | ~18pt | up to 2 lines | name ≤ ~42 characters |
| `condensed` | ~13pt | up to 3 lines | name ≤ ~87 characters |
| `condensed` + truncation | ~13pt | 3 lines | longer — truncate to the budget and append `…` (U+2026, one character, not three periods) |

The character thresholds above are **starting values**, derived from the 70mm slot width and the
average advance width of the display face at each size. They must be tuned against a real render
during implementation and then **pinned by tests**, so the numbers the code ships with are the ones
that were actually looked at. QA must include a long-name organisation.

### 7.3 Cover band

The band (`print.css:574-583`, `position: absolute; bottom: 0; height: 18mm;
background: var(--color-primary)`) currently carries `.band-site` — the site name at 11pt/700
(`print.css:584-588`). It becomes the "Powered by &lt;site&gt;" slot, as **two tiers**, following
the reference design's `.pby`/`.band-brand` split (`build_report.py:935-937`):

- `Powered by` — ~7.5pt, the band's muted-on-primary treatment
- the site name — ~10–11pt, bold

The two-tier treatment matters: setting the whole string at one uniform size makes the mark read as
merely *differently labelled* at the same weight as the brand above it, rather than visibly
subordinate to it.

**When `show_powered_by` is false, the band renders empty** — the solid colour block stays (it is
part of the page's composition, not a container for the mark), and nothing is written on it.

## 8. Interior page furniture

`@page :first` suppresses every margin box on the cover (`print.css:75-89`), so everything in this
section applies from page 2 onward.

**Footer row, three boxes:**

| Box | Content | Treatment |
|---|---|---|
| `@bottom-left` | `organisation · cohort · Cohort progress report` — a running element, `.footer-identity` | 7pt, `var(--color-muted)` (unchanged, `print.css:106-116`) |
| `@bottom-center` | **new** — `Powered by <site>`, a running element | 7pt, `var(--color-muted)` — the same "document furniture" register as its neighbours |
| `@bottom-right` | page counter (unchanged) | unchanged |

The identity line's organisation name is the pre-truncated `organisation.footer_name` (§6). Budget:
**40 characters, then `…`** — again a starting value to be tuned against a real render and pinned
by a test. The line may wrap within its margin box; the page's bottom margin is 16mm
(`print.css:34-65`), which is ample at 7pt. **QA must confirm the wrapped line does not collide
with the centre box.**

The reader of a single extracted page loses the tail of a very long organisation name. That is the
accepted trade-off for a footer whose height never changes: the cover always shows the name in
full, and it also appears in full in the cover metadata list.

**When `show_powered_by` is false**, the `@bottom-center` box is empty and the other two boxes are
unaffected.

The new box's content must be a **running element**, not a CSS string (§4.3).

## 9. PDF document metadata

Only `<title>` is set today. WeasyPrint's mapping, verified against the installed 69.0 source
(`weasyprint/html.py:339-409`, `weasyprint/pdf/__init__.py:250-270`):

| PDF field | Source | This change |
|---|---|---|
| `/Author` | `<meta name="author">` | **set to the organisation name** |
| `/Creator` | `<meta name="generator">` | **set to the site name** |
| `/Title` | `<title>` | unchanged |
| `/Producer` | written unconditionally by WeasyPrint | not settable — will read `WeasyPrint 69.0` |
| `/Lang` | `<html lang>` | unchanged, stays `en` |

**Exactly one `<meta name="author">` tag.** WeasyPrint keeps *every* `author` meta tag and joins
them with `", "` into the classic `/Author` info-dict field
(`weasyprint/pdf/__init__.py:256`) — it does not take the first and discard the rest. A second tag
(for instance adding the site as a second author) would land in a reader's document-properties
panel as `"Northside College, Bright Academy"`. Do not add one.

`/Lang` stays `en` deliberately: an organisation name in Cyrillic does not imply the report's body
text — which is in FLS's own UI language — is in that language.

## 10. Download filename

`download_report_view()` currently builds
`f"{slugify(report.cohort.name)}-progress-report.pdf"` (`views.py:118`) and passes it to
`FileResponse(..., as_attachment=True, filename=filename)` (`views.py:123`).

Changes:

```python
report = get_object_or_404(
    GeneratedReport.objects.select_related("cohort__organisation"), pk=object_id
)
...
filename = (
    f"{slugify(report.cohort.organisation.name, allow_unicode=True)}-"
    f"{slugify(report.cohort.name, allow_unicode=True)}-progress-report.pdf"
)
```

- The queryset's `select_related("cohort")` (`views.py:111-113`) must become
  `select_related("cohort__organisation")`, or every download issues one extra query. The same
  pattern already exists at `views.py:56`.
- **`allow_unicode=True`** per §4.2 #6. `slugify` strips everything that is not a word character,
  whitespace or a hyphen, so a literal `/` in an organisation name is removed before it can reach
  `FileResponse` — which matters, because `FileResponse.set_headers()` runs `os.path.basename()` on
  the filename (`django/http/response.py:607`) and would otherwise silently discard everything
  before the last `/`.
- **Do not hand-build the `Content-Disposition` header.** Django's
  `content_disposition_header()` (`django/utils/http.py:370-395`) already implements RFC 6266 §5's
  decision tree and is CR/LF-safe by construction: any control character fails its quotable-character
  regex and falls to the percent-encoded `filename*=utf-8''…` branch. Passing a plain string to
  `FileResponse(filename=...)` gets all of this for free.
- **No separate length cap needed** — `slugify` never lengthens a string, and
  `Organisation.name` is already bounded at 150 characters.

*Accepted limitation:* Django emits either `filename="…"` **or** `filename*=utf-8''…`, never both,
while RFC 6266 §5 recommends emitting both so a user agent without RFC 5987 support still gets an
ASCII fallback. No browser in practice is affected. Hand-rolling a dual-form header would mean
re-implementing the injection-safety logic Django already provides. Accepted as-is.

**The stored filename does not change.** `report_upload_path()` stays pk-derived and
identity-blind by design (`reports/models.py:24-33`); only the `Content-Disposition` name carries
the organisation.

## 11. Known consequences and accepted limitations

These should be stated plainly in the spec rather than left implicit.

### 11.1 CSS cannot truncate under WeasyPrint

Verified against the installed WeasyPrint 69.0: `text-overflow` appears **nowhere** in the package
— it is an unrecognised declaration, silently dropped by the CSS parser exactly like a typo, with
zero visual effect. `block-ellipsis` is recognised at parse level
(`weasyprint/css/properties.py:272,309`) but has no layout implementation wired up, so it is a
different flavour of no-op.

This is stronger than "unreliable": **neither property does anything.** Every truncation decision in
this feature is therefore deterministic Python, computed in `gather.py` and asserted in pure unit
tests.

### 11.2 Generated PDFs are immutable snapshots

A report is rendered once and stored; nothing re-renders it. An organisation that uploads a new
logo, or is renamed, **does not retroactively change reports already generated.** This is already
true of the current design — the spec states it plainly so it is not discovered later as a surprise.

### 11.3 Raster logos only, and a print-legibility floor

SVG is deliberately blocked at upload (`validators.py:21-22`, extension allowlist plus a Pillow
format check) because it is XML that can carry scripts. Nobody should expect vector-crisp marks in
the PDF, and this is not revisited here.

The legibility arithmetic, stated as a fact the spec can quote (the *warning* it would justify is
out of scope, §3):

> A logo displayed at 12mm tall needs ≈142px of source height to print at the 300dpi "full quality"
> reference point, or ≈71px at the 150dpi "acceptable minimum". FLS accepts uploads from 64×32px
> (`validators.py:25`) — a logo at the accepted minimum resolves to roughly 68dpi in the slot, below
> even the 150dpi floor.

At the 16mm slot this spec adopts, the required source heights scale up proportionally (≈190px at
300dpi, ≈95px at 150dpi).

Existing protections need no change: the 2 MiB cap (`validators.py:23`), the 4000px dimension cap
(`:24`), and Pillow's decompression-bomb guard — which FLS already escalates from warning to error
(`validators.py:56`), closing the band Pillow itself leaves as a mere warning.

### 11.4 `alt` text does nothing in an untagged PDF

FLS's PDFs are untagged (no `pdf_variant` is passed, `render.py:259-261`), so there is no structure
tree for `alt` to attach to and no generic viewer's accessibility tooling reads it. Setting
`alt=""` is still correct HTML, costs nothing, and is groundwork if PDF/UA is ever turned on — but
**this change must not be described as an accessibility improvement.** PDF/UA tagging is explicitly
out of scope.

What *does* help: the organisation's name is present as real text on the cover regardless of
whether a logo renders.

### 11.5 Non-Latin organisation names

The bundled fallback face is the full DejaVu Sans
(`freedom_ls/reports/static/reports/fonts/DejaVuSans.ttf`), last in every configured stack —
Inter (display), Source Sans 3 (body), Source Code Pro (mono)
(`freedom_ls/reports/config.py:91-97`).

Accepted limitation, to be stated in this wording:

> Organisation names in Chinese, Japanese or Korean script (Han, Hangul, Kana) render as
> missing-glyph boxes on the cover and in the footer. Every other script the fallback face supports
> — including Cyrillic, Greek, Arabic, Hebrew, Devanagari, Thai, Armenian and Georgian — renders
> correctly, in a fallback weight and style that will not visually match the display face.

This is a materially narrower gap than "non-Latin names do not render". Rarer scripts not listed
(Khmer, Myanmar, Tibetan, Sinhala, Mongolian) are unconfirmed and plausibly also absent.

Note the interaction with §10: a CJK organisation's *download filename* preserves its name
correctly even though its name does not render on the *cover*. Both behaviours are intended.

### 12.2 New tests

**The acceptance criterion that protects against the production break** (§5.1) is a storage double
whose `.path()` raises, mirroring `S3Storage` (which inherits `Storage.path()`'s default
`NotImplementedError`) while leaving `.open()`/`.save()`/`.exists()`/`.url()` real, so a render can
still complete end to end:

```python
class PathlessFileSystemStorage(FileSystemStorage):
    def path(self, name: str) -> str:
        raise NotImplementedError(
            "PathlessFileSystemStorage.path() was called -- the code under test used "
            "FieldFile.path or storage.path() instead of the storage API, which breaks "
            "on S3 in production."
        )
```

Wire it through a fixture overriding `STORAGES["default"]`, following the existing
`isolated_reports_storage` idiom (`reports/tests/conftest.py:15-31`).

| Test | Markers | Asserts |

**The three existing fetcher tests (`test_render.py:258-278`) must pass unmodified.** If any of
them needs to change to accommodate the new branch, the branch was not additive — that is the
review signal that the allowlist's shape was altered rather than extended.

### 12.3 Why a storage double and not `moto`/localstack

The acceptance criterion is narrow: *this code path never calls `.path()`, whatever backend is
configured*. A double that raises on exactly that method proves exactly that, faster and more
maintainably than standing up a fake S3. Proving S3's network behaviour (auth headers, bucket
routing) is `django-storages`' job, not this feature's.

### 12.4 QA scenarios

The QA fixture commands already support this work: `qa_create_report_fixtures.py` takes
`--organisation-slug` (lines 374-378) and reports logo presence in its summary (lines 434-435);
`qa_create_report_cohort.py` falls back to the default organisation (lines 589-592) and reports the
same (lines 776-780).

QA must cover: an organisation **with** a logo; an organisation **without** one (wordmark); the
**house/default** organisation (no "Powered by"); a **long** organisation name (both size classes
and the footer truncation); and a **non-Latin** name.

## 13. Success criteria

1. A report for a cohort in a normal organisation renders that organisation's logo, top-left, on
   the cover, contained and undistorted, with the platform reduced to "Powered by &lt;site&gt;" on
   the cover band and in every interior page footer.
2. An organisation with no logo renders its name as a wordmark in the same slot, and the cover
   reads as finished rather than broken. No monogram appears anywhere on the report.
3. A report for a cohort in the site's `is_default` organisation shows **no** "Powered by" mark, in
   either the band or the footer.
4. **The logo resolves through the storage API and never calls `.path()`** — proven by a test
   against a storage double whose `.path()` raises, so the implementation cannot pass in
   development while being broken on S3.
5. The three existing URL-fetcher tests pass **unmodified**, and the new `data:` branch accepts only
   base64 payloads of the three allowed image mediatypes under the 2 MiB decoded cap.
6. A missing, deleted, or invalid logo file falls back to the wordmark and the report still
   generates successfully.
7. The interior footer reads `organisation · cohort · Cohort progress report`, with the site named
   once per page — in the "Powered by" box only.
8. The generated PDF's document properties show the organisation as Author and the site as Creator,
   with exactly one author entry.
9. The download filename carries the organisation name, preserving its own script, with a valid
   `Content-Disposition` header in both the ASCII and non-ASCII cases. The stored filename is
   unchanged.
10. A 150-character organisation name renders without overflowing the cover slot or breaking the
    footer row, at thresholds pinned by tests and verified against a real render.
11. No migrations are produced by this change.

4. **DejaVu Sans coverage.** Described as Cyrillic/Greek/Arabic only. The shipped face is the full
   family and covers considerably more; the real gap is specifically CJK/Hangul/Kana (§11.5).
5. **On-screen organisation chip sizing.** Described as `h-8 max-w-32`; after the recent extraction
   and restack it is `h-16 max-w-48` with a `bg-surface` plate
