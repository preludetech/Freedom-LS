# Research: codebase (what spec 10 touches, reuses, conflicts with)

Read-only survey, nothing run. Paths relative to the repo root. Findings are from reading source on branch `educator-interface-10-reporting-dashboards`.

## 0. Headline findings

1. The panel framework is NOT a planned thing: it exists as the `freedom_ls/panel_framework/` app and the educator interface is already rebuilt on it (specs 1-7 and 9 are in the tree; the roadmap table lists only 8, 10, 11, 12 as unfinished). The idea's "spec 4 components", "spec 3 quick view", "spec 2 export hook" all exist. `spec_dd/3. done/` is empty/absent in this worktree, so "done" is inferred from code plus the roadmap table (only 8, 10, 11, 12 listed). `spec_dd/2. in progress/` holds only this spec (idea.md, todo.md).
2. The dashboard is a stub: `DashboardPanel` (title "Reporting") renders "On-screen reporting for {org} arrives in a later release." and `test_dashboard.py::test_dashboard_renders_the_reporting_placeholder` asserts that exact string (must be updated).
3. The cohort Overview tab already has a "Needs attention" panel that is a TODO placeholder, and a "Course completion" panel that uses a different (aggregate) definition of progress from the report's gather.
4. There is NO per-learner gatherer as a public function. `_build_learner_detail` in `reports/gather.py` is private and takes whole-cohort index bundles. Single-learner reuse means calling the loaders with `learner_ids=[one]`, which still needs cohort registrations (see section 6, risk R2).
5. Definitions of "learner in a cohort", "progress", "last activity" differ between the report and the educator interface (section 6). These are the main design risks.
6. App-dependency: `educator_interface` does not currently depend on `reports` (docs/app_structure.md). `reports` does not depend on `educator_interface` or `panel_framework`. A new edge `educator_interface -> reports` is acyclic but must be declared/approved (section 8).

## 1. `freedom_ls/reports/`

Meta ordering `-requested_at`. One-in-flight rule is a DB partial unique constraint `one_inflight_report_per_cohort` (`UniqueConstraint(fields=["cohort"], condition=Q(status__in=[pending, running]))`). There is no created-for-a-version/data-hash field; no retention (TODO in `signals.py`, do not delete).
- `tasks.py`: `_generate_cohort_report_task(report_id, site_id)` (`django.tasks` `@task()`), delegating to `generate_cohort_report(report_id, site_id)`: loads row by `pk`+`site_id`, sets running, calls `gather_cohort_report_data(str(report.cohort_id), site_id, requested_by_name=...)` then `render_report_pdf(data)`, saves file, status ready; catches only `ReportRenderError, ReportTooLargeError, Cohort.DoesNotExist` -> failed with `error_message=str(exc)`; `finally` marks a still-running row failed. Permission is `can(user, "freedom_ls_learner_management.download_cohort_report", cohort)` (from `learner_management.capabilities`). Download: `get_object_or_404`, same `can()`, 404 unless `status==ready and file`, filename `{org-slug}-{cohort-slug}-progress-report.pdf` via `slugify(allow_unicode=True)`, `FileResponse(as_attachment=True)`, `Cache-Control: private, no-store, must-revalidate`; `FileNotFoundError` -> 404. Both are tied to admin (`admin_view`, `ModelAdmin`); the educator-interface needs the create/enqueue and stream logic extracted into non-admin functions (CLAUDE.md: avoid repetition). `test_views.py` asserts the download query budget (`django_assert_max_num_queries(8)`).

Stays (idea says admin route stays).

Educator-interface scoped sibling: `cohorts_visible_to(user, organisation, capability=VIEW_COHORT)` (org-scoped; honours capability arg, so `capability="...download_cohort_report"` is possible, as `DELETE_COHORTMEMBERSHIP` is used elsewhere in `views.py`).

### Query shape of the gather (estimated from source, not measured)
Loader sequence in `gather_cohort_report_data`, each run once:
1. `load_cohort`: 1 query (select_related organisation).
2. `load_registrations`: 1 query (select_related course).
3. `load_roster`: 1 query (`CohortMembership` select_related `learner__user`); sorts in Python; raises `ReportTooLargeError` here.
4. `build_course_catalogue`: per registered course, `course.viewable_items()` -> `children()` traversal "memoized on the instance". Queries scale with number of courses and course structure (parts/collections), NOT with learners. Probably the largest unknown constant; `GATHER_QUERY_BOUND = 12` in `test_gather.py` is for one course with one quiz.
5. `load_progress_index`: `TopicProgress` (1 query, `values_list`, joins through `course_progress`) + `FormProgress` (1 query, `select_related("form","course_attempt__course_progress")`, ordered); this one hydrates every sitting as a model object (rows = learners x forms x attempts), the heaviest memory/CPU item.
6. `load_first_attempt_ids`: 1 query with a `Window(RowNumber)`.
7. `load_quiz_questions`: 1 query + 1 prefetch of options.
8. `load_selected_options_by_pair`: 1 query + 1 prefetch of `selected_options` (hydrates every `QuestionAnswer` for every completed attempt; rows = attempts x questions).
9. `load_distractor_rows`: 1 aggregate query.
10. `load_organisation_logo_data_uri`, `resolve_site_name`: storage read, 0-1 queries (`test_indexes.py` asserts 0/1).
Total roughly 11-13 fixed queries plus per-course catalogue traversal; `test_query_count_is_constant_across_learner_and_question_scale` proves the count does not grow with learners (2 vs 6) or questions. No per-learner query loop. Cost with scale is therefore Python/memory, not query count: all pure-Python loops are O(learners x items) (`_build_learner_row` per learner per course per quiz column; `_build_learner_detail` re-walks `catalogue.all_items` and every quiz per learner; `_completion_counts`/`_latest_completion`/`_completed_items` each iterate all items per learner; `_build_summary_tables` copies rows again; `tally_quiz_answers` is O(sittings x questions)). So 300 learners x (say) 3 courses x 50 items x quizzes is the thing to time; wall-clock, not queries, is the measurement to take. Existing precedent: it already runs inside a background task, never in a request.
- Not memoised, so on-screen rendering in a request would redo all of it per page view and per tab refresh (panels re-fetch on `COHORT_CHANGED` events).
- Gathered data is frozen dataclasses with `UUID`/`datetime` (not JSON-safe as-is): caching in Django cache (pickle) would work; storing as JSON would need a serialiser. No cache layer exists in `reports` today.

## 4. Cheap aggregates for dashboard tiles (without the gather)

Models (`learner_progress/models.py`): `CourseProgress(learner PROTECT, course, learner_registration | cohort_registration (exactly one), created_at, started_at, last_accessed_time (written by the player, not auto_now), completed_time, progress_percentage int default 0 db_index, last_accessed_item)`; `TopicProgress(course_progress, topic, start_time, last_accessed_time auto_now, complete_time)`, index `(course_progress, complete_time)`; `CourseFormAttempt(course_progress, collection_item, form_progress 1:1)`; `form_engine.FormProgress` (scores JSON, completed_time, `quiz_percentage()`, `passed()`).
Possible tiles with single indexed aggregates (all scoped by `cohorts_visible_to(user, organisation)`, `learners_visible_to(user, organisation)`):
- Cohorts: `cohorts_visible_to(...).filter(is_active=True).count()` (1 query; exactly the `CohortDataTable` base queryset).
- Active learners: `learners_visible_to(user, org).count()` (default excludes removed; `learner_status`/`learner_status_q` distinguish pending). Decide whether "pending" (never logged in) counts as active; `LearnerStatus` vocabulary exists (`ACTIVE`, `PENDING`, `REMOVED`).
- Average progress: `CourseProgress.objects.filter(learner__in=visible_learners[, cohort_registration__cohort__in=visible_cohorts]).aggregate(Avg("progress_percentage"))`, 1 query, uses stored percentage (spec better-course-progress-tracking); caveats: records exist only for minted registrations, learner holding records from two registrations counts twice, "average" should pick a unit (per record, per learner via furthest record as `learner_course_summaries` does with `max`).
- Last activity / inactive count: `Max("last_accessed_time")` or `Count(filter=last_accessed_time__lt=now-7d)` per learner via `CourseProgress`; `LearnerDataTable` already annotates `last_active=Max("course_progress_records__last_accessed_time")`.
- Not started: `progress_percentage=0` / `started_at IS NULL` records; Completed: `completed_time IS NOT NULL`.
NOT cheap: "needs attention" exactly as the report defines it. `no_activity` (no TopicProgress or FormProgress rows at all) and `inactive` (>7 days since last COMPLETION) are expressible as annotated subqueries/Exists over `TopicProgress.complete_time` and `FormProgress.completed_time` (note differing from `CourseProgress.last_accessed_time` which is "last visited"); `failed_latest_quiz` needs the latest completed sitting across ALL quizzes in the learner's covered courses with the form's `quiz_pass_percentage` vs `scores` JSON, i.e. the python `_score_attempt` logic (`fp.quiz_percentage()`, `fp.passed()`, `ValueError` handling), not a clean ORM aggregate. So the dashboard tile "learners needing attention" and the needs-attention list either (a) run the gather per visible cohort (cost multiplies by number of cohorts, 12+ queries and a full O(L x items) each), (b) use a reduced ORM subset (two of three rules) which breaks "one definition", or (c) read the latest generated/cached gather output. This is the main design call. Existing `form_engine.queries.attempt_completes_form` and `learner_progress.queries.completed_form_item_ids*` hold the sitting-decides-completion rule used by both worlds.
- Average progress inconsistency: report `completion_percentage` is recomputed from `TopicProgress.complete_time`/`FormProgress.completed_time` over `viewable_items()` (topics and forms; per `qa_create_report_cohort` docstring, `CourseProgress.progress_percentage` is never read by the gather), whereas the learner page, quick view, learner table "Courses" cell all show stored `progress_percentage`. Two numbers for "progress" can disagree for the same learner/course; the spec must pick which the dashboard tile uses and say so (the idea: "same numbers as the PDF" for the report tab; org tiles from `CourseProgress`).

## 5. Status badge vocabulary and duplicate status definitions
- `StatusBadge(tone, label)` dataclass in `panel_framework/views.py` + `<c-panel-status-badge tone label>` (tones success/warning/error/info/muted; other values fall back to muted via `panel_tags.tone`). Callers pass sentence-case labels; the badge owns no domain words.
- Existing domain status mappings in `educator_interface/views.py`: `_LEARNER_STATUS_TONES = {ACTIVE: success, PENDING: info, REMOVED: muted}`; `learner_status_badge`; `active_status_badge(is_active)` -> Active(success)/Inactive(muted), also `cotton/active-status-badge.html`; templates `data-table-cells/learner_status.html`, `active_status.html`. These are lifecycle statuses (account/registration state) and must not be confused with progress/attention statuses: "inactive" already means `is_active=False` for cohorts/registrations, while the report flag `inactive` ("No activity recently") means 7 days without a completion. The idea's vocabulary collision: a learner can be "Active" (lifecycle) and "Inactive" (attention flag) at once. Label copy must disambiguate (report label "No activity recently" already avoids the word).
- Report flags: `AtRiskFlag(rule_id, label, reason, severity)` with severity error/warning = badge tone. Proposed status set (idea): no_activity/failed_latest_quiz/inactive + not started / in progress / complete; not started/complete are derivable from `completion_percentage == 0/100` (`CompletionStats.not_started_count/complete_count`), "in progress" is the remainder. None exist as a shared function or enum today: the report's flags live in `AT_RISK_RULES`; "not started" in `_completion_statistics`; the Python `Literal`-style tone maps live in educator_interface. A single status module in `reports` (e.g. mapping `rule_id`/completion to `StatusBadge`-compatible tone+label) would be new code; `reports` must not import `panel_framework` (not an allowed edge: reports does not depend on it), so the module should return plain `(tone: str, label: str)` or the mapping lives in educator_interface keyed on `rule_id`/`severity`.
- Learner-facing: no overlap found in `learner_interface` (not checked in depth).

## 6. Conflicts and risks

R1. Roster semantics. `indexes.load_roster` takes every `CohortMembership` of the cohort, including memberships of removed learners (`Learner.is_active=False`), and ignores learner status; `cohort_counts`/`CohortLearnersPanel` count only active learners, and `CohortCourseCompletionPanel` narrows to active, current members "or they would disagree with the Learners tab". The report's `cohort_size` can therefore differ from the cohort header stat. Also `reports.md` documents the report as a snapshot including "learners as they were". Fix options: filter the roster in `load_roster` (changes PDF output; the PDF pipeline is out of scope per idea) or document/accept the difference on screen. Decide explicitly.
R2. Report covers only the cohort's own registrations (`reports.md` Limits: individual registrations not covered; `_registration_ids(registrations)` filter on `course_progress__cohort_registration__in`). The learner drill-down on the learner page lists individual registrations too (`LearnerCoursesPanel`). "Built from the report's per-learner gatherer" cannot cover individually registered courses, and cannot cover a learner in several cohorts without one gather per cohort; also the gather needs a cohort id (so which cohort for a learner with several?). The drill-down per course also needs `CourseProgress`-based data for individual registrations. Likely outcome: a narrower query "with the same shape" is needed (the idea allows it), reusing `fold_*`/`_quiz_result_for`/`_score_attempt`/`at_risk` rules over indexes loaded for `[learner_id]` with `registrations` = that learner's registrations; `load_topic_progress_rows`/`load_form_progress_rows` take `registrations` and `learner_ids` params and would work if `_registration_ids` accepted individual registrations, which it does not (hard-coded `cohort_registration__in`). `build_course_catalogue` and `_build_learner_detail` need `CohortCourseRegistration` objects (`reg.course`, `reg.course_id`, `reg.is_active`). This is a refactor of `reports` internals, not a pure reuse. Existing test suite (`test_gather.py` ~1000 lines, `test_indexes.py`) pins these functions.
R3. Request-time gathering vs `site_id`: gather requires explicit `site_id`; use `cohort.site_id`. Called inside an HTMX request it also does PDF-grade extras (logo read, `resolve_site_name`) and the catalogue traversal; consider splitting a `gather_cohort_progress(...)` core without branding (the dataclass `CohortReportData` requires `OrganisationBrand` etc., so a core/branding split touches the contract).
R4. On-screen vs PDF consistency: the on-screen tab and the PDF come from separate gathers at different instants unless the tab reads the latest ready report's data; `GeneratedReport` stores only the PDF file (no gathered data, no JSON). "From the last generated report's data" is not possible today without a model change (new field or stored JSON) or re-parsing a PDF. Live render or cache are the only options without a migration. `generated_at` is available on `CohortReportData` for a "figures as of" label.
R5. One-in-flight rule surface: DB constraint + `IntegrityError` race path; the UI state "A report is being generated" needs to read `status in (pending, running)` per cohort; a `pending` row whose worker is down persists (housekeeping reaps stuck `running` only; late-unpicked tasks are handled via the task layer). Also: after failure the educator must be able to retry immediately (docs say yes) - the view must show `error_message` (contains `REPORTS_MAX_LEARNERS` text) and retry. Tests exist for the admin flow (`test_views.py`, `test_admin.py`, `test_tasks.py`); extraction must keep those green.
R6. Permissions mismatch between roles and the org dashboard: `cohort_viewer`/`cohort_admin` roles are object-scoped to specific cohorts; `organisations_accessible_to` lets them enter the org interface; dashboard tiles must be computed over `cohorts_visible_to(user, org)` / `learners_visible_to(user, org)` (both already scope correctly: a cohort-scoped learner sees only members of granted cohorts). The report download uses `download_cohort_report` via `can()`, held by all four roles, whereas the cohort page uses `view_cohort`; for button visibility use the same `can()` check as `reports/views.py` (note `can()` costs ~2-4 queries per call; do not call per row). Gather runs over the whole cohort roster regardless of viewer: a cohort_viewer with a cohort grant sees all its learners already, so no extra scoping.
R7. Learner privacy surface: the report exposes wrong answers and answer text per learner; `LearnerQuickView` is documented as showing "only what the educator could already see". On-screen panels must go through the same `cohorts_visible_to` authorisation (the cohort `authorise_instance` check on the instance covers the cohort tab).
R8. "Inactive" semantics differ: report inactivity = days since last COMPLETION (`last_completed_at` from `complete_time`/`completed_time`), whereas the learner list "Last active" is `Max(CourseProgress.last_accessed_time)` (last visited). A learner can read as active in the list and flagged inactive on the dashboard. Surface the definition in copy (the report has a methodology partial `reports/partials/methodology.html` with the wording).
R9. 7-day threshold and the three rules are hard-coded in `AT_RISK_RULES` (no setting). Using them on a dashboard that runs per request means the threshold is code, not config; acceptable (docs say so) but an org-level query reimplementation would duplicate the number.
R10. Tailwind bundle dependency: PDF generation fails without the compiled `vendor/tailwind.output.css` (`ReportRenderError`); in dev/CI fresh clones tests that render whole reports are skipped via `requires_tailwind_bundle`. On-screen panels do not need it; PDF-from-interface does.
R11. Timing of the Overview "Needs attention" and "Course completion" panels: they refresh on `COHORT_CHANGED`; if they call the gather, every refresh repeats it. The report tab, if it uses `refresh_events`, will refetch on every cohort change.
R12. File contention with parallel specs: `educator_interface/views.py` is shared with spec 8 (bulk ops, also adds bulk actions on learner/cohort tables) and was edited by 6/7/9; spec 10 adds panels there. Consider putting new panels/tables in a new module (e.g. `educator_interface/reporting.py`) imported by `views.py` to limit merge conflict (views.py is already ~1800 lines).
