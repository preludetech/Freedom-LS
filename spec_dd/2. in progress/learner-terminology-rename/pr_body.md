# `student` → `learner` terminology rename

FLS has standardised on **learner**. Three apps are renamed, and with them every import path, app label,
database table, permission string, URL name, template path and static path they own. There are no
compatibility shims. Downstream migration instructions are in `upgrade_notes.md` in this spec directory.

**Review with rename detection on:** `git diff -M -C df02d990..HEAD`.
Note the merge base is `df02d990`, **not** `main` — see "Merge conflict ahead" below.

## Open judgement calls — overrule any of these

1. **`verbose_name = "User Deadline Override"`** on the `UserCohortDeadlineOverride` admin inline
   (`learner_management/admin.py:106-107`). Spec §11.4 lists this model **by name** in the "user" bucket and
   §15 keeps the model's name, so a `verbose_name` saying "Learner" would disagree with its own model.
   *Overrule to "Learner Deadline Override"* if you read §11.4's general "deadlines are a learner context"
   rule as governing.

2. **Panel keys `"students"` → `"learners"` change a URL the browser actually requests.** Panel keys are the
   last segment of the lazy-load URL `panel_framework/views.py` builds, so:
   - `…/cohorts/<pk>/__tabs/details/__panels/students` → `…/__panels/learners`
   - `…/courses/<pk>/__panels/students` → `…/__panels/learners`

   Key and `hx-get` target move together because the URL is *derived* from the key — there is no second site
   to keep in sync. **This is the only URL in the entire rename that changes.** Learner-facing URL paths are
   byte-identical; only their *names* changed. *Overrule by keeping the key and renaming only the label* if
   you want URL stability. This is why batch 6 needs browser verification and not only pytest.

3. **`instructor` and `ta` are now permission-identical** (both reduce to `view_cohort` alone) after the four
   dead codenames were deleted. Both roles are kept — neither is referenced elsewhere and deleting one is a
   scope widening. `test_site_admin_is_superset_of_instructor` still holds.

4. **`registry.py`'s commented permission strings were corrected to `user*`, not `learner*`.** They named
   `studentcourseregistration` and `studentcohortdeadlineoverride`, models already renamed to `User*` by
   earlier work. A mechanical sweep would have produced names for models that do not exist. Only
   `studentdeadline` became `learnerdeadline`.

5. **Batch 4 deletes 20 existing migration files**, against `CLAUDE.md`'s "never edit existing migration
   files" rule. Taken knowingly, once. Two of the deleted migrations hardcode raw-SQL table names built from
   the old app label, so an in-place rewrite means hand-editing SQL string literals; Django ships no
   `RenameApp`, so there is no in-rule path. **This rests entirely on the load-bearing assumption that no
   downstream has a persisted, migrated database.** If that assumption is wrong, this batch changes shape.

## Two test-quality consequences, stated plainly

- **`test_roles.py` no longer guards against `view_student` being reintroduced.** The plan's TDD instruction
  ("drop the `view_student` line, watch it fail") cannot produce a genuine red — dropping the line leaves a
  test that passes either way. A temporarily inverted assertion was used to get a real red, then the test was
  reduced to the plan's stated final shape.
- **The negative table-name assertions in `test_resume_and_redirect.py:533-534` were verified still live.**
  These assert a table name is *absent* from captured SQL, so after the label rename they could have passed
  trivially and stopped testing anything. Verified by deliberately breaking the query under test and
  confirming the assertion fires, then restoring.

## The user-vs-learner audit (spec's non-scriptable step)

Mechanical renaming fixes the wrong word, not the vague one. The batch 2–6 diff was walked asking, at each
renamed site, whether the code should have said "learner" all along and instead says "user".

**Deliberately left as "user"**: `UserCourseRegistration` and its `related_name`, `CohortMembership`,
`UserCohortDeadlineOverride`, the educator `Users` directory (an account directory spanning educators and
staff, not a learner roster), `RequestUser`, webhook payload keys, and comments naming an in-scope identifier
literally called `user`.

**Changed**: three class docstrings in `learner_progress/models.py` — `FormProgress`, `TopicProgress`,
`CourseProgress` — from "Tracks a user's progress" to "Tracks a learner's progress". Progress is the most
explicitly learner-scoped context in the spec. The `user` FK fields themselves are untouched. **This is the
one place the audit widened beyond a grep hit; it is three lines to revert.**

## Merge conflict ahead — needs a decision

`main` has advanced 20+ commits past this branch's merge base with the `basic_reports` work. That branch:

- adds a whole new `freedom_ls/reports` app that uses "student" throughout (`gather.py`, `report_data.py`,
  `at_risk.py`, `indexes.py`, `forms.py`, `admin.py`, `models.py`, migrations, factories — plus a
  user-visible "student detail report")
- **splits `student_progress/models.py`** into separate modules, and modifies `student_management/queries.py`

Both of those files were renamed wholesale here, so the merge will conflict substantially, and once merged
the word "student" is back in the tree — gate 7 would no longer pass on `main`.

**This is out of scope for this PR** (the spec froze its inventory at branch time) and needs a decision:
either a follow-up sweep of `freedom_ls/reports` after the merge, or fold it in before merging.
