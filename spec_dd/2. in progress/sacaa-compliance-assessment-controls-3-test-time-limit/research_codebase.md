## 2. `FormProgress` (form_engine/models.py:419-474, 606-635)

- `start_time = DateTimeField(auto_now_add=True)` (438): set when the row is created, i.e. in `get_or_create_incomplete` (learner_progress/attempts.py:84-110), reached from `form_start` and from the declaration POST. The clock therefore starts at sitting creation, not at the first page view. For a declaration quiz the sitting is created by the signing POST (`form_declaration` -> `start_attempt(declaration=...)`, views.py:2119), so signing time is excluded and the clock starts when the declaration is saved. `start_time` is immutable by `auto_now_add`, so it is a sound anchor (tests that want a past start must `update()` it).
- `last_updated_time` is `auto_now` (439): any `save()` bumps it. It cannot stand in for "when it expired".
- `complete()` (606-635): idempotent on `completed_time`; stamps `completed_time = timezone.now()` (627) inside `transaction.atomic()`, then sends `form_attempt_completed` (signals.py:7; receiver `learner_progress/signals.py:170`) after the block. **No reason parameter and no reason field.** Its callers: `form_fill_page` (views.py:2321), `form_submit_and_exit` (3237), `finalise_stale_incomplete` (attempts.py:136), the admin (`form_engine/admin.py`, `completed_time` read-only at 122-129).
- A reason field belongs on `FormProgress` in `form_engine` (a `CharField` with `choices` and `default` of learner submitted, matching the idea's "no backfill"), with `complete(reason=...)`. Spec 5 adds values later: a `TextChoices` class beside `FormStrategy` in `form_engine/models.py` (exported via `__all__` at ~50-62) keeps extension to one place. Changing choices later needs a (no-op schema) migration each time.
- `completed_time` for an expired sitting: `complete()` stamps *now*. A sweep that runs hours after expiry (or a learner returning a day later) would record `completed_time` hours after the limit, not at `start_time + limit`. Consequences: the attempts table "Completed" column, the audit story ("result came from a lapsed clock") and **spec 2's wait, which is measured from `completed_time`**. The spec must say whether an expired sitting is stamped with the expiry instant or the real time (then `complete()` needs a way to take it). Not decided in the idea.
- `scores`, `max_score`: unchanged; `complete()` already marks saved answers via `score(path)`. A sitting with no answers scores 0 of `max_score` (served paper's count), so `quiz_verdict` is "failed", not None.

## 3. Start path: `start_attempt`, `_form_start_gate`, `finalise_stale_incomplete`

- `_form_start_gate` (views.py:1978-2021): access check, `_ensure_player_course_progress`, outline, `_blocked_item_redirect(refuse_closed=True)`. Returns a `FormStartGate` (1967-1975) with `redirect` or the collection item, record, decision, index. Shared by `form_start` (2044) and `form_declaration` (2081). It never touches the open sitting.
- `start_attempt` (attempts.py:184-227): takes `select_for_update` on `CourseProgress` (205), reads `get_latest_incomplete`, reuses an unanswered sitting started within `START_REUSE_WINDOW` = 10 s (`_kept_open`, 140-154), else `finalise_stale_incomplete`, then `get_or_create_incomplete`.
- **`finalise_stale_incomplete` is gated on `form.submit_on_exit`** (attempts.py:126). So on a save-on-exit quiz today an open sitting is always resumed. An expired sitting needs completing in the same place for every quiz, whatever `submit_on_exit` says, under the same lock, before `get_or_create_incomplete` (otherwise the learner resumes an expired sitting) and before spec 2 counts attempts. The idea says "the start route" completes it; it does not mention `close_left_signed_sitting` (attempts.py:157-181), the declaration route's equivalent, which has the same submit-on-exit gate and so also needs the expiry rule. `_kept_open`'s 10 s reuse window also must not keep an expired sitting alive (only matters for limits under ~10 s, but the order of checks should put expiry first).
- `view_course_item` (views.py:1583-1594) is the third caller of `finalise_stale_incomplete` and is where the start page (`view_form`, 1897-1964, template `course_form.html`) gets built. It runs only when `not paused and not closed` (1586-1587) and after the access gates.
- `_form_start_gate` has no "refusal with a reason" outcome today (spec 2 will add one). This spec needs no new gate outcome if expiry is completed rather than refused, but it must run its expiry completion *before* spec 2's count; an agreed hook point (a helper called at the top of `start_attempt`'s locked block) avoids both specs editing the same lines differently.

## 5. `form_submit_and_exit` and the exit dialog's skip-required pattern

- Dialog markup: course_form_page.html:142-158. A `type=submit` button with `form="runner-page-form"`, `formaction="{{ submit_and_exit_url }}"`, `formnovalidate`; the JS `_onSubmit` honours `event.submitter?.formNoValidate`. The pattern only exists on `submit_on_exit` forms (the `{% if form.submit_on_exit %}` branch).
- `form_submit_and_exit` (views.py:3150-3243): POST-only. **Redirects away without completing when `not form.submit_on_exit and not closed`** (3194-3199). So a time-limited quiz that does not set `submit_on_exit` would have its expiry POST bounced to the start page. The expiry route needs a third pass condition (limit expired), alongside `closed` (decision ended or `_is_closed_for_learner`, 3191). Either reuse this endpoint with an `expired` branch, or add a new endpoint; the spec must choose.
- The endpoint saves the posted page with `submit_page(..., require_answers=False)` (3216-3222), **unless closed** (`posted = None if closed else ...`, 3217), then `complete()`. The `closed` branch is the existing precedent for "save nothing, just complete", which is what "a page posted after expiry is not saved" needs. The expired case should follow it (`posted=None` when the server finds the sitting expired).
- **Contradiction with "regardless of the number of questions answered":** if `submit_page` rejects an answer (a type check failure, e.g. a number out of range), the endpoint re-renders the page (3223-3236) and does not complete. At expiry that would leave the sitting open past the limit. The expiry path must drop rejected answers and complete.
- Access states: `_course_access_redirect(... route=PlayerRoute.SUBMIT_AND_EXIT)` and `_read_only_route_redirect` (1265-1299) keep submit-and-exit open for a learner without content access (`submit_open`) so an open attempt can be finalised; the results route stays open if a completed attempt exists. Expiry completion should live where a paused, closed or access-ended learner is also reached, since the clock "keeps running if the learner leaves, logs out or the course is paused" (idea). Today a paused learner never reaches `form_fill_page` (redirected) and `view_course_item` skips finalising when `paused` or `closed` (1583-1587), so expiry completion placed in those views' happy path would miss them. Put it in a shared helper called before those gates (and in the sweep).

### Timing tension with "no grace period" (flag for the spec)

The client counts down from the server-sent remaining seconds and posts the current page "when the countdown reaches zero". The client's zero is reached only after the response has travelled to the browser, and the POST then travels back, so the server will almost always see the post *after* `start_time + limit`. With "a page posted after expiry is not saved" (answers.md), the learner's current page is discarded in nearly every case, which defeats the idea's reason for posting the page with the submit. This is not contradicted by any code; it follows from the two decisions together. The spec has to resolve it, for example by sending the client a deadline a little earlier than the server's, by a stated tolerance, or by accepting that the current page is lost and saying so in the learner-facing warning copy. (The page's state before the last "Next" is what is saved, since answers save per page on POST: `form_fill_page` -> `submit_page` -> `save_answers`.)

## 6. Results page

`course_form_complete` (views.py:2346-2500): uses `completed_attempts(course_progress, collection_item).first()` (2376-2380); **it never looks at an open sitting**. A learner with an expired open sitting who has an earlier completed attempt would see the old result. The expiry helper must run first in this view, after the access redirect. `_course_access_redirect(route=FORM_RESULTS)` allows the page only when a completed attempt exists (1285-1291); a learner with no previous completed attempt and an expired open sitting would be redirected before the helper ran, so the helper has to run before that gate too, or that gate's `completed_attempts(...).exists()` check must follow it.

Template `learner_interface/templates/learner_interface/course_form_complete.html` has the verdict banner (lines ~30-40) and the retry button (~260). A line saying "time ran out" for an expired sitting belongs in its banner; the reason is read from the sitting (`form_progress`), already loaded in the view.

## 7. `run_housekeeping_sweeps` and the unscoped manager

- `deployment/housekeeping.py:292-498`. Structure: a sequence of independent `try / except SWEEP_FAILURES (DatabaseError, CommandError)` blocks (`SWEEP_FAILURES` at 289; sweeps use `except DatabaseError`), each appending to `sweep_failures`, `findings` or `notes`, returning `HousekeepingOutcome(sweep_failures, findings, notes)`. Add a block after the last one (the referral prunes) in the same shape, with a `notes.append(f"Completed {n} time-expired sitting(s).")`.
- Unscoped manager precedent: `GeneratedReport._base_manager.filter(...)` (182) and `LearnerImport._base_manager` (263), commented "housekeeping has no request to derive a site from, and every site's rows are in scope". `FormProgress` is a `SiteAwareModel`, so the sweep must use `FormProgress._base_manager`. Check `site_aware_models` for the manager shape (`objects` filters by current site; `_base_manager` is Django's unfiltered default, set via `Meta.base_manager_name` or default).
- Per-row work: a DB-level filter cannot compare `start_time + limit` because the limit lives on `Form` in minutes; use `ExpressionWrapper(F("start_time") + F("form__time_limit_minutes") * timedelta(minutes=1))` annotated and `filter(completed_time__isnull=True, form__time_limit_minutes__isnull=False, expires_at__lte=now)`. The ORM-only rule (CLAUDE.md) is satisfied. Then `sitting.complete(reason=...)` per row, each in its own `try`, since `complete()` runs `ensure_served_paper`, a delete and `form_attempt_completed` receivers that can raise `DatabaseError`. Mark the failures per row (the orphan sweeps count `left_running`).
- **`complete()` under no request**: `form_attempt_completed` receivers (`learner_progress/signals.py:172` `recalculate_course_progress_on_form_attempt`, and the webhooks path) work from the row, not a request, per the existing `finalise_stale_incomplete` use, so this holds. But those receivers and `FormProgress` managers run under whatever site context the sweep sets: `get_latest_incomplete` etc. use site-aware `objects`. Check each receiver for an implicit current-site read before deciding the sweep needs a per-site context. Not fully checked here.
- Only sittings with a `CourseFormAttempt` count toward spec 2; a sweep should complete standalone `FormProgress` too, or limit itself to course sittings. The idea speaks only of quiz sittings in a course.
- The sweep needs a lock or an idempotency argument: `complete()` is idempotent on `completed_time` but not safe against two concurrent `complete()` calls (it reads `completed_time` before the atomic block). The runner and the sweep can race. `start_attempt` locks `CourseProgress`; a `select_for_update` on the `FormProgress` row inside the helper would close it.
- `HOUSEKEEPING_*` config keys are in `deployment/config.py`; a sweep with no config needs none.

## 10. Deadlines app's now-comparison

- `deadlines/consequences.py:29-57`: `close_instant` = due instant + grace window, `is_closed(resolved, policy, completed, now)` is `instant is not None and not completed and now > instant`, `has_access_ended(time_limit, policy, now)` similar. The view calls these with `now=timezone.now()` per request (`_is_closed_for_learner`, views.py:1245-1262, and `form_submit_and_exit` 3191-3193). A strict `now > instant` (not `>=`) is the repo's convention at the boundary; adopt the same for `now > start_time + limit`, and put it in one pure function (e.g. in `form_engine/queries.py` beside `quiz_verdict`, or on `FormProgress`) used by every call site and by the sweep's SQL annotation, so the views and the sweep cannot disagree on the boundary.
- Nothing from `deadlines` is reused (idea is explicit); do not import it from `form_engine` (the app has no dependency on `deadlines`).
- Interaction worth stating: an item can also be `closed` by a deadline (grace) or access can end. `form_submit_and_exit` completes an open sitting when `closed`, with no reason. A closed-completed sitting is recorded as "learner submitted" by default, which is wrong for audit. Out of scope here, but the reason field's default will mislabel these completions; the spec should say whether closure and access end get their own values now or in spec 5.

## 11. Collisions with `sacaa-compliance-assessment-controls-2-attempt-limits` (read its idea.md)

- Same functions: `start_attempt`, `_form_start_gate`, `finalise_stale_incomplete`, the `Form` schema (`knobs` dict), `form_engine` migration `0018`, `content_save.save_form`, `content_preview._quiz_facts`, the bundled `schema.py` and `form-files.md`, the demo quiz `form.md`. Run one at a time, as both ideas say.
- Ordering contract between the two: spec 2 counts **completed** attempts and treats "an expired attempt counts" (idea of spec 3, line 34; spec 2 line 30). That is true only if an expired open sitting is completed before the count. The expiry completion must therefore sit inside `start_attempt`'s locked block ahead of the count; spec 2's own open question ("does a time-limited, expired ... attempt that is still open block the next start?", recommends "existing stale-attempt handling runs first, then the count") assumes `finalise_stale_incomplete` completes it, which today it does **only for `submit_on_exit`** forms. That assumption fails for a save-on-exit time-limited quiz unless this spec changes it. Say so in both specs.
- `completed_time` semantics (section 2) feed spec 2's wait ("measured from the failed attempt's `completed_time`"): a late-completed expired sitting starts the wait late.
- Spec 2's refusal outcome in `_form_start_gate` and this spec's "expired start completes then proceeds" must not fight: complete first, then evaluate the cap, in one order.
- Attempt numbers (`reports/gather.py:392`, `attempt_numbers`) count completed sittings only, so an expired sitting gets a number once completed. No change.
- Spec 2 adds start-page content (attempts used/left) to `view_form`/`form_start_page_buttons`; this spec adds the limit chip to `form_facts.html`: different spots, same template `course_form.html`/`utils.form_start_page_buttons`.

## 12. Things in the idea the code contradicts or leaves unsaid

1. "Any request that touches an expired open sitting completes it: the start route, the runner pages, the results page and `form_submit_and_exit`" is not possible by adding a call inside those views alone: (a) `finalise_stale_incomplete` is `submit_on_exit`-only; (b) paused, closed and access-ended learners are redirected before the sitting is read (`form_fill_page` 2259-2267, `view_course_item` 1583-1587, `_course_access_redirect`); (c) `course_form_complete` ignores open sittings; (d) `form_submit_and_exit` refuses non-`submit_on_exit` forms unless closed. A single helper called before those gates is required, plus the sweep.
2. "The post must skip the required-answer check ... pattern of the exit dialog": the exit dialog exists only for `submit_on_exit` forms and goes through `formnovalidate` / `submitter.formNoValidate`. An auto-post is a script-driven submit with no submitter, so `_onSubmit` (JS 308-321) would run `_revealMissingCheckboxGroups()` and cancel it. The countdown must submit through a path that skips that check (e.g. a flag on the component, or `formEl.submit()` as `submit()` does, which fires no submit event, plus `formaction` set to the exit endpoint). Server-side the skip is `require_answers=False`.
3. `form_submit_and_exit`'s rejected-answer branch can leave a sitting open after expiry (section 5).
