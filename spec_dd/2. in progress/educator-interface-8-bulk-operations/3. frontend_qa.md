# Frontend QA: bulk operations

This change adds the learner CSV import (upload, preview, result, template and error-rows
download), bulk actions on the learners and cohorts lists, "Select all N matching" on tables with
bulk actions, a background path for large imports and runs, and the housekeeping sweeps behind
them.

What a browser can see:

- **Import learners** is a link on the learners list and on a cohort's Learners tab, leading to a
  three-step page: Upload, Preview, Result. The preview labels every row (new account, joined,
  reactivated, added to cohort, already a member, error) and says how many learners "Add N
  learners" would add. The result page reports what happened and offers the error rows as a CSV.
- **Bulk actions** appear as a checkbox column and a selection bar on the learners list (Add to
  cohort, Remove from cohort, and under "More actions": Register for a course, Unregister from a
  course, Deactivate, Reactivate, Resend setup email) and on the cohorts list (Register for a
  course, Unregister from a course, and under "More actions": Deactivate, Reactivate). Each confirms
  with the counts that will change and the counts that will be skipped, then shows a result
  summary.
- **Select all N matching** lets a selection reach every row the filter matched, across pages,
  minus the rows unticked afterwards.
- **A large import** goes to the background and lands on a result page that polls until it is
  done.
- **A large bulk run** goes to the background without leaving the table: the modal closes, the
  button that started it shows a spinner, the checkboxes and bulk buttons are disabled, and when it
  finishes the table refreshes and the result opens in the modal. The requester also gets a
  notification, already marked read if they saw the modal.

Beyond the golden path, this run hunts for:

- **Over-granting.** A cohort admin reaching Deactivate, Reactivate, Resend setup email, the
  import, or a cohort they hold no grant on through a bulk picker; a cohort viewer seeing a
  checkbox column at all.
- **Enumeration.** Another organisation's import, run or learner answering anything but 404; a
  colleague's import page or run status URL answering anyone who did not request it.
- **Stale selections.** A selection whose count changed in another tab must be refused with "The
  selection changed since you opened this." rather than act on the wrong rows. A selected row
  that changed but is still selected is checked again at confirm and skipped with its reason.
- **Repeat submissions.** Confirming an import twice, uploading the same file twice, or running the
  same bulk action twice must add nothing twice and send no second email.
- **Bad files.** An Excel file, a Latin-1 file, a file with the wrong headers, an empty file and
  a file over the row limit must each be refused with the sentence the spec gives, and leave
  nothing behind.

## §0 Setup

### 0.1 Server

1. `PORT=$(.claude/ds/scripts/find_available_port.sh)`. Use that number literally from here on.
2. `uv run python manage.py runserver $PORT`, backgrounded.
3. Base URL: `http://127.0.0.1:$PORT`. Check that `#debug-branch-badge`, bottom left, names
   `educator-interface-8-bulk-operations`.
4. Mailpit at `http://localhost:8025` receives every email the dev server sends. Clear its inbox
   before §2 and again before §4.
5. The dev settings run tasks inline (`ImmediateBackend`), so a background import finishes before
   its result page first loads. `BULK_BACKGROUND_THRESHOLD` is read from Django settings only,
   not the environment. §6.14 needs runs that wait for a worker, so it restarts the server on a
   scratch settings module, `config/settings_qa_background.py` (don't commit it):

   ```python
   from config.settings_dev import *  # noqa: F403
   from freedom_ls.deployment import settings_defaults as fls_defaults

   BULK_BACKGROUND_THRESHOLD = 5
   TASKS = fls_defaults.DATABASE_TASKS
   ```

   With it, a queued run stays queued until
   `DJANGO_SETTINGS_MODULE=config.settings_qa_background uv run python manage.py db_worker --batch`
   processes everything outstanding and exits. Setup emails queue the same way, so §6.14 sends
   none until the worker runs.
