# Spec: Bulk operations

Spec 8 of the educator interface rebuild. Source: `idea.md` beside this file, and the "Educator
interface rebuild" section of `spec_dd/1. next/roadmap.md`.

## Purpose

Today an educator can add at most 50 learners through the paste dialog, and can act on only one
learner or cohort at a time.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `LearnerImport` | coined | One uploaded CSV file and its rows, from upload through preview to result. |
| `LearnerImportRow` | coined | One data line of a `LearnerImport`, with its preview label and its final label. |
| `ImportLabel` | coined | The one label an import row gets, derived from spec 7's `AddOutcome` and `CohortOutcome` (R4). `already_member` also covers an existing learner when no cohort was given. |
| `BulkActionRun` | coined | One execution of a `BulkAction` over a snapshot of selected keys, with its result. |
| `BulkOutcome` | coined | What `BulkAction.apply` did, or would do, to one object: `changed`, `skipped` or `failed`, plus a reason. |
| `BulkResult` | coined | What `BulkAction.execute` returns: counts per `BulkOutcome` status and reason, plus the skipped and failed objects. |
| `EducatorBulkAction` | coined | The `BulkAction` subclass in `educator_interface` that adds per-object permission and the background path. |
| run status | narrowed | `RunStatus`: `queued`, `running`, `done`, `failed` on `BulkActionRun`; `ImportStatus` prepends `previewed` for `LearnerImport`. These deliberately differ from `GeneratedReport`'s `pending`/`ready` (`freedom_ls/reports/models.py`). |

In copy, an import row that is not written is "not added". "Skipped" belongs to bulk runs.

## Scope

In:

- The learner CSV import: upload, preview and result pages, a downloadable template and a
  downloadable error-rows CSV.
- Bulk actions on the learners list (`LearnerConfig`): add to cohort, remove from cohort, register
  for a course, unregister from a course, deactivate, reactivate, resend setup email.
- Bulk actions on the cohorts list (`CohortConfig`): register for a course, unregister from a
  course, deactivate, reactivate.
- "Select all N matching" on any table with bulk actions. This is the `all_matching` selection mode
  that spec 2 reserved.
- A background path for imports and bulk runs above a threshold. An import gets a result page that
  polls. A bulk run keeps the educator on the table, which polls and then shows the result modal, and
  its requester gets an in-app notification when it finishes.
- Housekeeping sweeps that fail stuck records and delete old ones.

Out:

- Importing anything but learners. Updating an existing user's details from a file. Creating
  cohorts from the `cohort` column.
- Manual column mapping.
- Email notification when a background run finishes, and any notification for a finished import.
- Bulk actions on the cohort's learners tab (`CohortLearnersPanel`) and on the members section.
- Bulk cohort move. Bulk delete.
- Export beyond what spec 2's table export and spec 10's roster give.
- A per-object audit entry. Spec 11 lifts it from `BulkActionRun` and `LearnerImport` later.
- A generic importer framework. CSV parsing and the error CSV writer are plain functions that a
  later importer can call.
- A "resume" control for a failed import.

## Decisions

1. **Valid rows commit, error rows are reported.** Each row commits in its own
   `transaction.atomic()`, because a setup email that has already gone out cannot roll back with a
   batch.
2. **Preview is advisory; commit re-classifies.** The result page reports what actually happened,
   which may differ from the preview label.
3. **One extra label, `added_to_cohort`.** It covers an existing learner of the organisation who is
   newly added to the import's cohort. "Already a member" would hide the change, and "joined" would
   claim one that did not happen.
4. **One threshold for imports and bulk runs**, `BULK_BACKGROUND_THRESHOLD`, default 250. The
   An import's result page has its own URL, so the educator can leave and come back. A bulk run has
   no page: the table it was started from shows the run in progress and then the result modal, and
   the `bulk_action.finished` notification covers an educator who left.
5. **Bulk actions are gated by the single action's capability, not by `bulk_manage_learners`.** A
   bulk action is offered to anyone who could perform its single action on some object in the
   organisation, and each object is checked. A `cohort_admin` gets bulk actions within their
   cohorts. `bulk_manage_learners` gates the import from the learners list. This narrows spec 5's
   matrix row "CSV import, bulk actions" to "CSV import".
6. **A partly permitted selection runs on the permitted objects.** Objects the user may not act on
   are skipped under their own reason. A selection in which no object would change cannot be
   confirmed.
7. **Side effects stay per object.** Each object goes through the same service as the single
   action, so webhooks, the setup email and the course-registration notification fire once per
   object, as if done by hand.
8. **Import and run records live in `learner_management`,** a data app. `deployment`'s housekeeping
   then depends on a data app, not the `educator_interface` view layer.
9. **The mockups give layout only.** `Educator Cohorts and Admin.dc.html` (the bulk-import dialog)
   and `Educator Mobile Cohorts and Admin.dc.html` (M11) supply the stepper, the file chip and the
   callout.

## Requirements

### R1. Panel framework: bulk action contract

`freedom_ls/panel_framework/bulk_actions.py`, `freedom_ls/panel_framework/views.py`
(`_handle_bulk_action`, `_BulkConfirmation`), and the bulk confirmation partials under
`panel_framework/templates/panel_framework/partials/`.

1. `BulkAction` gains:
   - `variant: str = "secondary"`, the button style of its bar button and its Confirm button, as
     `PanelAction.variant` is.
   - `form_class: type[forms.Form] | None = None`. When set, the confirmation renders the form (the
     target picker) above the confirmation sentence.
   - `classify_all(user, queryset, cleaned_data) -> dict[key, BulkOutcome]`. It is read-only and
     runs in a fixed number of queries. It works out the permitted objects with one queryset (R6),
     not with `can()` per object.
   - `apply(user, obj, cleaned_data) -> BulkOutcome`, which does the work for one object.
   - `BulkOutcome` is a frozen dataclass of `status` (`"changed"`, `"skipped"`, `"failed"`) and
     `reason: str` (empty for `changed`). `apply` and `classify_all` take a user, not a request, so
     a task can call them.
2. `execute(request, queryset)` returns a `BulkResult`, or a `BackgroundRun` holding a status URL
   when the action has handed the run to a task. Its default calls `run_apply`, which
   calls `apply` on each object inside its own `transaction.atomic()` and tallies the outcomes. A
   `failed` outcome comes only from an exception type the action names in `failure_exceptions`.
   Any other exception propagates.
3. The confirmation shows the verb, the target and the counts from `classify_all`, supplied by
   `confirmation_wording(...) -> ConfirmationWording` (the sentence, the skip counts and any
   consequence lines), using the single action's wording: "Add 12 learners to Accra January. 3 are already in the cohort and will be
   skipped. 2 are learners you don't have permission to change and will be skipped." When no object
   would be `changed`, it says why and Confirm is disabled. Above `BULK_BACKGROUND_THRESHOLD`
   objects, it shows only the total and says the run goes to the background and that a
   notification follows when it finishes.
4. Response contract of the bulk-action URL:
   - The first POST renders the confirmation: a modal over htmx, the confirm page with JS off.
   - A POST with `refresh=1`, sent by htmx when the picker changes, returns the confirmation
     fragment re-rendered for the new target. Confirm stays disabled until the form is valid.
   - The confirmed POST carries `expected_count`. If the resolved count differs, the response is a
     422 with the confirmation re-rendered at the new count and the line "The selection changed
     since you opened this."
   - A confirmed POST that runs inline returns the result summary: in the modal over htmx, as a page
     with JS off. Over htmx the response carries the panel's `refresh_events` in `HX-Trigger`, so
     the table refreshes behind the summary and Close only closes.
   - A confirmed POST that goes to the background answers 204 over htmx, with `closeModal` and
     `bulkRunStarted` (`region`, `action`, `label`, `status_url`) in `HX-Trigger`. The table's
     selection component keeps the run in an Alpine store keyed by region, so it survives the
     table's own refreshes. While the run goes, the bulk buttons and "More actions" are disabled,
     the button that started it shows a spinner, every row checkbox is disabled and the bar's
     status reads "<Label> is running…". The store polls `status_url` every 2 seconds into
     `#app-modal-body`, skipping a tick while a modal is open or the tab is hidden, and stops if
     the table leaves the page. With JS off the answer is a 303 back to the table with a flash
     saying a notification will follow.
5. `max_rows` (500) applies to `mode=keys` only. An `all_matching` selection has no cap.
6. The stub action in `panel_framework/tests/stub_panels.py` keeps working with an `execute` that
   returns a `BulkResult` and no `classify_all`. Such an action confirms with the plain count.

### R2. Panel framework: select all matching

`resolve_selection` and `parse_selection` in `bulk_actions.py`, the `tableSelection` Alpine
component in `panel_framework/static/panel_framework/js/alpine-components.js`, and the selection bar
template.

1. `resolve_selection` handles `mode="all_matching"`. It takes the table state from the bulk-action
   request's own `request.GET`, which the bar already puts in the action URL. It applies the table's
   `parse_query` and `filter_queryset` over `panel.get_queryset(request)` and excludes the posted
   `excluded` keys. `Selection.query_string` is removed. The 422 "Not supported yet" branch in
   `_handle_bulk_action` goes.
2. When every row on the page is selected and the table has more rows than the page shows, the bar
   says "All 25 on this page are selected." with a button "Select all 312 matching". Once it is
   chosen, the bar says "All 312 matching are selected." with "Clear selection". Unticking a row in
   this mode adds its key to `excluded`, and the count drops by one.
3. The bar's count text sits in a `role="status"` region that is present before it changes. The
   header checkbox keeps meaning "this page".
4. A table swap (filter, search, sort or page) clears the selection in both modes, as it does today.

### R3. Learner management services

`freedom_ls/learner_management/learner_actions.py`, `freedom_ls/learner_management/utils.py`,
`freedom_ls/learner_management/queries.py`, `freedom_ls/educator_interface/actions.py`.

1. The decision `_add_one` makes is split out into a pure function, `decide_add`. It takes the
   matched user (or none), the learner row (or none), its `is_active` and whether the membership
   exists, and it returns the `AddOutcome` and `CohortOutcome`.
   - `_add_one` becomes public as `add_learner(organisation, entry, cohort) -> AddLearnerResult` and
     uses the pure function.
   - New `classify_learner_entry(organisation, entry, cohort) -> AddLearnerResult` is read-only. It
     uses `lookup_user`, which raises `EmailInUseOnAnotherSite`, and the same pure function. It
     accepts a preloaded `ImportLookup` (the users, learners and memberships for a whole file) so a
     preview runs in a fixed number of queries.
   - `add_learners` keeps its signature and behaviour and calls `add_learner`.
   - The existing `_add_one`/`add_learners` tests pass unchanged.
2. A cohort-against-organisation check, `check_cohort_for(organisation_id, cohort)`, raises
   `ValueError` for an inactive cohort or one in another organisation. `add_learners`, `add_learner`
   and `_check_cohort` all use it.
3. New `deactivate_cohort(cohort) -> bool` and `reactivate_cohort(cohort) -> bool` report whether
   anything changed. `CohortStateAction.handle_submit` calls them in place of its inline `save`.
4. `register_cohort_for_course` and `unregister_cohort_from_course` return whether anything
   changed, as the learner services do. Their existing callers adjust.
5. New `can_on_any(user, organisation, capability) -> bool` in `queries.py` returns
   `can(user, capability, organisation)` or
   `cohorts_visible_to(user, organisation, capability=capability).exists()`. New
   `learners_permitted_for(user, organisation, capability)` beside it: every visible learner for
   an organisation-level grant, otherwise the members of the cohorts that grant the capability.

### R6. Learner import

New module `freedom_ls/educator_interface/learner_import.py`, new `freedom_ls/base/csv_import.py`,
`freedom_ls/educator_interface/tasks.py`.

| Path (under `organisations/<slug>/`) | Name | Does |
| --- | --- | --- |
| `learners/import` | `learner_import` | GET the upload form; POST upload |
| `learners/import/template.csv` | `learner_import_template` | the template |
| `learners/import/<uuid>` | `learner_import_preview` | GET preview; POST confirm |
| `learners/import/<uuid>/result` | `learner_import_result` | result page |
| `learners/import/<uuid>/status` | `learner_import_status` | polled progress fragment |
| `learners/import/<uuid>/errors.csv` | `learner_import_errors` | error rows CSV |

**Gate.** From the learners list, an import needs `bulk_manage_learners` and `ADD_LEARNER` on the
organisation. With `?cohort=<pk>` (the cohort entry point), it needs `ADD_LEARNER` on the
organisation and `ADD_COHORTMEMBERSHIP` on that cohort, and the cohort must be active.

Each page shows a stepper: an `<ol>` of Upload, Preview and Result with `aria-current="step"` on
the current step, plus "Step 2 of 3" in text.

**Names.** In `csv_import.py`: `parse_csv(uploaded_file, max_rows) -> list[dict[str, str]]`,
raising `CsvImportError` with the message to show, and `write_error_csv`. In `learner_import.py`:
`check_import_gate(user, organisation, cohort) -> bool`, `create_learner_import(...)` (parse, label
and store), `check_rows(...)` (the shared classification steps up to cohort resolution),
`preview_rows(...)` and `commit_rows(...)` (the preview and commit endings over `check_rows`) and
`run_learner_import`.

**Entry points.**

- An "Import learners" link (not a modal trigger) in `LearnerConfig.get_actions` and in
  `CohortLearnersPanel.get_actions`: `ImportLearnersAction`, a `PanelAction` whose trigger template
  is a link to the import page. The cohort link passes `?cohort=<pk>`. Each appears only to a
  user who passes the matching gate.
- The add-learners paste dialog (`AddLearnersAction`) links to the import page where it states its
  50-line cap.

**Upload.**

1. The page shows:
   - a file input;
   - the accepted headers on one code line (`email,first_name,last_name,cohort`);
   - "`email` is required; `cohort` is matched by name";
   - a link to the template.

   On the cohort entry point, the page names the cohort and says the `cohort` column is ignored.
2. The template is UTF-8 with a BOM (`UTF8_BOM` from `base/csv_safety.py`). It holds the four
   headers and two example rows.
3. Parsing in `csv_import.py` knows nothing about learners. It:
   - rejects files over 1 MB, and files that start with `PK` ("This looks like an Excel file. Save
     it as CSV UTF-8 and upload that.");
   - decodes as `utf-8-sig`; a `UnicodeDecodeError` gives "Save the file as CSV UTF-8 and upload it
     again.";
   - takes the delimiter from the header line, comma or semicolon;
   - trims and case-folds headers; a missing `email`, an unknown header or a repeated header
     rejects the file with one message that names every unknown, repeated and missing header, then
     lists the accepted ones;
   - reads with `csv.DictReader(strict=True)`; a `csv.Error` names the line;
   - skips rows whose cells are all blank;
   - rejects a file with no data rows, or with more than `LEARNER_IMPORT_MAX_ROWS` ("2,431 rows;
     the limit is 2,000"). It never truncates.
4. A file-level failure re-renders the form with a 422 and an error summary that takes focus.
   Nothing is stored.
5. On success, the view creates the `LearnerImport` and its rows with `preview_label` set, then
   redirects (303) to the preview.

**Row classification.** Preview and commit use the same steps, in order:

- The email is trimmed, with zero-width and non-breaking spaces removed. A blank email is an error:
  "Email is empty."
- Field lengths: email 254, names and cohort 150. A value over the limit is an error naming the
  column.
- A later row with the same email as an earlier one (case-insensitive) is an error: "Same email as
  line N."
- Cohort: on the cohort entry point, the import's cohort. Otherwise a non-blank `cohort` cell is
  matched case-insensitively against active cohorts in
  `cohorts_visible_to(user, organisation, capability=ADD_COHORTMEMBERSHIP)`. No match is an error:
  "No active cohort called 'X' that you can add learners to." A blank cell means no cohort.
- Then `classify_learner_entry` at preview, or `add_learner` at commit, mapped through the label
  table. `INVALID_EMAIL` reads "This isn't a valid email address." `EMAIL_IN_USE_ELSEWHERE` reads
  "This address belongs to an account on another site." It never names the account.

The preview loads the existing users, learners, memberships and cohorts for the whole file in a
fixed number of queries, not one per row.

**Preview (GET).**

1. A file chip with the file name and the row count, and an "Upload a different file" link.
2. A count per label, summing to the row count. Each count links to `?label=<label>`, which filters
   the table and survives reload and Back.
3. A `<table>` of rows with these columns: line, email, first name, last name, cohort, label (as
   text) and reason. 50 rows per page; cards on mobile. No status is shown by colour alone.
4. Notes:
   - "N new accounts will get a setup email."
   - "Existing accounts keep their names."
   - "Counts can change if someone else adds these learners before you confirm."
5. When there are errors, a "Download the N error rows" link.
6. The confirm button reads "Add N learners". N counts the rows not labelled `error` or
   `already_member`.
   - With errors, the page adds "N rows with errors will not be added."
   - When N is above the threshold, the page says the import runs in the background and that the
     result page will show progress.
   - When N is 0, there is no confirm button, and the page says why.
7. An import not in `previewed` redirects to its result page.

**Commit (POST).**

1. A conditional update moves `previewed` to `queued` (when N is above the threshold) or to
   `running`. If no row changes, the view redirects to the result page.
2. The view re-checks the gate, then runs `run_learner_import` inline, or enqueues it, and redirects
   to the result page.
3. `run_learner_import(import_id, site_id)` is a plain function. A `@task()` wrapper in `tasks.py`
   takes only those two primitives, following `freedom_ls/reports/tasks.py`. The function:
   - sets `running` and `started_at`;
   - re-checks `requested_by` against the gate. If the user no longer passes, it sets `failed` with
     the message "You no longer have permission to import learners here.";
   - processes the rows whose `final_label` is null, in line order. Each row is classified again,
     cohort resolution included. If it is not an error, `add_learner` runs inside its own
     `transaction.atomic()`, and the row's `final_label` and `final_reason` are saved in the same
     transaction;
   - sets `done`. An unexpected exception sets `failed` with a generic `error_message`, then
     re-raises.

   Rows that already hold a final label are left alone, so a re-enqueued task resumes where it
   stopped.

**Result.**

1. While the import is `queued` or `running`, the page shows "Added N of M rows" and a `<progress>`.
   It is a fragment from `learner_import_status`, polled with `hx-trigger="every 2s"`. When the
   import is done, the fragment comes back without the trigger and holds the final result. The text
   sits in a `role="status"` region.
2. When done, the page shows:
   - the headline "Added N learners. M rows were not added.";
   - a count per final label, in the preview's order and wording;
   - "N setup emails were sent.";
   - the first 50 error rows inline, and the error CSV link;
   - a link to the cohort's learners tab (cohort import) or the learners list, and "Import another
     file";
   - "Uploading the whole file again is safe: rows already added show as 'already a member'."
3. When failed, the page shows "Stopped after N of M rows", the reason, and the same re-upload line.

**Error rows CSV.** The header is `email,first_name,last_name,cohort,reason`.

- It holds the rows whose `final_label` is `error`, plus, while uncommitted, the rows whose
  `preview_label` is `error`.
- Cells keep their original values, the file starts with a UTF-8 BOM, and `escape_csv_formula` is
  applied to every cell, header included.
- The file name is `learner-import-errors-<YYYY-MM-DD>.csv`.
- `write_error_csv(header, rows)` in `csv_import.py` writes it, streaming like the table export.

### R7. Bulk actions

`freedom_ls/educator_interface/actions.py`, `forms.py`, `views.py` (`LearnerConfig.get_bulk_actions`,
`CohortConfig.get_bulk_actions`), and `tasks.py`.

**Base class.** `EducatorBulkAction(BulkAction)` adds:

- `table_key` as a class attribute. The action registry in `actions.py` is keyed on
  `(table_key, action_name)` and read through `bulk_action_for(table_key, action_name)`;
  `bulk_actions_for_table(table_key)` lists a table's actions in registration order, which is the
  bar's order.
- `has_permission(request)`, which is `can_on_any(user, organisation, capability)`. When it is
  false for every action, the checkbox column does not render (spec 2's existing rule).
- `permitted(user, organisation, queryset, cleaned_data) -> QuerySet`, the one queryset
  `classify_all` narrows with: `learners_permitted_for` with the capability, `cohorts_visible_to`
  with the capability, or everything or nothing from a single `can()` on the target cohort for
  the membership actions.
- `classify_all`, which narrows to the permitted objects with `permitted`. Every other object is
  `skipped` with "you don't have permission to change them".
- `apply`, which re-checks `can(user, capability, scope)` with the scope object the single action
  uses before it calls the service.
- `execute`, which snapshots the resolved keys into a new `BulkActionRun`. At or below the
  threshold it runs `run_bulk_action` inline. Above it, it enqueues the task.

`run_bulk_action(run_id, site_id)` follows `run_learner_import`:

- It finds the action through the registry and re-resolves the target from `target`.
- It loads each key with `_base_manager`, scoped to the organisation. A key that no longer resolves
  is `skipped` with "no longer exists".

A run has no page of its own. Its status URL, `organisations/<slug>/bulk-runs/<uuid>/status`
(`bulk_action_run_status`), answers 204 while the run is queued or running. Once it is done it
answers the same result modal an inline run shows; once it has failed, a modal saying "Stopped
after X of Y <noun>." with the error. Either answer carries the list section's `refresh_events`
in `HX-Trigger`, so the table refreshes behind the modal, and marks the run's notification read,
since the requester has now seen the outcome.

`_run_bulk_action_task` raises a `bulk_action.finished` notification for `requested_by` once the
run is done or failed. An inline run raises none: its modal is the feedback. The message is a
sentence for someone who wasn't watching, such as "Deactivate finished: 298 learners changed, 2
skipped." or "Deactivate stopped after 120 of 300 learners.", and it links to the run's table.
The `notifications` skill's checklist for the category:

1. Actor: the requester started the run, but the work happened in the background where they may
   not be watching. If they are still on the table, the modal shows the outcome and the
   notification is marked read when it does.
2. Without it: nothing, once they have left the table.
3. What they do: open the table to check the result. The notification links there.
4. Frequency: once per background run, only above the threshold, so rarely.
5. In-app is enough.

### R8. Housekeeping

`freedom_ls/deployment/housekeeping.py` (`run_housekeeping_sweeps`). The sweeps follow the
`GeneratedReport` ones and are reported the way `mark_orphaned_running_reports_failed` reports:

1. Delete a `LearnerImport` still `previewed` 24 hours after `created_at`.
2. Fail a `queued` import or run older than `HOUSEKEEPING_UNPICKED_TASK_MAX_AGE_SECONDS`.
3. Fail a `running` import or run whose `started_at` is older than
   `HOUSEKEEPING_ORPHANED_REPORT_MAX_AGE_SECONDS`.
4. Delete an import or run whose `finished_at` is more than `BULK_RECORD_RETENTION_DAYS` ago.

A failed record gets `finished_at` like any other terminal record, so sweep 4 deletes it in time.

## Success criteria

- A 30-row file with two bad emails previews 28 rows to add and 2 errors. Confirming adds the 28,
  and the error CSV holds exactly the 2, with reasons.
- Uploading the same file again previews every valid row as `already_member`, and confirming sends
  no email.
- With the threshold at 5, a 10-row import enqueues a task, and its result page polls until the
  import is done.
- "Select all N matching" on a filtered learners list acts on exactly the N rows the filter matched
  at confirm time, minus the excluded ones.
