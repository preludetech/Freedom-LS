# Spec: Bulk operations

Spec 8 of the educator interface rebuild. Source: `idea.md` beside this file, and the "Educator
interface rebuild" section of `spec_dd/1. next/roadmap.md`. Research: the `research_*.md` files
beside this file.

## Purpose

Schools add learners by the intake, and educators act on whole groups at once. Today an educator
can add at most 50 learners through the paste dialog and act on one learner or cohort at a time.
This spec adds a CSV import of learners, with a preview before anything is written, and
multi-select bulk actions on the learners and cohorts tables, including "select all matching the
filter". Large runs go to a background task.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `LearnerImport` | coined | One uploaded CSV file and its rows, from upload through preview to result. No existing term. |
| `LearnerImportRow` | coined | One data line of a `LearnerImport`, with its preview label and its final outcome. |
| `BulkActionRun` | coined | One execution of a `BulkAction` over a snapshot of selected rows, with its result. |
| import label | coined | The one label each import row gets: `new_account`, `joined`, `reactivated`, `added_to_cohort`, `already_member`, `error`. |

## Scope

In:

- The learner CSV import: upload, preview and result pages, a downloadable template and a
  downloadable error-rows CSV.
- Bulk actions on the learners list (`LearnerConfig`): add to cohort, remove from cohort, register
  for a course, unregister from a course, deactivate, reactivate, resend setup email.
- Bulk actions on the cohorts list (`CohortConfig`): register for a course, unregister from a
  course, deactivate, reactivate.
- "Select all N matching" on any table with bulk actions: the `all_matching` selection mode that
  spec 2 reserved.
- A background path for imports and bulk runs above a threshold, with a result page that polls.
- Housekeeping sweeps that expire and delete old import and run records.

Out:

- Importing anything but learners. Updating an existing user's details from a file. Creating
  cohorts from the `cohort` column.
- Manual column mapping.
- Email or in-app notification when a background run finishes.
- Bulk actions on the cohort's learners tab (`CohortLearnersPanel`) and on the members section.
- Bulk cohort move.
- Export beyond what spec 2's table export and spec 10's roster give.
- A per-object audit entry. Spec 11 lifts it from `BulkActionRun` and `LearnerImport` later.
- A generic importer framework. CSV parsing and the error CSV writer are plain functions a later
  importer can call.

## Decisions

1. **Strict headers.** Headers are matched by name after trimming and case-folding. A missing
   `email` header, an unknown header or a repeated header rejects the file at upload with a message
   that names the offending headers and lists the accepted ones. The template makes mapping
   unnecessary for a four-column file.
2. **The parsed rows are stored as `LearnerImportRow` rows, not as a file.** The worker and every
   web process can read them, nothing needs a storage alias, and expiry is a delete.
3. **Preview is advisory; commit re-classifies.** Commit runs each row through spec 7's add path
   again and records what actually happened. The result page reports the final outcome, which may
   differ from the preview label.
4. **Valid rows commit, error rows are reported.** Each row commits in its own
   `transaction.atomic()`, because a setup email already sent cannot roll back with a batch.
5. **One extra label, `added_to_cohort`.** It covers an existing learner of the organisation who is
   newly added to the import's cohort. "Already a member" would hide the change and "joined" would
   claim one that did not happen.
6. **Background delivery is the polling result page only.** No email and no notification. The page
   has its own URL, so the educator can leave and come back. FLS does not notify people about what
   they just did.
7. **One threshold for imports and bulk runs**, `BULK_BACKGROUND_THRESHOLD`, default 250. At or
   below it the work runs in the request. Above it, the work runs in a task.
8. **Bulk actions are gated by the single action's capability, not by `bulk_manage_learners`.** A
   bulk action is offered to anyone who could perform its single action on some object in the
   organisation, and each object is checked with `can()`. A `cohort_admin` gets bulk actions within
   their cohorts. `bulk_manage_learners` gates the CSV import only. This narrows spec 5's matrix row
   "CSV import, bulk actions" to "CSV import".
9. **A partly permitted selection runs on the permitted objects.** Objects the user may not act on
   are skipped and counted under their own reason. A selection with no permitted object cannot be
   confirmed.
10. **Every bulk run is a `BulkActionRun`, small or large.** An inline run completes before the
    response and its result shows in the modal. A background run redirects to its result page. The
    record is what spec 11 lifts.
11. **Only the user who started an import or run can open its pages.** Anyone else gets a 404, the
    same as an out-of-scope object.
12. **Side effects stay per object.** Each object goes through the same service as the single
    action. Webhooks, the setup email and the course-registration notification therefore fire once
    per object, exactly as if the educator had done each one by hand.
13. **The mockups give layout only.** `Educator Cohorts and Admin.dc.html` (bulk-import dialog) and
    `Educator Mobile Cohorts and Admin.dc.html` (M11) supply the stepper, the file chip and the
    callout. Their mapping step, modal chrome and extra fields are not built. The steps are Upload,
    Preview and Result.

## Requirements

### R1. Panel framework: bulk action contract

`freedom_ls/panel_framework/bulk_actions.py`, `freedom_ls/panel_framework/views.py`
(`_handle_bulk_action`, `_BulkConfirmation`), the bulk confirmation partials under
`panel_framework/templates/panel_framework/partials/`.

1. `BulkAction` gains:
   - `form_class: type[forms.Form] | None = None`. When set, the confirmation modal renders the
     form (the target picker) above the confirmation sentence. The sentence and counts re-render
     over htmx when the picker changes. Confirm stays disabled until the form is valid.
   - `classify(user, obj, cleaned_data) -> BulkOutcome`: read-only, the outcome applying would
     have.
   - `apply(user, obj, cleaned_data) -> BulkOutcome`: does the work for one object and returns what
     happened.
   - `BulkOutcome` is a frozen dataclass of `status` (`"changed"`, `"skipped"`, `"failed"`) and
     `reason: str` (empty for `changed`). Every `apply` and `classify` takes a user, not a request,
     so a task can call them.
2. `execute(request, queryset)` returns a `BulkResult`: counts per status and per skip reason, plus
   the per-object list of `(key, row label, outcome)`. Its default loops `apply` over the objects,
   each in its own `transaction.atomic()`. A `failed` outcome comes from a caught, specific
   exception. Any other exception propagates.
3. The confirmation shows the verb, the target and the counts from `classify`: "Add 12 learners to
   Accra January. 3 are already in the cohort and will be skipped. 2 are learners you can't manage
   and will be skipped." Above `BULK_BACKGROUND_THRESHOLD` objects it shows only the total, says the
   run will go to the background, and says skips are reported in the result.
4. The confirm form carries `expected_count`. If the resolved count at execute differs, the view
   answers 422 with the confirmation re-rendered at the new count and the line "The selection
   changed since you opened this."
5. `max_rows` (500) applies to `mode=keys` only. An `all_matching` selection has no cap.
6. The existing stub action in `panel_framework/tests/stub_panels.py` keeps working: an action that
   overrides `execute` and defines no `classify` still confirms with the plain count.

### R2. Panel framework: select all matching

`resolve_selection` and `parse_selection` in `bulk_actions.py`, the `tableSelection` Alpine
component in `panel_framework/static/panel_framework/js/alpine-components.js`, the selection bar
template.

1. `resolve_selection` handles `mode="all_matching"`. It parses the posted `query_string` with the
   table's own `parse_query`, applies `filter_queryset` over `panel.get_queryset(request)`, and
   excludes the posted `excluded` keys. Parameters the table does not declare are ignored, as on a
   table GET. The 422 "Not supported yet" branch in `_handle_bulk_action` goes.
2. When every row on the page is selected and the table has more rows than the page shows, the bar
   says "All 25 on this page are selected." with a button "Select all 312 matching". Once chosen it
   says "All 312 matching are selected." with "Clear selection". Unticking a row in this mode adds
   its key to `excluded` and the count drops by one.
3. The bar's count text sits in a `role="status"` region present before it changes. The header
   checkbox keeps meaning "this page".
4. A table swap (filter, search, sort, page) clears the selection in both modes, as today.
5. `BulkAction.execute` and the background run never see the query string. They see the resolved
   objects, snapshotted to a key list (R6).

### R5. Learner import: pages

New routes in `freedom_ls/educator_interface/urls.py`, placed before the
`organisations/<slug>/<path_string>` catch-all. They render inside the interface shell and resolve
the organisation through the same organisation-scoped request as `views.interface`, so any other
organisation is a 404. Every route checks `bulk_manage_learners` and `add_learner` on the
organisation. A user who can see the organisation but lacks them gets the 403 denied response.
Import and result routes also 404 for anyone but `requested_by`.

| Path (under `organisations/<slug>/`) | Name | Does |
| --- | --- | --- |
| `learners/import` | `learner_import` | GET the upload form; POST upload |
| `learners/import/template.csv` | `learner_import_template` | the template |
| `learners/import/<uuid>` | `learner_import_preview` | GET preview; POST confirm |
| `learners/import/<uuid>/result` | `learner_import_result` | result page |
| `learners/import/<uuid>/status` | `learner_import_status` | polled progress fragment |
| `learners/import/<uuid>/errors.csv` | `learner_import_errors` | error rows CSV |

Every page shows a stepper, an `<ol>` of Upload, Preview and Result with `aria-current="step"` on
the current step, plus "Step 2 of 3" in text.

**Entry points.** An "Import learners" link (not a modal trigger) in `LearnerConfig.get_actions`
and in `CohortLearnersPanel.get_actions`. The cohort one passes `?cohort=<pk>` and appears only for
an active cohort on which the user holds the membership-add capability. The add-learners paste
dialog (`AddLearnersAction`) links to the import page where it states its 50-line cap.

**Upload (`learner_import`).**

1. A file input, the accepted headers in a code line (`email,first_name,last_name,cohort`), "`email`
   is required; `cohort` is matched by name", and a link to the template. On the cohort entry point
   the page names the cohort and says the `cohort` column is ignored.
2. The template is UTF-8 with a BOM (`base/csv_safety.py`'s `UTF8_BOM`): the four headers and two
   example rows.
3. Parsing lives in a new `freedom_ls/base/csv_import.py` with no learner knowledge. It:
   - rejects files over 1 MB, and files that start with `PK` ("This looks like an Excel file. Save
     it as CSV UTF-8 and upload that.");
   - decodes as `utf-8-sig`; a `UnicodeDecodeError` gives "Save the file as CSV UTF-8 and upload it
     again.";
   - takes the delimiter from the header line, comma or semicolon;
   - reads with `csv.DictReader(strict=True)`; a `csv.Error` names the line;
   - skips rows whose cells are all blank;
   - rejects a file with no data rows, or more than `LEARNER_IMPORT_MAX_ROWS` ("2,431 rows; the
     limit is 2,000"). It never truncates.
4. File-level failures re-render the form with a 422 and an error summary that takes focus. Nothing
   is stored.
5. On success it creates the `LearnerImport` and its rows with `preview_label` set, then redirects
   (303) to the preview.

**Row classification (preview and commit).** Per row, in order:

- Email trimmed (zero-width and non-breaking spaces removed). A blank email is an error, "Email is
  empty."
- Field lengths: email 254, names and cohort 150. Over → error naming the column.
- A later row with the same email (case-insensitive) as an earlier one → error "Same email as line
  N."
- Cohort: on the cohort entry point, the import's cohort. Otherwise a non-blank `cohort` cell is
  matched case-insensitively against
  `cohorts_visible_to(user, organisation, capability=ADD_COHORTMEMBERSHIP)` with `is_active=True`.
  No match → error "No active cohort called 'X' that you can add learners to." A blank cell means
  no cohort.
- Then `classify_learner_entry` at preview, or `add_learner` at commit, mapped through the label
  table. `INVALID_EMAIL` reads "This isn't a valid email address." `EMAIL_IN_USE_ELSEWHERE` reads
  "This address belongs to an account on another site." It never names the account.

Preview loads the existing users, learners, memberships and cohorts for the whole file in a fixed
number of queries, not per row.

**Preview (`learner_import_preview`, GET).**

1. A file chip showing the name and the row count, with an "Upload a different file" link back to
   the upload step.
2. A count per label, summing to the row count. Each count links to `?label=<label>`, which filters
   the table and survives reload and Back.
3. A `<table>` of rows: line, email, first name, last name, cohort, label as text, reason. 50 rows
   per page. Mobile shows the same as cards. No status is shown by colour alone.
4. Notes: "N new accounts will get a setup email." "Existing accounts keep their names." "Counts
   can change if someone else adds these learners before you confirm."
5. When errors exist: "Download the N error rows" (`learner_import_errors`).
6. The confirm button reads "Add N learners", where N counts the rows not labelled `error` or
   `already_member`. With errors it adds "N rows with errors will be skipped." When N is above the
   threshold, the page says the import will run in the background and the result page will show
   progress. When N is 0, there is no confirm button and the page says why.
7. A `LearnerImport` not in `previewed` redirects from the preview to its result page.

**Commit (`learner_import_preview`, POST).**

1. A conditional update moves `previewed` to `queued` (above the threshold) or `running`. If no row
   changes, the import was already confirmed and the view redirects to the result page. A double
   submit runs nothing twice.
2. It re-checks the route's capabilities. Then, at or below the threshold, it runs
   `run_learner_import` inline. Above it, it enqueues the task. Either way it redirects (303, or
   `HX-Redirect`) to the result page.
3. `run_learner_import(import_id, site_id)` is a plain function in
   `freedom_ls/educator_interface/learner_import.py`. A `@task()` wrapper in
   `freedom_ls/educator_interface/tasks.py` takes only those two primitives, following
   `freedom_ls/reports/tasks.py`. It reads with `_base_manager` filtered on `site_id`. It:
   - sets `running` and `started_at`;
   - re-checks `requested_by`'s capabilities on the organisation and the cohort. If they are gone,
     it sets `failed` with "You no longer have permission to import learners here.";
   - processes rows whose `outcome` is null, in line order. Each row is classified again (cohort
     resolution included) and, if not an error, `add_learner` runs inside its own
     `transaction.atomic()`. The row's `outcome` and `reason` are saved in the same transaction and
     `processed_count` is updated;
   - leaves rows already holding an outcome alone, so a retried task resumes;
   - sets `done` and `finished_at`. An unexpected exception sets `failed` with a generic
     `error_message`, then re-raises.

**Result (`learner_import_result`).**

1. While `queued` or `running`: "Added N of M rows" and a `<progress>`, in a fragment from
   `learner_import_status` polled with `hx-trigger="every 2s"`. When done, the fragment comes back
   without the trigger and holds the final result. The text sits in a `role="status"` region.
2. Done: the headline "Added N learners. M rows were skipped.", counts per final outcome in the
   preview's order and wording, "N setup emails were sent.", the first 50 error rows inline, the
   error CSV link, a link to the cohort's learners tab (cohort import) or the learners list, and
   "Import another file". It also says re-uploading the whole file is safe: rows already added
   show as "already a member".
3. Failed: "Stopped after N of M rows", the reason, and the same re-upload line.

**Error rows CSV (`learner_import_errors`).** Header `email,first_name,last_name,cohort,reason`.
It holds the rows whose `outcome` is `error`, or whose `preview_label` is `error` while uncommitted.
Original cell values. A UTF-8 BOM. `escape_csv_formula` on every cell, header included. The file
name is `learner-import-errors-<YYYY-MM-DD>.csv`. Written by a helper in `base/csv_import.py`
(`write_error_csv(header, rows)`) that streams like the table export.

### R6. Bulk actions

`freedom_ls/educator_interface/actions.py`, `freedom_ls/educator_interface/forms.py`,
`freedom_ls/educator_interface/views.py` (`LearnerConfig.get_bulk_actions`,
`CohortConfig.get_bulk_actions`), `freedom_ls/educator_interface/models.py`, `tasks.py`.

**Base class.** `EducatorBulkAction(BulkAction)` in `actions.py` adds:

- `has_permission(request)`: true when the user holds the single action's capability on at least
  one object of that kind in the organisation. When it is false for every action, the checkbox
  column does not render (spec 2's existing rule).
- `classify`/`apply`: first check `can(user, capability, scope)` with the same scope object the
  single action uses (the learner, the cohort, or the target cohort for membership). A failed check
  is `skipped` with "you can't manage them".
- `execute`: snapshots the resolved keys into a new `BulkActionRun`. At or below the threshold it
  runs `run_bulk_action` inline and the modal swaps to the result summary: counts and the skipped
  rows with reasons, first 20. Closing it fires the table's changed event so the table refreshes.
  Above the threshold it enqueues the task and redirects to the run's result page.

`BulkActionRun(SiteAwareModel)`: UUID `id`, `organisation`, `requested_by`, `table_key` and
`action_name` (which action), `target` (JSON, e.g. `{"cohort": "<pk>"}`), `keys` (JSON list,
the snapshot), `status` (`queued`, `running`, `done`, `failed`), `processed_count`, `result` (JSON
of counts and per-object `{key, row_label, status, reason}`), `error_message`, `created_at`,
`started_at`, `finished_at`.

`run_bulk_action(run_id, site_id)` follows `run_learner_import`. It looks up the action through a
registry in `actions.py` keyed by `(table_key, action_name)`, re-resolves the target from `target`,
and loads each key with `_base_manager` scoped to the organisation. A key that no longer resolves
is `skipped` with "no longer exists". Each `apply` call re-checks permission for `requested_by`.

Result page: `organisations/<slug>/bulk-runs/<uuid>` (`bulk_action_run`) and its polled fragment
`organisations/<slug>/bulk-runs/<uuid>/status` (`bulk_action_run_status`). They behave like the
import result page and link back to the table.

**Learners list actions.** Each reuses the single action's capability, consequence wording
(`educator_interface/templates/educator_interface/modal/*_confirmation.html`, pluralised with
`count_phrase`) and service:

| Bulk action | Single action it mirrors | Target picker | Service | Skipped when |
| --- | --- | --- | --- | --- |
| Add to cohort | `AddToCohortAction` | active cohort the user can add members to | `add_to_cohort` | already a member |
| Remove from cohort | `RemoveFromCohortAction` | cohort the user can remove members from | `remove_from_cohort` | not a member |
| Register for a course | `RegisterLearnerForCourseAction` | course, from the single form's queryset | `register_for_course` | already registered individually |
| Unregister from a course | `UnregisterLearnerFromCourseAction` | course | `unregister_from_course` | no individual registration |
| Deactivate | `DeactivateLearnerAction` | none | `deactivate_learner` | already inactive |
| Reactivate | `ReactivateLearnerAction` | none | `reactivate_learner` | already active |
| Resend setup email | `ResendSetupEmailAction` | none | `resend_account_setup_email` | `AccountAlreadySetUp` ("account already set up"), `SetupEmailRecentlySent` ("setup email sent recently") |

- Remove from cohort's confirmation names the courses the learners lose access to, through
  `courses_losing_access`.
- Unregister's confirmation says how many keep access through a cohort, through `other_grants_for`.
- Register's confirmation says each learner is notified.

**Cohorts list actions.**

| Bulk action | Single action it mirrors | Target picker | Service | Skipped when |
| --- | --- | --- | --- | --- |
| Register for a course | `RegisterCohortForCourseAction` | course | `register_cohort_for_course` | inactive cohort, already registered |
| Unregister from a course | `UnregisterCohortFromCourseAction` | course | `unregister_cohort_from_course` on the cohort's registration | inactive cohort, not registered |
| Deactivate | `DeactivateCohortAction` | none | `deactivate_cohort` | already inactive |
| Reactivate | `ReactivateCohortAction` | none | `reactivate_cohort` | already active |

The bulk pickers are new forms in `forms.py`, not tied to one object. They offer every target the
user may act on in the organisation, rather than excluding targets one object already has.

**Action bar.** The two most-used actions of each table show in the bar, with the rest under "More
actions". Add to cohort and Remove from cohort sit next to each other. Deactivate and unregister
use the destructive button style, and initial focus lands on Cancel.

## Testing

Unit and view tests (`fls-dev:testing` markers and site-aware fixtures):

- Parsing: BOM header, semicolon file, `.xlsx` bytes, undecodable bytes, malformed quoting, blank
  rows skipped, over-row-cap rejected with the count, missing `email`, unknown header, repeated
  header. Each rejection is a 422 that stores nothing.
- Classification: every label, every error reason, within-file duplicate, cohort by name
  (case-insensitive, inactive, invisible to the user), cohort column ignored on the cohort entry
  point, the `added_to_cohort` case.
- `classify_learner_entry` returns what `add_learner` then does, for every branch, with no writes.
- Commit: valid rows commit when other rows are errors; a row whose state changed after preview
  reports its real outcome; a second import of the same file gives `already_member` on every row
  and sends no email; a double confirm runs once; a task interrupted mid-file resumes without
  repeating rows; names of an existing user are unchanged; the setup email goes only to new
  accounts.
- Background path: with the threshold set low and `TASKS` on the database backend
  (`transaction=True`), confirm enqueues and the result page shows the queued state; at or below
  the threshold nothing is enqueued.
- Permission: lost capability between preview and commit fails the run; another organisation's
  import is a 404; another user's import or run is a 404; a user without `bulk_manage_learners`
  gets 403 on the import routes.
- Error CSV: formula cells are escaped, the BOM is present, and the reason column is last.
- `all_matching`: resolves through the table's filters, honours `excluded`, ignores undeclared
  parameters, never crosses the panel's scope; an `expected_count` mismatch is a 422.
- Each bulk action: changed, skipped and not-permitted objects counted correctly, using the single
  action's service (its webhook fires once per changed object, none per skipped one). A
  `cohort_admin` sees learner bulk actions and acts only on learners in their cohorts.
- `deactivate_cohort`/`reactivate_cohort` and the single cohort state actions still pass their

## Success criteria

- A 30-row file with two bad emails previews 28 valid rows and 2 errors. Confirming adds the 28 and
  the error CSV holds exactly the 2, with reasons.
- Uploading the same file again previews every valid row as `already_member`, and confirming sends
  no email.
- No existing user's first or last name changes through an import.
- A file with an unknown header is rejected at upload with a message naming it.
- With the threshold at 5, a 10-row import enqueues a task and its result page polls until done.
- A `cohort_admin` can bulk-add learners to their cohort, and learners outside their cohorts are
  reported as skipped.
- "Select all N matching" on a filtered learners list acts on exactly the N rows the filter matched
  at confirm time, minus the excluded ones.
- Every learner bulk add has a bulk remove beside it in the action bar.
- Import and run records past their expiry or retention are gone after `fls_run_housekeeping`.
