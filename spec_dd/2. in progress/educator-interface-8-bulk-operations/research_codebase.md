## 2. Row selection and bulk actions (spec 2): a seam, with gaps

`freedom_ls/panel_framework/bulk_actions.py` holds `BulkAction`, `Selection`, `parse_selection` and `resolve_selection`. `freedom_ls/panel_framework/views.py` holds `_handle_bulk_action` (about line 608) and `_BulkConfirmation`.

- `BulkAction` has `label`, `action_name`, `max_rows = 500`, `confirm_template_name`, `has_permission(request)` and `execute(request, queryset) -> None`. Its URL is `<table base_url>/__actions/<action_name>`.
- The flow is: POST, then permission (403), then selection, then a 422 if the count is 0 or over `max_rows`, then a confirmation modal with the count, then a POST with `confirmed=1` that calls `execute` and redirects to the table URL (`HX-Redirect` for htmx, 303 otherwise).
- Registration: `DataTablePanel.get_bulk_actions()` (`panels.py:271`) and `ListViewConfig.get_bulk_actions(request)` (`views.py:253`). Both default to `[]`. The checkbox column, header checkbox and selection bar render only when at least one registered action passes `has_permission`. Spec 6 and spec 7 both say the selection column "appears when spec 8 registers its actions".
- `LearnerDataTable.get_row_label` exists (`educator_interface/views.py:531`). `CohortDataTable` (line 309) has no declared label. Check it.
- **Gap 1: "select all matching the current filter" is not shipped.** `Selection.mode == "all_matching"` parses, but `_handle_bulk_action` answers 422 "Not supported yet". `resolve_selection` handles `keys` only. The spec 2 spec reserved the payload (`query_string`, `excluded`) and said the table-state serialiser (spec 2 line 72, the filter/search/sort parameters) would be reused. There is also no "select all N matching" banner in the UI. Spec 8 must either build it (resolver, banner, `excluded`) or declare it out and keep the page-selection limit. The idea says "if spec 2 shipped it", so the answer is no.
- **Gap 2: `BulkAction` is too thin for the idea.** `execute(request, queryset)` returns `None`. There is no per-object permission hook, no target picker (cohort or course), no per-object result and no way to report skipped or failed rows. `has_permission(request)` is request-only. The only confirmation template is a generic "This will affect N noun" (`panel_framework/partials/bulk_confirmation.html`, `bulk_confirmation_message.html`, `bulk_confirmation_form.html`). Spec 8 has to extend it: a picker form step, wording that matches the single actions, and a result summary instead of a silent redirect. Where the extension goes (a `BulkAction` subclass in `educator_interface`, or a framework change) is a decision for the spec.
- **Gap 3: `max_rows = 500` is a hard 422, with no truncation.** It sits below Django's `DATA_UPLOAD_MAX_NUMBER_FIELDS` (1000), because the keys travel as form fields. The idea's "large selections go through the background path" collides with this cap. Selections over the background threshold but under 500 are possible. Anything above 500 needs `all_matching`, which is not built.
- The selection is cleared on every table swap (the Alpine component `tableSelection`) and never lives in the URL. The only existing `BulkAction` is a test stub (`panel_framework/tests/stub_panels.py`, `test_bulk_actions.py`).
- A hit from the old TODO block in `educator_interface/views.py:228-237` ("Checkboxes and bulk actions", "Export as csv") is still in place. Export as csv is done (spec 2, see section 8). Per CLAUDE.md, a TODO is deleted only when done, so spec 8 should trim only the "Checkboxes and bulk actions" lines once they are done. The other lines in that block (searchable dropdown filters, instance edit, send_email) are not this spec's.

## 3. The add-learner path (spec 7): reuse it, with caveats

`freedom_ls/learner_management/learner_actions.py` is "the single seam": one transaction, no request, webhook events on commit.

- `add_learners(organisation, entries: list[LearnerEntry], cohort=None) -> list[AddLearnerResult]` is atomic over **all** entries, dedupes by lowercase email, and raises `ValueError` before writing if the cohort is inactive or in another organisation. `_add_one` does: `validate_email`, then `match_or_create_user` (from `freedom_ls/accounts/account_setup.py`), then `ensure_learner`, then `reactivate_learner` if the learner is inactive, then `send_account_setup_email` for a new account, then `add_to_cohort`.
- Outcomes: `AddOutcome` is `CREATED`, `JOINED`, `REACTIVATED`, `ALREADY_LEARNER`, `INVALID_EMAIL`, `EMAIL_IN_USE_ELSEWHERE`. `CohortOutcome` is `ADDED`, `ALREADY_MEMBER`. These map onto the idea's preview labels:
  - new account is `CREATED`;
  - existing account joined is `JOINED`;
  - already a member is `ALREADY_LEARNER` with `ALREADY_MEMBER`;
  - reactivated is `REACTIVATED`;
  - error is `INVALID_EMAIL` or `EMAIL_IN_USE_ELSEWHERE`.
- **Gap 4: there is no dry-run.** `add_learners` writes immediately. The preview needs a read-only classifier that mirrors `_add_one`'s branches, using `lookup_user(site, email)` (read-only, raises `EmailInUseOnAnotherSite`) plus `Learner._base_manager.filter(user, organisation)` plus `CohortMembership` existence. Write it next to `_add_one` and share the branch logic, so preview and commit cannot drift. The idea says commit is "row by row", and the idea's default is valid rows commit and error rows are reported. That fits `_add_one` per row, but `add_learners`' single outer `transaction.atomic()` is all-or-nothing at the DB level; invalid rows return an outcome rather than raising, so they do not roll anything back. The unexpected-exception case (a real crash mid-batch) rolls the whole call back. A chunked loop calling `_add_one` (or `add_learners` per chunk) would limit that.
- The "already a member" label with no cohort given (import without a cohort) is `ALREADY_LEARNER` alone. The idea's wording "already a member" needs a decision: a member of the organisation, or of the cohort.
- A cohort passed to the import is matched by **name within the organisation** (new work). Cohort names are not unique in the model unless a constraint says so. Check `Cohort` for a unique constraint on `(organisation, name)` before relying on it. Resolve against `cohorts_visible_to(user, org, capability=ADD_COHORTMEMBERSHIP).filter(is_active=True)`, as `AddLearnersAction._cohorts` does (`educator_interface/actions.py` ~1114). `add_learners` takes one cohort for all entries, so a per-row `cohort` column means grouping rows by cohort and calling per group, or calling `_add_one` directly with each row's cohort.
- Idempotence holds already: `ensure_learner` is idempotent, `add_to_cohort` is `get_or_create`, and the second run gives `ALREADY_LEARNER` plus `ALREADY_MEMBER`. The setup email goes out only for newly created accounts. It is queued with `transaction.on_commit`, as is the webhook, so a task that wraps the loop in `atomic()` sends on commit.
- Existing users are never overwritten: `match_or_create_user` "Names are only used for a new user". This satisfies the idea's "never overwrite" rule.
- `AddLearnersAction` / `AddLearnersToCohortAction` (`actions.py` ~1095-1200) is the interactive paste-emails flow, capped at 50 lines (spec 7 line 309: "larger lists are spec 8's CSV import"). `AddLearnersForm` is in `educator_interface/forms.py`. The result modal template is `educator_interface/modal/add_learners_results.html`. Reuse the outcome wording. Note the 50-line cap: the CSV import is the replacement for bigger lists, so the add-learners modal should probably link to the import page.
- Fired webhook events: `learner.added` (with `account_created`), `learner.reactivated`, `cohort.member_added`, `cohort.member_removed`, all already in `FLS_WEBHOOK_EVENT_TYPES`. They fire per row, so a 500-row import fires hundreds of webhook tasks. Check that against the background setup.

## 5. Permission matrix

Defined in `freedom_ls/role_based_permissions/roles.py`. Roles: `site_admin`, `organisation_admin`, `cohort_admin`, `cohort_viewer` (spec 5 renamed three). `can(user, capability, scope_obj)` is in `learner_management/capabilities.py:170`. It resolves superuser, then site, then organisation, then cohort grants, covering a Learner through a `CohortMembership`. It ignores the object's `is_active`. The matrix test is `educator_interface/tests/invariants/test_permission_matrix.py` (symbols `BULK_MANAGE_LEARNERS`, `CHANGE_LEARNER`, ...). A new action capability or a new row must be added there too.

- `bulk_manage_learners` ("Can bulk manage learners") exists on `Learner.Meta.permissions` (`learner_management/models.py:83`, migration 0004), is in the registry (`registry.py:77`) and is held by `site_admin` and `organisation_admin` only (organisation scope). It is **not used by any view or action yet**; only the matrix test references it. The spec 5 table (`spec_dd/3. done/.../educator-interface-5-permissions/1. spec.md:55`) says "CSV import, bulk actions: `bulk_manage_learners` (organisation)". So the CSV import page is gated by `bulk_manage_learners` on the organisation, plus `add_learner` (pending-account creation).
- Who holds what for the single actions:
  - `change_learner` (deactivate, reactivate, resend): `site_admin`, `organisation_admin` only.
  - `add_learner`: `site_admin`, `organisation_admin` only.
  - `change_cohort`: `site_admin`, `organisation_admin` only.
  - `add_cohortmembership`, `delete_cohortmembership`, `add_/change_cohortcourseregistration`, `add_/change_learnercourseregistration`: also `cohort_admin`, on their cohorts.
- **Conflict to settle in the spec:** the idea says bulk actions are "offered only to roles the spec 5 matrix allows for the single action, and each object is checked server-side". A `cohort_admin` is allowed the cohort-membership and registration single actions but does not hold `bulk_manage_learners`, which is the only bulk-named capability. Choose one: (a) bulk actions require `bulk_manage_learners` as well as the single capability (a cohort admin gets no bulk actions), or (b) bulk is gated only by the single capability, with `bulk_manage_learners` for the import alone. The matrix test must encode the choice. Either way the check is per object with `can(user, capability, obj)`, as `MoveToCohortAction.handle_submit` does for the destination. The current `BulkAction.has_permission(request)` cannot see the objects, hence gap 2.
- Scope: `learners_visible_to`, `cohorts_visible_to` and `get_queryset` of the panel (what `resolve_selection` intersects) already bound a selection to what the user can see. Still check `can` on each, because a cohort admin can see a learner (via cohort A) without the right to change them.
- The denied experience: out-of-scope is a 404, a visible but forbidden action is 403 (`denied_response`) with who-to-ask copy. For a mixed bulk selection, the spec should decide whether a partly permitted selection is refused whole or run on the permitted objects and reported (the idea implies per-object checking, so skipped-with-reason).

## 9. Site-aware and multi-tenant implications

- `SiteAwareManager` ANDs the thread-local ambient site onto `objects`. In a task there is no ambient site (empty or wrong), so a task must pass `site_id` and use `_base_manager` with explicit site filters (as `reports/tasks.py` and the learner services do). The learner services already use `_base_manager` and write `site=learner.site`.
- `Learner` is one per `(user, organisation)` (`unique_learner_per_organisation`) and carries `site` and `organisation`. `lookup_user` spans all sites on purpose and refuses a match on another site (`EmailInUseOnAnotherSite`); an import row hitting that is an error row with a reason. The error message must not name the other account.
- Any new model for the job must be a `SiteAwareModel` and filter by organisation. Reads of it must go through the organisation-scoped request (`OrganisationScopedRequest`, `educator_interface/views.py`), and the import URL must live in the interface's organisation namespace so cross-organisation access is a 404 (`OrganisationScopeDenied`).
- Routing: `educator_interface/urls.py` has only three routes: `root`, `messages_unread_count`, and a catch-all `organisations/<slug>/<path_string>` served by `views.interface`. **A new import page does not slot in as a plain Django URL.** It would either be a new `re_path` placed **before** the catch-all, or a section/panel config registered in the framework (`OrganisationSectionConfig` subclasses such as `LearnerConfig`, `CohortConfig`, which have `get_actions` and `instance_view`). Check how `messages/unread-count` was added and how the framework resolves `__actions` paths. The "page, not a modal, with its own URL and Back works" requirement favours a `re_path`/view rendering inside the interface shell. Check `_base_interface.html` for the shell. A cohort-scoped entry point (`cohorts/<pk>/learners` tab with the cohort implied) can use a query parameter, as `AddLearnersAction._preset_cohort` does for `?cohort=<pk>`.
- Both entry points' buttons should be actions from `LearnerConfig.get_actions` (`AddLearnersAction()` today, line ~1067) and `CohortLearnersPanel.get_actions` (line ~805), gated by `bulk_manage_learners` and rendered as a link, not a modal trigger. Check that `PanelAction` supports a plain link trigger (a `trigger_template_name` other than `modal_trigger.html`).

`comparable-systems-learner-management.md` (`spec_dd/1. next/educator-interface-full-polish/`), section 3 "Bulk-only and bulk-first" (lines 88-100), is the relevant part:

- CSV import is bulk-only everywhere and is where account creation, "existing email" handling and group assignment meet. Moodle's Upload users does all three in one pass, with a preview, and offers four explicit modes for existing accounts. Docebo has an opt-in "update existing". TalentLMS upserts by username. Canvas links an existing login.
- Docebo runs any mass action over **250 users** as a background job. No other system documents a threshold, but their CSV imports are all asynchronous. This is the basis for the idea's "low hundreds" default; **250** is a defensible default.
- Bulk actions come in pairs where liked, alone where complained about (Moodle bulk add to cohort but no bulk remove, MDL-61007; TalentLMS pairs every add with a remove). This is the basis for "every add has its remove".
- Section 4 (audit and reversibility) and section 1 (a reversible off state is the default removal) support deactivate-not-delete and the audit entry. Open edX's batch enrolment box (one learner is a batch of one) is the pattern behind spec 7's paste dialog.

## 13. Conflicts, gaps and decisions to carry into the spec

1. No "select all matching" resolver or UI (gap 1). Decide: build it, or limit bulk selection to the 500-key page-selection cap and say so.
2. `BulkAction` lacks a per-object permission hook, a target picker, per-object results and a result summary (gap 2). The extension point must be chosen (framework change versus subclass).
3. `max_rows = 500` hard-fails; the idea's threshold (default about 250) means selections of 250-500 go to the background and above 500 are refused unless `all_matching` ships.
4. `add_learners` has no dry-run (gap 4); the preview needs a shared read-only classifier. Cohort given per row needs per-row calls.
5. No cohort deactivate/reactivate service (gap 5); extract one.
6. No job-record model, and the `ImmediateBackend` does not persist results (gap 6). A result needs a row of its own; the model's app and the poll or email choice follow from that. In dev and tests the "background" path runs inline, so polling shows the finished state at once.
7. `bulk_manage_learners` is defined but unused (section 5). The cohort admin question is open.
8. The mockup's step 2 is column mapping and its form is a modal, against the idea's page and preview (section 11).
9. URLs: `educator_interface/urls.py` is a catch-all; a new page route must go before it or be registered through the framework (section 9).
10. The old TODO in `educator_interface/views.py:228-233` covers bulk actions and export. Update, do not delete, the parts this spec does not complete.
11. Bulk register fires `comms` notifications and webhooks per learner; the setup email goes per new account. State this in the spec.
12. Roadmap says specs 8 and 9 "reuse the account-creation path that 7 builds" (match by email, or create and send setup email): that is `match_or_create_user` plus `send_account_setup_email`/`_add_one`. Do not write a second path.
