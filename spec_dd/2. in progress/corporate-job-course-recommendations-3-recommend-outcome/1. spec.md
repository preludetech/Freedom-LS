# Spec: Recommend outcome for registration rules

Spec 3 of 5 in the Registration rules effort. Scope and settled behaviour come from `idea.md` and
the "Registration rules" section of `spec_dd/1. next/roadmap.md`. It builds on spec 2's engine
(`spec_dd/3. done/2026-10-23_20:02_corporate-job-course-recommendations-2-registration-rules/1. spec.md`).
The evidence is in the `research_*.md` files beside this spec.

## Purpose

A registration rule can only register learners today. Some courses should be offered rather than
imposed. This spec adds the `recommend` outcome: a rule puts its course in each matching learner's
"Recommended courses" dashboard section by creating a `RecommendedCourse`, and removes it when the
learner stops matching. It also makes every registration path clear a stale recommendation.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| recommend rule | narrowed | A `RegistrationRule` with `outcome="recommend"` (`freedom_ls/registration_rules/models.py`). A rule with `outcome="register"` is a register rule. |
| recommendation source (`RuleRecommendation`) | coined | A row recording that one recommend rule wants one `RecommendedCourse` to exist. No existing term: `RuleRegistration` is one-to-one and single-owner. |
| rule-made recommendation | coined | A `RecommendedCourse` with at least one `RuleRecommendation`. |
| admin-made recommendation | coined | A `RecommendedCourse` with no `RuleRecommendation`, made in the Django admin or by a QA command. Rules never touch one. |
| registered (for a recommendation) | narrowed | The user-wide test in `is_registered_for_course_expression` (`freedom_ls/learner_management/queries.py`): an active registration through an active `Learner` in any organisation, or an access-granting cohort registration. |

## Scope

In:

- `RegistrationRule.Outcome.RECOMMEND`, chosen on the rule's add page.
- `RuleRecommendation` in the rules app; a uniqueness constraint on `RecommendedCourse`, with a
  migration that removes existing duplicates.
- Evaluation, preview, deletion and triggers for recommend rules, beside the register path.
- Clearing a user's recommendation whenever they become registered for its course, on every path.
- Re-evaluating a user when they stop being registered, so a still-matching recommend rule
  recommends again.
- Admin: the outcome field and column, rule provenance on `RecommendedCourseAdmin`, a warning on
  deleting a rule-made recommendation.

Out (from `idea.md`): dismissal, ranking, reasons or expiry on a recommendation; recommendations
from form answers (the commented-out `form_progress` FK stays); notifications and webhook events;
educator-interface screens (spec 4); CSV import (spec 5); any change to the dashboard templates.

## Decisions

1. **One source row per rule, not a single owner.** A `RecommendedCourse` exists while it has a
   `RuleRecommendation`; each rule adds and removes only its own. This answers the idea's
   organisation question: a rule touches only its own sources, so one organisation's rule never
   removes a recommendation another organisation's rule (or staff) wants, and no hand-over across
   organisations is needed. The row needs no organisation column; a source's organisation is its
   rule's.
2. **Provenance is a side table in the optional rules app**, as spec 2 did for registrations.
   `course_recommendations` gains no FK to the rules app; its only schema change is the
   constraint.
3. **A rule matches a user**, not a `Learner`: user U matches rule R when U's `Learner` in
   R's organisation (at most one, `unique_learner_per_organisation`) is returned by the kind's
   `matching_learners`. `RecommendedCourse` is keyed on `User`.
4. **A registered user is treated as not matching** a recommend rule, so evaluation never creates
   a recommendation for them and drops any source it still holds for them.
5. **The dashboard shows the union** of a user's recommendations across organisations, once per
   course. It gains no organisation filter.
6. **Retraction is a hard delete** of the `RecommendedCourse` when its last source goes. A
   recommendation holds no learner data, so spec 2's started-gate does not apply. A recommendation
   that comes back is a new row with a new `created_at`, so it sorts to the top of the section.
7. **Clearing lives in `course_recommendations`**, as receivers on `learner_management` models.
   This adds the runtime edge `course_recommendations -> learner_management` (no cycle) and keeps
   core apps ignorant of the rules app. The self-registration view's own delete goes.
8. **A rule's `outcome` is set on the add page and read-only afterwards**, like `organisation` and
   `course` (spec 2 decision 9). Switching would silently swap registrations for recommendations.
9. **Staff may delete a rule-made recommendation**; the delete page warns that it comes back while
   the rule still matches. Dismissal is out of scope.

## Requirements

### `RecommendedCourse` (`freedom_ls/course_recommendations/`)

- `models.py`: add `UniqueConstraint(fields=["site", "user", "course"],
  name="unique_recommended_course")`. Rewrite the stale class docstring ("Created when a parent
  fills out a form") and the module docstring to say rows are made by staff or by registration
  rules, one per user and course. Keep the "standalone and additive" sentence and the
  commented-out `form_progress` FK.
- Migrations: `0002` is a `RunPython` that, per (`site_id`, `user_id`, `course_id`), keeps the
  oldest row (`created_at`, then `id`) and deletes the rest, through `apps.get_model`, with
  `reverse_code=migrations.RunPython.noop`. `0003` adds the constraint and depends on `0002`.
- `admin.py`: `RecommendedCourseAdmin` gets a form using `ConstraintValidationFormMixin`
  (`freedom_ls/site_aware_models/forms.py`), so a duplicate add is a form error, not a 500
  (`site` is excluded from the form).
- `queries.py`: add `clear_registered_recommendations(site_id: int, user_ids: Iterable[UUID]) ->
  int`. It deletes, through `RecommendedCourse._base_manager`, every recommendation of
  those users for a course they are registered for, admin-made ones included, and returns the
  count. "Registered" uses the same conditions as `is_registered_for_course_expression`; add a
  set-based sibling in `freedom_ls/learner_management/queries.py` (for example
  `registered_course_pairs(site_id, user_ids) -> QuerySet` of (`user_id`, `course_id`)) so the
  two never drift. The rules app reuses that sibling for decision 4.
- New `signals.py`, connected from a `ready()` on `CourseRecommendationsConfig`. Each receiver
  skips `raw=True` and calls `clear_registered_recommendations` for the affected users:

  | Event | Users |
  | --- | --- |
  | `LearnerCourseRegistration` `post_save`, `is_active=True` | the learner's user |
  | `CohortCourseRegistration` `post_save`, `is_active=True` | users of the cohort's members |
  | `CohortMembership` `post_save`, created | the member's user |
  | `Cohort` `post_save`, `is_active=True` | users of the cohort's members |
  | `Learner` `post_save`, `is_active=True` | the learner's user |

  The registered check inside the function makes a receiver that fires when nothing changed
  harmless. Paths that bypass signals (`bulk_create`, `QuerySet.update()`) clear nothing; decision
  4 cleans up a rule's own sources on its next run.
- `freedom_ls/learner_interface/views.py`: delete the `RecommendedCourse.objects.filter(...)
  .delete()` after the self-registration `update_or_create` (line 913) and its import if unused.
  The `LearnerCourseRegistration` receiver covers it.

### Models (`freedom_ls/registration_rules/models.py`)

- `RegistrationRule.Outcome` gains `RECOMMEND = "recommend"`. Default stays `register`.
- `RuleRecommendation(SiteAwareModel)`:

  | Field | Type |
  | --- | --- |
  | `recommendation` | FK `freedom_ls_course_recommendations.RecommendedCourse`, CASCADE, `related_name="rule_recommendations"` |
  | `rule` | FK `RegistrationRule`, CASCADE, `related_name="rule_recommendations"` |

  `UniqueConstraint(fields=["site", "recommendation", "rule"], name="unique_rule_recommendation")`.
  A rule never adds a source to an admin-made recommendation.
- One migration, `0004`, for the choice change and the new model, depending on
  `freedom_ls_course_recommendations` `0003`.

### Evaluation (`freedom_ls/registration_rules/evaluation.py`)

- Every existing path that reads rules filters by outcome: `classify_rule_changes`,
  `apply_rule_changes` and `_hand_overs` see only register rules. A recommend rule never creates a
  `LearnerCourseRegistration` or a `RuleRegistration`.
- Add a read, `classify_recommendation_changes(rule, state, user_ids=None) ->
  RecommendationChanges`, and a write, `apply_recommendation_changes(rule, changes) ->
  EvaluationResult`. The preview runs the read alone. For rule R on course C:
  - **matched**: users of `matching_learners(state)`, minus registered users (decision 4).
  - `recommend`: matched users with no `RecommendedCourse` for C. The write creates the row and
    R's source in one savepoint; an `IntegrityError` on `unique_recommended_course` re-reads the
    row and adds R's source only if the row is rule-made.
  - `add_source`: matched users whose recommendation for C is rule-made and has no source from R.
  - Matched users with an admin-made recommendation: left alone.
  - `remove`: users R has a source for who are not matched, where R's is the only source. The write
    deletes the `RecommendedCourse`.
  - `drop_source`: the same, where other sources remain, with the other rules' names. The write
    deletes R's source only.
  - Adding a source to an existing row, and deleting a source or row, lock the `RecommendedCourse`
    with `select_for_update()` and re-check its sources inside the batch transaction, so two rules
    cannot race one row into a deleted-with-a-source or sourceless state.
- `RecommendationChanges` is a frozen dataclass of those four groups, by user pk.
  `EvaluationResult` gains `recommended` and `recommendations_removed` (user pks), merged by
  `merged_with`.
- `evaluate_rule` dispatches on `rule.outcome`. For a recommend rule its scope is every user R
  matches plus every user R has a source for, batched by `REGISTRATION_RULE_BATCH_SIZE` in user-pk
  order, with the same per-batch transaction, rule lock, switch re-read and `last_evaluated_at`
  handling as the register path. A disabled rule matches nobody, so its run removes all its
  sources (the idea's "disabling counts as every learner unmatching").
- `evaluate_learner(learner_id, site_id)` also runs every enabled recommend rule of the learner's
  organisation, and every rule with a source on a recommendation of the learner's user, scoped to
  that user. It keeps the `Learner` lock; the row locks above cover the same user evaluated through
  two `Learner` rows at once.
- `evaluate_organisation` needs no change: it runs `evaluate_rule` per rule.
- The organisation switch gates recommend rules through the existing `rules_enabled_for` early
  returns. Off means nothing is evaluated and existing recommendations stay.

### Triggers (`freedom_ls/registration_rules/signals.py`)

- Spec 2's triggers carry the new outcome unchanged. `_learner_needs_evaluation` is also true when
  any rule has a source on a recommendation of the learner's user.
- New: when a user may have stopped being registered for a course, enqueue `evaluate_learner` for
  each of the user's active `Learner`s whose organisation has an enabled recommend rule on that
  course and its switch on:

  | Event | Users and courses |
  | --- | --- |
  | `LearnerCourseRegistration` `post_save` with `is_active=False`, or `post_delete` | the learner's user, that course |
  | `CohortCourseRegistration` `post_save` with `is_active=False`, or `post_delete` | each member's user, that course |
  | `CohortMembership` `post_delete` | the member's user, the cohort's registered courses |
  | `Cohort` `post_save` with `is_active=False` | each member's user, the cohort's registered courses |
  | `Learner` `post_save` with `is_active=False` | the user's other `Learner`s, courses registered through this one |

  Each skips `raw=True` and enqueues through `_enqueue_once` after commit. A register rule's own
  retraction also fires the first row. That is wanted, because a learner a register rule lets go
  of can then be recommended the course.

### Deletion

- `_delete_refusal` (`admin.py`) also refuses a disabled rule whose last change is unapplied while
  it has any `RuleRecommendation`: "Rule still removing its recommendations: {name}".
- `snapshot_rule_name_before_delete`'s `pre_delete` path also deletes every `RecommendedCourse`
  whose only source is the rule, so a CASCADE never leaves a rule-made row looking admin-made.

### Admin (`freedom_ls/registration_rules/admin.py`)

- `RegistrationRuleAdmin`: `outcome` on the add page as radio buttons, with help text in learner
  terms ("Register: matching learners are registered. Recommend: the course appears in their
  Recommended courses and they choose whether to register."); read-only on the change page
  (decision 8). Add `outcome` to `list_display` and `list_filter`.
- `_change_form_warnings`: for a recommend rule on an unpublished course, "This course is not
  published. The rule still recommends it, but learners will not see the recommendation until it
  is."
- Preview (`_render_preview`, `admin/registration_rules/preview.html`): a recommend rule runs
  `classify_recommendation_changes` against the same submitted `RuleState` and shows "Will be
  recommended" (`recommend`), "Recommendation will be removed" (`remove`) and "Stops matching but
  stays recommended" (`drop_source`, reason "Also recommended by {rule names}"), each a full list
  of user name and email with counts in the headings, behind the same `view_learner` permission
  gate and switch-off notice. A recommend rule's preview never shows the register headings or
  "Started the course". `add_source` is not listed: nothing changes on that learner's dashboard.
- `RecommendedCourseAdmin`, wired at import time from the rules app as `registration_rule` is
  wired onto `LearnerCourseRegistrationAdmin`:
  - a read-only "Registration rules" field listing the source rules as links, blank for an
    admin-made recommendation;
  - a "Made by" `list_display` column (the rule names, or "Staff") and a `list_filter` with
    "Registration rule" and "Staff";
  - on the delete confirmation page, single or bulk, a warning when any selected row is rule-made:
    it comes back on the next evaluation while the rule still matches; disable or change the rule
    instead.

### QA helpers (`freedom_ls/qa_helpers/management/commands/`)

`qa_create_rich_dashboard_learner` and `qa_extend_start_here_section` create recommendations and
registrations for the same learner. Check each still produces the dashboard it was written for
now that registering clears a recommendation, and that none creates a duplicate the constraint
rejects.

## Testing

Recommend-outcome tests go in `freedom_ls/registration_rules/tests/`, with a `RuleRecommendationFactory`
in `freedom_ls/registration_rules/factories.py`. Clearing tests go in
`freedom_ls/course_recommendations/tests/`, which must not import the rules app.

To prove:

- Migration: duplicate rows for one (site, user, course) collapse to the oldest; distinct rows and
  other sites are untouched; the constraint then holds.
- Admin form: adding a duplicate recommendation shows a form error.
- Recommend: a matching user gets one `RecommendedCourse` and one source; a second evaluation
  creates nothing; a recommend rule creates no registration and no `RuleRegistration`.
- No takeover: a matching user with an admin-made recommendation keeps it with no source; the rule
  unmatching or being disabled leaves it.
- Registered users skipped: via an individual registration, a cohort registration, and a
  registration through the user's `Learner` in another organisation; a rule-made recommendation
  for a user registered through `bulk_create` is removed on the rule's next run.
- Unmatch and disable: the recommendation is deleted; with a second enabled rule (same or other
  organisation) also sourcing it, only the first rule's source goes and the row stays; disabling
  both removes it.
- Two organisations: user U in organisations A and B, a recommend rule in each on one course; U
  sees one recommendation with two sources; A's rule unmatching leaves it; neither rule's run
  reads or writes the other's sources.
- Concurrency: a create racing an existing row joins or skips per the rules above; a source removal
  racing a source add leaves a row with a source or no row.
- Switch off: no trigger changes anything and existing recommendations stay; turning it on catches up.
- Clearing, each row of the clearing table: the user's recommendation for that course is deleted,
  admin-made and rule-made; an inactive registration, an inactive `Learner` or an inactive cohort
  clears nothing; self-registration still clears (the first test of that path).
- Re-recommend, each row of the trigger table: after the registration stops granting access, the
  still-matching user is recommended again; a user still registered another way is not.
- Register rules unaffected: a register and a recommend rule on one course, `_hand_overs` never
  offers the recommend rule; spec 2's existing tests pass unchanged.
- Deletion: refused while a disabled recommend rule's run is pending and it holds sources; deleting
  a rule removes recommendations it alone sourced.
- Preview: for edit, enable and disable, the three lists match what the confirmed save then does;
  the "Also recommended by" reason names the other rule; a recommend rule's page shows no register
  headings.
- Admin: `outcome` is on the add page and read-only on the change page; the "Made by" column,
  filter and "Registration rules" field render; the delete page warns for a rule-made row only.
- Tasks run with no request against two sites and touch only the given site.
- With `freedom_ls.registration_rules` removed from `INSTALLED_APPS`, the dashboard, clearing and
  `RecommendedCourseAdmin` tests pass.
- One Playwright flow (`fls-dev:playwright-tests`): create a recommend rule, enable it, confirm the
  preview, see the course under "Recommended courses" on the learner's dashboard, register, and
  see it move to the learner's current courses.

## Open questions

Defaults taken; overrule any of them:

- A recommendation that disappears tells the learner nothing (no notification, no reason).
- No cap on how many recommendations a rule creates; the dashboard section is already paginated.
- The idea's Totara "visible learning" example is catalogue gating, not a recommendation; SAP
  SuccessFactors and Arcoro are the precedents (`research_reference_implementations.md` §1).
