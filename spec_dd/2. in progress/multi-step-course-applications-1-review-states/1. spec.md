# Spec: Application review states

Spec 1 of 11 in the Multi-step course applications effort (`spec_dd/1. next/roadmap.md`). Inputs: `idea.md`,
`answers.md` and the `research_*.md` files beside this spec.

## Purpose

A `CourseApplication` has no state today. Whether it is submitted is worked out from its form sitting, and
nothing can approve, reject or withdraw it. This spec adds a stored state and an organisation, the service
functions that change the state, and the applicant-facing surfaces: the status page in plain words, the reject
message, withdraw, and "apply again" after a closed application. Approve and reject are service functions with
no screen.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| open application | coined | `state` is `draft` or `submitted`: the applicant can still withdraw it. |
| active application | coined | `state` is `draft`, `submitted` or `approved`: at most one per (site, user, course). |
| closed application | coined | `state` is `rejected` or `withdrawn`: the applicant may apply again. |
| reject message | coined | `CourseApplication.rejection_message`, the reviewer's text the applicant reads. |

## Scope

In:

- `CourseApplication.state`, `organisation`, `submitted_at`, `decided_at`, `withdrawn_at`, `rejection_message`, and
  migrations that fill them for existing rows.
- Service functions `submit_application`, `withdraw_application`, `approve_application`, `reject_application`.
- The partial unique constraint over active applications, and every lookup that assumed one application per
  account and course.
- Status page, withdraw with a confirm dialog, dashboard panel, course CTA, claim rule, API, export and admin.
- Audit actions `application.approved` and `application.rejected`, their glossary entries and README rows.

Out: the reviewer role, inbox and review screen, and moving applications between organisations
(`multi-step-course-applications-2-reviewers-and-inbox`); registering the applicant on approval
(`multi-step-course-applications-3-approval-outcome`); reopening the form (`multi-step-course-applications-4-reopen-form`);
requirements; email; `application.*` webhooks; Django admin review actions; copying answers into a new application
when applying again; undoing a decision or a withdraw.

## Decisions

1. **`approved` counts as active.** An approved applicant cannot start a second application for the course, so the
   partial index covers `draft`, `submitted` and `approved`. Only a rejected or withdrawn application lets the
   applicant apply again.
2. **Every closed state is final.** No state returns to `draft` or `submitted` in this spec, so the claim rule needs
   nothing beyond "prefer the active application".
3. **Timestamps are stored, one per fact.** `submitted_at` (set by submit), `decided_at` (approve or reject; the state
   says which), `withdrawn_at`. No `approved_at`/`rejected_at` pair, which would allow both being set at once. No
   `decided_by` field: the audit entry holds the actor.
4. **`is_submitted` means `submitted_at is not None`.** An application withdrawn from `draft` was never submitted; one
   withdrawn after submitting was. `submitted_time` returns `submitted_at`. Both stay on the model and in the API.
5. **The reject message is required, stored on the application and set once.** It is stricter than the reference
   systems on purpose (`answers.md`). It never goes into the audit entry.
6. **Approve and reject act on `submitted` only** (`answers.md`). Withdraw acts on `draft` and `submitted`. Submit acts
   on `draft`. A repeated action on an application already in the target state is refused like any other, so a
   double-clicked withdraw raises and the view shows the current state.
7. **Withdraw is offered to claimed applications only** (assumed default, see Open questions). An unclaimed applicant
   sees its state and any reject message, and claims the application to withdraw or apply again.

## Requirements

### Model: `freedom_ls/course_applications/models.py`

- `CourseApplication.State(models.TextChoices)`: `DRAFT = "draft"`, `SUBMITTED = "submitted"`, `APPROVED = "approved"`,
  `REJECTED = "rejected"`, `WITHDRAWN = "withdrawn"`. Module constants `OPEN_STATES`, `ACTIVE_STATES` and `CLOSED_STATES`
  hold the sets from Terminology. A comment beside `ACTIVE_STATES` says the constraint condition repeats it and changing
  it needs a migration.
- Fields:
  - `state = CharField(max_length=20, choices=State.choices, default=State.DRAFT)`.
  - `organisation = ForeignKey("freedom_ls_organisations.Organisation", on_delete=PROTECT, related_name="course_applications")`, non-null after the migrations.
  - `submitted_at`, `decided_at`, `withdrawn_at`: nullable `DateTimeField`s, written only by the service functions and
    the data migration.
  - `rejection_message = TextField(blank=True)`. The services cap it at `REJECTION_MESSAGE_MAX_LENGTH = 2000`.
- Constraints:
  - Remove `unique_application_per_site_user_course`. Add
    `UniqueConstraint(fields=["site", "user", "course"], condition=Q(state__in=["draft", "submitted", "approved"]), name="unique_active_application_per_site_user_course")`.
    Unclaimed applications (`user` null) are not constrained, as today.
  - `CheckConstraint`s: `submitted_at` is set when `state` is `submitted`, `approved` or `rejected`; `decided_at` is set
    exactly when `state` is `approved` or `rejected`; `withdrawn_at` is set exactly when `state` is `withdrawn`;
    `rejection_message` is non-empty exactly when `state` is `rejected`.
- `is_submitted` and `submitted_time` follow Decision 4 and stop reading `form_progress`.
- New property `is_open` (`state in OPEN_STATES`), which the templates use instead of naming states.
- Rewrite the module docstring and the class docstring NOTE to describe what exists now: `TextChoices` plus service
  functions in `transitions.py`, audit through `audit_log`, no FSM, no transition table, no signal.

### Migrations: `freedom_ls/course_applications/migrations/` (from `0009`)

Three migrations, in this order, because the constraint condition reads `state` and the check constraints need filled
rows:

1. Add `state` (default `draft`), nullable `organisation`, the three timestamps and `rejection_message`.
2. `RunPython(backfill, RunPython.noop)` with historical models only:
   - No sitting, or a completed sitting: `state="submitted"`, `submitted_at` = `form_progress.completed_time`, else
     `created_at`. An open sitting: `state="draft"`.
   - `organisation`: the course's only row in `Course.organisations` when it has exactly one (count over the M2M in
     SQL), otherwise the organisation with `is_default=True` for the application's own `site_id`. A site with no default
     organisation raises with a message naming the site. Never leave a null.
   - Set `updated_at` to the migration time on every row so API consumers polling `updated_since` see the new fields.
     The migration cannot import `touch_application_updated_at`.
3. Make `organisation` non-null; remove the old constraint and add the partial one in the same migration; add the check
   constraints.

Run `uv run manage.py makemigrations` and `migrate`; never edit `0001` to `0008`.

### Service functions: new `freedom_ls/course_applications/transitions.py`

House style for each one: one `transaction.atomic()`; lock the bare row with
`CourseApplication._base_manager.select_for_update().get(pk=...)` (no `select_related`, since `user`, `form_progress`
and `anonymous_applicant` are nullable joins that `FOR UPDATE` refuses); check the state against one `ALLOWED_FROM`
mapping; write the state and timestamp from a single `timezone.now()` with `save()` (or `update_fields` that include
`updated_at`); return the locked instance.

| Function | Allowed from | Writes | Audit |
| --- | --- | --- | --- |
| `submit_application(application)` | `draft` | `state=submitted`, `submitted_at` | none |
| `withdraw_application(application)` | `draft`, `submitted` | `state=withdrawn`, `withdrawn_at` | none |
| `approve_application(application, *, actor: User)` | `submitted`, and `user` is set | `state=approved`, `decided_at` | `application.approved` |
| `reject_application(application, *, actor: User, message: str)` | `submitted` | `state=rejected`, `decided_at`, `rejection_message` | `application.rejected` |

- Exceptions in `freedom_ls/course_applications/exceptions.py`: base `ApplicationTransitionError`, with
  `ApplicationStateError` (wrong current state; carries the current state), `UnclaimedApplicationError` (approve with no
  `user`), `RejectionMessageError` (message empty after stripping whitespace, or over the cap; checked before locking).
- A refused call writes nothing: no state change, no `updated_at` move, no audit entry.
- Audit entries go through `audit_log.writer.record_entry` inside the same transaction, only after the state changed:
  `actor=actor`, `target=application`, `target_label=f"{course.title} application {application.pk}"`,
  `organisation=application.organisation`, `subjects=(application.course,)`,
  `details={"from": "submitted", "to": "approved" | "rejected"}` (`TextChoices` values). No entry carries the applicant's
  name or email, or the reject message.
- `course_access.analytics_events.record_application_submitted` stays in the views, after the service call commits.

### Creating and submitting: `freedom_ls/course_applications/views.py`

- `_start_application`: look up the account's (or anonymous applicant's) active application instead of
  `get_or_create(course=..., user=...)` over every row. Create a new row only when none is active. On create, set
  `organisation` with a new helper `organisation_for_new_application(course)` in `queries.py`, which reads
  `course.organisations.all()` directly. `Course.single_organisation()` returns `None` for the default organisation,
  so it does not fit. A course with no form is created `draft` and submitted with `submit_application` in the same
  transaction. An `IntegrityError` from two racing creates is caught inside a savepoint, and the existing active row is
  returned.
- `apply`: an existing active application redirects to its status page as today. A closed one falls through to start a
  new application, and the coming-soon redirect applies to it.
- `application_check_answers`: `form_progress.complete()` and `submit_application(app)` run in one
  `transaction.atomic()`. A non-draft application cannot be submitted again: its POST redirects to the status page.
- Every reader that tested `form_progress.completed_time` for "submitted" reads state instead:
  `application_status` (the draft redirect fires only for `state == draft`), `application_form_page` (`read_only`
  unless `state == draft`), `_owned_application_with_form`, `applicant_details`, `claim_application`
  (`held_application` reads the account's active application), and the anonymous dashboard branch in `backends.py`
  (`state="draft"`). A withdrawn or rejected application's form pages accept no writes.

### Withdraw

- New view `withdraw_application` at `status/<uuid:pk>/withdraw/`, `name="withdraw"`, `@require_POST`, following
  `change_applicant_email`: `_owned_application(..., next_url=status_url)`, 404 for an application the session or account
  does not own, and 404 for an unclaimed one (Decision 7).
- On success: redirect to the status page with the message "Application withdrawn.". On `ApplicationStateError`:
  redirect to the status page with "This application can no longer be withdrawn." (HTMX request: 422 with the same
  message.)
- The confirm dialog is a new CSP-safe Alpine component `withdrawDialog` in
  `freedom_ls/course_applications/static/course_applications/js/alpine-components.js`, registered on `alpine:init`
  beside `claimLinkNotice`. It gives the same behaviour as `makeConfirmDialog` in `learner_interface`: focus trap,
  Escape closes it, focus returns to the trigger. `course_applications` must not import from `learner_interface`.
  Without JavaScript the trigger is a plain form that still POSTs.

### Status page: `templates/course_applications/application_status.html`

Each state has a heading, one sentence on what is true now and what happens next, and a chip. Dates use `<c-date>`.
`head_title` includes the state.

| State | Chip (variant) | Heading | Body | Actions |
| --- | --- | --- | --- | --- |
| draft | Not submitted (warning) | Your application | "You started your application for {course} but have not submitted it." | Continue application; Withdraw application |
| submitted | Awaiting review (info) | Your application | "Your application for {course} is waiting for review. The decision will show here." Submitted {date}. | Withdraw application |
| approved | Approved (success) | Your application was approved | "Your application for {course} was approved on {date}." | Back to dashboard |
| rejected | Not approved (neutral) | Your application was not approved | "Your application for {course} was not approved on {date}." Then a region headed "Message from the reviewer" holding the reject message, escaped, line breaks kept. Then "You can apply again." | Apply again |
| withdrawn | Withdrawn (neutral) | You withdrew your application | "You withdrew your application for {course} on {date}. Nobody will review it." | Apply again |

- The approved row promises nothing about course access; `multi-step-course-applications-3-approval-outcome` adds the
  next step.
- Drop "You will be notified once a decision has been made": no email is sent.
- Unclaimed applications keep the "Check your email" claim notice and also show the state block. "Apply again" and
  withdraw are not shown to them.
- Confirm dialog copy: title "Withdraw your application?"; body for a draft "Your application for {course} is a draft.
  If you withdraw it, nobody will review it. You can apply again later."; for submitted "Your application for {course}
  is waiting for review. If you withdraw it, nobody will review it. You can apply again later."; buttons
  "Keep application" and "Withdraw application".
- The success toast in `application_check_answers` changes "pending review" to "waiting for review".
- Rewrite the template NOTE comment and the `apply` and `application_status` docstring NOTEs to match what now exists.

### Dashboard panel: `queries.py`, `backends.py`, `templates/course_applications/partials/dashboard_applications.html`

- Rename `get_active_applications(user)` to `get_dashboard_applications(user)` and update its callers. It returns the
  account's active applications, plus each rejected application that no newer application for the same course has

- Rows use the status page's chips. Draft: the existing hint and "Continue application". Submitted and approved: "View my

### Course CTA: `backends.py` `ApplicationCourseAccessBackend._gated_decision`, `queries.get_application_for_course`

- An active application: "View my application" (unchanged). A closed one: "Apply again" to `course_applications:apply`,

### Claim: `freedom_ls/course_applications/claims.py` `attach_to_user`, `receivers.adopt_anonymous_applications_on_login`

Keep the user-row lock. `held` becomes the account's active application for the course (closed ones are ignored and
never deleted). Rule, with incoming as the anonymous applicant's application:

| Held (account, active) | Incoming | Result |
| --- | --- | --- |
| none | any | incoming attaches |
| any | `rejected` or `withdrawn` | incoming attaches beside it (no index collision) |
| `submitted` or `approved` | `draft` or `submitted` | held wins; incoming erased with its applicant |
| `draft` | `draft` or `submitted` | incoming wins; held discarded with `_discard_draft` |

`adopt_anonymous_applications_on_login` picks its toast verb from `result.application.is_submitted` as today.

## Testing

- **Transitions:** parametrised over every (function, from-state) pair: allowed ones change state and timestamp and move
  `updated_at`; refused ones raise `ApplicationStateError` and change nothing. Approve with no `user` raises
  `UnclaimedApplicationError`. Reject with an empty, whitespace-only or over-cap message raises
  `RejectionMessageError`. A `transaction=True` test where two calls race: the second is refused.
- **Audit:** exactly one entry per approve or reject, with `from`/`to`, the course as subject and the application's
  organisation. None for a refused call, for submit or for withdraw. No entry contains the applicant's name, email or
  the reject message.
- **Migrations:** seeded rows covering no sitting, completed sitting and open sitting, each with and without a user,
  across two sites; courses with zero, one and two owning organisations. Assert state, `submitted_at`,
  `organisation` and moved `updated_at`. A site with no default organisation raises.
- **Constraints:** a second active application for the same (site, user, course) is refused; a new one after reject or
  withdraw is allowed; each check constraint rejects a row that breaks it.
- **Views:** a form-less course submits at creation; check answers submits once; a closed application's form pages
  refuse writes; withdraw is POST-only, owner-only, 404 when unclaimed, and refused from a closed state; apply after a
  closed application creates a new row; the status page renders each state's copy and the reject message escaped.
- **Claim:** one test per row of the claim table, including a held closed application left untouched.
- **Panel and CTA:** each state's chip and buttons; a rejected application hidden once superseded; withdrawn never
  shown; CTA for active, closed and none; query counts stay bounded.
- **API, export, admin:** new fields and column present; the state filter matches `state`; the admin stays read-only.
- **Vocabulary invariant** passes with the new noun, verbs and group.
- Update the existing assertions on "Pending review", "Incomplete" and "pending review" copy, the one-application-per-
  account tests (`tests/test_models.py`, `tests/test_views.py`, `tests/test_claims.py`) and the Playwright panel
  assertions in `tests/playwright/test_application_form_flow.py`. Add a Playwright flow: withdraw through the confirm
  dialog, then apply again.

## Open questions

- Q: Can an unclaimed applicant withdraw or apply again? → A: No. Withdraw and "Apply again" are shown to claimed
  applications only; an unclaimed one shows its state and reject message beside the claim notice. (assumed default:
  `AnonymousApplicant` is one-to-one with its application, so a second anonymous application needs new session
  plumbing, and claiming first is one step. Overrule by editing Decision 7 and the Withdraw section.)
- Q: Is the reject message capped? → A: 2000 characters, enforced by the service. (assumed default: long enough for a
  reason, short enough for the status page. Overrule by editing `REJECTION_MESSAGE_MAX_LENGTH`.)
- Q: Does applying again count as a second referral conversion? → A: Yes, `record_conversion` runs for each new
  application as today. (assumed default: each application is its own attempt. Overrule in Creating and submitting.)

## Success criteria

- Every `CourseApplication` row has a `state` and an `organisation` after `migrate`, and the check constraints hold.
- The four service functions allow exactly the transitions in their table and raise the named exceptions otherwise.
- Approve and reject write one audit entry each; submit and withdraw write none; no entry names the applicant.
- A signed-in applicant can withdraw an open application after confirming, see "You withdrew your application", and
  start a new application from "Apply again".
- A rejected application's status page and dashboard row show the decision; the status page shows the reject message.
- `/api/` course-application rows include `state`, `organisation_id`, `decided_at` and `withdrawn_at`; the export has a
  `state` column; the admin filters by state and has no review actions.
- `uv run pytest` passes, including the vocabulary invariant.
