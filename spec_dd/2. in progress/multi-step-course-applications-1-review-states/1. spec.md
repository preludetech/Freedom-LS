# Spec: Application review states

Spec 1 of 11 in the Multi-step course applications effort (`spec_dd/1. next/roadmap.md`).

## Purpose

A `CourseApplication` has no state today. Whether it is submitted is worked out from its form sitting, and
nothing can approve, reject or withdraw it. This spec adds a stored state and an organisation, the service
functions that change the state, and the applicant-facing pages: the status page in plain words, the rejection
message, withdraw, and "apply again" after a closed application.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| open application | coined | `state` is `draft` or `submitted`: the applicant can still withdraw it. |
| active application | coined | `state` is `draft`, `submitted` or `approved`: at most one per (site, user, course). Not `is_active`; `CourseApplication` has no such flag. |
| closed application | coined | `state` is `rejected` or `withdrawn`: the applicant may apply again. Unrelated to course visibility or messaging. |
| rejection message | coined | `CourseApplication.rejection_message`, the reviewer's text the applicant reads. |

## Scope

In: the state, organisation, timestamps and rejection message on `CourseApplication`, with migrations that fill
them; the service functions that change state; the partial unique constraint over active applications; and every
page, lookup and integration below.

Out: the reviewer role, inbox and review screen, and moving applications between organisations
(`multi-step-course-applications-2-reviewers-and-inbox`); registering the applicant on approval and anything the
approved page says about course access (`multi-step-course-applications-3-approval-outcome`); reopening the form
(`multi-step-course-applications-4-reopen-form`); requirements; email; `application.*` webhooks; Django admin review
actions; copying answers into a new application when applying again; undoing a decision or a withdraw.

## Decisions

1. **`approved` counts as active.** An approved applicant cannot start a second application for the course; only a
   rejected or withdrawn application lets the applicant apply again.
2. **Every closed state is final.** No state returns to `draft` or `submitted` in this spec, so the claim rule needs
   nothing beyond "prefer the active application".
3. **Timestamps are stored, one per fact.** `submitted_at`, `decided_at` (approve or reject; the state says which) and
   `withdrawn_at`, not an `approved_at`/`rejected_at` pair. No `decided_by` field: the audit entry holds the actor.
4. **`is_submitted` means `submitted_at is not None`.** An application withdrawn from `draft` was never submitted; one
   withdrawn after submitting was. `submitted_time` is the retained name for `submitted_at`, kept for the API.
5. **The rejection message is required, stored on the application and set once** (`answers.md`). It never goes into
   the audit entry.
6. **A repeated action is refused like any other.** A double-clicked withdraw raises and the view shows the current
   state.
7. **Withdraw and "Apply again" are for claimed applications only** (`answers.md`). An unclaimed applicant sees the
   state and any rejection message beside the claim notice, and claims the application to withdraw or apply again.
   Reject works on an unclaimed application, which stays unclaimed until its applicant claims it.

## Requirements

### Model: `freedom_ls/course_applications/models.py`

- `CourseApplication.State(models.TextChoices)`: `DRAFT = "draft"`, `SUBMITTED = "submitted"`, `APPROVED = "approved"`,
  `REJECTED = "rejected"`, `WITHDRAWN = "withdrawn"`. Module constants `OPEN_STATES`, `ACTIVE_STATES` and `CLOSED_STATES`
  hold the sets from Terminology. A comment beside `ACTIVE_STATES` says the constraint condition repeats it and changing
  it needs a migration.
- Fields:
  - `state = CharField(max_length=20, choices=State.choices, default=State.DRAFT)`.
  - `organisation = ForeignKey("freedom_ls_organisations.Organisation", on_delete=PROTECT, related_name="course_applications")`, non-null.
  - `submitted_at`, `decided_at`, `withdrawn_at`: nullable `DateTimeField`s, written only by the service functions and
    the data migration.
  - `rejection_message = TextField(blank=True)`, capped by the services at `REJECTION_MESSAGE_MAX_LENGTH = 2000`.
- Constraints:
  - Replace `unique_application_per_site_user_course` with
    `UniqueConstraint(fields=["site", "user", "course"], condition=Q(state__in=["draft", "submitted", "approved"]), name="unique_active_application_per_site_user_course")`.
    Unclaimed applications (`user` null) are not constrained, as today.
  - `CheckConstraint`s: `submitted_at` is set when `state` is `submitted`, `approved` or `rejected`; `decided_at` is set
    exactly when `state` is `approved` or `rejected`; `withdrawn_at` is set exactly when `state` is `withdrawn`;
    `rejection_message` is non-empty exactly when `state` is `rejected`.
- `is_submitted` and `submitted_time` follow Decision 4 and stop reading `form_progress`.
- New property `is_open` (`state in OPEN_STATES`), which the templates use instead of naming states.
- The module and class docstrings, and the NOTE blocks in `apply`, `application_status` and `application_status.html`,
  describe what now exists: `TextChoices` plus service functions in `transitions.py`, audit through `audit_log`, no
  FSM, no transition table, no signal.

### Migrations: `freedom_ls/course_applications/migrations/` (from `0009`)

The first depends on the latest `freedom_ls_organisations` and `freedom_ls_content_engine` migrations. Order matters
because the constraint condition reads `state` and the check constraints need filled rows:

1. Add `state` (default `draft`), nullable `organisation`, the three timestamps and `rejection_message`.
2. `RunPython(backfill, RunPython.noop)` with historical models only:
   - No sitting, or a completed sitting: `state="submitted"`, `submitted_at` = `form_progress.completed_time`, else
     `created_at`. An open sitting: `state="draft"`.
   - `organisation`: the rule `organisation_for_new_application` uses (Creating and submitting), restated over
     historical models with the owner count done in SQL and the default read by `is_default=True` for the application's
     own `site_id`. A site with no default organisation raises with a message naming the site.
   - Set `updated_at` to the migration time on every row so API consumers polling `updated_since` see the new fields.
3. Make `organisation` non-null, swap the unique constraint, and add the check constraints. One migration is fine at
   this table's size.

### Service functions: new `freedom_ls/course_applications/transitions.py`

Each function runs in one `transaction.atomic()`, locks the bare row with
`CourseApplication._base_manager.select_for_update().get(pk=...)` (no `select_related`: `FOR UPDATE` refuses the
nullable joins), checks the state against one `ALLOWED_FROM` mapping, writes the state and timestamp from a single
`timezone.now()` with a save that moves `updated_at`, copies the written fields onto the instance passed in, and returns
it.

| Function | Allowed from | Writes | Audit |
| --- | --- | --- | --- |
| `submit_application(application)` | `draft` | `state=submitted`, `submitted_at` | none |
| `withdraw_application(application)` | `draft`, `submitted` | `state=withdrawn`, `withdrawn_at` | none |
| `approve_application(application, *, actor: User)` | `submitted`, and `user` is set | `state=approved`, `decided_at` | `application.approved` |
| `reject_application(application, *, actor: User, message: str)` | `submitted` | `state=rejected`, `decided_at`, `rejection_message` | `application.rejected` |

- Exceptions in `freedom_ls/course_applications/exceptions.py`: base `ApplicationTransitionError`, with
  `ApplicationStateError` (wrong current state; carries the current state), `UnclaimedApplicationError` (approve with no
  `user`), `RejectionMessageError` (message empty after stripping whitespace, or over the cap; checked before locking).
- A refused call writes nothing: no state change, no `updated_at` move, no audit entry.
- Audit entries go through `audit_log.writer.record_entry` inside the same transaction, only after the state changed:
  `actor=actor`, `target=application`, `target_label=f"{course.title} application {application.pk}"`,
  `organisation=application.organisation`, `subjects=(application.course,)`,
  `details={"from": "submitted", "to": "approved" | "rejected"}` (`TextChoices` values). No entry carries the applicant's
  name or email, or the rejection message.
- `course_access.analytics_events.record_application_submitted` stays in the views, after the service call commits.

### Creating and submitting: `freedom_ls/course_applications/views.py`, `queries.py`

- New `queries.organisation_for_new_application(course)`: the course's only owning organisation when
  `course.organisations.all()` has exactly one, otherwise the site default from `get_default_organisation`.
  (`Course.single_organisation()` returns `None` for the default organisation, so it does not fit.)
- `_start_application`: look up the account's (or anonymous applicant's) active application instead of
  `get_or_create(course=..., user=...)` over every row, and create a new row only when none is active, with
  `organisation` from the helper. A course with no form is created `draft` and submitted with `submit_application` in
  the same transaction. On the signed-in path, an `IntegrityError` from two racing creates is caught inside a savepoint
  and the existing active row is returned; anonymous creation keeps its current handling.
- `apply`: redirects to the status page only when `get_application_for_course` returns an application in
  `ACTIVE_STATES`. A closed one falls through to start a new application, and the coming-soon redirect applies to it.
- `application_check_answers`: `form_progress.complete()` and `submit_application(app)` run in one
  `transaction.atomic()`. A non-draft application cannot be submitted again: its POST redirects to the status page.
  The success toast reads "waiting for review" instead of "pending review".
- The check-your-answers page is read-only whenever the application is not a draft. The intro "Nothing is sent until
  you press Submit application. You can change any section from here." and each section's Edit link show only for a
  draft, beside the Submit application button. Every other state ends with one info notice, worded like the read-only
  form page, then the "Your application" button to the status page:
  - submitted: "This application has been submitted and is waiting for review."
  - approved or rejected: "A decision has been made on this application, so it can no longer be changed."
  - withdrawn (a draft or a submitted one): "You withdrew this application, so it can no longer be changed."
- Every reader that tested `form_progress.completed_time` for "submitted" reads state instead:
  `application_status` (the redirect into the form fires only for an unclaimed `draft`; a claimed draft renders its status page so it can be withdrawn), `application_form_page` (`read_only`
  unless `state == draft`), `_owned_application_with_form`, `applicant_details`, `claim_application`
  (`held_application` reads the account's active application), and the anonymous dashboard branch in `backends.py`
  (`state="draft"`). A withdrawn or rejected application's form pages accept no writes.
- `record_conversion` runs for each new application, as today, so applying again records a second conversion.

### Withdraw

- New view `withdraw_application` at `status/<uuid:pk>/withdraw/`, `name="withdraw"`, `@require_POST`, following
  `change_applicant_email`: `_owned_application(..., next_url=status_url)`, 404 for an application the session or account
  does not own, and 404 for an unclaimed one.
- On success it redirects to the status page with the message "Application withdrawn.". On `ApplicationStateError` it
  redirects there with "This application can no longer be withdrawn.".
- The confirm dialog is a new CSP-safe Alpine component `withdrawDialog` in
  `freedom_ls/course_applications/static/course_applications/js/alpine-components.js`, registered on `alpine:init`
  beside `claimLinkNotice`. It reimplements the behaviour of `learner_interface`'s private `makeConfirmDialog` (focus
  trap, Escape closes, focus returns to the trigger); `course_applications` must not import from `learner_interface`.
  Without JavaScript the form still POSTs.
- Dialog copy: title "Withdraw your application?"; body for a draft "Your application for {course} is a draft. If you
  withdraw it, nobody will review it. You can apply again later."; for submitted "Your application for {course} is
  waiting for review. If you withdraw it, nobody will review it. You can apply again later."; buttons
  "Keep application" and "Withdraw application".

### Status page: `templates/course_applications/application_status.html`

Each state has a heading, one sentence on what is true now and what happens next, and a details card. Dates use `<c-date>`.
`head_title` includes the state. "You will be notified once a decision has been made" is removed.

| State | Chip (variant) | Heading | Body | Actions |
| --- | --- | --- | --- | --- |
| draft | Not submitted (warning) | Your application | "You started your application for {course} but have not submitted it." | Continue application; Withdraw application |
| submitted | Waiting for review (info) | Your application | "Your application for {course} is waiting for review. The decision will show here." | Withdraw application |
| approved | Approved (success) | Your application was approved | "Your application for {course} was approved on {date}." | None |
| rejected | Not approved (muted) | Your application was not approved | "Your application for {course} was not approved on {date}." Then a region headed "Message from the reviewer" holding the rejection message, escaped, line breaks kept. Then "You can apply again." | Apply again |
| withdrawn | Withdrawn (muted) | You withdrew your application | "You withdrew your application for {course} on {date}. Nobody will review it." | Apply again |

Unclaimed applications keep the "Check your email" claim notice above the state block, without withdraw or
"Apply again", and their details card has no "Next step" row.

The page starts with a "Back" link at the top left, above the heading: `<c-back-link>` with `historyBackLink`, the
same as the course details page, falling back to the dashboard. No button on the page goes back.

Under the state sentence a "Details" card lists the application's facts in a definition list, each row shown only
when it has a value:

| Row | Value |
| --- | --- |
| Course | The course title, linking to the course details page |
| Status | The state chip |
| Started | `created_at` |
| Progress | Draft with a form only: "{n} of {m} questions answered" |
| Submitted | `submitted_at` |
| Decision | `decided_at` (approved and rejected) |
| Withdrawn | `withdrawn_at` |
| Next step | Draft: "Finish and submit your application." Submitted: "Nothing. We will review your application." Approved: "Nothing. Your application was approved." Rejected and withdrawn, claimed: "You can apply again." |

The actions sit under the card. "Withdraw application" is `variant="error"` (red), on the page and in the dialog.

### Dashboard panel: `queries.py`, `backends.py`, `templates/course_applications/partials/dashboard_applications.html`

- Rename `get_active_applications(user)` to `get_dashboard_applications(user)`. It returns the account's active
  applications, plus each rejected application that no newer application for the same course has superseded
  (`answers.md`). Withdrawn applications are not shown.
- `panel_rows` orders open first, then approved and rejected, newest first within each group, using a `Case`/`When`
  annotation and an `Exists` subquery for "superseded", with no per-row query. Prefetching and paging
  (`APPLICATIONS_PAGE_SIZE`) are unchanged.
- Rows use the status page's chips. Every row has a "Details" link to the application's status page (not the course page).
  Draft: the existing hint and a "Continue application" button. Submitted and approved: "Details" only. Rejected: hint
  "Decision on {date}. Read the reviewer's message." with "Details" and a secondary "Apply again". The row does not show the rejection message itself.

### Course CTA: `backends.py` `ApplicationCourseAccessBackend._gated_decision`, `queries.get_application_for_course`

- `get_application_for_course(*, user, course)` returns the active application if there is one, otherwise the newest
  closed one by `created_at`, otherwise `None`, with an explicit order instead of a bare `.first()`.
- An active application: "View my application" (unchanged). A closed one: "Apply again" to `course_applications:apply`,
  with a secondary link "View your previous application" to its status page. None: "Apply now" (unchanged).

### Claim: `freedom_ls/course_applications/claims.py` `attach_to_user`

Keep the user-row lock. `held` becomes the account's active application for the course (closed ones are ignored and
never deleted). With incoming as the anonymous applicant's application:

| Held (account, active) | Incoming | Result |
| --- | --- | --- |
| none | any | incoming attaches |
| any | `rejected` or `withdrawn` | incoming attaches beside it (no index collision) |
| `submitted` or `approved` | `draft` or `submitted` | held wins; incoming erased with its applicant |
| `draft` | `draft` or `submitted` | incoming wins; held discarded with `_discard_draft` |

`receivers.adopt_anonymous_applications_on_login` picks its toast verb from `result.application.is_submitted` as today.

### Factories and QA commands

- `freedom_ls/course_applications/factories.py` `CourseApplicationFactory` sets `organisation` (the site default) and
  derives `state` and `submitted_at` with `LazyAttribute`s over the resolved `form_progress`, so every built row meets
  the check constraints. Traits cover `approved`, `rejected` and `withdrawn`. A test that calls `complete()` after
  building a row also calls `submit_application`.
- QA commands that complete an application sitting call `submit_application`; direct `CourseApplication.objects.create`
  callers set `organisation` and `state`.

## Testing

- **Transitions:** parametrised over every (function, from-state) pair: allowed ones change state and timestamp, move
  `updated_at` and update the passed instance; refused ones raise `ApplicationStateError` and change nothing. Approve
  with no `user` raises `UnclaimedApplicationError`. Reject with an empty, whitespace-only or over-cap message raises
  `RejectionMessageError`. A `transaction=True` test where two calls race: the second is refused.
- **Audit:** exactly one entry per approve or reject, with `from`/`to`, the course as subject and the application's
  organisation. None for a refused call, for submit or for withdraw. No entry contains the applicant's name, email or
  the rejection message.
- **Migrations:** seeded rows covering no sitting, completed sitting and open sitting, each with and without a user,
  across two sites; courses with zero, one and two owning organisations. Assert state, `submitted_at`,
  `organisation` and moved `updated_at`. A site with no default organisation raises.
- **Constraints:** a second active application for the same (site, user, course) is refused; a new one after reject or
  withdraw is allowed; each check constraint rejects a row that breaks it.
- **Views:** apply after a closed application creates a new row; a closed application's form pages refuse writes;
  withdraw 404s for an unclaimed application and is refused from a closed state; the rejection message renders
  escaped.
- **Claim:** one test per row of the claim table, using factory-built rows for incoming closed states.
- **Panel and CTA:** a rejected application is hidden once superseded; withdrawn is never shown. The panel and API
  query counts are equal for one row and for several (`django_assert_num_queries`).
- **Playwright:** withdraw through the confirm dialog, then apply again.

## Open questions

- Q: Is the rejection message capped? → A: 2000 characters, enforced by the service. (assumed default: long enough for
  a reason, short enough for the status page. Overrule by editing `REJECTION_MESSAGE_MAX_LENGTH` in Model.)
- Q: Does applying again count as a second referral conversion? → A: Yes. (assumed default: each application is its
  own attempt. Overrule in Creating and submitting.)
- Q: Vocabulary: keep "active application" and "closed application", define `application` and widen the withdraw row in
  the glossary? → A: Yes, as written in Terminology and Audit and glossary. (assumed default: the review's recommended
  options; the names match existing `get_active_applications` usage. Overrule in Terminology.)

## Success criteria

- A signed-in applicant can withdraw an open application after confirming, see "You withdrew your application", and
  start a new application from "Apply again".
- After `migrate` on a copy of production data, no `CourseApplication` has a null `organisation` and every row's
  `state` matches its sitting.
- `uv run pytest` passes.
