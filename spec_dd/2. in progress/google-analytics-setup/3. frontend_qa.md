# Frontend QA: Google Analytics 4 and Google Ads

GA4 loads from a measurement ID and sends `user_id` for logged-in users. One boolean,
`analytics_enabled`, gates both GA4 and PostHog, and turns both off on allauth's two token-bearing
pages.

Google Ads rides on the same tag. With `GOOGLE_ADS_CONVERSION_ID` set, the page adds a second
config call, `["config", "AW-QATEST000"]`, after the GA4 one. An event whose name is mapped to a
label in `GOOGLE_ADS_CONVERSION_LABELS` also sends a native Ads conversion,
`["event", "conversion", {"send_to": "AW-QATEST000/<label>"}]`, in the same script as its GA4
event. This run maps `sign_up` and `course_registered` and leaves the other events unmapped, so a
`conversion` entry may appear only directly after one of those two.

FLS sends five events, each recorded once in the session and emitted by the next render.
`research_event_taxonomy.md` explains the design.

| Event | Parameters besides the course parameters |
| --- | --- |
| `sign_up` | `method: "email"`. No course parameters |
| `course_access_requested` | `request_kind`: `"interest"` or `"application"` |
| `course_registered` | `registration_method: "self_registration"` |
| `course_started` | `registration_source`: `"individual"` or `"cohort"` |
| `course_completed` | `registration_source` |

The course parameters are `course_slug`, `course_id` (the course UUID) and `access_type` (`"free"`
or `"application_gated"`). Every `course_*` event carries all three.

`tutorial_begin` and `tutorial_complete` are gone. `generate_lead` stays in the code for downstream
marketing forms, but FLS has no page that sends it, and applications no longer do. None of the three
may appear anywhere in this run.

The measurement ID used here is fake, so nothing reaches a real GA4 property. Every check reads what
the page pushed to `window.dataLayer`, or whether the `gtag/js` loader was requested. Read the data
layer with:

```js
JSON.stringify(Array.from(window.dataLayer || []).map(entry => Array.from(entry)))
```

An event shows up as `["event", "sign_up", {"method": "email"}]`. The config call shows up as
`["config", "G-QATEST0000", {...}]`. For an anonymous visitor that last object is empty.

**Check the whole parameter object on every event, not only the name.** Compare `course_slug` and
`course_id` against the slug and UUID that the seed command prints in §0.2.

Beyond the golden path this run hunts for six things:

- **An event that fires twice, or not at all.** The events partial is included in two places on a
  full page, and the course player swaps only `#interface-main`. Both are easy to get wrong.
- **An event with wrong or missing parameters.** A course event naming the wrong course, or
  `access_type: "free"` on the application-gated course.
- **An HTMX partial that swallows the event.** The express-interest button swaps a fragment. The
  event has to fire at that swap, not on some later page.
- **A one-time key reaching an analytics service.** Neither snippet may load on the two token-bearing
  pages.
- **PostHog changing by accident.** Its gate was edited, so it is re-checked.
- **A conversion that fires apart from its event.** A `conversion` entry with no mapped event
  directly before it, a mapped event with no `conversion` after it, or a `conversion` with a
  wrong `send_to`.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

The Django debug toolbar sits over some buttons ("Remove interest", the course player's "Next")
and intercepts the click. Remove it with `document.getElementById('djDebug')?.remove()` before
clicking anything it covers.

Dev mail goes to Mailpit at `http://localhost:8025`, not the `runserver` console. Confirmation and
password-reset links are read from there.

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh`. Note the number and use it literally from here on.
2. Start the server backgrounded, as its own call, with all three services configured:
   `GOOGLE_ANALYTICS_MEASUREMENT_ID=G-QATEST0000 GOOGLE_ADS_CONVERSION_ID=AW-QATEST000 GOOGLE_ADS_CONVERSION_LABELS=sign_up=QAsignup,course_registered=QAregistered POSTHOG_API_KEY=phc_qatest uv run python manage.py runserver <PORT>`
   This is "the full configuration" below.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `google-analytics-setup` branch. If it names another branch, another server holds the port. Go
   back to step 1.

### 0.2 Seed data

1. Demo content loaded: `uv run python manage.py content_save demo_content DemoDev`.
2. Run `uv run python manage.py qa_create_ga_setup_seed`. It is idempotent, so run it again before
   any re-run of this plan. **Write down every slug, UUID and learner pk it prints.** It sets up:
   - **Learner A** (`qa-learner-a@email.com`): registered, with fresh progress, for the short demo
     course `standard-markdown-demo-finance` and for `qa-second-course`.
   - **Learner B** (`qa-learner-b@email.com`): no `CourseApplication`, and not registered for
     `qa-free-course-self-registration`.
   - **Learner C** (`qa-learner-c@email.com`): granted `qa-cohort-course` through a cohort
     registration only.
   - `qa-application-gated-course-no-form`, an application-gated course with no application form.
   - `qa-coming-soon-course`, a coming-soon course nobody has expressed interest in.

   Every learner's password equals their email.
3. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
4. **An application-gated course with an application form.** The demo content's "Functionality
   Demo - Application gated course", slug `functionality-demo-application-gated-course`. Ask the
   `fls-dev:qa-data-helper` agent for its UUID.

Anything else that is missing is created through the `fls-dev:qa-data-helper` agent, never by hand.

## §1 The snippet loads, and only when configured

1. Signed out, open `http://127.0.0.1:<PORT>/`. Expect a network request to
   `https://www.googletagmanager.com/gtag/js?id=G-QATEST0000`.
2. Read the data layer. Expect a `js` entry and `["config", "G-QATEST0000", {}]`. The object has no
   `user_id` and no `content_group`.
3. Expect `["config", "AW-QATEST000"]` directly after the GA4 config entry, with no third element.
4. View the page source. Expect `posthog.init('phc_qatest'` to be there as before.
5. Expect no `["event", ...]` entry that FLS pushed. (`gtag.js` may add entries of its own, which is
   fine. None of the five FLS events, and no `conversion`, may be there.)

### 1.1 Unconfigured deployment stays silent

1. Stop the server. Start it again on the same port with no Google variables:
   `POSTHOG_API_KEY=phc_qatest uv run python manage.py runserver <PORT>`
2. Open `/`. Expect no request to `googletagmanager.com`, `window.gtag` undefined, and PostHog still
   initialised.
3. Log in as Learner A and open the dashboard. Expect the same: no GA4, no console errors.
4. **GA4 without Ads.** Restart with `GOOGLE_ANALYTICS_MEASUREMENT_ID=G-QATEST0000` and
   `POSTHOG_API_KEY=phc_qatest` only. Open `/`. Expect the GA4 config entry and no `AW-` anywhere in
   the data layer or the page source.
5. **Ads without GA4.** Restart with `GOOGLE_ADS_CONVERSION_ID=AW-QATEST000` and
   `POSTHOG_API_KEY=phc_qatest` only. Expect the `runserver` output to include the
   `freedom_ls_deployment.W002` warning. Open `/`. Expect no request to `googletagmanager.com`,
   `window.gtag` undefined, and no `AW-` in the page source.
6. **Labels without Ads.** Restart with `GOOGLE_ANALYTICS_MEASUREMENT_ID=G-QATEST0000`,
   `GOOGLE_ADS_CONVERSION_LABELS=sign_up=QAsignup` and `POSTHOG_API_KEY=phc_qatest`. Expect the
   `freedom_ls_deployment.W003` warning in the `runserver` output. Sign up a fresh account. On the
   verify-your-email page expect the `sign_up` event and no `conversion` entry.
7. **A malformed label.** Try to start with `GOOGLE_ADS_CONVERSION_LABELS=sign_up` (no `=`).
   Expect the server to refuse to start with an `ImproperlyConfigured` error naming `sign_up`.
8. Stop the server and restart it with the full configuration, as in §0.1 step 2.

## §3 `sign_up`

1. Signed out, open the sign-up page and create a new account with a fresh email address.
2. On the page you land on (the verify-your-email page), read the data layer. Expect exactly one
   `["event", "sign_up", {"method": "email"}]`, followed directly by exactly one
   `["event", "conversion", {"send_to": "AW-QATEST000/QAsignup"}]`.
3. Reload the page. Expect no `sign_up` entry and no `conversion` entry. Both are one-shot.
4. **Failure branch.** Open the sign-up page again and submit the email address you just used.
   Whatever the page says, expect no `sign_up` event and no `conversion` on the resulting page.
5. **Invalid input.** Submit the sign-up form with mismatched passwords. Expect the form to re-render
   with errors and no `sign_up` event and no `conversion`.

## §5 `course_access_requested`

In every check below, expect no `generate_lead` entry anywhere. Applications used to send it.
`course_access_requested` is not mapped to an Ads label, so expect no `conversion` entry anywhere
in this section either.

### 5.1 Application with a form

1. Log in as Learner B. Open `functionality-demo-application-gated-course` and click "Apply now".
2. On the first form page, expect no `course_access_requested`. A draft is not a request.
3. Leave a required question blank on a form page and submit that page. Expect a 422 re-render of
   the page with the error, and no event. (The form blocks at the page, so check-your-answers
   cannot be reached with a required answer missing.)
4. Complete the answers and submit. On the dashboard you land on, expect the usual success message
   and exactly one event:
   `["event", "course_access_requested", {"course_slug": "<slug>", "course_id": "<uuid>", "access_type": "application_gated", "request_kind": "application"}]`
5. Reload. Expect no event.
6. Open the application's status page and the course's apply URL again. Expect a redirect to the
   status page and no event.

### 5.2 Application with no form

1. Still Learner B, open `qa-application-gated-course-no-form` and click "Apply now".
2. On the confirmation page ("Apply to ...?"), expect no event.
3. Confirm. On the status page, expect exactly one `course_access_requested` with this course's slug
   and UUID, `access_type: "application_gated"` and `request_kind: "application"`.
4. Visit the apply URL again. Expect the status page and no second event.

### 5.3 Interest, signed in

1. Still Learner B, open `qa-coming-soon-course`. Read the data layer length before doing anything.
2. Click "I'm interested". The button area swaps in place and the page does not reload. Expect the
   data layer to gain exactly one entry:
   `["event", "course_access_requested", {"course_slug": "qa-coming-soon-course", "course_id": "<uuid>", "access_type": "free", "request_kind": "interest"}]`
3. Confirm the script cleaned up after itself.
   `document.querySelectorAll('[id^="express-interest-cta-"] script').length` should be `0`.
4. Click "Remove interest". Expect no new event.
5. Click "I'm interested" again. The row is new again, so expect one more event. That is correct.
6. Reload the page, which now shows the "Interested" state. Expect no event on load.
7. Open any other page. Expect no `course_access_requested` there. The swap already spent it.

### 5.4 Interest, anonymous

1. Log out. Open `qa-coming-soon-course` and click "I'm interested". Expect a redirect to sign-in and
   no event on the sign-in page.
2. Sign in as Learner C. Expect to land back on the course page, showing "Interested", with exactly
   one `course_access_requested` carrying `request_kind: "interest"`.
3. Reload. Expect no event.
4. Type the deferred URL into the address bar:
   `http://127.0.0.1:<PORT>` plus the path of `course_interest:deferred_express_interest` for this
   slug. Expect a redirect to the course page and no event.

## §7 `course_started` and `course_completed` in the course player

Neither event is mapped to an Ads label, so expect no `conversion` entry anywhere in this section.

Log in as Learner A.

1. From the dashboard, open `standard-markdown-demo-finance` and open its first course item. Expect
   exactly one `course_started` with this course's slug and UUID, `access_type: "free"` and
   `registration_source: "individual"`. Expect no `course_registered`. Learner A was registered by
   the seed command, outside the browser.
2. Reload. Expect no `course_started`.
3. Click "Next". This is a boosted navigation, so the page does not reload and `window.dataLayer`
   keeps growing. Expect the URL to change and no new `course_started`. GA4's own history-based page
   view is `gtag.js`'s business and may not happen at all with a fake ID, so do not look for it.
4. Work through to the last course item and click "Finish Course". This is also boosted. On the
   completion page, expect exactly one `course_completed` added to the data layer, with the same four
   parameters as step 1.
5. Confirm the event script cleaned up after itself: `document.querySelectorAll('#interface-main script')`
   should contain no script whose text includes `course_completed`.
6. Press the browser's Back button, then Forward. Expect no second `course_completed`.
7. Reload the completion page. Expect no `course_completed`.
8. **Full-page route to the same moment.** Reset Learner A's `completed_time` to null through the
   data helper, then type the course's finish URL into the address bar. Expect exactly one
   `course_completed`, and only one event script in the page source, not one per include point.
9. **Withheld completion.** Through the data helper, give Learner A another course with an unread
   topic, then open that course's finish URL directly. Expect the "not complete" page and no
   `course_completed`.

### 7.1 Two courses in one session

1. Still Learner A, in the same browser session, open `qa-second-course` and its first item. Expect
   one `course_started` whose `course_slug` is `qa-second-course` and whose `course_id` is that
   course's UUID. The first course's event earlier in the session must not suppress this one.

### 7.2 A cohort learner

1. Log in as Learner C. Open `qa-cohort-course` from the dashboard and open its first item. Expect
   one `course_started` with `registration_source: "cohort"`, and no `course_registered`.
2. Click "Finish Course". Expect one `course_completed` with `registration_source: "cohort"`.

## §8 Nothing else broke

1. As the superuser, open the Django admin. Expect it to load normally. The admin does not extend
   `_base.html`, so expect no GA4 there.
2. Open a URL that does not exist. Expect the 404 page, styled as before, with no console errors.
3. Open the educator interface as the superuser and click through two sidebar links. Expect the
   panel swaps to work and no FLS event in the data layer.
4. On any page, check the browser console. Expect no JavaScript errors from the GA4 or PostHog
   blocks. CSP report-only warnings naming `googletagmanager.com`, `google-analytics.com`,
   `googleadservices.com`, `doubleclick.net`, `googlesyndication.com`, `google.com`,
   `google.co.za` or `posthog.com` should not appear. (A report-only warning never blocks anything,
   but one naming these hosts means the CSP entries are wrong. Requests to those hosts failing with
   4xx are expected: the IDs are fake.)
5. Follow the Privacy link in the footer. Expect version 1.2, a usage analytics section naming
   Google Analytics 4 and PostHog, a line saying analytics records which courses you request,
   register for, start and complete, an advertising measurement section naming Google Ads, the GA
   opt-out link and the Google ads settings link. The text is served from git `HEAD`, so an
   uncommitted edit will not show.
6. Search every data layer you read in this run for `tutorial_begin`, `tutorial_complete` and
   `generate_lead`. Expect none.
7. Search every data layer you read in this run for `conversion`. Every match must sit directly
   after a `sign_up` or `course_registered` entry, and every `sign_up` and `course_registered`
   must have one. Its `send_to` must be `AW-QATEST000/QAsignup` or `AW-QATEST000/QAregistered`
   respectively.

## Not covered in the browser

Two things have no FLS page to exercise, so unit tests cover them and this plan does not.

- **`generate_lead`.** FLS ships no lead form. `base/tests/test_google_analytics.py` covers a
  downstream caller recording it, and `deployment/tests/test_context_processors.py` covers the
  rendering and the escaping of parameter values.
- **`content_group`.** No FLS template fills the `google_analytics_config_params` block.
  `TestGoogleAnalyticsConfigParamsBlock` renders a template that does.
- **A conversion label that would close the script element.** `TestGoogleAdsConversionRendering`
  covers the escaping.
