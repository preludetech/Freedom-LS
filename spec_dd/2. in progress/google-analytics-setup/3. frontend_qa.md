# Frontend QA: Google Analytics 4

GA4 loads from a measurement ID, sends `user_id` for logged-in users, and emits four GA4 events
(`sign_up`, `generate_lead`, `tutorial_begin`, `tutorial_complete`) from one-shot flags. One boolean,
`analytics_enabled`, now gates both GA4 and PostHog, and turns both off on allauth's two
token-bearing pages.

The measurement ID used here is fake, so nothing reaches a real GA4 property. Every check reads what
the page pushed to `window.dataLayer`, or whether the `gtag/js` loader was requested. Read the data
layer with:

```js
Array.from(window.dataLayer || []).map(entry => Array.from(entry))
```

An event shows up as `["event", "sign_up"]`. The config call shows up as
`["config", "G-QATEST0000", {...}]`.

Beyond the golden path this run hunts for three things:

- **An event that fires twice, or not at all.** The events partial is included in two places, and the
  course player swaps only `#interface-main`. Both are easy to get wrong.
- **A one-time key reaching an analytics service.** Neither snippet may load on the two token-bearing
  pages.
- **PostHog changing by accident.** Its gate was edited, so it is re-checked.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh`. Note the number and use it literally from here on.
2. Start the server backgrounded, as its own call, with both services configured:
   `GOOGLE_ANALYTICS_MEASUREMENT_ID=G-QATEST0000 POSTHOG_API_KEY=phc_qatest uv run python manage.py runserver <PORT>`
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `google-analytics-setup` branch. If it names another branch, another server holds the port. Go
   back to step 1.

### 0.2 Seed data

Missing data is created through the `fls-dev:qa-data-helper` agent, never by hand.

1. Demo content loaded: `uv run python manage.py content_save demo_content DemoDev`.
2. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
3. **Learner A:** a learner account, no staff flag, verified email, password equal to the email.
   Registered for one short course with at least two course items, with a `CourseProgress` whose
   `started_at` and `completed_time` are both null. Note the course slug. On a re-run, reset those
   two fields and the learner's `TopicProgress` for the course.
4. **Learner B:** a second learner account, verified email, holding no `CourseApplication`.
5. **An application-gated course with an application form** (the demo content's "By application"
   course) and **one application-gated course with no application form**. Ask the data helper for the
   second if the demo content has none.

## §1 The snippet loads, and only when configured

1. Signed out, open `http://127.0.0.1:<PORT>/`. Expect a network request to
   `https://www.googletagmanager.com/gtag/js?id=G-QATEST0000`.
2. Read the data layer. Expect a `js` entry and `["config", "G-QATEST0000"]` with no `user_id`.
3. View the page source. Expect `posthog.init('phc_qatest'` to be there as before.
4. Expect no `["event", ...]` entry that FLS pushed. (`gtag.js` may add entries of its own, which is
   fine. None of the four FLS events may be there.)

### 1.1 Unconfigured deployment stays silent

1. Stop the server. Start it again on the same port with no GA variable:
   `POSTHOG_API_KEY=phc_qatest uv run python manage.py runserver <PORT>`
2. Open `/`. Expect no request to `googletagmanager.com`, `window.gtag` undefined, and PostHog still
   initialised.
3. Log in as Learner A and open the dashboard. Expect the same: no GA4, no console errors.
4. Stop the server and restart it with both variables, as in §0.1 step 2.

## §2 `user_id`

1. Log in as Learner A. On the dashboard, read the data layer. Expect the config entry to carry
   `user_id` equal to Learner A's numeric pk, as a string. Confirm the pk with the data helper or the
   Django admin.
2. Search the page source for Learner A's email inside the GA4 `<script>` block. Expect no match.
   (The header may show the email elsewhere on the page. Only the GA4 block matters.)
3. Log out. On the page you land on, expect the config entry to have no `user_id`.

---

## §3 `sign_up`

1. Signed out, open the sign-up page and create a new account with a fresh email address.
2. On the page you land on (the verify-your-email page), read the data layer. Expect exactly one
   `["event", "sign_up"]`.
3. Reload the page. Expect no `sign_up` entry. The flag is one-shot.
4. **Failure branch.** Open the sign-up page again and submit the email address you just used.
   Whatever the page says, expect no `sign_up` event on the resulting page.
5. **Invalid input.** Submit the sign-up form with mismatched passwords. Expect the form to re-render
   with errors and no `sign_up` event.

---

## §4 Token-bearing pages load no analytics

1. Find the confirmation link for the §3 account in the `runserver` console output. Open it.
2. On `http://127.0.0.1:<PORT>/accounts/confirm-email/<key>/`, expect no request to
   `googletagmanager.com`, `window.gtag` undefined, `window.posthog` undefined, and no
   `posthog.init(` in the page source.
3. Confirm the email. On the next ordinary page, expect both snippets back.
4. Log out. Request a password reset for Learner B, take the link from the console, and open it.
   Expect the same as step 2 on the set-password page: neither snippet loads.
5. Set a new password equal to the email again so later sections can log in. On the page after the
   reset, expect both snippets back.
6. **A pending flag survives a token page.** Sign up another fresh account, and without visiting any
   other page open its confirmation link from the console. Expect no analytics on that page. Then
   open `/`. Expect `["event", "sign_up"]` there, once. (If the verify-your-email page already
   emitted the event in this flow, the flag is spent and `/` shows nothing. That is also correct.
   What must not happen is an event on the token page.)

## §5 `generate_lead`

### 5.1 Application with a form

1. Log in as Learner B. Open the "By application" course and click "Apply now".
2. On the first form page, expect no `generate_lead`. A draft is not a lead.
3. Fill the form to the check-your-answers page. Leave one required question blank if the form lets
   you reach that page without it, and submit. Expect the error, and no `generate_lead`.
4. Complete the answers and submit. On the dashboard you land on, expect exactly one
   `["event", "generate_lead"]` and the usual success message.
5. Reload. Expect no `generate_lead`.
6. Open the application's status page and the course's apply URL again. Expect a redirect to the
   status page and no `generate_lead`.

### 5.2 Application with no form

1. Still Learner B, open the application-gated course with no form and click "Apply now".
2. On the confirmation page ("Apply to ...?"), expect no `generate_lead`.
3. Confirm. On the status page, expect exactly one `generate_lead`.
4. Visit the apply URL again. Expect the status page and no second event.

## §6 `tutorial_begin` and `tutorial_complete` in the course player

Log in as Learner A.

1. From the dashboard, open the course from §0.2 and open its first course item. Expect exactly one
   `["event", "tutorial_begin"]`.
2. Reload. Expect no `tutorial_begin`.
3. Click "Next". This is a boosted navigation, so the page does not reload and `window.dataLayer`
   keeps growing. Expect the URL to change and no new `tutorial_begin`. GA4's own history-based page
   view is `gtag.js`'s business and may not happen at all with a fake ID, so do not look for it.
4. Work through to the last course item and click "Finish Course". This is also boosted. On the
   completion page, expect exactly one `["event", "tutorial_complete"]` added to the data layer.
5. Confirm the event script cleaned up after itself: `document.querySelectorAll('#interface-main script')`
   should contain no script whose text includes `tutorial_complete`.
6. Press the browser's Back button, then Forward. Expect no second `tutorial_complete`.
7. Reload the completion page. Expect no `tutorial_complete`.
8. **Full-page route to the same moment.** Reset Learner A's `completed_time` to null through the
   data helper, then type the course's finish URL into the address bar. Expect exactly one
   `tutorial_complete`, and only one event script in the page source, not one per include point.
9. **Withheld completion.** Through the data helper, give Learner A a second course with an unread
   topic, then open that course's finish URL directly. Expect the "not complete" page and no
   `tutorial_complete`.

## §7 Nothing else broke

1. As the superuser, open the Django admin. Expect it to load normally. The admin does not extend
   `_base.html`, so expect no GA4 there.
2. Open a URL that does not exist. Expect the 404 page, styled as before, with no console errors.
3. Open the educator interface as the superuser and click through two sidebar links. Expect the
   panel swaps to work and no FLS event in the data layer.
4. On any page, check the browser console. Expect no JavaScript errors from the GA4 or PostHog
   blocks. CSP report-only warnings naming `googletagmanager.com`, `google-analytics.com` or
   `posthog.com` should not appear. (A report-only warning never blocks anything, but one naming
   these hosts means the CSP entries are wrong.)
5. Follow the Privacy link in the footer.
   Expect version 1.1, a usage analytics section naming Google Analytics 4 and PostHog, and the
   opt-out link. The text is served from git `HEAD`, so an uncommitted edit will not show.
