# Spec: theme-fit alerts for app pages

Idea: `idea.md`. Recorded answers: `answers.md`. Research: `research_*.md` in this directory.

## Purpose

App pages show status messages through `<c-callout>`, which carries the course-content look, and
through `<c-panel-notice>`, which only panels and dialogs use. Neither fits the learner and educator
design as a general component, and nothing keeps content-engine widgets out of app templates.

This work adds one alert component, `<c-alert>`, in the base app. It replaces both components,
deletes them, and adds a test that keeps content widgets out of app templates. The content engine
and `<c-admonition>` do not change.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| alert (`<c-alert>`) | coined | A static, toned status box in an app page, panel or dialog. The `.alert` theme classes (`tailwind.components.css`, `docs/how tos/theme-fls.md`) already use the word and become this component's styling. No glossary entry or cotton component uses it. `docs/product/notifications.md` uses "pop-up alerts" for an unbuilt notification delivery, which this is not. |
| content widget | narrowed | A content-engine cotton component that exists only for authored markdown: the banned list under "Guard test". `MARKDOWN_ALLOWED_TAGS` in `config/settings_base.py` is the wider list markdown may use. |
| toast | narrowed | The dismissible, fixed-position message from Django's messages framework (`base/templates/partials/messages.html`, `_toast.html`). Not an alert. |

"Callout" stays the product-docs word for a content admonition only.

## Scope

In:

- `<c-alert>` in `freedom_ls/base/templates/cotton/alert.html`.
- Migrating every `<c-callout>` and `<c-panel-notice>` use in `freedom_ls/`, and the hand-built
  alert box in `base/templates/partials/form.html`.
- Deleting both old components and their tests.
- A guard test for app templates.
- Skills, brand guidelines, docs and upgrade notes.

Out:

- `freedom_ls/content_engine/` and `<c-admonition>`.
- Toasts.
- Field-level error text beside a field or control (such as `comms/partials/composer.html:88`).
- The dialog error summary (`panel_framework/partials/error_summary.html`). It is a validation summary that takes focus, a different job.
- Dismissing an alert.
- Copy changes to migrated messages, and merging the paused and access-ended pair in `course_detail.html`.
- First Class's `lp/step.html`. Downstream projects migrate through the upgrade notes.

## Decisions

- **One component everywhere, with no aliases.** `c-callout` and `c-panel-notice` are deleted, so
  every context has one right answer (`answers.md`).
- **The panel framework depends on `<c-alert>` as a host component.**
  `extract_panels_framework-4-template-contract` lists it in the host contract beside `c-button` and
  `c-chip` (`answers.md`).
- **The attribute is `tone`**, the name `c-panel-notice` and `c-button` already use.
- **The look is `c-panel-notice`'s.** A tinted box with a thin full border, `rounded-md`, and no
  outer margin; the parent spaces its children. The left stripe and large title are the content
  look.
- **The styling lives in the `.alert` theme classes**, so a theme reshapes every alert in one place.
- **Live roles follow `c-panel-notice`.** `error` gets `role="alert"`, `success` gets
  `role="status"`, and `info` and `warning` get none because they are read in place. The HTMX
  error re-renders and their tests already rely on this.
- **Every tone shows a decorative icon** (`aria-hidden`). The tone never relies on colour alone
  (WCAG 1.4.1).
- **The title is not a heading.** Its right level depends on where the alert sits, and most alerts
  are one sentence.

## Requirements

### The component

`freedom_ls/base/templates/cotton/alert.html`:

```html
<c-alert tone="info|success|warning|error" title="…">One or two sentences.</c-alert>
```

- `<c-vars tone="info" title="" class="" />`. An unknown tone renders as `info`, never nothing.
- The outer box is `class="alert alert-{{ tone }}{% if class %} {{ class }}{% endif %}"`, followed
  by `{{ attrs }}`, so `id`, `data-testid`, `tabindex` and `hx-*` pass through. This is the pattern
  `callout.html` uses.
- Layout lives in the template: a flex row with a gap, the `<c-icon>` first with `shrink-0` and an
  `alert-icon` class, then the title and the default slot. Icon names follow `partials/_toast.html`:
  `info`, `success`, `warning`, `error`.
- `title` renders as `<strong class="block font-semibold">` when given.
- The slot takes plain text, inline markup, a list or a `<c-button>`.
- No `text-sm`. The alert inherits the body size of its context, as the panel-framework rule for
  notices in dialog bodies requires.

`tailwind.components.css`, the `.alert` family:

- Add `.alert-warning`.
- `.alert` padding becomes `p-3`.
- Each tone class sets `bg-<tone>/10 border-<tone>/20 text-on-surface`. Tone-coloured text fails
  contrast on these tints for warning and success.
- `.alert-<tone> .alert-icon` sets the icon colour to the tone, so a theme can repoint it.
- `freedom_ls/themes/first_class/static/themes/first_class/theme.css` overrides `.alert*` with
  `-light` tints. Keep each override working and add a first_class `.alert-warning` to match them.

### Migrations

Each use becomes `<c-alert>` with the same tone, title and body, and keeps its `data-testid` and
`id`.

- `c-callout` (`level` becomes `tone`), 11 uses across 8 templates:
  - `base/templates/account/login.html`
  - `course_applications/templates/course_applications/applicant_details.html`
  - `course_applications/templates/course_applications/check_your_answers.html` (2 uses)
  - `course_applications/templates/course_applications/form_page.html`
  - `educator_interface/templates/educator_interface/panels/course_content.html`. Drop the
    `class="my-0"` workaround.
  - `form_engine/templates/form_engine/partials/answer_errors.html` (2 uses)
  - `form_engine/templates/form_engine/question.html`. Its developer-only "UNHANDLED FORM TYPE"
    box becomes an `error` alert like the rest.
  - `learner_interface/templates/learner_interface/course_detail.html` (2 uses)
- Where an `error` callout sits in a bare `<div role="alert">` wrapper (`answer_errors.html`,
  `applicant_details.html`), drop the wrapper and move its `data-testid` and `id` onto the
  `<c-alert>`, so the page has one `role="alert"` region. `login.html` keeps its wrapper, since its
  alert is `info` and has no role. Check `accounts/tests/_auth_page_helpers.py` (`_alert_html`) and
  the form_engine tests still find each region.
- Pages that relied on `c-callout`'s `my-6` get their spacing from the parent.
- `c-panel-notice`: all 15 templates (`grep -rln '<c-panel-notice' freedom_ls`), 14 panel and dialog
  templates plus the reference page. `educator_interface/partials/staff_only_admin_callout.html`
  keeps its filename, which `educator_interface/views.py` names.
- `base/templates/partials/form.html`: the hand-built `bg-error/10 border border-error/20 …` box
  becomes `<c-alert tone="error">`.

### Deletions

- `freedom_ls/panel_framework/templates/cotton/panel-notice.html` and

### Guard test

New `freedom_ls/base/tests/invariants/test_app_templates_use_app_components.py`, in the shape of
`freedom_ls/icons/tests/invariants/test_no_font_awesome.py`: a scan with a carve-out, parametrised
per banned tag.

- It scans `freedom_ls/*/templates/**/*.html`, except `freedom_ls/content_engine/templates/`, where
  the widgets live and nest.
- It skips text inside `{% comment %}…{% endcomment %}` and `{# … #}`.
- A tag matches as `<c-NAME(?![\w-])`, so `<c-card` does not catch a future `<c-card-…>`.
- These tags are banned:
  - The content widgets: `c-admonition`, `c-accordion`, `c-flashcard`, `c-pull-quote`, `c-equation`,
    `c-youtube`, `c-pdf-embed`, `c-file-download`, `c-code-block`, `c-table`, `c-picture`,
    `c-image-grid`, `c-card`, `c-content-link` and `c-article-link`.
  - The deleted components: `c-callout` and `c-panel-notice`.
- App templates may still use the other content-engine components: `c-course-price`,
  `c-organisation-byline`, `c-organisation-mark`, `c-article-byline`, `c-article-card` and `c-grid`.
- A failure names the file, the tag and the fix: "use `<c-alert>` for a status message in an app
  page; content widgets are for authored markdown only".
- The reference page escapes any banned tag it shows as sample code.

Related tests:

- `panel_framework/tests/invariants/test_templates.py` `FORBIDDEN_IN_DIALOGS` drops its
  `<c-callout>` entry. Its hand-built `bg-error/10` box rule stays, and its message names `<c-alert>`.
- `learner_interface/tests/views/test_course_player.py` `test_the_closed_notice_is_not_a_callout`
  becomes `test_the_closed_notice_is_not_an_alert_box`. It asserts that no node under the notice's
  parent has the `alert` class, so the "a page a person cannot use is never a boxed alert" rule
  stays guarded.

## Testing

- Component tests (`freedom_ls/base/tests/components/test_alert_component.py`):
  - each tone renders `alert alert-<tone>` and its icon
  - an unknown tone renders as `info`
  - the role mapping for all four tones
  - the title renders as non-heading text
  - a passed `class` merges into the one class attribute
  - `id` and `data-testid` land on the box
- The guard test fails on a fixture holding `<c-admonition>`, `<c-callout>` or `<c-panel-notice>`,
  passes on `<c-course-price>`, and ignores a banned tag inside either comment form.
- Feature tests that find a migrated alert by text, `data-testid` or `role` pass without changes to
  their assertions.
- Frontend QA covers each migrated page at the QA viewports:
  - the alert's width matches its container
  - the spacing around it holds
  - tint, text and icon are readable for every tone in both themes

## Open questions

- Q: Should the login page's "New here?" prompt become a plain line under the form instead of an alert? → A: It stays an `info` alert. (assumed default: the migration is like-for-like. Overrule by editing "Migrations".)
- Q: Should the developer-only "UNHANDLED FORM TYPE" box in `question.html` raise an exception instead? → A: It stays an `error` alert. (assumed default: failure behaviour is outside this spec. Overrule by editing "Migrations".)
- Q: Product docs call some of these boxes a "notice". Should they say "alert"? → A: No, product docs keep "notice" for what a person reads, and "alert" is the component name. (assumed default: reader-facing wording is not a code identifier. Overrule by editing "Documentation and downstream".)
- Q: Should the alert offer a compact size? → A: No, one size that inherits its context's text size. (assumed default: the panel and page uses differ only in text size. Overrule by editing "The component".)
