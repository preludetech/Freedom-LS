# Spec: theme-fit alerts for app pages

Idea: `idea.md`. Recorded answers: `answers.md`. Research: `research_*.md` in this directory.

## Purpose

App pages show status messages in two components that do not fit the learner and educator design.
`<c-callout>` (`freedom_ls/base/templates/cotton/callout.html`) carries the course-content look:
`my-6` margin, a thick left stripe, an `h4 text-xl` title and an indented body. It is used in 10 app
templates. `<c-panel-notice>` (`freedom_ls/panel_framework/templates/cotton/panel-notice.html`) is
a compact notice that only panels and dialogs use. Authors pick whichever is nearest, and nothing
stops them reaching for a content-engine widget.

This work adds one alert component, `<c-alert>`, in the base app for every app page. It replaces
both `c-callout` and `c-panel-notice`, deletes them, and adds a test that keeps content-engine
widgets out of app templates. The content engine and `<c-admonition>` do not change.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| alert (`<c-alert>`) | coined | A static, toned status box in an app page, panel or dialog. No glossary entry or component uses the word today. `role="alert"` (ARIA) and the comms composer's `alert` string are unrelated. |
| content widget | narrowed | A content-engine cotton component that exists only for authored markdown (the list under "Guard test"). `config/settings_base.py` `MARKDOWN_ALLOWED_TAGS` lists the widgets markdown may use. |

## Scope

In:

- `<c-alert>` in `freedom_ls/base/templates/cotton/alert.html`.
- Every `<c-callout>` and `<c-panel-notice>` use in `freedom_ls/` moves to `<c-alert>`.
- The hand-built alert box in `freedom_ls/base/templates/partials/form.html:20` moves to `<c-alert>`.
- `callout.html`, `panel-notice.html` and their component tests are deleted.
- A guard test for app templates.
- Skills, brand guidelines, docs and upgrade notes.

Out:

- `freedom_ls/content_engine/` and `<c-admonition>`: no change.
- Toasts (`base/templates/partials/messages.html`, `_toast.html`). They are dismissible and fixed-position, a different job.
- Field-level error text (`text-error text-sm` lines beside a field or control, such as `comms/partials/composer.html:88`).
- The dialog error summary (`panel_framework/templates/panel_framework/partials/error_summary.html`). It is a validation summary that takes focus, a different job from a notice.
- Dismissing an alert. Alerts are static.
- Copy changes to migrated messages, and merging the paused/access-ended pair in `course_detail.html`.
- First Class's `lp/step.html`. Downstream projects migrate through the upgrade notes.

## Decisions

- **One component everywhere.** `c-panel-notice` is deleted rather than kept beside `c-alert`, so
  there is one right answer in every context (`answers.md`).
- **`c-callout` and `c-panel-notice` are deleted, not aliased.** Downstream projects migrate through
  the upgrade notes (`answers.md`).
- **The attribute is `tone`**, the name `c-panel-notice` and `c-button` already use. `level` is not
  kept.
- **The look is `c-panel-notice`'s, not `c-callout`'s.** That means a tinted box with a thin full
  border, `rounded-md`, and no outer margin, because the parent spaces its children. The thick left
  stripe and large title belong to content.
- **The styling lives in the existing `.alert` theme classes** in `tailwind.components.css`, so a
  theme reshapes every alert in one place. `docs/how tos/theme-fls.md` already documents these
  classes as a theme hook. Today no template uses them.
- **Live roles follow `c-panel-notice`.** `error` gets `role="alert"` and `success` gets
  `role="status"`. `info` and `warning` get no role, because they are read in place. Existing
  tests and the HTMX error re-renders already rely on this mapping.
- **Each tone shows an icon.** The icon is decorative (`aria-hidden`). The tone is never conveyed by
  colour alone (WCAG 1.4.1).
- **The title is not a heading.** Its right level depends on where the alert sits, and most alerts
  are one sentence.

## Requirements

### The component

`freedom_ls/base/templates/cotton/alert.html`:

```html
<c-alert tone="info|success|warning|error" title="…">One or two sentences.</c-alert>
```

- `tone` defaults to `info`. An unknown tone renders as `info`, never nothing. (Today `c-callout`
  renders nothing for an unknown level.)
- `title` is optional. It renders as a bold first line (`<strong class="block font-semibold">`),
  not a heading element.
- The default slot is the body. It takes plain text, inline markup, a list or a `<c-button>`.
- `{{ attrs }}` passes through, so callers can add `id`, `data-testid`, `tabindex` and `hx-*`
  attributes and set `class`. A passed `class` is appended to the alert's own classes.
- Markup: an outer box with classes `alert alert-<tone>`, with a `<c-icon>` and the title and slot
  beside it. Icon names follow the toast mapping in `partials/_toast.html`: `info`, `success`,
  `warning`, `error`.
- Roles as in "Decisions".
- Text uses `text-on-surface` on the tint. A tone colour on its `/10` tint fails contrast for warning
  and success, which is what `test_callout_component.py` guarded against.
- No `text-sm`: the alert inherits the body size of the page, panel or dialog it sits in. This
  follows the panel-framework rule "Lists, consequences, notices and errors in the body take no
  `text-sm`".

`tailwind.components.css` (the `.alert` family, lines 371-386):

- Add `.alert-warning` beside `.alert-success`, `.alert-error` and `.alert-info`.
- Change the four tone classes to match `c-panel-notice`'s current tint: `bg-<tone>/10 border-<tone>/20`.
- Change `.alert` padding to `p-3`.
- Each tone class sets the icon colour, so a theme can repoint it.
- `freedom_ls/themes/first_class/static/themes/first_class/theme.css:165-175` overrides `.alert*`.
  Keep each override working, and add a warning override if the theme needs one for contrast.

### Guard test

New `freedom_ls/base/tests/invariants/test_app_templates_use_app_components.py`. It follows the
shape of `freedom_ls/icons/tests/invariants/test_no_font_awesome.py`: a scan with a carve-out,
parametrised per rule.

It scans `freedom_ls/*/templates/**/*.html`, with two exclusions:

- `freedom_ls/content_engine/templates/`, where the widgets live and nest.
- Text inside `{% comment %}…{% endcomment %}` blocks.

The rules:

- No content widget tag. The banned set is the content-engine cotton components that exist only for
  authored markdown: `c-admonition`, `c-accordion`, `c-flashcard`, `c-pull-quote`, `c-equation`,
  `c-youtube`, `c-pdf-embed`, `c-file-download`, `c-code-block`, `c-table`, `c-picture`,
  `c-image-grid`, `c-card`, `c-content-link` and `c-article-link`.
- Content-engine components that app templates legitimately render stay allowed: `c-course-price`,
  `c-organisation-byline`, `c-organisation-mark`, `c-article-byline`, `c-article-card` and
  `c-grid`.
- No `<c-callout` and no `<c-panel-notice`, so the deleted components are not reintroduced.
- The failure message names the file, the tag and the replacement: "use `<c-alert>` for a status
  message in an app page; content widgets are for authored markdown only".

Other tests change too:

- `panel_framework/tests/invariants/test_templates.py` `FORBIDDEN_IN_DIALOGS`:
  - Drop the `<c-callout>` entry, since the new guard covers it.
  - Keep the hand-built `bg-error/10` box rule. Its message now points to `<c-alert>`.
- `learner_interface/tests/views/test_course_player.py:4462` (`test_the_closed_notice_is_not_a_callout`)
  keys on `c-callout`'s `border-l-4`. Re-point it to assert that no `.alert` element sits under the
  closed notice, so it keeps guarding the "a page a person cannot use is never a callout box" rule.
- `freedom_ls/markdown_rendering/tests/test_markdown_utils.py` keeps its tests that `<c-callout>`
  in markdown is stripped. They use the literal string and still guard the content side.

## Testing

- Component tests (`freedom_ls/base/tests/components/test_alert_component.py`):
  - each tone renders `alert alert-<tone>` and its icon
  - an unknown tone renders as `info`
  - roles: `error` gives `role="alert"`, `success` gives `role="status"`, `info` and `warning` have
    none
  - the title renders when given and is not a heading
  - a passed `class`, `id` and `data-testid` land on the box
  - body text uses `text-on-surface`, not a bare `text-<tone>`
- The guard test fails on a fixture template that holds `<c-admonition>`, `<c-callout>` or
  `<c-panel-notice>`, passes on `<c-course-price>`, and ignores a tag inside `{% comment %}`.
- Every existing feature test that finds a migrated alert by text, `data-testid` or `role` still
  passes unchanged. That includes `accounts/tests/test_views.py:292-380`,
  `learner_interface/tests/views/test_course_paused.py:284-305` and
  `educator_interface/tests/test_views.py:8142`, plus the panel and dialog tests that relied on
  `c-panel-notice`.
- Frontend QA covers each migrated page: alert width matches its container, the spacing around it
  holds, and the warning and success tints are readable in both themes.

## Open questions

- Q: The panel framework is being extracted into its own package. Moving its templates from its own
  `c-panel-notice` to base's `c-alert` adds a host dependency. Should the framework keep its own
  notice instead? → A: No. The framework uses `<c-alert>`, and
  `extract_panels_framework-4-template-contract` lists it in the host contract like `c-button` and
  `c-chip`. (assumed default: the user chose one component everywhere, and spec 4 already
  handles base components as a host contract. Overrule by editing "Decisions".)
- Q: Should the login page's "New here?" prompt stay an alert, or become a plain line of text under
  the form? → A: It stays an `info` alert. (assumed default: the scope is a like-for-like
  migration, and its tests find it through the surrounding `role="alert"` region. Overrule by
  editing "Migrations".)
- Q: Should `form_engine/question.html`'s developer-only "UNHANDLED FORM TYPE" box become an
  exception instead? → A: It stays an `error` alert. (assumed default: changing failure behaviour
  is outside this spec. Overrule by editing "Migrations".)
- Q: Should the alert take a compact size? → A: No. There is one size, and it inherits the body
  text size of its context. (assumed default: `c-panel-notice` and the page uses differ only in
  text size, and the dialog rule already forbids `text-sm` for notices. Overrule by editing "The
  component".)
