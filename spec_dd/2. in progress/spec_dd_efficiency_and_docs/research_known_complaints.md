# Research: known complaints about agentic coding and spec-driven development

Spec: `spec_dd_efficiency_and_docs`. Question: what do users commonly complain about with this kind of work, and what remedy do people recommend?

Caveat: the web sources are mostly blogs, forum threads and GitHub issues, not studies. Numbers are individual teams' experience. Treat them as direction, not benchmarks.

## Part 1: external complaints and remedies

| # | Complaint | Recommended remedy | Maps to idea item |
|---|-----------|--------------------|-------------------|
| 1 | The agent runs the full suite on nearly every round. One team had an eight-minute build with the full suite in almost every agent round, so the suite became the bottleneck. | Order checks by speed. Seconds: linters, type checkers, targeted tests on the affected unit. Minutes: full unit suite. Full suite on merge and on a schedule, or when build/CI config changes or the selector errors. Always run new and changed tests. Move E2E-scale tests to nightly. | 2, 5, main thing |
| 2 | Flaky tests derail the agent. About 15% of failures on PR branches in one team were flaky, and "an LLM doesn't know that". Agents also "fix" tests that are not broken, and write flaky tests themselves (fixed sleeps, unordered results, randomness). | Quarantine known-flaky tests out of the inner loop and re-run them separately. Do not retry silently into a pass. Diagnose and fix the root cause. A caution from one team: after quarantining, the remaining "non-flaky" tests gave more false positives, so quarantine is not a substitute for fixing. | 6 |
| 3 | Runaway test processes left behind by an agent that moved on (seven stuck test processes holding DB connections and CPU). | Kill runs older than a threshold well above normal suite time. Run one test run at a time. | 2, 6 |
| 4 | The agent stops to ask permission or ends a turn with a procedural question even when the next action is defined by an approved plan. Reported as a regression on a newer model, and as drift in long sessions even after autonomy was granted. Issues were opened on the Claude Code tracker. | Allow rules in settings control what the agent can do without asking. Instructions in CLAUDE.md or the command control what it does without asking. A gap between the two causes the pauses. Be specific in the command: name the recoverable states and the action to take (for example "push main, then continue"). A vague "just do it" can backfire. Auto mode is Anthropic's direction. | 6 |
| 5 | CLAUDE.md and skills are overlong. A big always-loaded file costs context every turn (one estimate: 7,000 to 10,000 tokens per turn for a 1,000-line file, mostly things the model already knows). Claude Code itself warns on large files. | Move task-specific material into skills that load on demand (progressive disclosure). Cut what Claude can infer from the code. Cut generic advice ("write clean code") and duplicated rules. Do not repeat skill descriptions in CLAUDE.md. Keep the always-loaded file short. Advice on size conflicts (about 50 lines, 200 lines, or about 2.5k to 4k tokens), so the numbers are not authoritative. Prompt caching cuts the money cost (cached reads at about 10% of base input price) but not the context pressure. | 3 |
| 6 | Spec-driven tools add ceremony. Spec Kit produces a large artifact tree (constitution, spec, plan, tasks, contracts). A Hacker News commenter found it "too slow, too much tweaking before seeing code" on a small CLI tool. Commenters compare it to waterfall. People copy a skill, run it once, find it slow and go back to unstructured prompting. | Match ceremony to task size. Lighter flows (OpenSpec: small change proposals with localized spec deltas). Defenders say the trade is speed for traceability and that a short spec is cheaper than fixing misunderstandings. A spec cannot compensate for slow review or missing tests. | 4, 1 |
| 7 | Docs that hide the flow. Spec-driven tool write-ups say a bad process moves ambiguity from chat into markdown, and that the user cannot see what happens in each step. | Show the flow visually and keep each command file clear to a human reader. (Inference from the sources, not a direct quote.) | 1 |

## Part 2: in-house evidence (this repo)

Paths are relative to the repo root.

1. **No feedback or complaint file is configured.** `.claude/sdd/config.md` has no feedback-rule section. Its "Rule Files" are brand and panel-framework skills only. The complaints live in the idea and in past specs.
2. **Test tiers already exist.** `.claude/sdd/config.md` points "Test tiers" at `claude_plugins/django-stack/resources/test_tiers.md`, which defines `none`, `targeted` and `full`, memory-aware runs, and "when a targeted run or full run fails". The complaint in the idea (full suite repeated) is therefore about where steps still choose `full`, not about missing tiers. The spec should audit which commands (rebase, finish_worktree, implement, review) name `full` and whether a `none` or `targeted` tier would do. A rebase that only moved spec files should be `none` (the file's own rule: "an untracked file no rule knows is `none`; a tracked one is `full`").
3. **Rebase hooks and pre-test rebuild** are configured (`claude_plugins/django-stack/commands/rebase_main.md`, `.claude/fls-dev/scripts/rebuild_after_rebase.sh`, a front-end check). Each rebase can trigger a rebuild, a front-end check and a test run. These are the "ceremony after rebase" the idea complains about.
4. **Parallel finish clash.** `spec_dd/0. maybe/better-finish-worktree-command/idea.md`: finishing several worktrees at once makes them clash. One finishes, the others must rebase and may conflict, and all run tests at once, "eating up ram, causing tests to crash and need to be restarted (wasting time)". The user's own proposed remedy: a "ready to finish" marker per worktree, plus one main-side command that crunches through ready worktrees with no confirmation. This is related to item 6 of the current idea (finish keeps stopping) and the spec should decide whether it absorbs or leaves it.
5. **RAM crashes of test runs** were addressed by the done spec `spec_dd/3. done/2026-11-13_14:59_claude-ram-usage/` (memory gate, xdist sizing, crash retry of unfinished tests only, `oom_score_adj`). It has its own `research_known_complaints.md`. Remedy already adopted: gate on free memory and retry only unfinished tests. Do not redo.
6. **Earlier efficiency round.** `spec_dd/3. done/2026-06-01_12:31_sdd-token-efficiency-and-structure/idea.md`: model tiering (Haiku for mechanical steps, Sonnet for review and research, Opus for authoring), one subagent per unit writing its own output file, resume by skipping units whose output exists, structured `blocked: needs X` returns, trim padding in command files, prefer paths over contents, and no re-reading files to "verify". Run commands on the main thread because subagents cannot nest. This is the baseline. Token work now should audit what grew back since, not repeat it.
7. **Flaky and redundant tests** were cleaned in earlier specs (`spec_dd/3. done/2026-05-02_18:13_testing-best-practice-phase-3-cleanup-flaky-and-redundant-tests/`, phase 4 e2e hardening). Flakiness still occurs, so the finish step needs a diagnose-and-fix path (answers.md: fix lands in the current branch).
8. **Rebase collisions are planned for.** `spec_dd/1. next/roadmap.md` repeatedly notes "whichever lands second rebases" (lines 91, 120, 189, 237, 304). Rebasing onto a moved main is expected and frequent, which is why a rebase that triggers a full run each time is costly.
9. **`address_pr_review`** is named by the user as unused. The config still has "PR Hooks: Fetch PR comments". That hook is a likely removal candidate with it, and the spec should confirm.
10. **Every done spec's todo ends with** `(cmd) Run /finish_worktree to clean up the worktree`. Several are left unticked (for example `2026-05-30_13:27_header-bar-upgrades`, `2026-05-07_themable-implementations-phase-3-component-class-overrides`), which is weak evidence that finish sometimes stops before completing. Not proven.

## Part 3: how the complaints line up with the answers already given

- Full suite at "sensible checkpoints", targeted elsewhere: matches the external consensus (complaint 1). Remedy to adopt: name the checkpoints in the spec, run new and changed tests always, and let a no-code-change rebase skip tests.
- Flaky fix in the current branch: matches the external advice to diagnose root causes instead of silent retry or quarantine (complaint 2). Add a bounded attempt count so a subagent does not loop on a real defect.
- Agent stopping: give the finish command a list of recoverable states (unpushed main, main moved, flaky test) with the action for each, and a short list of states that really need a human (conflict that changes meaning, change that invalidates QA). This matches complaint 4.
- `.drawio.svg` diagrams: addresses complaint 7. Keep command files human-readable while cutting tokens: move reference detail into on-demand files and keep the always-loaded text short (complaint 5).
