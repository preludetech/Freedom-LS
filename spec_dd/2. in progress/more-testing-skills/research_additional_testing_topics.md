# Research: additional testing topics beyond the confirmed skills

Confirmed skills already scoped by the idea: test organisation, Django Admin, Django Tasks, middleware,
signals, management commands, migrations. This doc surveys **other** areas that plausibly deserve their
own skill/resource doc, ranked by value and grounded in what FLS actually contains.

Method: PART A = web best-practice check (URLs cited). PART B = grep/read of FLS code to confirm the area
exists and is (or isn't) already tested/covered. Existing coverage checked against
`fls-claude-plugin/skills/testing/SKILL.md`, `fls-claude-plugin/skills/multi-tenant/SKILL.md`,
`fls-claude-plugin/skills/template/SKILL.md`, and `fls-claude-plugin/skills/playwright-tests/SKILL.md`.

## Ranked recommendations

| # | Area | Why it matters for FLS | FLS has the code? | Already covered by a skill? | Recommended action |
|---|---|---|---|---|---|
| 1 | **Multi-tenant / site-isolation testing** (asserting `SiteAwareManager` queries don't leak across `Site`s) | This is the core security boundary of a multi-tenant LMS. `SiteAwareManager.get_queryset()` (`freedom_ls/site_aware_models/models.py:43-50`) silently filters every site-aware model by the thread-local current site. A dropped `.filter(site=...)` anywhere is a cross-tenant data leak, and Django gives no structural protection against it. | Yes — `freedom_ls/site_aware_models/models.py` (`SiteAwareManager`, `SiteAwareModelBase`), used by `app_authentication.Client`, `role_based_permissions` models, `content_engine`, `student_management`, etc. | Partially. `fls-claude-plugin/skills/multi-tenant/SKILL.md` says "In tests, always use `mock_site_context`" but gives no pattern for proving isolation. `freedom_ls/site_aware_models/tests/test_factories.py` only checks that a factory *creates* objects on the right site (`test_site_can_be_overridden_explicitly`) — no test anywhere creates objects on **two** sites and asserts a query under site A excludes site B's rows. | **New skill/resource**: "Testing site isolation" — the two-site fixture pattern (create under site A and site B via `mock_site_context`, assert `Model.objects.all()` excludes the other site's rows), plus a note that this is the pattern every new site-aware model/view should get at least one regression test for. |
| 2 | **Model/form validation** (`clean()`, `full_clean()`, validators, `ValidationError` both ways) | Django does **not** call `full_clean()` on `save()`; a validator that's never exercised via `full_clean()` in a test gives false confidence. 10 of FLS's `models.py` files define `clean()`/`full_clean()`/raise `ValidationError` (`webhooks`, `content_engine`, `site_aware_models`, `accounts`, `course_interest`, `course_applications`, `student_progress`, `student_management`, `role_based_permissions`, `app_authentication`). | Yes, widespread — see file list above. | No dedicated section; the base `testing` skill has a generic "test validation both ways" rule (line 172-174 of SKILL.md) but no Django-specific `full_clean()`/factory-validity guidance. | **New resource doc** (fold into `resources/testing.md` rather than a standalone skill — it's a recurring pattern, not a distinct workflow): explicit `full_clean()` calls in tests, testing `clean()` vs field validators separately, and whether/when factories should call `full_clean()` on build (trade-off: catches bad factory data vs. slows down bulk creation). |
| 3 | **Permissions / RBAC** (`role_based_permissions` app: role gating, object-level role assignment, `has_perm`) | FLS ships a full custom RBAC system (`Role`, `ObjectRoleAssignment`, a registry/loader, `sync_role_permissions`/`validate_role_permissions` management commands) consumed by `panel_framework` and `webhooks` views. Getting permission tests wrong (e.g. patching `request.user` or skipping `has_perm`) silently defeats access control. | Yes — `freedom_ls/role_based_permissions/` (`models.py`, `registry.py`, `roles.py`, `loader.py`, `utils.py`, `management/commands/{sync,validate}_role_permissions.py`), consumed by `freedom_ls/panel_framework/` and `freedom_ls/webhooks/views.py`. Already has 7 test files (`test_registry.py`, `test_loader.py`, `test_types.py`, `test_roles.py`, `test_models.py`, `test_utils.py`, `test_management_commands.py`). | No. Not one of the 7 confirmed skills; the app's own `README.md` documents the system but not how to test it. | **New skill**: "Testing permissions/RBAC" — patterns for testing role assignment, `has_perm`/object-level checks via `client.force_login` (not mocked `request.user`, per the existing testing skill's own rule), and testing the `sync_role_permissions`/`validate_role_permissions` commands (cross-reference the confirmed "management commands" skill instead of duplicating). |
| 4 | **API-key / client authentication testing** | FLS has an `app_authentication` app whose `Client` model (`api_key = secrets.token_urlsafe(48)`, `is_active`) exists specifically "to allow other applications to authenticate and use an API exposed here." Once that authentication is wired up (checking the key on incoming requests), it needs dedicated testing guidance (valid key, invalid key, inactive client, wrong-site client). | **Product gap, not just a testing gap**: `freedom_ls/app_authentication/models.py` + `admin.py` + `factories.py` exist, but a repo-wide grep for `api_key` usage outside `app_authentication` found **no middleware, permission class, or view that actually validates a `Client.api_key` against a request** — it's currently just an admin-managed registry. `freedom_ls/app_authentication/tests/__init__.py` is the only test file (empty). | No. | **Recommend, but flag as premature**: don't write a "testing API-key auth" skill until the auth-checking code exists (there's nothing to test yet beyond the `Client` model itself, which needs the ordinary model-validation coverage from #2). Note the gap so whoever builds the API-auth wiring knows a skill should follow it. Do **not** confuse this with webhook signature testing below, which is a separate, already-solved problem. |
| 5 | **Webhook HMAC signature testing** | `freedom_ls/webhooks/` signs outgoing webhook payloads (`v1,<base64 hmac-sha256>` scheme) and delivers them; a broken signature breaks every downstream integration silently. | Yes, and **already well covered**: `freedom_ls/webhooks/tests/test_signing.py` verifies the signature format, a hand-computed HMAC (independent oracle, not a tautology), and that body/secret/id/timestamp all change the signature. Plus `test_delivery.py`, `test_integration.py`, `test_events.py`, `test_registry.py`, `test_models.py`, `test_presets.py`, `test_rendering.py`, `test_admin.py`, `test_send_test_views.py` — 11 test files total. | No dedicated skill, but the code+tests are already a strong worked example. | **Skip / low priority** for a new skill — this area is a model of good practice already, not a gap. If a skill is written, it should be a short resource *pointing at* `test_signing.py` as the canonical HMAC-testing example rather than reinventing guidance. |
| 6 | **Caching / cache invalidation** (`functools.cache` on config/backend loaders) | Stale cached config (e.g. course-access backend resolution) causes hard-to-reproduce bugs where a test passes in isolation but fails under `pytest-randomly` reordering because an earlier test's cached value leaks in. | Yes — `freedom_ls/course_access/loader.py:23` decorates `get_course_access_backend` with `@functools.cache`; the module's own docstring already says tests must call `get_course_access_backend.cache_clear()` before/after (lines 5, 33). `course_access/tests/` has 9 test files exercising backends/overrides. | Not explicit. The confirmed "test organisation" skill is the natural home (conftest/fixture patterns), and existing FLS code already demonstrates the fix inline. | **Fold into the "test organisation" skill** as a short subsection ("cached module-level singletons need an autouse `cache_clear()` fixture, not per-test manual calls") rather than a standalone skill — it's a narrow, already-solved pattern in FLS's own code, but worth codifying so new `@functools.cache` usages don't reintroduce order-dependent test pollution. `pytest-antilru` is a possible tooling option if this recurs elsewhere. |
| 7 | **Email testing (`django.core.mail.outbox`)** | Sending the wrong email, to the wrong recipient, or a broken template is a real (if not novel) failure mode for an LMS that emails registration/reset/notification content. | Yes, and **already well covered**: `freedom_ls/accounts/tests/test_allauth_account_adapter.py` asserts on `mail.outbox` (length, MIME parts, headers) for `AccountAdapter.send_mail`; `freedom_ls/accounts/tests/test_email_templates.py` covers template rendering with de-branded, hard-coded theme context (not live config) and a max-size assertion; `resources/email_templates.md` documents the context-variable contract. | No dedicated skill, but two solid existing test files plus a resource doc. | **Skip** — no material gap. At most, add one cross-reference line from the future "test organisation" or a resources index pointing at these two files as the canonical email-testing examples. |
| 8 | **Template tags / filters unit testing** | FLS has 9 files registering custom tags/filters (`content_tags.py`, `course_icon_tags.py`, `base_tags.py`, `pagination_tags.py`, `course_storage_keys.py`, `icon_tags.py`, `panel_tags.py`, `data_table_tags.py`, `fls_base_filters.py`). Testing these as plain Python functions (not through full page renders) is cheap and catches edge cases (empty input, `None`, invalid args) that end-to-end/Playwright tests won't reach. | Yes — the 9 files above. | Explicitly **not** covered: `fls-claude-plugin/skills/template/SKILL.md` has zero mentions of testing; the confirmed skills list doesn't include it either. Overlaps with, but is distinct from, `fls:template` (authoring conventions) and `fls:playwright-tests` (browser-level). | **New short resource doc**, not a full skill — cross-reference from both `fls:testing` and `fls:template` rather than duplicating. Content: use `django.template.Template(...).render(django.template.Context({...}))` for isolated tag/filter tests (no `RequestContext`/view needed) [Django docs: how-to custom template tags, https://docs.djangoproject.com/en/6.0/howto/custom-template-tags/]; reserve Playwright for tags whose output depends on HTMX/Alpine interactivity. |
| 9 | **Health checks / smoke / conformance tests** | Wrong readiness/liveness behaviour breaks orchestration (k8s-style probes); conformance tests guard against downstream projects breaking FLS's portability contracts. | Yes, and **already thoroughly covered** by a dedicated, still-active spec_dd initiative: `freedom_ls/health/tests/` (2 files, incl. async-view-under-ThreadPoolExecutor pattern), `freedom_ls/deployment/tests/` (5 files: sentry, context processors, storage, settings defaults, system checks), `freedom_ls/contrib/conformance/` (registry + `test_conformance_meta.py`, a meta-test proving the conformance probes "have teeth"). See `spec_dd/3. done/2026-08-24_06:31_fls-test-portability-part-2/`, `spec_dd/3. done/2026-08-23_16:23_fls-integration-system-checks/`, `spec_dd/3. done/2026-08-24_06:31_test_portability_4_upgrade_notes_and_docs/`. | No dedicated skill, but an entire active spec_dd track already owns this area's evolution and its own research docs (`research_conformance_tooling.md`, `research_django_system_checks.md`). | **Skip** — do not duplicate. This is being actively developed under its own initiative; a testing-skills spec should not compete with it. If anything, once that initiative lands, a short cross-reference from `fls:testing` to its output would suffice — not a new skill from this spec. |

## Summary of concrete recommendations (decision-ready)

**New skills (standalone, like admin/tasks/middleware):**
1. Testing site isolation (multi-tenant leak-proofing) — highest security value, zero current coverage of the actual isolation property.
2. Testing permissions/RBAC (`role_based_permissions`) — substantial existing app + tests, no guidance layer.

**New resource docs (fold into existing skill/`resources/testing.md`, not standalone skills):**
3. Model/form validation (`clean()`/`full_clean()`/`ValidationError`) — recurring pattern across 10 files.
4. Cached module-level singletons (`functools.cache` + `cache_clear()` fixture pattern) — fold into "test organisation" skill.
5. Template tag/filter unit testing — short doc, cross-referenced from `fls:testing` and `fls:template`.

**Flag but don't build yet:**
6. API-key/client authentication testing (`app_authentication`) — the authentication-checking code itself doesn't exist yet; write the skill once the feature lands, not before. Note this as a product TODO, not a testing-skill gap.

**Skip (already well covered, don't duplicate):**
7. Webhook HMAC signing (`webhooks/tests/test_signing.py` is already exemplary).
8. Email/outbox testing (`accounts/tests/test_allauth_account_adapter.py`, `test_email_templates.py`, `resources/email_templates.md`).
9. Health/smoke/conformance testing (owned by the active `fls-test-portability` spec_dd track).
