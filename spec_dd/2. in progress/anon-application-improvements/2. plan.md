# Implementation plan: anonymous application improvements

Source: `1. spec.md` in this directory. The three `research_*.md` files beside it hold the
codebase facts the spec rests on. The decisions of
`spec_dd/3. done/2026-10-12_18:37_ananomous-course-applications/1. spec.md` stand unless the spec
changes them.

Code snippets below are shapes, not finished files: they omit imports, and the implementer adds
them with full type hints on every function and no `Any`. Comments and docstrings inside the
snippets are written to be copied as they are, with one exception: a line of the form
`...  # <note>` is an instruction to the implementer about what fills the gap, and is never
copied. Nothing else in this document is copied: never put a sentence that names a slice into
code, a test name or a template comment.

Every slice is committed on its own with `uv run manage.py makemigrations --check` clean, the
default test suite green (`uv run pytest`) and the pre-commit hooks passing. Follow TDD inside each
slice: the tests a slice names are written first and fail before the code lands. Each test bullet
below is one behaviour, so it is one test; where a bullet lists several outcomes of one action,
write one test per outcome around a shared arrange helper. A non-browser test calls the code once:
anything that needs the system in a prior state arranges that state first.

## Decisions the plan makes

- **The claim email reads the application row, not the reverse one-to-one cache.**
  `send_application_claim_email` needs `is_submitted` for its wording. `application_of(applicant)`
  returns whatever `CourseApplication` object the applicant's reverse one-to-one cache holds, and
  right after `_start_application` that is an object created before the sitting was attached (the
  helper re-fetches the row under lock into a second object), so it would read as submitted. The
  email helper therefore reads the row afresh with one query:
  `CourseApplication.objects.filter(anonymous_applicant=applicant).select_related("form_progress").first()`.
  A send is rare enough that the query costs nothing measurable.

  > **Assumed default:** keep the applicant-taking signature and the fresh row read, rather than
  > passing the application into `send_application_claim_email`. Why: the spec names the function
  > by its applicant and `application_of`, and the fresh read is the smallest change that is
  > always right; passing the application would touch four call sites. To change: Slice 3.

- **The details step restores the stored address before calling `update_applicant_email`.**
  `ApplicantDetailsForm` is a `ModelForm`, and `is_valid()` writes the posted address onto the
  bound applicant instance. The view already keeps `previous_email`; it puts that back onto the
  instance and then calls `update_applicant_email(applicant, email)`, so the one helper sees a real
  change and bumps the version. Then `form.save()` writes the name and consent evidence onto the
  same object.

  > **Assumed default:** the restore stays in the view and the version-bump test in Slice 4
  > guards it, rather than bumping the version inside `ApplicantDetailsForm.save()`. Why: the
  > spec makes `update_applicant_email` the one place an address changes, and a second site that
  > knows "a changed address bumps the version" is what that rule forbids. To change: Slice 4.

  > **Assumed default:** two concurrent address changes from one session (A→B and A→C in the same
  > instant) are accepted as a double-submit edge case: both read version 0, both write 1, and the
  > later `form.save()` wins the whole row. Why: the posts come from one browser that navigates
  > sequentially, and the same last-writer race exists in `form.save()` today. To change: Slice 4
  > (`update_applicant_email` could lock the row and write `F("claim_link_version") + 1`, and the
  > view would then save only the name and consent fields).

- **The details-step rate-limit dance becomes a small object.** The dry run happens before
  validation and the spend after it, with form validation in between, so a single function
  cannot hold both halves. `_AddressLimit` (one per POST) exposes `refuse_if_exhausted()`,
  `spend()` and `spend_for_honeypot()`; `applicant_details` and `change_applicant_email` both use
  it. The typed temporaries (`allowed: bool = ...`) stay where allauth's untyped returns need them
  for mypy, and the docstring states the honeypot asymmetry (a trip always spends, whether or not
  the address changed, as it does today).
- **`tripped_honeypot` becomes a module function beside `reject_honeypot`.** Both forms need the
  same three lines; `tripped_honeypot(form)` in `freedom_ls/accounts/forms.py` serves both without
  a mixin.
- **Held submitted against incoming submitted also tells the applicant.** The spec names copy for
  held-submitted-incoming-draft and for held-draft. Today's rule also discards an incoming
  submitted application when the account already holds a submitted one, and the spec's success
  criterion is that no attach silently deletes anything, so the confirm page says "You've already
  applied for <course>. This application will be discarded." in that case.
- **Login adoption reports both outcomes.** The spec names a message when the held application is
  kept; the success criterion forbids any silent discard, so the receiver also says when the
  account's unfinished application was replaced by the one the session was working on.

  > **Assumed default:** add the second message. Why: the spec's success criterion "No attach
  > silently deletes an application the applicant was told nothing about" covers the login path
  > too. To change: Slice 2.

- **The login-adoption messages are sent `fail_silently=True`.** `client.force_login` and shell
  logins fire `user_logged_in` with a bare request that has no messages storage; the receiver must
  not raise there.
- **The anonymous dashboard query is skipped by Django, not by a new helper.** With an empty
  session map, `owned_applications(request)` filters on `anonymous_applicant__pk__in=[]`, which
  Django resolves to an empty result without a query. The backend relies on that and the test pins
  it with `django_assert_max_num_queries(0)`.
- **`VisibilityEnforcingBackend` shares its checks through one private method.**
  `_visibility_decision(user, course)` returns the coming-soon, hidden or free-override decision,
  or `None` when the inner backend decides; `get_access` and `get_access_for_request` both call it.
- **`ApplicationCourseAccessBackend` splits the gated branch into two private methods.**
  `_ungated_decision(user, course)` returns the invalid-config or inherited decision, or `None`
  when the course is gated and the visitor unregistered; `_gated_decision(course, application)`
  builds "View my application" or "Apply now". `get_access` and `get_access_for_request` both use
  them, differing only in how they find the application.
- **Slice order.** Claiming a draft and the merge rule land before the early email makes draft
  claims reachable, so no intermediate commit discards an application silently. The claim link
  version lands before the notice offers "Wrong address? Change it", so a changed address always
  clears the sent stamp and invalidates earlier links by the time the notice points at the step.
  The request-aware dashboard method lands with the dashboard slice that first calls it.

## Slice 1: claiming a draft through its claim link

**Behaviour:** a claim link whose application is still a draft confirms, creates or joins the
account, signs the applicant in and lands them on the draft's resume page. Until this slice the
link renders "invalid" for a draft, which would make the early email of Slice 3 useless.

### `freedom_ls/course_applications/views.py`

`claim_application`: drop the `or not application.is_submitted` clause from the invalid check.
Every `_render_claim` call that has an applicant (the `confirm`, `expired` and `resent` states)
passes `is_submitted=application.is_submitted`, so each state can word itself for a draft:

```python
if request.method != "POST":
    return _render_claim(
        request,
        "confirm",
        link.applicant,
        applicant_email=link.applicant.email,
        is_submitted=application.is_submitted,
        sets_password=claim_sets_a_password(owner),
        signed_in_as=...,
    )
```

The redirect to the status page after a successful claim is unchanged: `application_status`
already sends a draft on to `_resume_url`, and `_owned_application` finds it through
`user=request.user` now that `attach_to_user` set `user` on the application and its sitting.

### Template: `course_applications/claim.html`

The confirm state branches on `is_submitted`:

- `head_title` and the `<h1>`: "Finish your application for <course>" when submitted, "Continue
  your application for <course>" when not.
- The confirm paragraph for a draft: "Press Confirm to verify <strong>{{ applicant_email }}</strong>.
  You'll then be taken back to your application." followed by the existing password or signed-in
  sentence. No mention of review.
- The `expired` state's muted line reads "Links to continue an application stop working after a
  few days." when `is_submitted` is false; the `resent` state is the same for both.

> **Assumed default:** the draft confirm page says what the spec words (verify the address,
> return to the application, then the existing password or sign-in sentence) and does not add a
> sentence about the consent being recorded against the account. Why: the submitted confirm page
> has never said so either, and the discard notices of Slice 2 cover the one new consequence a
> draft claim can have. To change: this section.

## Slice 2: the merge rule, and telling the applicant what an attach discards

**Behaviour:** between two applications for one course at attach time, a submitted one beats a
draft and between two drafts the incoming one wins. The claim confirm page and the login adoption
say what happens. This lands before the early email so no reachable claim discards anything
silently.

### `freedom_ls/course_applications/claims.py`

`attach_to_user` tie-break at lines 233-237:

```python
if held is not None:
    if held.is_submitted:
        # A request already made stands; the incoming one could only repeat or
        # precede it, so it goes with its applicant.
        erase_anonymous_applicant(applicant)
        return held
    # The account's draft gives way: the applicant has just been working on
    # the incoming one, whether that is further along or a submission.
    _discard_draft(held)
```

Rewrite the docstring's rule sentence to match: "a submitted application beats a draft, and
between two drafts the incoming one stays".

### `freedom_ls/course_applications/views.py`

`claim_application`, confirm state: after `owner` resolves on the same site, find what the account
holds for the course and name the outcome as one short string the template switches on:

```python
held = (
    CourseApplication.objects.filter(user=owner.user, course=link.applicant.course)
    .select_related("form_progress")
    .first()
    if owner is not None
    else None
)
held_application = "" if held is None else ("submitted" if held.is_submitted else "draft")
...
_render_claim(request, "confirm", link.applicant, ..., held_application=held_application)
```

### Template: `claim.html`

In the confirm state, after the verify sentence:

```django

    <p>You've already applied for {{ course.title }}. This unfinished application will be discarded.</p>
{% elif held_application == "submitted" %}
    <p>You've already applied for {{ course.title }}. This application will be discarded.</p>
{% elif held_application == "draft" %}
    <p>This replaces the unfinished application for {{ course.title }} already on your account.</p>
```

### `freedom_ls/course_applications/receivers.py`

`adopt_anonymous_applications_on_login`, inside the loop, with `remembered_anonymous_applicants`
gaining `"course"` in its `select_related`:

```python
# Read before the attach: an incoming application that loses is erased
# with its applicant, and the message still has to name the course.
course_title = applicant.course.title
held = attach_to_user(application, applicant, user)
# Never raises: a login from the shell or a test client has no messages storage.

    messages.info(
        request,
        f"You had already applied for {course_title}, so that application was kept.",
        fail_silently=True,
    )

    messages.info(
        request,
        f"Your unfinished application for {course_title} was replaced by the one you just started.",

```

`held_was_a_draft` needs the receiver to know what the account held before the attach, which
`attach_to_user` finds and discards internally. Give `attach_to_user` that knowledge to return
rather than re-querying: extend `ClaimOutcome`-style reporting with a small frozen dataclass
`AttachResult(application: CourseApplication, discarded_draft: bool)` returned by
`attach_to_user`, and have `attach_claimed_application` read `.application` from it. The receiver
then branches on `result.application.pk != application.pk` and `result.discarded_draft`.

> **Assumed default:** the tie-break, the confirm-page copy and the two login-adoption messages
> stay in one slice. Why: they share one rule and one arrange helper, and the messages are the
> rule's user-facing half. To change: split the receiver change into its own slice after this
> one.

## Slice 3: the claim email goes out at the details step, not at submit

**Behaviour:** on a course with a form, the details step sends one claim email with draft wording
as soon as the applicant gives an address; check-your-answers sends nothing. A form-less course is
unchanged.

### `freedom_ls/course_applications/emails.py`

```python
def send_application_claim_email(request: HttpRequest, applicant: AnonymousApplicant) -> bool:
    ...
    # The row, not the applicant's cached reverse relation: the cache can hold
    # an object made before the sitting was attached, which reads as submitted.
    application = (
        CourseApplication.objects.filter(anonymous_applicant=applicant)
        .select_related("form_progress")
        .first()
    )
    is_submitted = application is not None and application.is_submitted
    ... send_mail(..., {"course": ..., "claim_url": ..., "site_name": ..., "user": None,
                        "is_submitted": is_submitted})
```

The email carries nothing the applicant typed: course title, site name and the link only. A
visitor can now cause this email to reach any address by typing it at the first step, so the
draft branch must not add the first name or anything else from the form.

### Email templates: `course_applications/templates/course_applications/email/`

Branch on `is_submitted` in all three:

- `application_claim_subject.txt`: submitted keeps "Finish your application for {{ course.title }}";
  draft is "Continue your application for {{ course.title }}".
- `application_claim_message.txt` and `.html`: the submitted branch is today's copy. The draft
  branch says "You started an application for {{ course.title }} on {{ site_name }}." then
  "Follow the link below to confirm your email address and get back to your application." The
  button and the plain-text line read "Continue your application". The closing "If you didn't
  apply..." sentence stays in both branches. No mention of review or of anything being received.

### `freedom_ls/course_applications/views.py`

`applicant_details`, after `form.is_valid()`:

```python
email = form.cleaned_data["email"]

...  # the rate-limit spend and the double-click guard, unchanged
```

`address_changed` is `True` for a new applicant (`previous_email` is `None`) and for a changed

`application_check_answers`: remove the `send_application_claim_email` call at lines 536-537, so
the unverified branch is just `return redirect("course_applications:status", pk=app.pk)`.

```python
def _token_payload(payload: object) -> tuple[UUID, int] | None:
    """The applicant pk and link version a token names, or None for a shape
    that was never ours.

    A bare pk string is a link signed before versions existed; it reads as
    version 0, so links already in mailboxes keep working until the address
    next changes.
    """
    if isinstance(payload, str):
        pk_text, version = payload, 0
    elif isinstance(payload, dict) and isinstance(payload.get("v"), int):
        pk_text, version = str(payload.get("a", "")), payload["v"]
    else:
        return None
    try:
        return UUID(pk_text), version
    except ValueError:
        return None


def read_claim_token(token: str) -> ClaimLink | None:

    try:
        payload = signing.loads(token, salt=CLAIM_TOKEN_SALT, max_age=max_age)
        expired = False
    except signing.SignatureExpired:
        payload = signing.loads(token, salt=CLAIM_TOKEN_SALT)
        expired = True
    except signing.BadSignature:
        return None

    if named is None:

    applicant = (AnonymousApplicant.objects.filter(pk=pk).select_related(...).first())

    # since changed; it is unusable even for a fresh link, which would go to
    # that old address.
    if applicant is None or applicant.claim_link_version != version:
        return None
    return ClaimLink(applicant, expired)


def update_applicant_email(applicant: AnonymousApplicant, email: str) -> bool:
    """Change the address every claim link for this applicant is bound to.

    The version moves on so earlier links stop matching, and the sent stamp
    clears so the pages say truthfully that nothing has reached the new
    address yet. Returns False, and writes nothing, for an address equal to
    the stored one.
    """
    email = normalise_email(email)
    if email == applicant.email:
        return False
    applicant.email = email
    applicant.claim_link_version += 1
    applicant.claim_email_sent_at = None
    applicant.save(
        update_fields=["email", "claim_link_version", "claim_email_sent_at", "updated_at"]
    )
    return True
```

```python
@dataclass(frozen=True)
class _AddressLimit:
    """The per-address `application_details` bucket one POST would spend.

    Tested before validation, so nothing is written for an exhausted address,
    and spent after it, so a typo or a name-only change costs nothing. The
    bucket is shared by everyone who posts the address, so a POST that would
    not spend it is never refused. A honeypot trip always spends it, changed
    address or not: a bot pays for every attempt.
    """

    request: HttpRequest
    key: str
    would_spend: bool

    @classmethod
    def for_post(cls, request: HttpRequest, posted_email: str, previous_email: str | None) -> _AddressLimit:
        site = get_cached_site(request)
        if not isinstance(site, Site):
            # A host that resolves no Site could not save the applicant either.
            raise Http404
        return cls(request, email_rate_limit_key(site, posted_email), normalise_email(posted_email) != previous_email)

    def refuse_if_exhausted(self) -> HttpResponse | None:
        if not self.would_spend:
            return None
        allowed: bool = ratelimit.consume(self.request, action=DETAILS_RATE_LIMIT_ACTION, key=self.key, dry_run=True)
        return None if allowed else ratelimit.respond_429(self.request)

    def spend(self) -> HttpResponse | None:
        if not self.would_spend:
            return None
        limited: HttpResponse | None = ratelimit.consume_or_429(self.request, action=DETAILS_RATE_LIMIT_ACTION, key=self.key)
        return limited

    def spend_for_honeypot(self) -> None:
        ratelimit.consume(self.request, action=DETAILS_RATE_LIMIT_ACTION, key=self.key)
```

```python
    """Move a submitted, unverified application to another address.

    The old address was never proven, so it hears nothing. Every link sent to
    it stops working and one new link goes to the new address. A draft
    changes its address on the details step instead, where the applicant
    already is.
    """
    status_url = reverse("course_applications:status", kwargs={"pk": pk})
    # A visitor whose session ended is sent to log in and then to the status
    # page, not back to this POST-only URL.

    if isinstance(found, HttpResponse):

    applicant = _unverified_applicant_of(app)
    if not app.is_submitted:
        raise Http404
    limit = _AddressLimit.for_post(request, request.POST.get("email", ""), applicant.email)
    refused = limit.refuse_if_exhausted()
    if refused is not None:
        return refused
    form = ApplicantEmailForm(request.POST, request=request)

        if limited is not None:

        if update_applicant_email(applicant, form.cleaned_data["email"]):
            _report_claim_email(request, applicant)
        return redirect(status_url)

    return _render_status(request, app, form, status=422)
```

### `freedom_ls/course_applications/backends.py`

```python
def get_dashboard_contributions_for_request(self, *, request):
    """The signed-in user's applications, or the drafts an anonymous session holds.

    A visitor sees only what their browser can still act on: a submitted
    application waits for the claim link, so it is not listed here.
    """
    if request.user.is_authenticated:
        return self.get_dashboard_contributions(user=request.user)
    from freedom_ls.course_applications.anonymous_session import owned_applications
    # An empty session map makes this an `IN ()` filter, which Django answers
    # without a query.
    drafts = list(
        owned_applications(request)
        .filter(form_progress__isnull=False, form_progress__completed_time__isnull=True)
        .select_related("course", "form_progress")
        .order_by("-created_at")
    )
    return self._applications_panel(drafts)

def _applications_panel(self, applications: list[CourseApplication]) -> list[DashboardContribution]:
    if not applications:
        return []
    return [DashboardContribution(template_name="course_applications/partials/dashboard_applications.html", context={"applications": applications})]
```

`get_dashboard_contributions` calls `_applications_panel(list(get_active_applications(user)))`.
