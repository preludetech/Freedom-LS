# Spec: anonymous application improvements

Idea: `idea.md`. Research: `research_current_anon_apply_flow.md`,
`research_early_verification_email_ux.md`, `research_resume_anonymous_draft_ux.md`. This builds on
`spec_dd/3. done/2026-10-12_18:37_ananomous-course-applications/1. spec.md`, whose decisions stand
unless this spec changes them.

## Purpose

The claim link goes out only when an anonymous application is submitted, so an applicant who stops
halfway, loses their session or changes device can't get back to their draft, and a mistyped
address goes unnoticed until it can't be fixed. An anonymous applicant who returns to the dashboard
or the course page sees nothing of the draft their browser holds. This spec sends the claim link
straight after the applicant details step, lets it claim a draft, lets the applicant correct their
address before and after submitting, and shows the session's drafts on the dashboard and course
page.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| `claim_link_version` | coined | Integer on `AnonymousApplicant`, carried in the claim token. A link is valid only while its version matches. No existing field records which claim links are current. |
| claim link notice | coined | The callout on every form page and on check-your-answers of an unverified draft, naming the address the claim link went to, with resend and change-address actions. |

## Scope

In:

- Sending the claim email from the applicant details step on a course with a form, and not again at
  submit.
- Claiming a draft through its claim link.
- Changing the address on a draft (details step) and on a submitted unverified application (status
  page), with earlier links invalidated.
- The anonymous session's drafts in the dashboard's "Your applications" panel, and "View my
  application" on the course page.

Out:

- Form-less courses: the email is still sent on the `apply.html` confirmation POST.
- A "Not you? Discard" action, reminder emails, automatic purging of unclaimed drafts, and any
  change to session lifetime.
- Any change for signed-in applicants, beyond the shared tie-break in `attach_to_user`.
- Notifying the old address when the address changes. It was never proven, so it may be a
  stranger's mailbox.
- An audit trail of address changes for staff.

## Decisions

| Decision | Reason |
| --- | --- |
| Earlier links are invalidated by a version counter in the token, not by putting the address in it. | Address binding revives an old link when the applicant changes A→B→A. |
| A plain resend to an unchanged address does not bump the version. | Every link in that mailbox goes to the same person; killing them only produces "invalid link" pages. |
| An existing pk-only token reads as version 0. | Links already in mailboxes keep working until the address next changes. |
| Between two applications for one course at attach time, a submitted one beats a draft; between two drafts, the incoming one wins. | User decision. The applicant has just been working on the incoming draft. |
| A draft's resend goes through `application_status`'s existing POST. | Reuses the one resend path and its rate limit; the draft redirect then returns the applicant to their form. |
| The request reaches the access backend through two new request-aware methods, not a `request=` parameter on the existing ones. | Downstream backends that override `get_access(self, *, user, course)` would raise `TypeError` on a new keyword. |
| The course page shows "View my application" for any application the session owns, draft or submitted. | Matches the signed-in rule (`get_application_for_course` returns either). Submitted unverified applications already redirect from `apply` to the status page. |

## Requirements

### Data model: `freedom_ls/course_applications/models.py`

- `AnonymousApplicant.claim_link_version = models.PositiveIntegerField(default=0)`. One new migration;
  existing rows get 0.

### Claim token: `freedom_ls/course_applications/claims.py`

- `claim_token(applicant)` signs `{"a": str(applicant.pk), "v": applicant.claim_link_version}` with
  the existing `CLAIM_TOKEN_SALT`.
- `read_claim_token(token)` accepts that payload, and a bare pk string as `v = 0`. It returns
  `None` when `v` differs from the applicant's `claim_link_version`, in both the in-date and the
  expired branch (`claims.py:89-93`), so an old-address link never reaches "send a new link".
- New `update_applicant_email(applicant, email)` is the one place an address changes: it sets
  `email`, increments `claim_link_version`, clears `claim_email_sent_at`, and saves those fields
  plus `updated_at`. The details step and the status page's change form both call it. A
  normalised address equal to the stored one changes nothing.

### Merge rule: `attach_to_user` (`claims.py:205-246`)

- Replace the tie-break at `claims.py:233-237`: the incoming application loses only when the held
  one is submitted. Otherwise the held draft goes through `_discard_draft` and the incoming
  application is attached.
- The rule serves both callers: `claim_application` and `adopt_anonymous_applications_on_login`
  (`receivers.py:71-94`).
- When an attach discards anything, the applicant is told:
  - Claim page `confirm` state (`claim.html`): when the address's same-site owner already holds an
    application for the course, it says which survives. Held submitted, incoming draft: "You've
    already applied for <course>. This unfinished application will be discarded." Held draft:
    "This replaces the unfinished application for <course> already on your account." The view
    resolves this with `resolve_claim_owner` and one query for that owner's application.
  - Login adoption: when the receiver's attach keeps the held application over an incoming one, it
    adds a `messages.info` naming the course and saying the earlier application was kept.

### Claiming a draft: `claim_application` (`course_applications/views.py:606-678`)

- Remove the `not application.is_submitted` clause (`views.py:627`). A draft is claimed exactly as a
  submitted application is: user created or joined, `LegalConsent` written, `user.registered` fired,
  signed in, set-password when needed, then the status page, which redirects a draft to its resume
  page.
- `_render_claim` passes `is_submitted`. Draft wording on `claim.html`: `head_title` and h1
  "Continue your application for <course>"; the confirm text says following it verifies the
  address and returns them to their application. No mention of review.

### Claim email: `freedom_ls/course_applications/emails.py` and `templates/course_applications/email/`

- `send_application_claim_email` adds `is_submitted` (from `application_of(applicant)`) to the
  context. `application_claim_subject.txt` and `application_claim_message.{txt,html}` branch on it:
  - draft: subject "Continue your application for <course>"; body says the link takes them back to
    their application and confirms their email address; button "Continue your application"; no
    mention of review or of the application being received.
  - submitted: today's copy.
- The early send, the draft resend and the expired-link resend all use this one function.

### Applicant details step: `applicant_details` (`views.py:310-391`)

- On a course with a form, after `_start_application` and `allow_anonymous_form_progress`
  (`views.py:376-379`), when the normalised address is new or differs from `previous_email`, call
  `send_application_claim_email`. A changed address on an existing applicant goes through
  `update_applicant_email` first. A name-only change sends nothing.
- The send's result does not change the response: it always redirects to `_resume_url`.
- The response is identical whether or not the address has an account; the step still never reads
  `User` or `EmailAddress`.

### No email at submit: `application_check_answers` (`views.py:535-538`)

- Remove the `send_application_claim_email` call. The early email is the only claim email unless
  the applicant asks for another.

### Claim link notice

- New partial `course_applications/partials/claim_link_notice.html`, a `c-callout`, included by
  `form_page.html` and the check-your-answers template whenever the application is unverified and
  has an `anonymous_applicant`. It reads `claim_email_sent_at` from the database, so it survives a
  reload.
  - Sent: "We've emailed a link to <email> so you can come back to this application. Carry on
    here."
  - Not sent (failed or rate-limited): "We couldn't email <email> just now. You can carry on and
    send the link again."
  - Both: a POST form "Send the link again" to `course_applications:status`, and a "Wrong address?
    Change it" link to `course_applications:applicant_details`.
- `application_status` handles its POST before the draft redirect (`views.py:200-202`), so a draft
  can resend. The 404 guard for verified or applicant-less applications stays. After the toast it
  redirects to the status page, which sends a draft on to its resume page.

### Status page change of address

- New URL `status/<uuid:pk>/change-email/`, name `change_applicant_email`, view
  `change_applicant_email`, POST only, with ownership checked by
  `_owned_application` over `owned_applications(request)`.
  404 for a verified application, one with no applicant, or a draft (drafts change address on the
  details step).
- Form: a new `ApplicantEmailForm` (`forms.py`) with the email field and the honeypot, not
  `ApplicantDetailsForm`.
- Rate limiting reuses the `application_details` action and `email_rate_limit_key` on the new
  address. Extract the dry-run-then-consume block at `views.py:342-361` into one helper that both
  views call. A changed address then goes through `update_applicant_email` and
  `send_application_claim_email`.
- Valid: redirect to the status page. The toast depends only on whether the send went through,
  never on whether the address has an account (the existing "We've emailed a link to <email>." or
  "We couldn't email <email> just now. Try again in a little while."). Unchanged address: redirect with no
  send. Invalid email: re-render the status page with the form's errors, HTTP 422. Honeypot: refused
  the way the details step refuses it.
- `application_status.html` unverified branch: keep "sent to <email>" and the resend form; add the
  change-address form. The copy no longer says the email was sent on submission.

### Access backend: `freedom_ls/course_access/backends.py`

- `CourseAccessBackend` gains:
  - `get_access_for_request(self, *, request: HttpRequest, course: Course) -> CourseAccessDecision`,
    default `self.get_access(user=request.user, course=course)`;
  - `get_dashboard_contributions_for_request(self, *, request: HttpRequest) -> list[DashboardContribution]`,
    default `self.get_dashboard_contributions(user=request.user)`.
- `VisibilityEnforcingBackend` implements `get_access_for_request` by running its existing
  coming-soon, hidden and override checks, then calling `self._inner.get_access_for_request`. Share
  the checks with `get_access` (`:357-396`) rather than copying them. It forwards
  `get_dashboard_contributions_for_request` to the inner backend.

### Applications backend: `freedom_ls/course_applications/backends.py`

- `ApplicationCourseAccessBackend.get_dashboard_contributions_for_request`: signed in, the existing
  user path. Anonymous: the session's drafts, from `owned_applications(request)` filtered to
  `form_progress__isnull=False, form_progress__completed_time__isnull=True`, with
  `select_related("course", "form_progress")`, ordered `-created_at`. No drafts: `[]`. An empty
  session map runs no query. It renders through the existing
  `partials/dashboard_applications.html`, which shows no name, email or answers.
- `ApplicationCourseAccessBackend.get_access_for_request`: signed in, `get_access`. Anonymous: when
  `anonymous_applicant_for_course(request, course)` resolves an application, return the same
  "View my application" decision as the signed-in path (`backends.py:141-153`); build it in one
  helper used by both paths. Otherwise `get_access`. No session entry runs no extra query.

### Learner interface: `freedom_ls/learner_interface/`

- `dashboard` (`views.py:631-640`): call `get_dashboard_contributions_for_request(request=request)`
  for every visitor. Remove the `if inputs.is_auth` gate there and the `{% if
  user.is_authenticated %}` around the panel loop in `dashboard.html:31-35`.
- `course_detail` (`views.py:716`): call `get_access_for_request(request=request, course=course)`.
- Other `get_access` callers stay user-based. `learner_interface` gains no import of
  `course_applications`.

## Testing

- Details step on a form course: one claim email to the posted address, with draft wording; redirect
  to page 1. Reposting with only a name change sends nothing. Reposting with a new address sends
  once to it, bumps `claim_link_version`, and the earlier link renders "invalid".
- A failed or rate-limited send at the details step still redirects to page 1, and the notice says
  the email didn't go out.
- Check-your-answers POST sends no email. A form-less course still sends one on confirmation.
- The notice shows on every form page and on check-your-answers of an unverified draft, in its
  sent and not-sent states, and not on a signed-in applicant's pages.
- Resend from the notice on a draft: one email, toast, lands back on the form.
- Claim of a draft: user created or joined, consent written, webhook fired once, session key
  changes, ends on the draft's resume page. The origin session's map no longer resolves it.
- Merge: held submitted + incoming draft keeps the submitted one and the confirm page says so; held
  draft + incoming draft attaches the incoming one and discards the held draft and its sitting;
  held draft + incoming submitted attaches the incoming one. Login adoption follows the same rule
  and adds the message when the held application is kept.
- Tokens: a bare-pk token reads as version 0; a token whose version is behind is invalid in both the
  in-date and expired branches; an A→B→A change leaves the first link invalid.
- Status-page change of address: sends to the new address only, invalidates earlier links, gives
  identical responses for an address with and without an account, refuses a draft or verified
  application with 404, returns 422 for an invalid email, honours `application_details` limits.
  Staff admin shows the new address with the unverified flag.
- Dashboard: an anonymous session with two drafts gets both rows, newest first, with no name or
  email in the HTML; a submitted application, a claimed one, an erased one and another session's
  are absent; an anonymous visitor with no session map gets no panel and no extra query.
- Course page: an anonymous session with a draft or submitted application for the course gets
  "View my application" to the status page; without one, "Apply now", with no extra query.
- `VisibilityEnforcingBackend` forwards both new methods and applies its visibility checks in
  `get_access_for_request`. Base and `FreeOnlyCourseAccessBackend` defaults delegate to the
  user-based methods.
- Rewrite the tests that encode the old behaviour: `test_views.py::test_claim_of_a_draft_application_renders_the_invalid_page`,
  `test_emails.py::test_check_answers_submission_sends_one_email` and the send-failure tests that
  go through submit, `test_claims.py::test_a_claim_over_a_draft_on_the_account_replaces_the_draft`,
  the token tests at `test_claims.py:46-63`, `test_receivers.py::test_signing_in_drops_a_draft_for_a_course_the_account_already_applied_to`,
  and the anonymous dashboard tests in `learner_interface/tests/views/test_course_listing.py`
  (1647-1705).
- Playwright (`course_applications/tests/playwright/test_application_form_flow.py`): anonymous
  details → notice on page 1 → follow the emailed link in a fresh browser context → signed in on
  the draft. Anonymous draft shows on the dashboard and its Continue resumes it.

## Documentation and downstream

- `docs/product/learner-experience.md`: the email goes out after the details step, the notice,
  claiming a draft, changing the address, drafts on the anonymous dashboard and course page.
- `docs/product/authentication.md`: a claim can now create an account for an applicant who hasn't
  submitted.
- `docs/product/webhooks.md`: `user.registered` can fire before an application is submitted.
- `docs/product/admin-interface.md`: "Email verified" no longer implies submitted; the address on an
  unverified application can change after submission.
- `docs/product/configuration-and-extension.md`: the two request-aware backend methods and their
  defaults.
- Upgrade notes: a downstream backend that subclasses `ApplicationCourseAccessBackend` and overrides
  `get_access` or `get_dashboard_contributions` must also override the request-aware method to keep
  the anonymous panel and CTA. Claim links sent before the upgrade keep working until the address
  changes. Overridden claim email templates need the draft wording.
- `qa_helpers` commands that build applicants: check they work with `claim_link_version`'s default.

## Open questions

- A plain resend keeps earlier links valid. Bump the version on resend too if only the newest link
  should work.
- No audit of address changes: staff see only the current address.
- No extra per-application limit on address changes; the per-address `application_details` and
  `application_claim_email` limits apply.

## Success criteria

- An anonymous applicant on a form course receives exactly one claim email, sent from the details
  step, and none at submit.
- That link, opened in another browser before submitting, signs them in on their draft.
- After an address change, every earlier link renders the invalid page and the new address gets one
  email.
- An anonymous session's drafts appear on the dashboard with no name or email in the page, and the
  course page says "View my application".
- No attach silently deletes an application the applicant was told nothing about.
- `learner_interface` imports nothing from `course_applications`.
- `uv run manage.py makemigrations --check` is clean and `uv run pytest` passes.
