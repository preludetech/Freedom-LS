# Frontend QA: error pages

Eight pages, all of which only exist because something went wrong, and six of which Django will not
show you at all under `DEBUG=True`. Read §0 in full before starting — it is not boilerplate, and
skipping it produces a run where every test "passes" against Django's debug traceback page.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

---

## §0 Setup

### 0.1 Why this run needs two servers

`DEBUG=True` never reaches `handler404`/`handler403`/`handler400`/`handler500` — Django serves its
own yellow traceback and "technical" debug pages instead. `403_csrf.html` and `429.html` do render
under `DEBUG=True`, but the rest do not, so the bulk of this plan runs against `DEBUG=False`.

Two things stop working when you flip that switch, which is why part of the run happens before it:

- **The branch badge disappears.** `freedom_ls.base.context_processors.debug_branch_info` returns an
  empty dict when `settings.DEBUG` is false, so `#debug-branch-badge` is absent by design. The
  standard "confirm the server is on this branch" check has to happen on the plain dev server.
- **The axes lockout page is unaffected either way.** django-axes renders
  `accounts/lockout.html` through an ordinary `render(..., status=429)`, not through an error
  handler, and its counters live in Postgres rather than the cache. It is also independent of
  `ACCOUNT_RATE_LIMITS`, which dev sets to `False`. So it is the one page that is *easier* to test on
  the plain dev server.

So: **Server A** is the ordinary dev server (§1). **Server B** replaces it on the same port with
`DEBUG=False` (§2 onward). The session cookie and the database are unchanged across the swap, so a
login made against Server A survives into Server B.

### 0.2 Seed data

The `demodev@email.com` account from `.claude/fls-dev/config.md` is all this run needs. No courses,
cohorts or progress are involved — every page under test is chrome, not content. If that account is
missing, create it with the standard dev seed before starting.

### 0.3 Server A

1. `.claude/ds/scripts/find_available_port.sh` — note the number, use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the `error-pages` branch.
   If it names another branch, another server has the port — go back to step 1.
4. Sign in as `demodev@email.com`.

### 0.4 The two throwaway files

`503.html` is not reachable through any FLS route, and neither is a deliberate 403 or 400. Both files
below are scaffolding for this run only and are deleted in §7. Neither is committed.

`config/settings_qa_check.py`:

```python
# Throwaway QA scaffolding. Delete after this run — see the QA plan's cleanup step.
from .settings_dev import *  # noqa: F401,F403

DEBUG = False

# 127.0.0.1 only, on purpose. Reaching the same server on http://localhost:<PORT>/
# then raises DisallowedHost, which is a real 400 through the real middleware.
ALLOWED_HOSTS = ["127.0.0.1"]

# WhiteNoise stops using the staticfiles finders once DEBUG is False, and this
# project only defines STATIC_ROOT in production. Without these two lines every
# page under test renders with no stylesheet and the whole run is meaningless.
WHITENOISE_AUTOREFRESH = True
WHITENOISE_USE_FINDERS = True

# settings_dev sets ACCOUNT_RATE_LIMITS = False, which zeroes every allauth
# scope, not just the two FLS overrides. Restore them. The scopes that need many
# repeated submissions to trip by hand are lowered — the rendered page is the
# same at any limit value, and the point here is to reach the page.
ACCOUNT_RATE_LIMITS = {
    "signup": "5/m/ip",
    "login": "3/m/ip",
    "login_failed": "10/m/ip,5/5m/key",
    "reset_password": "2/m/ip",  # pragma: allowlist secret
    "reset_password_from_key": "2/m/ip",  # pragma: allowlist secret
    "change_password": "2/m/user",  # pragma: allowlist secret
    "manage_email": "2/m/user",
    "reauthenticate": "2/m/user",
}

ROOT_URLCONF = "config.urls_qa_check"
```

`config/urls_qa_check.py`:

```python
# Throwaway QA scaffolding. Delete after this run — see the QA plan's cleanup step.
from django.core.exceptions import BadRequest, PermissionDenied
from django.http import HttpRequest, HttpResponse
from django.shortcuts import render
from django.urls import path

from config.urls import urlpatterns as real_urlpatterns


def qa_403(request: HttpRequest) -> HttpResponse:
    raise PermissionDenied


def qa_400(request: HttpRequest) -> HttpResponse:
    raise BadRequest


def qa_500(request: HttpRequest) -> HttpResponse:
    _ = 1 / 0
    return HttpResponse()


def qa_503(request: HttpRequest) -> HttpResponse:
    return render(request, "503.html", status=503)


urlpatterns = [
    path("qa-error/403/", qa_403),
    path("qa-error/400/", qa_400),
    path("qa-error/500/", qa_500),
    path("qa-error/503/", qa_503),
    *real_urlpatterns,
]
```

### 0.5 Clearing counters mid-run

- **allauth rate limits** live in dev's per-process `LocMemCache`. There is no reset command. The
  only way to clear them is to restart the server, which is why §4's scopes are ordered so each is
  tripped once.
- **axes lockouts** live in Postgres. `uv run python manage.py axes_reset` clears them and prints how
  many rows it removed.

## §1 The lockout page, on Server A

Run this before flipping to `DEBUG=False`, and use a throwaway address so the `demodev` account is
never the one locked.

**1.1 — the lockout page appears.** Sign out. On `http://127.0.0.1:<PORT>/accounts/login/`, submit
`qa-lockout@example.com` with a wrong password five times.

Expect: the fifth submission returns the restyled lockout page — the site header, a circular status
mark, a small "Error 429" label, the heading "Too many sign-in attempts", the body copy, a "Back to
sign in" button and a "Reset it now" password-reset link. Confirm the network panel shows status
**429**, not 200. Confirm the page shows **no** countdown, no "try again in N minutes", and no
attempts-remaining figure.

**1.2 — both links still work.** Click "Back to sign in": the login form loads. Go back, click
"Reset it now": the password-reset form loads.

**1.3 — the lockout is real, and scoped.** Reload the lockout URL: still 429. Now try
`demodev@email.com` with the *correct* password from the same browser: it signs in normally. That
proves the lockout keyed on the pair, not on the address.

**1.4 — clean up.** `uv run python manage.py axes_reset`. Sign back in as `demodev@email.com`.

## §3 The four Django-served pages

**3.1 — 404, signed in.** Visit `http://127.0.0.1:<PORT>/does-not-exist-abc123/`.

Expect: the site header with the user menu, then the panel — a neutral-grey circular mark, "Error
404", the heading "We cannot find that page", the body copy, a "Go to your dashboard" primary button
and a "Browse courses" secondary button. Status **404** in the network panel.

Then check what is *not* there: the string `does-not-exist-abc123` must not appear anywhere in the
rendered page. Django hands the requested path to this template and we deliberately never render it.
Search the page text for it.

**3.2 — 404, signed out.** Sign out and visit the same URL. Same panel, but the header now shows the
signed-out prompt instead of the user menu. Both buttons still render and both still work — the
dashboard is public. Sign back in.

**3.3 — the 404's buttons go somewhere.** Click "Go to your dashboard" — the dashboard loads. Go
back, click "Browse courses" — the course catalogue loads.

**3.4 — 403.** Visit `http://127.0.0.1:<PORT>/qa-error/403/`.

Expect: a warning-tinted mark, "Error 403", the heading "You do not have access to this page", the
body copy naming "an administrator" generically, a "Browse courses" primary button and a "Sign in as
a different account" secondary button. Status **403**.

Check the copy does not name a specific administrator, a specific course, or the resource that was
refused.

**3.5 — the 403's second action actually works while signed in.** This is the branch most likely to
be quietly broken: allauth redirects an already-authenticated visitor away from the login form. Still
signed in as `demodev@email.com`, click "Sign in as a different account".

Expect: a sign-out confirmation page, and after confirming, the **login form**. If you land back on
your own dashboard still signed in, that is a bug — the link is pointing straight at
`account_login` instead of through logout.

**3.6 — the 403's second action while signed out.** Sign out, revisit `/qa-error/403/`, click the
same button. Expect the login form directly, with no sign-out step. Sign back in.

**3.7 — 400 from a raised `BadRequest`.** Visit `http://127.0.0.1:<PORT>/qa-error/400/`.

Expect: "Error 400", the heading "We could not handle that request", the body copy, a single "Go to
your dashboard" button, and status **400**. Confirm there is **no** retry affordance — retrying a
malformed request fails identically.

**3.8 — 400 from a real `DisallowedHost`.** Visit `http://localhost:<PORT>/` — the same server, a
host name not in `ALLOWED_HOSTS`.

Expect the same 400 page, produced by the real middleware rather than a test view. It will be
unstyled, because the stylesheet request is rejected on the same grounds. That is correct behaviour
and the page must still read top to bottom in a sensible order: status label, heading, body, link.
Screenshot it — this doubles as the "reads with no stylesheet" check.

**3.9 — 403 CSRF.** Sign out and open `http://127.0.0.1:<PORT>/accounts/login/`. Clear the CSRF
cookie without reloading:

```js
document.cookie = "csrftoken=; Max-Age=0; path=/";
```

Now submit the login form.

Expect: "Error 403", the heading "The form was not sent", body copy explaining the session expired
and that nothing was saved, and a "Sign in again" button. Status **403**.

Check that Django's built-in fallback is gone: the phrases "CSRF verification failed",
"Request aborted", "Help" and "More information is available with DEBUG=True" must not appear, and
the page must carry the site header and theme rather than Django's bare stylesheet-less markup.

**3.10 — 500.** Sign back in, then visit `http://127.0.0.1:<PORT>/qa-error/500/`.

Expect a visibly plainer page than the others: **no site header, no logo, no user menu**, just the
panel on the page background, styled. An error-tinted mark, "Error 500", the heading "Sorry, there is
a problem with this page", two paragraphs — the second saying work may not have been saved — a "Try
again" primary action and a "Go to your dashboard" secondary. Status **500**.

Check what is absent: no reference code, no "the team has been paged", no support link, no status
link, no claim about which topic or course your progress reached.

**3.11 — the 500's "Try again" is honest.** Click it. It reloads the same failing URL and 500s again.
That is correct: the page reloads rather than pretending to recover. Confirm the second response is
also 500 and not a silent 200.

**3.12 — the 500's dashboard link works.** Click "Go to your dashboard": the real dashboard loads,
signed in, with the header back.

**3.13 — 503.** Visit `http://127.0.0.1:<PORT>/qa-error/503/`.

Expect the same standalone treatment as the 500 — no header, no navigation — with an info-tinted
mark, "Error 503", the heading "Sorry, the service is unavailable", one line of body copy, and a
single "Try again" action. Status **503**.

Check that nothing on the page implies the service is up: no header, no user menu, no dashboard link,
no maintenance window, no "back in N minutes", no status-page link.

## §4 Every rate limit

`research_rate_limit_surfaces.md` lists thirteen scopes. Seven of them return a hard 429 through the
template under test; the other six either render something else or are unreachable. Work through all
thirteen and record each.

Trip each scope **once**. Dev's cache is per-process with no reset command, so a scope you exhaust
stays exhausted until Server B is restarted.

### 4.1 The seven hard-429 scopes

For every one of these, expect the same page: the site header, a warning-tinted mark, "Error 429",
the heading "You have made too many attempts", the body copy, and a single "Try again" action, at
status **429**. In every case confirm allauth's bare fallback — a stylesheet-less page reading
"429 Too Many Requests" — is *not* what you got.

**allauth ignores GET.** `consume()` returns early on any `GET` unless the view asked for
`limit_get=True`, and none of these do. Every recipe below is therefore a form **submission**, not a
page visit. Repeatedly reloading a URL will never trip any of them.

**Order matters**, because two of these lock you out of the steps that follow. Work down the table in
the order given: the signed-in scopes first while you can still stay signed in, then the reset
scopes, then `signup`, then `login` last of all.

| Order | # | Scope | How to trip it | Shell |
| --- | --- | --- | --- | --- |
| 1st | 6 | `change_password` | Signed in, submit `/accounts/password/change/` three times. Getting the current password wrong is fine — a rejected submission still counts. | **signed in** |
| 2nd | 7 | `manage_email` | Signed in, submit "Add email" on `/accounts/email/` three times. | **signed in** |
| 3rd | 8 | `reauthenticate` | Signed in, submit `/accounts/reauthenticate/` three times with a wrong password. | **signed in** |
| 4th | 5 | `reset_password_from_key` | Before tripping row 4: request one password reset for `demodev@email.com`, collect the link from Mailpit at `http://localhost:8025`, open it, then submit the set-password form three times with two mismatched passwords so each submission is rejected and re-renders. | signed out |
| 5th | 4 | `reset_password` | Sign out. Submit `/accounts/password/reset/` three times. | signed out |
| 6th | 1 | `signup` | Sign out. Submit `/accounts/signup/` six times. | signed out |
| 7th | 2 | `login` | Sign out. Submit `/accounts/login/` four times. | signed out |

Rows 6, 7 and 8 are the ones this feature exists for as much as the signed-out ones — a learner deep
in account settings hits exactly the same bare fallback today. For each of the three, confirm the
page renders **inside the signed-in shell**: the header shows the user menu, not the sign-in prompt.

Once row 2 is tripped, nobody can sign in from this address until Server B is restarted. If you still
need a signed-in session after that, restart Server B — which also clears every allauth counter, so
do not restart before you have finished the whole table.

### 4.2 The six that do not render this page

| --- | --- | --- | --- |
| 3 | `login_failed` | **Not** a 429. Eleven failed logins from one address, or six against one email inside five minutes, re-renders the ordinary login page at status 200 with the inline message "Too many failed login attempts. Try again later." | Confirm you get the login form with an inline error, **not** the 429 page and **not** a 429 status. Wiring this scope to the error page would be a regression. |
| 9 | `confirm_email` | Silent by design. Repeatedly triggering a verification-email resend inside three minutes changes nothing on screen. | Confirm no error page appears and no toast claims a failure. |

### 4.3 What must never appear on any 429

On every 429 page you reached, confirm: no countdown, no ticking timer, no "unlocks in N minutes", no
"limit N requests per minute", no attempts-remaining figure, and no automatic retry. FLS cannot read
a real cooldown back out of allauth's cache keys, so any such number would be invented.

## §5 Accessibility and resilience

Run these against `/does-not-exist-abc123/` (a shell page) and `/qa-error/500/` (a standalone page).

**5.1 — the tab title.** Each of the eight pages has its own `<title>`, and no two are the same.
Collect them all and compare.

**5.2 — one heading in the content.** The page's own `<h1>` is the error heading. Shell pages also
carry the site-title `<h1>` in the header, which every FLS page has — that is expected and is not a
finding. The standalone 500 and 503 must have exactly one `<h1>` each.

**5.3 — the mark is silent to assistive technology.** In the accessibility snapshot, the circular
status icon must not appear as an image or announce a label. The severity has to be readable from the
"Error NNN" label and the heading alone.

**5.4 — colour is not the only signal.** Squint at, or desaturate, the 500 and the 404 side by side.
The status label and heading text alone must tell you which is which.

**5.5 — no stylesheet.** On the 500 page, disable the stylesheet:

```js
document.querySelectorAll('link[rel="stylesheet"]').forEach(el => el.remove());
```

The page must still read top to bottom in a sensible order — status label, heading, body, actions —
with every link and button still visible and clickable. Nothing may be hidden. §3.8 already gave you
one real-world instance of this; this is the deliberate version.

**5.6 — `noindex`.** Every one of the eight pages must carry
`<meta name="robots" content="noindex" />`. Check the page source on at least the 404, the 500 and
the 429.

**5.7 — narrow viewport.** At mobile width, the panel must not overflow horizontally, the heading
must wrap rather than clip, and the two action buttons must stack rather than crush. Check the 404
(two buttons) and the 500 (two buttons, no header).

## §6 Side-effects on things that already worked

**6.1 — ordinary pages are unchanged.** Load the dashboard, the course catalogue, a course detail
page and `/accounts/password/change/`. Nothing about the header, the toasts or the layout should have
shifted. The shared component is new, but `accounts/lockout.html` changed the layout it extends, so
confirm the account pages around it still look right.

**6.2 — the lockout page and the 429 page match.** Put the §1 screenshot next to a §4.1 screenshot.
Same mark, same label treatment, same heading scale, same button styling. They are the two faces of
the same status code and should be indistinguishable apart from their words.

**6.3 — an error inside the course player still escapes it.** Open a course and start moving through
it, so the boosted `#interface-main` shell is in play. Then edit the address bar to a bad course-item
index under the same course and navigate.

Expect a full-page reload onto the real 404 page, complete with the site header — not a silently
stale player. This is existing behaviour from `interface-swap-fallback.js`, but these pages are the
thing it now reloads onto, so confirm it lands correctly.

**6.4 — an htmx error outside the player is still swallowed.** This is a known gap, not a bug to
file: an htmx request that 404s outside `#interface-main` changes nothing on screen and the visitor
sees no error page at all. If you happen to observe it, record it as the known gap the idea document
names, not as a regression.

**6.5 — the toast system is untouched.** Trigger any ordinary success or error toast (saving a
profile change is enough). Toasts must look exactly as they did before.

## What counts as a failure

- Any page returning 200 when it should return its real status code.
- Any page showing Django's or allauth's stock fallback instead of the branded panel.
- Any page that is a dead end.
- A 500 or 503 that renders the site header, or whose stylesheet fails to load.
- A retry offered on 404, 403 or 400.
- A countdown, a cooldown, a limit figure, a reference code, a support link or a status link on any
  page.
- The requested path, an exception message, a stack trace or a framework version appearing on any
  page.
- The 403's "Sign in as a different account" bouncing a signed-in visitor back to their dashboard.
- A 429 rendered outside the signed-in shell when it was reached from account settings.
