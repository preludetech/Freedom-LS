# Frontend QA: messaging policy configuration in the admin

The only screens this feature adds are Django admin pages: a "Messaging policy" section with six
configuration models (site, organisation, cohort, learner, learner course registration, cohort
course registration). Each row holds tri-state flags (Inherit / Open / Closed), and the site row
also chooses which educator roles are offered to learners. This run creates every row kind as a
superuser, checks the offered-roles field's three stored meanings (settings default, nobody, a
list), and tries the ways a row could be saved wrongly: a duplicate for the same owner, a role the
site does not know, and both "default" and specific roles at once.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

---

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh` — note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `user-communication-3-messaging-policy` branch. If it names another branch, another server holds
   the port; go back to step 1.

### 0.2 Seed data

Every item below must exist before §1. Missing data is created through the `fls-dev:qa-data-helper`
agent, never by hand.

1. **Demo content loaded.** `uv run python manage.py content_save demo_content DemoDev`. Any demo
   course will do for the registrations below; call the one used *the course*.
2. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
3. **An organisation** named `QA Messaging Org` on the DemoDev site, with **one cohort** named
   `QA Messaging Cohort`.
4. **A learner** `qa_messaging_learner@email.com` with an active `Learner` row in
   `QA Messaging Org`, a `CohortMembership` in `QA Messaging Cohort`, and an active
   `LearnerCourseRegistration` for the course.
5. **A cohort course registration**: `QA Messaging Cohort` registered for the course.
6. **No messaging configuration rows at all** for the DemoDev site, the organisation, the cohort,
   the learner or the registrations. If any exist from an earlier run, remove them first.

Sign in as `demodev@email.com` and open `http://127.0.0.1:<PORT>/admin/`.

## §2 Site messaging config

### 2.1 Add with defaults

1. Open `/admin/freedom_ls_messaging_policy/sitemessagingconfig/add/`.
2. Expect three dropdowns, "Learner to educator", "Learner to cohort peer", "Learner to course
   peer", each preselected to "Inherit", each with the help text `"Inherit" uses the next level up.`
3. Expect no "Site" field anywhere on the form.
4. Expect an "Offered educator roles" group of checkboxes whose first option is the settings
   default ("Use the settings default" or similar wording) and which is **ticked**, followed by one
   checkbox per role that can see learners: Cohort admin, Cohort viewer, Organisation admin, Site
   admin. Roles that cannot see learners (Learner, Observer, System Administrator) are not listed.
5. Save with nothing changed. Expect the changelist to show one row whose first column reads
   "Messaging config for DemoDev" (the site's name) and whose flag columns all show `Inherit`.

### 2.2 A second row for the site is refused

1. Open the add page again and save with defaults.
2. Expect to stay on the form with a validation error saying a site messaging config already
   exists for this site (field-level or form-level), not a server error page. The changelist still
   holds exactly one row.

### 2.3 Offered roles: a list

1. Open the existing row's change page. Expect the settings-default option ticked and every role
   unticked.
2. Untick the settings default, tick "Cohort admin" and "Cohort viewer", set "Learner to educator"
   to "Open", save.
3. Reopen the row. Expect "Cohort admin" and "Cohort viewer" ticked, the default option unticked,
   and "Learner to educator" showing "Open".

### 2.4 Offered roles: nobody

1. Untick every checkbox (no default, no roles), save.
2. Reopen. Expect every checkbox unticked, including the default option. This is the "offer
   nobody" state and must not snap back to the default.

### 2.5 Default plus a role is refused

1. Tick the settings default and "Site admin", save.
2. Expect a validation error on "Offered educator roles" saying to choose either the default or
   specific roles. Nothing is saved: reopening the row shows the §2.4 state.

### 2.6 An unknown role key is refused (adversarial)

1. On the change page, use the browser's JavaScript to add a checkbox to the offered-roles group
   with `name` equal to the existing checkboxes' name and `value="made_up_role"`, tick it, and
   submit the form.
2. Expect a validation error on "Offered educator roles" ("Select a valid choice" or the model's
   own unknown-key message). The row is unchanged.

### 2.7 Back to the default

1. Tick only the settings default, save, reopen. Expect the default option ticked and no roles
   ticked.

## §3 Organisation messaging config

1. Open `/admin/freedom_ls_messaging_policy/organisationmessagingconfig/add/`.
2. Expect an "Organisation" autocomplete and the three flag dropdowns. Type `QA Mess` in the
   autocomplete and pick `QA Messaging Org`.
3. Set "Learner to cohort peer" to "Closed", save. Expect the changelist row to name the
   organisation and show `Inherit`, `Closed`, `Inherit`.
4. Add a second row for the same organisation. Expect a validation error that a config for this
   organisation already exists; one row remains.
5. Open `/admin/freedom_ls_organisations/organisation/` and the organisation's change page. Expect
   no messaging inline or messaging fields there: the configuration is edited only on its own
   pages.

---

## §4 Cohort messaging config

1. Open `/admin/freedom_ls_messaging_policy/cohortmessagingconfig/add/`. Expect a "Cohort"
   autocomplete; pick `QA Messaging Cohort`.
2. Set "Learner to cohort peer" to "Open", save. Expect the row in the changelist with the cohort's
   name and `Inherit`, `Open`, `Inherit`.
3. Use the changelist filter on "Learner to cohort peer" = Open. Expect the row; filter on Closed,
   expect none.
4. Delete this cohort config from its change page. Expect the changelist empty afterwards and the
   cohort itself still present under Learner management.

## §5 Learner messaging config

1. Open `/admin/freedom_ls_messaging_policy/learnermessagingconfig/add/`. Expect a "Learner"
   autocomplete; type `qa_messaging` and pick the learner (shown as `<email> - QA Messaging Org`).
2. Set all three flags to "Closed", save. Expect the changelist row naming the learner with three
   `Closed` values.
3. Add a second row for the same learner. Expect the duplicate validation error.

## §6 Registration messaging configs

### 6.1 Learner course registration

1. Open `/admin/freedom_ls_messaging_policy/learnercourseregistrationmessagingconfig/add/`.
2. Expect a "Registration" autocomplete and **only one** flag, "Learner to course peer". No
   "Learner to educator" or "Learner to cohort peer" field.
3. Pick the learner's registration for the course (search by the learner's email), set the flag to
   "Open", save. Expect the changelist row naming the registration with `Open`.

### 6.2 Cohort course registration

1. Open `/admin/freedom_ls_messaging_policy/cohortcourseregistrationmessagingconfig/add/`.
2. Expect a "Registration" autocomplete and only the "Learner to course peer" flag.
3. Pick `QA Messaging Cohort`'s registration for the course, leave "Inherit", save. Expect the row
   with `Inherit`.

## §7 Cascade on owner deletion

1. Under Learner management, delete the `LearnerCourseRegistration` used in §6.1 from its own
   admin page (the delete confirmation lists the messaging config as a related object).
2. Open `/admin/freedom_ls_messaging_policy/learnercourseregistrationmessagingconfig/`. Expect the
   row from §6.1 gone.
3. Ask the `fls-dev:qa-data-helper` agent to recreate that registration so later runs start from
   §0.2 again.
