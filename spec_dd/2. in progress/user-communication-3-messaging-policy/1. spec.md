# Spec: Messaging policy

Spec 3 of 8 in the User communication effort (`spec_dd/1. next/roadmap.md`). Source:
`idea.md` in this directory. The research files beside it hold the reasoning and worked examples.

## Purpose

Every messaging surface that specs 4 to 6 build has to answer one question: may this user message
that user? This spec answers it in one place. A swappable `MessagingPolicy` answers it, using
layered configuration that a site admin edits in the Django admin. Beside it sit the relationship
queries the policy needs: a learner's educators, a learner's peers, and an educator's colleagues.
Nothing here is learner-facing or educator-facing.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| educator of a learner | coined | a user who reaches an active `Learner` through an active role assignment whose role is in `roles_granting(VIEW_LEARNER, site)`, gated the way `learners_visible_to` gates it. This is the inverse of `learners_visible_to`, minus its superuser branch |
| offered educator | coined | an educator of a learner whose role toward that learner is on the offered-roles list. Only offered educators can receive a learner's first message |
| peer | coined | another user's active `Learner` row in the same organisation that shares a `CohortMembership` cohort, or a course through an active `LearnerCourseRegistration` or `CohortCourseRegistration` |
| colleague | coined | a user who holds a `VIEW_LEARNER`-granting role in the same organisation as another user, on the organisation or on one of its cohorts. A `site_admin` is a colleague of every such user on the site |
| candidate | coined | one concrete link between a sender and a recipient (a shared cohort, a shared course through one of the sender's registrations, or an offered educator's role link). The configuration chain is resolved once per candidate |

## Scope

In:

- The `MessagingPolicy` contract in `comms`: three questions, a typed decision, refusal reason
  codes, the `MESSAGING_POLICY` setting and its cached loader.
- A new app, `freedom_ls/messaging_policy`, that holds the default `LayeredMessagingPolicy`, the
  configuration models at each level, their admin, and the settings defaults.
- `educators_of`, `peers_of` and `colleagues_of` in `freedom_ls/learner_management/queries.py`.
- System checks, tests, docs, glossary and the app-dependency map.

Out:

- Any screen beyond the Django admin, including a "why" screen and an educator-interface editor
  (specs 4 and 5 build the inbox, composer and quick view). Spec 4 keeps a conversation readable
  after replies close and words each refusal reason.
- Report and block (spec 6). The policy leaves room for block to be checked after it.
- A recipient-side veto or opt-out.
- Named presets, the platform-wide per-user level of service, and any subscriptions feature.
- Safeguarding modes for sites serving minors.
- Group conversations, announcements, forums, inline feedback.
- Notification configuration (specs 1 and 2).

## Decisions

1. **Educators can always start a conversation with any learner they are an educator of.** There
   is no flag for it. Under the any-open rule a close on one level could not shut a pair that
   another role link leaves open, so the flag could not mean what an admin expects. The way to
   stop an educator is to remove the role.
2. **Superusers get no messaging rights from `is_superuser`.** A superuser counts as an educator
   or colleague only through a role row like anyone else. `educators_of` therefore leaves out the
   superuser branch of `learners_visible_to`, and the agreement test carves superusers out
   explicitly.
3. **A `site_admin` is a colleague of every educator on the site.**
4. **The contract lives in `comms`. The default policy and every configuration model live in the
   new `messaging_policy` app**, which depends on `comms`, `learner_management`, `organisations`
   and `role_based_permissions`. This copies `course_access` and `course_applications`. `comms`
   gains no runtime edge.
5. **Each level has its own config model, OneToOne to the model that owns it.** The flags are
   shared through one abstract Django model, `MessagingFlags`, which the user explicitly approved.
   A reverse OneToOne is a LEFT JOIN, so the chain resolves inside a single queryset.
6. **A registration-level config carries only the shared-course flag.** No role is scoped to a
   course, so a learner-to-educator or cohort-peer flag on a registration would have no candidate
   to apply to.
7. **The offered-roles list lives in a Django setting and can be overridden on the site row.**
   `None` on the site row inherits the setting. `[]` offers nobody.
8. **Replies are allowed when either direction's start is allowed now.** A learner can therefore
   answer an educator who wrote first, and closing configuration or ending a relationship stops
   replies on both sides.
9. **Resolution pools the sender's active `Learner` rows on the site.** Each candidate resolves
   through the chain of its own organisation. The default policy ignores the conversation passed
   to `can_reply`, so it does not matter whether spec 4 keeps one conversation per pair or one per
   organisation.
10. **`MessagingDecision.__bool__` raises `TypeError`.** An object that is always truthy would make
    `if policy.can_start(...)` allow everything. Raising forces callers to write `.allowed`.
11. **`MESSAGING_POLICY` defaults to the layered policy's dotted path**, so FLS works without any
    configuration. A string default creates no import edge.
12. **No inlines on owner admins.** An inline in the `learner_management` or `organisations` admin
    would import `messaging_policy` in the wrong direction. Each config model gets its own admin.

## Requirements

### The contract (`freedom_ls/comms`)

New module `freedom_ls/comms/messaging_policy.py`:

```python
class MessagingRefusal(StrEnum):
    SAME_USER = "same_user"
    INACTIVE_USER = "inactive_user"                       # sender or recipient User.is_active is False
    NO_RELATIONSHIP = "no_relationship"                   # no candidate, colleague or educator link on this site
    CLOSED_BY_CONFIGURATION = "closed_by_configuration"   # candidates exist, none resolves open

@dataclass(frozen=True, slots=True)
class MessagingDecision:
    allowed: bool
    reason: MessagingRefusal | None = None
    # __post_init__: allowed == (reason is None), else ValueError
    # __bool__: raises TypeError("use .allowed")
    # classmethods allow() and refuse(reason)

class MessagingPolicy:
    def can_start(self, *, sender: User, recipient: User, site: Site) -> MessagingDecision: ...
    def can_reply(self, *, sender: User, recipient: User, site: Site, conversation: Model) -> MessagingDecision: ...
    def recipients_for(self, *, sender: User, site: Site) -> QuerySet[User]: ...
```

- `MessagingPolicy` is a plain class whose methods raise `NotImplementedError`. Do not make it an
  `abc.ABC`. This follows `CourseAccessBackend` in `freedom_ls/course_access/backends.py`.
- `conversation` is typed `Model` because spec 4 creates `Conversation`. The default policy does
  not read it.
- A policy instance is stateless and never caches an answer.
- Spec 6 adds its block reason to `MessagingRefusal`. This spec defines no block code.

`freedom_ls/comms/config.py`: declare `MESSAGING_POLICY: str`, with
`Setting(default="freedom_ls.messaging_policy.policy.LayeredMessagingPolicy")`.

New `freedom_ls/comms/messaging_loader.py`: `get_messaging_policy() -> MessagingPolicy`, decorated
with `@functools.cache`, that runs `import_string(config.MESSAGING_POLICY)()`. This is the same
pattern as `freedom_ls/course_access/loader.py`. Add an autouse fixture that calls
`cache_clear()` before and after each test, beside `_clear_course_access_backend_cache` in
`freedom_ls/conftest.py`.

`freedom_ls/comms/checks.py`, continuing from `E002`:

- `E003`: `MESSAGING_POLICY` does not import, or does not name a subclass of `MessagingPolicy`.
- `E004`: `MESSAGING_POLICY` starts with `freedom_ls.` and no installed app provides it. Copy
  `E003` in `freedom_ls/course_access/checks.py`.

`comms` keeps its runtime imports limited to `accounts`, `base` and `site_aware_models`.

### Relationship queries (`freedom_ls/learner_management/queries.py`)

All three take the site explicitly, filter every site-aware table with `site=`, never call
`_current_site()`, and return the same result inside and outside a request. They reuse the
helpers in `freedom_ls/learner_management/capabilities.py` (`roles_granting`,
`_active_role_assignments`, `_member_organisations` and the gate logic). They never read guardian
rows and never hard-code a role key. Each returns a queryset that can be filtered further, built
from `pk__in` or `Exists` subqueries, never from `.union()`.

- `educators_of(learner: Learner) -> QuerySet[User]`. Returns active users who are educators of
  that learner, and nothing if `learner.is_active` is False. There are three sources: a
  `SiteRoleAssignment` (ungated); an `ObjectRoleAssignment` on `learner.organisation`, gated on an
  active `OrganisationMember` for it; and an `ObjectRoleAssignment` on any cohort the learner is a
  member of, gated on an active `OrganisationMember` of the cohort's organisation. Like
  `learners_visible_to`, it does not check the learner's `User.is_active` and does not exclude
  the learner's own user.
- `peers_of(learner: Learner) -> QuerySet[Learner]`. Returns other users' active `Learner` rows in
  `learner.organisation` that share a cohort with the learner, or share a course with an active
  registration on both sides (either path, each side independently). A learner who is not active
  has no peers. The membership and registration conditions for a given path go in one `filter()`
  call, as the comment on `is_registered_for_course_expression` explains.
- `colleagues_of(user: User, site: Site) -> QuerySet[User]`. Returns the active users, other than
  `user`, who share an organisation-scoped or cohort-scoped `VIEW_LEARNER` role with them in the
  same organisation (gated on `OrganisationMember`). If either user holds `site_admin` on the
  site, they are colleagues of every holder of such a role on that site, other site admins
  included.

The default policy's per-candidate expressions must use the same link predicates as these
functions, so that the relationship query and the policy cannot drift. One way to do this is to
factor the predicates into helpers that both of them call.

### The new app (`freedom_ls/messaging_policy`)

Label `freedom_ls_messaging_policy`. Add it to `INSTALLED_APPS` in `config/settings_base.py`
after `freedom_ls.comms`.

**`config.py`** (`AppSettings`):

- `MESSAGING_DEFAULT_FLAGS: dict[str, str]`. The default is
  `{"learner_to_educator": "closed", "learner_to_cohort_peer": "closed", "learner_to_course_peer": "closed"}`.
  Every value is `open` or `closed`.
- `MESSAGING_OFFERED_EDUCATOR_ROLES: list[str]`, with the default `["cohort_admin"]`. An install
  without cohorts adds `organisation_admin`.

**`models.py`.** Every model is `SiteAwareModel, TimestampedModel`:

```python
class MessagingFlag(models.TextChoices):
    INHERIT = "inherit"
    OPEN = "open"
    CLOSED = "closed"

class MessagingFlags(models.Model):            # abstract
    learner_to_educator = CharField(max_length=7, choices=MessagingFlag, default=INHERIT)
    learner_to_cohort_peer = ...
    learner_to_course_peer = ...
```

| Model | Owner field | Flags |
| --- | --- | --- |
| `SiteMessagingConfig` | `site` (from `SiteAwareModel`), `UniqueConstraint(fields=["site"])` as on `SiteSignupPolicy` | `MessagingFlags`, plus `offered_educator_roles = JSONField(null=True, blank=True)` |
| `OrganisationMessagingConfig` | `organisation = OneToOneField(Organisation, CASCADE, related_name="messaging_config")` | `MessagingFlags` |
| `CohortMessagingConfig` | `cohort = OneToOneField(Cohort, …)` | `MessagingFlags` |
| `LearnerMessagingConfig` | `learner = OneToOneField(Learner, …)` | `MessagingFlags` |
| `LearnerCourseRegistrationMessagingConfig` | `registration = OneToOneField(LearnerCourseRegistration, …)` | `learner_to_course_peer` only |
| `CohortCourseRegistrationMessagingConfig` | `registration = OneToOneField(CohortCourseRegistration, …)` | `learner_to_course_peer` only |

Every flag column gets a `CheckConstraint(condition=Q(<flag>__in=MessagingFlag.values))`. A
missing row behaves exactly like a row whose flags are all `inherit`.

**The resolver.** It walks an ordered list of layers, most specific first. It returns the first
value that is not `inherit`, together with the name of the layer that supplied it
(`ResolvedFlag(value, source)`). The settings default always supplies a value. The chain depends
on the kind of candidate. The learner level belongs to the sender's `Learner` row in the
candidate's organisation.

| Candidate | Flag | Chain, most specific first |
| --- | --- | --- |
| Shared cohort C | `learner_to_cohort_peer` | learner, cohort C, organisation, site, settings |
| Shared course via the sender's `LearnerCourseRegistration` R | `learner_to_course_peer` | learner, registration R, organisation, site, settings |
| Shared course via the sender's `CohortCourseRegistration` R on cohort C | `learner_to_course_peer` | learner, registration R, cohort C, organisation, site, settings |
| Offered educator's role on cohort C | `learner_to_educator` | learner, cohort C, organisation, site, settings |
| Offered educator's role on the organisation, or `site_admin` | `learner_to_educator` | learner, organisation, site, settings |

The layer list is a single module-level sequence. A later per-user level of service becomes one
more entry at the front of the list, with no change to any existing row. In SQL, the same chain
is `Coalesce(NullIf(<layer>, "inherit"), …, Value(<default>))`. The layers that depend only on
the sender (learner, organisation, site, settings) can be resolved in Python first and passed in
as a value. When the learner layer is set, the whole candidate kind collapses to a constant.

**`policy.py`.** `LayeredMessagingPolicy(MessagingPolicy)`:

- `can_start` checks in this order:
  1. `sender == recipient` → `SAME_USER`.
  2. Either user is inactive → `INACTIVE_USER`.
  3. The recipient is in `colleagues_of(sender, site)` → allowed.
  4. The sender is in `educators_of(row)` for any active `Learner` row of the recipient on the
     site → allowed.
  5. Any candidate from any of the sender's active `Learner` rows on the site, reaching the
     recipient, resolves `open` → allowed.
  6. Otherwise `CLOSED_BY_CONFIGURATION` if at least one candidate exists, else
     `NO_RELATIONSHIP`.
- The educator candidates in step 5 come only from roles on the offered list. The offered list is
  the site row's `offered_educator_roles` when that is not `None`, otherwise
  `MESSAGING_OFFERED_EDUCATOR_ROLES`, intersected with `roles_granting(VIEW_LEARNER, site)`.
  Offered educators are always a subset of `educators_of`.
- `can_reply` is allowed when `can_start(sender → recipient)` or `can_start(recipient → sender)` is
  allowed. When both are refused, it returns the sender-direction refusal.
- `recipients_for` returns a single `User` queryset. It ORs together the colleagues, the users
  whose active `Learner` rows the sender is an educator of, and the users reachable through an
  open candidate. It excludes the sender and inactive users. Evaluating it costs a fixed number of
  queries that does not grow with the number of learners, cohorts or registrations. It does not
  use `distinct()`.
- All three methods share one per-candidate resolution. They have no parallel implementation.

**`admin.py`.** Register one `SiteAwareModelAdmin` per model, with an autocomplete on the owner
field. `list_display` shows the owner and the flags. Each flag carries `help_text` explaining that
"Inherit" uses the next level up. On `SiteMessagingConfig`, `offered_educator_roles` is a
multiple-choice field built from `roles_granting(VIEW_LEARNER, site)`, with a way to say "use the
settings default" (`None`) that is distinct from an empty selection (`[]`). Model `clean()` runs
the same validator, so a non-admin writer is also refused an unknown key.

**`checks.py`:**

- `freedom_ls_messaging_policy.E001`: a `MESSAGING_DEFAULT_FLAGS` key is missing or unknown, or a
  value is not `open` or `closed`.
- `E002`: a `MESSAGING_OFFERED_EDUCATOR_ROLES` key is missing from the base role config or from
  any module in `FREEDOMLS_PERMISSIONS_MODULES`.
- `W001` (tagged as a database check, and silent on an unmigrated database the way
  `freedom_ls/course_access/checks.py` is): a stored `offered_educator_roles` key is missing from
  that site's role config. This catches roles removed after the row was saved.

## Testing

Follow the `fls-dev:testing` skill. Tests live in `freedom_ls/messaging_policy/tests/`,
`freedom_ls/comms/tests/` and `freedom_ls/learner_management/tests/`.

- **Agreement matrix.** For every educator × organisation × learner in a scenario world,
  `learner in learners_visible_to(educator, org)` iff `educator in educators_of(learner)`. Use
  `test_learners_visible_to_agrees_with_can_on_every_learner` in
  `freedom_ls/educator_interface/tests/test_permission_matrix.py` as the model. The world covers
  `site_admin`; `organisation_admin` with and without an active `OrganisationMember`;
  `cohort_admin` and `cohort_viewer` on one cohort and on two; an inactive assignment; an inactive
  user; a custom role from a test role config; a user with no role; learners in zero, one and two
  cohorts; an inactive learner; one user with `Learner` rows in two organisations. Run it under
  `mock_site_context` and with no request on the thread-local. Superusers and self-visibility get
  their own tests. A comment points at the planned `Cohort.is_active`.
- **`peers_of`.** Covers a shared cohort, a shared course through each pair of registration paths,
  an inactive learner on either side, an inactive registration, a course shared across two
  organisations (not peers), and self exclusion.
- **`colleagues_of`.** Covers an organisation role and a cohort role in the same organisation, a
  role in another organisation (not a colleague), a `site_admin` with everyone, the
  `OrganisationMember` gate, a superuser without a role (not a colleague), and a non-`VIEW_LEARNER`
  role (not a colleague).
- **Resolver.** A parametrised table of layer values that checks the expected value and source for
  every chain above. It also proves that a missing row equals an all-`inherit` row, and that the
  learner layer beats every other layer.
- **Policy outcomes.** The worked examples 1 to 9 in `research_pair_resolution.md`, rewritten for
  the current role keys, as named tests: two cohorts that conflict, a stop at the learner level,
  the paid learner, a course with two registration kinds, the asymmetric sender-only course case,
  course peers across organisations, a removed learner, and a multi-organisation educator.
- **Out-of-the-box rules** with no config rows: an educator may start with a learner they can see,
  and the learner may reply. A learner may not start with an educator or a peer. Colleagues may
  start with each other. A superuser with no role may start with nobody.
- **Offered educators.** By default `cohort_admin` is offered, while `cohort_viewer`,
  `organisation_admin` and `site_admin` are not. A site override applies. `None` and `[]` behave
  differently. Every offered educator is in `educators_of`. On a site with no cohorts and
  `organisation_admin` offered, an opened learner reaches their organisation admins with no
  special case.
- **Replies after change.** Closing config, deactivating a registration, removing a learner and
  removing a role each refuse replies in both directions, with the expected reason.
- **Reason codes**, one test per `MessagingRefusal` member.
- **Consistency.** Across the scenario world, `user in recipients_for(sender)` iff
  `can_start(sender, user).allowed`.
- **Query counts.** `recipients_for` and `can_start` use pinned counts that do not change when the
  world grows fivefold. The SQL contains no `DISTINCT`.
- **`MessagingDecision`.** `bool()` raises, and the `allowed`/`reason` invariant is enforced.
- **Checks.** Each check ID fires on bad input and stays silent on good input. The admin form
  rejects an unknown role key.
- **Boundary.** Extend `freedom_ls/comms/tests/test_boundaries.py` so that nothing under `comms`
  imports `learner_management`, `organisations`, `role_based_permissions` or `messaging_policy`.

## Open questions

Defaults taken. The user can overrule any of them.

- **Reason codes.** There are four, and a removed sender `Learner` row is plain `NO_RELATIONSHIP`
  with no separate "removed" code. Spec 4 supplies the wording and may ask for a finer split.
- **The `conversation` parameter** is typed `Model`. Spec 4 may prefer a narrower type, which
  would change the contract.
- **A role key that is unknown at runtime** (removed from the role config after it was saved) is
  dropped quietly and reported by `W001`. It does not raise during a request.
- **`Cohort.is_active`** (`educator-interface-6-cohort-administration`). Whether an inactive
  cohort still links peers and educators gets decided there. The agreement test catches a change
  made on one side only.

## Success criteria

- With no config rows, an educator's `can_start` on a learner from `learners_visible_to` is
  allowed, and that learner's `can_reply` to the educator is allowed.
- With no config rows, a learner's `can_start` on any educator or peer returns
  `CLOSED_BY_CONFIGURATION`.
- The agreement matrix passes inside and outside a request.
- `recipients_for` agrees with `can_start` across the whole scenario world.
- The `recipients_for` query count is the same for the small world and the fivefold world.
- Swapping `MESSAGING_POLICY` to a test subclass changes what `get_messaging_policy()` returns.
- `uv run manage.py check` reports `freedom_ls_comms.E003` for a bad path and
  `freedom_ls_messaging_policy.E002` for an unknown default role key.
- The boundary test proves `comms` imports none of the four apps.
- A site admin can create every config model in the Django admin, and cannot save an offered role
  that is missing from the site's role config.
- `docs/app_structure.md`, `docs/product/messaging.md` and the glossary describe the new app and
  the new terms.
