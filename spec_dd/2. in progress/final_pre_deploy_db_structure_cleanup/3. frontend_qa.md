# Frontend QA: final pre-deploy database structure cleanup

## What this is testing, and why a browser is needed at all

Most of this change is invisible from the outside. It is field renames, `on_delete` rules, app
labels and constraint spellings. But five classes of breakage in it are invisible to `pytest`,
`manage.py check` and `mypy` too, and only a browser catches them:

1. **Django admin string lookups.** `list_display`, `list_select_related`, `list_filter`,
   `search_fields`, `autocomplete_fields`, `ordering` and `fieldsets` are resolved at *query* and
   *render* time, not import time. A missed `collection` → `course` rename returns wrong or empty
   results, or a 500 on one changelist, rather than raising at startup.
2. **Admin URL names.** The `webhooks` label change moves every `admin:webhooks_*` route to
   `admin:freedom_ls_webhooks_*`. A missed one is a `NoReverseMatch` on a page nobody's unit test
   loads.
3. **Constraint validation that silently stops running.** Respelling `"site_id"` → `"site"` in a
   `Meta.constraint` disables that constraint's admin-form validation unless a
   `ConstraintValidationFormMixin` form is wired on. The symptom is an `IntegrityError` **500**
   where a field error used to appear, and only submitting a real duplicate through a real form
   surfaces it. This is the single highest-value area below.
4. **Delete surfaces.** Django hides the delete affordance in three separate places (detail-page
   button, `delete_selected` bulk action, per-row inline checkbox) governed by two separate hooks.
   You have to look at all three, on a parent *and* its inlines.
5. **Template variable renames.** `{{ registration.collection.title }}` failing silently renders an
   empty cell. Nothing complains.

Treat any 500, any `NoReverseMatch`, any empty column that used to have content, and any surviving
`collection` label where a course is meant, as a bug, whether or not the step asks for it.

## Setup

### 1. Rebuild the database

App labels changed and migration history was replaced wholesale, so the old tables and
`django_migrations` rows are meaningless. Do a clean rebuild. Do **not** QA against a database
carried over from before this change.

```bash
.claude/fls-dev/scripts/dev_db_delete.sh
.claude/fls-dev/scripts/dev_db_init.sh
uv run python manage.py migrate
uv run python manage.py create_demo_data
uv run python manage.py content_save ./demo_content DemoDev
```

### 2. Kill any server left running from before the change

`ContentType.objects.get_for_model()` caches per process. A `runserver` alive across the label
change serves stale content types and produces confusing, wrong results.

```bash
.claude/ds/scripts/kill_runserver.sh
```

### 3. Start a server on a free port

```bash
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL is `http://127.0.0.1:$PORT`. Substitute the literal port number into every URL below.

> **Port note.** `config/settings_dev.py` sets `FORCE_SITE_NAME = "DemoDev"`, so `get_cached_site()`
> returns the DemoDev site for every request regardless of host or port. Any port serves DemoDev
> data; you do not need port 8000 and you do not need a hosts-file entry.

## Test 3. Duplicates return a field error, not a 500 (the §4.6 trap)

This is the highest-risk area in the change. Every one of these forms had its constraint respelled or
newly site-scoped; if the `ConstraintValidationFormMixin` wiring was missed, the constraint stops
being checked while cleaning and the duplicate blows up at the database instead.

For each row below: create a valid record first (confirm it **saves**), then submit an exact
duplicate and confirm you get a **red inline field error on the form**, on the page, with the form
re-rendered. **not** a yellow Django 500 debug page reading `IntegrityError` / `duplicate key value
violates unique constraint`.

| Admin | Duplicate to submit | Constraint |
| --- | --- | --- |
| `/admin/freedom_ls_learner_management/cohort/add/` | Same **name** + same **organisation** as an existing cohort | `unique_cohort_name_per_organisation` |
| `/admin/freedom_ls_learner_management/learnercourseregistration/add/` | Same **learner** + same **course** | `unique_learner_course_registration` |
| `/admin/freedom_ls_learner_management/cohortcourseregistration/add/` | Same **cohort** + same **course** | `unique_cohort_course_registration` |
| `/admin/freedom_ls_learner_management/learner/add/` | Same **user** + same **organisation** | `unique_learner_per_organisation` |
| `/admin/freedom_ls_course_interest/courseinterest/add/` | Same **user** + same **course** | `unique_course_interest` |
| `/admin/freedom_ls_content_engine/file/add/` | Same **file path** | `unique_file_path_per_site` |
| `/admin/freedom_ls_webhooks/webhooksecret/add/` | Same **name** | `unique_webhook_secret_name_per_site` |

**3.1 The negative case for Cohort. Prove the scope is per organisation, not per site.** Create a
cohort named `QA Duplicate Check` in organisation A. Now create a cohort with the **same name** in
organisation **B**. It must **save successfully**. If it is rejected, the constraint is scoped wrong
(the old name `unique_cohort_name_per_site` claimed a scope it never had).

**3.2 `WebhookSecret` after `clean_name` was deleted.** The hand-rolled duplicate check in
`WebhookSecretForm.clean_name` is removed, so the constraint is now the only place the rule lives.
Beyond the duplicate case above, confirm the *rest* of that form still behaves: create a secret with
a fresh name and a value, save it, reopen it. The value field must render as a masked password input
with the "Enter new value to change" placeholder, and saving with it **left blank** must keep the
existing value rather than wiping it.

**3.3 Educator-facing cohort form.** The same trap exists outside the admin. Log in as
`demodev@email.com`, go to `/educator/`, pick an organisation, and open the cohort create/edit form.
Submit a name that already exists **in that organisation**. Expect a field error rendered inline in
the educator UI, not a 500. Then submit a genuinely new name and confirm it saves and the cohort
appears in the list.

## Test 5. Deletion semantics, seen from the UI

**5.1 `PROTECT` on `QuestionAnswer.question`.** Content admins can no longer delete, so drive this
through the shell rather than the browser and then confirm the browser is unaffected:

```bash
uv run python manage.py shell -c "
from freedom_ls.form_engine.models import FormQuestion
q = FormQuestion.objects.filter(questionanswer__isnull=False).first()
try:
    q.delete()
    print('BUG: deleted')
except Exception as exc:
    print(type(exc).__name__, exc)
"
```

Expect `ProtectedError`. Then reload the form-question changelist in the browser and confirm nothing
was removed.

**5.2 `PROTECT` on the registration course FKs.** Same shape: try to delete a `Course` that has a
`LearnerCourseRegistration`. Expect `ProtectedError`, and the course still present in
`/admin/freedom_ls_content_engine/course/`.

**5.3 Deadline survives its content type. The half-nulled row.** This is the branch the change
introduces and the one most likely to be broken.

Ask `fls-dev:qa-data-helper` to delete the `ContentType` row a `CohortDeadline` points at (leaving
`object_id` populated). Then, in the browser:

- `/admin/freedom_ls_learner_management/cohortdeadline/`. The row is **still there**, and its
  Content Item column reads **"Whole course"**.
- Open that row and press **Save without changing anything.** It must save cleanly. A validation
  error here means `clean()` is still keying on `object_id` as well as `content_type`.
- Now try to create a *second* whole-course deadline on the **same** cohort course registration.
  Expect the "A course-level deadline already exists for this cohort registration." validation
  error. The half-nulled row must still be found by the duplicate check.
- Repeat the first two steps for `LearnerDeadline` and `LearnerCohortDeadlineOverride`.

**5.4 Webhook delivery survives its endpoint.**

- Go to `/admin/freedom_ls_webhooks/webhookendpoint/`, open an endpoint, and use the **Send Test**
  action to produce a delivery. (If "Send Test" 404s or raises `NoReverseMatch`, that is the label
  change missing an admin URL name; see Test 6.1.)

  down; only content admins are).
- Go to `/admin/freedom_ls_webhooks/webhookdelivery/`. The delivery row must **still be there**, and
  its **Endpoint** column must still show the URL you noted. A blank column or a 500 means the

- Open that delivery's detail page. It must render, not 500.
- Select that orphaned delivery and run the **"Retry failed/stuck/dead-lettered deliveries"** action.
  It must complete without an exception; the orphaned row is simply skipped.
- Select a *live* delivery (one whose endpoint still exists) and run the same action. It must still
  actually retry.

## What counts as a finding

- Any HTTP 500, `IntegrityError` page, `NoReverseMatch`, or `AttributeError: 'NoneType'`.
- Any column, cell or panel that renders empty where data exists.
- A delete button, bulk action or inline delete checkbox surviving on any of the eleven content
  admins.
- A delete affordance *disappearing* from `FormProgress` or `QuestionAnswer`.
- A duplicate submission producing a 500 rather than a field error, on any of the eight forms in
  Test 3.
- The word "collection" appearing in the UI where a course is meant.

Route anything you find through the `fls-dev:qa-bugfixer` agent. One bug, one failing test, one
minimal fix.
