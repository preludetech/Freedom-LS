# Research: app boundaries, labels and table namespacing

## Executive summary

Do now, before deploy: give `webhooks` an explicit `freedom_ls_webhooks` label (`freedom_ls/webhooks/apps.py:4-6` has no `label`, so Django defaults it to plain `webhooks`, and its four models' tables are `webhooks_*` — the only app of 23 with real tables that breaks the otherwise-universal `freedom_ls_<app>` convention). This is the one genuine table-namespacing gap in the whole codebase; `health` and `icons` also lack explicit labels but own zero tables, so their risk is a *label*-namespace collision only (Django refuses to boot with two apps sharing a label — loud, immediate, `ImproperlyConfigured`, not a silent bug), which is real but far cheaper to fix (no migration touch, `apps.py` one-liner) — do it in the same pass anyway, for the same reason: it's free now and each is a plausible name for a downstream project's own app (a health-check app and an icon-handling app are common, generic names; "webhooks" doubly so). Django's own docs warn that changing `AppConfig.label` after migrations have shipped "will result in breaking changes to a project or, in the case of a reusable app, any existing installs" (docs.djangoproject.com/en/6.0/ref/applications/) — FLS has no installs yet, so this is the last free window. Beyond labels: no app is *badly* named enough to warrant a rename outside the terminology spec's already-planned `student_management → learner_management` (do-later, owned there) — but that rename is a good moment to also ask whether "management" is the right noun for what's inside (cohorts, registrations, deadlines, recommendations); I don't think a further split earns its migration cost pre-deploy, and say so explicitly in §2. `calculate_course_progress_percentage` (`freedom_ls/student_management/utils.py:15-64`) is confirmed as the sole cause of the `student_progress → student_management` edge in `docs/app_structure.md:112` — moving it to `student_progress` (which is the only app that calls it) removes that edge outright and costs one function move plus three import fixes; do it now, it's nearly free. I checked every other app's `utils.py` (`role_based_permissions`, `accounts`, `organisations`, `student_interface`) for the same smell and found none — each file's functions operate on that app's own models and the cross-app imports they do make already match declared, accepted edges in `docs/app_structure.md`. `app_authentication` (uninstalled, no migrations, a `Client` model storing API keys in a plaintext `CharField`) should be deleted, not kept dormant — dead code with a model is a liability with no offsetting benefit pre-deploy, and if API-client auth is wanted later it should be redesigned properly (hashed keys, not resurrected as-is). `xapi_learning_record_store` should be **kept** dormant exactly as-is (100% commented-out, no tables, no INSTALLED_APPS entry, so zero cost) because a live sibling spec (`xapi_implementation`) already intends to build on it and explicitly plans the very rename (`xapi_learning_record_store` → `xapi`) this idea would otherwise flag — don't duplicate that decision here, just note it lands as a normal part of that spec, not this one. On "what else deserves its own app": the three deadline models (`CohortDeadline`, `StudentDeadline`, `UserCohortDeadlineOverride`, `student_management/models.py:135-291`) are tightly coupled children of the registration models with no independent identity — not worth splitting out. The `course_access` / `course_applications` / `course_interest` trio looks like three tiny apps that could be one (course_access has zero models at all), but the separation is deliberate and already paying for itself: `course_access` is a pluggable-backend seam (`COURSE_ACCESS_BACKEND` setting, `config/settings_base.py:420-425`, swapped via `import_string`, never a direct import) and `course_applications`/`course_interest` are two independent, explicitly-scoped-for-future-growth feature slivers (each file's own docstring says so) — merging them would tangle a designed extension point for no pre-deploy benefit. `reports` already exists as its own well-scoped app (`freedom_ls/reports/`, installed, migrated) — the idea's "should X be its own app" question is already answered correctly for it; nothing to do.

## 1. The app-label collision risk

**Verified state of every app's label** (`freedom_ls/*/apps.py`):

| App | `label` | Has models/tables? |
|---|---|---|
| `webhooks` | **none set** → defaults to `webhooks` (`freedom_ls/webhooks/apps.py:4-6`, only `name = "freedom_ls.webhooks"`) | Yes — 4 models (`WebhookEndpoint`, `WebhookEvent`, `WebhookDelivery`, `WebhookSecret`, `freedom_ls/webhooks/models.py:48,366,375,415`), tables `webhooks_*` |
| `health` | **none set** → defaults to `health` (`freedom_ls/health/apps.py:4-5`) | No — no `models.py` in the app at all |
| `icons` | **none set** → defaults to `icons` (`freedom_ls/icons/apps.py:4-5`) | No — no `models.py` |
| all other 20 apps | explicit `freedom_ls_<app>` | — |

Everything else checked per the task has **no label-collision exposure at all**, because it is not a Django app:

- `contrib` (`freedom_ls/contrib/__init__.py` — a bare package, no `apps.py`) and its `contrib/conformance/` sub-package (`freedom_ls/contrib/conformance/test_migrations.py` etc.) are plain Python, imported by pytest and by whatever downstream conformance harness runs them — never listed in `INSTALLED_APPS`.
- `freedom_ls/tests/` (`playwright_fixtures.py`, `app_guards.py`) — same: a bare package, no `apps.py`.
- `themes/` (`freedom_ls/themes/default/`, `freedom_ls/themes/first_class/`) — only `theme.md` + `theme.css` per theme, no Python at all, not an app.
- `qa_helpers` **does** have a proper label (`freedom_ls_qa_helpers`, `freedom_ls/qa_helpers/apps.py:4-7`) and so carries no collision risk itself, but it is installed **only** in `config/settings_dev.py:46-50`, never in `config/settings_base.py` — i.e. it never ships to a downstream production `INSTALLED_APPS` at all, which is worth noting as a mitigating fact for anyone worried about its footprint.
- `base`, `deployment`, `panel_framework` all have explicit `freedom_ls_`-prefixed labels (`base/apps.py:6-7`, `deployment/apps.py:5-6`, `panel_framework/apps.py:6-7`) and, per repo-wide `models.py` glob, **none of the three has a `models.py`** — infra-only apps, correctly labeled, zero tables, nothing to do.

**How real is the risk.** FLS is installed as a git submodule "alongside a downstream project's own apps" (per this idea's background) — the downstream project's `INSTALLED_APPS` mixes its own apps with FLS's. `webhooks`, `health`, and `icons` are exactly the kind of generic, common name a downstream Django project is likely to also pick for its own app (a health-check app, an icon/asset app, a webhooks-delivery app are all ordinary, unremarkable app names — far more likely to collide than, say, `freedom_ls_content_engine`). Django requires `AppConfig.label` to be unique across the whole project and raises `django.core.exceptions.ImproperlyConfigured: Application labels aren't unique, duplicates: <label>` at `django.apps.registry.Apps.populate()` time — i.e. at process boot, before a single view or management command runs. This is **loud, not silent**: nothing runs at all until fixed. The downside for a downstream operator hitting it is not corruption, it's "my app won't start until I relabel *my* app to work around *your* submodule" — annoying and unplanned-for, but not data-destructive.

**What a label change touches, checked explicitly:**

- `AUTH_USER_MODEL`-style string references: not applicable to `webhooks`/`health`/`icons` — nothing points at them by label string except migrations (below). (`AUTH_USER_MODEL = "freedom_ls_accounts.User"`, `config/settings_base.py:265`, is the one live example of this pattern in the codebase and is unaffected — `accounts` already has its correct label.)
- Permission strings: grepped `webhooks\.` and `freedom_ls_webhooks` across `freedom_ls/` — zero hits in `role_based_permissions/registry.py` or anywhere else referencing a `webhooks.<perm>`-style codename. Webhooks has no guardian/role integration today, so relabeling adds no permission-string fallout.
- `apps.get_model(...)` calls: grepped for `get_model("webhooks` / `get_model(app_label="webhooks` — zero hits.
- Migration `dependencies` / FK targets: **this is the real cost.** `freedom_ls/webhooks/migrations/` has 10 files; 9 of them reference the label `'webhooks'` explicitly, either in `dependencies = [('webhooks', '000N_...')]` (migrations `0002`–`0010`) or in FK `to='webhooks.webhookendpoint'` / `to='webhooks.webhookevent'` (`0001_initial.py:62-63`). Every one of those 9 files needs its label string rewritten to `freedom_ls_webhooks` for a clean relabel — mechanically identical to what `learner-terminology-rename`'s todo already plans to do for `student_management`/`student_progress`'s own migrations (`spec_dd/2. in progress/learner-terminology-rename/idea.md:50-63`), but that spec's scope table (`idea.md:29-46`) does **not** include `webhooks` — this is net-new work, not something that rename will pick up for free.
- Generic-relation `ContentType` rows: grepped every webhook model name (`webhookendpoint`, `webhookevent`, `webhookdelivery`, `webhooksecret`) case-insensitively across `freedom_ls/` — no `GenericForeignKey` anywhere targets a webhook model (the codebase's only `GenericForeignKey` users are the three deadline models in `student_management`, pointing at `Topic`/`Form`, see §5). So no stale `ContentType` rows to worry about from a relabel — a plain `ContentType.objects.filter(app_label="webhooks").update(app_label="freedom_ls_webhooks")` (or letting the migration framework's `RenameModel`-style handling reconcile it, since pre-deploy there's no data to preserve at all) would be the whole fix.

**Cost now vs. after deploy.** Now: rewrite 9 migration `dependencies`/FK-target strings, add one `label = "freedom_ls_webhooks"` line to `apps.py`, rerun `makemigrations`/`migrate` against a rebuilt dev DB (no data to protect, per this idea's own framing) — an afternoon, self-contained to one app, no downstream coordination needed because there are no downstream installs yet. After deploy: exactly the breaking-change scenario Django's own docs warn about — a downstream operator's production tables silently become `freedom_ls_webhooks_*` under their feet on the next submodule bump unless a hand-authored data migration renames them in place, *and* every downstream customization that queried `webhooks_*` tables directly or referenced the `webhooks` app label breaks. Fix it now.

`health` and `icons` cost less to fix (label-only, no migrations exist because no models exist) but the risk they mitigate is the same class of failure (boot-time collision) and the fix is a one-line add each — bundle it into the same pass as `webhooks` rather than leaving two of three known-generic labels unfixed.

**A guardrail worth adding while in there:** `freedom_ls/contrib/conformance/test_migrations.py` already probes for model/migration drift as a conformance check (diffing `ProjectState.from_apps(apps)` against the migration graph, no DB needed). A companion assertion — every `INSTALLED_APPS` app's resolved label starts with `freedom_ls_` (or is a small documented allowlist) — would catch a *future* unlabeled app before it ships, at near-zero cost, in the same style as the existing `base/checks.py` system checks (`freedom_ls_base.E001`/`E002`, `freedom_ls/base/checks.py:16-53`). This is a small, mechanical do-now addition, not scope creep — the machinery and convention already exist, this only closes a real gap in it.

## 2. App naming

The word-level student→learner sweep across `student_management`, `student_progress`, `student_interface` is fully owned by `spec_dd/2. in progress/learner-terminology-rename/idea.md` and explicitly out of scope here — but that spec's own scope note (`idea.md:145-147`, "Renaming any other app. `educator_interface` and the rest keep their names.") makes clear it is a **word swap**, not a re-think of app boundaries. So the question this idea actually asks — is the *concept* right, not just the word — is still open for `student_management` (destined to become `learner_management`).

**`student_management` / future `learner_management`.** Contents, confirmed (`freedom_ls/student_management/models.py`): `Cohort` (16-32), `CohortMembership` (35-48), `UserCourseRegistration` (51-106), `CohortCourseRegistration` (109-132), `CohortDeadline` (135-179), `StudentDeadline` (182-226), `UserCohortDeadlineOverride` (229-290), `RecommendedCourse` (293-319). That's cohorts + registrations (individual and cohort-wide) + deadlines (three variants) + recommendations — "management" is a vague catch-all, but it is an accurate one: every model here is administrative bookkeeping *about* a learner's relationship to a course, which is a coherent single concern, not an accidental grab-bag. I don't think a further split (e.g. peeling deadlines into their own app, see §5) earns its migration cost pre-deploy. Recommendation: let the terminology rename carry this to `learner_management` and stop there; don't open a second restructuring inside the same word-swap PR, and don't treat "management" as broken enough to need more than that.

**`base`.** Infra-only (middleware, theming, env helpers, git utils, webhook-event-type constants, app settings base class — `freedom_ls/base/*.py`), no models, imported by nearly everything (`docs/app_structure.md:38-121` shows 9 runtime dependents). The name is fine for what it is: a shared-kernel app. Nothing to rename.

**`contrib`.** Not an installed app at all (§1) — a bare namespace package holding `contrib/conformance/`, a conformance test-probe suite referenced by `docs/product/configuration-and-extension.md:87-102`. The name matches Django convention (`django.contrib.*` is the same pattern: optional, opt-in, not core) and needs no change.

**`site_aware_models`.** Accurately named — it is the multi-tenancy base-model/manager/middleware layer, and every other site-scoped model literally extends `SiteAwareModel` from it. No better name suggests itself; leave it.

**`panel_framework`.** Accurately named — a generic, content-agnostic UI framework (`tabs.py`, `panels.py`, `tables.py`, `actions.py`, `views.py`) consumed by `educator_interface`, with no models of its own. Fine as-is.

**`course_access` / `course_applications` / `course_interest`.** Three small apps, one genuinely tiny each: `course_access` has **no models at all** (confirmed — no `models.py` in the directory listing), only a pluggable access-decision layer; `course_applications` has exactly one model, `CourseApplication` (`freedom_ls/course_applications/models.py:17-54`, 55 lines total); `course_interest` has exactly one model, `CourseInterest` (`freedom_ls/course_interest/models.py:17-48`, 49 lines total). On raw size this looks like the definition of "should be one app." It should stay three, for a reason visible in the code itself, not just convention:

  - `course_access` is explicitly a **swappable backend seam**. `config/settings_base.py:419-425`: `COURSE_ACCESS_BACKEND` defaults to `freedom_ls.course_applications.backends.ApplicationCourseAccessBackend`, with the comment "The free-only core default backend (`freedom_ls.course_access.backends.FreeOnlyCourseAccessBackend`) is the no-applications fallback. This is a project settings string in `config`, NOT a `course_access` import — so `course_access` still never depends on `course_applications`." That is a deliberate, documented, one-directional decoupling (confirmed in `docs/app_structure.md:47-58`: `course_access --> accounts, base, content_engine, student_management` at runtime, with only a **test-only** dashed edge `course_access -.-> course_applications`, never a runtime one). Folding `course_applications` into `course_access` would make that seam impossible to express — the whole point is that the free-tier backend must be installable *without* the application-gating app.
  - `course_applications` and `course_interest` are each explicitly staged for independent future growth, in their own docstrings: `course_applications/models.py:1-30` — "Application review will later add a state machine, transitions, notes, signals, and permissions... Application forms will add a config FK and answer/file children... Do not architect these away — leave this model standalone and additive." `course_interest/models.py:1-26` — "when notify-on-launch lands, this model gains a `notified_at` DateTimeField... Do not architect this away." These are not accidental one-model apps; they are minimal seeds with committed future shapes that are unrelated to each other (application review vs. notify-on-launch email). Merging them now would force an un-merge later at exactly the moment new fields and permissions land — worse timing than doing nothing.

  Recommendation: **won't-do.** The apparent smallness is by design, not neglect; each app's own comments already reasoned about this and reached a documented decision.

**`xapi_learning_record_store`.** Covered in §4 (dormant-apps question) and cross-referenced to `xapi_implementation`, which already plans the package rename to `xapi` (`spec_dd/1. next/xapi_implementation/0. idea.md:7-9`: "Rename the existing `xapi_learning_record_store` directory to `xapi` (the app config already uses `freedom_ls.xapi`)"). Note the app's `name` is *already* `freedom_ls.xapi` (`freedom_ls/xapi_learning_record_store/apps.py:6`) while its package directory and `label` (`freedom_ls_xapi`) lag behind — i.e. the rename is already half-done in code, just not the directory. Nothing for this idea to add; that spec owns finishing it.

## 3. Misplaced code that distorts the dependency graph

**Confirmed: `calculate_course_progress_percentage` is the sole cause of the `student_progress → student_management` edge**, and moving it removes the edge outright. Its only call sites, repo-wide (grep for the function name):

- Definition: `freedom_ls/student_management/utils.py:15-64`.
- Callers: `freedom_ls/student_progress/signals.py:25` (import), `:89` (call); `freedom_ls/student_progress/management/commands/recalculate_progress_percentages.py:6` (import), `:53` (call); `freedom_ls/qa_helpers/management/commands/qa_create_rich_dashboard_student.py:39,200`; and its own tests, `freedom_ls/student_management/tests/test_course_progress_calculation.py` (9 call sites, all local to the app that currently owns it).

Every real caller is `student_progress`; `qa_helpers` already depends on both apps directly (`docs/app_structure.md:74-82`) so its import is unaffected either way. The function's own body has **no dependency on any `student_management` model or import** — it takes a `Course` (from `content_engine`, type-hinted via `TYPE_CHECKING` at `utils.py:10`) and two sets of UUIDs, and walks `course.children()`. There is no reason for it to live in `student_management` at all; it was placed there historically, not for a structural reason. Moving it to `freedom_ls/student_progress/utils.py` (or inlining into `signals.py` given it has essentially one real caller-class) removes the `student_progress → student_management` edge from `docs/app_structure.md:112` (regenerate via `/app_map` after the move — do not hand-edit, per that file's own header, `docs/app_structure.md:1-11`). This is the single cheapest, cleanest fix in this whole research unit: one function, three import-site updates, and — note — `is_registered_for_course` in the same file (`student_management/utils.py:67-91`) stays exactly where it is, its docstring even explaining why: "Extracted from `student_interface.utils.get_is_registered` so that `course_access.backends` can call it without creating a dependency cycle." That one earns its home; `calculate_course_progress_percentage` does not.

**Audit of every other app's `utils.py`** (the only other candidates for the same smell, per repo-wide glob `freedom_ls/*/utils.py`): `role_based_permissions/utils.py` (`clear_permission_cache`, `assign_object_role`, `sync_user_object_permissions`, etc., `freedom_ls/role_based_permissions/utils.py:29-374`) — all operate on that app's own `models.py` (`SystemRoleAssignment`/`SiteRoleAssignment`/`ObjectRoleAssignment`) plus generic `Model`/`ContentType` — correctly scoped. `accounts/utils.py` (`get_client_ip`, `get_signup_policy_for_request`, `get_effective_require_name`, etc., `:14-68`) — imports only `site_aware_models.get_cached_site`, an already-declared edge (`docs/app_structure.md:40`) — correctly scoped. `organisations/utils.py` — one function, `get_default_organisation(site)` (`:10`), self-contained — correctly scoped. `student_interface/utils.py` — the largest, importing from `content_engine`, `student_management`, `student_progress` (`:14-37`), but every one of those is already a declared runtime edge for `student_interface` in `docs/app_structure.md:93-102`, and the functions themselves (`get_is_registered`, `get_course_index`, `get_content_status`, etc., `:73-774`) are all genuinely about orchestrating the player experience across those three apps' models — that's `student_interface`'s actual job, not misplacement. **Verdict: no other misplaced function found.** `calculate_course_progress_percentage` is the one real case.

**`SiteFactory` in `accounts`** — flagged in `spec_dd/1. next/debt_markdown_rendering_package_isolation/idea.md:95-103` as "the biggest single lever for tidying the test-dependency graph" ("`SiteFactory` wraps the Django builtin `Site` but lives in `accounts`, so `webhooks`, `site_aware_models` and many others import it from there... Relocating it... removes a swathe of dashed `… → accounts` edges"). That spec explicitly owns assessing and (possibly) moving it as part of its general test-isolation pass — don't duplicate the analysis here; just note it's the one other known dependency-graph distortion in the codebase and it's accounted for elsewhere.

## 4. The two dormant apps

**`app_authentication`.** Not in `INSTALLED_APPS` (commented out, `config/settings_base.py:99`), no `migrations/` directory at all (confirmed — `Glob` for `freedom_ls/app_authentication/*.py` returns only `__init__.py`, `apps.py`, `factories.py`, `admin.py`, `models.py`, no `migrations/`), so its table has genuinely never existed and creating it post-deploy is a non-event, structurally. But the model itself is a liability independent of migration timing: `Client(SiteAwareModel)` (`freedom_ls/app_authentication/models.py:8-43`) stores `api_key = models.CharField(max_length=64, unique=True, editable=False, ...)` (`:15-20`) generated via `secrets.token_urlsafe(48)` (`:41-43`) — a **plaintext, queryable, admin-visible** API key, with a working `admin.py` that would expose it in the Django admin the moment the app is ever installed. This is dead code that, if anyone flips it on casually (uncomments one `INSTALLED_APPS` line), ships a real credential-handling bug with no review gate in front of it, because nothing currently exercises or tests that path meaningfully as a security-relevant feature. Recommendation: **delete**, not keep dormant. If API-client authentication is wanted later, it should be scoped and built properly (hashed/salted key storage, a real rotation story) as its own reviewed feature, not resurrected wholesale from a half-finished sketch. Keeping it "just in case" costs nothing in migrations but costs real risk the moment someone flips the switch without re-reading it carefully.

**`xapi_learning_record_store`.** `models.py` is 100% commented-out (`freedom_ls/xapi_learning_record_store/models.py:1-37`, every line prefixed `#`), not in `INSTALLED_APPS`, no tables, and — per §2 — its `AppConfig.name` is already `freedom_ls.xapi` (`apps.py:6`) while the directory and `label` haven't caught up yet. `spec_dd/1. next/xapi_implementation/0. idea.md` is a live, detailed idea (research docs on the xAPI standard, DB strategy, frontend tracking, Django prior art already exist alongside it) that explicitly plans to build the real thing here and finish the rename. Recommendation: **keep dormant, exactly as-is** — there is nothing to clean up that spec won't clean up itself as a byproduct of implementing, and touching it now (e.g. deleting the sketch, or doing the rename early) would just create merge friction against that in-flight work for zero benefit.

## 5. What else deserves its own app, or should be folded in

**The three deadline models** (`CohortDeadline`, `StudentDeadline`, `UserCohortDeadlineOverride`, `student_management/models.py:135-291`) are a plausible-looking split candidate by line count (157 lines, roughly a fifth of the file) and by conceptual distinctness (deadline logic vs. registration/membership bookkeeping), but they fail the "does it earn its migration cost" test on inspection: every one of them is a direct FK child of `CohortCourseRegistration` or `UserCourseRegistration` (`:138-142`, `:185-189`, `:232-236`) with **no independent identity or lifecycle** — this exact conclusion was already reached by the sibling organisations research (`spec_dd/3. done/2026-08-21_09:09_organisations/research_codebase_impact.md:35-38`, evaluating the same three models for a `school` FK: "No — inherits via..." in every case). Splitting them into their own app would mean either a forward FK from `student_management`/`learner_management` into a new app (fine) or, worse, the new app reaching back into `learner_management` for its own FK targets (a real, avoidable new cross-app coupling for no behavioural gain). There's also a real practical cost: `deadline_utils.py` (`freedom_ls/student_management/deadline_utils.py`) and the educator-interface `CohortCourseProgressPanel` already query across cohort/registration/deadline models together in single call sites (per the prior research doc's §3, `educator_interface/views.py:623-661`), so splitting deadlines out would scatter, not simplify, the app's most complex existing query surface. **Won't-do.**

**`reports`.** Already exists, already its own well-scoped app (`freedom_ls/reports/`, installed at `config/settings_base.py:114`, migrated), one model (`GeneratedReport`, `freedom_ls/reports/models.py:44-95`) with a sensible boundary (report generation/storage, not report *data* — it FKs out to `Cohort` for what it's reporting on, `models.py:51-55`) and a genuinely good `db_table`-avoidance/pk-derived-upload-path pattern worth nothing more than a nod. This is the idea's "should X be its own app" question already answered correctly by prior work; nothing to recommend.

**`course_access` / `course_applications` / `course_interest`.** Covered fully in §2 — deliberately separate, won't-do.

**Forms inside `content_engine`.** The idea's own headline example ("should the forms that are managed by the content engine be in their own app?") is out of scope for this research unit by design — it belongs to a sibling extraction-focused research pass in this same spec. For context only (not analysis): `content_engine/models.py` confirms `Form`, `FormPage`, `FormContent`, `FormQuestion`, `QuestionOption` (`:421,456,485,503,552`) as five of the file's eighteen classes — cross-reference that unit rather than duplicating its verdict here.

## Risks and gotchas

1. **The `webhooks` label fix is the one item in this whole unit with a real "after deploy" cost cliff**, per Django's own documented warning (docs.djangoproject.com/en/6.0/ref/applications/): once a downstream install has run `migrate` against `webhooks_*` tables, relabeling means either a hand-authored, downstream-run data migration to rename tables and reconcile `ContentType` rows, or living with the inconsistency forever. Right now it is a same-afternoon, single-app change (§1). This is the highest-priority single item in this research unit.
2. **`health` and `icons` are lower-cost but not lower-probability** — they have no tables, so relabeling later is cheap regardless of timing, but they are exactly the kind of generic app name a downstream project is likely to also use, so the boot-time collision itself could happen at any point, including after deploy, with no warning until it does. Fix alongside `webhooks` while the diff is already open, not because it's urgent on its own timeline.
3. **`app_authentication`'s plaintext `api_key` field is a latent security smell, not just dead code** (§4) — the risk isn't the app being uninstalled today, it's someone re-enabling it later without re-reading `models.py:15-20,41-43` closely enough to notice the credential-handling issue. Deleting it removes that latent trap entirely; keeping it "dormant" does not.
4. **Don't let the `webhooks` migration-string rewrite bleed into the terminology-rename spec's PR** — they are mechanically similar (both rewrite app-label strings across a migration history) but are two separate specs' scope tables (`learner-terminology-rename/idea.md:29-46` explicitly excludes `webhooks`). Land them as distinct, reviewable changes so a structure-review gate (`claude_plugins/fls-dev/commands/plan_structure_review.md`) can diff each against `docs/app_structure.md` independently.
