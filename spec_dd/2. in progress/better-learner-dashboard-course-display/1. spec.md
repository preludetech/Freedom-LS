# Better learner dashboard course display

## Purpose

The learner dashboard shows courses in four fixed sections, none of them configurable and none of
them sorted. `Course` has no `Meta.ordering` and no query on the dashboard path calls `order_by`, so
In Progress, Available courses and Learning History arrive in whatever order Postgres returns.
Available courses is hard-capped at three by a `break` in the view. In Progress is unbounded and
costs roughly fifteen queries per registered course.

This work lets a site say which courses go where on the dashboard, gives every section a total
order, and caps each course grid to one row with in-place pagination. The approach was settled in
`idea.md`.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `CourseCategory` | coined | A named, ordered group of courses, authored in the content repo and scoped to one site. Identified by an authored `uuid` like every other content type; referred to by its `slug`, which is unique within its site. No existing FLS identifier. |
| `Course.categories` | coined | A many-to-many to `CourseCategory`. Every category a course belongs to. Written by the loader and read by nothing in this work; it exists for the catalogue filtering that follows. |
| `Course.dashboard_category` | coined | A FK to `CourseCategory`. The one category the dashboard places the course in, and the only one any rule in this spec reads. Named for `show_on_dashboard` rather than "primary", because the dashboard is its only reader. |
| `Course.category` | retired | Was a free-text `CharField` and a `course.md` front-matter key. Both go. The key now fails validation with a message naming `categories` and `dashboard_category`. `Topic.category`, `Activity.category`, `CoursePart.category`, `FormPage.category` and `FormQuestion.category` keep their present meanings and are untouched. |
| `show_on_dashboard` | coined | Whether a `CourseCategory` gets a dashboard section of its own. It says nothing about whether its courses appear; a course under a category with the flag off still shows, in the catch-all. Named this rather than `visibility`, because `Course.visibility` is already a three-way published/coming_soon/hidden enum. |

## Scope

**In.** A `CourseCategory` content type declared in one authored file; `Course.categories` as a
many-to-many to it and `Course.dashboard_category` as the foreign key every dashboard rule reads;
cross-file validation of both references; a total order for every dashboard section; per-section
pagination; a Coming soon section; both fields in the course admin; sentence-case section headings;
a query-count bound on the dashboard.

**Out.** The flat catalogue at `/courses/` is untouched, so every "Browse all" goes to every course
rather than to one category's courses, and a category that grows to many pages is a content problem
for the builder until the catalogue can filter. In progress, Recommended courses and Learning history
are not split by category. No tooling for the foreign-key upgrade. No learner-side control
(favouriting, hiding, archiving) and no per-learner collapsed state. No distinct visual treatment for
the first category section. No express-interest control on a Coming soon card, which stays a link to
the detail page where that control already lives. No curated list that headlines one course out of
each of several categories without moving them; that is a different model.

**Also out: any reader of `Course.categories`.** No catalogue filter, no chips on the course card, no
per-category page. The field is written and validated here so that the work which does read it
inherits a curated, ordered, load-validated vocabulary rather than inventing an axis of its own.

**Also out: subcategories.** No `parent` on `CourseCategory`. A tree makes filtering, per-level
ordering and cycle-checking in the offline validator all expensive; `research_organising_axes.md` §1
holds the cost. A nullable self-FK stays additive later, and no authored file would have to change
for it.

The access backend's `get_dashboard_contributions` is not the home for this: it hands back
pre-rendered HTML above the whole course list, for authenticated learners only
(`course_access/backends.py:161-169`, `views.py:318-324`), so the view cannot order, page or
deduplicate what is inside it. It stays where it is and grouping is built alongside it.

## Decisions

**Categories are authored in one file, not one file each.** `course_categories.yaml` at the content
repo root holds every category in a single YAML document, in display order. Order is the position in
the list, so there is no `order:` key to reconcile across files and no collision to resolve. A form
page's questions already work this way
(`freedom_ls/content_engine/management/commands/content_save.py:712-727`; later citations shorten
this path).

**Files rather than admin rows**, because `content_validate` takes no site argument and so cannot
check an admin-managed vocabulary before a load at all. With categories in the repo, a bad slug is
caught by `content_validate`, by `content_save`, and by the bundled offline validator that runs with
no Django and no database.

**A course may belong to several categories, and names one of them as its `dashboard_category`.**
Every rule in §5 reads that single field, so a course renders one card, in one section, however many
categories it carries. The alternative was a second, uncurated axis for the catalogue, with no display
label, no order, no per-site declaration and no load-time validation; `research_organising_axes.md`
§3 makes that comparison.

**`dashboard_category` is an explicit key, never "the first one listed".** Position already means
display order in `children:` and in the declaration file, and a third meaning fails silently: someone
tidies a list into alphabetical order, a course moves section, and nothing in the diff says so. The
one shorthand is that **`dashboard_category` omitted with exactly one entry in `categories` resolves
to that entry.** Omitted with two or more is a load error naming the candidates. Omitted with no
categories at all is the catch-all, which is the unconfigured default every site starts from.

**A category is identified by an authored `uuid`, like every other content type, and referred to by
its `slug`.** Each entry in `course_categories.yaml` carries a uuid, the loader writes it back on
first save, and every later load matches the row with `update_or_create(id=<uuid>, site=site)`.
`SiteAwareModel` already makes that uuid the primary key (`site_aware_models/models.py:161`). The uuid
sits on each entry rather than at the top of the file, because this file describes many rows; a form
question's `options:` already take that shape (`form_engine/schema.py:87-98`, written back by
`content_save.py:153-197`). The slug is the reference an author types and a course names. Renaming a
slug is an ordinary edit: the row is found by its uuid, and every course still naming the old slug
fails validation with a message saying so. Renaming a `title` is the usual way to change what a
section is called.

**Categories are site-aware.** `CourseCategory` extends the same `SiteAwareModel` base as every other
content model, so a category belongs to exactly one site, and
`unique_course_category_slug_per_site` stops two sites' slugs colliding. Two sites keeping their own
declarations get their own rows and may reuse each other's slugs and titles, because the uuids differ.

**Loading one content repo into two sites in one database stays blocked, for categories as for
everything else.** The authored uuid is a global primary key, so the second site's
`update_or_create(id=X, site=site_2)` finds no row, falls through to `create`, hits a duplicate key,
and the atomic block aborts the load. That is a pre-existing limit of the content loader, it applies
to all nine content types, and this work neither fixes it nor makes it worse. Giving categories a
`(site, slug)` identity instead would have bought one content type an exemption the other eight lack;
any real answer has to work for courses, topics and activities too, most likely through a per-site
key, and that is a spec of its own. Separate databases per site are unaffected.

**No minimum-course threshold and no cap on the number of sections, for any section.** Every category
with `show_on_dashboard` true and at least one visible course renders, in configured order, however
many that is, and Coming soon renders with a single course. The configuration is authoritative and
the code adds no cutoffs of its own. A rendered section is never collapsed or put behind a
disclosure; it shows its cards and pages to the rest.

**A category with `show_on_dashboard: false` renders no section, and its courses fall through to
the catch-all.** The flag chooses which categories are worth a section of their own. It is not a
visibility control, and no course drops off the dashboard because of it; hiding a course is
`Course.visibility`'s job. A site can declare thirty categories for the catalogue to filter on, flag
three of them onto the dashboard, and still have every course reachable from the home page.

**Page size is three for every paginated section**, matching the cap the code hard-codes today and
one full grid row at the `lg` breakpoint. A module constant, not a setting. In progress pays the most
for this, because a learner returning to one course may have to page to it; the started-first order
in §5 is what keeps that course on page one, and one rule for every section beats a special case.

**Every course grid on the page is paginated, Recommended courses included.**
`RecommendedCourse` rows are curated per learner and usually few, but nothing caps them, and one
section quietly growing to twenty cards is the failure this work exists to stop. One rule for every
section also buys one template, one control and one set of tests.

**The catch-all keeps "Available courses", its `id="available-courses"` and its "Browse all courses"
link.** A site that declares no categories sees no category sections, every course in the catch-all,
and three of them, which is the same courses in the same place as today.

**`Course.Meta.ordering = ["title", "pk"]`.** A total order is a precondition for pagination,
because paging an unordered sequence shows a learner the same course twice, or never. `title` is not
unique, so `pk` is the tie-breaker. The catalogue becomes alphabetical as a consequence.

**Pagination controls keep a real `href` and are enhanced with HTMX, and the URL is never pushed.**
The dashboard is the site root, so the paged content has to be reachable without JavaScript and by a
crawler. Eight history entries between a learner and wherever they came from is a bad Back button on
a home page. Both `hx-push-url` and `hx-replace-url` stay off.

**No data migration for the foreign key.** Drop the old column and add the FK. A data migration
could create one category per distinct existing string, but no file would declare those categories,
so the site's next routine `content_save` would fail every course referencing them. A documented
manual step is better; the upgrade note carries it.

## Requirements

### 1. The `CourseCategory` content type

**Model**, in `freedom_ls/content_engine/models/courses.py` beside `Course`:

```python
class CourseCategory(TitledContent):
    """A named, ordered group of courses, declared in the content repo."""

    CONTENT_TYPE = SchemaContentTypes.COURSE_CATEGORIES

    order = models.PositiveIntegerField(default=0)
    show_on_dashboard = models.BooleanField(default=True)

    class Meta:
        ordering = ["order", "title"]
        constraints = [
            models.UniqueConstraint(
                fields=["site", "slug"], name="unique_course_category_slug_per_site"
            )
        ]

    def __str__(self) -> str:
        return self.title
```

`TitledContent` (`freedom_ls/content_base/models.py:65-82`) supplies `title`, `subtitle`,
`description` and `slug`. `BaseContent` supplies `file_path`, `meta`, `tags` and `content_type`. Do
not inherit `MarkdownContent`, because a category has no body. `Topic`
(`freedom_ls/content_engine/models/topics.py:8-23`) is the model to pattern-match on.

`order` is the field FLS already uses for an authored sequence. `ContentCollectionItem`
(`courses.py:306-307`) and the four `form_engine` models all declare `ordering = ["order"]`. `title`
is the tie-breaker.

**`Course.category` becomes two fields**, replacing the `CharField` at `courses.py:36`:

```python
categories = models.ManyToManyField(
    "freedom_ls_content_engine.CourseCategory",
    blank=True,
    related_name="courses",
)
dashboard_category = models.ForeignKey(
    "freedom_ls_content_engine.CourseCategory",
    null=True,
    blank=True,
    on_delete=models.SET_NULL,
    related_name="dashboard_courses",
)
```

`courses` goes on the many-to-many because that is the general relation, which forces the foreign key
to take the other `related_name`. A course may have neither field set. `SET_NULL` rather than
`PROTECT`, because a course surviving with no dashboard placement beats a blocked delete, and content
is never deleted through the admin anyway.

**Migrations.** Create `CourseCategory`, remove the old `category` `CharField`, add the foreign key,
add the many-to-many through table, add `Course.Meta.ordering`. Never edit an existing migration. No
`RunPython`. Do not try to convert the field in place: a single `AlterField` generates cleanly and
then fails at `migrate` time, because `"Technical Skills"::uuid` is not a valid Postgres cast.

**Factory.** `CourseCategoryFactory` in `freedom_ls/content_engine/factories.py`. `CourseFactory`
continues to set neither field.

### 2. The authored declaration

**Schema**, in `freedom_ls/content_engine/schema.py`:

```python
class CourseCategoryEntry(BaseModel):
    model_config = ConfigDict(extra="forbid")

    slug: str
    title: str
    description: str | None = None
    show_on_dashboard: bool = True
    uuid: str | None = None


class CourseCategories(BaseBaseContentModel, content_type=ContentType.COURSE_CATEGORIES):
    categories: list[CourseCategoryEntry]
```

Add `COURSE_CATEGORIES` to `ContentType` (`freedom_ls/content_base/schema.py:8-18`). The class
registers itself through `__init_subclass__` by declaring `content_type=`, and because it lives in
`content_engine/schema.py`, `ContentEngineConfig.ready()` already imports it
(`content_engine/apps.py:10-14`), so no new wiring is needed.
`freedom_ls/content_base/tests/test_schema_registry.py` asserts `set(ContentType) == set(SCHEMAS)`,
so the enum member and the class have to land together.

**Authored shape**, `course_categories.yaml` at the content repo root:

```yaml
---
content_type: COURSE_CATEGORIES
categories:
  - slug: start-here
    title: Start here
    description: New? Begin with these.
    show_on_dashboard: true
  - slug: technical
    title: Technical
    description: Hands-on, tool-specific courses.
---
```

`slug` is the key a course names in its front matter. `title` is the section heading and
`description` the line under it. Position in `categories` is the display order.
`show_on_dashboard` defaults to true when omitted. No entry above carries a `uuid`, which is what a
hand-written file looks like; the first load writes one into each entry and every load after that
matches on it.

**The `Course` schema gains two keys and rejects the old one.** Add `categories: list[str] = []` and
`dashboard_category: str | None = None` to `content_engine/schema.py`'s `Course` class (`:57`).

Then override the inherited `category` on that same class so it **fails** with a message naming the
two keys that replace it. Without the override the retired key still validates, because
`BaseContentModel.category` (`content_base/schema.py:51-53`) is shared with TOPIC, ACTIVITY and
COURSE_PART, whose models keep their `CharField`s. An author who leaves `category: Technical` on a
`course.md` would then get a clean load and a course that appears in no section, with nothing
anywhere saying why.

Front matter, in the two shapes an author will write:

```yaml
categories:
  - technical
```

```yaml
categories:
  - technical
  - python
dashboard_category: technical
```

`categories:` names two different things: the list of entries in
`course_categories.yaml`, and a list of slugs on a `course.md`. Both schemas set `extra="forbid"` and
the two shapes have nothing in common, so writing one where the other belongs fails at validation
with a pydantic error naming the file. A course-side key like `category_slugs:` would be worse to
read for a gain the validator already provides.

**Write-back, one uuid per entry.** A first load writes a `uuid` into every entry that lacks one,
so the file above comes back with each entry gaining a line:

```yaml
  - slug: start-here
    title: Start here
    description: New? Begin with these.
    show_on_dashboard: true
    uuid: 5c1f0a3e-7c2b-4a91-9f0d-2d6a1b83e4c7
```

`update_file_with_uuid` (`content_save.py:99-150`) is the wrong tool: it adds one top-level `uuid`
to the first document lacking one, which on this file means a stray key beside `categories:` and no
entry touched. The precedent is `update_file_with_option_uuids` (`:153-197`), which walks a nested
list and writes a uuid into each member; `update_file_with_category_uuids` is its sibling. Write the
file once, after every entry is saved, and only when at least one entry lacked a uuid, which is the
condition `save_form_question` already applies to its options (`:429-431`).

### 3. Loading

**A `COURSE_CATEGORIES` phase before the Courses phase** in `save_content_to_db`
(`content_save.py:609-829`, phases at `:645`, `:651`, `:658`, `:664`, `:672`, `:679`, `:729`). The
loader groups every parsed item by `content_type` and saves the groups in a hard-coded phase order,
so a phase ahead of Courses is a guarantee rather than a sort. The whole function is
`@transaction.atomic`, so a half-categorised database cannot occur.

```python
def save_course_categories(item, site, base_path):
    """Save every CourseCategory declared in one file, order from list position."""
    relative_path = str(item.file_path.relative_to(base_path))
    categories = []
    written = []
    for index, entry in enumerate(item.categories):
        category = save_with_uuid(
            CourseCategory,
            entry,
            site,
            None,
            update_file=False,
            derive_slug=False,
            order=index,
            file_path=relative_path,
        )
        categories.append(category)
        written.append((index, category.id))

    if any(entry.uuid is None for entry in item.categories):
        update_file_with_category_uuids(item.file_path, written)

    return categories
```

One parsed item becomes many rows, which is the shape `save_form_question` uses for its options
(`content_save.py:400-433`), down to the `update_file=False`, the `base_path` of `None` and the bulk
write-back afterwards. An entry is a nested model with no `file_path` of its own, so the file's
relative path goes in through `extra_fields`, the same route `order` takes.

**`derive_slug` is a new keyword argument on `save_with_uuid`**, defaulting to `True`, so every
existing caller is untouched. It guards the two lines at `:267-270` that overwrite `slug` with
`slugify(title)` through `get_unique_slug`. Every other content type wants that, because its slug is
derived and nothing refers to it by name. A category's slug is authored and every course names it, so
deriving it would move the slug out from under every referencing course the moment somebody edited a
title. One default-preserving flag on the shared function beats a hand-written copy of its uuid
branch, which would drift from the original the first time either changed.

`description` is `str | None` in the schema and `blank=True, default=""` on the model.
`save_with_uuid` dumps with `exclude_none=True`, so an entry with no `description:` leaves whatever
is stored alone rather than clearing it. That is how every optional field on every other content
type already behaves: deleting the key does not delete the text, `description: ""` does.

**`save_course` resolves `dashboard_category` to an instance.** Add both new keys to the
`exclude_fields={"children"}` it already passes, and hand the resolved `dashboard_category` row in
through `extra_fields`, the same route `children`, `options`, `form`, `form_page` and `order` already
take. Look it up with `site=site` explicit, as `CourseCategory._base_manager.get(site=site,
slug=slug)`. A management command has no thread-local request, so `SiteAwareManager` filters nothing
there (`site_aware_models/models.py:117-129`) and a lookup that omits `site` would resolve against
the wrong site's row, or raise `MultipleObjectsReturned`, on a multi-site database. `_base_manager`
follows `get_unique_slug` (`site_aware_models/slugs.py:53-57`), which documents why: under an ambient
request `objects` also ANDs in that request's site, so a load passing any other site would find
nothing.

Resolve the shorthand here, once: an absent `dashboard_category` with exactly one entry in
`categories` resolves to that entry. `categories` is written from what the file declares either way,
so the file still describes what is stored.

**`categories` needs a post-save pass.** `save_with_uuid` feeds its fields into
`update_or_create(defaults=...)` (`:272-275`), and Django refuses direct assignment to the forward
side of a many-to-many, so a `categories` entry in `extra_fields` raises rather than saving. Write it
after the instance exists, with `course.categories.set(rows)`, in the same post-save pass that
resolves `children` into `ContentCollectionItem` rows (`content_save.py:788-805`), so both authored
reference lists are resolved in one place inside the existing `@transaction.atomic`. A course cannot
then survive a failed load carrying half its categories.

**Exclude `COURSE_CATEGORIES` from the child auto-discovery walk.** When a course or part declares
no `children:`, the walk adds *any* `.md`/`.yaml`/`.yml` file in its directory as a child, with no
content-type check at all (`content_save.py:743-748`). §4 rejects a category file inside a course
directory before a load, but `save_content_to_db` is also called directly, so add the content-type
check there too.

**The file wins on every field, including `order` and `show_on_dashboard`.** An admin edit lasts
until the next content load. Ordering is therefore authored, so two sites loading the same content
repo get the same ordering, and an admin edit is a temporary override rather than per-site
configuration. A category dropped from the file is not deleted; its row and its courses stay put
until a builder removes it. The load adds and updates, it does not prune.

**A course's category set is replaced by a reload, not merged into.** `set()` is a replace, so
dropping a slug from a course's `categories` and reloading removes that membership. It is the one
place where a load takes something away, so it is written down here. The `CourseCategory` row
survives; only this course's membership of it goes.

### 4. Validation

The check lives in `validate()` (`freedom_ls/content_engine/validate.py:301-352`), so all three
entry points report it: `content_validate`, `content_save`'s internal `validate(path)` call
(`content_save.py:838`), and the bundled offline validator. `content_validate` takes no site
argument and needs none, because the check is file against file.

**This is FLS's first cross-file check.** `validate()` today validates each file in isolation and
discards the parsed model. It must keep the parsed items so a second pass can resolve references,
because a category file appearing later in the sorted walk has to satisfy a course seen earlier.
Two passes, not one interleaved pass. Pass one collects the declared slugs with the file that
declared each, pass two resolves every slug each course names, in `categories` and in
`dashboard_category` alike, and checks the two against each other. Accumulate every error and report
them together, which is what `validate()` already does for per-file failures (`:330-352`), so an
author with five typos gets five lines rather than five runs.

Errors to raise:

| Condition | Error |
| --- | --- |
| A slug in a course's `categories` matches no declared slug | Names the file, quotes the bad slug and says which position in the list it came from, lists the declared slugs and the file declaring them, and says that adding a category is as valid a fix as correcting the typo |
| A course's `dashboard_category` matches no declared slug | The same message, naming the key rather than a list position |
| A course's `dashboard_category` names a slug absent from its own `categories` | Names both, and says the dashboard category has to be one the course belongs to. Adding the slug to `categories` is as valid a fix as changing the key |
| A course omits `dashboard_category` and declares two or more `categories` | Names the file and lists the candidates. Never a silent fall to the catch-all |
| A course carries the retired `category` key | Names the file and says to use `categories`, and `dashboard_category` when there is more than one. Raised by the schema override in §2 and reported through the same run |
| Two `COURSE_CATEGORIES` declarations in one repo, whether in two files or two `---` documents of one | Names both; the display order would otherwise be ambiguous, and the write-back in §2 counts on there being one |
| Two entries sharing a `slug` | Names the slug and the file |
| Two entries sharing a `uuid` | Names the uuid and both slugs. An entry copied without clearing its uuid would otherwise load as one row overwriting the other, and a category would vanish with nothing said |
| An entry whose `slug` is not a valid slug (letters, digits, hyphens and underscores) | Names the slug and the file. The slug is authored, not slugified (§3), and it becomes a `SlugField` value and a query-parameter name (§6), so nothing else constrains it |
| An entry whose `slug` is a reserved section slug (§5) | Names the slug and lists the reserved set |
| A `COURSE_CATEGORIES` file inside a course or part directory | Names the file and says to move it to the repo root |

A course with no `categories` and no `dashboard_category` is not an error and gets no message. That is
the catch-all. A course with exactly one category and no `dashboard_category` is not an error either;
it resolves. Build every message from the parsed file path the validator already carries, because
naming the wrong file is worse than saying nothing.

The worked message shape, following `save_with_uuid`'s "here is what you wrote, here is what is
valid" (`content_save.py:258-265`):

```
❌ Unknown category in courses/data-literacy/course.md
Content type: COURSE

  • Field: categories[1]
    Problem: no category is declared with this slug in this content repo
    Given value: 'tecnical'

    Categories declared in this repo (course_categories.yaml):
      start-here
      technical
      leadership

    Fix the slug, or add an entry to course_categories.yaml declaring it.
```

### 5. The dashboard

Section order for a signed-in learner with something in progress:

| # | Section | Notes |
| --- | --- | --- |
| 1 | Greeting | unchanged |
| 2 | Backend-contributed panels | unchanged |
| 3 | In progress | paginated |
| 4 | The first rendered category section | the site's headline group |
| 5 | Recommended courses | paginated |
| 6 | The remaining category sections | configured order, each paginated |
| 7 | Available courses | the catch-all, paginated, keeps "Browse all courses" |
| 8 | Coming soon | paginated |
| 9 | Learning history | paginated |

A signed-in learner with nothing in progress gets the same sections with In progress moved from
position 3 to between Coming soon and Learning history, where its existing "everything you're
signed up for is finished and waiting in your Learning History below" copy sits next to the history
it names. An anonymous visitor gets the hero in place of the greeting, and no In progress or
Learning history, as today.

Every section except In progress hides itself when it has nothing to show, which is what the
template already does. In progress keeps its two-branch empty state and its two `data-testid`s.

Headings go to sentence case: "In progress", "Recommended courses", "Available courses", "Coming
soon", "Learning history". Two of the five change.

**The discovery pool** is today's, meaning visible courses (`backend.filter_visible`) minus
registered courses minus recommended courses, with `excluded_ids` unchanged (`views.py:308-310`).
Split it into sections in this order:

1. Coming-soon courses go to Coming soon, whatever their category. Coming soon is what
   `is_coming_soon_for_display` says it is (`freedom_ls/course_access/overrides.py:21-28`):
   `visibility == COMING_SOON` with the visibility override off. The category sections and the
   catch-all page in the database (§7), so they apply that rule as a queryset filter, and the filter
   must read the override through `override_visibility_to_visible()`, never `Course.visibility`
   alone, or the existing visibility-preview override silently stops working.
2. Courses whose `dashboard_category` has `show_on_dashboard` true go to that category's section.
3. Courses whose `dashboard_category` has `show_on_dashboard` false go to Available courses,
   beside the uncategorised ones.
4. Courses with no `dashboard_category` go to Available courses.

**`Course.categories` is not consulted at any point in that split.** A course's other categories have
no effect on the dashboard, which is what keeps one course to one card in one section however many
categories it carries. A course whose `dashboard_category` is hidden lands in Available courses, not
in whichever of its other categories happens to have a section on screen.

No grouping rule may read `Course.access_config`, which is backend-private
(`content_engine/models/courses.py:37-49`). A rule that wants to tell free courses from gated ones
goes through `backend.get_access_badge`.

**Section identity.** Each section has a slug: the reserved built-ins `in-progress`, `recommended`,
`available`, `coming-soon` and `history`, plus one per category. The slug names the section's page
parameter. Keep `id="current-courses"`, `id="recommended-courses"`, `id="available-courses"` and
`id="learning-history"` on the existing wrappers, because returning learners' muscle memory and the
existing tests both depend on them.

**Ordering.** Every section needs a total order before it can be paginated at all.

| Section | Order |
| --- | --- |
| In progress | started courses first, most recently accessed first; then registrations with no progress, newest registration first; `slug` as the tie-breaker |
| Category sections, Available courses, Coming soon | `Course.Meta.ordering`, so alphabetical by title |
| Recommended courses | `RecommendedCourse.Meta.ordering = ["-created_at"]`, with the course slug as the tie-breaker |
| Learning history | completion date, most recent first |

Recommended courses needs its tie-breaker for the same reason every other section does.
`RecommendedCourse.created_at` is `auto_now_add`, and one form submission that recommends four
courses writes four rows inside one transaction, so `-created_at` alone is not a total order.
`_visible_recommendations` (`views.py:159-178`) returns a Python list rather than a queryset, so the
sort and the paging both happen in Python, as they do for In progress.

The In progress rule is the one that carries weight. `get_current_courses`
(`learner_interface/utils.py:825-853`) includes registrations with no progress at all, so a learner
bulk-registered onto a cohort's courses currently gets those cards mixed in with the one course they
are actually reading. Without started-before-unstarted, pagination will faithfully bury the course
the learner came back for on page two. It is a Python sort, because the list is assembled after
per-learner progress work. Express it as one key tuple, so the bucket boundary cannot be crossed by
accident:

```python
def _in_progress_sort_key(course: Course) -> tuple[int, float, str]:
    if course.started_at is not None:
        reference_time = course.last_accessed_time or course.started_at
        return (0, -reference_time.timestamp(), course.slug)
    if course.registered_at is not None:
        return (1, -course.registered_at.timestamp(), course.slug)
    return (2, 0.0, course.slug)
```

`started_at`, not `last_accessed_time`, is the field that means started
(`learner_progress/models.py:139`). Both are written in one save on first content access
(`views.py:704-707`), and the comment at `models.py:134-137` forbids reading either of these
timestamps for another. `registered_at` is `CourseProgress.created_at`, which `models.py:134`
documents as the registration date. `get_course_registrations` (`utils.py:353-359`) returns courses
carrying no registration date of their own, and a course may be registered through either
`LearnerCourseRegistration` or `CohortCourseRegistration`. A registered course with no record at all
is already possible (`utils.py:840-843`) and sorts last.

`get_current_courses` therefore stamps `started_at`, `last_accessed_time` and `registered_at` off
the resolved record alongside the `progress_percentage` it already stamps, and
`get_completed_courses` (`utils.py:804-822`) stamps `completed_time` and sorts by it descending.

### 6. Pagination

**Page state is one namespaced query parameter per section**, `page_<section-slug>`, written only
when that section is not on page one. A learner paging one section produces one short parameter, not
one per section.

Build each link by copying the incoming querydict and touching only its own key, so an unrecognised
parameter passes through untouched with no allowlist to maintain. A bookmark taken before a category
was renamed, or a stray UTM tag, both survive:

```python
def section_page_href(request: HttpRequest, param_name: str, page_number: int) -> str:
    query = request.GET.copy()
    if page_number <= 1:
        query.pop(param_name, None)
    else:
        query[param_name] = str(page_number)
    encoded = query.urlencode()
    return f"{request.path}?{encoded}" if encoded else request.path
```

This replaces the two-paginator `join_query`/`extra_params` pattern
(`freedom_ls/base/templatetags/pagination_tags.py`,
`educator_interface/templates/educator_interface/partials/course_progress_panel.html:161-184`),
which makes every control carry every other paginator's page number explicitly and does not survive
six sections.

Read the page with `Paginator.get_page()`, never `page()`. `get_page` clamps a non-integer, negative,
zero or out-of-range value to a valid page and never raises, which is right for a public
home page. A bad page number is not a validation error, so return 200, not 422.

**A new lightweight control**, at
`freedom_ls/learner_interface/templates/cotton/course-section-pagination.html`. No page numbers,
just previous and next, with the position stated in text ("1 to 3 of 12"). A numbered paginator
in every section down a dashboard is more controls than cards. `<c-pagination>`
(`freedom_ls/base/templates/cotton/pagination.html`) belongs to the educator tables and is left
alone. The new component is its sibling and matches its contract, taking a `page_obj`, a base URL, a
target id and a page parameter name. Cotton names resolve flat across apps, so this name must not
collide with `pagination`.

**Accessibility** is where this pattern usually fails. `research_dashboard_pagination.md` §4 holds
the full checklist and the WCAG references. The items that matter most:

- **Both controls always render**, disabled in place at the boundaries via `aria-disabled="true"`
  plus suppressed activation, never omitted and never the `disabled` attribute. `<c-pagination>`
  omits them today (`{% if page_obj.has_previous %}`), which for a swapped grid means the control
  the learner just pressed can vanish as a result of pressing it, leaving nothing to return focus to.
- **The swap boundary sits below the section's `<h2>`**, so the heading survives as a focus target
  and heading order cannot break. Target an inner wrapper holding the grid, the position text and
  the controls.
- **Focus** returns to the pressed control in the newly rendered section. If it is now at a
  boundary, focus moves to the section's `<h2>` with `tabindex="-1"`. Never let focus fall to
  `<body>`. The htmx `focus-scroll` and `show:` swap modifiers are about scrolling and do not solve
  this.
- **The position change is announced** through a single page-level
  `role="status" aria-atomic="true"` region in `dashboard.html`, updated out of band with
  `hx-swap-oob="true"`. A live region inserted *by* the swap is frequently not announced, because
  screen readers watch regions that already existed. This is the only legitimate OOB swap here.
- **Each section's controls carry a name saying which section they belong to.** Six identical
  "Next" links on one page defeat anyone navigating by link list. Wrap them in a `<nav>` with a
  unique `aria-label`.
- Do not scroll after the swap, and do not pad a short final page with empty cards.

**The endpoint is the dashboard itself.** The control's `href` and its `hx-get` are the same URL,
and `dashboard` branches on `request.headers.get("HX-Request") == "true"` to return one section's
partial instead of the page. One URL per page state keeps the `href` a real link that a crawler or a
no-JS visitor can follow to a complete page, and raises no duplicate-content question. On an HTMX
request, build **only** the requested section. The whole point of the swap is not paying for the
other eight.

**Templates.** `learner_interface/templates/learner_interface/partials/course_list.html` already
holds each section as a `{% partialdef %}` with a shared `section-heading` and `course-grid`
(`:8-20`). Extend that rather than introducing stand-alone files per section. A category section
reuses `course-grid` and `course_card.html` verbatim through the existing
`{% with courses=... %}{% partial course-grid %}{% endwith %}` idiom; `course_card.html` is a plain
include driven by ambient context, not a cotton component. The heading row gains the description on
the left, and the position text, controls and "Browse all" link on the right, per `image.png`. Reuse
the `<c-button variant="link" size="small" icon_right="next">` shape already used for "Browse all
courses" (`course_list.html:76-82`). A category section's "Browse all" goes to
`learner_interface:courses`, the flat catalogue.

### 7. Cost

The dashboard is expensive per registered course. `_annotate_registered_courses`
(`views.py:181-210`) calls `backend.get_access` and `_annotate_next_up` per course, and
`_annotate_next_up` builds the full player index through `get_course_index`, roughly fifteen queries
each, unbounded, with no test pinning it.

**Sort, then paginate, then annotate.** Annotating a page instead of the whole list is where the win
is. Annotating first and paginating after would keep the cost and gain nothing.

**The category sections and the catch-all page in the database.** With the foreign key, a
category's courses are a real queryset, so those sections get `COUNT(*)` plus `LIMIT`/`OFFSET`
instead of loading every course on the site into memory the way `_available_courses` does today,
iterating the whole visible-course queryset and only then breaking at three (`views.py:262`,
`:280-281`). In progress and Recommended courses cannot page in the database, because both are
Python lists assembled after per-learner work, so paging them saves rendering and per-course
annotation rather than queries.

Declare `select_related("dashboard_category")` once, on a shared queryset helper every discovery
section builds from, rather than at five call sites.

**Nothing prefetches `categories`.** No dashboard rule reads it, so the many-to-many adds no query and
no join to this page. If a later change makes the dashboard read it, that change owns the
`prefetch_related` and the query-count bound that goes with it.

## Testing

**Ordering.** In progress puts a started course ahead of an unstarted one whatever order the
registrations were created in; within the started bucket, most-recently-accessed first; within the
unstarted bucket, newest registration first. Learning history is completion-date descending.
Category sections, the catch-all and Coming soon are alphabetical by title. A course never appears
on two pages of one section, and never on none.

**Pagination.** A section with four courses renders three and reports "1 to 3 of 4". Page two
renders the fourth. `page_<slug>=abc`, `=0`, `=-1` and `=9999` all render a valid page with a 200.
An unrecognised `page_*` parameter is ignored and does not raise. A link built for one section
preserves every other section's parameter and omits its own when the target is page one. The HTMX
request returns one section rather than the page, and the same URL without the `HX-Request` header
returns the whole page. Recommended courses pages like the rest: four recommendations render three
and a working next. It gets its own case because it is the one section whose rows are
`RecommendedCourse` objects rather than `Course` objects, so it is the one a shared helper is most
likely to miss.

**Accessibility.** Both controls are present and `aria-disabled` at the boundaries. Each section's
`<nav>` has a unique `aria-label`. The `<h2>` is outside the swapped fragment. The page carries one
`role="status"` region and the fragment updates it out of band.

**Grouping.** A course lands in its `dashboard_category`'s section and nowhere else. A course with no
`dashboard_category` lands in Available courses. A course whose `dashboard_category` has
`show_on_dashboard: false` lands in Available courses, that category renders no section, and the
course appears in none of its other categories' sections while those are on screen. A course in
three categories with an explicit `dashboard_category` renders exactly one card, in that section, and
in none of the other two. A course with one category and no `dashboard_category` lands in that
category's section. A coming-soon course lands in Coming soon whatever its categories, and does so
through the override-aware rule, proved by a test with `OVERRIDE_COURSE_VISIBILITY_TO_VISIBLE` set.
Category sections render in configured order. Fifty categories render fifty sections. A category
with no visible course renders nothing. One coming-soon course renders a Coming soon section.

**The unconfigured default.** With no `course_categories.yaml`, the dashboard renders In progress,
Recommended courses, Available courses with three courses and its "Browse all courses" link, and
Learning history, which is the same sections in the same order as today.

**Validation.** A course naming an undeclared slug in `categories` fails `content_validate`, and the
message names the file, quotes the slug and lists the declared slugs. The same for an undeclared
`dashboard_category`. A `dashboard_category` outside that course's own `categories` fails. Omitting
`dashboard_category` with two or more categories fails and names the candidates. The retired
`category` key fails with a message naming both replacements. All of them fail `save_content_to_db`
before any row is written. Five bad courses produce five messages in one run. A category file
appearing after the courses that reference it validates. Two `COURSE_CATEGORIES` declarations,
duplicate slugs, duplicate uuids, an invalid slug, a reserved slug and a category file inside a
course directory each fail with their own message. Omitting both new keys passes, and so does one
category with no `dashboard_category`.

**Loading.** A first load writes a uuid into every entry in place, leaving the other entries'
formatting and the rest of the file alone. An authored slug survives that load unchanged, and
survives a title edit unchanged, which is the regression `derive_slug=False` exists to prevent.
Renaming an entry's slug while its uuid stays put renames the row rather than creating a second one,
and every course still naming the old slug then fails validation. `order` follows list position and
changes when the list is reordered. A second load of an unchanged declaration adds no rows and leaves
`course_categories.yaml` byte-identical on disk. `save_content_to_db` called directly on a category
file loose inside a course directory does not adopt it as a course child. The single-category
shorthand resolves, so a course declaring one category and no `dashboard_category` loads with both
set. Dropping a slug from a course's `categories` and reloading removes that membership, because
`set()` replaces. A load that fails after the course phase leaves no course carrying a partial
category set.

**Two sites, one database.** Two sites with their own declarations, reusing each other's slugs
and titles but carrying different uuids, get their own rows, and site B's dashboard shows only site
B's. Loading one declaration into both sites fails on the duplicate primary key, the way
every other content type already fails. Pin that limit with a test naming it, so the next person to
try it reads an assertion rather than a stack trace.

**Cost.** A `django_assert_max_num_queries` bound on the dashboard, with a learner registered for
ten courses, proving the query count no longer grows with registration count past the page size.
Derive the number from a passing run with the intended `select_related` in place, not from the
current baseline. Pin In progress and a category section separately, so a failure says which
regressed. The count does not change when a course carries five categories rather than one, which is
what proves the many-to-many costs this page nothing.

**Existing tests that change.** `test_dashboard_sorts_each_course_into_its_own_section`
(`test_dashboard_view.py:148`, exact pk lists) and `test_dashboard_available_capped_at_three`
(`:211`) both assert against today's unordered, hard-capped behaviour.
`test_listing_visibility.py:303` and `:366` assert coming-soon courses on the dashboard and must
look in the Coming soon section. The `courses` fixture (`tests/conftest.py:43-53`) creates exactly
three courses. `test_anonymous_home_page.py` and `test_course_cards.py` assert the section ids and
card markup that must not move.

## Documentation and downstream

**Deliberate changes to today's page**, beyond category grouping. Each needs to reach the product
docs and the upgrade note, because each is visible on a site that configures nothing:

- Every section now shows at most three courses and pages to the rest, where In progress,
  Recommended courses and Learning history were unbounded.
- Coming-soon courses move out of Available courses into their own section.
- Section headings normalise to sentence case, so "In Progress" and "Recommended Courses" change.
- In progress, Available courses and Learning history gain a deterministic order where they had
  none.

say that `Course.category` is replaced by `categories` and `dashboard_category`, and that the
migration **drops the old column without preserving its values**, so an operator with data in that
column must capture it before migrating. It must then say what the manual fix is: author a
`course_categories.yaml`, add `categories:` to the course files with `dashboard_category:` where a
course has more than one, reload. And it must state the trap, which is that a site repopulating the
rows by hand without adding matching declarations will find its next routine `content_save` failing
every course that names one. It must also say that the retired `category:` key now fails validation
rather than being ignored, so a content repo carrying it will not load until the key is changed.
`spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/upgrade_notes.md` is the closest
model, the most recent note documenting a breaking model change with no automatic path for existing
data.

**Author-facing documentation.** `claude_plugins/fls-content/skills/content-types/SKILL.md` opens
with "FLS has **eight** content types" and a table of all eight, so a ninth means the count, a table

`claude_plugins/fls-content/skills/conventions/SKILL.md:55-62` lists the files identified by name

`docs/product/content-editing-workflow.md:28-42` carries the same content-type table and needs the

The category page does not contradict the shared field table at `SKILL.md:40`, which tells an author
that every content file carries a `uuid` written by `content_save` on first run. This one does too.
What the page has to add is where the uuid goes: one per entry rather than one for the file, never

## Open questions

**Are there downstream installations with data in `Course.category`?** Nothing in this repository
populates it. No demo course file sets it, `CourseFactory` does not, and the only writer is one QA
seed command. The number of affected installations may well be zero, which is what makes "an upgrade
note, not a command" affordable. An operator who knows otherwise should say so before the migration
lands. Rejecting the retired key rather than ignoring it raises the stakes slightly, because such an
installation's content repo stops loading until the key is changed, which is the intended trade: a
failed load that says what to do beats a successful load that quietly drops every course into the
catch-all.

## Success criteria

- `course_categories.yaml` declaring three categories, loaded into a site whose courses name them,
  renders three category sections on the dashboard in list order, and reordering the list and
  reloading reorders the sections.
- Setting `show_on_dashboard: false` on a category removes its section and moves its courses into
  Available courses.
- A course declaring three categories with an explicit `dashboard_category` renders exactly one card,
  in that category's section.
- A course naming a slug no category declares fails `content_validate` with a message naming the
  file, the slug and the declared set, and fails `content_save` before any row is written.
- Editing a category's `title` and reloading leaves its `slug` unchanged and every course still in
  that section, and leaves `course_categories.yaml` unmodified on disk, the first load having
  already written its uuids.
- Two sites declaring the same slugs and titles in their own files, with different uuids, get their
  own rows in one database, and each dashboard shows only its own.
- No paginated section renders more than three cards, each shows its position as text and a working
  previous and next, and every control works with JavaScript disabled.
- A learner registered for ten courses sees three In progress cards, most-recently-accessed first,
  and the dashboard's query count does not grow with the eleventh registration.
- On a site with no `course_categories.yaml`, the dashboard shows the same sections in the same
  order with the same three catch-all courses as before this change.
- Two dashboard renders with unchanged data produce the same order.
