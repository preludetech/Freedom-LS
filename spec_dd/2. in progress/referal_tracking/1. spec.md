# Spec: tracking where learners come from

## 1. Purpose

FLS records nothing about how a learner found it. An operator running adverts cannot tell which of
them produced a signup, and so cannot tell which campaign is worth spending more on.

This work adds two read-only records. `SignupAttribution` holds one row per signed-up `User`,
written once on the signup POST, describing the visit that brought that person in. `FirstTouchCount`
is a daily tally of arrivals per attribution key, the denominator the attribution rows lack: signups
over first touches, both grouped by campaign, is a conversion rate.

The approach is settled in `idea.md` and not reopened here: first touch only, a signed first-party
cookie as the only durable store, nothing written to the session on a landing, capture on the signup
POST rather than at email confirmation, the row keyed on `User` rather than `Learner`, advert codes
as free text with no `Advert` table, and no bot filtering.

## 2. Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| `SignupAttribution` | coined | The write-once row recording where one signed-up `User` came from. |
| `FirstTouchCount` | coined | The daily tally of first touches per attribution key. Holds no personal data. |
| **advert code** | coined | The opaque identifier naming one advert. Free text, no table. |
| **first touch** | coined | The visitor's first landing within the cookie's 90 days. Every frozen field on the row describes that one visit. |
| **attribution key** | coined | The six-value tuple a `FirstTouchCount` row counts: advert code plus the five UTM values. |

"Referral" and "referrer code" are not used in this spec, despite the app being named
`referral_tracking`. Those words belong to the deferred partner-`Organisation` work (§8). Nothing
here resolves a code to an `Organisation`.

## 3. Scope

**In.** A new `freedom_ls/referral_tracking` app holding both models, the capture middleware, the
cookie, the signup-time write, two read-only admins with a CSV export action, and one setting group.

**Out.** Referrer codes for partner organisations. A per-`Site` switch for capture. Erasure and
anonymisation beyond what the `User` cascade gives. Bot filtering. Any `Advert` table. Any
dashboard, report or conversion-rate view: the two changelists and their export are the whole
interface. Any question needing a per-visitor landing record, listed in `idea.md` under "What this
deliberately cannot answer". Joining forward from the row to course registration and progress stays
possible through `user`, so the row caches none of it.

## 4. Decisions

- **`referral_tracking` is an ordinary FLS app**, not the extractable `referral-link-tracker` that
  `docs/app_conventions.md` names. Both models are `SiteAwareModel`, and the app imports from
  `site_aware_models` and `base`. An extractable app could import neither and would have no `site`
  to key the tally on. If that planned app is meant to be this one, this spec changes; until someone
  says so, the convention doc's entry is read as naming a different app.
- **The new app's runtime imports are `base` and `site_aware_models`, and `accounts` imports it.**
  The models FK to `settings.AUTH_USER_MODEL` as a string, and only the tests import from
  `accounts` (its `UserFactory`).
- **The row is written from `SiteAwareSignupForm.custom_signup()`**, the hook that writes
  `LegalConsent` and the only place holding both the cookie-bearing request and the new user.
  Accounts created any other way, by admin, management command or data import, get no row.
- **The attribution key is the advert code plus all five UTM values.** Slicing per creative rather
  than only per campaign is worth the key space, and the overflow row absorbs what the cap cannot.
- **Every captured field has one cap, applied identically in the cookie payload and the column.** The
  row is written from whatever the cookie carried, so a second tier would document a length the
  column can never reach.
- **`_ga`, `_fbp` and `_fbc` are read from the signup request whenever present**, with no setting
  gating them. On a deployment running no analytics they are blank.
- **`utm_medium` is free text**, trimmed, lower-cased and truncated, with no vocabulary check. The
  row cannot be reprocessed, so a closed set would bake a silent bucketing error in permanently where
  free text leaves a visible typo.
- **`has_view_permission` is not overridden** on either admin. Django's default gates read access on
  a granted permission. An `is_staff` check would hand every staff member a table of personal data
  regardless of what they were granted.
- **Nothing swallows exceptions.** Capture sanitises and truncates before every write. The two
  expected failures, an invalid cookie (§5.4) and a concurrent insert of the same tally row (§5.3),
  are caught by type and given a defined outcome.

### 5.2 `SignupAttribution`

`freedom_ls/referral_tracking/models.py`. Subclasses `SiteAwareModel`
(`freedom_ls.site_aware_models.models`), as `LegalConsent` does.

```python
user = models.OneToOneField(
    settings.AUTH_USER_MODEL,
    on_delete=models.CASCADE,
    related_name="signup_attribution",

```

`CASCADE` matches `LegalConsent.user`: deleting an account removes the row, and that is the only
erasure path this work ships (§8).

Frozen at first landing, carried in the cookie:

| Field | Type | Cap |
| --- | --- | --- |
| `advert_code` | `CharField(blank=True)` | 64 |
| `utm_source` | `CharField(blank=True)` | 64 |
| `utm_medium` | `CharField(blank=True)` | 64 |
| `utm_campaign` | `CharField(blank=True)` | 255 |
| `utm_content` | `CharField(blank=True)` | 128 |
| `utm_term` | `CharField(blank=True)` | 128 |
| `gclid` | `CharField(blank=True)` | 128 |
| `gbraid` | `CharField(blank=True)` | 128 |
| `wbraid` | `CharField(blank=True)` | 128 |
| `fbclid` | `CharField(blank=True)` | 256 |
| `landing_path` | `CharField(blank=True)` | 255 |
| `referer` | `CharField(blank=True)` | 255 |
| `raw_query` | `CharField(blank=True)` | 512 |
| `first_seen` | `DateTimeField()` | n/a |

Taken from the signup request itself:

| Field | Type | Cap |
| --- | --- | --- |
| `ga_cookie` | `CharField(blank=True)` | 64 |
| `fbp_cookie` | `CharField(blank=True)` | 64 |
| `fbc_cookie` | `CharField(blank=True)` | 320 |
| `client_ip` | `GenericIPAddressField(null=True, blank=True)` | n/a |
| `user_agent` | `CharField(blank=True)` | 512 |
| `signed_up_at` | `DateTimeField(auto_now_add=True)` | n/a |

`landing_path`, `referer` and `raw_query` are `CharField`, never `URLField`. The point of those
fields is to record whatever arrived, and `URLField`'s validator would reject a malformed value
rather than store it.

`gbraid` and `wbraid` are in because Safari's Private Browsing strips `gclid` and `fbclid` from URLs
and those two exist to survive it. `msclkid`, `ttclid` and `li_fat_id` stay out until someone runs
those platforms.

`signed_up_at` exists alongside `user.date_joined` so `date_hierarchy` can drill down by signup date
without a join on every changelist load. `first_seen` is the landing time, which with a 90-day cookie
is often a different month.

`Meta.indexes`: `(site, signed_up_at)`, `(site, utm_source)`, `(site, utm_campaign)`.
`Meta.ordering = ["-signed_up_at"]`.

`save()` mirrors `LegalConsent.save()` (`freedom_ls/accounts/models.py:198`): raise `ValueError` on an
update, distinguished with `self._state.adding` because `SiteAwareModel`'s UUID pk is populated before
the row exists. Carry the same docstring caveat. The guard does not cover `QuerySet.update()`, which
is why the admin is registered read-only as a second layer.

### 5.3 `FirstTouchCount`

Also `SiteAwareModel`. Fields: `day` (`DateField`), the six attribution-key columns with the same
caps as above, `is_overflow` (`BooleanField(default=False)`), `key_hash` (`CharField(max_length=64)`)
and `count` (`PositiveIntegerField(default=0)`).

```python
class Meta:
    constraints = [
        models.UniqueConstraint(
            fields=["site", "day", "key_hash"], name="unique_first_touch_count"
        ),
    ]
    indexes = [
        models.Index(fields=["site", "utm_source"]),
        models.Index(fields=["site", "utm_campaign"]),
    ]
```

The constraint is on `key_hash` rather than the six key columns because six text columns at their
full caps can exceed Postgres's btree index row limit under multi-byte input, and a fixed
64-character digest cannot. The six columns stay as plain columns so the admin can filter and display
them. `site` is named explicitly, following `SiteSignupPolicy.Meta.constraints`
(`freedom_ls/accounts/models.py:155`). No admin form ever validates this constraint, since both
admins are read-only, so the `ConstraintValidationFormMixin` that `docs/app_conventions.md` pairs
with site-scoped constraints is not needed.

`day` comes from `timezone.localdate()`, so days follow the project's `TIME_ZONE`.

The digest:

```python
KEY_SEPARATOR = "\x1f"
OVERFLOW_SENTINEL = "\x00overflow"

def attribution_key_hash(*values: str) -> str:
    return hashlib.sha256(KEY_SEPARATOR.join(values).encode("utf-8")).hexdigest()
```

Capture strips all control characters (§5.4), so no real key can contain `\x1f` or `\x00`. The
separator cannot be forged into a colliding key, and the overflow row's sentinel cannot collide with
a real one.

`count` carries `help_text` saying that the figure counts cookie mints, that bots and link unfurlers
inflate it, and that it is for comparing campaigns against each other rather than as an absolute
count. It renders on the read-only detail view, and it is the only place the admin states the caveat.

The increment, in `freedom_ls/referral_tracking/counters.py`:

```python
def increment_first_touch(
    *, site: Site, day: date, key_hash: str, is_overflow: bool = False, **key_fields: str
) -> None:
    updated = FirstTouchCount.objects.filter(
        site=site, day=day, key_hash=key_hash
    ).update(count=F("count") + 1)
    if updated:
        return
    if not is_overflow and (
        FirstTouchCount.objects.filter(site=site, day=day, is_overflow=False).count()
        >= config.REFERRAL_TRACKING_FIRST_TOUCH_KEY_CAP
    ):
        increment_first_touch(
            site=site,
            day=day,
            key_hash=attribution_key_hash(OVERFLOW_SENTINEL),
            is_overflow=True,
        )
        return
    try:
        with transaction.atomic():
            FirstTouchCount.objects.create(
                site=site, day=day, key_hash=key_hash, is_overflow=is_overflow,
                count=1, **key_fields,
            )
    except IntegrityError:
        FirstTouchCount.objects.filter(
            site=site, day=day, key_hash=key_hash
        ).update(count=F("count") + 1)
```

The update runs first so the cap only applies to a key that would be new today. The overflow row
has six blank key columns and is excluded from its own count.

The nested `transaction.atomic()` matters. A failed `INSERT` leaves the connection unusable until
something rolls it back to a savepoint, so without it the fallback `update()` would raise
`TransactionManagementError` instead of recovering.

The cap is soft. Two concurrent requests carrying two novel keys can both count `cap - 1` under
`READ COMMITTED` and both create, landing a row past the cap. Closing that needs a per-day row lock
on every mint, which is the wrong price for an exact ceiling on a comparative number.

### 5.4 Capture

`freedom_ls/referral_tracking/capture.py`.

The tracked parameters, any one of which triggers a mint:

```python
TRACKED_PARAMS = (
    "advert_code",
    "utm_source", "utm_medium", "utm_campaign", "utm_content", "utm_term",
    "gclid", "gbraid", "wbraid", "fbclid",
)
```

`advert_code` is the query parameter name as well as the field name. `ref` is not used; it is
reserved for the deferred referrer-code work.

Sanitisation, in this order, for every captured value:

1. **Do not decode again.** `request.GET` is already fully decoded. A second `unquote()` corrupts a
   legitimate `%2B` and is itself a way to smuggle characters past a filter that only inspects the
   once-decoded form.
2. **Strip `\x00` to `\x1F`, and `\x7F`.** The null byte matters most: psycopg raises a plain
   `ValueError` before the value reaches Postgres, which 500s the request rather than surfacing as a
   catchable database error.
3. **`unicodedata.normalize("NFC", value)`.** `NFC`, not `NFKC`, which also collapses compatibility
   variants that someone may have meant.
4. **`.strip()`.** Leading and trailing only; internal whitespace is meaningful.
5. **`.lower()` on `utm_source` and `utm_medium` only.** Plain `.lower()`, not `.casefold()`.
6. **Truncate to the field's cap**, last, because normalisation changes length.

Where a parameter appears twice in one URL, Django's `QueryDict` last-value-wins applies.

`landing_path` is `request.path`; `referer` is `request.headers.get("Referer", "")`; `raw_query` is
`request.META.get("QUERY_STRING", "")`. All three go through steps 2 to 4, and step 6.

The cookie payload is compact JSON with short keys, UTF-8 encoded, then URL-safe base64, then
`response.set_signed_cookie(...)`. The base64 step keeps the value token-safe so `SimpleCookie` does
not quote-escape the JSON and inflate it. With the caps in §5.2 an all-ASCII worst-case payload is
around 3.3KB signed, inside the 4096-byte cookie limit. Multi-byte values can push a worst case past
that limit, and a browser drops an oversize cookie without saying so. The cost is bounded: that
visitor's signup records as direct while the tally has already counted the touch.

Cookie attributes: `salt="freedom_ls.referral_tracking"`, `max_age` from the setting, `httponly=True`,
`samesite="Lax"`, `secure=settings.SESSION_COOKIE_SECURE`, and no `domain`, so the cookie is
host-only. An FLS `Site` is one domain.

Reads pass `max_age` explicitly so the 90-day boundary is enforced server-side from the signed
timestamp rather than trusted to the browser. `BadSignature`, which covers its subclass
`SignatureExpired`, is caught and treated exactly as "no cookie present", and so is an unparseable
payload. A tampered, stale or corrupted cookie is routine, and every one of those cases wants the
same behaviour.

### 5.5 Middleware

`AttributionCaptureMiddleware` in `freedom_ls/referral_tracking/middleware.py`, following the shape of
`freedom_ls/site_aware_models/middleware.py`. Added to `MIDDLEWARE` in `config/settings_base.py:147`
immediately after `freedom_ls.site_aware_models.middleware.CurrentSiteMiddleware`, so the site
thread-local is populated for the whole of the new middleware's work, including its response phase.

Order of checks, chosen so an untracked request does no work at all:

1. Not a `GET` → return.
2. No `TRACKED_PARAMS` key in `request.GET` → return. Ordinary traffic stops here, having read a dict.
3. A valid signed cookie already present → return. No overwrite, no tally. First touch stays frozen
   here.
4. `get_cached_site(request)` is not a `Site` instance → return. A rejected Host resolves to
   `UnknownSite`, which is not a row.
5. Parse and sanitise, set the signed cookie on the response, and increment the tally.

Steps 1 to 3 touch no database. Step 4 is the first query, on the mint path only, and is served from
Django's site cache after the first request in a process.

On a response that mints a cookie, and only then:

- `patch_vary_headers(response, ["Cookie"])`, mirroring what `SessionMiddleware` already does.
- `patch_cache_control(response, private=True, no_store=True)`.

`Vary` alone is not enough. A shared cache that ignores it would bake one visitor's signed cookie
into a cached response and serve it to everyone who follows, attributing their signups to the first
visitor's campaign. FLS ships no cache middleware, but it is installed into projects that may front
it with a CDN.

### 5.6 The signup write

In `SiteAwareSignupForm.custom_signup()`, `freedom_ls/accounts/forms.py:133`, after the existing
`LegalConsent` loop and outside its `transaction.atomic()` block, so an attribution failure cannot
roll back recorded consents. Reuse the `ip` local already computed there rather than calling
`get_client_ip` a second time.

The read of `_ga`, `_fbp` and `_fbc` is `request.COOKIES.get(name, "")`, passed through the same
sanitisation as every other captured value (§5.4 steps 2 to 4 and 6), so truncated to the caps in
§5.2. `user_agent` is `request.headers.get("User-Agent", "")`, sanitised the same way as the frozen
text fields.

Where the cookie is absent, expired or unreadable, the row is still written: `utm_source="direct"`,
`utm_medium="none"`, every other frozen field blank, and `first_seen` set to the signup time. That
makes "we have no idea where this person came from" a value that filters and counts like any other
channel instead of a column of nulls indistinguishable from a capture bug. A crafted
`?utm_source=direct` is stored identically, and is not worth distinguishing.

Direct signups have no counterpart in `FirstTouchCount`, because the tally only increments when a
cookie is minted. They have no denominator.

### 5.7 Admin

`freedom_ls/referral_tracking/admin.py`. Both admins subclass `SiteAwareModelAdmin`
(`freedom_ls/site_aware_models/admin.py:15`) and are read-only exactly as
`LegalConsentAdmin` (`freedom_ls/accounts/admin.py:64`) is: `readonly_fields` covering every field,
plus `has_add_permission`, `has_change_permission` and `has_delete_permission` all returning `False`.

`SignupAttributionAdmin`:

- `date_hierarchy = "signed_up_at"`
- `list_display = ["user", "advert_code", "utm_source", "utm_medium", "utm_campaign", "first_seen", "signed_up_at"]`
- `list_select_related = ["user"]`
- `list_filter = ["utm_source", "utm_medium", "utm_campaign"]`
- `search_fields = ["user__email", "utm_campaign", "advert_code"]`

Click identifiers, the three ad-cookie values, `client_ip` and `user_agent` are near-unique per
visitor. They appear on the detail view and in the export, never in a filter.

`FirstTouchCountAdmin`:

- `date_hierarchy = "day"`
- `list_display = ["day", "advert_code", "utm_source", "utm_medium", "utm_campaign", "utm_content", "utm_term", "is_overflow", "count"]`
- `list_filter = ["utm_source", "utm_medium", "utm_campaign", "is_overflow"]`
- `search_fields = ["utm_campaign", "advert_code"]`

`list_filter` uses Django's default `AllValuesFieldListFilter`, backed by the indexes above, rather
than a cached `SimpleListFilter` sourced from `FirstTouchCount`. The tally accumulates daily and is
the larger table at any realistic volume, so sourcing choices from it would cost more, not less.

### 5.8 CSV export

`freedom_ls/referral_tracking/exports.py`, registered as an `@admin.action` on both admins. FLS has
no existing export to inherit from and `django-import-export` is not a dependency; the
`unfold.contrib.import_export` entry in `INSTALLED_APPS` is only Unfold's styling for a package that
is not installed.

```python
FORMULA_TRIGGERS = ("=", "+", "-", "@", "\t", "\r")

def escape_csv_formula(value: str) -> str:
    """Stop a cell being executed as a formula when the CSV is opened."""
    if value and value[0] in FORMULA_TRIGGERS:
        return f"'{value}"
    return value
```

Apply it to every exported value and to no header. `utm_campaign`, `advert_code`, `landing_path`,
`referer` and `raw_query` are all typed by whoever crafted the URL, and the spreadsheet a human opens
is this feature's only consumer.

Build the rows with `csv.writer` at its default `QUOTE_MINIMAL`, never by joining strings, so an
embedded separator or quote needs no handling of its own. Prefix the body with `codecs.BOM_UTF8` so
Excel on Windows detects UTF-8, write timestamps ISO 8601, and walk the queryset with `.iterator()`.

The export covers every field on the model, including the ones the changelist omits. Django's
"select all N across pages" gesture already hands the action the full filtered queryset via
`select_across`, so exporting a whole filtered set needs no special-casing.

The action takes no `permissions=` argument: anyone who can view the changelist can export it.

## 6. Testing

`freedom_ls/referral_tracking/tests/`. Use `django_assert_num_queries`, `time_machine` for frozen
time, plain `django.test.Client`, and the project-root `mock_site_context` / `site` fixtures
(`freedom_ls/conftest.py:136`, `:102`). Add a `SignupAttributionFactory(SiteAwareFactory)` following
`LegalConsentFactory` (`freedom_ls/accounts/factories.py:74`).

**Middleware.** A cookie is set on a GET carrying a tracked parameter, with `HttpOnly` and
`SameSite=Lax`; no cookie is set on a GET carrying none; a second landing inside the window leaves the
cookie byte-identical; the cookie's `max-age` is 90 days; a forged cookie value is treated as absent
rather than raising; a minting response carries `Vary: Cookie` and
`Cache-Control: private, no-store`. The zero-query claim for an untracked GET is tested on the
middleware alone, instantiated around a stub `get_response`, because the full stack's session,
authentication and view queries would swamp the assertion.

**Sanitisation.** A value containing a null byte is stored, stripped, without raising. Control
characters are removed. `utm_source=Facebook` stores as `facebook` while `utm_campaign=Spring Sale`
keeps its case. An over-length value is truncated, not rejected. A duplicated parameter takes the
last value. A value already containing `%2B` is not decoded twice.

**Signup write.** A signup after a tracked landing records the campaign. A signup with no prior
landing records `direct`/`none` and a `first_seen` equal to the signup time. Email confirmation from
a fresh `Client()`, a different browser with no cookie jar, leaves the row unchanged; that is the
regression test for capturing on the POST at all. A second `save()` on an existing row raises
`ValueError`. Deleting the user deletes the row.

**Tally.** A mint increments the row for its key. A second visitor on the same key increments the same
row rather than creating one. A distinct key creates a distinct row. Two keys differing only in
`utm_content` are counted separately. Past the cap, a novel key increments the overflow row and no new
key row appears. A landing that mints no cookie increments nothing. A concurrent insert of the same
key is recovered from without raising, and the resulting count is 2.

**Admin.** Both changelists render for a staff user with the view permission. Add, change and delete
are refused on both. The CSV export escapes a `utm_campaign` of `=1+1`, emits the BOM, and includes
the fields the changelist omits.

## 7. Documentation and downstream

- Regenerate `docs/app_structure.md` with `/ds:app_map`. It gains the node and the edges in §4.
- `upgrade_notes.md` must carry: the new app to add to `INSTALLED_APPS`, the new middleware entry and
  where it goes in the list, the three settings and their defaults, and the migration.
- `docs/product/` gains a page for this feature, via `/fls-dev:update_product_docs`, and that page
  is the privacy pack. FLS is installed into other people's projects and the operator is the data
  controller, so the page has to make their own assessment a filling-in exercise rather than an
  investigation of FLS internals. It states the full field list, the data flow from landing to row,
  the retention position (§8), and four things the operator has to settle:
  - The attribution cookie is very unlikely to be "strictly necessary" under ePrivacy and PECR. In
    the EU and UK, assume it needs consent like an analytics cookie.
  - Reading a `_ga`, `_fbp` or `_fbc` cookie is itself regulated under Article 5(3). A banner
    covering analytics does not obviously cover a second application copying that identifier into a
    permanent record against a name.
  - A DPIA is likely required rather than merely prudent, because this combines cookie values,
    ad-network identifiers, IP and user agent against an identity.
  - `get_client_ip` with no `TRUSTED_PROXY_IP_HEADER` configured behind a proxy returns
    `REMOTE_ADDR`, the proxy's own address, identical on every row. The failure is silent.

  `research_attribution_privacy.md` has the citations. The "Personal Data Collected" list in
  `docs/product/security-and-data-handling.md` gains the new fields and links to the page.

## 8. Open questions

- **Retention.** This work ships no retention period and no scheduled deletion. The only way a row
  goes away is the `User` cascade. An operator needs a stated position, and CNIL's 13-month cookie /
  25-month data caps are the usual anchor for this class of data. Settling on a default belongs with
  the deferred erasure work, but the privacy pack cannot be written without naming what today's
  answer is: kept until the account is deleted.
- **The cap's default.** `1000` distinct keys per site per day is a guess. An operator running many
  concurrent creatives may need it higher; nobody will know until real traffic exists.

## 9. Success criteria

- A GET carrying `?utm_source=x` sets one signed, `HttpOnly`, host-only cookie; a GET carrying no
  tracked parameter sets none and costs the middleware no query.
- A second landing inside 90 days leaves the cookie and the tally untouched.
- A signup after a tracked landing has a `SignupAttribution` row whose frozen fields match that
  landing; confirming the email from a different browser does not change it.
- Every signup through the signup form has exactly one row, including one with no cookie, which
  reads `direct` / `none`.
- Past the cap, further novel keys for that site and day land on the overflow row.
- Signups grouped by campaign over first touches grouped by campaign, for a date range, is obtainable
  from the two changelists without writing SQL.
- Neither model can be added to, changed or deleted through the admin.
- A row whose `utm_campaign` is `=1+1` exports as a cell Excel and Sheets open as text.
- Deleting a `User` deletes their `SignupAttribution` row.
- `docs/app_structure.md` shows `accounts --> referral_tracking` and no edge from
  `referral_tracking` to any app other than `base` and `site_aware_models`, tests aside.
