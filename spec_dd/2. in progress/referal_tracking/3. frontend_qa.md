# Frontend QA — tracking where learners come from

The change adds a middleware that sets a signed `fls_attribution` cookie on the first landing that
carries an advert or UTM parameter, tallies that landing in `FirstTouchCount`, and writes one
`SignupAttribution` row per signup. The only screens are two read-only admin changelists with a CSV
export. Nothing a learner sees changes, so the risk is in what runs on every request (the
middleware), what happens at signup, and whether the admin is as read-only as it claims.

## §0 Setup

### Start the server

```bash
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL is `http://127.0.0.1:$PORT`. Substitute it everywhere below.

### Mail

Signup confirmation emails land in Mailpit at `http://localhost:8025` (see
`dev_db/docker-compose.yaml`). Every signup test below needs it running.

### Login

Admin is `demodev@email.com` / `demodev@email.com` (password equals email). Admin lives at
`http://127.0.0.1:$PORT/admin/`. The two changelists are:

- `http://127.0.0.1:$PORT/admin/freedom_ls_referral_tracking/signupattribution/`
- `http://127.0.0.1:$PORT/admin/freedom_ls_referral_tracking/firsttouchcount/`

### Cookie inspection

Several tests check the `fls_attribution` cookie. Use the browser's devtools (Application → Cookies)
or, in Playwright, read the response headers of the landing request. The cookie must be `HttpOnly`,
so `document.cookie` will never show it: that absence is itself expected.

### Fresh visitors

Each landing test needs a browser with no `fls_attribution` cookie. Delete the cookie for
`127.0.0.1` between tests, or use a new incognito / Playwright context. A signup test also needs an
email address never used on this database.

### Lowering the cap for §7

The overflow row appears only after the site has seen the cap's worth of distinct attribution keys
today (default 1000). Seed that many rows for today rather than clicking a thousand times:

```bash
uv run python manage.py shell -c "
from datetime import date
from django.contrib.sites.models import Site
from django.utils import timezone
from freedom_ls.referral_tracking.counters import attribution_key_hash
from freedom_ls.referral_tracking.models import FirstTouchCount
site = Site.objects.get(name='DemoDev')
day = timezone.localdate()
rows = [
    FirstTouchCount(site=site, day=day, utm_source='seed', utm_campaign=f'seed-{i}',
                    key_hash=attribution_key_hash('', 'seed', '', f'seed-{i}', '', ''), count=1)
    for i in range(1000)
]
FirstTouchCount.objects.bulk_create(rows)
print(FirstTouchCount.objects.filter(site=site, day=day).count())
"
```

To remove the seed afterwards:

```bash
uv run python manage.py shell -c "
from freedom_ls.referral_tracking.models import FirstTouchCount
print(FirstTouchCount.objects.filter(utm_source='seed').delete())
"
```

## §1 A tracked landing mints the cookie and tallies once

1. In a fresh browser, open
   `http://127.0.0.1:$PORT/courses/?utm_source=Facebook&utm_medium=CPC&utm_campaign=Spring%20Sale&utm_content=blue&advert_code=AD-7`.

**Expect:**

- The course listing renders normally. No error, no visible change. (`/` itself redirects an
  anonymous visitor to login; a tracked landing there mints on the redirect response, which is
  also fine, but `/courses/` keeps the check simple.)
- The response sets an `fls_attribution` cookie: `HttpOnly`, `SameSite=Lax`, `Max-Age` of 90 days
  (7776000 seconds), no `Domain` attribute, not `Secure` (dev runs over HTTP).
- The response carries `Vary: Cookie` and `Cache-Control: private, no-store`.

2. Log in as admin and open the `FirstTouchCount` changelist.

**Expect:**

- One row for today with `utm_source` `facebook` and `utm_medium` `cpc` (lower-cased),
  `utm_campaign` `Spring Sale` (case kept), `utm_content` `blue`, `advert_code` `AD-7`, `count` 1,
  `is_overflow` unticked.
- Opening the row shows every field read-only and the `count` help text about cookie mints, bots and
  comparing campaigns.

3. Log out, go back to the first browser (cookie still present) and load the same URL again, then a
   different one: `http://127.0.0.1:$PORT/courses/?utm_source=google&utm_campaign=Other`.

**Expect:**

- Neither response sets a new `fls_attribution` cookie. The stored cookie value is unchanged.
- The `FirstTouchCount` changelist still shows `count` 1 for the Facebook row and no Google row.
  First touch stays frozen.

## §2 Untracked traffic is untouched

1. In a fresh browser, open `http://127.0.0.1:$PORT/courses/`, then
   `http://127.0.0.1:$PORT/accounts/login/`, then `http://127.0.0.1:$PORT/courses/?foo=bar&ref=partner`.

**Expect:**

- No `fls_attribution` cookie is set by any of them. `ref` is not a tracked parameter.
- No new `FirstTouchCount` row appears.
- The site behaves exactly as before: login page renders, the course listing renders, HTMX
  interactions on any page still work (the middleware sits in every request).

2. Send a POST whose URL carries a tracked parameter, from the shell:

```bash
curl -si -X POST "http://127.0.0.1:$PORT/accounts/login/?utm_source=post-test" | grep -i set-cookie
```

**Expect:**

- No `fls_attribution` in the output (a CSRF 403 is fine; the point is the headers), and no
  `post-test` row in the tally. Only GETs mint.

## §3 Signup after a tracked landing

1. In a fresh browser, open
   `http://127.0.0.1:$PORT/courses/?utm_source=linkedin&utm_medium=social&utm_campaign=qa-signup&gclid=abc123`.
2. Go to `http://127.0.0.1:$PORT/accounts/signup/` and sign up with a never-used email, e.g.
   `qa-linkedin@example.com`.
3. Do **not** confirm the email yet. As admin, open the `SignupAttribution` changelist.

**Expect:**

- One row for `qa-linkedin@example.com`: `utm_source` `linkedin`, `utm_medium` `social`,
  `utm_campaign` `qa-signup`, `first_seen` at the landing time, `signed_up_at` at the POST time.
- The detail view shows `gclid` `abc123`, `landing_path` `/courses/`, `raw_query` the full query
  string, `client_ip` `127.0.0.1`, a `user_agent`, and blank `ga_cookie` / `fbp_cookie` /
  `fbc_cookie`. The row exists before the email is confirmed.

4. Open Mailpit, copy the confirmation link, and open it in a **different** browser context (a new
   incognito window) that has never visited the site.

**Expect:**

- Confirmation succeeds and logs the learner in as normal.
- The `SignupAttribution` row is unchanged: still `linkedin` / `qa-signup`, same `first_seen`.

5. Repeat step 4's idea the other way round: in a third fresh context, first land on
   `http://127.0.0.1:$PORT/courses/?utm_source=decoy&utm_campaign=decoy`, then open a confirmation link for
   another signup made without any landing.

**Expect:**

- That learner's row still reads `direct` / `none`. Confirmation never writes attribution.

## §4 Signup with no landing

1. In a fresh browser with no `fls_attribution` cookie, sign up directly at
   `http://127.0.0.1:$PORT/accounts/signup/` with a new email.

**Expect:**

- A `SignupAttribution` row with `utm_source` `direct`, `utm_medium` `none`, every other frozen field
  blank, and `first_seen` equal to `signed_up_at`.
- No `FirstTouchCount` row is added for this signup.

2. Sign up a third time, this time having landed on `http://127.0.0.1:$PORT/courses/?utm_source=direct`
   first.

**Expect:**

- The row reads `direct` and the tally has a `direct` row with `count` 1. The crafted value is
  stored as-is and is not distinguished from a real direct signup.

## §5 Malformed and hostile input

1. In a fresh browser, open
   `http://127.0.0.1:$PORT/courses/?utm_source=%00Face%09book&utm_campaign=%3D1%2B1&utm_term=a%252Bb&utm_content=` followed by 200 characters of `x`.

**Expect:**

- The page renders (no 500). The tally row shows `utm_source` `facebook` (null and tab stripped,
  lower-cased), `utm_campaign` `=1+1` stored literally, `utm_term` `a%2Bb` (not decoded a second
  time to `a+b`), and `utm_content` cut to 128 characters.

2. Edit the `fls_attribution` cookie value in devtools to any other string, then load
   `http://127.0.0.1:$PORT/courses/?utm_source=after-forge`.

**Expect:**

- No error. The forged cookie is replaced by a freshly minted one for `after-forge`, and the tally
  gains an `after-forge` row. A tampered cookie counts as absent.

3. With the forged cookie still in place (re-forge it), sign up with a new email.

**Expect:**

- The row reads `direct` / `none`. Nothing from the forged value is stored.

## §6 The admin is read-only

1. As admin, open both changelists.

**Expect:**

- No "Add" button on either. Visiting the add URL directly
  (`.../signupattribution/add/`, `.../firsttouchcount/add/`) returns 403.
- On a row's detail page every field is displayed as text, with no inputs and no Save or Delete
  buttons. The delete URL (`.../<id>/delete/`) returns 403.
- The `SignupAttribution` changelist has a date drilldown by `signed_up_at`, filters for
  `utm_source`, `utm_medium` and `utm_campaign`, and a search box that finds a row by email,
  campaign or advert code. `gclid`, the ad cookies, `client_ip` and `user_agent` are not offered as
  filters.
- The `FirstTouchCount` changelist has a date drilldown by `day` and filters for `utm_source`,
  `utm_medium`, `utm_campaign` and `is_overflow`.

2. Create a staff user with no permissions on the new models: in the `User` admin, add a user, tick
   `is_staff`, grant no permissions. Log in as that user in another context.

**Expect:**

- The two models are absent from the admin index, and both changelist URLs return 403.
- Grant only "Can view signup attribution" and reload: the changelist renders, the add URL still
  returns 403, and the export action is available.

## §7 The overflow row

1. Run the seed script from §0 so today already holds 1000 distinct keys.
2. In a fresh browser, land on `http://127.0.0.1:$PORT/courses/?utm_source=past-cap&utm_campaign=novel`.
3. Open the `FirstTouchCount` changelist and filter `is_overflow` = Yes.

**Expect:**

- One overflow row for today with blank key columns and `count` 1. No `past-cap` row exists.

4. Delete the cookie and land on the same URL again; then land on one of the seeded keys, e.g.
   `http://127.0.0.1:$PORT/courses/?utm_source=seed&utm_campaign=seed-5`.

**Expect:**

- The overflow row's `count` is 2. The `seed-5` row's `count` is 2: an existing key still gets its
  own increment past the cap.

5. Remove the seed rows with the second script in §0.

## §8 CSV export

1. In the `SignupAttribution` changelist, filter by `utm_campaign` = `qa-signup` (from §3), tick the
   row, choose "Export selected signup attributions" and run it.

**Expect:**

- An immediate `SignupAttribution-<today>.csv` download with no intermediate form. Opened in a text
  editor it begins with the UTF-8 BOM (`EF BB BF`), has a header row naming every model field
  including `gclid`, `client_ip` and `user_agent` but not `site`, and one data row. `first_seen`
  and `signed_up_at` are ISO 8601. The `user` column is the email.

2. Export the `FirstTouchCount` row from §5 whose `utm_campaign` is `=1+1`, via "Export selected
   first touch counts".

**Expect:**

- In the file the cell reads `'=1+1`. Opened in Excel, Google Sheets or LibreOffice the cell shows
  text, not the number 2. `is_overflow` reads `0`.

3. On a changelist with more than one page (use the seeded tally rows before removing them), tick
   the header checkbox, click "Select all N", and run the action.

**Expect:**

- The CSV holds every row in the filtered set, not only the visible page.

4. On the same filtered changelist, tick nothing and click the "Export" button at the top of the
   list.

**Expect:**

- The same filtered set downloads immediately.

5. Open one `SignupAttribution` row's detail page.

**Expect:**

- No "Export" button on the read-only form.

6. As the staff user with no permissions from §6, open
   `/admin/freedom_ls_referral_tracking/signupattribution/export/` directly.

**Expect:**

- 403.

## §9 What else could break

The middleware runs on every request, so check the site still behaves for existing flows once with
and once without a tracked parameter on the URL:

- A 404 URL with `?utm_source=x`: renders the 404 page, and the cookie is still minted (the spec
  does not gate on status).
- The course player and any HTMX partial: no duplicated `Vary` headers, no broken responses.
- The admin itself under `?utm_source=x`: the admin renders, and the visit is tallied like any
  other GET. That is expected, not a bug.
- A signup where the browser has `_ga`, `_fbp` and `_fbc` cookies set for `127.0.0.1` (set them by
  hand in devtools): the row's `ga_cookie`, `fbp_cookie` and `fbc_cookie` hold those values.
- Deleting a user with a `SignupAttribution` row from the `User` admin: the deletion summary lists
  the attribution row, and after deletion the row is gone from the changelist.
