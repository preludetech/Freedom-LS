# Spec: panel framework package, git-tag install, FLS switches over

Spec 5 of 6 in the Panel framework extraction effort (`spec_dd/1. next/roadmap.md`, "Panel framework
extraction"). Idea: `idea.md`. Up-front answers: `answers.md`. Research: `research_*.md` in this
directory. `research_codebase.md` holds the full file:line inventory this spec summarises.

## Purpose

Another Django project needs the panel framework, and today it can only be had by vendoring FLS.
This spec moves `freedom_ls/panel_framework` into the public `preludetech/django-panel-framework`
repo under the MIT licence and tags it `v0.1.0`. FLS then installs it by that tag. Framework edits
stay live in every FLS worktree, and First-Class and the concrete template pick the change up through
the normal upgrade-notes flow. Behaviour does not change: specs 3 and 4 already made the code
standalone.

## Scope

**In**
- The package repo's contents, build, licence, changelog, CI and first tag `v0.1.0`.
- In FLS: the dependency line, deleting the in-tree app, rewriting every `freedom_ls.panel_framework`
  reference, the migration fix-up and old-table drop, the live-edit loop, the landing check, CI,
  Tailwind wiring, docs and skills, and `upgrade_notes.md`.
- `freedom_ls_infra/fls-base/Dockerfile`: add `git`.

**Out**
- The Claude Code plugin, its commands, the consumer-suite script and the developer doc (spec 6).
  The repo layout leaves room for `claude_plugins/panel-framework/`.
- Any change to framework behaviour or its host contract.
- PyPI, a private repo, a submodule, a shared core package, outside contributions.
- Migrating data from the old table.
- Editing First-Class or the concrete template directly. Both take this through `upgrade_notes.md`.
- The pre-existing fault in `fls-base/Dockerfile` stage 1, a Node-only stage that runs
  `npm run tailwind_build` when FLS's script calls `uv run manage.py`.
- Tidying `/home/sheena/workspace/lms/django_apps/`.

## Decisions

- **Distribution.** Distribution `django-panel-framework`; import name and app label `panel_framework`.
  FLS pins it in `[project].dependencies` as
  `django-panel-framework @ git+https://github.com/preludetech/django-panel-framework.git@v0.1.0`,
  with no `[tool.uv.sources]` entry and no `uv.toml`. `fls-base` installs with
  `uv pip install --system -r pyproject.toml`, which reads only `[project].dependencies`. Spike 2
  (`research_spikes.md`) confirmed that a path-installed FLS passes the line on to First-Class and
  the template with no entry of their own. FLS keeps legacy setuptools; a move to hatchling would
  need `allow-direct-references`.
- **Repo history.** One fresh import commit that names the FLS commit it was copied from. No
  history extraction.
- **Tags are immutable.** `v0.1.0` and later tags are never moved or deleted, and `main` history is
  never rewritten: `uv.lock` pins the commit. A bad release is fixed forward with a new tag.
- **Agents push and tag.** The implementation pushes to `preludetech/django-panel-framework` and
  creates and pushes `v0.1.0` once the package suite passes, without a stop.
- **Old data is dropped, not migrated.** The new `0001` creates `panel_framework_bulkactionrun`,
  so it never collides with `freedom_ls_panel_framework_bulkactionrun`.
- **The drop uses no SQL.** It is a `RunPython` that checks for the table through
  `connection.introspection.table_names()` and calls `schema_editor.delete_model` on a throwaway
  model whose `Meta.apps` is a private `django.apps.registry.Apps()` and whose `db_table` is the old
  name. No raw-SQL security review is needed.
- **Live editing needs `UV_NO_SYNC=1`.** Spike 1 showed that a plain `uv run` uninstalls the
  editable copy and puts back the locked one. The pre-commit hook runs `uv run`, so the variable
  must be set in the committing environment too.
- **Tailwind `@source` stays plain.** `@source not-ignored:` is a build error in Tailwind 4.1.16,
  and a plain `@source "<path>"` already scans a gitignored `.venv` (spec 4's probe).
  `write_panel_framework_css` keeps its current output form.
- **The FLS drift guard goes.** `educator_interface/tests/invariants/test_framework_copies_match_base.py`
  is deleted: from `v0.1.0` the package owns its copies and may diverge on purpose.
- **The landing check runs before landing, never on commit.** An editable copy that differs from
  the lock is normal while work is in progress.

## Requirements

### 1. The package repo

Local checkout: `/home/sheena/workspace/software_factory/django-panel-framework.git/main`, a
worktree of a bare repo whose `origin` is `git@github.com:preludetech/django-panel-framework.git`.
It holds one commit with an empty `README.md`.

Layout:

```
pyproject.toml  uv.lock  LICENSE  README.md  CHANGELOG.md  package.json  package-lock.json
.gitignore  .github/workflows/tests.yml
panel_framework/          # the app, including HOST_CONTRACT.md, css/, py.typed, testing/
tests/                    # the standalone suites; not shipped in the wheel
```

**The app.** The contents of `freedom_ls/panel_framework/` minus `tests/`, with these changes:
- Every `freedom_ls.panel_framework` prefix becomes `panel_framework`, in code, dotted-string
  settings defaults (`config.py`), `HOST_CONTRACT.md` and docstrings.
- `apps.py`: `name = "panel_framework"`. The `label` line goes, because the default equals it.
- `write_panel_framework_css.py`: `apps.get_app_config("panel_framework")`.
- Every system check id `freedom_ls_panel_framework.<code>` becomes `panel_framework.<code>`, codes
  unchanged.
- `migrations/` holds a single regenerated `0001_initial` for the current `BulkActionRun`, including
  the `site` FK with `related_name="+"` and its dependency on `sites`. `makemigrations --check`
  reports nothing.
- `RunStatus`, `BulkActionRun`, `PanelBodyTooLargeError` and every name FLS imports today stay
  importable from the same module paths under `panel_framework`.
- `py.typed` is shipped, so FLS's mypy type-checks the imports.
- `tests/invariants/template_rules.py` moves to `panel_framework/testing/template_rules.py`. It is
  the public helper hosts use to run the framework's template rules over their own templates, and
  FLS imports it from there.

**Tests.** The standalone suites from specs 3 and 4 (unit, component, invariants, Playwright) move to
`tests/` at the repo root. Their settings module, URLconf, `standalone_app` and fixtures are rewritten
to `tests.*` dotted paths. Stub models and checks tests use the `panel_framework` label.
`test_import_guard.py` forbids any `freedom_ls` import. Tests that name FLS only to assert its absence
are reworded without the name or dropped. A test marked `needs_fls_host` moves to FLS beside the
code it exercises, and the marker leaves both repos. `pytest` run at the repo root runs the full
standalone suite. The suite runs on SQLite, as specs 3 and 4 delivered it.

An FLS test whose only subject is framework code moves here, for example
`educator_interface/tests/invariants/test_bulk_run_scoping.py`'s scan of `bulk_runs.py`.

**Build.** `[build-system]` requires `hatchling>=1.27` with `build-backend = "hatchling.build"`.
`[tool.hatch.build.targets.wheel] packages = ["panel_framework"]`. The sdist includes the package,
`LICENSE`, `README.md`, `CHANGELOG.md` and `pyproject.toml`. `[project]`:
`requires-python = ">=3.13"`, runtime dependencies `django>=6.0,<6.1` and `django-cotton>=2.1.3`,
`license = "MIT"`,
`license-files = ["LICENSE", "panel_framework/templates/panel_framework/icons/HEROICONS_LICENSE.txt"]`,
and no `License ::` classifier. A `dev` dependency group carries the test tools the suites need,
including `lxml`, `cssselect` and `pytest-playwright`. `uv.lock` is committed.

**Licence.** `LICENSE` is the standard MIT text with `Copyright (c) 2026 Prelude Technologies`,
then a "Third-party material" section naming Heroicons (icon SVG bodies, MIT,
Copyright (c) Tailwind Labs, Inc.) and the path of its notice file. `HEROICONS_LICENSE.txt` stays
verbatim beside the icons.

**README.** Says the package is MIT licensed and that outside contributions (pull requests, patches)
are not accepted for now. It gives the install steps: the PEP 508 line, the `INSTALLED_APPS` entry
(after any app whose templates override the framework's), the URL include, the
`write_panel_framework_css` step before every Tailwind build with the `@import` of its output, and
the settings the app declares. It points at `HOST_CONTRACT.md` for the host contract. No
`CONTRIBUTING.md`.

**CHANGELOG.md.** The deprecation rule comes first: a breaking change keeps the old name, path or
setting working for one tag and emits a `DeprecationWarning` subclass, with `stacklevel=2`. Then one entry per tag, newest
first, headed `## [0.1.0] - <date>`. Each entry starts with a fixed flag block using FLS's
`upgrade_notes.md` keys: `requires_migrations`, `requires_template_review` with
`changed_template_paths`, `requires_settings_change`, `requires_tailwind_rebuild`. Prose follows.

**Front-end build.** `package.json` carries the `panel_framework_css` script and the Tailwind 4.1.16+
dependency that build the gitignored `panel_framework/static/panel_framework/css/reference.css` from
`tests/css/reference_input.css`. Both are moving here from FLS. `.gitignore` lists `reference.css`.

**CI** (`.github/workflows/tests.yml`, Python 3.13, Django 6.0): `uv sync --locked`; `ruff`;
`makemigrations --check`; the wheel test; `npm ci` and `npm run panel_framework_css`;
`playwright install --with-deps chromium`; `pytest` across every tier. On a `v*` tag, a step fails
unless the tag, the `pyproject.toml` version and the top `CHANGELOG.md` entry agree.

**Release.** `v0.1.0` is an annotated tag on the commit where the package CI passes.

### 3. FLS: migrations

- `educator_interface` migrations `0001_rename_unregister_bulk_runs`, `0002_move_learner_bulk_runs`
  and `0003_move_cohort_bulk_runs` keep their names and their place in the chain. Their dependency on
  `("freedom_ls_panel_framework", "0001_initial")` is removed, and their operations become
  `migrations.RunPython(migrations.RunPython.noop, migrations.RunPython.noop)`. They repointed
  `action_path` strings on rows this spec discards. This is a deliberate exception to "never edit an
  existing migration": the app they depend on stops existing, and without the edit every `migrate`
  raises `NodeNotFoundError`. Their tests, `educator_interface/tests/migrations/test_0001…0003`, are
  deleted.
- A new `educator_interface/migrations/0004_drop_legacy_panel_framework.py`, `RunPython` only, with
  a no-op reverse. It depends on `0003` and `("contenttypes", "0002_remove_content_type_name")`, and
  not on any `panel_framework` migration. In one function it:
  1. drops `freedom_ls_panel_framework_bulkactionrun` if it exists, as in Decisions;
  2. deletes `django_migrations` rows with `app="freedom_ls_panel_framework"` through
     `MigrationRecorder(schema_editor.connection).migration_qs`;
  3. deletes `ContentType` rows with `app_label="freedom_ls_panel_framework"` through the historical
     model, so `Permission` rows cascade.
  On a fresh database every step is a no-op.

### 4. FLS: live editing

- `claude_plugins/fls-dev/scripts/rebuild_after_rebase.sh` (POSIX `sh`, `set -eu`) links the package
  right after `uv sync`, before `npm run tailwind_build`, which runs `write_panel_framework_css`:
  - `PANEL_FRAMEWORK_DIR` is absolute and defaults to
    `/home/sheena/workspace/software_factory/django-panel-framework.git/main`.
  - When the directory exists and holds a `pyproject.toml`, the script runs
    `uv pip install --no-deps -e "$PANEL_FRAMEWORK_DIR"`.
  - Otherwise it prints one line naming the path and what was missing, says the locked copy stays in
    use, and carries on with exit status 0.
- `claude_plugins/fls-dev/skills/git-worktree-setup/SKILL.md` documents the loop:
  - `PANEL_FRAMEWORK_DIR` and its default.
  - `UV_NO_SYNC=1` is required in the developer's shell and in the per-machine
    `.claude/settings.local.json` `env` block for agents. Without it, `uv run` and the pre-commit
    hook put the locked copy back.
  - A new dependency is not picked up until `uv sync` runs; `rebuild_after_rebase.sh` then re-links.
  - Switching between the editable and locked copies changes `tailwind.panel_framework.css`, so
    Tailwind is rebuilt.
  - A framework change FLS needs follows one route: edit and test in the package, tag, bump the pin
    and `uv lock` in the same FLS change, then run the FLS suite.
  - The fallback is `uv run --with-editable "$PANEL_FRAMEWORK_DIR" <cmd>` for a one-off run.
- All of this lives in `fls-dev`. Nothing goes into `sdd` or `ds`.

### 5. FLS: the landing check

- `claude_plugins/fls-dev/scripts/check_panel_framework_pin.py`:
  - Reads the locked commit of `django-panel-framework` from `uv.lock` with `tomllib`, from the part
    of its git `source` after `#`.
  - Reads the installed copy's PEP 610 `direct_url.json` through `importlib.metadata`.
  - Exits 0 when the installed copy is the locked git commit, or is an editable checkout whose `HEAD`
    is the locked commit and whose working tree is clean.
  - Otherwise exits non-zero. It prints the installed and locked commits and the next step: commit
    and tag in the package, bump the pin, `uv lock`, re-run.
- It runs before landing. `.claude/sdd/config.md`'s `Pre-test rebuild` points at a new fls-dev wrapper
  that runs `rebuild_after_rebase.sh` and then the check. `sdd:finish_worktree` reports a failing
  prepare step as `pre-test rebuild failed` and lands nothing. The wrapper is generated the same way
  as the existing `.claude/fls-dev/scripts/` wrappers. `.claude/settings.json` gets allow entries for
  it in the forms the existing wrappers use.

## Testing

**Package**
- Wheel and sdist contents: build both into `tmp_path` with `uv build`, the wheel from the sdist.
  The test asserts the wheel contains:
  - every file under `panel_framework/` in the source tree except `__pycache__`;
  - `HEROICONS_LICENSE.txt`, `0001_initial.py`, the three `css/` files, the two JS files and the
    icon bodies;
  - `LICENSE` and the Heroicons notice under `*.dist-info/licenses/`;
  - `License-Expression: MIT` in `METADATA`.

  It also asserts that `tests/`, `node_modules` and `reference.css` are absent.
- Clean install: in CI, the built wheel goes into a fresh venv, where `import panel_framework` and
  `manage.py check` against the standalone settings both pass.
- The moved standalone suites pass from a clean clone with `pytest`. A failure is fixed at its cause
  in the package, never with a shim.
- The tag, version and changelog agreement check fails on a mismatched tag.

**FLS**
- The full suite passes against the locked `v0.1.0` with the in-tree app gone, and `uv run manage.py
  check` reports no `panel_framework` messages under the default and `first_class` themes.
- `0004_drop_legacy_panel_framework`, tested in three cases:
  - on a database holding the old table, its two `django_migrations` rows and its ContentType and
    Permission rows: all are removed, and `panel_framework_bulkactionrun` is untouched;
  - a second run is a no-op;
  - on a fresh database nothing is dropped and nothing fails.
- `migrate` on a fresh database, and on a copy of a database migrated at `main`, completes with no
  `NodeNotFoundError`.
- The Tailwind coverage invariant (`base/tests/invariants/test_panel_framework_tailwind.py`) builds
  FLS's real stylesheet and finds a class used only in framework templates, plus `.panel-surface`. It
  builds once against the installed copy and once against an editable copy.
- `check_panel_framework_pin.py` is tested in `tests/` (where `fls-dev` scripts are tested) for four
  cases: a locked git install passes; an editable checkout at the locked commit and clean passes; an
  editable checkout at another commit fails; a dirty one fails. Fixture `uv.lock` and
  `direct_url.json` files drive it, with no network.
- The link step in `rebuild_after_rebase.sh` is tested for three cases: directory missing, directory
  without `pyproject.toml`, directory present. The first two skip with the message and exit 0.
- `rg 'freedom_ls\.panel_framework|freedom_ls/panel_framework|freedom_ls_panel_framework'` over
  `freedom_ls`, `config`, `claude_plugins`, `test_organisation`, `docs` and `.claude/skills` finds
  only the migration `0004` and its test.

## Documentation and downstream

`upgrade_notes.md` beside this spec, written through `/fls-dev:update_upgrade_notes`. Its flags:

```yaml
requires_migrations: true
requires_template_review: true      # framework templates now come from the package
requires_settings_change: true
changed_settings:
  - INSTALLED_APPS          # hard
  - SILENCED_SYSTEM_CHECKS  # optional
requires_package_upgrade: true
changed_packages:
  - django-panel-framework @ git+https://github.com/preludetech/django-panel-framework.git@v0.1.0
requires_npm_install: false
requires_tailwind_rebuild: true
```

Breaking changes:
- The in-tree app is gone.
- The import prefix and app label are now `panel_framework`.
- Check ids are now `panel_framework.<code>`.
- The old table and its rows are dropped by `educator_interface 0004`.

Manual steps:
1. Run `uv lock`. The dependency arrives transitively through `freedom_ls`, so the project's
   `pyproject.toml` needs no entry.
2. In `INSTALLED_APPS`, replace `"freedom_ls.panel_framework"` with `"panel_framework"`, after
   `freedom_ls.base`.
3. Change any `include("freedom_ls.panel_framework.urls")` to `include("panel_framework.urls")`.
4. Rename `freedom_ls_panel_framework.*` entries in `SILENCED_SYSTEM_CHECKS`. A project with its own
   settings module also replaces any `freedom_ls.panel_framework…` dotted setting value.
5. Make the Tailwind build include the package's templates and `css/panel_framework.css` from the
   installed copy:
   - First-Class: replace the `@import` that reads the CSS from the submodule path.
   - The template: add the import, since it never had one.
   - A Node-only Tailwind Docker stage is fed by a Python-dependency stage that runs first. That
     stage installs `git` (the template's `uv:0.9-python3.13-bookworm-slim` image has none;
     First-Class's already does), and the Tailwind stage copies the installed `panel_framework`
     directory to the path the input names.
6. Rebuild Tailwind and run `migrate`.

## Open questions

These were found after the up-front questions and took their defaults.

- Q: How do `educator_interface` migrations 0001 to 0003, which depend on the old label, survive the
  app's removal? → A: Neutralised to no-ops with the dependency removed, and their tests deleted
  (assumed default: the data they repointed is dropped anyway, and it is the smallest edit that keeps
  the deployed `django_migrations` rows valid. A stub app keeping the old label and migrations would
  avoid editing them, but it would leave a dead app in `INSTALLED_APPS`. Overrule by editing
  Requirements §3.)
- Q: Which app hosts the drop migration? → A: `educator_interface`, as `0004` (assumed default:
  `base` has no migrations package, and `educator_interface` is the only app that ever depended on
  the old label. Overrule by editing Requirements §3.)
- Q: Do the check ids change with the label? → A: Yes, to `panel_framework.<code>` (assumed default:
  `v0.1.0` is the one release where every label-bound name changes together, and no FLS settings
  silence them. Overrule by editing Requirements §1.)
- Q: Where do the framework's tests live, given that FLS imports `tests.invariants.template_rules`?
  → A: `tests/` moves to the repo root and is not shipped; `template_rules` becomes the public
  `panel_framework.testing.template_rules` (assumed default: it keeps test-only code out of the
  wheel and gives hosts a supported import. Overrule by editing Requirements §1.)
- Q: Where do the package tests marked `needs_fls_host` go? → A: Into FLS, beside the code they
  exercise (assumed default: they need FLS's URLconf and icon set, which the package cannot supply.
  Overrule by editing Requirements §1.)
- Q: What does the package CI cover? → A: Python 3.13 and Django 6.0 only, with the SQLite standalone
  suite (assumed default: this matches the pinned `django>=6.0,<6.1` and specs 3 and 4's suite, and a
  Postgres leg or a wider matrix can come with a later tag. Overrule by editing Requirements §1.)
- Q: Framework code leaves FLS's coverage source; does `COVERAGE_FAIL_UNDER: 92` change? → A: No,
  unless the measured value falls below it, in which case the plan records the new figure for a
  decision (assumed default: the gate exists to catch regressions in FLS code. Overrule by editing
  Requirements §6.)
- Q: The landing check runs inside the `Pre-test rebuild` step, which a `tier: none` landing skips.
  Is that gap acceptable? → A: Yes (assumed default: `tier: none` means no Python changed, so the
  pin cannot have drifted from the code. Overrule by editing Requirements §5.)
- Q: `.claude/fls-dev/config.md` lists only First-Class as a concrete project. How does the template
  receive the notes? → A: This spec does not change that config. Taking the template through
  `/fls-dev:update_concrete_projects` means adding it there first, and that is a human step in
  `todo.md` (assumed default: the list drives every future spec's integration run, so changing it is
  the user's call. Overrule by editing Documentation and downstream.)
