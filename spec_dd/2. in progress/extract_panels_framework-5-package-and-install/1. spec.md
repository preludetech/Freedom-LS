# Spec: panel framework package, git-tag install, FLS switches over

Spec 5 of 6 in the Panel framework extraction effort (`spec_dd/1. next/roadmap.md`, "Panel framework
extraction"). Idea: `idea.md`. Up-front answers: `answers.md`. Research: `research_*.md` in this
directory. `research_codebase.md` holds the file:line inventory, and `research_spikes.md` holds the
uv and Docker spike results.

## Purpose

Another Django project needs the panel framework, and today it can only be had by vendoring FLS.
This spec moves `freedom_ls/panel_framework` into the public `preludetech/django-panel-framework`
repo under the MIT licence, tags it `v0.1.0`, and has FLS install it by that tag. Behaviour does not
change.

## Scope

**In**
- The package repo's contents, build, licence, changelog, CI and first tag `v0.1.0`.
- In FLS: the dependency, deleting the in-tree app, the reference rewrite, the migration fix-up and
  old-table drop, per-worktree live editing, the landing check, CI, Tailwind, docs and skills, and
  `upgrade_notes.md`.
- `/home/sheena/workspace/lms/freedom_ls_infra/fls-base/Dockerfile`: add `git`.

**Out**
- The Claude Code plugin, its commands, the consumer-suite script and the developer doc (spec 6).
  The repo layout leaves room for `claude_plugins/panel-framework/`.
- Any change to framework behaviour or its host contract.
- PyPI, a private repo, a submodule, a shared core package, outside contributions.
- Migrating data from the old table.
- Editing First-Class or the concrete template directly. Both take this through `upgrade_notes.md`.
- The pre-existing fault in `fls-base/Dockerfile` stage 1, a Node-only stage that runs
  `npm run tailwind_build` when FLS's script calls `uv run manage.py`.
- Tidying `/home/sheena/workspace/lms/django_apps/`.

## Decisions

- **The pin.** FLS declares
  `django-panel-framework @ git+https://github.com/preludetech/django-panel-framework.git@v0.1.0` in
  `[project].dependencies`, with no `[tool.uv.sources]` entry and no `uv.toml`. The `fls-base` image
  installs with `uv pip install --system -r pyproject.toml`, which reads only that table.
  First-Class and the template get the dependency transitively (spike 2).
- **Names.** Distribution `django-panel-framework`; import name and app label `panel_framework`.
- **Repo history.** One fresh import commit that names the FLS commit it was copied from.
- **Tags are never moved or deleted, and `main` history is never rewritten.** A bad release is fixed
  forward with a new tag.
- **Tailwind `@source` stays plain.** `@source not-ignored:` is a build error in Tailwind 4.1.16, and
  `write_panel_framework_css` keeps its current output form (spec 4's probe, `research_prior_art.md`
  §5).

## Requirements

### 1. The package repo

The repo is a bare repo with worktrees, laid out like FLS:
`/home/sheena/workspace/software_factory/django-panel-framework.git`, with `origin` at
`git@github.com:preludetech/django-panel-framework.git`. Its `main` worktree is
`.../django-panel-framework.git/main` and holds one commit with an empty `README.md`.

Layout:

```
pyproject.toml  uv.lock  LICENSE  README.md  CHANGELOG.md  package.json  package-lock.json
.gitignore  .github/workflows/tests.yml
panel_framework/          # the app, including HOST_CONTRACT.md, css/, py.typed, testing/
tests/                    # the standalone suites; not shipped in the wheel
```

**The app.** This is the contents of `freedom_ls/panel_framework/` minus `tests/`, with these changes:
- Every `freedom_ls.panel_framework` prefix becomes `panel_framework`. That covers code, dotted-string
  settings defaults (`config.py`), `HOST_CONTRACT.md` and docstrings.
- `apps.py`: `name = "panel_framework"`. The `label` line goes, because the default equals it.
- `write_panel_framework_css.py`: `apps.get_app_config("panel_framework")`.
- Every system check id `freedom_ls_panel_framework.<code>` becomes `panel_framework.<code>`. The
  codes stay the same.
- `migrations/` holds a single regenerated `0001_initial` for the current `BulkActionRun`. It
  includes the `site` FK with `related_name="+"` and depends on `sites`. Because it creates
  `panel_framework_bulkactionrun`, it never collides with the old
  `freedom_ls_panel_framework_bulkactionrun`. `makemigrations --check` reports nothing.
- `RunStatus`, `BulkActionRun`, `PanelBodyTooLargeError` and every other name FLS imports today stay
  importable at the same module paths under `panel_framework`.
- `py.typed` ships with the package.
- `tests/invariants/template_rules.py` moves to `panel_framework/testing/template_rules.py`. Hosts
  use this public helper to run the framework's template rules over their own templates.

**Tests.** The standalone suites from specs 3 and 4 move to `tests/` at the repo root: unit,
component, invariants and Playwright.
- Their settings module, URLconf, `standalone_app`, fixtures and `template_rules` imports are
  rewritten to `tests.*` and `panel_framework.testing.*`.
- Stub models and the checks tests use the `panel_framework` label.
- `test_import_guard.py` forbids any `freedom_ls` import.
- Tests that name FLS only to assert its absence are reworded without the name, or dropped.
- A test marked `needs_fls_host` moves to FLS, beside the code it exercises. The marker leaves both
  repos.
- An FLS test whose only subject is framework code moves here. One example is
  `educator_interface/tests/invariants/test_bulk_run_scoping.py`, which scans `bulk_runs.py`.
- `pytest` at the repo root runs the whole suite on SQLite.

**Build.**
- `[build-system]` requires `hatchling>=1.27`, with `build-backend = "hatchling.build"`.
- `[tool.hatch.build.targets.wheel] packages = ["panel_framework"]`.
- The sdist includes the package, `LICENSE`, `README.md`, `CHANGELOG.md` and `pyproject.toml`.
- `[project]` sets:
  - `requires-python = ">=3.13"`;
  - runtime dependencies `django>=6.0,<6.1` and `django-cotton>=2.1.3`;
  - `license = "MIT"`;
  - `license-files = ["LICENSE", "panel_framework/templates/panel_framework/icons/HEROICONS_LICENSE.txt"]`;
  - no `License ::` classifier.
- A `dev` dependency group carries the test tools, including `lxml`, `cssselect` and
  `pytest-playwright`.
- `uv.lock` is committed.

**Licence.** `LICENSE` is the standard MIT text with `Copyright (c) 2026 Prelude Technologies`. After
it, a "Third-party material" section names Heroicons (icon SVG bodies, MIT, Copyright (c) Tailwind
Labs, Inc.) and gives the path of its notice file. `HEROICONS_LICENSE.txt` stays verbatim beside the
icons.

**README.** It says the package is MIT licensed and that outside contributions (pull requests,
patches) are not accepted for now. It gives the install steps:
- the PEP 508 line;
- the `INSTALLED_APPS` entry, after any app whose templates override the framework's;
- the URL include;
- `write_panel_framework_css` before every Tailwind build, plus the `@import` of its output;
- the settings the app declares.

It points at `HOST_CONTRACT.md` for the host contract. There is no `CONTRIBUTING.md`.

**CHANGELOG.md.** The deprecation rule comes first: a breaking change keeps the old name, path or
setting working for one tag and emits a `DeprecationWarning` subclass with `stacklevel=2`. Below it
comes one entry per tag, newest first, headed `## [0.1.0] - <date>`. Each entry opens with a fixed
flag block using FLS's `upgrade_notes.md` keys, then prose. The keys are `requires_migrations`,
`requires_template_review` with `changed_template_paths`, `requires_settings_change` and
`requires_tailwind_rebuild`.

**Front-end build.** `package.json` carries two things that move here from FLS: the
`panel_framework_css` script and a Tailwind 4.1.16+ dependency. Together they build
`panel_framework/static/panel_framework/css/reference.css` from `tests/css/reference_input.css`.
`.gitignore` lists `reference.css`.

**CI** (`.github/workflows/tests.yml`, Python 3.13, Django 6.0) runs, in order:
- `uv sync --locked`;
- `ruff`;
- `makemigrations --check`;
- the wheel test, then a clean install of the built wheel;
- `npm ci` and `npm run panel_framework_css`;
- `playwright install --with-deps chromium`;
- `pytest`.

On a `v*` tag, a step fails unless the tag, the `pyproject.toml` version and the top `CHANGELOG.md`
entry agree.

**Release.** `v0.1.0` is an annotated tag on the commit where the package CI passes. The
implementation pushes the branch and the tag without a stop. If the remote or the permission system
refuses the push, the run returns `blocked` and hands over the exact commands. FLS's pin is committed
only after the tag exists on GitHub.

### 2. FLS: dependency and deletion

- `pyproject.toml`: the pin goes into `[project].dependencies`, and `uv lock` records the tag's
  commit. The `needs_fls_host` marker goes. ruff's isort now sorts `panel_framework` imports as
  third-party.
- `freedom_ls/panel_framework/` is deleted.
- `educator_interface/tests/invariants/test_framework_copies_match_base.py` loses every case that
  compares a framework copy. From `v0.1.0` the package owns its copies and may diverge on purpose.
  The cases that compare the in-tree `freedom_ls.icons` copies with `freedom_ls.base` stay.
- `config/settings_base.py`: in `INSTALLED_APPS`, `"freedom_ls.panel_framework"` becomes
  `"panel_framework"` in the same position, after `freedom_ls.base`. FLS's overrides of
  `panel_framework/reference/base.html` and `cotton/panel-icon.html` depend on that order.
- `config/urls.py`: the `DEBUG`-only include becomes `include("panel_framework.urls")`.
- Every remaining `freedom_ls.panel_framework` reference becomes `panel_framework`. That includes
  imports inside functions and `monkeypatch` targets.
- Old-label check ids in FLS tests follow the rename (`test_system_checks.py:44`,
  `test_settings_defaults.py:357`).
- FLS tests that read package files by path resolve them through `Path(panel_framework.__file__).parent`.
  The `reference.css` gitignore assertion goes.
- `package.json`: the `panel_framework_css` script goes, and so does its call from `tailwind_build`.
- `.gitignore`: the `reference.css` entry goes. `tailwind.panel_framework.css` stays.

### 3. FLS: migrations

- **`educator_interface` 0001 to 0003 become no-ops.** These are
  `0001_rename_unregister_bulk_runs`, `0002_move_learner_bulk_runs` and `0003_move_cohort_bulk_runs`.
  - They keep their names and their place in the chain.
  - Their dependency on `("freedom_ls_panel_framework", "0001_initial")` goes.
  - Their operations become
    `migrations.RunPython(migrations.RunPython.noop, migrations.RunPython.noop)`.
  - Their tests are deleted: `educator_interface/tests/migrations/test_0001_rename_unregister_bulk_runs.py`,
    `test_0002_move_learner_bulk_runs.py` and `test_0003_move_cohort_bulk_runs.py`.

  This is a recorded exception to "never edit an existing migration". The app they depend on stops
  existing, so without the edit every `migrate` raises `NodeNotFoundError`. The rows they rewrote are
  dropped anyway. A stub app that kept the old label was rejected because it leaves a dead app in
  `INSTALLED_APPS`.
- **A new `educator_interface/migrations/0004_drop_legacy_panel_framework.py`.**
  - It is `RunPython` only, with a no-op reverse.
  - It depends on `0003` and on the latest migration of every installed app with a model holding a
    foreign key to `ContentType`. Today those apps are `contenttypes`, `auth`, `admin`, `guardian`,
    `audit_log`, `comms`, `referral_tracking` and `role_based_permissions`. That puts every such
    model in the historical state, so the deletes cascade, or are refused where the foreign key is
    `PROTECT`. None of those migrations may depend back on `educator_interface`.
  - It depends on no `panel_framework` migration.

  In one function it:
  1. Drops `freedom_ls_panel_framework_bulkactionrun` when
     `schema_editor.connection.introspection.table_names()` lists it. It calls
     `schema_editor.delete_model` on a throwaway model whose `Meta` sets `apps` to a private
     `django.apps.registry.Apps()`, `app_label` to a throwaway label and `db_table` to the old name.
     There is no raw SQL, so no security review is needed.
  2. Deletes `django_migrations` rows with `app="freedom_ls_panel_framework"` through
     `MigrationRecorder(schema_editor.connection).migration_qs`.
  3. Deletes `ContentType` rows with `app_label="freedom_ls_panel_framework"` through the historical
     model, which cascades to the dependent rows.

  On a fresh database every step is a no-op.

### 4. FLS: live editing, one package worktree per FLS worktree

Each FLS worktree uses its own copy of the framework, so framework work runs in parallel:
- An FLS worktree on branch `<branch>` links the package worktree of the same name,
  `$PANEL_FRAMEWORK_REPO/<branch>`. `PANEL_FRAMEWORK_REPO` defaults to
  `/home/sheena/workspace/software_factory/django-panel-framework.git`.
- `PANEL_FRAMEWORK_DIR`, when set, overrides that path.
- With no such worktree, the FLS worktree runs on the locked tag. FLS `main` pairs with the package's
  `main`.

**The link step.** It is a new script, `claude_plugins/fls-dev/scripts/link_panel_framework.sh`
(POSIX `sh`, `set -eu`). `rebuild_after_rebase.sh` sources it with `.` right after `uv sync`,
before `npm run tailwind_build` runs `write_panel_framework_css`. Sourcing it lets the export below
reach the rest of the rebuild, and it can still be run on its own under test. The link step:
- resolves the directory as above;
- when the directory holds a `pyproject.toml`, runs `uv pip install --no-deps -e "<dir>"` and
  `export UV_NO_SYNC=1` for the rest of `rebuild_after_rebase.sh`, so its later `uv run` calls keep
  the link;
- otherwise prints one line naming the path and saying the locked copy stays in use. It then carries
  on without an `exit`, since an `exit` in a sourced script would end the rebuild.

**Package worktrees are created by hand.** The command is
`git -C "$PANEL_FRAMEWORK_REPO" worktree add "<branch>" -b "<branch>"`. The next
`rebuild_after_rebase.sh` links it.

**The skill.** `claude_plugins/fls-dev/skills/git-worktree-setup/SKILL.md` documents:
- the pairing, the two variables and the create command;
- that `UV_NO_SYNC=1` is required in the developer's shell and in the per-machine
  `.claude/settings.local.json` `env` block for agents. Spike 1 showed that a plain `uv run`,
  including the one in the pre-commit hook, uninstalls the editable copy and restores the locked one;
- that a new dependency is picked up only by `uv sync`, after which `rebuild_after_rebase.sh`
  re-links;
- the one route for a framework change FLS needs: edit and test in the paired package worktree, tag,
  then bump the pin and run `uv lock` in the same FLS change, and run the FLS suite;
- the one-off fallback, `uv run --with-editable "<dir>" <cmd>`.

All of this lives in `fls-dev`. Nothing goes into `sdd` or `ds`.

### 5. FLS: the landing check

**The script.** `claude_plugins/fls-dev/scripts/check_panel_framework_pin.py`:
- reads the locked commit of `django-panel-framework` from `uv.lock` with `tomllib`, taking the part
  of its git `source` after `#`;
- reads the installed copy's PEP 610 `direct_url.json` through `importlib.metadata`;
- for an editable copy, reads `git -C <dir> rev-parse HEAD` and `git -C <dir> status --porcelain`;
- exits 0 when the installed copy is the locked git commit, or is an editable worktree whose `HEAD`
  is the locked commit and whose tree is clean;
- otherwise exits non-zero, printing the installed and locked commits and the next step: commit and
  tag in the package worktree, bump the pin, `uv lock`, re-run.

A branch that never paired a package worktree runs on the locked copy and always passes.

**The wiring.** The check runs before landing and never on commit:
- `.claude/sdd/config.md`'s `Pre-test rebuild` points at a new wrapper,
  `.claude/fls-dev/scripts/prepare_landing.sh`. It runs `rebuild_after_rebase.sh`, then the check
  with `.venv/bin/python`, never `uv run`. Variables the rebuild set in its own process do not reach
  the wrapper, and a `uv run` would restore the locked copy before the check saw the link.
- The wrapper is generated from a new template in `claude_plugins/fls-dev/templates/wrapper_scripts/`
  by `fls-dev:init`, with the same placeholder, `"$@"` pass-through and project-specific section as
  the existing wrappers. If `fls-dev:init` lists wrappers by name, it and its tests gain the entry. `.claude/settings.json` gets allow entries for it in
  the forms the existing wrappers use.
- `.claude/ds/config.md`'s `Rebuild script` keeps the old wrapper, so a pin mismatch never blocks a
  rebase.
- `sdd:finish_worktree` reports a failing prepare step as `pre-test rebuild failed` and lands
  nothing.

### 6. FLS: CI, Docker, Tailwind, coverage

- `.github/workflows/tests.yml`: all seven `uv sync` lines become `uv sync --locked`. The
  `standalone-tests` matrix drops `panel_framework` and keeps `icons`.
- `fls-base/Dockerfile`: `git` joins the stage-2 `apt-get install` line. The infra directory is not
  a git repository, so the edit is made in place and nothing is committed there.
  The image has to be rebuilt and published before any deploy of an FLS commit carrying the pin.
- `tailwind.input.css` keeps importing `./tailwind.panel_framework.css`. Generated from an installed
  copy, that file names `./.venv/lib/python3.13/site-packages/panel_framework/...`. Generated from a
  linked worktree, it names that worktree's absolute path. Switching between the two means
  rebuilding Tailwind.
- `COVERAGE_FAIL_UNDER: 92` stays. If FLS's measured coverage falls below it once framework code
  leaves the coverage source, the plan records the measured figure for a decision.

### 7. FLS: docs, skills, generated files

- Regenerate `docs/app_structure.md` (`generate_app_map.py`) and
  `test_organisation/import_contracts.toml` (`/ds:app_map`). Then delete the baseline and exemption

## Testing

**Package**
- **Wheel and sdist contents.** `uv build` builds both into `tmp_path`, with the wheel built from the
  sdist. An optional `PANEL_FRAMEWORK_WHEEL` path tests a given wheel instead. The wheel must contain:
  - every file `git ls-files panel_framework` lists;
  - `LICENSE` and the Heroicons notice under `*.dist-info/licenses/`;
  - `License-Expression: MIT` in `METADATA`.

  It must not contain `tests/`, `node_modules` or `reference.css`.
- **Clean install.** In CI, the built wheel goes into a fresh venv, where `import panel_framework` and
  `manage.py check` against the standalone settings both pass.
- **Clean-clone suite.** The moved suites pass from a clean clone. A failure is fixed at its cause in
  the package, never with a shim.
- **Tag check.** The tag, version and changelog check fails on a mismatched tag.

**FLS**
- **Full suite.** It passes against the locked `v0.1.0` with the in-tree app gone. This includes the
  tests that moved in from the package's `needs_fls_host` set; each of those is found by name in the
  FLS run. `uv run manage.py check` reports no `panel_framework` messages under the default and
  `first_class` themes.
- **`0004`.** It is tested on a database holding the old table, its two `django_migrations` rows,
  and its ContentType rows with dependent `Permission` and `LogEntry` rows. It is also tested with a
  row in each listed app's model that has a foreign key to `ContentType`. All of these are removed,
  and `panel_framework_bulkactionrun` is untouched. A second run is a no-op. On a fresh database it
  drops nothing and does not fail.
- **`migrate`.** It completes with no `NodeNotFoundError` on a fresh database and on a database
  migrated at `main`.
- **Tailwind coverage invariant** (`base/tests/invariants/test_panel_framework_tailwind.py`). It
  builds FLS's real stylesheet and finds a class used only in framework templates, plus
  `.panel-surface`. It runs twice:
  - against the installed copy;
  - against a temporary copy of the package directory outside `site-packages`, with the command's
    view of the app path patched to it. This covers the linked-worktree path form without touching
    the venv.
- **`check_panel_framework_pin.py`.** It is tested in `tests/`, where `fls-dev` scripts are tested,
  using fixture `uv.lock` and `direct_url.json` files and a throwaway git repo in `tmp_path`, with no
  network. A locked git install passes. A clean editable copy at the locked commit passes. An editable
  copy at another commit fails, and so does a dirty one.
- **`link_panel_framework.sh`.** It is sourced in a subshell with `uv` stubbed on `PATH`, for four
  cases. With no paired worktree, and with a directory that has no `pyproject.toml`, it skips with
  the message, and the subshell carries on past it. With a paired worktree, it links and exports
  `UV_NO_SYNC=1`. When `PANEL_FRAMEWORK_DIR` is set, it overrides the pairing.
  `tests/test_rebuild_after_rebase.py`'s stubbed-tool log assertions gain the link step between
  `uv sync` and `npm i`.
- **Closing grep.** `rg 'freedom_ls\.panel_framework|freedom_ls/panel_framework|freedom_ls_panel_framework'`
  over `freedom_ls`, `config`, `claude_plugins`, `test_organisation`, `docs` and `.claude/skills`
  finds only `0004` and its test.

## Documentation and downstream

`upgrade_notes.md` beside this spec is written through `/fls-dev:update_upgrade_notes`. That command
derives the final flags from the diff. Its starting point:

```yaml
requires_migrations: true
requires_template_review: true
changed_template_paths:
  - panel_framework/reference/base.html
  - cotton/panel-icon.html
requires_settings_change: true
changed_settings:
  - INSTALLED_APPS          # hard
  - SILENCED_SYSTEM_CHECKS  # optional
requires_package_upgrade: true
changed_packages:
  - django-panel-framework @ git+https://github.com/preludetech/django-panel-framework.git@v0.1.0
requires_npm_install: false
changed_npm_packages: []
requires_tailwind_rebuild: true
```

`changed_template_paths` lists every framework template that FLS, First-Class or the template
overrides. `changed_packages` uses the pin, because a git dependency has no `==version` form.

**Breaking changes:**
- the in-tree app is gone;
- the import prefix and the app label are now `panel_framework`;
- check ids are now `panel_framework.<code>`;
- `educator_interface 0004` drops the old table and its rows.

**Manual steps**, each phrased as a check in the reader's project:
1. Run `uv lock`. The dependency arrives through `freedom_ls`, so `pyproject.toml` needs no entry.
2. In `INSTALLED_APPS`, replace `"freedom_ls.panel_framework"` with `"panel_framework"`, after
   `freedom_ls.base`.
3. Change any `include("freedom_ls.panel_framework.urls")` to `include("panel_framework.urls")`.
4. Rename `freedom_ls_panel_framework.*` entries in `SILENCED_SYSTEM_CHECKS`, and any
   `freedom_ls.panel_framework…` dotted setting value in the project's own settings.
5. Make the Tailwind build include the package's templates and `css/panel_framework.css` from the
   installed copy:
   - replace any `@import` that reads the CSS from the submodule path;
   - add the import where there is none;
   - if Tailwind builds in a Node-only Docker stage, feed it from a Python-dependency stage that runs
     first and installs `git` (`research_spikes.md`: the `uv:0.9-python3.13-bookworm-slim` image has
     none). The Tailwind stage copies the installed `panel_framework` directory to the path the
     input names.
6. Rebuild Tailwind and run `migrate`.

## Open questions

These were found after the up-front questions and took their defaults.

- Q: Which app hosts the drop migration? → A: `educator_interface`, as `0004` (assumed default:
  `base` has no migrations package, and `educator_interface` is the only app that ever depended on
  the old label. Overrule by editing Requirements §3.)
- Q: Do the check ids change with the label? → A: Yes, to `panel_framework.<code>` (assumed default:
  `v0.1.0` is the one release where every label-bound name changes together, and no FLS settings
  silence them. Overrule by editing Requirements §1.)
- Q: Where do the framework's tests live, given that FLS imports `tests.invariants.template_rules`?
  → A: `tests/` moves to the repo root and is not shipped. `template_rules` becomes the public
  `panel_framework.testing.template_rules` (assumed default: it keeps test-only code out of the
  wheel and gives hosts a supported import. Overrule by editing Requirements §1.)
- Q: Where do the package tests marked `needs_fls_host` go? → A: Into FLS, beside the code they
  exercise (assumed default: they need FLS's URLconf and icon set, which the package cannot supply.
  Overrule by editing Requirements §1.)
- Q: What does the package CI cover? → A: Python 3.13 and Django 6.0 only, with the SQLite standalone
  suite (assumed default: this matches the pinned `django>=6.0,<6.1` and specs 3 and 4's suite. A
  Postgres leg or a wider matrix can come with a later tag. Overrule by editing Requirements §1.)
- Q: Is a package worktree created automatically when an FLS worktree is set up? → A: No, by hand
  with the documented command (assumed default: most FLS branches never touch the framework and
  should run on the locked tag. Overrule by editing Requirements §4.)
- Q: The landing check runs inside the `Pre-test rebuild` step, which a `tier: none` landing skips.
  Is that gap acceptable? → A: Yes (assumed default: `tier: none` means no Python changed, so the
  pin cannot have drifted from the code. Overrule by editing Requirements §5.)
- Q: `.claude/fls-dev/config.md` lists only First-Class as a concrete project. How does the template

## Success criteria

- `github.com/preludetech/django-panel-framework` has tag `v0.1.0`, and its CI passes on that tag.
- `pip wheel --no-deps -w <empty dir> "<the pin>"` produces a wheel. The wheel test passes with
  `PANEL_FRAMEWORK_WHEEL` set to it.
- `uv sync --locked`, `uv run pytest` and `uv run manage.py check` pass in a fresh FLS clone with no
  paired package worktree.
- `uv run manage.py migrate` passes on a fresh database and on a database migrated at `main`.
  Afterwards `freedom_ls_panel_framework_bulkactionrun` does not exist.
- Two FLS worktrees, each paired with its own package worktree, import `panel_framework` from their
  own pair. With `UV_NO_SYNC=1`, `uv run python -c "import panel_framework; print(panel_framework.__file__)"`
  shows this.
- An FLS worktree paired with a package worktree ahead of the locked commit fails
  `prepare_landing.sh`, and an unpaired one passes it.
- `docker build` of `fls-base` succeeds, and `git --version` runs in stage 2.
