## 1. In this repo: the Deadlines effort so far

### 1.1 First attempt (2026-02), built then replaced

- `spec_dd/3. done/2026-02-19_19:25_deadlines/1. spec.md`: three models in `student_management` (`CohortDeadline`, `StudentDeadline`, `StudentCohortDeadlineOverride`), each with a generic FK to a topic/form/part, an absolute `deadline` datetime and `is_hard_deadline`. Resolution: item beats course; student override beats cohort deadline; with several registrations "most permissive wins for access, show all". Hard deadline passed on an incomplete item = locked in the table of contents.
- `2026-02-21_16:30_deadlines_deactivate`: a `DEADLINES_ACTIVE` flag was added purely for performance (skip the deadline queries when a deployment does not use them). `DEADLINES_ACTIVE` and the lock-on-expiry behaviour were then removed by spec 1.
- Why it was replaced (spec 1, "Removal" and `upgrade_notes.md`): the old model was absolute-date only, had no reason/actor, no relative dates, no policy, and hard-locked content. Spec 1 deleted all three models with no data migrated (`learner_management.0007_delete_deadline_models`).
- Lessons that carry forward:
  - The old design had NO notion of extension or pause. An "override" was just another absolute date. Anything built now cannot be bolted onto removed code.
  - Hard-lock-on-expiry was the thing users reported as punitive; spec 2 replaced it with opt-in consequences (close items, end access) rather than defaults. **[C1]** Pause must not reintroduce a hard lock by default: it blocks opening only while a pause is open, and it is staff-initiated.
  - Multi-registration "most permissive" was dropped. Since spec 2 (Decision 4) one `CourseProgress` has exactly one governing registration. **[C2]** A pause or extension attaches to the `CourseProgress` (or its governing layer), not to a registration pair.

### 1.2 Spec 1: `2026-10-25_17:46_deadlines-1-dates-and-overdue` (merged)

Decisions that constrain this spec (`1. spec.md`):

- **Override models** `CohortDeadlineOverride` and `LearnerDeadlineOverride` (`freedom_ls/deadlines/models.py`). Fields: layer FK (`cohort_registration` or `course_progress`), `collection_item` (null = the course time limit), `kind` (`fixed` | `relative` | `none`), `due_date`, `due_time`, `due_days_after_registration`, `replaced_value`, `set_by` (FK user, SET_NULL), `reason` (TextField). One row per (layer, collection item) and one per layer for the time limit, enforced by conditional `UniqueConstraint`s. **[C3]** An override today is a replacement VALUE, one per target. It has no "plus N days" form. The decided "extensions stack" (answers.md) means either a new kind/record that adds a delta on top of the resolved value, or a stack of extension rows; the one-row-per-target constraint cannot hold a stack. A pure value replacement is exactly LearnDash's "replaces, not adds" failure (4.4).
- **`replaced_value`**: canonical string of the value beneath when the override was saved (`relative:14`, `fixed:2026-03-14T17:00`, `none`), recomputed by `DeadlineOverrideFormSet` on each save, and compared to the live value beneath to show "Default has changed since this override was set (was X, now Y)". **[C4]** If extensions/pauses are inputs to the resolver, `content_default_for` / `canonical_beneath` must not treat an extension or pause shift as a "default change", or the admin note fires on every pause.
- **Resolver** (`freedom_ls/deadlines/resolver.py`): `resolve_deadline(layers, registration_date, tz)` is pure, no ORM. Layers most specific first, first layer holding a value wins (learner > cohort registration > content). `DeadlineValue`, `DeadlineLayer`, `ResolvedDeadline(due_at, source)`; `course_deadlines(course_progress)` and `course_deadlines_for(records)` with query counts independent of item/card count (spec 8 raised the ceiling from 5 to 6, `plan_notes.md`). **[C5]** The pause/extension shift goes inside this resolver (idea.md), must keep it pure and the query budget bounded. Any new table read (pauses, extensions) costs a query in `course_deadlines_for`, so read all pauses for all records in one query, and update the ceilings in `deadlines/tests/test_resolver.py` (last raised in spec 8: 5 to 6 and 6 to 7). `ResolvedDeadline.source` is `content | cohort_registration | learner`; **[C6]** decide whether a shifted date keeps its source or gains a visible "extended" attribution (the admin "Effective deadlines" field and `effective_deadline_policy` print `source`).
- **Dates**: a date-only due falls due at 23:59:59.999999 in the site zone; relative dates count from `registration_date` = date of `CourseProgress.created_at` in the site zone, computed on local dates so DST does not move the time. Time limit always ends at end of its day. `none` kind removes a deadline. `due_time` is never allowed on a time-limit row. **[C7]** The answers.md choice "whole days, rounded up; dates stay dates, learner keeps end-of-day" fits this: shift on LOCAL DATES, not by adding a timedelta to an instant, or a DST change inside a 4-day shift moves 23:59 to 22:59/00:59. A fixed-with-`due_time` value (e.g. 17:00) keeps its time of day and shifts by whole days.
- **Relative deadlines count from registration date.** A pause does not move the registration date. **[C8]** Shifting must be applied to the resolved due date (or equivalently to `registration_date`'s days offset), never by editing `created_at`.
- **Overdue** is `now > due_at` and only for incomplete items (`is_overdue`); an incomplete course with a passed time-limit end is overdue. Learner wording is "Deadline" / "Missed deadline", never "Due"/"Overdue". Time shown through `local_time` tag in the learner's browser zone.
- **Carry-over on re-sync**: overrides move with a re-placed item (one new, one stale placement); stale placements are not pruned. **[C9]** Extension rows keyed to `ContentCollectionItem` inherit the same stale-placement behaviour; a pause is keyed to `CourseProgress` and is unaffected by re-sync.
- Out of scope in spec 1, left for later: extensions and pause (3, 4), reminders (5), educator screens (6), overdue in Needs attention (7). Spec 1 QA found 0 bugs; notes only: unfold inline rows show "CohortDeadlineOverride object (uuid)" because the models have no `__str__` (cosmetic, `qa_report.md`). **[C10]** Give new admin-edited records a `__str__` so inline row headers read well.
- `upgrade_notes.md`: new app `freedom_ls.deadlines` must be in `INSTALLED_APPS`; no system check detects it missing. Relevant only if this spec adds a new app/model: add to the existing `freedom_ls.deadlines` app.

### 1.3 Spec 2: `2026-11-01_23:53_deadlines-2-consequence-policy` (merged)

Decisions and findings that constrain this spec (`1. spec.md`, `qa_report.md`, `todo.md`, `upgrade_notes.md`):

- **Policy layer order**, most specific first: `registration, cohort, organisation, course, site, settings`. Every layer can hold every setting; switches are three-state (`inherit/on/off`); `grace_window` is a nullable `DurationField` (null = inherit, zero is a real value). Six sparse `*DeadlineConfig` models, one-to-one `related_name="deadline_config"`, built on abstract `DeadlineConfigFields`; `LayeredDeadlinePolicy.LAYER_ORDER` is "the only place the order is written"; settings layer is `DEADLINE_POLICY_DEFAULTS`, validated by system checks E001 (must name exactly the six fields with set values) and E002 (policy class). **[C11]** The pause limits (self-pause allowed, max count, max length) are new fields on `DeadlineConfigFields`. That means: a migration on all six models, new `CheckConstraint`s (spec 2 added one per choice field and one for `grace_window >= 0`; limits need `>= 0` or `>= 1` checks), E001 must be changed to name the new fields exactly (it currently says "exactly the six fields"), `ResolvedDeadlinePolicy` and its `sources` mapping, `DEADLINE_POLICY_DEFAULTS` default dict, upgrade notes (the `DEADLINE_POLICY_DEFAULTS` setting now requires the new keys; an existing project that set the dict will FAIL E001 on upgrade unless the check is made tolerant or the notes call it out), and the `effective_deadline_policy` admin panel. A custom `DeadlinePolicy` subclass written against spec 2's contract also needs to return the new fields. Spec 2 chose an abstract base for the field set; `DeadlineConfigFields` already exists, so no new abstract class is needed (project rule: no new abstract bases unless asked).
- **Tri-state vs nullable for limits**: "inherit" for a count/length is null, "unlimited" needs its own representation, and "0 pauses" means "no self-pause". **[C12]** Mirror spec 2's lesson (QA 1.1: "all-Inherit row saves and reopens as Inherit with empty grace; grace 0 reopens as 00:00:00"; spec test "round-trips Inherit as inherit/null, not off/zero"): zero and unset must stay distinct for count and duration limits.
- **Grace window** is added to the resolved due instant: `close_instant = due_at + grace_window`; "any deadline override that moves the date moves the close instant with it" (Decision 6). **[C13]** This is the structural answer to idea.md's "one action moves due and close together": there is no stored close date, so an extension that moves `due_at` moves the close instant and the overdue mark together. The Canvas due/Until mismatch (4.3) cannot occur here, provided the extension is applied inside the resolver before `shows_overdue`/`close_instant`/`access_end_instant` are computed. The risk is the opposite: a second code path (admin "effective deadlines", dashboard card, closing in `form_submit_and_exit`) that reads raw columns or the pre-shift value. Spec 2 had to add `_deadline_policy_or_none` plumbing in each view; every consumer of `course_deadlines` gets the shift automatically only if the shift is inside it.
- **Boundaries**: `now > instant` for overdue, close and access end (Decision 7); a completed item never closes (9); a course already completed (`CourseProgress.completed_time` set) never has access ended.
- **Closing and attempts**: "A closed form with an open attempt can be submitted, not continued, whatever its exit mode" (Decision 10). `form_submit_and_exit` on a closed placement or an ended-access learner skips the `submit_on_exit` guard and the answer save and only calls `complete()`; posted answers are not saved. `form_start`/`form_fill_page` on a closed item redirect to the item page (the closed notice), which has a "Submit your answers" button for an open attempt. **[C14]** This is the opposite of answers.md's decided pause behaviour ("Frozen. The attempt and its answers are kept, and the learner continues it after resume"). Pause must NOT route through the closed/ended path, or an open attempt would be finalised (scored) by the "Submit your answers" button or by `form_submit_and_exit`, which is destruction of in-progress work. Specifically, the `access_ended` branch of `form_submit_and_exit` (`learner_interface/views.py` ~2338: `closed = decision.access_ended_at is not None or _is_closed_for_learner(...)`) and the `_course_access_redirect` allow-list (`submit-and-exit`, results of a completed attempt) must NOT be reused for paused courses unless submit-and-exit is refused while paused. Also decide whether a paused-and-closed-by-deadline item is possible: an item can only close past its close instant, and the pause shifts unmet dates on resume, so an item that was closed before the pause stays closed only if its shifted date is still past; after the shift it may reopen. State this explicitly.
- **Where access end is enforced**: `DeadlineEnforcingBackend` wraps the inner course access backend (loader returns `VisibilityEnforcingBackend(DeadlineEnforcingBackend(inner))`), only when the inner decision has `can_access_content=True`; adds `access_ended_at` and `after_access_ended` to `CourseAccessDecision`; cost cap of 18 queries; `is_registered_for_course` unchanged, so hidden-course visibility, messaging peers and educator confirmations do not follow a deadline; `override_access_to_free()` bypasses it. Decision 15: ending access writes nothing (no `is_active=False`, no `course.unregistered`, no stored status). A deactivated registration gets the inner decision, not "access ended" (spec 2 test). **[C15]** A paused course is the same shape: read at access time, registration stays active (idea.md). The natural design is a sibling decision field (e.g. `paused_until`/`paused_at`) set by the same wrapper, plus `after_access_ended`-like handling of what a paused learner can open ("nothing can be opened; past results stay visible"). Reuse the "learner always entitled to the score they earned" rule (Decision 13) for results pages, but NOT the "submit and exit stays open" allowance (C14). The 18-query cap must be re-checked: a pause lookup adds a query (per record) and must be folded into the existing `course_progress_for` read, with a test that the count does not depend on the course's size.
- **What an ended learner can open**: `after_access_ended` = `outline_and_results` (default; outline + completed items + results) or `nothing`. The dashboard keeps an ended course in the current list with "Access ended <date>"; `course_detail` shows "Your access ... ended on <date>. Your progress is saved. Ask your educator to restore it."; `course_home` redirects an ended learner to `course_detail`. **[C16]** Idea.md wants "Course detail and the dashboard show the paused state and the planned resume date" and "past results stay visible"; model the paused copy on the access-ended copy, one shared label partial (`partials/deadline_labels.html` is already the single source for TOC row, item header and card line) and the same `outline_and_results` behaviour. Note the dashboard and course-detail screens already key off `access_ended_at`; a paused flag must not make `access_ended_at` truthy (different copy, "Access ends" would be wrong).
- **Restore = a time-limit override** (Decision 14): a fixed end date (allowed from spec 2: `kind=fixed` on the time limit, `due_date`, no `due_time`) or a day count on a learner or cohort override. Staff pre-spec-3 restore access by giving a new end date; this is exactly the Moodle/TalentLMS/LearnDash "reactivate with a new end date" pattern the idea contrasts with. **[C17]** An "extension of the time limit" in this spec overlaps with restore: decide whether extending a time limit that has already ended restores access (it should, since `access_end_instant` moves) and whether that is described as an extension or a restore in the audit/webhook.
- **Layer owners / registration governs** (Decisions 4, 5): the registration layer is the row of whichever registration minted the `CourseProgress`. **[C18]** The pause limits resolve through these layers using `CourseProgress`; limits are read, not stored, on the pause row (staff are not held to them; spec 4's self-pause is).
- **QA findings and Decide items spec 2 left** (relevant to the same surfaces):
  - Bug B1 (UNRESOLVED in `qa_report.md`, later `todo.md` lists the Decide items as done): the dashboard card's "Closed" deadline line dropped the item name. Lesson: every new state added to `partials/deadline_labels.html` (paused, extended) needs a card variant that names the item/course.
  - Bug B2 (UNRESOLVED in the report): the results page under `after_access_ended=nothing` still drew an empty outline panel (empty `course_index` passed to the chrome). **[C19]** A paused learner's results page needs the same care: a state that hides the outline must hide the panel, not pass an empty list.
  - Decide items in `todo.md` (all ticked): mark_overdue off dropped the card date; `<c-callout>` dropped its `class`; a closed failed quiz read "Closed" with no way to results; a failed quiz's results said "try again" when no retry was offered; the course detail outline ignored closing. **[C20]** Each is "a new blocking state forgot a surface". For pause, enumerate every surface: TOC rows, item header, course detail outline, results page retry/next/previous, dashboard card, `all_courses`, the retry button, the "Next"/"Previous" buttons (QA note: an ended learner is offered "Next", which only bounces to detail), and the "Free - open to everyone / One click" side panel that still showed above the ended message.
  - Observations not actioned: ended learner's player outline still prints "Missed deadline" chips on locked rows. **[C21]** Spec 3 should decide whether a paused course shows the overdue chip (idea.md: no reminders to a paused learner; the clock is stopped, so showing "Missed deadline" while paused is the same Moodle confusion in 4.3). Recommend: suppress overdue/closes/access-ends wording while paused and show "Paused" instead; on resume the shifted dates apply.
  - Test-plan errors recorded: the player outline test expected wrong locked/closed rows because sequential unlock wins over closing (Decision 11). Pause tests should assume sequential unlock still decides what is `BLOCKED`.
  - Test tooling note: a scripted admin delete hit the admin header's "Log out" button. Not a product issue; relevant when writing QA for an admin action button.
- **Out-of-scope items spec 2 explicitly pushed to spec 3**: "Extensions, pause and pause limits (spec 3); learner self-pause (spec 4)". The roadmap also states in spec 2: "`notify_educators` is stored and resolved only", raising it is spec 5. The roadmap notes record spec 2's resolved unknowns and "update the ideas of specs 3, 4, 6 and 7". **[C22]** Pause/extension must not raise educator notifications (spec 5), only the learner notification (idea.md).

## 2. In this repo: other "state with a reason and an actor" and "shift dates" logic

Search terms: `reason`, `paused`, `suspend`, `extension`, `deactivat`, `is_active`, `access_ended`.

- **No pause, suspend, extension or date-shift logic exists anywhere** under `freedom_ls/` (checked: no function named `*shift*`, `*extend*`, `*extension*` outside unrelated `role_based_permissions/types.py:178` and `content_save.py`). `research_current_deadlines.md` section 4 says the same. This spec is the first.
- **Records with a reason**: only the two deadline override models (`reason` TextField, `set_by`), `AuditLogEntry.reason` (`CharField(max_length=REASON_LENGTH)`, `freedom_ls/audit_log/models.py:103`) and `learner_management` registration-rule `preview_reason`/`final_reason` (a different thing). The pattern for a state flip with a reason is not a status table but a service function plus an audit entry:
  - `freedom_ls/learner_management/learner_actions.py`: `deactivate_learner`, `reactivate_learner`, `deactivate_cohort`, `reactivate_cohort`, `deactivate_registration` (returns False when already in that state), `register_for_course` (reactivates an inactive registration). Each is `transaction.atomic()`, locks the row (`select_for_update`), flips `is_active` with `save(update_fields=["is_active"])`, and calls `record_learner_entry(learner, "<noun>.<verb>", actor, reason=reason, details={...})`. Webhooks fire from the model's `post_save` receiver or via `fire_webhook_event_on_commit` (`learner_management/utils.py:133`), never inline.
  - **[C26]** Pause/resume/extend should be service functions of this shape: atomic, idempotent (False when no change), audit entry with `actor` and `reason`, webhook `on_commit`. The admin and the later educator screen (spec 6) and self-pause (spec 4) all call the same function. The roadmap says spec 6 "Every change is audit-logged"; hence audit codes need to exist now or spec 6 invents them. Add codes to `freedom_ls/audit_log/actions.py` (registry of `AuditAction(code, label, describe, group)`; groups today: Learners, Cohort membership, Course registrations, Cohorts, Staff and roles, Other). A new group "Deadlines" would be needed or use "Course registrations"; note `AUDIT_ACTION_GROUPS` is a fixed tuple and `test_vocabulary.py` checks every code against glossary nouns and verbs.
- **Webhook event types** (`freedom_ls/base/webhook_event_types.py`): `FLS_WEBHOOK_EVENT_TYPES` is a list of `("noun.verb", label)`; `WEBHOOK_EVENT_TYPE_SAMPLES` has one sample payload per type (used by the admin test button). Existing payload convention: user events carry `user_id`, `user_email`; registration events add `course_id`, `course_title`, `organisation_id`, `course_progress_id`, `registered_at`; learner events carry `learner_id`, `organisation_id`; cohort events `cohort_id`, `cohort_name`. File header: "A webhook event type that is also an audit action carries the audit action's code and label" (invariant tests `audit_log/tests/invariants/test_vocabulary.py:95-123`: every event type uses a glossary noun and verb; a shared type is the same string and label in both; webhook-only types are exactly the ones listed; every event type has a sample payload). **[C27]** Pause, resume and extension each need: an entry in `FLS_WEBHOOK_EVENT_TYPES`, a sample in `WEBHOOK_EVENT_TYPE_SAMPLES`, a glossary noun and verb (`fls-dev:domain-glossary`: "pause"/"extension" are not yet nouns; they must be added or the vocabulary test fails), and, if staff-initiated, the same code as the audit action. Event names in the style `course_pause.started`/`course.paused`/`course.resumed`/`deadline.extended` are open; "A resume also fires when it was planned" (evaluated when read) means the planned-resume webhook is fired by spec 5's sweep (idea.md), so the payload must work with `actor=None`. `deadline.missed` is spec 5's. Payload convention per idea.md: user, organisation, learner, course.
- **Registration inactive vs active again** (`learner_management/models.py`): `_is_new_or_reactivated`, `loaded_is_active` tracking (lines 34-126) so `post_save` receivers know whether a save turned `is_active` on or off; every `is_active` writer saves with `update_fields=["is_active"]`, which skips `auto_now`, so "the stamp rides along" (line ~141). `LearnerCourseRegistration` / `CohortCourseRegistration` have `is_active`. `course_access` never reads `is_active` in its own code; tests show "A deactivated registration gets the inner decision, not 'access ended'" (`course_access/tests/test_backends.py:551`). **[C28]** A pause record's `status`/`ended_at` should follow the same dirty-field discipline if a `post_save` receiver fires the webhook: "resume" is a state transition and must fire once, even when the planned-resume branch and a staff resume race. Fire from the service function or a receiver that checks the previous state, never both.
- **Reactivation semantics are already worked out and reusable as a lesson**: `register_for_course` and `self_register` reactivate an inactive registration; "The log records staff actions, so a new self-registration writes nothing; a reactivation undoes a staff action, so it is written, as the system" (`learner_actions.py:348`). **[C29]** Analogue for pause: a staff pause is logged and notifies; a planned-resume taking effect is "the system" acting, and its webhook is fired by the sweep, whether or not an audit entry is written for it is a decision to settle (self-pause in spec 4 writes nothing, per idea.md "A learner pausing themselves is not notified").
- **Why not use `is_active=False` on the registration**: `is_active=False` fires `registration.deactivated` and (per idea.md and spec 2 Decision 15) "No `course.unregistered` fires and the course does not drop off the dashboard". Deactivating also hides the course (`NOT REGISTERED`, "Enrol for free" - spec 2 QA 4.5.2). Confirmed: pause must not be built on `is_active`.
- **Admin actions with an intermediate form/page**:
  - `freedom_ls/registration_rules/admin.py:299-373` - overrides the change view to render a confirmation/preview `TemplateResponse` (`admin/registration_rules/preview.html`) with posted fields carried as hidden inputs (`posted` list) and `admin_page_context(request, model_admin, title)` from `site_aware_models/admin.py:92` (supplies sidebar, theme, breadcrumb). This is the in-repo precedent for a two-step admin flow.
  - `freedom_ls/api_admin/admin.py:196` - `TemplateResponse(request, "admin/api_admin/key_issued.html", context)` for a one-time result page.
  - `@admin.action` is used by `hr_attributes/admin.py:57,72` (Deactivate/Activate), `webhooks/admin.py:116,122,252`, `api_admin/admin.py:106` (Revoke, `permissions=["change"]`), `referral_tracking/admin.py:179`. All are one-click, none asks for a reason. **[C30]** No existing admin action takes a free-text reason via an intermediate form. A pause/extend "action" with required `reason` is new ground: build it on Django's admin-action pattern (action returns a `TemplateResponse`/redirect for a form page, form posts back), using `admin_page_context`, `permissions=[...]` (not `is_staff`), `fls-dev:admin-interface` conventions, and RBAC: check which role may do it (an organisation admin sees only their organisation: idea.md says "staff pause and resume any learner", but `educator_interface` invariants test organisation isolation `educator_interface/tests/invariants/test_organisation_isolation.py`, so the Django admin action must not leak across organisations/sites). Alternative: an inline on `CourseProgressAdmin` (as deadlines inlines already attach there via `deadlines/admin.py`) with a `reason` field; that works for pause/resume and per-item extension but not for the "shift the whole course by N days" action. Both paths exist; the inline path is lower risk and has precedent (`DeadlineOverrideFormSet` stamps `set_by` from `request.user`).
  - `ConstraintValidationFormMixin` (`site_aware_models/forms.py`) is the repo's way to enforce `UniqueConstraint`s as form errors in admin (used by every deadline config admin); a new constraint (e.g. "one open pause per CourseProgress") should use it, or the admin returns a 500 (spec 2 QA 1.2 checked "no 500").
- **Notifications**: `fls-dev:notifications` skill (idea.md reference) governs in-app notifications; email arrives later with `user-communication-2-notification-email` (roadmap). No notification code touches deadlines yet. **[C31]** Notify on staff pause/resume/extension only; the planned-resume and a self-pause do not notify (idea.md). The extension can touch hundreds of items in the whole-course shift; emit ONE notification per action, not per item (the research on notification fatigue, sentiment file section e; Docebo/Edinburgh).

## 3. Parent-effort research (spec_dd/1. next/deadlines/)

Only what bears on pause and extension.

### research_deadlines_user_sentiment.md
- **(b) Extensions**: Moodle's "Grant extension" with multi-select is liked; Canvas multiple per-student extensions are "tedious and difficult" because each assignment is edited separately; the pain is repetition. Canvas "Assign To": extending "Until" alone does not stop the late flag. Overrides don't survive Moodle backup/restore. LearnDash extend-access REPLACES the existing end date. Wish: stackable extensions (a third-party plugin exists because purchased days should add onto existing expiry). Open edX lets learners shift suggested due dates themselves once a date has passed. Institutional extension policies show staff expect fees, limits (one 8-week extension, a second for severe illness, 16-week cap), request deadlines and a documented reason.
- **(c) Pause**: evidence is thin for LMSs. Subscription surveys (vendor, commercial interest) say pause is the most wanted feature and 25% pause instead of cancelling; medical leave is accepted when documented and time away may or may not count against the maximum completion time (Royal Roads counts it). Gym grievances: billing continued during freezes, freezes refused or hard to get; regulators got involved. No community thread found asking for "pause course clock" in Moodle, Canvas, TalentLMS or Docebo.
- **Implication 2** (STRONG): make per-learner extension cheap in bulk, from the learner's progress view as well as from the item. Pain is repetition. Spec 3 covers one learner (single item or whole-course shift), bulk across learners is spec 6. **[C32]**
- **Implication 3** (STRONG): one extension action moves due and close dates together, impossible to apply so that it still shows late. See C13.
- **Implication 5** (STRONG for Coursera): never destroy learner work on reset, extend or pause. See C14.
- **Implication 7** (MODERATE; no LMS thread, rests on adjacent domains): model pause as a first-class record with a reason, an approval option, resume date, and a rule for shifting dates; "Hard rule from the gym complaints: stopping the clock and any charge must happen together and be easy to request." FLS has no charge, so only the easy-to-request half applies; approval and fees are out of scope (idea.md).
- **Implication 8** (MODERATE): cap and document extension and pause: count and length limits, request-before-end rules, documented reason; configurable per course/organisation. Spec 3 covers pause limits as policy settings only; extension limits are not in the idea, so do not build them (project rule: do not build what is not requested).
- Also relevant: implication 4 (overrides must follow or visibly flag base-date edits and survive course copy): C4.

### research_lms_deadlines_landscape.md
- **(b) overrides**: Moodle precedence user > group, most lenient wins; Moodle 5.2 mentions a "Reason for override" note; Moodle overrides are not updated when the base due date changes; TalentLMS instructor can change the expiration for one user; LearnDash extend replaces; Moodle enrolment suspend then reactivate with a new "Enrolment ends"; Coursera reset shifts assignment deadlines forward, unavailable on degree/MasterTrack, and community posts report loss of submissions. Recurring design points: precedence, an audit note, and whether the override tracks base-date edits.
- **(c) pause**: no LMS has first-class clock-stop semantics; LMS norm is reactivate with a new end date. Stripe `pause_collection`: subscription stays `active`, `resumes_at` for auto-resume, `behavior` for invoices created during the pause. Gymbox: max 3 months frozen in any 12, a freeze extends the minimum term by the frozen months. Nuffield: up to 12 months, only for listed reasons, sometimes with proof. Pattern: limits on count and total length per period, reason-gated, optional staff approval, fees, term extension equal to paused time, auto-resume at a set date. **Gap flagged by the researcher: no source found on how item-level due dates shift on resume.** Coursera and TalentLMS shift forward by choice, not by computed paused duration. **[C33]** FLS is designing this from nothing; the whole-days-rounded-up rule is original. There is no precedent to copy and no reported failure mode, so test it harder (see section 5).
- Patterns most relevant: pause as a first-class record (start, optional planned resume, reason, actor, status); on resume shift the course window and UNMET relative dates by the paused duration; limits max count and max total length per period (note: gyms use "per period"; the idea says "how many pauses, how long a pause may last", not per period, so per-pause length and total count only, no rolling window); destructive actions non-destructive.
- Pitfalls: "extending only the close date" (Canvas); "extension stacking" (LearnDash, vendor claim); "overrides not tracking base-date edits" (Moodle); destructive resets (Coursera); reminder anchored to enrolment date does not move when deadlines are extended (Docebo). **[C34]** Spec 5 reminders will read the effective deadline, so the shift must be in the resolver (C5), and no reminder for a paused learner (idea.md).

## 4. Elsewhere: what went wrong and the lesson

### 4.1 Coursera "reset deadlines" lost work
- Learners report assignments and quiz submissions disappeared or locked after a reset: <https://community.deeplearning.ai/t/my-compleated-assignments-disappeared-with-no-warning-after-deadline-reset/5861>, <https://community.deeplearning.ai/t/resetting-deadline-removed-quiz-and-home-submissions/7643>, <https://community.deeplearning.ai/t/assignment-progress-lost/3609>. Landscape file (section b) summarises: a reset can move the learner to a new course version/session and lose submissions. A "reset" is also only offered after missing two assessment deadlines or about two weeks, so learners cannot reset early (<https://community.deeplearning.ai/t/how-do-i-reset-my-deadlines-to-get-the-new-content-without-waiting-for-two-weeks-to-get-the-new-content/516413>); advisory deadlines "auto-reset with no grading penalty" (<https://community.deeplearning.ai/t/how-can-i-reset-the-course-deadline-i-am-not-trying-to-pursue-a-grade/270822>).
- What went wrong: the reset coupled a date shift to a session/version change, so the mutation touched the learner's data, not just the dates.
- Lesson: a date shift must only write date-related rows (pause/extension records), never touch `TopicProgress`, `FormProgress`, attempts or answers. **[C35]** Add tests that a pause, resume and extension (single and whole-course) leave every progress row and answer byte-identical (row counts and `updated_at`), and that resume never recreates a `CourseProgress` (a cohort move mints a new `CourseProgress`, spec 1 Decision 6; that is not what resume does).

### 4.2 Open edX "reset deadlines" / shift dates
- The Open edX reset works by changing the learner's schedule start date (personalised learning schedule), so suggested due dates shift (<https://docs.openedx.org/en/ulmo/educators/how-tos/course_development/set_course_pacing.html>). A reset is available only if a sequential's due date has passed and it is incomplete. Search turned up no named open bug but showed repeated fixes in the same area: "Update the shift dates logic for problems" (<https://git.andalsoftware.com/Andal.LND/edx-platform/src/commit/4230f1fb3922a2df3e86b8789b4cd677dfdf4b1d>), "Fixes for shift deadlines during masquerade in Learning MFE" (<https://git.andalsoftware.com/Andal.LND/edx-platform/commit/2f7fcdea8595542fc4bdd5471f7b3e4abffc59ed>), and "AA-12 reset self paced due dates" (<https://git.andalsoftware.com/Andal.LND/edx-platform/src/commit/be3b15062198d9d8f97be9ebdf19e42bcdcb6b4d>). One commit's docstring says that changes to the reset endpoint must be mirrored by a related function ("If updates are happening to the logic here, ALSO UPDATE the `reset_course_deadlines`"), i.e. the shift logic lives in two places that must be kept in step (read from the search summary, not confirmed against the source). Evidence is a commit trail, not an incident write-up: treat as WEAK.
- Lesson: keep ONE shift implementation. **[C36]** Idea.md decided "the whole-course case reuses the pause shift maths" and "applied inside the one resolver, not in a second one" - the same trap. Put the whole-day rounding and the "only unmet deadlines" selection in one function used by resume, the whole-course extension and (later) spec 4's self-resume. Open edX also shows that shifting is state-dependent (past-due and incomplete only); FLS's "met deadlines are untouched" rule is the same filter: define "met" as the item complete at resume time (or at shift time), and say what happens to an item completed AFTER the shift was recorded but before another resolution (a deadline that is computed at read time cannot "un-shift" it, so the shift rule must be a function of current completion, or the shift is stored per item at resume).
- Also from the same family: Open edX relative dates anchor to the enrolment/start date and shifting that anchor moves every date at once (pause by moving `registration_date`). FLS cannot do that without changing relative-date semantics for other layers (C8), and moving the anchor would shift MET deadlines and fixed dates inconsistently.

### 4.3 Moodle: extension vs override confusion (overdue shown while open)
- A user override changes the Due date column; "Grant extension" only adds "Extension granted until" text in the Status column. Result: students with an extension still receive due-soon and overdue notifications tied to the original date (<https://tracker-old.moodle.org/browse/MDL-85113>); calendar and timeline disagree, and adding a user override removes the extension event (<https://tracker-old.moodle.org/browse/MDL-85403>, marked duplicate); extensions not shown in the dashboard timeline (<https://tracker-old.moodle.org/browse/MDL-77441>) nor in the grader's submission page (<https://tracker-old.moodle.org/browse/MDL-78639>); for an overridden student a submission after the default date but before the override date can show as on time on the summary page while the grading table marks it late (<https://tracker-old.moodle.org/browse/MDL-57708>). Original design intent for the student view: show an "Extension due date" next to time remaining (<https://tracker-old.moodle.org/browse/MDL-31295>). Warwick notes Grant extension only appears when the assignment has a due date (<https://warwick.ac.uk/services/digitallearning/support/guides/moodle-guides/mdl-98>).
- What went wrong: two representations of "this learner's date" (an override row, and an extension note) that different surfaces read differently.
- Lesson: **[C37]** one representation, one reader. FLS has the right shape (a single resolver feeds the TOC, card, detail, policy, closing and the admin panel) but spec 3 must not create a second place where a date is held. Test that for the same item and `now`, the TOC, player header, dashboard card, `effective_deadlines` admin field, `close_instant` and the (future) reminder agree after: an extension, a pause in progress, and a resume. Spec 2 already ran that class of test ("The TOC and the redirect agree for the same item and `now`"). Also: a notification that fires on the original date is the Moodle bug; spec 5 must consume the resolved date, and spec 3 must make "no reminder for a paused learner" hold by the pause being visible to the same resolver call.

### 4.4 LearnDash extension replaces, not adds
- LearnDash "Extend access" sets a new end date, replacing the existing one; group end dates cap the course extension (<https://learndash.com/support/kb/add-ons/users/extend-access/>, <https://learndash.com/support/wp-json/wp/v2/docs/5491>). A third-party plugin exists specifically because purchased days should add onto existing expiry (<https://ko.wordpress.org/plugins/course-access-extender-for-learndash/>); the landscape file records a vendor claim that core "mishandles stacked extensions" (vendor claim, unverified).
- Lesson: answers.md has already decided "stack". **[C38]** Define stacking precisely: each extension is "N more days" or "to this date" applied on top of the current resolved date, pauses included. Clarify "to this date" in a stack: it sets a target; a later "to this date" earlier than the current resolved value would shorten the deadline - decide whether to reject it (an extension cannot shorten), the sensible default. Also decide how an extension "to this date" interacts with a later pause shift (pause shifts the unmet dates after the extension is applied, in order of creation), and whether the stack is ordered by creation time (a pause started before an extension vs after it: for whole-day shifts these commute only for "N more days"; "to this date" does not commute with a later pause, so order must be defined).

### 4.5 Stripe pause_collection pitfalls
- Source: <https://docs.stripe.com/billing/subscriptions/pause-payment>. Facts: the subscription stays `status=active` while collection is paused; invoices are still generated, with a `behavior` (`void`, `keep_as_draft`, `mark_uncollectible`) deciding what happens to them; invoices created before the pause are NOT affected and keep retrying unless voided; with `behavior=void` all invoices created before `resumes_at` are voided immediately; upcoming-invoice emails and webhooks are suppressed during the pause; with no `resumes_at` the pause is indefinite until `pause_collection` is unset; unsetting only affects future invoices; custom code that finalises invoices can conflict with the setting. A separate full pause (`status=paused`, stops invoice generation and advancing periods, needs flexible billing mode) exists: <https://docs.stripe.com/changelog/dahlia/2026-05-27/pause-subscriptions>. The search found nothing on proration for `pause_collection` (not verified here).
- What goes wrong in practice (inferred from the docs, not from a post-mortem): the pause only affects things created from now on, leaving earlier artefacts (invoices already created) behaving as before; "still active" status misleads code that assumes active means billing as usual; indefinite pauses with no `resumes_at` pile up.
- Lessons: **[C39]** (a) Like Stripe, FLS keeps the registration `active` through a pause; every consumer that asks "is this learner active" (dashboard, messaging peers, educator lists, reports, at-risk lists in spec 7) must not read "active" as "currently working". Spec 7 will list overdue learners: it must exclude paused ones; coordinate (roadmap says 7 runs beside 3). (b) A pause with no planned resume is indefinite: decide whether the policy `max length` applies to staff pauses (idea.md: no) and whether the admin warns or the resume date is optional; Stripe's own default is "indefinite", FLS idea.md allows it ("may carry a planned resume date"). Without a limit, an abandoned pause would stop the clock forever and suppress reminders forever. State that staff-created open-ended pauses are visible in a list (admin changelist filter "currently paused") so they can be found. (c) Stripe's `behavior` flag shows that "what happens to things already scheduled in the paused window" needs a rule: for FLS, the things in flight are an open form attempt (frozen, C14), an already-sent reminder (n/a, spec 5), and an item that closes during the pause window (a pause stops the clock, so nothing should close or end access during it - the resolver must treat `now` as frozen at pause start for all consequence checks). (d) Suppressed notifications: no reminder for a paused learner but staff are notified of nothing; a long-open pause should be discoverable.

### 4.6 Other
- TalentLMS/Moodle/LearnDash reactivate with a new end date (landscape section c) - no post-mortems found; the failure is that the shifted end date is guessed by staff rather than computed from the pause, which is the gap this spec fills. <https://telsupport.brookes.ac.uk/articles/how-do-i-reactivate-suspended-enrolments-in-moodle/>
- Gym freeze grievances (billing continued during closures, freezes hard to get, regulators): <https://billypenn.com/2020/04/10/some-philly-gyms-delayed-membership-freeze-causing-customer-outrage/>, <https://ag.ny.gov/press-release/2020/attorney-general-james-delivers-financial-relief-new-york-sports-clubs-and>. Lesson already in implication 7: the pause and its consequence (stopped clock) must happen together and be easy to request. For FLS: the pause must take effect immediately when staff save it, and the learner must be told at once (idea.md notification). A pause staff meant to start tomorrow ("planned start") is not in the idea; start is now.
- Canvas "Assign To" pitfalls (extend Until and due together; accidental removal of "Everyone" wiped others' access): <https://help.harmonizelearning.com/hc/en-us/articles/32768471875469>, <https://support.csuchico.edu/TDClient/1984/Portal/KB/PrintArticle?ID=113756>. Lesson (C13): there is no "Everyone" row to remove in FLS; deleting a learner override returns to the layer beneath. Deleting an EXTENSION record from the admin must therefore be treated as an undo (the date drops back), and the admin must make that obvious.

## 5. Constraints on this spec (consolidated)

Locked by prior specs or the idea:
- C1 No default hard lock; pause blocks opening only while open.
- C2 Pause/extension hangs off the `CourseProgress`, not a registration pair.
- C3 Extensions are additive but today's override row is a replacement value, one per target: add a delta form or a separate record.
- C4 `replaced_value` / "Default has changed" must not fire because of pause/extension.
- C5 Shift lives in `resolve_deadline`/`course_deadlines(_for)`; stay pure; read all pauses/extensions in bounded queries; update the ceilings (currently 6; see spec 8 `plan_notes.md`).
- C6 `ResolvedDeadline.source`: decide whether to carry an "extended/paused" attribution.
- C7 Shift in whole local days; dates remain dates; DST-safe; `due_time` preserved.
- C8 Never edit `created_at` or `registration_date`.
- C9 Extension rows keyed to `ContentCollectionItem` share the stale-placement behaviour.
- C10 `__str__` on new admin-edited models.
- C11 Pause limits are new fields on `DeadlineConfigFields` for all six models: migration, constraints, E001 exact-field check, `ResolvedDeadlinePolicy`, defaults dict, upgrade notes (existing `DEADLINE_POLICY_DEFAULTS` overrides will fail E001), effective-policy panel, custom-policy subclasses.
- C12 Unset vs zero vs unlimited must stay distinct for the limits.
- C13 Due and close move together by construction (close = due + grace); keep every consumer on the resolver.
- C14 Pause must not use the closed/ended "submit and exit" path; open attempts are frozen.
- C15 Paused is a read-time access state like access-ended, registration stays active; keep within the 18-query cap and constant in course size.
- C16 Reuse the `deadline_labels.html` partial and the `outline_and_results` behaviour for results; `access_ended_at` must not be set for a pause.
- C17 Extending an ended time limit restores access; say so.
- C18 Limits are read through the layer order from the `CourseProgress`; staff are not held to them.
- C19, C20 Enumerate every surface (empty outline panel, retry/next/previous, dashboard card item name, `all_courses`, "Free · open to everyone" side panel).
- C21 Do not show "Missed deadline"/"Closes"/"Access ends" wording while paused.
- C22 No educator notifications (spec 5).
- C23 QA admin URLs `/admin/freedom_ls_deadlines/...`; run on the Site's port.
- C24 Content layer is one layer (spec 8).
- C25 Record shape is an API for specs 4, 5, 6: keep start, optional planned resume, reason, actor, status, stored shift.
- C26 Service functions (atomic, idempotent, audit, on-commit webhook) not admin-only logic.
- C27 Webhook event types need `FLS_WEBHOOK_EVENT_TYPES`, samples, glossary nouns/verbs, audit code parity.
- C28, C29 Fire the resume webhook exactly once; the planned resume is fired by spec 5's sweep with no actor.
- C30 No precedent for an admin action that takes a reason: choose action+intermediate form or inline; respect organisation/site isolation.
- C31 One notification per action.
- C32 Bulk across learners is spec 6.
Design lessons from elsewhere:
- C33 No precedent for item-level shifting on resume: test hard.
- C34 Reminders (spec 5) must read the shifted date.
- C35 Date operations never touch progress, answers or `CourseProgress` identity.
- C36 One shift function for resume and whole-course extension; define "met" precisely.
- C37 One representation, one reader; consistency test across surfaces.
- C38 Define stacking, "to this date" vs "N more days", ordering with pauses, and whether an extension can shorten.
- C39 "Active" registration is not "working": spec 7 and other lists must treat paused learners; open-ended pauses need discoverability; freeze `now` during a pause for all consequence checks.
