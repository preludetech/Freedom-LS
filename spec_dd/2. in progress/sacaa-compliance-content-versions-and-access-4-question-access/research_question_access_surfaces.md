# Research: where questions and correct answers are visible today, and what gating them would take

Idea: `spec_dd/1. next/sacaa-compliance-content-versions-and-access/idea.md`, section "Educator interface new permission for viewing question banks". Codebase research only. Paths are relative to the repo root.

Goal restated: only certain people may view a course's questions and answers (correct answers); each view writes an audit log entry; question viewing is removed from the Django admin.

## 1. Surfaces where question text, option text or correct answers are visible

"Question" = `FormQuestion.question` (markdown), "option" = `QuestionOption.text`, "correct" = `QuestionOption.correct` (nullable bool; `True` required, `False` forbidden, `None` neutral; `form_engine/scoring.py` `is_quiz_answer_correct`).

### 1a. Django admin (staff; gated by Django model permissions only)

No FLS role grants any `freedom_ls_form_engine.*` or `freedom_ls_content_engine.*` permission (`role_based_permissions/roles.py` `BASE_ROLES`; the registry `role_based_permissions/registry.py` has them commented out). So in practice these admin pages are reached by superusers, plus any staff user someone granted model permissions to directly in the admin (`docs/product/admin-interface.md` line 70: "Access follows the standard view permissions, so a staff user granted them can read applications, answers and files without being a superuser"). No custom `has_view_permission` on any of the form_engine or content_engine admins, so the check is Django's stock `has_view_permission` (the model's `view_*` permission, or superuser).

### 1c. API

`CourseApplicationApiViewSet` (`course_applications/api.py`): each application's answers carry `question_text`, `question_type` and `value` (answer text or option text). Gated by an API key with scope `ApiScope.COURSE_APPLICATIONS` (`required_scope`), site-bound. No correct-answer field. Not staff in the role sense; flag as a surface an API-key holder can read question text through.

### 1d. QA and dev views

No views. `qa_helpers` management commands (`qa_create_*`; for example `qa_create_checkbox_scoring_quiz.py` prints "CORRECT"/"incorrect" per option) and `dev_tools` commands are shell tools for developers, and `content_save` / `content_engine/validate.py` print question text in errors. All need shell access, so outside the view-gating question. `form_engine/factories.py` and `qa_helpers` create fixtures with `correct` flags; tests exist that cover the preview (`educator_interface/tests/`).

### 1e. Learner-facing (out of scope for gating)

Learners see correct answers after a quiz: `learner_interface/views.py` `course_form_complete` (line ~2165-2173) calls `FormProgress.get_incorrect_quiz_answers` (`form_engine/models.py` lines 683-740), which returns `correct_options`. Template `learner_interface/course_form_complete.html` (lines 87-151) renders "Incorrect answers review" with the learner's pick and the correct answer, **only when `form.quiz_show_incorrect` is true** (`Form.quiz_show_incorrect`, required for `QUIZ` strategy in `form_engine/schema.py`). `show_answer_key` is never set on a learner page. So correct answers reach learners by design, per quiz, as a content setting. The model docstring says the function is written so the incorrect answers can also be shown to the teacher. Worth noting in the spec as out of scope: if SACAA wants correct answers hidden from learners too, that is a separate change to `quiz_show_incorrect`.

## 2. The permission system (`freedom_ls/role_based_permissions`)

- **Declaration.** Permissions are `"app_label.codename"` strings. The authoritative list is `registry.py` `PERMISSIONS: dict[str, str]` (string -> description). `validate_role_permissions` (CI command) fails if a role references a string not in `PERMISSIONS`. Custom (non-CRUD) permissions are declared as Django `Meta.permissions` on a model, then migrated: examples `learner_management/models.py` `Cohort.Meta.permissions = [("download_cohort_report", ...)]`, `Learner.Meta.permissions = [("bulk_manage_learners", ...)]`, `StaffMember.Meta.permissions = [("view_organisation_staff", ...), ("view_organisation_staff_roles", ...)]`. `freedom_ls_comms.view_conversation` is a stock Django `view_` permission of `comms.Conversation`. `roles.py` comment: "As features are built, add the relevant permissions ... and create data migrations for them."
- **Roles.** `roles.py` `BASE_ROLES` (a `SiteRolesConfig`; `types.py` `Role(display_name, permissions: frozenset[str], assignment_scope, lti_role, role_type, description)`). Roles today:
  - `site_admin` (scope `site`): everything incl. `view_auditlogentry`, `view_conversation`, `view_cohort`, `view_learner`, `download_cohort_report`, assign permissions.
  - `organisation_admin` (scope `object`, assigned on an `Organisation`): same set minus site/`change_user` and `assign_site_admin`.
  - `cohort_admin` (object, on a `Cohort`): cohort/learner management, `view_auditlogentry`, `download_cohort_report`.
  - `cohort_viewer` (object, on a `Cohort`): `view_cohort`, `view_learner`, `download_cohort_report`.
  - `organisation_staff_viewer`, `organisation_staff_roles_viewer` (object, on an `Organisation`): staff list only.
  - Placeholders with empty permissions: `system_admin` (scope `system`), `learner`, `observer` (comment: FUTURE `freedom_ls_content_engine.view_course`).
  - No course-scoped role exists. There is no `course_admin`.
- **Per-site overrides.** `loader.py` `get_role_config(site_name)`; setting `FREEDOMLS_PERMISSIONS_MODULES` (`config.py`) maps a site name to a module exposing `ROLES`, built with `BASE_ROLES.extend({...})`, which supports full replacement, `add_permissions` / `remove_permissions`, and `inherits` (`types.py` `SiteRolesConfig.extend`). A downstream site can therefore grant the new permission to its own roles without a code change to FLS, so the default only matters for FLS's base roles.
- **"sync_role_permissions".** `management/commands/sync_role_permissions.py`: Phase 1 `_ensure_permissions_exist` creates missing `auth.Permission` rows for every string in the role config (finding a ContentType by guessing the model from the codename, falling back to the first ContentType of the app label); Phases 2-3 re-sync guardian object permissions for all active `ObjectRoleAssignment`/`SiteRoleAssignment` via `utils.sync_user_object_permissions`; also reports drift and orphans. That sync only writes guardian rows whose permission's content type matches the target object's (`_filter_perms_for_content_type`), which matters for the Django admin and guardian, **not** for educator interface checks.
- **How checks actually run.** The educator interface does not use guardian rows. `learner_management/capabilities.py` `can(user, capability, scope)` reads the role config and role assignments live ("a config change or a fresh grant takes effect immediately, with nothing to re-sync"): superuser -> site grant -> organisation grant (gated on an active `StaffMember`) -> cohort grant (scope itself or a Learner via `CohortMembership`). `roles_granting(capability, site)` lists the roles carrying a string. Supported scope types are only `Site, Organisation, Cohort, Learner` (`_site_of` / `_organisation_of` raise `TypeError` for anything else), so **`can()` cannot take a `Course` as scope today**. The educator course page's panels default to `scope_object()` = the instance; a `Course` would raise unless the panel passes the organisation (`request.organisation`) or `can()` gains a Course rule. A grant on a `Cohort` never covers an organisation-level check, so a cohort-scoped role holder would fail an Organisation-scope check; that decides who "certain people" can be.
- **Worked example.** `VIEW_LEARNER = "freedom_ls_learner_management.view_learner"` (`learner_management/queries.py` line 92) is a constant used by `can`, `roles_granting(VIEW_LEARNER, site)` and the messaging policy. `VIEW_CONVERSATION = "freedom_ls_comms.view_conversation"` (same file) is the closest precedent: a permission added for oversight, held by `site_admin` and `organisation_admin` only (not cohort roles), checked by `ViewConversationAction.capability = VIEW_CONVERSATION` and `can(request.user, VIEW_CONVERSATION, learner)`.
- **Adding a new permission (steps, inferred from those precedents).**
  1. Pick a model and name, e.g. `FormQuestion.Meta.permissions = [("view_course_questions", ...)]` or a stock `view_formquestion`; makemigrations/migrate.
  2. Add the string to `registry.py` `PERMISSIONS`.
  3. Add it to the chosen roles in `roles.py` `BASE_ROLES` (and tests such as `role_based_permissions/tests/test_roles.py`).
  4. Define the constant beside `VIEW_CONVERSATION` and set it as `capability` on `PreviewContentAction` and the quiz confusion panel; decide the scope object.
  5. Run `sync_role_permissions` on deploy so the `Permission` row exists (it creates it if missing).
  6. Existing sites with `FREEDOMLS_PERMISSIONS_MODULES` overrides built with `BASE_ROLES.extend(...)` inherit the base grant unless they replace the role wholesale.
  Note a role gaining a permission applies instantly to `can()`; the guardian sync matters only for admin object-permissions.

## 3. The audit log (`freedom_ls/audit_log`)

- **Writing an entry.** `audit_log/writer.py` `record_entry(*, action, actor, target, target_label, organisation, subjects=(), reason="", details=None, run_id=None, site=None)`. Raises `ValueError` for an unregistered action or reason over 500 chars. Site comes from the target (must be `Site` or `SiteAwareModelBase`; `Course` and `FormQuestion` qualify through `content_base/models.py` `BaseContent(SiteAwareModel, ...)`) or an explicit `site`. Opens no transaction. `organisation` is nullable. `subjects` is a list of `app_label.model:pk` keys that decide which History tabs the entry appears on; the target is always included. Entries are append-only (`AuditLogEntry.save/delete/update` raise `AppendOnlyError`). `details` holds ids, labels and counts only, never tokens, links or emails.
- **Actions and verbs.** `audit_log/actions.py` `FLS_AUDIT_ACTIONS` registers each `AuditAction(code, label, describe, group)`; `record_entry` validates the code against it. Codes are `noun.verb`, with noun and verb restricted to the domain glossary's lists, enforced by `audit_log/tests/invariants/test_vocabulary.py` (`NOUNS`, `VERBS`; `test_an_actions_group_follows_its_noun` requires the action's group to equal `NOUN_GROUPS.get(noun, "Other")` and group to be in `AUDIT_ACTION_GROUPS`). Glossary `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md` (Changes section, line ~209): "`viewed` | Something was read, not changed: `conversation.viewed`, a conversation opened under oversight. Only for a read worth auditing. | not `opened`, `accessed`, `read`". Today's nouns: learner, cohort, cohort_membership, registration, cohort_registration, role, staff_member, user, course, deadline, bulk_action, import, conversation, api_key, audit_log. **No `question` noun and no `form` noun exist**, so `question.viewed` needs a glossary addition first (the glossary is "where a new word is agreed first"), or reuse the existing `course` noun as `course.viewed` (group "Course progress", which reads wrongly for a staff read of content) or add the noun and a group. Webhook-vs-audit parity tests do not apply (no webhook for a view).
- **`conversation.viewed` precedent** (`educator_interface/views.py` `ViewConversationAction.get_context_data`, line ~925):
  `record_entry(action="conversation.viewed", actor=viewer, target=conversation, target_label="Conversation with <name>", organisation=learner.organisation, subjects=[learner])`.
  Rules visible in that class: the entry is written on the action's GET, only when `HX-Request == "true"` (a plain GET from a prefetch or cross-site tag raises 404 and writes nothing); no dedupe: every open writes one entry; the older-messages paging view `partial_oversight_thread_older` "records nothing, since the open that reached this page already did". Test helper at `educator_interface/tests/test_views.py` line ~4468. The audit action has no `describe` and sits in group "Other". The README table (`audit_log/README.md`) has not been updated for `conversation.viewed`, `api_key.*`; the README's table is the place to add a new row.
- **Cost of a view entry.** One `AuditLogEntry` row per request that reveals questions, no dedupe, as with `conversation.viewed`. For this feature that means: one row per preview modal open (a single-page form preview or one page of a multi-page form per click, so a reviewer stepping through a 5-page quiz writes 5 rows); one row per quiz-confusion region load on the cohort page (lazy body, cached; `?refresh=1` reloads); one per PDF report download (and arguably one at generation). Each row: an INSERT with a `ContentType` lookup (cached) and a GIN-indexed `subjects` array. Retention is by `prune_audit_log` (default keep forever). Options if the volume matters: dedupe per (actor, course, form, page) within a time window (new logic; the log has no precedent for it and "Write only when state changed" in the README is about changes, not reads); or log at the course level (`target=course`, `details={"form": ..., "page": ...}`) rather than per question. Entries should name the course and form in `details` (labels stored at write time).
- **Where entries show.** The educator interface audit log is visible to holders of `freedom_ls_audit_log.view_auditlogentry` (`panels/audit_log/config.py`; site_admin, organisation_admin, cohort_admin) and lists entries by `organisation`. A course has no History tab, so a course-targeted entry appears only in the organisation Audit log (and the Django admin `AuditLogEntryAdmin`), unless the spec also adds a course History panel (`panels/audit_log/data_table_panels.py` shows the targeted-by-subject pattern for learner and cohort). Because a Course can belong to several organisations (`CourseAdmin.organisation_names`), pass the organisation in view (`request.organisation`) as the entry's `organisation`.
- The log "records staff actions only" (README), so staff views fit.

## 4. Removing question viewing from the Django admin

What would go (surfaces from 1a): `FormQuestionAdmin` / `FormQuestionWithSectionsAdmin`, `QuestionOptionAdmin`, the `FormQuestionInline` on `FormPageAdmin`, the `QuestionOptionInline`, `_condition_label` columns on `FormPageAdmin` and `FormContentAdmin`, and the answers document (`answer_groups`) on `FormProgressAdmin`, `QuestionAnswerAdmin` and `CourseApplicationAdmin`, plus the application CSV export columns.

Mechanisms available in this codebase:
- **Unregister the model.** `accounts/admin.py` unregisters `Group` and `EmailAddress`; `site_aware_models/admin.py` unregisters `Site`; `content_engine/admin.py` unregisters and re-registers `FormQuestion`. `admin_change_link` (`site_aware_models/admin.py`) already copes with an unregistered model ("NotRegistered -> plain text, a link that ends in a 403 is worse than none"), so unregistering does not break the links built from `FormProgressAdmin`/`CourseApplicationAdmin`. Autocomplete or `list_filter` that point at an unregistered model break: `QuestionOptionAdmin.list_filter = ("question__form_page__form",)` and `FormProgressAdmin` autocomplete filter on `form` rely on the form admin, not the question admins; no `autocomplete_fields` point at `FormQuestion` or `QuestionOption` (found none). `QuestionAnswerAdmin` has `list_filter` on `question__form_page__form` and `search_fields` on question text; those exist on the answer admin, so removing the question admins alone leaves question text on `QuestionAnswerAdmin`, `FormPageAdmin` and the answers document.
- **Hide from non-superusers, keep for superusers only** (precedent `mail/admin.py` `OutboundEmailAdmin`: `has_module_permission` and `has_view_permission` return `request.user.is_superuser`). This does not satisfy "removed from admin", because a superuser still sees the questions and the requirement wants every view logged. Superusers also pass every `can()` check (`capabilities.py` `can`, `user.is_superuser`), so they would also pass the new educator permission.
- **Readonly / exclude.** `FormContentAdmin` uses `exclude = ["condition_option"]` and `readonly_fields = ("condition",)`; `QuestionAnswerFileAdmin` uses `exclude = ["site", "file"]` ("rendering the field would put a storage URL on the page"). The same pattern can drop `question` from `FormPageAdmin.FormQuestionInline` (remove the inline) and the `condition` columns, and drop the answers template section from `answers_change_form.html` (which `CourseApplicationAdmin` and `FormProgressAdmin` both use; the template is `form_engine/templates/admin/form_engine/answers_change_form.html` including `_answers.html`).
- **Precedent for hiding a model from admin entirely:** unregistering `Group`, `EmailAddress`, `Site`; no model is hidden for the reason of confidentiality. Unregistration of an FLS model: none other than the re-register of `FormQuestion`.

What in the admin depends on seeing questions:
- Content edits: the docs state there is no browser editor and no admin authoring (`docs/product/content-editing-workflow.md`: "All authoring happens in files ... content cannot be deleted from the admin"). `content_save` is the writer. Admin edits to `FormQuestion` / `QuestionOption` are an unintended content path that would also defeat version-control, so removing them is consistent. Existing tests: `content_engine/tests/test_admin.py` `TestFormQuestionSections` (line ~508) and `FormQuestionWithSectionsAdmin` import (line 24) would go or change.
- Learner-support and application review: admins read applications and their answers (`CourseApplicationAdmin`, `FormProgressAdmin`) to see what an applicant wrote. Application forms are surveys; the compliance requirement concerns quiz question banks. Open question for the owner: remove only quiz questions' exposure (e.g. only forms with `strategy == QUIZ`), or all question text. The answers document is by form, so a conditional hide by `Form.strategy` is possible without a schema change.
- `docs/product/admin-interface.md` and `security-and-data-handling.md` describe these admin pages and must change with them.
- `FormProgressAdmin` / `QuestionAnswerAdmin` `answer_preview` show the learner's option text; after versioning lands, showing "which version of the question they answered" will come from the answer record, so the live join in `answer_groups` is the thing to replace.

## 5. Implications for the cut

1. **Two surfaces to gate in the educator interface**, not one: the course outline content preview (`PreviewContentAction`, currently `capability = None`, reachable by anyone with `view_cohort` in the organisation, and `show_answer_key=True` marks the correct options) and the cohort report's quiz-confusion panel (`CohortReportBodyPanel`, no capability; shows question text and correct options on screen). The cohort report PDF (`download_cohort_report`) is a third, already permission-gated, and carries questions and correct answers. The spec must say whether the new permission also gates the on-screen confusion table and the PDF, or only the outline preview. If the PDF stays under `download_cohort_report`, a cohort_viewer without the new permission still gets every question and correct answer in the PDF.
2. **New permission, constant and wiring.** New string in `registry.py` `PERMISSIONS`, Meta.permissions + migration on a model, constant next to `VIEW_CONVERSATION`, `capability=` on the action and panel, role grants in `roles.py`. **Scope problem:** `can()` has no Course scope; the permission has to be checked against the organisation (or `can()` extended). Cohort-scoped roles (`cohort_admin`, `cohort_viewer`) are scoped to a cohort, so an organisation-scope check leaves them out; there is no course-scoped role. The idea's phrase "on their courses" implies either a new course-scoped role (assignment scope `object` on a `Course`, new `can()` rule, new `ObjectRoleAssignment` target) or reading it as "in their organisation".
3. **Superusers pass `can()`** and stay able to view. Decide whether a superuser's view is logged (it should be, same code path) and note the admin cannot remain a back door.
4. **Audit action.** Needs a glossary-agreed noun: `question` (new) with `viewed` (existing verb), or reuse `course`. Add to `test_vocabulary.py` `NOUNS` (and `NOUN_GROUPS` if grouped), `actions.py` `FLS_AUDIT_ACTIONS`, glossary, and README table. Decide target (course vs form vs form page), `subjects`, and `details` (form slug, page, number of questions). Write it in the same request that renders the questions (HTMX-only for the preview, as `ViewConversationAction` does), so a prefetch writes nothing.
5. **Volume.** Without dedupe it is one entry per preview modal open (per page of a form). Owner decides: accept (matches `conversation.viewed`), or dedupe within a window, or log once per form open rather than per page.
6. **Admin removal scope.** Remove or unregister `FormQuestion` (both registrations), `QuestionOption`, the question inline on `FormPageAdmin`, the `condition` text columns, and decide the fate of the answer-text surfaces (`QuestionAnswerAdmin`, the answers document on `FormProgressAdmin` and `CourseApplicationAdmin`, the application CSV export). `admin_change_link` and `FormQuestionWithSectionsAdmin`'s tests are the code to adjust. A superuser-only `has_view_permission` is the weaker option and keeps the unlogged back door.
7. **Learners see correct answers** when `Form.quiz_show_incorrect` is true (`course_form_complete`). Out of scope for this gating; note it so the spec does not claim "correct answers visible to certain people only".
