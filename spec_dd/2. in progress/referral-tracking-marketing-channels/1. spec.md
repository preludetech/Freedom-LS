# Spec: marketing channels for referral tracking

Idea: `idea.md`. Up-front answers: `answers.md`. Research: `research_*.md` in this directory.

## Purpose

`SignupAttribution` records what a visitor arrived with (UTM fields, codes, click identifiers, the
referer). It never says what kind of traffic that was, so every project that reports on signups
works out "where are our signups coming from?" from the same fields. First-Class-LMS already wrote
a pure classifier for this (`apps/admin_dashboard/channels.py` in that repo). This spec moves it
into `referral_tracking` so that First-Class-LMS can delete its copy.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| channel | narrowed | `docs/product/signup-attribution.md`, which uses the word loosely for the `direct`/`none` marker. Here: the kind of traffic a first touch was, one `Channel` value. |
| platform | narrowed | `docs/product/signup-attribution.md` ("ad-platform click identifiers"), widened here to any brand a first touch came through ("Google", "Facebook", "LinkedIn"). Held in `ChannelResult.source_platform`, empty when none is known. Not FLS itself. |
| basis | coined | The field a channel call rests on: one `ChannelBasis` value. |
| first touch | narrowed | `docs/product/signup-attribution.md`: here, the stored values of one `SignupAttribution` row (or a record with the same fields), wrapped as `FirstTouch`. `FirstTouch` is unrelated to `FirstTouchCount` and to `Conversion.first_touch`, which points at an `AttributionTouch`. |

`Channel.REFERRAL` means "arrived from another site, or carried a referral code". It is a channel
value, not a `ReferralCode`.

## Scope

In:

- A new pure module, `freedom_ls/referral_tracking/channels.py`. It takes no request and makes no
  database query.
- Its tests, and a "Marketing channels" section in `docs/product/signup-attribution.md`.

Out:

- Any UI, admin column, admin filter, API field or CSV column. Projects call the module directly
  (`answers.md`).
- New capture, new model fields, or migrations (`idea.md`).
- Storing a channel. Callers classify at read time, so a rule change reclassifies history.
- Project-extensible tables. The tables are module constants, and a project that needs more wraps
  `classify` (`answers.md`).
- `msclkid`, `ttclid`, `li_fat_id` and other click identifiers that `SignupAttribution` has no column
  for. Reading them out of `raw_query` is not done.
- Classifying `AttributionTouch` rows. They lack the click-identifier and referer fields.
- Dropping self-referrals or payment-gateway referers. The classifier does not know the site's host.

## Decisions

- **Port the reference's rules and tables as they are, except where listed below.**
- **A `referral_code` gives Referral when nothing stronger is present.** A referral code is explicit
  first-party intent, while `fbclid` alone is a guess, so the code also beats `fbclid`. The reference
  ignores the code.
- **`advert_code` is ignored by `classify`.** It names an advert, not a channel.
- **`ChannelBasis` values are snake_case tokens with human labels.** The reference's `"fbclid only"`
  becomes `fbclid_only`, so a First-Class-LMS CSV that exports `basis.value` changes in that value
  and gains `referral_code`.
- **The Google country-domain pattern also accepts `google.com.<cc>`** (`google.com.au`,
  `google.com.br`). The reference's regex sends these to Referral.
- **`EMAIL_HOSTS` gains `outlook.office.com`, `outlook.office365.com` and `mail.proton.me`.** Email
  referers come only from webmail, and these three are common.
- **`FirstTouch.from_record` takes any object with the first-touch field names**, so First-Class-LMS
  can pass its own `LeadSubmission` without an adapter.
- **A `utm_source` matches the source tables exactly.** A host-shaped source (`facebook.com`) is not
  looked up in the host tables.
- **Paid means GA4's pattern, `^(.*cp.*|ppc|retargeting|paid.*)$`, on the medium.** Marketers tag
  for GA4.

## Requirements

### `freedom_ls/referral_tracking/channels.py` (new)

First-Class-LMS imports these public names, so they keep the reference's names and shapes:

- `Channel(models.TextChoices)`: `DIRECT`, `ORGANIC_SEARCH`, `PAID_SEARCH`, `ORGANIC_SOCIAL`,
  `PAID_SOCIAL`, `EMAIL`, `REFERRAL`, `OTHER`, `UNKNOWN`. Each value is the member name in lowercase,
  and each label is in sentence case ("Organic search"). The declaration order is the display order,
  because `.choices` feeds filter dropdowns.
- `ChannelBasis(models.TextChoices)`:

  | Member | Value | Label |
  | --- | --- | --- |
  | `UTM` | `utm` | UTM tags |
  | `GCLID` | `gclid` | Google click ID |
  | `REFERER` | `referer` | Referring site |
  | `REFERRAL_CODE` | `referral_code` | Referral code |
  | `FBCLID_ONLY` | `fbclid_only` | Meta click ID only |
  | `NONE` | `none` | No signal |

- `FirstTouchFields(Protocol)`: the `str` attributes `advert_code`, `referral_code`, `utm_source`,
  `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gclid`, `gbraid`, `wbraid`, `fbclid`,
  `landing_path`, `referer` and `raw_query`. `SignupAttribution` satisfies it.
- `FirstTouch`: a frozen dataclass with exactly those fields plus `first_seen: datetime`. Its
  classmethod `from_record(record: FirstTouchFields, first_seen: datetime) -> FirstTouch` copies the
  fields by name.
- `ChannelResult`: a frozen dataclass `(channel: Channel, source_platform: str, basis: ChannelBasis)`.
  It is positional and compared by value.
- `classify(first_touch: FirstTouch | None) -> ChannelResult`: the first rule that matches wins.
  1. `None` gives `UNKNOWN`, `""`, `NONE`.
  2. `utm_source` and `utm_medium` are stripped and lowercased. If either is non-empty and the pair is
     not a direct pair, the UTM rules decide and nothing later runs.
  3. Any of `gclid`, `gbraid` or `wbraid` gives `PAID_SEARCH`, `"Google"`, `GCLID`.
  4. A referer with a host (from `referers.referer_host`) is decided by the referer rules, with
     basis `REFERER`.
  5. A non-empty `referral_code` gives `REFERRAL`, `""`, `REFERRAL_CODE`.
  6. A non-empty `fbclid` gives `ORGANIC_SOCIAL`, `"Meta"`, `FBCLID_ONLY`.
  7. Otherwise `DIRECT`, `""`, `NONE`.
- `is_direct_pair(utm_source, utm_medium) -> bool`: true when the source is `direct` or `(direct)` and
  the medium is `none`, `(none)` or `(not set)`. This covers the `direct`/`none` marker that
  `capture.record_signup_attribution` writes for an untracked signup.
- `has_signal(first_touch: FirstTouch) -> bool`: true when the touch has a non-direct UTM pair, an
  `advert_code`, a `referral_code`, a click identifier or a referer host. It strips and lowercases
  the UTM pair as `classify` does, so a whitespace-only source is no signal. It counts
  `advert_code`, because it asks whether the touch carried anything, not whether it can be
  classified.

UTM rules, matched in this order on the lowercased source and medium (as the reference's
`_utm_result`):

1. A search source with a paid medium gives Paid search.
2. A social or video source with a paid medium gives Paid social.
3. A display medium, or any other paid medium, gives Other.
4. A search source, or the medium `organic`, gives Organic search.
5. A social or video source, a social medium, or a medium containing `video` gives Organic social.
6. An email source or medium gives Email, platform `Email`.
7. A referral medium gives Referral.
8. Anything else gives Other.

The platform for rules 1, 2, 4 and 5 comes from the source table. Sources match exactly, never as
substrings, so the short aliases (`x`, `fb`, `ig`, `tt`, `an`, `msg`) are safe.

Referer rules, in this order (as the reference's `_referer_result`):

1. An `android-app://` referer, detected on the raw value, looks the package up in `APP_PACKAGES`.
   An unlisted package gives Referral.
2. An `EMAIL_HOSTS` match gives Email.
3. The pattern `^google\.([a-z]{2,3}|co\.[a-z]{2}|com\.[a-z]{2})$` gives Organic search, Google.
4. `SEARCH_HOSTS` gives Organic search. `SOCIAL_HOSTS` and `VIDEO_HOSTS` give Organic social.
5. Any other host gives Referral with no platform.

A host matches a listed host when it equals it or ends with `"." + listed`. A referer never yields
a paid channel.

The source tables, host tables, `APP_PACKAGES` and the medium sets (`DIRECT_SOURCES`,
`DIRECT_MEDIA`, `DISPLAY_MEDIA`, `SOCIAL_MEDIA`, `EMAIL_VALUES`, `REFERRAL_MEDIA`) are module
constants, with the values from the reference's `channels.py`. The module imports nothing from FLS
except `freedom_ls.referral_tracking.referers.referer_host`. It may use the standard library and
`django.db.models`.

## Testing

`freedom_ls/referral_tracking/tests/test_channels.py` is pure `pytest` with `parametrize` tables and
no database mark. A test that needs a `SignupAttribution` uses an unsaved
`SignupAttribution(...)`, not a factory, which would save a row. It has to prove:

- The UTM rules: each rule, case-insensitivity, the aliases, paid against organic per platform, a
  medium with no source, and an unrecognised pair giving Other.
- The direct pair: the truth table, and that it falls through to a click identifier, a referer and
  a referral code. `SignupAttribution(utm_source="direct", utm_medium="none")` classifies as Direct
  with basis `none`.
- Precedence: UTM beats a click identifier, a click identifier beats a referer, a referer beats a
  referral code, a referral code beats `fbclid`, and `fbclid` beats Direct.
- An `advert_code` alone gives Direct, and `has_signal` is true for it. A whitespace-only
  `utm_source` is no signal.
- Referers: the subdomains `l.facebook.com`, `lm.facebook.com`, `m.facebook.com`, `l.instagram.com`
  and `search.yahoo.com`; `google.co.za`, `google.com.au` and `google.de`; `accounts.google.com` and
  `docs.google.com` giving Referral; the lookalikes `box.com` (not X) and `ghost.co` (not `t.co`);
  each new `EMAIL_HOSTS` entry; `mail.yahoo.com` giving Email, not Yahoo search; listed and unlisted
  Android packages; an unparseable referer giving Direct.
- Within each host table, no entry equals or is a dot-suffix of another.
- `FirstTouch.from_record` on an unsaved `SignupAttribution` copies every field. The `FirstTouch`
  field set equals a literal list of the fourteen names plus `first_seen`, and equals
  `FirstTouchFields.__annotations__` plus `first_seen`.
- The `Channel` and `ChannelBasis` values and their order are pinned, so a rename fails a test.

## Documentation and downstream

- `docs/product/signup-attribution.md`: a "Marketing channels" section. It names the nine channels
  and the basis labels, and says the channel is computed, never stored. It states the limits:
  - Direct means no stored signal, not a typed URL. Until
    `referral-tracking-external-referer-first-touch` ships, an untagged visit stores no referer, so
    organic search and plain referrals mostly read as Direct.
  - A click identifier alone is an inference: `gclid` may be Display or YouTube, and `fbclid` may be
    organic or paid.
  - A self-referral is the caller's to filter.
- `upgrade_notes.md` (via `/fls-dev:update_upgrade_notes`): no migration or settings change. A
  project with its own copy imports from `freedom_ls.referral_tracking.channels` and deletes the
  copy. The notes list each behaviour change under Decisions, plus the new `ChannelBasis` member
  `REFERRAL_CODE` and the `ChannelBasis` labels, which are now human text rather than the values.

## Success criteria

- `docs/app_structure.md` is unchanged after `/ds:app_map`, so `referral_tracking` has no new
  dependency.
- `docs/product/signup-attribution.md` has a "Marketing channels" section covering the limits above.
- `uv run pytest freedom_ls/referral_tracking/tests/test_channels.py` passes.
