# Spec: marketing channels for referral tracking

Idea: `idea.md`. Up-front answers: `answers.md`. Research: `research_*.md` in this directory.

## Purpose

`SignupAttribution` records what a visitor arrived with (UTM fields, codes, click identifiers, the
referer). It never says what kind of traffic that was, so every project that reports on signups
works out "where are our signups coming from?" from the same fields. First-Class-LMS already wrote
a pure classifier for this (`apps/admin_dashboard/channels.py` in that repo). This spec moves it
into `referral_tracking` so that First-Class-LMS can delete its copy.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| channel | coined | The kind of traffic a first touch was: one `Channel` value. FLS has no existing word for this. |
| platform | coined | The brand a first touch came through ("Google", "Facebook", "LinkedIn"), held in `ChannelResult.source_platform`. Empty when none is known. |
| basis | coined | The field a channel call rests on: one `ChannelBasis` value. |
| first touch | narrowed | `docs/product/signup-attribution.md`: here, the stored values of one `SignupAttribution` row (or a record with the same fields), wrapped as `FirstTouch`. `FirstTouch` is unrelated to `FirstTouchCount`. |

`Channel.REFERRAL` means "arrived from another site, or carried a referral code". It is a channel
value, not a `ReferralCode`.

## Scope

In:

- A new pure module, `freedom_ls/referral_tracking/channels.py`. It takes no request and makes no
  database query.
- Its tests, and a "Marketing channels" section in `docs/product/signup-attribution.md`.

Out:

- Any UI, admin column, admin filter, API field or CSV column. Projects call the module directly
  (`answers.md`).
- New capture, new model fields, or migrations (`idea.md`).
- Storing a channel. Callers classify at read time, so a rule change reclassifies history.
- Project-extensible tables. The tables are module constants, and a project that needs more wraps
  `classify` (`answers.md`).
- `msclkid`, `ttclid`, `li_fat_id` and other click identifiers that `SignupAttribution` has no column
  for. Reading them out of `raw_query` is not done.
- Classifying `AttributionTouch` rows. They lack the click-identifier and referer fields.
- Dropping self-referrals or payment-gateway referers. The classifier does not know the site's host.
  A first touch is captured on landing, so a self-referral is the caller's problem, and the docs
  say so.

## Decisions

- **Port the reference's rules and tables as they are, except where listed below.** It follows the
  GA4 default channel group for manual traffic, reduced to nine channels (`research_best_practices.md`
  §7 explains each reduction). First-Class-LMS's report numbers change only where this list says so.
- **A `referral_code` gives Referral when the touch has no non-direct UTM, no Google click
  identifier and no referer host.** It is checked before `fbclid`. A referral code is explicit
  first-party intent, and `fbclid` alone is a guess. The reference ignores the code and returns
  Direct or Organic social.
- **`advert_code` is ignored by `classify`**, because it names an advert, not a channel. It still
  counts in `has_signal`, which asks "did this touch carry anything?", not "can it be classified?".
- **`ChannelBasis` values are snake_case tokens with human labels.** The reference's `"fbclid only"`
  becomes `fbclid_only`. A First-Class-LMS CSV that exports `basis.value` changes in that one value,
  and the upgrade notes say so.
- **The Google country-domain pattern also accepts `google.com.<cc>`** (`google.com.au`,
  `google.com.br`). The reference's regex sends these to Referral.
- **`EMAIL_HOSTS` gains `outlook.office.com`, `outlook.office365.com` and `mail.proton.me`.**
  Webmail is the only source of email referers, and these three are common.
- **`FirstTouch.from_record` takes any object with the first-touch field names**, typed as a
  `Protocol`, not a union of models. That way First-Class-LMS can pass its own `LeadSubmission`
  without an adapter, and `channels.py` imports no model.

## Requirements

### `freedom_ls/referral_tracking/channels.py` (new)

Public names. First-Class-LMS imports these, so they keep the reference's names and shapes:

- `Channel(models.TextChoices)`: `DIRECT`, `ORGANIC_SEARCH`, `PAID_SEARCH`, `ORGANIC_SOCIAL`,
  `PAID_SOCIAL`, `EMAIL`, `REFERRAL`, `OTHER`, `UNKNOWN`. The values are the lowercase snake_case of
  the member name, and the labels are in sentence case ("Organic search"). Members are declared in
  that order, which is the display order: `.choices` feeds filter dropdowns.
- `ChannelBasis(models.TextChoices)`:

  | Member | Value | Label |
  | --- | --- | --- |
  | `UTM` | `utm` | UTM tags |
  | `GCLID` | `gclid` | Google click ID |
  | `REFERER` | `referer` | Referring site |
  | `REFERRAL_CODE` | `referral_code` | Referral code |
  | `FBCLID_ONLY` | `fbclid_only` | Meta click ID only |
  | `NONE` | `none` | No signal |

- `FirstTouchFields(Protocol)`: the `str` attributes `advert_code`, `referral_code`, `utm_source`,
  `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gclid`, `gbraid`, `wbraid`, `fbclid`,
  `landing_path`, `referer` and `raw_query`. `SignupAttribution` satisfies it.
- `FirstTouch`: a frozen dataclass with exactly those fields plus `first_seen: datetime`. A
  First-Class-LMS test asserts the field set. It has a classmethod
  `from_record(record: FirstTouchFields, first_seen: datetime) -> FirstTouch`, which copies the
  fields by name.
- `ChannelResult`: a frozen dataclass `(channel: Channel, source_platform: str, basis: ChannelBasis)`,
  positional and compared by value.
- `classify(first_touch: FirstTouch | None) -> ChannelResult`: the first rule that matches wins.
  1. `None` gives `UNKNOWN`, `""`, `NONE`.
  2. `utm_source` and `utm_medium` are stripped and lowercased. If either is non-empty and the pair is
     not a direct pair, the UTM rules decide and nothing later runs.
  3. Any of `gclid`, `gbraid` or `wbraid` gives `PAID_SEARCH`, `"Google"`, `GCLID`.
  4. A referer with a host (from `referers.referer_host`) is decided by the referer rules, with
     basis `REFERER`.
  5. A non-empty `referral_code` gives `REFERRAL`, `""`, `REFERRAL_CODE`.
  6. A non-empty `fbclid` gives `ORGANIC_SOCIAL`, `"Meta"`, `FBCLID_ONLY`.
  7. Otherwise `DIRECT`, `""`, `NONE`.
- `is_direct_pair(utm_source, utm_medium) -> bool`: true when the source is `direct` or `(direct)` and
  the medium is `none`, `(none)` or `(not set)`. This covers the `direct`/`none` marker that
  `capture.record_signup_attribution` writes for an untracked signup.
- `has_signal(first_touch: FirstTouch) -> bool`: true when the touch has a non-direct UTM pair, an
  `advert_code`, a `referral_code`, a click identifier or a referer host.

UTM rules, matched in this order on the lowercased source and medium (as the reference's
`_utm_result`). "Paid" means the medium matches `^(.*cp.*|ppc|retargeting|paid.*)$`.

1. A search source with a paid medium gives Paid search.
2. A social or video source with a paid medium gives Paid social.
3. A display medium (`display`, `banner`, `expandable`, `interstitial`, `cpm`), or any other paid
   medium, gives Other.
4. A search source, or the medium `organic`, gives Organic search.
5. A social or video source, a social medium, or a medium containing `video` gives Organic social.
6. An email source or medium gives Email.
7. The medium `referral`, `app`, `link` or `affiliate` gives Referral.
8. Anything else gives Other.

The platform comes from the source table. Sources match exactly, never as substrings, so the short
aliases (`x`, `fb`, `ig`, `tt`, `an`, `msg`) are safe.

Referer rules, in this order (as the reference's `_referer_result`):

1. An `android-app://` referer, detected on the raw value, looks the package up in `APP_PACKAGES`.
   An unlisted package gives Referral.
2. An `EMAIL_HOSTS` match gives Email.
3. The Google search-host pattern `^google\.([a-z]{2,3}|co\.[a-z]{2}|com\.[a-z]{2})$` gives Organic
   search, Google.
4. `SEARCH_HOSTS` gives Organic search. `SOCIAL_HOSTS` and `VIDEO_HOSTS` give Organic social.
5. Any other host gives Referral with no platform.

A host matches a listed host when it equals it or ends with `"." + listed`. A referer never yields
a paid channel.

The tables (`SEARCH_SOURCES`, `SOCIAL_SOURCES`, `VIDEO_SOURCES`, `SEARCH_HOSTS`, `SOCIAL_HOSTS`,
`VIDEO_HOSTS`, `EMAIL_HOSTS`, `APP_PACKAGES` and the medium sets) are module constants copied from
the reference, with the three `EMAIL_HOSTS` additions above. The module imports only `re`,
`dataclasses`, `datetime`, `typing.Protocol`, `django.db.models` and
`freedom_ls.referral_tracking.referers.referer_host`. It adds no app-level import edge.

`referers.py`, the models and capture are unchanged.

## Testing

`freedom_ls/referral_tracking/tests/test_channels.py`: pure `pytest` with `parametrize` tables and no
database. It ports the reference's `test_channels.py` and adds the FLS changes. It has to prove:

- The UTM table: every rule above, case-insensitivity, the aliases, paid against organic per
  platform, a medium with no source, and an unrecognised pair giving Other.
- The direct pair: the truth table, and that it falls through to a click identifier, a referer and
  a referral code. A `SignupAttributionFactory()` row (the `direct`/`none` marker) classifies as
  Direct with basis `none`.
- Precedence: UTM beats a click identifier, a click identifier beats a referer, a referer beats a
  referral code, a referral code beats `fbclid`, and `fbclid` beats Direct.
- An `advert_code` alone gives Direct, and `has_signal` is true for it.
- Referers: the subdomains `l.facebook.com`, `lm.facebook.com`, `m.facebook.com`, `l.instagram.com`
  and `search.yahoo.com`; `google.co.za`, `google.com.au` and `google.de`; `accounts.google.com` and
  `docs.google.com` giving Referral; the lookalikes `box.com` (not X) and `ghost.co` (not `t.co`);
  each new `EMAIL_HOSTS` entry; listed and unlisted Android packages; an unparseable referer giving
  Direct.
- An invariant: within each host table, no entry equals or is a dot-suffix of another.
  `_lookup` returns the first match, so an overlap would make the result depend on dict order.
  Across tables the order of the referer rules decides, and a test pins it: `mail.yahoo.com` is
  Email, not Yahoo search.
- `classify(None)` gives Unknown.
- `FirstTouch.from_record` on a `SignupAttribution` copies every field. Its field set equals the
  `FirstTouchFields` attribute names plus `first_seen`.
- `ChannelBasis` and `Channel` values and order are pinned, so a rename fails a test.

## Documentation and downstream

- `docs/product/signup-attribution.md`: a "Marketing channels" section. It names the nine channels
  and the basis values, and states the limits: Direct means no stored signal, not a typed URL. Until
  `referral-tracking-external-referer-first-touch` ships, an untagged visit stores no referer, so
  organic search and plain referrals mostly read as Direct. A click identifier alone is an inference
  (`gclid` may be Display or YouTube, `fbclid` may be organic or paid). The tables are fixed. A
  self-referral is the caller's to filter. It also says the channel is computed, never stored.
- `upgrade_notes.md` (via `/fls-dev:update_upgrade_notes`): no migration or settings change. A
  project with its own copy imports from `freedom_ls.referral_tracking.channels` and deletes the
  copy. It lists the behaviour differences from First-Class-LMS's copy: a referral code now gives
  Referral; `"fbclid only"` is now `fbclid_only`; `google.com.<cc>` is search; three new webmail
  hosts; `from_record` takes any object with the fields.

## Open questions

- Q: Should a `utm_source` given as a host (`facebook.com`, `l.facebook.com`) be matched against the
  host tables? → A: No. Sources match the exact source tables only, as in the reference. (assumed
  default: such a tag lands in Other or a medium-based channel, which is visible and fixable by
  tagging. Overrule by editing "UTM rules".)
- Q: Should the paid-medium pattern be tightened from GA4's `.*cp.*` to an explicit list? → A: No.
  Keep GA4's pattern. (assumed default: it matches GA4, which marketers tag for, and over-matching
  needs a medium containing "cp". Overrule by editing "UTM rules".)
- Q: Should `ChannelBasis` keep the reference's `"fbclid only"` value so First-Class-LMS's CSV export
  is unchanged? → A: No. Use `fbclid_only`. (assumed default: one downstream project, one value, and
  the upgrade notes name it. Overrule by editing the `ChannelBasis` table.)

## Success criteria

- `from freedom_ls.referral_tracking.channels import Channel, ChannelBasis, ChannelResult, FirstTouch, classify, has_signal, is_direct_pair` works, and `channels.py` imports no model.
- `uv run pytest freedom_ls/referral_tracking/tests/test_channels.py` passes with no database fixture.
- A `SignupAttribution` with only `referral_code="abc"` set (UTM `direct`/`none`) classifies as `ChannelResult(Channel.REFERRAL, "", ChannelBasis.REFERRAL_CODE)`.
- A referer of `https://www.google.com.au/` classifies as Organic search, Google.
- The table-overlap invariant test passes.
- `docs/product/signup-attribution.md` has a "Marketing channels" section, and the `docs/app_structure.md` dependency list for `referral_tracking` is unchanged.
