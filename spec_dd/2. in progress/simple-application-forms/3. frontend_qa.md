# Frontend QA: simple application forms

An application-gated course can now name an application form. Applying takes the learner through
that form page by page, lets them attach a file, shows a check-your-answers page, and only then
records the submission. This run walks that flow, breaks it in the ways an applicant plausibly
would, and checks the admin side of the uploaded files. It then walks the course player's own
forms — one multi-page quiz and one single-page form of each kind — because the question markup
and the page arithmetic are now shared code, and a learner sitting a quiz has to see exactly what
they saw before.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

---

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh` — note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `simple-application-forms` branch. If it names another branch, another server holds the port; go
   back to step 1.

### 0.2 Seed data

Every item below must exist before §1. Missing data is created through the `fls-dev:qa-data-helper`
agent, never by hand.

1. **Demo content loaded.** `uv run python manage.py content_save demo_content DemoDev`. This
   loads `functionality_demo_application_gated` (the gated course that names a form) and
   `functionality_demo_application_form` (the form itself, in its own top-level directory). Re-run
   it if in doubt; it is idempotent.
2. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
3. **Applicant:** a learner account with no staff flag, verified email, password equal to the email
   per project convention, registered for no course and holding no application. Call it the
   *applicant* below. On a second run of this plan the account from the first run already holds an
   application and its form sitting: clear them in that order — the `CourseApplication` first, then
   its `FormProgress`, which is RESTRICTed for as long as the application names it.
4. **Second learner:** another such account, used only for the cross-account 404 checks. Call it the
   *bystander*.
5. **Staff non-superuser:** an account with `is_staff=True`, `is_superuser=False`, and the
   `view_questionanswer`, `view_formprogress` and `view_questionanswerfile` permissions granted
   directly. Call it the *reviewer*. The point of this account is to prove those permissions are not
   enough.
6. **Gated course with no form:** run `uv run python manage.py qa_create_application_docs_scenario`.
   It creates a gated course whose `course.md` equivalent names no `application_form`, plus a
   learner who already applied to it. Use its course for §1 only; its learner is not needed.
7. **The applicant is registered for the three open demo courses** used in §8:
   `functionality_demo_end_with_quiz`, `functionality_demo_end_with_topic` and
   `functionality_demo_course_parts`. All three are free, so the applicant can enrol from the
   catalogue. They must hold no form attempt at any placement in them: on a second run of this plan,
   clear the earlier run's `CourseFormAttempt` and `FormProgress` rows for those placements, so
   every form's start screen reads "Start Form" rather than "Continue Form" or "Try Again".
8. **Three files on disk**, in the scratch directory, each named as shown:
   - `id-scan.png`: any PNG under 1 MB with real pixel content.
   - `id-scan.pdf`: any PDF under 1 MB.
   - `not-an-image.png`: a text file (for example the string `hello`) saved with a `.png` name.
   - `too-big.jpg`: a JPEG of at least 7 MB. `dd if=/dev/urandom bs=1M count=7 >> ` a small real
     JPEG is enough; the client-side check reads only the size.

## §1 The control: a gated course without a form still works as before

Signed in as the applicant.

1. Open the catalogue and the course from §0.2 item 6. Expect the "By application" badge and an
   "Apply now" button.
2. Click "Apply now". Expect the confirmation page "Apply to <course>".
3. Click "Submit application". Expect the status page saying the application was received and is
   pending review, with "Back to dashboard". No form page appears at any point.
4. Open the dashboard. Expect the "Your applications" panel listing the course. Click it. Expect the
   same status page, not a redirect into a form.

## §2 Applying to a course that names a form

Still the applicant.

1. Open the catalogue and the course titled from `functionality_demo_application_gated/course.md`.
   Expect "By application" and "Apply now".
2. Click "Apply now", then "Submit application". Expect to land on
   `http://127.0.0.1:<PORT>/applications/application/<uuid>/page/1/`. Note the uuid; it is used
   throughout. The page shows the course title as an eyebrow, the first page's title as the
   heading, a strip of page dots with "1" highlighted and "2" not yet clickable, and the page-one
   questions: a short text, a number, a multiple choice, a checkbox group, a long text.
3. Confirm the number question renders as an `<input type="number">` (the browser's spinner is
   visible, and typing letters is refused).
4. Click "Next" with nothing filled in. Expect the page to re-render (HTTP 422 in the network
   panel) with a callout naming the required question numbers, for example "Questions 1, 2 and 3
   need answers before you can continue." Nothing advances.
5. Fill in only the short text and click "Next". Expect the same callout naming the remaining
   required numbers, and the short text you typed still in its box. A rejected page keeps good
   answers.
6. Fill in every required question, leave the optional checkbox group and the long text blank,
   and click "Next". Expect page 2 with dot "2" highlighted and dot "1" now a link.
7. Click dot "1". Expect page 1 with every answer you gave still present. Click "Next" again to
   return to page 2.

## §3 The file question

On page 2 as the applicant.

1. Expect a required file question with a file picker, the hint "JPEG, PNG or PDF, up to 6 MB", and
   no "Remove" button.
2. Pick `too-big.jpg`. Expect an inline message that the file is larger than 6 MB and no network
   request (check the network panel). The picker is empty again.
3. Pick `not-an-image.png`. Expect a network POST returning 422 and the widget re-rendered with a
   message that the file is not a readable image or PDF. Nothing is attached.
4. Pick `id-scan.png`. Expect the widget to swap to its attached state without a full page load:
   the filename `id-scan.png`, its size, a "Download" link, a "Replace" control and a "Remove"
   button.
5. Click "Download". Expect the browser to save a file named `id-scan.png` (an attachment, not an
   inline render). Open it and confirm it is the image you uploaded.
6. With a screen reader or the accessibility tree, confirm the "Remove" and "Replace" controls
   carry the question text in their accessible names, not a bare "Remove".
7. Open the dashboard in the same tab (leave without clicking "Next"). Expect the "Your
   applications" panel to list the course. Click it. Expect to land back on page 2, not the status
   page, with `id-scan.png` still attached.
8. Click "Replace" and pick `id-scan.pdf`. Expect the attached state to now show `id-scan.pdf`. Click
   "Download" and confirm it is the PDF.
9. Click "Remove". Expect the widget to return to the empty picker, and the note that the question
   is unanswered until another file is attached.
10. Click "Next" with the file question empty. Expect the 422 callout naming the file question's
    number. The application is incomplete again, as the widget warned.
11. Pick `id-scan.png` again and click "Next". Expect the check-your-answers page.

## §4 The check-your-answers page

1. Expect the "Check your answers" title, a note that nothing is sent until you press Submit
   application, then one card per form page in form order: "About you" and "Supporting documents".
   Each card has a tinted header bar with the page title on the left and an "Edit" link with a
   pencil icon on the right, and a body of one row per question: the question as a muted label,
   the answer beside it. The optional questions you skipped read "Not answered". The file row shows
   `id-scan.png`, its size and a "Download" button, and no thumbnail. There is no two-column grid
   of questions: every row runs the full width of its card.
2. Repeat at 375px wide. Expect each row to stack the question above its answer, the cards to fill
   the width, and the "Download" button to be comfortably tappable (at least 24px tall).
3. In the accessibility tree, confirm each "Edit" link's accessible name includes its page title
   ("Edit About you"), so a links list does not read "Edit" over and over.
4. Click "Edit" on "About you". Expect page 1 with your answers pre-filled, a "Back to your answers"
   link in place of "Previous", and the primary button reading "Save and return to your answers".
   Change the text and click it. Expect to land straight back on the check-your-answers page, not
   on page 2, with the new text showing.
5. Click "Edit" on "About you" again, then click "Back to your answers" without changing anything.
   Expect the check-your-answers page, unchanged.
6. Click "Edit" on "About you", then use the page-jump nav to open page 2. Expect page 2's button to
   read "Check your answers", not "Save and return to your answers": jumping elsewhere leaves edit
   mode.
7. Do not submit yet.

### 4.1 Posting the last page directly

The check is whole-form, not per-page. Prove it.

1. Open `http://127.0.0.1:<PORT>/applications/application/<uuid>/page/1/`, clear the number
   answer, and click "Next". Expect the 422 callout for page 1, because the number question is
   required. That is the per-page check.
2. Now open page 2 directly by URL and click "Next" (the file is attached, so page 2 passes). Expect
   the check-your-answers page with the number row reading "Not answered".
3. Click "Submit application". Expect the page to re-render (422) with a callout naming the number
   question. No status page, no submission.
4. Use the "About you" card's "Edit" link, give the number an answer, and click "Save and return to
   your answers". Expect the check page with the number row filled in.

## §5 Submitting, and what read-only means afterwards

1. Click "Submit application". Expect the status page ("received and is currently pending review").
2. Open `http://127.0.0.1:<PORT>/applications/application/<uuid>/page/2/`. Expect the page to
   render with the info callout that the application has been submitted, every input disabled, the
   file shown with a "Download" link but no "Replace" or "Remove", and no "Next" button.
3. Open `.../application/<uuid>/check-your-answers/`. Expect the cards with no "Edit" links, a
   success callout, and no submit button.
4. Using the browser's developer tools, re-send the earlier "Submit application" POST (or submit the
   form from a stale tab). Expect a redirect to the status page and no error.
5. Open the course detail page. Expect the button to read "View my application" and to lead to the
   status page, not into the form.
6. Open the dashboard. Expect the course listed under "Your applications", leading to the status
   page.

## §7 The admin side of uploaded files

### 7.1 Superuser

Sign in as `demodev@email.com` and open `http://127.0.0.1:<PORT>/admin/`.

1. Under "Form engine", open "Question answer files". Expect a row for the applicant's `id-scan.png`
   with a "Download" link, and no scan-status column or filter anywhere on the page.
2. Open the row. Expect the original filename and timestamps, all read-only, and no raw file path or
   inline file link.
3. Back on the changelist, click "Download". Expect the same PNG as an attachment.
4. Open the actions dropdown. Expect no "Mark selected files clean" or "Mark selected files rejected"
   entry -- FLS does no scanning, and there is nothing to clear.
5. Open "Question answers" and "Form progress records". Expect the applicant's rows to be visible,
   and the answer preview column to show the text answers.
6. Still in "Form progress records", tick the applicant's row, choose "Delete selected form progress
   records" and run it. Expect a refusal page listing the course application among the protected
   related objects, with no confirmation button. Go back and confirm the row is still there. The
   sitting is the only record of what this applicant was asked, so nothing may delete it while the
   application stands.

### 7.2 Staff non-superuser

Sign out and sign in as the reviewer. Open `http://127.0.0.1:<PORT>/admin/`.

1. Expect "Question answers", "Form progress records" and "Question answer files" to be absent from
   the index, or to return 403 when opened by URL
   (`/admin/freedom_ls_form_engine/questionanswerfile/`).
2. Paste the file download URL from 7.1 step 3. Expect 403.
3. Sign out.

### 7.3 A form created in the admin gets a slug

As `demodev@email.com`:

1. Under "Form engine", "Forms", click "Add form". Fill in only the title "Admin form one" and
   strategy "UNSCORED". Save. Expect success, and the slug field to show `admin-form-one`.
2. Add a second form titled "Admin form one" again. Save. Expect success with a distinct slug (for
   example `admin-form-one-2`), not a uniqueness error.

## §8 The course player's own forms are unchanged

The questions a learner sees, and the page arithmetic behind the runner, are now shared with the
application shell. Nothing here is new functionality: every step below is something that worked
before this branch and has to keep working. Walk both shapes a course form comes in — a multi-page
one and a single-page one — because the paging split is exactly what tells them apart.

Signed in as the applicant, who is registered for the three courses in §0.2 item 7. Reach every form
through the course outline rather than by typing a URL; the item index is positional and the player
locks items you have not unlocked yet.

### 8.1 A multi-page quiz: the runner chrome

`functionality_demo_end_with_quiz`, the "Mid course Quiz" item. Two pages, three required multiple
choice questions each, `submit_on_exit: true`, `quiz_show_incorrect: true`, pass mark 80.

1. Open the item. Expect the start screen inside the ordinary player chrome (sidebar, breadcrumb),
   the form title, 6 questions, 2 pages, and a single "Start Form" button.
2. Click "Start Form". Expect the runner: no site header, no sidebar. A sticky top bar with an exit
   X on the left, the form title centred, and "0 of 6 answered" on the right. Below it "Page 1 of 2"
   with the progress bar half filled, then two page dots — dot 1 current, dot 2 not a link.
3. Expect the page heading "Page 1", the page's content block with its diagram image, then the three
   questions numbered `1.` to `3.`, each with a red asterisk, each a radio group. No "Select all that
   apply." hint, no number spinner, no file picker.
4. Answer one question. Expect the tally to read "1 of 6 answered" with no page load.
5. Click "Next" with a question still blank. Expect the browser's own required-field prompt to stop
   the submission on that radio group. Nothing advances.
6. Answer all three and click "Next". Expect page 2: dot 2 current, dot 1 now a link, "3 of 6
   answered", the bar full, and the questions numbered `4.` to `6.` — the numbering runs through the
   form, it does not restart at 1 on each page.

### 8.2 The page-jump nav does not re-lock

1. On page 2, click dot 1. Expect page 1 with its three answers still selected, and **dot 2 still a
   link**. Stepping back must not lock the page you have already reached.
2. Click "Next" to return to page 2.

### 8.3 Leaving a submit-on-exit quiz

1. Click the exit X. Expect the "Leave the test?" dialog saying "Leaving now will submit your answers
   and score your attempt. You won't be able to change your answers afterwards.", with "Keep going"
   and "Leave and submit".
2. Press Escape. Expect the dialog to close and the runner to be exactly as it was. Reopen it and
   click "Keep going". Same.
3. Click "Leave and submit" with page 2 unanswered. Expect the results page: a score ring, the
   percentage scored on the answers given, "failed" against the 80% pass mark, and the incorrect
   answers listed (`quiz_show_incorrect: true`).
4. Go back to the item's start screen. Expect a single "Try Again" button — a failed quiz offers a
   retry and nothing else.

### 8.4 A clean retake, and the results page

1. Click "Try Again". Expect a fresh sitting opening on **page 1**, the tally back at "0 of 6", and
   dot 2 locked again. A new attempt must not inherit the previous one's resume page.
2. Answer both pages correctly. On page 2, click "Next" and expect the review/submit dialog to open
   rather than the answers posting straight through.
3. Confirm the submission. Expect the results page with the score ring at 100%, verdict passed, and
   no incorrect-answer list.
4. Return to the course outline. Expect the quiz marked complete and the item after it unlocked.

### 8.5 Leaving a save-on-exit quiz, and resuming

`functionality_demo_end_with_quiz`, the "End course Quiz" item. Two pages, `submit_on_exit` unset,
`quiz_show_incorrect: false`, pass mark 50.

1. Start it, answer page 1, and click "Next" to reach page 2.
2. Click the exit X. Expect the same dialog frame but different copy — "Your progress is saved — you
   can resume later." — and a "Leave and save" button instead of "Leave and submit".
3. Click "Leave and save". Expect the item's start screen, now offering "Continue Form".
4. Click "Continue Form". Expect **page 2, not page 1**, with the tally reading "3 of 6 answered"
   and both dots links.
5. Answer page 2 and submit through the dialog. Expect the results page with the score ring and the
   verdict against the 50% mark, and **no** incorrect-answer review — this quiz has
   `quiz_show_incorrect: false`.

### 8.6 A single-page form: the survey

`functionality_demo_end_with_topic`, the "Course Feedback Survey" item. One page, five questions
covering the four original types, `CATEGORY_VALUE_SUM`.

1. Open the item. Expect the start screen to read 5 questions and 1 page. Click "Start Form".
2. Expect, precisely because the form has one page: **no page dots at all**, "Page 1 of 1" with the
   bar full, **no "Previous" link**, and none of the "Going back won't save unsaved changes on this
   page." note.
3. Expect all four original question types rendering as before: two radio groups, a checkbox group
   carrying the "Select all that apply." hint, a single-line text input, and a textarea. Questions
   `1.` and `2.` carry the required asterisk; `3.`, `4.` and `5.` do not.
4. The one page is also the last page, so "Next" opens the submit dialog immediately rather than
   advancing. Answer the two required questions, click "Next", and confirm in the dialog.
5. Expect the non-quiz results page: "Form complete!", category score bars for Satisfaction and
   Recommendation, no score ring and no pass/fail verdict — this form has no pass mark to claim
   either way.

A note, not a step: the survey's checkbox group is optional, so the hidden
`data-checkbox-required-message` paragraph should be **absent** from it. No demo form ships a
required checkbox group, so the client-side "Select at least one option." message cannot be reached
from stock content. Record that as a coverage gap under the report's General notes. Do not make a
checkbox group required to get at it.

### 8.7 A single-page quiz

`functionality_demo_course_parts`, the "Knowledge Check" item inside the "Core Concepts" part. One
page, three required multiple choice questions, `quiz_show_incorrect: true`, pass mark 80.

1. Open it through the outline and start it. Expect one page, no page dots, "Page 1 of 1", "0 of 3
   answered", and no "Previous" link.
2. Answer two of the three correctly and submit through the dialog. Expect the results page: the
   score ring at 67%, verdict failed against the 80% mark, and the one wrong answer listed.
3. Back on the start screen, expect "Try Again" only. Retake, answer all three correctly, and submit.
   Expect verdict passed, the outline marking the item complete, and the next item in the part
   unlocked.

### 8.8 Nothing from the application shell leaks in

Across every page in this section: no "Application for" eyebrow, no file picker, no
`<input type="number">`, no check-your-answers cards, no "Back to your answers" link and no "Save
and return to your answers" button. The runner still suppresses the site header and the course
sidebar; the start and results pages still have them.

### 8.9 The runner at 375px

Repeat enough of 8.1 and 8.6 to see the runner narrow: the multi-page quiz and the single-page
survey.

1. The sticky top bar and the sticky footer stay put while the questions scroll between them.
2. On the multi-page quiz the page dots stay tappable and the "Previous" and "Next" buttons go full
   width and stack, "Next" above "Previous". On the single-page survey there is one full-width
   button and no dots.
3. The exit dialog and the submit dialog both fit inside the viewport, with their buttons reachable
   without a horizontal scroll.
