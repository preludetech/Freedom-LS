# Spec: simple application forms

## Purpose

An application-gated course can be applied to today, but the applicant is never asked anything.
`ApplicationCourseAccessBackend` shows an "Apply now" CTA, `apply` creates a `CourseApplication`, and
a status page says the request was received. Give each gated course a questionnaire the applicant
fills in, so there is something to read when the review workflow lands.

Forms differ per course. They are short and unscored, and some ask the applicant to upload a
document. The approach is settled in `idea.md`: reuse `form_engine` rather than grow a second
question-and-answer family.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| check-your-answers page | coined | The page that follows the last `FormPage` of an application form: every answer laid out in one card per page, an edit link per card, and the submit control. Named for the GOV.UK pattern. Deliberately not called a "review page", because *review* is reserved for the application review workflow the first NOTE at `course_applications/models.py:23-27` holds open. |

Everything else uses existing words. In particular: **form progress record** for `FormProgress` (the
sitting), **course form attempt** for `CourseFormAttempt`, **collection item** for the
`ContentCollectionItem` row and **child** for the object it resolves to.

## Scope

**In.** `FormStrategy.UNSCORED`. `QuestionType.NUMBER` and `QuestionType.FILE_UPLOAD`, with the file
answer's model, storage, validation, quarantine seam and serving. `Course.application_form`, bound by
path at content load. `CourseApplication.form` and `.form_progress`. The applicant's paged form flow
and its check-your-answers page. Extracting the form half of `form_fill_page` into `form_engine`,
along with the four question-input templates. Three shipped defects that block or would be duplicated
by the above: the resume rule, `children:` path resolution, and `FormAdmin`'s missing slug. A demo
application form and a gated demo course.

**Out.**

- **The review workflow.** State machine, reviewer notes, approve/reject/withdraw/needs-changes, the
  active-state partial unique index. Reserved by the first NOTE in `course_applications/models.py`
  and untouched. Answers are read in the Django admin.
- **A pluggable form-context backend.** §12 of the extraction spec reserved one; there is one
  consumer here, not a plugin point. The split below moves paging, validation and saving into
  `form_engine` and leaves each flow to answer "may this person fill this in, and what wraps it" in
  its own view. `research_form_context_backend.md` holds the design for whoever needs it.
- **A rewrite of the exam runner.** Only the form half moves. The exit dialog, unload guard, live
  answered tally, start screen and results screen stay in `learner_interface` on the same Alpine
  components. If the split changes anything an exam candidate can see, it has gone wrong.
- **The first deployment's actual questions**, and referral prefill, which needs referral capture.
- **A shipped virus scanner, encryption at rest, a retention scheduler.** Scanning gets a seam.
  Database and backup encryption are handled at the infrastructure layer. Nothing expires on a timer.
- **Conditional questions, a dropdown type, a boolean type, per-question upload configuration,
  numeric range validation, client-side image downscaling.** Each is buildable the day a form is
  awkward without it.
- **Option-id ownership on submit.** `submitted_option_ids` does not check that a submitted
  `QuestionOption` belongs to the question being answered. It predates this work and is not made
  worse by it, but it now applies to application answers too.

## Decisions

1. **`FormStrategy.UNSCORED` describes the form, not who is using it.** An unscored form is a form
   nobody scores; an application form is one use of that and a survey is another. No `APPLICATION`
   strategy, and nothing on `Form` records the role. Anything needing to tell an application answer
   from a quiz answer asks the application.
2. **An application's form progress record is never adopted into a `CourseFormAttempt`.** This is
   what keeps application answers unreachable from the cohort report and the educator data table by
   construction rather than by filter, and the review spec inherits it. If an approved learner is
   later meant to sit the same form as course content, that is a fresh sitting.
3. **A course names its application form by a path, and the loader resolves it to a foreign key.** A
   path survives a rename and a slug does not, and resolution inside the load transaction fails
   immediately rather than needing a system check afterwards. The cost is one application-shaped
   field on `Course`; the alternative, keeping the binding in `access_config`, would have the loader
   writing into JSON it is explicitly forbidden to interpret.
4. **Author-written paths resolve relative to the directory of the file that declares them.** This is
   what `course-files.md:67-72` already documents for `children:`, so the fix makes the documented
   form work rather than replacing it.
5. **`CourseApplication` holds a direct link to its sitting.** Resolving by `(user, form)` would be a
   bug waiting for the first shared form. `FormProgress` has no uniqueness on that pair, so an
   applicant to two courses sharing one form would read and overwrite one application's answers from
   the other. `form` is resolved once at creation so changing a course's form does not rewrite a
   historical applicant's questions.
6. **The application form is optional for a gated course.** A course with no `application_form` keeps
   today's flow exactly: apply, then the status page. No existing deployment breaks on upgrade.
7. **`QuestionType.FILE_UPLOAD` is a question type, not an application feature.** Same shape of
   decision as `UNSCORED`. The cost is real and permanent: `form_engine` gains object storage, a
   private bucket, a quarantine state and files a right-to-erasure request has to reach, for every
   deployment, whether or not it ever asks anyone for a file.
8. **The upload never rides the page POST.** A file input sends nothing on a re-post, so a file
   question reads as blank every time the applicant revisits its page, and `save_answers` would
   delete the row holding their ID scan on the most ordinary action available. Upload and removal
   each get their own endpoint and their own request, and `save_answers` skips file questions
   outright.
9. **Files are streamed by a permission-checked view, never a signed bucket URL.** A signature is
   minted once and carries no session, so it can neither re-check the scan state on each fetch nor
   express superuser-only, and a file reclassified as rejected stays fetchable for the rest of the
   signature's life.
10. **The form half of `form_fill_page` moves into `form_engine`; it is not copied.** The required
    check, the resume rule and the page-accessibility rule would otherwise exist twice and drift, and
    two of the three are wrong today.
11. **Draft versus submitted is `FormProgress.completed_time`.** `state` and `submitted_at` are
    spoken for by the review spec, and adding either now is the pre-building its NOTE forbids.
12. **`CourseApplication.form_progress` is nullable, `on_delete=RESTRICT`**, and the application
    keeps no second copy of the form. The sitting is the only record of what an applicant was
    asked, so it cannot be deleted while the application stands; a purge of the answers has to
    take the application with them. `RESTRICT` rather than `PROTECT` because deleting the
    applicant must still take both rows away together, which `PROTECT` refuses.
13. **The answer admins are superuser-gated.** Today's superuser-only reality is an accident of no
    role holding `view_questionanswer`; applicant PII lands in that shared table, so the guarantee is
    made explicit before it does.

## Requirements

### `form_engine`: enums, scoring and paging

`freedom_ls/form_engine/enums.py`

- `QuestionType` gains `NUMBER = "number"` and `FILE_UPLOAD = "file_upload"`.
- `FREE_TEXT_QUESTION_TYPES` gains `NUMBER` and **only** `NUMBER`. A number answer is stored in
  `QuestionAnswer.text_answer` exactly as a short text answer is; the type changes the markup and the
  browser's native constraint, not the storage slot. Every module that needs to know which slot a
  question uses already branches on this frozenset.
- `FormStrategy` gains `UNSCORED = "UNSCORED"`.

`freedom_ls/form_engine/schema.py` carries its own pydantic `QuestionType` and `FormStrategy`
`StrEnum`s (`:13-26`), separate from the model enums above. **Both gain the same members**, with the
same values. Without that the loader rejects `strategy: UNSCORED` and `type: file_upload` at
validation, and the demo content below cannot load. `Form.validate_quiz_fields` needs no change:
`UNSCORED` takes its existing non-`QUIZ` branch, which requires the two quiz fields to be unset.

`freedom_ls/form_engine/models.py`

- `FormProgress.score()` (`:495-503`) gains an `UNSCORED` branch that returns without writing
  `scores`, ahead of the `raise Exception(f"Unhandled Strategy: ...")` fallthrough that a third
  strategy value hits today.
- `FormProgress.save_answers()` (`:290-311`) skips any question whose type is `FILE_UPLOAD` before it
  reaches the blank-deletes-the-row branch. It must not read, create or delete a row for one. This
  lands in `form_engine` so it is a property of the question type and holds even if a file question
  is later placed on a page form.
- `FormProgress.get_current_page_number()` (`:251-272`) keeps its meaning, the first page carrying an
  unanswered question, and gains nothing. The resume defect is fixed by callers using
  `resume_page_number` below instead.

`freedom_ls/form_engine/submissions.py`

- `has_submitted_answer` keeps its POST-shaped signature and returns `False` for a `FILE_UPLOAD`
  question, since `request.POST` never carries one. Presence of a file answer is read from stored
  state, by `is_answered` below.

New module `freedom_ls/form_engine/paging.py`, the form half of `form_fill_page`, with no course
anywhere in it:

- `is_answered(question, form_progress) -> bool`. Whether a stored `QuestionAnswer` row exists for
  the question. The single source for "has this been answered" wherever `request.POST` cannot say so.
- `resume_page_number(form_progress) -> int`. Returns `max(form_progress.get_current_page_number(),
  furthest_answered_page)`, where `furthest_answered_page` is the highest 1-based page number
  carrying any stored answer. This is the corrected computation `learner_interface/views.py:1150-1167`
  already performs for the page-jump links and never applies to the resume redirect. **This fixes the
  shipped defect**: a skipped optional question on page two currently drags every future resume back
  to page two, forever.
- `page_accessibility_limit(form_progress, current_page_number) -> int`. Returns
  `max(resume_page_number(...), current_page_number)`, the page-jump rule the runner computes today.
- `build_page_links(form, form_progress, current_page_number, url_for_page)` → a list of
  `{"number", "title", "url", "is_current", "is_accessible"}` dicts. `url_for_page` is a
  `Callable[[int], str]`, so each flow reverses its own route; this is the only extracted piece
  carrying a URL.
- `unanswered_required_on_page(questions, post_data, form_progress) -> list[FormQuestion]`. The
  required questions the POST left blank, reading `has_submitted_answer` for every type except
  `FILE_UPLOAD`, and `is_answered` for that one.
- `unanswered_required_in_form(form_progress) -> list[FormQuestion]`. The same check across every
  question in the form, reading stored state only. Per-page validation is not enough: nothing
  enforces page order on POST, so the last page can be posted directly and a required question on a
  never-visited page sails through.
- `unanswered_required_message(questions) -> str`. Moved verbatim from
  `learner_interface/views.py:1027-1033` (`_unanswered_required_message`), which is a sentence about
  question numbers with no course in it.
- `answered_counts(form, form_progress, current_page_questions)` → the `answered_count`,
  `answered_other_pages` and `total_question_count` tallies from `views.py:1193-1200`.

### `form_engine`: file answers

`freedom_ls/form_engine/models.py`

```python
class ScanStatus(models.TextChoices):
    PENDING = "pending", _("Pending scan")
    CLEAN = "clean", _("Clean")
    REJECTED = "rejected", _("Rejected")


class QuestionAnswerFile(SiteAwareModel, TimestampedModel):
    answer = models.OneToOneField(
        QuestionAnswer, on_delete=models.CASCADE, related_name="answer_file"
    )
    file = models.FileField(
        upload_to=question_answer_file_upload_to, storage=get_user_uploads_storage
    )
    original_filename = models.CharField(max_length=255)
    scan_status = models.CharField(
        max_length=20, choices=ScanStatus.choices, default=ScanStatus.PENDING
    )
```

Those three columns on `QuestionAnswer` itself would widen a table shared by every quiz answer in the
system to hold nulls for very nearly every row it will ever have.

- `question_answer_file_upload_to(instance, filename)` returns
  `f"user_uploads/{instance.answer.form_progress.user_id}/form_answers/{instance.pk}{ext}"`, where
  `ext` is decided by FLS from the detected type, never taken from `filename`. The `user_uploads/`
  segment namespaces this away from the report prefix sharing the same private bucket. The user
  segment is deliberately predictable: it names a scope, not an object, so a future erasure request
  is a scoped delete rather than a bucket scan. The leaf is the row's own `SiteAwareModel` UUID,
  because the applicant's filename is attacker-controlled and can carry path segments. The caller
  must assign `answer` before assigning `file`, since `upload_to` reaches the user through it.
- `get_user_uploads_storage()` resolves the `user_uploads` alias through `storage_for_alias(...)`,
  mirroring `get_organisation_logo_storage` (`organisations/models.py:51-55`). This is that alias's
  first consumer.
- `QuestionAnswerFile.save()` performs the superseded-object sweep `Organisation.save()`
  (`organisations/models.py:116-134`) already does, scoped to its one `file` field: capture the
  stored name, save, delete the previous object if the name changed. Replacing a `.jpg` with a `.pdf`
  changes the key's extension and would otherwise orphan the old object. `user_uploads` is **not**
  added to `_OVERWRITE_PURPOSES`; that set is per-alias, and changing it would change the guarantee
  for every future field on the alias.
- New module `freedom_ls/form_engine/receivers.py` holds a `post_delete` receiver calling
  `instance.file.delete(save=False)`, mirroring `reports/signals.py:15-27`. It cannot live in
  `form_engine/signals.py`: that module defines `form_attempt_completed` and `models.py:18` imports
  it, so a receiver there importing `QuestionAnswerFile` back is a circular import. Django does not
  delete from storage when a row goes, and a removed file still sitting in the bucket is the worst
  outcome available here: the applicant is told it is gone and their ID scan is not. The receiver's
  presence is also what disables Django's fast-delete for this model, so the file is removed on a
  cascade from deleting the user as well, which is what makes the erasure prefix mean anything.
- `FormEngineConfig.ready()` (`form_engine/apps.py`) imports `checks` and `receivers` alongside
  `schema`, mirroring `reports/apps.py:11`. Neither registers otherwise.

**The invariant.** A `QuestionAnswer` row exists if and only if its question has a real answer.
Removing a file deletes the `QuestionAnswer` row, not just the `QuestionAnswerFile`; nothing creates
the parent row without a file. Break it and the required check reads an empty row as answered and the
resume rule drags the applicant back to a page they already finished.

New module `freedom_ls/form_engine/uploads.py`

- Constants, one set, not per-question configuration: `MAX_UPLOAD_BYTES = 6 * 1024 * 1024`, allowed
  extensions `{".jpg", ".jpeg", ".png", ".pdf"}`, allowed types JPEG, PNG and PDF. Not WebP, which no
  camera or scanner produces; not HEIC, which would need another dependency to decode.
- `validate_and_sanitise(uploaded_file) -> tuple[ContentFile, str]` returning the bytes to store and
  the extension to store them under, raising `ValidationError` otherwise. Checks run cheapest first:
  extension allowlist, `uploaded_file.size`, a bounded read of `MAX_UPLOAD_BYTES + 1`, then the real
  type. The browser's `Content-Type` and the original filename are applicant-controlled and neither
  is evidence of anything.
- PDFs are identified by the five magic bytes `%PDF-` and stored unchanged.
- Images are decoded and re-encoded through Pillow. That strips EXIF, since a phone photo of an ID
  carries the coordinates of where it was taken, and forces a full decode of the pixel stream, which
  catches an image that parses at the header and not beyond. One operation buys both, at the cost of
  some detail a reviewer reading a passport page will not see. Follow `check_logo_safety`
  (`organisations/validators.py:56-102`) exactly, including its `verify()`-then-reopen shape, and
  reuse `freedom_ls/base/images.py`'s `bomb_warnings_as_errors()` context manager and its
  `BOMB_FAILURES` / `DECODE_FAILURES` tuples rather than hand-listing exception types. No new
  dependency. Pillow is already here.

### `form_engine`: the upload and download endpoints

New `freedom_ls/form_engine/views.py` and `freedom_ls/form_engine/urls.py` (`app_name = "form_engine"`),
included from `config/urls.py`. These are `form_engine`'s first routes.

- `question_file_upload(request, progress_pk, question_pk)`, `@login_required @require_POST`. Resolves
  the form progress record with `get_object_or_404(FormProgress, pk=progress_pk, user=request.user)`
  and the question from that record's own form, never from anything else in the request. Refuses with
  409 when `completed_time` is set: a finished sitting takes no more writes. Runs
  `validate_and_sanitise`, creates or replaces the `QuestionAnswer` and its `QuestionAnswerFile`
  together, and renders the attached-state widget fragment. A `ValidationError` re-renders the empty
  widget with the message and HTTP 422.
- `question_file_remove(request, progress_pk, question_pk)`, same guards. Deletes the
  `QuestionAnswer` row, which cascades the `QuestionAnswerFile` and fires the receiver that deletes
  the stored object. Renders the empty widget.
- `stream_question_answer_file(question_answer_file) -> FileResponse` is the shared streaming helper,
  mirroring `download_report_view` (`reports/views.py:109-132`): `file.open("rb")` guarded by
  `FileNotFoundError` → `Http404`, `FileResponse(..., as_attachment=True, filename=...)` with
  `Cache-Control: private, no-store, must-revalidate`. `filename` is server-derived from
  `original_filename` via `slugify` plus the stored extension, never used verbatim.
- `own_question_answer_file(request, file_pk)`, `@login_required`. The applicant re-opening their own
  upload. Ownership is `question_answer_file.answer.form_progress.user == request.user`, 404
  otherwise. **It does not gate on `scan_status`**: the applicant already possesses the document, and
  in a stock install nothing ever clears it, so gating would mean the applicant can never re-open
  what they just attached. `as_attachment` plus the site-wide `SECURE_CONTENT_TYPE_NOSNIFF` is what
  keeps serving it back inert.
- The reviewer's view hangs off `QuestionAnswerFileAdmin.get_urls()` through
  `self.admin_site.admin_view(...)`, the way `GeneratedReportAdmin` wires its download
  (`reports/admin.py:114-134`), with no public route. It checks `request.user.is_superuser` itself
  (`admin_view` only guarantees staff) and, unlike the applicant's view, **refuses anything whose
  `scan_status` is not `CLEAN`**. The changelist renders no link at all until then, mirroring
  `GeneratedReportAdmin.download` (`reports/admin.py:101-108`).

### `form_engine`: the quarantine seam

- `freedom_ls/form_engine/config.py`, this app's first: a `FormEngineConfig(AppSettings)` declaring
  `FILE_SCAN_BACKEND = Setting(default="freedom_ls.form_engine.scanning.NoOpScanner")`, plus
  `config = FormEngineConfig()`. Not `required=True`, because unlike `COURSE_ACCESS_BACKEND` a safe
  default exists. Sharing a name with `FormEngineConfig(AppConfig)` in `apps.py` is the convention
  every other app already follows.
- `freedom_ls/form_engine/scanning.py`: the scanner interface and `NoOpScanner`, which **clears
  nothing**. Every file it sees stays `PENDING`. A default that cleared everything would let every
  deployment believe files were scanned when they were not. A `functools.cache`d loader resolves the
  dotted path through `import_string`, mirroring `get_course_access_backend`
  (`course_access/loader.py:1-37`), including its cache-clearing caveat for tests.
- `freedom_ls/form_engine/checks.py`, this app's first: a `@register(Tags.security)` warning,
  following `check_preview_overrides_disabled_in_production` (`course_access/checks.py:107-136`) and
  the `<app_label>.W00N` id convention, that fires when `settings.DEBUG` is `False` and
  `config.FILE_SCAN_BACKEND` is still the shipped no-op.
- `QuestionAnswerFileAdmin` carries `mark_clean` and `mark_rejected` admin actions, superuser-only. In
  a stock install this is the only thing that ever clears a file, and it has to exist from the first
  day or stock FLS has a review queue nobody can open. A custom `@admin.action` does **not** write a
  `LogEntry` the way editing through the change form does, so each action calls
  `LogEntry.objects.log_actions(...)` with `action_flag=CHANGE` over the selected queryset, one row
  per object. (Django 6 removed the older per-object `log_action`.) No `LogEntry` call exists
  anywhere in the codebase today.

The applicant sees none of this. A scan state offers them no action, submission is not gated on it,
and telling them their document is pending raises a question they cannot answer.

### `form_engine`: templates

`freedom_ls/form_engine/templates/form_engine/`, this app's first templates.

- `inputs/multiple_choice.html`, `inputs/checkboxes.html`, `inputs/short_text.html` and
  `inputs/long_text.html`, moved verbatim from the `{% partialdef %}` blocks at
  `learner_interface/templates/learner_interface/course_form_page.html:38-113`. `inputs/number.html`
  and `inputs/file_upload.html` join them as new siblings.
- `question.html` is the dispatcher, moved from the `form-question` partial (`:115-158`), with
  `number` and `file_upload` branches added to its `question.type` ladder ahead of the
  `<c-callout level="error">ERROR! UNHANDLED FORM TYPE</c-callout>` fallthrough.
- `course_form_page.html` keeps everything else: the exit dialog, the page dots, the exam top bar, the
  submit dialog, the progress strip, and includes `form_engine/question.html` where its partials were.

`file_upload.html` is the HTMX swap target, a wrapper `<div id="question-{{ question.id }}-file"
aria-live="polite">` with two states.

- **Empty** is a file picker with `accept` set from the allowed extensions and a client-side size
  check, so the common oversized file never reaches a bare rejection at the edge.
- **Attached** shows the applicant's own `original_filename` and the file size, a download link to
  `own_question_answer_file`, and two separate controls. **Remove is its own action, not a side effect
  of replace**: an applicant who uploaded the wrong document and does not have the right one to hand
  needs to be rid of it now, rather than stuck with it until they find a replacement. Removing a file
  from a required question puts the application back into an incomplete state, and the widget says so
  where it happens rather than letting the applicant find out on the check-your-answers page.
- The attached state renders no `<input type="file">`, so the page form posts nothing for that
  question and stays an ordinary urlencoded form. `#runner-page-form` (`course_form_page.html:422`)
  has no `enctype` today and gains none.
- Accessible naming: the empty state's `sr-only` label is the question text, and the 422 message is
  rendered inside the wrapper, so the `aria-live` region announces it on swap. The Replace and Remove
  controls carry their own question-identifying accessible name, so a screen-reader user hears which
  question's file they are acting on rather than a bare "Remove".

These templates bring `form_engine --> base` and `form_engine --> icons` for `c-callout` and `c-icon`.
`form_engine` has no template-level dependency of any kind today; both targets are leaf apps with no
edge back, so the graph stays acyclic. The way to dodge them is to inline an SVG in a form template,
which is worse.

The required-checkbox hint (`course_form_page.html:150-156`) travels with the fieldset into
`question.html`, because `examRunnerForm` finds it with `closest("fieldset").querySelector(...)` and
it must stay a descendant of the fieldset for the exam candidate to keep seeing it. It is a hidden
paragraph revealed only by `examRunnerForm`, a `learner_interface` Alpine component, so under the
application shell it never appears. Nothing goes unvalidated: the server-side required check rejects
the page either way and names the question. The applicant gets that message a round trip later than
the exam candidate does, and that is the whole cost.

### `form_engine`: admin

- `FormAdmin` (`admin.py:151-179`) gains a `save_model` override that mints a slug from the title when
  blank, following `OrganisationAdmin.save_model` (`organisations/admin.py:26-40`). `slug` is
  read-only there with no save override today, so a form created through the admin saves with an empty
  slug and the second one collides on `unique_form_slug_per_site`. It has never mattered because every
  form has come through the loader; it matters as soon as anyone authors one another way.
- `QuestionAnswerAdmin` (`:231-261`), `FormProgressAdmin` (`:191-228`) and the new
  `QuestionAnswerFileAdmin` override `has_view_permission` and `has_change_permission` to require
  `request.user.is_superuser`. `QuestionAnswerAdmin.answer_preview` renders answer text straight into
  the changelist, which is where applicant PII would otherwise surface to any staff user granted
  `view_questionanswer`.

### `learner_interface`: the caller

`form_fill_page` (`views.py:1037-1247`) keeps the course access redirect, `_blocked_item_redirect`,
`_player_chrome_context`, the `get_or_create_incomplete` / `get_latest_incomplete` /
`finalise_stale_incomplete` calls into `learner_progress/attempts.py`, the submit-on-exit safety net
and the exam Alpine components, and calls `form_engine.paging` for the middle. It reverses

`_unanswered_required_message` is deleted from this module.

Both of the runner's resume call sites switch from `get_current_page_number()` to
`resume_page_number()`: the redirect in `form_start` (`views.py:1016`) and the `page_number` the form
start screen puts behind its Resume button (`views.py:951`). They have to move together, or the
button and the redirect it fires disagree.

**Its behaviour does not otherwise change, and its existing tests are what says so.**

### `content_engine`: binding and the loader

`freedom_ls/content_engine/models/courses.py`

- `Course` gains `application_form = models.ForeignKey("freedom_ls_form_engine.Form", null=True,
  blank=True, on_delete=models.SET_NULL, related_name="application_courses")`. No new app edge, since
  `content_engine --> form_engine` already exists. The path the foreign key is resolved from is the
  `application_form` key inside `access_config`, since which form gates a course and whether it is
  gated at all are one authoring decision.

`freedom_ls/content_engine/schema.py`

- The `Course` pydantic model is unchanged: `access_config` already carries arbitrary keys through
  untouched. `Course` sets `extra="forbid"`, so a top-level `application_form:` fails the load and
  names the file, which is the signal an author moving the key needs.

`freedom_ls/course_access/backends.py` and `freedom_ls/course_applications/backends.py`

- `FreeOnlyCourseAccessBackend` gains `_ALLOWED_CONFIG_KEYS`, widened by subclasses exactly as
  `_ALLOWED_ACCESS_TYPES` already is, and its `validate_course_config` returns every allowed key
  rather than only `access_type` — the loader reads the path back off the normalised config.
  `ApplicationCourseAccessBackend` allows `application_form`, requires it to be a non-empty string,
  and refuses it on a course that is not `application_gated`.

`freedom_ls/content_engine/management/commands/content_save.py`, `save_content_to_db` (`:609-829`)

- **Author-written paths are resolved against the declaring file's own directory** before the
  `content_by_path` lookup, and `content_by_path`'s keys are normalised the same way. Today
  `Child.path` (`content_engine/schema.py:46-54`) is used raw, with no validator, no `.resolve()` and
  no join, while `content_by_path` is keyed on the content-root walk. So a `children:` entry written
  the way the docs document never matches, and the loop at `:789-820` falls into its `logger.warning`
  branch and silently drops the child. The loop runs over `collections_data`, so the fix covers
  `CoursePart` children as well as `Course` children.
- That `logger.warning` becomes a raised error naming the collection and the unresolved path. The load
  is already `@transaction.atomic`, so nothing partial commits.
- `application_form` resolves in the same final phase as collection children (`:730-820`), after every
  `Form` in the run has been saved (`:670-676`) and is a key in `content_by_path`, and writes back to
  the already-saved `Course` row. **This ordering is load-bearing**: courses are saved before forms
  (`:656-668`), so the binding cannot be set in `save_course`.
- That binding pass is the one place in core that reads an `access_config` key by name. It decides
  nothing; the path has to be resolved against the file that declared it, which only the loader can
  do. The `BACKEND-PRIVATE` comment on the model records the exception rather than being falsified
  by it.
- A path that resolves to something other than a `Form` is an error, not a silent skip.

A form becomes course content only when some collection's `children:` list or directory scan claims
it, so an application form in its own top-level directory loads, validates, and is reachable by
nothing. One form may serve several courses; nothing in the loader or the model prevents it.

`freedom_ls/course_applications/models.py`

  blank=True, on_delete=models.RESTRICT, related_name="course_application")`. The form is read

`freedom_ls/course_applications/views.py`

- `apply` still shows `apply.html` on GET. Its POST creates the application; when
  `course.application_form` is set it also creates the form progress record, stores both on the
  application, and redirects into page 1 of the form. When it is not set, it redirects to the status
  page, which is what happens today.
- `application_status` gains the resume routing: an application whose form progress record is
  unfinished redirects into the form at `resume_page_number`; anything else renders as it does today.
  Putting it here rather than in `apply` is what makes the existing "View my application" CTA and the
  dashboard partial route a returning applicant correctly. `ApplicationCourseAccessBackend` and
  `partials/dashboard_applications.html` need no change, and should get none.
- `application_form_page(request, pk, page_number)`, `@login_required`. Resolves with
  `get_object_or_404(CourseApplication, pk=pk, user=request.user)`, the pattern `application_status`
  (`:76`) already uses, then reads the form from `application.form` and the questions from that
  form's own pages. It never accepts a form id, form slug, course slug, `FormProgress` pk or question
  id from the request to select what is saved against. Read-only once `form_progress.completed_time`
  is set; **that check lives here**, so when review lands and read-only-ness follows `state` instead,
  one call site changes. POST saves through `save_answers` regardless of validation outcome, so a
  rejected page does not throw away good answers, and re-renders with HTTP 422 and
  `unanswered_required_message` when required questions are blank.
- `application_check_answers(request, pk)` renders the check-your-answers page: a title, a one-line
  note that nothing is sent until they press submit, then one card per `FormPage` in form order. A
  card's header bar carries the page title (or "Page N" when the page has none) and an "Edit" link;
  its body lists that page's questions as label/value rows, in page order. The Edit link is an
  ordinary `<a href>` to that page with `?return=check` appended. `application_form_page` reads
  that marker: the page's primary button reads "Save and return to your answers", the secondary
  link "Back to your answers", and a successful POST redirects here instead of advancing. The page
  form posts to its own URL, query string included, so the marker survives a 422 re-render. The
  page-jump nav links stay plain, so jumping to another page leaves edit mode. Each Edit link
  carries visually-hidden text naming its page, so a screen-reader user navigating by link list
  does not hear "Edit" repeated. A file answer shows its `original_filename`, its size and a
  download button. No thumbnail. Its POST runs
  `unanswered_required_in_form` and, on success only, calls `form_progress.complete()` and redirects
  to the status page. **This is the only correct home for the whole-form required check**, and
  submission is one-way until the review spec adds a needs-changes round trip.

`freedom_ls/course_applications/urls.py` gains two routes beside `apply` and `status`:
`application/<uuid:pk>/page/<int:page_number>/` (`name="form_page"`),
`application/<uuid:pk>/check-your-answers/` (`name="check_answers"`).

`freedom_ls/course_applications/templates/course_applications/` gains `form_page.html` and
`check_your_answers.html`, extending the plain site base, not `_exam_runner_base.html`. The applicant
does not get the exam runner: its chrome is built for a timed, scored test, and the
leaving-will-submit-and-score dialog, the answered count framed as exam progress and the unload guard

from `form_engine/question.html`.

### Settings and storage

`config/settings_prod.py:53` raises `DATA_UPLOAD_MAX_MEMORY_SIZE` from 5 MB to
`10_485_760  # 10 MB`. A body over it raises `RequestDataTooBig` before any view code runs and
surfaces as a bare HTTP 400, so there is no friendly error to be had above the cap, and a phone photo
is routinely 2 to 8 MB. FLS's own per-file limit of 6 MB sits well under it, so an oversized file
gets a proper in-form message and the rest of the request still fits underneath.

`FILE_UPLOAD_MAX_MEMORY_SIZE` (`:54`) stays at 5 MB. It rejects nothing. It is only the threshold
above which Django spools an upload to a temp file instead of holding it in the worker, and
`validate_and_sanitise` reads in bounded chunks either way.

The matching edge change is **not in this repository**: there is no `Caddyfile`, no deployment
conformance artifact naming a request-body-size directive, and the edge lives in a separate
infrastructure repository. It is an operator action, recorded in the upgrade notes and in Open
Questions below, not something this repo's settings or checks can enforce.

## Testing

**The runner is unchanged where it must be.** The existing `learner_interface` form tests
(`tests/test_form_page_navigation.py`, `test_form_runner_views.py`, `test_form_complete_results.py`,
`test_form_start_page_buttons.py`, and the `tests/playwright/` form suite) pass untouched, except
where they assert the old backward-resume behaviour.

**The three defect fixes, each with a test that fails before it.**

- Resume: a learner skips an optional question on page two, answers everything on pages three and
  four, and resumes at page four rather than page two.
- `children:`: a course with an explicit `children:` list written relative to its own directory
  resolves every child, and a `children:` entry naming a path that does not exist raises rather than
  logging a warning. Neither is covered today.
- `FormAdmin`: two forms created through the admin with no slug both save, with distinct slugs.

**`form_engine` unit tests**, in the style of `tests/test_save_answers.py`.

- `save_answers` leaves a `FILE_UPLOAD` question's `QuestionAnswer` row untouched when the POST
  carries nothing for it. This is the regression that would delete an applicant's ID scan on the most
  ordinary action available.
- `score()` on an `UNSCORED` form writes no `scores` and does not raise.
- `unanswered_required_in_form` catches a required question on a page the applicant never visited,
  where `unanswered_required_on_page` on the last page does not.
- `resume_page_number` and `page_accessibility_limit`, directly.
- A `NUMBER` answer round-trips through `text_answer`.
- The demo application form loads: `strategy: UNSCORED` and a `file_upload` question pass schema
  validation and reach the database.

**Upload validation**, in the shape of `organisations/tests/test_validators.py`: one rejection path
per test, `SimpleUploadedFile` fixtures, reusing `freedom_ls/tests/images.py`'s corruption helpers.
Named cases: an executable renamed `.png`; a PDF renamed `.jpg`; a valid header with a truncated pixel
stream; an image over `MAX_IMAGE_PIXELS`; a file over 6 MB; a filename carrying `../`; a JPEG carrying
GPS EXIF, asserting the stored bytes no longer do.

**File lifecycle.**

- Removing a file deletes the `QuestionAnswer` row and the stored object, not just the row.
- Deleting the applicant's `User` cascades to the stored object. The erasure prefix is only worth
  having if this holds.
- Replacing a `.jpg` with a `.pdf` leaves exactly one object behind, not two.

**Access.**

- The applicant's file view 404s for a different logged-in user, and serves the owner regardless of
  scan state.
- The admin file view refuses a non-superuser staff user, and refuses a `PENDING` file for a superuser.
- `application_form_page` and `application_check_answers` 404 for a non-owner, and refuse writes once
  `completed_time` is set.
- A POST naming another form's question saves nothing.
- Completing an application's sitting creates no `CourseFormAttempt` and moves no `CourseProgress`
  percentage.

**Playwright**, marked `playwright` and `fls_internal` where it drives the demo content: apply, walk
the pages, attach a file, leave and return to confirm the file survives, remove it and confirm the
required check fires, use an Edit link from the check-your-answers page and save straight back to it,
submit, and confirm a second submit is refused.

## Open questions

- **The edge proxy.** The infrastructure repository must allow a 10 MB request body on the app site.
  Until it does, an upload between the edge's current 5 MB and FLS's 6 MB per-file limit is cut off
  with a bare 413 rather than an in-form message. This repository cannot make or verify that change.
- **Nothing inspects the inside of a PDF.** A payload embedded in a well-formed one passes every check
  here; the quarantine scanner is the only control for it, and stock FLS ships none. So in a stock
  install every uploaded file stays `PENDING` until a superuser clears it by hand. An operator who
  wants a review queue that moves has to either point `FILE_SCAN_BACKEND` at something real or accept
  the manual step.

## Success criteria

- An applicant to a gated course whose `course.md` names an application form lands in that form's
  first page after confirming, not on the status page.
- An applicant to a gated course that names no form reaches the status page exactly as they do today.
- Answering every required question and submitting from the check-your-answers page stamps
  `FormProgress.completed_time`; returning to the form afterwards is read-only.
- Posting the last page directly, with a required question on an earlier page left blank, does not
  produce a submitted application.
- A skipped optional question does not send a returning learner or applicant backwards, in either flow.
- A course with an explicit `children:` list written as `course-files.md` documents it resolves every
  child; one naming a missing path fails the load.
- Attaching a file, leaving the page and returning shows the file still attached.
- Removing a file leaves no object in the bucket, and neither does deleting the applicant's account.
- A superuser can open an applicant's uploaded file from the Django admin only after marking it clean,
  and that marking leaves a `LogEntry` row.
- A staff user who is not a superuser sees no answers and no files in the admin.
- `manage.py check` warns, with `DEBUG=False` and the shipped no-op scanner configured, and is silent
  once a real one is.
- Every existing `learner_interface` form test passes, apart from those asserting the old resume
  behaviour.
