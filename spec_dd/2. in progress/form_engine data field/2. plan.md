# Implementation plan: typed question types for `form_engine`

Source: `idea.md` in this directory, and the four research files beside it.

`QuestionType` has six members and none of them can say "this is a date". This adds `date`, `time`,
`email`, `url`, `phone` and `dropdown`, and with them `form_engine`'s first server-side check on what
an answer contains. Storage does not change: every answer stays a string in the existing
`text_answer` column, or `selected_options` for `dropdown`.

Follow TDD throughout: a failing test first, then the code that passes it.

---

## What already exists, and must be reused

- **`FormProgress.save_answers`** (`freedom_ls/form_engine/models.py:310`) is the single write point
  for `text_answer` in the whole application. Three callers: `course_applications/views.py:202`,
  `learner_interface/views.py:1383`, and `learner_interface/views.py:1667`
  (`_save_posted_page_answers`, the submit-and-exit path).
- **`FREE_TEXT_QUESTION_TYPES`** (`freedom_ls/form_engine/enums.py:24`) is the switch that decides
  `text_answer` versus `selected_options` in `save_answers`, `has_submitted_answer`
  (`submissions.py:23`) and `get_incorrect_quiz_answers` (`models.py:567`).
- **`unanswered_required_on_page` / `unanswered_required_message`**
  (`freedom_ls/form_engine/paging.py:97` and `:135`) are the existing per-page validation path, used
  identically by both runners. The new content check extends this path; it does not replace it.
- **`FormProgress.existing_answers_dict`** (`models.py:294`) is what feeds `value="..."` back into
  every widget on a re-render. It reads stored rows only — which is why a rejected answer needs its
  own way home (Task 4).
- **`freedom_ls/form_engine/templatetags/form_engine_tags.py`** already exists (`upload_limits`) and
  is the right home for the new display filter.
- **`inputs/file_upload.html:42-44`** is the existing precedent for an error string belonging to one
  question's widget.
- **`save_with_uuid`** (`freedom_ls/content_engine/management/commands/content_save.py:234`) maps
  pydantic fields onto model fields generically and hard-fails when the two drift, so a new schema
  field needs a matching model field and nothing else.

Two things the idea assumes that are not true in the code, and the plan works around:

- The file-upload widget does **not** use `aria-describedby` or `aria-invalid`. Neither does anything
  else in FLS — a repo-wide grep finds one unrelated hit in
  `content_engine/templates/cotton/picture.html`. The ARIA wiring below is new.
- The display filter does **not** go in `fls_base_filters`. `freedom_ls/base` has no outgoing app
  dependencies today, and a question-type-aware filter would create a `base → form_engine` edge from
  the foundation app. It goes in `form_engine_tags` instead. The concept is the idea's; only the
  module differs.

**On the word "rejected".** The idea's vocabulary is "A rejected value is not stored", and this plan
uses `rejected_*` for every identifier that names one. `course_applications` separately has
`approve`/`reject` for a whole application; the nouns differ (an answer is not an application) and
the idea's word wins.

## Task 1 — the six question types

**`freedom_ls/form_engine/enums.py`**

Add to `QuestionType`: `DATE = "date"`, `TIME = "time"`, `EMAIL = "email"`, `URL = "url"`,
`PHONE = "phone"`, `DROPDOWN = "dropdown"`. Every value fits `FormQuestion.type`'s existing
`max_length=20`.

Add `DATE`, `TIME`, `EMAIL`, `URL` and `PHONE` to `FREE_TEXT_QUESTION_TYPES` — they all store a
string in `text_answer`. **`DROPDOWN` stays out**: it carries `QuestionOption` rows and writes
`selected_options`, exactly like `multiple_choice`, so leaving it out of the frozenset is what makes
`save_answers`, `has_submitted_answer` and the quiz paths handle it with no further change.

**`freedom_ls/form_engine/schema.py`**

Mirror the six members into the pydantic `QuestionType` `StrEnum`. Update the hard-coded type list in
the `type:` field's `description` string on `FormQuestion` — it enumerates the valid values and is
what an author reads.

Compare question types with `==`, never `is`. A `type` read back from the database is a plain `str`,
not a `TextChoices` member, and every existing comparison in the app (`models.py:320`,
`submissions.py:33`, `paging.py:109`) uses `==`.

Tests: `freedom_ls/form_engine/tests/test_schema.py` already has the shape
(`FormQuestion.model_validate({...})`, no DB) — extend it for the new types.

## Task 2 — `min` and `max` on `FormQuestion`

**`freedom_ls/form_engine/models.py`** — `FormQuestion` gains:

```python
min = models.CharField(max_length=20, blank=True, default="")
max = models.CharField(max_length=20, blank=True, default="")
```

They hold an ISO date (`YYYY-MM-DD`), a time (`HH:MM`) or a plain number, and are rendered straight
into the matching HTML attribute. They apply to `date`, `time` and `number`; `number` gets the bounds
it lacks today as a side effect. **Both bounds are inclusive**, matching what the HTML attributes
mean, so a `max` of today accepts today.

**`freedom_ls/form_engine/schema.py`** — `min` and `max` on the pydantic `FormQuestion`, with a
`field_validator(mode="before")` coercing to `str`. Without it, `min: 0` arrives as an `int` and an
unquoted `min: 1930-01-01` arrives as a `datetime.date`, since PyYAML resolves both — and
`ConfigDict(extra="forbid")` plus `save_with_uuid`'s field check mean the two sides must line up
exactly.

## Task 3 — `freedom_ls/form_engine/typed_answers.py` (new module)

One module owning both halves of "what does this answer mean", so the parsing rules are written once
and the validator and the formatter cannot drift.

It imports `enums` and `django.utils` only — never `models`, which imports it. `FormQuestion` is
referenced under `from __future__ import annotations` plus a `TYPE_CHECKING` block, exactly the way
`submissions.py:1-10` does it. Add `"typed_answers"` to the parametrize list at
`freedom_ls/form_engine/tests/test_import_independence.py:34`, which spawns a fresh interpreter to
prove each helper loads without dragging `models` in behind it — the boundary is worthless unpinned.

```python
@dataclass(frozen=True)
class RejectedAnswer:
    """A submitted answer that failed its question type's check."""

    text: str       # what the person typed, so the page can hand it back
    message: str    # what to tell them, naming the format and the value

def answer_error(question: FormQuestion, text: str) -> str | None:
    """Why `text` is not a valid answer to `question`, or None when it is."""

def format_answer(question_type: str, text: str) -> str:
    """A stored answer rendered for a reader.

    Returns the raw string unchanged when it will not parse.
    """
```

Sketch of the dispatch:

```
answer_error(question, text):
    if question.type == QuestionType.DATE:
        value = _parsed_date(text)
        if value is None:
            return f'You entered "{text}". Enter a date in the format YYYY-MM-DD.'
        return _bounds_error(question, value, _parsed_date, "date")
    if question.type == QuestionType.TIME:
        ... same shape, format HH:MM, _parsed_time ...
    if question.type == QuestionType.NUMBER:
        ... int(text), ValueError -> message; then bounds ...
    if question.type == QuestionType.EMAIL:
        EmailValidator()(text) -> ValidationError -> message
    if question.type == QuestionType.URL:
        URLValidator()(_with_scheme(text)) -> ValidationError -> message
    return None            # phone, short_text, long_text: nothing to check
```

Four traps, all from `research_server_side_answer_validation.md`, each needing a line of code:

- `parse_date` and `parse_time` return `None` for a malformed string like `banana`, but **raise
  `ValueError`** for a well-formed impossible one like `2025-02-30`. Private `_parsed_date` /
  `_parsed_time` helpers catch `ValueError` and return `None`, so both failures reach one branch. A
  check that only tests for `None` 500s.
- `URLValidator` rejects a schemeless string, so `linkedin.com/in/me` fails. `_with_scheme` prepends
  `https://` before validating when the value carries no scheme, the way `forms.URLField` does.
- `EmailValidator` rejects any single-label domain other than `localhost`. Nothing to fix — worth a
  comment, because it bites in dev before it bites in production.
- `phone` is checked for nothing beyond being present. `<input type="tel">` is a numeric-keypad hint
  and nothing more; real phone validation means `libphonenumber` and a country, which is a different
  piece of work.

`min`/`max` are compared against the **parsed** value, after parsing succeeds, never against the
string. A bound the module itself cannot parse is ignored rather than failing closed, matching what
the browser does with an unparseable `min` attribute.

Messages name the expected format *and* recite the rejected value. Naming the format is what meets
WCAG 3.3.3; reciting the value matters most for date and time, whose native inputs discard any
`value` they cannot parse and so cannot show it back.

`format_answer` parses with the same helpers and formats with `django.utils.formats.date_format` /
`time_format`, so a date answer reads the way every other date on the site reads
(`March 14, 1987`, `2:30 p.m.`). Anything that will not parse falls back to the raw string — there
will be such rows: answers written before any of this existed, and answers under a question whose
`type` an admin changed afterwards.

Catch only the exceptions these calls actually raise: `ValueError` from `dateparse` and `int()`,
`django.core.exceptions.ValidationError` from the two validators.

Tests: new `freedom_ls/form_engine/tests/test_typed_answers.py`. Cover each type's accept and reject,
`2025-02-30` specifically, `banana`, a schemeless URL that must be accepted, a single-label email
domain, both bounds at their inclusive edge, and the unparseable-stored-value fallback.

## Task 4 — reject an answer at the write point, and hand it back

**`freedom_ls/form_engine/models.py`**, `FormProgress.save_answers`. The signature returns the
rejected answers instead of `None`:

```python
def save_answers(self, questions, post_data) -> dict[UUID, RejectedAnswer]:
    """Persist the answers in `post_data` for `questions`.

    A question submitted with no answer stores no row, and loses any row from an
    earlier visit ... (existing text)

    An answer whose content is not valid for the question's type is neither
    written nor deleted: the row from an earlier visit, if there is one, is left
    exactly as it was. Storing it would leave a rejected value counting as an
    answer, which would satisfy the required-question check and let an
    application through. It comes back in the return value instead, so the page
    that re-renders can show the person what they typed.
    """
    rejected: dict[UUID, RejectedAnswer] = {}
    for question in questions:
        ... existing FILE_UPLOAD and has_submitted_answer branches ...
        if question.type in FREE_TEXT_QUESTION_TYPES:
            text = submitted_text_answer(question, post_data)
            message = answer_error(question, text)
            if message is not None:
                rejected[question.id] = RejectedAnswer(text=text, message=message)
                continue
        ... existing get_or_create and write ...
    return rejected
```

**Why here rather than a sibling of `unanswered_required_on_page` in `paging.py`.** A paging-level
function would need each view to filter the question list before calling `save_answers`, and
`_save_posted_page_answers` — the submit-and-exit path, which deliberately skips the required check —
would keep storing rejected values, because it is not one of the callers doing the filtering. Putting
the check at the single write point closes that hole once. On that path the rejected answer is simply
dropped: the person is leaving and there is no page to report it on.

**`freedom_ls/form_engine/paging.py`** gains one function, mirroring `unanswered_required_message`
word for word so the two page-level callouts read alike:

```python
def rejected_answers_message(questions: list[FormQuestion]) -> str:
    """Name the questions whose answers were not valid for their type."""
    # "Question 3 needs a valid answer."
    # "Questions 3, 5 and 7 need valid answers."
```

Tests: extend `freedom_ls/form_engine/tests/test_save_answers.py` (a rejected value is not stored; a
prior valid row survives a rejected resubmission; the returned `RejectedAnswer` carries the submitted
text; a valid date round-trips) and `freedom_ls/form_engine/tests/test_paging.py` (the message,
singular and plural). `test_save_answers.py:28` has the `_post_data` `QueryDict` helper to build
submissions with.

## Task 5 — the shared scalar input template

Tasks 5 and 6 must land in the same change: Task 5 deletes two templates that Task 6's rewritten
dispatch is what stops including. Split across two commits, the page raises `TemplateDoesNotExist`.

**New: `freedom_ls/form_engine/templates/form_engine/inputs/text_input.html`**

`short_text`, `number`, `date`, `time`, `email`, `url` and `phone` are the same ten lines of markup
apart from the `type` attribute and the input mode. Seven copies of it is the repetition the project
forbids, so there is one partial, parameterised:

```django
{% load fls_base_filters %}
<label class="sr-only" for="question_{{ question.id }}">{{ question.rendered_question }}</label>
<input type="{{ input_type }}"
       {% if input_mode %}inputmode="{{ input_mode }}"{% endif %}
       id="question_{{ question.id }}"
       name="question_{{ question.id }}"
       class="w-full rounded-md border border-border bg-white px-3 py-2 text-on-surface
              focus:outline-none focus:ring-2 focus:ring-primary focus:border-primary"
       {% if question.min %}min="{{ question.min }}"{% endif %}
       {% if question.max %}max="{{ question.max }}"{% endif %}
       {% if question.required %}required{% endif %}
       {% if read_only %}disabled{% endif %}
       {% if rejected %}aria-invalid="true" aria-describedby="question_{{ question.id }}_error"{% endif %}
       {% if rejected %}value="{{ rejected.text }}"{% else %}{% with answer=existing_answers|get_dict_item:question.id %}{% if answer %}value="{{ answer.text_answer }}"{% endif %}{% endwith %}{% endif %} />
```

The `rejected.text` branch is what keeps the person's own words on the page. For a text-shaped type —
email, url, phone, short text, number — the value they typed comes straight back, which is the
project's established principle and what the idea asks for. For `date` and `time` the browser
discards a value it cannot parse and the field renders empty whatever we send; that is the HTML
value-sanitisation rule, not a bug to work around, and it is why the error message recites the value.

The class list is carried over verbatim from `short_text.html`. `bg-white` is not an FLS role token,
but it is what these inputs render today and what `themes/first_class/theme.css` itself uses;
swapping it for `bg-surface` here would silently restyle every scalar input in every form. Leave it,
and treat it as its own piece of work.

`inputs/short_text.html` and `inputs/number.html` are deleted in its favour. Themes shadow templates
by path, so a downstream that shadowed either one loses its override — but one that shadows
`text_input.html` now restyles every scalar input at once, which is the better surface.

**New: `freedom_ls/form_engine/templates/form_engine/inputs/dropdown.html`**

A `<select id="question_{{ question.id }}" name="question_{{ question.id }}">` carrying the same
class list, `required`, `disabled` and ARIA attributes as `text_input.html`. A blank first
`<option value="">` so an optional question can be left unanswered, then one
`<option value="{{ option.id }}">{{ option.text }}</option>` per `question.options.all`, marked
`selected` when the option is in `answer.selected_options.all` — the same lookup
`inputs/multiple_choice.html` already does.

`dropdown` earns its place once a question has more than about seven options, where a wall of radio
buttons stops being readable. It is not a solution to the country question: a plain `<select>` of 195
entries is nobody's idea of usable, and a searchable control is the real answer if that comes up.


The `{% else %}` branch that renders `ERROR! UNHANDLED FORM TYPE` stays — a test pins it.

The whole dispatch block and the new error element are wrapped so the partials see `rejected`:

```django
{% with rejected=rejected_answers|get_dict_item:question.id %}
    <div class="space-y-2 clear-both">
        ... dispatch ladder ...
    </div>
    {% if rejected %}
        <p class="text-sm text-error" id="question_{{ question.id }}_error">
            <span class="sr-only">Error: </span>{{ rejected.message }}
        </p>
    {% endif %}
{% endwith %}
```

`rejected_answers` is absent on a GET, so `get_dict_item`'s `None` guard returns `None` and the
element never renders. The visually-hidden `Error:` prefix is what makes a screen reader announce the
text as an error while sighted readers just see red. No icon: `c-icon` is the only sanctioned way to
add one and nothing here needs it.

Dates and times render as native inputs: one `<input type="date">` per date question, `type="time"`
for time. The widget differs per browser and platform and there is no making them match; all of them
submit the same string. This is a deliberate trade against the accessibility literature — GOV.UK, NHS
and USWDS all reject the native date input for dates a person already knows, because the picker opens
on the current month whatever `max` says. Their answer is a fieldset of three plain text inputs,
which is a composite widget with composite parsing and per-part errors: more work than every other
type here combined, and not what is being built. The evidence is in
`research_native_date_inputs.md` for whoever reopens the question — that is a note for a reader of
this plan, not a pointer to leave in a code comment.

Tests: extend `freedom_ls/form_engine/tests/test_question_template.py`, which already pins the type
ladder. One test per new type's input, one for the `min`/`max` attributes, one for the error element
rendering with `aria-invalid` and an `aria-describedby` whose value matches the element's own `id`,
one for the rejected text coming back in `value`, and one for nothing rendering when
`rejected_answers` is empty.

## Out of scope, stated so it is not discovered later

**Quiz scoring.** `is_quiz_answer_correct` (`freedom_ls/form_engine/scoring.py:11`) returns `False`
for any question with no correct option, so the new typed fields score zero in a quiz. There is no
`correct_answer` field and no change to the scoring strategies.
`get_incorrect_quiz_answers` (`models.py:567`) already skips `FREE_TEXT_QUESTION_TYPES`, so the five
new text types skip with it and no answer text reaches the quiz results page. `dropdown` scores
correctly with no work at all, because it carries `QuestionOption` rows with `correct`.

**No `datetime`.** `datetime-local` carries no timezone, so a stored value would be a bare wall-clock
string in a project running `USE_TZ = True`, ambiguous the moment two respondents sit in different
places. No comparable form builder ships a combined type either. An author who needs both asks for a
date and a time.

**`yes_no` and rating/scale.** Both are authoring conveniences over `multiple_choice`, which already
does both, and `CATEGORY_VALUE_SUM` already exists for Likert scales. A first-class `yes_no` would
steer authors toward bare "Yes"/"No" labels where descriptive option text reads better.

**Matrix and grid questions.** One scale applied across several sub-items in a single question needs a
question × row × column shape that `FormQuestion` and `QuestionOption` do not have.

**Multi-file upload.** Needs `QuestionAnswerFile` to stop being a `OneToOneField`.

**`address`, `country` and `signature`.** Composite storage, a maintained reference list, and image
capture respectively. None of them is a string in `text_answer`.

**Per-site date formats.** `LANGUAGE_CODE` and `TIME_ZONE` are process-wide Django settings;
`freedom_ls/site_aware_models/config.py` has no locale field. Every site on an install sees the same
format, and changing that is new work on `site_aware_models`, not something this change touches.

**`bg-white` in the input class list.** Carried over unchanged. Moving the scalar inputs onto a role
token is its own piece of work with its own visual review.

## Conventions this work must follow

- Type hints on every function, no `Any`, no `# type: ignore`. Modern syntax (`X | None`,
  `dict[UUID, RejectedAnswer]`).
- Catch specific exceptions. `ValueError` from `dateparse` and `int()`, `ValidationError` from the
  Django validators — never a bare `except`.
- Tests at `freedom_ls/<app>/tests/test_<module>.py`. Every DB test takes `mock_site_context`;
  `FormQuestion` is site-aware and the fixture is what sets the thread-local site. Only tests that
  read `demo_content/` are marked `fls_internal`.
- `uv run pytest` must stay above the `--cov-fail-under=73` gate.
- `uv run manage.py makemigrations` after the model change, then `migrate`. Never edit an existing
  migration.
- Do not delete any existing `TODO` or `@claude` comment.
