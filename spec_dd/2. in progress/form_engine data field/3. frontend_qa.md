# Frontend QA: typed question types for `form_engine`

Six new question types (`date`, `time`, `email`, `url`, `phone`, `dropdown`), bounds (`min`/`max`) on
`date`, `time` and `number`, the first server-side check on what an answer *contains*, a per-question
error slot, and formatted dates and times on the way back out.

This run walks both form runners — the application shell and the course player's own runner, which
share `question.html` — breaks each of the new types in the ways a real person would, and checks the
three read surfaces (check-your-answers, the admin answer preview, the runner's re-render).

Two things it deliberately hunts for beyond the golden path:

- **Nothing already working may change.** `short_text` and `number` now render through a shared
  partial that replaced their own templates, so every existing question type is re-checked.
- **A rejected answer must not be stored.** That is the whole reason the check exists: a stored
  `banana` under a required date question would satisfy the required-question check and let an
  application through.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh` — note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `form_engine_data_field` branch. If it names another branch, another server holds the port; go
   back to step 1.

### 0.2 Seed data

Missing data is created through the `fls-dev:qa-data-helper` agent, never by hand.

1. **Demo content loaded.** `uv run python manage.py content_save demo_content DemoDev`. This is what
   creates the new questions, so a stale load means the whole run tests nothing. It is idempotent;
   re-run it if in doubt. Confirm the command exits without a validation error — a schema/model
   mismatch on `min`/`max` surfaces here first.
2. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
3. **Applicant:** a learner account, no staff flag, verified email, password equal to the email per
   project convention, holding no application and registered for no course. On a re-run, the account
   from the previous run already holds an application and its form sitting: clear them in that order
   — the `CourseApplication` first, then its `FormProgress`, which is RESTRICTed while the
   application names it.
4. **The applicant is registered for `functionality_demo_end_with_topic`**, used in §6 for the course
   player's own runner, and holds no form attempt at that placement — so the form's start screen
   reads "Start Form", not "Continue Form".

## §1 The new types render

Signed in as the applicant.

1. Open the catalogue, find the course from `functionality_demo_application_gated/course.md`
   ("By application"), and click "Apply now". Expect to land on
   `http://127.0.0.1:<PORT>/applications/application/<uuid>/page/1/`. Note the uuid.
2. On page 1 ("About you"), expect — alongside the questions that were already there — an email
   question, a URL question, a phone question, and a date-of-birth question.
3. Check each new input's actual type in the DOM, not just its appearance:
   - the email question is `<input type="email">`
   - the URL question is `<input type="url">`
   - the phone question is `<input type="tel">` and carries `inputmode="tel"`
   - the date question is `<input type="date">` and carries both a `min` and a `max` attribute
4. Confirm the date input opens a native picker on click (a calendar grid in Chromium). This is
   browser furniture and will look different on other platforms; all that matters is that it is the
   native control and not a plain text box.
5. Confirm the number question ("How many years have you been writing software?") now carries
   `min="0"` and `max="70"`. It rendered through a replaced template, so also confirm it still has
   `type="number"` and `inputmode="numeric"`.
6. Confirm the questions that were already on this page are unchanged: the short text is still
   `<input type="text">`, the multiple choice still renders radio-styled options, the checkbox group
   still renders its indicators, the long text is still a `<textarea>`. Every question still shows
   its number and, where required, the red asterisk with the `(required)` screen-reader text.
7. Navigate to the availability page (page 3, reachable by clicking through). Expect a
   `<input type="time">` and a `<select>` dropdown. Open the dropdown and confirm it lists the
   authored options with a blank entry first.

**Fail if:** any question renders the red `ERROR! UNHANDLED FORM TYPE` callout — that is the
dispatch ladder missing a branch.

## §2 The happy path stores and advances

Still on page 1.

1. Fill every question on the page with a valid answer. Use the date picker for the date, and type
   `demo@example.com` for the email.
2. For the URL, type `linkedin.com/in/someone` — **with no scheme**. This must be accepted: the
   server prepends `https://` before validating, the way Django's own `URLField` does. A rejection
   here is a bug, not a stricter rule.
3. Click "Next". Expect to advance to page 2, not a 422 re-render. No error callout appears.
4. Click back to page 1 (the page dots). Expect every answer to come back populated — in particular
   the date input shows the date you picked, and the dropdown on page 3 shows the option you chose.

**Fail if:** the date input comes back empty after a valid answer. That means a formatted value
reached the `value` attribute; only the raw ISO string may go there.

## §3 A rejected answer: the core behaviour

This is the section the whole change exists for. A native date input cannot be typed into with
`banana`, so drive the POST directly rather than through the widget.

1. On page 1, fill every question validly **except** the date of birth.
2. Using the browser's dev tools (or `browser_evaluate`), change the date input's `type` attribute to
   `text` and set its value to `banana`, then submit the form. This is exactly what a crafted POST
   does, and it is the case the server has to catch.
3. Expect the page to re-render, not advance. Confirm the response status is **422**.
4. Expect a callout at the top of the page naming the question — "Question N needs a valid answer."
5. Expect a per-question error directly under the date input reading something like
   `You entered "banana". Enter a date in the format YYYY-MM-DD.` — it must recite the value back,
   because the native date input cannot show it.
6. Inspect the date input. It must carry `aria-invalid="true"` and an `aria-describedby` whose value
   is the `id` of that error paragraph. Confirm the two ids actually match — a typo here silently
   breaks the announcement and looks fine on screen.
7. The date input itself renders **empty**. That is correct and expected: the browser discards any
   `value` it cannot parse. This is why step 5 matters.
8. Confirm **the other answers on the page survived**. The email, URL, phone, short text and so on
   all come back populated. Rejecting one answer must not throw away the rest of the work.
9. Now the other half of the same rule. Submit `notanemail` in the email question (a plain
   `type="email"` box, so you can type it directly) with everything else valid. After the 422,
   the email input must still contain **`notanemail`** — the text-shaped types hand back exactly
   what the person typed, so they can correct it in place rather than retype it. Only `date` and
   `time` come back empty, and only because the browser blanks them.
10. Fix the date with the picker and the email, then click "Next". Expect to advance, with no error.

## §4 The rejected value is not stored

1. Repeat §3 steps 1–3 so the page is sitting at 422 with the date rejected.
2. Navigate away to page 2, then back to page 1. The date input must be **empty** — `banana` was
   never written.
3. Now answer the date validly and click "Next" so it is stored. Return to page 1, and repeat the
   `banana` submission. After the 422, navigate away and back: the date input must show the
   **previously stored valid date**, unchanged. A rejected answer neither overwrites nor deletes the
   good row that was already there.
4. Walk to the check-your-answers page. The date of birth must show the earlier valid date, never
   `banana`.

**Fail if:** `banana` appears anywhere, or the previously valid answer has been wiped.

## §5 The other types' failure branches

Each of these follows the §3 shape: set the value, submit, expect 422 with a per-question error that
names the format, confirm nothing was stored, and — for every type except `date` and `time` —
confirm the rejected text comes back in the input.

1. **Email** — submit `notanemail`. Expect a rejection. Then submit `someone@localhost`: expect it to
   be **accepted** (Django allows `localhost` specifically). Then `someone@internal`: expect a
   rejection, because a single-label domain other than `localhost` is refused. This surprises people
   in dev before it surprises them in production, so it is worth seeing once.
2. **URL** — submit `not a url` (with the space). Expect a rejection naming the format.
3. **Date out of bounds** — submit a date before the question's `min` or after its `max` (for a date
   of birth, try `2190-01-01`). Expect a rejection. The browser also refuses this client-side, so
   drive it the same way as §3: the point is that the server enforces it again, since `min` in the
   markup is a hint anyone can edit away.
4. **An impossible but well-formed date** — submit `2025-02-30`. Expect a **422 with an error
   message**, not a 500. This is the specific trap: Django's `parse_date` returns `None` for
   `banana` but *raises* for `2025-02-30`, and code that only checks for `None` crashes here.
   A 500 on this step is the single most likely bug in the whole change.
5. **Number out of bounds** — submit `400` for the years-of-experience question (`max: 70`). Expect a
   rejection.
6. **Time** — on page 3, submit `25:00` for the time question. Expect a rejection, not a 500 (same
   trap as step 4, via `parse_time`).
7. **Phone** — submit `not a number at all`. Expect it to be **accepted**. `type="tel"` is a keyboard
   hint and nothing more; real phone validation is deliberately out of scope. A rejection here is a
   bug.
8. **Several at once** — reject the date *and* the email in one submission. Expect the top callout to
   name both question numbers in one sentence ("Questions N and M need valid answers.") and expect
   both inputs to carry their own error text and their own `aria-describedby`.

## §6 A required question with a rejected answer must not let the form through

The dangerous case: a required date question whose answer was rejected leaves no stored row, and the
final submission has to notice.

1. Leave the date of birth answered with a rejected value only — never with a valid one. (If it is
   already stored from an earlier section, clear that answer through the `fls-dev:qa-data-helper`
   agent first, or restart with a fresh applicant.)
2. Answer everything else on every page validly.
3. Reach the check-your-answers page. The date of birth row must read "Not answered", not `banana`.
4. Click "Submit application". Expect a **422** and the "Question N needs an answer" callout — the
   whole-form required check catches it, because no row was stored.
5. Go back, answer the date validly, and submit again. Expect the success message and the redirect to
   the dashboard.

**Fail if:** the application submits while the date of birth holds a rejected value. That is the
failure the "do not store a rejected answer" rule exists to prevent.

## §7 Stored answers read properly on the way out

1. On the check-your-answers page of the submitted application, find the date of birth. It must read
   as a formatted date — `March 14, 1987`, not `1987-03-14`.
2. The time answer must read as a formatted time — `2:30 p.m.`, not `14:30`.
3. The email, URL and phone answers read exactly as typed — no formatting, and the URL shows what the
   applicant entered rather than a rewritten one.
4. The dropdown answer shows the chosen option's **text**, not its id.
5. Every answer that was already displayed before this change still reads the same: short text, long
   text (with its line breaks preserved), number, the multiple-choice and checkbox option texts, and
   the file with its download button.

## §8 The admin side

Signed in as the superuser at `http://127.0.0.1:<PORT>/admin/`.

1. Open the Question answers changelist. The "Answer" column for the date-of-birth answer must show
   the formatted date, not the raw ISO string. The time answer likewise.
2. Open that answer's change form. The `text_answer` field must still hold the **raw ISO string** —
   it is an edit widget, and reformatting it would change what gets saved back on an untouched save.
3. Search the changelist for the raw ISO string (`1987-03-14`). It must find the row: search runs
   against what is stored, not what is displayed.
4. Open a `Form progress` record and check the inline answers. Same rule: raw string in the edit
   widget.
5. Open a `Form question` in the admin. The type dropdown must list all twelve types, and the
   `min`/`max` fields must be present and editable.

**Fail if:** the changelist takes visibly longer to load than before, or the admin page count jumps —
the answer preview now reads the question, which needs `list_select_related` to stay cheap.

## §9 The course player's own runner

`question.html` is shared, so everything above has a second consumer. This section proves the shared
markup did not regress the learner-facing runner.

1. Sign in as the applicant and open `functionality_demo_end_with_topic`.
2. Start its survey form. Expect every question to render as it did before: the multiple choice, the
   checkbox group, the short text and the long text.
3. Submit the page with a required question left blank. Expect the existing "Missing answers" callout
   and a 422, unchanged.
4. Submit the page with a required **checkbox group** left empty. Expect the client-side "Select at
   least one option." message under that group — it is revealed by the runner's Alpine component and
   is the one per-question message that already existed. Confirm the new error slot has not displaced
   it.
5. Complete the form and reach the results page. Confirm scoring is unchanged.

**Fail if:** the runner's live answered-count tally, its page dots, or its save-and-exit and
submit-and-exit buttons behave any differently than before.

## §10 Adversarial and edge cases

1. **Empty optional typed question.** Leave the phone question (optional) blank and submit. Expect no
   error and no stored row — a blank answer is not an invalid one.
2. **Whitespace only.** Submit `   ` for the email question. Expect it to be treated as blank, not as
   an invalid email, since the answer is trimmed before anything else looks at it.
3. **Submit-and-exit carrying a rejected value.** In the course player's runner, set a rejected value
   on a typed question and use "Leave and submit" / save-and-exit. Expect no 500. The rejected value
   is silently dropped — there is no page to report it on — and the attempt finalises with that
   question unanswered.
4. **Two sittings.** Confirm a second applicant's rejected answer does not affect the first
   applicant's stored answers.
5. **A read-only form.** Reopen a submitted application's form page. Every input, including the new
   date, time and dropdown, must be `disabled`, and no error slot renders.
6. **Mobile width.** At ~400px, confirm the new inputs and the error text do not overflow, the
   dropdown is reachable, and the error paragraph wraps rather than pushing the page sideways.
7. **An answer stored under a question whose type changed.** Through the admin, change a `short_text`
   question that already holds the answer `hello` to type `date`. Then open the check-your-answers
   page. It must display `hello` unchanged — an unparseable stored value falls back to the raw
   string, never a crash and never a blank.
