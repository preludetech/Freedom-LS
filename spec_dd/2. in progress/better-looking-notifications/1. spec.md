# Spec: better-looking notifications

## Purpose

The notifications UI that `user-communication-1-notifications-core` built looks nothing like its
registered Claude Design design, because SDD never carried the design past the plan (`idea.md`,
"What went wrong"). Phase 1 fixes how SDD carries a design from registration to QA. Phase 2
rebuilds the notifications UI through the fixed process, and so tests it.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| drawn element | coined | A control, region or state that a design's artboard draws. Only the ones the spec asks for are built. "Item" is taken. |
| design check | coined | Comparing a screenshot of the running app with the design screenshot for the same state, against the plan's checklist for that state. "Conformance" is taken (`freedom_ls/contrib/conformance/`). |
| design state | coined | One artboard, as a state the app must reach. Its id is `<section-id>/<artboard-id>`, and its design screenshot is `design_screenshots/<section-id>__<artboard-id>.png`. |
| design checklist | coined | The checkable lines that close a design state's transcription in the plan. The design check and QA check against it. |
| design miss | coined | A design checklist line the design check finds unmet. |
| token mapping | coined | The plan's table saying which FLS token, cotton component or semantic icon expresses each visual treatment the design draws, and what is lost. |
| artboard | borrowed | Claude Design's `DCArtboard` in `design-canvas.jsx`: one framed screen-state on a design canvas. |
| handoff prompt | borrowed | The prompt Claude Design copies for a selection (`design sync prompt.md` is one). |

## Scope

**In, phase 1 (SDD process).** `/sdd:register_design` takes a handoff prompt, syncs the design's
source and screenshots every artboard. `/sdd:spec_from_idea`, `/sdd:plan_from_spec`,
`/sdd:implement_plan` and `/fls-dev:do_qa` build and check against those files. Every step treats
the design as a visual reference, never a source of scope: the specs and existing functionality
decide what is built, anything else the design draws is left out without asking, and FLS's own
theme, tokens and icons style it.

**In, phase 2 (notifications UI).** Re-register `spec_dd/1. next/user-communication/`, then
restyle every surface `user-communication-1-notifications-core` built: the bell and badge; the
panel as a desktop popover and as the full-width sheet at 375px; the notification centre
populated, all read, empty, with the Unread filter empty, as a long list, and at 375px. Their
behaviour does not change.

**Out:**
- Every drawn element the phase 2 scope above does not name, including the Preferences gear and
  button, the "about" line, "Show older notifications", `role="dialog"` on the panel and the
  message notification item.
- `header_bar.html`'s site title hiding instead of truncating at 375px. It belongs to `base`, not
  `comms`.
- The bell's 40px hit target against the design's 44px.
- Re-registering any design other than `user-communication`, the only `design.md` in the repo.
- Pixel diffing. FLS's theme deliberately differs from the design's.

## Decisions

1. **Two phases on one branch.** Phase 2 is planned only after phase 1 is implemented, so its plan
   goes through the new transcription and design checks. Phase 2's files carry the suffix `2b`:
   `2b. plan.md`, `3b. frontend_qa.md`, and batch markers `[batch 2b.N]`.
2. **The design source is committed whole, including `design-system/kit.css`.** A worktree only has
   what git has, and `kit.css` styles every artboard.
3. **The screenshots come from a script, not from Playwright MCP.** A script run by
   `sdd:sdd-mechanic` produces the same PNGs on every run and costs no model context.
4. **Hooks skip `design_source/`, and the secrets baseline is not used for it.** Synced files must
   stay byte-identical, and re-syncs are routine, so re-baselining every SRI `integrity` hash on
   each one is churn.
5. **Design misses are fixed where they are found.** Implementation sends its own misses back to a
   fix batch. QA triages them like bugs, so a miss can reach `fls-dev:qa-bugfixer`. This overrides
   the idea's "never auto-fixed".
6. **The browser half of implementation's design check sits behind a project hook.** The sdd
   plugin depends on no other plugin, and the dev server, test data and Playwright server are
   fls-dev's and ds's.
7. **The category tile colour is optional.** A category with no colour gets a neutral tile. That is
   what the design draws for registration, the one category FLS ships, so no downstream project
   breaks.
8. **`check_all` maps to Heroicons `check-circle`.** Heroicons has no double tick. Lucide,
   Tabler and Phosphor get their real double tick.

## Requirements

### Registration: `claude_plugins/sdd/commands/register_design.md`

- **Input.** The second argument is a handoff prompt, pasted or given as a file path. A bare
  `https://claude.ai/design/p/…` link is still accepted. From the prompt, take the project id and
  entry file from the link, the focus files from "Focus on these files" and the imports from "Also
  read these files". Given a bare link, work out the file list as today, and say so in the summary.
- **`design_prompt.md`.** Copy the prompt verbatim into `<spec-dir>/design_prompt.md`.
- **`design_source/`.** Sync through `DesignSync` `get_file`, at depth 0: the focus files, the
  listed imports, and every local file they reference through `@import`, `<link href>` or
  `<script src>`, repeated until nothing new turns up. Write each file whole and unedited to
  `<spec-dir>/design_source/<project path>`, never summarised or trimmed. Skip external URLs and
  binaries (fonts, images). On re-registration, replace the directory's contents.
- **`design_screenshots/`.** Delegate to `sdd:sdd-mechanic`, which runs `design_screenshots.sh
  <spec-dir>`, resolving the script's path through `PLUGINS_ROOT` the way `pre_step_rebase.md`
  Step 3 resolves `upstream_change_scan.sh`. The directory must never be `screenshots/`, which
  `do_qa` wipes on every run.
- **No scope questions.** Registration asks the user nothing about what the design draws. The
  design is a visual reference: whatever no spec asks for is left out silently.
- **Re-registration.** `design.md` is still rewritten whole.
- **The `design.md` template (L66-110).** "Made of" comes from the prompt, and the "ignore the
  other files" line goes. "How to read it" says to read `design_source/` and
  `design_screenshots/` from the repo first, and to use `DesignSync` only to re-register. "How to
  treat it" says the design is a visual reference drawn without knowledge of FLS's features, plans
  or theme; the spec and existing functionality win; and FLS's theme tokens, fonts, components and
  icon set style it, with no new themes, tokens, fonts or icons proposed.
- **The commit step** stages `design_prompt.md`, `design_source/` and `design_screenshots/`.

### Screenshot script: `claude_plugins/sdd/scripts/design_screenshots.{sh,py}` and `claude_plugins/sdd/resources/design_canvas_flat.jsx`

- `design_canvas_flat.jsx` is the stand-in from `research_design_render_spike.md`, unchanged in
  behaviour. Every artboard renders 1:1 inside `data-artboard="<section-id>/<artboard-id>"`.
- `design_screenshots.sh` is a thin wrapper in the style of
  `claude_plugins/fls-dev/scripts/compress_screenshots.sh` that runs
  `uv run --with playwright python design_screenshots.py "$@"`. It installs Chromium through
  `playwright install chromium` when it is missing, and accepts that a Playwright version change
  costs a one-off download.
- `design_screenshots.py <spec-dir>`:
  1. Read the entry file from `design.md`'s "Entry file" line. Copy `design_source/` to a
     temporary directory. When the entry file loads `design-canvas.jsx`, replace that file with
     the stand-in. `design_source/` itself is never modified.
  2. Serve the copy on `127.0.0.1` on a free port.
  3. Open it in Chromium at viewport 1440x900 with `deviceScaleFactor: 1`. Wait for `networkidle`,
     then for the `[data-artboard]` count to stop changing.
  4. Clear the old PNGs, then take one element screenshot per artboard (`animations: "disabled"`,
     `scale: "css"`) into `<spec-dir>/design_screenshots/<section-id>__<artboard-id>.png`.
  5. If the design has no canvas, screenshot the whole page at widths 1280 and 375 instead.
  6. Exit non-zero, naming the problem, when the entry file is missing, the page fails to render,
     or it finds no artboards.
- `.claude/settings.json` gets an allow entry for the `.sh`, after the existing
  `claude_plugins/sdd/scripts/*` entries (L106-107).

### Spec step: `claude_plugins/sdd/commands/spec_from_idea.md`

The design passage (L65-68) gains this rule: the spec's scope comes from the idea alone. A drawn
element the idea does not ask for is left out without a question, and no theme, token, font or
icon from the design enters the spec. Resources names `design.md`.

### Plan step: `claude_plugins/sdd/commands/plan_from_spec.md`

- An optional suffix argument makes the run write, and commit, suffixed files: `2b` writes
  `2b. plan.md` and `3b. frontend_qa.md`. Without it, the names stay `2. plan.md` and
  `3. frontend_qa.md`.
- Step 1 (L38): when a `design.md` applies, the plan reads `design_source/`, `design_screenshots/`
  and gains a **Design** section with two parts.
  - A per-state transcription for each designed screen and state the plan builds: its design
    screenshot file; the elements in order with their hierarchy and copy; which controls show in
    which state; and how to reach the state in the running app (URL and data). Drawn elements the spec does
    not build are omitted silently. The screenshot wins over the CSS when
    they disagree.
  - A token mapping: `Design treatment | FLS token / component / icon | Lost`. It covers every tint,
    tile, weight, text treatment and icon the transcription uses, in the shape of
    `spec_dd/3. done/2026-09-08_17:31_better-form-start-page/research_design_source.md`. Only existing
    theme tokens, components and semantic icons; "Lost" is styling that is dropped, never
    something to add.
- Each slice that builds a designed screen is marked with the states it builds.
- Step 5: each frontend QA test that maps to a design state names that state's design screenshot
  and carries its design checklist, taken from the transcription.

### Implementation step: `claude_plugins/sdd/commands/implement_plan.md`

- The same optional suffix argument selects `<suffix>. plan.md`, and batch markers become
  `[batch <suffix>.N]`, so the resume scan never mistakes phase 1's `[batch N]` commits for phase
  2's.
- Every batch brief (Step 2) passes paths, not contents: the plan's Design section, and the design
  screenshots for the batch's states. It also says to build only what the Design section
  transcribes, in FLS's theme.
- After a slice marked with design states returns `ok`, the depth-0 orchestrator runs a design
  check:
  1. Follow the `Design check` hook (below) with the spec dir and the slice's states. It returns
     one screenshot path per state and width.
  2. Read each screenshot and its design screenshot. List each one's elements region by region,
     then diff the lists against the plan's checklist. Judge layout, order, hierarchy, relative
     density, states and copy. Do not judge colour, font, icons or exact pixels. A drawn element the checklist does not
     list is not a miss.
  3. Spawn one fix batch with the list of misses, then check again.
  4. A miss that survives two fix batches unchanged stops the run with `status: blocked`, naming
     the miss. It points to a contradiction between the plan and the tokens that a human has to
     settle.
- A blank or absent `Design check` value skips the check, and the run's summary says so.
- `allowed-tools` gains `ToolSearch`.

### Design check hook: `.claude/sdd/config.md` and `claude_plugins/fls-dev/commands/protected/design_check.md`

- `/sdd:init` adds a `Design check` key to the config (blank is valid), in its own `## Design Hooks`
  section after `## Rebase Hooks`, read the same way (`config.local.md` wins).
- `/fls-dev:init` points it at `claude_plugins/fls-dev/commands/protected/design_check.md`, only
  when the key is blank or absent. It never overwrites a value, and this is its one write outside
  its own slice besides the legacy migration. That
  helper runs inline at depth 0, like `frontend_check.md`, and declares its own browser tools. It
  starts the server the way `do_qa.md` Steps 3-4 do, sets up each state's data the way `do_qa.md`
  Rule 2 does, and screenshots each state at the design's widths through
  `mcp__plugin_ds_playwright__*` into `.sdd-work/`.

### QA: `claude_plugins/fls-dev/commands/do_qa.md`

- Steps 7-9: for every test that names a design screenshot, put this run's screenshot beside it,
  check the test's design checklist the same way as implementation's step 2, and record a
  `<section>.<n>-design` row in the report.
- A drawn element the checklist does not list passes when the build lacks it.
- Step 13: a design miss is a bug for the triage gate. It meets green-lane condition 1 when the
  plan's checklist names the expected treatment. The other four conditions apply unchanged, and
  the fixer's failing test is a Playwright test.
- Step 15: an unresolved design miss becomes an item under category 1. Nothing the design draws
  ever becomes a "decide whether to build" item.

### Pre-commit: `.pre-commit-config.yaml`

`trailing-whitespace`, `end-of-file-fixer` and `detect-secrets` exclude `(^|/)design_source/`.
`check-added-large-files` keeps scanning `design_screenshots/`.

### Phase 2 setup

- Run the new `/sdd:register_design spec_dd/1. next/user-communication/` with
  `design sync prompt.md`. It writes `design_prompt.md`, `design_source/` and `design_screenshots/`
  there, and rewrites `design.md`.
- Once re-registration is committed, delete the stand-ins beside this spec: `design_source/`,
  `design_screenshots/`, `design_snapshot_notifications.md` and `design sync prompt.md`.

### Phase 2 UI: `freedom_ls/comms/`, `freedom_ls/base/`, `freedom_ls/icons/`

`research_design_vs_built_gap.md` lists the gap screen by screen, and the per-state transcription in
`2b. plan.md` holds the details. The spec fixes these outcomes:

- **Category colour.** In `freedom_ls/base/notification_categories.py`, add
  `NotificationColour(StrEnum)` with `PRIMARY`, `SUCCESS`, `WARNING`, `INFO` and `ERROR`, and add
  `colour: NotificationColour | None = None` as the last field of `NotificationCategory`.
  `course.registered` stays `None`. `Notification.colour` in `freedom_ls/comms/models.py` reads it
  the way `Notification.icon` does.
- **Icon tile** (`partials/notification_row.html`). The icon sits in a small rounded tile. Each
  colour maps to literal classes in the template, so Tailwind sees them: the `*-light` /
  `on-*-light` pair for each status, `bg-primary/10 text-primary` for primary, and
  `bg-surface-2 text-muted` for `None`. The glyph must reach 3:1 against its tile under every
  shipped theme.
- **Whole-row target.** The message link uses the row's text colour with no underline. A stretched
  `::after` covers the row, so the whole row is the click target, with a pointer cursor. The row
  keeps its single `<a>` to `comms:notification_open`. A notification with no URL keeps its
  `<span>` and no click target. The Mark read/unread `c-button` stays a sibling of the link, never
  inside it, and sits above the stretched area.
- **Unread rows** get a primary opacity-modifier tint, on top of the bold weight, the dot and the
  label. The visible "Unread" label becomes `aria-hidden="true"`, because the `sr-only` "Unread."
  prefix already announces it.
- **Messages** clamp to two lines wherever the design screenshot clamps them.
- **Day headings** (`notification_list.html`) are uppercase, tracked and muted, at the size the
  design screenshots show.
- **Badge** (`partials/notification_badge.html`) gets a ring in the header colour, so it separates
  from the bell.
- **Filter** (`notification_list.html`) keeps its two `<a>` elements with `aria-current`. They lose
  the underline and read as the design's segmented control.
- **Mark all as read**, in the panel (`partials/notification_panel.html`) and on the centre,
  becomes a ghost `c-button` with `icon_left="check_all"`. Add `check_all` to
  `SEMANTIC_ICON_NAMES` (`freedom_ls/icons/semantic_names.py`) and to all four dicts in
  `freedom_ls/icons/mappings.py`: Heroicons `check-circle`, Lucide `check-check`, Tabler `checks`,
  Phosphor `checks`.
- **All-read banner** uses `c-icon name="success"` in place of `complete`.
- **No new theme tokens.** No changes to views, URLs, the Alpine component or polling.

## Testing

- Registration run against `spec_dd/1. next/user-communication/`:
  - `design_source/` holds every prompt-listed file plus `design-system/colors_and_type.css`, found
    by following `kit.css`'s `@import`.
  - `design_screenshots/` holds one PNG for every artboard in `User Communication.html`, including
    the ten spike names (`uc-1-bell__hd.png` … `uc-2-centre__emptym.png`).
  - `git commit` of the result passes pre-commit without changing any synced file.
- `design_screenshots.py` fails with a named error when `design_source/` has no entry file, or
  when the page renders no artboards.
- Registration and the later steps never ask the user whether to build something the design draws.
- `implement_plan` with suffix `2b` skips no `2b` batch because of phase 1's `[batch N]` commits.
- `NotificationCategory` built without `colour` gets `None`. `Notification.colour` passes the
  category's colour through.
- Row rendering (`freedom_ls/comms/tests/test_rendering.py`):
  - an unread row carries the tint class and `aria-hidden` on its visible label;
  - `Mark read` is not a descendant of the row's `<a>`;
  - each `NotificationColour` and `None` renders its tile classes.
- `check_all` resolves in all four icon sets, and the icon system checks
  (`freedom_ls/icons/checks.py`) pass.
- Playwright (`freedom_ls/comms/tests/playwright/test_notification_bell.py`,
  `test_notification_centre.py`): the existing tests still pass. Clicking a row outside the message
  text opens its target. On the centre, clicking Mark read in a row marks it read without
  navigating.
- `3b. frontend_qa.md`: each of the ten design states is compared, with a design row in the report.

## Success criteria

- `spec_dd/1. next/user-communication/` holds `design_prompt.md`, `design_source/` (with
  `design-system/kit.css` and `colors_and_type.css`), and `design_screenshots/`.
- The new `design.md` no longer tells readers to ignore `design-system/`, and says the design is
  a visual reference that never sets scope or theme.
- `2b. plan.md` has a per-state transcription for all ten design states and a token mapping.
- The `implement_plan` run for `2b. plan.md` logs a design check after each designed slice.
- `qa_report.md` for `3b. frontend_qa.md` has a design row for each of the ten states, with no
  unexplained miss.
- In the running app, no notification row title and no All/Unread pill is underlined or
  link-coloured, unread rows are tinted, every row's icon sits in a tile, and Mark all as read shows
  the `check_all` icon in the panel and on the centre.
- `uv run pytest` passes.
