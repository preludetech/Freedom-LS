# Spec, part two: the About you page

Builds on `1. spec.md` in this directory (part one), which is implemented on this branch. Where this
spec changes a part-one rule it says which section it replaces; everything else in part one stands.
The branch merges once both parts are implemented.

## 1. Purpose

Part one asks an anonymous applicant for their email at the very end, and the first form-page POST
has to create the application and its sitting. That puts a row-less page 1 in front of every
anonymous visitor, with a file question that cannot be used until the page is saved. It also gives
form authors no reliable way to know who applied. Every form asks for name and email itself, and a
signed-in applicant answers questions the account already holds.

After this work, an anonymous applicant starts on a fixed **About you** page that asks for their
name and email. That page creates the unclaimed application and its sitting, and every form page
after it has a sitting behind it. A signed-in applicant is never asked for what their account
already holds. About you looks exactly like the other pages of the application form.

## 2. Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| About you page | coined | The fixed first page of an application, owned by `course_applications`, asking for the applicant's name and email. It is not a `FormPage`: no form author creates it, and its answers are fields on `CourseApplication`, not `QuestionAnswer` rows. |

"Unclaimed", "claim", "handoff" and "sitting" keep part one's meanings.

## 3. Scope

In:

- The About you page for anonymous applicants, on form courses and no-form courses, rendered with
  the same markup as a form page.
- `first_name` and `last_name` on `CourseApplication`.
- Signed-in applicants: About you is shown only when the account is missing a field it requires, and
  only that field; the value is saved to the account.
- Check-your-answers shows an About you section; the email field moves off it.
- The handoff prefills signup's name fields as well as the email.
- The claim's draft rule reads submission, not a blank email.
- Removing part one's row-less page-1 machinery, which this makes dead.
- The demo application form stops asking for name and email.

Out: fields configurable per site; a phone number (waits for `phone-number-form-field`); changing
the account's name at claim; the two open part-one QA items in `todo.md` §9, which stay where they
are.

## 4. Decisions

- **Fixed fields: first name, last name, email.** First name is required when the site's signup
  policy requires a name (`get_effective_require_name` in `freedom_ls/accounts/utils.py`, the rule
  `SiteAwareSignupForm` uses), otherwise optional and labelled "First name (optional)". Last name is
  always optional. Email is always required.
- **About you is not a form-engine page.** A `FormPage` would be counted in page numbering, marking,
  question numbers and the course-content runner, and a signed-in applicant would need it hidden. A
  `course_applications` page that reuses form-engine markup stays out of all of that.
- **One source of markup.** About you renders through the same templates as a form question, so a
  change to how questions look changes About you too. A copy of the markup is not acceptable.
- **About you fields are unnumbered.** Form question numbers stay the same for signed-in and
  anonymous applicants, and the error messages that name question numbers stay true.
- **An unsubmitted draft is still claimed on session possession alone** (unchanged from part one
  §4). Its email is now typed rather than blank, so the claim tests `is_submitted` instead.
- **A claimed unsubmitted draft takes the account's name and email.** It becomes a signed-in
  applicant's draft, and a signed-in applicant's decision goes to the account email. A submitted
  application keeps what was typed. It is the record of what was sent, and its email has already
  matched a verified address.
- **The claim never writes to the account.** The typed name is used to prefill signup and is kept on
  the application, nothing more.

## 5. Requirements

### 5.1 Data model (`freedom_ls/course_applications/models.py`)

- New `first_name = models.CharField(max_length=200, blank=True)` and
  `last_name = models.CharField(max_length=200, blank=True)` on `CourseApplication`, matching
  `User.first_name`/`last_name`.
- A schema migration, then a data migration that copies `first_name` and `last_name` from `user` on
  every existing claimed row on every site (`apps.get_model`, as part one's email backfill does).
  Unclaimed rows created under part one keep blank names.
- After this, no row has an empty `email`, so part one §5.1's "Empty only on an unsubmitted anonymous
  draft" no longer holds, and the model docstring says so.
- `CourseApplicationFactory` fills the names from the user, and the `unclaimed` trait sets a name.

### 5.2 Shared field markup (`freedom_ls/form_engine/templates/`)

`question.html` and `inputs/text_input.html` today read a `FormQuestion`. Extract from them a field
shell and a text input that take plain values, and make `question.html` and `text_input.html` use
them:

- the shell: `<fieldset>`, `<legend>` with an optional number, the required asterisk and the sr-only
  "(required)", the error line `<p class="text-sm text-error" id="…_error">` with its sr-only
  "Error: ";
- the input: `type`, `inputmode`, `id`, `name`, value, `required`, `disabled`, `autocomplete`, and
  `aria-invalid`/`aria-describedby` when there is an error, with today's classes.

Cotton components or includes; the plan picks, following `fls-dev:template`. Rendered output for a
form question is byte-for-byte what it is today, apart from whitespace.

### 5.3 The About you page

New template `course_applications/about_you.html`, using the same shell as `form_page.html`: either
`form_page.html` is split so both extend a common layout, or About you extends it. It shows, in
`form_page.html`'s order and classes:

- the browser-only notice (part one §5.9) for an anonymous visitor or an unclaimed application;
- "Application for {course}", then `<h1>About you</h1>`;
- the page-links nav (§5.5);
- the `answer_errors.html` summary at the top, with a one-line "Check the details below." when the
  form is refused;
- the fields, each through the shared shell and input from §5.2: "First name" (`autocomplete="given-name"`),
  "Last name (optional)" (`family-name`), "Email address" (`type="email"`, `email`), each with its
  error line;
- the honeypot field in a hidden container, as part one's email partial does;
- the privacy statement and link that `partials/applicant_email_fields.html` carries today, below
  the email field;
- the button row: no Previous; "Next" on a form course, "Submit application" on a no-form course.

The form is `ApplicantDetailsForm` in `freedom_ls/course_applications/forms.py`, replacing
`ApplicantEmailForm`: `HoneypotFormMixin` plus the three fields. `first_name` is required per §4,
names are stripped, the email is lowercased as today. It takes the fields to show, so the signed-in
case (§5.6) can ask for only the missing ones. Django's default widget rendering is never used;
the template draws each field from the bound form's values and errors.

### 5.4 The anonymous flow (`freedom_ls/course_applications/views.py`)

Replaces part one §5.3 steps 6 to 9 and the §5.5 email-at-submit rule for anonymous applicants.

- **Apply URL, GET, nothing held for this course:** render About you. No row, no session write.
- **Apply URL, POST:** validate. Invalid: 422, About you re-rendered with the typed values and
  errors, nothing created, the start cap not counted. Valid: the start cap (`_start_cap_response`)
  runs, then in one transaction:
  - **Form course:** create the sitting (`user=None`) and the application (`user=None`, names,
    email, `form_progress`); `remember_anonymous_sitting` and `remember_unclaimed_application`;
    redirect to `_resume_url`, which is page 1, or check-your-answers for a form with no pages.
  - **No-form course:** create the application with names and email, `record_application_submitted`,
    `remember_unclaimed_application`, `_redirect_to_handoff`.
- **The held-application branch** at the top of `_apply_anonymous` is unchanged.
- **New route** `application/<uuid:pk>/about-you/`, name `course_applications:about_you`, view
  `application_about_you`, `@never_cache_same_origin`, resolved through `_application_for_request`:
  - unclaimed and unsubmitted: GET renders About you over the stored values; a valid POST saves the
    three fields and redirects to page 1, or to check-your-answers when the URL carries
    `?return=check` (`RETURN_TO_CHECK`), as a form page does. Invalid POST: 422.
  - unclaimed and submitted: renders read-only, disabled fields and no button, as a submitted form
    page does.
  - claimed: redirect to `_resume_url` (or the status page once submitted). The account is the source
    of a claimed applicant's details.
- **Form page 1** of an unclaimed application: Previous links to `about_you`.
- **Check-your-answers:**
  - An "About you" card with name and email comes first, in the same card markup as the page sections.
    For an unclaimed unsubmitted application it has an Edit link to `about_you?return=check`; for a
    claimed one it has no Edit link and reads from the application, which holds the account's
    details.
  - The email field, `ApplicantEmailForm` and the `applicant_email_fields.html` partial go. The
    "Your decision will be sent to …" line goes too, since the card shows the address.
  - Anonymous POST: the whole-form check (422 as today), then `form_progress.complete()`,
    `record_application_submitted`, `_redirect_to_handoff`. No email is read from the POST.
- **The handoff** (`_redirect_to_handoff`) adds `first_name` and `last_name`, when not blank, to the
  signup query string beside `email`. The toast is unchanged.
- **Signup prefill:** `SiteAwareSignupForm` (`freedom_ls/accounts/forms.py`) sets the initial value
  of `first_name` and `last_name` from the request's query string, capped at the field's
  `max_length`. allauth already does this for `email`, but not for these two fields. A value in the
  POST always wins over the query string.

### 5.5 Page-links nav

For an application that shows About you (unclaimed), the nav's first entry is About you and the form
pages follow. Displayed numbers run 1 to n+1. Form-page URLs keep their form page numbers, and
`page_context`/`build_page_links` in `form_engine` stay generic: `course_applications` prepends the
entry and renumbers. About you is always accessible, and the form pages' accessibility is unchanged.
On About you itself, before any row exists, the nav shows About you as current and page 1 as not
yet reachable.

A claimed application's nav is as today.

### 5.6 Signed-in applicants

- **Nothing missing.** This is the normal case, and the flow is as today. `_start_application` copies the
  account's `first_name`, `last_name` and `email` into the application's `defaults`.
- **Missing a required field.** In practice this is an empty first name on a site that requires one. The
  apply URL renders About you with only the missing fields, and the email is not asked. A valid POST saves
  them to the account (`User.save(update_fields=[...])`), then continues as the signed-in apply does
  today, copying the now-complete details into the application. This page uses the same template and
  markup as the anonymous one, with the nav entries shown as for an unclaimed application. The
  existing short-circuits (existing application, held unclaimed application, coming soon) run before
  it.
- A blank optional field is never asked for.

### 5.7 Claim (`freedom_ls/course_applications/claims.py`)

Replaces part one §5.6 steps 4 and 5 for the test that decides between the two:

- Unsubmitted (`not application.is_submitted`): attach on session possession, and set the
  application's `email`, `first_name` and `last_name` from the account.
- Submitted: require the verified-address match as today; on a match, attach and keep the typed
  details.

`_attach` loses its "fill a blank email" branch; the field update moves to the unsubmitted case.
Nothing in the claim writes to `User`.

### 5.8 Removals

These existed only because an anonymous page 1 had no sitting behind it, and they go along with the
tests that pin them:

- `ignore_file_questions` on `submit_page` (`form_engine/page_flow.py`) and
  `unanswered_required_on_page` (`form_engine/paging.py`);
- `form_progress: FormProgress | None` and the `answers` override on `page_context`, and the `None`
  branch of `build_page_links`; both take a sitting again;
- the "Save this page to attach a file." branch in `form_engine/question.html`;
- the create-validate-rollback body of `_apply_anonymous_form_course`;
- `SAVED_FOR_FILE`, its context key and its callout in `form_page.html`;
- `ApplicantEmailForm` and `partials/applicant_email_fields.html`;
- part one §8's "an application form with no pages gives the anonymous apply URL a 404": About you
  now leads to check-your-answers.

The learner-interface runner's `page_context` call (`learner_interface/views.py`) already passes a
sitting and is unaffected.

### 5.9 Admin (`freedom_ls/course_applications/admin.py`)

`applicant_name` returns the application's own `first_name`/`last_name`, falling back to the user's
name when both are blank. `search_fields` gains `first_name` and `last_name`. The change page shows
the three fields read-only.

### 5.10 Demo content

`demo_content/functionality_demo_application_form/1. about-you.yaml` drops the "What is your full
name?" and "What is your email address?" questions, and the page is retitled so it no longer shares
the About you page's name (for example "Your background"). Keep the UUIDs of the questions that
remain.

## 8. Open questions

Defaults taken; overrule by editing this file.

- The names go in the signup URL beside the email, with the same exposure part one accepted for the
  email.
- Unclaimed applications created under part one have blank names and show the typed email in the
  admin, as today.
- A signed-in applicant whose session holds an unclaimed draft is still sent to the claim landing
  by `apply`, before any About you check.

## 9. Success criteria

- An anonymous visitor who clicks "Apply now" sees About you; no row exists until they submit it.
- About you and a form page, screenshotted side by side at the three QA viewports, use the same
  heading, nav, field, error and button styles.
- After About you, page 1's file question accepts a file without a prior save.
- Check-your-answers shows the About you details and has no email field; submitting lands on signup
  with email and first name prefilled.
- A signed-in applicant with a complete account never sees About you; one missing a required first
  name is asked for only that, and it is saved to the account.
- Claiming an unsubmitted draft gives it the account's name and email; claiming a submitted one keeps
  the typed details; the account's name never changes.
- `ignore_file_questions`, `SAVED_FOR_FILE` and the sitting-less `page_context` path no longer exist.
- The full test suite passes.
