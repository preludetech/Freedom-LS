# Frontend QA: allow anonymous course applications

An anonymous visitor can now fill in and submit a course application before creating an account.
The email is typed at submit, the visitor is handed off to signup with it prefilled, and the
application is attached to the account on the first verified login in the same browser. Signed-in
applicants see their account email read-only. The admin lists unclaimed applications and can delete
them. This run walks the anonymous journey for a form course and a no-form course, the claim in
its matching, mismatching and second-browser forms, the session-possession 404s, the caps, the
signed-in flow, and the admin.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

"A fresh browser" below means a new Playwright browser context with no cookies. "The same browser"
means the context that holds the application's session cookie. Keep track of which is which:
most of the claim tests turn on it.

---

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh` — note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `allow-course-apply-anon` branch. If it names another branch, another server holds the port; go
   back to step 1.
4. Signup confirmation mail lands in Mailpit at `http://localhost:8025`. Open it once now to check
   it is up.

### 0.2 Seed data

Every item below must exist before §1. Missing data is created through the `fls-dev:qa-data-helper`
agent, never by hand.

1. **Demo content loaded.** `uv run python manage.py content_save demo_content DemoDev`. This loads
   the course titled "Functionality Demo - Application gated course" (call it *the form course*)
   and its three-page form ("About you", "Supporting documents" with a required file question,
   "Availability"). Idempotent.
2. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
3. **The no-form course.** `uv run python manage.py qa_create_application_docs_scenario` creates
   an application-gated course that names no form, slug `advanced-product-analytics-masterclass`
   (call it *the no-form course*), and the learner `demodev_applicant@email.com` who already
   applied to it.
4. **A gated course with a file question on page 1.** Through the data helper: an
   application-gated course titled "QA page-one file course" whose form has one page holding a
   required short-text question "Your name" and a required file question "Upload your ID". Call it
   *the page-one-file course*.
5. **A gated course with a page-less form.** Through the data helper: an application-gated course
   titled "QA page-less course" whose application form has no pages. Call it *the page-less
   course*.
6. **A hidden gated course.** Through the data helper: an application-gated course titled "QA
   hidden gated course" with visibility hidden, naming the demo application form. Note its slug.
7. **Two verified learners with no applications:**
   `uv run python manage.py qa_create_clean_applicant --email qa.anon.a@email.com` and the same for
   `qa.anon.b@email.com`. Password equals the email.
8. **The DemoDev `SiteSignupPolicy`** has `allow_signups=True` (the default). §7 flips it and flips
   it back.
9. **A PNG to upload.** Any PNG under 1 MB with real pixel content, saved as `id-scan.png` in the
   scratch directory.
10. **Fresh addresses.** Each test that signs up needs an address no account holds. Use
    `qa-anon-<n>@example.com` with a new `<n>` per test, and note which were used.

Between sections, unclaimed applications are removed through the admin (§8.3 covers the deletion
itself), never by database command.

## §1 The anonymous form journey

### 1.1 "Apply now" opens page 1 without creating anything

1. In a fresh browser, open `http://127.0.0.1:<PORT>/courses/`, click the form course, then
   "Apply now".
2. **Verify:** the URL is `/applications/apply/<slug>/` (the apply URL, not a page URL). The page
   heading is "About you". No redirect to signup or login.
3. **Verify:** an info callout reads "This application is saved in this browser only, for up to
   14 days. Submit it to keep it." (the number is `SESSION_COOKIE_AGE` in days; 14 in dev).
4. **Verify:** the page nav shows three page links; only "1" is clickable, "2" and "3" are not.
5. **Verify:** every question is blank; nothing is prefilled.
6. Sign in as `demodev@email.com` in another browser, open the admin at
   `http://127.0.0.1:<PORT>/admin/`, "Course applications". **Verify:** no new row exists for the
   form course (the GET created nothing).

### 1.2 A refused first page creates nothing but keeps what was typed

1. In the same fresh browser, type a two-paragraph answer into "Why do you want to take this
   course?" and tick one "Which of these interest you?" box, leave every required field blank, and
   press "Next".
2. **Verify:** the page re-renders (status 422 in the network log) with the error naming the
   required questions, still at the apply URL, with the long answer and the tick still there.
3. **Verify** in the admin: still no row.

### 1.3 The first save creates the draft and advances

1. Fill in "What is your full name?" (`Anon Applicant`), date of birth, email
   (`qa-anon-1@example.com`), years of software `3`, pick one "How did you hear" option. Press
   "Next".
2. **Verify:** the URL is now `/applications/application/<uuid>/page/2/` and the heading is
   "Supporting documents". The browser-only callout is still shown.
3. **Verify** in the admin: one row for the form course, Applicant column empty, "Claimed"
   unticked, "Submitted" unticked.
4. Click page link "1". **Verify:** the answers from step 1 are there.

### 1.4 Attach, replace, download and remove a file anonymously

1. On page 2, choose `id-scan.png` on "Upload a scan of your ID or a recent certificate".
2. **Verify:** the widget swaps to show `id-scan.png` with its size, a "Download" button, a
   "Replace" picker and a "Remove" button. No page reload.
3. Click "Download". **Verify:** the file downloads as an attachment (the response is a 200 with
   `Content-Disposition: attachment`), not a 404 or a login redirect.
4. Click "Remove". **Verify:** the widget says "File removed. This question needs a file before you
   can submit." Attach the file again.
5. Press "Next" without the file attached first, once, to check the required rule: remove the file,
   press "Next". **Verify:** 422 with the required-question error. Attach again, press "Next".
6. **Verify:** page 3, "Availability". Pick a time and a time zone. Press "Next".

### 1.5 Check your answers, the email field and the handoff

1. **Verify:** the check-your-answers page lists all three sections with the answers given and the
   file with a "Download" button. The browser-only callout is shown.
2. **Verify:** below the answers and above "Submit application" is the field labelled "Where
   should we send your decision?" with the statement "We use this address to link your application
   to your account and to send your decision. An application that is never linked to an account is
   kept until an administrator removes it." If the site has a privacy document, a link to it
   follows; if not, no link and no broken text.
3. Press "Submit application" with the email blank. **Verify:** 422, an error on the email field,
   nothing else changes, and the admin row is still "Submitted" unticked.
4. Type `QA-Anon-1@Example.com` (mixed case on purpose). Press "Submit application".
5. **Verify:** the browser lands on the signup page, URL `/accounts/signup/?email=qa-anon-1%40example.com&next=%2Fapplications%2Fclaim%2F`
   (the email lowercased, `next` the claim landing page). The email field is prefilled with the
   lowercased address. A success toast reads "Your application for Functionality Demo -
   Application gated course has been sent. Create an account or log in with
   qa-anon-1@example.com to see its progress."
6. **Verify** in the admin: the row now shows `qa-anon-1@example.com` in the Applicant column,
   "Submitted" ticked, "Claimed" unticked. Open it. **Verify:** the Applicant summary row says
   "Unclaimed: email unverified" and the answers document shows the answers and the file.
7. **Verify:** Mailpit holds no new message (nothing is sent at submit).

### 1.6 Apply again after submitting goes back to the handoff

1. In the same browser, open the form course's detail page and click "Apply now".
2. **Verify:** straight back to the signup page with the same `email` and `next`, and the same
   toast. No second row in the admin.
3. Use the browser's back button to return to the check-your-answers page (or open its URL).
   **Verify:** it renders read-only with the submitted callout, and its "Your application" button
   leads back to the signup handoff, not to a login page.

### 1.7 Signup and verification in the same browser claim the application

1. On the signup page, complete the form for `qa-anon-1@example.com` (names, password, consent
   boxes if shown). Submit.
2. **Verify:** the "confirmation email sent" page. Open Mailpit, open the latest message to that
   address, copy the `/accounts/confirm-email/<key>/` link, open it in the **same** browser and
   confirm.
3. **Verify:** the browser lands on the application's status page (`/applications/status/<uuid>/`)
   with a success toast "Your application for Functionality Demo - Application gated course is now
   on your dashboard."
4. Open `http://127.0.0.1:<PORT>/`. **Verify:** the dashboard's "Your applications" panel lists
   the course as "Pending review".
5. **Verify** in the admin: the row's Applicant column still shows the email, "Claimed" is now
   ticked, and the change page's Applicant row links to the user. Open "Form progress records":
   the sitting's User column names the user, not "Unclaimed".
6. Open the check-your-answers page for the application from the dashboard link. **Verify:** the
   file's "Download" still works for the now signed-in owner.

### 1.8 The claim landing page on a revisit

1. Still signed in, open `http://127.0.0.1:<PORT>/applications/claim/` directly.
2. **Verify:** redirected to the dashboard with an info toast "We couldn't find an application in
   this browser."
3. Send a POST to the same URL (for example by submitting a form with that action, or via the
   network tool). **Verify:** 405.
4. Sign out. Open `/applications/claim/` again. **Verify:** redirect to login with `next` set to it.

## §3 Mismatch, second browser, collision

### 3.1 A different verified email leaves the application unclaimed

1. In a fresh browser, apply anonymously to the form course through to submit with the email
   `qa-anon-3@example.com` (answer the required questions; attach the PNG on page 2).
2. On the signup page use the "Log in" switch and log in as `qa.anon.a@email.com`.
3. **Verify:** the mismatch page: heading "Link your application", a warning callout saying this
   account's email is not the one on the application to the course (`qa-anon-3@example.com`),
   with a link to the account email page and the instruction to press "Link my application" once
   it is verified and to stay signed in. A "Link my application" button and a "Back to the course"
   button.
4. **Verify** in the admin: the row is still unclaimed.
5. Press "Link my application" straight away, without verifying anything. **Verify:** the same
   mismatch page again; the admin row is still unclaimed.
6. Still signed in as `qa.anon.a`, open the account email page via the mismatch page's link, add
   `qa-anon-3@example.com`, and verify it from Mailpit in the same browser. Do **not** sign out.
7. Open `http://127.0.0.1:<PORT>/applications/claim/` (or go back to the mismatch page and press
   "Link my application"). **Verify:** the status page for the application with the "is now on
   your dashboard" toast. The admin shows it claimed by `qa.anon.a`.
8. Side effect: sign out, then open the form course and sign in as `qa.anon.a` again. **Verify:**
   the application is still on the dashboard (the claim stuck) and "Apply now" on that course leads
   to its status page, as for any applicant with an existing application.

### 3.2 A second browser never receives the application

1. In a fresh browser (A), apply anonymously to the no-form course and submit with
   `qa-anon-4@example.com`. Close the tab but keep the context.
2. In another fresh browser (B), sign up as `qa-anon-4@example.com` directly at
   `/accounts/signup/` (no `next`), confirm the email from Mailpit in browser B.
3. **Verify:** browser B lands on the dashboard with no application panel; the admin row is still
   unclaimed. Browser B opening `/applications/claim/` gets "We couldn't find an application in
   this browser."
4. Back in browser A, open `http://127.0.0.1:<PORT>/accounts/login/?next=/applications/claim/` and
   log in as `qa-anon-4@example.com`. **Verify:** now it is claimed, with the toast and status page.

### 3.3 An existing application to the same course wins

1. `qa.anon.b@email.com` applies while signed in to the no-form course (press "Apply now", then
   "Submit application"). Sign out.
2. In the same browser, apply anonymously to the no-form course with `qa.anon.b@email.com` and
   submit. On the signup page, switch to login and log in as `qa.anon.b`.
3. **Verify:** the status page of the **first** application with the info toast "You had already
   applied to <course>. This is your application." In the admin the anonymous row is still
   unclaimed and the id is gone from the browser (opening `/applications/claim/` again says
   nothing was found).

## §8 Abuse controls

### 8.1 The start cap

1. The dev defaults allow 10 starts per hour per address. In a fresh browser, start the no-form
   apply and submit it 11 times in a row, each with a new address `qa-cap-<n>@example.com`
   (after each handoff, clear the browser's cookies so the next "Apply now" is a new start,
   or use a fresh context each time: the cap counts the address, not the session).
2. **Verify:** the 11th submit renders the "You have made too many attempts" page at status 429
   with a `Retry-After` header, and the admin gains no 11th row.
3. **Verify:** a signed-in user (`qa.anon.b`) can still apply to another gated course from the same
   machine straight away.
4. Clear the cache so later sections are not throttled: `uv run python manage.py shell -c
   "from django.core.cache import cache; cache.clear()"`.

### 8.2 The upload cap

1. In a fresh browser, start the form course anonymously, reach page 2, and attach then replace
   the PNG repeatedly, 31 uploads in all.
2. **Verify:** the 31st attempt swaps the widget to its error state with "Too many uploads from
   your network. Try again in a few minutes." while the previously attached file stays listed with
   its Download button. No page reload, no 429 page.
3. Clear the cache as in §8.1 step 4.

### 8.3 Honeypot

1. On an anonymous check-your-answers page, use the browser devtools to reveal the hidden
   `fax_number` input, type anything into it, fill the email and submit.
2. **Verify:** 422 with the form-level error "We couldn't process this application. If you used
   autofill or a password manager, please try typing your email address in by hand." The admin row
   is still "Submitted" unticked and has no email.

## §9 Admin: listing, filtering, deleting

Sign in as `demodev@email.com` and open "Course applications".

### 9.1 Listing and filters

1. **Verify:** the columns are Applicant, Claimed, Applicant name, Course, Submitted, Submitted
   time, Created. Unclaimed rows show the typed email and a dash for the name; claimed rows show
   the user's email and name.
2. **Verify:** a "claimed" filter beside "submitted" with "Claimed" and "Unclaimed"; each narrows
   the list correctly.
3. Search for one of the typed addresses (for example `qa-anon-3`). **Verify:** the unclaimed row
   with that email is found.
4. **Verify:** the actions dropdown offers no "Delete selected"; selecting rows offers no bulk
   delete.

### 9.2 Delete is offered only for unclaimed rows, and only with the permission

1. Open a claimed row. **Verify:** no "Delete" button; opening
   `/admin/freedom_ls_course_applications/courseapplication/<uuid>/delete/` directly is 403.
2. Open an unclaimed row with a file (make one: a fresh browser applies to the form course with
   the PNG and submits with `qa-anon-6@example.com`). **Verify:** a "Delete" button.
3. Sign in as `qa_reviewer@email.com` (seeded by
   `uv run python manage.py qa_create_application_review_accounts`; staff with view permissions
   only). Open the same unclaimed row. **Verify:** no "Delete" button, and the delete URL is 403.
   Sign back in as the superuser.

### 9.3 Deleting removes the sitting and the file

1. Note the sitting's uuid and the file's storage path (the "Form progress record" link and the
   answer-file admin row).
2. Press "Delete". **Verify:** the confirmation page lists the application, its form progress
   record, its answers and its answer file. Confirm.
3. **Verify:** the row is gone; "Form progress records" has no row with that uuid; "Question answer
   files" has no row for it; the stored object is gone from the media directory the server writes
   to (`ls` the `user_uploads/form_answers/<sitting uuid>/` folder under the dev media root).

### 9.4 Other admins tolerate unclaimed rows

1. With at least one unclaimed application present, open "Form progress records" and "Question
   answer files". **Verify:** both lists render, with "Unclaimed" in the User / Applicant column
   for the unclaimed sitting, and the sitting's change page opens and links to its application.
