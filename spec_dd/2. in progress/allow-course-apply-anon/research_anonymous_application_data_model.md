# Research: data model for an anonymous application and its later claim

Topic: where a `CourseApplication` started by an anonymous visitor lives before a user account claims it, what the form sitting (`FormProgress`) needs, and how the claim, identity, cleanup and migration work.

## Summary recommendation

1. Make `CourseApplication.user` and `FormProgress.user` nullable and add `CourseApplication.email`. An unclaimed application is simply an application with no owner yet and no submission. This is option (a), with the sitting following it. Option (b) does not remove the need for an owner-less sitting, so it adds a model without removing the hard part. Option (c) cannot hold file uploads or the existing page flow.
2. Keep the existing `(site, user, course)` unique constraint exactly as it is. Postgres treats NULLs as distinct, so unclaimed rows are automatically exempt and claimed rows stay unique. Later, review's active-state partial index should carry `user IS NOT NULL` in its condition.
3. An anonymous application is never submitted. The sitting is only completed, and `record_application_submitted` only fires, after the claim, in an authenticated request. So everything downstream (review queue, webhooks, analytics, dashboard) only ever sees owned applications.
4. The capability to continue or claim a draft is the Django session, which holds the draft pk per course. The UUID pk alone is not a credential. A signed token (`django.core.signing`) is only needed if resume-from-another-browser is added.
5. Claim is one compare-and-set transaction, with "existing submitted application wins, otherwise the freshly claimed draft wins" as the conflict rule.
6. Add an `expire_unclaimed_applications` sweep to `run_housekeeping_sweeps` that deletes ownerless applications and their sittings after a configurable number of days. A `post_delete` receiver already removes stored files.

## What the code looks like today

- `CourseApplication` (`freedom_ls/course_applications/models.py`): non-null `user` (CASCADE), `course`, nullable `form_progress` OneToOne (RESTRICT), `UniqueConstraint(site, user, course)`, `is_submitted` is derived (`form_progress is None or completed_time is not None`). The docstring says the review spec will add `state` (FSM, protected), notes, transitions and an active-state partial unique index that REPLACES the plain constraint, and that this must not be architected away. The review research (`spec_dd/1. next/educator-interface-full-polish/application-review-ui/research_review_workflow.md`) lists the states `draft, submitted, under_review, changes_requested, approved, rejected, withdrawn` (optional `expired`), with `submit: draft -> submitted` and `withdraw` from draft. So "draft" is already a planned state; an unclaimed application is a draft with no owner.
- `views.py`: `apply` and `_start_application` use `@acquisition_login_required`, `get_or_create(user, course)`, create `FormProgress(user=..., form=course.application_form)`. Check-your-answers POST calls `form_progress.complete()` then `record_application_submitted`. Every view does `get_object_or_404(..., pk=pk, user=request.user)`. Course with no form: POST to `apply` creates the application, which is the submission.
- `queries.py`: `get_application_for_course` returns None and `get_active_applications` returns `.none()` for anonymous users. `backends.py` uses these for the "View my application" CTA and the dashboard panel; both are keyed on an authenticated user.
- `FormProgress` (`form_engine/models.py`): non-null `user` (CASCADE, related_name `form_progress`), `__str__` uses `self.user`. `QuestionAnswerFile.question_answer_file_upload_to` builds `user_uploads/{user_id}/form_answers/{pk}{ext}` from `answer.form_progress.user_id`; the comment says "the applicant prefix is what gives an erasure request a single subtree to sweep". `own_question_answer_file` serves files with `answer__form_progress__user=request.user` and `@login_required`. A `post_delete` receiver on `QuestionAnswerFile` (`form_engine/receivers.py`) removes the stored object.
- Other readers of `FormProgress.user`: only `form_engine/admin.py` (search on `form_progress__user__email`, an "Applicant" column, `list_select_related`), `form_engine/views.py` (the owner file view), `course_applications/admin.py` (`user` columns, search, change link), QA/dev commands, and `learner_progress/attempts.py`, which only ever creates attempts with `user=course_progress.learner.user` and filters by course-side relations. So quizzes always set a user; nullability does not change their behaviour provided the new null case never reaches the course side. The coupling is shallow and concentrated in admin, the file path, and the owner file view.
- `freedom_ls/webhooks/presets.py` has no application events (grep for "application" only matches `application/json`). The only submission side effect is `record_application_submitted` (GA4 `course_access_requested`, `request_kind=application`), which takes a `request`. `LegalConsent` is in `accounts/models.py` and is user-keyed; applications do not touch it today.
- `course_interest` solves the same acquisition problem without a draft row: the anonymous POST stashes the slug in the session and `redirect_to_auth(next=deferred_view)`; the deferred GET view `login_required`s, pops the session key, and only then writes. That works because an interest is a single click with no payload. An application with a multi-page form and file uploads has a payload, which is why it needs a row.
- `SiteAwareModel` provides a uuid4 pk and `site` FK, filtered by `SiteAwareManager`.

## Q1. Where does an anonymous application live before claim?

### (a) Nullable `user` plus `email` (recommended)

Fields: `CourseApplication.user` null, `email` EmailField (blank only for legacy), `FormProgress.user` null. No new model.

- Unique constraint: unchanged. A claimed row is still unique per `(site, user, course)`; unclaimed rows are intentionally unbounded. Do not try to make `(site, email, course)` unique: the typed email is unverified, different browsers legitimately produce several drafts, and a unique-by-email rule would let one person's typo or malice block another's application. Duplicates are resolved at claim time (Q3). Within one browser the session maps course to draft pk, so a revisit reuses the draft.
- Future FSM: the draft state exists already. Rule to keep compatible: `user IS NULL` implies `state = draft`. Express as a CheckConstraint once `state` exists. The active-state partial unique index becomes `condition = active states AND user IS NOT NULL` (redundant in Postgres because NULLs are distinct, but explicit). `submit` must require `user` set; reviewers' queue filters `user__isnull=False`.
- Site isolation: unchanged. The draft carries `site`; every lookup goes through `SiteAwareManager`, so a draft token or session from site A cannot claim on site B. Housekeeping must use `_base_manager` (as `find_orphaned_running_reports` does) because there is no request.
- Admin/review: the admin currently reads `obj.user.email` and `obj.user.last_name`; those need a fallback to `obj.email`. Recommend unclaimed drafts show in admin (the email is a lead, which is the stated reason for collecting it) but are excluded from the review queue and from the default state counts. A filter "Unclaimed" is cheap.
- Dashboard: no change. `get_active_applications` stays empty for anonymous users; the anonymous equivalent is a session lookup (see below), not a dashboard panel. After claim the row appears normally.
- `get_application_for_course`: keep the authenticated contract. Add a sibling for the anonymous draft in the current session (pk from the session, then fetch with `user__isnull=True`). Do not widen the existing function: the backend's CTA would otherwise show "View my application" to an anonymous visitor, and `status` is `login_required`. Whether the anonymous CTA should read "Continue your application" is a UX question for the spec.
- Webhooks/analytics: nothing fires for a draft. `record_application_submitted` stays on submit, after claim. Consider whether to record a funnel event for "application started" separately; that is new scope.

Cost: the draft sits in the same table the reviewers use, so every consumer must remember `user` can be null. Mitigation: only the admin and the owner views read `.user` today; a custom manager or queryset method `owned()` / `unclaimed()` keeps this contained.

### (b) Separate draft model converted on claim

An `UnclaimedApplication` (course, email, form_progress) turned into a `CourseApplication` on claim.

- Pros: `CourseApplication.user` stays non-null, the unique constraint and review model are untouched, admin and review code unchanged.
- Cons: the answers live on `FormProgress`, which has a non-null `user`, so the sitting still cannot be created without a user. (b) therefore does not escape the `FormProgress.user` question; it only moves the null from one table to another and adds a second model whose lifecycle (draft, convert, expire) re-implements `CourseApplication`'s. The OneToOne from `CourseApplication.form_progress` has to be re-pointed at claim, and the claim becomes create-plus-delete rather than a single update. It also duplicates "what is a draft", which the future FSM already defines.
- Only worth choosing if the owner decides `FormProgress` must stay user-non-null at all costs, in which case the anonymous sitting would need a placeholder user (Q2), which is worse.

### (c) Session-only draft, no DB row until auth

- Cannot hold uploads (`answer_file` is a storage-backed row), and the whole page flow (`submit_page`, `existing_answers_dict`, `unanswered_required_in_form`, check-answers) reads `QuestionAnswer` rows. It would mean re-implementing storage of answers in the session, with cookie/session size limits and no support for files. It also gives no lead (the email is lost on abandon) and loses everything if the session expires or the visitor changes device. Rejected.
- A cheaper variant of (c) is fine for one case: a course with no form. There the application is the submission, so the anonymous journey is "confirm, authenticate, create". It can use the `course_interest` session-stash pattern with no row. Recommendation: still use the uniform unclaimed row if the spec wants the email captured as a lead for these courses; otherwise the stash is simpler. This is a spec decision.

## Q2. What an anonymous sitting requires

Options: nullable `FormProgress.user`; a placeholder user; defer creating the sitting.

- Deferring the sitting is not possible: answers and uploads are written page by page, before the end, and the end is where authentication happens.
- Placeholder user (a real `User` row created for the visitor, e.g. an inactive or "guest" user): reuses all existing code unchanged, but `User` is a site-aware, email-based account model. It pollutes the user table, interferes with unique email and signup (the visitor's real signup collides with the guest account on the same email, which then needs a merge), shows up in educator and cohort lists, and every claim becomes a user merge (re-pointing the sitting, the application and uploads, plus deleting the guest). It also creates accounts without consent. Rejected.
- Nullable `FormProgress.user` (recommended). Concrete consequences:
  - Quizzes inside courses always set `user` in `learner_progress/attempts.py`, so nothing changes for them. Add a check that the course-side creation path never sees a null (type narrowing, not a new feature).
  - `FormProgress.__str__` and `QuestionAnswer.__str__` use `self.user`; they need an "(anonymous)" form.
  - The upload key `user_uploads/{user_id}/...` would read `user_uploads/None/...`. This needs a decision. Options: (i) a stable prefix not tied to ownership, such as the sitting pk, used for all new uploads, so nothing has to move at claim and erasure sweeps by rows (via `QuestionAnswerFile` through the sitting) rather than by prefix; (ii) `user_uploads/anonymous/{sitting_pk}/...` for anonymous uploads, leaving them under that prefix after claim and sweeping by rows at erasure; (iii) copy and delete the objects at claim (rejected: storage copy in the middle of a claim transaction is not atomic and leaves orphans on failure). Recommend (i) or (ii). Both mean the "single subtree per applicant" erasure assumption in the upload-to docstring no longer holds and the erasure procedure must also query the database. Flag it in the spec and in the erasure documentation. Files already stored under `{user_id}` stay where they are.
  - Serving: `own_question_answer_file` is `login_required` and scoped to `form_progress__user=request.user`. Applicants must still be able to see/download what they attached on the pages before authenticating, so an anonymous variant scoped to the session's draft is needed. Ownership of the sitting (via the session capability) stays "the whole control", never URL unguessability, matching the current comment. The admin download path needs no change.
  - Admin on `form_engine`: the search `form_progress__user__email` and the Applicant column need an email fallback (through `course_application.email`).
  - CASCADE on `user`: unclaimed rows have no user to cascade, so only housekeeping deletes them. That is another reason the sweep in Q5 is required, not optional.
  - Integrity: add a CheckConstraint-style rule in code that a sitting with a null user must have a `course_application` (an ownerless quiz sitting is a bug). It is a cross-table rule; Postgres cannot express it as a plain CheckConstraint. Enforce it in the creation helper and in a test.
- Privacy note for the spec: an anonymous sitting means unauthenticated, unverified people can upload ID scans and personal answers before any account or consent exists. Retention (Q5) and ensuring the pages carry the same privacy notice as the signed-in flow matter more than they did.

## Q3. The claim step

What transfers: only ownership. The application row gets `user`; the sitting gets `user`. Answers, selected options and `QuestionAnswerFile` rows hang off the sitting, so they move with it with no copy. Stored files do not move (see Q2). `LegalConsent` does not transfer: it is created by the signup/auth flow for the account, not by the application, and the draft carries none.

Shape (one transaction):
1. Resolve the draft from the session pk, scoped by `SiteAwareManager`.
2. Compare-and-set: `CourseApplication.objects.filter(pk=pk, user__isnull=True).update(user=user)`. A count of 1 means this request claimed it. A count of 0 means either it is already claimed by this same user (treat as success, idempotent: the user double-clicked or reloaded the post-login redirect) or by someone else (treat as 404, never reveal). Do the same `update` for the sitting inside the same transaction. A `select_for_update` on the draft row first is an alternative; the conditional update is simpler and race-safe on its own because only one UPDATE can match `user IS NULL`.
3. Remove the pk from the session once claimed (as `deferred_express_interest` pops its key).
4. Only after the claim, complete the sitting and call `record_application_submitted`, if the claim was triggered by the visitor pressing Submit. Auto-submit on return from auth (via a session "submit intent" flag, like the session key in `course_interest`) versus landing on check-your-answers once more for a second press is a UX decision. The idea says authenticate at the end and then the application "becomes claimed", which reads like claim plus submit in one step. Recommend claim-and-submit when the intent flag is present, claim-only otherwise; do the submit through the same code path as the existing check-answers POST so the validation of unanswered required questions still runs.
5. The claim must be reached with a GET after the auth redirect (the same reason `course_interest` has a deferred GET view). The session flag, not the URL, is what authorises it, so a forged link or prefetch claims nothing.

Claiming user already has an application for the course (the unique constraint would raise IntegrityError, so this must be handled explicitly before the update):
- Existing application is submitted (or, once FSM exists, anything past draft): keep the existing one. Delete the claimed draft, its sitting and files (post_delete receiver handles files), tell the user, and redirect to the existing status page. Rationale: it is the one the applicant and reviewers already know; never overwrite a submitted application with later answers silently.
- Existing application is itself an unsubmitted draft: keep the one just claimed (the user has just completed it), delete the old draft and its sitting. Alternative "keep the one with more answers" is more code for a rare case; "keep the existing one" loses what the user just typed, which is the worse failure.
- No merging of answers across sittings: pages and answers are bound to a form version and a merge has no safe rule.
- Deletion order: the application points at the sitting with RESTRICT, so delete the application first, then the sitting.
- Once review adds terminal states and the active-state partial index, a prior rejected/withdrawn application does not conflict; the claim creates the user's new active application subject to whatever re-apply rules the review spec sets.

Typed email differs from the claiming account's email:
- The claim authority is the session capability, not the email. The person who completed the form and then proved control of an account is the applicant. Blocking on mismatch would break the common case of someone applying with a work email and signing up with a personal one.
- Never auto-claim by matching email at signup or login (the "link by email" approach). Evidence: WooCommerce forum replies decline it because anyone can type someone else's address when placing a guest order, and Adobe Commerce ships it as an off-by-default setting. Here the typed email is unverified, so a stranger could plant drafts against a victim's email; they must not attach to the victim's account when the victim signs up.
- Keep the typed `email` on the row after claim as the contact email given on the application. Reviewers and admin show both when they differ (account email is authoritative for sending anything later). This also means signed-in applicants have `email` filled from `user.email` at creation, which satisfies the "autofill if signed in" requirement and keeps one place for admin to read.
- A non-blocking, tidy extra: if the account email is verified and equals the typed email, nothing special happens; the difference is only recorded.

## Q4. Identity of the anonymous draft across requests

- Session key vs token vs both: use the session as the credential. Store `{course_id: draft_pk}` in the session. Every anonymous view (form page, check answers, file download) must verify that the pk in the URL equals the session's pk for that course, in addition to `user__isnull=True`. This is also what survives the auth redirect: Django's `login()` calls `cycle_key()` and keeps the session data when no other user was logged in, and the existing `course_interest` deferred pattern already relies on the session surviving signup/login. Check that the allauth/custom signup path in this project does not flush the session when a different user was previously logged in on that browser; if it does, the claim silently finds nothing, so the claim view should handle "no draft in session" by sending the user to the course page, not a 500.
- Is the UUID pk enough as a capability URL? `SiteAwareModel.id` is uuid4 (122 random bits), so it is unguessable by enumeration. But a capability URL is also exposed by browser history, referrer headers, proxy and server logs, analytics (GA4 records page URLs, and `course_event_params` shows page paths are tracked), and shared or public computers. The drafts hold personal answers and ID scans, so URL knowledge must not be the credential. The existing code made the same call for files ("ownership is the whole control, never the unguessability of the URL"). Keep the existing `uuid:pk` URL shape for continuity, add the session check on top.
- When is a signed token needed? Only to resume or claim from a different browser or device (for example, an emailed "continue your application" link, or an auth flow that completes in another browser such as an email confirmation link opened on a phone). Recommend not building that in this iteration: the idea does not ask for it, and an emailed link sends mail to an unverified address. If added later, use `django.core.signing.dumps({"app": str(pk)}, salt="course-application-claim")` and `loads(..., salt=..., max_age=...)`. The salt namespaces tokens so one purpose's token is not valid for another, and `max_age` raises `SignatureExpired`. No DB column is required; a stored random `claim_token` would only be needed if tokens must be revocable or single-use. If single-use matters, the compare-and-set claim already makes it effectively single-use.
- Expiry: the session lifetime bounds browser-side access; the retention sweep (Q5) bounds server-side life. A draft whose session expired is unreachable, and then becomes a lead whose email is the only trace until swept. Make that explicit in the spec so nobody promises "resume later" without the token feature.

## Q5. Abandoned drafts: retention and cleanup

- Where: `freedom_ls/deployment/housekeeping.py`. `run_housekeeping_sweeps` runs each sweep in its own try/except for `SWEEP_FAILURES = (CommandError, DatabaseError)`, appending to `sweep_failures` or `notes`; the job is invoked by `fls_run_housekeeping` on a schedule the deploying project supplies. Add one more step following the pattern of `mark_orphaned_running_reports_failed`: a function that finds unclaimed applications past the age, deletes, and returns a count; a note "Deleted N unclaimed application(s)"; failure goes to `sweep_failures` (a sweep that fails to run withholds the heartbeat, which is right for a privacy-relevant deletion).
- Age setting: add `HOUSEKEEPING_UNCLAIMED_APPLICATION_MAX_AGE_DAYS` alongside the existing `HOUSEKEEPING_*` entries in `freedom_ls/deployment/config.py` (they are typed `Setting(default=...)` in seconds today, so a seconds-based name would match convention more closely). Suggested default 14 days: long enough for someone to come back after a long form with a document hunt, short enough given the data is unverified personal information. Measure from the sitting's `last_updated_time` (or the application's `updated_at`, whichever the answer-save path bumps; the sitting's field is bumped by `auto_now` whenever it is saved) so an active drafter is never cut off.
- Queryset: `CourseApplication._base_manager.filter(user__isnull=True, updated_at__lte=cutoff)` across all sites; no request means no current site. Do not delete anything with a user, and never a submitted row (an unclaimed row cannot be submitted by the rule in the summary, but include `form_progress__completed_time__isnull=True` as a belt-and-braces guard).
- Files: deleting the `QuestionAnswer` rows cascades to `QuestionAnswerFile`, and the existing `post_delete` receiver on `QuestionAnswerFile` removes the stored object, so no extra file handling is needed as long as deletion goes through the ORM (`.delete()`), not a bulk raw delete. Storage errors in the receiver should be considered: a failed storage delete after the row is gone leaves an orphan with no row to sweep it. Check how the receiver handles failures and whether it needs an orphan reconciliation; the current design deletes files only via rows.
- Order: delete the application first, then its sitting (RESTRICT on `form_progress`). Wrap per row in a transaction, so one failure does not block the rest of the batch, in the same spirit as the orphan sweeps' per-row try/except.
- Sentry: follow the existing convention of a constant message with the variable parts on the scope, if something unexpected is found; a routine deletion count goes in `notes` only.

## Q6. Migration shape (high level)

- `CourseApplication`: `user` becomes nullable; new `email` field; the `unique_application_per_site_user_course` constraint is unchanged (it keeps meaning for owned rows). Optionally add a CheckConstraint that an ownerless row must have an email.
- `FormProgress`: `user` becomes nullable.
- Backfill: existing `CourseApplication` rows need `email` populated from `user.email` (a data migration; the field is required for new rows, so the migration adds it blank then fills, then new rows always set it; or keep it blank-allowed at the model level and fill in the application-creation code). No backfill for `user` and none for `FormProgress`. Existing upload keys are untouched.
- Make the new rows' creation path the only place that sets `email`. Do not edit old migration files (project rule); new migrations only.
- No change needed on the course side or in `learner_progress`, since quizzes keep setting `user`.
- Before review's FSM migration lands, nothing here has to be undone; the later migration replaces the constraint as the docstring says, and adds `state` default `draft`, which is exactly what unclaimed rows are.

## Open decisions for the spec (not settled by this research)

1. Claim and submit in one step after authentication, or claim then press Submit again.
2. Whether no-form courses create an unclaimed row (to capture the lead) or use the session-stash pattern with no row.
3. Upload key scheme for anonymous uploads and how the erasure procedure sweeps them (Q2).
4. Retention default and whether the typed email on an expired draft is retained anywhere as a lead (as written, it is deleted with the row).
5. Whether to support resume from another browser (signed token), deferred here.
6. Whether the anonymous visitor gets any cue that a draft exists on the course page (CTA "Continue your application") requiring a session-based query next to the backend's `get_access`.
