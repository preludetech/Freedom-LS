# Research: abuse, security and privacy of anonymous applications

Topic: what changes when an unauthenticated visitor can start a `CourseApplication` (and its `FormProgress` sitting, and uploaded `QuestionAnswerFile`s) and only authenticates at the end, at which point the application is claimed by their `User`. Style mirrors `spec_dd/3. done/2026-05-05_08:18_better-registration/threat_model.md`; it extends that model (signup bot/mailbomb TA7, enumeration V7.3, open redirect V1.4, IP helper V5.3) rather than repeating it.

## 1. What the codebase does today (the baseline being relaxed)

Every application surface is gated on a signed-in owner:

- `course_applications/views.py`: `apply` is `@acquisition_login_required`; `application_status`, `application_form_page` and `application_check_answers` are `@login_required` and every lookup is `get_object_or_404(..., pk=pk, user=request.user)`. Non-owners get 404. The UUID pk is therefore never the control; ownership is.
- `form_engine/views.py`: `partial_question_file_upload` and `partial_question_file_remove` are `@login_required`/`@require_POST` and scope through `_owned_file_question`. `own_question_answer_file` filters `answer__form_progress__user=request.user` and its docstring states the principle: "Ownership is the whole control ... never the unguessability of the URL." `stream_question_answer_file` serves an attachment with `Cache-Control: private, no-store, must-revalidate`.
- `check_answers` sets `Cache-Control: no-store`.
- `form_engine/uploads.py`: single gate, 6 MB cap checked before read, extension allowlist, content-sniffed type, images decoded and re-encoded (EXIF/GPS dropped, decompression-bomb guard), PDFs stored as supplied. No malware scanning (stated openly in `docs/product/security-and-data-handling.md`).
- `apply` calls `raise_404_if_hidden_unregistered(user, course)` first, then the existing-application short-circuit, then the COMING_SOON redirect. `course_access/visibility.py` takes a `RequestUser`, so it can already receive an anonymous user (an anonymous user is never registered, so HIDDEN always 404s).
- `course_interest/views.py` already has the anonymous pattern: an anonymous POST for any slug gets an identical `redirect_to_auth` and so does not confirm a course exists.
- `CourseApplication.user` and (by the `FormProgress(user=user, ...)` call) `FormProgress.user` are non-null FKs with `on_delete=CASCADE`. Today there is no such thing as an application without a `User`. The feature must introduce one; that is the root of most threats below (and is a modelling question for the data-model research, not decided here).

## 2. Threat list

Likelihood is for a public learning site that runs paid advertising (signup-attribution doc shows ad-click tracking, so bot traffic and ad-fraud-adjacent traffic are realistic).

### T1. Junk applications and storage abuse (anonymous row and file creation)

- Threat: an unauthenticated client scripts POSTs that create `CourseApplication` + `FormProgress` + `QuestionAnswer` rows and uploads up to 6 MB per file to object storage, with no account to cost-limit or ban. Also pollutes the reviewer queue with junk applications (reviewer time is the scarcest resource) and may seed the claim step with attacker-chosen content.
- Harms: operator (storage cost, DB growth, reviewer time), legitimate applicants (queue noise), reviewers (hostile file content: no malware scanning, PDFs stored as supplied, see baseline).
- Likelihood: high for form spam once the CTA is public; medium for deliberate storage exhaustion.
- Existing mitigation: the upload gate bounds each file (size, type, bomb) but is per-request; nothing bounds how many. Everything today is bounded by the account-creation cost (signup rate limit 5/min/IP, email verification, honeypot). Removing the login requirement removes all of those from this path.
- Recommended mitigation (design-level):
  - Per-IP creation cap using the `referral_tracking/hits.py` pattern (salted-HMAC key from `get_client_ip`, `cache.add`/`cache.incr`) rather than a new dependency; or `allauth.core.ratelimit` if the team accepts the coupling. Note both are cache-backed and dev may switch them off the same way `ACCOUNT_RATE_LIMITS = False` does; the cap should have its own switch so dev and tests can still exercise it.
  - A cap on concurrent unclaimed drafts per session (and per IP over a window), distinct from the rate: rate stops bursts, a cap stops slow accumulation.
  - Reuse the honeypot pattern on the email-capture step (hidden non-autofill field).
  - The strongest single structural control: defer file upload until after authentication. A visitor can answer text questions anonymously, and the file question says "you will upload after confirming your email". This removes the storage-abuse and hostile-file surface from the unauthenticated path entirely, at a UX cost (the upload page of the form is reordered or the draft is incomplete at claim). If uploads must be allowed anonymously, enforce a smaller per-draft total and count files against the same per-IP/session cap, and have a sweep delete them (T7).
  - Do not rely on a CAPTCHA unless abuse is observed (matches the better-registration stance, V7.2); record it as the escalation path.
  - Unclaimed work should never enter the reviewer queue: an application is "submitted" only after claim (and email verification, T5). The `record_application_submitted` analytics event and any future `app.submit()` transition must not fire for unclaimed drafts, or ad/analytics funnels count bot traffic as applications.

### T2. Email flooding and use of the site as a spam relay

- Threat: the feature asks for an email address, and probably sends something to it (verification code, claim link, "confirm your application"). Anyone can type any address, so the site emails third parties on demand: mailbombing a victim, or harassment/phishing with our domain's reputation (and our sender reputation and email-provider reputation suffer; blocklisting would break real verification emails).
- Harms: arbitrary third-party mailboxes, the operator's sending domain.
- Likelihood: high if any email is sent on the anonymous step; none if the design sends nothing until authentication.
- Existing mitigation: allauth rate-limits its own signup, login-failure, password-reset and confirmation-email actions per IP and per key (allauth rate limit docs, https://docs.allauth.org/en/latest/account/rate_limits.html; the project's own `ACCOUNT_RATE_LIMITS` sets only `signup` and `login_failed`, everything else is at allauth defaults). Those limits cover allauth's views only, not ours. Note the project's comment in `settings_base.py`: a `key`-scoped rate cannot be set on `signup` because the view supplies no key, so per-email limiting must be done by whoever has the key in hand.
- Recommended mitigation: the cleanest compliant design is to send no email at the anonymous step at all. The email address typed on the draft is only a claim label; the mail that does go out is allauth's own signup or login flow at the end (already rate-limited per IP/key, and verification-gated). If the feature does send its own mail (a magic "resume your application" link), it needs, additively: a per-email cap (hashed key) and a per-IP cap, a fixed resend interval, a uniform response regardless of the address (T3), and a ceiling per draft. A one-time code or link sent to the address is a credential and falls under the project's existing "Queued Email" caveat (a stored message holds a live credential if email queueing is on).
- Also: an anonymous POST must not trigger a send to an address already tied to an account differently from a new one (T3).

### T3. Account and email enumeration through the email step

- Threat: the obvious UX is "this email already has an account, log in instead". That tells an attacker which addresses are registered (and, on a multi-site install, registered on this Site). Also a timing and response-shape side channel if the existing-account branch does a different amount of work or a different redirect.
- Harms: registered learners (targeted phishing, credential stuffing prioritisation).
- Likelihood: certain if implemented naively; the attack needs only an unauthenticated request.
- Existing mitigation: `ACCOUNT_PREVENT_ENUMERATION = True` (`settings_base.py:431`); `docs/product/authentication.md` states responses do not distinguish "email not registered" from "password incorrect", and the failed-login "create an account" prompt is identical whatever email was typed. The better-registration threat model flagged V7.3 as "confirm enabled"; it is. allauth's behaviour with it on: signup with an existing address looks like success and the existing owner gets an informational email (allauth docs, https://docs.allauth.org/en/latest/account/configuration.html, `ACCOUNT_PREVENT_ENUMERATION`).
- Requirement and compliant design: the response to an email submission must be identical (same page, same status, same copy, comparable work) whether or not the address belongs to an account on this Site. The visitor must therefore never be told "you already have an account". The way that stays compliant: after email capture, send every visitor to one generic "continue to confirm your application" authentication step (the existing `acquisition_auth_url`/`redirect_to_auth` hand-off with `next` set to the claim URL, which already offers both signup and login). A returning learner who logs in with that email is simply authenticated; a new one signs up. The decision of who they are is made at the point where allauth already handles it uniformly. A signed-in visitor's email is autofilled from their session, which discloses nothing to a different person.
- Corollary for autofill: only prefill from `request.user.email`, never from any other source (cookie, prior draft) that a different person on the same device could read.
- Corollary for "already applied": a visitor who types an email and a course that already has an application for that user must not see "you already applied"; that fact surfaces only after authentication, as `apply` already does (it redirects an existing applicant to their status page).

### T4. Draft exposure: a draft reachable before authentication

- Threat: today the draft URLs (`/applications/<uuid>/pages/<n>`, check-answers, file download) are guarded by `user=request.user`. A pre-auth draft has no user, so the guard must become something else, and any weaker guard exposes answers (which can include a government ID scan) and uploads to whoever holds the URL: shared links, browser history, referrer leakage to third-party analytics tags (GA4/Meta pixels load on pages), prefetch/link scanners (email scanners follow links), shared computers, and screenshots in support tickets.
- Harms: the applicant (PII, ID documents), operator (breach notification under POPIA, see T7).
- Likelihood: medium; becomes high if the guard is "UUID is unguessable".
- Existing mitigation: ownership checks plus `no-store` on check-answers and the attachment downloads. Project doctrine (`own_question_answer_file` docstring): the URL's unguessability is not the control. A UUIDv4 pk is 122 random bits, so guessing is not the practical risk; leakage is.
- Options compared:
  - Session binding: the draft's pk is stored in `request.session` and every draft view requires membership; a URL alone grants nothing. Strongest against URL leakage, matches the doctrine, and the draft cannot be shared. Weakness: lost session cookie means a lost draft (expiry, new device, a private window, or the email-verification click opening in a different browser than the one the draft began in, which is routine for "click the link in your email" on mobile).
  - Signed token in URL (Django `signing`/`TimestampSigner`, https://docs.djangoproject.com/en/stable/topics/signing/): survives a lost cookie, but it is a bearer credential: whoever has the link has the draft, and it leaks via history, referrer and scanners. Acceptable only for a narrow purpose such as a single-use, short-lived claim link, never for reading answers or downloading files.
  - Bare UUID pk with no further check: not acceptable (violates the project's own doctrine).
  - Recommendation: session binding is the access rule for reading/editing a draft and for any file download before claim. The session-lost case is handled by making loss cheap and honest ("your draft expired, start again"), not by a leak-prone fallback. After claim, access reverts to the existing `user=request.user` rule, so the existing views, tests and `Cache-Control` behaviour stay authoritative.
- Specifics:
  - Uploads and downloads before claim: serve only through a view that checks the session binding on every request, with the same `private, no-store` headers; never a storage URL. If uploads are deferred (T1) this vanishes. Never expose answers or files to any other unauthenticated route.
  - Cache and referrer: apply `Cache-Control: no-store` to every anonymous draft page (today only check-answers has it; form pages and the draft entry point do not), and `Referrer-Policy: same-origin` or `no-referrer` for those pages so a draft URL does not travel to the analytics hosts the pages load. Do not put a draft id in any analytics event payload (the project says analytics receive no identifiers).
  - The 404-not-403 convention: a wrong or foreign draft id returns 404, identical to a nonexistent one, matching the existing views.
  - Prefetch: draft-advancing steps must be POST (state change is POST-only), so link scanners cannot advance or claim a draft by GET.
  - Session-lost case: the draft is orphaned until deleted by retention (T7); no recovery path that bypasses binding.

### T5. Claim hijacking: binding a draft to the wrong account

- Threat A (victim's address on attacker's draft): attacker starts a draft typing victim@example.com. If claim rules are "whoever signs up or logs in with that email gets the draft", the victim later signs up and finds an application they did not write, containing attacker-chosen answers/files, possibly already visible to reviewers as the victim's own submission (impersonation; the victim could be treated as having applied, or have attacker's uploaded content attached to their account).
- Threat B (attacker claims victim's draft): attacker learns a draft id or claim token (T4) and logs into their own account to claim someone else's answers and ID scan, or races the legitimate applicant to the claim.
- Threat C (account takeover by pre-registration): attacker typed the draft email and uses the claim step to create an account for the victim's address before they do. allauth's mandatory email verification (`ACCOUNT_EMAIL_VERIFICATION = "mandatory"`, login blocked until the link is followed) is what makes this safe only if claim is gated on it.
- Harms: the victim, the integrity of the review queue, the applicant.
- Likelihood: B and A low-medium (needs a leak or a deliberate target); C low.
- Existing mitigation: none for the draft concept. For identity, allauth's mandatory verification and the project's `LegalConsent` at signup cover the account side.
- Required rule (what must be true for a claim to succeed), all three together:
  1. The claimant is authenticated as a `User` on this Site.
  2. The claimant holds the draft: its id is in their own session (the same session that created it, which survives login, see T8), or they present a valid signed single-use claim token that was minted for that draft.
  3. The claimant's verified email equals the draft's typed email (case-normalised the way `User` stores addresses). Verified means allauth has marked the address verified, not merely typed at signup. If the account's verified email differs from the typed one, no claim: the draft stays unclaimed or the visitor is asked to continue as a new application, but never silently attached.
- With rule 3, Threat A's victim signing up later cannot be given the attacker's draft, because the attacker's draft is bound to the attacker's session: the victim (a different browser/session) fails rule 2. This is the key reason session binding beats email matching as the primary join key; the typed email is a consistency check, not the authority. An unbound draft that only matches by email must never be claimable.
- Ordering with verification: claim happens after the account is verified and logged in (after allauth's `ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION = True` log-in), not at signup POST time. With mandatory verification the signup POST does not log the user in; the verification click may happen in another browser (T4). Consequences: the claim step must be reachable from the post-verification landing, and must tolerate that the session holding the draft is gone; in that case the claim does not happen (rule 2) and the learner is told to start again, rather than falling back to email-only matching.
- A claim is single-use and atomic: a draft transitions unclaimed to claimed once, under a lock/atomic update, so two racing requests cannot both claim, and a claimed draft is never re-claimable. Failed or mismatched claims return the same response as "no draft here" (no oracle for which drafts exist).
- Existing-application collision: the claimant may already have an application for that course (the unique constraint on user+course, `get_or_create` in `_start_application`). The claim must not overwrite or merge into it silently; the existing application wins (consistent with `apply` redirecting an existing applicant to status) and the draft is discarded or left to retention.
- The claim must not elevate anything: it attaches answers and files only; it grants no registration, no `LegalConsent` (T7), and does not skip the `RegistrationCompletionMiddleware` additional-registration-forms step.

### T6. Hidden and coming-soon courses

- Threat: an anonymous draft flow that looks up the course by slug and then branches ("this course exists, here is the form" vs 404) lets an anonymous visitor probe slugs and discover HIDDEN courses (this is exactly what `raise_404_if_hidden_unregistered` and the `course_interest` docstring guard against). Related: a COMING_SOON course must not become applyable by an anonymous visitor either.
- Harms: operator (unreleased or private programmes disclosed), also an information leak about a hiring/programme pipeline.
- Likelihood: medium; slug guessing is trivial, and the existing code shows the project has already treated this as a real concern.
- Existing mitigation: authenticated `apply` calls `raise_404_if_hidden_unregistered` before anything else, then existing-application redirect, then COMING_SOON redirect. `course_interest` handles the anonymous case by redirecting to auth identically for any slug before the course lookup (its docstring says so explicitly).
- Recommended: the anonymous apply entry point must apply the same ordering, hidden check first with an anonymous user (the helper already accepts `RequestUser`, so a HIDDEN course 404s for every anonymous visitor, identical to a nonexistent slug), COMING_SOON redirects to the detail page's express-interest CTA, and nothing is created until both pass. No differing status, redirect target or timing between "no such slug" and "hidden". The claim step must repeat the check: a course flipped to HIDDEN or COMING_SOON between draft creation and claim must not be turned into an application (the existing comment in `apply` makes an exception only for an applicant who already has an application record; a draft is not one, so it gets no such exemption). Registered learners of a hidden course are irrelevant to anonymous visitors; do not create a path that registers an unregistered visitor via claim.

### T7. PII and retention of unclaimed drafts

- Threat: an unclaimed draft holds an email address and free-text answers, potentially an ID scan, for a person who has not created an account, has not accepted terms or privacy (`LegalConsent` is only written at signup, with doc version, git hash and IP), and may be a third party whose address was typed by someone else (T5A). Today none of this exists in the database before an account does. The repo also has no retention or deletion tooling at all (`security-and-data-handling.md`: "Retention, Deletion, and Data-Subject Rights (not yet built)"; application answers and uploads are explicitly listed as having no retention policy, and `housekeeping.py` has no sweep for them). Unclaimed drafts would be the first data in FLS that is held with no account that could ever be deleted to cascade-remove it (account deletion currently removes answers and files through the CASCADE from `User`).
- Harms: data subjects (privacy), operator (POPIA/GDPR exposure, storage), applicants who never intended to proceed.
- Likelihood: certain, this is by-design retention of abandoned drafts; the legal risk depends on retention length and notice.
- Existing mitigation: private no-store file serving, EXIF stripping, cascade delete on user removal. Nothing for unclaimed or abandoned data.
- Recommended:
  - A hard expiry for unclaimed drafts, short (days, not months; tie it to something the visitor can understand, e.g. the session lifetime of 2 weeks at most) and a housekeeping sweep in `deployment/housekeeping.py` in the existing style (a separate try/except step, its own count in `notes`) that deletes expired unclaimed drafts including their stored objects (the `QuestionAnswerFile` post_delete receiver already removes the stored object when the row is deleted, so the sweep must delete via the ORM, not `queryset._raw_delete`). Housekeeping uses `_base_manager` for cross-site work (see `find_orphaned_running_reports`), so the same applies to sweeping site-aware rows. The existing `clearsessions` step shows the project already accepts a scheduled sweep run by the downstream deployment's cron.
  - Collect the minimum before authentication: email and the answers the form needs; consider delaying free-text and especially ID-document questions until after authentication.
  - Notice: at the email field, a short plain statement that the address and answers are held for N days to let them finish and are used for nothing else, linking the site's privacy document (the legal-doc view exists). Do not record this as `LegalConsent`: that model is the append-only evidence of acceptance by a user at signup and must not be written for an anonymous visitor (V4.2 in the better-registration model: limit the code paths that create `LegalConsent`). Acceptance of terms and privacy (when `REQUIRE_TERMS_ACCEPTANCE`/the Site's `SiteSignupPolicy` demands it) stays at the authentication step, i.e. before claim; the claim must not complete without passing the same signup-policy gates a normal signup does.
  - Lawful basis: the operator is the controller (the signup-attribution doc says the same). For an anonymous visitor who typed their own address to start an application, the realistic bases are steps taken at the data subject's request prior to entering a contract (GDPR Art. 6(1)(b), https://gdpr-info.eu/art-6-gdpr/) or legitimate interests (Art. 6(1)(f)) with a balancing test; consent (6(1)(a)) is the weaker basis because it would need to be recorded and withdrawable. POPIA's equivalent (s11) allows processing necessary to carry out actions for the data subject, https://popia.co.za/section-11-consent-justification-and-objection/ (cited from POPIA section index; operator should confirm with counsel). A third-party-typed address (T5A) has no valid basis for the data about that person beyond their address, which is a reason for short retention and for not using the typed address for anything but the claim match. This is a statement for the operator's own privacy assessment, not something FLS can decide; document it the way `signup-attribution.md` does ("starting point, not a finished assessment").
  - Do not copy the anonymous draft's email into any marketing, analytics or webhook payload. The `user.registered` webhook fires only on account creation; an unclaimed draft must not fire any webhook, and the draft email must not enter GA4/Meta events (the project guarantees no identifiers reach them).
  - Right-to-erasure: with no account there is nothing for the data subject to log in to delete. Without tooling, an operator can delete by email through the admin; flag as a documented gap, not a built feature, consistent with how the docs already describe it.
  - Add the new data class to `docs/product/security-and-data-handling.md` "Personal Data Collected" (a doc change for whoever implements; not a built control).

### T8. CSRF, anonymous sessions, session fixation, and keeping the draft across login

- Threat: (a) anonymous sessions are created on first draft write, creating rows in the session table that bots can inflate; (b) session fixation: an attacker plants a known session id in the victim's browser, the victim authenticates, the attacker rides it; (c) the draft reference is lost at login because the session is replaced; (d) CSRF on anonymous POSTs.
- Existing mitigation and confirmed behaviour:
  - Django `login()` handles fixation: when there is no existing authenticated user in the session it calls `request.session.cycle_key()`, which issues a new session key but keeps the session data (https://docs.djangoproject.com/en/stable/topics/http/sessions/#django.contrib.sessions.backends.base.SessionBase.cycle_key, and the `login()` docs, https://docs.djangoproject.com/en/stable/topics/auth/default/#django.contrib.auth.login: "In case no session key... Session data set before login is maintained"). If a different user is already authenticated in that session, `login()` flushes it instead, so data would be dropped in that edge case (e.g. a shared computer where another account is still signed in): treat "draft survives login" as true for the anonymous-to-user transition only, and have the claim handle the missing-draft case gracefully. allauth uses Django's `login()`; its stashed-login flow (login blocked pending email verification) also keeps the session until the user completes it, but the verification can complete in another browser (T4/T5), where the session, and so the draft, is absent.
  - The session cookie flags in production (Secure, HttpOnly, Lax) mitigate theft; `SameSite=Lax` still sends the cookie on top-level GET navigations, so the claim redirect after login (same-site) keeps the session; a cross-site link into the draft would not carry POST cookies, which is fine.
  - CSRF: the whole site uses Django's CSRF middleware and the HTMX header on `<body>`; the anonymous email-capture POST gets a CSRF token like any anonymous form (login and signup already are). The anonymous draft endpoints must not be `csrf_exempt`. An attacker cannot make a victim's browser create a draft meaningfully with CSRF (it would be created in the victim's session, which is the T1/T4 concern, not data theft), but exemption would remove the origin check for bot throttling.
  - Session-table inflation: creating a session per anonymous visit is the real cost. Only create a session (write to `request.session`) when the visitor actually submits the email step or first answer, never on a GET of the entry page; a GET that just renders the form should not call anything that saves the session. `clearsessions` in housekeeping already purges expired rows, so inflation is bounded by `SESSION_COOKIE_AGE` (2 weeks) rather than forever, and per-IP creation caps (T1) bound the rate.
- Recommended: store only the draft reference (primary key) in the session under one namespaced key (like `CACHE_SESSION_KEY` for the registration-completion middleware), never answers or the email beyond what is needed; read it after login and clear it on claim; handle "session key present but draft gone/claimed/expired" as the normal "start again" path with the same response as no draft.

### T9. Open redirect through `next` to the claim URL

- Threat: the hand-off to authentication carries `next` pointing at the claim URL; a tampered `next` could send the freshly authenticated visitor off-site (phishing after a trusted login) or to a URL that claims someone else's draft.
- Existing mitigation: `accounts/views.py::_safe_post_completion_redirect` validates with `url_has_allowed_host_and_scheme(next_url, allowed_hosts={request.get_host()}, require_https=request.is_secure())` and falls back to `LOGIN_REDIRECT_URL`; `authentication.md` says every preserved destination is a same-host path validated before use, including through the additional-form steps (Django docs, https://docs.djangoproject.com/en/stable/ref/utils/#django.utils.http.url_has_allowed_host_and_scheme; OWASP, https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html).
- Recommended: build `next` server-side from `reverse()` for the claim URL (never echo a client-supplied URL), pass it through the same validated hand-off the project already uses (`redirect_to_auth`/`acquisition_auth_url`), and make the claim URL carry no authority of its own: it names no draft; the draft is found from the session (T4/T5), so a tampered or shared claim URL cannot move another person's draft. A claim URL that carries a signed token must additionally be single-use and short-lived.

## 3. Cross-cutting findings

- Ownership, not unguessability, is the project's control for everything applicant-submitted. The feature's central design question is what replaces `user=request.user` before there is a user. The research answer is session binding (T4), with the typed email as a consistency check and verified email as the claim gate (T5); signed tokens are not a read credential.
- Every anonymous path must have a response indistinguishable from "nothing here": enumeration (T3), hidden courses (T6), foreign/expired drafts (T4/T5), failed claims (T5). This is the project's existing stance (404 for non-owners, uniform redirect for course interest, `ACCOUNT_PREVENT_ENUMERATION`).
- The feature removes the cost of an account from abuse, so the controls that were implicit (signup rate limit, verification, honeypot) must be re-created at the draft creation point: per-IP rate, per-session draft cap, honeypot, short expiry. Deferred upload is the most effective single reduction in attack surface.
- Nothing about the unclaimed state may behave like a submitted application: no reviewer queue entry, no analytics `application_submitted` event, no webhook, no notification, no `LegalConsent`.
- Dev and tests: allauth rate limits are off in dev (`ACCOUNT_RATE_LIMITS = False`); a new cap must have its own setting so it is testable and not silently disabled in dev with no test coverage, mirroring `tests/test_signup_rate_limit.py` which overrides `ACCOUNT_RATE_LIMITS` to prove the limit fires.
- Gaps this feature inherits and does not close (state as accepted or future work, as the project's docs do): no malware scanning of PDFs, no retention tooling for applications, no data-subject-rights tooling, no audit log of downloads, no CAPTCHA.

## 4. Open questions for the spec to settle

1. Does the anonymous step send any email of its own, or only hand off to allauth signup/login at the end? (Decides most of T2.)
2. Are file questions answerable before authentication, or deferred to after claim? (Decides most of T1/T4/T7.)
3. How long is an unclaimed draft kept, and who runs the sweep (housekeeping step in `deployment/housekeeping.py`, scheduled by the downstream deployment)?
4. When the verification email is followed in another browser and the session draft is gone, is the visitor told to start again (recommended) or is there a signed single-use resume link (adds a bearer credential)?
5. What does the claim do if the claimant already has an application for the course (existing application wins is the recommendation)?
6. How is an application without a `User` represented (nullable FK vs a separate pre-claim model)? Out of scope here, but both `CourseApplication.user` and `FormProgress.user` are non-null with CASCADE today and the choice changes every retention and site-isolation answer above.
