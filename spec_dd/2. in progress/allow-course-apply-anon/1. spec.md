# Spec: allow anonymous course applications

Idea: `idea.md` in this directory. Research: the five `research_*.md` files beside it.

## 1. Purpose

A visitor who clicks "Apply now" on an application-gated course is sent to signup before they see a
single question, and some never come back. After this work the application form is the first thing
they see. The account is created at the end, and the application is attached to it on their first
verified login in that browser.

## 2. Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| unclaimed | coined | A `CourseApplication` whose `user` is null. Its sitting (`FormProgress`) has a null `user` too. No existing term: today every application has an owner. |
| claim | coined | The single transition that sets `user` on an unclaimed application and on its sitting. Runs once, atomically, under the rule in §5.6. |
| handoff | coined | The `redirect_to_auth` call that follows an anonymous submit: to the signup page with the typed email prefilled and `next` set to the claim landing page. No existing term: `redirect_to_auth` names the helper, not this use of it. |

"Sitting" is the glossary's word for a `FormProgress` and is used as such throughout.

## 3. Scope

In:

- An anonymous visitor on a site that is open for signups can start, fill in, upload to and submit
  an application without an account, for both form courses and no-form courses.
- The email address is typed at submit, on the check-your-answers page or the no-form confirmation
  page, with a plain privacy statement beside it.
- The browser session is the credential for every unclaimed-application page and file.
- The handoff to signup, and a claim that runs from a `user_logged_in` receiver and from a landing
  page.
- A signed-in applicant's pages show the account email read-only; their flow is otherwise unchanged.
- Admin: unclaimed applications are listed under their email, marked unclaimed, and can be deleted
  together with their sitting and files.
- Per-IP caps on creating unclaimed applications and on anonymous uploads, a honeypot on the email
  form, and `no-store` plus a same-origin referrer policy on every unclaimed-application response.
- Product documentation and the upload-key rule in the file-storage skill.

Out (from `idea.md`, "Not in scope"): resuming from another browser or device, any emailed resume
or claim link, login by code, a "Continue your application" label on the course page, any webhook
or notification for an unclaimed application, a CAPTCHA, and an expiry job. Also out: a per-draft
ceiling on file count or size (§8), and changes to the application review state machine.

## 4. Decisions

- **Submission precedes authentication.** The application reaches the admin the moment the
  anonymous visitor submits; the analytics submission event fires there, as today (`idea.md`).
- **Entry without rows.** "Apply now" stays a GET link. For an anonymous visitor the apply URL
  renders page 1 of the form with no rows; the first page-1 POST creates the application and
  sitting, and a POST that fails validation creates nothing. The no-form flow (GET confirmation,
  POST creates) is already on this rule.
- **The session holds lists, not single ids.** One browser can hold drafts for several courses.
- **Two session keys, one per app.** `form_engine` cannot import `course_applications`
  (`docs/app_structure.md`), so `form_engine` owns the sitting ids its file views check and
  `course_applications` owns the application ids the claim reads. Both are written where the
  sitting is created and cleared together at claim.
- **An unsubmitted draft is claimed on session possession alone.** It has no email, so the
  verified-email rule cannot apply; the session is the credential that created it. A submitted
  unclaimed application needs the verified-email match as well.
- **Storage keys are keyed by sitting for every new upload**, signed in or not:
  `user_uploads/form_answers/{form_progress_pk}/{file_pk}{ext}`. Nothing moves at claim, and
  erasure finds files through rows. Existing objects stay where they are. This replaces the
  "prefixed by the uploading user" rule in the file-storage skill (§7).
- **The per-IP cap fails closed on an unknown client IP and open on a cache error.** Creating rows
  and files is where abuse costs us, so a `PermissionDenied` from `get_client_ip` propagates (403), as
  signup's consent capture already does. A cache backend error reports to Sentry and lets the
  request through, as `referral_tracking/hits.py` does.
- **Mismatch leaves the application in the session.** The claim retries on every later login, so
  verifying the typed address on this account and logging in again attaches it. No "use this account
  instead" path: that would make the typed email meaningless.
- **Admin delete is per object only.** The bulk `delete_selected` action stays unavailable, so a
  mixed selection can never remove a claimed application.
- **The honeypot keeps the signup honeypot's warning log.** The extracted mixin carries its
  existing behaviour; no new log line is added.

### 5.2 Session possession

New `freedom_ls/form_engine/anonymous_sittings.py`:

```python
ANONYMOUS_SITTINGS_SESSION_KEY = "form_engine_anonymous_sitting_ids"

def remember_anonymous_sitting(request: HttpRequest, form_progress: FormProgress) -> None: ...
def forget_anonymous_sitting(request: HttpRequest, form_progress_pk: str) -> None: ...
def request_holds_sitting(request: HttpRequest, form_progress_pk: str) -> bool: ...
def sitting_for_request(request: HttpRequest, progress_pk: str) -> FormProgress:
    """The sitting this request may read and write, or Http404.

    The requester's own sitting (user=request.user), or an unowned sitting
    whose id is in the session. Nothing else. A signed-in user still reaches
    a session-held unowned sitting, which is the mismatch case in §5.6.
    """
```

New `freedom_ls/course_applications/claims.py`:

```python
UNCLAIMED_APPLICATIONS_SESSION_KEY = "course_applications_unclaimed_ids"
CLAIM_REPORT_SESSION_KEY = "course_applications_claim_report"

def remember_unclaimed_application(request: HttpRequest, application: CourseApplication) -> None: ...
def unclaimed_application_ids(request: HttpRequest) -> list[str]: ...
def unclaimed_application_for_course(request: HttpRequest, course: Course) -> CourseApplication | None: ...
def claim_unclaimed_applications(request: HttpRequest, user: User) -> ClaimReport: ...
```

Rules for both modules: ids are stored as `str(pk)` (the session serialiser is JSON); every write
reassigns the list rather than mutating it in place; an anonymous GET never writes to the session;
a foreign, wrong, claimed or missing id answers 404 exactly like a missing one.
`remember_anonymous_sitting` and `remember_unclaimed_application` are called together wherever a
sitting is created (§5.3).

### 5.3 The apply entry (`freedom_ls/course_applications/views.py`)

`apply` loses `@acquisition_login_required`. Its order becomes:

1. Anonymous visitor and `acquisition_auth_url(request)` is `None` (signups closed):
   `redirect_to_auth(request, next_url=request.get_full_path())`, before any course lookup, exactly
   today's closed-site behaviour.
2. `get_object_or_404(Course, slug=...)`, then `raise_404_if_hidden_unregistered(request.user,
   course)`. The helper already accepts `AnonymousUser`; a hidden slug now 404s for an anonymous
   visitor on an open site.
3. Signed in: unchanged (existing application short-circuit, coming-soon redirect, start). The
   `_start_application` call sets `email=user.email`.
4. Anonymous with an unclaimed application for this course in the session
   (`unclaimed_application_for_course`): submitted, so redirect to the handoff (§5.5); unsubmitted,
   so redirect to `_resume_url`.
5. Coming soon: redirect to the course detail page, as today.
6. Form course, GET: render page 1 with no rows. `page_context` in `form_engine/page_flow.py`
   accepts `form_progress=None` and renders no answers, page links with only page 1 reachable, and
   the file-upload widget replaced by the sentence "Save this page to attach a file." The form posts
   to the apply URL. A form with no pages has no page 1 to render, so the anonymous GET is 404 (§8).
7. Form course, POST: the per-IP cap (§5.8), then inside `transaction.atomic()` create the
   application (`user=None`, `email=""`) and its sitting (`user=None`) and run `submit_page` on
   page 1. The required-answer check on this first save ignores file questions, because a file is
   measured against its stored row and no row could have existed yet. On any other validation
   error, `transaction.set_rollback(True)` and re-render the row-less page with the errors at 422.
   On success, `remember_anonymous_sitting` and `remember_unclaimed_application`, then redirect to
   page 1 of the new draft when page 1 holds a file question (with an info callout "Your answers are
   saved. You can now attach your file."; the usual required check applies from that save on),
   otherwise to wherever `submit_page` sends a signed-in applicant.
8. No-form course, GET: render `apply.html`. Anonymous: with the email form (§5.5). Signed in: with
   the read-only email line.
9. No-form course, POST: anonymous: the cap, the email form (honeypot, email), then create the
   application with `email` set, `record_application_submitted`, `remember_unclaimed_application`,
   handoff. Signed in: as today, plus `email=user.email`.

`_start_application` never calls `get_or_create(user=None, ...)`, because with a null user that
matches a stranger's draft.

`_owned_application_with_form` becomes `_application_for_request(request, pk)`: the requester's own
application (`user=request.user`), or an unclaimed one whose id is in the session; 404 otherwise.
`application_form_page` and `application_check_answers` lose `@login_required` and use it.
`application_status` keeps `@login_required` and the `user=request.user` lookup.

### 5.4 Files on an unclaimed sitting (`freedom_ls/form_engine/views.py`)

`partial_question_file_upload`, `partial_question_file_remove` and `own_question_answer_file` lose
`@login_required`. `_owned_file_question` resolves the sitting through `sitting_for_request`;
`own_question_answer_file` looks up `answer__form_progress` through the same rule. The anonymous
upload path checks the upload cap (§5.8) before reading the file; when it fires, the widget renders
its error state over whatever is attached ("Too many uploads from your network. Try again in a few
minutes.") at 422, through the same path a refused upload uses. 422 rather than 429 because it is
the only error status the site's `htmx:beforeSwap` rule (`base/static/base/js/alpine-components.js`)
swaps into the widget. `question_answer_file_download_view` (staff) and
`stream_question_answer_file` are unchanged. The module and `own_question_answer_file` docstrings
state the new rule: ownership or session possession is the whole control, never the URL.

### 5.5 Submit, email and handoff

New `freedom_ls/course_applications/forms.py`, `ApplicantEmailForm(HoneypotFormMixin, forms.Form)`
with one `email = forms.EmailField()`. Its clean strips and lowercases the address, as allauth's

`HoneypotFormMixin` is extracted from `SiteAwareSignupForm` in `freedom_ls/accounts/forms.py`:
`HoneypotInput`, the `fax_number` field, the `clean()` check, `_log_honeypot_trip` with a context

Check-your-answers page (`check_your_answers.html`, `application_check_answers`):

- Anonymous: below the answers and above "Submit application", the email field with the label
  "Where should we send your decision?" and this statement: "We use this address to link your
  application to your account and to send your decision. An application that is never linked to an
  account is kept until an administrator removes it." followed by a link to the site's privacy
  document when `has_legal_doc(site, "privacy")` is true. No `LegalConsent` is written.
- Anonymous POST: the whole-form check first (422 as today), then the email form (422 with its
  errors), then in one transaction `form_progress.complete()`, `application.email = ...` and
  `save`; then `record_application_submitted` and the handoff.
- Signed in: a plain line "Your decision will be sent to {{ request.user.email }}." in the page's
  own style, no component. POST unchanged.
- The page keeps `Cache-Control: no-store` (§5.8 adds the referrer policy).

`apply.html` (no-form confirmation) gets the same field, statement and read-only line.

The handoff: `messages.success(request, "Your application for {course} has been sent. Create an
account or log in with {email} to see its progress.")`, then
`redirect_to_auth(request, next_url=reverse("course_applications:claim"), auth_url=...)` where
`auth_url` is `acquisition_auth_url(request)` with `?email=<typed email>` appended (`urlencode`)
when it is the signup page. If signups closed after the draft began it is `None`, so the visitor
goes to login. `redirect_to_login` keeps that query string when it adds `next`. The signup page's
existing "Log in" switch carries `next`. The signup page extends `_base.html` through
`allauth/layouts/base.html`, so the message renders there. The site never says whether the address
has an account. No account lookup runs on the submit path, and the response is identical for a
registered and an unregistered address. No email is sent from the anonymous step; the only mail is
allauth's own signup and verification mail.

After the handoff, a visitor who returns to the course page in the same browser and clicks "Apply
now" is sent back to the handoff (§5.3 step 4).

### 5.6 Claim

`claim_unclaimed_applications(request, user)` in `claims.py`, one `transaction.atomic()` per id in
`unclaimed_application_ids(request)`:

1. Lock the row: `CourseApplication.objects.select_for_update(of=("self",)).filter(pk=pk)`
   (site-scoped by the manager). Missing, or claimed by another user: drop the id from the session
   and record nothing. Already claimed by this user: drop the id and record `claimed` (idempotent).
2. Hidden course: `course.visibility == HIDDEN` and the user is not registered: drop the id, do not
   claim.
3. Collision: `CourseApplication.objects.filter(user=user, course=application.course).exists()`:
   drop the id, record the existing application as `collided`. An `IntegrityError` from step 4,
   caught inside a nested `transaction.atomic()` savepoint, is the same outcome.
4. Unsubmitted draft (`email == ""`): set `user` on the application and its sitting, set
   `email=user.email`, drop the id, record `claimed`.
5. Submitted (`email` set): requires `EmailAddress.objects.filter(user=user, verified=True,
   email__iexact=application.email).exists()`. Match: as step 4. Mismatch: keep the id, record
   `mismatched`.
6. Drop the sitting id from `form_engine`'s key for every claimed or dropped application.

It returns `ClaimReport` (a frozen dataclass: `claimed`, `collided`, `mismatched` as lists of
application pks) and stores it under `CLAIM_REPORT_SESSION_KEY`, merged into any report already
there, so the landing page sees what the receiver did. With no ids in the session it returns an
empty report and writes nothing.

Receiver: new `freedom_ls/course_applications/signals.py`, `claim_on_login(sender, request, user,
**kwargs)` on `django.contrib.auth.signals.user_logged_in`, connected from
`CourseApplicationsConfig.ready()` (the "No signals yet" comment there is updated). It calls the
function and catches `DatabaseError`, reporting to Sentry and leaving the application unclaimed. A
login must never fail because of a claim. The receiver no-ops when the session holds no ids.

Landing page: URL `applications/claim/`, name `course_applications:claim`, view `claim_landing`,
`@login_required`, GET only. It calls the claim function once more (covering a login that fired
before the id was in the session, and the mismatch retry), pops the merged report, and responds:

- one claimed, submitted: redirect to its status page with the message "Your application for
  {course} is now on your dashboard."
- one claimed, unsubmitted: redirect to `_resume_url` for it.
- several claimed: redirect to the dashboard with the same message per course.
- collision only: redirect to the existing application's status page with "You had already applied
  to {course}. This is your application."
- mismatch: render `course_applications/claim_mismatch.html`: a `<c-callout level="warning">`
  saying this account's email differs from the one on the application ({email}), with links to the
  account email page (`account_email`) to add and verify it, and to the course page. "Log in again
  once it is verified and the application will be linked."
- nothing: redirect to the dashboard with "We couldn't find an application in this browser."
- When outcomes mix, the mismatch page wins; the other outcomes' messages still show as toasts on
  it.

Claim never runs from `user_signed_up`, `pre_login` or `save_user`.

### 5.8 Abuse controls and headers

New `freedom_ls/accounts/throttling.py`:

```python
def is_ip_throttled(
    request: HttpRequest, *, namespace: str, scope: str, limit: int, window_seconds: int
) -> bool:
    """Fixed-window per-IP counter: salted_hmac(namespace, ip) key, cache.add then incr.

    limit or window <= 0 disables. PermissionDenied from get_client_ip propagates.
    Any cache backend error reports to Sentry and returns False.
    """
```

`referral_tracking/hits.py` calls it (catching `PermissionDenied` itself, keeping its fail-open
behaviour and its tests). The key never contains the raw address.

Settings, declared per the `AppSettings` pattern:

- New `freedom_ls/course_applications/config.py`: `COURSE_APPLICATIONS_ANONYMOUS_START_LIMIT`
  (default 10) and `COURSE_APPLICATIONS_ANONYMOUS_START_WINDOW_SECONDS` (default 3600). Counted on
  every anonymous POST that creates an application. When it fires: the existing `429.html` at
  status 429 with `Retry-After`.
- New `freedom_ls/form_engine/config.py`: `FORM_ENGINE_ANONYMOUS_UPLOAD_LIMIT` (default 30) and
  `FORM_ENGINE_ANONYMOUS_UPLOAD_WINDOW_SECONDS` (default 3600). Counted on every anonymous upload
  POST. When it fires: §5.4.

Neither cap counts signed-in requests or GETs. Both are on by default in dev and test; `<= 0`
disables. Tests that drive a cap clear the cache around each test, as
`referral_tracking/tests/conftest.py` does, so counters never leak between tests.

New decorator `never_cache_same_origin` in `freedom_ls/accounts/decorators.py`: `never_cache`
plus `Referrer-Policy: same-origin`. Applied to `apply`, `application_form_page`,
`application_check_answers`, `claim_landing`, `partial_question_file_upload`,
`partial_question_file_remove` and `own_question_answer_file`. The per-view header wins over
`SECURE_REFERRER_POLICY` because `SecurityMiddleware` uses `setdefault`.

Anonymous POSTs are never `csrf_exempt`. No draft id or email enters an analytics event or webhook.

## 8. Open questions

Defaults taken; overrule by editing this file.

- Cap defaults: 10 application starts and 30 uploads per IP per hour.
- No per-draft ceiling on file count or total size; the upload cap and the 6 MB gate are the
  controls. Add one if abuse is observed.
- A page-1 file question costs one extra return to page 1 after the first save (§5.3 step 7). The
  alternative is a POST "Apply now" button on the course page, which creates the rows on the click.
- An application form with no pages gives the anonymous apply URL a 404 (§5.3 step 6); the
  signed-in path still lands on check-your-answers. It is an authoring error, not worth a flow of its own.
- The upload cap answers 422 in the widget (§5.4), and the start cap reuses the site's `429.html`
  rather than carrying its own copy (§5.8).
- A signed-in user whose session holds an unclaimed application (the mismatch case) can still read
  its pages and files until it is claimed (§5.2, §5.3).
- The 404 for a wrong, foreign or expired id is the stock 404 page, not a "start again" page.
- The claim requires a verified `EmailAddress` even on a site whose `ACCOUNT_EMAIL_VERIFICATION`
  is not `mandatory`; the documentation says so.
- The signup page's "Log in" switch does not carry the typed email; a returning applicant retypes it.
- `qa_reset_course_application` is not extended; QA removes unclaimed rows through the admin.
- The handoff URL carries the typed email as a query parameter, so it appears in the browser history
  and server logs of the visitor who typed it. Accepted.

## 9. Success criteria

- An anonymous visitor on an open site clicks "Apply now" and sees page 1 of the form; no
  `CourseApplication` or `FormProgress` row exists until their first POST.
- The same visitor can complete every page, attach and download a file, submit with an email, and
  is redirected to signup with that email prefilled and `next` set to the claim landing page.
- After signup and verification in the same browser they land on the application's status page, the
  application and sitting have `user` set, and the dashboard panel lists it.
- Logging in with an account whose verified email differs leaves `user` null, shows the mismatch
  page, and a later login with the address verified claims it.
- A second browser that signs up with the typed email never receives the application.
- A request for an unclaimed application page or file without its id in the session is 404.
- The admin lists an unclaimed application under its typed email, marked not claimed, and deleting
  it removes its sitting and stored files; a claimed application still cannot be deleted.
- The full test suite passes.
