# Spec: claude-plugin-tidy-up

## Purpose

Seven project skills sit in `.claude/skills/`, outside the plugin structure the rest of the
Claude-facing content follows. Downstream projects can't install them, and the generic ones are
mixed in with FLS-only ones. Separately, much of the Claude-facing markdown in `claude_plugins/` is
wordier than it needs to be, and every extra word costs context on every load.

This work moves each skill into the plugin it belongs to, then tightens all in-scope Claude-facing
content with the `writing-for-agents` skill without changing what any of it makes an agent do.

## Scope

In:

- A new generic plugin, `claude_plugins/productivity` (manifest name `productivity`), holding
  `answer`, `unslop` and `writing-for-agents`, with its own `/productivity:init`.
- `domain-glossary` and `notifications` move to `fls-dev`.
- `code-comments` moves to `ds`, made generic. Its planning-document rules move to `sdd`.
- Every reference to a moved skill is re-pointed.
- A tightening pass over every `.md` file in `claude_plugins/sdd`, `claude_plugins/django-stack`,
  `claude_plugins/fls-dev`, `claude_plugins/fls-content`, `claude_plugins/productivity` and
  `.claude/skills/brand-guidelines/`.

Out:

- Tightening `CLAUDE.md`, `.claude/*/config.md`, `claude_plugins/turn-progress`,
  `.claude/agent-memory/` and anything under `spec_dd/`. Part 1 still edits the lines in these
  that name a moved skill.
- Re-pointing skill references in `spec_dd/3. done/` (history) and in other specs under
  `spec_dd/2. in progress/` (owned by their own worktrees).
- A marketplace manifest, alias commands for the old bare names, and plugin eval suites.

## Decisions

- **One spec, batched.** The moves land first and are validated on their own; the tightening pass
  follows plugin by plugin. A regression in a tightened file can then never be confused with a
  broken move.
- **`productivity` is generic.** The `CLAUDE.md` Plugins rule names only `ds` and `sdd`; this spec
  extends it to `productivity`, and `CLAUDE.md` is updated to say so.
- **`sdd` hard-depends on `productivity`.** It names `productivity:unslop` directly; its README and
  init say `productivity` must be loaded alongside it. `ds` still depends on no other plugin.
- **`code-comments` splits.** General comment style is `ds:code-comments`. The rules about
  planning-document references leaking into code are an SDD concern and go to `sdd`. No `fls-dev`
  overlay: once the examples are neutralised nothing FLS-specific is left.
- **Tightening is verified by per-file review, with no word target.** Each rewritten file is compared
  against its original for dropped instructions. Word counts are reported, never budgeted.
- **Files the in-progress spec `test-organisation-and-hygene-2-sdd-review-and-boy-scout` edits are
  tightened last**, so that spec likely lands first. They are
  `claude_plugins/sdd/commands/implement_plan.md`, `claude_plugins/sdd/commands/plan_from_spec.md`
  and `claude_plugins/sdd/commands/protected/pre_step_rebase.md`.
- **Skill directory names don't change on the move.** Only the namespace prefix does.

## Requirements

### R1. The `productivity` plugin

- `claude_plugins/productivity/.claude-plugin/plugin.json`: `name: productivity`,
  `version: 1.0.0`, a one-line description naming its three skills.
- `git mv` `.claude/skills/{answer,unslop,writing-for-agents}` to
  `claude_plugins/productivity/skills/`, sibling files included (`writing-for-agents/SKILL-MECHANICS.md`).
  Frontmatter is unchanged by the move. In particular `answer` keeps
  `disable-model-invocation: true` and `argument-hint`.
- `claude_plugins/productivity/README.md` in the shape the other plugin READMEs use: purpose,
  manifest name and namespace (`/productivity:*`, `Skill(productivity:*)`), a table of the three
  skills with how each is invoked (`answer` is user-only, invoked as `/productivity:answer <question>`;
  the other two trigger by description), "depends on no other plugin", how to load it.
- `claude_plugins/productivity/commands/init.md`, following the `sdd` init contract: a preflight
  that writes nothing; merge only its own `"productivity": true` under `enabledPlugins` and its own
  `Skill(productivity:*)` under `permissions.allow` in `.claude/settings.json`; add only its own
  `--plugin-dir` line to `claude.sh`; idempotent; never prompts. No `.claude/productivity/` config
  directory: the plugin has no per-project settings.
- `claude_plugins/productivity/resources/launcher_editing.md`: a fourth copy of the shared file, with
  its one-row table naming `productivity`. The `PLUGINS_ROOT` rule text is copied verbatim from the
  other inits.
- Because its init mentions `--plugin-dir`, `/ds:init`'s discovery rule
  (`claude_plugins/django-stack/commands/init.md`, the "run `/<name>:init`" step) flags a missing
  `productivity` launcher line with no change to `ds`.
- This repo: run `/productivity:init` (or apply its result by hand) so `claude.sh`,
  `enabledPlugins` and `permissions.allow` carry `productivity`.

### R2. `domain-glossary` and `notifications` move to `fls-dev`

- `git mv` both to `claude_plugins/fls-dev/skills/`.
- `.claude/sdd/config.md` `## Vocabulary Sources`: `.claude/skills/domain-glossary/SKILL.md` becomes
  `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md`.
- `claude_plugins/fls-dev/README.md`: the skill inventory and the list of FLS-specific skills name
  both.

### R3. `code-comments` splits between `ds` and `sdd`

- `git mv` `.claude/skills/code-comments` to `claude_plugins/django-stack/skills/code-comments`, then
  make it generic:
  - The description drops "in the FreedomLS codebase" and the planning-document trigger list.
  - The section "Write comments that stand without the planning documents" and its examples leave
    this file (see below).
  - Every remaining example uses neutral domain names in place of FLS ones (educator panel events,
    `REGISTRATION_CHANGED`, runner `Cache-Control`, `form_submit_and_exit`, save-on-exit forms, quiz
    scores, coming-soon course).
  - "Respect protected comments" states the rule (a `TODO` or `@claude` comment is never deleted
    until its work is done) without citing `CLAUDE.md`.
- `claude_plugins/sdd/skills/planning-references-in-code/SKILL.md` (new skill,
  `sdd:planning-references-in-code`): the planning-document rules that left `code-comments`, in
  `sdd`'s own terms. Its description carries the trigger the old `code-comments` description had for
  this case: writing or reviewing a comment while implementing a spec, plan or QA fix. The body holds the reference kinds table, why they rot, "rewrite
  each reference as the fact it stood for", and the BAD/GOOD examples, neutralised. The example path
  is a `spec_dd/` path of a made-up effort, since `spec_dd/` is `sdd`'s own convention.
- `sdd` applies that skill's file (`${CLAUDE_PLUGIN_ROOT}/skills/planning-references-in-code/SKILL.md`)
  wherever it applies the `Comment standard` hook, whatever the hook says:
  - `claude_plugins/sdd/commands/implement_plan.md`, the batch brief ("read and follow the
    `Comment standard` file") and the comment-review worker's closed checklist.
  - The `comments` row of `claude_plugins/sdd/resources/plan_review_dimensions.md` cites it as
    evidence.
- `claude_plugins/fls-dev/agents/qa-bugfixer.md` (line 217, "Follow the `code-comments` skill")
  follows `ds:code-comments` and `sdd:planning-references-in-code`, loaded with the `Skill` tool
  (a cross-plugin file is never read by path).
- `.claude/sdd/config.md` `## Review Hooks`: `Comment standard` becomes
  `claude_plugins/django-stack/skills/code-comments/SKILL.md`. It stays a path, because review
  workers read files and can't load skills.
- `claude_plugins/fls-dev/commands/init.md` Step 8b: a blank `Comment standard`, or one equal to the
  old `.claude/skills/code-comments/SKILL.md` when that file no longer exists, is set to
  `<PLUGINS_ROOT>/claude_plugins/django-stack/skills/code-comments/SKILL.md`, the same prefix rule
  as the other Step 8b keys. The "only when that file exists" guard and its outstanding action go.
- `claude_plugins/django-stack/README.md`: inventory counts the new skill.

### R4. `sdd` depends on `productivity`

- `claude_plugins/sdd/resources/writing_standard.md` (line 50) and
  `claude_plugins/sdd/commands/spec_from_idea.md` (line 132) name `productivity:unslop`.
- `claude_plugins/sdd/README.md`: "independent" becomes a statement that `sdd` needs `productivity`
  loaded, and why (`unslop` in the writing standard). Its skill inventory counts
  `planning-references-in-code`.
- `claude_plugins/sdd/commands/init.md`: when `claude.sh` has no `productivity` `--plugin-dir` line,
  list "run `/productivity:init`" as an outstanding action. It does not add the line itself.

### R6. Tightening pass

Every `.md` file in scope (see Scope) is rewritten per `productivity:writing-for-agents`, one file
at a time. A rewrite keeps:

- **Every instruction, rule, threshold, gotcha and "never" item**, and the one example that
  disambiguates each. Padding goes; behaviour stays.
- **Every skill description's trigger branches.** A description may shrink, but each distinct case
  that should fire the skill keeps a trigger, front-loaded. The `fls-dev` overlay descriptions lead
  with the distinguishing words instead of the shared "FreedomLS-specific extension of the ds:X
  skill" opener.
- **Exact strings other files or tools match on:** frontmatter keys and values
  (`name`, `description` semantics, `disable-model-invocation`, `argument-hint`, `allowed-tools`,
  `model`, `skills:`), `.claude/*/config.md` section and key names, return contracts and `status:`
  footers, step numbers and headings another file cites (for example `spec_review.md` Step 1 to
  Step 4, cited by `spec_from_idea.md`), file names, `${CLAUDE_PLUGIN_ROOT}` paths, and every
  heading and literal asserted by `tests/test_update_concrete_projects.py`.
- **`TODO` and `@claude` comments.**
- **Explicit steps in files a Haiku-tier agent follows** (the `sdd:sdd-mechanic` inputs such as
  `resources/commit_and_push.md` and `commands/protected/update_todo.md`): the weakest model that
  reads a file sets how much it can lose.

Deliberate copies are tightened identically or not at all: `launcher_editing.md` (ds, sdd, fls-dev,
productivity), `wrapper_script_migration.md` (ds, fls-dev), `agent_memory_guidelines.md` (ds, sdd,
fls-dev), and the `PLUGINS_ROOT` rule in each init.

The pass rewrites in place. It doesn't rename, move, split or merge files, and doesn't add content to
a generic plugin that names a project value.

Each file's rewrite is reviewed against its original (`git show <base>:<path>`) for dropped
instructions before it is committed. Before and after word counts are recorded per plugin.

## Testing

- `claude plugin validate --strict` passes for `productivity`, `ds`, `sdd`, `fls-dev` and
  `fls-content`, after the moves and after each tightening batch.
- A session started with `./claude.sh` lists each moved skill exactly once, under its new name, with
  no project-level duplicate. `/productivity:answer` works and `answer` does not auto-trigger.
- `uv run pytest tests/test_update_concrete_projects.py` passes after every batch that touches a file
  it reads.
- A grep for the old forms (`.claude/skills/{answer,unslop,writing-for-agents,code-comments,domain-glossary,notifications}`,
  `Skill(domain-glossary)`, `Skill(notifications)`, and bare backticked `` `unslop` ``,
  `` `code-comments` ``, `` `domain-glossary` ``, `` `writing-for-agents` `` used as skill names)
  finds nothing outside `spec_dd/3. done/` and other specs under `spec_dd/2. in progress/`.
- A grep for `FreedomLS`, `FLS`, `freedom_ls` and `fls-dev` finds nothing new in
  `claude_plugins/productivity`, `claude_plugins/django-stack` or `claude_plugins/sdd`.
- `/fls-dev:init` run on this repo leaves `Comment standard` pointing at the `ds` file and reports
  no outstanding comment-standard action.

## Documentation and downstream

- `/sdd:document`'s upgrade-notes hook records, for downstream projects: each skill's old and new
  invocation and path, the new `productivity` plugin and that `sdd` now needs it (run
  `/productivity:init`), the `/answer` to `/productivity:answer` change, and that a
  `Comment standard` or `## Vocabulary Sources` entry pointing at an old `.claude/skills/` path must
  be re-pointed (`/fls-dev:init` re-points the comment standard).
- Plugin READMEs (R1 to R4) carry current inventories.

## Success criteria

- `ls .claude/skills` prints `brand-guidelines` only.
- `claude_plugins/productivity/skills/` holds `answer`, `unslop`, `writing-for-agents`;
  `claude_plugins/fls-dev/skills/` holds `domain-glossary` and `notifications`;
  `claude_plugins/django-stack/skills/` holds `code-comments`.
- `claude_plugins/django-stack/skills/code-comments/SKILL.md` contains no FLS name, no `spec_dd/`
  path and no planning-document section; `sdd:planning-references-in-code` holds that section and
  `implement_plan.md` reads it.
- `claude.sh`, `enabledPlugins` and `permissions.allow` include `productivity`.
- Every check under Testing passes.
- Every in-scope `.md` file has been through the tightening pass, each with a review against its
  original, and the per-plugin before and after word counts are reported.
