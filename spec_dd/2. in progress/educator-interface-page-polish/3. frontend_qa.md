# Frontend QA: Educator interface page polish

## Setup

- Start the dev server with the `Dev server start` command from `## QA Hooks` in
  `.claude/sdd/config.md`, on `$PORT`. Base URL: `http://127.0.0.1:$PORT`.
- Log in at `/accounts/login/` as the admin from `## QA Login` (an organisation admin).
- The organisation slug is the one the educator interface lands on after login; call it `<org>`.
  Educator URLs are under `/<interface prefix>/<org>/…`: take the prefix from the address bar after
  clicking into the educator interface.
- Viewports: 375px (phone), 768px, 1280px. Collapse the Django debug toolbar before screenshots.

### Data needed (ask the QA data helper for anything missing)

1. Learner **A**: registered (individually or through cohorts) on 5 courses with items:
   - course 1: flagged (a failed latest quiz attempt), little recent activity;
   - course 2: in progress (some topics complete), most recent activity;
   - course 3: complete (100%);
   - course 4: not started, no course progress record;
   - course 5: in progress, older activity, with a long title (60+ characters).
2. Learner **B**: on exactly 3 courses.
3. Learner **C**: on no courses.
4. Learner **D**: holds one course both through a cohort and individually; only the cohort
   registration has a failed latest quiz attempt.
5. A learner with no recorded activity on a course with items (shows the "No recorded activity"
   flag).
6. A cohort over the report learner limit (`REPORTS_MAX_LEARNERS`), for the dashboard callout. If
   that is too large to seed, ask the data helper to lower the setting for the run or skip test 6
   step 4 and say so.
7. A course shared to the organisation by another organisation, held by learner A (for "Shared by").
8. A second educator account holding only a cohort-scoped role that can see learners but not rename
   them (for test 4).
9. Enough learners to run a bulk action in the request (below the background threshold) and,
   if feasible, enough to make one run in the background.

## Test 7: Bulk confirm dialog during an in-request run

URL: the learners list. Select a few learners (in-request size).

1. Choose a bulk action that changes something (for example deactivate or add to a cohort) and open
   its confirmation dialog.
2. Before confirming: Cancel and the close button work, Esc closes the dialog. Reopen it.
3. Slow the request so the run state is visible: use the Playwright MCP to route the confirm POST
   with a delay (or throttle the network in devtools), then click the confirm button.
4. While it runs:
   - the confirm button shows its loading text;
   - Cancel and the close button are disabled;
   - the body shows "This is running and can't be stopped. Wait for it to finish.";
   - pressing Esc twice leaves the dialog open;
   - clicking the backdrop leaves it open.
5. When it finishes: the result replaces the body and Cancel/close work again. Close the dialog.
   The selection bar and table reflect the change.
6. Error branch: route the confirm POST to fail (return 500, or abort it). Cancel and close become
   enabled again and a red alert line in the dialog reads "This did not finish. Some changes may
   not have been made. Reload the list to see which, then run it again." The dialog closes with Esc.
7. Repeat-submit: in a held run, try clicking the confirm button again. It stays disabled; only one
   run happens (check the result count and the audit log entry count).
8. Background run (if data item 9 allows): select enough rows to run in the background, confirm.
   The dialog closes and the selection bar shows progress, as before. Before confirming, the dialog
   shows no running sentence.
9. Other dialogs and drawers are unaffected: open a learner quick view and a filter sheet (at
   375px); their close buttons work. Open "Add learner": Cancel and Esc close it.
