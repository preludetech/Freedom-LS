# Spec: anonymous course applications

Idea: `idea.md`. Research: `research_current_apply_and_signup_flow.md`,
`research_anonymous_apply_security.md`, `research_guest_apply_ux_patterns.md`.

## Purpose

An anonymous visitor who clicks **Apply now** is sent to the full signup page, and has to verify
their email before they get back to the application. Many give up there. This spec lets them apply
straight away. An applicant details step asks for the signup details without a password. Their
application is stored as they go and reaches staff on submit. An email sent after submission proves
they own the address and attaches the application to an account.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| `AnonymousApplicant` | coined | The details an anonymous visitor gives on the applicant details step, for one course. No existing model holds pre-account applicant data. |
| applicant details step | coined | The page that collects an `AnonymousApplicant`. It sits before form page 1 and is not a `FormPage`. |
| claim link | coined | The signed link in the post-submit email. Following it attaches the application to a `User`. "Confirmation" is not used because allauth's email confirmation is a different mechanism. |
| unverified application | coined | A `CourseApplication` with `user` null, meaning nobody has followed its claim link yet. |

## Scope

In:

- The applicant details step, for anonymous visitors, on every `application_gated` course, whether
  or not it has a form, and whether or not `SiteSignupPolicy.allow_signups` is on.
- Anonymous access to the application pages, check-your-answers, the status page and the
  form_engine file endpoints, limited to the visitor's own unverified application.
- The claim email and the claim view, for a new email and for an existing account on the same site.
- An unverified flag on every admin screen that shows an application, its sitting or its files.
- Rate limits, honeypot, consent capture and erasure by email for anonymous applicants.

Out:

- The normal signup page. The authenticated apply path. CAPTCHA.
- An email whose account belongs to **another site**. The claim view must not attach the
  application to that account, log anyone in or create a user (the global `User.email` unique
  constraint would refuse it anyway). What that person sees is left for the multi-site email
  uniqueness work.
- Automatic purging. Anonymous applicants, drafts and unverified applications are kept until an
  operator erases them.
- Moving uploaded files when an application is claimed.

## Decisions

| Decision | Reason |
| --- | --- |
| No `User` exists until the claim link is followed. `CourseApplication.user` and `FormProgress.user` become nullable, and the visitor's details live on `AnonymousApplicant`. | A real `CourseApplication` is what lets staff see the application on submit. Creating a user early would collide with the globally unique email and fire signup side effects for an unverified address. With no account to pre-create, an impostor has nothing to leave behind for the claim to invalidate. |
| The applicant details step never queries `User` or `EmailAddress`. | The response is the same for new and registered emails by construction, so timing can't give it away. |
| The same claim email goes to every applicant. | The send doesn't depend on whether an account exists, so nothing branches before the mailbox is proven. |
| Following the claim link for an existing same-site account attaches the application and logs the person in. | Mailbox control already gets them in today through password reset (`ACCOUNT_LOGIN_ON_PASSWORD_RESET`). FLS has no MFA for this to bypass. |
| An existing account that already has an application for the course keeps both. The unique constraint covers only applications started while signed in. | User decision. |
| The claim link is a GET page with a POST **Confirm** button. | Mail scanners prefetch links. A GET must not change state. |
| The link expires after allauth's `EMAIL_CONFIRMATION_EXPIRE_DAYS`. An expired link offers to send a new one to the stored address. | This reuses the expiry signup already uses, and the new link still only goes to that mailbox. |
| Uploaded files stay at their pre-claim path after a claim. | Deletion is row-driven (`QuestionAnswerFile` post_delete), so erasing the user still removes the files. |

## Requirements

### Data model: `freedom_ls/course_applications/models.py`

- New `AnonymousApplicant(SiteAwareModel)`:
  - `course` FK to `Course` (CASCADE).
  - `email` (stored stripped and lowercased), `first_name`, `last_name`.
  - Consent evidence: `terms_version`, `terms_git_hash`, `privacy_version`, `privacy_git_hash`
    (blank when that document was not asked for), `consent_ip_address` (nullable),
    `consented_at` (nullable). Values come from `get_legal_doc(site, ...)` and `get_client_ip`,
    the same sources `SiteAwareSignupForm.custom_signup` uses (`accounts/forms.py:169`).
  - `user` nullable FK to `User` (CASCADE, `related_name="anonymous_applications"`), set on claim.
  - `claimed_at` nullable. It is set once and makes the claim single-use.
  - `created_at`, `updated_at`.
- `CourseApplication` (`models.py:18`):
  - `user` becomes `null=True`.
  - New `anonymous_applicant` nullable `OneToOneField(AnonymousApplicant, on_delete=CASCADE,
    related_name="course_application")`. It stays set after a claim, so the record of how the
    application started survives.
  - `unique_application_per_site_user_course` gains `condition=Q(anonymous_applicant__isnull=True)`.
    The model docstring's note about the future partial index stays.
  - New property `is_email_verified`: `user_id is not None`.
- `get_application_for_course` (`queries.py:23`) orders by `-created_at` before `.first()`, so it
  returns the most recent of two applications.
- Register `AnonymousApplicant` in `USER_ERASURE_CASCADE_MODELS`.

### Data model: `freedom_ls/form_engine/models.py`

- `FormProgress.user` (`:247`) becomes `null=True`. A user-less sitting is an anonymous visitor's.
  `form_engine` stays ignorant of `course_applications`.
- `question_answer_file_upload_to` (`:688`) uses `user_uploads/anonymous/{form_progress_id}/form_answers/{pk}{ext}`
  when the sitting has no user. Storage alias, size and type limits (`form_engine/uploads.py`) are
  unchanged.
- `FormProgress.complete()` on a user-less sitting sends `form_attempt_completed` with `user=None`.
  The receiver in `learner_progress/signals.py` must return without doing anything in that case.

### Data model: `freedom_ls/accounts/models.py`

- `LegalConsent.consent_method` gains the choice `application_details_step`. `timestamp` stays
  `auto_now_add`, so it records the claim time. The click time stays on
  `AnonymousApplicant.consented_at`.

### Anonymous session access

- `course_applications` keeps a session map from course id to `AnonymousApplicant` pk. A visitor
  owns an application when its `anonymous_applicant` is in their map and its `user` is null. One
  helper resolves "the application this request may act on", for a signed-in owner or an anonymous
  one. `_owned_application_with_form` (`views.py:142`) and `application_status` (`:114`) use it in
  place of `user=request.user`. `application_status`, `application_form_page` and
  `application_check_answers` drop `@login_required`. An anonymous request with no access gets a 404.
- `form_engine` keeps its own session list of user-less `FormProgress` pks. It exposes a function
  that grants access to a sitting and a lookup that accepts either `user=request.user` or a granted
  user-less sitting. `_owned_file_question` (`form_engine/views.py:33`) and
  `own_question_answer_file` (`:162`) use it. `question_file_upload`, `question_file_remove` and
  `own_question_answer_file` drop `@login_required`.
- Every lookup stays site-scoped through `SiteAwareManager`, so a session from another host
  resolves nothing.
- A claimed application (`user` set) is reachable only by that signed-in user.

### `apply` and the applicant details step: `freedom_ls/course_applications/views.py`, `urls.py`

- `apply` (`:59`) drops `@acquisition_login_required`. A signed-in request runs the existing code
  unchanged. `acquisition_login_required` itself is not changed: enrol-for-free and
  `course_interest` still use it.
- Anonymous `apply` keeps the hidden-course 404 and the coming-soon redirect. Then:
  - no `AnonymousApplicant` for this course in the session → redirect to the details step;
  - an application exists → `_resume_url` if unsubmitted, the status page if submitted;
  - details done on a form-less course → render `apply.html`, whose Previous goes back to the
    details step. Its POST creates the `CourseApplication` (which is submitted on creation), fires
    `record_application_submitted` and sends the claim email.
- New URL `apply/<slug:course_slug>/your-details/`, name `applicant_details`, view
  `applicant_details`:
  - Anonymous only. A signed-in visitor is redirected to `apply`.
  - Fields: email (required), first name (required when `get_effective_require_name`), last name,
    the `accept_terms` / `accept_privacy` checkboxes when `get_effective_require_terms_acceptance`
    and `has_legal_doc` say so, and the `fax_number` honeypot. Validation is a Django form,
    `ApplicantDetailsForm`. Move the honeypot check out of `SiteAwareSignupForm.clean`
    (`accounts/forms.py:139`) into a shared function both forms call, so behaviour and logging
    stay the same.
  - It renders inside `form_page.html`'s frame ("Application for <course>", the page heading, the
    same footer buttons). The text fields go through `form_engine/inputs/text_input.html`. The
    consent checkboxes link to `accounts:legal_doc` the way `base/templates/account/signup.html:30-68`
    does. A refused POST returns 422.
  - A valid POST creates the `AnonymousApplicant`, or updates the one in the session for this course,
    and adds it to the session map. For a course with a form, the first POST also creates the
    `CourseApplication` (user null) and its `FormProgress` (user null), grants the session access to
    the sitting, and redirects to `_resume_url`. A form-less course redirects to `apply`.
  - Once the application is submitted the step redirects to the status page.
- `application_form_page`: for an anonymous visitor on page 1, `previous_page_url` is the details
  step. Page numbering, `build_page_links`, `resume_page_number` and check-your-answers sections are
  unchanged.
- `application_check_answers` POST for an anonymous visitor completes the sitting, fires
  `record_application_submitted` and sends the claim email, then redirects to the status page
  instead of `learner_interface:dashboard`.
- `application_status.html` for an unverified application says the application was received, that
  a link was emailed to the stored address, and that following it finishes their account.

### Rate limits: `config/settings_base.py`

- Add these to `ACCOUNT_RATE_LIMITS` (`:455`). An action missing from the dict is silently
  unlimited:
  - `"application_details": "5/m/ip,5/h/key"`, consumed with `allauth.core.ratelimit.consume_or_429`
    on the details step's POST.
  - `"application_claim_email": "3/h/key"`, consumed with `ratelimit.consume` before each claim
    email. When the limit is hit, the email is skipped and the response does not change.
- The key is `f"{site.pk}:{email}"` with the normalised email. `settings_dev.py` keeps
  `ACCOUNT_RATE_LIMITS = False`.

### Claim email and claim view

- `send_application_claim_email(request, applicant)` sends
  `course_applications/email/application_claim` through `get_adapter(request).send_mail`. The body
  names the site and the course, holds the claim link and a line for people who didn't apply. It
  never includes the typed name. The templates extend `emails/base_email.{html,txt}`.
- The token is `django.core.signing` over the applicant pk with salt
  `"freedom_ls.course_applications.claim"`, checked with `max_age` set to allauth's
  `EMAIL_CONFIRMATION_EXPIRE_DAYS`.
- New URL `claim/<str:token>/`, name `claim`, view `claim_application`, open to anonymous visitors:
  - GET with a valid, unclaimed token renders a confirm page with a POST button.
  - GET with an expired token renders a page with a POST "send a new link" button. That button
    resends to the stored address (subject to `application_claim_email`).
  - A bad signature, an already-claimed applicant, or one with no submitted application renders the
    same "link invalid or already used" page.
  - POST runs in one transaction with `select_for_update` on the applicant and looks the email up
    case-insensitively across all sites:
    - **No account.** Create a `User` with the applicant's email and names, an unusable password
      (not through `UserManager.create_user`, which demands one), the current site, and a verified primary `EmailAddress`. Write one `LegalConsent` per accepted
      document from the stored evidence, with `consent_method="application_details_step"`. Set
      `user` on the application, its sitting and the applicant, and set `claimed_at`. After commit,
      fire `user.registered`, `record_sign_up` and `record_signup_attribution` with the claiming
      request. This path ignores `allow_signups`.
    - **Account on this site.** Set `user` on the application, its sitting and the applicant, and
      set `claimed_at`. The profile is not touched and no `LegalConsent` is written.
    - **Account on another site.** Nothing changes. Render the invalid-link page.
  - After a successful claim, log the user in with `django.contrib.auth.login`, which rotates the
    session key, and remove the applicant from the session map. An inactive account is attached
    but not logged in, and is sent to the login page.
  - Redirect: a new user goes to allauth's `account_set_password` with `next` set to the status
    page. An existing user goes straight to the status page. `RegistrationCompletionMiddleware`
    applies as usual from then on.

### Admin

- `CourseApplicationAdmin` (`course_applications/admin.py:58`):
  - an "Email verified" boolean column and filter;
  - `applicant_email` / `applicant_name` read from `anonymous_applicant` when `user` is null;
  - search covers `anonymous_applicant__email`;
  - an "Unverified email" row at the top of the change page's `summary_rows` for an unverified
    application.
- `FormProgressAdmin` (`form_engine/admin.py:261`) and `QuestionAnswerFileAdmin` (`:414`) show
  user-less sittings as unverified, with the applicant email reached through the
  `course_application` reverse accessor, the way `render_change_form` already does (`:341`).
  `form_engine` gains no import of `course_applications`.
- New read-only `AnonymousApplicantAdmin` (a `SiteAwareModelAdmin`), searchable by email. Its delete
  is the erasure path. Deleting an applicant removes its application, sitting, answers and files.
  The sitting needs explicit handling because `CourseApplication.form_progress` is RESTRICT.

## Testing

- Anonymous Apply on a form course goes to the details step. A valid POST lands on form page 1 with
  no `User` created. Page 1's Previous goes back to the details step.
- A form-less course goes details → `apply.html` → POST → status page. One unverified application
  and one claim email result.
- The details step's response, status code and redirect are identical for a new email, an email
  registered on this site and one registered on another site. No `User` query runs (assert with
  `django_assert_num_queries` or a patched manager).
- The details step works with `allow_signups=False`. It shows the name and consent fields according
  to `SiteSignupPolicy`. A filled honeypot is refused the way signup refuses it.
- Rate limits: the sixth POST in a minute from one IP gets 429. Per-email limits hold across IPs.
  Claim emails beyond three an hour are skipped and the page is unchanged.
- An anonymous visitor can open, answer, upload to, download from and submit only their own
  application. Another session, another site, or the application after its claim gets a 404.
- An anonymous upload is stored under `user_uploads/anonymous/<form_progress_id>/form_answers/`
  within the existing limits (extend `form_engine/tests/test_models.py:43-58`).
- Claim, new email: the user is created with an unusable password, a verified `EmailAddress`,
  `LegalConsent` rows carrying the stored version, hash and IP, and webhook, analytics and
  attribution fired once. The session key changes and the response redirects to set-password.
- Claim, existing same-site account: the application attaches, the profile is unchanged, no
  `LegalConsent` is written, the person is logged in with a new session key, and an earlier
  application to the same course remains. `get_application_for_course` returns the newer one.
- Claim, another-site account: nothing attaches, no user is created, the invalid-link page renders.
- The claim link is single-use. GET changes nothing. An expired token offers a resend.
- `FormProgress.complete()` on a user-less sitting doesn't fail and changes no course progress.
- Signed-in apply behaves exactly as before. Rewrite the anonymous redirect-to-signup tests in
  `course_applications/tests/test_views.py` (~1274-1370) for the new flow.
- Admin: the unverified flag shows on all three screens, and deleting an `AnonymousApplicant`
  removes its application, sitting and files.
- Playwright: extend `course_applications/tests/playwright/test_application_form_flow.py` with the
  anonymous path, from details through submit.

## Documentation and downstream

- `docs/product/learner-experience.md`: "Deferred-login Intent Completion" no longer covers
  Apply now. Describe the anonymous flow and the claim email.
- `docs/product/authentication.md`: accounts created by a claim, with no password until set, and
  claim acting as sign-in for existing accounts.
- `docs/product/signup-attribution.md`: a claim records attribution from the claiming request.
- `docs/product/webhooks.md`: `user.registered` also fires on a claim.
- `docs/product/admin-interface.md`, `docs/product/security-and-data-handling.md`: the unverified
  flag, `AnonymousApplicant` erasure, anonymous uploads, and the fact that there is no automatic
  purge.
- Upgrade notes: projects that set their own `ACCOUNT_RATE_LIMITS` must add `application_details`
  and `application_claim_email`, or those actions are unlimited. A cache shared between processes
  is needed for the limits to hold in production.
- `qa_helpers` commands that build or reset applications must handle a null `user`.

## Open questions

- An email that belongs to an account on another site: what the claim page tells that person, and
  whether the application can ever be claimed.
- The idea asks for a retention period. The user chose no automatic purge, so erasure on request is
  the only removal path. Check that this matches what the privacy notice says.
- Signup attribution is taken from the claiming request, so a claim in another browser records
  "direct". Snapshotting the attribution cookie on the details step would fix that, at the cost of
  more fields.
- An applicant who mistyped their email can't correct it after submitting, and the application stays
  unverified. Staff can see the email in the admin.

## Success criteria

- An anonymous visitor completes an application on a form course and on a form-less course without
  creating a password, verifying an email or logging in, and staff see it flagged as unverified.
- The details step's response is byte-identical apart from CSRF tokens for new, same-site-registered
  and other-site-registered emails.
- Following the claim link creates and logs in a new user or attaches to and logs in an existing
  same-site user, and the session key changes.
- No `User`, `LegalConsent`, `SignupAttribution`, webhook or sign-up analytics event exists for an
  unclaimed applicant.
- Signed-in apply tests pass unchanged.
- `uv run manage.py makemigrations --check` is clean and `uv run pytest` passes.
