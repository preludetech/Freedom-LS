# Spec: a batch re-runs only the tests that failed

## Purpose

After a fix, a batch and the other callers listed below finish once the failed tests and the tests
the fix's own diff selects pass. They no longer run the whole tier a second time. The whole-tier
gate stays at `implement_plan`'s final full run and at the `finish_worktree` checkpoint. The case
for it is in `idea.md`.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| failed-only re-run | coined | After a fix, one tier-shaped run (the tier's `-m`, the runner prefix, `-n auto`) of the failed and unfinished tests by node ID plus the targeted selection for the fix's own diff. Unlike the tier definition's "single test run", it covers every failed test at once and adds the fix's selection. |
| whole-tier re-run | coined | A failed-only re-run followed, once it passes, by the tier again as it first ran. |

## Scope

In:

- The section "When a targeted run or full run fails" in `test_tiers.md`, split into the two
  re-runs.
- `run_test_tier.md` taking the failed node IDs and returning them.
- The test runner printing failed and unfinished node IDs.
- The callers that opt into the failed-only re-run: a batch, every fix batch (`design fix`,
  `review fix`, `integration fix`), the integration run after a batch wave, the fix after
  `implement_plan`'s final full run, and the rebase command's `targeted` test step.

Out:

- Flaky tests: the flaky test guide owns them.
- Which tests the first run selects: `faster-test-runs-8-narrower-targeted-tier` owns
  `select_tests.py` and the targeted bullet of `test_tiers.md`.
- The `finish_worktree` checkpoint and its own failure rules ("Flaky tests", "Obvious failures").
- `full_run_record.py`.

## Decisions

- **The caller picks the re-run, not the tier name.** The checkpoint can resolve to `targeted`
  (`run_test_tier.md` Step 2), so a rule keyed on "a failed targeted run" would reach it. A caller
  that names neither re-run gets the whole-tier re-run, so no caller this spec leaves out loses its
  gate.
- **Explicit node IDs, not `--lf`.** `--lf` falls back to the whole selection on an empty or stale
  cache and a bare `--lf` drops the tier's `-m` (`research_known_complaints.md`).
- **The runner shares a file with `faster-test-runs-9-machine-wide-test-run-limit`.** This spec
  edits only the closing lines; whichever lands second rebases.

## Requirements

### 1. Tier definition: `claude_plugins/django-stack/resources/test_tiers.md`

Rewrite "When a targeted run or full run fails". It still addresses the agent that owns the change,
never a mechanic briefed only to run a tier.

The failed set is the node IDs the failed run printed: the runner's `run: failed` and
`run: unfinished` lines (Requirement 2). When the runner printed no `run: summary (merged)` line
(no runner, `DS_TEST_MEMORY_GUARD=off`, or its plain fallback), it is pytest's `FAILED <node id>`
short-summary lines. A failed run whose runner printed `run: failed ... and N more` takes the
whole-tier re-run whatever the caller asked for.

Fix the failure, then re-run as the caller says. Two subsections:

**Failed-only re-run.** Run the selector with the fix's diff: the files the fix edited as explicit
paths when the fix is uncommitted (a batch's work is uncommitted, so `--working-tree` would select
the whole batch again), `--range <sha before the fix>..HEAD` when it is committed. Then:

- `tier: targeted` → run the printed `command:` line with the failed set appended.
- `tier: none` → run the command below, spelled once in this section, with the failed set as its
  paths:
  `.claude/ds/scripts/run_tests.sh uv run pytest -n auto --no-cov -m '<markers>' <node ids>`,
  where `<markers>` is `markers` from `[tool.test_tiers]` (omit `-m` when unset) and the runner
  prefix is dropped when it is not installed.
- `tier: full` (the fix touched an escalation path) → run the full tier. It is an ordinary full
  run: its pass finishes the step and it writes the full-run record as any full run does.

Each node ID is single-quoted on the command line. The step is done when that run passes. A
failure in it is fixed the same way, with its own failed set and the new fix's diff.

**Whole-tier re-run.** The failed-only re-run, then once it passes the tier again as it first ran.
The gate is the whole tier.

Remove the `uv run pytest --lf --no-cov` command.

Add to "Reporting": a failed-only re-run reports
`tier: <tier> · summary: failed-only re-run of <n> tests + fix selection: <verdict line>`, after
the failed run's report line, which stays in the report.

### 2. Test runner: `claude_plugins/django-stack/scripts/run_tests.py`

`print_closing_lines` prints, before `run: summary (merged)`:

- one `run: failed <node id>` line per test whose merged outcome is `failed`, including tests
  that crashed their worker in every attempt;
- one `run: unfinished <node id>` line per test still unfinished when the run ends `FAIL`.

Lines are in sorted node-ID order. At most 200 lines are printed in total, then
`run: failed ... and <n> more`. A `PASS` run prints none. An `INCOMPLETE` run prints no
`run: unfinished` lines: it stays blocked on memory, not a failure to fix.

### 3. Helper: `claude_plugins/sdd/commands/protected/run_test_tier.md`

- A new optional input, `<failed>`: the failed set of an earlier run. With it the helper runs the
  tier definition's failed-only re-run with `<diff>` as the fix's diff, in place of `<tier>`.
- Step 4's return gains the failed set when the run fails:
  `tier: ... · summary: ... · failed: <node ids, space-separated, or the "and N more" note>`.
- Step 3 is unchanged: a failed-only re-run records only when it ran the full tier.

### 4. Callers that opt into the failed-only re-run

Each passes `<failed>` to `run_test_tier.md` or points at the failed-only re-run by name, and does
not restate it.

- `claude_plugins/sdd/commands/implement_plan.md`, batch brief Step 3 point 3: a failure follows
  the failed-only re-run, and the batch is done when it passes. Fix batches inherit this through the
  existing "runs `targeted` the same way" line. The batch-wave rule ("The tier must pass before the
  next batch wave is formed") counts a batch's passing failed-only re-run.
- Same file, "After integration": the integration run stays. The mechanic returns the failed set;
  a sub-agent fixes the failure, commits `[batch <id>] integration fix`, and follows the failed-only
  re-run with `--range <sha before the fix>..HEAD`.
- Same file, Step 3 point 3: the fix sub-agent keeps looping on the single test run until each test
  passes, then follows the failed-only re-run with the fix's range. The final full run stays the
  gate.
- `claude_plugins/django-stack/commands/rebase_main.md`, Step 9: a failed `targeted` run follows
  the failed-only re-run, selecting from the committed fix's range in one selector call. A failed
  `full` run follows the whole-tier re-run. The limit is three fix attempts of either kind.
  `pre_step_rebase.md` reaches this through `rebase_main.md` and needs no edit.

### 5. Callers that keep the whole tier

`claude_plugins/sdd/agents/qa-bugfixer.md` Step 5 (see Open questions) and `finish_worktree.md`
need no edit beyond keeping their pointer to the restructured section valid.

## Testing

- `tests/test_run_tests.py`: a failed run prints one `run: failed` line per failed test, in sorted
  order; a test that crashed its worker in every attempt is printed as failed; a `FAIL` run with
  unfinished tests prints `run: unfinished` lines; more than 200 prints the `and N more` line; a
  `PASS` run prints none; an `INCOMPLETE` run prints no `run: unfinished` lines.
- `tests/test_test_tiers.py`: the allowlist passes, the failure section names both re-runs, and no
  plugin file spells `--lf`.
- A prompt test beside `tests/test_rebase_prompts.py`: `implement_plan.md`, `rebase_main.md` and
  `run_test_tier.md` name the failed-only re-run; `qa-bugfixer.md` and `finish_worktree.md` do not.
- The existing assertions in `tests/test_checkpoint_prompts.py` and `tests/test_rebase_prompts.py`
  still hold or are updated where the reworded text moves them; `implement_plan.md` still asks for
  `<tier>: full` exactly once.

## Documentation and downstream

Update `claude_plugins/sdd/commands/README.md` and the `implement_plan` and `rebase` diagrams in
`claude_plugins/sdd/docs/diagrams/` where they describe the whole-tier re-run;
`check_diagrams.py` must pass. Concrete projects take the plugins through the FLS submodule; no
project config changes.

## Open questions

- Q: Does `qa-bugfixer`'s targeted run follow the failed-only re-run? → A: No, it keeps the
  whole-tier re-run (assumed default: `qa_fix` skips re-driving the regression layer on the
  strength of that run, so narrowing it removes a check nobody replaces. Overrule by editing
  Requirements 5.)

## Success criteria

- `git grep -- '--lf' claude_plugins` finds nothing.
- `uv run pytest tests/test_run_tests.py tests/test_test_tiers.py tests/test_checkpoint_prompts.py tests/test_rebase_prompts.py`
  and the new prompt test pass.
- In a batch whose targeted run fails, the next run's command names only the failed node IDs plus
  the fix diff's selection, and the batch commits once that run passes.
