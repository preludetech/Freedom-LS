# Spec: a batch re-runs only the tests that failed

## Purpose

When a batch's test run fails, the tier definition makes the batch fix the failure, re-run the
failures, then run the whole tier again (`claude_plugins/django-stack/resources/test_tiers.md`,
"When a targeted run or full run fails"). Every failure therefore costs the tier twice, and under
load the second run can fail on another slow test and start the cycle again. After this spec a
batch, and the other callers listed below, finish once the failed tests and the tests the fix's own
change selects pass. The whole-tier gate stays at `implement_plan`'s final full run and at the
`finish_worktree` checkpoint. See `idea.md` for the numbers.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| failed-only re-run | coined | After a fix, one run of the failed tests by node ID plus the targeted selection for the fix's own diff. No existing term: today's `--lf` re-run is a step towards the whole tier, not a finish. |
| whole-tier re-run | coined | After a fix and a passing failed-only re-run, the tier run again as it first ran. Today's only rule. |

## Scope

In:

- The failure section of the tier definition, split into the failed-only re-run and the
  whole-tier re-run, with the whole-tier re-run as the default.
- The callers that opt into the failed-only re-run: a batch, every fix batch (`design fix`,
  `review fix`, `integration fix`), the integration run after a batch wave, the fix after
  `implement_plan`'s final full run, and the rebase command's `targeted` test step.
- The test runner printing the node ID of every failed test, crash-counted ones included.

Out:

- Flaky tests: the flaky test guide owns them.
- Which tests the first run selects: `faster-test-runs-8-narrower-targeted-tier` owns
  `select_tests.py` and the targeted bullet of `test_tiers.md`.
- The `finish_worktree` checkpoint and its own failure rules ("Flaky tests", "Obvious failures").
- The full-run record (`run_test_tier.md` Step 3, `full_run_record.py`): a failed-only re-run never
  writes it.

## Decisions

- **The rule depends on the caller, not the tier name.** The checkpoint can resolve to `targeted`
  (`run_test_tier.md` Step 2), so "a failed targeted run re-runs only failures" would reach it.
- **Whole-tier re-run is the default.** A caller that only says "follow the failure section" keeps
  today's behaviour, so a caller this spec does not name cannot lose its gate by accident.
- **The failed set comes from explicit node IDs, not `--lf`.** `--lf` falls back to the whole
  selection on an empty or stale cache (`--lfnf` defaults to `all`), its cache is last-writer-wins
  per worktree, a bare `--lf` drops the tier's `-m`, and `--lf <paths>` is an intersection, not a
  union (`research_known_complaints.md`, `research_reference_implementations.md`).
- **The runner prints the failed node IDs.** It already merges outcomes across attempts and counts
  a test that crashed its worker in every attempt as failed; printing them gives the agent the
  exact set. This touches the runner, which `faster-test-runs-9-machine-wide-test-run-limit` also
  changes; the edit is limited to the closing lines, so whichever lands second rebases.
- **The fix's diff is the fix's own files.** In a batch the work is uncommitted, so
  `--working-tree` would select the whole batch again. An uncommitted fix passes the files it
  edited as explicit paths; a committed fix passes `--range <sha before the fix>..HEAD`.
- **A fix that touches an escalation path escalates.** The selector already turns such a diff into
  `tier: full`; the failed-only re-run then runs the full tier, which is the right outcome.

## Requirements

### 1. Tier definition: `claude_plugins/django-stack/resources/test_tiers.md`

Rewrite "When a targeted run or full run fails". It still addresses the agent that owns the change,
never a mechanic briefed only to run a tier. It says:

1. Fix the failure. The failed tests are the node IDs the failed run printed: the runner's
   `run: failed <node id>` lines (Requirement 2), or pytest's `FAILED <node id>` short-summary
   lines without the runner.
2. Re-run as the caller says. A caller that names neither re-run gets the whole-tier re-run.

Two subsections follow.

**Failed-only re-run.** Run the selector with the fix's diff: the files the fix edited as explicit
paths when the fix is uncommitted, `--range <sha before the fix>..HEAD` when it is committed. Then:

- `tier: targeted` → run the printed `command:` line with the failed node IDs appended.
- `tier: none` → run the targeted command's shape with only the failed node IDs as paths, keeping
  the tier's `-m '<markers>'` from `[tool.test_tiers]` and the runner prefix when installed. Spell
  this command once, in this section.
- `tier: full` → run the full tier.

The step is done when that run passes. The whole tier is not run again. A failure in the re-run is
fixed the same way, with the new failures and the new fix's diff.

**Whole-tier re-run.** Today's text without the `--lf` command: fix, run the failed-only re-run,
then once it passes run the whole tier as it first ran. The gate is the whole tier.

Add to "Reporting": a failed-only re-run reports
`tier: <tier> · summary: failed-only re-run of <n> failed tests + fix selection: <runner summary and RESULT line>`,
after the failed run's own report line, which stays in the report. A failed-only re-run never
reports as a bare tier pass.

Remove the `uv run pytest --lf --no-cov` command. No other file spells it.

### 2. Test runner: `claude_plugins/django-stack/scripts/run_tests.py`

`print_closing_lines` prints one `run: failed <node id>` line per test whose merged outcome is
`failed`, repeat crashers included, before the `run: summary (merged)` line, in collection order.
A `PASS` run prints none. `RESULT INCOMPLETE` stays a memory block, not a failure to fix; the
unfinished tests are not printed as failed.

### 3. Callers that opt into the failed-only re-run

Each points at the tier definition's "Failed-only re-run" by name and does not restate it.

- `claude_plugins/sdd/commands/implement_plan.md`, batch brief Step 3 point 3: a failure follows
  the failed-only re-run. "Done when" is the failed-only re-run's passing line. Fix batches
  inherit it through the existing "runs `targeted` the same way" line.
- Same file, the batch wave rule ("The tier must pass before the next batch wave is formed"):
  reword so a batch's passing failed-only re-run satisfies it.
- Same file, "After integration": keep the integration run. A failure is fixed by a sub-agent
  following the failed-only re-run with `--range <sha before the fix>..HEAD`, committed as
  `[batch <id>] integration fix`. Replace the "as Step 3 point 3 does" pointer, which names the
  wrong step.
- Same file, Step 3 point 3 (the fix after the final full run): replace the restated node-ID and
  range text with a pointer to the failed-only re-run. Behaviour is unchanged, and the final full
  run itself stays the gate.
- `claude_plugins/django-stack/commands/rebase_main.md`, Step 9: a failed `targeted` run follows
  the failed-only re-run with the committed fix's range. A failed `full` run follows the whole-tier
  re-run. "Three attempts" counts failed-only re-runs for `targeted` and whole-tier re-runs for
  `full`.

### 4. Callers that keep the whole tier

No edit beyond keeping their pointer valid after the section is restructured:
`claude_plugins/sdd/agents/qa-bugfixer.md` Step 5 (its run is the regression proof
`do_qa_fix_loop.md` and the sdd README rely on), and `finish_worktree.md`, which follows its own
rules.

## Testing

- `tests/test_run_tests.py`: a failed run prints one `run: failed <node id>` line per failed test;
  a test that crashed its worker in every attempt is printed as failed; a `PASS` run prints none;
  an `INCOMPLETE` run does not print its unfinished tests as failed.
- `tests/test_test_tiers.py`: the allowlist still passes, the failure section names both re-runs,
  and no plugin file spells `--lf`.
- A prompt test beside `tests/test_rebase_prompts.py` and `tests/test_checkpoint_prompts.py`:
  `implement_plan.md` and `rebase_main.md` name the failed-only re-run; `qa-bugfixer.md` and
  `finish_worktree.md` do not; `implement_plan.md` still asks for `<tier>: full` exactly once.

## Open questions

- Q: Does `qa-bugfixer`'s targeted run follow the failed-only re-run? → A: No, it keeps the
  whole-tier re-run (assumed default: `qa_fix` skips re-driving the regression layer on the
  strength of that run, so narrowing it removes a check nobody replaces. Overrule by editing
  Requirements 4.)

## Success criteria

- After a batch's targeted run fails and is fixed, the batch's next run names only the failed node
  IDs plus the fix diff's selection, and the batch commits once that run passes.
- A failed `targeted` rebase run is followed by a failed-only re-run; a failed `full` rebase run is
  followed by the whole tier.
- `qa-bugfixer`, the `finish_worktree` checkpoint and `implement_plan`'s final full run behave as
  before.
- A test that crashed its worker in every attempt appears as a `run: failed` line and is in the
  failed-only re-run.
- `git grep -- '--lf' claude_plugins` finds nothing.
- `uv run pytest tests/test_run_tests.py tests/test_test_tiers.py` and the new prompt test pass.
