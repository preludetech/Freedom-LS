# Spec: Audit log

Spec 11 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Source: `idea.md`. `research_codebase.md` section 4 holds the action inventory, with the
file and line of each write point.

## Purpose

Organisation admins can now deactivate learners, move memberships, unregister cohorts and remove
roles from a screen, and nothing records who did it. This spec adds one append-only record of every
such action, written by the role utilities and every educator interface action, and shows it on the
learner page, the cohort page and an organisation-level log.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `AuditLogEntry` | coined | One row of the audit log: an actor did an audit action to a target in an organisation. `LegalConsent` and `ApplicationStateTransition` are single-purpose audit records; nothing records educator and role changes. |
| audit action | coined | A registered `AuditAction` (code, label, describe). Its code is a `noun.verb` string such as `learner.deactivated`, stored in `AuditLogEntry.action`. Not a `PanelAction` (the UI control that performs it) or a `BulkAction`. |
| subject key | coined | `"<app_label>.<model_name>:<pk>"`, the string an entry stores for each object whose history it belongs in. |
| bulk run | coined | One execution of a `BulkAction` or a CSV import commit (spec 8). Its entries share a `run_id`. |

## Scope

In:

- A new app, `freedom_ls/audit_log`, holding the `AuditLogEntry` model, the writer, the audit
  action registry, a read-only admin and a prune command.
- Entries written by the object-role and site-role utilities and by every action in specs 6, 7 and
  9, with an `actor` and a `reason` passed to the service functions that lack them.
- The writer contract spec 8 calls for bulk runs and import commits.
- An optional reason on removals and deactivations, entered in the confirm dialog.
- A History tab on the learner page and the cohort page, and an organisation-level Audit log section.
- A `view_auditlogentry` capability for `site_admin` and `organisation_admin`.

Out:

- Field-level change tracking, undo, restoring from the log.
- Anything learner-facing.
- Login and authentication events (`django-axes` and allauth record those).
- Webhook deliveries and report generations; `WebhookDelivery` and the report models are their
  own record.
- System-role changes (`assign_system_role`, `remove_system_role`): `SystemRoleAssignment` has no
  site and is never changed from the educator interface. Their two `# TODO: AuditLog entry`
  comments stay.
- Showing site-role entries in the educator interface. They have no organisation; the Django admin
  shows them.
- Changes made by editing models directly in the Django admin, which bypass the service functions.
- A backfill of past actions. History starts at the upgrade.
- Database-level immutability (triggers, revoked privileges). Append-only holds against application
  code only.

## Decisions

1. **A new app.** `learner_management` imports `role_based_permissions`, so the role utilities
   can't import a model there; the model needs an app that both can import.
2. **An entry is findable through `subjects`, a list of subject keys with a GIN index.** A move
   names a learner and two cohorts and must show on all three pages, which one generic target can't
   do.
3. **A bulk run writes a normal entry per changed object and one summary entry, all sharing a
   `run_id`,** so learner and cohort history show what a bulk run did to them.
4. **Write only when state changed.** A no-op writes nothing, and a refused or rolled-back action
   writes nothing because the write sits inside the action's `transaction.atomic()`. The one
   exception is `learner.setup_email_resent`: sending an email counts as a change.
5. **Raw role-utility calls with no actor are logged, as "System".** Fixtures, QA commands and the
   `pre_delete` receiver that clears a deleted cohort's roles call the utilities with no actor. No
   Django admin registers the role assignment models; edits made there would bypass the utilities.
6. **Deleting a user leaves their entries, names included.** `actor_label`, `target_label` and the
   old and new names in `learner.renamed` stay as written, and the append-only guards give the
   application no way to rewrite them. An erasure request that covers the audit log is an
   operator's task: `prune_audit_log` by age, or direct database access. The security doc says so.

## Requirements

### `audit_log` app

New app `freedom_ls/audit_log`: label `freedom_ls_audit_log`, `verbose_name="Audit log"`, in
`INSTALLED_APPS` in `config/settings_base.py`, following `docs/app_conventions.md`. It depends on
`accounts`, `base`, `organisations` and `site_aware_models` only. `role_based_permissions`,
`learner_management` and `educator_interface` import it.

### `AuditLogEntry` model

`freedom_ls/audit_log/models.py`, `AuditLogEntry(SiteAwareModel)`:

| Field | Type | Notes |
| --- | --- | --- |
| `created_at` | `DateTimeField(default=timezone.now)` | Time of the action, UTC. |
| `organisation` | FK `freedom_ls_organisations.Organisation`, `null=True`, `on_delete=PROTECT`, `related_name="+"` | Null for site-role entries. `PROTECT` matches `Learner` and `Cohort`. |
| `actor` | FK `AUTH_USER_MODEL`, `null=True`, `on_delete=SET_NULL`, `related_name="+"` | Null for a system action, or once the user is deleted. |
| `actor_label` | `CharField(max_length=255, blank=True)` | `actor.display_name` at write time; empty for a system action. Kept after the user is deleted. |
| `action` | `CharField(max_length=100)` | An audit action code. No `choices=`; the writer validates it. |
| `target_content_type` | FK `ContentType`, `on_delete=PROTECT` | With `target_object_id`, a `GenericForeignKey` `target`. |
| `target_object_id` | `CharField(max_length=255)` | Open set, per `docs/app_conventions.md`. |
| `target_label` | `CharField(max_length=255)` | Reads after the target is gone. |
| `subjects` | `ArrayField(CharField(max_length=300))` | Subject keys, always including the target's. |
| `reason` | `CharField(max_length=500, blank=True)` | Optional, stripped. |
| `details` | `JSONField(default=dict, blank=True)` | Ids, labels, counts. Never tokens, links or email addresses beyond the labels. |
| `run_id` | `UUIDField(null=True, blank=True)` | Set on every entry of a bulk run. |

Meta: `ordering = ("-created_at", "-id")`; indexes on `(organisation, -created_at)`, `run_id`, and
a `GinIndex` on `subjects`. The model's default `view_auditlogentry` permission is the capability;
no `Meta.permissions`.

Append-only, three layers:

- `AuditLogEntryQuerySet`, whose `update()`, `delete()` and `bulk_update()` raise `AppendOnlyError`
  (new, in `audit_log/exceptions.py`). The one update allowed is exactly `update(actor=None)`:
  deleting a user runs the `actor` FK's `SET_NULL` through `_base_manager.update()`, and without
  the exception no user who acted on an entry could be deleted. `create()` and `bulk_create()`
  work. One method,
  `prune_before(cutoff)`, is the only delete path. `objects =
  SiteAwareManager.from_queryset(AuditLogEntryQuerySet)()`, plus `unscoped =
  AuditLogEntryQuerySet.as_manager()` for reads and writes outside a request, with
  `Meta.base_manager_name = "unscoped"` so `_base_manager` carries the same guards.
- `save()` raises `AppendOnlyError` on a row that isn't being added; `delete()` raises always.
- A read-only admin (below).

### Writer

`freedom_ls/audit_log/writer.py`, with `JSONValue` a recursive type alias in `audit_log/types.py`:

```python
def record_entry(
    *,
    action: str,
    actor: User | None,
    target: Model,
    target_label: str,
    organisation: Organisation | None,
    subjects: Iterable[Model] = (),
    reason: str = "",
    details: Mapping[str, JSONValue] | None = None,
    run_id: UUID | None = None,
    site: Site | None = None,
) -> AuditLogEntry: ...
```

- Raises `ValueError` for an unregistered `action`, as `webhooks.registry.validate_event_type` does.
- Takes `site` from the argument, else from the target (`site_of`), never from the request, so it
  works in a background task or a management command. Creates through `unscoped`.
- Builds `subjects` from `target` plus every object in `subjects`.
- Fills `actor_label` from `actor.display_name`.
- Callers pass `target_label`: `user.display_name` for a learner, a user or an `OrganisationMember`,
  `cohort.name` for a cohort.
- Opens no transaction and registers no `on_commit`; the caller's transaction holds it. Not wrapped
  in a `try`.

`record_run_summary(...)`, same module, writes the summary entry of a bulk run. It takes the
`run_id`, the `organisation`, the actor, the reason and a `details` dict with the run's counts by
outcome (`changed`, `skipped`, `failed`) and up to 50 skipped or failed rows as
`{"label": str, "outcome": str}`, plus `truncated: bool`. Its target is the organisation. A bulk
run's per-object entries carry the same `run_id` and the same reason.

### Audit action registry

`freedom_ls/audit_log/actions.py` defines `AuditAction(code, label, describe)`, where `describe` is
an optional `Callable[[AuditLogEntry], str]` that renders the details line, and
`FLS_AUDIT_ACTIONS`. `freedom_ls/audit_log/config.py` adds `AUDIT_LOG_EXTRA_ACTIONS:
Setting(default={})`, a `{code: label}` dict a downstream project fills. `get_audit_action(code)`
returns the registered audit action, or a fallback whose label is the code so an entry from a
removed setting still renders. A system check fails (`freedom_ls_audit_log.E001`) when an extra code
collides with an FLS code or isn't `noun.verb`. Labels render at read time.

Audit action codes are a namespace separate from webhook event types. Some strings match
(`learner.added`); others differ (`cohort_membership.added` against `cohort.member_added`). The
README lists the pairs.

FLS codes, with the labels the UI and product docs use:

| Code | Label | Target | Other subjects | `details` |
| --- | --- | --- | --- | --- |
| `learner.added` | Learner added | learner | cohort, if one was given | `outcome` (`created`, `joined`, `reactivated`) |
| `learner.renamed` | Learner renamed | learner | | `old`, `new` |
| `learner.deactivated` | Learner deactivated | learner | | |
| `learner.reactivated` | Learner reactivated | learner | | |
| `learner.setup_email_resent` | Setup email resent | learner | | |
| `cohort_membership.added` | Added to cohort | learner | cohort | `cohort` label |
| `cohort_membership.removed` | Removed from cohort | learner | cohort | `cohort` label |
| `cohort_membership.moved` | Moved between cohorts | learner | both cohorts | `source`, `destination` labels, `move_id` |
| `registration.added` | Registered for course | learner | | `course` label |
| `registration.reregistered` | Re-registered for course | learner | | `course` label |
| `registration.unregistered` | Unregistered from course | learner | | `course` label |
| `cohort.created` | Cohort created | cohort | | |
| `cohort.renamed` | Cohort renamed | cohort | | `old`, `new` |
| `cohort.deactivated` | Cohort deactivated | cohort | | |
| `cohort.reactivated` | Cohort reactivated | cohort | | |
| `cohort.deleted` | Cohort deleted | cohort | | |
| `cohort_registration.added` | Cohort registered for course | cohort | | `course` label |
| `cohort_registration.reregistered` | Cohort re-registered for course | cohort | | `course` label |
| `cohort_registration.unregistered` | Cohort unregistered from course | cohort | | `course` label |
| `role.granted` | Role granted | user | the object the role is on (`ObjectRoleAssignment.target`) | `role` code, `role_label`, `scope` label |
| `role.removed` | Role removed | user | the object the role is on (`ObjectRoleAssignment.target`) | `role` code, `role_label`, `scope` label |
| `member.suspended` | Member suspended | `OrganisationMember` | its user | |
| `member.reactivated` | Member reactivated | `OrganisationMember` | its user | |
| `bulk_action.completed` | Bulk action completed | organisation | | run summary, plus `bulk_action` (the per-object audit action code) |
| `import.committed` | Import committed | organisation | | run summary |

The `describe` renderer for `role.granted` and `role.removed` reads "`role_label` on `scope`" from
the entry's details, falling back to the `role` code when the label is absent. The role utilities
store `role_label` (the role's `display_name` from `get_role_config`, or the code for a role no
longer configured) at write time, like every other label in `details`, so `audit_log` never imports
`role_based_permissions`. `bulk_action.completed` and `import.committed` are the summary actions.

### Writers in the role utilities

`freedom_ls/role_based_permissions/utils.py`:

- `assign_object_role` and `remove_object_role` (TODOs at lines 271 and 294) and `assign_site_role`
  and `remove_site_role` (lines 328 and 373) write `role.granted` or `role.removed`, inside a
  `transaction.atomic()` that also covers the assignment change. The entry in `remove_site_role`
  moves inside its existing atomic block. Each TODO is removed once its entry is written.
- `assign_*` writes when the assignment row changed: created, reactivated, or re-granted by a
  different grantor (which moves `assigned_by` and `assigned_at`, the "added by" and "added on" the
  UI shows). A re-grant by the same grantor changes nothing and writes nothing.
- `remove_*` filters its `update()` on `is_active=True` and writes when the count is non-zero.
- `remove_object_role` and `remove_site_role` gain keyword-only `reason: str = ""`; the actor is
  the existing `assigned_by` or `removed_by`.
- The organisation comes from `organisations.utils.organisation_of`: the target itself when it is
  an `Organisation`, the target's `organisation` attribute when it has one, and null otherwise and
  for site roles. `capabilities._organisation_of` keeps its allow-list of scope kinds and delegates
  to the same function, so the two never disagree.
- `delete_role_rows_for(target, *, removed_by=None, reason="")` writes `role.removed` for each
  active assignment on the target before deleting the rows. The `pre_delete` receiver on `Cohort`
  calls it with no actor, so a cohort deleted from the Django admin logs its roles as removed by
  the system; `DeleteEmptyCohortAction` calls it first with the actor and reason, so the receiver
  then finds nothing.
- Site-role entries pass `site` explicitly (the role's site, not the user's).
- `assign_system_role`, `remove_system_role` and their TODOs are untouched.
- The `view_audit_log` placeholder comments in `registry.py:131` and `roles.py:134` describe a
  platform-wide log for `system_admin`, which this spec doesn't build. They stay.

- `learner_management/learner_actions.py` (`deactivate_learner`, `reactivate_learner`,

  single actions are not bulk runs.

### Readers

A base `AuditLogEntryTable(DataTable)`, a `TargetedAuditLogEntryTable` subclass and an
organisation-log subclass of that, in `educator_interface`.
Columns: When (absolute date and time in the project's `TIME_ZONE` via `timezone.localtime`, in a
`<time datetime>` element), Who (`actor_label`, or "System" when `actor_label` is empty), What (the
audit action label), Details (the action's `describe` line, then the reason on its own line when
present). The targeted subclass adds Target (`target_label`), for tables whose rows are about
different objects; the cohort History and the organisation log use it, the learner History doesn't.
Mobile cards: What and Target primary, When and Who secondary. `page_size = 25`. No bulk actions, no search, no sort controls; the
order is the model's.

- **Learner page.** `LearnerHistoryPanel` (`educator_interface/views.py:695`) becomes a
  `DataTablePanel` over entries whose `subjects` contain the learner's subject key, with
  `capability = "freedom_ls_audit_log.view_auditlogentry"`. It keeps `refresh_events =
  (LEARNER_CHANGED,)`. Empty state: "No history for this learner yet. Actions such as moving or
  deactivating them are recorded here."
- **Cohort page.** `CohortTabSet` (`views.py:963`) gains `"history": CohortHistoryPanel`, the same
  shape over the cohort's subject key, refreshing on `COHORT_CHANGED`. It uses the targeted table,
  so each row names the learner, user or member it is about; rows about the cohort itself show the
  cohort's name. Empty state: "No history for
  this cohort yet. Actions such as adding learners or registering it for a course are recorded here."
- **Organisation log.** `AuditLogConfig(OrganisationSectionConfig, ListViewConfig)`, title "Audit
  log", under the Administration nav group beside `MemberConfig`, with `view_capability` set to the
  capability and a `check_access_exempt_reason` (entries have no instance pages). Its queryset is the
  organisation's entries, minus entries with a `run_id` whose action is not a summary action, so a
  500-row run is one row. Filters, each a `TableFilter` subclass with its own `apply`:
  - Who: users who are the actor on this organisation's entries, plus "System" (`actor` null and
    `actor_label` empty). Entries by a deleted user show their stored name and match no Who choice.
  - What: multi-select over the registered audit actions.
  - When: single-select presets Today, Last 7 days, Last 30 days, Last 90 days, Last 12 months, in
    the project's `TIME_ZONE`. No default window.
  A summary row's Details holds a `<details>` disclosure, "Show N entries", listing up to 50 of the
  run's per-object entries as "Who, What, Target", then "and N more". `get_rows` fetches these for
  the page's run ids in one query.
  Empty states: "Nothing has been recorded for this organisation yet." and, with filters applied,
  "No entries match these filters." with spec 2's clear-all link.
- Every queryset is filtered to the request's organisation; the learner and cohort pages already
  are, through their instance.
- `interface_walk.py` and `test_config_authorisation.py` cover the new section through the
  exemption.

### Retention

`freedom_ls/audit_log/management/commands/prune_audit_log.py`:

- `--older-than DAYS`, defaulting to the `AUDIT_LOG_RETENTION_DAYS` setting (`Setting(default=None)`
  in `audit_log/config.py`). With neither, it exits with an error and deletes nothing.
- `--dry-run` prints the count it would delete.
- Deletes through `prune_before(cutoff)` in batches of 1,000 and prints the count deleted.
- Not called from `fls_run_housekeeping`. An operator schedules it.

## Testing

- **Model:** `save()` on an existing entry, `delete()`, and queryset `update()`, `delete()` and
  `bulk_update()` raise `AppendOnlyError` through `objects`, `unscoped` and `_base_manager`;
  `prune_before` deletes; `bulk_create` works.
- **Writer:** an unknown action raises `ValueError`; `site` comes from the target with no request,
  or from the argument; a null actor is allowed; `actor_label` and `target_label` survive deleting
  the actor and the target; `subjects` holds the target's key plus the extra subjects.
- **Registry:** an `AUDIT_LOG_EXTRA_ACTIONS` code is accepted by `record_entry`; a colliding or
  malformed code fails the system check; an unregistered code already in the table renders its code.
- **Writers:** one test per audit action code except the two summary codes, proving the action,
  actor, target, organisation, subjects and details, through one shared assertion helper. Per
  writer: a no-op writes nothing, and an action rolled back after the write leaves no entry.
  Removing an already-removed role writes nothing. A re-grant by another grantor writes a second
  `role.granted` with the new grantor as actor; by the same grantor, nothing. `add_learners`
  reactivating a learner into a cohort writes exactly one entry, and an active learner newly put
  in the cohort writes one `cohort_membership.added`. The four role utilities log `assigned_by=None`
  as a null actor; the two system-role utilities write nothing. `delete_role_rows_for` writes one
  `role.removed` per active assignment and none for inactive ones, with `role_label` falling back to
  the code for a retired role; deleting a cohort through the action records its roles as removed by
  the deleter, with the reason, before `cohort.deleted`.
- **Reason:** a reason typed into each of the eight dialogs reaches the entry, including the cohort
  delete; over 500 characters returns 422 with the dialog re-rendered.
- **Bulk-run contract:** `record_run_summary` plus per-object entries with a shared `run_id`; the
  per-object entries show on the learner's History tab and not in the organisation log; the summary's
  disclosure lists them, capped at 50.
- **Readers:** newest first with a stable order across pages; a move shows on the learner and both
  cohorts; each date preset; the Who filter, with "System" excluding a deleted user's entries;
  labels containing HTML are escaped.
- **Permissions:** the matrix tests pass with the new row; a cohort admin sees no History tab and
  gets a 404 on the section; an organisation admin never sees another organisation's entries; a site
  admin sees each organisation's own.
- **Prune command:** dry run deletes nothing; deletes only entries older than the cutoff; refuses to
  run with no age.
- **Browser flow:** deactivate a learner with a reason, then see it on the learner's History tab and
  in the organisation log.
