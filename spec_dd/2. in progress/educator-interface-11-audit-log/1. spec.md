# Spec: Audit log

Spec 11 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Source: `idea.md`. Research beside it: `research_codebase.md` (the full action inventory
with file and line for each write point), `research_best_practices.md`,
`research_reference_implementations.md`, `research_prior_art.md`, `research_ux_patterns.md`,
`research_known_complaints.md`.

## Purpose

Organisation admins can now deactivate learners, move memberships, unregister cohorts and remove
roles from a screen, and nothing records who did it. This spec adds one append-only record of every
such action, written by the role utilities and every educator interface action, and shows it on the
learner page, the cohort page and an organisation-level log.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `AuditLogEntry` | coined | One row of the audit log: an actor did an action to a target in an organisation. No existing model records actions. |
| audit action | coined | A registered `noun.verb` string naming what an entry records, such as `learner.deactivated`. Distinct from a panel action (`PanelAction`), which is the UI control that performs it. |
| subject key | coined | `"<app_label>.<model_name>:<pk>"`, the string an entry stores for each object it should appear in the history of. |
| bulk run | coined | One execution of a bulk action or a CSV import commit (spec 8). Its entries share a `run_id`. |

## Scope

In:

- A new app, `freedom_ls/audit_log`, holding the `AuditLogEntry` model, the writer, the audit
  action registry, a read-only admin and a prune command.
- Entries written by the object-role and site-role utilities and by every action in specs 6, 7 and
  9, with an `actor` passed down to the service functions that lack one.
- The writer contract spec 8 calls for bulk runs and import commits.
- An optional reason on removals and deactivations, entered in the confirm dialog.
- A History tab on the learner page and the cohort page, and an organisation-level Audit log section.
- A `view_auditlogentry` capability for `site_admin` and `organisation_admin`.

Out:

- Field-level change tracking, undo, restoring from the log.
- Anything learner-facing.
- Login and authentication events (`django-axes` and allauth record those).
- Webhook deliveries and report generations; `WebhookDelivery` and the report models are their
  own record.
- System-role changes (`assign_system_role`, `remove_system_role`): `SystemRoleAssignment` has no
  site and is never changed from the educator interface. Their two `# TODO: AuditLog entry`
  comments stay.
- Changes made by editing models directly in the Django admin, which bypass the service functions.
- A backfill of past actions. History starts at the upgrade.
- A CSV export of the log (see Open questions).
- Database-level immutability (triggers, revoked privileges). Append-only holds against application
  code only, and the docs say so.

## Decisions

1. **A new app, not `role_based_permissions` or `learner_management`.** `learner_management` imports
   `role_based_permissions`, so the role utilities can't import a model there. Putting it in
   `role_based_permissions` would make that generic app depend on `organisations`.
2. **An entry is findable through `subjects`, a list of subject keys with a GIN index.** A move
   names a learner and two cohorts, and must show on all three pages. A single generic target can't
   do that. Searching `details` can't use an index.
3. **A bulk run writes a normal entry per changed object and one summary entry, all sharing a
   `run_id`.** Learner and cohort history then show what a bulk run did to them. The organisation
   log shows the summary and hides the run's per-object entries, so a 500-row run is one row there.
4. **Write only when state changed.** A removal that removed nothing, or a grant that already held,
   writes no entry. A refused or rolled-back action writes none, because the write sits inside the
   action's `transaction.atomic()`.
5. **Raw role-utility calls with no actor are logged, as "System".** Fixtures, QA commands and the
   Django admin's role edits call the utilities with `assigned_by=None`. Recording them is the honest
   answer to "who did this".
6. **The actor and target labels are stored at write time and kept after the user is deleted.**
   `actor` is `SET_NULL`; `actor_label` keeps the name. Nothing rewrites a label on erasure; the
   security doc states this.
7. **Audit action codes are `noun.verb` strings validated by a registry, with no `choices=`.** A
   downstream project adds codes through a setting without a migration. Labels render at read time,
   so wording can change without touching data.
8. **The date filter is a preset choice filter**, built on `ChoiceFilter`, so spec 2's table
   framework gains no new widget.
9. **Spec 8 lands either side of this spec.** Whichever lands second wires spec 8's bulk actions and
   import commit to the writer's bulk-run contract.

## Requirements

### `audit_log` app

New app `freedom_ls/audit_log`: label `freedom_ls_audit_log`, `verbose_name="Audit log"`, added to
`INSTALLED_APPS` in `config/settings_base.py`, following `docs/app_conventions.md`. It depends on
`accounts`, `base`, `organisations` and `site_aware_models` only. `docs/app_structure.md` and
`test_organisation/import_contracts.toml` regenerate through `/ds:app_map`.

### `AuditLogEntry` model

`freedom_ls/audit_log/models.py`, `AuditLogEntry(SiteAwareModel)`:

| Field | Type | Notes |
| --- | --- | --- |
| `created_at` | `DateTimeField(default=timezone.now)` | Time of the action, UTC. |
| `organisation` | FK `freedom_ls_organisations.Organisation`, `null=True`, `on_delete=PROTECT`, `related_name="+"` | Null for site-role entries. `PROTECT` matches `Learner` and `Cohort`: an organisation with history isn't deleted. |
| `actor` | FK `AUTH_USER_MODEL`, `null=True`, `on_delete=SET_NULL`, `related_name="+"` | Null for a system action, or once the user is deleted. |
| `actor_label` | `CharField(max_length=255, blank=True)` | `actor.display_name` at write time; empty for a system action. |
| `action` | `CharField(max_length=100)` | A registered audit action code. |
| `target_content_type` | FK `ContentType`, `on_delete=PROTECT` | With `target_object_id`, a `GenericForeignKey` `target`. |
| `target_object_id` | `CharField(max_length=255)` | Open set, per `docs/app_conventions.md`. |
| `target_label` | `CharField(max_length=255)` | Reads after the target is gone. |
| `subjects` | `ArrayField(CharField(max_length=300))` | Subject keys, always including the target's. |
| `reason` | `CharField(max_length=500, blank=True)` | Optional, stripped. |
| `details` | `JSONField(default=dict, blank=True)` | Ids, labels, counts. Never tokens, links or email addresses beyond the labels. |
| `run_id` | `UUIDField(null=True, blank=True)` | Set on every entry of a bulk run. |

Meta: `ordering = ("-created_at", "-id")`; indexes on `(organisation, -created_at)`, `run_id`, and
a `GinIndex` on `subjects`. The model's default `view_auditlogentry` permission is the capability;
no `Meta.permissions`.

Append-only, three layers:

- An `AuditLogEntryQuerySet` composed with the site-aware queryset whose `update()`, `delete()` and
  `bulk_update()` raise `AppendOnlyError` (new, in `audit_log/exceptions.py`). `bulk_create()` and
  `create()` work. One named method, `prune_before(cutoff)`, is the only delete path, used by the
  prune command.
- `save()` raises `AppendOnlyError` on a row that isn't being added; `delete()` raises always.
- A read-only admin (below).

### Writer

`freedom_ls/audit_log/writer.py`:

```python
def record_entry(
    *,
    action: str,
    actor: User | None,
    target: Model,
    target_label: str,
    organisation: Organisation | None,
    subjects: Iterable[Model] = (),
    reason: str = "",
    details: Mapping[str, JSONValue] | None = None,
    run_id: UUID | None = None,
) -> AuditLogEntry: ...
```

- Raises `ValueError` for an unregistered `action`, as `webhooks.registry.validate_event_type` does.
- Takes `site` from the target (`site_of`), never from the request, so it works in a background
  task or a management command. Reads and writes through `_base_manager`.
- Builds `subjects` from `target` plus every object in `subjects`.
- Fills `actor_label` from `actor.display_name`.
- Callers pass `target_label`: `user.display_name` for a learner or a user, `cohort.name` for a
  cohort. `Learner.__str__` includes the organisation, so it is not the label.
- Runs no `transaction.atomic()` and no `on_commit`; the caller's transaction holds it. Not wrapped
  in a `try`.

`record_run_summary(...)`, same module, writes the summary entry of a bulk run. It takes the
`run_id`, the `organisation`, the actor, the reason and a `details` dict with the run's counts by
outcome (`changed`, `skipped`, `failed`) and up to 50 skipped or failed rows as
`{"label": str, "outcome": str}`, plus `truncated: bool`. Its target is the organisation. A bulk
run's per-object entries carry the same `run_id` and the same reason.

### Audit action registry

`freedom_ls/audit_log/actions.py` defines `AuditAction(code, label, describe)`, where `describe` is
an optional `Callable[[AuditLogEntry], str]` that renders the details line, and
`FLS_AUDIT_ACTIONS`. `freedom_ls/audit_log/config.py` adds `AUDIT_LOG_EXTRA_ACTIONS:
Setting(default={})`, a `{code: label}` dict a downstream project fills. `get_audit_action(code)`
returns the registered action, or a fallback whose label is the code itself so an entry from a
removed setting still renders. A system check fails (`freedom_ls_audit_log.E001`) when an extra code
collides with an FLS code or isn't `noun.verb`.

FLS codes, with the labels the UI and product docs use:

| Code | Label | Target | Other subjects | `details` |
| --- | --- | --- | --- | --- |
| `learner.added` | Learner added | learner | cohort, if one was given | `outcome` (`created`, `joined`, `reactivated`) |
| `learner.renamed` | Learner renamed | learner | | `old`, `new` |
| `learner.deactivated` | Learner deactivated | learner | | |
| `learner.reactivated` | Learner reactivated | learner | | |
| `learner.setup_email_resent` | Setup email resent | learner | | |
| `membership.added` | Added to cohort | learner | cohort | `cohort` label |
| `membership.removed` | Removed from cohort | learner | cohort | `cohort` label |
| `membership.moved` | Moved between cohorts | learner | both cohorts | `source`, `destination` labels, `move_id` |
| `registration.added` | Registered for course | learner | | `course` label |
| `registration.reactivated` | Registration reactivated | learner | | `course` label |
| `registration.deactivated` | Registration deactivated | learner | | `course` label |
| `cohort.created` | Cohort created | cohort | | |
| `cohort.renamed` | Cohort renamed | cohort | | `old`, `new` |
| `cohort.deactivated` | Cohort deactivated | cohort | | |
| `cohort.reactivated` | Cohort reactivated | cohort | | |
| `cohort.deleted` | Cohort deleted | cohort | | |
| `cohort_registration.added` | Cohort registered for course | cohort | | `course` label |
| `cohort_registration.reactivated` | Cohort registration reactivated | cohort | | `course` label |
| `cohort_registration.deactivated` | Cohort registration deactivated | cohort | | `course` label |
| `role.granted` | Role granted | user | the role's target object | `role` code, `scope` label |
| `role.removed` | Role removed | user | the role's target object | `role` code, `scope` label |
| `member.suspended` | Member suspended | user | | |

| `bulk_action.completed` | Bulk action completed | organisation | | run summary, plus `bulk_action` (the per-object code) |

`role.granted` and `role.removed` render the role's `display_name` from `get_role_config`, not a
copied string. `bulk_action.completed` and `import.committed` are the summary actions the
organisation log keeps when it hides a run's per-object entries.

### Writers in the educator interface actions

Every action in the inventory in `research_codebase.md` section 4 writes the entry its row in the
registry table names, inside the action's transaction, only when state changed.

- `learner_management/learner_actions.py` (`deactivate_learner`, `reactivate_learner`,
  `add_to_cohort`, `remove_from_cohort`, `move_between_cohorts`, `register_for_course`,
  `unregister_from_course`, `add_learners`) and `learner_management/utils.py`
  (`register_cohort_for_course`, `unregister_cohort_from_course`) gain keyword-only
  `actor: User | None = None` and `reason: str = ""`, and write the entry themselves.
  `register_cohort_for_course` and `unregister_cohort_from_course` gain a `transaction.atomic()`.
  Callers in `educator_interface/actions.py` pass `ctx.request.user`; `qa_helpers` callers pass
  nothing.
- `learner_management/role_assignment.py` `set_organisation_member_active` writes
  `member.suspended` or `member.reactivated`.
- Actions with no service function (`CreateCohortAction`, `EditCohortAction`,
  `EditLearnerNameAction`, `CohortStateAction` and its two subclasses, `DeleteEmptyCohortAction`,
  `ResendSetupEmailAction`) write from the panel action, with the save and the entry in one
  `transaction.atomic()`. `cohort.renamed` and `learner.renamed` are written only when
  `form.changed_data` is non-empty. `cohort.deleted` is written before the delete, with the
  cohort's name as the label.
- Multi-object single actions (`AddLearnersAction`, `AddExistingLearnersAction`,
  `ChangeCohortsAction`, `AddMemberAction`) write one entry per changed object and no summary. They
  are not bulk runs.

### Reason in the confirm dialog

The confirm dialogs of `DeactivateLearnerAction`, `RemoveFromCohortAction`,
`UnregisterLearnerFromCourseAction`, `UnregisterCohortFromCourseAction`, `DeactivateCohortAction`,
`DeleteEmptyCohortAction`, `RemoveRoleAction` and `SuspendMemberAction` gain an optional single-line
"Reason (optional)" input, max 500 characters, with the help text "Only staff can see this. It is
shown in the history." A reason over 500 characters returns 422 with the dialog re-rendered and the
error on the field. An empty reason is stored as `""`. The reason reaches the entry through the
service function's `reason` argument. Spec 8's bulk confirmation (`bulk_confirmation.html`) takes the
same input once for the whole run.

### Readers

One table, `AuditLogEntryTable(DataTable)` in `educator_interface/views.py` (or a module beside it),
used by all three views. Columns: When (absolute date and time in the site's time zone, a `<time
datetime>` element), Who (`actor_label`, or "System" when the entry has no actor), What (the audit
action label), Target (`target_label`; org log only), Details (the action's `describe` line, then the
reason on its own line when present). Mobile cards: What and Target primary, When and Who secondary.
`page_size = 25`. No bulk actions, no search, no sort controls; the order is the model's.

- **Learner page.** `LearnerHistoryPanel` (`educator_interface/views.py:695`) becomes a
  `DataTablePanel` over entries whose `subjects` contain the learner's subject key, with
  `capability = "freedom_ls_audit_log.view_auditlogentry"`. It keeps `refresh_events =
  (LEARNER_CHANGED,)`. Empty state: "No history for this learner yet. Actions such as moving or
  deactivating them are recorded here."
- **Cohort page.** `CohortTabSet` (`views.py:963`) gains `"history": CohortHistoryPanel`, the same
  shape over the cohort's subject key, refreshing on `COHORT_CHANGED`. Empty state: "No history for
  this cohort yet. Actions such as adding learners or registering it for a course are recorded here."
- **Organisation log.** `AuditLogConfig(OrganisationSectionConfig, ListViewConfig)`, title "Audit
  log", under the Administration nav group beside `MemberConfig`, with `view_capability` set to the
  capability and a `check_access_exempt_reason` (entries have no instance pages). Its queryset is the
  organisation's entries, excluding entries with a `run_id` whose action is not a summary action.
  Filters:
  - Who: actors appearing in this organisation's entries, plus "System".
  - What: multi-select over the registered audit actions.
  - When: presets Today, Last 7 days, Last 30 days, Last 90 days, Last 12 months, interpreted in the
    site's time zone. No default window.
  A summary row's Details holds a `<details>` disclosure, "Show N entries", listing up to 50 of the
  run's per-object entries as "Who, What, Target", then "and N more" when there are more.
  Empty states: "Nothing has been recorded for this organisation yet." and, with filters applied,
  "No entries match these filters." with spec 2's clear-all link.
- Site-role entries (no organisation) are visible in the Django admin only.
- Every queryset is filtered to the request's organisation; the learner and cohort pages already
  are, through their instance.
- `interface_walk.py` and `test_config_authorisation.py` cover the new section through the
  exemption.

### Retention

`freedom_ls/audit_log/management/commands/prune_audit_log.py`:

- `--older-than DAYS`, defaulting to the `AUDIT_LOG_RETENTION_DAYS` setting (`Setting(default=None)`
  in `audit_log/config.py`). With neither, it exits with an error and deletes nothing.
- `--dry-run` prints the count it would delete.
- Deletes through `prune_before(cutoff)` in batches of 1,000 and prints the count deleted.
- Not called from `fls_run_housekeeping`. An operator schedules it.

## Testing

- **Model:** `save()` on an existing entry, `delete()`, and queryset `update()`, `delete()` and
  `bulk_update()` raise `AppendOnlyError`; `prune_before` deletes; `bulk_create` works.
- **Writer:** an unknown action raises `ValueError`; `site` comes from the target with no request;
  a null actor is allowed; `actor_label` and `target_label` survive deleting the actor and the
  target; `subjects` holds the target's key plus the extra subjects.
- **Registry:** an `AUDIT_LOG_EXTRA_ACTIONS` code is accepted by `record_entry`; a colliding or
  malformed code fails the system check; an unregistered code already in the table renders its code.
- **Writers:** one test per audit action code proving the right action, actor, target, organisation,
  subjects and details. One shared assertion helper. A test per writer that a no-op change writes
  nothing and that an action rolled back after the write leaves no entry. The four role utilities
  log with `assigned_by=None` as a null actor; the two system-role utilities write nothing.
- **Reason:** a reason typed into each of the eight dialogs reaches the entry; over 500 characters
  returns 422.
- **Bulk-run contract:** `record_run_summary` plus per-object entries with a shared `run_id`; the
  per-object entries show on the learner's History tab and not in the organisation log; the summary's
  disclosure lists them, capped at 50.
- **Readers:** newest first with a stable order across pages; a move shows on the learner and both
  cohorts; each date preset and the Who filter including "System"; labels containing HTML are escaped.
- **Permissions:** the matrix tests pass with the new row; a cohort admin sees no History tab and
  gets a 404 on the section; an organisation admin never sees another organisation's entries; a site
  admin sees each organisation's own.
- **Prune command:** dry run deletes nothing; deletes only entries older than the cutoff; refuses to
  run with no age.
- **Browser flow:** deactivate a learner with a reason, then see it on the learner's History tab and
  in the organisation log.

## Success criteria

- Every audit action code in the registry table has a writer and a passing test.
- `grep -n "TODO: AuditLog" freedom_ls/role_based_permissions/utils.py` finds only the two
  system-role lines.
- No code path outside `prune_before` can update or delete an `AuditLogEntry`, and tests prove it.
- An organisation admin sees History tabs on learner and cohort pages and the Audit log section;
  a cohort admin sees neither.
- A membership move appears on the learner's and both cohorts' History tabs.
- `prune_audit_log --older-than 30 --dry-run` reports a count and deletes nothing.
- `uv run manage.py makemigrations --check` is clean and the import contracts pass.
