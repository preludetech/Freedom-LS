# Implementation plan: learner dashboard small fixes

Two changes, both confined to `freedom_ls/learner_interface/views.py` and its tests.

1. A `Course` whose `visibility` is `CourseVisibility.COMING_SOON` and whose `dashboard_category`
   is a `CourseCategory` with `show_on_dashboard=True` renders in **both** that category's section
   and **Coming soon**.
2. **Recommended courses** and **Coming soon** get the **Browse all courses** button that every
   category section and **Available courses** already has.

No model fields, no migrations, no new URLs, no template changes, no new settings.

## What already exists — reuse, don't rebuild

Read these before writing anything. Each one is machinery the change leans on rather than repeats.

- `_coming_soon_split` (`views.py:291-305`, renamed in 1.2) is the **single** place the discovery
  pool is divided, and the single place `override_visibility_to_visible()` is consulted for section
  assembly. Both render paths — the full page (`_dashboard_sections`) and the htmx single-section swap
  (`_requested_section`) — consume the `coming_soon` / `rest` querysets it produced once per
  request via `_dashboard_inputs`. Change the pool here and both paths change together. Do not add
  a second visibility check anywhere downstream.
- `Course.Meta.ordering = ["title", "pk"]` (`freedom_ls/content_engine/models/courses.py:145`)
  already gives every derived queryset alphabetical-by-title order. Interleaving comes free
  **provided the widened pool stays one queryset**. Concatenating two lists in Python would group
  the coming-soon courses at one end and is wrong.
- `page_for` and `SECTION_PAGE_SIZE` (`dashboard_sections.py:25,120-145`) already page each section
  independently off its own `page_<slug>` parameter. One course legitimately sitting on page 1 of
  Coming soon and page 2 of its category section needs no new code.
- `course_list.html:39` already guards the Browse all courses button on
  `{% if section.browse_all_url %}`. Task 2 is a view change only — do not touch the template.
- `_annotate_discovery_courses` (`views.py:308-323`) already stamps the access badge and
  `listing_status` for every discovery section including Coming soon. The card
  (`course_card.html`) branches on `listing_status`, so a coming-soon card carries its own
  "Coming soon" eyebrow and no enrol control wherever it renders. No per-course interest lookup,
  no new annotation, no card change is needed for the second placement.
- `Q` and `reverse` are already imported in `views.py` (lines 10, 20).

### 1.2 Change the pool

One expression in `_coming_soon_split` (`views.py:291-305`), plus a rename. Parameter and return
annotations stay exactly as they are, and the override branch is untouched; only the second element
of the returned tuple changes, so it keeps coming-soon courses whose dashboard category is shown:

```python
def _discovery_pools(
    courses: QuerySet[Course],
) -> tuple[QuerySet[Course], QuerySet[Course]]:
    if override_visibility_to_visible():
        return courses.none(), courses
    is_coming_soon = Q(visibility=CourseVisibility.COMING_SOON)
    has_shown_category = Q(dashboard_category__show_on_dashboard=True)
    return (
        courses.filter(is_coming_soon),
        courses.filter(~is_coming_soon | has_shown_category),
    )
```

The two named `Q` objects are there so `CourseVisibility.COMING_SOON` is spelled once and the second
line reads as the rule it is: not coming soon, or in a shown category.

**Rename `_coming_soon_split` to `_discovery_pools`.** The two querysets it returns now overlap
deliberately, so a name promising a split is false. `_dashboard_inputs` (`views.py:473`) is the only
call site. Keep the `coming_soon` and `rest` names on `_DashboardInputs` and on every section
builder's parameter — read as "the pool the rest of the sections draw from", `rest` is still
accurate, and the field is threaded through six call sites for no gain. Do **not** rename it to
anything built on "catalogue": in this product the catalogue is the all-courses page a Browse all
courses button leads to, and reusing the word for a dashboard pool would be a genuine collision.

Do not use `.exclude(visibility=..., dashboard_category__show_on_dashboard=False)` instead. Django
ANDs an `exclude()`'s keyword arguments and negates the group, which handles the no-category case
differently across the outer join.

Why this shape rather than widening `_category_section` itself:

- **The category section needs no change.** `rest.filter(dashboard_category=category)` picks the
  coming-soon course up automatically, and every caller of `_category_section` already guarantees
  the category is shown — `_dashboard_sections` iterates
  `CourseCategory.objects.filter(show_on_dashboard=True)` and `_requested_section` uses
  `get_object_or_404(CourseCategory, slug=slug, show_on_dashboard=True)`.
- **Available courses is safe by construction, not by a second filter.** Its catch-all is
  `Q(dashboard_category__isnull=True) | Q(dashboard_category__show_on_dashboard=False)`. Every
  coming-soon course now in `rest` has a non-null, shown category, so none of them can match.
  A coming-soon course with no category, or with a hidden one, never enters `rest` at all — it
  stays in the `coming_soon` half only. No course renders three times.
- **Coming soon stays a complete roll-up.** The first half of the tuple is unchanged, so every
  coming-soon course is still in it whatever its category.
- **The visibility preview is untouched.** The override branch returns before the new expression is
  reached.
- **Ordering is inherited.** One `.filter()` on one queryset, so `Course.Meta.ordering` still
  applies and the coming-soon courses take their alphabetical places.

The SQL this compiles to was checked against the real schema:

```sql
... LEFT OUTER JOIN coursecategory ON (course.dashboard_category_id = coursecategory.id)
WHERE (NOT (course.visibility = coming_soon) OR coursecategory.show_on_dashboard)
ORDER BY course.title ASC, course.id ASC
```

`visibility` is non-nullable, so `~Q(...)` stays a plain `NOT (...)` with no null-guard subquery.
Putting `dashboard_category__show_on_dashboard` on the OR side promotes the join to LEFT OUTER, so a
published course with no dashboard category still matches on the first clause, while a coming-soon
course with no dashboard category gets `FALSE OR NULL` and is excluded. The join is a foreign key,
one row per course, so no `.distinct()` is needed. `ORDER BY title, id` survives, which is the
alphabetical interleave.

### 2.2 Pass the URL

`reverse("learner_interface:courses")` would be spelled out four times in `views.py` after this
change. Extract it once and call it from all four section builders:

```python
def _browse_all_url() -> str:
    """The catalogue link behind every Browse all courses button.

    Unparameterised: a section's button lands on the whole catalogue, not on
    that section's own slice of it.
    """
    return reverse("learner_interface:courses")
```

Then:

- `_category_section` (`views.py:379`) and `_available_section` (`views.py:408`): replace the inline
  `reverse(...)` with `_browse_all_url()`.
- `_recommended_section` (`views.py:346-358`): add `browse_all_url=_browse_all_url()` to the
  `DashboardSection(...)` call.
- `_coming_soon_section` (`views.py:412-424`): the same.

`_in_progress_section` and `_history_section` stay as they are, leaving `browse_all_url` at its `""`
default so the template guard suppresses the button. Do not give `DashboardSection.browse_all_url` a
non-empty default — those two sections rely on the empty one.
