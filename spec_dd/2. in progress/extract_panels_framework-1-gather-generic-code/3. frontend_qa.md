# Frontend QA: generic panel code gathered into the framework

Checks in a browser that the educator interface still works after its dialogs, notices, tables,
lists and sidebar moved onto framework shapes, and that learners see no change. Wording is meant
to be the same as before; what changed on purpose is listed in each test under "Expect".

## Setup

1. Build the stylesheet: `npm run tailwind_build`.
2. Start the server on a free port: `uv run python manage.py runserver $PORT`. Base URL:
   `http://127.0.0.1:$PORT`.
3. Log in at `http://127.0.0.1:$PORT/accounts/login/` with the QA login from
   `.claude/sdd/config.md` (`## QA Login`). That user is a site admin and an organisation admin of
   the dev organisation.
4. Open `http://127.0.0.1:$PORT/educator/` and note the organisation slug in the URL
   (`/educator/organisations/<slug>/...`). Every educator URL below uses that `<slug>`:
   - Dashboard: `/educator/organisations/<slug>/`
   - Learners: `/educator/organisations/<slug>/learners/`
   - Cohorts: `/educator/organisations/<slug>/cohorts/`
   - Staff, audit log (History): from the sidebar
5. Data, on the site being browsed and in that organisation. Ask the QA data helper for whatever
   is missing; the existing commands `qa_create_educator_interface_seed`,
   `qa_create_cohort_administration_scenario`, `qa_create_learner_administration_scenario`,
   `qa_create_staff_administration_scenario`, `qa_create_bulk_operations_scenario`,
   `qa_create_report_cohort` and `qa_create_audit_log_history` cover most of it.
   - an active cohort with at least 3 learners and 2 course registrations ("QA cohort A")
   - a second active cohort ("QA cohort B") and one inactive cohort
   - an empty active cohort (no learners, no registrations)
   - a learner with an active course registration, one inactive registration and a quiz attempt
   - a learner whose account is not set up yet (pending), and one whose account is set up
   - a deactivated learner
   - a second staff member with a role limited to one cohort
   - more than 25 active learners, so the learners table pages
   - audit log entries older and newer than 7 days
   - a learner who has a conversation with another user (for oversight)
6. A learner login registered on a course with several topics, for Test 12.

Viewports: 1920 (desktop), 768 (tablet) and 375 (phone). "No sideways scroll" means
`document.documentElement.scrollWidth <= window.innerWidth` after layout settles.

Keep the browser console open for every test. A missing Alpine component (`sidePanel`,
`refreshTimer`, `eventRefresh`) or a CSP-build Alpine error shows there and nowhere else. Any
console error fails the test it appears in.

## Test 1: a confirm dialog with a reason (deactivate a cohort)

1. Open QA cohort A's page at 1920 and click "Deactivate" (Settings tab if it is not in the header).
2. Expect a dialog titled "Deactivate QA cohort A?", body paragraphs about learners keeping
   progress and registrations stopping access, a "Reason (optional)" field with the help text
   "Only staff can see this. It is shown in the history.", then a footer with "Cancel" at the left
   and one "Deactivate" button at the right.
3. Expect keyboard focus on "Cancel" when the dialog opens.
4. Expect the body text at the base size: the same size as the field label, not smaller.
5. Type "QA test reason" in the reason field, then click the footer's "Cancel". Expect the dialog
   to close at once, with no "Discard changes?" prompt.
6. Open it again, type a reason, then click the header's close (×). Expect the prompt "Discard
   changes?" with "The changes you made haven't been saved.", "Keep editing" at the left and
   "Discard" at the right. Click "Keep editing": the dialog returns with the typed reason. Press
   Esc: the prompt shows again. Click "Discard": the dialog closes.
7. Open it again, paste a reason longer than 500 characters and submit. Expect the dialog to stay
   open with an error on the reason field, and the cohort still active.
8. Submit with a short reason. Expect the button to read "Deactivating…" while it works, then the
   page to reload showing the cohort as inactive.
9. Open the cohort's History. Expect the deactivation entry to show the reason.
10. Repeat steps 1-4 at 375. Expect the dialog as a bottom sheet, the footer in view, the close
    control at least 44px square, and no sideways scroll.

## Test 2: confirm dialogs without a reason, and their tones

1. On the inactive cohort, click "Reactivate". Expect a dialog titled "Reactivate <cohort>?" with
   no reason field, "Cancel" focused, one "Reactivate" button. Confirm. Expect "Reactivating…"
   then the cohort active.
2. On a learner's page, open "Deactivate", then cancel; on the deactivated learner open
   "Reactivate" and confirm. Expect each dialog to have a title, body, Cancel and one confirm
   button, and the learner's state to change.
3. On the pending learner, click "Resend setup email". Expect a confirm dialog; confirm it. Expect
   the dialog to close and no error.
4. On a learner's Registrations panel, use the row actions to deactivate the active registration
   (reason field present) and reactivate the inactive one (no reason field). Expect each to act on
   the row it was opened from.
5. On QA cohort A's learner list, use a row's "Remove from cohort". Expect the confirm button in
   the error (red) style. Cancel.
6. On the Staff page, open "Deactivate" for the second staff member, and "Deactivate role" for
   their role. Expect confirm dialogs with a reason field. Cancel both.
7. For every dialog above expect: the Deactivate and Reactivate buttons in the primary style, the
   Remove and Delete buttons in the error style, and a loading text ending in "…" (one character,
   not three dots).

## Test 3: refusal dialogs have a title, a message and a Close button

Each refusal comes from a stale page: open the dialog in one tab, make the change in a second tab,
then submit in the first.

1. Cohort already inactive: open "Deactivate" on an active cohort in tab 1; deactivate it in tab 2;
   submit in tab 1. Expect a dialog titled "<cohort> is inactive" saying the change was not made,
   with one "Close" button, focused. Click it: the dialog closes.
2. Cohort already active: the same with "Reactivate" on an inactive cohort. Expect a titled
   message and "Close".
3. Learner already in state: the same with a learner's "Deactivate".
4. Account already set up: on the set-up learner, request the resend through a stale tab (open the
   dialog while the learner is pending is not possible here, so use the pending learner, set their
   password in tab 2 through the setup link, then submit in tab 1). Expect a titled message and
   "Close". If this cannot be staged, record it as not run.
5. Setup email recently sent: on the pending learner, confirm "Resend setup email" twice in quick
   succession. Expect the second to answer with a titled message and "Close".
6. Staff change refused: on the Staff page, try to deactivate your own account, or remove your own
   last admin role. Expect a refusal dialog with a "Close" button in a footer, not inside the body.
7. For each: expect no form, no Cancel, exactly one Close, and the page behind unchanged.

## Test 4: delete a cohort

1. Open the empty cohort and click "Delete". Expect a dialog titled "Delete <cohort>" saying it
   cannot be undone, a reason field, "Cancel" focused, and one red "Delete" button.
2. Open QA cohort A (not empty). Expect either no Delete action, or a dialog that explains why it
   cannot be deleted and offers no Delete button.
3. Stale case: open Delete on the empty cohort in tab 1, add a learner to it in tab 2, submit in
   tab 1. Expect the dialog to stay open with an error box naming why, focus on that box, and the
   cohort still there.
4. Delete the empty cohort (remove the learner first). Expect "Deleting…", then the cohorts list
   without it.

## Test 5: the multi-step dialogs

1. Move a learner: on QA cohort A's learner list, click a row's "Move". Expect a cohort picker.
   With no cohort chosen, expect "Move" disabled and the sentence "Choose a cohort to move them
   to." beside it. Choose QA cohort B: "Move" enables. Cancel.
2. Stale move: open "Move" for a learner in tab 1, remove that learner from the cohort in tab 2,
   submit in tab 1. Expect a refusal dialog with a title, a message and "Close".
3. Add staff member: open "Add staff member". Submit an empty email. Expect an error summary at
   the top that takes focus and counts the fields to fix. Enter the second staff member's email
   and continue. Expect the role step with a cohort checklist. Cancel from the footer after
   typing: no discard prompt.
4. Change cohorts: on the second staff member's cohort-limited role, open "Change cohorts". Expect
   the same cohort checklist layout as step 3. Submit without changing anything. Expect a refusal
   saying nothing changed, with "Close".
5. Add learner: open "Add learner" on the learners page, add a new email, and expect the result
   dialog with a "Close" or continue footer and no button group.
6. Conversation oversight: on the learner with a conversation, open the conversation from the
   Messages panel. Expect the thread in a dialog that ends in a footer with "Close".
7. Add to cohort (picker): on a learner's page click "Add to cohort". Expect a form dialog with a
   cohort select. Change the select: the dialog re-renders without an error. Submit with nothing
   chosen: a 422 re-render with the error summary. Choose a cohort and submit: the learner joins.
8. Register for a course: on QA cohort A, open "Register for a course", pick a course. Expect the
   dialog to re-render showing what the choice means, then submit. Expect the registration listed.

## Test 6: the quick view's close control and discard prompt

1. On the learners table at 1920, click a learner's quick-view button. Expect the quick view to
   open beside the table, with a close control the same size as a dialog's (44px).
2. Close it with the control. Expect focus back on the button that opened it.
3. Open the Messages composer from the header's messages button (or a learner's "Message" action,
   whichever opens in the quick view). Type a message, then press Esc. Expect the prompt
   "Discard your message?" with the composer's own body sentence, "Keep editing" and "Discard".
   "Keep editing" returns to the draft; "Discard" closes.
4. At 375, open a learner's quick view. Expect it full width with the close control reachable and
   no sideways scroll.

## Test 7: bulk actions

1. On the learners table, tick 3 learners and click "Deactivate". Expect a confirmation dialog
   with the sentence, any skip lines, "Cancel" and "Deactivate". Cancel.
2. Tick one pending and one set-up learner and choose "Resend setup email" under More. Expect the
   sentence "Resend the setup email to 1 learner." and the line "1 learner is already set up and
   will be skipped." Confirm. Expect a result dialog with a "Close" button.
3. Tick only set-up learners and choose "Resend setup email". Expect the confirm button disabled,
   with the reason shown beside it.
4. If a selection produces a notice (for example the selection changed since the dialog opened),
   expect it in an amber warning box, not a red one.
5. JavaScript off: disable JavaScript, tick 2 learners and submit "Deactivate" from the bar's
   fallback. Expect the learners page with the confirmation open over it; both the close control
   and "Cancel" are links back to the learners page with the same query string. Re-enable
   JavaScript.
6. Start a bulk action over more than 25 learners (Select all). Expect it to run and finish with a
   result, and a notification for the finished run.
7. On the cohorts table, tick 2 cohorts. Expect the cohort bulk actions in the same order as
   before: Deactivate, Reactivate, Register for a course, then Deactivate a course registration.

## Test 8: filters

1. Cohorts table: expect inactive cohorts hidden. Toggle "Show inactive". Expect the URL to gain
   `inactive=1` and the inactive cohort to appear. Toggle it off: it goes.
2. History (audit log): open the "When" filter. Expect the options Today, Last 7 days, Last 30
   days, Last 90 days and Last 12 months (the same five as before). Choose "Last 7 days". Expect
   only entries from the last 7 calendar days, and the URL to carry `when=7d`.
3. Edit the URL to `when=bogus`. Expect the full list and no error page.
4. With a filter applied on a table, expect an applied-filter chip that removes the filter when
   clicked, and the search field, filter toggle, sort and Export CSV in the same places as before.
5. At 375, open the filter sheet from the toolbar. Expect it to open as a sheet with a close
   control, and to stay closed at 1920.

## Test 9: reports, the dashboard and lazy panels

1. Open the dashboard. Expect skeleton placeholders first, then the figures. Expect stat tiles
   that link somewhere to be one link each, and the attention list rows to show a person link with
   a quick-view button that opens the quick view.
2. Open QA cohort A's Reports tab. Expect the report body to load after a skeleton, with its two
   tables styled like the data tables (same header style), section headings in one style, and
   statuses as badges.
3. Generate a report download. Expect the downloads region to show the file in a table with the
   same header style, and an empty downloads list (before generating) to read as a compact empty
   state.
4. JavaScript off: load the cohort's Reports tab. Expect a link reading "Load the figures" where
   the body would be; following it shows the body. Re-enable JavaScript.
5. If a cohort larger than the report limit exists (or the limit can be lowered in dev settings),
   open its report. Expect the over-limit message in an amber warning notice and no table.
6. At 375, expect the report tables to scroll inside their own region or render as cards, with no
   sideways scroll of the page.

## Test 10: learner import pages

1. Open `/educator/organisations/<slug>/learners/import/`. Expect the format table styled like the
   other tables, and the upload button at the small size.
2. Upload a file with a wrong header. Expect the error in a red notice with `role="alert"`.
3. Upload a valid CSV of 30 rows with 2 invalid rows. Expect the preview: stat tiles that filter
   the rows when clicked (the selected tile marked as current), row statuses as badges, the table
   in the shared style, and the shared pager under it. At 375 expect cards, not a squeezed table.
4. Expect the error rows listed in a table in the shared style, inside an amber warning notice
   section. It is a warning, not an error: the other rows can still be imported, and an error
   notice is an alert that a screen reader would read out whole, table included.
5. Confirm the import. Expect the result page, with its action buttons at the small size and its
   list of outcomes as list rows.

## Test 11: instance pages, lists and people

1. Open a cohort page. Expect the details panel to show the status as a badge and dates in the
   usual format, the Settings tab's staff list as list rows with a name and, under a named person,
   their email, and section headings in one style.
2. Open a learner page. Expect the same for its details, the Registrations panel as list rows
   with row actions, the Courses panel with quiz attempts in a table in the shared style and
   Passed/Failed as badges.
3. Edit the cohort's name on its Settings tab and save. Expect the page title and the header to
   update without a full reload. Submit an empty name: expect an error notice.
4. On the cohorts table, expect the courses column as a list, the learner count and last-active
   columns filled, and "—" where a value is empty.
5. On the History table, expand a row. Expect a label/value list. For an entry whose user was
   deleted, expect a fallback icon in place of the avatar.
6. With the learners table open, add a learner through "Add learner". Expect the table to refresh
   by itself and keep the current search and filters.
7. Empty states: a cohort with no staff, a learner with no messages. Expect the compact empty
   state, not bare text.
8. At 375, check one cohort page and one learner page for sideways scroll, and that every button
   is at least 44px tall.

## Test 12: the sidebar, the header and learner pages

1. At 375 on the educator dashboard, open the sidebar from the header's menu button. Expect it to
   slide in; close it with its close control and again with Esc. Navigate with a sidebar link:
   the sidebar closes and the page changes.
2. At 1920, expect the sidebar docked, and its collapsed or expanded state remembered after a
   reload.
3. On any educator page, expect the header's messages button to show its count. Send a message to
   the QA user from another account (or the data helper): within a minute the count updates
   without a reload.
4. Log in as the learner. Open a course. At 375, open and close the course's table of contents
   from its toggle; at 1920 expect it docked. Expect the messages button and notification bell to
   work as before.
5. As the learner, open a topic and an activity. Expect no visual change from before and no
   console errors.
6. Open the component reference page if the dev URLs expose it. Expect an example of the notice in
   each tone, the static table, the list rows and the heading.

## Test 13: sweep for leftovers

1. On each of: dashboard, learners, a learner, cohorts, a cohort (each tab), Staff, History, the
   import pages: expect no unstyled or missing component (a literal `<c-...>` tag in the page
   source, an empty gap where a button was, or a raw `{{ ... }}`).
2. Open every action in each page's header and row menus once and close it with the footer's
   Cancel or Close. Expect each dialog to have a header with a close control, a body, and exactly
   one footer.
3. Tab through one confirm dialog and one form dialog with the keyboard. Expect focus to stay
   inside the dialog and return to the trigger when it closes.
