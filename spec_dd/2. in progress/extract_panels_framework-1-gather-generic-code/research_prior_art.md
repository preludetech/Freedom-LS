## Hazard found: `sidePanel` is used outside the framework

`sidePanel` is not only a framework toolbar helper. `freedom_ls/base/templates/_base_interface.html` (line 158, `x-data="sidePanel"`, the shared sidebar for all interfaces), `learner_interface/templates/learner_interface/_course_base.html` (comment line 93, in a sidePanel ancestor) and `content_engine/static/content_engine/js/alpine-components.js` (line 87 comment "Mirrors sidePanel") depend on it. `freedom_ls/base/templates/_base.html` lines 66-67 load only `base/js/alpine-components.js` and `comms/js/alpine-components.js` globally (CSP Alpine build, `defer`, line 71, plus an `extra_alpine_components` block). If `sidePanel` moves into `panel_framework/js/alpine-components.js`, every page that renders `_base_interface.html` (learner course pages included) must load the framework JS, or the sidebar breaks. Likewise `refreshTimer` moving out of `comms` means `_base.html` / comms partials (`messages_button.html`, `conversation_list.html`, `thread.html`) need the framework script; today `_base.html` loads comms JS for all pages. The spec must decide between: (a) load framework JS globally in `_base.html`, (b) keep `sidePanel` in `base` and have the framework's `table_toolbar` depend on the host to provide it (host contract, spec 4), or (c) move it and add the script to the shared base. This contradicts the idea's "confirm nothing else in `base` depends on `sidePanel`": something does.

## Elsewhere (general practice, not web-verified)

- Extracting an app from a monolith: move code first, keep tests passing before changing behaviour; do not rename and move in the same step (matches this effort's ordering with spec 5). Use `git mv` so history follows, and move tests with the code.
- Templates and static files are resolved by app-relative path (`app_directories` loader, `STATICFILES`, cotton by name). Moving a template file between apps does not break `{% include 'panel_framework/...' %}` only if template names are updated everywhere; Django has no alias. Cotton components resolve by filename across all apps' `templates/cotton/`, so a moved `modal-trigger.html` keeps its tag name but an old copy left in `base` would silently shadow or be shadowed depending on `INSTALLED_APPS` order: delete the old file in the same commit.
- Staticfiles: `collectstatic` manifest hashing and browser caches mean a moved JS file needs a rebuild; Tailwind content globs must include the new location (`npm run tailwind_build`) or utility classes in moved templates are purged.
- Alpine registration ordering: `Alpine.data(...)` must run in `alpine:init`, before Alpine starts, and with `<script defer>` the order of component scripts must precede the Alpine core script (here the CSP build at `_base.html` line 71, after the component scripts). A missing registration is silent under the CSP build apart from a console error, which is why the idea's check (every Alpine name used in framework templates is registered in the framework JS) is worth having. Also check that a component name registered in two files is not defined twice (last wins).
- Public-surface practice: `__all__` per module plus a test that imports every name a host uses (matches the answers already given).
