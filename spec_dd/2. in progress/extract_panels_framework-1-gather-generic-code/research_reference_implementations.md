## 1. Bulk actions and their registry

| System | Declaration | Keyed by | Source |
|---|---|---|---|
| Wagtail (verified) | Subclass `BulkAction` (or listing base for pages/images/documents/users/snippets); register with `@hooks.register("register_bulk_action")`. Attrs: `display_name`, `aria_label`, `action_type` (unique id, used in URL), `models`, `action_priority`, `classes`, `template_name`. | `models` list on the class; the registry is the hook list, filtered per listing | https://docs.wagtail.org/en/stable/extending/custom_bulk_actions.html ; code in `wagtail/admin/views/bulk_action/` and `wagtail/admin/admin_url_finder`/`wagtail/admin/ui/` (from knowledge) |
| Django admin (verified) | Function `(modeladmin, request, queryset)` with `@admin.action(description=, permissions=)`, listed in `ModelAdmin.actions`; site-wide via `AdminSite.add_action(fn, name)`; `get_actions()` overrides per request (6.1 returns `Action` objects, adds `location`) | per `ModelAdmin` (so per model); site-wide for all | https://docs.djangoproject.com/en/stable/ref/contrib/admin/actions/ |
| django-unfold (from knowledge) | Same `@action(description=, permissions=, url_path=)` decorator from `unfold.decorators`; `actions_list`, `actions_row`, `actions_detail`, `actions_submit_line` lists on `ModelAdmin` | per `ModelAdmin` | https://unfoldadmin.com/docs/actions/ (the `/actions/overview/` URL 404s) |
| django-import-export (from knowledge) | Not bulk actions; `ExportActionMixin` adds one "export selected" admin action that redirects to its own form view (format choice, field selection). | per `ModelAdmin` | https://django-import-export.readthedocs.io/en/latest/admin_integration.html |
| neapolitan (from knowledge) | No bulk actions. `CRUDView` subclass keyed by `model`, `fields`, `filterset_fields`; URLs generated by `CRUDView.get_urls()`. Declarative, one class per model. | per view class | https://github.com/carltongibson/neapolitan |

Takeaways for FLS (`register_bulk_action`, `bulk_actions_for_table`):
- Wagtail is the closest analogue: a class with a stable `action_type` id, a `models`/table key, a per-object permission check (`check_perm`, items split into with/without access, which matches `permitted` / `skip_reason`), a classmethod `execute_action(objects, **kwargs)` returning counts, `get_execution_context()` for the acting user, and `get_success_message(...)` (matches `sentence`). Its confirmation template is a base template with overridable blocks, with a shared `confirmation/form.html` partial. That is the pattern for a generic `consequences` template that hosts extend.
- Django admin keys by ModelAdmin and has site-wide `add_action`; permissions are model-level only and object-level checks go inside the action. FLS keying by table, not model, is the deviation; both Django and Wagtail document the key as a class attribute, not a call argument. Registration in both is explicit (decorator or list), not discovery by import side effect (Wagtail uses hooks, which are loaded from each app's `wagtail_hooks.py`).
- Both fail loudly on a duplicate id? Wagtail does not document this; worth a framework test that registering the same `(table, action_type)` twice raises.

## 2. Optional / required confirmation reasons

- Wagtail: no reason field. Confirmation is a template with a `form_section` block, so extra inputs are added by overriding the template and `get_context_data`. https://docs.wagtail.org/en/stable/extending/custom_bulk_actions.html
- Django admin: the documented pattern for extra input is "return a redirect to your own view with ids in the query string"; the built-in delete confirmation is the model. https://docs.djangoproject.com/en/stable/ref/contrib/admin/actions/ . Django's `ModelAdmin.message_user` handles the result message.
- Unfold (from knowledge): action forms via `action_form` / `ActionForm` subclass with an extra field set on `ModelAdmin.action_form`; Django admin's own `ModelAdmin.action_form` (an `ActionForm` with a hidden `select_across`) is the base. Reasons-style fields are normal form fields on that form. Django: `django/contrib/admin/helpers.py` `ActionForm`.
- Takeaway: nobody ships a "reason" concept. The common shape is a plain Django form attached to the action, rendered by the confirm template; optional vs required is just `required=` on the field. Keeping `ReasonForm` a plain form with `required=False` now, and flipping to `required=True` in spec 2, matches that; no separate dialog class is needed.

## 3. Lazy panels and error signalling for async regions

- HTMX pattern (from knowledge): `hx-trigger="load"` (or `revealed`) on a placeholder, `hx-swap="outerHTML"`; errors via status codes. HTMX 2.x does not swap 4xx/5xx responses by default; opt in with `htmx.config.responseHandling` (2.x) or the `htmx:beforeSwap` event setting `evt.detail.shouldSwap = true` and `isError = false`. https://htmx.org/events/#htmx:beforeSwap , https://htmx.org/docs/#modifying_swapping_behavior_with_events . FLS already uses 422 for HTMX validation errors (project CLAUDE.md), so a too-large region should likewise return a swappable status (422 or 413) carrying a rendered message fragment, with the host-raised framework error supplying the message.
- Wagtail (from knowledge): dashboard panels (`construct_homepage_panels`) render server-side, no lazy skeleton; its `ReportView`s paginate and export by streaming. Not a source for lazy errors.
- Django REST/DRF and Django admin offer nothing on this; the closest idiom is a custom exception class mapped to a response (like `Http404`/`PermissionDenied` mapped by the handler). A `PanelRegionError(message)` that `render_region` catches and renders into the region (and the host raises/translates) matches that idiom.

## 4. Toggle and date-range filters

- django-filter (from knowledge): `FilterSet` with declared `Filter` classes; `BooleanFilter`/`BooleanWidget` for toggles, `DateFromToRangeFilter` with `RangeWidget` (two inputs `field_after`/`field_before`), `DateRangeFilter` with preset choices ("today", "yesterday", "past 7 days", "this month", "this year") implemented as a `choices` dict of name to `(label, callable(qs, name))`. Docs: https://django-filter.readthedocs.io/en/stable/ref/filters.html ; source `django_filters/filters.py` (`DateRangeFilter`), `django_filters/widgets.py`.
  - Useful for `AuditPeriodFilter`: a field-name parameter plus a named dict of preset windows is exactly django-filter's `DateRangeFilter.options`. Naming it a "period filter taking a field name and preset windows" is consistent.
- Django admin: `SimpleListFilter` (`title`, `parameter_name`, `lookups()`, `queryset()`) and `DateFieldListFilter` (presets: Any date, Today, Past 7 days, This month, This year). A toggle is normally a two-choice `SimpleListFilter`. https://docs.djangoproject.com/en/stable/ref/contrib/admin/filters/ (from knowledge).
- django-tables2: no filters; pairs with django-filter through `SingleTableMixin` + `FilterView` (`django_tables2.views.SingleTableMixin`, `django_filters.views.FilterView`). https://django-tables2.readthedocs.io/en/latest/pages/filtering.html (from knowledge).
- Unfold: ships `unfold.contrib.filters` (`RangeDateFilter`, `RangeDateTimeFilter`, `CheckboxFilter`, `RadioFilter`) as Django `ListFilter` subclasses. https://unfoldadmin.com/docs/filters/ (from knowledge).
- Takeaway: both Django and django-filter keep the filter's URL parameter name, field name and presets as constructor/class attributes, and the filter owns both its `queryset()` narrowing and its widget. That backs a generic toggle filter (parameter name, field, true-value) and period filter (parameter name, field name, presets) while keeping existing FLS call sites behaviour-identical via defaults.

## 5. Public API declaration

- django-filter: `django_filters/__init__.py` defines `__all__` re-exporting filters and `FilterSet`; docs list the public classes. Source: https://github.com/carltongibson/django-filter/blob/main/django_filters/__init__.py (from knowledge).
- django-tables2: `django_tables2/__init__.py` re-exports `Table`, columns, `RequestConfig`, with `__all__`-style listing; internals under `django_tables2/utils.py` are "not public". https://github.com/jieter/django-tables2/blob/master/django_tables2/__init__.py (from knowledge).
- Wagtail: public API is "documented modules"; `wagtail.admin` internals are explicitly unsupported unless in the docs; deprecation policy and release notes list API breaks. https://docs.wagtail.org/en/stable/releases/upgrading.html (from knowledge).
- Takeaway: `__all__` per module (the settled choice) is the norm in the small libraries. A test can compare `__all__` against names imported from the framework across the repo (`from freedom_ls.panel_framework.X import name`): each name used outside the package must be in that module's `__all__`. Rename private `views.py` helpers with a leading underscore.

## 6. JS component packaging and tests

- Alpine components are registered in one file via `document.addEventListener("alpine:init", () => Alpine.data("name", ...))`. Docs: https://alpinejs.dev/globals/alpine-data . Unfold ships its JS under `unfold/static/unfold/js/` (bundled; from knowledge); Wagtail uses webpack-built `client/` with Jest unit tests and `client/tests` (from knowledge); django-cotton libraries ship plain files and test via rendered HTML.
- Wagtail testing of JS: Jest for components (`client/src/**/*.test.js`), Django `TestCase` for rendered markup; browser-level only for a few flows. https://docs.wagtail.org/en/stable/contributing/ui_guidelines.html (from knowledge).
- Takeaway for the "every Alpine name used in a framework template is registered" check: it is a static test (regex `x-data="(\w+)` over framework templates, compare with `Alpine.data("…")` names in `alpine-components.js`), no browser needed; browser tests (Playwright on stub panels) cover behaviour. Nothing found in these projects does the static check; it is cheap and local.

## 7. Template and component testing

- django-cotton (from knowledge): components are tested by rendering `Template("{% load cotton %}<c-name .../>").render(Context())` and asserting on the output, the library's own tests do this in `django_cotton/tests/`. https://github.com/wrabit/django-cotton/tree/main/django_cotton/tests . Cotton docs: https://django-cotton.com
- django-tables2: tests render tables with `Table(data).as_html(request)` and assert `<td>` content (`tests/test_templatetags.py`, `tests/test_rendering.py`). https://github.com/jieter/django-tables2/tree/master/tests
- Wagtail: `TestCase` + `self.assertContains`/`assertTagInHTML` and `wagtail.test.utils.WagtailTestUtils`; template-driven bulk action tests in `wagtail/admin/tests/test_bulk_actions/`. https://github.com/wagtail/wagtail/tree/main/wagtail/admin/tests (from knowledge)
- Django admin: `assertContains` against `admin_views` tests; actions tested via `client.post(url, {"action": name, "_selected_action": [...]})`. https://github.com/django/django/tree/main/tests/admin_views
- Takeaway: render-and-assert-HTML per component is the universal pattern; one test module per component group (`data-table*`, `panel-*`, `modal-*`) with a small render helper.

## 8. Stale/orphaned job reapers

- Celery (verified settings): `task_acks_late` redelivers on worker loss; `task_reject_on_worker_lost` requeues (can loop); `task_time_limit` kills over-long tasks; `result_expires` deletes stored results (default 1 day) and is the analogue of deleting stale previews and retention deletion; `visibility_timeout` goes through `broker_transport_options`. https://docs.celeryq.dev/en/stable/userguide/configuration.html
- django-q2 (from knowledge): `timeout` and `retry` settings; `retry` must exceed `timeout`; `Schedule` rows are driven by the cluster's own scheduler; success/failure results pruned by `save_limit`. https://django-q2.readthedocs.io/en/master/configure.html
- django-rq / RQ (from knowledge): `StartedJobRegistry` holds running jobs with heartbeat expiry; `StartedJobRegistry.cleanup()` moves jobs whose worker died to `FailedJobRegistry`; `rq.registry.clean_registries(queue)` is a plain callable that hosts invoke on a schedule. https://python-rq.org/docs/job_registries/ . This is the closest model for the "plain callable the host schedules" decision, and returns counts.
- Takeaway: all of them separate (a) reaping rows whose worker vanished, driven by a heartbeat or timeout threshold, from (b) retention deletion by age, and all take thresholds as arguments or settings. Callable shape: `sweep_bulk_action_runs(*, now=None, unpicked_after, orphaned_after, preview_ttl, retention) -> SweepResult(counts)`; takes `now` for tests; idempotent. Host schedules it by cron/management command/task of its choosing.

## Suggested spec decisions drawn from the above

1. Generic bulk action: class attrs for id, `permitted()` per object, `skip_reason()`, classmethod/instance `perform()`, `sentence()`, template with overridable blocks (Wagtail style). Registry keyed by table; duplicate registration raises.
2. `ReasonForm`: plain Django form, `required=False` now.
3. Framework error type (e.g. `PanelRegionError`) carrying the message; `render_region` renders it, status swappable by HTMX (422 per project convention).
4. Toggle and period filters: parameter name and field name as constructor args, presets as a dict; defaults reproduce current FLS behaviour (answers the "constructor shape" open question toward the general form with defaults, to be confirmed by existing table tests).
5. `__all__` per public module plus a repo-wide test that every `panel_framework` name imported elsewhere is in `__all__`.
6. Static Alpine-name registration test plus Playwright stub-panel tests; component tests by render-and-assert.
7. Housekeeping: plain callable with injected `now`, thresholds as arguments, returns counts; RQ `clean_registries` is the precedent.
