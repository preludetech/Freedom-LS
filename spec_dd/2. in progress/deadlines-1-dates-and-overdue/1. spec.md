# Spec: due dates, course time limit and overdue

Spec 1 of 7 in the Deadlines effort (`spec_dd/1. next/roadmap.md`, "Deadlines"). Source:
`idea.md` in this directory.

## Purpose

Today's deadlines are fixed datetimes that can only lock an item. They cannot say "due 30 days
after registration", there is no course time limit, and no time zone or end-of-day rule is
defined. This spec removes them and adds two kinds of deadline: a due date on a placed content item
and a time limit on a whole course. Each is authored in content, overridden per cohort course
registration and per learner in the Django admin, and resolved by one resolver. Learners see due
dates and an "overdue" mark. Nothing is enforced.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| registration date | narrowed | The date part of `CourseProgress.created_at` in the site time zone. "Start" is taken (`started_at` is first access), so relative deadlines count from the registration date. |
| content default | coined | The deadline a course author writes in frontmatter, stored on the `ContentCollectionItem` (item) or the `Course` (time limit). |
| time limit end | coined | The instant the course time limit runs out for one learner. |
| overdue | coined | An incomplete item whose effective due instant has passed, or an incomplete course whose time limit end has passed. |

## Scope

In:

- Removing the old deadline implementation (`CohortDeadline`, `LearnerDeadline`,
  `LearnerCohortDeadlineOverride`, `deadline_utils.py`, `DEADLINES_ACTIVE`, their admins, the TOC
  badges and lock, the four `qa_create_*deadline*` commands). No rows are migrated.
- Item due dates (fixed date, optional time, or days after registration) and a course time limit
  (days after registration), authored in frontmatter and validated on load.
- Cohort-course-registration and learner overrides in the Django admin, with actor, reason and a
  drift flag.
- A per-site time zone.
- One resolver; due dates and overdue on the table of contents, course detail and the dashboard
  course card.
- The `fls-content` plugin learning the new fields.

Out: everything after a date passes beyond the mark (spec 2); extensions and pause (3, 4);
reminders (5); educator-interface screens (6); overdue in Needs attention and reports (7); a user
time zone field; part-level deadlines; capping item due dates at the time limit end; pruning stale
placements on re-import (today's sync leaves a moved child's old placement in place, and this spec
does not change that beyond carrying overrides, below).

## Decisions

1. **New app `freedom_ls/deadlines`.** It holds the override models, the resolver, the admin
   inlines and the display template tag. Specs 2 to 7 add to it.
2. **Content defaults live on the item's own file**, not on the `children:` list. Auto-discovered
   children (every demo course) have no `children:` entry. The sync copies the item's fields onto
   every `ContentCollectionItem` that places it, so a file placed twice carries the same default on
   both placements; overrides still differ per placement.
3. **A fixed due date takes an optional time.** Without one it falls due at the end of that day,
   23:59:59.999999 in the site time zone. Overdue means `now > due_at`.
4. **An override keeps its own value and flags drift.** It stores the value it replaced (the
   resolution of the layers beneath it when it was saved). When that value later differs, the admin
   says so. Deleting the override returns the learner or cohort to the layers beneath.
5. **An override can say "no deadline"**, removing a content default for that cohort or learner.
   `kind` distinguishes it from "no override".
6. **The learner override keys on `CourseProgress`.** That is the record of the one registration
   `learner_for_course` resolves, on both the individual and cohort paths; a cohort move mints a new
   `CourseProgress` and starts the learner afresh, overrides included.
7. **Every override records `set_by`, `updated_at` and an optional `reason`.** Spec 3 or 6 may
   make the reason required for extensions.
8. **A fixed date earlier than the learner's registration still applies.** The item shows overdue
   from day one; a learner override is the remedy.
9. **A passed time limit end makes the course overdue** when the course is incomplete.
10. **Learner-facing dates render in the learner's own time zone, in the browser**, without a zone
    label unless the site turns one on. With no JavaScript the server text shows the site zone,
    labelled. Admin dates always name the site zone.
11. **Within one layer the latest instant wins, and "no deadline" beats any date.** The unique
    constraints below allow one value per layer per placement, so this matters only to later specs
    that add layers; the resolver implements it once.
12. **Re-import carries overrides to a moved placement.** See "Content loading".

### Content authoring and validation

Item fields, on the `Topic` and `Form` schemas (`content_engine/schema.py`,
`form_engine/schema.py`), shared through one pydantic model rather than copied:

```yaml
due_date: 2026-03-14          # YAML date; a datetime is rejected
due_time: "17:00"             # optional, 24-hour HH:MM; needs due_date or due_days_after_registration
due_days_after_registration: 14   # integer >= 0
```

Course field, on the `Course` schema:

```yaml
time_limit_days: 90           # integer >= 1
```

Validation, raised as `ValueError` in model validators so `content_validate` and the sync report
name the file and field:

- `due_date` and `due_days_after_registration` together is an error.
- `due_time` without either is an error.
- Negative or non-integer days, `time_limit_days < 1`, a malformed time: errors.

### Content loading (`content_engine/management/commands/content_save.py`)

- New nullable columns on `ContentCollectionItem` (`content_engine/models/courses.py:518`):
  `due_date` (`DateField`), `due_time` (`TimeField`), `due_days_after_registration`
  (`PositiveIntegerField`). The placement write (`update_or_create` at ~:1100) sets them from the
  child's frontmatter on every sync; an absent field clears the column, since frontmatter is the
  source.
- The due fields are excluded from the `Topic`/`Form` model save; they are not columns on those
  models.
- New nullable `Course.time_limit_days` (`PositiveIntegerField`), written by `save_course` like any
  scalar field.
- **Override carry-over.** After a course's child pass, take each placement in the course (the
  course and its parts) that this load created. If the same child has exactly one other placement
  in the course that this load did not write, move that placement's `CohortDeadlineOverride` and
  `LearnerDeadlineOverride` rows to the new placement. Any other case leaves the rows where they
  are. This runs inside the load's existing transaction.

### Override models (`freedom_ls/deadlines/models.py`)

Two models, `SiteAwareModel, TimestampedModel`, the same fields apart from the layer FK:

| Field | Type |
| --- | --- |
| `cohort_registration` (on `CohortDeadlineOverride`) | FK `CohortCourseRegistration`, CASCADE, `related_name="deadline_overrides"` |
| `course_progress` (on `LearnerDeadlineOverride`) | FK `CourseProgress`, CASCADE, `related_name="deadline_overrides"` |
| `collection_item` | FK `ContentCollectionItem`, null, CASCADE. Null means the row overrides the course time limit. |
| `kind` | `TextChoices` `DeadlineKind`: `fixed`, `relative`, `none` |
| `due_date`, `due_time`, `days_after_registration` | nullable, as the content fields |
| `replaced_value` | `CharField`: canonical form of the value beneath when saved, e.g. `relative:14`, `fixed:2026-03-14T17:00`, `none` |
| `set_by` | FK `AUTH_USER_MODEL`, null, `SET_NULL`, `related_name="+"` |
| `reason` | `TextField(blank=True)` |

- Unique: one row per (layer FK, `collection_item`) with `collection_item` set, and one per layer FK
  with it null (conditional `UniqueConstraint`s).
- `clean()`: `fixed` needs `due_date`; `relative` needs `days_after_registration`; `none` needs
  neither field set; `due_time` only with `fixed` or `relative`; a time-limit row cannot be `fixed`;
  `collection_item` belongs to the registration's course and is a viewable item, not a part.
- Factories for both models and `SiteTimeZoneConfig`.

### Resolver (`freedom_ls/deadlines/resolver.py`)

- `DeadlineValue`: frozen dataclass of `kind`, `due_date`, `due_time`, `days`. One value type
  for content defaults and both override layers.
- `DeadlineSource`: `content`, `cohort`, `learner`.
- `ResolvedDeadline`: frozen dataclass of `due_at: datetime | None`, `source: DeadlineSource | None`,
  `default_changed: bool`.
- `resolve_deadline(layers, registration_date, tz) -> ResolvedDeadline`: pure, no ORM. Layers are
  most specific first; the first layer holding a value wins. Fixed: `due_date` at `due_time` or end
  of day in `tz`. Relative: `registration_date + days` at `due_time` or end of day in `tz`, computed
  on local dates so a DST change does not move the time. `none`: `due_at=None`.
- `course_deadlines(course_progress) -> CourseDeadlines`: `items: dict[UUID, ResolvedDeadline]` keyed
  by `ContentCollectionItem` id, and `time_limit: ResolvedDeadline`. Its query count does not
  depend on the number of items.
- `course_deadlines_for(course_progress_records) -> dict[UUID, CourseDeadlines]` for the dashboard.
  Its query count does not depend on the number of cards.
- `is_overdue(resolved, completed, now) -> bool`. `now` is taken once per request and passed in.

### Learner interface (`freedom_ls/learner_interface`)

- **Display.** A template tag in `deadlines/templatetags/` renders
  `<time datetime="<ISO UTC>">` with server text in the site zone, labelled. A `localTime` Alpine
  component in `base/static/base/js/alpine-components.js` rewrites the text in the browser's zone
  via `Intl.DateTimeFormat` (day, short month, year, hour, minute), adding the zone name only when
  `shows_time_zone_to_learners` is on. Every learner date goes through it.
- **Overdue mark.** `<c-panel-status-badge tone="error" label="Overdue">`, text and colour, per
  `brand-guidelines`.
- **Table of contents.** `get_course_index` (`utils.py:463`) takes the `CourseDeadlines` and adds
  `due_at` and `is_overdue` to each item dict. `course_minimal_toc.html` shows "Due <date>" in the
  right-hand `shrink-0` column and the overdue badge on overdue rows. A completed row shows neither.
  Part rows show no date. Because the partial is shared, course detail and the player sidebar both
  show this.
- **Course detail** (`views.py:703`): for a registered learner, load the governing
  `CourseProgress` and its `CourseDeadlines`. With a time limit, show "Finish by <date>" in the stat
  row; once passed and incomplete, "Time limit ended <date>" with the overdue badge.
- **Dashboard card** (`_annotate_registered_courses`, `partials/course_card.html`): one line in the
  card body, above the progress bar, never in the eyebrow slot, in this order:
  1. Time limit ended and course incomplete: overdue badge and "Time limit ended <date>".
  2. Any overdue items: `<c-panel-status-badge tone="error" label="N overdue">`.
  3. Otherwise the earliest future due date or time limit end: muted "Next due <date>".
  4. None of these, or the course is complete: nothing.
  The overdue count comes from the index `_annotate_next_up` already builds, not a second index.

## Testing

- Schema: each validation rule, accepted and rejected; YAML date versus datetime.
- Sync: due fields land on each placement of a file placed twice; an absent field clears; course
  `time_limit_days` saves; carry-over moves overrides in the one-new-one-stale case and leaves them
  in the others; a failing load rolls back carry-over.
- Resolver (pure): each layer beating the one beneath; `none` at each layer; fixed with and
  without time; relative from a registration date; end of day at the boundary (one microsecond
  before and after); a relative date across a DST change landing on local end of day; a fixed date
  before registration; `default_changed` true and false.
- Query counts: `course_deadlines` and `course_deadlines_for` are constant in item and card count;
  the TOC and dashboard query counts rise by a fixed amount only.
- Overdue: incomplete past due is overdue; completing it clears the mark on TOC, course detail and
  dashboard; the time limit end passing makes an incomplete course overdue, a complete one not.
- Surfaces agree: for each layer, the TOC, course detail and dashboard show the same effective
  date.
- Site isolation: overrides and `SiteTimeZoneConfig` of another site never apply.
- One registration governs: a learner in two organisations sees each registration's own deadlines.
- Admin: `clean()` rules; `set_by` stamped; drift message shown after a content default changes;
  the effective-deadlines field.
- Display: `<time datetime>` carries the UTC instant; server text names the site zone; a browser
  test checks the local rewrite with and without `show_time_zone_to_learners`.
- Removal: no `Deadline`/`DEADLINES_ACTIVE`/`deadline_utils` reference remains outside migrations
  and the kept items; `makemigrations --check` passes.

## Success criteria

- No old deadline model, setting, admin, command or badge remains; the migration drops the tables.
- A topic with `due_days_after_registration: 14` shows, for a learner registered on 1 March, "Due
  15 Mar" at the end of that day in the site zone.
- `content_validate` rejects each invalid field combination with the file and field named.
- A cohort override beats the content default and a learner override beats both, on all three
  surfaces.
- A `none` override removes the due date for that cohort or learner.
- Changing the content default after an override is saved shows the drift message on that override.
- Moving a child to another part and re-syncing keeps its overrides.
- A completed item never shows overdue; an incomplete past-due item does on TOC, course detail and
  dashboard.
- The dashboard card shows "N overdue", "Time limit ended", "Next due" or nothing, per the order
  above.
- With JavaScript, learner dates show in the browser's zone without a zone name unless the site
  turns it on.
- TOC and dashboard query counts do not grow with item or card count.
