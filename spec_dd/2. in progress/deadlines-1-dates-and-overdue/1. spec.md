# Spec: due dates, course time limit and overdue

Spec 1 of 7 in the Deadlines effort (`spec_dd/1. next/roadmap.md`, "Deadlines"). Source:
`idea.md` in this directory.

## Purpose

This spec removes the old deadlines and adds two kinds of deadline: a due date on a collection item
and a time limit on a whole course. Each is authored in content, overridden per cohort course
registration and per learner in the Django admin, and resolved by one resolver. Learners see due
dates and an overdue mark. Nothing is enforced.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| registration date | narrowed | The date part of `CourseProgress.created_at` in the site time zone. "Start" is taken (`started_at` is first access), so relative deadlines count from the registration date. |
| content default | coined | The deadline a course author writes in frontmatter, stored on the `ContentCollectionItem` or, for the time limit, the `Course`. |
| deadline override | narrowed | A `CohortDeadlineOverride` or `LearnerDeadlineOverride` row. Not `ContentCollectionItem.overrides`, which this spec leaves alone. |
| time limit end | coined | The instant the course time limit runs out for one learner. |
| overdue | narrowed | From `docs/product/learner-experience.md:288` and the `cohort_needs_attention.html` TODO. Here, an incomplete collection item whose effective due instant has passed, or an incomplete course whose time limit end has passed. |

## Scope

In:

- Removing the old deadline implementation, with no rows migrated (see Removal).
- Collection item due dates (fixed date with optional time, or days after registration) and a
  course time limit (days after registration), authored in frontmatter and validated on load.
- Deadline overrides per cohort course registration and per learner in the Django admin, with
  actor, reason and a "default changed" flag.
- A per-site time zone.
- One resolver; due dates and overdue on the table of contents, course detail and the dashboard
  course card.
- The `fls-content` plugin learning the new fields.

Out: everything after a date passes beyond the mark (spec 2); extensions and pause (3, 4);
reminders (5); educator-interface screens (6); overdue in Needs attention and reports (7); a user
time zone field; part-level deadlines; capping due dates at the time limit end; pruning stale
placements on re-import (today's sync leaves a moved child's old `ContentCollectionItem` in place).

## Decisions

1. **New app `freedom_ls/deadlines`.** It holds the deadline override models, the resolver, the
   admin inlines, the carry-over and the display template tag. Specs 2 to 7 add to it.
2. **Content defaults live on the child's own file**, not on the `children:` list. Auto-discovered
   children (every demo course) have no `children:` entry. A file placed twice carries the same
   default on both collection items; deadline overrides still differ per collection item.
3. **A fixed due date takes an optional time.** Without one, a due date (fixed or relative) falls
   due at the end of that day, 23:59:59.999999 in the site time zone. Overdue means `now > due_at`.
   The time limit always ends at the end of its day.
4. **A deadline override keeps its own value and flags when the default changed** (see Override
   models and Admin). Deleting it returns the learner or cohort to the layers beneath.
5. **A deadline override can say "no deadline"**, removing a content default for that cohort or
   learner. `kind` distinguishes it from "no override".
6. **The learner deadline override keys on `CourseProgress`.** A cohort move mints a new one and
   starts the learner afresh, deadline overrides included.
7. **A fixed date earlier than the learner's registration still applies.** The child shows overdue
   from day one; a learner deadline override is the remedy.
8. **A passed time limit end makes an incomplete course overdue.**
9. **Learner-facing dates render in the learner's own time zone, in the browser**, without a zone
   label unless the site turns one on. With no JavaScript the server text shows the site zone,
   labelled. Admin dates always name the site zone.

### Content authoring and validation

Child fields, on the `Topic` and `Form` schemas (`content_engine/schema.py`,
`form_engine/schema.py`), shared through one pydantic model, `DueDateFields` in
`content_base/schema.py`, rather than copied; `DUE_DATE_FIELD_NAMES` beside it is the set of its
field names, for the loader's `exclude_fields`:

```yaml
due_date: 2026-03-14          # YAML date; a datetime is rejected, midnight included
due_time: "17:00"             # optional, 24-hour HH:MM; needs due_date or due_days_after_registration
due_days_after_registration: 14   # integer >= 0
```

Course field, on the `Course` schema:

```yaml
time_limit_days: 90           # integer >= 1
```

Validation, raised as `ValueError` in validators so `content_validate` and the sync report name the
file and field:

- `due_date` must be a `date` and not a `datetime`, checked in a `field_validator(mode="before")`
  (`type(value) is date`), because PyYAML yields a `datetime` for `2026-03-14 00:00:00` and
  pydantic's lax `date` accepts it.
- `due_date` and `due_days_after_registration` together is an error.
- `due_time` without either is an error.
- Negative or non-integer days, `time_limit_days < 1`, a malformed time: errors.

No validator imports Django, so the bundled plugin copy needs no patch.

### Content loading (`content_engine/management/commands/content_save.py`)

- New nullable columns on `ContentCollectionItem` (`content_engine/models/courses.py:518`):
  `due_date` (`DateField`), `due_time` (`TimeField`), `due_days_after_registration`
  (`PositiveIntegerField`).
- `content_by_path` holds saved model instances, not schemas, so the loader keeps a
  `schema_by_path` map filled alongside it. The child pass reads the due fields from it and sets
  them in the `update_or_create` at ~:1100 on every sync; an absent field clears the column.
- The due fields go in `exclude_fields` for the topic and form saves; they are not columns on
  `Topic` or `Form`.
- New nullable `Course.time_limit_days` (`PositiveIntegerField`), written by `save_course` like any
  scalar field.
- **Deadline override carry-over.** `content_engine` sits below `deadlines`, so the loader sends a
  signal, `collection_items_synced` in `content_engine/signals.py`, once after the child pass,
  inside the load's transaction, with `site`, `created` (the collection items this load made) and
  `written` (every collection item it touched).
  A receiver in `deadlines/signals.py`, `carry_over_deadline_overrides`, takes each created
  collection item;
  if the same child has exactly one other collection item in the course (the course and its parts)
  that this load did not write, it moves that one's deadline overrides to the new collection item.
  Any other case leaves the rows where they are.

### Deadline override models (`freedom_ls/deadlines/models.py`)

Two models, `SiteAwareModel, TimestampedModel`, the same fields apart from the layer FK:

| Field | Type |
| --- | --- |
| `cohort_registration` (on `CohortDeadlineOverride`) | FK `CohortCourseRegistration`, CASCADE, `related_name="deadline_overrides"` |
| `course_progress` (on `LearnerDeadlineOverride`) | FK `CourseProgress`, CASCADE, `related_name="deadline_overrides"` |
| `collection_item` | FK `ContentCollectionItem`, null, CASCADE. Null means the row overrides the course time limit. |
| `kind` | `TextChoices` `DeadlineKind`: `fixed`, `relative`, `none` |
| `due_date`, `due_time`, `due_days_after_registration` | nullable, as on `ContentCollectionItem` |
| `replaced_value` | `CharField`: canonical form of the value beneath when saved, e.g. `relative:14`, `fixed:2026-03-14T17:00`, `none` |
| `set_by` | FK `AUTH_USER_MODEL`, null, `SET_NULL`, `related_name="+"` |
| `reason` | `TextField(blank=True)` |

- Unique: one row per (layer FK, `collection_item`) with `collection_item` set, and one per layer FK
  with it null (conditional `UniqueConstraint`s).
- `clean()`: `fixed` needs `due_date`; `relative` needs `due_days_after_registration`; `none`
  needs neither; `due_time` only with `fixed` or `relative` on a collection item row, never on a
  time-limit row; a time-limit row cannot be `fixed`; `collection_item` is one of the course's
  viewable collection items.
- `course_viewable_collection_items(course)` in `deadlines` returns those (the course's and its
  parts', via `Course.collection_items()`), for `clean()` and the admin picker.
- Factories for both models and `SiteTimeZoneConfig`.

### Resolver (`freedom_ls/deadlines/resolver.py`)

- `DeadlineValue`: frozen dataclass of `kind`, `due_date`, `due_time`,
  `due_days_after_registration`. One value type for content defaults and both deadline override
  layers. `DeadlineValue.canonical()` is the string `replaced_value` stores.
- `DeadlineSource`: `content`, `cohort_registration`, `learner`.
- `DeadlineLayer`: NamedTuple of `source`, `value: DeadlineValue | None`; the resolver's input
  row for one layer.
- `ResolvedDeadline`: frozen dataclass of `due_at: datetime | None`, `source: DeadlineSource | None`.
  Whether a content default moved under an override is the admin's per-row comparison
  (`canonical_beneath` against `replaced_value`), not the resolver's.
- `resolve_deadline(layers, registration_date, tz) -> ResolvedDeadline`: pure, no ORM. Layers are
  most specific first; the first layer holding a value wins. `due_instant(value, registration_date,
  tz)` turns the winning value into the instant: fixed: `due_date`; relative:
  `registration_date + due_days_after_registration`, on local dates so a DST change does not move
  the time. Either takes `due_time` or end of day per Decision 3. `none`: `due_at=None`. No layer
  holding a value resolves to `NO_DEADLINE`. `registration_date_of(course_progress, tz)` is the
  registration date the callers below pass in.
- `course_deadlines(course_progress) -> CourseDeadlines`: `items: dict[UUID, ResolvedDeadline]` keyed
  by `ContentCollectionItem` id, and `time_limit: ResolvedDeadline`. Its query count does not
  depend on the number of collection items.
- `course_deadlines_for(course_progress_records) -> dict[UUID, CourseDeadlines]` for the dashboard.
  Its query count does not depend on the number of cards.
- `is_overdue(resolved, completed, now) -> bool`. `now` is taken once per request and passed in.

### Learner interface (`freedom_ls/learner_interface`)

- **Display.** A template tag, `local_time` in `deadlines/templatetags/deadline_tags.py`, renders
  `<time datetime="<ISO UTC>">` with server text in the site zone. A `localTime` Alpine component in
  `base/static/base/js/alpine-components.js` rewrites the text with `Intl.DateTimeFormat` (day,
  short month, year, hour, minute), applying Decision 9. Every learner date goes through it. Add
  `localTime` to the `fls-dev:alpine-js` inventory.
- **Overdue mark.** `<c-panel-status-badge tone="error" label="Overdue">`, per `brand-guidelines`.
  This adds a `learner_interface → panel_framework` edge to `docs/app_structure.md`.
- **Table of contents.** `get_course_index` (`utils.py:463`) takes the `CourseDeadlines` and adds
  the `ContentCollectionItem` pk as `collection_item_id`, `due_at` and `is_overdue` to each child
  dict.
  `course_minimal_toc.html` shows "Due <date>" in the right-hand `shrink-0` column and the overdue
  badge on overdue rows. A completed row shows neither. Part rows show no date. Course detail and
  the player sidebar share the partial, so both show this.
- **Course detail** (`views.py:703`): for a registered learner, load the governing
  `CourseProgress` and its `CourseDeadlines`. With a time limit, the context carries
  `time_limit_end`; show "Finish by <date>" in the stat row; once passed and incomplete, "Time
  limit ended <date>" with the overdue badge. An
  unregistered visitor sees no deadline. The course-level overdue mark shows only here and on the
  dashboard card.
- **Dashboard card** (`_annotate_registered_courses`, `partials/course_card.html`): run
  `course_deadlines_for` once before the card loop and pass each card's `CourseDeadlines` to
  `_annotate_next_up`, which counts overdue children from the index it already builds. One line in
  the card body, above the progress bar, never in the eyebrow slot, first match wins:
  1. Time limit ended: overdue badge and "Time limit ended <date>".
  2. Any overdue children: `<c-panel-status-badge tone="error" label="N overdue">`.
  3. Otherwise the earliest future due date or time limit end: muted "Next due <date>".
  4. None of these: nothing.

## Testing

- Schema: each validation rule, accepted and rejected; a YAML date versus a midnight datetime.
- Sync: due fields land on each collection item of a file placed twice; an absent field clears;
  `time_limit_days` saves; carry-over moves deadline overrides in the one-new-one-stale case and
  leaves them in the others; a failing load rolls back carry-over.
- Resolver (pure): each layer beating the one beneath; `none` at each layer; fixed with and
  without time; relative from a registration date; end of day at the boundary (one microsecond
  before and after); a relative date across a DST change landing on local end of day; a fixed date
  before registration; `default_changed` true and false.
- Site time zone: no row falls back to `settings.TIME_ZONE` and `show_time_zone_to_learners=False`;
  a row's zone drives the resolver; an invalid IANA name is rejected.
- Query counts: `course_deadlines` and `course_deadlines_for` are constant in collection item and
  card count; the TOC and dashboard add no queries per collection item or per card.
- Overdue, on TOC, course detail and dashboard, which agree for each layer: an incomplete past-due
  child is overdue and completing it clears the mark; a learner registered after a fixed due date
  sees it overdue at once; a passed time limit end makes an incomplete course overdue on course
  detail and the dashboard; a `none` deadline override removes the date.
- Site isolation: deadline overrides and `SiteTimeZoneConfig` of another site never apply.
- One registration governs: a learner in two organisations sees each registration's own deadlines.
- Admin: `clean()` rules; `set_by` stamped; the "default changed" message after a content default
  changes; the effective-deadlines field.
- Display: `<time datetime>` carries the UTC instant; server text names the site zone; a browser
  test checks the local rewrite with and without `show_time_zone_to_learners`.
- Removal: no `Deadline`/`DEADLINES_ACTIVE`/`deadline_utils` reference remains outside migrations
  and the kept items; `makemigrations --check` passes.

## Success criteria

- A topic with `due_days_after_registration: 14` shows, for a learner registered on 1 March, due
  15 March at the end of that day in the site zone.
- A cohort deadline override beats the content default and a learner deadline override beats both,
  on the TOC, course detail and the dashboard card.
- Moving a child to another part and re-syncing keeps its deadline overrides.
