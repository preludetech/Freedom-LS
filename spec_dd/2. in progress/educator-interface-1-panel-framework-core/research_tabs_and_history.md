# Research: tabs and URL history for the panel framework

Extends `../educator-interface-full-polish/htmx-modal-drawer-url-state.md` section 3 (and its pitfalls) for spec 1's "URL state" settlement. Nothing below repeats a fact already stated there — read that section first. This note answers five things: how tabs work in the code today, primary-source htmx 2 facts that section 3 didn't already pin down, the accessibility model for a tab-like widget whose activation pushes a URL and fetches over the network, the bug reports this shape of thing tends to produce, and what proves the fix.

## 1. How tabs work in the code today

`freedom_ls/panel_framework/tabs.py` is nine lines: `Tab` is a `@dataclass` of `label: str` and `panels: dict[str, type[Panel]]`. It carries no URL, no permission hook (idea.md's "tabs have no permission hook" bullet), no active/default marking of its own.

`InstanceView` in `freedom_ls/panel_framework/views.py` owns tab dispatch:

- `_render_tabbed` (called from `render` when `self.tabs` is set) computes `active = active_tab if active_tab and active_tab in self.tabs else default_tab` — the *first* tab in dict-iteration order is the default, nothing declares it. It renders the active tab's panels inline via `render_tab`, leaves every other tab's `rendered_panels` as `""`, and hands `tab_container.html` a `tab_contexts` list plus `base_url`.
- `render_tab(request, tab_name, base_url)` renders one tab's panels to a string and wraps them in `tab_panels.html` (a plain `<div class="space-y-6">` looping `rendered_panels` — no chrome, no tablist).
- `_resolve_tabs` / `_ResolvedTab` in the path resolver handle `.../__tabs/<name>` segments generically, so `__tabs/<name>/__panels/<name>` and `__tabs/<name>/__actions/<name>` both work today.
- `_dispatch_tab(request, resolved_tab, base_url, is_htmx)`: **if `is_htmx` is true at all, it returns `HttpResponse(iv.render_tab(...))` — a bare fragment — with no check of `hx_target`.** This is the exact mechanism idea.md's last "Why" bullet describes ("On a history-cache miss, htmx sends a request with no target header and the view answers with a bare fragment, which htmx then swaps into `<body>`"): a genuine tab click, a `load-tab` lazy-load trigger, and an `HX-History-Restore-Request` all present as `HX-Request: true` with no distinguishing branch in `_dispatch_tab`, so all three get the same bare-fragment answer. The generic non-tab branch in `_dispatch_resolved` (`hx_target != "main-content"`) is never reached for tabs, because tabs are special-cased above it — so whatever history-restore branch the framework grows for lists/panels has to be threaded through `_dispatch_tab` too, not just the generic path.
- Non-HTMX GET to a tab URL (`is_htmx=False`) does render the full page (`iv.render(..., active_tab=tab_name)` in the `else` arm of `_dispatch_tab`) — so "every pushed URL renders a full page on plain GET" already holds for tabs specifically, independent of the fix above.

`tab_container.html` (template) puts `role="tablist"` / `role="tab"` / `aria-selected` on the buttons and `role="tabpanel"` on each panel `div`, but **no `aria-controls` on the tab buttons, no `aria-labelledby` or `tabindex` on the panels, and no `id` referenced by `aria-controls`** — the APG tabs wiring is half-done. The inactive-tab markup is `hx-get="{{ tab.load_url }}" hx-trigger="load-tab once"` on a child div — a **custom, non-standard trigger name**, fired only by `htmx.trigger(htmxEl, "load-tab")` from Alpine's `switchTab`, never by a real DOM event. That div has no `hx-push-url` and no `hx-target` of its own; the `hx-get` here is *not* what will change to satisfy "tabs switch through htmx" — the button (`x-on:click="handleTabClick"`) has no `hx-*` attributes at all today.

`alpine-components.js`, `Alpine.data("tabContainer", …)`:

- `handleTabClick` calls `this.switchTab(name)` then **`history.pushState({}, "", url)` directly** — this is the `history.pushState` call outside htmx that idea.md and the linked research both call out. htmx's own history machinery (`saveCurrentPageToHistory`, its `popstate` listener gated on `state.htmx`) never sees this entry, because the state object pushed here is `{}`, not `{htmx: true}`.
- `init()` installs its **own** `popstate` handler that regexes the tab name out of `location.pathname` and calls `switchTab`. This runs in parallel with (and independently of) whatever htmx's own `popstate` handler does for the surrounding page navigation, so the two history systems can each act on the same Back press.
- `switchTab(name)` only flips `activeTab` and, the first time a tab is shown, triggers the `load-tab` htmx request; `_updateTabUI()` (run via `$watch`) toggles `hidden` and the selected classes on already-rendered panels — this is already exactly the "Alpine only shows/hides already-loaded panels" behaviour the settled design wants; only the *history* half needs replacing.
- No `htmx.config`, no `historyCacheSize`, no `historyRestoreAsHxRequest` are set anywhere in `alpine-components.js` or any other JS file in the repo (grepped `htmx.config|historyCacheSize|htmx-config|historyRestoreAsHxRequest|refreshOnHistoryMiss` across the tree — the only hits are the two research docs, and `freedom_ls/base/templates/_base.html:73`, which has `<!-- <meta name="htmx-config" content='{"historyCacheSize": 0}' /> -->` **commented out**, confirming the linked research's "already commented out" note).
- `Vary` is set nowhere in `panel_framework`. The only `Vary` usage anywhere in the app is `freedom_ls/referral_tracking/middleware.py`, which calls `django.utils.cache.patch_vary_headers(response, ["Cookie"])` on tracked-landing responses — a working in-repo precedent for the call shape (`patch_vary_headers(response, [...])`), just not for these headers or this app.
- `pyproject.toml` has no `django-htmx` dependency (grepped) — confirmed against the "may not use django-htmx" hedge in the assignment.

Sidebar navigation already does what "tabs switch through htmx with a pushed URL" describes, one level up: `sidebar_nav.html`'s section/instance links are plain `<a href hx-get hx-target="#main-content" hx-push-url="true" hx-swap="outerHTML">` with `aria-current="page"` set from Python (`item.active`/`item.expanded`), no Alpine involved, no custom `role`. This is the working in-repo precedent for "a widget that changes the URL and fetches over HTTP should look like navigation, not like a same-page control" — see section 3.

**Playwright "no nested section" invariant**: only `freedom_ls/panel_framework/tests/playwright/test_data_table_panel_htmx.py` actually asserts it, via a shared `_expect_no_nested_panel(page)` helper (`expect(panel).to_have_count(1)`, `expect(panel.locator("section")).to_have_count(0)`) used by three tests (sort, paginate, the sort-param round-trip incidentally reuses the same page). idea.md's "the two Playwright modules keep their invariant" pairs this file with its directory sibling, `test_list_view_refresh_htmx.py` — that second module exercises the same live-server/htmx-swap machinery (a create-and-refresh flow) but does not itself assert the section-count invariant; it is the sibling module in the same package that a section-nesting regression in *this* spec's new tab/panel container work could plausibly also need to guard, not a second module already asserting the same thing today. Both are `@pytest.mark.playwright @pytest.mark.django_db(transaction=True)`, and both drive a `live_server`/`live_server_site` fixture pair defined in `freedom_ls/panel_framework/tests/conftest.py`. No Playwright module anywhere in the tree currently exercises Back/Forward or a direct GET of a pushed tab URL — `test_tabs.py` and `test_htmx_navigation.py` are Django `RequestFactory`-level tests, not browser tests, and neither sends `HX-History-Restore-Request`.

## 2. htmx 2 primary-source facts the linked research didn't already cover

Version actually shipped: `freedom_ls/base/templates/_base.html:54` loads `https://cdn.jsdelivr.net/npm/htmx.org@2.0.8/dist/htmx.min.js` — same pin the linked research used. The htmx CHANGELOG (https://github.com/bigskysoftware/htmx/blob/master/CHANGELOG.md) shows three 2.0.x releases since: **2.0.9** ("Fixed history `normalizePath` to resolve relative paths against the current page location rather than a dummy base URL"), 2.0.10, and **2.0.11** (2026-09-22, current npm `latest`, no history-specific entries). Everything cited below and in the linked research (sessionStorage-not-localStorage fix, "history restoration now follows the standard swapping code paths", the disabled-element re-enable-before-snapshot fix) shipped at or before 2.0.5–2.0.8, so it's already live in the pinned version. The one gap: **if the project ever pushes a relative-URL tab or panel link, 2.0.8 predates the 2.0.9 fix for resolving relative history paths against the current location** — every URL this framework builds today is server-generated and absolute-from-root (`base_url.rstrip('/') + "/__tabs/" + name`), so this is dormant, not live, but worth knowing if that ever changes.

- **`hx-history="false"`**: can be placed *anywhere* in the document — not only on the history element — to "embargo the current page state from the history cache", and applies to the whole page's snapshot regardless of where the attribute sits (htmx docs, [`hx-history`](https://htmx.org/attributes/hx-history/)). This is a narrower, targeted alternative to the global `historyCacheSize: 0` the settled design already chose — worth knowing it exists as a fallback if a future page needs the cache on in general but must still keep one sensitive fragment out of it, but it's per-page opt-out, not per-element granularity for what gets *swapped in* on restore.
- **The history element and `hx-history-elt`**: htmx's `getHistoryElement()` (2.0.8 source, `cdn.jsdelivr.net/npm/htmx.org@2.0.8/dist/htmx.js`) is `document.querySelector('[hx-history-elt],[data-hx-history-elt]') || document.body` — the snapshot/restore target defaults to `<body>` and nothing in `_base.html` or `_base_interface.html` overrides it with `hx-history-elt`. Because the default is the whole `<body>`, a tab button's `hx-push-url` doesn't need `hx-target` to be `<body>` or the history element for the push itself to be sound — htmx always snapshots the *entire* `<body>` on push, independent of what a given request's `hx-target` swapped. This only matters when `historyCacheSize > 0` (a snapshot has to exist to restore); with the settled `historyCacheSize: 0`, the whole question of *which* element gets snapshotted is moot, because nothing is ever snapshotted or replayed from cache — every restore is a fresh server round trip. That is itself a small, additional argument for turning the cache off: it also sidesteps ever having to reason about `hx-history-elt` for a nested tab/panel structure.
- **`historyRestoreAsHxRequest` — stronger primary-source wording than "default true"**: the htmx docs' Caching section, beyond stating the default, says outright: **"Always disable `htmx.config.historyRestoreAsHxRequest` so that these history full HTML requests are not cached with partial fragment responses."** (https://htmx.org/docs/#caching). That is htmx's own documentation recommending the setting unconditionally, not merely describing its existence — direct support for the settled design's choice to flip it, independent of the `Vary` header question.
- **GitHub issue #3037** (https://github.com/bigskysoftware/htmx/issues/3037, "restore from history requests now break documented hx-request behaviour"): the reporter traces the problem to PR #2013, which made cache-miss restore requests carry `HX-Request: true` by default — exactly the behaviour `historyRestoreAsHxRequest: true` produces — and states plainly that servers following htmx's own documented caching pattern (`Vary: HX-Request`, fragment when `HX-Request: true`) get a bad back-navigation as a direct result. The suggested backend workaround in the thread is to check `HX-History-Restore-Request` explicitly and treat it as a full-page request regardless of `HX-Request` — the second of the two options the linked research already lists (the other being flipping the config). This is corroboration from htmx's own issue tracker that the bug class idea.md describes ("chrome disappears" on cache miss) is a known, named htmx behaviour, not a project-specific mistake.
- **`htmx:historyItemCreated`** and **`htmx:historyCacheError`** (2.0.8 source): fired when htmx writes (`historyItemCreated`, detail `{item, cache}`) or fails to write (`historyCacheError`, includes the failure cause and current cache contents) a snapshot to the history cache. Neither fires when `historyCacheSize: 0`, since no snapshot is ever written — one more concrete, observable consequence of the setting (a test asserting "no `htmx:historyItemCreated` fires" is a way to pin the config is actually taking effect, distinct from asserting on the meta tag's presence).
- **`hx-push-url` and non-body `hx-target`**: htmx's own reference material doesn't document an interaction beyond "the `hx-history-elt` attribute allows changing which element is saved" — there's no special-casing of `hx-push-url` based on what `hx-target` is. The push and the snapshot are independent of the swap target; nothing stops a tab button whose `hx-target` is a tab panel `div` from also carrying `hx-push-url="true"`. The thing to get right is downstream of htmx, in the server: **every URL that can be pushed must independently render the full page on GET** (the linked research's rule), which for a tab means the same `.../__tabs/<name>` path has to work whether it's reached by clicking the tab (fragment swap into the panel) or by a plain browser GET (full page, tab pre-selected) — `InstanceView.render(..., active_tab=tab_name)` already does the second half; `_dispatch_tab`'s missing `hx_target` check (section 1) is what's currently wrong on the first half.

## 3. Accessibility: APG tabs vs. navigation links with `aria-current`

This is a genuine two-source tension, not a settled question — cite both sides.

**The APG tabs pattern** (https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) assumes same-page panel switching: `tablist`/`tab`/`aria-selected` on the buttons, `tabpanel` on the content, each tab's `aria-controls` pointing at its panel's `id`, each panel's `aria-labelledby` pointing back at its tab. Keyboard: Left/Right (wrapping) and Home/End move focus among tabs; Tab moves focus out of the tablist into the active panel's first focusable element. **Automatic vs. manual activation** is the load-bearing distinction for this spec: APG's own guidance is "It is recommended that tabs activate automatically when they receive focus **as long as their associated tab panels are displayed without noticeable latency**" — otherwise (i.e., when activating means waiting on a network request) manual activation, where arrow keys only move focus and Enter/Space activates, is what APG's own manual-activation example (https://www.w3.org/WAI/ARIA/apg/patterns/tabs/examples/tabs-manual/) documents. A tab whose first visit fires an `hx-get` is precisely the "noticeable latency" case: automatic activation would fire a network request on every arrow-key press while a user tabs past panels they don't want, which is both wasteful and a bad experience if the request is slow. This argues for manual activation (current code already effectively does this — `switchTab` only runs on click, there is no arrow-key handling at all today, so there's also a gap: arrow-key movement between tab buttons isn't implemented, only mouse/Enter-via-click is).

**The counter-argument — this isn't really a tabs widget** — comes from accessibility practitioners writing specifically about widgets that look like tabs but load a different resource per "tab": Adrian Roselli, in the post most directly on point (http://adrianroselli.com/2019/06/link-disclosure-widget-navigation.html) and in his older, since-flagged-as-superseded ARIA-tabs post, argues that the `tab` role promises same-document panel reveal, and a control that instead loads a different page/resource is semantically navigation wearing tab styling — assistive-technology users who know the tab keyboard model (arrow keys move *and* select, no page-load expectation) get a control that behaves like a link but doesn't announce as one. The "Tabs: truth, fiction and practical measures" piece (https://fuzzylogic.me/posts/tabs-truth-fiction-and-practical-measures/) draws the same line: `role="tab"` is for same-page content switching; a widget whose activation "loads different pages or external content" should drop the tab role and be marked up as `<nav>` + links + `aria-current="page"`, mirroring what this codebase's own `sidebar_nav.html` already does for section/instance navigation (section 1). GOV.UK's Design System tabs component (https://design-system.service.gov.uk/components/tabs/) is consistent with treating tabs as a same-page content-density device: it explicitly recommends tabs only when "the first section is more relevant than the others for most users" and "users will not need to view all the sections at once", and its no-JS fallback is a **table of contents that links to each section** — i.e., when JavaScript can't do same-page reveal, GOV.UK's own answer is links, not tabs. The Ministry of Justice Design System's separate **sub-navigation** component (https://design-patterns.service.justice.gov.uk/components/sub-navigation) is the direct precedent for "second-level navigation where each item is its own URL": `<nav aria-label>` + `<ul>` + `<a>` with `aria-current="page"` on the active item — structurally identical to what `sidebar_nav.html` already does one level up, and to what Roselli/fuzzy logic recommend for a tab-shaped control that navigates.

The educator interface's tab shape is genuinely a hybrid of both models, which is exactly why the tension matters here rather than being an academic point: **switching to an already-loaded tab is same-page panel reveal** (Alpine show/hide, no request) — real tabs behaviour, correctly `role="tab"`/`role="tabpanel"`. **Switching to a not-yet-loaded tab fires an `hx-get` and (per the settled design) pushes a URL that independently renders a full page on GET** — link/navigation behaviour, since the "tab" now has its own bookmarkable, shareable, reloadable address, exactly the property Roselli and fuzzy logic use to argue against the tab role. A design that wants to keep `role="tab"` throughout (as the current markup already half-does) has to accept that it's deliberately diverging from Roselli's and fuzzy logic's advice for the not-yet-loaded case, and should at minimum fix the gaps APG itself requires for a tabs pattern to be valid at all — `aria-controls` on each tab pointing at its panel's `id`, `aria-labelledby` on each panel pointing back, and (per APG's manual-activation example) real Left/Right/Home/End keyboard handling, none of which exist in `tab_container.html`/`alpine-components.js` today. A design that instead follows Roselli/fuzzy logic/GOV.UK/MOJ would drop `role="tab"`/`role="tablist"` for a `<nav>` + link markup identical in spirit to `sidebar_nav.html`, accepting the loss of arrow-key roving-tabindex navigation in exchange for correct, boring link semantics that need no ARIA at all — Roselli's point about site navigation elsewhere (http://adrianroselli.com/2017/10/dont-use-aria-menu-roles-for-site-nav.html) is that a plain nav needs no ARIA at all, and every role added is a promise to implement the matching keyboard model correctly.

**Focus management on swap**: APG's dialog/tabs guidance in general (and the pattern already established for this framework's own OOB navigation bundle, see below) doesn't call for moving focus into a tabpanel on an htmx-driven switch the way a full navigation would — the user's focus is already on the tab control they just activated, and APG's own manual-activation model leaves focus on the tab, not the panel, after Enter/Space. This argues against moving focus programmatically after a tab's htmx swap completes, whichever markup model is chosen.

**Live announcement**: the framework's `announcer.html` (`freedom_ls/panel_framework/templates/panel_framework/partials/announcer.html`) is a persistent `#scope-announcer` div updated by an `innerHTML`-swap OOB fragment, deliberately never replaced wholesale ("some screen readers never announce a live region that was torn down and rebuilt" — the template's own comment). It is currently only ever rendered when `request.panel_announcement` is set on the *navigation* branch of `panel_framework_view` (`is_navigation`, i.e. `HX-Target: main-content`) — see `test_htmx_navigation.py::test_htmx_navigation_includes_announcer_when_set`. A tab switch to a not-yet-loaded tab is, per `_dispatch_tab`, an `is_htmx=True` request whose `HX-Target` is the tab panel, not `main-content` — it never reaches the `is_navigation` branch and so never gets the announcer OOB bundle today. If a tab switch should announce anything (e.g. "Showing Learners tab" for a screen-reader user who didn't visually see the swap), that has to be added as its own concern in the tab dispatch path — it isn't inherited for free from the mechanism that already exists for section navigation, because tabs deliberately bypass that mechanism (`not isinstance(current, _ResolvedTab)` in `_dispatch_resolved`, section 1) to stay a bare-fragment response.

## 4. Bugs and complaints this shape of thing produces

- **Back showing the wrong tab under the URL that's now current** — exactly idea.md's own diagnosis, and a documented, named htmx failure mode independent of this codebase: GitHub issue #854 ("hx-push-url doesn't work properly on device back button click", https://github.com/bigskysoftware/htmx/issues/854) and #461 ("Scroll position after hx-push-url and back navigation is incorrect", https://github.com/bigskysoftware/htmx/issues/461) are both reports of `hx-push-url` history entries not round-tripping cleanly through Back/Forward. Issue #3165 ("hx-history not working on partial content", https://github.com/bigskysoftware/htmx/issues/3165) and #1201 ("Back/Forward browser buttons loading HTMX partial content only", https://github.com/bigskysoftware/htmx/issues/1201) are both reports of the *general* shape of bug idea.md describes: a URL gets pushed for what was, at the time, a partial-content swap, and Back/Forward later re-requests that URL and gets (or restores a cached) fragment with no page chrome. The common thread across all four: whenever a pushed URL and a served fragment are allowed to diverge from "this URL, requested plainly, always yields the full page", Back/Forward eventually surfaces the mismatch.
- **Stale cached fragments / double history entries**: `alpine-components.js`'s `handleTabClick` pushing its own `history.pushState({}, "", url)` (section 1) is the double-history-entry mechanism in concrete form here — htmx's own `hx-push-url` machinery, once wired onto the tab buttons, will push its own entry for the same navigation; leaving the manual `history.pushState` call in place alongside it would produce two entries (or, worse, one entry each stamped by a different, non-cooperating system — htmx only acts on entries whose `state.htmx` is set, so the Alpine-pushed entry is invisible to htmx's `popstate` handler and vice versa, which is exactly how "Back shows one tab's content under another tab's URL" happens: the URL bar reflects whichever pushState happened, while the DOM reflects whichever popstate handler reacted).
- **bfcache**: this is a *different* cache from htmx's own JS-managed history cache — the browser-native back-forward cache freezes the whole page (DOM, JS heap, in-flight timers) in memory rather than replaying a server response. MDN's bfcache-blocking-reasons catalogue (https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Monitoring_bfcache_blocking_reasons) lists `response-cache-control-no-store`/`no-cache`, open WebSocket/EventSource connections, an `unload` listener, and outstanding network requests at the moment of navigation as blockers. Grepping the app for `Cache-Control`/`no-store`/`no-cache` (`freedom_ls/reports`, `freedom_ls/referral_tracking`, `freedom_ls/form_engine`, `freedom_ls/course_applications`) shows **none of those hits touch `panel_framework` or `educator_interface`** — nothing here currently sets a `Cache-Control` header that would itself disqualify these pages from bfcache. That means bfcache is, at least today, a live possibility for these pages independent of `historyCacheSize`; turning off htmx's own history cache doesn't touch bfcache eligibility one way or the other, and a future `never_cache`/`Cache-Control: no-store` decision on these authenticated views (plausible, given learner/educator data) would need to be made with bfcache eligibility in mind as a side effect, not just XSS/staleness concerns.
- **`Vary` and CDN/browser caching**: the linked research already quotes htmx's own Caching docs on `Vary: HX-Request`. The project's only working precedent for actually *setting* a `Vary` header, `patch_vary_headers` in `freedom_ls/referral_tracking/middleware.py`, is per-request middleware, not a per-view decorator — worth knowing as a second implementation shape (middleware vs. `django.views.decorators.vary.vary_on_headers`) already living in the codebase, alongside Django's own `django.utils.cache.patch_vary_headers` utility the linked research already names. django-htmx's own tips page recommends the decorator form directly, `@vary_on_headers("HX-Request")` (Django's stock `vary_on_headers` decorator, not a django-htmx-specific one) paired with `@cache_control(max_age=...)` — worth citing since it's the same recommendation from a project that exists specifically to smooth over htmx/Django integration, even though this project doesn't depend on it. https://django-htmx.readthedocs.io/en/latest/tips.html is the source page; note it did not, on fetch, surface guidance beyond CSRF/partial-rendering/extension-install topics in the section reachable without deeper navigation, so treat the `vary_on_headers` pairing as general Django/htmx caching guidance rather than a django-htmx-specific mechanism.

## 5. What proves this (described, not written)

- **Back/Forward through a tab switch, in a real browser**: a Playwright test that loads an instance page, clicks a second (not-yet-loaded) tab, confirms the fragment swap landed (some marker text unique to that tab's content), then calls `page.go_back()` and asserts both the URL and the visible active tab reverted together — this is the test the linked research's pitfalls section is implicitly asking for, and it's the one thing no existing test (Playwright or otherwise) in `panel_framework/tests/` currently does. `go_forward()` after that completes the round trip.
- **Direct GET of a pushed tab URL**: a plain Django test-client GET (no `HX-Request` header at all) to `.../__tabs/<name>` asserting the response is a full page (page chrome present — sidebar, breadcrumbs — and the target tab marked active/selected), exercising exactly the same code path `_dispatch_tab`'s `else` arm already takes today, so this can be a fast, non-Playwright regression test living alongside `test_tabs.py`/`test_htmx_navigation.py`.
- **The history-restore branch specifically**: a Django test-client GET to a tab (or panel, or list) URL with both `HTTP_HX_REQUEST="true"` and `HTTP_HX_HISTORY_RESTORE_REQUEST="true"` set (mirroring how `test_htmx_navigation.py`'s `_make_request` already builds header kwargs) and no `HX-Target`, asserting a full page comes back rather than a bare fragment — this is the request shape idea.md's bug report and GitHub issue #3037 both describe, and today's `_dispatch_tab` would fail it (section 1: it only checks `is_htmx`, not the restore header) even though the generic non-tab path might already pass or fail differently depending on how the fix lands. Worth two variants: one hitting a tab URL, one hitting a plain list/instance URL, since section 1 shows the tab path bypasses the generic dispatch branch entirely.
- **`Vary` header presence**: an assertion on `response.headers["Vary"]` (or `response.get("Vary")`) containing both `HX-Request` and `HX-Target`, run against at minimum one non-HTMX response, one bare-fragment HTMX response, and one navigation-bundle HTMX response from the same URL — proving the header is set on every branch `panel_framework_view` can take for a given path, not just one of them, since a cache only needs one un-`Vary`'d branch to serve the wrong body for a given URL.
- **No stray `history.pushState`**: once tabs move to `hx-push-url`, a unit-level check (JS-level, via a Playwright test asserting `history.length` grows by exactly one per tab click, not two) is the direct test for "Alpine no longer also calls `pushState`" — cheap to write once the double-push bug class (section 4) is fixed, and the kind of regression that reappears silently if a future edit reintroduces a manual `pushState` call alongside `hx-push-url`.
- **No nested `<section>`**: the existing `_expect_no_nested_panel` helper in `test_data_table_panel_htmx.py` (section 1) is the direct precedent to extend to the tab container — a tab panel is itself a place a `DataTablePanel` or `instance_details_panel.html` can render, so the same swap-nesting bug this helper was written to catch (a panel's own wrapper duplicating on every swap) can recur specifically for a lazy-loaded tab's first `hx-get`, which is a different request shape (an initial fetch-into-empty-div, not a same-element sort/paginate re-swap) than either of the two existing tests exercises.
