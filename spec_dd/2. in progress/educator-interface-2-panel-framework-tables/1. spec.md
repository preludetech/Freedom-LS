# Spec: panel framework tables

Spec 2 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Written against `idea.md` and the `research_*.md` files beside it.

## Purpose

Two data tables on one page share their unprefixed `search`, `sort`, `order` and `page` query
parameters, so a full-page load of `?page=2` pages both (`CohortDetailsStack`). Links are
hand-built strings, the sort headers put search text into the URL unencoded, and a filter would
have to be threaded by hand through `c-pagination`'s `extra_params`. The table layer also lacks
the filters, row selection, CSV export and mobile layout that specs 6, 7, 8 and 10 build on. This
spec rebuilds the table layer inside `panel_framework` to provide all of them.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| table key | coined | A table's declared, stable name (`learners`). Its DOM id and every query parameter it reads derive from it. |
| `TableQuery` | coined | One table's validated query state (search, sort, page, applied filters), parsed once per request from its own prefixed parameters. |
| `TableFilter` | coined | Base class of a declared filter. Concrete kinds: `ChoiceFilter`, `RelatedChoiceFilter`, `BooleanFilter`. |
| `Selection` | coined | The rows a bulk-action request names: `mode` plus that mode's fields. |
| `BulkAction` | coined | An action a table panel registers that runs once over the resolved selection. |
| `ExportColumn` | coined | One column of a table's CSV export, independent of its on-screen `Column`s. |
| `PanelContext.page_url` | coined | The URL a full-page GET renders for the page a panel sits on, as opposed to `base_url`, the panel's own segment. |

## Scope

In:

- The table templates and tag library move from `base` to `panel_framework`.
- Per-table key and prefixed query state, with links built through `{% querystring %}`.
- The server pushes and replaces the browser URL. Swaps announce their result and move focus.
- Declared filters and the toolbar that renders them.
- Row selection, the bulk-action mechanism and one stub action under test.
- The CSV export hook and streamed response.
- Stacked cards below `md` and the mobile "Filter & sort" sheet.
- `Column` becomes a dataclass.
- Every existing educator table gets a table key, the new page size and a default card.

Out:

- Declaring filters, selection or export on the existing educator tables. Specs 6, 7 and 10 do
  that when they rebuild each table.
- Real bulk actions, the "select all matching" UI and the `all_matching` resolution branch (spec
  8). The CSV import (spec 8). The roster export's content (spec 10).
- Column-level permissions. A column picker. Counts on filter choices. The live count on the
  mobile sheet's submit button. Shift-click range selection.
- Export as its own permission (spec 5). Export as an audited event (spec 11).
- bfcache eligibility of authenticated pages (open from spec 1).
- Permission checks of its own. Tables use only spec 1's hooks (`Panel.has_permission`,
  `authorise_instance`, the scoped `get_queryset`), which spec 5 will change.

## Decisions

1. **The key lives on `DataTablePanel.table_key`, not on `DataTable`.** `CohortDataTable` and
   `LearnerDataTable` are each already bound under two panels, and a key on the table class would
   force one key across placements. `ListViewConfig.table_key` covers the framework-built
   `ListViewPanel`.
2. **The page URL reaches nested panels as a new `PanelContext.page_url` field.** A `TabSet` child
   advances it to its own `base_url` and a `PanelStack` child inherits it unchanged. This mirrors
   the existing `child_segment` distinction. Stripping `__panels` segments out of a string would
   re-derive the same distinction by parsing.
3. **System checks enforce the key rules**, beside `E001` to `E003` in
   `panel_framework/checks.py`, not per request. A system check fails at startup and in CI.
   `sections_by_url_name()` only fails when a request arrives.
4. **`Column` becomes a dataclass.** Typos in column declarations then fail loudly. Filters and
   `BulkAction` follow the `PanelAction` style: plain classes, class attributes for static
   configuration, `__init__` for per-declaration configuration.
5. **The CSV safety helper moves to `freedom_ls/base/csv_safety.py`.** That adds one new edge,
   `panel_framework --> base`, approved for this spec. `site_aware_models` already depends on
   `base`.
6. **The header checkbox is a native checkbox using the `indeterminate` DOM property, without
   `aria-checked`.** ARIA in HTML forbids `aria-checked` on `input type=checkbox`, which corrects
   the idea's `aria-checked="mixed"`.
7. **The row cap is `BulkAction.max_rows = 500`. The framework rejects a request over it and
   never truncates.** A truncated request would act on fewer rows than the confirmation promised. 500
   also sits below Django's `DATA_UPLOAD_MAX_NUMBER_FIELDS` (1000).
8. **`c-pagination` gains an optional input for prebuilt page links and keeps its current
   behaviour when that input is absent.** Downstream projects may call it with
   `page_param_name`/`extra_params`.

## Requirements

### Template and tag moves

- Move `freedom_ls/base/templates/cotton/data-table.html` and `cotton/data-table-cells/{text,link,
  boolean}.html` to `freedom_ls/panel_framework/templates/cotton/` at the same relative paths.
  Cotton's namespace is flat, so `<c-data-table>` and every `"cotton/data-table-cells/..."`
  template path keep working.
- Move `freedom_ls/base/templatetags/data_table_tags.py` (`getattr_str`) to
  `freedom_ls/panel_framework/templatetags/data_table_tags.py`. Keep the library name, so
  `educator_interface`'s `cohort_links.html` and `_link_to_cohort.html` keep their `{% load %}`.
- `freedom_ls/base/templates/cotton/pagination.html` stays. It gains an optional `links` input,
  a list of `{number, changes, current}` entries plus previous/next entries, each rendered as
  `{% querystring request.GET changes %}`. When `links` is absent it behaves as today.
  `pagination_suffix` and `join_query` stay for that path. The table layer stops using them.

### Table key and query state (`panel_framework/tables.py`, `panels.py`, `views.py`, `context.py`, `checks.py`)

- `DataTablePanel.table_key: str` is required. `_bind_root` copies `ListViewConfig.table_key: str`
  onto the `ListViewPanel` next to `table.data_table = section.list_view`.
- `DataTablePanel.region_id` returns `f"{table_key}-table"`. The fragment root is
  `<div id="{{ region_id }}">`, swapped `outerHTML`. The panel's outer `<section>` still carries
  no id because `region_template_name` is set.
- Parameters are `<key>-q`, `<key>-sort` (a sortable column's `sort_field`, with a leading `-` for
  descending), `<key>-page`, `<key>-export` and `<key>-<filter key>`. The `order` parameter goes. A table
  reads only its own parameters. A top-level parameter added later (spec 3's possible `?peek=`)
  must not begin with any table key followed by `-`.
- `DataTable.parse_query(request, key) -> TableQuery` reads and validates them once. An unknown
  sort value is ignored. The page goes through `Paginator.get_page`, which clamps it. A filter
  value that fails validation is dropped silently.
- `TableQuery` is a frozen dataclass: `key`, `search`, `sort`, `page`, and `filters:
  dict[str, list[str]]` holding validated values only. `to_params() -> dict[str, list[str]]`
  serialises it. That value renders the toolbar, and spec 8's `all_matching` payload will carry it.
- **System checks** (new ids after `E003`):
  - `table_key` matches `[a-z0-9_]+`.
  - No two `DataTablePanel`s in one container's descendant tree share a key. The check covers
    every tab, which is stricter than "rendered together" but can be checked statically.
  - Filter keys match `[a-z0-9_]+` and are none of `q`, `sort`, `page`, `export`.
- `PanelContext` gains `page_url: str = ""`. `_bind_root` sets it equal to the root's `base_url`.
  In `Panel._shown_children` (`panels.py:86-97`), a `TabSet` child sets `page_url` to its new
  `base_url` and a `PanelStack` child keeps the parent's.
- `DataTable.page_size` defaults to `25`. A table can still override it.

### Narrowing rows once

- `DataTable.filter_queryset(request, queryset, query) -> QuerySet` applies search
  (`search_fields`, OR'd `__icontains`), then the declared filters, then the sort. It narrows an
  already-scoped queryset and never widens it.
- `get_rows` paginates `filter_queryset`'s result. The export iterates it unpaginated. Spec 8's
  `all_matching` resolution will call it. No other code path parses a table's parameters.

### Link building and URL state

- Python on the table builds a changes dict per link. A sort header gets
  `{"<key>-sort": "-name", "<key>-page": None}`, a page link `{"<key>-page": n}`, a filter link
  sets that filter's key (a list for several values) and `"<key>-page": None`. "Clear all" sets
  every filter key and the page to `None`, and leaves search and sort alone.
- Templates always merge with `{% querystring request.GET changes %}`, passing `request.GET`
  explicitly. Every control is a real link or form: `href` is `page_url` plus the query string,
  and `hx-get` is `base_url` plus the same query string. No control sets `hx-push-url`.
- The search input uses `type="search"`, `hx-trigger="input changed delay:300ms, search"` and
  `hx-sync="this:replace"`. Its id is `<key>-search`. The search form and the mobile sheet form
  submit to a URL with no query string (`page_url` without JavaScript, `base_url` with htmx). They
  carry every other current parameter as hidden inputs, except the table's own page and the fields
  the form itself supplies.
- **Server-set history.** On an htmx response for a table region, `_respond`
  (`views.py:428-474`) sets `HX-Replace-Url` when `HX-Trigger` is `<key>-search`, and
  `HX-Push-Url` otherwise. The value is `page_url` plus the request's query string. The panel
  sub-URL never reaches the address bar. `Vary: HX-Request, HX-Target,
  HX-History-Restore-Request` stays.
- A plain GET to any URL a table pushes renders the full page with every table in its stated
  state, including with JavaScript off.

### Announcement and focus

- A table region swap renders through a new `panel_framework/table_response.html`: the region
  plus `partials/announcer.html` out of band, like `tab_response.html`. The message reads "Showing
  1–25 of 143, sorted by Name". Without a sort the clause is omitted. With no rows it reads "No
  results".
- The fragment's first element is a `tabindex="-1"` anchor. A document-level `htmx:afterSettle`
  listener in `panel_framework/static/panel_framework/js/alpine-components.js` focuses it when the
  swapped target is a table region.

### Columns (`tables.py`)

- `Column` is a dataclass with `header`, `template`, `attr`, `text_attr`, `sortable`,
  `sort_field` (derived as `_prepare_columns` does today), `url_name`, `url_path_template`,
  `htmx_nav`, `header_class`, `cell_class`, and `card: Literal["primary", "secondary", "md_only"]
  = "secondary"`.
- A cell template that needs more fields gets a `Column` subclass. `educator_interface`'s
  relation-link cells (`relation_set`, `link_text_attr`, `link_object_attr`, `item_id`,
  `url_param`) are the case to convert.
- `get_columns()` returns `list[Column]`. All six `DataTable` subclasses in
  `educator_interface/views.py` are converted.

### Declared filters (new `panel_framework/filters.py`)

- `DataTable.get_filters() -> list[TableFilter]`, default `[]`.
- `TableFilter` has `key`, `label` and `always_shown: bool = False`. It declares
  `validate(values: list[str], request) -> list[str]` (return what survives) and
  `apply(queryset, values) -> QuerySet`. `apply` takes a lookup path given at declaration
  (`ChoiceFilter("status", "Status", lookup="status", choices=[...])`) and can be overridden.
- `ChoiceFilter` has static `choices` or overrides `get_choices(request) -> list[tuple[str,
  str]]` and accepts several values. `RelatedChoiceFilter` takes its choices from `get_queryset(
  request)`, which must be scoped the way `DataTable.get_queryset(request)` is. `BooleanFilter`
  narrows when its parameter is present with value `1` and does nothing when absent.
- A filter with a fiddly value may call a single `forms.Field.clean()` inside `validate`. No
  `Form` is adopted.
- **Toolbar** (desktop, left to right, per screen 02): search, then a pill per `always_shown`
  filter with no value (label and caret), then a chip per applied filter ("Status: Stalled,
  Invited" plus a remove link), then "Add filter", then "Clear all" when any filter is set. Pushed
  right: "Sorted by <column>" as text, and "Export CSV" when the table exports.
- Every pill, chip and "Add filter" opens a disclosure listing choices as links, with the current
  values marked. Each link toggles one value. "Add filter" lists only filters not already shown.
  These are `<details>`-based and work with JavaScript off.

### Row selection and bulk actions (new `panel_framework/bulk_actions.py`)

- `DataTablePanel.get_bulk_actions() -> list[BulkAction]` and `ListViewConfig.get_bulk_actions(
  request)`, both default `[]`. The checkbox column, header checkbox, card checkboxes and bar
  render only when at least one registered action passes `has_permission(request)`.
- `BulkAction` has `label`, `action_name`, `max_rows = 500`, `confirm_template_name`,
  `has_permission(request) -> bool` and `execute(request, queryset) -> None`. Its URL is
  `<table panel base_url>/__actions/<action_name>`, resolved by `_resolve_action`
  (`views.py:222-243`), which also searches the table panel's bulk actions.
- **Markup.** The table and the cards sit inside one `<form method="post">` that includes
  `{% csrf_token %}`. Each row checkbox is `name="keys" value="<pk>"` with `aria-label="Select
  <row label>"`, where the row label is `DataTable.get_row_label(row) -> str` (default
  `str(row)`). A hidden `mode=keys` field goes with them. Each action is a submit button with
  `formaction`. The search form's controls sit outside this form or bind to their own form with
  the `form` attribute.
- **Header checkbox**: `aria-label="Select all on this page"`. Checked, unchecked or
  `indeterminate` through Alpine. See decision 6.
- **The bar** is `aria-live="polite"`. On desktop it shares the footer row with the result count
  and pagination, reading "3 selected · showing 1–25 of 143 learners" with the action buttons
  before the pagination. The noun is the model's `verbose_name_plural`.
- **Clearing.** Selection state lives in an Alpine component inside the fragment root. Every swap
  recreates it, so any `<key>-*` change clears the selection. Selection is never in the URL.
- **Payload.** `Selection` is `mode: Literal["keys", "all_matching"]` plus `keys: list[str]`, or
  `query_string` and `excluded`. This spec parses `keys`. Any other mode returns 422, "Not
  supported yet".
- **Resolution** has one function, `resolve_selection(panel, request, selection) -> QuerySet`. In
  `keys` mode it drops keys the model's primary-key field cannot parse (UUIDs today), then
  intersects the rest with `panel.get_queryset(request)` at submit time. A key outside the
  panel's scope drops out silently. Handlers never see keys or the payload.
- **Flow**, the confirm-then-act shape of `DeleteAction`:
  - The first POST checks `has_permission` (403 on failure). It resolves the selection. It renders
    `confirm_template_name` with the resolved count ("This will affect 3 learners") and a confirm
    submit carrying the same fields plus `confirmed=1`. A plain POST gets a full page and an htmx
    POST gets the same fragment `DeleteAction`'s confirmation uses.
  - The second POST resolves again. If the resolved count is 0 or over `max_rows`, it re-renders
    with 422 and a message naming the count and the cap. Otherwise it calls
    `execute(request, queryset)` and redirects to `page_url` with the current query string
    (`HX-Redirect` for htmx, 303 otherwise).
- The only action shipped is a stub `BulkAction` in `panel_framework/tests/`, used by tests.

### CSV export (`panels.py`, `views.py`, new `base/csv_safety.py`)

- `DataTable.get_export_columns() -> list[ExportColumn]`, default `[]`. `ExportColumn` is a
  dataclass with `header` and `value: str | Callable[[Model], object]`. A string is a dotted path
  resolved with `getattr_str`. `None` becomes an empty cell.
- `freedom_ls/base/csv_safety.py` holds `FORMULA_TRIGGERS`, `escape_csv_formula` and the BOM
  constant, moved out of `site_aware_models/admin_exports.py`. `FormulaSafeCSV` stays there and
  imports them.
- A GET to a table panel's `base_url` with `<key>-export=csv` returns the export. `_respond`
  checks this before its other branches. The request has already passed `_resolve_path`, so the
  panel's scoping and permission hooks apply unchanged. A table with no export columns, or an
  unrecognised format, returns 404.
- The export honours search, filters and sort, and skips pagination. The view builds the
  queryset (`filter_queryset(panel.get_queryset(request), ...)`) **before** constructing the
  `StreamingHttpResponse`. `SiteAwareManager` reads the site from a thread-local that is cleared
  before the stream is consumed, so a queryset built inside the generator would lose its site
  filter.
- The generator iterates `.iterator(chunk_size=500)`, writes with `csv.writer` over an echo
  buffer, escapes every string cell and emits the BOM first. Headers: `Content-Type: text/csv;
  charset=utf-8` and `Content-Disposition: attachment; filename="<key>[-<scope>]-<YYYY-MM-DD>.csv"`.
  The scope comes from `DataTablePanel.get_export_scope_slug(request) -> str`, default `""`, and
  goes through `slugify`, so the filename stays ASCII.
- The "Export CSV" control is a plain `<a href>` to that URL, never `hx-get`.

### Mobile

- Inside the same fragment root: the `<table>` wrapped in `hidden md:block`, and below `md` a
  `md:hidden` list of cards. The switch is pure CSS.
- The default card template (`cotton/data-table-card.html`) renders the `primary` column's cell
  (the first column if none is primary) as the title. `secondary` cells follow in declaration order
  as the meta line, and `md_only` columns are omitted. `DataTable.card_template: str | None`
  replaces the whole card for denser layouts such as M03's learner card. A table that drops a row
  menu from its card must keep every row-menu action reachable from the row's detail page.
- The mobile toolbar (M03): the search input on its own row, then applied-filter chips, "Filter",
  and "Sort" pushed right. "Filter" and "Sort" appear only when the table has filters or sortable
  columns. Both open the same sheet.
- **The sheet** (M04, "Filter & sort", "Reset", "Cancel") is a GET form: choice filters as
  checkbox toggle chips, a related filter as a `<select>`, and sort as a radio group with a
  checkmark. Its submit reads "Show results". "Reset" is a link clearing the table's filters and
  sort. The chrome is a `<dialog x-data="sidePanel" data-variant="bottom-sheet">` using `base`'s
  existing `sidePanel` controller, or spec 3's shared dialog if that has landed; no third dialog
  implementation. With JavaScript off the form must still be reachable and submittable below `md`.
- **Selection on cards.** Each card leads with a checkbox whose label gives a 44×44px tap target,
  always visible and never long-press, not overlapping the card's link. A "Select all on this
  page" toolbar control replaces the header checkbox. The bar is fixed to the bottom of the
  viewport.

### Existing educator tables (`educator_interface/views.py`)

- Every `DataTablePanel` subclass and `ListViewConfig` gets a `table_key` (for example `cohorts`,
  `learners`, `course_registrations`), unique per the system check. Columns get `card` groupings
  so the default card reads sensibly.
- The TODO block at `views.py:79-87` stays. The educator tables have not adopted filters,
  selection or export yet.

## Open questions

Defaults taken; overrule any of them:

- The bulk cap is 500 per action (`BulkAction.max_rows`), with 422 over it.
- Key uniqueness is a system check over each container's whole subtree, including tabs that never
  render together.
- The DOM id is `<key>-table`, not the bare key, so it cannot collide with other page ids.
- "Clear all" clears filters only, not search or sort.
- An unknown export format, or a table with no export columns, returns 404.
- The mobile submit reads "Show results". The mockup's live "Show 3 learners" is deferred.
- The TODO at `educator_interface/views.py:79-87` stays until specs 6, 7 and 8 declare filters,
  selection and export on the educator tables.
- Server-side cursors from `.iterator()` fail behind PgBouncer in transaction mode (use
  `DISABLE_SERVER_SIDE_CURSORS`). A sync Gunicorn worker can time out on a long download. Both are
  deployment notes, not code changes.

## Success criteria

- `?<a>-page=2` on the cohort details tab pages the learners table and leaves the registrations
  table on page 1.
- No template under `panel_framework` builds a table link by string concatenation or calls
  `pagination_suffix`.
- After any sort, filter or page change on a nested table, the address bar shows the page URL
  with prefixed parameters, never `__panels`. Reloading it renders the same state.
- Back after a table sort shows a table matching the address bar.
- With JavaScript off, sort, page, search, filters, the mobile sheet and the stub bulk action all
  work.
- A screen reader hears the result summary after a swap, and focus lands on the table anchor.
- An export of a filtered, searched and sorted table contains exactly the matching rows in that
  order, with formula cells escaped and a BOM.
- A selection containing a key outside the panel's scope acts only on in-scope rows, and the
  confirmation count equals the rows acted on.
- Below `md`, rows render as cards with working checkboxes and no horizontal scroll.
- `uv run manage.py check` fails on a duplicate table key.
- `uv run pytest` passes, including the Playwright tests.
