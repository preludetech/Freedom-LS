# Spec: notifications core

Spec 1 of 8 in the User communication effort (`spec_dd/1. next/roadmap.md`). The approach is
settled in `idea.md`; this spec fixes what has to be true when the work is done.

## Purpose

FLS can't tell a user about their own activity once the response that did it has gone: toasts
vanish and webhooks only go to outside systems. This spec adds a `comms` app with one call that
raises a notification for a user, a bell with an unread badge in the shared header, and a
notification centre page. Course registration and course completion are the first two events.
Later specs add events and delivery backends without changing callers.

## Terminology

| Term | Status | Meaning |
| --- | --- | --- |
| notification (`Notification`) | coined | One stored message to one `User` on one `Site` about something that happened to them. Not a toast (`django.contrib.messages`), and not a direct message (spec 4). |
| notification category (`NotificationCategory`) | coined | A registered kind of notification, keyed by a stable string such as `course.registered`. |
| seen (`Notification.seen_at`) | coined | The user has opened the bell panel or the notification centre since the notification arrived. Clears the badge. |
| read (`Notification.read_at`) | coined | The user followed the notification's link or marked it read. Reversible. |
| notification data (`Notification.data`) | coined | The small set of display facts captured when the notification is raised, such as the course title. Not "snapshot", which `content_snapshots` is taking. |
| delivery backend | coined | A class, named in a setting, that acts on a stored notification (email in spec 2). |
| notification centre | coined | The full-page list of a user's notifications. |

## Scope

In:

- New app `freedom_ls/comms`: `Notification` model, the category registry, `raise_notification`,
  the delivery-backend seam (empty list), views, templates, the badge poll.
- Bell, badge and panel in `partials/header_bar.html`, for every signed-in user.
- Notification centre page with All/Unread filters, day groups, pagination and mark read/unread.
- Raising `course.registered` and `course.completed` notifications from the two existing hooks.

Out:

- Email, preferences, unsubscribe (spec 2); digests and quiet hours (spec 7); direct messages and
  the message row in the panel (spec 4); Django Channels push (spec 8).
- Cohort registration, membership, deadline, application and course-launch events.
- `user.registered` welcome notification; allauth account mail.
- Showing a new notification as a toast.
- Retention and age-out. Every notification is kept.
- Backfilling. Every bell starts empty on release day.
- Any change to `fire_webhook_event` or `WEBHOOK_EVENT_TYPES`. `comms` never imports `webhooks`.
- From the design: the Preferences links (gear in the panel header, button on the centre),
  the "Show older notifications" button (the centre paginates instead), and the message item.

## Decisions

1. **`Notification` keys on `User`, not `Learner`.** Educators receive notifications too, and a
   notification is not scoped to an organisation.
2. **`object_id` is `CharField(max_length=255)`.** Downstream projects add categories whose
   targets FLS can't pin to a UUID pk, so this is the open-set case in `docs/app_conventions.md`,
   the same as `ObjectRoleAssignment.object_id`.
3. **Seen is a per-row `seen_at`, not a per-user high-water mark.** Only rows that arrived since
   the last open are ever unseen, so the bulk update stays small. A per-(user, site) marker would
   need a second model and gains nothing here.
4. **Mark unread clears `read_at` only.** The row keeps its `seen_at`, so it shows as unread in
   the panel and centre but does not come back onto the badge.
5. **Category text is a `gettext_lazy` string with named `%(key)s` placeholders**, filled from
   `Notification.data` at display time with `%`. Named placeholders let translators reorder the
   sentence; `str.format` and positional `%s` do not.
6. **Validation errors raise at the call; everything after them is failure-isolated.** An unknown
   category or missing data key is a programming error, so it raises in the caller, and tests
   catch it at each call site. Writing the row and dispatching backends run inside
   `transaction.on_commit(..., robust=True)`. Django then logs any exception and never passes it
   to the registration or completion that raised the notification. This adds no new logging
   code. `robust=True` protects only callbacks queued after this one; an earlier non-robust
   callback that raises still skips it.
7. **Both hooks call `raise_notification` before `fire_webhook_event`**, so a webhook failure
   can't skip the notification.
8. **Following a notification's link goes through a GET redirect view** that marks it read and
   redirects to the URL built from the live target. It never reads a redirect target from the
   request. An HTMX POST fired before navigation races the page unload.
9. **The bell is a WAI-ARIA disclosure, not `c-dropdown-menu`.** The panel holds links and
   buttons, not menu items, so the menu role and arrow-key model are wrong. The design's
   `role="dialog"` is not used either, because the panel does not trap focus.
10. **The badge is rendered by an inclusion tag, not a context processor.** A context processor
    would run the count query on every HTMX fragment rendered with a `RequestContext`.

## Requirements

### App and settings (`freedom_ls/comms/`)

- New app `freedom_ls.comms`: `apps.py` with `name="freedom_ls.comms"`,
  `label="freedom_ls_comms"`, `verbose_name="Notifications"`, `default_auto_field` set (per
  `docs/app_conventions.md`). Add it to `INSTALLED_APPS` in `config/settings_base.py`.
- `freedom_ls/comms/urls.py` with `app_name = "comms"`, included from `config/urls.py` as
  `path("notifications/", include("freedom_ls.comms.urls"))`.
- `freedom_ls/base/notification_categories.py`, importable from settings without loading apps,
  like `freedom_ls/base/webhook_event_types.py`:

  ```python
  @dataclass(frozen=True)
  class NotificationCategory:
      key: str            # stable; preferences and digests key off it
      label: StrPromise   # gettext_lazy, e.g. "Course registration"
      icon: str           # a c-icon name
      message: StrPromise # gettext_lazy with named %(...)s placeholders
      url_builder: str | None  # import path of (target) -> str | None

  FLS_NOTIFICATION_CATEGORIES: list[NotificationCategory] = [...]
  ```

  | key | label | icon | message | url_builder |
  | --- | --- | --- | --- | --- |
  | `course.registered` | Course registration | `course` | You're registered for %(course_title)s | `freedom_ls.learner_interface.notification_urls.course_home_url` |
  | `course.completed` | Course completion | `achievement` | You completed %(course_title)s | same |

  Both icons, and the bell's `notifications`, are existing semantic names, so no icon set needs a
  new mapping. The URL builder lives with the URL it reverses. `course_home_url(course)` returns
  `reverse("learner_interface:course_home", kwargs={"course_slug": course.slug})`.
- `freedom_ls/comms/config.py`: `CommsConfig(AppSettings)` declaring
  - `NOTIFICATION_CATEGORIES: list[NotificationCategory]`, default `FLS_NOTIFICATION_CATEGORIES`;
  - `NOTIFICATION_DELIVERY_BACKENDS: list[str]`, default `[]`;
  - `NOTIFICATION_BADGE_POLL_SECONDS: int`, default `45`.

  `config/settings_base.py` sets `NOTIFICATION_CATEGORIES = FLS_NOTIFICATION_CATEGORIES` with a
  comment showing how a downstream project appends its own, next to `WEBHOOK_EVENT_TYPES` (line
  479).
- `freedom_ls/comms/checks.py`: a system check that errors on duplicate category keys and on a
  delivery-backend path that doesn't import.
- A lookup `get_notification_category(key)` in `comms` that raises `ValueError` for an unknown
  key.

### Model (`freedom_ls/comms/models.py`)

`Notification(SiteAwareModel)`:

| Field | Definition |
| --- | --- |
| `user` | FK `AUTH_USER_MODEL`, `on_delete=CASCADE`, `related_name="notifications"` |
| `category` | `CharField(max_length=100)`, a registered key |
| `content_type` | FK `ContentType`, `on_delete=CASCADE` |
| `object_id` | `CharField(max_length=255)` |
| `target` | `GenericForeignKey("content_type", "object_id")`. No `GenericRelation` on `Course`, so deleting a target leaves the notification in place. |
| `data` | `JSONField(default=dict)` |
| `created_at` | `DateTimeField(auto_now_add=True)` |
| `seen_at` | `DateTimeField(null=True, blank=True)` |
| `read_at` | `DateTimeField(null=True, blank=True)` |

- Ordering is `("-created_at", "-id")`, so pagination is stable when timestamps tie.
- Indexes: `["user", "site", "-created_at"]` for the lists, and a partial index on
  `["user", "site"]` with `condition=Q(read_at__isnull=True, seen_at__isnull=True)` for the badge
  count.
- Queryset helpers on a manager that extends `SiteAwareManager`, so request-time site filtering
  stays: `for_user(user)`, `unread()` (`read_at` null),
  `unseen()` (unread and `seen_at` null). Rows whose category is no longer registered are left
  out of every surface and the badge.
- Rendering helpers: `message` (the category message filled from `data`) and `url`. `url` calls
  the category's URL builder on `target`, or returns `None` when the target no longer resolves or
  the category has no builder.
- `freedom_ls/comms/factories.py`: `NotificationFactory`.
- Run `makemigrations` for the new app.

### Raising (`freedom_ls/comms/notify.py`)

```python
def raise_notification(
    *, user: User, category: str, target: Model, site_id: UUID, data: dict[str, str]
) -> None:
```

- It first looks up the category (`ValueError` if the key is unknown) and checks that `data`
  supplies every placeholder in the category's `message` (`ValueError` naming any missing key).
  Both raise in the caller.
- Then, via `transaction.on_commit(..., robust=True)`, it creates the row with the given
  `site_id` (never from the request) and, for each path in `NOTIFICATION_DELIVERY_BACKENDS`,
  enqueues `deliver_notification` with `default_task_backend.enqueue(...)`, passing the backend
  path, the notification id and `site_id`. Outside a transaction `on_commit` runs at once, so
  management commands and tasks work unchanged.
- `freedom_ls/comms/delivery.py`: base class `NotificationDeliveryBackend` with
  `deliver(self, notification: Notification) -> None`, in the manner of `CourseAccessBackend`.
  The `@task` `deliver_notification` in `freedom_ls/comms/tasks.py` loads the notification through
  `_base_manager` filtered by `site_id`, resolves the backend with `import_string`, and calls
  `deliver`. Each backend runs as its own task, so one failing affects neither the row nor another
  backend.

### First events

- **Course registration** in `freedom_ls/learner_progress/signals.py`, `_ensure_and_announce`: when
  `announce` is true, call `raise_notification(user=learner.user, category="course.registered",
  target=registration.course, site_id=registration.site_id, data={"course_title":
  registration.course.title})`, placed before `fire_webhook_event`. The receiver's existing
  `created`/`is_active`/`raw` guards set the rules:
  - A new active registration from any path (self-registration, admin, QA commands, factories)
    notifies once.
  - Reactivating a registration, deactivating one, or activating one that was created inactive
    does not notify.
- **Course completion** in `course_finish`, `freedom_ls/learner_interface/views.py` (the branch at
  line 1636 that stamps `completed_time`): after the `save`, call
  `raise_notification(user=request.user, category="course.completed", target=course,
  site_id=course_progress.site_id, data={"course_title": course.title})`, before
  `fire_webhook_event`.
- Cohort registration and cohort membership raise nothing.

### Views and URLs (`freedom_ls/comms/views.py`)

Function-based views. Every one uses a guard built on `redirect_to_auth`, not a bare
`@login_required`, so an expired session under HTMX gets a 204 with `HX-Redirect`. Every query
goes through `Notification.objects` (the site-aware manager) filtered to `request.user`. Single-row
views use `get_object_or_404` on that filtered queryset, so another user's id returns 404.

| URL name | Path | Method | Does |
| --- | --- | --- | --- |
| `notification_list` | `""` | GET | The notification centre. `?filter=unread`, `?page=`. Marks the user's unseen rows seen. An HTMX page change returns only the list fragment. |
| `notification_panel` | `panel/` | GET | Panel fragment: the eight newest notifications. Marks unseen rows seen and returns the badge out of band. |
| `notification_badge` | `badge/` | GET | The badge fragment only, for polling. Does not extend a base template. |
| `notification_open` | `<uuid:pk>/open/` | GET | Sets `read_at` if unset and redirects to `notification.url`. If the target is gone, it redirects to the centre. |
| `notification_mark_read` | `<uuid:pk>/read/` | POST | Sets `read_at`. |
| `notification_mark_unread` | `<uuid:pk>/unread/` | POST | Clears `read_at`. |
| `notification_mark_all_read` | `read-all/` | POST | Sets `read_at` on all the user's unread rows on this site, not just those shown. |

- Mark actions return, for HTMX, the updated fragment of the surface that sent them (row, panel or
  list) plus the badge out of band, so the count changes without waiting for a poll. Without
  HTMX they redirect to the centre.
- Lists call `prefetch_related("target")` so target resolution doesn't run one query per row.
- The centre shows 20 per page.

### Header, bell and badge templates

- `freedom_ls/comms/templatetags/comms_tags.py`: inclusion tag `notification_bell`, rendering
  `comms/partials/notification_bell.html` with the unseen count and
  `NOTIFICATION_BADGE_POLL_SECONDS`.
- `freedom_ls/base/templates/partials/header_bar.html`: inside `{% if user.is_authenticated %}`,
  put `{% notification_bell %}` immediately before the `header_bar_user_menu.html` include.
- Bell button: `c-icon name="notifications"`, `aria-expanded`, `aria-controls` naming the panel,
  accessible name "Notifications, N new" or "Notifications, none new", using the exact count
  even above 99. The count sits in a `role="status"` live region. The visible badge shows
  1 to 99, then "99+", and is hidden at 0.
- Polling: the badge refreshes from `comms:notification_badge` every
  `NOTIFICATION_BADGE_POLL_SECONDS` while the tab is visible, and at once when a hidden tab
  becomes visible. The first count comes from the page render, so there is no poll on load.
  The visibility check can't be an `hx-trigger` filter expression, because htmx evaluates those
  with `Function`, and FLS runs Alpine's CSP build under a CSP with no `unsafe-eval`. The bell's Alpine
  component owns the timer and the visibility check and triggers the refresh.
- A refresh or out-of-band update never replaces the bell button, so keyboard focus survives. It
  updates the visible badge, the accessible name and the live region in place. A failed poll
  leaves the badge as it was. The count is not cached. HTMX polling is the only transport;
  nothing needs Channels or ASGI.
- Panel: the same Alpine component (see `fls-dev:alpine-js`) handles open and close. Escape and an
  outside click close it, and closing returns focus to the bell. Its content loads from
  `comms:notification_panel` each time it opens. At 375px it is a full-width sheet with a close
  button.
- Panel content (from design section 1): heading "Notifications" with "N unread", up to eight
  rows, and a footer with "Mark all as read" (disabled when nothing is unread) and "See all"
  (to the centre). If loading fails, the panel shows "Couldn't load your notifications." with a
  "Try again" button.
- A row (panel and centre): category icon; the message, linked through `notification_open` when
  `url` is not `None` and plain text otherwise; category label · relative time. An unread row
  has visually hidden "Unread." before the text, an "Unread" marker with an icon, and heavier
  text weight, so colour is never the only cue. Time is `<time datetime="…" title="<absolute>">`
  with relative text ("Just now", "N min ago", "N hours ago", "Yesterday, 16:20", "21 Sep", with
  the year added outside the current year).
- Colours come from FLS role tokens (`brand-guidelines`) and icons from `c-icon`. No value is
  copied from the design's theme.

### Notification centre (`comms/notification_list.html`)

- Extends the interface base like other signed-in pages. Heading "Notifications".
- Toolbar: All / Unread filter links (the current one marked `aria-current`, Unread showing its
  count), and "Mark all as read" (disabled when nothing is unread, hidden when the list is empty).
- Rows are grouped under day headings: "Today", "Yesterday", then "Monday 21 September", with the
  year added outside the current year. Days follow the active timezone. A day may split across
  pages. Each unread row has "Mark read" and each read row has "Mark unread". At 375px both are
  icon buttons whose accessible name includes the message.
- States from design section 2: populated; all read (a status banner "You're up to date.
  Everything has been read."); empty ("Nothing yet." / "We'll tell you here when something
  happens on your courses."); Unread filter with nothing unread ("No unread notifications.").
- Pagination uses `c-pagination` with `table_id` set to the list's id and the filter carried in
  the query string.
- Every control is keyboard-reachable with a visible focus ring. Every screen meets WCAG 2.2 AA
  and works at 375px.

## Testing

Unit and integration (`fls-dev:testing`, `mock_site_context` where the site-aware manager must
resolve a site):

- `raise_notification`: an unknown category raises; a missing data key raises; a valid call writes
  one row with the given site, target and data; a rolled-back transaction writes nothing; it works
  with no request.
- Failure isolation: an exception while writing the row, or from a backend, does not propagate
  out of registration creation or `course_finish`. A `fire_webhook_event` exception in either
  hook does not stop the notification.
- Delivery: with a fake backend configured, the task runs once per backend with the right
  notification. With the list empty, nothing is enqueued.
- System check: duplicate keys and bad backend paths error.
- Registration hook: self-registration, admin creation and a factory each notify once.
  Reactivation, deactivation, an inactive create, `raw` loads and cohort registration do not.
- Completion hook: the first finish notifies and repeat visits do not. It runs before the
  webhook.
- Rendering: the message uses the stored title after the course is renamed; `url` follows the new
  slug; a deleted target renders text with no link; an unregistered category is excluded.
- Seen and read: opening the panel or the centre marks unseen rows seen and zeroes the badge;
  mark read, mark unread and mark all read change only the current user's rows on the current
  site; mark unread doesn't restore the badge; `notification_open` marks read and redirects to the
  live URL, or to the centre when the target is gone.
- Isolation: another user's notification id returns 404 from every single-row view and is left
  unchanged; mark all read leaves other users' rows alone; a user on two sites sees only the
  current site's rows and count.
- Auth: every view answers an anonymous HTMX request with 204 and `HX-Redirect`.
- Query counts: the badge, panel and centre page run the same number of queries for 2 and 200
  notifications.
- Badge: the cap at "99+", the accessible name with the exact count, and the poll interval taken
  from the setting.

Playwright (`fls-dev:playwright-tests`):

- The bell opens and closes the panel by mouse and keyboard, `aria-expanded` follows, and focus
  returns to the bell on Escape.
- Opening the panel clears the badge. Mark all as read updates the panel and badge with no second
  request.
- The centre: filters, mark read and unread, pagination.
- A learner self-registers and then sees the registration notification in the bell.
- A badge refresh while the bell has focus leaves focus on the bell.
- The panel is a full-width sheet at 375px.

## Open questions

Defaults taken; overrule any of them.

- Mark unread does not put a notification back on the badge (Decision 4).
- A stored notification whose category a project later removes is hidden everywhere.
- Day grouping uses the site's active timezone (UTC today) until users have their own timezone.
- The centre shows 20 per page.
- The row marker reads "Unread" (the design draws "New"), so "new" keeps meaning unseen, as in the
  badge's accessible name.

## Success criteria

- Registering a learner for a course, by any path, produces exactly one `course.registered`
  notification for that learner's user on the registration's site.
- Finishing a course produces exactly one `course.completed` notification. Revisiting the
  completion page produces none.
- Making `raise_notification`'s write raise does not change the response of self-registration or
  `course_finish`.
- A signed-in learner and a signed-in educator both see the bell left of the avatar on the
  dashboard, the course player and the educator interface.
- The badge updates within one poll interval of a new notification while the tab is visible, and
  on returning to a hidden tab.
- Opening the panel or the centre zeroes the badge in the same response; following a link marks
  that notification read.
- `uv run pytest` passes, including the new unit and Playwright tests.
- `comms` does not import `webhooks` (checked by grep).
