# Frontend QA: notifications core

FLS now keeps a record of what happened to a user and shows it in two places: a bell with an
unread badge in the shared header, and a notification centre at `/notifications/`. Two events
raise notifications: registering for a course (`course.registered`, "You're registered for
<course>") and finishing one (`course.completed`, "You completed <course>").

Two words carry the whole feature. **Seen** means the user has opened the bell panel or the
centre since the notification arrived; it clears the badge. **Read** means the user followed the
notification's link or pressed "Mark read"; it can be undone with "Mark unread". A row marked
unread again shows as unread but does not come back onto the badge.

Beyond the golden path this run hunts for:

- **A notification raised twice, or never.** Re-registering, reactivating a registration, and
  revisiting the finish page must all raise nothing. Every registration path (self-service,
  admin) must raise exactly one.
- **Another user's rows leaking.** Every single-row URL takes a UUID. A UUID belonging to another
  user must 404 and leave that row untouched.
- **The badge lying.** It must clear when the panel or centre opens, stay clear after mark
  unread, refresh within one poll interval while the tab is visible, and refresh at once when a
  hidden tab comes back.
- **A swap that steals focus or breaks the header.** Badge refreshes and panel updates must never
  replace the bell button. The user menu next to it must keep working.
- **A registration that fails because notifications failed.** The bell is a side effect of
  registration and completion, never a gate on them.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh`
wherever this document writes `<PORT>`. Shell variables do not survive between tool calls.

The Django debug toolbar sits over parts of the header on narrow viewports. Remove it with
`document.getElementById('djDebug')?.remove()` before clicking anything it covers.

Credentials for the admin account are in `.claude/fls-dev/config.md`. Seeded QA users follow the
DemoDev convention: the password is the email address.

## §0 Setup

### 0.1 Server

1. Run `.claude/ds/scripts/find_available_port.sh`. Note the number and use it literally.
2. Start the server backgrounded, as its own call:
   `uv run python manage.py runserver <PORT>`
3. Base URL is `http://127.0.0.1:<PORT>`.

### 0.2 Seed data

Create these with the `fls-dev:qa-data-helper` agent (factories, `mock_site_context`, all on the
DemoDev site). Note every printed slug and UUID.

| Name | What |
| --- | --- |
| `notify.learner@demodev.example.com` | Learner A. 26 notifications: 3 unseen and unread created in the last hour (one "Just now", one "12 min ago"), 2 seen but unread from yesterday, the rest read and spread over the past six weeks so the centre spans two pages and several day headings. Include one whose course has since been deleted, and one with the category `legacy.unregistered` (not in the registry). |
| `notify.other@demodev.example.com` | Learner B. 2 unseen notifications. Print their UUIDs. |
| `notify.educator@demodev.example.com` | An educator with access to the educator interface and 1 unseen notification. |
| `notify.many@demodev.example.com` | Learner C with 120 unseen notifications. |
| Course "QA Notify Open" | Free, visible, self-registration allowed, with one short markdown topic. Learner A is **not** registered. |
| Course "QA Notify Finish" | Free, one short markdown topic. Learner A is registered and has not finished. |
| Course "QA Notify Reactivate" | Learner A has a registration that an admin deactivated (`is_active=False`). Print the registration UUID. |

No notification may exist for Learner A on "QA Notify Open" or "QA Notify Finish" before the run.

### 0.3 Raising a notification from the shell

Some checks need a notification to arrive while a tab is open. Use this as its own call, with the
email of the target user and the DemoDev site id:

```bash
uv run python manage.py shell -c "
from django.contrib.sites.models import Site
from freedom_ls.accounts.models import User
from freedom_ls.content_engine.models import Course
from freedom_ls.comms.notify import raise_notification
site = Site.objects.get(name='DemoDev')
user = User._base_manager.get(email='notify.learner@demodev.example.com')
course = Course._base_manager.filter(site=site).first()
raise_notification(user=user, category='course.registered', target=course, site_id=site.pk, data={'course_title': course.title})
print('raised')
"
```

## §1 The bell in the header

Log in as Learner A.

1. On the dashboard, expect a bell icon left of the avatar. Its badge shows **3**. Read the
   button's accessible name (snapshot or `getAttribute`): "Notifications, 3 new".
2. Open "QA Notify Finish" from the dashboard so the course player renders. The bell and badge are
   still in the header.
3. Log out. Log in as the educator. Visit `/educator/`. The bell is there with badge **1**.
4. Log in as Learner C. The badge reads **99+**; the accessible name says "Notifications, 120 new".
5. Log out. Visit `/`. Anonymous: no bell, the login prompt as before.
6. **Side effect.** Log in as Learner A again. Open the avatar menu next to the bell; it still
   opens, its items still work (Profile). Close it with Escape.

## §2 Badge polling

Log in as Learner A on the dashboard. Badge **3**.

1. Run the §0.3 shell command. Do not touch the page. Within 45 seconds the badge reads **4**. No
   page reload happened (the scroll position and any typed text survive).
2. Focus the bell with Tab. Run the shell command again. After the next refresh the badge reads
   **5** and `document.activeElement` is still the bell button.
3. Open a second tab on the site, switch back to the first, and confirm nothing else changed.
   Hide the first tab (switch to the second) and run the shell command. Switch back: the badge
   updates within about a second, not after a full interval.
4. Stop the server. Wait longer than a poll interval. The badge still shows its last count, not
   an error and not 0. Start the server again.

## §3 The panel

Log in as Learner A on the dashboard.

1. Click the bell. A panel opens under it: heading "Notifications" with "N unread", the eight
   newest rows, and a footer with "Mark all as read" and "See all". `aria-expanded` on the bell is
   `true`. The badge disappears in the same moment (no wait, no second request other than the
   panel load).
2. Each row shows a category icon, the message, the category label and a relative time ("Just
   now", "12 min ago", "Yesterday, HH:MM", "21 Sep"). Unread rows carry an "Unread" marker and
   heavier text. The deleted-course row, if it is among the eight, shows the message as plain
   text with no link.
3. Press Escape. The panel closes and focus is on the bell. Click the bell, then click elsewhere
   on the page. The panel closes.
4. Reload. The badge stays hidden: opening the panel marked those rows seen.
5. Tab to the bell, press Enter: it opens. Press Space: it toggles.
6. Click "Mark all as read". The rows lose their "Unread" markers, "N unread" disappears from the
   heading, and the button is disabled. No second request was needed for the badge (it was
   already 0).
7. Click "See all". You land on `/notifications/`.
8. **Failure branch.** Stop the server. Reload is impossible, so instead open the panel on a page
   that is already loaded (use the copy of the dashboard in another tab): it shows "Couldn't load
   your notifications." with "Try again". Start the server and click "Try again". The rows load.

## §4 The notification centre

Log in as Learner A. Visit `/notifications/`.

1. Heading "Notifications". Toolbar: "All" (current), "Unread" with a count, "Mark all as read".
2. Rows sit under day headings: "Today", "Yesterday", then "Monday 21 September" style headings.
   20 rows on page 1, pagination below. Click page 2: the list swaps in place and the URL carries
   `?page=2`. The `legacy.unregistered` row appears nowhere on either page.
3. Click "Unread". Only unread rows show. The URL carries `filter=unread`. If more than 20 exist,
   page 2 keeps `filter=unread`.
4. Mark one row read with its "Mark read" button. It leaves the Unread list. Switch to "All": it
   shows read with a "Mark unread" button. Click it: it is unread again.
5. **Badge check.** Read the badge after step 4: still 0. Mark unread did not restore it.
6. Click a row's message link on a course that still exists. You land on that course's home page
   (the resume redirect). Back at `/notifications/` that row is read.
7. Find the deleted-course row: plain text, no link. Take its UUID from the page (the `id` of its
   button ends in the UUID) and visit `/notifications/<uuid>/open/`. You are redirected to
   `/notifications/`, and the row is now read.
8. Click "Mark all as read". Every row is read; a banner "You're up to date. Everything has been
   read." shows; "Mark all as read" is disabled. Click it again anyway (it is disabled, so use
   `fetch` from the console with method POST and header `HX-Request: true` to `/notifications/read-all/`):
   the response is 200 and nothing changed.
9. Click "Unread": "No unread notifications."
10. Log in as a brand-new user (sign up via `/accounts/signup/`, confirm in Mailpit at
    `http://localhost:8025`) and visit `/notifications/`: "Nothing yet." / "We'll tell you here
    when something happens on your courses." with no "Mark all as read" button.

## §5 The two events

Log in as Learner A.

1. Visit the detail page for "QA Notify Open" and press its register button. You land in the
   course. The badge reads **1** (or more if §2 left unseen rows). Open the panel: the top row is
   "You're registered for QA Notify Open", label "Course registration", "Just now".
2. Visit the register URL for the same course again (repeat the click from the detail page if it
   is still offered, otherwise re-enter the same URL). No second registration notification.
3. Visit the register URL for "QA Notify Reactivate". You get into the course. Open the panel:
   there is **no** "You're registered for QA Notify Reactivate" row. Reactivation is silent.
4. Open "QA Notify Finish", read its one topic to the end and reach the finish page. Open the
   panel: "You completed QA Notify Finish", label "Course completion".
5. Reload the finish page twice. Still exactly one completion notification for that course in
   the centre.
6. **Admin path.** Log in as the admin in another browser context. In the admin, add a
   `LearnerCourseRegistration` for Learner B on "QA Notify Open". Log in as Learner B: one new
   "You're registered for QA Notify Open" row.
7. **Side effect.** In the admin, open Webhooks › Webhook events. The registration and completion
   above each created a `course.registered` / `course.completed` event row too. Notifications
   did not replace webhooks.

## §6 Isolation and permission branches

Log in as Learner A. Use Learner B's two notification UUIDs from §0.2.

1. Visit `/notifications/<B-uuid>/open/`: 404.
2. From the console, `fetch('/notifications/<B-uuid>/read/', {method: 'POST', headers: {'HX-Request': 'true', 'X-CSRFToken': document.body.getAttribute('hx-headers') && JSON.parse(document.body.getAttribute('hx-headers'))['X-CSRFToken']}})`:
   status 404. Same for `/unread/`.
3. Log in as Learner B: both rows are still unseen and unread (badge **2**, "Unread" markers).
4. As Learner B, `/notifications/read-all/` via the same fetch, then log in as Learner A: A's
   unread rows are unchanged.
5. `fetch('/notifications/<A-uuid>/read/', {method: 'GET'})` with A's own UUID: 405.
6. `/notifications/00000000-0000-0000-0000-000000000000/open/`: 404. `/notifications/not-a-uuid/open/`: 404.
7. Log out. Visit `/notifications/`: redirected to the login page with `next` pointing back.
   From the console, `fetch('/notifications/badge/', {headers: {'HX-Request': 'true'}})`: status
   204 and an `HX-Redirect` response header. Same for `/notifications/panel/`.
8. **Expired session under HTMX.** Log in as Learner A, then in a second tab log out. Back in the
   first tab click the bell: the browser navigates to the login page rather than swapping a login
   form into the panel.

## §8 Accessibility pass

On the dashboard and on `/notifications/` at 1280px, as Learner A:

1. Tab through the header: the bell has a visible focus ring. Its name announces the count. The
   badge count region has `role="status"`.
2. Open the panel with the keyboard; Tab moves through its rows and footer buttons; Escape returns
   focus to the bell.
3. On the centre, each unread row's link text is preceded by visually hidden "Unread." (check the
   accessibility tree or the link's accessible name).
4. Every `<time>` element has a `datetime` attribute and a `title` with the absolute time.
