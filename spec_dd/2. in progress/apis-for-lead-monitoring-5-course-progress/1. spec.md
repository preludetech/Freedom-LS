# Spec: Lead monitoring API, course progress

Spec 5 of 6 in the Lead monitoring API effort. Inputs: `idea.md` and the `research_*.md` files
beside it, the "Lead monitoring API" section of `spec_dd/1. next/roadmap.md`, the shipped
foundation spec `spec_dd/3. done/2026-11-03_09:54_apis-for-lead-monitoring-1-foundation-and-users/1. spec.md`,
and spec 4's `spec_dd/2. in progress/apis-for-lead-monitoring-4-registrations-and-interest/1. spec.md`.
The foundation's conventions (auth, scopes, site filtering, `(updated_at, id)` cursor, inclusive
`updated_since`, error shape, throttling) apply unchanged.

## Purpose

Registrations say who was enrolled; progress says whether that enrolment turned into activity and
completion. No export or API exposes `CourseProgress` today, and the model has no changed-since
signal: `progress_percentage` can change with no timestamp moving. This spec adds a read-only
`/api/v1/course-progress/` endpoint under the `registrations_and_progress` scope and gives
`CourseProgress` an `updated_at` that moves on every change to the row.

## Scope

In:

- `GET`, `HEAD` and `OPTIONS` list and detail for `CourseProgress`, one row per `CourseProgress`,
  scoped to the key's site.
- `CourseProgress.updated_at`, moved by every writer of the row, with a backfill for existing rows.
- `docs/api.md` and `docs/product/security-and-data-handling.md`.

Out:

- Topic progress, form attempts, scores and `last_accessed_item`.
- `CourseProgress.created_at` (the registration date): the registration endpoints expose
  `registered_at`.
- Any filter beyond `updated_since`, `cursor` and `page_size`.
- An `is_active` flag on the row. Rows under a deactivated registration or `Learner` are returned
  like any other.
- A deletion feed, write endpoints, webhooks, admin exports, admin changes, and any change to how
  the player sets `last_accessed_time`.

## Decisions

| Decision | Reason |
| --- | --- |
| Spec 4 lands first. This spec imports its user and organisation flattenings and its widened pagination type bound, and defines neither. | Spec 4 fixes both and records the dependency in the roadmap. |
| A bare `updated_at = models.DateTimeField(auto_now=True)`, not `TimestampedModel`. `CourseProgress` stays out of `TIMESTAMPED_MODELS` in `freedom_ls/contrib/conformance/tests/test_timestamped_models.py`. | The mixin would redeclare `created_at`, which here means the registration date, and that guardrail excludes progress records for the same reason. |
| `CourseProgress.save` adds `"updated_at"` to a non-empty `update_fields`. | Every production writer passes `update_fields`, which skips `auto_now`. One override also covers future writers. |
| API timestamp fields keep the model field names: `started_at`, `last_accessed_time`, `completed_time`. | The names are the vocabulary; spec 4 does the same with `registered_at`. |
| The registration is exposed as `registration_id` plus `registration_kind` (`"individual"` or `"cohort"`). | Spec 4 has no `kind` field and leaves the name to this spec. Exactly one registration FK is set (`course_progress_has_exactly_one_grant`). |
| Changes to the flattened user, organisation or course data, and to the registration's `is_active`, do not move the row's `updated_at`. | Same rule as spec 4. The users and registration endpoints carry those changes. |

## Requirements

### Model and migration

`freedom_ls/learner_progress/models.py`, `CourseProgress`:

- Add `updated_at = models.DateTimeField(auto_now=True)`, with a comment saying it is the
  changed-since signal, moved by every write, and that `last_accessed_time` is the learner's last
  visit and is not it.
- Add `models.Index(fields=["site", "updated_at", "id"], name="lp_progress_site_upd_idx")` to
  `Meta.indexes`, after the existing `(learner, course)` index. This copies
  `accounts_user_site_updated_idx`.
- Override `save` so that when `update_fields` is not `None` and not empty, `"updated_at"` is added
  to it before `super().save()`.

New migration `freedom_ls/learner_progress/migrations/0003_*.py`: add the column nullable; in
`RunPython` on the historical model, run one set-based
`_base_manager.update(updated_at=Greatest("created_at", "started_at", "last_accessed_time", "completed_time"))`
(PostgreSQL `GREATEST` skips nulls and `created_at` is never null); alter to non-null
`auto_now=True`; add the index. The reverse of the backfill is a no-op. Existing migrations are not
edited.

### Writers of `CourseProgress`

Each must leave `updated_at` at the time of the write:

| Writer | Location | Change |
| --- | --- | --- |
| Percentage recalculation | `freedom_ls/learner_progress/signals.py` `recalculate_progress_percentage` | Covered by the `save` override. Also: save only when the new percentage differs from the stored one, as the command below already does, so a no-op recalculation does not re-emit the row. |
| Percentage backfill command | `freedom_ls/learner_progress/management/commands/recalculate_progress_percentages.py` | Covered by the `save` override. |
| Cohort move, record moves | `signals.py` `cohort_registration` save in the progress-carry receiver | Covered by the `save` override. |
| Cohort move, swap | `signals.py`, the `CourseProgress._base_manager.filter(pk__in=...).update(cohort_registration=Case(...))` | Add `updated_at=timezone.now()` to the `update()` call. |
| Player visit | `freedom_ls/learner_interface/views.py`, the `save(update_fields=["last_accessed_item", "last_accessed_time", "started_at"])` | Covered by the `save` override. |
| Course completion | `freedom_ls/learner_interface/views.py`, the `save(update_fields=["completed_time"])` | Covered by the `save` override. |
| Minting | `freedom_ls/learner_progress/utils.py` `ensure_course_progress_record` (`get_or_create`), `ensure_course_progress_records_for_cohort_registration` (`bulk_create`) | None: `auto_now` stamps on insert. |

No other application code calls `QuerySet.update()` or `bulk_update()` on `CourseProgress`. The
`qa_helpers` seeding commands that do stay as they are. Application code added later that bypasses
`save()` must set `updated_at` itself.

`recalculate_progress_percentage` keeps `last_accessed_time` out of the write: recalculation moves
`updated_at` and never `last_accessed_time`.

### Endpoint

New `freedom_ls/learner_progress/api.py`, following `freedom_ls/accounts/api.py` and spec 4's
`freedom_ls/learner_management/api.py`:

- A `ModelSerializer` with an explicit `fields` tuple, all read-only, using spec 4's user
  flattening (from `freedom_ls/accounts/api.py`, source `learner.user`) and organisation flattening
  (from `freedom_ls/learner_management/api.py`, source `learner.organisation`).
- A `UpdatedSinceFilterSet` subclass with `fields: list[str] = []`.
- A `ReadOnlyApiViewSet` subclass with `required_scope = ApiScope.REGISTRATIONS_AND_PROGRESS` and a
  `get_queryset` that starts from `CourseProgress._base_manager` with
  `select_related("course", "learner__user", "learner__organisation")`, leaving the key's site to
  `filter_queryset`. `last_accessed_item` and the registration rows are not joined: the registration
  id and kind come from `learner_registration_id` and `cohort_registration_id`.
- `router.register("course-progress", ..., basename="course_progress")`.
  `autodiscover_modules("api")` in `freedom_ls/api/urls.py` picks the module up.

Fields, in this order:

| Field | Type | Source |
| --- | --- | --- |
| `id` | UUID string | `id` |
| `course_id` | UUID string | `course_id` |
| `course_title` | string | `course.title` |
| `registration_id` | UUID string | whichever of `learner_registration_id`, `cohort_registration_id` is set |
| `registration_kind` | `"individual"` or `"cohort"` | `"individual"` when `learner_registration_id` is set, else `"cohort"` |
| `user_id`, `user_email`, `user_first_name`, `user_last_name` | integer, strings | spec 4's user flattening |
| `organisation_id`, `organisation_name` | UUID string, string | spec 4's organisation flattening |
| `progress_percentage` | integer, 0 to 100 | `progress_percentage` |
| `started_at` | ISO 8601 or `null` | `started_at` |
| `last_accessed_time` | ISO 8601 or `null` | `last_accessed_time` |
| `completed_time` | ISO 8601 or `null` | `completed_time` |
| `updated_at` | ISO 8601 | `updated_at` |

`registration_id` and every `*_id` field are declared with their type, and `registration_kind` as
a two-value choice, so the OpenAPI schema types them. `registration_id` matches the `id` of the
learner course registrations or cohort course registrations endpoint, as `registration_kind` says.
No other field is returned.

## Testing

Endpoint tests in `freedom_ls/learner_progress/tests/test_api.py`, following
`freedom_ls/accounts/tests/test_api.py` and spec 4's endpoint tests, with the helpers in
`freedom_ls/api/tests/helpers.py`, the throttle cache cleared as `freedom_ls/api/tests/conftest.py`
does, and `ApiKeyFactory(scopes=[ApiScope.REGISTRATIONS_AND_PROGRESS])`. Prove:

- A key without `registrations_and_progress` gets 403; no key gets 401.
- The response's key set equals the field list above exactly.
- A row granted by a learner course registration has `registration_kind: "individual"` and that
  registration's id; a row granted by a cohort course registration has `"cohort"` and the cohort
  registration's id.
- A not-started row returns `started_at`, `last_accessed_time` and `completed_time` as `null` and
  `progress_percentage: 0`.
- A row under a deactivated `LearnerCourseRegistration` is returned.
- Rows on another site are absent from the list, and their detail is 404, using a second real
  `Site`.
- `updated_since` returns rows at or after the given time, and paging walks rows that share one
  `updated_at` with no gaps or duplicates.
- The query count is the same at page size 2 and at page size 50, with a mix of individual and
  cohort rows.
- Changing a flattened source (user email or name, organisation name, course title) leaves the
  row's `updated_at` unchanged.

Model and writer tests, in the existing `freedom_ls/learner_progress/tests/test_models.py`,
`test_signals.py`, `tests/management/commands/test_recalculate_progress_percentages.py` and the
`learner_interface` player tests:

- `updated_at` moves on create, on a full `save`, and on a `save(update_fields=[...])`.
- Each writer in the table above advances `updated_at`: recalculation after a topic or form
  completion, the backfill command, both cohort-move branches, a player visit and course completion.
- Recalculation advances `updated_at` and leaves `last_accessed_time` unchanged.
- Recalculation that yields the stored percentage writes nothing and leaves `updated_at` unchanged.
- The backfill sets `updated_at` to the latest of `created_at`, `started_at`,
  `last_accessed_time` and `completed_time`, for a row with only `created_at` and for a row with
  all four, following `freedom_ls/learner_management/tests/test_migrations.py`.

`freedom_ls/api/tests/invariants/test_api_docs.py` must still compile every Python block in
`docs/api.md`.

## Documentation and downstream

`docs/api.md`:

- The intro line and the scope-table note listing which endpoints exist gain course progress.
- A `## Course progress` section after the course interest section, in the shape of the Users
  section (summary table, `### Fields`, `### What moves `updated_at``), with an example response of
  one individual and one cohort row.
- Field notes: `id` is the upsert key. `progress_percentage` is an integer from 0 to 100, the stored
  value the learner sees. `started_at` `null` means not started; `completed_time` `null` means not
  completed. `last_accessed_time` is the learner's last visit and is not the sync key.
  `registration_id` joins to the registration endpoint that `registration_kind` names. Rows are per
  registration: one user can have several rows for one course.
- "What moves `updated_at`": any change to the row, including a background percentage
  recalculation, every content visit in the player, completion and a cohort move. Changes to user,
  organisation or course data and to the registration's `is_active` do not; read those from the
  users and registration endpoints. Rows that existed before this release carry the latest of their
  existing timestamps, so the first pull is a full pull.
- The "Deletions" table gains course progress: every foreign key on the row is `PROTECT`, so rows
  are deleted only by the `danger_clear_all_course_progress` dev command, invisibly to
  `updated_since`.
- The Python example's endpoint list gains `course-progress`.

`docs/product/security-and-data-handling.md`: extend the summary bullet and "### API Access
(built)" to say the `registrations_and_progress` scope exposes learner course progress with user
id, email, first and last name and organisation. Bump "Last updated".

The new `learner_progress -> api` import edge is recorded in `docs/app_structure.md` and
`test_organisation/import_contracts.toml`. The upgrade notes record that `learner_progress` ships a
migration that backfills `updated_at`.

## Success criteria

- The endpoint passes the endpoint tests listed under Testing.
- Completing a topic changes the row's `progress_percentage` and moves its `updated_at`, and the next
  `updated_since` pull returns it.
- After `migrate`, every existing row's `updated_at` equals the latest of its four existing
  timestamps.
- `freedom_ls/api/` and `TIMESTAMPED_MODELS` are unchanged.
- `uv run pytest` passes, mypy passes with no `# type: ignore`, the import linter passes and
  `uv run manage.py makemigrations --check` reports no changes.
- `docs/api.md` has the course progress section and `docs/product/security-and-data-handling.md`
  names the exposed fields with a bumped "Last updated".
