# Spec: SDD review and boy-scout for test organisation

Spec 2 of 15 in the Test organisation and hygiene effort (`spec_dd/1. next/roadmap.md`). The case
for it is in `idea.md` in this directory.

## Purpose

Wire the two test-organisation rules from `ds:testing` (mirroring and dependency direction,
`claude_plugins/django-stack/resources/testing.md` "Test organisation and hygiene") into
`implement_plan`. Batches are written with the testing skills loaded and reviewed against the rules
after they land. A boy-scout then tidies the test files each batch touched and flags plainly broken
code for the user to decide on.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| test-organisation review | coined | The read-only check of one batch's changes, or the whole branch's, against the two rules. `plan_structure_review` checks plans, not code, so no existing term fits. |
| boy-scout | coined | The per-batch agent that tidies test organisation in the touched files and flags broken code. Named for the Boy Scout Rule (`research_boy_scout_rule.md`). |
| touched files | coined | Paths the `[batch N]` commit and its `[batch N review-fix]` commits add or modify, at their current paths. |
| flagged item | coined | A spot in a touched file the boy-scout believes is plainly broken, reported with a recommendation and never fixed by the boy-scout. |

## Scope

In:

- A `## Testing Skills` section in `.claude/sdd/config.md`, its template in `sdd:init`, and this
  project's values.
- Two new agent files, `sdd-implementer` and `sdd-boy-scout`, and `Skill` added to `sdd-worker`'s
  tools.
- The per-batch follow-ons in `implement_plan` Step 2 and a final whole-branch review in Step 3.
- A scope-check script with tests, the commit-subject grammar, resume, and `boy_scout_record.md`.
- Wording updates in `pre_step_rebase.md`, the `sdd` READMEs, `model_tiering.md` and
  `.claude/settings.json`.

Out:

- Pre-commit or CI enforcement of either rule (`test-organisation-and-hygene-3-enforcement-checks`).
- Cleaning up existing tests in any app (specs 4 to 15).
- The boy-scout fixing anything beyond test organisation.
- Gating "every module has a test", and general test quality (assertions, redundancy, coverage).
- Anything added to the GitHub PR body.
- A `todo.md` item or `setup_todo_list.md` template entry for the review or the boy-scout.

## Decisions

1. **Skills are named in config and invoked from the brief, never listed under `skills:` in an
   agent file.** No file `sdd` ships names a `ds` or `fls-dev` skill. The `Agent` tool takes no
   skills at spawn time (`research_agent_skill_preload.md`, Option B), and a subagent can only
   invoke a skill if its `tools:` list includes `Skill`.
2. **Two new agent files, and the reviewer stays `sdd:sdd-worker`.** The implementer and the
   boy-scout need `Bash` and `Edit`, and a named agent's tools cannot be widened per spawn. The
   reviewer only reads files and writes one `.sdd-work/` file (`research_agent_file_shape.md`).
   `sdd-worker` gains `Skill` so it can load the testing skills. Other fan-out briefs never ask it
   to, so their behaviour is unchanged.
3. **`docs/app_structure.md` is read by path.** `sdd` already does this in
   `upstream_change_scan.sh` and `commands/README.md`, so no new coupling. The reviewer reads the
   "Dependency table" (`App | Runtime deps | Test-only deps`) itself rather than reusing
   `plan_structure_review.md`'s parse.
4. **A blank `## Testing Skills` turns the feature off**, because with no skills named there is no
   standard to review against. The batch worker still runs as `sdd:sdd-implementer`, its brief has
   no skill line, and the review, boy-scout and final review are skipped. If
   `docs/app_structure.md` is absent, the review checks mirroring only and the boy-scout removes no
   dependencies.
5. **The review runs before the boy-scout**, so later batches never build on a misplaced test and
   the boy-scout's budget is not spent on the batch's own mistakes. Those mistakes are always
   fixed and never count against the budget.
6. **"Split a module that has grown too big" means splitting a test module that tests more than one
   source module into one module per source module.** `ds:testing` has no size threshold, and
   mirroring gives a mechanical test. A split counts as one file against the budget.
7. **Only the boy-scout is confined to the touched files.** It returns deferred work and flagged
   items, and `implement_plan` writes the follow-ups, "not a bug" comments and the record itself,
   which keeps the scope check strict. Review fixes correct the batch's own mistakes and may edit
   any file that needs it, such as the app's existing `tests/conftest.py`.
8. **Tests pass after each move/edit pair, not after each move commit.** A move-only commit can
   break a test that depends on its directory's `conftest.py`, and the edit commit that follows
   restores it.

### Agent files

- `claude_plugins/sdd/agents/sdd-worker.md`: `tools:` gains `Skill`.

The two new files follow the body shape of `claude_plugins/fls-dev/agents/qa-bugfixer.md`: a
non-interactive contract, staging by explicit path only (never `-a`, `-A`, `.` or a directory),
`uv run git commit`, never `--no-verify`, and a one-line return contract. Neither has a `skills:`
key.

- `claude_plugins/sdd/agents/sdd-implementer.md`: `name: sdd-implementer`,
  `tools: Bash, Read, Edit, Write, Glob, Grep, Skill`, `model: sonnet`. It does one unit of work
  test-first, a plan batch or a fix, commits with the subject its brief gives, and returns
  `status=<ok|failed|blocked> commit=<subject|none> reason=<short>`. Its body holds the TDD and
  commit rules that `implement_plan.md` Step 2 now spells out inline.
- `claude_plugins/sdd/agents/sdd-boy-scout.md`: `name: sdd-boy-scout`, same tools and model. Its
  brief gives the batch number, the touched files, the remaining budget and whether
  `docs/app_structure.md` exists. It:
  - tidies test organisation only, in the touched files. It moves or renames a test file to mirror
    the app, removes an existing cross-app test dependency, or splits a module per Decision 6. It
    changes no assertion.
  - may create a new file only under the `tests/` directory of an app that one of its touched test
    files belongs to, such as a local fixture replacing a cross-app import, or a split-out module.
    A split keeps one part at the original path.
  - commits following the grammar below. A move is always followed by its edit commit. A split or a
    dependency removal is one edit commit on its own. It runs
    `uv run pytest <affected app test dirs>` after each pair or standalone edit.
  - stops at the budget and returns any violation past it as a deferred item, unfixed.
  - flags plainly broken code anywhere in the touched files, production code included, and never
    fixes it. Each flagged item carries `file:line`, why it is broken, a recommendation (fix now /
    record a follow-up / not a bug) and a drafted one-line "why this is correct" comment for the
    "not a bug" answer. It never suppresses its own flag, and does not flag a spot that already has
    a comment explaining why the code is correct.
  - writes `.sdd-work/boy_scout_batch_<N>.md` with sections `Tidied`, `Deferred`, `Flagged` and a
    `status:` footer, and returns `status=<ok|failed|blocked> report=<path> reason=<short>`.

### Commit-subject grammar

Every commit a batch produces carries its number. `implement_plan.md` states this table, and
resume, the budget and the scope check read it.

| Subject | Made by |
| --- | --- |
| `[batch N] <summary>` | implementer (unchanged) |
| `[batch N review-fix] <summary>` | fix agent, for a mechanical review finding |
| `[batch N boy-scout] move <old-path> -> <new-path>` | boy-scout; exactly one file, no content change |
| `[batch N boy-scout] edit <summary>` | boy-scout; the edit that goes with the move before it |
| `[batch N boy-scout] edit split <path> into <a>, <b>` | boy-scout; a split per Decision 6 |
| `[batch N boy-scout] edit drop <app> test dependency on <other-app>` | boy-scout; one cross-app dependency removed |
| `[batch N bug-fix] <summary>` | implementer, for a flagged item answered "fix it now" |
| `[batch N flag-note] <path>` | depth 0, the "not a bug" comment |
| `[batch N record] <summary>` | depth 0: `boy_scout_record.md` plus any follow-up files; always the batch's last commit |
| `[final review-fix] <summary>` | fix agent, for a finding of the final review |

`implement_plan` counts the budget fresh each time from
`git log $(git merge-base origin/main HEAD)..HEAD`:

- files moved = subjects matching `^\[batch [0-9]+ boy-scout\] (move |edit split )`. The cap is 3.
- dependencies removed = subjects matching `^\[batch [0-9]+ boy-scout\] edit drop `. The cap is 1.

Matching `[batch N]` needs the closing bracket straight after the number, so no follow-on commit
reads as the implementation's commit.

### `implement_plan.md` Step 2: the per-batch sequence

- Step 2's spawn changes from `subagent_type: "general-purpose"` to
  `subagent_type: "sdd:sdd-implementer"`, keeping the per-spawn `model: "sonnet"` and the opus
  override note. Step 3's fix agent changes the same way.
- Reword "As its final step, make the `[batch N] <summary>` commit" and "verify the `[batch N]`
  commit exists". A batch now owns several commits, and `[batch N]` is only the implementation's.
- **Resume** replaces the current resume scan. It keys on commit subjects, never SHAs, because
  `pre_step_rebase` rewrites every SHA. For each batch, from `git log` subjects:
  - no `[batch N]` → implement it, then run the follow-ons.
  - `[batch N]` but no `[batch N record]` → run the follow-ons only. Reuse a
    `.sdd-work/test_org_review_batch_<N>.md` or `.sdd-work/boy_scout_batch_<N>.md` that ends
    `status: ok`. A re-run boy-scout's brief lists the batch's existing `boy-scout` commits so it
    finishes a half-done pair rather than repeating it.
  - `[batch N record]` → skip.
- **Follow-ons** run in order after `[batch N]` lands and the suite passes. All are skipped when
  `## Testing Skills` is blank.
  1. **Review.** One `sdd:sdd-worker`, per the fan-out recipe (`plan_from_spec.md` Step 6 shape),
     writes `.sdd-work/test_org_review_batch_<N>.md`. Its brief holds the skill IDs, the touched
     files and the instruction to read `docs/app_structure.md`'s Dependency table. It checks each
     touched test file's placement against mirroring. It checks each touched test, conftest or
     factory file's imports of another app, and fixtures it pulls from a `conftest.py` under
     another app, against that app's Runtime deps. A project-wide pytest plugin (`pytest_plugins`,
     `pytest11`) is infrastructure, not an edge. Each finding has:

     ```
     - rule: mirroring | dependency-direction
       kind: mechanical | judgement
       file: <path>
       detail: <one line>
       recommendation: <one line, concrete enough to execute>
     ```

     `failed` retries twice with the prior error. Depth 0 resolves `blocked` from the code or via
     `AskUserQuestion`.
  2. **Review fixes.** Mechanical findings go to one `sdd:sdd-implementer`, which fixes them and
     commits `[batch N review-fix]`. Judgement findings go to the user at once via
     `AskUserQuestion`, up to four per call. An answer that needs code goes the same fix path, and
     the record notes an accepted new edge for `/app_map`.
  3. **Boy-scout.** Skip when no touched file is a test file or production code, such as a
     docs-only batch. Otherwise spawn one `sdd:sdd-boy-scout` with the remaining budget. `failed` →
     reset uncommitted work and retry up to twice. `blocked` → as for the review.
  4. **Scope check.** Via `sdd:sdd-mechanic`, run the scope-check script with `<from-ref>` at the
     commit before the boy-scout's first commit. A violation stops the run and goes to the user.
     Commits are never reverted automatically.
  5. **Flagged items.** Up to four per `AskUserQuestion`. Each question puts the boy-scout's
     recommendation first and offers three answers:
     - "Not a bug": depth 0 writes the drafted comment at the spot, following the `code-comments`
       skill (why the code is correct, never who judged it), and commits `[batch N flag-note]`.
     - "Fix it now": one `sdd:sdd-implementer` fixes it test-first in `[batch N bug-fix]`, before
       the next batch starts.
     - "Record a follow-up": handled like a deferred item.
  6. **Deferred items and follow-ups.** If a row with status `next` in `spec_dd/1. next/roadmap.md`
     has a Scope covering the item's app, append a bullet to that directory's `idea.md` under
     `## Follow-ups from other specs`, creating the heading if needed. Otherwise write a new
     `spec_dd/1. next/<slug>/idea.md` with `## What`, `## Why` and `## Resources`. `roadmap.md` is
     never edited; `/sdd:roadmap` picks new ideas up.
  7. **Record.** Append a `## Batch N` section to `<spec-dir>/boy_scout_record.md`: review findings
     and their fixes, what was tidied, what was deferred and where it went, and each flagged item
     with the user's answer. Commit it with any follow-up files as `[batch N record]` via
     `sdd:sdd-mechanic`, even when nothing else was committed. Delete the batch's two `.sdd-work/`
     files by name.

### `implement_plan.md` Step 3: the final review

- Before the existing success-criteria check, unless `## Testing Skills` is blank, one
  `sdd:sdd-worker` writes `.sdd-work/test_org_review_final.md` in the same finding format. The
  worker has no `Bash`, so its brief carries the files changed since
  `git merge-base origin/main HEAD`, the path to `boy_scout_record.md` and the budget counts. It
  looks for what no single batch shows: the same new cross-app edge in several batches, an edge
  one batch's boy-scout removed and a later batch reintroduced, and the total budget spent.
  Findings are handled as in follow-ons 2 and 5, with `[final review-fix]` commits.
- Once Step 3 passes, a `## Summary` section goes at the end of `boy_scout_record.md` and is
  committed with the final commit. The user gets a short summary in the conversation: counts of
  fixes, tidies, deferrals and flagged items by answer, plus any edge that needs `/app_map` re-run.

### Scope-check script

`claude_plugins/sdd/scripts/batch_scope_check.sh <batch-number> <from-ref> [<to-ref>]`
(`<to-ref>` defaults to `HEAD`). It follows `upstream_change_scan.sh`'s conventions: a header
comment stating the exit codes, `set -euo pipefail`, a `usage()` helper, and refs validated with
`git rev-parse --verify --quiet`. `implement_plan` resolves its path through the `PLUGINS_ROOT`
rule as in `pre_step_rebase.md` Step 3.

- Allowed set: every path added or modified by commits between the merge base with `origin/main`
  and `<from-ref>` whose subject is `[batch N] …` or `[batch N review-fix] …`.
- Walk each commit in `<from-ref>..<to-ref>` oldest first, checking only those whose subject starts
  `[batch N boy-scout]`. Per commit, with `git diff-tree --name-status -M`, so each move keeps its
  own rename:
  - `R old new`: `old` must be allowed. Then add `new` to the allowed set.
  - `M path`: must be allowed.
  - `A path`: must sit under the `tests/` directory of an app one allowed test file belongs to.
  - `D path` that git did not pair as a rename: a violation.
- Exit 0 in scope. Exit 1 on a violation, printing `OUT_OF_SCOPE:` and one path per line. Exit 64
  on bad arguments.
- `.claude/settings.json` gains `Bash(claude_plugins/sdd/scripts/batch_scope_check.sh:*)` beside
  the two existing `sdd` script entries.

### `pre_step_rebase.md`

Line 102: the scan's commit list shows how far implementation has got. A batch is finished at its
`[batch N record]` commit, or at `[batch N]` when the review is off. `upstream_change_scan.sh` needs
no change.

### Spec 3 hand-off

Whichever of this spec and `test-organisation-and-hygene-3-enforcement-checks` lands second makes
the review run the other's checks. If spec 3 is on `main` when this spec's plan is written, the plan
adds a `Test organisation check:` key to `## Testing Skills`. It names a command that
`sdd:sdd-mechanic` runs over the touched files before the review, and its output goes into the
reviewer's brief. Otherwise spec 3 adds that key.

## Testing

- `tests/test_batch_scope_check.py`, built like `tests/test_upstream_change_scan.py` (a hand-built
  git repo in `tmp_path`, no database):
  - a boy-scout modify inside the allowed set passes
  - a boy-scout move of an allowed file, then an edit at its new path, passes
  - a boy-scout modify of a file outside the set fails and names it
  - a new file under the same app's `tests/` passes
  - a new file under another app fails
  - a delete that is not a rename fails
  - a path touched only by a `[batch N review-fix]` commit is allowed
  - commits of another batch number do not widen the set
  - a non-boy-scout commit in the range is not checked
  - bad arguments exit 64
- The prompt-driven behaviour (resume states, budget counting, question flow) has no automated
  harness. The QA plan runs `/sdd:implement_plan` on a throwaway spec with a planted misplaced
  test, a planted cross-app import and a planted bug, then interrupts it and resumes.

## Open questions

Defaults taken; overrule any of them:

- A blank config disables review and boy-scout (Decision 4), rather than running them against the
  dependency table alone.
- A split counts as one file against the 3-file budget (Decision 6).
- Follow-ups go into a `next` cleanup spec's `idea.md` (follow-on 6), never into a spec already in
  progress in another worktree.
- `[batch N record]` is a new commit every batch (follow-on 7), so resume needs commit subjects
  alone.
