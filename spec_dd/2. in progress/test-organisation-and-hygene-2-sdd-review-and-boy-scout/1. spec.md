# Spec: SDD review and boy-scout for test organisation

Spec 2 of 15 in the Test organisation and hygiene effort (`spec_dd/1. next/roadmap.md`). Source:
`idea.md` in this directory.

## Purpose

`implement_plan` spawns its batch worker as a bare `general-purpose` subagent. The worker never
loads the testing skills, and nothing in SDD reviews the code and tests a batch produces. Every
spec therefore adds to the test disorganisation that specs 4 to 15 exist to clean up. This spec
wires the two test-organisation rules from `ds:testing` (mirroring and dependency direction,
`claude_plugins/django-stack/resources/testing.md` "Test organisation and hygiene") into
`implement_plan`. Batches are written with the testing skills loaded and reviewed against the rules
after they land. A boy-scout then tidies the test files each batch touched and flags plainly broken
code for the user to decide on.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| test-organisation review | coined | The read-only check of one batch's diff (or the whole branch's diff) against the two rules. No existing term: `plan_structure_review` checks plans, not code. |
| boy-scout | coined | The per-batch agent that tidies test organisation in the batch's touched files and flags broken code. From the Boy Scout Rule (`research_boy_scout_rule.md`). |
| touched files | narrowed | Paths the `[batch N]` commit and its `[batch N review-fix]` commits add or modify, at their current paths. |
| flagged item | coined | A spot in a touched file the boy-scout believes is plainly broken, reported with a recommendation and never fixed by the boy-scout. |

## Scope

In:

- A `## Testing Skills` section in `.claude/sdd/config.md`, its template in `sdd:init`, and this
  project's values.
- Two new agent files in `claude_plugins/sdd/agents/`: `sdd-implementer` and `sdd-boy-scout`.
- The per-batch follow-on sequence in `implement_plan`: review, review fixes, boy-scout, scope
  check, flagged-item decisions, record.
- A final whole-branch review in `implement_plan` Step 3.
- A scope-check script with tests, the commit-subject grammar, resume, and `boy_scout_record.md`.
- Wording updates in `pre_step_rebase.md`, the `sdd` READMEs and `.claude/settings.json`.

Out:

- Pre-commit or CI enforcement of either rule (`test-organisation-and-hygene-3-enforcement-checks`).
- Cleaning up existing tests in any app (specs 4 to 15).
- The boy-scout fixing anything beyond test organisation.
- Gating "every module has a test", and general test quality (assertions, redundancy, coverage).
- Anything added to the GitHub PR body.
- A `todo.md` item or `setup_todo_list.md` template entry for the review or the boy-scout.

## Decisions

1. **Skills are named in config and invoked from the brief, never listed under `skills:` in an
   agent file's frontmatter.** No file `sdd` ships names a `ds` or `fls-dev` skill. The `Agent`
   tool takes no skills at spawn time (`research_agent_skill_preload.md`, Option B).
2. **Two new agent files, and the reviewer stays `sdd:sdd-worker`.** The implementer and the
   boy-scout need `Bash` and `Edit`, and a named agent's tools cannot be widened per spawn. The
   reviewer only reads and writes one `.sdd-work/` file (`research_agent_file_shape.md`).
3. **`docs/app_structure.md` is read by path.** `sdd` already does this in
   `upstream_change_scan.sh` and `commands/README.md`, so this adds no coupling. The reviewer
   reads the "Dependency table" (`App | Runtime deps | Test-only deps`) directly and does not cite
   `plan_structure_review.md`'s parse.
4. **Blank `## Testing Skills` turns the feature off.** With no skills named there is no standard to
   review against. The batch worker still runs as `sdd:sdd-implementer`, but the review, boy-scout
   and final review are skipped. If `docs/app_structure.md` is absent, the review checks mirroring
   only, and the boy-scout removes no dependencies.
5. **The review runs before the boy-scout.** Later batches then never build on a misplaced test, and
   the boy-scout's budget is not spent on a batch's own mistakes. The batch's own mistakes are
   always fixed and never count against the budget.
6. **"Split a module that has grown too big" means splitting a test module that tests more than one
   source module into one module per source module.** `ds:testing` has no size threshold, and
   mirroring gives a mechanical criterion. A split counts as one file against the budget.
7. **The boy-scout writes only inside the touched files.** It returns deferred work and flagged
   items, and `implement_plan` writes the follow-ups, "not a bug" comments and the record itself.
   That keeps the scope check strict.
8. **"Fix it now" spawns a fresh `sdd:sdd-implementer`.** It fixes the item test-first in its own
   `[batch N bug-fix]` commit before the next batch starts.
9. **Resume keys on commit subjects, never on SHAs**, because `pre_step_rebase` rewrites every SHA.
   The `[batch N record]` commit marks a batch's follow-ons as finished.
10. **Tests pass after each commit pair, not after each move commit.** A move-only commit can break
    a test that depends on its directory's `conftest.py`. The following edit commit restores it, and
    the suite must pass once the pair lands.

### Agent files

Both follow the body shape of `claude_plugins/fls-dev/agents/qa-bugfixer.md`: a non-interactive
contract, staging by explicit path only (never `-a`, `-A`, `.` or a directory), `uv run git commit`,
never `--no-verify`, and a one-line return contract. Neither has a `skills:` key.

- `claude_plugins/sdd/agents/sdd-implementer.md`: `name: sdd-implementer`,
  `tools: Bash, Read, Edit, Write, Glob, Grep, Skill`, `model: sonnet`. It does one unit of work
  test-first: a plan batch or a fix. It commits with the subject its brief gives and returns
  `status=<ok|failed|blocked> commit=<subject|none> reason=<short>`. Its body holds the TDD and
  commit rules that `implement_plan.md` Step 2 currently spells out inline.
- `claude_plugins/sdd/agents/sdd-boy-scout.md`: `name: sdd-boy-scout`, same tools and model. Its
  brief gives it the batch number, the touched-files list, the remaining budget and whether
  `docs/app_structure.md` exists. It:
  - tidies test organisation only, in the touched files: moves or renames a test file to mirror
    the app, removes an existing cross-app test dependency, or splits a module per Decision 6. It
    changes no assertion.
  - may create a new file only under the `tests/` directory of an app one of its touched test
    files belongs to, such as a local fixture replacing a cross-app import or a split module.
  - makes a move commit then an edit commit, following the grammar below. It runs
    `uv run pytest <affected app test dirs>` after each pair.
  - stops at the budget and returns any violation past it as a deferred item, unfixed.
  - flags plainly broken code anywhere in the touched files, production code included, and never
    fixes it. Each flagged item carries `file:line`, why it is broken, a recommendation (fix now /
    record a follow-up / not a bug) and a drafted one-line "why this is correct" comment for use if
    the user answers "not a bug". It never suppresses its own flag. An existing comment at the spot
    explaining why the code is correct means it does not flag it again.
  - writes `.sdd-work/boy_scout_batch_<N>.md` with sections `Tidied`, `Deferred`, `Flagged` and a
    `status:` footer, and returns
    `status=<ok|failed|blocked> report=<path> reason=<short>`.

### Commit-subject grammar

Every commit a batch produces carries its number. `implement_plan.md` states this table, and
resume and the budget read it.

| Subject | Made by |
| --- | --- |
| `[batch N] <summary>` | implementer (unchanged) |
| `[batch N review-fix] <summary>` | fix agent, for a mechanical review finding |
| `[batch N boy-scout] move <old-path> -> <new-path>` | boy-scout; exactly one file, no content change |
| `[batch N boy-scout] edit <summary>` | boy-scout; the edit that goes with the move before it |
| `[batch N boy-scout] edit split <path> into <a>, <b>` | boy-scout; a split per Decision 6 |
| `[batch N boy-scout] edit drop <app> test dependency on <other-app>` | boy-scout; one cross-app dependency removed |
| `[batch N bug-fix] <summary>` | implementer, for a flagged item answered "fix it now" |
| `[batch N flag-note] <path>` | depth 0, the "not a bug" comment |
| `[batch N record] <summary>` | depth 0: `boy_scout_record.md` plus any follow-up files; always the batch's last commit |
| `[final review-fix] <summary>` | fix agent, for a finding of the final review |

`implement_plan` counts the budget fresh each time from `git log $(git merge-base origin/main HEAD)..HEAD`:

- files moved = subjects matching `^\[batch [0-9]+ boy-scout\] (move |edit split )`. The cap is 3.
- dependencies removed = subjects matching `^\[batch [0-9]+ boy-scout\] edit drop `. The cap is 1.

Matching `[batch N]` needs the closing bracket straight after the number, so no follow-on commit
reads as the implementation's commit.

### `implement_plan.md` Step 2: the per-batch sequence

- Step 2's spawn changes from `subagent_type: "general-purpose"` to
  `subagent_type: "sdd:sdd-implementer"`, keeping the per-spawn `model: "sonnet"` and the opus
  override note. The same change applies to Step 3's fix agent.
- The line-38 and line-43 wording ("As its final step, make the `[batch N] <summary>` commit";
  "verify the `[batch N]` commit exists") is reworded. A batch now owns several commits, and
  `[batch N]` is the implementation's commit, not the batch's only one.
- **Resume** (replaces line 31). For each batch, read `git log` subjects:
  - no `[batch N]` → implement it, then run the follow-ons.
  - `[batch N]` but no `[batch N record]` → run the follow-ons only. Reuse a
    `.sdd-work/test_org_review_batch_<N>.md` or `.sdd-work/boy_scout_batch_<N>.md` that ends
    `status: ok`. `implement_plan` briefs a boy-scout re-run with the batch's existing `boy-scout` commits so it
    finishes a half-done pair rather than repeating it.
  - `[batch N record]` → skip.
- **Follow-ons**, run in order after `[batch N]` lands and the suite passes. All are skipped when
  `## Testing Skills` is blank.
  1. **Review.** One `sdd:sdd-worker` per the fan-out recipe (`plan_from_spec.md` Step 6 shape)
     writes `.sdd-work/test_org_review_batch_<N>.md`. Its brief holds the skill IDs, the
     touched-files list and the instruction to read `docs/app_structure.md`'s Dependency table. It
     checks each touched test file's placement against mirroring. It also checks each touched test,
     conftest or factory file's imports of another app, and fixtures it pulls from a `conftest.py`
     under another app, against that app's Runtime deps. A project-wide pytest plugin
     (`pytest_plugins`, `pytest11`) is infrastructure, not an edge. Each finding has:

     ```
     - rule: mirroring | dependency-direction
       kind: mechanical | judgement
       file: <path>
       detail: <one line>
       recommendation: <one line, concrete enough to execute>
     ```

     `failed` retries twice with the prior error. Depth 0 resolves `blocked` from the code or via
     `AskUserQuestion`.
  2. **Review fixes.** Mechanical findings go to one `sdd:sdd-implementer`, which fixes them and
     commits `[batch N review-fix]`. Judgement findings go to the user at once via
     `AskUserQuestion`, up to four per call. An answer that needs code goes to the same fix path;
     the record notes an accepted new edge for `/app_map`.
  3. **Boy-scout.** Skip when no touched file is under a `tests/` directory and no production file
     was touched. Otherwise spawn one `sdd:sdd-boy-scout` with the remaining budget. `failed` →
     reset uncommitted work, retry up to twice. `blocked` → as for the review.
  4. **Scope check.** Via `sdd:sdd-mechanic`, run the scope-check script twice: after the review
     fixes, with `<from-ref>` at the `[batch N]` commit, and after the boy-scout, with `<from-ref>`
     at the commit before its first one. A violation stops the run and goes to the user. The
     commits are never reverted automatically. `bug-fix` and `flag-note` commits are not checked.
  5. **Flagged items.** Ask the user as soon as the boy-scout returns, up to four per
     `AskUserQuestion`. Each question carries the boy-scout's recommendation first and offers
     three answers:
     - "Not a bug": depth 0 writes the drafted comment at the spot, following the
       `code-comments` skill (why the code is correct, never who judged it), and commits
       `[batch N flag-note]`.
     - "Fix it now": one `sdd:sdd-implementer` fixes it test-first in `[batch N bug-fix]`.
     - "Record a follow-up": handled like a deferred item.
  6. **Deferred items and follow-ups.** If a row in state `next` in `spec_dd/1. next/roadmap.md`
     has a Scope that covers the item's app, append a bullet to that directory's `idea.md` under
     `## Follow-ups from other specs`, creating the heading if needed. Otherwise write a new
     `spec_dd/1. next/<slug>/idea.md` with `## What`, `## Why` and `## Resources`. `roadmap.md` is
     never edited; `/sdd:roadmap` picks new ideas up.
  7. **Record.** Append a `## Batch N` section to `<spec-dir>/boy_scout_record.md`: review
     findings and their fixes, what was tidied, what was deferred and where it went, and each
     flagged item with the user's answer. Commit it with any follow-up files as `[batch N record]`
     via `sdd:sdd-mechanic`. Delete the batch's two `.sdd-work/` files by name.

### `implement_plan.md` Step 3: the final review

- Before the existing success-criteria check, unless `## Testing Skills` is blank, one
  `sdd:sdd-worker` writes `.sdd-work/test_org_review_final.md` over
  `git diff $(git merge-base origin/main HEAD)..HEAD`, using the same finding format. It checks
  for what no single batch shows: the same new cross-app edge in several batches, an edge one
  batch's boy-scout removed and a later batch reintroduced, and the total budget spent. Findings
  are handled as in follow-ons 2 and 5, with `[final review-fix]` commits.
- Once Step 3 passes, a `## Summary` section is written at the end of `boy_scout_record.md` and
  committed with the final commit. The user gets a short summary of the record in the
  conversation: counts of fixes, tidies, deferrals and flagged items by answer, plus any edge that
  needs `/app_map` re-run.

### Scope-check script

`claude_plugins/sdd/scripts/batch_scope_check.sh <batch-number> <from-ref> [<to-ref>]`
(`<to-ref>` defaults to `HEAD`). It follows `upstream_change_scan.sh`'s conventions: a header
comment stating the exit codes, `set -euo pipefail`, a `usage()` helper, and refs validated with
`git rev-parse --verify --quiet`. `implement_plan` resolves its path through the `PLUGINS_ROOT` rule as in
`pre_step_rebase.md` Step 3.

- Allowed set: every path added or modified by commits between the merge base with `origin/main`
  and `<from-ref>` whose subject is `[batch N] …` or `[batch N review-fix] …`.
- Walk `git diff --name-status -M <from-ref> <to-ref>`:
  - `R old new`: `old` must be allowed. Then add `new` to the allowed set.
  - `M path`: must be allowed.
  - `A path`: must sit under the `tests/` directory of an app one allowed test file belongs to.
  - `D path` that git did not pair as a rename: a violation.
- Exit 0 in scope. Exit 1 on a violation, printing `OUT_OF_SCOPE:` and one path per line. Exit 64
  on bad arguments.
- `.claude/settings.json` gains `Bash(claude_plugins/sdd/scripts/batch_scope_check.sh:*)` beside
  the two existing `sdd` script entries.

### `pre_step_rebase.md`

Line 103: the scan's commit list shows how far implementation has got. A batch is finished at its
`[batch N record]` commit, or at `[batch N]` when the review is off. `upstream_change_scan.sh` needs
no change.

### Spec 3 hand-off

Whichever of this spec and `test-organisation-and-hygene-3-enforcement-checks` lands second makes
the review run the other's checks. If spec 3 is on `main` when this spec's plan is written, the
plan adds a `Test organisation check:` key to `## Testing Skills`. The key names a command that
`sdd:sdd-mechanic` runs over the touched files before the review, and its output goes into the
reviewer's brief. Otherwise spec 3 adds that key, and this spec leaves nothing for it.

## Testing

- `tests/test_batch_scope_check.py`, built like `tests/test_upstream_change_scan.py` (a hand-built
  git repo in `tmp_path`, no database):
  - a modify inside the allowed set passes
  - a pure move of an allowed file, then an edit at its new path, passes
  - a modify of a file outside the set fails and names it
  - a new file under the same app's `tests/` passes
  - a new file under another app fails
  - a delete that is not a rename fails
  - a path touched only by a `[batch N review-fix]` commit is allowed
  - commits of another batch number do not widen the set
  - bad arguments exit 64
- The prompt-driven behaviour (resume states, budget counting, question flow) has no automated
  harness. The QA plan covers it by running `/sdd:implement_plan` on a throwaway spec with a
  planted misplaced test, a planted cross-app import and a planted bug, then interrupting it and
  resuming.

## Open questions

Defaults taken; overrule any of them:

- **Blank config disables review and boy-scout** (Decision 4), rather than running them against the
  dependency table alone.
- **A split counts as one file** against the 3-file budget (Decision 6).
- **Follow-ups go into a `next` cleanup spec's `idea.md`** under `## Follow-ups from other specs`,
  never into a spec already in progress in another worktree.
- **`[batch N record]` is a new commit every batch**, even when nothing else was committed. This
  keeps resume on commit subjects alone.
