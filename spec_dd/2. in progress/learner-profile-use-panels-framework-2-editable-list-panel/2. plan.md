### How the panel and its actions fit together

`panels.py` already imports `actions.py`, so the actions cannot import the panel class at run
time. Each action takes the bound panel in its constructor and types it under `TYPE_CHECKING`:

```python
# actions.py
if TYPE_CHECKING:
    from freedom_ls.panel_framework.panels import EditableListPanel


class _EditableListAction(PanelAction):
    """What the three editable-list actions share: the bound panel, its
    events, and a capability asked of the parent."""

    #: False for a host subclass that states its own `capability`, or None
    #: to allow whoever can reach the panel.
    derive_capability: bool = True
    capability_verb: str = ""

    def __init__(self, panel: EditableListPanel) -> None:
        self.panel = panel
        self.success_events = panel.refresh_events

    def get_capability(self, ctx: PanelContext) -> str | None:
        if not self.derive_capability:
            return self.capability
        return _model_capability(self.panel.entry_model, self.capability_verb)

    def permission_object(self, ctx: PanelContext) -> Model | None:
        return ctx.instance
```

It is a plain mixin, not an abstract base class. A host that subclasses an action hands it to the
panel by overriding `get_actions()`, the hook every panel already has.

The panel reads its entries once and everything else reads that list:

```python
# panels.py
@dataclass(frozen=True)
class EditableListSummary:
    title: str
    detail: str = ""


class EditableListPanel(Panel):
    template_name = "panel_framework/panels/editable_list.html"
    form_class: type[forms.ModelForm]
    parent_field: str
    noun: str = ""
    empty_message: str
    max_entries: int | None = None
    add_another: bool = False
    layout: Literal["list", "table"] = "list"

    def __init__(self, ctx: PanelContext) -> None:
        if ctx.instance is None:
            raise ImproperlyConfigured(
                f"{type(self).__name__} lists a parent's entries and needs one."
            )
        super().__init__(ctx)

    def get_form_class(self) -> type[forms.ModelForm]:
        return self.form_class

    def get_entries(self) -> QuerySet[Model]:
        raise NotImplementedError

    def get_summary(self, entry: Model) -> EditableListSummary:
        raise NotImplementedError

    @property
    def entry_model(self) -> type[Model]:
        return self.get_form_class()._meta.model

    def get_noun(self) -> str:
        return self.noun or str(self.entry_model._meta.verbose_name)

    @cached_property
    def loaded_entries(self) -> list[Model]:
        # Evaluated once: the render, the cap and the Add trigger all read this list.
        return list(self.get_entries())

    def at_cap(self, count: int | None = None) -> bool:
        """Whether `count` entries fill the list; the loaded entries when not given."""
        if self.max_entries is None:
            return False
        return (len(self.loaded_entries) if count is None else count) >= self.max_entries

    def get_cap_line(self) -> str:
        return f"You can have up to {self.max_entries}. Remove one to add another."

    def get_actions(self) -> list[PanelAction]:
        return [
            EditableListAddAction(self),
            EditableListEditAction(self),
            EditableListRemoveAction(self),
        ]
```

`get_actions()` is called more than once per request (`available_actions`, the URL resolver), so
the actions hold no state of their own beyond the panel.

### The template context

`EditableListPanel.get_context_data()` adds plain values only, so the same template renders from
static data on the component reference page with no panel and no query:

| Key | Value |
| --- | --- |
| `layout` | `"list"` or `"table"` |
| `noun` | `get_noun()` |
| `empty_message` | the consumer's sentence |
| `entries` | one dict per loaded entry: `pk`, `title`, `detail`, `accessible_name` (`title`, or `"<title>, <detail>"` when detail is set), `edit_url`, `remove_url` (each empty when its action is not available), `focus_after_remove` (the next entry's pk, else the previous one's, else empty) |
| `add_trigger` | the add action's `get_trigger_context(ctx)` (`label`, `variant`, `action_url`), or `None` when the action is not in `available_actions` |
| `cap_line` | the cap sentence when the add is permitted and the list is at the cap, else `""` |
| `entry_count` | `count_noun(entry_model, len(loaded_entries))`, for the table layout's footer |

The panel keeps the model instances in `loaded_entries`; the context key `entries` holds the dicts
the template draws. `get_context_data`'s docstring says so.

One helper builds an entry trigger's URL, so the parameter name lives only in the action's
`row_param`:

```python
def _entry_action_url(self, action: PanelAction, entry: Model) -> str:
    return f"{action.get_action_url(self.ctx)}?{urlencode({action.row_param: entry.pk})}"
```

`title` and `detail` are plain strings and render autoescaped, in text and in attributes. No
template in this plan uses `|safe`.

   class EditableListAddAction(_EditableListAction, FormPanelAction):
       action_name = "add_entry"
       capability_verb = "add"
       submit_buttons = [{"label": "Add", "variant": "primary", "loading_text": "Adding…"}]

       def __init__(self, panel: EditableListPanel) -> None:
           super().__init__(panel)
           self.form_class = panel.get_form_class()
           self.label = self.form_title = f"Add {panel.get_noun()}"

       def get_form_kwargs(self, ctx: PanelContext) -> dict[str, object]:
           # A new entry that already belongs to the parent, so the form
           # validates what will be saved, never the parent itself.
           new_entry = self.panel.entry_model(**{self.panel.parent_field: ctx.instance})
           return {**super().get_form_kwargs(ctx), "instance": new_entry}

       def form_valid(self, ctx: PanelContext, form: forms.BaseForm) -> HttpResponse:

               entry = cast(forms.ModelForm, form).save()

How the pieces already behave, which the script leans on:

- A 204 fires the domain event and then `closeModal`. The dialog's close handler refocuses the
  trigger. The panel then refetches and swaps its `<section>`, the trigger goes with it, and the
  existing `htmx:afterSwap` fallback runs because `focusWasInTarget` is true and focus fell to
  `<body>`.
- The refetch's `requestConfig.triggeringEvent` is the domain event, and its `detail.ids[0]` is
  the entry's pk.
- A dialog that closes by Cancel or Esc never fires `closeModal`.
- An "Add and add another" save swaps the dialog body with a `[data-status-message]` notice in it.

The mechanism, all at module level in `alpine-components.js` (no new `x-data`):

```js
// The entry action whose dialog is open, noted when its trigger is clicked:
// the removed entry is gone from the refreshed list, so its title and the
// entry to focus next can only be read beforehand.
let pendingEntryAction = null;

htmx:beforeRequest   (elt has data-editable-list-action, target is #app-modal-body)
    pendingEntryAction = {
        trigger: elt,
        action: elt.dataset.editableListAction,        // add_entry | edit_entry | remove_entry
        panelId: elt.closest("[data-panel]").id,
        title: elt.dataset.entryTitle || "",
        focusAfterRemove: elt.dataset.focusAfterRemove || "",
        confirmed: false,
        addedAnother: false,
    }

htmx:afterRequest    (elt is pendingEntryAction.trigger, and the request failed)
    pendingEntryAction = null                          // no dialog opened

htmx:afterSwap       (target is #app-modal-body and it now holds [data-status-message])
    if (pendingEntryAction) pendingEntryAction.addedAnother = true

body "closeModal"    if (pendingEntryAction) pendingEntryAction.confirmed = true
                     // closeModal only ever follows a saved change.

#app-modal "close"   if pendingEntryAction is not confirmed:
                         if it addedAnother:
                             focus the panel's cap line, else its visible Add trigger
                         pendingEntryAction = null

htmx:afterSwap       (the swapped element's id is pendingEntryAction.panelId)
    if #app-modal is open or the action is not confirmed: return
    pk = String(requestConfig.triggeringEvent?.detail?.ids?.[0] ?? "")
    target, message =
        add_entry:    cap line if present, else the visible Edit trigger for pk;   "Added " + that trigger's title + "."
        edit_entry:   the visible Edit trigger for pk;                             "Saved " + its title + "."
        remove_entry: the visible Edit trigger for focusAfterRemove,
                      else the empty state's Add trigger;                          "Removed " + pending title + "."
    if (target) target.setAttribute("data-focus-target", "")
    document.getElementById("scope-announcer").textContent = message
    pendingEntryAction = null
```

  `dataset.entryPk === pk` and which has layout (`offsetParent !== null`). Values are compared,
  never built into a selector string.
- Register this `htmx:afterSwap` listener before the existing focus-fallback listener in the file,
  so the mark is on the element when the fallback runs.
- The existing fallback gains one branch: after the `sameField` check, a

- For an add at the cap the new entry's title still comes from its Edit trigger; only the focus

- The cap-line branch of the close handler cannot be reached through one dialog, because "Add and

- A dialog close that follows the "no longer available" 404 leaves `confirmed` false, so the
