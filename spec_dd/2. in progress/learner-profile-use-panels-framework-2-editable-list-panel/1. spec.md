# Spec: `EditableListPanel`

Idea: `idea.md`. Answers: `answers.md`. Research: `research_*.md` beside this file.

## Purpose

The panel framework has no shape for a short list of entries that belong to one object and that a
person adds to, edits and removes from. Today the only answer is a `DataTablePanel` with
hand-built row-scoped actions, which is heavy for five entries and needs a hand-written edit
action per list. `learner-public-profile-2-profile-and-page` (work experience) and
`learner-public-profile-4-certificates` need this shape. `EditableListPanel` builds it once, in
`freedom_ls/panel_framework`, with no FLS name in it.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| entry | coined | One row of an `EditableListPanel`: an instance of the form's model that the panel's `get_entries()` returns for the parent. Not the glossary's "list entry" (`JobTitle`, `Department`, `Location`), and not `AuditLogEntry`. |
| parent | narrowed | The panel's bound `ctx.instance` (`panel_framework/context.py`), here always the object the entries belong to. |

## Scope

In:

- `EditableListPanel` in `panel_framework/panels.py`, with its add, edit and remove actions in
  `panel_framework/actions.py`, its templates, a system check, framework tests, a static example on
  the component reference page, and the `fls-dev:panel-framework` skill update.
- A hidden-fields hook on `FormPanelAction`, so a row-scoped form dialog posts its row back.

Out:

- Manual reordering. The consumer's query sets the order.
- Inline editing of an entry inside the list.
- File fields on entries: `learner-profile-use-panels-framework-1-file-upload-actions` supplies
  them, and a consumer combines the two.
- Undo after a remove.
- Any consumer panel or page outside the framework's own tests.

## Decisions

- The entry travels as a request parameter (`row_param`), not a path segment: `?<row_param>=<pk>`
  on the trigger's GET, a hidden field on the POST. The URL router knows only `__actions/<name>`
  (`views.py`), and `PanelAction.get_row_object` already gives the 404 the idea asks for.
- `get_entries()` is the single scope. The list renders from it and each per-entry action's
  `get_row_queryset` returns it, so an entry outside the parent's entries is a 404 on GET and POST.
- The add, edit and remove actions are new classes, not changes to `CreateInstanceAction`,
  `EditAction` or `DeleteAction`. Those bind the page's instance (the parent) as the form instance
  or the deleted object, and `CreateInstanceAction` navigates instead of firing events. New classes
  also keep the overlap with the upload spec's edits to `FormPanelAction.get_form` and
  `modal/form.html` small. Whichever of the two lands second rebases (roadmap, "Account area on
  panels").
- The consumer chooses the layout: `layout = "list"` (`<c-panel-list>` rows) or `"table"` (static
  table rows inside `.panel-data-table`, cards when narrow). Default `"list"`.
- The component reference page stays static and zero-query: it shows the panel's markup with
  example data. The live add/edit/remove round trip runs on a stub tab in the test URLconf.

## Requirements

### Panel: `panel_framework/panels.py`

`EditableListPanel(Panel)`, added to `__all__`. A parent instance is required: construction
without `ctx.instance` raises `ImproperlyConfigured`, as `InstanceDetailsPanel` does.

What a consumer sets:

| Attribute / hook | Type | Default | Meaning |
| --- | --- | --- | --- |
| `form_class` | `type[ModelForm]` | required | The add and edit form. Its `Meta.model` is the entry model. It leaves out the parent field. |
| `parent_field` | `str` | required | The entry model's foreign key to the parent. The add action sets it. |
| `get_entries(self)` | `-> QuerySet` | required | The parent's entries, in display order. The consumer's ordering ends in a unique field (for example `-start_date, -pk`), so the order is stable. |
| `get_summary(self, entry)` | `-> EditableListSummary` | required | The entry's title and optional detail line. Reads only what `get_entries()` already loaded: no query per entry. |
| `noun` | `str` | entry model `verbose_name` | Words the labels: "Add work experience", the dialog titles. |
| `empty_message` | `str` | required | The empty state's sentence. |
| `max_entries` | `int \| None` | `None` | Optional cap. |
| `add_another` | `bool` | `False` | Offers "Add and add another" beside "Add". |
| `layout` | `Literal["list", "table"]` | `"list"` | Row markup. |
| `refresh_events` | `list[str]` | `[]` | The list's event. The panel passes it to its three actions as `success_events`, as `InstanceDetailsPanel.get_actions` does, so the consumer names it once. |

`EditableListSummary` is a frozen dataclass `(title: str, detail: str = "")`, exported from
`panels.__all__`. Both values render autoescaped.

`get_actions()` returns the add, edit and remove actions. `get_entries()` runs once per render.

### Actions: `panel_framework/actions.py`

Three classes, added to `__all__`, built by the panel and named by its `noun`:

- `EditableListAddAction(FormPanelAction)`: a footer action (`renders_in_footer = True`). The form
  takes no instance. On a valid POST it saves the entry with `parent_field` set to the parent, inside
  `transaction.atomic()` with the parent row locked (`select_for_update()`), and re-checks the cap
  under the lock. Success is `changed_response` with the panel's events (204, `HX-Trigger`,
  `closeModal`), never a navigation. Submit buttons: "Add" (loading "Adding…"), plus "Add and add
  another" when `add_another` is set. That button re-renders an empty form, and it is not offered
  when the save fills the last free place.
- `EditableListEditAction(FormPanelAction)`: a row action (`renders_in_footer = False`, `row_param`
  set, `get_row_queryset` returns `get_entries()`). The form's instance is `get_row_object(ctx)`.
  One "Save" button. Title "Edit <noun>".
- `EditableListRemoveAction(ConfirmAction)`: a row action scoped the same way. Label "Remove",
  `confirm_variant = "error"`, loading "Removing…". The dialog names the entry by its summary title
  and says the removal cannot be undone. Deletion runs in `transaction.atomic()`; a `ProtectedError`
  answers with `refusal_response`. Success is `changed_response` with the panel's events.

Each action derives its capability from the entry model (`add_`, `change_`, `delete_<model>`) and
asks it of the parent as `permission_object`, so a host's `has_capability` decides. A host may set
`capability = None` on a subclass.

The cap: when `max_entries` is set and `get_entries().count() >= max_entries`, the add action's
`is_offered` is false, and both its GET and its POST answer `refusal_response` (422, message dialog,
Close footer) with the cap line's wording. Edit and remove still work at the cap.

`FormPanelAction` gains `get_hidden_fields(self, ctx) -> dict[str, str]` (default `{}`), rendered as
hidden inputs inside the form in `panel_framework/modal/form.html`. The edit action returns its
`row_param` and the entry's pk, mirroring `ConfirmAction.get_hidden_fields`.

### Templates

`panel_framework/panels/editable_list.html` extending `panels/_editable_list_base.html`, the
two-layer pattern every framework panel uses. It extends `_panel_base.html`, so a panel with
`refresh_events` refetches its own region.

- Each entry shows its summary: the title in `font-medium`, the detail under it in
  `text-sm text-muted` when set. `layout = "list"` uses `<c-panel-list>` and `<c-panel-list-row>`
  with the buttons in the row's trailing slot. `layout = "table"` uses the framework's table
  components inside `.panel-data-table`, buttons in a `<c-data-table-actions>` cell, cards when the
  container is narrow, and the table footer's entry count.
- Per entry: an Edit trigger and a Remove trigger, `<c-modal-trigger size="small">`, URLs from
  `row_action_urls` plus `?<row_param>=<pk>`. The visible labels are "Edit" and "Remove". Each
  `aria_label` starts with the label and names the entry: "Edit <title>", or "Edit <title>, <detail>"
  when the detail is set. Remove is the same.
- Empty: `<c-panel-empty-state message="<empty_message>">` with the Add trigger in its slot, and no
  second Add in the footer.
- At the cap the footer shows a muted line in the Add trigger's place: "You can have up to
  <max_entries>. Remove one to add another." It carries `tabindex="-1"` so focus can land on it.
- Add and edit use `modal/form.html`. Remove uses `modal/confirm.html`.

### Focus and announcements

After the panel refreshes from its own event:

- Add saved: focus moves to the new entry's Edit trigger, or to the cap line when the add reached the
  cap.
- Edit saved: focus moves to that entry's Edit trigger.
- Remove confirmed: focus moves to the next entry's Edit trigger, else the previous one, else the
  empty state's Add trigger.
- Cancel or close without a change: focus returns to the trigger, as the modal host already does.

Each change is announced once through the modal host's live region (`#app-modal-status`): "Added
<title>", "Saved <title>", "Removed <title>". The mechanism lives in the framework's
`alpine-components.js` and reads the entry pk the success event carries
(`PanelAction.get_success_events`). Any new `x-data` name is registered there.

### Errors

- An invalid add or edit re-renders the form in the dialog with the person's values and errors, 422.
- An edit or remove for an entry that no longer exists (removed in another tab) answers 404, and the
  person sees the framework's message dialog, not an empty modal.

### System check: `panel_framework/checks.py`

A new check id, `freedom_ls_panel_framework.E009`, held in one constant, run over every
`EditableListPanel` subclass: `form_class` is set and is a `ModelForm`; `parent_field` names a
foreign key on the form's model; `max_entries` is `None` or a positive integer; `layout` is `"list"`
or `"table"`.

### Component reference page

`panel_framework/templates/panel_framework/reference/_examples.html` gains an "Editable list"
section with static examples `editable-list-default`, `editable-list-empty`, `editable-list-cap` and
`editable-list-table`, and `"editable-list"` joins `COMPONENT_NAMES` in the reference tests. The page
stays zero-query.

## Testing

Stub: a new `StubEntry` model in `tests/stub_models.py` (parent FK to `StubModel`, `title`, `detail`),
a stub `EditableListPanel` on `StubTabSet` reachable under `/test-panel/framework/stubs/<pk>/`, its
actions permitted as the existing stubs are.

- `tests/test_panels.py`: renders entries in `get_entries()` order with title and detail; the empty
  state with its Add trigger and no footer Add; the cap line in place of Add; no Add trigger and no
  cap line when the add is not permitted; `get_entries()` runs once and the summary adds no query
  per entry (`django_assert_num_queries`); both layouts; construction without a parent raises.
- `tests/test_actions.py`: add sets `parent_field` and fires the events; edit loads and saves the
  named entry; remove deletes it and fires the events; an entry of another parent and a missing or
  malformed pk give 404 on GET and POST for edit and remove; add GET and POST at the cap answer 422
  and create nothing; "Add and add another" is offered only when `add_another` is set and not on the
  last free place; invalid forms answer 422 with errors; `ProtectedError` on remove answers the
  refusal; the edit form posts its row back through `get_hidden_fields`.
- `tests/test_checks.py`: each E009 condition, and `test_call_command_check_passes_on_the_real_config`
  still passes.
- `tests/test_reference.py`: the new example ids exist, ids stay unique, the page stays zero-query.
- Invariants: `tests/invariants/test_templates.py` passes over the new templates (small triggers, no
  `|safe`, no hand-written table, dialog shape); `test_public_names.py` covers the new `__all__`
  entries; `test_alpine_registration.py` covers any new `x-data` name. A new invariant asserts that
  every per-entry trigger in `editable_list` templates carries an `aria_label`.
- Playwright (`tests/playwright/`): add an entry, edit it, remove it, on the stub tab, checking the
  list and the focus target after each; reach the cap and see the cap line; at 375px the dialogs and
  rows stay inside the viewport.

## Open questions

- Q: Which layout is the default when a consumer sets none? → A: `"list"` (assumed default: it is the
  lighter shape the idea asks for, and a consumer can pick `"table"`. Overrule by editing Decisions.)
- Q: Do the actions derive `add_`/`change_`/`delete_<entry model>` capabilities by default, or default to
  `capability = None`? → A: Derive them, asked of the parent (assumed default: deny by default matches
  every other framework action, and a self-service host opts out per subclass. Overrule by editing
  Requirements, Actions.)
- Q: What does the cap line say? → A: "You can have up to <max_entries>. Remove one to add another."
  (assumed default: it states the number and the way out without needing a plural noun. Overrule by
  editing Requirements, Templates.)

## Success criteria

- A stub `EditableListPanel` adds, edits and removes entries through dialogs, and the list refreshes
  by its event without a page load.
- An edit or remove naming another parent's entry answers 404 on GET and POST.
- At `max_entries` the Add trigger is replaced by the cap line, and a direct add GET or POST answers
  422 and creates nothing.
- Every per-entry trigger's accessible name names its entry.
- After add, edit and remove, focus lands on the target listed under Focus and announcements, checked
  by the Playwright flow.
- `uv run manage.py check` passes, and each E009 condition fails it in `tests/test_checks.py`.
- `tests/invariants/` and `tests/test_reference.py` pass.
- `SKILL.md` names `EditableListPanel` and no longer requires a data table for it.
