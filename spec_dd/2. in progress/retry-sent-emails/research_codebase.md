# Research: codebase (retry-sent-emails)

Question: what in today's code does this work touch, reuse or conflict with? All paths are relative to the repo root; line numbers are today's (2026-11-11, branch `retry-sent-emails`). Pinned versions: Django 6.0.4 (`uv.lock:628-629`), `django-tasks` 0.12.0 (`uv.lock:849`), `django-tasks-db` 0.12.0 (`uv.lock:863`, `pyproject.toml:35` pins `==0.12.0`).

## 1. Headline findings (things that change the design)

1. **The queue is not the production default.** `config/settings_prod.py:101-110` leaves `EMAIL_BACKEND` as Django's SMTP backend unless a deployment sets the env var. Only dev (`config/settings_dev.py:94-95`) selects `QueuedEmailBackend`. idea.md ("`QueuedEmailBackend` is already `EMAIL_BACKEND`, so every sender goes through it") and oldspec ("Auth mail is all FLS sends... leaves the request on the task queue") are true for dev and opt-in deployments only. The default production path (inline SMTP, no row, no retry) is untouched by any transport-layer retry. The spec must say so, or change the prod default, or accept the scope. The oldspec W001 check (supports_defer) only fires when the queue backend is selected, so it does not cover this.
2. **Two task frameworks coexist.** The mail code imports `from django.tasks import task, default_task_backend` (Django 6 native; `freedom_ls/mail/tasks.py:13`, `backends.py:25`). The DB backend and worker are the `django_tasks` backport: `django_tasks_db/backend.py:12-16` subclasses `django_tasks.backends.base.BaseTaskBackend`, and `db_worker.py:17-20` sends `django_tasks.signals.task_finished`. `django_tasks_db/compat.py:1-10` accepts both `Task` classes. Housekeeping imports `django_tasks` (`freedom_ls/deployment/housekeeping.py:15`). Native `django.tasks` backends/exceptions are `django.tasks.backends.immediate.ImmediateBackend` (`config/settings_base.py:615-619`) and the exception is `InvalidTask` (`.venv/.../django/tasks/exceptions.py:8`), not oldspec's `InvalidTaskError`.
3. **Failure-to-Sentry path (idea.md) holds, but via the backport signal.** `django_tasks.signals.log_task_finished` (`.venv/.../django_tasks/signals.py:55-70`) uses `logger.exception` for FAILED; the worker sends it from inside its `except BaseException` (`db_worker.py:176-188`). Under the native-`ImmediateBackend` (dev/tests) the equivalent receiver is `django/tasks/signals.py:50-65` (`logger.log(ERROR, exc_info=...)`). Sentry init: `freedom_ls/deployment/apps.py:9-13` -> `freedom_ls/deployment/sentry.py:27-38` (no explicit `integrations=`, so SDK defaults incl. logging apply). No-DSN means disabled.
4. **An existing caller depends on the inline failure signal.** `freedom_ls/course_applications/emails.py:14,43-60` catches `(OSError, QueuedEmailNotSentError)` around `get_adapter(request).send_mail(...)` and returns False so the page can say "the email did not go out". This comes from `QueuedEmailBackend._queue_or_send` raising when `result.status == FAILED` (`backends.py:77-81`; `_failure_detail` `:93-103`). Oldspec's send task catches transient errors and does not raise, so under the ImmediateBackend a transient failure would no longer fail the result and this caller would report True for a mail that is only queued for retry. Tests that raise it: `course_applications/tests/test_emails.py:292,429`. The spec must decide what an inline/immediate backend does with a classified transient failure (oldspec guards deferral with `supports_defer` but is silent here).
5. **Name collision.** `backends.py:33` already defines `QueuedEmailNotSentError`. Oldspec's `EmailNotSentError` "declared in `mail.py`" does not exist (`mail.py` does not exist; `UnserialisableMessageError` is in `freedom_ls/mail/serialisation.py:20`).
6. **A second `on_commit`-enqueue pattern already exists**, with `robust=True`: `freedom_ls/comms/notify.py:59-97` (`transaction.on_commit(write, robust=True)`; task enqueue inside the callback `:68-73`). Also `reports/services.py:92-93`, `accounts/account_setup.py:101-105`, `registration_rules/signals.py:62-76`. Reusable precedent for answer 2 (enqueue on commit). `on_commit(robust=True)` makes oldspec's hand-written "capture to Sentry and swallow" mostly unnecessary (Django logs the exception from a robust callback; verify it still reaches Sentry via the `django.db.backends.base` logger at ERROR).

## 3. Task framework, worker and watchdog

- `DatabaseBackend` (`django_tasks_db/backend.py:32-36`): `supports_defer = True`, `supports_priority = True`. Enqueue creates `DBTaskResult` with `args_kwargs=normalize_json({"args":..., "kwargs":...})` (`:70-78`), `run_after=task.run_after`. No `on_commit` handling in the backend itself, so the caller must wrap it.
- Native `BaseTaskBackend` (`.venv/.../django/tasks/backends/base.py:24,72-73`): `supports_defer = False` default; `validate_task` raises `InvalidTask("Backend does not support run_after.")`; `Task.__post_init__` calls `validate_task` (`django/tasks/base.py:54-55`) and `Task.using(run_after=...)` exists (`:61-77`). So oldspec's claim that `.using(run_after=...)` raises under the immediate backend still holds (exception name differs). Also `supports_priority` for the native ImmediateBackend: the task is priority 10 and works today, so it is accepted; no change.
- `TaskContext.attempts` exists (`django/tasks/base.py:222,247`), nothing increments it into a second run; `django_tasks_db/utils.py:72` `retry()` is DB-write backoff. idea.md holds.
- `HeartbeatWorker` copies `Worker.run()` (`freedom_ls/deployment/worker.py:3-4,191-206`), pinned to 0.12.0 with a test; **bumping the `django-tasks-db` pin is out of the question for this spec** (also not needed).
- Watchdog: `check_worker_heartbeat` -> `os._exit(1)` after `sentry_sdk.flush` (`worker.py:64-88`); oldspec's "kill is `os._exit`, skips bookkeeping" holds. Task ceiling = `WORKER_MAX_TASK_SECONDS` (1800, `freedom_ls/deployment/config.py:48`) + `WORKER_HEARTBEAT_MAX_AGE_SECONDS` (300, `:41`) + `WATCHDOG_POLL_SECONDS`; documented `config.py:42-47`. The per-task cap is applied at `worker.py:277-281`.
- `prune_db_task_results` (`django_tasks_db/management/commands/prune_db_task_results.py`): deletes finished results older than `--min-age-days` default **14** (`:59-64`), `--failed-min-age-days` default None -> same 14. Called from housekeeping as `call_command("prune_db_task_results", queue_name="*")` (`housekeeping.py:362`). It raises `CommandError` under the immediate backend (see `freedom_ls/conftest.py:379-385`). Oldspec "14 days" holds. Note: with one task row per attempt and a ladder of hours, per-attempt task rows are small once the payload is a UUID; the risk is only that rows carrying the full payload are copied per attempt, which is exactly what the row id design avoids.
- Scheduled/periodic mechanism: **none inside the tasks framework.** The only periodic driver is the external cron/CronJob running `fls_run_housekeeping` (`housekeeping.py:1-6`). A self-re-enqueueing deferred task (`run_after`) is the only in-framework "scheduled" mechanism, and it is lost if the row is lost. `deployment/tests/helpers.py` and `HOUSEKEEPING_HEARTBEAT_PATH` (`config.py:53`) are the health contract for the cron.

## 4. `fls_run_housekeeping` and how a sweep is registered

- Command: `freedom_ls/deployment/management/commands/fls_run_housekeeping.py:12-37`. Runs `run_housekeeping_sweeps()` once; prints `outcome.notes`; touches the heartbeat only if no `sweep_failures`; raises `CommandError` if `sweep_failures or findings`. `help` text (`:13-18`) lists the sweeps and will need updating.
- Registration is **hand-written inline** in `run_housekeeping_sweeps()` (`housekeeping.py:350-485`): each sweep gets its own `try/except` and appends to one of three lists. There is no registry or decorator; the bulk-record sweeps use a local tuple + loop (`:445-481`). Existing steps in order: `prune_db_task_results` (`:361-365`), `clearsessions` (`:367-371`), late unpicked tasks (`:373-387`), orphaned RUNNING tasks (`:393-411`), orphaned RUNNING reports (`:416-433`), stale learner-import previews (`:435-442`), then three bulk-record sweeps over `BULK_RECORD_MODELS` (`:444-481`).
- `SWEEP_FAILURES = (CommandError, DatabaseError)` (`:347`), but the in-file sweeps actually catch `DatabaseError` only except for `call_command` ones. `HousekeepingOutcome` is a NamedTuple at `:48-76` (oldspec said `:41`, now `:48`): `sweep_failures` withhold heartbeat; `findings` force non-zero exit but keep heartbeat; `notes` neither.
- Constant-message Sentry pattern: `mark_orphaned_running_tasks_failed` is at `:107` (oldspec said `:102`); the `new_scope()` + `set_extra` + constant `capture_message` pattern is `:142-149`, repeated at `:206-214`, `:278-283`.
- Config for housekeeping windows: `HOUSEKEEPING_UNPICKED_TASK_MAX_AGE_SECONDS`, `HOUSEKEEPING_ORPHANED_TASK_MAX_AGE_SECONDS`, `HOUSEKEEPING_ORPHANED_REPORT_MAX_AGE_SECONDS` in `deployment/config.py:19-21,54,61,67` (ceiling rule comment `:55-60`; oldspec said `config.py:56`: it is `deployment/config.py:55-60`). Retention for bulk records lives in `learner_management_config.BULK_RECORD_RETENTION_DAYS` (`housekeeping.py:464`), the precedent that **sweep-window settings sit with the app that owns the data**, not in `deployment`. For mail rows either approach has precedent; the oldspec's `HOUSEKEEPING_*_EMAIL_*` names in mail config would sit with the owner and mirror the learner_management precedent.
- Late-task check (`find_late_unpicked_tasks`, `:79-92`) already catches a deferred retry task that never gets picked up once `run_after` is past by 3600s, and `mark_orphaned_running_tasks_failed` closes a RUNNING task row for a killed worker as FAILED (not requeued). So a killed-mid-send worker yields: a FAILED task row (via orphan sweep) + a Sentry message; the email row would remain in `sending` and needs its own sweep. Interaction: the orphan sweep does NOT touch the mail row.
- Current sweep granularity: housekeeping is expected hourly-ish; docs/product/deployment.md line 13 contains the phrase "fails silently" (long line; confirm wording at edit time). An email sweep running only as often as cron is a coarse driver; the roadmap's dependence on a deferred task for precision stands.
- Test harness: `freedom_ls/deployment/tests/test_housekeeping.py` exercises the sweeps; the shared `database_task_backend` fixture is now **`freedom_ls/conftest.py:379-385`** (oldspec said `test_housekeeping.py:50`; now shared, also used by `registration_rules/tests/test_signals.py`). `django_capture_on_commit_callbacks` is used by the same tests, so the on_commit testing pattern exists.
