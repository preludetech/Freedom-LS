# Spec: retry sent emails

## Purpose

Outgoing mail goes onto the task queue (`freedom_ls/mail/backends.py`) and nothing retries it, so a
mail host unreachable for thirty seconds loses the message for good. Under
`ACCOUNT_EMAIL_VERIFICATION = "mandatory"` (`config/settings_base.py:437`), a lost verification mail
blocks registration. A send that raises reaches Sentry but leaves no per-message record to act on or
resend. A backend that returns 0 is recorded as a success. The full body, reset link included, sits
in `DBTaskResult.args_kwargs` for 14 days. `idea.md` records what was checked and why the retry
belongs in the transport layer.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `OutboundEmail` | coined | The row that owns one outgoing message: its payload until it is sent, then its status, attempts and next attempt time. Prose says "`OutboundEmail` rows", never "the outbox", which is `django.core.mail.outbox`. |

## Scope

**In.** An `OutboundEmail` row per outgoing message, written by `QueuedEmailBackend`. A send task that
classifies a failure and schedules its own next attempt. Housekeeping sweeps that re-drive due and
stuck rows and prune old ones. A superuser-only, read-only admin with a resend action. Payload
scrubbing. The discarded send count. `QueuedEmailBackend` as the production default.

**Out.**
- Per-category retry policies, priorities and a bulk queue.
- Bounce and complaint feedback after the provider accepts the message.
- Suppression lists.
- Fixing `WebhookDelivery.next_retry_at`.
- Any change to a call site: `freedom_ls/accounts/allauth_account_adapter.py` still calls
  `msg.send()`.
- Retrying the `UnserialisableMessageError` fallback, which sends inline and writes no row.

## Decisions

- **The task carries only the row id.** A counter in the task payload would copy the reset link into
  a new `DBTaskResult` on every attempt.
- **`OutboundEmail` is not a `SiteAwareModel` and has no `site` column.** `SiteAwareModelBase.site` is
  non-null, mail can be sent with no request, and the admin is superuser-only. This keeps `mail` off a
  `site_aware_models` edge.
- **`OutboundEmail` is not a `TimestampedModel`.** Its timestamps carry meaning
  (`freedom_ls/contrib/conformance/tests/test_timestamped_models.py:23-26`).
- **Every attempt is its own task.** A sleep loop would hold the single worker past
  `WORKER_MAX_TASK_SECONDS` and be killed by the watchdog's `os._exit`.
- **Delivery is at-least-once.** Housekeeping re-sends a row left `sending` by a killed worker, and the
  pinned `Message-ID` lets clients collapse a duplicate. This departs from the prepare-to-deploy
  never-requeue rule for the mail row only. The orphan reap still closes the task row.
- **An unclassified exception is not retried as transient.** The row stays `sending` and the task
  fails loudly. The stuck sweep picks the row up an hour later. A code bug is reported, not retried
  quietly six times.
- **The backoff helper is local.** It is shaped after `calculate_next_retry`
  (`freedom_ls/webhooks/delivery.py:230`) but not imported from it, because importing would point an
  infrastructure app at a product app.
- **No logging and no per-attempt Sentry event.** A transient failure is recorded on the row. Sentry
  hears about dead letters, permanent failures and stuck rows, each as a constant-text
  `capture_message` with only the row id, attempt count and status on the scope. `smtplib` exception
  text can carry recipient addresses, and `scrub_authorization` (`freedom_ls/deployment/sentry.py`)
  does not strip them.
- **`next_attempt_at` and `last_error` are named apart from `WebhookDelivery`'s `next_retry_at` and
  `last_response_error_message`.** `next_attempt_at` is non-null and read by a sweep. `last_error`
  holds an exception, not an HTTP response.

## Requirements

### 1. `OutboundEmail`, in a new `freedom_ls/mail/models.py`

The mail app gets its first model and `migrations/` package, and
`default_auto_field = "django.db.models.BigAutoField"` on `MailAppConfig` (`freedom_ls/mail/apps.py`).

| Field | Type | Note |
| --- | --- | --- |
| `id` | `UUIDField(primary_key=True, default=uuid4)` | |
| `message_id` | `CharField(max_length=255, db_index=True)` | The pinned RFC 5322 `Message-ID`. Not unique: a caller can send the same `EmailMessage` object twice. |
| `recipients` | `JSONField(default=list)` | `message.recipients()`: to, cc and bcc. Kept after scrubbing. |
| `subject` | `CharField(max_length=255)` | Truncated to fit. Kept after scrubbing. |
| `payload` | `JSONField(default=dict)` | The `SerialisedMessage`. Emptied on scrub. |
| `status` | `CharField(max_length=20, choices=Status.choices, default=Status.PENDING)` | See below. |
| `attempt_count` | `PositiveIntegerField(default=0)` | Incremented by the claim. |
| `next_attempt_at` | `DateTimeField` | Non-null, `timezone.now()` at creation. |
| `last_attempt_at` | `DateTimeField(null=True)` | Written by the claim. The stuck sweep and the payload scrub measure from it. |
| `last_error` | `TextField(blank=True, default="")` | `"<exception class path>: <message>"`, truncated to 1000 characters in `save()`. |
| `created_at` | `DateTimeField(auto_now_add=True)` | Row retention measures from it. |
| `sent_at` | `DateTimeField(null=True)` | |
| `scrubbed_at` | `DateTimeField(null=True)` | |

`OutboundEmail.Status` (`TextChoices`) reuses the `WebhookDelivery` words `pending`, `failed`,
`permanent_failure` and `dead_letter` for the same states. `sent` stands where `WebhookDelivery` says
`success`, and `sending` is new.

| Value | Meaning |
| --- | --- |
| `pending` | Written, first attempt not yet claimed. |
| `sending` | Claimed by a worker. |
| `failed` | A transient failure; `next_attempt_at` says when to try again. |
| `sent` | The upstream backend accepted it. |
| `permanent_failure` | Not worth retrying. |
| `dead_letter` | Ran out of attempts. |

One composite index on `(status, next_attempt_at)` and no single-column index on `status`.

### 2. `QueuedEmailBackend` writes the row (`freedom_ls/mail/backends.py`)

The two early paths stay as they are: no recipients is declined, and `UnserialisableMessageError`
falls back to `_send_now`. Otherwise, in order:

1. **Pin the `Message-ID`.**
   `message.extra_headers.setdefault("Message-ID", make_msgid(domain=DNS_NAME))`, using
   `email.utils.make_msgid` and `django.core.mail.utils.DNS_NAME`, as Django does. Without it, Django
   mints a new id on every attempt.
2. **Create the row** synchronously in whatever transaction is open, so a rollback takes it with it.
3. **Enqueue on commit.**
   `transaction.on_commit(<enqueue _send_email_task with str(email.pk)>, robust=True)`, the pattern in
   `freedom_ls/comms/notify.py:97`. The callback stores its `TaskResult` in a closure. An enqueue that
   fails after the commit is logged by Django and leaves a `pending` row for the requeue sweep.
4. **Report an inline failure.** Read `connection.in_atomic_block` before registering the callback.
   When it was false, the callback ran at once. If the captured result has finished (the
   `ImmediateBackend` of dev and tests, whose status is never `READY`), re-read the row. Any status
   but `sent` raises `QueuedEmailNotSentError` unless `fail_silently`. This keeps
   `freedom_ls/course_applications/emails.py:59` telling the applicant the email did not go out.
   Inside a transaction, no inline report is possible and `send()` returns 1. A `failed` row left
   this way is still retried by housekeeping.

A `DatabaseError` from the row insert keeps today's handling and comment: re-raise unless
`fail_silently`, and no fallback to an inline send.

`EMAIL_TASK_PRIORITY = 10` applies to retries as well as first attempts.

### 3. Error classification, in a new `freedom_ls/mail/errors.py`

`classify_send_error(exc: BaseException) -> SendErrorKind | None`, where `SendErrorKind` is a
`StrEnum` of `transient` and `permanent`. The rows are tested in this order: permanent, then
transient, then `None`.

| Kind | Exceptions |
| --- | --- |
| permanent | `SMTPAuthenticationError` with any code, 4xx included (retrying bad credentials across a backlog gets the sending account locked); `SMTPNotSupportedError`; any 5xx `smtp_code`; `SMTPRecipientsRefused` with any 5xx code; `BadHeaderError`; `SSLCertVerificationError`; `UnicodeEncodeError`. |
| transient | `SMTPServerDisconnected`, `SMTPConnectError`, `SMTPHeloError`; any exception with a 4xx `smtp_code` (covers `SMTPSenderRefused`, `SMTPDataError`); `SMTPRecipientsRefused` where every code is 4xx; `TimeoutError`, `ConnectionRefusedError`, `ConnectionResetError`, `BrokenPipeError`, `socket.gaierror`, `ssl.SSLError`; any other `OSError` or `SMTPException`; `UpstreamSendCountZeroError` (Requirement 6). |
| `None` | Anything else, such as a `KeyError` or `ValueError` from FLS's own code. |

The module docstring records the one blind spot. `smtplib.sendmail` raises only when every recipient
is refused, so a partial refusal is recorded as `sent` and not retried, because a retry would
duplicate to the recipients who accepted it.

### 4. The send, in `freedom_ls/mail/tasks.py`

`_send_email_task(email_id: str)` calls `send_outbound_email(email_id)`, which:

1. **Claims the row:**
   ```python
   now = timezone.now()
   claimed = OutboundEmail.objects.filter(
       pk=email_id,
       status__in=(Status.PENDING, Status.FAILED),
       next_attempt_at__lte=now,
   ).update(
       status=Status.SENDING,
       attempt_count=F("attempt_count") + 1,
       last_attempt_at=now,
   )
   if not claimed:
       return
   ```
   That single `UPDATE` is the guard against a second worker, a redelivered or stray task, a sweep and
   a resend racing each other, and against a stray task sending before the ladder says to.
2. Rebuilds the message with `deserialise_message`, applies `set_8bit_encoding`, and sends through
   `config.EMAIL_UPSTREAM_BACKEND` (`send_serialised_email`, with Requirement 6).
3. **On success**, in one `save`: `status=sent`, `sent_at`, `payload={}`, `scrubbed_at`,
   `last_error=""`. Nothing runs between the send and this write.
4. **On a transient failure**, calls `schedule_retry` (Requirement 5) and returns normally.
5. **On a permanent failure**, sets `status=permanent_failure` and `last_error`, and records the
   constant-text Sentry message.
6. **On `None`**, re-raises. The row stays `sending`, and the task result goes FAILED and reaches
   Sentry as it does today.

### 5. Scheduling and re-driving

**`freedom_ls/mail/retry.py`.**

- `next_attempt_delay(attempt_count: int) -> timedelta` walks `config.EMAIL_RETRY_DELAYS`, repeats
  the last value past the end, and adds `random.uniform(0, base * config.EMAIL_RETRY_JITTER_RATIO)`.
- `schedule_retry(email: OutboundEmail, exc: BaseException) -> None`:
  - At `config.EMAIL_MAX_ATTEMPTS`, the row goes to `dead_letter` with `last_error` set, and the
    constant-text Sentry message is recorded.
  - Otherwise the row goes to `failed` with
    `next_attempt_at = now + next_attempt_delay(attempt_count)` and `last_error`. When
    `default_task_backend.supports_defer` is true, it enqueues
    `_send_email_task.using(run_after=email.next_attempt_at).enqueue(str(email.pk))`. When it is
    false, nothing is enqueued and housekeeping drives the row. `.using(run_after=...)` raises
    `InvalidTask` on `ImmediateBackend`, and an undeferred enqueue there would run the whole ladder
    inside the request.

**Sweeps, in a new `freedom_ls/mail/sweeps.py`.** Each one is called from `run_housekeeping_sweeps()`
(`freedom_ls/deployment/housekeeping.py`) in its own `try`, in that function's style, and listed in
the `fls_run_housekeeping` help text. A `DatabaseError` becomes a `sweep_failures` entry.
`freedom_ls/deployment` importing `freedom_ls/mail` is a new edge, and not a cycle, because
`mail -.-> deployment` is test-only.

- `requeue_due_outbound_email() -> int` takes rows in `pending` or `failed` whose `next_attempt_at` is
  more than `config.HOUSEKEEPING_DUE_EMAIL_GRACE_SECONDS` in the past, oldest first, capped at
  `config.HOUSEKEEPING_EMAIL_REQUEUE_BATCH_SIZE`. For each, it sets `next_attempt_at = now` and
  enqueues an undeferred task. The reset means a run with the worker down does not requeue the same
  row on the next run. The count goes into `notes`. The sweep never sends.
- `recover_stuck_outbound_email() -> list[OutboundEmail]` takes rows in `sending` whose
  `last_attempt_at` is older than `config.HOUSEKEEPING_STUCK_EMAIL_MAX_AGE_SECONDS`. Below the attempt
  cap a row goes to `failed` with `next_attempt_at = now`, and the sweep enqueues it at once. At the
  cap it goes to `dead_letter`. Each one records the constant-text Sentry message. Rows this run
  dead-letters become one `findings` entry.
- `prune_outbound_email() -> None` deletes `sent`, `permanent_failure` and `dead_letter` rows whose
  `created_at` is older than `config.EMAIL_OUTBOUND_RETENTION_DAYS`. It empties `payload` and stamps
  `scrubbed_at` on `permanent_failure` and `dead_letter` rows whose `last_attempt_at` is older than
  `config.EMAIL_FAILED_PAYLOAD_RETENTION_DAYS`, so a resent row keeps its body for that long after its
  last failure. `pending`, `failed` and `sending` rows are never pruned.

### 6. The discarded send count (`send_serialised_email`)

```python
sent = connection.send_messages([message])
if not sent:
    raise UpstreamSendCountZeroError(
        f"{config.EMAIL_UPSTREAM_BACKEND} raised nothing and reported 0 messages sent."
    )
```

`UpstreamSendCountZeroError` is declared in `freedom_ls/mail/errors.py` and classified transient.

### 7. Admin, in a new `freedom_ls/mail/admin.py`

`OutboundEmailAdmin(unfold.admin.ModelAdmin)`. The FLS rule that admin classes extend
`SiteAwareModelAdmin` covers site-aware models (`claude_plugins/fls-dev/resources/admin_interface.md`),
and `OutboundEmail` has no `site` column. It is shaped after `WebhookDeliveryAdmin`
(`freedom_ls/webhooks/admin.py:202`), except where this section says otherwise.

- **Superusers only.** `has_module_permission` and `has_view_permission` return
  `request.user.is_superuser`. Add, change and delete permissions are `False`.
- `list_display`: recipients, subject, status, attempt count, next attempt, last attempt, last error
  (truncated). `list_filter`: status and `created_at`. `search_fields`: `message_id`, `subject` and
  `recipients`.
- `payload` appears nowhere, in no list, readonly field or detail view. When `scrubbed_at` is set,
  the detail page says the body was removed and that sending again means repeating the original
  action, such as a new password reset.
- **Resend**, as a bulk action and as an `actions_detail` button, gated by
  `has_resend_permission` returning `request.user.is_superuser`. It applies to `permanent_failure` and
  `dead_letter` rows whose payload is still present. It sets `status=pending`, `attempt_count=0`
  (a new ladder, not a continuation of the dead one) and `next_attempt_at=now` with a conditional
  `update` on those statuses, then enqueues on commit. It never sends inline. It reports
  `messages.success` with the number queued and `messages.warning` with the number skipped and why:
  already sent, in flight, or body removed. It records each resend with `log_change`.

### 8. Settings and checks

In `MailSettings.declared_settings` (`freedom_ls/mail/config.py`), all with defaults:

| Setting | Default |
| --- | --- |
| `EMAIL_MAX_ATTEMPTS` | `6` |
| `EMAIL_RETRY_DELAYS` | `[60, 300, 900, 1800, 3600]` seconds, about 1h51m before jitter |
| `EMAIL_RETRY_JITTER_RATIO` | `0.2` |
| `EMAIL_OUTBOUND_RETENTION_DAYS` | `30` |
| `EMAIL_FAILED_PAYLOAD_RETENTION_DAYS` | `3` |
| `HOUSEKEEPING_DUE_EMAIL_GRACE_SECONDS` | `300` |
| `HOUSEKEEPING_STUCK_EMAIL_MAX_AGE_SECONDS` | `3600` |
| `HOUSEKEEPING_EMAIL_REQUEUE_BATCH_SIZE` | `500` |

`HOUSEKEEPING_STUCK_EMAIL_MAX_AGE_SECONDS` must be at least `WORKER_MAX_TASK_SECONDS` plus
`WORKER_HEARTBEAT_MAX_AGE_SECONDS` plus one watchdog poll, the ceiling rule in
`freedom_ls/deployment/config.py:55-60`, so a send still in flight is never recovered out from under
its worker. A `deploy=True` check in `freedom_ls/deployment/checks.py` errors when it is not.

`freedom_ls_mail.W001` in `freedom_ls/mail/checks.py`, registered with `deploy=True`, warns when
`EMAIL_BACKEND` is `QueuedEmailBackend` and `default_task_backend.supports_defer` is false, because
then every retry waits for housekeeping.

### 9. Production default (`config/settings_prod.py`)

`EMAIL_BACKEND` defaults to `freedom_ls.mail.backends.QueuedEmailBackend`, still overridable through
the env var. The comment above it is rewritten. It says the queue is the default because it brings
retries, that it needs `fls_run_worker` and `fls_run_housekeeping`, and that the SMTP backend is the
explicit opt-out.

## Testing

`upstream_locmem` (`freedom_ls/mail/tests/conftest.py`) makes `mail.outbox` the record of what was
sent. `database_task_backend` (`freedom_ls/conftest.py:379`) swaps in the real database backend.
`django_capture_on_commit_callbacks` covers the on-commit enqueue. A test that crosses commits with
the database backend uses `django_db(transaction=True)`. Ladder tests move `timezone.now()` and call
the sweeps directly. Each new module has a mirrored test module: `test_models.py`, `test_errors.py`,
`test_retry.py`, `test_sweeps.py` and `test_admin.py` under `freedom_ls/mail/tests/`.

The named guards:

- The task argument is a UUID string and nothing else.
- A rolled-back transaction leaves neither a row nor a task.
- Under the inline backend, a transient failure raises `QueuedEmailNotSentError`, and the existing
  `course_applications/tests/test_emails.py` cases still pass.
- Classification, parametrised over the exceptions in Requirement 3's table, including a 4xx
  `SMTPAuthenticationError` as permanent and a plain `ValueError` as `None`.
- A redelivered task does not send twice, a `sent` row is never re-sent, and a task for a `failed`
  row that is not yet due does nothing.
- An unclassified exception leaves the row `sending` and fails the task result.
- Sentry messages carry no payload, recipient or error text on their scope.
- A due row is requeued by housekeeping with no admin involved, and a second run with the worker
  down does not requeue it again.
- Pruning deletes rows in all three terminal statuses past retention, scrubs failed payloads past
  their window, and never touches `pending`, `failed` or `sending` rows.
- A non-superuser staff user cannot see the module. No admin page renders the payload. The detail
  page shows the Resend button to a superuser, and a POST to it re-queues the row. If Unfold does
  not render `actions_detail` on a view-only page, resend ships as the bulk action only.
- The ladder finishes inside the 14-day task-result prune window, and the stuck window default is at
  or above the task ceiling.
- Importing production settings with no `EMAIL_BACKEND` env var gives `QueuedEmailBackend`, and the
  env var overrides it.

## Documentation and downstream

- `docs/product/deployment.md` says the queue is the production default, that the worker sends and
  retries mail, and that `fls_run_housekeeping` must run at least hourly to make retries certain. The
  "fails silently" on line 13 no longer holds for mail.
- `docs/product/configuration-and-extension.md` lists the new settings and the SMTP opt-out.
- `docs/product/security-and-data-handling.md` says what an `OutboundEmail` row stores, that the body
  is removed on delivery or three days after the last failure, and that rows live 30 days.
- `docs/app_structure.md` is regenerated.
- `upgrade_notes.md` says to run `migrate`, that a deployment with no worker must start one or set
  `EMAIL_BACKEND` to the SMTP backend, and that housekeeping must run at least hourly.
- `spec_dd/1. next/user-communication-2-notification-email/idea.md` points at this spec's final
  location.

## Open questions

- Whether a dead letter should escalate beyond a Sentry issue, for example to a daily digest of
  undelivered mail, once there are enough kinds of mail to make the volume worth reading.
- Allauth's login-by-code mail, if a deployment turns it on, expires in minutes, so retries late in
  the ladder deliver dead codes.
- Q: Should the stuck-window ceiling rule be enforced by a deploy check, or by the config test alone?
  → A: A `deploy=True` check in `freedom_ls/deployment/checks.py` (assumed default: an operator who
  raises `WORKER_MAX_TASK_SECONDS` otherwise gets an unsafe window with no warning. Overrule by
  editing Requirement 8.)

## Success criteria

- With the mail host refusing connections for ten minutes, the password reset arrives once the host
  is back, with no operator action and no second request.
- A worker killed mid-send leaves a row that the first housekeeping run after the stuck window
  re-enqueues, and the message then arrives.
- An SMTP 550 gives exactly one Sentry event and no second attempt.
