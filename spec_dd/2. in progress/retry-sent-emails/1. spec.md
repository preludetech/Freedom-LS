# Spec: retry sent emails

## Purpose

Outgoing mail goes onto the task queue (`freedom_ls/mail/backends.py`) and nothing retries it.
`django-tasks` and `django-tasks-db` 0.12.0 never re-run a FAILED result, so a mail host that is
unreachable for thirty seconds loses the message for good. Under
`ACCOUNT_EMAIL_VERIFICATION = "mandatory"` (`config/settings_base.py:437`), a lost verification mail
blocks registration. Three more failures stay silent: a backend that returns 0 without raising is
recorded as a success, a send that raises leaves nothing an operator can act on, and the full message
body, reset link included, sits in `DBTaskResult.args_kwargs` for 14 days.

The retry belongs at the transport layer. Every `EmailMessage.send()` already resolves through
`QueuedEmailBackend`, so progress mail to learners and messages to educators get the retry without
any code of their own. `idea.md` records what was checked and settled.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `OutboundEmail` | coined | The row that owns one outgoing message: its payload until it is sent, then its status, attempts and next attempt time. |
| the outbox table | coined | Prose for `OutboundEmail` rows. `django.core.mail.outbox` is the test-time list of sent messages, so never write a bare "the outbox". |

## Scope

**In.** An `OutboundEmail` row per outgoing message, written by `QueuedEmailBackend`. A send task that
classifies a failure and schedules its own next attempt. Housekeeping sweeps that re-drive due and
stuck rows and prune old ones. A superuser-only, read-only admin with a resend action. Payload
scrubbing. The discarded send count. `QueuedEmailBackend` as the production default.

**Out.**
- Per-category retry policies, priorities and a bulk queue.
- Bounce and complaint feedback after the provider accepts the message.
- Suppression lists.
- Fixing `WebhookDelivery.next_retry_at`, which has the flaw this spec must not copy.
- Any change to a call site: `freedom_ls/accounts/allauth_account_adapter.py` still calls
  `msg.send()`.

## Decisions

- **The task carries the row id and nothing else.** `_send_email_task(email_id: str)`. The only copy
  of the message is in a row whose retention this spec owns. An attempt counter in the task payload
  would copy the reset link into a fresh `DBTaskResult` on every attempt, and it would vanish with a
  lost task.
- **`OutboundEmail` is not a `SiteAwareModel` and has no `site` column.** `SiteAwareModelBase.site` is
  non-null, mail can be sent with no request, and the admin is superuser-only, so no site filter is
  needed. This keeps `mail` off a `site_aware_models` edge.
- **`OutboundEmail` is not a `TimestampedModel`.** Delivery records carry timestamps that mean
  something (`freedom_ls/contrib/conformance/tests/test_timestamped_models.py:23-26`). It declares
  `created_at`, `last_attempt_at`, `sent_at` and `scrubbed_at`.
- **Every attempt is its own task.** A sleep loop would hold the single worker past
  `WORKER_MAX_TASK_SECONDS`, and the watchdog's `os._exit` would kill it mid-flight.
- **Two drivers, one idempotent entry point.** A deferred task is precise but can be lost. A
  housekeeping sweep is coarse but cannot be lost. The claim `UPDATE` (Requirement 4) makes running
  both safe.
- **Delivery is at-least-once.** A worker killed after the provider accepted the message, and before
  the row was marked sent, is re-sent by housekeeping. This departs on purpose from the
  prepare-to-deploy rule that never requeues an orphaned task. That rule stays as it is for the task
  row, while the mail row is re-driven: a lost verification mail blocks registration, a duplicate is
  an annoyance, and the pinned `Message-ID` lets clients collapse it.
- **A rolled-back transaction sends nothing.** The row is written inside the caller's transaction and
  the task is enqueued on commit, so a rollback takes both. The account a link would point at was
  never written either.
- **The ladder is about two hours.** Six attempts with delays of 1, 5, 15, 30 and 60 minutes plus
  jitter. Auth mail that arrives later than that is mostly stale, because people request another one
  within minutes.
- **Resend gives a fresh ladder.** The admin resend resets `attempt_count` to 0 rather than adding to
  it, because the operator is starting a new delivery attempt, not continuing the one that died.
- **The backoff helper is local.** It is shaped after `calculate_next_retry`
  (`freedom_ls/webhooks/delivery.py:230`) but not imported from it: importing would point an
  infrastructure app at a product app.
- **No logging and no per-attempt Sentry event.** A transient failure is recorded on the row. Sentry
  hears about dead letters, permanent failures and stuck rows, each as a constant-text
  `capture_message` with only the row id, attempt count and status on the scope. Exception text from
  `smtplib` can carry recipient addresses, and `scrub_authorization` (`freedom_ls/deployment/sentry.py`)
  does not strip them.
- **The queue becomes the production default.** `docs/product/deployment.md` already makes
  `fls_run_worker` a required production process, and without the queue a production deployment gets
  none of this work.

## Requirements

### 1. `OutboundEmail`, in a new `freedom_ls/mail/models.py`

The mail app gets its first model and `migrations/` package (made with `makemigrations`), and
`default_auto_field = "django.db.models.BigAutoField"` on `MailAppConfig` (`freedom_ls/mail/apps.py`).

| Field | Type | Note |
| --- | --- | --- |
| `id` | `UUIDField(primary_key=True, default=uuid4)` | Passed to the task as `str`. |
| `message_id` | `CharField(max_length=255, unique=True)` | The pinned RFC 5322 `Message-ID` (Requirement 2). |
| `recipients` | `JSONField(default=list)` | `message.recipients()`: to, cc and bcc. Kept after scrubbing. |
| `subject` | `CharField(max_length=255)` | Truncated to fit. Kept after scrubbing. |
| `payload` | `JSONField(default=dict)` | The `SerialisedMessage`. Emptied on scrub. |
| `status` | `CharField(choices=OutboundEmail.Status, db_index=True)` | See below. |
| `attempt_count` | `PositiveIntegerField(default=0)` | Incremented by the claim. |
| `next_attempt_at` | `DateTimeField` | Non-null, `timezone.now()` at creation. |
| `last_attempt_at` | `DateTimeField(null=True)` | Written by the claim. The stuck sweep measures from it. |
| `last_error` | `TextField(blank=True, default="")` | `"<exception class path>: <message>"`, truncated to 1000 characters in `save()`. |
| `created_at` | `DateTimeField(auto_now_add=True)` | |
| `sent_at` | `DateTimeField(null=True)` | |
| `scrubbed_at` | `DateTimeField(null=True)` | |

`OutboundEmail.Status` (`TextChoices`) reuses the `WebhookDelivery` words for the same states:

| Value | Meaning |
| --- | --- |
| `pending` | Written, first attempt not yet claimed. |
| `sending` | Claimed by a worker. |
| `failed` | A transient failure; `next_attempt_at` says when to try again. |
| `sent` | The upstream backend accepted it. |
| `permanent_failure` | Not worth retrying. |
| `dead_letter` | Ran out of attempts. |

Composite index on `(status, next_attempt_at)`.

### 2. `QueuedEmailBackend` writes the row (`freedom_ls/mail/backends.py`)

The two early paths stay as they are: no recipients is declined, and `UnserialisableMessageError`
falls back to `_send_now`. The docstring says that fallback bypasses the outbox table and is never
retried.

Otherwise, in order:

1. **Pin the `Message-ID`.**
   `message.extra_headers.setdefault("Message-ID", make_msgid(domain=DNS_NAME))`, using
   `email.utils.make_msgid` and `django.core.mail.utils.DNS_NAME`. Without it, Django mints a new id
   on every attempt. `extra_headers` survives `serialise_message`.
2. **Create the row** synchronously, in whatever transaction is open, with `status=pending`.
3. **Enqueue on commit.** Call
   `transaction.on_commit(lambda: default_task_backend.enqueue(_send_email_task, args=[str(email.pk)], kwargs={}), robust=True)`,
   the pattern in `freedom_ls/comms/notify.py:97`. Outside an atomic block the callback runs at once.
   An enqueue that fails after the commit is logged by Django and leaves a `pending` row for the
   requeue sweep.
4. **Report an inline failure.** When the enqueue ran at once and the task backend ran the task
   inline (`ImmediateBackend`, dev and tests), re-read the row. Any status but `sent` raises
   `QueuedEmailNotSentError` unless `fail_silently`. This keeps
   `freedom_ls/course_applications/emails.py:59`, which tells the applicant the email did not go out,
   working. A `failed` row left this way is still retried by housekeeping.

A `DatabaseError` from the row insert keeps today's handling and comment: re-raise unless
`fail_silently`, and no fallback to an inline send.

`EMAIL_TASK_PRIORITY = 10` applies to retries as well as first attempts.

### 3. Error classification, in a new `freedom_ls/mail/errors.py`

`classify_send_error(exc: BaseException) -> SendErrorKind | None`, where `SendErrorKind` is a
`StrEnum` of `transient` and `permanent`. `None` means the exception is not a send failure.

| Kind | Exceptions |
| --- | --- |
| transient | `SMTPServerDisconnected`, `SMTPConnectError`, `SMTPHeloError`; any exception with a 4xx `smtp_code` (covers `SMTPSenderRefused`, `SMTPDataError`); `SMTPRecipientsRefused` where every code is 4xx; `TimeoutError`, `ConnectionRefusedError`, `ConnectionResetError`, `BrokenPipeError`, `socket.gaierror`, `ssl.SSLError` other than `SSLCertVerificationError`; any other `OSError` or `SMTPException`; `UpstreamSendCountZeroError` (Requirement 6). |
| permanent | `SMTPAuthenticationError` (retrying bad credentials across a backlog gets the sending account locked); `SMTPNotSupportedError`; any 5xx `smtp_code`; `SMTPRecipientsRefused` with any 5xx code; `ValueError` (covers `BadHeaderError` and `prep_address` failures); `SSLCertVerificationError`; `UnicodeEncodeError`. |
| `None` | Anything else, such as a `KeyError` from FLS's own code. |

The module docstring records the one blind spot. `smtplib.sendmail` raises only when every recipient
is refused, so a partial refusal is recorded as `sent` and not retried, because a retry would
duplicate to the recipients who accepted it.

### 4. The send, in `freedom_ls/mail/tasks.py`

`_send_email_task(email_id: str)` calls `send_outbound_email(email_id)`, which:

1. **Claims the row:**
   ```python
   claimed = OutboundEmail.objects.filter(
       pk=email_id, status__in=(Status.PENDING, Status.FAILED)
   ).update(
       status=Status.SENDING,
       attempt_count=F("attempt_count") + 1,
       last_attempt_at=timezone.now(),
   )
   if not claimed:
       return
   ```
   That single `UPDATE` is the guard against a second worker, a redelivered task, a sweep and a
   resend racing each other.
2. Rebuilds the message with `deserialise_message`, applies `set_8bit_encoding`, and sends through
   `config.EMAIL_UPSTREAM_BACKEND` (`send_serialised_email`, with Requirement 6).
3. **On success**, in one `save`: `status=sent`, `sent_at`, `payload={}`, `scrubbed_at`,
   `last_error=""`. Nothing runs between the send and this write.
4. **On a transient failure**, calls `schedule_retry` (Requirement 5) and returns normally.
5. **On a permanent failure**, sets `status=permanent_failure` and `last_error`, and records the
   constant-text Sentry message.
6. **On `None`**, re-raises. The row stays `sending` for the stuck sweep, and the task result goes
   FAILED and reaches Sentry as it does today.

### 5. Scheduling and re-driving

**`freedom_ls/mail/retry.py`.**

- `next_attempt_delay(attempt_count: int) -> timedelta` walks `config.EMAIL_RETRY_DELAYS`, repeats
  the last value past the end, and adds `random.uniform(0, base * config.EMAIL_RETRY_JITTER_RATIO)`.
- `schedule_retry(email: OutboundEmail, exc: BaseException) -> None`:
  - At `config.EMAIL_MAX_ATTEMPTS`, the row goes to `dead_letter` with `last_error` set, and the
    constant-text Sentry message is recorded.
  - Otherwise the row goes to `failed` with
    `next_attempt_at = now + next_attempt_delay(attempt_count)` and `last_error`. When
    `default_task_backend.supports_defer` is true, it enqueues
    `_send_email_task.using(run_after=email.next_attempt_at).enqueue(str(email.pk))`. When it is
    false, nothing is enqueued and housekeeping drives the row. `.using(run_after=...)` raises
    `InvalidTask` on `ImmediateBackend`, and an undeferred enqueue there would run the whole ladder
    inside the request.

**Sweeps, in a new `freedom_ls/mail/sweeps.py`.** Each one is called from `run_housekeeping_sweeps()`
(`freedom_ls/deployment/housekeeping.py`) in its own `try`, in that function's style, and listed in
the `fls_run_housekeeping` help text. A `DatabaseError` becomes a `sweep_failures` entry.

- `requeue_due_outbound_email() -> int` re-enqueues, undeferred, rows in `pending` or `failed` whose
  `next_attempt_at` is more than `config.HOUSEKEEPING_DUE_EMAIL_GRACE_SECONDS` in the past, oldest
  first, capped at `config.HOUSEKEEPING_EMAIL_REQUEUE_BATCH_SIZE`. It never sends. It covers a lost
  task, an enqueue that failed after the commit, and a backend that cannot defer. The count goes into
  `notes`.
- `recover_stuck_outbound_email() -> list[OutboundEmail]` takes rows in `sending` whose
  `last_attempt_at` is older than `config.HOUSEKEEPING_STUCK_EMAIL_MAX_AGE_SECONDS`. Below the attempt
  cap a row goes back to `failed` with `next_attempt_at = now`. At the cap it goes to `dead_letter`.
  Each one records the constant-text Sentry message. Rows this run dead-letters become one `findings`
  entry.
- `prune_outbound_email() -> None` deletes `sent`, `permanent_failure` and `dead_letter` rows older
  than `config.EMAIL_OUTBOX_RETENTION_DAYS`. It also empties `payload` and stamps `scrubbed_at` on
  `permanent_failure` and `dead_letter` rows older than
  `config.EMAIL_FAILED_PAYLOAD_RETENTION_DAYS`. The failed payload outlives the failure so that resend
  has something to send.

`freedom_ls/deployment` importing `freedom_ls/mail` is a new edge. It is not a cycle, because
`mail -.-> deployment` is test-only.

### 6. The discarded send count (`send_serialised_email`)

```python
sent = connection.send_messages([message])
if not sent:
    raise UpstreamSendCountZeroError(
        f"{config.EMAIL_UPSTREAM_BACKEND} raised nothing and reported 0 messages sent."
    )
```

`UpstreamSendCountZeroError` is declared in `freedom_ls/mail/errors.py` and classified transient.
`SMTPBackend.send_messages` returns 0 when `open()` fails quietly, and provider API backends return 0
for a rejected message.

### 7. Admin, in a new `freedom_ls/mail/admin.py`

`OutboundEmailAdmin(unfold.admin.ModelAdmin)`, not `SiteAwareModelAdmin`. It is shaped after
`WebhookDeliveryAdmin` (`freedom_ls/webhooks/admin.py:202`), except where this section says
otherwise.

- **Superusers only.** `has_module_permission` and `has_view_permission` return
  `request.user.is_superuser`. Add, change and delete permissions are `False`.
- `list_display`: recipients, subject, status, attempt count, next attempt, last attempt, last error
  (truncated). `list_filter`: status and `created_at`. `search_fields`: `message_id`, `subject` and
  `recipients`.
- `payload` appears nowhere, in no list, readonly field or detail view. When `scrubbed_at` is set,
  the detail page says the body was removed and that sending again means repeating the original
  action, such as a new password reset.
- **Resend**, as a bulk action and as an `actions_detail` button, gated on a custom `resend`
  permission and on `is_superuser`. It applies to `permanent_failure` and `dead_letter` rows whose
  payload is still present. It sets `status=pending`, `attempt_count=0` and `next_attempt_at=now`
  with a conditional `update` on those statuses, then enqueues on commit. It never sends inline.
  It reports `messages.success` with the number queued and `messages.warning` with the number skipped
  and why: already sent, in flight, or body removed. It records each resend with `log_change`.

### 8. Settings

In `MailSettings.declared_settings` (`freedom_ls/mail/config.py`), all with defaults:

| Setting | Default |
| --- | --- |
| `EMAIL_MAX_ATTEMPTS` | `6` |
| `EMAIL_RETRY_DELAYS` | `[60, 300, 900, 1800, 3600]` seconds, about 1h51m before jitter |
| `EMAIL_RETRY_JITTER_RATIO` | `0.2` |
| `EMAIL_OUTBOX_RETENTION_DAYS` | `30` |
| `EMAIL_FAILED_PAYLOAD_RETENTION_DAYS` | `3` |
| `HOUSEKEEPING_DUE_EMAIL_GRACE_SECONDS` | `300` |
| `HOUSEKEEPING_STUCK_EMAIL_MAX_AGE_SECONDS` | `3600` |
| `HOUSEKEEPING_EMAIL_REQUEUE_BATCH_SIZE` | `500` |

`HOUSEKEEPING_STUCK_EMAIL_MAX_AGE_SECONDS` follows the ceiling rule in
`freedom_ls/deployment/config.py:55-60`. It must be at least `WORKER_MAX_TASK_SECONDS` plus
`WORKER_HEARTBEAT_MAX_AGE_SECONDS` plus one watchdog poll, so a send that is still in flight is never
recovered out from under its worker.

`freedom_ls_mail.W001` in `freedom_ls/mail/checks.py`, registered with `deploy=True`, warns when
`EMAIL_BACKEND` is `QueuedEmailBackend` and `default_task_backend.supports_defer` is false, because
then every retry waits for housekeeping.

### 9. Production default (`config/settings_prod.py`)

`EMAIL_BACKEND` defaults to `freedom_ls.mail.backends.QueuedEmailBackend`, still overridable through
the env var. The comment above it is rewritten to say that the queue is the default because it brings
retries, that it needs `fls_run_worker` and `fls_run_housekeeping`, and that the SMTP backend is the
explicit opt-out.

## Testing

`upstream_locmem` (`freedom_ls/mail/tests/conftest.py`) makes `mail.outbox` the record of what was
sent. `database_task_backend` (`freedom_ls/conftest.py:379`) swaps in the real database backend.
`django_capture_on_commit_callbacks` covers the on-commit enqueue. Backend tests gain `django_db`.

**The backend.**
- One row per message, and none for a message with no recipients.
- The task argument is a UUID string and nothing else. This guards against the payload creeping back
  into `args_kwargs`.
- The `Message-ID` on the row matches the one in the delivered message.
- The enqueue happens on commit, and a rolled-back transaction leaves neither a row nor a task.
- An enqueue that raises after the commit leaves the row `pending` and does not propagate.
- Under the inline backend, a transient failure raises `QueuedEmailNotSentError`, and the existing
  `course_applications/tests/test_emails.py` cases still pass.

**The send.**
- A success marks the row `sent`, empties the payload, and keeps recipients, subject and
  `message_id`.
- A transient error schedules a retry with the expected delay. Parametrise over
  `SMTPServerDisconnected`, `SMTPConnectError`, `TimeoutError`, `ConnectionResetError`,
  `socket.gaierror`, `SMTPDataError(451, ...)`, `SMTPSenderRefused(452, ...)`,
  `SMTPRecipientsRefused({addr: (450, ...)})` and a backend returning 0.
- A permanent error is not retried. Parametrise over `SMTPRecipientsRefused({addr: (550, ...)})`,
  `SMTPSenderRefused(550, ...)`, `SMTPAuthenticationError`, `SMTPNotSupportedError`,
  `BadHeaderError` and `SSLCertVerificationError`.
- An unclassified exception propagates, leaves the row `sending` and fails the task result.
- The attempt cap dead-letters the row and records a Sentry message whose scope has no payload,
  recipient or error text.
- A redelivered task does not send twice, and a `sent` row is never re-sent.
- Jitter never shortens the base delay.

**The drivers.**
- Under the database backend, a retry is enqueued with a future `run_after`. Under a backend that
  cannot defer, no retry task is enqueued.
- A due row is requeued by housekeeping with no admin involved. This is the named guard against the
  `WebhookDelivery.next_retry_at` flaw.
- A row not yet due, or due but inside the grace window, is left alone.
- The requeue sweep respects the batch size.
- A row stuck in `sending` past the window goes back to `failed`, or to `dead_letter` at the cap,
  which is a finding.
- `sent` rows past retention are deleted, and failed rows past the payload window are scrubbed.
- A `DatabaseError` in a mail sweep is a sweep failure.

**The admin.**
- A non-superuser staff user cannot see the module.
- Resend re-queues `dead_letter` and `permanent_failure` rows, skips `sent`, `sending` and scrubbed
  rows with a warning that gives the count, writes a `LogEntry`, and sends nothing inside the request.
- No admin page renders the payload.

**Config and checks.**
- One assertion per new default, in `freedom_ls/mail/tests/test_config.py`.
- The ladder finishes inside the 14-day task-result prune window.
- The stuck window is at or above the true task ceiling.
- W001 fires only under `--deploy` with the queue selected on a backend that cannot defer.

## Open questions

- Whether a dead letter should escalate beyond a Sentry issue, for example to a daily digest of
  undelivered mail, once there are enough kinds of mail to make the volume worth reading.
- Allauth's login-by-code mail, if a deployment turns it on, expires in minutes, so retries late in
  the ladder deliver dead codes. One policy for all mail stands until a mail type needs another.

## Success criteria

- With the mail host refusing connections for ten minutes, the password reset arrives once the host
  is back, with no operator action and no second request.
- A `pending` row with no task is sent after the next `fls_run_housekeeping` run.
- A worker killed mid-send leaves a row that the next housekeeping run returns to `failed`.
- A `sent` row holds no body, alternatives or attachments.
- An SMTP 550 gives exactly one Sentry event and no second attempt.
- `DBTaskResult.args_kwargs` for `_send_email_task` holds a UUID string and nothing else.
- `freedom_ls/accounts/allauth_account_adapter.py` is unchanged.
- A fresh production settings import resolves `EMAIL_BACKEND` to `QueuedEmailBackend`.
