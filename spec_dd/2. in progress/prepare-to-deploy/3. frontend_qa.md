# Frontend QA — Prepare to deploy

Most of this feature is management commands and settings, but three changes are reachable from a
browser and all three can lock people out of the product if they are wrong:

- `AXES_LOCKOUT_PARAMETERS` moves from the flat form to the nested combined form, changing who gets
  locked out of the login page.
- `AXES_CLIENT_IP_CALLABLE` routes django-axes' notion of the visitor's address through FLS's own
  `get_client_ip`, which this change also rewrites.
- `setup_initial_prod_data` creates the administrative account that has to be able to sign in under
  `ACCOUNT_EMAIL_VERIFICATION = "mandatory"`.

The tests below exercise those, plus the failure and adversarial branches around them.

Everything runs under the **development** settings module. `TRUSTED_PROXY_IP_HEADER` is `None` in
development by design — that is itself one of the things being checked — so do not set it.

---

## §0 Setup

### Dev server

```bash
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL for everything below: `http://127.0.0.1:$PORT`

Development pins the site with `FORCE_SITE_NAME = "DemoDev"` (`config/settings_dev.py:107`), so the
port does not affect which site is served.

### Test data

Demo data must exist. If it does not:

```bash
uv run python manage.py create_demo_data
```

That gives:

| Account | Email | Password |
| --- | --- | --- |
| DemoDev admin | `demodev@email.com` | `demodev@email.com` |
| DemoDev learner | `demodev_s1@email.com` | `demodev_s1@email.com` |
| DemoDev learner | `demodev_s2@email.com` | `demodev_s2@email.com` |

The `DemoDev` site's domain is `127.0.0.1:8000`. §1 and §2 use that domain deliberately, so the
administrator the bootstrap command creates lands on the site the dev server actually serves.

### Reset between tests

Any test that locks an account out must clear the lockout afterwards, or later tests will be
testing the lockout rather than what they meant to test:

```bash
uv run python manage.py axes_reset
```

Lockouts also last one hour (`AXES_COOLOFF_TIME = 1`), so do not wait them out.

## §1 The bootstrap command creates an administrator who can actually sign in

This is the whole point of the command: an account with no verified `EmailAddress` row cannot log in
under mandatory verification, which is the failure this test catches.

1. In a terminal:

   ```bash
   uv run python manage.py setup_initial_prod_data qa-admin@example.test --domain 127.0.0.1:8000
   ```

   **Expect:** the command prints a generated password and a line saying it is shown once. Copy the
   password — it is stored nowhere else.

   **Expect:** the password is a long random string (roughly 22 characters, mixed case and digits).
   If it looks like the email address, or is short, that is a bug.

2. In the browser, go to `http://127.0.0.1:$PORT/accounts/login/`.

   **Expect:** the page renders with 200 and shows the email and password fields.

3. Sign in as `qa-admin@example.test` with the printed password.

   **Expect:** login succeeds. You land on the logged-in experience, or on the
   complete-registration page (`/accounts/complete-registration/`) if the DemoDev site's signup
   policy asks for extra forms. Either is a pass — what fails is being bounced back to the login
   page with "The email address and/or password you specified are not correct", which would mean the
   `EmailAddress` row is missing or not verified.

4. Log out.

## §2 Running it twice changes nothing

1. Note the DemoDev site's current name before re-running:

   ```bash
   uv run python manage.py shell -c "from django.contrib.sites.models import Site; print(Site.objects.get(domain='127.0.0.1:8000').name)"
   ```

   **Expect:** `DemoDev`.

2. Run the command a second time, same arguments:

   ```bash
   uv run python manage.py setup_initial_prod_data qa-admin@example.test --domain 127.0.0.1:8000
   ```

   **Expect:** it says the administrator already exists and the password is unchanged. **Expect no
   password in the output.** A second password printed here would mean the credential was reset.

3. Re-run the shell command from step 1.

   **Expect:** still `DemoDev`. The command's `--site-name` defaults to the domain, so a name of
   `127.0.0.1:8000` here would mean the existing row was overwritten.

4. In the browser, sign in again as `qa-admin@example.test` with the password from §1.

   **Expect:** login still succeeds with the **original** password.

## §3 The login page and the signup flow still work

The client-IP helper changed, and signup writes a `LegalConsent` row through it. A mistake there
throws on submit rather than failing quietly.

1. Visit `/accounts/login/` — **expect** 200, form renders.
2. Visit `/accounts/signup/` — **expect** 200, form renders with the terms checkbox (development
   sets `REQUIRE_TERMS_ACCEPTANCE = True`).
3. Visit `/accounts/password/reset/` — **expect** 200, form renders.
4. Sign in as `demodev_s1@email.com` / `demodev_s1@email.com`.
   **Expect:** success. Log out.
5. Complete a signup with a fresh address, e.g. `qa-signup-1@example.test`, ticking the terms
   checkbox.
   **Expect:** the flow completes to the "verify your email" page with no 500. A `TypeError` or
   `AttributeError` traceback here points straight at `get_client_ip`.
6. Confirm the consent row carries the address:

   ```bash
   uv run python manage.py shell -c "from freedom_ls.accounts.models import LegalConsent; c=LegalConsent._base_manager.order_by('-timestamp').first(); print(c.ip_address)"
   ```

   **Expect:** `127.0.0.1`, not blank and not `None`. With no proxy header configured the helper
   must fall through to `REMOTE_ADDR`; a blank value means the fallback broke.

### §3b Signing up again with an address that already exists

7. Submit the signup form again with `qa-signup-1@example.test`.

   **Expect:** the same "verify your email" outcome as a fresh signup, **not** an error saying the
   address is taken. `ACCOUNT_PREVENT_ENUMERATION = True` (`config/settings_base.py:391`) exists so
   the two responses are indistinguishable. A response that reveals the address is registered is a
   regression, and this feature's signup-path changes are close enough to it to be worth checking.

## §4 Lockout locks the pair, not the address (the headline change)

The flat `AXES_LOCKOUT_PARAMETERS` locked on address alone **or** username alone, which is how one
attacker on one address could lock every account behind a shared egress IP. The nested form requires
both together.

1. `uv run python manage.py axes_reset` first, so you start clean.

2. At `/accounts/login/`, submit five failed logins for `demodev_s1@email.com` with a deliberately
   wrong password (e.g. `wrong-password`).

   **Expect:** the first four show the ordinary invalid-credentials error. On the fifth, the account
   is locked — expect a lockout response (a 403 lockout page, or the login form with a lockout
   message, depending on the axes template in play). Note exactly what you see.

3. Still in the same browser, from the same address, sign in as **`demodev_s2@email.com`** with its
   correct password `demodev_s2@email.com`.

   **Expect: this succeeds.** This is the criterion. If the second account is locked out too, the
   flat form is still in effect and the change did not land.

4. Log out. Try `demodev_s1@email.com` again, this time with its **correct** password
   `demodev_s1@email.com`.

   **Expect:** still locked out. The lockout is keyed on the pair, and this is that pair.

5. Clean up: `uv run python manage.py axes_reset`.

6. **Expect:** `demodev_s1@email.com` can now sign in with its correct password.

## §5 A spoofed client-IP header changes nothing in development

`AXES_CLIENT_IP_CALLABLE` now points axes at `get_client_ip`. In development
`TRUSTED_PROXY_IP_HEADER` is `None`, so the helper must ignore any header a visitor sends and use
`REMOTE_ADDR`. If it did not, anyone could rotate a header value to shed their own lockout.

1. `uv run python manage.py axes_reset`.

2. Lock `demodev_s1@email.com` out again with five wrong passwords, as in §4.

3. Now send further login attempts for the same account with an `X-Real-IP` header set to something
   invented (e.g. `203.0.113.99`). In Playwright, set it with
   `browser_evaluate`-driven `fetch` or by configuring extra HTTP headers on the context; if that is
   not available, do it from the terminal instead:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST \
     -H "X-Real-IP: 203.0.113.99" \
     "http://127.0.0.1:$PORT/accounts/login/" \
     --data "login=demodev_s1@email.com&password=demodev_s1@email.com"
   ```

   **Expect:** still locked out — the header buys nothing. A successful login, or a fresh set of
   five attempts becoming available, means the header is being trusted when it must not be.

   (The CSRF failure a bare `curl` POST produces is fine for this check: what matters is that the
   request is not treated as coming from a different visitor. If the response is a CSRF error rather
   than a lockout, repeat the attempt through the browser with the header set instead.)

4. Clean up: `uv run python manage.py axes_reset`.

## §7 Bad input to the bootstrap command

1. Run it with no `--domain` under the development settings module, which declares no `HOST_DOMAIN`:

   ```bash
   uv run python manage.py setup_initial_prod_data qa-admin-2@example.test
   ```

   **Expect:** a clear error saying no `--domain` was given and `HOST_DOMAIN` is not set. **Expect
   no traceback**, and expect no `User` or `Site` row to have been created — check that
   `qa-admin-2@example.test` does not exist:

   ```bash
   uv run python manage.py shell -c "from freedom_ls.accounts.models import User; print(User._base_manager.filter(email='qa-admin-2@example.test').exists())"
   ```

   **Expect:** `False`.

2. Run it against a brand-new domain:

   ```bash
   uv run python manage.py setup_initial_prod_data qa-admin-3@example.test --domain qa-new.example.test
   ```

   **Expect:** it succeeds and prints a password.

   **Expect:** the new site got a default `Organisation` from the `post_save` receiver — the command
   must not create one itself, and the receiver must still cover this path:

   ```bash
   uv run python manage.py shell -c "from django.contrib.sites.models import Site; from freedom_ls.organisations.models import Organisation; s=Site.objects.get(domain='qa-new.example.test'); print(Organisation._base_manager.filter(site=s, is_default=True).exists())"
   ```

   **Expect:** `True`.

   Note: `qa-admin-3@example.test` belongs to a site the dev server does not serve, so it will
   **not** be able to sign in at `/accounts/login/`. That is correct site isolation, not a bug.

## §8 The two long-running commands

Not browser tests, but they are the other half of what this feature ships and a broken one is
invisible until a deploy.

1. Housekeeping, clean run:

   ```bash
   uv run python manage.py fls_run_housekeeping
   ```

   **Expect:** under the development settings the task backend is `ImmediateBackend`, so the prune
   step is expected to fail and the command should exit **non-zero** with a message naming
   `prune_db_task_results` on stderr. **Expect** the message to also show the session sweep ran —
   the point of the design is that one failing step does not stop the others. Confirm the exit code:

   ```bash
   uv run python manage.py fls_run_housekeeping; echo "exit=$?"
   ```

   **Expect:** `exit=1`.

   **Expect:** no heartbeat file was written, since the run was not clean.

2. Worker, briefly:

   ```bash
   uv run python manage.py fls_run_worker
   ```

   **Expect:** it starts and stays running rather than exiting immediately. In a second terminal,
   twice about two seconds apart:

   ```bash
   stat -c %y /tmp/heartbeat
   ```

   **Expect:** the timestamp advances between the two readings — the heartbeat is being touched once
   per poll while the worker idles.

   **Expect:** Ctrl-C shuts it down promptly and cleanly, without hanging on the watchdog thread.
