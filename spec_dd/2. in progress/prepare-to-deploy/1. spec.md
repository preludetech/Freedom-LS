# Prepare to deploy

## Purpose

FLS has never been deployed, and five things stand between it and a working stack: no `Site` row
matching a real hostname, no worker for the database task backend, nothing emptying the two tables
that grow for the life of a deployment (finished task results and expired `django_session` rows), a
proxy-blind client IP that turns django-axes into a denial of service on the login page, and no
production `CACHES`. `idea.md` argues each one. Where a note in a sub-directory recommends
otherwise, `idea.md` wins.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| heartbeat | coined | A file whose mtime a long-running FLS process updates once per completed cycle of its own work loop, so an external probe can assert the loop is still turning. No existing FLS term. |

## Scope

**In.** A first-run bootstrap management command; a worker command with a heartbeat and a
self-staleness check; a housekeeping command running both sweeps; the axes and allauth settings
that make visitor identity correct behind a proxy; a production `CACHES` setting; the deletion of
`create_site` and `create_site_superuser`; a docstring on `create_demo_data`.

**Out.** The Dockerfile, compose file, `.env.example` and CI workflows. FLS ships none of these
and is not going to. The Sentry cron-monitor check-in, whose slug and environment are fleet
conventions; the downstream wrapper does that. Parameterising `create_demo_data` by domain, or
changing its credentials. Any new `deploy=True` system check.

## Decisions

- **`setup_initial_prod_data` keeps the contract's name; the worker and housekeeping commands do
  not.** Django's `get_commands()` resolves a duplicate command name silently in favour of the app
  earliest in `INSTALLED_APPS`, and FLS apps sit earlier than a downstream's own. `CI-18` fixes the
  bootstrap command's name in both repos, so the collision there is the contract's and is a
  conversation with the downstream repo. Nothing forces the collision for the other two, so FLS
  ships `fls_run_worker` and `fls_run_housekeeping`, and downstream wrappers take the contract's
  `run_worker` and `run_housekeeping`.
- **The bootstrap command lives in `freedom_ls/accounts`, the other two in
  `freedom_ls/deployment`.** `deployment` today depends only on `base` (`docs/app_structure.md`);
  the worker and housekeeping commands touch only external packages and keep that edge count.
  `setup_initial_prod_data` writes `User`, `Site` and allauth `EmailAddress` rows, all of which
  `accounts` already reaches. Putting it in `deployment` would add `deployment → accounts`, and
  putting it in `site_aware_models` would break that app's deliberate zero outgoing edges.
- **`AXES_HANDLER` stays at its default.** django-axes 8.3.1 defaults to
  `axes.handlers.database.AxesDatabaseHandler`, which counts against `AccessAttempt` rows in
  Postgres and is already shared across gunicorn workers. Switching to the cache handler would
  discard the `AccessAttempt` audit trail and let a cull or a deploy clear live lockouts. The
  production cache is still required, because `CI-14` binds it and because allauth's
  `ACCOUNT_RATE_LIMITS` (`config/settings_base.py:392`) genuinely are per-worker and lost on
  restart today.
- **One client-IP setting, holding a plain HTTP header name.** `TRUSTED_PROXY_IP_HEADER` changes
  from a `request.META` key to a header name, because that is the form
  `ALLAUTH_TRUSTED_CLIENT_IP_HEADER` requires and the form the edge documents. One value feeds
  axes, allauth and `LegalConsent`, and the comma-split that made the old form dangerous goes away
  with it.
- **The worker carries a copy of `django_tasks_db`'s poll loop.** `Worker.run()` is the only method
  that executes once per poll whether or not a task was claimed, and `db_worker`'s `Command.handle`
  names `Worker` directly rather than through an overridable attribute, so there is no seam. A
  heartbeat touched anywhere else, on a timer or inside `run_task()`, stays green on a worker wedged
  inside a task, which is the failure this exists to catch. The copy is affordable because
  `django-tasks-db==0.12.0` is pinned exactly.
- **A watchdog thread, not `SIGALRM`.** A wedged worker is stuck inside `task.call()`, so the next
  iteration of its own loop never arrives. `SIGALRM` raises into `run_task()`'s broad
  `except BaseException`, which records an ordinary task failure and continues.

## Requirements

### The bootstrap command

Add `freedom_ls/accounts/management/commands/setup_initial_prod_data.py`, djclick, matching the
house thin-command idiom of `freedom_ls/role_based_permissions/management/commands/sync_role_permissions.py`:
a short `command()` calling module-level helpers that hold the logic.

Signature: one required `admin_email` argument, `--domain` defaulting to the settings module's
`HOST_DOMAIN`, `--site-name` defaulting to the resolved domain. `HOST_DOMAIN` is declared only in
`config/settings_prod.py`, so under any other settings module the attribute is absent rather than
empty; both cases raise `click.ClickException`.

What it writes:

- The `Site` row, looked up by `domain`, never by `name`. Keying on `name` is what made
  `create_site` reassign `site.domain` without saving. `Site.objects.get_or_create(domain=..., defaults={"name": ...})`.
- The administrative `User`: `is_staff`, `is_superuser` and `is_active` all true, and `site` set to
  that `Site`. `UserManager.create_user` and `create_superuser` (`freedom_ls/accounts/models.py:34`,
  `:57`) accept no `site` argument, so construct `User(...)` directly with `site=`, call
  `set_password()`, then `save()`.
- The allauth `EmailAddress` row, `verified=True, primary=True`, keyed on `(user, email)`. Without
  it the account cannot sign in under `ACCOUNT_EMAIL_VERIFICATION = "mandatory"`.

Nothing creates the default `Organisation`: the `post_save` receiver on `Site` at
`freedom_ls/organisations/signals.py:44` already does, whatever wrote the row.

Three properties bind, from `CI-18`:

- **Safe to run twice.** Every write is a lookup-or-create.
- **It never resets an existing password.** `set_password()` is reachable only inside the branch
  where the `User` row did not already exist. A second run prints nothing about the credential.
- **It generates the password and prints it once.** `django.utils.crypto.get_random_string`, the
  Django-recommended generator since `BaseUserManager.make_random_password()` was removed in 5.1,
  at a length giving at least 128 bits over its 62-character alphabet. The password reaches stdout
  and nothing else: no `logging` call, no file, no database column in plaintext.

Delete `freedom_ls/site_aware_models/management/commands/create_site.py` and
`create_site_superuser.py`. The second is zero bytes, so Django has never registered a command
under that name. Nothing executable imports either; the only reference is prose in the docstring at
`freedom_ls/organisations/signals.py:50`, which must be updated to stop naming `create_site`.

### The worker command

Add `freedom_ls/deployment/worker.py` and
`freedom_ls/deployment/management/commands/fls_run_worker.py`. Plain `BaseCommand`, matching
`db_worker` upstream and FLS's own tooling-invoked commands.

`fls_run_worker` takes no arguments. It touches the heartbeat once, starts the watchdog, then
constructs the FLS worker with `queue_names=["*"]` and `django_tasks_db`'s own defaults for
`interval`, `batch`, `backend_name`, `startup_delay`, `max_tasks` and `worker_id`
(`db_worker.Command.add_arguments`), calls `configure_signals()` and `run()`. `--reload` is not
carried over. Anyone wanting the full flag surface runs `db_worker`, which stays available.

`queue_names=["*"]` sets `Worker.process_all_queues`, so a task on any queue is picked up.
`db_worker`'s own default is `default` alone.

`freedom_ls/deployment/worker.py` holds:

- `HeartbeatWorker(Worker)`, overriding `run()` with a copy of `django_tasks_db`'s loop body plus a
  heartbeat touch in the position that executes on every iteration regardless of whether a task was
  claimed, after `close_old_connections()` and before the interval sleep. Nowhere else.
- A `touch_heartbeat(path)` helper: `Path(path).touch()`, creating parent directories if absent.
  Only mtime matters; the file's contents are never read.
- A watchdog started as a `threading.Thread(daemon=True)` before the loop, so a clean exit is never
  held open. It wakes every 30 seconds, reads the heartbeat file's mtime, and when that mtime is
  older than the staleness window calls `sentry_sdk.capture_message(...)`, then
  `sentry_sdk.flush(timeout=...)`, then `os._exit(1)`. The flush is not optional. `os._exit` skips
  `atexit`, and the SDK's automatic drain is an `atexit` integration, so without the flush the
  Sentry report is lost in exactly the case that matters. `sys.exit()` is wrong here. It raises
  `SystemExit` in the watchdog thread only and leaves the wedged main thread running.

Settings, declared on `DeploymentSettings` in `freedom_ls/deployment/config.py` and read through the
`config` singleton at call time:

- `WORKER_HEARTBEAT_PATH`, default `"/tmp/heartbeat"`. The path `COMPOSE-8` fixes, under `/tmp`
  because the image runs as a non-root user.
- `WORKER_HEARTBEAT_MAX_AGE_SECONDS`, default `300`. Matches the healthcheck's `-mmin -5` window,
  so the process exits at about the moment an external probe would go red. It is also the longest a
  task may run before being killed mid-flight; a deployment with longer tasks raises it.

### The housekeeping command

Add `freedom_ls/deployment/housekeeping.py` and
`freedom_ls/deployment/management/commands/fls_run_housekeeping.py`. Plain `BaseCommand`, no
arguments. It runs once and exits; the downstream wrapper supplies the loop and the interval.

One command rather than a shell chain, because every requirement on it is an exit-code decision.

Three steps, each in its own `try`/`except` so no failure stops a later step:

1. `call_command("prune_db_task_results", queue_name="*")`. `call_command` does not catch
   `CommandError`, which lives in `run_from_argv`, so the exception propagates into the local
   `except`. `--backend` needs no value, because FLS has one task backend, aliased `default`.
2. `call_command("clearsessions")`. FLS sets no `SESSION_ENGINE`, so Django's database backend
   applies and this is a real `DELETE FROM django_session WHERE expire_date < now()`.
3. The late-unpicked-task check. A worker polls once a second, so a task that was due more than an
   hour ago and is still `READY` means nothing is consuming. The worker heartbeat cannot see that,
   because a worker that stopped touches nothing at all. Scheduled tasks not yet due must not
   count. `DBTaskResult.run_after` is non-nullable and carries the sentinel `get_date_max()` (year
   9999) for a task enqueued with no schedule, so lateness is measured from `enqueued_at` on that
   branch and from `run_after` on the other:

   ```python
   cutoff = timezone.now() - timedelta(seconds=config.HOUSEKEEPING_UNPICKED_TASK_MAX_AGE_SECONDS)
   late = DBTaskResult.objects.filter(status=TaskResultStatus.READY).filter(
       Q(run_after=get_date_max(), enqueued_at__lte=cutoff)
       | Q(run_after__lt=get_date_max(), run_after__lte=cutoff)
   )
   ```

   A future `run_after` never satisfies `run_after__lte=cutoff`, so "not yet due is not late" falls
   out without a special case. Every queue, no scoping.

Every failure reaches Sentry explicitly, whether a sweep raised or the late-task check found rows.
A caught exception goes to `sentry_sdk.capture_exception(exc)`, late tasks to
`sentry_sdk.capture_message(...)`. Sentry's Django integration never sees either, because the
`except` blocks swallow them by design. `init_sentry()` is a no-op without a DSN
(`freedom_ls/deployment/sentry.py:9`), so these calls are safe in dev and CI.

After all three steps, if anything failed, raise `CommandError`, which `run_from_argv` turns into a
message on stderr and a non-zero exit. Touch the heartbeat only on a fully clean run, both sweeps
succeeded and no late tasks.

Both sweeps are already safe to run twice: `prune_db_task_results` deletes only `SUCCESSFUL` or
`FAILED` rows, and `clear_expired()` never touches a live session.

Settings on `DeploymentSettings`:

- `HOUSEKEEPING_HEARTBEAT_PATH`, default `"/tmp/heartbeat"`, the same default as the worker's
  because `COMPOSE-8` gives each process its own container and its own `/tmp`. It is a separate
  setting so a deployment that co-locates the two can point them at different files; on one shared
  file a daily sweep would keep a dead worker's heartbeat fresh.
- `HOUSEKEEPING_UNPICKED_TASK_MAX_AGE_SECONDS`, default `3600`.

### Visitor identity behind the edge

`TRUSTED_PROXY_IP_HEADER` changes meaning. It now holds a plain HTTP header name (`"X-Real-IP"`),
not a `request.META` key (`"HTTP_X_FORWARDED_FOR"`). Its declaration stays where it is, at
`config/settings_base.py:327` and in the `AccountsConfig` entry in `freedom_ls/accounts/config.py`,
which read the same value. The comment above that declaration gives the old `request.META` spelling
as its example and has to be rewritten with it.

In `freedom_ls/accounts/utils.py:14`, `get_client_ip` reads `request.headers.get(header_name)`
rather than `request.META`, and the comma-split at line 31 goes. A single-valued header set (not
appended) by the edge carries exactly one address; splitting it was only ever needed for
`X-Forwarded-For`, whose leftmost entry is whatever the visitor typed. Rewrite the docstring. Its
current `X-Forwarded-For` example is the header this must never read. `REMOTE_ADDR` stays the
fallback when the header is absent, which is what keeps the function correct on a deployment with
no proxy in front.

In `config/settings_base.py`, `AXES_LOCKOUT_PARAMETERS` (line 321) takes the nested form and two
settings join it beside the unchanged `AXES_FAILURE_LIMIT` and `AXES_COOLOFF_TIME`:

```python
AXES_LOCKOUT_PARAMETERS = [["ip_address", "username"]]
AXES_RESET_COOL_OFF_ON_FAILURE_DURING_LOCKOUT = False
AXES_CLIENT_IP_CALLABLE = "freedom_ls.accounts.utils.get_client_ip"
```

The nested list is one combined parameter, so a lockout needs address and username together; the
flat form axes reads today is two independent parameters and locks on either alone. axes' library
default for the cool-off setting is `True`, which measures the cool-off from the most recent
attempt including attempts made while already locked out, so a script that keeps trying holds its
own lockout open for as long as it runs. All three are correct in development too, so they belong
in the base module. `AXES_CLIENT_IP_CALLABLE` short-circuits axes' own resolution, which otherwise
ends at `REMOTE_ADDR`; it is safe unconditionally because `get_client_ip` falls back to
`REMOTE_ADDR` when no header is configured.

In `config/settings_prod.py`, two explicit lines:

```python
TRUSTED_PROXY_IP_HEADER = "X-Real-IP"
ALLAUTH_TRUSTED_CLIENT_IP_HEADER = TRUSTED_PROXY_IP_HEADER
```

Do not set `ALLAUTH_TRUSTED_PROXY_COUNT`; it selects the `X-Forwarded-For` path instead. Naming the
header removes allauth's fallback to `REMOTE_ADDR`, so the edge header becomes load-bearing for
login and signup. That is why the setting is prod-only and defaults to `None`. A development server
with no proxy in front must not have it set.

### The production cache

Add to `freedom_ls/deployment/settings_defaults.py`, beside `DATABASE_TASKS`:

```python
DATABASE_CACHES: dict[str, dict[str, object]] = {
    "default": {
        "BACKEND": "django.core.cache.backends.db.DatabaseCache",
        "LOCATION": "django_cache_table",
        "OPTIONS": {"MAX_ENTRIES": 5000},
    }
}
```

`config/settings_prod.py` sets `CACHES = fls_defaults.DATABASE_CACHES`. `LOCATION` and
`MAX_ENTRIES` are fixed by `CI-14`; Django's own `MAX_ENTRIES` default of 300 is too small to be
useful. The table is not a migration. `createcachetable` creates it, idempotently, and that runs
in the downstream's deploy sequence, not in FLS.

### `create_demo_data`

`freedom_ls/learner_management/management/commands/create_demo_data.py` keeps its hardcoded
loopback domains and its password-equals-email accounts; they are correct for development. Give it
a docstring, and replace its `help` string, currently "Create a superuser and 2 sites for initial
setup", with text saying it is a development command that must never be pointed at a reachable
hostname. It is the only command that writes `Site` rows, and reads from the outside like something
a staging tier could use.

## Testing

Tests go in `freedom_ls/<app>/tests/`, invoke commands through `call_command`, and stay unmarked,
since none of this touches FLS's own brand, theme or demo content. Site-aware models take the
`mock_site_context` fixture. djclick commands need `redirect_stdout` and raise `ClickException`;
plain `BaseCommand` commands accept `stdout=StringIO()` and raise `CommandError`.

**Bootstrap.** A first run creates the `Site`, the `User` with `site` set, and a verified primary
`EmailAddress`, and prints a password. A second run against the same domain and email changes no
password hash and prints no credential. A run whose domain matches an existing `Site` under a
different `name` leaves that row's domain intact, the case `create_site` got wrong. A run with no
`--domain` under a settings module that declares no `HOST_DOMAIN` raises `ClickException`. The
created `Site` has a default `Organisation`, which proves the receiver still fires for this path.

**Worker.** Test the heartbeat and watchdog logic as directly callable functions, not through a
live loop. No FLS convention or upstream tooling spins up a real `Worker` inside a test, and the
suite runs under `ImmediateBackend`. Touching an absent path creates it; touching an existing one
advances its mtime. A watchdog whose heartbeat is older than the window calls Sentry and then the
exit path, both mocked; one inside the window calls neither. A test asserts
`django_tasks_db.__version__ == "0.12.0"`, failing with a message naming
`freedom_ls/deployment/worker.py` as the copied loop that must be re-checked. A test asserts the
worker is constructed with `queue_names=["*"]`.

**Housekeeping.** A prune that raises still runs the session sweep, and vice versa; both failures
reach Sentry; the command exits non-zero in either case and does not touch the heartbeat. A clean
run touches it. A `READY` row enqueued two hours ago with the sentinel `run_after` is late; one
whose `run_after` is an hour in the future is not; one whose `run_after` was two hours ago is. A
`SUCCESSFUL` row of any age is not late. Expired sessions go and live ones stay.

**Client IP.** With no header configured, `get_client_ip` returns `REMOTE_ADDR`. With one
configured and present, it returns that value verbatim, including one containing a comma, which
must come back whole rather than split. With one configured and absent, it falls back to
`REMOTE_ADDR`. A test asserts `AXES_LOCKOUT_PARAMETERS` is the nested form, since the flat form is
the live denial of service.

## Documentation and downstream

- `docs/product/deployment.md:45` tells operators to run bare `db_worker`, and `:49` tells them to
  schedule `prune_db_task_results` themselves. Both are superseded by the two new commands.
- `docs/deployment-security-checklist.md` has no section on `CACHES` and none on the axes or
  allauth client-IP settings. Both are now deployment-security requirements.
- The changed meaning of `TRUSTED_PROXY_IP_HEADER` is a breaking change for any project that set
  it, and belongs in the upgrade notes with the old and new spellings side by side.
  `claude_plugins/fls-dev/skills/registration/SKILL.md:60` documents the old `request.META` form
  and has to move with it.
- The concrete-project template ships a `caddy` service publishing 80 and 443, and a `web`
  healthcheck built on a bare `urllib.request.urlopen` that cannot send `Accept: application/json`
  and so lands on the `Site.DoesNotExist` path. Neither is FLS's code, and both need fixing before
  anyone copies the template onto a fleet box.
- Downstream wrappers: `run_worker` calls `fls_run_worker`, `run_housekeeping` calls
  `fls_run_housekeeping` and adds the Sentry cron-monitor check-in.

## Open questions

- `CI-18` fixes `setup_initial_prod_data` as the name in both repos. FLS apps sit earlier in
  `INSTALLED_APPS` than a downstream's own, so FLS's would win silently. First-Class-LMS has
  recorded an intent to write one but has not; the conversation with that repo has to happen before
  either side ships. It carries a second item: the contract's runbook snippet invokes the command
  with no arguments and defines no environment key for the administrator's address, so FLS's
  required `admin_email` argument has to be added to that snippet.
- `EDGE-12` gives its own rationale for the cache as django-axes' failure counters needing to be
  shared across gunicorn workers. That is inaccurate under axes' default database handler. The
  clause's requirement stands; its reasoning is worth flagging to the infrastructure repo.
- A worker killed mid-task by the watchdog leaves its `DBTaskResult` row `RUNNING`. Nothing
  reclaims or reports it, since the late-task check looks only at `READY`. Whether that needs its
  own sweep is not settled here.

## Success criteria

- `manage.py setup_initial_prod_data admin@example.com --domain example.org` against a fresh
  database leaves a stack whose login, signup and password-reset pages return 200 on that host.
- Running it a second time leaves the administrator's password hash byte-identical.
- `manage.py fls_run_worker` executes a task enqueued on a non-`default` queue.
- Its heartbeat file's mtime advances at least once a second while the worker idles.
- A worker whose main thread is blocked past the staleness window exits non-zero, with an event in
  Sentry.
- `manage.py fls_run_housekeeping` with a deliberately broken prune still clears expired sessions,
  exits non-zero, reports to Sentry and leaves the heartbeat untouched.
- A `READY` task due 90 minutes ago fails the command; one scheduled for tomorrow does not.
- `manage.py create_site` and `manage.py create_site_superuser` both report an unknown command.
- Under `settings_prod`, five failed logins for one username from one address lock that pair only,
  and leave a second username on the same address able to sign in.
- Under `settings_prod`, `django.core.cache.cache` is a `DatabaseCache` against
  `django_cache_table`.
