## 2. Where the commit hash is stored and how `content_save` exposes it

Recorded by `-1-content-save-safety` (spec: `spec_dd/3. done/2026-11-22_10:30_...-1-content-save-safety/1. spec.md`, "Save record").

- Models in `content_engine/models/content_saves.py`: `ContentSave(SiteAwareModel)` with `saved_at` and `generate_uuids` (bool: true means the run wrote uuids into files, so the recorded commit does not contain them); `ContentSaveSource` (`content_save` FK PROTECT `related_name="sources"`, `order`, `repo_path`, `commit` char(64), no site column, unique (`content_save`,`order`)). One `ContentSave` per run, one source per source path. There is no single "the" hash on a save: a multi-path save has one commit per source path.
- Producer: in `content_engine/management/commands/content_save.py`, `command()` builds `source_commits = check_committed(paths, ignores)` (a list of `SourceCommit(path, repo_path, commit)`, line ~1841) and passes it to `save_content_to_db(..., source_commits=...)`. `save_content_to_db` calls `_write_sources(...)` (`@transaction.atomic`), which creates `ContentSave` + bulk `ContentSaveSource` at the very END (line ~1988), after every `_write_source(source, site, ledger)` has run and after retirement. `source_commits=None` (direct callers, tests, `loaded_demo_content`) creates no record.
- Consequence for versions: `save_form_question()` runs inside `_write_source()`, which receives only `source`, `site`, `ledger`. Neither the commit nor the `ContentSave` is in scope there, and the `ContentSave` row does not exist yet when a question version would be written. The spec has to either create `ContentSave`/sources before the writes (same transaction, same rollback) and thread the matching `SourceCommit` (by index of `sources` vs `source_commits`) to `save_form_question`, or add the commit to `_RunLedger`/an argument. A version row can then point at the `ContentSaveSource` that carried its file, or copy the sha. Without `source_commits` the hash must be nullable/blank.
- Layering: `content_engine` imports `form_engine` (`content_save.py` imports `form_engine.models`, `form_engine.signals`), not the reverse. A version model in `form_engine` cannot cleanly FK `ContentSaveSource`; options are a plain `commit` CharField (+ `content_save_id`/`generate_uuids` copies), or putting the version model in `content_engine` (where `FormQuestionTopic` already lives, `content_engine/models/question_sections.py`) but then `form_engine` readers (`conditions.py`, `models.py`) would import `content_engine`. `form_engine/tests/invariants/test_import_independence.py` guards only `scoring`, `signals`, `submissions`, `typed_answers`, `phone_numbers` against importing `form_engine.models`, so a new helper module has to be added to that list if it is meant to stay model-free.
- `generate_uuids=True` runs record a commit that lacks the uuids (spec -1 open question: "Spec 3 decides whether such saves count for question versions"). Still open; the version must at least be able to carry the flag.
- Uuids: with `--generate-uuids` a question or option with no uuid is `create()`d (`save_with_uuid`, `update_file_with_uuid`, `update_file_with_option_uuids`) and gets version 1 on that run. Options with no uuid are created fresh each run until written back; the version snapshot must hold the saved option ids (`saved_options` returned by `save_form_question`).

## 3. How `content_save` writes questions now (where the version hook sits)

`save_form_question(item, form_page, site, base_path, order, condition_option) -> (FormQuestion, list[QuestionOption])` (line ~961):
1. `save_with_uuid(FormQuestion, ..., exclude_fields={"options","when","sections"}, slug=..., group=..., explanation=...)`: `update_or_create`, then `markdown_translate(instance.content)` only `if item.content` (a `FormQuestion` has no `content`, so the `AttributeError` branch swallows it). **The seams research says markdown is translated after write; for `FormQuestion.question` that translation does not happen in `save_with_uuid`** (the `try: if item.content` raises `AttributeError` for a question and is ignored). Check whether `question` text is translated elsewhere (grep `markdown_translate` callers) before deciding "hash the stored value"; for questions the authored and stored value may already be identical. Verify before writing the spec.
2. Each option via `save_with_uuid(QuestionOption, ..., question=, order=idx, value=str(option.value))`; note `save_with_uuid` always sets `retired_at=None` on the option, and a re-saved row is overwritten wholesale.
3. Caller (`_write_source`, lines ~1652-1684) adds the question and options to `ledger.saw`, records `seen_question_ids`, builds `sections_by_question`, `options_by_slug`. After the loop: `replace_question_sections`, `mark_dropped_questions(...)`. The version write belongs in or immediately after `save_form_question`, comparing the new state to the latest `FormQuestionVersion` for that question.
4. An option previously retired (not in source) is not in `saved_options`; `retire_missing` marks it retired after the run. The snapshot "set of options" must say whether it is the live set at save time (items in `saved_options`) and what an option retirement does: dropping an option from the YAML changes the set, so `_retire_missing` (run after all writes, `retire_missing=True` only, i.e. command runs; not direct callers) happens AFTER the version compare. Either the version write must be deferred until after `_retire_missing` or the compare must treat "option in the YAML" as the set. A question retired whole (dropped from YAML) needs no new version ("a revision does not retire", and retiring does not revise; settled in the idea).
5. Everything runs in one `@transaction.atomic` (`_write_sources`), so versions roll back with the save.

Fields to snapshot vs the idea's list: `question`, `type`, `required`, `min`, `max`, `decimal_places`, options' `text`, `value`, `order`, `correct`, option ids. **Not in the idea's list but learner-visible/new since:** `FormQuestion.explanation` (shown in the learner revision feedback via `learner_interface/templates/learner_interface/partials/revision_feedback.html`; `revision` is not a past-attempt reader) and `QuestionOption.locked` (shuffle lock; idea excludes lock/group settings). Flag `explanation` to the spec author: idea says "nothing else counts", so a corrected explanation makes no version.

## 4. The served paper today (shuffle, pools, groups)

`form_engine/conditions.py`:
```python
class ServedPage(TypedDict):
    id: str
    children: list[str]

class ServedPaper(TypedDict):
    seed: int
    pages: list[ServedPage]
    options: dict[str, list[str]]   # question id -> option ids in served order
```
Stored in `FormProgress.served_paper` (JSON, null until written; migration `0010_formprogress_served_paper`, shuffle `0011`). Built by `form_engine/served_paper.py` `build_served_paper(form)`:
- `served_pages(form)` (live pages, a page with all children retired dropped), optional `shuffle_pages` shuffle.
- Per page `_served_children(page, form, seed)`: `shuffle_units(live_children(page))` (from `form_engine/units.py`, keep-together `group` runs) then `_drawn_units(units, page, seed)` (draw `page.draw` units via `rng.sample`, sorted to authored order) then, if `form.shuffle_questions`, shuffle the units, then flatten. Groups and draws therefore never appear in the stored JSON; only the flattened child id lists and the option id lists are stored. There is **no per-group or per-draw metadata** in the paper. The `versions` key is therefore a flat `question_id -> version_id` map, written in the same loop that fills `options` (line ~104: `for child in children: if isinstance(child, FormQuestion): ... options[str(child.id)] = option_ids`). Every served question needs an entry, including a question with no options (the `options` map omits questions with no options; a `versions` map must not).
- `_served_options()` shuffles `live_options(question)` with locks. The versions snapshot's option ids must match the live option ids at that instant, so the version to pin is "latest version at attempt start", and the served option list must be consistent with that version's option snapshot (the live rows at that time already equal the latest version, apart from retired options which `live_options` already excludes).
- Written once: `ensure_served_paper(form_progress)` (QUIZ strategy, open sitting, `served_paper IS NULL` guarded `update`). Callers: `learner_interface/views.py` lines ~2091, 2144, 2304, 3228 and `FormProgress.complete()`. At `complete()` it writes a paper for a sitting that never had one, so a paper written at completion pins the version current at completion, not at start. State this.
- `seed` plus `random.sample`/`shuffle` are not reproducible across Python versions (comment at the end of `build_served_paper`); the stored lists are the record. Same stance for `versions`.
- Old papers lack the `versions` key (`ServedPaper` is read with `served_paper["options"]`). The migration backfill must either add a `versions` key to existing papers or readers must tolerate its absence (`.get("versions", {})`). The TypedDict would need `total=False` or a `NotRequired`.
- Tests/factories: `form_engine/factories.py` has `served_paper_of(...)` and `served_papers_over_seeds(...)` (patch `served_paper_module.new_seed`), `FormFactory`, `FormPageFactory`, `FormContentFactory`, `FormQuestionFactory`, `QuestionOptionFactory`, `FormProgressFactory`, `FormDeclarationFactory`, `QuestionAnswerFactory`, `QuestionAnswerFileFactory`. A `FormQuestionVersionFactory` and a hook making `FormQuestionFactory` create version 1 (or the factories creating versions lazily) is needed, since `build_served_paper` will require a version per question. All existing tests that build a `FormProgress` with a hand-written `served_paper` dict (many in `form_engine/tests/test_conditions.py` (63 tests), `test_served_paper.py`, `test_models.py`, `learner_interface`, `educator_interface`) lack the `versions` key and have no version rows; the reader must tolerate this or those tests break en masse.

## 5. SittingPath: the API templates and readers use

`SittingPath` (`conditions.py`, frozen dataclass; fields `all_pages`, `children_by_page`, `question_ids`, `content_ids`, `served_options_by_question`, `has_missing_served_items`). Built by `served_path`, `compute_path`, `frozen_path`, `full_path` through `_path(...)`. Chosen by `sitting_path(form_progress, answers=None)`: served paper -> `served_path`; else `asked` -> `frozen_path`; else completed -> `full_path`; else `compute_path`. `current_path()` is the in-progress variant (paper else compute_path).

Methods/attrs consumers call: `pages`, `numbered_pages()`, `page_count`, `children_of(page)`, `questions_of(page)`, `questions()` (list of `FormQuestion`), `question_positions()`, `has_question(id)`, `question_ids`, `options_of(question)` (served `QuestionOption` list), `options_added_since(question)` (current live options not served and not retired), `as_asked()`, `has_missing_served_items`, page navigation helpers.

What a version-backed object must expose (as read by templates and code):
- Question: `id` (the `FormQuestion` id, used for `answers_by_question` keys, `question_positions`, `has_question`, gates), `question` text, `rendered_question()` (templates `question.html`, `inputs/*.html`, `answers/question.html`, `revision_feedback.html`), `rendered_explanation()` if explanation is versioned, `type`, `required`, `min`, `max`, `decimal_places`, `number_step` property, `question_number()` (calls `self.form_page.form` and walks live pages; it is a `FormQuestion` method, version-backed objects must not inherit a live-tree lookup), `is_retired` (`question.html` `show_retired` badge, `queries._row(... question_retired=question.is_retired)`), `form_page`, `condition_option`, `group`, `slug`, `category`, `order`, `pk`/`id`, `options.all()` (used in `form_engine_tags.question_options` fallback and `marking_options`), plus `isinstance(child, FormQuestion)` checks in `conditions.py`, `served_paper.py`, `models.py` (`_quiz_questions`), `quiz_attempt.py`. A proxy that is not a `FormQuestion` instance breaks every `isinstance` check; a `FormQuestion` instance with fields overwritten in memory (copy of the live instance with version values applied, never saved) keeps `isinstance`, the FK attributes and `rendered_question()` for free. Same for options: `QuestionOption` fields read are `id`, `text`, `value`, `order`, `correct`, `question_id`, `locked` (shuffle only), `is_retired`. Recommendation to weigh in the spec: build unsaved `FormQuestion`/`QuestionOption` instances from the version (instantiate with the live id), mark them non-saveable, so `isinstance`, templates, `is_quiz_answer_correct` (reads `.id`, `.correct`) and `marking_options` need no change. Danger: calling `.save()` on one would overwrite live content; a guard or `_state` is worth a test.
- Options on templates: `inputs/multiple_choice.html`, `checkboxes.html`, `dropdown.html` and `answers/options.html` use `option.text`, `option.value`, `option.id`, `option.correct` (when `show_answer_key`); learner `course_form_complete.html` uses `option.correct`, `option.text` on `item.learner_selected` / `item.correct_options`. `selected_options` on an answer is a live M2M; the template matches selection by option id (`answers/options.html`), so version options keep the live ids.
- `QuestionAnswer.selected_options` is a live M2M to `QuestionOption`. Answers store option ids only; if a live option row were ever deleted the M2M row cascades silently, so the snapshot (JSON with ids) is also the only place the option text then lives. Nothing deletes options today.

## 6. `served_path()` and the other path builders: where the version is injected

- `served_path(form, served_paper)` rebuilds from the live tree, taking each served id from `children_by_id` (live `FormQuestion`) and `child.options.all()` (live, including retired options, so a retired option stays visible to an old sitting) and sets `has_missing_served_items` when an id vanished. With versions it would look up `served_paper["versions"][question_id]` (a prefetch of all version rows for those ids in one query), build question/option instances from the snapshot, and keep missing-item logic. Option membership/ordering now comes from the version snapshot plus `served_paper["options"]` ordering; the "fell back to live options when none served" rule becomes "fall back to the version's options". Pages and content blocks stay live (`FormContent`/`FormPage` are not versioned, so stimulus text remains current wording; flag in the spec).
- `compute_path()` (non-QUIZ and in-flight non-served): has no paper, no `versions`. In-flight non-QUIZ sittings are the case where `QuestionAnswer.question_version` is the only pin, and only for questions already answered. `compute_path` serves the LIVE question for unanswered ones, and a revision mid-sitting makes a question answered under v1 still show v1 in the answer (FK) and the next ones as v2. The spec must pick: non-QUIZ is stated as "same stored data as today" in the idea (settled bullet "Non-QUIZ forms" with the FK as the cover) or pinned at first sight. Mind `answers_by_question()` keys answers by question id and `compute_path` builds `selected` from `answer.selected_options`; an answer's selected option ids that exist in v1 but not in the live v2 snapshot are the interesting case (live row gone/changed).
- `frozen_path()` and `full_path()` (sittings with no paper: older completed ones, and non-QUIZ completed): rebuild over the live tree with no pin at all. For a completed non-QUIZ sitting `QuestionAnswer.question_version` is the pin for answered questions; unanswered questions have nothing. For a pre-served-paper quiz sitting, the migration backfill (version 1 + answers pinned) is the only thing available.
- Anything that holds a `FormQuestion` from `form.pages` (e.g. `quiz_attempt._mark`, `get_incorrect_quiz_answers`) is passed instances from the path, so path-level substitution is enough, except where code re-queries by live id (`self.answers.get(question=question)` works since the version-backed instance carries the live id).
- Equality/identity hazards when version-backed instances replace live ones: code that compares `child in live` (`_kept_children` in `conditions.py`), uses `question.pk` for gates (`_condition_holds` uses `option.question_id`), `FormQuestion.question_number()`, and Django `==` (model equality is by pk and concrete model, so a copy equals the live row, hiding the difference; sets and dict keys by id are unaffected).

## 7. Overlap with `-4-question-access` (in progress, same effort) and later specs

Spec dir: `spec_dd/2. in progress/sacaa-compliance-content-versions-and-access-4-question-access/` (`idea.md`, `research_question_access_surfaces.md`, `todo.md`; no spec yet). Overlap:
- It removes the admin pages that edit or show questions and options: `FormQuestionAdmin`, the `content_engine` `FormQuestion` admin with sections, `QuestionOptionAdmin`, the question and option inlines on the `FormPage` admin, the condition text columns on form page and form content admins, and the QUIZ answer views (`QuestionAnswerAdmin` rows and the answers document on `FormProgressAdmin` for QUIZ forms). Other writers of question/option rows: `content_save` only, plus `dev_tools/management/commands/danger_content_delete.py`, `qa_helpers/management/commands/*` (many create questions/options/answers directly with the factories or ORM, so they bypass the version hook), and tests' factories.
- It gates the cohort report quiz panel and content preview (reports and `PreviewContentAction`, reading live rows by design).
- `-5-answered-version-review` (not yet an idea dir in progress or next that I read) adds the educator view of the version answered (and an audit entry) to the attempt review; this child must expose "which version, when saved, still served" data from the path/version without building that UI (settled). ## 9. Migration and backfill notes

- New `form_engine` migration after `0018`: create the version model, add nullable `QuestionAnswer.question_version` FK (on_delete PROTECT, versions are immutable and audit evidence), data migration creating version 1 per existing `FormQuestion` from live fields + options snapshot (including retired options, because old answers may select a retired option, and each option's `retired_at`/`is_retired` if the snapshot keeps it) and setting `question_version` on every existing `QuestionAnswer`. Scale concern: `QuestionAnswer` can be large; use a single `UPDATE ... FROM` via the ORM (`Subquery`/`OuterRef` update) rather than per-row saves. Site awareness: a version needs a `site` (use `SiteAwareModel`; the data migration runs without request, so use `_base_manager`/historical models).
- Backfill the `versions` key on existing `served_paper` JSON, or make readers fall back to "latest = version 1" when the key is absent. Without the key, a completed paper in the database would read the CURRENT latest version (not version 1 once a later save made version 2); backfilling the key at migration time is the one place that locks old papers to version 1.
- "Change detection on first run" (idea open point): the version-1 row from the migration has no commit hash and no source; the first `content_save` after the migration compares live-after-save to version 1. A question whose content is already identical makes no version 2. The comparison must be field-for-field on the same canonical form the migration wrote (same JSON key order, `value` as string, option order, `correct` None/True/False). Write one `snapshot_of(question, options)` function used by both the migration (via a local copy; migrations must not import app code that can change) and `content_save`, and a content hash (or compare the JSON dicts directly; a hash column is optional).
- Questions saved but never yet versioned and created after the migration: version 1 created by `content_save` at first save (the `update_or_create` branch in `save_with_uuid`).
- A question that changes in a run but is moved to another page or form: placement not versioned (settled).
