## A. Here: what the repo already decided

### A1. Paused `content_snapshots` (`spec_dd/0. paused/content_snapshots/0. idea.md`) (a)
- Idea: a standalone app of immutable, append-only, point-in-time snapshots of whole `content_engine` objects (Course, Topic, Form with pages, FormContent, FormQuestion), with referenced `File` ids, idempotent `take_snapshot`, hash-based change detection, "never prune" default.
- It never got a spec or code (no `freedom_ls/content_snapshots/` app exists; grep hits are only specs and ideas). It was paused, not rejected; no document records a reason for pausing.
- Open questions it left that this spec must answer on its own scale: storage shape (polymorphic JSON vs per-type), which fields enter the hash (`updated_at` must not), eager vs lazy trigger, backfill eager vs lazy, derived values (`max_score`) in or out.
- Every later spec treats it as out of scope or absent: `learner-interface-features-2-test-out/idea.md` says "Nothing here may assume either exists" and lists "content version has no home today"; the served-paper spec lists "Frozen copies of question text (`content_snapshots`, paused)" as out; retire-removed-content lists `content_snapshots` under Out. This idea's Out of scope does the same.
- Constraint: do not revive or depend on `content_snapshots`. Question-level version rows are the lightweight route, consistent with the earlier research finding that no surveyed LMS needs whole-course snapshots for question audit. A stimulus (`FormContent`) rewrite is therefore not versioned (settled in idea).

### A2. Served-paper record (`spec_dd/3. done/2026-11-20_10:30_sacaa-compliance-1-served-paper-record/`) (a)
- Decided and shipped: `FormProgress.served_paper` is JSON of ids only (`seed`, `pages[{id, children}]`, `options{question_id:[option_ids]}`), written once by `ensure_served_paper()` for QUIZ sittings before the first page, or at `complete()` for a sitting that has none. `served_path()` rebuilds a `SittingPath` from live rows by id and flags `has_missing_served_items`.
- Explicitly out of that spec: frozen copies of question text. It pinned structure and order, not content, deliberately leaving the version question to this effort.
- Constraints: (1) a `versions` key must be additive to that JSON, and old papers lack it (reader must tolerate absence); (2) non-QUIZ sittings have no paper, hence the settled `QuestionAnswer` FK; (3) `served_path()` returns live model instances today, so version-backed objects must match the `SittingPath` interface (the idea's open item 4); (4) the `ServedPaper` type in `form_engine/conditions.py` needs the new key typed (no `Any`).

### A3. `stored_score_outdated` (attempt-review spec, `spec_dd/3. done/2026-11-24_17:39_sacaa-compliance-4-attempt-review/1. spec.md` ~L102-110, plan ~L258-287) (a)
- Decided: the inline check in `learner_interface/views.py` was extracted into one `form_engine` function `stored_score_outdated(form_progress, path)`; it compares stored `score`/`max_score` against `compute_quiz_scores(path)` and is skipped when `path.has_missing_served_items`. `None` path (no served paper) keeps old behaviour. The template key is unchanged. Both the learner results view and the educator attempt review call it.
- The attempt-review spec states "Question wording is the current wording" and defers freezing; this spec removes that caveat.
- Constraint and risk: once `served_path()` returns pinned versions, `compute_quiz_scores(path)` recomputes against the answered version, so `stored_score_outdated` should become false for revised questions, which is the intended fix. But a sitting completed before this migration is pinned to the migration-time version 1 (not the original wording), so its recompute can still disagree with its frozen `scores` if the question changed earlier. Decide and test: the flag stays as a warning for those, and the docs say why (the idea already says "Regrading is not built"; stored scores never change).

### A4. Retire-removed-content (done 2026-11-26) (a)
Decisions that bind this spec:
- `retired_at` lives on `BaseContent` (so `FormQuestion`) and `QuestionOption`; the filter is explicit, never in a manager: `objects`/`_base_manager` stay unfiltered. A new version model must not add a second retired state (the idea already says so).
- "Pinning is for quiz papers only": a quiz sitting finishes on its `served_paper`; a sitting without a paper (surveys, `CATEGORY_VALUE_SUM`) reads the live tree, so a question retired mid-sitting drops out of the pages still to come. This is the precedent for the idea's non-QUIZ limit; the `QuestionAnswer` FK narrows it for answers already given, not for pages still to come.
- Scoring and answer review "read the options the sitting was offered plus the non-retired options added since", so a correct option added after marking counts and the review shows "This quiz has changed since the attempt was marked". With pinned versions this rule is superseded for pinned sittings: the pinned option snapshot is the answer key. Reconcile explicitly: after this spec, the "options added since" rule should apply only to sittings with no pinned version (non-QUIZ or pre-migration). Tests from the retire spec on scoring (a retired correct option left off a paper; a live correct option added since) will need revisiting, and the retired-options handling in `build_served_paper` (`live_options`) interacts with what a version snapshot records (record all options at save time, or only live ones? Recommendation: all rows present in the source at save time, with live option ids).
- `served_path`, `frozen_path`, `full_path` stay unfiltered so a pinned or finished sitting keeps retired content: versions must preserve this (a retired question keeps versions and answers).
- `save_with_uuid` always writes `retired_at=None` in `defaults`, so un-retire and content update are one write. The version-detection code in `save_form_question` therefore runs on the same write path; an un-retire alone must not create a version (retired_at is not a versioned field per the idea).
- `content_save` is one `@transaction.atomic` per run with a post-loop sweep; version saving should sit inside the same transaction so a rolled-back run saves no versions. Output is count lines printed after commit ("Retired: ... Un-retired: ..."); add "Versions saved: n" in the same style (c).
- `save_content_to_db` has opt-in flags (`retire_missing`) so tests and `demo_content_fixtures.py` stay additive; the version hook should not need an opt-in (always on) but callers without `source_commits` must still work (commit nullable on the version row).
- Revision (`freedom_ls/revision`) reads the live question and `live_options(question)`; it is unaffected, since the live row is always the latest version.

### A5. Content-save safety (done 2026-11-22) (a)
- `ContentSave` row with one `ContentSaveSource` per path holding the full HEAD sha (`CharField max 64`), `generate_uuids` flag; created only when `source_commits` is passed to `save_content_to_db`. The check and recording belong to the command; `save_content_to_db` never shells out to git.
- Constraint: a version's "commit hash" should reference the `ContentSave` (FK, nullable) or copy the sha of the source path holding the question. With several source paths, pick the `ContentSaveSource` whose path the question's file came from, or store the `ContentSave` and let readers resolve; state it. Callers with no `source_commits` produce versions without a commit (nullable).
- Tests that need git use dulwich and `committed_content_repo` in `freedom_ls/tests/git_repos.py`; reuse for version tests that assert the recorded commit.

### A6. Earlier in-repo research on the seams (`research_question_version_seams.md`) (a)
Not repeated here. Its findings that matter most as "what was already tried": shape (a) (version rows, stable id) vs shape (b) (new `FormQuestion` rows per revision, retire old) was costed and the idea has settled on (a). Shape (b) was rejected for identity churn: `update_file_with_uuid`, `_resolve_condition`, `condition_option` RESTRICT, shuffle groups, pools and section through rows would all break.

## B. Elsewhere: outcomes of question versioning (extends the earlier file)

### B1. Moodle 4.0 migration to `question_bank_entries` / `question_versions` / `question_references` (b)
All items are search-snippet summaries of tracker issues (pages not fetchable) and need checking on the tracker before being quoted.
- Upgrade cost and failure: MDL-73808 reports an upgrade from 3.9.12 / 4.0dev failing in `upgrade_migrate_question_table()`, the step that splits quiz slot data into the new tables, and notes high memory use and slowness. https://tracker-old.moodle.org/browse/MDL-73808 . MDL-74143 (Oracle 3.9 to 4.0 upgrade blocker, fixed; advice: run from the CLI). https://tracker-old.moodle.org/browse/MDL-74143 . MDL-74859 (re-running a failed upgrade errors because `question_bank_entries` already exists; Won't Fix). https://tracker-old.moodle.org/browse/MDL-74859 . MDL-76584 (a temporary `questionid` column is added to `question_bank_entries` during upgrade). https://tracker-old.moodle.org/browse/MDL-76584
  - Lesson for FLS: the version backfill (version 1 for every existing question, pin existing answers) must be a restartable, idempotent data migration that processes in batches (`iterator()`/`bulk_create`), run in the CLI-style deploy path, and not rely on a half-created state being re-runnable. A single `RunPython` that creates N version rows and updates every `QuestionAnswer` is the analogue of the slow Moodle step; at 1 row per question plus one UPDATE per answer set, prefer a single `UPDATE ... FROM` through the ORM (e.g. `Subquery`/`F` update) over per-row loops (c).
- Statistics performance: MDL-74762 says the 4.0 question-bank statistics columns issue many queries; workaround MDL-75576 is disabling `qbank_statistics`. https://tracker-old.moodle.org/browse/MDL-74762 , https://tracker-old.moodle.org/browse/MDL-75576
  - Lesson: any list that joins "latest version per entry" (Moodle's bank list shows the latest version per entry, MDL-84433) needs the latest-version lookup indexed and not N+1. For FLS, keep `(question, number)` unique and indexed, and have `content_save` compare against the latest in one query per question (c).
- Reference logic bugs: MDL-78025 (the quiz callback checked slot-to-version matching wrongly, should match the exact version or the latest non-draft). https://tracker-old.moodle.org/browse/MDL-78025 . MDL-74255 ("Always latest" picked a draft version, so correct answers were marked wrong). https://tracker-old.moodle.org/browse/MDL-74255
  - Lesson: Moodle's "latest" pointer is the bug source. FLS has no "latest pointer" separate from the live row (live row is always the latest), so there is no equivalent drift; but the version-to-live equality must be an invariant tested at the end of every `content_save` (live row fields and option set equal latest version snapshot), and any code path that edits the live row without saving a version (hand edits, `update()` in the retire sweep, `danger_content_delete`) must be shown not to touch versioned fields. Retire sweep `.update(retired_at=...)` is safe because `retired_at` is unversioned (c).
- Regrade after edit: MDL-74752 (reproduction: change the choices of a multiple-choice question, regrade; every choice then shows "This choice was deleted after the attempt was started"; forum reports say re-applying the fix and regrading does not recover affected attempts). https://tracker-old.moodle.org/browse/MDL-74752 . MDL-75823 (duplicate-marked report that after a regrade the student's original answer is erased from the database). https://tracker-old.moodle.org/browse/MDL-75823 . Forum: regrade can only switch an attempt to another version of the same question. https://moodle.org/mod/forum/discuss.php?d=458693
  - Lesson: answers recorded against option ids break when option identity is not stable across versions. Settled in the idea (live option ids carried in the snapshot; `QuestionAnswer.selected_options` still match; regrade not built). The required test: a revision that changes option text keeps option ids, and one that removes an option leaves the answer's selected option resolvable from the pinned snapshot (the live row may be retired but never deleted). Also: an answer must never be erased by a versioning operation (the Moodle MDL-75823 failure mode).
- Backup/restore: restoring a backup containing random questions between 3.3.4+ and 4.0.4+ errors. https://moodle.org/mod/forum/discuss.php?d=439615
  - Lesson: FLS has no backup/restore of content, but any fixture/dump path that loads questions without versions (e.g. `demo_content_fixtures.py`, tests using factories) must still produce a version, or the pinned reader must have a defined behaviour for a question with no version (c). The idea settles first-run: a question without a version gets version 1 on first `content_save` after migration.
- Bank duplication on import: version-creating imports are a plugin, not core, so stock import makes duplicate entries. https://moodle.org/plugins/qbank_importasversion . FLS is immune because the authored uuid is the sync key.
- Forum: "M401 - Update question after quiz probs" and "Problem with version question" show teachers surprised that an edit does not reach attempts in progress. https://moodle.org/mod/forum/discuss.php?d=434465 , https://moodle.org/mod/forum/discuss.php?d=438090 . Lesson: state the in-progress behaviour in the learner/educator docs; it is the commonest support question after rollout.
- Moodle feature request MDL-80006 asks for a "minor edit" that updates in-progress attempts without a new version. https://tracker-old.moodle.org/browse/MDL-80006 . The idea already rejects the carve-out; the audit argument stands.

### B2. Canvas New Quizzes (extends the earlier file) (b)
- Behaviour reported by institutions: once students have submitted, editing a bank item makes a copy (separate statistics); the original stays visible only in quizzes already taken. Sources already cited in the earlier file (kb.wisc.edu, Flinders). Additional point: Canvas "fork on use" gives per-version statistics for free, whereas FLS reports will mix versions (reports are out of scope per answers.md). That limitation has to be written into the report docs, since Canvas's separate-statistics behaviour is the thing an auditor would compare against.
- Known pain in Canvas threads: edits to a shared bank item silently propagating to other quizzes; unclear which of two behaviours applies. https://community.canvaslms.com/t5/Canvas-Ideas/New-Quizzes-allow-changes-to-item-banks/idi-p/573615 . FLS avoids this because pinning is per attempt, not per quiz.

### B3. Audit-led versioning in regulated e-learning (b, vendor material; no regulator text found)
- Vendors in regulated testing describe the same triplet: item version history with who/when, retire rather than delete, and a per-candidate record of the exact item version delivered. Questionmark: https://www.questionmark.com/platform/flexible-authoring/ . Practique (ExamRoom/RISR docs, via a search summary): retired items are archived and cannot be changed afterwards (a new version can be made), and items used in submitted exams cannot be deleted, to preserve the audit trail. https://risr-global.atlassian.net/wiki/x/XgD8Ag . Speedwell: complete history, who and when. https://e-assessment.com/news/sponsor/why-assessment-quality-starts-with-better-question-management . Exam Studio versioning: https://examstudio.com/capabilities/versioning-system/ . Compliance-training vendor framing (draft/review/approved/retired, evidence of which version each person took; vendor claim, not regulation): https://intercom.help/skill-studio-ai/en/articles/15162045-compliance-training-software-with-audit-ready-records-and-version-control-the-r
- Aviation and medical regulators: nothing found stating that an exam must be reproducible from a versioned bank (the earlier file already found EASA/FAA/UK CAA texts say the bank must be secured and reviewed, not versioned). The only regulator-adjacent wording remains the SACAA sentence in the idea and the SA-CATS 141.07.1 e-learning matrix (not readable). So "reproduce what the learner was asked" is an auditor expectation inferred from the SACAA sentence, not an external standard FLS can cite beyond that; do not claim wider compliance in docs (c).
- Differences from FLS: vendors record the item version at delivery in the result record (pin at start), which is what the idea does; none of the vendor sources describe recording the source commit. Commit hash on the version row is FLS's own addition.

## C. Constraints and recommendations for this spec

1. Version rows under a stable `FormQuestion` uuid: confirmed by Moodle (and by the in-repo shape (b) rejection). Do not add a "latest" pointer separate from the live row; assert live == latest at the end of each save (Moodle MDL-74255/78025 bug class).
2. Option ids must be stable in the snapshot and an answer's selected options must resolve from the snapshot even if the live option is retired (Moodle MDL-74752/75823 bug class). No versioning step may delete or rewrite an answer.
3. Backfill migration: idempotent, batched, bulk SQL via ORM; state "version 1 = content at migration time"; do not double-count on first `content_save` (idea item 6). Moodle upgrade failures (MDL-73808, 74859) show a non-restartable split step is the main upgrade risk.
4. Interaction with retire spec: reconcile its "options added since" scoring rule and its tests with pinned versions (A4); do not add a second retired state; version and un-retire share one write path; run inside the same transaction; add a count line to the command output in the same style.
5. `stored_score_outdated` stays as the single function; with a pinned path it should go quiet for revised-after-start questions and still warn for pre-migration sittings (A3).
6. Served paper: add `versions` additively; typed; old papers without it must read as "unpinned" (fall back to the answer FK, then the live row).
7. Docs to write plainly: in-progress attempts finish on pinned versions (Moodle's most common support question); aggregate reports mix versions (Canvas separates them); migration version 1 is not the original wording.
8. Do not revive `content_snapshots`; do not add a "minor edit" carve-out (Moodle MDL-80006 shows the demand and the audit reason against it).
