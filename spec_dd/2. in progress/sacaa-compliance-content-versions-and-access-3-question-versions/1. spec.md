# Spec: immutable question versions, pinned per sitting

Idea: `idea.md` in this directory. Answers recorded before writing: `answers.md`.

## Purpose

`content_save` overwrites `FormQuestion` and `QuestionOption` rows in place. A finished sitting then
shows and re-scores today's wording and today's correct answers against yesterday's answer, which
fails SACAA's rule that a revised question "should remain in the system for audit purposes". After
this spec, every change to a question saves an immutable `FormQuestionVersion`, each sitting pins the
versions it was served, and every reader of a past sitting reads the pinned version.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `FormQuestionVersion` | coined | One immutable saved state of a `FormQuestion`: its versioned fields and its option set. No existing model holds question history. |
| versioned fields | coined | `FormQuestion.question`, `type`, `required`, `min`, `max`, `decimal_places`, `explanation`, and the option set: every option's id, `text`, `value`, `order` and `correct`. |
| pinned version | coined | The `FormQuestionVersion` a sitting is held to for one question: the served paper's `versions` entry for a quiz sitting, `QuestionAnswer.question_version` for an answer. |
| version-backed question | coined | An unsaved `FormQuestion` instance (and its unsaved `QuestionOption` instances) carrying the live ids and the pinned version's field values. |

## Scope

In:
- The `FormQuestionVersion` model, its immutability guards and database trigger.
- Saving versions in `content_save`, with the commit hash, and the command's version output.
- Pinning: a `versions` key in the QUIZ served paper and a nullable `QuestionAnswer.question_version`.
- Readers of a sitting reading the pinned version: the learner quiz page, scoring, the results page
  and its incorrect-answers list, the stored-score check, the educator attempt review, the
  course-application export and API, the application "check your answers" page, and the survey and
  application answer views left in the admin.
- The migration that backfills version 1 and pins existing answers and papers.

Out:
- Reports in `freedom_ls/reports/`: they keep aggregating on the live row (`answers.md`).
- The educator view of which version was answered, when it changed and whether it is still served:
  `sacaa-compliance-content-versions-and-access-5-answered-version-review`.
- Removing the admin question pages and QUIZ answer views:
  `sacaa-compliance-content-versions-and-access-4-question-access`.
- Regrading, and any change to stored `FormProgress.scores`.
- Versioning `FormContent`, `FormPage`, topics or courses; `content_snapshots`.
- Revision questions (`freedom_ls/revision/`, the revision cards in `learner_interface/views.py`)
  and the educator content preview: they show the live question, which is always the latest version.

## Decisions

- **Versions are a new model under a stable `FormQuestion`.** The authored uuid stays the identity
  and the sync key; `QuestionAnswer`, `condition_option`, keep-together groups, pools and section
  links keep pointing at the live row.
- **Versioned fields are explicit columns plus an `options` JSON list.** The JSON holds the live
  option ids, so `QuestionAnswer.selected_options` (a live M2M) still matches a version's options.
- **`explanation` is versioned** (`answers.md`). `slug`, `group`, `category`, `tags`, `meta`,
  `file_path`, `order`, `form_page`, `condition_option`, `retired_at`, `dropped_from_source_at`,
  `QuestionOption.locked` and option `retired_at` are not.
- **Comparison is exact and on stored values.** `save_with_uuid` does not translate
  `FormQuestion.question` (it only translates a `content` field), so stored and authored text are the
  same; the comparison still reads the saved rows. No minor-edit carve-out: a typo fix is a version.
  A revert to earlier wording is a new version, never a reuse of an old one.
- **The option set is the options in the source file**, the `saved_options` that
  `save_form_question` returns. An option dropped from the file leaves the next version's set.
  Retiring or un-retiring a question alone makes no version.
- **The commit is a copied sha, not a foreign key.** `form_engine` must not import `content_engine`,
  so the version stores the `ContentSaveSource.commit` of the source path the question's file came
  from. A save with no `source_commits` (tests, demo fixtures) stores a blank commit. A
  `--generate-uuids` run records its commit too: that commit lacks only the uuids written back, not
  any versioned field.
- **Immutability is enforced twice** (`answers.md`): in Django (`save()` on an existing row,
  `delete()`, and the queryset's `update()`, `delete()` and `bulk_update()` raise) and in PostgreSQL
  (a `BEFORE UPDATE OR DELETE ... FOR EACH ROW` trigger raises). There is no `TRUNCATE` trigger,
  because Django's test flush for `transaction=True` tests truncates every table.
- **Pin in both places** (`answers.md`). The served paper pins every question a quiz sitting is
  served; the answer FK records the version the learner answered, which also covers survey and
  application sittings, which have no paper. For a quiz sitting the two always agree.
- **Version-backed questions are unsaved model instances, not a new class.** `isinstance(child,
  FormQuestion)` checks, templates (`rendered_question()`, `rendered_explanation()`, `option.text`,
  `option.correct`) and `is_quiz_answer_correct()` work unchanged. Calling `save()` or `delete()` on
  one raises.
- **The pinned version is the answer key.** For a pinned question, marking reads only the version's
  options. The rule from `sacaa-compliance-4-attempt-review` and the retire spec, "served options
  plus live options added since", now applies only to a question with no pin.
- **Hand edits in the admin are not guarded.** `-4-question-access` removes those pages. Until it
  lands, a hand edit changes the live row without a version; pinned readers do not see it, and the
  next `content_save` restores the file's state and versions it if it differs from the latest.

## Requirements

### Model: `form_engine/models.py`

`FormQuestionVersion(SiteAwareModel)`:
- `id` UUID primary key; `question` FK to `FormQuestion`, `on_delete=PROTECT`,
  `related_name="versions"`; `number` positive integer, unique with `question`, starting at 1.
- `question_text`, `type`, `required`, `min`, `max`, `decimal_places`, `explanation`, with the same
  field types and choices as on `FormQuestion`.
- `options`: JSON list of `{"id", "text", "value", "order", "correct"}` ordered by `order` then
  `id`, `id` as a string, `value` as a string, `correct` as `true`, `false` or `null`. Validated
  through a pydantic model on write and read.
- `saved_at` (set once at creation), `source_commit` (`CharField(max_length=64, blank=True)`),
  `from_migration` (boolean, true only on rows the backfill wrote).
- No `updated_at`. Immutability guards as in Decisions, with a custom manager and queryset.
- Methods: `as_question(live: FormQuestion) -> FormQuestion` and its options, which build the
  version-backed question from the live row (for `form_page`, `condition_option`, `group`, `slug`,
  `order`, `category`, `retired_at`) with the versioned field values overlaid; and
  `differs_from(question, options) -> list[str]`, returning the names of the versioned fields that
  differ (`question`, `type`, `required`, `min`, `max`, `decimal_places`, `explanation`, `options`).
- One creating function, `save_question_version(question, options, source_commit) ->
  tuple[FormQuestionVersion | None, list[str]]`. It locks the `FormQuestion` row with
  `select_for_update()`, compares with the latest version, and creates `number = latest + 1` only
  when something differs. It returns the new row (or `None`) and the changed fields.

`QuestionAnswer.question_version`: nullable FK to `FormQuestionVersion`, `on_delete=PROTECT`.

`FormQuestion` and `QuestionOption` instances built by `as_question` carry a marker that makes
`save()` and `delete()` raise.

### Saving: `content_engine/management/commands/content_save.py`

- `_write_source` receives the `SourceCommit` for its path (or `None`) and passes the sha to
  `save_form_question`, which calls `save_question_version(question, saved_options, sha)` after the
  options are saved. The run stays one transaction: a rolled-back run saves no version.
- A question with no version yet gets version 1 on its first save.
- The run ledger counts new, revised and unchanged questions. After commit, alongside the existing
  retire lines, the command prints:

  ```
  Question versions: 2 new, 3 revised, 120 unchanged
    forms/safety/q04.md (fuel-reserve): v2 → v3 (question, options)
  ```

  One indented line per revised question: file path, slug in brackets when it has one, old → new
  number, changed fields.
- `dev_tools/management/commands/danger_content_delete.py` disables the trigger on the version table
  for its own transaction only, deletes versions before questions, and re-enables it.

### Pinning: `form_engine/served_paper.py`, `form_engine/conditions.py`

- `ServedPaper` gains `versions: NotRequired[dict[str, str]]`: question id → version id, an entry
  for every served question, including those with no options.
- `build_served_paper()` fills it in the loop that fills `options`, loading the latest version of
  every served question in one query. A question with no version (built outside `content_save`) has
  no entry.
- A paper written by `ensure_served_paper()` at `complete()` pins the versions current at
  completion. The docs say so.

### Reading: `form_engine/conditions.py`

- `served_path()` loads every version in `served_paper["versions"]` in one query and puts the
  version-backed question in place of the live one. Options come from the version, ordered by
  `served_paper["options"]`. A served option id missing from the version (only possible on a
  migration-written version 1 whose option was already retired) reads the live option row.
- A question with no `versions` entry, or a paper with no `versions` key, reads the live row and
  sets no flag.
- `options_added_since()` returns nothing for a pinned question.
- `compute_path()`, `frozen_path()` and `full_path()` substitute the version-backed question for
  every question that has an answer with a `question_version`, using the answers they already load,
  so an answered question in a survey or application sitting shows the version answered. An
  unanswered question in a sitting with no paper shows the live row.

### Saving answers: `form_engine/models.py`, `form_engine/views.py`

- `FormProgress.save_answers()` sets `question_version` on every answer it writes: the pinned version
  for a version-backed question, otherwise the question's latest version (`None` when it has none).
  Re-saving an answer in a sitting with no paper moves the FK to the version current at that save.
- `partial_question_file_upload` sets it the same way.
- The `qa_helpers` scenario commands that create answers directly
  (`qa_create_quiz_declaration_scenario.py`, `qa_set_item_completion.py`) go through the same path.

### Scoring and results: `form_engine/models.py`, `form_engine/queries.py`, `learner_interface/views.py`

- `marking_options()`, `compute_quiz_scores()`, `score_quiz()` and `get_incorrect_quiz_answers()`
  read the questions and options the path hands them, so a pinned sitting is marked on its pinned
  versions. `stored_score_outdated()` is unchanged; a sitting answered before versions existed can
  still show the notice, because its version 1 is the content at migration time.
- The results page and its incorrect-answers list render the version-backed questions, unmarked.

### Educator attempt review: `educator_interface/panels/learner/quiz_attempt.py`

- Reads the pinned versions through `sitting_path()`.
- Remove the line "Question and option wording is the quiz's current wording." from
  `educator_interface/templates/educator_interface/panels/quiz_attempt_paper.html`, and the matching
  wording in `form_engine/queries.py`.

### Course applications: `course_applications/resources.py`, `course_applications/api.py`, `course_applications/views.py`

- The export keeps one column per question, headed with the live wording, and adds a column after
  each headed `<question> (version)` holding the answer's version `number`, blank when the answer
  has none (`answers.md`). Each answer cell is read through `answer.question_version`.
- `form_engine/exports.py` `answer_value()` and `answer_cell()` take the version-backed question and
  options for the answer. Selected option text comes from the version, ordered by its `order`.
- The API's `question_text` is the answered version's text.
- `check_your_answers.html` shows answered rows from the answer's version, unanswered rows from the
  live row.

### Admin answer views: `form_engine/queries.py`, `form_engine/admin.py`

- `answer_groups()`, `_answer_row()` and `_answers.html` read each answered row through its
  `question_version`. `QuestionAnswerAdmin.answer_preview` and `QuestionAnswerFileAdmin.question`
  read the answer's version text.

### Migrations: `form_engine/migrations/`

Three migrations after `0018`, in this order:
1. Create `FormQuestionVersion` and `QuestionAnswer.question_version`.
2. Data migration, batched (`iterator(chunk_size=...)`, `bulk_create(batch_size=...)`): for every
   `FormQuestion`, retired or not, version 1 from its current fields and its non-retired options,
   `from_migration=True`, `source_commit=""`; set every `QuestionAnswer.question_version` to its
   question's version 1 with one ORM `Subquery` update; add a `versions` key pointing at version 1
   to every non-null `FormProgress.served_paper`. The option snapshot is built by a copy of the
   shape inside the migration. Its docstring states that version 1 is the content when the migration
   ran, not necessarily the wording the learner saw. Re-running it creates nothing twice.
3. `RunSQL` installing the trigger, with reverse SQL dropping it.

`FormProgress.scores` and `asked` are not touched.

## Testing

- **Model:** `save()` of an existing version, `delete()`, and queryset `update()`/`delete()`/
  `bulk_update()` raise; raw SQL `UPDATE` and `DELETE` on the table raise at the database
  (`transaction=True`); `number` is unique per question; `save()` and `delete()` on a version-backed
  question or option raise.
- **Change detection:** each versioned field changed alone makes a version and is named in the
  changed fields; an added option, a removed option, a reordered option and a changed `correct` each
  make one; changing `slug`, `tags`, `meta`, `file_path`, `group`, `order`, page, `locked`, or
  retiring and un-retiring makes none; a second run on unchanged content makes none; a revert makes
  a new number.
- **`content_save`:** a run with a committed repo (`freedom_ls/tests/git_repos.py`
  `committed_content_repo`) stores the source path's sha; a direct `save_content_to_db` call stores
  a blank one; a failed run leaves no version; the summary and revised lines print as specified;
  `danger_content_delete` still empties content.
- **Pinning:** `build_served_paper()` writes a `versions` entry for every served question, including
  one with no options, under shuffle, keep-together groups and a draw; a question revised mid-sitting
  renders, validates and scores on the pinned version on the next page load; a sitting started after
  the revision gets the new version; `save_answers()` sets the FK to the pinned version.
- **Readers:** for a sitting answered on version 1 and a question since revised to version 2, the
  results page, incorrect-answers list, educator attempt review, admin answer view, application
  export (cell and version column), API and check-your-answers page show version 1's wording and
  version 1's correct answers; the stored score is unchanged; papers without `versions` and questions
  without versions read the live row. Query counts for the results page, export and admin answer view
  do not grow with the number of questions.
- **Survey sitting:** an answer saved on version 1 keeps version 1 after a revision; re-saving it
  after the revision moves it to version 2.
- **Migration:** a test in `form_engine/tests/migrations/` that the backfill makes one version 1
  per question (retired included), pins every answer and every paper, and that a `content_save` of
  unchanged content right after it makes no version 2.

## Documentation and downstream

- `docs/product/content-editing-workflow.md`: every change to a question's versioned fields makes a
  version, typo fixes included; the `content_save` version output; a fix reaches only sittings that
  start after it, and stored scores never change.
- `docs/product/learner-tracking.md`: sittings pin versions at start (a quiz paper written at
  completion pins at completion); answers record their version; version 1 of every question that
  existed before this release is the content at migration time, not the original wording; reports
  still aggregate on the live question, so a revised question mixes versions in one report row;
  `FormContent` and `FormPage` are not versioned, so a rewritten stimulus has no history.
- `docs/product/admin-interface.md`: admin answer views show the answered version.
- `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md`: add `FormQuestionVersion` and pinned
  version.
- `claude_plugins/fls-content` skills that describe editing questions: an edit makes a new version
  for learners who start afterwards.
- Upgrade notes: three new `form_engine` migrations, the backfill's run time on large
  `QuestionAnswer` tables, and the database trigger, which needs the migrating role to own the
  table.

## Success criteria

- Changing a question's text and running `content_save` creates version 2 with the commit sha and
  prints one revised line; running it again prints `0 revised`.
- A learner who started a quiz before the change sees, is marked on, and on the results page reads
  version 1; a learner who starts after sees version 2.
- `UPDATE` and `DELETE` on the version table fail in Django and in `psql`.
- The application export shows the answered wording's answer and a version number beside each
  question column.
- After the migration, every existing question has exactly one version, marked `from_migration`,
  and every existing answer and served paper points at it.
- The test suite passes.
