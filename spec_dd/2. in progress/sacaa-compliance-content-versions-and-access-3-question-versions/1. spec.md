# Spec: immutable question versions, pinned per sitting

Idea: `idea.md` in this directory. Answers recorded before and during writing: `answers.md`.

## Purpose

`content_save` overwrites `FormQuestion` and `QuestionOption` rows in place. A finished sitting then
shows and re-scores today's wording and today's correct answers against yesterday's answer, which
fails SACAA's rule that a revised question "should remain in the system for audit purposes". After
this spec, every change to a question saves an immutable `FormQuestionVersion`, each sitting pins the
versions it was served, and every reader of a past sitting reads the pinned version.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `FormQuestionVersion` | coined | One immutable saved state of a `FormQuestion`: its versioned fields and its option set. No existing model holds question history. |
| versioned fields | coined | `FormQuestion.question`, `type`, `required`, `min`, `max`, `decimal_places`, `explanation`, and the option set: every option's id, `text`, `value`, `order` and `correct`. |
| pinned version | coined | The `FormQuestionVersion` a sitting is held to for one question: the served paper's `versions` entry for a quiz sitting, `QuestionAnswer.question_version` for an answer. |
| version-backed question | coined | An unsaved `FormQuestion` instance, and its unsaved `QuestionOption` instances, carrying the live ids and the pinned version's field values. |

## Scope

In:
- The `FormQuestionVersion` model, its immutability guards and database trigger.
- Saving versions in `content_save`, with the commit hash, and the command's version output.
- Pinning: a `versions` key in the QUIZ served paper and a nullable `QuestionAnswer.question_version`.
- Readers of a sitting reading the pinned version: the learner quiz page, scoring, the results page
  and its incorrect-answers list, the stored-score check, the educator attempt review, the
  course-application export and API, the application "check your answers" page, and the survey and
  application answer views left in the admin.
- The migrations that backfill version 1 and pin existing answers and papers.

Out:
- Reports in `freedom_ls/reports/`: they keep aggregating on the live row (`answers.md`).
- The educator view of which version was answered, when it changed and whether it is still served:
  `sacaa-compliance-content-versions-and-access-5-answered-version-review`.
- Removing the admin question pages and QUIZ answer views:
  `sacaa-compliance-content-versions-and-access-4-question-access`. Until it lands, a hand edit in
  the admin changes the live row without a version; pinned readers do not see it, and the next
  `content_save` versions the file's state if it differs from the latest version.
- Regrading, and any change to stored `FormProgress.scores`.
- Versioning `FormContent`, `FormPage`, topics or courses; `content_snapshots`.
- Revision questions (`freedom_ls/revision/`, the revision cards in `learner_interface/views.py`)
  and the educator content preview: they show the live question, which is always the latest version.

## Decisions

- **Versions are a new model under a stable `FormQuestion`.** The authored uuid stays the identity
  and the sync key; `QuestionAnswer`, `condition_option`, keep-together groups, pools and section
  links keep pointing at the live row.
- **`explanation` is versioned** (`answers.md`). `slug`, `group`, `category`, `tags`, `meta`,
  `file_path`, `order`, `form_page`, `condition_option`, `retired_at`, `dropped_from_source_at`,
  `QuestionOption.locked` and option `retired_at` are not.
- **Comparison is exact, on the saved rows.** A typo fix or a revert to earlier wording is a new
  version.
- **The option set is the options in the source file**, the `saved_options` that
  `save_form_question` returns. An option dropped from the file leaves the next version's set.
  Retiring or un-retiring a question alone makes no version.
- **The commit is a copied sha, not a foreign key**, because `form_engine` must not import
  `content_engine`. A `--generate-uuids` run records its commit too: that commit lacks only the
  uuids written back, not any versioned field.
- **No `TRUNCATE` trigger** (`answers.md`): the test flush for `transaction=True` tests truncates
  every table.
- **Not a new class:** `isinstance(child, FormQuestion)` checks, templates and
  `is_quiz_answer_correct()` keep working on version-backed questions.
- **The pinned version is the answer key.** "Served options plus live options added since", from
  `sacaa-compliance-4-attempt-review` and the retire spec, applies only to a question with no pin.
- **Only the quiz runner renders pinned versions.** A survey or application sitting has no paper,
  so its runner shows the live question and an answer re-saved after a revision pins the new
  version. Read-only readers of an answer show the version it records.
- **Version 1 from the migration holds the options `content_save` would save next**: the
  non-retired options of a live question, every option of a retired one (retiring a question
  retires its options, and un-retiring restores them). The first `content_save` after the migration
  then makes no version for unchanged content. A selected option missing from an answer's version
  reads the live option row, which is never deleted.

## Requirements

### Model: `form_engine/models.py`

`FormQuestionVersion(SiteAwareModel)`:
- `id` UUID primary key; `question` FK to `FormQuestion`, `on_delete=PROTECT`,
  `related_name="versions"`; `number` positive integer, unique with `question`, starting at 1.
- `question_text` (holds `FormQuestion.question`; the name `question` is taken by the FK), `type`,
  `required`, `min`, `max`, `decimal_places`, `explanation`, with the same field types and choices
  as on `FormQuestion`. Changed-field lists use the `FormQuestion` names.
- `options`: JSON list of `{"id", "text", "value", "order", "correct"}` ordered by `order` then
  `id`, `id` and `value` as strings, `correct` as `true`, `false` or `null`. Validated through a
  pydantic model, `QuestionVersionOption`, on write and read.
- `saved_at` (set once at creation), `source_commit` (`CharField(max_length=64, blank=True)`),
  `from_migration` (boolean, true only on rows the backfill wrote). No `updated_at`.
- Immutability in Django: `save()` on an existing row and `delete()` raise; the queryset's
  `update()`, `delete()` and `bulk_update()` raise. The default manager is built with
  `SiteAwareManager.from_queryset(...)`. `Meta.base_manager_name` names a second guarded manager that
  does not filter by site, because the base manager serves related lookups such as
  `answer.question_version`. The database trigger is the backstop for any other path, the delete
  collector's cascade included.
- `as_question(live: FormQuestion) -> FormQuestion` builds the version-backed question: the live
  row's `form_page`, `condition_option`, `group`, `slug`, `order`, `category` and `retired_at`, with
  the versioned field values overlaid, `pinned_version` set to the version, and the `options`
  prefetch cache filled with the version's unsaved `QuestionOption` instances so
  `question.options.all()` returns them; each option carries `pinned_version` too. `save()` and
  `delete()` on these instances raise. `pinned_version` is `None` on every row loaded from the
  database.
- `differs_from(question, options) -> list[str]` returns the names of the versioned fields that
  differ (`question`, `type`, `required`, `min`, `max`, `decimal_places`, `explanation`, `options`).
- `save_question_version(question, options, source_commit) -> tuple[FormQuestionVersion | None,
  list[str]]` is the one creating function. It opens its own `transaction.atomic()`, locks the
  `FormQuestion` row with `select_for_update()`, compares with the latest version, and creates
  `number = latest + 1` only when something differs.
- `delete_question_versions(questions)` is the one deleting path, for development commands only.
  Callers delete the answers pinned to those versions first. In one transaction it disables the
  trigger, deletes the versions with a raw `DELETE` through the cursor (the queryset guard refuses
  an ORM delete), runs `SET CONSTRAINTS ALL IMMEDIATE`, and re-enables the trigger.

`QuestionAnswer.question_version`: nullable FK to `FormQuestionVersion`, `on_delete=PROTECT`. A null
value reads the live row.

`answered_questions(answers) -> dict[UUID, FormQuestion]` loads the versions of the given answers in
one query and returns the version-backed question per question id, or the live question for an
answer with no version. The answers passed are one sitting's, so each question id has one answer;
an answer whose `question_version` is already loaded costs no query. Read-only readers use it.

`answered_options(answer, question) -> list[QuestionOption]` returns the answer's selected options
as `question` holds them, ordered by `order`: the version's option for each selected id, the live
row for one the version lacks.

### Saving: `content_engine/management/commands/content_save.py`

- `_write_source` receives the `SourceCommit` for its path (or `None`) and passes the sha to
  `save_form_question`, which calls `save_question_version(question, saved_options, sha)` after the
  options are saved. A save with no `source_commits` stores a blank commit. A rolled-back run saves
  no version.
- A question with no version yet gets version 1 on its first save.
- The run ledger counts new, revised and unchanged questions. After commit, alongside the retire
  lines, the command prints:

  ```
  Question versions: 2 new, 3 revised, 120 unchanged
    forms/safety/q04.md (fuel-reserve): v2 → v3 (question, options)
  ```

  One indented line per revised question: file path, slug in brackets when it has one, old → new
  number, changed fields.
  A run that saves no questions prints no `Question versions:` line.
- `dev_tools/management/commands/danger_content_delete.py` and the `qa_helpers` commands that
  delete loaded forms (`qa_create_course_content_preview.py`,
  `qa_create_course_structure_variants.py`) call `delete_question_versions()` first.

### Pinning: `form_engine/served_paper.py`, `form_engine/conditions.py`

- `ServedPaper` gains `versions: NotRequired[dict[str, str]]`: question id → version id, an entry
  for every served question, including those with no options.
- `build_served_paper()` fills it in the loop that fills `options`, loading the latest version of
  every served question in one query. A question with no version (built outside `content_save`) has
  no entry.

### Reading the quiz runner and results: `form_engine/conditions.py`, `form_engine/models.py`, `form_engine/templatetags/form_engine_tags.py`

- `served_path()` loads every version in `served_paper["versions"]` in one query and puts the
  version-backed question in place of the live one. Options come from the version, ordered by
  `served_paper["options"]`; a served option id missing from the version reads the live option row.
  A question with no `versions` entry, or a paper with no `versions` key, reads the live row and sets
  no flag.
- `marking_options()`, `SittingPath.options_added_since()` and the `question_options` tag branch on
  `pinned_version`: a pinned question uses only the version's options and has nothing added since.
- `compute_quiz_scores()`, `score_quiz()` and `get_incorrect_quiz_answers()` read what the path
  hands them, so a pinned sitting is marked on its pinned versions. `stored_score_outdated()` is
  unchanged; a sitting answered before versions existed can still show the notice, because its
  version 1 is the content at migration time.
- `compute_path()`, `frozen_path()` and `full_path()` are unchanged.

### Saving answers: `form_engine/models.py`, `form_engine/views.py`, `qa_helpers`

- `FormProgress.save_answers()` sets `question_version` on every answer it writes: the
  `pinned_version` of a version-backed question, otherwise the question's latest version (`None`
  when it has none). One helper, `latest_versions(question_ids)`, loads the latest versions of all the
  questions in one query; the file-upload view and the `qa_helpers` helper use it too.
- `partial_question_file_upload` sets it the same way.
- The `qa_helpers` commands that create answers directly (`qa_create_dashboard_paging_fixtures.py`,
  `qa_create_rich_dashboard_learner.py`, `qa_create_report_cohort.py`) set it through one shared
  helper. `qa_create_quiz_declaration_scenario.py` and `qa_set_item_completion.py` write through
  `save_answers()` and are covered by it.

### Educator attempt review: `educator_interface/panels/learner/quiz_attempt.py`

- Reads the pinned versions through `sitting_path()`.
- Remove "Question and option wording is the quiz's current wording." from
  `educator_interface/templates/educator_interface/panels/quiz_attempt_paper.html`, and the matching
  wording in `form_engine/queries.py`.

### Course applications: `course_applications/resources.py`, `course_applications/api.py`, `course_applications/views.py`

- The export keeps one column per question, headed with the live wording, and adds a column after
  each headed `<question> (version)` holding the answer's version `number`, blank when the answer
  has none (`answers.md`).
- `form_engine/exports.py` `answer_value()` and `answer_cell()` take the question from
  `answered_questions()`. Selected option text comes from the version, ordered by its `order`.
- The API's `question_text` is the answered version's text.
- `check_your_answers.html` shows answered rows from `answered_questions()`, unanswered rows from the
  sitting's path: the live row, or, on a quiz-scored form whose served paper pins every question,
  the pinned version, so the row reads as the page its Edit link opens.

### Admin answer views: `form_engine/queries.py`, `form_engine/admin.py`

- `answer_groups()`, `_answer_row()` and `_answers.html` read each answered row through
  `answered_questions()`. `QuestionAnswerAdmin.answer_preview` and `QuestionAnswerFileAdmin.question`
  read the answer's version text.

### Migrations: `form_engine/migrations/`

Three migrations after `0018`, in this order, because the backfill must run before the trigger
exists:
1. Create `FormQuestionVersion` and `QuestionAnswer.question_version`.
2. Data migration. For every `FormQuestion`, retired or not: version 1 from its current fields and
   options, `from_migration=True`, `source_commit=""`, `site` set from the question.
   Every `QuestionAnswer.question_version` set to its question's version 1. A `versions` key added to
   every non-null `FormProgress.served_paper`, skipping question ids with no version. The option
   shape is copied into the migration, not imported. The docstring states that version 1 is the
   content when the migration ran, not necessarily the wording the learner saw. Re-running creates
   nothing twice. The reverse strips the `versions` keys, clears the FK and deletes the
   `from_migration` versions.
3. `RunSQL` installing a `BEFORE UPDATE OR DELETE ... FOR EACH ROW` trigger that raises, with
   reverse SQL dropping it.

`FormProgress.scores` and `asked` are not touched.

## Testing

- **Model:** the Django guards raise, including through the base manager; raw SQL `UPDATE` and
  `DELETE` on the table raise at the database (`transaction=True`); `number` is unique per question;
  `save()` and `delete()` on a version-backed question or option raise; `.options.all()` on a
  version-backed question returns the version's options; `delete_question_versions()` empties the
  table and leaves the trigger enabled.
- **Change detection:** each versioned field changed alone makes a version and is named in the
  changed fields; an added, removed or reordered option and a changed `correct` each make one;
  changing `slug`, `tags`, `meta`, `file_path`, `group`, `order`, page or `locked`, or retiring and
  un-retiring, makes none; a second run on unchanged content makes none; a revert makes a new number.
- **`content_save`:** a run with a committed repo (`freedom_ls/tests/git_repos.py`
  `committed_content_repo`) stores the source path's sha; a direct `save_content_to_db` call stores
  a blank one; a failed run leaves no version; the summary and revised lines print as specified;
  `danger_content_delete` still empties content.
- **Pinning:** `build_served_paper()` writes a `versions` entry for every served question, including
  one with no options, under shuffle, keep-together groups and a draw; a question revised mid-sitting
  renders, validates and scores on the pinned version on the next page load; a sitting started after
  the revision gets the new version; `save_answers()` sets the FK to the pinned version.
- **Readers:** for a sitting answered on version 1 and a question since revised to version 2, the
  results page, incorrect-answers list, educator attempt review, admin answer view, application
  export (cell and version column), API and check-your-answers page show version 1's wording and
  correct answers; the stored score is unchanged; papers without `versions`, answers with no
  version, and a selected option missing from the version read the live row. Query counts for the
  results page, export and admin answer view do not grow with the number of questions.
- **Survey sitting:** the runner shows version 2 after a revision; an answer saved on version 1
  shows version 1 in the admin answer view until it is re-saved, then version 2.
- **Migration:** a test in `form_engine/tests/migrations/` that the backfill makes one version 1 per
  question (retired included), pins every answer and every paper, reverses cleanly, and that a
  `content_save` of unchanged content right after it makes no version 2.
- Existing tests that delete forms or questions after loading content through `save_content_to_db`
  now hit `PROTECT`; the plan lists them and they call `delete_question_versions()`.

## Documentation and downstream

- `docs/product/content-editing-workflow.md`: every change to a question's versioned fields makes a
  version, typo fixes included; the `content_save` version output; a fix reaches only sittings that
  start after it, and stored scores never change.
- `docs/product/learner-tracking.md`: sittings pin versions at start (a quiz paper written at
  completion, for a sitting begun before served papers existed, pins at completion); answers record
  their version; version 1 of every question that existed before this release is the content at
  migration time, not the original wording; `FormContent` and `FormPage` are not versioned, so a
  rewritten stimulus has no history.
- `docs/product/reports.md` and `docs/product/learner-tracking.md`: reports aggregate on the live
  question, so a revised question mixes versions in one report row (`answers.md`).
- `docs/product/admin-interface.md`: admin answer views show the answered version.
- `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md`: add `FormQuestionVersion` and pinned
  version.
- `claude_plugins/fls-content` skills that describe editing questions: an edit makes a new version
  for learners who start afterwards.
- Upgrade notes: the backfill's run time on large `QuestionAnswer` tables; the migrating role must
  own the version table to create the trigger.

## Open questions

- Q: Which options go in a retired question's backfilled version 1? → A: All its options, since un-retiring restores them (assumed default: it keeps the "no version 2 after the migration" rule true for retired questions too. Overrule by editing Decisions, "Version 1 from the migration".)
- Q: How does `delete_question_versions()` get past the queryset guard, and what about pinned answers? → A: A raw `DELETE` through the cursor, after callers delete the pinned answers (assumed default: development commands only, and the PROTECT FK would refuse otherwise. Overrule by editing Model.)
- Q: Should the base manager filter by site? → A: No, it is a separate guarded manager (assumed default: related lookups such as `answer.question_version` must not depend on the request's site. Overrule by editing Model.)
- Q: How does `save_answers()` find latest versions without a query per question? → A: `latest_versions(question_ids)`, one query per page (assumed default: it matches the constant-query rule for readers. Overrule by editing Saving answers.)

## Success criteria

- Changing a question's text and running `content_save` creates version 2 with the commit sha; a
  second run prints `0 revised`.
- `UPDATE` and `DELETE` on the version table fail in `psql`.
