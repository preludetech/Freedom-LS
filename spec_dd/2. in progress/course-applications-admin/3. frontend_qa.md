# Frontend QA: course applications in the admin

The admin gains a read-only "Course applications" list and change page, and the "Form progress
records" change page now shows a sitting's answers as a read-only document instead of an editable
inline. Staff with the plain Django view permissions can read applications, answers and files;
the old superuser-only gate is gone. This run walks both pages as a superuser and as a
permission-limited staff viewer, checks the links between them, and tries the ways a reader could
be shown something they cannot open.

Substitute the literal port number chosen by `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `<PORT>`. Shell variables do not survive between tool calls.

---

## §0 Setup

### 0.1 Server

1. `.claude/ds/scripts/find_available_port.sh` — note the number and use it literally from here on.
2. Start `uv run python manage.py runserver <PORT>` backgrounded, as its own call.
3. Open `http://127.0.0.1:<PORT>/` and confirm `#debug-branch-badge` names the
   `course-applications-admin` branch. If it names another branch, another server holds the
   port; go back to step 1.

### 0.2 Seed data

Every item below must exist before §1. Missing data is created through the `fls-dev:qa-data-helper`
agent, never by hand.

1. **Demo content loaded.** `uv run python manage.py content_save demo_content DemoDev`. This
   loads `functionality_demo_application_gated` (the gated course, titled "Functionality Demo -
   Application gated course") and `functionality_demo_application_form` (its three-page form:
   "About you", "Supporting documents", "Availability"). Idempotent; re-run if in doubt.
2. **Superuser:** `demodev@email.com` from `.claude/fls-dev/config.md`.
3. **Reviewer, applicant, bystander:** run
   `uv run python manage.py qa_create_application_review_accounts`. It seeds
   `qa_reviewer@email.com` (staff, not superuser, holding exactly `view_courseapplication`,
   `view_formprogress`, `view_questionanswer` and `view_questionanswerfile`), and resets
   `qa_applicant@email.com` and `qa_bystander@email.com` to plain learners with no application.
   Password equals the email for each. Re-running it strips the applicant's earlier application,
   so run it once at the start, not between sections.
4. **A submitted application with answers and a file.** Sign in as `qa_applicant@email.com`,
   open the gated course from the catalogue, press "Apply", and fill the form:
   - "About you": full name `Ada QA`, date of birth `1990-02-03`, email, phone, portfolio URL,
     years of software `4`, pick one "How did you hear" option, tick two "Which of these
     interest you" boxes, and a "Why do you want to take this course?" answer of at least three
     paragraphs separated by blank lines.
   - "Supporting documents": upload `id-scan.png` (any PNG under 1 MB with real pixel content,
     saved in the scratch directory). Leave "Is there anything else we should know?" empty.
   - "Availability": pick a time and a time zone.
   - On "Check your answers", press "Submit application".
   Call this the *submitted application*. Sign out.
5. **A draft application.** Sign in as `qa_bystander@email.com`, press "Apply" on the same
   course, answer only the full name on "About you" (`Bea Draft`), press Continue once, then
   leave without submitting. Call this the *draft application*. Sign out.
6. **A no-form application.** `uv run python manage.py qa_create_application_docs_scenario`
   creates a gated course that names no form and a learner (`demodev_applicant@email.com`) who
   already applied to it. Call this the *no-form application*.
7. **A quiz sitting that is not an application.** Any completed `FormProgress` on a quiz placed in
   a demo course (for example sign in as `qa_applicant@email.com`, register for
   `functionality_demo_end_with_quiz`, and finish its quiz). Call this the *quiz sitting*.

## §1 The "Course applications" changelist (superuser)

Sign in as `demodev@email.com` and open `http://127.0.0.1:<PORT>/admin/`.

### 1.1 It is there, and it is read-only

1. Under "Course applications", open "Course applications"
   (`/admin/freedom_ls_course_applications/courseapplication/`). Expect a table with the
   columns Applicant, Applicant name, Course, Submitted, Submitted time, Created at.
2. Expect three rows: the submitted application (`qa_applicant@email.com`, "Ada QA", green
   tick, a Submitted time a few minutes old), the draft application
   (`qa_bystander@email.com`, "Bea Draft", red cross, an empty Submitted time), and the no-form
   application (`demodev_applicant@email.com`, green tick, Submitted time equal to its Created at).
3. Expect no "Add course application" button anywhere on the page, and no checkbox column or
   bulk "Delete selected" action.
4. Open the submitted application's row. Expect the change page to open in view mode: no
   "Save" bar, no "Delete" link, and "Submitted", "Submitted time" and "Created at" each
   shown as a plain read-only value. No "Updated at" field.
5. Visit `/admin/freedom_ls_course_applications/courseapplication/add/` directly. Expect 403.

### 1.2 Filters and search

1. Back on the changelist, apply the "submitted" filter set to "Submitted". Expect the submitted
   application and the no-form application; not the draft.
2. Set it to "Draft". Expect only the draft application.
3. Clear it. Use the course filter to pick "Functionality Demo - Application gated course".
   Expect the submitted and draft applications; the no-form application (which is on a
   different course) disappears.
4. Clear it. In the created-at range filter fill only the two date boxes with today's date,
   leave the time boxes empty, press "Apply filters". Expect all three rows to remain.
   Set the "from" date to tomorrow and apply. Expect no rows.
5. Clear the filters. Search `QA`. Expect only the submitted application (matched on the last
   name). Search `Draft`. Expect only the draft application. Search `gated`. Expect the
   submitted and draft applications (matched on the course title). Search `nobody@nowhere`.
   Expect "0 results".

### 1.3 Sorting

1. Click the "Applicant" column heading twice. Expect the rows to reorder by email ascending,
   then descending.
2. Click "Course". Expect the order to change without an error page. Expect the "Submitted"
   and "Submitted time" headings not to be sortable.

## §2 The change page of a submitted application (superuser)

Open the submitted application's change page from the changelist.

### 2.1 Summary

1. Expect a summary block above the answers with three rows: "Applicant" linking to
   `qa_applicant@email.com`, "Course" linking to the course title, and "Form progress record"
   linking to the sitting.
2. Click the "Applicant" link. Expect the User change page for `qa_applicant@email.com`. Go
   back.
3. Click the "Form progress record" link. Expect the Form progress record change page
   (`/admin/freedom_ls_form_engine/formprogress/<id>/change/`). Go back.

### 2.2 The answers document

1. Expect an "Answers" heading followed by three groups headed "About you", "Supporting
   documents" and "Availability", in that order.
2. In "About you", expect each question's text on the left with its answer on the right, in the
   order the form asks them: full name `Ada QA`, the date of birth shown as a readable date (for
   example "Feb. 3, 1990"), the email, phone and URL as typed, `4`, the chosen "How did you
   hear" option as its text (not a number or a widget), the two ticked interests joined by
   " · ", and the long "Why" answer in full with its paragraph breaks preserved and no
   "..." truncation.
3. In "Supporting documents", expect the file row to show `id-scan.png` and a "Download" link,
   and "Is there anything else we should know?" to read "Not answered".
4. Click "Download". Expect a file download named like `id-scan.png` (not a page), and the
   admin page still open behind it.
5. In "Availability", expect the chosen time rendered as a readable time (for example
   "2 p.m.") and the time zone as its option text.
6. Expect no editable inputs, selects or textareas anywhere in the answers document, and no
   per-row "Delete" checkbox.

### 2.3 A draft and a no-form application

1. Open the draft application's change page. Expect the same three summary rows, and an answers
   document where "About you" shows `Bea Draft` for the full name and "Not answered" for every
   other question, including every question on the other two pages.
2. Open the no-form application's change page. Expect "Applicant" and "Course" links, a "Form
   progress record" row reading "The course asked for no application form.", and no
   "Answers" heading at all.

## §3 The "Form progress records" change page (superuser)

### 3.1 An application sitting

1. Under "Form engine", open "Form progress records"
   (`/admin/freedom_ls_form_engine/formprogress/`) and open the row for
   `qa_applicant@email.com` on "Application form".
2. Expect "User" and "Form" shown as read-only text, not as dropdowns.
3. Expect the "Progress" fieldset to show Start time, Last updated time, Completed time, Scores
   and a "Furthest page reached" value of `3`.
4. Expect a summary row "Application" linking to "Application for Functionality Demo -
   Application gated course". Click it. Expect the Course applications change page from §2. Go
   back.
5. Expect the same answers document as §2.2, identical in grouping, order, option text, date
   formatting, the file row and "Not answered".
6. Expect no inline table of answers anywhere on the page, and no editable input, select or
   textarea in the answers document.
7. Press "Save" if a save bar is shown. Expect the page to save with no error and nothing to
   change.

### 3.2 A sitting that is not an application

1. Open the quiz sitting's row. Expect the answers document for the quiz, with the question
   text beside each answer and the chosen option texts, and no summary block above it.

### 3.3 The add page still works

1. Press "Add form progress record". Expect "User" and "Form" to be editable dropdowns on the
   add page and no answers document. Do not save; go back.

### 3.4 A question that left the form

1. Under "Form engine", "Form questions", open "Is there anything else we should know?" and
   change its "Form page" to any page of a different form (for example a page of the demo
   quiz). Save.
2. Open the submitted application's Form progress record page again. Expect "Supporting
   documents" to no longer list that question, and no extra group, because the applicant never
   answered it.
3. Now move "What is your full name?" to that other form's page the same way. Reload the Form
   progress record page. Expect "About you" to no longer show the full name, and a final group
   headed "Questions no longer on the form" listing "What is your full name?" with
   `Ada QA`, after "Availability".
4. Move both questions back to their original pages and restore their "Order" values. Reload.
   Expect the final group to be gone and both questions back in place.

## §4 The staff viewer (`qa_reviewer@email.com`)

Sign out and sign in as `qa_reviewer@email.com`. Open `http://127.0.0.1:<PORT>/admin/`.

### 4.1 What the view permissions open

1. Expect the admin index to list "Course applications" and, under "Form engine", "Form
   progress records", "Question answers" and "Question answer files", with no "Add" links on
   any of those rows.
2. Open "Course applications". Expect the same three rows as §1.1, and no add button.
3. Open the submitted application's change page. Expect the answers document exactly as in §2.2,
   including the file's "Download" link, because this account holds `view_questionanswerfile`.
4. Click "Download". Expect the file to download, not a 403.
5. Expect the summary's "Form progress record" row to be a link (this account may view form
   progress records) and the "Applicant" and "Course" rows to be plain text, not links (this
   account may not view users or courses). Confirm by hovering: no underline, no pointer, and
   no `href` in the element.
6. Open the "Form progress record" link. Expect the Form progress record change page with User
   and Form read-only, the answers document, the "Application" link back to the application
   (this account holds `view_courseapplication`), and no save bar.

### 4.2 What the view permissions do not open

1. Visit `/admin/freedom_ls_form_engine/formprogress/add/`. Expect 403.
2. Visit `/admin/freedom_ls_form_engine/questionanswer/<id>/delete/` for any answer id taken
   from the "Question answers" changelist. Expect 403.
3. Visit the submitted application's change URL with the trailing `/delete/` instead of
   `/change/`. Expect 403.

### 4.3 Without the file permission the download is plain text

1. As `demodev@email.com` in another browser context, open the User change page for
   `qa_reviewer@email.com` and remove `view_questionanswerfile` from its user permissions.
   Save.
2. Back as `qa_reviewer@email.com`, reload the submitted application's change page. Expect the
   file row to show `id-scan.png` as plain text with no "Download" link.
3. Visit the download URL directly:
   `/admin/freedom_ls_form_engine/questionanswerfile/<file id>/download/` (take the id from the
   §2.2 link as the superuser). Expect 403.
4. Expect "Question answer files" to be gone from the admin index for this account.
5. Restore the permission as the superuser.

### 4.4 A staff user with no permissions sees nothing

1. As `demodev@email.com`, open the User change page for `qa_reviewer@email.com`, remove all
   four permissions and save.
2. As `qa_reviewer@email.com`, reload the admin index. Expect none of the four models listed.
   Visit `/admin/freedom_ls_course_applications/courseapplication/` and
   `/admin/freedom_ls_form_engine/formprogress/` directly. Expect 403 on both.
3. Restore the four permissions by re-running
   `uv run python manage.py qa_create_application_review_accounts` only if the applicant's and
   bystander's applications are no longer needed; otherwise add them back by hand on the User
   change page.

## §5 Side effects

### 5.1 Erasing an applicant still works

1. As `demodev@email.com`, open the User change page for `qa_bystander@email.com` and press
   "Delete". Expect the confirmation page to list the course application and the form progress
   record among the objects to be deleted, and no "you don't have permission" notice. Confirm.
2. Reload the Course applications changelist. Expect the draft application gone and the other
   two rows intact.

### 5.2 The applicant's own pages are unchanged

1. Sign in as `qa_applicant@email.com`. Open the dashboard and the application's status page.
   Expect the submitted application to still show as submitted, and "Check your answers" to
   still render every page with "Not answered" for the question left blank.

### 5.3 The other Form engine admins still open

1. As `demodev@email.com`, open "Question answers" and "Question answer files". Expect both
   changelists to render, with the file row's "Download" link still working.
2. Open a question answer's change page. Expect it to still be editable (this plan changes only
   the Form progress record page).

### 5.4 Site isolation

1. If a second site exists in the dev database, confirm the Course applications changelist on
   this site shows no applications from it. If no second site exists, skip.
