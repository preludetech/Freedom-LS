# FLS data availability for the cohort report

## Bottom line

- **The core data exists** for most of the report: completion state and timestamps for topics and forms, quiz scores, per-question answers, and selected options are all in the DB. Nothing about the report requires a new *tracking* concept - it's mostly a query/aggregation problem, not a data-model problem.
- **Biggest real gap: "last item completed" doesn't exist as a field.** `CourseProgress.last_accessed_item` (`freedom_ls/student_progress/models.py:601-603`) means last *viewed*, not last *completed* - it's written on every page view (`freedom_ls/student_interface/views.py:591-596`), including items never finished. The report must derive "last completed" itself by taking `max(TopicProgress.complete_time, FormProgress.completed_time)` across a course's items - no shortcut exists.
- **Biggest surprise: outside an HTTP request, `SiteAwareModel` querysets are not site-filtered at all.** `SiteAwareManager.get_queryset()` only filters when `_thread_locals.request` is set (`freedom_ls/site_aware_models/models.py:43-50`); that thread-local is populated solely by `CurrentSiteMiddleware` (`freedom_ls/site_aware_models/middleware.py`) or the test-only `mock_site_context` fixture (`freedom_ls/conftest.py:106-136`). A PDF-generation code path that runs outside a real request (a management command, an async/Celery task, or a batch job) gets every site's data unless it filters by `site=` explicitly. The codebase's own `recalculate_progress_percentages` command (`freedom_ls/student_progress/management/commands/recalculate_progress_percentages.py:20-38`) demonstrates this exact pattern - it iterates `CourseProgress.objects.select_related("course").all()` with no site scoping because it's designed to run globally. The report generator must not copy that pattern.
- **"Number of attempts" is well-defined and derivable**: `FormProgress` has no `unique_together` on `(user, form)` (confirmed against `unique_together = ["user", "topic"]` on `TopicProgress`, `freedom_ls/student_progress/models.py:560`, vs. no such constraint on `FormProgress`, `freedom_ls/student_progress/models.py:126-149`, and the migration confirms it - `freedom_ls/student_progress/migrations/0001_initial.py`). The existing educator panel already counts attempts this way: `if fp.completed_time is not None: form_progress_map[key]["completed_count"] += 1` (`freedom_ls/educator_interface/views.py:380-381`) - count `FormProgress` rows with `completed_time__isnull=False`, ignore in-progress/abandoned attempts.
- **`FormProgress.scores` only stores totals, never per-question correctness**, and for `QUIZ` strategy it's just `{"score": int, "max_score": int}` (`freedom_ls/student_progress/models.py:454`). Per-question wrong-answer detail must be recomputed live from `QuestionAnswer` + `QuestionOption.correct`, using the same logic as `FormProgress.get_incorrect_quiz_answers()` (`freedom_ls/student_progress/models.py:467-519`) - but that method is per-attempt, unbatched, and does a query per question per attempt; it must not be called in a loop over 50 students x 10 quizzes x N attempts (see Query notes).
- **Scores are frozen at submission time but the "correct" flag is not** - `QuestionOption.correct` can be edited later via `content_save`'s `update_or_create(id=uuid, defaults=fields)` (`freedom_ls/content_engine/management/commands/content_save.py:289-292`, `417-450`). If course authors fix a wrong "correct" answer after some students have already sat the quiz, the frozen `scores` total and a live re-derivation of "which questions were wrong" (which the report needs for section 2/3) can disagree with what the student actually experienced. This is a pre-existing app inconsistency the report will surface, not one it creates.
- **Text-answer quiz questions (`short_text`/`long_text`) are effectively always scored wrong and have no "incorrect options"** - `score_quiz()` and `get_incorrect_quiz_answers()` both only ever look at `selected_options`, never `text_answer` (`freedom_ls/student_progress/models.py:419-455`, `467-519`). There is no manual-grading workflow. The report's "which incorrect options they selected" requirement is simply inapplicable to text questions; at best the report can show the raw `text_answer`.
- **Activities are not tracked at all** - there is no `ActivityProgress` model anywhere in the codebase (confirmed by grep), and `calculate_course_progress_percentage` only counts `TOPIC` and `FORM` content types (`freedom_ls/student_management/utils.py:44-54`). If a course's ordered content includes an `Activity`, the report has literally nothing to say about a student's status on it - it can't even show "not started".

## Gaps and recommended resolutions

1. No stored "last completed item" (cross-topic/form) field.
   - Derive it (recommended): compute per (user, course) via `Max(complete_time)`/`Max(completed_time)` over the course's `Topic`/`Form` IDs, comparing the two maxima in Python or SQL. No schema change needed; this is pure query work.
   - Alternative: add a `last_completed_item` GenericFK to `CourseProgress` mirroring `last_accessed_item`, updated in `CourseItemProgress.save()`. More invasive (new migration, new write path), not justified purely for a read-only report.

2. No per-question correctness stored on `FormProgress` - only aggregate `scores`.
   - Derive it (recommended, and it's the only way today) by joining `QuestionAnswer`/`selected_options` against `QuestionOption.correct` in bulk, as sketched above. This makes the report's "wrong answers" view a live re-derivation each run, with the content-drift caveat noted above.
   - Alternative: snapshot per-question correctness into `QuestionAnswer` (e.g. an `is_correct` bool written at scoring time) or extend `scores` JSON with a per-question breakdown, written once by `score_quiz()`/`complete()`. Would freeze historical correctness against later content edits and remove the need for a bulk re-derivation, at the cost of a migration + backfill and touching `student_progress` model/scoring code, which is out of scope for a read-only reporting feature unless the content-drift inconsistency is judged unacceptable.

3. No `ActivityProgress` - Activities are entirely untracked.
   - Drop from the report (recommended): the report's per-student/per-course item lists and completion counts should silently skip `Activity` items (as `calculate_course_progress_percentage` already does), and the "items in course" total used for percentages should likewise exclude them, matching existing product behaviour rather than inventing new semantics.
   - Alternative: add an `ActivityProgress` model. Out of scope - this is a tracking-feature gap that predates and is independent of the report.

4. No manual grading / correctness concept for `short_text`/`long_text` quiz questions.
   - Drop from the wrong-answer aggregation, show raw text separately (recommended). Document plainly in the report ("text answers are not auto-graded").
   - Alternative: build a grading workflow. Well out of scope.

5. No `is_active`/history on `CohortMembership`; no way to tell when a student left a cohort.
   - Accept as-is (recommended) - report reflects membership as of generation time; call this out in the title-page methodology note ("students shown reflect current cohort membership").
   - Alternative: add a `left_at`/`is_active` field + migration. Real product gap but unrelated to reporting; flag separately if historical accuracy across a term matters to stakeholders.

6. Content edits can retroactively change what "correct" means, desynchronizing frozen scores from live wrong-answer detail.
   - Accept and disclose (recommended): report should stamp "quiz content as of [generation date]" and could optionally flag (if easy) quizzes where `QuestionOption`/`FormQuestion` have no `modified`/`updated_at` timestamp to compare against - note there currently is no such timestamp on these content models (they inherit `BaseContent`/`TitledContent`, neither of which has `auto_now`), so even detecting "this question was edited after student X answered it" is not currently possible without adding one.
   - Alternative: add `updated_at = models.DateTimeField(auto_now=True)` to `BaseContent` (or just `FormQuestion`/`QuestionOption`) to let the report at least flag "content changed since this attempt" per question. Small, low-risk addition if this matters; otherwise accept the disclosed limitation.

7. `SiteAwareManager` is a no-op filter outside a request context.
   - See Site isolation notes below - this is a report implementation requirement, not a data-model gap, but it is the single highest-risk item on this list if the report is generated via a management command or async task.

## Query and performance notes

For a 50-student cohort x 3 courses x 10 quizzes each (~1,500 student-quiz pairs, each with N attempts and up to ~20 questions):

- Roster construction: one query - `CohortMembership.objects.filter(cohort=cohort).select_related("user")`.
- Course/content structure: for each of the 3 courses, `course.children_flat()` (`freedom_ls/content_engine/models.py:319-330`) is already memoized per-instance and internally does one `items` query + one query per child content type (via `prefetch_related("child")`, `freedom_ls/content_engine/models.py:313-317`) - reuse this rather than re-walking `ContentCollectionItem` by hand. Do this once per course, not once per student.
- Topic completion: one query per course (or one overall): `TopicProgress.objects.filter(user_id__in=student_ids, topic_id__in=course_topic_ids).select_related("topic")`.
- Form/quiz completion + attempts: one query per course: `FormProgress.objects.filter(user_id__in=student_ids, form_id__in=course_form_ids).select_related("form").order_by("form_id", "user_id", "-completed_time")`, then group in Python (mirrors `freedom_ls/educator_interface/views.py:366-382`), or use `Count("id", filter=Q(completed_time__isnull=False))` + a `Window(expression=RowNumber(), partition_by=[...], order_by=...)`/`Max("completed_time")` annotate-and-subquery pair to get "latest" per (user, form) in SQL rather than Python if the volumes get large.
- Per-question wrong-answer detail (the expensive part): do not call `FormProgress.get_incorrect_quiz_answers()` in a loop - it is per-instance, unbatched, and does a query per question (`freedom_ls/student_progress/models.py:467-519`). Instead:
  1. One query to get every `FormQuestion` for the relevant forms with `select_related("form_page")` and `prefetch_related("options")`, building a `{question_id: {option_id: is_correct}}` map in Python (small, bounded by quiz content size, not student count).
  2. One query: `QuestionAnswer.objects.filter(form_progress__in=relevant_attempts).select_related("question", "form_progress").prefetch_related("selected_options")`.
  3. Iterate in Python, comparing each answer's `selected_options` against the correctness map built in step 1, and aggregate counts with plain dict counters (or push the aggregation into the database via `QuestionAnswer.selected_options.through` if the checkbox M2M needs `Count`/`annotate` treatment for the cohort-wide confusion tab - e.g. `QuestionOption.objects.filter(questionanswer__form_progress__in=relevant_attempts).annotate(times_selected=Count("questionanswer"))`, filtered to `correct=False`).
- Aggregate primitives to prefer over Python loops where the ORM can do it: `Count()`, `Max()`, `Coalesce()` (already used at `freedom_ls/educator_interface/views.py:335`), `Subquery`/`OuterRef` for "latest row per group" (already used at `freedom_ls/educator_interface/views.py:324-330`), and `Window(expression=RowNumber())` for "Nth attempt" ranking if attempt-ordinal (not just count) is ever needed. The project's ORM-only convention (CLAUDE.md) forbids dropping to hand-written SQL escape hatches without a security review, so all of the above must stay within the ORM's annotate/aggregate/window API.
- N+1 risks to watch for: `Form.pages.all()` and `FormPage.children()` (`freedom_ls/content_engine/models.py:460-471`) are not prefetch-friendly as written (they do two separate queries - `text_items.all()` and `questions.all()` - merged in Python); if the report needs "all questions in a quiz, in order" repeatedly, precompute this once per form (not per student) and cache it, mirroring `Course.children()`'s per-instance memoization pattern (`freedom_ls/content_engine/models.py:297-317`).
- Every relation-traversal query above should carry `select_related()`/`prefetch_related()` per project convention (CLAUDE.md); the existing `CohortCourseProgressPanel` in `educator_interface/views.py` is the closest in-repo precedent for this exact shape of aggregation and is worth using as a structural template (though it's paginated per-column/per-student for an HTML matrix, whereas the PDF report needs the full unpaginated cohort x course-item cross product materialized at once - expect it to be a heavier one-shot query than the panel's).

## Site isolation notes

- `SiteAwareManager.get_queryset()` filters by site only when `_thread_locals.request` is set (`freedom_ls/site_aware_models/models.py:43-50`). That thread-local is populated exclusively by `CurrentSiteMiddleware.__call__` (`freedom_ls/site_aware_models/middleware.py:4-13`) during a real HTTP request, or by the test-only `mock_site_context` fixture (`freedom_ls/conftest.py:106-136`, which sets a `mocker.Mock()` with `_cached_site` and patches `get_current_site`).
- There is no general-purpose "run this code as if inside site X" context manager or decorator anywhere in the codebase (confirmed by grepping for `_thread_locals.request =` outside of `middleware.py`, `conftest.py`, and test files - no hits). The one existing precedent for a management command touching `SiteAwareModel`s outside a request, `recalculate_progress_percentages` (`freedom_ls/student_progress/management/commands/recalculate_progress_percentages.py:20-38`), deliberately iterates `CourseProgress.objects...all()` with no site scoping at all - it is written to operate across every site by design, which is fine for that command but is exactly the trap the report must avoid.
- Consequence for the report: if report generation is triggered synchronously inside an authenticated educator's HTTP request (e.g. a Django view rendering the PDF and returning it directly), `SiteAwareManager` naturally scopes every query to `request`'s site and no special handling is needed - this is the safest option and matches how the rest of `educator_interface` already works (`freedom_ls/educator_interface/views.py` never manually filters by site; it relies on the manager).
- If report generation instead runs outside a request (a management command, a Celery/async task, a queued "generate and email me the PDF" job), every `SiteAwareModel` query (`Cohort`, `CohortMembership`, `CohortCourseRegistration`, `Course`, `Topic`, `Form`, `TopicProgress`, `FormProgress`, `QuestionAnswer`, `QuestionOption`, etc.) must be explicitly filtered by `site=` (e.g. by starting every queryset from `cohort.site` obtained up front and passing `site_id` through), or must synthesize a fake request/thread-local the way `mock_site_context` does for tests - but doing that in production code (not tests) would be an unusual and risky pattern; explicit `.filter(site=...)` is the safer, more auditable choice for report code specifically.
- Because `Cohort` itself is site-aware and its `name` is only unique per site (`unique_cohort_name_per_site`, `freedom_ls/student_management/models.py:19-24`), the report's entry point (however it's invoked - by `Cohort.pk`) already pins the site: `cohort.site_id` should be threaded through every subsequent query as a belt-and-braces filter even inside a request context, since a stray unfiltered query anywhere in a long report-building call chain would otherwise leak cross-site data into a single PDF. This is a report-specific correctness requirement to build into whatever report-service function is written, not something the framework guarantees for you outside the request path.
- `docs/app_structure.md` shows `educator_interface` already legitimately depends on `content_engine`, `student_management`, and `student_progress` (`docs/app_structure.md:54-59`), so a report feature that spans those three apps introduces no new cross-app coupling if it's built inside (or alongside) `educator_interface` - it fits the existing dependency graph exactly.
