# Implementation plan: footer area

Source: `idea.md` in this directory (the spec stage was skipped; the idea is the spec).

## What this delivers

A `{% block footer %}` in `_base.html`, a `partials/footer_bar.html` partial that fills it with a
copyright line and links to the site's legal documents, a compact variant of that same partial on
the `_base_interface.html` shell, and a blanked block on the exam and form runner and on the five
error templates that extend `_base.html`. Plus the `--color-footer` / `--color-on-footer` theme
token pair the footer paints with.

## Decision taken during planning

`idea.md` left one question open: "Whether the footer gets its own `--color-footer` and
`--color-on-footer` token pair, the way the header and side panel have theme tokens, is a styling
question for the spec to settle."

**Settled: the token pair is added; no new component class.** The two tokens go into the
component-tier `@theme inline` block in the default theme, aliasing `--color-surface-2` and
`--color-on-surface` exactly the way `--color-header` aliases `--color-primary`. The footer's
layout stays as Tailwind utilities on the `<footer>` element in the partial, so nothing is added to
`tailwind.components.css`. A theme that wants a distinct footer colour sets the two tokens; a theme
that wants a different footer *shape* shadows the partial.

`text-muted` is deliberately **not** used for the copyright line. In the `first_class` theme
`--color-muted` is `#718096`, which measures roughly 3.6:1 against both `--color-surface` and
`--color-surface-2` — under the 4.5:1 that WCAG 1.4.3 requires for text at this size. The footer
text uses `text-on-footer` instead, which resolves to `--color-on-surface` (14:1 in `default`,
comparable in `first_class`).

## Task 1 — Failing tests for the footer partial and the block

Follow TDD: write these first and watch them fail before touching a template.

New file `freedom_ls/base/tests/test_footer_bar.py`. Model the module docstring and the
`RequestFactory` render helper on `freedom_ls/base/tests/test_head_metadata.py`. Take the
`mock_site_context` fixture (`freedom_ls/conftest.py:136`) in **every** test that renders one of
these templates, not only the ones asserting on `header_title`. `site_config` is a global context
processor and runs on every `_base.html` render regardless of what the body references, which is
why `test_head_metadata.py` and `test_error_pages.py` take the fixture throughout. The only tests
in those files that skip it do so deliberately, to exercise a failing site lookup — neither case
arises here.

Cover, at minimum:

- **The landmark placement.** Rendering `_base.html` puts `<footer` *after* `</main>` in the
  markup — the assertion that actually guards the `contentinfo` landmark. A footer nested inside
  `<main>` maps to `generic` with no warning, so this is the test that must not be allowed to
  weaken into "a `<footer>` exists somewhere".
- **Exactly one `<footer` element** in a rendered `_base.html` page.
- **No `role="contentinfo"`** anywhere in the rendered markup. The implicit role from `<footer>` is
  sufficient and the explicit one is flagged as redundant.
- **The copyright line** carries the current year and `header_title`.
- **Both legal links** render, pointing at `reverse("accounts:legal_doc", kwargs={"doc_type": ...})`
  for `terms` and `privacy`, with the link text `Terms and Conditions` and `Privacy Policy`.
- **Link order is stable** — terms before privacy — in both the full and the compact rendering
  (WCAG 3.2.3).
- **The footer `<nav>` carries `aria-label="Legal"`.**
- **`_base_interface.html` renders the compact variant**: still exactly one `<footer`, still after
  `</main>`, and carrying `data-compact="true"` — while `_base.html` carries
  `data-compact="false"`. Assert the attribute, **not** the `text-xs` / `py-2` utility classes:
  `claude_plugins/django-stack/skills/testing/SKILL.md:180` forbids asserting on styling, and
  `freedom_ls/base/tests/test_theme_tokens.py:8-10` states the same convention in the file this
  task otherwise copies. The attribute is the documented structural hook that
  `claude_plugins/fls-dev/resources/testing.md:60` asks for; how compact the compact variant
  *looks* is not a pytest question.
- **`_exam_runner_base.html` renders no `<footer`.**
- **Each of the five error templates that extend `_base.html`** — `400.html`, `403.html`,
  `403_csrf.html`, `404.html`, `429.html` — renders no `<footer`. Parametrize over the five names.

The panel_framework test template is covered by the existing panel_framework suite rather than by a
new test here: those tests already render it under a urlconf with no `accounts` app, so a missing
blank shows up as `NoReverseMatch` across that whole module. Do not add a duplicate test for it.

Add one more assertion to the existing `freedom_ls/base/tests/test_theme_tokens.py`, in the
"Default theme token contract" section and in the style of the tests already there: the default
theme's `theme.css` declares `--color-footer:` and `--color-on-footer:`.

Note on collection safety: `500.html` and `503.html` are standalone documents that do not extend
`_base.html`, so they are outside this work. Their existing contract tests in
`freedom_ls/base/tests/test_error_pages.py` must stay green untouched.

## Task 2 — The `--color-footer` / `--color-on-footer` token pair

Edit `freedom_ls/themes/default/static/themes/default/theme.css`. Add the pair to the existing
component-tier `@theme inline` block (the one that currently holds `--color-header` and
`--color-sidepanel`), not a new block:

```css
    /* Site footer surface. Defaults to the secondary surface with the normal
     * body foreground; themes wanting a distinct footer set these rather than
     * restyling the partial. */
    --color-footer: var(--color-surface-2);
    --color-on-footer: var(--color-on-surface);
```

`@theme inline` (not bare `@theme`) is required, for the same reason the comment above the header
tokens gives: the alias has to resolve at use time so a theme overriding only `--color-surface-2`
still moves the footer.

Do **not** add overrides to `freedom_ls/themes/first_class/static/themes/first_class/theme.css`.
The defaults already give `first_class` a correct, contrast-passing footer, and an override there
would be styling nobody asked for.

## Task 3 — `partials/footer_bar.html`

New file `freedom_ls/base/templates/partials/footer_bar.html`. One template serves both the full
and the compact rendering, switched by a `compact` variable passed on the include. Two partials
would mean a downstream project had to shadow two files to change one footer; one file keeps the
override seam single.

```django
{% load i18n %}
<footer data-compact="{% if compact %}true{% else %}false{% endif %}"
        class="bg-footer text-on-footer border-t border-border
               px-4 sm:px-6 lg:px-8 {% if compact %}py-2{% else %}py-6{% endif %}">
    <div class="mx-auto w-full max-w-7xl flex flex-wrap items-center justify-center
                gap-x-4 gap-y-1 {% if compact %}text-xs{% else %}text-sm{% endif %}">
        <p class="text-on-footer">&copy; {% now "Y" %} {{ header_title }}</p>
        <nav aria-label="Legal" class="flex flex-wrap items-center gap-x-4 gap-y-1">
            <a href="{% url 'accounts:legal_doc' doc_type='terms' %}" class="py-1">{% trans "Terms and Conditions" %}</a>
            <a href="{% url 'accounts:legal_doc' doc_type='privacy' %}" class="py-1">{% trans "Privacy Policy" %}</a>
        </nav>
    </div>
</footer>
```

Why each piece is the way it is — these are constraints, not preferences:

- **`text-on-footer` is repeated on the `<p>`.** The base layer has `p { @apply text-on-surface }`,
  which would otherwise beat the inherited colour and defeat a theme that sets `--color-on-footer`
  to something other than the default alias.
- **The links carry no colour class.** The base `a` rule already gives them `text-primary underline`,
  which is what the signup consent links render as. Measured against `--color-footer` in both
  shipped themes this clears 4.5:1 (about 4.9:1 in `default`, about 9.2:1 in `first_class`).
- **No custom focus style.** Footer links get the same focus treatment as every other plain link in
  FLS. `--color-focus-ring` aliases `--color-primary`, which clears the 3:1 non-text threshold
  against the footer background in both themes. Adding a footer-only focus ring would be styling
  the idea did not ask for and would make the footer the one place links focus differently.
- **`data-compact` on the `<footer>`.** It says which variant rendered, so a test can assert the
  choice without pinning a utility class that a theme or a later spacing tweak is free to change.
  `data-*` hooks are already how this codebase exposes state to CSS and to tests — `data-scrolled`
  on the header (`partials/header_bar.html:4`), `data-variant` and `data-panel-open` on the side
  panel (`_base_interface.html:162`, `:186`).
- **`py-1` on the anchors.** Inside the flex `<nav>` the anchors are blockified, so the padding
  makes each target at least 24px tall and comfortably wider than 24px — meeting WCAG 2.5.8 on its
  own rather than relying on the inline-text exception, which these do not qualify for.
- **`aria-label="Legal"` on the `<nav>`.** Every secondary `<nav>` in FLS is labelled
  (`cotton/breadcrumbs.html:36`, `partials/course_minimal_toc.html:67`,
  `cotton/course-section-pagination.html:18`); a second unlabelled one would be indistinguishable
  from the header's.
- **No `role="contentinfo"`.** The implicit role is enough and the explicit one is flagged as
  redundant by validators.
- **No `hx-preserve`, no `aria-live`, no `@media print` rule.** Boosted player navigation targets
  and selects `#interface-main`, so the footer is never inside a swap; and FLS has no `@media print`
  rule anywhere today, so adding the first one here would be a new convention nobody asked for.

Write the template comments per the project's comment conventions — say *why* the non-obvious
choices are made (the repeated `text-on-footer`, the `compact` switch), and do not cite this plan or
any section number in them.

## Task 4 — The block in `_base.html`

Edit `freedom_ls/base/templates/_base.html`. Insert the block between `</main>` (line 117) and the
`{% if debug_branch_name %}` badge (line 118):

```django
        </main>

        {% block footer %}
            {% include "partials/footer_bar.html" %}
        {% endblock footer %}

        {% if debug_branch_name %}
```

The placement is the feature, not an aesthetic choice: as a sibling of `<main>` the `<footer>` maps
to the `contentinfo` landmark; nested inside it, it maps to `generic` and the landmark is lost
silently. Put that reason in a template comment above the block, since the next person to tidy this
file needs to know it cannot be moved inside `<main>`.

## Task 5 — The compact variant on `_base_interface.html`

Edit `freedom_ls/base/templates/_base_interface.html`. Add a top-level block override — alongside
`{% block body %}`, not inside it:

```django
{% block footer %}
    {% include "partials/footer_bar.html" with compact=True %}
{% endblock footer %}
```

This shell's desktop sidebar is a sticky full-height column, so a full-bleed footer under the whole
grid would make a learner scroll a viewport of pinned sidebar to reach it. The compact bar keeps the
legal links on the most learner-facing pages in the product at a small scroll cost. Note in the
comment that aligning the footer to the content column instead would mean restructuring the grid
*and* would put the footer back inside `<main>`, losing the landmark.

Two of the three consumers of this shell — `learner_interface/_course_base.html` and
`educator_interface/interface.html` — inherit the compact footer with no change of their own.

**The third consumer needs the block blanked.**
`freedom_ls/panel_framework/tests/templates/panel_framework/test_interface.html` also extends
`_base_interface.html`, and it runs under `freedom_ls.panel_framework.tests.root_urls`, which
registers no `accounts` app. The footer reverses `accounts:legal_doc` unconditionally, so the
inherited footer raises `NoReverseMatch` in every panel_framework test that renders a full page.
Add the blank alongside the header blank that template already carries for exactly this reason:

```django
{% block footer %}{% endblock footer %}
```

Extend that template's existing comment — which already says "These tests run on their own
ROOT_URLCONF, which registers no consumer app. The shared header reverses accounts: and
educator_interface: URLs that urlconf does not carry" — to cover the footer, rather than writing a
second comment saying the same thing.
