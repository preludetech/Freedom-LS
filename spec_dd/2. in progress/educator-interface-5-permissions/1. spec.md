# Spec: educator permissions

Spec 5 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). The problems it fixes are listed under "Why" in `idea.md`, and the code behind each one
is in `research_current_permission_machinery.md`.

This spec renames the roles after what they allow. It adds a capability layer that answers every
permission question in the educator interface, and an `OrganisationMember` row that switches a
person's grants in an organisation on and off. It enforces who may assign which role, and it gives a
denied action a response the user can see.

## Terminology

| Term | Status | Meaning / source |
|---|---|---|
| `OrganisationMember` | coined | A (user, organisation, `is_active`) row recording that a user helps run an organisation's learners, whether or not they teach. It is the counterpart of `Learner` and never means a learner. `OrganisationMember` has no hits in the code or the glossary. |
| capability | narrowed | `role_based_permissions/types.py` ("a single role and its capabilities"). Here it means one permission string in `app_label.codename` form, listed in a `Role.permissions` set and asked of a scope object through `can` rather than through guardian. |
| scope object | coined | The `Site`, `Organisation`, `Cohort` or `Learner` a capability is asked of. For a create action it is the container the new object goes into. Not the same thing as `SCOPE_OBJECT`, which is an assignment scope, nor `panel_scope_name`, the display string a host sets for the page title. `PanelContext.scope` holds one, and the `scope` parameter of `can`, `has_capability` and `get_denied_context` receives one. |

## Scope

In:

- Rename three role keys, with a data migration, and rewrite every role's display name and description.
- Capability strings for every matrix row below, and the four roles' permission sets.
- The `OrganisationMember` model, its backfill, and the rule that it gates every organisation and cohort grant.
- `can`, and the `_visible_to` helpers rebuilt as its queryset twin.
- The panel framework's permission contract: a scope object, deny by default, and no `has_perm` left in the framework.
- The checked assignment utilities: who may assign what, self-assignment, last-admin refusal under a lock, and inactive targets.
- The denied experience: 404 for out-of-scope objects, the 403 fragment, and hidden controls and panels.
- The report generate and download checks.
- Closing the two course-detail row leaks from `notes_from_spec_1_review.md`.

Out:

- The screen for managing organisation members, including adding and deactivating an `OrganisationMember` (spec 9). Until it ships, operators have no way to deactivate one, and the Django admin gets nothing. The audit log (spec 11).
- The screens that use the capabilities for learners, cohorts, bulk operations and reports (specs 6 to 10). This spec defines the capabilities and wires them only into actions that exist today.
- New roles, per-site custom roles, the mockups' "roles and permissions" screen.
- Learner-facing permissions.
- The `CourseConfig` exemption from `authorise_instance`, which spec 6 removes.

## The matrix

Each row lists the capability strings it maps to and the scope object they are asked of. A string
with no app label below is `freedom_ls_learner_management.*`. A row with no built-in model permission
gets a custom `Meta.permissions` entry on the model it acts on.

| Action | Strings (scope object) | site_admin | organisation_admin | cohort_admin | cohort_viewer |
|---|---|---|---|---|---|
| See the organisation dashboard and reports | `freedom_ls_organisations.view_organisation` (organisation); `view_cohort` (cohort); `view_learner` (learner) | all organisations | own organisation | assigned cohorts only | assigned cohorts only |
| Add, deactivate, reactivate learners | `add_learner` (organisation); `change_learner` (learner) | yes | own organisation | no | no |
| Cohort membership add, remove, move | `add_cohortmembership`, `delete_cohortmembership` (cohort) | yes | own organisation | within assigned cohorts; a move needs `delete_` on the source and `add_` on the destination | no |
| Cohort and individual registration, unregistration | `add_cohortcourseregistration`, `change_cohortcourseregistration` (cohort); `add_learnercourseregistration`, `change_learnercourseregistration` (learner) | yes | own organisation | within assigned cohorts | no |
| Cohort create, edit, deactivate, delete when empty | `add_cohort` (organisation); `change_cohort`, `delete_cohort` (cohort) | yes | own organisation | no | no |
| CSV import, bulk actions | `bulk_manage_learners` (organisation), custom on `Learner` | yes | own organisation | no | no |
| Add, remove, scope cohort admins and cohort viewers; add and remove organisation members | `freedom_ls_role_based_permissions.assign_cohort_admin`, `.assign_cohort_viewer` (cohort); `view_organisationmember`, `add_organisationmember`, `change_organisationmember` (organisation) | yes | own organisation | no | no |
| Add and remove organisation admins | `freedom_ls_role_based_permissions.assign_organisation_admin` (organisation) | yes | own organisation | no | no |
| Grant or remove site_admin | `freedom_ls_role_based_permissions.assign_site_admin` (site) | yes | no | no | no |
| Generate and download reports | `download_cohort_report` (cohort or organisation), custom on `Cohort` | yes | own organisation | assigned cohorts | assigned cohorts |

The product owner has confirmed these rows. A person may hold several roles and gets the union.
`cohort_viewer` changes nothing. A cohort admin may not edit a cohort's name or description. A later
spec that builds a capability outside these rows adds the row, the string and the check together;
spec 11 adds the audit log row.

### `OrganisationMember` (`freedom_ls/learner_management/`)

- `models.py`:

  ```python
  class OrganisationMember(SiteAwareModel):
      user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
      organisation = models.ForeignKey("freedom_ls_organisations.Organisation", on_delete=models.PROTECT)
      is_active = models.BooleanField(default=True)
      created_at = models.DateTimeField(auto_now_add=True)

      class Meta:
          constraints = [UniqueConstraint(fields=["site", "user", "organisation"], name="unique_member_per_organisation")]
  ```

  No manager hides inactive rows. `OrganisationMember` and `Learner` are independent, so a user may hold both in the same organisation.
- Custom `Meta.permissions` on `Learner` for `bulk_manage_learners`, and on `Cohort` for `download_cohort_report`.
- `utils.ensure_organisation_member(user, organisation) -> OrganisationMember`: `_base_manager.get_or_create` with `site=organisation.site`, for the same reason `ensure_learner` uses `_base_manager`, and `is_active=True` as the default. It returns an existing row unchanged, even an inactive one, so a deactivated member is never silently reactivated.
- A `post_save` receiver on `ObjectRoleAssignment`, registered in `apps.py` `ready()`: when the saved row is active and its target is an `Organisation` or a `Cohort`, call `ensure_organisation_member` for the target's organisation. Every path that creates a grant, including the raw utility, the QA commands and test fixtures, then gets the row.
- Migration, schema then data: create `OrganisationMember`, then backfill one active row per (user, organisation) for every active `ObjectRoleAssignment` whose role is `organisation_admin` (target organisation) or `cohort_admin` or `cohort_viewer` (target cohort, walked to its organisation). It depends on `role_based_permissions` `0002_rename_educator_roles` and uses the historical `ContentType`. It is idempotent through `get_or_create`, and its reverse is a no-op.
- `factories.py`: `OrganisationMemberFactory`.
- `admin.py`: no change.

Deactivating an `OrganisationMember` never touches role assignments or guardian rows, and
reactivating it restores exactly the grants the user had.

### Capability layer (`freedom_ls/learner_management/capabilities.py`, `queries.py`)

`can` and `OrganisationMember` live in `learner_management`, beside the helpers they must agree with.
That adds one runtime edge, `learner_management → role_based_permissions`. `panel_framework` imports
none of it.

- `can(user: RequestUser, capability: str, scope: Model) -> bool` reads role assignments and the role config, never guardian rows, so a stale guardian row cannot outlive a deactivated `OrganisationMember`. A grant on a container covers everything inside it, with nothing written onto the children. It resolves as follows:
  1. Anonymous or inactive user → `False`. Active superuser → `True`.
  2. `roles_granting(capability, site)`: the role keys whose `permissions` contain the capability, from `get_role_config(site.name)`, where `site` is the scope object's site. A config change needs no guardian re-sync.
  3. An active `SiteRoleAssignment` on that site with a granting role → `True`. No `OrganisationMember` is needed.
  4. Otherwise find the scope object's organisation. A `Site` has none, so the answer is `False`. The user needs an active `OrganisationMember` for it, or the answer is `False`.
  5. An active `ObjectRoleAssignment` with a granting role on the organisation → `True`.
  6. An active `ObjectRoleAssignment` with a granting role on a cohort covering the scope object → `True`. The scope object is covered when it is that cohort, or a learner with a `CohortMembership` in it. A cohort grant never covers an organisation.
- `can` ignores the scope object's own `is_active`. What an inactive cohort or learner still allows is up to specs 6 and 7. Deactivating a cohort leaves the grants on it intact.
- `can` and the helpers in `queries.py` are built from the same private queryset builders in `capabilities.py`, one per step above. Neither re-implements a branch of the other.
- `queries.py`: rebuild `organisations_accessible_to`, `cohorts_visible_to`, `all_cohorts_visible_to`, `can_view_cohort` and `learners_visible_to` on those builders, keeping their signatures. `organisations_accessible_to` returns every organisation on the site for a `site_admin`, plus, with an active `OrganisationMember`, the organisations where an organisation role grants `view_organisation` and those where the user has a `view_cohort` grant on a cohort. `learners_visible_to` keeps applying `is_active=True` outside the visibility branches. Drop the `get_objects_for_user` import.
- `queries.py`: add `active_organisation_admins(organisation) -> QuerySet[User]`, the active users holding an active `organisation_admin` assignment on the organisation and an active `OrganisationMember` in it. The last-admin check and the "who to ask" copy both read it.
- Every existing caller follows without edits: `CohortConfig.authorise_instance`, `LearnerConfig.authorise_instance`, the organisation switcher, the context processors and `reports/admin.py`.

### Panel framework contract (`freedom_ls/panel_framework/`)

- `context.py` `PanelContext`: add `scope: Model | None`, the object a list-level action is asked about, and `config: type[SectionConfigBase]`. Child contexts inherit both through `dataclasses.replace`. `scope_object()` returns `instance`, or `scope` when there is no instance.
- `views.py` `SectionConfigBase`:
  - `get_scope(cls, request) -> Model | None`, default `None`. `_bind_root` sets `ctx.scope` from it.
  - `has_capability(cls, request, capability: str, scope: Model) -> bool`, default `False`, deny by default like `authorise_instance`.
  - `get_denied_context(cls, request, capability: str | None, scope: Model | None) -> dict[str, str]`, default generic copy (see "Denied experience"). Both arguments may be `None`, because a consumer's own `has_permission` can deny an action that declares no capability.
- `actions.py` `PanelAction`: `has_permission(self, ctx: PanelContext) -> bool` replaces `(request, instance)`. Add a `capability: str | None = None` attribute, `get_capability(self, ctx) -> str | None`, default `self.capability`, and `permission_object(self, ctx) -> Model | None`, default `ctx.scope_object()`. The default `has_permission` returns `True` when `get_capability` is `None`, `False` when the permission object is `None`, and otherwise asks `ctx.config.has_capability(...)`.
  - `CreateInstanceAction`: `get_capability` falls back to `f"{app_label}.add_{model_name}"` when `capability` is unset. The objectless `has_perm` goes.
  - `EditAction` and `DeleteAction`: `get_capability` falls back to `change_` and `delete_` of the model. `DeleteAction` asks about `ctx.instance` only and still denies when there is none. Their `has_perm` calls go.
  - Nothing in `panel_framework` calls `has_perm` afterwards.
- `panels.py` `Panel`: add `capability: str | None = None`. The default `has_permission` asks `ctx.config.has_capability` about `ctx.scope_object()` when `capability` is set, and returns `True` otherwise. A consumer may still override it.
- Pass the context at every action permission call: `_main_for` for list and instance actions, `_handle_action`, and `Panel.get_context_data`.
- `_handle_action` on denial:
  - For an htmx request, render `panel_framework/partials/action_denied.html` with `get_denied_context(...)` at status 403, into the action's own target.
  - Otherwise raise `PermissionDenied`, so the existing `403.html` renders.
- `freedom_ls/base/static/base/js/alpine-components.js`, the `htmx:beforeSwap` listener: treat 403 the way it treats 422 (`shouldSwap = true`, `isError = false`). No extension and no `responseHandling` change.

### Checked assignment utilities (`freedom_ls/learner_management/role_assignment.py`)

Spec 9 calls these. The raw utilities in `role_based_permissions/utils.py` stay available for QA
commands, fixtures and the Django admin.

```python
def assign_role(grantor: User, user: User, role: str, target: Site | Organisation | Cohort) -> None: ...
def remove_role(grantor: User, user: User, role: str, target: Site | Organisation | Cohort) -> None: ...
def set_organisation_member_active(actor: User, member: OrganisationMember, is_active: bool) -> None: ...
```

For `set_organisation_member_active`, `actor` and `member.user` take the places of `grantor` and
`user`. The checks run in this order. Each failure raises `RoleChangeRefused` with the reason shown
and changes nothing:

1. `grantor == user` → `SELF`.
2. Assigning to an inactive user → `INACTIVE_USER`. Removal is allowed.
3. `can(grantor, f"freedom_ls_role_based_permissions.assign_{role}", target)` is false → `NOT_PERMITTED`. For `set_organisation_member_active` the capability is `change_organisationmember` on the organisation. A downstream custom role such as `senior_ta` has no `assign_` string, so it stays assignable only through the raw utilities and the admin.
4. Removing an active `organisation_admin` assignment, or deactivating an `OrganisationMember` who holds one, when the grantor is neither a superuser nor an active `site_admin`: lock the `Organisation` row with `select_for_update()`, count `active_organisation_admins(organisation)` other than the user, and refuse at zero → `LAST_ORGANISATION_ADMIN`.
5. `site_admin` removal goes through `remove_site_role`, so `LAST_SITE_ADMIN` applies there.

A last admin trying to remove themselves is refused as `SELF`. The count, the removal and the
deactivation happen in one transaction under the lock. The lock is on the scope row because locking
assignment rows leaves a race between a removal and a deactivation, and an empty set of rows locks
nothing. Assigning a role creates the `OrganisationMember` through the receiver and does not
reactivate an inactive one.

### Denied experience

- **Out of scope → 404.** An organisation, cohort or learner outside the user's scope is a 404 through `authorise_instance` and the visibility helpers. That includes a cohort a cohort admin holds no grant on, inside an organisation they can otherwise enter, and any organisation where their `OrganisationMember` row is inactive. An htmx request to an action whose object is out of scope, such as a stale delete after the grant went, gets the 404 as the fragment in `action_unavailable.html` ("This is no longer available", Close only), so the page shows something instead of dropping the response. Its copy does not say whether the object was removed or the access was.
- **Visible but not permitted → 403.** The fragment in `action_denied.html` carries its own heading and says what happened ("You can't use “<label>” here any more", where <label> is the action's `label`, so the sentence reads the same for "Delete" and "Create Cohort"), why ("Your role doesn't allow it"), and who to ask. It offers close or back only, never retry. It does not distinguish "your role changed" from "you never had it".
- **Who to ask** names a role scoped to the object: an organisation admin of <organisation name>. It names `active_organisation_admins` only when the user holds `view_organisationmember` on that organisation. The framework's default copy is "Ask an administrator".
- **Hidden, not disabled.** Actions whose `has_permission` is false are not rendered. Panels and tabs set `capability` or override `Panel.has_permission`. Lists filter rows through the visibility helpers.

## Testing

- **Matrix test** (`freedom_ls/educator_interface/tests/test_permission_matrix.py`). `MATRIX` is a hand-written transcription of the matrix table, reviewed against it and not parsed from it. It is parametrised over role × capability string × scope relation, where the relation is own, other cohort in the same organisation, other organisation and other site, and asserts `can`. It also includes:
  - a completeness test: every (role, capability) pair in the four roles' cross-product has a case;
  - an interface-completeness test: every `capability` declared on an action or panel reachable from the educator interface's sections, by the enumeration `test_config_authorisation.py` builds, is in `MATRIX`;
  - an agreement test: for each role and scope relation, `can(view_cohort)` and `can(view_learner)` agree with `cohorts_visible_to` and `learners_visible_to` on active objects;
  - the `OrganisationMember` gate: every organisation-scoped `True` case turns `False` when the member row is deactivated and back to `True` on reactivation, with the assignment rows unchanged.
- **`can` unit tests** (`learner_management/tests/test_capabilities.py`):
  - a cohort created after the grant is covered with nothing re-synced;
  - a changed role config, after `clear_caches()`, takes effect with no guardian re-sync;
  - `site_admin` needs no `OrganisationMember`, and gets `True` for cohort capabilities, closing the `TestSiteRoleFunctions` gap;
  - a superuser gets `True`;
  - inactive and anonymous users get `False`.
- **Assignment rules** (`learner_management/tests/test_role_assignment.py`), one test per refusal reason, plus:
  - an organisation admin assigning in another organisation → `NOT_PERMITTED`;
  - a cohort admin assigning anything → `NOT_PERMITTED`;
  - a site admin removing the last organisation admin succeeds;
  - the last admin removing themselves → `SELF`;
  - deactivating the last organisation admin's `OrganisationMember` → `LAST_ORGANISATION_ADMIN`;
  - assigning to a user with an inactive `OrganisationMember` leaves it inactive;
  - the captured SQL contains `FOR UPDATE` on the scope row.
- **`remove_site_role`** (`role_based_permissions/tests/test_utils.py`): refuses the last active `site_admin`, and counts only active users.
- **Migrations**: the rename's forward and reverse functions, including a row with an unrelated role left untouched. The backfill creates one `OrganisationMember` per (user, organisation) from organisation and cohort grants, and running it twice creates nothing new.
- **`post_save` receiver**: the raw `assign_object_role` on a cohort creates an active `OrganisationMember`, and leaves an existing inactive one inactive.
- **Reports** (`reports/tests/test_views.py`): generate and download are refused for a user whose roles lack `download_cohort_report`.
- **Framework** (`panel_framework/tests/`):
  - a list-level `CreateInstanceAction` is asked about `ctx.scope`, and one inside an instance view about `ctx.instance`;
  - built-in actions deny when `has_capability` is left at its default;
  - `Panel.capability` hides a panel and makes its URL a 404;
  - `_handle_action` returns the 403 fragment for htmx and raises `PermissionDenied` otherwise.
- **Endpoint tests, one per denial shape** (`educator_interface/tests/test_denied_experience.py`):
  - a 404 for a cohort outside a cohort admin's grants, inside their organisation;
  - the 403 fragment for a create posted after the grant was removed;
  - the 404 "no longer available" fragment for an htmx delete on a cohort that left scope after the grant was removed;
  - the create-cohort control absent for a cohort viewer;
  - a Playwright test that the 403 fragment swaps into place, in `educator_interface/tests/playwright/test_denied_experience.py` and marked `playwright`, where every browser test lives.
- **Course detail leaks** (`test_organisation_isolation.py`): a cohort-scoped educator sees neither another cohort's direct registrations nor another cohort in either course-detail panel.
- `test_config_authorisation.py` keeps its assertions. Its enumeration of reachable panels and actions moves to a shared test helper, so the matrix test walks the same surface. Every test that uses the old role strings is updated, and the `_organisation_staff_user` helpers in `reports/tests/test_views.py` and `reports/tests/test_admin.py` are renamed. `test_roles.py`'s subset assertions now compare `cohort_viewer` with `cohort_admin`.

## Success criteria

- `rg '"(organisation_staff|instructor|ta)"' freedom_ls config` finds no role keys.
- `uv run manage.py validate_role_permissions` passes.
- `uv run manage.py makemigrations --check` reports no changes.
- After `migrate`, no assignment row has an old key, and every active organisation or cohort grant holder has an active `OrganisationMember`.
- An organisation admin with no superuser flag can create a cohort in their organisation through the interface.
- `rg -w has_perm freedom_ls/panel_framework` finds nothing. The `-w` keeps `has_permission` out of the match.
- `uv run pytest` passes, including the matrix and completeness tests.
