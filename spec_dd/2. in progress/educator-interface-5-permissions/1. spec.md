# Spec: educator permissions

Spec 5 of 12 in the educator interface rebuild (`spec_dd/1. next/roadmap.md`, "Educator interface
rebuild"). Written against `idea.md` and the research files beside it.

## Purpose

The existing roles can't express what the educator interface offers, and some of the checks that
exist can never pass. `instructor` and `ta` carry identical permissions. Role sync drops every
`site_admin` cohort permission, and an objectless `add_cohort` check means only a superuser can
create a cohort. Nothing checks who may assign which role, nothing records which educators belong
to an organisation, and a denied action fails silently. This spec renames the roles after what they
allow and adds a capability layer that answers every permission question in the interface. It also
adds an `Educator` association that gates grants per organisation, enforces the assignment rules
and gives the denied experience a response the user can see.

## Terminology

| Term | Status | Meaning / source |
|---|---|---|
| `Educator` | coined | A (user, organisation, `is_active`) row recording that a user administers learners in an organisation. The educator's counterpart of `Learner`. No existing term; `Educator` has no hits as an identifier or in the glossary. |
| capability | coined | A permission string in `app_label.codename` form, listed in a `Role.permissions` set and asked of a scope object through `can`. Every capability is a permission string. The word marks the string being checked through the layer instead of guardian. |
| scope object | coined | The `Site`, `Organisation`, `Cohort` or `Learner` a capability is asked of. For a create action it is the container the new object goes into. |

## Scope

In:

- Rename three role keys, with a data migration, and rewrite every role's display name and description.
- Capability strings for every matrix row below, and the four roles' permission sets.
- The `Educator` model, its backfill, and the rule that it gates every organisation and cohort grant.
- `can`, and the `_visible_to` helpers rebuilt as its queryset twin.
- The panel framework's permission contract: a scope object, deny by default, and no `has_perm` left in the framework.
- The checked assignment utilities: who may assign what, self-assignment, last-admin refusal under a lock, and inactive targets.
- The denied experience: 404 for out-of-scope objects, the 403 fragment, and hidden controls and panels.
- Closing the two course-detail row leaks from `notes_from_spec_1_review.md`.

Out:

- The educators screen, including adding and removing an `Educator` (spec 9). The audit log (spec 11).
- The screens that use the capabilities for learners, cohorts, bulk operations and reports (specs 6 to 10). This spec defines the capabilities and wires them only into actions that exist today.
- New roles, per-site custom roles, the mockups' "roles and permissions" screen.
- Learner-facing permissions.
- The `CourseConfig` exemption from `authorise_instance`, which spec 6 removes.

## Decisions

1. **Capabilities are permission strings in `Role.permissions`.** A downstream `add_permissions` override works unchanged, `validate_role_permissions` already checks them against `registry.PERMISSIONS`, and guardian sync still handles direct cohort grants. A row with no built-in model permission gets a custom `Meta.permissions` entry on the model it acts on.
2. **`can` reads role assignments and the role config, never guardian rows.** Otherwise a stale guardian row would let a cohort grant work after its `Educator` row has been deactivated. Grants on a container cover everything inside it, with nothing written onto the children.
3. **The capability layer and `Educator` live in `learner_management`.** That costs one new runtime edge, `learner_management → role_based_permissions`, and puts `can` beside the helpers it has to agree with. `panel_framework` imports none of it.
4. **Assigning an organisation or cohort role creates the `Educator` row when it is missing,** in a `post_save` receiver on `ObjectRoleAssignment` in `learner_management`. Every path that creates a grant, including the raw utility, the QA commands and test fixtures, then gets the association without depending on the wrong app. An existing inactive row is left inactive, so a deactivated educator is never silently reactivated.
5. **Guardian sync is unchanged.** It keeps writing rows for object roles on their own content type, and the Django admin's `GuardedSiteAwareModelAdmin` still reads them. The educator interface and the visibility helpers stop reading guardian.
6. **Superusers hold every capability,** as they do under `has_perm` today.
7. **The last-admin guards lock the scope row,** meaning the `Site` or `Organisation`, with `select_for_update()` inside `transaction.atomic()`. Locking only the assignment rows leaves a race between an assignment removal and an `Educator` deactivation, and an empty set of rows locks nothing at all.
8. **Downstream configs that still use the old keys break at import.** `SiteRolesConfig.extend` already raises `ValueError` on an unknown `inherits`, so there is no alias table. The upgrade notes give the mapping.

## The matrix

Each row lists the capability strings it maps to and the scope object they are asked of. Every
string without an app label prefix below is `freedom_ls_learner_management.*`.

| Capability | Strings (scope object) | site_admin | organisation_admin | cohort_admin | cohort_viewer |
|---|---|---|---|---|---|
| See the organisation dashboard and reports | `freedom_ls_organisations.view_organisation` (organisation); `view_cohort` (cohort); `view_learner` (learner) | all organisations | own organisation | assigned cohorts only | assigned cohorts only |
| Add, deactivate, reactivate learners | `add_learner` (organisation); `change_learner` (learner) | yes | own organisation | no | no |
| Cohort membership add, remove, move | `add_cohortmembership`, `delete_cohortmembership` (cohort) | yes | own organisation | within assigned cohorts; a move needs `delete_` on the source and `add_` on the destination | no |
| Cohort and individual registration, unregistration | `add_cohortcourseregistration`, `change_cohortcourseregistration` (cohort); `add_learnercourseregistration`, `change_learnercourseregistration` (learner) | yes | own organisation | within assigned cohorts | no |
| Cohort create, edit, deactivate, delete when empty | `add_cohort` (organisation); `change_cohort`, `delete_cohort` (cohort) | yes | own organisation | no | no |
| CSV import, bulk actions | `bulk_manage_learners` (organisation), custom on `Learner` | yes | own organisation | no | no |
| Add, remove, scope cohort admins and cohort viewers; add and remove the association | `freedom_ls_role_based_permissions.assign_cohort_admin`, `.assign_cohort_viewer` (cohort); `view_educator`, `add_educator`, `change_educator` (organisation) | yes | own organisation | no | no |
| Add and remove organisation admins | `freedom_ls_role_based_permissions.assign_organisation_admin` (organisation) | yes | own organisation | no | no |
| Grant or remove site_admin | `freedom_ls_role_based_permissions.assign_site_admin` (site) | yes | no | no | no |
| Generate and download reports | `download_cohort_report` (cohort or organisation), custom on `Cohort` | yes | own organisation | assigned cohorts | assigned cohorts |

The product owner has confirmed these rows. A person may hold several roles, and they get the
union. `cohort_viewer` changes nothing, by definition. A later spec that builds a capability outside
these rows adds the row, the string and the check together; spec 11 adds the audit log row.

A cohort admin may not edit a cohort's name or description (no `change_cohort`).

### `Educator` (`freedom_ls/learner_management/`)

### Capability layer (`freedom_ls/learner_management/capabilities.py`, `queries.py`)

- `can(user: RequestUser, capability: str, scope: Model) -> bool`. It resolves as follows:
  1. Anonymous or inactive user → `False`. Active superuser → `True`.
  2. `roles_granting(capability, site)`: the role keys whose `permissions` contain the capability, from `get_role_config(site.name)`, where `site` is the scope object's site. The config is read on every check, so a changed `FREEDOMLS_PERMISSIONS_MODULES` override takes effect on the next check.
  3. An active `SiteRoleAssignment` on that site with a granting role → `True`. No association is needed.
  4. Otherwise find the scope object's organisation (a `Site` has none, so the answer is `False`). The user needs an active `Educator` for it, or the answer is `False`.
  5. An active `ObjectRoleAssignment` with a granting role on the organisation → `True`.
  6. An active `ObjectRoleAssignment` with a granting role on a cohort covering the scope object → `True`. The scope object is covered when it is that cohort, or a learner with a `CohortMembership` in it. An organisation scope object is never covered by a cohort grant.
- `can` does not look at the scope object's own `is_active`. What an inactive cohort or learner still allows is up to specs 6 and 7. Deactivating a cohort leaves the grants on it intact.
- `can` and the helpers in `queries.py` are built from the same private queryset builders in `capabilities.py`, one per step above. Neither re-implements a branch of the other. None of them reads guardian.
- `queries.py`: rebuild `organisations_accessible_to`, `cohorts_visible_to`, `all_cohorts_visible_to`, `can_view_cohort` and `learners_visible_to` on those builders, keeping their signatures. `organisations_accessible_to` returns every organisation on the site for a `site_admin`, the organisations where an organisation role grants `view_organisation` (with an active `Educator`), and the organisations where the user has a `view_cohort` grant on a cohort (with an active `Educator`). `learners_visible_to` keeps applying `is_active=True` outside the visibility branches. Drop the `get_objects_for_user` import.
- Every existing caller follows without edits: `CohortConfig.authorise_instance`, `LearnerConfig.authorise_instance`, the organisation switcher and the context processors.

### Panel framework contract (`freedom_ls/panel_framework/`)

- `context.py` `PanelContext`: add `scope: Model | None`, the object a list-level action is asked about, and `config: type[SectionConfigBase]`. Child contexts inherit both through `dataclasses.replace`.
- `views.py` `SectionConfigBase`:
  - `get_scope(cls, request) -> Model | None`, default `None`. `_bind_root` sets `ctx.scope` from it.
  - `has_capability(cls, request, capability: str, obj: Model) -> bool`, default `False`, deny by default like `authorise_instance`.
  - `get_denied_context(cls, request, capability: str, obj: Model) -> dict[str, str]`, default generic copy (see "Denied experience").
- `actions.py` `PanelAction`: `has_permission(self, ctx: PanelContext) -> bool`, replacing `(request, instance)`. Add a `capability: str | None = None` attribute and `permission_object(self, ctx) -> Model | None`, default `ctx.instance`. The default `has_permission` returns `True` when `capability` is `None`, `False` when the permission object is `None`, and otherwise asks `ctx.config.has_capability(...)`.
  - `CreateInstanceAction`: `capability` defaults to `f"{app_label}.add_{model_name}"`, and `permission_object` returns `ctx.scope`. The objectless `has_perm` goes.
  - `EditAction` and `DeleteAction`: `capability` defaults to `change_` and `delete_` of the model, and the permission object is the instance. Their `has_perm` calls go.
  - Nothing in `panel_framework` calls `has_perm` afterwards.
- `panels.py` `Panel`: add `capability: str | None = None`. The default `has_permission` asks `ctx.config.has_capability` about `ctx.instance or ctx.scope` when `capability` is set, and returns `True` otherwise. A consumer may still override it.
- Update the callers in `views.py`: `_main_for`, the instance-level action filter and `_handle_action`.
- `_handle_action` on denial:
  - For an htmx request, render `panel_framework/action_denied.html` with `get_denied_context(...)` at status 403, into the action's own target.
  - Otherwise raise `PermissionDenied`, so the existing `403.html` renders.
- `freedom_ls/base/static/base/js/alpine-components.js`, the `htmx:beforeSwap` listener: treat 403 the way it treats 422 (`shouldSwap = true`, `isError = false`). No extension and no `responseHandling` change.

### Checked assignment utilities (`freedom_ls/learner_management/role_assignment.py`)

The path spec 9 calls. The raw utilities in `role_based_permissions/utils.py` stay available for QA
commands, fixtures and the Django admin.

```python
def assign_educator_role(grantor: User, user: User, role: str, target: Site | Organisation | Cohort) -> None: ...
def remove_educator_role(grantor: User, user: User, role: str, target: Site | Organisation | Cohort) -> None: ...
def set_educator_active(actor: User, educator: Educator, is_active: bool) -> None: ...
```

These checks run in this order. Each failure raises `RoleChangeRefused` with the reason shown and
changes nothing:

1. `grantor == user` → `SELF`.
2. The target user is inactive → `INACTIVE_USER`. This applies to assignment only; removal is allowed.
3. `can(grantor, f"freedom_ls_role_based_permissions.assign_{role}", target)` is false → `NOT_PERMITTED`. For `set_educator_active` the capability is `change_educator` on the organisation.
4. Removing an `organisation_admin` assignment, or deactivating an `Educator` who holds one, when the grantor holds no active `site_admin` role: lock the `Organisation` row, count the other active `organisation_admin` assignments on it whose users are active and have an active `Educator`, and refuse at zero → `LAST_ORGANISATION_ADMIN`.
5. `site_admin` removal goes through `remove_site_role`, so `LAST_SITE_ADMIN` applies there (see "Roles").

The self check comes first, so a last admin trying to remove themselves is refused as `SELF`. The
count, the removal and the deactivation happen in one transaction under the lock. Assigning a role
creates the `Educator` through Decision 4 and does not reactivate an inactive one.

### Denied experience

- **Out of scope → 404.** An organisation, cohort or learner outside the user's scope is a 404 through `authorise_instance` and the visibility helpers. That includes a cohort a cohort admin holds no grant on, inside an organisation they can otherwise enter, and any organisation where their `Educator` row is inactive.
- **Visible but not permitted → 403.** The fragment in `action_denied.html` carries its own heading and says what happened ("You can't <action> here any more"), why ("Your role doesn't allow it"), and who to ask. It offers close or back only, never retry. It does not distinguish "your role changed" from "you never had it".
- **Who to ask** names a role scoped to the object: an organisation admin of <organisation name>. It names people, the active organisation admins, only when the user holds `view_educator` on that organisation. The framework's default copy is "Ask an administrator".
- **Hidden, not disabled.** Actions whose `has_permission` is false are not rendered (existing filter). Panels and tabs set `capability` or override `Panel.has_permission`. Lists filter rows through the visibility helpers.

## Testing

- **Matrix test** (`freedom_ls/educator_interface/tests/test_permission_matrix.py`). `MATRIX` is a hand-written transcription of the matrix table, reviewed against it and not parsed from it. It is parametrised over role × capability string × scope relation, where the relation is own, other cohort in the same organisation, other organisation and other site, and asserts `can`. It also includes:
  - a completeness test: every (role, capability) pair in the four roles' cross-product has a case;
  - an interface-completeness test: every `capability` declared on an action or panel reachable from the educator interface's sections (the same enumeration `test_config_authorisation.py` builds) is in `MATRIX`;
  - an agreement test: for each role and scope relation, `can(view_cohort)` / `can(view_learner)` agrees with `cohorts_visible_to` / `learners_visible_to` on active objects;
  - the `Educator` gate: every organisation-scoped `True` case turns `False` when the `Educator` is deactivated and back to `True` on reactivation, with the assignment rows unchanged.
- **`can` unit tests** (`learner_management/tests/test_capabilities.py`):
  - a cohort created after the grant is covered with nothing re-synced;
  - a patched role config takes effect on the next call;
  - `site_admin` needs no `Educator`;
  - a superuser gets `True`;
  - inactive and anonymous users get `False`.
  - It also closes the `TestSiteRoleFunctions` gap: `site_admin` gets `True` for cohort capabilities through `can`.
- **Assignment rules** (`learner_management/tests/test_role_assignment.py`), one test per refusal reason, plus:
  - an organisation admin assigning in another organisation → `NOT_PERMITTED`;
  - a cohort admin assigning anything → `NOT_PERMITTED`;
  - a site admin removing the last organisation admin succeeds;
  - the last admin removing themselves → `SELF`;
  - deactivating the last organisation admin's `Educator` → `LAST_ORGANISATION_ADMIN`;
  - assigning to a user with an inactive `Educator` leaves it inactive.
  - To prove the lock, assert that the captured SQL contains `FOR UPDATE` on the scope row.
- **`remove_site_role`** (`role_based_permissions/tests/test_utils.py`): refuses the last active `site_admin`, and counts only active users.
- **Migrations**: the rename's forward and reverse functions, including a row with an unrelated role left untouched. The backfill creates one `Educator` per (user, organisation) from organisation and cohort grants, and running it twice creates nothing new.
- **`post_save` receiver**: the raw `assign_object_role` on a cohort creates an active `Educator`, and it leaves an existing inactive one inactive.
- **Framework** (`panel_framework/tests/`):
  - `CreateInstanceAction` is asked about `ctx.scope`;
  - built-in actions deny when `has_capability` is left at its default;
  - `Panel.capability` hides a panel and makes its URL a 404;
  - `_handle_action` returns the 403 fragment for htmx and raises `PermissionDenied` otherwise.
- **Endpoint tests, one per denial shape** (`educator_interface/tests/test_denied_experience.py`):
  - a 404 for a cohort outside a cohort admin's grants, inside their organisation;
  - the 403 fragment for a create posted after the grant was removed;
  - the create-cohort control absent for a cohort viewer;
  - a Playwright test that the 403 fragment swaps into place.
- **Course detail leaks** (`test_organisation_isolation.py`): a cohort-scoped educator sees neither the rows of another cohort's direct registrations nor another cohort in either course-detail panel.
- `test_config_authorisation.py` stays as it is. Every test that uses the old role strings, and the `_organisation_staff_user` helpers in `reports/tests/test_views.py` and `test_admin.py`, is renamed. `test_roles.py`'s subset assertions now compare `cohort_viewer` with `cohort_admin`.

## Open questions

Each has a default the spec uses. The user can overrule any of them.

- A cohort admin may not edit a cohort's name or description. Default: no.
- `set_educator_active` applies the same self and last-organisation-admin guards as role removal. Default: yes.
- The checked path can assign only roles with an `assign_<role>` string in `registry.PERMISSIONS`. A downstream custom role such as `senior_ta` stays assignable only through the raw utilities and the admin. Default: accept that.
- `senior_ta` keeps its key in `demodev.py`. Default: yes.
- Superusers pass every `can` check. Default: yes.
- Operators can't deactivate an `Educator` before spec 9 ships a screen. Default: accept that; the Django admin gets nothing.

## Success criteria

- `rg '"(organisation_staff|instructor|ta)"' freedom_ls config` finds no role keys.
- `uv run manage.py validate_role_permissions` passes.
- `uv run manage.py makemigrations --check` reports no changes.
- After `migrate`, no assignment row has an old key, and every active organisation or cohort grant holder has an active `Educator`.
- An organisation admin with no superuser flag can create a cohort in their organisation through the interface, and a cohort admin gets no create control.
- A `site_admin` without superuser sees every organisation on the site and has cohort capabilities through `can`.
- Deactivating an `Educator` makes that organisation 404 for the user, and reactivating it restores access with no change to any assignment row.
- Removing the last `site_admin`, or an organisation admin removing the last organisation admin, raises `RoleChangeRefused`.
- A denied htmx action shows the 403 fragment in place of the form.
- `rg "has_perm" freedom_ls/panel_framework` finds nothing.
- Both course-detail panels show a cohort-scoped educator only rows from their own cohorts.
- `uv run pytest` passes, including the matrix and completeness tests.
