# Implementation plan — express interest survives sign-in

## The bug

An anonymous visitor on a coming-soon course detail page clicks **"I'm
interested"**, signs in, and lands on
`/interest/courses/<slug>/express-interest/` with **HTTP 405**.

The chain, confirmed end to end:

1. `freedom_ls/learner_interface/templates/learner_interface/course_detail.html:140-145`
   renders the express-interest CTA for everyone who is not registered —
   anonymous visitors included. The partial
   (`freedom_ls/course_interest/templates/course_interest/partials/express_interest_cta.html:34-40`)
   `hx-post`s to `course_interest:express_interest`.
2. That view is `@login_required` then `@require_POST`
   (`freedom_ls/course_interest/views.py:21-23`). `login_required` is
   outermost, so an anonymous POST returns 302 to
   `/accounts/login/?next=/interest/courses/<slug>/express-interest/`.
3. htmx follows the 302 inside its XHR and swaps the entire allauth login page
   into `#express-interest-cta-<slug>` (`hx-swap="outerHTML"`). That is the
   "sign-in form on the course page" from the report — no sign-in form is
   authored into the detail template.
4. Sign-in succeeds. allauth's `NextRedirectMixin` checks only host safety, not
   whether the target accepts GET, so the browser GETs a `@require_POST`
   endpoint → **405**.

So there are two defects behind one click: the `next` handed to the login page
is a POST-only URL, and the redirect is delivered in a form htmx mishandles.

The codebase already names the thing that broke: *"deferred login — user intent
survives authentication"* (`freedom_ls/accounts/tests/test_deferred_login.py:1`).
The GET-safe siblings `learner_interface:initiate_course_access` and
`course_applications:apply` are immune, and `freedom_ls/learner_interface/views.py:540-541`
already carries a comment warning that the coming-soon `cta_url` is POST-only
and "redirecting the browser there would 405". The interest endpoints never got
that protection.

## Target behaviour

The click survives the sign-in. After authenticating, the visitor is back on
the course detail page, the CTA already reads **Interested**, and the
`CourseInterest` row exists.

### Task 1 — the failing test (RED)

Add a full round-trip to `freedom_ls/accounts/tests/test_deferred_login.py` —
the file that owns this concept.

Take `client` (unauthenticated by default) and `mock_site_context` — the
latter is mandatory for site-aware models, and `CourseInterest` is one.

Send this POST **without** the `HX-Request` header. Task 4 changes the htmx
response from `302` + `Location` to `204` + `HX-Redirect`, so a round-trip test
that read `Location` off an htmx request would go green at RED and then break at
GREEN. The non-htmx branch stays a plain 302 either side of the fix, which is
what makes this test a stable RED→GREEN witness. The htmx response shape is
pinned separately in Task 4.

```
course = CourseFactory(visibility=CourseVisibility.COMING_SOON)
response = client.post(express_interest_url)
next_url = _next_param(response["Location"])
client.force_login(user)
followed = client.get(next_url)

assert followed.status_code != 405
assert CourseInterest.objects.filter(user=user, course=course).exists()
assert followed redirects to learner_interface:course_detail
```

Confirm it fails today with 405 before touching any view. It does:
`login_required` is htmx-unaware and always sets `next` to
`request.get_full_path()` — the POST-only URL itself — so the final GET hits
`@require_POST` head-on.

### Task 2 — GET-safe landing view

`freedom_ls/course_interest/urls.py` — new entry alongside the two partials:

```python
path(
    "courses/<slug:course_slug>/deferred-express-interest/",
    views.deferred_express_interest,
    name="deferred_express_interest",
),
```

`freedom_ls/course_interest/views.py`:

```python
@login_required
def deferred_express_interest(request: HttpRequest, course_slug: str) -> HttpResponse:
    """Where a deferred-login express-interest click lands after sign-in.

    GET-safe by design: login_required sends anonymous visitors to the login
    page with this URL as next, and the browser returns to it with a GET.
    """
    course = get_object_or_404(Course, slug=course_slug)
    raise_404_if_hidden_unregistered(request.user, course)
    if course.visibility == CourseVisibility.COMING_SOON:
        CourseInterest.objects.get_or_create(user=request.user, course=course)
    return redirect("learner_interface:course_detail", course_slug=course.slug)
```

A GET that mutates is the established shape here —
`learner_interface:initiate_course_access` (`freedom_ls/learner_interface/views.py:525`)
is a `@login_required` GET that creates a `LearnerCourseRegistration` for
exactly this reason.

A course that stopped being coming-soon between the click and the sign-in
records nothing and still lands on the detail page. That mirrors
`initiate_course_access`'s coming-soon fallback rather than the POST endpoint's
422 — by then there is no CTA left to re-render, so there is no validation
error to report.

### Task 3 — htmx-aware auth redirect helper

Add to `freedom_ls/accounts/utils.py` — the app's existing "shared helpers"
module, which already holds request-adjacent helpers like `get_client_ip` and
`get_signup_policy_for_request`. Do **not** create a new module for one
function: `freedom_ls/accounts/middleware.py:97-102` already imports from
`.utils` locally, inside `__call__`, "to avoid app-loading order issues", so
Task 5 adds one name to that existing local-import line rather than inventing
the same workaround again for a second module.

```python
def redirect_to_auth(
    request: HttpRequest,
    *,
    next_url: str | None = None,
    auth_url: str | None = None,
) -> HttpResponse:
    """Send a visitor to an auth page, optionally returning them to next_url.

    htmx follows a 302 inside its XHR and swaps the target's HTML into the
    element that made the request, so a login page ends up inside a button.
    An htmx request gets 204 + HX-Redirect and the browser really navigates.

    next_url must be GET-safe: the browser returns to it with a GET.
    auth_url defaults to settings.LOGIN_URL, matching login_required.
    """
    if next_url:
        target = redirect_to_login(next_url, auth_url).url
    else:
        target = resolve_url(auth_url or settings.LOGIN_URL)
    if request.headers.get("HX-Request"):
        response = HttpResponse(status=204)
        response["HX-Redirect"] = target
        return response
    return redirect(target)
```

204 rather than 422: the house rule in `CLAUDE.md` and `ds:htmx` reserves 422
for HTMX *validation* errors. This is not one — it is a redirect the browser
must perform, so it takes the `HX-Redirect` shape `panel_framework` already
uses.

`next_url` is always built server-side with `reverse()`, and the middleware
case passes `request.get_full_path()` — the current request's own path. No
caller may pass a `next` taken from user input without running it through
`url_has_allowed_host_and_scheme` first; `fls-dev:registration` calls an
unvalidated `?next=` redirect an open-redirect bug, and
`freedom_ls/accounts/views.py:60-68` is the existing validator to reuse if that
ever changes.

### Task 4 — rewire the two interest endpoints

In `freedom_ls/course_interest/views.py`, drop `@login_required` from
`partial_express_interest` and `partial_remove_interest` (leaving
`@require_POST` outermost) and branch on the anonymous case explicitly, so the
`next` handed out is one chosen for the purpose rather than the current URL:

- `partial_express_interest`, anonymous →
  `redirect_to_auth(request, next_url=reverse("course_interest:deferred_express_interest", kwargs={"course_slug": course_slug}))`
- `partial_remove_interest`, anonymous →
  `redirect_to_auth(request, next_url=reverse("learner_interface:course_detail", kwargs={"course_slug": course_slug}))`
  — an anonymous visitor has no interest to remove, so there is nothing to
  defer; return them to the page.

Resolve the slug *after* the anonymous branch. An anonymous POST for any slug —
hidden, coming-soon, or nonexistent — then gets an identical login redirect and
confirms nothing about the course, which is what happens today.

Update the two existing tests at
`freedom_ls/course_interest/tests/test_views.py:280-306`. They currently assert
only `302` and `"/accounts/" in Location`; they must now assert **204 +
`HX-Redirect`** for an htmx request and a plain **302** for a non-htmx one, and
pin the `next` target in both.

These are where the htmx response shape gets pinned — Task 1's round-trip
deliberately stays on the non-htmx branch.

`TestExpressInterestGetRejected` (`freedom_ls/course_interest/tests/test_views.py:240-268`)
stays exactly as it is — a bare GET on a POST-only partial is still 405, and
that is correct.

### Task 5 — carry intent through registration completion

`freedom_ls/accounts/middleware.py:117` returns
`redirect(reverse("accounts:complete_registration"))` and drops `next`, so a
signed-in-but-incomplete user loses the same intent — silently, instead of
405-ing. `complete_registration_view` already accepts and re-emits `next`
safely (`freedom_ls/accounts/views.py:60-68` and `:107-112`), so only the
middleware changes:

```python
completion_url = reverse("accounts:complete_registration")
if request.method in ("GET", "HEAD"):
    return redirect_to_auth(
        request, next_url=request.get_full_path(), auth_url=completion_url
    )
return redirect_to_auth(request, auth_url=completion_url)
```

Extend the existing local-import line at `freedom_ls/accounts/middleware.py:97-102`
with `redirect_to_auth`; do not add a module-scope import.

The method guard is load-bearing: carrying a POST path as `next` would recreate
the very 405 this branch fixes.

### Task 6 — harden the sibling auth branches

`course_applications:apply`, `course_applications:status` and
`learner_interface:initiate_course_access` are GET-safe and structurally sound.
The gap is assertions — `freedom_ls/course_applications/tests/test_views.py:54`
and `:300` check only `"/accounts/" in Location`.

Tighten those two, and extend `freedom_ls/accounts/tests/test_deferred_login.py`
to cover:

- anonymous POST to `apply` → login with `next` = the apply URL → after
  sign-in the GET renders the confirmation page and creates no application.
- anonymous request for `apply`, `initiate_course_access` and `status` against
  a **hidden** course → login redirect, never a 404. No enumeration signal.
- anonymous `initiate_course_access` on a coming-soon course → after sign-in,
  redirect to the detail page with no `LearnerCourseRegistration` created.
- `application_status` after deferred login: owner 200, non-owner 404.
- repeat submissions stay idempotent on both interest and application.

Fix whatever these turn up. If they all pass first time, the tests are the
deliverable.
