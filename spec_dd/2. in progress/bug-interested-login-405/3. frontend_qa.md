# Frontend QA — express interest survives sign-in

Browser QA for the anonymous → sign-in → interested journey and the branches
around it. Use the `playwright` MCP server.

## §0 Setup

```bash
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL: `http://127.0.0.1:$PORT`

**Dev credentials** (from `.claude/fls-dev/config.md`):
`demodev@email.com` / `demodev@email.com`

### Data needed

Ask the `fls-dev:qa-data-helper` agent to create anything missing:

1. A course with `visibility = coming_soon` and a known slug. Note the slug as
   `<COMING_SOON_SLUG>` — every step below uses it.
2. A second course with `visibility = hidden` and a known slug,
   `<HIDDEN_SLUG>`, that the QA user is **not** registered for.
3. A published, free course with a known slug, `<PUBLISHED_SLUG>`.
4. A learner account that is **not** the dev admin and has **no**
   `CourseInterest` for `<COMING_SOON_SLUG>` — call it the QA learner. Note its
   email and password.
5. Confirm no `CourseInterest` row exists for the QA learner on
   `<COMING_SOON_SLUG>` before each run of Test 1, and delete it between runs.

Use a fresh incognito/private context for every "anonymous" step — a leftover
session silently turns an anonymous test into a signed-in one.

---

## Test 1 — the reported bug: interest survives sign-in

The core regression. This is the exact journey from the report.

1. Anonymous, go to `/courses/<COMING_SOON_SLUG>/detail/`.
2. **Expect:** the right-hand panel shows "Coming soon", the subtext
   "Register your interest and we'll let you know when the course is ready.",
   and a primary **"I'm interested"** button.
3. Click **"I'm interested"**.
4. **Expect:** the whole browser navigates to the sign-in page — a real page
   load at `/accounts/login/?next=...`, with full site chrome.
   **Fail if:** a sign-in form appears *inside* the right-hand panel while the
   course page stays behind it. That is the original bug's first symptom (htmx
   swapping the login page into the CTA slot).
5. Check the address bar: `next` must point at a
   **`deferred-express-interest`** URL, not `express-interest`.
6. Sign in as the QA learner.
7. **Expect:** you land back on `/courses/<COMING_SOON_SLUG>/detail/`.
8. **Expect:** the panel now shows a green check + **"Interested"** and a quiet
   **"Remove interest"** control.
   **Fail if:** you see an HTTP 405 page, a "Method Not Allowed" message, or a
   raw `/interest/...` URL in the address bar.
9. Confirm the copy does **not** promise a notification email — "Interested"
   and "Remove interest" only.

## Test 2 — already signed in (the path that always worked)

Confirm the fix did not disturb the normal case.

1. Signed in as the QA learner, first remove the interest from Test 1 (click
   **"Remove interest"**).
2. **Expect:** the panel swaps in place, without a page reload, back to
   **"I'm interested"**.
3. Click **"I'm interested"**.
4. **Expect:** the panel swaps in place, without a page reload, to
   **"Interested"**. No navigation, no login page.
5. Reload the page.
6. **Expect:** still **"Interested"** — the state persisted, it was not just a
   client-side swap.

---

## Test 3 — repeat clicks and double submission

1. Signed in and already interested, click **"Remove interest"** then
   **"I'm interested"** three times in quick succession.
2. **Expect:** the panel ends in a consistent state matching the last click. No
   error toast, no duplicated buttons, no stacked CTA blocks.
3. Reload.
4. **Expect:** the reloaded state matches what the panel showed.
5. Ask `fls-dev:qa-data-helper` to confirm exactly **one** `CourseInterest` row
   exists for this learner and course — not several.

---

## Test 4 — remove interest while signed out

The other POST-only endpoint. An anonymous visitor has nothing to remove, so
this should degrade politely rather than 405.

1. Signed in, express interest in `<COMING_SOON_SLUG>` so the "Remove interest"
   control is on the page.
2. Sign out **in a second tab**, then return to the first tab (still showing
   the stale "Interested" panel) and click **"Remove interest"**.
3. **Expect:** the browser navigates to the sign-in page.
   **Fail if:** a 405 page, or a login form swapped into the panel.
4. Sign back in.
5. **Expect:** you land on `/courses/<COMING_SOON_SLUG>/detail/` and the
   interest is **still there** ("Interested"). Signing in must not have removed
   it — the removal was never authorised.

## Test 5 — the course stopped being coming-soon mid-flow

1. Anonymous, open `/courses/<COMING_SOON_SLUG>/detail/` and click
   **"I'm interested"** to reach the sign-in page. **Do not sign in yet.**
2. In another browser (as admin, `/admin/`), flip that course's visibility to
   **published**.
3. Return to the sign-in page and sign in.
4. **Expect:** you land on the course detail page showing the normal
   enrolment CTA ("Enrol for free" / "Start course"), not an error.
   **Fail if:** 405, 422, or a stack trace.
5. Ask `fls-dev:qa-data-helper` to confirm **no** `CourseInterest` row was
   created — the course was no longer coming soon.
6. Set the course back to **coming soon** afterwards.

## Test 6 — hidden courses leak nothing (enumeration)

An anonymous visitor must not be able to tell a hidden course from a
nonexistent one.

1. Anonymous, go to `/courses/<HIDDEN_SLUG>/detail/`. **Expect:** 404.
2. Anonymous, go to `/courses/definitely-not-a-real-course-xyz/detail/`.
   **Expect:** 404. The two pages must look identical.
3. Anonymous, go to `/applications/apply/<HIDDEN_SLUG>/`.
   **Expect:** redirect to the sign-in page — **not** a 404, and not an error
   naming the course.
4. Anonymous, go to `/courses/<HIDDEN_SLUG>/access/`.
   **Expect:** redirect to the sign-in page.
5. Sign in as the QA learner (who is not registered for the hidden course) and
   let the `next` redirect run.
6. **Expect:** a 404 at that point. The 404 arrives only *after*
   authentication, never before.

## Test 7 — apply and self-registration still round-trip

The sibling flows the fix must not have disturbed.

1. Anonymous, go to `/courses/<PUBLISHED_SLUG>/detail/`.
2. Click the enrolment CTA ("Enrol for free").
3. **Expect:** the sign-in page, with `next` pointing at the course's
   `/access/` URL.
4. Sign in as the QA learner.
5. **Expect:** you are enrolled and land inside the course player on the first
   item — not back on the detail page, not a 405.
6. If an application-gated course exists in this environment, repeat with it:
   anonymous → "Apply now" → sign-in → **expect** the apply *confirmation*
   page, with an explicit "Apply" button still to press.
   **Fail if:** the application is created automatically by the redirect
   without you confirming.

## Test 8 — signing up as a brand new user mid-flow

The signup arm of the same funnel.

1. Anonymous, go to `/courses/<COMING_SOON_SLUG>/detail/` and click
   **"I'm interested"**.
2. On the sign-in page, follow the **Sign up** link.
3. Register a brand new email address.
4. Complete email verification (in dev, the confirmation link is printed to the
   `runserver` console).
5. **Expect:** no 405 anywhere in the chain, and no login form rendered inside
   a course panel.
6. Note where you land. Record the outcome either way — whether the interest
   survived the signup detour or the user simply ends up signed in on the site.
   Losing intent across the *signup* arm is acceptable; a 405 or a broken page
   is not.

---

## Test 9 — an existing account tries to sign up again

1. Anonymous, from the coming-soon CTA, reach the sign-in page and follow
   **Sign up**.
2. Enter the QA learner's **existing** email address and submit.
3. **Expect:** a neutral response that does not confirm whether that email is
   already registered (`ACCOUNT_PREVENT_ENUMERATION` is on).
   **Fail if:** an error explicitly says the account already exists.
4. **Expect:** no 405, no unstyled page, no traceback.

---

## Test 10 — invalid sign-in credentials in the middle of the flow

1. Anonymous, from the coming-soon CTA, reach the sign-in page.
2. Enter a wrong password and submit.
3. **Expect:** the sign-in page redisplays with a validation error, still
   carrying the same `next` value.
4. Sign in correctly on the second attempt.
5. **Expect:** you still land on the course detail page showing
   **"Interested"** — the failed attempt did not lose the intent.
   **Fail if:** you land on the site home page instead.

## Test 11 — small screens

1. Resize to a phone viewport (approx. 390 × 844).
2. Repeat Test 1 steps 1–8.
3. **Expect:** the CTA panel appears above the course content (it is
   `order-first` on mobile), the sign-in navigation works the same way, and the
   "Interested" state is legible and not clipped.

## Reporting

For each test record: pass / fail, the URL at each navigation, and a screenshot
of any failure. For a failure, note the HTTP status shown and whether the
sign-in form appeared as a full page or inside the course panel — that
distinction separates the two defects behind this bug.
