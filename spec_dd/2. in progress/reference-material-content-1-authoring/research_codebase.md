# R2: codebase touch points for reference-material-content-1-authoring

Builds on `research_content_loader.md` (R1); nothing from it is repeated. Facts and risks only, no plan. Paths are repo-relative. Vocabulary as in R1: collection item = a `ContentCollectionItem` row; part placement = a course's collection item whose child is a `CoursePart`.

## 1. Do the cross-file rules need `_ParsedByPath`?

`freedom_ls/content_engine/validate.py`:

- `validate(path)` parses only `get_all_files(path)`. When `path` is a single course directory, a part reached through `../` is not in `all_parsed`. `_ParsedByPath.get(key)` (line ~744) parses it from disk on first use; a file that is missing or fails to parse gives `None`, and the `ValueError` is swallowed (the per-file pass owns that error).
- `_ParsedByPath.children_of(part)` calls `collection_children(part)`, which for a part with no `children:` runs `auto_discovered_children`, which calls `parse_single_file` on every file beside the part. That raises `ValueError` for an unparsable file; `_nested_list_errors` catches it and reports it. Any new rule that lists a part's topics through `children_of` has to catch the same `ValueError`, or one broken sibling aborts the whole validate run instead of becoming a reported error.
- Rule "part in both `children:` and `reference:`": compares resolved keys only (`resolve_author_path(course.file_path, entry.path)`). It needs no parsing of the part, so it does not need `_ParsedByPath`. The same key comparison already powers `_repeated_indices` / `validate_children_lists` and does not depend on the target existing.
- Rule "reference entry points at a non-part file": needs the target's `content_type`, so it needs `_ParsedByPath.get` for a target outside the validated path. Same pattern as `_direct_entry_errors`, which skips a target of `None`, leaving the unknown-child check to report it.
- Rule "no due keys on a topic inside a reference part": needs the part's children and each child's parsed model. A part outside the validated path has neither in `all_parsed`, so it needs `_ParsedByPath.children_of(part)` plus `.get(child_key)`. Without it, `validate(<course dir>)` of a course that references a `../` part would pass, while `save_content_to_db` (which parses the whole root) would fail: the two check lists would disagree.
- `save_content_to_db` runs `validate_children_lists`, `validate_due_date_placements` and `validate_question_sections(..., loaded_root=path)` (content_save.py ~1062). `validate_question_sections` shows the other mode: with `loaded_root`, lookup is a plain dict over `all_parsed`, and a target outside the root is reported as "not loaded with the form". A reference rule run in the save path has all files in `all_parsed`, so the dict form is enough there; `validate(path)` needs the disk-reading form. This is the one existing precedent for a rule with both modes (the `lookup` callable at validate.py ~976).
- A topic's due keys live in its own frontmatter (`schema.Topic` includes `DueDateFields`; `Activity` does not). Auto-discovered part children can also be `ACTIVITY` or nested directories whose main file is a topic or form. "Not a `Topic`" for a part child therefore also catches `Activity` files and `Form` directories; the idea names only Form and nested part, so an `Activity` child is a case the rule wording does not cover.
- No existing rule checks the types of a part's children. `_DUE_DATE_CHILD_TYPES` (TOPIC, FORM) is the only type set near it, and it governs due keys, not membership.
- Shared-part risk (from the idea, now concrete): a part with due keys on topic files, placed in course A's `children:` and also named in course B's `reference:`, fails B's rule on every run. Because validation is whole-root, that failure blocks the whole load, not just B.
- Both `_nested_list_errors` and `_direct_entry_errors` take an entry typed `Child`. A reference entry of a different class would not reach them, so existing due-date placement code does not need to change, but any new helper that wants `item.children` and `item.reference` together must handle `Course` only (`CoursePart` has no `reference:` in the idea).

## 2. Where a `reference:` entry pointing at a non-part file is caught

- Pydantic can only check the shape of a `reference:` entry (path string, no extra keys). The target's `content_type` is in another file, so the schema cannot see it. "Not a part" is a cross-file rule in `validate.py`, in the same family as `_direct_entry_errors` ("a due date on a {type} placement") and `_section_problem` (`_SECTION_TYPES`).
- A path that names nothing: today `children:` leaves it to the load, which raises `ValueError("Collection '...' names a child at ... that was not loaded")` in the `collection_children` loop of `save_content_to_db`. There is no validator-side unknown-child check in `validate()` (the docstring of `validate_due_date_placements` mentions one "unknown-child check", but the only enforcement found is the loader's `ValueError`). A `reference:` entry that names nothing would need either a validator error or the same loader `ValueError`; neither exists for a second list.
- A path inside a `_`/`.`-prefixed directory, or outside the loaded root: `is_loader_skipped` and the root test in `_section_problem` are the precedents (`SECTION_SKIPPED_FIX`, `SECTION_OUTSIDE_FIX`). The `children:` loop has no such check beyond the loader's "was not loaded".
- Models of `content_by_path` values: it holds Topic, Activity, Course, CoursePart and Form rows (`save_content_to_db` ~1107-1150). A loader-side `isinstance(row, CoursePart)` check (like the `isinstance(form, Form)` check for `application_form`, content_save.py ~1259) is the existing pattern if the check is made at save time.
- The offline copy `claude_plugins/fls-content/validate/validate.py` has its own copy of every function above; a rule added in one place needs the matching code and a test in `claude_plugins/fls-content/validate/tests/test_validator.py`.

## 3. What the course to part collection item has hanging off it

`freedom_ls/content_engine/models/courses.py`:

- `ContentCollectionItem(SiteAwareModel, TimestampedModel)`: `collection_type` and `child_type` are FKs to `DjangoContentType` (CASCADE); `collection_id` and `child_id` are plain `UUIDField`s. A course to part row has `collection_type=Course`, `child_type=CoursePart`. Its own columns carry due values (`due_date`, `due_time`, `due_days_after_registration`, `no_due_date`).
- `CoursePartChildDueDate.part_collection_item` FK to the course to part row, `on_delete=CASCADE`, `related_name="child_due_dates"`. Its `collection_item` FK (the part to child row) is `CASCADE`, `related_name="+"`. Unique on `(part_collection_item, collection_item)`. Deleting a course to part row cascades every `CoursePartChildDueDate` whose `part_collection_item` it is; the part's own part to topic rows are untouched (they belong to the part).
- `freedom_ls/deadlines/models.py` FKs to `ContentCollectionItem`, all `related_name="+"`:
  - `CohortDeadlineOverride.collection_item` (line ~83): `null=True`, `CASCADE`.
  - `LearnerDeadlineOverride.collection_item` (line ~161): `null=True`, `CASCADE`.
  - `DeadlineExtension.collection_item` (line ~523): `null=True`, `CASCADE`. This model is not named in the idea's cleanup ("deadline overrides on it and its part-placement due dates"), but it cascades the same way when its row is the one deleted, so a deleted course to part row also removes any `DeadlineExtension` that targets it. Its `target_kind` is `ExtensionTarget`; its `reason` and `granted_at` are learner-facing audit data.
  - A `collection_item` of `None` on these means "the whole course", so a deleted collection item is not folded into a course-wide row; the rows are removed.
- Progress FKs to `ContentCollectionItem` (`freedom_ls/learner_progress/models.py`), all `null=True`, `SET_NULL`: `TopicProgress.collection_item` (~76), `CourseProgress.last_accessed_item` (~153, `related_name="+"`), `CourseFormAttempt.collection_item` (~273, `related_name="form_attempts"`). These are normally set to part to topic or course to topic rows, but `CourseProgress.last_accessed_item` can hold a course to part row (a part is a navigable step in the flat index only through its children, so this is unlikely but not constrained). A delete nulls the pointers rather than removing progress.
- `TopicProgress.topic` and `CourseProgress.course` are `PROTECT`, so the cleanup does not threaten learner progress. Progress percentages are not recomputed (answers.md).
- Deleting through the queryset `ContentCollectionItem.objects.filter(...).delete()` collects the cascades above through Django's collector; `.delete()` on a queryset of the default manager is site-filtered by `SiteAwareManager` when a request/site context exists. The loader runs with no request, so, as the comment at content_save.py ~1328 says, "the site goes on every write and delete by hand" (`site=site` in the existing `CoursePartChildDueDate` delete, line ~1356).
- Signals: `collection_items_synced` is sent after the loop, with `created`, `written`, `moved`. `deadlines/signals.py` `carry_over_deadline_overrides` is driven by `moved`. There is no `post_delete`/`pre_delete` handler for `ContentCollectionItem` found in these files; the cleanup deletion would trigger none. It runs outside any signal consumer of `written`.
- `moved_children(site, written, loaded_collections)` (R1 section 1) runs after the loop over `written`. The cleanup placement relative to it matters: if a part is moved from `children:` to `reference:` and a topic of that part is also placed elsewhere in the same course, `_left_behind` reads `course.viewable_collection_items()`, which still includes the stale part until it is deleted.
- Only the course that lists the part is cleaned: the cleanup must filter on `collection_id=<that course>`, `collection_type=Course`, `child_type=CoursePart`, `child_id=<part>`. Another course's rows for the same part have different `collection_id`.

### How `content_save` prints today

`freedom_ls/content_engine/management/commands/content_save.py`:

- Per-row messages use `logger.info` (`Saved Topic: ...`, `Added <Class> '<title>' to <Class> '<title>' (order=N)`, line ~1312). `logging` is not configured to display at default CLI level in this command (`command()` uses `logger.info("Validating content...")`), so these are diagnostic, not user output.
- User-visible output is `click.echo` (from `djclick`/`click`): cache notices and "Wrote N and removed M file(s) under ..." (~1083-1089), `"✓ Successfully saved all content for site: {site_name}"` (~1378), and the final `Images: N seen (...)` line (~1385). Image decisions use `click.echo("\n".join(lines))` (~1030).
- Tests of this output: `save_content_to_db` is called directly by tests, with `capsys`/`click` capture; the `"Wrote N and removed M file(s)"` line sets a precedent for a counted line naming what was removed. Nothing existing prints a per-course "removed" line; the nearest wording is the "removed" in the cache line.
- A removal message would sit with the other `click.echo` output (before the `✓ Successfully saved` line, or after) or in `logger.info`; only the former is visible in a normal run. CLAUDE.md says no logging unless asked.

## 6. Delete command, admin, base class, auto-discovery

- `freedom_ls/dev_tools/management/commands/danger_content_delete.py`: `models_to_delete` list (lines 44-57) in order: Forms, Form Pages, Form Content, Form Questions, Question Options, Topics, Activities, Courses, Course Parts, Articles, Collection Items, Files. Counts use `model.objects.all().count()`, deletes use `model.objects.all().delete()`, all in one `transaction.atomic()`. A `CourseReferencePart` is not imported or listed; whether it is deleted depends on cascade. If both FKs are `CASCADE`, the Courses/Course Parts deletes remove it, and it is simply not in the count line. If `course_part` were `PROTECT`, the `Course Parts` delete would raise. `CourseReferencePart` must be listed before `Courses` and `Course Parts` if it is to be counted and deleted explicitly (as for `ContentCollectionItem`, listed last because it has no FK to the models above). The command has no PROTECT handling beyond the ordering comments.
  - The idea says the model is "counted and deleted by `danger_content_delete`". There is a test for this command: not located in this research; its `models_to_delete` expectations need a read.
- `freedom_ls/content_engine/admin.py`:
  - `CourseAdmin` (line 186): `inlines = [ContentCollectionItemInline]` only. `ContentCollectionItemInline` is a `GenericTabularInline` (`ct_field="collection_type"`, `ct_fk_field="collection_id"`, `can_delete=False`, `extra=1`). `readonly_fields` of the course include `categories`, `organisations`, `shared_with`, `audience`; `has_delete_permission` is False.
  - `CoursePartAdmin` (line 265): `inlines = [ContentCollectionItemInline]`; `readonly_fields = ("slug",)`; delete disabled.
  - `CoursePartChildDueDateInline` (line 283) is a read-only `TabularInline` on `ContentCollectionItemAdmin` (`max_num=0`, `can_delete=False`, `has_add_permission` False). It is the precedent for a loader-written, read-only inline. `ContentCollectionItemAdmin` has `has_delete_permission` False.
  - Every inline and admin here is read-only where the loader writes the data; no existing admin lets a human add a placement meaningfully (`ContentCollectionItemInline` has `extra=1` but readonly due fields). A `CourseReferencePart` inline on `CourseAdmin` has to follow `SiteAwareModelAdmin` (imported from `freedom_ls.site_aware_models.admin`), and `fls-dev:admin-interface` for read-only/`can_delete` choices.
  - There is no `CourseReferencePartAdmin` and no `admin.register` for a new model yet.
- `freedom_ls/site_aware_models/models.py`: `SiteAwareModelBase` (line 132) has `site = ForeignKey(Site, on_delete=PROTECT)`, `objects = SiteAwareManager()`, and a `save`/`full_clean` that fills `site` from the request thread-local if unset; with no request (the loader), `site` must be passed explicitly. `SiteAwareModel` (line 166) adds `id = UUIDField(primary_key=True, default=uuid4)`. `TimestampedModel` is separate and composed (`ContentCollectionItem(SiteAwareModel, TimestampedModel)`; `CoursePartChildDueDate(SiteAwareModel)` has no timestamps). The idea names `SiteAwareModel` only, matching `CoursePartChildDueDate`. `SiteAwareManager` filters by the current site when a request exists, so loader writes use `site=site` and `_base_manager` or explicit filters, as the existing code does.
  - Unique constraints on site-aware models in this app include the site (`unique_course_part_slug_per_site`); `CoursePartChildDueDate`'s unique constraint (`cpcdd_one_value_per_child`) omits the site because its FKs already pin it. A `(course, course_part)` unique constraint would sit the same way.
- Auto-discovery skipping a `reference/` directory (`auto_discovered_children`, validate.py ~63): it skips only names starting `_` or `.` (`is_skipped_path`); there is no named-directory skip list. A `reference/` subdirectory is entered, and its direct files looked at (`for f in sorted(item.iterdir())`). A `reference/part.yaml`, `reference/course.md`, `reference/form.md`, or any `.md`/`.yaml` with `TOPIC`/`ACTIVITY` type placed directly in `reference/` is adopted. In the layout from the idea (`reference/1. regulations/part.yaml`), nothing sits directly in `reference/`, so nothing is adopted. The same function is the one place to exclude it, and it is shared by the validator, the loader, `_ParsedByPath.children_of`, and the offline validator copy; a change here has to land in both copies.
  - It is the same function used for a part's auto-discovered children, so a name-based skip of `reference` would also skip a topic directory or part named `reference` inside a part; the idea says "a course directory's `reference/`", so the skip would need to apply to the course's own directory only (it receives `collection_file`, and `collection_file.parent` for a course is the course directory; whether a file is a course or part is not visible without parsing `collection_file`, which the function does not do today).
  - `get_all_files`/`is_loader_skipped` still loads every file under `reference/`, so reference parts and their topics are saved as rows regardless (R1).
  - Also note: `auto_discovered_children` only matters when `children:` is empty; with `children:` listed, `reference/` is never consulted.

## 7. Conflicts with the SACAA specs

- `spec_dd/2. in progress/sacaa-compliance-content-versions-and-access-1-content-save-safety/` (now in progress, with a `todo.md`; it was in `1. next` when the idea was written). Its idea changes:
  - `content_save` takes several paths and one site, so `save_content_to_db(path, site_name)` and `content_key`/`file_path` relative to one path become multi-path. A `reference:` entry that must be "under the loaded `content_save` root" has to be re-stated for several roots; `_section_problem`'s `loaded_root` handling and `save_content_to_db`'s `path` argument are the same seam.
  - `--generate-uuids` flag and a uuid-missing failure before any write; the idea says the check sits "only in the save" and the signature is open ("takes the flag and defaults it to True").
  - A git clean-tree check in the command, and a recorded HEAD commit per path.
  - The placement-check list in `save_content_to_db` (`validate_children_lists`, `validate_due_date_placements`, `validate_question_sections`) is where both specs add or touch checks. Two branches editing that list conflict textually.
  - `demo_content/` must carry all uuids so it loads with the flag off. A new demo course for this spec must therefore carry uuids on the course, parts and topics (R1 notes `course.md` needs a uuid), or it breaks the demo load once that spec lands.
- `spec_dd/1. next/sacaa-compliance-content-versions-and-access-2-retire-removed-content/idea.md`:
  - Adds a retired state on `Course`, `CoursePart`, `Topic`, `Activity`, `Article`, `Form` and others, set when a uuid is absent from the run; a retired `Course` leaves the learner's course list. `CourseReferencePart` rows pointing at a retired part or course are not discussed; the reconcile of reference rows ("rows not named by the load are deleted for the courses in that load") is replace semantics, the reverse of retire-never-delete for authored content. The two specs disagree on prune versus retire for the `reference:` list only in that this idea deletes `CourseReferencePart` (derived, not authored content) and does not retire anything; the retire idea marks `ContentCollectionItem` left-behind rows as an open question ("Recommend: a collection item whose child is retired is skipped when outlines are read, but the row itself is not given a retired state").
  - That open question is the same row this spec deletes: it leaves left-behind rows in place; this spec deletes the one course to part row for a part newly in `reference:`. If retire lands first and chooses "hide, do not delete", the cleanup here remains a delete of a live row, not a left-behind one.
  - The retire spec states "`danger_content_delete` stays the only thing that deletes content" and "Never deleted". The cleanup here is a delete performed by `content_save` of a derived row (`ContentCollectionItem`), with cascades into `CohortDeadlineOverride`, `LearnerDeadlineOverride`, `DeadlineExtension` and `CoursePartChildDueDate`. Those are learner/educator-entered data, which the retire spec's "kept for audit" principle treats as protected for retired content, though not for a derived collection item.
  - "One run covers all of the site's content": the retire spec makes absence-from-run meaningful per site; `CourseReferencePart` reconcile is per course in the load, so a course not in the run keeps its rows, consistent with `loaded_course_ids` (content_save ~1331).
  - Both change `save_content_to_db` after the placement loop (retire pass) and the schema file; textual conflict is likely around content_save.py ~1268-1376 and `validate.py` `collection_children`.
- The idea's own "Collision" line already names both; the only one currently in flight is `-1-content-save-safety`.

## 8. Other facts not in R1

- `Course` schema (`freedom_ls/content_engine/schema.py` line 369) has `extra="forbid"`, `children: list[Child]` (line 376) and `CoursePart.children` (line 553). `Child(PlacementDueDate)` (line 199) with `PlacementDueDate` in `content_base/schema.py` (line 128, `extra="forbid"`, `_no_due_date_stands_alone`, `holds_due_value`). A new entry class that omits `DueDateFields` rejects due keys at parse time through `extra="forbid"`, with pydantic's "Extra inputs are not permitted" wording, not the placement-error layout used by the cross-file rules.
- `save_course` excludes `{"children", "categories", "dashboard_category", "price", ...}` from the model fields (content_save.py ~619); `save_course_part` excludes `{"children"}` (~666). A `reference` field on `Course` has to be in the first set or `save_with_uuid` raises `ValueError`.
- The loader writes `CourseReferencePart` after both the course and the referenced part exist. `collections_data` is courses first, then parts (the `for item in grouped.get(COURSE)` loop runs before parts, content_save ~1129), which is why the part-placement due-date pass is a second pass after the loop (~1324). Reference rows can use the same second-pass timing or `content_by_path`, which holds all parts after saving.
