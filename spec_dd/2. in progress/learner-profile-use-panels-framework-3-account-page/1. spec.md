# Spec: every signed-in user edits their account on panels

Idea: `idea.md`. Answers: `answers.md`. Code facts: `research_codebase.md`.

## Purpose

The account page (`accounts:account_profile`) is a hand-built page with two plain forms, and the
email and password pages sit under it in a bottom link list. Public-profile editing
(`learner-public-profile-2-profile-and-page` on) adds panels to this area, so the area has to be
on the panel framework first. This spec moves name and profile picture editing onto panels in an
account area with its own shell and sidebar, and moves email and password management onto
panels on the same page, with framework actions that call allauth's forms and flows. It applies to every signed-in user: learners, educators and admins.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| account area | coined | The signed-in user's own settings pages that share the account shell and its sidebar: Personal details (name, profile picture, email addresses, password), and the sections later specs add. No existing term; "profile" is kept for the coming public profile. |
| account shell | coined | The page template every account-area page renders in. It extends `_base_interface.html` and uses that template's sidebar drawer on small screens. Distinct from the educator `_shell.html`. |

## Scope

In:

- A panel framework host for the account area in `accounts`, with one `ObjectViewConfig` section,
  Personal details, holding the Name, Profile picture, Email addresses and Password panels.
- The account shell and its sidebar, used by the Personal details page and, through the
  `allauth/layouts/manage.html` override, by the remaining allauth management pages (social
  connections, MFA, sessions), which it wraps in the header band, canvas and a card.
- Moving every panel form's submit buttons into the card footer: the inline record form (account
  and educator Name panels) and the Profile picture panel.
- Fixing the inline record form's extra space under the field row (bug B1 in the done spec
  `learner-profile-use-panels-framework-1-file-upload-actions`'s `qa_report.md`). This is the
  panel framework's only change; nothing account-specific goes into it.
- The header user menu, tests, upgrade notes, product docs and the parent idea's stale line.

Out:

- Public profile, work experience, completed courses and certificates panels (`learner-public-profile-*`).
- Enabling MFA, sessions or social accounts.
- Changing allauth's forms, flows, rate limits or emails. The email and password panels call them.
- `complete_registration`, `legal_doc`, login, signup, password reset, email confirmation and
  reauthentication: they keep the entrance layout. allauth builds reauthentication on
  `account/base_entrance.html`.
- The educator interface's own pages. Its sidebar cog keeps its "Account settings" label.

## Decisions

- **Labels.** The area is "Account". The sidebar lists Personal details (plus the optional allauth
  entries when enabled). The
  Personal details page's heading and document title are "Personal details". The header user
  menu item (`partials/header_bar_user_menu.html`) reads "Account". The page is not called
  "Profile", so the public profile keeps that word. These labels were checked against
  `fls-dev:domain-glossary` (no entry uses them) and `brand-guidelines` (sentence case).
- **Sections are sidebar entries, not tabs.** Each entry is its own page; a panel page is one
  `PanelStack`. Later specs add entries to the same sidebar list.
- **The sidebar is an `accounts` partial with plain links.** The framework's `sidebar_nav.html`
  links only panel sections, by `hx-get` into `#main-content`, and the optional entries are
  allauth pages.
- **A panel form's buttons are in the card footer**, right-aligned like Deactivate, never beside
  the fields (`fls-dev:panel-framework`, "Adding and editing records").
- **Email addresses are rows with their own actions.** No radio picks an address for shared
  buttons.
- **Confirmation.** Each account save shows the out-of-band toast from `partials/messages.html`
  ("Name saved", "Profile picture saved", "Profile picture removed") and swaps the header avatar
  out of band. The swap covers name saves too, which goes beyond the recorded answer, because the
  avatar shows the initials from the name when there is no picture. A response that carries the
  toast gets no framework error message (`fls-dev:panel-framework`, "Forms with a file field").
- **Removing a picture is an error-tone confirmation dialog** in `#app-modal`, per
  `fls-dev:panel-framework`. The upload form loses its "Remove" checkbox.
- **Own-object access only.** A refused submission never reaches `request.user` or the header,
  and nothing in a URL names a user.
- **No audit entries.** The audit log is organisation-scoped and a user's own account has no
  organisation.
- **Accounts code copies the educator pattern; it never imports `educator_interface`.**
  `LearnerNamePanel` and `EditLearnerNameAction` are the model to follow, not a dependency.

## Requirements

### Host, URLs and config (`freedom_ls/accounts/`)

- **Code layout follows the educator interface refactor.** The "Educator interface code layout"
  section of `spec_dd/1. next/roadmap.md` (parent `educator-interface-refactor`, first spec
  `educator-interface-refactor-1-scaffolding-and-common`) sets the structure; `accounts` uses the
  same one so the two hosts read alike:
  - One `panels/<area>/` package per sidebar section. This spec adds
    `accounts/panels/personal_details/`; later specs add their own sections (public profile, work
    experience) as sibling packages, not as modules inside this one.
  - An area holds only the modules from the effort's list that it has content for: `config.py`,
    `data_tables.py`, `data_table_panels.py`, `panels.py`, `instance_view.py` (a file, not a
    package), `actions.py`, `bulk_actions.py`, `filters.py`, `quick_view.py`. Personal details needs
    `config.py`, `panels.py`, `instance_view.py` and `actions.py`.
  - Code that more than one account area uses goes in `accounts/panels/common/`. Create it only
    when a second area needs the code; this spec has one area, so it has no `common/`.
  - Every `__init__.py` (`panels/`, `panels/personal_details/`) is empty, with no package-level
    imports or re-exports.
  - The account area's only code in `views.py` is the host view that calls `panel_framework_view`
    and its `list[NavGroup]`, as the educator `views.py` keeps only the shell. Section, panel and
    action classes do not go in `views.py` or a flat `accounts/actions.py`. The other views in
    `accounts/views.py` (`legal_doc_view`, `complete_registration_view`) are not moved.
  - Tests mirror the code: `accounts/tests/panels/personal_details/test_<module>.py`, with empty
    `tests/panels/__init__.py` and `tests/panels/personal_details/__init__.py`. `playwright/` tests
    stay in `accounts/tests/playwright/`. No new `mirroring_baseline.txt` line is added.
- `urls.py`: `profile/` and `profile/<path:path_string>` both carry the name `account_profile`, so
  `reverse("accounts:account_profile")` with no kwargs still works (header menu, educator cog,
  `EXEMPT_URL_NAMES`, existing tests). The host pattern stays under `profile/` so it never swallows
  `legal/` or `complete-registration/`.
- The host view is `@login_required` (anonymous users go to login; `check_request` alone would
  404 them) and calls `panel_framework_view` with the account area's `list[NavGroup]`, the account
  page template and `url_name="accounts:account_profile"`. An empty `path_string` redirects to the
  first section, as the educator `interface` view does.
- The Personal details section is an `ObjectViewConfig` with `url_name = "personal-details"`:
  - `get_object`: a fresh copy of the signed-in user, `User._base_manager.get(pk=request.user.pk)`,
    as `_own_user` does today.
  - `authorise_instance`: 404 unless the instance's pk is `request.user.pk`.
  - `has_capability`: grants the account actions' capabilities on the signed-in user's own row
    only; denies everything else. Every account action, the removal included, names its
    capability explicitly (`get_capability` on the `EditAction`s, since `EditAction` falls back to
    `accounts.change_user`, which a learner lacks).
  - `get_instance_label`: "Personal details".
- `edit_profile`, `edit_profile_picture`, the `account_profile_picture` URL and
  `accounts/profile.html` are removed.
- `EXEMPT_URL_NAMES` in `accounts/middleware.py` is unchanged. Panel and action URLs resolve to
  `account_profile`, so a user with incomplete registration forms is still sent to
  `complete_registration`.

### Saving and the header avatar

- An account save answers 200, not `EditAction`'s 204, because htmx drops a 204's body. The body
  replaces the form it came from with the form re-rendered unbound from the saved values. The
  account action adds the success message, so `HtmxMessagesMiddleware` appends the toast, and adds
  the header avatar partial out of band. Its `HX-Trigger` carries the panel's refresh event.
- The header avatar moves out of `header_bar_user_menu.html` into a partial with a stable id. It
  takes the user as an explicit argument, since the context's `user` is `request.user` as loaded
  before the save. The partial holds a visually hidden name ("Open user menu for <display name>"),
  so the trigger's accessible name changes with it. The dropdown button and its Alpine state are
  not swapped.

### Name panel

- Edits `first_name` and `last_name`, posted to an `EditAction` subclass with
  `renders_in_footer = False`, through `panel_framework/panels/inline_form_panel.html`: the fields
  in the body, Save in the card footer (`form=` the inline form).
- Validation is today's `UserForm`: both fields optional, at most 200 characters. An invalid
  submit answers 422 and shows each error as one line under its field (`role="alert"`,
  `aria-describedby`, `aria-invalid`).

### Profile picture panel

- Shows the stored picture (or the initials fallback) from a copy of the user that the upload
  form does not bind to, so a refused file never shows as the current picture.
- Renders its own form in an `accounts` template rather than `inline_record_form.html`, because
  that partial renders neither help text nor a preview. The form copies the partial's wiring:
  multipart `hx-encoding`, `x-data="refocusAfterRequest"`, the `[data-request-error]` element,
  and the target-self swap so a 422 shows the errors in place. It shows the field's help text
  ("JPEG, PNG or WebP, up to 10 MB…"), which the input names with `aria-describedby`. The
  `accept` list stays `image/jpeg,image/png,image/webp`. Save picture sits in the card footer,
  after Remove picture, and submits the form through `form=`.
- Uploads with `ProfilePictureForm`'s validation, WebP re-encoding and storage unchanged
  (`validate_profile_picture`, `encode_profile_picture`, the `profile_pictures` storage alias,
  `profile_picture_upload_to`). Replacing deletes the superseded file after commit, as
  `ProfilePictureForm.save` does today. The form no longer adds `remove_profile_picture`.
- A refused file answers 422 with its field error (for example `WRONG_TYPE`), and the panel still
  shows the stored picture.
- "Remove picture" shows only when a picture is stored. It is a `ConfirmAction` with
  `confirm_variant = "error"`, whose dialog says the current picture will be deleted and the
  initials shown instead. Confirming calls a shared method alongside `ProfilePictureForm.save`
  that clears `profile_picture` under the same row lock and deletes the file after commit. The
  action answers 200 with the toast and avatar out of band and `build_hx_trigger(...,
  close_modal=True)` with the panel's refresh event.

### Email addresses panel

- One row per `EmailAddress` of the signed-in user (allauth's `list_email_addresses`): the address,
  its badges (Primary; Verified, or Unverified in the warning tone) and that row's own actions, on
  one line, wrapping on a phone.
- Row actions, each scoped to the user's own addresses (another user's address pk 404s): Make
  primary (when `can_mark_as_primary`, calls `mark_as_primary`), Resend verification (unverified
  only, sends allauth's confirmation), Remove (an error-tone `ConfirmAction`, when
  `can_delete_email`, calls `delete_email`).
- The footer holds Add email, opening a dialog with allauth's `AddEmailForm`, saved through
  `add_email`. The new address shows as Unverified.
- Each action keeps allauth's `manage_email` rate limit, toasts its outcome, refreshes the panel,
  and leaves no allauth message to show again on the next page load.

### Password panel

- An inline form: allauth's `ChangePasswordForm` (Current password, New password, New password
  again) for a user with a usable password, saved and finalised with `finalize_password_change`;
  otherwise `SetPasswordForm` titled "Set password", finalised with `finalize_password_set`.
- "Change password" (or "Set password") is in the card footer; "Forgot password?" links to
  allauth's password reset from the body. Errors are one line under their field. allauth's
  `change_password` rate limit applies.

### Old allauth URLs

- `account_email`, `account_change_password` and `account_set_password` still reverse and
  redirect to the Personal details page.

### Account shell and sidebar (`freedom_ls/accounts/templates/accounts/`)

- The account shell extends `_base_interface.html` and supplies the panel framework host
  contract in `spec_dd/1. next/extract_panels_framework/research_coupling_audit.md` T11 and J3.
  `extract_panels_framework-4-template-contract` supersedes that list when it lands, and the
  shell rebases across `extract_panels_framework-5-package-and-install`. The shell includes
  `modal_host.html`, `quick_view_host.html` and `announcer_host.html`, loads
  `panel_framework/js/alpine-components.js` in `extra_alpine_components`, and renders
  `#interface-main`. It uses framework partials and `panel-*` components only, no educator
  templates.
- The shell owns the sidebar and the hosts. Its `content` block holds only an inner block
  under another name, `account_main`, which the panel page template fills. allauth page
  templates override `content` themselves, so on those pages their body replaces `account_main`
  directly; `manage.html` adds no wrapper inside `content` (a nested `content` block there would
  be replaced along with it) and sets its padding and width through the shell's `main_class`
  block instead. The announcer host sits beside the modal host, outside `content`, so neither
  page type loses it. Panel pages get their header band from `views/_main_base.html` as today.
  allauth pages keep their own `<h1>`.
- The mobile sidebar toggle is the first item in the heading's row, at the left of the `<h1>`:
  `_main_base.html` draws it on panel pages, and `manage.html` draws the same header band (toggle
  and heading in one row) on allauth pages. A page never shows two, and never puts the toggle on a
  row of its own.
- The document title on the Personal details page is "Personal details — <site_title>": the shell
  passes `site_name=site_title` into `document_title.html`. allauth pages keep their own
  `head_title`.
- The sidebar partial renders `<nav id="sidebar-nav" aria-label="Account">` from one Python list
  of entries (label, URL name) in `accounts`. The active entry carries `aria-current="page"`, found
  from `request.resolver_match`. No entry carries
  `hx-get` or `hx-boost`, so `panel_framework_view`'s navigation response, which would swap in the
  framework's one-entry nav, is never requested.
- After Personal details, the sidebar keeps today's guarded entries for allauth's social
  connections, MFA and sessions pages (`{% url … as x %}`), so they appear only if a project
  enables those apps.
- The sidebar has no Log out entry. The header user menu keeps log out.

### allauth pages

- The `allauth/layouts/manage.html` override moves from `freedom_ls/base/templates/` to
  `freedom_ls/accounts/templates/`, so `base` templates never extend an `accounts` template.
  `accounts` precedes `allauth` in `INSTALLED_APPS`, so the override still wins; the `base` copy
  is deleted, since `base` precedes `accounts` and would shadow it. The template path is
  unchanged for theme overrides. It extends the account shell, draws the header band (toggle and
  page title in one row) and puts allauth's `content` inside a `<c-panel-card>` on the panel
  canvas. Django messages from allauth views show as toasts, as they do today.
- `entrance.html`, `base.html` and `elements/button.html` are unchanged.
- allauth's forms, flows, rate limits, reauthentication and emails are unchanged; its email and
  password views are reached only through the redirects above.

### Inline record form spacing (`freedom_ls/panel_framework/templates/panel_framework/partials/inline_record_form.html`)

- Neither the hidden `[data-request-error]` element nor the base `form { @apply space-y-2 }` rule
  in `tailwind.components.css` adds space under the field row. The fix applies to every inline
  record form, educator and account.
- The Save button moves out of the form into `partials/inline_record_form_submit.html`, rendered in
  the card footer with `form=`, `hx-indicator` and `hx-disabled-elt` pointing at it.

## Testing

Write the name-flow tests against today's `edit_profile` first, then move them to the panel:
GET shows the stored names; a valid POST saves; blank names are accepted; a 201-character name is
refused. The picture-era tests in `accounts/tests/test_views.py:937-1090` are the regression list
for the picture panel and are rewritten against it.

- **Access.** Anonymous GET of `/accounts/profile/`, the section, a panel URL and an action URL
  redirects to login. `authorise_instance` 404s for another user's row. `has_capability` denies a
  capability the account actions do not use, and each of the three actions is denied without its
  own. A learner, an educator and an admin each see and save their own Personal details.
  `/accounts/profile/` redirects to `personal-details`, and `reverse("accounts:account_profile")`
  with no kwargs resolves.
- **Name panel.** Valid save: 200, names stored, the form re-rendered with them, HX-Trigger
  carries the refresh event, the "Name saved" toast and the header avatar partial (new initials
  and hidden name) are in the response, and no audit entry is written. Invalid: 422 with one-line
  errors and `aria-invalid`.
- **Picture panel.** Valid upload: stored as WebP, superseded file deleted, toast, header avatar
  swap. Refused file: 422, field error, stored picture still shown. Help text rendered and named by
  `aria-describedby`; no `remove_profile_picture` field. Remove trigger absent with no picture.
  The remove confirmation is error-tone and names the picture. Confirmed removal: file deleted,
  initials shown, toast, `closeModal` in HX-Trigger.
- **Email and password panels.** Add, resend, make primary and remove an address; another user's
  address 404s; the primary address cannot be removed; rate limits apply. Change and set password;
  a wrong current password answers 422 with its field error. The three old allauth URLs redirect.
- **Footer buttons.** No panel template puts a submit button in its body; the inline form's submit
  sits in the card footer.
- **Shell and sidebar.** The Personal details page renders the sidebar with its entry marked `aria-current="page"`,
  plus `#interface-main`, `#sidebar-nav`, `#app-modal`, `#app-modal-body` and `#quick-view`. The
  Personal details page also has `#main-content` and `#instance-header`, and its `<title>` is
  "Personal details — <site_title>". allauth pages show one mobile sidebar toggle, in the heading's
  row. An entry added
  to the sidebar list renders as a plain link with the right `aria-current`. No sidebar link
  carries `hx-get` or `hx-boost`, and a request with `HX-Request` and `HX-Target: main-content`
  still returns the account nav. `account_reauthenticate` renders the entrance layout.
- **Header menu.** `base/tests/components/test_header_bar_user_menu.py` asserts "Account".
- **Unchanged.** `accounts/tests/test_middleware.py`, `educator_interface/tests/test_sidebar.py:170-185`,
  `contrib/conformance/test_urls.py:79`, `base/tests/invariants/test_error_pages.py:55-63` and
  `manage.py check` (`check_panels`) pass.
- **Browser.** `accounts/tests/playwright/test_profile_picture_flow.py` is rewritten for the panel:
  upload, refused file with its error lined up under the field, confirmed removal, and the header
  avatar changing without a reload. A Playwright test measures the rendered inline record form on
  both the account name panel and the educator learner name panel and asserts no space below the
  field row beyond the form's own padding.

## Open questions

- Q: Keep the `accounts:account_profile_picture` URL answering for downstream callers? → A: Removed and listed as a breaking change. (assumed default: only `profile.html` and tests reverse it in FLS, and keeping a dead endpoint is unrequested work. Overrule by editing Host, URLs and config.)
- Q: Should reauthentication render in the account shell? → A: No, it keeps the entrance layout. (assumed default: allauth builds it on `base_entrance.html`, and the idea keeps the entrance flows as they are. Overrule by editing Scope.)
- Q: Keep the guarded social, MFA and sessions sidebar entries? → A: Kept, rendering only when the app is enabled. (assumed default: today's `manage.html` has them, and dropping them would hide those pages from a project that enables one. Overrule by editing Account shell and sidebar.)

## Success criteria

- A learner, an educator and an admin each change their name, picture, email addresses and
  password at `/accounts/profile/`
  without a full page reload, and see a toast and the new header avatar.
- Every request for someone else's account data 404s, and anonymous requests redirect to login.
- The inline record form shows no extra space under its field row, measured in a browser.
