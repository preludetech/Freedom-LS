# Spec: chain the SDD steps

Source: `idea.md` and the `research_*.md` files beside it.

## Purpose

Each SDD command ends by telling the user which command to run next. Between `/sdd:start` and the
spec, between the implemented plan and its QA pass, and between the documentation hooks and the
pull request, nothing needs a human decision, yet the pipeline stops and waits for one. Batches of
a plan run one at a time even when the plan says they are independent. Every question a chain can
ask up front is asked once, while setup work runs, so the chain does not stall on it.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| batch wave | coined | the batches `implement_plan` runs at the same time: every remaining batch whose `Builds on:` slices are all committed, capped by `Parallel batches`. Distinct from the review wave of `spec_review.md`. |
| batch worktree | coined | the short-lived worktree a batch wave's sub-agent works in, created by the `Agent` tool's `isolation: "worktree"` option under `.claude/worktrees/` of the feature worktree. A batch is one vertical slice. |
| hook mode | narrowed | `claude_plugins/sdd/skills/claude-code-authoring/SKILL.md` "Hook mode", as amended by the requirement under `claude-code-authoring/` below |

"Batch" (`commands/implement_plan.md` Step 2), "slice" (`commands/plan_from_spec.md` Step 3),
"spec directory" (`commands/README.md`), "feature worktree" (`commands/finish_worktree.md`),
"mechanic" (`agents/sdd-mechanic.md`) and "worker" (`agents/sdd-worker.md`) keep the meanings in the
files named. "Slice" is plan content; "batch" is its execution.

## Scope

In:

- `/sdd:start` continues, inside the new worktree, into `/sdd:register_design` (when the spec
  directory holds a `design_prompt.md`) and `/sdd:spec_from_idea`, asking its questions while the
  worktree is being set up.
- `/sdd:implement_plan` runs independent batches of a plan in parallel batch worktrees, integrates
  them, and continues into the QA command once the plan is implemented.
- `/sdd:plan_from_spec` declares, per slice, what it builds on and what it touches, and the plan
  review checks those lines.
- `/sdd:document` executes the remaining documentation items in `todo.md`, then opens the pull
  request.
- Hook-mode entry for `register_design`, `spec_from_idea` and `do_qa`; the config key, settings,
  ignores and docs the above need.

Out:

- Parallel QA. QA drives one browser against one dev server and one database; it stays
  sequential at depth 0.
- Chaining across a human gate: spec to plan, plan to implementation, QA to documentation. The
  `(user)` review items between them stay.
- An opt-out argument for the chains. Every chained step is runnable alone, and a chain stops on
  its own on `failed`, `blocked` or `paused`.
- Agent teams, headless `claude -p` runs, Claude Code hooks, plan or permission modes.
- Changing what `/sdd:finish_worktree`, `/sdd:address_pr_review`, `/sdd:make_pr_quickly` or
  `/sdd:roadmap` do, beyond the one cleanup step named below.

## Decisions

- **A chain is a read-and-follow at depth 0, never a spawn.** A command wrapped in a sub-agent
  loses its fan-out and its questions (`claude-code-authoring`: no nesting, `AskUserQuestion` is
  orchestrator-only). The chaining command's `allowed-tools` is the union of its hooks'.
- **The session crosses into the new worktree with `EnterWorktree` by path.** The bare-repo layout
  lists every sibling worktree in `git worktree list`, which is what the tool requires. Writing the
  spec on `main` first would put spec commits on `main`. A headless run could not ask anything.
- **Hook mode keeps the tick when the `todo.md` item names the command.** Otherwise a chained
  `spec_from_idea` or `do_qa` leaves its own item unticked and the checklist lies.
- **The plan declares parallelism; `implement_plan` never infers it.** A plan without the lines
  runs sequentially, so older plans keep working.
- **Batch worktrees come from `isolation: "worktree"`, not from `git worktree add`.** The option
  pins the sub-agent's working directory; a hand-made sibling worktree would need `cd` on every
  call, and `cd` prompts.
- **A batch wave of one runs in the feature worktree.** A batch worktree costs a full Setup script
  run; it is only paid when two or more batches can run at once.
- **Integration is `git cherry-pick` of marker commits in plan order, never a merge commit.** The
  rebase command refuses a branch with merge commits, and the resume scan matches commit subjects,
  which cherry-pick preserves.
- **A batch that fails, blocks or conflicts re-runs alone in the feature worktree, before the next
  batch wave.** `blocked` can then ask at depth 0 and a conflict cannot repeat.
- **A crashed worker's worktree is torn down with one `cd <path> && <Teardown script>` call.** The
  Teardown script keys off the current branch, so it has to run inside the worktree. The
  permission prompt that call raises is accepted: it only happens on a resumed, attended run.
- **Extra documentation items run one sub-agent at a time.** They share a worktree and each
  commits; parallel commits in one worktree race on the index.
- **Commits are a plain `git commit`.** Claude Code refuses `uv run git commit` inside a worktree
  it isolates (after `EnterWorktree`, and in an `isolation: "worktree"` sub-agent), which is where
  both chains commit. The shared pre-commit hook becomes a shim that runs pre-commit from the
  committing worktree's own environment, so the hooks still fire.
- **The PR opens whatever is outstanding.** The report lists what is left; the user asked for the
  PR to exist regardless.
- **QA stays independently runnable.** `do_qa` gains a hook-mode entry and nothing else.

### `claude_plugins/sdd/commands/start.md`

   its answer can be "stop". Steps 1 and 2 are as today.

   as `spec_from_idea.md` Step 1 spawns its workers) and, while it runs, asks the front-loaded
   batch at depth 0:
   - Read the idea and every sibling `*.md` in the spec directory. Ask the questions
     `spec_from_idea.md` Step 2 point 1 describes ("the questions the idea itself leaves open and
     no research task bears on"), under the recipe's test, up to four per `AskUserQuestion`, each
     with a recommended answer and one clause on why it matters. Further calls follow while the
     mechanic runs. Nothing is held back for a question.
   - When `<spec-dir>/design_prompt.md` exists and `<spec-dir>/design.md` does not: load
     `DesignSync` (`ToolSearch` with `select:DesignSync`), take the project id from the prompt the

     one question: "Run `/design-login` now, then choose Done (Recommended)" or "Register the
     design without reading it". The answer is passed to the hook in step 6.
   - Answers stay in context until step 5. Collect the mechanic's return after the questions; a
     `blocked` return is handled as today (ask, re-spawn) and the chain continues after it.
4. Step 4, new: enter the worktree. Load the tool (`ToolSearch` with `select:EnterWorktree`), then
   call `EnterWorktree` with `path` set to the worktree path the mechanic reported. Confirm
   `git branch --show-current` prints the spec directory's folder name; otherwise stop with
   `status: failed` and the reason.
5. Step 5, new: write `<spec-dir>/answers.md` in a single `Write`:

   ```markdown
   # Answers: <spec name>

   Asked by `/sdd:start` before the spec was written.

   - Q: <question>? → A: <answer> (asked up front)
   ```

   One line per question asked in step 3, including the design-login answer. No questions asked
   is an empty list under the heading, and the file is still written. When step 7 will be skipped,
   or the chain stops before `spec_from_idea` Step 4 commits, delegate a commit of `answers.md` to
   `sdd:sdd-mechanic` via `commit_and_push.md` with `<summary>` `record the up-front answers`;
   otherwise `spec_from_idea` Step 4 commits it.
6. Step 6, new: register the design. When `design_prompt.md` exists and `design.md` does not, read
   `${CLAUDE_PLUGIN_ROOT}/commands/register_design.md` and follow it with `mode: hook`,
   `<spec-dir>`, the design input `<spec-dir>/design_prompt.md`, no notes, and the design-login
   answer. Otherwise skip and say which condition failed.
7. Step 7, new: write the spec. When `<todo-path>` has the unticked item naming
   `/sdd:spec_from_idea`, read `${CLAUDE_PLUGIN_ROOT}/commands/spec_from_idea.md` and follow it with
   `mode: hook`, `<spec-dir>`, `<todo-path>`, the idea path and `answers: <spec-dir>/answers.md`.
   Otherwise skip and say so.
8. Step 8: report, in this fixed shape, at most fifteen lines: one line per step (`done`,
   `skipped: <why>`, or the status that stopped the chain); the worktree path; the artifacts
   written with their paths; the number of assumed defaults the spec recorded and the grep that
   finds them (`## Open questions`); the next human step from `todo.md`.
9. Chain stop rule, stated once in the file: a step that returns `failed`, `blocked` or `paused`
   ends the run. The report says what finished, why it stopped, and the single command that
   continues (`/sdd:register_design <spec-dir>/design_prompt.md` or
   `/sdd:spec_from_idea <idea path>`), to be run from inside the worktree.

1. Opens with an "Inputs from the caller" line: `<spec-dir>`, the design input (a prompt, a prompt

### `claude_plugins/sdd/commands/spec_from_idea.md`

1. Opens with an "Inputs from the caller" line: `<spec-dir>`, `<todo-path>`, the idea path,
   `answers: <path>` and `mode: hook`.
2. In hook mode Step 0 (pre-step rebase) is skipped; Step 9 (todo tick), Steps 4 and 10 (commits)

3. Step 2 reads `<spec-dir>/answers.md` when it exists, in either mode, before asking anything. A

### `claude_plugins/sdd/commands/plan_from_spec.md` and `claude_plugins/sdd/resources/plan_review_dimensions.md`

   is its slice number, and adds two lines every slice carries, after its behaviour line and
   before any `**Design states:**` line:
   - `**Builds on:** none` or `**Builds on:** slices <n>, <m>`: the earlier slices whose work this
     slice edits, imports, migrates on top of, or needs in the database. A slice builds on every
     earlier slice whose `Touches:` overlaps its own; a slice that adds a schema-migration file
     builds on every earlier slice that adds one in the same migration directory; a slice that
     changes a dependency manifest or lockfile builds on every earlier slice.

     directory means everything under it. Shared groundwork placed before a slice is listed under
     that slice.
   `implement_plan` reads both lines. Two slices with no `Builds on:` path between them may run at
   the same time, so their `Touches:` must be disjoint.

### `claude_plugins/sdd/commands/implement_plan.md`

1. Frontmatter: `allowed-tools` becomes the union of the current list and `do_qa.md`'s.
2. Step 2 is rewritten around batch waves. The batch definition, the marker commit, the resume
   scan, the batch brief, the Design check and the Batch review stay as they are. The sequential
   loop becomes:
   - **Cap.** Read `Parallel batches` under `## Worktree Scripts` in `.claude/sdd/config.md`
     (`config.local.md` wins). Blank, absent or `1` is `1`.
   - **Leftover batch worktrees.** Before spawning anything, run `git worktree list`. For each
     worktree under this checkout's `.claude/worktrees/` whose branch holds a commit matching the
     plan's anchored `[batch …]` pattern: cherry-pick, in plan order, every such commit whose id has
     no marker on the feature branch; then run the Teardown script inside it (`cd <path> &&
     <script>`, one call), `git worktree remove --force --force .claude/worktrees/<name>` and
     `git branch -D <branch>`. Any other worktree under `.claude/worktrees/` is left alone and named
     in the Step 3 summary.
   - **Resume reviews.** On resume, the Design check and Batch review run again for every batch
     whose marker commit is later than the last `review fix`, `design fix` or `integration fix`
     commit, or for the last batch when there is none.
   - **Batch waves.** `remaining` is the batches without a marker commit, in plan order. Repeat until it
     is empty: `ready` is every batch in `remaining` whose `Builds on:` slices all have a marker
     commit. A plan whose slices carry no `Builds on:` line, or that Step 2 regrouped into batches,
     has `ready` = the first remaining batch. The batch wave is the first `min(len(ready), cap)` of
     `ready`.
   - **A batch wave of one** runs in the feature worktree exactly as a batch runs today, including
     `failed` (reset, retry twice) and `blocked` (ask at depth 0, re-spawn), then its Design check
     and Batch review.
   - **A batch wave of two or more.** Record `wave-base` = `git rev-parse HEAD`. Resolve the Setup and
     Teardown script values once at depth 0 (`config.local.md` is gitignored and absent in a batch
     worktree). Spawn every batch of the batch wave in one message, each `subagent_type:
     "general-purpose"`, `model: "sonnet"`, `isolation: "worktree"`. The brief is today's batch
     brief plus: first run `<Setup script>` from the worktree root (blank: nothing); work only
     inside this worktree; whatever the outcome, run `<Teardown script>` the same way before
     returning (blank: nothing); return `status: ok|failed|blocked · reason: <short> · worktree:
     <abs path> · branch: <name>`.
   - **Integration.** When every worker of the batch wave has returned, for each `ok` batch in plan
     order, cherry-pick the commits on its branch whose subject matches the plan's anchored
     `[batch …]` pattern. A conflict is `git cherry-pick --abort` and the batch is marked `failed`
     with the conflicting files as its reason. Then, for every batch of the batch wave, `git worktree
     remove --force .claude/worktrees/<name>` and `git branch -D <branch>`.
   - **After integration.** Run the `Migrate` command under `## QA Dev Data` in `.claude/sdd/config.md`
     when non-blank, so the feature worktree's dev database holds the batch wave's migrations before the
     Design check starts a server. Then delegate to `sdd:sdd-mechanic`: read
     `${CLAUDE_PLUGIN_ROOT}/commands/protected/run_test_tier.md` and follow it with `<tier>`:
     `targeted` and `<diff>`: `--range <wave-base>..HEAD`. A failure is fixed by a sub-agent as
     Step 3 point 3 does, committed as `[batch <id>] integration fix` with the id of the last
     integrated batch. Then, for each integrated batch in plan order, the Design check and the
     Batch review run as today.
   - **Retries.** Each batch of the batch wave that returned `failed` or `blocked`, or conflicted, re-runs
     at once as a batch wave of one, in plan order, with its attempt count and reason, before the next
     batch wave is formed. The limit stays two retries per batch. A batch that exhausts them stops the
     run with `status: failed`, naming it and every batch that builds on it.
3. The section "DO NOT run the frontend_qa plan during implementation" becomes one line: QA runs
   in Step 5, never inside a batch, and a plan step that says to run it is ignored.
4. Step 3's summary also lists, per batch wave, its batches and where they ran, and the leftover
   worktrees removed or left.
5. Step 5, new, after the todo tick in Step 4: run QA.
   - Read `QA command` under `## QA Hooks` in `.claude/sdd/config.md` (`config.local.md` wins).
     Blank: say "no QA command configured; the checklist's QA item is a user item" and go to Step 6.
   - The QA file (`3. frontend_qa.md`, or the suffix form from "Input") does not exist: say the
     plan has no QA plan and go to Step 6.
   - The value names a command of this plugin (`sdd:<name>`): read
     `${CLAUDE_PLUGIN_ROOT}/commands/<name>.md` and follow it with `mode: hook`, `<spec-dir>`,
     `<todo-path>` and the QA file path. Any other value: invoke it with the `Skill` tool and
     `args: "spec-dir=<spec-dir> todo-path=<todo-path> plan=<QA file> mode: hook"`.
6. Step 6, new: final report. The QA report path, the bug counts per lane, the `Decide` items
   filed, and the next human step from `todo.md`. A QA hook that returned `failed` or `blocked` is
   reported with its reason; the implementation commits are already on the branch, and
   `/sdd:do_qa` is the command that continues.

## Testing

Proved with a throwaway spec directory on a local branch, the way `qa-boy-scout-throwaway` was
used, never merged.

1. **Start chain, no design.** `/sdd:start` on the throwaway idea ends with the session inside the
   new worktree; `answers.md`, the research files and `1. spec.md` are committed on the feature
   branch; `main` holds only the move commit; every question in `answers.md` was asked while the
   Setup script ran; after the spec is written only the Step 7 review batch asks.
2. **Worktree entry spike.** After `EnterWorktree`, `.claude/worktrees/`, `.claude/settings.json`
   and `CLAUDE.md` resolve to the entered worktree, not the launch checkout.
3. **Start chain with a design.** With a `design_prompt.md` present, `design.md` is committed
   before the research workers are spawned and the idea's Resources bullet points at it. With
   `/design-login` refused, the coverage table reads "not yet read" and the chain continues.
4. **Chain stop.** A mechanic returning `blocked` is asked about and the chain continues; a
   `paused` or `failed` hook ends the run with the report's next-command line, and `answers.md`
   is committed.
5. **Batch wave.** A plan with two slices, both `Builds on: none`, disjoint `Touches:`, and
   `Parallel batches: 2`: two worktrees exist during the batch wave; afterwards both marker commits are on
   the feature branch and no worktree, branch or database is left.
6. **Conflict.** Two slices in one batch wave that edit the same file: the plan review flags the plan;
   with the flag overridden, the cherry-pick aborts and the batch re-runs alone before the next
   batch wave.
7. **Resume.** A batch wave interrupted after one worker committed: re-running integrates that branch,
   removes the leftover worktrees it owns, leaves any other worktree alone, and re-runs the other
   batch.
8. **Older plan.** A plan without `Builds on:` lines runs every batch sequentially, as before.
9. **QA chain.** After the last batch, `qa_report.md` exists and the QA item is ticked; `/sdd:do_qa`
   run again by hand on the same branch works unchanged. A plan long enough to exhaust the session
   context before QA is re-run with `/sdd:do_qa` alone, which already works.
10. **Document chain.** With one extra item between the `/sdd:document` and `/sdd:make_pr_quickly`
    items: the item's work is committed and ticked, a PR exists, and the PR item is ticked; a
    second run ticks the item without a second commit.
11. **Standalone commands.** `/sdd:register_design`, `/sdd:spec_from_idea` and `/sdd:do_qa` run
    by hand behave as before.

## Success criteria

- `/sdd:start` ends inside the new worktree with `1. spec.md` committed on the feature branch.
- No question that `/sdd:start` could ask up front is asked after the spec is written.
- With a `design_prompt.md` present, `design.md` exists before the research workers spawn.
- Two independent batches run at the same time when `Parallel batches` is `2` or more, and nothing
  of theirs survives on disk or in the database afterwards.
- A plan without `Builds on:` lines produces the same commits as before.
- `implement_plan` ends with `qa_report.md` on the branch when a QA command and QA file exist.
- `/sdd:document` prints a PR URL and ticks every documentation item it executed.
- The plan review rejects a plan whose independent slices share a path.
- No FLS name, path or value appears in `claude_plugins/sdd`.
