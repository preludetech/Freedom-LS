# Spec: chain the SDD steps

Source: `idea.md`, the `research_*.md` files beside it, and the answers recorded in this file's
Decisions.

## Purpose

Each SDD command ends by telling the user which command to run next. Between `/sdd:start` and the
spec, and between the implemented plan and its QA pass, nothing needs a human decision, yet the
pipeline stops and waits for one. Batches of a plan run one at a time even when the plan says they
are independent. This spec makes `/sdd:start` continue into design registration and the spec,
`/sdd:implement_plan` continue into QA and run independent slices in parallel worktrees, and
`/sdd:document` finish the documentation items in the checklist and open the pull request. Every
question a chain can ask is asked once, up front, while setup work runs.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| wave | coined | the batches of a plan that `implement_plan` runs at the same time: every remaining batch whose `Builds on:` slices are all committed, capped by `Parallel batches` |
| slice worktree | coined | the short-lived git worktree a wave's batch sub-agent works in, created by the `Agent` tool's `isolation: "worktree"` option under `.claude/worktrees/` of the feature worktree |
| hook mode | narrowed | `claude_plugins/sdd/skills/claude-code-authoring/SKILL.md` "Hook mode"; here extended so a command keeps the `todo.md` tick of the item that names it |

"Batch", "slice", "spec directory", "feature worktree", "mechanic" and "worker" keep the meanings
`claude_plugins/sdd/commands/README.md` gives them.

## Scope

In:

- `/sdd:start` continues, inside the new worktree, into `/sdd:register_design` (when the spec
  directory holds a `design_prompt.md`) and `/sdd:spec_from_idea`, asking its questions while the
  worktree is being set up.
- `/sdd:implement_plan` runs independent slices of a plan in parallel slice worktrees, integrates
  them, and continues into the QA command once the plan is implemented.
- `/sdd:plan_from_spec` declares, per slice, what it builds on and what it touches, and the plan
  review checks those lines.
- `/sdd:document` executes the remaining documentation items in `todo.md`, then opens the pull
  request.
- Hook-mode entry for `register_design`, `spec_from_idea` and `do_qa`; the config key, settings,
  ignores and docs the above need.

Out:

- Parallel QA. QA drives one browser against one dev server and one database; it stays
  sequential at depth 0.
- Chaining across a human gate: spec to plan, plan to implementation, QA to documentation. The
  `(user)` review items between them stay.
- Agent teams, headless `claude -p` runs, Claude Code hooks, plan or permission modes.
- Changing what `/sdd:finish_worktree`, `/sdd:address_pr_review`, `/sdd:make_pr_quickly` or
  `/sdd:roadmap` do, beyond the one cleanup step named below.

## Decisions

- **A chain is a read-and-follow at depth 0, never a spawn.** A command wrapped in a sub-agent
  loses its fan-out and its questions (`claude-code-authoring`: no nesting, `AskUserQuestion` is
  orchestrator-only). The chaining command's `allowed-tools` is the union of its hooks'.
- **The session crosses into the new worktree with `EnterWorktree` by path.** The bare-repo layout
  lists every sibling worktree in `git worktree list`, which is what the tool requires. Writing the
  spec on `main` first would put spec commits on `main`. A headless run could not ask anything.
- **Hook mode keeps the tick when the `todo.md` item names the command.** Otherwise a chained
  `spec_from_idea` or `do_qa` leaves its own item unticked and the checklist lies. The skill text is
  amended, not contradicted.
- **The plan declares parallelism; `implement_plan` never infers it.** `Builds on:` and `Touches:`
  lines per slice, checked by a plan review dimension. A plan without them runs sequentially, so
  older plans keep working.
- **Slice worktrees come from `isolation: "worktree"`, not from `git worktree add`.** The option
  pins the sub-agent's working directory, so every relative path in the helper files it follows
  resolves inside its worktree; a hand-made sibling worktree would need `cd` on every call. The
  project's own Setup and Teardown scripts run inside it, so a slice gets the same per-branch
  resources a feature worktree gets. It requires `worktree.baseRef: "head"`, or the slice would
  branch from `origin/main` instead of the feature branch.
- **A wave of one runs in the feature worktree.** A slice worktree costs a full Setup script run;
  it is only paid when two or more batches can run at once.
- **Integration is `git cherry-pick` in plan order, never a merge commit.** The rebase command
  refuses a branch with merge commits, and the resume scan matches commit subjects, which
  cherry-pick preserves.
- **A slice that fails, blocks or conflicts re-runs in the feature worktree after its wave.** The
  retry is a single-batch wave, so `blocked` can ask at depth 0 and a conflict cannot repeat.
- **Extra documentation items run one sub-agent at a time.** They share a worktree, likely share
  files, and each commits; parallel commits in one worktree race on the index.
- **QA stays independently runnable.** `do_qa` gains a hook-mode entry and nothing else; standalone
  behaviour is unchanged.

## Requirements

### `claude_plugins/sdd/commands/start.md`

1. Frontmatter: `allowed-tools` becomes the union of the current list, `AskUserQuestion` (used
   today but not declared), `EnterWorktree`, and the lists of `register_design.md` and
   `spec_from_idea.md` (`Edit`, `Grep`, `ToolSearch`, `WebFetch`, `WebSearch`).
2. Step 0 (roadmap precursor and dependency questions) is unchanged and runs before anything is
   spawned, because its answer can be "stop".
3. Steps 1 and 2 (todo list, move and commit) are unchanged.
4. Step 3 spawns the `start_worktree.md` mechanic and, while it runs, asks the front-loaded batch at
   depth 0:
   - Read the idea and every sibling `*.md` in the spec directory. Ask the questions
     `spec_from_idea.md` Step 2 point 1 describes ("the questions the idea itself leaves open and
     no research task bears on"), under the recipe's test, up to four per `AskUserQuestion`, each
     with a recommended answer and one clause on why it matters. Further calls follow while the
     mechanic runs. Nothing is held back for a question.
   - When `<spec-dir>/design_prompt.md` exists and `<spec-dir>/design.md` does not: load
     `DesignSync` (`ToolSearch` with `select:DesignSync`), take the project id from the prompt the
     way `register_design.md` Step 1 does, and call `get_project`. On an authorisation error, ask
     one question: "Run `/design-login` now, then choose Done (Recommended)" or "Register the
     design without reading it". The answer is passed to the hook in step 7.
   - Answers stay in context until step 6.
5. A mechanic that returns `blocked` is handled as today (ask, re-spawn); the chain continues after
   it.
6. Step 4, new: enter the worktree. Call `EnterWorktree` with `path` set to the worktree path the
   mechanic reported. Confirm `git branch --show-current` prints the spec directory's folder name;
   otherwise stop with `status: failed` and the reason. Then write `<spec-dir>/answers.md` in a
   single `Write`:

   ```markdown
   # Answers: <spec name>

   Asked by `/sdd:start` before the spec was written.

   - Q: <question>? → A: <answer> (asked up front)
   ```

   One line per question asked in step 4, including the design-login answer. No questions asked
   is an empty list under the heading, and the file is still written.
7. Step 5, new: register the design. When `design_prompt.md` exists and `design.md` does not, read
   `${CLAUDE_PLUGIN_ROOT}/commands/register_design.md` and follow it with `mode: hook`,
   `<spec-dir>`, the design input `<spec-dir>/design_prompt.md`, no notes, and the design-login
   answer. Otherwise skip and say which condition failed.
8. Step 6, new: write the spec. When `<todo-path>` has the unticked item naming
   `/sdd:spec_from_idea`, read `${CLAUDE_PLUGIN_ROOT}/commands/spec_from_idea.md` and follow it with
   `mode: hook`, `<spec-dir>`, `<todo-path>`, the idea path and `answers: <spec-dir>/answers.md`.
   Otherwise skip and say so.
9. Step 7: report, in this fixed shape, at most fifteen lines: one line per step (`done`,
   `skipped: <why>`, or the status that stopped the chain); the worktree path; the artifacts
   written with their paths; the number of assumed defaults the spec recorded and the grep that
   finds them (`## Open questions`); the next human step from `todo.md`.
10. Chain stop rule, stated once in the file: a step that returns `failed`, `blocked` or `paused`
    ends the run. The report says what finished, why it stopped, and the single command that
    continues (`/sdd:register_design <spec-dir>/design_prompt.md` or
    `/sdd:spec_from_idea <idea path>`), to be run from inside the worktree.

### `claude_plugins/sdd/commands/register_design.md`

1. Opens with an "Inputs from the caller" line: `<spec-dir>`, the design input (a prompt, a prompt
   file path or a link), optional notes, the design-login answer, and `mode: hook`. Without
   `mode: hook` the command is standalone and unchanged.
2. In hook mode Step 1 takes its inputs from the caller instead of `$ARGUMENTS`. When the design
   input is `<spec-dir>/design_prompt.md` itself, the verbatim write of `design_prompt.md` is a
   no-op: the file is read before anything writes to that path.
3. In hook mode Step 2's `/design-login` prompt is replaced by the caller's answer: "Done" retries
   once; "without reading it" registers the design with the coverage table marked "not yet read",
   as the standalone fallback already does.
4. Steps 3 to 6 are unchanged. The commit still happens in hook mode.

### `claude_plugins/sdd/commands/spec_from_idea.md`

1. Opens with an "Inputs from the caller" line: `<spec-dir>`, `<todo-path>`, the idea path,
   `answers: <path>` and `mode: hook`.
2. In hook mode Step 0 (pre-step rebase) is skipped; Step 9 (todo tick) and Steps 4 and 10
   (commits) run as they do standalone.
3. Step 2 reads `<spec-dir>/answers.md` when it exists, in either mode, before asking anything. A
   question the file answers is never asked again; its answer counts as a recorded answer for Step
   3 and for the review wave's `completeness` dimension.
4. Step 3 lists `answers.md` among the inputs the spec is written against. Step 4 stages it with
   the spec and the research files.

### `claude_plugins/sdd/commands/plan_from_spec.md` and `claude_plugins/sdd/resources/plan_review_dimensions.md`

1. Step 3 "Order the plan as vertical slices" adds two lines every slice carries, after its
   behaviour line and before any `**Design states:**` line:
   - `**Builds on:** none` or `**Builds on:** slices <n>, <m>`: the earlier slices whose work this
     slice edits, imports, migrates on top of, or needs in the database. A slice builds on every
     earlier slice whose `Touches:` overlaps its own; a slice that adds a migration builds on every
     earlier slice that adds a migration to the same app; a slice that changes a dependency manifest
     or lockfile builds on every earlier slice.
   - `**Touches:** <paths>`: the files and directories the slice creates or edits, one per comma. A
     directory means everything under it. Shared groundwork placed before a slice is listed under
     that slice.
   `implement_plan` reads both lines. Two slices with no `Builds on:` path between them may run at
   the same time, so their `Touches:` must be disjoint.
2. `plan_review_dimensions.md` gains a row:

   | id | checks | evidence it may cite | clear fixes |
   | --- | --- | --- | --- |
   | `parallel_safety` | every slice has `Builds on:` and `Touches:`; two slices with no `Builds on:` path between them have disjoint `Touches:`; migration, manifest and lockfile rules above | the two slices' lines | a missing line; a missing `Builds on:` entry where the overlap is literal |

3. The plan still never mentions the QA file (Step 5 rule unchanged).
4. Step 8: items added with `add_after:"Run `/sdd:document`|…"` carry the marker `cmd`, since
   `/sdd:document` now executes them.

### `claude_plugins/sdd/commands/implement_plan.md`

1. Frontmatter: `allowed-tools` becomes the union of the current list and `do_qa.md`'s.
2. Step 2 is rewritten around waves. Keep the batch definition, the marker commit, the resume scan,
   the batch brief, the Design check and the Batch review as they are. Replace the sequential loop
   with:
   - **Cap.** Read `Parallel batches` under `## Worktree Scripts` in `.claude/sdd/config.md`
     (`config.local.md` wins). Blank, absent or `1` is `1`.
   - **Leftover slice worktrees.** Before spawning anything, run `git worktree list`. For each
     worktree whose path is under this checkout's `.claude/worktrees/`: if its branch holds a
     `[batch <id>]` commit whose id has no marker on the feature branch, integrate that branch as
     below; then, whether or not it held one, run the Teardown script from inside it when its worker
     did not return `ok` (a Bash call that starts with `cd <path> &&`), `git worktree remove --force
     <path>` and `git branch -D <branch>`. Name each one in the Step 3 summary.
   - **Waves.** `remaining` is the batches without a marker commit, in plan order. Repeat until it
     is empty: `ready` is every batch in `remaining` whose `Builds on:` slices all have a marker
     commit. A plan whose slices carry no `Builds on:` line has `ready` = the first remaining batch.
     The wave is the first `min(len(ready), cap)` of `ready`.
   - **A wave of one** runs in the feature worktree exactly as a batch runs today, including
     `failed` (reset, retry twice) and `blocked` (ask at depth 0, re-spawn), then its Design check
     and Batch review.
   - **A wave of two or more.** Record `wave-base` = `git rev-parse HEAD`. Spawn every batch of the
     wave in one message, each `subagent_type: "general-purpose"`, `model: "sonnet"`,
     `isolation: "worktree"`. The brief is today's batch brief plus: first, read `## Worktree
     Scripts` in `.claude/sdd/config.md` and run the Setup script from the worktree root (blank:
     nothing); work only inside this worktree; after the marker commit, run the Teardown script the
     same way (blank: nothing); return `status: ok|failed|blocked · reason: <short> · worktree: <abs
     path> · branch: <name>`.
   - **Integration.** When every worker of the wave has returned, for each `ok` batch in plan
     order: `git cherry-pick <wave-base>..<branch>`. A conflict is `git cherry-pick --abort` and the
     batch is marked `failed` with the conflicting files as its reason. Then, for every batch of the
     wave, `git worktree remove --force <worktree>` and `git branch -D <branch>`; a worker that did
     not return `ok` has the Teardown script run inside its worktree first, as for leftovers.
   - **Wave tests.** Delegate to `sdd:sdd-mechanic`: read
     `${CLAUDE_PLUGIN_ROOT}/commands/protected/run_test_tier.md` and follow it with `<tier>`:
     `targeted` and `<diff>`: the range `<wave-base>..HEAD`. A failure is fixed by a sub-agent as
     Step 3 point 3 does, committed as `[batch <id>] integration fix` with the id of the last
     integrated batch.
   - Then, for each integrated batch in plan order, the Design check and the Batch review run as
     today.
   - Batches that returned `failed` or `blocked`, or conflicted, go back into `remaining` with
     their attempt count and reason, and run as waves of one when they are next `ready`. The
     attempt limit stays two retries per batch.
3. The section "DO NOT run the frontend_qa plan during implementation" is replaced by one line:
   QA runs in Step 5, never inside a batch, and a plan step that says to run it is ignored.
4. Step 5, new, after the todo tick in Step 4: run QA.
   - Read `QA command` under `## QA Hooks` in `.claude/sdd/config.md` (`config.local.md` wins).
     Blank: say "no QA command configured; the checklist's QA item is a user item" and end.
   - The QA file (`3. frontend_qa.md`, or the suffix form from "Input") does not exist: say the
     plan has no QA plan and end.
   - The value names a command of this plugin (`sdd:<name>`): read
     `${CLAUDE_PLUGIN_ROOT}/commands/<name>.md` and follow it with `mode: hook`, `<spec-dir>`,
     `<todo-path>` and the QA file path. Any other value: invoke it with the `Skill` tool and
     `args: "spec-dir=<spec-dir> todo-path=<todo-path> plan=<QA file> mode: hook"`.
   - The QA hook ticks its own item and commits, as it does standalone.
5. The Step 3 summary gains: per wave, its batches and where they ran; leftovers removed; the QA
   report path, the bug counts per lane, the `Decide` items filed, and the next human step. A QA
   hook that returns `failed` or `blocked` is reported with its reason; the implementation commits
   are already on the branch.

## Testing

Proved with a throwaway spec directory on a local branch, the way `qa-boy-scout-throwaway` was
used, never merged.

1. **Start chain, no design.** `/sdd:start` on the throwaway idea ends with the session inside the
   new worktree; `answers.md`, the six `research_*.md` and `1. spec.md` are committed on the feature
   branch; the `Run /sdd:spec_from_idea` item is ticked; `main` holds only the move commit; every
   question in `answers.md` was asked while the Setup script ran, none after the spec was written.
2. **Start chain with a design.** With a `design_prompt.md` in the directory, `design.md` is
   committed before the research workers are spawned and the idea's Resources bullet points at it.
   With `/design-login` refused, the coverage table reads "not yet read" and the chain continues.
3. **Chain stop.** A `start_worktree.md` mechanic returning `blocked` (dirty tree) is asked about
   at depth 0 and the chain continues; a `paused` or `failed` hook ends the run with the report's
   next-command line.
4. **Parallel wave.** A plan with two slices, both `Builds on: none`, disjoint `Touches:`, and
   `Parallel batches: 2`: two worktrees appear under `.claude/worktrees/` during the wave; afterwards
   both `[batch <id>]` commits are on the feature branch, the worktrees and branches are gone,
   `uv run python -m dev_db.stale_dbs` lists nothing for them, the targeted tier ran once over the
   wave, and the Design check and Batch review ran per batch.
5. **Conflict.** Two slices in one wave that edit the same file: the plan review's
   `parallel_safety` row flags the plan; with the flag overridden, the cherry-pick conflict aborts,
   the slice re-runs alone in the feature worktree, and its marker commit lands.
6. **Resume.** A wave interrupted after one worker committed: re-running `implement_plan`
   integrates that slice's branch, removes both slice worktrees, and re-runs the other slice.
7. **Older plan.** A plan without `Builds on:` lines runs every batch sequentially in the feature
   worktree, as before.
8. **QA chain.** After the last batch, `qa_report.md` exists, the QA item is ticked by the hook,
   and `/sdd:do_qa` run again by hand on the same branch works unchanged.
9. **Document chain.** With one extra item between the `/sdd:document` and `/sdd:make_pr_quickly`
   items, the item's work is committed and ticked, a PR exists, and the PR item is ticked.
10. **Standalone commands.** `/sdd:register_design`, `/sdd:spec_from_idea` and `/sdd:do_qa` run by
    hand behave as before, pre-step rebase included.

## Open questions

- Q: Should the chains have an opt-out argument? → A: No (assumed default: every chained step is
  runnable alone and the chain stops on its own on `failed`, `blocked` or `paused`; a flag is a
  feature the idea does not ask for. Overrule by editing Scope.)
- Q: Do `spec_from_idea`'s mid-run question batches still ask when it runs as a hook? → A: Yes
  (assumed default: they are the existing behaviour and fall within minutes of the front-loaded
  batch; a later question takes its recorded default as today. Overrule by editing the
  `spec_from_idea.md` requirements.)
- Q: Is a wave integrated by cherry-pick or by rebasing each slice branch? → A: Cherry-pick
  (assumed default: one allow entry, subjects preserved, no branch rewriting. Overrule by editing
  Decisions.)

## Success criteria

- `/sdd:start` on an idea ends inside the new worktree with `1. spec.md` committed on the feature
  branch and no question asked after the spec was written.
- With a `design_prompt.md` present, `design.md` is committed before the research wave spawns.
- `implement_plan` runs a two-slice independent plan with `Parallel batches: 2` in two slice
  worktrees and leaves neither worktree, branch nor database behind.
- A plan without `Builds on:` lines runs sequentially and produces the same commits as before.
- `implement_plan` ends with `qa_report.md` on the branch when a QA command and QA file exist.
- `/sdd:document` ticks every documentation item it executed and prints a PR URL.
- `register_design`, `spec_from_idea` and `do_qa` run standalone with no change in behaviour.
- The plan review rejects a plan whose independent slices share a path.
- No FLS name, path or value appears in `claude_plugins/sdd`; the new key lives in
  `.claude/sdd/config.md`.
