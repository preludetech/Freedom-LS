# Plan: chain the SDD steps

Spec: `1. spec.md`. Every path below is relative to the project root. The whole change is to
Claude Code plugin files (slash-command markdown, resources, skills, READMEs) and three project
config files. No Python, template or migration changes.

## What exists today, and what the plan reuses

- **Chaining pattern.** No command invokes another today. The only reuse mechanisms are "read
  `<file>` and follow its steps" at depth 0 (used for `protected/*.md` helpers) and the `Skill`
  tool for another plugin's hook (`document.md` Step 2). The chains in this plan use the first for
  commands of this plugin and the second for a QA command of another plugin, exactly as
  `claude_plugins/sdd/skills/claude-code-authoring/SKILL.md` "Hook mode" already prescribes.
- **Hook-mode precedent.** `do_qa.md` already has an "Inputs from the caller" line (for
  `project-root:` mode) and a per-step "in this mode, skip" bullet list. The new hook-mode entries
  copy that shape.
- **Background spawn precedent.** `spec_from_idea.md` Step 1 spawns research workers "straight
  away, in the background". `start.md` Step 3 reuses that wording for the `start_worktree.md`
  mechanic.
- **Batch mechanics that stay.** `implement_plan.md` Step 2's batch definition, marker commit,
  resume scan, batch brief, Design check and Batch review are unchanged. The batch wave loop wraps
  them.
- **Config reading precedent.** Every reader of `.claude/sdd/config.md` says "(`config.local.md`
  wins)" and treats blank, absent section or absent file alike. `Parallel batches` is read the same
  way.
- **Settings merge precedent.** `init.md` Step 1 item 2 defines "absent means no byte-identical
  string" and never removes an entry. The three new allow entries and the `worktree.baseRef` key
  merge under that rule.
- **Todo helper.** `protected/update_todo.md` already supports `tick:` by unique substring and
  `add_after:`; nothing in it changes.
- **Commit helper.** `resources/commit_and_push.md` is the commit step every chained command keeps.
- **Test gate on plugin prose.** `tests/test_test_tiers.py` fails when a plugin markdown file
  spells out a pytest invocation outside its allow-list. No edited file may add one. The targeted
  tier for any `claude_plugins/*/**/*.md` change runs `tests/test_test_tiers.py`,
  `tests/test_concrete_spec_integration.py` and `tests/test_update_concrete_projects.py`
  (`pyproject.toml` `[tool.test_tiers.tooling]`).
- **FLS overlay.** `claude_plugins/fls-dev/skills/git-worktree-setup/SKILL.md` is the one file
  outside `claude_plugins/sdd` and the project config that changes. FLS names belong there and
  nowhere under `claude_plugins/sdd`.

## Rules every slice follows

- Follow `claude_plugins/sdd/skills/claude-code-authoring/SKILL.md` for every command edit: fan-out
  only at depth 0, `AskUserQuestion` only at depth 0, spawn-time input only, hook mode as that
  skill defines it, `allowed-tools` of a chaining command is the union of its hooks' lists.
- Follow `claude_plugins/productivity/skills/writing-for-agents/SKILL.md` and
  `claude_plugins/productivity/skills/unslop/SKILL.md` for the prose: one source of truth per rule
  (state the chain stop rule once; point at the skill for hook mode instead of restating it), every
  step ends on a checkable completion criterion, no em dashes in new text.
- Keep the spec's vocabulary: batch wave, batch worktree, feature worktree, marker commit, hook
  mode, Setup script, Teardown script, `Parallel batches`, `answers.md`.
- No FLS name, path, app or value under `claude_plugins/sdd`. The check is
  `grep -rniE 'fls|freedom|install_dev|dev_db' claude_plugins/sdd` printing nothing new.
- Never spell out a pytest invocation in a plugin markdown file.
- Never delete a `TODO` or `@claude` comment.
- Each slice ends with the targeted tier passing (the batch runs it through
  `protected/run_test_tier.md`) and `uv run pre-commit run --files <edited files>` clean.

## Slices

Slices are numbered from 1. Each carries `Builds on:` and `Touches:` so that two slices with no
`Builds on:` path between them have disjoint `Touches:` and can run at the same time.

> **Assumed default:** Slice 1 stays first and the README edits stay together in the last slice,
> so a README is stale between slices inside this one branch. Why: keeping the two READMEs out of
> every other slice's `Touches:` keeps those slices disjoint and runnable at the same time, and no
> command breaks while a README lags. To change: fold each README edit into the slice that makes it
> true and add `Builds on:` edges for the shared README paths (Slice 13).
