# Frontend QA: header Login / Sign up buttons keep the post-auth target

## Setup

```bash
uv run python manage.py qa_create_course_access_types   # gated course on DemoDev, plus a learner
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

- Base URL: `http://127.0.0.1:$PORT`
- Confirmation emails land in Mailpit at `http://localhost:8025`.
- Sign-ups must be allowed on the site. If the header shows no Sign up button, enable `allow_signups` on the site's Site signup policy in the admin.
- Use a fresh private window for each scenario so no session or login carries over.
- Note the application-gated course's slug from the command output (or from the course list). Below, `<apply-url>` means `/applications/apply/<slug>/`.

## Scenario 1: sign up through the header button from the sign-in page (the reported bug)

1. Go to the home page while logged out. Open the application-gated course and click Apply.
2. Expect the sign-in page, with a URL containing `?next=%2Fapplications%2Fapply%2F<slug>%2F`.
3. Hover or inspect the header **Sign up** button. Its href must contain the same `next`.
4. Click the header **Sign up** button. The signup page URL must carry that `next`.
5. Complete the form with a new email address and submit. Expect the "verify your email" page.
6. Open the confirmation email in Mailpit, follow its link, and confirm.
7. **Expect:** you are logged in and land on the apply page for that course, not the home page.

## Scenario 2: sign up through the in-form link (must still work)

Repeat Scenario 1, but at step 4 click the sign-up link inside the sign-in form. Use a different new email address. **Expect** the same landing on the apply page.

## Scenario 3: header Login button from the signup page

1. Logged out, click Apply on the gated course, then click the in-form sign-up link.
2. On the signup page, inspect the header **Login** button. Its href must contain the `next` for `<apply-url>`.
3. Click it and sign in as the learner that `qa_create_course_access_types` created (password equals the email).
4. **Expect:** you land on the apply page.

## Scenario 4: no pending target means no change

1. Logged out, go straight to the home page and a course detail page.
2. Inspect the header **Login** and **Sign up** hrefs. They must be exactly `/accounts/login/` and `/accounts/signup/`, with no `next`.
3. Sign in from the header. **Expect** the home page, as before.

## Scenario 5: unsafe `next` is not forwarded

1. Logged out, visit `/accounts/login/?next=https://evil.example.com/`.
2. Inspect the header **Login** and **Sign up** hrefs. **Expect** no `next` and no `evil.example.com` anywhere in them.
3. Visit `/accounts/login/?next=%22%3E%3Cscript%3Ealert(1)%3C/script%3E` (a relative, HTML-breaking value). **Expect** the page renders normally, no script runs, and the header hrefs are well formed (the value is either dropped or URL-encoded).

## Scenario 6: an existing account signs up again via the header

1. Logged out, click Apply on the gated course, then click the header **Sign up** button.
2. Submit the signup form using the existing learner's email.
3. **Expect** allauth's normal enumeration-safe behaviour (the "verify your email" page, plus an "account already exists" email in Mailpit). There is no error page, and the URL still carries `next`.

## Scenario 7: signups disabled

1. In the admin, set the site's signup policy `allow_signups` to off.
2. Logged out, click Apply on the gated course.
3. **Expect** the header shows Login only, with `next` in its href. Signing in lands on the apply page.
4. Turn `allow_signups` back on.

## Scenario 8: mobile width

At a phone-width viewport, repeat Scenario 1 steps 1 to 4. **Expect** the header buttons render and behave the same.
