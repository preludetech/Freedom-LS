# Plan: header Login / Sign up buttons keep the post-auth target

## Problem

An anonymous visitor clicks Apply on an application-gated course. `@login_required` sends them to `/accounts/login/?next=<apply-url>`. That page has two sign-up links:

- The link inside the sign-in form, rendered by allauth from `signup_url`, which carries `?next=<apply-url>`.
- The Sign up button in the header, from `freedom_ls/base/templates/partials/login_prompt.html`, which is a bare `{% url 'account_signup' %}`.

A visitor who signs up through the header button loses `next`. After email confirmation they land on `LOGIN_REDIRECT_URL` (`/`) instead of the apply page. The header Login button has the same defect: on the signup page it drops `next` too.

`freedom_ls/accounts/tests/test_auth_next_target_lost.py` (untracked, written while reproducing the bug) already demonstrates this. Two of its tests fail on the current code.

## Decision

The header Login and Sign up buttons forward the current request's `next`, when it is present and safe, exactly as allauth's in-form links do. With no `next` (or an unsafe one), the buttons render the bare URLs they render today. They don't fall back to the current page, and they aren't hidden on auth pages.

## Existing functionality to reuse

- `allauth.account.utils.passthrough_next_redirect_url(request, url, redirect_field_name)` is what allauth uses (via `get_entrance_context_data`) to build the in-form `login_url` / `signup_url`. It reads `next` from the request, validates it with the account adapter's `is_safe_url`, and appends it with `add_query_params`. Reusing it means the header and the form can't disagree about what counts as a safe `next`.
- `django.contrib.auth.REDIRECT_FIELD_NAME` (`"next"`) is the field name `@login_required` and allauth's views both use.
- The adapter's `is_safe_url` reads `allauth.core.context.request`, which `AccountMiddleware` binds for real requests. Tests that render with a bare `RequestFactory` request must bind it themselves with `allauth.core.context.request_context(request)`. `freedom_ls/accounts/tests/test_signup_form.py` has the existing pattern in its `allauth_request_ctx` fixture.
- `freedom_ls/base/tests/test_header_bar_user_menu.py` renders `partials/header_bar.html` through `render_to_string(request=...)`. Its `TestAnonymousHeader` class is the place for the header-rendering test.

## Where the tag lives

`base` has no runtime dependencies (`docs/app_structure.md`), and every Python `allauth` import already sits in `accounts`. So the tag goes in a new `accounts` tag library, `freedom_ls/accounts/templatetags/accounts_tags.py`, named after the `<app>_tags.py` convention (`base_tags.py`, `content_tags.py`, …). `login_prompt.html` stays in `base` and loads the library with `{% load accounts_tags %}`. That is a template-level lookup, not a Python import, so it adds no `base → accounts` import. It needs no settings change, so downstream projects get the fix without config edits.

### Task 2: `url_with_next` template tag

Create `freedom_ls/accounts/templatetags/__init__.py` (empty) and `freedom_ls/accounts/templatetags/accounts_tags.py`.

Tests first, in `freedom_ls/accounts/tests/test_accounts_tags.py`. Each test builds a `RequestFactory` request, wraps the render in `with request_context(request):` (see Existing functionality), and renders `{% load accounts_tags %}{% url_with_next "account_signup" %}` with `Context({"request": request})`:

- A `@pytest.mark.parametrize` table, since the assertion shape is identical and only the input varies:
  - `next=/applications/apply/x/` → `/accounts/signup/?next=%2Fapplications%2Fapply%2Fx%2F`
  - no `next` → `/accounts/signup/`
  - off-host `next=https://evil.example.com/` → `/accounts/signup/`
- A separate test for no `request` in the context → `/accounts/signup/`. Its context setup differs, so it gets its own test.

Implementation (pseudocode):

```python
from allauth.account.utils import passthrough_next_redirect_url
from django import template
from django.contrib.auth import REDIRECT_FIELD_NAME
from django.http import HttpRequest
from django.urls import reverse

register = template.Library()


@register.simple_tag(takes_context=True)
def url_with_next(context: template.Context, url_name: str) -> str:
    """Reverse `url_name`, carrying the current request's safe `next` along.

    Usage: {% url_with_next "account_signup" as signup_url %}

    Goes through allauth's own passthrough so these links and allauth's
    in-form links agree on which `next` values are safe.
    """
    url = reverse(url_name)
    request: HttpRequest | None = context.get("request")
    if request is None:
        return url
    return passthrough_next_redirect_url(request, url, REDIRECT_FIELD_NAME)
```

`simple_tag` output is autoescaped, which is correct inside an `href`. Tests that string-match hrefs `html.unescape` them (the Task 1 helpers already do).

### Task 3: use the tag in the header login prompt

File: `freedom_ls/base/templates/partials/login_prompt.html`.

```django
{% load accounts_tags %}
{% url_with_next "account_login" as login_url %}
<div class="flex items-center gap-2">
    <c-button href="{{ login_url }}">Login</c-button>
    {% if allow_signups %}
        {% url_with_next "account_signup" as signup_url %}
        <c-button href="{{ signup_url }}">Sign up</c-button>
    {% endif %}
</div>
```

The partial must `{% load accounts_tags %}` itself. A `{% load %}` in a parent template doesn't reach included templates.

## Out of scope

- Hiding the header buttons on auth pages.
- Using the current page as `next` when the request has none.
- Other pages that link to `account_login` without `next` (`403.html`, `403_csrf.html`, `lockout.html`). They aren't reached with a pending `next` in the reported flow.
