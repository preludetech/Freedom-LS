# Research: codebase (design_educator-interface-bulk-action)

All paths are relative to the repo root. Line numbers are as read on 2026-11-09 at branch `design_educator-interface-bulk-action`. The design (`design.md`, 02b/02c/02d PNGs) is a visual reference only; scope is `idea.md`.

## 1. Summary of what exists vs the idea

Today a bulk-action bar already exists, and it works. It is the wrong shape rather than missing:

| Idea item | Today |
|---|---|
| Bar appears above the table on selection | The bar is the **footer** (`table_selection_bar.html`), rendered after the table inside the `<form>`, sharing a row with the pager. Below `lg` it is `fixed` to the viewport bottom. The filter toolbar stays visible above the table at all times. |
| Shows count | Yes: `<span x-text="count"></span> selected · showing a–b of N noun` in a `role="status"` span. |
| Select all | Two routes: the header checkbox (`data-select-all`, this page only) and a prompt link "Select all N matching" (`selectAllMatching`, all rows matching filters across pagination), shown only after the page is fully ticked. |
| De-select all | Only the "Clear selection" link, shown only in `all_matching` mode. Unticking the header checkbox deselects the page. There is **no** always-visible clear control in `keys` mode. |
| Clear button on right | No. |
| Text-only bulk buttons | No. First two actions are `c-button` with `variant="{{ entry.action.variant }}"` (default `secondary`, which is outlined: `border border-primary`; `remove_from_cohort` is `error`, which is filled). |
| "More" is a dropdown | Yes, but labelled "More actions", trigger is `btn btn-secondary btn-sm` (outlined). It already uses `<c-dropdown-menu>`. Playwright finds it by `name="More actions"`. |
| Modal for confirm/forms | Already done: the shared `#app-modal` `<dialog>` (modal_host.html) receives `bulk_confirmation.html` (with `bulk_picker.html` for forms) and then `bulk_result.html`. Restyle only, if at all. |

So the work is mostly (a) moving/re-laying-out the bar in `table_selection_bar.html` + `cotton/data-table.html`, (b) extending `tableSelection`, (c) restyling the buttons and trigger, (d) re-pinning tests. The confirmation/result modal is the existing framework dialog and should be reused, not rebuilt.

## 7. The filter bar it replaces / sits beside

`partials/table_toolbar.html` (243 lines), included at data-table.html:36, **before and outside** the bulk `<form>`. Contents: search form (`<form id="{{ query.key }}-search" hx-get ... hx-preserve>`, `c-panel-search-field`), per-filter `<details>` chips (`c-chip`), "Add filter" `<details>`, "Clear all" link button, Export CSV (`ml-auto`); `md:hidden` mobile row with Filter button (opens `table_sheet.html` through `sidePanel`), Sort `c-dropdown-menu`, Export. The design (02b) shows the selection bar **replacing** the filter bar while a selection exists and the filter bar returning when cleared (02d). Implementation constraints:
- The toolbar is outside the `<form>`; the bar must be inside it (checkboxes, `x-data`, hidden inputs, `formaction`). Either move the toolbar inside the form, or swap the two with the Alpine state (`hasSelection`) on the wrapper, or put `x-data` on a wrapper that spans toolbar + bar + table. The search form and `hx-preserve` search input cannot be nested in the bulk `<form>` (nested forms are invalid HTML), so the safest shape is: wrapper element carries `x-data="tableSelection"`, the bulk `<form>` stays around table + bar, and the toolbar is toggled with `x-show="!hasSelection"` from the same Alpine scope. `tableSelection` currently finds the form via `event.target.closest("form")` and `this.$el` (as the form); moving `x-data` to a wrapper breaks `clearSelection` (`_visibleRowBoxes(this.$el)` expects `$el` to contain the checkboxes, which a wrapper still does) but `this.$refs.modeInput`, `$refs.excluded` must stay in scope.
- `hx-preserve` on the search input and the afterSwap focus handling (alpine-components.js 1053-1172) operate on `[data-table-region]`; hiding the toolbar with `x-show` keeps the input in the DOM, so preserved-input handling is unaffected; removing it from the DOM would be affected.
- The toolbar renders nothing when there is no search/toolbar/sort/export (`{% if searchable or toolbar ... %}` class), so tables with no filters need the bar to render on its own.
- `exports` is referenced but `export_changes`/`exports` are context supplied by `DataTable.get_context`; the Export CSV button is a link, not a bulk action. The design's bar shows "Export" and "Message" as bar actions; the codebase has neither as a `BulkAction`. Do not add them (not in the idea).

## 9. What "select all" means today

- Header checkbox (`data-select-all`): ticks every **visible** row checkbox on the current page only (`toggleAll` -> `_visibleRowBoxes`). Same for the mobile "Select all on this page".
- "Select all N matching" (`selectAllMatching`): switches `mode` to `all_matching`, sets `count = total` (the paginator count, i.e. every row matching the current search/filters across all pages). Offered only after the page is fully ticked and when `total > page`. In this mode rows can still be unticked on the current page, recorded as `excluded` ids; `count = total - excluded.length`. Server resolves it from `request.GET` through `panel.narrow` then `.exclude(pk__in=excluded)` (`resolve_selection`, bulk_actions.py:443). Cap: `action.max_rows` (500) unless the run goes to the background.
- Selection never persists across page/sort/filter: the region is swapped outerHTML and the component rebuilt.
- The design's "Select all 31" (02b) corresponds to all matching rows, i.e. `selectAllMatching`, now offered directly on the bar. The idea's "de-select all" and "Clear" are two controls; the design shows only "Clear" at right plus an indeterminate header checkbox. Clarify: "de-select all" may be the header checkbox untick, and "Clear" the bar button, both calling `clearSelection`.

## 10. How selected IDs are submitted

A single `<form method="post">` per table wraps the rows and the bar. Row checkboxes are `name="keys" value="<pk>"` (tables and cards both, so the same pk can be submitted twice only if both are checked; the cards/table are mutually hidden, and `_visibleRowBoxes` counts only the visible set but the form submits every **checked** native checkbox, hidden or not). `mode` hidden input (`x-ref="modeInput"`), and for `all_matching` hidden `excluded` inputs. The action URL carries the table state as a query string via `{% querystring request.GET %}`. Confirmation fragments re-emit the same data through `bulk_selection_inputs.html`. Server: `parse_selection` (bulk_actions.py:426) -> `Selection(mode, keys, excluded)` -> `resolve_selection`.

## 15. Conflicts and risks

1. **Layout inversion**: the bar is the footer today, sharing a row with the pager, `entry_count` and `showEntryCount`, and is `fixed` below `lg`. Moving it above the table (in the toolbar's slot) means: the pager and entry count must move to the footer (`table_footer.html`) for bulk tables too; the fixed-bottom mode, `barHeight`, `measureBar`, `ResizeObserver`, `x-on:resize.window` on the form, `md:pb-40 lg:pb-0`, `pb-64` and `x-bind:style paddingBottom` wiring become dead code (if the bar is no longer fixed) and four Playwright tests plus the SKILL.md section depend on them. Decide explicitly: drop the fixed behaviour and delete its code and tests, or keep a fixed bottom bar on phones. The idea says "appears above the table"; the design is desktop 1440 only, so phone behaviour is unspecified. Deleting the fixed mobile bar is the simplest but a design call; if kept, on a phone the bar should still stay reachable.
2. **Toolbar is outside the form** (2.1/7): the "replace the filter bar" swap needs Alpine state shared across the two, with no nested forms. `tableSelection` uses `event.target.closest("form")` (update, toggleAll) and `this.$el` as the form (clearSelection); `x-data` on the form is what makes `$refs` resolve.
3. **Select all semantics**: an "All N" control directly on the bar (design: "Select all 31") reuses `selectAllMatching`; existing copy ("All N on this page are selected." prompt, "Changing page, sort or filters clears the selection.") and its Playwright test must be reconciled. `count` in `all_matching` mode is a client calculation; `max_rows` 500 still blocks all-matching over the cap in-request (only background runs are unbounded), and the confirmation then shows the error "N matching; the limit is 500" in the modal.
4. **Header checkbox vs bar checkbox**: the design draws an indeterminate checkbox in the bar. `update()` syncs every `[data-select-all]` in the form, so a bar checkbox with `data-select-all` and `x-on:change="toggleAll"` will be synced for free. The mobile "Select all on this page" row also carries `data-select-all`; tests use `.locator("#x thead").get_by_label("Select all on this page")` to disambiguate, so a third `aria-label` of the same text would break the strict-mode locators in both Playwright files. Use a different label ("Select all" vs "Select all on this page") or scope.
5. **Running state**: `running` hides the actions fieldset, swaps in the "X is running…" status, and disables all checkboxes (`x-bind:disabled="running"`). Must survive the rewrite; tests assert checkbox disabled counts (`2 + 2 * len(learners)`) and `More actions` hidden during the run.
6. **Accessibility pinned**: the `role="status"` span must exist before any selection (test: `get_by_role("status")` count 1 within `#stubs-table`); the status element must be unique within the table region (adding a second `role="status"` breaks `to_have_count(1)`).
7. **Dropdown details**: `dropdownMenu.positionMenu` places a `fixed` panel from the trigger's bottom-right, flips when out of the viewport and closes on page scroll; with the bar at the top of a long table this is fine, but a sticky bar would conflict with `closeOnScroll`. Items are `c-button dropdown="true"`, which carries `text-muted` and cannot show a danger tone or description line without extra `class`; the design's "Deactivate" with a red tone and a hint is not available without scope creep. The `<noscript>` fallback of the "more" actions (lines 68-77) should be kept or consciously dropped (no-JS tests exist at test_data_table_flow.py:571 and test_learners_list_flow.py:243, :281).
8. **Variants**: the text-only look = `variant="ghost"` or `"link"` with `size="small"`; both already exist. Using `entry.action.variant` as today yields secondary (outline) and error (filled) so it must be overridden. Remove-from-cohort's `variant="error"` is the only existing destructive hint; text-only error would need a text colour utility with theme tokens (`test_no_panel_component_uses_raw_colours` applies; use `text-error`).
9. **`BulkAction.variant` is a public attribute** used by `bulk_actions.py:164` and read only by the selection bar; if the bar stops using it, it becomes unused (do not silently leave dead code; either keep it driving a tone or remove it, and update `stub_panels.py`/docs). `extract_panels_framework-4` would carry the API into a package, so decide now.
10. **No-JS**: the bar's controls are real submit buttons with `formaction`; `x-show`-hidden elements (without Alpine, `x-show` is not applied) stay visible, so the whole bar shows, including the clear/select-all controls that would do nothing without JS. Existing behaviour; `x-cloak` is used on some spans only.
11. **Dialog invariants**: any change to `bulk_confirmation.html`/`bulk_result.html` must keep the `<c-modal-footer>` and avoid `<c-button-group>`. The design's modal additions (icon badge, row list, notify checkbox) are out of scope and would require new context (names of selected rows are not currently passed to the confirm template, only `count`/`wording`).
12. **Plugin rule** (CLAUDE.md): `claude_plugins/fls-dev` may be edited to update the panel-framework and alpine-js skills; the generic `ds`, `sdd`, `productivity` plugins may not gain FLS content.
13. **Copy strings** are asserted verbatim by tests (see 12). Changing "More actions" to "More" (the idea says "a 'More' button") requires updating `get_by_role("button", name="More actions")` in 6+ places; Playwright's `name=` matches substring by default, so "More" would still match "More actions", but not the reverse, so rename tests together with the template.
