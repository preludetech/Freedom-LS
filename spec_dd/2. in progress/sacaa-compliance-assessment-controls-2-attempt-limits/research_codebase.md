## 1. `start_attempt` and the lock (learner_progress/attempts.py)

- `start_attempt` 184-227. Inside `transaction.atomic()` it takes `CourseProgress.objects.select_for_update().get(pk=...)` (205), reads `get_latest_incomplete` (206), computes `reusable` via `_kept_open(open_sitting, signing=declaration is not None)` (207-209), and if not reusable calls `finalise_stale_incomplete` (211-215), then `get_or_create_incomplete` (216), then saves an unsaved `FormDeclaration` onto the sitting if there is none yet (217-226).
- `_kept_open` 140-154: open sitting is kept when it has no answers AND (started within `START_REUSE_WINDOW`, 10 s, line 32, OR signing and no declaration row yet). A kept open sitting is the "continue" path the idea says a cap must never block.
- `finalise_stale_incomplete` 113-137: no-op unless `form.submit_on_exit` (126-127); completes the open sitting via `.complete()` (136) unless `last_updated_time <= kept_if_untouched_since` (131-135). So **stale handling only completes a sitting for `submit_on_exit` forms today**; for other forms an old open sitting is not finalised and `get_or_create_incomplete` (84-110) simply returns it (94-96). A completed-by-stale sitting changes the completed count, so the count/wait read has to sit after line 215 and before 216, inside the lock (answer: "stale handling runs first then count is read").
- The cap/wait read must be inside this lock to be race-safe. `close_left_signed_sitting` 157-181 takes the same lock (172) for the declaration path but only finalises, never creates.
- Callers of `start_attempt`: views.py:2071 (`form_start`, non-declaration) and 2119 (`form_declaration` POST); qa_helpers/management/commands/qa_create_quiz_declaration_scenario.py:100. `get_or_create_incomplete` callers: attempts.py:79 (`ensure_attempt`), 216, qa_helpers qa_create_attempt_review_scenario.py:640 and qa_create_quiz_declaration_scenario.py:199 (QA seeding bypassing the gate).
- Completed attempts per record and placement: `completed_attempts(course_progress, collection_item)` 254-273, `FormProgress.objects.filter(course_attempt__course_progress=..., course_attempt__collection_item=..., completed_time__isnull=False).select_related("form").order_by("-completed_time")`. `sittings_at_placement` 238-251 gives `has_open`/`has_completed` flags only. `latest_attempt` 53-66 orders by `-form_progress__start_time` (not completed time). There is no count helper and no helper returning "latest completed attempt's verdict". No stored attempt counter exists.
- Placement vs form: `completed_attempts` keys on `collection_item` (placement); `reports/indexes.py:399` `completed_sitting_ids_of` (used by `attempt_number_of`, gather.py:399) keys on `form_id` under the course progress, so a form placed twice in one course numbers across both placements there but not in `completed_attempts`. Test at learner_interface/tests/views/test_course_player.py:3309 (`test_two_placements_of_one_form_keep_separate_attempts`) pins the placement-scoped behaviour.

## 2. The start gate and views (learner_interface/views.py)

- `FormStartGate` dataclass 1967-1975: fields `redirect`, `collection_item`, `course_progress`, `decision`, `course_index`. Only a redirect outcome exists. `_form_start_gate` 1978-2021 runs access (1987-1991), `_ensure_player_course_progress` (1992), `_blocked_item_redirect(..., refuse_closed=True)` (2000-2008), and the no-record redirect (2010-2020). It "writes nothing except the player's course progress record" (1980). The gate runs **outside** the `start_attempt` lock, so a gate check is advisory; the authoritative check has to be in `start_attempt`.
- `form_start` 2043-2077 (GET that writes): declaration forms go `close_left_signed_sitting` (2060) then redirect to `form_declaration` unless a signed sitting is open (2065-2067); others call `start_attempt` (2071). Then `ensure_served_paper` (2076) and `_form_page_redirect` (2077).

A refusal for a declaration quiz has to come before the learner is asked to sign (gate) and again in `start_attempt` (POST).
- `view_form` 1897-1964: reads `get_latest_incomplete` (1918) and `completed_attempts(...)[:5]` (1927-1929; a sliced queryset, so an attempt count needs a separate query), builds `buttons` via `form_start_page_buttons` (1938-1947, empty list when `paused`), renders `learner_interface/course_form.html` with context keys `course, form, incomplete_form_progress, completed_form_progress, index, page_number, buttons, next_url, previous_url, question_count, page_count` (1949-1962). It is reached from `view_course_item` (1675) after a stale-finalise step at 1583-1594 (submit-on-exit only, skipped when paused or closed), so the start page already sees stale handling before reading counts.
- `course_form_complete` 2346-2501: reads the latest completed attempt (2376-2380; redirects to the item if none, 2381-2386), computes `percentage` (2399-2402) and `quiz_verdict` "passed"/"failed"/None (2409-2411), `item_closed` (2434), `retry_url` = `form_start` URL (2458-2461), context incl. `access_ended, paused, item_closed, quiz_verdict, retry_url` (2477-2494). Retry is shown only when `quiz_verdict == "failed" and not item_closed` and not `access_ended`/`paused` (template line 258-263).
- Existing redirect-with-reason precedent for a refusal outcome: none for form start; closed items redirect via `_blocked_item_redirect`. A new refusal outcome would be a new field on `FormStartGate` (or a render of a reason page), as the idea says.
- `learner_interface/utils.py:285-313`: `outstanding_items` (finish page) links to `learner_interface:form_start` for an item with a completed sitting (`sat_item_ids`, 285-291; url 304-309; `is_retry` 310). The comment at 297-303 says form_start is only offered for a re-sit. A capped or waiting learner following that link would reach the new refusal; the finish page does not know about caps. Test: test_course_player.py:2689 `test_finish_page_names_the_unpassed_quiz_and_links_to_its_retry`, 2781-2811 (start screen vs form_start for unstarted forms).

## 4. Pass/fail of a completed attempt

- Verdict source: `form_engine/queries.py:29-52` `quiz_verdict(form, form_progress) -> bool | None`: None when strategy is not QUIZ or `quiz_pass_percentage is None` (42-43) or `passed()` raises `ValueError` (44-52). `FormProgress.passed()` models.py:501-507 raises `ValueError` if `form.quiz_pass_percentage is None` (502-506); `quiz_percentage()` models.py:479 reads `scores["score"]`/`["max_score"]` and raises when absent. `attempt_completes_form` queries.py:55-67 is `quiz_verdict(...) is not False`.
- Score written by `score_quiz` via `compute_quiz_scores` (models.py:787 def); `FormProgress.complete()` models.py:606.
- Latest completed attempt decides completion: learner_progress/queries.py (research 3 cites 49-91, 125-158); tests pin it: learner_progress/tests/test_models.py:220-232 `test_failing_a_retry_uncounts_a_previously_passed_quiz`, test_models.py:205-217 (fail then pass).
- Reports verdict: reports/gather.py:367-389 `score_attempt` (comment 372-375 explains the two raising calls); at_risk rule reports/at_risk.py:99 reads `passed`.
- Educator panel uses the same: educator_interface/panels/learner/quiz_attempt.py:177, 190.
- Results page verdict is recomputed in the view (views.py:2409-2411), not through `quiz_verdict()`; the start page uses `quiz_verdict()` (utils.py:964). Both agree except where `passed()` raises (the view's `percentage` guard at 2399-2402 covers it).
- A quiz with no verdict (None) has no pass or fail, so "waits apply after a failed attempt only" and "refuse after a pass" both need a stated rule for None (`Form.quiz_pass_percentage` is nullable on the model, models.py:79-83, though QUIZ front matter requires it, schema.py:142-145).
