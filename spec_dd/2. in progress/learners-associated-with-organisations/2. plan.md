# Implementation plan: Learners associated with organisations

Implements `1. spec.md`. Read that first — this plan does not restate the reasoning, only the work.

## How to run this plan

**Order is load-bearing.** Renaming `UserCourseRegistration.user` breaks ~76 files at once, so the
tree does not import cleanly part-way through group A, and the test suite cannot run until group E.
Do not try to keep it green step by step; keep it green at the **group boundaries** marked below.

**TDD applies to new behaviour, not to the rename.** Where a step introduces behaviour that does not
exist today — the `Learner` model, `ensure_learner`, `learner__is_active` gating, `learners_visible_to` —
write the named failing test first. Where a step re-expresses an existing fact through a renamed
field, the existing suite is the test: it must go from red to green with no assertion changed except
the field names.

**Checkpoints.** Run these at the group boundaries that name them:

```
uv run pytest                                   # full suite
uv run manage.py makemigrations --check         # no pending migrations
uv run pre-commit run --all-files               # ruff + mypy + bandit
```

### A1. `Learner` in `freedom_ls/learner_management/models.py`

Write first: `learner_management/tests/test_learner.py` — the unique constraint rejects a duplicate
`(user, organisation)`; the same user may hold rows in two organisations; a `Learner` takes its
`site` from its organisation.

```python
class Learner(SiteAwareModel):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    organisation = models.ForeignKey(
        "freedom_ls_organisations.Organisation", on_delete=models.PROTECT
    )
    is_active = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["user", "organisation"], name="unique_learner_per_organisation"
            )
        ]

    def __str__(self) -> str:
        return f"{self.user} - {self.organisation}"
```

No `related_name` on either FK — §6's queries rely on the default reverse names `learner` and
`cohortmembership`. Place the class **above** `CohortMembership`, which is about to point at it.

The docstring records the one behaviour a reader will not guess: a self-service registration on the
default organisation silently reactivates a removed learner (spec §7.4). Do not cite spec section
numbers in it — see the `code-comments` skill.

### C1. `learner_management/utils.py::is_registered_for_course` (`:67-91`)

Keep the `if not user.is_authenticated: return False` guard exactly where it is.

```python
direct = LearnerCourseRegistration.objects.filter(
    learner__user=user, learner__is_active=True, collection=course, is_active=True
).exists()
if direct:
    return True
return CohortCourseRegistration.objects.filter(
    cohort__cohortmembership__learner__user=user,
    cohort__cohortmembership__learner__is_active=True,
    collection=course,
    is_active=True,
```

**Both cohort conditions must sit in one `filter()` call.** Django applies several conditions on a
multi-valued relation within a single `filter()` to the same joined row; split across two calls they
may match different rows, so a cohort holding the removed learner *and* any other active learner
would grant access. `CohortMembership` is unique on `(learner, cohort)`, so a cohort has many
memberships and this is reachable. The third test above pins it.

```python
def learners_visible_to(
```

## Group E — Factories, seed data, and the test sweep

### E1. `learner_management/factories.py`

```python
class LearnerFactory(SiteAwareFactory):
    class Meta:
        model = Learner

    user = factory.SubFactory(UserFactory)
    organisation = factory.SubFactory(OrganisationFactory)

    @classmethod
    def _create(
        cls,
        model_class: type[django_models.Model],
        *args: object,
        **kwargs: object,
    ) -> django_models.Model:
        return ensure_learner(
            cast(User, kwargs["user"]), cast(Organisation, kwargs["organisation"])
        )
```

**The two `cast()`s are load-bearing.** `SiteAwareFactory._create` types `**kwargs` as `object`
(`site_aware_models/factories.py:39-48`), and matching that signature is what the override requires —
but `ensure_learner` takes a concrete `User` and `Organisation`, so passing `object` straight through
is an `arg-type` failure under this repo's mypy. `factories.py` sits outside `tests/`, so
`pyproject.toml`'s `*.tests.*` override does not cover it. `cast()` to a concrete type keeps this
`Any`-free and `# type: ignore`-free, matching how the codebase already narrows `request.user`.

`SiteAwareFactory` overrides `_create` (`site_aware_models/factories.py:38-48`), so factory_boy's
`django_get_or_create` never fires — delegating to `ensure_learner` is what makes the factory
idempotent, and **that idempotence is load-bearing** for E4. The `site` kwarg arrives from
`SiteAwareFactory` and is deliberately dropped: `ensure_learner` derives it from `organisation.site`.
Type hints match the overridden `_create` — a bare signature fails mypy in pre-commit.

Then:

- `CohortMembershipFactory`: `user = SubFactory(UserFactory)` → `learner = SubFactory(LearnerFactory)`
- `UserCourseRegistrationFactory` → `LearnerCourseRegistrationFactory`: drop `organisation` and
  `user`, add `learner = SubFactory(LearnerFactory)`
- `UserCohortDeadlineOverrideFactory`: `user` → `learner = SubFactory(LearnerFactory)`
- `LearnerDeadlineFactory`: `learner_course_registration` sub-factory renamed
- `RecommendedCourseFactory`: unchanged

**No back-compat `user=` / `organisation=` shim.** A shim would let test code keep thinking in fields
this design removes.
