# Spec: Learners associated with organisations

Follow-on from the shipped Organisation layer (`spec_dd/3. done/2026-08-21_09:09_organisations`) and
the merged terminology rename (`spec_dd/3. done/2026-08-22_15:42_learner-terminology-rename`).

---

## 1. Summary

Introduce an explicit **`Learner`** model: a row recording that a `accounts.User` is associated with
an `Organisation`. A user may be a Learner of several organisations on the same Site.

Today "who belongs to this organisation" is derived, never stored. `users_visible_to`
(`freedom_ls/learner_management/queries.py:196-218`) answers it by unioning "members of cohorts in
this organisation" with "holders of a `UserCourseRegistration` in this organisation". There is no way
to say a person is one of an organisation's learners *before* a registration exists, and no way for
an educator to curate the roster at all.

This cut ships:

- the `Learner` model in `freedom_ls/learner_management/`, with one migration (`0002_learner`);
- an idempotent `ensure_learner(user, organisation)` helper, plus `post_save` receivers on
  `CohortMembership` and `UserCourseRegistration` that delegate to it;
- a `rebuild_learners` management command that derives missing rows from existing data;
- a behaviour change to `users_visible_to`'s second branch;
- educator roster screens: the existing **Users** section becomes **Learners**, with an add action
  and a remove action;
- the four `*_learner` permission codenames registered in `role_based_permissions/registry.py`;
- QA seed data for the three states that only exist because of this cut.

### 1.1 This reverses a stated non-goal of the Organisation cut

The Organisation cut said: "**No organisation membership object.** A learner's organisation comes
from their registrations" (`spec_dd/3. done/2026-08-21_09:09_organisations/1. spec.md:1079`).

That call was made to avoid Docebo's multi-branch cleanup pain. Docebo's walk-back was a reaction to
several branch admins editing one shared, mutable *profile* — not to multi-org membership as such.
FLS already avoids that trigger: profile fields live on the one Site-wide `accounts.User`, and
Organisation is explicitly not a profile-ownership boundary. **The reversal is deliberate.** It is
recorded here, in full, so nobody re-litigates it from the old document.

---

## 2. Why this matters

**A roster you cannot curate is not a roster.** An educator running an organisation has no way to say
"this person is one of ours" until the person registers for something. Pre-building a cohort's intake,
or tracking someone who has been told they will join, is not expressible.

**The "invisible learner" is currently reachable.** Someone can be actively studying through an
organisation while being absent from any list their educator can see, or present on a list while
having no relationship to the organisation at all. Across every product surveyed
(`research_cross_org_identity_ux.md`), this state is a gap in the market rather than a solved
problem — the closest prior art is Docebo's pipe-delimited CSV export and Moodle's cohort-sync forum
folklore, both widely reported as confusing. The removal rule in §7 makes the first half of that state
**unreachable by construction**, which is a stronger answer than any product surveyed has. That is
the single strongest claim this cut makes against the prior art.

**Provenance is what makes repair safe.** Without knowing *why* a membership row exists, a repair
command cannot rebuild derived rows without clobbering a hand-curated roster. No product researched
ships a provenance field on the membership row (`research_multi_org_learner_modelling.md`), and
Docebo's cleanup story — export branches as a pipe-delimited column, correct, re-import — is the cost
of not having one.

## 3. Data model

`Learner`, a `SiteAwareModel`, in **`freedom_ls/learner_management/models.py`**.

| Field | Definition | Why |
|---|---|---|
| `user` | FK `settings.AUTH_USER_MODEL`, `on_delete=CASCADE` | Matches four of the five existing user FKs in the app. No `related_name` — the default reverse query name `learner` is what `Q(learner__organisation=…)` in §6.1 relies on |
| `organisation` | FK `freedom_ls_organisations.Organisation`, `on_delete=PROTECT` | Matches `Cohort.organisation` (`models.py:17-20`) and `UserCourseRegistration.organisation` (`:54-57`), and backs up the admin's refusal to delete organisations |
| `is_active` | `BooleanField(default=True)` | Roster state. `False` means "removed from this organisation", never "deleted" |
| `source` | `CharField(max_length=20, choices=Source.choices, default=Source.AUTO)` | Which of the two creation paths made this row |
| `added_by` | FK `settings.AUTH_USER_MODEL`, `null=True`, `blank=True`, `on_delete=SET_NULL`, `related_name="+"` | Set for manual adds only; accountability for a deliberate roster action |
| `created_at` | `DateTimeField(auto_now_add=True)` | |

```python
class Learner(SiteAwareModel):
    class Source(models.TextChoices):
        AUTO = "auto", _("Automatic")
        MANUAL = "manual", _("Manual")

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["site_id", "user", "organisation"],
                name="unique_learner_per_organisation",
            )
        ]
        indexes = [models.Index(fields=["organisation", "is_active"])]
```

### 3.1 The decisions inside that table

**`related_name="+"` on `added_by` is load-bearing, not decoration.** Without it the reverse accessor
collides with `Learner.user`'s. It is also the field most likely to be dropped by accident. The shape
is copied byte-for-byte from `ObjectRoleAssignment.assigned_by`
(`freedom_ls/role_based_permissions/models.py:96-103`), which is the closest structural analogue to
`Learner` in the repo — a `SiteAwareModel` join row with a user FK, an `is_active`, an actor FK and an
`auto_now_add` timestamp. The convention is unanimous across four models.

**The unique constraint spells `site_id`, not `site`.** This is not cosmetic.
`ConstraintValidationFormMixin` (`freedom_ls/site_aware_models/forms.py:20-58`) documents the
consequence: `UniqueConstraint.validate()` compares the exclusion set of field *names* against the
strings in `fields` verbatim, so spelling `"site"` makes any `ModelForm` that does not render `site`
skip the whole constraint at clean time and fail with an `IntegrityError` 500 instead of a field
error. `learner_management`'s three existing constraints all use `"site_id"` (`models.py:26`, `:70`,
`:126`); `organisations` uses `"site"`. **Follow the local convention.**

**`site` is belt-and-braces, not load-bearing.** An `Organisation` already belongs to exactly one
Site, so `(user, organisation)` is already unique site-wide. The column is included to mirror
`unique_user_course_registration` and to keep the model consistent with every other `SiteAwareModel`.

**`source` uses `TextChoices` with lowercase values.** Two conventions coexist in the tree:
`TextChoices` throughout `content_engine` (`CourseVisibility` at `content_engine/models.py:47-53` is
the model to copy), and plain constants plus a `CHOICES` list in the two most recently shipped apps
(`reports/models.py:11-21`, `webhooks/models.py:53-60`). **Naming the choice explicitly matters**,
because an implementer will otherwise copy whichever they read last. `learner_management` has no
choice field of any kind today, so this is the app's first. No `db_index` on `source` — nothing
filters on it in a hot path; `rebuild_learners` filters on it once per run.

**`source` is the field that makes the rest of the design safe.** It is what lets `rebuild_learners`
rebuild auto-derived rows without ever clobbering a roster an educator curated by hand. It is a
net-new idea relative to the prior art, not a copy of it, and it must **not** grow into a status
field.

**No `pending`/`invited` status.** Every product that has those states uses them to drive
self-registration or SSO flows this cut is not building. Adding the field now with nothing to drive
it is the version of a status field the research found products regret. A boolean also earns its keep
here because the one thing an enum would buy — distinguishing "never added" from "removed" — is
already carried by row existence plus `source`.

**`is_active` is filtered explicitly at every call site, never in a manager.** Three reasons, in
decreasing order of force:

1. The default manager slot is already occupied. `Learner.objects` is `SiteAwareManager`, which
   already overrides `get_queryset()` to filter by site.
2. It would break `ensure_learner`. A manager that hides `is_active=False` rows makes
   `get_or_create`'s `get` half miss every removed learner, so re-adding one would attempt an INSERT
   and hit the unique constraint. Reactivation is a first-class requirement (§5.1), so the row must
   stay findable.
3. Django's own guidance: a default manager "should not override `get_queryset()` to filter out any
   rows" because it may be used as the base manager. Every `is_active` in `freedom_ls/` is filtered at
   the call site; there is no filtering default manager anywhere in the codebase.

### 3.2 App placement

**`learner_management`, not a new app and not `organisations`.** `learner_management` already depends
on both `organisations` and `accounts` (`docs/app_structure.md:81`, `:84` — both edges verified), so
`Learner` adds **zero new edges**. Putting the sync receivers in `organisations` instead would force
`organisations` — whose only runtime deps are `base` and `site_aware_models` — to import
`learner_management` models as signal senders, inverting the edge the Organisation cut deliberately
established (its Decision 2). Regenerate `docs/app_structure.md` with `/ds:app_map` regardless.

**Landmine: `accounts` must never gain a runtime dependency on `learner_management`.** That edge is
test-only today (`docs/app_structure.md:116`, dashed) and the invariant is currently unbroken. Nearly
every app depends on `accounts`, so wiring Learner creation into the signup flow itself would create
a cycle through most of the codebase. Signup alone creates no registration or cohort membership
today, so nothing needs this — but it is the direction a naive implementation reaches for.

## 4. Authorisation

### 4.1 The naive route is silently broken

The idea proposed registering `view_learner`/`add_learner`/`change_learner`/`delete_learner` and
granting them to roles. **That does not work, and it fails without an error.**

`_filter_perms_for_content_type` (`freedom_ls/role_based_permissions/utils.py:123-137`) keeps a
permission only when `app_label == ct.app_label` and the codename exists for that content type.
`sync_user_object_permissions` applies that filter before assigning (`utils.py:168-169`). So a role
with `assignment_scope=SCOPE_OBJECT` assigned on an `Organisation` can only ever carry
`freedom_ls_organisations.*` codenames. `freedom_ls_learner_management.add_learner` is dropped before
`assign_perm` is called, and `has_perm` returns `False` forever. It passes `validate_role_permissions`
— which only checks registry membership (`validate_role_permissions.py:76-81`) — and then fails
silently at runtime.

The constraint is already documented at `freedom_ls/role_based_permissions/roles.py:63-69`. The same
filter applies to `SCOPE_SITE` assignments, which sync against the `Site` content type, so
**`site_admin`'s four existing `*_cohort` grants (`roles.py:24-27`) are already dead strings.** Do not
copy that pattern believing it grants anything.

### 4.2 What this cut does instead

**Register the four codenames; grant them to no role; gate in Python on the organisation.**

Add to `freedom_ls/role_based_permissions/registry.py`, alongside the `*_cohort` block at `:53-56`:

```python
    "freedom_ls_learner_management.view_learner": "Can view learner",
    "freedom_ls_learner_management.add_learner": "Can add learner",
    "freedom_ls_learner_management.change_learner": "Can change learner",
    "freedom_ls_learner_management.delete_learner": "Can delete learner",
```

Django generates these codenames at the next `migrate` once the model exists. They are registered so
the admin and future work have them, and so `registry.py` stays a complete inventory. **No role in
this cut holds them.**

The effective gate for both roster actions is:

```python
user.has_perm("freedom_ls_organisations.view_organisation", organisation)
```

— the exact check `users_visible_to` already uses (`queries.py:214-216`) and `cohorts_visible_to`
uses (`queries.py:154-156`). This adds **no new authorisation surface**, which is precisely what the
idea asks for.

**This is deliberately minimal wiring.** A larger build-out of the educator interface is planned
separately and will take roster authorisation over the line. This cut does not attempt to fix the
cross-content-type permission sync, and does not add a custom `manage_organisation_learners`
permission on `Organisation`. Both are real options; both are out of scope here.

**Use the narrow check, not `organisations_accessible_to`.** That helper (`queries.py:105-127`) is a
**union** of role-holders and per-cohort-grant holders. Using it for roster writes would hand a
cohort-only educator write powers over the whole organisation's roster. The roster actions are bounded
to organisations the educator holds an **organisation role** on — the first branch only.

**Derive the per-object check from the queryset, never reimplement it.** FLS's convention is
queryset-first, stated at `can_view_cohort` (`queries.py:186-193`): expressed through the queryset
"so a per-object check can never disagree with the queryset that populates a list or a dropdown".

## 5. Keeping rows in sync

Three parts, all shipped together.

### 5.1 `ensure_learner(user, organisation, source=Source.AUTO, added_by=None)`

The single source of truth for how a `Learner` row gets made. Idempotent. It also **reactivates** a
row that was previously removed: a fresh registration or cohort membership is a live signal of
re-association, and leaving it deactivated would recreate the invisible-learner state the removal rule
exists to prevent.

```python
learner, created = Learner._base_manager.get_or_create(
    site=organisation.site,
    user=user,
    organisation=organisation,
    defaults={"source": source, "added_by": added_by},
)
if not created and not learner.is_active:
    learner.is_active = True
    learner.save(update_fields=["is_active"])
return learner
```

**`_base_manager`, not `objects`. This is the highest-risk detail in the cut.**
`SiteAwareManager.get_queryset()` (`freedom_ls/site_aware_models/models.py:43-50`) ANDs the ambient
thread-local site onto every lookup when a request exists, and **silently returns unfiltered rows when
one does not**. `ensure_learner` runs from a `post_save` receiver that may fire under a request for a
different Site, and from `rebuild_learners` under no request at all. Using `objects` would make the
`get` half of `get_or_create` miss whenever a different site is ambient, so the `create` half would
attempt a second INSERT and hit the unique constraint. This exact bug has an in-repo docstring
(`freedom_ls/organisations/signals.py:26-34`) and an in-repo regression test
(`freedom_ls/organisations/tests/test_signals.py:49`). Copy both.

**Pass `site=organisation.site` explicitly.** Do not rely on `_set_site_from_request()` — it only
populates `site` when a thread-local request exists, and only when `site_id` is already falsy.

**`update_or_create` is rejected.** It would overwrite `source` and `added_by` on every registration
save, turning a curated `manual` row into an `auto` one — destroying exactly the distinction the
design rests on. `get_or_create` plus a targeted `save(update_fields=["is_active"])` writes `source`
and `added_by` once, at creation, and never again. **Reactivation must not touch `source`**; the
`update_fields` list enforces that mechanically.

**Plain `get_or_create`, with no `IntegrityError` retry wrapper — and that is a decision, not an
oversight.** `get_or_create` can genuinely raise `IntegrityError` under concurrency (Django tickets
#24009, #7402, #12579). Handling it correctly would require wrapping the call in its own
`transaction.atomic()` savepoint, because catching a `DatabaseError` inside an enclosing atomic block
poisons that transaction — and the enclosing block here is `UserCourseRegistration.save()`'s, which
contains the registration insert. FLS is a single-site LMS expecting 2–5 organisations per Site with
no concurrent-registration pressure; the unique constraint makes the race produce an error rather than
a duplicate; the model is explicitly best-effort with `rebuild_learners` as the recovery path. The
savepoint costs a round-trip on the hot path and buys almost nothing. The precedent agrees:
`_ensure_default_organisation` (`organisations/signals.py:35-42`) uses plain `get_or_create`.

### 5.2 `post_save` receivers

A new `freedom_ls/learner_management/signals.py`, connected from a new `ready()` on
`LearnerManagementConfig` (`apps.py`, which has none today):

```python
def ready(self) -> None:
    from freedom_ls.learner_management import signals  # noqa: F401
```

One receiver function decorated for both senders, following
`freedom_ls/learner_progress/signals.py:99-125` exactly:

```python
@receiver(post_save, sender=CohortMembership)
@receiver(post_save, sender=UserCourseRegistration)
def ensure_learner_on_save(
    sender: type[models.Model],
    instance: models.Model,
    raw: bool = False,
    **kwargs: object,
) -> None:
```

**`raw` is an explicit keyword parameter with an early return**, not pulled out of `**kwargs`. `raw`
saves come from `loaddata`, which writes exactly the rows in the fixture; deriving extra `Learner`
rows from a fixture load would invent data the fixture author did not ask for. Django's own reference
says of `raw`: "One should not query/modify other records in the database as the database might not be
in a consistent state yet."

**Not gated on `created`, and a reviewer will ask why.** `created` is only `True` on insert, so a
`created`-gated receiver would miss the "learner was removed, then their existing registration was
re-saved" path — which is exactly the reactivation requirement. Since `ensure_learner` is idempotent
by construction, calling it on every save costs one indexed lookup and is strictly safer. Note the
contrasting precedents that *do* gate: `learner_progress/signals.py:120-125` declines on
non-transitions, and `UserCourseRegistration.save()` gates its webhook on `self._state.adding`
(`models.py:76`) — both because those side effects are not idempotent.

**No `dispatch_uid`.** These are module-level functions connected via `@receiver` at import time;
Python object identity already dedupes them and a repeated import is a no-op. `dispatch_uid` is used
nowhere in the repo, and neither `learner_progress/signals.py` nor `organisations/signals.py` nor
`reports/signals.py` uses it. Adding it here would be inconsistent noise.

**Why a signal rather than an explicit call.** Django's docs advise preferring an explicit call when
sender and receiver are both inside your project — and that advice is right, but its premise does not
hold here. That sentence is explicitly about *custom* signals; `post_save` is a built-in. FLS ships as
a submodule into projects **designed** to extend it, so a downstream project's own code creating a
`UserCourseRegistration` is definitionally outside FLS's project and an explicit call can never fire
there. A signal covers code FLS has never seen, as long as it calls `.save()`. FLS has already made
exactly this call twice — for `learner_progress` (`signals.py:6-8`) and for `organisations`
(`signals.py:49-54`, "so `site_aware_models` keeps its zero outgoing edges, and so the admin, the
shell and `SiteFactory` are covered too"). The honest cost the precedent also records: a receiver
naming its senders is not inherited by subclasses the way a `save()` override would be.

**Zero call-site changes.** `SiteAwareFactory._create` calls `obj.save()` directly
(`freedom_ls/site_aware_models/factories.py:38-48`), so every factory call site fires the receiver
with no factory changes — 157 `UserCourseRegistrationFactory(` occurrences across 45 files and 91
`CohortMembershipFactory(` across 23 files, 248 across roughly 62 files. (The idea's "~448 across 58
files" is a different, all-factories metric; the conclusion is unchanged.) The **31** QA seeding
commands under `qa_helpers/` — which pytest never collects, and which were an easy-to-miss trap in the
Organisation cut — are covered for the same reason. The idea's count of 14 is stale.

### 5.3 Webhook ordering — resolved, and improved

The idea flags an ordering hazard around the `course.registered` webhook. **Ordering is already
correct by construction.** In `UserCourseRegistration.save()`
(`freedom_ls/learner_management/models.py:75-103`), `super().save()` at line 77 reaches Django's
`save_base`, which sends `post_save` immediately after `_save_table` — so `ensure_learner` runs there
— and only then does control return to line 78-103 and call `fire_webhook_event` at line 94. **The
`Learner` row is written before the `WebhookEvent` row is even created, in the same transaction, with
no extra work.**

What was genuinely open is *commit* ordering. There is no `transaction.atomic` or
`transaction.on_commit` anywhere in that path, and under `ImmediateBackend` — used in dev and in the
test suite (`config/settings_base.py:413-417`) — the HTTP delivery runs inline inside `.save()`, so a
consumer can be called while the registration and the `Learner` row are still uncommitted.

**Decision: defer the webhook fire to `transaction.on_commit`.**

```python
def save(self, *args: object, **kwargs: object) -> None:
    is_new = self._state.adding
    super().save(*args, **kwargs)
    if is_new:
        ...
        transaction.on_commit(lambda: fire_webhook_event("course.registered", payload))
```

A consumer may reasonably expect the association to exist when the event arrives, and it now does —
committed, not merely written. The webhook system has no production implementation and FLS is not
live, so there is nothing downstream to protect.

**Do not wrap `ensure_learner` in `on_commit`.** That would be actively harmful: it moves the
`Learner` insert to *after* the `WebhookEvent` is created, and removes the insert from the
registration's transaction, so a rollback would leave an orphan `Learner` row. The receiver stays on
`post_save`, inside the transaction.

**Test impact is small.** `freedom_ls/learner_management/tests/test_registration_webhook_events.py`
already runs under `@pytest.mark.django_db(transaction=True)` with the comment "transaction=True so
that on_commit hooks for webhook event delivery fire under test" — the tests were written expecting
this. Any test that is not already `transaction=True` uses
`django_capture_on_commit_callbacks`. Payload values must be captured **before** the callback is
registered, not read off `self` inside the lambda.

**`fire_webhook_event` silently returns outside a request context** (`webhooks/events.py:22-24`), so
`rebuild_learners` and `migrate` fire no webhooks. That is the desired behaviour and needs no guard.

### 5.4 Best-effort, and say so

**State plainly, in the model docstring and the upgrade notes, that `Learner` rows are best-effort and
eventually consistent, not a transactional guarantee**, and name `rebuild_learners` as the recovery
path. The residual gap is `bulk_create()`, `queryset.update()` and `loaddata` — all silent, no
exception, no log. The educator roster would simply under-count, with nothing prompting anyone to
notice.

There is a direct stylistic precedent for this docstring, including the wording pattern and the
matching test: `learner_progress/signals.py:108-111` and
`learner_progress/tests/test_completion_signal.py:73-87`. Write it as reasoning, with no citation of
this document — per the `code-comments` skill, section references in code are forbidden.

## 6. Educator interface

### 6.1 `users_visible_to`'s second branch becomes a direct fact

At `freedom_ls/learner_management/queries.py:217`:

```python
# before
visible |= Q(usercourseregistration__organisation=organisation)
# after
visible |= Q(learner__organisation=organisation, learner__is_active=True)
```

**This is a behaviour change, not a refactor.** The set of visible users shifts in *both* directions:

- **Newly visible** — a manually added learner with no registration at all.
- **Newly invisible** — someone holding a registration whose `Learner` row was removed, or never
  created (a row written by `bulk_create`/`update()` before a `rebuild_learners` run).

Both directions need a test (§11).

**The cohort branch survives unchanged**, and so does `.distinct()`. The first branch exists because a
per-cohort guardian grant says nothing about people outside that cohort: an educator holding only a
cohort grant must never see the organisation's individually-registered roster. That constraint is
about the *educator's* authorisation level, not about how a learner's association is stored, so
`Learner` does not touch it. `.distinct()` stays for the same reason it exists now — two join paths
into `User`.

**The function keeps its name.** It returns `User` rows, which is what it is called after, and
renaming it would churn three call sites and eight tests for no behavioural gain. The *interface*
concept becomes "learner" (§6.2); the queryset helper's name is internal.

**Untouched:** `organisation_for_learner_course` and `latest_registration` answer a different question
("which organisation is this course being studied through") and are not superseded.
`CohortCourseProgressPanel` does not funnel through `users_visible_to` at all and is out of scope.

### 6.2 The Users section becomes the Learners section

**Educators should not browse Users; they browse Learners.** The educator interface has exactly three
sections (`educator_interface/views.py:1147-1149`): Cohorts, Users, Courses. The Users section is
already organisation-scoped through `users_visible_to`, and with §6.1 in place a manually added
learner appears there automatically. So this cut **repurposes that section** rather than adding a
fourth. Two overlapping people-lists in one interface would be confusing, and a new config would need
its own data table, seeder branch and authorisation declaration.

Changes:

| Today | After |
|---|---|
| `UserConfig.url_name = "users"` | `"learners"` |
| `UserConfig.menu_label = "Users"` | `"Learners"` |
| `UserConfig` / `UserDataTable` / `UserInstanceView` | `LearnerConfig` / `LearnerDataTable` / `LearnerInstanceView` |
| `url_path_template: "users/{pk}"` | `"learners/{pk}"` |

`model` stays `User` — the rows are people, and `Learner` is the association, not the person. The
class rename is mechanical and keeps the interface coherent with the terminology rename that just
shipped.

**No new URL patterns.** `educator_interface/urls.py:5-19` is two `re_path`s — `root` and a catch-all
`organisations/<organisation_slug>/<path_string>` — and everything else is a `path_string` walked by
`panel_framework` (`panel_framework/views.py:343-376`). Roster actions become
`.../__actions/<action_name>`. Links are built with
`reverse("educator_interface:interface", kwargs={"organisation_slug": …, "path_string": …})`.
**Inventing new URL names here would be fighting the routing design.**

The `users/` → `learners/` path change is user-visible and breaks any bookmarked URL. It goes in the
upgrade notes. `educator_interface/tests/test_config_authorisation.py` enumerates `interface_config`
rather than `urlpatterns`, so it adapts; its `_seed_instance` dispatcher (`:40-61`) needs its branch
renamed.

**Keep the prefetch-scoping discipline verbatim.** `LearnerDataTable.get_queryset` already wraps
`users_visible_to` in two `Prefetch`es that re-scope `cohortmembership_set` and
`usercourseregistration_set` to the organisation (`views.py:166-179`), with a comment explaining that
a learner studying through two organisations would otherwise list both. That comment is the exact
hazard this cut widens, and the prefetches must stay scoped.

### 6.3 Add a learner

A list-level `FormPanelAction` on `LearnerConfig.get_actions`, mirroring `CreateCohortAction`
(`views.py:836-838`).

**It is a lookup, never an account creation.** The duplicate-account trap is the most consistently
reported sharp edge across every vendor researched: Canvas's remedy is an admin-arbitrated merge with
no undo; Docebo silently creates a second abandoned account that restarts the learner's history;
Moodle admins resort to fake emails to satisfy uniqueness. The best pattern found is from adjacent
B2B SaaS — Microsoft Entra External ID's detect-and-attach. **The add flow searches existing users on
this Site and must not create accounts.**

**v1 is an exact-email lookup**, not a typeahead. No autocomplete exists anywhere in the educator
interface — the only typeahead in the product is Django admin's `autocomplete_fields`, which is
admin-only. Building one is out of scope for minimal wiring. A single email field in a modal,
submitted, resolved.

**The lookup must not reuse `DataTable.search_fields`.** That search filters `get_queryset` — i.e.
`users_visible_to` — so it can only find people *already* visible in the organisation, which is
exactly wrong for adding someone who is not yet a learner of it.

**Where it lives:** a new helper in `freedom_ls/accounts/utils.py`, the declared home for shared
account helpers. It already imports only `site_aware_models` plus its own `config`/`models`, so a
lookup helper adds **zero new edges** and — critically — keeps `accounts` free of any dependency on
`learner_management` (§3.2's landmine). `learner_management → accounts` already exists, so the add
flow imports it freely. The same "does this email already have an account here?" question will be
asked by any future self-registration path, which is why it belongs there rather than in the view.

**Scope: this Site, and nothing is said about other Sites.** `accounts/models.py:68` makes
`User.email` globally unique across *all* Sites, while `UserManager.get_queryset` site-filters. So an
email can be held by a user on a sibling Site: the lookup finds nothing, but creating that account
would fail the global constraint. **The message is the same either way — "No account with that email
on this site."** Telling one tenant's staff that a person has an account on another tenant's site is a
cross-tenant existence disclosure, and the isolation discipline the Organisation cut committed to
rules it out. The lookup uses the site-filtered `User.objects`, never `_base_manager`.

On success: `ensure_learner(user, organisation, source=Source.MANUAL, added_by=request.user)`.
On no match: **422** with the modal re-rendered and the reason named, following
`FormPanelAction.form_invalid` (`panel_framework/actions.py:72-87`).

### 6.4 Remove a learner

An **instance-level** action on `LearnerInstanceView.get_actions`, mirroring
`CohortInstanceView.get_actions` (`views.py:776-790`), which returns a `DeleteAction`.

**Deliberately instance-level, not a per-row button.** There are no row-level actions anywhere in
`panel_framework` today — the six cell templates render links, text and booleans, and none renders a
button, a form, or an HTMX-posting control. Building them is a net-new pattern, and there is a
standing TODO asking for them (`educator_interface/views.py:104-112`) that **must not be deleted**.
An instance-level action delivers "one at a time" without introducing that pattern.

Confirmation follows `panel_framework/partials/delete_confirmation.html`: a `<c-modal>` with an
explicit trigger slot, `hx-post`, `hx-disabled-elt` to prevent double-submit, and a loading state.
**Never `hx-confirm`** — it appears nowhere in the tree.

See §7 for the refusal rule, which is the substance of this action.

### 6.5 Copy

The roster screens say "learner" consistently, and the pass audits for "user" leaking through where
"learner" is meant — precisely where Absorb's and Docebo's own UI copy gets sloppy. Per the
`brand-guidelines` skill: "learners", not "students"; error messages name the specific problem and
suggest a specific fix, in plain language, with no jargon codes and **no exclamation points on
routine actions**.

Icons are `<c-icon name="…" />` by semantic name only, `size-4` inside tables. `user`, `check`,
`close`, `error` and `warning` already exist.

## 7. Removal

**Removing a learner is soft, and it is refused while they are still active in the organisation.**

An educator may remove a learner from an organisation only when that learner has **no active
`UserCourseRegistration` in it and no `CohortMembership` in any of its cohorts**. Otherwise the action
is refused with an explanation naming what is blocking it and what to do about it.

**This is the point of the rule.** It makes "enrolled but not on the roster" — someone actively
studying who has silently vanished from their educator's list — **unreachable by construction**.

### 7.1 The refusal

**422 with a re-rendered fragment carrying the reason**, matching `FormPanelAction.form_invalid`'s
status code and the repo-wide "HTTP 422 for HTMX validation errors" rule. Not a 403 (the educator may
do this in general), not a silent no-op, and not a bare status — `alpine-components.js:9-14` swaps
422 bodies, so the response must be renderable HTML.

**There is no precedent for a `PanelAction` that refuses with an explanation.** `has_permission`
returning `False` merely hides the button, and `DeleteAction.handle_submit` (`actions.py:257-265`) has
no error path at all — it deletes unconditionally. **This cut introduces the pattern**; say so.

**Two layers, following `reports/views.py:79-106`** — which pre-checks for the friendly message and
also catches the race, both producing the same text:

1. `render()` pre-checks and shows the blocking reason in place of the confirm button, so a blocked
   removal is visible before the educator commits to it.
2. `handle_submit()` re-checks inside `transaction.atomic()` and returns 422 if blocked, so a
   registration created between check and write cannot slip through.

The check lives in the action, **not in `Learner.clean()`** — `clean()` is not run by `save()`, and
the refusal is about a user action, not about row validity.

Brand-compliant copy names the problem and the fix:

> Ana Silva still has 2 active course registrations with Northside, and is a member of Year 10
> Science. Deactivate those registrations and remove her from the cohort before removing her from the
> organisation.

Not: "Error: cannot remove learner — active enrolments detected."

### 7.2 What removal does and does not do

Removal sets `is_active = False`. It **never** cascades to `UserCourseRegistration`,
`CohortMembership`, or any progress model.

That cascade is precisely where Moodle's cohort sync burned people: removing cohort membership
destructively unenrols the user from every synced course *by default*, and keeping the enrolment while
merely suspending access is opt-in configuration. Docebo's community advice is to move a departed user
to a separate branch and leave enrolments untouched, because "if you were to unenroll users who had
completed courses, you would actually be removing their learning history". Absorb made soft the safe
default explicitly. **The cross-product rule: every product that got this right did so by never
letting the higher-level membership object's lifecycle delete the lower-level enrolment rows.**

FLS is better placed than any product surveyed to avoid it cheaply, because `UserCourseRegistration`
already carries its own `is_active` and its own `organisation` FK — the two lifecycles are decoupled
by construction, not by discipline. **The non-cascade is an explicit invariant with a test** (§11).

Re-adding a removed learner flips `is_active` back, via the same `ensure_learner` helper. There is no
history to restore, because none was ever at risk.

**No hard delete on `Learner` in this cut**, following the discipline the Organisation cut applied to
`Organisation` itself. `LearnerAdmin` overrides `has_delete_permission` to return `False`, copying
`OrganisationAdmin` (`organisations/admin.py:22-25`). This also sidesteps a real compliance question:
"delete this learner" from Organisation A is meaningless when the same person also studies with
Organisation B on the same Site, and legal retention can override an erasure request outright.

### 7.3 The state this leaves open, deliberately

A removed learner with no registration and no cohort membership disappears from the Learners list
entirely — there is no "show removed" filter in this cut. Re-adding them goes through the same
add-a-learner lookup (§6.3), which reactivates the existing row rather than creating a second one.
That is the whole reason `ensure_learner` reactivates rather than inserting.

FLS lands in the "ghost rows that outlive their trigger" trap by design: removal is soft and
`rebuild_learners` only inserts. The deliberate lever that resolves it is manual removal by an
educator — which is exactly what the products that got this right (Canvas, Absorb, Docebo's advised
practice) provide, and what the ones that got complaints lacked.

## 8. The `rebuild_learners` command

`freedom_ls/learner_management/management/commands/rebuild_learners.py`.

**Ships in this change, not as a follow-up.** With no backfill migration it is the *only* thing that
derives `Learner` rows from existing `UserCourseRegistration` and `CohortMembership` data, and the
only mitigation for the gaps a signal cannot close.

**It only inserts missing rows. It never deletes, never touches a `manual` row, and never reactivates
a removed learner** — otherwise every run would resurrect exactly the people educators deliberately
took off the roster, turning the deliberate lever of §7 into a no-op.

Implement that as an explicit **set difference** — derived `(user, organisation)` pairs minus existing
`Learner` pairs — not as `get_or_create` in a loop. `get_or_create` would reactivate nothing but would
also mask a bug where the derivation is wrong.

### 8.1 Structure

**`djclick`, not `BaseCommand`.** All ~48 management commands in `freedom_ls/` use `djclick`;
`add_arguments`, `self.stdout.write`, `self.style` and `CommandError` have **zero** occurrences.
Follow `learner_progress/management/commands/recalculate_progress_percentages.py`: `import djclick as
click`, `@click.command()` on a module-level `def command(...) -> None:`, a docstring that becomes
`--help`, `click.echo` for output, `raise click.ClickException(...)` for failure, and a final line
counting what changed against what was examined.

| Concept | FLS equivalent |
|---|---|
| `handle()` | `@click.command()` on `def command(...) -> None:` |
| optional argument | `@click.option("--dry-run", is_flag=True, default=False, help="…")` |
| `self.stdout.write` | `click.echo(...)` |
| success styling | `click.secho(..., fg="green")` |
| `raise CommandError` | `raise click.ClickException(...)` |

**`--dry-run` is a genuinely new pattern** — no command in the repo has one. The closest in-repo idiom
for the *semantics* is `sync_user_object_permissions`'s `dry_run: bool = False` parameter
(`role_based_permissions/utils.py:141`, `:176`): compute everything, report the diff, write nothing.

Batching follows `recalculate_progress_percentages.py:17`, `:39`: `from itertools import batched` with
a module-level size constant carrying a comment explaining *why* the batch exists, and `.iterator()`
on the outer scans.

### 8.2 The derivation rule

**Extract it as an importable callable**, so the command stays thin and "who should be a Learner" has
one home:

> `UserCourseRegistration(user, organisation)` ∪ `CohortMembership.user × Cohort.organisation`

**Include registrations regardless of `is_active`.** `CohortMembership` has no `is_active` concept at
all, so excluding inactive registrations would treat the two source relations inconsistently for what
is meant to be one fact. `Learner.is_active` is *roster* state; registration status stays on the
registration. Someone who registered and cancelled lands on the roster as a live learner an educator
can then legitimately remove — which they are permitted to do, since no active registration remains.
This is the rule most likely to be implemented wrong; it gets its own test.

### 8.3 Site handling — one decision, three consequences

**No thread-local request exists during a management command**, exactly as none exists during
`migrate`. Everything below follows from that single fact:

1. Use `_base_manager` or an explicit `.filter(site=…)` everywhere. **The trap runs in the opposite
   direction from the obvious one:** `SiteAwareManager` falls through to *unfiltered* rather than
   raising, so `Learner.objects.filter(organisation=…)` will appear to work while silently ignoring
   site, and the bug surfaces only on a multi-site install.
2. Construct every `Learner` with `site=organisation.site` explicitly. This matters especially if
   `bulk_create` is used: it does not call `save()`, so `SiteAwareModelBase.save()` never populates
   `site`. `bulk_create(ignore_conflicts=True)` has **zero call sites** in the repo (the single
   mention is a docstring at `learner_progress/signals.py:109`) — flag it in the plan as a genuinely
   new pattern.
3. No webhooks fire. `fire_webhook_event` returns early with no request (`webhooks/events.py:22-24`).

**Do not copy the QA commands' `_site_context` helper.** `qa_create_organisation_scenarios.py:118-140`
deliberately *installs* a thread-local request so that indirectly-created models get a `site` — which
also means the site-aware managers filter and webhooks fire inside those commands. (The idea's blanket
"no thread-local request exists during a management command" is true by default but false for the QA
commands.) `rebuild_learners` must resolve Site explicitly from the organisation instead.

### 8.4 Cross-site rows: assert, do not propagate

Nothing in the schema stops a `Cohort` or a registration from pointing at an organisation on another
Site. No current code path produces it, but if the data holds one, `rebuild_learners` **fails loudly
naming the offending IDs** rather than quietly minting a cross-site `Learner`.

Follow `validate_role_permissions.py:57-59`: accumulate an `errors: list[str]`, then raise a single
`click.ClickException` with all of them joined. (The precedent the idea cited,
`student_management/migrations/0006_validate_no_duplicate_students.py`, was dropped when the rename
regenerated the app's migrations — there is no in-repo migration example left to copy.)

## 9. Migration and rollout

**No backfill. There is no production data to protect.** FLS has no live installs, so the dev database
is dropped and rebuilt rather than migrated forward — and the Organisation cut already told any
operator with existing data not to upgrade, so nothing downstream is carrying rows a backfill would
have to find. The earlier plan for a `RunPython` derivation step is dropped.

That leaves **one migration**: `freedom_ls/learner_management/migrations/0002_learner.py`, a single
`CreateModel` with every field `NOT NULL`, the unique constraint and the index included. It depends on
`("freedom_ls_learner_management", "0001_initial")` and on
`("freedom_ls_organisations", "0002_organisation_is_default_and_more")`. Nothing existing is narrowed,
so reverse is a plain table drop with no data loss to warn about.

`learner_management` is at `0001_initial` and nothing else — the rename deleted and regenerated the
three renamed apps' migration histories, so any pre-rename migration filename quoted in this
directory's research no longer exists. (`accounts` was **not** regenerated; it is at `0005`.)

**The four `*_learner` permissions do not exist during the migration that creates the model.** Django
creates default permissions on `post_migrate`. Nothing in this cut's migration may reference them, and
any future data migration granting them must be a separate, later migration.

**Upgrade notes** must say:

- Run `migrate`.
- Any installation that somehow *does* carry pre-existing registrations or cohort memberships runs
  `rebuild_learners` once after migrating. That is the substitute for a backfill, and it is the same
  command that serves as the ongoing recovery path.
- The educator interface path `organisations/<slug>/users/…` is now
  `organisations/<slug>/learners/…`.
- `Learner` rows are best-effort and eventually consistent; `rebuild_learners` is the repair path.
- `course.registered` webhooks now fire after commit rather than inside the transaction.

Regenerate `docs/app_structure.md` with `/ds:app_map` (no new edges expected — this verifies it).

## 12. Decisions and rationale

1. **`Learner` is a roster record, not an access gate.** Nothing checks "is this person a Learner?"
   before granting access to anything. Registration and cohort membership keep working exactly as they
   do today; they simply also ensure a row exists. This follows the Organisation cut's Decision 5 —
   loosening later is easy, tightening later is not. It is also Canvas's framing for
   `UserAccountAssociation`, verbatim in effect. (§1, §3)
2. **Authorisation is a Python check on `view_organisation`, not a `*_learner` role grant.** The naive
   route is silently broken by guardian's content-type filter. Minimal wiring now; the educator
   interface build-out takes it over the line. (§4)
3. **`_base_manager`, not `objects`, in `ensure_learner` and `rebuild_learners`.** The single
   highest-risk detail, with a regression test. (§5.1, §8.3)
4. **The receiver is not gated on `created`.** Gating would miss reactivation. `ensure_learner` is
   idempotent, so the gate buys nothing. (§5.2)
5. **A signal, not an explicit call.** FLS ships as a submodule into projects designed to extend it,
   so downstream code creating a registration is outside FLS's project and an explicit call can never
   reach it. FLS has made this call twice already. (§5.2)
6. **The webhook fires on commit.** Ordering was already correct; commit-ordering was not. A consumer
   may reasonably expect the association to exist when the event arrives. `ensure_learner` stays on
   `post_save` inside the transaction — deferring *it* would be actively harmful. (§5.3)
7. **`get_or_create` with no `IntegrityError` retry, and `update_or_create` rejected.** The savepoint
   costs a hot-path round-trip and buys almost nothing at FLS's scale; `update_or_create` would clobber
   `source`. Both are decisions, not oversights. (§5.1)
8. **`is_active` is filtered explicitly, never in a manager.** A filtering default manager would break
   `ensure_learner`'s `get` half and collide with `SiteAwareManager`. (§3.1)
9. **The Users section becomes the Learners section** rather than a fourth section appearing beside it.
   Educators browse learners, not users. (§6.2)
10. **Remove is instance-level, not per-row.** Row-level actions do not exist in `panel_framework`;
    building them is out of scope and there is a standing TODO for them that stays. (§6.4)
11. **Removal is refused, not warned about, and returns 422 with the fix named.** The refusal is what
    makes "enrolled but invisible" unreachable by construction. This introduces a new pattern — no
    action in the repo refuses with an explanation today. (§7.1)
12. **Removal never cascades.** The invariant every product that got this right shares, and cheap here
    because the two lifecycles are already decoupled by construction. Pinned by a test. (§7.2)
13. **Add-a-learner is an exact-email lookup on this Site that never creates accounts**, and says
    nothing about other Sites. Cross-tenant existence disclosure is ruled out. The helper lives in
    `accounts/utils.py`, where a future self-registration path will also need it. (§6.3)
14. **No backfill; `rebuild_learners` ships instead.** No live installs, database rebuilt from
    scratch. The derivation is an importable callable so the rule has one home. (§8, §9)
15. **`rebuild_learners` only inserts.** Never deletes, never touches `manual`, never reactivates —
    otherwise it would undo the deliberate removals the roster exists to record. (§8)
16. **`Learner` lives in `learner_management`** — zero new app-graph edges, and it keeps
    `organisations` from having to import `learner_management`. (§3.2)

## 13. Non-goals for this cut

Stated explicitly so they are deferrals, not gaps.

- **No learner-facing changes.** A learner studying through two organisations still sees one merged
  course list, with the existing per-course organisation logo as the only cue. *Caveat:* the
  existing-account lookup (§6.3) is a shared surface that will not stay confined to the educator
  interface — hence naming where it lives, even though the learner UI stays out.
- **No gating.** Being a Learner is never a precondition for registering or joining a cohort.
- **No hard delete, no merge.** Same reasoning as `Organisation` itself.
- **No bulk add/remove and no CSV import.** Every product that has these has them because branches
  hold hundreds of users; FLS expects 2–5 organisations per Site.
- **No typeahead / autocomplete in the add flow.** v1 is an exact-email lookup. None exists in the
  educator interface today.
- **No "show removed learners" filter.** Re-adding goes through the add flow, which reactivates.
- **No row-level actions in `panel_framework`.** The standing TODO at `educator_interface/views.py:104-112`
  stays in place.
- **No self-registration via an organisation-specific signup URL, no SSO attribute mapping, no invite
  links.** All blocked on learner-facing work, or on infrastructure FLS doesn't have.
- **No `pending`/`invited` states.**
- **No periodic reconciliation task.** FLS has a background-task system but no scheduled-task
  infrastructure; that would be net-new scope. `rebuild_learners` run by hand, or by a downstream
  project's own cron, is the v1 substitute.
- **No cross-organisation admin view.** "Show me this person across every organisation" is a real want,
  but it must be an explicitly authorised site-level capability if it is ever built — never a side
  effect of holding two organisation roles at once. That is exactly how Canvas's long-standing
  cross-account visibility leak happened.
- **No fix to the cross-content-type permission sync**, and no custom
  `manage_organisation_learners` permission on `Organisation`. Both would work; both are bigger than
  this cut. `site_admin`'s existing dead `*_cohort` grants are left as they are.
- **Not wired into `course_interest`, `course_applications` or `RecommendedCourse`.** There is no
  organisation to attach at those points in the flow, and none of them writes a registration today.
  When application acceptance ships it will need `ensure_learner` — note it there, don't pre-build it.
- **The terminology rename is not in this cut.** It shipped separately and is merged. Residual
  `student_*` strings are that spec's business, not this one's (and there are none left in
  `freedom_ls/`).

## 14. Success criteria

**Data and migration**

1. `Learner` exists in `learner_management` with all six fields, the unique constraint on
   `(site_id, user, organisation)` and the `(organisation, is_active)` index.

## 15. Known risks

1. **The permission landmine is easy to re-introduce.** A future contributor granting
   `freedom_ls_learner_management.add_learner` to `organisation_staff` will see CI pass and the feature
   silently deny. Criterion 13 is the guard. Worth a probe during planning: confirm whether
   `site_admin`'s existing `*_cohort` grants reach guardian at all.
2. **`users_visible_to` shifts in both directions.** Any row written by `bulk_create`, `update()` or
   `loaddata` before a `rebuild_learners` run makes a genuinely registered learner invisible to their
   educator. This is the under-counting failure mode §5.4 warns about, and it is silent.
3. **Row-level actions remain absent.** Removal being instance-level means an educator must open a
   learner to remove them. Acceptable for 2–5 organisations; it will not scale, and the standing TODO
   tracks it.
4. **The `users/` → `learners/` path change breaks bookmarks** and any downstream template hardcoding
   the segment. Mitigated only by upgrade notes, since FLS is not live.
5. **`bulk_create(ignore_conflicts=True)` is a new pattern** with no in-repo precedent, and it bypasses
   `SiteAwareModelBase.save()` so `site` must be set by hand on every instance. If the plan uses it,
   that is the thing to review hardest.
6. **Deferring the webhook to `on_commit` changes shipped semantics.** Low risk — the webhook system
   has no production implementation, FLS is not live, and the existing tests already run with
   `transaction=True` — but any test not doing so needs `django_capture_on_commit_callbacks`, and
   payload values must be captured before the callback is registered.
7. **QA data is the only source of interesting rows.** With no backfill and a rebuilt database, if the
   seeding command is not extended, the three new states cannot be exercised at all — and pytest never
   collects those commands, so nothing fails to warn you.
