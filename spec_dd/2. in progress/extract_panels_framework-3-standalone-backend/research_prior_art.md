# Research: prior art for extract_panels_framework-3-standalone-backend

Question: what has already been tried for this, here or elsewhere, and what happened? Local findings are grepped from the worktree. Web findings carry URLs. Nothing in `spec_dd/` has tried a standalone backend, a framework-owned site manager, or a second pytest config before. This is the first attempt, so the prior art is the audit, spec 1, the csv spec, and general lessons.

### CSV formula spec (done 2026-11-09, `csv-formula-extra-triggers`)

Its `1. spec.md` is the source for the widened helper:

- `FORMULA_TRIGGERS = ("=", "+", "-", "@", "\t", "\r", "\n", "＝", "＋", "－", "＠")`, a tuple of single-character `str`, name kept because tests import, parametrise over and `sorted()` it.
- `escape_csv_formula(value: str) -> str` prefixes `'` when the first character is a trigger, or the first non-whitespace character (by `str.isspace()`) is. Empty string unchanged. Leading whitespace is kept. Later lines of a multi-line cell are not marked.
- Its expected-results table (14 rows incl. `" @SUM(A1)"`, `"　=1+1"`, `"one\ntwo"` unchanged, `"Notes:\n- one\n- two"` unchanged) is the test list the copy must carry. A separate test pins the tuple's exact contents so a trigger cannot drop out. Integration cases exist in `test_admin_exports.py` and `panel_framework/tests/test_tables.py` (a cell starting with `＝`).
- It explicitly said: "`spec_dd/1. next/extract_panels_framework-3-standalone-backend` copies `escape_csv_formula` into the standalone package (`idea.md:14`). That copy has to take this version, so that idea gets a line saying so." The idea now carries that line.
- Out of scope there, so the copy must not add them: NFKC normalisation, small-form lookalikes, zero-width and bidi characters, numeric-looking exemptions.
- Risk specific to a copy: two copies of a security helper can drift. This is the accepted cost in "What is settled", but it means any later trigger change needs to touch both. An FLS-side test that asserts the two `FORMULA_TRIGGERS` tuples are equal is possible but would itself import across the boundary, which the import guard forbids for framework files. If wanted it belongs in an FLS test outside the framework tree. Mention it in the spec as an option, not a requirement.

### Related FLS code history and conventions

- `freedom_ls/site_aware_models/models.py`: `SiteAwareManager.get_queryset` filters by `get_cached_site(_thread_locals.request)` and falls through unfiltered when there is no request or the host is rejected (`UnknownSite`). `SiteAwareModelBase.save/full_clean` fill `site` from the thread-local only if `site_id` is unset. Important behavioural point for the copy: today a request with no ambient site is **unfiltered**, and a save with no site fails on "field cannot be null". The framework replacement should be stricter, not equal: `for_request` with an unresolvable site should return nothing or raise, never everything. "Behaves exactly as today" in the idea holds for resolved requests only.
- `get_cached_site` caches `_cached_site` on the request and handles `DisallowedHost`. The answers' "cached on the request" is the same pattern. Use a private attribute name of the framework's own, not `_cached_site`, so the two caches cannot disagree if FLS's resolver returns a different object.
- FLS already shows the worker-side pattern: `_base_manager.filter(site_id=..., pk=...)` in `bulk_runs.py:_run_on_site` ("no ambient site") and in `deployment/housekeeping.py` for `GeneratedReport`, `LearnerImport`. The `fls-dev:multi-tenant` skill covers it ("Sweeps over site-aware rows"). `ApiKey._base_manager` in `api/authentication.py` is another example of explicit site filtering with a resolved site. The framework's own manager should keep `_base_manager` semantics for the worker: a plain manager (Django's `_base_manager` is a plain `Manager` unless `Meta.base_manager_name` is set), so setting a custom `objects` does not change worker behaviour.
- Streaming export: `views.py:_export_response` documents that "a `StreamingHttpResponse`'s body is read after the middleware that clears the site thread local has already run", so the host's queryset is built before the response is returned. That is the thread-local hazard already hit once. An explicit request-taking method removes that class of bug for `BulkActionRun`, but the export queryset is the host's (`panel.get_export_queryset`) and stays the host's concern.
- `freedom_ls/tests/site_context.py` (`site_context`, `drop_ambient_request`) patches four things together (thread-local request, `SITE_CACHE`, `get_current_site` in two modules, `SiteManager.get_current`) because "all four have to agree or a factory-built row lands on a different site". `drop_ambient_request` exists because a response is read after the view returned. With an explicit resolver none of this is needed, but the framework's equivalent tests must prove site isolation by building two `Site` rows and a second request, not by patching.

## 2. Here: hazards found in the current tree (no earlier spec covers them)

1. **Ancestor `conftest.py` is still collected.** `freedom_ls/conftest.py` sits above `freedom_ls/panel_framework/tests/`, and pytest loads every `conftest.py` from `rootdir`/`confcutdir` down. A "separate pytest config" does not stop it. The FLS root conftest has seven `autouse` fixtures (`_disable_force_site_name` sets `settings.FORCE_SITE_NAME`, `_clear_course_access_backend_cache`, `_clear_messaging_policy_cache`, and others) that import FLS code and would fail or silently no-op under minimal settings. Use `--confcutdir` pointing at the framework's `tests/`, or a framework-level rootdir, and test that it works by running the standalone command and asserting no FLS fixture is requested. `--noconftest` is wrong: it also drops the framework's own conftest.
2. **The FLS `[tool.pytest.ini_options]` carries options that need FLS plugins.** `DJANGO_SETTINGS_MODULE = "config.settings_dev"`, `env = [...]` (pytest-env), and `addopts` with `--tracing`, `--screenshot`, `--disable-socket`, `--allow-hosts`, `--dist loadfile`, `-m 'not ci_only and not weasyprint and not dev_tooling'`, `--strict-markers` with FLS marker names. A second ini file (`-c path`) replaces the whole ini section, so these are not inherited, which is good, but its `addopts` must declare what it needs, and its marker list must include any marker the framework's tests use under `--strict-markers`. A shell `DJANGO_SETTINGS_MODULE` env var takes precedence over ini in pytest-django, so the standalone command should pass `--ds` explicitly.
3. **Namespace-package import workaround.** `tests/conftest.py:18-24` and `stub_panels.py:11-17` use relative imports because there is no `freedom_ls/__init__.py`, which makes pytest import the tests as `panel_framework.tests.*`. Under a second rootdir/confcutdir the module-name resolution can change (rootdir-relative, `rootdir/conftest.py` insertion into `sys.path`). The audit (X9) says this goes away only when the package gets a normal root, which is spec 5. Test the standalone command with `-p no:cacheprovider` off and `--import-mode` explicitly (`importlib` avoids the namespace problem but changes how test modules import siblings).
4. **Stub models register against the live app label** (`tests/conftest.py:42,65`, `app_models = apps.all_models.get("freedom_ls_panel_framework", {})`). Under minimal settings with the label kept, this works unchanged (audit X10). Check test teardown: leftover registry entries across the two test sessions do not matter because they are separate processes.
5. **Migration state when `BulkActionRun` stops subclassing `SiteAwareModel`.** `SiteAwareModel` is abstract, so `0001_initial` already lists the concrete fields (UUID `id`, `site` FK `on_delete=PROTECT`, etc.), not a base. Dropping an abstract parent while redeclaring the same fields generates no schema change, but the field definitions must match **exactly** (`id = UUIDField(primary_key=True, default=uuid.uuid4, editable=False)`, `site = ForeignKey(Site, on_delete=PROTECT)`). Verify with `uv run manage.py makemigrations --check --dry-run`. A new custom manager only appears in migration state if `use_in_migrations = True`; do not set it. Also `SiteAwareModelBase` overrides `save` and `full_clean`, so the framework model needs its own `save`/`full_clean` (or a pre-save that fails loudly) and `BulkActionRun.save` already exists and must keep its scope behaviour.
6. **Admin and other code that relied on the auto-filter.** Anything that reads `BulkActionRun.objects` outside the three known files (admin registration, `qa_helpers/management/commands/qa_create_bulk_operations_scenario.py`, `learner_management`, `deployment/housekeeping.py`, FLS tests) silently changes meaning when `objects` no longer filters by the thread-local. Grep before the change and decide for each whether it needs `for_request`, an explicit `site`, or `_base_manager`. A search for `BulkActionRun` call sites outside the framework is a task for the plan.
7. **`site_aware_models` is imported by FLS-only checks.** FLS contract tests (`import_contracts.toml`, `import_baseline.txt`, `mirroring_baseline.txt`) track `freedom_ls.panel_framework` imports (36 hits in `import_contracts.toml` per the audit). Removing imports of `site_aware_models` and `base` from the framework should shrink the baseline. These files regenerate with `/ds:app_map` and a stale baseline may fail the FLS suite, so run the contract tests, not only the framework's.

## 3. Elsewhere (web)

### Thread-local tenancy and background workers

- django-multitenant documents that the current tenant lives in thread-local storage and must be cleared at the end of every request, because a web server thread outlives the request and the next request on that thread would otherwise inherit the tenant. https://django-multitenant.readthedocs.io/en/latest/usage.html
- A Viget write-up describes the same leak in Celery workers: a value set by one task stayed in thread-local storage and was visible to the next task. Their fix was a context manager that sets and clears the tenant explicitly. A second, lower-authority source says workers must take the tenant id from task arguments and re-populate state. This matches the framework's existing `_run_bulk_action_task(run_id, site_id)`. https://www.viget.com/articles/multi-tenancy-in-django , https://www.technetexperts.com/django-multi-tenant-architecture/
- A Django forum thread says `asgiref.local.Local` is the safer drop-in for thread-locals under async, and that plain thread-locals do not work in async views. FLS's `_thread_locals = local()` is plain `threading.local`. This supports removing the ambient request from the framework rather than copying it. https://forum.djangoproject.com/t/django-and-multi-tenancy-issue/18730
- "A Convention Is Not a Constraint" argues that tenant filtering by convention (a manager someone must remember) fails silently, and that enforcement belongs in a constraint. Relevant to `for_request`: a request-taking method is a convention, so the spec should add a test that enumerates every read path (list, lookup, worker, sweep) against two sites, as the stated "isolated by site" constraint. https://simplethread.com/a-convention-is-not-a-constraint/
- Unresolved: no source found specific to the explicit-queryset-method pattern in Django (`for_request`). It is a plain custom QuerySet method. I found no write-up of pitfalls beyond the above.

### Changing a model's base class and migrations

- Django's autodetector does not record base-class changes well. #36959 "Model bases isn't updated when changing parent classes" (no operation to update `bases` in migration state), #25247 "makemigrations unable to generate necessary migration for making a superclass abstract", #31329 (concrete to abstract can create invalid migrations, closed as a duplicate), #29574 (abstract to concrete: foreign key mismatch, open). These concern **concrete** parents or multi-table inheritance. `SiteAwareModel` is abstract, so removing an abstract parent that contributes fields is the safe path, provided the fields are redeclared identically. https://code.djangoproject.com/ticket/36959 (via https://go.mail-archive.com/django-updates@googlegroups.com/msg245192.html), https://code.djangoproject.com/ticket/25247 , https://code.djangoproject.com/ticket/31329 , https://code.djangoproject.com/ticket/29574
- Practical result: prove "no migration" with `makemigrations --check` and a test that compares the model's field deconstruction to the migration, rather than trusting the autodetector.

### Test-config collisions

- No web source needed for the core point; it is documented pytest behaviour (conftest collection walks up from the test path to `rootdir`/`confcutdir`; `-c` replaces the ini file; `--ds` beats the ini for pytest-django). Treat this as unverified here: the hazard in 2.1 and 2.2 should be reproduced with one dry run before the spec relies on it. Pytest's own docs: https://docs.pytest.org/en/stable/reference/reference.html#confval-confcutdir and pytest-django's: https://pytest-django.readthedocs.io/en/latest/configuring_django.html

## 4. What this means for the spec

- Nothing was tried before, so the design is not contradicted by history. The audit and the answers agree.
- Add to the plan: the sweep (`housekeeping.py`) and the admin and QA command as paths to cover; a tenant-isolation test per path with two `Site` rows; `makemigrations --check` as an explicit gate; a `--confcutdir`-based standalone command and a test that proves FLS fixtures are not pulled in; the widened CSV helper copy with all 14 table rows plus the pinning test; and an import guard that covers `tests/` and treats `freedom_ls.panel_framework...` self-imports as allowed (the idea says "from outside the framework", and today the framework imports itself as `freedom_ls.panel_framework`, so the guard must allow that prefix).
- Stricter-than-today behaviour on an unresolved site is a deliberate difference from `SiteAwareManager`, and the spec should say so.
- Unverified: whether any FLS code relies on `BulkActionRun.objects` being auto-filtered outside the three files listed; the plan must grep for it.
