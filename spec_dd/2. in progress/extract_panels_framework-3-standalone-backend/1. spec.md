# Spec: the panel framework's backend stands alone

Spec 3 of 6 in the Panel framework extraction effort (`spec_dd/1. next/roadmap.md`, "Panel framework
extraction"). Idea: `idea.md`. Answers: `answers.md`.

## Purpose

Another Django project needs the panel framework, and it cannot install a package whose model,
settings helper and formatting import FLS. This spec removes every Python import of `freedom_ls`
from outside `freedom_ls/panel_framework/`, without moving the code yet. The framework's unit tests
then run under a minimal settings module with no FLS conftest. Educators see no change, and tenant
isolation of bulk-action runs behaves as it does today.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| standalone run | coined | The framework's unit tests run by the separate pytest command below, under `freedom_ls/panel_framework/tests/standalone_settings.py`, with no FLS conftest |
| `needs_fls_templates` | coined | pytest marker on a framework unit test that asserts markup only FLS's real templates or icon set produce; deselected in the standalone run until spec 4 |

## Scope

In:

- The six non-test imports from outside the framework: `models.py:13`, `config.py:17`,
  `tables.py:12`, `views.py:33-34`, `field_display.py:74`.
- `BulkActionRun`'s site handling: a framework-owned manager, explicit `site` on create, and the
  `PANEL_FRAMEWORK_SITE_RESOLVER` setting.
- A `TASKS` system check.
- The standalone run: settings, pytest config, conftest fixtures and stand-in templates, covering
  the 19 unit test files (18 top-level `tests/test_*.py` plus `tests/templatetags/test_panel_tags.py`).
- `lxml` declared as a test dependency.
- An import guard test.
- FLS wiring: the resolver setting, and the seven FLS test call sites that create a run without a
  site.

Out (owner in brackets):

- Migration `0001_initial` rewrite, app label rename, check-id prefix change, ContentType handling
  [spec 5].
- Templates, JS, CSS, icons, the page shell, primitives, and the component, invariant (beyond
  `lxml`) and Playwright tiers [spec 4].
- The package repo, its `pyproject.toml`, installing it into FLS [spec 5].
- Any change to `SiteAwareModel` or `site_aware_models` for the rest of FLS.
- The stale-run sweep's placement (already in the framework from spec 1) and `RunStatus` reuse by
  `learner_management`.

## Decisions

- **Copies, not a shared core package.** `AppSettings`, the CSV helpers and the two date formats are
  copied in; FLS keeps its own. If the site handling turns out to need `site_aware_models`
  internals, stop and say so. FLS's resolver is passed by dotted path, so the framework never
  imports it.
- **Explicit scoping, no ambient request.** Reads go through `BulkActionRun.objects.for_request(request)`
  or `for_site(site_id)`; creation passes `site`. Nothing reads a thread-local.
- **Stricter than today on an unresolved site.** `SiteAwareManager` returns every site's rows when
  the request's site is not a `Site` row. `for_request` returns no rows instead, and creation refuses.
- **No save-time site fallback.** A run saved without a site fails on the NOT NULL constraint. FLS
  callers that relied on the thread-local hook pass `site=`; that is the only FLS edit beyond
  settings.
- **No abstract base class** replaces `SiteAwareModel`; `BulkActionRun` declares `id` and `site`
  itself.
- **`site` stays a required FK to `django.contrib.sites`.** A single-site host relies on the
  default resolver.
- **SQLite in memory for the standalone run.** Static search found no PostgreSQL-only construct in
  the framework (only `icontains` at `tables.py:405`, ASCII-only case folding on SQLite). FLS's own
  run keeps PostgreSQL, so both databases are exercised.

## Requirements

### 1. Settings helper (`config.py`)

- A new framework module (`freedom_ls/panel_framework/app_settings.py`) holds a copy of `Setting`
  and `AppSettings` from `freedom_ls/base/app_settings.py`. `required_settings_errors` is not copied:
  the framework declares no required setting.
- `config.py` imports from it and declares a second setting:

  ```python
  "SITE_RESOLVER": Setting(default="django.contrib.sites.shortcuts.get_current_site"),
  ```

  read as `settings.PANEL_FRAMEWORK_SITE_RESOLVER`. The `AppSettings` copy may gain a prefix, or the
  setting may be declared under its full name; either way the Django setting name is
  `PANEL_FRAMEWORK_SITE_RESOLVER` and `BULK_BACKGROUND_THRESHOLD` keeps its current name.
- Settings are read on access, never cached at import, so `override_settings` works.

### 2. Site resolution (`freedom_ls/panel_framework/sites.py`, new)

- `resolve_site(request: HttpRequest) -> Site | None`:
  - returns `request._panel_framework_site` when that attribute is set;
  - otherwise imports `config.SITE_RESOLVER` with `django.utils.module_loading.import_string` at
    call time (not module import, so FLS's test patches of `get_current_site` stay effective), calls
    it with the request, and stores the result on `request._panel_framework_site`;
  - returns `None` when the resolver returns anything that is not a `Site` instance (a
    `RequestSite`, or FLS's `UnknownSite`);
  - raises `ImproperlyConfigured` naming the setting and the bad value when the path cannot be
    imported or is not callable.
- The attribute name is the framework's own, so it never aliases FLS's `request._cached_site`.

### 3. `BulkActionRun` (`models.py`)

- Subclasses `models.Model`. Declares, before its own fields and with definitions identical to
  `SiteAwareModel`'s:

  ```python
  id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
  site = models.ForeignKey(Site, on_delete=models.PROTECT)
  ```

- `objects` is a framework manager built from a `BulkActionRunQuerySet` with:
  - `for_site(site_id: int)`: `filter(site_id=site_id)`;
  - `for_request(request)`: `for_site(site.pk)` when `resolve_site(request)` is a `Site`, else
    `none()`.
- The manager does not set `use_in_migrations`, and `Meta.base_manager_name` stays unset, so
  `_base_manager` stays Django's plain manager (relied on by `bulk_runs.py:72-80`,
  `housekeeping.py` and FLS's `qa_create_bulk_operations_scenario`).
- `uv run manage.py makemigrations --check --dry-run` reports no change.

### 4. Read and write paths

| Path | After this spec |
| --- | --- |
| `views.py:1147` `_handle_run_status` | `BulkActionRun.objects.for_request(request).filter(...)`; another site's run is a 404 |
| `bulk_actions.py:383` `RecordedBulkAction.execute` | resolves the site with `resolve_site(ctx.request)` and passes `site=` to `create`. A `None` site raises `PermissionDenied`, and no row is written |
| `bulk_actions.py:396,398`, `tasks.py` `_run_bulk_action_task(run_id, site_id)` | unchanged signature; still pass `run.site_id` |
| `bulk_runs.py:72-80` `_run_on_site` | unchanged (`_base_manager.filter(site_id=..., pk=...)`) |
| `housekeeping.py` | unchanged; still cross-site via `_base_manager`, closing runs on every site |

The planner greps for every other `BulkActionRun.objects` use in FLS. Each one either relies on no
filtering (and is single-site in tests) or is given `for_site`/`for_request`.

### 5. CSV helpers (`tables.py`, `views.py`)

- A new framework module (`freedom_ls/panel_framework/csv_safety.py`) holds copies of
  `FORMULA_TRIGGERS`, the E.164 phone-number exemption, `escape_csv_formula`, `UTF8_BOM` and
  `EchoWriter`, taken from `freedom_ls/base/csv_safety.py` and `csv_import.py:135-141` as they are
  on main (the widened csv-formula-extra-triggers version). Nothing else from `csv_import.py` is
  copied.
- `tables.py` and `views.py` import from it. FLS's own modules are untouched.
- Its tests are a copy of `freedom_ls/base/tests/test_csv_safety.py`, including the test that pins
  the exact `FORMULA_TRIGGERS` tuple.

### 6. Date formats (`field_display.py`)

`field_display.py` stops importing `freedom_ls.base.date_display`. The framework defines its own
`DATE_DISPLAY_FORMAT = "j M Y"` and `DATETIME_DISPLAY_FORMAT = "j M Y, H:i"`, in `field_display.py`
or a small framework module. Rendered dates do not change.

### 7. `TASKS` check (`checks.py`, `apps.py`)

- A second check function, registered in `PanelFrameworkConfig.ready()` with plain `register` (not
  `deploy=True`).
- When `settings.DEBUG` is False and `settings.TASKS["default"]["BACKEND"]` is
  `"django.tasks.backends.immediate.ImmediateBackend"` or `"django.tasks.backends.dummy.DummyBackend"`,
  it returns one `Warning` with id `freedom_ls_panel_framework.W001`. The message names the backend.
  The hint says bulk actions over `BULK_BACKGROUND_THRESHOLD` rows run as background tasks and need
  a durable backend with a worker, and that the warning can be silenced by id.
- It compares dotted strings and imports no backend class.
- FLS's existing `test_checks.py::test_call_command_check_passes_on_the_real_config` still passes;
  a warning does not fail `check`.

### 8. FLS wiring

- `config/settings_base.py` sets
  `PANEL_FRAMEWORK_SITE_RESOLVER = "freedom_ls.site_aware_models.models.get_cached_site"`, so FLS
  keeps `FORCE_SITE_NAME` and its own request cache.
- The seven FLS test call sites that create a run with no site pass `site=` explicitly:
  `educator_interface/tests/test_views.py:5485`, `test_actions.py:7367,8338`,
  `test_notification_urls.py:18,35`, `invariants/test_config_authorisation.py:203`,
  `invariants/test_organisation_isolation.py:171`.
- `pyproject.toml` declares `lxml` in both dev lists (`[project.optional-dependencies].dev` and
  `[dependency-groups].dev`), with `uv.lock` updated.
- The `needs_fls_templates` marker is added to the FLS `markers` list (needed under
  `--strict-markers`). The FLS run does not deselect it.
- Import contracts and baselines (`test_organisation/`) are regenerated where the removed edges
  change them.

### 9. The standalone run

All files live in `freedom_ls/panel_framework/tests/`, so spec 5 moves them with the package.

- **pytest config.** `standalone_pytest.ini`. It is not named `pytest.ini`,
  `.pytest.ini`, `tox.ini`, `setup.cfg` or `pyproject.toml`, because pytest would otherwise discover
  it for any FLS run targeted at framework files and switch FLS to the standalone settings. It
  declares the settings module, `python_files`, the 19 unit files' locations (ignoring
  `components/`, `invariants/` and `playwright/`), its own `addopts` with no Playwright or FLS
  options, `-m "not needs_fls_templates"`, and its own marker list.
- **Command.** `uv run pytest -c freedom_ls/panel_framework/tests/standalone_pytest.ini`. Because
  `-c` makes `tests/` the rootdir and confcutdir, neither the repo-root `conftest.py` nor
  `freedom_ls/conftest.py` loads. A shell `DJANGO_SETTINGS_MODULE` must not override it; the ini or
  the command pins the settings module explicitly.
- **Settings.** `standalone_settings.py`. SQLite in memory; `INSTALLED_APPS` of `django.contrib`
  `auth`, `contenttypes`, `sessions`, `sites`, `messages`, `admin` (for `admin:login` in
  `root_urls.py`), `django_cotton`, the framework, and a test app; `AUTH_USER_MODEL` pointing at the
  test app's user; `TEMPLATES` with the cotton loader, the request context processor, a stand-in
  `site_name` context processor, and the stand-in template directory first; `TASKS` with
  `ImmediateBackend`; `SITE_ID` unset, so the default resolver matches by host.
- **Test app.** A minimal email-login user model (`USERNAME_FIELD = "email"`, a manager whose
  `create_user(email=..., password=..., **extra)` serves `helpers.make_staff_user`), with its
  migration or `MIGRATION_MODULES` handling chosen by the plan.
- **Stand-in templates.** A directory only the standalone settings include. It holds minimal cotton
  components for every primitive the unit tests render (`c-icon`, `c-button`, `c-button-group`,
  `c-chip`, `c-pagination`, `c-dropdown-menu`, `c-callout`, `c-back-link`, `c-page`) and a
  stand-in `_base_interface.html` for `panel_framework/test_interface.html`. Each keeps the props
  and slots the framework passes. They are test fixtures, not spec 4's components.
- **Fixtures.** The framework's own test tree provides `site` and a site-context fixture that work
  in both runs. In the standalone run they make `resolve_site` return the test site. In the FLS run
  they must not break FLS's context processors. The FLS helpers `drop_ambient_request`, `SiteFactory`,
  `site_context` and `mock_site_context` are no longer imported by framework tests;
  `Site.objects.create` replaces `SiteFactory`. `logged_in_client` and `database_task_backend` are
  not needed (no framework test uses them). The plan settles how the fixtures coexist with the FLS
  root conftest's same-named fixtures. Changes to `tests/conftest.py` are kept small, because spec 2
  edits it too.
- **`needs_fls_templates`** marks the tests whose assertions depend on FLS's real templates or icon
  set, at least `test_tables.py:2208,2225` (heroicons SVG via `FREEDOM_LS_ICON_SET`). Any other test
  that fails only because a stand-in renders different markup is marked rather than having its
  assertion weakened.
- Module import naming: `freedom_ls/` has no `__init__.py`, so tests import as
  `panel_framework.tests.*` (`tests/conftest.py:18-24`). The standalone run must import the
  framework and its tests under one name each. A `--collect-only` run proves this.

### 10. Import guard (`tests/test_import_guard.py`, new)

- Parses every `.py` file under `freedom_ls/panel_framework/` with `ast` and fails on any `import`
  or `from` naming a `freedom_ls` module outside `freedom_ls.panel_framework`. The failure message
  names the file, line and import.
- Covers non-test code, `tests/` and `migrations/`. Exempt by name, in a pinned tuple in the test:
  `tests/components/`, `tests/invariants/`, `tests/playwright/`. Spec 4 removes them.
- Runs in both the FLS run and the standalone run.

## Testing

What has to be proved:

- **Tenant isolation, per path, with two `Site` rows.** `for_request` returns only the request
  site's runs; the run-status view 404s on another site's run; a bulk action creates its run under
  the request's site; `_run_on_site` will not load a run under the wrong `site_id`; the sweep still
  closes stale runs on every site.
- **Unresolved site.** A resolver returning a non-`Site` gives `for_request` no rows and makes
  creation raise `PermissionDenied`.
- **Resolver.** The default resolves by host; the setting overrides it; the result is cached on the
  request (the resolver is called once per request); an unimportable or non-callable path raises
  `ImproperlyConfigured` naming the setting.
- **`TASKS` check.** Warns for immediate and dummy backends with `DEBUG=False`; silent with
  `DEBUG=True`; silent for a durable backend.
- **CSV copy.** The copied `test_csv_safety.py` cases, including the pinned trigger tuple.
- **Migration.** `makemigrations --check --dry-run` is clean in FLS.
- **Standalone run.** The command passes with every non-`needs_fls_templates` unit test selected,
  and a collect-only run shows that no FLS conftest or `freedom_ls/tests` module is imported.
- **Import guard.** Passes, and fails when a fixture file with a `freedom_ls.base` import is added
  (proven by the test's own parametrised case over a temporary file).
- **FLS full suite.** Green, with the only test edits being the seven `site=` additions and the
  framework's own tests.

`test_models.py::test_a_run_takes_its_site_from_the_ambient_site` and
`test_the_default_manager_hides_another_sites_runs` assert the behaviour being replaced; they are
rewritten for explicit scoping.

## Documentation and downstream

- `claude_plugins/fls-dev/skills/panel-framework/SKILL.md`: the resolver setting, `for_request` and
  `for_site`, `site=` on create, the `TASKS` warning, and the import guard. `fls-dev:multi-tenant`
  notes that `BulkActionRun` is not a `SiteAwareModel`.
- `claude_plugins/fls-dev/skills/testing/SKILL.md`: the standalone command and the
  `needs_fls_templates` marker. Nothing goes into the generic `django-stack` tier docs.
- Upgrade notes: `requires_settings_change: true`. A downstream project inheriting
  `config/settings_base.py` gets the setting; one with its own settings must set
  `PANEL_FRAMEWORK_SITE_RESOLVER` to its resolver or accept `get_current_site`. Production with a
  durable `TASKS` backend sees no warning.

## Open questions

Assumed defaults; each holds unless the user overrides it.

- The standalone run is a documented command, not a new entry in `[tool.test_tiers]`, which has no
  concept of an extra named tier. Making it a tier needs a generic-plugin change and belongs in its
  own spec.
- `PermissionDenied` is the error when a bulk action is confirmed on a request with no resolvable
  site.
- No FLS-side test asserts the two `FORMULA_TRIGGERS` copies are equal; each copy pins its own tuple.
- No system check validates `PANEL_FRAMEWORK_SITE_RESOLVER` at startup; a bad path raises
  `ImproperlyConfigured` at first use.
- Spec 2's new framework tests, if spec 2 lands first, are audited against the guard and the
  standalone run during this spec's rebase; if this spec lands first, spec 2 rebases onto the guard.

## Success criteria

- `grep -rn "freedom_ls\." freedom_ls/panel_framework --include=*.py` shows only
  `freedom_ls.panel_framework` imports, apart from the three exempt test directories.
- `uv run pytest -c freedom_ls/panel_framework/tests/standalone_pytest.ini` passes.
- `uv run pytest` (FLS full suite) passes.
- `uv run manage.py makemigrations --check --dry-run` exits 0.
- `uv run manage.py check` with `DEBUG=False` and `ImmediateBackend` prints
  `freedom_ls_panel_framework.W001`; with FLS's production `TASKS` it does not.
- `BulkActionRun.__mro__` contains no `freedom_ls.site_aware_models` class.
- The two-site isolation tests listed under Testing exist and pass.
