# Spec: Content save safety

Spec 1 of 5 in the SACAA content versions and access effort (`spec_dd/1. next/roadmap.md`,
section "SACAA content versions and access"). Idea: `idea.md`. Up-front answers: `answers.md`.
Research: `research_*.md` beside this file.

## Purpose

`content_save` loads only committed content from one or more source paths, refuses missing uuids unless
told to generate them, and records the commit each save came from. Why: `idea.md`.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `ContentSave` | coined | One successful run of `content_save` for one site: when, and with which flag. No existing record of a save exists. |
| `ContentSaveSource` | coined | One source path of a `ContentSave`, with the HEAD commit it was loaded from. |
| `SourceCommit` | coined | In memory only: one source path, its subdirectory relative to the content repo root, and its HEAD commit (fields `path`, `repo_path`, `commit`). The command builds it from the git check, and `save_content_to_db` turns each into a `ContentSaveSource` row. |
| `UncommittedPath` | coined | One dirty file found by the git check: a repo-relative POSIX path and a kind. |
| **source path** | narrowed | A path argument to `content_save`. Today the single `path` argument. |
| **content repo root** | coined | The top of the git working tree that holds a source path. `.fls-content.yaml` is read from here. |
| **ignore list** | coined | The `ignore:` entries of the `.fls-content.yaml` at a content repo root. "Ignored" means listed there; "gitignored" means excluded by `.gitignore`; names the content scanner passes over (a leading `_` or `.`, `README.md`, `CLAUDE.md`, a trailing `~`) are "skipped". |

## Scope

In:

- `content_save` takes several source paths, checks that they are clean git trees, refuses
  missing uuids unless `--generate-uuids` is passed, and records a `ContentSave`.
- With `settings.DEBUG` on, an unknown organisation slug in course frontmatter creates the
  `Organisation`.
- `.fls-content.yaml` gains `ignore:`, honoured by `content_save`, `content_validate` and the offline
  `fls-content` validator.
- Docs and the `fls-content` plugin describe the new authoring flow.

Out:

- Retiring removed content, "one call covers the site's whole source", and `file_path` collisions
  between separate calls: `sacaa-compliance-content-versions-and-access-2-retire-removed-content`.
- Question versions, and anything that reads `ContentSave` for them:
  `sacaa-compliance-content-versions-and-access-3-question-versions`.
- Remote, push or upstream checks.
- Any change to what `content_validate` checks, apart from honouring the ignore list (skipping
  ignored paths and rejecting `children:` or `sections:` entries that name one).
- An admin page or any other UI for `ContentSave`.

## Decisions

- **dulwich reads git state.** The clean check needs the index, the HEAD tree (often in a pack
  file) and `.gitignore` rules. dulwich is pure Python and needs no `git` binary. A hand-written
  reader would reimplement git in an audit-critical path. Pin the lowest dulwich release that has
  `porcelain.worktree_add` and `porcelain.status(untracked_files="all")`.
- **The git check and the recorded commit belong to the command.** `save_content_to_db` never
  checks git, because tests and downstream callers load from temporary directories.
- **`save_content_to_db` defaults `generate_uuids=True`** so existing callers and tests that load
  uuid-less temporary files keep working.
- **The uuid check runs only on the save path.** `content_validate` and the offline validator keep
  accepting uuid-less authoring work.
- **Each source path is self-contained.** Every path-based reference (`children:`, `sections:`,
  images, auto-discovered children) resolves inside its own source path, as today. Each path is
  validated on its own.
- **`file_path` stays relative to its own source path, and two source paths in one call that yield
  the same relative path fail the save.** Template tags look files up by `file_path` alone, so a
  collision would be ambiguous, and no database constraint catches it (`File` is keyed
  `(site, file_path)` and is silently overwritten).
- **The git check covers the whole source path, filtered from a whole-repo status.** A small
  subdirectory of a large repo pays for the full status. Content repos are small, so the cost is
  accepted.

## Requirements

### Command line: `freedom_ls/content_engine/management/commands/content_save.py` `command`

- Arguments: `@click.argument("paths", nargs=-1, required=True)` followed by
  `@click.argument("site_name")`. `content_save <path> <site>` keeps working.
- `--generate-uuids` flag, default False.
- The `@click.command()` docstring (the `--help` text) shows the several-path form, e.g.
  `python manage.py content_save ../bloom_content ../bloom_extra Bloom`.
- The command runs these steps in order. A failure in steps 1 to 3, or in the missing-uuid or
  collision check at the start of step 4, stops the run before anything is written to the
  database, the source files or file storage. A later failure inside step 4 rolls back the database
  rows; files already uploaded and `_optimised/` files already written stay, as today.
  1. **Path checks.** Each path exists. No path is equal to, or inside, another path. Each path's
     ignore list is read and checked here; a malformed entry raises `CommandError` naming the entry
     and the `.fls-content.yaml` it came from.
  2. **Git check, for every path** (see below). All dirty files across all paths are reported
     together.
  3. **Validation.** `validate(path, ignore=...)` for every path. Problems from all paths are
     collected into one report, each labelled with its path.
  4. **Save.** `save_content_to_db(paths, site_name, generate_uuids=..., source_commits=...)`.
- New refusals (path checks, git check, missing uuids, collisions, debug organisation name clash)
  raise `django.core.management.CommandError`, so the author sees the message without a traceback
  and the exit code is 1. They keep the existing message style: the `❌` prefix, a count line, the
  list, and the fix last. Existing `ValueError` failures stay as they are.

### Git check: `freedom_ls/base/git_utils.py`

New public functions built on dulwich. The module's branch cache is not used.

- `find_repo_root(path: Path) -> Path | None`: walks up from `path` to the working tree root
  (`dulwich.repo.Repo.discover`). Handles a `.git` directory, a `.git` file (linked worktree), and
  `commondir`.
- `uncommitted_paths(path: Path) -> list[UncommittedPath]`: every staged, modified, deleted or
  untracked file under `path`, with its kind (`staged`, `modified`, `deleted`, `untracked`). Built on
  `dulwich.porcelain.status`, called with `untracked_files="all"`. An unstaged path whose
  working-tree file does not exist is `deleted`; any other unstaged path is `modified`. Every entry
  of the staged `add`, `delete` and `modify` lists is `staged`. A path in both the staged and
  unstaged lists is one `UncommittedPath` whose kind joins both (`staged, modified` or
  `staged, deleted`). Changes outside `path` in the same repo are not reported. Gitignored files are
  not reported.
- `head_commit_of(path: Path) -> str`: the full HEAD commit sha of the repo holding `path`.
- `tracked_files(path: Path) -> frozenset[Path]`: the absolute path of every file in the index of
  the repo holding `path`. The command uses it for the "must be in the index" rule below.
- The command refuses: a path not inside a git working tree; a repo with no commit at HEAD (unborn
  branch); any uncommitted path.
- Every file the save reads must be in the index: the `get_all_files` result for each path, and the
  `.fls-content.yaml` at the content repo root. A file that is gitignored is reported as
  `untracked (gitignored)`. An uncommitted `.fls-content.yaml` is listed once per content repo root,
  under its own heading naming that root, before the per-path groups.
- The ignore list does not exempt a file from the git check (`answers.md`). An ignored file in the
  list is marked `(in the .fls-content.yaml ignore list; it still has to be committed)`.
- The refusal lists dirty files grouped by source path (as the author typed it), as paths relative
  to the content repo root with their kind, at most 20 per path followed by `... and N more`, and
  ends: commit or remove these files, then run again.
- `get_head_commit` and `get_current_branch` keep their behaviour for their current callers
  (`base/context_processors.py`, `accounts/management/commands/build_legal_docs_manifest.py`).

### Missing uuids and several paths: `save_content_to_db`

- New signature:

  ```python
  def save_content_to_db(
      paths: Path | str | Sequence[Path | str],
      site_name: str,
      *,
      generate_uuids: bool = True,
      source_commits: Sequence[SourceCommit] | None = None,
  ) -> None
  ```

  A single path keeps working.
- It reads each path's ignore list itself (`find_repo_root` plus the pure reader below), so direct
  callers such as `loaded_demo_content` honour it too. A path outside any repo gets an empty list.
- One `@transaction.atomic` call covers every path, so a database failure in any path rolls back
  the rows of all of them.
- With `generate_uuids=False`, after every path is parsed and its placements checked, and before
  the first write (`save_file_to_db`, the first call that writes into `_optimised/`): if any uuid is
  missing, raise. The check covers `item.uuid` for Topic, Activity, Article, Course, CoursePart,
  Form, FormPage, FormContent and FormQuestion; each `QuestionOption` in `item.options`; and each
  entry of a `COURSE_CATEGORIES` document (`item.categories`). Every missing uuid in every path is
  reported together, grouped by source path and file, each line naming the kind and title (and, for
  an option or category entry, its parent and position). The message ends: run again with
  `--generate-uuids`, then commit the changed files. `missing_uuids(all_parsed)` in `content_save.py`
  lists them as `(file, description)` pairs, so the demo content test runs the same check.
- With `generate_uuids=True`, behaviour is today's: uuids are written into the source files.
- Before the first write, two source paths yielding the same relative path (content file or
  uploaded `File`) raise, naming the relative path and both source paths.
- Each source path gets its own `ImageCache(path)`, and its manifests are written under that path,
  as today.
- When `source_commits` is given, a `ContentSave` with one `ContentSaveSource` per path is created
  inside the same transaction, so a rolled-back save leaves no record. Without it, no record.

### Save record: `freedom_ls/content_engine/models/`

- `ContentSave(SiteAwareModel)`: `saved_at` (DateTimeField, `default=timezone.now`), and
  `generate_uuids` (BooleanField). A save run with `--generate-uuids` records the HEAD commit
  checked before the run, which does not contain the uuids the run wrote. The flag tells a reader
  so.
- `ContentSaveSource`: `content_save` (FK, `related_name="sources"`, `on_delete=PROTECT`), `order`
  (PositiveIntegerField, position on the command line), `repo_path` (CharField, the source path
  relative to its content repo root, `""` for the root), `commit` (CharField, max 64, the full sha).
  Unique on `(content_save, order)`.
- Only `save_content_to_db` writes these rows. Nothing updates or deletes them.

### Debug organisations: `_resolve_organisations` in `content_save.py`

- With `settings.DEBUG` on, each slug in `organisations` or `shared_with` that has no
  `Organisation` on the site is created with
  `Organisation._base_manager.get_or_create(site=site, slug=slug, defaults={"name": derived})`.
  `ensure_organisation` is not used, because it keys on name and may suffix the slug.
- Derived name: split the slug on `-` and `_`, capitalise the first letter of each word, and join
  with spaces (`harbour-college` → `Harbour College`). `str.title()` is not used.
- `Organisation` names are unique per site (`unique_organisation_name_per_site`). When another
  organisation on the site already holds the derived name, the save refuses with a `❌` message
  naming the slug, the course file, and that organisation with its slug.
- The save's transaction covers the creation, so a failed save rolls it back.
- With `settings.DEBUG` off, an unknown slug fails as today.

### Ignore list: `freedom_ls/content_engine/validate.py`

- Read from `.fls-content.yaml` at the content repo root of each path. A missing file, a path
  outside any repo, or a file with no `ignore:` key means an empty list in Django. The offline
  validator keeps requiring the file.
- Format: `ignore:` is a list of strings. Each entry is an exact POSIX path relative to the content
  repo root, naming a file or a folder. A folder entry covers everything beneath it. A leading `./`
  and a trailing `/` are stripped. An entry that is absolute, contains `..`, or contains `*`, `?` or
  `[` is an error naming the entry. Matching is by path component, so `docs` does not match
  `docs-old`.
- A pure reader, `read_ignore_list(root: Path) -> frozenset[Path]` (stdlib and `yaml` only), takes
  the root, reads and checks the entries, and returns them as absolute paths resolved against that
  root. Every consumer matches a file with `is_ignored(file_path, ignore)`, by absolute path
  component, so none needs the root.
- `ignore_list_for(path: Path) -> frozenset[Path]` in `freedom_ls/content_engine/ignore_list.py`
  joins `find_repo_root` and `read_ignore_list` for the Django callers (`content_save`,
  `save_content_to_db`, `content_validate`). It is not in `validate.py`, which stays free of
  dulwich so the offline copy can be re-synced.
- An ignored path is never parsed as content, never uploaded as a `File`, and never adopted by child
  auto-discovery. `collection_children` uses the ignore list only for auto-discovery and keeps every
  explicit `children:` entry. `validate` rejects an explicit `children:` entry naming an ignored
  path (a new check, reported with the other `Invalid children list` errors), and `_section_problem`
  rejects a `sections:` target naming one; both say
  `content_save skips this file: it is in the .fls-content.yaml ignore list` and tell the author to
  remove the entry or the ignore line. An image or file reference to an ignored file fails as a
  missing file does today.
- The ignore list is passed to `get_all_files`, `is_loader_skipped`, `collection_children` and
  everything that calls it (`auto_discovered_children`, `_ParsedByPath.children_of`,
  `validate_children_lists`, `validate_due_date_placements`, the save's child loop in
  `content_save.py`), `_section_problem`, and `validate(path, ignore=...)`.
- `content_validate` (`content_validate.py`) reads the ignore list the same way and passes it to
  `validate`. It performs no git check.
- The offline validator (`claude_plugins/fls-content/validate/validate.py`) treats the current
  directory as the content repo root, as it already does for `.fls-content.yaml`. It reads `ignore`
  from that file and resolves entries against it. Its `__main__` "no content files" warning uses
  the filtered file list. The `is_skipped_path` docstring in both
  `freedom_ls/content_engine/validate.py` and the offline copy says "skipped" instead of "ignored".
  The offline copy's header records the `ignore` reading under patch 4 (the only code path that
  reads `.fls-content.yaml`), so a re-sync keeps it.

## Testing

Tests that need a git repo build it with dulwich (`porcelain.init`, `add`, `commit`), so the suite
does not need a `git` binary. One shared fixture, `committed_content_repo`, builds a committed content repo in `tmp_path`. It and
the helpers `init_repo` and `commit_all` live in `freedom_ls/tests/git_repos.py`.
Refusal tests call `call_command("content_save", *paths, site, "--traceback")` so the
`CommandError` is raised, and assert on its message.

- **Command arguments:** one path plus site works; three paths plus site works; a path inside
  another path, or the same path twice, is refused before the git check.
- **Git check:** clean repo passes and records the HEAD sha; each of modified, staged, deleted and
  untracked under the path is refused and listed with its kind; a change outside the source path in
  the same repo does not block; a gitignored file the content scanner does not read does not block;
  a gitignored file the content scanner would read is refused; an uncommitted `.fls-content.yaml`
  at the repo root of a subdirectory path is refused; a path outside any repo is refused; a repo
  with no commits is refused; a linked worktree works; a dirty tree with missing uuids reports only
  the dirty tree; an ignored file with uncommitted changes is refused.
- **Missing uuids:** with the flag off, a missing uuid of each kind (the nine models, an option,
  a category entry) fails, and all are reported in one message across two paths. After the failure
  the database, source files, `_optimised/` and file storage are unchanged. With the flag on,
  today's write-back happens.
- **Several paths:** content from two paths lands in one save; a validation failure in the second
  path writes nothing from the first; the same relative path in two paths fails naming both; each
  path gets its own image cache manifests.
- **Save record:** a successful command run creates one `ContentSave` with one
  `ContentSaveSource` per path, in order, with `repo_path` and `commit`, and `generate_uuids`
  matching the flag. A failed save leaves none. A direct `save_content_to_db` call without
  `source_commits` creates none.
- **Debug organisations:** with `settings.DEBUG = True`, an unknown slug in `organisations` and in
  `shared_with` creates the organisation with the derived name and links it; a derived name already
  held by another organisation is refused naming both; a later failure in the same save rolls the
  organisation back. With DEBUG off, the existing
  `test_unknown_organisation_slug_fails_naming_slug_file_and_valid_slugs` tests still pass.
- **Ignore list:** an ignored file and an ignored folder are not parsed, uploaded or
  auto-discovered, through both the command and a direct `save_content_to_db` call; an explicit
  `children:` entry or `sections:` target that is ignored is rejected; a missing file means nothing
  is ignored; malformed entries (absolute, `..`, glob characters) fail naming the entry; `docs` does
  not ignore `docs-old`; an image reference to an ignored file fails as a missing file;
  `content_validate` honours the list; the offline validator's tests
  (`claude_plugins/fls-content/validate/tests/test_validator.py`) cover the same cases.
- **Demo content:** a test parses all of `demo_content/` and fails when any content item, option or
  category entry has no uuid.
- **Existing tests** that call the `content_save` command run against a committed repo with uuids,
  or call `save_content_to_db` directly where the command itself is not under test.
- **git_utils:** `find_repo_root`, `uncommitted_paths` and `head_commit_of` against a plain repo, a
  subdirectory, a linked worktree, a detached HEAD and packed refs.

- `docs/product/content-editing-workflow.md` (lines 19 and 46): the author runs
  `content_save --generate-uuids` to write uuids, then commits. A plain run fails on a missing uuid

- Upgrade notes for downstream projects (`/fls-dev:update_upgrade_notes`): `content_save` now needs

  Downstream deploy scripts that run `content_save` on a checkout with local changes will fail.

## Open questions

- Q: Should the clean check use dulwich, a new dependency? → A: Yes (assumed default: a
  hand-written index, pack and gitignore reader is a large, risky reimplementation for an audit
  gate. Overrule by editing Decisions and "Git check").
- Q: Must a source path be self-contained, or can references cross source paths? → A:
  Self-contained, each path validated on its own as today (assumed default: today's resolution is
  per root and the idea asks for nothing more. Spec 2, which makes one call cover the whole source,
  can widen it. Overrule by editing Decisions).
- Q: What does a `--generate-uuids` save record as its commit? → A: The HEAD checked before the
  run, with `ContentSave.generate_uuids` set (assumed default: the run wrote uuids the commit lacks,
  and the flag says so. Spec 3 decides whether such saves count for question versions. Overrule by
  editing "Save record").
- Q: Is a source path inside, or equal to, another source path refused? → A: Yes, before the git
  check (assumed default: it would load the same files twice. Overrule by editing "Command line").
- Q: How long is the dirty-file list? → A: 20 per path, then a count (assumed default: the author
  needs the count and a sample. Missing uuids are not capped because each needs a fix. Overrule by
  editing "Git check").
- Q: Is "an image reference to an ignored file fails as a missing file" tested? → A: Yes, in the
  Ignore list test bullet (assumed default: one cheap case pins the rule. Overrule by editing
  Testing).
- Q: Does Purpose say "git trees" or "source paths"? → A: "source paths" (assumed default: matches
  Terminology. Overrule by editing Purpose).

## Success criteria

- With `settings.DEBUG` on, or on a site where `ensure_demo_organisations` has run,
  `content_save demo_content <site>` from a clean FLS checkout loads with no flag and creates one
  `ContentSave`.
- `content_save` on a tree with any uncommitted or untracked file under the path exits 1, lists the
  files, and changes nothing.
- The `content_engine` and `base` tests pass with no `git` binary on `PATH`.
- `grep -rniE "written back|writes? (it|the uuid) back|Written by .content_save|automatically generated|gains a .uuid|uuid added|on first run|first .content_save" docs/product claude_plugins/fls-content demo_content`
  returns only lines that name `--generate-uuids`.
