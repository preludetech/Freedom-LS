# Spec: Content save safety

Spec 1 of 5 in the SACAA content versions and access effort (`spec_dd/1. next/roadmap.md`,
section "SACAA content versions and access"). Idea: `idea.md`. Up-front answers: `answers.md`.
Research: `research_*.md` beside this file.

## Purpose

`content_save` writes uuids into the author's files, takes one path, and loads whatever is on disk,
committed or not. For SACAA, the question text a learner saw must trace back to a committed state of
the content, and a forgotten uuid must not quietly become a new row. After this spec, `content_save`
loads one or more clean git trees, refuses missing uuids unless told to generate them, records the
HEAD commit of each path, and skips the paths a content repo lists under `ignore:` in
`.fls-content.yaml`. In development it also creates organisations that course frontmatter names.

## Terminology

| Term | Status | Meaning / source |
| --- | --- | --- |
| `ContentSave` | coined | One successful run of `content_save` for one site: when, and with which flag. No existing record of a save exists. |
| `ContentSaveSource` | coined | One source path of a `ContentSave`, with the HEAD commit it was loaded from. |
| **source path** | narrowed | A path argument to `content_save`. Today the single `path` argument. |
| **content repo root** | coined | The top of the git working tree that holds a source path. `.fls-content.yaml` is read from here. |
| **ignore list** | coined | The `ignore:` entries of the `.fls-content.yaml` at a content repo root. |

## Scope

In:

- `content_save` takes one or more source paths and one site, checks that every source path is a
  clean git tree, refuses missing uuids unless `--generate-uuids` is passed, and records a
  `ContentSave`.
- With `settings.DEBUG` on, an unknown organisation slug in `organisations` or `shared_with` creates
  the `Organisation`.
- `.fls-content.yaml` gains `ignore:`. `content_save`, `content_validate` and the offline
  `fls-content` validator skip ignored paths.
- `demo_content/` keeps every uuid, and that is enforced by a test.
- Docs and the `fls-content` plugin describe the new authoring flow.

Out:

- Retiring removed content, and "one call covers the site's whole source":
  `sacaa-compliance-content-versions-and-access-2-retire-removed-content`.
- Question versions, and anything that reads `ContentSave` for them:
  `sacaa-compliance-content-versions-and-access-3-question-versions`.
- Remote, push or upstream checks.
- Any change to what `content_validate` checks, apart from skipping ignored paths.
- An admin page or any other UI for `ContentSave`.

## Decisions

- **dulwich reads git state.** The clean check needs the index, the HEAD tree (often in a pack
  file) and `.gitignore` rules. dulwich is pure Python and needs no `git` binary. A hand-written
  reader would be a git reimplementation in an audit-critical path. Add it with `uv add dulwich`.
- **The git check and the recorded commit belong to the command.** `save_content_to_db` never
  checks git, because tests and downstream callers load from temporary directories. It records a
  `ContentSave` only when the caller hands it the sources.
- **`save_content_to_db` defaults `generate_uuids=True`. The command defaults it to False.**
  Existing callers and tests that load uuid-less temporary files keep working.
- **The uuid check runs only on the save path.** `content_validate` and the offline validator keep
  accepting uuid-less authoring work.
- **Each source path is self-contained.** Every path-based reference (`children:`, `sections:`,
  images, auto-discovered children) resolves inside its own source path, as today. Each path is
  validated on its own.
- **`file_path` stays relative to its own source path.** Two source paths that yield the same
  relative path fail the save. Template tags look files up by `file_path` alone, so a collision
  would be ambiguous, and no database constraint catches it (`File` is keyed
  `(site, file_path)` and is silently overwritten).
- **Gitignored files are not dirty, but a loaded file must be tracked.** This matches `git status`.
  A gitignored file that the save would read fails the save, so nothing uncommitted is loaded.
- **The ignore list does not exempt a path from the git check** (`answers.md`). An ignored file
  with uncommitted changes still fails the save.

## Requirements

### Command line: `freedom_ls/content_engine/management/commands/content_save.py` `command`

- Arguments: `@click.argument("paths", nargs=-1, required=True)` followed by
  `@click.argument("site_name")`. `content_save <path> <site>` keeps working.
- `--generate-uuids` flag, default False.
- The `@click.command()` docstring (the `--help` text) shows the several-path form, e.g.
  `python manage.py content_save ../bloom_content ../bloom_extra Bloom`.
- The command runs these steps in order. A step that fails stops the run, and nothing is written to
  the database, the source files or file storage:
  1. **Path checks.** Each path exists. No path is equal to, or inside, another path.
  2. **Git check, for every path** (see below). All dirty files across all paths are reported
     together.
  3. **Validation.** `validate(path, ignore=...)` for every path. Problems from all paths are
     collected into one report, each labelled with its path.
  4. **Save.** `save_content_to_db(paths, site_name, generate_uuids=..., sources=...)`. The
     missing-uuid check and the relative-path collision check happen inside it, before any write.
- New refusals (path checks, git check, missing uuids, collisions) raise
  `django.core.management.CommandError`, so the author sees the message without a traceback and the
  exit code is 1. They keep the existing message style: the `❌` prefix, a count line, the list,
  and the fix last. Existing `ValueError` failures stay as they are.

### Git check: `freedom_ls/base/git_utils.py`

New public functions built on dulwich. The module's branch cache is not used.

- `find_repo_root(path: Path) -> Path | None`: walks up from `path` to the working tree root
  (`dulwich.repo.Repo.discover`). Handles a `.git` directory, a `.git` file (linked worktree), and
  `commondir`.
- `uncommitted_paths(path: Path) -> list[UncommittedPath]`: every staged, modified, deleted or
  untracked file under `path` (repo-relative POSIX path plus a kind: `staged`, `modified`, `deleted`,
  `untracked`). Built on `dulwich.porcelain.status`. Changes outside `path` in the same repo are not
  reported. Gitignored files are not reported.
- `head_commit_of(path: Path) -> str`: the full HEAD commit sha of the repo holding `path`.
- Failures the command reports as refusals: a path not inside a git working tree; a repo with no
  commit at HEAD (unborn branch); any uncommitted path.
- The tracked-file rule: every file the save reads (the `get_all_files` result for each path) must be
  in the index. A file that is not (because it is gitignored) is reported as `untracked (gitignored)`.
- The refusal lists dirty files grouped by source path (as the author typed it), as paths relative
  to the content repo root with their kind, at most 20 per path followed by `... and N more`, and
  ends: commit or remove these files, then run again. An ignored path in the list is marked
  `(in the .fls-content.yaml ignore list; it still has to be committed)`.
- `get_head_commit` and `get_current_branch` keep their behaviour for their current callers
  (`base/context_processors.py`, `accounts/management/commands/build_legal_docs_manifest.py`).

### Missing uuids: `save_content_to_db`

- New signature:

  ```python
  def save_content_to_db(
      paths: Path | str | Sequence[Path | str],
      site_name: str,
      *,
      generate_uuids: bool = True,
      sources: Sequence[ContentSourceState] | None = None,
  ) -> None
  ```

  A single path keeps working. `ContentSourceState` holds a source path, its repo-relative
  subdirectory and its HEAD commit, and is what the command builds from the git check.
- One `@transaction.atomic` call covers every path, so a database failure in any path rolls back
  the rows of all of them.
- With `generate_uuids=False`, after every path is parsed and its placements checked, and before
  the first write (`save_file_to_db`, the first call that writes into `_optimised/`): if any uuid is
  missing, raise. The check covers `item.uuid` for Topic, Activity, Article, Course, CoursePart,
  Form, FormPage, FormContent and FormQuestion; each `QuestionOption` in `item.options`; and each
  entry of a `COURSE_CATEGORIES` document (`item.categories`). Every missing uuid in every path is
  reported together, grouped by source path and file, each line naming the kind and title (and, for
  an option or category entry, its parent and position). The message ends: run again with
  `--generate-uuids`, then commit the changed files.
- With `generate_uuids=True`, behaviour is today's: uuids are written into the source files.
- Relative-path collisions: before the first write, if two source paths yield the same relative
  path (content file or uploaded `File`), raise, naming the relative path and both source paths.
- Each source path gets its own `ImageCache(path)`, and its manifests are written under that path,
  as today.
- When `sources` is given, a `ContentSave` with one `ContentSaveSource` per path is created inside
  the same transaction, so a rolled-back save leaves no record.

### Save record: `freedom_ls/content_engine/models/`

- `ContentSave(SiteAwareModel)`: `saved_at` (DateTimeField, `default=timezone.now`), and
  `generate_uuids` (BooleanField). A save run with `--generate-uuids` records the HEAD commit
  checked before the run, which does not contain the uuids the run wrote. The flag tells a reader
  so.
- `ContentSaveSource`: `content_save` (FK, `related_name="sources"`, `on_delete=PROTECT`), `order`
  (PositiveIntegerField, position on the command line), `repo_path` (CharField, the source path
  relative to its content repo root, `""` for the root), `commit` (CharField, max 64, the full sha).
  Unique on `(content_save, order)`.
- Only `save_content_to_db` writes these rows. Nothing updates or deletes them.
- Migration via `uv run manage.py makemigrations`.

### Debug organisations: `_resolve_organisations` in `content_save.py`

- With `settings.DEBUG` on, each slug in `organisations` or `shared_with` that has no
  `Organisation` on the site is created with
  `Organisation._base_manager.get_or_create(site=site, slug=slug, defaults={"name": derived})`.
  `ensure_organisation` is not used, because it keys on name and may suffix the slug.
- Derived name: split the slug on `-` and `_`, capitalise the first letter of each word, and join
  with spaces (`harbour-college` → `Harbour College`). `str.title()` is not used.
- The save's transaction covers the creation, so a failed save rolls it back.
- With `settings.DEBUG` off, an unknown slug fails as today.

### Ignore list

- Read from `.fls-content.yaml` at the content repo root of each path (`find_repo_root`). A missing
  file, a path outside any repo, or a file with no `ignore:` key means an empty list in Django. The
  offline validator keeps requiring the file.
- Format: `ignore:` is a list of strings. Each entry is an exact POSIX path relative to the content
  repo root, naming a file or a folder. A folder entry covers everything beneath it. A leading `./`
  and a trailing `/` are stripped. An entry that is absolute, contains `..`, or contains `*`, `?` or
  `[` is an error naming the entry. Matching is by path component, so `docs` does not match
  `docs-old`.
- An ignored path is never parsed as content, never uploaded as a `File`, never adopted by child
  auto-discovery, and is rejected as a `sections:` target with the same kind of message as a
  `_`-prefixed name.
- A pure function in `freedom_ls/content_engine/validate.py` (stdlib and `yaml` only) reads and
  normalises the list. `get_all_files`, `auto_discovered_children` and `_section_problem` take the
  ignore list, and so does `validate(path, ignore=...)`. `is_loader_skipped` gains the check, given
  the content repo root as a second base.
- `content_validate` (`content_validate.py`) reads the ignore list the same way and passes it to
  `validate`. It performs no git check.
- The offline validator (`claude_plugins/fls-content/validate/validate.py`) picks up the change
  through `/fls-dev:update_claude_plugin_fls_content`. Its patch notes gain an entry: it reads
  `ignore` from the `.fls-content.yaml` it already reads at the current directory, and its
  `__main__` "no content files" warning uses the filtered file list.

## Testing

Tests that need a git repo build it with dulwich (`porcelain.init`, `add`, `commit`), so the suite
does not need a `git` binary. One shared fixture builds a committed content repo in `tmp_path`.

- **Command arguments:** one path plus site works; three paths plus site works; a path inside
  another path, or the same path twice, is refused before the git check.
- **Git check:** clean repo passes and records the HEAD sha; each of modified, staged, deleted and
  untracked under the path is refused and listed with its kind; a change outside the source path in
  the same repo does not block; a gitignored file the loader does not read does not block; a
  gitignored file the loader would read is refused; a path outside any repo is refused; a repo with
  no commits is refused; a source path that is a subdirectory works; a linked worktree works; a
  dirty tree with missing uuids reports only the dirty tree; an ignored file with uncommitted
  changes is refused.
- **Missing uuids:** with the flag off, a missing uuid of each kind (the nine models, an option,
  a category entry) fails, and all are reported in one message across two paths. After the failure
  the database, source files, `_optimised/` and file storage are unchanged. With the flag on,
  today's write-back happens.
- **Several paths:** content from two paths lands in one save; a validation failure in the second
  path writes nothing from the first; the same relative path in two paths fails naming both; each
  path gets its own image cache manifests.
- **Save record:** a successful command run creates one `ContentSave` with one
  `ContentSaveSource` per path, in order, with `repo_path` and `commit`, and `generate_uuids`
  matching the flag. A failed save leaves none. A direct `save_content_to_db` call without
  `sources` creates none.
- **Debug organisations:** with `settings.DEBUG = True`, an unknown slug in `organisations` and in
  `shared_with` creates the organisation with the derived name and links it. A later failure in the
  same save rolls the organisation back. With DEBUG off, the existing
  `test_unknown_organisation_slug_fails_naming_slug_file_and_valid_slugs` tests still pass.
- **Ignore list:** an ignored file and an ignored folder are not parsed, uploaded or
  auto-discovered; a `sections:` target that is ignored is rejected; a missing file means nothing is
  ignored; malformed entries (absolute, `..`, glob characters) fail naming the entry; `docs` does
  not ignore `docs-old`; `content_validate` honours the list; the offline validator's tests
  (`claude_plugins/fls-content/validate/tests/test_validator.py`) cover the same cases.
- **Demo content:** a test parses all of `demo_content/` and fails when any item, option or category
  entry has no uuid.
- **Existing tests:** the four `call_command("content_save", ...)` sites
  (`test_content_save.py:3332`, `test_moved_children.py:66`, `deadlines/tests/test_signals.py:53`
  and `:76`) move onto the committed-repo fixture, with uuids in their files, or call
  `save_content_to_db` directly where the command itself is not under test.
- **git_utils:** `find_repo_root`, `uncommitted_paths` and `head_commit_of` against a plain repo, a
  subdirectory, a linked worktree, a detached HEAD and packed refs.

## Open questions

- Q: Should the clean check use dulwich, a new dependency? → A: Yes (assumed default: a
  hand-written index, pack and gitignore reader is a large, risky reimplementation for an audit
  gate. Overrule by editing Decisions and "Git check").
- Q: Must a source path be self-contained, or can references cross source paths? → A:
  Self-contained, each path validated on its own as today (assumed default: today's resolution is
  per root and the idea asks for nothing more. Spec 2, which makes one call cover the whole source,
  can widen it. Overrule by editing Decisions).
- Q: What does a `--generate-uuids` save record as its commit? → A: The HEAD checked before the
  run, with `ContentSave.generate_uuids` set (assumed default: the run wrote uuids the commit lacks,
  and the flag says so. Spec 3 decides whether such saves count for question versions. Overrule by
  editing "Save record").
- Q: Is a source path inside, or equal to, another source path refused? → A: Yes, before the git
  check (assumed default: it would load the same files twice. Overrule by editing "Command line").
- Q: How long is the dirty-file list? → A: 20 per path, then a count (assumed default: the author
  needs the count and a sample. Missing uuids are not capped because each needs a fix. Overrule by
  editing "Git check").

## Success criteria

- `content_save demo_content <site>` from a clean FLS checkout loads with no flag and creates one
  `ContentSave`.
- `content_save` on a tree with any uncommitted or untracked file under the path exits 1, lists the
  files, and changes nothing.
- `content_save` on uuid-less content exits 1, lists every missing uuid, and changes nothing. The
  same run with `--generate-uuids` writes them.
- `content_save a b <site>` loads both paths in one transaction and records two
  `ContentSaveSource` rows with their commits.
- With DEBUG on, a course naming an unknown organisation slug saves and the organisation exists
  with the derived name.
- A file listed under `ignore:` is skipped by `content_save`, `content_validate` and the offline
  validator.
- The `content_engine` and `base` tests pass with no `git` binary on `PATH`.
- `grep -rn "written back" docs/product claude_plugins/fls-content` finds no claim that a plain
  `content_save` writes uuids.
