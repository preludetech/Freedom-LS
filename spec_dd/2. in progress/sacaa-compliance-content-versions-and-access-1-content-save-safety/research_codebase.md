## 2. Where uuids are written back

All in `content_save.py`:

- `update_file_with_category_uuids(file_path, written)` line 223: entries of the `COURSE_CATEGORIES` document, by index.

- `File` rows (via `save_file_to_db`, line 946) get no uuid. `ContentCollectionItem` and `CoursePartChildDueDate` are derived and get none.

Where to put the missing-uuid check, as it stands: a pre-write pass over `all_parsed` in `save_content_to_db`, after the placement checks (line 1068) and before `save_file_to_db` at 1071, is before every write (storage, DB, source files). The base schema field is `uuid: str | None` at `content_base/schema.py:34`. A parsed item carries `file_path`, so every missing uuid can be reported with file, kind and entry index together.

Note the dependency the effort research flagged: option uuid write-back needs the question uuid already in the file (`update_file_with_option_uuids` matches on it). With `--generate-uuids` the question gets its uuid first within the same run, so it works.

## 5. `freedom_ls/base/git_utils.py`

What exists (filesystem only, no `subprocess`):
- `get_current_branch(base_dir=None)` (cached module-level, `_clear_branch_cache`), `get_head_commit(base_dir=None)` (line 31), `_resolve_git_dir`, `_resolve_ref`, `_refs_search_dirs`, `_read_commondir`, `_read_loose_ref`, `_read_packed_ref`, `_looks_like_sha`, `_read_branch`, `branch_to_db_name`.
- `get_head_commit` handles: `.git` directory, `.git` file with `gitdir:` (absolute or relative), detached HEAD (40-hex), a loose ref, `packed-refs` (skips `#` and `^` lines), and worktrees via `commondir` (per-worktree dir first, then common dir). Tests: `freedom_ls/base/tests/test_git_utils.py` class `TestGetHeadCommit` covers detached, loose, packed, worktree loose via commondir, worktree packed via commondir, no git dir, unresolvable ref. `freedom_ls/accounts/tests/_git_helpers.py` has `run_git`, `init_repo`, `commit_all` (real git, tests only).

What it cannot do today (gaps for this spec):
- **Subdirectory**: `_resolve_git_dir(base_dir)` looks only for `base_dir / ".git"`. It does not walk up. A path that is a subdirectory of a repo (`demo_content` inside the FLS repo) returns None. A new function must walk the parents to find the repo root (stop on first `.git` that is a dir or a `gitdir:` file) and report the root, since `.fls-content.yaml` and `ignore:` entries are relative to that root (answers.md).
- **Dirty and untracked state**: nothing. A binary-free check has to read `.git/index` (git index format: `DIRC` header, version 2, 3 or 4, entries with ctime/mtime/dev/ino/mode/uid/gid/size/sha1/flags/path; v4 uses prefix-compressed path names; extensions such as `TREE`, `REUC`, `link`, `UNTR`, `FSMN` follow; with a split index `link` extension and `sharedindex.<sha>`; sparse index uses a `sdir` extension). It then has to compare each tracked file to the index (stat shortcut, else SHA-1 of the blob contents `blob <size>\0<data>`, with CRLF/`core.autocrlf`/filter conversions as a known limitation) and find untracked files by walking the tree and subtracting the index, applying `.gitignore` (per directory, `$GIT_DIR/info/exclude`, `core.excludesFile`) or declaring that ignored files count as untracked-clean. Whether gitignored files count as "untracked" is a spec decision: git's own `status` excludes them.
- **Staged but uncommitted**: needs comparing the index entry sha to the HEAD tree entry, so reading the HEAD commit's tree object. Git objects are zlib-compressed loose files at `objects/xx/yyyy...` or inside pack files (`.pack` plus `.idx`, with delta chains: OFS_DELTA and REF_DELTA). Reading HEAD's tree from a packed repo needs a pack reader. A real repo with `git gc` will have its HEAD commit in a pack. Skipping the HEAD-tree comparison would miss "staged but not committed" (index differs from HEAD), unless the check also considers a mismatch between index and HEAD as dirty. This is the largest implementation risk for "does not depend on a git binary".
- **Worktrees with a `.git` file**: handled by `_resolve_git_dir` for HEAD and refs. The per-worktree index is `<gitdir>/index` (for a linked worktree, inside `.git/worktrees/<name>/`), and `commondir` gives the shared object store. `_resolve_git_dir` already returns the per-worktree dir, so the index is at `git_dir / "index"`. Objects must come from the common dir (`objects/`), plus `objects/info/alternates`.
- **Packed refs**: handled for `get_head_commit` (reads the `packed-refs` file in either dir). Not an issue for the clean check except peeled `^` lines, which are skipped.
- A detached HEAD works; a "ref: refs/heads/x" whose ref is missing (an unborn branch, no commits) returns None.
- The existing `get_head_commit` takes a directory that must hold `.git`; the idea's recommendation "extend to take a directory" means adding the parent-walk. Existing callers (grep `get_head_commit|git_utils`): `freedom_ls/base/context_processors.py`, `freedom_ls/accounts/management/commands/build_legal_docs_manifest.py`, plus tests. `freedom_ls/accounts/legal_docs.py:75` shells out to `git` via `subprocess.run` to read a blob at HEAD, so the "no git binary" rule is not universal in the repo, but is explicit in `git_utils`'s docstring.
- The module keeps a module-level branch cache; any new function should not use it.

## 8. How scanning decides what is content (where `ignore:` plugs in)

`freedom_ls/content_engine/validate.py`:
- `is_skipped_path(path)` (line 39): name starts with `_` or `.`.
- `is_loader_skipped(file_path, base_path)` (line 121): `README.md` / `CLAUDE.md` by file name (any depth), names ending `~`, `is_skipped_path` on the file, and on every directory between `base_path` and the file (not above it).

## 11. Conflicts and interaction points to carry into the spec

1. **Tests calling `call_command("content_save", ...)`** (four sites in section 1) will hit an always-on git check and a default-False uuid check. They need a git-initialised tree with committed, uuid-carrying files, or to move to `save_content_to_db`.
2. **Dirty-tree check vs. the command's own writes.** `--generate-uuids` rewrites files; image caching writes `_optimised/` files and manifests. Order inside one call must be: parse all paths, git check (all paths), uuid check (all paths), validate (all paths), then write.
