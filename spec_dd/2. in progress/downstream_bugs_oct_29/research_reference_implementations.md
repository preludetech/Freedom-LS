## 1. Honeypot widgets (honeypot-rerenders-its-value)

- **django-honeypot** (jamesturk) [V]: no form widget. Template tag `render_honeypot_field` returns context `{"fieldname": field_name, "value": value}`; `value` comes from `settings.HONEYPOT_VALUE` (default `""`, callable allowed). The template emits a fresh `<input>` with that server-chosen value, never the submitted one. So a tripped value is never echoed because the field is not bound to the POST. Source: https://github.com/jamesturk/django-honeypot/blob/main/honeypot/templatetags/honeypot.py . Its `HONEYPOT_VERIFIER` check is value-equality (a tripped field is one that differs from `HONEYPOT_VALUE`), so a blank-by-default is the norm.
- **django-admin-honeypot** [K]: not a form honeypot. It is a fake `/admin/` login that logs attempts; no widget. Not relevant to the fix.
- **Wagtail `wagtail.contrib.forms`** [K]: no honeypot built in (spam protection is by third-party `wagtail-django-recaptcha` / `wagtail-turnstile`). Nothing to copy.
- **django-allauth** [K]: no signup honeypot in core (65.x). Only `ACCOUNT_SIGNUP_FORM_HONEYPOT_FIELD` existed in old 0.x releases (a hidden field named by the setting; the signup view silently succeeded/rejected). Not a model for widget rendering.
- **Django core hook** [K]: `Widget.format_value(value)` is the documented override point; returning `None` makes `get_context` set `widget["value"]` to `None`, so the `<input>` omits `value`. This matches the idea's suggested `HoneypotInput.format_value -> None`. Alternative used by django-simple-captcha/django-recaptcha-style widgets: `value_omitted_from_data` plus `render()` that ignores `value`. Docs: https://docs.djangoproject.com/en/stable/ref/forms/widgets/#django.forms.Widget.format_value
- Implementation choice settled: override at the widget (one place, shared by signup and both application forms), not per form or template.

## 2. allauth template overrides in real projects (allauth-pages-use-stock-templates-and-copy)

- **cookiecutter-django** [K]: `{{cookiecutter.project_slug}}/templates/account/` overrides `base.html`, `base_entrance.html`, `base_manage.html`, `login.html`, `signup.html`, `logout.html`, `email.html`, `email_confirm.html`, `password_change.html`, `password_reset*.html`, `verification_sent.html`, `verified_email_required.html`, etc. Uses `{% element h1 %}`/`{% element form %}` allauth elements and `{% trans %}` copy. Logout page is a single `<form method="post" action="{% url 'account_logout' %}">` with one submit button, no manage nav. Source: https://github.com/cookiecutter/cookiecutter-django/tree/master/%7B%7Bcookiecutter.project_slug%7D%7D/templates/account
- **allauth 65.x template structure** [V/K]: elements live at `allauth/templates/allauth/elements/*.html` (e.g. `alert.html` is just `<p>{% slot message %}{% endslot %}</p>`, fetched). Page templates `{% extends "account/base_manage.html" %}` / `base_entrance.html`; overriding `account/base_manage.html` or `account/base_entrance.html` alone removes the manage nav everywhere (this is how the double "Sign Out" is fixed). Overriding `allauth/layouts/base.html`, `entrance.html`, `manage.html` is the documented path. Docs: https://docs.allauth.org/en/latest/common/templates.html
- **django-allauth-ui** (danihodovic) [K]: ships complete replacement templates under `allauth_ui/templates/` styled with daisyUI/Tailwind; overrides every account page including `email.html` with per-address buttons. Closest analogue to FLS's Tailwind stack. https://github.com/danihodovic/django-allauth-ui
- **allauth `email.html` / hiding resend+remove** [K]: stock template renders `{% element button name="action_send" %}` and `action_remove` for all addresses and `action_primary` only `{% if emailaddresses|length > 1 %}`-style gating is NOT in stock; projects hide in override with `{% if emailaddresses|length > 1 or not emailaddress.verified %}`. allauth view already refuses removing the only primary (message `account_cannot_delete_primary_email`), so hiding is cosmetic; the template context exposes `emailaddress.verified` and `.primary`.
- **Already-confirmed re-click** [K]: `EmailConfirmationHMAC.from_key` -> `EmailAddress.objects.filter(verified=False)`; a used key resolves to `None` -> `email_confirm.html` renders the "expired or invalid" branch (`{% if confirmation %} ... {% else %}`). Override pattern: in `email_confirm.html` else-branch show "This address is already confirmed" if `request.user.is_authenticated`. A view-level option is subclassing `ConfirmEmailView` and checking `EmailAddress.objects.filter(email=..., verified=True)`; wire it through urls before allauth's.
- **`next` after verification** [V]: `DefaultAccountAdapter.get_email_verification_redirect_url(self, email_address: EmailAddress) -> str` ("The URL to return to after email verification."); it ignores `next`, uses `EMAIL_CONFIRMATION_AUTHENTICATED_REDIRECT_URL` / `..._ANONYMOUS_REDIRECT_URL`, else `get_login_redirect_url(request)`. Because it receives the `EmailAddress`, a server-side store keyed on that address (e.g. a model/row written at signup and read in this hook) is the natural fit; it is the only adapter hook with the address in hand. No mainstream project found that stores `next` on EmailAddress; common approach is the session (lost cross-device, as the bug says) or encoding `next` in the confirmation link. Source: https://github.com/pennersr/django-allauth/blob/main/allauth/account/adapter.py . Also `is_safe_url(self, url)` is the hook to validate any stored target.
- **Enumeration-safe "someone added your address" mail** [K]: allauth's `email_confirmation_message.txt` is the same for signup and add-email; `email_confirmation_signup_message.txt` is a separate template used when `signup=True`, so FLS can reword only the add-email variant by overriding `account/email/email_confirmation_message.txt` (non-signup) without touching the signup one.

## 3. Nested Markdown components and double sanitising (accordion-strips-nested-component-attributes)

- **python-markdown `md_in_html`** [K]: `<div markdown="1">` blocks are parsed by Markdown in one pass; inner raw HTML is stashed in the `htmlStash` and re-inserted after parsing (placeholders), never re-parsed. Docs: https://python-markdown.github.io/extensions/md_in_html/ . Lesson: container content is rendered once, inline, in the same parse.
- **MkDocs Material** [K]: admonitions/tabs/content tabs nest via `pymdownx.superfences` + `admonition` (indented block parsed recursively inside the same Markdown run). No HTML sanitiser at all; trust model is author-controlled source. https://squidfunnel.github.io/mkdocs-material/reference/admonitions/
- **Wagtail** [K]: StreamField blocks render their own template with `{{ value }}`/`{% include_block %}` (child blocks rendered by their own templates, output already final). RichText is sanitised (if at all) at input/save (Draftail contentstate -> whitelisted by `wagtail.whitelist`/`nh3`) not on the rendered page. Nesting never re-cleans component output. https://docs.wagtail.org/en/stable/topics/streamfield.html
- **django-markdownx** [K]: renders Markdown once server-side on request; sanitising, if wanted, is left to the project (typically `bleach`/`nh3` in a single pipeline step on the final string).
- **Hugo shortcodes** [K]: `{{% shortcode %}}` (percent form) renders inner content as Markdown and nests; `{{< >}}` form leaves inner as-is. Output is not sanitised again.
- **Pelican** [K]: Markdown reader runs once; plugins add components; no second pass.
- Pattern across all: **sanitise author source once (or trust it), render containers as one pipeline, never clean component-generated HTML**. Matches both options in the idea; option 1 (`sanitize=False` for slot rendering) is the Hugo `%` equivalent; option 2 (render nested Markdown before cotton) is the md_in_html/htmlStash equivalent.

## 4. Skip link + single h1 header (header-site-name-is-an-h1)

- **Django admin** [V] (`django/contrib/admin/templates/admin/base.html`): `<a href="#content-start" class="skip-to-content-link">{% translate 'Skip to main content' %}</a>`; `<header id="header">` with `branding` block empty by default; the only `<h1>` is `{% if title %}<h1>{{ title }}</h1>{% endif %}` inside `content_title`; `<nav aria-label="Breadcrumbs">` and `<li aria-current="page">`; `<main>` carries `tabindex="-1"` and the `id="content-start"` target sits just before the content. The site name in admin's header is `<div id="site-name"><a href="{% url 'admin:index' %}">{{ site_header }}</a></div>`, a `div`, not an h1 [K]. https://github.com/django/django/blob/main/django/contrib/admin/templates/admin/base.html
- **GOV.UK Design System** [K]: skip link is the first focusable element: `<a href="#main-content" class="govuk-skip-link" data-module="govuk-skip-link">Skip to main content</a>`; header has the logo link in a non-heading element; page `<h1 class="govuk-heading-xl">` is in `<main id="main-content" role="main">`. https://design-system.service.gov.uk/components/skip-link/ and https://design-system.service.gov.uk/components/header/
- **USWDS** [K]: `<a class="usa-skipnav" href="#main-content">Skip to main content</a>` first in body; `usa-logo` is a `<div class="usa-logo"><em class="usa-logo__text"><a>` - not a heading. https://designsystem.digital.gov/components/skipnav/
- **Wagtail admin** [K]: `<a href="#main" class="skiplink">Skip to main content</a>`-style link; page title is the single `<h1>` in `header` partial.
- Settled choice: site name is a link in a `div`/`span` (or `<p>`), the per-page h1 stays in `<main>`; skip link first in `<body>` pointing at an id on `<main>`.

## 5. Form error summary with role=alert and focus (allauth-pages... ACCT-3)

- **GOV.UK error summary** [K]: `<div class="govuk-error-summary" data-module="govuk-error-summary"><div role="alert"><h2 class="govuk-error-summary__title">There is a problem</h2><div class="govuk-error-summary__body"><ul class="govuk-list govuk-error-summary__list"><li><a href="#field-id">Error text</a></li>...`. The JS module focuses the summary on page load (`tabindex="-1"`) unless `data-disable-auto-focus`. Each field also shows `<p id="x-error" class="govuk-error-message"><span class="govuk-visually-hidden">Error:</span> msg</p>` and the input gets `aria-describedby="x-error"`; error message sits between label/hint and input (fixes the "error under wrong input" ordering). https://design-system.service.gov.uk/components/error-summary/
- **Django admin** [K]: `{% if form.errors %}<p class="errornote">Please correct the error below.</p>{{ adminform.form.non_field_errors }}{% endif %}`; no role/focus; Django 5.x `ErrorList` renders `<ul class="errorlist" id="id_x_error">` and widgets get `aria-describedby`/`aria-invalid="true"` automatically (Django 5.0+ `BoundField.build_widget_attrs`).
- **allauth 65.x** [V]: `allauth/elements/alert.html` is only `<p>{% slot message %}{% endslot %}</p>`; no role, no focus. Form error rendering is `{% element field %}` plus `form.non_field_errors`. So FLS must add `role="alert"` and focus itself (as login.html does for `role="alert"`).
- Settled: `role="alert"` wrapper for non-field errors + `autofocus`/`tabindex="-1"` focus on the summary (GOV.UK) and render each field error after its own input via `{{ field.errors }}` with `aria-describedby`.
- Autocomplete tokens (`given-name`, `family-name`) per WHATWG; Django widget `attrs={"autocomplete": "given-name"}`.

## 6. Login/signup links that remember the current page (header-auth-links-drop-the-current-page)

- **Django `redirect_to_login`** [K]: `django.contrib.auth.views.redirect_to_login(next, login_url=None, redirect_field_name="next")` builds `login_url?next=<quoted next>` (uses `QueryDict.urlencode(safe="/")`). `@login_required` and `LoginRequiredMixin` call it with `request.get_full_path()`.
- **allauth** [K]: `{% load allauth %}`/`account_tags`: template tag `{% passthrough_next_redirect_url %}` in `account_tags`: emits `&next=<urlencoded>` (or `?next=`) from `request.GET` / `POST` `next` so login<->signup cross-links keep it. Source: `allauth/account/templatetags/account.py` ( `passthrough_next_redirect_url`, `url_with_redirect` in `allauth/account/utils.py`/`utils.py` ). Reference: https://github.com/pennersr/django-allauth/blob/main/allauth/account/templatetags/account.py . Stock allauth nav links do NOT add `next` from the current page, only pass through an existing one.
- **cookiecutter-django navbar** [K]: `<a id="log-in-link" class="nav-link" href="{% url 'account_login' %}">Sign In</a>` with no `next`; i.e. same gap.
- **Typical fix** [K]: `href="{% url 'account_login' %}?next={{ request.get_full_path|urlencode }}"`. Must not append on auth pages themselves (avoid `next=/accounts/login/`) and only for GET; validate with `url_has_allowed_host_and_scheme` (allauth `adapter.is_safe_url` does so on receipt).
- GOV.UK avoids a global sign-in link; services return the user via the service's own session. Not a model.

## 7. "Continue where you left off" CTA (course-detail-continue-restarts-at-item-one)

- **Open edX course home** [K]: "Start Course" if no activity, "Resume Course" otherwise. Resume URL comes from `lms/djangoapps/courseware/` `get_last_accessed_courseware` / the `student_module` + Learning Sequence "last position" (`/api/courseware/resume/<course_id>` returns `{"section_url": ...}` or `{"section_url": None}`, falling back to course start). Label picked in `outline` `resume_course` `{ has_visited_course, resume_course_url }`. https://github.com/openedx/edx-platform (`openedx/features/course_experience/url_helpers.py: get_courseware_url`, `views/course_home.py`) and https://docs.openedx.org/
- **Moodle** [K]: course page shows "Continue" via block "Course overview" / `core_course` "Resume course" using `user_lastaccess`/completion; since Moodle 4, "Resume course" = first incomplete activity (`completion_info`) falling back to first activity.
- **Canvas** [K]: module progression and "Resume"? Canvas has no explicit resume; "Start Course/Continue" appears in mobile dashboard via last-viewed module item.
- **Coursera** [K]: "Resume" button opens the first not-completed item in order (computed on the server; skipping completed leading items), "Start" when no progress.
- Common rule: label = Start when no progress, otherwise Resume/Continue; target = last visited item (Open edX) or first not-completed item in course order (Moodle/Coursera); fall back to first item when everything is complete or no data. FLS has a progress app: first-incomplete is derivable without a new last-visited store.

## 8. Save-and-exit on multi-page forms (leave-and-save-discards-the-current-page)

- **GOV.UK pattern "Save and return later" / "Save and come back"** [K]: https://design-system.service.gov.uk/patterns/ (no formal pattern page; guidance in "Question pages" + service manual "Save and return"). Guidance: the "Save and come back later" button submits the current page; the service saves answers **without validating** what the user entered, then returns them to the same page on resume; validation is deferred to the final check/submit step. Explicit rule: do not show errors on save-and-exit.
- **Qualtrics** [K]: "Save and Continue" saves partial response on page change; responses recorded on resume link `?...&Q_R=`; no validation on save.
- **Open edX problem blocks** [K]: "Save" button posts `problem_save` handler that stores `student_answers` without grading or requiring completeness; "Submit" grades. Source: `xmodule/capa_block.py` `save_problem`. https://github.com/openedx/edx-platform/blob/master/xmodule/capa_block.py
- Pattern: separate Save endpoint/branch that persists raw answers (partial, nullable) and skips `is_valid` required checks; only the Submit branch validates. Apply that to the leave-and-save view: persist current page's posted answers best-effort.

## 9. Empty-form / structural validation at import (zero-page-form-blocks-course-completion; also the import-time part)

- **Open edX OLX import** [K]: `import_course_from_xml` is permissive; a problem with no `<choiceresponse>` etc. imports and the CAPA block shows an error at render. Studio validation is in `StudioValidationMessage` via `validate()` on blocks: severity `WARNING`/`ERROR` with text such as "This component has no content." (`xblock.validation.ValidationMessage`). https://github.com/openedx/xblock-utils / `xblock/validation.py`.
- **Moodle** [K]: quiz with no questions is allowed; student sees "This quiz has no questions" / "Quiz is not available" and `quiz_is_ok_to_attempt` returns `quiz_no_questions` error message "This quiz has not been set up yet"; completion rules (completion on grade) simply never trigger. Restore doesn't reject empty containers.
- **Static site generators** [K]: Hugo warns (`WARN`) on empty sections, errors only on parse failures; MkDocs `strict` fails builds on broken nav links, not empty pages.
- Lesson for the bug: treat a zero-page form as vacuously complete (nothing to answer) at runtime, and if import rejects it, phrase it as `<path>: form "<title>" has no pages; add at least one page or remove the form` (identify file + what + fix, as Studio's validation messages do). Moodle precedent favours not blocking completion on empty containers.

## 10. Mermaid in Markdown (learner-ux-polish-from-mega-qa, if mermaid is listed)

- **mkdocs-material** [K]: `pymdownx.superfences` with custom fence: `{name: mermaid, class: mermaid, format: !!python/name:pymdownx.superfences.fence_code_format}` emits `<pre class="mermaid"><code>...</code></pre>`; Material's JS loads mermaid lazily and renders client-side, with theme sync. https://squidfunnel.github.io/mkdocs-material/reference/diagrams/
- **GitHub** [K]: a ```` ```mermaid ```` fence is rendered client-side in a sandboxed iframe; the rest of the HTML stays sanitised. https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams
- **Docusaurus** [K]: `@docusaurus/theme-mermaid`, `markdown: { mermaid: true }`; the remark plugin turns `mermaid` code fences into `<Mermaid value="..."/>` components; config `themeConfig.mermaid.options` passes mermaid options. https://docusaurus.io/docs/markdown-features/diagrams
- **Security** [K]: Mermaid's `securityLevel` is `'strict'` by default (encodes HTML in labels, disables click handlers); `'loose'`/`'sandbox'` are opt-in. With nh3 in FLS: the fence becomes `<pre><code class="language-mermaid">` which survives nh3 if `class` on `code` is allowed; client JS then reads `textContent`, so no raw HTML passes through. Call `mermaid.initialize({startOnLoad:false, securityLevel:'strict'})`. https://mermaid.js.org/config/usage.html#securitylevel

## 11. Feature flags silencing producers (sidebar-sections-test-assumes-messaging-is-enabled)

- **django-waffle** [K]: `flag_is_active(request, "name")`, `switch_is_active("name")`; docs say to gate in view/template and in signal handlers/tasks that write. Nothing automatic. https://waffle.readthedocs.io/
- **Open edX toggles** [K]: `WaffleFlag`/`SettingToggle` (`openedx.core.djangoapps.waffle_utils`) checked inside the producer too, e.g. notifications `ENABLE_NOTIFICATIONS` is consulted in `notification_events`/`send_notifications` handlers so disabled => no `Notification` rows. https://github.com/openedx/edx-platform/tree/master/openedx/core/djangoapps/notifications
- Pattern: one `is_enabled()` helper, called by (a) template/context processor, (b) the writer's single entry point (`create_notification`-style function returns early), so there is no accumulation and no hidden unread badge.

## 12. Portable tests in reusable apps (icon-intrinsic-size..., sidebar-sections-test...)

- **django-allauth** [K]: tests use `@pytest.fixture` + `settings` fixture, `override_settings`, and `pytest.mark.parametrize` over settings (e.g. `ACCOUNT_LOGIN_METHODS`, `ACCOUNT_EMAIL_VERIFICATION`); `allauth/conftest.py` defines per-test settings fixtures and a `reset_adapter` fixture. https://github.com/pennersr/django-allauth/blob/main/allauth/conftest.py
- **Wagtail** [K]: `@override_settings(...)` on test classes and `with self.settings(...)`; its own test settings in `wagtail/test/settings.py` are minimal and every test that depends on a non-default value pins it.
- **DRF** [K]: `@override_settings(REST_FRAMEWORK={...})` / `rest_framework.settings.reload_api_settings` on `setting_changed`; tests never assume defaults implicitly.
- **django-cotton** [K]: tests render with `override_settings(TEMPLATES=...)` and a `settings.COTTON_*` fixture; component output asserted against stub templates it creates in tmp dirs.
- Pattern for FLS: pin the feature setting (`settings.X = ...` fixture) in the test, assert against the configured value read from settings/registry (not a literal like the default icon size/messaging on), parametrize on/off where both matter.

## 13. Registered learner on a gated/priced course (registered-learner-on-gated-course; apply-view-accepts-courses-that-need-no-application)

- **Open edX course about page** [K]: if the user is enrolled, `course_about` shows "You are enrolled in this course" and a "View Course" button (`reg_then_add_to_cart`/`is_enrolled` branch in `lms/templates/courseware/course_about.html`); the "Enroll Now" / price block is only rendered `{% if not registered %}`. https://github.com/openedx/edx-platform/blob/master/lms/templates/courseware/course_about.html
- **Moodle** [K]: enrolment page (`enrol/index.php`) redirects enrolled users to the course; self-enrol and payment (`enrol_fee`/PayPal) forms are shown only to non-enrolled users; enrolled users see "Continue"/course page. "You are already enrolled" notice appears if one lands on the enrol page.
