## 0. Headline findings (read first)

Items where a prior decision is reversed or an accepted state is re-opened. The spec must name each and say why it now differs.

1. **Notifications (`learner-ux-polish`, last section) reverses a decision.** Done `2026-09-27_00:24_user-communication-1-notifications-core/1. spec.md` Decision 11: "Notifications are still raised and stored, and the `/notifications/` URLs still answer, so a site that turns the bell on later shows the history. The idea's fix (early return in `raise_notification` plus 404 the views) contradicts all three. It also collides with queued `1. next/user-communication-2-notification-email/idea.md`: email "reaches people who are already not logged in" and is "a delivery backend on spec 1's notification layer" (`NOTIFICATION_DELIVERY_BACKENDS`, called inside `raise_notification`'s `create_and_enqueue`). Gating the writer on the bell flag would silence email for any site that has the bell off.
2. **Header auth links (`header-auth-links-drop-the-current-page`) re-adds what a revert removed.** Done `2026-07-17_09:12_bugfix-shitty-allauth-decisions/1. spec.md` success criterion 2: "`login_prompt.html`'s two buttons link to bare `{{ login_url }}` / `{{ signup_url }}` with no `?next=` query param". Criterion 4 accepted that a visitor who passes the forced registration-completion step "deliberately loses that destination ... this is the accepted vanilla trade-off". Check the earlier reasons for the revert before re-adding (middleware `next`-forwarding was the bulk of the mess; the header fallback is the smaller half).
3. **`apply` tweak (`DISC-2`) must not key off `application_form`.** `freedom_ls/course_applications/views.py:132-135` docstring: a gated course that names no form "keeps the confirmation page, because there creating the application is the submission itself". 4. **Zero-page forms (`LEARN-5`) are a legitimate state for application forms.** `freedom_ls/course_applications/views.py:706-713` `_resume_url`: "A form with no pages has nothing to fill in, so the only place left to send the applicant is the page they submit from." ## 5. Prior art elsewhere (brief)

Searches returned little; stated plainly, not padded.

- **allauth, re-clicking a used confirmation link (ACCT-8).** No issue found that says "show already confirmed". Related allauth issues about single-use and purge of confirmations: [#641 Setting required for Email verification link to expire on single use](https://github.com/pennersr/django-allauth/issues/641), [#638 Purge used email confirmation](https://github.com/pennersr/django-allauth/issues/638), [#1522 Email Verification Link Invalidation](https://github.com/pennersr/django-allauth/issues/1522) (titles only; bodies not read). Docs: [account configuration](https://docs.allauth.org/en/latest/account/configuration.html): "`ACCOUNT_EMAIL_CONFIRMATION_HMAC` ... Current versions use HMAC based keys that do not require server side state." The idea's cause (lookup with `verified=False`) is consistent with that; it is not documented upstream as intended.
- **allauth, `next` lost across devices (ACCT-6).** No upstream issue found. Allauth keeps the post-signup redirect in the session; the confirmation key carries no `next`. Relevant settings: `ACCOUNT_EMAIL_CONFIRMATION_AUTHENTICATED_REDIRECT_URL` (default `None`) and `ACCOUNT_EMAIL_CONFIRMATION_ANONYMOUS_REDIRECT_URL` (default `settings.LOGIN_URL`) at the docs link above. Also `ACCOUNT_EMAIL_VERIFICATION_BY_CODE_ENABLED` (default `False`; the code is typed in the browser that signed up, which sidesteps the cross-device problem without storing `next`). FLS enables neither (`config/settings_base.py:431-438`). Analogy only: [Bubble forum, confirmation fails in another browser](https://forum.bubble.io/t/email-confirmation-not-working-when-a-user-opens-on-another-browser/396072).
- **allauth, adding another account's address (ACCT-9).** Docs say `ACCOUNT_PREVENT_ENUMERATION` "Controls whether or not information is revealed about whether or not a user account exists" and, since 0.52.0, signup sends an `account_already_exists` email under mandatory verification ([release notes 2022](https://docs.allauth.org/en/latest/release-notes/2022.html)). FLS already overrides `account_already_exists_message.*`. I found no allauth source or issue showing the add-email page sending that template; verify in `allauth/account/` before assuming a hook exists. Wording-only change is safe: it does not alter the enumeration behaviour.
- **nh3 / bleach, double sanitising.** No issue or post addresses attributes lost on a second pass. Background only: [Adam Johnson on nh3](https://adamj.eu/tech/2023/12/13/django-sanitize-incoming-html-nh3/), [pydanny bleach to nh3](https://pydanny.com/posts/2023-06-converting-from-bleach-to-nh3) (nh3 removes disallowed tags and attributes rather than escaping). The cause here is local: second `nh3.clean` with the Markdown allowlist applied to component output.
- **Django honeypot / `format_value`.** No Django ticket or django-honeypot issue found. [django-honeypot](https://github.com/jamesturk/django-honeypot) renders its field from a template with a fixed value, not from the bound form. `Widget.format_value` is the documented hook for what a bound widget renders, so the idea's override is idiomatic.
- **Course "Continue" button restarting (LEARN-2).** No matching bug report. Open edX documents the dashboard button as "Resume Course" that opens the unit most recently completed ([support article](https://support.edx.org/hc/en-us/articles/360000396027-Return-to-where-you-were-working-in-a-course)); Moodle's third-party [Resume Button plugin](https://moodle.org/plugins/local_resume) goes to the last accessed activity and switches to "Start Again" (first activity) only when everything is complete. Both agree with the idea: "Continue" resumes, "Start again/Review" restarts.
