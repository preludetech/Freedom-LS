# Frontend QA: panel framework components

Browser checks for `1. spec.md` in this directory. Every test names where to go, what to do and what
you should see. Tests 1 to 4 are the golden path; tests 5 to 10 are the side effects and failure
branches this change can reach.

## §0 Setup

Port and server:

```
PORT=$(.claude/ds/scripts/find_available_port.sh)
uv run python manage.py runserver $PORT
```

Base URL: `http://127.0.0.1:$PORT`. Confirm the `debug-branch-badge` in the bottom-left corner names
`educator-interface-4-panel-framework-components` before testing anything.

Login: the staff account in `.claude/fls-dev/config.md` (admin email and password). Log in at
`/accounts/login/`, or through the header's login link.

Seed data needed (create whatever is missing with the `fls-dev:qa-data-helper` agent):

- An organisation the staff user can manage as an educator, with at least two cohorts. One cohort has
  three or more learners and a course registration, so its tab set and tables have rows.
- One cohort named exactly `<b>Escaped</b> Cohort` (with the angle brackets typed in).
- A learner account that is **not** staff, with a known password, for the access-control test.

Viewports used below: desktop 1920x1080, mobile 375x812, tablet 768x1024.

---

## Test 1: the reference page shows every component

1. Logged in as staff, at desktop, go to `/panel-framework/components/`.
2. Expect a 200 page in the site's normal chrome (header bar, footer), with one section heading per
   component: page header, stat tile and stat row, status badge, avatar chip, attention list, progress
   bar, card, definition list, toolbar, empty state, skeleton.
3. Under each heading, each example has a one-line "Use when" note. Spot-check in DevTools that
   example wrappers carry ids such as `stat-tile-boxed-delta-down`, `status-badge-success`,
   `card-landmark`, `filter-toggle-pressed`, `skeleton-row`.
4. Status badges: the five tones read as distinct colours and their text is clearly legible on the
   tint (dark text on a pale tint, no pale-on-pale).
5. Stat tiles: the value sits above the label; a delta with `up` shows an upward trend icon and one
   with `down` a downward one. Confirm the icon has no tooltip or announced name (it is decorative).
6. Avatar chips: initials appear in a coloured circle with the full name beside it. Different example
   ids give different circle colours. No circle is green, yellow or red (nothing reads as a status).
7. Progress bars: a filled track with the percentage as text beside it.
8. Cards: bordered, rounded, no drop shadow. The card with actions has a bordered footer with buttons
   at the right. The card without a title has no header strip.
9. Toolbar: search field, filter toggles, actions on one row; the pressed toggle shows a check icon
   and a filled background; the applied-filter row shows chips with an "x" button and a "Clear all"
   link.
10. Empty state: centred icon, one sentence, one button. Skeletons: pulsing grey blocks in text, tile
    and row shapes.
11. Console: no errors.

## Test 2: educator list pages have a page header with the actions in it

1. Go to `/educator/` and pick the organisation. Open **Cohorts**.
2. Expect a single `h1` reading "Cohorts" at the top of the content area, under the breadcrumbs, with
   the "Create Cohort" button on the same row at the right.
3. The cohort table sits in a card: white surface, border, rounded corners, no shadow.
4. Repeat for **Learners** and **Courses**: an `h1` with that word. Any create button sits in the
   header row.
5. Open **Dashboard**: an `h1` reading "Dashboard" now appears above its panel.

## Test 3: the list still refreshes after a create

1. On **Cohorts**, click "Create Cohort", fill the form and submit.
2. Expect the modal to close and the new cohort to appear in the table without a full page reload
   (the URL does not change and the page does not flash).
3. The header and its "Create Cohort" button are still present after the refresh.
4. Console: no errors.

## Test 4: the instance page: header, tabs, details card, in-place title update

1. Open a cohort from the Cohorts table.
2. Expect the cohort name as the `h1` with the Edit and Delete actions on the same row at the right,
   and a tab bar beneath. The active tab has a primary-coloured underline and darker text; other tabs
   are muted.
3. The Details panel is a card with a "Details" heading strip. The fields render as small uppercase
   labels with values below them in a grid (not a two-column table). Any boolean field shows a
   check or cross icon.
4. Click **Edit**, change the cohort's name, save.
5. Expect the `h1` to change to the new name without a page reload, and the details card to show the
   new name.
6. Switch tabs. The tab's content swaps and the URL updates; go Back and the previous tab returns.
7. Click **Delete**, cancel the confirmation. Nothing changes.

## Test 5: escaping in the page header

1. Open the cohort named `<b>Escaped</b> Cohort`.
2. Expect the `h1` to show the literal text `<b>Escaped</b> Cohort`, not bold "Escaped".
3. Rename it through Edit to `<script>alert(1)</script>`. Expect the literal text in the title and
   no dialog.
4. Rename it back.

## Test 6: reference page access control

1. Log out. Go to `/panel-framework/components/`.
2. Expect a redirect to the admin login page (`/admin/login/?next=/panel-framework/components/`),
   not a 403 or 404.
3. Log in as the non-staff learner. Go to `/panel-framework/components/` again.
4. Expect the admin login page again (a non-staff user is refused the same way as an anonymous one).
5. Log back in as staff before continuing.

## Test 7: mobile layout (375x812)

1. Open a cohort page. Expect the Edit and Delete buttons on their own row under the title, and no
   horizontal scrollbar on the page.
2. The tab bar scrolls sideways if it does not fit; tab labels do not wrap onto two lines.
3. The details card shows one label and value per row, stacked.
4. Go to `/panel-framework/components/`. In the attention list example, tap the row's reason text
   (not the name). Expect the page to navigate to that row's target (the URL gains the row's fragment).
   The "Message" action is not shown on mobile; a right-pointing arrow trails each row.
5. In the page header example with a stats row, the stats sit under the title and the actions are on
   a row below.
6. Scroll the whole reference page: no element pushes the page wider than the screen.

## Test 8: tablet layout (768x1024)

1. Cohorts list, cohort page and the reference page all render with the header actions beside the
   title, tabs on one line, and the details grid in columns. No overflow.

## Test 9: learner-facing chips still look right

1. As staff, go to the learner home `/` and to a course page that shows a status chip (for example a
   "Complete" or "In progress" label on a course card or in the course player).
2. Expect status chips with pale tints and dark legible text. Primary and secondary chips are
   unchanged (brand colour on a light tint).

## Test 10: forced colours and keyboard

1. In Chrome DevTools, open the Rendering panel and set **Emulate CSS media feature forced-colors**
   to `active`. Reload `/panel-framework/components/`.
2. Expect: every status badge has a visible outline; the progress bar has a visible border and a
   distinguishable fill; the pressed filter toggle is filled with the highlight colour and the
   unpressed ones have a border. Turn the emulation off.
3. Keyboard only: Tab through the toolbar example. The search field, each filter toggle, each
   applied-filter "x" button and "Clear all" receive focus in order with a visible ring. In the
   DevTools accessibility pane, an applied-filter "x" button is named "Remove filter: <label>" and an
   attention row's "Message" link is named "Message <person's name>".
