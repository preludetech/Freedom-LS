# Research: codebase (educator-interface-course-content-preview)

Question: what in the existing codebase does this work touch, reuse or conflict with?
Idea (`idea.md`): educators see a course details page in the educator interface with the course's details and its table of contents (TOC); each TOC entry has a preview button that opens a modal showing that content rendered.
All paths are relative to the repo root. Line numbers are as of this worktree.

## 1. Headline findings

1. **A Courses section and a course instance page already exist.** The new work extends it; it does not create it. `CourseConfig` (`freedom_ls/educator_interface/views.py:1907`) is in the "Teaching" nav group (`views.py:2136-2142`) with `CourseInstanceView` -> `CoursePanelStack` (`views.py:1895-1904`). That stack has three children: `details` (`CourseDetailsPanel`, fields only `title` and `dashboard_category`), `cohorts` (`CourseCohortRegistrationsPanel`), `learners` (`CourseLearnerRegistrationsPanel`). It has no tabs, no TOC and no content.
2. **No educator-side TOC or content renderer exists.** The only TOC builder is learner-shaped: `learner_interface/utils.py:get_course_index` (line 479). It takes a `user`, a `can_access_content` flag from the access backend, a `CourseProgress`, deadlines and statuses (BLOCKED/READY/...). Item URLs are learner-player URLs (`learner_interface:view_course_item`, 1-based index among viewable items).
3. **The learner-side item views write progress on GET.** They cannot be reused as the modal body. Topic/form markdown rendering and form-question templates can be reused.
4. **There is a row-level "open in modal" pattern** (`PanelAction` with `renders_in_footer = False` + `<c-modal-trigger>` + a modal fragment template). `ViewConversationAction` (`views.py:1159`) is a read-only precedent.
5. **Import-linter / app graph:** `educator_interface` has no runtime edge to `form_engine`, `content_base`, `markdown_rendering` or `learner_interface` (`docs/app_structure.md:319`). Rendering a Form preview or using `render_markdown` directly would add a new cross-app edge (see section 7).
6. `docs/product/educator-interface.md` currently states "Courses have no quick view" (line 62) and "The Courses section is read-only" (line 111); both need revisiting when this ships.

## 2. Educator interface structure

### Files (`freedom_ls/educator_interface/`)
`views.py` (all configs, tables, panels, actions; ~2800 lines), `urls.py`, `quick_views.py`, `actions.py`, `filters.py`, `forms.py`, `paths.py` (`interface_path(organisation, "courses/<pk>")`), `events.py`, `templates/educator_interface/{panels,modal,partials,quick_views,data-table-cells}`, `templatetags/educator_tags.py`. `admin.py`, `staff.py`, `reporting.py`, `messaging.py`, `learner_import.py` are unrelated.

### URL pattern
`urls.py`: `app_name = "educator_interface"`. One catch-all `re_path(r"^organisations/(?P<organisation_slug>[-\w]+)/(?P<path_string>.*)$", views.interface, name="interface")`, preceded by a few explicit routes (report download, import, oversight older). All panel pages, tabs, actions and quick views are resolved by the panel framework from `path_string`:
- list: `courses`; instance: `courses/<uuid>`
- tab: `.../__tabs/<name>`; stack child: `.../__panels/<name>`
- action: `.../__actions/<action_name>` (GET renders the modal fragment, POST/DELETE submits) (`panel_framework/views.py:_handle_action`, line 995; `PanelAction.get_action_url` in `panel_framework/actions.py:135`)
- quick view: `<section>/<pk>/__quick-view`
A non-panel route needs its own `re_path` before the catch-all (as the import and report-download routes do) and must call `_attach_organisation`/`scope_request` itself (`views.py:2179, 2247`).

### Existing Course page and list (what to extend)
- `CourseDataTable` (`views.py:1698`): rows scoped by `courses_visible_to(user, organisation)`; columns Title (link `courses/{pk}`), Visibility, Interest, Active Learners, Active Cohorts, Cohorts. No quick view (`CourseConfig` has no `quick_view`).
- `CourseDetailsPanel(InstanceDetailsPanel)` (`views.py:1821`): `model = Course`, `fields = ["title", "dashboard_category"]`. Extending `fields` is the cheap way to "show the course details": `Course` has `subtitle`, `description`, `visibility`, `difficulty`, `estimated_duration`, `time_limit_days`, `learning_outcomes` (ArrayField), `organisations` (M2M), `audience`, price fields, `categories`, `icon`, `table_of_contents_in_development`, `content` (markdown) (`content_engine/models/courses.py:149-270`). `lookup_field`/`display_for_field` handle model fields; M2M/array/duration display may need method/property accessors or a custom template.
- `CourseConfig` (`views.py:1907`): `url_name="courses"`, `icon="course"`, `table_key="courses"`, `instance_view=CourseInstanceView`; `authorise_instance` raises `OrganisationScopeDenied` unless `courses_visible_to(...).filter(pk=...)` matches. No `view_capability`, so the Courses section shows to anyone who can enter the organisation.
- `CourseInstanceView` has no `get_actions`, status badge, subtitle or stats overrides (compare `CohortInstanceView`, `views.py:1573`).
- Tests: `educator_interface/tests/test_views.py` (155 mentions of course), `test_course_visibility_and_interest.py` (imports `CourseDataTable`), `tests/invariants/test_permission_matrix.py`, `test_organisation_isolation.py`, `tests/interface_walk.py` (walks every section's instance, tab, panel and action path; a new action is picked up automatically via `get_actions`), `tests/playwright/test_section_smoke.py`.

### Permissions / who sees which courses
- Entry: `organisations_accessible_to(user)` (`learner_management/queries.py:404`): an organisation-level role granting `freedom_ls_organisations.view_organisation`, or a role on any cohort in the organisation granting `view_cohort`; superusers see all. `_resolve_organisation` (`views.py:2167`) 404s otherwise. So org admin, site admin, cohort admin and cohort viewer can all reach the interface.
- Course visibility: `courses_visible_to(user, organisation)` (`learner_management/queries.py:493`): every PUBLISHED course open to the organisation (`open_to_organisation_expression`: non-organisation courses, public ones, and the organisation's own), plus any course (any visibility, including hidden / coming soon) that a visible cohort or learner holds a registration for. A course belonging only to other organisations with no local registration is excluded, superusers included. It is not role-differentiated: every educator who reaches the organisation gets the same course set, narrowed by the cohorts/learners they can see only for the registration-based part.
- `OrganisationSectionConfig.has_capability` delegates to `can(user, capability, scope)` where scope is the `Organisation` (`views.py:254-288`). `PanelAction.capability` / `Panel.capability` are asked against `ctx.scope_object()`. A read-only preview action can have `capability = None` (allowed whenever the page is reachable) and rely on `CourseConfig.authorise_instance`, or declare a capability. No course-content capability exists today (grep for `view_course` finds none in role code).
- The product doc's rule: out-of-scope pages 404 identically to missing ones (`docs/product/educator-interface.md` Access control). A preview of a child (Topic/Form) must be resolved *through the already-authorised course* (a child of its collection items) and not by a bare pk, or it would expose content of an unauthorised course.
- Hidden / coming-soon / `table_of_contents_in_development` courses: educators can already open the course page for hidden courses via a registration. The learner details page hides the "Course content" section when `table_of_contents_in_development` is true (`learner_interface/templates/learner_interface/course_detail.html:284`). Whether the educator TOC honours that flag is an open question for the spec.

### Modals, sheets, quick views
- Shared modal host: `panel_framework/templates/panel_framework/partials/modal_host.html`: native `<dialog id="app-modal" x-data="appModal">`, body `#app-modal-body`. CSS: width `min(92vw, 32rem)`, max-height `min(90dvh, 100%)`, scrolls vertically, clips horizontal overflow; below `sm` it is a bottom sheet. Behaviour in `panel_framework/static/panel_framework/js/alpine-components.js` (`appModal`; discard-prompt for dirty forms, `requestClose`). **The default width (32rem) is narrow for rendered course content (tables, code blocks, images, flashcards); no existing fragment widens it.** `panel_framework/modal/read_only.html` wraps content in `max-w-prose`.
- Trigger: `<c-modal-trigger url label variant size aria_label>` (`freedom_ls/base/templates/cotton/modal-trigger.html`): `hx-get` into `#app-modal-body`, `hx-disabled-elt`. Row triggers live in cell templates inside `<c-data-table-actions>` (e.g. `educator_interface/data-table-cells/cohort_member_actions.html`). Every trigger is `size="small"`; test `test_every_framework_action_trigger_is_small` enforces it.
- Fragment shape: starts with `<c-modal-header focus_title="true">Title</c-modal-header>` (`panel_framework/templates/cotton/modal-header.html`; sticky header with close button), body, and for dialogs with actions ends in `<c-modal-footer>`. Read-only base: `panel_framework/templates/panel_framework/modal/read_only.html` (blocks `title`, `content`).
- Closest precedent: `ViewConversationAction` (`views.py:1159`): `PanelAction`, `renders_in_footer = False`, `template_name = "educator_interface/modal/conversation_oversight.html"`, `get_context_data` reads a query parameter (`?conversation=<pk>`), authorises it via a scoped queryset with `get_object_or_404`, raises 404 on non-HTMX GET (`HX-Request` header), and `handle_submit` raises 404. Row-scoped actions expose their URL to cell templates as `row_action_urls[action_name]` (`panel_framework/panels.py:155-179`), and tests walk them via `interface_walk.py`.
- `PanelAction.trigger_template_name` for non-form actions defaults to `partials/action_button.html`; `FormPanelAction`/`DeleteAction` use `partials/modal_trigger.html`. A pure read action built on `PanelAction` with a row trigger in a cell template (as `ViewConversationAction`, `DeactivateCohortRegistrationAction`) is the shape that fits.
- Quick view (`educator_interface/quick_views.py`, `panel_framework/quick_view.py`): a side drawer `#quick-view` opened with `show()` (non-modal, list stays tappable; `test_the_quick_view_is_never_modal`). Only learners and cohorts have one. The idea asks for a modal, so the quick-view drawer is not the fit; docs describing "preview" on Learners/Cohorts use the drawer.
- Panel-framework invariant tests that any new template must pass: `panel_framework/tests/invariants/test_templates.py` (control links are components, triggers small, dialog ends in `<c-modal-footer>`, no raw colours, modal host clips overflow). A read-only content modal with no actions has only the header (the read-only base has no footer).
- Dialog a11y per docs: dialogs take names from headings, focus moves in, Escape closes, focus returns.

## 3. Content models and TOC

`freedom_ls/content_engine/models/` is a package (`courses.py`, `topics.py`, `articles.py`, `files.py`); `content_base/models.py` has the abstract bases. (The task text says `models.py`; it is a package.)

- `Course(MarkdownContent, TitledContent)` (`courses.py:149`). `CoursePart(TitledContent)` (510): a chapter, no markdown content of its own. `Topic(TitledContent, MarkdownContent)` (`topics.py:8`). `Activity` (`topics.py:26`) is not used by FLS courses. `Form(TitledContent, MarkdownContent)` is in `form_engine/models.py:52`.
- `ContentCollectionItem` (`courses.py:557`): the placement through-model: generic FK `collection` (Course or CoursePart), generic FK `child` (Topic, Form or CoursePart), `order`, due keys. Use "collection item" for the row and "child" for the resolved object (glossary `claude_plugins/fls-dev/skills/domain-glossary/SKILL.md`). "Course item" is already used by `view_course_item`; the glossary says to reuse only deliberately. The glossary has no term "table of contents"; the codebase says "course index" (`get_course_index`), "outline" (`<nav aria-label="Course outline">`), "table of contents" in `Course.table_of_contents_in_development`, and "ToC"/"Course content" on the learner details page.
- Accessors: `Course.collection_items()` (line 444, memoised per instance, prefetches generic `child`), `collection_items_flat()` (455, parts' rows inlined after the part's own row), `viewable_collection_items()` (467, no `CoursePart`), `children()`, `children_flat()`, `viewable_items()`; `CoursePart.collection_items()` / `children()`. Parts are one level deep (nested parts are skipped defensively in `get_course_index`). Query count: one items query plus one per child content type.
- Type discrimination: `child.content_type` (`"TOPIC"`, `"FORM"`, `"COURSE_PART"`; `SchemaContentTypes` in `content_base/schema.py`) or `isinstance`.
- Form tree: `Form` -> `FormPage` (`pages`, ordered; `condition_option`) -> `FormContent` (markdown, `text_items`) and `FormQuestion` (`questions`, `type`, `required`, `options`->`QuestionOption`) (`form_engine/models.py:91-275`). `Form.strategy` (`FormStrategy`: quiz / survey / etc., `form_engine/enums.py`), `quiz_pass_percentage`, `submit_on_exit`. `FormPage.children()` merges text items and questions by `order`.

### How the learner TOC is built (reference only, not reusable as-is)
- `learner_interface/utils.py`: `get_course_index(user, course, current_index=None, *, can_access_content, course_progress, course_deadlines, deadline_policy, now, access_ended_outline)` (479) -> list of dicts (`title`, `type`, `status`, `url`, `is_current`, `children` for parts, `contains_current`, deadline keys). It runs progress queries (`_fetch_player_progress_maps`) when the user may access content; with `can_access_content=False` every row is BLOCKED with `url=None`. Statuses and `url`s are learner semantics.
- Template: `learner_interface/templates/learner_interface/partials/course_minimal_toc.html` (partialdef `course-children`, used by `course_detail.html:290` with `hide_deadlines=True`). Renders `<nav aria-label="Course outline">`, numbering (`1.`, `1.1`), type icon (`topic`, `form`, `folder`), Alpine `coursePart` expand/collapse (`course_part_storage_key_tag`, `localStorage` keys), items as `<a href="{{ child.url }}">` or muted spans. It depends on `learner_interface` Alpine components and storage-key template tags, and on the `url`/`status` dict keys, so it is not directly reusable inside the educator interface. Its structure (numbering, icons, part grouping) is the visual reference for an educator TOC.
- Index numbering: the player's `index` is the 1-based position among `viewable_collection_items()` (parts consume no index). Both the learner TOC and the educator TOC can derive the same ordering from `Course.collection_items()` / `viewable_collection_items()`.

## 4. Rendering content

- Markdown: `MarkdownContent.rendered_content()` (`content_base/models.py:90`) -> `freedom_ls.markdown_rendering.markdown_utils.render_markdown(self.content, None, context={"content_instance": self})`. Pipeline per skill `claude_plugins/fls-dev/skills/markdown-content/SKILL.md` and `claude_plugins/fls-dev/resources/markdown_content.md`: markdown -> nh3 sanitise (allowlist `MARKDOWN_ALLOWED_TAGS` in `config/settings_base.py`) -> cotton components -> safe HTML; H1 -> H2. Called with **no request**, so embedded components must not depend on request context. In templates: `{{ topic.rendered_content }}` (method call, marked safe) wrapped in `<c-markdown-container>` (`freedom_ls/base/templates/cotton/markdown-container.html`; `width="full"` and class attrs used in learner templates). `{% markdown value %}` tag in `content_engine/templatetags/content_tags.py:140`.
- Learner topic template: `learner_interface/templates/learner_interface/course_topic.html` extends `learner_interface/_course_base.html` (player chrome, TOC panel, `coursePlayer` Alpine). Its body is just `<c-markdown-container>{{ topic.rendered_content }}</c-markdown-container>`; the rest is player chrome and a "mark complete" form. So the topic body is trivially reproduced in a modal with `{{ topic.rendered_content }}`; the learner template itself is not reusable.
- Embedded components in content: `content_engine/templates/cotton/` (`admonition`, `flashcard`, `accordion`, `youtube`, `picture`, `pdf-embed`, `file-download`, `table`, `code-block`, `content-link`, `article-link`, `grid`, `card`, ...). Caveats:
  - `content-link.html` links to `content_obj.preview_url`, and `Topic.preview_url()` (`topics.py:22`) reverses `content_engine:topic_detail`. `config/urls.py:67` has the content-preview URLs commented out and `content_engine` has no `urls.py`, so that link is likely a pre-existing broken/unverified path inside any rendered content that uses it (not verified at runtime). It shows a TODO "non-preview link" in the template. Not a blocker but a modal preview will surface it.
  - `picture`/`file-download`/`pdf-embed` resolve files through `content_tags.get_file_by_path` and file storage; they are request-free and can render in a modal. Images in a 32rem dialog will be constrained; cotton components like `flashcard`, `accordion`, `table` rely on Alpine/CSS available globally in the base template.
  - Alpine components used by content (accordion/flashcard) are registered in the base/learner Alpine bundles; the educator shell loads panel_framework's and its own Alpine bundle. Whether the educator shell (`educator_interface/interface.html`, `_shell.html`) loads the `base`-level Alpine components the cotton markdown components need was not verified and is a risk for the spec to check (components are in `content_engine/templates/cotton/` and inline `x-data`; the learner course detail page loads `learner_interface/js/alpine-components.js` via `extra_alpine_components`).
- Forms / quizzes:
  - Models render through `form_engine/templates/form_engine/question.html` (a `<fieldset>` per question, inputs under `form_engine/templates/form_engine/inputs/*.html`) and `form_engine/partials/page_children.html` (iterates `page_children`: `FORM_QUESTION` -> `question.html`, `FORM_CONTENT` -> `<c-markdown-container>{{ child.rendered_content }}`). The partial's comment documents the context it reads: `page_children`, `question_positions`, `existing_answers`, `rejected_answers`, `read_only`.
  - **A `read_only` mode exists:** `form_engine/page_flow.py:page_context(..., read_only=False)` puts `read_only` in context, and `inputs/multiple_choice.html:23` renders `disabled` when set. The only caller using it today is `course_applications/views.py:744-783` (a completed application shown read-only; template `course_applications/templates/course_applications/form_page.html`). I did not verify that every input template under `form_engine/inputs/` honours `read_only` (multiple_choice does; check checkboxes, text_input, long_text, dropdown, file_upload).
  - Building the page data without a `FormProgress`: `page_context` needs a `FormProgress` and a `SittingPath`. `form_engine/conditions.py:full_path(form)` (line 247) builds a `SittingPath` over every page and child with no progress (used for old completed sittings), and `compute_path(form, {})` builds the unanswered path (conditional pages/questions gated on an option are hidden). `SittingPath.children_of(page)` and `.question_positions()` supply `page_children` and `question_positions` without touching progress. `page_context` also calls `form_progress.existing_answers_dict` and `build_page_links(form_progress, ...)`, so a preview would build its own small context (`page_children`, `question_positions`, `existing_answers={}`, `rejected_answers={}`, `read_only=True`) rather than call `page_context`. `load_form_tree(form)` prefetches the tree (`FORM_TREE_LOOKUPS`).
  - Form start screen content (`learner_interface/course_form.html`): `form.rendered_content`, question count (`count_form_questions`) and page count (`form.pages.count()`), previous attempts. Learner-specific parts (buttons, previous attempts) are not wanted in a preview.
  - Quiz correctness data: `QuestionOption.correct` (nullable bool). Rendering the form with the `question.html` templates does not reveal `correct`. Whether an educator preview should show correct answers is a spec decision; the learner templates do not.
  - Question types handled in `question.html`: `multiple_choice`, `checkboxes`, `short_text`, `long_text`, `number`, `date`, `time`, `email`, `url`, `phone`, `dropdown`, `file_upload`; anything else renders a red "UNHANDLED FORM TYPE" callout. `file_upload.html` uses `upload_limits` and may include JS-driven HTMX endpoints (`form_engine/urls.py`: `partial_question_file_upload`, `partial_question_file_remove`) that need a `FormProgress`; a read-only preview must not render a live uploader.
  - Alpine: the learner runner wraps pages in `examRunnerForm` / `examRunner` (`learner_interface/templates/learner_interface/course_form_page.html`, `alpine-components.js`). `question.html` comments that "outside the runner nothing reveals" the checkbox-required message (`data-checkbox-required-message`), so `question.html` is already designed to render outside the runner (it is also used under the course application shell).
- CoursePart in the TOC: a heading row with no content; has `title`, `subtitle`, `category`; no `content`. A "preview" for a part has nothing to render beyond title/children, so the preview button applies to Topic and Form children only (spec decision).

## 5. Learner-side side effects on view (must be avoided in a preview)

All in `freedom_ls/learner_interface/views.py`:
- `view_course_item` (1455), `@login_required`: calls `_ensure_player_course_progress` (**creates a `CourseProgress` row** via `ensure_course_progress_record` when missing, line 1488 / 1609); writes `course_progress.last_accessed_item`, `last_accessed_time` and `started_at` and calls `record_course_started(...)` (a webhook/analytics event) and `course_progress.save(...)` (1564-1577). Also applies `_course_access_decision`, sequential-unlock redirects (`_blocked_item_redirect`) and closed-item notices (`_render_closed_notice`).
- `view_topic` (1706): `TopicProgress.objects.get_or_create(...)` and `.save()` on every view; POST `mark_complete` sets `complete_time` and redirects.
- `view_form` (1759): `finalise_stale_incomplete(...)` (can finalise and score an attempt).
- `form_start` (1829): GET **creates** a `FormProgress` via `get_or_create_incomplete`. `form_fill_page` (1955): POST saves answers and may complete; GET calls `record_page_reached`. `course_form_complete`, `course_finish`, `form_submit_and_exit` are writing views.
- Consequence: an educator pointed at `learner_interface:view_course_item` would be registered/tracked (or 403/redirected for lack of registration). The educator preview must build its own read-only view. The learner `course_detail` view (`learner_interface/views.py:947`) is read-only and public but applies learner access/CTA logic and renders `course_detail.html`, which is a full page extending `_base.html` (hero, sign-up panel, acquisition CTA, express-interest control, JSON-LD); it is not embeddable in the educator shell.
- Render-time side effects: `rendered_content()` is a pure function of the stored markdown (no DB writes). `question.html` templates are pure given context.

## 7. App dependency rules (import-linter)

- `docs/app_structure.md` is the authoritative graph (generated by `/app_map`; do not hand-edit). `educator_interface` runtime deps: accounts, audit_log, base, comms, content_engine, learner_management, learner_progress, organisations, panel_framework, reports, role_based_permissions, site_aware_models; test-only: course_interest (line 319; `test_organisation/declared_edges.toml` declares only `base -> learner_management`).
- `educator_interface` does **not** depend on: `form_engine`, `content_base`, `markdown_rendering`, `learner_interface`, `course_access`, `deadlines`. Importing `learner_interface` from `educator_interface` (e.g. `get_course_index`, `learner_interface.utils`) would be a brand-new edge in the wrong direction (educator -> learner), and `learner_interface` is a heavy dependency (course_access, deadlines, webhooks). The graph says to call out and get approval for any new cross-app edge before code is written (`docs/app_structure.md` line 5). Regenerate with `/app_map` if the edge is added.
- Reaching content stays inside allowed edges when it uses only `content_engine` models: `Course.collection_items()`, `child.rendered_content()` (the method lives in `content_base` but is called on a `content_engine` instance; no import needed), `isinstance(child, Topic/CoursePart)` from `content_engine.models`. Form children: `isinstance(child, Form)` needs `form_engine.models`; `content_type == "FORM"` string comparison avoids the import. `content_engine` itself depends on `form_engine` (graph line 311) and `learner_progress` depends on `form_engine`, so `form_engine` is transitively present but not a declared edge for `educator_interface`.
- Template includes across apps are not import edges but are coupling: `{% include "form_engine/partials/page_children.html" %}` and `form_engine/question.html` are `form_engine` templates (the same cross-app template use already occurs in `course_applications`); including them from an educator template adds a template-level (not Python) dependency.
- Import-linter contracts in `test_organisation/import_contracts.toml` (generated; `[[tool.importlinter.contracts]]` per app) are `forbidden` contracts on **test modules** only (`source_modules = ["freedom_ls.<app>.tests", ...factories]` may not import apps outside the app's runtime deps, with `ignore_imports` baselines). The educator contract (line 188) therefore constrains educator *tests*: tests for the preview may use `content_engine` factories but not `form_engine.factories` or `learner_interface` helpers without a new baseline entry. `lint-imports` is the command; runtime imports are policed by the generated graph/`/app_map` and review rather than this file.

- Content rendering: `child.rendered_content()` in `<c-markdown-container>`; forms via `SittingPath` (`full_path` / `compute_path(form, {})`), `form_engine/partials/page_children.html`, `form_engine/question.html` and `read_only=True`.
- Visual reference only: learner `course_minimal_toc.html` numbering/icons/part grouping; `course_detail.html` field set.

Conflicts / constraints:
- Learner player views write progress on GET and enforce access/unlock/closed gates; not usable. The learner TOC builder and partial are learner-state-coupled and `learner_interface`-coupled (new educator -> learner edge; heavy deps).
- `educator_interface` has no declared edge to `form_engine`/`markdown_rendering`/`content_base`; importing `form_engine` Python names (e.g. `Form`, `full_path`, `FormStrategy`) adds one and requires approval + `/app_map` regeneration; template-level includes of `form_engine` templates add template coupling; educator test imports of `form_engine.factories` would hit the educator import contract.
- Modal host is 32rem wide and a `<dialog>` that clips horizontal overflow; rich markdown (tables, code, images, quiz forms) may need a wider variant (no existing precedent for a wide `#app-modal`). The `appModal` discard-prompt logic is for dirty forms; a read-only quiz preview with disabled inputs should not trip it (unverified).
- The educator shell's Alpine/CSS bundles may not include everything content components expect (not verified).
- `CoursePanelStack` is a stack, not tabs; adding a TOC tab changes the page shape (`interface_walk.py`/`test_section_smoke.py` walk it automatically; update any tests asserting the stack's children).
- `CourseDetailsPanel` currently shows only `title` and `dashboard_category`; `docs/product/educator-interface.md` says the course page shows "the title and category, the cohorts registered... and any direct registrations", and "Courses have no quick view" / "read-only" statements need updating.
- Terminology: the glossary has no canonical "table of contents"/"preview" noun. Use `Course`, `CoursePart`, `Topic`, `Form`, `ContentCollectionItem` (collection item / child) and avoid new senses for bare "item". "Course item" is taken by the player route name. "Preview" is already used for the learner/cohort quick view (a drawer) and for the import preview step.
- Unverified runtime concerns: `content-link` `preview_url` reverse (broken URL name), `read_only` support across all input templates, educator-shell Alpine coverage for cotton markdown components, and `file_upload.html` behaviour with no `FormProgress`. Each should be checked by a spec/plan test rather than assumed.
