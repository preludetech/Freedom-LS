# Frontend QA: deadlines-8 review fixes

The branch reworks code behind per-placement due dates without changing any page on purpose:

- **Moved children.** When a content load moves a topic or form to another part, the course's
  placement due dates and the deadline override and extension rows on the old collection item
  now follow it from one shared step (`content_engine/moved_children.py`). Only rows in a course
  or part the load saved count as left behind. A row outside the load is never treated as a move,
  because it may be a deliberate second placement.
- **Resolver.** The content defaults are read in three queries and skip the course time limit.
  The dates a learner sees must not change.
- **Deadline override admin.** With no course (the add page) the inline no longer treats the
  content defaults as an empty map. Each row reads its own course instead.
- **Validation.** One shared "this child is named twice" check for top-level and nested
  `children:` lists. A multi-document file's last document is read wherever it is validated.
  `save_content_to_db` checks placements again when called without the command.

The aim of this run is to show nothing broke: learner deadlines, the override admin and the
author errors read as they did on `main`. The moved-children behaviour gets its own checks.

**Viewports.** Every changed path is Python, so diff scoping classes this branch `BACKEND_ONLY`:
desktop only. §4 runs in the terminal.

Substitute the literal port number from `.claude/ds/scripts/find_available_port.sh` wherever
this document writes `$PORT`. Shell variables do not survive between tool calls.

**Dates.** "Reg" is the date part of the learner's `CourseProgress.created_at` in the site
zone. The site zone is `Africa/Johannesburg`, and the browser runs in that zone with the en-US
locale, so an end-of-day instant prints as "Nov 19, 2026, 11:59 PM".

**Wording.** Learner pages say "Deadline" and "Missed deadline" only. "No due date",
"Placement", "Override" or "no_due_date" on a learner page is a bug.

## §3 A child moved to another part

This is the change's main new behaviour. Each step edits `demo_content/`. §5 restores it.

### 3.1 Set up a course that places both parts, and a deliberate second placement

1. Edit the placement course's `course.md`. Make its `children:` list:

   ```yaml
   children:
   - path: ../functionality_demo_course_parts/01. Getting Started/part.yaml
   - children:
     - due_days_after_registration: 3
       path: 01. key-ideas/content.md
     - no_due_date: true
       path: 03. knowledge-check/form.md
     path: ../functionality_demo_course_parts/02. Core Concepts/part.yaml
   - path: ../functionality_demo_course_parts/01. Getting Started/02. what-to-expect/content.md
     due_days_after_registration: 9
   ```

   The last entry places `What to Expect` a second time, directly on the course, with its own
   date.
2. `uv run python manage.py content_save demo_content DemoDev`. If the load refuses the direct
   second placement, record the message, delete that entry, re-run, and mark 3.4 PARTIAL.
3. As the fresh learner open the placement course. Expect `Getting Started` (Welcome, What to
   Expect at Reg + 7), `Core Concepts` as in 2.1 step 5, and a top-level `What to Expect` at
   "Deadline <Reg + 9>, 11:59 PM".
4. As the superuser, on the fresh learner's placement-course record page, add a third override
   row on the **top-level** `What to Expect`: days `15`, reason "QA second placement". The picker
   lists `What to Expect` twice. Use the entry that is not under `Getting Started`. If the labels
   do not tell them apart, note it and pick the later entry. Save and continue editing. Expect
   "Content default" "9 days after registration".
5. Note, from `/admin/` > Content engine > Content collection items (filter child type =
   course part), the placement course's `Core Concepts` row: its read-only child due dates inline
   lists `Key Ideas` (3 days) and `Knowledge Check` (No due date). The `Getting Started` row's
   inline is empty.

### 3.2 Move Key Ideas into Getting Started, loading only the parts course

1. `git mv "demo_content/functionality_demo_course_parts/02. Core Concepts/01. key-ideas" "demo_content/functionality_demo_course_parts/01. Getting Started/03. key-ideas"`.

   Expect "✓ Successfully saved all content". If the subdirectory load fails for a reason

3. Content admin, as in 3.1 step 5: the placement course's `Getting Started` row now lists

   date followed the child.
4. The fresh learner's placement-course record page: the 10-day `Key Ideas` override is now on the
   `Key Ideas` under `Getting Started`. Its "Content default" reads "3 days after registration",
   with no "Default has changed" note. The `Knowledge Check` row is unchanged.
5. As the fresh learner open the placement course and expand `Getting Started`: `Key Ideas` reads
   "Deadline <Reg + 10>, 11:59 PM". The load keeps the row a moved child left behind, so
   `Key Ideas` may also still be listed under `Core Concepts`. That listing is existing behaviour

6. The cohort registration page: the 20-day `Key Ideas` override from 2.2 now sits on the
   `Getting Started` `Key Ideas` and still reads "Content default" "14 days after registration
   at 17:00".
7. The record page for `qa_deadline_extended@email.com` on the parts course: the `Key Ideas`
   effective deadline matches 1.4 step 1. `/admin/` > Deadlines > Deadline extensions lists that
   learner's two `Key Ideas` extensions against the `Getting Started` item.

## §4 What an author sees when a `children:` list names a child twice

Terminal only. Work on a scratch copy outside `demo_content/`:
`cp -r demo_content/functionality_demo_course_parts .sdd-work/qa_review_fixes_bad`. Edit the
copied `course.md` as each test says, then run both commands. Each must give the same verdict.

- `uv run python manage.py content_validate .sdd-work/qa_review_fixes_bad`
- `uv run --no-project --with pydantic --with pyyaml --with python-frontmatter --with babel python claude_plugins/fls-content/validate/validate.py .sdd-work/qa_review_fixes_bad`

The copy keeps the demo uuids, so never load it with `content_save`.

### 4.1 Top-level, named twice

```yaml
children:
  - path: 01. Getting Started/part.yaml
  - path: 02. Core Concepts/part.yaml
  - path: 01. Getting Started/part.yaml
```

Expect both to fail with "Invalid children list", naming `children[2]` and "this child is named
twice" with "Name each child once.". `children[0]` is not named.

### 4.2 Nested, named three times

```yaml
children:
  - path: 01. Getting Started/part.yaml
    children:
      - path: 01. welcome/content.md
        due_days_after_registration: 2
      - path: 01. welcome/content.md
      - path: 01. welcome/content.md
  - path: 02. Core Concepts/part.yaml
  - path: 03. Wrapping Up/part.yaml
```

Expect both to fail naming `children[0].children[1]` and `children[0].children[2]`, each "this
child is named twice". Not `children[0].children[0]`.

### 4.3 The earlier placement errors still read the same

Replace the nested list with a single entry whose path is `99. missing/content.md`. Expect
both to fail naming `children[0].children[0]`, the given path and the part's real children
(`01. welcome/content.md`, `02. what-to-expect/content.md`).

### 4.4 A valid file passes

```yaml
children:
  - path: 01. Getting Started/part.yaml
    children:
      - path: 01. welcome/content.md
        no_due_date: true
  - path: 02. Core Concepts/part.yaml
  - path: 03. Wrapping Up/part.yaml
```

Expect both to exit zero. Then delete `.sdd-work/qa_review_fixes_bad` with
`claude_plugins/sdd/scripts/delete_sdd_work_files.sh`, or ask the data helper. Never run a raw
recursive force-delete.

### 4.5 The demo content still validates

`uv run python manage.py content_validate demo_content` and the bundled validator on
`demo_content` both exit zero.
