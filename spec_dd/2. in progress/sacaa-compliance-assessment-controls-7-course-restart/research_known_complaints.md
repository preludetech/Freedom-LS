# Research: known complaints about course reset, recompletion and re-enrolment

Topic `known_complaints`. Each complaint is paired with the design choice in our decided model (see `answers.md`) that avoids it. Platform terms are the platforms' own. Ours: one `LearnerCourseRegistration` is one run; a restart supersedes it and mints a new linked registration; a single `registration.restarted` webhook.

Evidence quality: Moodle, Docebo, Canvas, Totara and edX are backed by sources found. Cornerstone, duplicate-webhook complaints and enrolment-id-change integration complaints were searched for and NOT found; those rows are marked as inferred from the mechanism, not from a user report.

## Complaints and what avoids them

| # | Complaint | Platform and source | Design choice that avoids it |
|---|---|---|---|
| 1 | Reset is destructive and irreversible, and wipes records that must be kept. Docs say "back up first". | Moodle core Reset course ([docs](https://docs.moodle.org/en/Reset_course)); Canvas Reset Course Content, official guidance says all content and student data is gone ([Ohio help](https://help.ohio.edu/TDClient/30/Portal/KB/Article/976/Resetting-a-course-in-Canvas)); TalentLMS says course reset cannot be undone ([help](https://help.talentlms.com/hc/en-us/articles/9652249254812-How-to-reset-a-user-s-progress-in-a-specific-course)). Moodle's own proposal notes many organisations must keep historic records ([Course Reset Proposal](https://docs.moodle.org/dev/Course_Reset_Proposal)). | Archive, never delete. The earlier registration and its `CourseProgress`, `TopicProgress`, `CourseFormAttempt`, `FormProgress` and `QuestionAnswer` rows are untouched and read-only. Nothing is zeroed in place. |
| 2 | Archiving covers only some data; other activity data is not archived or cleared. Requests for archiving assignments (#238), quiz questions, scores and answers (#198), issued badges (#45). | Moodle recompletion issues ([GitHub issues](https://github.com/danmarsden/moodle-local_recompletion/issues)); plugin page says other activities "may require manual intervention" ([plugin](https://moodle.org/plugins/local_recompletion)). | Archive-by-reference, not archive-by-copy. We keep the original rows and start a new registration, so every table (present and future) is retained with no per-activity archive code. Cost: every reader must be run-aware (see 9). |
| 3 | Old certificate or completion indicators persist into the new run, so the learner cannot get a fresh one (certificate activity data not cleared; completion ticks stay in navigation). | Moodle recompletion plugin page comments ([plugin](https://moodle.org/plugins/local_recompletion)). | The new run is a new registration with a fresh `CourseProgress`. Nothing carries over, so nothing needs clearing. Certificates are out of scope (no model), but any future certificate hangs off a run. |
| 4 | Only the first completion is tracked. A retake does not change the completion date, so certificates and reports show the old date. Resetting clears the original completion data. Still open in Oct 2022. | Docebo: [course not showing last completion date](https://community.docebo.com/product-q-a-7/course-not-showing-last-completion-date-1969) (workaround of editing the enrolment date is called a hack). | Each run has its own completion and completion date. A completed earlier run keeps its completion, date and scores, so "was this learner certified on this date" stays answerable, and `course.completed` fires once per run. |
| 5 | Old grades and completions mix into current reports; or, the opposite, history becomes invisible after reset. | Docebo thread above; Totara stores only a thin history row (id, courseid, userid, timecompleted, grade) and exposes it through separate "previous completions" reports ([resetting completions](https://totara.help/docs/resetting-completions)); Moodle 5.0 and 5.1 users report archive completions not visible and the "Archive Course Completions" custom report broken after upgrade, so compliance cannot be shown ([plugin page](https://moodle.org/plugins/local_recompletion)). | Readers skip superseded registrations by default (current run only). Reports and the progress API show earlier runs only with an explicit run label. Because history is the real rows, not a reduced history table, an earlier run keeps full detail and reports can be added without a data migration. Spec should name which reports show earlier runs and how they are labelled. |
| 6 | Accidental reset with no undo or confirmation. | Canvas: reset changes the course id and recovery is "no guarantee", only an admin may get it back ([Canvas blog](https://community.canvaslms.com/t5/Canvas-LMS-Blog/What-quot-Reset-Course-Content-quot-Really-Does-and-How-to-Undo/bc-p/274721), [university desk](https://support.msjc.edu/support/solutions/articles/20000056902)). | A mistaken restart cannot be undone (decided), but nothing is lost: the earlier run is intact and readable. Mitigate with the shared confirm dialog, a required reason, and restricting the action to `CHANGE_LEARNER_REGISTRATION` holders on an active registration. Note the trade-off: no undo means a wrong restart is permanently a superseded run. The spec should say how staff correct a wrong restart (e.g. nothing, or a manual re-registration) rather than leave it implied. |
| 7 | No reason or audit trail for who reset what. | Not a quoted complaint; Moodle docs note course logs are not deleted by reset but reset itself carries no reason ([docs](https://docs.moodle.org/en/Reset_course)). Inferred. | Required reason, stored on the restart; one `record_learner_entry` audit entry with actor, reason and the closed run, in the same `transaction.atomic()` as the state change. |
| 8 | Reset also resets the attempt count (all-or-nothing), so "limited attempts" settings are bypassed or surprising. | Docebo ([thread](https://community.docebo.com/product-q-a-7/course-not-showing-last-completion-date-1969)); edX tells learners that unenrol and re-enrol does not reset progress or attempts, and they must wait for a future session ([edX help](https://support.edx.org/hc/en-us/articles/207249538-If-I-fail-a-course-can-I-retake-it)). | Attempts are counted per `CourseProgress`, so a new run starts at zero by construction, and only staff can trigger it. The attempt-limit spec's per-quiz lock stays a lock, not an auto-restart. The earlier run's attempt count stays on record, so the number of re-writes is countable from the chain. |
| 9 | Deadline wrongly kept, or reset wrongly. Recompletion "period" bugs (period set to 0 by default #122; calculated date wrong), per-group reset period requested (#62). Docebo users edit enrolment dates as a workaround. | Moodle recompletion [issues](https://github.com/danmarsden/moodle-local_recompletion/issues) and [plugin page](https://moodle.org/plugins/local_recompletion). | The deadline clock is `CourseProgress.created_at`, so a new run restarts it by construction. The new registration copies registration-level deadline config, so the rule carries over and only the clock restarts (decided). Reminders, at-risk and pauses must skip a superseded run, otherwise the learner gets reminders for a closed run (the same family as stale-state complaints; inferred). |
| 10 | Re-enrolment or unenrol/re-enrol does nothing, or resumes where the learner was, so staff cannot give a clean retake. | edX help above; TalentLMS notes unenrolling does not reset progress ([help](https://help.talentlms.com/hc/en-us/articles/360014573994-How-to-reset-a-user-s-progress-to-all-courses-at-once)); our own idea.md notes deregister and re-register resumes. | Restart is a distinct, named action, not a side effect of re-registering. Reactivating a superseded registration is refused, so the old run cannot be revived and mixed with the new. |
| 11 | Reset reaches shared state: resetting one training material resets it in other courses that share it; a cohort or group-wide reset hits everyone. | Docebo official note on shared training material ([help](https://help.docebo.com/hc/en-us/articles/360020126719-Resetting-the-completion-of-training-material)). | A restart acts on one learner's registration. For cohort learners it mints an individual registration and closes the run for that learner only, leaving the cohort registration and other members untouched (decided). |
| 12 | Recompletion fires no event, or events the integrator cannot interpret. Moodle requests that recompletion trigger events (#249). Duplicate completion events: no user report found; inferred risk is that a restart emitted as `registration.deactivated` plus `registration.added` looks like a user leaving and rejoining, and may trigger offboarding or onboarding automation. | [Moodle issue list](https://github.com/danmarsden/moodle-local_recompletion/issues). | Single `registration.restarted` event with earlier and new registration ids and the reason; no `registration.added` or `registration.deactivated` (decided). `course.completed` once per run. Spec should state payload ids so an integrator can link runs, and say that consumers keyed on registration id will see a new id (see 13). |
| 13 | Integrations break when the enrolment or course id changes on reset. Canvas reset creates a new course id, breaking links and bookmarks ([Ohio help](https://help.ohio.edu/TDClient/30/Portal/KB/Article/976/Resetting-a-course-in-Canvas)). No enrolment-id integration complaint found for the other platforms; Cornerstone not found. | Canvas only. | Our model also changes the registration id on restart, which is the same hazard in a different place. Avoided by the event carrying both ids, by keeping the learner and course ids stable, and by the `previous_registration` link so an integrator can walk the chain. State in the spec that the registration id is a run id, not a stable learner-course key. |
| 14 | Learners confused about lost progress. | No direct learner-quote found. Weak evidence: edX learners ask whether they can retake and are told they cannot reset progress ([edX help](https://support.edx.org/hc/en-us/articles/207249538-If-I-fail-a-course-can-I-retake-it)). Inferred. | Staff restart is the only trigger (a learner never has progress vanish unprompted). Notify the learner in-app, written for someone who was not there ("Your course X has been restarted"), linking to the course. No learner-facing earlier-run view is built; the notification should say what happened and that the earlier work is kept on record. |
| 15 | Restart state is held in a plugin that lags platform upgrades and needs cron, so compliance reporting breaks on upgrade. | Moodle recompletion needs cron; 5.0 and 5.1 reports of the archive report breaking ([plugin](https://moodle.org/plugins/local_recompletion)). | Restart is synchronous core code (one transaction), not a scheduled job or plugin. Archive data lives in the normal tables, so there is no separate archive schema to migrate or break. |

## Prior-art contrast worth keeping

- Totara keeps history in a thin history table and restores the latest history record on reassignment ([Totara](https://totara.help/docs/resetting-completions), [certifications](https://totara.help/docs/what-are-certifications)). Our chain keeps full rows, so no information is lost in the archive step.
- Moodle recompletion deletes quiz/SCORM data from live tables and copies it to archive tables (plugin page). Our model never moves rows.

## Residual risks the spec should address (what the model does not avoid)

1. Every run-aware reader must be changed or it will show or act on a superseded run. The risk is silent: wrong reminders, wrong matrix cell, wrong export. Candidate list is in idea.md and `research_course_restart.md`. The cohort matrix and cohort report must follow the chain (decided).
2. Unique constraints on registration must still allow a new individual registration alongside a superseded one, and a cohort registration alongside an individual one for the same learner. Confirm the constraint design is explicit.
3. No undo plus a superseded state that refuses reactivation: define the support path for an erroneous restart.
4. Registration id changes per run (row 13): document for integrators.
5. Reports that sum or count learners by registration may double-count a restarted learner unless they filter superseded registrations.
