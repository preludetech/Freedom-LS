# Research: codebase touch points for option C (registration chain)

Scope: what existing code the decided shape touches, reuses or conflicts with. Findings only, read-only pass. Paths are relative to the repo root; line numbers were read in this worktree. This adds to `research_course_restart.md`, which frames option B; where the two disagree, this file is about option C. Terms follow the domain glossary: course progress record, registration, cohort registration, individual registration.

Decided shape (from `answers.md`): one registration = one run. A restart marks the earlier registration superseded (a state separate from `is_active`, recording the successor), mints a new registration linked back to it, copies registration-level deadline config, and fires only `registration.restarted`. For a cohort learner the new registration is an individual one linked to the cohort registration, and the cohort run is closed for that learner only.

## 0. Findings that change the picture (read these first)

1. **There is no CSV import of course registrations.** `learner_management/learner_actions.py:400-700` (`add_learner`, `add_learners`, `ImportLookup`) imports learners and cohort membership only; no registration is created there. `LearnerImport` (`models.py` ~362+) is the only import model. The brief's "CSV import of registrations" has nothing to touch. The only bulk registration paths are the educator bulk actions (`educator_interface/panels/learner/bulk_actions.py:307-364`) and the registration-rules engine (section 8).
2. **No admin registers `LearnerCourseRegistration` or `CohortCourseRegistration`.** There is no `learner_management/admin.py`; the only registration-related admin classes are the deadline-config admins (`deadlines/admin.py:478-501`), the messaging-config admins (`messaging_policy/admin.py:82,96`) and the picker form helpers (`learner_management/admin_forms.py:154-200`). `CourseProgressAdmin` is already read-only (`learner_progress/admin.py:246-247`, `ReadOnlyAdminMixin`). The admin work is therefore: the two registration-config pickers must not offer a superseded registration, and `LearnerRegistrationPickerForm` (`admin_forms.py:162-180`) lists every registration with no filter.
3. **A superseded row left `is_active=True` keeps granting access and is read as live by about two dozen sites.** Every reader tests `is_active=True` (listed in section 3). If the spec keeps superseded and `is_active` independent (as the owner said), each of those must add a "not superseded" test. If instead the restart also sets `is_active=False`, the `post_save` receiver would fire `registration.deactivated` (`learner_progress/signals.py:361-366`), which the owner ruled out; the restart would have to bypass it. This is the spec's biggest design choice and it is not settled by the answers.
4. **The cohort registration cannot carry a per-learner superseded state.** It is shared by the whole cohort (`learner_management/models.py:319-347`). "Closed for this learner only" needs new storage, either a column on the learner's cohort-granted `CourseProgress` (`learner_progress/models.py:127-133`) or a new table keyed by (cohort registration, learner). The owner said the restart supersedes the earlier registration, which is only literally true for an individual registration. Section 4 lists the readers that must see this.
5. **`learner_for_course` ranks cohort over individual** (`learner_management/queries.py:403-445`). After a cohort learner is restarted, the cohort registration is still active, so the resolver returns it, not the new individual registration. Nothing in the existing order makes the chain head win. This breaks the restart unless the resolver is changed (section 3).

## 1. Registration unique constraints

- `unique_learner_course_registration` on (`site`, `learner`, `course`) (`learner_management/models.py:299-304`). `unique_cohort_course_registration` on (`site`, `course`, `cohort`) (`models.py:342-347`).
- For option C only the individual constraint must give way, because a restart mints an individual registration. Cohort registrations are never minted by a restart, so that constraint stays.
- Ways to allow a superseded row (decision for the spec):
  - Make it conditional: `condition=Q(superseded_by__isnull=True)` (or whatever the superseded marker is). Postgres 17 and Django 6 handle a conditional `UniqueConstraint`; the repo already uses one (`deadlines/models.py:111-121`). Pre-existing rows have no marker, so the data migration is a plain `AddField` with null default and a constraint swap; existing migrations are never edited (CLAUDE.md), so this is a new `learner_management/migrations/0013_*`. (Migrations 0001-0012 exist; 0011 added `updated_at`.)
  - Or widen it to include a run key. Option C as decided has no run number, so the conditional form is the natural fit.
- Consequence of two rows per (learner, course): every `get_or_create` / `.get()` / `.first()` keyed on (learner, course) breaks or picks the wrong row:
  - `_ensure_registration` uses `get_or_create(site, learner, course)` (`learner_actions.py:333-338`). After a restart it would raise `MultipleObjectsReturned`. It needs to look only at the chain head. It is called by `register_for_course` (`:303-319`) and `self_register` (`:348-372`). Whether a learner whose registration was restarted can be "registered again" (the head is active already, so `None`) is straightforward; whether re-registering after deactivating the head works is the same as today.
  - `deactivate_registration` filters `(learner, course, is_active=True).first()` (`learner_actions.py:384-386`). It would deactivate the superseded row if that row is still `is_active=True`. It must target the head.
  - `latest_registration` orders `(-is_active, -learner__is_active, -registered_at)` (`learner_management/queries.py:374-400`). With a superseded row still active, the newer row wins by `registered_at`, which happens to be right for a restart, but only by timestamp. A not-superseded filter is more honest than relying on it. Its docstring describes "one per organisation" rows, which is not the case the code enforces (the constraint is per learner, and a learner belongs to one organisation).
  - `LearnerRegistrationsPanel` lists every individual row for the learner (`educator_interface/panels/learner/data_table_panels.py:153-157`), so superseded rows would show as extra "Individual" rows. The same applies to `educator_interface/panels/course/data_tables.py:207` and `:89` (active filter only).
- `registration_rules/evaluation.py:150-199` builds `registered_ids` from every registration row of the course, active or not, and treats any existing row as "belongs to someone else unless a rule made it". The restart's new row has no `RuleRegistration`, so a rule never touches it (good). A rule-owned superseded row, if still `is_active=True`, can still be retracted (`:302-311`), reactivated (`:275-283`), or handed over (`:291-297`); see section 8.

## 2. Row lifecycle: `post_save` receivers fire on the new registration

Minting the new `LearnerCourseRegistration` through the ORM runs these receivers. All assume a "new" registration means a new learner enrolment:

- `learner_progress/signals.py:348-376` `ensure_course_progress_on_learner_registration`: on create, `transaction.on_commit` calls `_ensure_and_announce(..., announce=created, created=created, notify=created)`. `_ensure_and_announce` (`:251-305`) mints the course progress record (`ensure_course_progress_record`) **and** raises the `course.registered` notification unless `self_registered`, **and** fires `registration.added`. The owner wants no `registration.added`. The restart must either suppress the receiver's announcement for this row (a flag on the instance, as `self_registered` does for the notification, or a context marker like registration_rules' `is_engine_write()`), or the record mint must be moved out of the receiver. A staff restart is not a registration, so the learner must also not get "You've been registered for X" (`course.registered`); the restart's own notification replaces it (section 7).
- `_announce_deactivated` (`signals.py:308-322`) runs when `loaded_is_active` True flips to False. Superseding by flipping `is_active` would trigger it. If superseded is a separate column and `is_active` stays True, the receiver does not fire (it keys only on `loaded_is_active`, `LoadedIsActiveMixin` at `models.py:64-127`). That favours the separate-column design the owner chose.
- `course_recommendations/signals.py:52-66`: `clear_on_learner_registration` clears the learner's recommendation for the course when a registration is created active (`_granted`, `:43-49`). Harmless for a restart (the course is already granted) but runs.
- `registration_rules/signals.py:196-225` `detach_rule_on_foreign_is_active_change` (pre_save): deletes the `RuleRegistration` row when a non-engine save flips `is_active`. A restart that does not touch `is_active` on the superseded row leaves rule ownership intact on it.
- `registration_rules/signals.py:419-480` is a `post_save`/`pre_delete` receiver on `LearnerCourseRegistration`; it re-evaluates the learner's rules. Not read in full; the spec should check it does not treat the new unowned row as a reason to re-register or retract.
- `messaging_policy` and the deadlines app key config on the registration, not on a signal (section 6).
- `UpdatedAtInUpdateFieldsMixin` (`models.py:130-153`) adds `updated_at` to any `update_fields` save; the registrations API syncs on `updated_at`, so writing the superseded marker with `update_fields=["superseded_by"]` is picked up by a consumer syncing on `updated_at`. `LearnerCourseRegistrationApiSerializer` (`learner_management/api.py:12-41`) should expose the new fields (superseded marker, `previous_registration_id`) and `read_only_fields = fields` already holds.

## 3. Registration resolution and the readers of `is_active`

The resolution order today:

- `learner_for_course` (`learner_management/queries.py:403-445`): the first access-granting cohort registration of an active member, ordered `(-is_active, -registered_at)`; else `latest_registration`. Used by `course_progress_for` (`learner_progress/queries.py:199`) and `_ensure_player_course_progress` (`learner_interface/views.py:1716-1721`, which writes a record).
- `course_progress_by_course_for` (`learner_progress/queries.py:222-320`) restates the order in bulk: cohort rows first (`:250-275`), then individual rows via `setdefault` (`:277-287`). The comment at `:244-247` says it must match `learner_for_course`; the two must be changed together.
- `course_progress_for` / `course_progress_by_course_for` / `started_course_exists` are the only readers the docstring (`queries.py:184-212`) allows; the docstring also names four exceptions (educator matrix, reports, `recalculate_progress_percentages`, the API).

What option C needs here:

- Rule for "which registration is the learner's current run": the chain head, i.e. the registration that is not superseded and that no other registration supersedes. For a cohort learner with a closed cohort run, the cohort row must be skipped for that learner and the individual head returned. Precedence "cohort beats individual" must become "an individual head linked back to a cohort registration (or any not-superseded successor) beats the cohort registration it closed".
- The cohort branch (`queries.py:413-440`) looks up membership of an active Learner in the cohort; it has no hook for "closed for this learner". The bulk branch (`learner_progress/queries.py:250-275`) is a values_list over the same rows. Both need the same exclusion, ideally from one helper (the existing code already repeats the order in two places).
- Other readers that treat "has an active individual registration" or "is in a cohort with an active cohort registration" as "this registration is the current one":
  - `is_registered_for_course` (`learner_management/utils.py:29-64`), `is_registered_for_course_expression` (`learner_management/queries.py:163-197`), `registered_course_pairs` (`:208-237`), `LEARNER_REGISTRATION_GRANTS_ACCESS` (`:134`): these are access, not run resolution. They keep working because the learner still holds an active registration (the new head, and for a superseded row still `is_active=True`). No change needed for access, but a cohort learner now has two grants.
  - `members_keeping_access`, `other_grants_for`, `_courses_reached`, `courses_losing_access` (`queries.py:636-720`): these treat an active individual registration as keeping access. After a cohort-learner restart, the learner holds an individual registration, so deactivating the cohort registration or removing the learner from the cohort **no longer removes the learner's access to the course** (their individual head keeps it). That is a behaviour change to state in the spec; it is the same state as "registered individually and via a cohort" today, but staff did not choose it. The confirm dialogs (`panels/common/registration_actions.py:111-126`, `:178-200`) name "keeping" learners from these functions, so the wording is affected, and a superseded individual row still `is_active=True` would be counted as keeping access too.
  - `registrations_of` (`queries.py:1075-1089`), `peers_of`, `holds_registration_for_any_expression`: peer and messaging resolution count active registrations; a superseded-but-active row adds a duplicate (distinct is already applied in `peers_through`, so likely harmless).
  - `messaging_policy/policy.py:515-543` resolves each active registration through its own config chain; a learner holding both a superseded and a head registration would be resolved through both, with the old row's `messaging_config` (section 6).
- `registrations_with_progress_for_learner` (`learner_progress/queries.py:340-410`): one entry per active individual registration and per cohort registration, each with its own record. After a restart it would show both the superseded individual row and the head (if still `is_active=True`), and for a cohort learner both the cohort row (with the closed record) and the new individual row. This feeds the learner quick view (`educator_interface/panels/learner/quick_view.py:22-32`) and the Courses card (`panels/learner/panels.py:105-154`, via `visible_registrations_with_progress`).
- Also `learner_interface/utils.py:430,566,1004,1058,1209` and `views.py:335,946,1527,1792,2376,2565`, and `course_access/backends.py:652,702-710`, all go through `course_progress_for` / `course_progress_by_course_for`, so fixing those two functions fixes the learner side. `course_access/backends.py:166` and `:539` mention registration lookups in comments only.

## 4. `ensure_course_progress_record`, the fan-out and the cohort-move carry

- `ensure_course_progress_record` (`learner_progress/utils.py:70-101`) is `get_or_create` on (learner, grant column). With the registration-chain shape each run has its own registration, so the new individual registration gets its own record with no change to this function or to the two `CourseProgress` unique constraints (`learner_progress/models.py:169-177`). This is the main advantage of option C over B and needs no run-aware change. A restart cannot create a record for the superseded registration (it already has one) and the receiver is idempotent.
- Cohort fan-out `ensure_course_progress_records_for_cohort_registration` (`utils.py:104-143`) excludes members who already hold a record for that registration (`:121-125`), so a closed cohort run is never re-minted. `_ensure_for_membership` (`learner_progress/signals.py:325-334`) uses `ensure_course_progress_record`, `get_or_create`, so a learner removed and re-added to the same cohort gets their closed record back, still closed if the closure is stored with the record or keyed to the registration. If the closure is stored in a separate table keyed to (cohort registration, learner), it survives the same way.
- **Cohort-move carry** (`utils.py:164-199`, `signals.py:407-442`): `plan_progress_carry` selects records with `cohort_registration__cohort=source`, active registration, and a destination registration for the same course. It does not know a record is closed. Consequences for a restarted cohort learner moved to another cohort that also holds the course:
  - The closed (superseded) cohort record would be carried to the destination registration (`signals.py:429-431`) or swapped with an existing record (`:432-442`), "the further wins": the closed 100% run could replace the learner's live position under the destination cohort, or the closure marker would be left behind on the source.
  - The destination registration then makes the learner's cohort grant live again (they are in an active cohort holding the course), so, depending on the representation, the learner would silently get a third run, or the carried record would show as the current run again.
  - The spec must decide: skip closed records in `plan_progress_carry`, and decide whether the destination cohort fan-out (`_ensure_for_membership`, `signals.py:394-404`) should mint a fresh run for that learner (a hidden second restart) or leave the learner on the individual head. The individual head would still be resolved first if the resolver rule from section 3 prefers chain heads.
  - `ProgressCarry` and `MoveProgressOutcome` also feed the move confirmation preview (`utils.py:202-216`); the preview should exclude closed records.
- Closed-cohort-run representation, where the data lives and who reads it:
  - Option 1: a nullable column on `CourseProgress`, e.g. a pointer to the successor `LearnerCourseRegistration` (the superseding registration), set only on cohort-granted records. Pros: travels with the record, the record is already the unit of "a run" in the report and API code, no new table. Cons: the carry (above) moves the column with the record to another cohort registration; the marker would then mean "the learner's run under *that* cohort registration is closed", which is wrong for the destination. A single-grant `CourseProgress` row for an individual run is closed by its registration's superseded state, so two mechanisms exist.
  - Option 2: a new table keyed on (cohort registration, learner) holding the successor. Pros: survives the carry as a separate decision, semantically "the cohort run is closed for this learner". Cons: a new model, readers must join it.
  - Either way the grant for the *learner* is read in the places listed in section 3 plus the two reports in section 9; nothing today asks "is this learner's cohort run closed".

## 5. Services and educator actions

- Shape to follow: `deactivate_registration` (`learner_actions.py:375-398`): one `transaction.atomic()`, a `select_for_update` on the learner (`:383`), a state write, `record_learner_entry(learner, action, actor, reason=..., details={...})`. `record_learner_entry` is at `:64-84`; webhooks go through `fire_webhook_event_on_commit` (imported `:36`; `_fire` at `:43-48` merges `learner_webhook_payload`). A `restart_course` service would sit beside it, and would call `record_learner_entry` with a new action `registration.restarted`.
- Refusals today are `ValueError` / typed errors (`CohortUnavailableError`, `learner_actions.py:163-181`; `require_course_open_to` / `CourseNotOpenError` at `learner_management/queries.py:347-366`). Restart refusals needed: no active registration (a restart is only on an active registration), already superseded, learner inactive. `register_for_course` calls `require_course_open_to(course, learner.organisation)` (`:311`); the restart mints a new registration, and `LearnerCourseRegistration.clean()` calls `validate_course_open_to` only on a new or reactivated row (`models.py:306-313`, `_is_new_or_reactivated` at `:34-50`). A restart of a course that has since been closed to the learner's organisation or retired is a spec decision (the registration rules path skips such courses at `registration_rules/evaluation.py:242-245`).
- **Reactivate refuses superseded.** The refusal must be in the service layer, not only the action, because there are four entry points that reactivate:
  1. `LearnerRegistrationReactivation.handle_submit` (`panels/common/registration_actions.py:256-270`) calls `register_for_course`, whose `_ensure_registration` calls `get_or_create`; on a superseded row it would flip `is_active` and fire `registration.reactivated`. `get_row_queryset` (`:231-238`) filters `is_active=False`; a superseded row left `is_active=True` is not offered, but a superseded row with `is_active=False` (previously deactivated before restart cannot happen since restart needs an active row, but a later deactivation of the superseded row can) would be.
  2. `register_for_course` / `self_register` (`learner_actions.py:303-372`).
  3. The bulk action `RegisterForCourseBulkAction` (`panels/learner/bulk_actions.py:330-350`).
  4. The rules engine `_set_is_active(..., True)` (`registration_rules/evaluation.py:275-283`) and Django admin edits of the deadline-config / the registration if exposed.
- Educator learner page actions are classes in `panels/learner/actions.py`; the shared confirm dialogs are `ConfirmAction` subclasses in `panels/common/registration_actions.py`, with `capability = CHANGE_LEARNER_REGISTRATION` (`:67-69`), `row_param = "registration"`, `get_row_queryset`, `get_confirm_context`, `handle_submit`, `ctx.reason`, and `registration_changed_response(learner)` (`:140-144`) that emits `REGISTRATION_CHANGED` and `LEARNER_CHANGED`. The learner page concrete subclasses mix in `EducatorReasonMixin` (`panels/learner/actions.py:329-353`) and scope rows to the learner. `DeactivateRegistrationAction` and `ReactivateRegistrationAction` are listed on `LearnerRegistrationsPanel.get_actions` (`data_table_panels.py:143-147`).
- A restart action has two row kinds. The Registrations card builds `RegistrationRow` for both individual and cohort rows (`data_table_panels.py:103-197`, `is_individual` at `:132-134`). The existing dialogs handle only individual rows; the cohort row has no per-learner action (the cohort-level `CohortRegistrationDeactivation` acts on the whole cohort, `:74-137`). A restart dialog must work from either kind and, for the cohort kind, the row identifies a cohort registration plus the learner on the page, not a row-level object the `row_param` mechanism picks today (the `get_row_queryset` returns one model's queryset; the cohort variant needs the learner from `ctx.instance`).
- The Courses card (`LearnerCoursesPanel`, `panels/learner/panels.py:105-154`) is the other candidate home for a per-course restart button, since it is per course; its actions today are only `RegisterLearnerForCourseAction`. The idea says "the educator interface learner page"; either card works. The "earlier runs" list the idea recommends has no existing component.
- Gate for who can restart: `CHANGE_LEARNER_REGISTRATION` = `freedom_ls_learner_management.change_learnercourseregistration` (`registration_actions.py:67-69`); a cohort learner's restart mints an individual registration, so `add_learnercourseregistration` (`ADD_LEARNER_REGISTRATION`, `:66`) is arguably the capability that matches what is created. A cohort-scoped educator (cohort admin) may hold `change_learnercourseregistration` on the learner via the cohort. This is a decision point for the spec; the idea recommends the change capability.
- Bulk restart is not requested; the learner bulk actions (`bulk_actions.py`) need no change except that `CourseRegistrationBulkAction.get_queryset` (`:307-328`) and the deactivate bulk (`:352+`) filter `LearnerCourseRegistration.objects.filter(...)` which would include superseded rows.

## 6. Registration-level config copied to the new registration

Two config tables hang off the registration and one-to-one by registration:

- Deadlines: `CohortCourseRegistrationDeadlineConfig` (`deadlines/models.py:386-399`, `OneToOneField`) and `LearnerCourseRegistrationDeadlineConfig` (`:402-415`), both `DeadlineConfigFields`. The "registration" layer is the most specific layer in `LayeredDeadlinePolicy.LAYER_ORDER` (`deadlines/policy.py:82-89`); `resolve_for` reads the cohort-registration row for cohort records and the learner-registration row for individual ones (`:136-147`, `:153-168`).
- Messaging: `LearnerCourseRegistrationMessagingConfig` (`messaging_policy/models.py:147-166`) and `CohortCourseRegistrationMessagingConfig` (`:169-186`), one `learner_to_course_peer` flag each. The owner said "registration-level deadline config is copied"; the messaging config is also registration-level and would silently be lost for the new row. State whether it is copied (probably yes, same reasoning).
- Copy semantics:
  - Individual -> individual: copy the `LearnerCourseRegistrationDeadlineConfig` row field by field to the new registration (fields come from `DeadlineConfigFields`; `deadlines/models.py` ~280-340). The clone must write an audit-free copy; the deadlines admin can edit it.
  - **Cohort -> individual loses two layers that are not "registration-level" config.** (a) The cohort layer (`CohortDeadlineConfig`) applies only when `record.cohort_registration_id is not None` (`policy.py:153-161`, `cohort_row` is `None` otherwise), so the restarted learner stops inheriting the cohort's deadline config. (b) `CohortDeadlineOverride` rows (per-item and time-limit due dates for a cohort registration, `deadlines/models.py:77-122`) are read only for cohort-granted records (`deadlines/resolver.py:320-321`, `:386-391`), so the new run loses the cohort's per-item deadlines. The owner's answer covers only "registration-level config", i.e. the cohort registration's `CohortCourseRegistrationDeadlineConfig` row, so a cohort learner restarted today would get the cohort registration's config copied onto an individual registration but would lose the cohort-layer config and the cohort overrides unless the spec says to copy them as well (the overrides have no per-learner equivalent short of `LearnerDeadlineOverride` rows on the new record, `deadlines/models.py:154+`, which are record-level).
  - `CoursePause`, `DeadlineExtension` and `LearnerDeadlineOverride` are per record (CASCADE to `CourseProgress`, `deadlines/models.py:156,437,519`), so they stay with the earlier run and do not carry, which is the intent (clock restart).
  - Deadline start is `CourseProgress.created_at` (`deadlines/resolver.py:153-154`); a new registration's new record sets it to the restart moment (the record is minted by `post_save` on_commit, so `created_at` is the commit time). Fine.
- Deadline readers that iterate records rather than resolve through the learner (reminders, at-risk, pauses in `deadlines-5/6/7`, `spec_dd/1. next/deadlines-*`) key on `CourseProgress`. A superseded run's record has no marker of its own under option C (the marker is on the registration), so those readers must join `learner_registration` / `cohort_registration` to test it. For a cohort-granted closed record the join marker is the section 4 representation. The existing code that already iterates records: `learner_progress/signals.py:209-213` (recalculate on content change; harmless for superseded runs, keeps percentages current), `management/commands/recalculate_progress_percentages.py:29-36`, `deadlines/` admin (`admin.py:95-150`), and the API.
- Admin-side: `CourseProgressAdmin` (`learner_progress/admin.py:246-320`) lists every record; it should show which run and its status, and add a filter. The deadline admins' registration pickers (`learner_management/admin_forms.py:154-200`, `deadlines/admin.py:482-501`) list every registration, so a superseded one is selectable for a config.

## 7. Audit log and webhooks

- Audit registry: `audit_log/actions.py:174+` `FLS_AUDIT_ACTIONS`, a tuple of `AuditAction(code, label, describe, group)`. `registration.*` entries at `:208-225`, group `"Course registrations"`, `describe` = `_describe_course` (`:90-94`). Add `AuditAction("registration.restarted", "Learner course restarted", <describer>, group="Course registrations")`. `AUDIT_ACTION_GROUPS` (`:20-29`) already has the group. A describer would read `details` for the reason, earlier and new registration, and cohort when the restart came through one. The reason goes in `reason` (`record_learner_entry(..., reason=...)`), not `details`.
- `audit_log/README.md:86-99,140-151` is the action table the README keeps in step with the registry (and `audit_log/tests/invariants/test_vocabulary.py:107-145`). That test requires that every `FLS_WEBHOOK_EVENT_TYPES` code is also an audit code with the **same label** (`:117`), every event type has a sample (`:135`), and (`:129`) lists the webhook-only codes allowed. Adding `registration.restarted` as both means the label strings must match exactly.

## 8. Registration rules (a conflict not named in the brief)

`registration_rules` (an optional app) owns `LearnerCourseRegistration` rows through `RuleRegistration` (`registration_rules/models.py:103-130`, OneToOne to the registration, CASCADE).

- The engine register step creates rows by `LearnerCourseRegistration(...).save()` and relies on the unique constraint to skip learners who already hold one (`evaluation.py:246-271`, `except IntegrityError: continue`). With a conditional unique constraint, a restarted learner holds a head, so the constraint still blocks a second active row (as long as the head is not superseded). Good.
- `classify_rule_changes` (`:139-199`): `registered_ids` is every row of the course, so a learner with only a superseded row (not possible: a restart always creates the head) is fine; a learner with a rule-owned superseded row and a manual head: `rows` has two rows for the learner; the owned superseded row, if `is_active=True` and the learner stops matching and has not started (`started_course_exists` is true after any run activity, `learner_progress/queries.py:33-46`; a restart of an untouched run has not started), is **retracted**, flipping `is_active` False and firing `registration.deactivated` for a row that should have been left alone. Equally `reactivate` selects rows with `is_retracted`, which would reactivate a superseded row. So the engine's three writes (register, reactivate, retract) must skip superseded rows, and the superseded row should be detached from the rule (`RuleRegistration` deleted or carried), because the new head is not rule-owned. Whether the head should inherit the rule ownership (so the rule can retract it when the learner stops matching) is a spec decision. The brief's research does not mention registration rules at all.
- `_hand_overs` and the evaluation preview UI read `rule_registration` per learner. Not all read here.

## 9. Reports, cohort pages and the educator learner page

Cohort report (`reports/gather.py`, `reports/indexes.py`):

- `load_registrations(cohort, site_id)` (`indexes.py:215-222`) returns every `CohortCourseRegistration` of the cohort (active and inactive, ordered `-is_active`, course title). `_load_progress_core` (`gather.py:789-799`) builds the roster, catalogue and progress index from these registrations only.
- The progress index is **keyed by learner**: topic rows `course_progress__learner_id` (`indexes.py:378-388`), form rows keyed by `course_attempt__course_progress__learner_id` (`:465-526`), and `fold_topic_progress_rows` unions completions per learner id across all rows (`:391-408`). The query filter `_registration_filter` (`:355-364`) limits rows to the cohort registrations passed in. Therefore a restarted cohort learner's new individual-run rows are **not** in the cohort report at all today; the report would keep showing the closed cohort run (100% or failed) and never the new run. "Follow the chain to the learner's current run" means the cohort report loaders must be given the learner's chain-head individual registrations too (`_registration_ids` already accepts individual registrations: `indexes.py:327-352`), and, because folds key on the learner, the report must pick exactly one record per (learner, course): if both the closed cohort record and the new individual record were passed, the topic fold (`:398-402`) would union their completed topics and the form fold would pick the newest sitting across both (`:489-500`), mixing runs. The current-run selection has to happen before folding (filter by the resolved record ids), not after.
- `_build_course_section` (`gather.py:633-673`) is per cohort registration and its `learner_rows` come from `roster.learner_ids` (`:655`), so a restarted learner's row would need a label ("restart") and a source other than the cohort registration. - `load_first_attempt_ids` (`indexes.py:566-603`) partitions by learner and form across the registrations passed in and treats the earliest completed sitting as the first attempt for the confusion tally. If the new run's rows are added, "first attempt" would remain the earlier run's (correct for "first attempt ever", wrong for "first attempt this run"); decide which.

## 13. Other things worth knowing

- `LoadedIsActiveMixin` (`models.py:64-127`) tracks `loaded_is_active`; a new `superseded` column could not reuse it and needs its own `flipped_*` logic only if receivers need it. Receivers that gate on `instance.is_active` (`learner_progress/signals.py:367-371` returns early for inactive rows) would still mint a record for the new row since it is created active.
- `registered_at` is `auto_now_add` (`models.py:290`): a new registration's `registered_at` is the restart moment; consumers that read "registered_at" (the `registration.added` payload, the API) get a new value per run, which is the intent ("clock restarts").
- Migrations: `learner_management` is at `0012_alter_staffmember_options`; `learner_progress` and `deadlines` (to `0007`) would also migrate if the closure column or table lives there. Cross-app: `learner_management` is lower than `learner_progress` in the app structure (`deadlines/admin.py:390` comment: "belongs to a lower app in docs/app_structure.md"), so a column on `LearnerCourseRegistration` pointing at nothing in `learner_progress` is fine, but a closure marker on `CourseProgress` pointing at `LearnerCourseRegistration` follows the existing FK direction (`learner_progress/models.py:120-126`), while a closure table in `learner_management` keyed on cohort registration and learner would not import `learner_progress`.
- Spec-level choices still open under the decided shape: whether superseded sets `is_active` too (section 0.3); where the cohort-run closure lives (section 4); chain head rule for resolution when a learner also holds a different cohort grant for the course; whether the registration rules head inherits `RuleRegistration` (section 8); whether the cohort-layer deadline config and cohort overrides are carried (section 6); messaging config copy; capability (`change` vs `add`, section 5); a restart of a registration whose course is now retired or closed to the organisation; cohort moves of a restarted learner (section 4); the effect on `members_keeping_access` (section 3).
