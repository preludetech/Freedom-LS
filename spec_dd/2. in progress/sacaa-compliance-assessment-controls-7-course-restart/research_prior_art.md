# Research: prior art for course restart

Question: what has already been tried here or elsewhere for restarting a course while keeping the earlier records, and what happened. Read-only pass over spec docs and code comments (no shell). Owner decisions taken as given (`answers.md`): one registration = one run; restart supersedes the registration and mints a new one linked back (option C); a cohort learner gets a new individual registration linked to the cohort registration; new "superseded" state distinct from `is_active`; deadline config copied; `registration.restarted` webhook only.

## Part 1. Here: earlier decisions this spec must respect

Paths are relative to the repo root.

### 1.1 `better-course-progress-tracking` (done, 2026-08-28) is the main precedent

Folder: `spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/` (`1. spec.md`, `decision.md`, `research_recertification_and_retakes.md`, `research_enrolment_bound_progress_lifecycle.md`).

- **A retake was deliberately deferred, and the spec said what it would take.** `1. spec.md:234-238`: "nothing ever deletes or supersedes a record ... A retake is an explicit action, and it belongs to `spec_dd/1. next/learner-management-actions/`; the schema makes it representable the day it is wanted, with no further migration, because a second registration already means a second record." That folder no longer exists in `1. next` (Glob found nothing), so this spec is the one that picks up the retake. The "second registration means a second record" premise is the one the owner's option C leans on, but it ignores the individual-registration unique constraint (see 1.4).
- **"A second grant is a second enrolment."** `1. spec.md:616-620`: `ensure_course_progress_record` is keyed on `(registration, learner)`, not `(learner, course)`. A learner with a cohort grant and an individual grant holds two records. "What must never happen is one grant re-pointing or resetting another grant's record." Code comment: `freedom_ls/learner_progress/utils.py:77-81`. A restart minting an individual registration for a cohort learner creates exactly this two-record state on purpose, so the new registration must be what resolution returns and the old cohort record must stop resolving.
- **Resolution order: cohort beats individual.** `1. spec.md:704-725`: `course_progress_for` resolves the registration first, "cohort registration wins, otherwise `latest_registration`'s `(-is_active, -registered_at)` tiebreak", then reads the one record. Implemented in `freedom_ls/learner_management/queries.py` (`learner_for_course`, about lines 389-431) and `freedom_ls/learner_progress/queries.py:184-320`. This is the biggest conflict for the cohort case. A restarted cohort learner holds a live cohort registration (shared by the cohort, so it cannot be deactivated or superseded for everyone) and a new individual registration. Under the existing order the cohort one wins and the learner would keep landing on the old run. The spec must either change the order for "a learner whose cohort run was closed for them" or make the resolver skip a cohort registration the learner has been restarted off. This needs an explicit per-learner marker, since the cohort registration itself stays active. The spec also pinned a tiebreak test for two cohorts (`1. spec.md:717-725`); that test must keep passing.
- **Three read paths are exempt from "resolve via `course_progress_for`"**: the educator matrix, the reports app starting from a cohort roster, and `recalculate_progress_percentages` (`1. spec.md:727-733`). "Anything else filtering `CourseProgress` by hand is a defect." These three are the ones that will not follow the resolver automatically. They match answers.md Q12 (the cohort pages must follow the chain).
- **Do nothing on deactivate, membership removal or learner deactivation.** `1. spec.md:215-224` and `decision.md:255-263`. Every system surveyed preserves by default. Only an explicit named operation resets. A restart must be that explicit operation and must not be triggered from membership or registration churn signals.
- **Cohort move carries the record.** `decision.md:283-288` and `1. spec.md:245-253`: re-point or carry, "the further record wins and the other is parked" (`freedom_ls/learner_progress/signals.py:381-417`, `utils.py:164-199`). A restarted individual registration is not tied to a cohort, so a later cohort move must not carry or merge into it. A learner who was restarted and is then moved to another cohort that holds the same course is a new collision (a third record) that no earlier spec considered. Decide who wins.
- **`continued_from` was floated and dropped.** `decision.md:60-65` proposed a `continued_from` self-FK on `CourseProgress` ("escape hatch for a future cohort-move ... column now, no behaviour") and `is_active` on `CourseProgress` with a partial unique constraint `(learner, course) WHERE is_active`. The shipped spec removed both and keyed uniqueness on the registration instead (`1. spec.md:297`, "dropping `CourseProgress.is_active` costs nothing: the flag would have encoded an answer the registrations already carry", line 714). That is a recorded vote for "the registration carries the current-or-not answer", which supports option C, and a recorded vote against a flag on the progress record (option B). The linked-record idea (`continued_from`) was considered and rejected as unneeded then, so a link on the registration is new design.
- **"Do not make the pass the permission gate."** `decision.md:225-243`. Entry is `learner.is_active` and any live grant (`is_registered_for_course`, `freedom_ls/learner_management/utils.py:69-101`). A superseded registration must stop granting entry, or the learner could open the old run from the old registration, and `is_registered_for_course` and the cohort branch must be checked for this. Four models carry `is_active` and the spec warned their meanings could diverge. Adding "superseded" as a fifth state is the same risk, so define it once.
- **Certificates must bind to an immutable completion.** `research_recertification_and_retakes.md:195-200`. No certificate model exists yet, but a superseded run must keep its `completed_time` unchanged.

### 1.2 Registration state: deactivate and reactivate

- `deactivate_registration` keeps records, flips `is_active`, writes `registration.deactivated`; re-registering reactivates the same row and `ensure_course_progress_record` returns the existing record untouched (`freedom_ls/learner_management/learner_actions.py:322-398`; `utils.py:70-101`; recorded in `spec_dd/2. in progress/.../research_course_restart.md` section 2). The new "superseded" state needs "reactivate refuses it" (answers.md Q6). The existing `ReactivateRegistrationAction` (`educator_interface/panels/learner/actions.py:344`), `_ensure_registration` (`get_or_create` plus reactivate, `learner_actions.py:322-345`), the CSV import and the bulk register path all call these and must refuse or route around a superseded row. `_ensure_registration` is the dangerous one: registering a learner again for a course they were restarted on, via `get_or_create(learner, course)`, will find the old superseded row. The unique constraint `unique_learner_course_registration` (`learner_management/models.py:299-304`, (`site`, `learner`, `course`)) is the real blocker for option C. Option C requires changing it to exclude superseded rows (a partial unique constraint) or including a run key, and `_ensure_registration` must be re-keyed to the current row.
- `registration.added` and `registration.deactivated` webhooks exist; answers.md Q13 decides restart sends neither. The notifications-core research noted `registration.added` fires on `created` only and re-registration after deactivation does not announce (`spec_dd/3. done/2026-09-27_00:24_user-communication-1-notifications-core/research_first_events_edge_cases.md:41,78`). So a minted-new registration would, unless suppressed, send "you have been registered" notifications and the `course.registered` event from `LearnerCourseRegistration.save()` (`1. spec.md` "course.registered fires from `.save()`", `decision.md:276-278`). The restart must mint the new registration without those side effects.
- Deadlines: `deadlines/resolver.py:153` uses `CourseProgress.created_at`; the deadline specs (`spec_dd/1. next/deadlines-4-learner-self-pause`, `-5-reminders`, `-6-educator-management`, `-7-educator-at-risk`) all key on `CourseProgress` and registration-level config (`spec_dd/1. next/deadlines/research_deadline_integration_points.md:233` notes re-registration reactivates the same row). A superseded registration's `CourseProgress` must be skipped by reminders and at-risk. Because `CourseProgress` stays attached to the superseded registration, "skip superseded" is a join through the registration, not a flag on the record (a consequence of choosing C over B).
- The Deadlines effort lists "recertification, retakes" as out of scope (`spec_dd/1. next/roadmap.md`, deadlines section; `spec_dd/1. next/learner-interface-features-2-test-out/idea.md:60`, open question 12). The roadmap wording needs reconciling.

### 1.3 Audit log design

`spec_dd/3. done/2026-10-29_08:48_educator-interface-11-audit-log/1. spec.md`:
- One append-only `AuditLogEntry`; an `actor` FK `SET_NULL` plus `actor_label` text kept after user deletion; `details` JSON of ids and labels only; the one allowed update is `update(actor=None)` (lines 10, 90-109). Entries survive deleting the user and keep names (line 68-69).
- Service functions take `actor` and `reason`, call `record_learner_entry(...)` in the same transaction. Actions are a registry (`freedom_ls/audit_log/actions.py`, `registration.*` at about lines 185-199). A restart adds an action there. Because the entry is append-only, details must carry both registration ids and the run number so the chain can be rebuilt from the log alone, even if a row is later force-deleted.
- Force-delete (`spec_dd/3. done/2026-11-26_10:19_sacaa-complianc-deletion-and-declaration-1-force-delete/`) deals with the same `CourseProgress`, `FormProgress` and `QuestionAnswer` rows. If a new self-FK `previous_registration` is `PROTECT`, force-delete of an old run's registration will be blocked by the new one; if `SET_NULL`, the chain breaks silently. The spec must choose, and coordinate with force-delete's deletion order.

### 1.4 What `idea.md` assumed that the owner override changes

- The idea recommended B and said C "keeps one registration and one grant" is not true for C. Option C breaks the constraint `unique_learner_course_registration` on `LearnerCourseRegistration`, which the research (`research_course_restart.md` section 4) lists as C's main cost: `latest_registration`, `_ensure_registration`, `registration.added`, and CSV import "all assume one individual registration per course".
- Cohort case under C: a cohort registration cannot be superseded for one learner, so the owner chose an individual registration "linked back to the cohort registration" and the learner's run closed "for that learner only" (answers.md Q5). That closure has no home on `CohortCourseRegistration`. It needs either a per-learner marker on the `CourseProgress` of the cohort run, or the new registration's back-link being the signal the resolver checks. The idea's B had the marker on the progress record, and the 2026-08 spec rejected that kind of flag. The spec has to pick where "closed for this learner" lives.
- Test-out (`spec_dd/1. next/learner-interface-features-2-test-out/idea.md:55`, open question 7, `research_content_and_completion.md:44,64`) asked: "a new registration outside this work, or a link from the new progress record to prior completed evidence". The owner's choice answers it as "a new registration with a link". That decision must be recorded in the test-out folder too, per the idea's "record the decision in both specs". It also affects renewal: under C the renewal is another registration with a new start reason, and the individual unique constraint must tolerate a chain of arbitrary length, not just one restart.
- Previous cap discussion: `spec_dd/2. in progress/sacaa-compliance-assessment-controls-2-attempt-limits/idea.md:61` counts attempts per `CourseProgress`; a new registration gets a new record, so the attempt count resets naturally.

## Part 2. Elsewhere: how other LMSes did it and what went wrong

Most of this comes from the earlier research in this repo, which cited the URLs below. The Moodle search in this pass found nothing new that confirms a re-firing completion event.

| System | Mechanism | Problems reported |
| --- | --- | --- |
| Moodle `local_recompletion` | Resets completion, optionally archives to separate tables; quiz attempts archived-and-wiped or kept-and-appended | Archive needs custom report sources; old certificate still served after reset; some activities (simple certificate) not cleared; log entries missing after a 4.3.3 upgrade |
| Moodle course reset | Deletes user data "forever" | Records lost; only logs survive |
| Moodle re-enrol | Progress returns on re-enrol | Not a reset; completion date reset to re-enrolment date; cohort sync add/remove cycles lose quiz and SCORM data |
| Totara certification | Resets completion on the recert path, keeps prior cycle in history | Refresher taken before the window opens is recorded but not credited; admins patch data by hand |
| Docebo | Retake renews the enrolment: previous enrolment archived, new one created | Outside the Certification app one completion per (user, course); retakes keep the first completion; "Completed" course beside "Expired" certification; workaround is renaming courses per cycle |
| Absorb | Re-enrol archives old enrolments, resets lesson progress | Reports show only current by default; historic enrolment is a separate report; no retroactive certificate |
| Open edX | `CourseEnrollment.is_active` toggle; state kept | Re-enrolled learners find old state; staff reset attempts by script |
| SCORM | New registration is a deliberate act | A registration silently resolving to a different one is the failure |

Lessons that bear on the owner's option C:
1. **Archived-and-linked beats overwrite-in-place.** Docebo and Absorb mint a new enrolment and keep the old one; that is option C. Moodle's wipe-then-archive produces reporting gaps. Source: `spec_dd/3. done/2026-08-28_14:19_better-course-progress-tracking/research_recertification_and_retakes.md:79-112, 114-140`.
2. **Reports double-count when two runs of one learner and course are not partitioned.** Docebo and Absorb community reports describe "Not Started" archived rows masking "Completed" current ones. Fix used by Absorb: current reports show only the live enrolment, with a separate historic report (`research_recertification_and_retakes.md:202-227`). Here the places to watch: `reports/gather.py:1005`, `reports/indexes.py:291-323` (`_registration_filter`), the progress API (`learner_progress/api.py:55-61` lists every record with `registration_id`), the educator matrix and cohort report. Any count of "learners who completed" must count learners, not runs, and any per-cohort total must not count a restarted cohort learner both under the cohort and individually.
3. **Certificates bound to a live row change after a reset.** Moodle customcert plus recompletion retroactively changes the certificate (customcert issue 484; Moodle forum threads below). Keep `completed_time` and scores on the superseded run immutable and never recompute them. This is already an idea requirement; the lesson is to make it a test.
4. **Compliance status derived separately from enrolment status drifts** (Docebo, "Course Status Not Matching Certification Status"). Define "current run" once (the resolver) and let every reader use it. The 2026-08 spec already warned that anything filtering `CourseProgress` by hand is a defect.
5. **Completion events re-firing.** No documented case of `course.completed` or webhooks firing wrongly was found for recompletion in this pass (a Moodle search returned only a general duplicate completion event bug, MDL-45581, unrelated to reset). The risk is by inference: in FLS `course_finish` fires `course.completed` and the GA4 event once per record (`freedom_ls/learner_interface/views.py:3059-3131`), so a new record fires again, which the idea wants ("once per run"). A downstream consumer that treats `course.completed` as once per learner and course, such as an external HR system, would see a second completion. The webhook payload should carry the registration id and run number so consumers can tell. Treat as an open risk, not an observed failure.
6. **Early or out-of-window runs not credited** (Totara). Does not apply to a manual restart, but the same shape shows in renewals: do not let "which run counts" depend on the window state.

## Part 3. Implications for the spec

- C is consistent with Docebo and Absorb and with the 2026-08 spec's "the registration carries the answer", but it contradicts that spec's assumption that "a second registration already means a second record" works without schema change (it does not for individual registrations). List the constraint, `_ensure_registration`, CSV import, `latest_registration` and the resolver as the touch points.
- The cohort-beats-individual resolver order is the highest-risk piece. State explicitly how a restarted cohort learner resolves, and test it with a learner holding a cohort grant, a superseded run, and a new individual registration.
- Define "superseded" once, and make `is_registered_for_course`, reactivate, `_ensure_registration` and bulk register consistent with it.
- Restart must not fire `registration.added`, `registration.deactivated`, `course.registered` or the registration notification. Answers.md Q13 covers the webhook; the `LearnerCourseRegistration.save()` side effect and in-app notifications are the likely leak.
- Record the decision in `spec_dd/1. next/learner-interface-features-2-test-out/idea.md` (open question 7) and the roadmap wording reconciliation (open question 12).
- Audit entries carry both registration ids, the run position and the reason.
- Force-delete interaction: decide `on_delete` for the back-link, and what a purge of an old registration does to the chain.
